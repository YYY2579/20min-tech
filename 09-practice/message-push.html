二十分钟学透消息推送系统

推送的本质是把一条消息，在正确的时机，经过一条还活着的通道，送到一个还愿意接收的人。这篇讲机制：四层架构怎么分层、国内 Android 为什么必须走厂商通道、目标人群怎么圈、频控与智能推送怎么做、到达率和回执怎么统计、通道故障怎么兜底，以及通道故障无兜底、过度推送被关权限、回执丢失、token 不清理四个经典死法。

先建立一个总认知：推送系统是典型的分层系统——接入层管流量、逻辑层管决策、通道层管投递、数据层管账。工程事故几乎都出在层与层的缝隙里：接入层放进来了超量请求、逻辑层没做频控、通道层故障没切换、数据层回执没落账。每一层各自做好不够，缝隙要有监控兜住。
模块 1

推送系统架构：四层分工

层职责关键技术
接入层接收发送请求，鉴权、限流、参数校验、写入消息队列API 网关、令牌桶限流、Kafka 削峰
逻辑层目标解析（用户→设备）、频控、模板渲染、A/B 分流、发送策略用户画像查询、Redis 计数、规则引擎
通道层对接各推送通道，投递、失败重试、通道切换、回执接收厂商 SDK、APNs、自建长连接、熔断
数据层消息记录、目标快照、设备 token、回执、统计报表MySQL + Kafka + ClickHouse/Doris 类 OLAP

一次推送的完整链路

提交：业务方调用推送 API，携带目标（用户/人群包）、渠道、内容模板、幂等键。接入层校验 + 限流，写入 push_message 与 Kafka
异步消费：发送服务从 Kafka 消费，做目标展开（userId → 在线设备 token 列表）、频控检查、模板渲染（变量填充）
通道选择：按设备平台/厂商选通道（iOS→APNs，Android 小米→小米推送，App 在线→长连接直发）
投递：调通道 SDK 下发；结果（成功/失败/异步回执）写入 push_receipt
回收：客户端曝光/点击上报、厂商回执回调，汇总成到达率/点击率报表
# 为什么必须异步（Kafka 削峰）：
# 一次大促推送 500 万人，同步调用 API 等全部投递完再返回 = 接口超时 + 连接打满
# 正确形态：API 只做校验和落库（毫秒级返回），投递走异步消费，
#           消费进度、失败率、回执全部可观测，失败可重放
# 代价：API 返回"已受理"≠"已送达"，业务方要看的是最终报表，不是接口返回值
接入层的幂等键不能省。业务方网络超时重试、脚本重发都会造成重复推送。幂等键建议用业务含义拼接（如 order_ship_notice_{orderId}），同一订单的发货通知全局只允许一条。接入层按幂等键去重，重复请求直接返回首次的 messageId。
模块 2

通道选型：厂商 / 长连接 / 短信

通道机制到达率时效成本
厂商推送接入小米/华为/OPPO/vivo/FCM 推送服务，系统级通道，无需 App 存活高（Android 现实可达 70%~90%）秒级免费（有频次/条数配额）
APNsApple 官方推送，iOS 唯一选择高秒级免费
自建长连接App 与自建 WebSocket/MQTT 保持连接，服务端直推取决于连接存活（IM 在线可达 95%+）毫秒级高（连接维护成本）
短信走运营商网关最高（几乎必达）秒级~分钟高（约 0.03~0.05 元/条）
邮件SMTP / 企业邮箱通道低（易进垃圾箱）分钟级极低

选型的三个硬约束

  • 国内 Android 没有"App 自己收推送"的选项。系统省电策略会杀后台进程，自建长连接在杀进程的机器上必死；只有接入厂商推送（系统级通道）才有到达率。国内 Android = 厂商推送聚合（自接 4~5 家或走聚合 SDK）。
  • iOS 只有 APNs。自建长连接在 iOS 上同样会被杀，且静默推送（content-available）有频率限制，不能当常规通道。
  • 海外 Android = FCM。Google 服务在海外的系统级地位相当于国内厂商推送之和；国内没有 GMS，FCM 不可用。
# 通道决策表（一条消息怎么选通道）
设备是 iPhone                     → APNs
设备是 Android 且 App 不在前台     → 厂商推送（按机型选小米/华为/OPPO/vivo/FCM）
设备是 Android 且 App 长连接在线   → 长连接直发（毫秒级，省厂商配额）
消息是验证码/支付/风控告警         → 短信兜底（必达优先，成本其次）
消息是营销活动                    → 厂商推送 + 频控，失败不兜底（成本敏感）
海外用户                         → FCM + APNs，短信走国际网关
聚合 SDK（个推/极光/友盟）的取舍：好处是接一家覆盖所有厂商、统一回执格式；代价是数据经过第三方、到达率统计口径受制于人、按量计费。量小（< 日百万）用聚合，量大自建通道层（各家 SDK 接口差异用适配器模式收拢，工作量约 2~3 人月）。金融、强合规场景倾向自建，数据不出境。
模块 3

推送目标模型

目标类型解析方式规模适用
userId 列表查 device_token 表拿该用户全部设备万级交易通知、定向触达
deviceToken直接指定单设备个位数调试、客服代发
alias账号体系内的别名（userId/手机号映射）万级按账号推送，一台设备一个 alias
tag 标签标签系统圈选（如"近 7 天未下单"）十万~百万精细化运营
人群包离线圈好的用户 ID 文件（用户画像系统产出）百万~千万大促、召回活动
广播全量用户千万级公告（慎用，见模块 4 频控）

设备 token 的维护（最容易烂尾的模块）

# token 生命周期管理，三件事必须做：
# 1. 注册：App 启动/登录时上报 (device_id, user_id, platform, vendor, token)
#    按 device_id 做主键（一台设备一行），user_id 可变（换账号登录要改绑）
# 2. 失效：厂商返回 token invalid / APNs 反馈 BadDeviceToken
#    → 标记 status=INVALID，不再投递，定期物理清理
# 3. 多端：一个 user_id 对应多行 token，推送默认全端发
#    （用户已在一端读过的消息，其他端可折叠——去重靠 msg_id）

# 换绑的坑：用户 A 退出登录，用户 B 登录同一台设备
# token 行的 user_id 必须从 A 改成 B，否则 A 的消息会推给 B 的设备
# 这是真实的越权事故类型：没换绑 = 隐私泄露

人群包的工程问题

人群包动辄千万级，直接展开成 userId 列表再逐条查 token，会把逻辑层查爆。正确做法：人群包在画像系统侧就按设备维度圈好（或圈选后物化成 token 列表文件存对象存储），推送侧只读文件流式消费，不在线做"用户→设备"的多对多展开。

模块 4

推送时机与策略

频次控制：三层防线

层级规则实现
全局频控全平台每天推送总量上限（防运营失控）Redis 全局计数，超量拒绝
单用户频控每人每天 ≤ N 条（营销类建议 ≤ 2，交易通知不控）Redis 按 userId 计数，Lua 原子
单用户分类频控营销类 ≤ 2/天，交易类 ≤ 20/天，互不占用key 带 bizType 维度
# Redis + Lua 实现的单用户单类日频控（原子检查 + 计数）
-- KEYS[1]=freq:push:{userId}:{bizType}:{date}, ARGV[1]=limit, ARGV[2]=ttl(秒)
local key   = KEYS[1]
local limit = tonumber(ARGV[1])
local ttl   = tonumber(ARGV[2])
local count = tonumber(redis.call('GET', key) or '0')
if count >= limit then
  return -1                      -- 超限，拒绝
end
redis.call('INCR', key)
if count == 0 then
  redis.call('EXPIRE', key, ttl)   -- 第一次计数时设过期，按天清零
end
return count + 1                  -- 当前是第几条

智能推送：把"什么时候发"变成数据问题

  • 用户活跃时段模型：统计每个用户历史点击推送的时间分布，取最高频时段（如"该用户历史上 78% 的点击发生在 21:00-22:00"）发送，CTR 通常比固定时间发高 30% 以上
  • 分时段发送：大促消息按用户时区分批，别在凌晨三点群发把用户叫醒——那是卸载的经典诱因
  • 合并发送：短时间内同类通知（3 条物流更新）合并为一条，减少打扰
  • 勿扰时段：22:00-08:00 只放行交易类（支付结果、风控告警），营销类全部拦截
频控的粒度要想清楚：按"人"还是按"设备"？按 userId 控——同一用户手机+平板只算 2 条。按设备控会翻倍。按人控的 key 是 userId + bizType + date，且大促期间运营喊"就多发一天"的时候，要有系统和流程说"不"——频控是防卸载的最后闸门，不是可以通融的参数。
模块 5

到达率与送达回执

推送漏斗：每一层都有损耗

环节说明典型损耗原因
提交 → 受理API 收到并落库参数错、限流拒绝、幂等去重
受理 → 厂商接收通道层调厂商接口成功厂商配额满、接口超时、token 格式错
厂商接收 → 到达设备设备收到通知栏消息设备离线、通知栏权限被关、厂商限额丢弃
到达 → 点击用户点开文案不吸引、时机不对（睡觉中）
# 到达率的正确口径（业界常见"数据打架"就打架在口径上）
通道到达率 = 厂商回执 delivered 数 / 厂商接口 success 数
# 注意分母：厂商说"已下发"≠"设备已收到"，部分厂商只有"已送达"回执
# 自建长连接通道：ack 回执 = 客户端收到即回，口径最准
# 曝光点击率 CTR = 点击上报数 / 到达数，用客户端埋点，不用厂商口径

# 为什么不能只用厂商回执：
# 1. 部分厂商不返回 delivered 回执（只有下发成功）
# 2. 用户关了通知栏权限，消息"到达"了但用户看不到——厂商仍算送达
# 3. 所以客户端曝光埋点（onNotificationArrived）才是到达率的金标准，
#    厂商回执用来做通道健康度，两个都要采

回执处理的三种来源

  1. 同步返回：调厂商接口立即知道成功/失败（可判定的错误：token 失效、参数错）
  2. 异步回调：厂商 Webhook 推送送达/点击回执（分钟级延迟，需验签防伪造）
  3. 客户端上报：曝光/点击埋点直连数据层（最准，但依赖 App 版本覆盖率）
回执丢失 = 统计系统变瞎子。厂商 Webhook 丢了（网络抖动、限流、没做幂等重复入库），到达率曲线出现诡异缺口，运营以为推送没效果，加大力度继续发，形成恶性循环。防护：回执接口独立部署不与其他业务混用；按 messageId 幂等落库；Webhook 要有对账补偿（小时级拉一次厂商侧记录兜底）；回执堆积量监控。
模块 6

失败重试、兜底与 A/B 测试

失败分类：不是所有失败都配重试

失败类型例子策略
可重试厂商接口超时、限流 429、服务端 5xx指数退避重试 2~3 次（间隔 1s/10s/60s）
不可重试token 失效、参数非法、内容审核拒绝标记失败并处理 token（失效则清理），重试无意义
通道级故障某厂商整体不可用（503 持续）熔断切换备用通道，不是重试原通道

通道兜底：主备 + 熔断

# 兜底策略矩阵（按消息重要性分级）
P0 验证码/支付/风控    → 短信必达兜底；厂商通道失败立即转短信，不管成本
P1 交易通知（发货/退款）→ 厂商失败重试 3 次 → 长连接在线则直发 → 转短信（预算内）
P2 营销活动            → 厂商失败即丢弃，进补偿队列下次活动顺带发，不兜底

# 熔断器三个状态（按通道维度，不是全局一个）
# CLOSED：正常放行，统计错误率
# OPEN：错误率 > 50% 持续 1 分钟 → 打开，后续请求直接走备用通道，不再试探原通道
# HALF_OPEN：打开 30 秒后放 10% 流量试探，成功率恢复则关闭
# 关键：每个厂商通道独立熔断——小米挂了不该影响华为用户

A/B 测试

  • 分流：按 userId 哈希分桶（如 hash(userId) % 100），保证同一用户始终在同一组，避免"同一用户收到两种文案"
  • 实验对象：文案（长短/emoji/利益点前置）、发送时间（固定 vs 智能时段）、通道优先级（长连接 vs 厂商）
  • 指标：主指标 CTR / 到达率；护栏指标卸载率、关闭通知率（点击率涨但关闭率也涨的实验是失败的）
  • 样本量：每组至少覆盖一个完整推送周期，避免"周末效应"污染结论
A/B 的实验单元是"用户"不是"设备"，也不是"发送批次"。按设备分桶，多设备用户会被分到两组自相矛盾；按批次分桶（这一批发 A、下一批发 B）则文案效果和时间效应混在一起，结论不可信。userId 取模 + 实验期间固定分组，是底线要求。
模块 7

多租户、配额与核心表设计

多租户与配额

维度机制超量处理
数据隔离所有表带 tenant_id，查询强制带条件（或行级安全）漏带 tenant_id = 数据串租户，安全事故
配额管理每租户每日可推送条数（按合同/等级）超额拒绝并通知租户；VIP 可买量
并发控制单租户同时进行的推送任务数上限排队或拒绝，防一个租户打满通道
成本隔离短信等付费通道按租户计账余额不足自动降级为免费通道

核心表设计

-- 1. 推送消息主表（一次推送任务 = 一行）
CREATE TABLE push_message (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id     BIGINT      NOT NULL,                -- 多租户隔离
  msg_uuid      VARCHAR(64) NOT NULL,                -- 全局唯一，回执关联用
  idempotent_key VARCHAR(128),                       -- 业务幂等键，唯一索引
  biz_type      VARCHAR(32) NOT NULL,                -- TRADE / MARKETING / RISK
  target_type   VARCHAR(16) NOT NULL,                -- USER_ID / TAG / CROWD / BROADCAST
  title         VARCHAR(128),
  body          VARCHAR(512) NOT NULL,
  channel       VARCHAR(32),                          -- 期望通道，实际以路由为准
  status        VARCHAR(16) NOT NULL,                -- PENDING/SENDING/DONE/FAILED
  total_cnt     INT DEFAULT 0,                        -- 目标总数（快照）
  plan_time     TIMESTAMP,                            -- 定时发送时间
  created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_idem (tenant_id, idempotent_key),
  KEY idx_tenant_status (tenant_id, status)
) ENGINE=InnoDB;

-- 2. 设备 token 表（一台设备一行，user_id 可变）
CREATE TABLE device_token (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  device_id   VARCHAR(64) NOT NULL,                  -- 设备唯一标识
  user_id     BIGINT,                                -- 可空：未登录设备也能收广播
  tenant_id   BIGINT      NOT NULL,
  platform    VARCHAR(16) NOT NULL,                  -- IOS / ANDROID
  vendor      VARCHAR(16),                           -- XIAOMI/HUAWEI/OPPO/VIVO/FCM
  token       VARCHAR(512) NOT NULL,
  status      VARCHAR(16) DEFAULT 'ACTIVE',          -- ACTIVE / INVALID
  updated_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_device (tenant_id, device_id),
  KEY idx_user (tenant_id, user_id, status)
) ENGINE=InnoDB;

-- 3. 消息-目标关联表（发送实例，一条消息对一台设备的投递记录）
CREATE TABLE push_target (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  msg_id      BIGINT      NOT NULL,
  device_id   VARCHAR(64) NOT NULL,
  channel     VARCHAR(32) NOT NULL,                  -- 实际走的通道
  send_status VARCHAR(16) NOT NULL,                  -- SENT/FAILED/DROPPED
  fail_reason VARCHAR(256),
  KEY idx_msg (msg_id, send_status)
) ENGINE=InnoDB;

-- 4. 回执表（送达/点击，来自厂商回调 + 客户端上报）
CREATE TABLE push_receipt (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  msg_id      BIGINT      NOT NULL,
  device_id   VARCHAR(64) NOT NULL,
  event_type  VARCHAR(16) NOT NULL,                  -- DELIVERED / CLICKED / DISMISSED
  event_time  TIMESTAMP NOT NULL,
  source      VARCHAR(16),                           -- VENDOR / CLIENT
  UNIQUE KEY uk_event (msg_id, device_id, event_type, source)  -- 幂等
) ENGINE=InnoDB;

-- 5. 租户配额表
CREATE TABLE push_quota (
  tenant_id     BIGINT PRIMARY KEY,
  daily_limit   INT NOT NULL,                         -- 每日条数上限
  daily_used    INT DEFAULT 0,
  sms_balance   INT DEFAULT 0,                        -- 短信余额（条）
  reset_date    DATE NOT NULL
) ENGINE=InnoDB;
表设计的三个关键决策：① push_target 按消息分表或分区（单消息目标可达千万级，一张表存全量很快膨胀）；② 所有表带 tenant_id 且查询强制带（建议用 MyBatis 拦截器或 ORM 多租户插件自动注入，别靠人记得）；③ 回执表 uk_event 唯一键防厂商重复回调，ClickHouse/Doris 类 OLAP 承接统计查询，别在 MySQL 上跑到达率聚合。
模块 8

十个线上坑

1
通道整体故障，推送全丢无兜底
某厂商推送服务宕机 2 小时，验证码类消息全部失败没人切换短信。P0/P1 消息必须有主备通道和熔断切换，且切换是自动的，不等人工发现。
2
过度推送被用户关权限、被厂商降权
营销消息一天 5 条，用户关通知栏权限 → 后续连交易通知也收不到；厂商对推送打开率低的 App 限额降级。频控按人按类，营销类严控。
3
回执丢失，到达率统计失真
厂商 Webhook 抖动丢包、接口没做幂等重复入库，曲线出现缺口，运营误判推送无效加大发送量。回执接口独立部署 + 幂等 + 小时级补偿对账。
4
失效 token 不清理，持续浪费配额
卸载用户、恢复出厂设置的设备 token 一直留在表里，每次推送都调一次接口失败一次，白白消耗厂商配额和线程。收到失效回执立即标记 INVALID 并定期清理。
5
单用户无频控，被用户当成骚扰
订单状态每变一次推一条，退款+退货+改址 20 分钟推 8 条。同类通知按 msg_id 折叠、按人按类设上限。
6
人群包千万级，同步展开把逻辑层查垮
API 里同步做 userId→token 展开，接口超时且 DB 连接池打满。人群包必须预物化成设备维度，异步流式消费。
7
多租户隔离没做好，A 的消息推给 B 的用户
查询漏带 tenant_id，或缓存 key 没带租户前缀。全表强制 tenant_id + 缓存 key 带前缀 + 自动化越权测试。
8
短信兜底无预算控制，一夜烧掉几十万
通道故障触发兜底，千万级用户全部转短信，按 0.05 元/条一夜 50 万。兜底必须分级（P0 才转短信）+ 租户余额校验 + 兜底量告警。
9
换设备/换账号不换绑 token，消息推错人
用户 A 退出、B 登录同一台设备，token 行 user_id 还是 A，A 的订单通知推给了 B。登录态变更时必须更新 user_id 绑定关系。
10
大促批量推送峰值把发送服务打挂
运营同时提交 20 个千万级人群包，消费速度跟不上，Kafka 堆积、DB 写入打满。接入层限流 + 发送任务排队 + 按租户并发控制 + 消费进度监控。
自测

六道题

1. 国内 Android 设备的常规推送，为什么必须接入厂商推送通道？
正确答案：系统级通道。国产 ROM 的省电策略会冻结未白名单 App 的后台进程，自建长连接随之断开。厂商推送由系统托管，App 死了消息照样到通知栏。iOS 同理只有 APNs 可靠，海外 Android 则是 FCM。
2. "厂商接口返回成功"能否直接当作"消息已到达设备"？
正确答案：接口成功 ≠ 到达。链路是"接口成功 → 厂商下发 → 设备收到 → 用户看到"，后三段都可能损耗。到达率的金标准是客户端曝光埋点，厂商回执用于通道健康度监控，两者都要采。
3. 推送时收到厂商返回 "token invalid"，正确的处理是？
正确答案：标记失效并停投。token 失效（卸载、恢复出厂设置）是永久性的，重试无意义还浪费配额和线程。同时要更新 device_token.status=INVALID，统计侧要能看到"失效设备占比"这个指标。
4. 关于单用户推送频控，正确的设计是？
正确答案：按人按类计数。同一用户手机+平板应该共享配额，否则多设备用户被双倍打扰。分类计数让交易通知不被营销配额挤占。实现用 Redis + Lua 保证原子性，key 带 userId + bizType + date。
5. 某厂商推送通道持续 503，系统应该怎么应对？
正确答案：熔断 + 切备用通道。持续故障时重试原通道只会让队列堆积；全部暂停会让交易类消息也停摆。正确做法是按通道维度熔断（不影响其他厂商通道），P0/P1 消息按分级走备用通道，P2 营销消息进补偿队列。
6. 多租户推送平台，防止租户间数据串扰最关键的机制是？
正确答案：全表 tenant_id + 框架层强制注入。靠调用方传参等于把正确性寄托在运气上，一个漏传就是数据泄露。用 ORM 多租户插件/拦截器自动注入条件，配合越权自动化测试。物理隔离只适合超大合规场景，成本极高。

# 发送服务核心代码结构（Java，真实分层）
public class PushSendService {
    public void send(Message msg) {
        List<Device> devices = resolveTargets(msg);          // 目标 → 设备列表
        for (Device d : devices) {
            if (!freqLimiter.tryAcquire(d.getUserId(), msg.getBizType())) {
                receipts.add(dropped(d, "FREQ_LIMIT"));   // 频控拦截也要记录
                continue;
            }
            Channel ch = channelRouter.route(d, msg);         // 按设备+消息分级选通道
            SendResult r = ch.send(d, render(msg, d));        // 投递（内部含重试）
            if (r.isRetryable()) { retryQueue.offer(msg, d); }
            if (r.tokenInvalid()) { tokenService.markInvalid(d); }
            receiptRepo.save(r.toReceipt());                  // 所有结果落账，含失败原因
        }
    }
}
