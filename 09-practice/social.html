二十分钟学透社交系统设计

社交系统的技术主线只有一条：关系链怎么存、内容怎么分、互动怎么计数。大 V 热点、计数竞争、关系深查询是三个反复出事的地方，这篇直接讲机制、表结构和坑。

模块 1

社交核心模型：四类实体

所有社交产品拆开都是四类实体，以及它们之间的连接方式。先建立这个骨架，后面所有设计都是往骨架上挂肉。

实体存什么关键特征
用户 user资料、设置、计数器（关注数/粉丝数）读多写极少，可重缓存
关系 followA 是否关注 B、何时关注、分组写扩散的源头，决定内容分发的形状
内容 post正文/图片/视频、可见范围、互动计数读远大于写，热点极度不均（大 V）
互动 interaction点赞、评论、转发、收藏高并发小写，计数竞争重灾区
私信 message2 人会话内的消息序列本质是单聊 IM，可复用 IM 能力

一张图看清连接关系（文字版）

user ──follow──> user        （关系链，社交的骨架）
user ──publish──> post       （内容，1 对 N）
user ──like/comment/share──> post   （互动，N 对 N）
user ──send──> message ──> user     （私信，2 人会话）

核心矛盾：关系是"多对多图"，内容是"按作者查"，互动是"按内容计数"。
三种查询模式完全不同，所以存储选型也完全不同 —— 这是本篇的主线。
设计社交系统先问三个问题：① 关系是单向还是双向（决定 follow 表结构和 Timeline 模型）；② 内容分发是推还是拉（决定写扩散的规模）；③ 互动计数允许多少秒的不一致（决定计数走库还是走缓存）。这三个答案定了，架构就出来了。
模块 2

关注模型：单向、双向与密友

"关注"不是一个功能，是一组权限模型。选错模型，后面的 Timeline 和隐私体系都要返工。

模型语义技术实现
单向关注A 关注 B，B 不需要同意。微博/Twitter/B 站一条 follow 记录即可，立即生效
双向关注互为好友。早期 QQ/微信/朋友圈申请 → 同意 → 写两条记录；拒绝不写
密友关注之上的白名单，内容只给密友看follow 表加 is_close 标记，或独立白名单表
特别关注内容实时推送优先、Timeline 置顶follow 表加 is_special 标记，推送走优先队列
分组/圈子关注列表分组管理，可按组看内容follow 表加 group_id，或独立分组表

表设计上的差异

-- 单向模型：一条记录就是全部
INSERT INTO follow(user_id, target_id) VALUES (100, 200);

-- 双向模型：申请/同意状态机（多了 status 与确认时间）
-- status: 0 待同意  1 已关注  2 已拒绝  3 已拉黑
INSERT INTO follow(user_id, target_id, status) VALUES (100, 200, 0);
UPDATE follow SET status = 1 WHERE user_id = 100 AND target_id = 200;
-- 同意时双向写入（200 也关注 100），保证双向查询都是 O(1)

-- 密友/特别关注：加标记位，不要建新表
ALTER TABLE follow ADD COLUMN is_close TINYINT DEFAULT 0;   -- 密友
ALTER TABLE follow ADD COLUMN is_special TINYINT DEFAULT 0; -- 特别关注
双向模型的性能陷阱：每次关注/取关要维护两条记录和两个计数器，且"申请-同意"跨了时间，中间状态（待同意）要考虑取消、过期、被拒绝后再申请。工程上把关注做成异步状态机：请求先写待处理记录，同意后发消息给申请方，由申请方完成双向写入。
模块 3

关系链存储：关系表 vs 图数据库

关系查询有三类：关注列表、粉丝列表、共同关注。前两类关系表轻松搞定，第三类（以及二度人脉）才是选型分水岭。

方案对比

方案代表优势劣势
关系表MySQL / TiDB简单可靠、运维成熟、可事务；关注/粉丝列表 O(1) 索引查询共同关注靠 JOIN，大表慢；多跳遍历行数爆炸
图数据库Neo4j、TAO、JanusGraph多跳遍历、共同关注原生支持（一跳聚合）运维重、生态小、大厂（如 Meta TAO）自建门槛高
混合架构
（主流）		MySQL 关系 + Redis 计数 + 离线图计算各取所长：关系存表、计数走缓存、共同关注异步预计算组件多，一致性靠最终一致

核心表 DDL

-- 关注关系表：整个社交系统的骨架
CREATE TABLE follow (
  user_id    BIGINT       NOT NULL                COMMENT '关注方',
  target_id  BIGINT       NOT NULL                COMMENT '被关注方',
  status     TINYINT      DEFAULT 1               COMMENT '1 关注 0 已取消',
  is_close   TINYINT      DEFAULT 0               COMMENT '密友标记',
  created_at TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (user_id, target_id),
  KEY idx_target_time (target_id, created_at)     -- 反查粉丝列表
) COMMENT '关注关系';

-- 查询我关注的人（分页）：
SELECT target_id, created_at FROM follow
WHERE user_id = 100 AND status = 1
ORDER BY created_at DESC LIMIT 20 OFFSET 0;

-- 查询我的粉丝（分页）：
SELECT user_id, created_at FROM follow
WHERE target_id = 100 AND status = 1
ORDER BY created_at DESC LIMIT 20 OFFSET 0;

-- 计数单独放 Redis，不要 COUNT(*) 全表扫
INCR follow:count:100        # 我的关注数
INCR fans:count:200         # 200 的粉丝数

共同关注：三种实现的代价

-- 方案一：实时 SQL JOIN（小号可行）
SELECT f1.target_id
FROM follow f1 JOIN follow f2 ON f1.target_id = f2.target_id
WHERE f1.user_id = 100 AND f2.user_id = 200
LIMIT 20;

-- 代价：以"关注数较小的一方"驱动。
-- 双方各关注 200 人 → 最多 200 次索引探测，可接受；
-- 一方关注 5000 人 → 5000 次探测，慢查询。

-- 方案二：Redis Set 交集（关注列表已缓存的场景）
SINTER following:100 following:200

-- 方案三：异步预计算（主流）
# 定时任务/消息触发：把共同关注算好写缓存 key = mutual:100:200，TTL 1 小时
# 用户关注新人时，增量反查对方关注列表与本列表取交集，只更新差量

-- 图数据库写法（Neo4j Cypher）：
# MATCH (a:User {id:100})-[:FOLLOW]->(x)<-[:FOLLOW]-(b:User {id:200})
# RETURN x LIMIT 20
# 一跳遍历，但 Neo4j 在千亿边规模下的运维成本极高，多数团队用混合方案

二度人脉与深查询的爆炸

# 平均每人关注 200 人，遍历规模：
一跳（关注的人）      = 200
两跳（二度人脉）      = 200 × 200 = 4 万
三跳                  = 4 万 × 200 = 800 万

# 工程红线：
# ① 深度硬限制 2~3 跳，超过直接拒绝或降级为抽样
# ② 遍历必须设超时（如 200ms）和结果上限（如 1000 节点）
# ③ "可能认识的人"用离线批量算（每天一次），不要在线实时遍历
模块 4

内容分发：Timeline 的三种模式

Timeline 是社交系统的吞吐命门。核心决策：发帖时把内容推进粉丝收件箱（推），还是读取时聚合关注对象的内容（拉）。

模式读 / 写成本延迟致命问题
推 push读 O(1)
写 O(粉丝数)		低大 V 发帖 = fanout 爆炸。1000 万粉 = 1000 万次收件箱写
拉 pull读 O(关注数)
写 O(1)		中关注 2000 人时聚合超时；读路径压力大
推拉结合
（主流）		大部分 O(1)低实现复杂，要维护两套路径

推模式：写扩散

# 发帖后的异步 fanout（关键：异步 + 分片 + 削峰）
用户发帖 ──> 写 post 表 ──> 发 MQ 消息 ──> fanout worker 消费
                                        │
        for 粉丝 in 粉丝列表(按 uid 范围分片, 每片 1000):
            写 timeline_inbox(粉丝, post_id, 时间戳)
            Redis: ZADD inbox:{粉丝} {时间戳} {post_id}

# 收件箱表（每用户只保留最近 500~1000 条）
CREATE TABLE timeline_inbox (
  user_id    BIGINT NOT NULL,
  post_id    BIGINT NOT NULL,
  author_id  BIGINT NOT NULL,
  created_at BIGINT NOT NULL COMMENT '毫秒时间戳',
  PRIMARY KEY (user_id, created_at, post_id)
);

# 读 Timeline：一次索引扫描拿最新 20 条，再批量查 post 详情（避免 N+1）
SELECT post_id, author_id, created_at FROM timeline_inbox
WHERE user_id = 100 ORDER BY created_at DESC LIMIT 20;

拉模式：读扩散

# 读时聚合关注对象的最新内容
SELECT id, user_id, content, created_at FROM post
WHERE user_id IN (我关注的 200 个 uid)
ORDER BY created_at DESC LIMIT 20;

# 问题：IN 列表 200 个 uid 时 MySQL 可用，2000 个就危险；
# 优化：关注列表走缓存；或改为主键范围查询 + 应用层归并；
# 再激进：每个关注对象最近 20 条各自缓存，读时内存归并排序。

推拉结合：业界标准答案

普通用户（粉丝 < 阈值）走推：发帖时写所有粉丝收件箱，读 O(1)。阈值通常取 1000~10000
大 V（粉丝 ≥ 阈值）走拉：发帖只写自己的 post 表，读 Timeline 时额外拉取"关注的大 V 最新 N 条"，与收件箱归并
大 V 列表单独缓存：每个用户维护"我关注的大 V"列表（通常 < 100 人），读时一次聚合，成本可控
未读水位：每用户存 last_read 游标（时间戳或 seq），下拉时只取更新的，避免重复读
纯推模式的经典事故：某千万粉大 V 深夜发帖，fanout worker 瞬间产生 1000 万次收件箱写，Redis 主库带宽打满、从库延迟飙升，全站 Timeline 读取超时。修复方案就是推拉结合 + fanout 分片限速。大 V 的判断必须在架构期做，不能等出事再加。
收件箱清理策略：每用户 inbox 保留最近 500~1000 条即可（没人翻到一年前）。超出的异步删除，Redis ZSet 用 ZREMRANGEBYRANK inbox:100 0 -1001 截断。永远不要给 inbox 设"永久保留"。
模块 5

互动计数架构：点赞、评论、转发

计数是社交系统里写最频繁、竞争最激烈的数据。核心矛盾：热点内容的计数竞争和读放大的成本。

三个典型错误

-- 错误一：读出来 +1 再写回（非原子，并发少计）
int n = SELECT like_count FROM post WHERE id = 100;
UPDATE post SET like_count = n + 1 WHERE id = 100;

-- 错误二：直接 UPDATE ... = ... + 1（原子，但热点内容行锁串行化）
UPDATE post SET like_count = like_count + 1 WHERE id = 100;
# 热点内容几千 TPS 打同一行，行锁排队，整表写入变慢

-- 错误三：每次都 COUNT(*) 实时算
SELECT COUNT(*) FROM post_like WHERE post_id = 100;  # 百万级点赞直接超时

正确架构：Redis 原子计数 + 异步落库

# 写路径（点赞）：
SADD liked:100 88482391            # 去重：已点过返回 0，直接拒绝
INCR like:count:100               # 原子 +1，微秒级返回
发布 LikeEvent 到 MQ ──> 消费方每秒批量合并 ──> UPDATE post SET like_count = n

# 读路径：
GET like:count:100                # 直接读 Redis，不打库
Redis 未命中时回源数据库并回填缓存

# 取消点赞：
SREM liked:100 88482391
DECR like:count:100

计数分片：百万级点赞的热点解

# 单个计数器仍可能成为热点（爆款内容 10 万+ TPS）
# 分 16 个槽，写时随机落一个槽，读时求和：
INCR like:count:100:7              # slot = hash(uid) % 16
SUM = Σ GET like:count:100:0 .. 15   # 读 16 次，Pipeline 一次网络往返

# 落库时同样分段累加，最后合并为一行；
# 用户侧感知：点赞数本身允许秒级不一致（用户看不出 100 万和 100 万 +5 的差别）

最终一致的兜底

问题解法
Redis 重启丢计数MQ 消费方定时（每分钟）把增量落库；启动时从库预热回填
落库延迟导致数字回跳落库用"覆盖写"（取 Redis 快照值），不要用累加
取消点赞的竞态先 SREM 成功再 DECR，顺序保证；或改用"事件溯源 + 重放"
前端重复点击按钮级防抖 + 乐观更新（先 +1 渲染，失败回滚）
评论/转发的计数比点赞更重：它们是"内容型互动"，本身要建表、要走审核、要触发通知。计数只是附属。设计时把"互动"分成两类：轻互动（点赞收藏，只计数）+ 重互动（评论转发，写内容），两类走不同链路，别混在一个表里。
模块 6

私信：复用 IM 能力

社交私信本质是2 人单聊，不需要自研消息系统。复用 IM 能力的三个关键点：会话模型、seq 对齐、已读机制。

会话与消息模型

# 会话 ID 生成：两个 uid 拼接，保证双向唯一且无状态可算
conv_id = min(a, b) + "_" + max(a, b)      # 如 100_200

-- 会话表
CREATE TABLE dm_conversation (
  conv_id      VARCHAR(32) PRIMARY KEY,
  user_a       BIGINT NOT NULL,
  user_b       BIGINT NOT NULL,
  last_seq     BIGINT DEFAULT 0,           -- 最新消息 seq
  updated_at   TIMESTAMP
);

-- 消息表（按 conv_id 分库分表，seq 会话内自增）
CREATE TABLE dm_message (
  conv_id    VARCHAR(32) NOT NULL,
  seq        BIGINT       NOT NULL,        -- 会话内自增，不是全局消息 ID
  sender_id  BIGINT       NOT NULL,
  msg_type   TINYINT      NOT NULL,        -- 1 文本 2 图片 3 语音 4 视频
  content    TEXT,                          -- 文本直接存；媒体存 URL
  status     TINYINT      DEFAULT 0,        -- 0 正常 1 已撤回 2 已焚
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (conv_id, seq)
);

-- 收件箱（每用户视角：未读、最近会话）
CREATE TABLE dm_inbox (
  user_id      BIGINT NOT NULL,
  conv_id      VARCHAR(32) NOT NULL,
  last_read_seq BIGINT DEFAULT 0,           -- 已读水位
  unread       INT DEFAULT 0,
  PRIMARY KEY (user_id, conv_id)
);

seq 机制：IM 的心脏

  • 会话内 seq 自增（Redis INCR），作为消息唯一标识和排序依据。全局消息 ID 会引入分片问题，会话内 seq 天然有序
  • 客户端对齐：收到 seq=105，说明 104 之前都该有；缺了就拿 last_seq 向服务端补拉
  • 断线重连：客户端上报 last_seq，服务端从该点续传，不重发历史
  • 未读计算：unread = last_seq - last_read_seq，无需逐条计数

与陌生人社交的风控差异

场景策略
陌生人首条私信先审后发：内容过反垃圾才投递；新注册/低信用用户每日私信上限（如 20 条）
未回复轰炸对方未回复前最多发 1~2 条，之后的进"折叠区"不通知
已读回执双向开关。关闭时不更新 last_read_seq 的对外可见性
离线推送走厂商通道（APNs / FCM / 各安卓厂商），内容脱敏（"你有一条新消息"）
模块 7

反垃圾与关系风控

社交的反垃圾是双线作战：内容线（发什么）+ 关系线（和谁连接）。多数团队只做内容线，关系线失守会被薅成骗子的温床。

内容审核链路

用户发布 ──> 实时机审（< 100ms） ──> 命中?
                    │
        ┌───────────┴───────────┐
       否                    是/不确定
        │                     │
   直接发布              先发后审 或 先审后发
                              │
                    ┌─────────┴─────────┐
                  人审队列（按优先级）  自动处置（删除/限流/禁言）
层手段典型参数
敏感词DFA/Trie 树匹配，支持变体（拼音、拆字、谐音）词库百万级，匹配耗时 < 5 ms
文本分类预训练模型（BERT 类）判违规类别GPU 推理 10~30 ms/条
图片/视频OCR 抽文字 + 分类模型；视频抽帧（每 2 秒 1 帧）抽帧 5~10 张/视频
人审机审不确定（置信度 0.3~0.8）进队列队列延迟 < 5 分钟；高危秒级

关系风控：查"连接行为"

风险识别手段处置
批量关注速率检测：1 分钟关注 > 30 人、每天 > 500 人即异常限流、验证码、关系链降级（隐藏）
僵尸粉特征：无头像、无内容、关注/粉丝比 > 50、注册时间集中批量标记、不计入粉丝数
机器注册设备指纹 + IP 聚类：同设备/同网段批量注册注册环节拦截、短信/人验升级
垃圾私信相同内容高频群发、含外链/联系方式先审后发、折叠、封号
ShadowBan（影子封禁）是社交产品的核心技术。不告诉用户他被限制了，只是他的内容/关注不再分发给别人。这样骗子无法感知、无法快速换号重试，而正常用户完全无感。实现上就是在分发链路加一个"发布者信用分"过滤，不在前端暴露。
模块 8

隐私与容量估算

隐私功能的技术本质是读路径上的可见性过滤；容量估算的方法论是从 DAU 推导读写 QPS 和存储。两个都给你完整过程。

隐私三件套的实现

# 1. 拉黑：双向即时生效，缓存必须双删
写 block 表(user_id, target_id) ──> 删双方关系缓存
                                    ──> 解除关注关系（双向）
                                    ──> 内容分发链路加黑名单过滤
# 坑：只删库不删缓存 → 拉黑后对方内容仍可见几分钟。必须"改库 + 删缓存 + 延迟双删"

# 2. 可见范围：读时校验，不要靠写时隔离
post.visibility: 0 公开 | 1 粉丝可见 | 2 密友可见 | 3 仅自己
读内容时: 校验 关注关系 + is_close + 黑名单，三个条件都过才返回

# 3. 阅后即焚：物理删除，不留任何副本
消息 status = 2（已焚）+ TTL 到点物理 DELETE
媒体文件：对象存储设 lifecycle 规则自动删除
# 红线：不进缓存、不进 binlog 备份、不做离线归档。只"标记删除"等于没焚

容量估算（完整过程）

# 假设条件：DAU 500 万；人均关注 200；5% 日活用户发帖；
#           每人每天刷 Timeline 20 次，每次 20 条；发帖粉丝平均 200

# ① 日发帖量
500 万 × 5% = 25 万帖/日 ≈ 2.9 帖/秒（平均），峰值按 3 倍 ≈ 9 帖/秒

# ② 推模式收件箱写（假设 90% 是普通用户，走推）
25 万 × 90% × 200 粉丝 = 4500 万次写/日 ≈ 520 TPS，峰值 ×3 ≈ 1560 TPS

# ③ Timeline 读
500 万 × 20 次 × 20 条 = 20 亿条/日
QPS = 20 亿 ÷ 86400 ≈ 2.3 万 QPS（平均），峰值 ×3 ≈ 7 万 QPS
# 结论：读远大于写，inbox 用 Redis ZSet 缓存，DB 只做持久化

# ④ 互动写（点赞/评论/转发）
# 假设 30% 帖子被点赞，人均点 10 个赞/日：
500 万 × 10 = 5000 万赞/日 ≈ 580 TPS，峰值 ×3 ≈ 1740 TPS
# 全部走 Redis INCR，落库异步合并

# ⑤ 存储（只算增量，不含媒体）
帖子内容：25 万 × 2KB = 500 MB/日
收件箱索引：4500 万 × 32B = 1.4 GB/日
Redis 收件箱缓存：只缓存活跃用户（近 7 天登录，按 30% 算）
  150 万用户 × 500 条 × 32B ≈ 24 GB（常驻内存）
关系表：日增关注关系按 DAU×5% = 25 万行/日 ≈ 7.5 GB/年

# ⑥ 私信（假设 10% DAU 每天发 10 条）
500 万 × 10% × 10 = 500 万条/日 ≈ 58 TPS，峰值 ×3 ≈ 174 TPS
消息表按 conv_id 分 1024 张表，单表日增 5000 行
容量估算的三条经验：① 峰值按平均 3 倍估（晚高峰、热点事件可能到 10 倍，单独评估）；② 读永远比写多 1~2 个数量级，缓存优先保读路径；③ 存储算增量不算存量，但必须算 5 年存量——25 万帖/日 × 365 × 5 = 4.5 亿帖，单表 5 亿行就该分表了。
模块 9

十个线上坑

1
点赞用"查出来 +1 再写回"
并发下必少计，且超卖的点赞数永远对不上。用 Redis INCR 原子操作，落库用覆盖写不用累加。
2
热点内容计数行锁竞争
爆款内容几千 TPS 打同一行 UPDATE，行锁排队拖垮整表。计数必须外置到 Redis；极端热点用 16 槽分片。
3
纯推模式遇上大 V 发帖
1000 万粉 = 1000 万次收件箱写，Redis 带宽瞬间打满，全站 Timeline 超时。必须推拉结合：粉丝超阈值走拉。
4
拉模式关注列表过大
用户关注 5000 人，IN 列表爆炸，聚合查询超时。关注列表缓存 + 内存归并；超 2000 关注强制部分转推。
5
共同关注实时 JOIN 大表
一方关注 5000+ 人时，JOIN 扫描几千行，慢查询。用"小号驱动 + 结果上限 + 异步预计算缓存"。
6
关系链深查询无限制
三度人脉 = 800 万节点遍历，直接拖垮库。深度硬限制 2~3 跳、设超时和结果上限、可能认识的人离线算。
7
阅后即焚只做标记删除
数据进缓存、binlog、离线备份，永久可恢复。必须物理删除 + TTL + 对象存储 lifecycle，且不进备份链路。
8
拉黑不删缓存，内容残留
拉黑后对方内容还可见几分钟，投诉重灾区。拉黑要"改库 + 删缓存 + 延迟双删"，分发链路加黑名单过滤。
9
私信用全局消息 ID 当 seq
分库分表后全局 ID 乱序，客户端按 seq 补拉全乱。必须用会话内自增 seq，全局 ID 只做寻址。
10
计数缓存无兜底，重启全归零
Redis 重启丢失全部计数，点赞数显示 0。必须定时（每分钟）落库 + 启动回填，接受秒级不一致。
自测

六道题

1. 一个 1000 万粉丝的大 V 发帖，纯推模式会发生什么？
正确答案：1000 万次 fanout 写。推模式的写成本是 O(粉丝数)，大 V 发帖就是写扩散事故。解法是推拉结合：粉丝数超阈值（如 5000）的用户走拉模式，读时聚合。
2. 计算"我和某人的共同关注"，最高效稳妥的做法是？
正确答案：小号驱动 + 预计算缓存。JOIN 的代价取决于关注数大的一方，大 V 参与时实时 JOIN 会慢查询。工程主流是混合：小号实时算、热点组合异步预计算 + 缓存，图数据库适合多跳遍历但运维重。
3. 高并发下的点赞计数，正确的架构是？
正确答案：Redis 计数 + 异步落库。直接 UPDATE 有热点行锁竞争；COUNT(*) 在百万级点赞上直接超时。配套：SADD 去重防重复点赞、定时落库兜底、落库用覆盖写不用累加。
4. 推拉结合的 Timeline 中，大 V 的内容走哪条路径？
正确答案：拉。大 V 发帖只写自己的 post 表；粉丝读 Timeline 时，把收件箱内容与"关注的大 V 最新 N 条"归并。这样大 V 发帖成本 O(1)，读端只增加一次可控的聚合。
5. 实现"阅后即焚"，技术上的关键要求是？
正确答案：物理删除 + 全链路不留副本。只标记删除的话，数据仍在缓存、binlog、备份里，等于没焚。媒体文件要用对象存储 lifecycle 自动删，消息表设 TTL 物理 DELETE。
6. 关系链存储的业界主流选型是？
正确答案：混合架构。关系本身用关系表（关注/粉丝列表 O(1)），计数走 Redis，共同关注和二度人脉异步预计算。图数据库在多跳遍历上有优势但运维成本高，适合已有图基础设施的团队。
