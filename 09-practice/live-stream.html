二十分钟学透直播系统架构

直播的难点不在"把流推上去"，而在低延迟、百万级并发分发、成本控制和分钟级容灾。这篇讲端到端链路、四种协议的真实延迟账、CDN 分发机制、弹幕消息架构和带宽成本怎么算。

模块 1

直播核心链路：从摄像头到屏幕

一次直播经过五个环节，每一环都贡献延迟。先把链路背下来，后面所有优化都是针对其中某一环。

链路全景

① 主播端采集编码      ② 推流上行        ③ 服务端处理        ④ CDN 分发       ⑤ 播放器
摄像头 / OBS ────────> 推流节点 ingest ────────> 源站 + 转码集群 ────────> 边缘节点 ────────> 观众播放器
  H.264 / AAC           RTMP 或 SRT           转码 / 时移 / 录制       HTTP-FLV / HLS    解码渲染

端到端延迟预算（以 720p、30fps 为例）

环节耗时说明
采集 + 编码30~100 msOBS 用 x264 veryfast 或硬编（NVENC/QSV/VideoToolbox）。B 帧会增加延迟，直播一般关 B 帧
推流上行80~500 ms取决于主播网络 RTT 与抖动。跨网、4G/5G 弱网时显著变大，这是 RTMP/SRT 的重传代价
服务端处理100~1000 ms不转码只透传约 100 ms；走转码集群再加 300~1000 ms（解码 + 编码 + 推 CDN）
CDN 分发50~300 ms边缘命中时只算最后一跳；未命中回源则再加 200~500 ms
播放器缓冲1000~2000 ms为了抗抖动主动攒的数据。这是延迟的大头，也是可调节项
合计 HTTP-FLV1.5~4 sPC 直播主流方案
合计 HLS6~10 s分片机制导致，详见模块 2

一条真实的推流命令

# ffmpeg 推一路 720p 直播流（参数逐项解释见下）
ffmpeg -re -i input.mp4 \
  -c:v libx264 -preset veryfast -tune zerolatency \
  -b:v 2500k -maxrate 2500k -bufsize 5000k \
  -g 60 -keyint_min 60 -sc_threshold 0 \
  -c:a aac -b:a 128k -ar 44100 \
  -f flv rtmp://push.live.example.com/live/abc123
参数作用
-tune zerolatency关闭 B 帧、重排等增加延迟的编码选项，延迟换画质
-g 60 -keyint_min 60GOP 固定 60 帧 = 2 秒（30fps）。服务端切片和转码都依赖规律的关键帧
-sc_threshold 0禁止场景切换时自动插入关键帧，避免 GOP 大小不均匀
-bufsize 5000kCBR 缓冲区，通常取 2 倍码率。太小会花屏，太大延迟高
-re按真实速度读文件，模拟直播（不加会瞬间推完）
-f flv rtmp://...以 FLV 封装走 RTMP 推流，1935 端口
OBS 里最容易错的一项：关键帧间隔。必须设为 2 秒（或 1 秒），不能选"自动"。HLS 切片、转码对齐、时移回放全都依赖 GOP 边界。OBS 默认不固定关键帧，会导致服务端切出的 ts 分片以非关键帧开头，播放端直接花屏。
模块 2

五种协议：延迟、封装与适用场景

选协议就是选延迟。先看账，再讲故事。

协议典型延迟承载方式主要用途
RTMP1~3 sTCP 长连接（1935），FLV 消息块推流（主播 → 服务端）。Flash 已死，但推流生态仍是最广
HTTP-FLV1~3 sHTTP 长连接，顺序拉取 FLV tag拉流（PC 直播播放端主力，可完整走 CDN）
HLS5~10 s
（LL-HLS ~2 s）		HTTP 短连接，m3u8 索引 + ts/fMP4 分片拉流（移动端、海量观众、Apple 生态唯一解）
WebRTC200~500 msUDP，SRTP 加密，RTP 媒体包连麦、超低延迟互动、云游戏
SRT1~3 sUDP + 应用层 ARQ 重传弱网上行（户外直播、跨地区贡献）

HLS 为什么慢：看一个真实的 m3u8

# stream.m3u8 实际内容
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:1024
#EXTINF:2.000,
seg_1024.ts
#EXTINF:2.000,
seg_1025.ts
#EXTINF:2.000,
seg_1026.ts

# 播放器逻辑：拿到列表时最后一片可能还没写完，通常要等"3 个分片"才起播
# 延迟 ≈ TARGETDURATION × 分片数 = 2s × 3 = 6s，再加网络与缓冲

# 降低延迟的三个旋钮：
hls_time 1            # 分片时长 2s → 1s
hls_list_size 3       # 列表只保留 3 片（不要留 10 片，那是时移回看用的）
#EXT-X-PART          # LL-HLS：0.3s 的部分分片，可把延迟压到 2s 左右
选型结论：推流用 RTMP（兼容性最好）或 SRT（弱网优先）；PC 播放端用 HTTP-FLV；移动端和海量分发用 HLS；互动连麦用 WebRTC。没有一种协议通吃全部场景，成熟方案都是推 RTMP、播 HTTP-FLV/HLS 双协议、连麦 WebRTC 的混合体。
RTMP 已经"推流专用化"。浏览器不再支持 RTMP 播放（Flash 2020 年底被移除），任何"网页播 RTMP"的方案（如 flv.js）本质上都是把 FLV 流重新封装成 HTTP-FLV 播放。设计系统时不要假设播放端能直连 RTMP。
模块 3

CDN 与边缘节点

直播 CDN 不是"缓存图片的 CDN"，它不做长期缓存，做的是实时流的中转与就近分发。理解层级和回源是排障的第一步。

层级结构

源站 origin ──> 中心层 L1（省级） ──> 边缘层 L2（地市级） ──> 用户
直播流：  边缘未命中时逐级回源，命中率做到 95%+ 时回源压力可忽略
点播流：  边缘长期缓存，一次回源长期服务
概念说明
回源 pull边缘收到播放请求、本地没有该流时，向上级拉流并转发。直播常用，首次播放多 200~500 ms
预热 push直播开始前把流主动推到各边缘节点。大直播开播前 5~10 分钟做，避免开播瞬间回源风暴
HTTPDNS绕过 LocalDNS 做调度，防止域名劫持，同时支持按用户 IP 精准分配边缘节点
接入调度客户端上报探测数据（连通率、下载速率、首屏时间），调度系统排序后下发最优节点 IP 列表
单飞回源同一分片/流被多个用户同时请求时，只回源一次再复制分发（single-flight），防止回源打挂源站

首屏时间：直播的核心体验指标

定义：从用户点击播放到看到第一帧画面的时间。业界参考值：HTTP-FLV < 400 ms，HLS < 1000 ms。

  • 预连接：进入直播间就建立 TCP/TLS 连接，不等点击播放
  • 预加载：提前拉 m3u8 或 flv header，缓存首片
  • 就近调度：HTTPDNS + 质量探测，避免跨运营商绕行
  • 边缘预热：大直播提前推流到边缘，消除首次回源
  • GOP 缓存：播放器从关键帧起播，第一个关键帧必须最快到达
排障口诀："先看边缘命中率，再看源站水位。"卡顿率先查用户接入节点是否就近（跨网必然卡），再查边缘命中率是否跌了（跌了说明回源链路或节点异常），最后查源站带宽和 CPU。这三个数在监控面板上都应该有。
模块 4

转码与多码率自适应

观众网络千差万别，多码率是唯一解。转码集群是直播系统里最贵的计算资源，也是画质与成本的调节阀。

码率阶梯（720p 源为例）

档位分辨率帧率视频码率音频码率
原画1080p304000 kbps128 kbps
超清720p302000 kbps128 kbps
高清540p301200 kbps96 kbps
标清480p30800 kbps64 kbps
流畅360p30400 kbps64 kbps

转码架构要点

  • 一路源、多路输出：源流只解码一次，同时编码出 N 个档位。级联转码（转完再转）会累积延迟和画质损失，必须禁止
  • CPU vs GPU：x264 CPU 编码单机约 10~20 路 720p；NVENC（T4/L4）约 30~60 路，延迟还低 100~200 ms。大平台转码全部 GPU 化
  • 转码延迟：收流 → 解码 → 缩放编码 → 推 CDN，单跳 300~1000 ms。这是端到端延迟里服务端能砍掉的部分
  • 按需转码：没有观众的档位不转。某档位连续 30 秒无拉流就停转，有请求再秒级恢复
  • GOP 对齐：切片必须切在关键帧上，且各档位分片时长一致（如都是 2s），否则 ABR 切换时会花屏

播放端 ABR（自适应码率）逻辑

# 简化的 ABR 决策（播放器每 2~3 个分片评估一次）
下载速率 estimated_bw = 最近 3 片实际下载字节数 / 下载耗时
if estimated_bw > 当前档位码率 × 1.5:  升档
elif estimated_bw < 当前档位码率 × 1.1:  降档
else:                                    保持

# 升级要保守（×1.5 才升），降级要果断（×1.1 就降）
# 抗抖动：buffer 水位低于 1s 时无条件降到最低档，先保流畅再保画质
弱网策略优先级：流畅 > 实时 > 清晰。卡顿是观众流失的第一原因，模糊只是体验降级。设计档位阶梯时，"流畅档 400 kbps" 必须保证 3G 网络也能拉得动，这是兜底不是装饰。
模块 5

连麦与互动：低延迟方案

连麦是直播里延迟要求最高的场景：两个主播对话，超过 400 ms 就会出现"抢话"。唯一的选择是 WebRTC。

WebRTC 为什么快

机制作用
UDP 直传不做 TCP 重传与拥塞窗口爬升，发出去就到。延迟预算约 1 个 RTT（同城 20~50 ms）
SRTP 加密强制加密，密钥经 DTLS 握手交换
jitter buffer播放端 50~200 ms 缓冲对抗网络抖动，是延迟的主要来源
NACK/FEC丢包重传与前向纠错，弱网下保画质，代价是少量延迟

连麦时序（文字版）

观众发起申请 → 信令服务器转发到主播端（WebSocket 信令通道）
主播同意 → 双方开始 ICE 协商（STUN 打洞、TURN 中继兜底）
观众推 RTC 流 → SFU → 主播端播放；同时主播把自己的 RTC 流给观众
画面合成 → 主播端或云端把"主播画面 + 连麦小窗"合成一路主流
主流推流 → 转码 → CDN → 普通观众（仍有 2~4 s 延迟）
一个必须理解的延迟差：连麦双方之间是 200~400 ms，但普通观众看到连麦内容仍是 2~4 s。因为观众走的是 CDN 分发链路。想让观众也低延迟，要么推 LL-HLS（约 2 s），要么让播放端也走 WebRTC（成本高 5~10 倍，只用于赛事、演唱会等超低延迟场景）。

SFU 与 MCU

模式原理适用
SFU
转发型		收到流不转码直接转发给房间内其他人多人连麦（3~9 人）。上行带宽 O(N)，服务端几乎零 CPU
MCU
合流型		把多路流解码 + 解码混成一路再转发大房间、下行带宽敏感的场景。CPU 成本高（软件混流每路约 1~2 核）
云端混流GPU 集群做合成（布局、logo、字幕）连麦 + 直播分发混合场景，合出的主流直接进转码链路

互动消息与媒体流分离

点赞、礼物、弹幕、信令全部走 WebSocket 消息通道，不占用 RTC 带宽。原因：① 消息量小但突发高，走消息队列可削峰；② 消息可持久化、可补发；③ 媒体流一旦中断无法补，必须专线专用。两套通道完全解耦，任何一套出问题不拖垮另一套。

模块 6

弹幕系统的消息架构

弹幕是直播里 QPS 最高、长连接最多的系统。核心矛盾：一条弹幕只需广播给同房间的人，但网关机器是全局共享的。解法是"按房间分区"。

完整消息链路

客户端 ──WebSocket──> 接入网关 ──> Kafka ──> 广播 Worker ──> 同组网关 ──> 房间在线用户
                         │                   │
                     限流/鉴权          partition = room_id % 32
                     本地 seq 分配       保证同房间消息有序
组件职责与关键参数
接入网关维持 WebSocket 长连接。单机 5~10 万连接（每连接约 10~50 KB 内存），受文件描述符限制（ulimit 需调到 100 万+）
房间分区room_id % N 决定由哪组网关服务。一条弹幕只在同组内广播，天然把热点房间隔离在单组内
消息队列Kafka，按 room_id 分区，保证同房间有序；广播 Worker 消费后推给对应网关组
seq 机制每房间一个自增 seq。客户端按 seq 检测乱序/丢包；断线重连时带 last_seq，服务端补发缺失消息
历史弹幕进直播间先拉最近 50 条（Redis ZSet，score = seq），避免"进来几分钟没弹幕"

消息格式与真实参数

// 一条弹幕的 JSON
{
  "room_id": 100120,
  "seq": 95271,
  "uid": 88482391,
  "type": "danmaku",        // danmaku / gift / like / enter
  "content": "主播这波操作可以",
  "color": 16777215,
  "ts": 1740000000
}

// 限流参数（业界常见值）
单用户发送：    1~2 条/秒（粉丝牌/会员可放宽到 5 条/秒）
单房间上行：    1000~5000 条/秒，超出后丢弃非会员弹幕保核心消息
下行合并：     网关侧攒 100 ms 批量下发，减少 syscall 与包量

// 心跳与重连
ping 间隔 30~60 s，3 个周期未响应断开；客户端指数退避重连（1s/2s/4s…封顶 30s）

容量估算（给过程）

# 假设：同时开播 10 万个房间，平均每房间 100 人在线
总长连接 = 10 万房间 × 100 人 = 1000 万连接
网关数量 = 1000 万 ÷ 1 万连接/台 = 1000 台网关

# 弹幕流量：
# 假设 20% 房间活跃，每活跃房间 50 条/秒，每条 200 字节
峰值消息量 = 10万 × 20% × 50 = 100 万条/秒
带宽（仅下发）≈ 100万 × 200B = 200 MB/s（1.6 Gbps）
# 结论：弹幕系统的瓶颈是"连接数"和"广播扇出"，不是带宽
最大坑：网关无差别全局广播。早期简易实现把每条弹幕推给所有网关，再让网关自己过滤房间，结果一个百万人在线的直播间能让全网关 CPU 打满。正确做法是分区路由：消息从产生那一刻起就只流向该房间所在的网关组。
模块 7

录制与回放

录制是直播的副产品，但做不好会让"回放"变成投诉重灾区。核心要求：旁路录制不抢资源、时间戳对齐墙钟、断流能补。

旁路录制链路

源站主流 ──> 录制集群（旁路，不占直播分发链路）
              │
              ├─> ts 切片（6~10 s/片）
              ├─> 定时合并为 mp4
              ├─> 上传对象存储（S3 / OSS / COS）
              └─> 写入索引（room_id、开始时间、时长、URL）
要点说明
旁路原则从源站流复制一份录制，与转码、分发完全隔离。录制挂了不影响观看，这是硬要求
时间戳对齐切片内 PTS 与墙钟（NTP 同步）对齐，否则回放进度条对不上"主播说的第几分钟"。ffmpeg 用 -copyts 保留原始时间戳
断流补录推流中断时录制进程标记空档，主播重推后继续录制，最终 mp4 里补黑帧或提示，不能丢文件
存储策略mp4 存标准对象存储，设置生命周期规则（如 30 天转低频存储，1 年删除）。索引单独存数据库，支持按主播/时间检索

时移回看（timeshift）

# 时移 = 把 HLS 窗口从"3 片"拉长到"10 分钟"
ffmpeg -i rtmp://origin/live/stream -c copy \
  -hls_time 2 -hls_list_size 300 -hls_flags delete_segments+append_list \
  stream.m3u8

# hls_list_size 300 × 2s = 600s = 10 分钟窗口
# 观众拖动进度条时，播放器请求 MEDIA-SEQUENCE 更早的分片即可
# 代价：源站/边缘需缓存 10 分钟的 ts 分片，带宽与存储成本上升

时移回看和完整回放的区别：时移只覆盖"最近 N 分钟"，边看边录；完整回放是录制合并后的 mp4/VOD，支持永久保存和倍速。两者常常同时提供。

录制事故第一名：时间戳没对齐。表现是回放进度条走到某处，画面内容对不上；或者两个机位录的文件差几秒，剪辑时对不上轴。根因是录制服务器没做 NTP 同步、或切片时丢了 PTS。上线前必须核对：录制文件内部时间与墙钟误差 < 500 ms。
模块 8

容灾与成本

直播是实时业务，故障期每分每秒都是观众流失。容灾的核心是自动化切换 + 短 m3u8 缓存；成本的核心是带宽就是命。

多 CDN 切换

机制说明
主备域名播放地址用主 CDN 域名，故障时播放器/调度系统切到备用域名（如 cdn-a / cdn-b 两家厂商）
播放端切换连续 N 次加载失败（N 一般取 2~3）或卡顿率超阈值 → 自动切备用地址重试。N 太小会误切，太大切换慢
调度侧切换调度系统综合各 CDN 质量探测数据主动下发切换指令，比播放端被动重试更快（秒级 vs 十秒级）
m3u8 缓存 TTLCDN 上 m3u8 缓存必须设 1~2 s。设成 30 s 的话，切换域名后观众还在读旧节点的过期列表，表现为"切了但没生效"

主备流（双路上行）

主播推两路流：主（cdn-a 链路）+ 备（cdn-b 链路），码率可不同（备路可降一档省带宽）
播放端默认拉主；主失败自动切备。
成本：上行与分发带宽约 +60%（备路只推流，播放端平时不拉）。
适用：S 级赛事、晚会、发布会。日常直播用多 CDN 单路即可。

成本账（这是直播架构师的必修课）

# 场景：5 万并发观众，平均混合码率 1.5 Mbps，直播 4 小时
峰值带宽 = 50,000 × 1.5 Mbps = 75 Gbps
单秒流量 = 75 Gbps ÷ 8 = 9.375 GB/s
总流量   = 9.375 GB/s × 4 × 3600 s = 135,000 GB ≈ 132 TB

# CDN 计费方式（国内主流）：
# ① 按 95th 峰值带宽（月结）——适合流量平稳，突发会被记高
# ② 按流量阶梯计费——适合日常直播，用得少付得少
# 以某云 95th 计费约 25 元/Mbps/天估算：
单场带宽成本 ≈ 75,000 Mbps × 25 元 × (4h/24h) ≈ 31 万元/场
# 结论：带宽占直播总成本 70%+，转码算力约 10~15%，其余是存储与运维

降本手段

  • 码率优化：默认档位不要盲目 1080p。多数内容 720p 足够，带宽立省 50%
  • 按需转码：无人观看的档位停转，只保 1~2 个基础档
  • 闲时降配：非黄金时段缩容转码集群与边缘预热范围
  • P2P 分发：观众之间互拉流量，大房间可省 30~50% 带宽，代价是客户端复杂度和上传占用
  • 带宽封顶告警：给每路流设带宽上限与日账单告警，防"一夜被刷爆"
可用性目标怎么写：直播核心链路（推流→播放）年可用性 99.99% = 全年停机不超过 52 分钟。事故 MTTR（恢复时间）目标 < 5 分钟，靠多 CDN 自动切换达成；MTBF 靠源站/转码集群冗余达成。S 级直播还要做全链路演练：定期手动断一路 CDN，验证切换真的生效。
模块 9

十个线上坑

1
拉流地址写死单 CDN 域名
该 CDN 出故障时播放端无路可走。必须接多 CDN + 播放端失败切换逻辑，且 m3u8 的 CDN 缓存 TTL 压到 1~2 s，否则切换不生效。
2
OBS 关键帧设成"自动"
GOP 不均匀导致服务端切片切在非关键帧上，播放花屏、ABR 切换失败。OBS 里必须显式设 2 秒，ffmpeg 侧用 -g 60 -keyint_min 60 -sc_threshold 0。
3
只监控推流成功率，不监控播放卡顿
推流 100% 成功但观众全在卡顿的案例极其常见（边缘节点故障、回源拥塞）。必须监控播放侧指标：首屏时间、卡顿率、秒开率、各档位切换频次。
4
转码级联
把已转码的流再送进转码集群，延迟累积、画质代代劣化。正确做法是源流只解码一次，并行输出全部档位；级联应在架构评审时明确禁止。
5
弹幕网关无分区，全局广播
一条弹幕推给所有网关再本地过滤，热点房间打满全网关 CPU。必须按 room_id 分区路由，消息只在本组内扇出。
6
软件混流不设上限
ffmpeg filter_complex 混流每路约 1~2 核 CPU，并发连麦一多就饱和，表现为连麦画面卡住但声音正常。混流集群要有限流和排队，并优先用 GPU。
7
m3u8 在 CDN 上缓存时间过长
设了 30 s 缓存，切 CDN 后观众仍从旧节点读到过期分片列表，"切了没生效"。HLS 的 m3u8 缓存 TTL 必须是 1~2 s，ts 分片可以长缓存（内容不变）。
8
播放器 buffer 策略一刀切
起播 buffer 设 2 s，弱网用户永远在加载；设 10 s，延迟大到没法互动。正确做法是分级：起播小 buffer（1 s），稳定后按网络动态调整，buffer 低于 1 s 强制降档。
9
带宽不设封顶与告警
被盗刷或配置错误时账单一夜翻十倍。必须给每路流设带宽上限、日流量告警、异常爬升自动通知；95th 计费的月份要盯预测值。
10
录制时间戳未对齐墙钟
回放进度错乱、多机位对不上轴。录制服务器必须 NTP 同步，ffmpeg 用 -copyts 保留 PTS，上线前抽查录制文件内部时间与墙钟误差 < 500 ms。
自测

六道题

1. 下列协议中，端到端延迟最低的是？
正确答案：WebRTC（200~500 ms）。它走 UDP 不经过 TCP 拥塞控制和分片累积。HTTP-FLV 约 1~3 s，HLS 约 5~10 s（LL-HLS 可压到 2 s 左右）。
2. HLS 延迟大的主要原因是？
正确答案：分片累积。延迟 ≈ TARGETDURATION × 列表分片数，2 s × 3 = 6 s。降延迟手段：缩短分片时长（hls_time 1）、减少列表片数、或用 LL-HLS 的 EXT-X-PART 部分分片。
3. 相比 RTMP 拉流，HTTP-FLV 的核心优势是？
正确答案：走 HTTP 可过 CDN。延迟量级与 RTMP 相当（1~3 s），但 HTTP-FLV 能享受 CDN 的边缘分发、缓存和调度，且不再依赖 Flash（浏览器需 flv.js 等方案转封装）。
4. 百万人在线的直播间发一条弹幕，正确的广播方式是？
正确答案：房间分区 + 组内广播。无分区全局广播会让一个热点房间耗尽全网关 CPU；轮询拉取延迟不可接受。工程上还要叠加 seq 去重、100 ms 下行合并、单用户/单房间限流。
5. 多 CDN 切换已正确配置，但观众仍长时间卡顿不恢复。最可能的原因是？
正确答案：m3u8 缓存 TTL 过长。HLS 的 m3u8 必须设 1~2 s 短缓存，ts 分片可长缓存。否则切换域名后观众拿到的还是旧节点分片列表，表现为"切换不生效"。
6. 一场 5 万并发、平均 1.5 Mbps、4 小时的直播，带宽成本的大头是什么？
正确答案：CDN 带宽。5 万 × 1.5 Mbps = 75 Gbps，4 小时约 132 TB。带宽通常占直播总成本 70% 以上，转码算力约 10~15%。降本优先级：码率优化 > 按需转码 > P2P > 闲时降配。
