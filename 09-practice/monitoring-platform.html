二十分钟学透 监控告警平台设计实战

监控平台不是"装个 Prometheus + Grafana"就完事。这篇讲机制：指标模型怎么设计才不炸、告警怎么分级抑制收敛、on-call 怎么联动、容量怎么算，以及告警风暴、阈值拍脑袋、只监控不发这三个经典死法。

建议对着你司现有监控平台读：先看它的指标命名规范和告警分级表
开始前

监控平台到底解决什么问题

一句话：让故障在"用户投诉之前"被发现，并且能快速定位到根因。拆开是三件事：

能力回答的问题典型实现
可观测（Observability）系统现在健康吗？哪里慢了？哪里错了？Metrics + Logging + Tracing 三位一体
告警（Alerting）出事了，该通知谁？半夜叫不叫人？告警规则引擎 + 分级 + on-call 排班
定位（Diagnosis）为什么出问题？根因在哪一层？大盘、下钻、链路追踪、CMDB 关联
一个常见误区：把监控当"看板工程"。Grafana 大盘画得再漂亮，如果告警规则是拍脑袋设的、没人值班、告警一发几百条，那等于没监控。监控的价值 = 发现率 × 及时性 × 准确率，任何一个为零，整体就是零。
模块 1

整体架构：采集 / 存储 / 计算 / 告警 / 可视化

主流架构（以 Prometheus 生态为范本）分五层。每一层都有明确的职责边界和数据流向。

┌─────────────────────────────────────────────────────────────┐
│  采集层 Exporter / Agent                                     │
│  node_exporter(机器)  mysqld_exporter(DB)                     │
│  app /metrics 端点(业务埋点)  kafka_exporter otel-collector   │
└──────────────┬──────────────────────────────────────────────┘
               │ pull(拉取) 或 push(推送) 原始指标
┌──────────────▼──────────────────────────────────────────────┐
│  存储层 TSDB                                                │
│  Prometheus(单机/Thanos/VictoriaMetrics) 本地 TSDB + 对象存储  │
└──────────────┬──────────────────────────────────────────────┘
               │ PromQL 查询
┌──────────────▼──────────────────────────────────────────────┐
│  计算层 Rule Engine                                         │
│  Recording Rules(预聚合降本)  Alert Rules(阈值/同比/环比)     │
└──────────────┬──────────────────────────────────────────────┘
               │ firing alerts
┌──────────────▼──────────────────────────────────────────────┐
│  告警层 Alertmanager                                        │
│  分组(group) 抑制(inhibit) 静默(silence) 路由(route→渠道)     │
└──────────────┬──────────────────────────────────────────────┘
               │ 电话/短信/IM/值班系统
┌──────────────▼──────────────────────────────────────────────┐
│  可视化层 Grafana / 自研大盘                                 │
└─────────────────────────────────────────────────────────────┘
层关键决策点常见选型
采集pull 还是 push？采集间隔多长？谁发现 target 挂了？pull 为主（Prometheus SD），日志/事件类用 push（Kafka/Loki）
存储保留多久？单机够不够？要不要全局视图？Prometheus 本地 15 天；长期用 VictoriaMetrics / Thanos + S3
计算哪些查询要预聚合？告警规则放哪管理？Recording rules 把慢查询固化成新指标；规则用 GitOps 管理
告警怎么分组？谁被通知？升级路径是什么？Alertmanager + PagerDuty / 自研 on-call
可视化大盘谁维护？怎么防止"看板垃圾场"？Grafana + 代码化管理（Jsonnet / Terraform），禁止手改线上大盘
pull 与 push 的真实差别：Prometheus 的 pull 模式要求 target 可达，且天然知道 target 是死是活（拉取失败 = up{job="x"} = 0），这是 push 模式（如 InfluxDB、 statsd 直推）做不到的 —— push 模式下 target 自己挂了，你收到的最后一条数据看起来"岁月静好"。所以即使中间有 Pushgateway / vmagent，也要保留主动探测。
模块 2

指标模型设计：标签规范、基数控制、分层聚合

指标模型是监控平台的"数据建模"，设计错了后面全歪。核心矛盾：标签（label）越丰富，能回答的问题越多，但存储和查询成本指数级上升。

命名规范

规范正例 / 反例
三层结构：命名空间_子系统_指标名_单位http_requests_total{code="200"}
反例：requestCount、请求总数
基础单位，不用 K/M 缩写node_memory_bytes 而不是 node_memory_mb
_total 后缀表示累计计数器requests_total，查询时用 rate() 取增量
标签小写 + 下划线，值用枚举env="prod" 而不是 env="生产环境"
必备标准标签service / env / cluster / instance / zone

基数（Cardinality）控制——最贵的教训

一条时间序列 = 指标名 + 所有标签值组合的唯一标识。基数爆炸是监控平台的头号死因。

# 基数计算示例
http_requests_total{service="api", method="GET|POST", path, code="200|500|...", pod="20个"}
# 如果 path 是"原始 URL"，比如 /user/12345/order/67890
# 基数 = method(2) × path(百万级) × code(5) × pod(20) = 千万级序列 → 直接炸

# 正确做法：path 做归一化（路由模板）
http_requests_total{path="/user/:id/order/:oid"}  # 基数 = 路由模板数量，通常几十
标签类型是否可加原因
枚举值（status=success/fail）推荐值域有限，每个值就是一条序列
低基数 ID（pod 名、机器名）谨慎pod 重建序列就漂移，用实例数 × 基数估算成本
高基数 ID（user_id、order_id、trace_id）禁止一条指标能裂变成几百万条序列，TSDB 直接被打死
message、堆栈、URL 原文禁止属于日志不属于指标，送 Loki / ES

分层聚合：RED 与 USE

方法适用对象三要素
RED 方法请求驱动型（服务、接口）Rate 请求速率 / Errors 错误率 / Duration 延迟分布
USE 方法资源型（CPU、内存、磁盘、网卡）Utilization 使用率 / Saturation 饱和度 / Errors 错误数
四大黄金信号通用（Google SRE）延迟 / 流量 / 错误 / 饱和度
工程落地顺序：① 每个服务先按 RED 埋三个指标（rate、error ratio、p99 latency），覆盖 80% 故障发现；② 机器按 USE 用现成 exporter 覆盖；③ 有富余预算再上业务指标（订单量、支付成功率）；④ 所有指标接入前过一遍"基数评审"，评估新增序列数，超过阈值的要打回。
模块 3

告警体系：分级、抑制、收敛、升级

告警体系的设计目标是：该叫的时候一定叫，不该叫的时候一声不吭。靠四件事：分级、抑制、收敛、升级。

告警分级

级别定义响应要求通知方式
P0核心业务受损、资金损失、数据丢失风险立即响应，5 分钟内有人处理电话 + 短信，循环拨打直到接起
P1核心功能降级，部分用户受影响30 分钟内响应IM 群 + 短信
P2非核心功能异常，有损服务工作时间处理IM 群，工作时间
P3隐患类：容量将满、证书临期排期内处理邮件 / 工单，不打扰

抑制（Inhibit）：一个故障只发一条告警

网络抖动导致机房 A 全挂，几千个 target 同时告警 —— 这就是告警风暴。抑制规则的作用是：当"上游/全局"告警已触发时，压制其下游/局部的告警。

# Alertmanager 抑制示例：机房级告警抑制机器级告警
inhibit_rules:
  - source_matchers:
      - severity="critical"
      - alertname="IDC-Down"          # 上游：机房整体不可用
    target_matchers:
      - severity=~"warning|info"       # 下游：被波及的实例告警全部静默
    equal: ['idc']

收敛（Group）：把相关的告警合并

机制作用Alertmanager 配置
分组 group_by同组告警合并成一条通知group_by: ['alertname', 'service']
等待 group_wait等一会儿，把同窗口的告警凑一桌group_wait: 30s
重复间隔 group_interval已通知组的新增告警打包再发group_interval: 5m
重复抑制 repeat_interval同一告警未恢复，静默多久不再发repeat_interval: 4h

升级（Escalation）：没人认领就往上捅

T+0：P0/P1 触发，电话 + IM 通知一线值班（当前 on-call）
T+5min：未认领（ack）→ 升级通知二线（备份值班 + 主管）
T+15min：仍未认领 → 升级到 SRE 负责人 / CTO，并拉应急群
全程：告警触发即自动建 incident 工单，记录时间线，事后复盘必须引用工单
告警疲劳是组织病不是技术病：如果一个值班人一周被叫醒 5 次，其中 4 次是误报，第 5 次真的他也会当误报处理。衡量指标：告警准确率（真故障/总告警）目标 > 90%，P0 月均误报 < 2 次。做不到就砍阈值、加持续时间（for: 5m）、修数据质量，而不是"大家忍一忍"。
模块 4

值班与 on-call 联动

告警的终点是人。on-call 机制决定了告警从"一条消息"到"一次响应"的转化率。

要素设计要点
排班表按周轮转，主备双人（primary + secondary），节假日单独排。日历要可订阅（ICS）
认领（ack）告警必须显式 ack，ack 后停止升级，同时记录"谁在处理"
升级路径没人 ack 就按时间轴升级，避免"以为别人会处理"
处理 SOP每个 recurring 告警配 runbook：看到什么 → 查什么 → 做什么。没有 runbook 的告警不配发
事后闭环每次 P0/P1 出复盘：加监控了吗？告警及时吗？误报要不要修？
补偿机制夜间被叫、节假日值班要有补贴或调休，否则排班表没人接
# 一个最小可用的 on-call 状态流转
FIRING ──通知──> primary 电话/IM
   │
   ├─ ack ──> INVESTIGATING（记录处理人）──> RESOLVED
   │                                        （触发恢复通知 + 工单自动关单）
   └─ 5min 未 ack ──> 通知 secondary
          │
          └─ 15min 未 ack ──> 通知负责人，拉应急群
值班三定律：① 没有补偿的轮值是耍流氓，排班会崩；② 告警必须能 ack，不能 ack 的系统等于逼所有人无视；③ 复盘必须回填到监控：每次故障后问一句"这次故障监控提前发现了吗？"，把答案变成新的告警规则。
模块 5

自监控：监控系统自己的监控

一个没人监控的监控系统，是集群里最大的单点。自监控要独立于主监控：主监控挂了，自监控要还能发出"监控挂了"的告警。

自监控项判断方法异常处理
采集存活up{job="node"} == 0 持续 5 分钟检查 exporter 进程、网络、SD 配置
数据新鲜度最新样本时间戳距 now > 2×scrape_interval采集卡死 / 时钟漂移 / TSDB 写阻塞
告警链路心跳告警：每 5 分钟发一条"监控系统存活"的低优先级消息到独立渠道链路断了立刻能发现（看门狗式）
Alertmanager 状态alertmanager_alerts_received_total 掉零；集群成员数 < 2HA 实例挂了要补
规则评估rule_evaluation_failures_total > 0；某规则 last evaluation 时间变老规则写错 / 查询超时 / PromQL 太重
存储水位磁盘使用率 > 75%；序列数接近上限扩盘 / 降基数 / 加长期存储
# 数据新鲜度自监控 PromQL：超过 2 个采集周期没数据就告警
time() - max by (job) (timestamp(up{job=~".+"})) > 2 * 60

# 心跳告警：Prometheus 侧
- alert: MonitoringPipelineHeartbeat
  expr: vector(1)          # 永远为真，5 分钟发一次
  for: 0m
  labels: {severity: info}
  annotations:
    summary: "监控链路存活心跳 {{ $labels.instance }}"
心跳告警的正确用法：不要指望它"告诉人一切正常"，它的价值是证明链路断了 —— 心跳是定时发到独立 IM 群的，一旦群里心跳停了，说明监控系统自己出事了。发送通道必须和主告警通道解耦（比如主告警走电话系统，心跳走另一个 IM 机器人），否则一荣俱荣一损俱损。
模块 6

容量估算：用数字说话

容量估算不是玄学，是乘法。下面用一套真实量级的算例走一遍全过程。

算例背景

  • 业务规模：2000 台物理机/虚机，300 个微服务实例（每服务 3~10 pod）
  • 采集间隔：15 秒（Prometheus 默认）
  • 保留策略：热数据 15 天本地 + 长期 13 个月对象存储

第一步：算序列总数（基数）

# 每台机器（node_exporter）约 800~1000 条序列
机器序列 = 2000 × 900        = 1,800,000

# 每个业务实例：RED 指标 + JVM/运行时 + 依赖，约 1500 条
业务序列 = 300 × 3.5(pod均值) × 1500 = 1,575,000

# 中间件：MySQL 50 实例 × 2000 + Redis 100 实例 × 1500 + Kafka 20×3000
中间件序列 = 100,000 + 150,000 + 60,000 = 310,000

# 合计活跃序列
总序列 ≈ 1,800,000 + 1,575,000 + 310,000 ≈ 370 万条

第二步：算写入与存储

项目计算过程结果
样本写入速率370 万序列 ÷ 15s≈ 24.7 万样本/秒
未压缩样本大小每样本约 1~2 字节（delta-of-delta + varint）压缩前 ≈ 24.7万 × 2B ≈ 0.5 MB/s
压缩后磁盘增量压缩率约 10~15:1≈ 35~55 KB/s
15 天热数据45KB/s × 86400 × 15≈ 58 GB
13 个月长期45KB/s × 86400 × 395（降采样 5m 后约 ×1/20）降采样后 ≈ 45KB/s ÷ 20 × 3.4e7 ≈ 75 GB
内存经验值每百万活跃序列约 2~4 GB 内存370 万 × 3GB ≈ 11 GB/实例

第三步：得出部署结论

  • 单台 Prometheus 建议活跃序列 < 200 万（再大查询和 compaction 都吃力）→ 至少 2~3 个 Prometheus 分片，按业务线/中间件分片
  • 需要全局查询视图 → 上加 Thanos Query / VictoriaCluster，冷数据进对象存储
  • 磁盘：每分片热数据 ≥ 100GB（留 40% 余量给 compaction 临时文件）
  • 成本参考：若不降基数，序列翻 10 倍，存储和内存同步翻 10 倍 —— 基数治理的 ROI 是监控平台所有优化里最高的
估算口诀：序列数 ÷ 间隔 = 写入速率；写入速率 × 保留秒数 × 压缩系数 = 磁盘；活跃序列 × 2~4GB/百万 = 内存。四个数乘出来，加 30~50% 余量，就是采购单。记住一个数量级感觉：15s 间隔下，100 万序列 ≈ 6.7 万样本/s ≈ 每日 6~9 GB 压缩后数据。
模块 7

与 CMDB / 服务树集成

监控数据回答"什么指标异常了"，CMDB（配置管理数据库）回答"这是谁的服务、归谁负责"。两者不打通，告警就是"某台 10.0.3.17 CPU 高了"，没人知道该找谁。

集成点

CMDB 提供监控消费方式
服务树/归属（服务→团队→负责人）告警路由按服务标签找到负责人电话；事故复盘自动拉组织架构
实例清单与元数据（IP、机型、地域）Prometheus service discovery 的 file_sd / 云 SD 数据源；标签富化（zone、idc、owner）
变更记录（发布、扩缩容、配置变更）告警时间轴上叠加变更事件，定位"是不是发布搞的"
依赖关系（A 调 B 调 C）故障传播分析：根因服务高亮，下游告警抑制

落地方式

# 方式一：标签富化（推荐）—— CMDB 数据周期性写进指标标签
http_requests_total{service="order", team="trade", owner="zhangsan", zone="az1"}

# 方式二：告警时关联查询 —— 告警 webhook 里带 instance IP，
# 通知前回调 CMDB API 反查负责人，动态填充 @人

# 方式三：服务树即配置源 —— 大盘、告警规则按服务树节点自动继承
# 新服务注册到服务树叶子节点，自动获得父级的大盘模板和告警基线
两个一致性坑：① CMDB 里的实例已经下线了，监控还在采（僵尸 target，up=1 但是没人用的机器）；② CMDB 显示已下线，监控 target 没了但服务还在跑（漏采）。解法：每日对账作业 —— 拿 CMDB 清单和 Prometheus 的 target 列表做双向 diff，两边都生成差异报告，进工单闭环。
模块 8

核心配置示例

下面是一套可以直接参考的最小可用配置：Prometheus 抓取 + 告警规则 + Alertmanager 路由与抑制。

Prometheus 抓取配置

# prometheus.yml 片段
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels: {cluster: "prod-east", replica: "A"}

rule_files:
  - /etc/prometheus/rules/*.yml

scrape_configs:
  - job_name: node
    file_sd_configs:
      - files: ["/etc/prometheus/targets/nodes/*.json"]   # CMDB 生成
    relabel_configs:
      - source_labels: [__address__]
        regex: "(.*):.*"
        target_label: instance
        replacement: "$1"

  - job_name: app
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        action: keep
        regex: "true"                                       # 只抓带注解的 pod

告警规则（分级 + 持续时间 + runbook）

# rules/service.yml 片段
groups:
  - name: order-service
    rules:
      - alert: OrderErrorRateHigh
        expr: |
          sum by (service)(rate(http_requests_total{service="order",code=~"5.."}[5m]))
          / sum by (service)(rate(http_requests_total{service="order"}[5m])) > 0.05
        for: 5m                    # 持续 5 分钟才触发，躲过瞬时毛刺
        labels: {severity: critical, team: trade}
        annotations:
          summary: "订单服务 5xx 错误率 {{ $value | humanizePercentage }}"
          runbook: "https://wiki/runbook/order-5xx"   # 没有 runbook 的告警不该存在

      - alert: OrderLatencyP99High
        expr: |
          histogram_quantile(0.99, sum by (le)(rate(http_duration_seconds_bucket{service="order"}[10m]))) > 1.5
        for: 10m
        labels: {severity: warning, team: trade}

Alertmanager 路由（分级分流）

# alertmanager.yml 片段
route:
  receiver: default-im
  group_by: ['alertname', 'service', 'cluster']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers:
        - severity = "critical"
      receiver: pager-critical        # P0/P1 走电话
      repeat_interval: 1h
      continue: true                  # 继续匹配后续路由（同时进 IM 群）
    - matchers:
        - severity =~ "warning|info"
      receiver: im-only               # P2/P3 只进 IM，不打电话
      repeat_interval: 12h

inhibit_rules:                          # 机房挂了，别再用机器告警刷屏
  - source_matchers: [alertname="IDC-Down", severity="critical"]
    target_matchers: [severity=~"warning|info"]
    equal: ['idc']

receivers:
  - name: pager-critical
    webhook_configs: [{url: "http://oncall-system/api/v1/alert", send_resolved: true}]
  - name: im-only
    webhook_configs: [{url: "http://bot.internal/alert", send_resolved: true}]
  - name: default-im
    webhook_configs: [{url: "http://bot.internal/alert", send_resolved: true}]
三条配置纪律：① 告警规则必须进 Git 仓库，Code Review 后才能上线，禁止在 Grafana 页面上手点"创建告警"；② 每条告警必须有 runbook 链接，值班人半夜 3 点看到"磁盘满了"要知道第一步跑什么命令；③ for 持续时间必须显式设置，默认 0s 的规则会把一次发布重试的抖动变成一次 P0。
模块 9

十个线上坑

1
告警风暴：一次网络抖动发几千条告警
机房/核心交换机故障时，所有下游实例同时 up=0，短信通道都被打爆，真正的告警被淹没。必须配 inhibit_rules（机房级抑制实例级）+ group_by 收敛，并对通知渠道本身限流。
2
阈值拍脑袋：CPU > 80% 就告警
80% 哪来的？为什么不是 75% 或 90%？正确做法是看历史分布定基线（如 p99 水位上浮 20%），或用同比/环比（"较昨天同时段高 50%"），而不是一个魔数用三年。
3
只监控不发：大盘很漂亮，告警规则是空的
看板是给人"主动看"的，告警是机器"主动叫"的。核心链路（下单、支付、登录）没有配置告警规则，等于把发现故障的希望寄托在用户投诉上。每条黄金链路都必须有对应的告警。
4
标签基数爆炸：把 user_id 塞进标签
一条指标裂变成几百万条序列，TSDB 内存和磁盘双双起飞，查询直接超时。指标里只允许枚举值和低基数 ID；高基数数据（用户、订单、URL 原文）是日志的活，送 Loki/ES。
5
没有自监控：监控系统自己挂了三天没人知道
Prometheus 磁盘写满、Alertmanager 集群脑裂、规则评估失败，这些都不会"自己报警"。必须配心跳告警 + 数据新鲜度检查，且发送通道与主告警解耦。
6
告警没人认领：没有 ack 机制，全靠@所有人
告警发到群里，每个人都以为别人会处理。必须接 on-call 系统：告警直达当前值班人，未认领按时间轴升级（5 分钟二线、15 分钟负责人），ack 后停止升级。
7
告警没有 for 持续时间：发布一次抖三次 P0
滚动发布、重试、GC 都会造成秒级毛刺，规则 for: 0m 全部照单全收。所有 rate/error 类告警至少 for: 5m；容量类（磁盘将满）可以短，但要配合趋势判断。
8
CMDB 与监控两边不同步
机器下线了监控还在抓（僵尸 target 刷错误日志），新扩容的机器没进 target 列表（裸奔）。必须做每日双向对账：CMDB 清单 vs Prometheus targets，差异进工单。
9
监控平台本身不做高可用：单点 Prometheus
一台 Prometheus 管所有业务，它挂了全公司监控瞎一半。至少按业务线分片 + 双实例互备（Thanos Sidecar / VMCluster），Alertmanager 集群模式（≥3 实例）保证告警通道不中断。
10
复盘不回流：同样的故障犯第二次
故障复盘报告写完归档，监控缺口没有补：这次是缓存命中率跌了导致的，复盘后并没有加"缓存命中率"告警。闭环要求：每个 P0/P1 复盘必须产出"新增/修改的监控项"清单，并纳入下个迭代。
自测

六道题

1. 机房核心交换机故障，几千个实例同时 up=0，告警把短信通道打爆。最有效的治理手段是？
正确答案：inhibit_rules 抑制。根因是"一个全局故障产生了海量派生告警"，抑制规则让上层 critical 告警触发时自动静音下层 warning/info，一条通知解决问题。repeat_interval 只降低重复频率，解决不了首轮的几千条并发。
2. 关于指标标签（label）的基数，哪种做法是正确的？
正确答案：用路由模板归一化。序列数 = 指标名 × 各标签值组合数，user_id、原始 URL 会让一条指标裂变成百万级序列，TSDB 内存和磁盘都扛不住。高基数数据应该走日志（Loki/ES）链路。
3. 关于自监控，下列说法最重要的是？
正确答案：通道解耦。自监控的核心不是"监控系统自己的指标"，而是"监控系统整体失效时还能通知到人"。心跳消息要走独立渠道（如另一个 IM 机器人），心跳停了即证明链路断裂。
4. 估算容量：370 万活跃序列、15 秒采集间隔，样本写入速率约为多少？
正确答案：约 24.7 万样本/秒。计算：3,700,000 ÷ 15s ≈ 246,667 样本/秒。记忆锚点：15s 间隔下 100 万序列 ≈ 6.7 万样本/s ≈ 每日 6~9 GB 压缩后数据。单台 Prometheus 建议活跃序列控制在 200 万以内，所以这套规模至少分 2~3 片。
5. 告警分级里，P2 级告警（非核心功能受损）的正确处理方式是？
正确答案：IM/工单，工作时段处理。分级的意义是"按影响匹配通知强度"：P0/P1 电话 + 立即响应，P2 工作时段 IM，P3 邮件/工单。全部电话会制造告警疲劳，全部静默则会漏掉真实劣化。
6. 一条 order 服务 5xx 错误率告警规则，哪种写法最合理？
正确答案：5m 窗口 + for: 5m + runbook。瞬时毛刺（重试、发布抖动）用 for 持续时间过滤；runbook 保证半夜被叫的人知道第一步干什么；severity 标签决定路由到哪个通知渠道。"只看大盘"等于把发现故障寄托在人的自觉上。
