二十分钟学透短链系统设计

短链是"最简单的分布式系统，也是最容易翻车的读系统"。一个 6 位字符串背后是：发号器、Base62、301/302 的取舍、缓存层级、容量估算。这篇把 s.url.cn/a1B2c3 一次跳转背后的一切讲透。

开始前

短链到底是个什么东西

剥开所有花活，短链系统只做两件事：把一个长 URL 映射成一个短码，访问短码时 301/302 跳回长 URL。全部设计问题都围绕这两个动作展开。

写链路（低频，几百 QPS）
提交长链发号器生成短码写映射存储写缓存返回短链
读链路（高频，几十万 QPS）
DNS 解析短域名边缘节点 / 网关本地缓存 → Redis → DB返回 302 + Location异步埋点上报

注意读写比例的悬殊：写一次，读几千到几百万次。所以短链是典型的"读放大"系统，读链路决定架构，写链路决定正确性。业内参照系：微博 t.cn 日均跳转百亿次级，腾讯 url.cn 同量级；本篇算例取日均 10 亿次跳转、存量 5 亿条短链。

一个反直觉的结论：短链的技术难度不在"生成"，在跳转的可用性。用户对"生成慢 1 秒"无感，但对"点了不跳"零容忍。所以架构上读链路要冗余到偏执：多级缓存、多活部署、降级预案。
模块 1

核心原理：发号 + 映射

短码本质上是一个全局唯一 ID 的 Base62 编码。理解这一点，所有方案都顺理成章。

Base62 字符集与容量

// 字符集：0-9 + a-z + A-Z = 62 个字符，避免特殊字符（URL 安全、免转义）
charset = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

// 容量（这是选短码长度的唯一依据）
62^1 =                   62
62^4 =             14,776,336   // 1400 万，4 位不够用
62^6 =         56,800,235,584   // 568 亿，6 位是业界标配
62^7 =      3,521,614,606,208   // 3.5 万亿，7 位留给超大规模

// 为什么不用更短？4 位只有 1477 万，撞库+遍历风险高；
// 为什么不用更长？每多 1 位字符，短信/物料成本上升，且输入易错

编码与解码（进制转换）

public static final String CHARS = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";

// 10 进制 ID → 6 位短码（不足 6 位前面补 '0'）
public static String encode(long id) {
  if (id == 0) return "0";
  StringBuilder sb = new StringBuilder();
  while (id > 0) {
    sb.append(CHARS.charAt((int)(id % 62)));
    id /= 62;
  }
  return sb.reverse().toString();
}

// 短码 → 10 进制 ID（解码不是必须的，但调试/反查很有用）
public static long decode(String code) {
  long id = 0;
  for (char c : code.toCharArray()) {
    id = id * 62 + CHARS.indexOf(c);
  }
  return id;
}

// 关键细节：发号器给出的是"全局唯一整数"，短码 = encode(id)
// 所以问题立刻收敛为：如何高性能地发号？—— 这是模块 2 的全部内容

一个必须做的变换：短码加散列

如果直接用自增 ID 编码，短码是连续的：000001、000002、000003。后果是任何人都能遍历你的全部短链，爬走内容、估算业务量。解法：编码前对 ID 做一个可逆或可查的扰乱——常见做法是用一个固定密钥的对称加密 / Feistel 网络（FPE 保留格式加密），保证同一个 ID 永远映射到同一个"看起来随机"的短码，且不碰撞。简单场景也可以接受"随机生成 + 冲突重试"（见模块 2）。

模块 2

发号器：四种方案

发号器的唯一 KPI：趋势递增、全局唯一、高可用、不泄露业务量。四种方案，按规模选用。

方案发号速率ID 位数适用与风险
数据库自增单机 ~5 千/s短（编码后 6 位内）最简单。单点瓶颈 + 宕机丢号；自增 ID 泄露总量。只适合起步期
号段模式单机 ~10 万/s短最常用（美团 Leaf 号段版）。批量取号段（如一次取 1000），DB 压力降到 1/1000
雪花算法单机 ~10 万/s长（19 位数字，Base62 后 11~12 字符）无单点、自带时间信息，但编码后超出 6 位，且依赖机器时钟（回拨风险）
随机生成 + 冲突重试~5 万/s可控 6 位直接随机 6 位，查重撞了重试。后期碰撞率上升（生日悖论），需监控重试次数

号段模式实现（生产主流）

-- 号段表：每个业务一个 tag，step 是每次取的号段长度
CREATE TABLE id_segment (
  tag       VARCHAR(32) PRIMARY KEY,
  max_id   BIGINT NOT NULL,   -- 当前已发到的最大号
  step      INT NOT NULL       -- 每次取的步长，如 1000
  version  INT NOT NULL       -- 乐观锁
);

-- 取号段：一次 UPDATE 拿 1000 个号（原子）
UPDATE id_segment
   SET max_id = max_id + step, version = version + 1
 WHERE tag = 'short_url' AND version = ?;

-- 拿到 max_id 后，在内存里顺序分配 [max_id-step+1, max_id]
-- 用完再取下一段。DB 压力 = 发号量 / step = 10万/s ÷ 1000 = 100 QPS，毫无压力

// 内存分配（应用内，无锁 AtomicLong）
AtomicLong current = new AtomicLong(maxId - step + 1);
public long nextId() {
  long id = current.incrementAndGet();      // 先自增再用
  if (id > maxId) loadNextSegment();        // 越过段尾，异步加载下一段
  return id;
}
号段模式的两个坑：① 号段浪费——每次取 1000 个，进程重启没用完的就永远丢了（可接受：6 位空间有 568 亿）；② 取号段时 DB 抖动 = 发号暂停——解法是"双 buffer"：当前段用到 80% 时就异步预取下一段，像 GC 的卡片标记。Leaf 的"双 buffer 优化"说的就是这件事。

方案选择决策树

  • 日增短链 < 10 万：号段模式单点足够，别上分布式
  • 日增短链 10 万 ~ 1 亿：号段模式 + 多实例（每实例独立 tag 或共享号段）
  • 需要嵌入时间戳做运维排查：雪花，但接受 11 位短码或截断哈希（截断有碰撞风险，必须查重）
  • 绝对不接受 ID 泄露业务量：号段/雪花 + FPE 散列输出
模块 3

存储选型：KV 还是关系型

短链的核心操作只有一个：code → long_url。看起来 KV 就够了，但"管理后台"的需求会把关系型拉回来。生产答案：两层都用。

维度纯 KV（Redis/RocksDB）关系型（MySQL）
跳转读性能极高（单机 10 万 QPS+）一般（需索引 + 连接池，单机 ~1 万 QPS）
多条件查询基本不支持（按创建者查、按时间查都困难）原生支持（索引 + SQL）
事务/一致性有限完整 ACID（生成时要保证 code 不重复）
成本内存贵（Redis），RocksDB 便宜磁盘便宜，扩容靠分库分表

生产架构：MySQL 为源，Redis 为盾

-- MySQL：唯一真相，按 code 哈希分 128 库（5 亿条 × ~300 字节 ≈ 150GB）
CREATE TABLE short_url (
  code       VARCHAR(8)  PRIMARY KEY,   -- 短码，唯一
  long_url  VARCHAR(2048) NOT NULL,   -- 原始长链
  long_md5  CHAR(32)     NOT NULL,       -- 长链摘要，判重用
  creator   BIGINT       NOT NULL DEFAULT 0,
  status    TINYINT      NOT NULL DEFAULT 1, -- 1有效 0禁用
  expire_at DATETIME     NULL,          -- NULL=永久
  KEY idx_creator (creator, id),
  KEY idx_expire (status, expire_at)   -- 过期扫描
) ENGINE=InnoDB;

-- Redis：跳转热数据，value 序列化 long_url（热点短链）
-- key: su:{code}  value: long_url  TTL: 24h + 随机偏移
-- 容量预估：热点 1000 万条 × 250 字节 ≈ 2.5GB，一个集群搞定
为什么长链要存 md5：同一个长链可能被提交多次。有 md5 就能做"相同长链返回同一短码"（幂等创建），也方便按长链反查。但 md5 相同不代表长链相同（碰撞），判重只在创建侧用，跳转侧永远以 code 为准。

长链长度必须限制（血泪教训）

有的"长链"用户会贴进几 MB 的带参 URL（追踪参数堆叠）。必须限制：入库前校验长度 ≤ 2048 字节，超长拒绝。否则存储爆炸、MySQL 单行超限（行大小限制 65535 字节）、缓存价值归零。

模块 4

跳转：301 还是 302

这是短链第一个真正的架构决策。HTTP 重定向有两个状态码，行为差异巨大，选错要么丢统计、要么白烧带宽。

维度301 Moved Permanently302 Found（临时重定向）
浏览器行为永久缓存跳转，后续点击直接去目标，不再请求短链服务每次都请求短链服务
服务端压力低（只扛首次）高（每次都打到你）
点击统计统计不到（浏览器本地跳了）完整统计
修改目标已缓存的用户改不了随时改，下次点击生效
禁用短链缓存用户仍能打开立即生效
# 302 响应（带统计 + 风控能力，业界主流选择）
HTTP/1.1 302 Found
Location: https://item.example.com/detail?id=1234567
Cache-Control: no-cache          # 禁止中间层缓存重定向结果

# 301 的正确用法：短链服务自身做"永久跳转"场景，如域名迁移、旧域名归档
# 301 + Location: 新短域名/新码 —— 让浏览器把旧短域名整个缓存掉
最常见的选型错误：用了 301 又要点击统计。结果是统计数字永远偏低（只有首次点击被记录），而且短链被投诉下架时，浏览器缓存里的用户还能打开——这在内容合规场景是严重事故。需要统计/风控/可禁用，一律 302；纯粹省带宽的静态归档场景才用 301。

CDN 与缓存层的配合

  • 302 不缓存（Cache-Control: no-cache），所以 CDN 对跳转请求基本是"透传 + 边缘回源"，帮不上忙，别指望 CDN 抗跳转
  • CDN 真正的作用是 DNS 调度到最近边缘节点 + 静态资源（管理后台、JS SDK）
  • 如果想用 CDN 抗跳转读，可以上"边缘短链"方案：把热映射推到边缘节点（如腾讯云 EdgeOne 的边缘 KV），命中就直接在边缘跳，不回源。代价是数据一致性弱化，适合热点链接
模块 5

高并发读优化

跳转是纯读、无副作用、允许最终一致——这是缓存的完美场景。目标：把 40 万 QPS 的峰值挡在离用户最近的地方。

四级缓存体系与命中率

层级命中率说明
OpenResty 本地缓存~85%在网关层用 Lua 直接查共享 dict 缓存（lua_shared_dict），不经过应用，单机 5 万+ QPS
应用本地缓存（Caffeine）~10%防 Redis 热 key，TTL 60 秒，容量 10 万条
Redis 集群~4%主力分布式缓存，热点 key 单独实例
MySQL~1%兜底 + 回填缓存。真正落到库的读要 < 1%
-- OpenResty 层 Lua：跳转全流程在网关完成，不回源应用
local cache = ngx.shared.shortlink_cache   -- 共享内存 dict
local code = ngx.var.code

-- 1. 本地缓存命中
local target = cache:get(code)
if target then
  return redirect(target)
end

-- 2. 未命中 → Redis（连接池，避免每请求新建连接）
local redis = require("resty.redis")
local red = redis:new()
red:set_timeout(50)          -- 50ms 超时，慢于这个值直接降级
red:connect("127.0.0.1", 6379)
target = red:get("su:"..code)
red:set_keepalive(10000, 100) -- 连接池复用

if target then
  cache:set(code, target, 60)  -- 回填本地，60 秒
  return redirect(target)
end

-- 3. 未命中 → 回源应用查 DB 并回填；DB 也没有 → 404 页
return origin_lookup(code)

热 key 与冷 key 的分治

  • 热 key（爆款短链，QPS 占单 key 万级）：本地缓存吸收 + 必要时该 key 多副本（如 su:{code}:1 ~ su:{code}:16 随机读，写时全写）
  • 冷 key（长尾，创建后无人点）：只存在于 MySQL，别灌 Redis，否则缓存 99% 是垃圾，命中率暴跌
  • 缓存预热：Top 100 万热短链提前灌入 OpenResty 本地缓存，大促/晚会前必做
本地缓存的一致性代价：本地缓存 60 秒 TTL 意味着"禁用短链"最多 60 秒后才全网生效。合规场景（诈骗链接下架）不能忍——解法是主动失效广播：禁用操作发 MQ，各网关节点订阅后删本地缓存，生效时间从 60 秒降到 1 秒内。记住：本地缓存必须配主动失效通道，否则就是合规隐患。
模块 6

防刷与风控

短链是黑产的重灾区：刷点击量骗营销结算、把短链当钓鱼入口、把服务当免费跳板。防刷不是可选项，是短链系统的内置模块。

手段做法拦什么
短码不可遍历发号加散列（FPE），不用连续自增批量爬取全部短链
IP 限流网关层每 IP 100 次/分钟，超限返回 429 或验证码页单机刷量
单短链限流单 code 超过 1 万 QPS 时触发人机校验集中刷单个链接
目标页审查创建时 + 定时任务扫描目标域名，对接黑产/赌博/诈骗 URL 库恶意内容（合规红线）
设备指纹JS SDK 采集浏览器特征，识别模拟器/群控高级刷量（换 IP 不换设备）
验证码异常流量弹滑块/短信验证，通过后短期免验机器流量
# 网关限流（OpenResty，按 IP，令牌桶）
lua_shared_dict limit_store 100m;
access_by_lua_block {
  local limit = require "resty.limit.count"
  local lim = limit:new("limit_store", 100, 60)  -- 100 次 / 60 秒
  local key = ngx.var.remote_addr
  local delay, err = lim:incoming(key, true)
  if not delay then
    if err == "rejected" then
      ngx.exit(429)   -- 或跳验证码页
    end
  end
}
合规是短链的生死线：短链被用于钓鱼/赌博，服务方要担连带责任。必须做到：创建时审核（或先跳中间页提示）+ 定时扫描 + 用户举报通道 + 一键全渠道禁用（含主动失效广播）。这四件事做不到，就不要对外提供短链服务。
模块 7

数据分析：点击埋点

短链的核心商业价值是知道每个链接被谁、在哪、什么时候点了。埋点的第一原则：绝不能让统计拖慢跳转。

异步埋点链路

跳转时采集：在网关层拿 IP（解析地域）、UA（解析设备/浏览器）、Referer、时间戳、code——不查库，纯内存操作
发 MQ 不等待：采集数据写 Kafka（本地聚合 100 条或 100ms 批量发），不等 ACK，失败就丢——统计允许秒级丢失，跳转不能慢 1ms
双路消费：实时路（Flink 聚合分钟级 PV/UV/地域，进 Redis 供实时看板）+ 离线路（落 ClickHouse/Hive，T+1 报表）
UV 去重：实时 UV 用 HyperLogLog（误差 0.81% 可接受）；精确 UV 用 (code, 日期, 设备指纹) 离线去重

埋点字段设计

字段说明
code / ts / trace_id短码、点击时间（毫秒）、链路 ID（串起跳转和后续转化）
ip / geoIP 及解析出的国家省市运营商
ua / os / deviceUA 原文 + 解析出的操作系统、设备类型
referer / channel来源（微信/微博/短信）、UTM 参数透传
统计数字永远对不齐是常态，提前和业务达成一致：实时 PV 与离线 PV 差 1%~3%（MQ 丢消息、Flink 窗口边界）；UV 误差 1% 左右（HyperLogLog）。结算类数据（分润、计费）一律以离线 T+1 为准，实时数据只做监控看板。
模块 8

容量估算与过期回收

容量估算是短链面试/评审的必答题。套路固定：从业务量出发，分读写两条链路算，每步给公式。

读链路（跳转）

// 输入：日均 10 亿次跳转，峰值集中在晚 8-9 点占 15%
峰值 QPS = 10亿 × 0.15 / 3600 = 41.7 万 QPS

// 分层吸收（命中率见模块 5）
OpenResty 本地缓存扛掉 85% → 剩余 6.3 万 QPS 穿透
Redis 扛掉剩余的大部分 → MySQL 实际读 = 41.7万 × 4% × 1% ≈ 167 QPS

// 带宽（大头是响应，跳转响应 ≈ 300~500 字节）
41.7 万 QPS × 400 字节 ≈ 167 MB/s 出站带宽
// → 单机 1Gbps=125MB/s，至少 2 台起步；按 3 台 + 30% 冗余 = 4 台网关

// Redis 容量：热点 1000 万条 × 250 字节 ≈ 2.5GB → 1 主 2 从足够

写链路与存储

// 输入：日均 200 万次创建，存量 5 亿条，保留 5 年
// 单条存储：code 7B + long_url 平均 300B + 元数据 100B ≈ 407B，按 512B 算
5 亿 × 512B ≈ 256 GB（MySQL 分 128 库，每库 2GB，非常轻松）

// 写 QPS：200 万 / 86400 ≈ 23 QPS 平均，晚高峰 × 5 ≈ 115 QPS
// 23 QPS 的写，单库 MySQL 都富余 —— 短链的写在存储层根本不是问题

// 冷数据归档：3 年前且 90 天无点击 → 迁 HBase/对象存储，MySQL 只留 3 年
容量估算的三个结论（记住这些数量级）：① 短链是读:写 ≈ 5000:1 的系统，所有容量问题都是读问题；② 10 亿次日跳转发号量只有几十 QPS，号段模式绰绰有余；③ 真正贵的是带宽和网关机器（40 万 QPS 不是缓存能全挡的），不是存储。

过期与回收

  • 过期判定在跳转侧：读到映射先查 expire_at < now 或 status=0，是则返回"已过期"页，不给跳
  • 物理回收：每日任务扫描 idx_expire 索引，批量删除 + 删 Redis key + 发失效广播
  • 短码绝不回收复用：用户书签、已发出的短信里的旧码必须继续有效或明确提示失效。复用短码 = 把 A 的用户导去 B 的页面，是重大事故
  • Redis TTL 设 24h + 随机 0~600 秒：避免同时失效引发缓存雪崩，同时保证禁用操作最长 1 天内生效
模块 9

十个线上坑

1
用 301 又要点击统计
浏览器永久缓存跳转，后续点击不再请求服务端，统计永远偏低；禁用短链也不生效。要统计/风控一律用 302。
2
短码用连续自增 ID，可被遍历
000001、000002 顺序可猜，竞品能爬走你全部链接。发号后必须做散列（FPE/Feistel）输出。
3
跳转链路同步写埋点
每次跳转等 Kafka ACK，P99 从 5ms 涨到 50ms，40 万 QPS 下网关全被打挂。埋点必须本地聚合 + 异步发，丢就丢。
4
本地缓存没有主动失效通道
60 秒 TTL 意味着禁用一个钓鱼链接要等 1 分钟，合规事故事故。禁用操作必须发广播删各节点本地缓存。
5
不限制长链长度
用户贴进几 MB 的追踪参数长链，MySQL 单行超限、缓存价值归零。入库前强制 ≤ 2048 字节。
6
所有短链无脑灌 Redis
冷 key 占满内存，命中率暴跌还浪费钱。只灌 Top 100 万热链，长尾留在 MySQL。
7
回收的短码重新分配给新链接
用户书签/旧短信里的码跳到别人的页面，重大事故。短码一次性，永不复用。
8
号段模式单发号实例，没有预取
号段用完同步等 DB，发号 P99 飙到几十毫秒；DB 抖动直接发号中断。用双 buffer 预取下一段。
9
没有防刷，被当成免费跳板
黑产刷量骗结算、挂钓鱼页，服务方担连带责任。IP 限流 + 单链限流 + 目标页审查 + 验证码，一个不能少。
10
创建短链不做幂等
同一长链重复提交生成多个短码，统计分散、管理混乱。用 long_md5 做唯一约束或创建前查重，相同长链返回同一短码。
自测

六道题

1. 短链系统需要完整统计每次点击、并能随时禁用某个链接，应该用哪个状态码？
正确答案：302。301 会被浏览器永久缓存，后续点击不再请求服务端，统计不到也禁不掉。302 每次都回服务端，统计和禁用都能生效（代价是服务端要扛全部读流量，靠缓存体系解决）。
2. 6 位 Base62 短码的总容量约为多少？
正确答案：约 568 亿（62 的 6 次方 = 56,800,235,584）。3.5 万亿是 7 位的容量；6200 万是混淆项。5 亿存量短链用 6 位，空间余量 100 倍以上。
3. 美团 Leaf 的"号段模式"核心思想是？
正确答案：批量取号段 + 内存分配。10 万 QPS 的发号需求，DB 实际只承受 10 万/1000 = 100 QPS。进阶是双 buffer 预取，避免号段用完时同步等待。
4. 关于短链的埋点，正确做法是？
正确答案：本地聚合 + 异步发送。跳转延迟是生死线（40 万 QPS），统计允许秒级丢失。同步等 ACK 会让 P99 从 5ms 恶化到 50ms，直接打挂网关。
5. 日跳转 10 亿次、峰值 15% 集中在 1 小时，峰值 QPS 约为多少？
正确答案：约 42 万 QPS。10 亿 × 0.15 ÷ 3600 秒 ≈ 41.7 万。1.2 万是"除以 24 小时"的日均值错误算法；280 万是没乘峰值系数的错误。容量规划必须用峰值，用均值备容量等于裸奔。
6. 一个短链过期被回收后，它的短码应该如何处理？
正确答案：永不复用。用户书签、已发出的短信/物料里的旧码还在流传，复用会把 A 的用户导去 B 的页面，是重大事故。568 亿的空间完全不需要靠复用节省。
