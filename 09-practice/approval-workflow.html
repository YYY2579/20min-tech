开始前

工作流四个核心概念

所有工作流系统（无论自研还是 Camunda）都围绕四个实体。分清"定义"和"实例"，是理解一切的前提。

概念是什么类比
流程定义
Process Definition		流程的模板：有哪些节点、什么顺序、谁审批。部署后不可变Java 的 Class
流程实例
Process Instance		一次具体的审批（如"张三的 2026-10 报销单 #1024"）。从开始事件跑到结束事件Java 的 Object
任务
Task / Activity		实例中的某个节点。用户任务（待人工审批）和服务任务（系统自动执行）都要落库一次方法调用
网关
Gateway		控制流向：排他网关（XOR，二选一）、并行网关（AND，都走）、包含网关（OR，条件组合）if / fork / switch
一次报销审批的完整生命周期（文字版时序）
1. 张三提交报销 12000 元 → 启动实例 I-1024（引用流程定义 D-EXPENSE v3）
2. 引擎创建任务 T1 = "直属经理审批"，分配给李四（张三的 leader）
3. 李四点"同意" → T1 完成 → 引擎推进到排他网关 G1
4. G1 求值：amount > 5000 = true → 走向"总监审批"分支
5. 创建任务 T2 = "总监审批"，分配给王五
6. 王五点"同意" → T2 完成 → 并行网关 G2（AND）：同时分出两个服务任务
   - S1 打款（调用财务系统 API）
   - S2 发通知（调用消息中心）
7. S1、S2 都完成 → 汇入结束事件 → 实例状态 = COMPLETED

关键认知：实例 I-1024 引用的是定义 D-EXPENSE v3，
即使之后部署了 v4，这个实例仍按 v3 跑完 —— 这就是模块 5 的版本隔离
模块 1

BPMN 2.0 基础元素与代码映射

BPMN 2.0 是审批流的"标准语言"。不需要全会画，但必须知道每个图形元素对应引擎里的什么行为，否则你看流程定义 XML 像看天书。

1.1 必懂的 12 个元素

元素图形语义与代码映射
开始事件 Start Event单线圆实例入口。消息开始事件 = 等外部消息（如"表单提交"）才启动
结束事件 End Event粗边圆实例终止。错误结束事件 = 抛出 BPMN Error 供上层捕获
用户任务 User Task圆角矩形+人像生成一条待办：assignee（指定人）/ candidateUsers（候选组）
服务任务 Service Task圆角矩形+齿轮自动执行：调 Java Delegate / HTTP / Expression（如 ${bean.method()}）
排他网关 Exclusive (XOR)菱形+×只走第一条条件为真的流。每条出流必须有 condition，否则引擎报错
并行网关 Parallel (AND)菱形++所有出流同时走（会签发起）；所有入流到齐才继续（会签汇总）
包含网关 Inclusive (OR)菱形+○所有条件为真的流都走；汇合时按完成的组合判断
序列流 Sequence Flow箭头连接线。条件流带 conditionExpression
子流程 Sub-Process大圆角矩形内嵌流程，可独立回滚。调用活动（Call Activity）= 跨流程跳转
边界事件 Boundary Event矩形边上的圆挂在节点上：超时/出错/收到消息时触发（如"审批超时自动提醒"）
消息事件 Message Event信封圆收发消息：等待外部系统回调再继续（如等支付结果）
数据对象 Data Object文档形流程变量。整个实例执行期的上下文都在这里

1.2 一段真实的 BPMN XML（报销流程）

<!-- Camunda / Flowable 通用的 BPMN 2.0 片段 -->
<process id="expense-approval" name="报销审批" isExecutable="true">

  <startEvent id="start" name="提交报销"/>

  <sequenceFlow id="f1" sourceRef="start" targetRef="managerTask"/>

  <userTask id="managerTask" name="直属经理审批">
    <extensionElements>
      <camunda:assignee>${managerId}</camunda:assignee>
      <camunda:dueDate>${dueDate}</camunda:dueDate>
    </extensionElements>
  </userTask>

  <sequenceFlow id="f2" sourceRef="managerTask" targetRef="gateAmount"/>

  <exclusiveGateway id="gateAmount" name="金额判断"/>

  <!-- 条件表达式：金额>5000 走总监，否则跳过 -->
  <sequenceFlow id="fBig" sourceRef="gateAmount" targetRef="directorTask">
    <conditionExpression>${amount > 5000}</conditionExpression>
  </sequenceFlow>
  <sequenceFlow id="fSmall" sourceRef="gateAmount" targetRef="financeTask">
    <conditionExpression>${amount <= 5000}</conditionExpression>
  </sequenceFlow>

  <userTask id="directorTask" name="总监审批">
    <extensionElements>
      <camunda:candidateGroups>director</camunda:candidateGroups>
    </extensionElements>
  </userTask>

  <parallelGateway id="fork" name="并行处理"/>
  <sequenceFlow id="f3" sourceRef="directorTask" targetRef="fork"/>
  <sequenceFlow id="f3b" sourceRef="fSmall" targetRef="fork"/>

  <userTask id="financeTask" name="财务复核"/>
  <serviceTask id="payTask" name="自动打款"
      expression="${payService.transfer(execution)}"/>
  <serviceTask id="notifyTask" name="发通知"
      expression="${notifyService.send(execution)}"/>

  <sequenceFlow id="f4" sourceRef="fork" targetRef="financeTask"/>
  <sequenceFlow id="f5" sourceRef="financeTask" targetRef="payTask"/>
  <sequenceFlow id="f6" sourceRef="payTask" targetRef="notifyTask"/>
  <sequenceFlow id="f7" sourceRef="notifyTask" targetRef="end"/>

  <endEvent id="end" name="完成"/>
</process>
XML 的工程真相：BPMN XML 是给引擎吃的，不是给你手写的。生产流程一定是可视化设计器画出来存 XML，或者干脆用 JSON 定义（Flowable 6.7+ / 自研引擎常用）。手写 XML 只发生在流程极简单（3~5 节点）或需要 diff 版本时。无论哪种，XML 必须入库 + 版本化，不能只存文件系统。
模块 2

引擎选型：Camunda / Flowable / 自研状态机

选型的核心不是功能对比，是你的流程有多复杂、变更有多频繁、团队有多大。三个选项各有死穴。

维度CamundaFlowable自研状态机
定位企业级 BPM，功能最全Activiti 延续，轻量灵活状态 + 转换表
适合场景复杂流程、会签/子流程/事件多中小流程、要嵌入业务系统简单线性审批（≤6 节点）
可视化设计器有（BPMN Modeler）有（bpmn.js 同源）无（自己画或配置化）
运维成本高（20+ 张引擎表）中（28 张表左右）低（3~5 张表）
死穴重、学习曲线陡；简单流程杀鸡用牛刀社区版功能裁剪（历史数据清理等）复杂流程（并行/回退）很快失控
典型用户银行核心、保险理赔互联网中台、OA订单状态机、简单审批

2.1 自研状态机的最小实现（简单审批够用）

-- 状态机四张表，覆盖 80% 的审批需求
CREATE TABLE wf_definition (        -- 流程定义（JSON 描述，版本化）
  id           BIGINT NOT NULL AUTO_INCREMENT,
  code         VARCHAR(64) NOT NULL,    -- 'expense'
  version      INT NOT NULL,        -- 1,2,3...
  nodes_json   JSON NOT NULL,     -- [{"id":"mgr","type":"APPROVE","assigneeExpr":"managerId"}]
  edges_json   JSON NOT NULL,     -- [{"from":"mgr","to":"fin","cond":"amount>5000"}]
  status       TINYINT DEFAULT 1,  -- 1=生效 0=停用
  PRIMARY KEY (id),
  UNIQUE KEY uk_code_ver (code, version)
);

CREATE TABLE wf_instance (
  id           BIGINT NOT NULL AUTO_INCREMENT,
  def_id       BIGINT NOT NULL,   -- 引用定义版本（不可变）
  biz_type     VARCHAR(32) NOT NULL, -- 'expense'
  biz_id       BIGINT NOT NULL,   -- 业务单据 ID
  current_node VARCHAR(64) NOT NULL, -- 当前所在节点
  status       TINYINT NOT NULL,   -- 0=运行中 1=通过 2=驳回 3=撤销
  vars_json    JSON,           -- 流程变量
  create_time  BIGINT NOT NULL,
  end_time     BIGINT DEFAULT NULL,
  PRIMARY KEY (id),
  KEY idx_biz (biz_type, biz_id),
  KEY idx_status_node (status, current_node)  -- 查待办
);

CREATE TABLE wf_task (
  id           BIGINT NOT NULL AUTO_INCREMENT,
  instance_id  BIGINT NOT NULL,
  node_id      VARCHAR(64) NOT NULL,
  assignee     BIGINT NOT NULL,
  mode         TINYINT DEFAULT 1,  -- 1=或签 2=会签 3=依次
  status      TINYINT DEFAULT 0,  -- 0=待办 1=已办 2=已转办
  action       VARCHAR(16),      -- approve / reject / back
  comment      VARCHAR(500),
  create_time  BIGINT NOT NULL,
  finish_time  BIGINT DEFAULT NULL,
  PRIMARY KEY (id),
  KEY idx_assignee (assignee, status, create_time DESC)
);

CREATE TABLE wf_operation_log (       -- 全量操作流水，审计用
  id           BIGINT NOT NULL AUTO_INCREMENT,
  instance_id  BIGINT NOT NULL,
  node_id      VARCHAR(64),
  operator     BIGINT NOT NULL,
  action       VARCHAR(16) NOT NULL,  -- submit/approve/reject/back/delegate
  detail       JSON,
  create_time  BIGINT NOT NULL,
  PRIMARY KEY (id),
  KEY idx_instance (instance_id, create_time)
);
选型决策树：流程会不会经常变（业务自助配）？→ 会：Camunda/Flowable。流程固定且简单（就 3 级审批）？→ 自研状态机，别引引擎。中间态（复杂但不变，如信贷审批）→ Camunda，它的事件/子流程/事务能救命。自研的死穴从来不是"做不出"，是"半年后流程加了并行和回退，代码变成一团意大利面"。
模块 3

会签 / 或签 / 依次审批 / 条件分支

四种流转模式覆盖 95% 的审批场景。它们的底层差异在于"任务数"和"完成条件"。

模式任务模型完成条件
或签
（默认）		生成 N 个任务，分给 N 个候选人任意一人处理即完成，其余任务级联关闭
会签
（AND）		生成 N 个任务，全部必须处理全部通过才继续；一人驳回整个流程驳回（或按比例通过）
依次审批
（串行）		只生成第 1 个任务，处理完才生成下一个链条走完才继续，驳回即中断后续
条件分支网关求值，只走条件为真的流每条流都必须有 condition；必须有一条 default 兜底流
===== 会签的完整生命周期（最容易出错的地方）=====
# 发起：并行网关 fork → 生成 N 个任务（mode=会签），实例等待
# 处理：每个审批人独立 approve / reject

# 完成判定（每处理一个任务都要重算）：
def check_join(instance, node):
    tasks = load_tasks(instance, node, mode=AND)
    finished = [t for t in tasks if t.status != PENDING]
    if any(t.action == REJECT for t in finished):
        return REJECTED          # 一人否决，全盘否决
    if len(finished) == len(tasks):
        return APPROVED           # 全员通过
    return WAITING

# 关键细节 1：会签中有人驳回 → 其余 PENDING 任务必须级联置为 CANCELLED
#   否则那些审批人还能继续点"同意"，把已驳回的流程又往前推
# 关键细节 2：会签通过比例可配置（如 3/5 同意即通过）→
#   需要计数器：approved_count >= ceil(N * ratio) 时提前收敛
# 关键细节 3：会签成员动态变化（加签进来的也算）→ 任务总数以"最终人数"为准

===== 或签 =====
def handle_vote(instance, task, action):
    task.finish(action)
    if action == APPROVE:
        cancel_other_tasks(instance, task.node)   # 关闭同节点其余任务
        advance(instance)
    else:
        reject_flow(instance, task.comment)
# 或签的坑：A 点了同意推进了流程，B 的旧任务还挂在待办列表 → 用户看到"幽灵待办"

===== 条件分支的兜底 =====
# 排他网关求值时，所有 condition 都不匹配怎么办？
# 必须配 default 流（default="fSmall"），否则流程卡死在网关，实例永远不结束
# 工程铁律：每个排他网关必须有 default 流，且条件表达式求值失败也要走 default
会签三大事故：① 一人驳回后没级联取消其他任务，其他审批人继续同意，流程状态错乱；② 按比例会签没做计数器并发控制，第 3 票同意时重复触发"流程通过"；③ 会签成员列表在审批途中被改了（组织架构调整），导致等待一个永远不处理的任务。解法：每个任务处理都在同一事务里重算完成条件 + 级联取消，成员变更走模块 4 的代理机制而不是直接改任务表。
模块 4

审批人、代理与加签

真人世界的审批充满意外：审批人休假了、临时要加一个领导、需要转给下属办。工作流系统必须把这四种"人"的变化建模成一等公民。

操作语义实现要点
委托
Delegate		"我休假期间的单子都归小李"规则级：用户维度 + 时间维度。分配任务时按规则改 assignee，原审批人仍可见
转办
Transfer		"这一单转给小王处理"任务级：改当前任务 assignee，记录操作日志，旧任务置 TRANSFERRED
加签
AddSign		"这单还得赵总看一下"在当前节点前插入新任务。会签加签 = 全员重审；或签加签 = 二选一
减签
RemoveSign		"小李不用审了"撤销指定任务。已处理的不能减，只能记录作废意见
# 委托规则（分配时动态解析，不是改任务表）
-- delegate_rule(user_id, delegate_to, start_time, end_time, biz_types_json)
-- 分配算法：assignee = 当前用户
--           rule = 查 delegate_rule（用户匹配 + 时间覆盖 + 业务类型匹配）
--           if rule exists: assignee = rule.delegate_to，任务记录 origin_assignee

# 转办（任务级，一次性的）
UPDATE wf_task SET assignee = :newUserId, status = 0
WHERE id = :taskId AND assignee = :currentUserId AND status = 0;

-- 流程推进到节点时才解析当前岗位的现任负责人
-- 已生成但未处理的任务 → 定时任务扫描，按岗位重新解析并迁移（带日志）
审批人设计的核心原则：任务分配用"岗位 + 规则"解析，不要存死"人"。存死人的后果：审批人离职后，他的待办成了幽灵，流程永远推进不了。按岗位解析时，解析时机也有讲究：提交时解析（快，但组织变化后过期）vs 节点激活时解析（慢一点，但永远准确）——生产推荐节点激活时解析，未处理的旧任务用补偿任务修正。
模块 5

流程版本与迁移

流程一定会改：加一个审批节点、改一个条件。版本管理的核心问题：改定义后，正在跑的旧实例怎么办？

5.1 版本部署与隔离

策略做法适用
新实例用新版
（推荐）		部署 v(N+1)，存量实例继续按 vN 跑完绝大多数场景。简单、无风险
全量迁移把存量实例的节点映射到新版对应节点仅当旧版有 bug 必须修复时；需要节点映射表
双轨并行按业务属性分流（如金额 > 1 万走新版）大版本灰度，观察新版稳定性
# 版本切换的最小风险流程
1. 新定义以 version = N+1 入库，status = DRAFT（不影响任何实例）
2. 用 10 条影子实例（模拟数据）跑新版，验证每个节点/网关/条件
3. 灰度：按业务 ID 哈希 5% 新实例走 N+1，对比通过率/耗时/驳回率
4. 全量：version = N+1 设为 ACTIVE，新启动的实例全部引用它
5. 存量：vN 实例继续跑完（原则：不迁移运行中的实例）
6. 观察：vN 全部结束后，vN 归档为 DISABLED（不可启动，仅可查询）

# 必须迁移时的节点映射（旧版删了节点/改了 ID）
-- migration_map(def_id_old, def_id_new, node_old, node_new)
-- 迁移脚本：按 current_node 查 map，找不到映射的实例挂起并告警，绝不瞎猜

5.2 回退与中止

  • 回退（Back）：审批人驳回到指定节点（通常是上一个）。实现=当前节点及之后已完成的任务全部标记作废，在目标节点重新生成任务，变量回滚到该节点的历史快照。不能只改 current_node，任务和变量都要跟着回退
  • 撤销（Withdraw）：申请人主动终止未完成实例，状态置 CANCELLED，所有待办级联关闭。已执行的副作用（如已打款）要触发补偿
  • 中止（Terminate）：管理员强制结束异常实例（如业务流程依赖的系统挂了）。必须记录原因，且允许重启新实例
回退是最容易写出 bug 的功能：常见三种错——① 只改了 current_node，旧任务还在待办列表里（审批人还能点同意）；② 回退后变量没恢复，下游节点读到中间态数据；③ 回退到已执行的并行分支，分支任务重复生成。正确做法：回退 = 事务内完成"作废未来任务 + 恢复节点 + 恢复变量快照 + 写日志"四件事，缺一不可。
模块 6

与业务系统集成

工作流引擎是"协调者"，不是"业务实现者"。集成设计的核心是：谁调谁、失败怎么办、状态怎么对齐。

6.1 三种集成方式

方式机制适用与坑
同步 API 调用业务系统调引擎 REST API（启动实例、查询待办、完成任务）简单直接。但审批动作要事务：引擎状态和业务状态必须一致，建议引擎写本地消息表，业务最终一致
事件订阅引擎发 MQ 事件（task_created/instance_completed），业务系统订阅消费解耦。坑：消息丢失/重复 → 消费必须幂等（按事件 ID 去重）；消息乱序 → 带版本号
回调 / 服务任务流程推进到服务任务时，引擎回调业务系统 HTTP/Java 接口适合编排业务动作。坑：回调超时 → 重试策略 + 幂等 + 死信队列
# 审批通过 → 触发业务动作（事件方式的标准实现）
# 1. 审批人点"同意" → 引擎事务内：更新任务 + 推进实例 + 写 outbox 表
INSERT INTO wf_outbox (event_id, event_type, payload, status)
VALUES (uuid, 'instance_completed', '{"instanceId":1024}', 0);
# 2. 独立投递器扫 outbox → 发 MQ → 标记已发送（本地事务保证必达）
# 3. 业务系统消费：审批通过 → 执行打款（幂等：按 instanceId 查是否已打）

# 为什么必须 outbox 而不是直接发 MQ？
# 直接发：MQ 发送成功但本地事务回滚 → 事件是假的，业务执行了不该执行的动作
# outbox：事件和状态变更同一个本地事务，必达且一致（事务消息的标准模式）

# 回调重试策略（服务任务）
-- 重试 3 次，间隔 1s / 10s / 60s，仍失败进死信队列 + 告警
-- 回调接口必须幂等：携带 execution_id + task_id，业务侧按此去重

6.2 待办中心

待办不是引擎的事，是业务门户的事：聚合各流程来源的待办（OA、财务、HR），统一展示/处理/已办。引擎只提供"我的任务"查询接口，待办中心做聚合和权限过滤。

模块 7

性能：实例量大时的索引与归档

审批流的量特征是实例数随业务线性增长，且永远只查"最近的"和"我的"。性能设计围绕两个词：索引和归档。

7.1 索引策略

查询场景索引说明
我的待办(assignee, status, create_time DESC)最高频。覆盖 90% 流量
按业务单查流程(biz_type, biz_id)详情页反查，唯一
运行中的实例(status, current_node)运维监控、超时扫描
实例的操作流水(instance_id, create_time)审批记录页，按时间倒序
超时任务扫描(status, due_time)定时任务扫将超时/已超时
# 容量算例：日均 5 万实例，平均 4 个任务/实例
# 实例表：5万/天 × 365 × 3年 = 5.5亿行 → 单表放不下
# 任务表：20万/天 × 3年 = 2.2亿行
# 流水表：假设每实例 6 次操作 = 30万行/天 × 3年 = 3.3亿行

# 分治方案：
# 1. 热数据（90 天内）留主库：覆盖绝大多数查询
# 2. 冷数据（90 天前）迁历史库：wf_instance_2024 / wf_task_2024 按年分表
# 3. 已完成实例 30 天后压缩：vars_json 大字段单独存对象存储，主表留摘要
# 4. 运行中实例永远热：status=0 的数据量 = 5万/天 × 平均流转 3 天 ≈ 15万行，无压力

# 归档任务（夜间低峰执行）
-- DELETE 主库？不行，要可查！INSERT INTO 历史库 SELECT ... 后，
-- 主库按 id 范围 DELETE（限流批删，每批 1000 行，sleep 100ms，避免主从延迟）
-- 查询侧：先查主库，未命中再查历史库（按年路由），前端无感知
实例量大时的三个性能杀手：① count(*) 统计待办数量——大表 count 全表扫描，改维护计数器或用 explain 友好的近似值；② 深分页查已办列表——用 (finish_time, id) 游标，别用 offset；③ 定时任务全表扫超时——按 (status, due_time) 索引 + 增量扫描（记录上次扫到的最大 id），不要每小时全表过一遍。
模块 8

十个线上坑

1
排他网关没配 default 流，条件都不匹配时流程卡死
实例永远停在网关，既不推进也不报错。每个排他网关必须有兜底流，条件求值异常也要走 default。
2
会签一人驳回后，其他待办没级联取消
其他审批人继续点同意，已驳回的流程又被推着走，状态机错乱。驳回必须同事务级联取消全部 PENDING 任务。
3
或签先处理的人推进了流程，后处理的人点"同意"成功
旧任务没关，用户重复提交。完成任务必须校验任务属于当前节点且仍 PENDING（WHERE status=0）。
4
审批人存死"人"而不是"岗位"，人离职后流程卡死
离职账号的待办永远没人处理。按岗位/规则在节点激活时解析审批人，历史任务用补偿任务迁移。
5
回退只改 current_node，旧任务和变量没恢复
审批人还能在旧节点点同意；下游读到中间态变量。回退必须四件套：作废任务 + 恢复节点 + 恢复变量快照 + 写日志。
6
流程版本切换时，存量实例被新版定义污染
实例推进时按最新版定义解析节点，旧实例走到新节点直接报错。实例必须锁定启动时的 def_id，版本隔离不可变。
7
审批动作没做幂等，重复点击/网络重发导致双审批
打款执行了两次。所有写操作按 (task_id, action) 唯一约束或乐观锁，接口层也要防重令牌。
8
直接发 MQ 通知业务系统，不用事务消息
MQ 发送成功但本地事务回滚，业务系统执行了假事件。必须 outbox 模式：事件与状态变更同事务，独立投递器发送。
9
待办列表用 count(*) 统计总数
任务表过亿后，每次打开待办页全表扫描，页面卡死。改维护计数器或近似值，列表用游标分页。
10
流程定义只存 XML 文件不进库，无版本概念
改一次流程覆盖旧文件，正在跑的实例引用不到原定义，回滚无从谈起。定义必须入库 + 版本化 + 生效/停用状态。
自测

六道题

1. 会签（并行审批）中，5 个审批人有 1 人点了"驳回"，系统应该怎么做？
正确答案：立即驳回 + 级联取消。会签一人否决全盘否决（除非配置按比例通过）。其余 PENDING 任务必须同事务取消，否则那些审批人还能继续点"同意"，把已驳回的流程又往前推。
2. 流程定义从 v2 升级到 v3（新增一个审批节点），正在跑的 v2 实例应该？
正确答案：实例锁定启动时的定义版本。实例引用 def_id 后不可变，v2 实例跑完为止。只有旧版有严重 bug 时才做节点映射迁移。自动升级会让旧实例走到新节点直接报错。
3. 审批通过后要通知财务系统打款，最可靠的集成方式是？
正确答案：outbox 事务消息 + 幂等消费。直接同步调用会把外部系统稳定性绑进本地事务（财务挂了流程也提交不了）；轮询有延迟且量大后压力大。outbox 保证事件与状态变更原子，MQ 保证可靠投递。
4. 审批人"张三"下周休假，他期间的单子都要归"小李"处理，应该实现为？
正确答案：委托规则。转办是任务级一次性操作，只处理已生成的单；委托是规则级，覆盖时间窗内所有新任务。分配时解析，原审批人 origin_assignee 保留可查。
5. 一个跑了 3 年、5 亿实例的审批系统，"我的已办"列表打开越来越慢，最可能的原因和解法？
正确答案：分页方式 + 归档策略。offset=10000 要扫描丢弃前 1 万行；count(*) 在大表上是全表扫描。解法：游标分页（finish_time, id）、待办数用计数器、90 天前数据迁历史库按年分表。
6. 自研状态机做审批流程，最可能在哪类需求上失控？
正确答案：并行 + 回退组合。线性和简单分支用状态机很优雅；但并行分支的 join 判定、回退时的任务作废与变量恢复、加签的任务插入与唤醒，会让状态机代码迅速膨胀成意大利面。这类场景应该上 Camunda/Flowable。
