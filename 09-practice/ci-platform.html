模块 1

CI 平台架构：四大件

无论自研还是用开源，一个 CI 平台都由四个核心组件构成。先把职责分清楚，再看开源方案各自动了哪块。

组件职责关键指标
调度器 Scheduler接收触发（webhook/定时/手动），展开 DAG，分配任务到执行器调度延迟 < 1 s；支持优先级队列
执行器 Executor真正跑构建的容器/VM。拉代码、装依赖、编译、跑测试、传产物并发数；单任务资源规格；启动耗时
缓存服务 Cache依赖缓存、Docker 层缓存、构建产物的分布式存储命中率（目标 70%+）；拉取带宽
制品库 Artifacts二进制产物的存储、版本管理、晋级、检索可用性 99.99%；拉取延迟；不可变性
辅助件Secret 管理（Vault）、日志服务、审计、通知日志秒级可见；审计留存 180 天+

一次构建的完整旅程

代码 push ──> Webhook ──> API 服务 ──> 调度器
                                    │

容量估算（给过程）

# 假设：日均 2 万次构建，平均耗时 6 分钟，峰值是平均的 5 倍
平均并发 = 20000 × 6 ÷ (24 × 60) = 83 个并发任务
峰值并发 = 83 × 5 = 415 个并发任务

# 单任务规格 2C4G，K8s 节点 8C16G（每节点跑 3 个任务 Pod）
所需节点 = 415 ÷ 3 ≈ 140 台节点（预留 20% 缓冲 ≈ 170 台）

# 缓存流量：60% 任务命中缓存，平均拉 500MB
缓存带宽 = 415 × 60% × 500MB ÷ 6min ≈ 35 MB/s（持续）
# 结论：并发是容量规划的第一变量，缓存带宽是第二变量
模块 2

流水线模型：DAG 编排

流水线不是"阶段串行"那么简单。现代 CI 的核心抽象是 DAG（有向无环图）：任务声明依赖，调度器按拓扑序执行，能并行的并行。

概念说明
阶段 stage粗粒度串行边界：build 完才 test。适合门禁语义（不过测试不许部署）
任务 job/task最小执行单元，同 stage 内默认并行
DAG 依赖任务级依赖声明。test 只需等 build，不等同 stage 的其他任务，省等待时间
矩阵 matrix一个任务模板 × 多组参数展开（如 Go 1.21/1.22 × linux/mac）
并发组同一 group 的任务互斥，新触发可取消旧的（cancel-in-progress）
触发器push / MR / tag / 定时 / 手动 / API，各自配过滤规则

GitLab CI 完整示例（DAG + 矩阵 + 环境）

# .gitlab-ci.yml
stages: [build, test, deploy]

variables:
  GOPROXY: "https://goproxy.cn,direct"

build:
  stage: build
  image: golang:1.22
  script:
    - go build -ldflags "-s -w" -o app ./cmd/server
  artifacts:
    paths: [app]
    expire_in: 1 week

test-unit:
  stage: test
  needs: [build]          # DAG：只依赖 build，不等同 stage 其他任务
  image: golang:1.22
  script:
    - go test -race -coverprofile=cover.out ./...
  coverage: '/coverage: \d+.\d+%/'

test-matrix:
  stage: test
  needs: [build]
  parallel:
    matrix:               # 2×2 = 4 个任务并行
      - GO: ["1.21", "1.22"]
        OS: ["linux", "darwin"]
  image: golang:$GO
  tags: [$OS-runner]
  script:
    - go test ./...

deploy-staging:
  stage: deploy
  needs: [test-unit, test-matrix]   # 两个 test 都过才部署
  environment:
    name: staging
  script:
    - ./deploy.sh staging
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy-prod:
  stage: deploy
  needs: [deploy-staging]
  environment:
    name: production
  script:
    - ./deploy.sh prod
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  when: manual            # 生产部署必须人工确认

Jenkins Declarative Pipeline（K8s 动态 agent）

// Jenkinsfile
pipeline {
  agent {
    kubernetes {
      yaml '''
        apiVersion: v1
        kind: Pod
        metadata:
          namespace: ci
        spec:
          containers:
          - name: builder
            image: golang:1.22
            command: ['sleep']
            args: ['99d']
            resources:
              requests: {cpu: "2", memory: "4Gi"}
              limits:   {cpu: "4", memory: "8Gi"}
      '''
    }
  }
  options {
    timeout(time: 30, unit: 'MINUTES')
    disableConcurrentBuilds()          # 同分支并发互斥
    buildDiscarder(logRotator(numToKeepStr: '50'))
  }
  stages {
    stage('Build') { steps { sh 'go build -o app ./cmd/server' } }
    stage('Test') {
      parallel(
        'unit': { sh 'go test -race ./...' },
        'lint': { sh 'golangci-lint run' }
      )
    }
  }
  post {
    always  { junit 'report.xml' }
    failure { slackSend channel: '#ci', message: "failed: ${env.BUILD_URL}" }
  }
}
矩阵的乘法陷阱：matrix 是笛卡尔积。GO × OS × ARCH = 2 × 2 × 2 = 8 个任务；再加数据库版本就变成 24 个。上线前必须算组合数，超 10 个组合的任务要考虑拆成多个 job 或用 exclude 剪枝，否则一次 push 打满整个集群。
模块 3

执行环境：容器化 Executor

执行环境的核心要求是无状态和一致性：每次构建都是干净环境，构建之间互不影响。这是"可复现构建"的基础。

Executor 类型隔离性适用
容器 executor进程级（Namespace/CGroup）主流。K8s Pod / Docker，秒级启动
VM executor硬件虚拟化级需要完整内核隔离、特殊内核参数的场景（如某些安全构建）
bare-metal无性能压测、特定硬件依赖（iOS 构建需 macOS）

关键机制

# 1. 每次构建全新 Pod：代码在 emptyDir，跑完即毁，绝不复用
#    杜绝"上次构建的残留文件"导致的环境漂移

# 2. 镜像预热：常用基础镜像预拉到节点
#    冷启动 Pod ≈ 2~5 s（拉镜像占大头），预热后 < 1 s
#    预热池：维护"最近 N 天用过的镜像"列表，DaemonSet 定时同步

# 3. 资源配额：每个 namespace 设 ResourceQuota，防一个业务抢光集群
apiVersion: v1
kind: ResourceQuota
metadata:
  name: ci-quota
  namespace: ci
spec:
  hard:
    requests.cpu: "200"
    requests.memory: 400Gi
    limits.cpu: "400"
    limits.memory: 800Gi
    pods: "200"

# 4. sidecar 模式：主容器构建，sidecar 负责日志上报/缓存上传/制品上传
#    主容器只关心业务命令，平台能力全部下沉到 sidecar

# 5. 超时与清理：
#    任务级 timeout（如 30 分钟）、僵尸 Pod 回收（GC 控制器，15 分钟扫一次）
可复现构建三件套：pin 镜像 digest、lock 依赖版本、记录工具链版本。任何一环用了浮动版本（latest、*、SNAPSHOT），构建就不可复现，线上事故复盘时无法还原当时的二进制。正确写法：FROM golang:1.22.5@sha256:abc...、go.sum 提交入库、CI 里打印 go version 与编译器信息进产物元数据。
模块 4

构建加速：缓存设计

构建慢的账：拉依赖 60%、编译 25%、拉镜像 10%、其他 5%。缓存是唯一能把分钟级压到秒级的手段，而缓存的关键全在 key 设计。

四类缓存

类型缓存什么典型位置
依赖缓存maven ~/.m2、npm node_modules、go mod、pip cache分布式缓存（S3/NAS）按 key 拉取
Docker 层缓存镜像构建的每一层registry 或 BuildKit cache
构建工具缓存Gradle build cache、Bazel action cache、ccache分布式缓存服务
缓存挂载构建过程产生的临时目录BuildKit cache mount

缓存 key：命中率的全部

# 错误的 key：对源码内容做 hash
cache:
  key:
    files: [**/*.go]        # ✗ 改一行代码 → 全量 hash 变化 → 缓存全失效
  paths: [.cache/go-build]

# 正确的 key：只对"依赖声明文件"做 hash
cache:
  key:
    files: [go.sum]         # ✓ 依赖没变 → 命中；依赖变了 → 才失效
  paths: [.cache/go-build]

# 通用公式：
#   cache key = hash(依赖 lock 文件) + 运行时版本 + 平台标识
#   例：go1.22-linux-{{ checksum "go.sum" }}

# 不同生态的 lock 文件：
#   Go:     go.sum        Node: package-lock.json / pnpm-lock.yaml
#   Java:   pom.xml(或 gradle.lockfile)   Python: requirements.txt(带 hash)
#   Rust:  Cargo.lock    PHP: composer.lock

Docker 多阶段构建 + BuildKit 缓存挂载

# syntax=docker/dockerfile:1
FROM golang:1.22.5 AS builder
WORKDIR /src

# 第一层：只拷依赖声明（变化少，命中率高）
COPY go.mod go.sum ./
RUN go mod download

# 第二层：拷源码编译
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go build -ldflags "-s -w" -o /app

# 运行阶段：精简基础镜像，无编译工具链
FROM gcr.io/distroless/static-debian12
COPY --from=builder /app /app
ENTRYPOINT ["/app"]

# 构建命令（缓存推到 registry，团队共享）：
docker buildx build \
  --cache-from type=registry,ref=registry.example.com/cache/app:buildcache \
  --cache-to   type=registry,ref=registry.example.com/cache/app:buildcache,mode=max \
  -t registry.example.com/app:$CI_COMMIT_SHA .

分布式缓存与命中率治理

  • 存储：对象存储（S3/OSS/MinIO）做后端，按 key 寻址，天然分布式共享，不占节点磁盘
  • 本地热副本：节点上保留 LRU 本地副本（如最近 20GB），二次命中免网络
  • 命中率监控：按业务/仓库维度统计，目标 70%+；低于 50% 的仓库重点治理 key 设计
  • 缓存消毒：key 里加运行时版本，防止"缓存里混着旧版本依赖"（缓存中毒）
  • 增量构建：monorepo 按变更目录裁剪构建范围（Bazel/Turbo/Nx 的看家本领）
加速效果的量级感：Java Maven 项目冷构建 8~12 分钟，依赖缓存命中后 2~4 分钟；Go 项目冷构建 3 分钟，命中后 40 秒；Node 项目差异最大，node_modules 缓存能把 5 分钟压到 1 分钟。先上依赖缓存，再上层缓存，收益按这个顺序排。
模块 5

制品管理：晋级与版本策略

制品是 CI 与 CD 之间唯一的契约。核心原则：一次构建、多处晋级、不可变、可回溯。

版本策略

策略格式适用
语义化版本MAJOR.MINOR.PATCH对外发布的库和服务，如 1.4.2
构建号版本1.4.2+ci.1024内部服务，CI 自动追加构建号保证唯一
Commit 短 hash1.4.2-a3f9c2d快速定位代码，常与前两者组合
digest 引用sha256:9f2c...部署时的最终引用，保证内容不可变

不可变性：tag 不可覆盖

# 铁律：任何 tag 一旦推送，禁止覆盖。release-1.4.2 永远指向同一个二进制。

# 错误做法：每次构建都打同样的 tag
docker tag app:ci registry/app:latest   # ✗ latest 被覆盖，无法知道线上跑的是哪次构建

# 正确做法：唯一 tag + digest 双保险
docker tag app:ci registry/app:1.4.2-ci.1024
docker push registry/app:1.4.2-ci.1024
# 部署清单记录 digest：
image: registry/app:1.4.2-ci.1024@sha256:9f2c8a...

# 镜像晋级 = 给同一个 digest 打新 tag，不重新构建：
docker tag registry/app:1.4.2-ci.1024 registry/app:staging-latest
# 晋级到生产：同一个 digest 打 prod tag
docker tag registry/app:1.4.2-ci.1024 registry/app:prod-v1.4.2

晋级（Promotion）的正确姿势

一次构建：CI 产出二进制，上传制品库，记录完整元数据（commit SHA、构建号、时间、依赖清单 SBOM、触发人）
逐级晋级：dev → test → staging → prod，每一级都是同一个二进制换环境配置，不是重新构建
门禁控制：每级晋级跑自动化验证（测试、安全扫描），生产级加人工审批
回滚：出问题时把 tag/digest 指回上一个版本，秒级完成，不需要重新构建
最危险的偷懒：每个环境各构建一次。"dev 构建过了，test 再构建一遍，prod 发布时再构建一遍"——三次编译可能引入不同的依赖解析结果（即使有 lock 文件也有工具链差异），结果是测过的二进制 ≠ 上线的二进制，事故复盘时对不上。必须坚持"构建一次，晋级多次"。

保留策略

  • 失败构建的产物：1 天后删除（排查窗口足够）
  • 日常成功构建：保留最近 50~100 个
  • 发版制品（打 release tag 的）：永久保留，配合合规要求
  • 制品库元数据单独存数据库，支持按 commit/版本/时间反查
模块 6

权限与审计

CI/CD 平台手里握着"改代码 + 上生产"两把刀。权限设计的核心原则：代码权限与部署权限分离，生产环境单独授权。

权限点谁能有说明
触发/查看构建全体研发只读权限，人人可自助排查
改流水线配置Tech Lead / 模块负责人.gitlab-ci.yml 走代码评审，等同代码权限
部署 dev/test研发 + QA测试环境放开，鼓励自测
部署 staging研发 + 运维准生产环境，变更需记录
部署 production单独授权 + 审批与代码合并权限解耦：能合代码 ≠ 能上生产

为什么要分离两把刀

  • 权限最小化：实习生能合并 feature 分支，但不该能直接把全站发到生产
  • 误操作防护：代码合并是日常操作，生产部署是高风险操作，混在一起等于把高风险操作的权限发给所有人
  • 审计可追责：出了问题能回答"谁部署的、部署的哪个版本、谁审批的"
  • 合规要求：金融/等保场景强制要求职责分离（SoD，职责分离控制）

Secret 管理

# 分级存放：
# ① 低敏（非生产数据库密码）：CI 变量，masked + protected 分支限定
# ② 高敏（生产密钥、云 AK/SK）：Vault / K8s Secret，运行时注入，不落盘

# GitLab CI 变量示例：
variables:
  DEPLOY_TOKEN:
    value: "glpat-xxxxxxxx"
    masked: true        # 日志中自动打码
    protected: true     # 只有保护分支能拿到

# 日志脱敏：CI 系统对输出做正则扫描（AK 模式、token 模式），命中即替换
# 红线：禁止 echo $SECRET 到日志；禁止把密钥写进制品层（docker history 可见）

# K8s Secret 注入 Pod：
env:
  - name: DB_PASSWORD
    valueFrom:
      secretKeyRef:
        name: app-secret
        key: db-password

审计日志必备字段

字段示例
operatorzhangsan（触发/部署人）
actiondeploy.production / pipeline.update
targetapp:1.4.2-ci.1024 @ sha256:9f2c...
environmentproduction
approverlisi（生产审批人）
timestamp2026-10-18T14:32:00+08:00
sourcecommit a3f9c2d / MR !1024
resultsuccess / failed / rolled-back

留存要求：生产相关审计日志不少于 180 天，不可篡改（追加写或外发日志服务）。

模块 7

多环境晋级：dev → test → staging → prod

多环境的目的是让问题在廉价的环境暴露，不在生产爆炸。技术核心：同一制品 + 不同配置，环境逐级逼近生产。

环境用途数据发布方式
dev研发联调、冒烟假数据 / 脱敏小样本push 自动部署
testQA 全量回归、自动化测试造数工具生成MR 合并自动部署
staging上线前最终验证、压测、演练生产脱敏全量（或等比例抽样）手动触发，自动门禁
prod生产真实数据人工审批 + 灰度

晋级链路的工程要点

# 1. 配置外置：同一镜像，配置走环境变量/配置中心
#    禁止把配置打进镜像（那样每个环境都要重新构建）
env:
  - name: APP_ENV
    value: "staging"
  - name: CONFIG_CENTER
    value: "http://apollo-config:8080"

# 2. staging 与 prod 同构：
#    相同中间件版本（MySQL/Redis/MQ 大版本一致）
#    相同部署拓扑（staging 按 1:4 缩小，但服务类型齐全）
#    相同网络策略（staging 独立 namespace，不共享 prod 中间件）

# 3. 生产灰度：
#    金丝雀：5% 流量 → 观察 10 分钟 → 50% → 观察 → 100%
#    蓝绿：新旧两套并存，一键切回
#    回滚：digest 指回旧版本，秒级生效

# 4. 变更窗口：生产发布集中在低峰期（如 10:00-11:30 / 14:00-17:00）
#    封网期（大促、财报日）禁止发布，由平台策略强制

# 5. 配置漂移检测：
#    staging 与 prod 的部署清单（镜像/副本数/资源）定期 diff，告警差异
"在我机器上好的"的工程解药是 staging 同构。很多团队 staging 用着旧的中间件版本、缩水的拓扑、共享的测试数据库，导致 staging 验证通过、生产出问题。判断标准很简单：staging 能不能复现 90% 的生产问题？不能就是同构没做到位。
模块 8

自研 vs 开源

选型的正确答案取决于团队规模和痛点，不存在"自研一定好"或"开源一定香"。先看对比，再看决策路径。

方案优势劣势
Jenkins插件生态最大（2000+），灵活度最高，社区资料多配置 drift 严重（UI 点出来的配置难追溯）、JCasC 治理成本高、UI 老旧、大规模 master 瓶颈
GitLab CI与代码仓一体化、YAML 声明式（随代码走）、MR 集成顺滑、Runner 可水平扩展YAML 复杂后难维护、Runner 大规模管理要自己做、重功能绑定 GitLab 生态
Tekton / ArgoK8s 原生（Pipeline 就是 CRD）、云原生生态、无服务器组件学习曲线陡、调试体验差、小团队用不起来

模块 9

十个线上坑

1
基础镜像用 latest，构建环境漂移
同一条流水线上周能过这周挂，因为镜像里的工具链静默升级。必须 pin 到 digest：FROM golang:1.22.5@sha256:abc...，升级走显式变更。
2
缓存 key 对源码 hash，命中率趋近于零
改一行代码整个缓存失效，等于没缓存。key 只能对依赖 lock 文件 hash（go.sum / package-lock.json / pom.xml），加运行时版本和平台标识。
3
缓存中毒
key 相同但内容被污染（如中间步骤失败留下了半个缓存），后续全部构建拿到脏缓存，错得莫名其妙。对策：缓存只在任务成功时上传，key 加内容校验，发现中毒按 key 前缀整体清除。
4
并发构建无配额，节点被抢光
一个大 monorepo 触发 50 个任务，把集群 CPU/内存占满，其他团队排队。用 namespace 级 ResourceQuota + 队列优先级 + 单流水线并发上限（max_parallel）。
5
制品 tag 可覆盖，版本不可回溯
latest 反复被覆盖，出事故时说不清线上跑的是哪次构建。tag 唯一化（版本+构建号），部署记录 digest，release 制品永久保留。
6
部署权限 = 代码权限
任何能合并代码的人都能发生产，误操作和越权无法追责。生产部署单独授权 + 审批流，代码权限与部署权限解耦，审计日志记全操作链。
7
流水线无并发组，同分支重复触发
连续 push 三次触发三次构建并行跑，互相踩 workspace、重复部署。必须配并发组：同 group 互斥，新触发取消旧任务（cancel-in-progress）。
8
凭据明文进日志
echo 密码、错误堆栈带 token、密钥打进镜像层，日志系统和镜像仓库全泄露。变量必须 masked+protected，日志侧加正则脱敏，密钥运行时注入。
9
矩阵组合爆炸
matrix 是笛卡尔积，GO×OS×ARCH×DB = 24 个任务，一次 push 打满集群。上线前算组合数，超 10 组合就拆分或 exclude 剪枝。
10
每个环境重新构建 + 重试不幂等
"dev 构建一次、test 再构建、prod 发布再构建"导致测的 ≠ 上的；重试不幂等导致重复部署、重复发消息。坚持构建一次多次晋级；重试逻辑加幂等键（构建号/部署单号）。
自测

六道题

1. 依赖缓存的 key 应该基于什么计算？
正确答案：lock 文件 hash + 运行时版本。对源码 hash 会导致改一行代码缓存全失效；只对 lock 文件 hash 才能做到"依赖不变则命中、依赖变才失效"。
2. "这条流水线上周还成功，这周莫名失败"，最可能的原因是？
正确答案：基础镜像漂移。latest 是浮动版本，镜像内容会变，构建不可复现。必须 pin 到 digest（FROM golang:1.22.5@sha256:...），升级作为显式变更走评审。
3. GitLab CI 中让 test 不必等同 stage 的其他任务、只等 build，用什么语法？
正确答案：needs。它声明任务级依赖，让流水线变成 DAG，可跳过 stage 边界的串行等待。dependencies 只控制产物下载，不控制执行顺序。
4. "制品晋级"的正确含义是？
正确答案：同一制品逐级流转。一次构建、多处晋级才能保证"测过的二进制就是上线的二进制"；每个环境重新构建会引入工具链和依赖解析差异，是重大事故源。
5. 并发构建互相争抢资源，把集群打满，怎么治理？
正确答案：配额 + 优先级 + 并发上限。ResourceQuota 限制单团队上限，优先级队列保证核心仓库先跑，max_parallel 限制单条流水线展开的任务数。超售会让 OOM 更严重。
6. 为什么生产部署权限必须与代码合并权限分离？
正确答案：权限最小化与追责。合并代码高频低风险，发布生产低频高风险，权限混发等于把高风险操作开放给所有人。生产部署应单独授权 + 审批，且审计日志记全"谁部署、哪个版本、谁审批"。
