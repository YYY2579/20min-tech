阶段 0 · 架构

先想清楚，再动手

架构方向最值钱的能力，是在写第一行代码之前把系统想明白。这一阶段不碰键盘，但决定了后面所有工作。

0.1 定需求：我们搭什么

选一个短链服务（类似 t.cn）。理由是它足够小、但五脏俱全：有写有读、有缓存有数据库、有跳转有统计，是练架构最合适的载体。

类别具体目标
功能需求① 长链接换短链 ② 访问短链 302 跳转 ③ 记录访问次数
性能目标跳转接口 P99 延迟 < 50ms；峰值支撑 1000 QPS
可用性目标99.9%（约每月允许 43 分钟不可用）
数据目标短链 7 天内有效，过期后仍可查询历史统计
为什么非功能需求比功能需求更重要？因为功能需求决定"做什么"，非功能需求决定"架构长什么样"。
同样是短链服务，100 QPS 用单体 + 单库就够，10 万 QPS 就得上分片 + 多级缓存。先定清楚量级，架构才有依据。

0.3 架构决策记录（ADR）

这是架构方向的核心交付物。每个决策都要写清"选项、决定、理由、代价"，而不是只说结论。

决策选项决定与理由
短码怎么生成自增 ID 转 62 进制 / 哈希取前 7 位 / UUID选自增 ID 转 62 进制。哈希会碰撞要额外查重，UUID 太长。代价是短码可被枚举，敏感业务要加随机盐
数据存哪只存 MySQL / 只存 Redis / 两者都存选Redis 存映射 + MySQL 存全量。Redis 挂了还能回源，MySQL 挂了不影响跳转
怎么部署裸机 / Docker / K8s选 K8s。滚动更新、自愈、扩缩容都是现成的，代价是运维复杂度上升
API 是否无状态有状态（本地缓存 session）/ 无状态选无状态。这是能水平扩容的前提，所有共享状态外置到 Redis
统计怎么记同步写库 / 异步批量落库选异步。跳转路径上不能有写库操作，否则 P99 撑不住 50ms
一致性要求强一致 / 最终一致选最终一致。统计数字晚几秒无所谓，但跳转必须准 —— 关键路径只读，不走事务
ADR 的价值在于"以后有人问为什么这么设计"时，你能翻出记录。半年后你自己都会忘。这也是为什么大厂的技术方案评审一定要写这个。

0.4 容量估算（架构师基本功）

不用很精确，但必须能算出一个数量级。估算错了，架构就选错了。

# 假设日活 100 万用户，人均每天 2 次创建、20 次访问
写 QPS = 1,000,000 × 2  / 86400 ≈ 23
读 QPS = 1,000,000 × 20 / 86400 ≈ 231

# 互联网流量有峰谷，按 3~5 倍峰值系数算
读峰值 QPS ≈ 231 × 4 ≈ 1000     ← 这就是我们定的目标

# 单副本能扛多少？按经验值估
单副本 ≈ 500 QPS（简单查询 + 缓存命中）
需要副本 = 1000 / 500 = 2，再加 1 个冗余应对故障 → 3 副本

# 存储估算
每天新增 = 100万 × 2 = 200 万条
每条 ≈ 500 字节（短码 + 长链接 + 时间）
每天新增 ≈ 1 GB，一年 ≈ 365 GB
→ 单表能撑到千万级，一年内不用分库分表，但要做分区表

# Redis 内存估算
热数据比例 ≈ 20%，保留 7 天 = 200万 × 7 × 0.2 = 280 万条
每条 ≈ 200 字节 → 约 560 MB
→ 选 2GB 规格，留一倍余量给 fork 和峰值
容量估算最常见的两个错误：
① 忘了峰值系数。按平均值买机器，一到大促就崩。互联网流量峰值通常是均值的 3~5 倍，秒杀类能到几十倍。
② 忘了冗余。算出需要 2 个副本就买 2 个，那挂一个就只剩 50% 容量了。要按"坏掉一个还能扛住峰值"来设计。
✓
验收标准：你能在 5 分钟内给一个不懂技术的人讲清这个系统怎么工作，并且能回答"如果 Redis 挂了会怎样""为什么需要 3 个副本"这类问题。

1.3 最小可用的 API

# app/main.py
import os, time, string
from fastapi import FastAPI, HTTPException, Response
from fastapi.responses import RedirectResponse
from pydantic import BaseModel
from prometheus_client import Counter, Histogram, generate_latest
import redis as redis_lib

app = FastAPI()
r = redis_lib.Redis(
    host=os.getenv("REDIS_HOST", "localhost"),
    port=int(os.getenv("REDIS_PORT", 6379)),
    decode_responses=True,
    socket_timeout=1,
)
BASE_URL = os.getenv("BASE_URL", "http://localhost:8000")
TTL = int(os.getenv("LINK_TTL", 7 * 86400))
ALPHABET = string.digits + string.ascii_letters

# ---- 指标（阶段 4 会用）----
REQUESTS = Counter("http_requests_total", "Total requests",
                   ["method", "path", "status"])
LATENCY = Histogram("http_request_duration_seconds", "Latency", ["path"])

def to_base62(n: int) -> str:
    s = ""
    while n:
        n, rem = divmod(n, 62)
        s = ALPHABET[rem] + s
    return s or "0"

class ShortenReq(BaseModel):
    url: str

# ---- 存活探针：进程还活着就行 ----
@app.get("/healthz")
def healthz():
    return {"status": "ok"}

# ---- 就绪探针：依赖也得能用 ----
@app.get("/readyz")
def readyz():
    try:
        r.ping()
    except Exception as e:
        raise HTTPException(503, f"redis not ready: {e}")
    return {"status": "ready"}

@app.post("/api/shorten")
def shorten(req: ShortenReq):
    # 已存在就直接返回，避免重复生成
    exist = r.get(f"url:{req.url}")
    if exist:
        return {"code": exist, "short": f"{BASE_URL}/{exist}"}
    code = to_base62(r.incr("global:id"))
    with r.pipeline() as p:      # 批量提交，减少往返
        p.set(f"code:{code}", req.url, ex=TTL)
        p.set(f"url:{req.url}", code, ex=TTL)
        p.execute()
    return {"code": code, "short": f"{BASE_URL}/{code}"}

@app.get("/{code}")
def redirect(code: str):
    url = r.get(f"code:{code}")
    if not url:
        raise HTTPException(404, "link not found or expired")
    r.incr(f"stat:{code}")            # 异步统计，不阻塞跳转
    return RedirectResponse(url, status_code=302)

@app.get("/metrics")
def metrics():
    return Response(generate_latest(), media_type="text/plain")

1.4 存活探针 vs 就绪探针（必须分清）

探针回答什么问题失败后果
liveness
/healthz		进程还活着吗？需不需要重启？重启容器。所以这里绝不能检查外部依赖 —— 否则 Redis 一抖，所有 Pod 全被重启，雪上加霜
readiness
/readyz		现在能接流量吗？从 Service 摘掉，不接流量，但不重启。依赖不可用时应该返回失败
这是新手最容易配错的地方：把依赖检查写进 liveness。
后果：数据库稍微慢一下 → liveness 超时 → 所有 Pod 被重启 → 重启期间请求全失败 → 更慢 → 更多重启。一次小抖动被放大成全面故障。
记住：liveness 只检查自己，readiness 才检查依赖。
✓
验收标准：本机能完成"创建短链 → 访问短链 → 跳转成功"的完整闭环；停掉 Redis 后 /readyz 正确报错，而 /healthz 不受影响。
阶段 2 · 构建

容器化与镜像优化

镜像不只是"能跑就行"。镜像越小，拉取越快，扩缩容和故障恢复就越快 —— 这是直接影响可用性的运维指标。

2.1 多阶段构建的 Dockerfile

# ---------- 构建阶段 ----------
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --no-cache-dir --user -r requirements.txt

# ---------- 运行阶段 ----------
FROM python:3.12-slim

# 建一个非 root 用户（安全基线）
RUN useradd --create-home --uid 10001 appuser

WORKDIR /app
# 只拷依赖，不拷构建缓存
COPY --from=builder /root/.local /home/appuser/.local
COPY --chown=appuser:appuser app/ ./app/

ENV PATH=/home/appuser/.local/bin:$PATH \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1

USER appuser
EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s \
  CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:8000/healthz')"

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

2.2 .dockerignore（最容易忘，但影响最大）

.git
.venv
__pycache__
*.pyc
*.log
.env
tests/
deploy/
README.md
不写 .dockerignore 的三个后果：① .git 和 .venv 被打进镜像，体积暴涨几百 MB；② 每次改代码都导致 COPY 层缓存失效，构建变慢；③ .env 里的密钥被打进镜像 —— 这是安全事故。

2.3 优化前后对比

做法镜像大小说明
python:3.12（完整版）+ 单阶段约 1.1 GB包含了编译工具链、文档、测试套件
python:3.12-slim + 单阶段约 220 MB去掉了大部分非必需包
slim + 多阶段 + 只拷依赖约 150 MB推荐做法。编译依赖留在构建阶段，不进最终镜像
alpine + 多阶段约 80 MB更小，但 musl libc 可能导致某些库编译问题，需实测
为什么镜像小对运维重要？K8s 扩容时新 Pod 要先把镜像拉到节点上。1GB 镜像在弱网下可能要几分钟，这期间新 Pod 一直处于 ContainerCreating，扩不出容量。故障恢复速度直接受镜像大小影响。
✓
验收标准：镜像小于 200MB，容器内 whoami 输出非 root，docker ps 显示状态为 healthy。
阶段 3 · 部署

部署到 Kubernetes

这一阶段把服务真正跑进集群。重点不是"能跑起来"，而是滚动更新不中断、出问题能回滚、能自动扩缩容。

3.1 配置与密钥分离

# deploy/k8s/00-namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: shortlink

# deploy/k8s/01-config.yaml —— 普通配置
apiVersion: v1
kind: ConfigMap
metadata:
  name: shortlink-config
  namespace: shortlink
data:
  REDIS_HOST: "redis.shortlink.svc.cluster.local"
  REDIS_PORT: "6379"
  BASE_URL: "https://s.example.com"
  LINK_TTL: "604800"

# deploy/k8s/02-secret.yaml —— 敏感信息
apiVersion: v1
kind: Secret
metadata:
  name: shortlink-secret
  namespace: shortlink
type: Opaque
stringData:                      # 用 stringData 可以直接写明文，K8s 帮你编码
  DB_PASSWORD: "换成你的密码"
Secret 默认只是 base64 编码，不是加密！拿到集群权限的人都能解开。生产环境要做三件事：① 开启 etcd 的静态加密；② 用 RBAC 限制谁能读 Secret；③ 更彻底的做法是接外部密钥管理（Vault、云厂商 KMS），Secret 里只放引用。

3.2 Deployment（重点是探针和优雅停机）

# deploy/k8s/03-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shortlink-api
  namespace: shortlink
spec:
  replicas: 3
  revisionHistoryLimit: 5        # 保留 5 个历史版本用于回滚
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1                  # 先多起 1 个新 Pod
      maxUnavailable: 0            # 保证可用数不减 ← 不中断的关键
  selector:
    matchLabels:
      app: shortlink-api
  template:
    metadata:
      labels:
        app: shortlink-api
    spec:
      terminationGracePeriodSeconds: 40   # 给优雅停机留时间
      containers:
      - name: api
        image: registry.example.com/shortlink-api:v1.0.0
        ports:
        - containerPort: 8000
        envFrom:
        - configMapRef: { name: shortlink-config }
        - secretRef:    { name: shortlink-secret }
        resources:
          requests: { cpu: "100m", memory: "128Mi" }   # 调度依据
          limits:   { cpu: "500m", memory: "512Mi" }   # 上限，防打爆节点
        livenessProbe:                # 只查自己
          httpGet: { path: /healthz, port: 8000 }
          initialDelaySeconds: 10
          periodSeconds: 10
          failureThreshold: 3
        readinessProbe:               # 查依赖
          httpGet: { path: /readyz, port: 8000 }
          initialDelaySeconds: 5
          periodSeconds: 5
          failureThreshold: 2
        lifecycle:
          preStop:
            exec:
              command: ["sh", "-c", "sleep 5"]   # 等 Service 摘掉自己再退
为什么 preStop 要 sleep 5 秒？这是优雅停机的关键细节。
Pod 被删除时，K8s 同时做两件事：① 从 Service 摘掉它；② 给它发 SIGTERM。但"摘掉"这个动作在 kube-proxy 上是异步生效的 —— 在它生效之前，仍然有新请求被转发过来。
如果进程收到 SIGTERM 立刻退出，这些请求就会失败。所以要先 sleep 几秒，等摘除生效，再退出。
完整链条：preStop sleep 5s → SIGTERM → 应用停止接收新请求、处理完存量请求 → 退出。而 terminationGracePeriodSeconds 必须大于这个总耗时，否则会被 SIGKILL 强杀。

3.3 Service 与 Ingress

# deploy/k8s/04-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: shortlink-api
  namespace: shortlink
spec:
  type: ClusterIP          # 只在集群内部可达的虚拟 IP，集群外访问不到
  selector:
    app: shortlink-api        # 必须和 Pod 的 labels 完全一致
  ports:
  - port: 80
    targetPort: 8000

# deploy/k8s/05-ingress.yaml —— 外部入口
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shortlink
  namespace: shortlink
  annotations:
    nginx.ingress.kubernetes.io/limit-rps: "200"      # 入口层限流
spec:
  ingressClassName: nginx
  tls:
  - hosts: ["s.example.com"]
    secretName: shortlink-tls
  rules:
  - host: s.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: shortlink-api
            port: { number: 80 }

3.4 自动扩缩容与中断预算

# deploy/k8s/06-hpa.yaml
# HPA = HorizontalPodAutoscaler，水平自动扩缩容：按指标自动调整 Pod 副本数
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: shortlink-api
  namespace: shortlink
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: shortlink-api
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target: { type: Utilization, averageUtilization: 70 }

# deploy/k8s/07-pdb.yaml —— 自愿中断时至少保留几个
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: shortlink-api
  namespace: shortlink
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: shortlink-api
PDB 是很多人忽略但很重要的一环。集群升级、节点维护时，K8s 会驱逐 Pod。没有 PDB 的话，它可能一次性把 3 个副本全赶走，服务直接不可用。配上 minAvailable: 2，驱逐就会排队进行，保证始终有 2 个在跑。
注意 PDB 只管"自愿中断"（维护、驱逐），不管节点宕机这种"非自愿中断" —— 后者要靠多副本 + 反亲和性来兜。
✓
验收标准：滚动更新期间持续压测，错误率为 0；一键回滚能在 30 秒内生效；压测时副本数从 3 自动涨到 5 以上，压力下去后自动缩回。
阶段 4 · 可观测性

让系统"看得见"

运维方向的核心能力。没有可观测性的系统等于黑盒 —— 出故障时你只能猜。可观测性由三根支柱组成：日志、指标、链路追踪。

4.1 结构化日志

# 不要这样打日志
print(f"user {uid} created link {code} at {time}")

# 要这样打：JSON 格式，机器可解析、可检索、可聚合
import json, logging, time

def log(**fields):
    print(json.dumps({
        "ts": time.strftime("%Y-%m-%dT%H:%M:%S%z"),
        "level": fields.pop("level", "info"),
        "service": "shortlink-api",
        **fields,
    }, ensure_ascii=False))

log(event="link_created", code=code, trace_id=tid)
# 输出：{"ts":"2026-10-16T02:30:00+0800","level":"info",
#       "service":"shortlink-api","event":"link_created","code":"aB3","trace_id":"..."}

关键是要带 trace_id（一次请求的唯一标识）。这样一次请求跨多个服务产生的所有日志，能用它串起来。

4.2 指标暴露

阶段 1 的代码里已经埋好了 Prometheus 指标。补充一个中间件，自动记录所有请求：

@app.middleware("http")
async def metrics_middleware(request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    LATENCY.labels(request.url.path).observe(time.perf_counter() - start)
    REQUESTS.labels(request.method, request.url.path,
                    response.status_code).inc()
    return response

4.3 黄金四信号

指标千千万，但真正决定"服务好不好"的只有四个。这是 Google SRE 书里的核心概念，监控面板第一屏就该是它们。

信号回答什么问题对应指标
延迟 Latency请求要多久？P50 / P95 / P99 分位延迟。看平均值会骗人
流量 Traffic现在有多大压力？QPS、并发连接数
错误 Errors有多少请求失败了？错误率、5xx 占比、超时数
饱和度 Saturation还有多少余量？CPU / 内存 / 连接池使用率、队列长度
为什么必须看分位数而不是平均值？
100 个请求：99 个用了 10ms，1 个用了 5 秒。平均值是 60ms，看起来很正常 —— 但那个用户等了 5 秒。
平均值会把长尾藏起来。P99 才反映真实体验。监控告警应该盯 P99，而不是均值。

4.4 每一层该监控什么

层次关键指标
业务层短链创建数、跳转数、跳转成功率、短码碰撞率
应用层QPS、P99 延迟、错误率、线程/连接池使用率、GC 时间
缓存层命中率、内存使用率、淘汰数量、慢查询、连接数
数据库层QPS、慢查询数、连接数、主从延迟、锁等待
容器层CPU/内存使用率、重启次数、OOM 次数、就绪探针失败率
节点层load、CPU/内存/磁盘使用率、网络丢包、磁盘 IO 等待

4.5 告警设计（比监控更重要）

告警设计的核心原则：告警要指向"用户正在受影响"，而不是"某个指标异常"。
坏告警："CPU 超过 80%" —— CPU 高不一定是问题，可能只是正常忙。半夜三点把你叫醒，结果什么都没发生。这叫告警疲劳，久了就没人看了。
好告警："跳转接口 P99 延迟超过 200ms 持续 5 分钟" —— 这是用户真的在等。
好告警："5xx 错误率超过 1% 持续 3 分钟" —— 用户真的在失败。
级别触发条件动作
P0 紧急核心接口不可用、错误率 > 5%电话 + 群通知，立刻响应
P1 重要P99 延迟翻倍、缓存命中率骤降群通知，当天处理
P2 提醒磁盘使用率 > 80%、证书 30 天内过期工单，排期处理
P3 观察副本数达到 HPA 上限、慢查询增多记录，周会复盘

4.6 链路追踪

一次请求可能经过 Ingress → API → Redis → MySQL。当它变慢时，你需要知道慢在哪一段。链路追踪就是给每次请求一个全局 ID，把各段的耗时串成一条时间线。

落地路径：先做日志里带 trace_id（成本最低、收益最大），再考虑接入 OpenTelemetry + Jaeger。别一上来就上全套，先把 ID 串起来就能解决 80% 的问题。

✓
验收标准：打开 Grafana 能一眼看出系统当前健康状况；人为打挂接口后，告警在 3 分钟内送达；能用 trace_id 从日志里还原一次完整请求。

消除单点与容量保障

可用性目标 99.9% 不是喊出来的，是逐个消除单点换来的。

5.1 单点清单：逐层排查

层次潜在单点应对
入口Ingress 只有 1 个副本Ingress 至少 2 副本 + 前置负载均衡
应用Pod 全在同一节点上配 反亲和性，强制打散到不同节点
应用滚动更新时中断maxUnavailable: 0 + preStop 优雅停机
缓存Redis 单点主从 + 哨兵，或 Cluster 分片
数据库MySQL 单点主从复制 + 自动故障转移（MHA / Orchestrator / 云托管）
数据库连接数耗尽连接池 + 上限控制，别让应用裸连
依赖外部 API 挂了拖垮自己超时 + 熔断 + 降级
DNS解析失败本地缓存 + 多 DNS 服务器

5.2 反亲和性：别让所有鸡蛋在一个篮子里

affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchLabels: { app: shortlink-api }
        topologyKey: kubernetes.io/hostname    # 按节点打散
用 preferred 还是 required？
preferred（软约束）：尽量打散，实在没条件也允许挤在一起。推荐 —— 副本数多于节点数时不会卡在 Pending。
required（硬约束）：必须打散，否则 Pod 起不来。副本数 > 节点数时会永远 Pending，是个经典事故。

5.3 优雅停机：应用侧也要配合

先补一个名词：SIGTERM 是 15 号信号，含义是"请你优雅地退出" —— 收到它的进程应该保存数据、处理完手头的请求再关闭。与之相对的是 SIGKILL（9 号信号），内核直接终止，进程没有任何反应机会。K8s 删 Pod 时发的是 SIGTERM。

import signal, sys, threading

shutting_down = threading.Event()

def handle_sigterm(signum, frame):
    log(level="warn", event="shutdown_started")
    shutting_down.set()          # 1. 标记：新请求直接拒绝或返回 503
    # 2. 等待存量请求处理完（这里等 20 秒）
    time.sleep(20)
    # 3. 关闭连接池，让 TCP 优雅关闭而不是 RST
    r.close()
    sys.exit(0)

signal.signal(signal.SIGTERM, handle_sigterm)
不处理 SIGTERM 的后果：每次发布都会有用户遇到 502。
K8s 删 Pod 的完整时序是：从 Service 摘除 → 发 SIGTERM → 等 terminationGracePeriodSeconds → 超时则 SIGKILL。
如果应用收到 SIGTERM 直接死掉，正在处理的请求会被直接掐断，客户端看到连接被重置。用户看到的就是"服务偶尔报错"，而且这种错很难复现、很难排查。

5.4 限流、熔断、降级（三件套）

手段解决什么实现位置
限流流量超过容量时主动拒绝，保住大多数用户Ingress（入口层）、应用层（Redis 令牌桶，第 9 期讲过）
熔断下游持续失败时，快速失败不再傻等，避免线程被耗尽应用层（Hystrix / Resilience4j 风格）
降级依赖不可用时返回兜底数据，保证主流程可用应用层
用我们的系统举例：
限流：Ingress 配 limit-rps: 200，超过直接返回 429，保护后端。
降级：Redis 挂了 → 跳转接口回源查 MySQL（慢一点但能用），而不是直接 500。
熔断：如果统计服务挂了，不要让它拖累跳转主流程 —— 统计是旁路，失败就丢弃。
核心思想：分清哪些是"关键路径"，哪些是"旁路"。旁路的东西坏了，绝不能影响关键路径。

5.5 压测与容量验证

# 用 wrk 压测跳转接口（读路径）
wrk -t4 -c100 -d60s --latency https://s.example.com/aB3

# 关注结果里的这几行
# Latency  P50 / P99  ← 分位延迟
# Req/Sec              ← 实际吞吐
# Socket errors        ← 有没有连接被拒

# 用 k6 做带场景的压测（更贴近真实流量）
k6 run --vus 100 --duration 5m loadtest.js

压测要看三件事：① 在目标 QPS 下 P99 是否达标；② 系统还有多少余量（继续加压到出错，看拐点在哪）；③ 压测过程中 HPA 是否正确扩容。

✓
验收标准：能回答"如果任意一个组件挂掉，系统会怎样"；压测达到 1000 QPS 且 P99 < 50ms；发布期间零错误。
阶段 6 · 演练

故意搞坏它：五个故障演练

这一步是把前 10 期全部用上的地方。真正的运维能力，是在故障现场练出来的，不是在文档里读出来的。每个故障都请先自己排查，再看答案。

演练 1：Pod 一直重启

# 制造故障：把镜像 tag 改成一个不存在的版本
kubectl set image deployment/shortlink-api api=shortlink-api:v9.9.9 -n shortlink

排查思路（用第 4 期 K8s 三板斧）：① kubectl get pods 看状态是 ImagePullBackOff 还是 CrashLoopBackOff；② kubectl describe pod 看 Events；③ 判断方向 —— ImagePull 是配置问题（名字/权限/网络），CrashLoop 是应用问题（去 logs）。

答案：ImagePullBackOff，镜像 tag 不存在。修复：kubectl rollout undo deployment/shortlink-api -n shortlink

演练 2：接口返回 502

# 制造故障：把 Service 的 targetPort 改成错误端口
kubectl patch svc shortlink-api -n shortlink -p '{"spec":{"ports":[{"port":80,"targetPort":9999}]}}'

排查思路（用第 8 期 HTTP）：502 意味着网关拿到的是无效响应 → 后端不可达。先确认 Pod 本身健康（kubectl get pods 是 Running），那就说明问题在 Service 和 Pod 之间的映射上 → kubectl describe svc 看 Endpoints 是不是空的。

答案：targetPort 指错了，流量转到了一个没人监听的端口。这是典型的"Pod 好好的但访问不通"。

演练 3：响应突然变慢

# 制造故障：给容器加 CPU 限制到极低，制造资源竞争
kubectl set resources deployment/shortlink-api -n shortlink \
  --limits=cpu=50m,memory=128Mi

排查思路（用第 10 期 Linux USE 方法）：① kubectl top pods 看资源使用；② 进容器 kubectl exec -it 名字 -- sh，跑 top 看 CPU 是否打满、%wa 高不高；③ 判断是 CPU 瓶颈（%us 高）还是 IO 瓶颈（%wa 高）。

答案：CPU limit 太低导致被 cgroup 限流（throttling）。查 container_cpu_cfs_throttled_seconds_total 指标能直接看到。这也是为什么 resources.limits 不能随手填一个小值。

演练 4：缓存击穿导致数据库压力飙升

# 制造故障：删掉一个热点短码的缓存，同时持续压测这个短码
kubectl exec -it redis-0 -n shortlink -- redis-cli DEL code:aB3
wrk -t4 -c200 -d60s https://s.example.com/aB3

排查思路（用第 9 期 Redis）：① 看 Redis 命中率指标是否骤降；② 看 MySQL 的 QPS 和连接数是否暴涨；③ 判断属于三大问题里的哪一种 —— 这里是"击穿"（单个热点 key 失效）。

答案与修复：用互斥锁让只有一个请求去查库回填，或者给热点 key 设"逻辑过期"永不过期。对比一下：如果是穿透（查不存在的 code），要缓存空值；如果是雪崩（大批 key 同时过期），要给 TTL 加随机值。

演练 5：慢查询拖垮接口

# 制造故障：在数据库里塞 500 万条数据，然后跑一个没有索引的查询
SELECT * FROM links WHERE url LIKE '%example%';

排查思路（用第 3 期 MySQL / 第 5 期 PG）：① 开慢查询日志，找出耗时最长的 SQL；② EXPLAIN 看执行计划，重点看 type 是不是 ALL（全表扫描）；③ 检查为什么没走索引 —— 是不是 前导模糊匹配，或者索引列被函数包住了。

答案：LIKE '%example%' 前导有 %，索引用不上。修复方向：改成前缀匹配 LIKE 'example%'，或者引入全文检索（PG 的 tsvector / Elasticsearch）。

阶段 7 · CI/CD

让发布变成一件无聊的事

运维的终极目标：发布不再需要紧张。因为流程自动化、可回滚、可灰度。

7.1 流水线设计

提交代码
   │
   ├─▶ ① 静态检查（lint / 类型检查）
   ├─▶ ② 单元测试
   ├─▶ ③ 构建镜像（多阶段，带版本 tag）
   ├─▶ ④ 扫描镜像漏洞
   ├─▶ ⑤ 推送到镜像仓库
   ├─▶ ⑥ 部署到预发环境 + 冒烟测试
   └─▶ ⑦ 灰度发布 → 观察 → 全量 / 回滚
关键设计原则：镜像只构建一次，各环境用同一个镜像。不要"预发构建一次、生产再构建一次" —— 那两次构建的产物可能不一样，预发测过了不代表生产没问题。用同一个镜像 + 不同的配置（ConfigMap），才是正确的做法。

7.2 GitHub Actions 示例

# .github/workflows/deploy.yml
name: build-and-deploy
on:
  push:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v4

    - name: 静态检查与测试
      run: |
        pip install -r requirements.txt
        ruff check .
        pytest -q

    - name: 构建并推送镜像
      run: |
        TAG=${GITHUB_SHA::7}
        docker build -t $REGISTRY/shortlink-api:$TAG .
        docker push $REGISTRY/shortlink-api:$TAG
        echo "TAG=$TAG" >> $GITHUB_ENV

    - name: 部署到预发
      run: |
        kubectl set image deployment/shortlink-api \
          api=$REGISTRY/shortlink-api:$TAG -n shortlink-staging
        kubectl rollout status deployment/shortlink-api \
          -n shortlink-staging --timeout=120s

7.3 灰度发布策略

策略做法适用
滚动发布逐个替换 Pod，用 maxSurge / maxUnavailable 控制节奏最简单，K8s 原生支持。但没有"部分用户先试"的能力
金丝雀发布先放 1 个新版本 Pod，只把 5% 流量导过去，观察后再全量需要 Ingress 按权重分流。风险最低
蓝绿发布部署一套完整新环境，验证后一键切流量回滚最快（切回来就行），但要双倍资源
功能开关代码先上线，功能用开关控制，随时关掉和发布解耦，最灵活。但代码里会留开关逻辑

7.4 回滚决策：什么时候该回滚

原则：回滚要果断，不要"再观察一下"。
立刻回滚的信号：核心接口错误率上升、P99 延迟翻倍、出现数据错误。
可以观察的信号：非核心功能异常、日志里出现警告但没有用户影响。
回滚决策不该在现场临时讨论 —— 应该提前定义好阈值，写进发布流程："错误率超过 1% 持续 3 分钟，自动回滚"。
回滚不是失败，是成熟。压着问题不回滚，把小故障拖成大事故，才是真的失败。
✓
验收标准：改一行代码推上去，全自动完成到预发环境；并且你亲手触发过一次自动回滚，确认它真的有效。
