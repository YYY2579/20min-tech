开始前

起一个能练的环境

练 CDC 必须有一个开了 binlog 的 MySQL。DataX 从官网下载即可运行，不需要额外服务。

# 源库：MySQL 8，开启 ROW 格式 binlog + GTID（CDC 的前提）
docker run -d --name mysql-src -p 3306:3306 -e MYSQL_ROOT_PASSWORD=root123 \
  mysql:8.0 --server-id=1 --log-bin=mysql-bin --binlog-format=ROW \
  --gtid-mode=ON --enforce-gtid-consistency=ON

# CDC 账号必须有的两个权限（很多人漏掉第二个）
CREATE USER 'cdc'@'%' IDENTIFIED BY 'cdc123';
GRANT SELECT, REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'cdc'@'%';

# DataX：解压即用，Python 版入口是 bin/datax.py
# https://github.com/alibaba/DataX/releases
python bin/datax.py job/mysql2mysql.json

# 造测试数据：50 万行订单
INSERT INTO t_order(user_id, amount, status, update_time)
SELECT FLOOR(RAND()*10000), ROUND(RAND()*1000,2), 'PAID', NOW()
FROM information_schema.columns a, information_schema.columns b
LIMIT 500000;
CDC 的三条硬前提：① binlog-format=ROW（Statement 格式拿不到前后镜像，CDC 工具基本不支持）；② 账号有 REPLICATION SLAVE / REPLICATION CLIENT；③ 表必须有主键——没有主键的 binlog 事件解析后无法定位行，Flink CDC 直接报错，Canal 只能以列值硬匹配。
模块 1

ETL vs ELT 与三种同步模式

ETL 与 ELT 的区别只有一个：转换发生在哪

维度ETLELT
转换位置抽取后、加载前，在独立转换引擎里完成（Kettle、DataX + Spark）先加载进数仓/数据湖，在仓内用 SQL 转换（Hive、Spark、Doris、dbt）
中间存储需要独立的转换区，链路长、组件多直接落 ODS 贴源层，链路短
扩展性转换引擎是瓶颈，数据量涨就得扩引擎数仓本身弹性扩缩容，转换只是 SQL
调试成本可视化编排，但排查要翻配置和日志转换逻辑就是 SQL，可单步执行、可 diff
适用异构系统、 legacy 数仓、需要复杂清洗逻辑云数仓（Snowflake/BigQuery/StarRocks/Doris）+ dbt，当前主流
一句话选择：新平台直接走 ELT——同步层只负责"原样搬进 ODS"（这也让同步层变得简单可靠），所有清洗、关联、聚合做成 SQL 模型分层（ODS→DWD→DWS→ADS）。只有"数据还没进仓就要过滤掉大部分"或"源和目标异构且无法用 SQL 表达"时才用 ETL。

三种同步模式的取舍

模式机制源库压力延迟一致性风险
全量SELECT * 整表拉取，覆盖或截断目标表高（大表全扫）分钟~小时级低（自包含，跑完即完整快照）
增量按水线字段（update_time > ?）拉变更中（依赖索引）分钟级高：漏更新、漏删除、时钟回拨
CDC伪装成从库订阅 binlog，捕获 INSERT/UPDATE/DELETE低（只读日志，不查表）秒级中：需处理顺序、重复、schema 变更
# 增量同步的水线 SQL（正确形态）
SELECT id, user_id, amount, status, update_time
FROM t_order
WHERE update_time >= '${last_watermark}'
  AND update_time <  '${batch_end}'      # 右开区间，防止下一批漏/重
ORDER BY update_time
LIMIT 100000;

# 跑完后：last_watermark = batch_end，落库到一张 watermark 表
# 增量同步的两个硬条件：
# 1. update_time 上必须有索引，否则每次全表扫描
# 2. 历史行不允许被 update_time 之前的 UPDATE 改状态
#    （"改旧单状态"的业务会永远漏掉这条变更）

容量估算（给计算过程）

一张 5000 万行、平均单行 500 字节的订单表：
全量数据量 = 5×107 × 500B = 2.5×1010B ≈ 23.3 GB。
按每天 1% 行发生变更、每次变更涉及整行 = 500B 计：日增量 ≈ 5×105 × 500B = 250 MB/天。
若 1 小时内要同步完全量 23.3 GB：持续带宽 = 23.3 GB × 8 / 3600 s ≈ 51.8 Mbps，留一倍余量 → 链路至少 100 Mbps。这就是"要不要上 CDC"的决策依据：全量每天 100 Mbps 跑 1 小时，多数内网链路和源库 IO 都吃不消。

这份配置里每个关键参数在决定什么

参数作用与坑
splitPk: idDataX 按主键范围把表切成 N 个分片，每个 Task 读一片。不加则单线程读整表；主键分布不均（如按时间递增的 id，新数据集中在尾部）会造成分片倾斜
channel: 3reader→writer 的缓冲区队列数，控制内存占用和背压。默认 1，大表调 3~5
byte: 10485760每秒最多 10 MB，保护源库和网卡。不限速的 DataX 能把源库 IO 打满，连带线上业务变慢
errorLimit脏数据容忍度。record=0 表示一条都不许错。设 percentage 前想清楚：脏数据静默跳过 = 丢数据
preSql: TRUNCATE全量覆盖场景先清空目标表。必须确认下游没人读这张表，否则清空到灌完之间窗口期查不到数据
rewriteBatchedStatementsMySQL JDK5+ 驱动参数，把多条 INSERT 合并成一条批量语句，写入性能可提升数倍
DataX 的语义边界：单表任务不是原子的。失败时目标表可能处于"清了一半、灌了一半"的状态，重跑前必须自己处理。而且 DataX 不感知目标端已有数据，幂等要么靠 preSql 清表（全量），要么靠目标端 ON DUPLICATE KEY UPDATE（增量）。把 DataX 当"插一次就跑完"的工具，重复执行就是重复数据。
模块 3

实时同步：Canal / Debezium / Flink CDC

工具架构schema 变更一致性
Canalserver 伪装 MySQL 从库拉 binlog，client 消费（常用 canal-server + MQ）弱（需 client 自行适配）at-least-once，客户端自己幂等
Debezium基于 Kafka Connect，source connector 读 binlog 写 Kafka topic强：DDL 事件进独立 schema change topicat-least-once；快照阶段支持 exactly-once 语义
Flink CDCflink-cdc-connectors 内嵌 Debezium 反序列化，直接出 DataStream强（自动传播部分 DDL）checkpoint + 2PC sink 可做到 exactly-once

Flink CDC SQL 方式（生产常用形态）

-- 一张 binlog 源表，自动解析 DML（含 DELETE）
CREATE TABLE orders_cdc (
  id          BIGINT,
  user_id     BIGINT,
  amount      DECIMAL(10,2),
  status      VARCHAR(16),
  update_time TIMESTAMP(3),
  PRIMARY KEY (id) NOT ENFORCED
) WITH (
  'connector' = 'mysql-cdc',
  'hostname' = '127.0.0.1',
  'port' = '3306',
  'username' = 'flink',
  'password' = 'flink',
  'database-name' = 'orders',
  'table-name' = 't_order',
  'server-id' = '5400-5404',
  'scan.incremental.snapshot.enabled' = 'true'
);

-- 实时宽表：订单流 JOIN 用户维表，写入下游
INSERT INTO dw.dwd_order_full
SELECT o.id, o.user_id, u.name, o.amount, o.status, o.update_time
FROM orders_cdc o
JOIN users_cdc u ON o.user_id = u.id;

Java DataStream 版的核心两行（说明 schema 也是数据流的一部分）

// binlog 源是 Flink Source，支持从 checkpoint 位点恢复，重启不丢
MySqlSource<String> source = MySqlSource.<String>builder()
    .hostname("127.0.0.1").port(3306)
    .databaseList("orders").tableList("orders.t_order")
    .username("flink").password("flink")
    .deserializer(new JsonDebeziumDeserializationSchema())
    .startupOptions(StartupOptions.initial())
    .build();
env.fromSource(source, WatermarkStrategy.noWatermarks(), "mysql-cdc");

一致性保证的三层防线

  1. 语义层：CDC 本身是 at-least-once。任务重启、重试必然产生重复事件，一致性靠目标端幂等兜底——主键冲突时 INSERT ... ON DUPLICATE KEY UPDATE，或目标库用 REPLACE INTO。
  2. 顺序层：单表的 binlog 事件严格按提交顺序排列，但写进 Kafka 多分区后会乱序。必须按主键取模分区，保证同一行的所有变更进同一分区、有序消费，否则"先删后插"可能被消费成"先插后删"，最终留下旧值。
  3. 事务层：要 exactly-once 就上 Flink checkpoint + 两阶段提交 sink（如 Kafka）。代价是延迟增加和 sink 必须支持事务（MySQL JDBC sink 目前只做到幂等写，不是真正的 2PC）。
大事务是 CDC 的头号杀手。源库一个事务 UPDATE 了 200 万行，binlog 会连续吐 200 万条变更事件。CDC 消费端反序列化跟不上，lag 从秒级涨到小时级，下游看到的数据停留在几小时前。发现 lag 涨先查源库：SELECT * FROM information_schema.innodb_trx WHERE trx_started < NOW() - INTERVAL 60 SECOND，揪出长事务让它改批量提交。同时给 CDC 任务配 lag 告警（binlog 位点差 > 100MB 或延迟 > 30s 即告警）。
模块 4

任务调度与依赖

调度系统的本质是按 DAG 在正确的时间触发正确的任务，并在失败时知道该重试哪些。数据同步管道的调度比离线批处理更敏感：上游晚到 10 分钟，下游全部指标延迟。

依赖类型定义坑
同周期依赖T 日任务依赖 T 日的上游任务（最常见）上游延迟 → 级联等待， SLA 层层透支
跨周期依赖T 日 02:00 的全量任务依赖 T-1 日所有小时任务依赖判断错误会读到不完整分区
自依赖本任务上一个实例完成才能触发下一个（串行化）上次实例卡住 → 本次永不触发，静默停摆

调度器选型

系统依赖模型适用
AirflowPython 定义 DAG，XCom 传参，生态大云数仓 ELT、Python 数据团队
DolphinScheduler可视化 DAG，国产，工作流+数据质量一体国内中台、多团队共用调度
XXL-Job轻量，单任务粒度为主，路由/分片广播同步任务、轻量批处理（详见调度专题）

补数据（backfill）的正确姿势

# 补数据是事故高发区：直接改调度周期触发，会级联触发整条下游 DAG
# 正确做法：补数据任务打标记，只跑自己，不触发下游
INSERT INTO dw.dwd_order
SELECT * FROM ods.t_order_raw
WHERE dt = '2026-10-12'
  AND is_backfill = 1;   # 分区标记，与日常跑批物理隔离

# 补完再单独触发下游的"指定分区"实例，而不是整个 DAG
# 核心原则：补数据是手术，不是扫射。能按分区/按日期精确重跑，就别整条链路重跑
SLA 倒逼设计：给每条链路定义"承诺完成时间"（如 07:00 前产出 T-1 报表），拆解为每个节点的 deadline，哪个节点超时就告警到责任人，而不是等下游业务方早上来问"怎么还没数据"。同步任务的监控四件套：运行时长趋势、成功率、数据量波动（±30% 告警）、端到端延迟（源库最新时间 vs 目标库最新时间）。
模块 5

数据质量与血缘

校验规则：强规则阻断，弱规则告警

规则类型检查 SQL 示例级别
主键唯一SELECT id, COUNT(*) c FROM t GROUP BY id HAVING c > 1强（阻断下游）
空值率SELECT COUNT(*) FROM t WHERE user_id IS NULL强（核心字段）
枚举合法SELECT DISTINCT status FROM t WHERE status NOT IN ('PAID','REFUND')弱→强
行数波动ABS(today_count - avg_7d) / avg_7d > 0.3弱（大促会误报，设白名单）
值域检查SELECT COUNT(*) FROM t WHERE amount < 0强
主外键LEFT JOIN 维表 ON ... WHERE 维表.id IS NULL弱（维表延迟会误报）
规则怎么落地：同步任务后置一个"质量检查步骤"，强规则失败 → 任务标红 + 阻断下游 + 通知值班；弱规则失败 → 记录质量报告不阻断。工具有 Great Expectations（Python）、Deequ（Spark）、DolphinScheduler 内置质量模块。别追求规则全覆盖——先从"主键唯一 + 空值率 + 行数波动"三条开始，它们能拦住 80% 的事故。

血缘（Lineage）：自动化解析，禁止人工维护

血缘回答两个问题："这张表的下游有哪些，改它会影响谁"和"这个指标数字错了，从哪条链路开始查"。实现方式是解析 ETL 任务的 SQL AST 提取表/字段依赖，按标准协议上报（OpenLineage 是当前事实标准，Marquez/DataHub/Apollo Atlas 可做存储与可视化）。

# 血缘为什么必须自动解析：
# 人工维护的 wiki 在第一次表改名后就是废纸，没人会记得更新
# 正确链路：任务调度器/OOzzie 每次执行时上报 OpenLineage 事件
#   → collector 落库 → 前端画表级/字段级血缘图 → 支持影响分析
# 关键能力：改表前先查"下游消费者列表"，群里挨个通知
模块 6

schema 变更处理与一致性对账

上游 DDL 是同步链路最常见的"无预警故障"

变更类型对同步任务的影响处理方式
加列（有默认值）增量 SQL 列清单不含新列 → 新列数据永远丢；binlog 含新字段但 writer 列不匹配 → 报错同步配置加"自动同步列"或定期 diff 源/目标 schema
删列目标端残留该列，binlog 里消失 → 目标端永远保留旧值目标表同步 DROP，或映射为 NULL
改类型（加宽）INT→BIGINT：binlog 解析正常，目标端写入可能截断目标端类型同步扩大，先改下游再改上游
改类型（缩窄）VARCHAR(64)→VARCHAR(32)：超长值写入失败或截断禁止缩窄，或同步任务加长度校验
改主键 / 加主键splitPk 失效、CDC 解析报错、幂等键变化停机变更，评估全量重建
# Debezium 的 schema 变更处理：DDL 事件进独立 topic
# myserver.orders.t_order        → 数据事件（DML）
# myserver.schema-changes.orders → DDL 事件（ALTER TABLE 等）
# 消费者要订阅两个 topic，否则上游加列后 consumer 反序列化直接抛异常

# Flink CDC 的 schema 变更传播（有限支持）：
# 加列、删列会自动传播到下游；但改主键、改列类型会抛异常
# 应对：把 CDC 任务的目标表建成"宽表 + JSON 扩展列"，吸收新增字段
# ALTER TABLE dw.dwd_order ADD COLUMN extra JSON DEFAULT NULL;
最典型的静默事故：上游给 t_order 加了 coupon_amount 列，同步任务因为列清单写死而不报错也不同步新列，报表少算优惠金额，三周后财务对账才发现。解法：① 同步配置不要写死列清单（或写"SELECT *"）；② 每日跑一次 schema diff 作业，源目标结构不一致即告警；③ 关键表新列上线走变更评审。

一致性对账：最后防线，不能省

层级方法能发现什么
行数对账SELECT COUNT(*) FROM src 对比 dst整表丢失、任务整体失败
聚合对账SUM(amount), MAX(id) 按分区对比部分行丢失、金额被改小
内容对账MD5(GROUP_CONCAT(...ORDER BY id)) 全表 checksum行内容被篡改、更新丢失（成本最高）
实时对账CDC 变更流与目标端逐条比对（如 Flink 双流 JOIN）分钟级不一致，不用等 T+1
-- T+1 聚合对账 SQL（按天分区）
SELECT dt,
       COUNT(*)      AS cnt_src,
       SUM(amount)   AS amt_src
FROM ods.t_order_raw
WHERE dt = '2026-10-17'
GROUP BY dt;

-- 与数仓侧同口径结果对比，差异 > 0 即写入对账差异表：
-- 差异表字段：dt, table_name, check_type, src_value, dst_value, status
-- 修复流程：标记 status=待重跑 → 只重跑该分区 → 复检 → 关闭
-- 关键：对账任务本身也要监控（对账任务挂了 = 系统瞎了）
模块 7

容量与性能

并行度估算公式

# 批处理并行度
并行度 = 表数量 × 单表分片数
单表分片数 = 表数据量 ÷ 单 Task 吞吐（DataX 经验值 5~20 MB/s，取决于行宽）
# 例：10 张表共 50 GB，单 task 10 MB/s，要求 1 小时完成
#   需要 50GB/3600s ≈ 14 MB/s 持续 → 至少 2 个 task
#   考虑 3 倍余量（源库竞争、网络抖动、GC）→ 每表 2~4 片

# CDC 并行度
并行度 = 库表数 ÷ 单 task 可监听表数
# Flink CDC 单 task 监听多表（一张 binlog 流拆多表），并行度 = min(表数, 集群 slot 数)
# 注意：Flink CDC 的并行度不能大于表的 binlog 分区有序性要求，
#       单表提升并行度会破坏表内顺序，只能按表分

源库保护与带宽

手段做法
读从库DataX/Canal 指向只读从库，隔离主库压力（注意从库延迟会造成数据滞后）
限速DataX speed.byte；Flink 源限 executor 并行度 + 背压； Canal canal.instance.memory.bufferSize

必须盯的监控指标

CDC lag（秒）binlog 最新位点时间 - 当前消费位点时间，> 60s 告警
binlog 位点差（MB）累计未消费 binlog 量，突增 = 大事务或消费阻塞
任务运行时长与历史 P95 对比，劣化 50% 即预警
数据量波动本次同步行数 vs 近 7 天同时段均值，±30% 告警
源库主从延迟Seconds_Behind_Master，同步期间持续上涨说明压垮了从库
目标端写入失败率按错误码分组：超时/死锁/列不匹配分别报警
binlog 会被自动清理，这是 CDC 的隐藏红线。MySQL binlog_expire_logs_seconds（默认 2592000 = 30 天）过期后旧位点失效。如果 CDC 任务挂了 3 天没人管，恢复时报"binlog file not found"，只能重新全量快照。所以 CDC 任务必须有：① 位点 checkpoint 持久化；② 任务存活告警（挂了 10 分钟就喊人）；③ 定期演练"从 checkpoint 恢复"。
模块 8

十个线上坑

1
增量同步靠 update_time，但字段上没索引
每次同步全表扫描，源库 CPU 打满，连带线上业务变慢。加组合索引 (update_time, id)，并 EXPLAIN 确认走索引。
2
"改旧单"导致增量永久漏数据
业务把 30 天前的订单状态从"已完成"改为"已退款"，水线 SQL 永远捞不回来。历史数据修正要么触发全量，要么用 binlog 兜底（CDC 天然覆盖）。
3
增量同步丢 DELETE
update_time 模式只能感知插入和更新，源库的删除操作在目标端永远少一行。需要感知删除就走 CDC，或源库软删除（改状态位而非真删）。
4
重复执行 = 重复数据（无幂等）
任务失败重跑，目标端又插一遍。幂等三选一：主键冲突 ON DUPLICATE KEY UPDATE、REPLACE INTO、或先按主键删除再插入。
5
上游加列，同步任务静默少一列
列清单写死在配置里，新列既不报错也不同步，报表口径悄悄变化。每日 schema diff 作业 + 配置不写死列清单。
6
splitPk 选自增主键，分片严重倾斜
id 1~1000 万集中在最近三个月，尾部分片数据量是头部的几十倍，任务整体被最慢分片拖住。换分布均匀的列，或先按时间范围预分区再各自分片。
7
大事务把 CDC lag 拖到小时级
源库一个事务改 200 万行，binlog 连续涌入，消费端跟不上，下游数据停留在几小时前。规范批量提交（每批 1 万行一个事务），监控 innodb_trx 长事务。
8
补数据触发整条 DAG，下游重复计算
为了修一天的数据，重跑上游导致下游十个任务全部重新计算，成本翻倍且报表互相覆盖。补数据必须打标记、按分区精确重跑、不自动触发下游。
9
binlog 过期，CDC 位点失效
CDC 任务故障 3 天没人处理，binlog 被自动清理，恢复时只能全量重建，期间数据空洞。监控任务存活 + 位点连续性，故障恢复 SOP 写清楚。
10
敏感数据明文同步到数仓
手机号、身份证全量落 ODS，数仓权限比业务库宽得多，等于扩大暴露面。入库前脱敏（掩码/哈希/保留格式加密），数仓按列授权，审计导出行为。
自测

六道题

1. ETL 和 ELT 最本质的区别是？
正确答案：转换发生的位置。ELT 依赖数仓的弹性算力，把清洗逻辑变成 SQL 模型，是当前云数仓的主流做法；ETL 的转换在独立引擎里完成，链路更长但适合异构场景。
2. 增量同步用 WHERE update_time > last_watermark 捞数据，以下哪个场景会丢数据？
正确答案：删除历史订单。水线模式只捕获"水线之后发生变化的行"：删除的目标行 update_time 不会变（且行已不存在），增量 SQL 永远感知不到。插入和更新都会被 update_time 捕获。
3. DataX 配置中 splitPk 的作用是？
正确答案：分片读取。DataX 按 splitPk 的范围把单表拆成多个分片，每个 Task 读一片，这是它并行的来源。不配 splitPk 则单线程读整表，大表会跑得非常慢。
4. 为什么说 CDC 对源库的压力比全量 SELECT 小得多？
正确答案：读 binlog，不查表。CDC 通过复制协议订阅已经写好的日志，源库的 CPU、Buffer Pool、IO 都不受影响。但要注意：大事务会让 binlog 流量突增，消费端 lag 上涨。
5. Flink CDC 任务重启后，如何保证已经处理过的 binlog 事件不重复影响下游？
正确答案：at-least-once + 目标端幂等。Flink checkpoint 恢复时会重放部分事件，这是设计使然；真正去重靠目标端主键冲突时走 UPDATE 分支。追求 exactly-once 需要 2PC sink，代价是延迟和复杂度。
6. 一条 5000 万行、单行 500B 的表，全量约多少数据量？要在 1 小时内同步完，不考虑余量至少需要多少持续带宽？
正确答案：23.3 GB / 52 Mbps。计算：5×107 × 500B = 2.5×1010B ≈ 23.3 GB；带宽 = 23.3 GB × 8 ÷ 3600 s ≈ 51.8 Mbps。实际工程要再留 2~3 倍余量给源库竞争、网络抖动和失败重试。
