二十分钟学透分布式任务调度系统

任务调度的本质是在正确的时间、把任务交给正确的机器、执行一次且仅一次。这篇讲机制：调度中心/执行器/注册中心怎么分层、触发与路由的完整链路、分片广播怎么把 500 万行的任务拆给 8 台机器、重试与幂等怎么配合、Quartz Cluster / XXL-Job / ElasticJob 怎么选，以及重复执行、单点、任务堆积、时钟漂移四个经典死法。

三个容易混淆的角色：调度中心决定"何时触发、触发谁"（无状态，可集群）；执行器是干活的业务进程（有状态，跑真实业务代码）；注册中心/数据库让调度中心知道有哪些执行器在线。把三者合在一个进程里"看起来更简单"，实际是把自己绑死在单点上——分层的目的就是让调度可以集群扩容，而业务机器各自独立。
模块 1

调度系统核心与架构

一句话定义：调度系统 = 触发器 + 路由器 + 执行器注册表 + 监控告警。所有功能都围绕"把一次任务触发准确送到一台健康的机器上并执行成功"展开。

职责机制失败形态
触发按 CRON/延迟/事件产生触发信号，记录任务实例漏触发（时间漂移）、重复触发（多调度节点）
路由从在线执行器列表里按策略选一台派发选到已下线机器、全部选中一台（热点）
执行执行器线程池接收、执行业务逻辑、回报结果线程池打满、执行中进程被杀无感知
监控重试超时检测、失败重试、故障转移、日志汇总失败无人知、重试无幂等越重越错

XXL-Job 的完整链路

执行器启动：向调度中心注册（appName + IP + 端口），之后每 30 秒心跳续约
调度线程到点：调度中心集群通过 DB 锁竞争选出唯一节点，读取未来 5 秒内需要触发的任务
生成任务实例：写入任务日志表（状态=待执行），按路由策略选一台执行器
派发执行：Netty/HTTP 推送执行请求，执行器线程池领取执行，日志实时回传调度中心
结果回报：成功/失败回报；失败按配置重试（重新走一遍路由）；超时未回报触发故障转移
# 调度中心的 DB 锁竞争（XXL-Job 用轻量行锁 + 时间片）
# quartz 集群用 LOCKS 表对 TRIGGER_ACCESS 行加悲观锁，锁竞争的节点：
#   - Quartz Cluster：每触发一次都抢一次锁，节点多时锁冲突严重
#   - XXL-Job：按"未来时间片"预锁，锁粒度粗、冲突少，集群规模不受锁限制
# 结论：调度节点数 Quartz 建议 <= 3，XXL-Job 可以水平扩到 10+
调度中心必须无状态。所有任务定义、触发记录、执行日志都在数据库，调度节点只做计算和转发。这样任何一个调度节点宕机，剩下的节点接管触发，任务不丢不重。把任务配置缓存在调度节点内存里、或者依赖节点本地文件，是分布式调度的大忌。
模块 2

触发方式与 misfire 处理

方式机制适用坑
CRON表达式描述触发时刻（秒 分 时 日 月 周 [年]）绝大多数定时场景时区、不存在的日期（2 月 30 日）、表达式写错静默不触发
固定延迟上次执行结束后间隔 N 秒再触发怕任务重叠的轮询（如拉消息）执行慢时触发频率自动降低，可能永远追不上产出
固定速率无论上次是否结束，每 N 秒触发一次心跳、指标采集会重叠执行，必须配"单实例并发策略"
API/事件触发外部系统调接口触发一次（带参数）补数据、手动重跑、工作流下游无鉴权就是任意执行入口，必须加 token + 限流
工作流 DAG上游任务成功事件触发下游多步骤数据管道、发布流水线依赖成环、部分失败时下游状态机复杂
# CRON 表达式（6 位：秒 分 时 日 月 周；7 位带年）
0 0 2 * * ?          # 每天 02:00 —— 最常用的离线跑批
0 0/5 * * * ?        # 每 5 分钟
0 0 0 L * ?          # 每月最后一天
0 0 12 ? * WED       # 每周三中午
0 0 0 1 1 ?          # 每年 1 月 1 日

# 高危表达式（能解析但语义危险）
0 0 0 29 2 ?         # 2 月 29 日 —— 只有闰年存在，平年永不触发
0 0 0 * * ?          # 每天 0 点但没考虑时区，容器 UTC 时差 8 小时
0 0/30 * * * ?       # 每 30 分钟，但如果任务要跑 40 分钟，就会背靠背重叠

misfire（错过触发）策略

任务到点但系统繁忙/重启，恢复后这一拍要不要补？不同框架语义不同，选错要么丢一次要么补十次：

策略行为适用
fire now（立即补）错过的全部立即补触发金融类一次都不能丢；小心补出十次
next with current count立即触发一次，计数正常推进幂等任务的折中
next with remaining count丢弃错过的，只触发下一拍指标采集类可丢场景
do nothing错过就错过强节流任务（如限频拉取）
错过的触发补不补，先问"这次任务重复执行的代价"。发券任务错过 10 拍 = 补 10 次重复发券（必须幂等兜底）；对账任务错过 1 拍 = 当天账不平（必须补）。统一建议：补偿语义在框架层配置，幂等保证在业务层实现，两层都要有，别指望单层。
模块 3

分片广播：大数据量任务拆分

场景：凌晨给 500 万沉睡用户发券。单机顺序处理按 2000 条/秒算要 4 小时，早过了业务窗口。解法是分片广播：把任务广播给所有在线执行器，每台机器只处理 1/N。

分片广播执行时序

触发：调度中心向该任务所有在线执行器同时派发执行请求（不是选一台）
携带分片参数：每台机器收到自己的 shardIndex（我是第几片）和 shardTotal（总共几片）
取数：每台机器按 WHERE id % shardTotal = shardIndex 只捞自己那片数据
扩容加速：分片总数随在线执行器数量自动变化，8 台机器就是 8 片，时间从 4 小时降到 30 分钟
// XXL-Job 分片任务代码（真实 API：XxlJobHelper）
@XxlJob("sendCouponHandler")
public ReturnT<String> sendCouponHandler() {
    int shardIndex = XxlJobHelper.getShardIndex();   // 当前机器分片号 0~N-1
    int shardTotal = XxlJobHelper.getShardTotal();   // 总片数 = 在线执行器数
    XxlJobHelper.log("分片 {}/{} 开始", shardIndex, shardTotal);

    // 关键：按取模分片，保证同一用户始终落到同一台机器（幂等键不变）
    List<User> users = userMapper.selectSleepUsers(shardIndex, shardTotal);
    for (User u : users) {
        if (couponService.exists(u.getId())) continue;  // 幂等：已发过跳过
        couponService.issue(u.getId());
    }
    return ReturnT.SUCCESS;
}

# 对应 SQL：id % #{shardTotal} = #{shardIndex}
# 注意：取模字段必须分布均匀（自增 ID 可以，手机号后四位也可以）
# 如果取模字段倾斜（如 status 只有 3 个值），某片会拿 90% 数据

分片策略对比

策略机制特点
取模分片id % total = index简单均匀；扩容时 total 变化，数据会重新分布（本轮做完即稳定）
哈希取模+一致性按业务键哈希后映射扩容时只迁 1/N 数据，适合有状态分片
ElasticJob 数据分片基于注册中心的分片项，支持自定义分片算法分片与执行器解耦，弹性伸缩最优雅
按范围分片时间范围/ID 区间切给各机器适合天然分区数据（按天、按城市）
分片任务的三个暗坑：① 扩容时 total 变了——跑到一半加了机器，本轮不同机器用的 total 不一致，会有用户漏处理或重复处理（幂等键兜底）；② 某片失败整体语义——8 片里 1 片失败，是算整体失败重跑全部 8 片，还是只补失败那片？建议按片记录状态，只补失败片；③ 执行器缩容——机器下线时它那片数据没人处理，必须等下线机器回报结果或由其他机器接管未完成分片。
模块 4

失败重试与超时控制

重试的三层配置

层配置建议
任务级重试失败后自动重新触发 N 次，间隔递增（1min、5min、15min）瞬时故障（网络抖动）有效，3 次足够
failover 故障转移执行器超时未回报 → 换一台机器重跑应对机器宕机；要求任务可整体重入
busyover 忙碌转移目标执行器线程池忙 → 换一台避免全部任务挤在同一台
// XXL-Job 失败即重试的语义：返回 FAIL 或抛异常都会按重试次数重新触发
@XxlJob("syncOrderHandler")
public ReturnT<String> syncOrderHandler() {
    try {
        orderSyncService.sync();          // 内部按批次幂等
        XxlJobHelper.handleSuccess("同步完成，共 1200 单");
        return ReturnT.SUCCESS;
    } catch (RetryableException e) {
        // 可重试错误（下游超时）：返回 FAIL，框架自动重试
        XxlJobHelper.handleFail("下游超时: {}", e.getMessage());
        return ReturnT.FAIL;
    } catch (FatalException e) {
        // 致命错误（数据格式错）：重试也没用，标失败让人工介入
        XxlJobHelper.handleFail("数据格式错误，需人工介入");
        return ReturnT.FAIL;
    }
}

# 重试间隔配置（XXL-Job 2.4.1 支持）
# 任务管理页：重试次数=3，重试间隔按指数退避由框架默认策略处理
# 自研调度：建议存 3 个间隔值 [60s, 300s, 1800s]，别固定间隔猛敲

超时控制：三层防线

  1. 框架级超时：执行请求超过 N 分钟未回报 → 判定失败，触发 failover。阈值按任务 P99 时长 × 2 设置，太短会误杀长任务。
  2. 业务级超时：任务内部对下游调用设超时（HTTP 3s、DB 5s），别让一个慢下游拖垮整个任务线程。
  3. 进程级看护：任务线程注册取消回调，任务被放弃时能中断正在进行的批处理（检查中断标志），避免"僵尸执行"继续写数据。
failover 与幂等是绑定的。开启故障转移意味着"同一个任务实例可能被两台机器各跑一部分"。如果任务没有幂等设计（如直接 INSERT 发券记录），failover 就是把单点故障升级成数据事故。没有幂等保证的任务，宁可让 failover 只做告警不做自动重跑。
模块 5

路由策略与幂等设计

策略选择逻辑适用
FIRST固定选注册列表第一台单机任务"假装分布式"，无意义
ROUND（轮询）依次轮转，负载最均匀无状态批任务，默认推荐
RANDOM随机选一台与轮询近似，胜在无顺序状态
CONSISTENT_HASH按任务参数哈希，同参数尽量落同一台利用本地缓存/本地状态的任务
LEAST_FREQUENTLY_USED选累计使用最少的机器长尾均衡，机器性能差异大时
LEAST_RECENTLY_USED选最久未被使用的机器与 LFU 近似
FAILOVER按注册顺序探测，找到第一台健康的关心"别选到挂的机器"，不关心均衡
BUSYOVER目标忙则顺延下一台，都忙则排队任务时长差异大的混合集群
SHARDING_BROADCAST广播给全部在线执行器分片任务（模块 3）

一致性哈希的真实价值

某报表任务每次跑要加载 2GB 维度数据到本地缓存，ROUND 策略下每次都换机器、每次都重新加载 2GB。换成 CONSISTENT_HASH 后，同一任务固定落在同一台机器，本地缓存命中，任务从 20 分钟降到 4 分钟。代价是那台机器负载偏高——用 LFU 或给缓存预热单独留一组执行器来平衡。

幂等设计：任务重复执行的防火墙

# 幂等三件套：唯一键 + 状态机 + 去重表

# 1. 唯一键：任务实例 ID（调度框架生成，全局唯一）
#    每个触发都带 logId，业务表存 biz_key = logId，重复执行撞唯一键即拒
CREATE TABLE task_execution (
  log_id      BIGINT PRIMARY KEY,      -- 调度实例 ID = 幂等号
  task_name   VARCHAR(64),
  status      VARCHAR(16),             -- RUNNING / SUCCESS / FAILED
  started_at  TIMESTAMP,
  updated_at  TIMESTAMP
);

# 2. 状态机：先查状态再执行，RUNNING 直接返回（不并发重入）
#   UPDATE task_execution SET status='RUNNING' WHERE log_id=? AND status IS NULL
#   影响行数 = 0 → 说明已在跑或已跑过 → 直接返回

# 3. 业务侧幂等：发券先查 unique(user_id, coupon_batch_id)，存在即跳过
INSERT INTO user_coupon(user_id, batch_id, log_id)
VALUES (?, ?, ?)
ON DUPLICATE KEY UPDATE id=id;   -- 撞唯一键静默成功，不重复发
幂等的边界要想清楚：框架给的是"同一个任务实例不会并发执行"的保证，但 failover、重试、人工补触发都会创造新的实例 ID。所以幂等不能只靠 log_id，业务侧必须有独立于调度系统的幂等键（user_id + batch_id）。原则：调度的幂等防"同时跑"，业务的幂等防"跑两次"，两层缺一不可。
模块 6

框架对比：Quartz / XXL-Job / ElasticJob / PowerJob

框架架构与一致性优势短板
Quartz ClusterJDBCJobStore + LOCKS 表悲观锁，集群节点抢锁触发嵌入简单，无额外组件节点多锁冲突剧烈（建议 ≤3 节点）；无管理界面；无分片广播
XXL-Job调度中心（DB）+ 执行器（注册心跳），轻量锁 + 时间片Web 管理、日志在线看、路由/分片/重试齐全、社区活跃、学习成本低依赖中心化 DB；执行器非无状态（机器与任务有绑定关系）
ElasticJobZooKeeper 协调（3.x 也支持 etcd），数据分片 + 弹性伸缩分片模型优雅、扩容自动重分片、适合海量数据分片依赖 ZK；概念多（分片项/分片策略/监听器）；无 Web 控制台
PowerJob调度服务器 + Worker，支持 DAG 工作流功能最全（工作流/MapReduce 式/容器化）组件更重，社区规模小于前两者
云调度阿里 SchedulerX / AWS EventBridge Scheduler 等托管免运维、自带监控告警厂商绑定、单价、定制受限

选型决策（按团队现状）：① 单体应用内嵌定时任务、量小 → Quartz/Spring Schedule 就够，别上分布式；② 需要管理界面、多团队、任务多且杂 → XXL-Job（国内事实标准）；③ 单任务数据量大到必须分片、且执行器数量频繁变 → ElasticJob；④ 重工作流编排（DAG）→ PowerJob 或 Airflow（数据向）。已经跑稳的别迁移，选型成本远高于框架差异。
模块 7

弹性扩缩容与监控

执行器上下线的完整生命周期

上线注册：执行器启动即注册，调度中心路由表立即包含它（新机器马上参与负载）
心跳维持：每 30 秒心跳；连续 90 秒无心跳从路由表摘除（参数按集群规模调）
优雅下线：容器收到 SIGTERM → 先注销注册 → 等存量任务跑完（drain）→ 再退出。跳过注销直接杀，调度中心还以为它活着，任务派过去黑洞
下线补偿：已下线机器若还有未完成任务实例，靠 failover 由其他机器接管（要求幂等）

监控大盘必备指标

任务成功率 / 失败 Top10每日失败任务排行，@ 到负责人
执行时长 P50/P99耗时突增 50% 预警，通常是数据量或下游劣化
任务堆积量触发频率 × 时长 > 触发间隔 = 必然堆积
执行器在线数突然减少 = 批量宕机或注册链路故障
触发延迟计划时间 vs 实际触发时间，调度中心自身健康度
线程池使用率执行器线程池打满前扩容或限流
任务堆积的数学：某任务每 10 分钟触发一次，每次执行要 12 分钟。单机必然永远追不上——队列以每次 +2 分钟的速度增长。解法不是加机器，是先修慢的根因（批量化、并行化、分片），机器只是掩盖问题。判断公式：安全水位 = 执行时长 P99 < 触发间隔 × 0.8，超过就该治理了。
模块 8

十个线上坑

1
集群下同一任务被触发多次
调度节点集群没有正确选主，或多节点同时触发。XXL-Job/Quartz 都靠 DB 锁选主，但自研调度如果漏了锁竞争，全网重复执行是迟早的事。
2
调度中心是单点，且状态在本地
调度节点内存里存任务定义，重启后配置丢失；或单节点 DB 挂了全站定时任务停摆。调度中心必须无状态 + 多实例 + DB 高可用。
3
任务堆积没人发现，日志盘先满
执行慢于触发频率，队列持续增长；同时单次日志量暴增把磁盘打满，连带其他任务挂。监控执行时长趋势 + 磁盘水位。
4
节点时钟漂移，触发时间对不齐
机器间 NTP 不同步，A 节点认为 02:00 已到、B 节点认为没到，或分布式锁基于本地时间判断导致误判/漏判。所有机器同步 NTP，锁和超时判断基于单调时钟或服务端时间。
5
重试没有幂等，越重越错
发券任务失败重试 3 次，用户收到 3 张券。重试次数和幂等键必须同时设计，缺一个就是数据事故。
6
failover 与业务不可重入冲突
开了故障转移，但任务执行一半写坏中间状态，另一台机器从零跑完全部步骤，产生重复单据。不可重入的任务关闭 failover，改为告警人工处理。
7
执行器缩容时任务派发给已下线机器
容器被强杀没走注销流程，调度中心路由表仍包含它，任务派发过去无人执行直到超时。SIGTERM 处理里先注销再 drain，强杀场景靠 failover 兜底。
8
共享线程池，一个大任务堵死全部
所有任务共用一个 8 线程池，一个 30 分钟的报表任务占 6 个线程，其他任务全部排队延迟。按任务类型分池（核心池/批处理池），大任务独立队列。
9
API 触发接口无鉴权无限流
手动触发接口暴露内网，被脚本刷接口触发任务，或误传超大参数把任务打挂。触发接口加 token + 参数校验 + 单任务频率限制 + 全量审计。
10
补数据靠手动触发，没有审计和记录
线上出问题，有人手动触发了一次重跑，没记录没人知道，事后对账对不上。所有触发（自动/手动/API）必须落任务实例日志，可追溯到人。
自测

六道题

1. 一个任务要处理 500 万行数据，单机 4 小时，8 台执行器在线。最优方案是？
正确答案：分片广播。广播触发让所有在线执行器同时参与，每台带 shardIndex/shardTotal 只处理 1/N 数据，时间从 4 小时降到约 30 分钟，且扩容时自动加速。
2. 某任务每次执行要加载 2GB 本地缓存，希望尽量落在同一台机器上，应该选哪种路由策略？
正确答案：一致性哈希。按任务参数哈希后固定映射到同一台机器，本地缓存可以复用。ROUND/RANDOM 每次换机器，2GB 缓存每次重新加载，任务从 4 分钟变 20 分钟。
3. 关于调度系统的幂等设计，正确的说法是？
正确答案：两层都要。框架幂等只防"同一实例并发"，但 failover、重试、人工补触发都会创造新实例 ID。业务侧必须有独立幂等键（如 user_id + batch_id）防"跑两次"。
4. Quartz Cluster 模式为什么一般不建议超过 3 个调度节点？
正确答案：锁竞争。Quartz 集群靠数据库行锁选主，每次触发都抢锁，节点数增加后冲突概率平方级上升，触发延迟抖动大。XXL-Job 用时间片预锁，粒度粗，集群规模基本不受限。
5. 多台机器时钟不同步，对分布式调度最直接的风险是？
正确答案：触发与锁误判。节点 A 认为到点、节点 B 认为没到，集群选主和触发判断出现分歧；基于本地时间的分布式锁会提前释放或永不释放。所有节点必须同步 NTP。
6. failover（故障转移）与 busyover（忙碌转移）的区别是？
正确答案：超时无响应 vs 线程池忙。failover 指目标机器派发后超时未回报，换一台重跑（要求任务可重入）；busyover 指目标机器明确回复"忙"，顺延到下一台（任务还没开始跑，代价小得多）。
