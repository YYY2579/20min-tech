二十分钟学透秒杀系统设计

秒杀不是"高并发版下单"，是有损服务设计：100 万人抢 100 件货，系统的目标不是让 100 万人都成功，而是让该成功的成功、该拒绝的快速拒绝、系统不挂。这篇讲透削峰、预扣、隔离、对账四件事。

开始前

秒杀的特殊性：三个"不均"

普通大促是"流量涨 10 倍"，秒杀是"流量涨 1000 倍且全部砸向同一个 SKU"。秒杀系统的所有设计，都来自三个不均。

时间不均
10 万 QPS 集中在开抢后 1~3 秒，3 秒后归零。扩容来不及，必须提前按峰值备好
读写不均
读（详情页/资格校验）远大于写（扣库存）。但真正的竞争全在写——100 人抢最后 1 件
冷热不均
99% 的 SKU 无人问津，1% 的爆款承接全部流量。热点隔离由此而来

本篇算例参照系：100 件库存的爆款，活动页曝光 500 万人次，开抢瞬间涌入 30 万并发请求，实际库存 100 件。有效请求率 = 100/300000 = 0.03%——系统 99.97% 的工作是"快速拒绝"，这就是秒杀的本质。

秒杀的设计哲学（先记住这句）：把尽可能多的请求挡在离用户最近的地方。每一层拦截都让到达数据库的请求指数级减少：前端答题 → 网关限流 → 令牌校验 → Redis 预扣，四层下来，真正落到 MySQL 的写只有 100 条（= 库存数）。
模块 1

整体架构：四层漏斗

秒杀链路是标准的漏斗结构：每一层的唯一职责是用最低成本拦掉最多请求。

第 0 层 · 前端：按钮置灰 / 答题 / 动态 URL
30 万并发 → 12 万
第 1 层 · CDN + 网关限流：静态化 + limit_req
12 万 → 1.2 万（拦 90%）
第 2 层 · 秒杀服务：资格校验 + 令牌发放
1.2 万 → 1200（令牌 = 库存 10 倍）
第 3 层 · Redis 预扣：Lua 原子扣库存
1200 → 100（= 库存数）
第 4 层 · 异步落库：MQ → MySQL 订单
100 条写（不参与并发竞争）
分层架构（读写分离，异步优先）
前端 按钮置灰/答题/排队动画/动态 URL网关 限流/黑名单/风控秒杀服务 资格/令牌/排队（无状态，可水平扩）Redis 库存预扣/令牌/资格MQ 异步下单/削峰填谷MySQL 订单落库（唯一真相）

核心原则

  • 读多写少，读走缓存，写走异步：资格校验、库存查询全部读 Redis；下单是写，必须经过令牌 + 预扣两道闸
  • 一切同步调用只保留"必要最小集"：秒杀链路同步调用 = 资格校验 + Redis 预扣，总共 2 次。计价、优惠券、积分全部异步甚至省略
  • 请求有损是特性不是 bug：99.97% 的请求被拒绝是设计目标。返回"已抢完"要快（< 10ms），不要让用户转圈等失败
模块 2

削峰：把 30 万请求摊薄

削峰是秒杀的第一武器。四种手段，成本递增、效果也递增，组合使用。

手段一：答题 / 验证码（拉长时间维度）

  • 作用：把 1 秒内涌入的请求拉长到 5~30 秒（答题需要时间），同时把"脚本请求"挡在门外（黑产没有廉价的人肉答题产能）
  • 实现：开抢前展示答题/滑块，答对才发"答题通过凭证"（带签名 + 时效）；服务端只认凭证
  • 代价：真实用户体验受损，只用于高价值爆款（茅台、iPhone），普通商品不用

手段二：隐藏秒杀地址（防脚本蹲点）

// 秒杀开始前，接口地址对客户端不可见
// 1. 活动页不暴露真实下单 URL，只暴露"获取秒杀路径"接口
GET /seckill/path?activity_id=123
// 2. 服务端返回动态路径（带签名，一次性，绑定用户）：
//    /seckill/buy/a8f3d?token=hmac(activity_id, user_id, timestamp)
// 3. 下单接口校验 token 的签名 + 时效（如 60 秒）+ 一次性（Redis 记录已用）
// 效果：黑产脚本提前蹲点失效，因为路径开抢后才生成且每人不同

手段三：排队 + 令牌（流量整形）

  • 令牌桶：系统按库存的 10 倍发放令牌（如 1000 个），只有持令牌的请求能进预扣环节。令牌数是并发写量的总闸
  • 排队：拿不到令牌的请求进入排队（前端转圈动画），服务端按序放行或直接返回"排队人数过多"
  • 结果轮询：异步下单后，客户端每 1~2 秒轮询下单结果，不用长连接等（长连接把 30 万请求全挂住，连接数爆炸）

手段四：预约资格（开抢前分流）

活动前 1~3 天开放预约，只给预约用户开放购买入口。30 万并发直接降到预约人数的量级（通常 1/10），且预约名单本身是风控数据（过滤羊毛党）。大促标配。

削峰手段的选型逻辑：验证码伤用户体验、隐藏地址防不住人肉、排队让等待变长、预约缩盘子。没有完美方案，只有组合：预约缩量（提前 10 倍）→ 答题/验证码（再 3 倍 + 防机器）→ 令牌（最后 10 倍）→ 预扣（兜底到库存数）。
模块 3

库存扣减：Redis 预扣 + 异步落库

秒杀的库存扣减只有一种正确姿势：Redis 做唯一扣减点（ Lua 保证原子），MySQL 做最终记录，MQ 异步衔接，对账兜底。直接扣 MySQL 的都已阵亡（行锁竞争见电商篇）。

Lua 原子预扣（含防重 + 限购）

-- KEYS[1]=库存key KEYS[2]=用户已购key ARGV[1]=userId ARGV[2]=限购数
local stock = tonumber(redis.call('get', KEYS[1]) or '-1')
if stock == -1 then return -3 end        -- 未预热，拒绝
if stock <= 0 then return -1 end          -- 售罄
local bought = tonumber(redis.call('hget', KEYS[2], ARGV[1]) or '0')
if bought >= tonumber(ARGV[2]) then return -2 end  -- 超限购
redis.call('decrby', KEYS[1], 1)
redis.call('hincrby', KEYS[2], ARGV[1], 1)
redis.call('expire', KEYS[2], 86400)
return stock - 1                       -- 返回扣后库存

异步下单链路

// 1. 预扣成功 → 发 MQ（带 msg_id），立即返回用户"抢购成功，订单生成中"
// 2. 消费端：消费消息 → 幂等校验（msg_id 唯一索引）→ 写 MySQL 订单（待支付）
// 3. 用户轮询订单状态：待支付 → 展示收银台；30 分钟未支付 → 关单 + 回补库存

// 关键：MQ 消息必须带 msg_id，消费端用它去重（重试/重复投递不产生重复单）
// 关键：订单表的唯一键 = msg_id（或 (activity_id, user_id)），DB 层兜底幂等

超时未付：库存回补

# 关单链路（两个都要做，保证最终一致）
# 1. 延时消息：下单时发一条 30 分钟延时 MQ；到期检查订单状态
#    - 仍是待支付 → 关单 + Redis 库存 +1 + MySQL 预占释放
#    - 已支付 → 什么都不做
# 2. 补偿扫描（兜底）：定时任务扫"待支付且超时"的订单，防止延时消息丢失

# 回补的库存必须回到 Redis（用户可见的库存），否则出现
# "MySQL 显示有货但 Redis 已扣完"的分裂，超卖或丢单二选一
防超卖的最终防线永远是对账：Redis 预扣是内存操作，主从切换、AOF 丢数据都可能让 Redis 库存"凭空恢复"。每日对账：Redis 库存 + 已下单未付 + 已支付 = 活动总库存，偏差立即告警并冻结活动。对 MySQL 而言，Redis 的数字只是影子，订单表里的记录才是法律真相。
模块 4

热点隔离

秒杀流量 99% 打向同一个 SKU。不隔离的后果：这一个热点 key 打满 Redis 单节点、这一个 MySQL 行锁竞争瘫痪、顺带把同集群的其他业务全部拖死。

隔离维度做法
域名 / 入口秒杀独立域名（miaosha.example.com），DNS 独立解析，故障不互染
服务集群独立秒杀服务 + 独立网关 + 独立限流阈值。秒杀集群只做"资格 + 令牌 + 预扣"三件事
Redis独立 Redis 集群；库存 key 分片（见下）；活动元数据与库存分离
MySQL独立库 + 独立连接池。连接池打满只影响秒杀，不波及主站
MQ独立 topic。消费堆积不影响主站消息

热点 key 的三级拆解

// 问题：100 个库存 1 个 key，10 万 QPS 全打这一个 Redis 节点

// 第 1 级：库存分片（把 1 个 key 拆成 N 个，随机扣一个）
stock:sku:10086:0 ~ stock:sku:10086:15   // 16 个分片，每片 6~7 件
// 扣减时随机选片：slot = random(0,15)，扣 stock:sku:10086:{slot}
// 热点分散到 16 个 key（若分片恰好在不同节点，则分散到 16 个节点）

// 第 2 级：本地缓存（网关/应用层）
// 资格校验结果（"该用户可否购买"）本地缓存 5~10 秒，读请求不再打 Redis

// 第 3 级：本地令牌分段（极端方案）
// 开抢前把 1000 个令牌均分到 100 台机器的本地队列，本机令牌本机扣
// Redis 只做总量校准。写竞争从"全网 10 万 QPS 打 1 个 key"降为"单机 100 QPS"
隔离的验收标准：秒杀集群整体宕机，主站下单、商品详情、支付全部不受影响。做不到这一点，说明隔离没做完——通常是"秒杀服务偷偷调用了主站库存服务"或"共用了数据库连接池"。
模块 5

限流、熔断、降级

限流是秒杀的主武器（不是备用武器）。原则：每一层按自己容量限流，按下游容量的 70% 设阈值。

四层限流参数（算例：30 万并发）

层级阈值算法与说明
前端按钮置灰 + 答题开抢后按钮置灰 5 秒（防疯狂连点），从源头减少请求数
网关（Nginx）10 万 QPSlimit_req_zone 漏桶，按 IP + URI。超限直接返回 429 静态页，不打到后端
秒杀服务3 万 QPSSentinel 匀速器（令牌桶），削平突发；单机 1500 QPS × 20 台
Redis连接数 500 + 热点 key 限流单 key 超过 5 万 QPS 触发本地缓存顶包
MQ 消费消费能力 = 2000 单/s消费不过来就堆积（Kafka 保留 7 天），绝不同步阻塞用户
MySQL连接池 200写只来自 MQ 消费（100 单/活动），连接池永远不会满

熔断与降级预案

# 熔断触发条件（Sentinel 配置示例）
熔断策略：
  - 慢调用比例 > 50%（RT > 200ms）持续 10s → 熔断 30s
  - 异常比例 > 30% → 熔断 30s

# 降级清单（按优先级，触发即执行）
P0 库存查询降级：读本地缓存，允许 3 秒延迟
P1 资格服务降级：只校验本地签名，跳过风控
P2 风控降级：跳过实时风控，事后离线审计（高价值活动可接受）
P3 排队降级：关闭排队，直接返回"已抢完"
P4 活动降级：整个秒杀活动暂停，页面提示"活动太火爆"

# 原则：宁可拒绝 100 万用户，不能挂 1 个数据库
限流阈值拍脑袋是大忌：每个阈值必须来自压测数据。网关 10 万 QPS = "秒杀集群能消化的极限 × 0.7"，不是"感觉 10 万差不多"。没有全链路压测过的限流参数，等于没有限流。
模块 6

防刷与黑产对抗

秒杀是黑产利润率最高的战场（抢茅台转手赚 1000+）。对抗是持续军备竞赛，没有一劳永逸。

黑产手段对应防御
脚本高频请求动态 URL + 接口签名 + 单用户 QPS 限制（1 QPS）
虚拟机 / 群控多开设备指纹（IMEI/IDFA/MAC + 行为特征）+ 同设备多账号关联封杀
批量注册小号注册环节手机验证码 + 行为验证码 + 账号信誉分级（新号限制参与）
打码平台过验证码行为验证码（滑块轨迹/点击热力图分析）+ 语音验证码兜底
秒杀器改包重放接口参数签名 + nonce 一次性 + HTTPS 防中间人
内部人员泄露/串货令牌与用户绑定 + 风控审计 + 数据权限最小化
# 实时风控（Flink 流式计算，开抢前 5 分钟启动）
# 输入：点击流、登录流、下单流
# 规则（示例阈值）：
# - 单 IP 点击 > 50 次/秒 → 打标"疑似机器"，进验证码队列
# - 单设备 > 3 个账号参与 → 整设备拦截
# - 新注册 < 24h 账号下单 → 提高抽检比例
# 输出：黑名单（网关直接拦）+ 验证码队列 + 审计日志
限购是最后一道机械防线，必须做在原子层："一人一单"不能只在应用层判断（并发下双线程同时通过）。用 Redis 的 HINCRBY bought:{sku} {user_id} 1 和预扣放在同一个 Lua 脚本里（见模块 3），DB 层再加 UNIQUE(activity_id, user_id) 兜底。两层都要，少一层就是事故。
模块 7

全链路压测

秒杀系统的限流参数、扩容容量、降级阈值，只能来自压测。拍脑袋的参数等于没有。

压测三件套

流量染色：压测流量带标记（HTTP header x-stress-tag: gray），全链路透传——网关、服务、Redis、MQ、DB 都能识别"这是压测流量"
影子隔离：染色的写落到影子库/影子表（与生产数据物理隔离），读可读生产（保证链路真实）。Redis 用独立 db，MQ 用独立 topic
数据构造：造 100 万测试账号、千万级商品 SKU、与生产同量级的库存，用真实分布而不是全零数据（缓存命中率才会真实）

压测要回答的问题

问题达标线（算例）
系统能扛多大峰值？目标峰值的 1.5 倍 = 45 万并发
各层限流阈值多少？逐层加压，找到每层开始拒绝/超时的临界点，取其 70%
MQ 堆积会怎样？灌到消费 10 倍速，观察堆积量与消费恢复时间（应 < 30 分钟）
Redis 热 key 表现？单 key 10 万 QPS 下 RT 是否 < 5ms，CPU 是否打满单节点
降级开关是否有效？逐个触发降级开关，验证系统行为符合预案
压测的两个经典翻车点：① 影子没做干净——压测的"订单"写进了生产库，用户看到 phantom 订单；② 只压读不压写——资格查询 50 万 QPS 扛住了，但没验证"令牌发放 + 预扣"的写路径，正式开抢时写链路先崩。压测必须覆盖全链路 + 全读写 + 峰值 1.5 倍。
模块 8

复盘指标与十个坑

复盘看什么（活动结束后 48 小时内）

类别指标参考线
业务库存售罄用时、转化率（成功单/曝光）、客单价、黄牛识别率售罄 < 5 分钟为健康
技术峰值 QPS、P99 RT、错误率、降级触发次数、MQ 峰值堆积、Redis 热点 RTP99 < 100ms，错误率 < 0.1%
风控拦截机器请求数、验证码通过率、黑产账号处置数拦截率与误杀率同时监控
一致性超卖笔数（必须为 0）、少卖笔数、对账差异单超卖 = 事故，一票否决

十个线上坑

1
秒杀与主站共用服务和数据库
秒杀打挂库存服务/DB，主站下单一起陪葬。独立域名、独立集群、独立连接池，隔离验收标准是"秒杀全挂主站无感"。
2
直接扣 MySQL 库存
10 万人排队等一行锁，RT 飙升、连接池打满、雪崩。秒杀库存只走 Redis 预扣，MySQL 只做异步落库。
3
Redis 预扣不做对账
Redis 主从切换/AOF 丢失让库存"凭空恢复"，超卖。每日对账：Redis + 未付 + 已付 = 总库存。
4
令牌发放数大于库存承受力
发 10 万令牌但库存 100 件，预扣层照样被打满。令牌数 = 库存 × 5~10，与预扣能力匹配。
5
没有分层限流，网关直穿数据库
30 万并发直接打到服务层。每层按下游容量 70% 设阈值，超限就近拒绝，别把请求往上传。
6
秒杀地址提前暴露
脚本开抢前 1 秒开始蹲点，真实用户根本抢不到。动态 URL + 签名 + 一次性 token，地址开抢后才生成。
7
MQ 堆积导致"抢到但没订单"
预扣成功就提示用户抢到了，但 MQ 消费延迟 10 分钟，用户查不到订单疯狂投诉。提示语用"订单生成中"并给轮询，堆积超阈值时降级返回"系统繁忙"。
8
超时未付不释放库存
100 件货被 100 个不付款的"幽灵订单"锁死，活动实际少卖 80 件。延时消息 + 补偿扫描双保险回补 Redis。
9
压测影子隔离不干净

自测

六道题

1. 秒杀库存扣减的正确姿势是？
正确答案：Redis 预扣 + 异步落库 + 对账。MySQL 乐观锁在常规电商够用，但秒杀的 10 万并发会在一行锁上排队雪崩（行锁竞争上限约 3000~5000 TPS）。Redis DECR 可到 10 万+，代价是内存数据可能丢，必须对账兜底。
2. 关于削峰手段，说法错误的是？
正确答案：令牌 = 库存数是错误的。令牌应放库存的 5~10 倍：一部分持令牌用户会放弃支付/资格复审失败，留出缓冲才能把库存卖满。令牌数 = 库存数会导致大量库存卖不出去（少卖）。
3. 秒杀限流阈值应该怎么定？
正确答案：压测临界值的 70%。秒杀流量集中在秒级，扩容来不及（扩容一台机器要分钟级），必须提前按峰值备好。没有压测数据支撑的限流参数等于没有限流。
4. 用户秒杀成功但 30 分钟未支付，系统应该？
正确答案：关单 + 回补 Redis + 释放预占。不回补会导致"幽灵订单"锁死库存，活动实际少卖。延时消息 + 定时补偿扫描双保险，防止延时消息丢失造成库存泄漏。
5. 关于秒杀与主站的隔离，正确的验收标准是？
正确答案：秒杀全挂主站无感。这要求独立域名、独立服务、独立 Redis/DB/连接池。常见没做干净的暗坑：秒杀服务偷偷调用主站库存服务、共用数据库连接池。
6. 100 件库存、30 万并发，四层漏斗各层的核心职责排序正确的是？
正确答案：前端答题 → 网关限流 → 令牌 → 预扣 → 异步落库。原则是"把尽可能多的请求挡在离用户最近、成本最低的地方"：前端成本最低、DB 最贵，顺序反了就等于把最贵的资源暴露在最前面。
