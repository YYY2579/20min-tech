开始前

BI 平台架构：四段流水线

所有 BI 平台（自研或 Superset/Metabase 系）都是同一条流水线：数据源 → 建模 → 计算 → 展示。每段解决一个问题，段与段之间的契约就是平台设计的核心。

层职责关键技术
数据源接业务库、数仓、日志、API，统一元数据JDBC/连接池、数据源管理、查询下推
建模把物理表变成业务能懂的"数据集"（表关联、字段语义、指标定义）星型模型、语义层、连接管理
计算执行查询：翻译成 SQL、下推引擎、缓存、加速SQL 生成、预计算、列存、向量化执行
展示报表、仪表盘、大屏、导出、订阅图表渲染、权限过滤、定时任务
一次报表查询的完整链路（P99 要控在 3 秒内）
1. 用户打开"销售日报" → 前端请求 POST /api/query
2. API 层：鉴权 + 权限注入（行级：自动追加 WHERE region='华东'）
3. 计算层：查缓存（查询指纹一致直接返回，命中率目标 >70%）
4. 未命中 → SQL 生成：语义层把"销售额"翻译成 SUM(amount*quantity)
5. 下推执行：SQL 发给 ClickHouse/Doris（列存，亿行聚合 <1s）
6. 结果集 → 缓存（TTL 5~30 分钟，按数据更新频率）→ 返回前端
7. 前端渲染图表；明细超 1000 行走服务端分页，不全量拉

分层边界原则：
- 建模层不知道数据存在哪（MySQL/CH/Doris 对上层透明）
- 计算层不知道业务语义（只执行语义层翻译出的 SQL）
- 展示层不做任何计算（只渲染，避免同一指标前端后端口径不一致）
自研还是买？日活报表用户 < 50、数据量 < 亿级：Metabase/Superset 直接上，别自研。用户 > 500、有强定制（嵌入业务系统、复杂权限、国产化）：自研或基于开源二次开发。中间的灰色地带，先买后改，不要一上来就造轮子。
模块 1

语义层与指标一致性

BI 平台最大的价值不是画图，是让"销售额"在全公司只有一个定义。没有语义层的 BI，每个报表的 SQL 各写各的，三个月后同一个月度会有 7 个数字。

1.1 语义层的三个组成部分

概念定义示例
维度
Dimension		观察业务的角度，来自维度表日期、地区、渠道、商品类目
指标
Metric		可度量的数值，带聚合函数销售额、订单数、转化率
关系
Join		事实表与维度表的关联路径订单表.user_id → 用户表.id
# 语义层定义（YAML，指标平台的标配，与 Superset/Doris 语义层同思路）
metrics:
  - name: sales_amount            # 指标唯一标识
    label: 销售额
    description: "已支付订单的实付金额合计，不含退款单"
    type: sum                      # 聚合方式
    expr: amount                    # 底层字段（可含表达式）
    filters:                       # 指标自带过滤条件——口径的核心
      - status = 'paid'
      - refund_status != 'refunded'
    format: currency                # 展示格式

  - name: order_count
    label: 订单数
    type: count_distinct
    expr: order_id
    filters:
      - status = 'paid'

  - name: conversion_rate          # 派生指标 = 组合指标
    label: 支付转化率
    type: ratio
    numerator: order_count
    denominator: visit_count       # 引用另一个指标，不是裸写 SQL

dimensions:
  - name: region
    label: 大区
    expr: dim_user.region           # 关联维度表
  - name: pay_date
    label: 支付日期
    expr: toDate(fact_order.pay_time)  # 表达式维度

# 关键机制：口径变更 = 改一处 YAML，全平台所有引用该指标的报表同步生效
# 反例（没有语义层）：30 张报表里 30 段 SQL 各写各的 SUM(amount)，改口径要改 30 处

1.2 为什么指标平台是刚需

  • 单一事实来源：指标定义入库、可查、可 review。口径变更走审批，不是某个开发改完 SQL 偷偷上线
  • 防止"指标漂移"：新报表只能引用已注册指标，不允许裸写 SQL（或裸写 SQL 要过评审）——这是治理，不是技术
  • 口径可追溯：每个数字能点进去看定义、负责人、变更历史。会上吵架时直接看定义
  • 计算下推优化：语义层知道指标含派生关系（ratio），可以生成更优 SQL 或走预计算
指标口径打架的经典案例：运营看板的"GMV"含未支付订单，财务的"销售额"只含已支付，两个数差 30%，会上互相甩截图。根因：两个团队各自写 SQL。解法不是对齐一次数字，是建立"指标注册 + 唯一 owner + 变更评审"机制。
模块 2

报表类型与适用场景

四种报表类型对应四种用户、四种技术方案。选错类型是 BI 项目失败的第一原因——让运营用固定报表，或让高管看自助分析，都是灾难。

类型用户特征技术方案
固定报表一线运营、财务指标/维度固定，每天看同一张表预计算 + 缓存，P99 < 1s。SQL 固化，只允许筛选时间
自助分析分析师、业务负责人拖拽维度/指标，查询组合千变万化语义层 + 即席 SQL，查询队列 + 资源隔离，超时 30s
仪表盘管理层多图组合、全局筛选联动、下钻多查询并行 + 结果缓存，联动参数下推
数据大屏展厅、监控中心全屏视觉、实时刷新、地图WebSocket/SSE 推送，秒级刷新，只查聚合值

2.1 各类型的技术要点

# 固定报表（90% 的查询量在这里，必须快）
- 查询指纹 = (report_id, 筛选参数) → 缓存 key，命中直接返回
- 底层用物化视图/预计算表，报表 SQL 只查预计算表（行数少 3 个量级）
- 数据更新（T+1 或小时级）后主动失效缓存，不用等 TTL

# 自助分析（防止一个分析拖垮库）
- 每次查询必须带 LIMIT（下推）和超时（如 30s），无限制扫描直接拒绝
- 资源组隔离：分析师用 adhoc 资源组，限并发 10、限单查询 CPU/内存
- 慢查询引导：查询预估扫描行数 > 1亿 时提示"建议加筛选条件或走预计算"

# 仪表盘（10 个图 = 10 个查询，体验生死线）
- 并行发 10 个查询，不是串行（串行 P99 = 10 × 单图耗时）
- 全局筛选参数注入每个查询；图表间下钻 = 换维度重查
- 骨架屏 + 逐图加载，不要等全齐才渲染

# 数据大屏
- 轮询 5~15s 一次或 SSE 推送；只展示聚合数字，不渲染明细
- 地图数据用预聚合 GeoJSON，前端渲染不查库
- 断线重连 + 数据陈旧标识（超过 30s 没更新要显示"数据延迟"）
模块 3

查询加速：预计算 / 物化视图 / 列存

查询加速三板斧，按成本从低到高：缓存 → 预计算 → 换列存引擎。原则：能用缓存解决的不要预计算，能用预计算的不要扫原始表。

3.1 三板斧对比

手段机制适用与代价
结果缓存查询指纹 → 结果集，TTL 5~30 分钟固定报表首选。代价：内存；失效依赖数据更新通知
预计算表定时任务按维度组合预聚合，写 ADS 层表组合爆炸：维度 10 个全排列 = 1023 组合。只预 top 20 常用组合
物化视图引擎自动维护（Doris/StarRocks/CH 的 MV，或 PG 的 matview）写入时增量维护，查询自动路由。代价：写入变慢、存储翻倍
列存引擎ClickHouse / Doris / StarRocks 替换 MySQL 做分析亿行聚合亚秒级。代价：数据同步链路（CDC）、运维成本
# Doris 物化视图（查询自动命中，无需改 SQL）
CREATE MATERIALIZED VIEW mv_sales_daily
BUILD IMMEDIATE REFRESH AUTO              -- 数据变更自动增量刷新
AS SELECT
  pay_date, region, channel,                  -- 常用维度组合
  SUM(amount) AS sales_amount,           -- 预聚合指标
  COUNT(DISTINCT order_id) AS order_count
FROM fact_order
GROUP BY pay_date, region, channel;
-- 用户按"日期+大区+渠道"查销售额 → 引擎自动路由到 MV，秒回
-- 用户按"日期+商品类目"查 → MV 不覆盖，回退查原始表（慢）
-- 工程要点：上线前分析历史查询日志，MV 只覆盖高频组合，别全建

# 预计算表（MySQL 系分析库的老办法，可控性最强）
CREATE TABLE ads_sales_daily (
  stat_date  DATE NOT NULL,
  region     VARCHAR(32) NOT NULL,
  channel    VARCHAR(32) NOT NULL,
  sales      DECIMAL(18,2) NOT NULL,
  orders     BIGINT NOT NULL,
  PRIMARY KEY (stat_date, region, channel)   -- 覆盖索引，点查 O(1)
);
-- 报表 SQL：SELECT region, SUM(sales) FROM ads_sales_daily
--           WHERE stat_date BETWEEN ? AND ? GROUP BY region
-- 扫 30 行聚合 vs 扫 2 亿行聚合 —— 差 6 个数量级

3.2 加速效果算例

场景：查"近 30 天各大区每日销售额"，事实表 fact_order = 2亿行
- 直接扫原始表（ClickHouse）：1.2s（列存 + 分区裁剪，可接受但不快）
- MySQL 扫原始表：18s（必须避免）
- 预计算表（30天 × 8大区 = 240 行）：3ms（含索引点查）
- 结果缓存命中：0.5ms

成本账：
- 预计算任务：每天凌晨 30 分钟，扫全表一次聚合 → 换取白天 10万次查询每次 3ms
- 结论：查询:计算 = 10000:1 以上时，预计算永远划算
- 存储账：2亿行 × 200B = 40GB 事实表 → MV 240 行 × 100B ≈ 24KB（忽略不计）
模块 4

权限：行列级数据权限

BI 权限分两层：功能权限（能不能看这张报表）和数据权限（能看哪些行、哪些列）。数据权限做漏了，就是一次数据泄露事故。

4.1 三级数据权限

级别控制实现
列级权限
CLS		手机号、金额字段对某些角色不可见语义层字段加权限标签，查询生成时对无权限字段直接报错或返回脱敏值（138****5678）
行级权限
RLS		华东区经理只能看华东的数据查询时自动向 SQL 注入 WHERE 条件（用户改不了、绕不过）
行列组合既能看到部分行、又对某列脱敏两层规则叠加生效
# 行级权限的注入（必须在服务端 SQL 生成层，绝不能前端传参）
-- 权限规则表：rule(user_role, table, column, operator, value)
-- (manager_east, fact_order, region, =, '华东')

# SQL 生成器拿到语义层 AST 后：
# 1. 用户请求 = "按大区销售额"（没带任何地区筛选）
# 2. 权限引擎查出该用户的 RLS 规则 → region = '华东'
# 3. 生成的 SQL（注意 AND 的位置，必须包住整个用户条件，防 OR 注入）
SELECT region, SUM(amount) FROM fact_order
WHERE pay_date >= '2026-09-18'
  AND region = '华东'              -- 权限注入，用户无感知
GROUP BY region;

# 渗透测试必测的三种绕过：
# 1. 用户传 region='华北' 筛选 → 注入条件 AND region='华东' 后结果为空（正确，拦住了）
# 2. 用户传 region IN ('华东','华北') → 必须 AND (region='华东')，不能被 IN 展开绕过
# 3. 用户直接请求明细下载接口 → 下载也要过同一个 SQL 生成器，不能另走一条 SQL

# 列级脱敏（phone 字段）
def mask(value, field_perm):
    if field_perm == MASK: return value[:3] + '****' + value[-4:]
    if field_perm == HIDE: return None        # 字段不出现在结果集
    return value                              # 明文（仅高敏角色）
权限穿透的三个真实入口：① 导出/订阅接口不过权限层——报表页挡住了，点"导出 Excel"全量数据出去；② 下钻接口单独拼 SQL，忘了注入 RLS；③ 明细行点击按 ID 查单条记录（GET /detail?id=123），没校验该行是否属于用户的可见范围。铁律：所有出数据的接口必须走同一个 SQL 生成器，权限注入在这一层统一完成。
模块 5

大数据量下的性能：下推、分页、抽样

亿行表的即席查询，靠三个手段把 P99 压在 3 秒内：计算下推（让引擎干粗活）、服务端分页（别把 100 万行拉前端）、抽样加速（看趋势不需要精确值）。

5.1 计算下推

# 下推 = 把过滤/聚合/排序推到数据源执行，只传结果集回 BI 层
# 反例（拉回内存再算）：SELECT * FROM fact_order → 2亿行传到应用层 → OOM + 网络爆炸
# 正例（下推）：
SELECT pay_date, SUM(amount) FROM fact_order      -- 聚合下推
WHERE pay_date >= '2026-09-01'                -- 过滤下推（分区裁剪）
GROUP BY pay_date ORDER BY pay_date;          -- 排序下推
# 返回 30 行。数据源只回 30 行，网络传输 < 1KB

# ClickHouse 的进一步下推（索引 + 分区 + 列裁剪）
# - 分区裁剪：PARTITION BY toYYYYMM(pay_time)，WHERE 带月份直接跳过分区
# - 列裁剪：只 SELECT 用到的列，列存下 IO 减少 10 倍
# - 跳数索引：WHERE amount > 1000 走 minmax 索引，跳过 90% 数据块

5.2 明细分页

# 明细报表（如订单明细 500 万行）的正确分页姿势
# 1. 服务端分页：每页 100 行，SQL 带 LIMIT，前端只渲染当前页
-- SELECT * FROM fact_order WHERE ... ORDER BY id DESC LIMIT 100 OFFSET 0;
-- 深分页用游标替代 offset：WHERE id < {last_id} ORDER BY id DESC LIMIT 100

# 2. 异步导出：用户点"导出" → 生成任务 ID 立即返回 → 后台流式写 CSV
#    （MySQL 用流式游标/CH 用 INTO OUTFILE）→ 完成通知下载链接（有效期 24h）
#    500 万行 CSV ≈ 300MB，同步导不出（超时 + 内存）

# 3. 抽样（趋势类图表的加速器）
-- 查"近 90 天订单量趋势"，不需要逐日精确：
SELECT toStartOfWeek(pay_time) AS wk, COUNT(*) FROM fact_order
WHERE pay_time >= now() - INTERVAL 90 DAY GROUP BY wk;   -- 周聚合，13 个点
# 或 SAMPLE 0.1（CH 抽样查询，误差 <1%，速度 ×10，适合超长周期趋势）

5.3 查询治理

治理项规则
强制 LIMIT任何明细查询默认 LIMIT 10000，超过需申请；聚合查询不设上限
超时熔断单查询 30s 超时；连续 3 次超时自动禁用该报表并通知 owner
资源隔离固定报表走 batch 资源组（保吞吐），自助分析走 adhoc 组（限并发），互不挤占
慢查询日志记录 Top 50 慢查询（SQL + 耗时 + 用户），每周 review，该优化的优化、该加 MV 的加 MV
夜间窗口大查询（全量回溯、模型训练取数）只允许 0:00-6:00 执行，白天排队拒绝
模块 6

与数仓的分层配合

BI 平台是数仓的"最后一公里"。BI 查询哪一层，决定了快慢和数据质量。经典四层（阿里系 OneData 体系）：

层内容BI 怎么用
ODS贴源层：业务库原样同步，未加工BI 不要查。脏数据、无模型、量最大
DWD明细层：清洗、标准化、维度退化的事实宽表仅明细报表、下钻场景查。行数亿级，慢
DWS汇总层：按主题轻度聚合（用户日汇总、商品日汇总）自助分析主查这层。千万级，秒级
ADS应用层：面向具体报表预聚合，百/千行级固定报表、仪表盘只查这层，毫秒级
# 星型模型示例（DWS 层的"销售主题"）
# 事实表（亿级）：fact_order
#   order_id, user_id, product_id, shop_id, pay_time, amount, quantity, channel, status

# 维度表（万/百万级）：
CREATE TABLE dim_user (
  user_id     BIGINT PRIMARY KEY,
  region      VARCHAR(32),      -- 大区
  city        VARCHAR(32),
  register_dt DATE,             -- 注册日期（新老客判定）
  level       TINYINT           -- 会员等级
);
CREATE TABLE dim_product (
  product_id  BIGINT PRIMARY KEY,
  category_l1 VARCHAR(32),      -- 一级类目
  category_l2 VARCHAR(32),
  brand       VARCHAR(64),
  price_band  VARCHAR(16)       -- 价格带（分析常用，提前分好）
);

# 典型分析 SQL（查各大区各价格带的销售额，DWS + 维度退化）
SELECT u.region, p.price_band, SUM(f.amount) AS sales
FROM fact_order f
JOIN dim_user u    ON f.user_id = u.user_id
JOIN dim_product p ON f.product_id = p.product_id
WHERE f.pay_time >= '2026-09-01' AND f.status = 'paid'
GROUP BY u.region, p.price_band;
# 关键：region/price_band 是"维度退化"——常用维度直接冗余进事实表，
#       免 join 也能按大区聚合。join 在大表上永远是性能灾难
BI 与数仓的契约：① 报表需求先问"ADS 层有没有"，有则毫秒级上线，没有则走排期（加 ADS 表 = 开发 + 调度，按天计）；② DWD 只给明细和下钻用，且必须带分区和分区裁剪；③ 数仓的调度延迟（T+1 还是小时级）决定了报表能承诺的时效——向业务承诺"实时"前先看数仓链路，这是 BI 项目经理的保命常识。
模块 7

导出与订阅

导出和订阅是 BI 的"隐形杀手"：一个用户点一次全量导出，等于跑一次全表扫描。设计不好，一个人的操作能拖垮整个数仓。

7.1 异步导出

提交即返回：点"导出" → 生成导出任务（task_id）→ 立即返回"导出中，完成后通知"。前端轮询或 WebSocket 等结果，绝不能同步等
后台流式生成：任务队列消费 → 走同一个 SQL 生成器（过权限！）→ 流式写 CSV/XLSX（边查边写，不落全量内存）→ 上传对象存储
限流与配额：单用户同时最多 3 个导出任务；单次导出上限 100 万行 / 500MB；全平台并发导出 worker 数固定（如 8），超出排队
安全下发：下载链接带过期签名（24 小时有效），不暴露永久 URL；导出操作落审计日志（谁、什么时间、导了什么范围）

7.2 订阅推送

# 订阅 = 定时执行报表 + 结果推送（邮件/IM/Webhook）
# 订阅表：sub(id, report_id, user_id, cron_expr, channel, filter_json, status)
# cron_expr = "0 9 * * 1" → 每周一 9 点

# 执行链路：
# 1. 调度器（每分钟扫一遍）到点的订阅任务 → 推送到执行队列
# 2. 执行器：按订阅时保存的筛选参数跑查询（带权限注入，按订阅人身份）
# 3. 渲染：图表渲染成图片/PDF + 核心数字摘要（邮件正文直接看数）
# 4. 推送：邮件附件 / IM 卡片 / Webhook（企业微信、钉钉、飞书机器人）

# 关键设计：
# - 同一报表 100 人订阅 → 只跑 1 次查询，渲染 100 份推送（查询合并，省 99% 算力）
# - 失败重试 3 次，仍失败通知 owner；订阅人离职/无权限自动跳过并告警
# - 推送内容带"数据截止时间"（如 数据截至 2026-10-17 08:00），防误解
# - 邮件里禁止放全量明细（附件限 1 万行），要明细走异步导出
订阅的幂等与轰炸防护：调度系统重投会导致同一封邮件发 3 遍（任务按 sub_id + 执行日期做唯一键去重）；有人订阅了"每分钟刷新"的报表并开邮件推送，一早上 60 封——推送频率限制：邮件最少每天 1 次，IM 最少每 30 分钟 1 次，超频需求走大屏/监控。
模块 8

十个线上坑

1
没有语义层，各报表 SQL 各写各的，同一指标 7 个数字
会上互相甩截图，业务对 BI 失去信任。指标必须统一定义（YAML/指标平台），变更走评审，新报表只准引用注册指标。
2
报表直接查 ODS 贴源层
脏数据无清洗、无分区、量最大，一个报表扫 2 亿行 18 秒。报表只查 ADS/DWS，ODS 是数仓的原料不是 BI 的餐桌。
3
导出接口不过权限层，绕过 RLS 全量出数
报表页挡住了数据，点导出拿到全公司明细——数据泄露事故。所有出数接口必须走同一个 SQL 生成器，权限在这一层统一注入。
4
明细查询无 LIMIT，一次拉 100 万行到前端
浏览器内存爆炸、接口超时、数据库缓冲池被打满。明细强制服务端分页 + LIMIT 上限，深分页用游标。
5
自助分析无资源隔离，一个分析师拖垮全平台
一条 30s 的全表扫描占满连接池，所有报表一起超时。分析师走独立资源组限并发，慢查询熔断禁用。
6
仪表盘 10 个图串行发查询，P99 十几秒
用户体验生死线。多查询必须并行，配骨架屏逐图加载，全局筛选参数一次注入所有子查询。
7
缓存不失效，业务看了 3 小时前的数据
数据更新（T+1 完成）后缓存还在，运营按旧数做决策。缓存 TTL 只是一层兜底，数据管线完成事件要主动失效缓存。
8
导出同步生成，大报表直接超时 + OOM
500 万行同步导出必挂。必须异步化：任务队列 + 流式写文件 + 对象存储 + 完成通知。
9
物化视图全维度组合都建，写入性能崩了
10 个维度全排列 = 1023 个 MV，写入放大 1000 倍。只建历史查询日志里的 top 20 高频组合，其余回退原表。
10
订阅推送不过滤离职账号，邮件继续发
离职员工持续收到经营数据——既泄露又尴尬。订阅按身份鉴权，账号失效/无权限自动跳过并通知 owner。
自测

六道题

1. 为什么 BI 平台必须有语义层（指标定义）？
正确答案：统一指标口径。没有语义层时每个报表各自写 SQL，"销售额"能出现 7 个版本。语义层把指标定义（聚合方式+过滤条件+格式）集中管理，口径变更改一处全平台生效，且每个数字可追溯定义和 owner。
2. 华东区经理打开"全国销售报表"（他没带任何地区筛选），系统返回的数据应该是？
正确答案：自动注入 RLS 条件。行级权限必须在服务端 SQL 生成层统一注入，用户无感知也绕不过（包括导出、下钻、明细等所有出数接口）。返回空数据是过度拦截，返回全量就是权限穿透事故。
3. 查询"近 30 天各大区每日销售额"（事实表 2 亿行），最快的方案是？
正确答案：预计算/物化视图。固定报表的组合是已知的，预聚合后行数少 6 个数量级，查询从秒级降到毫秒级。扫描原始表只适合即席分析（组合不可预知）；拉内存算是最差方案，直接 OOM。
4. 用户要求导出一张 500 万行的明细报表，正确的做法是？
正确答案：异步导出。500 万行同步导出必超时/ OOM。异步化 = 任务队列 + 流式写入 + 对象存储 + 签名 URL。同时必须限流（并发数、行数上限）和过权限（导出不能绕过 RLS）。
5. BI 报表查询数仓时，固定报表和自助分析分别应该主要查哪一层？
正确答案：ADS + DWS。ADS 是面向具体报表预聚合的百/千行级表，固定报表组合已知，毫秒返回；DWS 是主题汇总的千万级，支撑即席组合。ODS 是原料层不能直接查，DWD 亿级明细只给下钻场景。
6. 仪表盘有 10 个图表，每个查询 800ms，怎么做能让首屏最快？
正确答案：并行 + 逐图渲染。串行 P99 = 10×800ms = 8s，用户必流失。并行后总耗时 ≈ 单查询最慢者。合并成一条 SQL 通常不可行（不同图表维度/粒度不同），且一条慢查询会阻塞整页。

术语一句话解释
语义层指标/维度的统一定义层，让"销售额"全平台只有一个口径
指标 Metric带聚合函数的可度量值（SUM/COUNT DISTINCT），可带过滤条件
维度 Dimension观察业务的角度（日期/地区/渠道），来自维度表
派生指标由其他指标组合而成（转化率 = 订单数/访客数），不裸写 SQL
星型模型中心事实表 + 周围维度表，BI 建模的标准形态
维度退化常用维度冗余进事实表，免 join 聚合，大表性能关键
ODS / DWD / DWS / ADS数仓四层：贴源 → 明细 → 汇总 → 应用，BI 主要查后两层
列存引擎ClickHouse/Doris/StarRocks，列式存储，亿行聚合亚秒级
物化视图预计算的物理结果，写入时维护，查询自动命中
预计算表定时任务按维度组合预聚合的 ADS 表，只建高频组合
查询下推过滤/聚合/排序推到数据源执行，只回传结果集
分区裁剪查询带分区字段条件，引擎跳过无关分区，IO 降一个量级
行级权限 RLS按用户注入 WHERE 条件，控制能看到哪些行
列级权限 CLS控制字段可见性：隐藏或脱敏（138****5678）
自助分析即席拖拽查询，组合不可预知，查 DWS 层 + 资源隔离
异步导出任务化导出：流式生成 + 对象存储 + 签名 URL，限流限行数
订阅推送定时执行报表推送到邮件/IM/Webhook，同报表多人订阅合并执行
资源组隔离固定报表与分析查询走不同资源组，互不挤占
慢查询治理Top 慢查询日志 + 超时熔断 + 夜间窗口，平台稳定的三件套
