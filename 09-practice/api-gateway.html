开始前

网关定位：流量入口与横切关注点

一句话定义：API 网关是所有外部流量的单一入口，把跨业务的通用能力（认证、限流、熔断、日志、灰度）从每个服务里抽出来集中实现。

能力没有网关时有网关时
认证鉴权每个服务各写一遍，漏一个就是一个洞网关统一验签，服务只认网关注入的身份头
限流各服务限流策略割裂，总量不可控入口级总量控制 + 服务级细分配额
灰度发布每个服务自己实现分流逻辑网关按流量百分比/头/用户标签路由
监控日志日志格式五花八门，无法关联统一 access log + trace_id 注入
安全防护WAF、防重放、黑白名单各搞各的入口统一防护，攻击在门外被拦
网关不是万能的，别把业务逻辑搬进网关。判断标准：这个逻辑是"每个服务都需要的通用能力"还是"某个服务特有的规则"？前者进网关，后者留在服务里。把业务判断（比如"这个用户能不能买"）塞进网关插件，会让网关变成第二个单体，且插件版本和服务版本互相耦合。

请求经过网关的完整生命周期

┌──────────────────────────────────────────────────────────────┐
│ 接入层：TLS 终止 → 连接管理 → 基础访问日志                      │
├──────────────────────────────────────────────────────────────┤
│ 前置插件链（顺序执行）：                                       │
│   ① IP 黑白名单 / WAF  ② 防重放(nonce+ts)  ③ 限流            │
│   ④ 认证验签  ⑤ 灰度标签解析  ⑥ trace_id 注入                │
├──────────────────────────────────────────────────────────────┤
│ 路由匹配：host + path + header → 选择 upstream + 权重          │
├──────────────────────────────────────────────────────────────┤
│ 转发：负载均衡（round-robin/least-conn/一致性哈希）            │
├──────────────────────────────────────────────────────────────┤
│ 后置插件链：响应改写 → 响应日志 → 指标上报                     │
└──────────────────────────────────────────────────────────────┘
插件顺序是安全设计的一部分：防重放必须在认证之前（避免未验签的请求消耗验签资源），限流在认证之前（防止恶意流量打爆验签服务），trace_id 注入要在最前面（保证全链路日志能串起来）。顺序写错，不是效果差，是防护被绕过。
模块 2

技术选型：Nginx+Kong/APISIX/自研

方案优势劣势适用
Nginx + Lua（OpenResty）性能极致、生态成熟、可控性强动态能力靠自己写，无管理面流量极大、定制深的大厂
Kong插件生态全（100+）、管理 UI、多协议PostgreSQL/Cassandra 依赖，重需要快速拼装能力的中型团队
Apache APISIXetcd 配置中心、性能高、插件热更新、国产活跃etcd 运维门槛，生态较 Kong 小云原生、要热更新和高性能
自研网关完全可控、深度定制周期长、坑全自己踩、要专职团队有特殊协议/合规要求的大厂

选型决策树

团队 < 5 人且求快：选 Kong/APISIX，别自研。自研网关的最小成本是 2 个资深工程师 + 1 年，还不含插件生态
流量峰值 > 50 万 QPS 或延迟要求 < 1ms：选 OpenResty 自建或 APISIX，Kong 的数据面延迟在这个量级会成为瓶颈
已有 K8s 体系：选 APISIX Ingress 或 Kong Ingress Controller，网关即 K8s 资源，GitOps 管理
需要 gRPC/Dubbo 多协议：APISIX 支持较好；纯 HTTP/JSON 三者都行
一个务实建议：先跑标准品，把"自研网关"留作最后选项。大多数团队高估了自己需求的独特性。Kong/APISIX 的插件机制能覆盖 90% 场景，剩下 10% 用插件/外部服务补。自研网关的真正门槛不是性能，是长期维护：安全漏洞响应、配置管理面、多活容灾、可观测性——每一项都是持续投入。
模块 3

动态配置与热更新

网关的配置（路由、插件、上游）变更必须不重启、不丢连接、秒级生效。这是网关区别于普通反向代理的核心能力。

三种配置同步机制对比

机制生效延迟一致性适用
轮询（pull）秒级（间隔可调）最终一致Kong DB 模式，简单可靠
长轮询/推送亚秒级近实时配置中心（Nacos/Apollo）
Watch（etcd）毫秒级强一致（raft）APISIX，节点订阅 etcd key
# 配置变更的标准链路（APISIX/etcd 模式）
运维/CI 写入 etcd ──► 所有网关节点 watch 到变更 ──► 本地重建路由表
                                          │
                                          ▼
                            新连接用新配置，存量连接不中断

# 灰度发布配置：先发 1 台节点 → 观察 → 全量
# 配置校验：CI 侧做 schema 校验，防止错误配置打到生产

热更新的三个工程细节

  • 配置版本化：每次变更生成版本号，出问题秒级回滚（而不是"再改一次改回去"）
  • 变更审计：谁、什么时候、改哪条路由/插件、前后 diff 是什么，全部落日志
  • 本地缓存兜底：etcd/配置中心短暂不可用时，网关用本地最后一份有效配置继续服务，不能因为配置中心挂了而拒绝流量
配置不同步是网关事故的头号来源：A 节点用的是新路由，B 节点还是旧路由，同一请求两次打到不同上游；或者插件在部分节点生效部分不生效，限流时有时无。对策：配置变更后必须有"全节点生效确认"机制（各节点上报配置版本，控制面确认一致才算变更完成），以及变更后的自动校验（探活 + 抽样请求比对）。
模块 4

插件机制

插件是网关能力的扩展单元。设计良好的插件机制 = 标准化生命周期 + 明确执行阶段 + 可独立灰度。

插件执行阶段

阶段能做什么示例插件
access（前置）改请求、拒绝请求、注入头认证、限流、WAF、防重放、灰度标签
header_filter / body_filter（后置）改响应头、改响应体响应脱敏、CORS、安全响应头
log（日志阶段）上报指标、发日志、异步通知access log、指标上报、审计

插件配置示例（Kong 风格声明式配置）

# 给某路由启用限流 + 认证 + 熔断三个插件
curl -X POST http://kong:8001/routes/order-api/plugins \
  -d "name=rate-limiting" \
  -d "config.minute=1000" \            # 每分钟 1000 次
  -d "config.policy=redis" \           # 集群级计数，不用 local
  -d "config.limit_by=consumer"        # 按调用方限，不是按 IP

curl -X POST http://kong:8001/routes/order-api/plugins \
  -d "name=jwt"                       # 验签后注入 X-Consumer-Username

curl -X POST http://kong:8001/routes/order-api/plugins \
  -d "name=circuit-breaker" \
  -d "config.failure_threshold=0.5" \ # 错误率 50% 触发熔断
  -d "config.window_seconds=30" \
  -d "config.recovery_seconds=10"      # 熔断 10s 后半开试探

插件治理纪律

  • 插件要有 owner 和 SLA：每个插件属于一个团队，故障时找得到人
  • 插件可独立灰度：按路由/按流量百分比启用新插件，出问题一键摘除
  • 插件超时预算：单个插件 P99 执行时间纳入网关总延迟预算（如总预算 10ms，插件占 5ms）
  • 禁止同步重逻辑：插件里不做慢查询、不发同步 HTTP（异步化或旁路化）
插件拖慢网关的典型原因：① 插件里同步调用外部服务（如每次请求查一次权限中心），把网关延迟从 1ms 拖到 50ms；② 插件用全局锁做计数，并发下互斥排队；③ 插件日志同步写盘/发 Kafka，IO 抖动直接卡请求。解法：本地缓存 + 异步化 + 降级开关，插件逻辑默认走"快路径"，异常走旁路不影响主流程。
模块 5

性能：连接复用、异步、零拷贝

手段做法收益量级
连接复用网关到上游用长连接池（keepalive），避免每请求新建 TCP + TLS延迟降 30%~60%，上游端口不耗尽
HTTP/2 多路复用客户端侧支持 h2，单连接多请求，减少握手移动端弱网收益明显
异步非阻塞 IOepoll/kqueue 事件驱动，单机十万级并发连接C10K 问题的基础解
零拷贝/内核旁路sendfile、DPDK/DPK 类方案（极端场景）大 body 转发场景收益大
CPU 亲和 + 多 workerworker 绑定 CPU 核，减少上下文切换吞吐提升 10%~30%
# Nginx  upstream 连接池配置（关键参数）
upstream order_svc {
  server 10.0.1.10:8080 max_fails=3 fail_timeout=10s;
  server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
  keepalive 64;                    # 每个 worker 保持 64 条空闲长连接
  keepalive_timeout 60s;
  keepalive_requests 1000;          # 单连接最多处理 1000 请求后重建
}
location /order/ {
  proxy_pass http://order_svc;
  proxy_http_version 1.1;
  proxy_set_header Connection "";   # 关键：清掉客户端的 Connection 头，否则 keepalive 失效
  proxy_next_upstream error timeout http_502;
}

延迟预算分配（总 P99 < 50ms 的分解）

环节预算
TLS + 接入层5ms
前置插件链（认证/限流）8ms
路由 + 转发（含连接池命中）10ms
上游服务处理25ms（服务自己的预算）
响应回程 + 后置插件2ms
网关性能的第一定律：能不经过网关就不经过。内部服务间调用走 Service Mesh 或直连，网关只承接南北向流量（外部进内部）。把东西向流量也塞进网关，会让网关成为全公司流量的单瓶颈，扩容成本和故障半径都失控。
模块 6

与 Service Mesh 的分工

Service Mesh（Istio/Linkerd）火了之后，经常有人问"网关是不是可以取消了"。答案是分工不同，不是替代关系。

维度API 网关Service Mesh
流量方向南北向（外部 → 内部）东西向（服务 ↔ 服务）
部署位置集群边缘，独立部署每个 Pod 一个 sidecar，随业务部署
核心能力认证、限流、灰度、协议转换、WAFmTLS、流量治理、重试、可观测
配置视角运维/SRE 视角，面向入口开发视角，面向服务间调用
延迟代价一跳，可控每跳两次 sidecar，累积延迟
# 典型拓扑：外部流量走网关，内部流量走 Mesh，网关即 Mesh 的 ingress
手机 App ──► API 网关集群 ──(mTLS)──► Istio Ingress Gateway
                                          │
                    ┌─────────────────────┼─────────────────────┐
                    ▼                     ▼                     ▼
               Service A              Service B              Service C
              (sidecar)               (sidecar)              (sidecar)
                    │ 东西向调用全走 sidecar，mTLS + 重试 + 遥测
分工口诀：网关管"进门"，Mesh 管"串门"。认证、限流、防攻击这些"入口治理"归网关；mTLS、重试、熔断、链路追踪这些"服务间治理"归 Mesh。两者重叠的部分（如熔断）以 Mesh 为主、网关兜底——网关的熔断保护的是"上游整体故障时快速失败"，Mesh 的熔断精细到单个上游实例。

# 网关层容灾三板斧
1. 入口层：DNS 多线路 + GSLB 健康检查，机房级故障秒级切流
2. 网关层：每机房独立网关集群（不跨机房依赖），配置中心多地域部署
3. 兜底层：静态降级页/CDN 缓存 —— 网关全挂时至少返回静态内容，不能白屏

可观测性三件套

维度指标告警示例
MetricsQPS、P50/P99 延迟、错误率、上游健康度、连接池使用率错误率 > 1% 持续 2 分钟 → P1

网关是排障的第一现场，日志必须能回答三个问题：这个请求走了哪条路由、命中了哪些插件、上游是谁、各段耗时多少。没有插件级耗时的 access log，等于把"网关自身慢"和"上游慢"混为一谈，排障时全靠猜。结构化日志（JSON）落地，字段：ts/trace_id/route/upstream/status/durations{access,plugins,upstream,total}。
模块 8

核心配置示例与十个坑

APISIX 声明式配置（真实可用）

# 1. 上游：连接池 + 健康检查
upstreams:
  - id: order-svc
    type: roundrobin
    nodes:
      "10.0.1.10:8080": 1
      "10.0.1.11:8080": 1
    scheme: http
    keepalive_pool:
      size: 64              # 连接池大小
      idle_timeout: 60s
    checks:                 # 主动健康检查
      active:
        type: http
        http_path: /health
        healthy: {successes: 2}
        unhealthy: {timeouts: 3}

# 2. 路由：前缀匹配 + 插件链（顺序即执行序）
routes:
  - id: order-api
    uri: /api/order/*
    upstream_id: order-svc
    plugins:
      trace-id: {}                        # 先生成 trace_id
      ip-restriction:                     # 黑白名单
        blacklist: ["10.66.0.0/16"]
      limit-req:                          # 限流：漏桶
        rate: 2000
        burst: 500
        rejected_code: 429
      jwt-auth:                           # 认证
        key: order-api-key
      prometheus: {}                      # 指标暴露

# 3. 灰度路由：按 header 分流 10% 到金丝雀上游
  - id: order-api-canary
    uri: /api/order/*
    upstream_id: order-svc-canary
    vars: [["http_x_canary", "==", "true"]]
    plugins:
      traffic-split:                      # APISIX 流量分割插件
        rules:
          - match: [["arg_version", "==", "v2"]]
            weighted_upstreams:
              canary: 10                  # 10% 流量
              stable: 90

Nginx 侧限流配置（兜底用）

# 按 IP 限流（Nginx 层最后一道闸，防网关集群被打穿）
limit_req_zone $binary_remote_addr zone=per_ip:10m rate=100r/s;
limit_conn_zone $binary_remote_addr zone=per_ip_conn:10m;

server {
  location /api/ {
    limit_req zone=per_ip burst=200 nodelay;   # 超了直接 429，不排队
    limit_conn per_ip_conn 50;                 # 单 IP 最多 50 并发
    limit_req_status 429;
    proxy_pass http://gateway_upstream;
  }
}

十个线上坑

1
网关单点：一个集群挂了全站不可用
网关是南北向总入口，天然单点风险。必须多机房部署 + DNS 健康检查切流 + 网关自身无状态（配置外置）。任何"网关集群只有一个"的设计都是在赌运气。
2
配置不同步：部分节点旧路由部分新路由
同一请求两次落到不同上游，限流时有时无。配置变更要有"全节点版本确认"机制，变更后自动探活校验；本地缓存兜底防止配置中心故障时拒绝服务。
3
插件里同步调外部服务，拖垮网关
每请求同步查一次权限中心，网关 P99 从 1ms 变 50ms，吞吐暴跌。插件逻辑必须本地缓存 + 异步化，慢路径旁路，默认走快路径。
4
限流只按 IP，NAT 下误杀一片用户
公司出口共享 IP，一个用户超限全体 429。限流维度要组合：IP + 用户 ID + 接口，优先按认证后的用户/API Key 限，IP 限流只做异常兜底。
5
限流用本地计数，多网关节点各自为政
每节点限 1000 QPS，10 个节点实际放进 1 万 QPS，上游照样挂。集群级限流必须用 Redis 等集中计数（允许极端情况下本地降级兜底）。
6
到上游没开连接复用，端口耗尽
每请求新建 TCP，上游 time_wait 打满，新连接被拒。upstream keepalive + proxy_set_header Connection ""（Nginx）或 keepalive_pool（APISIX），这一对参数漏一个，长连接就失效。
7
认证头被伪造成 X-User-Id 直穿服务
服务信任网关注入的身份头，但没校验"这个头只能来自网关"，内网直接伪造头调用服务越权。服务层要校验调用来源（mTLS/内部令牌），或只在 mesh 内可信。
8
灰度按流量百分比，用户跳变体验割裂
同一用户两次请求一个进新版一个进旧版，状态错乱。灰度要按用户维度粘性（hash user_id 分流），而不是纯随机比例。
9
access log 没有插件耗时，排障靠猜
"网关慢还是上游慢"分不清。结构化日志必须含分段耗时：接入/插件链/上游/回程，trace_id 串联全链路。
10
东西向流量全过网关，网关成全公司瓶颈
内部服务间调用也走网关，QPS 全集中到入口，扩容成本高、故障半径大。网关只管南北向，东西向走 Service Mesh 或服务直连。
自测

六道题

1. 网关插件链"防重放、认证、限流"的正确执行顺序是？
正确答案：防重放 → 限流 → 认证。逻辑：先用最便宜的检查（nonce/时间戳）挡掉明显非法的重复请求，再限流保护后续资源，最后才做最贵的验签。反过来会让恶意流量消耗验签算力，也能绕过限流打爆认证服务。
2. 多网关节点集群级限流（总配额 1 万 QPS），正确做法是？
正确答案：Redis 集中计数。本地计数下流量在各节点分布不均时，实际放行量会远超或远低于总配额（均匀分布是巧合不是常态）。集中计数保证全局准确，Redis 故障时降级为本地限流保命。
3. 关于 API 网关与 Service Mesh 的关系，正确的是？
正确答案：分工互补。网关负责入口治理（认证、限流、灰度、WAF），Mesh 负责服务间治理（mTLS、重试、细粒度熔断、东西向可观测）。Mesh 的 sidecar 在集群边缘，替代不了网关的入口策略与协议转换能力。
4. 网关到上游的请求延迟突然劣化，最不可能的原因是？
正确答案：路由表匹配复杂度。路由表通常几百条，前缀/哈希匹配是微秒级，且索引常驻内存。真实瓶颈几乎总是连接复用失效、上游变慢、或插件同步调用——优先查连接池配置和上游健康度。
5. 服务端收到了 X-User-Id: 10086 的请求头，正确的信任策略是？
正确答案：校验来源后才信。"网关注入的头"只有在"请求确实来自网关"时才可信。内网任何机器都能伪造这个头直连服务，必须配合 mTLS 或内部服务令牌做来源校验，形成第二道防线。
6. 网关配置热更新的核心要求是？
正确答案：热更新 + 本地兜底。重启意味着连接中断和可用性损失，凌晨窗口则意味着故障响应延迟。同时配置中心/etcd 故障时网关必须能用本地最后有效配置继续服务，不能因配置链路故障而拒绝流量。
