二十分钟学透 权限系统设计实战

权限系统的难点不是"能不能鉴权"，而是模型扛不扛得住业务演进、缓存一致性怎么兜、越权怎么防。这篇讲机制：从 SSO 落地到 RBAC→数据范围→ABAC 的演进路线，以及越权、循环继承、缓存不一致三个经典死法。

开始前

认证与授权：两个经常被混淆的词

概念英文回答的问题典型载体
认证Authentication你是谁？账号密码、短信验证码、证书、Token
授权Authorization你能干什么？角色、权限点、数据范围、策略

登录 ≠ 有权限。认证通过只证明"你是张三"，每次业务请求还要回答"张三能不能看这份订单"——后者是授权，发生在每一个 API 调用上，频率比认证高几个数量级。工程上的直接后果：认证可以慢一点（登录一次），授权必须快（每个请求都查）。

权限系统的三道防线：① 网关层粗粒度拦截（有没有登录、有没有这个菜单/接口的权限点）；② 服务层细粒度鉴权（这个订单是不是你的、这个金额超没超你的审批上限）；③ 数据层兜底（行级权限 SQL 改写、敏感字段脱敏）。只做①的系统，水平越权一抓一个准。
模块 1

认证中心设计：统一登录、SSO、OAuth2/OIDC 落地

认证中心（Auth Server）的职责：管凭证、发令牌、单点登录、联邦登录。内部系统三种落地形态，按演进顺序讲。

形态一：统一登录 + SSO（Cookie/Session 时代）

# 经典 SSO 流程（CAS 式 Ticket 模式）
用户访问 A 站 → A 站发现没登录 → 302 到认证中心
认证中心发现也没登录 → 展示登录页 → 用户输账号密码
认证中心签发全局 Ticket，302 回 A 站（带 ticket）
A 站用 ticket 后台换用户信息 → 建立本地 Session
用户访问 B 站 → B 站发现没登录 → 302 到认证中心
认证中心发现已登录 → 直接发新 ticket，302 回 B 站 → 无感登录（SSO）

形态二：OAuth2 + OIDC（Token 时代，当前主流）

角色在权限系统中的实体
Resource Owner终端用户（张三）
Client接入方：H5、App、第三方系统
Authorization Server认证中心本身
Resource Server各业务服务（订单、支付……）

OIDC 是 OAuth2 的认证扩展：OAuth2 只解决"委托授权"（让 A 代表你访问 B），OIDC 在其上加了 id_token（JWT，携带用户身份声明），才真正解决"你是谁"。内部系统对接时：授权码模式拿 access_token，同时拿 id_token 建本地会话。

# 授权码模式核心请求（内部系统最常用的模式）
# 1. 前端跳转，用户同意授权
GET /oauth2/authorize?response_type=code&client_id=web-portal&redirect_uri=https://portal/cb&scope=openid+profile&state=xyz

# 2. 后端用 code 换 token（code 一次性，10 分钟过期）
POST /oauth2/token
  grant_type=authorization_code&code=xxx&client_id=web-portal&client_secret=***

# 3. 返回
{
  "access_token": "eyJhbGciOiJSUzI1NiIs...",   # 访问令牌，JWT，短有效期(如2h)
  "refresh_token": "rt_8f3a...",                 # 刷新令牌，长有效期(如30d)，可轮换
  "id_token": "eyJ...",                          # OIDC 身份令牌，含 sub/name/email
  "expires_in": 7200
}

Token 选型：JWT vs 不透明 Token

方案优点缺点适用
JWT（自包含）资源服务本地验签，不查认证中心，无单点签发后无法主动失效（注销/改权限要等过期），payload 不能放敏感信息短时效 access_token + 网关统一验签
不透明 Token（引用式）服务端可随时作废、可查会话每次校验都要查 Redis/DB，有单点和延迟内部管理端、对撤销敏感的场景
JWT 失效问题是真实存在的坑：用户被开除、密码改了、权限降级了，已签发的 JWT 在过期前照样好用。缓解手段：access_token 有效期设短（15min~2h）+ refresh_token 可撤销（存 Redis 黑名单）+ 关键操作二次校验。别把用户角色全塞进 JWT 然后指望改角色立即生效。
模块 2

用户体系：账号、组织、角色

用户体系是权限的"主语"。三层结构：账号（谁）→ 组织（属于哪）→ 角色（能干什么）。

账号设计要点

维度设计决策
登录标识支持多标识：手机号 / 邮箱 / 工号 / 用户名，各建唯一索引，登录时按格式分发
凭证密码必须加盐哈希（bcrypt/argon2，禁止 MD5/SHA1）；密码与账号表分库存，防拖库后批量破解
账号状态状态机：待激活 / 正常 / 锁定（连续输错 N 次）/ 冻结 / 注销，每个状态决定允许的操作集
主体抽象用 principal_id 统一代表人、应用、服务账号，授权模型只认 principal，不认"是不是人"

组织架构

# 组织树（多层级，支持一人多部门）
集团
 ├─ 交易事业部 (dept_id=100)
 │   ├─ 订单组 (101)  ── 组长: zhangsan
 │   └─ 支付组 (102)
 └─ 技术中心 (200)
     ├─ 交易平台组 (201) ── 成员: lisi(同时归属 101，一人多部门)

# 落地方式：closure table 或路径枚举，避免递归查全链路
dept_closure(ancestor, descendant, depth)   # 101→100 深度1，101→1 深度2
一人多部门是常态不是异常：矩阵组织、借调、双线汇报都很常见。数据权限默认取"所有所属部门的并集"还是"主部门"是业务决策，必须在模型里显式表达，不能默认取第一个匹配的部门。
模块 3

授权模型演进：RBAC → RBAC+数据范围 → ABAC

授权模型不是一步到位的，是按业务复杂度逐级演进的。跳级的代价是返工，倒退的代价是越权。

第一级：RBAC（基于角色的访问控制）

用户 → 角色 → 权限点，三级关联。权限点是"功能按钮/API"级：order:create、report:export。

能力RBAC 是否覆盖
功能权限（菜单/按钮/接口）覆盖，这是 RBAC 的主场
数据权限（只能看自己的订单）不覆盖，角色一样但数据不同
动态条件（工作日可批、金额上限）不覆盖，需要属性判断
委派/临时授权（离职交接）靠加角色变通，无有效期概念

第二级：RBAC + 数据范围

角色绑定功能权限的同时，绑定数据范围：全部 / 本部门 / 本部门及以下 / 仅自己 / 自定义部门列表。鉴权时先查角色数据范围，再转成 SQL 条件：

# 数据范围 → SQL 改写示例
角色"订单专员"数据范围 = 本部门及以下
  → SELECT * FROM orders WHERE dept_id IN (
        SELECT descendant FROM dept_closure WHERE ancestor = 102)

# 组合判定：功能权限 AND 数据范围 AND 归属校验
canView(order) = hasPerm("order:view")          // 功能
             && inScope(order.dept_id)          // 数据范围
             && (order.owner == me || isSuperior) // 归属兜底

第三级：ABAC（基于属性的访问控制）

用"属性 + 条件表达式"描述策略，不再预定义角色组合。属性来自主体（部门、职级）、资源（金额、密级）、环境（时间、IP、设备）。

# 一条 ABAC 策略（伪代码）
allow if
  action in ["approve"]
  && resource.type == "refund"
  && resource.amount <= subject.approve_limit      // 审批额度
  && subject.dept in resource.business_depts        // 业务归属
  && env.time in workdays(9:00-18:00)               // 环境条件
  && env.ip in corporate_network                    // 网络条件

# 演进判断标准：RBAC+数据范围搞不定的场景出现 3 次以上，才上 ABAC
# 典型信号：审批额度分级、密级文档、跨租户共享、临时合规策略
模型适用规模运维成本
RBAC中小系统、内部管理端低，加权限 = 改角色
RBAC + 数据范围中台、多部门业务系统中，范围规则要评审
ABAC金融、合规敏感、大规模 SaaS高，策略即代码，要测试和审计
最常见的演进错误：直接上 ABAC。策略引擎、策略 DSL、策略测试一整套设施，业务还没到那个复杂度，最后运维不动又退回硬编码 if-else。正确姿势：RBAC 起步 → 数据范围补缺口 → 策略出现第三类重复模式时才抽象 ABAC。
模块 4

权限缓存与一致性

授权在每个请求上发生，必须缓存；但权限变更必须尽快生效。这个矛盾就是缓存一致性的全部战场。

缓存什么、放哪

缓存内容位置过期策略
用户→角色列表RedisTTL 5~15 分钟 + 变更主动删
角色→权限点全集（展开后）RedisTTL 30 分钟，角色变更时删
单次请求的鉴权结果请求上下文（ThreadLocal）随请求结束销毁，防同请求重复查
热点用户的权限位图本地缓存（Caffeine）TTL 1 分钟 + Redis Pub/Sub 广播失效

一致性方案对比

# 方案一：变更时主动删缓存（推荐）
管理员改角色 → 写 DB → 删 Redis 对应 key → 广播失效消息
各业务实例订阅失效消息 → 清本地缓存
# 生效延迟：秒级。风险：删缓存失败要靠 TTL 兜底

# 方案二：版本号比对
缓存 value = {version: 42, perms: [...]}
每次请求带上本地 version，服务端返回最新 version，不一致则重拉
# 生效延迟：一个请求周期。复杂度高，适合大规模场景

# 方案三：短 TTL 硬扛
不主动删，全靠 60 秒过期
# 生效延迟：最长 60 秒。高危操作（冻结、回收权限）绝不能用
权限收紧必须"先断后用"：把"允许"改成"拒绝"的敏感操作（收回权限、冻结账号），正确的顺序是：先让新请求直接拒绝（同步开关/黑名单立即生效）→ 再异步更新角色关系和清理缓存。反过来做（先慢慢删缓存）会在窗口期内继续放行。金融和权限场景，收紧操作永远走快速通道，放宽操作才可以等缓存。
模块 5

多租户隔离

多租户（SaaS 化）的核心问题：租户 A 的数据，租户 B 连看都不能看。三种隔离级别，成本和安全性递增。

级别做法成本适用
共享库 + 租户列所有表加 tenant_id，每个查询强制带条件最低中小 SaaS，租户同质
共享库 + Schema 隔离每租户独立 schema（PG 模式）中合规要求中等
独立库/实例每租户一套数据库最高大客户、金融、强合规
# 共享库模式的防线（缺一层就出事）
① 网关层：从 token 解析 tenant_id，注入请求头 X-Tenant-Id
② ORM 层：启用多租户插件，所有 SQL 自动拼接 tenant_id = ?（禁止手写 SQL 绕过）
③ DB 层：行级安全（RLS）+ 连接按租户绑定，双保险
④ 审计层：记录每次访问的 tenant_id，异常跨租访问自动告警

# 防"串租"的关键：tenant_id 只能来自服务端 token 解析，
# 永远不要信客户端传来的任何租户标识
多租户最典型的越权：改一个 URL 参数就能看别人的数据。根因是租户标识或资源 ID 只传了租户 A 的资源 ID，服务端没校验"这个资源属于当前租户"。防御口诀：资源查询必须带 tenant_id 作为查询条件，而不是查出来再比对。后者在并发下会被绕过，前者在 SQL 层就断了念想。
模块 6

审计日志与系统集成

审计日志：权限系统的"黑匣子"

要素要求
Who主体 ID（含应用/服务账号）、IP、设备指纹
When服务端时间戳，精度到毫秒，禁止用客户端时间
What动作 + 对象 + 结果（允许/拒绝 + 拒绝原因）
不可篡改只追加（append-only），WORM 存储或哈希链，保留 ≥ 180 天
可检索按人、按资源、按时间范围秒级查，支持"某账号最近被拒了哪些操作"

与网关/服务的集成

网关层：统一验签（JWT 公钥本地验）+ 权限点粗筛。URL 与权限点映射表由网关维护，新接口上线必须登记，未登记的 URL 默认拒绝
服务层：业务代码用注解/拦截器鉴权，如 @RequirePerm("order:refund:approve")，权限逻辑集中在拦截器，禁止散落在 if-else 里
数据层：数据范围转 SQL、敏感字段脱敏、行级权限。服务层漏判时，数据层是最后一道闸
管理面：权限变更（加角色、改范围）走审批流 + 双人复核，变更本身也是审计事件

性能与安全要点

要点做法
鉴权延迟预算网关鉴权 P99 < 5ms（本地验签 + 本地缓存），宁可缓存不同步也不能拖慢主链路
防权限枚举攻击403 和 404 分开返回要谨慎：批量试探资源 ID 时，统一返回 404 防信息泄露
凭证泄露响应refresh_token 异常使用（换 IP/设备）→ 自动撤销整个 token 家族 + 告警
密钥管理JWT 签名私钥在 HSM/KMS，支持密钥轮换（kid 头标识多密钥并存过渡）
防重放关键 API 带 nonce + 时间戳，5 分钟内重复 nonce 拒绝
模块 7

核心表设计与代码

六张核心表

-- 账号（与凭证分库存）
CREATE TABLE account (
  id            BIGINT PRIMARY KEY,
  principal_id  BIGINT NOT NULL,          -- 主体ID，人也、应用也罢都认它
  login_type    TINYINT NOT NULL,       -- 1手机 2邮箱 3工号
  login_id      VARCHAR(64) NOT NULL,
  tenant_id     BIGINT NOT NULL,       -- 多租户列
  status        TINYINT NOT NULL,       -- 账号状态机
  UNIQUE(tenant_id, login_type, login_id)
);

-- 角色（含数据范围）
CREATE TABLE role (
  id          BIGINT PRIMARY KEY,
  tenant_id   BIGINT NOT NULL,
  code        VARCHAR(64) NOT NULL,    -- ORDER_OPERATOR 等稳定编码
  data_scope  TINYINT NOT NULL,       -- 1全部 2本部门 3本部门及以下 4仅自己
  parent_id   BIGINT,                 -- 角色继承，防环靠应用层
  UNIQUE(tenant_id, code)
);

-- 权限点（功能权限原子单位）
CREATE TABLE permission (
  id     BIGINT PRIMARY KEY,
  code   VARCHAR(128) NOT NULL,       -- order:refund:approve
  type   TINYINT NOT NULL,           -- 1菜单 2按钮 3API
  UNIQUE(code)
);

-- 用户-角色 关联（带有效期，支持临时授权）
CREATE TABLE account_role (
  account_id  BIGINT NOT NULL,
  role_id     BIGINT NOT NULL,
  expire_at   DATETIME,               -- NULL=永久；借调/值班用
  PRIMARY KEY(account_id, role_id)
);

-- 角色-权限 关联
CREATE TABLE role_permission (
  role_id       BIGINT NOT NULL,
  permission_id BIGINT NOT NULL,
  PRIMARY KEY(role_id, permission_id)
);

-- 组织（含闭包表支持一人多部门）
CREATE TABLE department (
  id        BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  parent_id BIGINT,
  path      VARCHAR(512)             -- /1/100/101 路径枚举
);

鉴权代码骨架（含数据范围 SQL 改写）

// 1. 网关层：本地验签 + 粗筛
public class AuthFilter implements Filter {
  public void doFilter(req, resp, chain) {
    String jwt = req.getHeader("Authorization");
    Claims c = Jwts.parser().verifyWith(publicKey).build()
                .parseSignedClaims(jwt).getPayload();   // 本地验签，不调认证中心
    req.setAttribute("principalId", c.getSubject());
    req.setAttribute("tenantId", c.get("tenant_id"));   // 只信服务端解析
    chain.doFilter(req, resp);
  }
}

// 2. 服务层：注解式功能鉴权
@RequirePerm("order:refund:approve")
public RefundResult approve(Long refundId, Long amount) {
    // 3. 数据范围兜底：查询自带租户+范围条件，而不是查出来再比对
    RefundOrder o = refundMapper.selectForUpdate(refundId, tenantId(), dataScopes());
    if (o == null) throw new NotFoundException();   // 查不到=越权，统一404
    // 4. ABAC 属性判断（额度）
    if (amount > currentUser().getApproveLimit())
        throw new ForbiddenException("amount_exceeds_limit");
    return doApprove(o);
}
代码纪律三条：① 鉴权代码只走拦截器/注解，业务方法里不出现 if (hasPerm(...)) 散弹枪；② 资源查询把 tenant_id 和范围条件拼进 SQL，杜绝"查出来再判断归属"；③ 拒绝时记审计日志，且区分"无功能权限"和"资源不存在"——前者返回 403（但要防枚举），后者统一 404。
模块 8

十个线上坑

1
水平越权：改 URL 里的订单 ID 就能看别人的单
只校验了"登录没登录"，没校验"这个订单是不是你的/你部门的"。资源查询必须带 tenant_id + 数据范围作为 SQL 条件，查不到就返回 404，而不是查出来再比对。
2
垂直越权：普通用户调管理员接口
接口只做了登录校验，没做权限点校验。新接口上线必须登记权限点到网关映射表，未登记的 URL 默认全拒，而不是默认放行。
3
角色循环继承：A 继承 B，B 继承 A
建关系时没做环检测，展开权限时无限递归，栈溢出。写入时做拓扑检查（或限制继承深度 ≤ 3 层），展开时加访问标记防重入。
4
缓存不一致：改了权限半天不生效
角色变更只写了 DB，缓存靠 30 分钟 TTL 自然过期。变更必须主动删缓存 + 广播本地缓存失效；权限收紧类操作要先走黑名单快速通道立即拒绝，再异步清理。
5
JWT 里塞了角色信息，改角色后旧 token 照样放行
JWT 自包含、签发后不可改，过期前一直有效。access_token 短时效（≤2h）+ refresh_token 可撤销 + 关键操作实时查权限，三件套配齐。
6
密码用 MD5 存储，拖库后批量破解
MD5 无盐、太快，彩虹表秒破。必须用 bcrypt/argon2 加盐慢哈希，且凭证表与账号表分库存，降低单点泄露面。
7
403/404 不分，资源 ID 可被批量枚举
越权时返回"无权限"等于告诉攻击者"这个 ID 存在"。对资源归属类的拒绝统一返回 404，防信息泄露；功能权限缺失可以 403。
8
多租户系统里信了客户端传的 tenant_id
请求头里带 X-Tenant-Id 就被服务端采信，改一个头就串租。tenant_id 只能从服务端签发的 token 解析，客户端传来的任何租户标识一律忽略。
9
鉴权逻辑散落在业务代码里，新接口漏加
每个方法手写 if (hasPerm) 必然漏。鉴权必须收敛到网关 + 注解拦截器一层，配合"新接口不登记权限点就拒绝上线"的流水线卡点。
10
没有审计日志，出事后说不清谁干的
账号被盗用/内部误操作后无据可查。每次鉴权决策（含拒绝及原因）都要落不可篡改日志，保留 180 天以上，支持按人、按资源反查。
自测

六道题

1. 用户登录成功后访问 /order/12345，发现能看到别人的订单。这是哪类问题？根因是什么？
正确答案：水平越权。同等权限的用户互相访问对方的数据。根因是只校验了"登录 + 有 order:view 权限"，没校验"订单 12345 属于当前用户的数据范围"。防御：查询 SQL 强制带 tenant_id/数据范围条件，查不到返回 404。
2. 关于 JWT 作为 access_token，下列说法正确的是？
正确答案：JWT 过期前无法主动失效（无状态、自包含的代价）。缓解：access_token 短时效、refresh_token 服务端可撤销、关键操作实时查权限。payload 只是 Base64 编码不是加密，任何敏感信息都不能放。
3. 管理员刚把某用户的角色从"审批人"改成"普通员工"，哪种做法能最快确保旧权限立即失效？
正确答案：先黑名单拒绝、再异步清理。权限收紧操作必须"先断后用"：同步开关秒级生效，然后异步改关系、删缓存兜底。等缓存过期会有分钟级的放行窗口；清空全量缓存会把其他用户一起打挂。
4. RBAC + 数据范围模型里，"只能看本部门及以下部门的订单"如何落地？
正确答案：闭包表展开成 SQL 条件。dept_closure(ancestor, descendant) 查当前部门的所有后代，作为 IN 条件在数据库层过滤。内存过滤浪费 IO 且有并发风险；每部门建角色会让角色数随组织规模爆炸。
5. 多租户 SaaS 系统，以下哪种做法是从客户端请求中获取租户标识的安全方式？
正确答案：只信服务端 token 解析结果。租户标识是安全边界，客户端传什么都是不可信输入。请求头、URL 参数都能被篡改，只有服务端私钥签发的 token 才可信。
6. 什么时候适合从 RBAC + 数据范围演进到 ABAC？
正确答案：出现重复的属性判定模式、角色组合无法表达时。ABAC 的运维成本（策略引擎、DSL、测试）很高，跳级上线通常以返工收场。信号是"同类 if-else 在多个模块重复出现"，而不是角色数量多——角色多用角色组/继承解决。
