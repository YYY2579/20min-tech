开始前

CMS 的四个核心域

企业级 CMS（如政府门户、新闻站、电商内容中台）无论产品形态怎么变，内核都是四个域。理解这四个域的边界，比记住任何产品功能都重要。

域回答的问题核心产物
内容模型内容长什么样？有哪些字段？类型之间什么关系？schema（字段定义、类型继承树）
工作流内容从创作到上线经过哪些环节？谁能推进？状态机（草稿/审核/发布/下线）
发布内容怎么到用户眼前？怎么回滚？怎么灰度？发布管线、版本管理、静态化
权限谁能创建、谁能审、谁能发？数据范围怎么隔离？RBAC + 数据范围 + 站点隔离
四个域的联动关系：权限决定"谁能操作工作流里的哪个状态"，工作流决定"什么状态允许发布"，发布时按内容模型渲染页面。改任何一个域，另外三个都会受影响——这就是 CMS 改版总是事故频发的原因。
模块 1

内容模型设计

内容模型是 CMS 的地基。模型设计的目标：让运营自助配置新内容类型，而不需要开发改表。反面教材是 EAV（实体-属性-值）滥用。

1.1 三种建模范式对比

方案做法问题
宽表每种内容类型一张表，字段写死新类型 = DDL 改表，存量数据迁移痛苦；字段浪费（稀疏）
EAVentity/attribute/value 三张表，属性动态存查询灾难：按字段过滤要自关联 N 次；索引失效；数据无类型约束
JSON 字段
（推荐）		固定核心列 + JSON 存自定义字段，MySQL 5.7+/PG 原生支持JSON 内字段不能建高效索引（但可用生成列补救）
-- 推荐 schema：核心列固定 + ext_json 存自定义字段
CREATE TABLE content (
  id            BIGINT NOT NULL AUTO_INCREMENT,
  model_id      INT NOT NULL,            -- 内容模型 ID（文章/商品/专题）
  site_id       INT NOT NULL,            -- 站点隔离
  title         VARCHAR(255) NOT NULL,       -- 所有模型共享的核心列
  slug          VARCHAR(255) DEFAULT '',    -- URL 别名
  status        TINYINT NOT NULL DEFAULT 0, -- 0=草稿 1=审核中 2=已发布 3=已下线
  author_id     BIGINT NOT NULL,
  ext_json      JSON NOT NULL,             -- 自定义字段：{"author":"张三","source":"新华社"}
  publish_time  BIGINT DEFAULT NULL,     -- 定时发布的时间戳
  create_time   BIGINT NOT NULL,
  update_time   BIGINT NOT NULL,
  PRIMARY KEY (id),
  KEY idx_model_status (model_id, status, publish_time DESC)
) ENGINE=InnoDB;

-- 内容模型定义表：运营在后台配置"文章模型有哪些字段"
CREATE TABLE content_model (
  id            INT NOT NULL AUTO_INCREMENT,
  name          VARCHAR(64) NOT NULL,      -- "新闻文章"
  parent_id     INT DEFAULT 0,          -- 类型继承：0=根
  fields_json   JSON NOT NULL,         -- [{"key":"source","type":"string","required":true}]
  workflow_id   INT NOT NULL,          -- 绑定哪个工作流
  PRIMARY KEY (id)
) ENGINE=InnoDB;

1.2 类型继承与字段解析

模型树示例：基础内容（title, status）→ 图文内容（+cover, gallery）→ 新闻文章（+source, keyword）。读取一篇新闻时，按 parent 链自底向上合并 fields_json，得到完整字段集。继承让"所有新闻都有封面"这类规则只配一次。

# 字段解析（写入时校验 + 读取时投影）
# 写入：按继承链合并出全部字段定义 → 校验 required/类型/长度 → 存入 ext_json
# 读取：同样合并字段定义 → 从 ext_json 投影出前端需要的字段
# 关键：字段定义的解析结果必须缓存（模型定义变更频率极低），
#       不能每次写内容都去解析继承链

# JSON 字段的索引补救：MySQL 生成列
ALTER TABLE content ADD COLUMN src VARCHAR(64)
  GENERATED ALWAYS AS (JSON_UNQUOTE(JSON_EXTRACT(ext_json, '$.source'))) STORED,
  ADD INDEX idx_src (src);
# 效果：WHERE ext_json->'$.source' = '新华社' 能走索引（等价于 WHERE src = '新华社'）

1.3 Schema 演进的铁律

  • 只加不减：新字段加默认值；删除字段先在读取层停用（返回 null），确认无引用后再从 fields_json 移除——永远不要直接删字段定义
  • 字段重命名 = 加新 + 迁数据 + 双写过渡期 + 删旧，四步走，每步一个版本
  • 类型升级要向后兼容：string → int 之前，存量值必须能转换；不能转就先双写、分批回填
模块 2

草稿-审核-发布工作流

CMS 的工作流是有状态的状态机，核心原则：状态只增不减、转换必须显式、每次转换落流水。工作流状态丢失 = 内容卡死，是最高优先级故障。

2.1 状态机定义

状态集合（状态只增不减，废弃的状态保留不再进入）
  DRAFT(0)        -- 草稿：作者可编辑，仅自己可见
  REVIEWING(1)    -- 审核中：锁定编辑，等待审核人动作
  REJECTED(2)     -- 已驳回：携带驳回意见，回到作者
  PUBLISHED(3)    -- 已发布：线上可见，走发布管线
  OFFLINE(4)      -- 已下线：从线上撤下，内容保留

合法转换（所有其他转换一律拒绝）
  DRAFT      --提交审核--> REVIEWING      （作者）
  REVIEWING  --通过-----> PUBLISHED       （审核人）
  REVIEWING  --驳回-----> REJECTED        （审核人，必填意见）
  REJECTED   --修改提交-> REVIEWING       （作者）
  REJECTED   --撤回-----> DRAFT           （作者）
  PUBLISHED  --下线-----> OFFLINE         （发布者/管理员）
  PUBLISHED  --改内容---> REVIEWING       （作者，已发布内容修改必须重审）
  OFFLINE    --重新发布-> PUBLISHED       （发布者）

防腐化规则（状态机的关键护栏）：
1. 转换必须校验当前状态：UPDATE ... WHERE id=? AND status=? 利用行锁防并发
2. 每个动作落流水表：谁、什么时间、从什么状态、到什么状态、意见
3. 驳回必须带意见：意见为空直接拒绝转换
4. 已发布内容的修改 = 新版本进入 REVIEWING，线上仍展示旧版本（模块 3 讲）

2.2 状态转换的并发安全实现

-- 错误做法：先查状态，再更新（两次查询之间状态可能被别人改掉）
-- 正确做法：利用 WHERE status = 旧状态 做乐观并发控制
UPDATE content
SET status = 3, publish_time = UNIX_TIMESTAMP(NOW(3)) * 1000
WHERE id = 1001 AND status = 1;   -- 只有"审核中"才能被审过
-- affected_rows = 0 说明状态已被别人改动（并发审核/重复点击），直接拒绝本次操作
-- 比 SELECT FOR UPDATE 轻：无锁等待，失败即返回冲突

2.3 审核任务与提醒

机制实现
审核任务池提交审核时向审核人推送任务（站内信/IM webhook），任务与内容状态联动：内容被驳回/下线，任务自动关闭
超时提醒延迟队列：审核中超过 4 小时未处理 → 提醒审核人；超过 24 小时 → 升级到主管
防绕过发布动作必须由发布权限角色执行；作者账号即使有发布权限，也禁止审核自己提交的内容（同一个人不能既当运动员又当裁判）
工作流最常见的三处漏洞：① 前端只做了按钮置灰，后端没校验状态转换——直接改数据库/调接口就能跳过审核；② 没有利用 WHERE status=旧值，两个审核人同时点"通过"，状态机被推错；③ 驳回不写意见，作者不知道怎么改，来回空转。状态机必须全部在后端，且每个转换都落流水。
模块 3

发布与版本管理

发布不是改个 status 字段那么简单。生产级发布链路要回答四个问题：发什么、怎么渲染、怎么回滚、怎么灰度。

3.1 发布管线

定稿快照：发布时把当前内容（含 ext_json）完整拷贝为一条版本记录——发布的是快照，不是实时表。之后作者再改内容，不影响已发布版本
渲染：按内容模型的模板渲染成 HTML（服务端模板或增量渲染），渲染结果存对象存储/CDN
失效：向 CDN 和页面缓存推送失效请求（目录级 purge，如 /news/2026/**），带版本号防误删
生效验证：发布后自动回源验证一次（CDN 节点上实际请求该 URL，比对版本号），失败则告警并保留旧版本
-- 版本表：每次发布一条不可变记录
CREATE TABLE content_version (
  id            BIGINT NOT NULL AUTO_INCREMENT,
  content_id    BIGINT NOT NULL,
  version_no    INT NOT NULL,            -- 版本号：1,2,3...
  snapshot      JSON NOT NULL,           -- 发布时的完整内容快照
  render_url    VARCHAR(512),              -- 静态化后的地址
  published_by  BIGINT NOT NULL,
  publish_time  BIGINT NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_content_ver (content_id, version_no)
) ENGINE=InnoDB;

-- 内容表增加"当前线上版本"指针
ALTER TABLE content ADD COLUMN live_version INT DEFAULT NULL;
-- 回滚 = UPDATE content SET live_version = 5 WHERE id = 1001;（秒级，无需重新渲染）

3.2 回滚与灰度

能力实现
版本回溯live_version 指回任意历史版本，立即生效。静态化产物已存在，无需重渲染——回滚必须是 O(1) 操作
定时发布延迟队列扫描 publish_time <= now 且 status=已过审的内容，触发发布管线。注意幂等：同一条不能发两次
灰度发布新版本先只对 5% 流量生效：渲染层按用户 ID 哈希分流到新/旧 render_url，观察错误率后全量。适合首页/专题页等大改版
差异对比发布前展示新旧版本快照 diff（字段级），编辑确认后再发布——防止"顺手改错字段"上线
版本管理的本质：把"内容"和"内容的某个发布态"解耦。内容表存工作副本（作者一直在改），版本表存发布快照（线上实际展示）。没有版本表的 CMS，回滚只能靠改回去，一旦中间改过多轮就永远回不去了。
模块 4

多站点与多语言

集团级 CMS 的标配：一套后台管 N 个站点（主站、地方站、海外站），每站多语言。隔离做不好，一个站的内容会串到另一个站。

4.1 多站点隔离模型

层级隔离方式共享内容
数据层所有业务表带 site_id，查询强制 WHERE site_id=?媒体库、用户体系、标签库可跨站共享
配置层每站独立的模型/工作流/菜单/域名配置可继承"默认站点配置"，子站覆盖差异项
发布层独立域名 + 独立 CDN 目录，缓存 key 带 site 前缀共享模板引擎和渲染服务
权限层用户对站点有角色绑定：A 站编辑看不到 B 站内容超管跨站
# 多站点查询的强制约束（防穿透的关键）
# 所有 SQL 由 ORM 拦截器自动追加 site_id 条件，应用层不信任任何传入的 site_id
# SELECT * FROM content WHERE site_id = {当前会话站点} AND id = ?
# 血的教训：只按 id 查内容不查站点 → 编辑 A 站的人改 URL 里的 id 就能动 B 站内容

# CDN 缓存 key 设计（站点 + 语言 + 路径）
# cache key = {site}:{lang}:{path}  例：main:en-US:/news/2026/hello.html
# 发布 A 站中文版时 purge 范围 = main:zh-CN:/news/2026/**
# 绝不能 purge main:*（会把英文站一起清了，造成源站流量突刺）

4.2 多语言（i18n）的两种策略

策略做法适用
字段级翻译同一内容多份：content + content_i18n(lang, title, body)，按语言查正式内容，SEO 友好，每语言独立审核流
运行时翻译只存原文，页面渲染时调机器翻译 APIUGC、评论区，接受延迟和误差
  • 语言回退链：英文站缺法语内容时回退到英文，而不是 404。回退链配置：fr-CA → fr → en → 默认
  • 翻译状态独立：中文版已发布 ≠ 英文版已发布，i18n 记录有自己的 status，各自走工作流
  • URL 规范：子目录（/en/news/xxx）适合主站加语言；独立域名（en.example.com）适合海外站，CDN 和缓存天然隔离
模块 5

缓存与静态化

CMS 的读特征是读多写极少、内容变更集中、对首屏速度敏感——这是静态化的最佳战场。核心矛盾只有一句话：缓存越快，脏读风险越大。

5.1 渲染策略光谱

策略机制适用
纯动态每次请求查库渲染后台、低频页面。绝不上生产前台
页面缓存渲染结果缓存（Redis/本地），TTL 或主动失效列表页、详情页，秒级失效可接受
全量静态化发布时渲染成 HTML 推 CDN，源站零计算新闻详情、帮助中心。抗流量武器
增量静态再生
（ISR）		首访静态 + 后台按 TTL 重新生成 + 按需即时再生Next.js 等框架的主流方案，平衡实时与性能
ESI 片段缓存页面拆公共片段（导航/推荐）+ 私有片段，分别缓存头部导航全站共享、主体内容各不同的场景

5.2 缓存失效的正确姿势

# 失效链路：发布 → 失效 Redis → 失效 CDN（顺序不能反）
# 1. Redis：DEL page:{site}:{lang}:{path}（或按内容 ID 反查关联页面批量删）
# 2. CDN：purge URL / 目录，如 /news/2026/*（注意 5.1 节的 key 前缀设计）

# 关联反查：一篇内容出现在 N 个页面（详情页 + 列表页 + 专题页 + 首页）
# 发布时必须能找出所有关联页面 → 维护"内容 ID → 页面 key"的反查表
# 简化方案：按目录 purge（/news/2026/** 覆盖详情和当月列表）

# 版本号防脏：页面 URL 不带版本号，但响应头带 ETag / X-Content-Version
# 发布后灰度期对比新旧版本响应头，确认 CDN 已刷新再切全量
脏缓存的四种典型成因：① 发布时只删了 Redis 没 purge CDN，用户继续拿到旧静态页；② purge 目录写太宽（用了 /*），把无关页面一起清了，源站被回源打爆；③ 定时发布任务重复执行，缓存被反复删，永远热不起来；④ 静态化产物生成了一半就推了 CDN（渲染异常），用户看到半个页面。对策：失效链路带日志可追踪、purge 范围最小化、发布动作幂等、产物先校验再推送。
模块 6

三级权限与 CDN 配合

CMS 权限的行业标准是三级：编辑（创作）/ 审核（把关）/ 发布（上线）。加上数据范围（站点/栏目），构成完整的权限矩阵。

6.1 权限模型

角色能做什么关键约束
编辑创建/编辑草稿、提交审核、修改被驳回内容不能审核、不能发布；只能操作自己被授权的栏目
审核通过/驳回 REVIEWING 状态的内容不能审核自己提交的（权限互斥）；不能直接发布
发布发布已过审内容、下线、回滚版本只能发 status=审核通过的内容；发布动作全部落审计日志
管理员配置模型/工作流/站点/用户角色配置变更需二次确认，且影响存量的操作要提示
# 数据范围：角色 + 栏目 + 站点 三维权限
# user_role(user_id, role, site_id, column_ids_json)
# 例：张三 = 编辑 @ 主站 @ 栏目[新闻,体育]
#   → 只能创建/编辑"主站新闻体育"下的内容，看不到科技栏目

# 权限校验必须在服务端，且校验的是"状态 + 角色 + 数据范围"三要素
def can_publish(user, content):
    return (content.status == REVIEWED            # 状态对
        and has_role(user, PUBLISHER, content.site_id)   # 角色对
        and in_scope(user, content.column_id))            # 范围对

# 审核与编辑互斥：提交人 == 审核人 时直接拒绝（防止自己审自己）

6.2 与 CDN 的配合

静态内容全部上 CDN：详情页 HTML、图片、附件走 CDN，源站只服务动态接口和后台。CDN 是流量的第一道闸，源站 capacity 按 10% 峰值设计
预热：重大发布（首页改版、专题上线）前主动预热 CDN——把 URL 推给 CDN 节点预拉取，避免发布瞬间百万回源打爆源站
分级 TTL：详情页 HTML 缓存 1 小时（发布即失效兜底）；图片/视频缓存 30 天（内容不变，靠版本化 URL 更新）；接口不缓存
错误页兜底：源站 5xx 时 CDN 返回预置的错误页（静态 HTML），而不是把错误透传给用户。错误页也要定期更新，不能是十年前的那版
模块 7

十个线上坑

1
用 EAV 存自定义字段，查询和索引全崩
按字段过滤要自关联 N 次，数据量上万就超时。用 JSON 列 + 生成列建索引，或把高频过滤字段提为核心列。
2
模型变更直接删字段定义，存量内容读取报错
运营删了"来源"字段，历史新闻渲染时取 ext_json['source'] 直接抛异常页面 500。字段必须先停用（读取返回 null）再移除。
3
状态转换只在前端控制，后端不校验
绕过界面直接调 API 就能把 DRAFT 改成 PUBLISHED，审核流形同虚设。所有转换必须服务端校验 + WHERE status=旧值 乐观锁。
4
已发布内容修改后直接改原记录，旧版本丢失
改错一个字想回滚，发现旧内容已被覆盖。必须版本表存快照，线上展示 live_version 指向的版本。
5
定时发布任务不幂等，重复执行
调度系统重投导致同一条内容发布两次、版本号跳变、缓存被反复清。任务要带业务幂等键（content_id + publish_time）。
6
CDN purge 范围用 /*，发布后源站被回源打爆
一条内容发布清了全站缓存，百万请求同时回源，数据库连接池打满。purge 必须按最小目录（/news/2026/**）。
7
多站点查询不隔离，A 站编辑改到 B 站内容
接口只按 id 查不带 site_id，改 URL 参数即可跨站操作。ORM 层强制注入站点条件，不信任何传入的 site_id。
8
页面静态化只渲染了部分数据就推送 CDN
渲染时依赖的推荐服务超时，页面推上去缺了一块。产物推送前必须完整性校验（关键占位符非空），失败告警并保留旧版。
9
审核人也能提交审核，自己审自己
三级权限没有做角色互斥，审核人既是运动员又是裁判，工作流失去意义。提交人与审核人必须异人或强制会签。
10
工作流状态机边加边改，转换散落在各处
状态判断 if-else 散落在十几个服务里，加个"撤回"功能漏改一处就出现脏状态。状态机必须集中定义（配置 + 一张转换表），全部转换走同一个入口。
自测

六道题

1. CMS 内容模型要支持运营自助新增字段，最合理的存储方案是？
正确答案：JSON 列方案。EAV 查询要自关联 N 次、索引失效，数据量一大就崩；建新表则 DDL 频繁、存量迁移痛苦。JSON 列兼顾灵活性和单表查询性能，生成列解决索引问题。
2. 两个审核人同时点击"通过"同一篇内容，系统应该怎么处理？
正确答案：乐观并发控制。WHERE status=旧状态 保证只有第一个转换成功，第二个发现状态已变直接返回冲突。比分布式锁轻，也不需要等待。
3. 关于已发布内容的修改，正确的流程是？
正确答案：新版本重审，线上展示不中断。版本表存每次发布的快照，live_version 指针指向线上版本。直接改原记录会丢旧版本无法回滚；先下线则内容凭空消失，SEO 和用户体验都受损。
4. 一篇新闻详情页同时出现在列表页、专题页和首页，发布时缓存怎么失效？
正确答案：反查关联页面或按最小目录 purge。只删详情页会导致列表页/首页仍是旧数据；全量 purge 又会误伤无关页面导致源站回源突刺。需要维护"内容→页面"反查关系。
5. CMS 三级权限（编辑/审核/发布）的关键约束是什么？
正确答案：职责分离 + 服务端强制。三级权限的意义就是互相制衡：作者（编辑）不掌握上线权，审核人把关质量，发布人控制时机。任何互斥（尤其"自己不能审自己"）都必须在服务端实现，前端置灰只是体验。
6. 内容模型要删除一个已存在两年的字段"来源"，正确做法是？
正确答案：先停用再移除。直接删定义会让存量内容的渲染逻辑取不到值而报错（页面 500）。CMS 的模型演进铁律是只加不减、删除必须分期：停用期容忍旧数据存在，观察一个版本周期再清理。
