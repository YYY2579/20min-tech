开始前

Feed 到底在解什么问题

一句话：把"我关注的人产生的内容"，高效地组装成一条按时间排序的流，并在 200ms 内返回第 1 屏。所有设计决策都源于这句话里的三个词：关注、组装、时间排序。

系统Feed 形态核心挑战
微博 / Twitter关注流（单向关注）大 V 扇出、热点内容、未读管理
朋友圈 / 抖音关注关系流（双向好友）强关系、隐私控制、已读状态
抖音 / 头条推荐推荐流（不依赖关注）召回+排序模型、去重、兴趣衰减
GitHub / 钉钉事件流（动态聚合）聚合策略、@ 提及、通知合并
先分清楚两种流：关注流（Timeline）依赖显式关注关系，内容是"我关注的人发的"；推荐流依赖画像和模型，内容是"算法觉得你会喜欢的"。本篇讲关注流的工程骨架，推荐流只在排序介入点处涉及。
模块 1

核心模型：内容、关注关系、时间线

三个实体撑起整个系统：内容（Content）、关注关系（Follow）、时间线（Timeline）。Timeline 不是实体，是"视图"——由内容+关系计算出来的有序列表。

1.1 核心表设计（MySQL，生产可用）

-- 内容表：按内容 ID 分库分表（内容 ID 用雪花号，自带时间序）
CREATE TABLE content (
  id            BIGINT NOT NULL,          -- 雪花 ID，高 41 位是毫秒时间戳
  user_id       BIGINT NOT NULL,          -- 作者
  content_type  TINYINT NOT NULL,        -- 1=纯文本 2=图文 3=视频 4=转发
  text          VARCHAR(2000) NOT NULL DEFAULT '',
  media_json    JSON,                     -- 图片/视频地址、宽高、时长
  origin_id     BIGINT DEFAULT NULL,      -- 被转发的原内容 ID
  status        TINYINT DEFAULT 1,        -- 0=待审核 1=正常 2=已删除 3=仅自己可见
  create_time   BIGINT NOT NULL,          -- 毫秒时间戳，与 id 高 41 位一致
  PRIMARY KEY (id),
  KEY idx_user_time (user_id, create_time DESC)
) ENGINE=InnoDB;

-- 关注关系：粉丝侧和关注侧各一份索引，两种查询都会用
CREATE TABLE follow (
  id           BIGINT NOT NULL AUTO_INCREMENT,
  follower_id  BIGINT NOT NULL,   -- 谁关注了（粉丝）
  followee_id  BIGINT NOT NULL,   -- 被关注的人（大 V）
  status       TINYINT DEFAULT 1,  -- 1=关注 2=拉黑 3=特别关注
  create_time  BIGINT NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_f2e (follower_id, followee_id),
  KEY idx_e_time (followee_id, create_time DESC)  -- 查"大 V 的新粉丝"
) ENGINE=InnoDB;

-- 用户内容索引表：写扩散时"向粉丝 timeline 投递"只投 ID
CREATE TABLE user_post_index (
  user_id       BIGINT NOT NULL,
  content_id    BIGINT NOT NULL,
  create_time   BIGINT NOT NULL,
  PRIMARY KEY (user_id, content_id),
  KEY idx_time (user_id, create_time DESC)
) ENGINE=InnoDB;

1.2 时间线在 Redis 里的样子

# 每个粉丝一个 ZSet：member=content_id, score=create_time(毫秒)
ZADD timeline:1001 1718000000000 content:90001 1718000000001 content:90002
ZREVRANGEBYSCORE timeline:1001 +inf 1718000000000 LIMIT 0 20   # 最新 20 条

# 容量换算（必须先算这个再动手）
# 1 亿 DAU × 平均关注 200 人 × 每人每天发 0.5 条
# = 100,000,000 × 200 × 0.5 = 100 亿条/天 写入（如果纯写扩散）
# 单机 Redis 约 10w QPS 写 → 100亿 / 86400秒 ≈ 116万/秒，需要 12+ 台机器
时间线是有损存储：Redis 的 ZSet 不可能无限长。行业惯例是每个用户只保留最近 500~1000 条，更早的走"回拉"（模块 6 讲）。所以 Timeline 是"热点缓存"，不是"全量数据"——内容表才是真相，Timeline 只是索引。
模块 2

三种分发模式：推 / 拉 / 推拉结合

这是 Feed 面试的第一道题。核心区别只有一个：内容分发发生在"发的时候"还是"读的时候"。

2.1 模式对比

维度推模式（写扩散）拉模式（读扩散）推拉结合
分发时机发布时，写给所有粉丝读取时，聚合所有关注对象普通用户推、大 V 拉
读性能O(1)，直接读自己的 timelineO(N)，N=关注数，每次读都要聚合普通用户 O(1)，大 V 视情况
写性能大 V 发一条 = 千万次写入发布只写 1 次，极轻大 V 写轻、普通用户写 N 次
存储粉丝人均一份（冗余 ×N）内容只存一份混合
实时性准实时（推送链路有延迟）完全实时（读时算）普通用户准实时
典型用户普通用户（粉丝 < 1000）大 V（粉丝 > 100 万）生产系统标配
代表朋友圈、Twitter 普通用户Twitter 大 V、微博大 V微博、抖音关注流

2.2 推模式（写扩散）的流程

用户 A 发布内容 → 写入 content 表，拿到雪花 ID（自带毫秒时间戳，全局有序）
查询 A 的粉丝列表（粉丝 < 阈值时直接查 follow 表；超阈值走缓存/分页拉取）
把 content_id + create_time 写入每个粉丝的 timeline ZSet（ZADD）
粉丝读 Feed 时：ZREVRANGEBYSCORE timeline:{follower_id} +inf {cursor} LIMIT 0 20，拿到 ID 列表后批量查内容（mget）
# 扇出计算：A 有 500 粉丝，发 1 条内容 = 500 次 ZADD
# 若 A 每秒发 1 条，持续 1 小时：500 × 3600 = 180万次 ZADD，Redis 可承受
# 若 A 有 1000万 粉丝，发 1 条 = 1000万次 ZADD ≈ 1000万 QPS
# 单机 Redis 写上限约 10万/秒 → 需要 100 台机器同时写，还不算网络
# 结论：粉丝数超过阈值（通常 1万~10万）的大 V 绝不能走写扩散

2.3 拉模式（读扩散）的流程

# 读时聚合：用户 B 关注了 200 人
# 1. 查 B 的关注列表：[A1, A2, ..., A200]
# 2. 对每个关注对象，取其 user_post_index 里最新的几条
#    SELECT content_id FROM user_post_index WHERE user_id IN (...) ORDER BY create_time DESC
# 3. 内存里做 200 路归并（merge sort），取前 20 条

# 读耗时估算：200 个用户 × 2ms（各查一次索引）= 400ms（串行）
# 优化为并发查询（go routine / 线程池）：max(2ms) + 归并开销 ≈ 20ms
# 但关注 5000 人时，5000 路归并 + 5000 次查询，并发也救不回来
# 结论：纯拉模式只适合关注数 < 500 的中小 V，且必须加聚合缓存

2.4 大 V 的专门处理（推拉结合的核心）

判定标准：粉丝数 > 阈值（通常取 1 万）即视为大 V，切换为拉模式。大 V 的内容不进任何人的 timeline 推送链路，而是在用户刷新时实时拉取合并。工程上有三个细节决定成败：

  • 大 V 的"最近内容"要单独缓存：大 V 发的内容只写一份 zvip:{vv_id}，所有人共享读取。1000 万粉丝读同一条内容，实际只查 1 份缓存
  • 合并时的去重与截断：普通用户 timeline 里已经推送过的内容 ID 用 Set 去重（大 V 也可能因特殊关注被推送）；归并后按 score 截断到 page size
  • 大 V 内容要有独立过期：大 V 的 zvip 缓存设短 TTL（如 30 秒），保证热点突发时不会全量穿透到 DB
推拉结合的行业标准答案：普通用户（粉丝 < 1 万）走推——发布时写扩散到粉丝 timeline；大 V（粉丝 ≥ 1 万）走拉——发布时只写自己的内容索引，用户读时按需聚合。关注关系变更（新关注/取关）时，把新关注的大 V 的近期内容补拉到自己的 timeline，并清理已取关者的内容。
模块 3

读扩散 vs 写扩散的工程权衡

模块 2 讲了机制，这里讲决策矩阵——什么时候可以偏离标准答案。

场景特征推荐模式理由
强关系、粉丝数低（<500）写扩散扇出小，读 O(1)，实时性好。朋友圈、钉钉动态
弱关系、粉丝悬殊推拉结合微博、Twitter 的标准架构
关注数极多（>2000）读扩散归并成本可控，且避免给大 V 造成写压力
读多写少（QPS 读:写 > 100:1）写扩散写时多花一次扇出，读时全部 O(1)，总体最优
写多读少（全员高频发）读扩散写扩散会让扇出总量爆炸（N×M），读扩散只写 N 次
时效性要求高（秒级可见）读扩散写扩散有异步队列延迟；读扩散读到的是实时索引
存储成本敏感读扩散写扩散有 N 倍冗余；读扩散内容只存一份

3.1 扇出总量的量化公式

写扩散总写入量 = Σ(每个用户的粉丝数) = 总关注边数 × 内容发布率
读扩散总读取量 = Σ(每个用户的关注数) × 刷新率

算例（日活型产品）：
- 1 亿 DAU，平均每人关注 200，平均每人关注者 200（对称）
- 总关注边数 = 1亿 × 200 = 200亿条
- 平均发布率 = 0.5 条/人/天

写扩散：200亿边 × 0.5条 = 100亿次/天 写入 timeline ≈ 116万 QPS
  → 按单机 Redis 10w 写 QPS，需 12 台；考虑峰值 3 倍 → 36 台
读扩散：1亿 DAU × 每天刷新 10 次 × 200 路归并
  = 2000亿次/天 索引查询 ≈ 2300万 QPS（读），归并 CPU 开销巨大
  → 需要聚合缓存兜底，纯读扩散不可行

推拉结合：假设 1% 是大 V（粉丝>1万），99% 普通用户
  普通用户粉丝平均 200 × 0.99亿人 × 0.5条 ≈ 99亿次/天 推送（≈115万 QPS）
  大 V 内容走读：1亿人刷新时按需拉取，读缓存命中率 >99%
  结论：写量降 1%，读压力靠缓存扛，这是微博/抖音的实际路线
写扩散最大的坑不是量，是"删"：用户删除内容时，写扩散模式下要把所有粉丝 timeline 里的这条 ID 删掉——又是一次全量扇出。解法：timeline 里只存 ID，读时用内容表的 status 过滤（已删的不返回）。永远不要在写扩散模式下做"删除扇出"。
模块 4

分页与游标：为什么坚决不用 offset

Feed 分页是深分页问题的经典现场。offset 分页在 Feed 场景是错的，原因有三：数据实时新增、性能断崖、结果重复/遗漏。

4.1 offset 为什么不行

# 错误示范：MySQL offset 分页
SELECT * FROM content ORDER BY create_time DESC LIMIT 10000, 20;
# offset=10000 时 MySQL 要扫描并丢弃前 10000 行，数据量大时耗时线性增长
# 第 1 页：5ms → 第 500 页：200ms → 第 5000 页：2s+

# 更致命的问题：Feed 是活的
# 用户看第 1 屏时 top=100 条，10 分钟后刷新出 3 条新内容
# 用户翻到第 2 页（offset=20），拿到的是原第 21~40 条
# 但此时 top 20 已变成 [新1,新2,新3,旧1...旧17]
# → 用户第 2 页会看到 旧1~旧3 的重复！新内容把 offset 顶偏了

4.2 游标分页的正确姿势

# 游标 = 上一页最后一条的 (score, id) 二元组
# 请求：GET /feed?cursor={last_score}_{last_id}&size=20

-- MySQL 实现（利用 (create_time, id) 联合索引）
SELECT * FROM content
WHERE (create_time, id) < (1718000000000, 90001)
ORDER BY create_time DESC, id DESC
LIMIT 20;
-- 索引 (create_time, id) 直接定位到游标位置，O(logN)+20，与翻到多深无关

# Redis 实现（ZSet 天然支持）
ZREVRANGEBYSCORE timeline:1001 (1718000000001 -inf LIMIT 0 20
# 左括号 ( 表示开区间，恰好排除上一页最后一条，不会重复

# 为什么 score 相同要带 id 做 tiebreaker？
# 同一毫秒发多条内容时，只按 score 翻页会漏数据或重复
# (score, id) 二元组保证全序，雪花 ID 自带毫秒+序列号，天然唯一

4.3 三种 Feed 翻页语义对比

语义触发场景实现
加载更多（向下）用户主动下拉游标分页，游标 = 上一页末条 (score,id)
下拉刷新（向上）用户下拉回顶部查"比当前最新还新的"：score > 当前最新 score
回拉补洞timeline 只存 1000 条，翻到底了翻页到 ZSet 边界时，回源到 user_post_index / 大 V 的 zvip 补齐，再拼上游标
深分页 + 游标也不是万能的：用户连续翻 10 万条（极端场景）时，游标里的 score 会非常老，MySQL 走索引仍然快，但Redis ZSet 用 ZREVRANGEBYSCORE 翻老数据时要 skip 的元素太多（Redis 6.2 之后才支持 BYSCORE + LIMIT 内部优化，之前是 O(skip+n)）。解法：timeline 分层——最近的 1000 条在 Redis，更老的直接查 MySQL 的 user_post_index，翻页游标自然过渡。
模块 5

未读计数与多端同步

未读（红点）和多端同步是 Feed 的"体验层"需求，但工程上比主链路更难做对——它们涉及计数一致性和跨端状态对齐。

5.1 未读计数的三种实现

方案实现适用
全局计数器每个用户一个计数 key：INCR unread:{uid}，打开 Feed 时清零简单，但"打开"的定义模糊（看一眼算读过吗）
游标水位线记录用户"已读到的最新 content_id"，未读数 = timeline 中 score > 水位的条数与翻页强一致，推荐
时间水位线记录最后消费时间戳，未读 = create_time > 水位的内容数简单但时钟不一致时丢数据
# 水位线方案（业界主流，Instagram/微博同思路）
# 1. 用户读到某条内容 → 记录水位：SET read_mark:{uid} {content_id}
# 2. 未读数 = ZCOUNT timeline:{uid} ({watermark_score} +inf
#    （ZSet 的 member 就是 content_id，score 就是 create_time，天然可算）

# 关键细节：水位必须存"已读的最大 score"，而不是"读过的 ID 集合"
# 存 ID 集合的代价：用户翻 1000 条 = 1000 个 ID，集合无限膨胀
# 存水位的问题：用户可能跳着读（先看第 50 条，水位就被顶到 50）
# → 妥协：水位取"连续已读的边界"，发现跳读时只推进到连续段的末尾

5.2 多端同步

手机、平板、Web 同时登录时，核心问题是：一个端上的"已读"状态，如何同步到其他端，且不冲突。

读扩散推送（服务端 push）：timeline 更新时，通过长连接（WebSocket / MQTT）向在线端推送增量 ID 列表，端上本地合并。这是"实时新内容提示"的基础
读状态同步：客户端本地维护 read_mark，定期或在关键动作（退出应用、切后台）时上报服务端；服务端以最大水位为准合并（幂等，取 max）
版本号防冲突：每次读状态变更带单调递增的 version，服务端拒绝 version 小于当前记录的更新，避免旧设备回滚全局状态
全量对齐兜底：端上发现本地 timeline 与服务端版本差距过大时（如离线 2 小时），丢弃本地状态，用游标从服务端重新拉取
未读计数最容易崩的地方：大 V 发一条内容，1000 万粉丝的未读数全部 +1。如果每个粉丝的未读 key 都是 INCR，就是 1000 万次 Redis 写。解法：未读不做实时 INCR，改为读时计算（ZCOUNT 水位以上的条数）——水位以上通常不超过几十条，ZCOUNT 是 O(logN)，读一次的成本远低于维护 N 个计数器。
模块 6

推荐排序介入点与回拉补洞

纯时间序的 Feed 已经很少见——插入率、互动量、时效性都会干预排序。关键在于：排序介入点放在哪一层，决定了成本和效果。

6.1 三个介入点

介入点做法代价与效果
时间线层
（最轻）		发布时给 score 加权重：score = create_time + boost，boost 由作者等级/内容质量决定零读成本，但 boost 规则静态，无法个性化
合并层
（主流）		拉取 N 屏候选（如 200 条），用模型重排取前 20读时多花 10~30ms 推理，可个性化，业界主流
召回层
（最重）		不读 timeline，直接从推荐系统拉候选（兴趣向量 + 协同过滤）变成推荐流，Feed 只作为一路召回源
# 合并层重排的标准流程
# 1. 从 timeline 拉 200 条候选（10 屏）
# 2. 粗排过滤：已读过滤、低质过滤、作者拉黑过滤（O(N)，微秒级）
# 3. 精排模型：输入 (用户画像, 作者特征, 内容特征, 上下文) → 预估点击率
# 4. 取 top 20 返回，剩余 180 条丢弃或缓存

# 工程细节：粗排过滤必须在精排之前，否则浪费 90% 的推理算力
# 精排结果要带分数缓存 30~60 秒，同一用户连续翻页不重复推理

6.2 回拉补洞机制

Timeline 只存最近 1000 条，用户翻到底部时数据出现"空洞"（关注的人 3 天前发的内容不在 ZSet 里）。回拉就是读时按需补齐：

检测空洞：游标翻到 ZSet 末尾（返回条数 < page size），或返回内容中相邻两条的时间差 > 阈值（如 1 小时），判定需要回拉
回拉关注列表：取用户的关注对象（200 人），并发查各人的 user_post_index（MySQL）或 zvip 缓存（大 V），时间范围 = (游标 score, 游标 score - 补洞窗口)
合并排序：回拉结果与 timeline 尾部结果归并，按 (score, id) 排序后取一页，返回的游标推进到新的 (score, id)
防抖：回拉成本高（200 次索引查询），同一用户的回拉结果缓存 5 分钟；连续翻页时不重复回拉同一窗口
回拉的本质：写扩散是"空间换时间"（每个粉丝一份），回拉是"时间不够时用计算补"。1000 条 ZSet 覆盖普通用户 1~2 周的消费量，只有"考古式"翻页（看一个月前的内容）才会触发回拉，占比 < 1%，所以高成本可接受。
模块 7

热点与容量估算

Feed 的热点分两类：内容热点（一条爆款被千万人同时读）和事件热点（突发事件导致流量毛刺）。容量估算要按峰值 3 倍设计。

7.1 热点内容与突发热点

热点类型现象对策
爆款内容单条内容 QPS 达 10万+，全部走同一个 content_id 缓存 key多级缓存：本地缓存（Caffeine，1~5s TTL）+ Redis；CDN 缓存图片/视频
大 V 直播/发文发布瞬间 1000 万粉丝同时刷新，timeline 读取 QPS 尖刺读写分离（读从库）；请求合并（singleflight，相同请求只查一次）
突发事件社会热点导致全站流量 ×3，大 V 粉丝集中刷新降级开关：关闭精排模型只按时间序；关闭非核心功能（未读数、推荐）
缓存击穿大 V 内容缓存过期，千万请求穿透到 DB逻辑过期：key 永不过期，值内嵌过期时间，异步重建

7.2 容量估算完整算例

===== 输入参数（中型社交产品，上线第 2 年）=====
总用户     = 5000万，DAU = 1000万（20%）
人均关注   = 200（其中大 V 20 人，普通用户 180 人）
人均粉丝   = 200（分布极度不均：头部 1% 用户占 50% 边）
发布率     = 0.5 条/人/天 → 总发布量 = 1000万 × 0.5 = 500万条/天
刷新行为   = DAU 每天打开 App 10 次，每次下拉刷新 3 次 → 30 次/人/天

===== 写扩散链路（普通用户）=====
普通用户发布（粉丝<1万）的内容量 = 500万 × 99% = 495万条/天
扇出写入 = 495万条 × 平均粉丝 180 = 89.1亿次 ZADD/天
QPS = 89.1亿 / 86400 = 10,300 次/秒（均值），峰值按 3 倍 = 31,000 QPS
Redis 集群：单机 8万 写 QPS（保守值）→ 31,000/80,000 < 1 台
但大 V 突发 + 重试 + 冷启动 → 预留 6 个分片（N=6），每片一主一从

===== 读链路 =====
Feed 读 QPS = 1000万 DAU × 30 次/天 / 86400 = 3,472 次/秒（均值）
峰值（晚间 8-10 点集中 40%）= 3,472 × 3 = 10,400 QPS
每次 Feed 读 = 1 次 ZREVRANGEBYSCORE + 1 次批量 mget 内容
内容读取 P99 < 20ms（多级缓存命中时）

===== 存储 =====
timeline ZSet：1000万 DAU × 1000 条 × (8B member + 8B score + 16B 结构开销)
  ≈ 1000万 × 1000 × 32B = 320 GB（仅 Redis 内存，实际 ~2 倍 → 640GB）
内容表：500万条/天 × 365 天 × 1KB（含索引）= 182GB/年 → 3 年 550GB
MySQL 内容表按 content_id 分 32 库 × 32 表（每表约 500万 行/年）

===== 网络带宽 =====
每次 Feed 响应 = 20 条 × (ID + 摘要 + 图片 URL) ≈ 8KB
3,472 QPS × 8KB = 27.8 MB/s（均值），峰值 83 MB/s → 千兆网卡 ×2 或万兆
图片/视频走 CDN，不回源到 Feed 服务
容量规划的三个反直觉点：① timeline 的 Redis 内存比内容表大 3 倍以上——冗余存储的代价必须在预算内；② 读峰值和写峰值不同时发生——发布高峰在白天，读取高峰在晚间，容量不能简单相加；③ 大 V 粉丝数是长尾分布的——1% 用户占 50% 关注边，容量必须按头部设计，按均值设计会被头部打穿。
模块 8

十个线上坑

1
用 offset 做 Feed 分页
深分页性能断崖 + 新内容插入导致重复/遗漏。必须用 (score, id) 游标分页，且翻页游标要能无缝过渡到回拉。
2
大 V 走了写扩散，扇出风暴打爆集群
千万粉丝的大 V 发一条 = 千万次 ZADD，Redis 集群瞬间饱和。大 V 必须切换拉模式，阈值通常取 1 万粉丝。
3
删除内容时做全量扇出删除
把粉丝 timeline 里的 ID 全部删一遍，又是一次扇出风暴。正确做法：timeline 只存 ID，读时用内容表 status 过滤。
4
未读计数用 INCR 实时维护
大 V 发文导致千万粉丝未读数同时 +1，Redis 写打满。改为读时 ZCOUNT 水位线计算，写时零成本。
5
回拉时把用户所有关注对象的近期内容全量拉取
关注 200 人 = 200 次索引查询，回拉一次 P99 直接破秒。必须限制时间窗口（如只看 24 小时）、并发查询、结果缓存 5 分钟。
6
timeline 无上限，ZSet 无限增长
老用户 timeline 到几十万条，ZREVRANGEBYSCORE 翻页变慢、内存爆炸。必须 LTRIM/ZREMRANGEBYRANK 裁到 1000 条，配回拉兜底。
7
精排模型在每次翻页时都跑一遍
用户连续翻 10 页 = 10 次模型推理，GPU 成本和延迟都不可接受。候选集排序结果要缓存 30~60 秒，翻页直接消费缓存。
8
内容 ID 不用雪花号，用数据库自增
自增 ID 泄露业务量、且跨库分表时无法直接从 ID 推时间序。必须用雪花 ID，让 ID 高 41 位就是毫秒时间戳，时间线和游标全部复用它。
9
关注/取关时不补拉或清理 timeline
新关注一个大 V，他的历史内容不在自己 timeline 里，翻页时才暴露空洞；取关后内容残留。关注变更要触发"补拉近期 + 清理存量"。
10
多端已读状态直接覆盖，旧设备回滚全局
平板离线 2 小时后上线，用本地旧水位覆盖了手机的新水位。已读状态必须带单调 version，服务端只接受更大 version 的更新。
自测

六道题

1. 一个有 2000 万粉丝的大 V 发布了一条内容，系统应该采用哪种方式让粉丝看到？
正确答案：拉模式。写扩散需要 2000 万次 ZADD，约 200 秒才能写完（单机 10w QPS），期间粉丝看不到，且会把 Redis 写满。大 V 内容只写一份索引，读时按需聚合，是微博/Twitter 的标准做法。
2. Feed 分页坚决不用 offset 的核心原因是什么？
正确答案：性能 + 正确性双重问题。offset=10000 时 MySQL 要扫描丢弃前 10000 行；更致命的是 Feed 实时新增，第 2 页的 offset 会被新内容顶偏，用户看到重复内容。游标 (score, id) 同时解决两个问题。
3. 用户删除自己 3 天前发的一条内容，写扩散模式下最合理的做法是？
正确答案：只改 status，读时过滤。timeline 里只存 ID，读的时候用内容表 status 过滤已删内容。做删除扇出等于再打一次集群，而且粉丝可能还没读到就删了索引，逻辑上也不对。
4. 关于未读计数，以下哪种方案在大 V 发文时最稳？
正确答案：水位线 + 读时计算。INCR 方案在大 V 发文时要写千万个计数器；读时 ZCOUNT 是 O(logN)，且天然与翻页一致。客户端本地计数无法多端同步。
5. 用户的 timeline ZSet 只保留了最近 1000 条，当他翻到底部还想继续看，应该？
正确答案：回拉补洞。timeline 是有损缓存（只存热点），真相在内容索引表里。翻到底部时按游标的时间窗回源查询，控制窗口大小和并发，并对回拉结果做短缓存防抖。
6. 某产品 1 亿 DAU、人均关注 200、人均日发布 0.5 条，若纯写扩散，每天的 timeline 写入量约为多少？
正确答案：约 100 亿次/天。每次发布要扇出到全部粉丝：1亿 DAU × 0.5 条 = 5000 万条发布，每条 × 200 粉丝 = 100 亿次 timeline 写入，均值约 11.6 万 QPS，峰值 3 倍需要 Redis 集群分片承载。

术语表

术语一句话解释
Feed / Timeline信息流，按时间排序的内容列表，本质是内容+关注关系算出的视图
推模式（写扩散）发布时把内容 ID 写入所有粉丝的 timeline，读时 O(1)
拉模式（读扩散）发布时只写一份，读时聚合所有关注对象的内容，写轻读重
推拉结合普通用户推、大 V 拉的混合架构，业界主流
扇出 / Fan-out一条内容分发到的粉丝数量，扇出量 = Σ粉丝数
大 V粉丝数超阈值（通常 1 万）的用户，必须走拉模式
游标分页用上一页末条的 (score, id) 定位下一页，深分页不退化
回拉 / 补洞timeline 只存热点，翻到底时回源查索引补齐历史内容
水位线用户已读到的最大 score，未读数 = 水位以上的条数
读扩散推送timeline 更新时长连接推送增量 ID 到在线端，与"读扩散"是两回事
重排 / 精排拉取多屏候选后，用模型预估点击率重排取前 N
singleflight请求合并：相同 key 的并发请求只查一次，防缓存击穿
逻辑过期缓存 key 永不过期，值内嵌过期时间，过期后异步重建
雪花 ID分布式 ID，高 41 位是毫秒时间戳，全局有序且自带时间语义
ZSetRedis 有序集合，member=content_id, score=create_time，timeline 的载体
内容索引表user_id → content_id 的倒排表，读扩散和回拉的数据源
拉黑/过滤读时过滤不看的内容，粗排在精排之前，省 90% 推理算力
降级开关突发流量时关精排、关未读、关推荐，只保主链路
