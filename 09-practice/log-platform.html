二十分钟学透日志平台设计

日志平台是运维和排障的地基，也是公司里最容易被低估成本的系统（日增 10TB 的存储账单能吓死 CFO）。这篇讲透六段管道（采集→缓冲→处理→存储→查询→告警）、三种存储选型、和一套能落地的容量账。

开始前

日志平台解决什么问题

日志平台要回答运维和开发的三个日常问题："昨晚那个错误是谁打的"、"这个接口的 RT 为什么涨了"、"这次发布有没有引入异常"。所有设计都围绕"存得下、查得快、花得起"这个不可能三角展开。

采集 Agent Kafka 缓冲 解析处理 存储引擎 查询检索 告警联动
六段管道的职责边界
采集 每台机器一个 agent，读文件、转发缓冲 Kafka 削峰解耦、故障可重放处理 解析、丰富、脱敏、采样存储 ES / Loki / ClickHouse 按场景选查询 关键词检索 + 字段聚合告警 错误率突增、关键词命中

本篇算例参照系：1000 台容器（每台约 10 个 Pod），日增日志 10TB，峰值写入 100 万行/秒，查询以"最近 24 小时 + 关键词 + 服务名过滤"为主，QPS 约 50。保留要求：热 7 天全量检索、温 30 天、冷 1 年。

三个反直觉的成本事实（先记住）：① 日志原始量:存储量 ≈ 1:1.8~2.5（ES 索引膨胀），10TB/日存一年要 5PB 级；② 80% 的日志从来没人查（debug 级），直接丢弃或采样能省掉一半成本；③ 存储选型比"上 ES"更影响账单——同数据量 Loki 成本通常是 ES 的 1/5。
模块 1

采集层：Filebeat / Fluentd / Vector

采集 agent 跑在每一台业务机器上，第一纪律是不能影响业务：CPU < 5%、内存 < 200MB、磁盘 IO 可控。

维度FilebeatFluentdVector
语言GoRuby + CRust
常驻内存低（20~50MB）高（150MB+）低（30~60MB）
吞吐（单机）~10 万行/s~2~5 万行/s~30 万行/s
插件生态中等（官方模块 + 社区）极丰富（500+ 插件）中等（增长快）
配置语言YAML自定义 DSLTOML/YAML + VRL 脚本
背压控制有（队列满自动降速）有有（磁盘缓冲队列）
适用场景云原生/K8s 默认之选复杂处理、遗留系统高性能、统一采集+处理

Filebeat 生产配置（K8s DaemonSet）

# filebeat.yml —— 生产必须调的几个点
filebeat.inputs:
  - type: filestream        # 7.16+ 用 filestream 替代 log 输入，状态管理更稳
    id: app-logs
    paths:
      - /var/log/pods/*/*/*.log
    parsers:
      - container: ~        # 自动解析 K8s 容器日志格式（CRI）
    prospector.scanner.symlinks: true

processors:
  - drop_fields:            # 丢弃无用字段，省 20% 存储
      fields: ["agent.ephemeral_id", "log.offset"]
  - add_fields:             # 打上集群/环境标签，检索全靠它
      target: labels
      fields:
        cluster: prod-cn-east
        env: production

queue.mem:                  # 内存队列（背压缓冲）
  events: 4096
  flush.min_events: 512
  flush.timeout: 2s

output.kafka:               # 输出到 Kafka，不直连 ES（原因见模块 2）
  hosts: ["kafka-01:9092", "kafka-02:9092"]
  topic: 'app-logs-%{[labels.cluster]}'
  partition.round_robin: true
  required_acks: 1          # leader 确认即可，平衡可靠与延迟
  max_message_bytes: 1048576  # 1MB 上限，超过直接拒（防超大行）
采集层两个必须：① 限流——应用日志突发（如误开 debug）时 agent 要能顶住不拖垮机器：queue.mem 满了就走背压降速，而不是无限吃内存；② multiline 合并——Java 堆栈是多行，不合并的话一次异常在检索里碎成 50 行，根本没法看。multiline.pattern: '^\s' + multiline.negate: false + match: after。
模块 2

Kafka 缓冲：削峰与可重放

为什么不 agent 直写存储？因为日志流量有剧烈峰值，而存储的消费能力是平滑的。Kafka 在中间做缓冲，是日志平台的标准架构。

没有缓冲会怎样（算例）

// 峰值 100 万行/s，ES 集群稳定消费能力 40 万行/s
直写：超出的 60 万行/s → ES 拒绝写入 → agent 重试 → 雪崩

// 有 Kafka：
写入：100 万行/s 全部进 Kafka（Kafka 单集群可扛百万级/s）
消费：按 40 万行/s 匀速消费，堆积 60 万行/s

// 堆积量与恢复时间：
持续峰值 10 分钟 → 堆积 3.6 亿条
回填时间 = 3.6 亿 / 40 万每秒 ≈ 900 秒 = 15 分钟
// Kafka 磁盘成本：3.6 亿 × 1KB ≈ 360GB 峰值缓冲（保留 3 天 ≈ 1TB 磁盘）

Kafka 关键配置决策

决策点生产选择与理由
分区数与键按服务名做 key（同服务进同分区，保序）。分区数 = 峰值吞吐/单分区 10MB/s，算例给 24 分区
副本与 acks3 副本，min.insync.replicas=2。日志允许少量丢失，不为强一致牺牲吞吐
保留策略时间保留 3 天（缓冲 + 故障重放窗口），不用大小保留（流量波动大）
压缩compression.type=lz4——CPU 友好，压缩率约 3:1，省 2/3 磁盘
topic 规划按业务域分：logs.app / logs.access / logs.audit，隔离互相的流量突增
Kafka 带来的第二个红利：可重放。处理逻辑改错了（解析规则写错）、存储端故障丢了数据，可以把 Kafka 里的原始日志重新消费一遍，从任意 offset 开始。这是"agent 直写存储"永远做不到的——重放能力决定了日志平台的容错上限。
模块 3

解析与丰富

原始日志是给人看的文本，存储引擎要的是结构化字段。解析层的目标：把一行行文本变成带 timestamp/level/service/trace_id/message 的记录。

解析策略：JSON 优先，Grok 兜底

// 策略一：应用直接输出 JSON 日志（最优，零解析成本）
// logback/log4j2 配 JSON layout，或直接用 logstash-logback-encoder
{"ts":"2026-10-18T14:23:01.482Z","level":"ERROR","service":"order-api",
 "trace_id":"a1b2c3d4","msg":"payment timeout, orderId=9527"}

// 策略二：非结构化文本，用 Grok（正则别名库）解析
输入："2026-10-18 14:23:01 ERROR [order-api] payment timeout orderId=9527"
Grok：%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} \[%{DATA:service}\] %{GREEDYDATA:msg}
输出：ts=2026-10-18 14:23:01, level=ERROR, service=order-api, msg=payment timeout...

// 策略三：解析不了的原样存 message 字段 —— 绝不丢弃
// 解析失败率必须监控（> 1% 告警），说明应用改日志格式没同步

字段标准化与丰富

  • 标准化：全公司统一字段名（对标 ECS 规范）：timestamp / log.level / service.name / trace.id / message。不标准化的后果：A 团队叫 svc，B 团队叫 app，跨服务检索永远对不齐
  • 丰富（enrich）：IP → 地域（GeoIP 库）、UA → 设备类型、容器 ID → Pod/Service 名（K8s API 缓存）、trace_id → 关联链路追踪
  • 脱敏：正则替换敏感信息——手机号 1[3-9]\d{9} → 138****8888、身份证、银行卡。这是合规红线，必须在入库前完成
  • 采样与丢弃：DEBUG 级日志采样 1%（全存也没人查）、健康检查日志（GET /healthz）直接 drop。这两步能省 30%~50% 存储
多行日志必须在 agent 层合并，不能在解析层猜：Java 异常堆栈、Python traceback 都是多行。如果 agent 按行切开，解析层拿到的是一堆没有上下文的碎片。Filebeat 的 multiline 配置是所有 Java 服务上日志平台的第一个必改项。
模块 4

存储选型：ES vs Loki vs ClickHouse

这是日志平台最贵的一个决策。三种引擎的架构哲学完全不同，成本差一个数量级。选型错误 = 每年几十万冤枉钱。

维度ElasticsearchLokiClickHouse
索引方式全文倒排索引（每个 token 建索引）只索引标签（service/env 等少量字段）列式存储 + 跳数索引
关键词检索极强（毫秒级任意词）弱（要扫描压缩块，grep 式）中（token 分词检索）
聚合分析中（高基数聚合会 OOM）弱极强（亿级 GROUP BY 秒出）
存储膨胀高（1GB 原始 ≈ 1.8GB 索引+数据）低（压缩 5~10x，约 0.2GB）中（压缩 5~10x，约 0.15GB）
运维成本高（分片、mapping、GC 调优）低（无状态，依赖对象存储）中
适用场景排障检索（"找那条错误日志"）K8s 容器日志、成本敏感日志分析（"统计错误码分布"）

成本算例（日增 10TB，存 1 年）

// Elasticsearch：
10TB/日 × 1.8 膨胀 × 365 ≈ 6570TB ≈ 6.5 PB
// 就算只热 7 天，也需 126TB 热数据 → SSD 集群 20+ 节点，年账单数十万起

// Loki（日志体进对象存储 S3/OSS）：
10TB/日 × 0.2 压缩 × 365 ≈ 730TB，其中对象存储 90%（≈$0.02/GB/月）
730TB × 0.9 × 0.02 × 12 ≈ 15.8 万美元/年（约为 ES 的 1/4 ~ 1/10）

// ClickHouse：
10TB/日 × 0.15 × 365 ≈ 548TB，聚合查询能力反超 ES
// 适合"日志即数据"的场景：错误码分布、接口 RT 分布、用户行为分析

// 结论（业界主流组合）：
// 排障检索（最近 7 天）→ ES 或 Loki；长期归档 → 对象存储；
// 分析统计（TB 级聚合）→ ClickHouse。三件套各司其职，别指望一个引擎全包
选型的隐藏成本是运维，不是许可证：ES 的坑（分片数失控、mapping 爆炸、JVM GC、集群再平衡）能吃掉一个全职工程师。中小团队（< 50 台机器）直接用 Loki + Grafana，别碰 ES；数据量上来且检索是刚需，再上 ES；要做分析报表，加 ClickHouse。
模块 5

查询与检索优化

日志查询有两个截然不同的模式，优化手段完全相反。先想清楚你的查询是哪一种。

模式典型问题引擎与优化
点查检索"trace_id=a1b2 的日志"、"service=order 且含 timeout"ES/Loki。靠标签前缀过滤 + 倒排索引
聚合分析"各服务错误码 TOP10"、"接口 RT P99 按小时"ClickHouse。靠列式扫描 + 预聚合

ES 查询优化清单

// 1. 时间范围必须收窄（索引按天/小时切分，这是第一优化）
GET /logs-app-2026.10.18/_search
{ "query": { "bool": {
    "filter": [
      { "range": { "@timestamp": { "gte": "now-1h" } } },
      { "term":  { "service.name": "order-api" } }
    ],
    "must": [ { "match": { "message": "timeout" } } ]
} } }

// 关键点：filter 上下文（不打分、可缓存）放标签和时间，
// must 的全文检索放最后。顺序反了 = 先全文检索 10 亿文档再过滤

// 2. 高基数字段禁止聚合（如 user_id、trace_id 精确值有几亿个）
//    对高基数字段做 terms 聚合 → 每个 bucket 建 global ordinals → OOM

// 3. 深分页禁用 search_after/scroll 替代 from+size（from 10000 起性能断崖）

// 4. mapping 精打细算：只给"要检索的字段"建 keyword/text，
//    纯展示字段设 "index": false，能省 30% 索引体积

Loki 查询（LogQL）

# 标签选择器必须加（这是 Loki 的性能命门）
{cluster="prod-cn-east", service="order-api"} |= "timeout"
# 解析字段后按字段过滤（避免全文扫描）
{cluster="prod"} | json | level="ERROR" | line_format "{{.msg}}"
# 聚合（rate 是日志告警的基础）
sum(rate({cluster="prod"}[5m])) by (service)
查询优化的终极手段是"查前先想"：90% 的慢查询是因为没带时间范围或没带标签。把"最近 1 小时 + 服务名"做成查询界面的默认值，比任何索引调优都管用。另外：trace_id 点查要保证 ES/Loki 侧走 keyword 精确匹配，不要走全文检索（会被分词拆碎）。
模块 6

生命周期：热温冷与 ILM

日志的访问规律极其鲜明：昨天的日志查 100 次，上个月的日志查 1 次，去年的日志只为合规存档。分层的目标就是让数据躺在"配得上它被访问频率"的介质上。

层级介质保留能力
热SSD 节点7 天全索引、实时检索、聚合。承接 95% 查询
温HDD 节点30 天索引保留、查询慢 2~3 倍。force_merge 合并段
冷对象存储（S3/OSS）1 年可检索（需先 restore）、压缩归档。合规审计用
删除-> 1 年合规到期删除，索引快照级删除

ES ILM 策略配置

// 索引生命周期四阶段（节点角色：data-hot / data-warm / data-cold）
PUT _ilm/policy/logs-policy
{
  "policy": {
    "phases": {
      "hot":    { "min_age": "0ms",
                 "actions": { "rollover": { "max_size": "50gb", "max_age": "1d" } } },
      "warm":   { "min_age": "7d",
                 "actions": { "allocate": { "number_of_replicas": 1 },
                              "forcemerge": { "max_num_segments": 1 } } },
      "cold":   { "min_age": "30d",
                 "actions": { "searchable_snapshot": { "snapshot_repository": "oss-backup" } } },
      "delete": { "min_age": "365d",
                  "actions": { "delete": {} } }
    }
  }
}

// 索引模板绑定策略：logs-app-* 走 logs-policy
// 关键：hot 阶段 rollover 按 50GB/天切索引，避免单索引过大（检索慢、恢复难）
分层不是"到期搬家"那么简单，有两个坑：① 温层 forcemerge 是重操作（合并段吃 CPU/IO），要放在低峰期且限速；② 冷层可检索快照（searchable snapshot）是 ES 商业功能，开源版只能"恢复后才能查"（恢复 = 从对象存储拷回，小时级）。规划冷数据时先问合规：冷数据到底需不需要"在线检索"——90% 的答案是不需要，那归档到 S3 + Glacier 就行，成本再降一个量级。
模块 7

多租户、配额与告警

多租户与配额

  • 隔离粒度 = 索引前缀：logs-{team}-{service}-{date}，如 logs-trade-order-api-2026.10.18。查得到、删得掉、算得清账
  • 配额维度：每团队每日写入量上限（GB）+ 索引数上限 + 保留天数上限。超配额动作：先采样降级（DEBUG 直接丢）→ 再通知 → 最后拒绝写入（拒绝要谨慎，日志是排障刚需，逼急了他们自己搭野平台）
  • RBAC：索引级权限（交易团队看不到支付团队的敏感日志），字段级脱敏（手机号只对风控团队可见）

告警联动

# 日志告警的三类规则（与指标告警 Prometheus 互补）
1. 错误率突增：rate({level="ERROR"}[5m]) / rate(total[5m]) > 5% 持续 5min
2. 关键词命中：|= "OOMKilled" | |= "panic" | |= "payment failed"（ES: 定时查询 count 阈值）
3. 新模式出现：某服务首次出现的异常类型（聚类检测，进阶）

# 告警治理（防告警疲劳）：
# - 分级：P1 电话 + P2 群机器人 + P3 邮件日报
# - 聚合：同服务 5 分钟内相似告警合并为一条
# - 静默：发布窗口期自动静默已知错误
# - 值班认领制：没人认领的告警自动升级

# 工具链：ElastAlert2（ES）/ Grafana Alerting（Loki）/ 自研 Flink 作业
告警疲劳是真实的事故放大器：某团队日志规则太敏感，一天 200 条告警，值班直接免打扰——然后真正的 P0 事故被淹没在群里。铁律：每条告警规则上线前必须回答"触发了谁、做什么、不做会怎样"，答不上来就删掉。
模块 8

容量估算与十个坑

容量账（日增 10TB 场景，给计算过程）

// 1. 原始日志量
1000 台机器 × 每台 120KB/s × 86400s ≈ 10.4 TB/日
（业务日志:访问日志:审计 ≈ 6:3:1）

// 2. 处理后减量（解析层就该做）
丢弃健康检查 10% + DEBUG 采样 50% + 脱敏/去重 5% ≈ 留存 40%
10.4TB × 0.4 ≈ 4.2 TB/日 真正入库

// 3. 峰值写入
日常 12 万行/s，发布/故障时 3 倍 ≈ 100 万行/s（Kafka 扛，消费端 40 万行/s）

// 4. Kafka 缓冲
保留 3 天 × 4.2TB × 3:1 压缩 ≈ 38 TB 磁盘，3 副本 → 114TB（约 12 台 broker）

// 5. ES 热层（7 天）
4.2TB × 1.8 膨胀 × 7 ≈ 53 TB → SSD 节点 6~8 台（每台 8TB 可用）

// 6. 温层（30 天）+ 冷层（1 年）
温：4.2TB × 1.8 × 23 ≈ 174TB（HDD 或可检索快照）
冷：4.2TB × 0.2 压缩 × 335 ≈ 281TB → 对象存储（≈$0.02/GB/月 ≈ 6.7 万美元/年）

// 7. 查询容量
50 QPS × 平均扫描 5GB/查询 ≈ 250MB/s 读吞吐（热层 SSD 可扛）

十个线上坑

1
采集 agent 不限流，把业务机器拖垮
应用误开 debug 后日志暴涨 10 倍，agent 拼命读文件 + 发 Kafka，业务容器 CPU 被打满。队列满了必须走背压降速，agent 资源限额（limit/request）必须配。
2
多行日志没合并，堆栈碎成 50 行
Java 异常每行被当独立日志入库，检索时看不到完整堆栈。Filebeat multiline 是 Java 服务第一个必改配置。
3
单行超大日志（几 MB 的 payload dump）
ES 默认 http.max_content_length 100MB 但单文档过大照样拖慢集群；Kafka 单消息默认 1MB 直接拒。必须在 agent 层截断（truncate 到 10KB）+ 标记已截断。
4
日志时间戳混乱（容器时区、NTP 漂移）
同一台机器日志时间差几小时，跨服务链路对不齐。统一 UTC + 入库时用 Kafka 到达时间校准漂移超 5 分钟的机器告警。
5
纯文本日志，没有结构化字段
只能全文 grep，查个"order-api 的错误"要翻十万行。字段标准化（service/level/trace_id）是排障效率的分水岭。
6
不做热温冷分层，全存 SSD
10TB/日全热存储，年账单百万级。7 天前的日志查询频率是 1/100，让它躺对象存储。
7
敏感信息明文入库
手机号、身份证、密码出现在日志里直接进 ES，被检索出来就是合规事故（个保法）。入库前正则脱敏 + 定期全量扫描旧数据。
8
Kafka 分区倾斜
按服务名分区，某个大服务的日志量是其他的 100 倍，单分区打满而其他分区空闲。分区键加盐（service + hash(user_id)%N）或单独 topic。
9
ES 高基数字段聚合
对 user_id/trace_id 做 terms 聚合，global ordinals 内存爆炸，节点被 Killed。高基数字段只做精确点查，不做聚合。
10
告警规则太敏感，告警疲劳
一天 200 条告警，值班开免打扰，真正的 P0 被淹没。规则上线前必须过"触发了谁、做什么"评审，配套聚合/静默/分级。
自测

六道题

1. 日志平台在 agent 和存储之间加 Kafka 的核心原因是？
正确答案：削峰 + 可重放。峰值 100 万行/s 直写 ES（消费 40 万/s）会雪崩；Kafka 缓冲后匀速消费。额外红利：处理逻辑改错、存储故障后可以从任意 offset 重新消费原始日志。
2. 日增 10TB 日志，同数据量下存储成本最低的方案通常是？
正确答案：Loki。只索引标签、日志体压缩 5~10x 进对象存储，膨胀率约 0.2，通常是 ES（膨胀 1.8）的 1/5~1/10 成本。代价是关键词检索要扫描压缩块，慢于 ES。排障选 ES/Loki、分析选 ClickHouse、归档进对象存储，是主流组合。
3. 关于采集 agent（Filebeat）的多行合并，正确的是？
正确答案：必须配 multiline。agent 按行读取文件，不合并的话一次异常堆栈被切成几十条独立记录，解析层拿不到上下文，检索时完全没法看。这是 Java 服务接入日志平台的第一个必改项。
4. ES 查询"最近 1 小时 order-api 服务含 timeout 的日志"，正确的查询构造是？
正确答案：filter 前置。filter 上下文不打分、可缓存，先用时间 + 标签把候选集从 10 亿缩到百万级，全文检索只在候选集上跑。顺序反了等于全量扫描。深分页（from 10000+）性能断崖，要用 search_after。
5. 日志平台的"热温冷"分层，热数据一般保留多久？
正确答案：7 天热 + 30 天温 + 1 年冷。日志访问规律极其鲜明：昨天的日志查 100 次，上月查 1 次，去年只为合规。让数据躺在配得上访问频率的介质上，是成本优化的核心手段。
6. 关于日志脱敏，正确的是？
正确答案：入库前脱敏 + 旧数据补扫。日志里的手机号/身份证明文进 ES，任何有读权限的人都能检索出来，是个保法合规红线。权限控制防不住"有权限的人滥用"，脱敏是第一道防线。排障只需要掩码前后的部分字符，不影响定位。
