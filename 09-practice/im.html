二十分钟学透 IM 即时通讯系统

IM 的本质是带着序列号的长连接消息管道。难点不在"发消息"，在消息不丢、不重、不乱，在千万级连接的管理，在弱网下的对齐。这篇讲透 seq 机制、读写扩散、心跳重连三大命门。

开始前

IM 的四个核心概念

所有 IM（微信、Slack、Discord）都建立在四个概念上。这篇的所有设计，最终都落回这四个词。

长连接
客户端与服务端的持久 TCP/WebSocket 通道。一台网关机器维持 5~10 万条，是 IM 的地基
消息
有会话内 seq（严格递增）和全局 msg_id（雪花）。两个 ID 各司其职：排序 + 去重
会话
单聊或群聊的消息容器。conversation_id 是分库分表键、seq 的作用域、未读的作用域
未读
用 seq watermark（已读到的最大 seq）表示，不是计数器——避免并发更新丢失
整体分层（自底向上）
接入层 长连接网关（无状态，只管道协议）逻辑层 消息服务 / 会话服务 / 群服务 / 推送服务存储层 消息库（分片）+ 会话库 + Redis（在线状态/最近消息）外部 APNs / 厂商推送通道

本篇算例参照系：注册用户 5 亿、DAU 5000 万、峰值同时在线 1000 万、人均日发 30 条消息。单聊:群聊 ≈ 8:2，平均群 200 人。

模块 1

长连接管理：网关、心跳、重连

接入层只做一件事：把连接管好，把协议听懂，把消息转给逻辑层。它必须无状态——任何机器宕机，客户端重连到别的机器就能继续。

在线状态怎么存

# user_id → 所在网关 + 连接信息，存 Redis（带 TTL，断连自动过期）
SET online:{user_id} "gateway-07:conn-9527" EX 90
# TTL = 90s ≈ 3 个心跳周期，心跳每 30s 续一次；断连不续，90s 后自动判离线

# 一条消息的路由过程：
# 1. A 发消息 → 逻辑层写入消息库，拿到 seq
# 2. 逻辑层查 online:{B} → 得到 B 在 gateway-07 上
# 3. 逻辑层把消息投给 gateway-07（RPC/MQ）
# 4. gateway-07 通过 B 的长连接推送；B 回 ACK

心跳：为什么必须有，间隔怎么定

参数典型值说明
心跳间隔（客户端发）30s（WiFi）/ 5min（移动网络）移动网络省电优先，用厂商长连或推送通道保活
服务端超时90s 无任何数据≈ 3 个周期，容忍 2 次抖动，减少误杀
NAT 超时（运营商）5min 左右（部分 30s）心跳的根本作用：保活 NAT 映射。没有心跳，NAT 表项过期后静默丢包，双方都以为连接活着

断线重连：指数退避 + 随机抖动

// 重连策略：防止服务端故障时百万客户端同时重连（惊群）
int delay = Math.min(30_000, (1 << retryCount) * 1000);  // 1s,2s,4s...封顶 30s
delay += random(0, 1000);                              // 抖动，把重连打散
scheduleReconnect(delay);

// 重连成功后第一件事：同步，不是等新消息
onReconnect() {
  // 1. 重新登录，拿服务端确认的"每个会话的最新 seq"
  // 2. 本地逐会话对比：缺哪段就拉哪段（按 seq 范围拉历史消息）
  // 3. 把断线期间收到的推送（厂商通道）与本地库去重合并
}
静默断连是 IM 第一大体验杀手：NAT 超时后，客户端以为在线（实际 TCP 已死），服务端以为在线（Redis TTL 还没到），消息发出去石沉大海。解法三件套：心跳保活 + 心跳超时主动断 + 发送方对"长时间无 ACK"的消息走离线/推送兜底。

多端同步

  • 一条消息要推到该用户的全部在线端（手机 + PC + Pad），每端是独立连接、独立 seq 游标、独立 ACK
  • 每端独立维护"已同步到哪个 seq"：手机读到 seq=100，PC 可能还在 seq=60，互不影响
  • 登录互踢策略要产品定：手机端单点登录（微信模式，PC 与平板可共存），或全端共存。被踢的端收到"kick"帧后断链
模块 2

消息投递语义：至少一次 + 幂等

IM 的投递语义业界的共识答案：至少一次（at-least-once）+ 客户端幂等去重。为什么不用恰好一次？网络不可靠，"恰好一次"需要两阶段提交级别的开销，不值当。

三种语义对比

语义含义IM 适用性
至多一次发出去就不管，可能丢只适合"正在输入"这类状态提示，丢了无所谓
至少一次未收到 ACK 就重推，可能重复消息正文用这个，配合客户端去重，事实上的恰好一次
恰好一次不丢不重工程代价极高，IM 不用。重复由客户端按 msg_id 去重解决

seq 机制：排序与缺口检测

// 消息的两个 ID，缺一不可
msg_id  = 雪花 ID          // 全局唯一，客户端去重键（重推时同一个 msg_id）
seq     = 会话内递增整数    // 每会话独立计数：1,2,3,4... 用于排序 + 缺口检测

// 收到消息的处理（客户端）
onMessage(msg) {
  if (seenMsgIds.contains(msg.msg_id)) return;      // ① 幂等去重
  if (msg.seq == lastSeq + 1) {           // ② 正好接上
    appendAndRender(msg); lastSeq = msg.seq;
    flushPendingBuffer();               // 把缓冲里等待的消息补上
  } else if (msg.seq > lastSeq + 1) {     // ③ 有缺口，先缓冲
    pendingBuffer.put(msg.seq, msg);
    requestMissing(lastSeq + 1, msg.seq - 1);  // ④ 主动拉取缺失段
  }
  // seq < lastSeq+1 的旧消息直接丢弃
}

// 关键不变量：会话内 seq 连续。出现缺口 = 中间有消息丢了，必须补拉，
// 否则会话记录永久缺失一段（用户永远看不到那条消息）

ACK 与重推

# 服务端侧状态：每个连接维护"已 ACK 的最大 seq"
# 推送带 seq → 客户端回 ACK(conversation_id, max_seq) → 服务端记录
# 重推策略：消息发出 5s 未收到 ACK → 重推；重推 3 次仍无 ACK → 转离线推送
# 断线重连后：客户端上报本地 lastSeq，服务端从 lastSeq+1 开始补推

# 注意：ACK 是"最大连续 seq"，不是逐条 ACK（逐条 ACK 在弱网下放大流量）
# 但群聊里"缺 seq=3 但已收到 4,5"时，ACK 只能报到 2 —— 这是正确的行为

已读回执

  • 用户读到某会话的最新消息 → 上报 read(conversation_id, read_seq)
  • 服务端更新该用户在该会话的 watermark，并把 read_seq 推送给对方（单聊显示"已读"）
  • 已读不是消息，是状态：允许丢失、允许乱序，最终以最大 read_seq 为准
  • 群聊一般不展示"谁已读"（500 人群 500 条回执是灾难），只展示未读数
模块 3

消息存储：写扩散 vs 读扩散

这是 IM 存储最核心的决策。一条群消息，要么给每个成员写一份（写扩散），要么只写一份让大家来读（读扩散）。两者的写读成本完全相反。

维度写扩散（收件箱模式）读扩散（时间线模式）
写入成本高：200 人群一条消息写 200 行低：一条消息只写 1 行
读取成本低：直接读自己的收件箱，按 seq 范围查高：读时要聚合会话时间线 + 判断可见性
适用场景单聊（2 行/条）、小群（≤ 500 人）大群（千人以上）、直播间、频道
成员变更新成员进群前的消息不会出现在其收件箱新成员能看到进群前的历史（要按加群时间过滤）
删除/撤回要更新所有收件箱（ costly）只改一份，所有人生效

扩散比算例（直接决定选型）

// 场景：200 人群，每秒 10 条消息
写扩散：10 条/s × 200 行 = 2000 行/s（单会话）
读扩散：10 条/s × 1 行  = 10 行/s

// 场景：5000 人大群，每秒 5 条消息
写扩散：5 × 5000 = 25000 行/s（单群就吃掉一个分片的写能力）
读扩散：5 × 1    = 5 行/s（读时聚合，5 千人各拉一次）

// 结论（业界通用分界线）：
// < 500 人：写扩散（读快，删改可控）
// > 500 人：读扩散（写不起）
// 微信/Slack 的实际做法：单聊写扩散，群聊按规模切换，超大群读扩散

历史消息拉取

# 拉取协议：按 seq 游标分页，禁止 offset 深分页
GET /history?conversation_id=X&from_seq=1050&count=20

# 存储布局：
# - 最近 100 条：Redis（SortedSet，score=seq），毫秒级
# - 全部历史：MySQL 按 conversation_id 哈希分 128 库，索引 (conversation_id, seq)
# - 3 个月以前：归档 HBase/TiDB，查询走异步通道

# 为什么禁止 OFFSET 分页：
# LIMIT 1000000, 20 要扫并丢弃 100 万行，深翻页直接打爆 DB
# 正确做法：WHERE seq < last_seen_seq ORDER BY seq DESC LIMIT 20（游标翻页）
消息表设计三原则：① 分片键是 conversation_id（同一会话的消息落在同一分片，seq 分配才能连续）；② 索引就是 (conversation_id, seq)，不要加多余索引（写放大）；③ seq 由会话维度的发号器分配（Redis INCR + 定期持久化基准值，宕机丢几十个号可接受，绝不可回退）。
模块 4

群聊：成员、扩散比与未读

群聊的所有复杂度都来自一个数字：成员数 N。N 决定了扩散模型、未读策略、推送策略。

群规模存储模型关键策略
小群（≤ 200）写扩散成员全量内存缓存；消息直接推送到每个成员的连接
中群（200~2000）写扩散 + 批量推送按网关聚合（一次 RPC 推给网关，网关扇出到本机连接）
大群（2000~2万）读扩散未读只维护"最近 N 个会话"；成员拉取改增量同步；消息不进收件箱
超大群 / 频道读扩散 + 只读副本类直播形态，消息可丢失（演示"正在输入"级容忍），历史按需拉

群成员管理

-- 群成员表：按 group_id 分片
CREATE TABLE group_member (
  group_id  BIGINT NOT NULL,
  user_id   BIGINT NOT NULL,
  role      TINYINT,        -- 0成员 1管理员 2群主
  join_seq  BIGINT NOT NULL,   -- 入群时的会话 seq（可见性边界）
  PRIMARY KEY (group_id, user_id)
);

-- join_seq 的意义：读扩散模型下，新成员可见"入群时刻之后"的消息
-- 拉历史时 WHERE seq >= join_seq，天然过滤，不需要额外判断

-- 成员推送的扇出优化：
-- 不要 for member in members: rpc_push(member)  ← N 次 RPC
-- 而是 group_members_by_gateway() → rpc_push(gateway, [user_ids]) ← 网关数次 RPC

未读数的正确表示：seq watermark

# 错误做法：未读计数 +1/-1（并发更新丢失、撤回消息无法回退）
# 正确做法：每用户每会话维护 read_seq（已读到的最大 seq）
未读数 = 当前会话 max_seq - read_seq

# 好处：
# - 天然幂等：read_seq 重复设置无副作用
# - 撤回消息：max_seq 不变，未读数自动正确
# - 多端同步：每端本地存自己的 read_seq，互不干扰
大群未读的坑：万人群里 9990 人未读，如果给每人生成一条"未读数变更"通知，就是近万次写。解法：大群不推送未读变更，客户端打开会话时按 max_seq - read_seq 现场算。未读推送只对"小群 + 单聊"开放。
模块 5

离线推送

消息到达时用户不在线，就要走推送通道。核心原则：先查在线状态，在线走长连接，不在线走厂商通道。

查询在线状态：逻辑层查 online:{user_id}。命中 → 走长连接推送；未命中 → 进入离线流程
离线消息入库：消息已写入消息库（seq 已分配）。用户上线后按 seq 增量同步，不依赖推送内容
发厂商通道：iOS 走 APNs；Android 国内走厂商通道（小米/华为/OPPO/vivo/FCM），不能用自建长连——会被系统杀进程，且各厂商Push SDK要求接入
内容脱敏：推送 payload 不直接放消息原文（锁屏可见=隐私泄露），放"您有 1 条新消息"或通用文案，点击进 App 再拉取

各平台通道对比

通道到达率限制与注意
APNs（iOS）高payload ≤ 4KB；有频率限制；必须处理 token 失效（换机/卸载）回调
厂商通道（Android）中高各厂商配额不同（华为/小米较宽松）；需维护 token 注册表；通知栏样式受限
自建长连保活低国内 Android 基本不可行（厂商省电策略杀进程），不要作为主方案
短信/语音呼叫极高仅用于极高优先级（验证码、安全告警），成本高
推送与消息库的关系不能反：消息的"真相"永远是消息库 + seq，推送只是唤醒手段。永远不要依赖推送 payload 传递完整消息内容（丢 payload = 丢消息）。正确链路：推送只带"有新消息"提示 → 用户打开 App → 客户端按本地 lastSeq 做增量同步 → 从服务端拉取真实消息。
模块 6

音视频通话：架构差异

音视频通话复用 IM 的长连接做信令（邀请、振铃、挂断），但媒体流走完全独立的技术栈。两者延迟要求差两个数量级。

维度IM 消息音视频通话
传输协议TCP/WebSocket（可靠）UDP + RTP/RTCP（实时优先，容忍丢包）
延迟目标100ms~1s 可接受< 400ms 端到端（ITU 标准），超过就能感到对话迟滞
丢包处理重传（TCP 或应用层 ACK）不重传（来不及），用 FEC 前向纠错 + NACK 选择性重传关键帧
抖动处理不需要Jitter Buffer（抖动缓冲，通常 40~200ms 动态调整）
编解码无Opus（音频）/ H.264、H.265、AV1（视频），码率自适应 100kbps~4Mbps

通话拓扑

  • P2P（1v1 首选）：媒体不经过服务器，STUN 打洞直连。成本最低，延迟最小；打洞失败回落 TURN 中继
  • SFU（多人通话主流）：服务端只转发不混流，每路流独立订阅。支持 Simulcast（大小流，弱网用户订阅小流）。Zoom/Google Meet/腾讯会议均为此架构
  • MCU（合流）：服务端混音合成一路。客户端最简单，但服务端 CPU 成本极高，仅用于录制/直播场景

信令流程（复用 IM 长连接）

// 一次呼叫的信令序列（全部走已有的 IM 消息通道，带 msg_id + seq）
A → B: INVITE (sdp_offer, call_id)        // 邀请 + 媒体描述
B → A: RINGING                            // 振铃中（触发推送）
B → A: OK (sdp_answer)                    // 接听 + 应答
A ↔ B: ICE candidate 交换（N 条）          // 打洞候选地址
A ↔ B: RTP 媒体流（UDP 直连或经 SFU）      // 媒体面与信令面分离
A → B: BYE                                // 挂断

// 关键设计：call_id 全局唯一，超时未接听（60s）自动取消；
// 弱网时信令可重传（走 IM 的至少一次语义），媒体面靠 FEC/NACK 自愈
模块 7

弱网一致性与容量估算

弱网下的三条对齐协议

  • 本地 seq 对齐：客户端本地库（SQLite）为第一真相，每会话维护本地 lastSeq。任何来源的消息（长连接推送、同步拉取、历史回填）都先过"seq 对齐"逻辑（模块 2 的 onMessage），乱序到达按 seq 重排
  • 发送方乐观更新：点"发送"立即上屏（状态：发送中），服务端 ACK 后改"已发送"，超时失败显示"重发"按钮。绝不能等服务端确认才上屏——弱网下用户以为 App 卡死
  • 本地存储 + 最终同步：客户端的消息队列带发送状态机（发送中→成功/失败），失败的消息进入待重发队列，重连后按原 msg_id 重发（服务端去重）

容量估算：千万级在线

// 输入：峰值在线 1000 万，人均日发 30 条，心跳 30s 一次

// 1. 网关机器数
单机连接上限 ≈ 10 万（4C8G，调优 file descriptor + 内核参数后）
1000 万 / 10 万 = 100 台，× 1.3 冗余 ≈ 130 台

// 2. 消息下行带宽（主要成本）
1000 万在线 × 人均 30 条/86400s ≈ 3472 条/s（平均），峰值 × 5 ≈ 1.7 万条/s
每条 200 字节 → 1.7 万 × 200B ≈ 3.4 MB/s（小到意外！因为下行靠"在线的人均频率"低）

// 3. 心跳带宽（常被低估）
1000 万 × (1 次/30s) × 50 字节 ≈ 16.7 MB/s —— 是消息带宽的 5 倍！
// 所以心跳间隔每翻倍，全网带宽省一半；移动端用 5min 心跳就是这个原因

// 4. 消息存储（写扩散，平均扩散比 2.5）
5000 万 DAU × 30 条 × 2.5 ≈ 3.75 亿行/日 × 200B ≈ 75 GB/日
热数据 90 天 ≈ 6.75 TB；归档 3 年 ≈ 82 TB（HBase/TiDB）

// 5. 消息 QPS 峰值（逻辑层）
3.75 亿 / 86400 ≈ 4340 写/s（平均），峰值 × 10 ≈ 4.3 万写/s
// 按 conversation_id 分 128 库，每库峰值 340 写/s，MySQL 轻松

// 6. seq 分配：Redis INCR，每会话独立 key
// 4.3 万 QPS 分散在百万级会话 key 上，单 Redis 集群毫无压力
容量结论（记住三个数）：① 千万在线的瓶颈是网关连接数（130 台）和心跳带宽（17MB/s），不是消息带宽；② 存储瓶颈在写扩散的扩散比——群消息占比每升 10%，存储涨 40%；③ seq 分配必须走 Redis，不能走 DB（4 万 QPS 的 INCR 会打爆 MySQL）。
模块 8

十个线上坑

1
心跳间隔太长或没有，NAT 静默断连
运营商 NAT 5 分钟超时后静默丢包，双方都显示在线，消息发出去石沉大海。心跳保活 + 发送方超时兜底转离线推送。
2
消息只有 seq 没有 msg_id，重推导致重复
至少一次语义必然有重复投递，客户端必须按客户端生成的 msg_id 去重，否则用户看到两条一样的消息。
3
seq 出现缺口不做补拉
缺 seq=4 说明中间消息丢了，直接渲染 3 和 5，用户会话记录永久缺失一段。必须缓冲等待 + 主动拉取缺失区间。
4
未读用计数器 +1/-1
并发更新丢失未读数，撤回消息时未读无法回退。用 seq watermark：未读 = max_seq - read_seq。
5
单聊用读扩散、大群用写扩散
单聊读扩散拉历史要聚合，慢；5000 人群写扩散一条消息 2.5 万行/s，吃掉整个分片写能力。按 500 人分界线切换。
6
历史消息用 OFFSET 深分页
翻到第 1000 页时 LIMIT 1000000,20 扫并丢弃百万行，DB 直接卡死。必须用 seq 游标：WHERE seq < cursor LIMIT 20。
7
推送 payload 里放消息原文
锁屏界面泄露消息内容，隐私合规事故。payload 只放"您有新消息"，点击进 App 再拉取。
8
Android 用自建长连做离线保活
国内厂商省电策略必杀进程，到达率惨不忍睹。必须接厂商 Push 通道，自建长连只做在线时的媒体面辅助。
9
服务重启后客户端同时重连（惊群）
百万连接同时打到网关，重启的服务瞬间再次被打挂。重连必须指数退避 + 随机抖动，网关要能限流新连接。
10
ACK 用逐条确认
弱网下 ACK 流量放大数倍，还容易丢。ACK 只报"最大连续 seq"，有缺口时报缺口前一个值，缺失区间走主动拉取。
自测

六道题

1. IM 消息投递，业界主流做法是？
正确答案：至少一次 + 客户端幂等。网络不可靠时"恰好一次"需要两阶段提交级开销，不值当。服务端重推可能重复，客户端用客户端生成的 msg_id 去重，组合效果等于恰好一次。
2. 会话内消息的 seq 出现缺口（收到 3 和 5，缺 4），客户端应该？
正确答案：缓冲 + 主动补拉。seq 连续是 IM 的核心不变量，出现缺口说明中间消息丢了，不补拉就会永久缺失一段会话记录。
3. 5000 人的大群，消息存储应该用？
正确答案：读扩散。写扩散下一条消息 5000 行，每秒 5 条就是 2.5 万行/s，单群吃掉一个分片的写能力。读扩散写放大为 1，读的聚合成本由客户端分页拉取承担。分界线通常在 500 人。
4. 关于心跳，说法正确的是？
正确答案：保活 NAT 映射。运营商 NAT 表项约 5 分钟过期，过期后静默丢包，双方都以为在线。心跳太频繁则移动端耗电、全网带宽暴涨（千万在线时 1 秒一次心跳 ≈ 500MB/s）。
5. 未读数的最佳表示方式是？
正确答案：seq watermark。计数器方案在并发更新下会丢失，且撤回消息时无法回退。watermark 方案天然幂等、支持多端、撤回自动正确。
6. 千万级同时在线（1000 万），单网关 10 万连接，需要多少台网关（含 30% 冗余）？
正确答案：约 130 台。1000 万 ÷ 10 万 = 100 台，× 1.3 冗余 ≈ 130。同时注意：千万在线时心跳带宽（约 17MB/s）是消息带宽的数倍，心跳间隔和连接数是容量规划的两个主参数。
