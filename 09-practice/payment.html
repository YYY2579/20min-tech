二十分钟学透 支付系统设计实战

支付系统的第一性原则：钱不能多、不能少、不能说不清。这篇讲机制：状态机与幂等怎么保正确、掉单怎么补、对账怎么兜底、签名怎么防篡改，以及那些"看起来能跑、出事就是大事"的经典坑。

开始前

支付系统的四条铁律

铁律工程含义
不许多扣（不能多）任何操作幂等。重复请求、重复通知、重复回调，只能生效一次
不许少扣（不能少）该收的钱必须收到。掉单必须被发现并补偿，不能静默丢失
账实相符（不能说不清）每一笔钱都有流水，流水和账户余额永远对得上
全程可审计每个状态迁移有日志、有时间、有操作方，事后可复盘
支付和其他系统最大的差别：错误不可回滚，只能补偿。电商少发一件货可以补发，支付多扣一次钱用户会投诉到银保监。所以支付系统到处都是"双保险"：状态机 + 幂等 + 对账，三层各抓各的漏。任何一笔资金的最终状态，必须是"三账相符"的结果：业务账、支付账、渠道账。
模块 1

支付核心架构：收单 / 退款 / 对账 / 清结算

支付平台按资金流向分四大子系统。边界清晰、职责单一，出错时能定位到具体子系统。

┌──────────────────────────────────────────────────────────────┐
│ 业务侧（订单/交易）                                          │
└───────────┬───────────────────────────────┬────────────────┘
            │ 支付请求（创建支付单）           │ 退款请求
┌───────────▼───────────────┐   ┌───────────▼───────────────┐
│  收单系统 Acquiring        │   │  退款系统 Refund           │
│  支付单管理/路由/状态机     │◄──│  原路退回/部分退/幂等      │
└───────────┬───────────────┘   └───────────────────────────┘
            │ 渠道路由
┌───────────▼───────────────────────────────────────────────┐
│  统一支付网关 Channel Gateway                             │
│  渠道适配（微信/支付宝/银联/卡组织）签名验签/报文转换       │
└───────────┬───────────────────────────────────────────────┘
            │ 异步通知（回调）
┌───────────▼───────────────┐   ┌───────────────────────────┐
│  对账系统 Reconciliation   │──►│  清结算系统 Clearing       │
│  日终渠道账单 vs 平台流水  │   │  商户结算/T+1 打款/分账     │
└───────────────────────────┘   └───────────────────────────┘
子系统核心职责关键正确性要求
收单创建支付单、路由渠道、驱动状态机、接收回调支付单全局唯一；状态只能正向迁移
退款原路退回、部分退、多次退、退到关单累计退款额 ≤ 实收额；退款单幂等
对账拉渠道账单，与平台流水逐笔勾兑，出差错单一笔不漏；长款短款都要挂账
清结算算清每商户应收（交易额 − 手续费 − 退款），生成结算单打款结算单 = 明细汇总，可重算复现
为什么对账是"最后一道防线"：状态机可能因为丢消息卡住，异步通知可能因为网络延迟没到，这些都绕不开一个事实 —— 渠道侧的账单文件是"外部真相"。每天把渠道账单和平台流水逐笔比对，任何不一致都会暴露。前面所有机制（幂等、重试、确认）是"尽量不出错"，对账是"出了错一定发现"。
模块 2

支付状态机与幂等

支付单状态机

# 支付单六态与合法迁移（只允许沿箭头方向）
CREATED ──发起渠道──► PAYING ──渠道成功──► PAID
   ▲                      │                    │
   │                      │渠道失败             │业务确认入账
   └────关单/超时──────────┘                    ▼
(CLOSED) ◄──全额退款─── REFUNDING ◄──退款中── PAID

# 关键规则
① CREATED → PAYING 必须持锁 + 幂等号（同一 biz_no 只能发起一次）
② PAYING → PAID 只能由"渠道异步通知 + 主动查询"双重确认触发
③ PAID 之后只能走向 REFUNDING，永远回不到 PAYING
④ CLOSED 是终态；PAID 是事实终态（之后只有退款能改变账）

全局唯一流水号：幂等的基石

编号作用生成规则
支付单号 pay_no平台侧唯一，关联业务订单Biz + 日期 + 序列，如 PAY2026101800123456
渠道流水号 channel_no渠道侧唯一，回调时带回渠道生成，平台存储
幂等号 idempotent_key防重复提交，DB 唯一索引兜底业务单号 + 场景（如 order_123_pay）
# 幂等的三层防线
第一层 入口：同一 idempotent_key 的请求，直接返回首次结果（不重复执行）
第二层 DB：支付单表 idempotent_key 唯一索引，Insert 冲突即拒绝
第三层 状态机：UPDATE ... SET status='PAID' WHERE pay_no=? AND status='PAYING'
           # 影响行数 = 0 说明已被别人处理过，当前请求直接返回成功

# 回调处理的标准姿势（先查后改 + 状态条件更新）
public void onChannelNotify(String channelNo, String result) {
    PayOrder o = payMapper.selectByChannelNo(channelNo);   // 先查
    if (o == null) { log.warn("未知回调"); return; }
    if (!"PAYING".equals(o.getStatus())) return;        // 已处理，幂等返回
    int n = payMapper.updateStatus(o.getPayNo(), "PAYING", "PAID"); // CAS
    if (n == 1) { notifyBusiness(o); }                          // 只有抢到锁的线程推进业务
}
"先改状态再发消息"还是"先发消息再改状态"？支付场景的标准答案是：先落库（状态改 PAID），再发消息通知业务方。消息用本地事务表或事务消息保证最终送达。反过来做（先发消息）会出现"业务已加款、支付单却没改状态"的撕裂 —— 而支付单是钱的事实来源，必须以它为准。
模块 3

掉单处理：主动查询 / 异步通知 / 对账补偿

掉单 = 用户已付款，但平台侧支付单还是 PAYING。掉单一定会发生（网络分区、渠道回调丢、进程重启），设计目标是"发现并补偿，而不是祈祷不发生"。

三道防线，逐层兜底

第一道：异步通知。渠道回调推送支付结果。要求：验签通过才处理；回调接口幂等；收到先回执（HTTP 200）再处理，处理失败进重试队列（间隔 1s/5s/30s/2min/10min/30min）
第二道：主动查询。支付单 PAYING 超过 N 秒（如 5s）未终态，定时任务按渠道查询接口拉真实结果。查询频率前密后疏（5s/10s/30s/1min……），最多查到 24h 后移交对账
第三道：对账补偿。日终渠道账单里有"成功"记录而平台是 PAYING/CLOSED → 生成差错单"长款"，补推状态或退款。这是终极兜底，T+1 发现
# 主动查询任务的关键设计
选单：SELECT * FROM pay_order WHERE status='PAYING'
     AND create_time < NOW() - INTERVAL 5 SECOND LIMIT 500;  // 分批，防一次拉爆
查询：按渠道分组，合并查询（微信/支付宝都支持批量查询，减少 API 调用）
处理：查到终态 → 走标准状态迁移（和回调同一个入口，复用幂等）
     查不到 → 累加查询次数；超过阈值（如 20 次）→ 标"异常"进人工核查队列
防重：同一支付单的查询任务加分布式锁 / 状态位，避免多 worker 重复查
防线发现时效适用场景
异步通知秒级正常路径，95%+ 的订单在这步完成
主动查询5 秒 ~ 分钟级回调丢失、回调延迟、进程崩溃
对账补偿T+1渠道系统故障、极端异常，兜底一切
用户侧的兜底：支付结果页"手动同步"。前端在 PAYING 态轮询平台侧状态（不是直接问渠道），给用户一个"我已完成支付，刷新状态"的按钮 —— 用户点一下触发一次主动查询。这是把掉单的焦虑转移给用户自助，而不是让用户找客服。
模块 4

渠道路由与统一支付网关

渠道（微信、支付宝、银联、外卡）接口各异，统一网关把差异封在一层内：对上提供标准接口，对下适配各渠道。

网关职责

职责说明
协议适配各渠道报文（XML/JSON/表单）→ 内部标准模型，双向转换
签名验签出参加签、回调验签，密钥按渠道隔离管理
渠道路由按金额/费率/成功率/渠道状态选择最优渠道，支持渠道路由表动态配置
降级切换渠道超时/故障率超标 → 自动切换备用渠道，对上层透明
限流与隔离按渠道限流（别把微信的配额打满），慢渠道隔离线程池

渠道路由策略（按优先级）

# 路由决策链（任一规则命中即返回，全不命中走默认渠道）
1. 特殊业务路由：大额(≥5000元)→银行通道；跨境→外卡渠道
2. 渠道可用性过滤：剔除"熔断中/维护中/当日限额已满"的渠道
3. 成本优先：按渠道费率升序（同费率按成功率降序）
4. 成功率均衡：近 1h 成功率 < 99% 的渠道降权，流量切给健康渠道
5. 默认渠道：兜底配置
渠道降级的真实代价是"重复扣款风险"：用户点了支付，A 渠道发起后超时，系统自动切 B 渠道重发 —— 如果 A 其实成功了（只是响应慢），用户就被扣了两笔。正确做法：超时未终态的支付单不允许自动切渠道重发，只能继续查 A 的结果；只有明确失败（渠道返回 FAIL）才能换渠道。切渠道重发必须极其保守。
模块 5

安全：签名验签、密钥管理、敏感信息

签名：防篡改、防重放

# 标准签名算法（各渠道大同小异，以 RSA2/SHA256WithRSA 为例）
1. 构造待签串：除 sign 外所有字段，按 key 字典序排序，key=value&key=value 拼接
2. 加签：用商户私钥对待签串做 SHA256WithRSA，Base64 后作为 sign 字段
3. 验签：用平台/渠道公钥对收到的 sign 验证，比对重算结果

# 必加的防重放三件套
nonce  = 随机串（一次性，Redis 存 5 分钟，重复即拒绝）
timestamp = 请求时间戳（与服务器时间偏差 > 5 分钟即拒绝）
sign  = 覆盖以上所有字段的签名
场景签名方向说明
请求发往渠道平台私钥签名 → 渠道公钥验证明"我是合法商户"
渠道回调进来渠道私钥签名 → 平台公钥验证明"回调真的来自渠道"
平台回调业务方平台私钥签名 → 业务方公钥验业务方同样要验签，防伪造到账通知

密钥管理

  • 分渠道分环境隔离：生产/测试密钥分离，一渠道一密钥，泄露可控
  • KMS 托管：私钥存 HSM/KMS，应用只持密钥 ID；支持轮换（kid 标识并存过渡）
  • 定期轮换 + 应急撤销：证书到期自动告警；疑似泄露 10 分钟内完成撤销换新
  • 访问审计：每次密钥使用记录调用方、时间、用途

敏感信息

# 敏感数据处理红线
银行卡号：存储只留后四位，全号加密（ENV 可逆加密，密钥在 KMS）
CVV2：任何时候都不存储，验完即弃
日志：请求响应中的卡号/姓名/手机号必须脱敏（掩码规则）后再落盘
传输：全链路 TLS1.2+，敏感字段额外应用层加密（即使 TLS 被破解仍有屏障）
排查：脱敏数据 + 专用解密工具（解密动作本身记审计）
血的教训：回调没验签。攻击者伪造"支付成功"通知打到你的回调接口，你没验签就改了状态、发了货 —— 钱没收到，货出去了。回调验签是支付系统不可协商的红线，且要在状态迁移之前完成。同理，回调里的一切字段（金额、单号）都要和本地支付单比对，金额不一致以本地为准并告警。
模块 6

高可用：异步化、降级、对账系统

高可用手段

手段说明
异步化回调处理"先落状态、后推业务"；业务通知走消息队列重试。支付主链路只做最小的事
渠道降级渠道故障自动切换；排队机制（支付中提示"银行通道繁忙"，而不是报错）
多活容灾支付核心双活（分渠道维度切流），数据库主从 + 强同步，RPO ≈ 0 是底线
对账兜底任何中间态丢失都能被日终对账发现并补偿，这是高可用的最后一块拼图

对账系统：日终对账与差错处理

# 对账流程（T+1 日终）
1. 下载账单：定时拉取各渠道前一交易日账单文件（对账文件接口，非交易接口）
2. 标准化：渠道账单 → 统一格式（渠道单号/金额/时间/状态/手续费）
3. 逐笔勾兑：以 channel_no 为 key，平台流水 vs 渠道账单全量比对
4. 差错分类：
   长款：渠道有、平台无（或平台未成功）→ 查支付单，补状态或发起退款
   短款：平台有、渠道无（或平台成功渠道失败）→ 以渠道为准，冲正平台状态
   金额不一致：平台 100 渠道 99.99（手续费处理差异）→ 按规则平账
   状态不一致：两边状态映射不同 → 人工核查队列
5. 差错闭环：差错单自动处理（可自动补）或转人工，全部记录处理结果
差错类型含义处理
长款渠道成功、平台未入账补记流水；若业务已关单则原路退款
短款平台成功、渠道失败/无记录以渠道为准冲正；涉及发货的触发业务回滚
金额差两边金额不一致多为手续费/汇率差，按平账规则处理并记账
单边账一边有一边没有按外部真相（渠道）为准修正，记录原因
对账的核心原则：渠道账单是外部真相，但修正动作必须幂等且留痕。自动补单、自动退款这类补偿动作，本身也要走幂等（同一差错单只处理一次），且全部记录"谁在什么时候因为哪笔对账改了什么"。没有审计的自动补偿是把对账系统变成事故放大器。

签名示例代码（Java，RSA2）

// 1. 构造待签串：字典序 + key=value&key=value
public static String buildSignStr(Map<String,String> params) {
    return params.entrySet().stream()
        .filter(e -> e.getValue() != null && !"".equals(e.getValue())
                && !"sign".equals(e.getKey()))   // 排除空值和 sign 本身
        .sorted(Map.Entry.comparingByKey())                // 字典序
        .map(e -> e.getKey() + "=" + e.getValue())
        .collect(Collectors.joining("&"));
}

// 2. 加签（私钥在 KMS，应用只调用签名服务）
public static String sign(String content, String privateKey)
        throws Exception {
    Signature signature = Signature.getInstance("SHA256withRSA");
    signature.initSign(loadPrivateKey(privateKey));
    signature.update(content.getBytes(StandardCharsets.UTF_8));
    return Base64.getEncoder().encodeToString(signature.sign());
}

// 3. 验签（回调入口，失败直接拒绝）
public static boolean verify(String content, String sign,
        String publicKey) throws Exception {
    Signature signature = Signature.getInstance("SHA256withRSA");
    signature.initVerify(loadPublicKey(publicKey));
    signature.update(content.getBytes(StandardCharsets.UTF_8));
    return signature.verify(Base64.getDecoder().decode(sign));
}
签名实现的三个经典 bug：① 待签串没排除空值字段，渠道也排除 → 签不上；② 字段值里有 & 或 = 没做转义，被拆穿；③ 验签用的是"重排后的串"而不是原始报文顺序。 safest 的做法：保留渠道原始报文，验签时用原始串；与渠道联调时用他们提供的 demo 逐字节比对。
模块 8

十个线上坑

1
重复扣款：超时后自动切渠道重发
A 渠道超时未终态就切 B 渠道重发，A 其实成功了，用户被扣两笔。超时未终态只能继续查原渠道；明确失败才能换渠道。
2
回调没验签就改状态
伪造"支付成功"通知直接入库发货。回调必须先验签，且金额与本地支付单比对，不一致以本地为准并告警。
3
幂等只做在内存层，没做 DB 唯一索引
并发下两个请求同时通过内存检查，重复创建支付单/重复入账。幂等必须有 DB 唯一索引兜底（idempotent_key），内存检查只是优化。
4
金额用浮点数，分转元算出几分钱误差
0.1 + 0.2 != 0.3，对账天天金额差。全程整数分（BIGINT），展示时再除 100；绝不用 double 存钱。
5
掉单没人管：PAYING 状态睡 30 天
回调丢了、主动查询也没配，用户付了钱订单没动。必须配"PAYING 超时扫描 + 主动查询 + 对账兜底"三道防线，缺一道就是资金事故。
6
状态机能回跳：PAID 被打回 PAYING
代码没做 CAS 条件更新，异常重试把已成功的单子改回中间态，重复入账。所有状态迁移用 UPDATE ... WHERE status='旧态'，影响行数为 0 就放弃。
7
退款不校验累计上限
并发两笔部分退，各校验"本次 ≤ 剩余"都通过，加起来超退。累计退款校验要在行锁内做（SELECT ... FOR UPDATE），或 DB 层加约束。
8
对账只对"金额"不对"状态"
渠道成功平台失败（或反之）时金额相同，对账显示平。勾兑必须 (渠道单号, 金额, 状态) 三元组全匹配，单边账也要出差错单。
9
日志里打印完整卡号和 CVV2
合规事故，PCI-DSS 直接挂。敏感字段脱敏后落盘；CVV2 验完即弃永不存储；排查用专用解密工具且解密动作记审计。
10
结算单算错，商户集体投诉
结算金额 = 交易额 − 手续费 − 退款，漏了退款或手续费精度丢了分。结算单必须可由明细重算复现，出账前和明细双向核对，历史结算单不可变（红冲另开新单）。
自测

六道题

1. 用户在微信支付页面付款成功，但平台支付单一直是 PAYING，可能的原因和正确处理是？
正确答案：主动查询 + 对账兜底。掉单的第一道防线是回调，第二道是 PAYING 超时后的主动查询，第三道是 T+1 对账。直接关单会导致"用户付了钱、订单关了"的资金差错。
2. 防止"支付状态被重复修改"最可靠的机制是？
正确答案：带旧态条件的 CAS 更新。只有数据库的条件更新是原子的，并发下只有一个线程能把 PAYING 改成 PAID，其他线程影响行数为 0，自然幂等。内存 Set 多实例失效，if 判断有竞态窗口。
3. 渠道 A 支付请求发出后 10 秒未返回，此时最安全的做法是？
正确答案：继续查 A，不换渠道。A 可能已扣款只是响应慢，切 B 会导致重复扣款。只有渠道明确返回失败，才能更换渠道重试。
4. 对账发现"渠道账单有一笔成功、平台没有对应流水"（长款），正确处理是？
正确答案：生成差错单并幂等处理。长款意味着用户可能已扣款但平台没入账，必须处理（补单或退款），且补偿动作要幂等（同一差错单只处理一次）+ 留痕。忽略是资金损失，无记录的手改是审计事故。
5. 关于支付金额的存储，正确的是？
正确答案：BIGINT 存分。浮点数有精度问题（0.1+0.2≠0.3），分位误差在对账、结算里会被放大成资金差错。整数分是支付行业标准做法，汇率换算在边界处做且保留足够精度。
6. 收到渠道的支付回调通知，处理顺序应该是？
正确答案：先验签再改状态。验签不过可能是伪造通知；金额不一致要以本地支付单为准并告警。状态更新必须用带旧态的条件更新保证幂等，全部通过后才推业务消息。
