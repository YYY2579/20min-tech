二十分钟学透 搜索系统设计实战

搜索的本质是用倒排索引把"词"快速映射到"文档"，再用打分函数把最相关的排前面。这篇讲机制：查询解析怎么分词纠错、相关性怎么调、索引怎么在实时性和成本间权衡、ES 怎么配置，以及"搜不到"和"搜得慢"两类经典坑。

开始前

倒排索引：搜索的地基

数据库用 B+ 树按"值"找行，适合精确匹配；搜索的核心场景是"按词找文档"，倒排索引就是为此而生。

# 正排 vs 倒排（3 篇文档的例子）
正排（文档 → 含哪些词）：
  doc1: "手机 快充 充电器"
  doc2: "快充 数据线"
  doc3: "充电器 车载"

倒排（词 → 含它的文档 + 位置信息）：
  "手机"   → [(doc1, pos0)]
  "快充"   → [(doc1, pos1), (doc2, pos0)]
  "充电器" → [(doc1, pos2), (doc3, pos0)]
  "数据线" → [(doc2, pos1)]
  "车载"   → [(doc3, pos1)]

# 查询"快充 充电器"→ 取两个词的交集/并集 + TF-IDF 类打分排序
# 词典 term dictionary 常驻内存（FST 压缩），posting list 按块压缩存磁盘
结构作用工程要点
Term Dictionary词 → posting list 偏移用 FST（有限状态转换机）压缩，内存占用小、查询快
Posting List词出现的文档 ID + 词频 + 位置按块（block）压缩存储，按需解压
Doc Values文档 ID → 字段值（列式）排序、聚合、高亮用，不参与倒排
Stored Fields原始文档内容返回结果时取，占磁盘大头
一个关键认知：ES 的"索引"是"库表 + 倒排 + 正排"的合体。一个 index 类似数据库的一张表，一个 document 类似一行。区别在：ES 的字段要么进倒排（text 类型，可搜）、要么进 doc values（keyword/数值，可排序聚合）、要么 stored（可取回原文）。字段类型选错是搜索效果差的第一大原因。
模块 1

搜索架构：查询解析 / 召回 / 排序 / 重排

┌─────────────────────────────────────────────────────────────┐
│ 1. 查询解析 Query Analysis                                  │
│    分词 → 词权重 → 同义词扩展 → 拼写纠错 → 意图识别           │
└──────────────────────┬──────────────────────────────────────┘
                       │ 结构化查询
┌──────────────────────▼──────────────────────────────────────┐
│ 2. 召回 Recall（毫秒级，从海量文档中取候选集）                 │
│    倒排多路召回 + 向量召回(ANN) + 业务规则召回(新品/广告)      │
└──────────────────────┬──────────────────────────────────────┘
                       │ 候选集（千~万级）
┌──────────────────────▼──────────────────────────────────────┐
│ 3. 排序 Rank（粗排 BM25 + 业务权重，输出 Top N）               │
└──────────────────────┬──────────────────────────────────────┘
                       │ Top 100~500
┌──────────────────────▼──────────────────────────────────────┐
│ 4. 重排 Rerank（精排/业务逻辑：去重、多样性、广告插位、LTR）   │
└─────────────────────────────────────────────────────────────┘
阶段目标延迟预算
查询解析把用户输入变成可执行的结构化查询< 5ms（本地词典 + 缓存）
召回尽可能全，宁可多不可漏< 50ms，多路并行
排序相关性排序，取 Top N< 30ms
重排业务目标优先：新鲜度、多样性、商业插入< 20ms，纯内存计算
"搜不到"大概率是召回的问题，"排得烂"是排序的问题。排查时先看召回：用户搜"苹果手机"，分词后"苹果"命中了水果类文档，但用户要的是电子产品 —— 这是查询理解/词权重问题，调 BM25 参数没用。先定位阶段，再调参数，是搜索调优的基本纪律。
模块 2

索引构建：全量 + 增量、实时性权衡

索引构建要平衡三个矛盾：实时性（新数据多久可搜）、成本（构建/存储开销）、稳定性（不影响线上）。

三种构建方式

方式实时性适用
全量重建小时~天级离线数据、 mapping 变更（字段类型改不了，只能重建索引）
增量近实时秒级（refresh 间隔）业务主链路写入，ES 原生 refresh（默认 1s）
实时流毫秒级日志/埋点类，Kafka → Flink → ES，或 CDC 直连

主流架构：全量 + 增量双写，别名切换

# 经典索引重建流程（零停机）
1. 建新索引：products_v2（新 mapping/新分词器）
2. 全量回填：从 DB 读历史数据，bulk 写入 v2（限速，别打爆集群）
3. 增量追平：消费 binlog/MQ，把 2 期间的数据变更同步到 v2
4. 校验：v2 文档数 vs DB 记录数，抽样比对关键字段
5. 原子切换：POST /_aliases { actions: [
     {remove: {index: products_v1, alias: products}},
     {add:    {index: products_v2, alias: products}}
   ]}                          # 别名切换是原子的，业务无感知
6. 观察 24h → 删除 v1

# 日常增量：业务写 DB → CDC(Debezium/Canal) → MQ → 消费组写 ES
# 关键：以 DB 为主，ES 可随时重建 —— ES 是"派生数据"，不是事实来源

实时性权衡的量化决策

场景refresh 间隔理由
商品/内容搜索30s用户对新品即时性不敏感，省 merge 开销
订单/工单搜索1s（默认）客服刚建的工单要马上能查到
日志检索5~30s + rollover写入量巨大，segment 小文件多是灾难
IM 消息搜索近实时 = 写引擎特殊优化秒级都不行，需专门方案（写后立即可查）
把 ES 当数据库用的代价：直接让 ES 做事实存储（不接 DB 做主库），一旦索引损坏/迁移/mapping 改错，数据恢复极其痛苦。正确姿势：DB 是唯一事实来源，ES 是从属视图，任何时候都能从 DB 全量重建。做不到这点，就不是搜索系统，是又一个不敢动的事故源。
模块 3

查询分析：分词、同义词、纠错

查询分析是"理解用户想搜什么"，中文场景的难点全在这：分词歧义、同义表达、手滑打错。

分词器选型（中文）

分词器原理适用
IK（ik_smart / ik_max_word）词典 + 算法切分，细/粗粒度通用中文，ES 生态最常用
HanLP / JiebaNLP 模型，词性/实体识别需要实体识别的场景
拼音 / 边缘 n-gram按字/拼音切输入即搜（search-as-you-type）
standard按空格/标点粗切英文够用，中文会把整句当一个词
# ES 自定义分析器：索引用细粒度，搜索用粗粒度（常见组合拳）
PUT /products
{
  "settings": {
    "analysis": {
      "filter": {
        "my_synonyms": {                          // 同义词 filter
          "type": "synonym",
          "synonyms": ["手机,电话,phone", "电脑,计算机,computer"]
        }
      },
      "analyzer": {
        "index_analyzer": {                       // 写入时细切，召回全
          "type": "custom", "tokenizer": "ik_max_word",
          "filter": ["my_synonyms"]
        },
        "search_analyzer": {                      // 查询时粗切，精度高
          "type": "custom", "tokenizer": "ik_smart"
        }
      }
    }
  },
  "mappings": {
    "properties": {
      "title": { "type": "text", "analyzer": "index_analyzer",
                 "search_analyzer": "search_analyzer" }
    }
  }
}

纠错与查询理解

能力做法工程要点
拼写纠错编辑距离（Levenshtein）+ 词频，fuzzy 查询fuzzy 只对低频词开，高频词纠错反而帮倒忙
同义词扩展索引侧或查询侧扩展（synonym graph）扩展要控制爆炸："手机"扩出 20 个同义词会拖慢查询
停用词"的了吧呢"过滤别过度，搜"什么不能带上飞机"停用词是有意义的
意图识别分类/实体模型，改写查询"苹果"搜出水果还是手机，看用户历史与上下文
同义词的两个真实坑：① 索引侧加同义词会让"手机"和"电话"的文档互相污染，搜电话出来一堆手机；② 查询侧扩展会让查询变长变慢。折中：核心同义词查询侧扩（可控），长尾同义词干脆不放 —— 同义词表是需要持续运营的资产，不是配一次就完的配置。
模块 4

相关性排序：BM25 + 业务权重 + LTR

BM25：ES 默认打分的本质

BM25 是 TF-IDF 的改进版，核心直觉：词在文档里出现越多越相关（TF），但越常见的词越不值钱（IDF），长文档要吃亏修正（长度归一）。

# BM25 打分（简化式）
score(D, q) = Σ over terms t in q:
    IDF(t) × (f(t,D) × (k1 + 1)) / (f(t,D) + k1 × (1 - b + b × |D|/avgdl))

# IDF(t)  = ln((N - n(t) + 0.5) / (n(t) + 0.5) + 1)   N=总文档数, n=含该词文档数
# f(t,D)  = 词 t 在文档 D 中的出现次数
# |D|    = 文档字段长度，avgdl = 平均长度
# k1(默认1.2) 控制 TF 饱和度：词频从 1→2 加分明显，10→11 几乎不加
# b(默认0.75) 控制长度惩罚：b=1 完全惩罚长文档，b=0 不惩罚

# ES 中调整相关性：sim function_score
{
  "query": { "function_score": {
    "query": { "match": { "title": { "query": "快充 充电器",
                                            "boost": 2.0 } }},   // 标题命中加权
    "functions": [
      { "field_value_factor": { "field": "sales", "modifier": "log1p",
                                  "factor": 0.1, "missing": 1 } }   // 销量加分
    ],
    "boost_mode": "multiply"
  }}
}

业务权重调优

信号作用注意
字段加权（title > body）标题命中比正文命中更重要用 multi_match 的 fields 权重，别全靠 boost
时间衰减新内容加分（资讯、社区）gauss/exp 衰减函数，半衰期按业务设
热度/销量电商把交易数据混入相关性log1p 平滑，防头部商品通吃
个性化按用户历史偏好加权实时特征缓存 + 批量计算混合

LTR（Learning to Rank）简述

当人工调参到瓶颈，用机器学习代替手调：把 (查询, 文档) 对的特征（BM25 分、点击率、新鲜度、字段覆盖度）喂给模型，模型输出相关性分数。

# LTR 落地路径（渐进式，别一步到位）
阶段1：日志埋点 —— 记录 query/doc/特征/点击位置，攒训练数据
阶段2：pointwise 回归（LambdaMART 类）离线训练，导出模型
阶段3：ES 6.1+ 原生支持 rescorer 插件（ltr query），对 Top N 重打分
阶段4：点击日志回流 → 在线 A/B → 模型迭代，闭环

# 现实建议：日活搜索量 < 100 万时，BM25 + function_score 调参性价比最高；
# 量级和团队都到位再上 LTR —— LTR 的坑在特征工程和冷启动，不在算法
模块 5

性能优化：缓存、分片、超时降级

分片规划

参数建议
分片大小每分片 10~50 GB（日志类 30~50GB，搜索类可到 100GB）
分片数总分片数 ≈ 节点数 × 1~2 倍，别让一个索引占满集群
过度分片的代价每分片都有固定开销（内存、文件句柄、元数据），1000 个小分片能拖垮集群
副本1 副本起步（吞吐 + 高可用），读多可加到 2

      "delete": { "min_age": "30d", "actions": { "delete": {} } }

缓存体系（ES 自带三层）

缓存缓存什么注意事项
Page Cache热的 segment 文件给 ES 分 < 50% 内存，其余给 JVM
Request Cache聚合结果（size=0 的查询）自动失效于 refresh
Query Cachefilter 的 bitset 结果按分片缓存，高频 filter 收益大

超时与降级

# 查询三层防线
1. timeout 参数：GET /products/_search?timeout=500ms   // 超时返回部分结果而非挂死
2. 应用侧熔断：ES P99 延迟 > 1s 或错误率 > 5% → 切降级逻辑
   （返回缓存的热词结果 / 空结果 + "搜索服务开小差"）
3. 终态兜底：ES 整体不可用 → 返回空列表，主链路（浏览/下单）绝不能依赖搜索可用

# 慢查询治理三板斧
① 禁止深分页：from + size > 10000 报错，改用 search_after 游标
② 通配符开头的查询（*手机）全表扫描，禁
③ 聚合维度高基数（user_id 分组）先预计算或限流
深分页为什么慢：from=10000, size=10 意味着协调节点要从每个分片取回 10010 条，全局排序后再丢掉前 10000 条。分片越多越惨（数据量 × 分片数）。解法：search_after 游标翻页（记住上一页最后一条的排序值）、或限制最大页深（Google 也只让你翻几十页）。
模块 6

ELK vs 专用方案、数据同步、容量估算

技术选型

方案优势劣势适用
ELK / Elastic Stack生态全、ES 查询强、Kibana 可视化重（JVM）、贵（商业许可）、运维复杂日志检索 + 通用搜索，业界默认选择
OpenSearchES 7.10 开源分支，无许可争议生态略小于 ES怕 license 风险的自建
专用搜索（Meilisearch/Typesense）轻量、开箱即用的容错搜索数据量上限低（千万级以下）站内即时搜索、中小数据量
自建/云搜索（OpenSearch Service 等）免运维、弹性成本随规模上升不想养 ES 团队的业务

数据同步：CDC 双写对比

# 方案一：双写（业务同时写 DB 和 ES）—— 不推荐
优点：简单，实时
缺点：不一致无法兜底。DB 成功 ES 失败 → 数据缺失；
      ES 成功 DB 失败 → 幽灵数据；无重试机制，排查靠猜

# 方案二：CDC 单写（推荐）
业务只写 DB → binlog(Debezium/Canal) → MQ(Kafka) → 消费组写 ES
优点：业务零侵入；ES 挂了下游补消费，最终一致；可重放重建
缺点：秒级延迟；消费组要保证顺序（同主键进同分区）

# 方案三：定时全量校验补偿
CDC 之外，每日比对 DB 与 ES 记录数/checksum，差异进补偿队列
# 这是"ES 与 DB 不一致"的唯一根治手段，必配

容量估算（算例）

# 背景：商品搜索，500 万文档，平均每文档 1KB（含 2 个 text 字段）
原始数据：500 万 × 1KB            = 5 GB
倒排索引：约为原文的 20%~40%    ≈ 1~2 GB
doc values：数值/关键词字段       ≈ 0.5~1 GB
_source：原文存储                 = 5 GB
合计每副本 ≈ 12~14 GB，含 1 副本 ≈ 25 GB
结论：3 数据节点（每节点 8 GB 堆内存 + 16 GB 物理）绰绰有余

# 写入吞吐估算：日增 5 万文档（上架+更新）
峰值写入 = 5 万 × 3（重复更新系数）/ 86400 ≈ 2 doc/s
# 可忽略。但大促批量改价（一次改 50 万）→ bulk 限速 + 错峰

# 查询 QPS：峰值 200 QPS，P99 < 100ms
单分片查询 ≈ 5~20ms，3 分片并行 → 足够，无需额外优化
# 真正的瓶颈通常在聚合和深分页，不在简单 match 查询
模块 7

核心配置示例

# ===== 1. 索引 mapping（关键决策全在这）=====
PUT /products
{
  "settings": {
    "number_of_shards": 3,              // 建后不可改，按数据量规划
    "number_of_replicas": 1,
    "refresh_interval": "30s",             // 商品可搜延迟 30s，省 merge
    "analysis": { "analyzer": { "default": { "type": "ik_max_word" } } }
  },
  "mappings": {
    "dynamic": "strict",                     // 禁字段漂移，防 mapping 爆炸
    "properties": {
      "title":      { "type": "text", "analyzer": "ik_max_word",
                   "fields": { "keyword": { "type": "keyword" } } },  // 多字段：可搜+可精确聚合
      "brand":      { "type": "keyword" },        // 筛选/聚合一律 keyword
      "price":      { "type": "scaled_float", "scaling_factor": 100 }, // 分转元，精度不丢
      "sales":      { "type": "integer", "doc_values": true },
      "on_sale_at": { "type": "date" },
      "attrs":      { "type": "nested",            // 数组对象要 nested，防错位
                   "properties": { "k": {"type":"keyword"}, "v": {"type":"keyword"} } }
    }
  }
}

# ===== 2. 查询：相关性 + 业务权重 + 过滤 =====
GET /products/_search
{
  "query": { "function_score": {
    "query": { "bool": {
      "must": [
        { "multi_match": {
          "query": "快充 充电器",
          "fields": ["title^3", "description^1"],   // 标题权重 x3
          "type": "best_fields"
        }}
      ],
      "filter": [                                              // filter 不打分、可缓存
        { "term":  { "brand": "Anker" } },
        { "range": { "price": { "gte": 0, "lte": 20000 } } }
      ]
    }},
    "functions": [
      { "field_value_factor": { "field": "sales", "modifier": "log1p", "factor": 0.2 } },
      { "gauss": { "on_sale_at": { "origin": "now", "scale": "30d", "decay": 0.5 } }  // 30 天衰减一半
    ],
    "boost_mode": "multiply", "score_mode": "sum"
  }},
  "from": 0, "size": 20,                        // 深分页换 search_after
  "_source": ["title", "price", "brand"],      // 只取要的字段，省带宽
  "timeout": "500ms"
}

# ===== 3. bulk 写入（唯一正确的姿势）=====
POST /_bulk
{ "index": { "_index": "products", "_id": "P1001" } }   // 显式 _id，天然幂等
{ "title": "Anker 快充充电器", "price": 9900, "brand": "Anker" }
{ "update": { "_index": "products", "_id": "P1002" } }
{ "doc": { "price": 8900 }, "doc_as_upsert": true }    // 更新幂等

# bulk 铁律：每批 5~15MB / 1000~5000 条；失败项重试，别整批重试
# refresh 策略：批量导入时先 "refresh_interval": -1，导完再打开
三个一犯就痛的配置错误：① dynamic: true 放任业务字段漂移，半年后 mapping 里几百个垃圾字段，集群变慢；② text 字段直接做排序/聚合（fielddata 爆炸，直接 OOM）；③ 用默认分片数建小索引，几十个索引 × 5 分片，集群被元数据拖死。新索引上线前过一遍 mapping review，比出事后重建代价小一百倍。
模块 8

十个线上坑

1
业务双写 DB 和 ES，数据不一致无法兜底
DB 成功 ES 失败就丢数据，且无重试、无法感知。必须改 CDC 单写（binlog → MQ → 消费组写 ES），再加每日全量校验补偿。双写看似简单，实则是数据不一致的无底洞。
2
mapping 字段漂移，集群越来越慢
业务加了新字段没管，ES 自动动态映射，几百个无用字段拖垮一切。mapping 设 dynamic: strict 禁止未知字段，新字段走评审上线。
3
深分页 from + size = 10000+
协调节点要从每个分片取上万条再全局排序丢弃，延迟爆炸甚至 OOM。翻页一律 search_after 游标，并对页深设上限。
4
text 字段上排序/聚合，fielddata OOM
对 text 字段聚合会现场建 fielddata 正排，堆内存直接爆。聚合/排序用 keyword 字段（multi-fields 一份数据两种索引），数值排序用数值类型。
5
过度分片：几百个小分片拖垮集群
每分片有固定元数据和文件开销，索引建的时候随手 5 分片，一年后集群几千分片。单分片目标 10~50GB，总分片数 ≈ 节点数 × 1~2。
6
搜索做成了强依赖，ES 一挂全站瘫痪
首页/列表页直连 ES，没有降级逻辑。搜索必须是"可降级依赖"：ES 挂了返回空列表/缓存兜底，主链路（详情、下单）照常工作。熔断 + 超时 + 降级三件套配齐。
7
同义词表拍了一次脑袋就再也不管
用户搜"电脑"找不到"计算机"，搜"喵"找不到"猫"。同义词是持续运营的资产：从搜索日志挖高频无结果 query，每周补充词表并评估扩展爆炸。
8
相关性只调 BM25 参数，不看查询理解
搜"苹果"返回一堆水果，调 k1/b 永远调不好。根因在查询解析阶段（分词、意图、词权重），不在打分函数。先查分词结果，再谈调参。
9
JVM 堆给了 32GB，GC 停顿秒级
ES 堆内存超过 32GB 就失去压缩指针优化，CMS/G1 停顿变长。堆设物理内存的 50% 且封顶 32GB（一般 16GB 足够），另一半留给 page cache。
10
批量导入直接 full refresh，segment 爆炸
每次 bulk 都触发 refresh，产生几千个小 segment，查询慢且 merge 打满 CPU。批量导入先关 refresh，导完 forcemerge，日常 refresh 30s 起步。
自测

六道题

1. 用户搜索"苹果手机"返回了大量水果苹果，最该先排查哪个环节？
正确答案：先查查询解析。"苹果手机"应分成"苹果/手机"或整体识别为手机品类，词权重和意图错了，后面打分再准也白搭。调 k1/b 是排序阶段的事，解决不了"召回了错文档"的问题。
2. DB 与 ES 数据同步，最可靠的方案是？
正确答案：CDC 单写 + 校验补偿。双写有不一致无兜底、无重试的硬伤；小时级全量同步实时性不够。CDC 让业务零侵入，MQ 提供可靠重试，日校验保证最终一致。
3. 关于 ES 分页，from + size 超过 10000 会怎样，正确做法是？
正确答案：search_after 游标。深分页要从每个分片取 from+size 条再全局排序丢弃，成本 = 数据量 × 分片数。search_after 用上一页排序值定位，跳过历史数据，代价恒定。
4. 500 万文档、每文档 1KB 的商品搜索索引，合理的分片规划是？
正确答案：3 分片 + 1 副本。数据含索引和 _source 约 12~14GB/副本，3 分片每片约 4~5GB（略小但可接受，留增长空间）。过度分片有元数据和内存开销，分片不是越多越快。
5. 想让"新品"在搜索结果中靠前，同时不影响相关性主线，应该用？
正确答案：function_score 时间衰减。衰减函数把"新鲜度"作为叠加因子混入打分，主查询（BM25）不受影响。k1 控制词频饱和度和新鲜度无关；堆砌关键词是作弊且会被相关性反噬。
6. 搜索系统高可用的正确姿势是？
正确答案：超时 + 熔断 + 降级。搜索是体验增强而非交易主链路，ES 整体故障时应返回空列表或缓存兜底，商品详情/下单照常。多集群是过度设计，抛异常会把一个边缘故障放大成全站故障。
