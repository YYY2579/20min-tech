模块 1

核心域拆解：五个域，两种命运

域拆分的标准不是"功能相似"，而是变化频率、一致性要求、团队边界。电商里五个域的命运完全不同。

域核心实体一致性要求设计要点
商品域SPU / SKU / 类目 / 属性 / 价格弱一致（秒级可接受）读多写少，狂堆缓存。SPU 是销售单元（iPhone 15），SKU 是库存单元（黑色 128G）
订单域购物车 / 订单主档 / 订单明细 / 售后单强一致（资金相关）状态机驱动，一切流转可追溯。订单是法律凭证，数据要留档 3~5 年
库存域可售库存 / 预占 / 仓存 / 库存流水强一致（不能超卖）"可售"和"实物仓存"是两套账。预占（下单未付）→ 扣减（支付）→ 释放（取消）
支付域支付单 / 渠道 / 对账文件 / 退款单强一致（一分钱不能错）所有操作幂等。与第三方渠道每日对账，差异单人工介入
营销域优惠券 / 活动 / 价格 / 运费弱一致（领券要准）规则引擎化。优惠叠加规则是产品经理的重灾区，必须沉淀成可配置规则

为什么要拆域（而不是一个大服务）

  • 故障隔离 + 独立扩缩容：搜索挂了不影响下单；商品详情 10 万 QPS 要 100 台，库存 5 千 QPS 只要 5 台，绑在一起就得按最高配扩容
  • 存储选型不同：商品走 MySQL + Redis + ES；订单走 MySQL；库存走 Redis + MySQL；埋点走 Kafka
  • 团队边界清晰：订单团队维护一个域，接口契约化，上线互不阻塞
拆太细的代价（真实教训）：一次"创建订单"要调 7 个服务，P99 被最慢的服务拖到 800ms，一个服务抖动全链路雪崩。解法：核心链路（下单）保持"少而粗"的同步调用（≤4 个），非核心（积分、短信、发票、履约通知）全部走 MQ 异步。

域间关系（一张表看懂）

调用方被调方同步还是异步
订单服务库存服务（预占）同步，必须拿到结果才能创建订单
订单服务营销服务（计价）同步，价格错了用户会投诉
订单服务支付服务（创建支付单）同步或异步均可，通常同步返回收银台参数
订单服务履约服务（建单）异步（MQ），发货是秒级以后的事
支付服务订单服务（改状态）异步（MQ），支付成功后推进订单状态
订单服务积分/短信/发票异步（MQ），允许丢失（有补偿）
模块 2

核心表设计（DDL 级）

表结构是电商的"宪法"。下面四张表覆盖了 80% 的场景：SKU、订单主档、订单明细、库存。全部基于 MySQL 8.0 InnoDB。

SKU 表（商品域）

-- SKU：最小库存单元。5000 万行，按 spu_id 分库分表
CREATE TABLE sku (
  id            BIGINT PRIMARY KEY,      -- 雪花 ID，不用自增（防遍历）
  spu_id        BIGINT      NOT NULL,
  title         VARCHAR(128) NOT NULL,
  price         DECIMAL(10,2) NOT NULL,  -- 金额一律 DECIMAL，禁止 FLOAT/DOUBLE
  status       TINYINT      NOT NULL DEFAULT 1, -- 1上架 0下架
  version      INT         NOT NULL DEFAULT 0, -- 乐观锁版本号
  -- attrs: 规格属性（颜色/尺码）存 JSON，查询走 ES
  attrs        JSON,
  created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_spu (spu_id),
  KEY idx_status (status, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

订单主档（订单域）

-- order：一个用户下一单产生一行。按 user_id 分 128 库
CREATE TABLE `order` (
  id            BIGINT PRIMARY KEY,
  order_no      VARCHAR(32) NOT NULL UNIQUE, -- 业务单号，对外展示
  user_id       BIGINT NOT NULL,
  status       TINYINT NOT NULL,      -- 1待付 2已付 3待发 4已发 5完成 6取消
  pay_amount   DECIMAL(10,2) NOT NULL,   -- 实付金额
  total_amount DECIMAL(10,2) NOT NULL,
  discount_amount DECIMAL(10,2) NOT NULL DEFAULT 0,
  receiver_info JSON,                -- 收货人快照（下单时刻固化）
  expire_at    DATETIME     NOT NULL,      -- 支付超时时间
  KEY idx_user (user_id, id),          -- 我的订单列表
  KEY idx_status (status, expire_at)  -- 关单扫描
) ENGINE=InnoDB;

库存表（库存域）

-- inventory：available=可售 locked=预占 on_hand=实物仓存
-- 恒等式：available + locked = on_hand（对账脚本每天校验）
CREATE TABLE inventory (
  sku_id     BIGINT PRIMARY KEY,
  available  INT NOT NULL DEFAULT 0 CHECK (available >= 0),
  locked     INT NOT NULL DEFAULT 0,
  on_hand    INT NOT NULL DEFAULT 0,
  version   INT NOT NULL DEFAULT 0
) ENGINE=InnoDB;

-- inventory_log：库存流水，每一笔变动一行，出事靠它查
CREATE TABLE inventory_log (
  id        BIGINT PRIMARY KEY,
  sku_id   BIGINT NOT NULL,
  delta    INT NOT NULL,   -- +10 入库 / -1 扣减
  biz_type VARCHAR(32),  -- ORDER_LOCK / ORDER_PAY / ORDER_CANCEL
  biz_id   VARCHAR(64),  -- 订单号，幂等键
  UNIQUE KEY uk_biz (biz_type, biz_id)
);

订单号设计（细节见坑 4）

// 订单号 64 位：时间41 + 机器10 + 序列12，末尾拼 user_id 后4位做"分库基因"
// 拿到订单号就能算出 user_id 尾号 → 定位分库，不需要全局索引表
分库分表三原则：① 拆分键选 user_id（订单、购物车都按用户查）；② 单表控制在 500 万行以内；③ 需要跨库查的字段用基因法（把 user_id 尾号嵌进订单号），而不是建全局索引表——全局索引表在大促必成瓶颈。
模块 3

读多写少：缓存架构怎么堆

商品详情是典型读多写少：读:写 ≈ 1000:1。这个场景的解法是成熟套路，但有两个电商特有的坑：价格和库存不能乱缓存。

多级缓存层级与命中率目标

层级命中率说明
浏览器 / App 本地缓存~30%静态资源走 CDN（带 hash，有效期 1 年）；详情页骨架可缓存 30 秒
CDN~50%图片、视频、静态化页面。价格、库存必须动态回源或干脆不缓
网关 / OpenResty 本地缓存~40%热点商品详情整页缓存 1~5 秒，单机 QPS 提升一个数量级
应用本地缓存（Caffeine）~30%防 Redis 热点 key。TTL 10~60 秒，上限 1 万条，只缓存读多写极少的数据
Redis 集群~95%主力缓存层。多级防击穿：逻辑过期 + 互斥锁 + 空值缓存
MySQL~5%兜底。真正落到库的读要 < 10%

商品详情页的"分段缓存"策略（关键）

// 一个详情页 = 多个数据段，按变化频率分别缓存，不要整页一锅端
{
  "base":     { "sku": "...", "images": [...] },   // 商品基本信息：1 小时，静态
  "detail":   { "desc_html": "..." },             // 图文详情：CDN 级缓存
  "price":    { "sale_price": 4999, "rule": "..." }, // 价格：10 秒，且必须能被主动失效
  "stock":    { "available": 87 },                 // 库存：3 秒 + 主动失效，见下
  "promo":    { "coupon": "...", "activity": "..." }  // 营销：1 分钟
}

为什么库存和价格要单独处理？它们的变化直接影响资金正确性。库存缓存 3 秒意味着最多 3 秒的"脏库存"，用户看到有货但下单失败。解法：详情页显示"有货/紧张/无货"三态而不是精确数字，精确库存留给下单链路；价格短 TTL + 改价时主动删缓存（Canal 订阅 binlog 失效）。

缓存预热（大促前 2 小时开始）

# 1. 从只读副本限流拉取 Top 10 万商品（预热脚本限流 200 QPS，防把 DB 打挂）
# 2. 灌入 Redis + 应用本地缓存；详情页静态化推送 CDN
# 3. 库存预热：set stock:sku:{id} = 真实库存
# 4. 验证：抽样 1000 个 SKU 对比缓存与 DB 值
缓存预热最常见的死法：预热流量把数据库打挂。一次拉 10 万 SKU 详情，如果不限流地直查 MySQL，DB CPU 直接 100%。正确做法：预热脚本限流（如 200 QPS 查库）+ 分批 + 错峰，且优先从只读副本拉。

一个容量算例（读链路）

日常商品详情 5 万 QPS，大促 10 倍 = 50 万 QPS。假设各级命中率如上：落到 Redis 的量 = 50 万 × (1-0.30 浏览器) × (1-0.50 CDN) × (1-0.40 网关) × (1-0.30 本地) ≈ 50 万 × 0.7 × 0.5 × 0.6 × 0.7 ≈ 7350 QPS，Redis 集群 3 主 3 从（单机 8 核 16G，单机 3 万 QPS 上限）绰绰有余。落到 MySQL = 7350 × 5% ≈ 370 QPS，一个 4C8G 只读实例即可扛住。结论：读链路堆缓存就能解决，写链路才是生死线。

模块 4

库存扣减：超卖防护四板斧

超卖根因只有一个："查询库存 → 判断 → 扣减"三步在并发下不是原子的。两个请求同时查到 available=1，都去扣，库存变 -1。四种方案，可靠性递减、性能递增。

方案一：数据库乐观锁（最可靠，默认选它）

-- 利用"影响行数"做并发控制，一条 SQL 完成判断+扣减
UPDATE inventory
   SET available = available - 1, locked = locked + 1, version = version + 1
 WHERE sku_id = 10086
   AND available >= 1;

-- 关键：看 affected_rows
-- affected_rows = 1 → 扣减成功
-- affected_rows = 0 → 库存不足，返回"已抢完"（不是异常！）

-- 版本号乐观锁（等价写法，适合需要先读后写的场景）
UPDATE inventory SET available = available - 1, version = version + 1
 WHERE sku_id = 10086 AND version = 7;
-- version 变了就失败，重试（通常重试 3 次后放弃）

行锁竞争是它的极限：1000 个请求同时扣同一 SKU，全部排队在一行上，MySQL 单行约能支撑 3000~5000 TPS（Percona 5.7+ 实测区间）。超过这个值，要么削峰（见秒杀篇），要么拆分行。

方案二：库存分片（把一行拆成 N 行，分散行锁）

-- 一个 SKU 拆成 16 个分片，每个分片存 1/16 库存，随机选一个扣：
UPDATE inventory_shard SET available=available-1 WHERE sku_id=? AND shard=? AND available>=1
-- 总库存 = 各分片求和。扣减随机落到不同行，行锁竞争降到 1/16
-- 代价：可能"总量够但某分片空了"，接受少量误判或做二次归集

方案三：Redis 原子扣减（高并发首选）+ 异步落库

# Lua 脚本：扣减 + 记录已扣用户，原子完成，还防重复扣
# KEYS[1]=stock:sku:10086  ARGV[1]=userId  ARGV[2]=maxPerUser
local stock = tonumber(redis.call('get', KEYS[1]) or '0')
if stock <= 0 then return -1 end  -- 售罄
local key = 'bought:'..KEYS[1]..':'..ARGV[1]
if redis.call('exists', key) == 1 then return -2 end -- 已买过
redis.call('decrby', KEYS[1], 1)
redis.call('set', key, 1)
redis.call('expire', key, 86400)
return stock - 1

Redis 单机 DECR 可达 10 万+ TPS，且 Lua 保证原子性。但 Redis 是内存，宕机丢数据。所以必须配三件套：① 异步 MQ 把扣减流水落库；② 每日对账校准；③ Redis 宕机时降级到方案一。

方案四：异步对账（兜底，所有方案都要配）

# 1. 校验恒等式：available + locked = on_hand（MySQL 侧）
# 2. 校验 Redis 预扣总量 = MySQL locked 总量（偏差 > 0.1% 告警）
# 3. 用 inventory_log 重放每笔 biz_id，与当前 available 对账
# 4. 发现差异：优先以"支付成功记录"为准修正（宁少卖不多卖）

四种方案对比

方案可靠性性能（单 SKU）适用场景
DB 乐观锁最高（DB 是真相）~3000 TPS常规商品、日常下单。默认方案
库存分片高~5 万 TPS爆款但不到秒杀级，如店庆单品
Redis 预扣中（需对账兜底）~10 万 TPS秒杀、大促爆款。必须配异步落库 + 对账
异步对账兜底（非独立方案）批量所有方案都要配，防止"少卖/超卖"悄悄发生
一个真实的超卖案例：某电商用 Redis DECR 预扣，没做对账。Redis 主从切换时丢了 3 秒的扣减记录，恢复后库存"凭空"多出 200 件，全部超卖。教训：Redis 预扣的库存是"账面上的真相"，MySQL 才是法律上的真相，两者必须每日对账。
模块 5

订单状态机：一切流转可追溯

订单的核心是状态机。状态机的意义：任何状态迁移都必须由"事件 + 前置状态"共同决定，杜绝"待支付订单被发货"这种脏数据。

主链路状态流转（正向）

待支付 已支付 待发货 已发货 已完成

① 用户下单（预占库存成功）② 支付回调成功 ③ 仓库拣货出库 ④ 确认收货 / 7 天自动

异常与逆向流转

待支付 已取消 已支付 退款中 已退款 待发货 退款中

a. 超时未付/主动取消（释放库存） b. 已付未发全额退 c. 已发货走售后退货退款 d. 已付未发申请退款

状态迁移表（代码就照这张表写）

事件前置状态目标状态副作用动作
用户下单无待支付预占库存、创建支付单、发 MQ 建履约单、30 分钟延时关单
支付成功待支付已支付库存"预占转实扣"、清购物车、发 MQ 通知履约、记流水
超时关单待支付已取消释放预占库存、关闭支付单、发券退回（如用了券）
用户取消待支付 / 已支付未发已取消 / 退款中未付直接释放库存；已付走退款流程
仓库出库已支付已发货扣实物仓存、回填运单号、发短信
确认收货已发货已完成结算入账、发积分、订单归档
申请退款已支付 / 已发货退款中冻结订单、冻结库存、创建售后单
退款成功退款中已退款释放库存、原路退回、记对账流水
// 状态迁移的唯一入口：所有字段一起 CAS，天然幂等
int rows = jdbc.update(
  "UPDATE `order` SET status = ?, paid_at = NOW() " +
  "WHERE order_no = ? AND status = ?",   // ← status=? 是前置状态校验！
  NEW_STATUS.PAID, orderNo, OLD_STATUS.WAIT_PAY);
if (rows == 0) {
  // 两种情况：订单不存在，或状态已被改过（重复回调）
  // 两种情况都按"幂等成功"处理：查一下当前状态，是已支付就直接返回成功
  return idempotentSuccess();
}
状态机三铁律：① 迁移必须带前置状态条件（WHERE status=old），用数据库行锁做 CAS；② 终态（已完成/已取消/已退款）永不可逆；③ 每次迁移写一行 order_log（谁、何时、从哪到哪、为什么），出问题时这是唯一能复盘的东西。
模块 6

下单链路一致性：分布式事务怎么选

一次下单要动：订单库（建单）、库存库（预占）、营销库（用券/锁活动）、支付域（建支付单）。这些在不同库甚至不同机器上，要么都成功，要么都回滚——这就是分布式事务。

六种方案对比（按推荐度排序）

方案一致性性能电商适用性
Saga（正向+补偿）最终一致高下单链路首选。每个本地事务配一个补偿动作，失败了就反向执行
本地消息表最终一致高与 Saga 绝配。把"待发消息"和业务数据放同一事务，杜绝消息丢失
可靠消息（事务消息）最终一致高依赖 MQ 支持事务消息（RocketMQ 有，Kafka 需自己实现）
TCC最终一致中适合库存、余额这类"预留"语义。成本高（3 个接口）
最大努力通知弱高只用于通知类：短信、积分。允许丢，靠定时重试
2PC / XA强一致低（禁用）锁资源直到全局提交，大促下必然超时雪崩。电商不要用

下单链路实战：Saga + 本地消息表

// 下单编排：正向服务 + 补偿服务一一对应
// 原则：能异步的全部异步，只有"库存预占"和"计价"必须同步拿结果

public OrderResult placeOrder(PlaceOrderCmd cmd) {
  // 1. 本地事务：建单（待支付）+ 写本地消息表（同一事务，原子）
  tx.begin();
  Order order = orderRepo.create(cmd);
  msgRepo.save("ORDER_CREATED", order.getId());
  tx.commit();

  // 2. 同步：库存预占（失败必须回滚整单）
  try {
    stockClient.lock(order.getItems());
  } catch (StockNotEnoughException e) {
    cancelOrder(order.getId(), "库存不足");
    throw e;
  }

  // 3. 同步：营销计价（用券、算运费）
  PriceResult price = promoClient.calculate(cmd);

  // 4. 异步（MQ）：建履约单、发短信、加积分、记埋点
  mq.send("topic.fulfillment", order.getId());
  return OrderResult.ok(order.getId());
}

// 补偿接口：关单释放一切（幂等，靠 order_no 去重）
public void cancelOrder(Long orderId, String reason) {
  int rows = orderRepo.casStatus(orderId, WAIT_PAY, CANCELED);
  if (rows == 0) return;               // 已取消过，幂等
  stockClient.release(orderId);        // 释放预占
  couponClient.unuse(orderId);         // 退券
}

本地消息表怎么保证不丢消息

同事务写入：业务数据和消息行在同一个本地事务提交，要么都有要么都没有
定时扫描 + 消费端幂等：后台任务每 5 秒扫"待发送"消息投递到 MQ；消息带全局唯一 biz_id，消费方用唯一索引去重，重发不重复处理
对账兜底：每日比对"业务结果"与"消息消费结果"，差异进人工队列
补偿不是万能药：Saga 的补偿本身可能失败（补偿时库存服务挂了）。补偿必须可重试 + 幂等 + 最终对账；"钱"相关的补偿（退款失败）必须进人工工单。工程共识：最终一致 + 每日对账 + 异常人工介入，这就是电商的正确答案。
模块 7

秒杀与营销的隔离

秒杀和营销是流量的两个极端：秒杀是瞬时尖刺（10 万 QPS 集中在 1 秒），营销是规则复杂（优惠叠加算错就是资损）。两者都要与主站隔离，理由不同。

秒杀隔离（详见秒杀篇，这里讲隔离原则）

隔离维度做法
域名/入口隔离秒杀用独立域名 miaosha.example.com，与主站 DNS 分开，故障不互染
服务隔离独立秒杀服务集群（只做"资格校验 + 创建订单"两件事），不复用主站订单服务
缓存隔离独立 Redis 集群。大 key（库存）单独实例，避免影响其他业务
数据库隔离独立库 + 独立连接池。连接池满只影响秒杀，不拖垮主站
降级预案秒杀挂 → 页面降级为"活动太火爆"；绝不允许拖垮主站下单

营销：价格计算与优惠券

// 计价三步骤（顺序不能乱）
// 1. 单品价：SKU 原价 × 数量 → 商品总额
// 2. 店铺/活动级优惠：满减、直降、秒杀价（互斥规则在此层裁决）
// 3. 跨店优惠：平台券、红包（只能用于"优惠后"的金额）

// 平行优惠 vs 递进优惠（产品经理最容易吵的概念）
原价 100，满 100 减 20，平台券 9 折：
  平行：100 - 20 = 80，再 × 0.9 = 72   // 各优惠独立计算后叠加
  递进：80 的基础上再打 9 折 → 72，但门槛按"当前待优惠金额"重新判断

优惠券防超发：一张券库存 1000 张，10 万人同时领。必须原子：UPDATE coupon SET remain=remain-1 WHERE id=? AND remain>0，影响行数=0 就是领完了。再叠加一人一张：INSERT IGNORE INTO user_coupon(user_id, coupon_id)，唯一索引兜底。

资损红线：价格计算必须纯函数 + 可重算——给定同样的商品和优惠输入，任何时候重算结果必须一致。落库时把计价明细快照（用了哪些券、每步减了多少）存进订单，出争议时能复盘。永远不要让"先改价再算券"这类有顺序副作用的状态参与计价。

搜索与推荐（一句话架构）

  • 搜索：ES 倒排索引，查询 = 分词 → 倒排拉取 → BM25 + 业务权重（销量、评分、出价）打分 → 过滤（上下架、库存）→ 排序分页
  • 推荐：召回（协同过滤 + 向量相似 + 热门）→ 粗排（轻量模型截断到千级）→ 精排（深度模型）→ 重排（多样性、运营插槽），特征来自 Kafka + Flink 实时流
  • 共同点：都可以降级。搜索挂了出热销榜，推荐挂了出编辑精选——这是与交易链路的本质区别
模块 8

订单拆分、履约与压测

拆单：一笔订单怎么变成多个履约单

用户下单可能买 5 件商品，来自 3 个商家、2 个仓库，还有跨境商品。拆单在支付成功后异步进行，规则按优先级排列：

拆单维度优先级说明
商家（多商户平台）1不同商家必须拆，结算、售后都独立
仓库 / 发货地2同商家不同仓 → 拆成多包裹，物流单独立
业务类型3一般贸易 / 跨境保税 / 虚拟商品（充值卡）走完全不同流程
温层 / 时效4冷链（生鲜）与普通包裹必须分开履约

拆单完成后：每个履约单独立走"拣货 → 打包 → 发货 → 签收"，主订单状态取所有子单的最慢状态（全部签收才完成）。拆单结果落 fulfillment_order 表，与主订单 N:1。

压测与容量规划（给数字）

// 容量规划公式：从业务量反推，再压测校准
峰值 QPS = 日订单量 × 峰值集中系数 / 有效下单时长
  例：300 万单/日，大促 60% 集中在晚 8 点后 2 小时，则
  峰值 QPS = 300万 × 0.6 / (2 × 3600) ≈ 2500 TPS（日常），大促 10 倍 ≈ 2.5 万 TPS

单机容量（经验值，需压测校准）：
  下单接口（含 3 次同步 RPC + 2 次 DB 写）：4C8G 单机 500~800 TPS
  机器数 = 峰值 QPS / 单机容量 × 1.3 冗余
  2.5 万 TPS / 700 ≈ 36 台，×1.3 ≈ 47 台（下单集群）

MySQL 写容量：2.5 万单/s × 每单 3 张表 ≈ 7.5 万行/s → 必须分库分表

全链路压测三件套：① 流量染色——压测流量打特殊标记（HTTP header 带 x-stress-tag），全链路透传；② 影子库/影子表——染色的写落到影子库，与生产隔离；③ 读验证——压测中的查询允许读影子数据，保证链路真实。大促前必须压到目标峰值的 1.5 倍，否则峰值当天一定翻车。

压测暴露的三个经典瓶颈（提前剧透）：① 数据库连接池打满（2.5 万 TPS × 每单 2 连接，单库不够，靠分库解决）② Redis 热 key 把单节点 CPU 打满 ③ MQ 消费堆积导致"支付成功但订单状态没更新"。这三个问题在压测中暴露的成本是 0，在大促中暴露的成本是事故。
模块 9

十个线上坑

1
库存"先查后改"两步操作
并发下必超卖。必须一条 SQL 带 WHERE available>=1 做原子扣减，用影响行数判断成败。
2
订单状态用代码里 if-else 直接改，不带前置状态
支付回调和主动取消并发时，可能出现"已支付"和"已取消"互相覆盖、重复发货。必须 UPDATE ... WHERE status=期望旧值 做 CAS。
3
缓存里存了精确库存和实时价格
库存缓存 3 秒 = 3 秒内超卖风险；价格缓存不同步 = 用户截图投诉。详情页只显示三态库存，价格短 TTL + 主动失效。
4
订单号用数据库自增 ID
① 竞争对手能根据订单号增量算出你的日单量 ② 分库分表后无法定位数据在哪个库。必须用带时间戳+机器号+user_id 基因的雪花变体。
5
优惠券领取不校验库存、不校验一人一张
券比活动库存发得多、一人领 100 张。领取必须 UPDATE remain=remain-1 WHERE remain>0 + 唯一索引 (user_id, coupon_id)。
6
下单同步调用所有下游服务
P99 被最慢服务拖垮，一个抖动全链路超时。核心链路同步调用 ≤4 个，其余全走 MQ 异步。
7
用 2PC/XA 做下单分布式事务
锁资源直到全局提交，大促下连接池耗尽雪崩。用 Saga + 本地消息表做最终一致，配每日对账。
8
支付回调不幂等
渠道会重试回调，不幂等就会重复入账、重复发货、重复发券。支付单必须唯一键 (channel, out_trade_no)，状态机 CAS 更新。
9
大促前不预热、不压测
冷缓存 + 未校准的容量 = 开抢 3 分钟数据库被打挂。预热限流分批灌缓存，压测到目标 1.5 倍，减配预案提前演练。
10
超时关单只删了订单，没释放库存和券
库存被"幽灵订单"永久占用，越攒越多最后全店售罄。关单必须三件套：关单 + 释放预占 + 退券，且全部幂等。
自测

六道题

1. 防止超卖，最可靠的数据库层写法是？
正确答案：带条件的原子 UPDATE。"先查后改"在并发下两个事务可能同时读到 available=1。带 WHERE available>=1 的单条 UPDATE 由行锁保证串行，影响行数为 0 即库存不足。
2. 下单链路跨越订单库、库存库、营销库，工程上的首选方案是？
正确答案：Saga + 本地消息表 + 对账。2PC 在大促下会长时间锁资源导致雪崩；合并库等于放弃域隔离和独立扩缩容。电商追求最终一致，补偿失败进人工工单。
3. 支付渠道重复发送"支付成功"回调，系统应该怎么处理？
正确答案：幂等处理。渠道重试是正常行为，不能报错（否则渠道持续重试甚至告警）。用支付单唯一键 + UPDATE order SET status=已支付 WHERE status=待支付，影响行数为 0 说明处理过，直接返回成功。
4. 订单状态机设计中，下面哪个做法是正确的？
正确答案：迁移带前置状态 + 留日志。不带前置状态的并发更新会互相覆盖（如取消覆盖已支付）；终态可逆会让资金口径混乱；order_log 是事后复盘的唯一依据。
5. 关于商品详情页的库存展示，正确做法是？
正确答案：三态展示。精确库存是资金正确性问题，缓存会造成"看有货实际无货"的客诉和超卖风险。三态 + 下单链路兜底校验，兼顾体验与正确性。
6. 日订单 300 万，大促 60% 集中在晚 8 点后 2 小时，单机下单容量 700 TPS，预留 30% 冗余，约需要多少台下单机器？
正确答案：约 47 台。峰值 QPS = 300 万 × 0.6 / 7200 秒 ≈ 2500 TPS，大促按 10 倍算 2.5 万 TPS，除以单机 700 得 36 台，乘 1.3 冗余 ≈ 47 台。日常只要 4~5 台，容量按大促备、成本靠弹性伸缩。
