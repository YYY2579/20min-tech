二十分钟入门模型微调实战

微调不是"把模型变聪明"的银弹。这一篇解决四个问题：什么场景才该微调、LoRA 参数怎么设、显存怎么估、以及为什么 90% 的微调项目死在数据质量上。默认你有一张 24GB 以上的消费级显卡或能租到云 GPU。

开始前

模块 1

决策树：微调 vs RAG vs 提示词

这是整篇最重要的一节。大部分"想微调"的需求，用另外两种方案更便宜、更快、更可控。微调是最后手段，不是第一反应。

按问题类型选方案

你的问题首选方案理由
模型缺少私有知识（公司文档、产品参数、内部流程）RAG（检索增强）知识更新只需改向量库，当天生效；可给出出处；不会灾难性遗忘
模型不懂你的业务术语、格式、语气提示词，不够再 SFTfew-shot 给 3~5 个范例通常就能定型。稳定不下来再微调
需要稳定的结构化输出（固定 JSON schema、SQL 风格）SFT（微调）提示词能让 95% 的样本合规，微调是压最后 5% 和降 token 成本
需要特定领域深度能力（医学问答、法律文书、代码补全）领域 CPT + SFT继续预训练灌领域语料，再指令微调对齐格式
要压缩模型：让小模型学会大模型的输出风格SFT（蒸馏）用大模型生成的数据微调小模型，省钱且延迟低
需要屏蔽/对齐（不说违禁词、拒绝特定请求）DPO / 安全对齐偏好数据（chosen/rejected）是这类需求的标准解法

三个反例（这些情况别微调）

① "知识注入"别用微调。把 5000 条产品手册灌进模型，知识会过时、会张冠李戴、无法给出来源，还挤占通用能力。知识类需求用 RAG，改文档即生效。
② "格式要求"先试提示词。把输出格式、字段名、示例写进 system prompt，先测 200 条真实请求，准确率到 90% 以上再考虑微调。
③ 没有评测集别启动微调。说不清"变好多少"的训练，等于闭眼开车。微调前先攒 200~1000 条带标准答案的评测样本。

成本对比（以 7B 模型、内部 10 万次/天的调用量估算）

方案前期投入知识更新成本持续推理成本
提示词工程接近 0改 prompt，分钟级高（长 prompt，每次多花 token）
RAG中（建索引、检索链路）改文档，小时级中（检索 + 短 prompt）
SFT 微调高（数据 + GPU + 数天）重新训练，天级低（prompt 短、可配默认 system）
决策顺序建议：提示词 → RAG → 微调。能用便宜的方案达到 80 分，就别上贵的。微调真正的甜点场景是：高调用量 + 格式/风格稳定 + 提示词已到瓶颈，此时省下的推理 token 和稳定性收益能覆盖训练成本。
模块 2

三种微调范式：CPT、SFT、偏好对齐

三个词天天出现，区别在于训练目标、数据形态和算力量级完全不同。选错阶段等于用大炮打蚊子。

范式数据形态数据量级算力与场景
CPT
继续预训练		纯文本无标注语料（PDF、内部 wiki、代码）GB 级（数十亿 token）贵，接近预训练。注入领域知识/术语，让模型"见过"你的领域语言
SFT
指令微调		指令-回答对（chat 多轮对话）千条 ~ 十万条最常用。教模型"怎么回答"：格式、风格、拒绝边界
RLHF / DPO
偏好对齐		偏好对（同一个问题的好/坏两个回答）万条 ~ 十万条教模型"什么是好回答"。降低有害输出、贴合人类偏好

SFT 数据长什么样（ShareGPT 格式，业界最通用）

// 一条多轮对话样本，LLaMA-Factory / Axolotl 都认这个格式
{
  "conversations": [
    {"from": "system", "value": "你是某银行的风控助手，只回答风控规则问题。"},
    {"from": "human",  "value": "用户近 6 个月有 3 次逾期，能通过吗？"},
    {"from": "gpt",    "value": "不能。根据规则 R-114，近 6 个月逾期超过 2 次即拒贷。"},
    {"from": "human",  "value": "那担保人能替代吗？"},
    {"from": "gpt",    "value": "可以，但需……"}
  ]
}

DPO 数据长什么样

// 同一个 prompt，一个"好回答"一个"坏回答"，模型学这个相对偏好
{
  "prompt":   "用户 A 月收入 8000，想贷 50 万，怎么回复？",
  "chosen":   "根据收入偿债比规则，50 万远超您的偿债能力，建议……",
  "rejected": "没问题，50 万可以批，请提供身份证。"  // 违规回答，作为负样本
}

RLHF/PPO vs DPO：为什么现在都推荐先试 DPO

维度PPO（经典 RLHF）DPO
需要几个模型4 个：策略、参考、奖励、价值网络，显存爆炸2 个：策略 + 参考模型，省一半以上显存
训练稳定性差，奖励黑客、KL 系数要反复调，容易崩好，就是监督学习，超参少
数据要求奖励模型标注质量要求高直接吃偏好对，容易构造
效果上限理论上限高，适合大规模对齐大多数业务场景已够用，首选
DPO 的关键超参是 beta（通常 0.05~0.5，默认 0.1）。它控制模型离参考模型的偏离程度：太小 → 模型为了刷偏好分胡说八道（奖励黑客）；太大 → 学不动，等于没训。DPO 是 2023 年后的主流做法（Rafailov 等人的论文），具体实现以 TRL 等库当前文档为准。
模块 3

LoRA 与 QLoRA：原理与参数

LoRA 是"用最小成本微调大模型"的默认答案。原理一句话能说完，但参数设错，效果差一倍、显存多一倍。

原理：不动原权重，只训练一个"低秩补丁"

# 原始前向：Y = W·X，W 是 4096×4096 的权重矩阵，冻结不训
# LoRA：W' = W + B·A，A 是 4096×r，B 是 r×4096，只训练 A 和 B
# r=8 时，每层可训练参数从 1670 万降到 6.5 万（约 0.4%）

W  → 冻结，fp16 躺着不动                    # 原能力完整保留
A  → 随机初始化，可训练，4096×r          # 注入新知识
B  → 零初始化，可训练，r×4096            # 从 0 开始，训练初期 W'=W
Y  =  (W + alpha/r · B·A) · X              # alpha/r 是缩放系数
为什么低秩就够用：微调带来的"风格、格式、术语"变化是低维信号，不需要改整个矩阵的秩。实践中 r=8 就能覆盖绝大多数任务；r 加到 64 以上收益递减，而显存和过拟合风险线性上升。

四个核心参数怎么设

参数含义推荐值
r（rank）补丁的秩，决定容量起步 8，风格/格式任务 16，领域 CPT 32~64。7B 模型 r 超过 64 基本是浪费
lora_alpha缩放系数，实际缩放 = alpha / r习惯取 alpha = 2r（r=8 配 alpha=16），缩放稳定在 2 附近。alpha 单独调大不涨能力，只放大更新幅度
target_modules给哪些层挂补丁省显存只挂注意力：q_proj,k_proj,v_proj,o_proj；要效果挂全部线性层（含 gate/up/down_proj），显存 +20% 左右
lora_dropout防过拟合数据量大（万条以上）设 0.05~0.1；数据量小（千条）可设 0 或 0.05，避免训不动

QLoRA：在 LoRA 之上再压显存

# QLoRA 三板斧（Dettmers 等人 2023 年提出）
1. 基座权重压到 4-bit NF4（正态浮点量化，比 INT4 更适合高斯分布的权重）
   → 7B 模型权重从 14GB 降到约 4GB
2. 量化引入的误差用 双重量化 Double Quantization 再压一次
   → 每参数再省约 0.37 bit
3. 用 分页优化器 Paged Optimizers 防显存峰值溢出
   → 显存不够时把优化器状态换到 CPU 内存，长序列时不炸
# 结果：65B 模型能在单张 48GB 卡上微调；7B 在 10~14GB 就能跑

# QLoRA 配置示例（LLaMA-Factory 里就是加两行）
quantization_bit: 4
quantization_method: bnb          # bitsandbytes 实现
方案7B 权重占用效果差异
fp16 全参微调14 GB（不含优化器）基准，理论上限
LoRA（fp16）14 GB与全参几乎持平（多数任务差距在 1~2 个点内）
QLoRA（4bit）约 4 GB比 fp16 LoRA 略低但通常可忽略，性价比之王
QLoRA 的两个真实代价：① 训练吞吐比 fp16 LoRA 低 20%~40%（量化/反量化有开销，unsloth 等优化内核能补回来）；② 基座是量化加载的，导出时必须走"反量化 + merge"或继续用量化推理，直接给 vLLM 喂 4bit 权重是不支持的，要先合并再导出 fp16。
模块 4

数据准备：质量永远排在第一

微调圈的老话：Garbage in, garbage out。同样的超参，好数据和差数据的效果差距比任何调参都大。LIMA 那篇论文用 1000 条精调数据就证明了：数据质量比数量重要一个数量级。

数据量经验法则（7B 模型）

目标建议数据量说明
统一输出格式/语气500 ~ 2000 条少量即可，重点在覆盖面
垂直领域问答（有标准答案）3000 ~ 10000 条覆盖主要意图，每个意图至少几十条
领域知识 CPTGB 级纯文本不是条数概念，是 token 量
偏好对齐 DPO5000 条以上偏好对比 SFT 更需要量，太少的偏好对容易过拟合

数据清洗清单（按顺序过一遍）

去重：完全相同的样本直接删；近似重复用 MinHash/SimHash 查（两问两答 90% 相似就是重复）。重复样本会让模型复读
去噪：删空回答、删"抱歉我无法回答"占比过高的废样本、删乱码和截断的样本。训练数据里混入截断样本，模型就学会说半句话
PII 与合规：手机号、身份证、银行卡号打码或删除。微调数据会进模型权重，事后删不掉
格式统一：chat template 与推理时完全一致（同一个 tokenizer、同一套 special token）。模板不匹配是上线后效果崩掉的头号原因
负样本配比：涉及拒答/安全的数据，正负样本建议 1:1 到 3:1。负样本太少学不会拒绝，太多模型变得啥都不敢答
混入通用数据防遗忘：领域 SFT 里掺 5%~15% 的通用对话数据，显著缓解灾难性遗忘

一条真实的配比方案（客服场景 SFT）

# 总 12000 条，按意图分层抽样，保证每类都有足够样本
业务问答（订单/物流/售后规则）   8000 条   # 66.7% 主任务
多轮追问与澄清                   1500 条   # 12.5% 覆盖上下文继承
拒答与越界处理                   1000 条   #  8.3% 安全边界
通用闲聊 + 常识                  1500 条   # 12.5% 防遗忘配比

数据构造的最高性价比做法：用大模型造数据，人来审。用 GPT-4 级别模型或内部强模型按业务 schema 批量生成候选样本，再用规则 + 人工抽检（抽检 5%~10%）过滤。但注意：模型自己生成的数据会带上它的错误和偏见，人工审核环节不能省。涉及事实准确性的场景（金额、法规条款），必须业务专家逐条过。
模块 5

训练框架选型

生态很大，但个人到小团队的真实选择就四个。选框架的原则：先看你的卡，再看你的数据格式，最后看社区活跃度。

框架定位上手难度适合谁
LLaMA-Factory全功能 WebUI + 配置化，支持 100+ 模型低（有图形界面和配置文件）大多数团队的首选。WebUI 里可视化 loss、直接评估、一键导出
unsloth手写优化内核，单卡提速省显存低（Notebook 友好）单张消费卡（24GB 及以下）。比原生快约 2 倍、显存省一半以上

框架细节和模型支持列表变化很快（LLaMA-Factory 每隔几周就有新模型接入），选型前以各项目 GitHub 当前 README 为准。不要追新：选一个你团队能看懂的，把链路跑通比用最新框架重要。基座模型则建议选有商用许可的（Qwen、Llama 系看具体版本的 License），避免合规风险。
模块 6

超参与显存估算

这一节是纯干货：先会算显存，再谈调参。算错显存，训练跑到一半 OOM，一天白等。

显存构成公式（训练阶段）

# 显存 ≈ 权重 + 梯度 + 优化器状态 + 激活值 + 框架开销(10%~20%)

# 混合精度 + Adam 的"每参数字节数"经验值：
全参微调：16 字节/参数   # fp16权重2 + fp16梯度2 + fp32主权重4 + Adam的m,v各4
LoRA：    约 2 字节/参数  # 只有冻结的 fp16 权重，训练参数不到 1%
QLoRA：   约 0.5 字节/参数 # 4bit 基座 + 可忽略的适配器

# 7B 模型粗算：
全参：7e9 × 16B ≈ 112 GB  → 单张 80G 都装不下，必须多卡 ZeRO-3
LoRA：7e9 × 2B  ≈ 14 GB  → 单张 24G 可以，激活值还能放宽
QLoRA：7e9 × 0.5B ≈ 3.5 GB → 12G 显卡也能玩

# 有效 batch size 计算（最容易搞错的一点）：
global_batch = per_device_batch × gradient_accumulation_steps × GPU 数
# 4 × 8 × 1 = 32。显存不够就降 per_device，靠 accum 补回来

7B 模型训练显存对比表（seq 2048，含激活值量级参考）

项目全参数LoRAQLoRA说明
权重14 GB14 GB约 4 GBQLoRA 的 4bit 是含量化常数的近似值
梯度14 GB可忽略可忽略只有可训练参数才有梯度
Adam 状态56 GB可忽略可忽略全参的大头，占了一半以上
激活值20~40 GB20~40 GB20~40 GB随 batch × seq_len 涨。开梯度检查点后除以 4~6
合计（开检查点）80~120 GB25~40 GB10~16 GB量级参考，实测用 torch.cuda.max_memory_allocated() 验证

核心超参怎么定

超参LoRA 推荐值全参推荐值
学习率1e-4 ~ 3e-41e-5 ~ 2e-5（比 LoRA 低一个量级）
epoch2 ~ 41 ~ 2（全参更容易过拟合）
warmup3%~10% 步数同左，防早期震荡
LR 调度cosine（默认）cosine / linear
精度bf16（有 Ampere+ 卡）bf16，fp16 注意 loss 缩放
权重衰减0 或 0.010.01 ~ 0.1
学习率是唯一能"一票否决"的超参。LoRA 用全参的学习率（1e-5）会训不动；全参用 LoRA 的学习率（1e-4）会直接 loss 爆炸或 NaN。判断信号：开训后 200 步内 loss 不降 → 学率太小或数据有问题；loss 出现 NaN/尖刺 → 学习率太大，降一半再来。

模块 7

评估与过拟合

"loss 降了"不等于"变好了"。没有业务评测集的微调，等于没做评估。

三层评估体系

层级手段回答什么问题
训练曲线train loss vs eval loss 曲线有没有过拟合、学习率是否合理
通用基准C-Eval、MMLU、GSM8K、HumanEval 等（用基座同款 prompt）通用能力有没有被微调搞坏（遗忘检测）
业务黄金集200~1000 条真实场景样本 + 人工/规则评分唯一重要的指标：业务上到底变好没有

过拟合的识别信号

# 信号一：train loss 降到 0.3，eval loss 反而升到 1.2
# → 典型过拟合，减 epoch、加 dropout、扩数据

# 信号二：对训练集里的问题回答完美，换个问法就崩
# → 模型在"背答案"不是"学规律"，数据同质化太严重

# 信号三：通用基准分数大幅下滑（比如 C-Eval 掉 10 个点）
# → 灾难性遗忘，掺通用数据、降学习率、早停

# 信号四：输出开始机械复读训练数据的句式
# → 重复样本太多或 epoch 过多，先去重再降 epoch

最小可用评估脚本思路

# 1. 切分：微调数据里留出 5% 作为 eval（不许 shuffle 到训练集）
val_size: 0.05

# 2. 黄金集独立于训练数据，覆盖真实分布，人工写标准答案
# 3. 对比四个档位，别只测最终模型：
#    base（原模型） / base+prompt（好提示词） / sft / sft+DPO
# 4. 评分：客观题用规则判分，主观题用 LLM-as-judge + 人工抽检
# 5. 报告里必须写：平均分 + 分意图分数 + 拒答正确率 + 延迟
LLM-as-judge 是双刃剑：用强模型给弱模型输出打分，能覆盖主观维度（有帮助性、安全性、格式合规），但judge 自己有偏好（偏爱长回答、偏爱自己的风格）。做法：judge 打分 + 人工抽检 10% 校准，两者一致率低于 85% 就别信 judge。
模块 8

推理部署微调模型

训练完只是中点。LoRA 有两条部署路线：合并权重（简单）或在线挂 adapter（灵活）。选错路线，上线时才发现加载不了。

路线一：合并权重（最常用）

# 用 peft 把 LoRA 权重合并进基座，产出一个完整模型
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import PeftModel

base = AutoModelForCausalLM.from_pretrained("./Qwen2.5-7B-Instruct", torch_dtype="bfloat16", device_map="auto")
model = PeftModel.from_pretrained(base, "./saves/qwen7b-lora-customer")
merged = model.merge_and_unload()          # W' = W + (alpha/r)·B·A 写回权重
merged.save_pretrained("./qwen7b-customer-merged")
AutoTokenizer.from_pretrained("./Qwen2.5-7B-Instruct").save_pretrained("./qwen7b-customer-merged")

# 注意：QLoRA 训出来的适配器，合并前基座要用 fp16 重新加载
# 直接 merge 4bit 基座会得到垃圾权重

路线二：vLLM 在线加载 LoRA（多租户/频繁切换）

# 一个 vLLM 实例同时服务多个 adapter，请求时按名字选择
python -m vllm.entrypoints.openai.api_server \
  --model ./Qwen2.5-7B-Instruct \
  --enable-lora \
  --max-lora-rank 64 \
  --lora-modules customer=./saves/qwen7b-lora-customer \
  --lora-modules legal=./saves/qwen7b-lora-legal \
  --gpu-memory-utilization 0.85 \
  --max-model-len 4096

# 调用时指定用哪个 adapter（OpenAI 兼容 API 的 model 字段）
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "customer", "messages": [{"role":"user","content":"怎么退款？"}]}'
维度合并权重在线 LoRA
适用场景单一场景、追求极限性能一个基座服务多个业务、adapter 频繁迭代
显存一份完整权重基座 + 每个 adapter 少量额外（rank 越大越贵）
切换成本要重启服务请求级切换，秒级生效
性能损耗无vLLM 的 LoRA serving 有少量开销，持续优化中

上线前 checklist

apply_chat_template推理时的 chat template 必须和训练时同版本，tokenizer 一个字节都不能差
temperature=0 对拍 50 条同一输入多次采样，输出应稳定。抖动大说明训练不充分
对比 base 模型A/B 跑黄金集：sft 必须显著优于 base+好提示词，否则别上线
压测 P99 延迟与显存vLLM 参数（max-model-len、gpu-memory-utilization）按真实流量调
记录 artifact 指纹基座版本 + adapter hash + 数据版本 + 超参，缺一项无法复现
避坑

十个真实工程坑

1
数据质量差：噪声、错标、格式混乱
最常见也最致命。错误答案会被忠实学会，训练数据里 5% 的脏数据能让效果掉 20 个点。先花 70% 时间洗数据，再开训。
2
学习率张冠李戴
LoRA 用了全参的 1e-5（训不动），或全参用了 LoRA 的 1e-4（NaN）。记住差一个量级，换范式先换学习率。
3
灾难性遗忘：垂直能力上去了，通用能力崩了
只用领域数据训练的模型，常识和指令遵循明显退化。解法：掺 5%~15% 通用数据、降 epoch、监控通用基准。
4
没有评测集就开训
训练曲线好看就上线，结果业务方一测全是问题。微调前先攒黄金集，没有黄金集的项目不该立项。
5
train_on_inputs 没关，模型学会复读 prompt
loss 降得飞快，推理时把用户问题原样奉还或自顾自续写问题。训练 loss 必须只算在回答 token 上。
6
chat template 不匹配
训练用 A 模板、推理用 B 模板（或 tokenizer 版本变了），效果断崖下跌。模板和 tokenizer 要当代码一样做版本管理。
7
epoch 过多 + 样本高度重复
500 条数据训 10 个 epoch，模型进入背答案模式，换个说法就答错。小数据 2~3 个 epoch 足够，先去重。
8
基座选型只看 benchmark 分数
忽略 License（能不能商用）、多语言能力、上下文长度、生态成熟度。选错基座，训练数据全白搭。
9
LoRA 参数拍脑袋：r 盲目设 256
r 越大不等于越好：显存线性涨、过拟合风险涨、收益早就饱和。r=8~32 覆盖绝大多数任务，先小后大。
10
训完不验推理直接发布
训练 loss 正常，但推理出现空回复、无限复读、乱码 special token。上线前必须用真实推理链路（不是训练框架）抽测 100 条。
自测

六道题

1. 产品要求"问答机器人掌握公司最新的产品文档，且文档每周更新"，最该用什么方案？
正确答案：RAG。知识频繁更新 + 需要来源可追溯，是 RAG 的主场。微调的知识会过时、无法更新单条知识、还会挤占通用能力。微调适合格式/风格/能力，不适合知识库。
2. LoRA 中 lora_alpha=32、lora_rank=16，实际缩放系数是多少？作用是什么？
正确答案：alpha/r = 2。缩放系数控制补丁的影响力，习惯取 alpha=2r 让缩放稳定。可训练参数量由 r 和 target_modules 决定，与 alpha 无关。
3. 7B 模型做全参数微调（混合精度 + Adam），权重/梯度/优化器状态大约占多少显存？
正确答案：约 112 GB。混合精度训练每参数约 16 字节：fp16 权重 2 + fp16 梯度 2 + fp32 主权重 4 + Adam 的 m/v 各 4。7B × 16B ≈ 112GB，再算激活值。这就是全参必须多卡分片、而 LoRA 单卡可跑的原因。
4. 相比 PPO，DPO 的主要优势是？
正确答案：不需要奖励模型。PPO 要同时加载策略、参考、奖励、价值四个模型，显存爆炸且超参敏感；DPO 直接在偏好对上做监督学习，只用策略 + 参考模型。业务场景先试 DPO，不够再上 PPO。
5. 训练中 train loss 降到 0.35，eval loss 却从 0.9 升到 1.2，说明什么？怎么办？
正确答案：过拟合。train/eval loss 背离是教科书级信号。解法：减少 epoch、提高 lora_dropout、扩充数据、检查重复样本。同时用通用基准确认是否伴随灾难性遗忘。
6. 微调模型上线后，模型经常把用户的问题原样复述一遍再回答，最可能的原因是？
正确答案：prompt 的 loss 没屏蔽。如果训练目标包含输入 token，模型会学会"复读并续写输入"。正确做法是只在回答 token 上计算 loss（各框架里对应 train_on_inputs=false 或 completion-only loss）。
