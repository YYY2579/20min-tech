模块 1

从关键词检索到语义检索

先看清楚传统关键词检索（如 Elasticsearch 的 BM25）为什么会漏，才能理解语义检索补上了什么。

关键词检索的局限

问题例子
同义词用户搜"笔记本"，文档里写的是"笔记本电脑"，BM25 因为词不匹配而漏召回
表述差异问"怎么重启服务"，文档标题是"服务进程的重新拉起方法"，字面几乎不重叠
多语言中文问、英文答，词表完全不交叉
口语与术语用户说"卡住了"，文档写"响应超时 / 阻塞"，靠词形匹配不到

语义检索的原理差异

维度关键词检索（BM25）语义检索（向量）
匹配依据词是否出现、出现频率、逆文档频率语义向量之间的空间距离
强项精确匹配：订单号、错误码、人名、专有名词模糊表达、同义改写、跨语言
弱项换个说法就找不到精确串（如"ERR_5021"）可能被语义"平滑"掉，反而不准
可解释性高，能指出命中哪个词低，只能给出相似度分数
结论：两者不是替代关系，而是互补。真实系统几乎都做混合检索（Hybrid Search）：向量检索负责"语义召回"，关键词检索负责"精确召回"，然后把两路结果融合（常用 RRF，Reciprocal Rank Fusion，倒数排名融合，即按两路的排名倒数相加重新排序）。
实践建议：先做向量检索跑通，再补关键词检索。别一上来就砍掉关键词——很多"搜不到订单号"的线上问题，都是因为只用向量。
模块 2

向量嵌入 Embedding

嵌入（Embedding）就是把一段文本送进嵌入模型，得到一个固定长度的浮点数数组，例如 [0.013, -0.244, 0.087, ...]，共 1536 个数。这个数组就是文本在"语义空间"里的坐标。

分词：文本先被切成 token。
编码：token 经过模型编码成上下文相关的表示。
池化：把整段话的表示"压缩"成一个固定长度的向量（通常取平均或取特殊 token 的输出）。
归一化：很多模型会顺手把向量长度缩到 1，方便后续用点积算相似度。

嵌入模型的选型维度

维度怎么权衡
维度常见 384 / 768 / 1024 / 1536 / 3072。维度越高表达力越强，但存储和计算成本成正比。很多模型支持"降维输出"（如 1536 → 512），牺牲一点精度换 3 倍存储节省
语言纯英文模型在中文上会明显退化。中文场景必须选多语言模型或中文专优模型
领域通用模型在医疗/法律/代码等垂直领域可能不够准。有些厂商提供领域嵌入模型
成本API 按 token 计费（通常比生成模型便宜得多）；自建则要算 GPU 成本
是否可本地部署数据敏感、离线场景必须本地跑（如 bge、m3e 这类开源模型）。本地部署意味着没有网络延迟、数据不出域
最大输入长度多数嵌入模型只能吃 512 个 token 左右，超长会被截断。这直接约束了你的切分大小
最容易混淆的一点：嵌入模型和生成模型是两回事。
① 嵌入模型：输入文本 → 输出向量。只做"表示"，不能生成文字，也几乎不能推理。典型用途是检索、聚类、去重。
② 生成模型（就是第 18 期讲的大模型）：输入文本 → 输出文本。
它们可以来自同一个厂商，但接口、模型名、计费、能力完全不同。别指望嵌入模型回答你的问题，也别用生成模型去算向量。 
# 用 API 生成嵌入（伪代码，接口大同小异）
resp = client.embeddings.create(
    model="text-embedding-3-small",
    input=["如何重启服务", "服务进程重新拉起的方法"],   # 可批量，省钱又省时间
)
v1, v2 = resp.data[0].embedding, resp.data[1].embedding
# 这两句话字面几乎不重叠，但向量会非常接近 —— 这就是语义检索能召回到的原因

# 关键工程原则：入库和查询必须用同一个嵌入模型
# 换了模型 = 向量空间变了 = 旧索引全部作废，必须全量重建
模块 3

相似度度量

向量库要回答的问题是"哪几个向量离查询向量最近"。怎么定义"近"，有三种常见度量，选错会直接影响效果。

度量含义适用
余弦相似度看两个向量的夹角，范围 -1~1，越接近 1 越相似。忽略向量长度文本检索默认选择。因为文本相似度关心"方向"而非"长短"
点积两个向量对应元素相乘再求和。同时受方向和长度影响归一化后等价于余弦。推荐系统常用，因为向量长度本身可能编码了"热度/置信度"
欧氏距离空间中两点的直线距离，越小越相似坐标本身有物理意义的场景（如图片特征、地理位置向量）
# 归一化后，余弦与点积等价（这是向量库能用点积加速的根本原因）
cos(A, B) = (A · B) / (|A| * |B|)

# 若 |A| = |B| = 1，则分母为 1，于是：
cos(A, B) = A · B        # 余弦 = 点积

# 欧氏距离与余弦的关系（向量归一化后）
||A - B||² = ||A||² + ||B||² - 2·A·B = 2 - 2·cos(A,B)
# 所以归一化后，欧氏距离和余弦也是单调对应的，排序结果一致
为什么内积（点积）适合推荐场景？因为推荐里我们往往希望"既相似又热门"的排前面。如果向量长度编码了"流行度"（训练时用交互次数加权），那么点积会同时奖励方向一致（相似）和长度大（热门）。而余弦把长度归一化掉了，就只看相似度。这就是同一个技术在不同场景的取舍。
实操建议：① 文本检索，选余弦，或者把向量归一化后用点积；② 选定一种度量后，建索引时也要声明同一种度量，两者不一致会导致结果完全错乱；③ 不同嵌入模型的输出尺度不同，不要混用不同模型产生的向量。
模块 4

ANN 近似最近邻索引

暴力搜索（Brute-force / Flat）就是拿查询向量和库里每一个向量算一遍距离，再排序。它结果 100% 准确，但复杂度是 O(N)。100 万条、1536 维的向量，一次查询要算 15 亿次浮点乘法 —— 单次可能几百毫秒，高并发直接崩。
ANN（Approximate Nearest Neighbor，近似最近邻）的思路是：牺牲一点点召回率，换取几个数量级的加速。

四类索引的原理与适用

索引原理适用
HNSW
图索引		构建一个多层的"近邻图"，查询时像走高速一样从稀疏上层快速靠近，再在下层精细搜索首选。召回率和延迟都好，适合内存充足的场景。缺点是内存占用大、构建慢
IVF
倒排		先用聚类把向量分成 N 个"桶"（簇），查询时只搜最近的几个桶数据量大、内存紧张。通过 nprobe 控制搜几个桶，权衡速度与召回
PQ
乘积量化		把高维向量切成小段，每段用一个小码本压缩成几个字节，大幅省内存超大规模、内存吃紧。精度损失较大，常和 IVF 组合成 IVF-PQ
LSH
局部敏感哈希		用一组哈希函数，让相似的向量更可能落到同一个桶原理简单、支持流式更新，但召回率一般，现在较少作为首选

关键参数含义

参数含义与调优方向
HNSW: M每个节点在图中保留的邻居数。越大召回越高、内存越多、构建越慢。常用 16~48，默认 16
HNSW: efConstruction建图时的搜索广度。越大图质量越好、构建越慢。常用 100~500
HNSW: efSearch查询时的搜索广度。越大召回越高、延迟越高。这是最常调的旋钮，典型 64~256
IVF: nlist聚类成多少个桶。经验值约为 sqrt(N)，即 100 万条约用 1000
IVF: nprobe查询时搜几个桶。越大召回越高越慢。典型取 nlist 的 1%~10%
PQ: m / nbits切几段、每段用几位编码。段数越多精度越高、压缩率越低
调参的本质是一次权衡：召回率 ↔ 延迟 ↔ 内存，三者不可能同时最优。工程做法：先用一组默认参数跑通，再用真实查询集测"召回率@K"（即 ANN 返回的前 K 条里，有多少是暴力搜索真正的前 K 条）。召回率低于 90% 就调大 efSearch 或 nprobe，直到满足业务要求。不要凭感觉调参。
一个反直觉但重要的点：向量库返回的相似度分数，只在同一批数据、同一模型、同一度量下可比。它不是概率，不能说"相似度 0.8 就是 80% 相关"。设阈值时要基于你自己的数据分布去测，别照搬别人文章里的 0.7。
模块 5

选型对比：六个常见选项

这是最常被问、也最容易过度设计的一节。绝大多数项目的正确起点是 pgvector，而不是先上一个独立的向量数据库。

方案定位规模与特点代价
pgvectorPostgreSQL 扩展千万级以内很舒服。能用 SQL 和元数据一起过滤，事务一致超大规模（亿级+）性能不如专用库；调优要懂 PG
Milvus专用向量数据库亿级到百亿级，分布式、可水平扩展，索引种类最全部署运维最重（依赖 etcd、对象存储、消息队列），小项目属于杀鸡用牛刀
Qdrant专用向量数据库Rust 实现，单机性能好，过滤（payload filter）能力很强，部署简单超大规模需要集群版；生态比 Milvus 略小
Weaviate专用向量数据库内置混合检索、模块化（可挂嵌入/生成模型），开箱即用的 RAG 能力抽象层多，调优不如裸库直观；资源占用偏高
Redis缓存 + 向量（Redis Stack）如果你已经在用 Redis，加个模块就能做向量检索，延迟极低内存成本高；持久化和大规模检索不如专用库
Elasticsearch搜索平台BM25 关键词检索 + 向量检索原生一体，混合检索最顺手资源消耗大；向量检索性能不如专用库；运维成本高

选型建议（按场景）

数据 < 1000 万，已有 PG
直接用 pgvector。省一个中间件、省一套运维，还能和业务表 join、用事务。90% 的项目停在这里就够了。
要混合检索，已有 ES
用 Elasticsearch。关键词和向量在一个系统里，不用维护两套。
千万~亿级，要独立扩展
选 Qdrant（轻）或 Milvus（重但能上规模）。优先 Qdrant，除非确实要百亿级。
要开箱即用的 RAG
试 Weaviate，它把嵌入、检索、生成串好了，快速验证想法很方便。
最常见的过度设计：数据才几万条，就上 Milvus 集群 + etcd + MinIO，结果运维复杂度远超收益。先问自己三个问题：① 数据量到底多少（几万？几百万？几亿？）；② 是否需要和现有数据库做事务性操作；③ 团队有没有人能运维分布式系统。三个问题的答案往往指向 pgvector。
模块 6

RAG 落地细节：切分、过滤、重排

向量库只是"存和找"。真正决定 RAG 效果好坏的，是怎么切、怎么过滤、怎么重排。这一节是实战含量最高的部分。

文档切分策略

策略做法取舍
固定长度按 token 数切（如 512），带重叠实现最简单。可能切断句子和语义单元，需要重叠来缓解
按结构按标题、段落、代码块、表格切推荐。尊重文档原有结构，语义完整度高
按语义用嵌入模型判断相邻句子是否"同话题"，在话题切换处切效果好但计算成本高，适合高价值文档
父子切分小块用于检索，命中后返回它所属的大块给模型检索准 + 上下文全，是当前较优实践
切分是最容易翻车的一步，记住两条：
① 切太碎 → 单个 chunk 语义不完整（比如把一句话切成两半），检索出来看不懂，模型也无从回答；
② 切太大 → 一个 chunk 混了好几个话题，向量变成"平均语义"，谁都不像，检索反而不准，还挤占上下文。
经验值：中文 300~800 字（约 300~800 token），重叠 10%~20%。但这个数必须用你的数据实测，不同文档类型差别很大。

元数据过滤（Metadata Filtering）

元数据就是跟着每个 chunk 一起存的"标签"：来源文档、章节、创建时间、部门、权限等级、语言。它的作用是在向量检索之前先把范围缩小。

# 没有元数据过滤：查询"今年的报销标准"
# 向量检索可能召回 2020 年的旧政策 —— 语义很像，但答案已经作废

# 有元数据过滤：先限定 year = 2026 AND dept = 'finance'
# 再在符合条件的数据里做向量检索，结果就对了

# 关键点：权限也必须靠元数据过滤来实现
# 否则员工 A 可能检索到员工 B 的隐私文档 —— 这是安全事故，不是效果问题

召回数量与重排（Rerank）

先粗召回：向量检索取 Top-K（K 通常 20~100），目标是尽量不漏，宁多勿缺。
再重排：用重排模型（cross-encoder，把"问题 + 候选"一起送进模型精算相关性）对这 K 条重新打分。
后精选：取重排后的 Top-N（N 通常 3~8），拼进提示词。N 越小越省 token、噪声越少。
为什么"召回多 + 重排精"比"直接召回想取的条数"好？因为向量检索是"粗筛"，靠的是语义距离，容易把真正相关的排在第 15 位。重排模型更慢但更准，能在更大的候选池里挑出真正的前几名。这是提升 RAG 准确率性价比最高的一步。

上下文拼装的顺序与长度控制

  • 顺序：把最相关的放最前面和最后面。因为长上下文里模型对开头和结尾更敏感，中间容易被忽略。
  • 长度：总输入控制在模型窗口的一半以内，给输出和后续对话留余量。输入越长越贵、越慢、越容易分心。
  • 去重：同一文档的重叠 chunk 会重复出现，要按来源去重，避免同一段话说三遍。
  • 标注来源：给每个片段编号，要求模型回答时引用编号，便于追溯和展示。

多路召回

同一个问题，从多个角度同时召回，再融合结果，能显著提升覆盖率：

路子说明
向量召回语义相似，覆盖同义改写
关键词召回BM25，覆盖精确串（订单号、错误码、专有名词）
多查询改写让大模型把原问题改写成 3~5 个不同说法，分别召回再合并（Multi-Query）
假设性答案先让模型"猜"一个答案，再用这个答案去检索（HyDE）。答案的语义往往比问题更接近文档
模块 7

性能、成本与运维

向量库上线后，真正让人头疼的是这三件事：构建要多久、内存要多少、数据怎么更新。

内存占用估算

# 纯向量数据的理论内存（不算索引和元数据开销）
内存 = 向量条数 × 维度 × 每维字节数

# 例：1000 万条 × 1536 维 × 4 字节(float32) = 61.4 GB
# 这还没算 HNSW 索引本身（图结构通常再增加 30%~100%）
# 加上索引后，1000 万条 HNSW 实测量级在 80~120 GB

# 省钱手段：
# 1) 降维：1536 → 512，存储直接省 2/3，精度损失通常可接受
# 2) 量化：float32 → int8，省 4 倍；或用 PQ 压缩，省 10~30 倍
# 3) 冷热分离：不常查的历史数据放磁盘索引（如 DiskANN）

索引构建时间

HNSW 是增量可插入的，但批量导入时构建索引比逐条插入快得多。所以初始导入应该：先关索引（或不建索引）灌数据，全部导完再统一建索引。逐条插入 + 实时建图，速度可能慢一个数量级。

增量更新与删除

操作注意事项
新增直接插入即可，HNSW 支持在线插入，但频繁插入会让图结构退化，建议定期重建
更新向量变了通常要先删后插。很多库不支持"原地改向量"
删除部分实现是"标记删除"（软删），空间不会立即回收，需要定期压实（compaction）
换嵌入模型必须全量重建。新模型的向量空间和旧的不兼容，混在一起检索结果完全错乱

备份与高可用

  • pgvector：跟着 PostgreSQL 的备份方案走（物理备份 / 逻辑备份），最省心。
  • 专用向量库：用自带的快照功能，快照体积可能很大（向量 + 索引），要单独规划存储和恢复时间。
  • 高可用：单机 Qdrant/Milvus 挂了服务就断了。生产要评估是否需要副本。pgvector 直接复用 PG 的主从，是它的一大优势。

监控指标

指标为什么重要
召回率 @K用离线查询集定期测，这是检索质量的核心指标，比延迟更重要
查询延迟 P50 / P95 / P99P99 才反映真实体验，平均值会掩盖长尾
QPS / 并发判断是否需要扩容或调整索引参数
内存使用率向量库通常是内存密集型，接近上限就要扩容或量化
索引构建进度重建索引期间资源会飙升，要避开业务高峰
过滤命中率如果元数据过滤后候选集过小，会显著影响召回，需要预警
一个常被忽略的运维风险：索引构建的内存峰值。重建 HNSW 索引时，内存占用会短暂接近翻倍（旧索引 + 新索引同时存在）。在内存已经用到 70% 的实例上直接重建，很可能触发 OOM。做法：预留足够内存、在低峰期重建、或者用新实例建好再切流量。
常见坑

十个工程坑

1
切分太碎，语义断裂
把一句话切成两半，检索出来的 chunk 自己都看不懂，模型无从回答。合理粒度中文 300~800 字，并加 10%~20% 重叠。
2
切分太大，检索不准
一个 chunk 混了多个话题，向量变成"平均语义"，谁都不像。用按结构切分或父子切分解决。
3
只用向量检索，不用关键词
搜订单号、错误码、专有名词时，向量可能把精确串"平滑"掉，导致搜不到。要用混合检索。
4
没有元数据过滤，召回无关内容
召回了过期政策、别的部门文档、无权限内容。元数据过滤既是效果问题，也是安全问题。
5
换了嵌入模型但没重建索引
新旧向量不在同一语义空间，混在一起检索结果完全错乱。换模型必须全量重建。
6
忽略索引构建的内存峰值
重建索引时内存可能接近翻倍，在已用 70% 内存的实例上重建会 OOM。低峰期重建或换实例。
7
把向量库当主数据库用
向量库不擅长复杂事务、关联查询、强一致。它只负责"存向量 + 找近邻"，业务数据还是放关系库。
8
相似度阈值照搬别人的数字
相似度不是概率，不同模型、不同数据分布下尺度完全不同。0.7 在别人的数据里是"相关"，在你的数据里可能毫无意义。
9
只用单一索引参数，从不测召回率
HNSW 的 efSearch、IVF 的 nprobe 直接决定召回质量。不测召回率就调参，等于闭着眼睛开车。
10
盲目上专用向量数据库
数据才几万条就上 Milvus 集群，运维复杂度远超收益。绝大多数项目 pgvector 就够了。
自测

六道题

1. 用户搜"笔记本"，文档里写的是"笔记本电脑"，关键词检索漏召回。这体现了什么问题？
正确答案：关键词检索的固有局限。BM25 靠词形匹配，同义词、改写表达都召不回。语义检索能补上，但精确串（订单号）还得靠关键词，所以要混合检索。
2. 关于嵌入模型和生成模型，哪个说法是对的？
正确答案：两者是两回事。嵌入模型输入文本输出向量，用于检索/聚类/去重；生成模型输入文本输出文本。可以来自同一厂商，但绝不可混用。
3. 文本检索场景最常用的相似度度量是？
正确答案：余弦相似度。它只看方向、忽略长度，符合"文本相似度与长度无关"的直觉。归一化后余弦等价于点积，所以向量库常用点积加速。
4. HNSW 索引里，查询时控制"召回率 ↔ 延迟"权衡的关键参数是？
正确答案：efSearch。它是查询时的搜索广度，调大召回高但慢，调小快但可能漏。M 影响图结构和内存，efConstruction 影响构建质量与构建时间。
5. 一个已有 PostgreSQL、数据量约 500 万条的团队要做向量检索，最合理的起点是？
正确答案：pgvector。千万级以内很舒服，还能和业务表 join、用事务、复用 PG 主从备份。上专用库只在规模或过滤需求真正超出时才划算。
6. 提升 RAG 准确率，性价比最高的一步通常是？
正确答案：多召回 + 重排。向量检索是粗筛，真相关的内容可能排在十几位；重排模型更慢但更准，能在更大的候选池里挑出真正的前几名。切太碎反而破坏语义。

术语表

术语一句话解释
语义检索按语义相似度而非字面匹配来检索，靠向量距离实现
Embedding 嵌入把文本映射成固定长度的向量，语义相近则向量距离近
向量维度向量的长度，常见 384~3072，越高表达力越强、成本越高
余弦相似度看两向量夹角，只关心方向不关心长度，文本检索默认度量
点积同时受方向和长度影响，归一化后等价于余弦，推荐场景常用
欧氏距离空间直线距离，越小越相似，适合坐标有物理意义的场景
归一化把向量长度缩到 1，使余弦与点积等价，便于加速
ANN近似最近邻，牺牲少量召回率换取大幅加速
HNSW多层近邻图索引，召回高延迟低，内存占用大
IVF倒排文件索引，先聚类分桶，查询时只搜最近的几个桶
PQ乘积量化，把向量压缩成极少量字节，大幅省内存
LSH局部敏感哈希，让相似向量更可能落到同一个桶
efSearchHNSW 查询广度，调大召回高但慢，是最常调的旋钮
nprobeIVF 查询时搜几个桶，越大召回越高越慢
召回率 @KANN 返回的前 K 条里，有多少是暴力搜索真正的前 K 条
Chunking 切分把长文档切成小块，供向量化与检索
元数据过滤按标签（时间/部门/权限）先缩小范围再做向量检索
Rerank 重排用更准的模型对召回结果重新排序，提升相关性
混合检索向量 + 关键词两路召回并融合，兼顾语义与精确匹配
RRF倒数排名融合，按各路排名倒数相加来合并多路召回结果
