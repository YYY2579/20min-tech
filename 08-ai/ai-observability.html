开始前

先搞清楚：传统监控失明在哪

传统可观测性假设系统是确定性的：同样的输入必然产生同样的输出，所以"请求 200、延迟 50ms"就等于"服务正常"。LLM 应用打破了这个假设——

# 同一个请求，两次调用，HTTP 层完全一致：
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" -X POST $API/chat \
  -d '{"q":"我们支持7天无理由退货吗"}'
200 1.832s
curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" -X POST $API/chat \
  -d '{"q":"我们支持7天无理由退货吗"}'
200 1.805s

# 但响应内容可能是：
"支持。签收后7天内可无理由退货，运费由商家承担。"   # 正确
"不支持。本公司商品一经售出概不退换。"               # 与知识库矛盾（幻觉/检索失败）
"抱歉，我无法回答这个问题。"                         # 过度拒答

# → 监控一切正常，业务已经在出事。这就是本篇要解决的问题。
核心差异三条：① 非确定性——同样的输入可能有不同的输出，质量是个分布不是开关；② token 成为一等公民——延迟、成本、限流都由 token 驱动，请求数不再够用；③ 质量本身成为观测对象——必须把"回答得好不好"变成可持续采集的信号，而不只是上线前跑一遍评测。
模块 1

传统 vs AI 可观测性

维度传统 Web 服务LLM 应用
健康定义状态码 200 + 延迟达标 = 健康还要加质量信号：相关性、groundedness、拒答率、用户反馈
延迟度量总延迟，P50/P99总延迟 + TTFT（首 token 延迟） + 每 token 生成速率，流式场景三者体感不同
计量单位QPS、请求数token 数（输入/输出分开）、上下文长度、模型版本、缓存命中
成本信号基础设施成本（CPU/内存/带宽）按请求/按 token 的模型调用成本，通常远超基础设施成本
故障模式5xx、超时、连接拒绝还包括：格式崩坏、幻觉、过度拒答、内容审核拦截、token 截断（finish_reason=length）
归因难度服务 → 接口 → 依赖请求 → 检索质量？prompt 版本？模型版本？缓存？ 变量多且互相纠缠
变更影响代码发布代码 + prompt + 模型版本 + 知识库更新，四个变量都能改变行为
推论：AI 可观测性 = 传统三支柱（指标/日志/追踪）+ 两个新增量：token 维度与质量维度。前者是计量问题，后者是评估问题（评估体系详见本系列评估篇），本篇讲怎么把它们接进日常运维。
模块 2

追踪：一次请求的 trace 长什么样

RAG/Agent 应用的一次用户请求，天然是一条多段流水线。trace 的设计目标：任何质量问题，能沿着 span 树定位到是哪一段出的错。

# 一次 RAG 问答的 span 树（每个 span 记录耗时 + 关键属性）
trace: rag-query (整个请求，根 span)
├── s1  input_guard          输入审核/注入检测        12ms
├── s2  embed_query          查询向量化                45ms
├── s3  vector_search        向量检索 top-k            38ms   ← 检索质量
│       attrs: k=5, 命中数, 最高分 0.82, 阈值过滤后剩 3
├── s4  rerank               重排序                    60ms   ← 可选
├── s5  prompt_build         prompt 组装                2ms   ← prompt 版本 v2.3
│       attrs: system_hash, 模板版本, 上下文 token 数 2143
├── s6  llm_chat             模型生成（流式）          2100ms  ← 生成质量
│       attrs: model=gpt-4o-mini, ttft=380ms, 输出 token=612,
│              finish_reason=stop, temperature=0.3
├── s7  output_guard         输出审核/脱敏/schema     180ms
└── s8  log_persist          落库                       15ms

# 定位问题的标准路径：
# 回答与知识库矛盾 → 先看 s3 检索命中了什么 → 命中对但 s6 没用上 → prompt/生成问题
# 回答引用不存在 → s6 生成问题 → 看 prompt 版本和模型版本有没有变
# 延迟突增 → 看哪段 span 变长（s6 的 ttft 还是 s3 的检索）

span 设计的四条军规

  • 每个外部调用一个 span：模型调用、检索、rerank、工具调用各占一个，不要揉成一个"处理中"的大 span。
  • 属性（attribute）带上定位所需的全部上下文：模型名、prompt 模板版本、top-k、阈值、token 数、缓存命中与否。缺了这些，出了事只能看耗时。
  • prompt 全文不要塞进 span 属性（体量爆炸、隐私风险），存哈希 + 版本号，全文去日志系统按需查。
  • 流式生成记两个时间点：请求发出到首 token（TTFT）、首 token 到结束（生成阶段），合并记一个总延迟会丢掉关键信息。

OpenTelemetry GenAI 语义约定

OTel 社区制定了 GenAI 专用语义约定（semantic conventions），让不同厂商的 LLM 追踪可以落到同一套属性名上。属性名以 semconv 当前版本为准，以下为常见核心属性：

属性示例值 / 说明
gen_ai.operation.namechat / embeddings / execute_tool
gen_ai.systemopenai / gcp.gemini 等，标识提供商
gen_ai.request.model请求的模型名
gen_ai.request.temperature / top_p / max_tokens采样参数
gen_ai.usage.input_tokens / output_tokenstoken 用量（部分厂商拆更细，如 cached_tokens）
gen_ai.response.model实际响应的模型（可能与请求不同）
gen_ai.response.finish_reasonsstop / length / tool_calls
server.address / server.port调用的服务端点
error.type错误分类，遵循 OTel 通用约定
# 用 OpenTelemetry Python SDK 给 LLM 调用打 span（伪代码，API 以当前文档为准）
from opentelemetry import trace
tracer = trace.get_tracer("rag-service")

def chat_with_span(messages, model):
    with tracer.start_as_current_span("chat " + model) as span:
        t0 = time.time()
        first_token_at = None
        chunks = []
        for chunk in client.chat.completions.create(model=model, messages=messages, stream=True):
            if first_token_at is None:
                first_token_at = time.time()
            chunks.append(chunk)
        # ---- 落属性：出问题时就靠这些定位 ----
        span.set_attribute("gen_ai.system", "openai")
        span.set_attribute("gen_ai.request.model", model)
        span.set_attribute("gen_ai.usage.input_tokens", usage.input_tokens)
        span.set_attribute("gen_ai.usage.output_tokens", usage.output_tokens)
        span.set_attribute("gen_ai.usage.time_to_first_token_ms", (first_token_at - t0) * 1000)
        span.set_attribute("gen_ai.response.finish_reasons", finish_reason)
        return "".join(chunks)
token 用量拿不到怎么办？流式响应的最后几个 chunk 才带 usage（且部分厂商默认不返回，需要在请求里开 stream_options: {"include_usage": true} 之类的开关——具体参数以厂商文档为准）。拿不到就按 tokenizer 本地估算，并在文档里注明"估算值"，别让成本大盘建立在不准的数上。

模块 4

日志：prompt/response 留存与隐私

LLM 日志是双刃剑：不留，出问题无法复盘；全留，就是一份完整的"用户敏感信息 + 商业机密"档案，还面临删除权（用户要求删除个人数据时，日志算不算？）的合规难题。

分层留存策略（推荐默认值）

数据类型保留期限说明
trace 元数据
（耗时、token、模型、状态码）		永久 / ≥1 年不含内容，体积小，是成本和质量趋势分析的基础
prompt/response 全文30~90 天明文留存便于调试；到期自动清除，写入存储桶生命周期策略
脱敏后全文
（PII 替换后）		1 年用于长期质量分析、评测集构建，不触碰原始敏感信息
被拦截/降级的请求≥6 个月安全审计与合规留证需要（与备案要求对齐，以现行规定为准）

落到工程的四个动作

采样落盘：全量 trace 太贵，正文按 5%~10% 抽样存（出错请求、被拦截请求 100% 存），元数据全量存。
写入前脱敏：PII 检测做在"离开应用进程之前"（Presidio 或正则，见护栏篇），脱敏规则和业务库保持一致。
删除链路：用户行使用户 ID 索引所有日志（trace 带 user_id 属性），收到删除请求能定位并清除——做不到可删除的留存等于给未来埋雷。
访问控制：明文日志按"需知才给"授权，访问本身记审计；调试走脱敏环境，生产明文要审批。
# 日志管线的两个关键点：先脱敏后落盘；user_id 贯穿全链路
def persist_trace(trace, user_id, sample_rate=0.1):
    # 1. 元数据全量落（便宜）
    metrics_store.write(trace.metrics_only())

    # 2. 正文抽样 + 脱敏后落（合规）
    if random.random() < sample_rate or trace.blocked:
        redacted = pii_redactor.redact(trace.full_text())      # 先脱敏
        object_store.put(
            key=f"traces/{date}/{trace.id}.json",
            body=redacted,
            tags={"user_id": user_id},                    # 删除链路靠它
            lifecycle_days=365,                      # 存储桶策略兜底
        )
最贵的错误：把 prompt 日志当"普通应用日志"处理。它会顺理成章地流进 ELK/Loki，跟着应用日志的默认保留期（有的团队是永久）活下来，且没有按 user_id 删除的能力。等合规审计或用户行使删除权时，你会发现要改的是整个日志架构。
模块 5

评估与观测的结合：在线抽样评估

离线评测回答"这个版本好不好"，在线评估回答"线上现在好不好"。后者是观测系统的核心增量：把评估从"发布前跑一次"变成"持续在跑的采样任务"。

在线信号的四个来源

信号采集方式优缺点
显式用户反馈点赞/点踩、评分、投诉入口最真实但覆盖率低（通常 <5% 用户会点），且生气的人更爱点
隐式行为信号重新生成率、复制率、会话放弃率、转人工率覆盖全量用户；"重新生成"是质量差的最强代理指标之一
LLM-as-Judge 抽样对 1%~5% 请求自动评分（相关性、groundedness、安全性）覆盖可控、维度全；judge 自身有偏，要定期和人工对齐
规则校验schema 通过率、引用有效率、拒答率、截断率零成本确定性信号，先于一切复杂评估
# 在线抽样评估的最小实现
def online_eval(trace):
    if not should_sample(trace, rate=0.02):     # 2% 抽样，按流量自适应
        return
    score = judge_score(
        question=trace.question,
        answer=trace.answer,
        contexts=trace.retrieved_chunks,
        rubric="faithfulness,relevance,safety",
    )
    quality_gauge.labels(model=trace.model, route=trace.route).set(score)
    if score < 0.6:
        bad_case_queue.push(trace.id)     # 进人工复盘队列

# judge 的 prompt 要固定版本，评分口径变化 = 指标断点
# 定期抽 100 条人工复评 judge 结论，偏差 >15% 就校准 judge prompt
judge 评分是"合成指标"，有两个已知坑：① 位置偏置——judge 倾向于给长回答高分、给第一个出现的选项高分， rubric 里要显式约束；② 自我偏好——用 GPT-4 评 GPT-4 的输出分会虚高，跨厂商组合更稳。改 judge 的 prompt 或模型版本，等于换了尺子，历史曲线要在看板上标注"口径变更"。
模块 6

告警设计：质量退化怎么发现

AI 应用最典型的故障不是 5xx 风暴，而是无声的质量退化：prompt 改版、模型静默更新、知识库变更、缓存策略调整，任何一个都可能让错误率保持 0% 的同时质量崩掉。告警必须覆盖这类"看起来正常"的故障。

告警分层

层级信号（示例规则）响应
P0 可用性错误率 > 1% 持续 5min；TTFT P99 > 5s；模型侧 429/5xx 飙升电话 + 自动降级（切备用模型/备用路由）
P1 质量judge 质量分 24h 滑动均值降 > 10%；截断率 > 5%；引用失效率 > 10%IM 告警，当班排查 prompt/模型/知识库变更
P1 成本日成本 > 预算 120%；输入 token 量较 7 日基线 > 3 倍查缓存命中、查异常流量、必要时限流
P2 趋势缓存命中率连降 3 天；输出 token 均长逐周上升 15%周报跟进，不打扰当班
# 质量退化告警（PromQL 示例）
# 规则：24h 滑动均值较前 24h 下降超过 10%
# expr:
#   (
#     avg_over_time(llm_quality_score[24h])
#     / avg_over_time(llm_quality_score[24h] offset 24h)
#   ) < 0.9
# for: 30m

# 成本突增（输入 token 3 倍突增，抓缓存失效/上下文膨胀/恶意刷量）
# expr:
#   sum(increase(llm_tokens_total{type="input"}[1h]))
#     > 3 * sum(increase(llm_tokens_total{type="input"}[1h] offset 25h))
# for: 15m
告警要能指向"最近的变更"。给看板和告警通知带上"最近 24h 内的 prompt 版本 / 模型版本 / 知识库更新时间"——80% 的质量退化是变更引起的，值班人第一眼看到变更记录，排查从半小时缩到五分钟。变更事件本身也要作为指标/事件流接入（deploy 事件、prompt 发布事件、模型路由切换事件）。

要快，本周上线

模块 8

十个工程坑

1
只观测基础设施，不观测模型行为
CPU/内存/GPU/网络全套大盘，唯独没有"模型回答质量"任何一个指标。正确率跌到 60% 监控一片绿。质量指标（judge 分、引用有效率、拒答率）必须进大盘。
2
全量 prompt/response 明文无限期留存
日志系统成了敏感信息档案馆，用户行使删除权时无法响应，合规审计直接卡死。分层留存 + 写入前脱敏 + user_id 索引，三件套必须在第一版就做。
3
只有聚合指标，没有 trace 明细
"平均延迟涨了 800ms"然后呢？没有 span 树，定位不到是检索慢、生成慢还是审核慢。聚合指标告警，trace 明细定位，两者缺一不可。
4
延迟只看平均值，不看 P99 和 TTFT
流式产品用户体感由首 token 决定：均值 1s 但 TTFT P99 8s，用户早以为死了。分位数 + TTFT 单独看，生成速率（token/s）也要看。
5
评估只在上线前跑，线上没有持续评估
上线时 95 分，三个月后知识库污染、prompt 被顺手改过、模型静默更新，质量悄悄滑坡没人知道。在线抽样评估是"质量监控"，不是可选项。
6
告警只看错误率，不看质量分
错误率 0% 和质量全崩可以同时成立——模型稳定地返回错误答案时 HTTP 层毫无异常。质量类指标要有独立告警通道。
7
prompt 没有版本管理
线上回答风格突变，排查时发现有人上周手动改过 prompt，没人记得改了什么。prompt 进 git，发布带版本号，trace 属性里记录 prompt 版本——和代码发布同等纪律。
8
span 粒度过粗，一个"处理中"包打天下
请求内部 2 秒花在哪完全黑盒。至少拆出：审核、检索、rerank、prompt 组装、模型调用、输出校验，每段带属性。
9
忽略 token 用量突增信号
输入 token 三倍暴涨，可能是缓存集体失效、上下文无限增长、有人刷量、或 retry 风暴——每一个都直接等于成本事故。token 曲线要和延迟曲线同等地位。
10
把抽样评估的结论当全量真相
2% 抽样的 judge 分只代表那 2%，流量结构变化（比如某渠道占比升高）会让分数漂移。抽样要分层（按路由/模型/渠道），看板标注样本量，结论要带置信意识。
自测

六道题

1. 模型稳定地开始返回错误答案，但 HTTP 200、延迟正常、错误率为 0。传统监控能发现吗？
正确答案：不能，必须引入质量信号。这正是 AI 可观测性的核心增量：LLM 应用"稳定地返回错误"在基础设施层是完全健康的。在线抽样评估 + 隐式行为信号（重新生成率、转人工率）+ 规则校验（截断率、引用失效率）构成质量观测的最小集合。
2. OpenTelemetry GenAI 语义约定中，记录一次 chat 调用 token 用量的属性是？
正确答案：gen_ai.usage.input_tokens / gen_ai.usage.output_tokens。遵循 semconv 的好处是跨厂商、跨后端（Jaeger/Tempo/Datadog）属性名一致，看板和告警不用为每个模型重写。具体属性清单以 semconv 当前版本为准。
3. 流式输出场景，为什么必须单独观测 TTFT（首 token 延迟）？
正确答案：TTFT 决定用户体感。总延迟 3s 里 TTFT 0.3s（边说边出）和 TTFT 2.5s（干等后齐出）是两个完全不同的产品体验。此外 TTFT 突增通常指向检索/上下文过长/网关排队，是独立于生成速率的故障信号。
4. 关于 prompt/response 日志留存，正确的策略是？
正确答案：分层留存 + 可删除。全量永久明文 = 合规地雷（删除权、审计）；完全不存 = 无法复盘。元数据（耗时/token/模型）不含内容、体积小，值得长期存做趋势分析；正文抽样 + 脱敏后留存平衡调试与隐私；被拦截请求按合规要求保留更久（以现行规定为准）。
5. 设计"质量退化告警"，最直接的触发信号是？
正确答案：judge 质量分滑动窗口下降。配套信号还有：截断率上升、引用失效率上升、重新生成率上升、转人工率上升。单看请求量没有意义（下降可能是正常的时段波动）；GPU 利用率是基础设施指标，与质量无因果。告警规则建议 for: 30m，避免单次抽样抖动误报。
6. 团队已有 Prometheus + Grafana + Jaeger，想最快给 LLM 应用加上观测，选型思路是？
正确答案：OTel 原生埋点，复用现有栈。OpenLLMetry 这类工具按 OTel GenAI 语义约定生成 span 和指标，直接进你已有的 Jaeger/Prometheus，运维、告警、看板全部复用。另两个选项的问题：新 SaaS 意味着数据外传 + 双套运维；厂商后台只有聚合用量，没有 trace、没有质量维度、没有按业务线的归因。

下一步怎么练：给你现在的 LLM 应用补三样东西 —— ① 给模型调用加上带 gen_ai.* 属性的 span（或先用 Helicone 代理顶一周）；② 建一个质量分指标（先用规则：截断率 + 引用有效率），接 24h 滑动窗口告警；③ 给日志加 user_id 标签和 30 天生命周期策略。

之后值得单独学：评估体系的系统建设（评测集、judge 校准、A/B）、多模型路由下的观测一致性、以及把 trace 数据变成评测数据（bad case 自动入池）的闭环。
