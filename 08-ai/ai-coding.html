二十分钟入门 AI 辅助编程实战

开始前

先摆正一个预期

AI 编程工具的实测收益，业界口径大致是：样板代码、测试、文档、简单 CRUD 上提速 30%~50%；复杂业务逻辑、跨模块重构上收益接近 0，甚至为负（因为你要花时间审查和修）。

任务类型AI 适配度原因
单元测试、重复 CRUD、格式转换高模式固定、边界清晰、错了立刻被发现
解释陌生代码、写正则/SQL高有大量公开模式可循，验证成本低
基于已有风格的新功能模块中能给上下文就有效，不给就瞎编
复杂业务规则、状态机、并发低需求本身就说不清，AI 只是把说不清变成写不出来
安全内核、加密、合规逻辑不用错了后果不可逆，审查成本高于自己写
本篇的核心立场：AI 是放大器，不是替代品。工程纪律好的团队用它提速；没有 code review、没有测试的团队用它加速制造技术债。先修纪律，再上工具。
模块 1

工具全景：五类工具的定位与差异

市面上的工具看起来都在"AI 写代码"，但交互范式完全不同。选型前先分清自己在买哪一类。

类型代表产品交互范式适合场景
行内补全GitHub Copilot、通义灵码、CodeiumIDE 里 Tab 补全，单行到整个函数日常编码提速，写样板和重复代码
对话式编辑器Cursor、Windsurf整个 IDE 围绕对话重构，能跨文件改中大型重构、跨文件改动、边聊边改
终端 AgentClaude Code、Aider、Gemini CLI命令行里自主读文件、跑命令、多步执行批量任务、脚本化改造、跨仓库操作
PR/评审机器人CodeRabbit、Greptile、自建 botPR 里自动评论代码问题补充人工 review，抓低级错误
测试/运维 Agent各厂商 Agent 平台自主跑测试、看日志、提修复 PR值班辅助、flaky test 分诊

几个常被搞混的差异点

  • Copilot 是"副驾驶"，Cursor/Claude Code 是"代驾"。前者补全你写的代码，后者按你的描述改代码。代驾快，但你得盯着路——上下文给错的代价是成片的错误改动
  • 终端 Agent 的威力在"能跑命令"。它能自己跑测试看报错再改，闭环能力比纯补全强一个量级。但反过来说，它能跑 rm -rf、能推代码、能改配置——权限必须收着
  • 通义灵码等国产工具的差异化在合规和中文场景：企业内网部署、代码不出境、中文注释和报错理解更好。选型时这是硬指标，不只是效果指标

模块 2

有效使用的三种模式

同样的工具，有人效率翻倍，有人收获一堆跑不了的代码。差别不在工具，在用法。

模式一：给足上下文（上下文是 AI 代码质量的第一变量）

# ✗ 烂提示：AI 只能瞎猜你的技术栈和风格
帮我写一个订单导出的函数

# ✓ 好提示：技术栈 + 约束 + 数据样例 + 期望输出 + 边界
背景：Java 17 + Spring Boot 3，MyBatis-Plus，已有 OrderMapper
任务：写一个导出订单为 CSV 的 Service 方法
约束：
  1. 必须流式写出（订单量大，不能全量加载到内存）
  2. 复用现有的 PageHelper 做分页拉取，每批 500 条
  3. 字段：订单号、金额(分)、状态、创建时间(yyyy-MM-dd HH:mm:ss)
  4. 金额要格式化成两位小数
  5. 文件名带时间戳，用 UTF-8 BOM（Excel 打开中文不乱码）
输入：OrderQueryDTO（字段见下）
输出：写完附上两个边界 case 的说明（空结果集、金额为 null）
给上下文的四件套：① 相关代码文件直接贴或 @ 引用（类型定义、基类、相似实现）；② 技术栈和版本（框架版本间 API 差异巨大）；③ 现有约定（"错误码用 BizException"、"日志用 @Slf4j"）；④ 边界和反例（"金额可能为 null"、"要考虑并发"）。AI 不知道你的项目约定，除非你告诉它。

模式二：任务分解（把"写个功能"拆成 AI 能吃的粒度）

先让 AI 出方案，不让它写代码。"这个需求有几种实现方式？各自权衡？"先对齐设计，避免它一头扎进错误实现
按"一个函数/一个类"的粒度下发。单次任务越大，错误率越高，审查越难。超过 200 行的生成，基本等于给自己埋雷
每步跑测试再下一步。AI 生成 → 跑现有测试 → 人工看 diff → 通过再继续。不让错误滚动累积
遇到报错，把完整堆栈贴回去。不要描述错误（"它好像不行"），要贴原文。AI 修 bug 的能力远强于猜 bug

模式三：测试驱动（让测试成为 AI 的"合同"）

# TDD + AI 的标准循环，把"验收标准"变成可执行代码
1. 你写测试：先写 3~5 个 case，覆盖正常路径 + 边界 + 异常
2. AI 写实现：目标明确——"让这些测试通过，不许改测试"
3. 跑测试：红了让 AI 继续修，绿了人看 diff
4. 补 case：让 AI"找出这个实现还有哪些没覆盖的场景"，再补测试

# 为什么有效：测试是唯一客观的"做完了"标准
# 没有测试的 AI 代码 = 没有验收标准的交付 = 你不知道它对不对
测试驱动是 AI 编程里 ROI 最高的习惯。它同时解决了三个问题：① 验收标准客观化；② AI 有明确目标，不会自由发挥；③ 审查时先看测试再看实现，审查效率翻倍。反过来，让 AI 既写测试又写实现是危险的——它会写出"专门配合自己错误实现"的测试。
模块 3

审查 AI 产出：四个维度

AI 代码的审查清单和人工代码不同：人工代码的典型错误是逻辑疏忽，AI 代码的典型错误是"看起来完全正确的幻觉"。审查重心要换。

① 正确性审查：找"似是而非"

  • 不存在的 API。调了一个方法名很合理、但你的依赖版本里根本没有的方法。解法：IDE 里编译 + 看 import 是否真实存在
  • 过时的用法。用了两年前网传博客里的废弃 API（比如老版本的线程池参数）。解法：对照官方当前文档抽查关键调用
  • 边界条件凭空假设。它假设入参非 null、假设列表非空、假设时间格式固定。解法：逐个数——每个入参、每个外部返回值，问一句"为 null/为空/超时会怎样"
  • 边界数字差一。分页 off-by-one、区间开闭。解法：用具体数字在脑子里跑一遍

② 安全审查：AI 是漏洞生成器的高产用户

# AI 高频生成的安全问题，逐条 grep 你的 diff：
SQL 拼接："SELECT * FROM t WHERE name = '" + name + "'"   # 注入，必须参数化
命令拼接：Runtime.getRuntime().exec("tar -xf " + filename)    # 命令注入
路径拼接：new File("/data/" + userPath)                        # 路径穿越
硬编码密钥：String key = "sk-abc123"                             # 凭证进代码
弱随机：new Random().nextInt() 用于 token 生成                # 应 SecureRandom
反序列化：ObjectInputStream.readObject() 接外部输入           # 高危
日志打印：log.info("user={}, token={}", user, token)            # 敏感信息泄露
AI 特别爱犯的两类安全错误：① 示例代码直接搬上生产——训练数据里大量教程代码含 SQL 拼接、硬编码密钥；② 过度"贴心"的错误处理——catch 住异常后打印完整堆栈（含变量值）到日志，把 PII 送进日志系统。

③ 许可证风险：最容易被忽视的一条

  • Copilot 类工具的代码建议可能复刻训练数据里的代码，包括 GPL 等强 Copyleft 许可证的代码。商用闭源产品混入 GPL 代码是法务事故
  • 缓解措施：① 开启厂商的"代码引用过滤"功能（Copilot 有 suggestions matching public code 的开关，关掉或配白名单）；② 对生成的成块代码（超过 10 行、明显是通用库逻辑）用代码查重工具扫公开仓库；③ 公司法务明确 AI 生成代码的许可证政策

④ 性能与可维护性：AI 的"能跑就行"倾向

AI 常见性能坑审查要点
循环里查库/调 RPC（N+1）看到 for 循环里有 mapper 调用或 HTTP 请求，默认有问题
一次性加载全量数据selectList() 无分页、stream().collect() 攒大 List
重复计算循环里反复算同一个值，不会提取变量
同步阻塞调用塞进异步方法async 方法体里出现阻塞 IO，"异步"名不副实
审查顺序建议：先跑测试和编译（挡掉 50%），再过安全 grep（挡掉 30%），最后才人肉读逻辑。把可自动化的先自动化，人只干人该干的事。有条件的话把这份清单做成 PR 模板，AI 生成的 PR 强制走一遍。
模块 4

团队落地：规范、安全与效能度量

个人用 AI 是习惯问题，团队用 AI 是治理问题。没有规范的团队推广 AI，等于给每个人配一把没有保险的枪。

① 私域代码安全：三条红线

红线一：核心代码不出境。涉及商业机密、未公开算法、客户数据的仓库，只用内网部署的工具或私有化模型。先盘点哪些仓库能连公网 AI，哪些不能，写进仓库 README
红线二：凭证和密钥不进 prompt。贴代码给 AI 前，先过一遍 secret 扫描（git-secrets、gitleaks）。.env、密钥配置、连接串是重灾区
红线三：生产数据不喂 AI。包含真实用户信息的日志、数据库导出，脱敏后才能用于调试 prompt

② 团队规范：写进 CONTRIBUTING.md 的四条

  • AI 生成的代码必须人工审查后才能提交，review 时标注"本 PR 含 AI 生成代码"，reviewer 按更严标准过
  • AI 生成代码必须附带测试，没有测试的 AI 代码默认不合入
  • 提交信息注明 AI 参与度（完全手写 / AI 辅助 / AI 为主），为事后追溯留线索
  • 安全敏感模块（认证、支付、加密）禁用 AI 生成，或必须两人以上审查

③ 效能度量：别被"代码行数"忽悠

指标可信度说明
代码行数 / 提交数低AI 让这两个数字虚涨，与价值几乎无关
需求交付周期（idea → 上线）高端到端时长，AI 省的是实现环节，这里能体现
PR 回合数 / review 耗时高AI 代码质量差会直接推高 review 成本，这是照妖镜
缺陷逃逸率（线上 bug 中 AI 代码占比）高最终裁判。AI 代码占比远高于产出占比就是警报
开发者主观调研（季度）中辅助参考，别当 KPI 考核，会逼出数据造假
效能度度的反模式：把 AI 使用率纳入 KPI。一旦和考核挂钩，数据立刻失真（人人汇报"重度使用"）。正确做法是度量结果指标（周期、缺陷率），不度量使用行为。另外建议做一次 A/B：同一类任务，一半允许用 AI 一半不允许，两周后对比交付周期和缺陷率——用自己团队的数据说话，比任何厂商报告都可靠。

④ 落地路线图：四周从试点到常态

阶段动作产出与验收
第 1 周
试点准备		盘点仓库密级，定"能用/不能用"清单；选 3~5 名志愿者；定工具与账号密级清单文档、工具采购/配额就绪、约定验收指标
第 2 周
受控试点		志愿者在低风险任务用（测试、样板、文档）；每天 15 分钟站会同步踩坑内部提示词模板 v1、问题清单（含安全事故记录）
第 3 周
度量评估		对照非试点组，看交付周期、review 回合数、缺陷逃逸率；决定推广/叫停/换工具评估报告（用数据，不用感觉）、规范定稿
第 4 周
全面推广		全员培训（2 小时：工具用法 + 审查清单 + 红线）；PR 模板和 CI 卡点上线规范进 CONTRIBUTING.md、CI 强制检查、季度回顾机制
试点选谁比试点做什么更重要。选"愿意折腾 + 愿意反馈"的中间层工程师，别选最资深的人（他们不用 AI 也能快，数据没区分度）也别选纯新人（他们判断不了对错）。试点期发现的安全事故（贴了密钥、代码外传）要公开复盘——这是全团队最有效的一次安全教育。
模块 5

什么时候不该用 AI

这一节是给"AI 万能论"泼冷水的。以下场景用了 AI，省下的时间会连本带利还回去。

场景风险理由与替代
密码学实现、密钥管理极高侧信道、常量时间比较等细节 AI 不可靠。只用经过审计的库，不自己写
认证/授权核心逻辑极高一个边界漏洞等于全线失守。人工写 + 安全评审
支付、资金相关计算极高浮点精度、舍入规则、幂等设计，错了是真金白银
强合规场景（等保、HIPAA、审计留痕）高代码要能向审计方解释每一行来源，AI 生成物增加举证难度
你不理解它在写什么的领域高审查不了 = 没有审查。先学领域，再借 AI 提速
没有测试的老代码大改高没有安全网的重构。先补特征测试，再动手
一个残酷的悖论：AI 在你最熟悉的领域最有用，在你最陌生的领域最危险。熟悉 → 你能审查，AI 是杠杆；陌生 → 你只能盲信，AI 是赌场。判断标准很简单：如果 AI 这段代码出 bug，你能在 review 时发现吗？发现不了，就别让它写。

避坑

十个真实工程坑

1
盲信生成：不编译不测试直接提交
AI 代码"看起来对"的概率远高于"跑起来对"的概率。不存在的 API、错误的包名，编译一道就现形。铁律：AI 代码不跑过测试不进 PR。
2
上下文污染：长会话里 AI 越改越离谱
一个会话里来回改十几轮后，AI 开始"忘记"早期约束，反复引入已修掉的 bug。解法：任务完成就开会话；大任务先沉淀成设计文档再开新会话。
3
许可证污染：GPL 代码片段进了闭源产品
训练数据里的开源代码被原样复刻。解法：开启代码引用过滤、大块生成做公开仓库查重、法务出书面政策。
4
技能退化：离开 AI 写不出代码的新人
新人从 Tab 补全开始，从没独立写过循环和异常处理，基础能力空心化。解法：团队定期"无 AI 日"，面试和考核保留手写环节。
5
把密钥、生产配置贴进 prompt
贴代码排查问题时把 .env、数据库连接串一起贴了出去。解法：贴之前过一遍 secret 扫描；排查日志先脱敏。
6
让 AI 既写测试又写实现
它会写出"专门配合自己错误实现"的测试，全绿但覆盖的是错误行为。测试必须人写或人审，AI 只负责让测试通过。
7
任务粒度过大：一次让 AI 改十个文件
生成上千行 diff，人工审查成本超过自己写。控制在"一个函数/一个文件"粒度，分批验收。
8
在陌生领域让 AI 主导设计
分布式锁、一致性协议这类设计，AI 能给你一个"看似合理的错误方案"，而你没有能力识别。陌生领域先人脑设计，AI 只做实现辅助。
9
安全模块不设防：AI 生成认证/支付代码直接合
AI 高频产出 SQL 拼接、弱随机、硬编码密钥。安全敏感模块必须双人审查 + 安全扫描，别开"AI 直通"后门。
10
没有度量就推广：用"感觉快了"决策
凭个体感受全团队推广，结果 review 成本暴涨、缺陷率上升。先小范围 A/B 两周，看交付周期和缺陷逃逸率再决定。
自测

六道题

1. 关于 AI 生成代码的审查，最优先的流程是？
正确答案：先自动化后人肉。编译 + 测试能挡掉约一半问题（不存在的 API、逻辑错误），安全扫描再挡掉一批，人只专注机器查不出的业务逻辑和设计问题。顺序反了会把宝贵的人力浪费在查拼写错误上。
2. AI 编程工具最可能带来什么法务风险？
正确答案：许可证污染。代码建议可能逐字复刻公开仓库里的强 Copyleft 代码。缓解：开启引用过滤、对成块生成做公开仓库查重、法务明确政策。这是最容易被忽视、后果最严重的风险。
3. 为什么"让 AI 自己写测试又写实现"是危险的？
正确答案：测试会被实现"带偏"。AI 的测试断言会围绕自己的实现写，而不是围绕需求写。正确分工：人写测试（验收标准），AI 写实现让测试通过；或人审 AI 写的测试。
4. 以下哪个场景最不适合用 AI 生成代码？
正确答案：密码学实现。常量时间比较、侧信道防护、密钥生命周期这些细节错一点就是严重漏洞，且 AI 训练数据里大量"教学版"实现本身就不安全。安全敏感代码只用经过审计的库，不自己生成。
5. 度量 AI 编程工具的团队效能，最可靠的指标是？
正确答案：结果指标。代码行数会被 AI 虚涨；自评会因社会期许失真。交付周期体现真实效率，缺陷逃逸率体现质量代价——两个一起看才能回答"到底值不值"。
6. "上下文污染"指什么？怎么缓解？
正确答案：长会话退化。上下文窗口里的早期约束被后续对话稀释，AI 开始"自由发挥"。缓解：单会话只干一件事；复杂任务先让 AI 产出设计文档，人改定稿，再开新会话实现。
