模块 1

为什么需要结构化输出

因为下游是程序，不是人。程序对"几乎合法"的容忍度是零。

场景结构化输出的形态
信息抽取从合同/邮件/工单里抽字段 → 入库。模型输出实体对象，程序直接写库
Agent 工具调用模型"决定调用哪个函数、传什么参数"本身就是一次结构化输出（函数名 + 参数 JSON）
分类与打标情感分类、意图识别、内容审核 → 枚举值 + 置信度，直接驱动业务分支
前端渲染模型生成 UI 配置/图表 schema/表单定义 → 前端直接渲染，不解析自然语言
中间表示（IR）模型生成查询 DSL、SQL 草案、工作流定义 → 程序校验后执行

解析失败的下游成本（为什么值得投入工程）

# 一次解析失败的连锁反应
模型输出 "```json\n{...}\n```"        # ① 带了 Markdown 代码围栏
  → json.loads 抛 JSONDecodeError     # ② 任务中断
  → 用户看到"系统繁忙"                 # ③ 体验受损（其实模型干得不错）
  → 重试/人工兜底，成本 ×3             # ④ 每个百分点失败率都是真金白银

# 行业经验：纯提示词约束的 JSON 合法率大约 90%~99%（随模型和 schema 复杂度波动）
# 约束解码（guided decoding）可以把它压到接近 0 —— 这就是本篇的核心杠杆
判断标准：只要模型输出要被 json.loads / JSON.parse / pydantic / zod 消费，就必须走结构化输出通道，并在 prompt 之外加机制保证。"提示词里写了只输出 JSON"是声明，不是保证。
模块 2

三条实现路线

路线机制特点
JSON modeAPI 参数（如 OpenAI 的 response_format={"type":"json_object"}）强制输出是合法 JSON，但不约束结构保证"能解析"，不保证"结构对"。schema 仍要写进提示词
Function / Tool calling定义工具的 input_schema，模型输出"调用哪个 + 参数 JSON"。参数结构由 schema 约束与工具生态原生打通；参数是对象型，顶层不能是数组；适合"动作决策"场景
约束解码（Guided Decoding）推理引擎在每生成一个 token 前按 schema/正则/语法屏蔽非法 token，从机制上不可能输出非法结构最强保证（100% 合法），本地推理（vLLM 等）常用；云端 API 的 "Structured Outputs" 即此路线

模块 3

Schema 设计：让模型少犯错的第一道防线

# 一个生产级 schema：发票抽取（JSON Schema 草案）
{
  "type": "object",
  "properties": {
    "invoice_no":   {"type": "string", "description": "发票号码，保留前导零"},
    "total_amount": {"type": "number", "description": "含税总金额（元），只数字不要货币符号"},
    "issue_date":   {"type": "string", "format": "date", "description": "开票日期，YYYY-MM-DD"},
    "status":       {"type": "string", "enum": ["valid", "invalid", "unknown"]},
    "items": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "name": {"type": "string"},
          "qty":  {"type": "integer"},
          "unit_price": {"type": "number"}
        },
        "required": ["name", "qty", "unit_price"],
        "additionalProperties": false      # 禁止模型自由加字段
      }
    },
    "confidence": {"type": "number", "minimum": 0, "maximum": 1}
  },
  "required": ["invoice_no", "total_amount", "status", "items"],
  "additionalProperties": false
}

Schema 设计七条军规

原则做法与理由
枚举优于自由文本status、category 这类封闭集合一律 enum。自由文本会让下游比较逻辑崩溃
描述即提示词每个字段写 description："保留前导零"、"只数字不要符号"。约束解码下 description 仍是模型选值的主要依据
嵌套不超 3~4 层深嵌套是模型出错重灾区，也是约束解码的性能杀手。平铺或用数组组织，别超过三四层
数组给上下界minItems/maxItems 防止模型返回 0 项或 100 项。抽取类任务 maxItems 通常 5~20
required 克制只有"抽不到就无法处理"的字段进 required。宽松 required 会让模型编造，严格 required 会让它失败重试
可选字段用 nullable 表达明确 null 的语义（"未提及"），与"空字符串"（"提及了但为空"）区分开
additionalProperties: false禁止模型私加字段。不加这条，strict 模式不生效，模型会自由发挥
各 API 对 schema 复杂度有上限（属性总数、嵌套深度、required 字段数等，且随版本调整）。设计阶段就把 schema 控制在 modest 规模：总属性几十个、嵌套三四层以内。超限不会给你友好报错，可能是静默降级或直接 400。
模块 4

校验与重试：闭环才是可靠性

约束解码保证"结构合法"，不保证"语义正确"——日期格式对但值是幻觉、金额是正的但张冠李戴。语义校验只能靠你的代码，校验失败就要重试。

# 两层校验：JSON Schema（结构）+ 业务规则（语义）
from jsonschema import validate, ValidationError

def validate_output(data: dict, schema: dict) -> list[str]:
    errors = []
    # 第一层：结构
    try:
        validate(instance=data, schema=schema)
    except ValidationError as e:
        errors.append(f"schema: {e.message}")
        return errors            # 结构都错，业务校验没意义
    # 第二层：业务规则（模型管不着的部分）
    if data["total_amount"] < 0:
        errors.append("金额不能为负")
    if data["issue_date"] > today():
        errors.append("开票日期不能是未来")
    calc = sum(i["qty"] * i["unit_price"] for i in data["items"])
    if abs(calc - data["total_amount"]) > 0.01:
        errors.append(f"明细合计 {calc} 与总额不符")
    return errors

重试策略：把错误"喂回"给模型

# 带错误反馈的重试（reflexion 式）：成功率远高于原样重发
def extract_with_retry(text, schema, max_retries=3):
    messages = [{"role": "user", "content": f"提取发票信息：{text}"}]
    for attempt in range(max_retries):
        resp = call_llm(messages, tools=[make_tool(schema)])      # schema 约束调用
        raw = resp.tool_calls[0].function.arguments
        try:
            data = json.loads(raw)
        except json.JSONDecodeError as e:
            messages += [{"role": "assistant", "content": raw},
                         {"role": "user", "content": f"输出不是合法 JSON：{e}。请严格按 schema 重新输出。"}]
            continue
        errors = validate_output(data, schema)
        if not errors:
            return data                                        # 成功
        # 关键：把校验错误作为新一轮 user 消息，让模型自己修
        messages += [{"role": "assistant", "content": json.dumps(data, ensure_ascii=False)},
                     {"role": "user", "content": "你的输出未通过校验：\n" + "\n".join(errors) +
                                 "\n请修正后重新输出完整 JSON。"}]
    raise ExtractionFailed(f"重试 {max_retries} 次仍失败")       # 升级：人工队列/降级模板
失败类型处理说明
结构非法带 schema 重试（约束解码下几乎不出现）重试时务必把错误原因回传
语义校验失败带具体错误项重试（"金额为负"比"输出有误"有用 10 倍）重试提示要指出哪个字段、错在哪
反复失败降级：换更强模型 / 转人工队列 / 模板兜底设重试上限（2~3 次），别无限重试烧钱
重试提示词的质量决定重试的效率："输出有误请重试"和"字段 issue_date 的日期晚于今天，且 total_amount 与明细之和不符，请修正这两个字段"——后者一次修好的概率高得多。把校验器的错误信息当作给模型的"编译器报错"来用。
模块 5

流式结构化输出

用户体验上，等 30 秒看一个完整 JSON 和逐字看到 JSON 长大是两回事。流式的关键不是"边收边显示原文"，而是增量解析出部分对象，让 UI 先渲染已有字段。

# Python：边收流边补全部分 JSON（partial-json-parser 思路）
from partial_json_parser import loads as partial_loads

buffer = ""
snapshot = {}
for chunk in stream:                       # 逐 chunk 拼接原始文本
    buffer += chunk
    try:
        snapshot = partial_loads(buffer)      # 不完整也能解析出已有前缀
    except Exception:
        continue                           # 这一小段还凑不出完整值，跳过
    render(snapshot)                      # UI 增量渲染（防抖 100~200ms）

final = json.loads(buffer)                 # 流结束后做完整校验
# 注意：partial_loads 只能解析"JSON 前缀"，遇到被截断的字符串会尽力猜
# 最终渲染必须以完整解析 + schema 校验的结果为准
// TypeScript：SSE 流 + zod 增量校验（Next.js 风格）
const res = await fetch("/api/extract", { method: "POST", body });
const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();

let buf = "";
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  buf += value;
  const partial = partialParse(buf);        // 部分解析
  if (partial) setForm(partial);            // 表单字段逐步点亮
}
const final = InvoiceSchema.parse(JSON.parse(buf));  // zod 收尾校验
流式形态处理要点
纯 JSON 流chunk 边界可能切断转义序列和半个字符串，拼接必须完整 buffer 后解析，别逐 chunk parse
工具参数流OpenAI 工具调用流按参数 JSON 的增量分片（arguments delta）；Anthropic 有 partial_json 增量事件
UI 渲染防抖（100~200ms）合并渲染；数组增量时用稳定 key；最终态必须用完整校验结果覆盖
流式的最大坑：把中间态当最终态。增量解析出的"半截字符串"可能显示错误值（如金额还只收到 "12" 实际是 "1234.56"）。渲染时可以亮中间态，但提交、入库、计费必须等完整校验通过。

模块 7

常见坑：让 JSON 炸掉的六种方式

坑现象与对策
输出被截断max_tokens 太小，JSON 只到一半：{"items": [{"name": "A"。对策：结构化任务的 max_tokens 按预估输出 2 倍给；监控 finish_reason=length
布尔/空值歧义模型输出 "true"（字符串）而不是 true；null vs "" vs 字段缺失三种"没有"混用。对策：schema 里明确类型；下游判空统一按"字段缺失或为 null"处理
数字被四舍五入JSON number 走浮点，12345678901234567890 变 1.2345678901234568e+19；金额出现 0.30000000000000004。对策：ID/长数字/精度金额在 schema 里定义成 string，程序侧再转
深层嵌套模型崩5 层以上嵌套，模型开始漏括号、漏引号。对策：schema 平摊到 3 层内；大数组拆成多次抽取
Markdown 围栏残留JSON mode 没开时模型爱包 ```json ... ```。对策：用结构化 API；解析前 strip 围栏只能当兜底
枚举值漂移schema 写 "valid"/"invalid"，模型输出 "Valid" 或 "有效"。对策：strict enum + 下游归一化（lower/strip）双保险
# 健壮解析函数：解析前的四道防御
def safe_parse(raw: str) -> dict:
    text = raw.strip()
    # 1. 剥 Markdown 围栏（兜底，正常不该走到这）
    if text.startswith("```"):
        text = re.sub(r"^```(?:json)?\s*|\s*```$", "", text)
    # 2. 截取第一个 { 到最后一个 }（模型前后加了废话时）
    start, end = text.find("{"), text.rfind("}")
    if start != -1 and end != -1:
        text = text[start:end+1]
    # 3. 正常解析
    return json.loads(text)          # 仍可能抛错 → 交给重试闭环

# 4. 永远不要用 eval / new Function 解析模型输出（代码注入！）
安全红线：模型输出是不可信输入。禁止 eval(model_output)、禁止 new Function(model_output)、禁止把模型输出直接拼进 SQL/shell。解析只用 json.loads 这类不执行代码的解析器，参数化查询走数据库驱动，命令执行走白名单。
模块 8

生产级完整示例：抽取 + 校验 + 重试 + 降级

把前面所有环节拼成一个可直接进项目的模块。

# invoice_extractor.py —— 结构化抽取的完整闭环
import json, os
from dataclasses import dataclass
from jsonschema import validate, ValidationError
from openai import OpenAI

client = OpenAI()
MODEL = os.environ.get("LLM_MODEL", "gpt-4o")

INVOICE_SCHEMA = {
    "type": "object",
    "properties": {
        "invoice_no": {"type": "string"},
        "total_amount": {"type": "number"},
        "status": {"type": "string", "enum": ["valid", "invalid", "unknown"]},
        "items": {
            "type": "array", "maxItems": 50,
            "items": {
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "qty": {"type": "integer"},
                    "unit_price": {"type": "number"},
                },
                "required": ["name", "qty", "unit_price"],
                "additionalProperties": False,
            },
        },
    },
    "required": ["invoice_no", "total_amount", "status"],
    "additionalProperties": False,
}

@dataclass
class Result:
    data: dict | None
    ok: bool
    attempts: int
    error: str = ""

def business_validate(d: dict) -> list[str]:
    errs = []
    if d["total_amount"] < 0:
        errs.append("total_amount 不能为负")
    if not d["invoice_no"].strip():
        errs.append("invoice_no 为空")
    return errs

def extract(text: str, max_retries: int = 3) -> Result:
    messages = [
        {"role": "system", "content": "你是发票信息抽取引擎，严格按 schema 输出。"},
        {"role": "user", "content": text},
    ]
    for attempt in range(1, max_retries + 1):
        resp = client.chat.completions.create(
            model=MODEL,
            messages=messages,
            response_format={"type": "json_schema",
                             "json_schema": {"name": "invoice", "strict": True,
                                          "schema": INVOICE_SCHEMA}},
            max_tokens=2048,                    # 给足输出额度，防截断
        )
        if resp.choices[0].finish_reason == "length":
            return Result(None, False, attempt, "输出被 max_tokens 截断")
        raw = resp.choices[0].message.content
        try:
            data = json.loads(raw)
            validate(instance=data, schema=INVOICE_SCHEMA)
        except (json.JSONDecodeError, ValidationError) as e:
            messages += [{"role": "assistant", "content": raw},
                         {"role": "user", "content": f"校验失败：{e}。请严格按 schema 重输。"}]
            continue
        errs = business_validate(data)
        if not errs:
            return Result(data, True, attempt)
        messages += [{"role": "assistant", "content": json.dumps(data, ensure_ascii=False)},
                     {"role": "user", "content": "业务校验未过：\n" + "\n".join(errs)}]
    # 降级路径：转人工 / 规则模板 / 更强模型
    return Result(None, False, max_retries, "多次重试失败，转人工")

# 监控指标：成功率、平均 attempt 数、各错误类型分布 —— 重试率上升是模型/提示词退化的早期信号
这份代码的四个可复用决策：① strict schema 走约束解码，结构错误在第一步就被消灭；② 校验错误回传给模型（reflexion），重试有的放矢；③ finish_reason=length 单独处理，不浪费重试次数；④ 失败有明确降级出口，绝不把异常抛给终端用户。
模块 9

十个常见坑

1
max_tokens 太小，JSON 输出被截断
输出停在半个对象，json.loads 必炸。结构化任务按预估输出的 2 倍预留 max_tokens，并监控 finish_reason=length 的比例。
2
布尔用字符串、空值三种写法混用
"true"/true、null/""/字段缺失混在一起，下游判空逻辑反复踩坑。schema 明确类型，空值语义在 description 里写死，下游统一按"缺失或 null"判空。
3
金额和长 ID 用 number 类型
JSON number 是浮点，长 ID 丢精度、金额出现 0.30000000000000004。ID、订单号、精度金额在 schema 里定义成 string，程序侧再转。
4
schema 嵌套五六层
深层嵌套是模型漏括号重灾区，也是约束解码的性能杀手。平摊到 3~4 层内，大数组拆多次抽取。
5
解析失败就原样重发请求
同样的输入大概率同样的错。重试必须带错误反馈：把 JSONDecodeError 或字段级校验错误作为新消息喂回模型，让它自己修。
6
不校验直接 json.loads 就用
约束解码只保证结构合法，语义错误（日期是未来、金额为负、明细对不上）它管不了。业务校验层不可省略，校验规则就是你的数据质量门禁。
7
枚举值大小写/语言漂移
schema 写 "valid"，模型返回 "Valid"/"有效"。strict enum 保证候选集，但模型选错项仍可能；下游加一层归一化（lower+strip+同义词映射）双保险。
8
流式解析把中间态当最终态
半截字符串渲染出错误金额，用户已看到并提交。中间态可亮，提交/入库必须等完整解析 + schema 校验通过。
9
用 eval / new Function 解析模型输出
模型输出是不可信输入，eval 它等于远程代码执行。只用 json.loads / JSON.parse，SQL 走参数化，命令走白名单。
10
以为开了 JSON mode 就万事大吉
JSON mode 只保证"是合法 JSON"，不保证结构、字段、语义对。schema 还是要写（进 json_schema 或提示词），校验重试闭环还是要建。
自测

六道题

1. JSON mode 和约束解码（Structured Outputs）的核心区别是？
正确答案：JSON mode 管"能解析"，约束解码管"结构对"。JSON mode 下模型仍可能缺字段、加字段、类型错；约束解码在每个 token 生成前按 schema 屏蔽非法选项，从机制上保证合 schema。语义正确则两者都不管，要靠业务校验。
2. 模型返回的 JSON 总是到一半就停（finish_reason=length），最先该查什么？
正确答案：调大 max_tokens。截断是输出额度耗尽，不是模型笨——强调一万遍也没用。结构化任务按预估输出的 2 倍预留，同时把 max_tokens 设小当成 bug 来查。
3. 要抽取"18 位订单号"和"12345.67 元金额"，schema 里类型应该怎么定义？
正确答案：都定义成 string。JSON number 走浮点，18 位整数超出 2^53 精度必丢，金额也会出现 0.30000000000000004。用 string 保真，程序侧用 Decimal/长整数处理。
4. 校验发现模型输出的 issue_date 是未来日期，最高效的重试方式是？
正确答案：带具体错误反馈重试。原样重发大概率犯同样的错；错误信息要精确到字段和原因（"编译器报错"式），模型一次修好的概率高得多。静默改写则掩盖了模型缺陷，污染数据质量。
5. 流式结构化输出中，把增量解析出的部分对象直接渲染，最大的风险是？
正确答案：中间态被当最终态。流式中途解析出的字符串可能只是完整值的前缀，直接提交就是脏数据。中间态可以亮（提升体验），提交、入库、计费必须等完整解析 + schema 校验通过。
6. 关于约束解码（guided decoding），下列说法正确的是？
正确答案：生成时按 schema 过滤 token。推理引擎（vLLM 的 guided_json 等）维护 schema 的自动机状态，非法 token 的 logits 被置为 -inf。云端 Structured Outputs 就是这条路线的托管版。代价是轻微的性能损失和 schema 复杂度上限。
