二十分钟学透 AI 成本优化

LLM 应用的账单和传统云账单逻辑完全不同：按 token 计费、输出比输入贵 3~5 倍、缓存和批处理有隐藏折扣、重试会翻倍烧钱。这篇用真实计算把成本构成、六大优化手段、归因预算和自建盈亏平衡讲透。

建议拿自己应用的真实账单对着看：你的单请求成本是多少钱？
开始前

先会算账：一张月度账单

全文用一个贯穿案例：RAG 智能客服，月请求 100 万次，平均输入 3,000 token（系统提示 500 + 检索片段 2,000 + 对话历史 500），平均输出 400 token。先算基线成本，后面每个优化手段都往这个基数上叠。

# 基线：全量走旗舰级 API（量级价：输入 $2.5/M token，输出 $10/M token）
输入成本 = 100万次 × 3,000 token = 3,000M token × $2.5/M  = $7,500
输出成本 = 100万次 × 400  token =  400M token × $10/M   = $4,000
                                            月度合计 = $11,500（单请求 $0.0115）

# 第一个反直觉事实：
# 输出 token 量只有输入的 13%，但因为单价贵 4 倍，输出占总成本 35%。
# 模型变啰嗦 → 输出成本等比例上涨，这是"话多"的真实代价。

# 第二个反直觉事实：
# 换成中端模型（$0.15/M 输入、$0.60/M 输出），同样的量：
输入 = 3,000M × $0.15 = $450；输出 = 400M × $0.60 = $240  →  $690/月
# 价格差 16.7 倍。模型分级是最大的单一杠杆（见模块 3）。
口径说明：文中价格为公开定价的量级参考（美元/百万 token），价格变动频繁且各厂商结构不同，精确数以厂商当前文档为准。方法不变：单价 × 用量，无论数字怎么变算法都一样。
模块 1

成本构成：不止"聊天那一下"

构成计费方式占比经验值
输入 token系统提示 + 检索上下文 + 对话历史，全额计费（缓存命中部分另有折扣）55%~70%——最大头，且最容易被忽视
输出 token模型生成部分，单价通常是输入的 3~5 倍25%~40%
提示缓存缓存写入/读取通常单独计价，结构因厂商而异（有的读 0.1x、有的 0.5x 输入价）可把重复前缀成本降 50%~90%
嵌入文档入库 + 查询向量化，单价低（~$0.02/M 量级）但量大累积可观通常 <5%，但建库期集中爆发
微调训练按 token/时长计费 + 微调版推理通常比基座贵 20%~100%一次性 + 持续溢价，要按摊销算
周边基础设施向量库、GPU（自托管）、观测存储、审核 API10%~30%，自托管时反超 API 成本
# 一个常见误判：以为"接入 LLM"只有对话费用
# 完整 RAG 应用的月成本示例（100 万次请求）：
模型调用（旗舰级）          $11,500    # 上面算过的
嵌入（建库 10 万文档 + 查询）  $50       # 10万文档×1k token×$0.02/M ≈ $2 + 查询 100万×100token×$0.02/M = $2
向量数据库（托管）           $200      # 100 万向量 × 768 维的托管价量级
观测存储（trace 元数据）       $80      # 见可观测性篇，成本可观测本身也是成本
内容审核 API                $150      # 按调用量计费
                    ----------
                    $11,980  # 模型调用占 96%，先优化它
优化顺序由占比决定：先啃模型调用（占绝对大头），再管嵌入和基础设施。反过来做（先折腾向量库选型）是典型的努力方向错误。

主流模型定价量级（$/百万 token，参考值）

档位代表（量级）输入输出适用

定价结构差异（比单价更重要）

结构规则工程含义
输入/输出价差输出单价 = 输入 × 3~5压缩输出（少废话）和压缩输入（少上下文）的 ROI 完全不同，要分开算
上下文长度分档部分厂商按上下文长度阶梯计价（如 ≤128k 更便宜）上下文别无脑涨，越过档位边界单价跳变
缓存计费两种主流结构：读取折扣型（命中按输入价的一成计）+ 写入溢价型（写入 1.25x、读取 0.1x）缓存不是免费午餐：短 TTL 缓存反复重写，可能比不用缓存还贵；迁移厂商要重算账
批处理折扣主流厂商批处理 API 统一 5 折左右，换取 24h 内完成离线任务（日报、批量标注）不用它等于白扔一半预算
最容易亏的钱：缓存用错形态。缓存命中折扣的前提是"前缀稳定复用"。如果你的 prompt 每轮都把最新时间戳放最前面，前缀永远不变→永远不命中；或者 TTL 设得比请求间隔还短，反复付"写入溢价"。用缓存前先统计：你的请求前缀重复率到底有多少。

隐藏计费口径（不看文档就会踩）

口径规则工程含义
最小计费单元多数厂商按实际 token 计，但部分产品有"每次调用最低计费 N token"大量小请求（分类、抽取）叠加起来比想象贵
速率限制的隐性成本免费额度/低价档通常绑定额定 RPM/TPM，超了要么限流要么自动升档计费压测时按"超限后的价"算成本，不是标价
上下文计费边界输入 token 含系统提示 + 历史 + 检索内容 + 工具定义；多轮对话历史全额重计第 10 轮对话的输入成本 ≈ 第 1 轮的 10 倍（不带摘要时）
失败调用只要产生了 token 就计费：超时、内容拦截、客户端取消都算重试和熔断策略直接等于成本策略
# 一个具体的例子：多轮对话不做摘要的输入成本膨胀
# 系统提示 500 + 每轮 QA 平均 600 token（问+答）
# 第 1 轮输入 ≈ 500 + 300(检索) = 800 token
# 第 10 轮输入 ≈ 500 + 300 + 9×600 = 6,200 token  ← 7.75 倍
# 解法：滑动窗口（只带最近 4 轮）+ 更早历史压缩成 200 token 摘要，
# 第 10 轮输入压到 ≈ 500 + 300 + 4×600 + 200 = 3,400 token，接近腰斩。
模块 3

六大优化手段（按 ROI 排序）

1. 模型分级路由（最大单一杠杆）

多数流量是简单的（FAQ、分类、抽取），旗舰模型是浪费。用轻量分类器（甚至一条规则/小模型）把请求分级：

# 分级路由：70% 走中端 + 30% 走旗舰
def route(request) -> str:
    # 规则兜底：短问题、命中 FAQ 库、无多轮推理特征 → 中端
    if len(request.text) < 50 and faq_hit(request):
        return "mid"
    # 不确定的交给分类器（本身用小模型，成本忽略不计）
    return classifier.predict(request)     # "mid" | "flagship"

# 成本：0.7 × $690 + 0.3 × $11,500 = $3,933/月，降幅 66%
# 前提：用评估集验证中端模型在"被路由到的流量"上质量达标（见评估篇）

2. 语义缓存（重复流量的杀手）

# FAQ / 客服场景重复率极高，语义缓存命中率常见 20%~40%
# 30% 命中 → 11,500 × (1-0.3) = $8,050/月，省 $3,450
def cached_chat(query_embedding, threshold=0.95):
    hit = vector_store.search(query_embedding, top_k=1)
    if hit and hit.score >= threshold:
        return hit.answer, cache_hit=True        # 零模型调用
    answer = llm.chat(...)                              # 未命中才调模型
    vector_store.upsert(query_embedding, answer)         # 回填缓存
    return answer, cache_hit=False

# 阈值是安全阀：0.95 以上才认"同一个问题"。
# 阈值放宽到 0.85，命中率涨但开始答错问题（见坑 6）。

3. 上下文裁剪（输入成本直接下降）

  • RAG top-k 精简：10 个片段压到 3 个 + rerank，输入从 3,000 → 1,500 token，输入成本直接砍半（$7,500 → $3,750）。先用评估确认质量不掉。
  • 对话历史摘要化：超过 N 轮后，旧历史压缩成摘要（几百 token），而不是全量带入。
  • 检索片段截断：每个片段只取最相关的 2~3 句（用片段内 rerank 或按相关段落切分），别把整篇文档塞进去。

4. 提示词压缩（系统提示瘦身）

# 系统提示从 1,200 token 压到 400：每请求省 800 token
# 100 万请求 × 800 = 800M token × $2.5/M = $2,000/月（旗舰价口径）

# 压缩手法：删例子（用 few-shot 1 个代替 5 个）、删客套、删重复约束、
# 用结构化短句代替长段落。压缩后必须跑回归——省 token 省坏了行为是灾难。

5. 批处理 API（离线任务 5 折）

日报生成、批量内容标注、数据清洗、离线摘要——这些不需要实时结果的任务走批处理接口（主流厂商约 5 折，24h 内返回）。假设 30% 请求可异步化：省 0.3 × 11,500 × 50% = $1,725/月。

6. 输出长度控制

# max_tokens 是硬闸：防止跑飞和死循环（见坑 8）
resp = client.chat.completions.create(
    model="...", messages=msgs,
    max_tokens=512,        # 按业务上限设，别用默认的大值
)

# 输出从 400 → 300 token（话术精简）：输出成本 $4,000 → $3,000，省 $1,000/月
# 但过度压缩损害质量和用户满意度——控制在评估可接受的范围内
组合效果（按顺序叠加）：语义缓存 30%（-$3,450）→ 剩余流量 70% 走中端路由（-$5,550）→ top-k 精简（再省约三成输入）→ 提示压缩。基线 $11,500 优化后约 $2,300/月，降幅约 80%，且每一步都有评估集保驾。这就是"省钱不省质量"的标准路径。
模块 4

推理优化：自建部署侧

走 API 的话这部分与你无关；自托管模型时，吞吐和显存就是金钱。

技术原理效果（量级）
vLLMPagedAttention（显存分页管理，消除碎片）+ continuous batching（连续批处理，不等整批到齐）相对朴素 HF 部署吞吐提升可达数倍到十几倍（官方 benchmark 口径，实际随负载变化）
量化权重 INT8/FP8/GPTQ/AWQ，减少显存占用与带宽压力显存降 50%~75%；吞吐升 30%~100%；精度损失需评估集验证
推测解码小模型先草拟、大模型并行验证，一次前向多 token延迟降 20%~40%，需要额外一个小模型显存
张量并行单模型切到多卡，突破单卡显存上限大模型的必经之路；跨卡通信有损耗
# vLLM 部署的最小骨架（以当前文档为准）
# pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --quantization awq \          # 或用 fp8/gptq，取决于模型仓库提供的版本
  --gpu-memory-utilization 0.9 \
  --max-model-len 8192 \        # 按需限制上下文，显存和 KV cache 都省
  --enable-prefix-caching       # 系统提示/公共前缀自动复用，等价于 prompt caching

# prefix caching 对 RAG 极其重要：系统提示 + 工具定义是稳定前缀，
# 命中时省掉整个前缀的 prefill 计算——延迟和算力双省。
量化不是免费的：INT8 通常几乎无损，4bit（AWQ/GPTQ）在复杂推理任务上可能出现可见退化。每次量化后必须跑评估集，拿"省下的显存/成本"和"掉的质量分"做交换决策，而不是默认量化一定安全。
模块 5

成本归因与预算

看不见归因的成本等于没有管理：月底一张 $11,500 的账单，说不出是哪条产品线烧的，就没有优化抓手，也防不住一夜烧完。

归因：标签体系是第一公民

# 每次模型调用带成本标签（和可观测性篇的指标标签同一套）
cost_counter.labels(
    team="customer-service",     # 业务线
    feature="rag-qa",              # 功能
    model="gpt-4o-mini",          # 模型档位
    tier="free|pro",              # 用户分层
).inc(estimated_cost)

# 分摊规则：系统提示、公共检索等共享成本按各业务线 token 量比例摊，
# 别按请求数摊（长上下文的业务会被严重低估）。

预算：三道闸

日预算告警（80% / 100% / 120% 三档）：超 80% 通知负责人，超 100% 限流降级，超 120% 电话 + 自动切中端模型。看板放一条"当前月预算消耗进度"线。
单租户限额：按用户/客户设日 token 上限，防大客户跑飞、防免费额度被羊毛党刷穿。
异常检测：单用户 token 消耗超其历史基线 10 倍、单 key QPS 超均值 5 倍 → 自动冻结待审（常见于 key 泄露被刷）。
# 成本中间件：请求前后各记一次，失败请求也记账（重试放大就是从这里漏的）
def cost_guard(user_id, team, fn, *args):
    budget = redis.get(f"budget:{user_id}:{today}")
    if budget >= DAILY_CAP:
        raise QuotaExceeded("今日额度已用完")
    try:
        return fn(*args)
    finally:
        # finally 里记账：超时、异常、被取消的调用同样产生了费用
        redis.incrbyfloat(f"budget:{user_id}:{today}", fn.cost)
        metrics.cost.labels(team=team).inc(fn.cost)
预算告警必须存在，且必须能被触发。真实事故模式：新功能上线 → prompt 里误带了全量知识库 → 单请求成本涨 50 倍 → 无告警 → 三天后收到账单 $40,000。日预算 + 单请求成本异常检测（>3σ）两道闸，能拦下绝大多数这类事故。
模块 6

自建 vs API：盈亏平衡估算

结论先行：稳定高负载才值得自建；负载波动大、团队没有推理运维能力，API 的总成本往往更低——因为 API 的成本是"按量付费"，自建的成本是"按容量付费"。

算一笔平衡账

# 自建侧（8×A100 80G 量级）
GPU 云主机（按需）        ~$30/hr × 24 × 30     = $21,600/月
预留/长约折扣                                     ≈ $13,000/月
推理运维（0.5~1 FTE 摊销）                       ≈ $8,000/月
                                        ----------
                                        合计 ≈ $20,000/月（固定成本，与用量无关）

# API 侧：单请求 $0.0115（基线案例），随用量线性增长

# 盈亏平衡点：
# 20,000 / 0.0115 ≈ 174 万请求/月
# → 月请求稳定超过 174 万，自建更便宜；低于它，API 更便宜。

但平衡点会骗人，看三个修正

修正项说明
GPU 利用率自建跑 20% 利用率 = 实际单请求成本 $0.0575，是 API 的 5 倍。流量有波峰波谷（白天高夜间低）时，按峰值买的卡大部分时间在空转
隐性成本模型升级（自建要重新量化、benchmark、回归）、安全补丁、SLA 责任、on-call——这些都不在 GPU 账单上，按 0.5~1 个 FTE 算并不夸张
混合架构常见最优解：基线负载自建 + 峰值溢出到 API（burst routing）。既压住固定成本，又保住峰值 SLA，还多一层故障转移
决策清单（满足多数再考虑自建）：① 月请求稳定在平衡点 2 倍以上；② 负载曲线平稳（峰谷比 < 3）；③ 团队有推理运维能力（vLLM/量化/监控）；④ 数据合规要求必须私有部署；⑤ 模型选择稳定（不是每季度追新）。任何一条不满足，API + 优化手段（模块 3）的性价比都更高。
模块 7

十个烧钱坑

1
忽视缓存计费规则，缓存反而更贵
缓存写入溢价 1.25x、TTL 比请求间隔短 → 每次都付全价写入费还从不命中。用缓存前先统计前缀重复率，TTL 按真实复用周期设。
2
retry 放大成本
超时无指数退避地重试 3 次 = 4 倍计费；更糟的是失败重试把已生成的输出全部重算。重试必须带退避 + 次数上限 + 只对"可重试错误"（429/5xx/超时）生效，且重试也计入预算。
3
无预算告警，一夜烧完
API key 泄露被刷、agent 死循环、prompt 误带全量上下文——任何一个都能让账单从 $11,500 变成 $40,000。日预算三档告警 + 单租户限额 + 异常冻结，一个都不能少。
4
只对比输入单价，忽略输出价差
输出单价是输入的 3~5 倍。选型只比输入价、不管模型话痨程度，实际账单可能反向超预算。评估时把"平均输出长度"纳入模型对比维度。
5
所有流量都用旗舰模型
FAQ、分类、抽取这类简单任务占流量 70%+，旗舰模型在这里没有质量优势。分级路由是最大单一杠杆（降幅可达 60%+），前提是拿评估集验证中端模型质量。
6
语义缓存只追命中率，不管错误命中
相似度阈值从 0.95 放宽到 0.85，命中率涨 15 个点，但"退货政策"的答案被缓存给了问"换货政策"的用户。错误命中是质量事故，比省的钱贵得多。阈值 + 缓存条目带原始问题原文供审计。
7
RAG 把全量文档塞进上下文
top-k=20、每片段 500 token，输入 10,000+ token，大半无关。输入成本直接 3 倍起。top-k 精简 + 片段截断 + rerank，先用评估确认质量不掉再上。
8
不设 max_tokens
模型偶发跑飞（重复生成、陷入循环）时输出几千 token，一次顶正常十次；agent 场景死循环能烧掉整日预算。按业务上限硬性设 max_tokens，配合 finish_reason=length 的监控。
9
离线任务走实时 API，没用批处理折扣
日报、批量标注、离线摘要明明能等 24 小时，却按实时价付全款。主流厂商批处理约 5 折，30% 请求可异步化 = 月省 15% 总预算。梳理任务清单时先问一句"结果需要马上要吗"。
10
自建只对比 GPU 单价，不算利用率
"API 单请求一毛钱，自建一秒只要一分钱"——然后卡跑 20% 利用率，实际单请求成本是 API 的 5 倍。自建前先压测出真实负载曲线，算清"有效单请求成本"，再谈平衡点。
自测

六道题

1. 月请求 100 万次，平均输入 3,000 token、输出 400 token，旗舰级 API 单价 $2.5/M 输入、$10/M 输出。月成本是多少？
正确答案：$11,500/月，输入占 65%。输入 3,000M token × $2.5/M = $7,500；输出 400M × $10/M = $4,000。输出单价虽贵 4 倍，但 token 量只有输入的 13%，所以输入才是最大头——这就是为什么"上下文裁剪"比"让模型少说话"优先级更高。
2. 同一案例，语义缓存命中率做到 30%，每月节省多少？
正确答案：$3,450。命中的请求完全不产生模型调用，输入输出全省：11,500 × 0.3 = $3,450/月，剩余成本 $8,050。注意缓存只对"重复/相似问题"有效，创造性任务（写作、脑暴）命中率天然低，别硬上。
3. 在案例基础上加一级路由：70% 请求走中端模型（$0.15/M、$0.60/M），30% 留旗舰。新月成本约多少？
正确答案：约 $3,933，降幅 66%。中端模型成本 = 3,000M×$0.15 + 400M×$0.60 = $690/月。混合 = 0.7×690 + 0.3×11,500 = 483 + 3,450 = $3,933。前提：用评估集验证中端模型在被路由的流量上质量达标——省了钱掉了质量是负优化。
4. 自建 8 卡 GPU 集群月成本约 $20,000（含运维摊销），API 单请求 $0.0115。盈亏平衡的月请求量约为？
正确答案：约 174 万请求/月。固定成本 ÷ 单请求 API 价 = 平衡点。但要打三个修正：GPU 利用率（20% 利用率下实际单请求成本 $0.0575，是 API 的 5 倍）、隐性运维成本、峰谷波动。工程上常见更优解是"基线自建 + 峰值溢出 API"的混合架构。
5. 某个接口超时后，客户端立即原样重试，最多 3 次。这对成本的影响是？
正确答案：最多 4 倍（1 次原始 + 3 次重试），且失败调用同样计费。模型是按 token 计费的，超时的请求只要已生成 token 就产生费用。无退避的重试还会在模型侧过载时火上浇油。正解：指数退避、次数上限、只重试可重试错误（429/5xx/超时）、重试计入预算。
6. 把应用从 A 厂商迁到 B 厂商，关于提示缓存成本，正确的预期是？
正确答案：结构因厂商而异，必须重算。主流结构至少两种：读取按输入价一折左右（可能还有写入溢价 1.25x）与读取按输入价五折左右。同样的请求模式，两种结构下月成本可能差 20%+。迁移时的标准动作：用真实流量回放，对比"缓存命中模式下的月账单"再决策。

优化手段 ROI 排序（先做上面的）

1. 模型分级路由70% 流量走中端，降幅可达 66%，最大单一杠杆
2. 语义缓存FAQ 类场景命中 30% = 省 30% 总成本，阈值 ≥0.95
3. 上下文裁剪top-k 精简 + 片段截断 + 历史摘要，直接砍输入大头
4. 批处理 API离线任务 5 折，30% 请求可异步 = 省 15% 预算
5. 提示词压缩系统提示 1,200→400 token，月省 $2,000（旗舰口径）
6. 输出长度控制max_tokens 硬闸 + 话术精简，防跑飞死循环
7. 自建/混合架构请求量超平衡点 2 倍且负载平稳再考虑

核心公式

# 单请求成本
cost = (input_tokens × price_in + output_tokens × price_out) / 1_000_000

# 缓存命中后的有效输入价（读取折扣型）
eff_in = hit_ratio × cached_price + (1 - hit_ratio) × price_in

# 盈亏平衡请求量
breakeven_rps = self_host_monthly_cost / api_cost_per_request

# 自建有效单请求成本（利用率修正）
eff_cost_self = self_host_monthly_cost / (capacity_rps × utilization × 2.6e6)
