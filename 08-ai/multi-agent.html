二十分钟学透多智能体协作

多 Agent 不是"把提示词复制五份"。它是分布式系统设计换了一层皮：任务分解、消息协议、状态一致性、错误级联、成本乘数，一个都跑不掉。这篇讲四种协作模式、通信协议、框架选型和怎么评估——以及为什么大多数系统应该先用单 Agent 把基线打出来。

开始前

口径与第一性原则

框架 API 和模型能力演进很快，具体用法以各框架当前文档为准。本篇讲的模式分类、一致性问题和评估方法不绑定任何框架。

第一性原则：多 Agent 是增加复杂度的最后手段，不是第一手段。每当你想"再拆一个 Agent"时，先回答三个问题：① 单 Agent + 更好的提示词/工具能不能做到？② 拆分带来的上下文隔离收益，是否大于通信开销？③ 错误在 Agent 之间传播时，有没有校验点能拦住？三个问题有两个答不上来，就还没到上多 Agent 的时候。
模块 1

何时需要多 Agent：单 Agent 的三个极限

单 Agent（一个模型循环 + 一套工具）在三个方向会撞墙，撞墙的位置就是多 Agent的合理起点。

极限现象多 Agent 的收益
上下文极限任务需要的领域知识、历史、工具结果超出窗口，或塞进去后信噪比崩掉每个 Agent 只带自己职责所需的最小上下文，用隔离换质量
角色极限一个提示词既要"严谨审计"又要"创造性生成"，两种人格互相打架，输出风格漂移不同角色用不同系统提示/模型/温度，专业化
并行极限五个独立子任务串行执行，延迟线性叠加Worker 并行，墙钟时间大幅下降

该拆与不该拆的判断表

场景建议
分类、抽取、单文档问答单 Agent。拆分纯属增加故障点
工具很多的 Agent（20+ 工具）先试工具分组/路由，不够再拆多 Agent
多源调研（搜索 + 代码 + 文档）后综合适合 Supervisor-Worker：并行搜集 + 汇总
内容生产线（写→审→改→发）适合流水线：阶段边界清晰、产物明确
高风险决策（资金、合规）可用辩论/评审模式，但最终决策必须留人工或强校验
"不同 Agent 用不同模型省钱"先做模型路由，多数场景不需要完整多 Agent 编排
行业现状的口径：多 Agent 框架的 Demo 都很惊艳，生产落地翻车的同样多。原因不是模式不对，是工程细节（状态、重试、评估、成本）在 Demo 里都被省略了。本篇的重点就是这些被省略的部分。
模块 2

四种协作模式

模式结构适用与软肋
主管-工人
(Supervisor-Worker)		一个主管 Agent 负责理解任务、分解、分配、汇总；工人 Agent 无状态执行子任务并返回结果最常用、最可控。软肋：主管是串行瓶颈，分解质量决定上限
流水线
(Pipeline)		阶段 A → B → C 顺序流转，每阶段一个 Agent，产物是下一阶段的输入阶段边界清晰的产线场景。软肋：错误逐级放大，早期错误晚期才发现
辩论
(Debate)		多个 Agent 持不同立场/视角对同一问题论证，裁判（或第 N 轮）收敛结论高风险决策、需要多视角审视。软肋：延迟和成本 ×N，容易无限辩论
群体/黑板
(Swarm / Blackboard)		无中心，Agent 围绕共享状态（黑板）自主认领任务、读写中间产物探索性任务。软肋：最难调试，状态竞争和不可预测性高，生产慎用
# 四种模式的拓扑与成本特征（示意）
Supervisor-Worker      Pipeline           Debate            Swarm
    [主管]             A→B→C→D          [辩方1]⇄[辩方2]     [黑板]
    / | \                                              ↗   ↓   ↖
 [工1][工2][工3]       各司其职           [裁判]收敛       [A]  [B]  [C]

并行度: 中              低                低（串行轮次）      高
可观测性: 高（中心节点）  高（线性链）       中（多路对话）      低（发散）
调试难度: 中            低                中                  高
典型失败: 主管误分解     错误级联           无限辩论            状态竞争
选型速记：任务可并行分解 → Supervisor-Worker；任务有明确阶段产物 → Pipeline；决策高风险需多视角 → Debate（加轮次上限）；其余 → 先别拆。生产系统里 Supervisor-Worker 占绝大多数，因为它有一个天然的观测点和控制点。
模块 3

通信协议：消息传递 vs 共享状态

多 Agent 系统的"网络层"。两种范式决定了你怎么调试、怎么扩展、怎么排查数据不一致。

范式机制取舍
消息传递Agent 之间收发带 schema 的消息（任务请求、结果、错误），通过队列/总线流转边界清晰、可重放、易扩展。代价：消息协议设计成本，版本演进要向前兼容
共享状态所有 Agent 读写同一个状态对象（内存 dict / 数据库 / 文件），像共享内存多线程实现简单、信息不丢。代价：竞争条件，两个 Agent 同时写一个字段就是数据竞争
# 消息传递：任务消息的 schema（用结构化输出保证可解析）
{
  "type": "object",
  "properties": {
    "task_id":    {"type": "string"},        # 全局唯一，用于追踪与去重
    "role":       {"type": "string", "enum": ["researcher", "coder", "reviewer"]},
    "input":      {"type": "object"},        # 任务输入，schema 按 role 分派
    "reply_to":   {"type": "string"},        # 结果回给谁
    "deadline_ms": {"type": "integer"},      # 超时保护，防 worker 卡死
    "trace_id":   {"type": "string"}         # 全链路追踪，评估归因的锚点
  },
  "required": ["task_id", "role", "input"]
}

# 共享状态的写入纪律（避免竞争的三条）
# 1. 每个字段有唯一"责任写者"（owner agent），其他人只读
# 2. 写操作带版本号（乐观锁）：if state.version == expected: write
# 3. 状态变更落日志：谁、何时、改了什么 —— 没有这个，不一致永远查不出
Handoff（交接）是最高危的通信时刻：A 把任务交给 B，交什么、交多少、B 怎么知道"够了"？工程惯例：交接消息只带结论 + 关键证据 + 未解决的问题，不要把 A 的全部上下文倒给 B——那是上下文重复传输（坑 #4），成本和噪声双爆炸。
模块 4

任务分解与分配

分解粒度：子任务要"可独立验证"。每个子任务的产出应该能单独校验（有明确成功标准），粒度太粗退化成串行单 Agent，太细则协调开销吃掉收益。经验值：单子任务 1~3 次工具调用可完成
分解方式：静态（预先定义 DAG）优先于动态（让模型现场分解）。静态分解可测试、可复现；动态分解灵活但每次行为不同，评估和调试都痛苦。混合式：静态骨架 + 局部动态
分配依据：按能力匹配，不按平均分配。子任务标注所需能力（检索/代码/推理），Agent 注册能力标签，主管按标签路由。顺带可以做成本路由：简单子任务给小模型
依赖处理：显式声明依赖图。无依赖的子任务并行，有依赖的串行等齐。用 DAG 而不是"主管现场判断顺序"，否则同一输入两次分解出不同执行路径，回归测试直接失效
# 静态 DAG 分解示例：调研任务
tasks = [
    {"id": "t1", "capability": "search",  "depends_on": [],        "brief": "查 2025 年推理模型价格趋势"},
    {"id": "t2", "capability": "search",  "depends_on": [],        "brief": "查三大厂上下文窗口规格"},
    {"id": "t3", "capability": "analysis", "depends_on": ["t1", "t2"], "brief": "交叉验证并写对比结论"},
]
# 执行引擎：t1、t2 并行 → 都完成后触发 t3
# 失败策略：t1 失败 → t3 拿不到输入 → 要么重试 t1，要么标记降级（部分结论）
# 关键：失败语义要在分解时定义，不要等运行时才发现"没有 Plan B"
可复现性是分解的硬指标：同一输入，两次运行的执行路径应该一致（或至少评估集上一致）。动态分解 + 随机采样会让"上周还好的系统"变成玄学。把分解逻辑本身当代码管理：版本化、可测试、变更走回归。
模块 5

冲突解决与一致性

多个 Agent 同时读写同一份状态时，你面对的是分布式系统的经典问题，只是节点换成了 LLM。

问题场景解法
写冲突两个 Worker 同时更新同一份"调研笔记"单一写者原则 + 版本号（乐观锁）；或合并策略（append-only 日志而非覆盖）
结论冲突评审 Agent 和写作 Agent 对"是否达标"判断相反预设仲裁者（裁判 Agent 或规则）；投票（多评审取多数）；升级人工
错误级联Worker A 的幻觉输出被 B 当事实引用，错误滚雪球每个交接点做校验（结构化输出 + 业务规则），错误不过夜；关键事实要求带来源
状态漂移长任务中两个 Agent 对"当前做到哪步"认知不一致单一事实来源（一个权威状态对象）；所有进度变更走它，Agent 不同步各自记账
# 乐观锁式状态更新：防止并发写覆盖
def update_state(store, key, new_value, expected_version):
    current = store.get(key)
    if current.version != expected_version:
        raise ConflictError(               # 版本变了 → 别人先写过
            f"{key} 已被修改（期望 v{expected_version}，实际 v{current.version}），"
            f"请基于最新值重新决策"
        )
    store.put(key, new_value, version=expected_version + 1)

# 错误级联的防护：交接点强制校验
def handoff(from_agent, to_agent, payload, schema, validators):
    errors = validate_against(payload, schema) + run_business_rules(payload, validators)
    if errors:
        return {"action": "reject", "errors": errors,
                "next": "retry_or_escalate"}     # 错误在这里被拦住
    return {"action": "accept", "payload": payload}
LLM 让一致性问题更难的新维度：Agent 的"判断"本身不可枚举。传统分布式系统里节点故障是二值的（挂/没挂），而 Agent 可能"自信地输出错误结论"——看起来成功了，数据是脏的。唯一防线是在每个交接点放结构化校验和业务规则，把"看起来对"变成"验过才对"。
模块 6

框架选型：LangGraph / AutoGen / CrewAI / MetaGPT

口径：截至各框架当前公开版本，能力以官方文档为准。这一领域版本迭代极快，选型前一定看最新 release note。

框架抽象层级编排模型定位与适用
LangGraph低层（图/状态机）节点 + 边的有向图，状态在节点间流转，支持循环、分支、人工介入生产首选：控制力强、可观测性好（检查点、时间旅行调试）、生态与 LangSmith 打通。学习曲线陡
AutoGen中层（对话驱动）多个 Agent 通过"对话"协作，GroupChat 多轮群聊微软出品，研究友好、快速验证多 Agent 对话模式；生产化需要自己补状态与监控
CrewAI高层（角色团队）定义角色/目标/工具，声明顺序或层级流程最快上手：概念贴近"团队分工"，适合原型和简单流程；深定制时受抽象约束
MetaGPT高层（SOP 驱动）把软件公司流程（PM→架构→开发→测试）固化为 SOP，Agent 按标准作业程序产出文档与代码软件工程全流程模拟的开创者，偏研究/特定场景；通用任务上偏重
# LangGraph 风格：把协作模式显式建模成图（概念示意）
from langgraph.graph import StateGraph, END

graph = StateGraph(AgentState)
graph.add_node("supervisor", supervisor_node)   # 分解与分配
graph.add_node("researcher", researcher_node)
graph.add_node("coder", coder_node)
graph.add_node("reviewer", reviewer_node)

graph.set_entry_point("supervisor")
graph.add_conditional_edges("supervisor", route,     # 路由函数
    {"research": "researcher", "code": "coder", "review": "reviewer", "done": END})
graph.add_edge("researcher", "supervisor")        # 工人干完回主管
graph.add_edge("coder", "reviewer")              # 流水线段
graph.add_edge("reviewer", "supervisor")
app = graph.compile(checkpointer=checkpointer)   # 检查点：崩溃后从状态恢复
选型的三个反模式：① 因为 Demo 炫选框架，不看自己要不要那么重的抽象；② 核心编排逻辑散落在框架魔法里，出问题看不懂内部状态——至少保证状态流转可导出、可回放；③ 绑定框架的私有抽象，结果换模型/换供应商时被锁死。核心逻辑（分解、校验、路由）尽量用自己的代码写，框架只做执行引擎。
模块 7

成本与延迟的乘数效应

多 Agent 的成本不是"几个 Agent 就几倍"那么简单，是几个乘数叠乘。

# 一次 Supervisor-Worker 任务的 token 账（假设）
主管分解（输入2k + 输出1k）              = 3k
Worker × 4，每个（输入 8k 共享上下文 + 输出 2k）= 40k     # ① 上下文重复传输！
主管汇总（输入 4 个 worker 结果 12k + 输出 2k）= 14k
─────────────────────────────────────────────
单次任务合计                             ≈ 57k token

# 对比：单 Agent 串行做同样的事
一个上下文滚动执行（10k 上下文 × 5 轮）     ≈ 50k
# 结论：这个例子里多 Agent 没省 token，只省了墙钟时间（4 个 worker 并行）
# 什么时候多 Agent 真的省？—— 每个 worker 只需要全局上下文的一小部分时
# Worker × 4，每个只带 2k 相关上下文 = 16k + 主管 5k ≈ 21k  ← 隔离的红利
乘数来源说明
上下文重复传输同一份背景资料被 N 个 Agent 各带一份。N=4 就是 4 倍输入。对策：只交结论 + 必要证据
协调轮次主管分解 + 汇总、评审往返，每轮都是完整的一次 API 调用，延迟串行叠加
重试放大单 Agent 重试 1 次 = 2× 成本；5 个 Agent 各重试 1 次 = 全链路重试风暴
汇总开销Worker 结果汇总回主管，结果本身也是 token；汇总后还要生成最终输出，又是完整一轮
# 预算守卫：每个任务独立的 token/时间熔断器
class BudgetGuard:
    def __init__(self, max_tokens=50_000, max_seconds=300):
        self.max_tokens, self.max_seconds = max_tokens, max_seconds
        self.tokens_used, self.started = 0, time.time()

    def check(self):
        if self.tokens_used > self.max_tokens:
            raise BudgetExceeded("token 熔断：任务超预算，走降级")
        if time.time() - self.started > self.max_seconds:
            raise BudgetExceeded("时间熔断：任务超时，返回当前最佳结果")

    def record(self, usage):
        self.tokens_used += usage.total_tokens
        self.check()          # 每次调用后检查，超限立即停

# 没有熔断器的多 Agent 系统 = 没有限流的下游服务，出事只是时间问题
成本失控的典型剧本：任务卡住 → Worker 反复重试 → 每次重试都带全量上下文 → 预算没有熔断 → 一觉醒来账单几千刀。每个任务必须带 token 预算 + 超时 + 最大轮次三个熔断器，熔断后走降级路径（返回部分结果 / 转人工），不是继续跑。
模块 8

评估：端到端成功率与归因

多 Agent 系统的评估比单 Agent 更难：错误可能来自分解、路由、某个 Worker、汇总或仲裁，只看最终成功率等于放弃debug。

层级指标怎么用
端到端任务成功率、人工升级率、用户满意度北极星指标。没有它一切免谈
阶段级分解合理性（子任务覆盖度/重叠度）、Worker 单任务成功率、汇总失真率定位"哪个环节在拖后腿"
归因trace_id 全链路记录：每次调用的输入/输出/token/耗时，按调用链回放失败案例能回答"错在哪一跳"
# 最小评估 harness：每个案例记录全链路，输出分层指标
def run_eval(cases, system):
    results = []
    for case in cases:
        trace = system.run(case.input, trace_id=case.id)   # 全链路带 trace
        results.append({
            "case_id": case.id,
            "e2e_success": judge(trace.final_output, case.expected),
            "decomposition_ok": judge_plan(trace.plan),
            "worker_success": {w.id: judge(w.output) for w in trace.workers},
            "tokens": trace.total_tokens,
            "latency_s": trace.latency,
            "escalated": trace.escalated_to_human,
        })
    # 分层报告：端到端成功率 = f(分解质量, worker 质量, 汇总质量)
    report(results)

# 归因的黄金数据：每个失败案例都能回答 ——
# ① 错在分解/Worker/汇总/仲裁哪一层？② 是能力问题（模型不会）还是工程问题（上下文缺失、校验缺失）？
# ③ 重试能救吗（偶发）还是每次都错（系统性）？
评估纪律：维护 30~50 个覆盖典型场景的回归案例集，每次改分解策略、换模型、调 prompt 都跑全量。多 Agent 系统的退化往往是静默的——某个环节的小改动让端到端掉 5 个点，没有回归集你一周都发现不了。
模块 9

十个常见坑

1
协调开销超过收益
拆分后通信、汇总、校验的成本高于并行/隔离的收益，系统比单 Agent 又慢又贵又脆。先量化基线（单 Agent 的成功率、成本、延迟），再证明多 Agent 每一项都更优。
2
没有单 Agent 基线就上多 Agent
无法回答"多 Agent 到底带来了什么"。基线是后续所有决策的参照系：成本涨了但成功率涨多少才算值，只有对比基线才知道。
3
错误级联：Worker 的幻觉被当成事实传递
每个交接点都是校验点。结构化输出 + 业务规则 + 关键事实带来源，错误要在产生的下一跳被拦住，不能流三个 Agent 才爆。
4
上下文重复传输
同一份背景资料每个 Worker 各带一遍，4 个 Worker = 4 倍输入成本。交接只带结论 + 关键证据 + 未解决问题，让 Worker 按需自取。
5
无限辩论/循环没有终止条件
两个 Agent 互相驳回能跑到天荒地老。硬性上限：最大轮次、最大 token、最大耗时，三个熔断器一个都不能少。
6
主管成为串行瓶颈
所有任务经过主管分解和汇总，并行度被锁死。对策：能静态分解的用 DAG；主管只做路由不做执行；必要时分层主管。
7
共享状态无写纪律，并发覆盖
两个 Worker 同时改状态，后写的覆盖先写的，数据丢失且无线索。单一写者原则 + 版本号 + 变更日志，三件套配齐。
8
框架魔法包裹核心逻辑，出问题看不懂
编排散落在框架内部，状态不可导出、链路不可回放。核心逻辑（分解、校验、路由）用自己的代码写，框架只当执行引擎，保证全链路 trace 可导出。
9
只测端到端，不做归因
成功率从 80% 跌到 65%，但不知道错在分解还是 Worker，优化无从下手。阶段级指标 + trace_id 全链路记录是 debug 的基础设施。
10
成本没有熔断，重试风暴
任务卡住触发全链路重试，没有 token/时间/轮次上限，账单失控。每个任务独立预算守卫，超限立即降级返回部分结果。
自测

六道题

1. 关于"何时该用多 Agent"，最稳妥的默认答案是？
正确答案：先建单 Agent 基线。多 Agent 是增加复杂度的最后手段：上下文隔离、角色专业化、并行度三个收益要逐一验证确实存在，且大于通信、汇总、校验的开销。没有基线，你永远不知道多 Agent 是帮忙还是帮倒忙。
2. Supervisor-Worker 模式最主要的性能瓶颈是？
正确答案：主管是串行瓶颈。Worker 可以并行，但"理解任务→分解"和"汇总结果"两步必须串行经过主管。对策：能静态分解的用预定义 DAG，主管退化为路由器；任务规模大时分层主管。
3. 防止"错误级联"（Worker 幻觉被下游当事实）最有效的机制是？
正确答案：交接点强制校验。错误发现的越晚，传播越广、修复越贵。用结构化输出约束格式 + 业务规则校验语义 + 关键事实要求带来源，把"看起来对"变成"验过才对"再放行。
4. 两个 Agent 辩论评审，跑了 20 轮还没收敛，首先该做什么？
正确答案：立即熔断。多 Agent 系统必须预设最大轮次、最大 token、最大耗时三个上限，超限走预设仲裁（规则/裁判/人工），返回当前最佳结论。无限辩论不是深刻，是失控。
5. 多 Agent 系统的 token 成本，最主要的放大来源是？
正确答案：上下文重复传输。N 个 Worker 各带一份背景就是 N 倍输入，再加主管汇总轮、评审往返、失败重试，乘数叠乘。对策：交接只带结论与必要证据；每个任务配 token 预算熔断器。
6. 多 Agent 系统的失败案例排查，最关键的基础设施是？
正确答案：全链路 trace + 阶段级指标。多 Agent 的错误可能来自分解、路由、某个 Worker、汇总或仲裁，只按端到端成功率无法定位。trace_id 贯穿所有调用，失败案例能回答"错在哪一跳、是能力问题还是工程问题、重试能不能救"。
