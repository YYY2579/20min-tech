开始前

多模态应用的统一骨架

不管做哪类多模态应用，管线结构都一样：输入预处理 → 模型推理 → 后处理结构化 → 业务落库。差别只在每一环用什么技术。

# 通用多模态管线（所有应用共享这个骨架）
原始输入（图片/PDF/音频）
   │
   ▼
[预处理]  压缩、格式转换、分辨率控制、页面渲染      # 成本控制主战场
   │
   ▼
[模型层]   VLM 理解 / OCR / ASR / 生成模型           # 贵，尽量少调
   │
   ▼
[后处理]   JSON schema 校验、字段归一化、置信度过滤   # 质量兜底
   │
   ▼
[业务层]   落库、触发流程、人工审核队列               # 低置信度必须转人工
多模态工程的第一原则：模型是最贵的一环，能不在模型里做的就不在模型里做。图片先裁剪到关键区域、PDF 先用文本层提取（不是每页都当图片）、能用规则校验的不用模型判断。预处理省一块钱，比优化 prompt 省一块钱容易得多。
模块 1

多模态能力全景

先建立地图。四类能力，成熟度和工程形态完全不同，别用同一套方案硬套。

能力输入 → 输出成熟度典型应用
视觉理解
VLM		图片 + 文本 → 文本高，API 成熟图片问答、图表分析、截图理解、质检
OCR / 文档解析图片/PDF → 结构化文本高，专用工具链成熟票据录入、合同抽取、表格识别
图像生成文本（±参考图）→ 图片高，可控性仍在演进营销素材、海报、电商图
语音ASR：音频→文本；TTS：文本→音频高，实时化在卷延迟语音助手、会议纪要、外呼

VLM vs 专用 OCR：什么时候用谁

场景推荐原因
标准票据、证件、表格专用 OCR 引擎准、快、便宜。版式固定，专用模型效果更好
版式不固定的文档（合同、报告）VLM / 文档解析管线要理解版面语义，OCR 只管识字不管段落结构
自然图片里的文字（招牌、手写）VLM场景 OCR 文本检测是另一个领域，VLM 直接理解
图表分析（趋势、异常点）VLM要视觉推理，不是文字识别
大批量低价值识别（百万张）专用 OCR成本差 10 倍以上，VLM 按 token 计费吃不消
选型口诀：固定的版式用专用工具，开放的视觉理解用 VLM，大批量先算成本再用 VLM。厂商模型能力更新很快（多模态模型每几个月一代），具体支持格式、上下文长度和计费以厂商当前文档为准。
模块 2

视觉理解应用

三个高频场景：图片问答、OCR 结构化、图表分析。工程重点分别是 prompt 设计、schema 约束和精度校准。

① 图片问答（VLM API 调用）

# OpenAI 兼容的多模态调用：图片走 content 数组，url 或 base64
import base64, openai

client = openai.OpenAI(base_url="https://api.example.com/v1")

def ask_about_image(image_path: str, question: str) -> str:
    with open(image_path, "rb") as f:
        b64 = base64.b64encode(f.read()).decode()

    resp = client.chat.completions.create(
        model="qwen-vl-max",              # 多模态模型名，以厂商文档为准
        messages=[{
            "role": "user",
            "content": [
                {"type": "image_url",
                 "image_url": {"url": "data:image/jpeg;base64," + b64}},
                {"type": "text", "text": question},
            ],
        }],
        max_tokens=1024,
    )
    return resp.choices[0].message.content

# prompt 要点：给角色 + 给判断标准 + 要求引用图中依据
question = """你是质检员。这张图是某工件的照片。
请判断：1) 是否有裂纹或变形 2) 尺寸标注是否清晰可读
每个结论必须说明依据（图中哪个位置支持你的判断）。
无法确定就说"无法确定"，不要猜。"""
多模态 prompt 的三条经验：① 允许说"无法确定"，否则模型会把模糊图硬答（幻觉重灾区）；② 要求引用图中位置（"左上角""第二行第三列"），可验证的回答质量高一个档；③ 一图一问，多张图多个问题串行问，别指望一次问十件事都答对。

② OCR 结构化：从图片到 JSON

# 管线：预处理 → VLM 抽取 → schema 校验 → 字段归一化
PROMPT = """从这张增值税发票中提取以下字段，严格输出 JSON，不要输出任何其他内容：
{
  "invoice_code": "发票代码，10位数字",
  "invoice_number": "发票号码，8位数字",
  "amount": "价税合计，保留两位小数的字符串",
  "invoice_date": "开票日期，格式 YYYY-MM-DD"
}
看不清的字段填 null，不要猜测。"""

import json, re
def extract_invoice(image_b64: str) -> dict:
    raw = ask_about_image_b64(image_b64, PROMPT)

    # 1. 剥掉 markdown 代码围栏（模型经常加 ```json）
    cleaned = re.sub(r"^```(json)?|```$", "", raw.strip(), flags=re.M)

    # 2. 解析 + schema 校验
    data = json.loads(cleaned)
    assert re.fullmatch(r"\d{10}", data["invoice_code"] or ""), "发票代码格式错"

    # 3. 字段归一化：金额转分、日期标准化
    data["amount_cents"] = int(round(float(data["amount"]) * 100))
    return data
结构化输出的三道质量闸，缺一道就出事：① 解析兜底——模型输出的 JSON 永远可能不合法，json.loads 外面必须包 try，失败进人工队列；② 格式校验——正则/长度/范围校验，错了重试一次（换个温度）或转人工；③ 字段级置信度——金额、日期这种关键字段，让模型同时输出置信度，低于阈值必须人工复核。把模型输出直接当数据落库，是票据类事故的标准剧本。

③ 图表分析：VLM + 数据双通道

# 架构：有原始数据就解析数据，没数据才走视觉识别
[图表图片] ──┬─→ 有源数据（Excel/API）→ 直接算指标 + VLM 描述图面     # 准
             └─→ 无源数据 → VLM 读图：标题/坐标轴/数据点 → 估读值    # 有误差

# 关键设计：估读值必须标注"估算"，不能当精确数据用
# VLM 读柱状图高度，误差轻松超过 10%，用来"看趋势"可以，用来"报数"不行
模块 3

文档智能：PDF 解析管线

PDF 是多模态里最脏的输入：扫描件、嵌套表格、跨页表格、页眉页脚。核心决策是先判断"有没有文本层"，别把可提取文本的 PDF 当图片烧钱。

管线：三级分流

第一级：探测文本层。用 pdfplumber/PyMuPDF 尝试提取文本。能提出文字（每页超过 N 个字符）→ 走文本管线，零视觉成本
第二级：版面分析。对复杂版式（多栏、表格、图文混排）用版面分析模型（或文档解析服务）识别区域类型：标题/正文/表格/图注
第三级：视觉兜底。扫描件、提取失败的页面才转成图片走 VLM。只转失败页，别整本转
# 用 PyMuPDF 做文本层探测 + 分级渲染
import fitz  # PyMuPDF

def classify_pages(pdf_path: str, min_chars: int = 50):
    doc = fitz.open(pdf_path)
    text_pages, image_pages = [], []
    for i, page in enumerate(doc):
        text = page.get_text().strip()
        (text_pages if len(text) >= min_chars else image_pages).append(i)
    return text_pages, image_pages, len(doc)

# 只把 image_pages 渲染成位图，控制 DPI（省钱的旋钮）
def render_page(pdf_path: str, page_no: int, dpi: int = 150):
    doc = fitz.open(pdf_path)
    page = doc[page_no]
    pix = page.get_pixmap(dpi=dpi)        # 150dpi 通常够 OCR；72dpi 会丢小字
    return pix.tobytes("png")

# 成本对比：200 页合同
# 全本转图片走 VLM：200 张图 × 约 1500 token/张 ≈ 30 万 token
# 分流后（180 页有文本层 + 20 页扫描）：文本 0 token + 20 张 ≈ 3 万 token
# 差 10 倍。这就是"先探测文本层"的价值

表格提取：三个层次的做法

方法适用准确率/成本
文本层 + 坐标聚类规整表格、有边框高准确、零成本。用 PyMuPDF 的 find_tables()
专用表格模型无线框、合并单元格准确率 85%~95%，按页计费
VLM 转 Markdown复杂版式兜底灵活但最贵，需要校验（表格列数一致性）
跨页表格是文档解析的头号难点。一个表格跨 3 页，每页都有表头——拼接时要判断"这是续表还是新表"。工程解法：用表头相似度判断连续性，相似度高则合并，并去掉续页的重复表头。让 VLM 一次看多页（如果上下文允许）比逐页抽再拼准确得多。
文档解析的验收标准：抽 50 页人工核对，字段级准确率定 KPI。常见要求：关键字段（金额、日期、甲乙方）99%+，一般字段 95%+。达不到就保留人工复核队列，别硬上全自动。解析质量通常和 PDF 质量强相关——先推动上游（扫描仪 DPI、原件质量）比优化模型划算。
模块 4

图像生成应用架构

图像生成的工程难点不在"生成"，在可控性和批量生产的良品率。架构上要把"生成"和"控制"分开设计。

应用架构四层

[需求层]    运营填表单：场景、尺寸、文案、品牌色
              │ 模板化，不让人裸写 prompt
              ▼
[提示词层]  模板 + 参数拼装 → 统一 prompt 生成器
              "一张{style}风格的{product}产品图，{background}背景，
               柔光，商业摄影，8k，居中构图"
              │ 负面 prompt 固定维护：模糊、变形手指、文字水印
              ▼
[生成层]    文生图 / 图生图 / 参考图控制
              │ 每请求生成 N=4 张候选，成本 ×4
              ▼
[后处理层] 自动筛选（尺寸/水印检测/黑边）+ 人工/规则挑选 → 合规审核 → 交付

参考图控制：三种手段按成本排序

手段控制什么成本与效果
图生图
image-to-image		整体构图、色调延续便宜。传原图 + 强度参数，保持大体结构
局部重绘
inpainting		只改指定区域（换背景、修手）中。要画 mask，电商换背景标配
参考图/风格参考角色一致性、风格迁移较贵（多传参考图，token 多），一致性最好

良品率工程：生成 4 张选 1 张的隐性成本

  • 候选数 N 是良品率的倒数函数：良品率 25% 时 N=4 才有得选。N=4 意味着成本 ×4，批量生成前先算单位良品成本 = 单价 × N / 良品率
  • 自动预筛省人工：尺寸校验、黑边/水印检测、NSFW 过滤，机器先砍掉明显废图，人只看候选
  • 批量任务的幂等与重试：同 seed + 同 prompt 可复现，失败重试用同 seed；结果按 内容hash 去重防重复计费
  • 人工兜底队列：自动筛选后仍不满意的进人工精修/重绘队列，别把不满意的图直接交付
合规红线：生成内容的版权与肖像。① 商用前确认模型的输出版权条款（各厂商政策不同）；② 不让用户上传他人肖像/品牌 logo 做参考图；③ 输出过 NSFW + 敏感标识检测（品牌 trademark）再交付。营销物料出事通常是合规问题，不是技术问题。
模块 5

语音管线：ASR → LLM → TTS

语音助手的延迟 = 三段串行之和。用户对"说完到听到"的容忍度约 2 秒，超过就觉得卡。优化手段是流式化 + 并行化。

朴素串行 vs 优化后

阶段朴素串行优化手段优化后
ASR 识别等用户说完再识别（500ms+）流式 ASR：边说边出中间结果用户说完即刻有全文
LLM 生成等全文生成完（1.5s+）流式生成，按句/按标点切分首句 300ms 可播
TTS 合成全文合成完再播（800ms+）流式 TTS：句级合成，边生成边播与 LLM 生成重叠
总延迟约 2.8s三段流水线重叠约 0.8s（到首句播放）
# 流式语音管线的骨架（伪代码，展示拼接逻辑）
async def voice_pipeline(audio_stream):
    # 1. 流式 ASR：边收音频边出中间/最终结果
    async for transcript in asr_stream(audio_stream):
        if transcript.is_final:
            user_text = transcript.text

    # 2. 流式 LLM：按标点切句，够一句就送 TTS

    async for chunk in llm_stream(user_text):
        sentence_buf += chunk
        if re.search(r"[。！？.!?]", sentence_buf):
            await tts_and_play(sentence_buf)   # 不等全文，先播这句
            sentence_buf = ""

    # 3. 首包优化：TTS 支持流式输入，边传文本边出音频
    #    体验关键指标：TTFB（首音频字节时间），不是总合成时间

语音场景的工程细节

VAD 端点检测判断用户什么时候说完，早了截断、晚了冷场。阈值按场景调
打断处理（barge-in）用户开口就停 TTS 播放，取消未播音频队列
TTS 音频缓存固定话术（"好的，正在查询"）预合成缓存，零延迟播放
数字/日期口播规范化"2026-10-18"读成"二零二六年十月十八日"，TTS 前做文本正则化
采样率对齐采集 16kHz 单声道是 ASR 标配，播放端按 TTS 输出率对齐，防变声
语音链路最容易被忽视的成本：TTS 按字符计费、ASR 按音频时长计费，双计费。一次 30 秒对话：ASR 30 秒 + TTS 回答 200 字 + LLM token。长回答场景（陪聊、播报）TTS 字符数是最大头——控制回答长度就是控制成本。另外自建 ASR/TTS 的延迟和成本账要算清楚：量小用 API，量大（每天几百小时）再考虑自建。
模块 6

多模态 RAG：图文混合检索

当知识库里既有文字又有图表图片时，检索层要升级。核心思路：把非文本内容转成可检索的文本表示，检索后再让 VLM 回答。

索引构建：三种非文本内容的处理

内容类型索引进度说明
图片VLM 生成描述文本 → 文本 embedding 入索引，同时存原图引用描述质量决定检索上限，prompt 要覆盖"图里有什么 + 可能的用途"
图表提取数据表 + VLM 生成图表解读，两路都入索引查询"去年销售额趋势"能同时命中数据表和文字解读
PDF 扫描页按模块 3 的管线提取文本/结构化后再索引表格转 Markdown，保持结构信息
# 检索 + 生成的完整链路
用户问题："去年 Q3 各区域的销售额趋势如何？"
   │
   ▼
[检索] 文本向量检索 → 命中"Q3 销售报告.pdf 第 12 页（含柱状图）"
   │      + 命中该图表的 VLM 描述："2025 Q3 华东区销售额环比上升……"
   ▼
[组装] 上下文 = 图表描述 + 原图引用 + 相关表格数据（Markdown）
   │
   ▼
[生成] VLM 同时收到：文本上下文 + 原图 → 综合回答
   │      # 关键：图必须原样传给 VLM，只传描述会丢细节
   ▼
[回答] "根据图表，华东区 Q3 销售额 1.2 亿，环比上升 15%，主要来自……"
多模态 RAG 的两个设计决定：① 描述与原文并存——描述用于检索（文本对文本），原图用于生成（视觉对视觉），两层各司其职；② 引用要指到页/图级别，用户能点开看原图，回答才可信。只存描述不存原图，等于让 VLM 盲答。
模块 7

成本与延迟特征 + 十个坑

多模态的成本结构和纯文本完全不同，三个吃钱大户：图片 token、分辨率、长文档。先看特征表，再看坑。

成本与延迟特征

能力计费模式典型延迟优化杠杆
VLM 图片理解按 token，图片也折算 token1~5s降分辨率、裁剪 ROI、控制图片数量
专用 OCR按页/按次百毫秒级能不用 VLM 就不用
文档解析按页/按文档秒级文本层探测优先，只渲染失败页
图像生成按张（× 分辨率档）3~15s降候选数 N、提升单次良品率
ASR按音频时长实时率的 0.1~0.3流式、VAD 防无效音频
TTS按字符数首包 200~800ms缓存固定话术、控制回答长度

图片 token 计费：最容易被低估的账

# 图片折算 token 的常见规律（各厂商规则不同，以当前文档为准）
图片 token ≈ f(分辨率)     # 通常是"先缩放到基准尺寸，再按 tile 数算"

# 算账：一张 4000×3000 的手机照片（约 3.6MB）
不处理直接传 → 可能折合 1500~3000 token
缩到 1024 长边 → 约 700~1200 token      # 降 50%+
裁剪到关键区域再传 → 约 300~600 token   # 降 80%

# 批量场景：每天 10 万张票据 OCR
不处理：10 万 × 2000 token = 2 亿 token/天    # 天价账单
预处理后：10 万 × 500 token = 5000 万 token/天 # 差 4 倍
三个吃钱大户，按危害排序：① 不压缩的图片——原图直传，token 翻几倍，且很多场景小字在缩略图上照样能读；② 分辨率盲目拉高——不是所有任务都需要高清，读文字 1024 长边起步，看细节才上高清；③ 长文档整本进上下文——200 页 PDF 全转图片塞上下文，token 爆炸且效果差（长上下文中间段被忽略）。先做预处理，再谈模型选型。

十个真实工程坑

1
原图直传，账单翻三倍
4K 照片直接 base64 塞请求。上传前先缩放 + 裁剪 ROI，票据类场景 150dpi 足够。预处理是成本优化第一杠杆。
2
可提取文本的 PDF 整本转图片
有文本层的 PDF 当扫描件烧 VLM token。先用 PyMuPDF 探测文本层，只把失败页转图，成本差 10 倍。
3
模型输出 JSON 直接落库
模型爱加 markdown 围栏、爱填猜测值。必须解析兜底 + schema 校验 + 关键字段置信度，低置信度转人工。
4
分辨率一刀切，要么糊要么贵
读小字用 72dpi 全丢，看全景用 4K 浪费。按任务定档：文字抽取 150dpi、图表分析 200dpi、质检细节按需。
5
长文档整本进上下文，效果反而差
200 页 PDF 全塞，token 爆炸且模型忽略中间段。按 RAG 思路切分检索，或分章节摘要再综合。
6
跨页表格拼接错乱
一个表格跨 3 页，逐页抽取后拼出 3 个半张表。用表头相似度判断续表，去掉重复表头再合并。
7
语音管线三段串行，延迟 3 秒+
ASR 等说完、LLM 等全文、TTS 等合成。三段全改流式 + 按句切分，首句延迟能压到 1 秒内。
8
图像生成不控候选数，成本失控
每次生成 8 张选 1 张，良品率 30% 都不到。先提 prompt 质量把良品率做上去，再降 N，别反过来。
9
多模态 RAG 只存描述不存原图
检索用描述、生成也用描述，细节全丢。两层分离：描述管检索，原图管生成，回答可引用原图。
10
忽略输入边界：超大图/超长音频直接打爆
用户传 50MB 原图或 2 小时录音，直接超模型限制报错或内存溢出。入口做大小/时长/格式校验，超限先转码压缩。
自测

六道题

1. 处理一份 200 页的合同 PDF（其中 180 页有文本层、20 页是扫描件），成本最优的管线是？
正确答案：文本层优先，只渲染失败页。有文本层的页面提取文本零成本零误差；扫描件才需要视觉模型。整本转图 token 成本高 10 倍，纯 OCR 又处理不了复杂版面。分级分流是多模态成本控制的基本功。
2. 用户上传 4000×3000 的照片让你提取其中的小票文字，第一步应该做什么？
正确答案：先裁剪 ROI 再控制分辨率。原图直传 token 可能翻几倍，且大部分面积是无关背景。裁剪到票据区域 + 长边 1500 左右，识别率和成本都最优。注意别压过头——小字场景 1024 以下可能丢字。
3. VLM 做票据结构化抽取，输出直接 json.loads 后落库，会遇到什么问题？
正确答案：三重兜底。模型输出经常带 ```json 围栏、金额写成"壹佰元整"、日期格式漂移、看不清时编一个值。必须：剥围栏 + 正则/格式校验 + 关键字段置信度，失败进人工队列。把模型输出当可信数据是票据类事故标准剧本。
4. 流式语音助手把总延迟从约 2.8s 压到 1s 内的核心手段是？
正确答案：全链路流式 + 重叠。ASR 边说边识别、LLM 出一句就送 TTS 播一句、TTS 边传文本边出音频。核心指标从"总时长"变成 TTFB（首音频时间）。换模型只优化单段，重叠才是数量级提升。
5. 多模态 RAG 中，图片被 VLM 生成的描述文本，最合理的用法是？
正确答案：两层分离。描述是文本，能进文本向量索引被检索到；但描述会丢细节，生成阶段必须把原图传给 VLM。只存描述等于盲答；只存原图则检索不到（除非有原生的多模态 embedding 且成本可控）。
6. 关于图片 token 计费，哪个说法是对的？
正确答案：按分辨率折算。各厂商都是"缩放 + 分块"的思路，具体规则以文档为准。一张高清图可能折合上千 token——这就是为什么预处理（裁剪 + 缩放）是第一成本杠杆。批量场景下不压缩的图片能让账单翻几倍。
