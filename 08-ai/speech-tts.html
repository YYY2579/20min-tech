开始前

起一个能练的环境

# 2. 确认 ffmpeg 可用（重采样、转码全靠它）

# 3. 把任意音频转成 ASR 友好的格式：16kHz 单声道 WAV

# 4. 查看音频元信息（采样率/声道/位深/时长）
ffprobe -v error -show_entries stream=sample_rate,channels,bits_per_sample -show_entries format=duration meeting_16k.wav

edge-tts --text "你好，这是一段流式语音合成测试。" --voice zh-CN-XiaoxiaoNeural --write-media hello.mp3
采样率是语音链路第一大坑：电话窄带 8kHz、宽带语音 16kHz、音乐 44.1/48kHz。ASR 模型基本按 16kHz 训练，直接把 44.1kHz 的音频喂进去，等于把语速拉慢 2.76 倍，识别错误率直接崩。所以入模前必须统一重采样到 16kHz 单声道 16bit PCM。
模块 1

语音技术栈全景

别只盯着"转文字"。一个完整的语音产品通常是多个能力的组合，每种能力的延迟档位和工程要求完全不同。

能力输入 → 输出延迟档位典型场景
ASR 语音识别音频 → 文本离线秒级；实时 300ms 级会议转写、字幕、语音输入法、呼叫中心质检
TTS 语音合成文本 → 音频首包 150~500ms语音播报、有声书、导航、数字人配音
VAD 端点检测音频 → 语音段边界帧级 10~30ms所有实时链路的前置，判断"用户说完了没"
唤醒词 KWS音频 → 是否命中<100ms 帧级"小爱同学"等 always-on 常开监听
声纹识别音频 → 身份1s 音频可判身份核验、免密登录、说话人认证
说话人分离音频 → 谁在何时说离线为主多人会议转写（"说了什么"+"谁说的"）
语音翻译音频 → 外文文本/语音秒级同传字幕、跨国会议
实时链路的本质是"分帧 + 增量输出"。音频按 10~30ms 一帧进入处理，系统每隔一个 chunk（常见 320~640ms）吐一次中间结果，用户看到的是"边猜边改"的文字。离线场景则相反：整段喂入，一次出全文，可以慢但求准。这两种架构不要混用 —— 拿离线模型做实时，延迟一定超；拿实时模型做离线，准确率一定掉。
模块 2

ASR 核心指标：WER / CER / RTF

这三个数是 ASR 的"体检报告"。选型时看 demo 没用，要看你自己业务测试集上的这三个数。

WER 与 CER

# 词错误率（英文等按词计）
WER = (S + D + I) / N
  # S = Substitution 替换（把 A 识别成 B）
  # D = Deletion   漏识别（参考里有，识别结果没有）
  # I = Insertion  多识别（参考里没有，识别结果冒出来）
  # N = 参考文本的总词数

# 中文更常用 CER（字错误率）：中文不分词，按"字"算更稳定
CER = (S + D + I) / 参考总字数

算例：参考文本 100 个词，识别结果 3 个错、2 个漏、1 个多

项目数值说明
参考词数 N100人工标注的标准文本
替换 S3例："腾讯"被识别成"腾迅"
删除 D2例：漏掉了"的"和"了"
插入 I1例：多识别出一个"嗯"
WER(3+2+1)/100 = 6%安静朗读场景的常见水平

不同场景的参考水位（量级，非承诺值）

场景WER 量级说明
安静朗读、近场麦克风3% ~ 5%最好是这种情况
会议、多人、有混响5% ~ 15%需要说话人分离和顺滑
电话 8kHz 窄带 + 噪声10% ~ 20%信道本身就丢了高频
强方言 / 强口音15% ~ 30%+通用模型直接失效，要领域模型

RTF：Real Time Factor 实时率

RTF = 音频处理耗时 / 音频本身时长

# 例：60 秒的音频，纯推理耗时 12 秒 → RTF = 0.2
# RTF = 0.2 的含义：处理速度是播放速度的 5 倍

# 三条推论：
# 1. RTF < 1 才有"追上实时"的资格，否则音频越攒越多
# 2. 批量转写可以容忍 RTF > 1（排队慢慢算）
# 3. 全双工实时交互要求 RTF 远小于 1（通常 < 0.1，给抖动留余量）
评测集必须是"你自己的数据"。公开测试集的 WER 没有参考价值 —— 领域术语（医疗、法律、金融）、口音、信噪比、录音设备全都不一样。上线前务必用真实业务录音（脱敏后）建一个 2~10 小时的测试集，这是选型唯一可信的依据。另外注意区分"纯推理 RTF"和"端到端 RTF"（后者含音频解码、网络、后处理），厂商宣传的一般是前者。
模块 3

流式 ASR 架构：VAD→识别→标点→顺滑

实时语音识别的标准管线分五级，每一级都可以单独成为延迟或准确率的瓶颈。

音频采集：16kHz 单声道 16bit PCM，按 10~30ms 分帧上行。移动端注意采集权限、回声消除（AEC）和静音抑制。
VAD 端点检测：判断"用户开始说了"（首点）和"说完了"（尾点）。尾点通常要求 300~500ms 连续静音才判定结束 —— 这 300~500ms 是延迟预算里最贵的一段。
流式识别：模型按 chunk（常见 320~640ms）增量解码，每来一个 chunk 吐一次中间结果。chunk 越小尾点越快，但上下文越短、准确率越低，是延迟与准确率的直接交换。
标点恢复：流式识别输出的是一串连续文字，需要单独模型加标点。标点同时是 TTS 分句的依据，不能省。
顺滑 + 后处理：去掉语气词（"嗯""啊"）、重复（"那个那个"）、口误；再做 ITN（"一百二十三"→"123"）、热词校正、敏感词过滤。

WebSocket 全双工协议（典型形态）

# 字段名各厂商不同，以下为典型形态，以厂商当前文档为准
client → server:  JSON 配置帧  {"format":"pcm","sample_rate":16000,"channels":1,
                               "language":"zh","enable_punctuation":true,"hotword":"达摩院"}
client → server:  二进制音频帧（PCM，建议 20ms/帧 = 640 字节 @16kHz 16bit mono）
server → client:  JSON 中间结果  {"text":"今天天气…","is_final":false,"begin_ms":0,"end_ms":1840}
server → client:  JSON 最终结果  {"text":"今天天气不错。","is_final":true}
client → server:  JSON 结束帧    {"action":"finish"}
# 一个可运行的流式 ASR 客户端骨架（websockets 库）
import asyncio, json, websockets

async def stream_asr(ws_url, wav_path, sample_rate=16000):
    async with websockets.connect(ws_url) as ws:
        # 1. 发配置帧（协议以厂商文档为准）
        await ws.send(json.dumps({
            "format": "pcm", "sample_rate": sample_rate,
            "channels": 1, "language": "zh", "enable_punctuation": True,
        }))
        # 2. 分帧推音频：20ms 一帧 = 16000*2*0.02 = 640 字节
        with open(wav_path, "rb") as f:
            while chunk := f.read(640):
                await ws.send(chunk)
        # 3. 发结束帧，触发服务端 finalize
        await ws.send(json.dumps({"action": "finish"}))
        # 4. 收结果：is_final=false 是中间结果，UI 要能"覆盖式"刷新
        async for msg in ws:
            data = json.loads(msg)
            print("[final]" if data.get("is_final") else "[partial]", data.get("text"))

asyncio.run(stream_asr("wss://asr.example.com/v1/realtime", "meeting_16k.wav"))
流式输出是"边猜边改"的。partial 结果之间不是追加关系而是覆盖关系 —— 同一个时刻区间，后面的结果会修正前面的。UI 层必须处理这个语义（只显示最新一段），日志层要只存 final 结果，否则转写文本会出现大量重复片段。
模块 4

TTS：三代合成技术与三阶段管线

三代合成技术

代际原理音质现状
参数合成用共振峰参数 + 规则生成波形机械音，一听就是机器人已淘汰，仅存于极低成本硬件
拼接合成从小时级录音库里挑"语音单元"拼起来自然度高需大量录音、不能随便换音色，已被神经合成取代
神经合成深度模型直接回归/生成声学特征接近真人当前主流，需 GPU 推理，支持流式

三阶段管线：文本前端 → 声学模型 → 声码器

阶段输入 → 输出单句耗时（GPU）常见坑
文本前端文本 → 音素 + 韵律标记< 5ms（CPU）多音字读错、数字读法混乱、中英混排失效
声学模型音素 → Mel 频谱 / 语音 token50 ~ 200ms漏字、重复读、语速失控
声码器声学特征 → 波形（24kHz 常见）20 ~ 100ms金属音、爆音（波形截断）
播放波形 → 音频输出流式分片卡顿、抖动缓冲配置不当

文本前端是中文 TTS 的重灾区：文本规整 TN（"123"→"一百二十三"）、多音字消歧（"银行"háng 不是 xíng）、G2P 转拼音/音素、韵律预测（停顿与重音）全在这一步。声学模型负责把音素变成声学特征（Mel 频谱图），有非自回归（FastSpeech 系，快、稳）和自回归（慢、易漂移）两条路线，也有 VITS 这类端到端模型把声学模型和声码器合成一个网络。声码器把频谱还原成波形，HiFi-GAN / BigVGAN / VocOS 是常见选择。

两阶段 vs 端到端："两阶段"（声学模型 + 声码器）可控性强、可以中途换音色/改语速、坏一个模块好修；端到端（VITS 类单阶段）延迟低、实现简单，但训练难、可控性弱。生产环境做实时播报，优先选支持流式的两阶段或流式端到端模型。
模块 5

实时 TTS：流式策略与首包延迟

实时 TTS 只有一个核心指标：首包延迟 TTFB（从提交文本到第一批音频可播）。用户对话场景的及格线约 300~500ms，理想 200ms 以内。

策略一：句子级分片（最基础，收益最大）

# 按标点切句，逐句合成、逐句播放 —— 首句永远先出声
import re

def split_sentences(text):
    parts = re.split(r"(?<=[。！？；!?;\n])", text)   # 保留标点的向后切分
    return [p for p in parts if p.strip()]

# 流水线：第 1 句合成时，第 2 句已进前端处理；第 1 句播放时，第 2 句在合成
# 首包延迟 ≈ 单句合成时间，与全文长度无关

策略二：流式合成与流式播放

# edge-tts 示例：边收音频分片边播（免费，走 Edge 朗读服务，仅限测试/个人用途）
import asyncio, edge_tts

async def main():
    text = "大家好。今天讲语音合成的流式策略。第一部分是句子级分片。"
    communicate = edge_tts.Communicate(text, voice="zh-CN-XiaoxiaoNeural", rate="+10%")
    async for chunk in communicate.stream():
        if chunk["type"] == "audio":
            player.write(chunk["data"])   # 第一个分片到达即可开播

asyncio.run(main())

首包延迟优化清单

手段典型收益说明
句子级分片秒级 → 几百 ms不等全文合成完，首句优先
流式声码器 / chunk 级合成再降 30%~50%声学模型边出特征、声码器边出波形
高频句缓存→ 0ms欢迎语、报数、固定话术直接播预合成音频
模型预热 / 长连接省 50~200ms避免冷启动和 TLS 握手落在关键路径上
播放 jitter buffer 调小省 50~100ms缓冲 2~3 个音频 chunk 防抖，卡顿时丢旧保新
"整段合成再播"是新手最常犯的错。一段 200 字的文本整段合成要 2~4 秒，用户盯着空白 4 秒才听到声音。另外注意：句级分片会丢失跨句韵律（句间停顿变生硬），对音色表现力要求高的场景（有声书）要权衡，可以用更大的语义单元（小句群）或开韵律上下文。
模块 6

语音交互 Pipeline 延迟拆解（数字算例）

一个"用户说完 → 系统答完"的经典链路：ASR → LLM → TTS。用参考值算一笔账，看每一分预算花在哪、怎么砍。

环节传统方案流式优化后优化手段
采集 + 网络上行50ms50ms就近接入、上行帧调小
VAD 尾点判定500ms300ms尾点静音阈值从 500ms 调到 300ms；语义 VAD 提前判停
ASR 最终结果300ms150ms流式 chunk 动态调整，尾点一出立即 finalize
LLM 首 token（TTFT）800ms400ms流式输出、就近推理、小模型兜底
LLM 全文生成2000ms被流水线掩盖关键：生成与 TTS 播放并行，不串行累加
TTS 首包500ms250ms句级分片 + 流式声码器
播放缓冲100ms60ms小 jitter buffer，卡顿丢旧保新
端到端合计≈ 4250ms≈ 1210ms优化后用户"问完 1.2 秒"开始听到回答
这笔账的核心洞察：架构改变的是"延迟的累加方式"。传统方案是串行的：每个环节等前一个环节全部完成，端到端 = 各段之和。全双工/流式架构是流水线的：LLM 吐第一个分句就开始送 TTS，LLM 还在生成时第一句已经在播了。所以链路里真正累加的只剩"首包类"延迟（VAD 尾点、ASR finalize、TTFT、TTS 首包），总生成时长被完全掩盖。这也是所有"低延迟语音助手"宣传的共同原理。
打断（barge-in）必须显式设计。用户说话说到一半想打断系统播报，链路要能做到：VAD 检测到用户语音 → 客户端立即停止播放 → 取消服务端正在进行的 TTS 合成 → 清掉该轮 ASR 的中间状态。没有打断的语音助手，用户体验是灾难级的。另外打断本身也要防误触发（咳嗽、背景人声），可以加"连续语音时长 > 300ms"或能量阈值双重确认。

代码 4：TTS 流式播报（edge-tts，带句级分片）

import asyncio, re, edge_tts

def split_sentences(text):
    parts = re.split(r"(?<=[。！？；!?;\n])", text)
    return [p for p in parts if p.strip()]

async def speak(text):
    for sent in split_sentences(text):        # 逐句，首句优先出声
        comm = edge_tts.Communicate(sent, voice="zh-CN-XiaoxiaoNeural")
        async for chunk in comm.stream():
            if chunk["type"] == "audio":
                player.write(chunk["data"])

asyncio.run(speak("订单已收到。预计三十分钟内送达。感谢您的耐心等待。"))
选型决策树：① 数据敏感、量大（日均音频 > 数十小时）→ 私有化 FunASR 系；② 快速验证 MVP、量小 → 商业 API；③ 多语言混杂、离线质量优先 → Whisper；④ 实时交互 → 只选支持流式的模型，Whisper 整段模型直接出局。TTS 侧同理：商用产品用商业 API（音色授权清晰），自建选 CosyVoice/VITS 类开源方案，音色的商用授权范围务必让法务过一遍。

中文场景六大坑

这些坑英文技术栈不存在或不明显，但每一个都能让中文语音产品的体验崩掉。

问题例子表现处理方式

避坑

十个真实坑

1
采样率不匹配，直接把 44.1kHz 音频喂 16kHz 模型
等于把语速拉慢 2.76 倍，WER 直接崩。入模前统一重采样：ffmpeg -i in.mp3 -ar 16000 -ac 1 -f wav out.wav。
2
实时链路用 Whisper 整段模型
Whisper 是 30s 窗口整段解码，尾点延迟秒级，RTF 也难看。实时场景换流式模型（Paraformer 系），或"流式出中间结果 + 整段校正"的混合架构。
3
VAD 尾点阈值拍脑袋
静音阈值 500ms：慢但稳，适合会议；300ms：快但容易把思考中的停顿切断，适合对话。按场景调，并用真实录音统计误切率。
4
WebSocket 不做重连和断点续传
弱网、切后台、NAT 超时都会断流，且往往静默失败（用户以为还在识别）。必须：指数退避重连 + 重发最后 2~3 秒音频 + 应用层心跳。
5
TTS 等全文合成完再播放
首包延迟 = 全文合成时间（2~4 秒）。必须句级分片流式播放，首包才能压到 300ms 以内。
6
数字读法不处理
"2024"读成"二千零二十四"还是"二零二四"随机漂移；电话号码按数值读出来没人听得懂。按业务定制 TN/ITN 规则表并回归测试。
7
多音字不处理
"银行"读成"yín xíng"、"重庆"读错音，品牌词一念错就是事故。自定义词典 + 发音标注，上线前把品牌/产品名全量过一遍。
8
热词一把梭
塞几百条热词、权重拉满，整体 WER 反而劣化。控制在几十条，低权重起步，测试集量化收益。
9
中英混排直接送 TTS
"GPU"被当中文读成"咕噗"，或英文整句被跳过。开多语言 TTS，或自己做语言分段，分别合成再拼接。
10
只用标准普通话 + 干净录音做测试
上线遇到 8kHz 电话信道、远场、电视背景声，WER 直接翻倍。测试集必须覆盖真实信道：不同采样率、噪声、口音、远场。
自测

六道题

1. 参考文本共 100 个词，识别结果有 3 个词被替换、2 个词漏识别、1 个词多识别。WER 是多少？
正确答案：6%。WER = (S + D + I) / N = (3 + 2 + 1) / 100 = 6%。中文场景通常按字算 CER，但公式完全一样。
2. 某 ASR 模型 RTF = 0.3，含义是？
正确答案：RTF = 处理耗时 / 音频时长 = 0.3，即处理速度是播放速度的约 3.3 倍。RTF < 1 是实时链路的入场券；全双工交互场景还要求 RTF 远小于 1（通常 < 0.1）给网络和抖动留余量。
3. 给中文 ASR 模型送音频，标准输入格式是？
正确答案：16kHz 单声道 16bit PCM。ASR 模型基本按 16kHz 训练，采样率不匹配等于改变语速，WER 直接崩。用 ffmpeg -ar 16000 -ac 1 统一转换。
4. 降低 TTS 首包延迟（TTFB）最有效的手段是？
正确答案：句子级分片 + 流式播放。整段合成的首包 = 全文合成时间（2~4 秒）；分片后首包 ≈ 单句合成时间（几百毫秒），且与全文长度无关。代价是损失部分跨句韵律。
5. 语音助手端到端延迟从约 4.3 秒优化到约 1.2 秒，最关键的架构变化是？
正确答案：流水线并行。LLM 吐第一个分句就送 TTS，生成与播放重叠，总生成时长被掩盖；真正累加的只剩 VAD 尾点、ASR finalize、LLM 首 token、TTS 首包这几段。VAD 不能去掉，只能把阈值调优。
6. 关于 ASR 热词，哪种做法是对的？
正确答案：控制数量与权重，量化验证。热词本质是给解码加偏置，过量或过权重会让模型把正常文本也往热词上靠，整体 WER 反而劣化。主流 ASR（如 FunASR）都支持 hotword 参数。
