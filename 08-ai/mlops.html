二十分钟入门 MLOps 工程体系

模型不是训练完就结束，是部署后开始腐烂。这篇讲 ML 的完整生命周期：实验管理、特征平台、部署策略、漂移监控、再训练触发——以及为什么 ML 流水线里最贵的是"数据"和"回滚能力"。

开始前

先跑起来实验管理

MLOps 的入口是"实验可追溯"。在搭任何复杂平台之前，先做到：每次训练有记录、每个模型有出处、每个指标能复现。

pip install mlflow开源实验管理标准件，tracking + registry + serving 一体
mlflow server --backend-store-uri sqlite:///mlflow.db --default-artifact-root ./mlruns本地起 tracking server，生产换 Postgres + S3/MinIO
MLFLOW_TRACKING_URI=http://localhost:5000训练脚本里设这个环境变量即开始记录
# 最小组装：起 server → 跑一个带记录的实验
mlflow server --host 0.0.0.0 --port 5000 \
  --backend-store-uri postgresql://user:pass@localhost/mlflow \
  --default-artifact-root s3://mlops-bucket/mlartifacts

# 训练脚本加三行就接入
import mlflow
mlflow.set_experiment("churn-prediction")
with mlflow.start_run():
    mlflow.log_params({"lr": 0.01, "max_depth": 6})
    model = train(...)
    mlflow.log_metric("auc", evaluate(model))
    mlflow.sklearn.log_model(model, "model")   # 模型文件自动存 artifact
MLOps 的第一性原理：能复现。三个月后有人问"线上这个模型是怎么训的"，你要能在 5 分钟内回答：代码版本、数据版本、超参、环境、随机种子。答不上来，说明你的 MLOps 还没开始。
模块 1

MLOps 与传统 DevOps 的差异

DevOps 的很多实践直接搬到 ML 上会失效。原因：ML 系统的不确定性来自两个 DevOps 不关心的维度——数据和统计规律。

维度传统 DevOpsMLOps
代码 + 配置决定系统行为的就是代码代码只决定"怎么学"，数据和超参同样决定系统行为
测试单元测试 + 集成测试，通过即上线要加数据验证（schema、分布、标注质量）和模型验证（指标、公平性）
部署滚动发布，新旧版本行为一致模型版本间行为可能大幅变化，要影子发布、灰度对比
监控CPU、内存、QPS、错误率上面全要，再加数据漂移、概念漂移、指标衰减
回滚回滚到上一个镜像即可回滚模型 + 回滚特征逻辑，因为服务端可能复现不了训练时的特征
团队开发 + 运维数据工程师 + ML 工程师 + 平台工程师 + 运维，角色更多、接口更碎

MLOps 要额外回答的三个问题

① 这个线上模型是哪个训练产物？（模型血缘：数据版本 + 代码版本 + 超参）
② 它现在还好吗？（不是服务活着，是预测还准吗——需要延迟标签回流）
③ 什么时候该重训？（漂移触发？定时？标签积累到阈值？）
最大的认知差：DevOps 里"部署完成"是终点，MLOps 里"部署完成"是腐烂的开始。用户行为在变、数据分布在变、欺诈手段在变，模型效果只会单调衰减。没有再训练机制的 ML 系统，上线那天就是效果最好的一天。
模块 2

ML 生命周期：五个环节

把 ML 项目当成一条流水线，而不是一个训练脚本。每个环节有明确的输入输出和验收标准，这才是工程化。

① 实验。目标：找到"值得投产"的配方。产出：MLflow run（超参 + 指标 + 模型 artifact）。验收：离线指标超过基线，且能在干净环境复现
② 训练。目标：把实验配方变成可版本化的正式产物。产出：注册模型（Registry）+ 训练数据快照。验收：流水线可一键重跑，产出模型指纹
③ 部署。目标：让模型以约定的延迟/吞吐对外服务。产出：推理服务 + 路由配置。验收：压测通过、影子流量对比达标、回滚演练通过
④ 监控。目标：知道模型"现在准不准"。产出：漂移仪表盘 + 告警。验收：能回答"昨天预测分布变了没有"
⑤ 再训练。目标：用新数据把效果拉回来。产出：新版本模型，回到 ②。验收：触发条件明确，重训流水线自动跑通

一个典型的流失预测项目时间线

时间阶段关键动作
T+0 ~ T+2 周实验定标签（什么算"流失"）、拉历史数据、跑 50+ run 找配方
T+2 ~ T+3 周训练全量数据训练 v1，注册模型，跑模型卡（数据范围、已知缺陷）
T+3 ~ T+4 周部署影子模式跑一周 → 10% 灰度 → 全量。每天对比影子与线上的 AUC
T+4 周起监控PSI 日报、AUC 周报（标签回流后）、漂移告警接值班
T+8 周再训练PSI 超阈值触发自动重训，新模型过灰度后替换
经验法则：实验占 30% 精力，把模型可靠地送上线占 40%，监控和再训练占 30%。大部分团队倒过来（90% 时间调模型），结果上线即巅峰，之后无人维护。
模块 3

实验管理：MLflow 与 W&B

实验管理工具的核心就四件事：run（记录）、artifact（存产物）、registry（管版本）、compare（比结果）。选型先想清楚自建还是托管。

工具部署形态优势注意点
MLflow开源自建（Docker Compose 起）tracking/registry/serving 全家桶、生态广、无厂商锁定UI 简陋、大规模实验检索慢、artifact 要自己接对象存储
W&B托管 SaaS（有私有部署）可视化强、报告协作好、 sweep 调参自动化数据出境合规要评估；免费额度外按量计费
其他—Neptune、Comet（类似 W&B）；国内厂商的一体化平台功能同质化，选团队顺手的

MLflow 的四个核心概念

# 1. Experiment：一个实验组，对应一个业务问题
mlflow.set_experiment("churn-prediction-v3")

# 2. Run：一次训练。params/metrics/tags 全部结构化记录
with mlflow.start_run(run_name="xgb-bs64-lr001"):
    mlflow.log_params({...})          # 超参，一次性的
    mlflow.log_metric("auc", 0.91)    # 指标，可带 step 记曲线
    mlflow.set_tag("data_version", "20261001")  # 标签，自定义维度

# 3. Artifact：模型文件、图表、数据样本，存对象存储
mlflow.sklearn.log_model(model, "model", registered_model_name="churn-model")

# 4. Registry：模型版本仓库。stage 管理：Staging → Production → Archived
client = MlflowClient()
client.transition_model_version_stage(
    name="churn-model", version=7, stage="Production")

模型注册表的最佳实践

  • 一个模型名对应一个服务角色（如 churn-model 是线上服务加载的名字），版本号递增
  • Stage 即开关：服务加载 models:/churn-model/Production，灰度时把新版本推到 Staging，改服务端引用即可，不用动服务
  • 模型卡写进 artifact：训练数据范围、评估指标、已知失效场景（"对新增渠道用户效果未验证"）——这是给 review 委员会看的
  • Promotion 要留痕：谁批准的、基于哪些指标、回滚预案是什么，记在 tag 或工单里
W&B 与 MLflow 不必二选一。常见组合：W&B 做实验期探索（可视化好），MLflow Registry 做模型版本管理（部署侧标准）。但两套系统意味着数据两份、元数据要同步——团队小于 5 个 ML 工程师时，先用 MLflow 一套，别过度设计。
模块 4

特征平台：离线在线一致性

特征平台是 MLOps 里最容易被低估的一环。它解决的核心问题只有一个：训练时用的特征，线上服务时必须能取到同样的值。

训练-服务偏斜（Training-Serving Skew）是什么

# 经典事故：同一个"用户近 30 天消费金额"特征，两边算法不同
离线训练（Spark，T+1 批量）：  # 用当天全量日志回算，含当天数据
  近30天金额 = SUM(orders.amount) WHERE date BETWEEN today-30 AND today

线上服务（Java 实时）：          # 只查得到实时库，边界差一天
  近30天金额 = SUM(orders.amount) WHERE create_time > now-30*86400

# 结果：离线 AUC 0.85，上线后 0.62。两边算的压根不是一个特征
训练-服务偏斜是 ML 上线事故的头号原因，而且极难排查——离线指标漂亮、线上效果烂，两边单看都没错，错在"不一致"。解法只有一个原则：同一份特征计算逻辑，离线线上共用。

特征平台的两条实现路线

路线做法适用
共享特征库离线批算写入特征存储（Redis/HBase），线上直接读取，训练时按 point-in-time join 回历史值主流方案。 Feast、Tecton 等框架即此思路
共享计算逻辑特征逻辑用同一份 DSL/库实现（如 Python UDF 同时跑 Spark 和 Flink），两边结果天然一致工程能力强的团队，避免双份实现的漂移
# point-in-time 取数：训练时按"事件发生时刻"取特征，防未来数据泄露
# 错：用今天的用户表 join 3 个月前的订单（特征里混进了未来信息）
# 对：按订单发生时间，取那一刻的用户属性快照
SELECT o.order_id, u.age, u.city
FROM orders o
JOIN user_features u ON u.user_id = o.user_id
WHERE u.event_time = (                          # 关键：不晚于订单时刻的最近一条特征
    SELECT MAX(event_time) FROM user_features uf
    WHERE uf.user_id = o.user_id AND uf.event_time <= o.order_time
)
数据泄露的隐蔽版本：比偏斜更阴险。训练时不小心用了标签之后才产生的信息（如"用户在订单后 7 天内是否投诉"来预测"是否流失"），离线 AUC 冲到 0.95，上线后原形毕露。特征时间戳必须严格早于标签时间，这条要用代码断言强制，不靠人 review。
小团队的务实路线：不建平台，先建规范。① 特征逻辑只写一份（SQL 或 Python），离线线上共用；② 每个特征有 owner、有数据契约（schema + 监控）；③ 特征表带 event_time 列，训练侧强制 point-in-time。三个 ML 工程师以下搞自建特征平台，投入产出比通常是负的。
模块 5

模型部署：batch / online / edge 与灰度策略

部署形态先于部署工具。先回答"多少延迟、多大流量、多频繁"，再选 batch、在线还是边缘。

形态适用场景典型延迟代表技术
Batch 离线推荐列表、用户分群、T+1 报表小时级Spark/Flink 批任务，结果写库或数仓
Online 在线搜索排序、风控实时决策、反欺诈毫秒~百毫秒TF Serving、Triton、自研 FastAPI + ONNX
Edge 边缘手机端推理、IoT、隐私敏感场景本地毫秒Core ML、TFLite、端侧量化模型

四种上线策略，安全性递增

策略做法风险与成本
直接替换新模型换旧模型，观察指标风险最高。只敢在小流量内部工具用
金丝雀 canary1% → 5% → 25% → 100%，每档观察指标主流。每档至少观察一个业务周期（推荐类至少一天）
影子 shadow新模型实时推理但不响应用户，只记录结果对比零用户风险。验证效果差异的金标准，成本是双倍算力
A/B 实验按用户分桶，新模型对实验组，统计显著性后决策科学但慢（要样本量），适合 C 端核心功能
# 影子模式的落地要点
1. 网关层复制实时请求 → 新模型服务（异步，不阻塞主链路）
2. 两边输出 + 特征输入全部落日志（后续做差异分析）
3. 对比维度：预测分布差异、关键 case 分歧率、延迟差异
4. 分歧率 > 阈值的 case 送人工标注，定位是改进还是回退

# 灰度自动化的最小配置（以 K8s 为例）
- 模型版本打成独立 Deployment（churn-model:v2）
- Service 按权重分流：stable 90% / canary 10%
- 每档设晋升条件：P99 延迟 < 基线 +10%，预测分布 PSI < 0.1
- 任一条件破线 → 自动回滚到 stable（Argo Rollouts 可配）
在线部署的隐形杀手：冷启动与资源争抢。模型加载慢（大模型几十秒）、首请求超时、GPU 显存被训练任务挤占。上线 checklist 必查：模型加载时间、预热请求、资源限额（requests/limits 写死）、以及"训练和推理能不能跑在同一集群"（能，但要隔离资源池和优先级）。
模块 6

模型监控：漂移与衰减

服务活着不等于模型健康。模型监控要回答两个问题：输入的数据变了吗（数据漂移）？输入输出关系变了吗（概念漂移）？以及最要紧的——效果烂了多少（性能衰减）。

类型含义检测手段
数据漂移输入特征分布变了（用户年龄结构迁移、新渠道涌入）PSI（群体稳定性指数）、KS 检验、分箱分布对比
概念漂移X 和 y 的关系变了（同样的特征，现在流失率不同）指标衰减监控（需要标签回流）
性能衰减业务指标随时间下滑，前两者共同作用的结果AUC/准确率的滚动窗口监控、业务 KPI 关联分析

PSI：最实用的漂移指标

# PSI = Σ (实际占比 - 预期占比) × ln(实际占比 / 预期占比)
# 按训练集分布为基准，分 10 箱，逐箱算再求和

PSI < 0.1   分布基本一致，放行
0.1 ~ 0.25  轻微漂移，关注趋势，不触发动作
PSI > 0.25  显著漂移，触发告警 + 评估重训

# 监控哪些维度：每个特征的 PSI + 预测值分布的 PSI（后者更灵敏，
# 因为它综合了所有特征的变化，且不需要等标签）
最大的监控难点：标签延迟。风控模型 7 天后才知道是否违约，推荐模型要等用户点击。没有标签就评不了准确率——所以预测分布监控（PSI）是第一道防线，指标衰减是第二道。两者都要有，只靠一个都会瞎。

监控分层清单

特征分布 PSI（日）输入侧哨兵，发现"数据变了"
预测分布 PSI（日）输出侧哨兵，无需标签，最灵敏
指标滚动 AUC（周）标签回流后的真指标，确认效果衰减
业务 KPI 关联（周）模型指标涨 ≠ 业务涨，要对照 GMV/转化率
服务指标（实时）延迟 P99、错误率、资源占用——DevOps 那套照搬
特征缺失率 / 默认值率（日）上游管道挂了会先体现在这里
模块 7

再训练触发策略与 CI/CD for ML

再训练不是"每周一早上定时跑"，而是有明确触发条件、有验证门禁、有回滚预案的自动化流程。业界称之为 CT（Continuous Training，持续训练）。

三种触发策略对比

策略触发条件优劣
定时重训每天/每周/每月，固定节奏简单可靠，但可能白训（数据没变）或漏训（月中劣化）
漂移触发PSI 超阈值、指标跌破基线推荐组合。及时且省算力，但要防抖动（设持续 N 天才触发）
标签积累触发新标注样本达到一定量（如 +10%）适合冷启动后的持续改进，常与漂移触发叠加
# 再训练的完整决策链（伪代码）
daily_check():
    psi = compute_psi(today_features, train_baseline)
    auc = rolling_auc(last_14d, if labels available)

    if psi > 0.25 and psi_streak > 3:      # 连续 3 天超阈值才触发，防抖
        trigger_retrain(reason="data_drift")
    elif auc < baseline - 0.03:              # 指标跌超 3 个点
        trigger_retrain(reason="performance_decay")
    elif new_labeled_samples > 0.1 * total:
        trigger_retrain(reason="label_accumulation")

trigger_retrain(reason):
    run_training_pipeline(data_snapshot="latest", version="auto")
    if eval_auc(new_model) > eval_auc(prod_model) + 0.01:   # 门禁：必须显著更好
        promote_to_canary()
    else:
        archive(reason="not_better")                   # 白训就归档，别硬上

CI/CD for ML：比传统 CI/CD 多三道门

阶段传统 CI/CDML 特有
CI 阶段代码 lint、单测、构建镜像数据验证（schema、缺失率、标注抽检）、训练 smoke test（小数据跑通全链路）
CD 阶段部署到 staging/prod模型门禁（指标超过基线）、影子对比、灰度自动晋升/回滚
CT 阶段无持续训练：漂移触发 → 自动重训 → 自动门禁 → 自动灰度
渐进式落地顺序（别一步到位）：① 先把训练脚本参数化 + MLflow 记录（1 周）；② 再接数据验证和 smoke test 进 CI（1 周）；③ 然后做模型门禁和 canary（2 周）；④ 最后才上自动重训（2 周+）。90% 的团队死在第三步之前——因为模型还没管好就想着全自动。
避坑

十个真实工程坑

1
训练-服务偏斜：离线 AUC 0.85，上线 0.62
同一个特征两边算法不同（时间边界差一天、聚合口径不同）。解法：特征逻辑只写一份共用，或建共享特征库按 point-in-time 取数。
2
模型腐烂无监控：上线半年没人看过指标
数据在变、用户在变，效果单调衰减。最小监控：特征 PSI 日报 + 预测分布 PSI + 标签回流后的滚动 AUC，缺一个都算没监控。
3
手工流程不可复现："我记得当时是这么调的"
模型是某台机器上跑的，数据版本说不清，三个月后无法复现也无法审计。所有训练必须进流水线 + MLflow 记录，人肉跑脚本是技术债。
4
数据泄露：特征里混进了"未来信息"
用标签产生之后的数据做特征（如用"7 天内是否投诉"预测"是否流失"），离线 0.95 上线崩盘。特征时间戳必须严格早于标签时间，用断言强制。
5
金丝雀没有晋升/回滚标准，灰度变成永久灰度
10% 流量跑了一个月，没人敢全量也没人敢回滚。每档灰度必须写死晋升条件和回滚条件（延迟、PSI、AUC），达标自动走。
6
训练推理抢资源：推理 P99 被训练任务打爆
同一个 GPU 集群跑训练和推理，训练一波潮直接把在线延迟拖垮。资源池隔离 + 优先级抢占，在线服务的 requests/limits 要写死。
7
把模型指标当业务指标：AUC 涨了业务跌了
过拟合了离线分布，或者优化目标本身就偏离业务（点击率涨但客单价跌）。监控必须关联业务 KPI，模型指标只是中间量。
8
再训练触发器没有防抖，一天重训八次
PSI 单日超阈值就触发，遇上数据源抽风全月白训。加持续天数要求（连续 3 天超线）+ 每日最多触发一次 + 重训要过门禁。
9
模型文件当二进制乱放：S3 里一堆 model.pkl
不知道哪个对应哪个版本、用什么数据训的。进 Registry：模型名 + 版本号 + stage + 模型卡 + 训练数据指纹，一个不能少。
10
没有回滚预案：新模型出事只能现找旧文件
旧模型早被覆盖、旧特征逻辑已下线，回滚比新写还慢。上一个生产版本的模型和特征快照至少保留 90 天，回滚流程每季度演练一次。
自测

六道题

1. "训练-服务偏斜"（Training-Serving Skew）指的是？
正确答案：特征计算逻辑两边不一致。经典如"近 30 天金额"离线含当天、线上不含，离线 AUC 0.85 上线 0.62。解法：特征逻辑只写一份共用（共享 DSL 或特征库按 point-in-time 取数）。这是 ML 上线事故头号原因。
2. 没有标签回流的情况下，最灵敏的模型健康监控指标是？
正确答案：预测分布 PSI。AUC 需要标签，风控/推荐场景标签可能延迟数天到数周；预测分布是所有特征变化的综合投影，无需标签即可计算。特征是第一道防线，PSI 是"穷人版实时监控"的核心。
3. PSI 值 0.3 表示什么？
正确答案：显著漂移。常用分级：小于 0.1 一致、0.1~0.25 轻微关注、超过 0.25 显著漂移。触发重训前还要加防抖（连续多天超线），且重训结果必须过"比线上显著更好"的门禁，否则归档。
4. 想验证新模型效果又完全不影响用户，应该用哪种部署策略？
正确答案：影子模式。影子零用户风险：请求复制一份给新模型，输出只落库不返回。对比预测分布和分歧 case，确认优于线上后再进金丝雀。金丝雀已经有用户暴露，属于第二道防线。
5. CI/CD for ML 相比传统 CI/CD，最需要新增的环节是？
正确答案：数据验证 + 模型门禁 + CT。ML 系统里代码之外，数据和统计规律同样决定行为：CI 要验证数据，CD 要门禁模型指标，外加传统 CI/CD 没有的持续训练闭环。传统环节照搬即可。
6. 关于"灾难性回滚缺失"，正确做法是？
正确答案：保留旧版本 + 定期演练。回滚不只是模型文件，还包括当时的特征逻辑和上游数据状态。只留代码不留模型和特征快照，回滚比新写还慢。这也是 ML 回滚比传统部署难的根本原因。
