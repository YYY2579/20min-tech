先建立直觉：你写的每一个字、每一个空格，在到达模型之前都会被切成 token。一个 token 大致是：英文 4 个字符、中文 1 个汉字、数字 3 位一组。这个"大致"就是本篇所有工程问题的根源。
模块 1

模型不读字符：从文字到 token id

LLM 的输入不是字符串，是一个整数序列。分词器（tokenizer）就是把字符串映射到整数序列的那张"码表 + 切分规则"。

# 一次 API 调用背后发生了什么
"你好，世界"
   ↓ tokenizer 切分 + 查词表
[144248, 8808, 2575, ...]        # token id 序列
   ↓ embedding 层查表
[[0.013, -0.22, ...], ...]       # 每个 id 变成一个向量
   ↓ Transformer 逐层计算
输出 logits → 采样 → 下一个 token id
   ↓ detokenizer 拼接
"！"

为什么不能用"词"做单位

方案问题
整词查表OOV（未登录词）灾难：词表装不下所有词（几十万常见词只是冰山一角），遇到没收录的词（新造词、错别字、罕见拼写、代码变量名）直接无法编码
单字符/单字节没有 OOV，但序列爆炸：一个英文单词平均 4~5 个字母就是 4~5 个 token，同样语义的文本 token 数多好几倍，上下文窗口和算力都被浪费
子词（当前主流）折中：常见词整体是一个 token，罕见词拆成熟悉的碎片。序列短、无 OOV、还能让"词根词缀"共享表示（如 un- + believ + able）
子词的核心红利是"压缩率 + 泛化"两头都要：高频组合整体编码省 token；低频组合拆碎仍可编码，且语义相近的碎片共享训练信号。现代 LLM 全部采用字节级子词（byte-level），即最终回退到 256 个字节，任何 Unicode 文本都不会出现 OOV。

一次"分词"的三步流水线（以 BPE 为例）

Normalization（归一化）：统一大小写、Unicode 规范化（NFC/NFD）、处理空白。注意：大小写归一化会让 "Apple" 和 "apple" 变得难以区分，现代模型大多不做大小写折叠
Pre-tokenization（预切分）：先按简单规则粗切——英文按单词和标点、空白单独成组、数字分组。关键：合并不会跨过预切分的边界，这就是"数字按 3 位一组"的来源
模型编码（Model）：对每个预切分片段，按词表优先级反复做"合并"直到全是单个 token，最后查 id
模块 2

四种主流算法：BPE、WordPiece、Unigram、SentencePiece

算法核心思想代表
BPE从"单字节/单字符"开始，统计语料中相邻 pair 的出现频率，每次把最高频的一对合并成新 token，重复 N 次得到 N+256 个词表GPT 全系（GPT-2 起为字节级 BBPE）
WordPiece同样做合并，但打分标准不同：选能让训练语料的语言模型似然提升最大的合并（用 ## 表示词中续接），是"带目标的 BPE"BERT、DistilBERT、Electra
Unigram反向操作：先构造一个很大的种子词表，然后循环"删掉那个删了之后似然损失最小的 token"，逐步瘦身到目标大小T5、ALBERT、LLaMA（早期版）
SentencePiece不是第四种算法，是工具包：把输入当原始字节流、不依赖预分词（空格也变成 token ▁），底层可选 BPE 或 Unigram。对中日韩这种无空格分词的语言天然友好LLaMA、T5、ChatGLM、多数中文模型

BPE 合并过程示意（对 "low lower newest" 这种小语料）

# 初始：每个字符是一个 token，词表 = 26 字母 + 特殊符号
l o w | l o w e r | n e w e s t

# 第 1 轮：统计相邻 pair 频率，'e'+'r' / 'l'+'o' / 'o'+'w' ...
# 假设最高频是 ('e','r') → 合并出新 token 'er'，词表 +1
l o w | l o w er | n e w e s t

# 继续迭代：('er','est') → 'erest'，('lo','w') → 'low' ...
# 最终 'lower' 可能被切成 lo w er / low er 等，取决于训练语料
# 训练目标：合并到预设词表大小（如 32000、100277、200000）
工程上只需要记住三件事：① 词表是训练时定死的，推理时只能查表，不能发明新 token；② 字节级词表（256 基础符号）保证任何字节序列可编码，代价是乱码/罕见字符会变成一串无意义碎片；③ 不同模型的 tokenizer 互不通用，数字 id 完全相同也可能对应完全不同的文本片段。
模块 3

词表差异：为什么中文"一个汉字一两个 token"

词表大小和训练语料构成，直接决定你的文本被切成多少段。同样一句话，不同模型的 token 数可能差 30% 以上——这直接等于成本和窗口利用率的差异。

词表 / 编码大小说明
r50k_base50,257GPT-3 时代，BPE 非字节级边界情况
p50k_base50,281Codex / text-davinci 系列
cl100k_base100,277GPT-3.5-Turbo / GPT-4 / GPT-4-Turbo，对中文明显更友好
o200k_base约 200,000GPT-4o 及后续，多语言覆盖大幅提升，中文字符碎片化显著减少
Llama 3128,256开源阵营大词表代表，跨语言均衡
Qwen2151,936中文语料占比高，中文压缩率优秀
bert-base-chinese21,128字粒度中文词表，单字即 token

各语言的"token 效率"（同样语义所需 token 数的相对量级）

语言典型比率（每 token 承载）工程含义
英文1 token ≈ 4 字符 ≈ 0.75 个单词词表设计的"主场"，效率最高
中文常用汉字 ≈ 1 token/字；次常用字 ≈ 2~3 字节级 token100k 词表下中文已很划算；200k 词表更省。同样信息量中文 token 通常少于英文
日/韩假名 ≈ 1~2 token/字，谚文按音节块切分介于中英之间
代码1 token ≈ 3~4 字符，缩进与重复符号会合并JSON/XML 这类结构化文本中，引号、括号、引号键名很吃 token
数字每 3 位一组（预切分规则）1234567890 → 4 个 token；长 ID、时间戳、哈希值是 token 杀手
量级结论（面试和容量估算都能用）：在 100k 级词表下，一个汉字约 1~2 个 token，一个英文单词约 1.3 个 token，一个阿拉伯数字约 1/3 个 token。用"中文每字 1.5 token"做粗估，误差通常在 ±30% 内——但上线前一定要用真实 tokenizer 校准，尤其是你的 Prompt 里有大量数字、代码、专有名词时。
为什么"词表大小"是厂商竞争点：同样一篇中文文档，词表覆盖好的模型可能 800 token，覆盖差的要 1200 token。对用户这是 33% 的成本差和上下文差；对厂商这是"同样硬件能服务更多请求"。所以 Qwen、Llama 3 都卷到 12 万~15 万词表，且训练语料的多语言配比直接决定中文效率。
模块 4

Token 计费与上下文窗口

token 是 LLM 世界的"字节 + 毫秒"：既决定你花多少钱，也决定模型一次能"看"多少东西。

计费模型

计费项说明
输入 token（prompt）每次请求都要全额付费，包括系统提示、历史消息、RAG 检索内容、工具定义。多轮对话如果不做处理，历史会线性累积
输出 token（completion）通常比输入贵数倍。模型逐 token 生成，输出越长延迟越高
缓存命中 tokenPrompt Caching / Context Caching：相同的前缀（系统提示、长文档）命中缓存时按折扣价计费、延迟更低。前提是前缀逐字节一致
usage 字段API 响应里的 prompt_tokens / completion_tokens / total_tokens 是真实计费依据，本地 tokenizer 计数只用于预估

上下文窗口（context window）

概念说明
窗口 = 输入 + 输出128k 窗口不是"能读 128k"，是"输入 + 输出加起来不超过 128k"。你塞 120k 的输入，模型最多只能再写 8k
max_tokensAPI 参数，限制单次输出长度。和窗口是两个独立参数，都设错都会出事
常见规格4k / 8k / 16k / 32k / 128k / 200k / 1M 不等，同模型不同版本窗口也不同。以所用模型当前文档为准
长窗口 ≠ 免费128k 窗口塞满 100k 的输入，单次请求成本就是实打实的 100k token 钱。而且注意力和延迟随长度增长，超长上下文中部信息的利用率会下降（见上下文工程篇）
# 一次请求的成本估算（以各厂商实时价目表为准）
cost = (prompt_tokens * price_in + completion_tokens * price_out) / 1000

# 多轮对话的隐性爆炸：不裁剪历史时，第 N 轮的输入 ≈ 系统提示 + 前 N-1 轮全部
# 轮次:   1      2      3      ...   N
# 输入:   S      S+T1   S+T1+T2 ...   S+sum(T1..Tn)   —— 平方级增长
# 解法：滑动窗口 / 摘要压缩历史 / 只带必要历史（详见上下文工程篇）
预算公式先算再写：单次请求 token 预算 = 系统提示 + 工具定义 + 检索内容 + 历史 + 用户输入 + 预留输出。任何一项超限，轻则触发窗口错误，重则历史被静默截断、模型"失忆"。把 max_tokens 留足（如窗口 128k、输入 100k 时输出至少要给 4k~16k）是基本素养。

② 截断：按 token 边界，不是按字符

# 错误示范：按字符截断 —— 会把 UTF-8 多字节字符和 token 边界砍断
bad = text[:1000]                    # 中文下可能产生乱码，token 数也不可控

# 正确：编码 → 截 id → 解码，保证落在 token 边界
enc = tiktoken.get_encoding("cl100k_base")
ids = enc.encode(text)
if len(ids) > budget:
    ids = ids[:budget]
truncated = enc.decode(ids)          # 永远是合法文本

# 截哪一端？三种策略
# 1) 截头部：保留最新内容（长文档问答常用，但丢开头背景）
# 2) 截尾部：保留开头背景（指令类任务常用，但丢最新信息）
# 3) 截中间：保留首尾（"Lost in the Middle"的对策，长上下文更推荐）
def truncate_middle(ids, budget):
    if len(ids) <= budget: return ids
    half = budget // 2
    return ids[:half] + ids[-(budget - half):]

③ 特殊 token：看不见但占额度

Token作用
<|endoftext|>文档结束符，GPT 系用于标识训练样本边界
<|im_start|> / <|im_end|>ChatML 等对话模板的角色边界标记，每轮消息都带
[CLS] / [SEP] / [PAD]BERT 系的句首、句间、填充标记
<|system|> 等角色标记不同模板命名不同，但都存在：每条消息的结构包装都要花钱
tiktoken 的"特殊 token 暗礁"：用 enc.encode(text) 编码一段含有 <|endoftext|> 字面量的普通文本时，默认会直接抛 ValueError（禁止特殊 token 混入普通文本）。处理用户输入必须先过滤或转义这些字面量，否则线上就是 500。需要放行时用 enc.encode(text, allowed_special="all")。
模块 6

中文分词四大陷阱

陷阱现象后果与对策
数字被打碎预切分规则把连续数字按 3 位一组切开，长数字串 token 数爆炸让模型做多位数算术、比对长 ID 时容易出错。对策：预算里给数字单独加权；对 ID/哈希考虑用十六进制短表示或提示模型逐位处理
代码/JSON 被切碎缩进、连续空格、转义符、罕见符号各自成 token；JSON 的键名引号重复出现结构化文本 token 效率低。对策：精简 schema 键名、用紧凑分隔、去掉无意义缩进；压缩历史工具结果
罕见词/生僻字未收录的词被拆成字节级碎片，一个词 4~8 个 token专有名词、新造词、化学式、人名是重灾区。对策：建立"术语 → 常用同义表述"的映射；对高频专有名词在提示中首次出现时给解释
中英混排中英之间无空格，切分器按脚本边界处理，可能出现高 token 碎片"用Python实现BPE算法"这类文本 token 数高于纯中文。对策：实测，不要按纯中文估算
# 实测对比（cl100k_base，量级参考，以你本地 tokenizer 为准）
"你好，世界"                    # 约 4~5 token（含标点）
"你好世界你好世界你好世界"        # 约 9 token —— 重复模式会被合并，不是 15
"Transformer"                  # 约 1~2 token（高频技术词整体成 token）
"tiktokenizer"                  # 约 3~4 token（生僻组合被拆碎）
"1234567890"                    # 4 token（123/456/789/0，数字按 3 位分组）

"    def foo():"                # 前导空格 + def + 空格 + foo + ( + ) + : 多个 token
"🚀🎉"                          # 每个 emoji 约 2~4 token（多字节 UTF-8 序列）
血泪模式：把一段含长数字 ID 的用户输入直接拼进 Prompt，token 数比你预估多 2 倍；或者 text[:2000] 截断把汉字砍成乱码，模型读到 å¿ 这种字节碎片后行为完全不可控。凡是涉及用户可控文本，一律先 tokenize 再截断。
模块 7

多语言与 Emoji 处理

多语言的三层坑

Unicode 规范化
同一个"é"可以是 1 个码位（NFC）或 e + 组合符（NFD），字节不同但看起来一样。tokenizer 通常做 NFC 归一化，但你自己做字符串比对（去重、缓存 key）时必须先 normalize，否则缓存永远打不中
脚本边界混排
拉丁、CJK、阿拉伯、Emoji 混排时，预切分按 Unicode 脚本类别断开。做多语言产品时，token 估算必须按目标语言分别校准，不能拿英文比率套中文
小语种碎片化
词表训练语料里占比小的语言（泰语、高棉语、非洲语言）大量走字节回退，1 个词 5~10 token。面向小语种的产品，成本模型要重算

Emoji 与特殊字符

字符类型token 量级说明
常用 emoji（😀🚀🎉）2~4 token/个UTF-8 多字节序列，部分被词表整体收录、部分按字节回退
组合 emoji（👨‍👩‍👧 零宽连接符）5+ token/个ZWJ 序列被拆成多个组件分别编码
零宽字符 / 控制字符1 token 或字节碎片不可见但占 token，还常导致缓存 key 不一致、日志显示异常
CJK 扩展区生僻字2~4 token/字超出基本区的汉字大多走字节回退
# Python：入库前清洗"看不见"的字符，统一规范化
import unicodedata

def clean_text(s: str) -> str:
    s = unicodedata.normalize("NFC", s)          # 统一码位形式
    s = "".join(
        ch for ch in s
        if unicodedata.category(ch) not in ("Cc", "Cf")  # 去控制/格式字符
    )
    return s

# 缓存 key 用规范化后的文本，否则 "café"（两种编码）会 miss 两次
稳妥做法：① 所有进入 Prompt 的文本先过 clean_text；② emoji 不是免费情绪表达，是 token 成本，产品文案里密集用 emoji 前先估算；③ 做国际化产品时，用各语言真实语料分别测 token 效率，再定定价和窗口策略。
模块 8

tiktoken 实战：预算管理三件套

下面这段是可直接进项目的"token 预算管理器"：计数、截断、成本估算，覆盖多轮对话最常见的三个需求。

# token_budget.py —— 最小可用的 token 预算管理
import tiktoken

class TokenBudget:
    def __init__(self, model: str = "gpt-4"):
        self.enc = tiktoken.encoding_for_model(model)

    def count(self, text: str) -> int:
        return len(self.enc.encode(text, disallowed_special=()))

    def fit(self, text: str, budget: int, keep: str = "tail") -> str:
        """把文本压进 budget 个 token。keep=head/tail/middle"""
        ids = self.enc.encode(text)
        if len(ids) <= budget:
            return text
        if keep == "head":
            ids = ids[:budget]
        elif keep == "tail":
            ids = ids[-budget:]
        else:  # middle：首尾各留一半
            half = budget // 2
            ids = ids[:half] + ids[-(budget - half):]
        return self.enc.decode(ids)

    def estimate_cost(self, prompt: str, completion: str,
                      price_in: float, price_out: float) -> float:
        """price 单位为 美元 / 1K token，以厂商实时价目为准"""
        p, c = self.count(prompt), self.count(completion)
        return (p * price_in + c * price_out) / 1000

# 用法
tb = TokenBudget("gpt-4")
system_prompt = tb.fit(long_doc, 6000, keep="head")   # 长文档留开头
user_input    = tb.fit(raw_input, 2000, keep="tail")  # 用户输入留最新

LangChain 等框架内置 token 计数回调，但底层还是调上面这些库，别重复造轮子
最终口径：本地计数用于事前预算和截断，API 返回的 usage 用于事后对账和计费。两者有毫厘级差异（消息结构包装 token），做成本报表时以 usage 为准，做截断时以本地计数为准（留 5%~10% 安全余量）。
模块 9

十个常见坑

1
用 len(text) 或字符数估算 token
中文一字一 token 上下浮动 50% 以上，数字和代码更是翻倍。必须用对应模型的 tokenizer 实测，或至少按"中文 1.5 token/字"估且留足余量。
2
用 text[:N] 按字符截断
把 UTF-8 多字节字符和 token 边界一起砍断，模型读到字节碎片后输出不可控。先 encode 再截 id 再 decode。
3
拿一个模型的 tokenizer 计数，发给另一个模型
词表不同，token 数能差 30%+。cl100k 的数不能直接当 Claude 或 Llama 的预算。每个模型用自己的 tokenizer。
4
忽略特殊 token 和消息结构的开销
每条消息的角色标记、模板包装、文档结束符都占 token。系统提示 + 工具定义动辄几千 token，预算表里必须单列。
5
tiktoken 编码含特殊 token 字面量的用户输入直接报错
enc.encode 默认禁止 <|endoftext|> 这类字面量，线上直接 500。用户输入先过滤/转义，或用 disallowed_special=() 显式放行。
6
长数字串、ID、哈希不预处理
10 位数字 = 4 token，40 位 UUID = 十几个 token，让模型做算术/比对时错误率飙升。考虑分段呈现或换用更短标识。
7
中英文成本估算错位
拿英文 0.75 词/token 的比率套中文，预算差一倍。中文常用字约 1 token/字，但次常用字、混排、emoji 全部超支，按真实语料测。
8
max_tokens 设太小，输出被静默截断
finish_reason=length 时 JSON/代码只剩一半，下游解析全线崩。生成结构化内容时 max_tokens 至少留预计输出的 2 倍。
9
只数输入不数输出，128k 窗口当 128k 输入用
窗口 = 输入 + 输出。塞满输入后模型一个字都写不了。预留输出额度是硬约束，不是优化项。
10
微调或换模型时 tokenizer 悄悄变了
换了 base 模型词表变了，历史缓存、prompt 模板、截断逻辑全部偏移。升级模型时把 tokenizer 当成破坏性变更来测试。
自测

六道题

1. 现代 LLM 普遍采用"字节级"（byte-level）词表，最大的好处是？
正确答案：任何文本可编码、无 OOV。基础词表只有 256 个字节符号，任何 Unicode 文本都能回退成字节碎片表示。代价是罕见字符会变成一串无意义 token。中文"1 token/字"不是字节级保证的，而是词表覆盖的结果。
2. cl100k_base 词表大约多大？
正确答案：100,277，用于 GPT-3.5-Turbo / GPT-4 系列。50,257 是 GPT-2 的 r50k_base；约 20 万是 GPT-4o 起的 o200k_base。词表越大通常多语言覆盖越好、中文越省 token。
3. 在 cl100k 中，"1234567890" 大约是几个 token？
正确答案：4 个。预切分规则把连续数字按最多 3 位一组切开（123/456/789/0）。这是长 ID、时间戳吃 token 的根源，也让模型直接做长数字算术更困难。
4. 要把一段中文严格限制在 4000 token 以内，正确做法是？
正确答案：先编码、按 token 数截 id、再解码。字符截断会砍断多字节字符产生乱码；按字节算（*3）既不准也会破坏边界。只有 tokenize → slice → detokenize 能保证落在合法 token 边界。
5. 用 tiktoken 编码一段用户输入，文本里含有字面量 "<|endoftext|>"，会发生什么？
正确答案：默认抛 ValueError。这是 tiktoken 的防呆设计，防止用户输入注入特殊 token 污染对话结构。处理用户文本要先过滤/转义，或显式用 disallowed_special=() / allowed_special 控制。
6. 模型的上下文窗口标称 128k，意味着？
正确答案：输入 + 输出共享同一个窗口。塞 120k 输入，输出最多剩 8k。多轮对话中历史消息还会逐轮累积占窗口，所以上下文管理（裁剪、摘要）是长对话应用的必修课，详见上下文工程篇。

BBPE字节级 BPE：基础符号是 256 个字节，无 OOV
WordPiece按语言模型似然增益做合并的变体，BERT 系采用

SentencePiece不依赖预分词的工具包，把空格也变成 token，对中文友好
