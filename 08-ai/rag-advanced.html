二十分钟学透 RAG 进阶

入门 RAG 是"切块 + 向量 + 检索 + 塞进提示词"。进阶 RAG 的战场在切分策略、混合检索、重排、查询理解和评测——效果差的系统，问题 80% 出在检索而不在生成。

模块 1

Pipeline 全链路

一条完整的 RAG 链路，离线建库 + 在线查询两段。每一段都有独立的故障模式和评测方法。

# ===== 离线：建库（Indexing） =====
原始文档(PDF/HTML/Word/MD)
   │  ① 解析：抽出正文 + 结构（标题层级、表格、页码）
   ▼
结构化文档块(document tree)
   │  ② 切分：按策略切成 chunk，保留元数据（来源、标题路径）
   ▼
chunk 列表 ──┬─▶ ③ 向量化：embedding 模型 → 稠密向量 ─▶ 向量索引
              └─▶ 关键词索引：BM25 / 倒排（不分词的中文先分词）

# ===== 在线：查询（Retrieval & Generation） =====
用户问题
   │  ④ 查询理解：改写 / 扩展 / HyDE / 多查询
   ▼
查询（可多个）
   │  ⑤ 检索：向量检索 + BM25 多路召回 ─▶ RRF 融合
   ▼
候选 chunk 集合（top 50~100）
   │  ⑥ 重排：cross-encoder 精排 ─▶ top 3~10
   ▼
   ┌───────────────┐
   │ ⑦ 上下文组装  │  长度预算：system + 历史 + 检索块 + 问题 ≤ 模型窗口
   └───────┬───────┘
           ▼
   生成答案（带引用编号）──▶ ⑧ 评测/观测：命中率、忠实度、延迟、成本
环节核心决策常见实现
① 解析表格、图片、页眉页脚怎么处理PDF: PyMuPDF/pdfplumber；结构化: Unstructured、MinerU 类工具
② 切分多大、按什么边界、重叠多少固定大小 / 递归 / 语义 / table-aware
③ 向量化选哪个模型、维度与成本BGE / GTE / OpenAI text-embedding 系列（以厂商文档为准）
⑤ 检索单路还是多路、怎么融合向量 + BM25 + RRF
⑥ 重排精排模型选型、延迟预算CrossEncoder（bge-reranker 系列）
⑦ 组装放几个 chunk、怎么排、带不带历史按相关性排序 + 编号 + 截断策略
架构决策点：链路越长效果越好，但延迟和复杂度也线性上升。务实路线：v1 做好切分 + 混合检索（不做重排）→ v2 加重排 → v3 加查询改写。每一步都用评测集量化收益，不做"感觉有提升"的优化。
模块 2

解析与切分策略

切分是 RAG 里影响最大、最容易被随意决定的环节。原则：一个 chunk 应该是一个语义自包含的单元。

三种切分策略对比

策略做法优劣
固定大小按字符/token 数硬切（如 512 token + 50 重叠）简单、快。但会从句子中间砍断，语义破碎；重叠只能部分缓解
结构感知按 Markdown 标题、HTML 标签、章节边界切保留文档结构，chunk 自带"标题路径"上下文。结构化文档的首选
语义切分按 embedding 相似度在句边界处断句聚类边界最自然，但慢（要先算向量）、参数敏感
table-aware表格整体作为一个 chunk；大表按行分组并携带表头表格被拆散 = 信息报废。含表格的文档必须单独处理表格
# LangChain 的递归切分（按分隔符优先级递归，示意）
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,          # 目标 chunk 大小（字符）
    chunk_overlap=80,        # 重叠，缓解跨块信息丢失；通常 10%~20%
    separators=["\n## ", "\n### ", "\n\n", "\n", "。", ""],
    # 优先按二级标题切，切不动再退到段落、句子、硬切
)
chunks = splitter.split_text(document_text)

# 表格处理：表格单独成 chunk，行分组时带上表头
# ┌──────────┬──────┐
# │ 产品 | 价格 │  ← 每个分片都重复这行表头
# ├──────────┼──────┤
# │ A      | 100  │  ← 分片1：A、B 两行
# │ B      | 200  │
# │ C      | 300  │  ← 分片2：C、D 两行 + 重复表头
# └──────────┴──────┘

chunk 大小怎么定

  • 不是越大越好，也不是越小越好。大 chunk 语义全但向量"主题被稀释"（一段话讲三件事，向量谁都像）；小 chunk 语义聚焦但缺上下文（"该产品支持退款"——哪个产品？）
  • 经验起点：中文 300~500 字/块，重叠 10%~20%；然后按评测集上的命中率调。没有放之四海皆准的参数
  • 元数据补偿：给小 chunk 补上"标题路径"和"文档摘要"再向量化，缓解缺上下文问题（检索时也能按元数据过滤）
  • 父子块（small-to-big）：检索用小 chunk（定位准），生成时把它的父块（更大范围）喂给模型。两全其美，代价是索引设计复杂一点
血泪教训：把 Markdown 文档按 512 字符硬切，标题"## 退款政策"留在了上一块末尾，下一块是"7 天内可退，运费自理"。用户问"退款政策"，检索到的 chunk 没有标题也没有主语——生成模型只能瞎猜。这就是"切分破坏语义"的典型现场。
模块 3

向量化与索引

决策要点
模型选型查询和文档必须用同一个模型（含相同的前缀/指令约定，部分模型对查询侧有特殊 prompt 前缀，以模型文档为准）。中文场景优先选中文语料训练的模型（如 BGE 系列），英文场景 MTEB 榜单可参考但别盲信
维度与量化维度越高语义越细但存储和计算越贵。百万级 chunk 可考虑 PQ/INT8 量化，十万级全量精度没压力
相似度余弦相似度是主流；注意归一化（多数模型输出已归一化，用内积 = 余弦）
元数据索引来源、标题路径、时间、权限标签必须入库。权限过滤靠元数据在检索层实现——"先检索再过滤"会导致 top-k 全是无权内容
更新策略文档变更的增量索引 vs 全量重建。chunk 粒度 + 内容哈希去重，删旧插新；向量库选型时确认支持按元数据删除
# 索引结构示意（记录长这样）

  "text": "退款需在签收后 7 天内申请，运费由买家承担……",
  "vector": [0.012, -0.034, ...],          # 与 text 同模型产出
  "metadata": {
    "source": "policy/refund.md",
    "title_path": "售后政策 > 退款",
    "doc_type": "policy",
    "visibility": ["public", "vip"],       # 权限标签
    "updated_at": "2026-10-01"
  }
}

# 检索时带过滤（伪代码）
results = vector_store.search(
    query_vec,
    top_k=50,
    filter={"visibility": {"$in": user_groups}}   # 权限前置到检索层
)
模型不匹配是静默杀手：索引用模型 A 建的，查询时用了模型 B——不报错，只是检索质量莫名其妙地差（两个向量空间的语言不通）。CI 里要固化"索引模型名"配置，升级 embedding 模型 = 全量重建索引 + 全量回归评测，不能只改一半。
模块 4

检索优化：混合检索与 RRF

向量检索抓"语义相似"，BM25 抓"关键词精确匹配"。两者失败模式互补，混合检索是性价比最高的一步优化。

召回方式擅长失败场景
纯向量同义改写、跨语言、概念相关专有名词、型号、错误码、缩写——"ERR_CONN_REFUSED"向量上离"连接被拒绝"并不近
纯 BM25关键词精确匹配、稀有词（ID、编号）同义替换、口语化提问完全失效
混合 + RRF两者并集，融合排序几乎无（除了复杂度和延迟）
# RRF（Reciprocal Rank Fusion）融合：只看排名不看分数
def rrf_fuse(rankings, k=60):
    """rankings: {检索器名: [doc_id, ...] 按相关度降序}"""
    scores = defaultdict(float)
    for docs in rankings.values():
        for rank, doc_id in enumerate(docs, start=1):
            scores[doc_id] += 1.0 / (k + rank)   # 排名第 1 加分最多，衰减平缓
    return sorted(scores.items(), key=lambda x: -x[1])

# 用法
vec_rank = [d.id for d in vector_search(q, top_k=50)]
bm25_rank = [d for d in bm25.get_top_n(q, corpus, n=50)]
fused = rrf_fuse({"vector": vec_rank, "bm25": bm25_rank}, k=60)

# 为什么 RRF 比"分数加权求和"好用：
# 1. 不依赖不同检索器分数尺度一致（余弦 0.8 和 BM25 12.3 没法直接加）
# 2. 只用排名，对头部结果友好、对尾部差距不敏感，鲁棒
# 3. k=60 是原论文的常用值，一般不需要调

多路召回（Multi-channel Recall）

  • 按内容类型分路：正文向量一路、表格一路、FAQ（问句对问句）一路——FAQ 用"问题"向量化而不是"答案"，匹配用户 query 更准
  • 按权限/业务域分路：每路带不同 metadata 过滤
  • 每路 top-k 放大（如各 50~100）再融合，融合后交给重排。直接每路只取 top-5 就融合，会丢掉大量候选
最小可用方案：向量 top-50 + BM25 top-50 → RRF 融合 → 取 top-20 进重排。这套组合不需要训练、不需要调参，对绝大多数中文知识库都是立竿见影的提升。
模块 5

重排与查询理解

Cross-Encoder 重排

双塔（bi-encoder）模型：文档和查询分别编码成向量，只能算相似度，看不到交互。Cross-Encoder 把"查询 + 文档"拼在一起过模型，直接输出相关度分数——精度高一个量级，但无法预计算，只能对候选集逐个推理，慢。

# CrossEncoder 重排（sentence-transformers，示意）
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-base")   # 选型以当前可用的中/英模型为准

pairs = [[query, chunk.text] for chunk in candidates]   # 候选来自混合召回 top-20
scores = reranker.predict(pairs)                    # 每条 0~1 相关度
ranked = sorted(zip(candidates, scores), key=lambda x: -x[1])
top_docs = [c for c, s in ranked[:5]]               # 精排后只取 top 5 进生成

# 延迟账：20 个候选 × 单次推理几 ms~几十 ms（取决于模型和硬件）= 几十到几百 ms
# 值得。检索阶段省下的 top-5 直接进生成，常把答案质量拉一个档
方案延迟精度适用
双塔向量（bi-encoder）ms 级中大规模初筛，索引可预计算
Cross-Encoder十~百 ms高候选集精排（20~100 条）
ColBERT（晚期交互）介于两者较高要精度又要速度的折中，实现复杂度高

查询理解三招

# ① 查询改写（Query Rewrite）：把口语/缺主语的问题改写成检索友好的形式
用户：那个退款要多久啊
改写：退款申请处理需要多长时间？退款到账时效
# 多轮对话里尤其重要：把"它多少钱"改写成"Pro 套餐多少钱"（先补全指代）

# ② HyDE（Hypothetical Document Embeddings）：
# 让模型先生成一个"假设答案"，用假设答案的向量去检索
# ——答案与答案在向量空间里比"问题与答案"更近
假设答案 = llm("请写一段可能回答该问题的文字，不需要准确：{question}")
query_vec = embed(假设答案)        # 用假设答案检索，而非原始问题

# ③ 多查询（Multi-Query）：一个问题生成多个角度的检索式
queries = llm("把这个问题改写成 3 个不同角度的检索查询：{question}")
all_results = concat([search(q) for q in queries])   # 各自召回后统一融合
HyDE 不是银弹：假设答案里的错误信息会把检索带偏（"生成错误答案 → 检索到错文档 → 生成更错的答案"）。事实型查询慎用；对"观点/解释型"问题效果更好。上任何查询改写都必须用评测集对比，主观感觉"变顺了"不算数。
模块 6

上下文组装、长度预算与引用

检索到的 top-k chunk 不是一股脑塞进去就行。组装策略直接影响生成质量。

长度预算分配

# 模型上下文窗口 8K token 的分配示意（按自己模型调整）
system 提示（规则、输出格式）          ~300 token   # 固定成本，尽量精简
对话历史（最近 N 轮，超出就摘要）      ~500 token
检索上下文（top-k chunk）              ~4000 token   # 主体，给足
用户问题                              ~50 token
生成预留                             ~800 token   # 别让输出被窗口截断
────────────────────────────────────────────
合计                                 ~5650 token，留足安全余量

# 原则：
# 1. 先减历史和 system，再减 chunk 数量；chunk 从相关性最低的开始砍
# 2. 超长文档： chunk 截断到句边界，别从单词中间砍
# 3. 预算要代码化：组装时按预算动态选 top-k，而不是写死 k=5

组装顺序与引用

  • 按相关性降序排列，最相关的放最后（靠近问题，利用模型对末尾的注意力优势）——这一点各家说法不一，以你自己评测集的结论为准
  • 每个 chunk 带编号 [1][2][3]，提示词要求"回答末尾用 [n] 标注来源"；前端把编号渲染成可点击链接，直达原文位置（精确到锚点）
  • 来源元数据进提示词（文档名、章节、更新时间），模型可以据此回答"这个信息来自哪里、可能过时"
  • 冲突处理：多个 chunk 说法不一致时，提示词明确要求"列出分歧"而不是自己选一个——这比让模型和稀泥可靠得多
# 组装后的提示词骨架
你是知识库助手。严格基于 <context></context> 回答，禁止使用外部知识。

<context>
[1] （来源：售后政策.md / 退款规则 / 更新于 2026-09）
    退款需在签收后 7 天内申请……
[2] （来源：会员权益.pdf / 第 3 页 / 更新于 2026-08）
    VIP 会员退款时效延长至 15 天……
</context>

<question>VIP 用户退款期限是多久？</question>

<rules>
回答末尾标注引用的资料编号；资料间冲突时列出分歧；资料未覆盖输出"资料未覆盖"。
</rules>
模块 7

评测：检索与生成分开看

RAG 的评测必须分层，端到端指标掩盖问题位置。检索指标回答"找没找到"，生成指标回答"答得好不好"。

指标定义合格线参考
Recall@K正确答案在 top-K 检索结果中的比例RAG 场景 K=5 时通常要求 ≥ 90%
MRR第一个正确答案排名的倒数均值，衡量"排得靠前"越高越好，关注长尾
nDCG@K考虑多相关文档分级位置的排序质量精排优化的直接观测指标
忠实度
Faithfulness		答案中的陈述能被检索内容支持的比例（反幻觉核心指标）≥ 95%，低于此先查检索再查提示词
答案相关性
Answer Relevancy		答案是否切题、不啰嗦结合人工抽检
延迟 / 成本p95 延迟、单次 token 成本检索 + 重排通常应 < 1s
# 检索评测：黄金问答对（问题 → 已知应命中的 chunk 或文档）
# eval_set.jsonl 每行：{"q": "...", "gold_doc_ids": ["doc42"], "gold_answer": "..."}

def evaluate_retrieval(eval_set, retrieve_fn, k=5):
    hits = 0
    for item in eval_set:
        results = retrieve_fn(item["q"], top_k=k)
        if any(r.doc_id in item["gold_doc_ids"] for r in results):
            hits += 1
    return {"recall@k": hits / len(eval_set)}

# 判读方法：
# Recall 低 → 问题在切分/embedding/索引，别动生成
# Recall 高但答案差 → 问题在重排/组装/提示词/模型
# 忠实度低 → 检索内容没约束住模型，或检索到的内容本身冲突/过时
评测集从哪来：① 真实用户日志里采样（最有价值）；② 业务专家写 30~50 条黄金问答对（覆盖高频+易错）；③ 用"问题 → 文档"的现成结构反推。冷启动 50 条足够开始，之后随数据飞轮扩充（详见《AI 应用评估体系》）。
模块 8

十个常见坑

1
切分破坏语义
按固定字符数硬切，标题和主语被切断，chunk 离开上下文就无法理解。按结构边界切；给小 chunk 补标题路径；表格必须 table-aware 处理。
2
embedding 模型不匹配
索库用一个模型、查询用另一个；或升级模型只改了查询侧没重建索引。不报错，效果莫名差。索引模型名进配置固化，换模型 = 全量重建 + 回归。
3
只评测端到端
"答案不好"是个无法行动的信号。不拆分层看：Recall@5 掉了是检索问题，忠实度掉了是生成问题。没有分层评测，优化就是盲人摸象。
4
纯向量检索
错误码、型号、专有名词的查询向量检索全线崩溃。上 BM25 混合 + RRF，这是零训练成本的最大单项提升。
5
权限在检索后过滤
先向量检索 top-10 再过滤权限，用户看到的经常不足 10 条甚至为空；更糟的是过滤逻辑漏了造成越权。权限标签必须作为检索条件（metadata filter）前置。
6
上下文无限膨胀
top-20 chunk 全塞进提示词，token 成本爆炸、延迟劣化、噪声稀释关键信息。做长度预算，动态选 k；重排后只取 top-3~5 进生成。
7
表格被拆散
Markdown 表格按字符切断，表头和数据分家，检索到半张表。表格整块成 chunk，大表按行分组且每组带表头。
8
多轮对话不带指代消解
第二轮问"它多少钱"，检索的是"它"的向量，结果全文乱飘。查询改写时先把指代补全（结合历史），再进检索。
9
无引用，答案无法溯源
用户不敢信、出争议无法仲裁、幻觉无法定位。chunk 编号 + 来源元数据 + 提示词强制引用标注，前端渲染可点击溯源。
10
文档更新了索引没更新
知识库改了三轮政策，答案还在引用旧版。索引要有增量更新机制（内容哈希检测变更），知识库变更触发重建受影响的 chunk，评测集定期用最新文档校准。
自测

六道题

1. 为什么混合检索（向量 + BM25 + RRF）通常优于纯向量检索？
正确答案：失败模式互补。向量检索对同义改写强，但对"ERR_CONN_REFUSED"这类精确 token 反而弱（它语义上离"连接被拒绝"并不近）；BM25 正好相反。RRF 用排名融合，回避了两种分数尺度不可比的问题。
2. RRF（Reciprocal Rank Fusion）相比"向量分数加权求和"的核心优势是？
正确答案：只用排名、不依赖分数尺度。余弦相似度 0.82 和 BM25 分数 12.3 没法直接相加；RRF 的 1/(k+rank) 形式让任何两个榜单都能融合，k=60 是原论文常用值，基本不用调。
3. RAG 系统 Recall@5 很高，但生成的答案经常幻觉。问题最可能出在哪？
正确答案：生成侧。Recall 高说明内容找到了，答案还错 = 重排没把最相关的排前面、组装时塞了噪声、或提示词没有严格约束"只基于资料回答"。判读方法：Recall 低修检索，Recall 高答案差修生成。
4. 关于 chunk 切分，哪种做法是对的？
正确答案：结构感知 + table-aware + 元数据补偿。硬切会从句子中间砍断；大 chunk 会稀释向量主题（一段讲三件事，跟谁都不像）。300~500 字按评测调，检索用小 chunk、生成用父子块是成熟折中。
5. 企业知识库按权限分级（公开/内部/机密），正确的做法是？
正确答案：权限前置到检索层。后过滤会导致有效结果不足（top-10 过滤后剩 2 条），且过滤逻辑一旦漏判就是越权事故。多索引方案在权限维度少时也可行，但维护成本随权限类型线性增长。
6. 关于 Cross-Encoder 重排，哪个说法是对的？
正确答案：拼接推理、精度高、不可预计算。这正是它只能做重排的原因：混合召回 top-20~50 后逐对打分，取 top-3~5 进生成。延迟几十到几百毫秒，通常值得。

RRF 最小实现

# 十行代码的混合检索融合
def rrf_fuse(rankings, k=60):
    scores = defaultdict(float)
    for docs in rankings.values():
        for rank, doc_id in enumerate(docs, 1):
            scores[doc_id] += 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda x: -x[1])

fused = rrf_fuse({
    "vector": [d.id for d in vector_search(q, 50)],
    "bm25": bm25_top50(q),
})
