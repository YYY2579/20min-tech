一个必须先建立的认知：AI 服务的运维和普通 Web 服务的运维，底层模型完全不同。普通服务是"无状态 + CPU 便宜 + 请求耗时稳定"；AI 服务是"有状态资产 + GPU 昂贵 + 请求耗时方差极大"。很多传统运维经验在这里会失效，甚至起反作用。这份文档的重点就是讲清楚哪些经验失效了、为什么、怎么办。
模块 1

AI 服务和普通服务的本质差异

先把差异看清楚，后面所有的设计决策都是从这里推导出来的。

维度普通 Web 服务AI 推理服务
计算资源CPU 便宜、易得、可超卖GPU 稀缺且昂贵。一张 A100 月租可能几千到上万，且不一定买得到
资源约束内存不够可以加，可以 swap显存是硬约束，放不下就是跑不起来，没有 swap 可言
请求耗时相对稳定，P99/P50 差 2~5 倍差异极大且不可预测。同一接口可能 200ms 也可能 30s，取决于输出长度
交互模型一问一答，请求-响应完整返回流式响应（SSE，Server-Sent Events）改变了整个链路，包括网关、超时、重试
服务本体无状态代码，随时重启、随时扩容模型是"有状态"的资产。几十 GB 的文件，加载要几分钟，重启成本极高
成本计量按 CPU 小时或请求数按 Token 数或 GPU 小时，两者差异巨大，选错成本模型能差 10 倍

差异一：GPU 是稀缺且昂贵的资源

这意味着资源利用率直接等于钱。CPU 服务让机器跑到 10% 利用率可能无所谓，但一张 GPU 空转 90% 就是在烧钱。所以 AI 服务的核心运维目标不是"稳定"这么简单，而是在高利用率下保持稳定。这两个目标天然冲突 —— 利用率越高，排队越长，延迟越差。

差异二：显存是硬约束

CPU 服务内存不够，可以加内存条、可以 swap、可以分批处理。GPU 显存不够，就是直接报 OOM（Out Of Memory），服务起不来。而且显存占用不是固定的 —— 它会随并发数和上下文长度动态增长（KV Cache，键值缓存，后面模块 3 详细讲）。

最典型的翻车场景：压测时用短 Prompt（比如 50 token）测出来能扛 100 并发，上线后真实用户 Prompt 是 2000 token，显存瞬间爆掉，服务 OOM 崩溃。
根因：压测的输入分布和真实分布不一致。显存占用和"输入+输出的总 token 数 × 并发数"成正比，短 Prompt 压测严重低估了真实需求。

差异三：请求耗时差异极大且不可预测

普通接口耗时基本稳定，AI 推理的耗时和输出 token 数线性相关。用户问"1+1 等于几"，输出 2 个 token，几百毫秒返回；用户让它"写一篇 2000 字的文章"，输出 3000 个 token，要几十秒。同一个接口，耗时能差 100 倍。

这直接导致三个后果：

  • 超时时间没法统一设。设 5 秒会把长输出全砍掉，设 60 秒会让故障请求占着连接不放
  • 按请求数限流是错的。一个请求可能只花 10 个 token，也可能花 4000 个 token，成本差 400 倍（见模块 7）
  • P99 延迟会非常难看。因为长尾请求天然存在，必须接受"总有一批请求很慢"

差异四：流式响应改变交互模型

大模型是逐个 token 生成的。如果等全部生成完再返回，用户要盯着空屏幕等十几秒，体验极差。所以业界标准做法是 SSE 流式返回：生成一个 token 就推一个。

# 流式响应的数据格式（SSE）
data: {"choices":[{"delta":{"content":"你"}}]}
data: {"choices":[{"delta":{"content":"好"}}]}
data: {"choices":[{"delta":{"content":"，"}}]}
...
data: [DONE]

# 非流式响应：等全部生成完，一次性返回一个完整 JSON

流式对运维的影响被严重低估：

  • 网关超时必须按"整个流"算。Nginx 的 proxy_read_timeout 如果设 60 秒，长输出会被中途掐断
  • 反向代理必须关掉缓冲。Nginx 默认会缓冲响应，流式会被攒成一坨再发，流式就白做了，要配 proxy_buffering off
  • 重试变得危险。非流式请求失败可以安全重试；流式请求中途断开重试，会重复计费、可能重复生成
  • 负载均衡要支持长连接。一个流可能持续几十秒，连接不能轻易被断

差异五：模型是"有状态"的资产，不是无状态代码

这是和微服务思维冲突最大的一点。代码是无状态的，改一行重新发布就行，秒级完成。模型不是：

  • 一个 7B 模型 FP16 是 14GB，70B 模型是 140GB。这是个巨大的文件
  • 加载到显存需要几分钟（从磁盘读 + 初始化）
  • 模型版本切换不是"改配置重启"，而是加载一份新的几十 GB 显存占用，旧的要先卸载
  • 所以"滚动发布"这种在 K8s 里理所当然的操作，在 GPU 节点上根本没有足够显存做蓝绿
推论：模型加载时间长 → 扩容慢 → 突发流量扛不住。这是 AI 服务弹性的核心矛盾，模块 8 专门讲。简单说：不能指望"流量来了再扩"，必须提前预热或用排队机制扛住。
模块 2

推理性能指标：先建立度量体系

你没法优化你测不出来的东西。AI 服务的指标和普通服务完全不同，必须先建立正确的度量体系。

五个核心指标

指标含义为什么重要
TTFT
首 Token 延迟		Time To First Token，从发请求到收到第一个 token 的时间决定"用户感觉快不快"。用户体感的是第一个字什么时候出现，不是全部生成完。包含排队 + 预填充（prefill）时间
TPOT
每 Token 输出时间		Time Per Output Token，生成每个 token 的平均耗时决定"文字刷得快不快"。TPOT × 输出长度 ≈ 生成耗时。人眼阅读约 5~10 token/秒，TPOT < 100ms 就很流畅
吞吐
tokens/s		整个系统每秒能产出多少 token决定"一张卡能服务多少人"。直接换算成成本：吞吐越高，单 token 成本越低
并发数同时处理的请求数并发不是越高越好。超过某个点，吞吐不再涨、延迟暴涨（见下面矛盾分析）
显存占用GPU 显存用了多少 / 总共多少硬约束。接近 100% 就意味着 OOM 风险。要区分"权重占用"和"KV Cache 占用"

为什么延迟和吞吐是矛盾的

这是 AI 服务最核心的权衡，必须理解透彻。推理分两个阶段：

阶段做什么计算特性
Prefill
预填充		把你的 Prompt（输入）全部读一遍，算出 KV Cache计算密集。GPU 算力吃满，一次能处理很多 token，效率高。决定 TTFT
Decode
解码		一个一个地生成输出 token访存密集。每生成一个 token 都要把整个模型权重读一遍，GPU 算力大量闲置。决定 TPOT
关键洞察：Decode 阶段 GPU 的算力是浪费的。因为生成每个 token 都要把几十 GB 的权重从显存读进计算单元，但只算一个 token 的矩阵乘法。瓶颈在显存带宽，不在算力。
所以：把多个请求的 Decode 阶段拼成一批，一次读权重算多个请求的 token —— 权重只读一遍，算力利用率上去了，总吞吐大幅提升。这就是批处理（batching）的本质。代价是：请求要等其他人一起凑批，单请求延迟变高。

结论：延迟和吞吐是跷跷板。想降延迟就得减少批大小（甚至单请求），吞吐就低、成本就高；想提吞吐就得加大批大小，延迟就上去。没有免费的午餐，只有根据业务目标做取舍。

批处理如何影响这两个指标

批大小吞吐单请求延迟适用场景
1（单请求）低（GPU 浪费）最低对延迟极敏感的交互式场景，且流量小
8~32中高中等大多数在线对话场景的甜点区
64~256最高高（排队久）离线批处理、文档摘要、数据清洗等不在乎单请求延迟的任务
实用的取舍口诀：在线对话看 TTFT（用户等第一个字），批处理看吞吐（总时间）。
在线场景要把 TTFT 压到 1 秒内、TPOT 压到 100ms 内；离线场景可以容忍 TTFT 几秒甚至几十秒，换取 3~5 倍的吞吐。

这些指标怎么监控

好消息是：主流推理框架（vLLM、TGI）都内置了 Prometheus 指标，不用自己埋点。

# vLLM 启动时暴露 /metrics 端点
vllm serve Qwen/Qwen2.5-7B-Instruct --port 8000

# 抓取到的关键指标（Prometheus 格式）
vllm:time_to_first_token_seconds        # TTFT 直方图
vllm:time_per_output_token_seconds       # TPOT 直方图
vllm:num_requests_running                # 正在处理的请求数
vllm:num_requests_waiting                # 排队中的请求数（关键！）
vllm:gpu_cache_usage_perc                # KV Cache 显存使用率
vllm:gpu_memory_utilization              # 整体显存利用率
vllm:request_prompt_tokens               # 输入 token 数分布
vllm:request_generation_tokens           # 输出 token 数分布
监控重点排序：① num_requests_waiting（排队长度，超过阈值说明容量不够，是最灵敏的报警指标）；② TTFT 的 P95/P99；③ gpu_cache_usage_perc（KV Cache 使用率，接近 100% 会开始抢占/拒绝请求）；④ 输出 token 数分布（用来做容量规划，比 QPS 准得多）。
模块 3

GPU 基础与显存估算

显存估算是 AI 运维的"九九乘法表"，必须会算。算不清就买不对卡、配不对并发。

显存被什么占用

占用项是否固定说明
模型权重固定模型参数本身占的空间。由参数量和精度决定，是最大的一块
KV Cache动态缓存每个请求的注意力键值，随并发数和上下文长度线性增长。是 OOM 的主要元凶
激活值 / 中间结果半固定推理时的中间张量，通常不大（训练时才是大头）
框架开销固定CUDA context、通信缓冲（张量并行时）、框架本身的显存池。通常预留 1~2GB

权重估算：参数量 × 精度字节数

公式极其简单：权重显存 ≈ 参数量 × 每个参数占的字节数。

精度每参数字节说明
FP324 字节训练用。推理几乎不用，太占显存
FP16 / BF162 字节推理默认精度。精度基本无损
INT81 字节量化到 8 位，显存减半，精度损失小（通常 < 1%）
INT40.5 字节量化到 4 位，显存再减半，精度有可感知损失
# 具体计算示例

7B 模型
  FP16:  7e9 × 2 = 14 GB
  INT8:  7e9 × 1 = 7 GB
  INT4:  7e9 × 0.5 = 3.5 GB

13B 模型
  FP16:  13e9 × 2 = 26 GB
  INT8:  13e9 × 1 = 13 GB
  INT4:  13e9 × 0.5 = 6.5 GB

70B 模型
  FP16:  70e9 × 2 = 140 GB   # 一张 A100 80G 都放不下，必须多卡
  INT8:  70e9 × 1 = 70 GB    # 勉强塞进一张 80G 卡
  INT4:  70e9 × 0.5 = 35 GB  # 一张 48G 卡可以

# 常见 GPU 显存：V100 32G / A100 40G or 80G / H100 80G
# A10 24G / RTX 4090 24G / L40S 48G
注意：这只是权重。算完权重后，还要留 KV Cache 的空间。70B INT4 是 35GB，放在 48GB 卡上，只剩 13GB 给 KV Cache 和框架开销 —— 并发数会很低。估算时必须两项一起算。

KV Cache 估算：真正决定并发数的东西

KV Cache 是 Transformer 推理时缓存的注意力键值对，用来避免重复计算历史 token。它随上下文长度和并发数线性增长，是显存估算里最容易被忽略、也最容易导致 OOM 的部分。

单个 token 的 KV Cache 大小公式：

# 单 token KV Cache 字节数
= 2 × 层数 × KV 头数 × 头维度 × 字节数
  ↑ K 和 V 两份    ↑ 注意是 KV 头数，不是 Q 头数（GQA 会少很多）

# 以 Llama 3 8B 为例
层数 = 32，Q 头数 = 32，KV 头数 = 8（GQA），头维度 = 128，FP16 = 2 字节
单 token = 2 × 32 × 8 × 128 × 2 = 131072 字节 = 128 KB / token

# 那么：
一个 4096 token 的请求  = 128KB × 4096 = 512 MB
16 个并发 × 4096 token  = 8 GB
32 个并发 × 8192 token  = 32 GB   # 注意这里翻了 4 倍！
这里藏着 AI 运维最大的坑：上下文长度翻倍，KV Cache 也翻倍；并发翻倍，再翻一倍。两个维度是乘法的。
所以 8B 模型权重才 16GB，但如果你允许 32K 上下文 × 32 并发，KV Cache 能到 128GB —— 远超模型权重本身。
实践建议：① 一定要限制 max-model-len（最大上下文长度），别用模型理论最大值；② 监控 gpu_cache_usage_perc；③ 容量规划按"峰值并发 × 典型上下文长度"算，别按平均值算。

为什么 GQA 很重要

老模型（如 Llama 2）用的是 MHA（多头注意力），KV 头数 = Q 头数（比如都是 32），KV Cache 会大 4 倍。新模型普遍用 GQA（Grouped Query Attention，分组查询注意力，多个 Q 头共享一组 KV 头），KV 头数降到 8 个，KV Cache 直接小 4 倍。选模型时这也是个考量点 —— 同样参数量，GQA 的模型能撑更高并发。

总显存需求汇总表

模型精度权重+ KV Cache（16 并发 × 4K ctx）建议显卡
7BFP1614 GB约 8 GB单张 24G（如 4090/A10）
7BINT43.5 GB约 8 GB单张 16G 就够
13BFP1626 GB约 12 GB单张 40G（A100）
70BINT435 GB约 20 GB单张 80G，或 2×48G
70BFP16140 GB约 20 GB4×80G 起步（张量并行）
一句话记住：显存 = 权重（参数量 × 精度字节）+ KV Cache（单 token 大小 × 上下文长度 × 并发数）+ 框架开销（1~2GB）。权重是死的，KV Cache 是活的，OOM 几乎都是 KV Cache 引起的。
模块 4

三种部署路线对比

这是每个团队都会面对的第一个决策：自己买卡跑，还是调 API？答案不是绝对的，取决于你的场景。

维度云厂商 API自建推理服务混合方案
成本模型按 token 计费，用多少付多少按 GPU 时长计费，闲置也花钱核心用自建，峰值溢出到 API
起步成本几乎为零，注册就能用高（买卡/租卡 + 搭建）中
延迟受网络和对方负载影响，不可控可控，可以优化到极致自建部分可控
数据合规数据出你的边界，敏感数据慎用数据完全在内部，合规无忧敏感数据走自建
可控性模型版本、参数、超时都受制于人完全可控，可换模型、可调参数高
运维复杂度低，对方负责高，GPU 调度、显存、弹性都要自己搞最高（两套都要维护）
弹性对方负责，通常很好差，模型加载慢，扩容要几分钟靠 API 兜底弹性
适合谁小团队、快速验证、流量波动大大流量、强合规、要深度优化有一定流量且要合规

成本交叉点：什么时候自建开始划算

自建不是天然便宜。GPU 租用成本是固定的（不管用不用都在烧钱），API 是变动的（用多少付多少）。所以存在一个流量交叉点：低于它用 API 划算，高于它自建划算。

# 粗算一下（数字仅为示例，实际按你拿到的价格填）

API 路线：
  假设 ¥1 / 百万 token（输入），¥2 / 百万 token（输出）
  日均 5000 万 token（输入输出各半）→ 约 ¥75/天

自建路线：
  一张 A10（24G，能跑 7B FP16）云上约 ¥10/小时
  → ¥240/天（不管用不用，24 小时都在烧）

# 结论：这个量级下，API 便宜 3 倍多，自建是亏的
# 只有当 token 量涨到几亿/天，或者有合规硬要求时，自建才开始划算
别忽略隐性成本。自建不只是卡钱：
① 人力 —— 要有人懂 vLLM、会调显存、会排 GPU 故障，这是稀缺技能；
② GPU 运维复杂度 —— 驱动版本、CUDA 版本、节点故障、多卡通信，坑极多；
③ 利用率风险 —— 如果流量波动大，夜里卡空转，实际单 token 成本可能比 API 还高。

决策树（按顺序判断）

有数据合规硬要求吗？（数据不能出内网）→ 有，直接自建或私有化部署，别再纠结成本。
是快速验证阶段吗？（还没确定产品形态）→ 是，用 API。这个阶段优化成本毫无意义，速度才是第一位。
日均 token 量算过吗？→ 没算过就先算，然后和"GPU 时长成本"对比。低于交叉点用 API。
对延迟有极致要求吗？（比如要 < 200ms TTFT）→ 是，自建（API 的网络和排队延迟不可控）。
需要微调/自定义模型吗？→ 是，必须自建（API 只提供固定模型）。
以上都不满足？→ 用 API。把精力放在业务上，等规模到了再自建。
最务实的建议：大多数团队应该从 API 开始，把应用层做扎实（Prompt 工程、缓存、路由、降级），等 token 量上来、成本痛点明确之后，再考虑把"高频、可预测"的那部分流量迁到自建。这个迁移过程里，你的应用层抽象要能同时接 API 和自建（统一 OpenAI 兼容接口），否则迁移会非常痛。
模块 5

推理优化手段

这些是推理框架（vLLM / TGI）内部做的事。你不需要自己实现，但必须理解它们，才能知道为什么有些配置有用、有些是玄学。

连续批处理 Continuous Batching

传统批处理（静态批处理）是"凑够一批一起跑，跑完这批再跑下一批"。问题是：一个批里有长有短，短的生成完了要等长的，GPU 闲置。而且新请求必须等当前批全部结束才能进来。

连续批处理（也叫迭代级调度）改成：每个 token 生成步骤都可以重新组批。短请求一生成完就退出、释放显存，新请求立刻补进来。GPU 几乎不闲置，吞吐能提升 2~10 倍。

这是 vLLM / TGI 相比裸 HuggingFace generate() 吞吐高一个数量级的核心原因。理解了它，你就明白为什么"用 transformers 库直接写个 FastAPI 服务"在生产上是不可接受的。

PagedAttention：分页显存管理

KV Cache 传统上是"给每个请求预分配一段连续显存，按最大长度预留"。问题：实际用不到那么长，浪费巨大（实测浪费 60%~80%）。

PagedAttention（vLLM 提出的技术）借鉴操作系统的虚拟内存分页思想：把 KV Cache 切成固定大小的"页"（block），按需分配、不要求连续。显存浪费降到 4% 以下，同样的显存能撑更多并发。

技术解决的问题效果
连续批处理GPU 因等待长请求而闲置吞吐提升 2~10 倍
PagedAttentionKV Cache 预分配浪费显存显存浪费从 60%+ 降到 < 4%，并发数大增
前缀缓存 Prefix Caching多个请求有相同的 System Prompt，重复计算相同前缀只算一次，TTFT 大幅下降
量化权重和 KV Cache 太占显存INT8/INT4 显存减半，吞吐略升，精度有损
投机解码 Speculative DecodingDecode 阶段访存密集、算力闲置用小模型"猜"多个 token，大模型一次验证，延迟降 1.5~2 倍

前缀缓存：最容易被忽视的免费优化

如果你的应用有一个很长的 System Prompt（比如 2000 token 的角色设定），而每个请求都带这个前缀，那么每个请求都要重复计算这 2000 个 token 的 KV。前缀缓存让这些重复部分只算一次。

# vLLM 开启前缀缓存（默认开启）
vllm serve Qwen/Qwen2.5-7B-Instruct --enable-prefix-caching

# 设计原则：把固定的 System Prompt 放最前面，可变内容放最后
✓ 好的 Prompt 结构（前缀命中率高）：
[固定角色设定 2000 token] + [固定格式要求] + [本次用户输入]

✗ 差的 Prompt 结构（前缀命中率低）：
[本次用户输入] + [固定角色设定]   # 前缀每次都不一样，缓存全失效
这是一个纯工程收益：不改模型、不改硬件，只调整 Prompt 结构（固定内容前置），就能显著降低 TTFT 和算力消耗。云厂商 API 也普遍对"缓存命中的输入 token"给折扣（比如 1/10 价格），所以这个优化在 API 路线下同样省钱。

量化的精度损失：不能只看显存

精度显存精度损失建议
FP16100%基准有显存就用这个，最稳
INT850%通常 < 1%，多数任务无感性价比最高，优先考虑
INT425%1%~5%，复杂推理/代码任务可能明显下降显存极度受限时用，务必做效果评测
INT4 激进量化< 25%可能显著退化，出现胡言乱语不建议生产使用
量化不是免费的午餐，而且损失是"任务相关"的。同样的 INT4 模型，做简单分类可能毫无影响，做数学推理或代码生成可能明显变差。
铁律：上线前必须用你的真实评测集跑一遍量化前后对比，不能只看"能跑起来"。很多团队省了这一步，上线后发现回答质量下降，回头找原因找了很久。

模块 6

成本控制

AI 服务的成本是最容易失控的部分 —— 因为它按 token 计费，而 token 量完全由用户输入和模型输出决定，稍不注意就是指数级增长。

两种成本模型

模型计费方式成本驱动因素
按 Token 计费
（API 路线）		输入 token + 输出 token 分别计价用量。用多少付多少，闲置不花钱。但用量失控时账单失控
按 GPU 时长计费
（自建路线）		按卡 × 小时利用率。利用率低 = 单位 token 成本高。闲置是最大浪费
注意输出 token 通常比输入贵 2~4 倍。因为 Decode 阶段比 Prefill 慢得多（模块 2 讲过）。所以控制输出长度比控制输入长度更省钱。一条 3000 字的回答，输出成本可能比它的输入高好几倍。

六个降本手段（按性价比排序）

1. 限制输出长度
给 max_tokens 设合理上限。默认不设 = 允许模型无限输出 = 成本无上限。这是最简单也最有效的措施。
2. Prompt 缓存
固定 System Prompt 前置，命中缓存后输入 token 可打折（部分厂商 1/10 价格）。零成本优化。
3. 模型分级路由
简单问题（分类、抽取、闲聊）用小模型，复杂推理才用大模型。成本能降一个数量级。
4. 结果缓存
相同（或相似）的问题直接返回缓存答案，不调模型。适合 FAQ、固定查询场景
5. 精简 Prompt
删掉冗余的 few-shot 示例、重复的上下文。输入 token 省下来是真金白银
6. 预算熔断
设每日/每用户 token 配额，超了直接拒绝或降级。防止账单爆炸的最后防线

模型分级路由：最被低估的降本手段

很多团队用最大的模型处理所有请求，包括"你好""谢谢"这种。这是巨大的浪费。

# 简单的分级路由策略（伪代码）
def route(prompt, user_tier):
    # 规则一：长度 + 关键词的简单分类
    if is_simple(prompt):          # 短问题、分类、抽取
        return small_model           # 小模型，便宜 10 倍
    if needs_reasoning(prompt):     # 数学、代码、多步推理
        return large_model           # 大模型
    if user_tier == "free":
        return small_model
    return medium_model

# 更高级：用小模型做"路由器"，判断该用哪个模型
# 但要注意：路由本身也有成本，别路由一次比省下的还贵
收益测算：假设 70% 的请求是简单问题，小模型成本是大模型的 1/10。那么分级路由后，成本变成 0.7 × 0.1 + 0.3 × 1 = 0.37，直接省 63%。这是纯工程手段，不需要任何模型改动。

预算上限与熔断

成本控制最后一道防线：硬性预算上限。没有它，一个 bug（比如死循环调用）、一次攻击、或一个用户刷量，就能让你一天的账单爆炸。

# 三层配额设计

第一层：单请求限制
  max_tokens = 2048           # 单次输出上限
  max_input_tokens = 8000     # 单次输入上限（超长直接截断或拒绝）

第二层：单用户配额
  每用户每天 100 万 token
  超了 → 降级到小模型，或提示"今日额度已用完"

第三层：全局熔断
  全系统每天 10 亿 token
  达到 90% → 告警 + 自动降级（全部走小模型）
  达到 100% → 熔断，只服务白名单用户
配额要按 token 算，不是按请求数。按请求数限流会被绕过：用户把 10 个请求合并成 1 个超长请求，请求数没变但成本涨 10 倍。必须统计每个用户的输入 + 输出 token 总量。这也呼应了模块 7 的"限流该按 token 配额"。
模块 7

可观测性与限流

AI 服务的监控和限流，都因为"请求成本差异极大"这个特性，和传统方案不一样。

该监控什么

指标健康范围（参考）异常意味着
TTFT P95< 1~2 秒排队严重，或 Prefill 太慢（Prompt 太长），容量不足
TPOT P95< 100~150 ms批太大、GPU 打满，或模型太大卡不够
Token 吞吐按你的硬件基准吞吐下降说明 GPU 有问题或批处理效率降低
显存使用率< 90%接近 100% 会开始抢占/拒绝请求，很快 OOM
排队长度接近 0最灵敏的容量预警。持续 > 0 说明请求进来得比处理得快
失败率 / 超时率< 0.1%OOM、上游故障、或超时配置不合理
输出 token 数分布业务相关分布右移说明用户在用更长输出，成本会上升
传统指标在这里不够用：QPS 在 AI 服务里意义不大 —— 10 QPS 的短请求可能很轻松，1 QPS 的超长请求就能压垮服务。必须用 token 维度的指标（token/s、平均输入/输出 token 数）来做容量判断。

为什么传统限流不适用

传统限流是"每秒最多 N 个请求"（QPS 限流）。在 AI 服务里这会出大问题：

# 场景：限流设为 100 QPS

情况 A：100 个请求，每个输入 20 token、输出 10 token
  总 token = 3000 token/s     → 轻松扛住

情况 B：100 个请求，每个输入 4000 token、输出 2000 token
  总 token = 600,000 token/s  → GPU 直接爆炸

# 同样是 100 QPS，资源消耗差了 200 倍！
# 按 QPS 限流 = 要么平时浪费额度，要么高峰期拦不住

正确做法：按 token 配额限流，而且要在多个层面同时限制：

限制类型含义目的
并发请求数上限同时在处理的请求数不超过 N保护显存（并发数直接决定 KV Cache 占用）
输入长度上限单个请求的输入 token 不超过 N防止超长 Prompt 拖慢 Prefill、占满 KV Cache
输出长度上限单个请求的输出 token 不超过 N防止成本失控、防止长输出占着 GPU
token 速率配额每用户/每应用每秒或每天的 token 总量公平分配、成本控制
一句话：把"按请求数限流"换成"按 token 预算限流 + 按并发数限流"。并发数保护硬件（显存），token 预算保护钱包。两者缺一不可。

降级策略

AI 服务的依赖链比普通服务更脆弱（可能依赖多个 API 供应商 + 自建集群 + 向量库），所以降级策略是刚需。

故障场景降级策略
大模型超时/故障降级到小模型（质量下降但可用）；或返回"服务繁忙，请稍后"
API 供应商故障切换到备用供应商（要求应用层抽象成统一接口，否则切不动）
GPU 集群 OOM降低最大并发、缩短最大上下文、拒绝新请求并排队
成本超预算全局降级到小模型，或只服务白名单
向量库/检索故障降级为"不带检索直接回答"（RAG 场景），或返回缓存答案
最常见的架构缺陷：整个系统只依赖一家 API 供应商，且没有降级路径。供应商一抖，全站不可用。
解法：① 应用层做统一的 LLM 抽象层（比如都走 OpenAI 兼容格式），换供应商只改配置；② 配置至少一个备用供应商，主备自动切换；③ 关键路径准备"无 AI"的兜底（比如返回预置话术）。不要假设 AI 服务永远可用。
模块 8

部署形态与弹性

这是 AI 运维里最"硬核"的部分，也是和传统运维经验冲突最大的部分。

GPU 节点调度

在 K8s 里调度 GPU，和调度 CPU 完全不同：

  • GPU 是不可分割的整数资源。不像 CPU 可以给 0.5 核，GPU 通常要么独占一张卡，要么用 MIG（Multi-Instance GPU，把一张卡切成多个小实例）或时间片共享
  • 节点数量少、单节点价值高。一个集群可能就几台 GPU 机器，一台挂了影响很大
  • 需要 GPU 感知的调度。要靠 NVIDIA device plugin 把 GPU 暴露给 K8s，还要考虑显存、卡型、拓扑（多卡通信要走 NVLink）
# K8s 里申请一张 GPU（Pod 资源声明）
resources:
  limits:
    nvidia.com/gpu: 1          # 申请 1 张 GPU，不可分割

# 多卡张量并行：一个 Pod 要 4 张卡（跑 70B 模型）
resources:
  limits:
    nvidia.com/gpu: 4

# 节点亲和性：指定卡型，避免调度到不合适的机器
nodeSelector:
  gpu-type: "a100"

模型加载慢导致扩容慢

这是 AI 服务弹性的核心矛盾：

# 传统 Web 服务扩容
新 Pod 启动 → 镜像已缓存 → 3~10 秒就绪 → 接流量
响应快，可以"流量来了再扩"

# AI 推理服务扩容
新 Pod 启动 → 下载/加载几十 GB 模型 → 3~10 分钟就绪 → 接流量
响应慢，等扩好流量高峰早过了
结论：AI 服务不能靠"流量驱动扩容"（HPA）扛突发。等你扩出来，高峰已经过去了。必须用其他手段：
① 预留容量 —— 按峰值准备常驻实例，用排队消化溢出（牺牲延迟保稳定）；
② 提前扩容 —— 按业务规律（比如上班时间）定时扩容，不等到指标触发；
③ 排队 + 限流 —— 流量超了就让用户排队，而不是无限接收导致崩溃。

冷启动问题

即使 Pod 已经启动，第一次请求也会特别慢（模型还没加载进显存 / CUDA 还没初始化）。解决思路：

手段做法效果
就绪探针（readinessProbe）探针检查 /health，模型真正加载完才返回 200避免模型没加载完就接流量
预热请求启动后主动发几个请求"暖机"避免第一个真实用户吃到冷启动延迟
模型预加载把模型文件挂载到节点本地（hostPath / 本地 SSD）避免每次从远端拉几十 GB
常驻实例池保持一定数量的"热"实例，不缩到 0彻底避免冷启动，代价是闲置成本

多模型共存的显存管理

一个团队往往要跑多个模型（不同尺寸、不同任务）。显存怎么分配是个问题：

  • 一个模型一个实例（推荐） —— 隔离好，互不影响，但每张卡只能跑一个模型，利用率低
  • 多模型共享一张卡 —— 用 LoRA（低秩适配，一种轻量微调技术）或多个小模型共存，需要框架支持（如 vLLM 的多 LoRA）
  • 动态加载卸载 —— 按需加载模型，但加载慢（几分钟），只适合低频模型
显存分配要留余量。把卡塞满（比如 7B FP16 用 14GB 卡塞 24GB 的卡，剩下的全给 KV Cache）看起来很划算，但一旦并发上来，KV Cache 撑爆就直接 OOM。
实践：vLLM 用 --gpu-memory-utilization 0.9 控制显存使用上限（默认 0.9），留 10% 给框架和其他开销。不要设成 1.0。

灰度发布模型版本

模型更新比代码更新风险更大 —— 效果变化是"软"的，不容易测出来，而且没法回滚得那么快（重新加载要几分钟）。

影子流量：新模型先只接收镜像流量（复制一份请求），不返回给用户，对比输出质量。
小流量灰度：切 1%~5% 真实流量到新模型，观察 TTFT、TPOT、失败率和业务指标。
逐步放量：每 30 分钟翻倍（5% → 10% → 20% → 50% → 100%），每步都看指标。
保留回滚路径：旧模型实例不要立刻销毁，保留一段时间，出问题能秒切回去（而不是重新加载几分钟）。
为什么模型灰度比代码灰度难：代码可以精确回滚到某个 commit，模型"回滚"意味着卸载新模型、重新加载旧模型（几分钟）。所以灰度期间要同时保留新旧两套模型实例，靠路由切换而不是靠重载。这需要额外的显存预算，规划时就要考虑进去。
常见坑

十个线上坑

1
按 QPS 规划容量，不按 Token 量
AI 服务的成本和质量由 token 量决定，不是请求数。同样 100 QPS，短请求轻松，长请求爆炸。必须按"峰值并发 × 平均上下文长度"和"token/s 吞吐"来规划。
2
忽略 KV Cache 的显存占用导致 OOM
只算了模型权重的显存，没算 KV Cache。上线后并发一上来，KV Cache 撑爆显存直接 OOM。要按"权重 + KV Cache（并发 × 上下文长度）+ 框架开销"整体估算。
3
模型加载期间流量打进来
模型要几分钟才能加载完，但 readinessProbe 配错了（或没配），K8s 以为 Pod 就绪就导流量，请求全部失败。必须用就绪探针等模型真正加载完。
4
没限制最大输出长度
不设 max_tokens，模型可能生成几千个 token，成本和延迟都失控。而且输出比输入贵好几倍。必须设合理上限。
5
把模型文件打进容器镜像
镜像几十上百 GB，构建慢、拉取慢、存储爆炸，扩容要等半天。模型应该放在外部存储（对象存储 / 共享卷 / 节点本地缓存），运行时挂载。
6
GPU 节点没有做资源隔离
多个服务共享一张卡，一个服务把显存吃满，其他全崩。要用 MIG、独立 Pod 显存限制，或干脆一个服务独占一张卡。
7
不做降级，API 供应商故障时全站不可用
整个系统只依赖一家 API，对方一抖全站挂。应用层要抽象成统一接口，配备用供应商，关键路径准备无 AI 的兜底方案。
8
流式响应被网关缓冲，流式白做
Nginx 默认会缓冲响应，SSE 流会被攒成一坨再发，用户还是要等全部生成完。必须配 proxy_buffering off，且超时按整个流设置。
9
压测用短 Prompt，上线遇长 Prompt 崩溃
压测输入分布和真实分布不一致，短 Prompt 严重低估显存需求。压测必须用真实分布（含长文本、长输出）。
10
量化后不做效果评测就上线
INT4 在简单任务上无感，在复杂推理/代码任务上可能明显退化。上线前必须用真实评测集对比量化前后的效果，不能只看"能跑起来"。
自测

六道题

1. 用户反馈"回答等很久才出第一个字"。应该优先优化哪个指标？
正确答案：TTFT。"第一个字什么时候出现"由 TTFT 决定，它包含排队时间和 Prefill 时间。优化手段：减少排队（加容量）、开启前缀缓存、缩短 Prompt。TPOT 决定的是"文字刷得快不快"。
2. 一个 7B 模型用 FP16 推理，仅模型权重需要多少显存？
正确答案：14 GB。公式：参数量 × 精度字节数 = 7×10⁹ × 2 字节 = 14 GB。注意这只是权重，还要加 KV Cache（随并发和上下文增长）和框架开销，实际需要更多。
3. 为什么加大批处理大小能提升吞吐但会增加延迟？
正确答案：Decode 阶段访存密集。生成每个 token 都要把整个权重从显存读进计算单元，瓶颈在显存带宽。批处理让权重只读一遍就服务多个请求，吞吐大幅提升；代价是请求要等待凑批，延迟变高。延迟和吞吐是跷跷板。
4. 关于 KV Cache 的显存占用，哪个说法是对的？
正确答案：随上下文长度和并发数线性增长，两者相乘。单 token KV Cache 大小固定（与层数、KV 头数、头维度、精度有关），但总占用 = 单 token 大小 × 上下文长度 × 并发数。上下文翻倍、并发翻倍，KV Cache 就涨 4 倍。这是最容易被忽略、最容易导致 OOM 的部分。
5. AI 服务的限流，为什么不该按 QPS 做？
正确答案：请求成本差异极大。同样 100 QPS，短请求总 token 3000/s 轻松扛住，长请求 600000/s 直接爆炸。正确做法是按 token 配额限流（保护钱包）+ 按并发数限流（保护显存）。
6. 为什么 AI 服务不能靠 HPA（按流量自动扩容）扛突发流量？
正确答案：模型加载慢。新实例要下载/加载几十 GB 模型，3~10 分钟才能就绪。等 HPA 扩出来，高峰早过了。应该用预留容量 + 排队限流 + 定时提前扩容来应对。

显存估算公式速查

# ===== 权重显存 =====
权重(GB) = 参数量(B) × 精度字节数
  精度字节数：FP32=4, FP16/BF16=2, INT8=1, INT4=0.5
  示例：7B FP16 = 7 × 2 = 14 GB

# ===== 单 token KV Cache =====
单token(KB) = 2 × 层数 × KV头数 × 头维度 × 精度字节数 ÷ 1024
  注意：是 KV 头数不是 Q 头数（GQA 模型 KV 头数远小于 Q 头数）
  示例(Llama3-8B)：2 × 32 × 8 × 128 × 2 ÷ 1024 = 128 KB/token

# ===== KV Cache 总量 =====
KV Cache(GB) = 单token(KB) × 上下文长度 × 并发数 ÷ 1024 ÷ 1024
  示例：128KB × 4096 × 16 ÷ 1024 ÷ 1024 = 8 GB

# ===== 总显存需求 =====
总显存 = 权重 + KV Cache + 框架开销(1~2GB)
  建议留 10% 余量（vLLM 默认 --gpu-memory-utilization 0.9）

术语表

术语一句话解释
推理 Inference用训练好的模型做预测/生成，区别于训练
TTFTTime To First Token，从发请求到收到第一个 token 的延迟
TPOTTime Per Output Token，生成每个 token 的平均耗时
吞吐 Throughput单位时间产出的 token 数，直接换算成成本
Prefill 预填充推理第一阶段，把输入 Prompt 全部算一遍，计算密集，决定 TTFT
Decode 解码推理第二阶段，逐个生成输出 token，访存密集，决定 TPOT
KV Cache缓存注意力键值，避免重复计算历史 token；随并发和上下文线性增长
GQA分组查询注意力，多个 Q 头共享 KV 头，把 KV Cache 缩小数倍
连续批处理每个 token 生成步骤都重新组批，GPU 不闲置，吞吐提升数倍
PagedAttention像虚拟内存分页一样管理 KV Cache，把显存浪费从 60%+ 降到 4% 以下
前缀缓存多个请求的相同前缀只计算一次，降低 TTFT 和算力消耗
投机解码用小模型猜多个 token，大模型一次验证，降低生成延迟
量化 Quantization用低精度（INT8/INT4）表示权重，省显存，但可能损失精度
张量并行 TP把一个大模型拆到多张卡上并行计算，用于跑超大模型
OOMOut Of Memory，显存不足，服务崩溃
SSEServer-Sent Events，流式返回 token 的标准协议
LoRA低秩适配，一种轻量微调技术，可让多个"模型变体"共享一份基础权重
MIGMulti-Instance GPU，把一张物理卡切成多个隔离的小实例
冷启动实例刚启动、模型未加载时的首次请求延迟
影子流量把真实请求复制一份发给新版本，不影响用户，用于验证效果
