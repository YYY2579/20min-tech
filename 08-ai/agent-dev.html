二十分钟学透 Agent 开发

Agent 不是"更长的提示词"，是一个把 LLM 当决策内核、带工具、带记忆、带停止条件的控制循环。这篇讲工程实现：ReAct 循环、工具调用协议、规划与反思、记忆分层、HITL 与观测。

开始前

先约定口径

工具调用的协议、消息格式各家演进很快（OpenAI 的 function calling / tools、Anthropic 的 tool use 等）。本篇以主流 API 的通用模式为例，具体字段以你所用模型的官方文档为准。

Agent 的本质
LLM 输出不再直接是答案，而是下一步动作（调哪个工具、传什么参数），由你的代码执行并把结果喂回去，循环直到任务完成
你负责的
工具实现、循环控制、超时与重试、权限边界、可观测性——模型只负责"决定做什么"
模型负责的
理解任务、选择工具、填参数、判断何时停止、组织最终答案
分界线
"模型决定、代码执行、结果回喂"——这条分界线画错（比如让模型直接执行命令）就是安全事故
模块 1

Agent 与 Workflow 的区别

这是 Agent 开发第一个也最重要的决策。Workflow 是预定义编排，Agent 是自主决策——Anthropic 的《Building Effective Agents》把这个区分讲得很清楚：能用工作流解决的，不要上 Agent。

维度Workflow（工作流）Agent（智能体）
控制流开发者写死：先 A 再 B，条件分支也是代码模型运行时决定下一步做什么
路径数量有限、可枚举开放，取决于模型每轮的判断
可测试性高。路径固定，用例可穷举低。同输入不同路径，需要统计式评测
延迟/成本可预测不可预测（循环几轮看模型心情）
适用流程明确的重复任务（文档处理管线、分类路由）开放式问题、步骤无法预先枚举的任务（调研、排障、复杂操作）

五种工作流模式（从简单到复杂）

链式（Chaining）。任务拆成固定步骤，上一步输出是下一步输入。加"门控"：每步后检查，不达标就提前退出。最常用，优先用它。
路由（Routing）。先分类，再把请求分给专门的下游（提示词/工具/模型）。适合多品类输入。
并行（Parallelization）。多个相同任务并发跑（Sectioning），或多个模型投票（Voting，即自洽性的工程化）。
编排者-工人（Orchestrator-Workers）。中央模型动态拆解任务、分派给工人模型、汇总结果。开始有"Agent 味"了，但拆解逻辑仍由模型主导、步骤不固定。
评估者-优化者（Evaluator-Optimizer）。一个模型生成、另一个模型按标准评审，不达标打回重做，循环直到达标或达上限。
务实建议：80% 的"Agent 需求"用链式 + 路由就能满足，且可测试、可预测。只有当"下一步做什么无法预先枚举"时，才值得上自主循环。为了 Agent 而 Agent，是成本、延迟、不可控的三重灾难。
模块 2

ReAct 模式

ReAct（Reason + Act）是 Agent 的基石循环：思考（这个情况该做什么）→ 行动（调工具）→ 观察（拿到结果）→ 再思考，直到模型输出"最终答案"而不是动作。

# ReAct 循环的轨迹长这样（模型每轮输出一块）
Thought: 用户问"上海明天适合晒被子吗"。需要查上海明天的天气。
Action: get_weather(city="上海", date="明天")
Observation: 多云，降水概率 30%，湿度 65%，东风 3 级
Thought: 降水概率 30% 有降雨可能，湿度 65% 偏高。结论：不太适合，
           建议再等一天。信息足够，可以回答了。
Final Answer: 明天上海多云，降水概率约 30%、湿度 65%，有降雨可能且
              湿度偏高，不太适合晒被子；建议避开明天，选连续晴天。 
# 工程实现骨架（Python 伪代码，API 调用以各家文档为准）
def run_agent(task, tools, max_steps=15):
    messages = [system_prompt, user_message(task)]
    for step in range(max_steps):                 # ① 硬性步数上限
        resp = llm.chat(messages, tools=tool_schemas(tools))
        if resp.tool_calls:                        # 模型要调工具
            for call in resp.tool_calls:
                result = execute_tool(call)           # 你的代码执行，带超时/权限检查
                messages.append(tool_result_message(call.id, result))
        else:
            return resp.content                    # 模型直接回答 = 任务完成
    return "已达到最大步数，任务未完成"             # ② 兜底退出

# 三个必须有的工程件：
# ① max_steps —— 没有它，模型可能永远"再想一步"（无限循环烧钱）
# ② 全局超时/预算 —— token 预算 + 墙钟时间，双上限
# ③ 兜底退出 —— 触顶时给出可解释的失败，而不是挂起
ReAct 的固有弱点：误差会累积——第 3 步的一个错误观察，会让后面 10 步全建在错误前提上；而且错误不会自愈，模型很少"回头看"推翻自己。对策：单步工具结果做校验（查天气返回"null"就告诉模型"查询失败，请重试或换数据源"）+ 周期性重规划（见模块 4）。
模块 3

工具调用

工具是 Agent 的手脚。工具调用的质量，70% 取决于工具描述（schema + description）写得好不好。

工具定义：给模型看的"API 文档"

# function calling 的工具定义（示意，字段以官方文档为准）
{
  "type": "function",
  "function": {
    "name": "query_order",
    "description": "查询订单详情。需要用户授权。返回订单状态、金额、物流信息。",
    "parameters": {
      "type": "object",
      "properties": {
        "order_id": {
          "type": "string",
          "description": "订单号，12 位数字。用户未提供时不要编造，先询问。"
        },
        "fields": {
          "type": "array",
          "items": {"enum": ["status", "amount", "logistics"]},
          "description": "需要返回的字段，默认全部"
        }
      },
      "required": ["order_id"]
    }
  }
}

# 写工具描述的要点：
# 1. description 写给模型看：说清"什么时候该用、什么时候不该用、
#    参数缺失时怎么办（询问用户而不是编造）"
# 2. 参数描述给边界和示例："12 位数字"比"订单号"有效得多
# 3. enum 收窄取值空间，比纯 string 描述可靠一个量级

并行调用与错误处理

# 模型可以一轮返回多个 tool_call（无依赖的应并行执行）
# 错误处理是工具层的第一公民，四种错误分级处理：
def execute_tool(call, ctx):
    try:
        args = validate(call.arguments, schema)      # 参数校验失败 → 把错误原因
        return TOOL_REGISTRY[call.name](args, ctx)   # 回喂给模型让它修正重试
    except ValidationError as e:
        return {"error": f"参数不合法：{e}。请修正后重试。"}    # 模型可恢复
    except ToolTimeout:
        return {"error": "查询超时。可稍后重试或告知用户稍后再试。"}
    except PermissionDenied:
        return {"error": "当前用户无此操作权限。请引导用户走人工流程。"}  # 不可恢复
    except Exception:
        return {"error": "服务暂时不可用，请稍后重试或转人工。"}      # 不暴露内部细节！

# 三条铁律：
# 1. 工具错误必须回喂给模型（附原因），让它自己修正——这是 Agent 健壮性的核心
# 2. 内部异常详情（堆栈、SQL）绝不进模型上下文，防信息泄露 + 防幻觉扩散
# 3. 高危工具（转账、删除、外发）不在工具层做，要过人机确认（见模块 6）
工具设计的常见错误：① 一个工具包打天下（一个 do_everything 带 20 个参数）——模型填参错误率飙升，拆成多个单一职责工具；② 工具返回整个 HTML 页面/几千行 JSON——先在你的代码里提炼成结构化摘要再回喂；③ 工具数量过多（> 20 个）导致模型选择困难，按场景动态加载工具子集。
模块 4

规划：任务分解与反思

任务分解的两种形态

形态做法适用
静态分解开始时让模型列出计划（plan-then-execute），之后按计划逐步执行步骤大体可预见的任务（调研报告、数据整理）
动态分解每轮由模型决定下一步（ReAct 的默认形态）步骤依赖执行结果的任务（排障、开放式调研）

反思（Reflexion）

# 周期性自查：每 N 步或关键节点，让模型评估当前进展
自查提示（每 5 步注入一次）：
  请评估当前任务进展：
  1. 目标是什么？已完成了哪些？
  2. 已有的信息是否支持得出结论？还缺什么？
  3. 之前是否有错误假设需要修正？
  输出：继续执行 / 需要补充信息【具体缺什么】 / 可以给出结论

# 生成-评估循环（Evaluator-Optimizer 模式）
draft = generate(task)
while not critique_is_pass(evaluate(draft, criteria)) and rounds < 3:
    draft = revise(draft, critique)     # 按评审意见重写，最多 3 轮

# 成本意识：每轮反思都是额外 LLM 调用。反思的价值与任务复杂度正相关，
# 简单任务（查天气）加反思纯属浪费；多步调研任务没有反思，误差会滚雪球。
分解粒度经验：一个子任务应该满足"单轮工具调用能完成、产出可验证"。如果分解出的子任务还需要再分解，说明粒度太粗；如果每个子任务只是一次简单查询，说明粒度太细（直接 ReAct 就行，不用显式规划）。
模块 5

三层记忆体系

层内容实现
短期记忆当前任务的对话历史、工具结果、中间推理就是 messages 数组。核心问题是会溢出
长期记忆跨会话的用户偏好、历史决策、事实性知识外部存储（KV/向量库）+ 按需检索
检索记忆可检索的历史经验（过去的案例、文档）向量库 + RAG（与 RAG 专题呼应）

上下文管理：Agent 的第一工程难题

# 上下文溢出的处理策略（按优先级）
# 1. 滚动摘要：历史超过阈值时，把旧轮次压缩成摘要，保留最近 N 轮原文
# 2. 工具结果瘦身：大结果只保留摘要 + 引用 ID，全文存外部，需要时再取
# 3. 外部记忆：把中间结论写进 scratchpad（文件/DB），需要时读回

def manage_context(messages, budget_tokens):
    if count_tokens(messages) <= budget_tokens:
        return messages
    # 保留 system + 最近 4 轮原文，中间部分摘要化
    head = messages[:1]
    recent = messages[-8:]
    middle = messages[1:-8]
    summary = llm.summarize(middle, prompt="用 200 字内概括已完成的关键事实和结论")
    return head + [summary_msg(summary)] + recent

# 预算分配（8K 窗口示例）：system ~300 / 摘要 ~300 / 近期历史 ~2000 /
#                       工具结果余量 ~3000 / 输出预留 ~800
记忆不是越多越好：长期记忆的写入要有质量标准——把"今天用户问过退款"这种无价值信息写进长期记忆，会污染后续所有检索。写入前先过一道"这条信息未来有用吗"的判断（可以用一次 LLM 调用做筛选，也可以规则化：只存显式偏好和重要决策）。
模块 6

多 Agent 协作与人机协同

多 Agent 不是银弹，是组织问题。先想清楚"为什么需要多个"，再选协作模式。（多 Agent 的系统性架构另见专题，这里只讲工程实现要点。）

三种协作拓扑

拓扑结构适用
主管-工人主管拆任务分派、汇总；工人各管一个领域（检索/计算/写作）任务可清晰分域的复杂任务。默认选择
流水线Agent A 的输出是 B 的输入，串成链有明确阶段的生产线式任务
辩论/评审多个 Agent 独立产出 + 互相评审投票高价值决策（用算力换质量，成本高）

人机协同（HITL）检查点

不可逆操作前转账、删数据、发对外消息、下单——执行前必须人工批准
高成本阈值预估 token/费用超阈值（如单任务 > $1）时暂停确认
低置信度时模型自评不确定、工具返回冲突信息时，升级人工
敏感数据访问读取 PII、财务数据前按权限策略确认
连续失败 N 次同一工具连续失败/循环，停止自动重试转人工
# HITL 的工程实现：把"人工批准"做成一个特殊工具
tools = [..., {
  "name": "request_human_approval",
  "description": "执行不可逆/高风险操作前，调用此工具请求人工批准。",
  "parameters": {"action": string, "risk_summary": string}
}]

# 该工具"执行" = 向审批系统发通知并阻塞等待（带超时）
# 批准 → 继续执行原操作；拒绝/超时 → 把结果回喂模型，走降级路径
# 关键：审批界面要展示"模型想做什么 + 参数 + 风险摘要"，人才能做有效判断
多 Agent 的三个真实成本：① 上下文不共享——工人之间传消息靠序列化，信息损耗大；② 错误传播——一个工人的幻觉被当成事实传给下一个；③ 调试噩梦——10 个 Agent 的交互路径组合爆炸。先从单 Agent + 丰富工具开始，确有必要再拆。
模块 7

评估与观测

Agent 的不可预测性要求统计式评测 + 全链路 trace，单次 case 通过说明不了任何问题。

核心指标

指标定义说明
任务成功率端到端完成且结果正确的比例北极星指标，人工标注或 LLM-judge 评
平均步数 / 成本每任务的 LLM 调用轮数、token 消耗发现"啰嗦 Agent"（10 步能做完的用了 30 步）
工具选择准确率该用工具 A 时用了 A 的比例定位"选错工具"问题
参数填充准确率工具参数正确的比例定位"工具描述不清"问题
循环/超限率触顶 max_steps 或超时退出的比例> 5% 就要排查，是鲁棒性红线
幻觉行动率调用了不存在的工具/编造参数的比例安全相关，重点监控

Trace：Agent 的日志

# 一次任务的 trace 结构（每步落库，可回放）
trace_id: tr-20261018-abc123
task: "帮我查下订单 12345 到哪了，顺便问问能改地址吗"
steps:
  - step 1 | thought: 先查订单物流 | tool: query_order(id=12345) | result: ok(180ms)
  - step 2 | thought: 查到了，在广州分拣。改地址需要调用物流接口
           | tool: modify_address(order_id=12345, new_addr="...")
           | result: error(参数不合法：缺少 region_code)
  - step 3 | thought: 向用户询问 region_code | tool: ask_user("请提供新地址的地区编码")
           | result: 用户回复（HITL）
  - step 4 | tool: modify_address(...) | result: ok
  - step 5 | final answer: "您的订单现在广州分拣中心……地址已修改成功"
summary: 成功 | 步数 5 | token 8,432 | 耗时 12.3s | 人工介入 1 次

# 工具选择：OpenTelemetry 语义约定 + Langfuse / LangSmith 等平台，
# 或自建（每步一个 span，挂 thought/tool/args/result/tokens 字段）
# trace 的用途：失败归因（哪一步开始歪）、成本审计、回归对比、badcase 回放
评测集建设：从真实用户任务采样 50~100 条，标注"期望调用的工具序列 + 期望最终答案"。每次改系统提示/换模型/换工具，全量跑回归，看成功率、平均步数、超限率三个数。评测方法论详见《AI 应用评估体系》。
模块 8

十个常见坑

1
没有 max_steps，无限循环
模型反复"再想一步"，token 账单指数增长，任务永不结束。硬性步数上限 + 全局 token/时间预算 + 循环检测（相同工具相同参数重复调用即中断）三件套缺一不可。
2
工具描述不清
description 写"查询订单"，不写"什么时候用、参数缺失怎么办、返回什么"。模型选错工具、编参数、重复调用。工具描述是写给模型的文档，要按 API 文档的标准写。
3
上下文溢出才处理
messages 无限增长，直到 API 报错或模型"忘记"开头指令。预算管理要前置：滚动摘要 + 工具结果瘦身 + 外部 scratchpad，在接近窗口上限前就动手。
4
幻觉行动
模型调用不存在的工具、编造参数值、声称执行了其实没执行的操作。对策：工具白名单强校验（不存在的调用直接报错回喂）、写操作必须返回真实执行凭证、最终答案要求引用工具结果。
5
工具错误不回喂
工具抛异常，代码 catch 后返回"查询失败"四个字，模型不知道缺什么参数、该重试还是放弃，只能瞎猜。错误信息要结构化回喂（原因 + 修复建议），这是 Agent 自愈的基础。
6
内部异常细节进上下文
堆栈、SQL、内部 IP、密钥片段直接回喂给模型，既泄露敏感信息又污染上下文。工具层做错误翻译：对内详细、对外（模型）只给结论和行动建议。
7
为了 Agent 而 Agent
流程固定的任务（格式转换、审批流）也上自主循环，成本高、延迟抖、不可测。先评估链式/路由工作流能不能满足——绝大多数场景能。
8
高危操作无人审
模型输出"调用 delete_all" 代码就执行，没有人工确认、没有 dry-run、没有操作审计。不可逆操作必须 HITL；所有写操作留审计日志（谁的任务、什么参数、谁批准的）。
9
多 Agent 过早拆分
任务还没跑顺就拆成 5 个 Agent，上下文传递靠自然语言，错误传播、调试困难。先单 Agent + 工具富化，出现明确的性能/上下文瓶颈再拆。
10
只测 happy path
评测集全是顺利场景，上线后工具超时、参数缺失、用户中途改需求全抓瞎。评测集必须包含故障注入（工具 500、超时、返回空）和多轮干扰场景。
自测

六道题

1. 判断该用 Workflow 还是 Agent 的核心标准是？
正确答案：步骤能否预先枚举。流程固定的任务用链式/路由工作流（可测、可预测、便宜）；只有"下一步做什么取决于执行结果、无法预先写死"时才值得上自主循环。为了 Agent 而 Agent是成本、延迟、不可控的三重灾难。
2. ReAct 循环中，防止无限循环的必备工程件是？
正确答案：硬性上限 + 预算 + 循环检测。提示词的"劝告"对循环行为基本无效；temperature=0 只降低随机性，不提供停止保证。相同工具相同参数重复调用是循环的典型信号，应直接中断。
3. 工具调用返回参数校验失败，正确的处理是？
正确答案：结构化回喂错误原因。Agent 的健壮性建立在"错误可自愈"上：模型看到"缺少 region_code 参数，请向用户询问或补全"就能修正。默默补默认值是埋雷（用错参数执行了错误操作），只说"失败"模型无法针对性修正。
4. 关于工具描述（schema 的 description），哪种说法是对的？
正确答案：描述写给模型看，决定工具选择质量。工具选择准确率、参数填充准确率两个指标直接受描述质量影响。"12 位数字"比"订单号"有效得多；enum 比纯 string 可靠一个量级。但也不是越长越好——冗余描述同样稀释注意力。
5. 哪些操作前必须设置人工确认（HITL）检查点？
正确答案：不可逆/高成本/低置信/敏感/连续失败五类。全量人工确认会让 Agent 失去意义（人比模型慢得多）。检查点的设计原则：操作不可逆性或成本越高、模型确定性越低，越要卡住；审批界面要展示"想做什么+参数+风险摘要"，人才能做有效判断。
6. Agent 系统上线后，最值得优先建设的可观测能力是？
正确答案：全链路 trace。Agent 的失败是"第 3 步开始歪"，没有分步 trace 根本无法归因。trace 同时支撑成本审计（token/步数）、回归对比（改提示词前后成功率）、badcase 回放。打印完整 prompt 到日志还有敏感数据泄露风险。
