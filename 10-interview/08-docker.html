读之前先答一句：你在容器里执行 free -h，看到的那 128G 是谁的内存？
开始前

三个现场：容器最容易骗人的三个地方

面试官问「容器和虚拟机有什么区别」，绝大多数人能背出「共享内核、启动快、更轻量」。但真正区分「背过」和「用过」的，是下面这三个现场：它们都会让一个熟练的 Linux 运维在容器里做出错误判断。

现场直觉判断真实情况
容器 --memory=2g，进去 free -h 显示 total 128G内存限制没生效，得重新配/proc/meminfo 不在默认隔离范围内，读到的是宿主机的。限制生效在 cgroup 里，看 /sys/fs/cgroup/memory.max
镜像 1.2G，这次只加了一个 10M 的 jar，构建完还是 1.2G镜像构建有 bug，或者层没复用每一层都是独立的，下层已有的文件不会因为上层 rm 而变小。镜像大小是各层增量之和，不是最终文件系统的大小
容器里 ps aux 看到一堆宿主机进程隔离失效了，可能要重装 Docker启动时用了 --pid=host（或者 --privileged 加上了宿主 PID 视图）。PID 隔离是按需开的，不是默认不可破
隔离靠 namespace
决定「你能看见什么」。进程号、网卡、挂载点、主机名、IPC、用户，各有一套独立的视图。
限制靠 cgroup
决定「你最多能用多少」。CPU 时间片、内存上限、进程数、IO 权重，都写在这里。
文件系统靠联合挂载
决定「你看到的是哪份文件」。只读层共享，可写层独占，改一个文件先复制上来。

这三件事拼起来就是容器：一个普通进程，被换了视图、上了限额、换了个根目录。没有虚拟化层，没有 Guest 内核，没有硬件模拟。所以它启动是毫秒级，也所以它的隔离强度低于虚拟机——内核只有一个，内核出问题，所有容器一起出问题。

为什么这句话值得反复说：面试里后面所有追问都挂在这句话上。问「容器里为什么不能改时间」，因为共享内核时钟；问「为什么容器里 top 看到宿主机的负载」，因为 /proc 的某些文件没隔离；问「为什么 limit 设了还是 OOM」，因为 cgroup 管的是这个进程组，不是那块内存条。开头这句答歪了，后面只能靠猜。

面试落点：「容器本质上是被 namespace 换了视图、被 cgroup 限了资源、用联合文件系统换了根目录的一个普通进程，和宿主机共享同一个内核。所以它轻、快，但隔离强度不如虚拟机；也所以容器里看到的部分 /proc 信息是宿主机的，判断资源要看 cgroup 而不是 free。」

模块 1

容器到底是什么：一句话拆成四件事

在容器里敲 uname -r，输出的内核版本和宿主机一模一样。这一条就够了：容器没有自己的内核。虚拟机有，容器没有，这是两者所有差异的源头。

把「容器」这个词拆开，实际上是四样东西的组合：

  • 一个进程：容器的生命周期等于 PID 1 的生命周期。PID 1 退出，容器就结束，不管里面还有没有别的进程。
  • 一组 namespace：让它看不见宿主机的其他进程、网卡、挂载点。
  • 一组 cgroup：让它最多只能用这么多 CPU 和内存。
  • 一个根文件系统：由镜像的只读层加一个可写层联合挂载而成，通常还会 pivot_root 切过去。
维度虚拟机容器
内核每个 VM 一套 Guest 内核，通过 Hypervisor 跑在虚拟硬件上共享宿主机内核，没有 Guest 内核
启动开销要引导内核、跑 init，秒级创建一个进程，毫秒级
隔离强度硬件级，Hypervisor 是边界内核级，namespace 是边界；内核漏洞可能穿透
密度一台宿主机几个到几十个几百个很常见，因为不额外占内核内存
能跑别的系统吗能，Windows 上跑 Linux 没问题不能，容器里的内核版本必须和宿主机一致
典型用途强隔离、多租户、异构系统打包交付、弹性扩缩、CI 环境

「容器不能跑不同内核」这句话在面试里很好用，因为它能顺势带出安全话题：容器共享内核，意味着内核的攻击面被所有容器共享；一个容器拿到内核提权，宿主机就没了。这也是 Kata Containers、gVisor 这类方案存在的理由——它们把「每个容器一个内核」这件事又加回去了，代价是启动变慢、兼容性下降。

# 容器内外内核版本一致，这是最直接的证据
uname -r
docker run --rm alpine uname -r

# 容器进程在宿主机上的真实 PID（不是容器里的 1）
docker inspect -f '{{.State.Pid}}' web
cat /proc/$(docker inspect -f '{{.State.Pid}}' web)/cgroup

# 看它到底被放进了哪些 namespace
ls -l /proc/$(docker inspect -f '{{.State.Pid}}' web)/ns/

还有一个常被忽略的判断：容器里能不能起 systemd，取决于你有没有给它特权。普通容器默认没有 CAP_SYS_ADMIN、没有可写的 cgroup 挂载、没有 udev，systemd 起来就报一堆错。所以「容器里跑 systemd」这个做法要么加 --privileged（等于放弃隔离），要么用 --cgroupns=host 加挂载，总之都不是常规路径。镜像应该直接跑应用进程，而不是跑一个 init 系统。

不要把「容器里 root」等同于「宿主机 root」。默认情况下容器里的 root 通过 user namespace 之外的方式映射，仍然是宿主机上的 root（只是被 capabilities 和 seccomp 削过）。只有开了 userns-remap 或 rootless 模式，UID 才真正错开。面试里被问「容器里 root 危险吗」，答案要分层说：默认危险，加 userns 或 rootless 才缓解。

面试落点：「容器是进程级隔离，不是虚拟化。它由 namespace、cgroup、联合文件系统三块拼起来，共享宿主机内核。所以启动快、密度高，但隔离弱于 VM，也不能跑异构内核。要更强隔离就上 Kata 或 gVisor，本质是把内核重新塞回每个容器里。」

模块 2

启动链路：docker 只是壳，真正干活的是 runc

「docker run 之后发生了什么」是这条链路上出现频率最高的追问。大部分人能答到 containerd，再往下就断了。而真正决定「容器怎么被创建出来」的那一步，在一个用完就退出的工具里。

完整链路是这样的：

docker CLI 把你的命令翻译成 REST 请求，发给 /var/run/docker.sock。它自己什么都不做，连镜像都不会拉。
dockerd 收到请求，负责镜像、网络、卷这些「上层」的事，然后把「创建容器」这件事交给 containerd。它自己也不直接创建进程。
containerd 是真正的容器生命周期管理器。它拉镜像（转成 OCI 布局）、准备 rootfs、生成 OCI runtime spec（config.json），然后调用运行时。
containerd-shim 先起来。它每个容器一个，作用是当容器进程的父进程：接管 stdin/stdout、回收僵尸进程、在 dockerd 或 containerd 重启时保住容器不死。
runc 由 shim 调起，读 config.json，创建 namespace、写 cgroup、挂载 rootfs、pivot_root、设置 capabilities 和 seccomp，最后 exec 出应用进程，然后自己退出。

关键点在最后一句：runc 是一次性工具，不是常驻进程。它退出的那一刻，应用进程被挂到 shim 名下（reparent），所以你在宿主机上 ps -ef 看到的父子关系是 shim → 应用，而不是 runc → 应用。这个细节能解释两件事：为什么 dockerd 重启容器不挂（shim 还在），为什么容器里的 PID 1 在宿主机上是一个非常普通的 pid。

# 看这条链路上的进程：每行对应一个环节
ps -ef | grep -E 'dockerd|containerd|shim' | grep -v grep

# 容器进程在宿主机上的 PID、父进程
PID=$(docker inspect -f '{{.State.Pid}}' web)
ps -o pid,ppid,comm -p $PID
ps -o pid,ppid,comm -p $(ps -o ppid= -p $PID)

# 确认运行时是 runc 还是别的（crun / kata）
docker info | grep -i -E 'runtime|storage driver|root dir'

# OCI spec 长什么样：namespace、cgroup、capabilities 都在里面
docker inspect -f '{{json .HostConfig.NanoCpus}}' web

顺带说清 Kubernetes 这边的关系，因为面试常连着问：kubelet 通过 CRI（Container Runtime Interface）调用容器运行时，最常用的是 containerd。早年的 dockershim 已经在 Kubernetes 1.24 移除，所以现在说「K8s 用 Docker」是不准确的——它用的是 containerd，只是镜像格式（OCI）还通用。这个点上答错，会被认为知识停留在三年前。

一个好用的类比：dockerd 像项目经理，接需求、协调资源；containerd 像包工头，管材料和工序；shim 像现场留守的人，负责收尾和顶着；runc 像施工队，干完这一票就撤。真正把墙砌起来的是施工队，但你平时打交道的永远是项目经理。
docker inspect -f '{{.State.Pid}}' NAME容器主进程在宿主机上的真实 PID，进 namespace、看 cgroup 都要用它
ps -ef | grep containerd-shim每个运行中的容器对应一个 shim，容器进程的父进程就是它
ls -l /proc/PID/ns/这个进程被放进了哪些 namespace，inode 相同即同一个
cat /sys/fs/cgroup/.../cpu.maxCPU 带宽限制的实际值，形如 150000 100000 表示 1.5 核
docker history --no-trunc IMAGE镜像每一层做了什么、多大，找体积异常的第一条命令

面试落点：「docker CLI 发请求给 dockerd，dockerd 转给 containerd，containerd 准备 rootfs 和 OCI spec 后调 shim，shim 调 runc。runc 创建 namespace 和 cgroup、切根、exec 出进程后自己退出，容器进程被挂到 shim 下。这样 dockerd 重启不影响容器，也解释了为什么宿主机上看到的父进程是 shim。」

模块 3

namespace 六种：每一种对应一句「为什么看不到」

「容器用到了哪些 namespace」这题不难，难在后面那句追问：「user namespace 是干什么的，为什么 Docker 默认不开？」能答上来的人不多。

namespace标识隔离了什么容器里的直观表现
Mountmnt挂载点视图容器里的 / 是镜像的根，看不到宿主机的 /var/lib/docker
PIDpid进程号空间应用是 PID 1，ps 只看到自己那几个进程
Networknet网卡、路由表、iptables、端口有自己的 eth0 和 lo，localhost 只指自己
UTSuts主机名与域名hostname 默认是容器 ID 的前 12 位
IPCipcSystem V IPC 与 POSIX 消息队列容器间的共享内存默认互不可见
UseruserUID/GID 映射容器里的 root 可以映射成宿主机上的普通用户

除了这六个，还有两个新一点的：cgroup namespace（让容器里的 /proc/self/cgroup 显示相对路径，不泄露宿主机层级，cgroup v2 环境下基本默认开启）和 time namespace（Linux 5.6 起，可以让容器有自己的单调时钟偏移，但对 CLOCK_REALTIME 仍然共享，所以「容器里改时间」依然做不到）。答出这两个是加分项，但要标明它们是后来加的，别把「六种」说成「八种就是标准答案」。

user namespace 值得单独说：它能把容器内的 UID 0 映射到宿主机上的一个非 0 的普通 UID（通过 /etc/subuid 分配一段范围）。这样即使容器里提权到 root，在宿主机上也只是一个没权限的用户，逃逸门槛大大提高。Docker 提供了 --userns-remap 和 rootless 模式来启用它，但默认不开，原因是兼容性：卷的属主会变、镜像里的固定 UID 会错位、某些需要真实 root 的操作会失败。

# 宿主机上列所有 namespace，能看到容器的 net/mnt 都在里面
lsns -t net
lsns -t mnt | head

# 两边的 net namespace 是不是同一个（inode 相同就是同一个）
readlink /proc/1/ns/net
readlink /proc/$(docker inspect -f '{{.State.Pid}}' web)/ns/net

# 进容器的网络 namespace 抓包/看端口，不用 docker exec
nsenter -t $(docker inspect -f '{{.State.Pid}}' web) -n ss -lntp

# 确认容器是否开了 user namespace 重映射
docker inspect -f '{{.HostConfig.UsernsMode}}' web
--pid=host 加 --privileged 基本等于把宿主机交出去。前者让你看见并 kill 宿主进程，后者给你几乎全部 capabilities 和所有设备。很多「调试方便」的写法最后变成了生产配置，这类容器一旦被拿到执行权限，逃逸成本接近零。

面试落点：「六种：mnt、pid、net、uts、ipc、user，分别管挂载点、进程号、网络、主机名、IPC 和 UID 映射。cgroup 和 time 是后来加的。user namespace 能把容器内 root 映射成宿主机普通用户，是重要的加固手段，但默认不开，因为卷属主和镜像内固定 UID 会出问题。」

模块 4

cgroup：--cpus 1.5 到底写进了哪个文件

「你给容器设了 2 核，怎么验证它真的只能用 2 核？」这个问题会筛掉一批人。能答出「看 cgroup 文件」的，再追问一句「v1 和 v2 分别是哪个文件」，剩下的就不多了。

cgroup 的作用是给一组进程记账并限额。v1 的做法是每种资源一个独立的层级树（cpu 一棵、memory 一棵、blkio 一棵），挂载点一堆，管理起来很乱；v2 改成单层级树，所有控制器挂在同一棵树上，通过 cgroup.controllers 和 cgroup.subtree_control 决定哪些控制器在子节点生效。

v2 文件含义对应 docker 参数
cpu.max格式是「配额 周期」，单位微秒。默认周期 100000--cpus=1.5 写成 150000 100000
cpu.weight相对权重，默认 100，范围 1~10000。只在争抢时起作用--cpu-shares（v1 语义，默认 1024）换算而来
cpu.stat累计用量，以及 nr_throttled / throttled_usec没有直接参数，用来判断有没有被限流
memory.max硬上限，超过就触发回收，回收不动就 OOM kill--memory=512m
memory.high软上限，超过会被限速回收，一般不杀进程Docker 不直接暴露，K8s 里也没有
memory.current当前用量，包含 page cache对应 docker stats 的内存列
memory.eventsoom 和 oom_kill 的累计次数判断「是不是真的被 OOM 杀了」
pids.max进程/线程数上限--pids-limit

v1 的对应关系要能说出来，因为很多老环境还在用：CPU 是 cpu.cfs_quota_us 和 cpu.cfs_period_us（配额 -1 表示不限制），内存是 memory.limit_in_bytes，OOM 计数在 memory.oom_control 和 memory.failcnt 里。路径是 /sys/fs/cgroup/cpu/... 和 /sys/fs/cgroup/memory/... 两棵不同的树。

# 1. 先确认宿主机用的是 v1 还是 v2
stat -fc %T /sys/fs/cgroup        # cgroup2fs 是 v2，tmpfs 一般是 v1
docker info | grep -i cgroup

# 2. 找到容器的 cgroup 路径（v2）
PID=$(docker inspect -f '{{.State.Pid}}' web)
cat /proc/$PID/cgroup             # 形如 0::/system.slice/docker-<id>.scope

# 3. 直接读限额，不猜
CG=/sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' web).scope
cat $CG/cpu.max                   # 150000 100000 就是 1.5 核
cat $CG/memory.max
cat $CG/memory.current
cat $CG/memory.events             # oom / oom_kill 计数

# 4. 判断有没有被 CPU 限流
grep -E 'nr_throttled|throttled_usec' $CG/cpu.stat

关于内存 limit，有两个必须说清的语义。第一，memory.max 管的是这个 cgroup 里所有进程的匿名内存加 page cache，不是「堆内存」。所以一个 Java 进程 limit 2G，堆设 1.8G，加上元空间、线程栈、直接内存、JIT 代码缓存，很容易顶到 2G，然后被内核杀掉——而堆 dump 上看不出任何异常。第二，快满的时候内核会先回收 page cache，回收不够才 OOM，所以「memory.current 长期贴着 max」不一定已经出事，但一定很危险，因为它没有余量应对突发。

CPU 这边，--cpus=1.5 是硬限流，超了就被 throttle，表现出来是延迟抖动而不是 CPU 100%。--cpu-shares 是软权重，只在机器忙的时候决定谁多分一点，空闲时一个 share 很小的容器也能跑满所有核。这两个经常被混为一谈：一个管上限，一个管分配比例。

cgroup 的统计有延迟，且不是免费的。高频轮询 memory.current 在大规模容器环境下会有可观的 CPU 开销，监控采集一般是 15~60 秒一次。所以「瞬时 OOM」在监控上可能只表现为一条毛刺，真正可靠的证据是 memory.events 里的 oom_kill 计数和 docker inspect 里的 OOMKilled。

面试落点：「--cpus 1.5 落到 cgroup v2 就是 cpu.max 写成 150000 100000，v1 是 cfs_quota_us 150000 加 cfs_period_us 100000；--memory 落到 memory.max。判断容器内存要看 memory.current 和 memory.events，不能看 free，因为 /proc/meminfo 没隔离。CPU 被限流看 cpu.stat 的 nr_throttled。」

模块 5

镜像分层与 overlay2：lowerdir、upperdir、merged

「docker 的镜像为什么能共享」和「overlay2 的四个目录分别是什么」，这两个问题经常连着问。前者考概念，后者考你有没有真的进 /var/lib/docker 看过。

镜像是一串只读层，每层是上一层的一个 diff。容器启动时，在这些只读层之上再加一个可写层，然后用联合文件系统把它们叠成一个完整视图。overlay2 就是 Docker 默认的联合文件系统驱动（老环境可能是 overlay，再老是 aufs/devicemapper，新内核上基本都是 overlay2）。

目录放什么能不能直接改
diff这一层自己的内容，只包含相对下层的增量能，但改了会破坏层的一致性，不要动
merged联合挂载后的完整视图，容器的根目录就是它这就是容器里看到的 /
workoverlayfs 自己用的工作目录，做原子替换时的中转不能，动了会挂
l短符号链接，指向各层的 diff 目录存在的意义是缩短 mount 参数长度（有长度上限）
link这一层的短标识，就是 l/ 里那个名字只读

挂载参数长这样：lowerdir=A:B:C,upperdir=D,diff,workdir=E。lowerdir 可以有多个，冒号分隔，顺序是从上到下——最左边是离可写层最近的那一层。官方文档写的 overlay2 下层数量上限是 128 层，超过这个数就要合并层（以你环境的存储驱动文档为准）。这也解释了一个实践建议：镜像层数不要太多，不是道德要求，是有硬上限。

# 看一个容器的联合挂载参数（最直接的证据）
docker inspect -f '{{json .GraphDriver.Data}}' web | tr ',' '\n'

# 该容器在宿主机上的目录结构
ID=$(docker inspect -f '{{.Id}}' web)
ls /var/lib/docker/overlay2/$ID/
ls /var/lib/docker/overlay2/l/ | head

# 镜像每层做了什么、多大
docker history --no-trunc myapp:1.0
docker image inspect myapp:1.0 -f '{{len .RootFS.Layers}} 层'

# 看某层到底加了哪些文件（不用装工具也能看）
ls /var/lib/docker/overlay2/<layer-id>/diff

为什么 RUN rm -rf /tmp/big 不减镜像体积？因为这条指令产生的是新的一层，里面只有一个「删除」的白障记录（whiteout），下层的那几个 G 还在，只是被遮住了。镜像总大小是所有层之和，遮住不等于删掉。要真的变小，只能让「产生」和「删除」发生在同一层（同一条 RUN 里），或者用多阶段构建，让最终镜像根本不包含那个中间产物。

一个排查技巧：镜像突然大了几百兆，先 docker history 看哪一层异常，再进那层的 diff 目录按大小排序找凶手。常见的是 apt 缓存没清、日志文件被打进镜像、构建时 COPY . . 把 .git 和本地 node_modules 带进去了。

面试落点：「镜像是一串只读层，容器在最上面加一个可写层，overlay2 把它们联合挂载成 merged 视图。目录上 diff 是本层增量，merged 是挂载后的完整视图，work 是 overlayfs 内部用的，l 是短链接用来压缩 mount 参数长度。所以 RUN rm 只能遮住下层文件，减不了体积，得靠同层清理或多阶段构建。」

模块 6

写时复制：改一个 1G 文件的第一个字节，要复制 1G

「容器里的写为什么慢」「为什么容器一删数据就没了」，这两个问题的答案都在 copy-up 里，而 copy-up 的粒度是整个文件，不是块。

流程是这样：容器要修改一个位于只读层的文件时，overlayfs 先把整个文件从 lowerdir 复制到 upperdir，然后在副本上做修改。这个动作叫 copy-up。它带来三个直接后果：

  • 第一次写大文件很慢。改一个 1G 日志文件的最后一个字节，也要先把 1G 完整复制一遍，磁盘 IO 和空间都翻倍。
  • 空间会超预期。容器里看着只改了几个小文件，宿主机上可写层可能涨了好几个 G。
  • 可写层是容器独占的。同一镜像起的十个容器，各自有一份可写层，谁改谁的，互不影响——这也是容器「无状态」的基础。
# 容器可写层改了什么（相对镜像）
docker diff web
# A 新增  C 修改  D 删除，只有这三类

# 可写层实际占了多少
docker ps -s
# SIZE 是可写层，VIRTUAL SIZE 是镜像层加可写层

# 在容器里写大文件，然后对比宿主机目录增长
docker exec web dd if=/dev/zero of=/data/big bs=1M count=512
du -sh /var/lib/docker/overlay2/$ID/diff

所以数据库、消息队列、日志采集的缓冲目录，全都不应该落在容器可写层。原因不只是性能：容器被删除、被重建、被调度到别的机器，可写层就没了。Kubernetes 里 Pod 重建是最常见的操作，写在可写层的数据等于扔进垃圾桶。正确做法是挂 volume（本地或网络存储），让数据的生命周期独立于容器。

写法数据在哪容器删了还在吗适合什么
直接写容器路径可写层（overlay2 upperdir）不在临时文件、缓存，丢了无所谓的
volume/var/lib/docker/volumes/<name>/_data在数据库、上传文件、需要备份的数据
bind mount宿主机上你指定的任意路径在配置文件、开发时的代码挂载、宿主机已有的数据目录
tmpfs内存不在，且重启就没了敏感临时数据、需要极低延迟的缓存

还有一个反模式：用 docker commit 把容器的修改固化成新镜像。它看起来很方便——进去装个软件、改个配置、提交一下。问题是这个过程不可复现、不可审计、没有构建缓存，而且会把可写层里的日志、临时文件、密钥一起打包进去。面试里被问「怎么把容器改动持久化」，正确答案是改 Dockerfile 重建，不是 commit。

copy-up 还有一个隐蔽的坑：inode 变了。容器启动时改了某个被进程打开的文件（比如配置文件），进程持有的还是旧 inode，读到的还是旧内容。所以「我明明改了配置，进程没生效」在容器里比在物理机上更常见——restart 容器比 reload 更可靠，因为 restart 会重新做一次挂载和 copy-up。

面试落点：「overlay2 的写时复制粒度是整个文件，改只读层里的文件要先把整个文件复制到可写层，所以改大文件又慢又费空间。可写层是容器独占的，容器一删就没了，所以持久化数据必须挂 volume 或 bind mount。想固化改动应该改 Dockerfile，不是 docker commit。」

模块 7

网络：docker0、veth 和那条 DNAT 规则

「-p 8080:80 是怎么生效的？」这题的标准答案是「iptables 做了端口映射」，但再往下问「那 docker-proxy 进程是干什么的」「为什么容器之间用容器名 ping 不通」，就开始分层了。

模式网络栈典型用途注意
bridge（默认）独立 netns，接在 docker0 网桥上，分配 172.17.0.0/16 的地址（以你环境为准）绝大多数单机场景要访问外网靠 NAT；跨容器通信走网桥
host直接用宿主机 netns性能敏感、需要看到真实客户端 IP-p 直接失效，因为已经没有独立的端口空间了；端口冲突就是真冲突
none只有 lo完全离线的计算任务、自定义网络方案没有 eth0，什么都不通，得自己配
container:<id>共享另一个容器的 netnssidecar 模式，比如代理、抓包两个容器共享 IP 和端口，会抢端口

bridge 模式的实现拆开是三样东西。第一是 veth pair：一对虚拟网卡，一头插在容器的 netns 里（容器内看到 eth0），另一头插在宿主机的 docker0 网桥上。从容器发出的包从一头进、另一头出，进入宿主机的协议栈。第二是 网桥：docker0 是个二层交换机，负责同一网段内的转发和 ARP。第三是 NAT 规则：出方向做 SNAT（把容器源地址换成宿主机地址），入方向做 DNAT（把宿主机的 8080 转到容器的 80）。

# 看网桥和挂在它上面的 veth
ip -br link show type bridge
bridge link show master docker0

# 端口映射对应的 DNAT 规则（-n 不解析，看得更清楚）
iptables -t nat -S DOCKER
# 典型长相：-A DOCKER ! -i docker0 -p tcp --dport 8080 -j DNAT --to-destination 172.17.0.2:80

# 出方向的 SNAT（MASQUERADE）
iptables -t nat -S POSTROUTING | grep -i masq

# 有没有 docker-proxy 在监听（userland-proxy 开着就有）
ps -ef | grep docker-proxy | grep -v grep
ss -lntp | grep 8080

docker-proxy 的存在经常被误解。它是用户态的端口转发进程，作用是兜底：当 iptables 的 DNAT 路径因为某些原因走不通时（比如流量来自宿主机本机、或者内核模块没加载、或者 hairpin NAT 场景），由它来接管。关掉 userland-proxy 之后只剩 iptables 规则，性能略好、规则更干净，但某些「从宿主机访问映射端口」的场景会失效。这个取舍要能说出来，而不是简单说「proxy 是多余的」。

容器间 DNS 是另一个高频坑。默认的 bridge 网络不带自动服务发现，容器之间只能用 IP 互访，或者用已经废弃的 --link。你自己 docker network create 出来的自定义 bridge 才会内嵌一个 DNS，监听在 127.0.0.11，把容器名和网络别名解析成 IP。所以「同一个 compose 文件里的服务能用服务名互访」不是因为它们在同一台机器，而是因为 compose 建了一个自定义网络。

还有一条常被问的：容器怎么访问宿主机上的服务？不能写 localhost，那指向容器自己。bridge 模式下宿主机在容器里的网关地址一般是 172.17.0.1（用 docker network inspect 看 Gateway 字段更准）；较新版本的 Docker 支持 --add-host=host.docker.internal:host-gateway 自动填这个地址。别硬编码 IP，换台机器就错。

面试落点：「默认 bridge 下每个容器有独立 netns，通过 veth pair 接到 docker0，出方向 SNAT、入方向 DNAT 做端口映射，userland-proxy 是兜底路径。host 模式共享宿主机网络栈，-p 就没意义了。容器名互相解析只有自定义网络才有，默认 bridge 不支持，因为内置 DNS 只在自定义网络里启用。」

模块 8

存储：volume 和 bind mount 不是一回事

「-v 和 --mount 有什么区别」是个很细的问题，但它能区分「照抄命令」和「读过文档」。更实用的是第三个问题：为什么生产上更推荐 volume 而不是 bind mount？

维度volumebind mount
存在哪Docker 管理的目录，默认 /var/lib/docker/volumes/<name>/_data宿主机上任意路径，你说了算
谁创建Docker 创建并管理，可以匿名也可以命名必须自己保证目录存在（-v 会自动建，--mount 不会）
可移植性好，换机器不用改路径差，依赖宿主机的目录结构和权限
备份用临时容器 tar，或者直接打包目录直接备份那个路径，最直观
典型用途数据库数据、需要长期保留的业务数据配置文件、开发时挂代码、宿主机已有的日志目录
权限问题由 Docker 初始化，属主相对可控宿主机上的 UID 直接映射进容器，很容易权限不足

语法上的差别值得记一下：-v 是位置参数，三个字段用冒号分隔（宿主路径:容器路径:选项），路径不存在时会自动创建目录——包括你手滑写错路径的时候，于是容器起来了、数据写进了一个空目录，排查半天。 --mount 是键值对，语义更明确，路径不存在会直接报错。所以脚本里更推荐 --mount，因为它失败得早。

# 命名卷：Docker 管理，推荐用于数据
docker volume create pgdata
docker run -d --name pg -v pgdata:/var/lib/postgresql/data postgres:16

# 同样的意思，用 --mount 写（注意 type 和 source）
docker run -d --name pg2 \
  --mount type=volume,source=pgdata,target=/var/lib/postgresql/data postgres:16

# bind mount：宿主路径必须存在（--mount 不会帮你建）
docker run -d --name web \
  --mount type=bind,source=/etc/myapp,target=/app/conf,readonly nginx

# 看容器挂了什么、卷在哪
docker inspect -f '{{json .Mounts}}' pg
docker volume inspect pgdata

# 备份一个卷：起个临时容器把两边都挂上
docker run --rm -v pgdata:/from -v $(pwd):/to alpine \
  tar czf /to/pgdata-$(date +%F).tgz -C /from .

权限问题在 bind mount 上特别常见：容器里进程以 UID 1000 跑，宿主机上的目录属主是 root，写就报 Permission denied。这不是 Docker 的 bug，是 Linux 权限在正常工作。解决办法有三个方向：改宿主机目录属主、让容器用匹配的 UID 跑（镜像里 USER 或 --user），或者干脆换成 volume 让 Docker 初始化。在 SELinux 开启的系统上还要加 :z 或 :Z 重新打标签，否则即使权限对了也读不到。

匿名卷是最容易被忽略的磁盘杀手。docker run -v /data 这种只写容器路径的写法会创建一个匿名卷，名字是一串哈希，容器删了它也不会自动删（除非 docker rm -v）。跑了几百次 CI 之后，/var/lib/docker/volumes 能吃掉几十 G，而 docker ps -s 里什么都看不出来。定期 docker volume ls -f dangling=true 清一下。

面试落点：「volume 由 Docker 管理，位置固定、可移植、适合存数据；bind mount 直接映射宿主机路径，适合配置和开发调试，但依赖宿主机的目录和权限。语法上 -v 会自动创建不存在的目录，--mount 不会，所以脚本里更安全。生产上数据库用 volume，配置文件用 bind 且只读挂载。」

模块 9

构建缓存：Dockerfile 的顺序就是构建速度

「为什么我改了一行代码，构建要重新下依赖？」因为 Dockerfile 的指令顺序错了。缓存的失效是链式的：某一层失效，它后面所有层都失效。

规则很朴素：每条指令产生一层，Docker 在构建时逐层比对，命中缓存就复用。比对的依据包括指令本身、父层 ID，以及 COPY/ADD 时文件内容的校验和。所以 COPY . . 是最毒的一行：只要项目里任何一个文件变了（包括编辑器生成的临时文件、日志、.git 里的东西），这一层就失效，后面的 npm install 全部重跑。

常见写法问题改成
先 COPY . . 再装依赖改一行业务代码，依赖全重装先 COPY 依赖清单，装完再 COPY 源码
RUN apt-get update 和 install 分两条缓存导致 update 用旧的索引，装包 404合并成一条，并在同一条里清缓存
RUN apt-get install 后不清理包缓存留在层里，镜像大几百兆同层 rm -rf /var/lib/apt/lists/*
单阶段构建，编译工具链留在镜像里最终镜像包含 gcc、源码、构建缓存多阶段构建，只 COPY 产物
没有 .dockerignore把 .git、node_modules、日志打进构建上下文加 .dockerignore，构建上下文越小越快
# 依赖清单单独一层：代码变了也不影响这一层
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .

# 多阶段：编译环境留在 builder 里，产物才进最终镜像
FROM golang:1.22 AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

FROM alpine:3.20
COPY --from=builder /out/app /usr/local/bin/app
ENTRYPOINT ["/usr/local/bin/app"]

# 构建时看清缓存命中情况，别靠猜
docker build --progress=plain -t myapp:1.0 .
docker build --no-cache -t myapp:1.0 .

# 清构建缓存（只清缓存，不动镜像）
docker builder prune

多阶段构建解决的不只是体积，还有安全：最终镜像里没有编译器、没有源码、没有测试依赖，攻击面小很多。配合 FROM scratch 或者 distroless 基础镜像，能把镜像压到几十兆。

BuildKit 之后多了一个更实用的能力：RUN --mount=type=cache，可以把包管理器的缓存目录挂进来，跨构建复用，但不写进最终镜像。这比「把缓存目录删掉」高明一个层次——既快又干净。另外 --mount=type=secret 可以让私有仓库的 token 只在构建时可见，不留在任何一层的历史里。这一点在面试里提一句，会显得你真的构建过东西。

不要在 Dockerfile 里写 ENV PASSWORD=xxx 或 ARG TOKEN 然后用在 RUN 里。它们会留在镜像的层元数据里，docker history --no-trunc 就能翻出来，推到公共仓库等于公开。要么用 BuildKit 的 secret 挂载，要么在运行时注入。

面试落点：「缓存是按层命中的，父层失效后面全失效。所以要把变化频率低的放前面：先 COPY 依赖清单装依赖，再 COPY 源码。apt 的 update 和 install 要合并到一层并在同层清理。最终镜像用多阶段构建，只把产物拷进去，既小又少攻击面。」

模块 10

10 个坑：面试官最爱在这里追问第二句

下面这些的共同点是：结论错得不明显，但方向一错，后面所有操作都是白费。每一条都能撑起一段三分钟的追问。

1
说容器是「轻量级虚拟机」
容器没有自己的内核，也没有硬件虚拟化层。共享内核决定了它启动快、密度高，也决定了它的隔离弱、不能跑异构系统。这句话一出口，后面问安全边界就答不了。
2
用 free 判断容器内存够不够
/proc/meminfo 默认不隔离，读到的是宿主机的。容器内存要看 cgroup 的 memory.current 和 memory.max，OOM 证据看 memory.events 和 inspect 的 OOMKilled。
3
以为 --cpu-shares 是 CPU 上限
它是相对权重，只在争抢时决定分配比例，空闲时容器照样能跑满所有核。要硬上限得用 --cpus（落到 cpu.max）。两个参数语义完全不同，混着说会被追问到崩。
4
用 RUN rm 来减小镜像
删除只在新层写了一条白障记录，下层的数据还在，镜像总大小不变。要么在同一层里清理，要么用多阶段构建让产物根本不进中间层。
5
把数据写在容器可写层
可写层跟着容器生命周期走，容器一删、Pod 一重建就没了。数据库、上传文件必须挂 volume。更隐蔽的是 copy-up：改大文件会把整个文件复制一遍，又慢又费空间。
6
认为 -p 在 host 网络下还生效
host 模式共享宿主机网络栈，没有独立的端口空间，-p 直接被忽略（多数版本连警告都不给）。端口冲突就是真冲突，和宿主机上其他进程抢。
7
在默认 bridge 网络里用容器名互 ping
默认 bridge 不带内置 DNS，只有自定义网络才有 127.0.0.11 那个解析器。--link 是已废弃的旧方案。要么建自定义网络，要么用 IP。
8
以为容器里的 root 就是宿主机的普通用户
默认情况下容器内 UID 0 就是宿主机 UID 0，只是被 capabilities、seccomp 削过。只有开了 userns-remap 或 rootless，UID 才真正错开。这个区别决定了逃逸的后果。
9
用 docker commit 固化改动
不可复现、不可审计、没有构建缓存，还会把日志、临时文件、密钥一起打包。正确做法是改 Dockerfile 重新构建，commit 只适合临时试验。
10
把 -v 写成宿主机不存在的路径
-v 会自动创建目录，于是容器正常启动、数据写进空目录、配置全部丢失，而日志里一句报错都没有。脚本里用 --mount，路径不存在会直接失败。

面试落点：这些坑不要一次全倒出来。挑一个跟你经历有关的，讲成「当时的判断 → 造成的现象 → 后来怎么定位 → 改成了什么」。第四段最重要，它证明你更新了自己的判断方式，而不是记住了一个结论。

自测

六道题

1. 容器以 --memory=2g 启动，进入容器执行 free -h 显示 total 128G。最合理的解释是？
正确答案：/proc/meminfo 未隔离。容器共享宿主机内核，/proc 下的很多文件仍然是宿主机的视图（部分发行版会用 lxcfs 挂载来伪造）。要确认限制，直接读 /sys/fs/cgroup/memory.max（v2）或 memory.limit_in_bytes（v1），或者看 docker inspect 的 HostConfig.Memory。
2. 容器退出码是 137，下面哪个原因不可能造成它？
正确答案：优雅退出返回 0。137 = 128 + 9，表示进程被信号 9（SIGKILL）终止。OOM、docker stop 超时后的强杀、手敲 kill -9 都会产生它；而收到 SIGTERM 后正常退出、返回 0，退出码就是 0，重启策略为 always 时仍会被拉起，但状态显示的是 Exited (0)，不是 137。
3. 容器要修改一个位于镜像只读层的 1G 文件里的一个字节，overlay2 会怎么做？
正确答案：复制整个文件。overlayfs 的 copy-up 粒度是文件，不是数据块。所以第一次写大文件会有一次完整的复制开销，磁盘空间也会翻倍。这也是数据库、日志目录不能放在可写层的原因之一——除了数据会随容器消失，性能也不合适。
4. 在 cgroup v2 环境下，docker run --cpus=1.5 最终写进 cpu.max 的值是？
正确答案：150000 100000。cpu.max 的格式是「配额 周期」，单位都是微秒，默认周期 100000 微秒（100ms）。1.5 核意味着每个周期最多用 150000 微秒的 CPU 时间。v1 里对应的是 cpu.cfs_quota_us=150000 与 cpu.cfs_period_us=100000 两个文件。
5. 两个容器用默认 bridge 网络启动，直接 ping 容器名 失败，最可能的原因是？
正确答案：默认 bridge 没有内嵌 DNS。Docker 只在用户自定义的 bridge 网络里启用内嵌 DNS（监听 127.0.0.11），把容器名和网络别名解析成容器 IP。默认 bridge 上只能用 IP，或者用已废弃的 --link。所以「同一个 compose 文件里的服务能用服务名互访」，原因是 compose 创建了自定义网络。
6. 关于 runc 在容器启动过程中的角色，下面哪个说法是对的？
正确答案：创建后退出。runc 是 OCI 运行时的参考实现，一次性的：读 config.json、建 namespace 和 cgroup、切根、exec 应用，然后退出。应用进程被 reparent 到 containerd-shim 名下，所以 dockerd 或 containerd 重启不会杀掉容器。拉镜像和准备 rootfs 是 containerd 的活。
