日志系统面试：ELK、Loki 与成本这道必答题

日志平台的难题不是收集，是存多久、怎么检索、谁为成本负责。

读之前先答一句：一次报错，你要多久才能在日志里定位到那一条？
开始前

三个现场：日志这件事，出问题的时候才知道它没做好

「用户投诉下单失败，我查了半小时日志，一条都没查到。」「磁盘被日志打满，业务写不进去了。」「月底账单出来，日志存储比所有机器加起来还贵。」这三件事的共同点是：平时没人管日志，出事的时候它要么查不到、要么拖垮业务、要么拖垮预算。

现场直觉答案真实原因
查不到那条报错日志丢了大概率不是丢了，是查不动：关键字被分词切碎、时间范围选错、日志在多集群里、或者字段在采集时被压成了字符串没解析出来
磁盘被日志打满日志量突然变大了通常是一条异常被反复打印（循环里的 error、重试风暴），或者日志没做轮转、或者采集 agent 挂了导致本地堆积。量变大只是表象
账单上存储最贵日志本来就多索引比原文贵。全文索引会额外存倒排结构和列存结构，加上副本，实际占用可能是原始日志的很多倍——倍数取决于你的字段结构和 mapping，必须实测
采集只解决「有没有」
把日志收上来是最简单的一步。真正决定这个平台好不好用的是后三步：能不能查到、查得快不快、存得起多久。
索引模型决定成本曲线
ELK 对内容建全文索引，检索强、代价高；Loki 只对标签建索引、内容压缩存储，写入和存储的开销低得多，代价是全文检索慢。
日志的价值随时间衰减
出错那一刻的日志价值最高，一周后基本只剩合规价值。保留策略本质是在给「价值衰减」定价，而不是简单地「存久一点更安全」。

这一篇按数据的流向组织：先分清四类日志（它们的保留期和检索需求完全不同），然后是采集、传输缓冲、存储与索引（这一节是全文的重点，会把 ES 和 Loki 的差异讲透），接着是三套查询语法、结构化规范、保留期与降采样、日志告警，最后是那道必答的成本题——「1TB/天 是怎么算出来的」。

先把一个普遍的错误认知纠正掉：「日志系统就是把日志存起来，需要的时候 grep」——这句话在小规模时成立，在每天几百 GB 以上就不成立了。规模上去之后，你需要回答三个问题：存多久（合规 vs 成本）、怎么检索（全文索引还是标签索引）、谁为成本负责（集中平台还是业务团队分摊）。这三个问题答不上来，平台一定会先变成成本问题，然后变成稳定性问题。

面试怎么答：「我理解日志系统的难点不在收集，在三个权衡：保留期（合规要求 vs 存储成本）、检索方式（全文索引强但贵，标签索引省但全文查不动）、以及成本归属（集中平台容易变成无底洞，最好能按业务线分摊）。所以我一般会先按日志类型分级——审计日志长期留存、业务日志中等、调试日志短期甚至采样——再决定用什么存储。」

模块 1

日志的四层：它们的保留期和检索需求完全不一样

把「日志」当成一类东西，是后面所有决策出错的根源。真实环境里至少有四层，它们的保留期要求、检索频率、丢失后果差别极大。混在一起存，结果就是：最贵的地方存了最没用的数据，最该留的反而被一起删了。

层次内容检索频率丢失后果保留倾向
业务日志订单创建、支付结果、风控决策这类有业务语义的记录中（对账、客诉、运营查询）可能引发资损争议、无法对账较长，且常需要独立归档
应用日志程序运行信息：INFO/WARN/ERROR、慢查询、依赖调用结果高（排障时）排障失去依据，但通常不直接造成损失短期热存（天级）+ 中期冷存
系统日志syslog、journald、内核日志、容器运行时、节点 agent低（出硬件/内核问题时才看）排查底层故障变困难中期，量通常不大
审计日志谁在什么时候对什么做了什么操作（登录、权限变更、删除动作）极低（事故事后追溯）合规风险，可能直接影响审计结论最长，通常要求不可篡改、独立存储

这个分层的实际用途是分流：不同层走不同的管道、不同的存储、不同的保留期。具体来说——审计日志单独一路，写入后基本不删，且要防止被业务应用篡改（写权限分离、落到独立账号下的存储）；业务日志可以结构化后单独建索引，因为它经常要按订单号精确查；应用日志量最大、价值衰减最快，是降采样和缩短保留期的主要对象；系统日志量小，跟随即可。

一个常见的错配：把 DEBUG 日志和业务日志混在一个索引里，然后给它们同样的保留期。DEBUG 日志的量通常是业务日志的几十倍，但它的价值窗口只有几小时——出问题的时候看，看完就没用了。给它们一样的保留策略，等于用最贵的存储去存一堆再也不会被看的数据。分流的最小改动：按级别拆索引或拆流，DEBUG 单独一条、保留两三天，ERROR 和业务日志保留三十天以上。

还有一个判断方法值得记住：问「这条日志一年后还有人查吗」。答「会」的，通常是业务日志和审计日志，需要冷存归档、需要能被检索（哪怕慢）；答「不会」的，是应用和调试日志，它们的保留期应该由「排障需要回溯多久」决定——一般覆盖一个发布周期加一点余量就够了，不需要按年算。

面试怎么答：「我先把日志分四层：业务、应用、系统、审计。它们的需求完全不同——审计日志留存最长且要防篡改，业务日志要能按业务主键查、常需要中长期留存，应用日志量最大但价值衰减最快，是降采样的主要对象。做平台时我会按层分流：不同管道、不同存储、不同保留期，而不是统一收进来统一存。」

模块 2

采集：agent 选型、多行合并与字段规范

采集这一层的技术难点只有两个：多行怎么合并（一条 Java 异常栈被切成几百条，日志系统就废了一半），以及元数据怎么补（一条日志如果不知道来自哪个服务、哪个 Pod、哪个环境，它几乎没有检索价值）。

agent特点典型场景
FilebeatGo 写的轻量采集器，资源占用小，输出到 Elasticsearch / Logstash / Kafka 都方便以 ES 为存储的主机日志采集
Fluent BitC 实现，内存占用很低，插件覆盖广，容器场景使用普遍K8s 集群内的日志采集（常以 DaemonSet 部署）
FluentdRuby 实现，插件生态最丰富，可用作聚合层做清洗和路由需要复杂解析与多路分发的中间层
Promtail面向 Loki 的采集器，负责读文件、打标签、推给 LokiLoki 方案下的标准采集组件
VectorRust 实现，定位是可编程的数据管道，采集 + 转换一体希望减少组件层数、把清洗前移的场景

多行合并的规则说起来很简单：以「新日志开始的行」为界，把后续不属于新日志的行并到上一条。实践中通常用「行首是否是时间戳」来判断——行首匹配 ^\d{4}-\d{2}-\d{2} 或 ^\[ 的是新日志，其余（栈帧、Caused by:）合并进去。也可以反过来配「以什么结尾算结束」，但可靠性不如前者。

# Filebeat 风格的多行配置（思路示例，参数名以你版本为准）
multiline.type: pattern
multiline.pattern: '^[0-9]{4}-[0-9]{2}-[0-9]{2}'   # 行首是日期 = 新日志
multiline.negate: true                             # 不匹配 pattern 的行...
multiline.match: after                             # ...合并到上一条之后

# Fluent Bit 风格：用 parser 定义首行规则
[MULTILINE_PARSER]
    name          java_stacktrace
    key_content   log
    rule          "start_state"   "/^\d{4}-\d{2}-\d{2}/"  "cont"
    rule          "cont"          "/^(?!\d{4}-\d{2}-\d{2})/" "cont"

容器场景的采集位置要清楚：容器把日志写到 stdout/stderr，容器运行时把它落到节点上的文件，kubelet 再在 /var/log/containers/ 下建符号链接指向真实文件（文件名里带 namespace、pod、container 信息）。所以采集器读的是节点上的文件，不是进容器里去读——这一点决定了它必须以 DaemonSet 形式每节点一个，也决定了它天然能看到同节点上所有 Pod 的日志（这是一个安全边界问题，多租户场景要注意）。

元数据补充是容器日志的价值所在。光有一行文本没用，必须补上 namespace、pod、container、node，以及 Pod 上的业务标签（app、env、version）。这些靠采集器调 Kubernetes API 做 enrich 得到。这里有个成本控制点：不要把 Pod 的所有 label 都当索引字段，只挑检索真正需要的几个——因为每多一个索引字段，写入成本就多一份。

# K8s 采集时补充元数据（Fluent Bit 风格，参数以版本为准）
[FILTER]
    Name                kubernetes
    Match               kube.*
    Merge_Log           On            # 把 JSON 日志解析后合并进顶层字段
    Keep_Log            Off
    Labels              On            # 只保留需要的 label，别全开
    Annotations         Off

# 采集状态自查：有没有读不动、有没有堆积
# Filebeat 自身指标里有 harvester 数量、发送队列长度、ack 延迟
curl -s localhost:5066/stats | head -40
一个几乎必踩的坑，值得单独记：日志轮转与采集位点冲突。采集器靠「文件 + 偏移量」记录读到哪了，靠 inode 或路径识别文件。如果日志轮转把文件改名/压缩/删除，或者容器重建导致文件消失，位点就对不上了——表现是「日志看起来丢了」或者「重复采集了一遍」。缓解办法：让采集按路径通配符识别、轮转策略用 copytruncate 或直接让应用写到 stdout 由运行时管理、以及给采集器配置「关闭太久的文件句柄要释放」这类参数（具体项以你使用的 agent 文档为准）。

面试怎么答：「采集层的两个难点是多行合并和元数据补充。多行用『行首是时间戳即为新日志』的规则把异常栈合并成一条，否则一条栈变几百条，后面怎么查都查不动。容器场景下采集器以 DaemonSet 部署、读节点上 /var/log/containers 下的文件，再用 Kubernetes API 补上 namespace、pod、container 和业务标签——但只补检索真正需要的字段，因为每多一个索引字段写入成本就多一份。另外要注意日志轮转和采集位点冲突会造成丢日志或重复采集。」

模块 3

传输与缓冲：削峰、背压，以及「丢哪种日志」的取舍

采集器直连存储是很多小规模方案的默认做法，它的致命问题是：下游一挂，上游就积压。积压要么撑爆采集器的内存和磁盘缓冲，要么触发丢弃——而丢弃是无差别的，审计日志和调试日志一起丢。所以传输层的核心不是「传得快」，是「有地方堆、并且知道该丢谁」。

机制作用代价
消息队列缓冲（Kafka 等）削峰：下游慢时堆在队列里，下游恢复后追平；同时天然支持多消费者（一路进 ES、一路进归档）多一个组件要运维；分区和消费者的并行度要设计
本地磁盘缓冲网络断时不丢，恢复后补传占本地磁盘；缓冲满了仍然要决策
背压下游慢时向上游施加压力，让采集降速降速意味着应用侧写日志可能变慢（如果应用同步写且管道打通了的话）
限流 / 丢弃保护下游不被打垮丢什么必须有明确策略，不能随机丢

为什么强调「丢什么」要预先定义？因为在真正的故障里，日志量往往是爆炸的——一个依赖超时会让所有实例在几秒内打出成千上万条 ERROR，这正好是下游最脆弱的时候。如果没有策略，结果是：最关键的故障期日志，恰恰是最可能丢的那些。所以按级别分流在这里第二次发挥作用：把 ERROR、审计、业务日志放进「不丢」的队列（容量给足、消费者优先），把 DEBUG/INFO 放进「可丢」的队列（容量小、超了就丢）。

# 分流的两条管道（思路示意，具体配置以你使用的组件为准）
# 管道 A：关键日志 —— 容量大、副本多、不允许丢
app_error / audit / business  →  topic.logs-critical   →  写入 ES（或 Loki）+ 长期保留

# 管道 B：调试日志 —— 容量小、可丢弃、保留期短
app_debug / app_info         →  topic.logs-bulk       →  采样后写入，保留 3 天

# 采集端的关键开关（概念示意）
queue.mem.events: 4096           # 内存队列
queue.disk.max_size: 1GB         # 磁盘缓冲上限，撑不住就要决策
output.kafka.required_acks: 1    # 可靠性与吞吐的取舍
别把「不丢日志」当成一个绝对目标。这是一个成本极高的承诺：意味着你要为峰值（而不是均值）准备容量，还要为下游长时间不可用准备堆积空间。更务实的做法是分层承诺——审计和业务日志承诺不丢（所以给足容量、单独管道），调试日志明确承诺「可能丢」（并且让所有人知道）。面试里能说出「我们对不同级别的日志有不同的可靠性承诺」，比说「我们的日志一条都不丢」可信得多，也专业得多。

还有一个经常被忽略的传输层问题：时间戳该用谁的。日志在应用侧生成、在采集侧被读、在存储侧被索引，中间可能有几秒到几分钟的延迟。如果索引时间用的是到达时间，那么一次下游积压会让所有日志的时间戳挤在一起，排障时的时间线完全错乱。正确做法是用日志自身的时间戳（采集器解析出 timestamp 字段并作为索引时间），到达时间只作为辅助字段记录延迟。配置里要注意时区：所有组件统一用 UTC 存储、展示层再转本地时区。

面试怎么答：「传输层我一定会加缓冲，通常是消息队列，作用是削峰和隔离下游故障。关键是丢日志的策略要预先定义——故障期日志量会爆炸，而随机丢弃恰恰会丢掉最关键的那批。所以我按级别分流：ERROR、审计、业务日志进『不丢』的管道，DEBUG/INFO 进『可丢』的管道并明确告知团队。另外一个细节是索引时间戳必须用日志自身的时间，用到达时间的话，一次积压会让整个时间线错乱。」

模块 4

存储与索引：全文索引和标签索引，是两条完全不同的成本曲线

这是整篇技术含量最高的一节，也是 ELK 和 Loki 全部差异的源头。差别不在「谁更快」，在「写一条日志的时候，各自往磁盘上多写了什么东西」。理解了这个，选型、成本估算、坑位全都能顺着推出来。

Elasticsearch：给内容建索引

一条日志进 ES，大致发生三件事：① 分词并建立倒排索引——把文本切成一个个词（term），记录「哪个词出现在哪些文档里」，这样搜一个词能立刻定位到文档；② 为聚合和排序建列存结构（doc_values），没有它就没法按字段做统计；③ 保存原始文档（_source），用于返回结果和重建索引。再加上副本分片（高可用和查询吞吐需要），实际磁盘占用是原始日志的若干倍——这个倍数取决于你的字段数、分词方式、是否关闭 _source 和副本数，必须用自己的真实样本实测，不要套用任何现成数字。

代价换来的能力是：任意字段的全文检索、复杂聚合、低延迟。你可以搜「消息里包含 connection refused 且 service 是 api 且时间在昨晚两点到三点」，几秒内出结果，还能直接按错误类型做分布图。

Loki：只给标签建索引

Loki 的做法完全不同：它不解析、不索引日志内容。它只给每条日志流（stream）打一组标签（label），比如 {namespace="prod", app="api", env="prod"}，然后为这组标签建一个很小的索引；日志内容本身被压缩成 chunk，直接扔进对象存储。

查询时发生的是：先用标签把范围缩到少数几个 stream，再把对应的 chunk 拉出来解压，在里面做类似 grep 的扫描。所以它的成本结构反过来了——写入几乎不做功（只压缩），存储便宜（对象存储 + 高压缩率），但全文检索一个罕见字符串会很慢，因为要扫大量数据。

维度Elasticsearch（全文索引）Loki（标签索引）
写入做功重：分词、建倒排、建列存、写副本轻：只压缩成 chunk，写对象存储
存储开销高：倒排 + 列存 + 原文 + 副本（倍数需实测）低：压缩后的原文 + 很小的标签索引
检索能力强：任意字段全文检索、复杂聚合、低延迟弱一些：必须先靠标签缩小范围，然后在 chunk 里扫描过滤
致命弱点成本高、资源（内存）需求大、mapping 爆炸高基数标签：标签组合太多会导致 stream 爆炸、chunk 碎片化
适合需要全文检索和复杂聚合、量中等、能承受成本量大、查询模式固定（按服务/环境过滤再筛关键字）、成本敏感
查询语法Lucene / KQL / ES DSLLogQL
Loki 的第一号禁忌：不要把高基数的值当标签。标签的作用是「把数据切成有限的几块」，所以它的取值集合必须小且稳定。典型的错误是把 trace_id、user_id、request_id、pod_name（如果 Pod 频繁重建）放进标签——每来一个请求就产生一个新 stream，索引会膨胀到无法维护，chunk 也会碎成一地。正确做法：这些值留在日志行的内容里，用过滤算子（|= "abc123"）去匹配。判断标准很简单：这个字段的取值会不会随时间无限增长？会，就不能做标签。

反过来，ES 也有对应的第一号禁忌：字段爆炸（mapping explosion）。如果日志是 JSON 且字段不固定（比如每个请求带不同的自定义字段），ES 默认会为每个新字段建索引，字段数涨到几千上万之后，集群元数据和内存会出问题。解决办法是：固定 schema、用模板限定字段、对不需要检索的字段关掉索引（index: false）或者干脆存成一个字符串不解析。

# ES 侧：通过模板控制字段行为（思路示例）
{
  "mappings": {
    "dynamic_templates": [
      { "strings_as_keyword": {
          "match_mapping_type": "string",
          "mapping": { "type": "keyword", "ignore_above": 1024 }   # 长文本不建 keyword
      }}
    ],
    "properties": {
      "message": { "type": "text" },                    # 需要全文检索
      "trace_id": { "type": "keyword" },                # 只精确匹配
      "raw_payload": { "type": "object", "enabled": false }  # 不解析、不索引
    }
  }
}

# Loki 侧：标签设计示例（好 vs 坏）
# 好：取值有限且稳定
{namespace="prod", app="api", env="prod", level="error"}
# 坏：取值无限增长 —— 直接毁掉 Loki
{namespace="prod", app="api", trace_id="8f3a...", user_id="10293"}

面试怎么答：「两者的根本差别在写入时多写了什么。ES 会分词建倒排索引、建列存结构、保存原文，再加上副本，磁盘占用是原始日志的若干倍——倍数取决于字段结构和副本数，必须实测，我不套用现成数字。换来的是任意字段的全文检索和复杂聚合。Loki 只对标签建索引，内容压缩成 chunk 存对象存储，写入和存储的开销低得多，代价是全文检索要先靠标签缩小范围再扫描 chunk，所以查罕见字符串慢。各自的致命弱点也不同：Loki 怕高基数标签（trace_id、user_id 绝不能做标签，要留在内容里用过滤算子匹配），ES 怕字段爆炸（要固定 schema、用模板限制、不需要检索的字段关掉索引）。」

模块 5

查询语法：同一个意图，三种写法

面试让你「写一条查询」，考的不是背语法，是你能不能把「我要找什么」翻译成「先缩小范围、再过滤」。这个思路在三种语法里是通用的：先用索引字段把数据量砍下来，再对内容做匹配。顺序反了，查询就会慢到不可接受。

统一用这个场景举例：找生产环境 api 服务里、状态码大于等于 500、且消息里含 "connection refused"、但排除健康检查路径的日志。

# 1) Lucene（Elasticsearch 的 query_string 语法，Kibana 老式搜索框、很多工具都支持）
service:api AND env:prod AND status:>=500 AND message:"connection refused" NOT path:/health

# 2) KQL（Kibana Query Language，Kibana 现在的默认语法，更接近自然语言）
service: "api" and env: "prod" and status >= 500
  and message: "connection refused" and not path: "health"

# 3) LogQL（Loki）：先选择器，再过滤管线，最后格式化
{namespace="prod", app="api"}
  |= "connection refused"          # 行过滤：包含
  != "health"                      # 行过滤：排除
  | json                           # 解析 JSON 行，把字段提出来
  | status >= 500                  # 字段过滤
  | line_format "{{.message}}"     # 只输出消息

# LogQL 的指标查询（把日志变成时间序列，用于告警）
sum by (app) (rate({namespace="prod"} |= "ERROR" [5m]))
语法结构容易写错的地方
Lucene字段:值 + AND/OR/NOT + 引号短语 + 范围 [a TO b] 或 >=不加引号的短语会被分词拆开，connection refused 变成「包含 connection 或 refused」
KQL同上，但用小写 and/or/not，字段和值之间可以有空格它对类型更敏感：对 text 字段做等值匹配可能查不到，要匹配 keyword 子字段
LogQL标签选择器 {...} → 行过滤 |= != |~ !~ → 解析器 | json | logfmt → 字段过滤 → 格式化/聚合顺序不能乱：必须先有选择器；| json 之后才能用字段过滤；正则过滤（|~）比字符串过滤贵得多

LogQL 的管线顺序值得单独记一下，因为它是 Loki 性能的命门：选择器用索引（便宜）→ 字符串过滤在解压后扫描（中等）→ 正则过滤（贵）→ 解析和字段过滤（贵）。所以写查询的习惯是：把最能缩小范围的条件放在最前面。比如先 |= "order_id=12345" 再 | json，比先 | json 再过滤快得多——因为前者在解压阶段就扔掉了绝大部分 chunk。

一个通用的慢查询诊断思路：先看你的查询有没有用到索引。ES 里就是「条件里有没有命中索引字段、有没有用 wildcard 前缀通配（*abc 这种前导通配符无法有效利用倒排索引，非常慢）」；Loki 里就是「选择器里的标签够不够具体」。如果选择器是 {namespace="prod"} 然后靠内容过滤，那本质上是在扫全量。加一个 app="api" 的标签，可能就把扫描量砍掉一个数量级。

面试怎么答：「思路是共通的：先用索引字段缩小范围，再对内容做匹配，顺序反了一定慢。ES 侧我会写 Lucene 或 KQL，注意短语要加引号否则会被分词拆开，还有前导通配符没法有效用索引。Loki 侧写 LogQL，结构是标签选择器 → 行过滤 → 解析 → 字段过滤 → 格式化，顺序不能乱，而且要把最能缩小范围的条件放最前面，先字符串过滤再 json 解析比反过来快得多。另外 LogQL 支持指标查询，可以把日志转成时间序列直接用于告警。」

模块 6

结构化日志规范：让日志能被机器读，而不是被人读

「我们的日志是 JSON 的」——这句话十次里有五次是错的：外层是 JSON，message 里面还是一长串手拼的字符串。真正的结构化是「每个需要被检索和聚合的值都是独立字段」，而不是「日志被包在 JSON 里」。

字段要求为什么
timestampISO 8601，带时区，统一 UTC 存储；精确到毫秒以上跨服务串联的基础。没有时区的时间戳在跨时区机器上是灾难
level固定几个值（ERROR/WARN/INFO/DEBUG），全公司统一分流、降采样、告警全靠它。一会儿 level 一会儿 severity，规则就写不下去
service / app服务名，来自部署配置而不是硬编码检索的第一维度。它必须是标签/索引字段
trace_id贯穿一次请求的唯一 ID，从网关生成并透传跨服务定位的唯一钥匙。它应该是内容字段而不是标签（高基数）
env / namespace环境标识把生产和预发彻底分开，避免查错环境
message人读的一句话，不要把变量拼进去拼进去的变量无法聚合。变量应该作为独立字段
# 反例：外层 JSON，内容全靠手拼 —— 无法聚合、无法精确过滤
{"level":"error","message":"user 10293 order 88123 failed: connection refused, retry 3"}

# 正例：可检索、可聚合、可按字段告警
{
  "timestamp": "2026-10-21T02:13:47.512Z",
  "level": "ERROR",
  "service": "order-api",
  "env": "prod",
  "trace_id": "8f3a1c2e9b7d",
  "event": "order_create_failed",
  "user_id": 10293,
  "order_id": 88123,
  "error_type": "ConnectionRefused",
  "upstream": "payment-svc",
  "retry_count": 3,
  "message": "创建订单失败，上游连接被拒"
}

为什么强调「不要把变量拼进 message」？因为一旦拼进去，message 的取值就变成了无限集合——你没法按 error_type 做分布统计，也没法写「只告警 ConnectionRefused」这种规则，只能靠正则去扒字符串，而正则既慢又脆（上游改一下措辞就失效）。判断标准：这个值会不会被用于过滤或聚合？会，就必须是独立字段。

敏感信息是这一节最硬的红线。日志里出现密码、token、身份证号、手机号、银行卡号、完整请求体，是最常见也最严重的一类泄露渠道——因为日志的存储权限通常比数据库宽得多，而且会被复制到多个系统、被下载到本地、被贴进工单和聊天群。三条必须做的：① 框架层统一脱敏（在日志输出前对已知敏感字段做掩码，不能靠每个开发记得）；② 禁止打印完整请求/响应体，要打就打脱敏后的摘要；③ 把「日志里有敏感信息」当安全事件处理——发现后要清理历史日志，而不只是改代码。

还有两个规范细节值得写进团队的约定：第一，错误日志要带上下文而不是只带一句话。「connection refused」这种日志毫无价值，有价值的是「连谁失败、重试第几次、trace_id 是什么」。第二，同一个错误不要在多层重复打印——调用链上每一层都打一遍 ERROR，会让错误计数翻好几倍，告警阈值全部失真。约定是：抛出异常的地方打 ERROR 并带完整上下文，中间层不打或者打 WARN，最外层统一记录并返回。

面试怎么答：「结构化的标准是『每个需要被检索和聚合的值都是独立字段』，而不是『日志包在 JSON 里』。必须有 timestamp（ISO 8601 带时区、统一 UTC）、level（全公司统一枚举）、service、env、trace_id、以及业务字段。关键是不要把变量拼进 message——拼进去之后就没法聚合也没法精确告警，只能靠正则扒字符串。另外 trace_id 是高基数的，在 Loki 里不能当标签，只能放内容里用过滤算子匹配。最后是脱敏，敏感信息进日志是最常见的泄露渠道，要在框架层统一掩码，不能靠人记得。」

模块 7

保留期、冷热分层与降采样：给「价值衰减」定价

日志的价值随时间急剧衰减：刚发生的一小时里它是排障的关键证据，一周后基本只剩合规价值，一年后几乎没人会查。保留策略的本质，就是给这条衰减曲线定价——而不管不顾地「多存几天更安全」，最终一定会变成账单问题。

层次介质与特点适合放什么
热本地 SSD / 高性能块存储，查询秒级最近几个小时到几天，排障真正会查的窗口
温性能较低的存储，查询变慢但仍可用几天到几周，偶尔回溯
冷对象存储，成本低、查询慢（可能需要先「解冻」）几周到几个月，合规要求或低频审计
归档 / 删除只留压缩原始文件（不能被检索，需要时再导入），或直接删除超过保留期的数据

ES 侧通常用索引生命周期管理（ILM）来驱动这套流转：按索引年龄或大小，自动把索引从热节点迁到温/冷节点、收缩分片、做快照，最后删除。具体阶段名称和可用动作以你使用的版本文档为准，不要凭记忆写死。Loki 侧的保留则由压缩器（compactor）和保留配置驱动，同样以版本文档为准。

# ES 侧：生命周期策略的形状（参数名与阶段以版本文档为准）
{
  "policy": {
    "phases": {
      "hot":  { "actions": { "rollover": { "max_age": "1d", "max_primary_shard_size": "50gb" } } },
      "warm": { "min_age": "3d",  "actions": { "forcemerge": {}, "shrink": {} } },
      "cold": { "min_age": "30d", "actions": { "searchable_snapshot": {} } },
      "delete":{ "min_age": "90d", "actions": { "delete": {} } }
    }
  }
}

# 降采样的两种做法
# ① 采集端采样：DEBUG 保留 10%，ERROR 全量
# ② 存储端降采样：热存保留原始日志，冷存只保留「按小时聚合的错误计数 + 少量样本」

降采样是被低估的一招。它的依据是：冷数据几乎不会被「逐条查看」，只会被「统计和抽样」。所以热存保留全量原文，冷存保留聚合结果 + 每类错误的少量样本，就能在保留可追溯能力的同时把存储砍掉一个量级。具体能砍多少取决于你的聚合粒度和样本比例，这个比例要用真实数据实测，不要套用任何现成数字。

一个能立刻做的成本动作：按级别拆保留期。把 DEBUG/INFO 的保留期设成 2~3 天，WARN/ERROR 设成 30 天，审计日志单独走长期归档。这是改动最小、收益最明显的一步——因为在大多数系统里，DEBUG/INFO 占了日志量的绝大部分，而它们的价值窗口只有几小时。做之前先统计一下各级别的占比，用数据说服团队，比讲道理有效。

还有两个成本管理动作值得提：① 按业务线分摊——给每条日志打上业务标签，按月出各业务线的日志量和存储成本。这一步的意义不在「收费」，在让成本有归属：当一个团队看到自己的日志占了全公司三分之一，优化就会自然发生。② 设置写入限流和配额——单个服务 unlimited 地写日志，会挤占整个平台。给每个服务设一个合理的写入上限，超了就采样或拒绝，并通知该团队。

面试怎么答：「保留策略的本质是给日志的价值衰减定价。我的做法是按级别和类型拆保留期：DEBUG/INFO 两三天，WARN/ERROR 三十天，审计日志单独长期归档；存储上用冷热分层，热存放排障窗口，冷存放对象存储供低频审计。另外降采样很有效——冷数据几乎不会被逐条查看，所以冷存只保留按小时聚合的错误计数加少量样本。管理上我会按业务线出成本报表，让成本有归属，再配合单服务的写入配额防止一个服务挤占整个平台。」

模块 8

日志告警：从「出现关键字就告警」到「错误率超过阈值」

日志告警最常见的失败模式是噪声：「message 里含 error 就告警」——结果一天几百条，一周之后所有人都在心里把它过滤掉了。真正可用的告警，是把日志先变成指标，再对指标告警。

做法问题
关键字出现即告警（message: error）噪声极大。很多 error 是预期内的（参数校验失败、用户输入错误），单条出现完全不代表故障
按条数告警（5 分钟内 > 10 条）流量翻倍时条数自然翻倍，误报；流量低谷时又不报。条数不是归一化指标
按错误率告警（错误数 / 请求数 > 阈值）推荐。它不受流量波动影响，且和业务影响直接对应
按「新增错误类型」告警有价值但实现复杂：需要维护「已知错误」基线，适合作为补充
# LogQL：把日志变成比率，再做告警（推荐写法）
# 错误率 = 含 ERROR 的速率 / 全部日志速率
sum(rate({namespace="prod", app="order-api"} |= "ERROR" [5m]))
  /
sum(rate({namespace="prod", app="order-api"} [5m]))
  > 0.01          # 超过 1% 触发（阈值要按你的基线定）

# ES 侧：用 DSL 做聚合后由告警引擎判定（Watcher / 外部告警器，思路示例）
# 查询：按 5 分钟分桶，统计 level=ERROR 的 doc_count 与总 doc_count，算比率
# 判定：连续 2 个桶超过阈值才告警（避免单次抖动）

# 关键细节：分母不能为 0，低流量时段要加最小样本量条件
#   错误率 > 1% AND 5 分钟内总请求数 > 100

三个让告警真正可用的细节：① 连续窗口判定——单一个 5 分钟窗口超阈值可能是抖动，要求「连续两个窗口」或「10 分钟内有 3 个窗口超阈值」能砍掉大量误报。② 最小样本量——低流量时段（凌晨）分母很小，1 条错误就是 100%，必须加「总请求数 > N」的前提条件。③ 告警要带上下文——一条「错误率 3.2%」的告警没有用，有用的是「order-api 在 prod 环境错误率 3.2%，主要错误类型 ConnectionRefused，上游 payment-svc，示例 trace_id: 8f3a1c2e9b7d，runbook 链接：...」。告警的目标是让人能在三十秒内开始行动，而不是让人先花十分钟去查日志。

别指望日志告警覆盖「没日志」的情况。如果服务整个挂掉、或者采集链路断了，错误数会变成 0——按「错误率 > 阈值」的规则，此时一切正常。所以必须配一条「日志量骤降」的告警（比如某服务 5 分钟内的日志条数低于历史同期的很小比例，或者干脆为 0）。这类「没有数据」的告警，是所有基于日志的告警体系里最容易被漏掉、也最致命的一条。

还有一条边界要说清：能用指标做的告警，不要基于日志做。请求成功率、延迟、QPS 这些应该来自 metrics（Prometheus 一类），因为它们更稳、更便宜、聚合是在采集侧就完成的。日志告警适合的场景是「指标里没有的信息」——比如某个特定错误类型首次出现、某个业务的对账异常、审计类的违规操作。把两者混为一谈，会得到一套又贵又不准的告警。

{namespace="prod", app="api"} |= "ERROR" | json | status >= 500LogQL：先标签缩小范围，再行过滤，再解析字段过滤
sum(rate({namespace="prod", app="api"} |= "ERROR" [5m]))把日志转成时间序列，是指标化告警的基础
service: "api" and env: "prod" and status >= 500KQL：Kibana 默认语法，短语要加引号否则被分词拆开
service:api AND env:prod AND message:"connection refused" NOT path:/healthLucene：ES 的 query_string 语法，短语必须加引号
ls /var/log/containers/ | head容器日志在节点上的落盘位置，采集器读的就是这些文件
journalctl -u kubelet --since "10 min ago" -p warning节点侧兜底：采集链路本身出问题时从这看

面试怎么答：「我不用『出现关键字就告警』，噪声太大。做法是把日志先变成指标再告警——用 LogQL 的 rate 或者 ES 的聚合算出错误率（错误数除以总请求数），因为错误率不受流量波动影响，比按条数告警稳得多。三个细节：连续多个窗口超阈值才触发、低流量时段加最小样本量条件、告警内容要带错误类型、上游、示例 trace_id 和 runbook 链接。另外必须配『日志量骤降』的告警，否则服务整个挂掉时错误率是 0，看起来一切正常。能用指标做的告警就不基于日志做。」

模块 9

面试话术：1TB/天 是怎么算出来的

「你们日志一天多少？存储怎么估？」这题的正确答法不是报一个数字，是把估算过程讲出来。因为面试官知道你不可能记住准确的量，他想看的是：你有没有一套可复现的估算方法，以及你知不知道误差在哪。

第一步：测单位产出。选一个有代表性的实例（或一个 Pod），统计它在峰值时段每分钟写多少字节日志。注意是峰值不是均值——容量必须按峰值配。做法可以是直接看日志文件的增长，也可以看采集器上报的字节数。
第二步：乘规模和时长。单实例每分钟字节数 × 实例数 × 1440 = 每天的原始字节数。这一步要说明「实例数按峰值副本数算」，并且别忘了非应用日志（系统日志、审计、网关、中间件）通常也要单列。
第三步：乘存储放大系数。原始日志进存储后不是 1:1。ES 要算倒排索引、列存结构、原文和副本；Loki 要算压缩后的 chunk 加标签索引。这个系数必须用你自己的真实样本实测——拿一段有代表性的日志，写进去，看实际占用了多少字节，再反推系数。不同字段结构、不同压缩率，结果可以差很多，绝不能套用别人给的数字。
第四步：乘保留期并分层。热存天数 × 热存单价 + 冷存天数 × 冷存单价，再加上副本和快照的份数。如果是多集群、多环境，分别算再加总。
第五步：说出误差来源。这一步是加分项：峰值估低了、日志量随业务增长、异常期会翻好几倍、压缩率取决于日志重复度、以及「你算的是今天，下个季度会变」。敢说误差在哪，比报一个精确数字可信得多。
# 估算的骨架（系数必须实测，这里只给结构）
per_instance_bytes_per_min = 实测（峰值时段）
instances                  = 峰值副本数
raw_bytes_per_day          = per_instance_bytes_per_min * instances * 1440 * 日志种类数

# ES 侧
stored_bytes = raw_bytes_per_day * 索引放大系数(实测) * (1 + 副本份数)
cost_hot     = stored_bytes * 热存天数 * 热存单价
cost_cold    = stored_bytes * 冷存天数 * 冷存单价        # 冷存通常还要 + 检索时的解冻成本

# Loki 侧
stored_bytes = raw_bytes_per_day * (1 / 压缩比(实测)) + 标签索引大小

# 别忘了：快照/备份份数、跨区域复制、以及查询本身对资源的消耗
一个完整示范（把方法讲清楚，不编数字）：「我先测单位产出——挑一个有代表性的 Pod，在峰值时段统计它一分钟写多少字节，然后乘以峰值副本数和 1440，得到每天的原始量。接着乘存储放大系数，这个系数我一定是实测的：拿一段真实日志写进去，看实际占了多少，反推出来，因为字段结构和压缩率对它的影响非常大，我不套用现成数字。然后按冷热两档分别乘保留天数和单价，再加上副本和快照的份数。最后我会说明误差在哪：峰值可能估低、日志量会随业务增长、异常期可能翻好几倍、压缩率取决于日志的重复度。所以这个数是一个量级和一套方法，不是承诺。」

如果面试官追问「那怎么降成本」，按优先级给四招：① 按级别拆保留期（改动最小、收益最大）；② 减少无用日志（重复打印、循环里的日志、DEBUG 上线没关）——这一招常常能砍掉一半量；③ 降采样与冷热分层；④ 换存储模型（量大且查询模式固定的场景，从全文索引换成标签索引）。顺序很重要：先砍量，再谈换架构。因为量没砍下来就换架构，只是把成本从一种形式换成另一种形式。

面试怎么答：「我不背数字，我讲方法：测单位产出（峰值时段）→ 乘规模和时长 → 乘实测出来的存储放大系数 → 按冷热分档乘保留期和单价 → 最后说清误差来源。系数必须实测，因为字段结构和压缩率影响很大。降成本我按优先级：先按级别拆保留期，再砍无用日志（重复打印、线上开 DEBUG 常常能砍掉一半），然后降采样和冷热分层，最后才考虑换存储模型——量没砍下来就换架构只是换一种花钱方式。」

模块 10

10 个坑：每一个都会让日志平台变成负担

这一节的坑有个共同形状：每一条在规模小的时候都不明显，量上去之后才爆发——而那时改造成本已经很高了。

1
把 trace_id、user_id 这类高基数字段当 Loki 标签
标签的作用是「把数据切成有限几块」。取值会无限增长的字段做标签，会让 stream 爆炸、chunk 碎片化，索引膨胀到无法维护。高基数值必须留在日志内容里，用 |= 过滤算子匹配。
2
「message 含 error 就告警」
噪声极大，一周后所有人都在心里屏蔽它。正确做法是把日志转成指标再告警：算错误率（错误数/请求数），加连续窗口判定和最小样本量条件。
3
只配了「错误率过高」，没配「日志量骤降」
服务整个挂掉或采集中断时，错误数变成 0，看起来一切正常。基于日志的告警体系必须有一条「没有数据」的告警。
4
异常栈没做多行合并
一条 Java 栈被切成几百条，日志量虚高、检索结果被单条栈刷屏、按条数告警彻底失真。用「行首是时间戳即为新日志」的规则合并。
5
采集直连存储，没有缓冲也没有丢弃策略
下游一挂就积压，撑爆内存后随机丢弃——而随机丢弃恰恰会丢掉故障期最关键的日志。加消息队列缓冲，并按级别定义「谁可以丢」。
6
日志里打印敏感信息和完整请求体
日志的存储权限通常比数据库宽得多，还会被复制到多个系统、贴进工单。必须在框架层统一脱敏，不能靠每个开发记得；发现泄露要清理历史日志而不只是改代码。
7
所有日志同一个保留期，冷数据全在热存储
DEBUG 的量通常是业务日志的几十倍，但价值窗口只有几小时。按级别拆保留期是改动最小、收益最大的一步。
8
字段命名不统一，level / log_level / severity 三种写法
分流规则、降采样规则、告警规则全都写不下去——每一条都要写三个变体。字段规范要在平台侧强制，而不是靠约定。
9
把变量拼进 message
拼进去之后无法聚合也无法精确过滤，只能靠正则扒字符串，而正则既慢又脆。凡是需要被过滤或聚合的值，都必须是独立字段。
10
索引时间用到达时间而不是日志自身时间
一次下游积压会让所有日志的时间戳挤在一起，排障时时间线完全错乱。必须用日志自身的 timestamp 做索引时间，到达时间只作为辅助字段，并且全链路统一 UTC。

面试怎么答：挑一个你真的处理过的讲完整。「我印象最深的是多行合并。之前 Java 服务的异常栈没配合并，一条栈变成三百多条日志，结果有两个后果：一是按条数告警的阈值彻底失真，一次异常就打爆；二是检索的时候结果页全是栈帧，真正的错误原因被淹没了。我们后来统一在采集端配了『行首是时间戳即为新日志』的规则，日志量当天就降了一大截——具体降多少取决于你们的栈有多长，这个要自己测。这件事让我意识到，日志平台的很多『性能问题』其实是『数据质量问题』，先治理数据再谈扩容。」

自测

六道题

1. Elasticsearch 和 Loki 在索引模型上的根本差异是什么？
正确答案：建不建内容索引。ES 写入时要分词、建倒排索引、建 doc_values 供聚合、保存 _source，再加上副本，实际占用是原始日志的若干倍（倍数取决于字段结构和副本数，必须实测）。换来任意字段全文检索和复杂聚合。Loki 只对标签建很小的索引，内容压缩成 chunk 进对象存储，查询时先用标签选出 stream 再解压扫描，所以全文查罕见字符串慢。各自的第一禁忌也不同：Loki 怕高基数标签，ES 怕字段爆炸。
2. 在 Loki 里，下面哪个字段不适合作为标签（label）？
正确答案：trace_id。标签的作用是「把数据切成有限的几块」，所以取值集合必须小且稳定。trace_id、user_id、request_id 这类每请求都不同的高基数值，会让每个请求产生一个新 stream，导致索引膨胀、chunk 碎片化，直接毁掉 Loki。正确做法是让它们留在日志行的内容里，用 |= "xxx" 这样的行过滤算子去匹配。判断标准：这个字段的取值会不会随时间无限增长？会，就不能做标签。
3. 关于日志告警，下面哪种做法最可靠？
正确答案：先转指标，再告警。关键字告警噪声太大；按条数告警会随流量波动误报（流量翻倍条数自然翻倍），因为条数不是归一化指标。错误率（错误数除以请求数）不受流量影响，配合连续多个窗口才触发、低流量时段加最小样本量条件，稳定性高得多。另外必须配「日志量骤降」告警——服务整个挂掉或采集中断时错误数是 0，看起来一切正常。
4. 采集端没配多行合并，最直接的后果是什么？
正确答案：一条栈变几百条。异常栈的每一行（包括 Caused by 和每个栈帧）都会被当成独立日志。后果有三个：日志量虚高、检索结果被单条栈刷屏导致真正的错误原因被淹没、以及按条数配置的告警阈值彻底失真。解决办法是在采集端配多行规则，通常用「行首是否匹配时间戳」来判断新日志的开始。
5. 索引时间应该用哪个时间戳？
正确答案：日志自身的时间戳。如果用到达时间，那么一次下游积压或采集中断恢复后，所有补传的日志时间戳会挤在同一时刻，排障时的时间线完全错乱——你看到的「凌晨三点错误暴涨」可能只是「那时积压清完了」。同时全链路要统一用 UTC 存储、展示层再转本地时区，避免跨时区机器对不上。
6. 面试官问「你们日志一天 1TB，存储成本怎么估」，最好的回答方式是？
正确答案：讲方法，不背数字。面试官知道你记不住准确量，他想看的是可复现的估算方法和对误差的认知。关键点是：单位产出要按峰值而不是均值测；存储放大系数（ES 的倒排+列存+原文+副本 / Loki 的压缩率）必须用自己的真实样本实测，因为字段结构和压缩率影响极大，不能套用现成数字；最后主动说明误差来源（峰值估低、业务增长、异常期翻几倍、压缩率随重复度变化）。敢说误差在哪，比报一个精确数字可信。
