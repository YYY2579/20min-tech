开始前

三个现场：都写着 OOM，病因却在四个不同的地方

半夜收到的第一条消息是「Java 挂了，日志里全是 OutOfMemoryError」。这句话几乎没有信息量——OutOfMemoryError 是四个完全不同故障的共同结局，把它当成一种病来治，是所有错误动作的起点。

下面三个现场，几乎覆盖了面试里对 JVM 的全部追问。它们的共同点是：报错文案告诉你「哪里装不下了」，但没告诉你「是谁装进去的」。

现场直觉动作真实原因
容器被 OOMKilled，但监控显示堆只用了 40%内存不够，给容器加大 limit可能是对的，也可能是错的。堆只是进程的一部分。元空间、直接内存、线程栈、JIT 代码缓存、GC 自身结构、glibc 的 malloc 碎片全在堆外，它们都算进 cgroup
报错 unable to create new native thread，值班说「内存不够，加吧」调大 -Xmx，或者给机器加内存和堆没关系。线程数摸到了 ulimit、cgroup 的 pids 上限，或者可用虚拟内存已经不足以再给一个线程开栈。调大 -Xmx 只会让剩下的空间更少
CPU 打满，加了机器半小时后又打满业务量上来了，扩容先看吃掉 CPU 的线程叫什么名字。如果是 GC 线程，扩容只是把「每次都活不长」复制一遍；如果是业务线程死循环，扩容也只是多几个一起转
信号一：内存
看报错文案的后半句。Java heap space、Metaspace、Direct buffer memory、unable to create new native thread 是四个不同的账单。
信号二：CPU
先把进程 CPU 拆成线程 CPU。top -Hp 加线程号转十六进制，再用 jstack 对号入座，这一步比任何猜想都快。
信号三：停顿
GC 停顿表现是「周期性卡顿」而不是「持续变慢」。看 jstat -gcutil 的 FGCT 增长速率，比看 CPU 曲线更直接。
信号四：阻塞
CPU 不高、内存不高、但 RT 涨了，说明线程在等——连接池、线程池队列、锁、下游。这是四类里最容易被误判成「资源不够」的一类。

这一篇的顺序：先把堆和非堆这条线画清楚（这是所有后续判断的地基），再交代垃圾回收器的取舍与容器里那个绕不开的坑，然后按四类 OOM 逐个拆，接着是 CPU 飙高、工具箱、慢请求与池资源。每一节收在一句可以直接说出口的话上，因为面试问 JVM，想听的是你怎么把一个笼统现象切成可验证的几个分支，不是你能背多少个参数名。

一条必须先接受的常识：运维不需要读懂字节码，但必须知道「-Xmx 管不到的内存远多于它管得到的」。这句是整篇的地基。你在容器里看到进程被杀、堆还剩一半，第一反应不该是「JVM 内存泄漏」，而是「堆之外的某一块账没算进来」。

面试怎么答：「我看到 OOM 不会直接加内存。先看报错文案里的后缀判断是堆、元空间、直接内存还是线程创建失败，因为它们的修复方向完全相反——堆不够可能是泄漏也可能是配置，线程创建失败再加大堆只会更糟。」

模块 1

内存结构：先把「-Xmx 管不到什么」列全

大部分人对 JVM 内存的印象止于「一块堆，参数 -Xms 和 -Xmx」。这个印象在生产上是有害的：它让人以为堆调好了内存就调好了。而实际上 cgroup 或者 OOM killer 卡的是进程的常驻内存，堆只是其中的一项。

先说历史，因为它解释了为什么会有「元空间」这个词。JDK 7 把字符串常量池和静态变量从永久代移到了堆；JDK 8 彻底去掉了永久代（PermGen），把类的元数据放进本地内存的 Metaspace。这个改动带来的直接影响是：以前那种「-XX:PermSize 设小了导致 PermGen OOM」的故障消失了，取而代之的是 Metaspace 类型的 OOM，而且它默认没有明确的硬上限（默认只受本机可用内存约束，具体以你 JDK 版本的文档为准），所以在容器里它敢一路涨到把 limit 顶穿。

区域装什么谁决定大小撑爆了报什么
堆 Heap对象实例、数组；内部还有新生代（Eden + Survivor）与老年代的划分-Xms / -Xmx，或容器场景下的百分比参数OutOfMemoryError: Java heap space
元空间 Metaspace类的元数据：Klass 结构、方法字节码、运行时常量池等-XX:MetaspaceSize（触发首次 GC 的阈值）、-XX:MaxMetaspaceSizeOutOfMemoryError: Metaspace
压缩类空间开启压缩指针时 Klass 所在的区域，计入 Metaspace 总量之内-XX:CompressedClassSpaceSize同上，也在 Metaspace 的报错里体现
代码缓存 CodeCacheJIT 把热点字节码编译成的本地机器码-XX:ReservedCodeCacheSize不会直接叫 OOM，表现为「CodeCache is full」警告后 JIT 停止编译、性能塌下去
线程栈每个线程一份，方法调用的栈帧-Xss，单个线程大小 × 线程数创建不了新线程时：unable to create new native thread；单个线程递归太深是 StackOverflowError，不是 OOM
直接内存ByteBuffer.allocateDirect、Netty 的池化 ByteBuf、部分压缩/网络库的堆外缓冲-XX:MaxDirectMemorySize，默认值随 JDK 版本不同，建议显式指定OutOfMemoryError: Direct buffer memory
GC 与 JVM 自身结构卡表、Remembered Set（G1/ZGC 尤其明显）、GC 线程栈、符号表、JIT 辅助数据不可配，随堆大小与并发度自然增长被系统层面的 OOM killer 或 cgroup 直接杀掉，JVM 自己往往来不及留下一条完整日志

把这张表翻译成一句话：进程 RSS ≈ 堆 + 元空间 + 代码缓存 + 直接内存 + 线程栈总量 + GC 自身开销 + 本地库与 glibc 分配。容器 limit 卡的是这个和，而你日常监控看到的「堆使用率」只是第一项。这就是为什么会出现「堆才用了三分之一，容器却被 OOMKilled」。

还有一个经常被忽略的量：glibc malloc 的 arena 碎片。频繁分配释放不同大小的内存块时，glibc 为了让多线程不互斥会开出多个分配区，归还给操作系统的时机并不积极。所以 RSS 可能明显高于 JVM 自己统计的已提交内存，表现为「曲线下不来」。这类问题在操作系统层看不到异常，但 top 的 RES 一直在高位。

# 想知道钱花在哪一层，JVM 自带的分账工具在这里（需要启动时加 -XX:NativeMemoryTracking=summary 或 detail）
jcmd <pid> VM.native_memory summary scale=MB
# 输出按 Java Heap / Class / Thread / Code / GC / Native Memory Tracking 等分类给出 reserved 与 committed

# 没开 NMT 的进程，至少能看到各池的上限与 Metaspace 用量
jcmd <pid> VM.system_properties | grep -i -E 'jdk.nio.MaxDirectMemorySize|MaxDirectMemorySize'
jstat -gcutil <pid> 1000 5
# 输出里 M 列（元空间使用率）、CCS 列（压缩类空间）经常是被忽略的那一列

# 操作系统视角的总账：RSS 与容器限额的距离
ps -o pid,rss,vsz,comm -p <pid>
cat /sys/fs/cgroup/memory.max        # cgroup v2；v1 路径为 /sys/fs/cgroup/memory/memory.limit_in_bytes，以你节点为准
NMT 不是事后能开的。-XX:NativeMemoryTracking 必须在启动时指定，运行中的进程补不上。所以对于容易出内存问题、又难以频繁重启的服务，建议把这个开关和 -XX:+HeapDumpOnOutOfMemoryError 一起常态化打开，它的运行时开销是可接受的（具体开销比例以你版本文档和实测为准），没有理由一直关着它。

另外一个必须提前想清楚的细节：堆转储 dump 往哪里写。-XX:HeapDumpPath 如果不指定，文件会落在进程的工作目录，也就是容器可写层，那里属于 ephemeral-storage，写几 GB 就可能把节点打到 DiskPressure，Pod 被驱逐。正确做法是给 dump 单独挂一个有容量上限的 emptyDir 或一块 PVC，并且事后清理。

面试怎么答：「-Xmx 只管堆。元空间放类的元数据、JDK 8 之后取代永久代并且默认没有明确上限；代码缓存放 JIT 编译产物；线程栈按线程数乘以 -Xss 线性增长；直接内存由 -XX:MaxDirectMemorySize 限制，Netty 这类框架会大量使用。它们都算进进程 RSS，所以容器里堆设得再合理，只要堆外没留位置，照样被 cgroup 杀。」

模块 2

垃圾回收器演进：不是一代比一代强，是取舍点一直变

「你们用的什么 GC？」这一句的合格答案不是说出名字，是说出为什么在当时选它。因为 Serial、Parallel、CMS、G1、ZGC 解决的是同一个问题的不同侧面：在「停顿时间」「吞吐量」「额外 CPU 与内存开销」这三个角里，每一代让出的东西都不一样。

先把三个底层事实对齐，否则后面会听不懂。第一，回收靠可达性分析：从 GC Roots（栈上的引用、静态字段、JNI 引用、活跃线程等）出发遍历引用图，到不了的判定为垃圾。第二，三种基础回收动作：标记-清除（速度快但产生碎片）、标记-复制（无碎片但要浪费一半空间，用在新生代）、标记-整理（移动对象，无碎片但要搬动内存，慢一些）。第三，Stop-The-World（STW）：为了保证引用关系在判定过程中不被业务线程改坏，某些阶段必须暂停业务线程；所谓低延迟收集器，本质是把「必须暂停的那部分」做得越来越短，剩下的活挪到与业务线程并发执行。

收集器工作方式取舍现状
Serial单线程回收，新生代复制、老年代标记-整理，全程 STW最简单、额外开销最小，堆一大停顿就无法接受小堆、CLI 工具、单核受限容器仍有价值
Parallel（Throughput）多线程并行做新生代与老年代的回收，仍然全程 STW目标是单位时间内干最多的活（吞吐量优先），单次停顿仍然明显JDK 8 服务端模式的默认组合（Parallel Scavenge + Parallel Old），批处理类任务依然是好选择
CMS老年代并发标记、并发清除，试图让大部分工作与业务线程同时跑停顿短，但标记-清除会产生碎片，且并发期间老年代还在增长，追不上就是 concurrent mode failure，退化成 Serial Old 做一次全量整理——那次停顿会非常长JDK 9 起标记为废弃、JDK 14 中移除（对应 JEP 相关变更，具体版本号以官方文档为准）。新环境不该再选它
G1把堆切成等大的 Region，按需回收收益最高的那批 Region（Mixed GC），可预测停顿模型兼顾吞吐与停顿，Region 之间靠 Remembered Set 记录跨区引用，因此额外内存开销高于 Parallel，且大对象（Humongous）处理有自己的麻烦JDK 9 起为默认收集器，绝大多数服务端应用的合理起点
ZGC / Shenandoah几乎全部标记与整理都并发完成，靠读屏障、染色指针/转发指针实现对象移动时业务线程不停停顿极短，代价是额外的 CPU 与内存开销，以及读屏障对吞吐的影响ZGC 在 JDK 11 以实验特性引入、JDK 15 转为生产可用（后续版本又引入了分代支持）；Shenandoah 稍晚引入，二者都不在所有发行版上默认提供。能力以你使用的 JDK 版本与实际发行版文档为准

关于停顿指标要有个诚实的说法：不建议在面试里背具体毫秒数。官方对各收集器的停顿描述是「目标」形式的（比如 ZGC 的目标一直是极低停顿），但这个值高度依赖堆大小、对象存活率、CPU 核数和你的业务形态。能说的应该是方法：以我压出来的 P99 停顿为准，而不是宣传材料上的数。这一句比背出某个数字可信得多。

真正落到运维面上的判断，其实是三步：看有没有必要换——如果 FGCT 的增长占比很低、单次 Full GC 也在业务可接受范围内，就不必动；看 CPU 是否还有余量——并发收集器是拿 CPU 换停顿，本身 CPU 就打满的应用上了 ZGC 只会更堵；看堆多大——堆小的时候 Serial/Parallel 可能反而更省资源，堆大且存活对象多的时候 G1 及之后的 Region 化设计才有优势。

# GC 总览：每 1 秒一次，共 5 次 —— 看趋势而不是单次瞬时值
jstat -gcutil <pid> 1000 5
# 列的含义（名字以你版本为准）：S0/S1 Survivor、E 伊甸园、O 老年代、M 元空间、CCS 压缩类空间
# YGC/YGCT 年轻代次数与耗时、FGC/FGCT Full GC 次数与耗时、GCT 总耗时

# 容量与耗时分开看，判断是不是「回收不出东西」
jstat -gc <pid> 1000 5

# 当前到底开的哪个收集器，别猜
jcmd <pid> VM.flags | grep -i -E 'useg1gc|useparallelgc|useconcmarksweepgc|usezgc|useshenandoahgc|maxgcpausemillis|maxheapsize'
java -XX:+PrintCommandLineFlags -version
三种典型的 GC 失败，可以直接从日志的字面区别出来：promotion failed 是新生代往老年代晋升时老年代放不下（老年代碎片或容量不足）；concurrent mode failure 是 CMS 并发回收还没跑完，业务已经把老年代填满，被迫 STW 全量回收；to-space exhausted 出现在 G1 上，是回收时用来搬运存活对象的空 Region 不够了。这三种对应不同的调法：前两种通常指向老年代容量或晋升速率，第三种往往是回收不够快（Region 太小或晋升太猛）。

面试怎么答：「我不按『越新越好』选 GC，按堆大小、停顿容忍和 CPU 余量三条来定。堆小、重点是吞吐的用 Parallel；常规服务端用 JDK 9 之后的默认 G1；堆很大且要求极低停顿才考虑 ZGC 或 Shenandoah，前提是 CPU 有余量给并发回收阶段，因为它本质是拿 CPU 换停顿。CMS 我不再选，它已经在新版本里被移除。」

模块 3

容器里的坑：JVM 看到的-XX与被限制的-XX不是一套

「我明明写了 -Xmx2g，容器给的也是 2Gi，为什么还是被 OOMKilled？」因为2Gi 是进程的总额度，而 -Xmx2g 只是说「堆最多可以到 2g」——两者看起来相等，实际是「全部预算」和「其中一项预算」的差别。

比这更早的一步问题是：早期 JVM 压根不知道自己在容器里。它会去读宿主机的物理内存和 CPU 核数来算默认堆大小、默认线程数、并行 GC 线程数。于是你给了一个 512Mi 的容器，JVM 按宿主机的 128G 内存算出了一个巨大的默认堆，然后刚启动就撞上 cgroup 的墙。这个能力是逐步补上的：JDK 8u191 之后的部分版本才开始引入 cgroup 内存感知（当时是 -XX:+UseCGroupMemoryLimitForHeap 这类开关），-XX:+UseContainerSupport 在较新的版本（大致是 JDK 10 起）默认开启；而 cgroup v2 的支持更晚。具体行为请以你实际运行时的 JDK 版本文档为准——这是这一节唯一不能凭记忆下结论的地方。

现象根因怎么验证
没设 -Xmx，容器里默认堆远大于 limit老版本按宿主机物理内存算默认堆容器内跑 java -XX:+PrintFlagsFinal -version | grep MaxHeapSize，和容器的 memory.max 比一下
设了 -Xmx 仍被 OOMKilled堆外预留不足给 cgroup 留忧看 NMT 的 committed 分布，或者用 MaxRAMPercentage 让 VM 自己按比例留位置
线程数、GC 并行线程数多得离谱CPU 数量同样取自宿主机Runtime.getRuntime().availableProcessors() 与实际 CPU quota 对比
CPU quota 是 2 核，但 JVM 认为有 32 核某些版本对 cpu shares 与 cpu quota 的处理策略不同查 ActiveProcessorCount、PreferContainerQuotaForCPUCount 一类开关是否存在于你的版本

所以生产上的常规做法是：不给死巴巴的 -Xmx，给百分比。-XX:MaxRAMPercentage 的含义是「堆上限取可用内存的百分之多少」，InitialRAMPercentage 定初始值，二者的默认值随版本不同（常见的说法是 25，但必须以你的 JDK 提供的 PrintFlagsFinal 输出为准）。用百分比的好处是：容器 limit 调整的时候参数不用跟着改，而且天然给堆外留出了比例。

那到底留多少给堆外？这没有通用答案，取决于你的应用有没有用 Netty、加载多少类、开多少线程。能给出的只是方法而不是数字：上线前用 NMT 打一次 committed 的分项，看堆之外的各项加起来占多少，然后在这个基础上留出安全余量，并用压测验证峰值不会突破。直接拍一个百分比然后祈祷，是这类故障最常见的起因。

# 容器里第一件事：确认 JVM 到底认为自己有多少内存、多少 CPU
java -XX:+PrintFlagsFinal -version | grep -i -E 'MaxRAMPercentage|InitialRAMPercentage|MaxHeapSize|ActiveProcessorCount|UseContainerSupport'

# 一套相对稳的容器启动参数骨架（数值需按你的应用实测调整，不要照抄）
# -XX:+UseContainerSupport
# -XX:MaxRAMPercentage=70          # 堆上限占「可用内存」的比例，剩下留给堆外
# -XX:InitialRAMPercentage=70      # 初值等于上限，避免运行中反复扩容 triggering Full GC
# -XX:MaxMetaspaceSize=256m        # 给元空间一个明确天花板，避免它无限涨顶穿容器
# -XX:MaxDirectMemorySize=256m     # 用 Netty/DirectBuffer 时必须显式指定
# -XX:ReservedCodeCacheSize=128m   # JIT 产物上限，太小会导致编译停在 C2 之前
# -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps
# -XX:+ExitOnOutOfMemoryError      # 让进程失能而不是带病活着，配合 K8s 重启策略

# Netty 自身也有直接内存账本，和 JVM 的不是同一本
# -Dio.netty.maxDirectMemory=0     # 0 表示由 Netty 自己管理，不走 JDK 的 allocateDirect 上限
# -Dio.netty.leakDetection.level=paranoid

# 容器共享内存默认很小，部分框架（含 Netty 的某些用法）会依赖 /dev/shm
df -h /dev/shm        # 具体默认大小以你的运行时配置为准
-XX:+ExitOnOutOfMemoryError 值得单独说。不加它的时候，进程 OOM 之后往往「活着但不可用了」：请求全部失败、探针可能还通、K8s 不知道该重启它。加了之后进程主动退出，由 restartPolicy 或探针把它换掉。这本质上是在告诉编排系统「我坏了」，而不是让它继续对外提供服务。反过来也要注意：如果 OOM 的根因是流量尖峰而不是泄漏，Pod 会进入反复重启的循环，这时稳定的做法是定位流量尖峰的来源，而不是把重启策略调得更激进。

最后一个容易漏的点：堆转储在容器里写入必须落到有独立容量的卷上。写进容器可写层，几 GB 的文件会直接把节点本地盘占满，触发 DiskPressure 和驱逐。挂一个带 sizeLimit 的 emptyDir 或者一块 PVC，并在排障之后清理文件，这是标准动作。

面试怎么答：「容器里我不用固定的 -Xmx 硬编，用 MaxRAMPercentage 让它按容器限额算，并且显式给 MaxMetaspaceSize、MaxDirectMemorySize、ReservedCodeCacheSize 定天花板——因为这几项目前在容器里没有天然上限，会一路涨到顶穿 cgroup。这里面的版本差异必须承认：cgroup 感知能力是逐步加入的，旧版本按宿主机算，所以到底认不认得 cgroup，要用 PrintFlagsFinal 实测，我一般不会在面试里把某个具体版本号说死。」

模块 4

四类 OOM（上）：Java heap space 与 Metaspace

这两类的共同点是：报错里直接写了是哪个区域，所以第一层判断不用猜。难的是第二层——「泄漏」和「配置不够」这两种完全不同的病，症状几乎一样。

Java heap space 的含义是：老年代晋升或大对象分配时找不到连续空间，回收完之后还是不够。它有两种成因。第一种是真的不够：流量涨了一倍，或者批处理的数据量比开发时候大了一个数量级，堆是按旧容量配的。第二种是对象本该死却没死：一个静态 Map 当作缓存一直在 put、线程池的 ThreadLocal 没 remove、注册进去的监听器没有注销、ResultSet 没关闭——这些东西从 GC Roots 一直可达，回收器没有资格动它们。

区分这两种的方法很机械，而且不需要看懂代码：看老年代在一次 Full GC 之后掉下去多少。如果是「不够」，Full GC 之后老年代会回落到很低的水平，曲线是对称的锯齿；如果是「泄漏」，每次 Full GC 能扫出的空间越来越少，底线一路上抬，锯齿的下沿是单调上升的线。这个信号比任何工具都早。真正要拿决策依据的时候再 dump：用 MAT 或其他分析工具看 Dominator Tree，排在上面的那一类对象（或持有它的那张 Map）就是答案。

Metaspace 的含义是：类的元数据撑爆了上限。要注意这里的关键是「类加载失败了不等于元空间出错」，反过来也一样。元空间涨上去常见的来源是：动态代理与字节码增强框架（大量冗长的运行时代理类）、脚本引擎反复求值、热部署反复加载同一个类螺旋、以及类加载器泄漏——一个 ClassLoader 只要还被某条引用链拽着，它加载过的所有类的元数据就一套都释放不掉。所以 Metaspace OOM 的根因几乎总是「数量」而不是「单个类的大小」。

类型典型成因定位命令修复方向
Java heap space容量不足，或对象被 GC Roots 持续引用（静态容器、ThreadLocal、监听器、未关闭资源）jstat -gcutil 看 O 列是否回不去；jmap -histo:live 看对象直方图；必要时 jmap -dump 分析 Dominator Tree泄漏就修引用；不泄漏就是容量问题，结合 MaxRAMPercentage 与副本数一起看
Metaspace类数量爆炸：动态代理、脚本引擎、反复部署、ClassLoader 泄漏jstat -gcutil 的 M 列；jcmd VM.classloader_stats；jmap -clstats（版本支持情况下）设 MaxMetaspaceSize 做保护，但必须同时查 ClassLoader 泄漏，否则只是把爆炸时间往后推
# 第一步永远是看曲线的形态，一秒一次连续采样
jstat -gcutil <pid> 1000 30 | awk 'NR==1 || $4 != "" {print}'
# 关注 O 列（老年代）每次 FGC 之后的低点有没有一路上抬

# 堆直方图：先看一眼谁最多，比直接 dump 轻量得多
jmap -histo:live <pid> | head -40

# 类加载器账本：每个 loader 加载了多少类、有没有死掉却还在
jcmd <pid> VM.classloader_stats

# 到了必须 dump 的时候：注意会 STW，且文件需要几倍堆大小的空间
jmap -dump:format=b,file=/dumps/heap.hprof <pid>
# 或者用 jcmd（新版本推荐），同样会暂停业务线程
jcmd <pid> GC.heap_dump /dumps/heap.hprof
heap dump 是「会让现场更糟」的动作，不能当成日常体检。它会触发一次 Full GC，并且文件体积接近堆的使用量。在线上做，必须确认：目标卷有足够空间（不要把节点写满导致驱逐）、这个文件不会落在容器可写层、以及已经准备好「做完之后立刻把文件搬走或分析完删掉」。更好的做法是让它自动发生在 OOM 那一刻（HeapDumpOnOutOfMemoryError），而不是你事后手动补。

面试怎么答：「heap space 我先分清是容量问题还是泄漏，方法是看 Full GC 之后老年代的低点有没有单调上抬——泄漏的下沿一直在涨。确认要动手的时候再 dump，用 Dominator Tree 找持有者。Metaspace 我第一时间怀疑的是 ClassLoader 有没有被引用链拽住，因为单个类一般不会大到撑爆，出问题的一定是数量或者加载器不释放；设 MaxMetaspaceSize 是保护不是修复。」

模块 5

四类 OOM（下）：Direct buffer 与 unable to create new native thread

这两类最能区分「背过」和「见过」。它们的共同特征是：都跟堆没关系，而且第一反应往往是错的。

Direct buffer memory 出现在堆外直接分配的场景：ByteBuffer.allocateDirect、Netty 的池化 ByteBuf、以及部分依赖于此的序列化/压缩/网络库。这里有个反直觉的地方值得说透：真正占用那块本地内存的，是一个很小的堆壳对象（Java 侧的引用对象），真正的内存在堆外。当壳对象变得不可达时，它的清理动作（Cleaner 机制）会在 GC 之后被安排执行去释放本地内存。问题在于：壳对象很小，堆几乎没有压力。堆没压力就不触发回收，不触发回收就不释放本地内存——于是本地内存一路涨到最后一句话：OutOfMemoryError: Direct buffer memory，而这时候你看堆的使用率可能还不到三成。

这条链路解释了两个常见错误。一是以为「调大堆就能解决」，实际是把触发机会推得更远。二是以为「 System.gc() 能救」，就算它真的触发了回收，也是用一次 Full GC 的停顿换一小片释放，代价极高；而且如果你的参数里为了别的理由加了 -XX:+DisableExplicitGC，这条路直接断了。正确的做法是给这个区域一个明确的数量边界：-XX:MaxDirectMemorySize 显式指定；Netty 还要单独看它自己的账本（-Dio.netty.maxDirectMemory 及其泄漏检测级别）；代码侧要检查 ByteBuf 有没有按约定释放（Netty 的引用计数依赖显式 release），池化的参数有没有和实际并发匹配。

unable to create new native thread 则完全是另一个方向。它说的是「操作系统（或者容器）不允许我再创建一个线程了」，触发条件有四种，和堆一条都不沾边：进程/用户的线程数操作数上限（ulimit -u 对应的 NPROC）；容器 pid 上限（Kubernetes 侧的 --pids-limit 或 kubelet 的 podPidsLimit）；系统层面的线程总量（/proc/sys/kernel/threads-max 一类）；以及剩余可用内存不足以开出一个新栈——每个线程要按 -Xss 预留一块栈空间，可用内存被别的区域吃光时，这里的答案是「没有地方放这个栈了」。

现象先看哪里常见结论
Direct buffer memoryMaxDirectMemorySize、Netty 的 maxDirectMemory 与泄漏检测日志显式设上限 + 查 ByteBuf 有没有 release；确认不是因为缩小了 MaxDirectMemorySize 却没改业务并发
unable to create new native thread当前线程数、ulimit -u、容器 pids 限额、系统 threads-max、剩余可用内存线程真的在泄漏（每次请求新建线程、线程池创建却没复用），或者 -Xss 配得过大
GC overhead limit exceededFGCT 占比与 Full GC 频率堆极小或严重泄漏，回收几乎扫不出空间。这是 JVM 在告诉你「继续下去没有意义」
Requested array size exceeds VM limit出错栈 frame某个长度参数失控（分页条数、一次加载全表），是业务参数问题不是 JVM 问题
# 线程爆了：先数清楚有多少个，再找它们的名字
ps -Lf -p <pid> | wc -l
ps -L -p <pid> -o nlwp=
cat /proc/<pid>/status | grep -i threads

# 上限在哪里：三个层面分别查
ulimit -u
cat /proc/sys/kernel/threads-max
cat /sys/fs/cgroup/pids.max            # cgroup v2；v1 路径与名称以你节点为准

# 线程在干什么：按线程名字归类，这一步通常直接给出答案
jstack <pid> | grep '"' | sed 's/".*"/<n>/' | head
jstack <pid> | grep -o '"[^"]*"' | sed 's/"//g' | sed 's/-[0-9]*$//' | sort | uniq -c | sort -rn | head -20

# 直接内存：先看 JVM 这条线，再看框架那条线

grep -i -E 'leak|directmemory' /path/to/app.log | tail -20
看到 unable to create new native thread 却去加大 -Xmx，是把最后的余量也吃掉。这类报错往往意味着可用内存已经很紧张，这时候把堆的上限调高，等于进一步压缩留给线程栈的空间。正确的顺序是先数线程数、看清是谁创建了这么多（通常是「每次请求 new Thread」或者某个池子的 core/max 设成了离谱的数），先治理数量；只有确认数量合理、而 -Xss 又确实偏大时，才考虑调整单个线程的栈大小。

面试怎么答：「Direct buffer 的问题是「壳在堆里、肉在堆外」，壳太小 GC 不触发，所以本地内存涨到上限时堆可能还很闲。解法是显式 MaxDirectMemorySize 加上框架自己的泄漏检测，而不是靠 System.gc()。unable to create new native thread 完全不是堆的问题，查的是 ulimit、容器的 pids 上限、系统线程总量和剩余内存是否够开栈——这时候加大堆只会更糟。」

模块 6

CPU 飙高：把进程 CPU 拆成线程 CPU，再看线程在干什么

「Java 进程 CPU 200%，是不是内存不够触发 Full GC 了？」——不一定，而且这两种的处理方向是相反的。看到进程 CPU 高，下一步永远是 top -Hp，这一步把「一个笼统的数字」变成「几个有名字的线程」，是全链路里信息增益最大的一步。

步骤 1：确认是进程还是容器。容器内执行 top 看到的是容器视角。先确认这个高 CPU 来自 Java 进程本身，还是它的某个子进程（有些服务会拉起 shell 或本地工具）。
步骤 2： top -Hp <pid> 找出线程。拿到占用最高的几个线程号（十进制）。如果是容器，注意是否有 pid namespace 隔离，工具要在同一个命名空间里跑。
步骤 3：十进制转十六进制。printf '%x\n' <tid>。jstack 里的线程号是十六进制的 nid，这一步不做就对不上号。
步骤 4： jstack 里对号入座。按 nid 定位并往上翻几十行栈帧，看最上面那个业务方法是不是熟悉——它通常就是热点。
步骤 5：连拍三次再下结论。单次快照可能正好抓到一个偶发状态。连续三次都停在同一处，才是热点；三次停在不同地方，那可能只是纯粹的高吞吐。

对号入座之后，通常落在三类结论里。第一类：业务线程。最常见的来源是死循环、正则回溯、或者对一个本该有出口的集合做了 O(n²) 的处理。这类情况下 CPU 会在没有对应流量增长的前提下被打满。第二类：GC 线程（名字里通常能看到 GC 相关的字样）。这说明「回收跟不上分配」，根因可能是堆太小、对象泄漏、或者晋升速率过高，这时候加大 CPU 于事无补。第三类： sy 高而不是 us 高。用户态不高、内核态高，通常是线程数量太多导致上下文切换繁忙，或者在做大量的小额网络读写。这一类的处理手段是减少线程数或批量化 IO，而不是扩容。

类型证据处理方向
业务热点方法同一个 nid 的栈连续多次一致，栈顶是某个业务方法看是否被调用次数爆炸（循环/重试失控），用采样分析器确认
GC 线程占 CPU线程名带 GC 字样；同时 jstat 显示 FGCT 增长极快回到第 4 节：分清泄漏与容量不足，别在这里停留
锁竞争大量线程处于 BLOCKED，等待同一把锁或一个池的资源定位持有者；如果资源是连接池，问题在下游
上下文切换过多vmstat 的 cs 列很高，sy 占比高线程数收敛、批量 IO；这类不是「忙」而是「切换累」
# 进程视角 → 线程视角
top -Hp <pid>

# 转换：top 给十进制，jstack 用十六进制 nid
printf '%x\n' 12345

# 抓栈：一次不够，建议间隔几秒抓三份
for i in 1 2 3; do jstack -l <pid> > /tmp/stack-$i.txt; sleep 3; done
jstack -l <pid> | grep -A 30 'nid=0x3039'

# 内核态 vs 用户态、上下文切换频次
pidstat -u -p <pid> 1 5
vmstat 1 5

# 有 Arthas 的话，这三步基本替代上面的手工流程
# thread -n 5        # CPU 最高的 5 个线程的栈
# thread -b          # 找出阻塞了别人的那个线程
# profiler start/stop  # 生成火焰图
一个能省很多时间的习惯：把「连续三次栈都在同一处」当成热点的定义。很多人抓一次栈，看到某个方法就下结论，结果那是碰巧被采到的一个正常路径。另外要注意，CPU 高不一定对应 RT 高：这几天轮回的是单线程死循环，RT 可能只在那一个请求上体现，平均值看着正常——所以要用高分位数而不是均值去发现。

面试怎么答：「CPU 高我不会先扩容。流程是 top -Hp 拆出线程、线程号转十六进制、用 jstack 抓连续三份栈比对：栈都一样是热点，='GC 线程'说明回收跟不上（回头查内存），BLOCKED 说明在等资源而不是在计算。还有一种情况是 sy 高、上下文切换大，那是线程太多而不是算力不够。」

模块 7

工具箱：四个 JDK 自带的，加一个在线诊断工具

JVM 的工具看名字很乱，其实分工非常清楚：jstat 看趋势、jmap 看内容、jstack 看此刻在干什么、jcmd 是它们的统一入口。加上 Arthas 做在线补充，日常排障基本够了。

工具回答什么问题典型用法与注意事项
jps这台机器上有哪些 Java 进程、用的是哪个启动类或 jar容器里往往只跑一个主进程，这一步通常能省掉 ps 的工序
jinfo这个进程实际生效的参数是什么看命令行参数与部分可动态修改的系统属性；实际生效值以它为准，别信配置文件
jstatGC 与各类池的趋势：频率、耗时、占用率jstat -gcutil 看容量百分比，-gc 看绝对字节数，-class 看类加载量与卸载量
jmap堆里现在有什么（直方图 / 转储）-histo:live 轻量；-dump 会 STW 且文件很大，线上慎用
jstack此刻每个线程在做什么、持有哪些锁加 -l 输出额外的锁与死锁信息；要连拍多份
jcmd上面多数能力的新入口，命令更规范jcmd <pid> help 列出所有能力：线程栈 Thread.print、堆转储 GC.heap_dump、VM 参数 VM.flags、本地内存 VM.native_memory
Arthas不重启、不改代码地看运行时dashboard 总览、thread -n 与 thread -b、watch/trace 看参数与耗时分布、jad 反编译确认线上是不是这份代码

容器里用这些工具有两个反复出现的坎。第一是命名空间：工具要和目标进程在同一个 PID 命名空间里，所以通常是 kubectl exec 进容器执行，而不是在节点上对着宿主机 PID 跑。第二是权限：attach 需要同一个用户、并且能够访问进程的相关目录，以非 root 运行的 Java 应用经常在这里碰壁。还有一个容易被忽略的前提：最小化镜像里没有 JDK 工具。如果你的基础镜像只带 JRE 或者被裁剪过，jcmd 可能压根不存在——这时候要么挂一个诊断 sidecar（同一 Pod、共享 PID、带完整 JDK），要么在镜像里预置好 arthas。

jcmd <pid> help

# 四个高频动作，尽量用 jcmd（jmap/jstack 在新版本里是 deprecated 的用法）
jcmd <pid> Thread.print -l
jcmd <pid> GC.heap_info

jcmd <pid> VM.native_memory summary scale=MB

jstat -class <pid> 1000 3

# Arthas 的典型三步：什么最热、谁堵着谁、这个方法被谁调
# dashboard
# thread -n 5
# watch com.xxx.OrderService create '{params, returnObj, #cost}' -x 2 -n 20
jstat -gcutil <pid> 1000 5GC 总览：先看 YGC/FGC 的频率与 FGCT 的增长速率
jcmd <pid> Thread.print -l抓线程栈，建议连拍三份，连续一致的那处栈才是热点

所有 attach 型工具都会让目标进程暂停一小会儿（安全点机制），这不是免费的。单次影响通常很小，但在一个已经很紧张的节点上反复执行，或者在同一个进程上同时开好几个分析会话，会让业务方感觉到明显的抖动。原则是一次做一个动作、做完立刻收工具，而不是把四五个会话挂在进程上慢慢看。

面试怎么答：「我用四个自带工具的思路是：jstat 看 GC 趋势、jmap/jcmd 看堆内容、jstack 看此刻在做什么、jcmd 作为统一入口。容器里要注意工具和进程必须在同一个 PID 命名空间、并且镜像里不一定有 JDK——这是两个很实际的坎。线上我倾向常态化打开 NativeMemoryTracking 和 OOM 自动转储，把「事后未必来得及开」的开关提前准备好。」

模块 8

慢请求与池资源：CPU 不高、内存不高，问题在「等」

这类现场最容易诱人走错方向：资源图表一片平静，但 RT 在涨、超时在涨。看一眼 CPU 和内存都健康，于是得出「资源充足但性能差」这个自相矛盾的结论。真正的原因是线程大部分时间没在计算，而是在等待。

等待发生在三个地方。线程池队列：任务进来先排队，队列长度持续增长说明处理速度跟不上提交速度；连接池：每个操作要先拿到一条到数据库或下游的连接，池子被占满就只能等；锁：synchronized 或者各种同步器上的争抢。这三者在 jstack 里的样子完全不一样——WAITING/blocked 的状态词和「waiting to lock」那一行会直接写出来。

线程池这里有个公认的坑必须知道：使用无界队列的任务池，最大线程数会失效。因为队列永远接收新任务，池永远不会走到「队列满了要扩容线程」那一步，所以你配的那个 maximumPoolSize 从头到尾没起作用。表现是「队列里的任务越堆越多，但线程数始终停在核心数」，队列变长带来的是内存增长和延迟增长，却不触发任何拒绝策略给你报警。把队列带上界，并明确定义满了之后怎么办（抛错还是让提交者自己跑），才能真正看见背压。

连接池这条链路通常是这样闭环的：某条 SQL 变慢 → 占用的连接不放 → 池满 → 后续请求排队拿连接 → 上游超时 → 上游重试 → 请求量翻倍 → 池更满。慢查询在这条链路的起点，症状却在应用层。所以处理顺序应该是先去数据库侧（慢日志、活跃会话、锁等待），再回来看连接池。连接池的连接数不是越大越好——超过数据库处理能力上限只会把数据库压垮，然后大家一起慢。

# jstack 里把所有线程的包名/状态词聚合一下，立刻能看出「大家都在等什么」
jstack <pid> | grep -o 'java.lang.Thread.State: [A-Z_]*' | sort | uniq -c | sort -rn
jstack <pid> | grep -B2 'waiting to lock' | head -20
jstack <pid> | grep -A5 'getConnection' | head -20

# 排查的目标是找出那一句「大家都在等同一个池 / 同一把锁」
# （下面的 Arthas 命令可以在不知道线程名的情况下先看整体）
# thread --state BLOCKED
# thread -b

# 数据库侧：同时对这条链路的下半段取样
SHOW PROCESSLIST;
SELECT * FROM information_schema.innodb_trx ORDER BY trx_started LIMIT 10\G
参数越大 ≠ 吞吐越高。线程池、连接池的容量一旦超过下游真实处理能力，效果是「把压力完整地传给下游，并附带更高的排队开销」，响应曲线会先变平、再陡峭上升，最后雪崩。治理的正确顺序是：先把下游为什么变慢解决掉（慢查询、超时配置、重试语义），再回头设定池大小。直接把连接池上限翻倍，往往是压垮数据库的最后一根稻草。

还有一个必须先想清楚的问题：重试会放大。上游超时后重试一次，中间那条请求大概率还在下游排队或者还在执行，于是同一个操作被执行两次。所以「超时时间长不长」和「重试几次」必须放在一起设计——尤其是写操作。评估标准很简单：这个接口的幂等性有没有被验证过？没有幂等保证就不该随便加重试。

面试怎么答：「CPU 和内存都不高的慢请求，本质是线程在某个地方等着拿资源。我用 jstack 把线程状态聚个类，WAITING 或 BLOCKED 的形态会告诉我是队列、是连接池还是锁。如果是数据库侧慢，问题往往不在连接池的大小而在那条 SQL；连接数往上调只会把压力推给数据库。另外我会检查重试有没有把请求放大，以及这个接口做没做幂等。」

模块 9

九个坑：每个错误的直觉都来自「把 -Xmx 当成全部」

下面这些不是知识缺口，是动作比判断快。它们看起来都很果断，共同点是把一次可解释的故障，变成一次需要更多运气才能解释的故障。

1
看到 OutOfMemoryError 就加内存
四类 OOM 里只有一类靠加堆能治。线程创建失败时加大堆反而挤掉栈的空间；Metaspace 爆了加堆一点关系没有。先看报错后缀。
2
以为 -Xmx 等于容器的内存上限
进程 RSS 还包含元空间、直接内存、线程栈、代码缓存和 GC 自身结构。二者相等意味着「堆把预算全用了」，必被 cgroup 杀。
3
Metaspace 爆了只调大 MaxMetaspaceSize
那是保护不是修复。类数量还在增长（动态代理、反复部署、ClassLoader 泄漏），把天花板抬高只是让爆炸晚一点发生。要用 jcmd VM.classloader_stats 找出谁在加载。
4
用 System.gc() 回收直接内存
它换来的是一次 Full GC 的停顿；而且很多环境为了别的原因开了 -XX:+DisableExplicitGC，这条路直接是断的。应该显式指定 MaxDirectMemorySize 并检查 ByteBuf 的释放。
5
把 JVM 版本对容器的感知能力当成理所当然
cgroup 感知是逐步加入的，旧版本按宿主机算默认堆。到底认不认，用 java -XX:+PrintFlagsFinal -version 实测，不要背版本号。
6
在线上对主进程随手 jmap -dump
会触发 Full GC，文件体积接近堆用量，写错位置还会把节点本地盘写满导致 Pod 被驱逐。应该靠 OOM 自动转储，dump 路径挂独立卷。
7
抓一次栈就下结论
单次快照可能正好采到一个无关路径。定义应当是「连续多份栈都停在同一处」才叫热点，而且一定要确认占 CPU 的是 GC 线程还是 BLOCKED 状态的业务线程。
8
线程池配了 maximumPoolSize 以为会自动扩容
无界队列永远吞任务，池永远走不到扩容那一步，最大线程数形同虚设，也永远不会触发拒绝策略让你察觉到积压。队列必须有上界。
9
慢了就调大连接池
慢的根因常在下游（慢查询、锁等待、外部接口超时）。池调大只是把压力转嫁给数据库，还会因为排队让曲线更陡。先查为什么占着连接不放。

面试怎么答：挑一条讲成三段：当时的判断、造成的后果、后来改成了什么。比如「有一次应用在容器里反复重启，我看监控堆才用一半，就判断是资源给少了，把 limit 从 2Gi 加到 4Gi，结果挂得更快——后来才发现是新版本上线加了个动态代理导致 Metaspace 一直涨，加大的只是 Metaspace 的可用空间。从那以后我先看 OOM 的后缀名再决定动什么。」第三段最重要，它证明你改的是判断方式。

自测

六道题

1. 日志里出现 java.lang.OutOfMemoryError: unable to create new native thread。最应该先看哪一项？
正确答案：线程数与各类上限。这条报错的含义是「不允许再创建新线程」，来源可能是用户级线程数限制、容器的 pids 限额、系统级线程总量，或者剩余内存不足以开出一块 -Xss 大小的栈。它与堆空间无关；此时加大 -Xmx 会挤占本就紧张的剩余内存，让情况更糟。
2. 容器 limit 是 2Gi，启动参数是 -Xmx2g，运行中被 OOMKilled。最可能的原因是？
正确答案：堆外没有留余地。容器限额约束的是进程常驻内存的总量，堆只是其中一项。把 -Xmx 设成和 limit 相等，等于把全部额度都交给堆，剩下的区域必然溢出，于是被 cgroup 直接杀掉——这和大家印象里的「Java 抛 OOM」不是一回事。
3. jstat -gcutil 显示 Old 区在每次 Full GC 之后的低点一路上抬，Full GC 越来越频繁。这说明什么？
正确答案：泄漏指向。判据是「回收后的低点单调上抬」：容量不足时，每次 Full GC 之后底线都会回落到差不多的位置；泄漏时底线一路抬高，可用空间持续收缩，回收频率随之上升。此时加大堆只会推迟爆炸时间，正确动作是 dump 后看 Dominator Tree 找出持有者。
4. 关于 Direct buffer memory，下面说法正确的是？
正确答案：第一段。堆里放的是引用壳，实际内存在堆外，由清理机制在壳对象被回收后释放。壳很小，堆压力因此可以长期很低、回收长期不触发，本地内存却一直在涨。调用 System.gc() 不是标准做法：它换来的是 Full GC 的停顿，而且在开了 -XX:+DisableExplicitGC 的环境里根本不生效。正解是显式 -XX:MaxDirectMemorySize 加框架侧的泄漏检测。
5. Java 进程 CPU 200%（两核打满），top -Hp 之后发现占用最高的是几个名字里带 GC 的线程。下一步最合理的是？
正确答案：回到内存侧。GC 线程吃 CPU 说明「回收跟不上分配」，扩容只是给了更多并行回收的能力但不改变泄漏或容量失衡的根因；重启则会丢失现场，且大概率复现。正确链路是用 jstat -gcutil 确认 Full GC 频率与回收效果，判断是容量问题还是泄漏。
6. CPU 和内存都平稳，但接口 RT 明显上升，jstack 里大量线程处于等待获取数据库连接的状态。最合理的处理顺序是？
正确答案：先治根因，再谈容量。连接池被打满通常是结果而不是原因：某条 SQL 变慢、锁等待或下游超时导致连接占用时长变大，请求于是开始排队。此时调大池会把更多并发压力原样推给数据库，可能把它彻底压垮；调大线程池同理，只是让排队点从连接池移到线程池。改容量之前必须先在数据库侧确认「连接为什么不放」。
