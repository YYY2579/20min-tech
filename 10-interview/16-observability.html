可观测性三支柱：指标、日志、链路怎么配合

metrics 告诉你「出事了」，traces 告诉你「哪一段慢」，logs 告诉你「为什么」。

读之前先答一句：只有一个 502 的错误率曲线，你能定位到哪一行代码吗？
开始前

一次 502，三种视角，三个都缺

晚上八点，网关的 502 比例从 0.1% 涨到 3%。看板上指标齐全：错误率、QPS、P99、下游依赖的调用量，全都有。但你盯着这四条曲线看了十分钟，还是不知道是哪一段出了问题——因为指标只告诉你「多少」，不告诉你「哪一个请求、卡在哪一步」。

于是去查日志。日志服务里 grep 502，出来三十万行，每行都是同样的 upstream sent invalid header。你能确认是某个下游返回了脏数据，但不知道是哪个下游、从什么时候开始、影响的是哪类请求。

再看链路。采样率 1%，一晚上只有几百条 trace，翻了半天没找到一条真正报错的——因为采样是随机的，它不认识「错误」这个概念。

这三个失败是同一类错误：用错工具回答错问题。指标不是用来定位单条请求的，日志不是用来做聚合趋势的，随机采样的 trace 也不是用来抓稀有错误的。三支柱之所以是三根柱子，不是因为厂商想多卖产品，是因为它们的成本结构和查询模式根本不同。

这一篇要讲清三件事：每种信号擅长回答什么问题、怎么埋点才让三者能互相关联、以及一次真实的排障应该按什么顺序在三种信号之间跳。最后会落到 OpenTelemetry 和采样策略——这两个是当下面试里区分「用过」和「搭过」的地方。

面试落点：「我的顺序是用指标发现、用链路定位、用日志解释。因为指标便宜、能覆盖全量，适合发现和告警；链路有请求级因果，能指出是哪一段；日志细节最全但最贵，只适合在已经锁定范围之后去查为什么。」

模块 1

三支柱：不是三种数据，是三种成本结构

「可观测性三支柱是什么」这题谁都会答。追问「为什么不能用日志替代指标」，才是真正在考你有没有算过账。

维度MetricsLogsTraces
数据形态预聚合的数值时间序列离散事件的文本或 JSON请求级的 span 树
成本驱动series 数量 × 采样点字节数（通常最贵）请求数 × span 数 × 采样率
基数容忍极低，标签值不能无限增长高，什么都能写中，受采样和存储周期限制
擅长回答多少、多快、趋势如何、要不要告警这一次具体发生了什么、错误原文是什么这个请求经过了谁、哪一段最慢
不擅长单个请求的细节、原因聚合统计、长期趋势（太贵）全量覆盖（采样必然丢）、长期留存
典型保留期数周到一年（视存储方案）数天到数月，错误级别更长数天到数周

为什么日志替代不了指标？算一笔账：一天一亿请求，每个请求打三行日志、每行 300 字节，就是 90GB/天。要在这个量级上算「过去 30 天每小时的 P99」，代价高到不可接受。而同样的问题用直方图指标表达，可能只有几千条 series、每天几 MB。指标是「提前把聚合做好」，代价是你只能问预先设计过的问题。

反过来，指标也替代不了日志。指标能告诉你错误率涨了，但涨的原因可能是下游超时、证书过期、某个字段解析失败、数据库死锁——这些信息都在错误内容和堆栈里，而把每一种错误原文做成标签，就是基数自杀。所以正确的分工是：指标负责「发现和缩小范围」，日志负责「解释」。中间那一步「是哪一个调用慢」，才轮到链路。

指标：广而浅
覆盖所有服务和依赖，成本低，能 7×24 盯着。它是雷达，不是显微镜。
链路：窄而深
只覆盖被采样的请求，但能给出完整的调用链和每一段的耗时。它是 X 光。
日志：全而贵
什么都能记，但成本随流量线性上涨。它是病历，只在需要的时候翻。

还有一个常被追问的点：这三者怎么算「可观测」而不是「可监控」？监控是「你预先知道要问什么」，可观测是「你能问出没预想过的问题」。区别在于标签和属性的丰富度：只看 CPU 和 QPS 是监控；能按用户、按地域、按版本、按依赖切片去问「为什么只有 iOS 用户在华东失败」，才叫可观测。但这句话有边界——丰富度受基数成本约束，所以「可观测」永远是在成本和自由度之间做取舍，不是越多越好。

面试怎么答：「三者的差别不在数据格式，在成本结构。指标是预聚合，最便宜，适合全量覆盖和告警；链路是采样后的请求级因果，适合定位；日志最贵但细节最全，适合解释。所以我不会问『哪个最好』，只会问『这个问题用哪个信号回答成本最低、信息又够用』。」

模块 2

黄金信号与 RED / USE：两套方法，两个视角

「监控该看哪些指标」——如果答案是「CPU、内存、磁盘、网络」，那只是机器的体检报告，不是服务的健康度。用户不关心你的磁盘，只关心请求有没有成功、快不快。

四个黄金信号是 Google SRE 里提出的一组：延迟、流量、错误、饱和度。前三个是用户视角，第四个是容量视角。第四个存在的理由是「预测」——延迟和错误是已经发生的事，饱和度是「快要发生」的事。

信号怎么量陷阱
延迟成功请求的耗时分布，通常看「阈值内完成的比例」必须把成功和失败的请求分开统计。失败请求往往几十毫秒就返回，混在一起会把平均值拉低，看起来「变快了」
流量QPS、并发连接数、消息消费速率要区分「用户流量」和「重试流量」。重试风暴时 QPS 翻倍，但真实用户没变
错误显式错误（5xx）+ 隐式错误（200 但内容错、超时、空结果）只看状态码会漏掉「协议层成功、业务层失败」的情况
饱和度最紧缺的那个资源的用量：连接池、线程池、队列长度、CPU throttling要找「最先满的那个」，而不是所有资源都盯。通常不是 CPU

RED 和 USE 是两套互补的方法，别混着用。RED 面向请求型服务：Rate（速率）、Errors（错误）、Duration（耗时），三个都是「请求视角」。USE 面向资源：Utilization（使用率）、Saturation（饱和度）、Errors（错误），三个都是「资源视角」。一个服务对外用 RED 定义 SLO，对内用 USE 找瓶颈——RED 告诉你用户疼了，USE 告诉你为什么疼。

# RED：请求速率
sum(rate(http_requests_total{job="api"}[5m]))

# RED：错误比例（注意分母用有效请求，别把 4xx 算进来）
sum(rate(http_requests_total{job="api",status=~"5.."}[5m]))
/
sum(rate(http_requests_total{job="api",status!~"4.."}[5m]))

# RED：延迟达标率，比 P99 更适合做告警
sum(rate(http_request_duration_seconds_bucket{job="api",le="0.3"}[5m]))
/
sum(rate(http_request_duration_seconds_count{job="api"}[5m]))

# USE：连接池饱和度——比 CPU 更常见的真实瓶颈
pg_stat_activity_count{state="active"} / pg_settings_max_connections
为什么延迟告警不用 P99？两个原因。第一，分位数不可聚合，多实例的 P99 没法合并成全局 P99。第二，P99 对桶的边界极其敏感，桶没设计好时它本身就是个估算值。而「300ms 内完成的比例」可以直接聚合、可以直接和 SLO 对比、也可以在告警里说清「现在有 2% 的用户超过 300ms」——这句话人能听懂。

还有一个经常被忽略的：饱和度和错误之间有时滞。连接池满了之后，应用会开始排队，然后是超时，最后才是错误率上升。如果只盯错误率，你会比用户晚一到两分钟知道。这也是为什么要给「饱和度」单独配一条 P3 告警——它不叫人起床，但它给你提前量。

面试怎么答：「对外用 RED 定义 SLO：速率、错误、耗时，都是请求视角；对内用 USE 找瓶颈：使用率、饱和度、错误，都是资源视角。延迟一定要把成功和失败分开统计，否则失败请求会把平均值拉低。饱和度是唯一带预测性的信号，值得单独盯。」

模块 3

指标埋点：桶的边界决定了你的 SLO 能不能被验证

埋点这件事，最贵的错误发生在设计阶段：桶设错了，三个月后想验证 SLO，发现数据根本不支持——桶太粗，P99 落在 +Inf 里；桶太细，series 爆了，Prometheus 先挂。

先说命名，因为它决定了三支柱能不能关联。指标名要有单位、要有类型后缀：Counter 用 _total，时间统一用秒（_seconds），大小统一用字节（_bytes）。不要用毫秒和秒混着来，也不要叫 request_time 这种既没单位也没类型的名字。标签只放低基数维度：method、status_class、route_template、region 可以；user_id、request_id、原始 URL 不行。

然后是桶。设计原则只有一条：在你要做判断的那个边界附近，必须有桶。SLO 是「95% 的请求在 300ms 内完成」，那 200ms、250ms、300ms、400ms 这四个桶就是必需品。没有它们，你算出来的「300ms 内比例」其实是相邻两个桶之间的线性插值，误差可能大到让结论翻转。

桶设计后果
用客户端默认桶，不按业务调默认桶通常覆盖毫秒到十秒，看着通用，但你的 SLO 边界往往正好落在两个桶中间
桶太少（三五个）分位数全靠插值，P99 基本是猜的
桶太多（三五十个）series 数按桶数线性上涨，标签一多直接打爆 TSDB
上界没覆盖到超时时间所有慢请求挤进 +Inf，你永远不知道到底多慢
用 Gauge 记单次耗时只剩最后一个值，分布全丢，什么也算不出来

算一下成本，面试里能报出这个乘法很加分：一条直方图的 series 数约等于 标签组合数 ×（桶数 + 2），加 2 是因为 _sum 和 _count。假设有 50 个路由、4 种方法、12 个桶，那就是 50 × 4 × 14 = 2800 条 series，只为一个指标。如果再把 status 细分成 20 种，立刻变成五万多条。这就是为什么「指标要克制」不是风格问题，是容量问题。

# 一个按 SLO 设计的桶：边界卡在 300ms，上界覆盖到 5s
http_request_duration_seconds_bucket{route="/pay",le="0.05"}
http_request_duration_seconds_bucket{route="/pay",le="0.1"}
http_request_duration_seconds_bucket{route="/pay",le="0.2"}
http_request_duration_seconds_bucket{route="/pay",le="0.3"}   # SLO 边界
http_request_duration_seconds_bucket{route="/pay",le="0.5"}
http_request_duration_seconds_bucket{route="/pay",le="1"}
http_request_duration_seconds_bucket{route="/pay",le="2"}
http_request_duration_seconds_bucket{route="/pay",le="5"}
http_request_duration_seconds_bucket{route="/pay",le="+Inf"}

# exemplar：把一次具体观测关联到 trace，指标点可以直接跳到链路
http_request_duration_seconds_bucket{route="/pay",le="0.3"} 1024 # {trace_id="4bf92f3577b34da6a3ce929d0e0e4736"} 0.287
exemplar 是被严重低估的一个功能。它让直方图的某个桶携带一个真实的 trace_id，于是你在 Grafana 上看到一个尖刺，可以直接点进去看那一次请求的完整链路。这是「指标发现问题 → 链路定位问题」这条路径上最短的一跳，成本几乎为零，值得默认打开。

面试怎么答：「指标名带单位和类型后缀，标签只放低基数维度。直方图的桶要卡在 SLO 边界附近，上界覆盖到超时时间，总数控制在十几个，因为 series 数约等于标签组合乘桶数加二。另外我会开 exemplar，让指标点能直接跳到对应的 trace。」

模块 4

日志：结构化是底线，成本控制是本事

日志的问题从来不是「记不记」，是「记多少、留多久、怎么查」。一个日活百万的服务，如果每个请求打五行 info，日志系统的账单会比计算资源还高。

先立一条底线：日志必须是结构化的。同一行文本 "user 123 login failed" 和 {"event":"login_failed","user_id":"123","reason":"bad_password"}，前者只能靠正则，后者可以直接按字段过滤和聚合。结构化不是为了好看，是为了可查询——排障时你少写十个正则，就多十分钟定位。

字段约定要统一，而且要和链路、指标对齐：时间戳、级别、服务名、环境、trace_id、span_id、消息、错误对象、耗时、HTTP 状态码。服务名这个字段尤其重要：如果指标里叫 job、日志里叫 app、链路里叫 service.name，那三者永远关联不上。统一到一套语义约定（OpenTelemetry 的 semantic conventions 就是干这个的），比事后写十个 JOIN 脚本划算。

级别要有纪律。error 的语义应该是「需要人来看的事」，而不是「捕获了一个异常」。一个每秒钟都在重试失败的连接池，如果每次都打 error，你的错误日志检索会立刻失效。可恢复的重试打 warn 并带上重试次数，只有最终失败才打 error。

控制手段做法代价
分级保留error 留 30 天，info 留 3 天，debug 默认关需要日志后端支持按级别设 TTL
采样info 按 1%~10% 采，error 全留采样后的日志不能用来算精确比例
采集侧过滤在 agent/Collector 就丢掉健康检查、静态资源的日志过滤规则要维护，容易误杀
字段裁剪不打整个请求体，只打关键字段和长度排障时需要临时加日志再发一次
限流按服务设每秒上限，超了丢弃并计数突发时可能丢掉关键日志，必须配「丢弃计数」告警

如果用的是 Loki 这类「只索引标签、内容压缩存储」的系统，有一条铁律：标签基数决定索引大小，绝不能把 trace_id 当标签。每个请求一个 trace_id，等于每个请求一条流，索引会先于存储爆炸。正确做法是把 trace_id 放进日志行里，用全文过滤查：

# 正确：按低基数标签选流，用 filter 找 trace_id
{service_name="api", env="prod"} |= "4bf92f3577b34da6a3ce929d0e0e4736"

# 错误：把请求级 ID 做成标签，Loki 会为每个值建一条 stream
{service_name="api", trace_id="4bf92f3577b34da6a3ce929d0e0e4736"}

# 统计某类错误的出现次数（结构化日志里的字段可以直接过滤）
sum by (service_name) (count_over_time({env="prod"} |= "level=error" [5m]))
日志里不要打敏感数据。手机号、身份证、卡号、token、完整的请求体——这些东西一旦进日志，就等于进了几十台机器的磁盘和若干个备份，合规上很难说清。要打就打脱敏后的前缀加长度，或者只打哈希。这一条在面试里提一句，会显得你有生产意识。

面试怎么答：「日志第一要求是结构化，字段名要和指标、链路统一，否则关联不上。成本靠分级保留、采样、采集侧过滤和字段裁剪控制。用 Loki 的话标签必须是低基数的，trace_id 只能放在日志内容里用全文检索，绝对不能做标签。」

模块 5

链路追踪：span 是树干，context 传播是命门

链路追踪的原理十分钟能讲完：一个 trace 是一次请求的完整调用树，一个 span 是其中一个工作单元，有开始时间、结束时间、名字、属性和父 span。真正难的不是概念，是让这条链不断。

一条 trace 由 trace_id 标识，全局唯一；每个 span 有自己的 span_id，并记录 parent_span_id。根 span 没有父，子 span 的父指向调用它的那个 span。这样一串起来，就是一棵树：谁的耗时包含谁、哪个环节是串行、哪个是并行，一目了然。

断链的根源只有一个：上下文没传过去。跨进程调用时，trace 信息必须放在协议头里带过去；到了对端，服务端从中取出 trace_id 和 parent_span_id，创建自己的 span。HTTP 用 header，gRPC 用 metadata，消息队列要放在消息属性里——最后这个最容易被漏掉，因为发消息和收消息是两个独立的消费链路，中间没有任何调用栈可以继承。

W3C 的 traceparent 是目前通用的传播格式，结构是四段用短横线连接：版本（2 位十六进制）、trace_id（32 位）、parent_id（16 位）、flags（2 位），总共 55 个字符。flags 的最低位表示「这个 trace 是否被采样」。还有一个配套的 tracestate，用来携带厂商私有的信息，可以有多条。

# traceparent 的结构（示例值，非真实链路）
00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
│  │                                │                │
│  │                                │                └─ flags: 01 表示已采样
│  │                                └─ 本段 span_id（16 位）
│  └─ trace_id（32 位）
└─ 版本号

# 抓包确认 header 有没有传过去
tcpdump -i eth0 -A -s0 'tcp port 8080' | grep -i -E 'traceparent|tracestate'

# 用 curl 手工带一个 trace 上下文，验证服务端有没有正确接续
curl -H 'traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01' \
     http://localhost:8080/api/ping
断链场景为什么断怎么修
经过网关后链路分成两段网关没透传 header，或者重新生成了 trace_id网关配置里显式放行 traceparent，禁止重新生成
线程池里丢上下文trace 存在 ThreadLocal 里，切线程就没了用支持上下文传递的包装器，或显式传递 context 对象
异步回调、定时任务断链没有调用栈可以继承把 context 作为参数显式传进任务
消息队列消费端是根 span生产端没把上下文写进消息头生产端注入、消费端提取，并记录 link 关系
跨语言服务对不上一边用 B3 一边用 W3C统一传播格式，或在网关注入转换
面试里最容易加分的细节：span 的耗时应该覆盖「这一段的全部时间」，包括等待下游的时间。父 span 的耗时 ≥ 所有子 span 耗时之和（并行时会更明显），而那些「父 span 很慢、子 span 都很快」的空隙，通常就是真正的瓶颈——它可能是排队、可能是 GC、可能是锁等待，而这些东西不会有独立的 span。

面试怎么答：「trace 是一棵 span 树，靠 trace_id 和 parent_span_id 串起来。断链的唯一原因是上下文没跨进程传过去，HTTP 走 header、gRPC 走 metadata、消息队列走消息属性。格式上我一般用 W3C 的 traceparent，flags 里带采样标记。看 trace 的时候除了看哪个 span 慢，还要看父 span 和子 span 之间的空隙，那才是真正没被埋点覆盖的地方。」

模块 6

把三者缝起来：exemplar、trace_id 和统一语义

很多团队三套系统都建了，但排障时还是要人肉在三个页面之间复制粘贴 ID。这不叫可观测性，这叫三个孤岛。缝合它们只需要三样东西，成本都不高。

指标到链路：exemplar。直方图观测时附带当前 trace_id，Prometheus 存下来，Grafana 上点一下尖刺就能跳到那条 trace。前提是 SDK 支持 exemplar，且抓取格式是 OpenMetrics。
链路的身份下放到日志：trace_id 注入。日志框架从当前 span 的上下文里取 trace_id 和 span_id，写进每一行。这样你在 trace 上看到某个慢 span，复制 trace_id 就能拿到那一段的全部日志。
三者共享同一套资源属性。service.name、deployment.environment、k8s.namespace.name、k8s.pod.name 在指标标签、日志字段、span 属性里用同样的名字和同样的值。名字不统一，前两步白做。

还有一条隐性的前提：时间必须同步。三套系统的数据来自不同机器，如果某台机器的时钟差了三分钟，你在 trace 上看到的耗时和日志里的时间戳就对不上，关联会变成误导。生产机器必须跑 NTP 或 chrony，容器里也要继承宿主机时间，这一点在面试里说出来很像「真的踩过」。

# 排障时的典型跳转路径（都是复制一个 ID 的事）
# 1. 指标异常 → exemplar 里拿到 trace_id
histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))

# 2. 用 trace_id 查这条链路的全部 span，找最慢的那一段
trace_id = 4bf92f3577b34da6a3ce929d0e0e4736

# 3. 用同一个 trace_id 查日志，看那一段到底报了什么
{service_name="payment"} |= "4bf92f3577b34da6a3ce929d0e0e4736"

为什么很多团队缝不上？最常见的原因是三套系统分别由不同的人搭的：监控用 Prometheus 那套命名，日志用 ELK 那套字段，链路用另一家 SaaS 的默认属性。等到要关联的时候，才发现 service、app、service_name 三个名字指的是同一个东西。这不是技术问题，是约定问题——而约定必须在埋点之前定，事后统一的成本高十倍。

面试怎么答：「关联靠三件事：exemplar 把指标点连到 trace，trace_id 注入日志把链路连到日志，统一资源属性让三者能按同一个维度过滤。前提是字段名和值必须一致，以及机器时间同步。这三件事都不难，难的是在埋点之前就把约定定下来。」

模块 7

OpenTelemetry：它解决的不是采集，是标准

「OTel 是什么」——如果答「一个采集器」，那把它和 Fluent Bit、Promtail 混为一谈了。OTel 真正的价值是把埋点从厂商 SDK 里解耦出来：换后端不用改代码，一套 SDK 同时产出指标、日志、链路。

它分三层：API 是埋点接口（你代码里调的），SDK 是实现（采样、批处理、导出），Collector 是独立的进程（接收、处理、转发）。协议叫 OTLP，跑在 gRPC 或 HTTP 上。这个分层的好处是：业务代码只依赖 API，具体用哪个后端、开不开采样，全在部署侧决定。

Collector 组件作用常见配置
receiver接收数据otlp、prometheus、filelog、jaeger
processor处理、过滤、采样、补属性memory_limiter、batch、tail_sampling、resource、filter
exporter发往后端otlp、prometheusremotewrite、loki、debug
connector把一种信号转成另一种从 span 里生成指标（spanmetrics）
extension自身运维能力health_check、pprof、zpages

部署形态有两种，选错了会很痛。Agent 模式是每台机器（或每个 DaemonSet）跑一个 Collector，就近接收、简单处理、直接转发，优点是网络短、故障域小。Gateway 模式是集中一层，做尾采样、脱敏、多后端分发，优点是策略统一，缺点是它成了关键路径——它挂了，全站的可观测数据就断了，所以必须多副本加缓冲。

Collector 里 memory_limiter 必须放在 processor 链的第一个。它的作用是在内存接近上限时拒绝新数据，避免自己被 OOM kill。如果它排在 batch 后面，前面的处理器已经把数据堆进内存了，限流就来不及了。这条几乎是 OTel 部署的常识题。

OTel 的代价也要说清楚，否则答案会显得像在背宣传材料：抽象层多，出问题时要在 API、SDK、Collector、后端四层之间排查；版本演进快，配置项经常改；链路埋点的性能开销取决于采样率和 span 数量，高 QPS 服务上要实测，不能想当然。

面试怎么答：「OTel 的核心价值是厂商中立和信号统一：业务只依赖 API，采样和导出在 SDK 和 Collector 里配。Collector 我会分 agent 和 gateway 两层，agent 就近收，gateway 做尾采样和多后端分发。部署上 memory_limiter 必须放第一个，而且 gateway 自己就是关键路径，要高可用。」

模块 8

一次 502 的全链路排查：三种信号怎么轮着用

把前面几节拼起来，走一遍完整的现场。注意每一步都在回答一个更窄的问题——排障的本质不是「看得更多」，是「把范围缩得更小」。

20:03  告警：pay 接口 5xx 比例 3%，SLO 快速燃烧
       │
20:04  ① 圈影响面（指标）
       │   - 只有 /pay 一个路由，其它接口正常
       │   - 三个可用区都在报，不是单机
       │   - 20:00 有一次发布，20:02 开始涨
       │   → 结论：和这次发布强相关，范围是 /pay 的下游调用
       │
20:06  ② 看依赖的错误率（指标）
       │   - 网关侧 502 上涨，upstream 是 payment-svc
       │   - payment-svc 自身的 5xx 没涨，但它的出向调用耗时涨了 4 倍
       │   → 结论：payment-svc 没挂，是它依赖的某个东西慢了
       │
20:08  ③ 找那一段（链路）
       │   - 按 route=/pay、status=5xx 过滤 trace
       │   - 最慢的 span 是 POST risk-service/score，P99 从 80ms 到 3.2s
       │   - 父 span 有 2.9s 是「空隙」，没有子 span
       │   → 结论：时间花在 risk-service 的连接建立或等待上
       │
20:10  ④ 看为什么（日志）
       │   - 用 trace_id 查 payment-svc 日志：connection pool timeout
       │   - 用同一时间段查 risk-service：连接数打满，正在排队
       │   → 结论：发布把 risk 客户端的连接池从 200 改成了 20
       │
20:12  ⑤ 止损（先恢复，再修复）
           - 回滚配置（不是回滚整个版本，只回滚连接池参数）
           - 观察 5xx 回落到基线，确认 SLO 停止燃烧
           - 事后：给连接池饱和度加 P3 告警，把参数纳入配置评审

这条时间线里有三个值得记住的判断。第一，第 ② 步看的是「出向」而不是「入向」：payment-svc 自己的错误率没涨，说明它没崩，问题在它调用的东西上。如果只看入向指标，你会误以为是 payment-svc 的问题，然后在错误的机器上翻半天。

第二，第 ③ 步的关键发现是「空隙」。父 span 3.2 秒，子 span 加起来只有 300 毫秒，中间那 2.9 秒没有任何 span——这通常意味着时间花在「没被埋点的地方」：连接池排队、DNS 解析、TLS 握手、线程池等待。链路追踪最有价值的用法不是看哪个 span 最长，是看哪里没有 span。

第三，止损和定位是两条线，可以并行但不能颠倒优先级。影响面在扩大时，先回滚再定位；影响面稳定时，可以先花五分钟拿到证据。但无论哪种，回滚前先存一份现场（trace_id、关键日志、指标截图），否则复盘时只能靠回忆。

现象先看哪个信号为什么
错误率整体上涨，原因不明指标的依赖维度先分清是自身还是下游，能砍掉一半排查范围
个别请求极慢，平均正常链路的慢 trace平均值掩盖长尾，只有 trace 能看到单次路径
某个下游报错，但不知具体原因日志（按 trace_id 过滤）错误原文、堆栈、返回值只在日志里
只有部分用户受影响按维度切分的指标地域、版本、设备这些维度只有指标能高效聚合

面试怎么答：「我先用指标圈定影响面和是否与变更相关，再看依赖维度的出向指标分清是自身还是下游，然后用链路找最慢的那一段——特别注意父 span 和子 span 之间的空隙，那通常是没有埋点的地方，比如连接池排队。最后用 trace_id 去日志里拿错误原文。整个过程是先止损再定位，但止损前会保留现场。」

模块 9

采样：头部采样省钱，尾部采样救命

「采样率设多少」——10% 是个常见的默认答案，也是最容易出事的答案。因为采样的目的不是「少存点」，是「别丢掉重要的那一条」，而重要的那一条恰恰是少数。

头部采样（head sampling）在请求开始时就决定了采不采，判断依据只有 trace_id 或者请求头，成本几乎为零，但它不知道这个请求最后会不会失败。于是 1% 的随机采样下，一次 0.01% 的错误可能一条都抓不到——而错误正是你最想看的。

尾部采样（tail sampling）等整条 trace 的 span 都到齐了再决定，因此可以按「有没有错误」「耗时是否超过阈值」「是否命中特定用户」来采。代价有三个：需要缓冲（内存换时间）、必须保证同一个 trace 的所有 span 落到同一个 Collector 实例（通常按 trace_id 做负载均衡）、以及决策窗口带来的延迟。

策略决策时机优点代价
头部采样请求开始零额外开销、实现简单、SDK 层就能做无法按结果采样，稀有错误容易全丢
尾部采样trace 结束后错误全采、慢请求全采，性价比极高要缓冲、要按 trace_id 路由、Collector 内存压力大
概率采样请求开始简单，量可控小流量服务的样本可能少到无法分析
按属性采样开始或结束可以只采某个租户、某个版本规则要维护，容易漏掉新服务

实践里最常用的是组合策略：头部先做一道粗筛（比如 20%），尾部再保底保留所有错误和慢请求，正常请求按低比例留。这样既控制了总量，又保证了「出事时一定有数据」。前提是头部采样率不能太低，否则错误的那条在第一步就被丢了，尾部再聪明也救不回来。

采样之后，trace 的数量就不能当 QPS 用了。十万请求采 1%，你看到 1000 条 trace，不代表 QPS 是 1000。更隐蔽的问题是：如果采样率中途调整过，同一天的漏斗分析会出现断崖。所有「比例型」的结论都必须来自全量指标，不能来自采样后的 trace 或日志。

还有一个必须说清的边界：SLO 的计算绝对不能用采样数据。SLO 要求的是「全部有效请求里成功的比例」，采样会带来统计偏差，尤其是当采样策略和结果相关时（比如「只采错误」），算出来的可用性会低得离谱。指标虽然也有成本，但它是全量的，这是它不可替代的地方。

面试怎么答：「头部采样在请求开始时决定，便宜但不知道结果，稀有错误容易丢；尾部采样等 trace 完整后按错误和延迟决策，能保证出事时有数据，代价是要缓冲和按 trace_id 路由。实践里我会组合使用：头部粗筛、尾部保错误和慢请求。另外采样后的数据不能用来算 SLO 或 QPS，那些必须用全量指标。」

坑

9 个坑：每一个都让「三支柱」变成「三孤岛」

这些坑有一个共同特征：单独看每套系统都正常，合起来用就废了。而且它们大多在搭建阶段埋下，排障当天才爆发。

1
把 trace_id 做成日志系统的标签
每个请求一个值，等于每个请求一条 stream，Loki 这类系统的索引会先崩。trace_id 只能放在日志内容里做全文过滤。
2
只有指标就想定位根因
指标只能告诉你「多少、哪一类」，回答不了「哪一个请求、卡在哪一行」。定位必须靠链路和日志，指标的作用是把范围缩小。
3
拿采样后的 trace 数当 QPS
1% 采样下看到 1000 条 trace，不代表 1000 QPS。采样率一变，历史对比全废。比例型结论只能用全量指标。
4
直方图桶用默认值，不覆盖 SLO 边界
SLO 是 300ms，桶边界却是 250ms 和 500ms，你算出来的达标率全靠插值。桶必须在判断边界附近加密。
5
日志里打完整请求体和敏感字段
成本翻几倍不说，手机号、token、卡号进了日志就等于进了所有备份，合规上很难解释。要打就打脱敏后的摘要。
6
异步和消息队列不透传 context
发消息时把 trace 上下文写进消息头，消费端提取出来接续。漏了这一步，链路会在 MQ 处断成两条，而 MQ 恰恰是最容易出问题的地方。
7
Collector 不配 memory_limiter，或者顺序放错
高峰期 Collector 自己被 OOM kill，可观测数据集体断流，而你正好在排障。memory_limiter 必须是 processor 链的第一个。
8
三套系统的服务名字段不统一
指标叫 job、日志叫 app、链路叫 service.name，关联脚本写不出来。这个约定必须在埋点之前定，事后统一的成本高十倍。
9
机器时间不同步
时间差几分钟，trace 的耗时和日志的时间戳就对不上，关联会变成误导。生产机必须跑时间同步，容器要继承宿主机时钟。

面试落点：第 1 个和第 8 个最适合讲。前者能带出「标签基数是所有可观测系统的共同约束」这个判断，后者能带出「约定先于工具」——这两句话都超出了「我会用某个产品」的层面，属于设计经验。

自测

六道题

1. 一个接口的错误率突然上涨，但不知道是自身问题还是下游问题。最合理的第一步是？
正确答案：看出向指标。自身入向 5xx 上涨、出向正常，多半是自己代码或资源的问题；入向正常而出向异常，问题在下游。这一步不改任何东西，却能把范围砍掉一半。翻全量日志和调采样率都是高成本动作，应该放在范围缩小之后。
2. 某直方图指标有 50 个路由、4 种方法、12 个桶。这个指标的 series 数量大致是多少？
正确答案：2800 条左右。直方图的每个标签组合会产生「桶数 + 2」条 series，多出来的两条是 _sum 和 _count。这也是为什么桶不能无脑加多——成本和桶数成正比。
3. 使用 Loki 收集日志时，下面哪个字段绝对不能作为标签（label）？
正确答案：trace_id。它的取值数量等于请求数量，每个值都会创建一条独立的 stream，标签索引会先于存储爆炸。正确做法是把 trace_id 写在日志内容里，用全文过滤（|=）去查。level 的取值也很少，作为标签是可接受的。
4. 关于 trace 上下文传播，哪个说法正确？
正确答案：第一项。trace 上下文的传递依赖显式携带：HTTP header、gRPC metadata、消息属性。同一个 SDK 也不会自动跨进程传，它只负责在收到 header 时解析。线程池切换会丢失存在 ThreadLocal 里的上下文，必须显式传递。
5. 为什么很多团队在尾部采样之外，还要保留一个较低的头部采样率？
正确答案：第三项。尾部采样需要把整条 trace 缓冲起来，如果全量上报，Collector 的内存和网络会先撑不住。头部粗筛能显著减量，但它按固定比例丢数据，比例太低时罕见错误会连同 trace 一起消失，所以两者要配合而不是互相替代。
6. 关于 RED 和 USE 的适用场景，哪个说法正确？
正确答案：第二项。RED 面向请求型服务，用来定义 SLO 和判断用户是否受影响；USE 面向资源，用来找瓶颈在哪。实际排障是先看 RED 知道用户疼了，再用 USE 找到为什么疼。
