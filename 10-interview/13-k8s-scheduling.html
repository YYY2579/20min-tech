调度、QoS、扩缩容与优雅发布

preStop 不 sleep 那几秒，就是你「每次发布都有 502」的根因。

读之前先答一句：Pod 被删的时候，是先从 Endpoints 摘掉，还是先收到 SIGTERM？
开始前

三个现场：都不是 bug，都是配置的默认值

「每次发布都有几十个 502，发布完就好。」「扩容了，Pod 全 Pending。」「HPA 配了 70%，CPU 到 90% 也不扩。」这三件事在同一个团队里往往同时存在，而且都有一个共同点：系统的默认行为恰好不是你想要的，而你从没改过它。

现场直觉答案真实原因
发布期间稳定出现 502，持续十几秒新版本有 bug，或者负载均衡抖动Pod 被删时，摘 Endpoints 和发 SIGTERM 是并行的，而规则同步有延迟。进程已经退出，流量还在往它身上打
HPA 扩到 20 个副本，一半 PendingHPA 有 bug，副本数算错了HPA 只管改 replicas，不管节点放不放得下。节点扩容要靠 Cluster Autoscaler，而它需要几分钟
CPU 打满但 HPA 不扩metrics 采集坏了HPA 的利用率是「用量 ÷ requests」。没设 requests，这个百分比根本算不出来，HPA 只会报 unable to get metric
调度是一次性的
scheduler 只在 Pod 创建时选一次节点，绑定后就不再管。节点变忙、标签变了，它都不会重新调度。
QoS 决定谁先死
节点资源不够时，kubelet 按 QoS 排序驱逐。这不是惩罚，是让你用配置声明「谁更不重要」。
发布是一个时序问题
502 几乎都出在「摘流量」和「停进程」之间的窗口里。把这个窗口抹平，比调任何超时都有效。

这一篇按「一个 Pod 怎么被安排 → 怎么被保护 → 怎么被扩缩 → 怎么被替换」的顺序走。前半段讲调度和约束，中间讲 QoS 与三种扩缩容，后半段讲滚动更新、优雅退出和探针设计——最后这三节是同一件事的三个面，目标都是让「替换一个 Pod」对用户不可见。

先把一句话记住：发布的本质不是「启动新版本」，是「把流量从旧版本挪到新版本，且中间不留空窗」。启动新版本 Kubernetes 已经帮你做了，不留空窗需要你配三个东西——readiness 探针、preStop 钩子、足够大的 grace period。缺一个就有 502。

面试怎么答：「K8s 的调度、驱逐、发布其实是一条链：调度决定 Pod 落在哪，QoS 决定资源紧张时谁先被赶走，滚动更新决定新旧怎么交替，优雅退出决定交替时流量会不会打空。我排 502 的时候不会先看应用日志，先看 preStop、grace period 和 readiness 这三处配置。」

模块 1

调度两步：先筛掉不能放的，再给能放的打分

调度的全部逻辑可以压成两句话：过滤（Filter）留下「放得下」的节点，打分（Score）在这些节点里挑「最合适」的一个。前者是硬条件，一票否决；后者是偏好，分出高下。理解这个分层，你才知道哪些配置会导致 Pending，哪些只是「尽量」。

阶段在做什么典型插件失败/结果
Filter（预选）逐个节点检查硬约束，不满足就排除NodeResourcesFit、TaintToleration、NodeAffinity、InterPodAffinity、VolumeBinding、NodePorts、NodeUnschedulable全被排除 → Pending，Events 里逐项列出原因
Score（优选）给通过的节点打 0-100 分，加权求和NodeResourcesFit（LeastAllocated / BalancedAllocation）、ImageLocality、InterPodAffinity、PodTopologySpread取最高分；同分随机
Bind把 Pod 的 nodeName 写上去—写失败会重试，绑定后不再变

NodeResourcesFit 的打分策略值得单独说一句，因为它解释了「为什么 Pod 总是堆到某一台机器上」。LeastAllocated 倾向选「已分配比例最低」的节点，也就是打散；BalancedAllocation 倾向选「CPU 和内存用量比例最接近」的节点，目的是避免一台机器 CPU 满了内存空着。不同发行版和版本的默认值不一样，以你集群的 scheduler 配置为准，但这两个策略的取舍是可以直接讲的。

# 1. 调度失败的原因：看 Events 里那句话，按节点分项统计
kubectl describe pod web-0 | sed -n '/Events/,$p'
kubectl get events --field-selector reason=FailedScheduling

# 2. 节点上「已经被 requests 占掉多少」——这才是调度依据
kubectl describe node node-1 | sed -n '/Allocated resources/,/Events/p'

# 3. 这个 Pod 到底要多少资源、有没有亲和约束
kubectl get pod web-0 -o jsonpath='{.spec.containers[*].resources}{"\n"}{.spec.nodeSelector}{"\n"}{.spec.affinity}{"\n"}'

# 4. 看 scheduler 自己的判断过程（需要开日志级别，生产慎用）
kubectl -n kube-system logs kube-scheduler-xxx --tail=50

# 5. 已经绑定的 Pod 不会被重新调度，这是设计不是 bug
kubectl get pod web-0 -o jsonpath='{.spec.nodeName}{" "}{.status.conditions}{"\n"}'

最容易答错的一个点：调度只发生一次。Pod 一旦绑定到节点，除非被删除重建，否则永远不会换节点，即使那台节点后来变得很忙、或者标签变了。IgnoredDuringExecution 这个名字就是在说这件事——「调度时看，运行中忽略」。想让 Pod 重新分布，只能靠重建（删掉让它被新调度），或者额外部署 descheduler 这类组件。

另一条链路是抢占（preemption）：高优先级 Pod 调度不上时，scheduler 会尝试驱逐某个节点上的低优先级 Pod 来腾位置。PriorityClass 就是给这件事用的。它的副作用很直接——你以为只是「让核心服务优先启动」，实际上它可能把别人的 Pod 杀掉。所以优先级要少用、分级要清楚，不要给一堆服务都配上高优先级。

「节点很空但 Pod Pending」的两种典型解释。一是 requests 虚高：所有 Pod 都写了 2 核 4G，节点账面早满了，实际用量只有 20%。二是硬约束：节点标签不匹配、污点不容忍、PVC 的可用区对不上。前者是容量规划问题，后者是配置问题，但现象完全一样，只能靠 Events 里那句话区分。

面试怎么答：「调度分过滤和打分两步。过滤是硬条件：资源、污点、亲和、卷、端口，任何一条不满足就排除；打分是偏好：资源均衡、镜像本地性、拓扑分散。所有过滤都失败才 Pending，Events 里会按节点列出原因。还有一点很重要：调度只发生一次，绑定后不会因为节点变忙而重新调度。」

模块 2

亲和与反亲和：required 是承诺，preferred 是愿望

「我想让这几个服务跑在一起」和「我想让它们别跑在一起」，在 Kubernetes 里是同一套语法的两个方向。而写错一个词——把 preferred 写成 required——就会把「尽量」变成「必须」，让 Pod 永久 Pending。

字段管的是硬/软写错的后果
nodeSelector节点标签，等值匹配硬没有匹配节点 → 永久 Pending
nodeAffinity.required...节点标签，支持表达式和集合硬同上，且表达式写错更难发现
nodeAffinity.preferred...节点标签，带 weight（1-100）软不满足也能调度，只是没享受到偏好
podAffinity和某些 Pod 靠近（同拓扑域）硬/软都有目标 Pod 不存在时，硬亲和会一直 Pending
podAntiAffinity和某些 Pod 分开（同拓扑域）硬/软都有副本数大于拓扑域数量 → 多余的永久 Pending

反亲和是发布事故的高发区，因为它的约束是「副本之间互斥」。你写「同一个 hostname 上不能有两个 web」，节点有 4 台，副本数从 3 扩到 6——多出来的 3 个副本没有任何节点可去。而 HPA 还在继续扩，于是你看到一半 Pod 在跑、一半 Pending，业务容量只有预期的一半。这类问题不会报错，只会安静地少一半容量。

# 硬反亲和：每个节点最多一个（副本数不能超过节点数）
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels: {app: web}
        topologyKey: kubernetes.io/hostname

# 软反亲和：尽量打散，放不下也不阻塞（weight 越高越优先）
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels: {app: web}
          topologyKey: kubernetes.io/hostname

# 节点亲和：用表达式而不是 nodeSelector，能表达集合和取反
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: node-pool
              operator: In
              values: [general, memory-optimized]

为什么硬亲和也危险？因为它的语义是「必须先有目标 Pod 存在」。两个服务互相硬亲和，谁先起来？都起不来。这类循环依赖在微服务里很常见，而且表现是「两个 Deployment 一直 Pending，删掉任何一个另一个就能起来」，非常反直觉。要打破它，只能至少有一边改成 preferred，或者去掉亲和用别的机制（比如同一个 Pod 里放 sidecar）。

还有一个语义细节值得说清：topologyKey 决定「多近算近」。用 kubernetes.io/hostname 就是同一台机器，用 topology.kubernetes.io/zone 就是同一个可用区。写错这一层，「打散」会变成「全部集中在同一台机器上」——因为约束的粒度变了，而你从 YAML 上看不出来。

硬反亲和不是「高可用配置」，它是「容量上限配置」。它给你的是「绝不同机」，代价是「副本数被节点数封顶」。真正想要「尽量打散、又不浪费容量」的，应该用拓扑分布约束（下一节），它允许倾斜，而不是一刀切。

面试怎么答：「亲和分节点和 Pod 两类，各有硬软两种。required 是一票否决，preferred 只影响打分。反亲和的坑最典型：用 hostname 做拓扑键、副本数超过节点数，多出来的副本永远 Pending，而且不报错。想打散又要保留弹性，应该用 topologySpreadConstraints 而不是硬反亲和。」

模块 3

污点与容忍：节点有脾气，Pod 有通行证

亲和是「Pod 挑节点」，污点是「节点拒绝 Pod」。这两个方向要分清：写亲和是你在表达偏好，写污点是节点在立规矩。而规矩有三种力度，其中一种会把你正在跑的 Pod 赶走。

Effect对新 Pod对已运行的 Pod典型用途
NoSchedule不容忍就不调度不动专用节点、GPU 节点、维护中的节点
PreferNoSchedule尽量不调度，没别的地方还是放不动软性的「别往这放」
NoExecute不容忍就不调度驱逐（可按 tolerationSeconds 延迟）节点异常、抢占、节点下线

这三个 effect 里，只有 NoExecute 会动已经在跑的 Pod，这也是「节点 NotReady 之后 Pod 被赶到别处」的机制——节点失联时，控制面给它打上 node.kubernetes.io/unreachable:NoExecute，Pod 等过 tolerationSeconds 就被驱逐重建。系统还维护另外几个：not-ready、memory-pressure、disk-pressure、pid-pressure、network-unavailable，以及 cordon 产生的 unschedulable。

容忍的写法有两种 operator，这个细节经常被问：Equal 要求 key、value、effect 都对上；Exists 只要求 key 存在，value 可以随便，甚至不写。所以「容忍这个 key 的所有污点」用 Exists 更省事，而「只容忍 value 是 gpu 的那种」必须用 Equal。effect 不写表示匹配该 key 的所有 effect。

# 给节点打污点（专用节点）
kubectl taint node node-1 dedicated=infra:NoSchedule

# 容忍的两种写法
tolerations:
  - key: dedicated
    operator: Equal
    value: infra
    effect: NoSchedule
  - key: node.kubernetes.io/unreachable
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 300     # 5 分钟后才赶我走

# 看节点上的污点与 Pod 上的容忍是否配对
kubectl describe node node-1 | grep -A3 Taints
kubectl get pod web-0 -o jsonpath='{.spec.tolerations}{"\n"}'

# cordon 本质是打 unschedulable 污点，drain 会逐出 Pod
kubectl cordon node-1
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data

# 去掉污点（注意末尾的减号）
kubectl taint node node-1 dedicated=infra:NoSchedule-

实践里最常见的误用，是给节点打污点做「专用池」，然后忘了 DaemonSet 和系统组件。日志采集、监控 agent 通常是 DaemonSet，它们的控制器会自动加一批容忍，所以还能跑；但你自己部署的 sidecar 式 agent、或者集群的 CNI、kube-proxy 如果是 Deployment 形态，就会全部 Pending。结果是节点起来了、Pod 也调度上去了，但网络不通——因为 CNI 的 Pod 没在这个节点上跑起来。

另一个细节：污点和容忍只是「准入」，不是「绑定」。容忍了某个污点，不代表 Pod 一定会调度到那台节点，它只是「不被这项拒绝」。要真的把 Pod 固定到专用节点，还得配 nodeAffinity 或者 nodeSelector——这是「专用节点池」的标准写法，两个都要写。

一个能立刻用的判断顺序：Pod Pending 且 Events 里出现 untolerated taint，先问三个问题——这个污点是谁加的？为什么加？不加会怎样？因为污点往往是别人（平台团队、升级流程、故障处理）临时加的，你贸然加容忍，等于绕过了别人设的保护。

面试怎么答：「污点是节点拒绝 Pod，容忍是 Pod 的通行证，方向跟亲和相反。三个 effect 里只有 NoExecute 会驱逐已运行的 Pod，节点 NotReady 时就是靠 unreachable:NoExecute 把 Pod 赶走重建的。容忍只保证不被拒绝，不保证一定调度上去，专用节点要同时配 nodeAffinity。」

模块 4

拓扑分布：允许一点倾斜，但别倒

反亲和是二元判断——同域里「有」或「没有」。但真实需求往往是「尽量平均，允许差一点」。这个需求用反亲和表达不了，用拓扑分布约束可以，而且它不会因为副本数超过域数量就卡死。

四个字段要一起理解：maxSkew 是允许的最大倾斜（某个域比最少的域最多多几个）；topologyKey 是域的粒度（可用区、节点）；whenUnsatisfiable 决定不满足时是拒绝调度（DoNotSchedule）还是只降分（ScheduleAnyway）；labelSelector 决定统计哪些 Pod。

字段含义写错会怎样
maxSkew域之间允许的最大数量差写 1 最严格，容易出现「为了凑平均反而调度不上」
topologyKey按什么维度分域写成 hostname 就变成「每节点一个」，和反亲和等价但不会卡死
whenUnsatisfiableDoNotSchedule 硬约束 / ScheduleAnyway 只影响打分业务对可用区有强要求时用软约束，等于没保障
labelSelector统计哪些 Pod 参与平衡选错会把别的服务的 Pod 算进来，导致分布莫名其妙
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels: {app: web}
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway     # 节点级别只做偏好
    labelSelector:
      matchLabels: {app: web}

为什么这个约束比反亲和更适合生产？举个例子：3 个可用区、6 个副本。用硬反亲和 + zone 粒度，每个区最多 2 个，刚好；但如果某个可用区挂了，只剩 4 个副本能跑，而新副本因为硬约束无法调度到那两个健康的区（每区已经 2 个，互斥），容量就永久降一半。用拓扑分布 + maxSkew 2，健康区可以各长到 3 个，容量恢复到 6。

还有一个容易被忽略的参数是 minDomains（较新版本支持，以你集群为准）。它解决的问题是：可用区只有 1 个能调度时，maxSkew 的计算会「退化」，所有副本堆在这一个区也算满足约束。设了 minDomains 之后，域数量不足时会认为不满足，从而拒绝调度——这是「宁可 Pending 也不要全堆在一个区」的选择。

拓扑分布和反亲和可以叠，但别指望它们互相兜底。硬反亲和会让 Pod 卡在 Pending，拓扑分布的软约束不会；反过来，软约束不提供任何可用性保证。想清楚你要的是「绝对不共存」还是「尽量均匀」，这两个诉求对应两套机制，混着写最容易出现「看起来配了高可用，实际全在一个区」。

面试怎么答：「拓扑分布约束解决的是『尽量均匀』，四个关键字段是 maxSkew、topologyKey、whenUnsatisfiable 和 labelSelector。它比硬反亲和更适合生产，因为反亲和会把副本数封顶在域数量上，一个区挂了容量就永久损失；拓扑分布允许健康区多承担一些。要强保证就用 DoNotSchedule，要弹性就用 ScheduleAnyway。」

模块 5

QoS 与驱逐：节点撑不住时，先杀谁

QoS 不是标签，是从 requests 与 limits 的关系里算出来的结果。它直接决定两件事：节点资源紧张时谁先被赶走，以及内核 OOM 时谁的「被杀分数」更高。

QoS条件oom_score_adj驱逐顺序
Guaranteed每个容器都设了 CPU 和内存，且 requests 等于 limits约 -997最后（几乎是最后）
Burstable设了 requests 或 limits，但不满足 Guaranteed2 到 999 之间，按内存 requests 占比算中间，按「超出 requests 的程度」排序
BestEffort所有容器都没设 requests 和 limits1000最先

这里有个值得说透的机制：Burstable 的驱逐排序不是按「谁用得多」，而是按 「用量相对 requests 超了多少」。一个 requests 100Mi、实际用 500Mi 的 Pod，比一个 requests 2Gi、实际用 2.1Gi 的 Pod 更先被赶走。这个设计的意思是：你声明了多少，就保护多少；超出的部分没有保护。

触发驱逐的是 kubelet 的资源水位，比如内存可用量低于硬阈值、本地磁盘使用率高于阈值。这些阈值是 kubelet 配置，不同发行版不一样（常见默认里内存硬阈值是 100Mi 量级、nodefs 和 imagefs 是百分比），所以不要背数字，去看你集群的 kubelet 配置或 describe node 里的 Conditions。软驱逐会带一个宽限期，硬驱逐立即动手。

# 1. 这个 Pod 实际是什么 QoS（系统算的，不能手写）
kubectl get pod web-0 -o jsonpath='{.status.qosClass}{"\n"}'

# 2. 驱逐的证据：Message 里写的是哪种资源
kubectl get pod -A -o custom-columns='NS:.metadata.namespace,NAME:.metadata.name,PHASE:.status.phase,REASON:.status.reason,MSG:.status.message' | grep -i evict

# 3. 节点压力状态（kubelet 打的 Condition）
kubectl describe node node-1 | sed -n '/Conditions/,/Addresses/p'

# 4. 容器的 oom_score_adj，能看出内核更倾向杀谁
kubectl exec web-0 -- cat /proc/1/oom_score_adj

# 5. 硬驱逐阈值（在节点上，路径和字段随版本变化，以你环境为准）
cat /var/lib/kubelet/config.yaml | sed -n '/evictionHard/,/^[a-z]/p'

有一个必须知道的事实：PDB 不保护节点压力驱逐。PodDisruptionBudget 约束的是通过 eviction API 发起的自愿中断（比如 drain、descheduler），而 kubelet 因为资源不足赶 Pod 走的是本地决策，不经过那个接口。所以「我配了 PDB，不会一次挂光」这个假设在节点 OOM 的场景里是不成立的。真正能减少这种情况的，是留出资源余量、把关键服务配成 Guaranteed、以及别让 requests 严重失真。

反过来说，BestEffort 也不是一无是处：批处理、可中断任务、压测工具用 BestEffort 是合理的——它们本来就该在资源紧张时先让路。问题出在把核心服务写成 BestEffort：没有任何 requests，调度器认为它不占资源，可以无限往上堆，节点一忙它第一个被杀，而且杀了之后重建还落在同一台节点上，继续被杀。

把 requests 写得很小来「提高调度成功率」，是一种自伤。requests 小意味着：调度时占位少（容易放上去）、驱逐时「超出 requests 的程度」大（更容易被赶走）、HPA 算 CPU 利用率时分母小（百分比虚高，可能触发无意义的扩容）。三个后果都指向同一个方向：你以为占了便宜，实际把稳定性押上了。

面试怎么答：「QoS 是 requests 和 limits 的关系算出来的，Guaranteed 是两者相等、BestEffort 是都不设、其余是 Burstable。驱逐顺序是 BestEffort 先走，Burstable 按超出 requests 的比例排序，Guaranteed 最后。要注意 PDB 不保护节点压力驱逐，它只约束 drain 这类走 eviction API 的自愿中断。」

模块 6

三种扩缩容：HPA 改副本，VPA 改规格，CA 加节点

这三个东西经常被混着说，其实它们改的是三个不同的东西：HPA 改 replicas，VPA 改 requests/limits，Cluster Autoscaler 改节点数量。搞混了就会问出「HPA 为什么没加机器」这种问题。

组件改什么指标从哪来生效速度
HPADeployment/StatefulSet 的 replicasmetrics-server（资源指标）、custom/external metrics（如 QPS、队列长度）十几秒到几分钟（采集间隔 + 稳定窗口）
VPAPod 的 requests/limits历史用量推荐值慢，通常需要重建 Pod 才生效
Cluster Autoscaler节点池的节点数是否有 Pending 的 Pod、节点是否长期低利用几分钟（创建节点 + 加入集群 + 拉镜像）

HPA 的算法值得写出来，因为它解释了很多「为什么不扩」：期望副本数 = 当前副本数 × 当前指标值 ÷ 目标指标值，向上取整。CPU 利用率的口径是「实际用量 ÷ requests 之和」，不是除以 limit，也不是除以节点容量。所以：没设 requests，这个百分比算不出来；requests 设得比实际低很多，百分比会虚高，一有流量就扩到天花板。

# HPA 配置：资源指标 + 行为控制
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: {kind: Deployment, name: web}
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 60}
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300    # 5 分钟内容忍更高的副本数
    scaleUp:
      stabilizationWindowSeconds: 0

# 排障：HPA 的 Conditions 会直接写「算不出来」的原因
kubectl get hpa web -o yaml | sed -n '/status:/,$p'
kubectl describe hpa web

# 指标链是否通：metrics-server → apiserver → HPA
kubectl top pod web-0
kubectl get apiservice v1beta1.metrics.k8s.io

# VPA 的推荐值（updateMode 为 Off 时只看不动）
kubectl describe vpa web-vpa | sed -n '/Recommendation/,$p'

# CA 的判断依据：有没有 Pending 且不可调度的 Pod
kubectl get pod -A --field-selector status.phase=Pending

「CPU 70% 却不扩」的排查顺序很固定：先看 HPA 的 Conditions。如果是 failed to get cpu utilization: missing request for cpu，就是没设 requests；如果是 unable to fetch metrics，就是 metrics-server 或 apiservice 不通；如果 Conditions 正常但 Replicas 不动，就看是不是已经到 maxReplicas，或者 scaleDown 的稳定窗口把扩容也压住了（少见，但行为配置写错时会发生）。

VPA 有两个使用上的硬约束：它会重建 Pod（除了 Off 和 Initial 之外的模式），所以不适合对可用性敏感、启动又慢的服务；它不要和 HPA 同时对同一个资源做决策，否则一个想加副本、一个想改 requests，指标口径互相打架，结果是来回震荡。常见的组合是 HPA 管副本（用 CPU 或 QPS），VPA 只出推荐值由人改，或者 VPA 管内存、HPA 管 CPU——后者的前提是你清楚这两个指标不会互相影响。

扩容是有延迟的，而延迟要靠余量兜。HPA 的链路是「采集指标 → 计算 → 改 replicas → 调度 → 拉镜像 → 启动 → Ready」，节点不够还要再加一段 CA 建节点的时间。整条链路走完可能是几分钟，而流量峰值往往只有几十秒。所以关键服务不能只靠 HPA，得有最低副本数保证余量，或者用低优先级的占位 Pod 做资源预留。

面试怎么答：「HPA 只改副本数，指标默认来自 metrics-server，CPU 利用率是相对 requests 算的，所以没设 requests 它就算不出来。VPA 改 requests 但通常要重建 Pod，不要和 HPA 对同一资源同时开。Cluster Autoscaler 是看到 Pending 才加节点，链路很长，所以关键服务的容量要靠 minReplicas 留余量，不能指望它秒级响应。」

模块 7

滚动更新：maxSurge 与 maxUnavailable 在算什么

这两个参数不是「速度调节旋钮」，它们在算容量边界：发布过程中最多能多出几个 Pod、最多能少几个可用 Pod。算错的方向只有两个——要么发布太慢，要么发布期间容量不够。

参数含义默认取 0 的后果
maxSurge允许超出期望副本数的 Pod 数（可以是数字或百分比）25%必须先删后建，发布期间容量下降
maxUnavailable允许不可用的 Pod 数25%必须先建后删，需要额外的节点资源
minReadySecondsPod Ready 之后还要稳定多久才算可用0刚 Ready 就继续推进，错误暴露得更快
progressDeadlineSeconds多久没进展就标记为失败600卡住时不报警，rollout status 一直等
revisionHistoryLimit保留多少个旧 ReplicaSet 供回滚10回滚不了太远的版本

算一笔账：副本 10，maxSurge 25% 就是 3（向上取整），maxUnavailable 25% 就是 2（向下取整）。发布时的峰值是 13 个 Pod，谷值是 8 个可用。这两个数字要提前和容量对齐：如果峰值 13 个放不下（节点资源不够），发布就会卡在「新 Pod Pending」；如果谷值 8 个撑不住流量，发布期间就会超时。把它们同时设为 0 是不允许的，apiserver 会直接拒绝。

# 看发布进度和卡住的原因
kubectl rollout status deploy/web --timeout=180s
kubectl rollout history deploy/web
kubectl describe deploy/web | sed -n '/Conditions/,$p'

# 暂停/恢复：可以做一次「只起新版本、不切完」的观察
kubectl rollout pause deploy/web
kubectl rollout resume deploy/web

# 回滚到上一个版本（ReplicaSet 还在，不需要重新构建）
kubectl rollout undo deploy/web

# PDB：约束自愿中断，不约束节点压力驱逐
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  minAvailable: 2          # 或 maxUnavailable: 1
  selector:
    matchLabels: {app: web}

PDB 有一个经典的自锁：minAvailable 写成 100% 或者等于副本数，drain 就永远等不到许可。因为滚动更新或 drain 必须先摘掉至少一个，而 PDB 说「一个都不能少」。现象是 kubectl drain 卡住、事件里反复出现 Cannot evict pod as it would violate the pod's disruption budget。这类问题在节点维护时最容易撞上，而且因为是「保护」而不是「故障」，很容易被误判成集群卡了。

PDB 和滚动更新的关系也要说清：它们不互相约束。Deployment 的滚动更新直接删旧 Pod，不走 eviction API，所以 PDB 管不到它；PDB 只在 drain、节点维护、descheduler 这类自愿中断场景生效。指望 PDB 来保证「发布时至少有几个可用」，方向是错的——那个要靠 maxUnavailable 和 readiness。

一套能直接用的参数组合：副本 ≥ 3，maxSurge 1 到 25%，maxUnavailable 0 到 1，minReadySeconds 10 到 30 秒，progressDeadlineSeconds 保持默认或按启动时间放大，再给关键服务配一个 minAvailable 为「副本数减一」的 PDB。这套组合的取舍是「发布慢一点，但不掉容量」，适合大多数在线服务。

面试怎么答：「maxSurge 和 maxUnavailable 算的是发布期间的容量上下界，两个都是百分比时一个向上取整一个向下取整，不能同时为 0。minReadySeconds 决定新 Pod 要稳定多久才算可用，它直接影响错误暴露的速度。PDB 只约束 drain 这类走 eviction API 的自愿中断，滚动更新不走那条路，所以 PDB 不能替代 maxUnavailable 的作用。」

模块 8

优雅退出：摘流量和发信号是并行的

这是本期最该记住的一节。绝大多数「发布时 502」的根因，是一个时序假设错了：很多人以为系统会「先把流量摘干净，再通知进程退出」。实际不是——这两件事同时开始，而摘流量要经过好几个组件才生效。

kubectl delete pod / Deployment 滚动更新
│
├─ t=0    Pod 标记 deletionTimestamp，状态变 Terminating
│         ├─ EndpointSlice 控制器开始把它从后端移除（异步，要传播）
│         └─ kubelet 开始执行 preStop hook（如果有）
│
├─ t=0~  kube-proxy 同步规则、Ingress controller 更新 upstream
│         这两个都有延迟：秒级到几十秒，取决于规模和实现
│         这段时间里，新连接还在往这个 Pod 打
│
├─ t=preStop 结束 → kubelet 发 SIGTERM
│         应用应该：停止接受新请求、等在途请求完成、关闭连接池
│
├─ t=preStop + 应用退出时间 → 容器退出
│
└─ t=terminationGracePeriodSeconds（默认 30s）到期 → SIGKILL，退出码 137
          preStop 的耗时是算在这 30 秒里的

看这张时序就明白 preStop 里 sleep 几秒的作用了：它不是「让应用多活一会儿」，是「给规则传播留时间」。在这几秒里，应用还在正常处理请求，但新的连接已经不再被路由过来。等传播完成，再让它退出，就不会有人打到已经关闭的端口。

现象原因改哪里
发布时稳定 502，持续十几秒没有 preStop，SIGTERM 后进程立即关闭监听，规则还没同步完加 preStop sleep 5-15 秒，同时应用要优雅关闭
偶发 connection reset应用收到 SIGTERM 直接 exit，在途请求被切断应用侧等 in-flight 请求结束，再退出
Pod 总是等满 30 秒才消失应用忽略了 SIGTERM，只能等 grace 到期被 SIGKILL修信号处理；顺便确认 PID 1 是应用本体
退出码 137，日志没有 shutdown 记录grace 不够，preStop + 退出耗时超了调大 terminationGracePeriodSeconds，别只调 preStop
SIGTERM 到不了应用CMD 用了 shell 形式，PID 1 是 sh，信号不转发改成 exec 形式，或用 tini/dumb-init
# 正确的三段式：给规则传播留时间 + 应用自己优雅关闭
spec:
  terminationGracePeriodSeconds: 60        # 要大于 preStop + 应用退出时间
  containers:
    - name: web
      lifecycle:
        preStop:
          exec:
            command: ["sleep", "10"]       # 这 10 秒算在 60 秒里
      # exec 形式，保证 PID 1 是应用，能收到 SIGTERM
      command: ["/app/server"]
      args: ["--port=8080"]

# 验证：删一个 Pod，盯着它什么时候从 EndpointSlice 消失、什么时候退出
kubectl delete pod web-0 &
watch -n1 'kubectl get endpointslice -l kubernetes.io/service-name=web -o wide'

# 确认进程收到的信号（应用日志里应该有 shutdown 记录）
kubectl logs web-0 --previous | tail -20

「sleep 10 秒」这个做法看起来很土，但它解决的是一个真实的不确定性：你无法知道规则传播需要多久。kube-proxy 的同步周期、Ingress controller 的 reload 延迟、客户端的连接池、上游 LB 的健康检查间隔，每一层都是变量。用一个略大于最坏情况的等待，比精确计算可靠得多。

应用侧要配合的部分不能省。收到 SIGTERM 之后，正确的顺序是：停止接受新连接 → 等在途请求完成（设一个上限）→ 关闭连接池和后台任务 → 退出。只做「收到信号就 exit」等于把在途请求全扔掉，preStop 再长也救不回来，因为那些请求是在 sleep 期间进来的。

kubectl get pod NAME -o jsonpath='{.spec.terminationGracePeriodSeconds}'先确认预算有多大，未设置时是 30 秒
kubectl get pod NAME -o jsonpath='{.spec.containers[*].lifecycle}'有没有 preStop，执行的是什么命令，sleep 几秒
kubectl get pod NAME -o jsonpath='{.spec.containers[*].command}'确认是 exec 形式，不是 sh -c 包一层
kubectl get endpointslice -l kubernetes.io/service-name=SVC -w删 Pod 时盯着后端什么时候消失，量出传播延迟
kubectl logs NAME --previous | tail -20有没有 shutdown 记录，决定了 SIGTERM 到底有没有到应用
kubectl get pod NAME -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'137 是被 SIGKILL，说明预算不够；0 或 143 才是正常收尾
两个时间要满足这个不等式：preStop 时长 + 应用优雅退出时长 < terminationGracePeriodSeconds。左边超了右边，kubelet 会直接 SIGKILL，应用来不及 flush，日志里什么都没有，退出码 137——看起来像被 OOM，其实是时间不够。改的时候两个一起看，只调 preStop 会把余量吃掉。

面试怎么答：「删 Pod 时，摘 Endpoints 和发 SIGTERM 是并行的，不是串行。规则传播有延迟，所以要在 preStop 里 sleep 几秒，让流量先停下来再退出。grace period 要大于 preStop 加应用退出时间，否则会被 SIGKILL。另外 CMD 必须是 exec 形式，shell 形式下 PID 1 是 sh，SIGTERM 到不了应用。」

模块 9

探针设计：它是发布系统的一部分，不是装饰

很多人把探针当成「加个 /healthz 就完事」。但在发布的语境里，探针决定了三件事：什么时候开始接流量、什么时候被摘掉、什么时候被重启。这三个动作直接对应发布的质量。

探针成功意味着失败的动作设计要点
startup启动完成，可以开始做别的检查重启容器预算要覆盖最慢启动路径，成功后自动让位
readiness能处理请求从 Endpoints 摘除，不重启反映「持续不可用」，不是「此刻有点忙」
liveness进程还值得救重启容器只查自己，绝不查下游

先说 liveness 的边界，因为它的错误代价最大。判断标准只有一句：「这个检查失败，重启能修好吗？」能——比如死锁、事件循环卡住、内存泄漏到无法服务，那就该重启。不能——比如数据库连不上、下游超时、配置中心不可用，重启只会让所有副本同时进入冷启动，把一次下游抖动放大成全站故障。

readiness 的边界相反：它应该表达「我现在不该接流量」，所以查依赖是合理的。但有两个前提：一是失败要能快速恢复（依赖回来就自动恢复，不需要人工干预），二是不要用它表达瞬时状态。查「连接池是否有空闲连接」这种指标，会让 Pod 在 Endpoints 里反复进出，客户端看到的是间歇性 502，比稳定地少一个副本更糟。

# 一套能直接用的三段式（注意预算和时间的关系）
startupProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 10
  failureThreshold: 30          # 最多等 300 秒，要覆盖最慢启动
readinessProbe:
  httpGet: {path: /ready, port: 8080}
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2           # 10 秒内摘流量，够快但不敏感
livenessProbe:
  httpGet: {path: /healthz, port: 8080}
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 3           # 约 30 秒才重启，容忍一次长 GC

# 确认探针真的在被执行（失败会写进 Events，也会反映在 ready 状态）
kubectl describe pod web-0 | grep -i -E 'probe|unhealthy'
kubectl get pod web-0 -o jsonpath='{.status.containerStatuses[0].ready}{"\n"}'

# 探针端点要独立于业务路由：不要经过鉴权中间件
kubectl exec web-0 -- wget -qO- http://127.0.0.1:8080/healthz

参数之间的关系要会算：最大等待时间约等于 periodSeconds 乘 failureThreshold。默认 period 是 10 秒、failureThreshold 是 3，所以默认配置下要连续失败三次、大约 30 秒才会动手。很多人以为「探针失败就立刻重启」，把 failureThreshold 调成 1、period 调成 1 秒，结果一次 GC 停顿就把自己重启了——这是自己制造的故障。

几个容易忽略的设计点：探针的 timeoutSeconds 必须小于 periodSeconds，否则上一次没超时下一次又开始了；探针端点要独立于业务路由，不要经过鉴权、限流、灰度中间件，否则中间件一抖，探针全挂；用 exec 探针要注意它每次都会 fork 一个进程，高频率下开销不小，能用 httpGet 就别用 exec；探针失败会把日志刷满，注意别让它变成日志量的主要来源。

探针还有一个发布期的副作用：它会把发布卡住。新 Pod 一直不 Ready，滚动更新就不会继续推进，超过 progressDeadlineSeconds 之后 Deployment 会被标记为失败（但不会自动回滚）。所以「发布卡住」时，第一件事是看新 Pod 的 readiness 为什么不过，而不是反复 rollout restart。

面试怎么答：「探针不是三个独立的开关，它们分别对应启动预算、接流量、重启三个决策。liveness 的判断标准是『重启能不能修好』，所以不能查下游；readiness 可以查依赖，但要能自动恢复；startup 的预算约等于 failureThreshold 乘 periodSeconds。最大等待时间默认是 30 秒这个量级，把它调成 1 秒等于让 GC 来决定你的可用性。」

模块 10

10 个坑：参数之间的乘法关系

这一节的坑有个共同点：单个参数看起来都合理，组合起来才出问题。maxUnavailable 和 PDB 组合、preStop 和 grace 组合、HPA 和 requests 组合——每一对都有一个隐含的不等式。

1
maxSurge 和 maxUnavailable 都设成 0
apiserver 会直接拒绝，因为这意味着「既不能多也不能少」，滚动更新无法推进。至少放开一个：要么多起 Pod 换容量，要么牺牲一点容量换速度。
2
PDB 的 minAvailable 等于副本数
drain 永远拿不到许可，节点维护会卡死，事件里反复报 would violate the pod's disruption budget。正确写法是 maxUnavailable: 1 或 minAvailable 比副本数少一个。
3
用硬反亲和做高可用，副本数又超过节点数
多出来的副本永久 Pending，而且不报错，只是容量少一半。想要「尽量打散」应该用拓扑分布约束，它允许倾斜但不会卡死。
4
不设 requests，却指望 HPA 按 CPU 扩
CPU 利用率的分母是 requests 之和，没设就计算不出来，HPA 的 Conditions 会写 missing request for cpu。HPA 依赖 requests 才能工作。
5
preStop 的 sleep 时长算在 grace 之外
它算在里面。grace 30 秒、preStop sleep 30 秒，应用就一点退出时间都没有，直接被 SIGKILL，退出码 137，日志里什么都没有。
6
CMD 用 shell 形式，却指望能优雅退出
shell 形式下 PID 1 是 sh，它不会把 SIGTERM 转发给子进程。应用等不到信号，只能等 grace 到期被杀。要改 exec 形式，或者引入 tini 之类的 init。
7
liveness 里查数据库
数据库一抖，所有副本同时重启，重启中的实例又加重数据库负担，形成级联。发布期间尤其致命：你分不清是「新版本有问题」还是「数据库在抖」。
8
CPU 型 HPA 用在 IO 密集服务上
IO 密集服务的瓶颈在等待，CPU 一直很低，HPA 永远不扩，而请求已经在排队。这类服务应该用 QPS、并发数或队列长度这类自定义指标。
9
VPA 和 HPA 同时对 CPU 做决策
VPA 改 requests，HPA 的利用率分母跟着变，两个控制器互相追着改，副本数和 requests 一起震荡。同一种资源只能有一个主导者。
10
只靠 HPA，不留容量余量
HPA 到 Pod Ready 要几十秒，节点不够还要等 Cluster Autoscaler 建节点，可能几分钟。流量峰值往往只有几十秒，等扩出来已经过去了。

面试怎么答：挑一个能算数字的讲。比如「我们发布时 502，一开始以为是镜像有问题，后来发现是没配 preStop，SIGTERM 之后进程立刻关监听，而 Ingress 的 upstream 还要几秒才更新完。加了 preStop sleep 8 秒、grace 调到 45 秒，并且让应用在 SIGTERM 后等 10 秒再退出，502 就没了。」有数字、有时序、有验证，比背十条坑有说服力。

自测

六道题

1. kube-scheduler 的调度过程，正确的描述是？
正确答案：先过滤再打分。过滤阶段是硬条件（资源、污点、亲和、卷、端口），任何一条不满足该节点就被排除；打分阶段只在通过的节点里比较资源均衡度、镜像本地性、拓扑分散等偏好，取最高分。这也是为什么 Pending 只会由过滤失败引起，打分低不会导致 Pending。
2. 一个 Deployment 配了硬反亲和（topologyKey 为 hostname，labelSelector 匹配自身），副本数 6，集群只有 4 个节点。会发生什么？
正确答案：4 个 Running、2 个永久 Pending。硬反亲和是逐 Pod 判定的：前 4 个分别落到 4 个节点，第 5、6 个在所有节点上都会与同标签的 Pod 冲突，于是永久 Pending 并在 Events 里报 didn't match pod anti-affinity rules。它不会自动放宽，也不会让已在跑的 Pod 让位，结果就是容量静默少三分之一。
3. HPA 配了 CPU 目标 60%，但一直不扩容，describe hpa 里出现 failed to get cpu utilization: missing request for cpu。原因是？
正确答案：缺 requests。HPA 的 CPU 利用率是「实际用量 ÷ requests 之和」，没有 requests 这个分母，百分比无从计算，HPA 只能报错并停止决策。如果只设了 limits，很多情况下 requests 会被默认成 limits，反而「碰巧能用」，但那等于按上限预留资源，调度会变紧。metrics-server 缺失报的是 unable to fetch metrics，文案不同。
4. 一个 Deployment 副本数是 3，PDB 配了 minAvailable: 3。执行 kubectl drain 维护节点时会发生什么？
正确答案：drain 卡住。PDB 的语义是「自愿中断时至少要保留这么多可用」，minAvailable 等于副本数意味着一个都不能少，而 drain 必须先驱逐至少一个，于是永远得不到许可。正确做法是 minAvailable 设为副本数减一，或改用 maxUnavailable: 1。注意 PDB 只约束 drain 这类走 eviction API 的操作，滚动更新不受它约束。
5. 每次滚动发布都会出现十几秒的 502，新 Pod 的 readiness 是正常的。最可能的原因？
正确答案：摘流量与停进程的竞态。删除 Pod 时，从 Endpoints 摘除和发送 SIGTERM 是并行的，kube-proxy 与 Ingress 更新 upstream 都有延迟。如果进程收到 SIGTERM 就关闭监听，这段窗口里到达的请求就会 502。修法是加 preStop sleep 几秒给规则传播留时间，同时应用侧要等在途请求处理完再退出。
6. 关于污点的三种 effect，下面哪个说法是对的？
正确答案：NoExecute 才会驱逐。NoSchedule 只影响新 Pod 的调度决策，已在运行的 Pod 不受影响；PreferNoSchedule 是软约束，没有别的地方可放时仍然会调度过去；NoExecute 既阻止新 Pod，也会驱逐不容忍的存量 Pod，tolerationSeconds 可以让它多留一会儿。节点 NotReady 时控制面加的就是 NoExecute 类污点。
