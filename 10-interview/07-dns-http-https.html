DNS 与 HTTP/HTTPS 高频问：从解析到握手

no-cache 不是不缓存，301 会被浏览器记很久——这些细节决定你答得像不像做过。

读之前先答一句：Cache-Control 里哪个指令是「真的不存」，哪个只是「存了但要先问」？
开始前

一次「优化」，让老用户跳了三个月的旧域名

迁移域名的时候，有人顺手把 302 改成了 301，理由是「301 对 SEO 更好」。上线两周后发现新域名有问题，配置回滚成 302。结果监控显示：还有三分之一的用户，访问老域名依然被跳到新域名——因为浏览器已经把 301 记在自己的缓存里了，服务端改回什么都没用。

这是 HTTP 里最典型的「语义没吃透」事故。状态码、缓存指令、DNS 的 TTL，这些东西的共同点是：它们不是配置项，是协议约定。写下去的那一刻，控制权就交给了浏览器、CDN 和递归解析器。

现场直觉答案真实原因
接口加了 no-cache，还是返回旧数据no-cache 就是「不缓存」，肯定生效了no-cache 的意思是「可以存，但每次用之前必须回源验证」。真正不存的是 no-store
域名改了解析，有的地方生效有的没生效DNS 出问题了，或者运营商劫持每一层缓存都按 TTL 走。旧 TTL 是 3600，就意味着一小时内一定有地方还拿着旧记录
App 报证书错误，浏览器打开正常App 的 SSL 库有 bug服务端没发中间证书。浏览器会自己去补链，Java 和很多移动端 SDK 不会

这一篇按「一个请求从域名到响应」的顺序走：DNS 解析链路 → 记录类型与 TTL → HTTP 版本演进 → 连接复用 → 缓存 → 状态码 → 认证 → HTTPS。每一节都落一句面试话术，因为这个方向的面试题几乎全是「你知道这个字段的准确语义吗」。

为什么这些细节值钱：「HTTP 有哪些状态码」谁都能说几个，「301 会被浏览器长期缓存、302 不会，所以域名迁移期间绝对不能用 301 做临时跳转」——这句话一说，面试官就知道你处理过真实的迁移。细节不是背出来的，是被坑出来的。

面试落点：「这套东西我记的是语义而不是配置：哪些能缓存、缓存多久、谁来验证、谁能改。因为一旦发出去，浏览器和 CDN 的行为就不受你控制了，回滚配置并不等于回滚效果。」

模块 1

DNS 解析链路：谁在递归，谁在迭代

「说说 DNS 解析过程。」大部分人能背出「浏览器缓存 → 系统缓存 → 本地 DNS → 根域名服务器 → 顶级域名服务器 → 权威服务器」。背得没错，但一追问「本地 DNS 和根之间是递归还是迭代」，就有一半人答反。

先把两个词分清：递归是「你帮我查到底，我只要最终答案」；迭代是「你告诉我下一步该问谁，我自己去问」。客户端（浏览器、你的程序）向递归解析器发起的查询是递归的，报文里那个 RD 标志位就是「Recursion Desired」。而递归解析器去问根、问 TLD、问权威，用的是迭代——根只会告诉你「去问这个 TLD 的服务器」，不会替你去问。

环节谁在做缓存什么怎么绕过它
浏览器缓存浏览器自己按域名记的解析结果，时长受浏览器自己的策略影响换一个浏览器或无痕窗口
系统缓存systemd-resolved / nscd / 系统 DNS 客户端按 TTL 缓存，可能还有自己的上限resolvectl flush-caches，或重启对应服务
hosts 文件nsswitch 的 files 模块不做缓存，直接命中看 /etc/hosts 里有没有写死
递归解析器运营商 DNS、公司内网 DNS、公共 DNS真正的解析结果缓存，按权威给的 TTL换 @8.8.8.8 对比，能立刻判断是不是它的问题
权威服务器域名托管商不缓存，它是数据的源头dig +trace 一路问下去

hosts 的优先级比很多人想的高：nsswitch.conf 里 hosts: files dns 这行的顺序决定了先查文件还是先查 DNS。有人为了临时测试往 hosts 里加了一行，半年后忘了，于是「只有这台机器解析到旧 IP」——这类问题查 DNS 查一天也查不出来。

# 完整答案：谁回的、TTL 还剩多少、走没走递归
dig example.com +noall +answer +stats

# 只要 IP
dig +short example.com

# 从根开始一路迭代，看每一层返回了什么（这一步最能说明「迭代」）
dig +trace example.com

# 直接问指定的解析器，用来对比不同递归解析器的结果
dig @8.8.8.8 example.com +short
dig @10.0.0.2 example.com +short

# 系统层面的解析结果（会走 nsswitch，能看到 hosts 的影响）
getent hosts example.com
resolvectl query example.com 2>/dev/null

还有一个常被问的细节：一次解析要几个 RTT。缓存全冷的情况下，递归解析器要依次问根、TLD、权威，至少三个往返，加上客户端到解析器这一段，冷启动可能几十到上百毫秒。这也是为什么「第一次访问慢、后面快」——不是服务器慢，是解析链路在跑。

面试落点：「客户端到递归解析器是递归查询，解析器到根、TLD、权威是迭代查询。缓存有四层：浏览器、操作系统、递归解析器、以及权威侧的 TTL。排查解析问题时，我会先用 dig @不同服务器 对比，一步就能判断是权威配错了还是某一层缓存没到期。」

模块 2

记录类型与 TTL：切换域名时最容易翻车的地方

「域名换了 IP，为什么有的用户还是访问旧地址？」这个问题每年都在发生，答案永远只有一个：你没有提前把 TTL 降下来。

类型作用容易踩的点
A域名 → IPv4 地址可以有多条，解析器会轮询或按策略返回
AAAA域名 → IPv6 地址客户端可能优先用 AAAA。只配了 A 但客户端强行走 IPv6，就会连不上
CNAME别名，指向另一个域名不能放在 zone 顶点（和 SOA、NS 冲突）；链条越长解析越慢
MX邮件服务器，带优先级只能指向域名，不能直接写 IP
TXT任意文本，常用于域名验证、SPF、DKIM一条记录有长度上限，超了要拆成多段
NS这个 zone 由哪些权威服务器负责改 NS 是改「谁来回答」，和改 A 记录完全是两件事
SOAzone 的元信息，含序列号和负缓存时长它的 minimum 字段决定「查不到」这个结果能缓存多久
CAA限定哪些 CA 能给这个域名签证书配错了会导致证书续签失败，而且报错很不直观

CNAME 那条「不能放顶点」值得展开：zone 顶点必须要有 SOA 和 NS 记录，而 CNAME 的语义是「这个名下不应该有其他任何记录」，两者冲突。所以 example.com 本身不能是 CNAME，只能 www.example.com 是。云厂商提供的 ALIAS / ANAME 就是绕开这个限制的方案——它在解析时把目标域名的 A 记录取回来，对外表现得像 A 记录。

TTL 的取舍是个纯工程问题：TTL 长，解析快、权威压力小，但切换慢；TTL 短，切换快，但解析次数多。标准做法是「切换前至少一个旧 TTL 的时间把 TTL 降下来」——比如现在是 3600，你要明天切，那就今天先把 TTL 改成 60，等一天让所有缓存都过期成 60 秒，明天切换时最多一分钟就全量生效，切完稳定了再把 TTL 升回去。

还有一个反直觉的点：「查不到」也是会被缓存的。如果你查询一个不存在的域名，解析器会拿到 NXDOMAIN，这个「不存在」的结论同样会缓存一段时间。缓存多久由权威返回的 SOA 记录里的 minimum 字段决定（实际取值还会和 SOA 自身的 TTL 取较小值）。所以刚配好一条记录却「有的地方还解析不到」，很可能不是没生效，而是之前的失败结果还在负缓存里。

# 看 TTL 还剩多少（第二列就是剩余秒数，递归解析器会递减）
dig example.com +noall +answer
# example.com.  213  IN  A  93.184.216.34

# 连续查两次，TTL 应该递减；不递减说明命中了不同的解析器
dig @8.8.8.8 example.com +noall +answer

# 查 CNAME 链，看经过了几跳
dig www.example.com CNAME +short

# 查 SOA，看负缓存时长（最后一个数字是 minimum）
dig example.com SOA +short

# 权威侧到底配了什么（绕过所有缓存，直接问权威）
dig @ns1.example.com example.com A +norecurse
「TTL 设 0 就等于不缓存」是个误解。TTL 0 只是告诉解析器「不要长期存」，很多解析器仍会短暂持有，浏览器也可能自己做一层缓存。真正的即时切换只能靠「提前降 TTL + 双端并存」：新旧 IP 同时提供服务一段时间，等流量自然迁移完再下线旧的。

面试落点：「切域名之前我一定会先降 TTL，至少提前一个旧 TTL 的时长，切完再升回去。因为 TTL 是权威告诉全世界『你可以记多久』，说出去就收不回来了。另外 CNAME 不能放 zone 顶点，这点经常被拿来考『你知不知道 ALIAS 是干什么的』。」

模块 3

HTTP 版本演进：队头阻塞被解决了三次

问「HTTP/1.1 和 HTTP/2 的区别」，答「多路复用」能过；追问「那 HTTP/2 还有没有队头阻塞」，就要看你是不是真的理解它解决的是哪一层的阻塞。

版本传输关键变化还剩什么问题
1.0TCP，默认短连接每个请求一个连接，用完就关每次都要握手，慢
1.1TCP，默认持久连接连接复用、Host 头（一个 IP 多个站点）、分块传输、缓存控制增强应用层队头阻塞：一个连接上请求必须按序返回
2TCP，二进制分帧多路复用（一个连接跑多个流）、HPACK 头压缩、流优先级TCP 层队头阻塞：丢一个包，这条连接上所有流都等
3QUIC（基于 UDP）0-RTT/1-RTT 建连、流级独立重传、连接迁移UDP 可能被某些网络限制；实现和调试都更复杂

三次「解决队头阻塞」，解决的是三个不同的东西，这是本节最值钱的一句话：

  • HTTP/1.1 的管道化想解决应用层的排队：一次性发多个请求，不用等前一个回来。但响应必须按请求顺序返回，前一个慢，后面全堵着，所以浏览器基本不用它，改成了「对同一个域名开 6 个左右并发连接」这种笨办法。
  • HTTP/2 的多路复用真正解决了应用层：把请求拆成帧，给每个帧打上流 ID，响应可以乱序返回再由客户端按流 ID 组装。所以一个连接就够了，不用再开六个。
  • HTTP/3 的 QUIC解决的是传输层：HTTP/2 再怎么多路复用，底下还是一条 TCP。TCP 保证「按序交付」，一旦中间丢了一个包，后面的数据即使到了也要在内核缓冲区等着，所有流一起卡。QUIC 把「有序」的责任上移到流一级，一个流丢包只影响这个流。

还有一个常被追问的点：HTTP/2 一定要 HTTPS 吗？协议规范上不强制，明文版本叫 h2c。但所有主流浏览器都只在 TLS 上启用 HTTP/2，所以做 Web 站点时，事实上就是「HTTPS 才有 HTTP/2」。这也反过来推动了全站 HTTPS。

顺带说一个已经过时的最佳实践：域名分片。HTTP/1.1 时代为了绕过「每个域名 6 个连接」的限制，会把静态资源拆到多个域名上。到了 HTTP/2，一个连接就能跑几十个流，域名分片反而要多建连接、多一次 DNS 和 TLS，是纯粹的反优化。面试里能主动说「这个手段在 HTTP/2 下已经不该用了」，比背版本特性更有分量。

# 看服务端到底协商到了哪个版本
curl -sI https://example.com | head -1
curl -s -o /dev/null -w '%{http_version}\n' https://example.com

# 强制用某个版本对比（服务端不一定都支持）
curl --http1.1 -sI https://example.com | head -1
curl --http2   -sI https://example.com | head -1

# 看 ALPN 协商出了什么协议
openssl s_client -connect example.com:443 -servername example.com -alpn h2,http/1.1 < /dev/null 2>&1 | grep ALPN

面试落点：「HTTP/2 解决的是应用层的队头阻塞，靠二进制分帧和流 ID 做多路复用；但底下还是 TCP，丢一个包整条连接都等，这是传输层的队头阻塞，要 HTTP/3 用 QUIC 才能解决。所以『HTTP/2 有没有队头阻塞』这个问题，答案取决于是哪一层。」

模块 4

连接复用：keep-alive 的坑在「谁先关」

服务端 keepalive_timeout 是 75 秒，客户端连接池的 idle 是 60 秒，看起来很安全。但链路上还有一个负载均衡，它的空闲超时是 30 秒——于是每隔半分钟就有一批请求报 connection reset。

连接复用的收益很好算：省掉 TCP 三次握手（一个 RTT）和 TLS 握手（一到两个 RTT）。跨地域 RTT 40ms 的话，一个请求光建连就要 100ms 上下，而复用之后这部分接近 0。所以只要是高频调用，连接池几乎是必选项。

它的成本也好算：连接是有状态的，而链路上每一个中间设备都有自己的状态超时。NAT 网关、四层负载均衡、云防火墙，都会在空闲一段时间后悄悄删掉自己的表项，而且通常不通知两端。这时连接在两端看来还活着，实际已经断了，下一次发包才会暴露——表现为 connection reset，或者请求发出去没有任何响应直到超时。

角色典型配置该怎么配合
服务端keepalive_timeout 决定空闲多久后关连接不要设太长，长连接会占 fd 和内存；也不要太短，否则复用率低
客户端连接池idle 超时、最大连接数、最大复用次数idle 要小于服务端和中间设备的超时，保证总是客户端先关
中间设备NAT / LB 的空闲表项超时，常见几分钟心跳间隔必须小于这个值，否则连接被静默删除
HTTP 层Connection: close 表示这次用完就关HTTP/1.1 默认持久，HTTP/2 里这个头没有意义

为什么强调「客户端先关」？因为主动关闭的一方会走完整的四次挥手，双方状态都干净；如果服务端先关，客户端手里的连接成了「半关闭」的陈旧连接，下一次借出去发请求就会失败。连接池一般会有「借出前检测」，但那个检测本身也有成本，而且很多实现只是检查 socket 是否可写，检测不出对端已经发了 FIN。

HTTP/2 把这个问题放大了一点：一个连接上跑着几十个流，连接一断，所有在途请求一起失败。所以 HTTP/2 的连接池通常只保留少量连接（甚至一个），靠 GOAWAY 帧做优雅关闭——服务端要下线时先发 GOAWAY，告诉客户端「别再在这个连接上开新流了」，等在途的流跑完再关。

连接池该开多大，是个能算的问题，不用拍脑袋。粗算用一条：需要的并发连接数约等于「每秒请求数 × 单个请求的平均耗时」。每秒 200 个请求、每个耗时 50 毫秒，那同一时刻在途的请求就是 10 个左右，池子开 20 到 30 就够，剩下的余量留给抖动。开成 500 的后果不是更快，而是对端要多维护 500 个连接、多 500 份 TLS 会话状态，自己的线程和 fd 也被占住，高峰期反而更容易排队。

怎么确认复用真的生效了，也有可观测的量。看服务端的 accept 速率：如果 QPS 是 200，accept 也是 200，说明每个请求都在新建连接，复用完全没起作用；正常情况 accept 应该远小于请求数。另一个信号是 TIME_WAIT 的数量突然上涨——它意味着大量连接在被反复创建和关闭，而不是被复用。

# 看响应头里的连接语义
curl -sI https://example.com | grep -iE 'connection|keep-alive'

# 复用同一个连接发多个请求，观察连接是否被重新建立
curl -sv https://example.com/a https://example.com/b 2>&1 | grep -E 'Re-using|Connected to'

# 服务端：ESTAB 应该稳定在一个区间，而不是跟着 QPS 一起涨
ss -tan state established '( sport = :443 )' | wc -l

# 连接反复建立/关闭的信号：TIME_WAIT 在涨
ss -tan state time-wait | wc -l
一个实用的排查技巧：如果「每隔 N 秒出现一批 reset」，先别怀疑代码，去量一下 N。N 约等于某个中间设备的空闲超时，那基本就是它删表了。把心跳或 idle 调到比 N 小，问题立刻消失。这种「周期性故障」的排查，量周期比看日志快得多。

面试落点：「连接复用省的是握手 RTT，代价是要处理链路上各种空闲超时。我的原则是客户端的 idle 一定小于服务端和中间设备的超时，让客户端先关；HTTP/2 还要靠 GOAWAY 做优雅下线，不然一个连接断了会带走几十个在途请求。」

模块 5

缓存：no-cache 和 no-store 差的是「存不存」

「加个 no-cache 让它别缓存。」这句话是缓存事故的主要来源。no-cache 的名字起得太坑，它的真实语义是「可以存，但每次用之前必须回源确认」，真正「别存」的是 no-store。

强缓存
还在 max-age 内，浏览器直接用本地副本，一个请求都不发。最快，但也最不听话。
协商缓存
有效期过了，带 ETag 或 Last-Modified 去问源站。回 304 就继续用，代价是一个 RTT。
不该缓存
用户相关的响应、一次性令牌、实时余额。这类东西要用 no-store，而不是 no-cache。

缓存分两类，判断顺序是先看强缓存，再看协商缓存：

  • 强缓存：浏览器判断还在有效期内，直接用自己的副本，一个请求都不发。控制字段是 Cache-Control: max-age=N，老版本用 Expires（绝对时间，受客户端时钟影响，现在只作为兜底）。
  • 协商缓存：有效期过了，浏览器带着验证字段去问源站「这个还能用吗」。源站回 304 就继续用本地副本（304 不带响应体），回 200 就传新的。控制字段是 ETag 配 If-None-Match，或者 Last-Modified 配 If-Modified-Since。
指令准确语义常见误用
no-store完全不存储，连磁盘和内存都不留用 no-cache 代替它，结果敏感响应还是被存下来了
no-cache可以存，但每次使用前必须向源站验证以为它等于「不缓存」，结果只是每次多一次 304 往返
max-age=NN 秒内可以直接用，不问源站给 HTML 设很长，发版后用户拿不到新页面
s-maxage=N只对共享缓存（CDN、代理）生效，优先级高于 max-age以为它也能控制浏览器，其实浏览器会忽略它
private只允许浏览器这类私有缓存存，CDN 不能存该加没加，导致带用户信息的响应被 CDN 缓存并广播给别人
public谁都能存，包括 CDN给带 Cookie 的响应加 public，等于把个性化内容公开
must-revalidate过期后不许用旧副本，必须验证成功才能用以为它能替代 no-cache，其实只管「过期之后」
immutable在有效期内连「刷新」都不用回源给会变的资源加，用户按刷新也拿不到新的
stale-while-revalidate过期后先给旧副本，同时后台去更新对一致性要求高的接口用，用户读到旧数据还不自知

几个必须说清的细节：

  • Cache-Control 的优先级高于 Expires。两个都在时，看 Cache-Control。这条是送分题，但答错的人不少。
  • no-store 和 no-cache 同时出现时，no-store 更严格，等于不存。反过来只写 no-cache，响应还是会被写进缓存。
  • ETag 比 Last-Modified 更准。Last-Modified 只精确到秒，同一秒内改两次就判断不出来；ETag 是内容指纹，内容变没变一目了然。ETag 分强弱，弱的带 W/ 前缀，表示「语义上等价」而不是「字节完全相同」。
  • 304 不带 body，但会带新的缓存头。所以 304 也可以用来「续期」——源站可以在 304 里把 max-age 再往后推。
  • Vary 是缓存键的一部分。同一个 URL，如果响应随 Accept-Encoding 或 User-Agent 变化，必须写 Vary，否则 CDN 会把 A 版本发给 B。写 Vary: * 等于告诉缓存「这个不能缓存」。
# 看响应头里的缓存策略
curl -sI https://example.com/app.js | grep -iE 'cache-control|etag|expires|last-modified|vary'

# 带 ETag 去验证，看是不是 304（-H 手动构造条件请求）
curl -sI -H 'If-None-Match: "abc123"' https://example.com/app.js | head -3

# 看完整的一次协商过程
curl -sv -H 'If-Modified-Since: Wed, 21 Oct 2026 02:00:00 GMT' \
  https://example.com/index.html 2>&1 | grep -E '^< HTTP|^< ETag|^< Cache'

工程上的常规做法是「HTML 不缓存、静态资源长缓存 + 文件名带哈希」：index.html 设 no-cache（每次验证，保证能拿到新版本），JS/CSS 设 max-age 一年加 immutable，文件名里带内容哈希，内容一变文件名就变，URL 自然失效。这样既拿到了强缓存的性能，又不会出现「发版后用户还在跑旧代码」。

把用户相关的响应配成 public 是安全事故，不是性能问题。一旦 CDN 缓存了带某个用户信息的页面，下一个请求同一个 URL 的人就会拿到别人的数据。带 Set-Cookie 或 Authorization 的响应，默认就该是 private，最好再加 no-store。

面试落点：「强缓存看 max-age，命中就一个请求都不发；协商缓存看 ETag 或 Last-Modified，回 304 继续用本地副本。no-cache 是『存但每次验证』，no-store 才是『完全不存』。实践里 HTML 用 no-cache、带哈希的静态资源用长 max-age 加 immutable。」

模块 6

状态码：301 和 302 差的不是数字，是「谁记多久」

「301 和 302 有什么区别？」「一个是永久，一个是临时。」这个答案只对了一半，缺的那一半是：永久意味着可以被缓存，而且浏览器真的会缓存很久。

状态码语义方法会不会变能不能被缓存
301永久重定向历史上很多客户端会把 POST 改成 GET可以，而且会被长期记住，直到缓存被清
302临时重定向同样有被改成 GET 的历史包袱默认不缓存，除非显式给了缓存头
303See Other，去看另一个地址明确要求改成 GET一般不缓存
307临时重定向，保持原方法POST 还是 POST，body 也保留默认不缓存
308永久重定向，保持原方法POST 还是 POST可以，和 301 一样会被记很久

301 的缓存行为没有一个统一的「过期时间」，浏览器可能记住几天到几个月不等，具体策略各家不同、也和是否清理过缓存有关。所以工程上的结论很干脆：只要这次跳转有可能要撤回，就别用 301。域名永久迁移、HTTP 跳 HTTPS 这类确定不回头的场景才用它。

307 和 308 存在的意义就是补上「方法不能变」这个洞。301/302 在早期实现里被大量客户端写成「一律转成 GET」，导致一个 POST 请求重定向后 body 丢了，服务端收到一个空请求。如果你的接口需要重定向后又保持 POST，只能用 307/308。

状态码谁产生的准确含义
304源站或缓存你手里的副本还能用，别重传了。响应不带 body
400服务端请求本身有问题：语法错、缺参数、header 不合法
401服务端没认证，或者认证失效。要带 WWW-Authenticate 说明怎么认证
403服务端认证过了，但没权限。和 401 的区别是「我知道你是谁，但你不能做这个」
404服务端资源不存在。可以被缓存，这一点常被忽略
429服务端限流。应该配 Retry-After 告诉客户端多久后重试
499Nginx（非标准）客户端在响应发出前断开，不是标准状态码
502 / 504网关前者是上游响应无效或连接被重置，后者是等上游超时

401 和 403 的区分是另一个高频点。判断标准很简单：换个身份能不能成？能成就是 403（权限不够），怎么换都不行、必须先去认证，就是 401。把权限不足返回 401，会让客户端不停地弹登录框，是很常见的实现错误。

还有一个细节：404 默认可缓存。如果某个资源上线前被访问过、返回了 404 并被 CDN 缓存，上线后用户可能还在看到 404。这类「上线了但打不开」的问题，八成是 CDN 缓存了一个早先的 404，刷新一下缓存就好。

curl -sI https://example.com | head -1只看状态码和 HTTP 版本，最快的一次体检
curl -sIL https://example.com跟着跳转走完，看清 301/302 链路上每一跳是谁
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' URL状态码配跳转目标，一次输出，方便写脚本批量查
curl -sv URL 2>&1 | grep '^< '只留响应头，看 Cache-Control、ETag、Set-Cookie 到底发了什么

面试落点：「301 是永久，意思是它可以被浏览器长期缓存，回滚配置也撤不回来，所以只在确定不回头的场景用。要保留请求方法用 307/308。401 是没认证，403 是认证了但没权限，区别是换个身份能不能成。」

模块 7

认证：Cookie、Session、JWT 各自的代价

「为什么不用 JWT 替代 Session？」这个问题如果答「因为 JWT 更先进」，基本就结束了。JWT 不是升级版 Session，它是用「无法主动撤销」换「服务端不用存状态」。

方案状态存在哪优点代价
Cookie客户端，就是一个传输载体浏览器自动携带，配合 HttpOnly 能挡住大部分 XSS 读取自动携带带来 CSRF 风险，要配 SameSite 和 token
Session服务端（内存、Redis、数据库）可以随时让某个会话失效；不往客户端放任何敏感信息多实例要共享存储；存储挂了全站登录态丢失
JWT客户端（签名保护的自包含令牌）服务端无状态，横向扩展方便；跨域、跨服务传递方便签发后无法主动撤销，只能等它过期；payload 只是编码不是加密

Cookie 的几个属性必须能说清：HttpOnly 让 JS 读不到（防 XSS 偷 token）；Secure 只在 HTTPS 上发送；SameSite 控制跨站请求要不要带这个 Cookie，Strict 最严、Lax 是常见的默认值、None 必须同时加 Secure；Domain 和 Path 决定作用范围，Domain 写宽了会让子域之间互相影响。

JWT 的结构是三段 base64url 用点连接：头部（算法）、载荷（声明）、签名。载荷是可读的——任何人拿到 token 都能解出里面的内容，所以绝不能放手机号、身份证、余额这类信息。它的安全性只来自签名，保证「没被篡改」，不保证「看不见」。

JWT 的撤销问题有几种常见解法：把有效期压到很短（几分钟）配一个长期 refresh token，refresh 存在服务端可以撤销；在服务端维护一个「已失效 jti 黑名单」，但这就又变成有状态了；或者在用户表上放一个 token 版本号，改密码或强制下线时把版本号加一，旧 token 的版本对不上就拒绝。三种都是「用一点状态换回可控性」，天下没有免费的无状态。

# 解出 JWT 的头部和载荷（只是 base64 解码，不需要密钥）
cut -d. -f1 token.txt | base64 -d 2>/dev/null
cut -d. -f2 token.txt | base64 -d 2>/dev/null

# 看服务端下发的 Cookie 属性
curl -sI https://example.com/login | grep -i set-cookie
两个 JWT 的实现级坑：① 一定要在服务端固定校验算法，别信头部里写的 alg，否则攻击者把 alg 改成 none 或换成对称算法就能伪造；② 对称密钥（HMAC）要足够长且不能泄露，非对称（RS256/ES256）要注意公钥混淆问题。这两条不是理论风险，是公开的经典漏洞模式。

面试落点：「Session 是有状态的，能随时踢人，代价是要共享存储；JWT 是无状态的，扩展方便，代价是签发后撤不回来，只能靠短过期加 refresh 或者版本号补救。选哪个取决于业务能不能接受『改密码后旧 token 还能用几分钟』。」

模块 8

HTTPS：握手轮次、证书链、SNI 与 HSTS

「HTTPS 握手几次？」这题的标准答案是「TLS 1.2 两次，TLS 1.3 一次」，但更值钱的是下一句：加上 TCP 的三次握手，一个全新的 HTTPS 请求在发数据之前已经花掉了两到三个 RTT。

阶段TLS 1.2TLS 1.3
完整握手2-RTT1-RTT
会话复用1-RTT（session id 或 session ticket）1-RTT；支持 0-RTT 恢复
密钥交换可以是 RSA（无前向安全），也可以是 (EC)DHE只保留 (EC)DHE，默认前向安全
加密套件包含非 AEAD 的老套件只保留 AEAD 类，删掉了大量历史包袱
握手中的明文证书是明文，能被中间人看到证书也加密了，只剩 SNI 等少数字段可见

0-RTT 值得单独提一句：它让客户端在第一个包里就带上应用数据，代价是这些数据可能被重放。所以只应该用于幂等请求，比如 GET 一个静态资源。用它发「下单」「支付」这种请求，是给自己埋雷。

证书链是排查 HTTPS 问题时最高频的坑。链条是：服务器证书（叶）→ 中间 CA → 根 CA。根证书预装在操作系统和浏览器的信任库里，服务端只需要发叶证书和中间证书，不需要发根。少发中间证书的症状是：浏览器能打开（它会顺着证书里的 AIA 地址自己去下载），但 curl、Java、Python requests、很多移动端 SDK 会直接报「unable to get local issuer certificate」。

数一数发了几张证书。正常情况下至少两张：叶证书加中间证书。只看到一张 s:，就是链不完整，这一条能解决掉一半的「某些客户端报错」问题。
看有效期和 SAN。域名匹配校验的是 SAN 扩展，不是 CN 字段。只配了 CN 没配 SAN 的老证书，在新版客户端上一样会失败。
换一个严格客户端复验。浏览器太宽容，会自己补链、会容忍一些不规范。用 curl 或者 openssl verify 跑一遍，能拿到更接近真实客户端的结果。
# 看服务端到底发了几张证书（-showcerts 会全部打印）
openssl s_client -connect example.com:443 -servername example.com -showcerts < /dev/null 2>&1 \
  | grep -E '^ *[0-9]+ s:|^ *i:'

# 只看到一张 s:（叶证书）说明中间证书没配

# 看有效期和 SAN（域名写在 SAN 里，不是 CN）
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>&1 \
  | openssl x509 -noout -dates -ext subjectAltName

# 验证链是否完整（这一步会模拟严格客户端）
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt chain.pem

SNI 是 TLS 握手里的一个扩展，客户端在 ClientHello 里说明「我要访问哪个域名」，服务端据此选证书。没有它，一个 IP 就只能挂一张证书。SNI 在 TLS 1.3 里默认仍然是明文的（除非用 ECH），所以「SNI 泄露了你访问了哪个站点」是一个真实的隐私问题——这也是为什么有些场景会用 ECH 或者干脆每个站点独立 IP。

HSTS 是一个响应头：Strict-Transport-Security: max-age=31536000; includeSubDomains。浏览器收到后，在有效期内对这个域名的所有请求都强制走 HTTPS，连用户手动输入 http:// 都会被本地改写成 https。它解决的是「第一次访问可能被降级」的问题——但第一次访问本身仍然可能明文，除非域名被加进了浏览器的 preload 列表。加 preload 要谨慎：一旦进了列表，撤回要等浏览器版本更新，周期很长。

顺带说清证书类型的现状：DV（域名验证）、OV（组织验证）、EV（扩展验证）在加密强度上没有区别，区别只在审核流程和证书里包含的信息。EV 证书曾经能让浏览器地址栏显示绿色公司名，这个 UI 已经被主流浏览器移除，所以「买 EV 更安全」这个说法现在站不住。

面试落点：「TLS 1.2 完整握手 2-RTT，1.3 是 1-RTT，还支持有重放风险的 0-RTT。证书链服务端要发叶证书和中间证书，少了中间证书浏览器能自己补、其他客户端不行。SNI 决定用哪张证书，HSTS 让浏览器以后强制走 HTTPS，但第一次访问还是可能明文。」

模块 9

9 个坑：语义记错，比不会更危险

这一节的坑有个共同点：它们不会让系统立刻报错，而是让系统安静地做错事。缓存错一天、跳转错三个月，发现的时候已经很难挽回。

1
把 no-cache 当成「不缓存」
它表示可以存，但每次用之前必须回源验证。要真的不存，得用 no-store。用错的结果是敏感响应被写进了磁盘，或者每次请求都多一次 304 往返。
2
用 301 做临时跳转
浏览器会把 301 记很久，服务端改回 302 也撤不回来。域名迁移、灰度切换这类可能回滚的场景，一律用 302 或 307。
3
切域名前不降 TTL
TTL 是权威告诉全世界「你可以记多久」，说出去就收不回来。旧 TTL 是 3600，切换后就一定有一小时的混乱期。要提前一个 TTL 降下来。
4
把 CNAME 放在 zone 顶点
顶点必须有 SOA 和 NS，和 CNAME「名下不能有其他记录」冲突，配了也不生效。要么用 ALIAS/ANAME，要么把顶点直接写成 A 记录。
5
给 HTML 设很长的 max-age
发版后用户拿不到新页面，而且你没有任何服务端手段能让他更新——他手里的 HTML 里引用的还是旧的带哈希的资源。HTML 应该用 no-cache。
6
CDN 缓存了带用户信息的响应
该加 private 没加，或者错用了 public。一旦缓存，A 用户的页面会被发给 B 用户。这是数据泄露，不是性能问题。
7
以为 HTTP/2 没有队头阻塞
它只解决了应用层。底下还是 TCP，丢一个包整条连接上所有流都等。传输层的队头阻塞要 HTTP/3 才能解决。
8
服务端只配了叶证书
浏览器能自己补链，所以「浏览器正常」不能作为验收标准。用 openssl s_client -showcerts 数一下发了几张证书，或者用严格客户端跑一次。
9
权限不足返回 401
客户端收到 401 会以为「需要登录」，于是不停弹登录框或者反复刷新 token。没权限就是 403，语义错了会引发一连串奇怪的客户端行为。

面试落点：这 9 条里挑一条讲，结构固定：当时的判断、造成的后果、后来改成了什么。第 2 条和第 3 条最好讲，因为它们有明确的时间线，听起来就是真事。

自测

六道题

1. 响应头是 Cache-Control: no-cache，它的准确含义是？
正确答案：存但每次验证。no-cache 的名字容易误导，它禁止的是「不经验证直接使用」，不是「存储」。真正完全不存的是 no-store。实践中的表现是每次请求都会带 If-None-Match 或 If-Modified-Since，源站回 304 就继续用本地副本。
2. 域名迁移时把 302 改成了 301，两周后回滚成 302，但部分用户仍然被跳到新域名。原因是？
正确答案：301 被浏览器记住。301 的语义是永久，客户端可以长期缓存这条跳转规则，具体时长由各家浏览器策略决定，可能长达数月。回滚服务端配置只影响之后的请求，已经缓存过的客户端不会重新来问。这就是「可能回滚的跳转不能用 301」的原因。
3. 客户端向本地递归解析器发起查询，以及递归解析器向根、TLD、权威服务器查询，分别属于？
正确答案：递归 + 迭代。客户端把 RD（Recursion Desired）置位，意思是「你帮我查到底，我只要最终答案」；递归解析器去问根时用的是迭代，根只会回「去问这个 TLD 的服务器」，不会替它继续查。所以「谁在递归」这个问题的答案是：只有客户端到解析器这一段。
4. 一个资源命中了强缓存（max-age 还没过期），浏览器会做什么？
正确答案：不发请求。强缓存的判定完全在客户端完成：还在 max-age 内就直接用，网络面板上显示的是 from disk cache 或 from memory cache，服务端根本收不到这次请求。会发条件请求的是协商缓存，那是有效期过了之后的事。
5. TLS 1.3 相比 TLS 1.2，完整握手的往返次数和密钥交换的变化是？
正确答案：2-RTT 降到 1-RTT。TLS 1.3 把密钥交换收敛到 (EC)DHE，删掉了 RSA 密钥交换，所以默认就有前向安全；同时精简了套件（只留 AEAD）、加密了握手中的证书部分。0-RTT 是会话恢复时的能力，不是完整握手，而且有重放风险，只适合幂等请求。
6. 团队想用 JWT 完全替代 Session，最主要的障碍是？
正确答案：无法主动撤销。JWT 是自包含的，服务端不存状态，所以没有「让某个 token 立刻失效」的原生手段。常见补救是把有效期压短配 refresh token、维护 jti 黑名单、或者在用户上加 token 版本号——但这三种都会重新引入状态。另外 JWT 的载荷只是 base64url 编码，不加密，谁都能解开看。
