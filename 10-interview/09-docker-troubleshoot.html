读之前先答一句：容器状态是 Exited (0)，这算成功还是失败？
开始前

三个现场：都是从「重启一下」开始的

容器排障最容易犯的错，不是不会看日志，是顺序错了：先猜镜像有问题，于是重新 docker build；猜网络有问题，于是 docker network prune；猜资源不够，于是加内存。半小时过去，现象还在，现场已经被自己破坏完了。

正确的顺序只有三步，而且每一步都比上一步贵：退出码 → 日志 → 进容器。退出码几乎零成本，却直接告诉你「是谁杀的、为什么退的」；日志告诉你「应用自己认为发生了什么」；进容器是最后一步，因为它会改变现场。

现场直觉动作真实原因
容器起来 2 秒就 Exited (0)，日志一片空白镜像坏了，重新构建一次主进程把自己放到后台了。容器的生命周期等于 PID 1，PID 1 一退容器就结束，跟镜像没关系
磁盘 100%，但 du -sh /var/lib/docker 加起来对不上有隐藏文件，或者统计有延迟容器的 json-file 日志默认不轮转，一个容器写几十 G 很常见；另外镜像层里被删掉的文件也算在磁盘上
宿主机 curl 127.0.0.1:8080 通，外面访问不通端口映射写错了映射规则在，但 firewalld/ufw 把 FORWARD 链默认策略设成了 DROP，转发的包被丢在外面
退出码先看
137、139、127、126 各对应一类原因。它不解释细节，但能一刀切开「被杀」「崩了」「找不到命令」。
日志看两头
开头看启动参数和配置加载，结尾看最后一句。中间那几千行重复的通常没信息量。
inspect 看事实
退出码、是否 OOM、重启次数、实际生效的 Cmd/Entrypoint、挂载和端口，全在这里，不靠记忆。
为什么要强调顺序：退出码是内核/运行时给出的客观事实，日志是应用的主观陈述，进容器是你的推测。先信事实，再听陈述，最后才验证推测。反过来的习惯一旦养成，就会变成「每次出事都重建镜像」，看起来在处理，其实在赌。

面试落点：「容器起不来我按三步走：先 docker ps -a 看状态和退出码，再 docker inspect 看 ExitCode、OOMKilled 和实际生效的启动命令，然后看 logs。这三步能覆盖大部分情况，进容器是最后一步，因为会改现场。」

模块 1

三步定位法：ps -a、inspect、logs 各回答什么

这三条命令人人都会敲，但大部分人只用了它们十分之一的信息量。真正的差别在于：你知道每一列、每个字段在回答哪个问题。

第一步 docker ps -a，看三样：STATUS 里的 Exited (N)、Restarting 的循环、以及 Up 3 seconds 这种「刚起来又要挂」的时间。 Restarting (1) 5 seconds ago 说明重启策略在生效，但应用一直在挂，这时候不要等它「自己好」。

第二步 docker inspect，这是信息最全的一步。至少要看五个字段：

字段回答什么
.State.ExitCode退出码。和 ps 里的一致，但方便脚本取值
.State.OOMKilled是不是被 cgroup 的内存限制杀掉的。137 的真假靠它区分
.State.Error运行时层面的错误，比如「OCI runtime create failed」
.Config.Entrypoint / .Cmd实际生效的启动命令。很多人以为写的是 A，实际被执行的是 B
.RestartCount重启了多少次。数字大说明在循环，不用等下次

第三步 docker logs。注意两个细节：一是它对已退出的容器同样有效（日志在 json-file 里），所以容器挂了也能看到最后的输出；二是它依赖日志驱动，如果 daemon 配的是 syslog、fluentd 这类不支持读取的驱动，docker logs 会直接报「configured logging driver does not support reading」，这时候要去日志系统里查。

# 1. 状态与退出码：-a 才能看到已退出的
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker ps -a --filter 'status=exited'

# 2. 一次性把关键字段取出来
docker inspect -f 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}} restarts={{.RestartCount}} err={{.State.Error}}' web
docker inspect -f 'entrypoint={{json .Config.Entrypoint}} cmd={{json .Config.Cmd}}' web

# 看完整的状态时间线，判断是启动失败还是跑了一阵才挂
docker inspect -f '{{.State.StartedAt}} -> {{.State.FinishedAt}}' web

# 3. 日志：开头、结尾、带时间戳
docker logs --tail 50 web
docker logs --since 10m -t web 2>&1 | head -40
docker logs web 2>&1 | tail -100

这三步之后，如果还没结论，第四条命令是 docker events。它能给出「什么时候创建、什么时候 start、什么时候 die、什么时候被 kill」的时间线，特别适合判断「是容器自己退的，还是被谁停的」。在有多人操作、或者有自动伸缩脚本的环境里，这条时间线经常直接指出元凶。

# 实时事件流，只过滤某个容器（另开一个窗口观察）
docker events --filter container=web --format '{{.Time}} {{.Action}} {{.Actor.ID}}'

# 过去的 30 分钟（需要 daemon 保存了事件，默认会保留一段时间）
docker events --since 30m --until 0s --filter type=container
一个能省十分钟的习惯：把 docker inspect -f 的常用字段写成一段别名或小脚本，比如 dstat NAME 一次输出退出码、OOM、重启次数、启动命令、挂载。出事的时候脑子是空的，靠肌肉记忆比靠临场拼字符串可靠。
docker ps -a --format 'table {{.Names}}\t{{.Status}}'先看 STATUS，Exited (N) 里的 N 就是第一手证据
docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' NAME退出码与是否被 OOM 杀掉，两个字段定性 90% 的启动失败
docker logs --tail 50 --since 10m -t NAME带时间戳看最后 50 行，已退出的容器同样能读
docker events --filter container=NAME谁在什么时候 start / die / kill，判断是自杀还是被杀
docker system df -v镜像、容器、卷、构建缓存各占多少，找磁盘先看这张表

面试落点：「ps -a 看状态和退出码，inspect 看 ExitCode、OOMKilled、RestartCount 和实际生效的 Entrypoint/Cmd，logs 看应用输出。这三步的信息量依次递增，成本也依次递增。如果还判断不了，用 docker events 看是谁在什么时候把它停掉的。」

模块 2

退出码：128+N 是最容易被忽略的一条规则

「137 是什么？」大部分人答「内存溢出」。这个答案只对了一部分——137 只说明进程收到了 SIGKILL，而 SIGKILL 可能来自 OOM killer，也可能来自 docker stop 等满 10 秒后的强杀，还可能来自你自己敲的 kill -9。

先把规则说清：应用正常退出时，退出码就是应用自己返回的值（0~255）；被信号杀死时，退出码是 128 加信号编号。所以 137 = 128 + 9（SIGKILL），143 = 128 + 15（SIGTERM），139 = 128 + 11（SIGSEGV），130 = 128 + 2（SIGINT）。

退出码含义典型成因
0主进程正常退出进程干完活自己退了（一次性任务正常）；或者它把自己 daemon 化了，PID 1 直接结束
1应用自己返回的错误配置解析失败、端口被占、连不上数据库、启动脚本里 set -e 中断
125Docker 自身出错，容器没跑起来参数非法、端口已被占用、挂载路径不存在、daemon 连不上
126命令存在但无法执行脚本没有执行权限、挂载带了 noexec、二进制架构不匹配
127找不到要执行的命令ENTRYPOINT 拼错、基础镜像里没这个 shell、PATH 不对
137被 SIGKILL 杀死OOM killer、docker stop 超时后强杀、人工 kill -9
139被 SIGSEGV 杀死（段错误）原生库崩溃、JVM 崩溃（配合 hs_err_pid 日志）、架构不匹配的二进制
143被 SIGTERM 杀死正常 docker stop 的默认信号；应用没处理就直接退了

125、126、127 这三个是 Docker 自己的约定，很多人不知道，所以看到 127 会去翻应用日志，翻了半天发现日志里啥也没有——因为命令根本没执行起来，应用连一行输出都没产生。127 的第一反应应该是「镜像里的可执行文件路径对不对」，而不是「代码有 bug」。

# 137 到底是不是 OOM：看这一个字段就够了
docker inspect -f '{{.State.OOMKilled}}' web
# true 才是被 cgroup 内存限制杀的；false 就要查是谁发的 SIGKILL

# 确认容器的 StopSignal 和超时时间（默认 SIGTERM，10 秒）
docker inspect -f 'stop={{.Config.StopSignal}} timeout={{.Config.StopTimeout}}' web

# 127 排查：进不去容器就用 --entrypoint 覆盖成 shell
docker run --rm --entrypoint sh myapp:1.0 -c 'ls -l /usr/local/bin; echo $PATH'

# 126 排查：看二进制架构和权限
docker run --rm --entrypoint sh myapp:1.0 -c 'file /app/server; ls -l /app/server'
不要用 137 直接下「内存不够」的结论。Kubernetes 里 kubectl delete pod 等满 grace period 之后也是 SIGKILL；CI 里 runner 被回收、宿主机重启、docker kill，全都是 137。要区分只能看 OOMKilled 字段和内核日志（dmesg 里的 oom-kill 记录）。

还有一个反直觉的点：退出码 0 不代表服务正常。在容器的语义里，0 只意味着「PID 1 正常结束了」。一个 nginx 容器如果启动脚本把 nginx 放到后台、脚本自己退出，容器立刻 Exited (0)，编排系统看到的是「成功」，重启策略 on-failure 甚至不会拉起它。这类问题排查起来最费劲，因为所有指标都显示「一切正常」。

面试落点：「退出码规则是正常退出用应用自己的返回值，被信号杀就是 128 加信号号。137 是 SIGKILL，可能是 OOM 也可能是 stop 超时或人工 kill，要看 inspect 的 OOMKilled。125/126/127 是 Docker 层面的错：参数错、没权限、找不到命令。0 只说明主进程正常退出，不代表服务可用。」

模块 3

启动就退出：多半是「前台进程」这四个字

「我的容器明明启动成功了，一秒钟就 Exited (0)。」这是新手最常见的一句话，也是面试里很好用的素材。原因通常只有三类：进程后台化了、启动命令被覆盖了、依赖没就绪。

第一类最典型。nginx 默认以 daemon 方式运行：主进程 fork 出 worker，自己退出。在物理机上这是好事，在容器里就是灾难——PID 1 退出，容器结束。容器的存活条件不是「里面有进程在跑」，而是「PID 1 还在」。所以官方镜像的启动命令都加了前台参数，比如 nginx -g 'daemon off;'；httpd 是 -DFOREGROUND；很多 Java 启动脚本里的 nohup ... & 也是同一个坑。

# 典型错误：脚本把服务放后台，然后自己退出
# start.sh
# nohup java -jar app.jar > /var/log/app.log 2>&1 &
# 容器立刻 Exited (0)，日志还是空的，因为输出重定向到文件了

# 正确写法：exec 让 PID 1 就是应用本身，信号才能打到它
# exec java -jar app.jar

# 排查时临时覆盖启动命令，进容器看现场（不要用于生产）
docker run --rm -it --entrypoint sh myapp:1.0
docker run -d --name keep --entrypoint sleep myapp:1.0 infinity

第二类是启动命令被覆盖。Dockerfile 里 ENTRYPOINT 和 CMD 的组合规则值得记准：ENTRYPOINT 是「可执行文件」，CMD 是「默认参数」；如果在 docker run 后面跟了命令，它会整体替换 CMD，而不是追加。所以一个写着 ENTRYPOINT ["/app/server"] 加 CMD ["--port","8080"] 的镜像，你 docker run image --help 得到的是 /app/server --help，不是 shell。很多人在这里绕很久，其实 docker inspect 一看 .Config.Cmd 就明白了。

第三类是依赖没就绪。应用启动时连不上数据库，直接 System.exit(1)，容器退出。这时候日志里通常有一行 Connection refused，而数据库容器可能只是还在初始化。解决办法不是「加 sleep 30」，而是让启动逻辑能重试，或者用编排层的健康检查来控制启动顺序（Compose 的 depends_on: condition: service_healthy，K8s 的 initContainer 或探针）。

现象判断处置
Exited (0)，日志空主进程后台化，或输出被重定向到文件改成前台运行 + exec，日志写 stdout
Exited (1)，日志有 Connection refused依赖未就绪，或地址写成了 localhost加重试、改配置、用服务名而不是 127.0.0.1
Exited (127)命令不存在看 ENTRYPOINT 路径、基础镜像里有没有这个 shell
Exited (126)没有执行权限，或架构不匹配chmod +x、检查 --platform
报 no such file or directory，但文件明明在脚本是 CRLF 换行，shebang 变成了 #!/bin/sh\r转成 LF，或在 Dockerfile 里 sed -i 's/\r$//'
Restarting (1) 循环重启策略在生效，但每次启动都失败先 docker update --restart=no 停掉循环，保留现场再查
别用 tail -f /dev/null 或 sleep infinity 当「修好了」。它只是让容器保持运行，应用根本没起来。真正要的是「进程在前台、日志到 stdout、信号能收到」。临时调试可以用，进了生产就是给自己埋雷。

面试落点：「容器 Exited (0) 而日志为空，我第一反应是主进程后台化了。容器的生命周期等于 PID 1，nginx 这种默认 daemon 的必须加 daemon off。第二种是 CMD 被 run 后面的参数整体替换了。第三种是依赖没起，日志里会有 Connection refused，该做重试而不是 sleep。」

模块 4

磁盘被写满：一半是日志，一半是镜像层

「磁盘 100% 了，删了几个镜像还是 100%。」这类工单的答案通常不在镜像上，而在 /var/lib/docker/containers 里那些没人看的 -json.log。

先把 Docker 占的空间拆成四块，这是回答「磁盘去哪了」的框架：

类别位置增长原因
镜像/var/lib/docker/overlay2（只读层）每次构建都留一份，tag 覆盖后旧镜像变成 dangling，没人清
容器可写层overlay2/<id>/diff应用往容器里写文件、日志没走 stdout、临时文件不清理
容器日志containers/<id>/<id>-json.logjson-file 驱动默认不限制大小、不轮转，一个容器写几十 G 很常见
卷/var/lib/docker/volumes匿名卷不随容器删除而清理，CI 环境里能攒出几十 G
# 先看总量分布：四类的占比一目了然
docker system df
docker system df -v          # 细到每个镜像、容器、卷

# 找最大的容器日志（这一步经常直接抓到元凶）
du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail -5

# 确认日志驱动和是否有大小限制
docker info --format '{{.LoggingDriver}}'
docker inspect -f '{{json .HostConfig.LogConfig}}' web

# 截断一个正在写的日志（比 rm 安全，句柄还在但空间立即释放）
: > /var/lib/docker/containers/<id>/<id>-json.log

日志不轮转是一个设计选择，不是 bug：Docker 默认把容器 stdout/stderr 落到 json-file，方便 docker logs 读，但它不会自动限制大小。要限制必须在 daemon 层或容器层显式配。注意 daemon 级的 log-opts 只对新建的容器生效，已经跑着的容器要重建才会应用。

# /etc/docker/daemon.json：全局限制，改完要重启 docker
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}

# 单个容器启动时指定（优先级更高）
docker run -d --log-opt max-size=50m --log-opt max-file=3 --name web nginx

# 也可以用 local 驱动，默认就带轮转，压缩率更好
# "log-driver": "local", "log-opts": {"max-size": "50m"}

清理要分清三个命令的破坏力，这是面试里很容易被追问的点：docker system prune 删停止的容器、未使用的网络、dangling 镜像和构建缓存；加 -a 会把所有没有被容器使用的镜像都删掉，包括你准备回滚用的那个 tag；加 --volumes 会删匿名卷，数据库数据可能一起没。这三者的区别必须能一句话说清，因为生产上敲错一个字母就是事故。

不要用 rm -rf /var/lib/docker/* 来救磁盘。它会把镜像、容器、卷、网络配置全部抹掉，Docker 重启后会以为自己是个新装的机器。而且如果有容器正在运行，删掉运行中的层目录会直接让进程读到 I/O 错误。要先停 Docker 服务，再决定删哪一块。

磁盘长期不够的根治办法是迁 data-root：把 /var/lib/docker 挪到更大的数据盘。步骤是停服务、用 rsync -aP 保留权限和硬链接地复制、改 /etc/docker/daemon.json 里的 data-root、启动、用 docker info 确认 Docker Root Dir 已经变了、最后再删旧目录。顺序不能反，先删再改等于自杀。

# 迁移 data-root 的完整步骤
systemctl stop docker
rsync -aP /var/lib/docker/ /data/docker/

# /etc/docker/daemon.json
# { "data-root": "/data/docker" }

systemctl start docker
docker info | grep -i 'root dir'
docker images | head            # 确认镜像还在
# 验证无误后再删旧目录

面试落点：「Docker 占空间分四块：镜像层、容器可写层、容器日志、卷。最常见的是 json-file 日志没限制，一个容器能写几十 G，用 du 找 *-json.log 最快。清理要区分 prune 和 prune -a，后者会删掉回滚用的镜像。根治是配 max-size 和迁 data-root。」

模块 5

端口与网络：映射成功不等于外部能访问

「-p 8080:80 明明写了，docker ps 也显示 0.0.0.0:8080->80/tcp，但外部就是打不开。」这个现场有五个常见分岔，得按顺序排除。

先确认监听地址。容器里如果应用只绑 127.0.0.1:80，宿主机 DNAT 过来的包进不去。容器里 ss -lntp 看到的是 127.0.0.1:80 就中招了，应用要绑 0.0.0.0。
再看宿主机端口有没有被占。bind: address already in use 时 Docker 返回 125，容器根本没创建。用 ss -lntp | grep 8080 找占用者，常见是上一个没退干净的容器或者宿主机的服务。
确认 DNAT 规则存在。iptables -t nat -S DOCKER 里应该有到容器 IP 的 DNAT。没有规则说明端口没发布成功，或者 iptables 被别的工具刷过。
查 FORWARD 链。这是最隐蔽的一层：firewalld 或 ufw 把 FORWARD 默认策略设成 DROP，宿主机本机访问没问题（走 INPUT），转发给容器的包全被丢。看 iptables -S FORWARD 和 firewall-cmd --state。
最后看云上的安全组。宿主机上 curl 通、同网段另一台机器不通，通常是安全组或网络 ACL 没放行，和 Docker 无关。
# 容器里到底监听的哪个地址（关键是 0.0.0.0 还是 127.0.0.1）
docker exec web ss -lntp
# 进不去容器就用 nsenter，效果一样还不受镜像里有没有 ss 的限制
nsenter -t $(docker inspect -f '{{.State.Pid}}' web) -n ss -lntp

# 宿主机侧的规则与转发策略
iptables -t nat -S DOCKER
iptables -S FORWARD
sysctl net.ipv4.ip_forward
firewall-cmd --state 2>/dev/null; ufw status 2>/dev/null

# 容器到容器的连通性，以及 DNS 解析
docker exec web getent hosts db
docker exec web cat /etc/resolv.conf

容器间通信失败，先分清两种情况：是解析不了名字，还是连不上 IP。解析不了，多半是用了默认 bridge——它不带内嵌 DNS，只有自定义网络才有 127.0.0.11 那个解析器。连不上 IP，则要查是不是在同一个网络里（docker network inspect 看 Containers 列表），以及目标端口有没有监听。

还有一个宿主 resolv.conf 的经典坑：在开了 systemd-resolved 的机器上，/etc/resolv.conf 里的 nameserver 是 127.0.0.53。Docker 会把它过滤掉（因为容器里的 127.0.0.1 是容器自己），如果过滤完一个都不剩，就退回公共 DNS，结果内网域名在容器里解析不了。现象是「宿主机能 ping 通内网域名，容器里不行」，解法是给 daemon 配 dns 项，或者用自定义网络。

容器访问宿主机服务，不要写 localhost。那指向容器自己。bridge 模式下用网关地址（docker network inspect bridge 的 Gateway，通常是 172.17.0.1），或者用 --add-host=host.docker.internal:host-gateway。硬编码 IP 的问题换台机器就暴露。

面试落点：「映射了但外部不通，我按五层查：容器里监听地址是不是 0.0.0.0、宿主机端口是否被占、DNAT 规则在不在、FORWARD 链有没有被防火墙 DROP、云安全组。宿主机本机通而外部不通，最可能是 FORWARD 或安全组。容器之间不通，先分清是 DNS 还是 IP 层。」

模块 6

时间差 8 小时：容器里默认是 UTC

「日志时间比实际早八小时」「定时任务在凌晨跑」，这两个现象的根因是同一个：大部分基础镜像里没有时区数据，容器默认走 UTC。

时区在 Linux 上是两样东西：/etc/localtime 这个文件（指向 tzdata 里的某个区域文件），以及 TZ 这个环境变量。glibc 的程序两者都认；但 Alpine 用的 musl 更依赖 TZ，而且 Alpine 默认不装 tzdata，你设了 TZ=Asia/Shanghai 它也不认识，最后还是 UTC。

做法适用注意
-e TZ=Asia/ShanghaiDebian/Ubuntu 系基础镜像，glibc 会读镜像里必须有 tzdata，否则变量无效
挂载 /etc/localtime:/etc/localtime:ro任何镜像，最直接依赖宿主机时区；跨机器部署时行为可能不一致
Dockerfile 里装 tzdata 并设置需要可移植的镜像Alpine 要 apk add --no-cache tzdata，会多几兆
JVM 参数 -Duser.timezone=Asia/ShanghaiJava 应用优先级高于系统时区，最稳；但日志框架自己也可能有配置
应用层统一用 UTC 存、展示时转换分布式系统的最佳实践需要前后端约定，改造成本高但最不容易出错
# 对比一下就知道差在哪
date
docker exec web date
docker exec web cat /etc/timezone 2>/dev/null
docker exec web ls -l /etc/localtime

# 临时验证：加上 TZ 再跑一次
docker run --rm -e TZ=Asia/Shanghai alpine date
# Alpine 没装 tzdata 时上面这条仍可能是 UTC
docker run --rm -e TZ=Asia/Shanghai alpine sh -c 'apk add -q tzdata && date'

# JVM 里确认实际生效的时区
docker exec app java -XshowSettings:properties -version 2>&1 | grep -i timezone

为什么这件事在排障里重要？因为它会污染所有基于时间的判断。日志时间和监控时间对不上，你会把「事故发生在 10:00」看成 02:00，去翻错误的监控窗口；定时任务按容器时间跑，备份在业务高峰执行；证书校验、token 过期、TOTP 验证码，全都可能因为时区错而失败。这类问题的特征是「逻辑都对，就是结果不对」，很难往时区上想。

一个判断技巧：如果偏差正好是整数小时（8 小时、5 小时半），先怀疑时区；如果是几秒到几分钟的漂移，那是 NTP 或时钟同步问题；如果是负的、而且忽大忽小，可能是日志采集链路的时间戳覆盖。三种原因的排查方向完全不同。

面试落点：「容器默认 UTC，因为基础镜像通常不带 tzdata。/etc/localtime 和 TZ 是两套机制，glibc 都认，Alpine 的 musl 更依赖 TZ 而且要先装 tzdata。Java 用 -Duser.timezone 最稳。工程上更好的做法是存储统一 UTC，展示层再转。」

模块 7

资源限制与 OOM：JVM 堆不是全部

「容器 limit 2G，JVM 堆设了 1.8G，还是被 OOMKilled，堆 dump 一看才用了 1.2G。」这不是玄学，是堆只是进程内存的一部分。

一个 Java 进程在容器里的内存占用，大致是这些加起来：堆（Xmx 上限）、元空间（Metaspace）、线程栈（每个线程约 1M 虚拟内存，实际占用少一些但会计入）、直接内存（NIO 的 DirectByteBuffer）、JIT 生成的代码缓存、GC 自身的结构、以及 glibc 的 malloc arena（多线程下容易碎片化膨胀）。所以 Xmx 设成 limit 的 90% 几乎必然出事，行业里常见的经验值是 70%~75%。

现象判断处置
ExitCode 137 + OOMKilled=truecgroup 内存到顶，内核杀的降 Xmx、查泄漏、确认 limit 是否合理
137 但 OOMKilled=false不是内存问题，是有人发了 SIGKILL查 docker stop、编排层驱逐、人工操作
容器内 free 显示宿主机内存/proc/meminfo 未隔离，误判看 cgroup 的 memory.current / memory.max
Java 8 老版本不认 cgroup 限制堆按宿主机内存算，一下就被杀升 JDK，或显式设 Xmx，或用 MaxRAMPercentage
刚启动就 OOM，堆还没热元空间 + 线程栈 + 直接内存超了给非堆留足空间，别把 Xmx 顶到 limit
# 是不是 OOM，一条命令定论
docker inspect -f 'oom={{.State.OOMKilled}} exit={{.State.ExitCode}}' app

# cgroup 侧的客观数据
CG=/sys/fs/cgroup/system.slice/docker-$(docker inspect -f '{{.Id}}' app).scope
cat $CG/memory.max $CG/memory.current
cat $CG/memory.events          # oom / oom_kill 的累计次数

# 容器的实时资源曲线
docker stats --no-stream app

# 让 JVM 自己按容器 limit 算堆（JDK 10+ 默认支持容器感知）
# -XX:MaxRAMPercentage=70 -XX:InitialRAMPercentage=40

还要说清 --memory-swap 的语义，因为它的默认值很容易被误解：它是「内存 + swap 的总量」，不是「swap 单独的量」。不设置时，如果设了 --memory，默认总量是它的两倍（以你环境为准）；设成和 --memory 相等表示禁用 swap；设成 -1 表示不限制。这意味着你以为没开 swap，其实可能开了，而 swap 一开，内存压力下的表现会从「干脆被 OOM」变成「慢慢被拖死」，更难排查。

OOMKilled 的容器，日志往往停在半句话上。因为它没有机会 flush。这时候不要指望应用日志给出原因，要看的是「死前内存曲线长什么样」——是缓慢爬升（泄漏）、还是瞬间尖峰（一次大查询、大文件、批量任务）。这两种的修法完全不同：前者要抓 dump，后者要限流或分批。

面试落点：「137 先看 OOMKilled。是 OOM 的话，Java 的堆只是进程内存的一部分，还有元空间、线程栈、直接内存和 malloc arena，所以 Xmx 一般设到 limit 的 70% 左右。老版本 JDK 8 不感知 cgroup，会按宿主机内存算堆，这是经典事故。另外 --memory-swap 是内存加 swap 的总量，不是 swap 的量。」

模块 8

构建失败：网络、缓存、多阶段，三类原因

「昨天还能构建，今天报错。」构建失败的原因比运行失败更集中，基本就是三类：拉不到东西、缓存给了旧结果、路径在多阶段之间对不上。

第一类最常见：RUN apt-get update 卡住或 404、pip install 超时、go mod download 连不上 proxy。原因可能是构建容器没有走代理、内网源配错、或者 DNS 在构建环境里不可用。要区分「网络不通」和「源上没有这个包」：前者是超时/连接拒绝，后者是 404/找不到版本。

# 构建时传代理（只在构建期生效，不会留在镜像里）
docker build --build-arg HTTP_PROXY=http://proxy:8080 \
             --build-arg HTTPS_PROXY=http://proxy:8080 -t myapp .

# 怀疑是构建网络问题，临时用宿主机网络验证
docker build --network=host -t myapp .

# 关掉缓存，确认是不是缓存导致用了旧的包索引
docker build --no-cache --progress=plain -t myapp . 2>&1 | tail -40

第二类是缓存。典型症状是「明明改了 Dockerfile 里的 apt 源，构建还用旧的」——因为 RUN apt-get update 那一层命中了缓存。update 和 install 必须写在同一条 RUN 里，这样缓存要么整体命中（索引和包是配套的），要么整体失效。分成两条写，就会出现「索引是三个月前的、包已经更新了」的 404。

第三类是多阶段。常见错误是 COPY --from=builder /app/bin/app /usr/local/bin/，但 builder 阶段实际产物在 /out/app。报错是 COPY failed: stat ...: file does not exist，看起来像权限问题，其实是路径错。另一个隐蔽的情况是 静态链接 vs 动态链接：builder 里编译出的二进制依赖 glibc，最终镜像用 alpine（musl），一跑就报 no such file or directory——不是文件不在，是解释器找不到。解法是静态编译（Go 的 CGO_ENABLED=0）或者最终镜像用同系的基础镜像。

报错关键词大概率原因验证方式
Could not resolve / connection timed out构建环境 DNS 或代理不通--network=host 重试一次
404 Not Found（apt/pip/npm）包索引过期或源地址错--no-cache 重建
no space left on device构建缓存 + 镜像把磁盘写满docker system df、docker builder prune
COPY failed: file does not exist多阶段路径错，或被 .dockerignore 排除在 builder 阶段 ls 一下产物路径
exec format error架构不匹配（arm 机器构建 amd64 镜像等）--platform linux/amd64，或检查基础镜像架构
permission denied（构建期）USER 切换后没权限写目录调换 USER 与 chown 的顺序
构建缓存在 CI 上比在本机更容易骗人。很多 CI 会把缓存目录挂来挂去，跨分支、跨提交复用。如果出现「本地能构建、CI 不能」，第一件事是 --no-cache 重跑一次；如果这样就过了，问题一定在缓存键上，而不是代码。

面试落点：「构建失败我分三类：网络（拉不到包）、缓存（用了旧索引）、多阶段（路径或架构不对）。apt 的 update 和 install 要同层，否则会出现索引和包不匹配的 404。多阶段最常见的坑是产物路径写错，以及用 alpine 跑 glibc 编译的二进制，报 no such file or directory 其实是解释器找不到。」

模块 9

Compose：depends_on 只保证顺序，不保证就绪

「我写了 depends_on: [db]，为什么应用还是连不上数据库？」因为短语法的 depends_on 只做一件事：先启动 db 容器，再启动 app 容器。它不等 db 里的进程真的能接受连接。

这个区别在数据库上特别致命：MySQL 容器 start 之后，要初始化数据目录、跑 init 脚本，可能几十秒才能接受连接。这段时间里 app 已经起来了，连不上就退出，然后重启策略再拉一次，循环几次才成功。你看到的是「偶尔能起来」，于是误以为是随机问题。

写法语义是否等就绪
depends_on: [db]只保证启动顺序否
depends_on: db: condition: service_started同上，显式写法否
condition: service_healthy等 healthcheck 变成 healthy是，但目标必须定义 healthcheck
condition: service_completed_successfully等一次性任务正常结束是，适合迁移、初始化任务
# 关键是给依赖方定义 healthcheck，否则 service_healthy 无意义
services:
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 30s
  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

start_period 这个参数值得单独说：它表示「这段时间内的失败不计入 retries」。慢启动的应用如果没设它，前几次探测失败就把容器标成 unhealthy 了，而它其实只是还没起来。这跟 K8s 的 startupProbe 是同一个思路。

# 看健康状态和最后一次探测的输出
docker ps --format 'table {{.Names}}\t{{.Status}}'
docker inspect -f '{{json .State.Health}}' app | head -c 600

# 等所有服务 healthy 再返回（CI 里很好用）
docker compose up -d --wait

# 只看某个服务的日志，带时间戳
docker compose logs -f --tail 50 app

还有一个与重启相关的语义要分清：restart: unless-stopped 会在容器退出时拉起，包括正常退出（exit 0）；on-failure 只在非 0 退出时拉起；always 连 Docker 重启后也会拉起。而 unhealthy 不会触发重启——Docker 的健康检查只改状态，不动容器（Swarm 模式才会重建）。很多人以为「配了 healthcheck 就会自动重启不健康的容器」，这是错的。

一个务实的原则：能在应用里做重试，就不要靠启动顺序。重试是运行时的能力，编排层只能控制启动时刻，两者不在一个层次上。把「等数据库」写进启动脚本，看起来简单，实际把故障从「启动失败」变成了「启动很慢但不知道在等谁」。

面试落点：「compose 的 depends_on 短语法只保证启动顺序，不等就绪；要等就绪得配 healthcheck 加 condition: service_healthy，还要给慢启动的服务设 start_period。另外 unhealthy 不会触发自动重启，那只是状态，不是重启策略。」

模块 10

10 个坑：排障时最容易做错的十件事

这些坑的共同点是：动作本身没错，时机错了。它们不会让问题变得更难，只会让现场消失，让你第二次遇到时还是不会。

1
只看日志不看退出码
127 和 126 的情况，应用连一行日志都没产生，日志里当然是空的。先看退出码能省掉一大圈。反过来，OOMKilled 的容器日志常常停在半句，也不能作为唯一依据。
2
看到 137 就说内存不够
137 只表示收到 SIGKILL。docker stop 等满超时、编排层驱逐、人工 kill -9 都是 137。要看 inspect 的 OOMKilled 字段才能定性。
3
一上来就 docker system prune -a
它删掉所有未被使用的镜像，包括你回滚要用的那个 tag。磁盘是腾出来了，下次回滚得重新拉，网络不好的时候就是二次事故。先 docker system df -v 看清楚再决定。
4
日志不配 max-size
json-file 默认不轮转，一个死循环打日志的容器能在一晚上写满磁盘，然后拖垮整台机器上的所有容器。这个配置要在 daemon 层全局设，别指望每个 compose 文件都记得写。
5
容器起不来就加 -it 或 restart
-it 会改变启动行为（有 TTY 和没有 TTY，很多程序的输出和缓冲策略都不一样），restart 会让失败循环反复覆盖日志。要保留现场，用 --entrypoint sh 单独起一个调试容器，别动原来那个。
6
端口冲突去改 Docker 配置
bind: address already in use 是宿主机上已经有进程占了这个端口，跟 Docker 的配置无关。ss -lntp 找出来，要么停掉它，要么换映射端口。
7
以为 -p 了就对外可用
firewalld/ufw 把 FORWARD 默认策略设为 DROP 时，宿主本机访问正常、外部全不通。这个现象特别有欺骗性，因为你在服务器上 curl 一百次都是通的。
8
容器里用 localhost 访问宿主机
localhost 在容器里指容器自己。要用网关地址或者 host.docker.internal。这个错误在把应用从物理机迁到容器时几乎必然发生一次。
9
JVM 堆按宿主机内存设
容器 limit 2G、Xmx 设 4G，结果容器被 OOMKilled，堆 dump 里却看不出问题，因为死的时候堆还没涨到 4G。堆要按 limit 算，还要给非堆留 25% 以上。
10
把 depends_on 当成「依赖已就绪」
它只保证启动顺序。数据库还在初始化时应用已经起来了，连不上就退出，重启几次碰巧成功——于是你以为问题解决了，直到下一次发布。

面试落点：这十条里最值得讲的是第 2 条和第 3 条，因为它们都涉及「动作很快、后果很重」。讲的时候给出具体数字：「一次 prune -a 删掉了 40 多个镜像，回滚时拉了二十分钟」——比说「要注意」有说服力得多。

自测

六道题

1. 容器启动后立刻变成 Exited (0)，日志里没有任何输出。最可能的原因是？
正确答案：主进程后台化。容器的生命周期绑定 PID 1，脚本用 nohup ... & 或服务自身 daemon 化后，PID 1 退出，容器立即结束并返回 0。日志为空通常是因为输出被重定向到文件了。修法是前台运行并用 exec 让应用成为 PID 1。内存不足会是 137，端口未映射不会导致退出。
2. 容器退出码 127，应该优先怀疑什么？
正确答案：命令不存在。127 是 shell/Docker 约定的「command not found」，容器里根本没有产生应用日志。架构不匹配通常报 exec format error 并返回 126 一类的错误；OOM 是 137；未捕获异常一般是 1。
3. 容器退出码 137，怎么判断是不是被内存限制杀的？
正确答案：看 OOMKilled。137 = 128 + 9，只说明进程收到 SIGKILL。OOM killer、docker stop 超时后的强杀、人工 kill -9 都会产生 137。OOMKilled 为 true，或者 cgroup 的 memory.events 里 oom_kill 计数增长，才是内存原因。Java 的 OutOfMemoryError 是堆内申请失败，被 cgroup 杀时往往没有这条日志。
4. 宿主机磁盘满了，du -sh /var/lib/docker 显示的空间远小于磁盘总量。最该先查什么？
正确答案：容器日志与已删除未释放的文件。json-file 默认不限制大小、不轮转，du -sh /var/lib/docker/containers/*/*-json.log 经常能直接抓到几十 G 的单个文件；另一种是文件被删但句柄未释放，df 满而 du 看不到。层数、版本、文件系统类型都不会造成这种差异。
5. -p 8080:80 已配置，docker ps 显示映射正常，在宿主机上 curl 127.0.0.1:8080 通，但从另一台机器访问超时。最可能的原因？
正确答案：FORWARD / 安全组。宿主机本机访问走 INPUT 链，转发到容器走 FORWARD 链。firewalld、ufw 或某些加固脚本把 FORWARD 默认策略设为 DROP 后，表现为「本机通、外部不通」。端口写反的话本机也不会通；容器崩了本机同样不通；网络类型不影响端口发布。
6. 容器 --memory=2g，JVM 设了 -Xmx1800m，运行一段时间后被 OOMKilled，但堆 dump 显示只用了 1.2G。最合理的解释是？
正确答案：堆外内存。Xmx 只限制堆，进程总内存还包括 Metaspace、每个线程的栈、NIO 直接内存、JIT 代码缓存、GC 结构和 glibc 的分配器开销。所以 Xmx 一般只给到 limit 的 70%~75%，或者用 MaxRAMPercentage 让 JVM 按 cgroup limit 自行计算。

DNAT端口映射的实现，改写目的地址；对应的出方向是 SNAT/MASQUERADE
