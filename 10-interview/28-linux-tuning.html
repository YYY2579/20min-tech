Linux 内核参数调优：面试爱问的那几个 sysctl

somaxconn、tcp_tw_reuse、vm.swappiness——能说清「调了会怎样、什么时候不该调」的人不多。

读之前先答一句：somaxconn 和 tcp_max_syn_backlog，哪个管的是「握完手等 accept」的队列？
开始前

一份从博客抄来的「万能优化」，把连接搞丢了

接手一台机器，/etc/sysctl.conf 里有二十几行，注释写着「高并发优化」。其中三行很眼熟：tcp_tw_recycle=1、tcp_tw_reuse=1、somaxconn=65535。机器前面是 NAT 网关，用户侧偶发「连接超时、重试就好」，监控上看不出任何异常——因为丢包发生在内核里，应用日志干净得像没发生过。

这三行分别踩了三个不同的坑：第一行在内核里已经不存在了；第二行只对出方向有效，服务端开了等于没开；第三行只调了内核的一半，应用那边的 listen backlog 没动，取小值之后仍然白调。它们共同说明一件事：内核参数不是「越大越好」的开关，每个参数都绑着一个具体的队列、计数器或者回收策略。

现场直觉答案真实原因
NAT 后面偶发连接超时，重试正常网络抖动，或者带宽不够开了 tcp_tw_recycle 的老内核会按时间戳判断报文新旧。NAT 后多台机器共用 IP，时间戳顺序乱了，正常包被当成旧包丢掉
服务端 TIME_WAIT 三万多，开了 reuse 没变化参数没生效，需要重启这个参数只作用于主动发起连接的一方。服务端的 TIME_WAIT 通常是客户端留下的，或者自己作为主动关闭方的那部分，跟被动连接无关
压测时新连接大量超时，ss -lnt 看着正常内核队列参数不够，调 somaxconn要看的不是连接状态，是监听队列：Recv-Q 贴着 Send-Q 就是 accept 队列满了，而应用 backlog 与 somaxconn 取小值
这一篇的立场：调优的第一动作是量，不是改。sysctl -a 里有两千多个参数，线上真正值得动的不到二十个，而且大部分时候正确答案是「不改，去改应用」。面试里能说出「这个参数我不建议动，因为……」的人，比能背十个推荐值的人可信。

按「资源 → 参数」组织：先讲调优的前提和观测，再依次是文件句柄、连接队列、TIME_WAIT 与端口、缓冲区与拥塞控制、内存、文件系统与 IO 调度，收在怎么持久化、怎么灰度、怎么回滚。

面试怎么答：「我调内核参数有三个前提：有基线数据、定位到了具体瓶颈、一次只改一个变量。因为大部分参数是互相牵制的，一次改五个，出了问题不知道回滚哪个，性能好了也不知道是哪一行起的作用。」

模块 1

调优的前提：先证明瓶颈在哪，再决定动不动手

「服务器性能不好，你会调什么参数？」这个问题如果直接开始报参数名，基本就废了。因为参数调优在绝大多数性能问题里排在最后——前面还有代码、SQL、架构、容量四层，任何一层的问题都不是 sysctl 能救的。

正确的顺序是：先定义症状（延迟高、吞吐上不去、连接失败、内存涨），再定位层（CPU、内存、IO、网络、应用），再看这一层有没有可调的队列或上限被打满，都排除完才轮到改参数。sysctl 能解决的，几乎只有一类问题：某个上限或队列长度成了瓶颈，而资源本身还有余量。

症状先看什么参数能不能救
新连接超时，老连接正常ss -lnt 的 Recv-Q、nstat 的 ListenOverflows能。队列上限或应用 accept 速度
吞吐上不去，延迟随距离增大RTT、窗口、重传率部分能。缓冲区小于 BDP 时有效
内存一直涨，最后 OOMRSS、page cache、swap 使用基本不能。先查泄漏和 limit
磁盘写延迟周期性飙高iostat -x 的 await、dirty 比例有时能。脏页回写参数
CPU 的 %sy 很高上下文切换、软中断、系统调用很少。多半是应用或中断分布问题

观测先固定成三条命令，别一上来就翻几十个文件：ss -s 看连接总量和状态分布，nstat -az 看协议栈计数器的累计值，sysctl -a 或者直接 cat /proc/sys/... 看当前值。计数器的关键是看增量，绝对值没有意义——一台跑了半年的机器，重传几十万次可能完全正常。

还有一件事必须在动手前做：记录基线。改之前的 QPS、P99、重传率、队列溢出数、内存占用，全部记下来。没有基线，改完你只能凭感觉说「好像快了」，这在生产上等于没验证。回滚也需要基线，否则不知道该退回哪个值。

# 三条命令建立基线
ss -s
nstat -az | grep -Ei 'ListenOverflows|ListenDrops|SyncookiesSent|RetransSegs|TCPTimeouts'
free -m; vmstat 1 3

# 关键参数的当前值（临时改动用 -w，重启失效）
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog
sysctl net.ipv4.tcp_tw_reuse net.ipv4.tcp_timestamps
sysctl vm.swappiness vm.overcommit_memory

# 看某个计数器每秒增量，比看总值有用
nstat -n1 -z TcpExtListenOverflows TcpExtListenDrops

面试怎么答：「我不会先问调什么参数，我会先问症状和基线。内核参数能解决的只有『上限或队列打满但资源还有余量』这一类问题。如果是 CPU 算不过来、内存泄漏、SQL 慢，调 sysctl 只是把问题往后推。」

模块 2

文件句柄：三个上限，改错一个等于没改

「Too many open files」是运维最熟的报错之一，但很多人改完 /etc/security/limits.conf 就以为完事了，重启服务照样报——因为 systemd 启动的服务根本不读那个文件，它读的是 unit 里的 LimitNOFILE。

这里有三个层次的上限，从下往上卡：内核全局的 fs.file-max（整机所有进程能开的 fd 总数）、单进程硬上限 fs.nr_open（setrlimit 能设到的天花板）、进程自身的 soft/hard limit（ulimit -n 看到的）。soft 是当前生效值，hard 是 soft 能调到多高；普通进程只能把 soft 提到 hard 以内，不能超过 fs.nr_open。

位置管什么调错的表现
fs.file-max整机 fd 总数上限进程级怎么调都提不上去，日志里可能出现 allocation failure
fs.nr_open单进程 fd 的绝对上限setrlimit 报 Invalid argument，服务起不来
ulimit -n / limits.confshell 会话及其子进程只对登录会话生效，systemd 服务不认
LimitNOFILEsystemd 管理的服务改 limits.conf 后重启服务，值还是旧的
容器 nofile容器内进程宿主调大了，容器里还是 1024

怎么算「该给多少」？不是拍一个 65535。先看真实的 fd 分布：ls /proc/<pid>/fd | wc -l 看当前用量，再按连接模型估峰值——一个进程持有 N 条连接，每条连接至少 1 个 fd，加上日志、配置文件、管道、epoll 句柄。给到峰值的 1.5 到 2 倍就够，给太大反而掩盖泄漏。

还有一个容易忽略的事实：fd 泄漏和内存泄漏经常同时出现。连接不关，fd 涨，每个连接还有读写缓冲，内存也涨。这时候调 ulimit 只是把爆炸时间往后推，从「一小时挂」变成「一天挂」，问题还在。

# 当前会话与进程的实际限制
ulimit -n
ulimit -Hn
cat /proc/$(pgrep -f myapp | head -1)/limits | grep -i 'open files'

# 内核层的两个上限
sysctl fs.file-max fs.nr_open

# systemd 服务的限制（改完要 daemon-reload + 重启服务）
systemctl show myapp -p LimitNOFILE
# /etc/systemd/system/myapp.service.d/override.conf
# [Service]
# LimitNOFILE=65535

# 谁在吃 fd
ls /proc/12345/fd | wc -l
lsof -p 12345 | awk '{print $5}' | sort | uniq -c | sort -rn | head
别把 fs.file-max 当成万能钥匙。它是整机总量，调得再大，单进程的 nofile 不放开照样撞墙；反过来，只把单进程调到几十万而 fs.nr_open 没跟上，设置直接失败。三个值的关系是「全局 ≥ 单进程硬上限 ≥ 进程 soft」，顺序搞反就会互相打架。

面试怎么答：「fd 有三个层次：fs.file-max 是整机总量，fs.nr_open 是单进程能设到的上限，ulimit 的 soft/hard 才是进程实际拿到的。systemd 服务不读 limits.conf，要改 unit 的 LimitNOFILE。调之前先算真实用量，不然只是把泄漏的爆炸时间往后推。」

模块 3

两个队列：somaxconn 管的是「握完手等 accept」那一个

这是本篇最容易被答错的一题，也是最能区分「背过」和「查过」的一题。面试官问「somaxconn 和 tcp_max_syn_backlog 有什么区别」，如果答「都是连接队列，一个总上限一个半连接上限」还算及格；如果答「都管全连接队列」或者「调大 somaxconn 就能防 SYN Flood」，就是错的。

服务端有两个队列，位置完全不同。半连接队列（SYN 队列）放的是「收到 SYN、回了 SYN-ACK、还在等最后一个 ACK」的连接，状态是 SYN_RECV。它的长度受 net.ipv4.tcp_max_syn_backlog 影响，灌满它的是 SYN Flood。全连接队列（accept 队列）放的是「三次握手已经完成、但应用还没调 accept 取走」的连接，状态在 ss 里表现为监听套接字的 Recv-Q。它的上限是 listen(fd, backlog) 与 somaxconn 的较小值。

维度半连接队列全连接队列
放什么SYN_RECV，握手未完成握手完成、等应用 accept
相关参数tcp_max_syn_backlog，受 syncookies 影响somaxconn 与应用 backlog 取小
谁打满它SYN Flood、客户端回程丢包应用 accept 太慢、突发流量
看什么指标ss -tan state syn-recv、SyncookiesSentss -lnt 的 Recv-Q/Send-Q、ListenOverflows
调参能解决吗缓解，但根治要靠 syncookies 和限速能缓解，但根治要提升 accept 速度

全连接队列溢出时，客户端看到的现象是超时而不是「连接被拒」。因为 tcp_abort_on_overflow 默认为 0 时，内核会把客户端的最后一个 ACK 丢掉，客户端以为自己已经 ESTABLISHED，发数据过去没有响应，重传几次后超时。这也是为什么「服务端 ss 看起来一切正常，客户端就是连不上」——连接压根没进到能被 ss 看见的状态。

调的时候必须两边一起调：内核的 somaxconn 和应用 listen() 的 backlog。Nginx 的 backlog 在 listen 80 backlog=4096 里，默认值以你环境的版本为准；Tomcat、Gunicorn、Node 各有自己的参数名。只改内核，取小值之后等于没改；只改应用，超过 somaxconn 的部分会被截断。

# 看监听队列水位：Recv-Q 接近 Send-Q 就是满了
ss -lnt
# State  Recv-Q  Send-Q  Local Address:Port
# LISTEN 4096    4096    0.0.0.0:8080        <-- 满了，应用 accept 跟不上

# 两个参数当前值（默认值随内核版本变化，以你环境为准）
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog
sysctl net.ipv4.tcp_abort_on_overflow

# 溢出计数看增量
nstat -n1 -z TcpExtListenOverflows TcpExtListenDrops TcpExtSyncookiesSent

# 半连接堆积
ss -tan state syn-recv | wc -l
关于半连接队列的边界要说清：tcp_max_syn_backlog 影响的是 SYN 队列能排多长，但它的最终有效长度还受内核版本、是否开启 syncookies 等因素影响，具体计算以你内核版本的文档和源码为准，不要照抄某个博客给的固定数字。能确定的是：它和 somaxconn 管的是两个不同的队列，不能互相替代。

SYN Flood 的正解不是把 tcp_max_syn_backlog 调到十万。队列再长也能被灌满，而且每个半连接都占内存。syncookies 才是那个「不存状态」的方案：队列满了之后不回 SYN-ACK 就丢，而是把连接信息编码进初始序号，客户端带回 ACK 时再校验重建。tcp_syncookies 有三个值：0 关闭，1 只在溢出时启用，2 无条件启用。多数发行版默认是 1，代价是部分 TCP 选项信息无法携带。

面试怎么答：「这是两个不同的队列。somaxconn 限制的是全连接队列，也就是握手完成、等着应用 accept 的那批，上限取 listen backlog 和 somaxconn 的较小值；tcp_max_syn_backlog 影响的是半连接队列，放 SYN_RECV。前者满了表现为客户端超时、ListenOverflows 增长，后者满了是被 SYN Flood 打。调 somaxconn 必须同时调应用 backlog，否则取小值等于没调。」

模块 4

TIME_WAIT 与端口：reuse 有边界，recycle 已经没了

这两个参数的名字只差几个字母，却是「还能用」和「已经不存在」的区别。更麻烦的是，网上大量「高并发优化」文章还在教人打开 tcp_tw_recycle，而它在 Linux 4.12 就已经从内核移除。你在新机器上执行 sysctl -w net.ipv4.tcp_tw_recycle=1，只会得到一个「no such file」类的错误。

先说 TIME_WAIT 是什么。主动关闭连接的一方在发完最后一个 ACK 后进入这个状态，Linux 上固定等 60 秒，没有 sysctl 能改这个时长。tcp_fin_timeout 改不了它，那个参数管的是「孤儿 FIN_WAIT_2」，两回事。堆积量约等于「每秒主动关闭的连接数 × 60」，所以它本质上是个容量信号。

再说 tcp_tw_reuse 的边界，这是最容易答错的地方。它允许主动发起连接的一方复用还在 TIME_WAIT 的四元组，只对出方向生效，而且需要开启 tcp_timestamps 才有意义（靠时间戳判断新连接的回绕序号是否安全）。它不能减少本机作为服务端被动关闭产生的 TIME_WAIT，也不能让监听套接字受益。所以「服务端 TIME_WAIT 多，开 reuse」这个动作，方向就是错的。

参数实际作用边界与现状
tcp_tw_reuse允许主动连接复用 TIME_WAIT 的四元组只影响出方向；依赖时间戳；不改变 TIME_WAIT 的时长
tcp_tw_recycle曾经用于快速回收 TIME_WAIT4.12 起已从内核移除；老内核开启后在 NAT 下会误丢连接，不应使用
tcp_max_tw_bucketsTIME_WAIT 套接字总数上限超限直接销毁并打日志，是掩盖不是解决
tcp_fin_timeout孤儿 FIN_WAIT_2 的超时跟 TIME_WAIT 无关，调它没用
ip_local_port_range客户端可用本地端口范围扩大能推迟端口耗尽，要同步看 conntrack 和防火墙
tcp_timestamps启用时间戳选项reuse 依赖它；关掉会让 PAWS 和 RTT 测量受影响

算一笔账就明白端口为什么会耗尽：假设本地端口范围给了约 2.8 万个，TIME_WAIT 60 秒，那么对同一个目的地址的新建连接速率上限大约是 28000 ÷ 60 ≈ 470 次/秒。超过这个量就会报 Cannot assign requested address。注意这里限定「同一个目的地址」，因为四元组里目的 IP 和端口不同也能复用同一个源端口。

正确的处置顺序是：先看是不是短连接打同一个下游，能不能改连接池或长连接；再看端口范围是否过窄；参数只作为辅助。tcp_tw_reuse 在「客户端侧、大量短连接、已开时间戳」这个组合下是有意义的，其他场景基本无效。

# 现状：端口范围、TIME_WAIT 数量、两个开关
sysctl net.ipv4.ip_local_port_range
ss -tan state time-wait | wc -l
sysctl net.ipv4.tcp_tw_reuse net.ipv4.tcp_timestamps

# 按远端聚合，看是不是集中在某几个下游（短连接的典型特征）
ss -tan state time-wait | awk 'NR>1 {print $5}' | cut -d: -f1 | \
  sort | uniq -c | sort -rn | head

# 确认这个内核到底有没有 recycle（新内核会报错，这是正常的）
sysctl net.ipv4.tcp_tw_recycle

# 临时调整（重启失效，持久化见模块 8）
sysctl -w net.ipv4.ip_local_port_range="10240 65000"
面试里提到 tcp_tw_recycle，唯一正确的说法是「它已被移除，不该用」。如果要展开，就说它在 NAT 环境下依赖对端时间戳递增来判断报文新旧，多台客户端共用出口 IP 时时间戳顺序不可比，正常报文会被丢弃，表现为「偶发连不上、重试就好」。这条历史正好解释了为什么内核把它删了，而不是留个开关。

面试怎么答：「TIME_WAIT 是主动关闭方等 60 秒，Linux 上改不了时长，tcp_fin_timeout 管的是另一件事。tcp_tw_reuse 只对主动发起连接的一方有效，而且依赖时间戳，服务端被动关闭的那部分用不上。tcp_tw_recycle 在 4.12 已经从内核移除，现在不该出现在任何配置里。真正的解法是长连接和连接池。」

模块 5

缓冲区与拥塞控制：先算 BDP，再谈调多大

「把 rmem_max 和 wmem_max 调到 16MB，网络就快了」——这句话在局域网低延迟环境里几乎没用，在跨地域链路上才可能有效。因为决定要不要调的不是「越大越好」，而是带宽时延积：这条链路上「在途数据」最多能有多少。

BDP 的算法很朴素：带宽 × RTT。100 Mbps 的链路、RTT 100ms，在途数据最多约 12.5 MB/s × 0.1s = 1.25 MB。如果接收窗口和缓冲区远小于这个值，发送方就会因为「窗口满了」停下来等 ACK，吞吐被卡在「窗口 ÷ RTT」，链路再宽也用不满。这就是长肥管道（长距离、高带宽）里单流跑不快的经典原因。

参数作用怎么用
net.ipv4.tcp_rmem接收缓冲的最小/默认/最大，三元组自动调优开启时，内核在 min 和 max 之间动态调整
net.ipv4.tcp_wmem发送缓冲的最小/默认/最大同上，最大值决定单连接能撑多大 BDP
net.core.rmem_max / wmem_max应用用 setsockopt 能设到的上限应用自己设缓冲区时受它限制
tcp_moderate_rcvbuf接收缓冲自动调优开关默认开启，一般不用动
tcp_congestion_control拥塞控制算法默认通常是 cubic，可切 bbr
default_qdisc默认排队规则BBR 通常搭配 fq

调缓冲区的风险要说清：每个连接都会占内存。最大缓冲调到 16MB，一万条活跃连接在极端情况下可能吃掉几十 GB。而且缓冲区太大会造成 bufferbloat——数据堆在队列里，延迟升高，交互型业务反而更差。所以「调大缓冲」这件事只对大带宽长延迟的吞吐型流量成立，对短请求、低延迟业务是负收益。

拥塞控制的选择是另一个维度。CUBIC 把丢包当拥塞信号，在有一定随机丢包的链路上会过度降速；BBR 持续测量瓶颈带宽和最小 RTT，不把丢包直接等同于拥塞。切 BBR 的前提是内核支持（4.9 以后的主线才有，具体以你内核为准），并且通常配合 fq 排队规则。切换是全局的，会影响这台机器上所有连接，必须灰度：先一台，观察吞吐、重传、CPU 和公平性，再推广。

# 看当前值和可用算法
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem
sysctl net.core.rmem_max net.core.wmem_max
sysctl net.ipv4.tcp_congestion_control
sysctl net.ipv4.tcp_available_congestion_control

# 单连接的窗口、RTT、重传，用来验证是不是窗口不够
ss -tin dst 10.0.0.12:8080
# 关注 rtt、cwnd、snd_wnd、rcv_space、retrans

# 切 BBR（先确认模块可用，再灰度）
modprobe tcp_bbr
sysctl -w net.ipv4.tcp_congestion_control=bbr
sysctl -w net.core.default_qdisc=fq

# 看队列规则是否生效
tc qdisc show dev eth0
别在容器里随手改 net.*。一部分网络参数是按 network namespace 隔离的，改了只影响当前命名空间；另一部分是全命名空间共享的，改了会影响宿主上的所有容器。具体哪些隔离、从哪个内核版本开始隔离，以你内核版本的文档为准。在容器里调参前先确认作用域，否则很容易「调了没效果」或者「影响了别人」。

面试怎么答：「缓冲区要不要调，先算 BDP：带宽乘 RTT。窗口小于 BDP 时吞吐会被卡住，这时候调大才有效。但缓冲区是按连接占内存的，调太大会 bufferbloat，延迟反而升高。拥塞控制我一般先看链路的丢包特征，BBR 适合有随机丢包的场景，切换要灰度，还要配 fq。」

模块 6

内存：swappiness 不是「关 swap 的开关」

「数据库服务器要把 swappiness 设成 0」——这句话流传极广，但它是把「减少换页」误解成了「禁止换页」。vm.swappiness 调的是回收匿名页和文件页的相对倾向，不是开关；设成 0 也不代表不会 swap，只是内核会尽量先回收 page cache。

取值范围在较新内核里是 0 到 200（100 表示匿名页和文件页同等对待），默认通常是 60。不同内核版本的语义和默认值有差异，以你环境为准。把它调低适合「延迟敏感、内存足够、希望尽量保留 page cache」的场景；调成 0 在内存压力大时可能导致回收不动匿名页，最后触发 OOM，而不是优雅地换出——这比 swap 更糟。

参数作用典型误用
vm.swappiness匿名页与文件页的回收倾向设 0 当成禁用 swap
vm.overcommit_memory0 启发式、1 总是允许、2 严格按上限无脑设 2，导致 fork 失败
vm.overcommit_ratio模式 2 下可超额的比例设了 2 却没算 CommitLimit
vm.dirty_ratio脏页占总内存多少时同步回写阻塞调很大，写突发时延迟飙升
vm.dirty_background_ratio多少时开始后台回写和 dirty_ratio 贴太近，失去缓冲
vm.min_free_kbytes内核保留的空闲内存水位调太大反而压缩可用内存

overcommit_memory 的三个值要能说清：0 是启发式判断，大多数情况够用；1 是「总是答应」，分配时不检查，真正写入时才可能 OOM；2 是「严格不许超过上限」，上限由 CommitLimit 决定，跟 overcommit_ratio 和 swap 有关。Redis 做后台保存时 fork 子进程，官方建议把 1 打开，原因是 fork 依赖 COW，而启发式判断可能在这种大地址空间下拒绝分配。这是特定场景的建议，不是所有服务的通用配置。

脏页参数是另一个高频现场：内存很大、写入很猛，dirty_ratio 默认在 20% 左右，意味着可以攒下几十 GB 脏页，攒到阈值后内核开始同步回写，所有写操作一起卡住，表现为「每隔一段时间 IO 延迟飙高」。这种周期性尖刺，调 dirty_background_ratio 让后台回写更早介入，比换 SSD 更直接。

# 内存与回收的现状
free -m
sysctl vm.swappiness vm.overcommit_memory vm.overcommit_ratio
grep -E 'CommitLimit|Committed_AS|Dirty|Writeback' /proc/meminfo

# 脏页回写参数（比例和字节两套，设了字节就以字节为准）
sysctl vm.dirty_ratio vm.dirty_background_ratio
sysctl vm.dirty_expire_centisecs vm.dirty_writeback_centisecs

# 透明大页：数据库和 Redis 场景经常要关掉或改成 madvise
cat /sys/kernel/mm/transparent_hugepage/enabled

# 谁在吃内存（RSS 会重复计共享库，PSS 更准）
ps -eo pid,rss,comm --sort=-rss | head
grep -E '^(AnonPages|Cached|Slab|SReclaimable)' /proc/meminfo
透明大页（THP）值得单独记一句。它把 4KB 页合并成 2MB，减少 TLB miss，对吞吐型负载有好处；但分配和整理大页时会引入延迟抖动，某些数据库和缓存服务因此建议设成 madvise 或 never。这是取舍不是定论：延迟敏感就保守，吞吐优先可以保留默认，改之前必须压测对比。

面试怎么答：「swappiness 调的是匿名页和文件页的回收倾向，不是 swap 开关，设 0 也可能换页，还可能更容易 OOM。overcommit 三个模式里，2 是严格上限，配错会让 fork 直接失败；Redis 建议设 1 是 fork 加 COW 的特定场景。脏页参数调不好会出现周期性写延迟尖刺。」

模块 7

文件系统与 IO 调度：先看设备类型，再选策略

「IO 调度器选哪个」——这题没有统一答案，只有「这块盘是什么类型」。给 NVMe 配 bfq，纯属浪费；给机械盘配 none，请求全堆在设备队列里，延迟会更难看。判断依据是设备的寻道成本和并发能力，不是「哪个名字新」。

挂载选项里最值得改的是 noatime。默认的 relatime 已经比老式的 atime 省很多（只在 atime 早于 mtime 或超过一天时更新），但对写密集、读频繁的目录，noatime 还能再省掉一批元数据写。代价是「最后访问时间」不再准确——如果有备份工具或审计依赖它，就不能关。

设备类型常用调度器理由
NVMe / 高性能 SSDnone（或 mq-deadline）设备自身并发强、没有寻道，内核再排序收益很小
普通 SATA SSDmq-deadline保证请求在截止时间内被处理，兼顾吞吐和延迟
机械盘bfq 或 mq-deadline需要合并和排序，减少寻道；bfq 对交互延迟更友好
虚拟化云盘跟随厂商建议，常为 none调度在宿主机侧做，客户机里再排一次意义有限

除了调度器，还有两个常被忽略的：read_ahead_kb（预读大小，顺序读大文件时可以调大，随机读调大是浪费）和文件系统的挂载参数（比如 nodiratime、日志模式）。这些都要配合业务 IO 模式来定，顺序读和随机读的最优值完全不同。

怎么判断 IO 是不是瓶颈？不要只看 %util。iostat -x 里更值得看的是 await（平均等待，含排队）、aqu-sz（平均队列长度）和 r/s、w/s 的分布。一块 NVMe 的 %util 到 100% 可能还有余量，因为设备内部并行度很高；而机械盘 await 一涨，基本就是队列堆起来了。

# 当前调度器与预读
cat /sys/block/nvme0n1/queue/scheduler
cat /sys/block/nvme0n1/queue/read_ahead_kb

# 临时切换调度器（重启失效，持久化用 udev 规则更稳）
echo mq-deadline > /sys/block/sda/queue/scheduler

# 挂载选项：确认 noatime 有没有生效
findmnt -no OPTIONS /
mount | grep ' / '

# IO 现状：await、aqu-sz 比 %util 更能说明排队
iostat -x 1 3
云环境里改调度器经常是无效动作。块设备可能是 virtio 或者厂商自研驱动，调度发生在宿主机；你在客户机里改了，看起来生效了，实际路径上并不经过。改之前先确认设备型号和虚拟化类型，再看厂商的推荐值，别把物理机的经验直接套上去。

面试怎么答：「调度器按设备选：NVMe 用 none，SATA SSD 用 mq-deadline，机械盘用 bfq 或 mq-deadline，云盘跟厂商建议。挂载上 noatime 能省元数据写，但要看有没有工具依赖 atime。判断 IO 瓶颈我看 await 和 aqu-sz，不只看 %util，因为 NVMe 的 util 到 100% 不代表饱和。」

模块 8

持久化与灰度：改内核参数是一次线上变更

「参数改了，重启之后全没了」——这是最冤的一类返工。反过来更危险的是「改了、也持久化了、但没人记得改过」，半年后换人接手，看到一堆来历不明的数字，不敢动也不敢删。

持久化的正确位置是 /etc/sysctl.d/ 下的独立文件，按文件名排序加载，用 sysctl --system 一次性应用。不要直接改 /etc/sysctl.conf，那个文件是兼容用的，多个团队往里追加，冲突了很难查。文件名带上用途和日期，比如 99-nginx-conn.conf，注释写清「为什么改、谁改的、对应哪次故障」，这比参数本身更重要。

要注意加载顺序：sysctl --system 会按文件名排序读多个目录，后读的覆盖先读的。所以 99- 开头的会覆盖 10- 开头的，同名参数以最后一个为准。排查「我明明写了为什么没生效」时，先看有没有别的文件在后面覆盖了它。

# /etc/sysctl.d/99-web-conn.conf
# 2026-03 新连接超时排查：accept 队列溢出，配合应用 backlog 一起调
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 4096

# Kubernetes 节点上常见的转发与端口范围
net.ipv4.ip_forward = 1
net.ipv4.ip_local_port_range = 10240 65000

# 应用并确认
sysctl --system
sysctl net.core.somaxconn

# 看某个参数被哪些文件定义过（排查覆盖）
grep -rn 'somaxconn' /etc/sysctl.conf /etc/sysctl.d/

灰度是另一半。内核参数影响的是整机所有进程，改错一次可能是全站故障，所以流程要和发布一样：选一台低峰期灰度机 → 记录基线 → 改一个参数 → 观察至少一个业务周期 → 对比指标 → 再推第二批。观察窗口不能太短，很多问题（比如脏页回写、端口耗尽）要十几分钟甚至几小时才显形。

写变更单。参数名、旧值、新值、依据、预期影响、回滚命令，五样缺一不可。没有回滚命令的变更不该执行。
先在一台上改。用 sysctl -w 临时生效，不写文件。这样重启就能回滚，适合先验证。
观察四类指标。业务的成功率与 P99、连接队列溢出计数、重传与超时计数、内存与脏页。至少看一个完整业务周期。
确认后写进 sysctl.d。同时把临时值改成文件里的持久值，避免「重启后行为变了」这种二次故障。
分批推，留回滚窗口。第二批、第三批之间留间隔。回滚就是改回旧值再 sysctl --system，事先把命令写在变更单里。
面试里的加分点不是「我调过什么」，是「我怎么知道它有效」。能说出「改之前记了基线，改完对比 ListenOverflows 的增量和 P99，灰度一天后才全量」，比报一串数字可信得多。参数值会过时，方法不会。

面试怎么答：「内核参数我当成一次线上变更来做：写进 /etc/sysctl.d 独立文件、注释写清原因、先在一台机器用 sysctl -w 验证、观察一个业务周期、再分批推。回滚命令提前写好。因为这类参数影响整机所有进程，出问题的面比单个服务大。」

模块 9

十个坑：抄来的配置，往往比默认值更危险

内核参数的坑有个共同特征：改错了不会立刻报错。系统照常启动，服务照常运行，问题在某个特定流量模式下才显形。所以下面十条里，一半是「不该改」，一半是「改了但没改对」。

1
打开 tcp_tw_recycle
这个参数在 Linux 4.12 已经被移除。老内核上开它，在 NAT 环境会按时间戳判断报文新旧，多客户端共用出口 IP 时正常包被丢弃，表现为偶发连接超时、重试就好。看到配置里有它，直接删。
2
以为 tcp_tw_reuse 能解决服务端的 TIME_WAIT
它只作用于主动发起连接的一方，还需要 tcp_timestamps 开启。服务端被动关闭产生的 TIME_WAIT 跟它无关。方向搞错，改了也看不到任何变化。
3
把 somaxconn 和 tcp_max_syn_backlog 当成同一个队列
前者限制全连接队列（等 accept），后者影响半连接队列（SYN_RECV）。一个满了表现为客户端超时、ListenOverflows 增长，另一个满了是被 SYN Flood 打。调错对象等于没调。
4
只调 somaxconn，不调应用 backlog
全连接队列上限取两者的较小值。内核调到 65535，Nginx 还是默认 backlog，实际生效的就是那个小的。两边必须一起改。
5
把 somaxconn 调到十万就以为能扛住高并发
队列只是缓冲，真正消费连接的是应用的 accept 速度。应用 accept 慢，队列再长也只是把超时时间往后推，同时占用更多内存。先看 Recv-Q 的增长趋势和应用的 accept 逻辑。
6
改了 limits.conf，systemd 服务不生效
limits.conf 由 PAM 在登录会话时应用，systemd 启动的服务走的是 unit 里的 LimitNOFILE。改完还要 daemon-reload 并重启服务，光 reload 不行。
7
把 vm.swappiness 设成 0 当成关闭 swap
它调的是回收倾向，不是开关。设 0 之后内核尽量不换出匿名页，内存压力大时可能直接触发 OOM，比换页更糟。延迟敏感场景调低可以，别把它当禁用。
8
vm.overcommit_memory 无脑设 2
模式 2 是严格上限，超过 CommitLimit 的分配直接失败，fork、启动大堆服务都可能报错。它适合需要确定性内存控制的场景，不适合所有机器。Redis 建议的是 1，不是 2。
9
把 TCP 缓冲区拉到最大就以为更快
缓冲区按连接占内存，调太大会 bufferbloat，排队延迟升高。要先算 BDP，再看业务是吞吐型还是延迟型。短请求业务调大缓冲通常是负收益。
10
改完不持久化，或者持久化后不记录
只 sysctl -w 不写文件，重启就回到旧值，下次故障重现；写了文件不写注释，半年后没人知道这几个数字是干什么的，没人敢删。参数、原因、日期、回滚方式，四样一起留下。

面试怎么答：挑一条最有把握的讲，重点放在「你怎么发现它错了」。比如「我们一台机器上有 tcp_tw_recycle，NAT 后面偶发超时，抓包看到服务端直接把包丢了、没有 RST，查下来是这个参数，删掉就好了，从那以后所有机器都加了配置审计」。有现象、有证据、有机制，才叫经验。

自测

六道题

1. 关于 net.ipv4.tcp_tw_recycle，下面哪个说法正确？
正确答案：已移除。它在 4.12 就被删掉了，新内核上设置会直接失败。老内核里它的机制依赖对端时间戳递增来判断报文新旧，NAT 后多台客户端共用 IP 时时间戳不可比，正常报文会被丢掉，所以内核选择移除而不是保留开关。
2. tcp_tw_reuse=1 对下面哪种情况有效？
正确答案：主动发起连接的一方。这个参数只影响出方向，并且依赖 tcp_timestamps（用时间戳判断新连接的序号是否安全）。它不缩短 TIME_WAIT 的 60 秒，也不作用于服务端被动关闭的那部分，所以「服务端 TIME_WAIT 多就开 reuse」是无效动作。
3. net.core.somaxconn 限制的是哪个队列？
正确答案：全连接队列。它和应用 listen() 的 backlog 一起决定 accept 队列长度，取较小值。半连接队列由 tcp_max_syn_backlog 影响（实际有效长度还受内核版本和 syncookies 影响）。两者是不同队列，不能互相替代。
4. 压测时客户端大量连接超时，服务端 ss -lnt 显示监听套接字 Recv-Q 等于 Send-Q，最可能的原因是？
正确答案：全连接队列满。Recv-Q 是当前等待 accept 的连接数，Send-Q 是队列上限，两者相等就是满了。默认 tcp_abort_on_overflow=0 时内核会丢掉客户端的 ACK，客户端以为自己已连上，实际发数据没响应，最后超时——所以现象是超时而不是拒绝。
5. 关于 vm.swappiness，下面哪个理解正确？
正确答案：回收倾向。它不是开关，设成 0 也不保证不换页，只是内核会尽量先回收 page cache；在内存压力大时反而可能更容易触发 OOM。取值上限在较新内核里是 200，默认通常是 60，具体语义和默认值以你环境的内核文档为准。
6. fs.file-max 和 fs.nr_open 的区别是？
正确答案：整机 vs 单进程。fs.file-max 是系统范围内所有进程能打开的 fd 总数；fs.nr_open 是单个进程通过 setrlimit 能设到的天花板。进程实际生效的是 ulimit 的 soft 值，systemd 服务则由 unit 的 LimitNOFILE 决定。

dirty_ratio脏页占比达到多少时同步回写，调不好会出现周期性写延迟尖刺
THP透明大页，减少 TLB miss，但可能带来延迟抖动，属于取舍
mq-deadline多队列下的截止时间调度器，SSD 常用；NVMe 常直接用 none
sysctl.d内核参数的持久化目录，按文件名排序加载，后加载的覆盖前面的
ss -lntRecv-Q 贴近 Send-Q 就是全连接队列满了
nstat -n1 -z TcpExtListenOverflows TcpExtListenDrops看每秒增量，判断队列是否在持续溢出
sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog两个队列的上限，别混为一谈
ss -tan state time-wait | wc -lTIME_WAIT 总量，配合远端聚合看是不是短连接
sysctl --system应用 /etc/sysctl.d 下的全部配置
下一步怎么练：① 在测试机上把 somaxconn 调到 8、应用 backlog 也调到 8，用 ab -c 50 压一下，看 Recv-Q 和 ListenOverflows 怎么变，这是理解两个队列最快的方式；② 用 ss -tan state time-wait 观察一次短连接脚本跑完后的堆积量，验证「速率乘 60」这个估算；③ 把 net.ipv4.tcp_tw_recycle 在一个新内核上设一次，亲眼看它报错，比背「已移除」记得牢。
