开始前

三个现场，全都不是「Nginx 坏了」

值班群里最常见的句式是「Nginx 又 502 了，重启一下」。重启确实有时能好，因为重启把卡住的上游连接全断了；但三五分钟后又复发，原因一个字都没查。Nginx 在绝大多数故障里不是被告，是唯一的目击者——它手里有上游的状态码、耗时、连接错误，只是没人去看它的日志。

先把三个高频现场摆出来，它们的共同点是「直觉指向 Nginx，证据指向别处」。

现场直觉答案真实原因
新加了一条 location /api，老接口突然 404Nginx 按书写顺序从上往下匹配，写在后面的没生效正则 location 的优先级高于普通前缀。~ \.php$ 这类规则一旦命中，最长前缀就被丢掉；想保住前缀得用 ^~
同一个后端，A 域名正常、B 域名 404后端服务对不同域名处理不一致两个 server 里 proxy_pass 一个带 URI、一个不带。带 URI 时匹配到的那段前缀会被替换掉，后端收到的路径根本不是它预期的
502 突增，重启 Nginx 缓解十分钟又复发Nginx 进程有问题，或者并发太高重启只是把上游连接池清空了。真实原因是上游连接被拒、全连接队列满、或响应头超过 proxy_buffer_size，日志里 upstream 那一行写得清清楚楚
为什么先讲这三个：它们分别对应「匹配规则记错」「路径改写没算清」「把转发者当责任方」。面试官问 Nginx，八成不是考你背不背得下 proxy_set_header，而是考你能不能说清一个请求在哪一层被改成了什么样。配置是结果，不是原因。

这一篇按「一个请求进来以后发生什么」组织：先看进程模型和它为什么快，再看配置是怎么一层层继承的，然后是 location 怎么选中、URI 怎么被改写、客户端 IP 怎么丢的，接着是超时、缓冲、502 家族，之后是限流和静态资源，收在十个坑。

面试怎么答：「Nginx 的题我一般从请求路径讲：进来先过 server 匹配，再选 location，然后决定 URI 要不要改写，再决定用不用缓冲、超时给多少，出错时看 upstream 那一行。把这五步说清，配置题基本都能推出来。」

模块 1

master 与 worker：快不是因为「用了 epoll」

「Nginx 为什么快」的标准答案是「epoll 加多路复用」。这句话不算错，但它解释不了为什么同样用 epoll 的很多服务没这么快，也解释不了为什么 Nginx 的 worker 数一般就等于核数，而不是几百个。

先看进程结构。master 不处理任何请求，它只做四件事：读配置、绑端口、管 worker、接信号。真正干活的是 worker，每个 worker 是单线程的，各自跑一个事件循环，彼此不共享连接状态。所以 Nginx 的性能不来自「线程多」，来自每个连接的处理成本极低：没有线程栈、没有锁竞争、没有为每个连接开协程，一个连接就是一个 fd 加一小块内存。

快的原因拆开是四条：事件驱动，一个 worker 用 epoll 同时盯上万 fd，谁就绪处理谁；进程数少，避免了大量上下文切换和缓存失效；零拷贝，静态文件走 sendfile，数据不经过用户态；内存池，每个连接的生命周期内少次分配、少次释放。epoll 只是第一条里的一块。

配置项它真正限制的东西常见误判
worker_processes autoworker 数量，auto 等于 CPU 核数调大不会更快。超过核数只增加调度开销，除非大量阻塞型第三方模块
worker_connections单个 worker 能同时打开多少连接它不是「客户端并发数」。反向代理时一个客户端占两条连接，客户端并发大约只有一半
worker_rlimit_nofileworker 进程的 fd 上限只调 worker_connections 而 fd 上限卡在 1024，超了直接报 too many open files
multi_accept一次是否尽量多 accept高并发下开它有帮助，低并发下没意义
accept_mutex / reuseport多个 worker 抢同一个 listen socket 的方式这是「惊群」问题，不是性能开关。reuseport 让内核按四元组散列到 worker，通常更省事

算并发上限时要把两段都算进去：客户端连接数上限约等于 worker_processes × worker_connections ÷ 2（反向代理场景），而且 worker_rlimit_nofile 要大于等于这个数。见过把 worker_connections 调到 65535、fd 上限还是 1024 的配置，跑了半年没出事，因为流量从来没到过那个水位——这种「配置看着很猛」的现场，一问峰值就露馅。

另一个必问点是 reload 为什么不断连接。执行 reload 时 master 重新解析配置、起一批新 worker，然后给旧 worker 发信号：别再接新连接了，把手上的处理完就退出。所以正在传输的请求不会被打断。代价是长连接和大文件会拖住旧 worker——一个跑着 WebSocket 的 worker 可能几个小时都退不掉，这段时间新旧两套配置同时在跑，内存翻倍。要兜底就配 worker_shutdown_timeout，到点强退。

# 看 worker 数量和各自吃掉的 CPU（正常应该比较均匀）
ps -eo pid,ppid,pcpu,rss,comm | grep nginx
top -H -p $(cat /run/nginx.pid)

# 看监听队列水位：Recv-Q 接近 Send-Q 就是 accept 跟不上
ss -lnt | grep -E ':80|:443'

# 打开状态页后，这三个数字比任何监控都直接
# curl -s http://127.0.0.1/nginx_status
# Active connections: 291
# server accepts handled requests
#  16630948 16630948 31070465
# Reading: 6 Writing: 179 Waiting: 106

# Waiting 高说明连接闲着（keepalive），Writing 高说明在回数据

状态页里 accepts 和 handled 如果不相等，说明有连接被丢弃过，通常是队列溢出或资源不足；Waiting 是空闲的 keepalive 连接，它高不代表慢，只代表连接复用做得好。

面试怎么答：「Nginx 快是几个因素叠加：单线程事件循环、worker 数等于核数所以没有线程切换、静态文件走 sendfile 零拷贝、连接级内存池。epoll 只是其中一环。并发上限要把 worker_connections 乘 worker 数，反向代理还要除以二，因为一个请求占两条连接。」

模块 2

配置层级：继承不是合并，是覆盖

一个很典型的现场：安全扫描说响应缺 X-Frame-Options，你去 http 块里加了一行 add_header，全站生效了。过了两周，某个业务在 server 里加了一行 add_header Cache-Control，那个站点的安全头全部消失，扫描又报。

原因是 Nginx 的继承规则分两类。值型指令（比如 client_max_body_size、proxy_read_timeout）是「子层没写就继承父层，写了就用子层的」。数组型指令（add_header、proxy_set_header）更狠：子层只要出现一条，父层的同类指令就完全不继承，而且不会合并。这就是「加了一行缓存头，丢了三个安全头」的机制。

层级能放什么典型错误
mainuser、worker_processes、pid、error_log把 server 块写在这里，启动直接报错
eventsworker_connections、multi_accept、use以为 worker_connections 是全局上限
httpmime、log_format、gzip、upstream、include在 http 里写 proxy_pass，非法
serverlisten、server_name、root、location两个 server 抢同一个 server_name，前一个静默生效
locationproxy_pass、try_files、limit_req、alias以为 location 里的配置能反向影响 server
if / limit_except极少数指令在 if 里写 proxy_pass，行为不可预期

组织配置的常规做法是主文件只留全局项，站点拆到 conf.d/*.conf 或 sites-enabled/*，用 include 引进来。通配符是按字典序展开的，所以文件名前面的数字有意义：00-default.conf 会排在 10-api.conf 前面。默认 server（listen 80 default_server）最好显式指定，否则就是第一个被加载的那个，改个文件名可能就把默认站点换了。

排「配置到底生效了没」只有一个可靠办法：nginx -T 把所有 include 展开后打印出来，直接搜关键字。nginx -t 只做语法检查，它不保证你改的那份文件被 include 了——这是新手最常踩的空转。

# 语法检查 + 打印最终生效的完整配置（含所有 include）
nginx -t
nginx -T 2>/dev/null | grep -n -A3 'server_name api.example.com'

# reload 的正确姿势：先测再重载，失败时老进程仍按老配置跑
nginx -t && nginx -s reload
systemctl reload nginx

# 确认 reload 真的换了 worker（PID 应该变了）
ps -eo pid,lstart,cmd | grep 'nginx: worker'
reload 失败不会中断服务，这是好事也是坑。nginx -t 不过就直接 reload，命令返回非零，但老进程照样服务，监控上什么都看不出来，你会以为改完了。所以「改完没生效」的第一步永远是看 reload 的返回码和 error_log，不是怀疑浏览器缓存。

面试怎么答：「Nginx 的配置是树形继承，值型指令子层覆盖父层，数组型指令子层一旦出现就完全不继承父层，add_header 丢安全头就是这么来的。查配置有没有生效我不看文件，直接 nginx -T 看展开后的结果。」

模块 3

location：先最长前缀，再正则，^~ 是刹车

「location 的匹配顺序是什么」这题，能背出「精确、前缀、正则、通用」四个词的很多，但给一段真实配置问「这个请求命中哪个」，答对的很少。因为顺序不是一条链，是两轮。

准确的流程是这样：先找精确匹配 =，命中就结束。没有精确匹配，就在所有普通前缀里找最长的那条，先记下来但不定。如果这条最长前缀带 ^~，就用它，不再看正则。否则按配置文件里出现的顺序逐个试正则 ~ 和 ~*，第一个命中的直接胜出，也不再看更长的前缀。正则全不命中，才回到刚才记住的最长前缀。

修饰符含义命中后什么时候用
=完全相等立即结束，优先级最高= /health 这类探针，省掉所有匹配开销
^~前缀匹配，且不再试正则用最长的那条，跳过正则静态目录、上传目录，防止被一条 .php 正则抢走
~区分大小写的正则按出现顺序，第一个命中即用后缀、路径重写、UA 判断
~*不区分大小写的正则同上图片后缀这类大小写混用的场景
无普通前缀记住最长的一条，参与第二轮比较绝大多数业务路由
@name命名 location不参与外部匹配只给 error_page、try_files 内部跳转用

两个细节最容易答错。第一，前缀匹配是字符串前缀，不是路径段：location /api 会匹配 /apiary，所以业务路由最好带上尾部斜杠写成 /api/。第二，正则的先后是书写顺序，不是长度顺序，两条正则都能命中时，写在前面那条赢，哪怕它更短。

^~ 存在的意义值得单独说。它不只是性能优化，更是意图声明：我这段路径不参与正则竞争。线上事故里很常见的一条是 location ~ \.(gif|jpg|png)$ 把 /upload/2024/logo.png 抢去走了动态代理，结果这个路径本该由静态目录处理。location ^~ /upload/ 一写，问题就没了。

# 匹配演示：请求 /static/img/logo.png
location = /health            { return 200 'ok'; }          # 只有完全等于才命中
location ^~ /static/          { root /data/www; }            # 命中，且不再看正则
location ~* \.(png|jpg|gif)$  { proxy_pass http://img_up; }  # 被 ^~ 挡住，不参与
location /                    { proxy_pass http://web_up; }  # 兜底

# 验证命中了哪条：给每条加一个独有的响应头，比看日志快
curl -sI https://example.com/static/img/logo.png | grep -i x-route

# 或者直接看 debug 日志里的 matching 过程（需要 debug 版本）
# error_log /var/log/nginx/error.log debug;
# grep 'using configuration' /var/log/nginx/error.log | tail

还有一个隐藏的交互：rewrite ... last 会重新走一遍 location 匹配，而 rewrite ... break 停在当前 location 继续往下执行。server 级的 rewrite 又在 location 选择之前执行。所以一段配置里同时有 rewrite 和 location 时，别靠猜，看日志里的 using configuration 那一行。

面试怎么答：「location 分两轮：先精确匹配，再找最长前缀并记住；如果最长前缀带 ^~ 就直接用，否则按书写顺序试正则，第一个命中就赢，都不中才回到最长前缀。所以正则不是比长度，是比顺序；前缀也不是按路径段，是字符串前缀。」

模块 4

proxy_pass 的尾斜杠：一个字符换一个路径

后端同学说「接口 404，路径是 /v1/users，但我网关明明转发的是 /api/v1/users」。这不是后端的问题，是 proxy_pass 后面那个斜杠把前缀吃掉了，而写配置的人以为它只是个格式习惯。

规则只有一句话：看 proxy_pass 后面有没有 URI（哪怕只有一个 /）。有 URI，就把「location 匹配到的前缀」替换成这个 URI，剩下的部分拼在后面；没有 URI（只有 http://upstream），就把原始请求 URI 原样传过去。

locationproxy_pass请求 /api/v1/users 转发成
/api/http://backend/api/v1/users（原样，最不容易错）
/api/http://backend//v1/users（前缀被替换成 /）
/api/http://backend/v2//v2/v1/users（前缀被替换成 /v2/）
/apihttp://backend//v1/users，而且 /apix 也会被匹配成 /x
~ ^/api/(.*)$http://backend/$1正则 location 里带 URI 会直接报配置错误，只能用变量拼

正则 location 里写 proxy_pass http://backend/; 是启动就失败的，报错大意是「正则 location、命名 location、if 块、limit_except 里不允许 proxy_pass 带 URI」。想改写路径就在正则里捕获，用变量拼出来，但要注意一旦 proxy_pass 里出现变量，Nginx 就不再用 upstream 块，而是走 resolver 动态解析，行为和性能都不一样。

顺着这条线，面试官一定会追问 upstream 的 keepalive。默认情况下 Nginx 到上游用的是 HTTP/1.0 且带 Connection: close，每个请求建一条连接，高 QPS 下上游机器上会堆满 TIME_WAIT。要复用必须三件套一起配：upstream 里写 keepalive 32，location 里写 proxy_http_version 1.1，再把 Connection 头置空。少一条都不生效，这是「配了没用」的典型。

# 前缀替换：/api/ 之后的内容拼到 / 后面
location /api/ {
    proxy_pass http://backend/;          # 注意这个斜杠
    proxy_http_version 1.1;
    proxy_set_header Connection "";     # 复用上游连接的关键
    proxy_set_header Host $host;
}

upstream backend {
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;
    keepalive 32;                        # 每个 worker 保持的空闲连接数
}

# 验证：直接打后端，看它眼里的路径到底是什么
curl -s http://10.0.0.21:8080/api/v1/users -o /dev/null -w '%{http_code}\n'
curl -sI https://example.com/api/v1/users | grep -i '^location'
上游返回重定向时还有一层。后端返回 Location: http://10.0.0.21:8080/login，客户端拿到这个内网地址是打不开的。proxy_redirect 负责改写它，默认值 default 会按 location 和 proxy_pass 推导；路径一改，推导就错，所以要么显式写替换规则，要么确认不需要就直接 off。这个点在「登录后跳转到了内网 IP」的故障里出场率极高。

面试怎么答：「proxy_pass 只看有没有 URI：没有 URI 就原样透传，有 URI 就把 location 前缀替换掉。所以 /api/ 配 http://backend/ 会让后端少一层前缀。上游要复用连接得同时配 keepalive、HTTP/1.1 和清空 Connection 头，少一个都退化成短连接。」

模块 5

真实客户端 IP：$remote_addr 一定不是你以为的那个人

风控说「这批请求全来自同一个 IP」，你一看日志，确实是同一个，于是把那个 IP 封了。五分钟后客服炸了——被封的是你们自己的四层负载均衡，全站用户都变成了这一个 IP。

原因很直接：$remote_addr 是 TCP 连接对端的地址，不是用户的地址。请求经过 SLB、CDN、Ingress 之后，对端永远是最近的那一跳。用户真实 IP 藏在 X-Forwarded-For 里，而这个头是追加的：每经过一个代理，代理把自己的对端地址加到末尾，所以它是一条链，不是单个值。

变量/头含义能不能直接用
$remote_addrTCP 对端地址，realip 模块生效后会被替换没配 realip 时，它就是上一跳代理
$http_x_forwarded_for客户端送来的 XFF 原值，一条逗号分隔的链不能，客户端可以随便伪造
$proxy_add_x_forwarded_for原 XFF 加上 $remote_addr转发给上游时用这个，是标准做法
X-Real-IP单值，通常是第一跳代理写入的只在整条链路都约定用它时可信
$realip_remote_addrrealip 改写之前的原始对端地址排查「到底是谁连进来的」时有用

正确做法是 realip 模块 + 白名单：用 set_real_ip_from 声明「只有这些网段发来的 XFF 我才信」，再用 real_ip_header 指定取哪个头。real_ip_recursive on 表示从右往左跳过所有可信地址，取第一个不可信的作为客户端 IP。多层代理时不开递归，取到的是倒数第二跳。

这里有个安全边界必须说清：如果 Nginx 直接暴露在公网，又无条件相信 XFF，任何人都能伪造 IP。限流按 IP 做、审计日志按 IP 记、后台白名单按 IP 放行，全都可被绕过。所以 set_real_ip_from 里只能写自己的负载均衡网段，不能写 0.0.0.0/0。

还有一个时序细节值得知道：realip 在请求处理的早期阶段执行，早于 limit_req 和 limit_conn。所以只要 realip 配对，限流 key 用 $binary_remote_addr 拿到的就是真实 IP；反过来，realip 没配，你的按 IP 限流实际上是在按「上一跳代理」限流，等于给全站设了一个总闸。

# 只信任自己的 LB 网段，递归取最左侧的不可信地址
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 172.16.0.0/12;
real_ip_header X-Forwarded-For;
real_ip_recursive on;

# 日志里同时打两个，排查时能立刻看出有没有被改写
log_format main '$remote_addr [$time_local] "$request" $status '
                'real=$realip_remote_addr xff="$http_x_forwarded_for" '
                'urt=$upstream_response_time rt=$request_time';

# 验证：伪造一个 XFF，看服务端认不认
curl -s -H 'X-Forwarded-For: 1.2.3.4' https://example.com/whoami

# 注意：请求如果直连 Nginx（不经过可信代理），XFF 应该被忽略
「把 XFF 第一个值当客户端 IP」是另一个常见错误。第一个值恰恰是客户端自己可以随便写的那一段。正确的是从右往左，跳过你信任的代理，取第一个不在白名单里的地址——这也正是 real_ip_recursive on 做的事。自己写脚本解析 XFF 时，顺序搞反等于把伪造权交给了攻击者。

面试怎么答：「$remote_addr 是 TCP 对端，过代理后就是上一跳。真实 IP 要从 XFF 里取，但不能无条件信：必须用 set_real_ip_from 限定可信代理，开 real_ip_recursive 从右往左取第一个不可信地址。realip 在 limit_req 之前执行，所以配对之后按 IP 限流才是按真实用户限流。」

模块 6

超时三兄弟：read_timeout 不是「总时长」

「接口 30 秒就断了，我把 proxy_read_timeout 从 60 调到 300，还是 30 秒断。」这句话里有两个误会：断它的可能根本不是 Nginx，而 proxy_read_timeout 管的也不是「一个请求最多花多久」。

三个 proxy 超时各管一段：connect 是跟上游建 TCP 连接的时间；send 是往上游写请求时，两次写操作之间的最大间隔；read 是从上游读响应时，两次读操作之间的最大间隔。三个都是「两次 I/O 之间」的间隔，不是整个请求的墙钟时间。所以一个持续慢慢吐数据的接口，总耗时可以远超 read_timeout 而不断开——因为每次读之间都没超。

指令管的是超时后的现象
proxy_connect_timeout与上游建立连接502，日志 connect() failed 或 timeout
proxy_send_timeout向上游发送请求的两次写之间502，日志 upstream timed out while sending request
proxy_read_timeout从上游读响应的两次读之间504，日志 upstream timed out while reading response header
client_header_timeout读完客户端请求头408，慢速攻击的防线之一
client_body_timeout读客户端请求体的两次读之间408，大文件上传慢会撞上
send_timeout向客户端发响应的两次写之间连接被关，客户端看到空响应
keepalive_timeout客户端空闲连接保留多久不是错误，是复用窗口

那「30 秒断」是谁干的？按可能性排：客户端自己的超时（最常见，SDK 默认 30 秒）、上游应用服务器的处理超时、四层负载均衡的空闲超时，排在末位的才是 Nginx。判断方法很简单：看 Nginx 日志里有没有对应的 504，没有就说明请求根本没在 Nginx 这一层超时，是客户端先走了。

缓冲是这条线上的另一半。proxy_buffering 默认开着：Nginx 尽快把上游的响应读进内存缓冲区（默认 proxy_buffers 8 4k/8k），读完就释放上游连接，然后按客户端的消费速度慢慢发。这样做的好处是慢客户端不会拖住上游；坏处是响应头超过 proxy_buffer_size 时直接 502，日志写 upstream sent too big header——大 Cookie、超长 JWT 就是典型肇事者。

有些场景必须关缓冲：SSE、WebSocket 之外的流式输出、大文件下载、需要实时看到进度的接口。关了之后上游连接会被客户端速度绑住，一个慢用户就占一个上游连接，并发容量要重新算。

# 普通 API：开缓冲，超时按上游 P99 留 2~3 倍余量
location /api/ {
    proxy_pass http://backend;
    proxy_connect_timeout 3s;
    proxy_send_timeout 10s;
    proxy_read_timeout 30s;
    proxy_buffering on;
    proxy_buffer_size 8k;          # 响应头，大 Cookie 场景要调
    proxy_buffers 16 8k;
}

# 流式接口：关缓冲，并且禁止 Nginx 攒包
location /api/stream {
    proxy_pass http://backend;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;      # 长连接按业务定
}

# 大文件上传：先落盘再转发，避免占满上游连接
client_max_body_size 200m;
proxy_request_buffering off;
别用调大超时来「解决」超时。504 说明上游在给定时间内没吐出数据，把它从 30 秒调到 300 秒，只是让用户多等 270 秒再看到错误，同时把 worker 连接多占 270 秒。正确顺序是：先看上游为什么慢（慢查询、锁、下游依赖），再决定这个接口该不该同步等这么久。

面试怎么答：「proxy 的三个超时都是两次 I/O 之间的间隔，不是请求总时长。read_timeout 超了是 504，connect 超了是 502。缓冲默认开着，能保护上游不被慢客户端拖住，但响应头超过 proxy_buffer_size 会 502，流式接口要显式关掉。」

模块 7

502 / 504 / 499 / 413：谁产生的，去谁的日志里找

「502 是什么原因」——这个问题如果没有限定条件，答案有十几种。但面试官想听的不是清单，是你按什么顺序把清单缩短。第一刀永远是把状态码和「谁产生的」对上。

关键认知：502 和 504 是 Nginx 代表上游写给客户端的，它说明「我跟上游之间出了问题」，而不是「Nginx 自己出了问题」。499 反过来，是客户端在 Nginx 发出响应之前就关了连接，Nginx 自己记的一个内部状态码。413 是 Nginx 直接拒的，请求根本没出去。

状态码谁产生日志里的关键字先查什么
502Nginx（代上游）connect() failed (111: Connection refused)上游端口没监听、进程挂了、端口配错、只监听了 127.0.0.1
502Nginx（代上游）no live upstreams所有后端都被 max_fails 摘了，或健康检查全失败
502Nginx（代上游）upstream prematurely closed connection上游处理到一半自己断了：崩溃、OOM、超时主动 close
502Nginx（代上游）upstream sent too big header响应头超过 proxy_buffer_size，调大缓冲而不是查上游
504Nginx（代上游）upstream timed out上游慢：数据库、下游依赖、GC、线程池排队
499Nginx 自己记请求行 + 499，通常带很长的 request_time客户端先超时断开。查客户端超时设置和后端真实耗时
413Nginx 直接拒client intended to send too large bodyclient_max_body_size 默认 1m，上传接口必须调
400 / 494Nginx 直接拒request header too largeCookie 太大、请求行太长，调 large_client_header_buffers

502 里最容易被误判的是 Connection refused 和 timeout 的区别。前者说明包到了对端、对端回了 RST，也就是「这台机器活着，但这个端口没人听」——去查进程和端口。后者说明包发出去没有任何回应，通常是防火墙 DROP、路由不通、或者全连接队列满了把 SYN 丢了。一个 RST 一个静默，排查方向完全不同。

还有一层重试逻辑要知道：proxy_next_upstream 默认只对 error 和 timeout 重试，不包括 502。所以「上游返回 502 时自动换一台」这个需求，必须显式加上 http_502。但要注意，非幂等请求（POST 下单、支付）重试会造成重复提交，这个开关不能无脑开。

# 日志里按 upstream 状态聚合，比看状态码有用得多
awk '{print $9, $10}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head

# 只看 502/504 的 upstream 那一行
grep -E ' (502|504) ' /var/log/nginx/access.log | \
  grep -o 'upstream=[^,]*' | sort | uniq -c | sort -rn

# 关键字段：上游状态、上游耗时、总耗时
log_format up '$remote_addr "$request" $status ua=$upstream_addr '
              'us=$upstream_status ut=$upstream_response_time rt=$request_time';

# 对比：request_time 远大于 upstream_response_time，说明慢在 Nginx 或客户端
连不上
refused、timeout、no live upstreams。先确认端口、进程、网络策略，这一步还轮不到看应用日志。
连上了又断
prematurely closed。上游崩溃、被 OOM、或者自己超时关了连接，去查上游的退出记录和错误日志。
回了但读不下
too big header。响应头超过缓冲区，调 proxy_buffer_size，跟上游代码没关系。

看 request_time 和 upstream_response_time 的差值，是定位「慢在谁身上」最快的办法。差值大，说明时间花在等客户端收数据、或者卡在 Nginx 的缓冲区；差值接近，说明时间全在上游，直接去查应用和数据库。

面试怎么答：「502 和 504 都是 Nginx 代上游写的，说明 Nginx 到上游这一段有问题，不是 Nginx 自身。502 看日志关键字分三类：连接被拒是端口没监听，no live upstreams 是全被摘了，响应头过大是缓冲区太小。504 是上游慢，499 是客户端先断。Nginx 的日志里 upstream 那一行基本能直接给出答案。」

模块 8

限流：limit_req 是速率，limit_conn 是并发

「我们配了限流，怎么还是被打挂了？」一看配置：limit_req zone=api burst=1000 nodelay。burst 给了 1000 又加了 nodelay，等于允许瞬时 1000 个请求全部放行——这不是限流，是把闸门焊死在全开位置。

两个模块管的事完全不同。limit_req 用漏桶控制速率，单位是每秒（或每分钟）请求数；limit_conn 控制同时存在的连接数。前者防「一瞬间来太多」，后者防「一个客户端占着不放」——比如慢接口、大文件下载、被恶意保持的长连接。

参数作用写错的后果
zone=name:10m共享内存区，存每个 key 的状态太小会频繁淘汰，限流不准；能存多少 key 取决于实现，以官方文档为准
rate=10r/s每个 key 的平均速率写成 10r/m 就是每 6 秒一个，容易被误读
burst=20允许排队的突发量不给 burst，超出速率的请求直接 503，抖动很大
nodelayburst 内的请求立即处理，不排队延迟配大 burst + nodelay 等于没限流
delay=8burst 里前 8 个延迟处理，其余立即需要较新版本支持，老版本不认这个参数
limit_conn addr 10单 key 最大并发连接和速率是两回事，只配一个挡不住另一类攻击
limit_req_status被限流时返回什么码默认 503，会被算进 5xx 告警，建议改成 429 单独统计

选 key 比调参数更重要。按 $binary_remote_addr 限流，在 NAT 和移动网络下会把一整栋楼、一整个运营商出口的用户算成一个人；按 $http_x_api_key 或用户 ID 限流更公平，但需要网关层先做完认证。真实系统里通常两层都做：入口按 IP 挡扫描，业务按租户限速。

还有一个架构层面的事实：Nginx 的限流是单机的。10 个副本、每台限 100 r/s，实际总放行是 1000 r/s。要精确的全局限流，得把计数放到 Redis 或者服务网格层，代价是多一次网络往返。面试里能主动说出「单机限流乘以副本数」这个乘法效应，比背参数名有价值得多。

# 定义区必须在 http 块里，只能定义一次
limit_req_zone  $binary_remote_addr zone=perip:10m rate=20r/s;
limit_conn_zone $binary_remote_addr zone=connip:10m;

server {
    location /api/ {
        limit_req zone=perip burst=40 nodelay;
        limit_req_status 429;              # 别混进 5xx 告警
        limit_conn connip 20;
        limit_conn_status 429;
        proxy_pass http://backend;
    }

    # 登录接口单独一个更严的桶
    location = /api/login {
        limit_req zone=perip burst=5;
        proxy_pass http://backend;
    }
}

# 验证：并发 50 个请求打 5 次，看 429 的比例
seq 50 | xargs -P50 -I{} curl -s -o /dev/null -w '%{http_code}\n' https://example.com/api/login
grep -c ' 429 ' /var/log/nginx/access.log
限流要配「可观测」。至少要知道三个数：被限流的请求数、被限流的 key 的分布、限流前后的上游 QPS。只配不限流等于没配，配了不观测等于不知道闸门在哪。生产上建议把 429 单独打一个日志文件或者单独一个指标，别和真正的错误混在一起。

面试怎么答：「limit_req 控速率、limit_conn 控并发，两个都要配。burst 是排队空间，nodelay 是让 burst 内的请求不延迟直接过，两个一起放大就等于没限流。key 的选择决定公平性，按 IP 在 NAT 下会误伤。还有 Nginx 限流是单机的，多副本时总阈值要乘以副本数。」

模块 9

静态资源：root 与 alias 差一个斜杠，缓存头差一个数量级

「图片 404，路径明明存在。」打开配置：location /static/ { alias /data/www/static; }。文件在 /data/www/static/logo.png，请求是 /static/logo.png，按理说该命中——但 alias 把 location 前缀替换成指定路径时，拼接结果变成了 /data/www/staticlogo.png。

规则是：alias 的路径结尾斜杠要和 location 的结尾斜杠对齐。location /static/ 配 alias /data/www/static/，替换后才拼得对。而 root 的语义完全不同：它不替换前缀，而是把完整 URI 拼在 root 后面，所以 root /data/www 加请求 /static/logo.png 得到 /data/www/static/logo.png，天然对齐。

写法请求 /static/a.png 对应的文件适用
root /data/www;/data/www/static/a.png目录结构和 URI 一致，首选
alias /data/www/;（location /static/）/data/www/a.pngURI 和磁盘目录不一致，比如映射到版本目录
alias /data/www;（location /static/）/data/wwwa.png错的，少一个斜杠就拼错
try_files $uri $uri/ /index.html;依次尝试，最后回落单页应用的前端路由

性能上有三个开关要一起看：sendfile on 让文件数据不经过用户态；tcp_nopush on 把响应头和文件开头合并成一个包发；tcp_nodelay on 在 keepalive 连接上禁用 Nagle，降低小包延迟。前两个是吞吐，第三个是延迟，它们不冲突。

缓存头是另一个高频考点。做法是按文件名分两类：带内容哈希的静态资源（app.3f9a2c.js）可以设一年 immutable，因为内容变了文件名就变了；入口 HTML 必须短缓存甚至 no-cache，否则用户会一直拿到旧版本引用旧资源。搞反的后果是「发布后用户白屏，强刷才好」。

gzip 的默认值也要记清：gzip 默认是 off，开了之后 gzip_types 默认只压 text/html，CSS 和 JS 不加进列表就不会被压。压缩级别 1 到 2 的性价比最高，往 9 调 CPU 涨得很快而体积降得很少。已经压过的格式（jpg、png、mp4、woff2）不要再压，白烧 CPU。

# 带哈希的静态资源：长缓存 + immutable
location ^~ /assets/ {
    root /data/www;
    expires 1y;
    add_header Cache-Control "public, max-age=31536000, immutable";
    access_log off;
}

# 入口 HTML：必须回源验证，不能长缓存
location = /index.html {
    root /data/www;
    add_header Cache-Control "no-cache";
}

# 单页应用路由回落（注意别把 /api 也吞了）
location / {
    try_files $uri $uri/ /index.html;
}

gzip on;
gzip_comp_level 2;
gzip_min_length 1024;
gzip_vary on;
gzip_types text/css application/javascript application/json image/svg+xml;

# 验证响应头，别靠猜
curl -sI https://example.com/assets/app.3f9a2c.js | grep -Ei 'cache-control|content-encoding|expires'
gzip 和流式接口是冲突的。压缩需要攒数据才能出效果，而 SSE 要求每条消息立刻到达。给 text/event-stream 开了 gzip，轻则消息延迟，重则整个连接卡住不吐数据。流式接口的 location 里应该显式 gzip off，同时 proxy_buffering off。

面试怎么答：「root 是把完整 URI 拼在 root 后面，alias 是把 location 前缀替换掉，所以 alias 两边的尾斜杠必须对齐。缓存策略按文件名分：带哈希的长缓存加 immutable，入口 HTML 用 no-cache。gzip 默认关，gzip_types 默认只压 html，这两点最容易被忽略。」

模块 10

十个坑：每一个都能让线上多一次故障

下面这些不是「配置写错一个字母」那种错，是判断方向错。它们的共同点是：看起来很有道理，改完当时也「好像好了」，但根因还在，下一次流量高峰照样复发。

1
以为 location 按从上到下的顺序匹配
普通前缀比的是长度，正则比的是书写顺序，而且正则优先于普通前缀。真按「从上到下」去推理，加一条规则就可能把另一条挤掉，而且不会有任何报错。
2
proxy_pass 尾斜杠随手写
带 URI 就替换前缀，不带就原样透传。这个差异不会报错，只会让后端收到一个不认识的路径。写完必须用 curl 打一次后端，看它实际收到的 URI。
3
把 proxy_read_timeout 当成请求总超时
它管的是两次读之间的间隔。慢慢吐数据的接口可以跑十分钟不断，而一个卡住不吐的接口 60 秒就 504。想限制总时长得在应用层做，Nginx 没有这个指令。
4
502 就重启 Nginx
502 是 Nginx 转述上游的问题，重启只能清掉连接池，根因一点没动。正确动作是 grep 日志里 upstream 那一行，先分清是 refused、timeout 还是 header too big。
5
不配 set_real_ip_from 就信 XFF
直接暴露的 Nginx 无条件相信 XFF，等于让客户端自己决定「我是谁」。限流、审计、IP 白名单全部可绕过。信任列表里只能写自己的代理网段，绝不能是 0.0.0.0/0。
6
以为 reload 一定平滑
reload 只是不再给旧 worker 派新连接。跑着 WebSocket、SSE、大文件下载的旧 worker 会一直不退出，新旧两套配置同时存在，内存翻倍。要配 worker_shutdown_timeout 兜底。
7
在子层加一条 add_header，把父层全冲掉
数组型指令不合并。子层只要出现一条 add_header，父层的安全头就全部失效。安全头要么全部下沉到每个 server，要么用 include 引入同一份片段。
8
把 worker_connections 当成客户端并发上限
反向代理时一个请求占两条连接，客户端并发大约只有一半；而且还要 worker_rlimit_nofile 撑得住。只调一个数，另一个还是 1024，照样报 too many open files。
9
burst 配很大还加 nodelay
这等于允许瞬时一大波全部通过。想削峰就别用 nodelay，让请求在桶里排队；想低延迟就用小 burst 加 nodelay。两者都想要，用 delay 参数分批。
10
以为 gzip 开了就全都压
gzip_types 默认只有 text/html，CSS、JS、JSON 不加进去不会被压。反过来给图片、视频开压缩是纯浪费 CPU。流式接口还必须显式关掉 gzip，否则消息会被攒住。

面试怎么答：这十个里挑一个讲，别只说「我踩过」。讲法固定三段：当时怎么判断的、错误判断造成了什么后果、后来用什么命令或者什么规则纠正了。第三段才是加分项，它证明你建立了检查机制，而不只是记住了这一次。

自测

六道题

1. 配置里有 location ^~ /static/、location ~* \.(png|jpg)$（写在后面）、location /。请求 /static/logo.png 命中哪一条？
正确答案：^~ /static/。匹配分两轮：先找最长前缀，/static/ 比 / 长；这条前缀带 ^~，于是直接采用，不再检查正则。如果没有 ^~，才会按书写顺序试正则，此时那条 ~* 会赢。
2. location /api/ { proxy_pass http://backend/; }，请求 /api/v1/users，后端收到的路径是？
正确答案：/v1/users。proxy_pass 带了 URI（那个 /），所以把 location 匹配到的前缀 /api/ 替换成 /，剩下的 v1/users 拼上去。写成 http://backend（不带斜杠）才是原样透传。
3. 关于 proxy_read_timeout 60s，下面哪个说法正确？
正确答案：两次读之间。它是 I/O 间隔超时，不是总时长。所以持续慢慢吐数据的接口可以超过 60 秒不断开，而卡住不吐的接口 60 秒就 504。建连是 proxy_connect_timeout，写请求是 proxy_send_timeout。
4. 访问日志里出现大量 499，最合理的判断是？
正确答案：客户端先断。499 是 Nginx 自定义的状态码，含义是「客户端关闭连接时我还没把响应发出去」。它最常见的成因是客户端超时（比如 SDK 默认 30 秒）比后端真实耗时短。看到 499 要同时看 request_time，确认是不是后端慢导致的。
5. 要用 X-Forwarded-For 取真实客户端 IP，哪组配置是安全的？
正确答案：限定可信网段 + 递归。只相信自己的代理发来的 XFF，并用 real_ip_recursive on 从右往左跳过可信地址，取第一个不可信的。信任 0.0.0.0/0 或直接取第一个值，都等于让客户端自己声明身份。
6. 一个反向代理的 Nginx，worker_processes 4、worker_connections 1024，客户端并发大约能到多少？
正确答案：约 2048。上限是 4 × 1024 = 4096 条连接，但反向代理时一个客户端请求要占「客户端到 Nginx」和「Nginx 到上游」两条，所以客户端并发大约减半。另外 worker_rlimit_nofile 必须大于等于 4096，否则 fd 会先耗尽。
