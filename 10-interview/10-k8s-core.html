读之前先答一句：你把一个 Pod 删了，它为什么又回来了？
开始前

三个现场：都像 bug，其实都是设计

刚接触 Kubernetes 的人，前两周一定会遇到下面这三件事，并且都会在心里骂一句「这东西怎么这么怪」。等你想明白它们为什么这样，Kubernetes 的核心就通了：它不是一台替你执行命令的机器，是一个不断把现实拉向期望的循环。

现场直觉判断真实原因
同一个 YAML kubectl apply 两次，第二次输出 unchanged，Pod 也没重启命令没生效，是不是要加 force声明式接口本来就是幂等的：期望状态没变，就没有任何需要调和的动作。这是特性，不是失灵
删掉一个 Pod，几秒后同名的新 Pod 又出现了（名字多了一段随机串）删除权限不够，或者有东西在跟我作对ReplicaSet 控制器发现实际副本数少于期望值，立刻补一个。你删的是 Pod，副本数的期望没变
Service 有 ClusterIP，Pod 也是 Running，从别的 Pod curl 过去超时网络插件坏了，或者 kube-proxy 挂了Service 的 selector 没匹配上任何 Ready 的 Pod，Endpoints 是空的，规则里没有后端，包被丢掉
对象是「意图」
YAML 描述的是你想要什么，不是你执行了什么。系统负责把现实搬到你写的那一页上。
控制器是「循环」
每个控制器盯一类对象，比较期望与实际，然后做差量。它不关心事件从哪来，只关心现在差多少。
apiserver 是「唯一入口」
所有组件都只跟它说话，它是唯一能读写 etcd 的角色。这条约束决定了整个系统的形态。

这一篇按「它解决什么问题 → 谁在干活 → 怎么表达意图 → 具体对象 → 边界与坑」的顺序走。不要把它当成对象清单背，每个对象存在的理由，都是某一个具体的运维问题。想不起理由的时候，回到「如果只有 Docker 会怎样」这个假设上，答案通常就出来了。

一个能贯穿全文的类比：你给管家写了一张便条「冰箱里常备两瓶牛奶」。管家每隔一会儿去看一眼，少了他就去买，多了他就拿走。你不需要每次都说「去买牛奶」——你只需要维护那张便条。便条是对象，管家是控制器，看一眼再动手是 reconcile。

面试落点：「Kubernetes 的核心是声明式 API 加控制循环。我写的是期望状态，控制器不断比较实际状态并做差量，所以我删掉 Pod 它会补回来，我重复 apply 也不会产生副作用。所有的排障，本质是看期望和实际在哪一层对不上。」

模块 1

它解决的问题：Docker 答不上的五个问题

「有 Docker 了，为什么还要 Kubernetes？」这题答「为了集群管理」太笼统。真正的答案是五个具体问题，每一个都能让只靠 Docker 的方案在上生产时卡住。

问题只有 Docker 时Kubernetes 的答案
调度你得自己决定这台机器还剩多少 CPU、该放到哪台scheduler 按 requests、亲和性、污点做筛选和打分，自动选节点
自愈容器挂了要有人或脚本去拉，机器挂了要人工迁移控制器维持副本数，节点失联后 Pod 会被重新调度
服务发现容器 IP 会变，你得自己维护一份地址表Service 给一组 Pod 一个稳定虚拟 IP，CoreDNS 提供名字
发布与回滚自己写脚本摘流量、起新容器、观察、回退Deployment 的滚动更新和 revision 回滚是内置能力
期望状态命令式：执行了什么就是什么，失败就是失败声明式：写下目标，系统持续收敛，中间失败了会重试

这五条里，最容易被低估的是第五条。前四条都能用脚本堆出来，第五条改变的是运维的心智模型：你不再关心「这一步有没有成功」，只关心「现在离目标还差多少」。这个转变带来的直接好处是，任何一次误操作都可以通过重新 apply 修正，而不需要知道系统当前处于哪个中间态。

代价也要说清楚，否则答案会显得只会夸：声明式系统更难调试。命令式脚本失败时，你看的是那一行命令的返回；声明式系统失败时，你要判断是哪个控制器没动作、为什么没动作、它看到的世界和你看到的是不是同一个。这就是为什么 kubectl describe 和 Events 在 K8s 排障里占那么大比重——它们是控制器「看到的现实」的出口。

Kubernetes 不是「更好的 Docker」。它不管镜像怎么构建，也不管单机上的容器怎么跑。它管的是「一群机器上，一组进程应该长什么样」。把这两个层次混在一起答，后面问「Pod 和容器什么关系」就一定答不清。

面试落点：「K8s 解决的是调度、自愈、服务发现、发布回滚和期望状态这五件事。前四件是用脚本也能勉强做的，第五件是范式变化：从『执行步骤』变成『维护目标』。代价是排障变复杂，因为你得判断是哪个控制器没把现实拉过去。」

模块 2

组件职责：谁跟 etcd 说话，谁跟容器说话

「K8s 有哪些组件」是送分题，但紧接着的「apiserver 挂了会怎样」「kubelet 挂了会怎样」是分水岭。答得出来，说明你理解的是数据流，不是名单。

组件位置职责挂了会怎样
kube-apiserver控制面唯一的 API 入口，做认证、鉴权、准入控制、校验，然后读写 etcd控制面瘫痪：不能查、不能改，但已运行的 Pod 继续跑
etcd控制面唯一的事实存储，强一致 KV，保存全部对象等同于失忆，apiserver 无法工作
kube-scheduler控制面给未绑定的 Pod 选节点：先过滤（资源、亲和、污点），再打分新 Pod 一直 Pending，已有 Pod 不受影响
kube-controller-manager控制面跑一堆控制器：Deployment、ReplicaSet、Node、Endpoints、Job、ServiceAccount…副本不再补齐，滚动更新停住，Endpoints 不更新
cloud-controller-manager控制面对接云厂商：负载均衡器、节点生命周期、路由LoadBalancer 类型的 Service 拿不到外部 IP
kubelet节点节点代理，watch 分给自己的 Pod，通过 CRI 调运行时，报状态、跑探针该节点上的 Pod 状态不再更新，最终被判失联并迁移
kube-proxy节点把 Service 的规则变成 iptables/IPVS 规则，做转发本节点的 Service 访问异常，ClusterIP 不通
容器运行时节点containerd / CRI-O，真正创建和运行容器（通过 CRI 接口）Pod 起不来，kubelet 报 runtime 相关错误
CoreDNS集群插件集群内 DNS，把 Service 名解析成 ClusterIP服务名解析失败，但用 IP 仍然通

有一条架构约束值得单独记：只有 apiserver 读写 etcd。scheduler、controller-manager、kubelet 全部通过 apiserver 的 watch 接口感知变化，谁都不直连 etcd。这条约束让 etcd 的访问可以被统一鉴权和审计，也让整个系统的耦合点只有一个。

另一点常被忽略：kubelet 不是「被 apiserver 指挥」的。它是主动 watch「绑定到本节点的 Pod」，然后自己决定怎么实现。apiserver 不发起连接，是 kubelet 连出去。所以 apiserver 短暂不可用时，已经调度好的 Pod 照常运行，kubelet 只是没法上报状态。

# 控制面组件在 kube-system 里（kubeadm 部署的形态）
kubectl -n kube-system get pod -o wide
kubectl -n kube-system get pod -l component=kube-apiserver

# 看某个对象被哪些控制器动过（ownerReferences 是链）
kubectl get pod web-6d4b9c7f5-x2k9p -o jsonpath='{.metadata.ownerReferences}'

# 节点的实际状态与容量，来自 kubelet 上报
kubectl describe node node-1 | sed -n '/Capacity/,/Events/p'

# apiserver 的健康探针（三个端点含义不同）
kubectl get --raw='/healthz?verbose' | head

排障时这个表非常实用：现象是「新 Pod 一直 Pending」→ 看 scheduler；「副本数不齐、Deployment 不动」→ 看 controller-manager；「Pod 起来但状态一直 ContainerCreating」→ 看 kubelet 和运行时；「服务名解析不了、IP 能通」→ 看 CoreDNS；「Service 完全不通」→ 看 kube-proxy 和 Endpoints。每一条都指向一个具体组件，而不是「集群坏了」。

一个常被追问的细节：kube-proxy 不是负载均衡器，也不转发流量。它只在节点上写规则，真正转发的是内核的 netfilter/IPVS。所以「kube-proxy 压力大」通常不是因为它处理了多少请求，而是规则数量太多导致同步慢。这个区别在面试里说出来，会显得你不是只背了组件名。
kubectl -n kube-system get pod -o wide一眼看到控制面与插件跑在哪，先确认它们都是 Running
kubectl get pod NAME -o jsonpath='{.metadata.ownerReferences}'这个 Pod 属于谁，顺着 owner 链能追到 Deployment
kubectl describe node NODE容量、已分配 requests、污点与 Conditions，调度问题从这里看
kubectl get events --sort-by=.lastTimestamp按时间排序的事件流，控制器「说了什么」都在这里
kubectl get --raw='/healthz?verbose'apiserver 各依赖的健康状态，判断控制面是否整体可用

面试落点：「apiserver 是唯一入口，也是唯一读写 etcd 的组件；scheduler 只管选节点；controller-manager 跑各种控制器做调和；kubelet 在节点上 watch 分给自己的 Pod，通过 CRI 调运行时；kube-proxy 只写转发规则，不转发流量。apiserver 挂了已运行的 Pod 不受影响，但控制面不能变更。」

模块 3

声明式与 reconcile：为什么 apply 是幂等的

「kubectl create 和 kubectl apply 有什么区别」这题，答「apply 能重复执行」只对了一半。真正的问题是：它凭什么能重复执行？

先把两个词分开。命令式是「做这件事」：创建、删除、扩容。它关心动作，重复执行会报错或者产生副作用。声明式是「要这个状态」：期望三个副本、镜像版本是 v2、端口是 8080。它关心结果，重复执行只要状态没变就是空操作。

维度kubectl createkubectl apply
语义创建对象，对象已存在就报 AlreadyExists把对象调到 YAML 描述的状态，不存在则创建
重复执行失败第二次返回 unchanged，不产生任何变更
怎么算差量不算，只提交客户端用 last-applied 注解做三方合并；服务端用 managedFields
会不会重启 Pod不会（它只创建对象）只有 Pod 模板真的变了才触发滚动更新
适合一次性对象、脚本里明确知道不存在日常管理、GitOps、CI 反复部署

幂等的来源是「比较而不是执行」。apiserver 收到 apply 后，把提交的内容和现有对象合并，如果合并结果和现有对象一致，就什么都不写，返回 unchanged。所以「apply 两次」不会产生两个 Deployment，也不会多出一个 ReplicaSet——因为期望状态没有变化。

这也解释了一个高频误解：apply 不会重启 Pod。很多人改完 YAML 发现 Pod 没重启，以为 apply 没生效。实际上只有 spec.template 变化才会生成新的 ReplicaSet 并滚动替换；改个 label、改个 annotation、加个无关字段，都不会动 Pod。要强制重启，得改模板里的某个字段（常见做法是加一个时间戳注解），而不是指望 apply 有「重跑」的意思。

# 看服务端记录的字段管理者（server-side apply 的痕迹）
kubectl get deploy web -o yaml | sed -n '/managedFields/,/^status/p' | head -30

# 看客户端 apply 留下的 last-applied 注解
kubectl get deploy web -o jsonpath='{.metadata.annotations.kubectl\.kubernetes\.io/last-applied-configuration}' | head -c 400

# 只看会改什么，不真改（排障时非常有用）
kubectl diff -f deploy.yaml

# 服务端 apply（字段所有权更清晰，冲突会明确报错）
kubectl apply --server-side -f deploy.yaml

再说 reconcile 的工作方式。控制器是电平触发（level-triggered）的，不是边沿触发：它不关心「刚才发生了一个删除事件」，而是每隔一段时间（以及每次被事件唤醒时）重新读一遍实际状态，和期望比一次。这个设计的好处是丢事件不会丢状态——即使中间漏了几个事件，下一轮比较照样能发现差异。代价是有一堆无意义的空转，所以控制器会用 informer 缓存和 workqueue 去重来省资源。

并发控制靠 resourceVersion：每次写入都会递增，更新时带上旧值，如果不匹配就报 conflict，让你重新读一遍再改。这是乐观锁，不阻塞读，冲突时重试。理解这一点，才能解释「为什么两个控制器同时改一个对象不会互相覆盖成脏数据」。

「期望状态」和「实际状态」要分清。YAML 里的 spec 是你写的期望；status 是控制器写回的现实。排障时看 status 里的 conditions，往往比看 Events 更直接——因为 conditions 是控制器明确表达的判断，比如 Available、Progressing、Ready。

面试落点：「create 是命令式，对象存在就报错；apply 是声明式，它把提交的内容和现有对象合并，一致就不写，所以幂等。它的幂等来自『比较』而不是『执行』。apply 不会重启 Pod，只有 Pod 模板变了才滚动。控制器是电平触发的，每轮重新比较期望和实际，所以丢事件不会导致状态漂移。」

模块 4

Pod：为什么里面要先跑一个「什么都不干」的容器

进到一个 Pod 的节点上看进程，会发现每个 Pod 都有一个 pause 容器，镜像很小，进程就干一件事：pause() 睡着。它不处理请求、不写日志，但没有它整个 Pod 就不成立。

原因在 namespace 的生命周期上。网络 namespace 需要一个「持有者」：如果 Pod 里第一个容器创建了 netns，它退出时 netns 就会消失，后面的容器就没了网络。所以先起一个永远不退出的 pause 容器，由它创建并持有 netns，其他容器通过 --net=container:pause 加进来。这个 pause 容器也叫 sandbox 容器。

于是 Pod 内的容器共享这些：

  • 网络 namespace：同一个 IP、同一个端口空间，互相可以用 localhost 访问。这是 sidecar 模式的基础。
  • IPC namespace：可以用 System V IPC 和 POSIX 共享内存通信。
  • UTS namespace：共享主机名，Pod 里的 hostname 就是 Pod 名。
  • 卷：同一个 Pod 里声明的 volume 可以挂到多个容器，用来交换文件。

不共享的是 PID namespace（默认各自独立，除非显式开启 shareProcessNamespace）和 mount namespace（各自有自己的根文件系统）。这个细节常被问：「同一个 Pod 里两个容器能看到对方的进程吗？」默认不能。

问题答案
Pod 是最小调度单位还是最小部署单位？都是。scheduler 以 Pod 为单位选节点，一个 Pod 里的容器一定在同一台机器上
一个 Pod 里能不能放两个业务容器？能，但它们会被绑在一起：同生共死、抢同一份资源、共享 IP。不适合放两个独立业务
「一个容器一个 Pod」对吗？作为默认实践是对的。Pod 的意义在于「必须共享网络和卷的进程组」，没有这层需求就别塞一起
Pod 能重启吗？不能。Pod 是重建的（新 UID、新 IP）。容器可以按 restartPolicy 重启，Pod 本身不会
Pod 的 IP 会变吗？会。重建、重新调度都会换 IP，所以不能拿 Pod IP 当稳定地址，要用 Service
# 看 Pod 里到底有几个容器（含 pause，需要看运行时层）
kubectl get pod web-0 -o jsonpath='{.spec.containers[*].name}'
kubectl get pod web-0 -o jsonpath='{.status.podIP} {.status.hostIP}'

# 在节点上能看到 sandbox 容器
crictl pods
crictl ps -p <sandbox-id>

# 进 Pod 的网络命名空间（排查网络时比 exec 更底层）
crictl inspectp <sandbox-id> | grep -i pid
nsenter -t <pid> -n ss -lntp

为什么「不该一个 Pod 塞多个业务容器」？因为它们共享命运和资源：一个 OOM，整个 Pod 可能被驱逐；一个把 CPU 吃满，另一个跟着被限流；滚动更新时一起重建，没法独立发布。sidecar 之所以合理，是因为它服务于主容器（日志采集、代理、证书轮转），生命周期本来就该一致。

不要把 Pod 当成「小虚拟机」来用。有人把应用、数据库、定时任务塞进一个 Pod，图省事。结果扩缩容时三个一起扩，数据库主从乱了；滚动更新时数据库跟着重启；资源限制也没法分别设。Pod 的边界应该是「这些进程必须在一起」，不是「这些进程属于同一个项目」。

面试落点：「Pod 是最小调度单位，里面的容器共享网络、IPC、UTS 和卷，所以能用 localhost 互访。pause 容器的作用是持有网络 namespace，不然第一个容器退出后网络就没了。默认 PID namespace 不共享。一个容器一个 Pod 是常态，多容器只用于必须共享网络和卷的 sidecar 场景。」

模块 5

工作负载对象：六个对象，一条 ownerReference 链

「Deployment 和 StatefulSet 有什么区别」几乎必问。标准答案是「有无状态、有无稳定网络标识」，但更本质的差别是：它们对「一个 Pod 是谁」这件事的定义不同。

对象管什么关键特性什么时候用
Pod一个或一组共享网络/卷的容器最小调度单位，不自我修复几乎不直接创建，除非调试或静态 Pod
ReplicaSet维持 N 个相同的 Pod按 selector 认领 Pod，多退少补几乎不直接用，由 Deployment 管理
Deployment无状态应用的副本与发布滚动更新、revision 回滚、Pod 可互换Web 服务、API 网关、无状态 worker
StatefulSet有状态应用固定序号名、稳定网络标识、每副本独立 PVC、有序启停数据库、消息队列、需要固定身份的集群成员
DaemonSet每个节点一个 Pod节点加入就自动部署，节点移除就回收日志采集、监控 agent、CNI、kube-proxy
Job跑完就结束的任务completions、parallelism、backoffLimit数据迁移、批处理、一次性脚本
CronJob按 cron 表达式跑 JobconcurrencyPolicy、startingDeadlineSeconds、历史保留数定时备份、报表、清理任务

先看这条链：Deployment → ReplicaSet → Pod。Deployment 不直接管 Pod，它管 ReplicaSet；每次 Pod 模板变化，它就创建一个新的 ReplicaSet，然后逐步把副本从旧的挪到新的，这就是滚动更新。旧 ReplicaSet 保留着（副本数归零），所以回滚只是把副本数挪回去，不需要重新构建。revisionHistoryLimit 控制保留多少个旧版本，默认值以你环境的版本为准。

StatefulSet 的差别在于「身份」。它的 Pod 名字是 web-0、web-1，不是随机串；每个 Pod 通过 headless Service（clusterIP: None）拿到一个稳定的 DNS 名，形如 web-0.web.default.svc.cluster.local；每个 Pod 用自己的 PVC（来自 volumeClaimTemplates），重建后还能挂回原来那块盘。默认的 podManagementPolicy 是 OrderedReady，也就是 0 号 Ready 之后才起 1 号，删除时倒序。这就是它能跑有状态集群的原因：成员有名字、有固定地址、有固定存储。

# 看 Deployment 下面的 ReplicaSet 与 Pod 的归属
kubectl get deploy,rs,pod -l app=web
kubectl get rs -o wide

# 回滚到上一个版本（不需要重新构建镜像）
kubectl rollout history deploy/web
kubectl rollout undo deploy/web
kubectl rollout status deploy/web --timeout=120s

# StatefulSet 的稳定 DNS 要配 headless Service
kubectl get svc web-headless -o jsonpath='{.spec.clusterIP}'
kubectl exec web-1 -- nslookup web-0.web-headless.default.svc.cluster.local

# Job 的完成情况与失败重试上限
kubectl get job migrate -o jsonpath='{.spec.backoffLimit} {.status.succeeded}/{.spec.completions}'

DaemonSet 值得单独提一句：它会绕过部分调度限制，因为它的语义是「每个（符合条件的）节点都要有一个」。节点打上污点后，普通 Pod 会被赶走，DaemonSet 的 Pod 往往因为内置的 tolerations 还留着。这也解释了为什么节点 NotReady 时，你还能看到 CNI 和日志 agent 的 Pod 挂在那里。

选型的一句话版本：「Pod 之间可互换、需要滚动发布 → Deployment；Pod 有身份、有独立存储、要按顺序启停 → StatefulSet；每个节点都要一份 → DaemonSet；跑完就结束 → Job；按时间跑 → CronJob。」把这句背熟，选型题就不会错。

面试落点：「Deployment 管无状态副本，通过 ReplicaSet 做版本管理，Pod 可互换；StatefulSet 给每个 Pod 固定序号、稳定 DNS 和独立 PVC，适合有状态集群；DaemonSet 保证每节点一个；Job 和 CronJob 管一次性与定时任务。它们都通过 ownerReference 形成层级，删上层会级联删下层。」

模块 6

Service：ClusterIP 不是一个进程

「ClusterIP 是怎么实现的？」很多人答「kube-proxy 监听了这个 IP」。这是错的。没有任何进程监听 ClusterIP，它是一串内核转发规则，包到了节点就被改写目的地址，直接送到某个 Pod。

Service 的本质是「一组 Pod 的稳定访问入口」。Pod IP 会变，Service 的 ClusterIP 在它生命周期内不变。这个虚拟 IP 不在任何网卡上，ping 它通常不通（因为它只处理特定协议的规则），但 TCP 连接会被 DNAT 到某个后端 Pod。

类型暴露范围实现典型场景
ClusterIP集群内分配一个虚拟 IP，kube-proxy 写 DNAT 规则内部服务互调，默认类型
NodePort集群外，通过任意节点的 IP + 端口在 ClusterIP 基础上，每个节点监听一个高端口并转发测试环境、没有 LB 的自建集群
LoadBalancer集群外，通过云负载均衡云控制器创建 LB，把流量导到 NodePort 或 Pod生产对外服务，需要固定公网入口
ExternalName集群内，解析到外部域名返回一条 CNAME，没有 ClusterIP，也没有后端把外部依赖（如托管数据库）包成集群内名字

NodePort 的端口不是随便填的。默认范围是 30000-32767，由 apiserver 的 --service-node-port-range 决定（以你环境为准）。写一个 8080 上去会被拒，报「provided port is not in the valid range」。这个限制经常让刚从 Docker 转过来的人困惑，因为 Docker 的 -p 8080:80 是想写多少写多少。

# 四种类型的字段差异，一眼能看出来
kubectl get svc web -o jsonpath='{.spec.type} {.spec.clusterIP} {.spec.ports[*].nodePort}'

# 关键：Endpoints 有没有后端。空的就说明 selector 没匹配上
kubectl get endpoints web
kubectl get endpointslice -l kubernetes.io/service-name=web

# 对比 Service 的 selector 和 Pod 的 label
kubectl get svc web -o jsonpath='{.spec.selector}'
kubectl get pod --show-labels

# 从集群内验证：先用名字，再用 ClusterIP，最后直接打 Pod IP
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- sh
# 进去后：nslookup web / wget -qO- web:8080 / wget -qO- <pod-ip>:8080

「Service 访问不通」这个现象，正确的排查顺序是从 Endpoints 往前推，而不是从网络往后查：

看 Endpoints 是否为空。空的话，问题在 selector 或 Pod 的 Ready 状态，跟网络一点关系都没有。这一步能解决大半问题。
看 targetPort 和容器实际监听端口是否一致。Service 的 port 是访问入口，targetPort 才是容器端口，两个都写 8080 但应用监听 8000，就会连不上。
看 Pod 是否 Ready。没 Ready 的 Pod 不会被放进 Endpoints（除非 publishNotReadyAddresses）。所以 readiness 探针配错，表现就是「Pod 明明在跑，Service 就是没后端」。
再看 kube-proxy 和规则。节点上 iptables -t nat -L KUBE-SERVICES -n 或 ipvsadm -Ln，确认规则存在。
最后才查 CNI 和 NetworkPolicy。前面都对还通不了，才怀疑网络插件或策略拦截。
headless Service（clusterIP: None）没有虚拟 IP，DNS 直接返回 Pod IP 列表。它常和 StatefulSet 搭配，给每个 Pod 一个稳定名字。但也意味着客户端要自己做负载均衡和重试——DNS 返回的第一个地址挂了，你得自己换下一个。别把它当成「省了一个 ClusterIP」的优化。

面试落点：「ClusterIP 不是进程，是 kube-proxy 写的内核 DNAT 规则，包到节点就被改写到某个 Pod。四种类型是 ClusterIP、NodePort、LoadBalancer、ExternalName；NodePort 默认 30000-32767。Service 不通先看 Endpoints，空的话是 selector 或 readiness 的问题，不是网络问题。」

模块 7

三种探针：liveness 只该查自己

「liveness 探针检查数据库连接，数据库抖了一下，整个服务被重启了三轮。」这是探针设计里最典型的事故，也是面试里最能体现判断力的一道题。

探针失败后发生什么该查什么不该查什么
liveness重启容器进程自己是否还活着、有没有死锁、事件循环有没有卡住下游依赖、数据库、缓存。这些挂了应该摘流量，不是重启自己
readiness从 Endpoints 摘除，不重启能否处理请求：依赖是否可用、预热是否完成、限流是否处于拒绝态无关的次要功能。它频繁翻转会造成流量抖动
startup成功前禁用另外两个探针；失败则重启慢启动应用（加载大模型、重建索引、JVM 预热）已经很快启动的服务，加了只是多一层配置

为什么 liveness 不能查下游？因为故障会横向放大。数据库慢了 → 所有 Pod 的 liveness 失败 → 全部重启 → 重启中的 Pod 更处理不了请求 → 数据库压力看似下降但请求全失败 → 恢复后又要同时冷启动。一个下游抖动被放大成一次全站故障，这就是「级联重启」。

正确的分工是：liveness 只回答「我这个进程还值得救吗」，readiness 回答「我现在能不能接流量」。数据库不可用时，readiness 失败、流量摘走，等数据库恢复再自动加回来，全程不重启，恢复是秒级的。

# liveness：只查自己，给足容忍次数
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

# readiness：可以查依赖，但要能快速恢复
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
  failureThreshold: 2

# startup：给慢启动留预算，成功后自动让位
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 30        # 最多等 300 秒

参数语义要说准：periodSeconds 默认 10 秒，timeoutSeconds 默认 1 秒，failureThreshold 默认 3，successThreshold 默认 1（liveness 和 startup 只能是 1）。所以默认配置下，一个 liveness 失败要连续 3 次、大约 30 秒才触发重启。很多人以为「探针失败就立刻重启」，于是把参数调得很激进，反而制造了误杀。

startup 探针的预算算法要会：最大等待时间约等于 failureThreshold 乘 periodSeconds。上面的例子是 30 乘 10，等于 300 秒。如果应用最慢要 5 分钟才能起来，这个预算必须大于它，否则会在启动完成前被杀，进入「启动 → 被杀 → 再启动」的死循环，看起来像 CrashLoopBackOff，其实是预算不够。

readiness 探针不要太敏感。它每失败一次就摘一次流量，恢复后又加回来。如果它查的是「数据库连接池是否有空闲连接」这种瞬时指标，就会导致 Pod 在 Endpoints 里反复进出，客户端看到的是间歇性 502。readiness 应该表达「持续不可用」，不是「此刻有点忙」。

面试落点：「liveness 失败重启容器，只能查自己，查下游会导致级联重启；readiness 失败摘流量不重启，可以查依赖；startup 用于慢启动，成功前屏蔽另外两个，预算约等于 failureThreshold 乘 periodSeconds。默认 period 10 秒、failureThreshold 3，所以不是一失败就重启。」

模块 8

requests / limits 与 QoS：调度看 requests，运行看 limits

「requests 和 limits 有什么区别？」这题的关键不是定义，而是它们作用在不同的阶段：requests 影响调度（能不能放到这台机器），limits 影响运行（跑起来最多能用多少）。

字段作用阶段超了会怎样CPU 与内存的差别
requests调度不会被「超」，它是节点分配的依据CPU 是时间片，内存是预留；两者都参与节点可用量计算
limits运行CPU 被 throttle（变慢），内存被 OOMKill（被杀）CPU 可压缩，内存不可压缩，这是最重要的一句话

为什么 CPU 超了只是变慢、内存超了就被杀？因为 CPU 是「按时间分配」的资源，超了就让你的进程少跑几个时间片，请求排队；内存是「按空间占用」的资源，超了没有地方放，只能杀掉一个进程腾地方。理解这一点，就能解释「为什么我的服务 CPU 打满只是变慢，内存涨一点就直接重启」。

QoS 是这三者的组合结果，一共三级：

QoS条件驱逐顺序典型写法
Guaranteed每个容器都设了 CPU 和内存，且 requests 等于 limits最后被驱逐核心服务，资源确定
Burstable设了 requests 或 limits，但不满足 Guaranteed中间，按超出 requests 的程度排序大多数业务服务
BestEffort所有容器都没设 requests 和 limits最先被驱逐临时任务、可中断的批处理

这里有个很容易答错的细节：如果只写 limits 不写 requests，Kubernetes 会把 limits 的值复制给 requests（在没有 LimitRange 兜底的情况下）。所以「只设 limits」看起来是「不占资源、用多少算多少」，实际是「按上限预留」，调度器会认为这个 Pod 要占满那么多，节点很快就放不下了。这个行为经常造成「节点明明很空，Pod 却 Pending」。

# 看 Pod 实际生效的 requests/limits 和 QoS 等级
kubectl get pod web-0 -o jsonpath='{.status.qosClass}{"\n"}'
kubectl get pod web-0 -o jsonpath='{range .spec.containers[*]}{.name}{" req="}{.resources.requests}{" lim="}{.resources.limits}{"\n"}{end}'

# 节点上被 requests 占掉多少（调度依据）
kubectl describe node node-1 | sed -n '/Allocated resources/,/Events/p'

# 看有没有被 CPU 限流（需要指标，容器层面也能看）
kubectl top pod web-0
kubectl exec web-0 -- cat /sys/fs/cgroup/cpu.stat | grep throttled

实际配置的经验值是：requests 按稳态用量给，limits 按峰值给，内存的 limits 不要压得太紧。因为内存不可压缩，limits 给得太小，一次流量尖峰或者一个大查询就 OOMKill，而重启后的冷启动会让下一次尖峰更容易触发，形成循环。CPU 的 limits 可以紧一些，代价只是变慢，不会死。

还有一个常被忽略的：LimitRange 会给没写 resources 的容器塞默认值。所以「我明明没设 requests，为什么 Pod 显示有 100m」——去 kubectl describe limitrange -n <ns> 看。这也解释了为什么两个集群里同样的 YAML，QoS 等级不一样。

面试落点：「requests 决定调度，limits 决定运行时上限。CPU 超限只是被 throttle，内存超限会 OOMKill，因为 CPU 可压缩、内存不可压缩。QoS 分 Guaranteed、Burstable、BestEffort，按这个顺序被驱逐。只设 limits 不设 requests 时，requests 会默认等于 limits，所以调度上等于按上限占资源。」

模块 9

Namespace 与 RBAC：它不是网络隔离

「两个 Namespace 里的 Pod 能互通吗？」能，默认就能，而且不需要任何配置。这是 Namespace 最常被误解的一点：它隔离的是名字和权限，不是网络。

Namespace 干三件事：给对象名加作用域（两个 ns 里可以各有一个叫 web 的 Deployment）、给 RBAC 划边界（这个用户只能改 dev 里的东西）、给配额划边界（ResourceQuota 按 ns 限制总量）。它不干的事：网络隔离（要靠 NetworkPolicy）、节点隔离（要靠亲和性和污点）、运行时隔离（同一个 ns 的 Pod 可能跑在不同节点上）。

# 配额与默认值：这两个对象经常成对出现
kubectl get resourcequota -n dev
kubectl describe resourcequota -n dev
kubectl get limitrange -n dev -o yaml | sed -n '/default/,/type/p'

# RBAC 四要素：谁能（subject）对什么（resource）做什么（verb）
kubectl get role,rolebinding -n dev
kubectl describe rolebinding dev-reader -n dev

# 最实用的鉴权命令：以某个 ServiceAccount 的身份试一下
kubectl auth can-i list pods -n dev --as=system:serviceaccount:dev:app
kubectl auth can-i delete nodes --as=system:serviceaccount:dev:app

RBAC 的结构其实只有四个词：Subject（User / Group / ServiceAccount）、Verb（get、list、watch、create、update、patch、delete）、Resource（pods、deployments…）、Scope（Role 在命名空间内，ClusterRole 是集群级）。绑定关系是 RoleBinding 把 Role 授给 Subject；RoleBinding 也可以引用 ClusterRole，但权限仍然只在该命名空间内生效。这个「ClusterRole + RoleBinding = 命名空间内的集群角色权限」是常考细节。

ServiceAccount 是给 Pod 用的身份。默认情况下，Pod 会自动挂载一个 token，应用可以用它访问 apiserver。这带来两个实践建议：不需要访问 apiserver 的 Pod，把 automountServiceAccountToken 设为 false；每个应用用自己的 SA，不要共用 default，更不要给它 cluster-admin。较新版本的 token 是投射卷、有有效期、绑定 audience 的，不再是永久有效的静态 secret——这一点如果还按老版本答，会显得知识没更新。

NetworkPolicy 只有在 CNI 支持时才生效。你把 YAML 写上去了，kubectl apply 也成功了，但如果网络插件不实现它，就是一张废纸——没有任何报错。判断方法：看 CNI 文档，或者起两个 Pod 实测一次「本该被拒绝」的流量是不是真的被拒。这类「配置成功但没生效」的问题，比配置失败更难发现。

面试落点：「Namespace 隔离名字、RBAC 和配额，不隔离网络，跨 ns 的 Pod 默认可通，要隔离得上 NetworkPolicy，而且得 CNI 支持。RBAC 是 subject、verb、resource 加作用域四要素，RoleBinding 引用 ClusterRole 时权限仍限于该命名空间。Pod 用 ServiceAccount 拿身份，不需要访问 apiserver 就该关掉 token 自动挂载。」

模块 10

9 个坑：面试里最容易被追到哑口的地方

这些不是「不知道」，是「知道一半」。Kubernetes 的追问特别喜欢停在边界上：你说得出概念，他就问「那这种情况下会怎样」。

1
说 Pod 会被「重启」
Pod 不会重启，只会被重建：新 UID、新 IP、新容器。容器可以按 restartPolicy 重启，Pod 这一层没有重启的概念。这个区别决定了「重启后 IP 变了」这类现象能不能解释。
2
以为 ClusterIP 上有进程在监听
它是 kube-proxy 写进内核的 DNAT 规则，不是 socket。所以 ping 不通是正常的，ss 也看不到监听。真正转发的是 netfilter/IPVS。
3
Service 不通先去查网络插件
先看 Endpoints 是不是空的。selector 写错、Pod 没 Ready、targetPort 不匹配，都会让 Endpoints 为空，这时候网络再正常也没用。
4
liveness 探针里查数据库
数据库抖动会让所有副本同时重启，把一次下游故障放大成全站故障。liveness 只查自己，依赖状态交给 readiness。
5
只写 limits 不写 requests
K8s 会把 limits 复制成 requests，调度器按上限预留。结果节点看着很空，Pod 却一直 Pending。requests 要按稳态给，limits 按峰值给。
6
把 Namespace 当网络隔离
跨 Namespace 的 Pod 默认可通。要隔离必须用 NetworkPolicy，而且依赖 CNI 实现，不支持的插件会静默忽略。
7
以为 apply 会重启 Pod
只有 spec.template 变了才滚动更新。改 label、改注解、改无关字段都不会动 Pod。要强制重启得改模板内容。
8
NodePort 随便写端口
默认只能用 30000-32767，范围由 apiserver 的 --service-node-port-range 决定。写 8080 会直接被拒，这不是权限问题，是范围问题。
9
把 limits 当成「保证」
limits 是上限，不是保证。节点资源紧张时，Burstable 和 BestEffort 会被驱逐，Guaranteed 只是最后被驱逐，也不是绝对不被驱逐。要稳定就多留余量、做好 PDB。

面试落点：这九条里，选一条你能讲出场景的。比如「我们一开始把数据库连接检查写进 liveness，结果 MySQL 主从切换时整个服务被重启了两轮，后来改成 readiness 查依赖、liveness 只查本地健康，切换时只是短暂摘流量」——有因果、有动作、有结果，比背九条坑有用。

自测

六道题

1. 用 kubectl delete pod 删掉一个由 Deployment 管理的 Pod，几秒后出现了一个新 Pod。原因是？
正确答案：ReplicaSet 补副本。Deployment 管 ReplicaSet，ReplicaSet 的期望副本数是 3 就维持 3 个。你删掉一个，实际变 2，控制器下一轮比较就创建一个新的。新 Pod 是新对象（新 UID、新 IP），不是「原来那个重启」。要真的减少副本，得改 replicas 或删上层对象。
2. Service 有 ClusterIP，后端 Pod 是 Running，但从其他 Pod 访问持续超时。kubectl get endpoints web 显示 <none>。最可能的原因是？
正确答案：selector 或 Ready 状态。Endpoints 为空说明 Endpoints 控制器没有找到符合条件的 Pod，常见原因是 selector 写错、Pod 的 label 不符，或者 Pod 存在但没有通过 readiness 探针（未 Ready 的 Pod 不会进 Endpoints）。这一步和网络无关，先修 selector 或探针。
3. 某服务的 liveness 探针里检查了数据库连接。数据库主从切换期间连接全部失败，最可能发生什么？
正确答案：级联重启。liveness 失败的动作就是重启容器，而它不区分「我自己坏了」还是「下游坏了」。所有副本同时因为同一个下游失败而重启，就是级联故障。正确做法是 liveness 只查进程自身，依赖状态放到 readiness，失败时只摘流量。
4. 一个 Pod 要被判定为 Guaranteed QoS，需要满足什么条件？
正确答案：requests 等于 limits。Guaranteed 要求 Pod 里每个容器都同时设置 CPU 和内存的 requests 与 limits，并且数值完全相等。少一个容器、少一种资源、或者数值不等，都会落到 Burstable。qosClass 是系统计算后写入 status 的，不能手动指定。
5. 一个应用启动需要 4 分钟，配置了 startupProbe，periodSeconds 10、failureThreshold 3。会发生什么？
正确答案：预算不足。startupProbe 的最大等待时间约等于 failureThreshold 乘 periodSeconds，这里是 3 乘 10 等于 30 秒。应用要 4 分钟才起来，会在第 30 秒被判失败并重启，看起来像 CrashLoopBackOff，实际是预算配小了。应该把 failureThreshold 提到 30 左右，留足 300 秒。
6. 关于控制面组件，下面哪个说法是正确的？
正确答案：apiserver 是唯一入口。etcd 只由 apiserver 访问，scheduler、controller-manager、kubelet 都通过 apiserver 的 API 和 watch 工作。scheduler 只负责选节点（bind），创建容器的是 kubelet 通过 CRI 调运行时；kube-proxy 只写 iptables/IPVS 规则，不转发流量。
