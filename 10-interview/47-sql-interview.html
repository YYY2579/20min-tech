SQL 面试 30 题：从慢查询到窗口函数

运维岗不写业务 SQL，但出报表、查数据、定位慢查询全靠它。

覆盖 8 大模块 30 道题 34 段可跑 SQL 10 个坑 6 道自测
20:00
读之前先答一句：LEFT JOIN 之后把条件写在 ON 和写在 WHERE，结果什么时候不一样？
开始前

面试官不考语法，考的是「你先确认什么」

「写一条 SQL，统计上个月每个城市消费金额前三的用户。」很多人听到这句就开始敲键盘，敲完发现漏了一个条件：同一个用户在多个城市有订单怎么办、退款的算不算、注册时间在上个月的才算还是下过单就算。面试官在第一分钟看到的不是你的 SQL，是你有没有问这些问题。

运维岗的 SQL 题和开发岗不太一样。开发考的是「业务逻辑能不能表达清楚」，运维考的是另外三样：你能不能从一堆表里快速拼出一张临时报表、你能不能判断一条慢 SQL 慢在哪、你能不能给出一句可执行的索引建议而不是「加个索引」。这三样都不需要你背语法，但都需要你知道执行顺序。

现场脱口而出的答案正确的第一步
「统计每个用户的订单数」直接写 GROUP BY先问：没下过单的用户要不要出现？决定了用 JOIN 还是 LEFT JOIN
「查没有订单的用户」NOT IN 子查询先确认子查询列有没有 NULL。有 NULL 就返回空集，这是最经典的静默错误
「这条 SQL 很慢」加索引先看 EXPLAIN 的 rows 和 Extra，确认是扫得多、回表多、还是排序多
「取每组前三条」GROUP BY 加 LIMITLIMIT 是对整个结果集生效的，不是对每组。要用窗口函数
版本假设（这一篇的所有 SQL 都基于它）：本文按 MySQL 8.0 语法写。窗口函数和 CTE 需要 8.0 及以上；EXPLAIN ANALYZE 需要 8.0.18 及以上；8.0 默认的 sql_mode 包含 ONLY_FULL_GROUP_BY，所以 SELECT 里出现非聚合列时必须出现在 GROUP BY 中。5.7 及更早版本没有窗口函数和 CTE。具体以你环境 SELECT VERSION(); 和 SELECT @@sql_mode; 的输出为准。

下面的 30 道题共用一张表结构，你可以整个复制到本地跑一遍。能跑通这件事本身就是面试加分项——很多人答题时写出的 SQL 连语法都过不了。

-- 建表：结构贴近真实业务，字段类型刻意选了常见的几种
CREATE TABLE users (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name        VARCHAR(64)     NOT NULL,
  city        VARCHAR(32)     NOT NULL,
  created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_city (city)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE orders (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id     BIGINT UNSIGNED NOT NULL,
  status      TINYINT         NOT NULL DEFAULT 0,  -- 0待付 1已付 2已退
  amount      DECIMAL(10,2)   NOT NULL,
  created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_user_status_created (user_id, status, created_at),
  KEY idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

测试数据量建议灌到几十万行以上，否则你会看到「加了索引和没加索引一个样」——因为小表优化器本来就会走全表扫。优化器的决策和表大小强相关，这点在面试里说出来很加分。

面试落点：「我写 SQL 之前会先确认语义：统计口径是什么、要不要包含零记录的行、时间范围按哪个字段算、NULL 怎么处理。确认完再动手，写出来的 SQL 我会用 EXPLAIN 看一眼扫描行数和有没有额外排序。」

模块 1

基础查询与过滤：WHERE 和 HAVING 到底谁先跑

「统计订单数超过 3 笔的用户」——这句需求里藏着两个过滤条件：一个是对行的（订单状态、时间范围），一个是对组的（订单数 > 3）。把它们写到同一个地方，是你写完 SQL 却跑不出结果的第一大原因。

MySQL 的执行顺序（逻辑上的）是这样的：FROM → WHERE → GROUP BY → 聚合 → HAVING → SELECT 里的表达式 → ORDER BY → LIMIT。记住两点就够了：WHERE 在分组之前过滤行，所以不能写聚合函数；HAVING 在分组之后过滤组，所以才能写 COUNT、SUM。窗口函数的位置更靠后（在 SELECT 阶段计算），这个放到模块 3 讲。

子句作用时机能写什么典型错误
WHERE分组前，逐行判断列条件、表达式，不能写聚合WHERE COUNT(*) > 3 会直接报错
GROUP BY把行收敛成组列名或表达式。ONLY_FULL_GROUP_BY 下 SELECT 的非聚合列必须在这里SELECT 里出现没分组也没聚合的列
HAVING分组后，逐组判断聚合条件，也可以写分组列把本该在 WHERE 的行条件写到这里，白白多扫一遍
ORDER BY最后排序列、表达式、别名大结果集排序会落临时表或磁盘

第 1 题：统计每个用户的订单数与总金额

-- 只统计已支付订单（status=1），按用户聚合
SELECT user_id,
       COUNT(*)          AS cnt,
       ROUND(SUM(amount), 2) AS total
FROM orders
WHERE status = 1
GROUP BY user_id
ORDER BY total DESC
LIMIT 20;

这一句里 WHERE status = 1 写在 GROUP BY 之前，意味着先把不相关的行砍掉再分组，参与聚合的行数最少。如果把它挪到 HAVING，MySQL 会把全表行都分组一遍再过滤，白白多算。

第 2 题：只保留订单数 ≥ 3 的用户

-- 聚合条件只能进 HAVING；WHERE 里写 COUNT(*) 会报语法错
SELECT user_id, COUNT(*) AS cnt, ROUND(SUM(amount), 2) AS total
FROM orders
WHERE status = 1
GROUP BY user_id
HAVING COUNT(*) >= 3
ORDER BY cnt DESC;

第 3 题：统计金额在 100 到 1000 之间的已支付订单

-- BETWEEN 是闭区间，等价于 >= 100 AND <= 1000
SELECT COUNT(*) AS cnt, ROUND(SUM(amount), 2) AS total
FROM orders
WHERE status = 1 AND amount BETWEEN 100 AND 1000;

第 4 题：一次扫描算出各状态的订单数

-- 用条件聚合，一次扫描拿到多列；比写三条 SQL 或一个 UNION 便宜得多
SELECT COUNT(*)                                                   AS all_cnt,
       SUM(CASE WHEN status = 0 THEN 1 ELSE 0 END)                AS unpaid_cnt,
       SUM(CASE WHEN status = 1 THEN 1 ELSE 0 END)                AS paid_cnt,
       SUM(CASE WHEN status = 2 THEN 1 ELSE 0 END)                AS refund_cnt,
       ROUND(SUM(CASE WHEN status = 1 THEN 1 ELSE 0 END)
             / COUNT(*) * 100, 2)                                 AS paid_pct
FROM orders;

MySQL 里 SUM(status = 1) 也能工作（布尔表达式返回 1 或 0），但 CASE WHEN 的可读性更好、换数据库也不会出错。注意 COUNT(*) 为 0 时除法会得到 NULL 或报错，取决于是否开启了错误模式；稳妥写法是外面套一层 IFNULL(..., 0)。

第 5 题：找出从未下过单的用户

-- 推荐写法：NOT EXISTS。语义直白，也不受 NULL 影响
SELECT u.id, u.name, u.city
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
)
ORDER BY u.id
LIMIT 50;

这里先给 EXISTS 版本而不是 NOT IN，是因为 NOT IN 遇到 NULL 会静默返回空集，这是面试里出现频率最高的一类错误。完整对比放在模块 6。

COUNT 的三个写法结果不一样。COUNT(*) 数行；COUNT(col) 只数 col 不为 NULL 的行，列有 NULL 时两者结果不同；COUNT(DISTINCT col) 数去重后的非 NULL 值。「统计用户数」写成 COUNT(user_id) 在有 NULL 的列上会算少，而且不会报错——静默的错误结果比报错危险得多。

面试落点：「WHERE 在分组前过滤行、不能写聚合；HAVING 在分组后过滤组。我会把行条件尽量写在 WHERE 里减少参与分组的行数，聚合条件才放 HAVING。另外 COUNT(*) 和 COUNT(col) 在有 NULL 时结果不同，这个我每次都会确认一遍列的 NULL 属性。」

模块 2

JOIN 全家桶：LEFT JOIN 悄悄退化成 INNER

「我用 LEFT JOIN 了，为什么没订单的用户没出现？」——十次里有九次，答案是你在 WHERE 里对右表的列加了条件。这个坑的可怕之处在于它不报错，只是安静地少了几行，而少掉的那几行往往正是你要统计的对象。

原理很简单：LEFT JOIN 会把左表没有匹配的行也保留，右表的列填 NULL。此时 WHERE o.status = 1 对这些行来说就是 NULL = 1，结果是未知，行被丢弃。效果等同于 INNER JOIN。把条件挪到 ON 里，它就变成连接条件的一部分，只影响「哪些右表行能匹配上」，不影响左表行的保留。

写法保留左表无匹配的行吗适用场景
INNER JOIN ... ON不保留只要两边都有的数据
LEFT JOIN ... ON保留要列出左表全部行，右表没有就补 NULL
LEFT JOIN ... ON 右表条件保留「所有用户 + 他们的已支付订单（没有就为空）」
LEFT JOIN ... WHERE 右表条件不保留，退化成 INNER几乎总是写错了，除非你本来就要 INNER
LEFT JOIN ... WHERE 右表主键 IS NULL只保留无匹配的行求差集，模块 6 会用到

第 6 题：查出用户名和订单信息（只要两边都有的）

SELECT u.id AS user_id, u.name, o.id AS order_id, o.amount, o.created_at
FROM users u
INNER JOIN orders o ON o.user_id = u.id
WHERE o.status = 1
ORDER BY o.created_at DESC
LIMIT 50;

第 7 题：列出所有用户，没有订单的也要出现

-- 注意 COUNT(o.id) 而不是 COUNT(*)：前者对无订单用户返回 0
SELECT u.id, u.name, COUNT(o.id) AS order_cnt, ROUND(IFNULL(SUM(o.amount), 0), 2) AS total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id AND o.status = 1
GROUP BY u.id, u.name
ORDER BY order_cnt DESC;

把 o.status = 1 写在 ON 里而不是 WHERE 里，是这道题唯一的考点。如果你写成 WHERE，结果只会剩下有已支付订单的用户，而「零订单用户」恰恰是这类报表通常最想看的那部分。

第 8 题：同一个需求，写成 WHERE 会怎样

-- 错误示范：条件在 WHERE，LEFT JOIN 退化成 INNER JOIN
SELECT u.id, u.name, COUNT(o.id) AS order_cnt
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.status = 1
GROUP BY u.id, u.name;

-- 验证方式：对比两个写法返回的行数
SELECT COUNT(*) FROM (
  SELECT u.id FROM users u LEFT JOIN orders o ON o.user_id = u.id AND o.status = 1 GROUP BY u.id
) a;
SELECT COUNT(*) FROM (
  SELECT u.id FROM users u LEFT JOIN orders o ON o.user_id = u.id WHERE o.status = 1 GROUP BY u.id
) b;

第 9 题：查出每个用户的第一笔订单金额

-- 先聚合出每个用户的最早时间，再关联回明细
SELECT f.user_id, o.id AS first_order_id, o.amount, o.created_at
FROM orders o
JOIN (
  SELECT user_id, MIN(created_at) AS first_at
  FROM orders
  GROUP BY user_id
) f ON f.user_id = o.user_id AND o.created_at = f.first_at
ORDER BY f.user_id;

这个写法有一个必须说明的边界：如果同一用户有两笔订单的 created_at 完全相同，会返回两行。要严格取一条，用模块 3 的 ROW_NUMBER 版本（第 11 题），并在排序里补上 id 作为决胜键。

第 10 题：JOIN 之前先聚合，避免行数放大

-- 反例：直接 JOIN orders 再 COUNT(DISTINCT) 或 SUM 会重复计算
-- 正例：先把 orders 收敛成「每用户一行」，再关联
SELECT u.id, u.name, u.city,
       IFNULL(t.cnt, 0)            AS cnt,
       ROUND(IFNULL(t.total, 0), 2) AS total
FROM users u
LEFT JOIN (
  SELECT user_id, COUNT(*) AS cnt, SUM(amount) AS total
  FROM orders
  WHERE status = 1
  GROUP BY user_id
) t ON t.user_id = u.id
ORDER BY total DESC
LIMIT 30;

「先聚合再关联」是写报表 SQL 最重要的一条纪律。一对多关联会把左表行数放大 N 倍，此时任何 SUM 都会被重复计算，而很多人是靠加 DISTINCT 去「修」——那只是掩盖问题，性能还更差。

验证行数有没有被放大的一个笨办法但很有效：分别跑 SELECT COUNT(*) FROM users 和你的 JOIN 结果的行数。如果 JOIN 后的行数大于左表行数，而你又没预料到，那就是关联键不唯一（比如关联了 orders 却按 user_id 分组）。每次写完多表查询都做这个对比，能挡掉大部分「报表数字对不上」。

面试落点：「LEFT JOIN 的条件写在 ON 和 WHERE 语义完全不同：写在 WHERE 里会退化成 INNER JOIN，因为无匹配行的右表列是 NULL，条件判断为未知就被丢弃了。另外多表查询我一定会先聚合再关联，避免一对多放大导致 SUM 重复计算。」

模块 3

窗口函数：排名、累计、环比，一次扫描全搞定

窗口函数和 GROUP BY 的区别一句话说清：GROUP BY 把多行压成一行，窗口函数保留原来的每一行，同时附加上一个「基于一组行算出来的值」。所以「每组 TopN」「累计求和」「环比」这些需要「既要看明细又要看组内统计」的场景，非它不可。

函数做什么关键参数
ROW_NUMBER()组内连续编号，1、2、3…… 并列也强制区分PARTITION BY 分组，ORDER BY 定序
RANK()并列同名次，下一名跳号（1、1、3）同上
DENSE_RANK()并列同名次，下一名不跳号（1、1、2）同上
LAG / LEAD取当前行之前 / 之后第 N 行的值LAG(col, N, 默认值)
SUM() OVER组内累计求和可加 ROWS BETWEEN ... PRECEDING AND CURRENT ROW

窗口函数只能出现在 SELECT 和 ORDER BY 里，不能直接写进 WHERE。因为它是在 WHERE 过滤之后才计算的。想「只保留组内第一名」，必须在外面套一层子查询或 CTE，用 WHERE 过滤那个编号列。这是面试里的一道高频追问，也是初学者最容易写出语法错误的地方。

第 11 题：查出每个用户最近的一笔订单

-- rn = 1 的过滤必须在外层：窗口函数在 WHERE 之后才计算
SELECT user_id, order_id, amount, created_at
FROM (
  SELECT o.user_id,
         o.id AS order_id,
         o.amount,
         o.created_at,
         ROW_NUMBER() OVER (
           PARTITION BY o.user_id
           ORDER BY o.created_at DESC, o.id DESC   -- id 作决胜键，保证结果确定
         ) AS rn
  FROM orders o
) t
WHERE t.rn = 1
ORDER BY t.user_id;

第 12 题：RANK / DENSE_RANK / ROW_NUMBER 差在哪

-- 三个函数并列跑一遍，看同一批金额下的名次差异
SELECT id,
       amount,
       ROW_NUMBER() OVER (ORDER BY amount DESC, id) AS rn,   -- 1,2,3,4
       RANK()       OVER (ORDER BY amount DESC)     AS rk,   -- 1,1,3,4
       DENSE_RANK() OVER (ORDER BY amount DESC)     AS drk   -- 1,1,2,3
FROM orders
WHERE status = 1
ORDER BY amount DESC, id
LIMIT 20;

注意 ROW_NUMBER() 的 ORDER BY 里加了 id：如果排序键有重复，ROW_NUMBER 的分配是不确定的，同一条 SQL 两次跑可能给出不同结果。「结果不确定」在分页场景里会表现成「翻页时有的行重复出现、有的行失踪」，非常难查。

第 13 题：按天统计订单量，并算出环比

WITH daily AS (
  SELECT DATE(created_at) AS d, COUNT(*) AS cnt
  FROM orders
  WHERE created_at >= '2026-09-01' AND created_at < '2026-10-01'
  GROUP BY DATE(created_at)
)
SELECT d,
       cnt,
       LAG(cnt) OVER (ORDER BY d) AS prev_cnt,
       ROUND((cnt - LAG(cnt) OVER (ORDER BY d))
             / LAG(cnt) OVER (ORDER BY d) * 100, 2) AS pct_change
FROM daily
ORDER BY d;

第一天的 prev_cnt 是 NULL，所以 pct_change 也是 NULL——NULL 参与算术会传播，这其实是我们想要的行为（除法分母为 NULL 不会报除零错）。如果你希望显示 0 而不是 NULL，外面套 IFNULL(..., 0)。

第 14 题：累计求和（running total）

WITH daily AS (
  SELECT DATE(created_at) AS d, COUNT(*) AS cnt
  FROM orders GROUP BY DATE(created_at)
)
SELECT d,
       cnt,
       SUM(cnt) OVER (ORDER BY d
                      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS run_cnt
FROM daily
ORDER BY d;

第 15 题：7 日移动平均

WITH daily AS (
  SELECT DATE(created_at) AS d, COUNT(*) AS cnt
  FROM orders GROUP BY DATE(created_at)
)
SELECT d,
       cnt,
       ROUND(AVG(cnt) OVER (ORDER BY d
                            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2) AS ma7
FROM daily
ORDER BY d;

窗口框架 ROWS BETWEEN 6 PRECEDING AND CURRENT ROW 的意思是「当前行加上前面 6 行，共 7 行」。它的前提是按天连续；如果中间有几天没有订单（行不存在），这 7 行覆盖的实际天数会超过 7 天。要严格按 7 天窗口，得先补齐日期（第 25 题）。

窗口函数的性能提醒：窗口函数要对整个分区排序或累积，分区很大时会用临时空间。给 PARTITION BY ... ORDER BY ... 配上一致的索引，可以让 MySQL 直接按索引顺序扫，省掉一次排序。这一点在 EXPLAIN 里表现为 Extra 中没有 Using filesort。

面试落点：「窗口函数保留明细行的同时给出组内统计值，这是它和 GROUP BY 的本质差别。它只能出现在 SELECT 和 ORDER BY，不能直接进 WHERE，所以取组内 TopN 必须外面套一层。另外 ROW_NUMBER 的 ORDER BY 要加唯一决胜键，否则结果不确定。」

模块 4

分组 TopN 与去重：LIMIT 管不了每组

「取每个城市消费前三的用户」——第一次写这道题的人有一半会写出 GROUP BY city LIMIT 3。这个写法返回的是「整个结果集的前 3 行」，和「每组前 3」毫无关系。它没有报错，只是给了一个看起来合理的错误答案。

第 16 题：每个城市消费金额 Top3 的用户

SELECT city, user_id, total, rn
FROM (
  SELECT u.city,
         o.user_id,
         ROUND(SUM(o.amount), 2) AS total,
         ROW_NUMBER() OVER (
           PARTITION BY u.city
           ORDER BY SUM(o.amount) DESC      -- 窗口的 ORDER BY 里可以用聚合函数
         ) AS rn
  FROM orders o
  JOIN users u ON u.id = o.user_id
  WHERE o.status = 1
  GROUP BY u.city, o.user_id
) t
WHERE t.rn <= 3
ORDER BY city, rn;

关键点：窗口函数在 GROUP BY 之后执行，所以窗口的 ORDER BY 里可以直接写 SUM(o.amount)。如果你觉得这样写难读，用 CTE 拆成两步（第 17 题）会更清楚，也让每一步都能单独验证。

第 17 题：用 CTE 把上面那题拆清楚

WITH city_user AS (
  SELECT u.city,
         o.user_id,
         ROUND(SUM(o.amount), 2) AS total
  FROM orders o
  JOIN users u ON u.id = o.user_id
  WHERE o.status = 1
  GROUP BY u.city, o.user_id
),
ranked AS (
  SELECT city, user_id, total,
         ROW_NUMBER() OVER (PARTITION BY city ORDER BY total DESC) AS rn
  FROM city_user
)
SELECT city, user_id, total, rn
FROM ranked
WHERE rn <= 3
ORDER BY city, rn;

想让并列第三名的用户都出现，把 ROW_NUMBER() 换成 DENSE_RANK()、条件改成 WHERE rn <= 3 即可，此时每组可能返回多于 3 行。这个取舍要跟需求方确认，不是技术选择。

第 18 题：删除重复数据，只保留 id 最小的一条

-- 这里按 (user_id, created_at) 判定重复，实际按你的业务唯一键替换
DELETE FROM orders
WHERE id IN (
  SELECT id
  FROM (
    SELECT id,
           ROW_NUMBER() OVER (PARTITION BY user_id, created_at ORDER BY id) AS rn
    FROM orders
  ) t
  WHERE t.rn > 1
);

外面那层 SELECT id FROM (...) t 不是多余的：MySQL 不允许一边修改某张表一边直接从它本身的子查询里读，包一层派生表会被物化，从而绕开这个限制。这是 MySQL 特有的写法约束。另外，生产上删数据前先跑一遍对应的 SELECT 看会删多少行，再改成 DELETE。

第 19 题：找出有重复下单记录的用户

SELECT user_id, COUNT(*) AS cnt
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 1
ORDER BY cnt DESC
LIMIT 20;

第 20 题：订单行数 vs 下单用户数

SELECT COUNT(*)                 AS order_rows,
       COUNT(DISTINCT user_id)   AS user_cnt
FROM orders
WHERE status = 1;

这一句常被用来回答「我们有多少下单用户」。COUNT(DISTINCT) 在大数据量上是比较贵的（需要去重结构），如果这张表的统计是高频需求，更好的做法是维护一张按日预聚合的汇总表，报表直接查汇总表。

「去重」这件事要先定义清楚什么叫重复。订单表里 (user_id, created_at) 相同的两行，可能是重复写入的脏数据，也可能是用户同一秒下了两笔不同的单——看 id 之外的字段才能判断。所以在动手删之前，先把疑似重复的行完整 SELECT 出来人工看几条，确认判重键选对了。删错了不可回滚，这是运维岗少数几个「必须先确认再执行」的操作之一。

面试落点：「分组 TopN 我用窗口函数，因为 LIMIT 作用于整个结果集而不是每个分组。写法是先按分组键聚合、再在外层按 ROW_NUMBER 过滤；并列要不要都保留取决于需求，用 DENSE_RANK 就行。去重前我会先把疑似重复的行完整查出来确认判重键，删数据是一次性的、不可回滚。」

模块 5

时间维度统计：按天、按周、按月、留存

报表需求里一半以上都带时间维度。这一块的考点不是函数记不记得住，而是你会不会为了能用上索引，把条件写成范围而不是函数——这一条直接决定报表是 200ms 还是 20 秒。

写法能不能用上 created_at 的索引为什么
WHERE DATE(created_at) = '2026-10-01'不能（普通索引）列被函数包住，B+ 树里存的是原值，没法按函数结果定位
WHERE created_at >= '2026-10-01' AND created_at < '2026-10-02'能纯范围条件，可以直接在索引上定位区间
GROUP BY DATE(created_at)分组不受影响分组表达式不参与索引定位，但会影响会不会出现临时表

第 21 题：按天统计订单量与金额

SELECT DATE(created_at)        AS d,
       COUNT(*)                AS cnt,
       ROUND(SUM(amount), 2)   AS amt
FROM orders
WHERE created_at >= '2026-09-01' AND created_at < '2026-10-01'
  AND status = 1
GROUP BY DATE(created_at)
ORDER BY d;

注意 WHERE 用的是半开区间 [09-01, 10-01)，而不是 BETWEEN '09-01' AND '09-30'。后者会漏掉 9 月 30 日当天 00:00 之后的数据（因为日期字面量会被补成 00:00:00）。时间范围一律用半开区间，能避开所有边界问题。

第 22 题：按周统计

-- %x = ISO 周所在的年份，%v = ISO 周序号(01-53)，周一为一周第一天
-- 用 %x 而不是 %Y，能避开跨年那周「年份和周数对不上」的问题
SELECT DATE_FORMAT(created_at, '%x-%v') AS yw,
       COUNT(*)                         AS cnt,
       ROUND(SUM(amount), 2)            AS amt
FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2026-11-01'
GROUP BY yw
ORDER BY yw;

第 23 题：按月统计并算环比

WITH monthly AS (
  SELECT DATE_FORMAT(created_at, '%Y-%m') AS ym,
         ROUND(SUM(amount), 2)            AS amt
  FROM orders
  WHERE status = 1
  GROUP BY DATE_FORMAT(created_at, '%Y-%m')
)
SELECT ym,
       amt,
       LAG(amt) OVER (ORDER BY ym) AS prev_amt,
       ROUND((amt - LAG(amt) OVER (ORDER BY ym))
             / LAG(amt) OVER (ORDER BY ym) * 100, 2) AS mom_pct
FROM monthly
ORDER BY ym;

'%Y-%m' 生成的字符串（如 '2026-09'）按字典序排序和按时间排序是一致的，所以这里直接 ORDER BY ym 是安全的。如果格式写成 '9月' 或 'Sep'，排序就会乱——这是很低级但真的会犯的错。

第 24 题：次日留存率

WITH new_users AS (
  SELECT id, DATE(created_at) AS reg_date
  FROM users
),
first_order AS (
  SELECT user_id, MIN(DATE(created_at)) AS first_order_date
  FROM orders
  GROUP BY user_id
)
SELECT n.reg_date,
       COUNT(*) AS new_cnt,
       SUM(CASE WHEN f.first_order_date = DATE_ADD(n.reg_date, INTERVAL 1 DAY)
                THEN 1 ELSE 0 END) AS retained_d1,
       ROUND(SUM(CASE WHEN f.first_order_date = DATE_ADD(n.reg_date, INTERVAL 1 DAY)
                      THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS d1_pct
FROM new_users n
LEFT JOIN first_order f ON f.user_id = n.id
GROUP BY n.reg_date
ORDER BY n.reg_date;

这里把留存的口径明确写成了「注册后第 1 天首次下单」。留存的定义至少有四五种（次日是否有任何行为、次日起 7 天内是否回访、注册当天是否下单……），面试里务必先问清口径再写，写完在 SQL 注释里把口径写下来。口径不同，数字可以差好几倍。

第 25 题：补齐没有订单的日期（让折线图不断点）

WITH RECURSIVE cal AS (
  SELECT DATE('2026-09-01') AS d
  UNION ALL
  SELECT DATE_ADD(d, INTERVAL 1 DAY) FROM cal WHERE d < DATE('2026-09-30')
),
daily AS (
  SELECT DATE(created_at) AS d, COUNT(*) AS cnt
  FROM orders
  WHERE created_at >= '2026-09-01' AND created_at < '2026-10-01'
  GROUP BY DATE(created_at)
)
SELECT c.d,
       IFNULL(t.cnt, 0) AS cnt
FROM cal c
LEFT JOIN daily t ON t.d = c.d
ORDER BY c.d;

递归 CTE 的默认递归深度是 1000（cte_max_recursion_depth），一次生成 30 天完全够用；要生成几年的日历就要调这个参数，或者干脆建一张物理日期维表。日期维表是数据仓库里的标准做法，运维做长期报表时建一张很划算。

时间字段的类型决定了你能不能省事。用 DATETIME 存本地时间，跨时区业务会出现对不齐；用 TIMESTAMP 会随会话时区变化，且范围有限。无论选哪个，团队内要统一，并且明确「报表按哪个时区出」。这个决定做错了，后面所有按天的报表都要重算一遍。

面试落点：「按时间过滤我一定写成半开区间而不是 BETWEEN，也不在索引列上套 DATE()，否则索引失效。跨年周我用 %x-%v 避免年份错配。留存我先问清口径再写，并把口径写进 SQL 注释。折线图断点用递归 CTE 或日期维表补齐。」

模块 6

存在性判断与 NULL：NOT IN 的静默陷阱

这是整篇里最值得记住的一节，因为它导致的错误不报错、不警告，只是安静地返回一个空结果集。如果你不知道这个规则，可能会盯着一条「看起来完全正确」的 SQL 查一个小时。

规则是这样的：x NOT IN (a, b, c) 等价于 x <> a AND x <> b AND x <> c。一旦列表里出现 NULL，某个 x <> NULL 的结果是「未知」，整个 AND 表达式的结果就是「未知」，而 WHERE 只接受「真」——所以一行都不会返回。

第 26 题：亲眼看到 NOT IN 遇 NULL 的结果

-- 三条表达式并排跑，结果分别是 1、NULL、0
SELECT (1 NOT IN (2, 3))       AS r_no_null,   -- 1（真）
       (1 NOT IN (2, 3, NULL)) AS r_with_null, -- NULL，不是 1！
       (1 NOT IN (1, 2))       AS r_false;     -- 0（假）

-- 由此推出的结论：下面这句在 orders.user_id 可能为 NULL 时，一行都不返回
SELECT id, name FROM users WHERE id NOT IN (SELECT user_id FROM orders);

-- 加上非空过滤可以救回来，但远不如直接改写成 NOT EXISTS 清晰
SELECT id, name FROM users
WHERE id NOT IN (SELECT user_id FROM orders WHERE user_id IS NOT NULL);

本例的 orders.user_id 是 NOT NULL，所以第一种写法是安全的；但你不能依赖「我记得这个列是非空的」——表结构会变，中间可能加了允许 NULL 的列，或者子查询里的表达式产生了 NULL。用 NOT EXISTS 就没有这个问题，因为 EXISTS 只判断有没有行，不做值比较。

第 27 题：EXISTS 与 IN 的互换

-- 写法 A：EXISTS（推荐，语义清晰，不受 NULL 影响）
SELECT u.id, u.name
FROM users u
WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 100
);

-- 写法 B：IN（MySQL 8 会把它优化成半连接，性能通常与 EXISTS 接近）
SELECT u.id, u.name
FROM users u
WHERE u.id IN (SELECT user_id FROM orders WHERE amount > 100);

在 MySQL 8 里，IN 子查询常被优化成 semi-join，和 EXISTS 的执行计划往往很接近，所以这两者的选择主要看可读性和 NULL 语义，而不是性能。但 NOT IN 和 NOT EXISTS 就不一样了：前者有 NULL 陷阱，且优化空间更小。写「不存在」一律用 NOT EXISTS。

第 28 题：求差集（在 users 但不在 orders）

-- LEFT JOIN + IS NULL：另一种写法，语义是「关联不到任何一行」
SELECT u.id, u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

这里的 WHERE o.id IS NULL 必须用右表的主键或非空列。用 o.user_id IS NULL 也可以，但可读性差；如果右表有个允许 NULL 的列，用它判断就会误判。

写法遇到 NULL 的行为建议
NOT IN (子查询)子查询含 NULL 时返回空集避免使用
NOT EXISTS不受影响首选
LEFT JOIN ... IS NULL不受影响可用，注意判空列要选非空的
IN (子查询)不受影响可用，MySQL 8 会做半连接优化
一个相关但更容易被忽略的陷阱：聚合函数遇到 NULL。SUM(col)、AVG(col)、COUNT(col) 都跳过 NULL，且当所有行都是 NULL 时返回 NULL 而不是 0。所以「平均订单金额」在有 NULL 金额时会算成「非 NULL 部分的平均」，分母悄悄变小了。要按全部行数算平均，写 SUM(col) / COUNT(*) 并配 IFNULL，而不是直接 AVG(col)。

面试落点：「写『不存在』我一律用 NOT EXISTS。NOT IN 在子查询含 NULL 时会返回空集，而且不报错——它是 x <> a AND x <> b 的展开，任一比较为未知整体就为未知。另外聚合函数跳过 NULL，全 NULL 时返回 NULL，所以我算平均值会先想清楚分母该是行数还是非 NULL 数。」

模块 7

慢查询诊断：EXPLAIN 要看哪几列

「这条 SQL 慢」在工单里等于没说。运维岗的 SQL 题，真正的分水岭是你能不能把「慢」拆成可比较的数字：扫了多少行、回了多少次表、排序用了多少内存、实际耗时分布在哪个环节。

列它在说什么怎么用
type访问方式，从好到差大致是 const > eq_ref > ref > range > index > ALL只说明方式，不说明代价。range 也可能扫几百万行
key实际选中的索引为 NULL 不等于有问题，要结合 rows 判断是不是优化器主动放弃
rows预估要扫多少行成本的核心指标。rows 接近全表行数，说明索引没起到过滤作用
filtered扫出来的行里能通过后续条件的百分比rows × filtered 才近似等于真正参与后续计算的行数
Extra补充动作信息量最大的一列，见下表
Extra 里的字样含义要不要处理
Using index覆盖索引，没有回表好信号，别去「优化」它
Using index condition索引下推生效，过滤在引擎层完成好信号
Using whereServer 层还要再过滤一遍索引用得不够充分，配合 rows 判断值不值得加索引
Using filesort无法利用索引顺序，额外排序小结果集可接受，大结果集要改索引或改 SQL
Using temporary用了内部临时表，常见于 GROUP BY、DISTINCT、UNION大表上出现必须处理，可能落到磁盘

第 29 题：诊断一条具体 SQL

-- 1. 先看优化器的估算（不执行）
EXPLAIN
SELECT o.id, o.amount
FROM orders o
WHERE o.user_id = 42 AND o.status = 1
ORDER BY o.created_at DESC
LIMIT 20;

-- 2. 8.0.18+ 用 EXPLAIN ANALYZE 看真实行数和耗时
--    注意：它会真的执行这条语句，DML 请务必不要直接跑
EXPLAIN ANALYZE
SELECT o.id, o.amount
FROM orders o
WHERE o.status = 1
ORDER BY o.created_at DESC
LIMIT 20;

-- 3. 从实例侧找最耗时的语句模板（digest 聚合）
SELECT DIGEST_TEXT AS sql_tpl,
       COUNT_STAR  AS exec_cnt,
       ROUND(SUM_TIMER_WAIT / 1000000000000, 2) AS total_sec,
       ROUND(AVG_TIMER_WAIT / 1000000000000, 4) AS avg_sec,
       SUM_ROWS_EXAMINED AS rows_examined
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

这段 digest 查询是运维岗最实用的一条：它按语句模板聚合，直接告诉你「哪类 SQL 总共最耗时」。注意要按总耗时排而不是按单次耗时排——一条跑 3 秒但一天只跑 1 次的 SQL，危害远小于一条 50ms 但一天跑 10 万次的。

EXPLAIN 的 rows 是估算，不是真实值。它基于索引的采样统计，数据分布倾斜时可能差一个数量级。所以不要因为「rows 只有 10」就放心，也不要因为「rows 是 80 万」就立刻加索引——用 EXPLAIN ANALYZE 看真实值，或者对比 performance_schema 里的 ROWS_EXAMINED。统计信息不准时可以用 ANALYZE TABLE 重采样，但大表上它有开销，别在高峰期跑。
EXPLAIN ANALYZE SELECT ...;8.0.18+，给出真实行数与耗时；会真的执行，DML 别直接跑
SELECT * FROM performance_schema.events_statements_summary_by_digest ORDER BY SUM_TIMER_WAIT DESC LIMIT 10\G按语句模板聚合，找全实例总耗时最高的 SQL
SELECT DIGEST_TEXT, COUNT_STAR, SUM_ROWS_EXAMINED FROM performance_schema.events_statements_summary_by_digest ORDER BY SUM_ROWS_EXAMINED DESC LIMIT 10\G按扫描行数排，找出「单行成本不高但扫得多」的语句
SHOW VARIABLES LIKE 'long_query_time'; SET GLOBAL slow_query_log = ON;确认并开启慢日志，阈值与是否需重启以版本为准
SELECT * FROM information_schema.processlist WHERE command != 'Sleep' ORDER BY time DESC LIMIT 10\G看当前正在跑的长查询与长事务
ANALYZE TABLE orders;统计信息明显失真时重采样；大表有开销，别在高峰期跑

其中「按扫描行数排」这一条常被忽略：一条 SQL 单次耗时不高，但每次扫 50 万行，一天跑十万次，对实例的总压力远大于一条偶尔跑一次的慢查询。看总耗时能找到最慢的，看总扫描行数能找到「最浪费的」——两个视角都要有。

面试落点：「我看 EXPLAIN 的顺序是 type → rows → Extra。type 只说明访问方式，rows 才说明扫多少。要真实值就用 EXPLAIN ANALYZE（注意它会真的执行）。找全实例最慢的 SQL 我查 performance_schema 的 digest 汇总表，按总耗时排，也会按总扫描行数排一次。」

模块 8

索引建议怎么给：最左前缀、覆盖索引与代价

「加个索引」不是建议，是一句没有信息量的话。一条可执行的建议至少要包含：建在哪些列上、什么顺序、能解决这条 SQL 的哪一段成本、以及代价是什么。

联合索引的排序规则是先按第一列排、相同再按第二列，就像电话簿先按姓再按名。由此推出最左前缀原则的两个推论：缺少最左列就无法用于定位；范围条件之后的列失去定位能力（因为前一列已经是范围了，后面的列在整体上不再有序）。

条件写法（索引 (a, b, c)）能用上几列能做什么
a = 1a定位
a = 1 AND b = 2a, b定位
a = 1 AND b > 2a, b（b 之后失效）定位，c 无法再用
a = 1 ORDER BY ba 定位，b 提供有序省掉排序
b = 2（不带 a）无法定位最多做索引全扫描，比全表扫便宜

第 30 题：给这条 SQL 一条完整的索引建议

-- 需求：后台按状态查最近 20 条订单
SELECT id, amount, created_at
FROM orders
WHERE status = 1
ORDER BY created_at DESC
LIMIT 20;

-- 建议一：等值列在前、排序列在后
ALTER TABLE orders ADD KEY idx_status_created (status, created_at);
-- 效果：status=1 定位 + created_at 直接有序，LIMIT 20 只扫 20 行

-- 建议二：8.0 支持降序索引，排序方向一致时更直接
ALTER TABLE orders ADD KEY idx_status_created_desc (status, created_at DESC);

-- 建议三：如果查询列固定就这三列，做成覆盖索引，连回表都省掉
ALTER TABLE orders ADD KEY idx_status_created_cover (status, created_at, amount);
-- 验证：Extra 出现 Using index（覆盖索引），并用 EXPLAIN ANALYZE 看实际扫描行数

给出建议时必须同时说代价，否则会被追问：每多一个索引，写操作就要多维护一棵 B+ 树，INSERT/UPDATE/DELETE 变慢，磁盘和 buffer pool 占用变大。所以「加索引」是拿写性能和空间换读性能，一张表上堆十几个索引通常是设计问题（往往是「每个报表需求来一个」积累出来的）。

-- 建完之后必须验证：对比建索引前后的执行计划
EXPLAIN SELECT id, amount, created_at FROM orders WHERE status = 1 ORDER BY created_at DESC LIMIT 20;

-- 看看这张表上已经堆了多少索引，有没有重复的
SHOW INDEX FROM orders;

-- 8.0 可以建不可见索引，先验证效果再决定是否真正启用
ALTER TABLE orders ALTER INDEX idx_status_created INVISIBLE;
ALTER TABLE orders ALTER INDEX idx_status_created VISIBLE;
面试里「给索引建议」的完整话术：「我会先确认这条 SQL 的访问模式（过滤列是什么、排序列是什么、返回哪些列、命中比例大概多少），然后按『等值列在前、范围/排序列在后』设计联合索引，尽量做成覆盖索引。建之前我会先看这张表现在有哪些索引，避免重复；建之后用 EXPLAIN 对比前后 rows 和 Extra 的变化，并说明代价是写变慢和空间变大。」说出代价，是这道题的及格线。

面试落点：「索引建议我给三样：建在哪些列什么顺序、解决这条 SQL 哪一段成本、代价是什么。顺序按『等值在前、范围或排序在后』，能覆盖就覆盖。建完用 EXPLAIN 对比前后，并且说明写性能会下降、空间会变大——不说代价的建议是不完整的。」

模块 9

面试话术：先确认语义，再动手写

SQL 题的表现分，一半在写之前的三十秒。面试官真正观察的是：你是直接开敲，还是先把模糊的地方问清楚。因为线上出问题的 SQL，八成不是语法错，是语义错——数字算对了口径，或者算错了口径但没人发现。

确认口径。「统计上个月的下单用户」——按创建时间还是支付时间？包含退款吗？同一用户多笔算一人还是多笔？这三问不问，写出来的 SQL 大概率要返工。
确认边界。空集合怎么办（除零、NULL）、时区按哪个、时间范围是闭区间还是半开。这些决定了你的 SQL 在极端情况下会不会崩或给出怪值。
确认规模。「这张表多大、每天增多少、这个查询多久跑一次」。报表跑一次十几秒可以接受，接口里每次请求都跑就不行——规模决定了你是写 SQL 还是要建汇总表。
边写边说。说出你为什么用 LEFT JOIN、为什么用窗口函数、为什么把条件放在 ON 里。面试官听的是你的推理，不是最终结果，很多题他根本不看你跑没跑通。
被追问怎么答
「这条 SQL 能优化吗？」「先看 EXPLAIN 的 rows 和 Extra 再回答。是扫得多就加索引或改条件，是排序多就调整索引顺序让它提供有序性，是回表多就做成覆盖索引，是 offset 大就换游标。不同原因做法完全不同。」
「窗口函数和 GROUP BY 怎么选？」「要保留明细行就用窗口函数，只要汇总结果就用 GROUP BY。窗口函数在 WHERE 之后计算，所以过滤窗口函数的结果必须外面套一层。」
「你怎么保证报表数字是对的？」「我会用两种独立算法交叉验证：比如『下单用户数』同时用 COUNT(DISTINCT) 和先聚合再 COUNT 两种写法对比；另外会抽查几条明细，看能不能对上汇总值。」
「数据量大了之后怎么办？」「两条路：一是按天预聚合到汇总表，报表查汇总表；二是把明细归档出去，只保留近期的。要不要分库分表要看单表容量和写入压力，不是一上来就分。」
「你写过最复杂的 SQL 是什么？」「讲一个带窗口函数和多层 CTE 的报表，重点讲你怎么拆步骤、怎么验证每一步。不要吹规模，讲结构和验证。」
三个一定会被扣分的说法：「加个索引就好了」（没说建在哪、代价是什么）、「这个我一般用 ORM 生成」（说明你没手写过多表查询）、「我记不清函数名叫什么了」（窗口函数和日期函数是这一篇的基础，函数名记不住基本等于没写过）。运维岗的 SQL 不要求你写得花，但要求你写得对、说得清为什么这么写。

面试落点：「我写 SQL 的习惯是先确认口径、边界和规模，再动手。写的时候会把每一步拆成 CTE，这样每一步都能单独跑、单独验证。写完用 EXPLAIN 看一眼，并且用另一种算法交叉验证汇总数字。规模大到一定程度我会建议建汇总表，而不是硬扛明细查询。」

模块 10

10 个坑：每一个都会给你一个看起来合理的错答案

这十条的共同特点是不报错。语法错误会被立刻发现，语义错误会安静地返回一个错的数字，然后被写进日报。

1
把聚合条件写进 WHERE
WHERE 在分组前执行，里面不能出现 COUNT/SUM。聚合条件必须放 HAVING。反过来，本该在 WHERE 的行条件放进 HAVING，会让全表都参与分组。
2
LEFT JOIN 的条件写在 WHERE 里
无匹配行的右表列是 NULL，条件判断为未知，行被丢弃，LEFT JOIN 退化成 INNER JOIN。要保留左表全部行就得写在 ON 里。
3
用 COUNT(列) 当行数
COUNT(列) 跳过 NULL，行数会算少；全 NULL 时返回 NULL 而不是 0。数行一律用 COUNT(*)。
4
NOT IN 撞上 NULL
它展开成 x <> a AND x <> b，任一比较为未知时整体为未知，WHERE 只接受真，于是返回空集且无任何提示。写「不存在」一律用 NOT EXISTS。
5
窗口函数直接写进 WHERE
窗口函数在 WHERE 之后才计算，直接写会报语法错。取组内 TopN 必须在子查询或 CTE 里算出编号，外层再过滤。
6
用 GROUP BY + LIMIT 做分组 TopN
LIMIT 作用于整个结果集，不是每个分组。分组 TopN 必须用 ROW_NUMBER/RANK，另外 ROW_NUMBER 的排序要加唯一决胜键。
7
在索引列上套 DATE() 做过滤
列被函数包住就无法用索引定位。改成半开区间范围条件：>= '2026-10-01' AND < '2026-10-02'，既准确又能走索引。
8
用 BETWEEN 框时间范围
日期字面量会被补成 00:00:00，BETWEEN '09-01' AND '09-30' 会漏掉 9 月 30 日当天几乎全部数据。时间范围一律用半开区间。
9
一对多 JOIN 后直接 SUM
关联把左表行数放大，SUM 会被重复计算。正确做法是先在子查询里把多的一方聚合到「每个键一行」，再关联。
10
把 SELECT * 的明细拉到客户端再统计
几十万行数据全量过网络，客户端内存和数据库连接都被占住。聚合应该让数据库做，只把汇总结果传回来。

面试落点：挑一条讲，按「当时的判断 → 造成的后果 → 后来改成什么」三段说。第三段最重要：它决定面试官认为你是「踩过坑」还是「长了记性」。

自测

六道题

1. 要「统计订单数不少于 3 笔的用户」，下面说法正确的是？
正确答案：行条件放 WHERE，聚合条件放 HAVING。WHERE 在分组之前逐行过滤，不能出现聚合函数（MySQL 会直接报错）；HAVING 在分组之后过滤组，才能写 COUNT/SUM。把行条件也放进 HAVING 会让全表行都参与分组，白白多算一遍。
2. FROM users u LEFT JOIN orders o ON o.user_id = u.id WHERE o.status = 1，结果和哪种 JOIN 一致？
正确答案：等价于 INNER JOIN。LEFT JOIN 保留的无匹配行里，右表列全是 NULL，o.status = 1 对这些行的判断结果是「未知」，WHERE 只接受「真」，于是整行被丢弃。想保留零订单用户，必须把条件移到 ON 里。
3. 子查询 SELECT user_id FROM orders 的结果里存在 NULL，那么 WHERE id NOT IN (子查询) 的结果是？
正确答案：返回空集，没有任何提示。x NOT IN (...) 展开为 x <> a AND x <> b AND ...，一旦列表里有 NULL，某个比较的结果就是「未知」，整个 AND 表达式为「未知」，而 WHERE 只接受「真」。这也是为什么写「不存在」应该用 NOT EXISTS。
4. 要「每个城市消费金额前三的用户」，正确的做法是？
正确答案：窗口函数编号后过滤。LIMIT 作用于整个结果集而不是每个分组，GROUP BY city LIMIT 3 只会返回总共 3 行。正确写法是先聚合到「每城市每用户一行」，再用 ROW_NUMBER() OVER (PARTITION BY city ORDER BY total DESC) 编号，最后在外层过滤——窗口函数不能写进 WHERE，必须套一层。
5. 为什么 WHERE ROW_NUMBER() OVER (...) = 1 会失败？
正确答案：窗口函数在 WHERE 之后计算。逻辑执行顺序是 FROM → WHERE → GROUP BY → 聚合 → HAVING → 窗口/SELECT → ORDER BY → LIMIT，所以窗口函数只能出现在 SELECT 和 ORDER BY 里。取组内第一名要在子查询或 CTE 中生成编号列，再由外层 WHERE 过滤。
6. EXPLAIN 显示 key 有值、rows 只有 50，但这条 SQL 线上跑了 3 秒。最合理的解释是？
正确答案：rows 是估算。它来自索引采样统计，数据分布倾斜时可能差一个数量级。要真实值用 EXPLAIN ANALYZE（注意它会真的执行语句，DML 不要直接跑），或查 performance_schema 里的 ROWS_EXAMINED。另外慢也可能来自回表、排序或锁等待，不能只盯 key 一列。
