读之前先回答一句：你说「机器很卡」的时候，卡的是 CPU、磁盘，还是网络？
开始前

三个现场：先别急着敲命令

凌晨两点电话响，值班的同学说「机器很卡」。你登上机器，手第一下落在哪？大部分人落在 top。这个动作本身没错，但它只是「看一眼」，还称不上排查。排查是带着假设去看：我怀疑哪一层，我用哪个指标证伪它。

下面三种现场在同一年里会反复出现，它们的共同点是——你的第一直觉往往指向错误的那一层。

现场直觉答案真实原因
load 12，CPU 8%监控坏了，或者 CPU 不够一堆进程卡在 D 状态（不可中断睡眠），等的是磁盘或网络文件系统。CPU 确实闲着，但任务是「卡住」而不是「跑满」
df 说满了，du 找不到有隐藏目录，或者 du 算错了文件被删了，但还有进程握着句柄。目录项没了，inode 和数据块还在，空间不释放
端口 telnet 通，业务报错网络没问题，是应用 bug三次握手成功只证明「有人在这个端口 listen」。accept 队列满、后端超时、TLS 握手失败，都能在端口通的前提下发生
为什么先讲这三个：它们分别对应「指标误读」「工具盲区」「层次混淆」三类错误。面试里问「你怎么排查」时，能主动说出这三类陷阱的人，比背十条命令的人可信得多——因为这说明你真的被坑过。

这一篇的组织方式是：先给一套不会漏项的检查顺序，再按 CPU、内存、IO、磁盘、网络五条线各拆一层，最后收成一张决策树。每条线都落一句「面试怎么答」，因为这个专栏的目的是让你在 20 分钟里拿到能说出口的东西。

面试落点：这三类陷阱可以当开场白用。「我排查一般先确认现象属于哪一层，因为最常见的三种错误是指标误读、工具盲区和层次混淆」——说完这句，面试官就知道你不是在背命令清单。

模块 1

USE 方法与固定顺序：把「猜」变成「排除」

USE 是 Brendan Gregg 提出的一套检查方法：对每一个资源，看三件事——使用率（Utilization，忙的时间占比）、饱和度（Saturation，排队排到什么程度）、错误（Errors，有没有报错计数）。它真正的价值不是那三个英文单词，而是给你一张不会漏项的表。

使用率
资源忙的时间占比。它只回答「忙不忙」，不回答「排队没有」。80% 的使用率可能很健康，也可能已经在抖。
饱和度
排队有多长。CPU 看 run queue，磁盘看 aqu-sz，网络看 accept 队列。它比使用率更接近用户实际感受到的延迟。
错误
硬件、驱动、协议栈的错误计数。只要错误在增长，先处理错误，别去调性能参数——那是两件事。

为什么强调「不会漏项」？因为人在紧张时只看得见自己熟悉的东西。熟悉 MySQL 的人会先去翻慢查询，熟悉网络的人会先 tcpdump，结果查了四十分钟才发现是磁盘 inode 满了。固定顺序的作用，是替你抵抗这种偏好。

资源使用率 U饱和度 S错误 E
CPUtop 的 us/sy 之和、mpstat 单核vmstat 的 r 列、load/核数dmesg 里的 MCE、machine check
内存free 的 available、/proc/meminfovmstat 的 si/so、PSI 的 memory someOOM killer 记录、malloc 失败
磁盘 IOiostat -x 的 %util、实际吞吐aqu-sz（平均队列长度）、await/sys/block/*/device/ioerr_cnt、dmesg
存储空间df -h、df -i无（空间是硬上限，满了就是满了）No space left on device
网络sar -n DEV、ip -s link 的带宽accept 队列、conntrack 用量、ss 的 Send-Qnstat 的重传、drop、ListenOverflows

我自己的固定顺序

先圈影响面：一台机器还是整个集群？一个接口还是全部？几点开始的？这三个答案能把范围砍掉一半，而且不影响线上任何一个字节。
再看最近变更：发布、配置、扩容、证书、DNS。线上 80% 的突发故障和变更有关，先问「十分钟前动了什么」比先看指标快得多。
然后过 USE 表：从最可能的那一行开始，但每一行都要给一个结论——正常、异常、还是没数据。没数据本身就是一个发现。
收敛到进程：资源异常一定对应到某个 pid。找不到对应进程，说明问题在更下层（内核、驱动、虚拟化层）。
验证而不是宣布：改一个变量，看指标是否跟着动。改了没变化，说明你的假设是错的，回去重来——这一步最容易被跳过。
面试怎么答：「我不会一上来就 top。先用两分钟圈定影响面和最近变更，再按 USE 把 CPU、内存、IO、磁盘、网络过一遍，每一项都要落到具体进程。因为排查的本质是排除法，不是灵感。」
模块 2

CPU：load average 是被误读最多的指标

面试官问「load 高怎么办」，十个候选人里八个回答「加 CPU」。这个答案在一种情况下是对的，在另外三种情况下会让你把故障搞大。

先把语义说准：Linux 的 load average 统计的是处于可运行状态（R）和不可中断睡眠状态（D）的进程数，再对 1、5、15 分钟做指数衰减平均。它不是 CPU 使用率，也不是「CPU 队列长度」——后者是 Solaris / AIX 上的语义，很多人把两套东西记混了，一张嘴就露馅。

D 状态是什么？进程发起一次磁盘读、一次 NFS 调用、一次某些类型的块设备操作时，会进入「不可中断睡眠」，意思是它连信号都不响应，必须等内核把那件事做完。这时候进程占着 load，但不占 CPU。所以 load 高而 CPU 空闲，几乎可以断定有人在等 IO。

# 1. 先分清是「跑满」还是「卡住」
uptime                       # 例如 12.4 11.8 9.2：三个窗口都在涨，说明是持续性的
nproc                        # 8 核的话，load 12 已经排队 1.5 倍
vmstat 1 5                   # 关键看 r（可运行）、b（D 状态）、wa、si/so

# 2. 如果 b 列一直大于 0、wa 高，去 IO 线看
ps -eo stat,pid,ppid,wchan:24,comm | awk '$1 ~ /^D/'    # 谁在 D，卡在哪个内核函数
iostat -x 1 3

# 3. 如果 r 列远大于核数，CPU 真的不够或有人在空转
mpstat -P ALL 1 3            # 看是全部打满，还是某一个核打满
pidstat -u 1 5               # 落到进程：%usr 高还是 %system 高
perf top -p $(pgrep -f java | head -1)   # 看热点函数，需要 perf 和调试符号

单核打满是个特别常见的坑。一个单线程的 Python 服务、一个只有一条 Reactor 线程的旧网关、一个 GC 线程受限的 JVM，都能把 8 核机器里的 1 个核吃到 100%，整体 CPU 看着只有 12%，但延迟已经崩了。mpstat -P ALL 一眼就能看出来，而 top 的默认汇总视图会把它平均掉。

现象大概率的原因下一步
%us 高、%sy 低应用自己在算：死循环、正则回溯、大 JSON 序列化、GCpidstat -u 找进程 → perf top 找函数 → 线程栈（jstack / py-spy）
%sy 高系统调用太频繁、锁竞争、上下文切换多vmstat 看 cs 和 in；pidstat -w 看自愿/非自愿切换；strace -c 统计调用
%wa 高等磁盘或网络文件系统直接转 IO 线，不要在 CPU 上花时间
%si 高软中断：网卡收包压力大cat /proc/softirqs 看 NET_RX；考虑多队列、RPS、减少小包
%st 高宿主机把 CPU 抢走了（你在虚机/容器里）这不是你的问题，找平台方要资源或换规格
别急着调优先级。有人一见 load 高就 renice 或把进程绑核，这只是在挪排队顺序，吞吐不会变好，还可能把另一个服务拖慢。先定位是「算得太多」还是「等得太久」，这两种的处理方向完全相反。

面试落点：「load 高我先看 vmstat 的 b 列和 wa。如果 b 大于 0、CPU 空闲，那是 D 状态进程在等 IO，加 CPU 一点用没有；如果 r 远大于核数、us 高，那才是真的算不过来。判断完再决定是优化代码、加副本，还是查磁盘。」

模块 3

内存：free 那一列不是「可用内存」

「内存只剩 200M 了，快挂了」——这句话每天在无数群里出现，其中大部分是误判。Linux 会把空闲内存拿去做 page cache，这是设计，不是故障。

free -h 的 free 列是「完全没被用过的内存」，buff/cache 是「用来缓存文件数据、但随时可以回收的内存」，available 才是「在不触发换页的前提下，大概还能申请到多少」。判断内存够不够，只看 available。

# 看 available，不看 free
free -h
#               total        used        free      shared  buff/cache   available
# Mem:           15Gi       9.1Gi       210Mi       380Mi       6.2Gi       5.8Gi

# 真正的换页信号：si/so 持续不为 0
vmstat 1 5                   # si=从 swap 读入, so=写入 swap，长期大于 0 才叫在换页

# 拆开看内存都被谁占了
grep -E 'MemTotal|MemAvailable|^Cached|^Dirty|^Writeback|^Slab|^SReclaimable|^AnonPages' /proc/meminfo

# 找内存大户（RSS 会把共享库重复计算，PSS 更准）
ps -eo rss,pid,comm --sort=-rss | head -10
smem -tk 2>/dev/null | tail -5

几个必须分清的判断：

  • buff/cache 大不是问题。它会在别人需要内存时被回收。真正不可回收的是 Dirty（还没落盘的脏页）和内核的不可回收 slab，这两块突然变大才值得警惕。
  • si/so 是换页，不是 swap 使用量。swap 里躺着 2G 数据但 si/so 为 0，说明那是很早以前换出去的冷页，不影响性能；反过来 swap 只用了 200M 但 si/so 一直在跳，说明系统在反复颠簸（thrashing），这比 OOM 更难受——它不杀进程，只是让一切变慢。
  • RSS 会被高估。多个进程映射同一个 so 或同一份 mmap 文件时，RSS 会各算一遍。要准确看 PSS（smem 或 /proc/PID/smaps_rollup）。

OOM killer：它不是随机杀人

内存真的不够时，内核会挑一个进程杀掉。挑选依据是 oom_score，用户可以用 oom_score_adj（范围 -1000 到 1000）调整权重，-1000 表示「尽量别杀我」。注意 adj 是 bias 不是绝对优先级，把它设成 -1000 也不能保证一定不被杀。

# 谁被杀了、杀了多大
dmesg -T | grep -i -E 'killed process|out of memory'
journalctl -k --since "1 hour ago" | grep -i oom

# 容器场景：cgroup 级 OOM 先发生，宿主机看不到全局 OOM
cat /sys/fs/cgroup/memory.max                      # cgroup v2
cat /sys/fs/cgroup/memory.events                   # 看 oom / oom_kill 计数

# 调整某个进程的权重（-1000 ~ 1000）
echo -500 > /proc/$(pgrep -f myapp)/oom_score_adj
线上别 echo 3 > /proc/sys/vm/drop_caches。它会把 page cache 全清掉，接下来所有读请求都打回磁盘，延迟瞬间抬高，而且缓存很快又会被填满——你只是制造了一次抖动，什么也没解决。要验证「是不是缓存导致内存高」，看 available 就够了。

面试落点：「判断内存够不够看 available，不看 free。buff/cache 是可回收的，free 小是正常的。真正的危险信号是 si/so 持续非 0（在颠簸），或者 dmesg 里出现 oom-killer。容器里还要看 cgroup 的 memory.max 和 memory.events，因为容器 OOM 常常不体现在宿主机层面。」

模块 4

IO：await、util、aqu-sz 三个数怎么一起读

磁盘这条线最容易「看错数」。因为 iostat 输出的列名很像，含义却差很远；更麻烦的是，同一个 %util，在机械盘和 NVMe 上代表的含义完全不同。

# -x 出扩展指标，1 秒一次，共 5 次
iostat -x 1 5
# Device  r/s   rkB/s  r_await  w/s   wkB/s  w_await  aqu-sz  %util
# sda    120   4800.0     1.20  860  34000.0    18.60    8.42   99.8

# 老版本 sysstat 里这一列叫 avgqu-sz，新版本叫 aqu-sz，是同一个东西
# 压力更大时用 PSI 看「有多少时间在等 IO」
cat /proc/pressure/io
指标它到底在说什么怎么用
await一个 IO 从提交到完成平均花了多少毫秒，包含排队时间和业务延迟对比。await 涨、吞吐不涨，就是排队了
r_await / w_await读写分开的 await写慢多半是 fsync 或日志盘；读慢可能是缓存没命中
aqu-sz平均有多少个 IO 在队列里等持续大于 1~2 说明设备处理不过来，是饱和度最直接的证据
%util设备「有 IO 在处理」的时间占比机械盘接近 100% 基本等于饱和；NVMe/RAID 因为能并行，100% 也可能还有余量
svctm老版本里的服务时间官方早已标注不可信，新版本已移除，别拿它下结论

为什么 %util 会误导？它的算法大致是「设备忙的累计时间 / 总时间」。一块能同时处理几十个请求的 NVMe，只要一直有请求在飞，这个比例就会贴着 100%，但它其实还能再塞更多。这时候该看的是 await 有没有随着并发上升而变长——变长了才是真饱和，没变长说明还在线性区。

定位到进程只有一条路：找 D 状态。

# 谁在等 IO，等在内核的哪个函数上
ps -eo stat,pid,ppid,wchan:28,comm | awk '$1 ~ /^D/'
cat /proc/12345/stack 2>/dev/null      # 需要 root，能看到内核调用栈

# 按进程看实际读写量（-o 只显示有 IO 的，-P 按进程，-a 累计）
iotop -oPa

# 块层视角：谁在发 IO、发多大、合并情况
cat /proc/diskstats
blktrace -d /dev/sda -o - | blkparse -i -   # 需要装 blktrace，开销不小，短时间用
文件系统层和块设备层不是一回事。iostat 看的是块设备，一次 4K 随机写可能在文件系统层被日志、extent 分配放大成好几次 IO；反过来，page cache 命中时应用觉得「写完了」，iostat 上什么也看不到。所以「应用慢但 iostat 很闲」是成立的，这时候要看 fsync 次数和文件系统日志，而不是怀疑 iostat 坏了。

面试落点：「我先看 aqu-sz 和 await，再看 %util。%util 对能并行的 SSD 会高估饱和度，所以我更信『await 随并发上升而变长』这个信号。定位到进程之后看 wchan，能知道它是卡在文件读写、fsync 还是网络文件系统上。」

模块 5

磁盘：df 和 du 打架，多半是句柄没放

这是运维面试的保留曲目：「df 显示磁盘满了，du 加起来只有一半，为什么？」答不上来，说明你没在真实环境里删过日志。

机制很简单：Linux 里文件名是目录项，指向 inode，inode 再指向数据块。删一个文件，只是把目录项摘掉、把 inode 的链接计数减一；只要还有进程握着这个文件的句柄（fd），链接计数就不为 0，数据块不会释放。于是 df 按「已分配块」算，空间还是满的；du 按「目录树」遍历，根本看不到这个文件。

# 1. 确认是「块满了」还是「inode 满了」——两者报错一样，原因完全不同
df -h
df -i

# 2. 找已删除但仍被打开的文件（link count = 0）
lsof +L1
# COMMAND  PID USER   FD   TYPE DEVICE   SIZE NLINK   NAME
# nginx   8123 root    5w   REG  253,0  18.4G     0 /var/log/nginx/access.log (deleted)

# 没有 lsof 时的兜底：直接翻 fd 目录
find /proc/*/fd -ls 2>/dev/null | grep deleted | head

# 3. 处理：让进程重新打开文件，而不是删了再删
#    正确姿势1：truncate 文件（如果路径还在）
: > /var/log/nginx/access.log
#    正确姿势2：reload/restart 进程，让它重新打开
nginx -s reopen
别用 rm 处理正在写的日志。rm 摘掉目录项，进程还握着 fd，空间一点不还，你会在十分钟后再收到一次「磁盘满」。要么用 : > file 截断，要么让进程 reopen。日志轮转配置里的 copytruncate 就是为这个场景准备的（代价是复制期间可能丢几行）。

inode 满：另一种「没空间」

报错同样是 No space left on device，但 df -h 显示还有一半空间——因为 inode 用完了。典型制造者：session 文件、邮件队列、缓存小文件、跑飞的临时文件。df -i 的 IUse% 会直接告诉你。找凶手用「按目录数文件」：

# 当前目录下每个子目录的文件数，从多到少
for d in */; do echo "$(find "$d" -xdev | wc -l)  $d"; done | sort -rn | head

# du 不要跨文件系统，否则挂载点会被重复统计
du -x -h --max-depth=1 / | sort -h | tail -10

# ext4 默认给 root 保留 5% 空间，纯数据盘可以调小
tune2fs -m 1 /dev/sdb1

还有一个常被忽略的点：磁盘满会让一切变慢，而不只是写失败。ext4 在空间紧张时分配策略退化，日志写入可能阻塞，数据库直接进入只读或者报错。所以「还剩 2%」就已经是故障状态了，容量告警应该设在 80%~85%，而不是 95%。

面试落点：「df 和 du 不一致，我第一反应是文件被删但句柄没释放，用 lsof +L1 确认，然后 truncate 或让进程 reopen。同时我会先 df -i 排除 inode 满，因为这两种情况报错文案一样，但处理方式完全不同。」

模块 6

网络：ss 的三个数就够判断大半

网络排查在单机上不需要上来就 tcpdump。先用 ss 看三件事：监听在不在、连接堆在哪、队列堵不堵。这三个看完了，八成问题已经有方向。

# 总览：各状态各有多少
ss -s

# 谁在监听哪个端口（-l listen, -n 数字, -t tcp, -p 进程）
ss -lntp

# 当前连接状态分布，按状态聚合
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn

# 只看某状态的连接（注意 state 后面接的是内核里的状态名）
ss -tan state established '( sport = :8080 )' | wc -l
ss -tan state time-wait | wc -l
你看到的含义该查什么
LISTEN 的 Recv-Q已经完成三次握手、但应用还没 accept 的连接数把它和 Send-Q（backlog 上限）比。贴近上限就是 accept 太慢
LISTEN 的 Send-Qlisten backlog 的上限值应用层 backlog 与内核 somaxconn 取小值，两边都要够
ESTAB 的 Recv-Q内核收到了但应用还没读走的字节数持续很大说明应用读得慢，是应用层问题
ESTAB 的 Send-Q已发出但还没被对端确认的字节数持续很大说明对端收得慢或链路拥塞
大量 CLOSE_WAIT对端关了，本端没调 close代码 bug（连接泄漏），不是内核参数问题

accept 队列溢出是最隐蔽的一类：客户端看到的是「连接超时」，服务端 ss 里看不出任何异常，因为连接压根没被建立到应用层。它记在计数器里：

# 半连接/全连接队列溢出、重传、丢包，都在这
nstat -az | grep -i -E 'ListenOverflows|ListenDrops|RetransSegs|TCPTimeouts'
netstat -s | grep -i -E 'listen|retrans'

# 网卡层面的丢包与错误
ip -s link show eth0
ethtool -S eth0 | grep -i -E 'drop|err|miss|fifo'

# conntrack 表满会静默丢包，dmesg 里有 nf_conntrack: table full
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max
分层再记一遍：链路（网线/网卡）→ IP（路由/防火墙）→ 端口（listen/队列）→ 协议（重传/MTU）→ 应用（超时/序列化）。ping 通只覆盖到 IP 层，telnet 通只覆盖到端口层，两者都通而业务失败，问题一定在上面两层。

面试落点：「我先 ss -lntp 确认监听，再看 ss -s 的状态分布和 Recv-Q，然后查 nstat 的 ListenOverflows 和重传。ping 通不等于没问题，它只证明 ICMP 那一层通。」

模块 7

进程与系统调用：把「慢」翻译成具体的等待

前面五条线最终都要落到一个进程上。ps 只告诉你它在不在，/proc 和 strace 才告诉你它在等什么。

状态含义排查意义
R正在运行或可运行很多 R 且核数不够，才是 CPU 瓶颈
S可中断睡眠，等事件正常。睡在 epoll_wait 上的服务大部分时间是 S
D不可中断睡眠等 IO。连 kill -9 都要等它醒过来
T被 SIGSTOP 停住有人调试或用 kill -STOP 冻过
Z僵尸，已退出但父进程没 wait占 pid 不占资源，多了会耗尽 pid
I内核线程的空闲态（较新内核）不占 load，别把它当成异常
# 进程的完整画像：内存、线程数、上下文切换、fd 用量
cat /proc/12345/status | grep -E 'State|VmRSS|Threads|voluntary'
cat /proc/12345/limits | grep -E 'open files|processes'
ls /proc/12345/fd | wc -l

# 它打开了哪些文件、哪个端口
lsof -p 12345 | head -30
lsof -i :8080

# 线程视图：哪个线程在吃 CPU
top -H -p 12345
ps -L -p 12345 -o tid,stat,pcpu,comm | sort -k3 -rn | head

strace 是「翻译器」：它把进程的每一次系统调用打出来，你能直接看到它在 read 上等了 3 秒，或者在疯狂 stat 同一个不存在的路径。

# 统计模式：哪些系统调用最耗时、失败最多——先看这个，开销相对可控
strace -c -p 12345
# % time     seconds  usecs/call     calls    errors syscall
#  92.31    8.421000      4210.5      2000           futex

# 跟踪模式：带时间戳、带耗时、跟子进程
strace -f -tt -T -p 12345 -e trace=network,file
# 只盯某个调用，减少噪音
strace -f -T -e trace=connect,recvfrom -s 200 -p 12345
strace 是靠 ptrace 让目标进程停下来的，开销可能是几倍到几十倍。在生产核心进程上直接挂，等于自己制造一次故障。要挂就限时间（timeout 10 strace ...）、限调用（-e trace=）、先挑一台流量小的实例。面试里主动说出这个限制，比背参数加分。

还有一类「慢」是 fd 泄漏：进程 ls /proc/PID/fd | wc -l 一路涨到 limits 里的上限，然后开始报 Too many open files。ulimit -n 只影响当前 shell 及其子进程，systemd 起的服务要改 unit 里的 LimitNOFILE，这是很多人改了没生效的原因。

面试落点：「应用慢的时候我会看它在哪个状态。S 是正常的等事件，D 是等 IO，R 多才是 CPU 不够。然后用 /proc/PID 看线程数、fd 用量和 limits，最后才上 strace，而且会限时间和限调用范围。」

模块 8

内核日志：OOM、hung task、丢包都在这里留了证据

应用日志告诉你「它认为自己出了什么问题」，内核日志告诉你「内核替它做了什么决定」。很多「莫名其妙重启」「莫名丢连接」，答案只在 dmesg 里。

# -T 把单调时钟换算成人类时间（注意：休眠/时钟调整后可能对不准）
dmesg -T | tail -50
dmesg -T -l err,warn | tail -50          # 只看错误和警告级别

# systemd 系统上，内核日志也在 journal 里，好处是能按时间窗过滤
journalctl -k -p err --since "30 min ago"
journalctl --since "2026-10-21 02:00" --until "2026-10-21 02:30" -p warning

# 关键字搜索：这几类信息值得记住长相
dmesg -T | grep -i -E 'oom|killed process|hung task|soft lockup|call trace'
日志长相含义处置方向
Out of memory: Killed processOOM killer 动手了，后面会带 pid、进程名和总虚拟内存看是谁吃了内存、有没有 limit、是不是泄漏
blocked for more than 120 secondshung task：某进程在 D 状态超过阈值（默认 120s）基本等于存储或驱动卡死，查内核栈和硬件
BUG: soft lockup某个 CPU 在内核态长时间不让出驱动 bug 或内核 bug，看调用栈，考虑升级内核
nf_conntrack: table full连接跟踪表满，新连接被丢调大 max 或缩短 established 超时，先确认为什么连接这么多
TCP: too many orphaned sockets孤儿连接太多，内存压力查短连接、TIME_WAIT 复用、tcp_max_orphans
mce / EDAC / I/O error硬件层错误：内存位翻转、磁盘坏道换硬件，别在软件层兜圈子

有个现实问题：dmesg 是环形缓冲区，量大了会覆盖。默认大小通常只有几百 KB，高频报错几分钟就能把最早的证据冲掉。如果你要事后复盘，得确认 kernel.printk 和 rsyslog/journald 有没有把 kern 日志落盘，而不是等出事了再敲 dmesg。

一个习惯：处理完任何一次故障，把当时的 dmesg -T | tail -100 和 journalctl -k --since 存一份到工单里。三个月后再出同类问题，这份日志比你的记忆可靠得多。

面试落点：「应用无故重启，我会先看 dmesg 里有没有 oom-killer 和 hung task。这两个是内核替应用做的决定，应用自己的日志里通常什么都没有。」

模块 10

9 个坑：面试官最爱在这里追问

下面这些不是知识错误，是判断错误。它们的共同点是：动作很快，方向错了，在线上会直接放大故障。

1
load 高就加 CPU
load 里含 D 状态进程。IO 卡住时 load 能到几十，CPU 却闲得发慌。加机器只会让更多进程一起去等同一块磁盘。
2
看 free 的 free 列判断内存不足
那一列是「完全没用过的内存」。Linux 主动拿空闲内存做 page cache，free 接近 0 是常态。要看 available。
3
觉得 buff/cache 大就 drop_caches
缓存是可回收的，清掉只会让后续读请求打回磁盘，制造一次延迟抖动，几分钟后缓存又长回来。问题一点没解决。
4
df 满了就 rm 正在写的日志
文件被删但句柄还在，空间不释放。十分钟后你会收到第二张工单。正确做法是 truncate 或让进程 reopen。
5
%util 100% 就断定磁盘到极限
这个指标对能并行的 SSD/NVMe 会高估饱和度。更可靠的信号是 await 随并发上升而变长、aqu-sz 持续大于 1。
6
直接在生产核心进程上挂 strace
ptrace 会让目标进程反复停下来，开销可能几倍到几十倍，一次排查变成一次事故。要限时间、限调用、挑低流量实例。
7
ping 通就说网络没问题
ICMP 通只证明到 IP 层。端口没监听、accept 队列满、TLS 握手失败，全都能在 ping 通的前提下发生。
8
CLOSE_WAIT 多去调内核参数
CLOSE_WAIT 是「对端关了、本端没 close」，这是应用没释放连接，改 tcp_fin_timeout 之类完全无效。TIME_WAIT 多才是主动关闭 + 短连接。
9
先重启再说
重启会把现场（D 状态进程、fd、内核日志中的计数）全部抹掉。除非影响面在扩大且没有其他止血手段，否则先留证据再动手。

面试落点：「你踩过什么坑」这类问题，答一个具体的、有前后因果的就够了。比如「我用 rm 删过一次正在写的 access.log，df 一点没降，后来才知道是句柄没释放」——比罗列五个坑名可信得多，因为它带着你当时的错误判断。

自测

六道题

1. 8 核机器 load average 是 12，top 显示 CPU 使用率 8%，%wa 也不高。最可能的情况是？
正确答案：D 状态进程堆积。Linux 的 load 统计「可运行 + 不可中断睡眠」的进程数，D 状态进程等 IO 时既不占 CPU 也照样计入 load，所以会出现 load 高、CPU 闲的组合。换页会体现在 si/so 和 %wa 上，与题干的「%wa 也不高」不符。
2. 判断一台机器内存是否紧张，应该看 free -h 的哪一列？
正确答案：available。free 列只是「完全没被用过」的内存，Linux 会主动把空闲内存用作 page cache，所以 free 很小是正常的；buff/cache 大部分可回收；available 才是内核给出的「还能用多少」的估算。
3. df -h 显示磁盘 100%，但 du -sh /* 加起来只有一半。下一步最该做什么？
正确答案：lsof +L1。文件被删除后，只要还有进程握着 fd，inode 和与其链接的数据块就不会释放：df 按已分配块统计仍然满，du 遍历目录树看不到它。确认后 truncate 该文件或让进程 reopen，而不是重启。
4. iostat -x 显示某 NVMe 盘 %util 长期 99%，但业务延迟没有明显变化。应该怎么判断？
正确答案：看 await 和 aqu-sz。%util 近似等于「有 IO 在处理的时间占比」，能并行的 SSD/NVMe 只要一直有请求在飞就会贴着 100%，并不代表没有余量。真正的饱和信号是排队变长、await 上升、吞吐不再增长。
5. 写文件时报 No space left on device，但 df -h 显示还有 40% 空闲。最可能的原因是？
正确答案：inode 耗尽。块空间和 inode 是两套独立资源，海量小文件（session、缓存、邮件队列）会把 inode 用光，报错文案和空间不足完全一样。用 df -i 一眼确认，然后再去找是哪个目录在制造小文件。
6. 服务端 ss -s 显示大量 CLOSE_WAIT，正确的判断是？
正确答案：应用没 close。CLOSE_WAIT 表示本端收到了对端的 FIN、回了 ACK，但应用始终没有调用 close，所以停在这个状态不动。它和内核参数基本无关，堆得越多说明泄漏越严重。TIME_WAIT 才是主动关闭方的正常状态。
