Ansible 与自动化运维：怎么讲才像做过

会写 playbook 不值钱，值钱的是你知道幂等和收敛在哪个环节被破坏。

读之前先答一句：你的 playbook 跑第二遍，凭什么结果和第一遍一样？
开始前

三个现场：playbook 都跑绿了，机器却没变成你想要的样子

「我明明改了默认值，怎么还是老端口？」「第二次跑，全部 changed，可我什么都没改。」「改了 nginx 配置，重启没生效，我问了半天才发现 handler 压根没被通知。」这三句话的共同点是——Ansible 没有报错，它只是诚实执行了你写的东西。而写的人以为自己在声明「期望状态」，实际上写的是一串动作。

现场直觉答案真实原因
改了 defaults/main.yml，端口没变Ansible 缓存了变量同一个变量在 group_vars/ 或 -e 里被赋过值，defaults 是优先级最低的一档，从来没机会生效
第二次跑还是 changed机器有问题，配置没落下去任务用的是 command/shell，模块不知道什么叫「已经是这个状态」，所以永远报 changed；至于配置落没落，取决于命令本身
改配置没重启handler 写错了handler 只在通知它的任务报告 changed 时才排入队列。如果那个任务第二次跑没变化（比如用了 command 但状态其实没变、或者文件本来就一样），handler 不会被触发
无 agent
靠 SSH（或 WinRM、本地、容器连接插件）执行，被管机器上不需要常驻进程。这既是它的最大优点，也决定了它没有「持续收敛」能力：跑完就结束，下一次之前机器可以随便被改。
模块负责幂等
幂等不是 Ansible 这个框架给你的，是模块给你的。copy 会先算校验和，command 什么都不会算。用错模块，幂等就没了。
变量决定不确定性
同样的代码在不同 inventory、不同 -e 下行为完全不同。22 级优先级不是要你背，是要你知道「改了没生效」该往哪查。

这一篇的组织方式是：先说面试官为什么爱问（他要量化你的自动化能力），再把核心概念和幂等语义讲准，然后是变量优先级、目录结构、三个真实运维任务、Vault，最后是和 Shell、Terraform 的分工，以及排障命令。每一节都落一句能直接说出口的话。

先把一个最常见的错误说法纠正掉：「Ansible 是声明式的，所以它是幂等的」——这句话不成立。Ansible 的执行模型是按序执行 task 列表，每个 task 调一个模块；幂等性来自模块自己实现的「先检查、再动手」逻辑。所以「幂等」是一个逐模块成立、逐模块失效的属性，不是全局保证。

面试怎么答：「我用 Ansible 主要做三件事——批量配置下发、滚动重启这类有顺序的变更、以及新机器的初始化。我判断一个 playbook 是不是靠谱，看两点：跑第二遍是不是全 ok 零 changed；以及 --check --diff 能不能提前看出它要动哪些文件。这两点做不到，说明里面有模块用错了或者变量没收敛。」

模块 1

为什么面试官爱问：他要的是「量化你的自动化能力」

「你会 Ansible 吗」这个问题几乎没有区分度，因为答「会」的人里，有写过三个 task 的，也有一千台机器的配置全在里面的。面试官真正想问的是三件事：你管过多大范围、你的改动怎么被验证、出问题你怎么回滚。这三个答案里只要有一个是具体的数字和流程，你就和「写过 playbook」的人分开了。

他其实在问答不上来的样子能得分的样子
规模「几百台吧」「三个环境共 N 台，按 role 分组，inventory 按业务线和环境两层组织，日常变更一次影响 20~50 台」
验证「跑完看结果」「先 --syntax-check 和 ansible-lint，再 --check --diff 看要改哪些文件，灰度一组，确认后全量」
回滚「改回去再跑一次」「配置是模板渲染的，回滚就是改变量或回退 Git 提交再跑一遍；涉及版本升级的用 serial 分批，出问题用 --limit 只修那几台」
幂等「Ansible 是幂等的」「模块层面幂等。command 必须配 creates/changed_when，否则每次都报 changed，handler 也会被误触发」

有一个很好用的自我检查：你能不能在三十秒内说出「上一次线上用 Ansible 做的变更是什么、影响了多少台、怎么验证的」。说不出来，面试官基本会判定你是「照着文档写过 demo」。所以这一篇里所有的技术点，最好都挂到一个你自己的例子上——哪怕例子很小（比如「我用它把 60 台机器的 logrotate 配置统一了」），也比空谈体系可信。

另一个常被追问的角度是「为什么不用 Shell 脚本」。这个问题后面有一节专门讲，这里先给结论：脚本解决「做一次」，Ansible 解决「随时可以再做一次，并且结果一样」。真正的差别不在语法，在状态检查和报告——Ansible 会告诉你每台机器是 changed 还是 ok、失败在哪一步，脚本要靠你自己 echo。

一个可以立刻补上的短板：准备好一句话讲清你的目录结构。「我们的 playbook 按角色拆，每个角色一个 Git 仓库或者一个目录，公共变量放 group_vars，环境差异用 inventory 区分，密钥用 ansible-vault 加密，CI 里跑 lint 和 check，apply 需要审批」——这句话里每一个逗号后面都可能被追问，但都答得上来，你就稳了。

面试怎么答：「我理解面试官问 Ansible，其实是在问自动化的成熟度。我会先说规模和结构，再说验证和回滚流程，最后说我认为最容易出问题的地方——幂等被 command 模块破坏、变量优先级导致的环境差异、以及 handler 没被触发导致改了配置没重启。这三件事我都在实际变更里遇到过。」

模块 2

核心概念：六个词，每个都对应一类问题

Ansible 的概念不算多，但每个概念都对应一类具体的故障。inventory 决定你改了谁，play 决定你做什么，role 决定怎么复用，module 决定幂不幂等，fact 决定分支判断的可靠性，handler 决定收尾动作什么时候执行。把它们和故障对上号，比背定义有用。

概念它是什么它对应的典型故障
inventory主机清单，可以是 INI/YAML 静态文件，也可以是动态脚本或插件（从云 API 拉）改错环境：以为在改 staging，其实 limit 没加，改了生产；动态 inventory 拉回来的机器比预期多
play一次「对哪批主机、执行哪组任务」的绑定，一个 playbook 里可以有多个 play变量作用域混乱：在 A play 里定义的 vars 在 B play 里不存在
role可复用的任务集合，带固定的目录结构变量被覆盖（defaults vs vars）、handler 名冲突、角色之间互相依赖没在 meta 里声明
module真正干活的最小单元，在远端执行并返回 JSON用了不幂等的模块（command/shell/raw）导致每次 changed；模块参数写错导致「跑绿了但没生效」
factAnsible 自动采集的主机信息（OS、IP、内存、磁盘、网卡…），也能自定义关掉 gather_facts 之后还在用 ansible_distribution，条件判断永远为假
handler被 notify 触发的收尾任务（典型是重启服务），默认在 play 末尾执行一次改了配置没重启；或者反过来，每次都重启（因为通知它的任务永远报 changed）

fact 的采集方式要说清楚，因为它经常被误解：Ansible 在目标机上执行一段采集脚本（不是靠读本地缓存），把结果作为变量注入。所以采集是有成本的——几百台机器、每台几十个 fact，光采集就要一段时间；可以用 gather_subset 只采需要的部分，或者开 fact cache（fact_caching，可选 jsonfile、redis、memcached 等后端，具体配置以你版本的文档为准）。

自定义 fact 有两条路：把静态文件放到 /etc/ansible/facts.d/*.fact（INI 或 JSON），或者用 set_fact 在运行时算出来。区别很重要——set_fact 的结果只在本次运行有效（除非开了 fact cache），而 facts.d 里的文件是持久的、每次都会被采集。

# 看某个主机到底有哪些 fact（排障利器，别猜）
ansible web-01 -m setup -a 'filter=ansible_distribution*'
ansible web-01 -m setup -a 'gather_subset=network'

# 只采一部分，能明显缩短大批量执行的时间
- hosts: all
  gather_facts: true
  gather_subset: ["network", "virtual"]

# 关掉采集但要用 fact 时，必须自己补上
- hosts: all
  gather_facts: false
  tasks:
    - ansible.builtin.setup:
        gather_subset: ["distribution"]
      when: needed | default(true)

handler 的语义值得单独记三条：第一，只有报告 changed 的任务才会触发 notify，ok 和 skipped 都不触发；第二，handler 在 play 的末尾统一执行，同一个 handler 被 notify 多次也只跑一次；第三，如果 play 在 handler 执行前失败，handler 不会执行——除非你用 meta: flush_handlers 提前冲刷，或者配置了在失败时也执行的选项（具体开关名以你版本为准）。「改了配置但服务没重启」这类事故，八成是第一条。

「handler 没跑」和「handler 不该跑的时候跑了」同样危险。后者更隐蔽：如果通知它的是一个 shell 任务（永远 changed），那每次执行 playbook 都会重启一次服务——在几百台上跑一遍，等于自己制造了一次全站抖动。所以给 command/shell 配 changed_when 不只是为了报告好看，是为了不误触发下游动作。

面试怎么答：「六个概念我按故障来记：inventory 决定影响面，所以要习惯性加 --limit 和 --list-hosts 确认；module 决定幂等，command 类模块必须自己声明 changed_when；fact 是采集出来的，关掉 gather_facts 再用 fact 就会静默失效；handler 只在通知它的任务 changed 时才执行，且在 play 末尾跑一次。」

模块 3

幂等性：它不是框架给的，是模块给的

幂等的定义很朴素：同一个操作执行一次和执行多次，系统的最终状态相同。对应到 Ansible 的报告里，就是「第二次跑，全是 ok，没有 changed」。这一节要回答的问题是：这个属性到底由谁保证，以及在哪些环节会悄悄失效。

答案是模块。以 copy 为例，它并不是无脑把文件传过去：它先在目标机上算出现有文件的校验和（checksum），和源文件的校验和比较，一样就返回 changed=false 直接结束，不一样才传。template 同理，而且它还会先把 Jinja 渲染完再比。service 会先查服务的当前状态，已经 started 就不动。yum/apt/dnf 会先查包是否已安装及版本。

所以「幂等」的本质是模块内部有一段「读当前状态 → 比较 → 决定是否写」的逻辑。而 command、shell、raw 这三个模块没有这段逻辑——它们只是把命令交给远端执行，返回码为 0 就报 changed。你让它跑 echo，它也报 changed。

模块幂等吗怎么用才不出事
copy / template天然幂等（比 checksum）配置里不要塞时间戳、随机数、UUID，否则每次渲染结果都不同，永远 changed
file幂等（比 state、mode、owner）mode 要写字符串 "0644"；写成 0644 会被当八进制字面量处理，得到意外权限
lineinfile / blockinfile条件幂等必须给 regexp 才能可靠判断「已经改过了」；多行块用 blockinfile，它靠 marker 注释界定
yum / apt / pip幂等，但 state=latest 会每次升级生产环境锁版本：name=nginx-1.24.0 或 state=present + 显式版本号，否则每次跑都可能升到新版本
service幂等（比当前状态）state=restarted 一定会重启；只有 started/stopped 才是幂等的。要「只在配置变了才重启」，用 handler
command / shell / raw不幂等三选一：加 creates/removes；加 changed_when；换成有对应功能的专用模块
uri / wait_for不产生变更，用于探测配 until + retries + delay 做轮询，比 sleep 可靠
# 反例：每次都是 changed，还会误触发 handler
- name: 安装 agent
  ansible.builtin.shell: curl -s http://pkg/apt/install.sh | bash

# 正例 1：用 creates 表达「已经做过了就不做」
- name: 初始化数据目录
  ansible.builtin.command: /opt/app/bin/init --datadir /data/app
  args:
    creates: /data/app/initialized.flag

# 正例 2：自己判断状态，自己声明 changed
- name: 检查是否已是目标版本
  ansible.builtin.command: /opt/app/bin/version
  register: ver
  changed_when: false        # 这是个只读检查，永远不算改变

- name: 升级到目标版本
  ansible.builtin.command: /opt/app/bin/upgrade --to 2.4.1
  when: ver.stdout is version('2.4.1', '<')   # 注意 < 要转义

# 正例 3：模块已经把状态判断做完了，不要自己去 shell
- name: 确保 nginx 配置是最新的
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    validate: /usr/sbin/nginx -t -c %s    # 落盘前先校验语法，错了不写入
    mode: "0644"
  notify: reload nginx

validate 这个参数值得单独强调，它是「改配置类变更」最实用的一道保险：模块会先把渲染好的内容写到一个临时文件，用你给的命令去校验它，校验通过才覆盖目标文件。这样即使模板里的变量算错了、渲染出一个语法错误的配置，也不会把线上服务搞挂——任务直接失败，原文件不动。nginx 用 nginx -t -c %s，sshd 用 sshd -t -f %s，%s 是临时文件路径的占位符。

还有一个破坏幂等的隐蔽来源：模板里的内容不稳定。比如模板里写了 {{ ansible_date_time.iso8601 }}，或者引用了一个每次都重新生成的随机 token，或者 lookup('pipe', ...) 去调一个返回时间相关结果的命令。这类模板每次渲染结果都不同，copy/template 永远报 changed，然后 notify 的 handler 每次都重启——表现就是「我什么都没改，跑一遍全站重启了」。所以模板里只放确定的配置，动态值要么放变量、要么放环境变量/配置文件由应用自己生成。

「幂等」还有一个常被忽略的边界：它只保证终态一致，不保证过程无害。比如一个任务把文件内容从 A 改成 B，第二次跑时文件已经是 B，它不会动——这是幂等。但如果中途有人手工把文件改成了 C，第二次跑会把 C 覆盖成 B，这个「覆盖」是正确的、也是你意料之外的。所以幂等不等于「不会覆盖别人的改动」，它恰恰意味着「任何偏离都会被拉回来」，这也是为什么「Ansible 管的文件不要手工改」要写成团队规则。

批量执行时还有两个保护参数值得记住：serial 控制分批（可以写数字、百分比或列表），max_failure_percentage 控制「失败多少就中止」。没有这两个，一个写错的模板会在几秒内推到全部机器。

面试怎么答：「幂等是模块属性不是框架属性。copy、template、file、service 这类模块内部会先读当前状态再比较，所以天然幂等；command、shell、raw 没有这个逻辑，返回码 0 就报 changed，必须配 creates/removes 或 changed_when。我判断一个 playbook 是否真的幂等，就看它跑第二遍是不是零 changed。另外 state=latest 和 state=restarted 这两个写法会破坏收敛，生产要锁版本、要用 handler 而不是无条件重启。」

模块 4

变量优先级：22 级不是让你背，是让你知道往哪查

「我改了变量，为什么没生效？」这是 Ansible 最高频的问题，没有之一。答案永远是优先级：同一个名字在别的地方被赋了值，而且那个地方优先级更高。官方文档给出的顺序有 22 级，从低到高如下（具体条目以你使用的 ansible-core 版本文档为准，历次版本间这个顺序基本稳定）。

级来源什么时候会撞车
1命令行值（如 -u，严格说不是变量）最低。基本不会成为「改了没生效」的原因
2role defaults（defaults/main.yml）最容易被覆盖的一档。你在这里改端口，group_vars 里有个同名的就白改
3~7inventory 的 group vars → inventory group_vars/all → playbook group_vars/all → inventory group_vars/* → playbook group_vars/*playbook 的 group_vars 高于 inventory 的。同名变量放两处，生效的是 playbook 那份
8~10inventory 的 host vars → inventory host_vars/* → playbook host_vars/*host 级永远压过 group 级。想给某一台特殊配置，写 host_vars 就对了
11主机 fact / 缓存的 set_fact容易踩坑的一级：你的自定义变量如果和某个 fact 同名（比如 ansible_hostname），会被 fact 压掉
12~14play vars → vars_prompt → vars_filesplay 里 vars: 写的比所有 group_vars 都高，很多人以为它最低
15role vars（vars/main.yml）角色内部的第二坑：defaults 最低、vars 很高。想让使用者能覆盖，放 defaults；想锁死，放 vars
16~17block vars → task vars只在该 task 内生效，用于临时覆盖
18include_vars运行时动态加载，压过前面所有静态定义
19set_fact / register运行时算出来的值优先级很高，且在本次运行内持续有效
20~21role（含 include_role）参数 → include 参数调用角色时传的参数，能压过角色内部的 vars
22extra vars（-e）永远赢。不管你在哪写了什么，-e 最大

22 级记不住没关系，记住四条就够用：

defaults 最低，vars 很高，-e 最高。角色里想给默认值就放 defaults/，放 vars/ 等于告诉别人「别改」。
host 压过 group。「某一台不一样」就写 host_vars/主机名，不要靠 when 在任务里判断主机名——那种写法会让任务列表越来越脏。
runtime 压过 static。set_fact 和 include_vars 优先级远高于文件里的定义，所以「怎么改都不生效」时，先搜有没有同名的 set_fact。
playbook 的 group_vars 压过 inventory 的。同一个变量在两处都写了，生效的是 playbook 目录下那份。
# 排障第一步：不要猜，直接问 Ansible 这个值到底是多少
ansible web-01 -m debug -a 'var=nginx_port' --extra-vars '@prod.yml'

# 在 playbook 里把整个变量空间打出来看（信息量大，排障时才用）
- name: 打印当前主机的所有变量
  ansible.builtin.debug:
    var: hostvars[inventory_hostname]
  when: debug_vars | default(false)

# 看某个变量到底是从哪来的（-vvvv 的输出里会有 "variable ... from ..."）
ansible-playbook site.yml --limit web-01 -vvvv | grep -i 'nginx_port'
「用 -e 传环境差异」是个坏习惯，虽然它排在最顶级。因为 -e 赢过一切，它会掩盖你在 group_vars 里写的正确配置，而且这个值不在代码里、不进评审、不进 Git。三个月后有人问「生产为什么是这个端口」，答案可能在某个人的 shell 历史里。环境差异应该落在 inventory 的 group_vars 或者独立的 --extra-vars @env/prod.yml 文件里，并且这个文件要进版本控制。

还有两个和变量相关的坑。第一，变量名覆盖 fact。如果你定义了一个叫 ansible_user 或者 ansible_port 的变量，它和连接用的内置变量同名，行为会非常诡异。自定义变量尽量加前缀，比如 app_nginx_port。第二，hash_behaviour。默认情况下同名哈希变量在不同层级是替换而不是合并（该配置项可以改成合并，但官方不推荐，很多角色依赖替换语义）。所以「我在 defaults 里写了 5 个键，在 group_vars 里只想覆盖 1 个」——默认行为会把另外 4 个也丢掉。要么整体重写，要么把键拆成独立的扁平变量。

面试怎么答：「变量优先级官方是 22 级，我记四条实用的：defaults 最低、role vars 很高、-e 最高；host 压过 group；运行时（set_fact、include_vars）压过静态定义；playbook 的 group_vars 压过 inventory 的。排障时我不猜，直接用 debug 打印变量值，或者 -vvvv 看它 from 哪里。另外同名哈希默认是替换不是合并，这点很容易踩。」

模块 5

角色目录结构：每个目录对应一种意图

角色的目录不是随便分的，它其实在表达「什么东西应该被使用者改，什么东西不该」。看懂目录结构，就看懂了这个角色的契约。很多人写角色只写 tasks/，把文件、模板、变量全塞在一个目录里，结果就是无法复用、无法覆盖、无法看懂。

目录放什么关键性质
defaults/main.yml角色的默认变量优先级最低（第 2 级），任何人都能覆盖。所有「可以被改的默认值」都放这里
vars/main.yml角色内部固定变量优先级很高（第 15 级），压过 group_vars 和 play vars。放「不该被随便改」的常量
tasks/main.yml任务列表，可以 include 子文件执行顺序是从上到下，不要写一个依赖「某天会被重排」的列表
handlers/main.yml重启、reload 这类收尾动作按名字被 notify，同名只跑一次。名字要带角色前缀，避免冲突
templates/*.j2Jinja2 模板会被渲染。放配置模板，变量从 defaults 来
files/*静态文件不渲染，原样拷贝。放二进制、证书、脚本
meta/main.yml角色依赖（dependencies）、支持的平台依赖在这里声明才会被自动先执行；漏了就会「跑不起来但说不清为什么」
README.md角色用法与变量说明不是可选件。没有 README 的角色，三个月后没人敢改

为什么 defaults 和 vars 的区分这么重要？因为它直接决定这个角色好不好用。全部写进 vars/，使用者想改端口就只能 fork 一份代码；全部写进 defaults/，又会把一些不该被碰的内部常量暴露出去。一个实用的分法：凡是有可能在不同环境、不同业务线取值不同的，放 defaults；凡是由角色逻辑推导出来的、或者改了就会出错的，放 vars。

# 一个标准角色的目录树
roles/nginx/
├── defaults/main.yml      # nginx_port: 80, nginx_worker_processes: auto （可覆盖）
├── vars/main.yml          # nginx_pkg_name: nginx （平台推导出来的常量）
├── tasks/main.yml
├── tasks/install.yml
├── tasks/configure.yml
├── handlers/main.yml      # name: "nginx reload"
├── templates/nginx.conf.j2
├── files/50x.html
├── meta/main.yml          # dependencies: [common]
└── README.md

# meta/main.yml：依赖显式声明，否则顺序不可控
dependencies:
  - role: common
    vars:
      ntp_servers: ["10.0.0.1", "10.0.0.2"]

# handlers/main.yml：名字带前缀，避免和其他角色的 reload 冲突
- name: nginx reload
  ansible.builtin.service:
    name: nginx
    state: reloaded

handler 名冲突是个真实的坑：如果两个角色都定义了一个叫 restart service 的 handler，Ansible 里只有一个会生效（同名覆盖），你的 notify 可能触发的是另一个角色的动作。所以 handler 一律加前缀，比如 nginx reload、php-fpm restart。或者用 listen 指定一个主题名，多个任务订阅同一个主题。

还有一个实践细节：tasks/main.yml 不要写太长。常见拆法是按阶段拆文件（install.yml、configure.yml、service.yml），main.yml 里只做 include。好处不只是整洁——你可以用 --start-at-task 从某个阶段继续，也可以在某个阶段加 tag 单独执行。tag 的用法是 ansible-playbook site.yml --tags nginx_config，调试时非常省时间。

判断一个角色写得好不好，看三件事：① defaults/main.yml 里有没有把所有可调项列全，并且每项有注释；② 跑两遍是不是零 changed；③ handler 名有没有前缀、有没有只在真正需要时才触发。这三条满足，这个角色就可以进团队共享库了。不满足的话，它会成为下一个「没人敢碰的目录」。

面试怎么答：「角色目录我按『可变/不可变』理解：defaults 优先级最低，放所有允许被覆盖的默认值；vars 优先级很高，放角色内部的常量，写进去基本等于不让人改。templates 会渲染、files 原样拷贝，两者别混。meta 里声明依赖，否则执行顺序不可控。handler 名字要带角色前缀，因为同名 handler 会互相覆盖。tasks 我习惯按阶段拆文件并用 tag 标记，方便 --tags 单独跑某一部分。」

模块 6

三个典型运维任务：配置下发、滚动重启、密钥分发

面试官让你「说一个你做过的 Ansible 场景」，这三个是最能展开的。它们的共同要求是：能说清楚顺序、能说清楚失败会怎样、能说清楚怎么验证。

任务一：批量改配置

关键不是「把文件传过去」，是三条保险：渲染前校验（validate）、改了才重启（handler）、失败不扩散（serial / max_failure_percentage）。缺任何一条，这个变更都有把全站搞挂的可能。

- name: 下发 nginx 配置
  hosts: web
  serial: "20%"                     # 一次只动 20%，别一次推全量
  max_failure_percentage: 10        # 失败超 10% 就停
  tasks:
    - name: 渲染配置（落盘前先跑 nginx -t）
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
        owner: root
        group: root
        mode: "0644"
        validate: /usr/sbin/nginx -t -c %s
      notify: nginx reload

    - name: 等端口就绪（防止 reload 期间连接被拒）
      ansible.builtin.wait_for:
        port: 80
        timeout: 20

    - name: 抽查一个业务 URL
      ansible.builtin.uri:
        url: "http://{{ ansible_default_ipv4.address }}/health"
        status_code: 200
      retries: 5
      delay: 2
      delegate_to: localhost         # 从控制节点发起，模拟真实访问路径

  handlers:
    - name: nginx reload
      ansible.builtin.service:
        name: nginx
        state: reloaded

任务二：滚动重启

滚动重启的难点不是重启，是「什么时候可以动下一批」。顺序是：从负载均衡摘掉 → 等现有请求处理完 → 重启 → 等健康检查通过 → 放回。Ansible 里对应 serial 分批、wait_for 等端口、uri 探活。如果你的摘流量动作是调 API 或者改某个注册中心状态，那一步要用 uri 模块并且自己定义成功条件。

- name: 滚动重启应用
  hosts: app
  serial: 2                        # 或者写 ["10%", "30%", "100%"] 分三轮加大
  any_errors_fatal: true           # 第一批挂了就不再继续
  tasks:
    - name: 摘流量
      ansible.builtin.uri:
        url: "http://lb.internal/api/downstream/remove"
        method: POST
        body_format: json
        body: {host: "{{ inventory_hostname }}"}
        status_code: 200

    - name: 等存量请求排空
      ansible.builtin.wait_for:
        path: /var/log/app/access.log
        search_regex: 'idle'       # 更稳的是查应用的连接数指标，这里仅为示例
        timeout: 30
      ignore_errors: true          # 探不到不应该中断整个变更

    - name: 重启
      ansible.builtin.service:
        name: app
        state: restarted

    - name: 等健康检查通过
      ansible.builtin.uri:
        url: "http://{{ ansible_host }}:8080/health"
        status_code: 200
      register: health
      until: health.status == 200
      retries: 20
      delay: 3

任务三：密钥与证书分发

这一类的核心要求是「文件权限正确、过程不泄露、可轮换」。三个必须做的动作：目标文件 mode: "0600"（私钥 0400 或 0600，证书可以 0644）；任务加 no_log: true 防止值被打进输出；内容本身用 Vault 加密（下一节讲）。

- name: 分发 TLS 证书与私钥
  hosts: web
  tasks:
    - name: 写私钥
      ansible.builtin.copy:
        content: "{{ tls_private_key }}"
        dest: /etc/nginx/tls/server.key
        owner: root
        mode: "0600"
      no_log: true                 # 关键：不要把内容打进日志
      notify: nginx reload

    - name: 写证书
      ansible.builtin.copy:
        content: "{{ tls_certificate }}"
        dest: /etc/nginx/tls/server.crt
        mode: "0644"

    - name: 分发 SSH 公钥（给运维账号）
      ansible.posix.authorized_key:
        user: ops
        key: "{{ lookup('file', 'keys/ops.pub') }}"
        state: present
      # 慎用 exclusive: true —— 它会删掉该用户下所有不在列表里的 key
authorized_key 的 exclusive: true 是双向的。它保证「只有我列出的 key 存在」，也就意味着会删掉机器上其他所有 key——包括你自己手动加的、包括别人应急时加的。用它能做到「密钥治理」，用错它会把所有人锁在门外。用的前提是：这份 key 列表是唯一权威来源，且你有带外方式（控制台 VNC、ILO/IPMI）能救回来。

面试怎么答：「我做过的典型变更有三类。批量改配置用 template 加 validate，配置落盘前先跑 nginx -t，语法错了就不写入，然后靠 handler 只在内容变化时才 reload，分批用 serial 加 max_failure_percentage。滚动重启的关键是摘流量、等排空、重启、探活这个顺序，探活用 uri 配 until 轮询，不用 sleep。密钥分发必须设 0600 权限、任务加 no_log，内容用 Vault 加密。这三类的共同点是：每一步失败都知道会怎样，而且失败不会扩散到全部机器。」

模块 7

Vault 与密钥管理：加密的是静态存储，不是运行时

「我们把密码放在 ansible-vault 里，所以是安全的」——这句话只对了一半。Vault 解决的是静态存储：Git 里的文件是密文，clone 下来也看不懂。但它不解决运行时：执行 playbook 时，Ansible 必须用密码解密，解密后的明文就在内存里、在网络传输的模块参数里、在可能输出的内容里。

它防住什么它防不住什么
Git 仓库泄露时，密钥不会明文暴露有 vault 密码的人能看到所有密钥（所以密码本身的分发才是关键）
代码评审时敏感值不出现在 diff 里运行时内存里的明文、模块参数传输过程中的明文
满足「配置不落明文」的合规要求-vvvv 输出、任务回显、失败信息里打出来的明文
可以用不同 vault-id 分环境、分权限目标机上落盘的文件权限没设对（Vault 管不了 chmod）
# 1. 加密整个变量文件（最常用，适合一组相关密钥）
ansible-vault create group_vars/prod/vault.yml
ansible-vault edit   group_vars/prod/vault.yml
ansible-vault view   group_vars/prod/vault.yml
ansible-vault rekey  group_vars/prod/vault.yml      # 换密码，轮换时必做

# 2. 只加密一个字符串（适合往已有 yml 里插一个密钥）
ansible-vault encrypt_string --vault-id prod@prompt 'sup3r-secret' --name 'db_password'

# 3. 运行时提供密码：交互、文件、脚本三种
ansible-playbook site.yml --ask-vault-pass
ansible-playbook site.yml --vault-password-file ~/.vault_pass
ansible-playbook site.yml --vault-id prod@~/.vault_pass_prod

# 4. 加密后的文件长这样（可以直接提交到 Git）
# $ANSIBLE_VAULT;1.1;AES256
# 363834393362313036396536...

vault-id 是个被低估的用法。它让你可以用不同的密码加密不同环境的密钥：--vault-id prod@/path/prod.key --vault-id staging@/path/staging.key。好处是「管 staging 的人拿不到生产的密钥」，而且密文里带着 id，出错时报错信息会告诉你是哪个 id 的密码不对，而不是笼统地失败。

最重要的实践问题：vault 密码放哪？三个选项，安全性递增：① 放在 CI 的密钥管理里（如 CI 变量的 masked/protected 类型），由流水线注入环境变量或临时文件——这是最常用也够用的方案；② 放在专门的密钥管理系统里，运行时通过脚本拉取（--vault-id prod@./get-vault-pass.sh，脚本执行后输出密码到 stdout）；③ 本地开发用 --ask-vault-pass 手动输入。绝对不要做的是把密码文件提交到 Git，或者明文写进 ansible.cfg 的 vault_password_file 并跟着代码走。

两个必须做的配套动作：第一，所有处理密钥的任务加 no_log: true。Vault 只加密存储，一旦任务把变量值作为结果返回，-v 以上的输出里就是明文——包括任务失败时的报错信息。第二，别忘了目标机上的文件权限。copy 一份私钥过去，Vault 不会帮你设 0600，权限得自己写 mode。这两件事没做，Vault 等于只做了一半。

最后一个务实的判断：如果密钥量很大或者需要审计和自动轮换，Vault 不是最优解，应该上专门的密钥管理系统（HashiCorp Vault、云厂商的 KMS/Secrets Manager 等），Ansible 在运行时通过 lookup 插件或者 API 去取，取到的值只在内存里，不落 Git。Ansible Vault 的定位是「中小规模、静态配置、团队内部」够用的方案，它的优势是不引入新依赖。

面试怎么答：「Vault 解决的是静态存储加密——Git 里是密文、评审看不到明文，但它不解决运行时：执行时明文在内存里、在模块参数里、可能在输出里。所以配套必须做两件事：处理密钥的任务加 no_log，以及目标文件的 mode 要显式设成 0600。密码本身的分发才是关键，我放 CI 的密钥管理里由流水线注入，绝不能提交到 Git。多环境用 vault-id 分开，轮换用 rekey。如果密钥量大或者要审计和自动轮换，就上专门的密钥管理系统，Ansible 运行时去取。」

模块 8

和 Shell 脚本、Terraform 的分工：谁管什么

这类问题一定会被问，因为它考的是你对工具边界的判断，而不是会不会用。回答的核心是一句话：按「资源的生命周期归谁管」来划分，而不是按「哪个工具更熟」划分。

工具它擅长它不擅长判断依据
Shell 脚本一次性动作、胶水逻辑、本地工具链、在 Ansible 里被 module 调用批量状态管理。它没有「当前状态」的概念，也没有结构化报告只跑一次、不需要报告 → 脚本
Ansible已有机器上的配置管理：装包、下发配置、起服务、初始化、有顺序的批量变更资源编排。它不知道「这台机器是哪次创建的」，也没有依赖图和 plan 预览机器已经有了，要让它变成某个样子 → Ansible
Terraform基础设施的创建与销毁：VPC、子网、云主机、数据库实例、IAM、DNS 记录机器内部的配置。它有 state，但把 OS 层配置写进去会让 state 和现实迅速脱节东西还不存在，要把它造出来并可复现地销毁 → Terraform

和 Shell 的区别，最直观的是报告能力。脚本跑完，你只知道退出码；哪台成功哪台失败、哪台其实没变化，得自己 grep 输出。Ansible 每台机器都返回结构化的结果：ok / changed / failed / skipped / unreachable，还能用 --check 先看一遍要动什么。这个差别在 5 台机器上不明显，在 500 台上就是「能不能安全做事」的差别。

和 Terraform 的区别，关键在state 和收敛方式。Terraform 维护一份 state 记录「我创建了哪些资源、它们的 ID 是什么」，因此它能算出「现实和声明之间的差」，并且敢销毁。Ansible 没有这份跨运行的状态记录（fact cache 只是缓存，不是资源清单），它每次都重新读目标机的当前状态来判断要不要动——所以Ansible 不会帮你删东西，Terraform 会。这就是为什么「删除一台机器」是 Terraform 的事，而「把一台机器的配置改掉」是 Ansible 的事。

一个很常见的误用：用 Ansible 去创建云资源。技术上能做到（云厂商都提供 Ansible 模块），但问题是：创建出来的资源没有 state 记录，第二次跑靠什么判断「已经存在」？通常只能靠名字匹配，于是要么重复创建、要么因为找不到而失败。这类「资源生命周期」的问题，就该交给有 state 的工具。反过来，用 Terraform 的 remote-exec 去跑一堆 shell 配置机器，同样是把状态写进了不该写的地方——改一行配置就要跑一次 apply，而且 apply 失败时 state 可能已经半新半旧。

合理的组合方式是这样的：Terraform 建资源 → 输出机器的 IP/分组信息 → 生成或更新 Ansible inventory → Ansible 做配置和初始化 → 应用发布交给 CI/Helm。每一层只管自己有权威状态的部分，层与层之间用明确的产物交接（inventory 文件、镜像 tag、制品版本号）。

还有一条边界值得说清：Kubernetes 里的东西，尽量不用 Ansible 管。Pod、Deployment、ConfigMap 有自己的控制器在持续收敛，你用 Ansible apply 一份 manifest，下次有人 kubectl edit，两边就开始打架。K8s 资源的正确入口是 GitOps（Argo CD / Flux）或者 CI 里的 helm/kubectl，Ansible 应该只管集群之外的部分（节点初始化、containerd 配置、仓库证书）。

面试怎么答：「我按资源生命周期划分：资源还不存在、需要可复现地创建和销毁，用 Terraform，因为它有 state 能算差异；机器已经存在、要让它变成某个配置状态，用 Ansible，因为它每次读当前状态、不会帮你删东西；一次性动作和胶水逻辑用 Shell。三者串起来是：Terraform 建资源并产出 inventory，Ansible 做配置和应用初始化，容器内的发布交给 CI 和 GitOps。K8s 里的资源我不让 Ansible 管，因为控制器会持续收敛，两边同时写同一个对象一定会打架。」

模块 9

排障与调试：从「跑绿了但没生效」到定位

Ansible 的失败分三类：连接类（SSH 不通、权限不够、Python 找不到）、语义类（跑绿了但没生效，通常是变量或模块参数问题）、顺序类（handler 没跑、依赖没先执行）。每一类有不同的第一条命令，用错了就是在绕圈子。

现象第一反应用哪个命令

ansible-playbook site.yml --syntax-check
ansible-lint site.yml

# 2. 干跑：看它会改什么、改之前和之后差在哪（最重要的一条）
ansible-playbook site.yml --check --diff --limit web-01

# 3. 确认影响面：先列主机，再决定要不要 limit
ansible-playbook site.yml --list-hosts
ansible-playbook site.yml --list-tasks
ansible-playbook site.yml --list-tags

# 4. 连接类问题：-vvvv 会把 SSH 的每一步打出来
ansible web-01 -m ping -vvvv
ansible web-01 -m command -a 'id' -b -K -vvvv      # -K 提示输入 sudo 密码

# 5. 逐步执行 / 从某个任务继续（调试长 playbook 很省时间）
ansible-playbook site.yml --step
ansible-playbook site.yml --start-at-task "下发 nginx 配置"

# 6. 并发与超时：大批量时按机器数调
ansible-playbook site.yml --forks 20
ansible-playbook site.yml --timeout 30

--check --diff 是本节的头号命令，但要清醒地知道它的边界：它只对支持 check mode 的模块有效。copy、template、file 这类会正常报告「要不要改」以及 diff；而 command、shell、raw 在 check mode 下默认被跳过（因为它们不支持），你看到的是「skipped」，不是「它会做什么」。所以如果你的 playbook 主体是 shell 命令，--check 基本不提供信息——这本身就是个信号：说明这段逻辑应该换成专用模块。

如果确实需要在 check mode 下也执行某个只读命令，可以在任务上写 check_mode: false 强制它运行（这个开关的含义是「即使处于 check mode，本任务也真正执行」，用的时候要确认它确实无害）。

「跑绿了但没生效」的排查顺序，建议固定成三步：第一步，--check --diff --limit 一台，看它认为要不要改——如果它说「不用改」，说明它以为目标已经是对的，问题在判断逻辑（变量、when 条件）；第二步，如果它说要改但改完没效果，看是不是改错了路径或者文件被别的东西覆盖（比如另一个角色、或者配置管理工具在打架）；第三步，-m debug -a 'var=xxx' 把变量实际值打出来，不要靠读代码推断。

连接类问题里，最常被忽略的是 Python 解释器。Ansible 的模块大多数要在目标机上用 Python 执行，现代版本会自动发现解释器，但在最小化镜像、容器、或者只有 Python3 且路径不标准的系统上会失败。现象通常是「/usr/bin/python: not found」或者一段看不懂的 discovery 警告。解决办法是在 inventory 里给这批主机设 ansible_python_interpreter=/usr/bin/python3，或者对完全不能用 Python 的场景改用 raw 模块先装一个。

ansible-playbook site.yml --syntax-check只查语法与结构，不连机器，CI 第一步
ansible-playbook site.yml --check --diff --limit web-01干跑并看文件差异，先在一台上确认它要动什么
ansible-playbook site.yml --list-hosts执行前确认影响面，避免改错环境
ansible web-01 -m debug -a 'var=nginx_port'打印变量的实际生效值，变量优先级问题的终结者
ansible web-01 -m ping -vvvv连接类故障的第一条命令，SSH/become/解释器都能看出来
ansible-playbook site.yml --start-at-task "下发 nginx 配置"从指定任务继续，调试长 playbook 省时间

面试怎么答：「排查我分三类。连接类用 ansible -m ping 加 -vvvv，看 SSH、become、Python 解释器；语义类（跑绿了没生效）先 --check --diff 看它认为要不要改，再用 debug 打变量实际值，不靠读代码推断；顺序类主要查 handler——它只在通知者 changed 时才跑，而且 check mode 下 command/shell 会被跳过，所以 --check 对这些模块不提供信息。CI 里固定跑 syntax-check 和 ansible-lint，成本几乎为零。」

模块 10

9 个坑：都是「看起来没问题」的那类

这一节的坑有个共同形状：Ansible 不会报错，它只是按你写的做了另一件事。所以它们不会在执行时暴露，而是在某次变更里变成一次事故。

1
用 shell 模块下发配置
shell 每次都报 changed，于是 handler 每次都触发、每次都重启。而且它不比 checksum，你无法知道文件到底改没改。能用 copy/template/file/lineinfile 就别用 shell。
2
默认值写进了 vars/main.yml
vars 优先级很高，会压过 group_vars 和 play vars，使用者改不动、只能 fork。允许覆盖的默认值必须放 defaults/main.yml。
3
state=latest 或 state=restarted 当默认写法
latest 会每次把包升到最新版，restarted 会每次重启，两者都破坏收敛。生产锁版本，重启交给 handler。
4
handler 名字和其他角色冲突
同名 handler 会互相覆盖，你 notify 的可能是另一个角色的动作。名字带角色前缀，或者用 listen 订阅主题。
5
模板里放了时间戳或随机数
每次渲染结果都不同，copy/template 永远 changed，然后每次都触发重启。模板只放确定的配置，动态值用变量或让应用自己生成。
6
以为 --check 能验证一切
command/shell/raw 在 check mode 下默认被跳过，你看到的「skipped」不代表安全。而且依赖前序任务结果的逻辑在 check 下根本不成立。
7
密钥放进 Vault 就不管了
Vault 只加密静态存储，运行时明文在内存和输出里。处理密钥的任务必须加 no_log，目标文件必须显式设置 mode 0600。
8
全量跑变更不加 serial 和 max_failure_percentage
一个写错的模板会在几秒内推到全部机器，没有中止点。分批 + 失败比例阈值是批量变更的底线配置。
9
用 -e 传递环境差异
-e 赢过一切，会掩盖代码里的正确配置，而且这个值不进 Git、不进评审。环境差异放 inventory 的 group_vars 或独立的 vars 文件，并且版本化。

面试怎么答：挑一个你真的踩过的讲完整。「我踩过最典型的一次是 handler 没触发：我改了 nginx 配置模板，跑完是 ok 不是 changed，因为那台机器之前被人手工改过、内容和模板渲染结果刚好一样，于是 reload 没执行，我以为配置下发了其实没有。后来我把规则改成——配置类变更必须 --check --diff 先确认有 diff，并且不允许手工改 Ansible 管的文件。这个经历让我意识到『ok』不一定是好消息，它也可能意味着『它以为不用动』。」

自测

六道题

1. 一个 playbook 跑第二遍仍然全部报 changed，最可能的原因是？
正确答案：command / shell 没有幂等逻辑。幂等是模块属性，copy、template、file、service 会先读当前状态再比较；command、shell、raw 只是把命令交给远端执行，退出码 0 即报 changed。修法是加 creates/removes、加 changed_when，或换成专用模块。这个坑的连带后果是 handler 会被误触发，导致每次执行都重启服务。
2. 关于 handler，下面哪个说法是对的？
正确答案：changed 才触发、末尾统一跑、同名只跑一次。ok 和 skipped 都不会触发 notify，所以「改了配置没重启」通常是通知者没有报告 changed。handler 默认排到 play 末尾统一执行，同一个 handler 被多次 notify 也只执行一次；想提前执行用 meta: flush_handlers。另外 handler 名字要保持唯一，同名会互相覆盖。
3. 你在角色的 defaults/main.yml 里改了一个变量，执行后没生效。最应该怀疑什么？
正确答案：被更高优先级覆盖了。role defaults 在官方 22 级顺序里排第 2，几乎是最低的一档；group_vars、host_vars、play vars、role vars、set_fact、include_vars、role 参数、-e 全部高于它。排障不要猜，用 ansible -m debug -a 'var=名字' 打印实际值，或 -vvvv 看它 from 哪里。
4. 角色的 defaults/main.yml 和 vars/main.yml 应该怎么区分使用？
正确答案：可变/不可变的分界。defaults 是最低优先级（第 2 级），任何 group_vars、host_vars、play vars、-e 都能覆盖它，所以所有「允许使用者改的默认值」都应该放这里；vars 排在第 15 级，压过 group_vars 和 play vars，写进去基本等于「不许改」。把可调项写进 vars 会让角色无法复用。
5. 关于 ansible-vault，下面哪个说法是准确的？
正确答案：只管静态，不管运行时。执行时 Ansible 必须解密，明文存在于内存、模块参数、以及可能的输出里——所以处理密钥的任务必须加 no_log: true（否则 -v 以上输出和失败信息里就是明文），并且 copy 到目标机的私钥要显式写 mode: "0600"。vault 密码本身的分发才是关键，应放在 CI 的密钥管理里，绝不能提交到 Git。
6. 为什么「用 Ansible 创建云主机、用 Terraform 配置机器内部」通常被认为是反过来的分工？
正确答案：按资源生命周期划分。Terraform 维护 state，知道「我创建了什么、ID 是什么」，因此能算出声明与现实的差、也敢做 destroy；Ansible 没有跨运行的资源清单，每次重新读目标机状态来判断要不要改，所以它不会帮你删除资源。把 OS 内部配置写进 Terraform，会让 state 与机器实际状态迅速脱节；用 Ansible 创建云资源，则缺少「已存在」的判断依据，容易重复创建。
