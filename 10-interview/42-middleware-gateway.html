中间件面试：API 网关、注册中心与配置中心

这三个组件名字不同，其实在回答同一个问题：东西变了，怎么让所有人知道。

读之前先答一句：注册中心整个集群都不可用，你的服务还能撑多久？答案取决于什么？
开始前

三个现场：都是「信息没同步」的后果

发布完一次，服务 A 一直连不上服务 B 的新实例；改了一个开关，十二台机器只生效了五台；外部请求全部超时，但后端监控显示所有实例都很闲。这三件事看起来是三个故障，本质是同一个：某个地方变了，而依赖它的那一端不知道。

单体时代这个问题不存在：调用是本地方法调用，配置在文件里和代码一起发布，入口只有一个反向代理。一旦拆成服务，「谁在哪」「参数是什么」「流量怎么进来」这三件事就分开了，注册中心、配置中心、网关就是这三个问题的答案。

现场直觉动作真实原因
B 扩容后，A 一直访问不到新实例，但也没报错网络不通，找网络同学A 本地缓存的服务列表没有更新，或者 B 的实例根本没注册成功。调用方不再直接知道下游的地址，它只认注册中心给的那份列表
改了一个限流阈值，一半机器生效一半没生效发布有问题，重新发一次配置中心推送到达了部分实例，或者这些实例压根没有监听这个键。动态生效的前提是代码路径里真的有「监听并重建」的逻辑，不是改了就自动变
外部流量全部超时，后端所有实例 CPU 都很低后端挂了，扩容入口那一层的工作量：TLS 握手、鉴权、限流、路由都在它这里。它被打满了，后面的服务自然闲着
网关
管南北向流量也就是从外部进来的那一段。它做的是全局策略：鉴权、限流、路由、协议转换，以及把这些事的重复实现收到一个位置。
注册中心
管东西向也就是服务之间互相调用时的地址问题。它回答「谁在哪、哪些还活着」，并且必须容忍自己的短暂不可用。
配置中心
管运行时参数。它把「改一个值」从一次全量发布，降级成一次带版本、可灰度、可回滚的发布动作。

这一篇的顺序：先说清这三个组件各自解决什么、以及它们的替代方案为什么不够；再逐个拆开讲职责、选型取舍和落地要领；然后是三者的边界与常见误用、以及「它们挂了怎么办」；最后收在九个坑上。每节留一句能直接说出口的话。

先建立一个判断标准：这三个组件都不是必需品，而是规模化之后的产物。服务数是三五个、机器是三五台的时候，DNS 加一份 Nginx 配置就能解决全部三个问题。面试里能说出「我现在这个规模不需要它」，比把功能清单背完整更有说服力——因为这说明你理解它解决问题的前提，而不是只见过它的名字。

面试怎么答：「这三个组件回答的是同一类问题：拓扑变了、参数变了、入口规则变了，怎么让相关方知道。网关管南北向的全局策略，注册中心管服务之间谁在哪，配置中心管运行时参数的发布。它们互相不能替代，因为要解决的问题和能容忍的故障行为都不一样。」

模块 1

从单体到分布式，冒出来的是三个新问题

不去理解「它们替代了什么」，就答不出「为什么需要它们」。这一节把单体时代的做法和分布式时代的做法放在一起对比，三个组件的必要性会自己浮出来。

第一个问题：地址在哪。单体时代，调用方把地址写在一张 Nginx 的 upstream 里，改一次配置 reload 一次就行。微服务的地址是会变的：扩容、缩容、滚动发布、故障重建，都会让实例列表变化，而且这些变化是自动发生的，人不再有机会去改那张表。所以「谁能告诉调用方最新的实例列表」就成了一个必须被解决的问题——这就是注册中心。

第二个问题：参数在哪。配置跟着镜像走的好处是可复现，坏处是改一个值要走一次完整的构建与发布。当你有二十个服务、每个服务三十个可能要微调的参数时，这套流程会明显拖慢响应速度。所以要把「不需要改代码的参数」挪出去，并且让它具备发布动作应有的属性：版本、灰度、回滚、审计——这就是配置中心。

第三个问题：入口规则在哪。单体只需要一个反向代理。服务拆开之后，客户端不可能自己去认识二十个服务：鉴权要做二十遍、限流要在每个服务里各实现一次、协议不统一时客户端要适配。所以需要一个统一的入口来承载这些横切能力——这就是 API 网关。

问题单体的做法为什么在分布式下失效谁来解决
服务在哪地址写在上游配置里实例列表会自己变，而且变化频率高于人改配置的速度注册中心
参数是什么配置文件随包发布改一个开关要全量发布，规模越大越慢配置中心
流量怎么进一层反向代理横切能力要在每个服务里重复实现，且难以统一变更API 网关

这里有一个常被忽略的成本视角：这三个组件自己也是分布式系统。它们要高可用、要部署多份、要监控、要有升级方案。所以「引入中间件」从来不是减少复杂度，而是把复杂度从每个服务内部搬到了一个集中的地方——这个搬迁是否划算，取决于服务数量和团队规模。这也是判断该不该上的唯一标准。

替代方案为什么不够：DNS 能解决名字解析，但它没有实例级健康检查，也没有秒级的变更感知（缓存时间这一条就决定了它的响应粒度）；Nginx upstream 里的 server 列表是静态的，除非你能接受每次变化都 reload 并且自己算健康检查；环境变量能改参数，但它把发布流程重新请回来了，并且无法灰度、无法审计。

# 注册中心在「东西向调用」里替代的就是这段静态列表
upstream order_service {
    server 10.0.1.11:8080;   # 实例变了要靠人改 + reload，且没有实例级健康判断
    server 10.0.1.12:8080;
}

# 配置则是：没有任何一个地方记录「谁在什么时候把哪个值改成了什么」
MAX_RETRY = 3        # 改这个值要走一次构建、测试、发布全流程

面试怎么答：「这三个组件分别替代的是上面那三种做法：注册中心替代静态上游列表，配置中心替代随包发布的配置文件，网关替代每个服务自己实现的那一套横切逻辑。引入它们的代价是它们自己也成了必须运维的分布式系统，所以我判断要不要上的标准是服务数量和团队能不能接得住，而不是功能清单好不好看。」

模块 2

API 网关：把横切能力收到一个位置，同时保持「薄」

网关最常见的失败不是性能不够，是越来越厚——业务团队发现「在网关加一段逻辑最快」，半年后发布互相阻塞，网关成了全公司唯一的发版瓶颈。

先把职责列清楚，因为面试里「网关做什么」通常要答五到七项：路由与负载均衡（按路径、域名、请求头把请求转发到对应服务）、鉴权与身份传递（校验令牌并往下游传递用户身份，而不是让每个服务各自校验一遍）、限流与熔断（在流量到达业务之前先把过量请求挡掉）、协议转换（对外 HTTP/JSON，对内可能是 gRPC 或别的协议）、TLS 终止与证书管理、统一日志与埋点（请求维度的一致性入口）、跨域与请求改写、以及灰度分流（按请求头或百分比把流量分到不同版本）。

然后是把边界说清楚的那一段，也是最加分的一段：网关要做的是「横切」而不是「业务」。判断方法很简单：这段逻辑换个业务要不要重写？如果答案是「要」，它就不该在网关里。在网关里做跨服务的编排、数据聚合、业务规则判断，短期很快，长期一定会变成发布瓶颈——因为它拖慢的是所有人。

能力网关该做的不该往它这儿放的
鉴权校验身份是否合法、是否过期，把结果透传给下游业务权限判断（这个人能不能看这份订单）
限流入口侧的粗粒度保护（按租户、按来源、按总量）细粒度业务配额，那属于业务自己的逻辑
路由按路径与版本转发把多个服务的返回拼成一个响应（那是编排层的活）
灰度按标签或比例把流量分到不同版本灰度策略里的业务条件（比如「只对老用户开放」）
日志统一的接入层访问日志与 trace 起始点把业务埋点全塞进来，日志量会失控

还有一个运维视角必须讲的点：网关限流挡不住内部放大的流量。网关只能在入口那一段设置阈值，而服务之间的调用会绕过它。所以一次外部请求在内部被放大十倍时，网关看到的量是 1，后端承受的是 10。正确的模型是两层：入口做总量保护，调用方自己做保护。同理，分布式限流需要一个共享的计数位置（比如一个中心化的计数服务），单机本地计数实现简单但在多实例下并不精确，两者要结合着用。

# 网关的典型配置形态：一条路由 = 匹配规则 + 一组过滤器
# 下面用 Spring Cloud Gateway 风格的示意，实际字段名以你使用的网关文档为准
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service      # lb:// 表示从注册中心取实例，网关依赖的就是它的列表
          predicates:
            - Path=/api/order/**
          filters:
            - StripPrefix=1
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 100
                redis-rate-limiter.burstCapacity: 200
网关是所有请求的必经之路，所以它的可用性指标要按「最高」那一档来设计。这意味着：多路部署加健康检查是世界观的下限；它的超时时间必须比下游短（否则下游卡住会把它的连接池占满从而拖垮整条链路）；它的资源要单独看，因为 TLS 加解密、限流计数、日志序列化都是实打实的 CPU 消耗。同时必须预留一条绕过它的应急通道——一旦网关本身出问题，至少内网还能直连。

面试怎么答：「网关我只放横切能力：鉴权、限流、路由、灰度、协议转换、TLS、统一日志。判断标准是这段逻辑换个业务要不要重写——要重写就是业务层的活，放进来会让网关变成全公司的发版瓶颈。另外网关限流只保护入口，内部调用会绕过它，所以 consumer 侧也要有自己的保护。」

模块 3

网关选型：先看「变更有多快」，再看生态

选网关最容易被误导的地方是盯着性能。真正决定长期成本的是「改一条路由要多久生效」——因为这决定了发布节奏。

下面这张表只讲定位，不讲性能排名：性能数字高度依赖压测场景，而你的场景（连接数、body 大小、TLS 与否、插件多少）几乎不可能和别人一样。把它当成选型依据是很危险的。

组件定位要留意的点
Nginx / OpenResty性能稳定的反向代理与边缘负载均衡，OpenResty 让你可以用脚本扩展行为原生配置的动态能力有限，想要「改一条路由不 reload 就生效」，通常要靠脚本扩展或配套组件
Kong基于 Nginx/OpenResty 的插件化网关，插件生态较完整，适合想要「开箱即用的一堆能力」的团队它的配置要落在一个外部存储里，那个存储本身要高可用，这是运维时必须补上的一环
Apache APISIX同样构建在 Nginx 之上，主打动态路由与热更新，配置放在分布式键值存储里动态能力强意味着更容易把东西堆上去，需要自己守住「网关要薄」的边界
Spring Cloud GatewayJava 技术栈的响应式网关，与 Spring Cloud 生态（注册发现、负载均衡、熔断）深度集成团队是 Java 栈时接入成本最低；它的表现与 JVM 调优高度相关，这正好是第 40 期那一套知识
Envoy / 网格入口云原生场景下的事实标准之一，配置由控制面统一下发，和服务网格是一套如果你不打算上网格，单独为了网关再运维一套 Envoy 控制面往往偏重

把这张表翻译成可操作的选型顺序：团队技术栈（Java 团队用 SCG 的边际成本最低；偏平台/网关层独立的团队可以用 Nginx 系）→ 变更频率（路由每天改和每月改，对动态能力的要求完全不同）→ 插件生态够不够用（鉴权、限流、灰度这些能不能少写代码）→ 是否已有服务网格（有网格就用它的入口能力，避免两套）→ 最后才是性能。至于具体的数值指标，请在你自己的流量模型下压一遍，别引用别人的数字。

还有一条纪律值得写进规范：路由变更要走一样的发布流程。网关配置经常被人当成「随手改」，而它影响面是全站。它应该有版本、有评审、有回滚方案，也有审计记录——和代码一样。

# 网关自身该被观测的几件事（具体暴露方式以你使用的网关为准）
# 1. 按路由维度的请求数、错误率、P99 延迟
# 2. 上游健康实例数：这是「路由配对了但实例都挂了」最快的发现方式
# 3. 限流触发次数与拒绝数：能证明保护策略真的在生效
# 4. 连接池/工作队列的饱和度：这是网关被拖垮的前兆

# Nginx 系常见的最小排查链
nginx -t
tail -f /var/log/nginx/error.log | grep -i upstream
不要在网关上直接改生产配置来验证想法。它是所有流量的必经点，任何一次语法错误或者路径写错，影响范围是整站。正确流程是：配置进版本库 → 在预发或灰度实例上校验 → 确认无误后再分发到生产。这一条看起来是常识，但线上事故里「手改网关」的比例非常高，因为它太方便了。

面试怎么答：「网关选型我先看团队栈和变更频率，性能放在最后，因为别人压出来的数字在我的流量模型下未必成立。Java 团队用 Spring Cloud Gateway 接入成本最低；需要高频动态路由就选类 Nginx 的动态网关；已经在用服务网格就直接复用它的入口能力。另外网关配置必须和代码一样进版本库、走评审和回滚，因为它影响的是全站。」

模块 4

注册中心：回答「谁在哪」，并且要容忍自己挂

注册中心的技术难点不在存储，在「什么时候该把一个实例从列表里拿掉」。这一判断做错了，要么把健康的实例误杀，要么把已经死的实例留着坑人。

先说机制。服务注册是实例启动后把自己的地址（IP、端口）和元数据（版本、分组、权重、机房）写进去。健康检查有两种方向：一种是客户端上报心跳，服务端在超过阈值没收到心跳时把它剔除；另一种是服务端主动探测（TCP 连接、HTTP 探活）。前者简单、可扩展，代价是「失联」和「下线」在一段时间里无法区分；后者更准确，代价是探测频率和存储压力的上升。服务发现则是调用方拿到列表的方式：可能是定期拉取、可能是服务端推送变更，而实际中几乎都会配一份本地缓存——这份缓存决定了注册中心挂掉之后业务还能撑多久。

组件一致性取向关键时刻的行为
Eureka偏 AP（可用性优先）有自我保护机制：短时间内大量心跳失败时，宁可保留可能已下线的实例也不摘除，理由是网络抖动造成的误摘危害更大。代价是客户端可能拿到坏地址，靠调用方容错兜住
Nacos同时支持两种模式临时实例走可用性优先的模式，持久实例走强一致模式。选哪种取决于这个实例要不要在被摘除后自动消失
Consul偏 CP（强一致）依赖共识协议，选举期间无法对外提供写入，换来的是拿到的一定是最新的信息。它的健康检查模型做得比较完整
ZooKeeperCP它本职是分布式协调服务（选主、分布式锁）。被拿来当注册中心时缺的是「面向服务的健康检查」：它擅长保一致，但不擅长判断一个实例是不是还能处理请求

为什么注册中心可以选择可用性优先？因为它对一致性的要求本来就不高：短暂拿到一个已经下线的地址，后果是一次调用失败，而这次失败可以由调用方的重试、超时和容错兜住。反过来说，它的一致性承诺如果太强，代价就是在它自己出问题时所有人一起不可用。这个取舍是注册中心区别于配置中心的核心：配置可以短暂陈旧但不能错，服务列表可以短暂不精确但必须拿得到。

# 看服务注册表里到底注册了什么（不同组件的接口不同，以下为示意，以你的版本为准）
curl -s http://eureka:8761/eureka/apps/ORDER-SERVICE | head -50
curl -s 'http://nacos:8848/nacos/v1/ns/instance/list?serviceName=order-service'
consul catalog services && consul catalog nodes -service=order-service

# 客户端侧也要能自证：我本地缓存的那份列表里有多少个实例
# 这一步是排查「明明注册了却访问不到」的关键，因为问题常常在调用方的缓存
curl -s 'http://nacos:8848/nacos/v1/ns/instance/list?serviceName=order-service'看注册表里到底注册了什么，接口以你使用的组件为准
consul catalog nodes -service=order-service另一侧的自证：健康实例到底有几个
kubectl get deploy order-service -o jsonpath='{.spec.template.spec.terminationGracePeriodSeconds}'确认优雅期长于「注销 + 传播」的总耗时
iptables -I OUTPUT -p tcp --dport 8848 -j DROP演练：掐掉注册中心，观察业务还能撑多久（记得恢复）
nginx -t网关配置改完必跑的一步，它把影响面最大的低级错误挡住
一个能直接减少事故的动作：把「注册成功的日志」做成启动环节的硬性检查项。很多「扩容后没流量」的故障，根因是实例启动成功但注册失败——网络策略、命名空间、凭证、地址选择（比如注册了容器 IP 而调用方只能通别的网段）都可能。写代码、写检查、写告警，别靠人看。

面试怎么答：「注册中心的核心是健康检查的判断，而不是存储。HealthCheck 有两种：客户端心跳和服务端主动探活。CAP 上注册中心通常选可用性优先，因为短暂拿到一个坏地址可以由调用方重试兜住，但如果它自己不可用就是全站故障。具体到组件：Eureka 偏 AP 且有自我保护，Consul 和 ZooKeeper 偏 CP，Nacos 两种模式都支持——关键不是说字母，而是能说出故障时它的行为。」

模块 5

上下线的时序：为什么「发布完有几十个 5xx」几乎都是取舍没算清

「我们每次发布都会抖一下」这句话背后通常不是优雅重启没做，而是四个时间间隔没有对齐。这一节把这四个数字讲清楚，这是注册中心最能体现工程水平的考点。

这四个时间是：心跳间隔（实例多久证明一次自己活着）、剔除阈值（多久没心跳就把它拿掉）、客户端缓存或刷新周期（调用方多久更新一次列表）、以及进程的关闭等待时间（收到停止信号到真正杀掉进程之间的窗口）。任何一个比另外几个短得太多，就会出现「列表里有一个已经不提供服务的地址」——用户的请求正好打过去，就是一个 5xx。

时序错误现象修法
先停进程，再（或不等）注销注销来不及生效，列表里还有这个地址先主动注销或把自己标记为不可用，再退出
注销后立刻退出进程调用方的缓存还没过期，这段时间持续报错注销后等待超过「客户端刷新周期 + 剔除传播时间」再退出
剔除阈值比网络抖动还短一次网络波动，大批实例被误判死亡并摘除阈值要能容忍短抖动，并且用服务端主动探活做交叉验证
容器编排层和注册中心各做一半K8s 已经发了停止信号，注册中心还在给流量把注销动作挂到停止钩子（preStop 一类机制）上，并留出足够的优雅期

把这个问题和容器结合起来看会更清楚：Kubernetes 删 Pod 的时序是「发信号 → 摘除流量 → 等优雅期 → 强杀」，而应用注册/注销的时序是「注销 → 等待传播 → 退出」。这两条链路如果各走各的，中间那段没人管的时间就是 5xx 的来源。所以正确的做法是把注销动作挂在停止钩子上，并且让优雅期长于「传播时间 + 在途请求处理完的时间」。

上线也一样有顺序：服务不应该在启动完成之前就注册。如果进程刚起来就注册，而此时连接池还没预热、缓存还没加载、依赖还没就绪，那么进来的第一批请求大概率失败。正确姿势是完成预热并自检通过之后再注册，这也是为什么很多框架提供「就绪之后才注册」的开关或者按需注册的能力。

# 优雅下线的标准动作顺序（伪代码，按你的框架实现）
# 1）把自己标记为不可用 / 主动注销，此时新流量不再进来
curl -X PUT http://registry/ deregister -d '{"service":"order-service","ip":"10.0.1.11","port":8080}'
# 2）等待：至少超过 客户端列表刷新周期 + 剔除传播时间
sleep 30
# 3）再停进程。K8s 场景要把它挂在 preStop，并确认优雅期足够
kill -TERM <pid>

# K8s 侧对齐：preStop 负责注销 + 等待， terminationGracePeriodSeconds 必须大于这段时间
kubectl get deploy order-service -o jsonpath='{.spec.template.spec.terminationGracePeriodSeconds}{"\n"}'
自我保护机制看起来像 bug，其实是刻意的取舍。当注册中心在短时间内收到大量心跳失败时，它无法区分「这些实例真的挂了」还是「我和它们之间的网络断了」。如果是后者，执行剔除等于把健康的实例全部误杀，流量就全没了。所以它选择保守：保留可能过期的列表，依赖调用方的容错去处理坏地址。理解这个故事，比记住某个开关的名字重要得多。

面试怎么答：「发布抖动基本是四个时间没对齐：心跳间隔、剔除阈值、客户端列表刷新周期、进程的优雅期。下线要先注销、等待传播、再退进程；上线要预热完再注册。容器场景要把注销挂到停止钩子上，并让优雅期长于传播时间。自我保护机制是刻意的取舍——宁可短暂保留过期地址，也不在网络抖动时大批误摘。」

模块 6

配置中心：推还是拉，以及「改了到底生效没有」

配置中心最容易被人误解的一点：它没有让配置「自动生效」，它只是把「变更」这件事变得又快又可控。真正让配置生效的，还是应用里那段监听并处理变更的代码。

先看两种基本模型。拉取是客户端按固定周期去问服务端，实现最简单，但延迟取决于轮询间隔，频率调高了会给服务端造成压力。长轮询是对它的改进：客户端发起请求后，服务端在没有变更时不立即返回，而是把这个连接保持住，直到有变更或者等待时间到达上限才响应。它用一次连接换来了「低延迟 + 低轮询压力」的组合，是很多配置中心的默认做法。推送（长连接或消息通道）能做到真正的实时，代价是要维护连接状态、重连、有序性以及广播范围。

模型延迟服务端压力实现复杂度
短轮询取决于轮询间隔实例多了以后请求量线性增长最低
长轮询变更即达连接保持但请求数低中等，要处理超时与重试
长连接推送最低连接成本高最高：重连、心跳、有序送达都要做
消息通道广播较低依赖中间件的可用性中等，但要额外运维一个中间件

接下来是发布属性，这一块决定它是「工具」还是「系统」。配置变更应该具备和代码发布一样的四个属性：版本（能回答上一次是什么值）、灰度（先对一台或一个实例组生效，确认无误再全量）、回滚（回滚本质上就是发布上一个版本；没有版本就没有回滚，只有手改回去）、以及审计（谁在什么时候改了什么，能不能追溯）。缺任何一项，它都比一份写在 Git 里的配置文件更危险——因为这次的影响面是全站，而你看不到变更历史。

然后是那个最常被漏掉的前提：动态生效只对「会重建的对象」成立。如果代码在启动时把配置值读进来然后固化在某个字段或者某个已经建好的连接池里，那么配置中心推送一万次也没用——因为没有人在推送到达时去重建那个对象。所以接入配置中心的正确做法是：把需要动态调整的资源放在一个「能响应变更并安全重建」的位置，并且在灰度的时候真的去验证它是否重建了。

最后是把敏感凭据单独拿出来说：数据库密码这类东西放进配置中心，等于把它放在一个可以被很多人看到的地方。所以这类值应当加密存储、由有权限的实例或客户端侧解密，并且配置中心自身的权限模型要足够细（谁能读哪个命名空间）。审计也要打开——因为「谁读了配置」有时和「谁改了配置」一样重要。

# 变更的最小闭环（以常见的开放接口示意，字段名以你使用的组件为准）
curl -X POST 'http://config:8848/nacos/v1/cs/configs' \
  -d 'dataId=order-service.yaml&group=PROD&content=maxRetry: 5'
# 更推荐的做法：从版本库出发，而不是对着生产接口手-post

# 客户端侧必须能自证「我拿到了什么版本」
curl -s http://127.0.0.1:8080/actuator/env | grep -i maxRetry
curl -s http://127.0.0.1:8080/actuator/configprops | head -40

# 本地快照是好东西，但它守的是「配置中心挂了还能起来」，不是「改错了能自动回来」
ls -l /opt/app/config-snapshot/
本地快照是配置中心的最后一道防线，务必明确它在不在。没有本地缓存/快照的服务，在配置中心不可用时连启动都启动不了，这时配置中心就从「弱依赖」变成了「强依赖」——而它的不可用会一次性影响所有服务。所以工程目标是：配置中心挂了，已有服务照常运行、新实例也能用上一次的快照拉起来。这个能力要定期演练，不要假设它存在。

面试怎么答：「配置中心的传输模型我按延迟和服务端压力选：短轮询最简单但延迟取决于间隔，长轮询用保持连接换来了低延迟和低请求量，长连接推送实时但成本和复杂度最高。更重要的是发布属性——版本、灰度、回滚、审计缺一不可，因为没有版本就没有回滚。另外动态生效只对会重建的对象成立，代码里没有监听与重建逻辑，推送到不了那个对象。本地快照必须有，否则它从弱依赖变成了强依赖。」

模块 7

三者的边界：它们不能互相替代，因为出故障时想要的行为不一样

把这三个组件串起来的那条线是「变更的传播方向」：网关的规则变了要立刻对全站生效；注册中心的地址变了要能容忍短暂陈旧；配置中心的键值变了要能灰度能回滚。这三个「想要的行为」不一致，就决定了它们必须是三套东西。

组件数据流方向变更的粒度故障时想要的行为
网关南北向：外部到内部按路由/按站点，通常是全站级规则要么全生效要么回退，不能一半一半
注册中心东西向：服务与服务之间按实例，变化频繁且自动发生必须继续提供列表，短暂不精确可以接受
配置中心服务端到每个实例的运行时参数按 dataId / 键，要求可灰度可以继续提供上一次的值，但不能提供错的

基于这张表，常见的误用就都能解释清楚了：用注册中心存配置——它能存，但没有版本、没有灰度、没有审计，配置项在服务数上做乘法之后体量也失控，而且这类读请求会和心跳的健康状态写在同一套压力之下。用配置中心做服务发现——它能下发地址，但没有健康检查，实例挂了不会自动从列表消失。用网关做服务间的调用——那等于所有内部流量都多绕一跳，并且把网关变成了一个吞吐瓶颈和单点。用数据库或协调服务临时顶替注册中心——它们能实现读写，但没有健康检查模型和「过期即失效」的语义，下线之后地址会一直留着僵尸。

判断归属的第一问：这份数据是「事实」还是「意图」？实例列表是事实（谁活着由健康检查结果决定），所以属于注册中心；参数是意图（我们希望它是什么值），所以属于配置中心。
第二问：这份数据在失效时应不应该自动消失？应该自动消失的是注册中心（实例断了心跳就该下线）；不应该消失的是配置（配置中心挂了不代表这个值失效）。
第三问：这份变更的影响面是全站还是单个服务？影响全站、需要统一生效入口策略的，才轮到网关。
# 反例清单：这些都见过，而且短期都「能用」
# 1）把开关塞进注册中心的元数据 —— 没有版本、没有灰度、改错了无法回滚
# 2）用配置中心下发下游地址 —— 实例挂了不会自动消失，调用方会一直重试一个死地址
# 3）所有内部调用都过一遍网关 —— 多一跳延迟 + 一个全站单点 + 一个吞吐瓶颈
# 4）网关里串联三个服务的返回 —— 短期最快，长期变成全公司的发版瓶颈
一句能用在取舍讨论里的话：这三个组件各自代表一种「不一致的容忍策略」。网关追求规则的统一，注册中心追求地址的可用，配置中心追求值的可追溯。当一个设计让某一处同时承担两种策略时，它通常就在制造未来的事故——比如那个既当配置又当注册的 etcd/数据库，往往最后两件事都做不好。

面试怎么答：「判断归属我问三件事：这份数据是事实还是意图、失效时应不应该自动消失、变更影响面是单服务还是全站。实例列表是事实且该自动消失，所以归注册中心；参数是意图且不该自动消失、还需要版本和灰度，所以归配置中心；全站级的入口策略才归网关。拿注册中心存配置是高频误用，因为它没有版本和回滚。」

模块 8

它们挂了怎么办：用「能不能降级到本地」判断强依赖还是弱依赖

「注册中心挂了会怎样？」这道题的满分答案包含两部分：存量系统还能撑多久，以及这段时间里哪些能力已经没了。只答其中一半，说明没真的想过。

注册中心不可用。调用方手里有一份本地缓存的实例列表，所以已经建立起来的调用还能继续，这就是设计上给它的降级空间。但同时有三件事做不了：新实例注册不上去（扩容出来的机器接不到流量）、故障实例不会被摘除（已经挂的地址继续被调用方命中，错误率上升）、以及元数据变更感知不到。所以在那一刻你不能做变更，尤其是不能做需要新实例接流的扩容——这一点很重要，因为出故障时人的第一反应常常是扩容。修复目标是高可用：多节点部署并满足多数派要求，网络与控制面单独监控。

配置中心不可用。同样靠本地快照。已经有这份文件的实例可以照常运行甚至重启——前提是本地快照真的存在并且被正确使用。如果你连这份降级文件都没有，那么配置中心就成了强依赖：它一挂，所有服务无法重启。所以工程目标非常具体：配置中心不可用时，服务能启动、能运行，只是不能改配置。这条必须演练。

网关不可用。它是必经点，没有本地快照可言，所以答案只能是冗余加健康检查：多实例、前面再有一层负载均衡或 VIP、健康检查自动摘除。并且必须提前想清楚「绕过网关」的应急通道——内网、管理面或运维通道要能直达服务，否则网关一挂你连排查的工具都没有。

组件挂掉能降级到立即失去的能力那一刻不要做
注册中心客户端本地列表缓存新实例注册、故障实例摘除、元数据变更不要扩容——新实例注册不上，接不到流量
配置中心本地快照 / 上次拉取的值改配置、灰度、动态调参不要重启那些没有本地快照的服务
网关无（必经点，只能靠冗余）入口流量全部中断不要在网关上临时改配置验证想法
# 演练脚本比文档有用：三个依赖各自「假装挂掉」一次
# 1）把到注册中心的网络封掉，观察业务 QPS 与错误率变化曲线的形状
iptables -I OUTPUT -p tcp --dport 8848 -j DROP
# 2）观察调用方列表是否还在：能不能找到入口证明自己用的是缓存
curl -s http://127.0.0.1:8080/actuator/health | head -20
# 3）恢复：这一步要有双人确认，别把演练打成事故
iptables -D OUTPUT -p tcp --dport 8848 -j DROP
判断强依赖还是弱依赖的方法只有一个：把它掐掉，看业务还能不能跑。口头上的「它是弱依赖」没有任何意义，只有演练过的才算。而且这个结论会随时间失效——一次「顺手」的改造（比如把某个校验改成每次调配置中心）就能把弱依赖变成强依赖。所以这类演练应该做成定期项，而不是上线时做一次。

面试怎么答：「注册中心挂了，存量调用靠本地缓存还能跑，但立刻失去的是新注册和故障摘除能力，所以那一刻最忌讳的就是扩容——新实例接不到流量。配置中心挂了靠本地快照，工程目标是服务仍能启动和运行，只是不能改配置。网关是必经点没有降级，只能靠多实例加健康检查，并且要预留绕过它的应急通道。判断强弱依赖的方法是掐一次看业务能不能跑，而且要定期重做。」

模块 9

九个坑：规模没到就上，或者上了却没改工程习惯

下面这两类问题往往同时出现：不该上的时候上了，该改习惯的时候没改。前者带来维护成本，后者带来事故。

1
把网关当业务编排层用
在网关里串联多个服务的返回结果，短期最快，长期所有人发布都要排队过它。判断标准：这段逻辑换个业务要不要重写？
2
用注册中心的元数据存配置
它能存，但没有版本、没有灰度、没有回滚、没有审计。而且配置项在服务数上做乘法，体量会失控。
3
用配置中心下发下游地址做「服务发现」
地址能下发，但没有健康检查，实例挂了不会自动从列表消失，调用方会一直重试一个死地址。
4
只背 CAP 三个字母，说不出故障时行为
说 ZooKeeper 能做注册中心所以用它，说不出它缺少面向服务的健康检查；说 Eureka 有自我保护，说不出那是防止网络抖动时大批误摘。
5
没有本地缓存与快照，依赖一挂就起不来
配置中心没有快照就是强依赖，注册中心没有缓存列表就是单点。这两份本地数据要定期演练验证真的存在。
6
优雅下线只有一半：注销之后立刻退进程
调用方的列表还没过期，这段时间持续产生 5xx。必须等待超过「列表刷新周期 + 剔除传播时间」。
7
心跳阈值比网络抖动还短
一次网络波动就把大批量健康实例误判死亡并摘除，流量瞬间无处可去。阈值要容忍短抖动，并用主动探活做交叉验证。
8
限流只在网关做一层
网关看不见服务之间的调用放大：入口这一段有人管，内部那一层没人管。入口做总量保护，调用方还要有自己的保护。
9
配置改动没有灰度和回滚
一次改全站，出错时只能手改回去，而「上一个值是什么」如果没有版本记录，本身就是猜的。

面试怎么答：挑一条讲成三段：当时的判断、造成的损失、后来改成了什么。比如「我们曾经把每个服务的下游地址写在配置中心，理由是『统一好管理』。结果有台实例宕机后，调用方一直按那份地址重试，错误率涨了十几分钟才有人去改配置。后来把地址发现搬回注册中心，把配置只留给真正的参数。」第三段最重要，它证明你理解了这两类数据的区别。

自测

六道题

1. 注册中心整个集群不可用，下面哪种说法正确？
正确答案：第三段。调用方本地缓存的实例列表决定了降级空间有多大。但同时失去的是三个能力：新实例注册、故障实例摘除、元数据变更感知。所以那一刻最不该做的就是依赖新实例接流的扩容——扩容出来的实例注册不上去，接不到流量。
2. 为什么很多注册中心在一致性上选择可用性优先？
正确答案：第二段。这是权衡的结果而不是定理的强制要求。服务列表短暂不精确的后果是单次调用失败，可由重试、超时、熔断兜住；而注册中心不可用会让所有调用方都拿不到列表。所以常见的设计是保留可能过期的列表（例如 Eureka 的自我保护），宁可把判断权交给调用方的容错。
3. 发布后总有几十个请求失败，最可能的原因是？
正确答案：第四段。四个时间必须对齐：心跳间隔、剔除阈值、客户端列表刷新周期、进程优雅期。标准顺序是先注销或标记不可用 → 等待传播 → 再退出；容器场景要把注销挂到停止钩子上并保证优雅期足够。这通常不是代码 bug，而是时序设计。
4. 配置中心已经推送成功，但应用的行为没有变化。最合理的判断是？
正确答案：第一段。动态生效并非自动：只有那些会被重建的对象（连接池、线程池、限流规则等）才能真正跟上变更。如果启动时把值读进一个普通字段，那么推送多少次都不会改变它。接入配置中心时，验证「它是否真的重建了」是必须的一步。
5. 关于把配置放在注册中心、或者把服务地址放在配置中心，正确的评价是？
正确答案：第三段。判断归属要看数据的性质：实例列表是事实且失效时应自动消失（归注册中心）；参数是意图、不该自动消失且需要版本与灰度（归配置中心）。注册中心没有版本概念因而无法回滚；配置中心没有健康检查因而无法自动摘除死实例。
6. 网关限流已经配好了，但后端仍然被打垮。最可能的原因是？
正确答案：第二段。网关处在南北向的入口位置，它看到的是外部请求量；而一次外部请求在内部可能被放大若干倍（循环调用、扇出查询、重试），这部分流量完全不经过网关。正确的模型是两层：入口做总量保护，每个调用方对自己的下游做保护。限流算法不是这里的关键。
收口

术语表与下一步

术语一句话解释
南北向 / 东西向南北向是外部到内部的流量（归网关），东西向是服务之间的流量（归注册中心）
服务注册实例启动后把地址与元数据写进注册中心；注册成功应当成为启动的硬性检查项
健康检查判断实例是否可用：客户端上报心跳（可扩展但难区分失联与下线）或服务端主动探活（更准但成本高）
自我保护注册中心在短时间内大量心跳失败时保留列表不摘除，宁可让调用方容错，也不冒网络抖动误杀健康实例的风险
优雅下线先注销或标记不可用 → 等待列表传播 → 再退出进程；容器场景要挂在停止钩子上
长轮询客户端请求后服务端保持连接直到有变更或超时，用一次连接换取低延迟与低请求压力
本地快照配置在客户端侧的持久化副本，它决定了配置中心是弱依赖还是强依赖
灰度先对部分实例生效验证无误再全量；没有版本就没有回滚
Sidecar / 网格入口与服务网格配套的流量入口方案，配置由控制面下发
preStop容器被删除前执行的钩子，是「注销动作挂在哪」的标准位置
分布式限流把计数放在多方共享的位置以保证全局阈值；本地计数实现简单但多实例下不精确
强依赖 / 弱依赖能否降级到本地数据继续运行；结论只能来自「掐一次」的演练，且会随时间失效
下一步怎么练：① 起一个注册中心加两个服务实例，手动停掉一个，观察它多长时间后才从调用方列表消失，把这个时间和你配置的心跳间隔、剔除阈值对上；② 在两台机器上部署同一个服务：其中一台有本地快照、一台没有，然后掐掉配置中心，看哪台还能重启；③ 做一个优雅下线的小实验：注销之后立刻退出进程，看调用方报错持续多长时间，再把等待时间加进去，对比 5xx 数量；④ 给网关配一条错误的路由，看它的失败在全站层面是什么表现，体会「必经点」这四个字的分量。
