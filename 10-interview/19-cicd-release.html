CI/CD 与发布策略：怎么发才不出事

发布出事的根因通常不是代码，是不可回滚的数据库变更和没写完的优雅退出。

读之前先答一句：回滚一个已经执行过 DROP COLUMN 的版本，数据从哪里回来？
开始前

三次发布，三次都不是代码的错

「新版本有问题，回滚。」这句话说出口的时候，很多人心里是没底的——因为他不确定回滚之后数据库还认不认旧代码。发布系统的成熟度，不体现在它能把代码推上去，而体现在它能不能把一个错误的版本干净地撤回来。

下面三种现场，是发布事故里最典型的三个类别：切换太快、变更不可逆、进程死得太急。它们和业务逻辑无关，全是流程和设计问题。

现场直觉答案真实原因
滚动更新刚开始，网关 502 涨了 30 秒新版本有 bug，或者机器性能不够旧 Pod 收到 SIGTERM 立刻退出，但负载均衡的端点摘除是异步的，这几百毫秒里流量还在往已死的进程上打
回滚镜像后服务起不来，报「列不存在」回滚不彻底，镜像没换对上一个版本已经执行了 DROP COLUMN。新代码不认旧表结构，旧代码也不认新表结构，两个方向都断了
灰度 5% 时一切正常，全量后错误率飙升灰度没用，纯属运气灰度只看了「请求成功率」，没看下游依赖的容量和慢查询。5% 的流量掩盖了连接池、缓存命中率这类非线性问题

把这三件事抽象一下，就是发布系统的三条铁律：流量要能慢慢给、数据要能向前兼容、进程要能体面地死。剩下的流水线设计、分支策略、制品管理，都是为这三条服务的。

可重复
同一个制品，从测试环境到生产环境不重新构建。构建一次、晋级多次，才能保证「测过的就是发的」。
可观测
发布过程中要有明确的判据：错误率、延迟、关键业务指标。没有判据的发布，等于闭着眼睛开车。
可回滚
回滚不只是换镜像。数据变更、配置变更、消息格式变更，每一个都要能退回去，或者一开始就不做成破坏性的。

这一篇按「一次发布的生命周期」组织：流水线该有哪几段、分支怎么管、制品怎么保证一致、流量怎么切、回滚怎么设计、开关怎么治理、上线前检查什么、K8s 里那些探针和优雅退出到底怎么配合。最后是九个坑和六道题。

面试落点：「我评价一套发布系统看三件事：制品是不是不可变、数据变更是不是向前兼容、出问题时能不能在几分钟内回到上一个稳定状态。这三件事决定了发布是工程，还是赌博。」

模块 1

流水线的六段：每一段失败都该指向不同的责任人

很多团队的「CI/CD」其实只有两段：拉代码、推镜像。中间没有测试，后面没有验证。这样的流水线跑得很快，但它只是把「手工发布」变成了「自动手工发布」。

一条能用的流水线，应该按反馈速度从快到慢排列，让开发在最便宜的阶段发现问题：

提交门禁：格式化、lint、类型检查、提交信息规范。几秒钟出结果，在本地或 pre-commit 就拦住，不占用 CI 资源。
构建：编译、打包、生成镜像。这一步的产物要被后续所有阶段复用，只做一次。构建慢就上依赖缓存和分层缓存，不要靠删测试来提速。
测试：单元测试跑得快、覆盖面广，放前面；集成测试依赖外部服务，放后面；端到端测试最慢最脆，只保留关键链路。测试失败必须阻断，不能设成「允许失败」。
制品：推送到镜像仓库，记录 tag 与 digest，附上构建号、commit、构建时间。这一步之后，产物就是不可变的，任何人不得重新构建同一版本。
部署：按环境逐级晋级（测试 → 预发 → 生产）。生产环境通常需要人工审批，但审批的内容应该是「变更说明和回滚方案」，而不是「点一下通过」。
验证：发布后自动跑冒烟用例、比对核心指标、观察一段固定窗口。验证不通过就自动回滚，别等人发现。

为什么强调「每段失败指向不同责任人」？因为流水线的价值不只是自动化，而是把问题定位到正确的环节。lint 挂了是开发本地没跑；集成测试挂了可能是环境或依赖；部署失败是配置或权限；验证失败才是这次变更本身有问题。如果所有失败都显示成「构建失败」，排查就从「看一眼日志」变成「从头查一遍」。

阶段典型耗时失败意味着
提交门禁秒级代码风格或类型问题，本地就该拦
构建分钟级依赖、编译、基础镜像变化
单测分钟级逻辑错误，最该在这一层拦住
集成 / E2E十分钟级接口契约、环境差异、数据准备
部署分钟级权限、配置、资源配额、镜像拉取
验证十分钟级变更本身有问题，或者容量不够
# 一条最小可用的流水线骨架（以 YAML 结构示意，字段名按你用的平台调整）
stages: [lint, build, test, package, deploy, verify]

build:
  stage: build
  script:
    - make build
  artifacts:
    expire_in: 1 day

package:
  stage: package
  script:
    # 用 commit 短哈希做 tag，绝不用 latest
    - docker build -t registry.example.com/shop/api:${CI_COMMIT_SHORT_SHA} .
    - docker push registry.example.com/shop/api:${CI_COMMIT_SHORT_SHA}
    # 记录 digest，后续所有环境都用它，不认 tag
    - docker inspect --format='{{index .RepoDigests 0}}' registry.example.com/shop/api:${CI_COMMIT_SHORT_SHA}

verify:
  stage: verify
  script:
    - ./scripts/smoke.sh
    - ./scripts/check-slo.sh --window 10m --max-error-rate 0.5
别在流水线里做「允许失败」的测试。一旦某个阶段的失败不阻断，它就会在三个月内变成永远红着、没人看的状态，然后真正的失败也被忽略。要么修好它，要么删掉它，不要留着当装饰。

面试落点：「流水线我按反馈速度排阶段：lint 和单测放最前，集成和 E2E 放后面，构建只做一次，产物晋级而不是重复构建。每个阶段的失败要能直接指向问题类型，最后一定要有发布后的自动验证，否则回滚永远靠人肉发现。」

模块 2

分支策略：分支活得越久，合并越像拆炸弹

「你们用 GitFlow 还是 trunk-based？」这个问题背后考的不是记不记得两种模型，而是你知不知道长生命周期分支的成本。

GitFlow 有 main、develop、feature/*、release/*、hotfix/* 五类分支，规则清晰，适合有明确版本号、需要同时维护多个已发布版本的产品（比如客户端、私有化部署）。代价是合并路径复杂：一个 hotfix 要同时合回 main 和 develop，漏一次就埋一个雷。

trunk-based 只有一个长期分支，所有人的改动以小批量、高频次直接进主干（或者经由存活不超过一两天的短分支）。它的前提很硬：必须有完善的自动化测试和 Feature Flag，否则未完成的功能会直接被发出去。收益也很明显：没有长期分叉，就没有大面积冲突；集成是持续的，不是发布前的一次性战役。

维度GitFlowtrunk-based
长期分支至少两个（main + develop）一个
合并冲突分支活得久，冲突大且晚发现小批量高频，冲突小且早发现
发布节奏按 release 分支批量发布随时可发布，靠开关控制可见性
前置条件分支纪律、版本管理高覆盖测试、Feature Flag、快速回滚能力
适合场景多版本并行维护、交付型项目SaaS、持续部署、单版本在线服务

不管选哪种，有几条是通用的：主干必须受保护（不能直接 push，必须过 CI 和评审）；分支存活时间要有限制（超过几天的分支要么拆小，要么强制 rebase）；发布分支只做修复不做功能，一旦开始往里加功能，它就变成了第二个 develop。

# 看分支活了多久：超过一周的分支要有人认领
git for-each-ref --sort=committerdate --format='%(committerdate:short) %(refname:short)' refs/heads

# 看一个分支落后主干多少：落后越多，合并越危险
git rev-list --count HEAD..origin/main

# 主干保护的关键配置（以你用的平台为准）：
#   禁止直接 push、必须 PR、必须通过 CI、至少一个 review、
#   合并前必须与主干同步、禁止 force push

# 用 squash 合并让主干历史保持线性，回滚时一个 commit 就是一个变更
git merge --squash feature/order-timeout
一个常被忽略的细节：回滚的粒度取决于提交历史。如果主干上是一个个 merge commit 混着几十个改动，你没法只回滚其中一个；如果每次合并是 squash 后的单个 commit，git revert 就能精确撤掉一个功能。分支策略不只影响协作，也影响你出事时的选择余地。

面试落点：「分支模型要和发布能力匹配。没有开关和自动化测试就上 trunk-based，等于把半成品直接发给用户；团队小、版本少却用完整 GitFlow，大部分流程是空转。我倾向于短分支 + 主干保护 + squash 合并，发布靠开关控制，而不是靠分支隔开。」

模块 3

制品不可变：测过的那个东西，必须就是发的那个

「测试环境是好的，生产怎么就不行？」——如果两个环境的镜像是分别构建的，这个问题就没有答案。因为你测的和发的根本不是同一个东西，哪怕代码一模一样。

镜像构建不是确定性的：基础镜像可能在这期间更新了，依赖安装可能拉到了新版本，构建时间戳会被写进产物，编译器的缓存状态也可能不同。任何一次重新构建，都是一次「未经测试的新制品」。所以规则只有一条：构建一次，之后所有环境都用同一个 digest 晋级。

tag 是可变的，digest 不是。同一个 tag 可以被反复推送覆盖，而 digest 由内容算出，改了内容 digest 就变。部署时用 digest 而不是 tag，才能保证「我部署的确实是那个东西」。latest 更糟：它既不可追溯，又会让 imagePullPolicy: IfNotPresent 的节点一直用旧缓存。

做法问题替代
每个环境重新构建测的和发的不是同一制品，环境差异无法排除构建一次，按环境晋级同一个 digest
用 latest 标签不可追溯、缓存不可控、回滚无目标commit 短哈希或版本号 + digest
把配置打进镜像换个环境就要重新构建，制品不再唯一配置外置：环境变量、ConfigMap、配置中心
只在镜像里放代码，密钥也打进去镜像一旦泄露，密钥全泄密钥由运行时注入，镜像里只有代码和依赖

「配置外置」这条经常被误解成「所有配置都放配置中心」。合理的分法是：和环境无关的（代码、依赖、静态资源）进镜像；和环境相关的（数据库地址、开关、密钥）在运行时注入。这样同一个镜像可以在测试、预发、生产三个环境跑，差异全部来自外部配置，出问题时可以把「镜像」和「配置」两个变量分开验证。

# 构建时打上可追溯的标签，并记录 digest
docker build -t registry.example.com/shop/api:1.8.3-9f2c1ab .
docker push registry.example.com/shop/api:1.8.3-9f2c1ab

# 用 digest 部署，杜绝 tag 被覆盖带来的不确定性
kubectl set image deployment/shop-api \
  api=registry.example.com/shop/api@sha256:<digest> -n prod

# 确认线上跑的到底是哪个镜像
kubectl get pods -n prod -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.containerStatuses[0].imageID}{"\n"}{end}'

# 回滚到上一个版本：Deployment 会保留 revision 历史
kubectl rollout history deployment/shop-api -n prod
kubectl rollout undo deployment/shop-api -n prod
面试怎么答：「制品不可变的落地方式就一句话：构建一次，用 digest 晋级。tag 只作为人类可读的别名，部署时认 digest。配置和密钥在运行时注入，不打进镜像。这样出问题时可以确定地说『线上跑的就是测试过的那一份』，而不是『代码应该一样』。」
模块 4

蓝绿、金丝雀、灰度：三种切流方式，三个不同的目的

很多人把这三个词当同义词用，都说成「先给一部分流量」。其实它们解决的问题不同：蓝绿买的是「切换和回滚的速度」，金丝雀买的是「用小流量验证风险」，灰度买的是「按人群精确控制」。

方式怎么切优点代价 / 限制
蓝绿两套完整环境，入口一次性切到新环境回滚极快，切回旧环境即可；新旧完全隔离资源翻倍；数据库通常共享，所以数据变更仍然要兼容；切换瞬间是「全有或全无」
金丝雀新版本只接一小部分流量（1%、5%、20%…），观察指标后逐步放大风险可控，能发现只有真实流量才暴露的问题需要流量切分能力和指标判据；版本共存期间要保证兼容
灰度按用户维度（UID 哈希、白名单、地域、设备）决定走哪个版本可控到人，适合功能验证和客诉处理同一个用户必须稳定落在同一版本，否则体验割裂

蓝绿最常见的误解是「安全」。它确实让回滚变快，但它不能帮你发现新版本的 bug——因为一切就是 100%，等发现问题时，所有人都已经受影响了。蓝绿适合「变更可控、验证充分、需要快速回退」的场景，比如基础设施升级、大版本切换。真正要降低发现风险，得靠金丝雀。

金丝雀的关键不在「切多少」，而在拿什么判断能不能继续。只看 HTTP 5xx 是不够的：一个把缓存命中率从 95% 打到 60% 的版本，5xx 可能一个都没有，但数据库压力会在一小时后爆炸。所以判据至少要覆盖三层：入口指标（错误率、P99 延迟）、依赖指标（数据库 QPS、慢查询数、缓存命中率）、业务指标（下单成功率、支付转化率）。

# 金丝雀的流量切分通常在入口层做，以 Nginx 权重为例（按需替换为你的网关）
upstream shop_api {
    server 10.0.1.11:8080 weight=95;   # 稳定版本
    server 10.0.1.12:8080 weight=5;    # 金丝雀版本
}

# Istio 里更常见的是按比例路由，改 VirtualService 的 weight
# 灰度到人则用匹配条件，例如按请求头里的用户 ID 取模

# 发布过程中盯这几个指标（示例查询，字段按你的监控系统调整）
# 入口错误率
sum(rate(http_requests_total{job="shop-api",code=~"5.."}[1m]))
  / sum(rate(http_requests_total{job="shop-api"}[1m]))

# 依赖侧：数据库 QPS 与慢查询，金丝雀放大前必须看
rate(mysql_global_status_questions[1m])
rate(mysql_global_status_slow_queries[1m])
金丝雀期间两个版本必须能同时读同一份数据。如果新版本写入了旧版本不认识的字段、或者改了枚举含义，那金丝雀就不是「降低风险」，而是「制造两个不兼容的世界」。切流方案的前提永远是数据兼容，这一点在下一节会展开。

面试落点：「蓝绿解决的是回滚速度，代价是资源翻倍，而且它是全量切换，发现问题的能力和直接发布差不多；金丝雀解决的是风险发现，关键在判据，不能只看 5xx，要看依赖和业务指标；灰度是按人群控制，要求同一用户稳定命中同一版本。三者可以叠加，但前提都是数据库向前兼容。」

模块 5

回滚设计：应用能退，数据退不回去

「回滚」这个词在应用层很轻——换个镜像而已。在数据层很重——DROP COLUMN 之后，数据是真的没了。所以发布设计的核心，不是让应用可回滚，而是让数据库变更永远不需要回滚。

做法叫 expand-contract（扩展-收缩），也叫并行变更。核心思想是把一次破坏性变更拆成多次兼容性变更，让任意两个相邻版本都能同时读写同一份数据：

Expand（扩展）：加新列 / 新表，设为可空或有默认值，不动旧结构。这一步对旧代码完全无感，可以先上。
双写：发布新代码，写数据时同时写新旧两处，读仍然读旧的。此时旧版本回滚也不影响，因为它只认旧列。
迁移：后台任务分批把历史数据补齐到新结构，控制批次大小，避免长事务和主从延迟。
切读：确认新结构数据完整后，代码改成读新、仍写双份。观察一段时间。
Contract（收缩）：确认没有旧版本实例在跑之后，停止写旧列，再下一个版本删掉旧列。删除永远单独一次发布，不和功能混在一起。

对照着看那些「绝对不能在同一次发布里做」的操作：重命名列（旧代码找不到旧名）、改列类型（新代码写进去的值旧代码读不出来）、删列（旧代码直接报错）、改枚举含义（同一个值在两个版本里意思不同，这类最隐蔽）、加非空无默认值的列（旧代码的 INSERT 会失败）。

变更能一次做完吗正确姿势
新增可空列可以先加列，代码后续再用；旧版本无感
重命名列不行加新列 → 双写 → 迁数据 → 切读 → 停写旧列 → 删旧列
改列类型不行按新类型加新列，双写并转换，切读后再删旧列
删列不行先确认无任何旧版本读取，单独一次发布删除
大表加索引看版本和工具用 online DDL 或 gh-ost，避开高峰，先确认没有长事务
数据回填不能一次全量分批、限速、可重入、有进度记录

还有一层经常被跳过：回滚要演练。很多团队的回滚方案写在文档里，从来没执行过。真正出事时才发现：镜像仓库里的旧 tag 被清了、旧版本的配置项已经删了、数据库迁移脚本的 down 根本没写、写了也不敢跑。回滚能力和代码覆盖率一样，没验证过就等于没有。

-- 反面例子：一次发布里同时改结构又改语义，回滚必炸
ALTER TABLE orders CHANGE COLUMN status state TINYINT NOT NULL;
-- 旧代码还在 SELECT status，直接报 Unknown column

-- 正面：扩展阶段只加不改，旧代码完全无感
ALTER TABLE orders ADD COLUMN state TINYINT NULL;
-- 双写一段时间、回填历史数据、切读之后，才在下一个版本收缩

-- 回填要分批，避免一次锁太多行、也避免从库延迟暴涨
UPDATE orders SET state = status
WHERE state IS NULL ORDER BY id LIMIT 1000;
-- 循环执行直到 affected rows 为 0，每批之间 sleep 一小段

# 回滚前先确认目标 revision 和它的镜像还在
kubectl rollout history deployment/shop-api -n prod
kubectl rollout undo deployment/shop-api -n prod --to-revision=7
备份不是回滚方案。从备份恢复意味着丢掉备份点之后的所有写入，通常是小时级的数据损失，而且恢复过程本身可能几十分钟。备份是「灾难恢复」的底线，不是「发布失败」的首选。发布失败的解法是向前兼容 + 快速切回旧版本，不是 restore。

面试落点：「应用回滚是换镜像，数据回滚基本不可能，所以我的原则是让数据变更永远向前兼容。具体就是 expand-contract：先加新结构、双写、迁数据、切读、最后单独一次发布删旧结构。任何一次发布都保证前后两个版本能同时读写同一份数据，这样回滚才真的可用。回滚方案必须演练过，没演练过的等于没有。」

模块 6

Feature Flag：把「部署」和「发布」拆成两件事

传统发布里，代码上线就等于功能上线。这两件事被绑死之后，你只有两个选择：要么等整个功能做完再发，要么发一个半成品。Feature Flag 的价值就是把它们拆开——代码可以先上，功能由开关决定对谁可见。

开关不止一种，用途和行为完全不同：

类型生命周期用途
发布开关几天到几周隐藏未完成的功能，功能全量后必须删除
实验开关一个实验周期A/B 测试，按用户分流，实验结束就清理
运维开关长期降级、熔断、限流的总闸，也就是常说的 kill switch
权限开关长期按租户 / 套餐 / 白名单开放功能

开关最大的成本不是实现，是债务。一个上线两年的发布开关，代码里还留着 if (flag) {...} else {...} 两条路径，测试要覆盖两遍，新人读代码要猜哪条是活的，最糟的是没人记得它现在是开还是关。所以每个开关从创建那天起就该有负责人和过期时间，到期自动告警。

另一个常见误解是「开关等于灰度」。开关控制的是功能可见性，灰度控制的是流量分配。两者组合起来才有用：新功能用开关包住，先用灰度给 1% 用户打开，指标正常再逐步放量，出问题先把开关关掉——关开关比回滚快得多，因为它不需要重新部署，也不影响同一版本里的其他改动。

# 开关的取值要能审计：谁改的、什么时候改的、改之前是什么
# 配置中心里的一条记录大致长这样
{
  "key": "order.new_pricing",
  "enabled": true,
  "rules": [
    {"type": "percentage", "value": 5},
    {"type": "whitelist", "value": ["uid:1001", "uid:1002"]}
  ],
  "owner": "team-order",
  "expire_at": "2026-12-31"
}

# 代码里的原则：先判开关，再走逻辑；默认值必须是"关闭"
# flag 的默认值决定了配置中心挂掉时的行为，这一条比开关本身更重要

# 排查"为什么这个用户看到了新功能"：先查开关快照，再查用户分桶
# 开关评估要能打印出命中规则，否则线上问题无法复现
默认值的方向很关键。开关默认关闭，配置中心挂了最坏是功能不生效；开关默认开启，配置中心挂了就是全量生效，而且你失去了关闭它的手段。凡是能造成写入或资损的开关，默认必须是关。

面试落点：「Feature Flag 的本质是把部署和发布解耦。发布开关是短期的，功能全量后要删；运维开关是长期的，用来做降级。开关的成本是债务，所以要有 owner 和过期时间。它比回滚快，因为不需要重新部署，但前提是默认值要安全，配置中心挂了不能把功能全放开。」

模块 7

发布前检查清单：能照着念的那种

清单的价值不在于全面，而在于在紧张的时候不用靠记忆。下面这份可以直接抄进发布单，每一项都要有明确答案，答不上来的那一项就是风险点。

类别要确认的事
变更内容这次改了什么、影响哪些接口和下游、有没有不兼容的接口契约变化
数据变更有没有 DDL / DML；是否向前兼容；能否在旧版本运行时执行；回填是否分批；有没有长事务
配置变更新增了哪些配置项、默认值是什么、各环境是否已配、配置中心不可用时行为如何
依赖依赖的服务 / 中间件版本是否兼容；对方是否已知晓；限流和超时是否有调整
容量新版本资源请求是否变化；副本数够不够；数据库连接池、缓存容量是否需要调整
观测关键指标、日志、告警是否覆盖新逻辑；出问题看哪几个面板
回滚回滚命令是什么、多久能完成、旧镜像和旧配置是否还在、数据能否兼容
人与时间谁执行、谁观察、谁决策回滚；避开业务高峰和上下游发布窗口
验证发布后跑哪几条冒烟用例；观察窗口多长；达到什么条件判定成功

这份清单里最容易空着的是「回滚多久能完成」和「达到什么条件判定成功」。前者决定你敢不敢发，后者决定你会不会在指标已经恶化时还在等「再看看」。把判据提前写死，是防止发布期间情绪化决策的唯一办法。

还有一条经验：一次发布只改一件事。把「升级依赖」「改配置」「上功能」打包在一起，出问题时你无法判断是哪个引起的，回滚也会把三件事一起撤掉。变更越小，定位越快，回滚越便宜。

# 发布前 5 分钟能跑完的自动检查，写进脚本比写进文档有用
# 1. 确认没有长事务（MySQL）
SELECT id, time, state, LEFT(info, 80)
FROM information_schema.processlist
WHERE time > 60 AND command != 'Sleep';

# 2. 确认目标集群当前是健康的：没有未完成的滚动更新
kubectl rollout status deployment/shop-api -n prod --timeout=5s
kubectl get pods -n prod -l app=shop-api

# 3. 确认旧版本镜像还在，回滚有目标
docker manifest inspect registry.example.com/shop/api:1.8.2

# 4. 记录发布前的基线指标，事后对比才有依据
#    错误率、P99、QPS、数据库连接数，各存一份快照
面试怎么答：「发布单我只强制三件事：数据变更是否兼容、回滚命令和时间、成功判据。其他的可以简化，这三项缺一个就不能发。因为数据不兼容会让回滚失效，不知道回滚时间就没法决定要不要回滚，没有判据就会在指标恶化时继续等。」
模块 8

K8s 滚动发布：探针和优雅退出是怎么配合的

「滚动更新的时候有几十秒的 502」——这个现象在 K8s 上极其常见，而且原因往往不是应用有 bug，是三个默认配置各干各的，没人管它们的配合。

先把三个探针的分工说清。readinessProbe 决定这个 Pod 是否接收流量，失败只是从 Service 端点里摘掉，不重启；livenessProbe 决定是否重启容器，失败会杀掉重建；startupProbe 用于启动很慢的应用，成功之前不执行另外两个探针。三者混用是事故高发点：把 liveness 配成和 readiness 一样的检查，依赖一抖动容器就被重启，重启后又没准备好，形成雪崩式重启。

再看退出流程。Pod 被删除时，K8s 会并行做两件事：从 Service 端点里摘除、向容器发 SIGTERM。问题在于，摘除是异步的——kube-proxy、Ingress、外部负载均衡各有各的同步周期，这期间仍然有流量打向这个 Pod。如果进程收到 SIGTERM 立刻退出，这些流量就全部失败。

所以正确的组合是：preStop 里先 sleep 几秒（等端点摘除生效），然后再让进程收到 SIGTERM，进程收到信号后停止接收新请求、处理完在途请求再退出，总时间必须小于 terminationGracePeriodSeconds（默认 30 秒，超时会 SIGKILL）。

# 一份能用的 Deployment 片段：滚动参数 + 三个探针 + 优雅退出
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1              # 先多起 1 个，保证容量不下降
      maxUnavailable: 0        # 不允许同时少 Pod，发布期间容量只增不减
  minReadySeconds: 10          # 新 Pod Ready 后再等 10 秒才算可用，避免"刚就绪就崩"
  template:
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: api
          image: registry.example.com/shop/api@sha256:<digest>
          readinessProbe:
            httpGet: { path: /healthz/ready, port: 8080 }
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet: { path: /healthz/live, port: 8080 }
            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 5
          lifecycle:
            preStop:
              exec:
                # 等端点摘除传播完成，再让进程退出；同时在应用侧停止接收新请求
                command: ["sh", "-c", "sleep 10"]

为什么 maxUnavailable: 0 很重要？默认值通常是 25%，六个副本意味着发布期间可能只剩四个半在扛流量，如果这时候流量正好在涨，剩下的 Pod 会被压垮，然后连锁反应。代价是发布变慢、需要额外资源起新 Pod——这是用资源换稳定，值得。

还有一个配套项：PodDisruptionBudget。它约束的是「自愿中断」（节点排水、集群升级），不是 Deployment 的滚动更新。很多人在滚动发布出问题时去调 PDB，发现完全没效果，因为两者管的是不同的东西。PDB 保护的是「驱逐时至少留几个可用」，滚动更新看的是 maxUnavailable。

# 观察一次滚动发布：看副本替换过程有没有出现可用数为 0
kubectl rollout status deployment/shop-api -n prod
kubectl get deployment shop-api -n prod -w

# 出问题立刻暂停，保留现场再决定回滚还是继续
kubectl rollout pause deployment/shop-api -n prod
kubectl rollout resume deployment/shop-api -n prod

# 看 Pod 为什么没就绪：事件里通常写得很清楚
kubectl describe pod -n prod -l app=shop-api | tail -40

# 排水节点时验证 PDB 是否生效（会被 PDB 拦住或放行）
kubectl drain node-1 --dry-run=server
优雅退出要在应用里真的实现。preStop 的 sleep 只是拖延时间，如果进程收到 SIGTERM 后立刻 exit(0)，那 10 秒只是让你晚 10 秒失败。应用必须做三件事：停止接受新连接、等在途请求处理完（有上限）、关闭连接池和消费者。消费型服务还要先停止拉取新消息，再处理完手头的。

面试落点：「滚动发布 502 的根因是端点摘除和进程退出之间存在时间差。解法是 preStop sleep 加应用侧的优雅退出，总时长要小于 terminationGracePeriodSeconds。探针要分工：readiness 管流量、liveness 管重启、startup 管慢启动。滚动参数我一般设 maxUnavailable 为 0，用资源换发布期间的容量稳定。」

模块 9

9 个坑：每一条都能独立造成一次事故

这些不是「最佳实践建议」，是已经重复发生过很多次的具体错误。共同点是：当时看起来都没问题。

1
每个环境重新构建镜像
基础镜像和依赖都可能变，测过的和发出去的不是同一个东西。构建一次，用 digest 晋级。
2
用 latest 标签部署
不可追溯、缓存不可控、回滚没有明确目标。至少用 commit 哈希，最好直接认 digest。
3
把配置和密钥打进镜像
制品不再唯一，换环境就要重建；镜像一旦泄露，密钥跟着泄。配置运行时注入。
4
数据库破坏性变更和代码同批上线
重命名列、改类型、删列，任何一项都会让回滚失效。用 expand-contract 拆成多次兼容变更。
5
回滚方案只写在文档里，从没演练
真出事才发现旧镜像被清理、旧配置已删除、down 脚本不存在。回滚要定期演练，至少每次大版本前跑一次。
6
把 liveness 配成和 readiness 一样
依赖抖动时容器被反复重启，重启后又没准备好，形成雪崩。liveness 只该判断「进程是不是死了」。
7
没有 preStop 和优雅退出
端点摘除有延迟，进程立刻退出就会丢请求。preStop 等几秒 + 应用处理完在途请求，两边都要做。
8
开关只增不减，没人负责
代码里堆积几十个永久开关，两条分支都要测试，没人知道线上是开是关。每个开关要有 owner 和过期时间。
9
发布完立刻宣布成功
错误率、延迟、依赖压力都有滞后性。至少留一个观察窗口，把发布前的基线拿出来对比，而不是看「没报错」。

面试落点：讲一个具体的。比如「我们有次发布把 liveness 和 readiness 配成同一个接口，结果数据库抖动了一下，所有 Pod 同时被判定不健康然后重启，本来只是一个依赖慢查询，最后变成全站不可用。后来 liveness 只检查进程存活，readiness 才检查依赖」。这类回答的杀伤力在于，它说明你真的见过连锁反应。

自测

六道题

1. 「制品不可变」在发布流程里的准确含义是？
正确答案：构建一次，按 digest 晋级。镜像构建不是确定性的（基础镜像、依赖版本、时间戳都可能变），重新构建等于发一个没测过的新制品。tag 只是人类可读的别名，可以被覆盖，digest 由内容决定，才能保证「测过的就是发的」。
2. 需要把 orders.status 重命名为 state，且不能停机。正确做法是？
正确答案：expand-contract 分步走。同一次发布里改结构又改代码，会让新旧版本都无法读写，回滚直接失效。分步做的核心是保证任意相邻两个版本能同时读写同一份数据：先扩展、再双写、迁移、切读，最后单独一次发布收缩。
3. readinessProbe 失败时，K8s 的行为是？
正确答案：摘流量，不重启。readiness 管的是「能不能接流量」，失败只是暂时移出端点，恢复后自动加回。liveness 失败才会重启容器。把两者配成同一个检查，依赖抖动就会引发全量重启，这是很典型的事故链。
4. 滚动更新期间出现约 30 秒的 502，最可能的原因是？
正确答案：摘除延迟 + 立即退出。删除 Pod 时摘除端点和发送 SIGTERM 是并行发生的，各层负载均衡同步需要时间。解法是 preStop 里 sleep 一段等传播完成，同时应用侧实现优雅退出：停止接收新请求、处理完在途请求再退出，总时长要小于 terminationGracePeriodSeconds。
5. 关于蓝绿发布和金丝雀发布，说法正确的是？
正确答案：蓝绿整体切、金丝雀逐步放。蓝绿的优势是回滚极快（切回旧环境），但切换即全量，发现问题的能力和直接发布接近，且资源要翻倍。金丝雀用小流量暴露问题，关键是判据要覆盖入口、依赖和业务三层指标。两者都要求数据库向前兼容。
6. 「部署（deploy）」和「发布（release）」的区别，用 Feature Flag 怎么解释？
正确答案：部署是代码到位，发布是功能可见。把两者解耦后，未完成的功能可以先合并、先部署，由开关控制可见性；出问题时关开关比回滚更快，因为不需要重新部署。但发布开关是短期债务，功能全量后必须删除，否则代码里会积累两条永久分支。
