AI 运维面试：AIOps 与大模型在运维里的真问题

「用大模型做智能运维」的靠谱答案和忽悠答案只差一句：你有没有可验证的数据。

20:00
读之前先答一句：模型告诉你是 A 服务导致 B 报警，你怎么判断它说的是不是真的？
开始前

「我们的智能根因分析准确率很高」——接下来这句话会被追问

技术分享会上有人演示了一套「智能根因分析」：告警进来，系统直接给出根因服务，看起来非常漂亮。台下有人问了两个问题：「准确率的分母是什么？」「标注是谁做的、怎么确认标对了？」台上的人答不上来。这不是个例，这是这类项目最常见的死法。

先把判断放前面：AIOps 项目失败的头号原因不是模型不够好，是没有可验证的数据。你没法证明它有用，就没法说服值班同学用它；值班同学不用它，它就永远拿不到反馈数据；拿不到反馈，它就永远改进不了。这是一个死循环，而且它往往在演示成功之后才暴露。

听起来很厉害的说法一句追问就露馅靠谱的说法应该是什么
我们的根因分析准确率很高「准确率的分母是什么？标注集怎么来的？」「我们在自己的 N 条历史告警标注集上测了 Top-3 命中情况，数字是 X，样本量偏小，还在积累」
大模型能自动定位故障「它给出的是候选还是结论？错了谁负责？」「它输出带证据的候选排序，值班同学确认后才会执行动作，我们记录采纳与否用于改进」
告警减少了很多「有没有因为降噪漏掉过真实故障？」「压缩率是这个数，同时我们统计了误合并和漏报，各是多少，采样方式是这个」
我们做了智能运维平台「里面哪些是规则、哪些是模型？」「大部分是聚合规则和拓扑关联，模型只用在 XX 一处，因为别的地方规则更可靠」
本篇的一条硬规矩：我不引用任何「某某方案让告警减少 XX%」「某模型准确率 XX%」这类数字。这类数字换个环境就不成立，而且你无法验证它的口径。面试里你应该说的永远是「我用我自己的数据测出来是多少、样本量多大、怎么标的」。说不出这些，就老实说「我们还在积累标注」。这比引用别人的数字可信得多。
场景
AIOps 真正落地的四类事：降噪、候选推荐、日志聚类、变更风险提示。都不是「自动决策」。
数据
告警、工单、变更、拓扑。数据质量决定上限，模型选择只在其次。
评估
指标必须写清分子分母和可测方法。没有标注集就没有准确率，只有感觉。
护栏
只读、人工确认、可灰度、可回滚、留反馈。缺一条就不该上线。

这篇按这个顺序写：先说清楚 AIOps 在解决什么、不解决什么；再讲四类真实场景和每类怎么评估；接着是根因推荐最关键的边界（相关性不是因果）；然后是大模型的可用点与不可用点、数据从哪来；最后是评估护栏、成本延迟，和一套讲得出口的方案话术。

面试落点：「我讲 AIOps 一定先说边界：它给的是候选和排序，不是结论；判断仍然由人做。我讲效果一定带上口径和样本量，说不出就说还在积累。因为这类项目死得最多的原因不是模型差，是没有可验证的数据。」

模块 1

AIOps 到底在解决什么：先把「不是什么」说清

「AIOps」这四个字被用得太宽，宽到可以把一个 grep 脚本也叫 AIOps。面试官问你 AIOps，第一句就该划边界——能划清边界的人，说明他真的做过，而不是看过宣传材料。

一个可用的定义：AIOps 是用统计和机器学习方法，在人力跟不上的环节，把「可能相关的信息」压缩成人能快速消化的候选集。注意三个关键词：人力跟不上（说明它解决的是规模问题，不是难度问题）、压缩（说明它的产出是更少的候选，不是更多的结论）、候选集（说明最终判断权在人手里）。

它解决的问题为什么人做不了它不解决的问题
告警太多，人看不完一次故障能产生成百上千条告警，值班同学根本不可能逐条看判断这条告警要不要处理（需要业务上下文）
候选根因太多，排查顺序靠猜一次变更可能同时影响十几个服务，人靠经验排顺序效率低给出确定无疑的根因（需要可干预的验证）
日志量太大，看不出模式每天几千万行日志，人没法人工归类判断某个新出现的日志模板是不是故障信号
历史经验散落在工单和复盘里文档没人读，出事时想不起来替代值班同学的责任判断

有三个前提，缺一个就不要启动：先有可观测性数据（指标、日志、链路至少有一类覆盖到位，否则模型没东西可学）、先有历史记录（过去的事故有没有留下时间线和结论，没有就是零样本）、先有可执行的动作（就算模型说对了，如果没有对应的止损动作，工作就停在推荐这一步，价值有限）。「我们数据还没采全就想做根因分析」是最常见的起手式错误。

一个必须说出口的边界：不要让模型直接执行变更。至少在你能回答下面三个问题之前不要：这个动作可回滚吗？误触发的代价是什么？有没有人在回路里确认？低风险、可回滚、有灰度这三条满足，才谈得上自动执行；而且即便如此，也建议先从「自动执行但只作用于非核心服务」开始。把「自动重启」这种动作交给一个会出错的模型，是拿可用性赌一个小概率。

还有一个反直觉的经验：很多号称 AIOps 的系统里，真正有用的部分是规则，不是模型。按服务和拓扑聚合告警、按时间窗合并、按依赖关系找上游——这些是确定性规则，效果稳定、可解释、维护成本低。模型只在「规则覆盖不到、且有足够标注数据」的地方才划算。主动说出这一点非常加分，因为它表明你知道什么时候不该上模型。

面试落点：「我把 AIOps 定义成『在人力跟不上的地方压缩候选集』，它给候选不给结论。启动前要有三个前提：可观测性数据、历史记录、可执行的动作。另外我先说清楚哪些部分用规则——规则稳定可解释，模型只在有标注且规则覆盖不到的地方才用。」

模块 2

四类真实落地场景：每类都要有一个可测指标

判断一个 AIOps 场景值不值得做，只问一句：做完之后，你用什么数字证明它有用？答不上来的场景，做出来也推不动。

场景输入输出可测指标（要写清分子分母）
告警降噪告警流 + 拓扑 + 时间合并后的告警组压缩率 = 1 − 合并后条数 / 原始条数；误合并率、漏报数（人工抽检）
根因推荐告警组 + 拓扑 + 变更 + 历史带证据的候选排序Top-K 命中率（需标注集，K 要固定）；人工采纳率、误采纳率
日志聚类日志流模板列表 + 每模板计数模板数量（压缩比）；新模板发现率；模板漂移率
变更风险提示变更单 + 历史事故风险等级 + 相似历史高风险标记的命中情况；误报率（标了高风险但没出事的比例）

这四类的共同点是：每一类都有一个「不能用它自己证明自己」的陷阱。告警降噪的压缩率可以靠无脑合并做到很高，代价是漏掉真实故障；根因推荐的命中率可以靠把候选给得很宽来刷高，代价是等于没推荐；日志聚类的模板数可以靠粗粒度合并压到很少，代价是丢失区分度。所以每一类都必须配一个反向指标——降噪配漏报，推荐配候选数量和采纳率，聚类配模板区分度。

# 告警降噪最朴素也最有效的一层：按指纹聚合（这属于规则，不属于模型）
# 指纹 = 告警名 + 服务 + 集群 + 实例维度，时间窗内合并
import json, hashlib
from collections import defaultdict

def fingerprint(alert):
    # 只取稳定的标签，剔除 value / 时间戳这类每次都变的东西
    keys = ['alertname', 'service', 'cluster', 'severity']
    raw = '|'.join(str(alert['labels'].get(k, '')) for k in keys)
    return hashlib.md5(raw.encode()).hexdigest()[:12]

groups = defaultdict(list)
for a in alerts_in_window:
    groups[fingerprint(a)].append(a)

# 输出：每个指纹一组，组内计数 + 首次时间 + 代表样本
for fp, items in sorted(groups.items(), key=lambda x: -len(x[1])):
    print(fp, len(items), items[0]['startsAt'], items[0]['labels'])

这段代码看起来平平无奇，但它是绝大多数降噪系统里贡献最大的一块。先把这一层做扎实，再谈模型。很多团队跳过这一步直接上聚类算法，效果不好又查不出原因，最后发现是因为标签命名不规范（同一个服务在不同团队里写了三种名字），聚合根本聚不起来。

判断「值不值得用模型」的三问：① 规则能不能覆盖大部分情况？能的话先用规则；② 有没有带标签的历史数据，量级够不够？没有就先攒数据；③ 错了的代价能不能接受？不能接受就必须保留人工确认环节。三问里只要有一个答不好，就别上模型，先把数据和规则做好，收益更确定。

面试落点：「我做场景选择只看一件事：做完用什么数字证明。而且每个正向指标都要配一个反向指标——降噪配漏报、推荐配采纳率和候选宽度、聚类配模板区分度。只报压缩率不报漏报的降噪方案，我没法判断它是不是在靠无脑合并刷数字。」

模块 3

告警降噪：聚合之后，相似历史从哪来

降噪分三层，顺序不能反：先聚合（把同一件事的告警并成一条）→ 再抑制（有上游故障就压掉下游的连锁告警）→ 最后才是相似历史匹配（这条告警以前出现过吗、当时怎么处理的）。跳过前两层直接做第三层，效果一定不好。

聚合：按指纹和时间窗合并。关键是标签规范——同一个服务在不同团队里叫法不同，聚合就失效。这一步是数据治理，不是算法。
抑制：靠拓扑和依赖关系。数据库挂了，上层二十个服务都会告警，真正需要看的只有一条。这一层依赖 CMDB 或服务依赖图的准确性，CMDB 过期是这一层最常见的失效原因。
相似历史：给这条告警附上「上次是怎么处理的」。做法是把告警的标签和文本做成向量或关键词集合，去历史工单里检索最相近的几条。
排序与展示：给候选不给结论。展示「最近三次同类告警的处理记录 + 链接」，让值班同学自己判断，而不是弹一个「建议执行 X」。

相似历史这一步有个绕不开的问题：「相似」的判定标准是什么？如果只看告警名，同一告警名在不同业务上的处理方式可能完全不同；如果把全文都算进去，又会因为 IP、ID 这类变量导致相似度全部失效。实用做法是去掉变量部分再比——把 IP、数字、UUID、时间戳替换成占位符，剩下的模板文本才是有效的比对对象。

# 把日志/告警文本里的变量替换成占位符，再做相似度比较
import re

PATTERNS = [
    (re.compile(r'\b(?:\d{1,3}\.){3}\d{1,3}\b'), '<IP>'),
    (re.compile(r'\b[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\b'), '<UUID>'),
    (re.compile(r'\b\d+\b'), '<NUM>'),
]

def to_template(text):
    for pat, repl in PATTERNS:
        text = pat.sub(repl, text)
    return text

# 同一类错误的两种写法，归一化后应得到同一个模板
print(to_template('connect 10.0.0.12:3306 failed after 3000 ms'))
print(to_template('connect 10.0.0.31:3306 failed after 500 ms'))
指标怎么算（分子 / 分母）为什么必须测
压缩率1 − 合并后通知条数 / 原始告警条数正向收益，但单独看会被无脑合并刷高
误合并率抽样中被判为「不该合并」的组 / 抽样组总数反向约束。合并过头会把不同故障压成一条
漏报因降噪而未被通知、但事后确认需要动作的告警数最关键的指标。它衡量的是损失，而且只能靠复盘回溯
无动作告警率值班同学未做任何处理的通知 / 通知总数衡量降噪是否降到了点子上，也衡量告警设计本身
「噪声标签从哪来」是这一节最难也最容易被跳过的问题。你要判断一条告警是不是噪声，前提是你知道这条告警当时该不该动作——这个信息只存在于值班同学的脑子里，事后就丢了。三个可行的来源：值班同学在告警系统里点「有用 / 噪声」（成本最低但要设计得足够轻）、复盘报告里记的时间线（质量最高但只覆盖大事故）、以及事后回溯标注（最慢，但能补历史数据）。没有这个标签，你口中的「降噪效果」就只是条数变少了，不等于变好了。

面试落点：「降噪我分三层：聚合、抑制、相似历史，前两层是规则和拓扑，第三层才用相似度。指标我至少报三个：压缩率、误合并率、漏报。其中漏报最关键也最难测，只能靠复盘回溯。噪声标签来自值班同学的即时反馈和复盘记录，没有标签就只能说条数变少了，不能说变好了。」

模块 4

根因推荐的边界：相关性不是因果

这是整篇最重要的一节。模型说「A 服务导致 B 告警」，它真正在说的是：历史上 A 告警之后 B 也告警，这种情况出现了很多次。这句话和「A 导致 B」之间，隔着至少三种可能。

混淆来源具体表现为什么危险
共同原因一次变更同时影响 A 和 B，模型学到「A 先于 B」，于是把 A 当成 B 的原因你去修 A，B 还在报警，而真正的根因是那次变更
时序巧合两个周期性问题（定时任务、连接池轮换）恰好在同一时段出现样本量足够大时纯巧合也能产生很高的相关性
采样偏差你只保留了事故时间段的数据，正常时段被丢弃在只有正样本的数据上，任何东西看起来都相关
观测偏差某个服务监控更完善，所以它的告警总是「先出现」模型学到的是「谁先被观测到」而不是「谁先出问题」

怎么降低误信？四条，按有效性排：

要求输出证据链，而不是单一结论。「A 可能是原因，依据是：A 的变更在 14:03、A 的错误率在 14:04 抬升、B 的依赖中只有 A 出了错」——有证据才能被人检验，只有结论没法检验。
明确标注「候选」而不是「根因」。产品上写「可能的原因（按可能性排序）」和写「根因：A」，会引导值班同学做出完全不同的行为。
用干预验证代替观察验证。最可靠的因果证据来自干预：把 A 摘掉或回滚，看 B 是否恢复。日常演练里可以做，事故中往往来不及——所以事故后的复盘要把「当时的判断对不对」记下来，这才是积累因果知识的地方。
保留人工否决的记录。值班同学选了第 3 个候选而不是模型给的第 1 个，这个信号极其宝贵，是改进模型的燃料。不记录就浪费了。
# 一个刻意做对了的「根因候选」输出结构：带证据、带置信、带人工确认位
{

「置信度 87%」这种数字是危险的。它看起来是一个概率，实际上往往是模型内部的相似度分数或softmax 输出，并没有校准过——它不代表「87% 的概率是对的」。把它显示成百分比，会让人误以为它很精确，从而放弃验证。更诚实的做法是给等级（高/中/低）或者干脆只给排序，并明确写出「这是候选排序，不是结论」。

还有一个必须提醒的边界：模型只在它见过的模式里可靠。遇到全新的故障模式（新的组件、新的失败方式），它的输出往往是「最像的历史案例」，而这个「像」可能只有表面相似。越是需要创造力的故障，模型越帮不上忙——这恰恰是最需要人的时候。所以在设计上要让系统知道「我不确定」，而不是永远给一个答案。

面试落点：「模型给出的相关性不等于因果，常见混淆有共同原因、时序巧合、采样偏差和观测偏差。我要求它输出证据链而不是结论，产品上写『可能的原因』而不是『根因』，并且记录值班同学最终选了哪个候选。置信度我倾向给等级不给百分比，因为未校准的分数会让人误以为很精确。」

模块 5

大模型在运维里的可用点：四个能用，三个别碰

大模型在运维里最靠谱的定位是「翻译器和摘要器」：把机器语言翻译成人话，把一堆材料压成一段可读的文字。它不是诊断引擎，也不该是。

可用点它解决什么必须配的护栏
报错与堆栈解读把一长串堆栈翻译成「可能是哪几类问题，先查什么」输出要给出方向而不是结论；附上「这只是可能方向」
Runbook 初稿生成从历史工单和复盘里生成一份处理步骤初稿人必须审；标注「未经演练验证」；链接到原始工单
故障摘要与时间线整理把告警、变更、日志片段压成一段交接用的文字只做摘要不做推断；关键数字要能回溯到原始指标
内部知识问答检索内部文档回答问题必须带引用链接；检索不到就明确说没有，不许编
别碰的点为什么
直接执行变更模型会出错，而变更的代价可能是业务中断。要执行就得有人工确认、可回滚、灰度三件套
凭空判断根因没有证据支撑的结论无法被检验，值班同学也无法快速证伪，只会浪费时间
输出精确数字让它算「这个月可用性是多少」很容易给出一个看似合理但错误的数字。数字应该由监控系统查出来，不是由模型生成
# 一个刻意保守的 prompt 骨架：限定输入、要求结构化、要求承认不知道
prompt = f"""
你是运维助手。只使用下面提供的材料回答问题，不得引入材料之外的信息。
如果材料中找不到答案，就输出 {{"answer": null, "reason": "材料不足"}}。
输出必须是 JSON，且 citations 里每条都要对应材料中的编号。

材料：
{context_with_ids}

问题：{question}
"""

# 期望的输出模式（用 schema 校验，校验不过就当作失败，不展示给用户）
schema = {
    "type": "object",
    "required": ["answer", "citations", "confidence"],
    "properties": {
        "answer":     {"type": ["string", "null"]},
        "citations":  {"type": "array", "items": {"type": "string"}},
        "confidence": {"enum": ["高", "中", "低", "无法判断"]}
    }
}

这段 prompt 里有两个刻意的约束值得抄：「只使用提供的材料」和「找不到就输出 null」。前者把幻觉的空间压到最小，后者给了模型一条体面的退路——如果强制它必须回答，它就只能编。「允许说不知道」是抑制幻觉最有效的一个设计。

把日志和配置发给外部模型服务之前，先做两件事。一是脱敏：IP、域名、 token、密钥、用户标识都要替换掉，日志里这些东西比你想的多；二是确认合规：数据能不能出网、能不能给第三方处理，这属于公司政策和法规问题，具体以你所在单位的合规要求为准，不要照抄别人的做法。运维数据往往包含了比想象中更多的敏感信息，堆栈里可能带内网域名，日志里可能带用户手机号。

还有一点容易被忽略：模型输出要能被校验。用 JSON schema 约束输出结构，校验不通过就当作失败（而不是把半截文本展示给值班同学）；对于输出里的服务名、指标名，要做一次「这个东西真的存在吗」的校验（去 CMDB 或指标元数据里查）。校验这一步成本很低，但能挡掉大部分「看起来很对其实是编的」输出。

面试落点：「我把大模型定位成翻译器和摘要器：报错解读、Runbook 初稿、故障摘要、带引用的知识问答。不让它执行变更、不让它凭空定根因、不让它输出精确数字。护栏上我做三件事：限定只用给定材料、允许它回答『不知道』、用 schema 校验输出并对服务名做存在性校验。」

模块 6

数据从哪来：四类源，以及它们各自有多脏

AIOps 的上限由数据质量决定，这一点在业内没有争议，但在项目里最常被忽略——因为数据治理枯燥、不出成果，而模型演示好看。结果就是大家花三个月调模型，最后发现是数据对不上。

数据源能提供什么典型的脏法
告警发生了什么、什么时候、严重级别命名不规范（同一服务三种写法）、级别乱填、无人认领的历史规则堆积
工单处理过程、最终结论、耗时结论字段空着、「已处理」三个字敷衍了事、处理和告警没有关联 ID
变更谁在什么时候改了什么最不完整的一类。手工改配置不登记、紧急发布不走系统、改了什么字段没记录
拓扑 / CMDB谁依赖谁，用于抑制和传播分析过期。服务下线了关系还在，新依赖没录进去，导致抑制规则失效

四个必须做的治理动作，按优先级：统一标识（同一个服务在所有系统里必须叫同一个名字，这一条做不到后面全白搭）、时间对齐（不同源的时钟必须同步，否则时序相关性分析的结果全是假的）、补齐关联（告警、工单、变更之间要有可关联的 ID 或时间窗，不然样本拼不起来）、结论字段强制（工单关闭时必须填「根因分类」和「处理动作」，这是最有价值也最难推的一项）。

「标注集」从哪来，是这一节最实际的问题。三个来源，按性价比排：① 值班同学的即时反馈（在告警旁边加一个「有用 / 噪声 / 已处理」的按钮，成本最低但要求设计得足够轻，一次点击就能完成）；② 复盘报告（质量最高，但只覆盖大事故，样本量小）；③ 事后集中标注（挑一段时间的历史告警，让资深同学集中标几百条，用来做第一批种子集）。建议先做第三种拿到种子集，再用第一种持续积累——反过来做会因为一开始没有基线而无法判断质量。

样本量这件事要诚实：几百条标注能支撑一个初步的离线评测，但要支撑「线上效果可信」通常需要更多，而且必须包含足够多的故障类型——如果 80% 的样本都是同一类故障，模型在这类上表现好没有意义。样本的分布比样本的数量更重要，这一点在面试里说出来很加分。

面试落点：「数据这块我先做四件事：统一服务标识、对齐时钟、补齐告警与变更的关联、强制工单填根因分类。其中最难推的是最后一项，但它的价值最高。标注集我先用事后集中标注拿几百条种子，再用值班同学的即时反馈持续积累。样本我会关注类型分布而不只是数量。」

模块 7

评估与护栏：指标要可测，动作要有人确认

这一节是整篇的及格线。讲 AIOps 方案不讲评估，等于没讲。而评估的第一条规矩是：每个指标都要写清楚分子和分母，以及这个数字是怎么采出来的。

指标分子 / 分母采集方式常见作弊方式
压缩率1 − 合并后通知数 / 原始告警数告警系统计数无条件合并，压到 1 条
误合并率抽检中被判「不该合并」的组 / 抽检组数人工抽检，必须有抽样方案只抽明显正确的组
漏报因降噪未通知但事后确认需动作的事件数复盘回溯，每周统计不复盘，所以永远是 0
Top-K 命中率正确根因出现在前 K 个候选中的样本数 / 标注样本总数离线评测，K 必须固定把 K 调大，或者候选给得很宽
人工采纳率值班采纳模型首推候选的次数 / 总推荐次数线上埋点只统计采纳的，不统计忽略的
人工否决率值班选了非首推候选的次数 / 总推荐次数线上埋点—（这是最重要的改进信号）

离线评测和线上效果之间有一道必须说清的鸿沟：离线命中率高，不代表值班同学会用。因为线上还有延迟、展示位置、信任度、以及「这个建议我能不能快速验证」这些因素。所以上线后必须测的是行为指标（采纳率、否决率、处理时长变化），而不只是准确度。

# 评估脚本的骨架：把「可测」这件事写成代码，口径才不会飘
def evaluate(preds, labels, k=3):
    # preds: {incident_id: [候选1, 候选2, ...]}   labels: {incident_id: 真实根因}
    hit = sum(1 for i, p in preds.items()
              if i in labels and labels[i] in p[:k])
    total = sum(1 for i in preds if i in labels)
    return {
        'k': k,
        'labeled_total': total,                      # 分母，必须报出来
        'top_k_hit': hit,
        'top_k_hit_rate': hit / total if total else None,
        'unlabeled': len(preds) - total,
    }

# 关键：同时报样本量和未标注数量。
# 只报一个「命中率」而不同时报分母，等于没有评估。
只读优先。第一阶段只做展示和推荐，不做任何写操作。这一条能消掉绝大部分风险。
人工确认环节不可省。任何会影响系统的动作都要有人点确认，并且记录这个人是谁、他改了什么——既是审计，也是反馈数据。
灰度和可回滚。先在一个非核心服务或一个值班小组里开，观察一段时间；出问题能一键关掉回到原来的流程。
反馈闭环。采纳、否决、误报都要回流成标注，定期重训或调规则。没有闭环的系统，上线那天就是它最好的一天。
「评估指标要可测」这句话的具体含义：你能说清楚这个数字是谁在什么时候、用什么方法采出来的，并且换一个人按同样的方法能采出同样的数。达不到这个标准的指标（比如「值班同学觉得好用」）可以作为参考，但不能作为验收标准。验收标准必须是可以重复测量的。

面试落点：「评估我要求每个指标写清分子分母和采集方式，并且报数时同时报样本量。离线我测 Top-K 命中率（K 固定），上线我测行为指标——采纳率、否决率、处理时长变化，因为离线准不等于值班会用。护栏四条：只读优先、人工确认、灰度可回滚、反馈闭环。」

模块 8

成本与延迟：大模型该放在链路的哪一环

一个常见的设计错误：把大模型调用放在告警触发的即时路径上。告警是秒级甚至毫秒级发生的，而大模型调用是百毫秒到秒级的，这个延迟会让你的告警系统变成瓶颈，而且成本高得离谱——大部分告警是重复的。

位置时效性要求适合放什么
告警触发即时路径毫秒到秒级只放规则：聚合、抑制、路由。不放模型调用
聚合之后、通知之前秒到十秒级可以放：轻量相似度检索、历史案例匹配
事故进行中，按需触发秒级可接受适合放：大模型做堆栈解读、故障摘要
事故后异步分钟到小时级适合放：生成复盘初稿、更新 Runbook、补标注

控制成本的四招，按有效性排：缓存（同一指纹的告警复用同一次结果，降噪之后重复告警本来就多，命中率很高）、裁剪上下文（只把必要的片段送进去，不要整份日志）、降频（不是每条告警都要调用，只在人工点开或事故升级时调用）、小模型兜底（分类、聚类这类任务用小模型或传统方法就够了，只有需要生成和理解时才用大模型）。

# 缓存是最便宜的一招：降噪之后相同指纹的告警占绝大多数
import hashlib, time, json

cache = {}   # 生产用 Redis，并设置 TTL

def summarize(alert_group, llm_call, ttl=3600):
    key = hashlib.md5(
        json.dumps(alert_group['template'], sort_keys=True).encode()
    ).hexdigest()
    hit = cache.get(key)
    if hit and time.time() - hit['ts'] < ttl:
        return hit['result'], True          # True 表示命中缓存
    result = llm_call(alert_group['sample'])
    cache[key] = {'ts': time.time(), 'result': result}
    return result, False

# 必须埋点：调用次数、缓存命中率、单次延迟、单次成本
# 没有这几个数字，你就无法回答「这套东西贵不贵」
成本这块不要凭感觉，要埋点。至少四个数字：调用次数（按场景分开）、缓存命中率、单次延迟的 P50/P99、单次成本。有了这四个数，你才能回答「这个场景值不值得用大模型」——有些场景算完会发现，用规则或者查表就能达到 80% 的效果，成本却低两个数量级。具体费用以你使用的服务和当时价格为准，不要引用别人的报价。

还有一个设计上的取舍：降级路径要先想好。模型服务不可用、超时、返回格式不对，这三种情况都要有明确行为——通常是「跳过这一步，按原流程走」而不是「阻塞等待」或「展示一个空结果」。AI 功能是增强，不能成为单点故障。这一点要在设计文档里写死，而不是留给实现的人临场决定。

面试落点：「大模型我不放在告警触发的即时路径上，那条路要毫秒到秒级。我放在聚合之后、或者事故进行中按需触发、或者事后异步。成本控制靠缓存、裁剪上下文、降频和小模型兜底，并且埋四个点：调用次数、缓存命中率、延迟分位、单次成本。降级路径必须预设：模型不可用就跳过它走原流程，AI 功能不能成为单点。」

模块 9

面试话术：讲一个有边界的方案

「你们用 AI 做了什么」这道题，满分答案的关键词是边界。讲得越大越像没做过，讲得越具体越可信。主动说出「我们没做什么、为什么不做」，比多报一个功能更有说服力。

先给场景和痛点。「我们值班同学平均每次故障要处理几十条告警，大部分是连锁告警。这不是难度问题，是规模问题。」——给现象，不给愿景。
再说数据和前提。「我们先做了两件事：统一了服务标识，把告警和变更记录关联起来。因为如果这两样对不上，后面做什么都不成立。」
再说方案，并且说清哪部分是规则。「降噪那一层其实是规则：按指纹聚合、按拓扑抑制。模型只用在相似历史匹配上，因为前面那两层规则更可靠也更可解释。」
最后说边界和评估。「它只给候选不给结论，值班同学确认后才会有动作。我们测压缩率、误合并率、漏报，还有采纳率和否决率。样本量目前还不大，数字我只能说在积累中。」
被追问怎么答
「准确率多少？」「我不引用别人的数字。在我们自己的标注集上，Top-K 命中的情况是 X，样本量 N，分布偏重某几类故障，所以这个数字只能说明在这几类上的表现。」
「会不会误判？」「会。所以它给的是候选排序，不是结论；产品上写的是『可能的原因』。我们记录值班同学最终选了哪个，否决的情况是最有价值的改进信号。」
「为什么不用大模型做根因？」「因为大模型给的是基于文本相似度的猜测，而根因需要可干预的验证。它的价值在翻译和摘要——把堆栈说成人话、把材料压成摘要。」
「它出错了谁负责？」「人不因为它的建议而免责。所有会影响系统的动作都有人点确认，并且记录是谁确认的。它不承载责任，只提供信息。」
「投入产出怎么算？」「我会算三笔：省下的值班时间、漏报造成的成本、以及这套系统本身的调用与维护成本。第三笔经常被忘，但它决定了能不能长期跑下去。」
一段可以直接说出口的收尾：「我做这类项目的原则是三句话：相关性不是因果，所以要给证据不给结论；动作必须有人确认，所以要设计人工环节不能省；效果必须可测，所以每个指标都要写清分子分母。在这三条都满足之前，我宁愿只做规则聚合——因为规则至少稳定、可解释、出了错我知道为什么。」

面试落点：「我讲方案一定带上边界：哪部分是规则、模型用在哪一处、它给候选不给结论、动作必须有人确认、评估指标怎么采。并且我会主动说我们没做什么——因为这类项目的失败大多来自把边界划得太大，而不是模型不够强。」

模块 10

9 个坑：每一个都能让项目悄悄死掉

这些坑的共同特点是不会立刻失败。演示能过、领导满意，然后在半年内因为没有可验证的价值而被悄悄放弃。

1
把相关性当成因果
「A 之后总是 B」可能是共同原因、时序巧合或采样偏差。要输出证据链、标注为候选、并用干预去验证。只给结论的系统没法被检验。
2
没有标注集就谈准确率
准确率的分母是带标签的样本。没有标注就只能说「条数变少了」，不能说「变准了」。先攒几百条种子集再谈评估。
3
让模型直接执行变更
模型会出错，而变更的代价可能是业务中断。要执行就得有人工确认、可回滚、灰度三件套，并且先从非核心服务开始。
4
只看离线评测就宣布成功
离线命中率高不代表值班会用。上线后必须测行为指标：采纳率、否决率、处理时长变化，而不只是准确度。
5
降噪只报压缩率
压缩率可以靠无脑合并刷高。必须同时报误合并率和漏报，其中漏报只能靠复盘回溯，最难测也最关键。
6
多源数据时间没对齐就做时序分析
各机器的时钟偏移会让「谁先谁后」完全失真，相关性分析的结果全是假的。先确认 NTP 真的在同步，再用已知事故反查偏差。
7
把日志原文直接发给外部模型
日志里常有 IP、token、用户标识。发送前要脱敏，并确认数据出网和第三方处理的合规要求——具体以所在单位的政策为准。
8
用「智能运维」包装一个规则引擎
用规则不丢人，规则稳定可解释。问题是包装之后没人敢质疑，也无法判断哪部分真的有效。诚实标注哪部分是规则、哪部分是模型。
9
没有人工反馈闭环
采纳、否决、误报不回流，模型永远停在上线那天的水平。反馈按钮要设计得足够轻，一次点击就能完成，否则没人用。

自测

六道题

1. 模型发现「A 服务告警之后 B 服务总是跟着告警」，因此判断 A 导致 B。这个推理最可能的问题是什么？
正确答案：可能是共同原因或巧合。共现和时序只能提供相关性，真正的因果需要干预验证（把 A 摘掉或回滚，看 B 是否恢复）。常见的混淆还有采样偏差（只保留事故时段数据）和观测偏差（谁监控更完善谁就先出现）。所以输出应该给证据链并标注为候选。
2. 一个告警降噪方案汇报「压缩率大幅提升」，你还应该要求它补充哪两个指标？
正确答案：误合并率和漏报。压缩率可以靠无条件合并刷到很高，代价是把不同故障压成一条、或者把真实故障吞掉。误合并率靠人工抽检（要说明抽样方案），漏报靠复盘回溯。只报正向不报反向指标的降噪方案无法评估。
3. 用大模型做内部知识问答，下面哪一项是必须有的护栏？
正确答案：限定材料 + 允许说不知道 + 带引用。限定材料把幻觉空间压到最小，允许「不知道」给了模型一条体面的退路（强制它必须回答就只能编），引用让值班同学能快速验证。水印不解决准确性问题，模型自评也不构成校验。
4. 启动一个根因推荐项目，下面哪个前提最容易被忽略却最致命？
正确答案：没有带标签的历史样本。评估需要分母（标注样本总数），改进需要反馈（值班同学最终选了哪个候选）。没有标注集就只能说「条数变少了」，谈不上准确；没有反馈闭环，系统上线那天就是它最好的一天。标注可以先用事后集中标注拿种子集，再用即时反馈积累。
5. 把大模型调用放在「告警触发的即时路径」上，最主要的问题是什么？
正确答案：延迟和成本不匹配。告警是秒级甚至毫秒级发生的，大模型调用是百毫秒到秒级，会变成瓶颈；而且降噪之后相同指纹的告警占绝大多数，重复调用成本极高。正确做法是放在聚合之后、按需触发、或事后异步，并配合缓存。
6. 关于让模型「自动执行止损动作」，最稳妥的态度是？
正确答案：三件套 + 灰度 + 降级。模型会出错，动作要有人工确认、可回滚、可灰度三条保障，并从非核心服务开始。同时必须预设降级路径：模型不可用或超时就跳过它走原流程——AI 功能是增强，不能成为单点故障。自动执行与否不看「准确率高不高」，看「误触发的代价能不能接受」。
