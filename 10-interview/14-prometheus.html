开始前

三个现场，三种「看起来对」的错

面试官在白板上写下一行 avg(rate(http_request_duration_seconds_sum[5m])) / avg(rate(http_request_duration_seconds_count[5m]))，问你「这是 P99 吗」。你说不是，他接着问「那你写一个」。这一问能筛掉七成人。

Prometheus 的题有个特点：语法谁都能背，但语义错一错就是量级错。面板上的数字看着很正常，结论却是反的。下面三个现场，都是「代码没报错、图也画出来了、结论是错的」。

现场常见写法错在哪
P99 面板显示 180ms，用户投诉 3 秒对分位数再取 avg分位数不是可加量。十个实例的 P99 求平均，既不等于全局 P99，也不代表任何一台
QPS 曲线全是尖刺和断点rate(x[1m])，抓取间隔也是 1m窗口里常常只有一两个样本，边界一对不齐就外推失败，返回空值
一次发版后 Prometheus 内存翻五倍URL 直接做了标签路径里带订单号，每个请求都是新 series。不是「监控变多了」，是基数被打爆了
为什么先摆这三个：它们分别对应「聚合语义」「时间窗口」「标签设计」三类错误，也是面试追问的三条主线。你把这三条讲清楚，比背二十个函数有用得多——因为函数可以查文档，语义错了查不出来。

这一篇按「数据怎么进来 → 怎么存 → 怎么算 → 怎么告 → 怎么长期留」走一遍，每一节都落一句能直接说出口的话。凡是我给具体默认值的地方，都以你环境的 --help 和官方文档为准，版本之间会变。

面试落点：「Prometheus 的坑大多不在语法，在语义。比如分位数不能跨实例平均，rate 的窗口必须覆盖足够多的抓取点，标签值一旦无限增长就会把 TSDB 打爆。这三件事我在线上都踩过。」

模块 1

Pull 模型与 TSDB：为什么是拉，以及拉不到时发生了什么

「为什么 Prometheus 用拉不用推？」标准答案是「拉更简单、好调试」。这个答案没错，但它答的是现象，不是设计取舍。追问一句「那五分钟就跑完的批处理任务怎么监控」，很多人就卡住了。

拉的本质是把「谁是被监控对象」这个知识放在服务端。目标列表来自服务发现（Kubernetes、Consul、文件、DNS），Prometheus 自己决定去谁那里、多久去一次、超时多久。这带来四个直接好处：服务端天然知道目标活着没有（up 这个指标就是抓取行为本身的副产品）；采集节奏由监控系统控制，不会被业务突发打崩；调试时 curl 一下目标的 /metrics 就能看到原始数据；目标下线后 series 自动进入 stale，不需要谁去通知谁。

代价也要说清楚：网络方向必须是「Prometheus 能连到目标」，跨网段、跨云、边缘节点经常不满足；短生命周期任务（CronJob、批处理）根本等不到你来拉，只能推。这就是 Pushgateway 存在的原因，也是它最容易出事的地方。

Pushgateway 不会自动清理。它是个「指标暂存柜」，推上去的 series 会一直留在那里，直到你删或者重启（是否持久化看启动参数）。一个跑完就退出的任务，如果每次都推同一个 job，那个值会永远停在最后一次，up 还是 1，看起来一切正常。正确做法是业务侧推一个时间戳指标，或者用带实例维度的 job 名并配 TTL 清理，告警里加 time() - push_time_seconds > 3600 这类判断。

存这一侧，先建立一个模型：一条 series 由指标名加一组标签唯一确定，一个样本是（时间戳, 浮点值）。Prometheus 把样本按时间切成块写盘，默认两小时一个 block，后台再把小 block 合并成大 block；新写入先进 WAL 再落盘，所以进程崩溃丢的是最后一段，不是全部。查询靠的是「按标签找 series」的倒排索引，加上按时间顺序扫样本。

你敲的命令它在回答什么
up上一次抓取成没成功。它为 0 时，其它指标全是旧值或不存在
scrape_duration_seconds抓一次花了多久。接近 timeout 说明目标本身慢或者指标太多
scrape_samples_scraped这次抓回多少条样本。它突然涨，就是基数出问题的第一信号
prometheus_tsdb_head_series当前活跃 series 数。这是容量规划最该盯的数
/api/v1/status/tsdb按指标名、标签名统计 series 数量，找基数元凶的第一站
# 配置写完先校验，别等 reload 才发现语法错
promtool check config /etc/prometheus/prometheus.yml

# 热加载（启动时加了 --web.enable-lifecycle 才有）
curl -X POST http://localhost:9090/-/reload

# 看目标自己吐出来的原始指标，排查「为什么这条 series 长这样」
curl -s http://10.0.0.12:9100/metrics | grep -E '^node_load|^node_memory'

# 线上最该常看的两个数
prometheus_tsdb_head_series
scrape_samples_scraped
curl -s localhost:9090/metrics | grep tsdb_head_series当前活跃 series 数，容量规划的第一指标
curl -s localhost:9090/api/v1/targets | jq '.data.activeTargets[] | {job:.labels.job, health}'所有抓取目标的健康状态，比看图快
promtool check rules /etc/prometheus/rules/*.yml规则文件语法校验，改完先跑这个再 reload

面试怎么答：「Pull 的核心好处是目标清单和采集节奏都由服务端掌握，抓取失败本身就是一个信号；代价是网络方向受限、短任务覆盖不了，所以要用 Pushgateway，而 Pushgateway 的老化必须自己管，否则会留下一堆永远不更新的假数据。」

模块 2

四种指标类型：选错的代价在三个月后显现

「Counter 和 Gauge 有什么区别」太浅，真正的分水岭是 Histogram 和 Summary。这两者选错，当下看不出来，等到你要做跨实例分位数、要做容量规划的时候，数据已经没法补了。

类型语义客户端产生什么适合不能做什么
Counter只增不减的累计值，进程重启归零一个值请求数、错误数、字节数直接看绝对值没意义，必须 rate/increase
Gauge可增可减的瞬时值一个值温度、队列长度、内存占用、并发数不能对它做 rate（会得到无意义的变化率）
Histogram按固定边界分桶累计_bucket{le}、_sum、_count延迟、大小分布，需要跨实例聚合分位数桶是预先定死的，事后改桶等于历史数据失真
Summary客户端自己算分位数{quantile="0.99"}、_sum、_count单实例精度要求高、不需要聚合分位数不能跨实例相加或平均，改了目标数就废

为什么 Summary 不能聚合？因为 P99 不是「第 99 个百分位的那个值」这么一个可加的东西。两台机器各 100 个请求，A 的 P99 是 10ms、B 的 P99 是 5s，合起来的 P99 可能是 5s，也可能不是——取决于那 198 个请求怎么分布。分位数丢掉了分布形状，只剩一个点，而聚合需要形状。Histogram 保留的是「每个桶里有多少个」，形状还在，所以能先加再算。

Counter 的重启归零值得单独说。Prometheus 的 rate() 会自动处理这种「掉到 0 再涨回来」的 reset：它把下降当成计数器重置，从零重新累加。所以你在代码里不要自己做归零保护，也不要手动写「如果当前值小于上次就置零」的逻辑，那会让 rate 算出负数或者巨大值。

# 一个 Histogram 在 exposition 格式里长这样（节选）
http_request_duration_seconds_bucket{le="0.1"} 24054
http_request_duration_seconds_bucket{le="0.5"} 133988
http_request_duration_seconds_bucket{le="1"} 144320
http_request_duration_seconds_bucket{le="+Inf"} 144320
http_request_duration_seconds_sum 53423.0
http_request_duration_seconds_count 144320

# 注意 le 是「小于等于」，桶是累计的，所以后面的数一定不小于前面的
# 平均延迟可以直接用 sum/count 算：
rate(http_request_duration_seconds_sum[5m]) / rate(http_request_duration_seconds_count[5m])
一句话选型：需要跨实例、需要和 SLO 对齐、需要事后换算法——用 Histogram；只有单实例、只关心本机分位数、且明确不聚合——才考虑 Summary。默认选 Histogram，因为改主意的成本低得多。

面试怎么答：「Counter 是累计量，重启归零由 rate 自动处理；Gauge 是瞬时值；Histogram 在客户端分桶、服务端能聚合出分位数，代价是桶要提前定；Summary 在客户端算分位数，精度高但不可聚合，多实例场景基本不能用。」

模块 3

PromQL 核心：rate 的窗口、外推，以及 by 与 without 的分工

PromQL 的语法十分钟能学会，语义要花很久。面试官问「rate 和 irate 什么区别」，答「一个平均一个瞬时」只能算及格；能接着说「所以 irate 不能用来做告警」才算过关。

rate(v[d]) 做的事是：取窗口内的样本，处理 counter reset，算出每秒平均增长，再把结果外推到窗口两端。外推是为了让相邻窗口的计算结果连续，但副作用是 increase() 会返回小数——比如 5 分钟里实际涨了 3 次，它可能给你 3.7。这不是 bug，是估算。知道这一点，你就不会在「请求数必须是整数」上纠结，也不会拿 increase 的结果直接对账。

窗口该开多大？一个经验规则是至少是抓取间隔的四倍。抓取间隔 15 秒，窗口就别低于 1 分钟；抓取间隔 1 分钟，窗口至少 4 分钟。窗口太小时，边界上常常只有一两个样本，甚至一个都没有——这时候 rate 直接返回空，图上是断点，告警里是「无数据」。这类问题在面板上表现为「偶尔掉一下」，很容易被当成采集抖动。

函数用几个样本特点什么时候用
rate窗口内全部（至少 2 个）平滑，有外推，慢变化也能看出来面板、告警、容量趋势，默认选它
irate最后 2 个灵敏，对单点抖动极其敏感看瞬时毛刺、调试；不要用于告警
increase同 rate等价于 rate 乘窗口秒数，可能带小数「这个窗口涨了多少」，适合报表
delta窗口内全部给 Gauge 用，不做 reset 处理温度、内存这类可增可减的值
deriv窗口内全部线性回归斜率，单位是每秒预测「多久写满」这类问题

聚合顺序是个高频送命题。sum(rate(http_requests_total[5m])) 是对的：先把每条 series 变成速率，再加起来。rate(sum(http_requests_total)[5m:1m]) 也能跑，但语义完全不同——它先把所有实例加成一个总数，再对这个总数求速率。后者在实例重启时会出问题：一台机器归零，总数掉一截，rate 把它当成一次 reset，结果偏低。所以能先 rate 就先 rate。

by 和 without 的区别只有一个：by 是白名单，只保留列出的标签；without 是黑名单，去掉列出的标签、保留其余。写告警时我倾向 by，因为新增标签不会意外把一条告警拆成十条。without(instance) 看着方便，但哪天有人加了个 pod 标签，告警数量立刻翻倍。

# 全局 QPS（先 rate 再 sum）
sum(rate(http_requests_total[5m]))

# 按接口分组的 5xx 比例，注意分母要加 0 保护，否则除零得到 NaN
sum by (path) (rate(http_requests_total{status=~"5.."}[5m]))
  /
sum by (path) (rate(http_requests_total[5m]))

# 与一小时前对比（offset 只改变取值时间，不改变求值时刻）
sum(rate(http_requests_total[5m])) - sum(rate(http_requests_total[5m] offset 1h))

# 子查询：对「已经聚合过的结果」再套一层时间函数
max_over_time( sum(rate(http_requests_total[1m]))[30m:1m] )

# 标签匹配：把两个指标的 instance 对齐，只保留左边
  rate(node_cpu_seconds_total{mode="idle"}[5m])
* on(instance) group_left(nodename) node_uname_info
查不到数据时先分三种情况：一是 series 根本不存在（标签写错、目标没被抓）；二是 series 存在但窗口里样本不够（窗口太小或抓取间隔变了）；三是结果为 NaN（除零、对负数开方）。count(metric) 能一秒区分前两种，比盯着空图猜快得多。

面试怎么答：「rate 是窗口内的平均速率并对两端外推，所以 increase 会有小数；irate 只看最后两个点，灵敏但抖动大，不适合告警。窗口我一般开到抓取间隔的四倍以上，太短会因为没有样本而断图。聚合顺序是先 rate 再 sum，反过来会在实例重启时算出偏低的值。」

模块 4

分位数：为什么必须用 Histogram，以及算错的两个动作

「P99 怎么算」这题的正确写法只有一种结构，但错误写法有十几种，而且都能跑出数来。面试时写出正确的那一行，再补一句「它是桶内线性插值，所以是近似值」，基本就稳了。

先记住正确写法：先对桶求速率、按 le 聚合、再喂给 histogram_quantile。三个动作的顺序不能换，le 不能丢。

# 正确：保留 le，先 rate 再 sum by (le)
histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m]))
)

# 错误 1：把 le 聚合掉了——函数拿不到桶边界，直接返回 NaN 或错值
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])))

# 错误 2：对已经算出来的分位数再聚合——数学上不成立
avg(histogram_quantile(0.99, sum by (le) (rate(http_request_duration_seconds_bucket[5m]))))

# 想要「每个接口各自的 P99」，就按接口分组，le 必须留在分组里
histogram_quantile(0.99,
  sum by (path, le) (rate(http_request_duration_seconds_bucket[5m]))
)

为什么是「近似」？因为原始数据已经变成桶了，桶里具体怎么分布没人知道。histogram_quantile 的做法是找到 P99 落在哪个桶，然后在这个桶的上下界之间做线性插值。如果 P99 落在最后一个有限桶和 +Inf 之间，它只能假设分布均匀，误差可能非常大——一个 10 秒的慢请求和一个 60 秒的超时，在 +Inf 桶里是没有区别的。

所以桶的设计不是随便填的。合理的做法是：在 SLO 边界附近加密。你的 SLO 是「95% 的请求在 300ms 内完成」，那 200ms、250ms、300ms、400ms 这几个桶必须有，否则你连「有没有达标」都测不准。桶的总数控制在十几个以内，桶越多，series 越多，成本按桶数线性上涨。

常见错误写法结果正确做法
对分位数求 avg / sum数字看着合理，结论完全错先聚合桶，再算分位数
聚合时丢掉 le返回 NaN 或毫无意义的常数sum by (le)
用 _sum / _count 当 P99那算的是平均延迟，会把长尾抹平分位数要用 _bucket
拿 Summary 的 quantile 跨实例相加结果无意义改用 Histogram，或改成「超过阈值的比例」
桶只设到 1s，业务有 5s 慢请求P99 全挤在 +Inf 里，永远算不准桶上界覆盖到超时时间
一个比 P99 更好用的写法：把「分位数」换成「超过阈值的请求占比」，它可以直接聚合、可以直接和 SLO 对比，也不受桶插值误差影响。
sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m])) / sum(rate(http_request_duration_seconds_count[5m]))
得到的是「300ms 内完成的比例」，SLO 要 99%，就看这个值有没有低于 0.99。面试里主动给出这个替代方案，是很明显的加分项。

面试怎么答：「分位数用 histogram_quantile，前提是先 rate、再 sum by (le)，le 一定不能丢。它是在桶内做线性插值，所以是近似值，桶的边界要卡在 SLO 附近。分位数本身不可聚合，所以不能对多个实例的 P99 求平均——要做全局视角，只能聚合桶，或者干脆监控『超过阈值的比例』。」

模块 5

基数爆炸：谁在偷偷制造 series

Prometheus 挂掉的原因里，最常见的一个不是查询写错，是标签值无限增长。它的表现很有欺骗性：采集正常、查询正常、磁盘慢慢涨，直到某天内存打满、写入变慢、查询超时，你才发现 series 从八十万变成了四百万。

先把账算清楚：一条 series 的数量 ≈ 指标名数量 × 各标签取值数量的组合。一个指标加一个 user_id 标签，有一百万用户，那就是一百万条 series。标签的每一个不同取值，都是一条新的时间线，不是一列数据。

制造者为什么致命怎么改
URL 路径直接做标签/order/20261021001 每个订单一条改成路由模板 /order/:id，或用 relabel 正则裁掉
user_id / order_id / session_id基数等于业务实体数量移到日志或 trace，指标里只留聚合维度
trace_id / request_id每个请求一条，最纯粹的灾难绝对不要出现在指标标签里
error message 原文同一类错误写法不同就是新值归一化成 error_type，比如 timeout / refused / 5xx
pod 名、容器 ID每次发布都产生新值，旧 series 还留着用 Deployment 级标签，或用 recording rule 提前降维
把状态码细到几十种再乘上 path、method，组合数爆炸指标里只留 2xx/3xx/4xx/5xx，细节留给日志

怎么找凶手？先看总量，再按指标名排序，最后看是哪个标签的取值最多。Prometheus 自带两个入口：HTTP API 的 /api/v1/status/tsdb，以及 promtool tsdb analyze。查询侧可以用 count by (__name__) 粗略排序——但这个查询本身很贵，生产上要慎用，最好在低峰期跑。

# 哪个指标名下的 series 最多（注意：这个查询本身开销很大）
topk(20, count by (__name__) ({__name__=~".+"}))

# 某个指标的标签取值有多少种——定位到具体标签
count(count by (path) (http_requests_total))

# 官方给的诊断入口，比手写查询轻
curl -s http://localhost:9090/api/v1/status/tsdb | jq '.data.seriesCountByMetricName[:10]'
curl -s http://localhost:9090/api/v1/status/tsdb | jq '.data.labelValueCountByLabelName[:10]'

# 离线分析 block，能看到标签对基数的贡献
promtool tsdb analyze /var/lib/prometheus/data

控制手段分三层。采集层用 metric_relabel_configs 直接丢掉不该存在的标签，或者用 sample_limit 让超限的目标直接抓取失败（宁可丢这个目标，也别拖垮整个实例）。存储层用 recording rule 把高基数维度提前聚合掉，面板只查规则产出的低基数指标。设计层是根本：指标只回答「多少、多快、多错」，具体是谁、哪一个，交给日志和链路。

# 采集时裁掉高基数标签：把 path 里的 ID 段替换掉
scrape_configs:
  - job_name: api
    metric_relabel_configs:
      - source_labels: [path]
        regex: '/order/[0-9]+'
        target_label: path
        replacement: '/order/:id'
      - regex: 'trace_id|request_id|user_id'
        action: labeldrop
    sample_limit: 50000      # 超过就整次抓取失败并置 up=0，属于兜底手段
别用 honor_labels: true 解决冲突。它的意思是「目标自己带的标签优先，冲突时给服务端标签加 exported_ 前缀」。听起来很客气，实际后果是目标可以随便往你的 TSDB 里塞标签——包括那个每请求都变的 ID。默认的 false 是更安全的选择。

面试怎么答：「基数是标签取值的组合数，一个 user_id 标签就能把 series 放大到用户量级。我排查会先看 head_series 和 tsdb 的统计接口，找到是哪个指标、哪个标签贡献最多，然后在采集层 relabel 掉，或者用 recording rule 降维。根治的办法是让指标只留可聚合的维度，把身份信息放到日志和 trace 里。」

模块 6

Recording rules：预计算能救面板，也能埋雷

面板打开要八秒，超时。有人提议「加机器」，有人提议「上 Thanos」。多数时候真正的解法是三条 recording rule——把重查询变成一条已经算好的 series。

recording rule 的机制很简单：按 interval 周期性地把一条表达式的结果写成新指标。它的收益来自两处：一是把「扫描大量原始样本」变成「读一条已经聚合的 series」；二是降维——把 path、instance 这些高基数标签在写入时就聚合掉，面板只面对几十条 series。

但它不是免费的。规则结果本身也要存，也要占 series；如果规则里保留了全部标签，你只是把「查询慢」换成了「存储涨」。更麻烦的是依赖关系：同一组内的规则按顺序执行，跨组按各自的 interval 执行，如果 A 组依赖 B 组的产出，就要保证 B 先算完，否则 A 会读到上一轮的值甚至空值。

groups:
  - name: api.rules
    interval: 30s
    rules:
      # 命名习惯：level:metric:operation，方便一眼看出粒度
      - record: api:http_requests:rate5m
        expr: sum by (path, status) (rate(http_requests_total[5m]))

      # 把 5xx 比例预先算好，面板和告警共用，避免两处逻辑漂移
      - record: api:http_error_ratio:rate5m
        expr: |
          sum by (path) (rate(http_requests_total{status=~"5.."}[5m]))
          /
          sum by (path) (rate(http_requests_total[5m]))

命名不是洁癖，是检索能力。推荐 level:metric:operations 这套：level 是聚合粒度（instance、api、cluster），metric 是原始指标名，operations 是做过什么（rate5m、sum）。看到名字就知道能不能直接用于告警，不用去翻规则文件。

症状可能的原因怎么办
面板慢，但规则指标很快规则覆盖不到这个查询补一条规则，或把面板改成查规则产出
规则执行时间越来越长规则里扫了全量标签，或者窗口太大缩短窗口、提前降维、拆分规则组
某个规则指标出现空洞上一轮还没算完，下一轮已经开始调大 interval、减少单组规则数、检查是否 OOM
存储涨得比预期快规则保留了全部原始标签在 by 里只留真正要用的维度
不要在 recording rule 里做 topk。topk 的结果依赖「当下谁排前面」，每轮算出来的标签集合都可能不同，最终你会得到一堆时有时无、互相覆盖的 series。要排名就在查询时算，要长期观察就固定一份白名单。

规则也要测试。promtool test rules 可以喂一组人工构造的输入序列，断言某个时刻的输出值——这样改规则时不用等到线上才发现算错。这条在面试里提一句，可信度会明显不一样，因为大多数人只知道写 YAML。

面试怎么答：「recording rule 解决两类问题：重查询的预计算，和高基数维度的提前聚合。写的时候要注意命名规范、组内依赖顺序、以及别把原始标签全带进来，否则只是把查询压力换成了存储压力。规则本身我会用 promtool test rules 做单元测试。」

模块 7

告警规则：for 管抖动，absent 管消失

「for 是干什么的」谁都会答「持续时间」。追问「那指标直接没了怎么办」——很多人会说「那就不会告警了」，然后意识到问题的严重性：最严重的故障，往往表现为指标消失。

for 的作用是把状态从 pending 推到 firing：表达式为真的持续时间超过 for，才真正发出去。它过滤的是抖动，不是过滤故障。设成 0s 意味着任何一次瞬时越界都会发，在业务有周期性尖刺时就是灾难。

但 for 有个副作用：故障恢复了、表达式变假，告警立刻停止。如果服务在阈值附近来回跳，你会收到「 firing → resolved → firing」的循环。keep_firing_for 就是为这个场景加的：表达式恢复后，仍然保持 firing 一段时间，避免闪断刷屏。较新版本的 Prometheus 支持这个字段，用之前确认你的版本。

指标消失的问题要用 absent 系列解决。absent(m) 在「一条 series 都没有」时返回 1；absent_over_time(m[5m]) 在「整个窗口内都没有」时返回 1。两者都不能写成 m == 0——后者在 series 不存在时同样不返回任何东西，你以为在监控「值为零」，实际上什么都没监控。

groups:
  - name: api.alerts
    rules:
      - alert: ApiHighErrorRate
        expr: |
          sum by (path) (rate(http_requests_total{status=~"5.."}[5m]))
          /
          sum by (path) (rate(http_requests_total[5m])) > 0.05
        for: 10m
        keep_firing_for: 5m
        labels:
          severity: critical
          team: api
        annotations:
          summary: "{{ $labels.path }} 5xx 比例 {{ $value | humanizePercentage }}"
          runbook: "https://wiki.example.com/runbook/api-5xx"

      # 抓取本身失败：up 是 Prometheus 自己产生的，最可靠
      - alert: TargetDown
        expr: up == 0
        for: 3m
        labels: {severity: critical}

      # 指标整体消失：不能用 == 0，必须用 absent
      - alert: MetricsMissing
        expr: absent(up{job="api"})
        for: 5m
        labels: {severity: warning}
写法语义适用
up == 0抓取失败，但目标还在目标列表里目标宕机、端口不通
absent(m)当前一条 series 都没有整个 job 被删、配置漏了
absent_over_time(m[10m])十分钟内一次都没出现过间歇性断采、指标改名后的静默失效
m == 0series 存在且值为 0只适合「确定永远存在」的指标
unless左集合里排除右集合「没有对应实例的孤儿指标」这类集合差
注释里的模板别放会变的东西。{{ $labels.instance }} 是稳定的，{{ $value }} 每次评估都变。如果把 $value 拼进 labels（不是 annotations），同一个告警会因为数值不同被当成不同告警，分组、抑制、静默全部失效。

面试怎么答：「for 用来压抖动，只有持续满足条件才发；keep_firing_for 解决恢复瞬间的反复横跳。指标消失是最危险的情况，必须用 absent 或 absent_over_time 单独覆盖，不能指望 == 0，因为 series 不存在时它什么也不返回。」

模块 8

Alertmanager：分组、抑制、静默，三件套各管一件事

Prometheus 只负责「算出来该不该告警」，Alertmanager 负责「这条告警该不该现在、发给谁、发几次」。两者的边界答不清，说明你只配过 receiver。

一条告警从 Prometheus 发到 Alertmanager 之后，要过四道工序：路由决定去哪个 receiver；分组把同一批告警合成一条通知；抑制让高级别告警压住低级别；静默按条件临时闭麦。分组靠 group_by，抑制靠 inhibit_rules，静默靠 UI 或 API 创建，三者不能互相替代。

group_by 写在 route 上，常见写法是按 alertname 和 cluster 分组。分组太细（比如把 instance 加进去）等于没分，一条告警一条消息；分组太粗（只按 cluster）会把完全不相关的问题塞进一条通知，值班的人要在里面找重点。

三个时间参数要分清：group_wait 是新组第一次发通知前等多久（攒一攒一起发）；group_interval 是同一组有变化时，两次通知之间的最小间隔；repeat_interval 是没变化时多久重发一次提醒。默认值以官方文档和你环境的配置为准，但语义是固定的：前两个控制「快」，最后一个控制「别忘」。

route:
  receiver: default
  group_by: [alertname, cluster]
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h
  routes:
    - matchers: [severity="critical"]
      receiver: pager
      group_wait: 10s
      repeat_interval: 1h
      continue: true          # 继续往下匹配，让 critical 也进工单系统
    - matchers: [severity="warning"]
      receiver: im

inhibit_rules:
  # 同一个实例上，宕机告警压住所有其它告警——避免一条根因刷出三十条
  - source_matchers: [alertname="TargetDown"]
    target_matchers: [severity=~"warning|critical"]
    equal: [instance]
抑制最常见的错是少写 equal。不写 equal 就意味着「全局生效」：A 机房的一台机器宕机，会把 B 机房所有同 severity 的告警一起压掉。必须写清楚「在哪几个标签相同的情况下才抑制」，通常至少要包含 instance 或 cluster。

静默和抑制的区别，用一个问题就能说清：抑制是「因为有别的事发生，所以这条不重要」；静默是「我知道，别吵」。静默必须带过期时间，而且要有人负责到期后的状态——我见过太多「上线前静默两小时，三个月后还静着」的案例，那段时间里真出事是没人知道的。规范做法是静默必须有工单号，到期自动失效，值班交接时检查当前生效的静默列表。

最后一句关于高可用：Alertmanager 集群靠 gossip 同步静默和通知记录，去重靠 notification log，所以集群节点之间必须能互相通信。不要只配 Prometheus 双写、不给 Alertmanager 组集群——那样每条告警会发两遍。

面试怎么答：「Prometheus 判断要不要告，Alertmanager 决定发给谁、发几次、和谁合并。分组解决『一次故障刷一百条』，抑制解决『根因告警该压住衍生告警』，静默是人工的临时闭麦、必须带过期时间。抑制规则里最容易出错的是 equal 没写全，会把不相干的范围一起压掉。」

模块 9

高可用与长期存储：双写、去重、降采样

「Prometheus 怎么做到高可用」——标准答案是「两台一起抓，双写」。接着追问「那查询和告警不会重复吗」，能答上来的不到一半。

先明确一件事：Prometheus 本身不是分布式系统。两个实例各自抓同样的目标、各自存一份数据，彼此不通信、不复制。这带来两个直接后果：查询要自己去重，告警要避免两边都发。

去重的办法是给两台实例打上同一个 replica 标签（不同值），查询时用 --query.replica-label 告诉 Prometheus 按这个标签去重。告警则相反：只让一台实例评估规则，或者让两台都算但 Alertmanager 侧靠 fingerprint 去重——前者更干净，后者更简单，取决于你的容忍度。

方案解决什么代价
本地 TSDB单机、短期（默认保留期以启动参数为准，常见是 15 天）不能水平扩展，实例挂了历史就断
remote_write把数据实时推给远端（Mimir、VictoriaMetrics、Thanos Receive 等）网络和队列成为新瓶颈，远端故障会积压 WAL
Thanos Sidecar把 block 上传对象存储，长期保留 + 全局查询查询有延迟（要等 block 上传），架构组件多
联邦从下级 Prometheus 拉取聚合后的少量指标只适合汇总，别指望它做全量长期存储
remote_write:
  - url: http://mimir:9009/api/v1/push
    queue_config:
      max_samples_per_send: 5000
      capacity: 10000
    write_relabel_configs:
      # 推到远端前先丢掉不需要长期保留的高基数指标
      - source_labels: [__name__]
        regex: 'go_.*|process_.*'
        action: drop

# 查询去重：告诉 Prometheus 哪个标签代表副本
--query.replica-label=replica

长期存储真正的难点不是「存下来」，是「查得动」。原始精度数据放一年，一次跨月的 range 查询会扫掉几十亿个样本。降采样就是为此存在的：把老数据按 5 分钟、1 小时聚合成更低精度。要注意降采样后的数据只能用来画趋势，不能再算精确的 rate 和分位数——那些桶已经被合并了，语义已经变了。

还有一笔账要算：series 数 × 采样点 = 存储量。抓取间隔从 15 秒改成 30 秒，存储直接减半，代价是分辨率变粗、短时尖刺可能看不到。这个取舍在面试里主动说出来，比背「Thanos 有五个组件」有价值。

面试怎么答：「Prometheus 的高可用是双实例各自抓取，不是复制，所以查询侧要按 replica 标签去重，告警侧要么只让一台评估，要么靠 Alertmanager 去重。长期存储一般走 remote_write 或 Thanos，用对象存储加降采样控制成本，但降采样后的数据不能再算精确分位数。」

坑

10 个坑：每一个都能让面板骗你三个月

下面这些不是语法错误，是语义错误。它们的共同点是：查询能跑、图能画、没人报警，直到某天你拿这个数做了决策。

1
rate 的窗口等于抓取间隔
窗口里经常只有一两个样本，边界一对不齐就返回空。窗口至少开到抓取间隔的四倍，否则你会看到一片断点和尖刺，还以为是采集不稳定。
2
先 sum 再 rate
rate(sum(...)) 把所有实例加成一个总数再求速率，某台机器重启归零时总数会掉一截，被当成 reset 处理，结果偏低。正确顺序是先 rate 再 sum。
3
对分位数求平均
avg(P99) 既不等于全局 P99，也不代表任何一台实例。分位数丢掉了分布形状，只有 Histogram 的桶能保留形状。要全局视角就聚合桶，或者改看「超过阈值的比例」。
4
histogram_quantile 时把 le 聚合掉
le 是桶边界，丢了它函数就没有坐标，返回 NaN 或一个常数。记住写 sum by (le)，要分组就写 sum by (path, le)。
5
把 request_id / trace_id 做成标签
这是最纯粹的基数灾难：每个请求一条 series。指标只该回答「多少、多快、多错」，具体是哪一个请求，去日志和链路里找。
6
告警的 for 设成 0s
任何一次瞬时越界都会发。业务有周期性尖刺时，你会被自己的告警淹没，然后开始忽略所有告警——这比不告警更危险。
7
用 m == 0 监控「指标消失」
series 不存在时这个表达式不返回任何东西，等于什么都没监控。要覆盖「消失」必须用 absent 或 absent_over_time。
8
抑制规则不写 equal
不写就是全局生效，一个机房的根因告警会把其它机房的告警一起压掉。equal 至少要有 instance 或 cluster。
9
双写却不配 replica 标签
两台 Prometheus 各存一份、各自评估规则，Alertmanager 收到两份 fingerprint 不同的告警，同一条故障发两遍。查询也会出现两条曲线互相盖住。
10
recording rule 保留全部原始标签
那不是预计算，是把「查询慢」换成了「存储涨」。规则的 by 子句只该留真正要用的维度，否则 series 数量和原始指标一样多。

面试落点：被问「你踩过什么坑」，挑第 3 个或第 5 个讲，讲清楚当时的错误判断和后来的修正。比如「我们曾经用 avg 把各实例的 P99 汇总，面板一直显示两百毫秒，用户投诉三秒，最后才发现聚合方式从根上就是错的」——这种细节比列十个坑名有说服力。

自测

六道题

1. 抓取间隔是 1 分钟，有人写了 rate(http_requests_total[1m])，面板上时不时出现断点。最可能的原因？
正确答案：样本数不足。rate 需要窗口内至少两个样本才能算斜率，窗口等于抓取间隔时，边界稍有错位就只剩一个甚至零个样本，结果直接为空。经验做法是窗口不小于抓取间隔的四倍。
2. increase(http_requests_total[5m]) 返回 3.7，而请求数不可能是小数。怎么解释？
正确答案：外推导致的估算。rate 会按窗口内样本的斜率向窗口边界外推，increase 等于 rate 乘窗口秒数，因此会得到小数。需要精确计数时应该用后端日志或离线数据对账，而不是指望 increase。
3. 下面哪个写法能正确算出所有实例合计的 P99 延迟？
正确答案：最后一项。必须先对 _bucket 求 rate，再按 le 聚合，最后喂给 histogram_quantile。少了 le 就没有桶边界；用 _sum 算的是平均值不是分位数；对分位数再取 avg 在数学上不成立。
4. 关于 Summary 和 Histogram，哪个说法正确？
正确答案：第一项。Summary 在客户端用滑动窗口算分位数，输出的只是一个点，丢掉分布形状后无法合并；Histogram 输出的是累计桶计数，形状还在，所以能先聚合再计算。另外 Histogram 的桶数是固定的，series 成本通常反而更高。
5. Prometheus 内存突然翻倍，怀疑基数爆炸。第一步最该做什么？
正确答案：查 tsdb 统计。基数问题的根因一定落在「某个标签的取值数量」上，官方诊断接口能直接给出按指标名和标签名的 series 排序，比手写 count by 查询更轻、更准。重启只会清掉 head，重新采集后照样涨回来。
6. 业务指标因为采集配置被误删而彻底消失，但服务确实挂了。下面哪种写法能覆盖「指标消失」这种情况？
正确答案：absent。m == 0 只在 series 存在且值为 0 时有输出，series 不存在时什么也不返回，等于没监控；rate 在无样本时同样是空；up == 1 只说明抓取成功，指标被删掉时它依然是 1。要覆盖「消失」必须用 absent 或 absent_over_time。
