TCP 面试：握手、挥手、状态机与那些追问

TIME_WAIT 多不是问题，CLOSE_WAIT 多才是你的代码没关连接。

读之前先答一句：那条停在 TIME_WAIT 的连接，是客户端留的还是服务端留的？
开始前

两张截图，两个完全不同的病

值班群先弹出一条：「网关的 TIME_WAIT 三万二了，是不是要调内核参数？」过了十分钟又弹一条：「订单服务 CLOSE_WAIT 一万八，也在涨。」两个人分别去翻 tcp_tw_reuse 和 tcp_fin_timeout，改完重启，第二天同样的数字照旧。

这两个状态看起来都像「连接堆积」，实际一个是协议的正常收尾，一个是代码没关连接。前者调参数只是把症状藏起来，后者调参数完全无效——因为 CLOSE_WAIT 在内核里根本没有超时定时器，只要应用不调 close()，它能躺到进程退出。

现场直觉答案真实原因
短连接网关 TIME_WAIT 3 万内核参数没优化，连接回收太慢每条主动关闭的连接都会留 60 秒。堆积量约等于「每秒新建连接数 × 60」，是算得出来的，不是故障
应用机 CLOSE_WAIT 1.8 万对端不关连接，或者网络有问题对端已经关了，本端内核回了 ACK，但应用始终没调 close。异常分支漏了释放、连接池只借不还，都会这样
新服务偶发连接超时，服务端 ss 看不出异常网络丢包，或者带宽打满accept 队列满了。握手在服务端内核里完成，但没进到应用层，所以 ss -lntp 看不到任何异常连接
先看状态
TIME_WAIT、CLOSE_WAIT、SYN_RECV 各有多少。这一步只回答一个问题：这是正常收尾、代码泄漏，还是被打了。
再看队列
半连接队列和全连接队列的水位。前者满是被打，后者满是应用 accept 太慢，两个方向的处理完全相反。
最后看计数
重传、超时、溢出这些计数器。它们不给结论，只给量级——但量级决定了这事要不要现在处理。

这一篇按「一个连接从出生到死亡」的顺序走：先看报文头里真正决定行为的那几个字段，再拆三次握手和它背后的队列，然后是四次挥手和 11 个状态的来龙去脉，接着是 TIME_WAIT、CLOSE_WAIT 这两个必考状态，最后落到重传、keepalive 和抓包判读。

为什么从状态机切入：面试官问「为什么四次挥手」「为什么 TIME_WAIT 要等 2MSL」，标准答案谁都会背。真正区分人的是他能不能指着某个状态说「我现在看到这个状态，说明卡在哪一步、下一步该看什么」。状态机不是用来背的，是用来定位的。

面试落点：被问到连接类故障时，先给一句定性：「我先看状态分布，是 TIME_WAIT 多还是 CLOSE_WAIT 多。前者多半是短连接 + 主动关闭，属于容量问题；后者一定是应用没释放，属于代码问题。两个方向的处理完全相反。」

模块 1

报文头里真正重要的六个字段

「TCP 报文头有哪些字段」这题，从源端口背到紧急指针，背完面试官一个也记不住。真正会被追问的只有六个，因为它们分别决定了寻址、有序、生命周期、流控、协商、校验这六件事。

字段长度它决定什么面试怎么追问
源/目的端口各 16 位找到两端的进程。IP 定位主机，端口定位进程「一个端口能有多少连接」——取决于四元组的组合数，不是端口号本身
序号 seq32 位字节流里每个字节的编号。SYN 和 FIN 各占一个序号「为什么 ISN 要随机」——防止旧报文混入，也提高序列号可预测的门槛
确认号 ack32 位「这个序号之前的字节我都收到了」，累积确认「ack 是累计的，那丢了中间一段怎么办」——重复 ACK + 快速重传 + SACK
标志位6 个经典位SYN 建连、FIN 关方向、RST 强拆、PSH 催上层读、ACK 确认、URG 基本不用「收到 RST 说明什么」——说明包到了，只是对方不认这个连接
窗口16 位接收方还能收多少字节，这是流控，防的是「发得比对方处理得快」「窗口和拥塞控制是一回事吗」——不是，窗口管接收方能力，拥塞窗口管网络能力
选项最多 40 字节MSS、窗口扩大因子、SACK、时间戳，握手时协商「MSS 怎么来的」——MTU 减去 IP 头和 TCP 头，以太网 1500 时典型是 1460

固定头 20 字节，选项最多 40 字节，所以整个 TCP 头最长 60 字节。这个数字在算 MSS 和抓包偏移时会用到，值得记住。

流量控制用的是接收窗口：接收方在 ACK 里告诉对方「我缓冲区还剩多少」。窗口变成 0 时发送方停止发送，靠窗口探测（window probe）定期问一句「现在有空间了吗」。这就是所谓的零窗口，抓包里表现为一串长度 0 的 ACK，随后是探测包。零窗口通常不是网络问题，是接收方应用读得太慢。

拥塞控制用的是拥塞窗口 cwnd，它只存在于发送方内核里，报文头上看不到。实际发送量取两者的较小值。面试里把这两个混为一谈，是很典型的减分点。

# -S 显示绝对序号，方便和日志对齐；默认显示的是相对序号
tcpdump -i eth0 -nn -S -c 6 'tcp port 8080 and host 10.0.0.12'

# 输出（节选，箭头表示方向）
# 10.0.0.5.51234 > 10.0.0.12.8080: Flags [S],  seq 1000001, win 64240,
#     options [mss 1460,sackOK,TS val 1 ecr 0,nop,wscale 7]
# 10.0.0.12.8080 > 10.0.0.5.51234: Flags [S.], seq 2000001, ack 1000002,
#     options [mss 1460,sackOK,TS val 2 ecr 1,nop,wscale 7]
# 10.0.0.5.51234 > 10.0.0.12.8080: Flags [.],  ack 2000002, win 502

# 看单个连接的实时内核指标：rtt、cwnd、重传、零窗口
ss -tin dst 10.0.0.12:8080

上面这段输出里有三个细节值得盯：第三次握手的 win 502 是压缩后的值，wscale 7 表示真实窗口要左移 7 位，也就是 502 乘 128；SYN-ACK 里的 ack 1000002 比客户端的 seq 大 1，因为 SYN 自己占掉一个序号，同理 FIN 也占一个；两边的 MSS 都是 1460，说明路径 MTU 是 1500，中间没有隧道封装。

面试落点：「TCP 的可靠不是『不丢』，是丢了能发现、能重传、能排序、能去重。它给你的是有序的字节流，不保证送达时间，也不保证消息边界——所以应用层还得自己做长度前缀或者分隔符，这就是常说的粘包。」

模块 2

三次握手：为什么两次不够，第三次又在确认什么

抓包里看到客户端发了 SYN，服务端回了 SYN-ACK，客户端没回 ACK，一秒后客户端又发了一次 SYN。这种现场八成不是「网络丢包」四个字能解释的，得看第三次握手到底在确认什么。

先把每一步的实质说清。SYN 带的是「我想建的连接，我的初始序号是 X」。SYN-ACK 带的是「我同意，我的初始序号是 Y，我确认你的 X」。最后的 ACK 带的是「我确认你的 Y」。两次握手只能让发起方确认对方的收发能力，没法让对方确认发起方的接收能力。

更硬的理由是历史连接。客户端发出一个 SYN，它在网络里滞留了很久，客户端早就超时重发、通信、关闭了。这个迟到的 SYN 到达服务端，如果只握两次手，服务端就直接建连、分配缓冲区，然后一直等一个永远不会来的数据。第三次握手让服务端在收到确认之前不分配完整资源，迟到的 SYN 就废在 SYN_RECV 里，超时自己消失。

丢的是哪个包客户端状态服务端状态现象
SYNSYN_SENT，超时重传（间隔指数增长）什么都没收到，无感客户端报连接超时，服务端日志干净
SYN-ACKSYN_SENT，重传 SYNSYN_RECV，重传 SYN-ACK两边都在重试，最后一起超时
最后一个 ACK认为已 ESTABLISHED，开始发数据停在 SYN_RECV，重传 SYN-ACK最阴的一种：客户端发数据收到 RST，但如果 SYN-ACK 重传被客户端补了 ACK，又能救回来

初始序号（ISN）不是从 0 或 1 开始，而是随机化。原因有两个层面：一是避免上一次连接残留在网络里的报文被这次连接当成有效数据；二是让外部攻击者难以猜出序列号去伪造报文。说自己「从 1 开始数」的答案，会被直接判定为只背过教材。

还有一个常被忽略的点：三次握手意味着一个 RTT 的纯等待，这段时间一个字节的业务数据都发不出去。跨地域机房 RTT 30ms，就是 30ms 的固定延迟成本——这也是长连接、连接池、TFO 这类优化存在的理由。TFO 把数据放进 SYN 里，但需要两端和中间设备都支持，实际落地要评估。

# 看握手到底卡在哪一步：抓 20 个包，只看 SYN/SYN-ACK/ACK
tcpdump -i eth0 -nn -c 20 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0 and port 8080'

# 内核层面的握手失败计数
nstat -az | grep -E 'TcpAttemptFails|TcpOutRsts|TcpExtTCPTimeouts|ListenOverflows'

# 当前有多少连接卡在 SYN_RECV（半连接）
ss -tan state syn-recv | wc -l

面试落点：「三次握手的第三次不是为了『再确认一次』这么空，它解决两件事：让服务端确认客户端真的收到了自己的 SYN，也就是双方收发能力都被验证过；同时让服务端在确认之前不把连接当完整连接，迟到的历史 SYN 就建不起来。ISN 随机化是为了防止旧报文混入和序列号被猜。」

模块 3

两个队列：SYN Flood 打的是哪一个

一台机器 ss -tan state syn-recv 常年几千，CPU 不高，带宽也没满，但新用户就是连不上。这种「资源看起来都够，就是接不进来」的现场，答案在队列里。

服务端有两个队列，很多人只知道一个：

  • 半连接队列（SYN queue）：收到 SYN、回了 SYN-ACK、还没收到最后 ACK 的连接，状态是 SYN_RECV。长度上限受 tcp_max_syn_backlog 影响。
  • 全连接队列（accept queue）：三次握手完成、等着应用调 accept() 取走的连接。长度上限取 listen(fd, backlog) 和 somaxconn 的较小值。

SYN Flood 打的是第一个：只发 SYN 不回 ACK，把半连接队列塞满，正常用户的 SYN 进来没地方放，直接被丢。服务端看起来「活着」，但新连接全超时。

syncookies 的思路是「干脆不存状态」：队列满了以后，服务端不回 SYN-ACK 就完事，而是把连接的必要信息（比如 MSS、时间戳的低位）编码进初始序号里发出去。客户端回 ACK 时，把这些信息带回来，服务端校验一下就知道这是不是自己发出去的，全程不需要在半连接队列里占一个槽。

net.ipv4.tcp_syncookies 有三个取值：0 关闭；1 只在 SYN 队列溢出时启用；2 无条件启用。大多数发行版默认是 1。代价是编码空间有限，部分选项信息会丢失（比如窗口扩大因子在早期实现里没法带），所以它是应急手段而不是常态配置。

计数器含义往哪查
ListenOverflows全连接队列满，握手完成的连接被丢弃的次数nstat -az | grep ListenOverflows
ListenDrops因队列满被丢的 SYN 总数，含上面那一项同上
SyncookiesSent发出了多少个 syncookie，说明半连接队列已经在溢出nstat -az | grep Syncookies
TcpExtTCPReqQFullDrop请求队列满导致的丢弃nstat -az | grep ReqQFull
ss -lnt 的 Recv-Q当前全连接队列里有几个连接在等 accept和 Send-Q（即 backlog 上限）对比
# 一眼看队列水位：Recv-Q 贴近 Send-Q 就是应用 accept 太慢
ss -lnt
# State   Recv-Q  Send-Q  Local Address:Port
# LISTEN  128     128     0.0.0.0:8080        <-- 满了

# 队列上限由两边取小：应用 backlog 与内核 somaxconn
cat /proc/sys/net/core/somaxconn
cat /proc/sys/net/ipv4/tcp_max_syn_backlog

# 溢出计数（看增量，不看绝对值）
nstat -az TcpExtListenOverflows TcpExtListenDrops TcpExtSyncookiesSent
watch -n1 'nstat TcpExtListenOverflows TcpExtListenDrops | tail -2'
全连接队列溢出时，客户端的现象是「超时」而不是「拒绝」。因为队列满时内核默认把最后一个 ACK 丢掉（tcp_abort_on_overflow=0，以你环境为准），客户端以为自己已经 ESTABLISHED，发数据过去才吃到 RST 或者干脆没回应。所以「连接被拒」和「连接超时」这两个现象，指向的是完全不同的位置：前者通常是端口没监听（内核回 RST），后者往往是队列满或防火墙 DROP。

调参的正确顺序是：先确认是哪个队列溢出；再看是应用 accept 太慢（线程池小、accept 后做了重活）还是流量真的超了；最后才是调 somaxconn 和应用 backlog，两边要一起调，只改一边等于没改。

面试落点：「SYN Flood 打的是半连接队列，防御手段是 syncookies 加连接数限制；全连接队列满则是应用 accept 太慢。这两个队列的溢出计数器不一样，一个看 SyncookiesSent，一个看 ListenOverflows，排查时先分清是哪个，再决定调内核还是改应用。」

模块 4

四次挥手与 11 个状态：每个状态都是一个卡点

抓包里看到 FIN、ACK、FIN、ACK 四行，候选人说「因为 TCP 是全双工」，然后就没词了。追问一句「那为什么有时候只看到三个包」，场面就冷了。

四次的本质是两个方向各自独立关闭。A 发 FIN，只表示「我这边的数据发完了」，不代表 B 也发完了。B 收到后先回 ACK（我知道了），等自己剩下的数据发完，再发一个 FIN（我也发完了）。两个 ACK 和两个 FIN，就是四次。

只看到三个包的情况是真实存在的：如果 B 收到 FIN 时手上没有待发数据，它的 ACK 和 FIN 可以合并成一个包发出去，抓包上就是 FIN、ACK、FIN+ACK、ACK——看起来像三次。四次是逻辑上的四次，物理上可以合并。能说出这一点，说明你真的抓过包而不是背过图。

状态谁在这怎么进来的卡在这里说明什么
LISTEN服务端调了 listen()正常。Recv-Q 满就是 accept 跟不上
SYN_SENT客户端发了 SYN等不到 SYN-ACK：对端没监听、被防火墙 DROP、或者回程不通
SYN_RECV服务端收到 SYN、发出 SYN-ACK大量堆积就是 SYN Flood，或者客户端侧回程被丢
ESTABLISHED双方握手完成正常。数量异常要结合业务量看
FIN_WAIT_1主动关闭方发了 FIN等对方 ACK。堆积说明对端不回包
FIN_WAIT_2主动关闭方收到 ACK，等对方 FIN对端迟迟不关。这个状态没有强制超时，只有孤儿连接才受 tcp_fin_timeout 约束
CLOSE_WAIT被动关闭方收到 FIN、回了 ACK应用没调 close。堆积就是连接泄漏，跟内核参数无关
LAST_ACK被动关闭方发了 FIN，等最后 ACK少见。等不到就重传 FIN，对端可能已经没了
CLOSING双方同时发 FIN（都先进 FIN_WAIT_1）少见。两边几乎同时关闭才会出现
TIME_WAIT主动关闭方发完最后一个 ACK正常收尾，等 2MSL。堆积看数量与增速
CLOSED—连接彻底消失不占资源，也查不到

这 11 个状态里，面试最爱追问的是 FIN_WAIT_2 和 CLOSING。前者因为「主动关闭方发完 FIN、收到 ACK 后就在这等，如果对端一直不发 FIN，它能等多久」——答案要分层：连接还被应用引用时，内核不设超时；应用已经 close 掉、只剩内核持有的孤儿连接，才受 tcp_fin_timeout（默认 60 秒，以你环境为准）约束。后者是双方同时关闭的产物，出现的概率低，但能证明你理解「两个方向独立」。

# 按状态聚合，一眼看分布
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -rn

# 只数某个状态（注意内核里的状态名用连字符）
ss -tan state close-wait | wc -l
ss -tan state fin-wait-2 | wc -l
ss -tan state time-wait | wc -l

# 看 CLOSE_WAIT 集中在哪个对端——这一步决定了去查哪段代码
ss -tan state close-wait | awk 'NR>1 {print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head

面试落点：「四次挥手是因为全双工，两个方向要各自关。但物理上 ACK 和 FIN 可以合并，所以抓包有时只看到三个包。状态机里我最关注 FIN_WAIT_2 和 CLOSE_WAIT：前者说明对端不关，后者说明本端不关，一个在等别人，一个是自己的 bug。」

模块 5

TIME_WAIT：2MSL 到底在等什么

「客户端报 Cannot assign requested address，一查是本地端口用完了，机器上三万个 TIME_WAIT。」这是短连接高并发场景里最常见的自伤，而它的成因是一条完全正常的协议规则。

谁进 TIME_WAIT？主动关闭的那一方。发完最后一个 ACK 之后，它不立刻销毁连接，而是等 2 倍报文最大生存时间（2MSL）。理由有两个，缺一不可：

  • 给最后一个 ACK 一次重来的机会。如果这个 ACK 丢了，对端会重传 FIN。这时候本端还在 TIME_WAIT，能再回一个 ACK；要是已经 CLOSED，收到 FIN 只能回 RST，对端就会认为「连接异常终止」而不是「正常关闭」。
  • 让这条连接的老报文在网络里自然消亡。同一个四元组（源 IP、源端口、目的 IP、目的端口）如果马上被新连接复用，上一轮滞留的报文可能被新连接当成有效数据收下，造成数据错乱。等 2MSL，就是等这些报文过期。

数字要说准：RFC 里 MSL 的建议值是 2 分钟，但 Linux 的实现把 TIME_WAIT 固定成 60 秒，不是严格按 2×MSL 算出来的，也没有 sysctl 能改它。有人拿 tcp_fin_timeout 去调 TIME_WAIT，那是改错了对象——这个参数管的是孤儿 FIN_WAIT_2。

手段实际作用适用边界
改成短连接变长连接从源头减少连接建立/关闭的次数最有效，但要评估中间设备的空闲超时和内存占用
让对端先关TIME_WAIT 落在被动方，把包袱转移出去只在你控制两端时可选，本质是把问题挪走
扩大 ip_local_port_range可用端口变多，端口耗尽推迟治标。默认范围以你环境为准，扩大后要同步检查 conntrack 和防火墙规则
tcp_tw_reuse=1允许主动发起连接的一方复用 TIME_WAIT 的四元组只对出方向生效，且需要时间戳开启（tcp_timestamps=1）。服务端作为被动关闭方，用不上它
tcp_max_tw_buckets限制 TIME_WAIT 总数，超了直接销毁只是把状态藏起来，超限时内核会打日志，属于掩盖而不是解决
tcp_tw_recycle已从 Linux 内核移除（4.12 起）不要再提。它在 NAT 环境下会误判时间戳、导致大量连接被丢

算一笔账，你就知道为什么短连接撑不住：假设本地端口范围给了约 2.8 万个端口，TIME_WAIT 60 秒，那么理论上的新建连接速率上限大约是 28000 ÷ 60 ≈ 470 次/秒。超过这个量，端口就会开始不够用，报错是 Cannot assign requested address。这个数字是粗算，实际还要看目的地址有几个（四元组里目的 IP 不同也能复用同一个源端口）。

# 端口范围与 TIME_WAIT 现状
cat /proc/sys/net/ipv4/ip_local_port_range
ss -s | grep -i timewait
ss -tan state time-wait | wc -l

# 按远端聚合，看是不是集中在某几个下游（说明是短连接打同一个服务）
ss -tan state time-wait | awk 'NR>1 {print $5}' | sort | uniq -c | sort -rn | head

# 复用开关（改之前先确认时间戳是开的，否则不生效）
cat /proc/sys/net/ipv4/tcp_tw_reuse
cat /proc/sys/net/ipv4/tcp_timestamps
「TIME_WAIT 三万个」本身不是告警项。它在告诉你「这个进程每秒新建了几百个连接」。真要处理，先问三个问题：为什么是短连接、能不能改成连接池、下游能不能接受长连接。把 60 秒改成 5 秒、把 reuse 打开，都只是把定时炸弹的引信剪短一截，连接数该涨还是涨。

面试落点：「TIME_WAIT 出现在主动关闭方，等 2MSL 是为了让最后一个 ACK 有机会重发、同时让旧报文过期。Linux 上是固定 60 秒，调不了。堆积量约等于 QPS 乘 60，所以它是容量信号，不是故障信号。真要解决就从长连接和连接池入手，tcp_tw_reuse 只对客户端出方向有用。」

模块 6

CLOSE_WAIT：唯一一个「没有超时」的状态

应用机的 CLOSE_WAIT 从 200 涨到 1.8 万，内存跟着涨，重启后半小时复发。运维把 tcp_fin_timeout 从 60 调到 10，把 tcp_keepalive_time 从 7200 调到 600，一点变化都没有——因为这个状态压根没有定时器。

CLOSE_WAIT 的形成过程很短：对端发来 FIN，本端内核回一个 ACK，然后把这件事交给应用，等应用调 close()。在应用调 close 之前，这个连接的 fd 一直开着，内核不会主动回收它，也不会因为它待太久而报警。所以它堆多少，就说明你的代码漏了多少。

这也是它和 TIME_WAIT 最本质的差别：TIME_WAIT 是内核在收尾，有明确的 60 秒；CLOSE_WAIT 是应用没收尾，没有期限。前者会自己消失，后者只会越来越多，直到 fd 耗尽，报 Too many open files。

先确认集中在谁身上。ss -tan state close-wait 按对端 IP 聚合。如果九成连的是同一个下游，说明是「调这个下游的那段代码」有问题；如果分散，更像是框架层的连接池泄漏。
再确认增长曲线。每 10 秒采一次数量。线性增长对应「每来一个请求漏一个」，阶梯式增长对应「某个定时任务或批量任务漏一批」，这两种的排查入口完全不同。
看 fd 指向什么。lsof -p <pid> 里找 socket，对照对端端口，能确认是 HTTP 客户端、数据库连接池还是消息队列的长连接。
看线程卡在哪。jstack / py-spy / pprof 抓一次栈，找阻塞在 read、wait 或者业务方法上的线程，往往能直接看到漏掉 close 的那个分支。
最后才看配置。连接池的 maxIdle、maxTotal、borrow 超时、泄漏检测阈值。很多「泄漏」其实是池子配置成了「只借不还」，比如拿到的连接在异常路径上没有归还。

代码层面的高频原因，按出现频率排：HTTP 客户端拿到响应后没关 body（Java 的 CloseableHttpResponse、Go 的 resp.Body）；数据库连接在 try 里借出、异常直接抛出，没有 finally 归还；异步回调里抛异常，跳过了收尾；自己写的 socket 长连接，重连时只建新的不关旧的；连接池的「空闲检测」把连接从池里摘掉了，但没有真正 close。

# 数量与增速
ss -tan state close-wait | wc -l
while true; do echo "$(date +%T) $(ss -tan state close-wait | wc -l)"; sleep 10; done

# 这个进程开了多少 fd，上限是多少
ls /proc/12345/fd | wc -l
grep 'open files' /proc/12345/limits

# 这些 fd 指向哪些远端
lsof -p 12345 -a -i TCP | awk '{print $9}' | sort | uniq -c | sort -rn | head
把 CLOSE_WAIT 说成「对端不关连接」，是把因果搞反了。对端已经关了（FIN 都发过来了），是本端不回 close。面试里这句话一出，后面讲什么参数都没用了。正确的说法是：「CLOSE_WAIT 说明我这边收到了 FIN 但应用没释放，属于连接泄漏，要去查代码里的释放路径。」

面试落点：「CLOSE_WAIT 堆积我第一步是按对端聚合，先定位到是哪一段调用；然后看增速是线性还是阶梯；再用 lsof 和线程栈找到具体的代码路径。它跟内核参数无关，因为内核在这个状态不设超时，就等应用 close。」

模块 7

重传与拥塞控制：RTO 是猜的，快重传是赌的

nstat 显示每秒几百个重传段，业务 P99 开始抖。有人第一反应是「网络抖动」，然后去 ping，ping 出来 0% 丢包，于是断定「网络没问题，是应用慢」。这个推理链条每一步都错。

先说重传怎么触发。发送方发一个段，启动一个定时器，超时没收到 ACK 就重发。这个超时时间叫 RTO，它不是固定值，而是根据往返时间 RTT 的采样动态估算的——经典算法用平滑 RTT 加一个与方差相关的项，RTT 抖得厉害时 RTO 就放大。Linux 上 RTO 有一个下限（约 200 毫秒），初始值约 1 秒，具体以你环境的内核为准。超时之后按指数退避，1 秒、2 秒、4 秒地翻倍，这就是为什么一次丢包会演变成几秒的卡顿。

另一条路是快速重传：接收方收到乱序的段，会立刻重复发上一个按序收到的 ACK。发送方连续收到三个重复 ACK，就判断「中间那个段丢了」，不等超时直接重传。SACK 选项让接收方能明确告诉对方「我收到了哪些区间」，避免一次重传一大片。

机制触发条件代价
超时重传RTO 到期没收到 ACK最贵。要等一个 RTO，还会把拥塞窗口打回起点
快速重传收到 3 个重复 ACK便宜。不用等超时，窗口只减半
SACK接收方通告已收到的区间减少不必要的重传，但选项占头部空间
DSACK告知对方「你重传的这个我早就收到了」用于推断是不是乱序而非丢包，帮助算法判断

拥塞控制的四段，用一句话各说清：慢启动是探路，窗口从很小开始指数增长（Linux 现在初始窗口是 10 个 MSS 量级）；拥塞避免是收敛，过了阈值改成线性增长；快重传/快恢复是纠错，三个重复 ACK 就重传并把窗口减半，不回到起点；超时是最坏情况，窗口直接回到最小，重新慢启动。

把丢包等同于拥塞，是传统算法的假设，也是它在弱网和无线场景下表现差的原因。BBR 换了个思路：不去猜「丢了就是堵了」，而是持续测量瓶颈带宽和最小 RTT，用这两个量估算应该发多快。它不把丢包当拥塞信号，所以在有一定随机丢包的链路上通常更稳，代价是更容易抢占带宽，多流共存时的公平性需要看具体版本和场景。

# 全局重传与超时计数（看增量）
nstat -az | grep -E 'TcpRetransSegs|TcpExtTCPTimeouts|TcpExtTCPLostRetransmit'

# 单连接的细节：rtt、cwnd、重传次数、是否在用 SACK
ss -tin dst 10.0.0.12:8080
# 关注 rtt:0.312/0.05、cwnd:10、retrans:0/3、sack_ok

# 当前可用的拥塞控制算法（内核里编进去的）
sysctl net.ipv4.tcp_available_congestion_control
sysctl net.ipv4.tcp_congestion_control

判断重传健不健康，别只看绝对值。业务量翻倍，重传数跟着翻倍是正常的。要看的是重传率（重传段 ÷ 总发送段）和它跟延迟的相关性。重传率在千分之几以内通常可以接受，具体阈值取决于链路类型；但如果你看到 P99 和重传率同时抬起来，那基本可以确定是同一件事。

面试落点：「RTO 是根据 RTT 采样动态算的，有下限，超时后指数退避；快速重传靠三个重复 ACK，代价比超时小得多。拥塞控制里慢启动是指数探路、拥塞避免是线性收敛。BBR 的区别是不把丢包当拥塞信号，改用带宽和最小 RTT 建模。」

模块 8

keepalive 有三层，混着说一定被追问

服务端把空闲连接回收设成 5 分钟，客户端连接池的 idle 也是 5 分钟，两边几乎同时动手。结果每隔一段时间，就有一批请求报 connection reset by peer——两边都在关，谁也不知道对方先关。

「keepalive」这个词被用在三个完全不同的地方，面试里混着说，追问一句就塌：

名字在哪一层做什么默认/常见值
TCP keepalive内核连接空闲到阈值后发探测包，判断对端主机还在不在Linux 默认空闲 7200 秒才开始探，间隔 75 秒，探 9 次；以你环境为准
HTTP keep-alive应用（协议头）一个 TCP 连接上跑多个请求，减少握手开销HTTP/1.1 默认持久连接，靠 Connection 头协商
应用层心跳业务协议定期发一个业务可识别的包，确认对方进程还能处理请求间隔由业务定，通常几秒到几十秒

关键区别在这：TCP keepalive 探测的是主机，不是进程。对端进程卡死、线程池打满、GC 停了 30 秒，只要内核还活着，它就会替进程回 ACK。所以你看到 keepalive 一切正常，业务请求却全部超时——这是完全可能发生的。要发现「进程假死」，只能靠应用层心跳或者业务探针。

反过来，应用层心跳也替代不了 TCP keepalive 的一个作用：维持中间设备的连接状态。NAT 网关、四层负载均衡、云安全组，都有各自的空闲超时表项，常见是几分钟。超时后它们静默删表，两端都不知道，直到下一次发包才吃到 RST 或者直接不通。所以心跳间隔必须小于链路上最短的那个空闲超时，而不是随便设个 30 秒。

两边同时关连接的问题，解决办法不是「谁别关」，而是让关闭有先后：客户端的 idle 时间要比服务端短一截（比如服务端 300 秒、客户端 240 秒），这样总是客户端先发现连接空闲、主动关掉，服务端那边收到的是一次正常的 FIN，而不是「我以为还活着、结果发过去被 RST」。这个技巧在连接池配置里非常实用。

# 内核 keepalive 的三个参数（秒）
sysctl net.ipv4.tcp_keepalive_time    # 空闲多久开始探测
sysctl net.ipv4.tcp_keepalive_intvl   # 探测间隔
sysctl net.ipv4.tcp_keepalive_probes  # 探测几次后判定死亡

# 应用可以按连接覆盖（SO_KEEPALIVE 只是开关，细粒度要靠 TCP_KEEPIDLE 等）
ss -tino | grep -A1 ESTAB
关于 HTTP/2 的一个细节：HTTP/2 有 PING 帧，可以在一个多路复用的连接上做应用层探测，但它探测的仍然是「对端协议栈是否响应」，不是「你的业务线程有没有被堵住」。所以做健康检查时，还是得有一个真正打到业务逻辑的接口。

面试落点：「keepalive 分三层：内核的 TCP keepalive 探主机，HTTP 的 keep-alive 是连接复用，业务心跳探进程。TCP keepalive 发现不了进程假死，因为内核会替它回 ACK。另外心跳间隔要小于中间设备的空闲超时，否则连接会被静默删掉。」

模块 9

抓包：带着问题抓，带着判读看

「你抓个包看看。」很多人抓完打开分析工具，看到几千行，然后不知道从哪一行开始看。抓包的价值不在抓，在于你抓之前已经想好要看什么。

抓之前先定三件事：抓哪个点（客户端还是服务端，两端都抓才能判断单向不通）、抓什么（host + port 精确过滤，别抓全量）、抓多少（-c 限包数，-w 落文件而不是刷屏）。生产上还要加一句 timeout 30，防止忘了停。

# 精确过滤 + 限数量 + 落文件（-s 0 抓完整包，-S 用绝对序号）
timeout 30 tcpdump -i eth0 -nn -s 0 -S -c 200 \
  'tcp port 8080 and host 10.0.0.12' -w /tmp/tcp-8080.pcap

# 只看握手和挥手（过滤标志位）
tcpdump -i eth0 -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'

# 只看重传：同一个序号出现两次（需要先落文件再分析更方便）
tcpdump -r /tmp/tcp-8080.pcap -nn | awk '{print $1,$3,$5,$7}' | sort | uniq -c | sort -rn | head

# 回来再看时，先看统计再看明细
tcpdump -r /tmp/tcp-8080.pcap -nn -q | tail -5
标志含义判读要点
[S]SYN只有它没有 [S.]，说明对端没回，问题在去程或对端没监听
[S.]SYN + ACK对端同意建连。同一个 SYN 对应多个 [S.] 就是重传
[.]纯 ACK长度 0 的 ACK 很常见。成串出现要警惕零窗口或 ACK 风暴
[P.]PSH + ACK带数据。看 len 和 seq 是否连续，不连续就是丢包或乱序
[F.]FIN + ACK一方开始关闭。谁先发 FIN，谁就是主动关闭方
[R] / [R.]RST收到 RST 说明包到了。要么端口没监听，要么连接已不存在（比如服务端重启）

判读的顺序建议固定成四步：握手有没有完成（看 [S] [S.] [.] 三行是否成对）→ 谁先发 RST 或 FIN（定主动权）→ seq 有没有重复（看重传）→ 窗口有没有变 0（看接收方处理能力）。这四步走完，八成问题已经有结论了。

tcpdump -i any -nn -S -c 20 'host H and tcp port P'抓一条流的握手，-S 用绝对序号方便和日志对齐
ss -tin dst H:P单连接的内核指标：rtt、cwnd、重传次数，比抓包更快看到拥塞状态
nstat -az | grep -E 'RetransSegs|TCPTimeouts'全局重传和超时计数，看增量不看绝对值
ss -tan state close-wait | wc -l连接泄漏的直接指标，配合对端聚合定位是哪段调用
ss -lntRecv-Q 贴近 Send-Q 就是 accept 队列满了
三个抓包的现实约束：① 高流量下 tcpdump 会丢包，结尾那行「packets dropped by kernel」就是证据，要减小过滤范围或者加大缓冲区；② 容器里抓包要进对应的网络命名空间，抓宿主机网卡看到的可能是 NAT 之后的地址；③ 开了网卡多队列或 GRO/LRO 时，抓到的「大包」是网卡聚合出来的，和线路上真实传输的包不一样，算 MTU 问题时要注意。

面试落点：「我抓包前先定过滤条件和抓点，两端都抓，这样才能区分是去程不通还是回程不通。判读按四步走：握手完成没有、谁先 RST、seq 有没有重复、窗口有没有变 0。看到 RST 我不会说被防火墙拦了，因为 RST 恰恰证明包到了对方。」

模块 10

10 个坑：每一个都能在面试里直接翻车

下面这些不是知识点错误，是判断方向错误。它们的共同点是「听起来很有经验」，实际上会把排查带偏，或者把参数改出事故。

1
TIME_WAIT 多就开 tcp_tw_recycle
这个参数已经从 Linux 内核移除（4.12 起），在 NAT 环境下它会按时间戳判断、把正常连接当成旧包丢掉。现在还提它，等于自报「我的知识停在几年前」。
2
把 CLOSE_WAIT 当成内核参数问题
这个状态在内核里没有超时定时器，就等应用调 close。调 tcp_fin_timeout 一点用没有，因为那个参数管的是孤儿 FIN_WAIT_2。方向错了，调什么都白调。
3
以为 tcp_tw_reuse 能救服务端
它只对「主动发起连接」的一方生效，服务端作为被动关闭方，TIME_WAIT 是客户端留下的。服务端开了也没用，而且它依赖时间戳，关掉时间戳就失效。
4
认为握手成功就代表服务可用
握手只证明「有人在这个端口 listen」，队列满、应用不 accept、TLS 握手失败、业务返回 500，全都能在握手成功的前提下发生。
5
把 TCP keepalive 当业务心跳
它探的是主机存活，对端进程卡死时内核照样回 ACK。要发现进程假死只能靠应用层心跳或者打到业务逻辑的健康检查。
6
看到 RST 就说「被防火墙拦了」
防火墙 DROP 的结果是超时，不是 RST。收到 RST 说明包已经到达对方协议栈，只是对方不认这个连接——端口没监听，或者连接已经被回收。
7
用 ping 的丢包率判断 TCP 质量
ICMP 可能被限速、被单独调度，和 TCP 的路径、队列、拥塞状态都不是一回事。ping 0% 丢包而 TCP 大量重传，是常见的组合。
8
只在一端抓包，没看到回包就断定对方没回
回程可能走了另一条链路、被策略路由带走，或者在容器环境里根本没经过你抓的那块网卡。抓不到回包只能说「这个点没看到」，不能说「对方没发」。
9
拿 ping 测端口和 MTU
ping 通只覆盖到 IP 层，和端口监听无关。测 MTU 要用带 DF 标志、指定包长的 ping，而且中间设备不一定会回 ICMP 不可达，黑洞就是这么来的。
10
认为 TCP 会保留消息边界
TCP 是字节流，一次 send 可能被拆成多个段，多个 send 也可能被合并。应用层必须自己定长度前缀或者分隔符，这就是粘包/拆包问题的根源。

面试落点：这 10 条里挑一条讲，讲法固定三段：当时的判断、造成的后果、后来改成了什么。第三段最重要——只说「踩过坑」不说明你改了判断方式，面试官会认为你还会再踩一次。

自测

六道题

1. 一条连接正常关闭后，TIME_WAIT 出现在哪一方？
正确答案：主动关闭方。TIME_WAIT 是「发完最后一个 ACK 之后」的状态，只有主动关闭的一方才需要等 2MSL：一是让最后一个 ACK 丢失时还能重发，二是让这条连接的老报文在网络中过期，避免被同一四元组的新连接误收。
2. 服务端 ss -s 显示 CLOSE_WAIT 一万多条且持续增长，正确的判断是？
正确答案：应用没 close。CLOSE_WAIT 表示本端已经回了 FIN 的 ACK，正在等本端应用关闭。对端该做的都做完了，剩下的是本端的事。这个状态在内核里没有超时定时器，堆多少就漏多少，直到 fd 耗尽。
3. 关于三次握手「为什么不能是两次」，下面哪个说法最站得住？
正确答案：历史 SYN。如果只握两次，一个早已失效、在网络里滞留很久的 SYN 到达服务端后，服务端会直接建连并分配资源，然后一直等数据。第三次握手让服务端在收到确认之前不把连接当成完整连接，迟到的 SYN 就废在 SYN_RECV 里自己超时。另外两次握手也无法让服务端确认客户端的接收能力。
4. 客户端大量报 Cannot assign requested address，机器上 TIME_WAIT 三万条，最合理的处置是？
正确答案：从连接模型入手。端口耗尽的根因是「短连接频率 × 60 秒」超过了可用端口数，参数只能治标。tcp_tw_recycle 已被内核移除；tcp_fin_timeout 管的是孤儿 FIN_WAIT_2，不是 TIME_WAIT；tcp_max_tw_buckets 只是把状态藏起来，超限时仍会丢连接。
5. 抓包里看到客户端发了 SYN，服务端回了 SYN-ACK，之后没有第三次握手，而是客户端重发 SYN。最不可能的原因是？
正确答案：服务端没监听。没监听时内核会直接回 RST，抓包上是一条 [R] 而不是 [S.]。既然已经看到 SYN-ACK，说明服务端协议栈收到了 SYN 并且愿意建连，问题出在回程或者第三次握手的 ACK 没到达，属于路径问题而不是监听问题。
6. 对端进程卡死（线程池打满，不再处理请求），但主机和内核都正常。哪种机制能发现这个问题？
正确答案：应用层心跳。TCP keepalive 的探测包由对端内核处理并回 ACK，进程是否还能干活它完全不知道。把 tcp_keepalive_time 调小只是让探测更频繁，结论还是一样——主机活着。要发现进程假死，只能有一个真正走到业务逻辑的健康检查。

术语表与下一步

术语一句话解释
ISN初始序号。随机化是为了防止旧报文混入，也提高序列号被猜中的门槛
MSS最大段长度，等于 MTU 减去 IP 头和 TCP 头，以太网 1500 时典型 1460
MSL报文在网络中的最大生存时间。TIME_WAIT 等 2MSL，Linux 实现直接固定为 60 秒
半连接队列存放 SYN_RECV 连接的队列，受 tcp_max_syn_backlog 影响，是 SYN Flood 的攻击目标
全连接队列存放已完成握手、等应用 accept 的连接，长度取 listen backlog 与 somaxconn 的较小值
syncookies队列满时不保存状态，把连接信息编码进 ISN，收到 ACK 再校验重建
RTO重传超时时间，根据 RTT 采样动态估算，有下限，超时后指数退避
快速重传收到三个重复 ACK 就立即重传，不必等 RTO 到期
SACK选择性确认，让接收方告诉发送方「我收到了哪些区间」，减少无谓重传
cwnd拥塞窗口，只存在于发送方内核，报文头看不到；实际发送量取它与接收窗口的较小值
零窗口接收方缓冲区满，通告窗口为 0，发送方停止发送并定期探测
CLOSE_WAIT被动关闭方收到 FIN 并回 ACK 后的状态，等应用 close，内核不设超时
TIME_WAIT主动关闭方发完最后一个 ACK 后的状态，Linux 固定 60 秒
粘包TCP 是字节流没有消息边界，应用层要自己用长度前缀或分隔符切分
