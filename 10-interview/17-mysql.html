开始前

四句话，四种被人追问到哑口的现场

「我们给 user_id 加了索引，QPS 反而掉了一半。」这句话在真实的复盘会上出现过无数次，说的人一脸困惑，听的人也不知道该问什么。它不是一个离奇的现象，而是一个成本和收益算错了的必然结果。

先把结论放前面：索引不是「让查询变快」的开关，它是一种用额外的写成本和空间，去换更少数据页读取的交易。当这笔交易不划算时，优化器会主动放弃索引；当你逼它用索引时（比如 FORCE INDEX），你就真的会看到变慢。

现场直觉答案真实原因
加了索引，QPS 从 3000 掉到 1200索引没建对，或者统计信息过期选择性太差（比如 status 只有 3 个值），优化器改走二级索引后，每次要回表几十万次随机读，比全表顺序扫更贵
EXPLAIN 走了索引，仍然 800ms索引失效了索引生效了，但只用来过滤或排序，扫描行数没降。真正的时间花在回表和排序上，rows 那一列才是答案
列表页翻到第 5000 页直接超时数据库性能不行，要加机器LIMIT 100000, 20 会先取出 100020 行再丢掉前 100000 行，翻得越深越慢，加机器只是把慢分摊掉
刚写入的数据，从库读不到代码有缓存，或者事务没提交读写分离 + 异步复制。写完立刻去从库读，从库的 SQL 线程还没回放到那条 binlog
结构
数据怎么落在页上、索引存了什么。这一层决定了「一次查询要读几个页」，是所有成本的源头。
成本
优化器按「读页数」估算代价。它宁可全表扫也不走索引，通常是因为它算出来走索引更贵，而不是它坏了。
并发
事务、锁、MVCC。这一层决定「两个人同时改同一行会发生什么」，也是面试里最容易问出深度的地方。

这篇不按教材顺序讲。它按面试的追问顺序走：先讲清一条查询的钱花在哪，再讲索引为什么会被放弃，然后是事务和锁的边界，最后落到慢查询和主从这些「线上真会出事」的地方。每一节末尾都留了一句可以直接说出口的话。

一个判断标准：如果你只能说「索引能加快查询」，那你是背的。如果你能说出「这条 SQL 走索引要回表 8 万次，优化器估算的代价高于全表扫 20 万个页，所以它选了 ALL」，那你就是懂的。面试官追问的永远是后半句。

面试落点：「加索引变慢这件事我遇到过，根因是选择性太低导致回表次数过多。索引的价值不在于『有没有』，而在于它能把扫描行数降到多少、以及回表要付多少次随机 IO。」

模块 1

InnoDB 的存储结构：三层树为什么能装两千万行

「B+ 树有几层」这种题，背「三层」没有意义。有意义的是你能不能在纸上算出三层大概能放多少行——算得出来，说明你知道页里装的是什么。

InnoDB 读写磁盘的最小单位是页，默认 16KB（innodb_page_size，实例初始化时确定，之后不能改）。一行数据不是单独存放的，而是和相邻的几十上百行挤在同一个页里。页内有一个「页目录」，用稀疏槽位记录每组最后一行的偏移，所以在页内按主键找一行是二分，不需要从头扫。

聚簇索引的意思是：整张表就是一棵以主键为键的 B+ 树，叶子节点直接放完整行数据。没有「索引文件」和「数据文件」的分离，主键索引即数据。所以「按主键查」是唯一一种一次定位就能拿到整行的方式，其他所有路径都要绕道。

层级存什么一条记录多大
非叶子页主键值 + 子页页号，只做导航，不含行数据BIGINT 主键 8 字节 + 页号 6 字节，约 14 字节
叶子页（聚簇）完整行：所有列 + 事务 ID + 回滚指针取决于行长，假设平均 1KB，一页约 16 行
叶子页（二级）索引列 + 主键值，不含其他列比聚簇叶子小得多，一页能放几百上千条

按上面的假设算一遍：一个非叶子页能放 16384 / 14 ≈ 1170 个指针。根页 1 个，第二层 1170 个，第三层 1170 × 1170 ≈ 137 万 个叶子页，每个叶子页 16 行，总量约 2200 万行，树高 3。这就是「三层两千万」的来历——它不是常数，是三个假设（主键 8 字节、行宽 1KB、页 16KB）算出来的结果。行宽变成 4KB，同样三层就只有五百多万行；主键换成 36 字节的 UUID，非叶子页能放的指针直接掉到三百多。

树高的意义在于磁盘 IO 次数：三层树查一行，最坏读 3 个页。但热数据在 buffer pool 里，根页和第二层几乎永远命中，实际往往只有一次真正的磁盘读。所以「优化 buffer pool」比「压低树高」更有效，这一点很多人反过来说。

# 页大小和默认行格式：动手前先确认，不同环境可能不同
SELECT @@innodb_page_size, @@innodb_default_row_format, @@innodb_buffer_pool_size;

# 用统计信息粗估表的体量（table_rows 是采样估算，不是精确值）
SELECT table_rows,
       ROUND(data_length / 1024 / 1024)  AS data_mb,
       ROUND(index_length / 1024 / 1024) AS index_mb
FROM information_schema.tables
WHERE table_schema = 'shop' AND table_name = 'orders';

# 看真实行格式与行宽：AVG_ROW_LENGTH 能帮你判断一页放几行
SHOW TABLE STATUS FROM shop LIKE 'orders'\G
为什么主键不建议用 UUID。两个代价叠加：一是随机写入导致 B+ 树不断页分裂，页填充率下降、碎片变多，同样的行数占更多页；二是所有二级索引的叶子都要存主键，主键从 8 字节变 36 字节，索引体积膨胀，缓存能装下的索引条目变少。用有序的雪花 ID 或自增，能同时避开这两个问题。

面试落点：「InnoDB 的页是 16KB，聚簇索引的叶子放整行，非叶子只放主键和页号。按 8 字节主键、1KB 行宽算，三层大约两千万行，所以一次主键查询最坏 3 次页读。用 UUID 会让非叶子页能放的指针变少，还会引起页分裂，这是我不推荐它的原因。」

模块 2

回表：二级索引真正的代价在这里

「二级索引查到主键，再拿主键去聚簇索引取整行」——这句话谁都会说。但面试官接着问「那为什么有时候它还不如全表扫」，能答上来的人立刻少一半。

关键在于两种 IO 的形态不同。全表扫是顺序读：页在磁盘上基本连续，预读能一次拉一批，读 20 万个页的吞吐很高。回表是随机读：按主键一个一个去聚簇索引里定位，每个主键落在哪个页没有规律，缓存没命中就是一次真实的随机 IO。随机 IO 的单次成本比顺序读高一个量级，所以「回表 8 万次」和「顺序扫 20 万个页」谁更贵，真的不一定。

这也解释了那个经典现象：给 status（只有 0/1/2 三个值）建索引，查询 2/3 的数据。优化器一算，走索引要回表几百万次，全表扫反而更便宜，于是 EXPLAIN 里 key 是 NULL、type 是 ALL。这不是索引失效，是优化器做了正确的事。区分「失效」和「放弃」，是这道题的分水岭。

访问方式IO 形态什么时候划算
全表扫描顺序读聚簇索引叶子，可预读命中比例高（比如超过两三成）、表小、行窄
二级索引 + 回表先扫二级索引（顺序），再逐行随机读聚簇索引命中比例低、过滤后行数少
覆盖索引只读二级索引，零回表查询列全在索引里，任何时候都划算
索引下推（ICP）在二级索引上先过滤，再决定回不回表联合索引里有范围条件、且过滤性强

覆盖索引为什么快？因为二级索引的叶子本来就带着主键，所以 SELECT id FROM orders WHERE user_id = 42 完全不需要回表。再加上查询需要的列，就构成一个「自带答案」的索引。它的收益不是「少读几个字段」，而是把 N 次随机 IO 变成 0 次。

索引下推（Index Condition Pushdown，MySQL 5.6 起支持）是另一层优化：联合索引 (user_id, status, created_at) 上，条件 user_id = 42 AND status > 1，如果没有 ICP，存储引擎只能按 user_id 把行全捞出来交给 Server 层再过滤；有 ICP 之后，status > 1 在引擎层就用索引里的值判断掉了，回表次数直接减少。它在 EXPLAIN 的 Extra 里显示为 Using index condition。

-- 建一张能复现问题的表，字段和索引都贴近真实业务
CREATE TABLE orders (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id     BIGINT UNSIGNED NOT NULL,
  status      TINYINT         NOT NULL DEFAULT 0,
  amount      DECIMAL(10,2)   NOT NULL,
  created_at  DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_user_status_created (user_id, status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 走索引且覆盖：Extra 里是 Using index，不回表
EXPLAIN SELECT id, created_at FROM orders
WHERE user_id = 42 AND status = 1 ORDER BY created_at DESC LIMIT 20;

-- 同样的条件，但要多取 amount：Extra 里 Using index 消失，开始回表
EXPLAIN SELECT id, amount FROM orders
WHERE user_id = 42 AND status = 1 ORDER BY created_at DESC LIMIT 20;

-- 选择性差的列单独建索引，优化器大概率直接放弃
EXPLAIN SELECT * FROM orders WHERE status = 1;
面试怎么答：「回表的代价是随机 IO。优化器估算成本时比的是页数，不是行数，所以当命中比例高的时候，全表顺序扫会比『二级索引 + 大量回表』更便宜，这时候 key 是 NULL 属于正常决策。要让它走索引，要么把查询变成覆盖索引，要么加一个过滤性更强的列进联合索引，而不是加 FORCE INDEX。」
模块 3

最左前缀与五类失效：索引列不能「被加工」

联合索引 (a, b, c)，条件写 WHERE b = 1 AND c = 2，能不能用索引？标准答案是「用不上定位，但可能用得上覆盖或下推」。这个区别，是背过的人和想过的人的分界线。

先建立正确的模型：联合索引的排序规则是先按 a 排，a 相同再按 b 排，b 相同再按 c 排。就像电话簿先按姓、再按名。你只知道名字不知道姓，就没法在电话簿里二分。所以：
· a 单独查：能用。
· a, b：都能用。
· a 等值 + b 范围：a、b 都能用于定位，c 不行（范围之后的列失去有序性）。
· b, c 不带 a：定位用不上，但如果查询列都在索引里，可以做一次索引全扫描（比全表扫小），type 显示 index。

「失效」这个词被用得太宽。准确地说有两类：一类是索引根本没法用来定位（列被函数包住、前导模糊匹配），一类是优化器算完觉得不划算主动放弃（选择性差、回表太多）。前者改 SQL，后者改索引设计，处理方式完全不同。

写法能不能用索引怎么改
WHERE DATE(created_at) = '2026-10-01'不能。列被函数包住，索引里存的是原值，B+ 树没法按函数结果找改成范围：>= '2026-10-01' AND < '2026-10-02'；或 MySQL 8.0 建函数索引
WHERE phone = 13800138000（phone 是 varchar）不能。字符串列被转成数字比较，等于对列做 CAST加引号写 '13800138000'。反过来数字列和字符串比较，通常仍能走索引
WHERE name LIKE '%张%'不能。前导通配符没有确定的前缀'张%' 可以；真的要做中缀搜索，上全文索引或搜索引擎
WHERE amount + 10 > 100不能。列参与运算移到右边：amount > 90
WHERE a = 1 OR b = 2（b 无索引）不能。OR 的任一支没有索引，整体退化成全表扫拆成两条 UNION ALL，或给 b 补索引
-- 用同一张表验证：把函数条件改成范围条件，看 rows 的变化
EXPLAIN SELECT * FROM orders WHERE DATE(created_at) = '2026-10-01';
EXPLAIN SELECT * FROM orders
WHERE created_at >= '2026-10-01 00:00:00' AND created_at < '2026-10-02 00:00:00';

-- 8.0 的函数索引：把表达式建成索引，注意查询写法要完全一致
ALTER TABLE orders
  ADD COLUMN created_date DATE GENERATED ALWAYS AS (DATE(created_at)) VIRTUAL,
  ADD KEY idx_created_date (created_date);

-- 排序也用得上索引：ORDER BY 的列顺序要和索引一致，且方向不能混
EXPLAIN SELECT id FROM orders WHERE user_id = 42 ORDER BY created_at DESC LIMIT 20;
-- Extra 里没有 Using filesort，说明排序免费搭了索引的车
还有一个容易漏的：ORDER BY 与 WHERE 抢索引。如果 WHERE 用了 a 做范围，ORDER BY 又想要 b 有序，两者不可兼得，MySQL 只能二选一，另一个走 filesort。这时候要么把范围条件换成等值（比如把时间范围拆成枚举），要么接受排序成本，要么建两条不同顺序的索引。

面试落点：「联合索引的有序性是从左到右逐列建立的，所以范围条件之后的列失去定位能力。失效分两种：列被函数或隐式转换包住属于『用不了』，选择性太差属于『优化器不想用』。前者改 SQL，后者改索引，把它们混在一起答，就会被继续追问。」

模块 4

MVCC：RR 下的快照读到底看见什么

「RR 隔离级别能不能避免幻读？」这个问题有标准答案，但标准答案是错的——准确说法是：快照读能，当前读要靠间隙锁，而且它不是无条件的。面试官如果追问一句「那我先 SELECT 再 UPDATE 呢」，只背结论的人就卡住了。

先把四个隔离级别和它们解决的问题摆清楚。读未提交（RU）什么都不防；读已提交（RC）防脏读；可重复读（RR）防不可重复读；串行化（Serializable）防幻读，代价是并发度极低。InnoDB 的默认是 RR，而很多互联网公司会主动改成 RC，因为 RC 少用间隙锁，死锁概率低——这个取舍本身就是个加分回答。

级别脏读不可重复读幻读实现手段
RU可能可能可能直接读最新版本
RC不会可能可能每条语句生成一个 ReadView
RR不会不会快照读不会，当前读靠 next-key lock事务内第一次快照读生成 ReadView，之后复用
Serializable不会不会不会普通 SELECT 也加共享锁

MVCC 的实现靠三样东西：行上的隐藏列 DB_TRX_ID（最后修改它的事务 ID）、DB_ROLL_PTR（指向 undo log 里的上一个版本）、以及 undo log 串起来的版本链。读的时候不是去锁行，而是沿着版本链往回找，找到第一个「对我可见」的版本。

判断可见性的结构叫 ReadView，核心就四个字段：m_ids（生成时还活跃的事务 ID 列表）、min_trx_id（其中最小）、max_trx_id（下一个要分配的 ID）、creator_trx_id（自己）。规则可以简化成三句话：

版本的事务 ID 小于 min_trx_id：说明它在我开始之前就提交了，可见。
大于等于 max_trx_id：说明它是在我之后才开的事务，不可见，顺着版本链往回找。
落在中间：如果它在 m_ids 里，说明当时还活着、没提交，不可见；不在里面说明已经提交，可见。

RC 和 RR 的唯一差别是 ReadView 的生成时机：RC 每条语句都新建一个，所以同一事务里两次查询能看到别人新提交的数据；RR 只在第一次快照读时建一次，之后一直复用，于是整个事务看到的是同一个「时间切片」。这就是「可重复读」四个字的物理含义。

-- 会话 A：确认当前隔离级别（5.7.20+ 用 transaction_isolation）
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- 会话 A：开启事务，先做一次快照读（此刻生成 ReadView）
BEGIN;
SELECT COUNT(*) FROM orders WHERE user_id = 42;

-- 会话 B：插入一条新数据并提交
BEGIN;
INSERT INTO orders (user_id, status, amount) VALUES (42, 1, 99.00);
COMMIT;

-- 会话 A：再查一次，行数不变（快照读）
SELECT COUNT(*) FROM orders WHERE user_id = 42;

-- 会话 A：改成当前读，幻影出现了——这是 RR 也挡不住的边界
SELECT COUNT(*) FROM orders WHERE user_id = 42 FOR UPDATE;
COMMIT;
长事务是隐形的炸弹。RR 下事务不结束，ReadView 就一直不释放，它之前的所有 undo 版本都不能被 purge 线程清理。SHOW ENGINE INNODB STATUS 里的 History list length 会一路涨，表空间只增不减，查询沿着越来越长的版本链往回走也越来越慢。所以「事务里不要放远程调用、不要等用户输入」不是风格问题，是容量问题。

面试落点：「RR 避免幻读要分两种读法：快照读靠 MVCC，ReadView 在事务第一次快照读时生成，所以整个事务看到同一个视图；当前读靠 next-key lock 锁住区间。但同一事务里先快照读、再当前读，仍然可能看到新插入的行，所以不能说 RR 完全消灭了幻读。」

模块 5

锁：RR 下一条 UPDATE 到底锁了多大范围

「UPDATE 会锁一行还是锁一张表？」这个问题的答案取决于WHERE 走不走索引，而不是取决于你的意愿。没索引就是锁全表所有行——注意，是给每一行都加上 next-key lock，而不是加一把表锁，但效果一样：别人全得等。

InnoDB 的锁按粒度分三层。表级的有意向锁（IS/IX），它的作用很单纯：快速判断表里有没有行被锁住，免得加表锁时还要逐行检查。行级的有三种：记录锁（Record Lock）锁住索引上的一条记录；间隙锁（Gap Lock）锁住两条记录之间的开区间，只存在于 RR；next-key lock 是「记录 + 前面的间隙」，左开右闭。

锁锁什么典型触发
记录锁索引上某一条具体记录唯一索引等值命中且记录存在
间隙锁两个索引值之间的空隙，不锁记录本身RR 下的范围查询、非唯一索引等值
next-key lock记录 + 它前面的间隙，左开右闭RR 下绝大多数加锁读
插入意向锁一种特殊的间隙锁，表示「我想往这个间隙插」INSERT 之前。它和间隙锁互斥，是死锁的常见来源
MDL元数据锁，语句级自动加DDL 要拿排他 MDL，会被长查询挡住，进而堵住后面所有请求

记住三条加锁规律，比背一堆例子有用：

唯一索引 + 等值 + 记录存在：next-key lock 退化成记录锁，只锁这一行。这是最理想的情况。
唯一索引 + 等值 + 记录不存在：锁住那个空隙，防止别人插进来。这就是「查一个不存在的 ID 也会锁住区间」的原因。
非唯一索引或范围条件：next-key lock 全量生效，会锁到「不满足条件但在区间内」的记录。RR 下这是死锁高发区。
-- 主键等值命中：只锁 id=100 这一行，别人改 101 不受影响
BEGIN;
SELECT * FROM orders WHERE id = 100 FOR UPDATE;

-- 非唯一索引等值：除了命中行，还会锁住相邻间隙（RR）
BEGIN;
SELECT * FROM orders WHERE user_id = 42 FOR UPDATE;

-- 没索引：每一行都被加上 next-key lock，等于锁表
BEGIN;
UPDATE orders SET status = 2 WHERE amount = 99.00;

-- 看谁在等谁（MySQL 8.0，5.7 用 information_schema.innodb_lock_waits）
SELECT * FROM performance_schema.data_locks\G
SELECT * FROM performance_schema.data_lock_waits\G

-- 锁等待超时，默认 50 秒，别在生产上调大
SELECT @@innodb_lock_wait_timeout;
MDL 是最容易被忽视的一把锁。一条执行 30 分钟的慢查询持着共享 MDL，此时有人执行 ALTER TABLE ADD COLUMN，DDL 排队等排他 MDL；而 DDL 后面所有新的查询又要排在 DDL 后面等共享 MDL——一条慢查询加上一个 DDL，可以把整张表彻底堵死。所以线上做 DDL 要用 pt-online-schema-change 或 gh-ost，并且先查 information_schema.processlist 有没有长事务。

面试落点：「加锁范围和 WHERE 用的索引强相关。唯一索引等值命中只锁一行；非唯一索引或范围条件在 RR 下会加 next-key lock，连间隙一起锁；如果 WHERE 没走索引，会对所有行加锁，效果等于锁表。所以线上 UPDATE 一定要走索引，这不是性能建议，是并发正确性问题。」

模块 6

死锁：不是数据库的 bug，是你的访问顺序有问题

「Deadlock found when trying to get lock; try restarting transaction」——看到这句，很多人的第一反应是让 DBA 调大超时。调大只会让它更晚发生，顺便让更多请求排队。

死锁的四个必要条件（互斥、占有且等待、不可剥夺、循环等待）在数据库里前三个都去不掉，只能破第四个：让所有人的加锁顺序一致。所以死锁排查的重点不是「怎么禁止」，而是「哪两条业务路径用相反的顺序锁了同两行」。

除了经典的「A 改订单再改库存，B 改库存再改订单」，还有两种更隐蔽的：

  • 间隙锁 + 插入意向锁：两个事务各自持有相邻区间的间隙锁，然后都想往对方区间插入。间隙锁之间不互斥，插入意向锁和间隙锁互斥，于是互相等。
  • 唯一键冲突：并发 INSERT 同一主键或唯一键时，失败的一方会去加共享锁（S 锁）读那行，而成功的一方持有排他锁（X 锁），第三方再进来就构成环。

所以「INSERT 不会死锁」是错的。批量插入时按主键排序，能消掉一大半这类问题。

-- 最近一次死锁的完整现场：两边各持有什么、在等什么、最终杀了谁
SHOW ENGINE INNODB STATUS\G
-- 在输出里找 LATEST DETECTED DEADLOCK 这一段

-- 让所有死锁都写进 error log（8.0 动态生效，无需重启）
SET GLOBAL innodb_print_all_deadlocks = ON;

-- 死锁检测默认开启：发现环就立刻回滚代价小的一方
SELECT @@innodb_deadlock_detect;
-- 高并发下检测本身耗 CPU，有的团队会关掉它、依赖超时，这是明确的取舍

-- 当前锁等待关系，先看是谁挡住了谁
SELECT waiting_pid, blocking_pid, waiting_query, blocking_query
FROM sys.innodb_lock_waits\G
减少死锁的手段为什么有效
固定加锁顺序（按主键升序、按业务 ID 排序）直接破坏循环等待，最根本的一条
事务尽量短，把远程调用挪到事务外持锁时间越短，交叉窗口越小
一次锁定所需全部行（SELECT ... FOR UPDATE 按主键排序）避免「边做边加锁」形成的交叉
WHERE 走索引，缩小加锁范围锁的行少了，碰撞概率自然下降
必要时降到 RC（binlog 用 ROW）RC 没有间隙锁，消掉一大类死锁
应用层对死锁做重试（有限次数 + 退避）死锁无法根除，重试是最后的兜底
一个真实的取舍：关掉 innodb_deadlock_detect 能省 CPU，但死锁会退化成「等 50 秒超时」，接口 RT 从毫秒变成几十秒。除非你的业务能接受这种长尾，否则别关。这类「有代价的优化」在面试里主动说出来，比说「要优化」有分量。

面试落点：「死锁的本质是循环等待加锁顺序不一致。我会先看 LATEST DETECTED DEADLOCK，确认两条 SQL 各自持有什么锁、在等什么锁，再回到业务代码确认加锁顺序。治理手段是固定顺序、缩短事务、让 WHERE 走索引；应用层一定要有重试，因为死锁不可能彻底消除。」

模块 7

EXPLAIN：只看 key 是不够的，要看 rows 和 Extra

很多人看 EXPLAIN 只看两列：key 有值就放心，type 是 ALL 就紧张。这两列都不够——真正决定耗时的，是 rows（预估扫多少行）和 Extra（有没有排序、有没有临时表、是不是覆盖索引）。

type 是访问类型，性能从好到差大致是：system > const > eq_ref > ref > range > index > ALL。看到 range 以上通常可以接受，看到 index 要警惕（扫了整个索引树），看到 ALL 就要问「为什么」。但注意：range 也可能扫几百万行，类型好不等于代价小。

列它在说什么怎么用
key实际用了哪个索引NULL 不一定是坏事，先看 rows 判断是不是主动放弃
key_len用到了索引的多少字节联合索引只用上前两列时，这个数会明显偏小，能反推用了几列
rows预估要扫多少行，是估算这是成本的核心。rows 接近全表行数，说明索引没起到过滤作用
filtered扫出来的行里，有多少百分比能通过后续条件rows × filtered 才是真正参与后续 JOIN 的行数
Extra补充动作：排序、临时表、覆盖、下推见下一张表，这一列的信息量最大
Extra 里的字样含义要不要处理
Using index覆盖索引，没回表这是好信号，别去「优化」它
Using index condition索引下推生效，过滤在引擎层完成好信号
Using whereServer 层还要再过滤一遍说明索引用得不够充分，配合 rows 判断值不值得加索引
Using filesort无法用索引顺序，额外排序小结果集可接受；大结果集要改索引或改 SQL
Using temporary用了内部临时表，常见于 GROUP BY、DISTINCT、UNION大表上出现就要处理，可能落到磁盘
Using join buffer被驱动表没索引，用了 join buffer 做块嵌套循环给被驱动表的关联列加索引
-- 传统 EXPLAIN：只给估算，不给真实耗时
EXPLAIN SELECT o.id, o.amount, u.name
FROM orders o JOIN users u ON u.id = o.user_id
WHERE o.status = 1 ORDER BY o.created_at DESC LIMIT 100;

-- 8.0.18+ 的 EXPLAIN ANALYZE：会真的执行，给出实际行数和耗时
-- 注意：DML 也会真的执行，只读语句才安全
EXPLAIN ANALYZE
SELECT o.id FROM orders o WHERE o.user_id = 42 AND o.status = 1;

-- 8.0 的树形格式，一眼看出哪个环节最贵
EXPLAIN FORMAT=TREE SELECT * FROM orders WHERE user_id = 42;

-- 统计信息不准会让优化器算错，必要时手动更新（大表注意开销）
ANALYZE TABLE orders;
EXPLAIN 的 rows 是采样估算，可能差一个数量级。InnoDB 靠索引页的随机采样来估计基数，数据分布倾斜时误差很大。所以不要因为「rows 只有 10」就断定没问题，也不要因为「rows 是 80 万」就直接加索引——用 EXPLAIN ANALYZE 或 SHOW PROFILE（旧版本）看真实值，再决定。

面试落点：「我看 EXPLAIN 的顺序是 type → rows → Extra。type 只说明访问方式，rows 才说明扫多少；Extra 里有 Using filesort 或 Using temporary，就说明索引没覆盖到排序和分组。如果 key 是 NULL，我会先算一下命中比例，判断是优化器主动放弃还是真的失效。」

模块 8

慢查询与深分页：把「慢」变成可比较的数字

「这条 SQL 有点慢」——这句话在工单里等于没说。慢查询治理的第一步不是优化，是把它变成一个数字：扫了多少行、回了多少次表、排序用了多大内存。

慢日志要开，但别乱开。long_query_time 的默认值较大（常见是 10 秒），线上业务基本要调到 1 秒甚至更低；log_queries_not_using_indexes 在小表多的库里会刷出大量无用记录，慎用。开了日志只是拿到原料，聚合分析才有结论——按「总耗时」排序，而不是按「单次最慢」排序，因为一条 3 秒跑 1 次的 SQL，危害远小于一条 50ms 跑 10 万次的 SQL。

-- 开慢日志：先看当前值，再改（部分参数需要重启，以版本为准）
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
SET GLOBAL min_examined_row_limit = 1000;   -- 扫得少的不记，减少噪音

-- 官方自带的两个汇总工具
# mysqldumpslow -s t -t 20 /var/log/mysql/slow.log
# pt-query-digest /var/log/mysql/slow.log > report.txt

-- 正在跑的语句：找长事务和卡住的查询
SELECT id, user, host, db, command, time, state, LEFT(info, 120) AS sql_text
FROM information_schema.processlist
WHERE command != 'Sleep' ORDER BY time DESC LIMIT 10;

深分页是另一个高频题，因为它的慢有明确的数学解释。LIMIT 100000, 20 不是「跳过 10 万行」，而是取出 100020 行，把前 100000 行丢掉。如果还带 SELECT *，那 10 万次回表一次不少。翻到后面几页，RT 线性上涨，这就是「第一页 20ms、第五千页 8 秒」的由来。

-- 慢：100020 行全部取出、回表，再丢掉 100000 行
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;

-- 改法一：游标（seek method）。要求有序、不回跳，最适合「下一页」式翻页
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;

-- 改法二：延迟关联。子查询只取主键（覆盖索引），再回表 20 次
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY id LIMIT 100000, 20) t ON o.id = t.id;

-- 改法三：业务上限制最大页数。翻到一万页之后的需求，八成是爬虫
-- 这一条最省钱，但要产品经理同意

三种改法的适用边界要说清：游标最快，但不支持跳页，且排序字段必须唯一（否则会漏行或重复）；延迟关联能跳页，但子查询仍然要扫 offset 行，只是省掉了回表；限制页数是产品方案。面试里能把「为什么游标要求排序字段唯一」讲出来，说明你真的用过。

面试怎么答：「深分页慢的本质是 offset 行必须被扫描和丢弃。我会先确认业务是否真的需要跳页：只翻下一页就用游标，把 offset 换成 WHERE id > 上一页最后一个 id；必须跳页就用延迟关联，让子查询走覆盖索引，把回表次数从十万降到二十。真正的解法往往在接口设计，不在 SQL。」
模块 9

主从复制：延迟不是「网络慢」四个字

「刚下的单，刷新一下订单列表没有了，再刷新又有了。」这类问题八成不是缓存，是读写分离撞上了复制延迟。而你去问「延迟多少」，对方回一句「Seconds_Behind_Master 是 0」——这个指标本身就可能骗人。

先把复制的三个线程说清：主库的 dump 线程把 binlog 发给从库；从库的 IO 线程接收并写入 relay log；从库的 SQL 线程（8.0 里叫 applier）回放 relay log。延迟可能发生在任何一段，但绝大多数是最后一段——单线程回放追不上主库的并发写入。

binlog 格式记什么取舍
STATEMENTSQL 原文日志小，但含 NOW()、UUID()、LIMIT 不带 ORDER BY 时主从不一致
ROW每一行改前改后的值最安全，是主流选择；缺点是日志量大，大更新会膨胀
MIXED按语句自动选折中，但排查时你永远不知道下一条是什么格式

延迟的常见原因，按出现频率排：大事务（一次删 50 万行，主库跑 10 秒，从库要回放 10 秒且期间无法并行）、从库配置差或还在承担查询、无主键表的 ROW 复制（每一行都要全表扫，代价是平方级）、DDL（从库串行执行，大表加索引能卡几十分钟）、单线程回放（主库 32 并发，从库 1 个线程）。

-- 8.0.22+ 用 REPLICA，旧版本把关键字换成 SLAVE，语义一致
SHOW REPLICA STATUS\G

-- 关键字段：
--   Replica_IO_Running / Replica_SQL_Running  两个都必须是 Yes
--   Seconds_Behind_Source                     只是粗略值，可能为 0 但实际有延迟
--   Retrieved_Gtid_Set / Executed_Gtid_Set    两个集合的差，才是真实缺口
--   Relay_Log_Space                           持续增长说明回放跟不上

-- 更可靠的做法：对比 GTID 集合，或写心跳表由主库定时更新
SELECT GTID_SUBTRACT(@@global.gtid_executed, '主库的 gtid_executed');

-- 并行回放（8.0 常见配置，具体参数含义以版本文档为准）
SHOW VARIABLES LIKE 'replica_parallel_workers';
SHOW VARIABLES LIKE 'replica_parallel_type';
Seconds_Behind_Master 为什么不准。它是「从库当前时间」减去「正在回放的那条 binlog 事件的时间戳」。如果主库很久没有写入，从库回放完了，差值就是 0——但它可能落后了几千个事务没被感知；如果主库时钟和从库不一致，这个数还会变成负数或巨大值。所以判断延迟要看 GTID 差集或心跳表，而不是这一个数字。

业务层怎么兜：写入后立刻要读的数据，强制走主库（按用户 ID 绑定，或者写入后 N 秒内读主库）；能容忍短暂不一致的（比如商品列表），才走从库。半同步复制能减少丢数据的窗口，但它不消除延迟——它保证的是「至少一个从库收到 binlog 才返回」，不是「从库已经回放完」。

面试落点：「复制分三段：主库 dump、从库 IO 线程写 relay log、SQL 线程回放。延迟绝大多数在回放这一段。Seconds_Behind_Master 只能参考，我更喜欢看 GTID 差集或者心跳表。治理上是大事务拆小、大表加主键、开并行回放；业务上对一致性敏感的操作强制走主库。」

模块 10

10 个坑：面试官最爱在这里追问第二句

下面这些不是知识点错误，是判断方式错误。它们的共同点是听起来很专业，一追问就露出没有真正处理过线上问题。

1
建了索引就以为一定会用
优化器按成本选路径。选择性差、回表太多、统计信息过期，都会让它主动放弃。先看 rows 和命中比例，再谈「失效」。
2
联合索引的列顺序随便排
顺序决定能用上几列。等值条件在前、范围条件在后、排序字段接在等值列后面，这个顺序不是风格问题，直接决定索引有没有用。
3
在索引列上套函数或做隐式转换
索引里存的是原值，一旦对列做 DATE()、CAST 或字符串拼数字，B+ 树就无序了。注意方向：varchar 列和数字比较才会失效，数字列和字符串比较通常仍走索引。
4
用 SELECT * 把覆盖索引毁掉
多取一列就可能触发回表。列表页只查展示需要的列，是很便宜的一次优化，而且能顺带减小网络传输。
5
以为 RR 完全消灭了幻读
快照读靠 MVCC，当前读靠 next-key lock。同一事务里先快照读、再 FOR UPDATE，仍会看到新插入的行。答「完全避免」会被追问到崩。
6
长事务不当回事
undo 不能 purge，history list 一路涨，表空间只增不减，查询沿版本链越走越慢。事务里放 RPC 和等用户输入，是最常见的元凶。
7
用 UUID 当主键
随机写入引起页分裂、填充率下降；36 字节的主键还会把所有二级索引一起撑大。要全局唯一就用有序 ID。
8
用 LIMIT offset 做深分页
offset 行必须被扫描并丢弃，越翻越慢。改成游标或延迟关联，或者产品层面限制最大页数。
9
无主键表 + 大事务，只盯着主库
ROW 格式下，无主键表的每一行更新在从库都要全表扫；大事务又无法并行回放。主库指标漂亮，从库延迟一小时。
10
业务高峰直接执行 DDL
DDL 要排他 MDL，前面一条长查询就能让它排队，而它后面所有请求都在等。上线前查长事务，用 gh-ost 这类工具，别在高峰动手。

面试落点：被问「你踩过什么坑」，讲一个有前后因果的。比如「我们给 status 建了索引，QPS 反而掉了，后来才想明白只有三个值、回表比例太高，优化器改回全表扫反而是对的。我们把索引改成 (status, created_at) 的联合索引，让列表页变成覆盖索引，才真正解决」——这比背十条坑名可信得多。

自测

六道题

1. 联合索引 (a, b, c)，查询条件是 WHERE b = 1 AND c = 2，且查询列都在索引里。最准确的说法是？
正确答案：只能做索引全扫描。联合索引按 a、b、c 的顺序逐级有序，缺少最左列 a 就无法二分定位。但因为查询列都在索引里，可以扫整个索引树而不是整张表，type 通常显示 index。MySQL 不会为了某条 SQL 自动调整索引列顺序。
2. 给只有 3 个取值的 status 列建了索引，查询 WHERE status = 1（命中约 2/3 的行），EXPLAIN 显示 type=ALL、key=NULL。最合理的解释是？
正确答案：优化器主动放弃。命中比例高时，走二级索引要回表几十万次随机读，比顺序扫整张表更贵。这不是「索引失效」，而是成本模型算出的正确决策。解决办法是让查询变成覆盖索引，或把过滤性更强的列放进联合索引，而不是 FORCE INDEX。
3. RR 隔离级别下，事务 A 先执行了一次普通 SELECT，之后事务 B 插入新行并提交。此时 A 再执行普通 SELECT，结果是？
正确答案：看不到，加锁读可能看到。RR 下 ReadView 在事务第一次快照读时生成，之后复用，所以普通 SELECT 看到的是同一个时间切片。而 FOR UPDATE 属于当前读，读最新已提交版本，会看到 B 插入的行——这正是「RR 不能完全避免幻读」的边界。
4. 主键 id 上执行 SELECT * FROM t WHERE id = 100 FOR UPDATE，且 id=100 这行存在。RR 下它加了什么锁？
正确答案：只加记录锁。唯一索引等值命中且记录存在时，next-key lock 会退化为记录锁，只锁这一行——这是加锁范围最小、并发最好的情况。如果记录不存在，则会锁住相应间隙；如果 WHERE 不走索引，才会对所有行加 next-key lock。
5. 订单表 500 万行，接口需要按 id 顺序翻页，目前用 LIMIT 4000000, 20，越翻越慢。最合适的改法是？
正确答案：游标翻页。offset 行必须被扫描并丢弃，加索引或加大缓存都不能消除这部分工作。游标把 offset 换成主键范围条件，每次只扫 20 行。前提是排序字段唯一且业务接受不能跳页；必须跳页时用延迟关联，让子查询走覆盖索引。
6. 从库 Seconds_Behind_Master 一直是 0，但业务反馈刚写入的数据读不到。最合理的下一步是？
正确答案：看 GTID 差集或心跳表。该指标是「从库当前时间」减去「正在回放事件的时间戳」，主库没有新写入时它会归零，无法反映真实缺口。对比 Retrieved_Gtid_Set 与 Executed_Gtid_Set 的差集，或用主库定时更新的心跳表，才可靠。

术语一句话解释
聚簇索引以主键组织的 B+ 树，叶子节点存放完整行，主键索引即数据本身
二级索引除主键外的索引，叶子只存索引列和主键值，取其他列必须回表
回表用二级索引拿到主键后，再去聚簇索引取整行的过程，代价是随机 IO
覆盖索引查询需要的列全在索引里，无需回表，EXPLAIN 的 Extra 显示 Using index
索引下推把部分过滤条件下推到存储引擎层，在回表前先用索引值筛掉不匹配的行
最左前缀联合索引按列顺序逐级有序，缺失最左列就无法用于定位
页分裂向已满的页插入数据时拆成两页，随机主键会造成填充率下降和碎片
MVCC多版本并发控制，用 undo log 版本链 + ReadView 实现无锁的一致性读
ReadView可见性判断结构，含 m_ids、min_trx_id、max_trx_id、creator_trx_id 四个关键字段
快照读 / 当前读普通 SELECT 读历史版本；加锁读和写操作读最新已提交版本
next-key lock记录锁加前面的间隙锁，左开右闭，RR 下范围查询的默认加锁方式
间隙锁锁住两个索引值之间的开区间，目的不是锁现有行，而是阻止插入
MDL元数据锁，DDL 需要排他 MDL，会被长查询阻塞并连带堵住后续所有请求
history list length未被 purge 的 undo 版本数量，长事务会让它持续增长
GTID全局事务标识，用集合差集判断复制进度比时间差可靠
