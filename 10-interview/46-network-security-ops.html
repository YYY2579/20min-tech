读之前先答一句：给你一份「137 个端口对公网开放」的清单，你第一个关哪个、为什么？
开始前

「全部关掉」不是安全，是一次没有预案的变更

安全同学发来一份清单：扫出来 137 个端口对公网开放，要求本周内收敛完。你挑了看起来最危险的几个直接关掉，第二天早上客服群炸了——监控 agent 连不上服务端、报表任务卡在半路、某个合作方的回调全失败。你做了安全要求的事，却被当成事故的责任人。

这件事的错不在「收紧访问」，在于你把一次影响面未知的变更当成了配置修改。安全加固和发布一样，都要先回答三个问题：这条规则现在在放谁进来、关掉之后谁会断、断了以后多久能发现。三个问题答不上来就动手，和闭着眼改生产配置没有区别。

常见说法听起来很专业的问题实际上的漏洞
我们把高危端口都封了「哪些算高危？」端口的「危险程度」取决于跑在上面的服务和它的认证方式，不是端口号本身。3306 暴露给内网业务是正常设计，暴露到公网才是问题
我们上了零信任「零信任里你去掉了哪个信任假设？」如果回答是「买了某产品」，说明没做。零信任改的是判断依据：从「你在内网所以可信」改成「你每次都要证明你是谁、这台设备合规吗、这次访问的上下文合理吗」
我们过了等保「整改项里你亲手做的是哪几条？」过测评是一次性事件。面试官想知道你知不知道「账号唯一、权限最小、操作可审计、日志能追溯到人」这些为什么重要
边界
谁可以进来。安全组、ACL、防火墙、零信任代理，这一层决定攻击面有多大。
身份
进来的是谁。账号、密钥、堡垒机、多因素，这一层决定一次登录后能干什么。
留痕
干了什么能查到。审计日志、命令留痕、日志留存周期，这一层决定事后能不能还原。
响应
出事了怎么办。隔离、取证、恢复的顺序，这一层决定损失有多大。
这篇的组织方式：先讲安全边界为什么从「城墙」变成了「每次访问都要证明」；然后讲规则怎么写、暴露面怎么盘；接着是 DDoS 与 CC 的分层判断、传输加密的取舍；再落到账号审计与合规的通用原则、应急响应的顺序；最后是加固的落地顺序和一套面试话术。每一节末尾都留一句可以直接说出口的话。

面试落点：「我收紧访问一定先做三件事：先加观测再改规则，先在非关键路径上灰度，先想好回滚。因为我遇到过『按清单封端口，第二天监控全断』——清单不知道这个端口背后跑的是什么。」

模块 1

安全边界的演变：从「你在内网」到「你每次都要证明」

传统模型是一句隐含假设：在内网的就是自己人。这条假设一旦成立，防火墙之内几乎畅通无阻——一台被钓鱼拿下的笔记本、一个被攻破的第三方运维账号，就能横着走完整片内网。

零信任不是某个产品，是把这条假设删掉。它把「一次登录、长期可信」换成三个每次都要重新回答的问题：你是谁（身份）、你用的这台设备合规吗（设备状态与补丁）、你这次访问的上下文合理吗（时间、地点、目标、行为基线）。判断发生在每次访问，而不是在边界那一次。

维度传统边界模型零信任思路
信任依据网络位置（IP、网段、VLAN）身份 + 设备状态 + 访问上下文
认证时机进内网时一次每次访问都校验，凭证有较短的有效期
网络可达性内网默认互通默认不可达，按需放行到具体应用
内部横向移动基本没有阻拦服务间也要认证授权，微隔离
运维代价低，但一旦被突破损失大高，策略数量和执行点都变多

别把零信任讲成「不用防火墙了」。落地时它是叠加而不是替换：边界依然存在（公网入口还是要收敛），只是在边界之内又加了一层按身份和设备的判断。真正的代价在运维侧——策略数量会从几十条变成几千条，执行点从一台防火墙变成每个应用前面的代理或 sidecar，出问题时的排查链路也变长。

面试官追问「那你现在是零信任吗」时的诚实答法：「我们没有完整落地，做的是其中几件性价比高的：SSH 走堡垒机并开了多因素、管理后台一律不直接暴露公网、服务间调用加了 mTLS 或至少做了来源限制、账号权限按季度复核。剩下的部分还在排期，因为策略治理的成本比买产品高得多。」这个回答比「上了」可信十倍。

还有一个常被忽略的前提：零信任的前提是身份体系干净。如果公司里还有一堆共享账号、离职没销户的账号、写死在配置文件里的密钥，那上再先进的网关也没用——攻击者用合法身份进来的。先清账号，再谈架构。

面试落点：「零信任不是产品，是去掉『内网即可信』这个假设。它的判断依据从网络位置换成身份加设备加上下文，代价是策略数量和执行点大幅增加。所以我不会说『我们上了零信任』，我只能说我们做了哪几件事、还差哪几件。」

模块 2

安全组 / ACL / 防火墙：规则设计的三条铁律

这三样东西经常被混着说，但它们的作用域和状态性不一样，写错了就会「明明放行了却还是不通」，然后花两小时查一个根本不存在的网络故障。

机制作用层有无状态最容易踩的点
云安全组实例（虚拟机网卡）级别有状态只需配入方向，回程自动放行；但跨安全组的双向访问要两边都配
网络 ACL子网级别无状态出入方向都要配，还要放行临时端口范围，否则「握手能过、数据回不来」
主机防火墙单机（iptables / nftables）有状态（需显式放 ESTABLISHED）规则顺序敏感，第一条匹配就生效；容器环境还会被 Docker 插入的规则影响

三条铁律，按重要性排：

默认拒绝，逐个放行。入方向默认全拒，只开必需的端口和来源。反过来「默认全开、把危险的加黑」永远追不上业务变化——新增的每一个服务都是新的暴露面。
来源写到最细。不要写 0.0.0.0/0，写具体的对端安全组、具体网段、具体 IP。SSH 只放办公网出口和堡垒机地址，数据库只放应用所在子网，管理后台只放内网或零信任网关的地址。
规则必须带注释和责任人。三个月后没人记得 10.0.0.0/8 -> 8080 是给谁开的。没有归属的规则既不敢删也不敢留，最后堆积成谁都不敢动的垃圾。
# 先看清楚当前到底开了什么（有状态规则集）
nft list ruleset 2>/dev/null | head -60
iptables -S 2>/dev/null | head -60

# 本机在监听哪些端口、绑在哪个地址上
ss -lntup

# 只开一条：允许堡垒机网段访问 SSH，其余入站默认丢
nft add rule inet filter input tcp dport 22 ip saddr 10.10.0.0/24 accept

# 无状态 ACL 要注意：入方向放行后，出方向的回程端口也要放
# 否则现象是「握手建上、数据传不动」

# 云上：安全组的『来源』优先填对端安全组 ID，而不是 CIDR
# 这样对端扩容换 IP 时规则不用改

一个高频追问：「为什么我加了放行规则还是不通？」排查顺序固定：规则顺序（前面有没有一条 DROP 先命中）、作用对象（你改的是子网 ACL 还是实例安全组）、方向（无状态 ACL 出方向没配）、以及容器环境里的规则注入——Docker 会在宿主机的 nat/filter 表里插自己的链，你加在 INPUT 上的规则对走 FORWARD 的容器流量无效。

改防火墙规则前先给自己留一条后路。远程机器上改 SSH 相关规则时，先开一个「已经建立的连接不受影响」的保底，或者用 at / systemd-run 挂一个 10 分钟后自动还原的定时任务，确认新规则没问题再取消。这不是小题大做——把自己锁在服务器外面是运维最尴尬的事故之一，而且它完全可预防。

面试落点：「规则设计我坚持三条：默认拒绝、来源写到最细、每条带注释和责任人。改之前我会先把『谁在用这条规则』查清楚，用连接数或日志确认，改的时候留一条自动还原的退路。安全组是有状态的只需配入方向，ACL 无状态要出入都配，这两个混着配就会出现握手能过数据回不来的怪现象。」

模块 3

暴露面盘点：先知道你有什么在外面

暴露面盘点不是跑一次扫描出一份报告。报告只是起点，真正的工作是给每一个开放项找到「它是谁开的、给谁用、能不能收」。找不到归属的开放项，就是未来的事故。

盘点分四条线走，缺一条就会有漏网之鱼：

线要拿到的清单常用手段
公网入口所有公网 IP、绑定的域名、放行的端口云控制台或 API 列举公网地址与带宽；对入口做端口扫描
主机监听每台机器在监听什么、绑在 0.0.0.0 还是 127.0.0.1批量执行 ss -lntup 汇总，对比基线
应用入口管理后台、中间件控制台、API 文档、调试端点网关/Ingress 的路由清单；代码里搜 /admin、/actuator、/swagger 这类路径
凭证与密钥公网可达服务上的弱口令、默认口令、代码里的硬编码密钥配置扫描与密钥扫描进 CI；对公网服务做弱口令自查
# 1. 批量收集监听情况（配合 ansible/pssh 在所有机器上跑一次）
ss -lntup | awk 'NR==1 || /LISTEN/ {print $1,$5,$6,$7}'

# 2. 从外面看自己：全端口 TCP 扫描（务必只扫自己的资产）
nmap -Pn -sT -p- --open -T3 your.public.ip
# --open 只显示开放的；UDP 扫描慢且结果噪声大，另行安排

# 3. 确认一个公网服务到底是谁在访问（有日志才有结论）
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# 4. 找机器上的 SUID 程序（提权路径之一）
find / -xdev -type f -perm -4000 2>/dev/null

# 5. 找没人管的监听：把当前结果与上周基线对比
diff <(ss -lntup | sort) /opt/baseline/listen.last

盘点之后是收敛顺序，这个顺序决定了你的工作会不会挨骂：先收「没有流量的」（日志里零访问的开放端口，风险最低），再收「有流量但来源明确的」（把 0.0.0.0/0 改成具体来源），最后才动「来源不明且流量大的」（这类要拉业务方 Confirm，往往要一两周）。反过来做，第一天就会出事。

「先加观测，再改规则」是这一节唯一必须记住的操作。具体做法：在收紧之前，先在网关或主机上把这条规则的命中计数、来源 IP、目标端口记下来，跑够一个业务周期（至少覆盖一个完整的工作日，最好一周，因为有些任务是按周跑的）。有了这份数据，你才知道关掉它会影响谁、影响多大。没有这份数据就去关端口，本质上是在赌。

还有两类特别容易被忘掉的暴露面：临时的（为了排查临时开的端口、临时放通的安全组、临时给合作方开的白名单，事后没人回收）和默认的（中间件自带的控制台、框架自带的调试端点、镜像里预置的默认账号）。前者靠流程——临时放行必须带到期时间；后者靠基线——新机器入网先过一遍标准检查。

面试落点：「我盘暴露面分四条线：公网入口、主机监听、应用入口、凭证密钥。收到清单后我不按危险程度收敛，我按『有没有流量、来源明不明确』排序，先收零访问的，再收来源明确的，来源不明且流量大的一定拉业务方确认。改之前先加观测跑一个业务周期，没有数据我不动规则。」

模块 4

DDoS 与 CC：先分清是哪一层被打满了

「我们被 DDoS 了」这句话信息量约等于零。带宽被打满、连接表被打满、应用线程池被打满、数据库被打满——这四种现象的处理方式完全不同，而且前两种你自己几乎无能为力，必须依赖上游。

层典型现象谁在消耗什么你能做的
带宽 / 容量入口带宽跑满，丢包率暴涨，正常请求也进不来链路带宽基本做不了，靠运营商或云厂商的清洗/高防；自己只能把入口收窄、减少可被打的目标
连接 / 状态表半连接数暴涨，dmesg 出现 SYN flood 提示，新连接建不上连接表、半连接队列、内存开 syncookies、调队列、缩短超时；云上靠高防
应用 / 请求层（CC）QPS 暴涨但带宽不高，接口 RT 上升，线程池耗尽CPU、线程池、连接池、下游限流、人机校验、降级、扩容、缓存前置
数据层慢查询堆积，连接池打满，主库 CPU 100%数据库连接与 IO限流上游、加缓存、摘掉非核心查询、只读从库分流

区分的关键指标很朴素：看带宽和 QPS 谁先到顶。带宽先满、QPS 不高，是大流量攻击；带宽没满、QPS 高得离谱且每个请求都很正常，是 CC。判断错了就会用错手段——对 CC 加带宽毫无用处，对大流量攻击加限流也拦不住（包在到你的限流组件之前就把链路占满了）。

# 连接总数与状态分布（先看是不是连接层被打）
ss -s
ss -tan state syn-recv | wc -l
ss -tan state established | wc -l

# 内核有没有在抱怨 SYN flood
dmesg -T | grep -i 'syn flood'

# 连接跟踪表是不是快满了（表满会静默丢新连接）
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max

# 请求层：来源 IP 分布，CC 一般有明显集中
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -20

# 抓包看包形态：大量 SYN 无 ACK、还是完整 HTTP 请求
tcpdump -nn -c 200 'tcp[tcpflags] & tcp-syn != 0'
ss -s先看连接总量和各状态分布，判断是不是连接层被打
dmesg -T | grep -i 'syn flood'内核对 SYN flood 有明确提示，别只盯应用日志
ss -tan state syn-recv | wc -l半连接堆积是 SYN 类攻击的直接证据
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head来源集中说明是 CC，分散则更像大流量攻击
cat /proc/sys/net/netfilter/nf_conntrack_count连接跟踪表接近上限时新连接会被静默丢弃
nft list ruleset | head -60改规则前先看清楚现有规则的顺序和命中情况

缓解手段按层次对号入座，别乱用：容量层靠上游清洗、高防、CDN 把流量分散掉，你自己能做的是提前把入口收敛、别把源站 IP 暴露出去；连接层靠 syncookies、调大队列、缩短半连接超时；请求层靠限流（按 IP、按用户、按接口分别设阈值）、人机校验、对非核心接口直接降级；数据层靠限流上游和加缓存。限流的位置越靠前越有效——在应用里限流，包已经进来了；在网关限流，链路还是被占着；在清洗中心拦掉，才真正省下了带宽。

一个容易被忽略的准备项：攻击发生的时候你没有时间做决策。所以平时就该准备好三样东西：上游清洗/高防的联系电话或工单入口（知道怎么触发、多久生效）、一份限流和降级的开关清单（哪个开关能立刻砍掉非核心流量）、一份正常流量的基线（不然你根本判断不出「涨了多少」算异常）。这三样都在平时准备，出事当天再做就已经晚了。

面试落点：「我先分清被打的是哪一层：带宽先满是大流量攻击，只能靠上游清洗和高防；QPS 高而带宽不高是 CC，靠限流、人机校验、降级。判断依据是带宽和 QPS 谁先到顶。限流位置越靠前越有效。平时我会准备好清洗入口、降级开关清单和流量基线，因为出事当天来不及做这些。」

模块 5

传输安全：版本、证书轮换，以及内网要不要加密

「内网流量不用加密」在很多公司还是默认做法。这句话在零信任语境下已经站不住了——内网不等于可信，一次抓包就能拿到明文的时代，未加密的内部调用就是最大的数据泄露面之一。

关于协议版本，实用的判断是：老版本该关就关，但关之前先确认没有老客户端。TLS 1.0/1.1 已经被主流标准和主流浏览器弃用，继续开着的意义主要是兼容极老的客户端；具体你的服务端支持到哪一版、默认最低版本是多少，以你环境的配置和官方文档为准，别照抄博客里的数字。关闭操作必须灰度，因为「某个合作伙伴的老 SDK 连不上」这种事只有真连的时候才会暴露。

动作为什么操作要点
禁老协议版本老版本有已知弱点，且不满足常见合规基线先统计客户端的协议分布再禁；禁完保留快速回退能力
证书轮换自动化手工换证书一定会忘，而过期是 P0 级事故用 ACME 类的自动签发；同时要有到期告警
到期告警提前30 天足够处理一次意外，7 天不够告警发给能换证书的人，不是发给值班群
内网加密内网不可信，明文等于把数据摊开服务网格 mTLS 是最省事的一条路；代价是延迟和复杂度
证书链完整链不全会导致部分客户端校验失败服务端要发中间证书，叶证书在前
# 看服务端实际协商出来的协议与证书有效期（一定要带 SNI）
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates

# 本机证书什么时候到期（换证书前后都看一眼）
openssl x509 -in /etc/ssl/certs/example.pem -noout -enddate

# 响应头里的安全相关配置（HSTS 等），有没有生效以实际响应为准
curl -sI https://example.com | grep -iE 'strict-transport|content-security|x-frame'

# 检查一个端口是不是明文协议（能 grep 到内容就是明文）
timeout 5 tcpdump -i any -A -nn -c 20 'tcp port 8080' 2>/dev/null | head -40
证书过期是唯一一种「可以 100% 预防却仍然每天都在发生」的故障。三件事必须做全：自动化签发和续期（别指望人记得）、到期告警独立于业务告警（业务挂了才发现的告警不算告警）、告警有明确 owner（发给群等于没人负责）。另外，证书轮换也是一次变更，轮换后要验证：链全不全、新证书有没有被所有实例拿到（有些实例可能没重载配置）。

内网加密的取舍要说清楚：mTLS 解决的是「服务间互相认证 + 流量加密」，但它不是免费的。代价是握手延迟（可以通过会话复用来摊薄）、证书生命周期管理（服务多了以后这是真正的运维负担）、以及排障变难（抓包看到的是密文，要调试得有办法解密或换个观测点）。所以常见做法是按数据敏感程度分级：涉及用户信息、凭证、支付的内部调用先上，纯内部指标上报这类可以先不上。

面试落点：「协议版本我按『先统计客户端分布、再灰度关闭』来做，具体版本支持以环境配置为准不照抄数字。证书必须自动续期，外加提前 30 天的到期告警并指定 owner。内网加密我支持做，但会按数据敏感度分级，因为它有延迟、证书管理和排障变难三个代价。」

模块 6

账号、权限、审计与日志留存：合规部分的通用原则

面试官问到等保、合规这类话题时，最忌讳的是背条款编号——你背的那条可能对不上最新版本，追问两句就露馅，而且背条款本身不构成能力。真正该讲的是通用原则，这些原则在任何一套标准里都成立。

先声明边界：不同行业、不同地区适用的标准和具体要求不一样，条款编号和级别划分也会更新。具体条款以最新标准和测评机构的解释为准，我不背编号。下面讲的是几乎所有合规体系都要求的通用原则，以及运维在每一条上要交什么作业。
通用原则它在防什么运维要交的作业
身份唯一出事时追不到人；共享账号泄露无法定位一人一账号，禁共享；离职即销户；接入统一身份源
权限最小一个账号被拿下就拿到全部权限按角色授权；高危操作二次审批；定期复核并回收
多因素口令泄露就等于账号失守管理入口、堡垒机、云控制台强制多因素
行为可审计事后还原不了「谁在什么时候做了什么」所有运维操作走堡垒机并留命令记录；禁用『先 sudo 再各干各的』
日志可追溯日志被删、被改、或者压根没记关键日志集中存储且应用账号只有追加权限；留存周期按行业规定和合同要求确定，不凭印象
密钥可轮换一个密钥用了三年，泄露了也不知道密钥进专门的管理系统，禁止写进代码和配置仓库；有轮换周期

这几条里，「权限最小」和「定期复核」是最难坚持的，因为它们和「方便」直接冲突。一个实用做法是：权限带有效期。给人授权时就写清楚到期时间，到期自动回收，需要再用就再申请。这比「每年做一次权限复核」有效得多——年度复核往往变成走过场，因为有几百条权限要确认，没人真的看。

# 谁在什么时候登录过（发行版不同，日志位置可能是 secure 或 auth.log）
last -n 20
journalctl -u sshd --since '2 hours ago' | grep -iE 'failed|accepted'

# 统计失败登录的来源，判断有没有在被爆破
grep -i 'failed password' /var/log/auth.log 2>/dev/null \
  | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head -10

# 系统里还有哪些能登录的账号（有没有忘了回收的）
awk -F: '$3 >= 1000 && $7 !~ /(nologin|false)/ {print $1, $3, $7}' /etc/passwd

# sudo 权限发给了谁（有没有给得过大）
grep -rE '^[^#]*ALL=' /etc/sudoers /etc/sudoers.d/ 2>/dev/null

# 审计子系统可用时，查登录类事件（auditd 是否启用以环境为准）
ausearch -m USER_LOGIN --start recent 2>/dev/null | head -20
「日志留存」这一条，运维最容易掉进的坑是只留了系统日志。合规和事后追溯真正需要的是业务操作日志——谁改了配置、谁导出了数据、谁审批了这次发布。系统日志只能告诉你「root 在 3 点登录了」，业务操作日志才能告诉你「张三在 3 点 05 分修改了支付限额」。第二类日志往往没人做，等要做的时候发现代码里根本没有埋点。

留存周期这一项要诚实：不要在网上找一个数字就写进方案。不同行业、不同合同里的要求不一样，正确做法是查你所在行业的规定和甲方合同，然后把结论写进运维规范。说「按行业规定和合同要求执行，我们的内部基线是 X 天」比说「按规定是 180 天」可信得多，因为前者表明你知道这个数字是有来源的。

面试落点：「合规部分我不背条款编号，讲的是通用原则：身份唯一、权限最小、多因素、行为可审计、日志可追溯、密钥可轮换。具体条款以最新标准和测评机构解释为准。运维侧我最强调的是权限带有效期和业务操作日志，因为前者能防权限堆积，后者决定了事后能不能还原。」

模块 7

应急响应：隔离、取证、恢复的顺序之争

「发现机器被入侵了，第一件事做什么？」很多人脱口而出「拔网线」。这个答案在有些情况下是对的，在另一些情况下会让你永远查不出是谁干的、怎么进来的。

先把目标说清楚：应急响应的目标不是「尽快恢复服务」，而是在控制损失的前提下，保留能回答「谁、怎么进来的、动过什么」的能力。这两个目标有张力，顺序就是在权衡这个张力。

先止损（分钟级）。如果攻击还在进行、数据还在外泄、或者横向移动还在扩散，先切断它：摘掉公网入口、隔离主机到单独 VLAN、吊销泄露的凭证和密钥、禁用被攻破的账号。这一优先级高于取证。
再取证（小时级）。止损动作要挑「保留证据」的那一种。能把主机隔离到只出不进的网段就别直接关机——关机丢的是内存里的东西：进程列表、网络连接、未落盘的恶意脚本。先做一次内存和关键状态的快照，再做磁盘镜像。
然后恢复（小时到天级）。恢复不要用「清理一下继续跑」的方式，要用重建：从可信的镜像或备份重建，密钥全部轮换，补丁打齐。被入侵过的主机上的任何二进制都被污染的可能。
最后复盘（天级）。写清楚时间线、入侵路径、影响范围（哪些数据可能被访问过）、以及改进项带 owner 和日期。没有改进项的复盘等于没复盘。
该做不该做原因
先吊销凭证和密钥先重启机器凭证泄露了重启也没用，对方还能再来；重启还会抹掉内存证据
隔离到可控网段直接关机或格式化关机丢内存状态，格式化丢磁盘证据，之后无法还原入侵路径
先快照再分析在受感染主机上跑分析工具你运行的每一个命令都可能改变状态，而且工具本身可能已被替换
重建而不是清理删掉可疑文件继续用你不知道有没有后门、有没有被替换的系统命令、有没有定时任务
记录所有操作与时间几个人同时上手各查各的多人操作会破坏现场，而且事后没人说得清是谁改的
# 止损第一步：摘掉这台机器的公网入口（云平台操作优先于本机操作）
# 然后在本机断掉对外连接，先把现场留住

# 取当前状态快照：进程、连接、定时任务、最近登录
ps auxef > /tmp/incident/ps.txt 2>&1
ss -tunap > /tmp/incident/net.txt 2>&1
crontab -l > /tmp/incident/cron.txt 2>&1
ls -la /etc/cron.d/ > /tmp/incident/crond.txt 2>&1
last -n 50 > /tmp/incident/last.txt 2>&1

# 找异常自启动：定时任务、systemd 单元、rc 脚本、profile
systemctl list-unit-files --state=enabled | head -40
grep -rIl 'curl\|wget\|base64 -d' /etc/cron.d /etc/systemd 2>/dev/null

# 关键：把命令记录落到一个只追加的位置，事后能还原你自己做了什么
# 有条件的话把所有操作同步到堡垒机的审计里
「先止损还是先取证」的正确判据是：攻击是否还在进行。还在进行（数据在持续外泄、横向移动在扩散、挖矿进程在跑）就先止损，用「摘入口、吊销凭证」这类不破坏证据的手段；已经停止（比如只是一次性的入侵，攻击者已经离开）就先取证，把内存和磁盘状态留下来。不要用「直接关机」当止损手段，它同时毁掉了取证能力，而摘掉公网入口通常能达到同样的效果。

面试落点：「第一件事不是拔网线，是判断攻击还在不在进行。还在进行就先摘入口、吊销泄露的凭证和密钥——这些动作能止损又不破坏证据。然后做内存和磁盘快照再分析，不在受害机上直接跑工具。恢复用重建不用清理，密钥全部轮换。最后复盘要有带 owner 和日期的改进项。」

模块 8

加固的落地顺序：先做哪件，为什么

安全加固的清单可以列得很长，但资源有限。真正决定成败的不是做多少项，是顺序——顺序错了，你会把力气花在收益最低的地方，还会惹恼业务方。

顺序做什么为什么排在这里
1清账号与密钥收益最高、成本最低、不需要协调任何人。共享账号、离职未销户、硬编码密钥，这几样改完攻击面立刻小一圈
2收敛公网暴露面直接决定「有多少东西能被从外面摸到」。按模块 3 的顺序做，先零访问后来源明确的
3加观测和审计有了审计，前面两步才知道做得对不对；有了观测，后面几步才有回滚依据
4补齐补丁与镜像基线收益确定，但需要重启或重建，所以要排在观测之后，且必须分批灰度
5传输加密与内网认证收益真实但代价明显（延迟、证书管理、排障变难），按数据敏感度分级推进
6微隔离与零信任成本最高、策略治理负担最重，前面几步没做完就上它，只会得到一堆没人维护的策略

这张表背后的逻辑只有一条：先做「不需要协调、可回滚、收益确定」的，再做「需要协调、影响链路、收益依赖设计」的。清账号不需要任何人同意，收敛暴露面只需要你自己加观测；而微隔离要每个业务方确认自己的调用关系，做不完就是一堆半成品。

每一步都要遵守同一套变更纪律：分批、可回滚、有验证标准。分批的意思是先在一台或一个非核心集群上做；可回滚的意思是改之前存一份当前配置的副本；有验证标准的意思是事先写明「做完之后跑什么命令、看到什么结果算成功」。缺任何一条，这次加固就是一次赌博。

# 改之前先存现场（配置、规则、当前连接情况）
cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak.$(date +%F)
nft list ruleset > /opt/backup/nft.$(date +%F).rules
ss -lntup > /opt/backup/listen.$(date +%F).txt

# 分批：先在一台机器上改，验证通过再批量
ansible -i inventory.ini 'groupa[0]' -m copy -a 'src=sshd_config.new dest=/etc/ssh/sshd_config' --check
ansible -i inventory.ini 'groupa[0]' -m service -a 'name=sshd state=reloaded'

# 验证：改完之后立刻确认新连接能建、老连接没断
ssh -o BatchMode=yes -o ConnectTimeout=5 user@target 'echo ok'
ss -tan state established | wc -l

# 回滚：一旦不对，用备份立刻还原
cp -a /etc/ssh/sshd_config.bak.$(date +%F) /etc/ssh/sshd_config
一个能立刻提升可信度的说法：被问「你怎么证明加固有效」时，不要说「我们做了 XX 项」。要说「我们有一个可重复的验证：每月跑一次暴露面盘点，把结果与上月基线对比，新增的开放项必须说明来源；账号每季度复核一次，超期未确认的自动回收；演练时我们用一个未授权的账号去尝试访问，看能不能被拦住」。能重复的验证比一次性整改有说服力得多。

面试落点：「我排优先级的依据是『需不需要协调、能不能回滚、收益确不确定』。清账号和收暴露面排最前，因为它们不需要协调、能回滚、收益确定；微隔离排最后，因为它依赖业务调用关系梳理，做不完就是半成品。每一步都分批、存现场、写清楚验证标准。」

模块 9

面试话术：讲一次收紧访问的经验

「讲一次你做安全加固的经历」——这道题的满分答案里，技术细节只占三分之一，另外三分之二是你怎么控制风险、怎么处理冲突。因为几乎所有人都能说出「我封了端口、开了多因素」，但只有做过的人才会讲到「我先加了两周观测」。

用这个结构讲，四段，每段一句话能说完：

背景与范围。「我们有 N 台机器，其中管理后台和几个中间件控制台对公网开放，是历史遗留，没人说得清是谁开的。」——给数字，但只给你确定知道的数字。
你的判断。「我没有直接按清单关端口，因为清单不知道每个端口背后是谁在用。我先加了观测，把来源 IP 和访问量记了两周。」
动作与冲突。「两周后发现有两个来源不明的访问，我拉业务方确认，其中一个是他们早就废弃的对账任务。剩下的收敛成分批灰度，先收零访问的，最后收有流量的，每批之间留观察窗口。」
结果与机制。「零业务中断完成收敛，并且把『临时放行必须带到期时间』写进了规范，之后新增的公网开放项都要登记 owner。」
被追问加分回答
「你关错了怎么办？」「每批都存了配置副本和回滚命令，回滚是分钟级的。而且我是按批次做的，最坏情况只影响一批。」
「业务方不同意收紧怎么办？」「我给他数据：这两周的访问来源和量级。他要么确认这是他的流量（那就把来源写细继续用），要么确认是废弃的（那就关）。用数据谈，不用『安全要求』压人。」
「你怎么知道做完之后没有遗漏？」「我把盘点做成了可重复的：每月跑一次，与上月基线对比，新增项必须说明来源。一次性整改会退化，可重复的检查不会。」
「零信任你们上了吗？」「部分。我们做了堡垒机加多因素、管理后台不直接暴露公网、权限带有效期。完整的微隔离还在排期，因为它需要梳理业务调用关系，成本比买产品高。」
「等保你们怎么过的？」「具体条款以最新标准和测评机构解释为准，我不背编号。我负责的作业是账号唯一、权限最小、操作可审计、日志能追溯到人这几条。」
三个绝对不要说的话：「我们把高危端口全封了」（说明你按编号做事而不是按服务）、「这个肯定是黑客攻击」（没有证据不要定性，说「现象是什么、我验证了什么」）、「安全那边要求的」（说明你只是执行者，没有自己的判断）。运维岗的安全题考的是判断力，不是服从度。

面试落点：「我讲加固经历一定带上『先观测两周』这个动作，因为它能同时体现我知道清单不可信、也知道怎么控制风险。结尾我会落到机制上——把盘点做成每月可重复的检查，把临时放行加上到期时间。一次性整改会退化，机制不会。」

模块 10

9 个坑：每一条都会让你挨一顿骂

安全运维的坑有个共同点：它们不会让你做错事，而是让你用正确的方法做错对象。比如「收紧访问」是对的，但收紧错了对象就是事故。

1
按端口号判断危不危险
危险的是「谁在访问、有没有认证」，不是端口号。3306 给内网业务用是正常设计，给公网用才是问题。按端口号封，会封掉业务、放过真正的风险。
2
不加观测就改规则
你不知道这个端口背后跑的是什么、谁在用。正确顺序是先记录来源和访问量，跑够一个业务周期（要覆盖按周跑的任务），再动手。
3
把安全组和 ACL 当成一回事
安全组有状态，只需配入方向；网络 ACL 无状态，出入都要配，还要放行回程端口。混着配就会出现「握手能建、数据传不动」。
4
规则不写注释和责任人
三个月后没人知道这条规则给谁开的，既不敢删也不敢留，最后堆成谁都不敢动的垃圾。规则上带 owner 和到期时间，是成本最低的治理手段。
5
远程改 SSH 规则不留退路
把自己锁在服务器外面是最尴尬的事故，而且完全可预防。先确认已有连接不受影响，或挂一个定时自动还原的任务，验证通过再取消。
6
DDoS 时只知道加机器
带宽层被打满加机器毫无用处，包在到你之前就把链路占满了。先分清是容量层、连接层、请求层还是数据层，再选手段。
7
证书靠人记得换
唯一一种可以百分之百预防却每天都在发生的故障。必须自动续期，外加独立于业务告警的到期提醒，并且指定明确 owner。
8
出事第一反应是关机
关机丢内存里的进程、连接和未落盘脚本，等于毁掉取证能力。摘公网入口和吊销凭证通常能达到同样的止损效果，且不破坏现场。
9
只留系统日志就说「有审计」
系统日志只能说明「root 在 3 点登录了」，业务操作日志才能说明「谁改了什么配置」。后者往往需要代码埋点，等要查的时候补就来不及了。

面试落点：挑一条讲，结构固定：当时的判断、造成的后果、后来改成了什么机制。第三段最重要——它决定面试官认为你是「踩过坑」还是「长了记性」。

自测

六道题

1. 拿到一份「137 个端口对公网开放」的扫描清单，最合理的第一动作是？
正确答案：先加观测。扫描清单只知道端口开着，不知道背后跑的是什么、谁在用。先记录来源 IP 和访问量并跑够一个业务周期（要覆盖按周执行的任务），才能按「有没有流量、来源明不明确」排序收敛。按端口号封会封掉业务，转发给别人则失去了运维的判断职责。
2. 云上把子网的网络 ACL 入方向放行了 8080，客户端却反馈「握手能建上、数据传输卡住」。最可能的原因是？
正确答案：ACL 无状态，出入都要配。安全组是有状态的，只需配入方向、回程自动放行；而网络 ACL 是无状态的，出方向的回程流量也要显式放行，否则就会出现握手成功但数据传不动的现象。这是两种机制混着配置时最典型的错误。
3. 入口带宽被打满、但 QPS 并不高，最准确的判断是？
正确答案：大流量攻击，靠上游。带宽先满而 QPS 不高，说明消耗的是链路带宽而不是应用资源。此时包在到达你的限流组件之前就把链路占满了，应用层限流无效。正确做法是触发运营商或云厂商的清洗、高防，把流量在入口侧拦掉；平时就该准备好清洗入口和流量基线。
4. 发现一台机器被入侵且攻击仍在进行（数据持续外泄），第一优先级动作是？
正确答案：用不破坏证据的方式先止损。攻击还在进行时止损优先于取证，但止损手段要挑：摘公网入口、吊销凭证和密钥，既能切断攻击又保留内存和磁盘状态。直接关机能止损但会毁掉内存里的进程、连接和未落盘脚本，导致事后无法还原入侵路径。
5. 关于「零信任」，下面哪种说法体现了你真的理解它？
正确答案：去掉「内网即可信」的假设。零信任改的是判断依据：不再因为「你在内网」就信任你，而是每次访问都要校验身份、设备状态和上下文。它不是某个产品，也不是拆掉防火墙——边界依然存在，只是在边界之内又加了一层判断。落地的主要代价是策略数量和执行点大幅增加。
6. 面试官问到等保 / 合规要求，最合适的回答方式是？
正确答案：讲通用原则并声明边界。条款编号会随标准更新而变化，背错了反而露馅。讲通用原则既准确又能体现你知道每一条背后防的是什么。留存周期这类数字要说明它来自行业规定和合同要求，而不是给自己找一个来源不明的数字。
