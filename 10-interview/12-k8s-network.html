读之前先答一句：客户端的包发到 ClusterIP，是谁把它改成 Pod IP 的？
开始前

三个现场：都叫「网络不通」，修的地方差三个组件

「服务调不通」是 K8s 里最没有信息量的一句话。同一个现象，可能是 DNS 解析到了错的名字、可能是 iptables 规则没下发、可能是跨节点封装把大包丢了、也可能是 Ingress 的 host 没匹配上。这四个原因分布在四个组件里，你在错的地方翻一天也不会有结果。

现场直觉答案真实原因
curl 服务名超时，直接 curl Pod IP 秒通网络插件坏了DNS 或 Service 规则。名字解析出来是 ClusterIP，而 ClusterIP 只是一串内核规则，规则没下发或端口写错，包就凭空消失
ping 通、小请求通，一传大文件就卡死带宽不够，或者对方处理慢MTU。Overlay 封装要额外占几十字节，Pod 里还按 1500 发，包在隧道口被分片或丢弃，表现为「握手成功、传数据卡住」
同一个命名空间内互通，跨命名空间全挂namespace 之间有隔离命名空间本身不隔离网络。是某个 NetworkPolicy 选中了目标 Pod，让它那个方向变成默认拒绝
数据面在核里
Service 转发、NetworkPolicy 拦截，最终都由内核的 netfilter/IPVS 或 eBPF 完成。没有哪个进程在「转发请求」。
控制面只写规则
kube-proxy、CNI 的 agent、CoreDNS 都是「把期望翻译成规则」的角色。规则写完就退出画面，剩下的事内核干。
地址会变，名字不变
Pod IP 随重建变动，ClusterIP 在 Service 生命周期内不变，域名靠 DNS 维护。三层地址各有各的失效方式。

这一篇按「一个请求从外到内」的顺序走：先看 Pod 网络模型和 CNI 铺的路，再拆 Service 这层虚拟地址怎么变成规则，然后是 NodePort、负载均衡和 Headless 的差别，接着是 Ingress、DNS 和 NetworkPolicy 三道关，最后把跨节点访问的完整路径和排查顺序收在一起。

一个能贯穿全文的判断：网络问题的排查顺序，永远是从「离你最近的确定性」往外推。你确定 Pod 在跑、确定端口在听、确定 IP 是多少，然后一层层往外验证。反过来从「外网打不开」往里查，你会同时怀疑五个组件。

面试怎么答：「K8s 网络我会分五层看：Pod 之间的三层连通（CNI 负责）、Service 的虚拟 IP（kube-proxy 写规则）、集群内名字解析（CoreDNS）、四层暴露（NodePort/LB）、七层入口（Ingress Controller）。每一层都有一个明确的负责人，出问题先定位是哪一层，再看那个组件的状态。」

模块 1

Pod 网络模型：一个 Pod 一个 IP，且不用 NAT

K8s 对 Pod 网络只提了三条要求：每个 Pod 有自己的 IP；所有 Pod 之间可以直接通，不需要 NAT；同一台机器上的容器和 Pod 看到彼此的地址是一样的。这三条听起来像废话，但它们决定了 CNI 必须实现什么。

实现方式在每台节点上是同一套：Pod 里有一块 eth0，它和宿主机上的一根 veth 配对；veth 这一头接到网桥（或者直接被路由规则处理），节点上的路由表知道「这个 Pod IP 应该从哪根 veth 出去」。跨节点的那一跳，才是 CNI 真正要解决的问题——别的节点怎么知道这个 Pod IP 在哪台机器上。

方案跨节点怎么走代价典型实现
Underlay / 路由把 Pod 网段的路由发布到物理网络，或节点之间直接路由性能最好，但要底层网络配合，IP 段规划要提前做Calico 的 BGP 模式
IPIP用 IP 协议套 IP，包头加 20 字节开销小，只支持 IPv4 单播；部分网络会拦协议号 4Calico 的 IPIP 模式
VXLAN用 UDP 封装二层帧，包头加 50 字节兼容性最好，能过大多数网络；封装/解封装有 CPU 开销Flannel、Calico 的 VXLAN 模式
host-gw纯路由，节点把对方 Pod 网段的下一跳指向对端节点最快，但要求所有节点在同一二层网络Flannel 的 host-gw

这四种方案的差别，落到排障上只有一个关键数字：MTU。物理网卡是 1500 时，VXLAN 之后 Pod 里能用的只有 1450，IPIP 之后是 1480。如果 CNI 没把这个值配到 Pod 的网卡上（或者某个节点配错了），Pod 会以为自己是 1500，发出去的大包在隧道口塞不进去——表现就是小请求正常，一传大数据就卡住，而且 ping 是通的，因为 ping 的包很小。

# 1. Pod 的 IP、所在节点、走的哪块网卡
kubectl get pod -o wide
kubectl exec web-0 -- ip -4 addr show eth0
kubectl exec web-0 -- ip route

# 2. Pod 网卡的 MTU：和节点物理网卡对比，差的就是封装开销
kubectl exec web-0 -- ip link show eth0 | grep -o 'mtu [0-9]*'
ip link show eth0 | grep -o 'mtu [0-9]*'

# 3. 节点上能看到 veth 配对和隧道路由
ip route | grep -E 'cali|flannel|cni'
ip -d link show | grep -A1 vxlan

# 4. CNI 的配置在哪：二进制、配置、日志三个位置
ls /etc/cni/net.d/
ls /opt/cni/bin/ | head
journalctl -u kubelet --since "10 min ago" | grep -i cni

# 5. MTU 验证：带 DF 标志打不同大小的包，找到不通的那个尺寸
kubectl exec web-0 -- ping -M do -s 1400 -c 2 <peer-pod-ip>
kubectl exec web-0 -- ping -M do -s 1450 -c 2 <peer-pod-ip>

CNI 本身是一个很薄的规范：容器运行时在创建 Pod 沙箱时调用 CNI 插件，传入 ADD、DEL、CHECK 三种命令，插件负责把网卡、IP、路由配好，然后返回结果。所以「Pod 卡在 ContainerCreating」时，一条很有效的路径是看 kubelet 日志里 CNI 那一段——IP 分配失败、插件二进制缺失、配置解析错，都会在这里留下一行。

还有一个常被问的细节：Pod 里的 lo 是一直有的，eth0 是 CNI 配的。所以「同一个 Pod 里两个容器用 localhost 互访」跟 CNI 无关，它们共享的是同一个网络命名空间，走的是回环。这也解释了为什么 sidecar 模式的代理能拦到主容器的流量——它们在同一张网卡上。

MTU 问题的迷惑性在于「有时通有时不通」。TCP 握手包很小，能过；一旦开始传数据，满载的 1500 字节包在隧道口超限，如果中间设备又不回 ICMP「需要分片」，发送方就一直重传。表现出来是：连接建立成功、小响应正常、下载大文件或调大接口卡死。看到这个组合，第一个怀疑对象应该是 MTU，而不是带宽。

面试怎么答：「K8s 的 Pod 网络模型是每个 Pod 一个 IP、Pod 之间直接通、不做 NAT。跨节点靠 CNI，路由型性能最好但要底层配合，隧道型兼容性好但有封装开销。这个开销在排障上就体现为 MTU：VXLAN 少 50 字节，IPIP 少 20 字节，配错就是小包通、大包卡。」

模块 2

Service：ClusterIP 上没有进程，只有规则

「kube-proxy 在 ClusterIP 上监听，把请求转给 Pod。」这句话是错的，而且是面试里区分「用过」和「背过」的分水岭。没有任何进程监听 ClusterIP，它甚至不在任何网卡上。包能被转走，是因为节点内核里有一条规则，把目的地址改写了。

完整的链条是这样：Service 对象创建后，控制器把匹配的 Pod 地址写进 EndpointSlice；每个节点上的 kube-proxy watch 到变化，把「ClusterIP:port → 一组 PodIP:port」翻译成 iptables 规则或 IPVS 虚拟服务；客户端发包时，包进入节点协议栈，在 PREROUTING/OUTPUT 阶段命中 DNAT 规则，目的地址被改成某个 Pod IP；回程靠 conntrack 把源地址改回去。

模式转发怎么做负载均衡规模上的问题
iptables每个 Service 一组链：KUBE-SERVICES → KUBE-SVC-xxx → KUBE-SEP-xxx用 statistic 模块按概率随机选一条规则数随 Service 和 Endpoint 线性增长，全量同步变慢，匹配是线性遍历
IPVS内核里的虚拟服务，真实服务器列表挂在上面哈希表，支持 rr、lc、sh 等调度算法规模好得多，但需要内核模块，且某些场景仍要配合 iptables
eBPF（CNI 自带）在 socket 层或 tc 层直接改写，绕过 conntrack由 CNI 实现决定性能好，但排查工具和 iptables 那套不一样，得看 CNI 自己的命令
# 1. 先确认这个 Service 有没有后端（一切都从这里分叉）
kubectl get endpointslice -l kubernetes.io/service-name=web -o wide

# 2. iptables 模式：看三条链是否串起来
iptables -t nat -L KUBE-SERVICES -n | grep <cluster-ip>
iptables -t nat -L KUBE-SVC-XXXXXXXX -n
iptables -t nat -L KUBE-SEP-XXXXXXXX -n

# 3. IPVS 模式：看虚拟服务和真实服务器
ipvsadm -Ln | grep -A3 <cluster-ip>

# 4. conntrack：一条连接的 DNAT 记录长什么样
conntrack -L -d <cluster-ip> 2>/dev/null | head

# 5. kube-proxy 自己的日志和模式
kubectl -n kube-system logs ds/kube-proxy --tail=50
kubectl -n kube-system get cm kube-proxy -o yaml | grep -E 'mode|scheduler'

这里有两个必须说清的细节。第一，ClusterIP 的 ping 不通是正常的。它是个虚拟地址，只对特定协议和端口的规则生效，ICMP 根本没有对应规则，包会被丢掉。所以「ping 一下 Service IP」这个动作没有任何诊断价值，很多人在这里得出「网络不通」的错误结论。

第二，DNAT 只在包第一次进入时发生，之后靠 conntrack 记住。这意味着一条长连接一旦被转到某个 Pod，就会一直粘在那个 Pod 上，不会因为后端扩容而重新分配。这也是「扩容了但流量没上来」的原因之一——老连接还在老 Pod 上。要重新分配，只能让连接断开重建（这也是为什么发布时优雅退出比扩容更重要）。

还有一个语义差异值得记：Service 的 port 和 targetPort 不是一回事。port 是别人访问你的入口，targetPort 是容器真实监听的端口，两者可以不同。targetPort 写名字时，必须和容器 ports[].name 完全一致；名字对不上，EndpointSlice 里的端口就是错的，连接直接被拒，而 Service 对象本身看起来完全正常。

「规则没下发」比「规则写错」更常见。kube-proxy 是按节点同步的，同步有延迟，节点多的时候可能几秒到几十秒。新建 Service 后立刻访问失败，先等一轮同步再下结论。另外 kube-proxy 挂了不会影响已有连接（规则还在内核里），但新 Service 会彻底不通——这个现象很容易被误判成「网络插件挂了」。

面试怎么答：「ClusterIP 不是进程，是 kube-proxy 写进内核的 DNAT 规则，iptables 模式是一串链加概率选择，IPVS 模式是内核里的虚拟服务。所以 ping ClusterIP 不通是正常的，它只对配置的端口有规则。DNAT 只在首包发生，之后靠 conntrack，所以长连接会粘在后端，扩容不会重新分配。」

模块 3

NodePort、LoadBalancer、Headless：三种暴露，三种失效方式

这三种类型经常被当成「暴露级别的递进」，其实它们的失效方式完全不同。NodePort 死在端口和策略上，LoadBalancer 死在云控制器和健康检查上，Headless 死在客户端假设上。

类型怎么工作源 IP典型坑
ClusterIP节点内 DNAT 到 Pod变成节点 IP（SNAT）集群外无法直接访问
NodePort每个节点监听 30000-32767 的某个端口，转发到 Service默认 SNAT 成节点 IP端口范围固定；安全组要放行；节点 IP 变了入口就变
LoadBalancer云控制器创建 LB，把流量导到 NodePort 或 Pod取决于 externalTrafficPolicy云控制器没跑就拿不到外部 IP；健康检查打错端口
HeadlessclusterIP 为 None，DNS 直接返回 Pod IP 列表客户端直连 Pod客户端要自己做负载均衡和重试；DNS 缓存会拿到已死的 IP

NodePort 有两个必须知道的约束。第一是端口范围由 apiserver 的 --service-node-port-range 决定，默认 30000-32767，写个小端口会被拒。第二是安全组和防火墙：很多云环境只放行了 80/443，NodePort 的 3 万端口在外面根本连不上，但集群内部测试一切正常，所以这类问题经常被拖到上线才炸。

externalTrafficPolicy 是这节最值得记住的字段，因为它同时影响三件事：

取值流量路径源 IP副作用
Cluster（默认）可以转到任意节点的 Pod，可能要再跨一次节点被 SNAT 成节点 IP，业务拿不到真实客户端 IP多一跳，延迟略高
Local只转到本节点上的 Pod保留真实源 IP本节点没有该服务的 Pod 时，流量被直接丢弃，不是转到别处

「Local 会丢包」这一点非常反直觉：你以为「本节点没有就找别的节点」，实际是「没有就丢」。所以在节点数少、副本数少、或者有节点亲和性的场景里，用 Local 很容易出现「部分节点访问不通，其他节点正常」的诡异现象——而这恰恰是最难查的一类，因为你的探针可能正好落在健康的节点上。

# 1. 三种类型的关键字段
kubectl get svc web -o jsonpath='{.spec.type}{" "}{.spec.clusterIP}{" "}{.spec.externalTrafficPolicy}{" "}{.spec.ports}{"\n"}'

# 2. LoadBalancer 拿不到外部 IP 时，先看云控制器和事件
kubectl -n kube-system get pod | grep -i cloud
kubectl describe svc web | sed -n '/Events/,$p'

# 3. NodePort 是否真的在每个节点上都监听（在节点上执行）
ss -lntp | grep <node-port>
iptables -t nat -L KUBE-NODEPORTS -n | head

# 4. Headless：DNS 返回的是一串 A 记录，不是一个 VIP
kubectl get svc web-headless -o jsonpath='{.spec.clusterIP}{"\n"}'
kubectl exec tmp -- nslookup web-headless.prod.svc.cluster.local

# 5. StatefulSet 的单 Pod 域名（需要 headless Service）
kubectl exec tmp -- nslookup web-0.web-headless.prod.svc.cluster.local

Headless 的误区值得单独说：它经常被当成「省一个 ClusterIP」的优化，实际上它把负载均衡的责任推给了客户端。DNS 返回一组地址，客户端通常只用第一个（或者按自己的策略选），如果第一个 Pod 挂了，客户端要自己发现并重试。而 DNS 还有缓存和 TTL，Pod 重建换了 IP 之后，客户端可能还拿着一批旧地址在打。StatefulSet 用它是为了「每个成员有稳定名字」，不是为了性能。

选型的一句话：集群内互调 → ClusterIP；临时对外、没有 LB → NodePort（记得放行安全组）；生产对外、需要固定入口和证书 → LoadBalancer 或 Ingress；需要每个成员单独寻址（数据库集群、Kafka） → Headless。

面试怎么答：「NodePort 是在每个节点开一个高端口转发，范围默认 30000 到 32767，问题通常出在安全组；LoadBalancer 靠云控制器创建真实 LB；Headless 没有 VIP，DNS 直接返回 Pod IP，客户端要自己做负载均衡。externalTrafficPolicy 设成 Local 能保留源 IP，但本节点没有后端时流量会被丢弃，这是它最容易踩的地方。」

模块 4

Ingress：它只是一份配置，干活的是 Controller

「我创建了 Ingress，为什么没生效？」因为 Ingress 对象本身不做任何事。它是一份声明「哪个域名、哪个路径应该转到哪个 Service」的配置，必须有一个 Ingress Controller 在跑，把它翻译成自己那套代理配置（nginx 的 server/location、traefik 的路由表、envoy 的 listener）。

这就解释了为什么「Ingress 创建成功但访问 404」是最高频的现象：对象合法，没人执行。判断只需要一条命令——集群里有没有 IngressClass、有没有对应的 controller Pod、这个 Ingress 有没有指定 class。

现象原因验证
所有域名都 404没有 controller，或者 Ingress 的 ingressClassName 没匹配上看 IngressClass 和 controller Pod 是否存在
某个域名 404，其他正常host 不匹配（含端口、大小写、通配符写法）curl 时带 Host 头，逐条对照规则
路径 404，根路径正常pathType 与 rewrite 配置不匹配Prefix 会把前缀带下去，Exact 必须完全相等
502 Bad GatewayController 连不上后端：Service 没后端、端口错、Pod 不 Ready看 controller 日志里的 upstream 地址
504 Gateway Timeout后端处理超过 proxy-read-timeout对照后端实际耗时，调超时而不是盲目加重试
413 Request Entity Too Large请求体超过 proxy-body-size按业务上限调整，不要设成无限大
# 1. 有没有 controller、有没有 class
kubectl get ingressclass
kubectl get pod -A | grep -i -E 'ingress|traefik|envoy'
kubectl get ingress web -o jsonpath='{.spec.ingressClassName}{" "}{.spec.rules}{"\n"}'

# 2. 带 Host 头验证路由，别用 IP 直接打
curl -sS -o /dev/null -w '%{http_code}\n' -H 'Host: api.example.com' http://<ingress-ip>/v1/users

# 3. controller 日志里能看到它选中的 upstream
kubectl -n ingress-nginx logs deploy/ingress-nginx-controller --tail=50

# 4. 确认后端 Service 和端口，Ingress 只认 serviceName + port
kubectl get ingress web -o jsonpath='{.spec.rules[*].http.paths[*].backend}{"\n"}'
kubectl get endpointslice -l kubernetes.io/service-name=web -o wide

# 5. TLS：证书在 Secret 里，名字要和 tls 段一致
kubectl get ingress web -o jsonpath='{.spec.tls}{"\n"}'
kubectl get secret web-tls -o jsonpath='{.type}{"\n"}'

Ingress 与 Service 的分工，用一句话说清：Service 解决「一组 Pod 的稳定四层地址」，Ingress 解决「HTTP 请求按域名和路径分给哪个 Service」。所以 Ingress 的后端一定是 Service，不能直接写 Pod；Ingress 也不做 TCP/UDP 的一般转发（那要靠 controller 自己的扩展配置，各家写法不同）。

另一个必须知道的现实：Ingress 的注解不跨 controller 通用。nginx.ingress.kubernetes.io/rewrite-target 只在 nginx 系 controller 上有效，换到 traefik 就是一堆没用的字符串，而且不会报错。所以从别的项目抄 Ingress YAML 时，先确认 controller 是不是同一家；不同家的话，规则能抄，注解不能抄。

pathType 是个安静的坑。Prefix 表示按路径前缀匹配，Exact 表示完全相等，ImplementationSpecific 交给 controller 自己解释。同一个 /api，写成 Prefix 时 /api/users 能命中，写成 Exact 时只有 /api 本身能命中。从 Exact 改成 Prefix 之后路径突然都能访问了，很多人以为是自己「修好了路由」，其实是把匹配范围放开了。

面试怎么答：「Ingress 是七层的路由声明，必须配 controller 才有用，对象创建成功不等于生效。排查先看 IngressClass 和 controller 是否存在，再看 host、path、pathType 是否匹配，最后看后端 Service 有没有 Endpoint。它还负责 TLS 终止，证书放在同命名空间的 Secret 里。注解是 controller 私有的，换一家就失效。」

模块 5

CoreDNS 与 ndots:5：那 5 秒延迟是怎么来的

「服务偶尔会慢 5 秒，重启就好了，过一阵又来。」这类现象有一个非常经典的成因，而且和业务代码一点关系都没有：Pod 里的 resolv.conf 带了一个 ndots:5，访问外部域名时先撞了五次不存在的集群内域名。

先看 Pod 里到底写了什么。Kubernetes 会给每个 Pod 生成一份 resolv.conf，search 域是一串后缀，ndots 是一个阈值：如果查询的名字里「点的数量」小于 ndots，就先依次拼接 search 里的后缀去查，全部失败才查原名。

# Pod 里的真实配置长这样（namespace 不同，第一行不同）
cat /etc/resolv.conf
# search prod.svc.cluster.local svc.cluster.local cluster.local
# nameserver 10.96.0.10
# options ndots:5

# 查一个外部域名时，DNS 查询的实际顺序是：
#   api.example.com.prod.svc.cluster.local   -> NXDOMAIN
#   api.example.com.svc.cluster.local        -> NXDOMAIN
#   api.example.com.cluster.local            -> NXDOMAIN
#   api.example.com.（原名）                  -> 成功

api.example.com 只有两个点，小于 5，所以前面那几次拼接查询都会真实发生。每次 NXDOMAIN 都要走一趟 CoreDNS，如果 CoreDNS 负载高、或者上游 DNS 慢，这几次查询累计起来就是几百毫秒到几秒。而 NXDOMAIN 还会被负缓存，某些客户端库在解析失败后会重试，把延迟放大成「偶尔 5 秒」。

解法有三个，按推荐程度排：写 FQDN（末尾加点），让客户端跳过 search 列表，这是最便宜的；在 Pod 的 dnsConfig 里把 ndots 调小（比如 2），但要确认集群内的短名访问是否还依赖它；部署 NodeLocal DNSCache，把 DNS 查询放到节点本地，减少往返和 CoreDNS 压力。三个可以叠加。

现象可能原因验证
所有名字都解析不了CoreDNS 全挂，或 kube-dns Service 没有 Endpointnslookup kubernetes.default，看有没有响应
集群内短名能解析，全名不能search 域不对（比如跨 ns 用了短名）对比 /etc/resolv.conf 的 search 与目标 ns
外部域名慢、内部快ndots:5 导致的 search 放大dig 时加 +search 观察查询次数
解析结果指向已删除的 PodDNS 缓存 / 负缓存，或 headless 地址未及时更新看 TTL，直接查 CoreDNS 的 kubernetes 插件结果
间歇性 SERVFAILCoreDNS 上游转发超时、并发不够看 CoreDNS 日志和 metrics 的请求延迟
# 1. 从 Pod 里查，别在节点上查——节点用的是另一份 resolv.conf
kubectl exec -it tmp -- cat /etc/resolv.conf
kubectl exec -it tmp -- nslookup web.prod.svc.cluster.local
kubectl exec -it tmp -- nslookup api.example.com

# 2. 看 search 列表参与了几次查询（dig 的输出会列出实际查询名）
kubectl exec -it tmp -- nslookup -debug api.example.com 2>&1 | grep -i 'query\|name'

# 3. 末尾加点 = 绝对域名，跳过 search 列表
kubectl exec -it tmp -- nslookup api.example.com.

# 4. CoreDNS 自己是否健康：副本数、日志、Corefile
kubectl -n kube-system get pod -l k8s-app=kube-dns -o wide
kubectl -n kube-system logs -l k8s-app=kube-dns --tail=50
kubectl -n kube-system get cm coredns -o yaml | sed -n '/Corefile/,/^  [a-z]/p'

# 5. 按 Pod 覆盖 DNS 参数（ndots 调小 + 指定 nameserver）
# spec.dnsConfig:
#   options: [{name: ndots, value: "2"}]
#   nameservers: ["10.96.0.10"]

CoreDNS 的工作方式值得记一句：它读一个叫 Corefile 的配置，里面最关键的插件是 kubernetes（负责 .cluster.local 这类集群内域名，直接查 apiserver 的 Service/Endpoint）和 forward（负责把外部域名转给上游）。所以「集群内域名解析不了」和「外部域名解析不了」是两条完全不同的链路，前者看 kubernetes 插件和 apiserver 连通性，后者看 forward 和节点上的上游 DNS。

一个容易忽略的细节：hostNetwork: true 的 Pod 用的是节点自己的 resolv.conf，不是集群那份。所以同一段代码，在普通 Pod 里能用短名访问 Service，在 hostNetwork 的 DaemonSet 里就解析不了。这类差异在部署日志采集、监控 agent 时经常遇到。

面试怎么答：「Pod 的 resolv.conf 里 search 有三个后缀、ndots 是 5，所以查询一个只有两个点的外部域名时，会先拼三次 search 后缀得到 NXDOMAIN，才查原名，延迟就是这么来的。解法是写 FQDN 末尾加点、把 ndots 调小、或者上 NodeLocal DNSCache。集群内域名和外部域名走的是 CoreDNS 的两个不同插件，排查要分开。」

模块 6

NetworkPolicy：写它的是 K8s，执行它的是 CNI

NetworkPolicy 有一个让所有人第一次遇到都会懵的语义：它不是「拒绝列表」，是「一旦选中就默认拒绝」。你写了一条「允许 frontend 访问 api」，结果 api 连 DNS 都查不了了——因为 egress 方向也被默认拒绝了，而你没写放行 53 端口的规则。

准确地说：一个 Pod 如果在某个方向上被任意一条策略选中，那个方向就变成默认拒绝，只允许策略里显式列出的流量。方向分 ingress 和 egress，由 policyTypes 决定；不写 policyTypes 时，有 ingress 规则就认为管 ingress，有 egress 规则就认为管 egress。

选择器选的是什么常见误用
podSelector同命名空间内的 Pod（按标签）以为能选到别的 ns 的 Pod，实际必须配 namespaceSelector
namespaceSelector整个命名空间里的 Pod（按 ns 标签）用 ns 的名字当标签——ns 必须有对应的 label 才匹配得上
ipBlockCIDR 段，可带 except用它写 Pod 网段，Pod 重建换 IP 后就失效了
ports端口和协议只写 port 不写 protocol，UDP 的 DNS 请求被拦
# 1. 策略存在不等于生效：先确认 CNI 是否实现了 NetworkPolicy
kubectl get netpol -A
kubectl -n kube-system get pod | grep -i -E 'calico|cilium|weave|canal'

# 2. 看这条策略选中了哪些 Pod（policy 的 podSelector 与 Pod 标签）
kubectl describe netpol allow-frontend -n prod
kubectl get pod -n prod --show-labels | grep api

# 3. egress 放行 DNS 是最容易漏的一条
#    ports: [{protocol: UDP, port: 53}, {protocol: TCP, port: 53}]
#    to: [{namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: kube-system}}}]

# 4. 实测：从 A Pod 打 B Pod，再用一个不该通的组合做对照
kubectl exec -it frontend-0 -n prod -- wget -qO- --timeout=3 http://api:8080/healthz
kubectl exec -it other-0 -n prod -- wget -qO- --timeout=3 http://api:8080/healthz

# 5. eBPF 型 CNI 有自己的策略视图（以你集群的 CNI 为准）
calicoctl get networkpolicy -A 2>/dev/null
cilium policy get 2>/dev/null | head

「CNI 不支持就是一张废纸」这句话要说得准确一点：对象会被 apiserver 接受，但没有任何组件去执行它，不会报错、不会告警、不会有事件。Flannel 单独使用时就是这样，它只做连通，不做策略；Canal 是 Flannel 加 Calico 的策略引擎，才有拦截能力。所以「我们上了 NetworkPolicy 做零信任」这句话，在面试里最好补一句「前提是 CNI 支持」，否则很容易被追问到哑口。

另一个实践中的取舍：默认拒绝 + 白名单是安全上正确的做法，但它的运维成本很高——每加一个依赖就要加一条规则，漏了就是线上故障，而且症状往往是「超时」而不是「拒绝」，因为策略通常是静默丢包。折中的做法是先用「监控模式」观察一段时间（部分 CNI 支持只记录不拦截），把真实流量摸清楚再收紧。

策略生效后现象是超时，不是 connection refused。因为它丢包而不是回 RST。这意味着你在应用日志里看到的是「请求超时」，在两端抓包看到的是「请求发出去了，没有回应」。如果不知道有策略这层，很容易一路查到网卡和交换机上去。

面试怎么答：「NetworkPolicy 是 Pod 级的三层/四层策略，由 CNI 执行，kube-proxy 不参与。它的语义是：Pod 一旦在某个方向上被策略选中，那个方向就默认拒绝，只放行显式允许的。最常见的坑是 egress 忘了放行 DNS，导致服务看起来「网络不通」其实是解析不了。CNI 不支持时策略会被静默忽略，配置成功但没效果。」

模块 7

一次跨节点访问的完整路径，和四个抓包点

把一个包从客户端 Pod 到服务端 Pod 的每一跳写出来，你才能在「不通」的时候说出「它死在第几跳」。这条路径上有四次地址变化，每一次都对应一个可以抓包的位置。

客户端 Pod（10.244.1.7）访问 web.prod.svc.cluster.local:8080
│
├─ ① Pod 内 eth0：目的地址 = ClusterIP 10.96.23.11
│     查 DNS 得到 ClusterIP；包从 eth0 发出
│
├─ ② 节点 A 的 veth 端：包进入主机协议栈
│     PREROUTING 命中 KUBE-SERVICES → DNAT 成 Pod IP 10.244.2.9
│     conntrack 记下这条映射
│
├─ ③ 节点 A 的路由：10.244.2.0/24 在节点 B 上
│     VXLAN 模式：包进 vxlan0，加 50 字节封装，从物理网卡发出
│     BGP/host-gw 模式：直接改写下一跳为节点 B，不封装
│
├─ ④ 节点 B 的隧道口：解封装，得到原始包（目的 10.244.2.9）
│     路由到目标 Pod 的 veth，送进网络命名空间
│
└─ ⑤ 服务端 Pod eth0：收到目的 10.244.2.9:8080
      回程按 conntrack 反向改写，源地址变回 ClusterIP
抓包点看到什么地址能证明什么
Pod 内 eth0源 Pod IP → ClusterIP应用有没有真的发出请求；DNS 解析结果对不对
节点上的 veth同上，但已经是主机视角包有没有离开 Pod（排除应用层问题）
隧道设备 / 物理网卡外层 IP → 外层 IP（封装后）跨节点这一段通不通；有没有被 MTU 卡住
服务端 Pod eth0源 Pod IP → 服务端 Pod IPDNAT 有没有发生；请求到没到目标进程
# 1. 在 Pod 内抓（需要镜像里有 tcpdump，或用临时调试容器）
kubectl exec -it client-0 -- tcpdump -i eth0 -nn -c 20 'tcp port 8080'

# 2. 在节点上抓 veth 和隧道口，两边对照看封装前后
tcpdump -i any -nn -c 20 'host 10.244.1.7 and host 10.244.2.9'
tcpdump -i vxlan0 -nn -c 10
tcpdump -i eth0 -nn -c 10 'udp port 8472'   # Flannel VXLAN 默认端口，以你集群为准

# 3. 看内核怎么改的地址，以及有没有被丢
conntrack -L | grep 10.96.23.11
nstat -az | grep -E 'IpInDiscards|IpOutDiscards|TcpRetransSegs'
ip -s link show vxlan0

# 4. 按 MTU 逐步试，找到能通的最大尺寸
kubectl exec -it client-0 -- ping -M do -s 1400 -c 1 10.244.2.9
kubectl exec -it client-0 -- ping -M do -s 1450 -c 1 10.244.2.9
kubectl exec -it client-0 -- ping -M do -s 1472 -c 1 10.244.2.9

这张路径图最有用的地方，是它告诉你「ping 通」到底证明了什么。Pod 之间的 ping 通只证明三层可达，它不经过 ClusterIP 的 DNAT（ping 的是 Pod IP），也不证明端口在监听、不证明策略放行、不证明 MTU 够。所以「ping 得通但服务不通」不是矛盾，是必然——它们走的是不同的路径。

还有一个隐蔽的细节：在节点上抓包，看到的可能不是应用真正发出的包。GRO/GSO 会把多个小段在网卡层合并成大包，你在物理网卡上看到的是合并后的形态；容器里抓包看到的是 Pod 命名空间里的原始形态。算 MTU 的时候要分清你在哪一层看，否则会得出「应用在发 64K 的包」这种结论。

一个判断口诀：源 Pod 有出、目标 Pod 没进 → 问题在中间（路由、封装、策略）；目标 Pod 有进但没回应 → 问题在应用（没监听、处理慢）；两边都有但客户端报错 → 看回程和被谁改了地址。这三句话能覆盖大部分跨节点问题。

面试怎么答：「跨节点访问的路径是：Pod 发出到 ClusterIP → 节点上 DNAT 成 Pod IP → 按路由走隧道或直接路由 → 对端解封装 → 送到目标 Pod。抓包点有四个：Pod 内、节点 veth、隧道口、目标 Pod。判断方法是看出和进：只有出没有进就是中间层的问题，有进没回就是应用的问题。」

模块 8

排查顺序：从 Pod 里往外走，七步

网络排障最怕的是同时怀疑五个组件。固定一个从内往外的顺序，每一步只回答一个问题，答完再走下一步。这个顺序的好处是：任何一步失败，后面的全都不用查。

DNS 解析对了吗：从客户端 Pod 里 nslookup 服务名。解析不出来，后面全免谈；解析出来但地址不对，说明 Service 或 search 域的问题。
ClusterIP 通不通：wget -qO- --timeout=3 http://svc:port/。注意用 TCP 而不是 ping——ping ClusterIP 永远不通，这是设计。
Pod IP 通不通：把服务名换成某个后端 Pod IP 直接打。通了说明问题在 Service 层（规则、端口映射），不通说明在 CNI 或应用监听。
跨节点还通吗：找一个在别的节点的 Pod 做对照。只有跨节点不通，就往 MTU、隧道、路由和策略上查。
四层暴露对不对：NodePort 就从集群外打节点 IP，LoadBalancer 就看有没有外部地址、健康检查过没过。
七层路由对不对：带上 Host 头打 Ingress，看是 404（规则没匹配）、502（后端连不上）还是 504（后端太慢）。三个码指向三个地方。
出集群这一段：最后才查 NAT 网关、出网策略、对端白名单。这一段已经不属于 K8s 了，但很多「集群内好好的、调外部就超时」的问题出在这里。
卡在第几步大概率的问题第一条命令
第 1 步：解析不出CoreDNS、search 域、跨 ns 用了短名cat /etc/resolv.conf + nslookup 全名
第 2 步：ClusterIP 不通Endpoints 为空、targetPort 错、kube-proxy 规则没下发kubectl get endpointslice
第 3 步：Pod IP 不通应用没监听在那个端口、监听在 127.0.0.1、NetworkPolicykubectl exec -- ss -lntp
第 4 步：只有跨节点不通MTU、隧道、节点路由、安全组ping -M do 逐步试尺寸
第 5 步：NodePort 从外面不通安全组、externalTrafficPolicy Local、防火墙ss -lntp 在节点上看端口
第 6 步：Ingress 报错404 规则、502 后端、504 超时controller 日志里的 upstream
kubectl get endpointslice -l kubernetes.io/service-name=SVC有没有后端，一步切开「服务发现」和「网络转发」
kubectl exec -it POD -- cat /etc/resolv.confsearch 域和 ndots，解释绝大多数「偶尔慢几秒」
kubectl exec -it POD -- nslookup SVC.NS.svc.cluster.local用全名验证，排除短名和 search 域的干扰
iptables -t nat -L KUBE-SERVICES -n | grep VIPiptables 模式下确认规则真的存在
ipvsadm -Ln | grep -A3 VIPIPVS 模式下看虚拟服务和真实服务器列表
kubectl exec -it POD -- ping -M do -s 1450 PEER_IP带 DF 测 MTU，小包通大包不通就是它
kubectl get netpol -A确认有没有策略选中了目标 Pod（CNI 不支持则等于没有）
不要跳过第 1 步。「DNS 肯定没问题」是排障里最贵的假设。它便宜（一条 nslookup）、快（几百毫秒），而且能一次性排除 search 域、跨命名空间短名、CoreDNS 挂掉三种情况。跳过它，你可能会花四十分钟在 iptables 里找一个根本不存在的规则。

面试怎么答：「我从 Pod 里往外走：先 nslookup 确认解析，再打 ClusterIP，再打 Pod IP，再区分是不是只有跨节点不通，然后才是 NodePort、Ingress、出集群。每一步只回答一个问题，前一步不通就不看后面。这样做的好处是任何一次排查都能给出一个明确的结论，而不是『试了几个办法好像好了』。」

模块 9

10 个坑：每一个都能让你查错组件

网络这一块的坑有个共同特征：它们不报错。规则写错了、策略没生效、MTU 差了 50 字节，系统都安静地按错误的方式运行，只有业务在超时。

1
用 ping 测 ClusterIP
ClusterIP 是虚拟地址，只有配置了端口的规则，没有 ICMP 规则。ping 不通是正常的，通不通都不说明服务可用。要用 TCP 打端口。
2
以为有进程监听 ClusterIP
没有任何进程监听它，ss 里也看不到。真正干活的是内核里的 DNAT 规则，出问题要查规则和 conntrack，不是查进程。
3
把 kube-proxy 当负载均衡器
它只负责把 Service 翻译成规则，不转发任何数据。它挂了已有连接照常（规则还在内核），但新 Service 会完全不通，这个组合很容易误判。
4
跨节点不通就换 CNI
先测 MTU。小包通、大包不通，或者 TLS 握手卡住，十个里有八个是封装后 MTU 没配对，换插件是成本最高且无效的做法。
5
把 ndots:5 的延迟当成 CoreDNS 故障
访问外部域名时先拼三次 search 后缀，这是配置行为不是故障。写 FQDN 末尾加点就能验证：加了点变快，就说明是 search 放大。
6
写了 NetworkPolicy 就以为隔离生效
执行者是 CNI。Flannel 单独用不实现策略，YAML 会被接受但没有任何效果，也不报错。必须实测一次「本该被拒绝」的流量。
7
策略只写 ingress，忘了 egress 的 DNS
一旦 Pod 在 egress 方向被选中，默认拒绝一切出站，包括 53 端口。表现是「服务突然解析不了域名」，而网络、CoreDNS 都是好的。
8
用 externalTrafficPolicy: Local 却没考虑节点分布
本节点没有这个服务的 Pod 时，流量被丢弃而不是转到别处。副本少或有节点亲和时，会出现「部分节点通、部分节点不通」。
9
把 Headless 当负载均衡用
DNS 返回一组 Pod IP，选哪个是客户端的事，重试也是客户端的事。第一个地址挂了就报错，这种「随机失败」在 Service 上是不会出现的。
10
在节点上抓包就以为抓到了真相
容器有自己的命名空间，节点上看到的是 NAT 之后的地址；GRO/GSO 还会把包合并成你从没发过的大包。算 MTU 时在错误的层看，结论一定是错的。

面试怎么答：挑一条讲成因果链：现象、误判、验证方式、改法。比如「有次跨节点调接口，小请求正常，传文件就卡住。我一开始怀疑带宽，加监控发现带宽很低。后来带 DF 打 1450 的包不通，才发现是节点上新装的 CNI 没把 MTU 配成 1450。这个坑让我以后看到『握手成功但传数据卡住』先测 MTU。」

自测

六道题

1. 关于 Service 的 ClusterIP，下面哪个说法是对的？
正确答案：内核 DNAT 规则。kube-proxy 只负责把 Service 和 EndpointSlice 翻译成 iptables 或 IPVS 规则，真正改写地址的是内核。所以 ClusterIP 不在任何网卡上、ss 看不到监听、ping 也不通（没有对应的 ICMP 规则），只有配置过的协议和端口才有转发规则。
2. 一个 Pod 访问外部域名 api.example.com 经常慢几百毫秒到几秒，访问集群内 Service 很快。最可能的原因？
正确答案：ndots:5 的 search 放大。api.example.com 只有两个点，小于 ndots 的阈值，解析器会依次拼接 search 里的三个后缀去查，全部失败后才查原名，每次 NXDOMAIN 都是一次真实查询。集群内 Service 名本来就匹配 search 域，所以不受影响。验证方法是查 api.example.com.（末尾加点）对比耗时。
3. 一个 headless Service（clusterIP: None）后有三个 Ready 的 Pod，客户端查它的域名会得到什么？
正确答案：多个 A 记录。headless Service 不分配虚拟 IP，DNS 直接返回后端 Pod 的地址列表（就绪的才会返回）。所以负载均衡和失败重试的责任转移给了客户端，这是它和普通 Service 最大的区别。StatefulSet 用它主要是为了给每个成员一个稳定域名，而不是为了性能。
4. 你写了一条 NetworkPolicy，只允许 frontend 访问 api 的 8080，apply 成功。之后 api 报「解析不了数据库域名」。最可能的原因？
正确答案：egress 默认拒绝，没放行 DNS。NetworkPolicy 的语义是「被选中即默认拒绝该方向」，必须显式列出允许的流量。只写 ingress 规则时，如果 policyTypes 里包含 Egress（或写了 egress 段），出站就被限制，UDP/TCP 53 必须单独放行，通常指向 kube-system 的 DNS Pod。
5. Pod 之间 ping 通，但调用一个返回大 JSON 的接口时稳定卡住；换成小响应就正常。最可能的原因？
正确答案：MTU。ping 的包很小，能过；TCP 握手也小，能过；一开始传数据，满载的 1500 字节包超过隧道能承载的大小，如果中间又不回「需要分片」的 ICMP，发送方只能一直重传。验证方法是带 DF 标志逐步加大包长，找到恰好不通的尺寸，再和 `ip link` 里的 mtu 值对照。
6. Ingress 对象创建成功，但访问域名一直返回 404（响应来自 controller 的默认后端）。最先该确认什么？
正确答案：controller 与路由规则。404 来自 controller 的默认后端，说明请求到达了 controller 但没有任何规则匹配——可能是没有 controller、ingressClassName 不匹配、host 写错（含端口和大小写）、或者 pathType 与实际路径不符。后端不通会表现为 502，不是 404；DNS 有问题则根本到不了 controller。

术语一句话解释
CNI容器网络接口规范，运行时通过 ADD/DEL/CHECK 调用插件，负责给 Pod 配网卡、IP 和路由
Overlay在物理网络之上再封一层（VXLAN/IPIP），让 Pod 网段跨节点互通，代价是包头开销和 MTU 变小
VXLAN用 UDP 封装二层帧，包头约 50 字节，MTU 1500 时 Pod 侧通常只能用 1450
BGP 模式把 Pod 网段路由发布给物理网络，不封装、性能最好，但要求底层网络配合
ClusterIPService 的虚拟地址，只存在于转发规则里，没有进程监听，ping 不通是正常的
DNAT把包的目的地址改写，Service 转发就是靠它；只在首包发生，之后由 conntrack 记住
conntrack连接跟踪表，记录五元组和地址改写结果，回程靠它还原；表满会静默丢包
EndpointSliceService 的后端地址列表，由控制器按 selector 和 Ready 状态维护
NodePort在每个节点开一个高端口（默认 30000-32767）转发到 Service，对外暴露的最简单方式
externalTrafficPolicyCluster 会 SNAT、可跨节点转发；Local 保留源 IP，但本节点无后端时直接丢包
Headless ServiceclusterIP 为 None，DNS 直接返回 Pod IP 列表，负载均衡由客户端负责
Ingress / IngressClass七层路由声明与它的「由谁来执行」标记，必须配套 controller 才有意义
ndotsresolv.conf 里的阈值：名字里的点数小于它就先用 search 后缀试，默认 5 会放大外部域名查询
NetworkPolicyPod 级三层/四层策略，由 CNI 执行；被选中即该方向默认拒绝，需要显式放行
