Linux 命令追问：不只问你怎么用，还问你为什么

面试官问 awk 不是想看你背参数，是想知道你怎么处理一亿行日志。

覆盖 8 大模块 25 道命令题 10 个坑 10 连问 6 道自测
20:00
先问自己一句：你写的命令，换成一亿行日志还跑得动吗？
开始前

同一个问题，两种回答差一个职级

面试官在纸上写：「统计 Nginx 日志里访问量前十的 IP。」

初级候选人在白板上写 awk '{print $1}' access.log | sort | uniq -c | sort -rn | head，写完抬头等着。高级候选人写完同一行，会补三句：这个日志格式里第一列是不是真的是 IP、一亿行的时候瓶颈在 sort、如果日志有几十个 G 我会先切时间窗再算。

命令题的区分度全在那三句里。语法谁都能查，判断力查不到。这一篇按这个思路组织：每个模块先给「怎么写」，再给「什么时候这么写会出事」，最后收在面试话术上。

知道语法
能拼出正确的管道，但说不出每一段的开销。这一层只能证明你用过 Linux。
知道边界
知道 sort 会把数据落盘、uniq 依赖相邻、xargs 会被空格搞死。这一层说明你处理过真实数据。
知道替代
知道什么时候该换工具：一亿行用 awk 单遍流式，超大文件用 split + 并行，长期需求写成脚本而不是一行流。
这篇的读法：不要背参数。把每一节的「这一行在什么规模下会失效」记住就够了——面试官追问的几乎全是这一类。

面试落点：被要求「写一行命令」时，先问一句日志格式和量级，再动手。这个动作看起来是拖延，实际上是在告诉对方：你知道这条命令的边界在哪，而不是只会背语法。

模块 1

查找与筛选：find 比「ls 管道」快在哪

「怎么找出三天前修改过、大于 100M 的日志文件？」这题的重点不是参数，是你能不能说清两条路的成本差别。

# 常见但不够好的写法
ls -l /var/log | grep "\.log$"

# find：在目录树上直接做系统调用，不排序、不解析输出
find /var/log -xdev -type f -name '*.log' -mtime +2 -size +100M

# 找到就执行，批量传参（一个进程处理多个文件）
find /data -xdev -type f -name '*.log' -mtime +7 -exec gzip {} +

# 文件名可能含空格/换行时，用 -print0 + xargs -0
find /data -type f -print0 | xargs -0 rm -f

为什么 ls | grep 不行？三个层面：

  • 进程成本：管道要起两个进程，find 只有一个。文件数上百万时，多一次 fork 和一次全量输出不是小数目。
  • 解析成本：ls -l 为了排版会调用 stat 拿每个文件的元数据（权限、大小、时间、链接数），而你只需要名字。find 只在需要判断 -size / -mtime 时才 stat。
  • 正确性：ls 的输出是给人看的，文件名里有空格、换行、甚至颜色控制字符时，grep 拿到的根本不是文件名。这是「看起来能用，偶尔出错」的典型。
场景该用什么为什么
按名字/时间/大小找文件find遍历在文件系统层完成，条件在遍历时剪枝
在文件内容里找字符串grep -rfind + xargs grep 也行，但多一次进程编排
按名字找可执行文件which / command -v / type要考虑 PATH 和别名、内建命令，find 反而错
按内容查找（索引）locate / plocate走预建索引，代价是要维护数据库且可能过期
按文件内容里的字段筛awkgrep 只给「行」，awk 能直接算

几个容易漏的点：-xdev 防止跨文件系统（否则会翻进 /proc、NFS 挂载点，慢十倍）；-delete 比 -exec rm 少一次进程创建，但删之前先用 -print 确认；-mtime +2 是「修改时间在 2×24 小时之前」，按天粒度取整，不是精确的 48 小时。

面试落点：「按文件找我用 find，因为它不排序、不格式化，也不需要解析人类可读的输出；按内容找用 grep -r。两个都要注意一件事：文件名可能含空格，所以生产脚本里我会用 -print0 配 xargs -0。」

模块 2

三剑客：grep 找行、sed 改行、awk 算列

很多人背了三者的参数，却说不清「什么时候该用哪个」。一句话分工：grep 是筛，sed 是改，awk 是算。搞混了就会写出 200 字符的 sed 脚本去干 awk 的活。

工具核心能力擅长不擅长
grep按模式匹配行大文件里快速筛行；-c -l -o -v 计数与反选；配合 -P 用 PCRE按列计算、跨行处理
sed流式逐行编辑批量替换、按行号/地址删改、在配置里插行多列聚合、复杂条件分支
awk按字段处理 + 编程取列、条件过滤、分组统计、求和求均值、格式化输出极端复杂的文本结构（该上 Python）
# grep：只输出匹配的那一段，不要整行
grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' access.log | sort -u | wc -l
grep -c ' 500 ' access.log                 # 计数，比 wc -l 省一次管道
grep -rn --include='*.conf' 'worker_processes' /etc/nginx

# sed：改配置，先备份再改；-i.bak 是 GNU sed 的写法
sed -i.bak 's/^worker_processes.*/worker_processes auto;/' /etc/nginx/nginx.conf
sed -n '10,20p' file.txt                   # 只看 10~20 行
sed '/^#/d;/^$/d' file.conf                # 删注释和空行

# awk：按字段算，这是它真正的战场
awk -F: '$3 >= 1000 {print $1, $3}' /etc/passwd
awk '{sum += $10} END {printf "总流量 %.2f GB\n", sum/1024/1024/1024}' access.log
sed -i 不是所有平台都一样。GNU sed（Linux）用 -i 直接改，BSD/macOS 的 sed 要求 -i '' 给个后缀参数，同一个脚本换个系统就跑不了。跨平台脚本里我一般写 -i.bak，改完顺手留个备份，出事能回滚。

awk 有几个反直觉的地方，面试很爱问：

  • 字段默认按空白切分，连续空格算一个分隔符，而且会吞掉行首空白——所以用 $1 取第一列时不用担心缩进。
  • 默认输出用空格连接。你 print $1, $2 得到的是空格分隔，不是原来的制表符；要保留原样就改 OFS。
  • 比较是「看起来像数字就按数字比」。从文本里读出来的字段，如果形如数字会按数值比较，但混入空值或带单位（如 12ms）就退化成字符串比较，"9" > "10" 会成立。这是统计脚本出错的高频原因。
  • 数组天生是哈希，cnt[$1]++ 就是分组计数，不需要先排序——这一点让它比「sort | uniq -c」在超大文件上更省。

面试落点：「筛行用 grep，改文件用 sed，算列和聚合用 awk。三者都能做文本处理，但 grep 不理解列，sed 不擅长聚合，用 awk 去做纯替换反而绕。」

模块 3

一行命令实战：日志分析的四个套路

这一节是面试现场最常被要求「写一下」的部分。四个套路练熟，覆盖 80% 的日志分析题。

① Top 10 来源 IP

# 默认 combined 格式：$1 是客户端 IP，$7 是路径，$9 是状态码
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10

# 一行 awk 版本：内存里直接计数，省掉 sort 的外部排序
awk '{c[$1]++} END {for (ip in c) print c[ip], ip}' access.log | sort -rn | head -10

差别在哪？第一个版本让 sort 对全部 IP 做一次全排序——sort 在数据超过内存时会落盘做外部归并，几十 G 的日志会把磁盘打满、把 IO 打爆。第二个版本只在 awk 内部维护一个哈希表，内存占用是「不同 IP 的数量」而不是「行数」，一亿行、十万个 IP 也就几 MB。最后只对十万个键排序，成本可以忽略。

② 状态码分布

awk '{print $9}' access.log | sort | uniq -c | sort -rn
# 只看 5xx 的比例
awk '$9 ~ /^5/ {n++} {t++} END {printf "5xx: %d / %d = %.2f%%\n", n, t, n*100/t}' access.log

③ P99 的粗算（以及它为什么粗）

# 需要把耗时字段($NF)全部排序后取第 99% 位
awk '{print $NF}' access.log | sort -n | awk '{a[NR]=$1} END {print a[int(NR*0.99)+1]}'

# 内存友好版：分桶直方图，误差取决于桶宽
awk '{b=int($NF/10)*10; c[b]++} END {for (k in c) print k, c[k]}' access.log | sort -n
两个必须说出口的坑：① 精确分位数需要保留全部样本，内存随行数线性增长，一亿行必炸；② 线上更常见的做法是分桶直方图（Prometheus 的 Histogram 就是这么干的），代价是分位数只能落在桶边界上，桶宽决定误差。面试里能主动说出这个取舍，比写出精确命令更值钱。

④ 每秒请求数的时间序列

# 按分钟聚合，看流量曲线（$4 是 [21/Oct/2026:02:31:07 这种格式）
awk -F'[][]' '{split($2, t, ":"); print t[2]":"t[3]}' access.log | uniq -c

# 用 awk 分组统计更稳，不依赖日志本身有序
awk -F'[][]' '{split($2, t, ":"); c[t[2]":"t[3]]++} END {for (k in c) print k, c[k]}' access.log | sort

最后一个套路里有个细节值得注意：uniq -c 只能合并相邻的重复行，所以它假设日志是按时间有序的。真实日志在轮转、多进程写入时并不总是严格有序，这时候必须用 awk 的哈希分组。「为什么这里不能用 uniq」是个很好的加分回答。

面试落点：「我会先确认日志格式和字段位置，再决定用 awk 取列。数据量大的时候我会尽量让 awk 一步做完聚合，把 sort 留到最后只排结果的 key，因为 sort 是全量排序、可能落盘，这是整条管道真正的瓶颈。」

模块 4

权限：目录上的 rwx 和文件上的 rwx 不是一回事

「目录的 r 和 x 分别是什么？」这题答错的人不少，因为大部分人只记住了「r 读、w 写、x 执行」这套文件语义，然后直接套到目录上。

位对文件对目录
r读内容列出目录里的名字（ls），但看不到详情
w修改内容创建、删除、重命名目录里的条目
x执行进入目录（cd）、访问其中的条目（stat/打开文件）

所以「目录有 r 无 x」的效果很怪：ls 能列出文件名，但每个文件的详细信息全是问号，也打不开其中任何一个文件。能看见名字，进不去。反过来「有 x 无 r」，你进得去、能打开你知道名字的文件，但列不出目录里有什么。

最容易答错的一条：删除一个文件，看的是它所在目录的 w 和 x，不是文件自己的 w。所以 /tmp 里你可以删掉别人的文件——除非有粘滞位。这就是 /tmp 权限 1777 的原因：所有人都能写，但只有文件属主、目录属主和 root 能删。 
# 数字权限：r=4 w=2 x=1，三位分别是 属主/属组/其他
chmod 644 file      # rw-r--r--
chmod 755 dir       # rwxr-xr-x

# 特殊位：4=SUID，2=SGID，1=sticky（放在三位数字前面）
chmod 4755 /usr/bin/passwd   # SUID：以文件属主身份运行
chmod 2775 /data/share       # SGID（目录）：新建文件继承目录的属组
chmod 1777 /tmp              # sticky：只能删自己的

# umask：从默认权限里「减掉」的位。022 → 目录 755，文件 644
umask                       # 目录 777 & ~022 = 755；文件 666 & ~022 = 644

# ACL：需要给某个人单独授权时，别用 777
setfacl -m u:deploy:rwx /data/app
getfacl /data/app           # ls -l 里权限位后面出现 + 号就表示有 ACL
特殊位作用对象实际效果典型例子
SUID可执行文件运行时的有效用户变成文件属主/usr/bin/passwd 需要写 shadow
SGID文件运行时继承文件属组少见的场景
SGID目录目录里新建的文件继承该目录的属组团队共享目录
sticky目录只有属主/目录属主/root 能删条目/tmp、共享上传目录

一个容易踩的事实：Linux 上给 shell 脚本加 SUID 是无效的，内核会忽略。想让脚本以别的身份跑，得用 sudo 规则、capabilities 或者编译成二进制。这条在面试里说出来，能立刻区分「背过 chmod 4755」和「真试过」。

面试落点：「目录的 r 是列名字、x 是进入和访问、w 是增删条目。删除文件取决于目录的 w+x，所以 /tmp 才需要粘滞位。SUID 我只在必须提权的二进制上开，脚本上开了也没用。」

模块 5

进程与服务：ps 看快照，systemd 管生命周期

「服务起不来怎么查」是命令题里出现频率最高的一题。答得好不好，取决于你有没有一个固定顺序，而不是知道多少参数。

# 1. 先看服务本身的状态和最近日志，不要先去翻进程
systemctl status myapp --no-pager -l
journalctl -u myapp -n 100 --no-pager
journalctl -u myapp --since "10 min ago" -p warning

# 2. 进程在不在，谁起的，父进程是谁
ps -ef | grep -v grep | grep myapp
pgrep -af myapp             # -a 显示完整命令行，-f 匹配整条命令
ps -o pid,ppid,stat,etime,cmd -p 12345

# 3. 端口有没有真的监听（很多时候进程活着但绑错了地址）
ss -lntp | grep 8080

# 4. 改了 unit 文件必须先 reload，否则 systemd 还用旧配置
systemctl daemon-reload
systemctl restart myapp
Type=systemd 怎么判断「启动成功」踩坑点
simplefork 出进程就算成功进程起来就崩也会显示 active，必须配探针或看日志
forking父进程退出才算成功要配 PIDFile，否则 systemd 找不到主进程
notify程序自己发 sd_notify 才算成功应用不支持就是超时失败
oneshot进程退出且退出码为 0不能 restart，只能 RemainAfterExit

几个高频混淆点，建议直接背下来：

  • systemctl start 是本次启动，enable 是开机自启，两件事。enable --now 才是「既自启又立刻起」。
  • kill 默认发 SIGTERM（15），进程可以捕获并优雅退出；kill -9 是 SIGKILL，内核直接回收，进程没有任何机会清理。先 15，等几秒，再不退才 9。
  • ps aux 和 ps -ef 是两套风格（BSD / UNIX），字段名不同但信息基本一致。面试里被问「%CPU 是什么」要答：进程生命周期内的平均 CPU 占用，不是瞬时值——瞬时值要用 top。
  • pgrep -f 匹配整条命令行，容易误杀（比如匹配到自己的 grep 或 tail 命令）。生产上用 pkill -f 前先 pgrep -af 看一眼。
systemctl status app -l --no-pager状态、退出码、最近几行日志，一屏看完
journalctl -u app -f -n 50跟服务日志，比 tail 文件可靠（轮转后照样能看）
systemctl list-units --failed一次列出所有启动失败的服务，批量故障时先跑这个
systemctl daemon-reload改完 unit 文件必须执行，否则 restart 用的还是旧配置
pgrep -af app按整条命令行匹配，先确认再决定要不要 kill
别用 ps -ef | grep xxx | awk '{print $2}' | xargs kill -9 这种一行流。中间任何一环出错（grep 匹配到自己、awk 取错列、xargs 拿到空参数），后果都是杀掉不该杀的进程。要按名字杀就用 pkill，要按 pid 杀就先确认 pid 列表。

面试落点：「服务起不来，我先 systemctl status 看状态和退出码，再看 journalctl -u 的最近日志，然后确认进程和端口。改过 unit 文件必须先 daemon-reload——这一步漏了，你会对着旧配置查半天。」

模块 6

磁盘与文件：df、du、inode 与两种链接

这一节的题几乎必考，因为它同时考「知不知道」和「有没有被坑过」。

# df 看文件系统层面（已分配块），du 看目录树层面（实际占用）
df -h
df -i                       # inode 用量，满了也会报 No space left
du -x -h --max-depth=1 /var | sort -h | tail

# 硬链接：同一个 inode，链接数 +1，不能跨文件系统、不能链目录
ln /data/a.log /data/b.log
ls -li /data/a.log /data/b.log     # 第一列 inode 号相同，第三列链接数变成 2

# 软链接：独立 inode，存的是目标路径，可以跨文件系统、可以悬空
ln -s /data/a.log /data/current.log
ls -l /data/current.log            # 会看到 current.log -> /data/a.log
对比项硬链接软链接（符号链接）
inode与源文件相同独立 inode
跨文件系统不行可以
链接目录不行（普通用户）可以
删除源文件数据还在，链接仍可访问变成悬空链接（dangling），访问报 No such file
占用空间只多一个目录项多一个 inode 和一小段路径字符串

ln -s 有个经典坑：相对路径是相对于链接所在目录，不是相对于你执行命令的目录。在 /opt 下执行 ln -s logs/app.log /var/www/cur.log，链接指向的是 /var/www/logs/app.log，不是 /opt/logs/app.log。要指对就写绝对路径，或者写 ../opt/logs/app.log 这种相对目标。

还有两个「体积对不上」的原因值得记住：

  • 稀疏文件：ls -l 显示逻辑大小（可能几十 G），du 显示实际占用（可能几 M）。数据库预分配文件和容器镜像层里很常见。要按逻辑大小算加 --apparent-size。
  • 块对齐：一个 1 字节的文件通常占 4K 块。几十万个小文件时，du 会比「文件大小之和」大一个数量级，这也是 inode 和磁盘同时吃紧的原因。
df 满、du 不满的三种可能，按概率排序：① 文件被删但句柄没释放（lsof +L1）；② 有目录被挂载覆盖了（挂载点下面原来的文件仍然占空间，但 du 看不见）；③ 文件系统元数据或保留块占用（ext4 默认给 root 留 5%）。三种都要会，第一种最常见。

面试落点：「df 看的是文件系统分配出去的块，du 看的是目录树里还能遍历到的文件。两者不一致，最常见的原因是文件被删除但进程还握着 fd，用 lsof +L1 能直接看到。另外我会顺手 df -i 排除 inode 耗尽。」

模块 7

性能与追踪：四个工具的分工

这题常以「线上 CPU 100%，你怎么查」的形式出现。很多人一口气报八个工具名，但说不出先看哪个、每个回答什么问题。工具名不是答案，顺序才是。

工具回答什么问题注意
top整机视角：哪个进程在吃 CPU/内存，负载多少%CPU 是进程生命周期均值；按 1 可以展开每个核
iostat块设备视角：IO 有多忙、排队多长%util 对 SSD 会高估，配合 await 看
strace进程视角：卡在哪个系统调用，失败了几次ptrace 开销大，限时间、限调用范围
lsof资源视角：这个进程开了哪些文件、端口、socket全量 lsof 很慢，尽量带 -p 或 -i
perf函数视角：CPU 时间花在哪个符号上需要符号表；没有 frame pointer 时栈可能不全
# 从粗到细的一条链
top -b -n1 | head -20                       # 谁在吃
top -H -p 12345                             # 哪个线程在吃
pidstat -u -t -p 12345 1 5                  # 线程级采样，比 top -H 更好读
strace -c -p 12345                          # 是不是系统调用打爆了
perf top -p 12345                           # 用户态热点函数
perf record -F 99 -g -p 12345 -- sleep 30 && perf report   # 采样30秒，出火焰图数据

两个判断经验：用户态高（%us）说明在算——死循环、正则回溯、序列化、GC；内核态高（%sy）说明在跟内核打交道——系统调用太频繁、锁竞争、上下文切换、网络收发。这一刀切下去，方向基本就定了。

面试里最容易被扣分的一句话：「我用 strace 看一下」。因为它默认会被理解成「我要在生产核心进程上挂 ptrace」。正确说法是：「我会在低峰期、挑一台流量小的实例，用 timeout 限制 10 秒，并且只 trace 网络相关的调用，先判断是不是连接层面的问题。」

面试落点：「我先用 top 分出是用户态还是内核态，再落到线程，然后才上 strace 或 perf。顺序反了的话，你会拿着一堆系统调用去解释一个其实是算法复杂度的问题。」

模块 8

传输与远程：scp 够用，rsync 才是干活的那个

「怎么把 200G 的数据传到另一台机器，中途断了怎么办？」这题考的不是 scp 的语法，是你有没有做过真正的数据搬迁。

# scp：简单直接，但没有增量、不能续传、断了从头来
scp -r ./dist user@10.0.0.12:/data/www/
scp -P 2222 -i ~/.ssh/id_ed25519 file user@host:/tmp/   # 注意 -P 是大写

# rsync：只传差异，支持断点、删除同步、排除规则
rsync -avz --partial --progress ./data/ user@10.0.0.12:/data/
rsync -avz --delete --dry-run ./www/ user@10.0.0.12:/data/www/   # 先干跑！
rsync -avz -e "ssh -p 2222" --exclude='*.log' ./app/ user@host:/opt/app/

rsync 的核心是「差异算法」：它把源文件分块算弱校验和 + 强校验和，让对端先在已有文件里找匹配块，只传不一致的部分。所以传大文件的小改动时优势极大；传一堆全新文件时，它和 scp 差不多，甚至因为多算校验而略慢。这个区别很多人说不清。

需求用什么理由
传几个小文件scp一条命令，没有额外依赖
同步目录、要增量rsync -avz只传差异，可断点续传
镜像目录（删多余文件）rsync --delete必须配 --dry-run 先看要删什么
临时访问内网服务ssh -L本地端口转发，不用改防火墙
把内网服务暴露出去ssh -R反向转发，需要对方允许 GatewayPorts
当 socks 代理用ssh -D动态转发，浏览器配 socks5 即可
# 本地转发：访问本机 8080 等于访问远端能看到的 db:3306
ssh -N -f -L 8080:db.internal:3306 jump@10.0.0.12

# ~/.ssh/config 里固化下来，比每次敲一长串参数可靠
# Host db-tunnel
#   HostName 10.0.0.12
#   User jump
#   LocalForward 8080 db.internal:3306
#   ServerAliveInterval 30
#   ProxyJump bastion
rsync --delete 是这条线上最危险的参数。源目录写错（少一个斜杠、多一个空格）、或者源目录恰好是空的，它会忠实地把目标目录清空。生产上我固定三步：先 --dry-run 看输出、确认路径末尾斜杠的语义（src/ 是「目录里的内容」，src 是「目录本身」）、再真跑。

面试落点：「小文件用 scp，目录同步和大文件用 rsync，因为 rsync 只传差异块、支持断点。rsync 的 --delete 我会先 dry-run，路径末尾有没有斜杠语义完全不同，这个坑踩过一次就忘不了。」

模块 9

命令题 10 连问：每个都给一句能说出口的答案

下面 10 个问题在面试里出现频率极高，答案要短、要准、要带一句「为什么」。太长反而显得在背。

grep -c 和 wc -l 有什么区别？grep -c 数的是匹配行数，wc -l 数的是总行数。另外文件末尾没有换行符时，wc -l 会少算一行，grep -c 仍然算。
> 和 >> 的区别？前者截断覆盖，后者追加。要清空一个正在被写的日志，用 : > file（或 truncate -s 0），不要用 rm。
cmd > f 2>&1 和 cmd 2>&1 > f 差在哪？顺序决定重定向生效的时刻。前者先把 stdout 指向 f，再把 stderr 复制到 stdout 当前的目标，两个都进 f；后者先把 stderr 指向当时的终端，再把 stdout 指向 f，结果是 stderr 还在终端。
| 和 tee 的区别？管道把 stdout 交给下一个进程，屏幕上什么都看不到；tee 是「一份给下游、一份写文件（或终端）」，排查时用 cmd | tee out.log 能边看边存。
uniq 为什么必须先 sort？uniq 只合并相邻的重复行。不排序直接用，重复项分散在文件各处，一个都合并不掉。要全局去重就 sort -u。
xargs 最常见的坑？按空白切分参数，文件名带空格就被拆成两个。用 find ... -print0 | xargs -0；或者干脆用 -exec {} + 不经过 xargs。
find -exec {} \; 和 {} + 的区别？分号是每个文件起一次进程，加号是攒一批一次传进去。上万个文件时性能差一个数量级。
&& 和 ; 的区别？&& 是前一条成功（退出码 0）才执行后一条，; 是无条件顺序执行。脚本开头写 set -euo pipefail 能让错误尽早暴露，比到处写 && 可靠。
kill -9 和 kill -15 怎么选？15 是 TERM，进程能捕获、能关连接、能落盘；9 是 KILL，内核直接回收，进程没有任何机会清理。先 15，等几秒不退再 9。
nohup 和 systemd 的区别？nohup 只是忽略 SIGHUP 并把输出重定向，进程挂了不会重启、开机不会自启；systemd 管生命周期、重启策略、日志收集、资源限制。生产上长期跑的东西应该交给 systemd 或容器编排。
用法建议：把这 10 条各写成一行贴在显示器旁边，面试前一天只读这个。它们覆盖了「命令细节」类问题的绝大多数，而且每条都带一个「为什么」，被追问也不会哑。

面试落点：这 10 问没有统一话术，但有个共同结构——先给结论，再给一句机制。比如「uniq 只合并相邻行，所以必须先 sort」，一句话就把用法和原理都说完了。

模块 10

10 个坑：每一条都在生产上出过事

命令题扣分往往不在「不会」，而在「会用但用错场景」。下面这些，面试官问「你踩过什么坑」时可以直接拿去讲。

1
用 ls | grep 找文件
ls 为了排版会 stat 每个文件，输出还是给人看的格式。文件名带空格或换行时结果直接是错的。用 find。
2
uniq 不排序直接用
它只合并相邻重复行。日志不是严格有序时，你会得到一堆「看起来去过重」其实没去的输出，还很难发现。
3
xargs 不处理空格和换行
默认按空白切分，一个带空格的文件名会变成两个参数，轻则报错重则删错文件。用 -0 配 -print0。
4
重定向顺序写反
2>&1 > f 会让 stderr 留在终端、stdout 进文件。写反了还自认为「日志都收集了」，排障时才发现少了最关键的那几行。
5
用 > 去「清空」正在写的日志
很多程序的 fd 有偏移量，截断后继续写会在文件里留一段空洞（看起来是磁盘占用比内容大）。优先让进程 reopen 或用日志轮转工具。
6
kill -9 当第一选择
进程没机会关连接、刷缓冲、释放锁。数据库类进程被 -9 之后可能需要恢复，缓存类进程会丢数据。
7
以为目录有 r 就能读里面的文件
缺 x 时连 stat 都失败，ls -l 全是问号。这是「权限看着对但就是打不开」的典型原因。
8
用 chmod 777 解决权限问题
它同时打开了写和执行，等于把问题从「打不开」换成「谁都能改」。真需要跨用户授权就用 ACL 或改属组。
9
rsync --delete 不 dry-run
源路径少写一个斜杠，语义就从「同步内容」变成「同步目录本身」，目标目录可能被清空。这类事故恢复代价极高。
10
在脚本里裸写 rm -rf $DIR
变量为空时命令变成 rm -rf，在错误目录下执行就是灾难。脚本开头 set -u，删除前判断目录非空，或者用 ${DIR:?} 强制要求变量有值。

面试落点：这 10 条里挑一条讲，讲法固定三段：当时的错误判断、造成的结果、后来改成了什么。第三段最重要——只说「踩过坑」不说明你改了习惯，面试官会认为你还会再踩一次。

自测

六道题

1. sort | uniq -c 里，为什么 uniq 前面必须先 sort？
正确答案：uniq 只处理相邻重复。uniq 的算法是「记住上一行，和当前行比」，所以它天然依赖输入有序。不排序时，同一个值出现在不同位置就会各算一次，看起来去重了其实没有。
2. cmd 2>&1 > out.log 的实际效果是？
正确答案：stderr 留在终端，stdout 进文件。重定向从左到右生效：先把 stderr 复制成「当前 stdout 的目标」（也就是终端），再把 stdout 改指到 out.log。想两个都进文件，必须写成 cmd > out.log 2>&1。
3. 一个目录权限是 dr--r--r--（只有 r，没有 x），普通用户能看到什么？
正确答案：能看名字，进不去。目录的 r 允许读取目录项列表，x 才允许穿越目录、对条目做 stat 或打开。缺 x 时 ls -l 会显示一堆问号，任何文件都打不开。
4. 用户 A 对 /data/report.csv 没有写权限，但对 /data 目录有 w 和 x。他能删除这个文件吗？
正确答案：能删。删除 / 重命名本质是修改父目录的目录项，只需要目录的 w + x。这正是 /tmp 需要粘滞位（1777）的原因：否则任何人都能删别人的临时文件。
5. 要把一个 200G 的目录同步到另一台机器，中途可能断线，最合适的做法是？
正确答案：rsync。它按块比对只传差异，断线后重跑会跳过已传部分。scp 没有增量也没有续传，断了就得从头来；tar + scp 虽然只传一个流，但同样不能续传，而且必须先有足够的临时空间。
6. find /data -name '*.log' -exec gzip {} \; 和把 \; 换成 + 有什么区别？
正确答案：批量和逐个的差别。分号结尾时 find 对每个匹配文件执行一次命令，上万个文件就是上万次 fork+exec；加号结尾时 find 会攒够一批参数再执行一次。两者都是串行执行，+ 快是因为进程创建少了。

术语表与下一步

术语一句话解释
管道把前一个进程的 stdout 接到后一个进程的 stdin，内核用管道缓冲区传递
重定向改变 fd 指向，顺序从左到右生效，2>&1 的位置决定结果
外部排序sort 在数据超过内存时落盘做归并，是日志分析管道里最常见的瓶颈
流式处理一次读一行、常量内存，awk 和 grep 都是这种模型
哈希聚合awk 数组天然是字典，c[$1]++ 就是分组计数，内存与「键的数量」成正比
umask创建文件时从默认权限里减掉的位，常见 022 得到 644/755
SUID / SGID运行时切换有效用户 / 有效属组；SGID 用在目录上是让新文件继承属组
粘滞位目录上的特殊位，限制只能删除自己的条目，/tmp 用它
ACL在传统 rwx 之外给单个用户或组授权，ls 权限位末尾的 + 表示存在 ACL
inode文件的元数据节点，硬链接共享同一个 inode，软链接有独立 inode
稀疏文件逻辑大小远大于实际占用，ls 与 du 的差异来源之一
dry-run只打印将要执行的动作而不真的执行，rsync / find -delete 前必做
set -euo pipefail脚本三件套：出错即停、未定义变量报错、管道中任一环失败即失败
