开始前

三个现场：配置都写了，效果都没有

「压测能扛 3000 QPS，大促 0 点还是挂了。」「熔断器上线半年，一次没触发过。」「降级开关一按，前端白屏，客服电话被打爆。」这三个人都在做正确的事，但三个人都漏了同一类东西：他们只写了阈值，没想清楚触发之后会发生什么。

现场直觉答案真实原因
压测 3000 QPS 通过，线上 1500 就雪崩压测数据造假，或者线上机器更差压测没有下游：真实链路里每个请求还要调三四个依赖，依赖一慢，线程池被占满，QPS 上限直接掉一个数量级。你压的是自己的 CPU，不是整条链路
熔断器从来没打开过系统太稳定了，好事统计窗口里没攒够最小请求数，或者异常在框架层被包装成了返回 200 的业务错误码，错误率算出来永远是 0
降级一开，用户以为数据丢了用户太敏感降级返回了空数组，前端渲染成「暂无数据」，而正常时有数据。降级的返回结构要和正常一致，并且要带「这是旧数据」的标记
限流看的是速率
它只回答「这一刻允不允许你进来」，不回答「进来之后快不快」。放进来但处理不完，等于把队列堆在应用里。
熔断看的是结果
它不关心你多快，只关心「最近这批请求里失败或慢的比例」。所以它天然滞后，是一个事后止损的机制。
降级是业务决策
它不是技术开关，是「资源不够时先放弃哪部分功能」的产品决定。这件事必须和产品一起定，不能运维一个人拍。

这一篇的顺序是：先把三种手段的边界划清（很多人答错就错在把它们当成互相替代的），再拆限流——四种算法的取舍、单机与分布式的代价，然后是熔断的三态、降级的形态，最后落在隔离、超时预算和重试放大这三件「不做就会把限流熔断全部作废」的事上。

先记住一句话：限流保护自己不被压垮，熔断保护自己不被下游拖死，降级保证核心业务还能喘气。三者之间没有替代关系——限流挡不住「下游慢导致线程池被占满」，熔断也挡不住「自己被瞬时流量打爆」。

面试怎么答：「这三个词经常被并列着问，但它们保护的对象不一样。限流是入口的闸门，前提是下游还活着；熔断是出口的保险丝，前提是下游已经不行了；降级是业务取舍，前提是资源不够、必须放弃一部分。另外还有两件底层的事：超时和隔离，没有这两样，前面三个配了也白配。」

模块 1

三种手段的分工：保护对象不同，别互相替代

判断一个人是不是真做过稳定性，有个很简单的方法：问他「限流和熔断能不能只留一个」。答「能」的，基本是背的；答「不能，它们管的不是同一件事」的，是踩过坑的。

手段保护谁触发条件触发后的行为怎么恢复
限流自己（以及身后的下游）单位时间内的请求数或并发数超过阈值拒绝（429 / 503）、排队、或降级处理速率回落到阈值以下就自动恢复，没有状态
熔断调用方自己一段时间内失败率或慢调用比例超过阈值，且样本足够直接快速失败，不再发起真实调用必须经过半开探测，成功才恢复
降级核心业务依赖不可用、容量不足，或人工开关走兜底逻辑：缓存、默认值、关闭非核心功能人工回切，或依赖恢复后自动回切
隔离其他调用方不需要触发，是常驻的资源划分把故障限制在一个池子/一个依赖内不涉及恢复，是预防
超时自己的线程和连接调用耗时超过设定值中断调用、释放资源、抛异常不涉及恢复，是止损

为什么限流挡不住下游变慢？算一笔账就清楚了。一个服务 200 个工作线程，正常下游 P99 是 20 毫秒，理论上限是 200 ÷ 0.02 = 10000 QPS。下游突然变成 2 秒，理论上限立刻变成 100 QPS——吞吐掉了两个数量级，但你一个请求都没拒绝。限流的阈值还写着 3000，它会老老实实把 3000 QPS 放进来，然后线程池排满、队列堆积、所有请求一起超时。这时候唯一有用的动作是「拒绝掉 2900 个」，而这需要限流阈值跟着 RT 变，或者干脆用并发数限流而不是 QPS 限流。

反过来，熔断也挡不住瞬时流量。熔断的统计窗口通常是秒级甚至十秒级，而秒杀的开场冲击是毫秒级的。等它统计出「错误率 80%」的时候，线程池早就满了。所以入口的瞬时保护只能靠限流（尤其是并发数或信号量这类不依赖时间窗口的），熔断负责的是「持续性的下游故障」。

先有超时：任何一个跨进程调用都必须有超时，且要有连接超时和读超时两个。没超时的调用等于把线程永久借给了对方。
再做隔离：每个依赖独立的线程池或连接池，让「一个依赖挂了」最多影响它自己那部分容量。
然后限流：入口按 QPS 或并发数设闸门，按接口分，不要全局一个阈值。
然后熔断：对每个外部依赖配熔断，让「已经确定不行」的调用尽快失败，把资源让出来。
最后降级：为每个核心接口准备一个「最差也能返回什么」的答案，这是熔断打开之后要走的路径。
只配限流不配超时，等于没配。因为限流按 QPS 算，而 QPS 是「进来多少」，不是「处理完多少」。请求进来后卡在下游，QPS 指标看着完全正常，线程池却已经满了。真正能反映「我快撑不住了」的指标是在途请求数和排队长度，这两个才应该进你的告警。

面试怎么答：「它们保护的对象不同。限流保护自己不被流量打爆，是按入口速率算的；熔断保护自己不被下游拖死，是按调用结果算的，必须有半开探测才能恢复；降级是业务上放弃一部分功能保核心。这三件事不能互相替代，因为限流挡不住下游变慢，熔断也挡不住毫秒级的瞬时冲击。真正的基础是超时和隔离。」

模块 2

窗口类算法：固定窗口的问题不是「不准」，是「准得离谱」

先说实话：固定窗口计数器在所有场景里都是最简单的一种，也几乎是最容易出事的一种。它的问题不在平均精度，而在边界那一瞬间——一个「每分钟 100 次」的限制，可以在两秒内放过 200 次。

怎么发生的？窗口是 [00:00, 01:00) 和 [01:00, 02:00)。客户端在 00:59.5 到 00:59.9 之间打 100 个请求，全部通过（第一窗口还有额度）；到 01:00.1 再打 100 个，也全部通过（新窗口额度重置）。两秒内 200 个请求，是限额的两倍。这就是所谓的临界问题，压在窗口边界上的流量会被放大一倍。

滑动窗口日志是最直接的修法：把每个请求的时间戳都记下来，每次请求时删掉窗口外的，数一下剩下的。它精确，没有近似，但代价是内存随限额线性增长——限额 10 万 QPS 的话，你要在一个进程里存 10 万个时间戳。所以它只适合「限额很小、精度要求高」的场景，比如「每个用户每分钟 5 次验证码」。

滑动窗口计数是工程上最常用的折中：把一个窗口切成 N 个小格（比如 1 分钟切成 6 个 10 秒的格），每次只统计「当前格 + 前面若干格」，并对上一整个窗口的计数按时间比例加权。它用一个估算值代替精确值：

# 滑动窗口计数的估算公式（当前窗口只过了一半，上一窗口就按一半权重算）
估算值 = 本窗口已计数 + 上一窗口计数 × (1 - 本窗口已过时间 / 窗口长度)

# 例：窗口 60 秒，切成 6 格（每格 10 秒），限额 100
# 当前在第 3 格（已过 25 秒），本窗口已计 40，上一窗口计 80
# 估算 = 40 + 80 × (1 - 25/60) = 40 + 46.7 = 86.7  → 还剩 13 个额度

# 格子越细，越接近真实滑动窗口；代价是每次请求要读多个格子

误差上限大概是「一个格子」的量级：极端情况下，真实的滑动窗口会认为某些请求已经过期，而分格估算还把它们算在内，于是偏保守（少放一点）；反过来也会有偏宽松的时刻。工程上没人纠结这个误差，因为格子可以切到 10 个以上，误差就在 10% 以内。

实现怎么算精度内存适合
固定窗口一个计数器 + 过期时间边界可放大到 2 倍O(1)按天/按小时的配额（如每日调用次数），边界问题影响小
滑动窗口日志存每个请求的时间戳精确O(限额)小限额、高精度，如短信验证码、登录失败次数
滑动窗口计数分格 + 上一窗口加权误差约一格O(格数)绝大多数在线限流，Sentinel 的默认统计就是这类
# 固定窗口：Redis INCR + EXPIRE，两行搞定，但有临界问题
local n = redis.call('INCR', KEYS[1])
if n == 1 then redis.call('PEXPIRE', KEYS[1], ARGV[1]) end
if n > tonumber(ARGV[2]) then return 0 else return 1 end

# 滑动窗口日志：ZSET 存时间戳，精确但要清理
local now = tonumber(ARGV[1])
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - tonumber(ARGV[2]))
local n = redis.call('ZCARD', KEYS[1])
if n < tonumber(ARGV[3]) then
  redis.call('ZADD', KEYS[1], now, ARGV[4])   # ARGV[4] 用 时间戳+随机数 保证 member 唯一
  redis.call('PEXPIRE', KEYS[1], tonumber(ARGV[2]))
  return 1
end
return 0

这两个脚本有个共同的坑：EXPIRE 只应该在第一次创建 key 时设。上面固定窗口的写法用了 if n == 1 来保证这一点；如果每次请求都刷新过期时间，这个 key 就永远不会过期，窗口会一直往后滑，最后限额形同虚设。这是线上排查「限流没生效」时最常见的代码级原因。

为什么面试官爱问临界问题：因为它能区分「背过四种算法」和「想过边界」。标准答法是：固定窗口在窗口边界会允许最多两倍限额通过；修法有两种，一是滑动窗口（日志精确、计数近似），二是改用令牌桶，因为令牌桶的额度是连续补充的，不存在「整点重置」这个动作。

面试怎么答：「固定窗口的问题是临界问题：一分钟 100 次的限制，在 59 秒和 01 秒各打 100 个，两秒内就过了 200 个。修法一是滑动窗口，日志版精确但内存和限额成正比，计数版分格加权，误差在一个格子以内；修法二是换成令牌桶，它的额度是匀速补的，没有重置边界。」

模块 3

令牌桶与漏桶：一个允许突发，一个消灭突发

这两个桶被讲混的概率极高。区别只有一句话：令牌桶允许突发（上限是桶容量），漏桶把突发摊平或丢弃（输出恒定）。所有的参数、实现、适用场景，都是从这一句推出来的。

令牌桶的工作方式：系统以固定速率 r 往桶里放令牌，桶最多装 b 个，多了就溢出丢掉。每个请求要先取一个令牌，取不到就拒绝或等待。关键在「桶可以攒」：如果一段时间没流量，桶会攒满 b 个令牌，下一个瞬间就能一次性通过 b 个请求。所以它的语义是「长期平均不超过 r，但允许最多 b 个的瞬时突发」。

漏桶的工作方式：请求先进桶（桶容量就是允许排队的长度），然后以恒定速率流出。桶满了就拒绝。注意这里没有「攒」的概念——漏桶不攒额度，它攒的是「待处理的请求」，输出的节奏永远是均匀的。这就是它能做流量整形（traffic shaping）的原因：把上游忽快忽慢的流量，变成下游能稳定消化的匀速流。

维度令牌桶漏桶
输出速率平均 r，瞬时可达 b恒定 r，任何时刻都不超过
突发允许，上限是桶容量 b不允许，突发只会被排队或丢弃
空闲后的行为攒满令牌，下次可突发不攒，空闲期直接浪费
典型实现Guava RateLimiter（SmoothBursty 默认最多攒 1 秒的令牌）、Sentinel 的 Warm Up、大多数 SDKnginx 的 limit_req、Sentinel 的「匀速排队」、网络设备的流量整形
适合在线 API：平时平稳，允许短促高峰（比如页面加载并发几个请求）保护下游：下游处理能力恒定（比如老系统、第三方接口、消息投递）
# 令牌桶：nginx 没有直接的令牌桶，limit_req 是漏桶模型
# rate=200r/s 是流出速率，burst=50 是桶容量（排队长度），nodelay 表示突发不延迟
limit_req_zone $binary_remote_addr zone=api:10m rate=200r/s;

server {
    location /api/ {
        limit_req zone=api burst=50 nodelay;
        # 超过 burst 的直接 503；不写 nodelay 则会按 rate 匀速放行，延迟会累积
        limit_req_status 429;
    }
}

# 令牌桶：Guava，一行创建，acquire 阻塞等待，tryAcquire 立即失败
RateLimiter limiter = RateLimiter.create(500);   # 500 令牌/秒
if (!limiter.tryAcquire()) { return tooManyRequests(); }

# 并发的限制不要用 QPS 桶硬凑，用信号量更准（它限的是"同时处理中"的数量）
Semaphore inflight = new Semaphore(200);

为什么说「burst 设太大等于没限流」？假设你限制 200 QPS，burst 设成 2000。平时没流量，桶攒满 2000 个令牌。大促开场第一秒，2000 个请求全部放行——这一秒的实际速率是 2000 QPS，是限额的 10 倍，下游直接被这一秒打挂。桶容量决定的是「你能承受多大的瞬时冲击」，它必须按下游的瞬时承受能力来定，不是「越大越宽松越好」。经验上 burst 取 rate 的 1 到 5 倍（也就是允许 1 到 5 秒的额度攒起来），超过这个量级基本等于给攻击者留了一个放大器。

反过来说，漏桶也不是万能的。它的「恒定输出」在客户端看来就是延迟：请求没被拒绝，但排队排了很久，最后超时了。所以用漏桶时一定要同时设「最大排队时间」，否则你会得到一批「成功了但客户端早就不等了」的请求——这些请求白占了下游资源，还制造了虚假的成功率。

一个必须说清的事实：令牌桶不限制并发，漏桶也不限制并发。它们限的都是「速率」。如果下游的瓶颈是并发（比如数据库连接池只有 50 个），你限 QPS 是没用的——50 个连接上一个慢查询就能把整个池子占满，而此时 QPS 可能远低于阈值。并发要用信号量或连接池上限来限，这是两个维度。

面试怎么答：「令牌桶按固定速率往桶里放令牌，桶能攒，所以允许突发，突发上限就是桶容量；漏桶是请求进桶、恒定速率流出，输出永远均匀，突发只能排队或丢弃。需要允许短促高峰的用令牌桶，需要保护恒定处理能力的下游用漏桶。两个都只限速率不限并发，并发要靠信号量。burst 设成速率的十倍，等于把限流变成了突发放大器。」

模块 4

分布式限流：扩容那一刻，你的单机阈值就失效了

单机限流有个隐藏的前提：副本数不变。4 个副本、每个限 500 QPS，集群总限额是 2000；某天扩容到 8 个副本，总限额自动变成 4000，而下游一点没变强。你什么都没改，保护却打了对折。

这个算术问题在两种情况下会立刻暴露：一是弹性扩缩容（HPA 把副本从 4 拉到 20，限额翻了 5 倍）；二是流量倾斜（网关的负载均衡不均是常态，热点副本先把本地额度用完，其他副本还闲着，整体利用率可能只有 50%）。所以「集群总量」这个概念，单机限流是表达不了的。

分布式限流的主流做法是「一个中心化的计数器 + 原子操作」。Redis 是最常见的选择，因为 INCR 是原子的，而复杂逻辑（令牌桶）要保证「读-算-写」三步原子，就必须用 Lua 脚本——Redis 执行 Lua 期间不会插入其他命令，这是它唯一的原子性保证方式。

# 分布式令牌桶：KEYS[1]=key, ARGV=速率, 容量, 当前时间ms, 需要令牌数
# 注意用 Redis 的 TIME 而不是客户端时间，避免多机时钟漂移
local t = redis.call('TIME')
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
local r  = tonumber(ARGV[1])
local b  = tonumber(ARGV[2])
local need = tonumber(ARGV[4])

local v = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(v[1]) or b
local ts     = tonumber(v[2]) or now

local delta = math.max(0, now - ts) / 1000
tokens = math.min(b, tokens + delta * r)

if tokens >= need then
  tokens = tokens - need
  redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
  redis.call('PEXPIRE', KEYS[1], math.ceil(b / r * 1000) + 1000)
  return 1
end

redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', now)
return 0

这段脚本能跑，但它有四个代价，面试里能把这四个说全，比会写脚本更有说服力：

代价具体是什么怎么缓解
多一次网络往返每个请求都要问一次 Redis，同机房 0.5 到 1 毫秒，跨机房几毫秒。对 P99 只有 20 毫秒的接口，这是实打实的开销本地批量领令牌：一次领 100 个，用完再领。RTT 摊薄 100 倍，代价是限额会超发（最多 副本数 × 批量）
Redis 单线程Lua 脚本在执行期间阻塞所有其他命令，脚本越复杂、key 越热，影响越大脚本保持短小；避免在大 key 上做 ZSET 范围删除（滑动窗口日志那套）
热点 key全局限流就是一个 key，QPS 上万时这个 key 所在的分片就是瓶颈，且无法靠加节点解决按「接口 + 用户段」拆 key，或者分层：全局限额用粗粒度、用户级用细粒度
可用性依赖Redis 挂了，限流器就挂了。这时候是放行还是拒绝？本地兜底：Redis 超时（比如 10 毫秒）就退化成单机限流，别让限流器自己变成故障源

第四点值得单独说，因为它是设计上的一个真取舍。fail-open（限流器不可用就全放行）保住业务，但失去了保护，如果此时正好有攻击或流量高峰，等于裸奔；fail-closed（全拒绝）保住保护，但把「限流器抖动」直接升级成「全站 5xx」。生产上通常选第三种：降级到单机限流——既不是全放，也不是全拒，而是退回到「每个副本自己管自己」的粗略保护。这个选择要在设计文档里写清楚，不要等故障时才争。

还有一条路是「网关集中限流」：所有流量本来就经过网关，在网关做一次全局限流，应用侧不用再管。它的好处是链路短、没有额外 RTT；坏处是只保护入口，服务之间的内部调用（A 调 B）绕不过网关，所以内部依赖的限流还是得在应用侧做。边车模式（Envoy 的 local rate limit + 全局 gRPC 限流服务）是这两种思路的结合，代价是运维复杂度。

时钟问题比你想的更常见。用客户端时间算令牌补充量，多台机器之间差几百毫秒是常事，更别说容器漂移后的时间跳变。后果是「令牌凭空多出来」或「一段时间不放令牌」。所以脚本里取时间要用 Redis 服务端的 TIME，这是唯一一个所有实例都认同的时钟。

面试怎么答：「单机限流的问题是总量随副本数变，扩容就失效，而且流量倾斜会让整体利用率很低。分布式限流用 Redis 加 Lua 保证原子性，代价是每个请求多一次 RTT、Lua 阻塞单线程、全局限额是个热点 key、还多了一个可用性依赖。缓解办法是本地批量领令牌摊薄 RTT，Redis 不可用时降级成单机限流而不是全放或全拒。时间要用 Redis 的 TIME，避免多机时钟不一致。」

模块 5

熔断三态：半开只放一个请求，不是放一批

熔断器最容易犯的错不是「阈值配错」，是「配了但永远不会触发」。第二容易犯的错，是把半开状态当成「恢复」，一次性把流量全放回去——那等于给刚出 ICU 的下游做一次压力测试。

状态机（三个状态，两条边由「统计结果」触发）

       失败率/慢调用率 ≥ 阈值，且样本数 ≥ 最小值
  ┌──────────────────────────────────────────┐
  │                                          ▼
[closed]  ────────────────────────────────> [open]
  ▲  正常放行全部请求                         │ 直接快速失败，不发起真实调用
  │                                          │ 持续 waitDurationInOpenState
  │  半开期探测全部成功                        ▼
  └────────────────────────────────────── [half-open]
                                             │ 只放 permittedNumberOfCalls 个探测请求
                                             │ 任一失败 ──> 回到 open，重新计时
                                             └──────────────

三个状态各自的语义要能一句话说清：closed 是正常态，所有请求都真的发出去，同时统计结果；open 是熔断态，请求不发出去了，直接抛异常或走降级，这一步的价值是「立刻把线程和连接还回来」；half-open 是探测态，放少量请求试探下游是否恢复，成功则 closed，失败则立刻回 open 并重新计时。

「重新计时」这四个字很关键。如果探测失败后不重置计时器，那么半开状态会一直循环探测，下游会被持续骚扰，等于熔断没生效。这是实现层面的细节，但面试里说出来会显得你真的读过源码或者踩过。

参数作用配错的后果
统计窗口（slidingWindowSize）用多少个请求或多长时间来算失败率太小：抖动就熔断；太大：故障了还迟迟不熔断
最小请求数（minimumNumberOfCalls）样本不足时不做判断不设或设成 1：凌晨一个请求失败就是 100% 失败率，天天误熔断
失败率阈值超过多少比例打开熔断设 90%：下游已经半死但还在拖着你，等于没配
慢调用阈值RT 超过多少算「慢」，慢请求占比多高算故障不配：下游不报错但变慢，熔断永远不触发，线程池照样被拖死
open 持续时间熔断后多久进入半开太短：下游还没恢复就反复探测；太长：恢复了也白等
半开允许请求数探测期放几个请求设成「全部」：恢复瞬间把下游二次打挂
# Resilience4j：按「实例名 = 依赖名」配置，注意慢调用也要算进去
resilience4j.circuitbreaker.instances.inventory:
  slidingWindowType: COUNT_BASED
  slidingWindowSize: 50
  minimumNumberOfCalls: 20
  failureRateThreshold: 50
  slowCallDurationThreshold: 800ms
  slowCallRateThreshold: 60
  waitDurationInOpenState: 10s
  permittedNumberOfCallsInHalfOpenState: 3
  automaticTransitionFromOpenToHalfOpenEnabled: true

# Sentinel：熔断规则有三种维度，timeWindow 单位是秒
# grade: 0=慢调用比例 1=异常比例 2=异常数
# slowRatioThreshold 只在 grade=0 时有意义；minRequestAmount 是样本下限
[{ "resource": "getInventory", "grade": 2, "count": 20,
   "timeWindow": 10, "minRequestAmount": 20, "statIntervalMs": 10000 }]

为什么必须配「慢调用」这一维？因为最典型的故障形态不是「下游报错」，而是「下游变慢」。报错是显性的，错误率会立刻上去；变慢是隐性的，错误率是 0，但每个请求占着线程 2 秒。而熔断器如果只看错误率，就会认为「一切正常」，眼睁睁看着线程池被占满。所以判断「这个依赖是不是不行了」，要看两个维度：失败的比例和慢的比例。

还有一个粒度问题：熔断器要按「依赖 + 接口」隔离，不要全局一个。如果 A 服务调用库存和调用优惠券共用一个熔断器，库存挂了会把优惠券也熔断，然后你发现「明明优惠券是好的，为什么也没了」——这叫误伤，是熔断配置里最难查的一类问题，因为日志里只有「circuit open」，看不出是谁拖累了谁。

一套能直接用的初始值：统计窗口 50 个请求（COUNT_BASED，比时间窗口在高 QPS 下更稳），最小请求数 20，失败率 50%，慢调用阈值取 P99 的 2 倍，慢调用比例 60%，open 持续 10 秒，半开放 3 个请求。这套值的逻辑是「宁可晚一点熔断，也不要天天误熔断」——误熔断的代价是所有请求都走降级，用户立刻能感知。

面试怎么答：「熔断有三个状态。closed 正常放行并统计，失败率或慢调用比例超过阈值、且样本数够，就进 open，直接快速失败不发起调用；open 持续一段时间后进 half-open，只放少量探测请求，成功就回 closed，失败就回 open 并重新计时。两个关键点：一要有最小请求数，否则低流量时会误熔断；二要统计慢调用，因为下游变慢时错误率是 0，只看错误率永远不会触发。」

模块 6

降级：最怕的不是功能没了，是用户以为数据没了

「降级返回空列表」这个决定，在技术上是合理的（防止服务被拖死），在产品上是灾难（用户以为自己的订单没了）。降级方案里最容易被忽略的一环，是返回什么形状的数据。

类型典型做法兜底从哪来要注意什么
读降级返回缓存、返回默认值、只返回主数据不返回附加信息本地缓存、Redis 里上一次的结果、静态兜底文案必须带「这是旧数据」的标记，前端要能显示「数据可能有延迟」
写降级同步转异步（先落队列）、只允许核心字段写、直接拒绝并给出明确错误码消息队列、本地磁盘缓冲要告知用户「稍后生效」，否则用户会重复提交
功能降级关掉非核心入口：推荐、评论、积分、排行榜配置中心开关关入口比「留着按钮但点了报错」好，后者是双重伤害
依赖降级切换备用通道、读走从库、换备用第三方预置的备用链路备用链路要定期演练，没演练过的备用链路等于没有

降级的返回结构必须和正常一致，这是硬要求。正常返回 {"items": [...], "total": 120}，降级就返回 {"items": [], "total": 0, "degraded": true}，而不是 {"code": 500, "msg": "系统繁忙"}。原因很实际：前端不用改代码，用户看到的是「暂无数据」而不是「系统错误」，这两者对留存的影响完全不同。至于「暂无数据」会不会让用户以为丢了数据——所以要加 degraded 字段，前端据此显示「当前展示的是缓存数据」。

开关的设计有四个要求，缺一个都会在故障时反噬你：

热生效：改配置不需要重启。配置中心推送 + 本地缓存 + 定时兜底拉取，三级保证。
能灰度：按用户 ID 哈希或按比例放量。一把全开的风险是「降级逻辑本身有 bug，全站立刻中招」。
能自动回切：依赖恢复后自动关掉降级，否则你会忘了关，然后带着降级状态跑一个月。
有观测：降级触发要打点（次数、原因、影响接口），并且要有告警。没有观测的降级等于「静默的功能缺失」，最危险。
# 一个能用的降级封装：先看开关，再走兜底，兜底失败也不能抛
public Result<List<Item>> listItems(long userId) {
    if (!switch.isOn("item.list", userId)) {        # 支持按用户灰度的开关
        metrics.counter("degrade.item.list").increment();
        return Result.ok(cachedItems(userId), true); # degraded=true
    }
    try {
        return Result.ok(remote.list(userId), false);
    } catch (Exception e) {
        metrics.counter("degrade.item.list.fallback").increment();
        # 兜底本身也要 try-catch：缓存读失败不能让整个接口 500
        return Result.ok(safeCached(userId), true);
    }
}

# 判断降级是否在生效：不要只看日志，看指标
# degraded_total / request_total 这个比例超过 1% 就该有人看一眼

自动降级和人工降级要配合用，不是二选一。自动降级的触发条件是「依赖不可用」，比如熔断打开了、超时率超阈值，这时候系统自己切兜底，等人来救已经晚了；人工降级的触发条件是「预期内的容量不足」，比如大促前主动关掉推荐、关掉实时积分，把资源让给下单链路。前者是止损，后者是预案。

降级最大的坑是「降级逻辑从没被验证过」。开关写好了、兜底代码写了，但一年没触发过。真到故障那天，一按开关发现兜底查询的 SQL 有语法错误、缓存的 key 早就改了格式、返回的字段少了一个导致前端渲染崩。所以降级必须定期演练：在低峰期真的把开关打开，看一眼页面。这比任何代码 review 都有效。

面试怎么答：「降级分读、写、功能、依赖四类。技术上的关键是返回结构要和正常一致，再加一个 degraded 标记，这样前端不用改、用户也不会以为数据丢了。开关要热生效、能灰度、能自动回切、有指标，最重要的是要定期演练——没演练过的降级路径，真出事时大概率是坏的。」

模块 7

隔离与超时预算：一个慢依赖，十分钟能吃掉整个服务

先算一道题：服务有 200 个工作线程，正常情况每个请求 20 毫秒，吞吐 10000 QPS。某个下游从 20 毫秒变成 3 秒，吞吐变成 200 ÷ 3 ≈ 66 QPS。也就是说，一个下游慢 150 倍，会把整个服务的容量砍掉 99%，而这时候你的限流、熔断可能都还没来得及反应。

这就是隔离存在的理由：把「所有请求共用一个线程池」改成「每个依赖一个池子」，那么慢的那个依赖最多占满它自己的池子，其他接口不受影响。这个模式的学名叫 bulkhead（船舱隔水舱），很形象——船撞破一个舱，其他舱还能浮着。

方式怎么实现优点硬伤
线程池隔离每个依赖一个独立线程池，调用在线程池里执行，主线程等待 Future能真正中断阻塞调用（超时后可以丢弃任务）；故障完全隔离线程数膨胀（依赖数 × 池大小）；ThreadLocal、MDC、TraceId 要手动透传；线程切换有开销
信号量隔离一个计数器，进入时 acquire，出来时 release，超过上限直接拒绝极轻量，没有额外线程，没有上下文问题不能中断正在阻塞的调用——调用就在当前线程里，信号量只能控制「有几个在跑」，控制不了「跑了多久」
连接池隔离每个依赖独立的 HTTP 连接池 / 数据库连接池，各自设上限直接限制了并发，也避免了「一个依赖占满所有连接」配置分散，容易被忽略；连接池满了的表现是等待，不是快速失败

信号量隔离的那个硬伤值得展开，因为它是选型的决定性因素：信号量的 release 只能在自己线程里执行，所以它没法「到点把任务掐掉」。你设了 200 个信号量、每个调用 3 秒，那么最坏情况是 200 个线程全卡 3 秒——信号量本身不会救你，只有底层客户端自己的超时能救你。所以：如果依赖的客户端有可靠的超时（比如 OkHttp 的 connectTimeout / readTimeout），信号量隔离够用；如果依赖可能永久挂住（老 SDK、文件 IO、第三方不可控的库），必须用线程池隔离，因为只有它能主动放弃。

接下来是超时预算，这是比隔离更容易被忽略的一层。很多人配超时的方式是「每层都设 1 秒」，看起来一致，实际上最坏链路是 1 + 1 + 1 = 3 秒，因为它们是串联的。用户等 3 秒早就走了。正确的做法是预算传递：入口定一个总 deadline（比如 800 毫秒），每往下一层就减掉本层的开销，子调用只能用剩下的时间。

# 预算传递：不是每层都设同样的超时，而是"你还剩多少时间"
入口（网关）   总预算 800ms
  └─ 服务 A   收到 deadLine=800，自己预留 50ms 序列化/网络 → 下游最多用 750
      ├─ 服务 B  deadLine=750，预留 50 → 下游最多用 700
      │   └─ DB  超时 300ms（必须 < 700）
      └─ 服务 C  deadLine=750，预留 50 → 下游最多用 700
          └─ 缓存 超时 50ms

# 三种超时都要设，缺一个就会出现"卡在奇怪的地方"
connectTimeout = 200ms     # 连不上要快速失败，不设会卡在 SYN 重传（几十秒）
readTimeout    = 500ms     # 连上了但不回数据
requestTimeout = 800ms     # 整体上限，包含重试和重定向

# 重试必须在预算内：800ms 的预算里，重试一次就意味着单次只能用 400ms

「只设读超时不设连接超时」是个非常常见的漏洞。TCP 连接建立失败时的默认重传行为可能让你等几十秒，而读超时对此完全无效——因为连接都还没建起来，谈不上「读」。同样，DNS 解析也可能挂很久，而大多数 HTTP 客户端的超时设置不覆盖 DNS 阶段。

隔离的粒度要按「依赖」而不是按「接口」。同一个下游的十个接口共用一个线程池是合理的（它们会互相挤，但至少挤的是同一个下游）；但如果把库存和优惠券放进同一个池子，库存挂了优惠券也没线程可用，隔离就白做了。反过来，池子切得太细（每个接口一个）会让线程总数失控，200 线程变成 2000 线程，GC 和上下文切换反而成为新问题。

面试怎么答：「一个下游从 20 毫秒变 3 秒，200 个线程的吞吐会从 10000 掉到 66，所以必须隔离。线程池隔离能中断阻塞调用、隔离彻底，代价是线程数和上下文传递；信号量隔离轻量但不能中断，所以只适合底层客户端有可靠超时的场景。超时要做预算传递，入口定总 deadline，每层减掉自己的开销，子调用只能用剩下的时间；连接超时、读超时、整体超时三个都要设。」

模块 8

重试放大：三层各重试三次，下游要扛 27 倍

重试是被误用最多的「高可用手段」。它在代码里长得像一行 for 循环，效果却是把一次故障放大成一次雪崩。算法很简单：每多一层重试，压力就乘以重试次数。

算一下：入口（网关）重试 3 次，服务 A 重试 3 次，服务 A 调的服务 B 也重试 3 次。一个用户请求在最坏情况下会让 B 收到 3 × 3 × 3 = 27 次调用。如果 B 本来就已经过载（这正是它超时的原因），这 27 倍压力会让它彻底起不来。更糟的是，重试通常发生在超时之后，而超时意味着「B 已经处理了很久」——你不但让它多干 27 倍的活，还都是在它最忙的时候。

情况能重试吗原因
连接被拒绝（connection refused）可以请求根本没到达对方，重试没有副作用
连接超时（握手阶段）可以，但要限次数请求也没到达业务逻辑，通常是网络或对方 accept 队列满
读超时（请求已发出）仅幂等操作可以对方可能已经执行成功了，只是回包慢。重试会造成重复下单/重复扣款
HTTP 500 / 502 / 503看语义，503 可重试500 是对方代码出错，重试大概率还是错；503 是暂时不可用，退避后可能恢复
HTTP 429可以，但必须按 Retry-After 退避对方明确告诉你「慢点」，硬重试等于加害
HTTP 400 / 401 / 403 / 404不要请求本身有问题，重试一万次也是同样的结果，只是浪费资源

所以重试的三个前提是：操作幂等、错误可重试、预算还够。第三条最容易被忽略——你的总预算是 800 毫秒，第一次调用已经花了 700 毫秒，剩下 100 毫秒根本不够再发一次，这时候「重试」的实际效果是「必然超时，还多占一条连接」。

退避策略解决的是「同时重试」问题。如果 1000 个客户端在同一时刻失败，然后都在 1 秒后重试，那么第 1 秒的流量尖峰和故障时一模一样，对方刚缓过来又被打一遍。指数退避把重试间隔拉开（1s、2s、4s、8s），而 jitter（抖动）把重试时刻打散——两者必须一起用，只做指数退避的话，所有客户端仍然会在同一个时刻一起重试。

# 指数退避 + full jitter：sleep = random(0, min(cap, base * 2^attempt))
# 只做指数退避不做抖动，等于把"同时失败"变成"同时重试"
long base = 50;      # 毫秒
long cap  = 2000;
for (int attempt = 0; attempt < maxAttempts; attempt++) {
    try { return call(); }
    catch (RetryableException e) {
        long ceiling = Math.min(cap, base * (1L << attempt));
        long sleep = ThreadLocalRandom.current().nextLong(0, ceiling + 1);  # full jitter
        if (remainingBudget() < sleep + estimatedCost()) break;             # 预算不够就不重试
        Thread.sleep(sleep);
    }
}

# 幂等键：写操作要能安全重试，就必须有服务端去重
# 客户端生成 UUID，放在 header 里；服务端用唯一索引或去重表挡住第二次
POST /orders
Idempotency-Key: 7f3c9a1e-...      # 同一个 key 重复提交，返回第一次的结果

还有两个工程上的做法值得说。一是把重试放在最外层：内层（服务之间）尽量不重试，让最外层统一决定「要不要再来一次」。这样放大倍数从 27 降到 3。内层不重试的代价是「单次抖动的成功率下降」，但换来的是「故障时不会雪崩」，这个交换在大多数系统里是划算的。二是设重试预算：重试请求不超过正常请求的 10%，超过就熔断重试本身。这是个很聪明的机制，因为它让重试的总量有上限，不会随着故障规模线性放大。

重试 + 熔断必须一起用，而且顺序要对。先判断熔断器是不是开着：开着就直接失败，别再重试（重试只会打到熔断器上，白白消耗线程）。熔断器关了才进入重试逻辑。如果顺序反了，你会看到「下游已经熔断，但重试还在不停地尝试」，日志里全是重试记录，实际一个请求都没发出去。

面试怎么答：「重试是乘法：三层各重试三次就是 27 倍压力，而且往往打在对方最忙的时候。所以重试要满足三个条件——幂等、错误可重试、预算还够。只重试连接类错误和 503/429，不重试 4xx 和读超时（除非幂等）。退避要加 jitter，否则所有客户端会同时重试。工程上把重试收敛到最外层，内层不重试，再加一个 10% 的重试预算兜底。」

模块 9

一套能报出口的数字：阈值是怎么算出来的

面试官问「你的限流阈值怎么定的」，答「看监控慢慢调」等于没答。他要听的是一条从压测数字推到配置值的推导链。下面这套数字是示例，你要用自己环境的压测结果替换，但推导方式可以直接用。

设定一个具体场景：商品详情接口，日常 800 QPS，大促峰值 3000 QPS，平时 4 个副本。单副本压测（含下游调用）在 P99 不超过 100 毫秒的前提下能扛 1200 QPS。

参数取值怎么推出来的
单副本限制流800 QPS压测上限 1200，留 1/3 余量。余量不是浪费，是给 GC、慢查询、突发下游延迟用的
集群总量限流3200 QPS4 副本 × 800。注意这是总量，扩容到 8 副本不会自动变成 6400，得手动改
令牌桶 burst1600取 rate 的 2 倍。允许 2 秒的额度攒起来，再大就是给瞬时冲击开门
工作线程数core 100 / max 200800 QPS × 0.1 秒 = 80 个并发在跑，取 100 打底，200 是给抖动留的
队列长度100超过 100 个排队说明处理不过来，再排只是让用户多等一秒然后超时
入口总超时800ms取用户可感知阈值的下限，同时要大于「下游 P99 + 一次重试」
下游 RPC 超时200ms下游 P99 是 80ms，2.5 倍余量；必须小于父预算 800 减去自身开销
熔断阈值失败率 50%，样本 ≥ 20样本 20 是为了避免低流量误判；50% 是「一半都失败了，肯定不是偶发」
熔断 open 时长10s给下游重启/切主留时间；太短会在恢复期反复打

几个推导里的细节值得单独讲，因为它们体现的是判断力而不是记忆力：

为什么单机限流要留 1/3 余量？因为「压测上限」是在干净环境下测出来的：没有 GC 抖动、没有慢查询、没有其他服务抢 CPU。生产环境的有效容量通常是压测值的 60% 到 80%。如果你把阈值设成压测上限，那么只要有一点抖动，系统就会在你「以为还没到限额」的时候开始排队。

为什么线程数不是「QPS 除以 RT」算出来的精确值？因为那个公式算的是稳态并发，而真实流量有波动。用 800 × 0.1 = 80 得到的 80 是平均值，峰值可能是 2 到 3 倍。所以 core 设 100，max 200，队列 100——三个数字一起构成一个「能吸收抖动但不会无限堆积」的结构。队列不能设大，因为排队不增加吞吐，只增加延迟。

为什么熔断的样本数要 20？假设某个依赖只有 1 QPS，统计窗口是 50 个请求，那么要 50 秒才能攒够样本。如果最小请求数设成 1，那么凌晨只要有一个请求失败，失败率就是 100%，熔断立刻打开，而这个依赖可能只是网络抖了一下。最小请求数的本质是「在样本不足时拒绝做统计判断」，这条设计能消掉绝大部分误熔断。

怎么验证这套数字是对的：① 压测时把下游人为注入 200 毫秒延迟（用 tc 或 mock），看限流和熔断是否按预期触发，以及触发后 P99 是否回落；② 把 Redis 停掉，看限流是否退化成单机而不是全站 500；③ 手工打开降级开关，走一遍完整链路，看前端渲染是否正常；④ 把某个下游进程 kill 掉，看熔断打开、降级生效、进程恢复后是否自动回切。这四步做完，你的「配置」才变成「能力」。

面试怎么答：「我一般从一个压测数字开始推。比如单副本压测能扛 1200 QPS，线上取 800，留三分之一给 GC 和下游抖动；集群总量是副本数乘 800，扩容时要手动改。线程数按 QPS 乘 RT 算稳态并发再留一倍余量，队列只留 100，因为排队不增加吞吐只增加延迟。超时用预算传递，入口 800 毫秒，下游 200 毫秒。熔断用失败率 50% 加最小样本 20，避免低流量误判。这些数字都要用故障注入验证过才算数。」

模块 10

9 个坑：每一个都能让配置变成装饰

这一节的坑分两类：一类是「参数配错」，一类是「机制没接上」。后一类更隐蔽——配置全都对，但因为它和别的机制的顺序错了，效果等于零。

1
令牌桶的 burst 设成速率的十倍
桶能攒令牌，burst 就是「允许一次放出多少」。设成 200 QPS 配 2000 burst，等于给了一个 10 倍的突发放大器，下游被第一秒打挂。经验值是 1 到 5 倍速率。
2
用固定窗口做过载保护
窗口边界会把限额放大一倍，而流量高峰恰好最可能在某个整点开始（定时任务、整点秒杀）。这类场景必须用滑动窗口或令牌桶。
3
单机限流，然后上了自动扩缩容
4 副本各限 500 是 2000，HPA 扩到 20 副本就变成 10000，下游一点没变强。总量限制必须放在一个中心点，或者按副本数动态计算单机阈值。
4
限流触发后返回 500
客户端看到 5xx 会重试，于是被限流的请求又回来了，实际压力比不限流还大。限流必须返回 429 或 503，并带上 Retry-After，让客户端知道该等多久。
5
熔断器不设最小请求数
低流量时一个失败就是 100% 失败率，熔断反复开关（状态抖动），业务时好时坏。这是「熔断太灵敏」的典型症状，加一个 minimumNumberOfCalls 就能消掉。
6
半开状态一次放全部流量
下游刚恢复，处理能力可能只有一半，一次放全量会立刻把它再打挂，然后回到 open，形成「恢复-打挂」的循环。半开只放个位数请求，成功后再逐步放量。
7
所有依赖共用一个线程池
隔离失效。一个慢依赖会占满整个池子，连「不依赖它」的接口也一起挂。这是「一个下游挂了，整个服务全挂」的最常见原因。
8
内层也重试，而且没有 jitter
三层各三次就是 27 倍，再加上所有客户端同时重试，等于给已经过载的下游补一脚。重试收敛到最外层，退避必须带抖动。
9
降级返回的结构和正常不一致
正常返回对象，降级返回 null 或错误码，前端要么崩要么显示「系统错误」。降级要返回同构数据加 degraded 标记，而且降级路径必须演练过。

面试怎么答：挑一个带数字的讲。比如「我们做过一次大促压测，单副本能扛 1200 QPS，就按 800 设了单机限流，集群总量写死在配置里是 3200。结果大促前扩容到 10 个副本，总量自动变成 8000，把下游的库存服务打挂了。后来改成总量在网关上集中限流，单机阈值只做兜底，并且 Redis 不可用时降级成单机限流而不是全放。这件事让我记住：限流阈值和副本数是耦合的，扩容的时候必须同步改。」

六道题

1. 令牌桶和漏桶最本质的区别是什么？
正确答案：令牌桶允许突发，漏桶输出恒定。令牌桶以固定速率补充令牌，桶能攒，空闲后攒满 b 个，下一瞬间可以一次通过 b 个请求，所以语义是「平均速率 r、突发上限 b」。漏桶是请求进桶、恒定速率流出，不攒额度，只攒待处理请求，因此能把突发流量整形为匀速流。两者限的都是速率，都不直接限制并发。
2. 用固定窗口计数器实现「每分钟最多 100 次」，可能出现的最坏情况是？
正确答案：边界双倍。固定窗口在两个窗口交界处会重置计数，压在边界上的流量可以吃满两个窗口的额度。修法有两种：改成滑动窗口（日志版精确、计数版分格加权近似），或者改用令牌桶（额度匀速补充，没有「整点重置」这个动作）。按天、按月的配额场景边界效应影响小，固定窗口仍可用。
3. 分布式限流用 Redis + Lua 实现，Redis 集群整体不可用时，下面哪种处理最合理？
正确答案：降级为单机限流。fail-closed 会把「限流器抖动」升级成「全站拒绝」，fail-open 则在流量高峰时完全裸奔，两者都是把一个小故障放大。生产上的常见做法是给 Redis 调用设很短的超时（比如 10 毫秒），超时就切本地令牌桶——精度下降，但保护还在。这个取舍要提前写进设计文档。
4. 熔断器进入 half-open 状态后，正确的行为是？
正确答案：少量探测。half-open 的意义是「用很小的代价试探下游是否恢复」，放全量等于给刚恢复的下游做压力测试，很容易二次打挂并回到 open，形成循环。探测失败后必须重置 open 计时器，否则会持续骚扰下游，等于熔断没生效。
5. 关于信号量隔离和线程池隔离，下面哪个说法是对的？
正确答案：信号量不能中断阻塞调用。信号量只控制「同时有几个在跑」，release 必须在原线程执行，它没有能力把卡住的调用掐掉；真正能主动放弃任务的只有线程池隔离。所以依赖的客户端有可靠超时时用信号量（轻量、无上下文问题），依赖可能永久挂住时用线程池。线程池隔离反而需要手动透传 ThreadLocal、MDC、TraceId。
6. 网关重试 3 次，服务 A 内部重试 3 次，服务 A 调用的服务 B 也重试 3 次。最坏情况下，一个用户请求会让 B 承受多少次调用？
正确答案：27 次。重试是乘法关系：3 × 3 × 3 = 27。而且这些重试往往发生在超时之后，也就是打在对方最忙的时刻。这正是「重试把一次故障放大成一次雪崩」的机制。工程上的做法是把重试收敛到最外层（放大倍数降到 3），内层不重试，并给重试设一个不超过正常流量 10% 的预算。
