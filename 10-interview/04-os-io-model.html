开始前

一个所有人都遇到过的现场

8 核机器，QPS 三千，每个请求要查两次 Redis、调一次下游 HTTP。CPU 使用率 25%，看着很闲，但接口 P99 从 80ms 抖到 900ms，高峰期还偶发超时。

翻代码：线程池 500 个线程，用的是阻塞 IO。看上去「线程多、能扛并发」，实际上 500 个线程在同一时刻能处理的请求就是 500 个，超出的全部排在队列里等。CPU 闲着，线程全在等网络——这就是典型的用线程数硬扛 IO 等待。

面试官问「你怎么优化」，如果你答「加到 2000 个线程」，他会接着问「一台机器最多能开多少线程，为什么」。这时候答不上来，前面讲的架构就全是空中楼阁。

省内存
线程栈是 MB 级预留，协程栈是 KB 级起点。这是「十万并发」在内存上的第一道门槛。
省切换
线程切换要进内核、保存上下文；协程切换在用户态完成，只换栈和寄存器。
省等待
IO 多路复用让一个线程同时盯住上万个连接，谁就绪处理谁，不再一对一死等。

这一篇就按这三条线索走：先讲清进程与线程在内存和调度上到底差什么，再讲协程省的是哪部分开销，然后是五种 IO 模型和 epoll 的真实边界，最后收在「线程池开多大」这条从应用问到内核的追问链上。

面试落点：面试官问「你怎么优化这个接口」时，别急着报技术名词。先说「它是 IO 密集还是 CPU 密集」，再说「瓶颈在等还是算」，最后才说方案。这一句话的顺序，本身就是判断力的展示。

模块 1

进程与线程：隔离的是地址空间，共享的也是它

「进程和线程的区别」几乎每场必问，但大部分人背的是「进程是资源分配单位、线程是调度单位」。这句话没错，却不足以支撑追问。真正该说的是：哪些东西被复制了，哪些被共享了，代价分别是什么。

资源进程之间同一进程内的线程之间
虚拟地址空间各自独立，互相看不见共享（代码段、数据段、堆、mmap 区）
页表 / TLB各自一套，切换要换页表共用一套，切换不刷 TLB
栈各自独立各自独立（这是线程唯一的大块私有内存）
寄存器上下文独立独立（切换时要保存/恢复）
打开的文件描述符独立（fork 时复制一份指向同一文件的 fd 表）共享同一张 fd 表
当前工作目录、umask独立共享
信号处理函数独立共享（进程级设置）
信号屏蔽字、errno—每个线程一份

这张表里最容易被追问的两行：栈是私有的，所以线程里的局部变量天然不共享，不需要加锁；fd 表是共享的，所以一个线程 close 了 fd，另一个线程手里的同一个 fd 立刻失效——这类 bug 极难查，因为看起来完全无辜。

切换到底贵在哪

线程切换要做的事：保存当前线程的寄存器到内核栈、切换内核栈、更新调度信息、恢复目标线程的寄存器。这中间不换地址空间，所以 TLB 基本不用刷（同一进程的虚拟地址映射没变）。

进程切换多做一步：换页表。换页表意味着 TLB 里的缓存大部分失效，接下来的一小段时间里，每次内存访问都可能要重新走多级页表。现代 CPU 有 PCID/ASID 这类标记来减少刷新，但代价依然比线程切换高。

不要背具体数字。「线程切换几微秒、进程切换几十微秒」这类说法在面试里很容易被反问「在什么硬件上、有没有跨核、缓存热不热」。稳妥的表述是：都是微秒量级，比一次函数调用贵三个数量级左右，进程切换因为要换地址空间所以更贵，实际值取决于硬件和缓存状态。

还有个反向的坑：线程不是越多越好，也不是越少越好。线程太多会带来三类开销——栈内存（每个线程默认预留 MB 级虚拟空间，实际按需提交）、调度开销（就绪线程多，每个时间片分到的 CPU 变少，缓存局部性变差）、锁竞争（临界区被更多线程争抢，上下文切换反而增加）。

# 看一个进程到底有多少线程、每个线程在干什么
ps -L -p 12345 -o pid,tid,stat,pcpu,comm
top -H -p 12345
cat /proc/12345/status | grep -E 'Threads|VmRSS'

# 线程的栈大小（默认值各发行版不同，以 ulimit -s 为准）
ulimit -s

# 系统级上限：这两个数决定了「最多能开多少线程」
cat /proc/sys/kernel/threads-max
cat /proc/sys/vm/max_map_count

「一台机器最多能开多少线程」的正确答法是分三个约束：内存（每线程栈 + 内核 task_struct）、内核参数（threads-max、pid_max、max_map_count）、实际收益（超过某个点，吞吐不再涨，延迟反而升）。前两个是硬上限，第三个才是你该关心的。

面试落点：「进程和线程的核心差别是地址空间是否独立。线程共享堆和 fd 表，各有自己的栈和寄存器，所以切换不用换页表，比进程切换便宜。但线程数受栈内存和调度开销约束，靠加线程扛 IO 是线性外推，迟早撞墙。」

模块 2

协程：省的不是 CPU，是「等」的成本

「协程比线程快」这句话是错的，而且错得很典型。协程不会让计算变快，它让等待变得便宜——便宜到你可以用同步的写法，开出十万个并发单元。

先把机制说清楚：协程是用户态的、协作式的执行单元。调度由运行时（Go runtime、libco、Python 的 asyncio）负责，切换时不进内核，只做两件事——保存当前协程的少量寄存器到它自己的栈上，把栈指针换到目标协程。没有系统调用、没有页表切换、没有内核调度器参与。

维度线程协程
调度者内核调度器用户态运行时
切换开销微秒量级，要陷入内核百纳秒量级，纯用户态
栈大小MB 级预留（以 ulimit -s 为准）KB 级起步，按需增长
切换时机时间片用完或被抢占协程自己让出（遇到 IO、显式 yield）
并行能力可真正多核并行单协程不并行，靠 M:N 映射到多个线程
阻塞的后果只阻塞自己阻塞了整个底层线程，同线程上其他协程全被拖住

最后一行是协程最大的陷阱。协程的调度是协作式的：只要有一个协程做了阻塞系统调用（比如同步的文件读写、没设超时的 DNS 查询），它所在的 OS 线程就卡住了，这个线程上排队的其他协程一个都跑不了。所以「协程 + 阻塞调用」是比「纯线程」更糟的组合，因为线程至少还能被内核切走。

# 直观对比：一万个并发单元需要多少栈内存
# 线程：默认栈 8MB（虚拟地址预留，实际按需提交，但地址空间要占）
# 10000 × 8MB = 80GB 虚拟地址 —— 64 位地址空间撑得住，物理内存和内核结构撑不住
# 协程：初始栈 KB 级，按需增长
# 10000 × 几 KB = 几十 MB —— 这才是「十万并发」能落地的原因

# Go 里看当前 goroutine 数量（pprof 或 runtime 指标）
# go tool pprof http://localhost:6060/debug/pprof/goroutine
# runtime.NumGoroutine()

两种协程实现，问法不一样

  • 有栈协程（Go 的 goroutine、C 的 libco）：每个协程有独立栈，可以随意嵌套调用，写起来和同步代码几乎一样。代价是栈内存和栈扩容时的搬迁。
  • 无栈协程（C# / Rust / Python 的 async）：编译器把函数改写成状态机，靠一个 future/promise 链推进，没有独立栈。省内存，但会「染色」——调用链上每一层都得是 async。

面试里如果被问「Go 的协程为什么能开十万个」，标准答案是三层：栈小且可增长（KB 级起步，不是 MB 级预留）、调度在用户态（M:N 模型，G 挂在 P 上，P 绑定 M，切换不陷内核）、网络 IO 由 runtime 的 netpoller 接管（协程发起网络读写时不阻塞线程，而是被挂起，等 epoll 通知再恢复）。三条缺一条，「十万」就不成立。

一个常被忽略的成本：协程不是免费的，每个协程仍有栈、有调度结构体、有 GC 需要扫描的根。开一千万个协程一样会把内存吃光。所谓「十万并发」通常是「十万个连接」而不是「十万个同时在算的任务」——大部分协程在等 IO，真正在跑的只有核数那么多。

面试落点：「协程不是更快，是更省。它省掉了内核调度和 MB 级栈，让每个并发单元的成本从 MB 降到 KB，所以能开很多。但它是协作式的，一个协程做阻塞调用会拖住整个线程，所以协程必须配非阻塞 IO 或者 runtime 接管网络。」

模块 3

四个词的两两组合：同步/异步、阻塞/非阻塞

这四个词被混用得一塌糊涂。有人把「非阻塞」当「异步」，有人觉得「用了 epoll 就是异步 IO」。先把定义钉死，后面的五种模型才不会乱。

维度在问什么两个取值
阻塞 / 非阻塞发起调用后，调用方线程会不会被挂起阻塞：挂起直到有结果；非阻塞：立刻返回，用返回值告诉你「还没好」
同步 / 异步整个 IO 操作由谁完成、结果怎么通知同步：调用方自己等或自己查；异步：内核做完再通知你，中间你完全不用管

关键在于：IO 有两个阶段——第一阶段「等数据就绪」（网卡收到包、磁盘读完），第二阶段「把数据从内核缓冲区拷到用户缓冲区」。判断同步还是异步，看的是第二阶段谁来做。只要还需要你自己调一次 read 去拷数据，它就是同步 IO，哪怕你等的时候用的是 epoll。

同步阻塞
read() 一调用就卡住，等数据到了、拷完了才返回。最简单，一个连接一个线程。
同步非阻塞
read() 立刻返回 EAGAIN，你自己循环重试。轮询，CPU 空转，通常要配多路复用才有意义。
异步非阻塞
你只提交请求，内核把数据拷完后通知你，全程没有一次「等」。POSIX AIO、io_uring 属于这一类。

至于「异步阻塞」这个格子，常见的解释是「用 select 阻塞等待，但等的是『就绪』而不是『完成』」——严格说它仍是同步 IO，只是把「等」从每个连接挪到了一个线程上。这个格子存在的意义，是提醒你「阻塞在等就绪」和「阻塞在等数据」是两件事。

# 非阻塞 fd 的典型用法：read 立刻返回，靠 errno 判断
fcntl(fd, F_SETFL, fcntl(fd, F_GETFL) | O_NONBLOCK);
n = read(fd, buf, sizeof(buf));
if (n == -1 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
    /* 还没数据，等下次通知；注意这两个常量在 Linux 上是同一个值 */
}
最常见的错误表述：「我们用了 epoll，所以是异步非阻塞 IO」。epoll 只解决第一阶段——告诉你哪个 fd 就绪了。真正读数据时你还是要调 read，这一步是同步拷贝。所以准确说法是「IO 多路复用 + 非阻塞 fd，属于同步非阻塞模型」。

面试落点：「阻塞非阻塞看调用方线程会不会挂起，同步异步看数据拷贝由谁完成。IO 多路复用把等待集中到一个线程，但它仍然是同步 IO，因为最后那次 read 还是要自己拷。真正的异步 IO 是内核拷完再通知你，Linux 上早期是 POSIX AIO，现在是 io_uring。」

模块 4

五种 IO 模型：一张表看完，两阶段一刀切

五种模型的名字很好背，难的是说清「它们都在哪个阶段阻塞」。记住一句话：前四种都卡在第二阶段，只有第五种两个阶段都不卡。

模型第一阶段（等数据）第二阶段（拷贝）典型系统调用
阻塞 IO阻塞阻塞默认的 read / recv
非阻塞 IO轮询，不阻塞阻塞O_NONBLOCK + read 循环
IO 多路复用阻塞在 select/poll/epoll_wait 上（一次等多个 fd）阻塞select / poll / epoll_wait
信号驱动 IO不阻塞，内核用 SIGIO 通知阻塞fcntl 设 O_ASYNC + signal handler
异步 IO不阻塞不阻塞，内核拷完再通知POSIX aio_*、io_uring

为什么信号驱动用得少？因为信号处理函数里能做的事非常有限（不能随便调非异步信号安全的函数），而且信号会丢、会合并，高并发下很难管理。教科书里讲它，更多是为了把「通知机制」这条线补全。

异步 IO 长期不流行的原因也很实际：Linux 原生的 POSIX AIO 实现一直不够好（glibc 的用户态模拟有很多限制），真正好用要等到 io_uring（较新的内核才提供，具体版本以你环境为准）。io_uring 用一对共享内存环形队列提交和回收请求，批量提交、减少系统调用次数，这是它在高 IOPS 场景下比 epoll 更占优的原因。

# 判断一个服务用的是哪种模型，看它停在哪个系统调用上
strace -f -e trace=network,epoll_wait,select,poll -p 12345
# 大量线程停在 read/recv  → 阻塞 IO，一连接一线程
# 少量线程停在 epoll_wait → 多路复用
# 停在 io_uring_enter     → 异步 IO

# 看进程打开的 socket 数量，判断「一连接一线程」是否成立
ls /proc/12345/fd | wc -l
ss -tanp | grep 12345 | wc -l
答题模板：「五种模型的分界线在第二阶段。阻塞、非阻塞、多路复用、信号驱动，前四种在『把数据从内核拷到用户』这一步都是阻塞的，所以都算同步 IO；只有异步 IO 是内核拷完了再通知，调用方全程没被卡住。」

面试落点：这张表能背下来就够了，但一定要补一句「实际工程里绝大多数是 IO 多路复用 + 非阻塞 fd，纯异步 IO 在 Linux 上要等 io_uring 才真正好用」。这句话能把「背书」和「用过」区分开。

模块 5

select / poll / epoll：差别不在名字，在数据结构

「epoll 为什么比 select 快」有三个标准答案：没有 fd 数量上限、不用每次把集合从用户态拷进内核、只返回就绪的 fd 而不是全部遍历。这三条背后是三个不同的数据结构决策。

对比项selectpollepoll
数据结构fd_set 位图（固定长度）pollfd 数组内核红黑树 + 就绪链表
fd 上限受 FD_SETSIZE 限制（常见默认 1024）无硬上限，受内存和打开文件数限制无硬上限，受内存和打开文件数限制
每次调用全量拷贝 fd 集合进内核，返回后还要遍历所有 fd全量拷贝数组，返回后遍历所有元素注册一次（epoll_ctl），之后只取就绪链表
复杂度O(n)O(n)注册 O(log n)，取就绪 O(k)（k 是就绪数）
触发模式水平触发水平触发水平触发（默认）+ 边缘触发
跨平台几乎所有系统多数 UnixLinux 专有（BSD 是 kqueue）

select 的 1024 不是「内核不愿意支持更多」，是 fd_set 这个结构本身用固定长度的位图表示，长度由编译期的 FD_SETSIZE 决定。改它需要重新编译程序，而且每次调用都要把整张位图拷进内核再拷回来，fd 一多，光是拷贝就吃满 CPU。

LT 与 ET：一个通知，两种语义

水平触发（LT，默认）：只要 fd 上还有数据没读完，下次 epoll_wait 还会告诉你。写错了也不容易出事，最多是重复通知。

边缘触发（ET）：只在状态变化的那一刻通知一次。你没读完，它也不会再提醒。所以 ET 模式必须配两个条件：fd 设为非阻塞、每次事件都循环读到返回 EAGAIN 为止。

# ET 模式的正确读法（伪代码）
for (;;) {
    n = read(fd, buf, sizeof(buf));
    if (n > 0) { append(buf, n); continue; }
    if (n == 0) { close(fd); break; }                    /* 对端关闭 */
    if (errno == EAGAIN || errno == EWOULDBLOCK) break;  /* 读干净了，等下次通知 */
    if (errno == EINTR) continue;
    break;
}
ET + 阻塞 fd = 卡死。循环读到没有数据时，如果 fd 是阻塞的，最后一次 read 会永远等下去，整个事件循环挂住。这个 bug 在压测时不一定复现（数据总是很多），偏偏在低峰期偶发，非常难查。

epoll 不是「O(1) 万能药」

这句话一定要会说，因为它能立刻把你和背博客的人区分开：

  • 取就绪是 O(k) 不是 O(1)。一万个 fd 同时就绪，epoll_wait 还是要返回一万个事件、你还是要处理一万次，这时候它和 poll 的差距没有想象中大。
  • 注册有成本。每次 epoll_ctl 都要在红黑树上操作，短连接场景（连接建立就关）下这个成本占比很高。长连接才是 epoll 的主场。
  • 对普通文件无效。磁盘文件永远是「就绪」的，epoll 起不到等待作用，读文件该阻塞还是阻塞。所以「用 epoll 加速读本地文件」是伪命题，那要靠 page cache 和异步 IO。
  • 有惊群问题。多个线程等同一个 listen fd 时，新连接可能唤醒所有线程。较新的内核提供 EPOLLEXCLUSIVE 来缓解，但需要显式设置。
  • 跨平台不通用。BSD/macOS 用 kqueue，Windows 用 IOCP，Go/Netty 这类框架为此做了抽象层。

面试落点：「select 慢在三点：fd 上限、每次全量拷贝、返回后全量遍历。epoll 用红黑树存注册关系、用就绪链表只返回活跃的，所以 fd 多但活跃少时优势明显。但它的取事件是 O(k)，fd 全都活跃时优势就没了，而且它对普通文件无效，短连接场景注册成本也不低。」

模块 6

零拷贝：省掉的是「用户态那一次搬运」

「零拷贝」这个名字有误导性，它从来不是「一次拷贝都没有」，而是「不让 CPU 参与那次没有必要的搬运」。把这个前提说清楚，后面的数字才站得住。

先看最朴素的「读文件再发出去」：

# 传统 read + write 发一个文件
n = read(file_fd, buf, len);    # ① DMA: 磁盘 → 内核页缓存
                                # ② CPU: 内核页缓存 → 用户缓冲区
write(sock_fd, buf, n);         # ③ CPU: 用户缓冲区 → socket 缓冲区
                                # ④ DMA: socket 缓冲区 → 网卡

# 一共 4 次拷贝（2 次 DMA + 2 次 CPU），4 次用户态/内核态切换

问题很明显：数据从磁盘到网卡，压根不需要经过用户态。应用只是想把文件内容转发出去，中间那次「内核 → 用户 → 内核」的往返纯属浪费——既费 CPU，又占内存带宽，还多两次上下文切换。

# sendfile：数据全程留在内核
sendfile(sock_fd, file_fd, NULL, len);
# ① DMA: 磁盘 → 页缓存
# ② CPU: 页缓存 → socket 缓冲区（若网卡支持 scatter-gather，这步也可省）
# ③ DMA: socket 缓冲区 → 网卡
# 切换变成 2 次，CPU 拷贝从 2 次降到 1 次，支持 SG-DMA 时降到 0 次

# mmap + write：把页缓存映射进用户态，省掉「内核→用户」那次拷贝
p = mmap(NULL, len, PROT_READ, MAP_PRIVATE, file_fd, 0);
write(sock_fd, p, len);   # 仍是 3 次拷贝，但少了一次 CPU 搬运
方式拷贝次数CPU 参与适用
read + write42 次数据要在用户态处理（压缩、加密、解析）
mmap + write31 次需要在用户态看数据，但不想复制
sendfile3（支持 SG 时 2）1 次（或 0 次）纯转发：静态文件、日志投递、代理
splice20 次通过管道在两个 fd 之间搬，内核内部完成

工程里的对应关系：Nginx 开 sendfile on 走的就是 sendfile；Kafka 消费端大量依赖 sendfile 把日志段直接推给客户端；Java 的 FileChannel.transferTo 在 Linux 上会落到 sendfile。而一旦你要对数据做压缩或加密（比如 HTTPS），零拷贝就用不上了——你必须把数据搬进用户态交给 TLS 库，这时候 sendfile 的优势消失。

别在面试里说「用了 sendfile 就是零拷贝，一次拷贝都没有」。准确说法是「减少了一次 CPU 拷贝和两次上下文切换；如果网卡支持 scatter-gather DMA，CPU 拷贝可以降到 0，但 DMA 拷贝始终存在——数据总要从一个地方到另一个地方。」

面试落点：「零拷贝的本质是取消用户态这趟中转。read+write 是 4 次拷贝 4 次切换，sendfile 是 3 次拷贝 2 次切换，网卡支持 SG 时 CPU 拷贝为 0。但只要你要修改数据，比如加 TLS，就还是得回到用户态，这个优化就用不上了。」

模块 7

page cache 与 writeback：write 返回不等于落盘

「为什么 write 成功了，机器断电数据还是丢了？」这题看着像数据库的题，其实是操作系统题。答案就一句：write 只是把数据交给了 page cache。

Linux 的读写都过 page cache：读的时候，如果页在缓存里就直接返回（缓存命中），不在就从磁盘读进来再返回；写的时候，数据先写进缓存页并把它标记为脏页（dirty），然后就返回了。真正写到磁盘，由内核的 writeback 线程在后面做。

# 看当前有多少脏页、多少正在回写
grep -E 'Dirty|Writeback|Cached|MemFree|MemAvailable' /proc/meminfo

# 回写相关的内核参数（默认值各发行版不同，以 sysctl 实际输出为准）
sysctl vm.dirty_ratio vm.dirty_background_ratio
sysctl vm.dirty_expire_centisecs vm.dirty_writeback_centisecs

# 强制落盘：fsync 刷数据+元数据，fdatasync 只刷数据
fsync(fd);
fdatasync(fd);

# 直接 IO：绕过 page cache，自己管对齐（数据库常用）
open(path, O_RDWR | O_DIRECT);
触发回写的条件含义
脏页超过 dirty_background_ratio后台线程开始异步回写，不影响应用
脏页超过 dirty_ratio写操作被同步阻塞，应用会明显卡顿
脏页存在超过 dirty_expire_centisecs周期性地把「太老」的脏页刷出去
显式 fsync / fdatasync / sync调用方自己要求落盘
内存压力要回收内存时，脏页必须先回写才能释放

为什么这事对运维重要？因为写入量的峰值会以「延迟抖动」的形式出现在你意想不到的地方。一批进程同时写文件，脏页攒到 dirty_ratio，内核开始同步回写，所有写入者一起卡住，监控上看到的是「磁盘 await 突然飙高、应用 P99 抖动」，而应用代码里根本没有慢操作。

page cache 还有一个容易误解的地方：它不只是缓存文件，还承担了「合并写」的职责。很多小写入在缓存里被合并成一次大的顺序写，这是 Linux 写性能看起来很好的主要原因。所以 O_DIRECT 绕过缓存并不总是更快——它避免了缓存占用和双份内存，但也失去了合并，随机小写的场景反而更慢。数据库选它是因为要自己控制刷盘时机和缓存策略，不是因为「绕过缓存一定快」。

一个直接可用的判断：如果应用说「我 write 成功了但数据没了」，先问它有没有 fsync。如果没有，那不是内核的 bug，是它把「写进缓存」当成了「写进磁盘」。数据库的 WAL、消息队列的持久化，都必须显式 fsync 才算数。

面试落点：「write 只写到 page cache 就返回，落盘由 writeback 异步完成。要保证持久化必须 fsync，而且要接受 fsync 的代价——它会把一次内存拷贝变成一次真实的磁盘等待。批量化、组提交、O_DIRECT 都是在跟这个代价做交易。」

模块 8

内存管理：虚拟内存、页表、TLB 与 NUMA

前面讲的都是「IO 怎么走」，这一节讲「内存怎么找」。因为在面试里，「为什么进程能用到比自己内存大的地址空间」「为什么两个进程访问同一块内存性能差很多」这类问题，答案都在这。

虚拟内存解决的三个问题：隔离（每个进程看到独立的地址空间，看不到别人的）、抽象（程序不用关心物理内存碎片，看到的永远是连续的）、超额分配（可以映射比物理内存更大的空间，用到了再从磁盘换入）。

概念是什么在哪体现
页表虚拟页号 → 物理页帧号的映射，多级结构以节省空间每次内存访问都要查（靠 TLB 加速）
TLB页表项的 CPU 缓存，命中就不用走多级页表进程切换要换页表，TLB 可能被刷
缺页中断访问的页没映射或不在内存，陷入内核处理minor（页在内存、只缺映射）比 major（要读盘）便宜得多
VSZ / RSS虚拟内存大小 / 实际驻留物理内存ps 的 VSZ 大不代表占内存，RSS 才接近真实
NUMA多路 CPU 各自挂本地内存，跨节点访问更慢数据库、JVM 大堆场景要绑核绑内存

TLB 为什么重要？一个 4 级页表，一次 TLB miss 要走 4 次内存访问才能拿到物理地址。程序如果有良好的局部性，TLB 命中率高，几乎无感；如果随机访问一大片内存（比如哈希表 key 分散、指针追逐），TLB 会疯狂 miss，性能可能掉一半。这也是「数组比链表快」的底层原因之一——不只是缓存预取，还有 TLB。

# 看缺页和换页
/usr/bin/time -v ./yourapp        # 输出里的 Major/Minor page faults
ps -o pid,vsz,rss,comm -p 12345
cat /proc/12345/status | grep -E 'VmPeak|VmSize|VmRSS|VmSwap'

# 大页：减少页表层级和 TLB 压力（默认策略各系统不同）
grep -i huge /proc/meminfo
cat /sys/kernel/mm/transparent_hugepage/enabled

# NUMA 视角：这个进程的内存分布在哪些节点上
numactl --hardware
numastat -p 12345

NUMA 值得单独提一句：双路服务器上，CPU0 访问挂在 CPU1 上的内存，延迟可能是本地的一倍多，带宽也更低。所以高性能服务会做绑核 + 本地内存分配。这个问题在容器里更隐蔽——你以为拿到的是 4 核，实际上可能是跨两个 NUMA 节点的 4 个超线程。

别把 VSZ 当内存占用。一个 JVM 进程 VSZ 几十 G 很常见，那是虚拟地址预留（堆的保留区、mmap 的库），实际 RSS 可能只有几 G。判断内存压力看 RSS 和 available，看 VSZ 只会吓到自己。

面试落点：「虚拟内存给了隔离和超额分配，代价是每次访问要查页表，靠 TLB 缓存。TLB miss 多的时候，随机访存的程序会明显变慢。多路机器上还有 NUMA，跨节点访问内存延迟更高，所以大内存服务会考虑绑核。」

模块 9

一条追问链：从「线程池开多大」问到内核

这是本篇最该背下来的一段，因为它把上面所有知识串成了一条线。面试官很可能就是这么一路问下去的。

问：线程池开多大？答：CPU 密集型大致取核数 + 1（留一个补位，防止某个线程缺页时 CPU 空转）；IO 密集型按等待比例放大，经验式是 N × (1 + 等待时间 / 计算时间)，但这个式子只是起点，必须压测。
追问：为什么不能直接开 1000 个？答：三类成本。栈内存（每线程 MB 级虚拟预留）、调度开销（就绪线程多，时间片变短、缓存局部性变差）、锁竞争（临界区争抢让上下文切换反而增加）。开太多吞吐不升，P99 先崩。
追问：IO 密集为什么可以多开？答：因为线程大部分时间在等，CPU 是空闲的。多开的意义是「让等待重叠起来」，把 CPU 的空档填满。但这是有上限的——等待本身不消耗 CPU，可线程的内存和切换要。
追问：那为什么不用协程？答：协程把每个并发单元的成本从 MB 降到 KB，同样内存能开更多。但它要求整条调用链都是非阻塞的，一个阻塞调用就会拖住整个线程。改造现有同步代码的成本很高。
追问：协程底层靠什么等 IO？答：靠 IO 多路复用。Go 的 netpoller 底层就是 epoll，协程发起网络读写时被挂起，epoll 通知就绪后再恢复。所以「协程」和「epoll」不是替代关系，是上下层。
追问：epoll 是 O(1) 吗？答：不是。注册是 O(log n)，取就绪是 O(k)。fd 全都活跃时它并不比 poll 快。它对普通文件也无效，因为文件永远就绪。
追问：那高并发下真正的瓶颈在哪？答：往往不在 IO 等待，而在下游。连接数上去了，数据库连接池、下游 QPS 配额、DNS 解析、TLS 握手 CPU，任何一环先到顶，前面的优化都白做。
nproc先确认核数，别拿 load 跟错误的基数比
ulimit -s单线程栈上限，直接决定「开一万个线程」在内存上是否可行
cat /proc/PID/status | grep Threads这个进程实际开了多少线程，跟线程池配置对不对得上
ss -tanp | grep -c ESTAB机器上现在有多少条已建立的连接，判断并发量级
strace -f -e trace=network,epoll_wait -p PID看线程停在 read 上还是 epoll_wait 上，反推 IO 模型
# 用 Little's Law 反推需要的并发数，比拍脑袋靠谱
并发数 L = 到达率 λ × 平均停留时间 W
# 例：3000 QPS，单请求平均耗时 50ms → L = 3000 × 0.05 = 150
# 也就是说稳态下同时「在系统里」的请求约 150 个
# 线程池开到 500，多出来的 350 个线程大部分时间在等队列，不是在干活

这段推导在面试里非常好用，因为它把「开多大」从拍数字变成了算数字。注意 Little's Law 算的是稳态平均并发，不是峰值。峰值要考虑突发系数，还要留余量给慢请求——一个 5 秒的慢请求会占住一个线程 5 秒，这类长尾才是线程池被撑爆的真凶。

一句话收口：「线程池大小不是配置项，是一个关于等待比例的估算，估算完必须用压测验证；验证的时候看的是 P99 和错误率，不是平均值。」
模块 10

9 个坑：说错一句就露底

这些是本篇里最容易被当成「常识」说错的点。面试官听到其中任何一句，都会顺着往下挖，而下面通常没有第二层。

1
「线程越多并发越高」
线程只是在等 IO 时能让出 CPU。等待不消耗 CPU，但线程本身要占栈、要被调度。到某个点之后，加线程只会让 P99 更差。
2
「协程比线程快」
协程不会让计算变快，它让「挂起和恢复」变便宜。CPU 密集的任务用协程一点也不会更快，甚至因为调度器在用户态而略慢。
3
「epoll 是 O(1) 的」
取就绪是 O(k)，注册是 O(log n)。fd 全部活跃时它和 poll 的差距很小。这句话说出口，基本会被追着问到底。
4
ET 模式配阻塞 fd
ET 要求一次读到 EAGAIN，阻塞 fd 的最后一次 read 会永远等下去，整个事件循环卡死。这个 bug 在低峰期才复现，极难定位。
5
把「非阻塞」当成「异步」
非阻塞只解决第一阶段（不等数据就绪），第二阶段的数据拷贝仍然是同步的。真正异步是内核拷完再通知。
6
「我们用了 epoll，所以是异步 IO」
IO 多路复用属于同步 IO 模型。它把等待集中了，但没有把拷贝交给内核。这句话是面试里最常见的概念混淆。
7
「sendfile 就是零拷贝，一次拷贝都没有」
DMA 拷贝始终存在。sendfile 省掉的是「内核 → 用户」那次 CPU 拷贝，网卡支持 SG-DMA 时 CPU 拷贝才能降到 0。
8
「page cache 占内存是浪费，应该清掉」
它是可回收的，而且承担了合并写的职责。清掉只会让后续读全部打回磁盘，制造一次延迟抖动。
9
「write 返回成功就是写进磁盘了」
write 只写到 page cache。要持久化必须 fsync，而 fsync 的代价是一次真实的磁盘等待——所有持久化设计都在跟这个代价做交易。

面试落点：这 9 条的共同点是「把机制记成了结论」。面试官顺着任何一条往下问一层，就到底了。所以准备的时候不要背结论，要能画出那条链路——比如从 write 到磁盘，中间有几层缓存、几次拷贝、谁在什么时候把数据刷出去。

自测

六道题

1. 同一进程内的两个线程，下面哪一项是各自独立的？
正确答案：栈和寄存器上下文。线程共享地址空间（含堆）、fd 表、工作目录和信号处理函数，但每个线程必须有独立的栈来存放自己的调用链和局部变量，切换时也要保存各自的寄存器。所以线程里的局部变量天然不共享。
2. 使用 epoll 的边缘触发（ET）模式，必须满足的条件是？
正确答案：非阻塞 + 读到 EAGAIN。ET 只在状态变化时通知一次，没读完也不会再提醒，所以必须一次把数据读干净；而「读到没有为止」这个循环只有在非阻塞 fd 上才会返回 EAGAIN，阻塞 fd 会在最后一次 read 上永远挂住。
3. select 的 1024 个 fd 上限，根本原因是？
正确答案：fd_set 是固定长度位图。这个上限来自用户态与内核态之间传递的数据结构大小，改它要重新编译程序。进程能打开多少文件由 ulimit -n 决定，和 select 的限制是两回事。
4. 相比 read + write，sendfile 省掉的是哪一次拷贝？
正确答案：内核到用户的那次 CPU 拷贝。sendfile 让数据全程留在内核态，应用不参与搬运，所以省掉了「内核 → 用户 → 内核」这个往返中的第一段。页缓存到 socket 缓冲区那次拷贝在网卡不支持 scatter-gather 时仍然存在；两次 DMA 始终存在。
5. 为什么说 IO 多路复用（epoll）属于同步 IO？
正确答案：拷贝阶段仍由应用完成。同步/异步的分界线在第二阶段：数据从内核缓冲区到用户缓冲区由谁来做。epoll 解决的是「等哪个 fd 就绪」，read 那一步仍然是同步阻塞的拷贝，所以它属于同步 IO（准确说是同步非阻塞 + 多路复用）。
6. 一个服务 QPS 3000、单请求平均耗时 50ms、以 IO 等待为主。用 Little's Law 估算，稳态下同时「在系统里」的请求大约是？
正确答案：150 个。L = λ × W = 3000 × 0.05 = 150。这个数说明稳态平均只有 150 个请求同时存在，线程池开到 500 意味着大部分线程在排队而不是在干活。注意它算的是平均值，峰值和长尾请求要另外留余量。
