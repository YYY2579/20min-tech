网络排障 12 个经典现象：从「ping 得通」到「就是打不开」

同一句「网络不通」，可能是 DNS、防火墙、MTU、回程路由、TLS 里的任意一层。先分层，再动手。

读之前先想一个你遇到过的「打不开」：当时你下的第一个命令是什么，它证明了什么？
开始前

「打不开」这三个字，能拆出十二种病

用户说「网站打不开」，你 ping 一下域名，通了，于是回一句「网络没问题，你清下缓存」。这句话在运维岗上是很危险的——ping 通只证明 ICMP 能来回，别的什么都不能证明。

同一个「打不开」，往下拆至少有十二种可能：DNS 解析到了错的 IP、端口没监听、防火墙 DROP 了包、安全组只放行了一半、MTU 太大被中间设备吞掉、回程路由走了另一条路、TLS 证书过期、代理环境变量指向一个早就下线的 squid、上游服务 502、网关等上游超时、客户端自己先超时断开，以及最容易被忽略的——十分钟前有人改了一个配置。

你看到的最容易得出的错误结论实际上它只证明了
ping 域名通网络没问题ICMP 到那个 IP 能往返。DNS 可能解析到了旧 IP，端口可能没开，TLS 可能失败
telnet 端口通服务正常三次握手成功，有人在这个端口 listen。应用可能返回 500，也可能 accept 了不处理
curl 返回 200用户那边也没问题你这台机器、这个时刻、这条路径是通的。用户可能在另一个省、走另一个出口、带着另一个 Cookie
这篇的组织方式：先给一套五层排查法，把「打不开」压成一道选择题；然后把 12 个现象按层分组，每个现象给「长什么样、先敲什么、看到什么就定性」；接着是抓包三步和一张现象对照表；最后讲变更类故障该先回滚还是先查。每一节都落一句面试话术。

面试落点：「用户说打不开，我不会先 ping。我会先问三件事：只有他一个人还是所有人都这样、换网络（4G）是否复现、什么时候开始的。这三问能把范围从『整个系统』缩小到『某条路径』或者『某个客户端』，然后再分层验证。」

模块 1

五层排查法：每层都要拿到一个能证伪的证据

分层不是为了画得好看，是为了让每一层都有一个明确的「通过/不通过」判据。没有判据的检查等于没检查——比如「我看了一下防火墙，好像没问题」，这句话在故障复盘里毫无价值。

层要回答的问题证据（命令）通过的标准
链路网卡通不通、有没有物理错误ip -s link、ethtool eth0UP 状态、RX/TX errors 不增长
IP地址对不对、路由走到哪、能不能到对端ip addr、ip route get、ping、mtr路由命中预期下一跳，ICMP 往返
端口对端有没有监听、包有没有被拦ss -lntp、nc -zv、nft list ruleset握手能完成，或被明确拒绝（RST）
协议MTU 合不合适、有没有重传、TLS 能不能协商ping -M do、nstat、openssl s_client大包能过、重传率正常、握手成功
应用服务返回什么、慢在哪一段curl -w、应用日志、链路追踪状态码正确、各阶段耗时在预算内

顺序上还有一个更实用的技巧：先近后远。先看发起方本地——DNS 解析对不对、hosts 有没有写死、代理变量有没有设、本机路由表正不正常；再看服务端——进程在不在、端口监听在哪个地址、负载高不高；最后才看中间——负载均衡、安全组、NAT、专线。理由是前两类你能自己改，中间那类要拉人。

另一条经验是双向验证。任何「不通」都要问一句：是去程不通，还是回程不通？只在一端抓包，看到包发出去了就断定「对端没回」，这个结论是不成立的——包可能到了对端，只是回程被丢了。

# 一条命令看清「我这张网卡、这个目标、走哪条路、源地址是谁」
ip route get 10.0.0.12

# 逐跳看：哪一跳开始丢包、哪一跳延迟突然抬高
mtr -n -c 20 10.0.0.12

# 端口探测：-z 只探测不发送数据，-v 打印结果，-w 超时
nc -zv -w 3 10.0.0.12 8080

# 本地监听情况：看清绑的是 0.0.0.0 还是 127.0.0.1
ss -lntp | grep 8080
别把「能 ping 通」当成「网络正常」的同义词。很多云环境对 ICMP 单独限速甚至不放行，ping 不通但业务正常的情况非常普遍；反过来 ping 通而业务全挂也每天都在发生。ICMP 只是一条独立的小路，它通不通和 TCP 那条路的关系很弱。

面试落点：「我按链路、IP、端口、协议、应用五层走，每一层都要给出一个可证伪的结论。顺序上先看发起方本地，再看服务端，最后看中间设备，因为前两段我自己能改。任何不通我都会确认是去程还是回程，只在一端抓包得出的结论不算数。」

模块 2

现象 1-3：通与不通之间的三种灰度

这三个现象在值班群里的描述几乎一模一样——「连不上」。但它们的成因、命令、修复动作完全不同，混在一起就只能靠猜。

ping 通、端口不通
先看服务绑的是哪个地址。127.0.0.1 和 0.0.0.0 是两个世界，前者只有本机能连。
被拒 vs 超时
拒绝说明包到了、对端不认；超时说明包没了。一个查服务，一个查网络。
同机通、跨机不通
绑定地址、协议族、本机防火墙、网络策略、路由，五选一，顺序别乱。

现象 1：ping 通，端口不通

最常见的原因是绑错地址：服务监听在 127.0.0.1:8080，本机 curl 通，外部连不上。这不是防火墙问题，是应用配置问题。第二种是防火墙 DROP，表现为超时而不是拒绝。第三种是上游安全组只放行了 ICMP 没放行 TCP——很多云主机的默认规则就是这样。

# 在服务端确认绑在哪个地址（0.0.0.0 和 :: 才是对外）
ss -lntp | grep 8080
# LISTEN 0 128 127.0.0.1:8080   <-- 只有本机能连
# LISTEN 0 128 0.0.0.0:8080     <-- 所有 IPv4 地址
# LISTEN 0 128 [::]:8080        <-- IPv6，是否兼 IPv4 取决于 net.ipv6.bindv6only

# 从客户端探测，区分「拒绝」和「超时」
nc -zv -w 3 10.0.0.12 8080
# 立刻返回 refused        → 包到了，没人监听或防火墙 REJECT
# 卡满 3 秒 timeout        → 包被丢了，路由/安全组/DROP 规则

# 服务端看规则（nft 与 iptables 在前端可能是同一套）
nft list ruleset 2>/dev/null | head -40
iptables -S 2>/dev/null | head -40

现象 2：连接被拒（RST）和连接超时，是两个世界

这条区分极其重要，因为它直接决定你下一步去哪。RST 意味着包到达了对端协议栈——路径是通的，是对端主动说「我不认这个连接」。原因通常是端口没监听、连接已被回收（服务重启过）、或者防火墙配了 reject-with tcp-reset。超时意味着包消失了——中间有设备 DROP、路由不可达、安全组没放行、或者回程不通。

客户端看到包到没到对端优先怀疑下一步
Connection refused到了端口没监听、进程挂了、绑了 127.0.0.1服务端 ss -lntp，看进程和绑定地址
Connection timed out没到（或被静默丢）安全组、iptables DROP、路由黑洞、回程不通两端抓包，确认包在哪一跳消失
Connection reset by peer到了，且连接曾建立对端进程崩溃、连接被中间设备清表、复用了已关闭的长连接看对端有没有重启、LB 的空闲超时
No route to host没到本机没有匹配路由，或收到 ICMP 主机不可达ip route get 确认下一跳

现象 3：同机通，跨机不通

同一台机器上 curl localhost:8080 正常，从另一台机器连就失败。这条的排查路径非常固定：绑定地址 → 监听协议族 → 本机防火墙 → 网络策略 → 路由。容器环境还要多一层：端口有没有映射出来、映射到了哪个地址、宿主机上的 DNAT 规则在不在。

一个容易漏的点：[::]:8080 看起来是 IPv6，但在多数 Linux 默认配置下同时接受 IPv4 映射地址。反过来，如果应用只绑了 IPv4 的 0.0.0.0，客户端用 IPv6 地址连就会失败——而 DNS 可能同时返回 A 和 AAAA 记录，客户端优先选哪个由系统决定，这就是「有的人能打开、有的人打不开」的一种来源。

# 容器场景：端口映射和宿主机规则
docker port myapp
iptables -t nat -S | grep 8080

# 看某个端口上到底有没有包进来（先抓再连，别反过来）
tcpdump -i any -nn -c 5 'tcp port 8080 and host 10.0.0.5'

面试落点：「连接被拒和连接超时我一定分开说。拒绝说明包到了、对端不认，去查监听和绑定地址；超时说明包被丢了，去查安全组、防火墙和路由。这两个现象混着说，等于承认自己没看抓包。」

模块 3

现象 4-6：慢、丢、卡在大包上

「能打开但很慢」比「完全打不开」更难查，因为它没有明确的失败点。这时候需要的不是更多工具，而是把一个请求切成几段分别计时。

现象 4：curl 很慢，慢在哪一段

一个 HTTPS 请求至少要经历 DNS 解析、TCP 握手、TLS 握手、服务端处理（TTFB）、内容传输五段。curl -w 能把每一段的累计时间打出来，两两相减就是这一段的耗时。这是整篇里最值得背下来的一条命令。

curl -o /dev/null -s -w '
  dns   %{time_namelookup}
  tcp   %{time_connect}
  tls   %{time_appconnect}
  ttfb  %{time_starttransfer}
  total %{time_total}
  code  %{http_code}
' https://example.com/api/health

# 各段耗时 = 后一个减前一个：
# DNS   = time_namelookup
# TCP   = time_connect - time_namelookup
# TLS   = time_appconnect - time_connect
# TTFB  = time_starttransfer - time_appconnect
# 传输  = time_total - time_starttransfer
哪一段大说明什么往下查
DNS 段解析慢，或者解析失败后在重试dig +stats 看查询耗时；换 @8.8.8.8 对比；查 resolv.conf 的 timeout/attempts
TCP 段握手 RTT 大，或者 SYN 在重传同地域应该在毫秒级；跨地域按物理距离算；异常大就查丢包和路由
TLS 段证书链太长、要多次往返、或者 OCSP 拉取超时openssl s_client 看握手轮次和证书链
TTFB 段服务端在算，或者上游慢应用日志、慢查询、下游依赖耗时
传输段响应体大，或者带宽受限看压缩有没有开、是不是在下大文件

一个特别常见的误判：DNS 段看起来只有 20ms，觉得很正常——但如果每次请求都花 20ms 解析，而连接池本来可以省掉这 20ms，那在 QPS 高的服务里就是实打实的浪费。所以「慢不慢」要跟这条链路的理论下限比，不是跟「感觉」比。

现象 5：丢包，但要先分清丢在哪

丢包至少有三个层次：物理/链路层（网卡、光模块、线路误码）、队列层（网卡 ring buffer 满、qdisc 丢弃、conntrack 表满）、策略层（安全组、限速、清洗设备）。它们都表现为「丢」，但修法完全不同。

# 1. 链路层有没有错
ip -s link show eth0
ethtool -S eth0 | grep -iE 'drop|err|miss|fifo|discard'

# 2. 内核协议栈的丢弃计数（这些比 ping 的丢包率精确得多）
nstat -az | grep -iE 'InDrops|InCsumErrors|TCPBacklogDrop|ListenOverflows|TCPTimeouts|RetransSegs'

# 3. 队列和限速
tc -s qdisc show dev eth0
cat /proc/sys/net/netfilter/nf_conntrack_count
cat /proc/sys/net/netfilter/nf_conntrack_max

# 4. 路径上哪一跳开始丢
mtr -n -c 50 10.0.0.12

判断方法：看计数器的增量，不看绝对值。机器跑了半年，丢包计数是几千，和「每分钟涨几百」完全是两回事。另外，间歇性失败要区分「固定比例」（更像丢包或限速）和「特定时间点」（更像定时任务、连接池轮换、证书检查）。

现象 6：MTU 黑洞，小包通大包不通

这是最像「玄学」的一类：TCP 三次握手成功（包很小），登录成功，执行一个返回大量数据的命令就卡住；小接口正常，返回大 JSON 的接口超时。典型的 MTU 黑洞。

机制是这样的：路径上某一段的 MTU 比两端小（隧道封装、PPPoE、VPN 都会吃掉几十字节）。发送方发了大包，且设置了「不允许分片」（DF 位）。中间设备本该回一个 ICMP「需要分片」，但如果这个 ICMP 被防火墙拦了，发送方永远收不到通知，就会一直重传那个大包，直到超时。

# 以太网 MTU 1500 时，1472 + 8(ICMP) + 20(IP) = 1500
# -M do 表示设置 DF 位，不允许分片
ping -M do -s 1472 -c 3 10.0.0.12

# 逐步缩小包长，找到能通过的最大值
ping -M do -s 1400 -c 3 10.0.0.12
ping -M do -s 1200 -c 3 10.0.0.12

# tracepath 会顺带做路径 MTU 探测
tracepath -n 10.0.0.12

# 看本机各接口的 MTU
ip link show | grep -E 'mtu|state'

修复方式有三条路：调小两端的 MTU（治本但不一定两边都能改）、在隧道网关上做 MSS clamping（把握手里通告的 MSS 改小，让发送方一开始就不发大包）、或者放行 ICMP 类型 3 代码 4（让 PMTU 发现能正常工作）。第三条最容易被忽略，也最容易在「安全加固」之后突然出现。

面试落点：「『慢』我一定先用 curl -w 分段，DNS、TCP、TLS、TTFB 四段分别看，不猜。『小包通大包不通』我第一反应是 MTU 黑洞，用 ping -M do 逐步缩小包长验证，根因往往是隧道封装加上 ICMP 被拦。」

模块 4

现象 7-9：502 / 504 / 499 的分水岭

这三个码在监控面板上长得像一家人，处理方向却完全不同。答错归属，你会去查一个根本没问题的组件。

状态码谁产生的字面含义实际在说
502网关（Nginx / LB）Bad Gateway我连上了上游，但收到的响应无法解析，或者连接直接被上游重置/拒绝
503网关或应用Service Unavailable我没有可用的上游（全被摘了）、或者我主动限流/维护
504网关Gateway Timeout我连上了上游，发了请求，但在超时时间内没等到响应
499Nginx（自定义）没有标准含义客户端在 Nginx 返回响应之前，自己把连接关了

看清这张表的关键是「谁写的这个码」。502 和 504 是网关替上游「代言」，所以日志在网关侧，但根因可能在上游；499 是网关记录「客户端跑了」，所以它几乎总是客户端的超时时间比服务端短的结果，而不是服务端的错。

现象 7：502 集中在发布之后

如果 502 只在发布窗口出现，八成是连接复用 + 上游重启：网关和后端之间是长连接，后端进程重启，旧连接在网关的连接池里还被认为是可用的，请求发过去吃到 RST，网关就记一个 502。解决办法是在上游优雅退出时先摘流量、等在途请求结束，或者让网关对幂等请求做一次重试。

如果 502 是常态，按这个顺序查：上游进程活着吗（ss -lntp）→ 网关到上游的地址和端口对不对（很多事故是 upstream 里写了旧 IP）→ 协议对不对（上游是 HTTPS 但配了 http，或者反过来）→ 请求头是不是太大（超了上游的缓冲限制）→ 上游有没有主动 reset（比如 body 太大、超时后直接关连接）。

现象 8：504 说明上游「慢」而不是「死」

504 的价值在于它把范围缩到了「上游处理时间 > 网关超时」。接下来要回答的是：上游真的慢，还是网关的超时设得太短？先直连上游绕过网关测一次，这一步能把责任分清楚。

# 绕过网关，直接打上游，看它到底多慢
curl -o /dev/null -s -w 'code=%{http_code} ttfb=%{time_starttransfer}\n' \
  http://10.0.0.21:8080/api/slow

# Nginx 侧：哪些超时参数在起作用（名字以你的版本为准）
# proxy_connect_timeout  连上游的超时
# proxy_send_timeout     发请求给上游的超时
# proxy_read_timeout     等上游响应的超时（504 多半是它）
nginx -T 2>/dev/null | grep -E 'proxy_(connect|send|read)_timeout'

# 看 upstream 的响应时间分布（需要在 log_format 里加 $upstream_response_time）
awk '{print $NF}' /var/log/nginx/access.log | sort -n | tail -20

现象 9：499 是客户端先跑了

499 不是 HTTP 标准状态码，是 Nginx 自己的约定。它出现说明：请求已经到达 Nginx，Nginx 转发给了上游，但在上游返回之前，客户端断开了。最常见的成因是客户端的超时时间小于服务端的处理时间。

所以看到 499 不要急着说「客户端有问题」。要问的是：为什么这个接口要处理这么久？是慢查询、是下游依赖、还是重试放大？499 常常是 504 的前兆——客户端等不及先断了，网关还在等上游，最后自己记一个 504。

别把 499 当成「客户端网络差」。如果 499 集中在某一个接口，那基本可以断定是这个接口慢；如果分散在所有接口，才去看客户端侧的超时配置、移动网络切换、或者中间设备的空闲超时。这两种情况的处理方向完全相反。

面试落点：「502 是网关收到了无效响应或连接被上游重置，504 是网关等上游超时，499 是客户端提前断开。前两个日志在网关、根因可能在上游，499 则要看是不是接口本身太慢。判断归属看是谁写的这个码，不看谁在报错。」

模块 5

现象 10-12：单向、TLS、代理变量

这三个现象共同的特点是「配置看起来都对」。它们不是漏配，而是配了但语义不对，或者环境变量在某个看不见的地方生效了。

现象 10：单向不通，去得回不来

判断方法很直接：两端同时抓包。A 端看到 SYN 发出、B 端没收到，问题在去程；B 端收到了、回了 SYN-ACK、A 端没收到，问题在回程。一句话就能把范围砍一半。

回程不通的常见原因：策略路由（源地址选路选错了出口）、非对称路由（去走专线回走公网，状态防火墙把回包当非法）、云环境的网络 ACL（无状态，需要双向放行，而安全组是有状态的，只需放入方向）。「安全组是有状态的」这一点经常被忘记，导致有人明明放行了入方向却还在查出方向。

# A 端抓（假设客户端 10.0.0.5，服务端 10.0.0.12）
tcpdump -i any -nn -c 20 'host 10.0.0.12 and tcp port 8080'

# B 端同时抓，然后对比两边的第一行时间戳
tcpdump -i any -nn -c 20 'host 10.0.0.5 and tcp port 8080'

# 看本机选的是哪个源地址、走哪个出口
ip route get 10.0.0.12 from 10.0.0.5

# 策略路由规则
ip rule show
ip route show table all | head -30

现象 11：TLS 握手失败

TLS 失败的信息量其实很大，只是很多人被一长串报错吓住了。按报错归类，基本就五种：证书过期、域名不匹配、证书链不完整、协议/套件不匹配、客户端时间不对（是的，时间不对会导致证书「还没生效」）。

# -servername 一定要带，否则 SNI 缺失，拿到的可能是默认站点的证书
openssl s_client -connect example.com:443 -servername example.com -showcerts < /dev/null

# 只看关键信息
openssl s_client -connect example.com:443 -servername example.com < /dev/null 2>&1 \
  | openssl x509 -noout -subject -issuer -dates

# 用 curl 看协商结果和证书链
curl -vI https://example.com 2>&1 | grep -E 'SSL|TLS|subject|issuer|expire'
报错关键词含义处理
certificate has expired证书过期换证书，同时把到期告警提前到 30 天
unable to get local issuer certificate链不完整，服务端没发中间证书在服务端配置里补上中间证书，顺序是叶证书在前
certificate verify failed根证书不在客户端信任库，或者被中间人替换先确认是不是自签/内部 CA，再确认信任库
wrong version number用 HTTPS 打了 HTTP 端口，或者反过来确认端口和协议，这个错和证书无关
handshake failure协议版本或加密套件没有交集看两端的 min version 和 cipher 配置

「链不完整」这一条值得单独说：浏览器往往能靠证书里的 AIA 地址自动补齐中间证书，所以「浏览器能打开」不代表链是完整的；而 Java、curl、某些移动端 SDK 不会去补，就会直接失败。「浏览器正常、App 报证书错误」是链不完整的经典信号。

现象 12：代理环境变量，看不见的手

同一个脚本，在你的终端跑得通，在 CI 里超时；curl 报连不上，ping 却通。查半天网络，最后发现是 https_proxy 指向了一个早就下线的代理。

# 大小写都要看：不同工具读的变量名不一样
env | grep -iE 'proxy|no_proxy'

# curl 会告诉你它有没有走代理
curl -v https://example.com 2>&1 | grep -iE 'proxy|connect to'

# 强制不走代理，用来对比
curl --noproxy '*' -v https://example.com

# systemd 服务不继承 shell 的 export，要单独配
systemctl show myapp -p Environment

几个坑：Java 默认不读 http_proxy，它读的是 -Dhttp.proxyHost 这类系统属性；systemd 启动的服务不继承你在 shell 里 export 的变量，要写进 unit 的 Environment 或者 EnvironmentFile；容器会继承构建时的环境变量，镜像里带了一个代理配置，跑到生产就全走代理了；no_proxy 的语法各家不同，有的支持 CIDR 有的不支持，写 *.internal 还是 .internal 要看具体工具。

面试落点：「单向不通我会两端同时抓包，看第一行包在哪边消失，这样能立刻分清去程还是回程。TLS 失败我先跑 openssl s_client 带 SNI，看是证书、链、还是协议版本的问题。代理的问题先 env | grep -i proxy，再确认这个进程到底有没有继承到这些变量。」

模块 6

抓包定位三步：在哪抓、抓什么、看什么

抓包这件事，90% 的失败发生在「抓之前」——抓错了网卡、过滤条件写宽了、只抓了一端。真正打开分析的时候，面对几千行，人是会放弃的。

定抓点。请求路径上有几个可能的观察点：客户端网卡、负载均衡、服务端网卡、容器内的 veth。至少选两个，才能判断「包在哪一段消失」。只有一个抓点，你只能得到「我这边看到了什么」，得不到结论。
定过滤。host + port 精确到一条流，别用 tcp 这种宽条件。同时限包数（-c）和时长（timeout），把结果落文件（-w）而不是刷屏。
定判读顺序。握手是否成对（S / S. / .）→ 谁先发 RST 或 FIN → seq 有没有重复（重传）→ 窗口有没有变 0 → len 是否和预期一致。这五问走完，大部分问题已经有答案。
# 一条流、限 500 包、完整包长、落文件
timeout 30 tcpdump -i eth0 -nn -s 0 -c 500 \
  'host 10.0.0.12 and tcp port 8080' -w /tmp/flow.pcap

# 容器里抓：先找到容器在宿主机上的 veth
ip link | grep -A1 veth
nsenter -t $(docker inspect -f '{{.State.Pid}}' myapp) -n tcpdump -i eth0 -nn -c 50

# 回看时先统计，再看明细
tcpdump -r /tmp/flow.pcap -nn -q | awk '{print $1}' | sort | uniq -c | sort -rn | head

# 只看 RST 和重传
tcpdump -r /tmp/flow.pcap -nn 'tcp[tcpflags] & tcp-rst != 0'
抓到的样子结论
只有 [S]，没有 [S.]对端没收到，或者收到了但没回。去对端抓，看有没有收到
有 [S.] 但没有第三次 [.]回程丢了，或者客户端不认这个 SYN-ACK
握完成后立刻 [R]服务端进程没监听、或者 accept 队列满后连接被回收
同一个 seq 反复出现重传。看间隔是 RTO 退避（1s、2s、4s）还是快速重传
窗口一直是 0接收方应用读得慢，不是网络问题
len 远小于 MSS 且频繁应用写得碎，Nagle 和延迟 ACK 在互相等
抓包本身的三个副作用：高 PPS 下 tcpdump 会丢包（结尾会打 "packets dropped by kernel"），此时结论不可信；-s 0 抓全包会显著增加磁盘和内存占用，几十秒就能写出几个 G；容器/云环境里抓到的地址可能是 NAT 之后的，别拿它去和业务日志里的客户端 IP 对。

面试落点：「我抓包一定抓两个点，不然没法判断包在哪一段消失。过滤条件精确到一条流，限时长限包数。判读按握手、RST、重传、窗口、长度五个问题走，不逐行读。」

模块 8

变更类故障：先回滚还是先查

这类故障最好判断，也最容易吵起来。「刚发完版就挂了，先回滚还是先查根因？」——这不是价值观问题，是一道有明确判据的选择题。

判据有三条，按顺序问：影响面在不在扩大？回滚成本有多高？回滚能不能真的撤销这次变更？

情况动作理由
影响面在扩大（错误率还在涨）先止损，回滚或摘流量根因可以事后查，用户流失不可逆
变更是明确的、可回滚的（镜像、配置）先回滚，保留现场回滚只要两分钟，查根因可能要两小时
变更不可逆（数据迁移、证书替换、DDL）先查，同时准备降级方案回滚可能造成数据不一致，比故障更麻烦
不确定是不是变更引起的先对比，再决定用 diff 和指标对比代替猜，五分钟能定性

「保留现场」这四个字经常被说成空话，具体是四件事：存一份当前配置（nginx -T、kubectl get -o yaml）、抓一次包或存一次线程栈、记下时间点（后面要跟监控对齐）、记下回滚前的版本号。这四件事加起来不超过三分钟，但能让复盘从「凭记忆」变成「看证据」。

# 配置有没有被改过（对比备份或版本库）
diff -u /etc/nginx/nginx.conf.bak /etc/nginx/nginx.conf

# K8s：看这次发布改了什么、能不能退回去
kubectl rollout history deployment/myapp
kubectl rollout undo deployment/myapp

# 证书什么时候到期（变更类故障的高频原因）
openssl x509 -in /etc/ssl/cert.pem -noout -enddate

# DNS 改过没有：对比两个解析器的结果
dig +short @10.0.0.2 example.com
dig +short @8.8.8.8 example.com

还有一个反直觉的经验：变更类故障里，真正「改错了」的比例没有想象中高，更多是「改对了但没改全」——只改了一台机器、只改了一个集群、只改了应用没改网关、灰度只放了 1% 就以为全量生效。所以第一个动作往往不是回滚，而是确认变更的实际覆盖范围：哪些实例拿到了新配置，哪些还是旧的。这种「新旧混跑」的状态，比一个纯粹的错误配置更难查。

一个实用习惯：任何变更前，把「怎么验证成功」和「怎么回滚」写成两行贴在工单里。写不出来，说明这次变更不该发。这比任何流程规范都有效，因为它逼你在动手前想清楚退路。

面试落点：「先回滚还是先查，我看三件事：影响面在不在扩大、回滚成本高不高、这次变更可不可逆。可逆且在扩大的，先回滚再查；不可逆的，先查同时准备降级。回滚前我会花三分钟存配置、抓一次现场、记下版本号，不然复盘的时候全靠回忆。」

模块 9

9 个坑：每一条都会让你多查两小时

网络排障的坑有个共同特征：它们不会让你得出错误答案，而是让你在一个错误的方向上非常努力。两小时后你精疲力尽，问题还在。

1
ping 通就宣布网络没问题
ICMP 和 TCP 走的是同一张路由表，但策略、限速、防火墙规则可以是分开的。ping 通只能证明「有去有回」，端口、TLS、应用层全都没被验证。
2
把「连接超时」和「连接被拒」当成一回事
拒绝说明包到了对端（路径通、策略放行），超时说明包没了（被丢或被拦）。一个查服务，一个查网络，方向完全相反。
3
只看 ping 的丢包率判断链路质量
ICMP 常被单独限速，ping 的丢包率和 TCP 的实际重传率可以差一个数量级。要看 nstat 的 RetransSegs 和 InDrops。
4
curl 慢就直接怀疑服务端
不分局段就没法定位。DNS 慢、TCP 握手慢、TLS 慢、TTFB 慢，四种情况的负责人完全不同。先用 -w 把时间切开。
5
遇到大包卡住就去调应用缓冲区
「小包通、大包不通」几乎就是 MTU 黑洞的签名。用 ping -M do 逐步缩小包长，两分钟能验证，比翻代码快得多。
6
看到 502 就去重启上游
502 可能是协议配错（http 打 https）、upstream 里写了旧 IP、请求头超限、或者连接池复用了已经关闭的长连接。重启只是把症状推迟。
7
只在一端抓包就下结论
「我这边发出去了，对端没回」——这个结论需要两端都抓才能成立。回程可能走了另一条链路，也可能在容器环境里根本没经过你抓的网卡。
8
忘记代理和 hosts 这两个隐形配置
「只有我这台机器不行」时，先看 env 里的 proxy 和 /etc/hosts。这两个东西的优先级比你想的高，而且经常是半年前某次临时排查留下的。
9
故障还在扩大就开始查根因
根因可以事后查，用户流失不可逆。先止损（回滚、摘流量、限流），把现场留下来，再坐下来分析。这两件事不冲突，只是有先后。

面试落点：这 9 条里挑一条讲，结构固定：当时的判断、造成的后果、后来改成了什么。第三段决定面试官认为你是「踩过坑」还是「长了记性」。

自测

六道题

1. 本机 curl 127.0.0.1:8080 正常，从另一台机器连 10.0.0.12:8080 报 Connection refused。最可能的原因是？
正确答案：只监听 127.0.0.1。refused 说明包已经到达对端协议栈，只是那个地址端口上没有监听者。防火墙 DROP 会表现为超时；MTU 问题通常发生在数据阶段而不是建连阶段；DNS 错误则连 IP 都不对，不会是这个报错。
2. 客户端连一个端口，卡了 30 秒后报 timeout，而不是立刻 refused。这说明？
正确答案：包被丢了。refused 需要对方回 RST，前提是包到达了对方协议栈。超时意味着 SYN 没得到任何回应——中间设备 DROP、安全组未放行、路由黑洞、回程被拦，都会这样。这也是为什么这两个现象必须分开说。
3. curl -w 显示 time_connect=0.05、time_appconnect=0.60、time_starttransfer=0.65。慢在哪一段？
正确答案：TLS 握手。time_appconnect 减去 time_connect 是 0.55 秒，说明 TLS 阶段很慢，常见原因是证书链过长、需要多次往返、或者 OCSP 拉取超时。TTFB 段只有 0.05 秒，说明服务端处理很快。
4. 一个接口返回大 JSON 时超时，返回小 JSON 正常；TCP 握手成功。最应该先验证什么？
正确答案：验 MTU。「小包通、大包不通」是 MTU 黑洞的典型签名：路径上某段 MTU 更小，大包带 DF 位被丢弃，而本该回来的 ICMP「需要分片」又被防火墙拦了，发送方只能一直重传。用 ping -M do 缩小包长两分钟就能验证。
5. 网关日志里 502 和 504 同时出现，下面哪个判断是对的？
正确答案：都指向网关与上游之间。502 表示连接建立了但响应不可用（拒绝、重置、无法解析）；504 表示请求发出去了但等不到响应。两者的日志都在网关，根因可能在上游，所以下一步是绕过网关直连上游测一次，把责任分清楚。
6. Nginx 日志里出现大量 499，最合理的解读是？
正确答案：客户端先断开。499 是 Nginx 的自定义状态码，没有标准含义，记录的是「客户端关闭了连接，而我还没把响应发出去」。它通常意味着接口处理时间超过了客户端的超时阈值，所以要去查这个接口为什么慢，而不是查客户端网络。

术语表与下一步

术语一句话解释
RST复位包。收到它说明包到了对方，只是对方不认这个连接
DF 位IP 头里的「不允许分片」标志，MTU 探测靠它触发 ICMP 通告
PMTU路径最大传输单元，是整条路径上最小的那个 MTU，不是两端接口的 MTU
MTU 黑洞大包被丢弃且 ICMP 通告也被拦，发送方永远不知道要减小包长
MSS clamping在网关上改写握手报文里的 MSS，让发送方一开始就不发超过路径 MTU 的包
TTFBTime To First Byte，从发出请求到收到第一个字节，主要反映服务端处理时间
非对称路由去程和回程走不同的路径，状态防火墙可能把回包判为非法
SNITLS 握手中的服务器名称指示，一个 IP 挂多张证书时靠它选证书
证书链叶证书 → 中间 CA → 根 CA。服务端要发中间证书，否则部分客户端验证失败
499Nginx 自定义状态码，表示客户端在响应发出前主动断开
conntrack连接跟踪表，表满后新连接被静默丢弃，dmesg 里有明确提示
