模块 1

第一原则：先收敛，再定位

新手最常见的失败不是"不会用工具"，而是在问题还没定义清楚时就开始猜。三条铁律，按顺序执行。

铁律一：先稳定复现，再谈定位

一个不能复现的 bug，你对它做的任何修改都无法验证。所以第一步永远是把复现条件收敛到最小：删掉无关输入、无关配置、无关步骤，直到"少任何一个条件就不出问题"。

复现要素要问的问题为什么重要
输入哪一条数据触发的？能缩到多小？缩到最小后往往一眼能看出是哪个字段异常
环境哪个版本、哪台机器、什么配置？区分"代码 bug"和"环境差异"的唯一办法
时序必须先做什么再做什么？并发几个请求？竞态类问题只在特定交错顺序下出现
频率100% 必现？1/1000？有没有规律？决定后面用"断点"还是"埋点统计"
# 复现记录应该长这样，而不是"偶尔报错"
现象：下单接口返回 500，日志里 NullPointerException at OrderService.java:142
复现：用户 ID 尾号为偶数 + 优惠券已过期 → 100% 必现
不触发：优惠券未过期 / 用户无优惠券
版本：order-service 2.4.1（2.4.0 不复现）
结论：2.4.0 → 2.4.1 之间引入

铁律二：一次只改一个变量

同时改日志、改配置、重启服务、清缓存，然后问题消失了 —— 你不知道是哪个动作起的作用，下次还会复发。每次实验只动一个变量，并且先写下预期结果：如果我的假设成立，应该看到什么？看不到就说明假设错了。

可证伪的假设 vs 不可证伪的猜测：
✗ "可能是缓存的问题" —— 无法验证，也无法推翻。
✓ "如果是缓存脏了，那么清掉 user:42 这个 key 后立刻恢复正常" —— 能做实验，能出结论。

铁律三：别凭直觉猜，先看证据

经验的价值是帮你排出假设的优先级，不是替代验证。人脑对"最近见过的模式"有过拟合倾向：上周是连接池打满，这周所有问题看起来都像连接池。用数据打脸比用直觉赌要快。

直觉式排查证据式排查
凭印象改代码，改完重启试试先在关键路径打点，确认耗时分布，再决定改哪
一次改五处，总有一处是对的一次改一处，每处都能归因
修好了就收工，不写结论记录"根因 + 验证方式"，下次能直接查
一句话总结第一原则：把"我觉得"换成"我观察到"，把"应该是"换成"如果是，那么应该能测到"。调试的全部技术，都是为这句话服务的。
模块 2

日志调试：最便宜也最容易搞砸

日志是最通用的调试手段 —— 不需要暂停进程，不需要调试器权限，生产环境也能用。但它也是最容易变成噪音的地方。

该在哪加日志

位置打什么作用
函数入口 / 出口关键参数、返回值、耗时能直接看出"有没有进来""出去时是什么"
外部调用前后目标地址、请求 ID、耗时、状态码区分"我的问题"和"依赖的问题"
状态变更点变更前后的值定位"值是什么时候被改坏的"
分支决策点走了哪个分支、判据的实际值解释"为什么走了这条路"
异常捕获处完整堆栈 + 上下文不要只打 e.message，堆栈才是定位依据

不该在哪加日志

  • 循环体内：10 万次循环就是 10 万行日志，磁盘写满、日志系统被打爆，而且真正有用的那行被淹了。要打就打循环外的汇总（次数、耗时、异常计数）。
  • 超高频路径：网关、序列化、鉴权这类每秒几万次的代码，即使 DEBUG 级别也要谨慎。
  • Getter / toString：会被框架隐式调用，日志量和调用次数完全失控。
  • 含敏感信息处：密码、token、身份证、完整手机号。脱敏后再打，否则日志系统本身变成泄露源。
# 反例：在循环里打日志
for order in orders:
    logger.info(f"processing order {order.id}")   # ✗ 10 万行
    process(order)

# 正例：聚合后打一条
ok, failed, cost = 0, [], 0
for order in orders:
    try:
        process(order); ok += 1
    except Exception as e:
        failed.append((order.id, type(e).__name__))
logger.info("batch done", extra={"total": len(orders), "ok": ok,
            "failed": len(failed), "cost_ms": cost})
# 失败明细单独打，且限制条数
if failed:
    logger.warning("batch failures", extra={"sample": failed[:5]})

日志级别的语义边界

级别不是"重要程度"，是"谁该被叫醒"。定错了，要么告警疲劳，要么事故无人知。

级别语义线上应该有多少
ERROR需要人介入，功能已经不可用应该是 0 或个位数/天。持续有 ERROR 说明告警配置失效了
WARN异常但已自愈（重试成功、降级生效）少量。突然放量通常是大故障的前兆
INFO关键业务事实：订单创建、任务完成每条业务主流程 1~3 条。用来还原时间线
DEBUG排查用的细节，默认关闭线上通常关闭，需要时动态打开
TRACE逐帧级别的细节，几乎不用只在本地复现疑难问题时开
把异常吞掉只打 WARN 是最坏的实践。"catch (Exception e) { log.warn(...) }" 会让一个真实故障在监控里完全隐形 —— 接口已经在返回错误了，日志里却风平浪静。捕获后要么处理，要么 ERROR 并带上堆栈，不要静默降级。

结构化日志：让日志能被机器查

纯文本日志只能靠正则硬抠，字段一改就全废。结构化日志把上下文变成字段，日志系统就能按字段过滤、聚合、画图。

# 纯文本（难查）
2026-10-17 10:23:41 INFO 用户 42 下单成功，订单 9001，耗时 137ms

# 结构化（可查）
{"ts":"2026-10-17T10:23:41.238Z","level":"INFO","msg":"order created",
 "trace_id":"a3f9...","user_id":42,"order_id":9001,"cost_ms":137}

字段命名要统一，否则跨服务串不起来。工程上够用的最小集合是：

字段约定
trace_id贯穿一次请求的全链路 ID，跨服务透传。没有它就无法把多个服务的日志拼成一条时间线
level / ts / msg固定三件套。ts 用带毫秒的 ISO8601，且统一时区（建议 UTC）
service / instance哪个服务、哪个实例。多副本时定位到具体机器
cost_ms耗时统一用毫秒整数，不要混用秒和微秒
err / stack错误类型和堆栈分开存，方便按错误类型聚合计数
三条实操建议：① 高频路径用采样（例如每 100 次打 1 条 + 计数）；② ERROR 不采样，全留；③ 日志框架的"是否输出"判断要放在字符串拼接之前，否则参数序列化的开销白付。
模块 3

断点调试：把进程按暂停

日志回答"发生了什么"，断点回答"现在是什么状态"。能暂停进程，就能随意翻看任意变量、任意层调用栈 —— 这是日志做不到的。

五种断点，各有用途

类型什么时候用注意
行断点已经大致知道问题在哪一段最常用，但循环里会反复命中
条件断点只在特定输入下才出问题性价比最高，能把 10 万次循环收敛到 1 次
观察点 watchpoint不知道谁改坏了这个变量变量被写时自动停下，直接抓到凶手
异常断点异常被上层 catch 吞掉，看不到抛出点在异常抛出的瞬间停，而不是被捕获处
方法断点想知道谁调用了这个方法命中时先看调用栈，比读代码快
# gdb：条件断点 + 观察点
(gdb) break process_order if order->amount > 100000     # 只在大额订单停
(gdb) watch balance                                      # balance 被写时停
(gdb) catch throw                                        # C++ 异常抛出时停

# pdb：条件断点
(Pdb) break order.py:142, amount > 100000
(Pdb) break order.py:142, user_id == 42

# Java（jdb）
> stop at com.demo.OrderService:142
> stop in com.demo.OrderService.calc
> catch java.lang.NullPointerException
条件断点的表达式有副作用要小心。很多调试器允许在条件里调用函数，但如果那个函数会修改状态（比如 queue.pop()），断点本身就会改变程序行为 —— 你调试的已经不是原来那个程序了。条件里只做纯读取。

读调用栈：自下而上还是自上而下

栈是"谁调用了谁"。停住时，最上面一帧是当前位置，最下面是入口（main / 线程启动函数）。

# 典型的栈（gdb bt）
#0  OrderService.calcTotal (this=0x7f...) at OrderService.java:142   <-- 崩在这里
#1  OrderService.createOrder (...) at OrderService.java:88
#2  OrderController.submit (...) at OrderController.java:41
#3  HttpHandler.handle (...) at HttpHandler.java:203
#4  Thread.run (...) at Thread.java:748                              <-- 线程入口
  • 看崩溃：从 #0 往上看，找到第一个属于你自己代码的帧。框架内部的帧通常只是转发。
  • 看"谁传了脏参数"：从 #0 往下走，逐个帧检查入参，找到参数第一次变成错值的那一层。
  • 看"为什么会走到这"：看 #2、#3 的分支条件，而不是死磕 #0。

变量查看的坑

现象原因与对策
<optimized out>编译开了优化（-O2），变量被寄存器复用或消除。用 -O0 -g 重编，或看反汇编
指针显示一个地址需要解引用。p *ptr、p ptr->field，数组用 p *arr@10 看前 10 个
容器只显示摘要gdb 需要 pretty-printer。C++ 装 libstdc++ 的 python 脚本；Go 用 dlv 原生命令更好
值和你预期不符先确认断点位置是"赋值前"还是"赋值后"。差一行，结论完全相反

表达式求值：能问就不猜

# 不用改代码、不用重启，直接问进程
(gdb) p order->items.size()
(gdb) p/x flags                      # 十六进制看位标志
(gdb) p *linked_list                 # 顺着链表看下一个节点
(gdb) call strlen(buf)               # 调用函数（有副作用，慎用）

# Python 调试器里可以直接执行任意语句
(Pdb) p [o.id for o in orders if o.amount > 100]
(Pdb) pp vars(order)
在多线程程序里，被暂停的只是当前线程。gdb 默认会停住所有线程（all-stop 模式），但某些调试器和某些平台下其他线程仍在跑 —— 你看到的变量可能在下一秒就变了。排查竞态时，用 info threads 逐个线程切过去看栈，比盯着一个线程猜更有效。
模块 4

二分定位：把 O(n) 变成 O(log n)

二分的本质不是"找中间"，是利用单调性做排除：只要能把搜索空间切成两半、并且能判断问题在哪一半，就能用 10 次实验定位 1000 个候选。

四种二分对象

类型切什么适用场景
代码二分注释掉一半逻辑 / 提前 return一个长函数里有十几步处理，不知道哪步坏了
数据二分只喂一半输入数据批量任务里某几条数据触发了问题
环境二分换机器 / 换版本 / 换配置项本地好、测试环境坏、生产更坏
提交二分在提交历史中找"第一个坏掉的版本"以前好的，最近坏了，但不知道哪次改动引入的

代码二分：把函数切成两段

# 一个 300 行的处理方法，输出不对。在中间插一个 return
def handle(payload):
    step1(payload)
    step2(payload)
    dump(payload)          # 打印中间状态
    return payload         # <-- 临时插在这里，看此时结果对不对
    step3(payload)
    step4(payload)
    return payload
# 如果此时对 → 问题在 step3/4；如果不对 → 问题在 step1/2。一次实验砍掉一半。
二分的前提是"单调"。如果前半段坏了、后半段又修回来了（比如两次 bug 相互抵消），二分就会给出错误结论。所以每次二分都要验证：切出来的那一半，确实是坏的，而不是"看起来坏"。

数据二分：找出那条毒数据

# 10 万条记录导入失败，先切成 5 万
head -n 50000 all.csv > half.csv && import half.csv
# 失败 → 毒数据在前 5 万；成功 → 在后 5 万。继续对半，17 次左右定位到 1 条。
# 100000 → 2^17 = 131072，所以最多 17 轮

# 更快的做法：先用 grep 按可疑字段过滤
awk -F, '$3 == ""' all.csv | head        # 先看有没有空字段

环境二分：控制变量表

变量怎么切
机器同一份代码换一台机器跑，排除硬件 / 内核参数
版本逐个降级依赖版本，找"从哪个版本开始坏"
配置把生产配置整份拷到本地；或本地配置逐段拷到测试环境
数据量小数据量正常、大数据量异常 → 指向内存 / 索引 / 分页
并发度单线程正常、并发异常 → 指向共享状态

git bisect：让机器帮你二分提交

当你确认"上个版本是好的、这个版本是坏的"，但中间有几百个提交，手工一个个 checkout 太慢。git bisect 会用二分法自动帮你挑提交，你只需要回答"好/坏"。

# 手动模式
git bisect start
git bisect bad                  # 当前版本是坏的
git bisect good v2.3.0          # 这个 tag 是好的
# git 会自动 checkout 到中间的提交，你测一下，然后回答：
git bisect good                 # 或者 git bisect bad
# 重复 log2(N) 次后，git 会输出 "first bad commit"
git bisect reset                # 回到原来的分支

# 自动模式：写一个脚本，返回 0 = 好，1 = 坏
git bisect start HEAD v2.3.0
git bisect run ./scripts/check_bug.sh
# 300 个提交只需约 9 次构建 + 测试
bisect run 的脚本要满足两点：① 退出码严格是 0/1（125 表示跳过这个提交，比如编译不过）；② 必须真的能区分好坏，不能有随机性。如果测试本身 flaky，bisect 会指向一个错误提交 —— 这比不 bisect 更糟。

成本对比很直观：

提交数量线性排查二分
100最多 100 次7 次
1000最多 1000 次10 次
10000最多 10000 次14 次
模块 5

五类故障的排查路径

不同类型的故障，第一步该做什么完全不同。先分类，再动手 —— 用错路径会浪费大量时间。

类型一：不报错但结果不对

首要问题：错在哪一步？这类问题没有异常、没有日志、没有告警，只能靠比对中间状态。

固定一份最小输入和期望输出。没有"正确答案"就无法判断对错，先把预期写成断言。
沿着数据流打点：入口、每个转换步骤后、出口，各打一次。找到"第一次偏离预期"的位置。
对比"对"与"错"两次执行的中间值。同一份代码，一个输入对、一个输入错，差异点就是嫌疑点。
检查隐式转换：精度丢失、时区、字符编码、类型强转、四舍五入方向。这类问题占比极高。

类型二：偶发故障

首要问题：触发条件是什么？偶发不等于随机，绝大多数"偶发"背后有确定的触发条件，只是你还没观察到。

可能的触发源怎么验证典型症状
并发 / 竞态加压到高并发，看是否必现只在流量高峰出问题
时序 / 超时人为注入延迟（如 tc netem）错误集中在某个时段
资源耗尽长时间跑，观察句柄 / 内存曲线运行越久越容易出
数据相关记录失败请求的完整输入换个用户 / 换个 ID 就好
外部依赖抖动统计失败时的下游耗时分布和下游的 P99 尖刺对齐
偶发问题的正确做法是"先收集，后分析"。不要试图复现，而是把失败现场的上下文完整记录下来：完整请求、trace_id、线程名、时间戳、当时的资源指标。等攒够 3~5 个样本，规律自然浮现。靠"再跑一次看看"永远收敛不了。

类型三：性能问题

首要问题：慢在哪一层？不要一上来就优化代码，先把时间拆开。

# 先量，再改。一次请求的总耗时 = 各段之和
网关 2ms → 应用 15ms → 数据库 480ms → 序列化 3ms
# 结论：优化应用代码毫无意义，问题在 DB

# 常见分层工具
perf top -p <pid>        # CPU 花在哪些函数（on-cpu）
py-spy top --pid <pid>   # Python 进程的实时火焰视图
go tool pprof http://localhost:6060/debug/pprof/profile   # CPU profile
EXPLAIN ANALYZE ...      # 看 SQL 的真实执行计划
现象大概率原因
CPU 高、QPS 低算法复杂度问题、锁竞争、GC 频繁、序列化开销
CPU 低、延迟高等 IO：DB 慢查询、下游超时、磁盘、网络。先看等待，不要看 CPU
延迟随流量线性上升排队。某处是串行瓶颈（单线程、连接池、全局锁）
P99 高但 P50 正常少量请求走了慢路径：缓存未命中、大 key、锁等待、GC 停顿
内存持续上涨泄漏（未关闭的句柄 / 无界缓存 / 事件监听未移除）

类型四：崩溃

首要问题：有没有留下现场？崩溃的第一优先级不是"猜原因"，是保住 core dump 和堆栈。

先确认 core dump 有没有开：ulimit -c 为 0 就永远不会生成，事后无法补救。
看退出码和信号：137 = SIGKILL（多半是 OOM Killer），139 = SIGSEGV（段错误），134 = SIGABRT（断言失败）。
读堆栈最上面那帧自己的代码，检查指针、数组下标、空值。
如果是"随机崩溃"，优先怀疑内存越界 / use-after-free，用 ASan 重编一次跑。
# 判断是不是被 OOM Killer 杀的（最常见的"无故消失"）
dmesg -T | grep -i "killed process"
# 输出类似：Out of memory: Killed process 12345 (java) total-vm:8g

# 看进程退出码
systemctl status myapp        # 看 Main PID exited, code=killed, status=9/KILL

类型五：只在生产复现

首要问题：生产和测试的差异清单是什么？这类问题不要试图"在生产上调试"，而要把差异搬回本地。

差异维度常见具体项排查手段
数据数据量、脏数据、历史遗留字段、编码脱敏后导一份生产数据到测试库
配置连接池大小、超时、开关、线程数diff 两份配置文件，逐项对齐
拓扑多副本、负载均衡、CDN、代理层看是否只在特定实例上出错
依赖版本中间件、JDK、内核、glibc打印运行时版本，和本地比对
流量并发度、请求大小、长连接用生产流量的录制回放
最有效的一招：流量录制回放。把生产入口的请求（脱敏后）录下来，在测试环境按原速率重放。如果能在测试环境复现，问题就变成了普通问题；如果复现不了，说明差异在环境而非代码，继续对照上表逐项排除。
模块 6

远程与生产调试：先划安全边界

生产调试的第一原则不是"怎么查到"，是"怎么查才不制造第二个故障"。一个 SIGSTOP 就能让健康检查失败、流量被打到别的实例、甚至触发滚动重启。

attach 到运行中的进程

# 通用：先找到 pid
pgrep -f "order-service"
ps -eo pid,ppid,rss,pcpu,etime,cmd --sort=-rss | head

# gdb attach（会暂停进程，谨慎）
gdb -p <pid>
(gdb) thread apply all bt        # 一次看所有线程的栈，找卡住的那个
(gdb) detach                     # 一定要 detach，直接退出会杀掉进程

# Go：不暂停也能看栈（向进程发 SIGQUIT 会打印所有 goroutine 栈后退出，慎用）
dlv attach <pid> --headless --listen=:2345
# 更安全的做法：开 pprof 端口，用 HTTP 抓
curl http://127.0.0.1:6060/debug/pprof/goroutine?debug=2

# Python：py-spy 不需要暂停进程，几乎零开销
py-spy dump --pid <pid>          # 打印所有线程的当前栈
py-spy top --pid <pid>           # 实时看热点函数

# Java：jstack 会触发 safepoint，有短暂停顿
jcmd <pid> Thread.print > /tmp/stack.txt
jcmd <pid> GC.heap_info

容器内调试

手段适用与代价
docker exec -it <c> sh镜像里有 shell 和工具才行。生产镜像常是 distroless，什么都没有
kubectl debug -it pod --image=busybox --target=app临时容器（ephemeral container），共享进程命名空间，能 nsenter 进目标
nsenter -t <pid> -n -p从宿主机进入容器的网络 / 进程命名空间，不依赖镜像内容
kubectl cp把 core dump / 堆转储拷出来慢慢分析，最安全
kubectl port-forward把 pprof / actuator 端口映射到本地，不暴露到公网
# 从宿主机进入容器命名空间排查（无需容器内有工具）
pid=$(docker inspect -f '{{.State.Pid}}' mycontainer)
nsenter -t $pid -n ss -lntp            # 看容器内监听端口
nsenter -t $pid -p -f --preserve-credentials strace -p 1

# Kubernetes：起一个共享进程空间的临时容器
kubectl debug -it mypod --image=nicolaka/netshoot --target=myapp
# 进去之后可以直接看到目标容器的进程
ps aux

生产操作的risk分级

级别操作要求
绿读日志、抓 pprof、dump 栈、看指标可直接做。注意抓栈本身有开销，别高频重复
黄动态调日志级别、attach 调试器、抓包需要有人知情；限定时长；记录操作
橙改配置、重启单实例、摘流量走变更流程；确认有多副本兜底
红改数据、删缓存、kill 进程、回滚双人复核；先备份；准备好回滚方案
生产调试的三条硬规则：
① 只读优先。能用 dump 解决就不 attach，能 attach 就不改代码。任何写操作都要先问"如果这一步出错，怎么恢复"。
② 限时。调试器 attach、抓包、开 TRACE 日志，全都要有超时。忘了关的 TRACE 日志能把磁盘写满，比原故障更严重。
③ 先摘流量再动手。要暂停进程，先把它从负载均衡里摘掉。否则健康检查超时 → 触发重启 → 你的调试现场直接消失。
不要在生产上直接改代码试。"我改一行日志再发一版看看" —— 这句话在事故期间意味着一次完整发布流程（构建、镜像、滚动更新、健康检查），通常 10 分钟起步，而且新版本可能引入新问题。事故期间只做可逆的、秒级生效的操作：调配置、切开关、摘流量、扩容。代码修复留到事后。
模块 7

事后分析：从现场还原真相

故障恢复不等于排查结束。真正有价值的产出是一份能防止同类问题再发生的复盘，而它的原料是崩溃现场和日志时间线。

core dump：崩溃现场的快照

# 1. 确认是否开启（0 表示不生成，事后无法补救）
ulimit -c                 # 当前 shell 的限制
cat /proc/sys/kernel/core_pattern   # core 文件写到哪里
# 常见值：core → 当前目录；|/usr/lib/systemd/systemd-coredump %P → 交给 systemd

# 2. 临时开启（只对当前 shell 生效）
ulimit -c unlimited
echo '/var/crash/core.%e.%p.%t' > /proc/sys/kernel/core_pattern

# 3. 分析
gdb /path/to/binary /var/crash/core.myapp.12345.1729134567
(gdb) bt full                  # 完整栈 + 每帧的局部变量
(gdb) thread apply all bt      # 所有线程（多线程崩溃必看）
(gdb) info registers           # 寄存器状态
(gdb) frame 3                  # 切到第 3 帧再看变量
core 文件和二进制必须严格匹配。版本不一致时 gdb 会给出错误的符号，看起来像"栈乱了"。所以发布时要把每个版本的二进制（带调试符号）归档保留，否则 core dump 拿到手也读不懂。

读 stack trace 的正确姿势

看到什么说明什么
最顶层是框架代码通常不是框架的错。往下找第一帧你的代码，问题多半在那
栈里出现 native 方法JNI / cgo 边界。检查传进去的参数类型和生命周期
"Caused by" 链从最下面那个 Caused by 开始读，那才是根因，上面都是包装
栈深度异常（几千层）递归没有终止条件，或者循环引用导致序列化爆栈
同一个方法反复出现递归。检查基准条件
# Java 典型的异常链，从下往上读
org.springframework.web.util.NestedServletException: Request processing failed
  Caused by: org.springframework.dao.DataIntegrityViolationException: could not execute statement
    Caused by: org.postgresql.util.PSQLException: duplicate key value violates unique constraint "uk_order_no"
# 根因是最后一行：唯一约束冲突。前面两层只是包装。

日志时间线还原

把多个服务的日志按时间排序，是理解"事故到底怎么发生的"的唯一可靠方式。前提是时钟对齐和链路 ID 透传。

先对齐时钟。多机部署必须开 NTP。时钟漂移几秒，时间线就会得出完全错误的因果结论。
用 trace_id 串起一次请求，按时间排序，画出它经过了哪些服务、每段耗时多少。
找出"第一个异常"，而不是"最响的那个"。下游雪崩往往由上游一个不起眼的超时引发。
对齐指标拐点：CPU、QPS、错误率、连接数的拐点时间和日志事件对上，因果链就成立了。
# 按时间合并多个服务的日志（先各自排序再 merge）
for f in logs/*.log; do
  sort -k1,1 "$f" > "$f.sorted"
done
sort -m -k1,1 logs/*.sorted | grep "a3f9c2" | less

# 只看某个 trace 的耗时分布
jq -r 'select(.trace_id=="a3f9c2") | "\(.ts) \(.service) \(.msg) \(.cost_ms)ms"' app.jsonl

复盘模板

部分要写什么常见错误
影响面多少用户、多少请求、持续多久、损失多少写"部分用户"，不给数字
时间线精确到分钟：首次异常、发现、响应、恢复只写"发现后立即处理"
直接原因触发故障的那件事（一条 SQL、一次发布）把直接原因当根因
根本原因为什么这件事能造成这么大影响（缺防护、缺监控、缺隔离）停在"人为失误"
改进项每条都要有 owner + 截止时间 + 验收标准写"加强监控"这种无法验收的项
5 Whys 的正确用法是往下挖系统缺陷，不是往下挖人的责任。
"发布导致故障" → 为什么发布会导致故障？→ 因为新代码有慢查询 → 为什么慢查询能上线？→ 因为 CI 没有 SQL 审查 → 为什么没有？→ 因为没人负责这块。
前三层是技术，第四层是流程。只停在"某人粗心"的复盘，什么都不会改变。
模块 8

调试的反模式

下面这些做法不是"效率低"，是会主动误导你。它们让你以为在推进，实际上在扩大搜索空间。

反模式一：乱加 print 不思考

在十个地方加 print，输出几百行，然后盯着屏幕找"哪里不对"。问题是你没有预期值，所以任何输出看起来都"好像有点怪"。

替代做法：加日志前先写下"如果假设 A 成立，这行应该打印什么"。打印结果和预期不符，才是有信息量的实验。

反模式二：改代码试错

"我把这个判空去掉试试""我把这个超时调大试试" —— 每次改动都要重启、重跑、观察，单次成本几十秒到几分钟，而且改完之后你面对的是一个新程序，之前的观察全部失效。

做法单次成本可归因性
改代码 + 重启 + 重跑30 秒 ~ 5 分钟差：同时改变了多个条件
调试器里改变量 / 调函数1 秒好：只改了内存状态
加日志后重跑一次完整运行好：只增加了观察，没改行为

反模式三：不看文档瞎猜

库的行为、API 的默认值、配置项的语义，全都有文档。花 30 秒查一下，比花 30 分钟验证一个错误假设划算得多。典型的"猜错"包括：

  • 以为连接池默认大小是 100，实际是 10（不同库不一样，必须查）。
  • 以为超时单位是秒，实际是毫秒，于是"超时设了 30"变成 30 毫秒。
  • 以为某个方法线程安全，实际不是。
  • 以为异常会被抛出，实际被库内部吞掉并返回了默认值。

反模式四：忽略"最近改了什么"

这是投入产出比最高的一条线索，却最常被跳过。"以前一直是好的"这句话意味着：变化发生在某个时间点，找到那个变化就找到了大半答案。

# 三分钟内能查完的清单
git log --oneline -20                    # 最近提交了什么
git log -p --since="2 days ago" -- path/to/module   # 只看相关模块
git diff v2.3.0..HEAD --stat             # 两个版本之间改了哪些文件

# 别忘了非代码变更
# - 配置中心有没有人改过？
# - 依赖有没有升级？
# - 数据库有没有加索引 / 改表结构？
# - 证书 / 域名 / DNS 有没有动？
# - 流量模式有没有变化（活动、爬虫、压测）？
常见坑

十个调试中的典型错误

1
在没复现的情况下就开始改代码
改完之后无法验证，只能靠"感觉好了"。先花时间把复现条件收敛，是唯一能省时间的做法。
2
一次改多个地方
问题消失了也不知道是哪处起的作用，下次复发还得重来。每次只动一个变量，并写下预期。
3
在循环里打日志
10 万次循环就是 10 万行，磁盘写满、日志系统被打爆，有用的那行被淹没。改成循环外聚合统计。
4
catch 住异常只打 WARN 或干脆不打
接口已经在返回错误，监控里却一片安静。捕获后要么处理，要么 ERROR 带堆栈，不要静默吞掉。
5
gdb attach 后直接 quit
没有 detach 就退出，会把被调试进程一起杀掉。生产上这一步等于人为制造一次故障。
6
调试时忘了关 TRACE 日志
开了就忘，几小时后磁盘写满，服务挂掉。所有临时调试开关都必须设超时或加进检查清单。
7
条件断点里调用有副作用的函数
断点本身改变了程序状态，你调试的已经不是原来的程序了。条件表达式只做纯读取。
8
用优化过的二进制去读 core dump
变量显示 optimized out，栈帧错位。发布时归档带符号的二进制，core 才有分析价值。
9
不看最近变更，直接怀疑老代码
"一直好好的突然坏了"，九成是最近有变化：发布、配置、依赖、证书、流量。先查变更记录。
10
把直接原因当成根本原因
"某条 SQL 慢"是直接原因；"慢 SQL 能上线且没有监控"才是根本原因。只修前者，同类问题必然复发。
自测

六道题

1. 线上偶发报错，一天出现三五次，本地无法复现。最合理的下一步是？
正确答案：先收集现场。偶发问题靠"再跑一次"收敛不了，必须把失败时的完整输入、trace_id、线程、资源指标记下来。攒 3~5 个样本后规律自然浮现。
2. 一个变量在某个时刻被改成了错误的值，但不知道是谁改的。最直接的手段是？
正确答案：观察点。watchpoint 会在变量被写入的瞬间中断，直接给出写入位置和调用栈，不需要事先知道有哪些写入点。
3. 300 个提交之间引入了 bug，已知 v2.3.0 是好的。用 git bisect 大约需要几次验证？
正确答案：约 9 次。二分每次砍掉一半，300 → 150 → 75 → 38 → 19 → 10 → 5 → 3 → 2 → 1。前提是测试脚本稳定，不能有随机性。
4. 服务延迟高，但 CPU 使用率只有 15%。应该优先看什么？
正确答案：看等待。CPU 低而延迟高，说明时间花在等 IO 或等锁上，profiling CPU 只会看到一堆 idle。先按链路分段量耗时。
5. 进程莫名其妙消失，日志没有任何异常。第一步应该查什么？
正确答案：看退出码和 dmesg。退出码 137（SIGKILL）配合 dmesg 里的 "Killed process" 就是 OOM Killer 的典型特征。这种情况下应用层日志当然什么都没有。
6. 关于生产环境调试，哪个做法是错的？
正确答案：在生产上改代码重部署。事故期间只做秒级可逆操作（调配置、切开关、摘流量）。重新部署要几分钟到十几分钟，还会引入新变量，是最危险的做法。

术语表

术语一句话解释
复现用最小条件稳定重现问题，是排查的前提
可证伪假设能设计实验来验证或推翻的猜测，而不是"可能是缓存问题"
断点 breakpoint让程序在指定位置暂停，以便检查状态
条件断点只在表达式为真时暂停，用于循环和特定输入
观察点 watchpoint变量被写入时自动暂停，用于抓"谁改的"
调用栈 call stack当前线程的函数调用链，栈顶是当前位置
core dump进程崩溃时的内存快照，配合符号可还原现场
stack trace异常发生时的调用栈文本，从抛出点向外展开
attach把调试器挂到已运行的进程上，无需重启
safepointJVM 中所有线程可安全暂停的位置，抓栈会等待它
OOM KillerLinux 内存不足时内核直接杀进程，应用层无感知
二分定位每次砍掉一半候选空间，用 log2(N) 次实验定位
git bisectGit 内置的提交二分工具，可脚本化自动执行
结构化日志以 key=value / JSON 输出字段，便于机器检索聚合
trace_id贯穿一次请求全链路的唯一 ID，跨服务透传
采样 sampling高频日志只保留一部分，控制量级同时保留统计特征
