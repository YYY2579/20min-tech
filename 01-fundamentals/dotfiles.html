二十分钟管好你的 dotfiles

dotfiles 不是"备份几个配置文件"，而是把你脑子里的工作环境变成可执行的代码。这篇讲清楚四种管理方案的取舍、分层设计、密钥隔离，以及换机器时那条能一次跑通的 bootstrap 脚本。

建议开两个终端：一个读，一个在 $HOME 里动手试软链
开始前

先看清你家里有什么

动手之前先做一次盘点。绝大多数人的 $HOME 里躺着几十个点文件，其中真正值得版本化的通常不超过 20 个。

# 列出家目录下所有点文件（含隐藏目录，只看一层）
ls -ld ~/.[!.]* 2>/dev/null

# 按修改时间排序，最近改过的才是你真正在用的
ls -lt ~/.[!.]* 2>/dev/null | head -30

# 看看哪些配置目录占了多少空间（nvim 的插件目录经常几个 G）
du -sh ~/.config/* 2>/dev/null | sort -h | tail -20

# 检查是不是已经有人替你管过了
ls -la ~ | grep -E '\.(dotfiles|cfg|config-repo)'
git -C ~/.dotfiles status 2>/dev/null
判断标准很简单：如果一个文件你换台机器会想"哎我那个配置呢"，它就该被管；如果它是程序自己生成的缓存、日志、锁文件、插件二进制，就不该管。这条线后面模块 3 会拆得更细。
模块 1

为什么要管：四个真实的痛点

场景没有 dotfiles 时会发生什么
换机器新笔记本到手，从零配 shell、编辑器、git 别名，熟练的人也要花 3~6 小时，而且一定会漏——漏的往往是那个"上次调了半小时才对的"小设置
多设备公司台式机、家里笔记本、跳板机各一套配置。改了一处忘了另一处，于是你在两台机器上按同一个快捷键，得到两种结果
环境可复现同事说"我这边能跑"，你说"我这边不行"。差异可能只是 JAVA_HOME 或某个 shell 函数。配置进版本库后，这类争论可以直接 git diff 收敛
配置即资产你花在 .vimrc、.gitconfig、starship.toml 上的时间是真实的沉没成本。它应该像代码一样有历史、能回滚、能 code review

还有一个容易被忽略的价值：dotfiles 是给未来的自己写的文档。半年后你看到 export GOPROXY=... 旁边一行注释写着"公司内网必须走这个代理，否则 go mod 超时"，就省下了一次排查。

一个可量化的收益：把 bootstrap 做成一条命令后，新机器从"开机"到"能干活"的时间可以压到 5 分钟以内，而且第 10 次和第 1 次的结果完全一致。这就是"环境即代码"（Environment as Code）在个人尺度上的落地。
模块 2

四种管理方案，怎么选

这四种不是"新旧替代"关系，而是复杂度递增、能力递增。选哪个取决于你有几台机器、配置里有没有机器特定的差异。

方案原理优点代价
手工软链仓库放 ~/dotfiles，自己 ln -s 到 $HOME零依赖，任何机器都能用，逻辑一眼看穿文件一多脚本就臭长；新增文件要改脚本；Windows 上软链要管理员权限
GNU stow按"包"组织目录，stow 自动把包内目录树镜像成软链不用写脚本，加一个工具只需加一个目录；卸载用 stow -D多一个依赖；只做软链，不解决模板渲染和机器差异；对已存在的真实文件会拒绝操作
bare git repo把 $HOME 本身当工作区，仓库元数据放在 ~/.dotfiles不需要软链，文件就在原位；git 命令加个别名即可；改完直接 commit容易误把整个家目录纳入跟踪，必须配 showUntrackedFiles no；分支切换会影响真实文件；跨机器差异要自己用 include 处理
chezmoi源目录 → 目标目录的声明式同步，支持模板、密码管理器、脚本钩子能力最全：模板渲染、按 OS/主机名分支、run_once 脚本、加密、diff 预览概念多（源状态/目标状态/模板/脚本）；需要学它的语法；团队里别人不一定用

手工软链的最小实现

# 目录结构：仓库里的文件名去掉开头的点，避免在仓库里也是隐藏文件
# ~/dotfiles/
#   zsh/zshrc
#   git/gitconfig
#   nvim/init.lua

ln -sf ~/dotfiles/zsh/zshrc      ~/.zshrc
ln -sf ~/dotfiles/git/gitconfig  ~/.gitconfig
ln -sfn ~/dotfiles/nvim          ~/.config/nvim   # -n 很重要，否则会链进目录内部

# 验证：应该显示 "xxx -> /home/you/dotfiles/..."
ls -l ~/.zshrc ~/.gitconfig

stow 的目录约定

# stow 要求包内保持"相对 $HOME 的路径"结构
# ~/dotfiles/zsh/.zshrc        →  ~/.zshrc
# ~/dotfiles/git/.gitconfig    →  ~/.gitconfig
# ~/dotfiles/nvim/.config/nvim →  ~/.config/nvim

cd ~/dotfiles
stow -v -t ~ zsh git nvim     # 安装（建立软链）
stow -v -D -t ~ nvim          # 卸载（删除软链，不动源文件）
stow -v -R -t ~ zsh           # 重新链接（改结构后常用）
stow -n -v -t ~ zsh           # dry-run，只打印不执行，先看再干
stow 最容易卡住的地方：目标位置已经存在一个真实文件（不是软链）时，stow 会直接报冲突并拒绝。
先用 stow -n -v 干跑看冲突列表，把原文件备份成 .bak 再执行。绝对不要为了"让它跑通"而加 --adopt——那会把目标文件反向搬进仓库，很容易覆盖掉你仓库里的版本。

bare git repo 的关键三行

# 1. 在 $HOME 建一个裸仓库，工作区就是家目录
git init --bare $HOME/.dotfiles

# 2. 定义一个别名（写进 .bashrc / .zshrc）
alias dot='/usr/bin/git --git-dir=$HOME/.dotfiles/ --work-tree=$HOME'

# 3. 关掉未跟踪文件提示，否则 git status 会把整个家目录列出来
dot config --local status.showUntrackedFiles no

# 之后就是普通 git 用法
dot add ~/.zshrc
dot commit -m "feat(zsh): 加 fzf 历史搜索"
dot remote add origin git@github.com:you/dotfiles.git
dot push -u origin master
裸仓库方案的经典事故：忘了设 status.showUntrackedFiles no，然后执行 dot add -A。
结果是把 Downloads、.ssh、几个 G 的模型权重全提交了，推到远端之后清理起来非常痛苦（需要 filter-repo 重写历史）。用裸仓库就必须永远用精确路径 add，禁用 add -A。

chezmoi 的日常命令

# 初始化：从远端仓库拉下来并立即应用
chezmoi init --apply git@github.com:you/dotfiles.git

# 把已有文件纳入管理（会复制到源目录）
chezmoi add ~/.zshrc

# 编辑源文件（不是直接改目标文件）
chezmoi edit ~/.zshrc

# 看源和目标差在哪，再决定是否应用
chezmoi diff
chezmoi apply

# 只看某台机器最终会渲染成什么（排查模板问题最快的方式）
chezmoi cat ~/.zshrc

# 从别的机器拉最新并应用
chezmoi update

chezmoi 的源目录有命名约定：dot_zshrc 对应 ~/.zshrc，dot_config/nvim/init.lua 对应 ~/.config/nvim/init.lua，private_ 前缀表示权限 0600，.tmpl 后缀表示要经过模板渲染。

怎么选

1~2 台机器
手工软链或 stow 就够。别为了 10 个文件引入模板引擎，维护成本会超过收益
想零软链
bare git repo。文件就在原位，某些工具（会检查真实路径的）不会出问题
3 台以上 + 有差异
chezmoi。模板 + 主机名分支是它真正的价值，软链方案做这件事很别扭
团队共享
stow 或 chezmoi。团队场景下可读性比炫技重要，新人要能看懂目录结构
模块 3

哪些该管，哪些碰都别碰

这条线画错，后果不对称：漏管一个配置只是麻烦，多管一个密钥就是安全事故。

类别典型文件结论
shell 配置.zshrc .bashrc .profile .config/fish/config.fish必管。这是最高频修改、最影响手感的部分
编辑器.vimrc .config/nvim/init.lua .editorconfig必管。但插件本体（lazy 的 lockfile 可以管，插件目录不行）要排除
工具配置.gitconfig .tmux.conf .config/starship.toml .config/ripgrep/config必管。这些都是"调好一次受益几年"的资产
CLI 工具清单Brewfile packages.txt该管。它让"装依赖"这一步可复现，是 bootstrap 的输入
密钥与凭据.ssh/id_* .aws/credentials .netrc .gnupg/绝对不管。见模块 5。.ssh/config 例外，它通常不含密钥本体
机器特定路径.config/*/local.conf 含绝对路径的配置拆出去。放进不进版本库的 local 文件，由主配置条件加载
缓存与状态.cache/ .local/share/ .zsh_history .viminfo不管。体积大、变动频繁、无复用价值
运行时生成.config/nvim/plugin/packer_compiled.lua .lesshst不管。由工具自己生成，提交了反而会引起冲突

一个容易漏的类别：.gitconfig 里的 [credential] helper 和某些 url.insteadOf。
如果里面写了带 token 的 URL（比如 https://user:ghp_xxx@github.com），那这个文件就已经是密钥文件了。提交前务必 grep -iE 'token|password|secret|ghp_' 扫一遍。
模块 4

分层设计：通用 + OS + 机器

一份配置要同时跑在 macOS、Linux 服务器、WSL 上，就必然存在差异。解法不是写三个仓库，而是三层加载：通用层永远加载，OS 层按平台加载，机器层按主机名加载。

# 目录结构
# ~/dotfiles/
# ├── shell/
# │   ├── rc.common        ← 通用：别名、函数、编辑器、历史设置
# │   ├── rc.darwin        ← macOS 专属：Homebrew 路径、pbcopy 别名
# │   ├── rc.linux         ← Linux 专属：apt 提示、systemd 相关
# │   ├── rc.wsl           ← WSL 专属：Windows 路径互操作
# │   └── rc.local         ← 机器专属（不入库，gitignore）
# └── zsh/.zshrc           ← 只负责按顺序 source 上面这些

# ===== ~/.zshrc 的骨架 =====
DOTFILES="$HOME/dotfiles"

# 1. 通用层：所有机器都加载
[[ -f "$DOTFILES/shell/rc.common" ]] && source "$DOTFILES/shell/rc.common"

# 2. OS 层：只加载匹配的那个
case "$(uname -s)" in
  Darwin)               source "$DOTFILES/shell/rc.darwin" ;;
  Linux)
    # WSL 的 Linux 内核会在 /proc/version 里带 Microsoft 字样
    if grep -qi microsoft /proc/version 2>/dev/null; then
      source "$DOTFILES/shell/rc.wsl"
    else
      source "$DOTFILES/shell/rc.linux"
    fi
    ;;
esac

# 3. 机器层：按主机名加载，文件不存在就跳过
host_file="$DOTFILES/shell/hosts/$(hostname -s).zsh"
[[ -f "$host_file" ]] && source "$host_file"

# 4. 本地覆盖层：永远最后加载，可以覆盖上面任何设置
[[ -f "$DOTFILES/shell/rc.local" ]] && source "$DOTFILES/shell/rc.local"
顺序就是优先级：后加载的覆盖先加载的。把 rc.local 放最后，意味着任何"这台机器就是要特殊一点"的临时改动都有地方放，而且永远不会污染仓库。

为什么用 case 而不是一串 if

写法问题
if [ "$OS" = "mac" ] ... elif ...依赖外部变量，$OS 在很多环境里根本没定义，判断永远为假
if [[ "$(uname)" == "Darwin" ]]可用，但多层嵌套后可读性差，且 WSL 会被识别成 Linux
case "$(uname -s)" in推荐。分支清晰、无嵌套、每个分支只做一件事
[ -d /Applications ] && ...靠目录存在性猜系统，在 CI 容器里容易误判

chezmoi 的等价写法

# 文件名：dot_zshrc.tmpl
{{ if eq .chezmoi.os "darwin" }}
export PATH="/opt/homebrew/bin:$PATH"
alias ll='ls -lahG'
{{ else if eq .chezmoi.os "linux" }}
alias ll='ls -lah --color=auto'
{{ end }}

# 按主机名分支
{{ if eq .chezmoi.hostname "workstation" }}
export HTTP_PROXY="http://127.0.0.1:7890"
{{ end }}

# 渲染结果可以先看再应用
# chezmoi cat ~/.zshrc
别把"分层"做成"分叉"。三层里通用层应该占 90% 的内容。如果你发现 rc.darwin 和 rc.linux 有 80% 重复，说明抽象错了——把重复部分提回 rc.common，OS 层只留真正不同的几行（包管理器路径、剪贴板命令、sed -i 的语法差异）。
模块 5

敏感信息：三条防线

dotfiles 仓库大概率会推到 GitHub。私有仓库也不是保险箱——权限误配、fork、CI 日志、离职交接都会让它泄露。正确的假设是：仓库内容随时可能公开。

防线做法适用
物理隔离密钥类文件根本不进仓库，用 ~/.secrets 单独放，权限 0600所有场景的底线
模板渲染仓库里存 .tmpl 或 .example，真实值从环境变量/密码管理器注入需要把密钥写进配置文件的场景（如 API key 写进 .npmrc）
提交前拦截pre-commit 钩子跑正则扫描，命中就拒绝提交防手滑，最后一道闸

方案一：~/.secrets 独立文件

# 1. 建文件并收紧权限（组和其他人完全不可读）
touch ~/.secrets
chmod 600 ~/.secrets

# 2. 内容就是普通的 export
# ~/.secrets 示例：
# export GITHUB_TOKEN="ghp_xxxxxxxx"
# export AWS_PROFILE="work"
# export OPENAI_API_KEY="sk-xxxx"

# 3. 在 rc.common 里条件加载（注意：不要 echo 任何值）
[[ -f "$HOME/.secrets" ]] && source "$HOME/.secrets"

# 4. 确认它被忽略了
git check-ignore -v ~/.secrets
权限 600 不是可选项。很多系统上默认 umask 是 022，新建文件是 644——同机器上的其他用户（包括某些服务账号）能直接读走你的 token。用 touch 建完立刻 chmod 600，或者直接 install -m 600 /dev/null ~/.secrets 一步到位。

方案二：模板 + 环境变量

# 仓库里放模板（可以公开）
# config/npmrc.tmpl
# //registry.npmjs.org/:_authToken=${NPM_TOKEN}

# 渲染脚本：只替换 ${VAR}，缺变量就报错退出
#!/usr/bin/env bash
set -euo pipefail
render() {
  local src="$1" dst="$2"
  # envsubst 只会替换 $VAR / ${VAR} 形式，不会执行任何代码
  envsubst < "$src" > "$dst"
  chmod 600 "$dst"
}
# 缺变量时 envsubst 会静默替换成空串，所以要自己先校验
: "${NPM_TOKEN:?NPM_TOKEN 未设置，请先 source ~/.secrets}"
render config/npmrc.tmpl "$HOME/.npmrc"
envsubst 的坑：它会把所有 $xxx 都当变量替换。如果模板里有 $1 或者 nginx 风格的 $host，会被替换成空串。
限制替换范围：envsubst '$NPM_TOKEN $API_HOST'，只替换你列出来的变量。

方案三：提交前扫描

# .git/hooks/pre-commit（记得 chmod +x）
#!/usr/bin/env bash
set -e
# 只扫暂存区的改动，不扫整个仓库
patterns='ghp_[A-Za-z0-9]{36}|sk-[A-Za-z0-9]{32,}|AKIA[0-9A-Z]{16}|-----BEGIN [A-Z ]*PRIVATE KEY-----'
# 加上常见赋值形式
patterns="$patterns|(password|passwd|secret|token|api_key)[[:space:]]*[:=][[:space:]]*['\"][^'\"]{8,}"

if git diff --cached -U0 | grep -nEi "$patterns"; then
  echo "✗ 暂存区疑似包含密钥，提交已中止"
  echo "  确认无误可 git commit --no-verify 跳过（不推荐）"
  exit 1
fi

更省事的做法是用现成工具，规则库更全：gitleaks protect --staged、detect-secrets-hook、trufflehog。它们除了正则还会做熵值检测，能抓到没有固定前缀的自定义 token。

已经提交了怎么办？分两步，缺一不可：
① 立刻吊销并轮换密钥。历史重写不能撤回已经泄露的东西，GitHub 的公开仓库几秒内就会被爬虫扫走。
② 再用 git filter-repo 清历史。只做第二步等于自欺欺人。
模块 6

bootstrap 脚本该做什么

bootstrap（引导脚本）的目标只有一个：在一台干净机器上，用一条命令把环境恢复到可用状态。它必须是幂等的——跑第二遍不能报错、不能重复追加内容。

检测系统与架构：确定是 macOS / Debian 系 / RHEL 系 / Arch / WSL，以及 x86_64 还是 arm64。这决定了后面所有分支。
安装基础依赖：git、curl、zsh。注意顺序——没有 git 就拉不到仓库，所以这一段必须在克隆之前，且要能容忍重复安装。
克隆或更新仓库：仓库不存在就 clone，已存在就 pull --ff-only。用 --ff-only 是为了在分叉时明确失败，而不是悄悄产生一个 merge commit。
备份已有配置：把即将被覆盖的真实文件移到 ~/.dotfiles-backup/时间戳/。这一步是安全网，绝不能省。
建立链接或应用模板：软链方案就 ln -sfn，chezmoi 就 apply。每一步都打印做了什么。
安装工具链：从 Brewfile / 包列表批量安装。这一步通常最慢，要给出进度提示，并允许跳过（比如只想更新配置时）。
提示后续动作：切换默认 shell（chsh -s $(which zsh)）、重新登录、手动放置 ~/.secrets。这些不能自动做，必须打印出来让人确认。
#!/usr/bin/env bash
# bootstrap.sh —— 幂等、可重复执行
set -euo pipefail

DOTFILES="${DOTFILES:-$HOME/dotfiles}"
REPO="${DOTFILES_REPO:-git@github.com:you/dotfiles.git}"
STAMP="$(date +%Y%m%d-%H%M%S)"
BACKUP="$HOME/.dotfiles-backup/$STAMP"

log()  { printf '\033[1;34m==>\033[0m %s\n' "$*"; }
warn() { printf '\033[1;33m!!\033[0m %s\n' "$*"; }

# ---------- 1. 检测系统 ----------
detect_os() {
  case "$(uname -s)" in
    Darwin) echo macos ;;
    Linux)
      if grep -qi microsoft /proc/version 2>/dev/null; then echo wsl
      elif [ -f /etc/debian_version ]; then echo debian
      elif [ -f /etc/redhat-release ]; then echo redhat
      elif [ -f /etc/arch-release ];   then echo arch
      else echo linux-unknown
      fi ;;
    *) echo unsupported ;;
  esac
}
OS="$(detect_os)"
ARCH="$(uname -m)"
log "系统=$OS 架构=$ARCH"

# ---------- 2. 基础依赖 ----------
need() { command -v "$1" >/dev/null 2>&1; }

install_base() {
  case "$OS" in
    macos)
      # 没装 Homebrew 才装，装了就不动
      need brew || /bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
      ;;
    debian)
      need git || { sudo apt-get update -qq && sudo apt-get install -y git curl zsh; } ;;
    redhat)

backup_and_link() {
  local src="$1" dst="$2"
  # 已经是正确指向的软链，直接跳过（幂等的关键）
  if [ -L "$dst" ] && [ "$(readlink "$dst")" = "$src" ]; then
    log "已就绪 $dst"; return 0
  fi
  # 真实文件或指向别处的软链，先备份
  if [ -e "$dst" ] || [ -L "$dst" ]; then
    mkdir -p "$BACKUP/$(dirname "${dst#$HOME/}")"
    mv "$dst" "$BACKUP/${dst#$HOME/}"
    warn "已备份 $dst -> $BACKUP"
  fi
  mkdir -p "$(dirname "$dst")"
  ln -sfn "$src" "$dst"
  log "链接 $dst -> $src"
}

backup_and_link "$DOTFILES/zsh/.zshrc"     "$HOME/.zshrc"
backup_and_link "$DOTFILES/git/.gitconfig" "$HOME/.gitconfig"
backup_and_link "$DOTFILES/nvim"           "$HOME/.config/nvim"

    debian|wsl) xargs -a "$DOTFILES/packages.txt" sudo apt-get install -y ;;

  esac

$(printf '\033[1;32m✓ 完成\033[0m')

  1. 切换默认 shell：  chsh -s $(command -v zsh)
  2. 放好密钥文件：    install -m 600 /dev/null ~/.secrets  然后填入内容
  3. 重新登录或执行：  exec zsh -l

EOF
幂等的三个技巧：① 建链前先判断 readlink 是否已经指向目标；② 装包前用 command -v 判断是否存在；③ 所有"写入配置文件"的操作改成"生成独立文件 + 被主配置 source"，避免重复追加。
第三点最重要——echo "xxx" >> ~/.zshrc 这种写法跑两遍就重复两行，是 bootstrap 脚本最常见的缺陷。
别在 bootstrap 里做这些事：自动 sudo 改系统配置、自动生成 SSH 密钥（应该由人决定是否覆盖）、自动 chsh（可能把 root 的 shell 改坏）、自动执行远端脚本而不校验（curl | bash 的供应链风险）。凡是不可逆或涉及身份的操作，都打印出来让人做。

WSL 的三个专属问题

问题原因与解法
跨文件系统极慢在 /mnt/c 下跑 git status 或 npm install 可能比在 ~ 下慢 10~20 倍。代码放 WSL 自己的 ext4（~/code），不要放 Windows 盘
文件权限错乱Windows 盘上的文件在 WSL 里全是 777，git 会认为所有文件都改了权限。解法：git config core.fileMode false
换行符冲突Windows 编辑器写入 CRLF，脚本在 Linux 里报 bad interpreter: ^M。全局设 core.autocrlf input，并加 .gitattributes 强制 *.sh text eol=lf
# .gitattributes —— 跨平台协作的必需品
* text=auto eol=lf
*.sh      text eol=lf
*.bat     text eol=crlf
*.ps1     text eol=crlf
*.png     binary
*.jpg     binary
*.woff2   binary
不要在 .zshrc 里做重活。每次开新终端都会执行它。如果在里面跑 brew --prefix、nvm use、conda activate 这类命令，开一个 tab 可能要 1~2 秒。
优化手段：① 用命令替换的结果做缓存文件；② 把 nvm 换成按需加载（进目录时才加载）；③ 用 zsh -i -c exit 配合 time 测启动耗时，找出最慢的那一行。
常见坑

十个踩过的坑

1
软链把已有文件覆盖了
ln -sf 会静默覆盖目标位置的真实文件，原配置直接丢失。建链前必须判断目标是否存在并备份；目录场景要加 -n，否则会把软链建到目录内部。
2
提交了 .ssh 或 token
最常见的泄露源。除了 .gitignore，还要有 pre-commit 扫描。一旦推上去，先轮换密钥再谈清理历史——顺序反了等于没做。
3
PATH 顺序错乱，装了两份同名工具
Homebrew 的 python 和系统 python 混用，which -a python3 出来一串。解法是 PATH 只在 rc.common 里拼一次，OS 层只 append 不 prepend，且不要重复 source。
4
同一个 rc 文件被 source 了两次
交互式 shell 嵌套、tmux 新窗口、su - 都会触发。表现是 PATH 里出现重复项、提示符被包两层。在文件开头加守卫：[ -n "$_RC_LOADED" ] && return; _RC_LOADED=1。
5
改了配置忘了 reload
改完 .zshrc 在当前终端不生效，以为写错了，反复排查。用 source ~/.zshrc 或 exec zsh -l。注意 source 不会清理旧变量，某些删除操作必须开新 shell 才能看到效果。
6
把缓存目录也提交了
nvim 的插件目录、.cache、node_modules 一旦入库，仓库体积暴涨且每次 diff 都噪声满屏。仓库应该只放"你手写的文本"。
7
裸仓库方案忘了关未跟踪提示
然后 git add -A 把整个家目录提交了。必须设 status.showUntrackedFiles no，并且永远用精确路径 add。
8
软链指向了相对路径
ln -s dotfiles/zshrc ~/.zshrc 建出来的是相对链接，从别的目录访问就断了。一律用绝对路径，或者在建链前 cd 到目标目录。
9
bootstrap 脚本不幂等
跑第二遍报错、或者往 .zshrc 里重复追加三行 export。所有写操作都要么可判断（已存在则跳过），要么写到独立文件再由主配置加载。
10
在配置里写死了绝对路径和主机名
换机器或改用户名后全线失效。用 $HOME、$(hostname -s)、${XDG_CONFIG_HOME:-$HOME/.config} 这类表达式，把机器相关的值放进不入库的 local 层。
自测

六道题

1. 用 ln -sf ~/dotfiles/nvim ~/.config/nvim 时，如果 ~/.config/nvim 已经是个目录，会发生什么？
正确答案：软链被建到目录内部。因为 -f 只对文件生效，对已存在的目录会当成"放进这个目录里"。必须加 -n（--no-dereference）才会把目录本身替换掉。这是 dotfiles 脚本里最高频的 bug。
2. 裸仓库（bare git repo）方案里，哪条配置是必须的？
正确答案：status.showUntrackedFiles=no。否则 git status 会把整个家目录的未跟踪文件列出来，输出几万行，而且极易让人误用 add -A 把不该提交的东西全部入库。
3. 下面哪个文件不该进 dotfiles 仓库？
正确答案：~/.ssh/id_ed25519。私钥永远不进版本库，即使是私有仓库。需要跨设备同步私钥时，用密码管理器或专门的密钥同步方案，不要用 git。
4. 分层设计里，机器特定配置应该放在哪一层？
正确答案：独立的 local 层。机器特定配置往往含内网地址、代理端口、私有路径，不适合入库。放在最后加载既能覆盖前面所有设置，又不会污染仓库。OS 层只处理平台差异，不处理单机差异。
5. bootstrap 脚本要"幂等"，最关键的做法是？
正确答案：先检测再操作。软链先看 readlink、装包先看 command -v、写配置改成"生成独立文件 + 主配置 source"。rm -rf 看似干净，实际会删掉用户的本地改动。
6. 密钥已经推到公开仓库了，第一步该做什么？
正确答案：立刻轮换。公开仓库的提交会被爬虫秒级抓取，历史重写无法撤回已泄露的内容。改成 private 也只是阻止后续访问，不能收回已被拉取的副本。清理历史是第二步。
