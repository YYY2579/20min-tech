开始前

三个心智模型

Linux 命令很多，但底层只有三个思想。抓住它们，命令就是自然推论。

思想含义带来的好处
一切皆文件设备、进程信息、网络状态，都以文件形式暴露。比如 /proc/cpuinfo 是 CPU 信息，/dev/sda 是磁盘所有工具都能统一处理它们，不用为每种资源学新语法
小工具 + 管道组合每个命令只做一件事，用 | 把前一个的输出接到后一个的输入几个简单命令拼起来能解决复杂问题，不用写脚本
一切皆文本配置是文本、日志是文本、命令输出是文本grep / sed / awk 三件套通吃所有场景

重定向与退出码（管道的基础）

# 重定向
cmd > file         # 标准输出写入文件（覆盖）
cmd >> file        # 追加
cmd 2> err.log     # 只把错误输出写入文件（2 = stderr）
cmd > out.log 2>&1  # 标准输出和错误都写进去（最常用）
cmd > /dev/null    # 丢弃输出（只关心退出码时）
cmd < input.txt    # 从文件读输入

# 退出码：0 表示成功，非 0 表示失败
echo $?                  # 上一条命令的退出码
cmd1 && cmd2          # cmd1 成功才执行 cmd2
cmd1 || cmd2          # cmd1 失败才执行 cmd2
cmd1 ; cmd2           # 顺序执行，不管成败
为什么退出码重要？因为它是脚本和 CI/CD 判断"上一步成没成功"的唯一依据。grep 找不到匹配时退出码是 1（不是错误），这在脚本里经常导致意外 —— 想忽略它就用 grep xxx || true。
模块 1

文件与文本处理：日志分析的日常

找文件

# find：按条件查找（功能最强）
find /var/log -name "*.log"                    # 按名字
find / -type f -size +100M 2>/dev/null         # 大于 100MB 的文件，排查磁盘满
find /data -mtime -1                           # 最近 1 天修改过的
find . -name "*.log" -delete                   # 找到并删除
find / -type f -size +100M -exec ls -lh {} \;  # 找到后执行命令
find 从根目录 / 搜会非常慢，而且会报一堆权限错误（用 2>/dev/null 丢掉）。先缩小范围，比如 /var、/home、/data。
另一个坑：find . -name "*.log" -delete 删之前一定要先跑一遍不带 -delete 的版本看清楚。

grep：搜索文本

grep "ERROR" app.log                     # 基本搜索
grep -i "error" app.log                  # 忽略大小写
grep -r "关键词" /path/                  # 递归搜索目录
grep -c "ERROR" app.log                  # 只输出匹配行数
grep -n "ERROR" app.log                  # 显示行号
grep -v "DEBUG" app.log                  # 反向：排除匹配的行
grep -A 3 -B 1 "Exception" app.log       # 显示匹配行后 3 行、前 1 行
grep -E "ERROR|WARN" app.log             # 扩展正则，用 | 表达"或"

sed：流式编辑

sed -n '100,200p' app.log                # 只打印 100-200 行
sed 's/old/new/g' file                   # 替换（不修改原文件）
sed -i 's/old/new/g' file                # 原地替换（会改文件，谨慎）
sed -i.bak 's/old/new/g' file            # 原地替换并留备份
sed '/^$/d' file                         # 删除空行

awk：按列处理（日志分析神器）

# 假设 access.log 格式：IP - - [时间] "请求" 状态码 大小
awk '{print $1}' access.log                       # 打印第 1 列（IP）
awk '{print $1, $9}' access.log                   # 打印 IP 和状态码
awk '$9 == 500' access.log                        # 筛选状态码是 500 的行
awk '$9 >= 400 {print $1, $9}' access.log         # 条件 + 输出
awk '{sum += $10} END {print sum/1024/1024 " MB"}' access.log   # 求和

五个实战组合（直接抄）

# ① 统计访问量 Top 10 的 IP
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10

# ② 统计各状态码出现次数
awk '{print $9}' access.log | sort | uniq -c | sort -rn

# ③ 实时看日志里的错误（最常用）
tail -f app.log | grep --line-buffered "ERROR"

# ④ 找出某时间段内的日志
sed -n '/2026-10-16 10:00/,/2026-10-16 11:00/p' app.log

# ⑤ 统计每分钟的请求量（看有没有突刺）
awk '{print substr($4, 2, 17)}' access.log | uniq -c
管道组合的读法：从左往右，每一步的输出就是下一步的输入。
以 ① 为例：awk 取 IP → sort 排序（uniq 要求相邻才能去重）→ uniq -c 统计连续重复的次数 → sort -rn 按数字倒序 → head -10 取前 10。
理解了这个链条，你就能自己拼出无数种分析。
模块 2

进程与作业管理

# 看进程
ps aux                                   # 所有进程，BSD 风格
ps -ef                                   # 所有进程，System V 风格
ps aux --sort=-%mem | head -10           # 按内存倒序取前 10
ps aux --sort=-%cpu | head -10           # 按 CPU 倒序
pgrep -f "python app.py"                 # 按名字找 PID
pstree -p                                # 进程树，看父子关系

# 实时监控
top                                      # 基础版。按 M 按内存排序，P 按 CPU，1 展开每核
htop                                     # 更好用（需安装）

# 结束进程
kill 12345                               # 发送 SIGTERM(15)，优雅退出，让程序清理资源
kill -9 12345                            # 发送 SIGKILL(9)，强杀，程序无法清理
pkill -f "python app.py"                 # 按名字杀
killall nginx                            # 按进程名杀所有
先 kill 再 kill -9，这个顺序很重要。SIGTERM 让程序有机会保存数据、关闭连接、释放锁；SIGKILL 直接由内核终止，程序没有任何反应机会。
直接 -9 可能导致：数据只写了一半、文件锁没释放、子进程变孤儿。只有在进程完全卡死不响应 SIGTERM 时才用 -9。 
# 后台运行
cmd &                    # 放到后台
nohup cmd &              # 后台运行且不受终端关闭影响，输出到 nohup.out
nohup cmd > out.log 2>&1 &   # 指定输出文件（更常用）
jobs                     # 看当前 shell 的后台任务
fg %1                    # 把任务 1 调回前台
bg %1                    # 让任务 1 继续在后台跑
disown %1                # 脱离 shell，关终端也不退出
nohup 和 disown 都只解决"终端关闭"，不解决"进程崩溃"。生产环境跑常驻服务应该用 systemd（模块 8 会讲）—— 它能自动重启、开机自启、统一管日志。
模块 3

权限与用户

# 权限的读法：-rwxr-xr--
#  第1位：类型（- 普通文件，d 目录，l 软链接）
#  2-4位：属主权限（u）
#  5-7位：属组权限（g）
#  8-10位：其他人权限（o）

# 数字表示：r=4  w=2  x=1
# 755 = rwxr-xr-x   644 = rw-r--r--   600 = rw-------

chmod 755 script.sh              # 数字方式（最常用）
chmod +x script.sh               # 加执行权限
chmod -R 755 /var/www            # 递归

chown user:group file            # 改属主和属组
chown -R www-data:www-data /var/www

# 查看自己是谁
whoami; id                       # id 会显示所属的所有组
sudo cmd                         # 以 root 身份执行
sudo -i                          # 切换到 root 的交互式 shell
三个必须知道的特殊权限位：
SUID（4）：chmod 4755，执行时以文件属主身份运行。/usr/bin/passwd 就是典型（普通用户也能改密码）。这也是提权攻击的重点目标。
SGID（2）：目录上设置后，新建文件继承目录的属组，团队共享目录常用。
Sticky（1）：/tmp 就是 1777，任何人都能建文件，但只能删自己的。
线上最危险的操作之一：chmod -R 777。它能"解决"权限问题，但把所有文件对所有用户开放读写执行，等于拆掉了整个安全模型。生产环境发现权限报错，应该去查"哪个用户需要什么权限"，而不是一把 777 了事。
模块 4

网络诊断

看本机网络状态

# ss 是现代替代 netstat 的工具，更快
ss -tulnp                # 所有监听中的 TCP/UDP 端口 + 对应进程 ← 最常用
ss -tan state established    # 已建立的连接
ss -s                    # 连接数汇总统计
ss -tan | awk '{print $1}' | sort | uniq -c   # 各状态连接数分布

# 老命令（有些系统还有）
netstat -tulnp
ss -tulnp 是排查"服务起没起来"的第一条命令。如果端口没在监听，后面的都不用查了。
参数记忆：-t TCP、-u UDP、-l 只看监听、-n 不解析域名（快）、-p 显示进程。

测连通性

ping -c 4 8.8.8.8                # 测通不通（注意：很多服务器禁 ICMP，ping 不通不代表不通）
traceroute 8.8.8.8               # 看路由跳转，定位在哪一跳断了
mtr 8.8.8.8                      # traceroute + ping 结合，持续统计每跳丢包率（更好用）
dig example.com                  # DNS 解析，看返回的 IP 和 TTL
dig +short example.com
dig @8.8.8.8 example.com         # 指定 DNS 服务器测试
nslookup example.com             # 老命令，简单场景够用

# 测端口通不通（nc = netcat，一个能读能写网络连接的小工具，比 ping 有用得多）
nc -zv host 443                  # 能连上会输出 succeeded
telnet host 443
curl -v telnet://host:443        # 没有 nc 时的替代

看请求

curl -v https://example.com                # 完整报文（配合第 8 期看）
curl -o /dev/null -s -w "%{http_code} %{time_total}\n" URL   # 只要状态码和耗时
curl --resolve example.com:443:1.2.3.4 https://example.com   # 绕过 DNS 直连某 IP
curl -x http://proxy:8080 URL              # 走代理
wget -c URL                                # 断点续传下载
tcpdump -i eth0 -nn port 80 -c 100 -w cap.pcap   # 抓包（配合第 1 期）
排查网络的正确顺序（不要跳步）：
① 本机服务在监听吗 → ss -tulnp | grep 端口
② 域名能解析吗 → dig 域名
③ 网络通吗 → ping / traceroute（注意 ICMP 可能被禁）
④ 目标端口通吗 → nc -zv host port（这一步最关键，能区分"网络不通"和"服务没起"）
⑤ 应用层返回什么 → curl -v
⑥ 包到底发出去了吗 → tcpdump
按这个顺序走，能避免 90% 的瞎猜。
模块 5

磁盘与 IO

# 磁盘空间
df -h                    # 各分区使用率（-h 人类可读）
df -ih                   # 看 inode 使用率！磁盘没满但 inode 满了也会写不进去

# 目录占用
du -sh /var/*            # 各子目录大小汇总
du -sh /* 2>/dev/null | sort -rh | head -10   # 找出最大的目录
du -ah /var | sort -rh | head -20             # 找出最大的文件
磁盘满的两个常见陷阱：
① 文件被删了但空间没释放 —— 某个进程还持有这个文件的句柄。用 lsof | grep deleted 找出来，重启那个进程就释放了。
② inode 用满 —— 小文件太多（比如大量临时文件、session 文件）。df -h 看着有空间，但就是写不进去。用 df -ih 确认。 
# IO 性能
iostat -x 1              # 每秒刷新，看每块磁盘的详细指标（需装 sysstat）
iotop                    # 看哪个进程在疯狂读写
vmstat 1                 # 综合视图：r 运行队列、b 阻塞、si/so 交换、wa IO 等待

# 谁占着文件/端口
lsof -p 12345            # 某进程打开的所有文件
lsof -i :8080            # 谁占用了 8080 端口 ← 排查端口冲突
lsof /var/log/app.log    # 谁在用这个文件

iostat 关键列怎么看

列含义与判断标准
%util磁盘繁忙度。持续接近 100% 说明磁盘是瓶颈
await平均 IO 等待时间（毫秒）。机械盘 > 20ms、SSD > 5ms 就偏高了
r/s w/s每秒读写次数（IOPS）
rkB/s wkB/s每秒读写吞吐量
aqu-sz平均请求队列长度，持续大于 1 说明有排队
模块 6

内存

free -h                  # 最直观的内存概览
vmstat 1                 # 关注 si/so（交换分区读写），非 0 说明在换页，性能会崩
ps aux --sort=-%mem | head -10    # 内存占用最高的进程
cat /proc/meminfo        # 详细内存信息

free -h 的输出怎么读

               total        used        free      shared  buff/cache   available
Mem:            15Gi       8.0Gi       1.2Gi       300Mi       6.0Gi       6.5Gi
Swap:          2.0Gi       100Mi       1.9Gi
关键：不要只看 free 那一列！
Linux 会用空闲内存做文件缓存（buff/cache），所以 free 很小是正常的，甚至是好事。
真正该看的是 available —— 它表示"应用真正还能用多少内存"。available 充足就没问题。
Swap 的 used 如果持续增长，说明物理内存不够了，系统在把内存换到磁盘上，性能会急剧下降。这是需要立刻处理的信号。
OOM Killer：内存耗尽时，Linux 内核会主动杀掉占用内存最多的进程。排查方法：
dmesg -T | grep -i "killed process" —— 能看到被杀的进程名和当时的调用栈。
如果被杀的是你的服务，说明它确实吃太多内存了（内存泄漏？缓存无上限？），而不是"系统有问题"。
模块 7

性能排查方法论（本篇核心）

前面都是工具。这一节讲怎么用 —— 线上报警了，你坐下来，第一步做什么。

USE 方法

对每一种资源，问三个问题：

维度含义典型指标
U 使用率资源被占用了多少CPU 使用率、内存使用率、磁盘 %util
S 饱和度有多少在排队等（比使用率更能说明问题）运行队列长度、IO 队列长度、swap 换页
E 错误有没有出错网卡丢包、磁盘坏道、OOM 事件
为什么"饱和度"比"使用率"更重要？因为使用率 100% 不一定有问题（比如 CPU 100% 但任务都在快速完成）。但只要有排队，就一定有延迟。看到队列长度持续增长，才是真问题。

排查顺序（固定流程，不要跳）

先看整体负载。uptime —— 看 1/5/15 分钟平均负载。负载值不应持续超过 CPU 核心数（nproc 看核心数）。15 分钟负载很高但 1 分钟低 → 问题可能已经过去。
看 CPU。top —— 重点看 %us（用户态，说明应用在算）、%sy（内核态，高说明系统调用多）、%wa（IO 等待，高说明瓶颈在磁盘不在 CPU）、%id（空闲）。
看内存。free -h 看 available，vmstat 1 看 si/so。si/so 非 0 = 在用 swap = 内存不够。
看磁盘 IO。iostat -x 1 看 %util 和 await，iotop 找是哪个进程。top 里 %wa 高的话，直接跳到这里。
看网络。ss -s 看连接数，sar -n DEV 1 看流量，netstat -s | grep -i retrans 看有没有重传。
定位到具体进程。ps aux --sort=-%cpu | head 或 --sort=-%mem，然后用 lsof -p PID、cat /proc/PID/status 深挖。

三个典型症状 → 病因对照

症状最可能的原因
负载高但 CPU 空闲大量进程在等 IO（%wa 高）。查磁盘：iostat -x 1
负载高但内存也没满可能是"不可中断睡眠"的进程（D 状态），通常还是卡在 IO 上。用 ps -eo state,pid,cmd | grep "^D"
响应慢但各项指标都正常查网络延迟（mtr）、查下游依赖（数据库、外部 API）、查应用内部（线程池满、锁竞争、GC）
补充一个关键概念：平均负载（load average）包含"运行中"和"不可中断睡眠（D 状态）"两类进程。所以 load 高不一定代表 CPU 忙 —— 如果 load 高而 CPU 空闲，八成是 IO 卡住了。这是新手最容易误判的地方，会白花很多时间在 CPU 上。
模块 8

systemd 与服务日志

# 服务管理
systemctl start nginx
systemctl stop nginx
systemctl restart nginx          # 完全重启
systemctl reload nginx           # 重载配置（不中断服务，推荐）
systemctl status nginx           # 看状态 ← 排查服务问题的第一步
systemctl enable nginx           # 开机自启
systemctl disable nginx
systemctl list-units --failed    # 列出所有启动失败的服务

# 日志（journalctl）
journalctl -u nginx              # 看某个服务的日志
journalctl -u nginx -f           # 实时跟踪（最常用）
journalctl -u nginx --since "10 min ago"
journalctl -u nginx --since "2026-10-16 10:00" --until "2026-10-16 11:00"
journalctl -p err -b             # 本次启动以来的所有错误
journalctl -n 100                # 最近 100 行
journalctl --disk-usage          # 日志占了多少磁盘
journalctl --vacuum-size=500M    # 清理日志，只保留 500M

写一个自己的 systemd 服务

# /etc/systemd/system/myapp.service
[Unit]
Description=My Python App
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/.venv/bin/python app.py
Restart=always                 # 崩溃自动重启
RestartSec=5
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
systemctl daemon-reload        # 改完配置必须执行
systemctl enable --now myapp   # 设置自启并立即启动
这比 nohup 强太多：崩溃自动重启、开机自启、日志统一进 journalctl、能用 systemctl 统一管理、可以设资源限制和依赖关系。生产环境的常驻服务都应该用 systemd。
模块 9

定时任务与远程操作

cron

crontab -e               # 编辑当前用户的定时任务
crontab -l               # 列出

# 格式：分 时 日 月 周  命令
#      0  2  *  *  *   /opt/backup.sh    # 每天凌晨 2 点
#      */5 *  *  *  *  /opt/check.sh     # 每 5 分钟
#      0  9  *  *  1-5 /opt/report.sh    # 工作日 9 点
#      0  0  1  *  *   /opt/monthly.sh   # 每月 1 号
cron 的三个经典坑：
① 环境变量不一样。cron 的 PATH 很短，命令要写绝对路径（用 which python 查）。
② 看不到输出。cron 的输出会发邮件，但通常没人看。调试时把输出重定向到文件：/opt/x.sh > /tmp/x.log 2>&1。
③ % 有特殊含义（表示换行），命令里用到 % 要转义成 \%。

ssh 与文件传输

# 免密登录（三行搞定）
ssh-keygen -t ed25519 -C "你的邮箱"      # 一路回车
ssh-copy-id user@host                    # 把公钥传到服务器
ssh user@host                            # 之后就不用输密码了

# 传输文件
scp file.txt user@host:/path/            # 上传
scp -r dir/ user@host:/path/             # 上传目录
scp user@host:/path/file.txt ./          # 下载

# rsync：更适合大量文件，支持增量同步（只传变化的部分）

十个高危坑

1
rm -rf 变量为空
rm -rf $DIR/ 如果 DIR 是空的，就变成了 rm -rf /。脚本里必须用 set -u 并在删除前检查变量非空。
2
chmod -R 777 解决权限问题
拆掉整个安全模型。应该查清楚哪个用户需要什么权限，精确授权。
3
直接 kill -9
程序没有机会保存数据、释放锁、关闭连接。先发 SIGTERM（默认 kill），等几秒不响应再 -9。
4
磁盘满了只删文件不查进程
文件被删了但进程还持有句柄，空间不会释放。用 lsof | grep deleted 找出来重启进程。
5
只看 df 不看 inode
磁盘有空间但 inode 用满，照样写不进去。用 df -ih 确认。
6
看到 load 高就去查 CPU
load 包含不可中断睡眠进程。load 高而 CPU 空闲，八成是 IO 卡住。先看 top 里的 %wa。
7
以为 free 小就是内存不足
buff/cache 占用是正常的。看 available 那一列才是真实可用内存。
8
cron 里用相对路径和简短 PATH
cron 的环境变量和登录 shell 不同，命令要写绝对路径，脚本开头显式设置 PATH。
9
在 / 下直接 find 或 du
遍历整个文件系统，慢且会产生大量 IO，可能把正在跑的服务拖慢。缩小到具体目录。
10
用 ping 判断服务是否可用
ping 通只说明网络层通，不代表服务端口开着；ping 不通也不代表服务不可用（ICMP 常被禁）。测端口要用 nc -zv host port 或 curl。
自测

六道题

1. 系统负载很高，但 CPU 使用率很低（%id 很高）。最可能的原因是？
正确答案：磁盘 IO 瓶颈。平均负载包含"不可中断睡眠（D 状态）"的进程，这些进程在等 IO 但没占用 CPU。所以 load 高而 CPU 空闲，第一个该查的就是 iostat -x 1。
2. 要排查某个端口被哪个进程占用了，用哪条命令？
正确答案：lsof -i :8080 或 ss -tulnp。前者按端口找进程，后者列出所有监听端口及对应进程。这是排查"端口冲突"和"服务起没起来"的标准动作。
3. free -h 显示 free 只有 1GB，但系统运行正常。应该怎么看？
正确答案：看 available。Linux 会用空闲内存做文件缓存（buff/cache），free 小是正常甚至有益的。真正该警惕的是 Swap 的 used 持续增长，那说明物理内存不够、在用磁盘换页。
4. 删除了一个大文件，但 df 显示磁盘空间没释放。为什么？
正确答案：进程还持有句柄。在 Linux 里，文件被删除后，只要还有进程打开它，磁盘块就不会释放。用 lsof | grep deleted 定位，重启该进程即可释放。
5. 要检查服务是否可用，为什么不该用 ping？
正确答案：ping 只到网络层，且 ICMP 常被禁。ping 通不代表服务端口开着；ping 不通也不代表服务不可用。测服务应该用 nc -zv host port（测端口）或 curl（测应用层）。
6. USE 方法里的"饱和度（Saturation）"指的是？
正确答案：排队等待的量。它比"使用率"更能说明问题 —— 使用率 100% 不一定有延迟，但只要有排队就一定有延迟。对应指标如运行队列长度、IO 队列长度、swap 换页频率。
