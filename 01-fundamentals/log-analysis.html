二十分钟学透日志分析

日志的价值不在"打得多"，而在出事时能回答三个问题：什么时候开始的、影响了谁、为什么。这篇讲清四类日志的分工、结构化字段怎么设计、量怎么控，以及 awk + sort + uniq 那套真正管用的分析套路。

开始前

先造一批能练手的日志

分析日志这件事，光看是学不会的。下面这段脚本会生成 5 万行 nginx 风格的访问日志，分布刻意做得不均匀：某个接口的错误率明显偏高，还有一批耗时异常的请求。后面的命令都拿它练。

# gen_log.py —— 生成 5 万行 combined 格式的访问日志
import random, datetime

random.seed(7)
paths = ["/api/orders", "/api/users", "/api/pay", "/api/search", "/health"]
weights = [30, 25, 10, 30, 5]
start = datetime.datetime(2026, 10, 17, 14, 0, 0)
lines = []

for i in range(50000):
    ts = start + datetime.timedelta(seconds=i // 12)      # 约 12 QPS
    path = random.choices(paths, weights)[0]
    # /api/pay 的错误率刻意做成 12%，其余 0.5%
    bad = random.random() < (0.12 if path == "/api/pay" else 0.005)
    status = random.choice([500, 502, 504]) if bad else 200
    # 1% 的请求是慢请求（1.5~8 秒）
    rt = round(random.uniform(1.5, 8.0), 3) if random.random() < 0.01 else round(random.uniform(0.003, 0.09), 3)
    t = ts.strftime("%d/%b/%Y:%H:%M:%S +0800")
    lines.append(f'10.0.{random.randint(0,3)}.{random.randint(1,254)} - - [{t}] "GET {path} HTTP/1.1" {status} {random.randint(200,9000)} "-" "curl/8.4.0" {rt}')

open("access.log", "w").write("\n".join(lines))
print(len(lines), "lines")
# 跑起来，然后看一眼长什么样
python gen_log.py
head -3 access.log
wc -l access.log

# 典型一行（注意字段位置，后面 awk 全靠它）
# 1:IP  4:时间  6:方法  7:路径  9:状态码  10:字节数  12:UA  13:耗时(秒)
10.0.1.23 - - [17/Oct/2026:14:00:00 +0800] "GET /api/pay HTTP/1.1" 500 3120 "-" "curl/8.4.0" 0.041
注意最后一列 $request_time 不是 nginx 默认格式自带的。它需要在 log_format 里显式加上，否则日志里根本没有耗时字段——这是排查慢请求时最常见的"我日志里怎么没这个信息"。日志格式要在上线前设计好，事后补是补不回历史数据的。
模块 1

日志的四个层次：谁产生、谁消费

很多人把"日志"当成一个整体，结果把审计日志和调试日志混在一个文件里，既查不动也不敢删。先按产生者和消费者分开。

类型谁产生记录什么谁消费
应用日志业务代码、框架、SDK请求处理过程、业务事件、异常堆栈、外部调用结果开发、值班工程师。用于定位 bug
访问日志Nginx、网关、负载均衡、CDN每个请求一行：来源 IP、路径、状态码、字节数、耗时、UA运维、安全、容量规划、计费。用于看流量与错误率
系统日志内核、systemd、syslog、容器运行时启动关机、OOM Killer、磁盘满、网卡异常、服务重启运维、SRE。用于判断"是不是机器/平台的问题"
审计日志应用、数据库、云平台、堡垒机谁在什么时间从哪里对什么资源做了什么操作，结果如何安全、合规、事后追责。用于回答"这是谁干的"
类型典型位置关键约束
应用日志stdout → 容器运行时 → 采集器必须带 trace_id；生产默认 INFO 级
访问日志/var/log/nginx/access.log量大，必须轮转；要记录耗时和 upstream 耗时
系统日志journalctl / /var/log/messages受 rate-limit 限制，短时间大量日志会被丢弃
审计日志独立存储，通常 WORM（一次写入多次读取）不可修改、不可采样、不可随意删除，保留期由合规决定
最危险的一种混用：把审计日志当普通应用日志打。一旦它进了会被采样、会被轮转删除、会被 DEBUG 级别过滤的通道，等出事需要举证时，你会发现"这条记录恰好没采到"。审计日志必须走独立通道、独立索引、独立保留策略，且写入失败要让业务失败（fail-closed），不能静默吞掉。
模块 2

结构化日志：为什么必须是 JSON

先看一条"人看着挺清楚"的日志，和它在机器眼里的样子。

# 反例：拼接字符串
2026-10-17 14:23:01 INFO user 123 login success from 1.2.3.4 cost 35ms

# 机器要解析它，得写正则。然后遇到这些情况就崩了：
# - 用户名里带空格："user john smith login success"
# - 消息里带引号或换行
# - 以后想加一个字段，所有正则全部失效

# 正例：一行一个 JSON 对象
{"ts":"2026-10-17T14:23:01.035Z","level":"INFO","service":"user-api","msg":"login_success",
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","user_id":123,"client_ip":"1.2.3.4","duration_ms":35}

JSON 的四个实际好处：字段可寻址（jq '.duration_ms' 直接取值，不用正则）、可加字段不破坏兼容、类型正确（数字是数字，能比较大小）、嵌套结构能表达上下文（错误对象、上游响应）。

字段设计：一套够用的最小集合

字段类型说明与坑
ts字符串ISO 8601 + UTC + 毫秒，如 2026-10-17T14:23:01.035Z。全链路统一 UTC，展示时再转本地时区
level字符串固定枚举，全大写：DEBUG/INFO/WARN/ERROR/FATAL。不要出现 "warning"、"Err" 这种变体
msg字符串稳定的短标识，不是给人读的长句。如 "payment_callback_verify_failed"，便于聚合统计
service字符串服务名，与部署单元一致。多实例再加 instance / pod
env / version字符串环境（prod/staging）与版本号。没有 version，你无法判断"新版本上线后才出现"
trace_id字符串全链路追踪 ID，32 位十六进制（W3C Trace Context 规范）。没有它，跨服务排查只能靠猜时间
span_id字符串当前操作 ID，16 位十六进制。用于区分同一次请求里的不同步骤
request_id字符串入口生成的请求 ID，用于没有接入链路追踪时兜底关联
duration_ms数字耗时，单位毫秒，纯数字。不要写 "1.2s" 或 "35ms" 这种带单位的字符串，否则没法做数值比较
status / error数字 / 对象HTTP 状态码用数字；错误用对象承载 type、message、stack，别全塞进 msg
user_id / tenant_id数字或字符串业务定位的关键维度。但注意：不要把它们做成日志系统的索引标签，高基数会拖垮存储
# 一条完整的错误日志：上下文足够，不用再问"当时发生了什么"
{
  "ts": "2026-10-17T14:23:01.035Z",
  "level": "ERROR",
  "service": "order-api",
  "version": "1.4.2",
  "env": "prod",
  "msg": "upstream_timeout",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "http": {"method": "POST", "path": "/api/orders", "status": 504},
  "duration_ms": 3002,
  "upstream": {"name": "inventory", "host": "inv-3:8080", "timeout_ms": 3000},
  "error": {"type": "TimeoutError", "message": "read timeout after 3000ms"},
  "retry": {"attempt": 3, "max": 3}
}
三个容易忽略的细节：
① 一条日志必须是一行。采集器按行读，多行堆栈会被拆成 N 条互不相关的记录。把 stack 放进 JSON 字段里（换行转义为 \n），而不是直接换行输出。
② 字段名要统一。同一个含义在不同服务里叫 traceId、trace_id、tid，跨服务查询就是灾难。团队应该有一份字段字典。
③ msg 要稳定。如果 msg 里拼了用户 ID 和订单号，那每条都是"唯一消息"，聚合统计完全失效——这些应该放字段。
模块 3

日志级别：判断标准与"ERROR 通胀"

级别判断标准典型例子
FATAL进程无法继续，必须退出配置加载失败、端口被占用、数据库连接池初始化失败
ERROR影响用户、需要人介入，或请求最终失败下游超时导致下单失败、支付回调验签失败、未捕获异常
WARN异常但已自愈或已降级，不影响最终结果重试第 2 次成功、缓存未命中回源、连接池使用率 85%
INFO关键状态变化，正常运行时也需要留痕服务启动、配置热加载、发布版本变更、订单状态流转
DEBUG排查细节，生产默认关闭SQL 与参数、上游原始响应、分支走向
TRACE比 DEBUG 更细，逐步骤序列化耗时、锁等待、逐条循环处理

一句话判据：这条日志出现时，有没有用户的请求因此失败？有 → ERROR；没有但需要人看一眼 → WARN；只是记录正常事实 → INFO。

把 ERROR 当 INFO 用，会精确地毁掉告警

假设一个服务 1000 QPS，每个请求打一条 INFO，每条 500 字节：

# 算一下量级
1000 QPS × 86400 秒 = 86,400,000 条/天
86,400,000 × 500 B  ≈ 43 GB/天（未压缩）

# 如果这些日志里 5% 是 ERROR（因为"任何异常都打 ERROR"）
86,400,000 × 5% = 4,320,000 条 ERROR/天

# 结果：告警规则 "ERROR 数 > 100/分钟" 永远在响
# 值班的人第一周还会看，第二周开始直接静音 —— 告警正式失效
反模式后果
捕获异常后打 ERROR 又继续返回成功ERROR 数量与实际故障脱钩，告警阈值无法设定
每个请求都打一条 "request received" ERRORERROR 率恒定为 100%，等于没有级别
把业务校验失败（如密码错误）打成 ERROR正常的用户行为被算成系统故障
吞掉异常只打一行 WARN，不带上堆栈真出事时无法定位，只能复现
生产开 DEBUG 忘了关日志量涨 10~50 倍，磁盘和采集链路一起崩
可用的经验阈值：健康系统的 ERROR 日志应低于请求量的 0.1%，且 ERROR 条数与"失败请求数"量级相当。如果你发现 ERROR 数远大于失败请求数，说明级别用错了；如果远小于，说明有异常被吞掉了。这个比值本身就是一个值得监控的指标。
模块 4

日志量控制：采样、异步、限流、脱敏

日志是要花钱的，而且写日志本身会抢业务的时间。控制量不是"少打点"，而是把有限的额度花在有用的地方。

手段怎么做边界与代价
头部采样请求进来时按比例决定"这个请求要不要记日志"，如 1/100简单、省资源。但会丢掉被采样请求里的所有错误，故障时可能一条 ERROR 都没有
尾部采样先把整条链路的数据收齐，再决定留不留：有错误的 100% 留，正常的按 1% 留需要缓冲，实现复杂，但这是生产环境最推荐的策略
按 key 哈希采样用 trace_id 或 user_id 做哈希取模，保证同一请求的所有日志同进同出避免"只有半条链路"，是采样的必要前提
异步写入业务线程只入队，后台线程批量刷盘/发送队列必须有界。无界队列在故障时会吃光内存
限流每服务每秒最多 N 条，超出丢弃并计数丢弃策略要分级：先丢 DEBUG，再丢 INFO，ERROR 尽量不丢
去重聚合相同"指纹"（msg + 关键字段）在 N 秒内只打一条，附带 repeated: 137适合高频重复错误，如连接被拒、限流触发

两个必须改掉的写法

# ✗ 反例一：在循环里打日志
for order in orders:                 # orders 有 10000 条
    log.info(f"processing {order.id}")   # 10000 条日志，99% 没人看
    process(order)

# ✓ 正例：聚合后打一条，保留统计和少量样本
ok, fail, samples = 0, 0, []
for order in orders:
    try:
        process(order); ok += 1
    except Exception as e:
        fail += 1
        if len(samples) < 3: samples.append(order.id)
log.info("batch_processed", total=len(orders), ok=ok, fail=fail, sample_ids=samples)

# ✗ 反例二：把整个大对象序列化进日志
log.info("response", body=resp.text)     # 可能 2MB，还带用户隐私

# ✓ 正例：只打标识 + 摘要，需要细节时靠 trace_id 去链路系统取
log.info("response_received", status=resp.status_code,
         bytes=len(resp.content), sha256=hashlib.sha256(resp.content).hexdigest()[:12])

脱敏要在序列化层做，不能靠自觉

字段处理方式例子
手机号中间四位掩码138****5678
身份证只留前 6 后 4110101********1234
银行卡只留后 4 位**** **** **** 1234
密码 / token / Cookie整字段删除，不是掩码[REDACTED]
请求体白名单字段才记录只留 order_id、amount
还有一个安全细节常被忽略：日志注入（log injection）。如果用户可控的输入被原样写进日志，攻击者可以塞入换行符伪造日志条目，或塞入 ANSI 转义序列污染终端。做法是：结构化输出（JSON 序列化会自动转义换行），并在展示层禁用 ANSI 解析。另外，日志内容若被渲染到 HTML 页面，必须转义，否则就是存储型 XSS。
模块 5

分析套路：四个动作定位任何故障

排查不是"翻日志找线索"，而是按固定顺序缩小范围。这四步能覆盖绝大多数线上问题。

按时间聚合，找"什么时候开始"。把日志按分钟或 5 分钟分桶计数，画出曲线。拐点就是起点，起点附近一定有一次变更（发布、配置、流量、依赖故障）。没有拐点的持续异常，通常是容量或长期存在的 bug。
按维度分组，找"影响了谁"。按状态码、路径、上游服务、实例、机房、用户分群统计。如果只有某个实例异常 → 机器/网络问题；只有某个接口 → 代码问题；所有接口都异常 → 依赖或基础设施问题。这一步决定你去看哪本日志。
找离群值，看"最坏情况"。平均值会骗人。看 P95 / P99，看 Top N 慢请求，看错误集中在哪几个 trace_id。一次故障往往只由少数请求触发，抓住它们比看总量有用得多。
时间线还原，回答"为什么"。拿一个失败的 trace_id，把它在所有服务里的日志按时间排序，看每一步的输入输出和耗时。故障的根因往往在第一个"看起来正常但变慢"的环节，而不是最后报错的那个。
现象第一步查什么常见结论
错误率突增，QPS 正常按状态码和上游分组某个依赖挂了，或某次发布引入 bug
错误率正常，延迟上涨P99 慢请求的 trace慢查询、锁等待、连接池耗尽、GC
只有部分实例异常按实例 IP / pod 分组单机故障、配置漂移、磁盘满
QPS 掉零，日志也停了系统日志 + 容器事件进程崩溃、被 OOM Killer 杀、健康检查失败
特定用户报错，别人正常按 user_id 过滤数据问题、灰度未覆盖、权限配置
先分清"全站"还是"局部"，能省一半时间。错误率上涨时，第一件事不是 grep 错误消息，而是看是不是所有实例都在涨。全站同时出问题，基本可以排除单机原因，直接去看最近一次变更和共享依赖；只有一台机器出问题，去看系统日志和磁盘。
模块 6

常用组合：awk + sort + uniq 的实战

这套命令的价值在于不需要任何平台，SSH 上去就能用。它们的共同模式是：取字段 → 过滤 → 排序 → 计数 → 取前 N。

1. 状态码分布

# 第 9 列是状态码。统计每个状态码出现多少次，按次数倒序
awk '{print $9}' access.log | sort | uniq -c | sort -rn

# 只看 5xx
awk '$9 >= 500 {print $9}' access.log | sort | uniq -c | sort -rn

# 算 5xx 占比（一条命令出结果）
awk '{t++; if($9>=500) e++} END{printf "total=%d err=%d rate=%.2f%%\n", t, e, e*100/t}' access.log

2. Top URL 与 Top IP

# 第 7 列是路径（含查询串）。取前 10
awk '{print $7}' access.log | sort | uniq -c | sort -rn | head -10

# 去掉查询串再统计（把 ? 之后截掉）
awk '{split($7,a,"?"); print a[1]}' access.log | sort | uniq -c | sort -rn | head -10

# 来源 IP 前 10，通常是攻击或爬虫的第一眼
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -10

3. 按分钟看请求量（找拐点）

# 时间字段是 [17/Oct/2026:14:23:01，第 4 列，取前 17 个字符就是"到分钟"
awk '{print substr($4,2,17)}' access.log | sort | uniq -c

# 只看 14:20 到 14:30 这个窗口
awk '$4 ~ /17\/Oct\/2026:14:2[0-9]/' access.log | wc -l

# 每分钟的 5xx 数量 —— 故障曲线就是这么画出来的
awk '$9>=500 {print substr($4,2,17)}' access.log | sort | uniq -c

4. 提取慢请求

# 第 13 列是耗时（秒）。取大于 1 秒的，按耗时倒序取前 20
awk '$13 > 1 {print $13, $7, $9}' access.log | sort -rn | head -20

# 按接口统计慢请求数量
awk '$13 > 1 {print $7}' access.log | sort | uniq -c | sort -rn

# 算 P95 耗时（把耗时排序后取第 95% 位置的值）
awk '{print $13}' access.log | sort -n | awk '{a[NR]=$1} END{print a[int(NR*0.95)]}'

5. 错误消息聚类（把"看起来都不同"的错误合并）

# 原始错误里带订单号、时间、IP，每条都不同，无法统计
# 做法：把数字和十六进制串替换成占位符，再统计
grep '"level":"ERROR"' app.log \
  | sed -E 's/[0-9a-f]{8,}/<HEX>/g; s/[0-9]+/<N>/g' \
  | sort | uniq -c | sort -rn | head -20

# 这一步能把 50 万条错误收敛成十几类，直接看出"主要矛盾"

6. 用 jq 分析结构化日志

# 按 level 统计
jq -r '.level' app.log | sort | uniq -c | sort -rn

# 筛出慢请求，输出成 TSV 便于二次处理
jq -r 'select(.duration_ms > 1000) | [.ts, .http.path, .duration_ms] | @tsv' app.log | head -20

# 按接口算平均耗时（先分组求和与计数，再相除）
jq -s 'group_by(.http.path) | map({path: .[0].http.path, n: length, avg: (map(.duration_ms) | add / length)}) | sort_by(-.avg) | .[:10]' app.log

# 拿一个 trace_id，把它在所有服务日志里的完整时间线拉出来
jq -r 'select(.trace_id == "4bf92f3577b34da6a3ce929d0e0e4736") | [.ts, .service, .msg, .duration_ms] | @tsv' *.log | sort

7. 系统日志与容器日志

# journald：看某个服务最近 30 分钟，优先级 warning 及以上
journalctl -u order-api --since "30 min ago" -p warning --no-pager

# 看 OOM Killer 有没有杀过进程（内存问题的第一现场）
journalctl -k --since "2026-10-17 00:00" | grep -i "out of memory"

# 容器日志：带时间戳，取最近 100 行
docker logs --since 30m --tail 100 -t order-api

# Kubernetes：看上一个崩溃实例的日志（重启排查必用）
kubectl logs order-api-7d9f --previous
把高频组合记成一句话："取列 → 过滤 → 排序 → 计数 → 取头部"。awk 负责取列和过滤，sort | uniq -c 负责计数，sort -rn | head 负责排头部。任何"哪一类最多"的问题，都是这四步的变形。
模块 7

日志与指标的分工：谁发现问题，谁定位原因

维度指标（Metrics）日志（Logs）
回答什么有没有问题？多大范围？多久了？为什么出问题？具体是哪个请求、哪个参数
数据形态按时间聚合的数值（计数器、直方图、仪表盘）离散的事件明细，每条带完整上下文
基数必须低基数。标签组合控制在几十到几千天然高基数，可以有 user_id、trace_id
成本低。一个时间序列每天几 KB高。一条 500 字节，乘上亿次
保留可以留 1~2 年，用于容量趋势通常 7~30 天，长期靠冷存
适合告警是。稳定、便宜、可算比率和分位数否（除少数业务关键事件）。日志告警易抖动、解析脆弱

所以正确的分工是：告警建在指标上，定位靠日志，两者用 trace_id 串起来。

# 一个完整的排查动线
1. 指标告警：order-api 的 5xx 比率 5 分钟内从 0.02% 涨到 4.1%
2. 看板下钻：按 instance 分组，发现只有 order-api-3 异常 → 排除全局依赖
3. 指标样本上的 exemplar 带着一个 trace_id：4bf92f35...
4. 用 trace_id 查日志：发现该实例连不上 inventory 的 10.2.3.4:8080
5. 查系统日志：该节点 14:22 有一条 "conntrack table full"
6. 结论：不是代码问题，是连接跟踪表打满 → 调参 + 扩容

# 关键：第 3 步的 exemplar。没有它，你只能靠时间戳猜是哪条日志
# Prometheus 的 histogram 支持 exemplar，OpenTelemetry 默认打通这三者
一个反直觉的结论：日志量越大，排查越慢。因为信噪比下降了。真正好用的日志系统，是INFO 很少但每条都有用，ERROR 全部带 trace_id 和上下文，DEBUG 需要时能临时打开。追求"把所有东西都记下来"的团队，最后往往在故障时找不到那一行。
模块 8

成本与保留：日志是要花钱的

日志系统的成本不只是磁盘。索引和查询往往比存储更贵——同样 1TB 数据，放在对象存储里很便宜，放进全文索引集群里可能贵一个数量级。

层级介质保留查询体验
热SSD + 索引集群（ES / Loki / ClickHouse）7~14 天秒级，支持全文检索与聚合。只放最近、最可能要查的
温大容量磁盘，压缩存储，索引精简30~90 天分钟级，适合按 trace_id 精确查
冷对象存储（S3 / OSS），压缩归档180 天~数年小时级，需要先恢复或走离线任务
成本项说明优化手段
存储原始体积 × 副本数压缩（文本通常 8~12 倍）、列式存储、只存必要字段
索引倒排索引体积常与原始数据相当甚至更大只索引查询会用到的字段；高基数字段（user_id、trace_id）不做标签
写入吞吐峰值 QPS × 单条大小客户端批量发送、压缩传输、采样
查询计算大范围聚合最贵预聚合、限制时间范围、避免 SELECT *
跨区传输日志跨地域汇聚本地采集本地存储，只把汇总指标传回中心

保留期怎么定

取下面两个约束里更长的那个：

  • 业务需要回看多久。大多数故障在 7 天内被发现，偶发问题可能一个月后才复盘。所以热存 7 天、温存 30 天是常见起点。
  • 合规要求。例如网络安全相关法规要求网络日志留存不少于六个月，金融、医疗行业另有更细的规定。审计日志的保留期必须按合规来，不能按成本来。
# 一个务实的策略（按级别差异化，而不是一刀切）
ERROR / FATAL   → 全量保留，热 30 天，冷 1 年
WARN            → 全量保留，热 14 天，冷 90 天
INFO            → 采样 10%，热 7 天，冷 30 天
DEBUG / TRACE   → 生产默认关闭，按需开启，最长 2 小时自动回滚
审计日志        → 独立通道，全量，不可篡改，保留 ≥ 6 个月（按合规）

# 磁盘保护：logrotate 的最小可用配置
/var/log/app/*.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
两个真实的翻车场景：
① 日志打满磁盘导致服务全挂。根分区被日志写满后，数据库写不进去、进程起不来。必须配轮转 + 磁盘使用率告警（80% 预警，90% 严重）。
② 把高基数字段做成索引标签。在 Loki 里给 user_id 或 trace_id 建标签，会生成天文数字的流（stream），索引直接爆掉。Loki 的标签只放 service、env、level 这类低基数字段，其余靠全文检索。
常见坑

十个日志坑

1
日志里打印了密码、token、身份证
日志系统往往权限更宽、保留更久、还会被同步到第三方平台。脱敏要做在序列化层，靠 code review 拦不住。
2
异常堆栈多行输出，被采集器拆成 N 条
采集器按行读取，堆栈的每一行都会变成独立记录，还丢了级别和 trace_id。把 stack 放进 JSON 字段，换行转义为 \n。
3
时间戳用本地时区，跨时区排查差 8 小时
存储统一用 UTC + ISO 8601，展示时再转本地时区。混用本地时间会让"日志和指标对不上"这种问题查一整天。
4
用字符串拼接而不是结构化字段
一旦格式变了，所有正则和告警规则全部失效。结构化输出是让日志可被程序消费的前提。
5
ERROR 泛滥，告警彻底失效
每个请求都打 ERROR，错误率恒定 100%，值班的人只能静音。ERROR 的判据是"用户请求是否因此失败"。
6
在循环里逐条打日志
一万次循环打一万条，99% 没人看，还把磁盘和采集链路打满。聚合成一条，带总数、失败数和少量样本。
7
生产开 DEBUG 忘了关
日志量涨 10~50 倍，可能直接把服务拖垮。动态调级别必须带自动过期，比如 30 分钟后强制回到 INFO。
8
只打结果不打上下文
"调用失败"这四个字没有任何信息量。至少要带：调谁、参数摘要、耗时、trace_id、错误类型。
9
日志文件不轮转，打满根分区
磁盘满之后数据库写不进、进程起不来，故障范围远超日志本身。轮转 + 使用率告警是底线配置。
10
把高基数字段做成索引标签
user_id、request_id、trace_id 做标签会导致流数量爆炸，索引成本和写入放大失控。高基数字段只做全文检索，不做标签。
自测

六道题

1. 下面哪个字段设计是明显错误的？
正确答案："duration": "35ms"。带单位的字符串无法做数值比较和聚合，P95、慢请求筛选全部失效。耗时必须是纯数字，单位写在字段名里。
2. 一个 1000 QPS 的服务，每请求打一条 500 字节的 INFO 日志，一天产生多少数据？
正确答案：约 43 GB。1000 × 86400 = 8640 万条，乘以 500 字节约 43 GB（未压缩）。这就是为什么"顺手打个 INFO"在生产环境是很贵的习惯。
3. 抓到一个失败请求的 trace_id 后，正确的下一步是？
正确答案：按 trace_id 还原时间线。根因往往在第一个"看起来正常但变慢"的环节，而不是最后报错的那个服务。关键字搜索会捞出大量无关记录。
4. 为什么告警应该建在指标上而不是日志上？
正确答案：指标更稳定更便宜。日志格式一变，基于正则的告警就失效；日志量大时，告警查询本身就会拖垮系统。例外是少数业务关键事件（如支付回调验签失败）。
5. 在 Loki 里把 user_id 建成标签，会发生什么？
正确答案：流数量爆炸。标签的每个组合都会生成独立的流，user_id 这种高基数字段会产生天文数字的流。高基数字段应做全文检索，标签只放 service、env、level 这类低基数字段。
6. 尾部采样（tail sampling）相比头部采样，最大的优势是？
正确答案：能保留所有错误请求。头部采样在请求开始时就要决定去留，可能把出错的请求也采样掉；尾部采样先缓冲，按结果决定，但实现复杂、需要额外内存。

术语表

术语一句话解释
结构化日志以固定字段（通常是 JSON）输出、可被程序直接解析的日志
trace_id一次请求在全链路的唯一标识，用于把多个服务的日志串起来
span_id链路中单个操作的标识，一个 trace 包含多个 span
W3C Trace Context跨服务传递链路信息的标准，通过 traceparent 请求头传播
头部采样请求开始时按比例决定是否记录，简单但可能丢掉错误
尾部采样收齐整条链路后再决定去留，可保证错误全留
日志轮转按大小或时间切分日志文件并删除旧文件，防止打满磁盘
日志注入攻击者通过可控输入插入换行或转义字符，伪造日志条目
脱敏对敏感字段做掩码或删除，避免隐私数据进入日志系统
基数（cardinality）某个字段不同取值的数量。user_id 基数极高，level 极低
exemplar指标样本上附带的 trace_id，用于从指标直接跳到具体请求
RED 方法Rate、Errors、Duration 三个指标，面向请求型服务
USE 方法Utilization、Saturation、Errors，面向资源
审计日志记录"谁在何时对什么做了什么"的不可篡改日志，用于合规与追责
WORM一次写入多次读取，写入后不可修改的存储特性
冷热分离近期数据放高性能存储，历史数据压缩归档到廉价介质
Loki只索引标签、不索引全文的日志系统，成本低，查询靠标签 + 过滤
ILM索引生命周期管理，按时间自动在热/温/冷/删除之间迁移
