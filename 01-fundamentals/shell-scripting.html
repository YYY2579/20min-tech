二十分钟学透 Shell 脚本

Shell 脚本的难点从来不是语法，而是它默认不报错。这篇的重点是：为什么脚本会静默失败、set -euo pipefail 到底管什么不管什么、引号怎么毁掉你的数据，以及怎么让脚本在出错时体面地退出。

开始前

先写一个"正确"的骨架

后面八节都在解释这个骨架里每一行的道理。先抄下来，以后每个脚本都从这里开始。

#!/usr/bin/env bash
# 用 env 而不是 /bin/bash：让脚本用 PATH 里的 bash，跨系统更稳

set -euo pipefail
# -e  命令失败就退出
# -u  用未定义变量就报错
# -o pipefail  管道里任何一段失败都算失败

# 可选但强烈建议
set -o errtrace      # ERR trap 能传进函数和子 shell
shopt -s inherit_errexit   # 命令替换里也遵守 -e（bash 4.4+）

# 出错时打印现场
trap 'echo "[FAIL] line $LINENO: $BASH_COMMAND" >&2' ERR

# 清理临时文件
TMPDIR=$(mktemp -d)
trap 'rm -rf "$TMPDIR"' EXIT

# 所有输出走 stderr，不污染 stdout（stdout 可能被管道接走）
log()  { printf '[%s] %s\n' "$(date '+%F %T')" "$*" >&2; }
die()  { log "ERROR: $*"; exit 1; }

main() {
    [[ $# -ge 1 ]] || die "usage: $0 <target>"
    local target=$1
    log "processing $target"
}

main "$@"
为什么用 main "$@" 包一层：① 所有变量在函数里默认是全局的，但你可以用 local 控制作用域；② 函数必须定义在调用之前，包成 main 可以让"定义"和"执行"分离，脚本结构更清楚；③ 如果脚本被 source 引入，main "$@" 会立即执行 —— 想避免就在前面加个判断，但绝大多数脚本不需要。
模块 1

为什么脚本会静默出错

这是 Shell 最反直觉的设计：它默认把每条命令都当成"尽力而为"，失败了继续往下跑。对交互式命令行这是优点（打错一条不影响下一条），对脚本就是灾难。

陷阱一：命令失败不中断

#!/bin/bash
# 意图：备份数据库，然后上传

mysqldump mydb > /backup/db.sql      # 假设这里失败了（磁盘满）
gzip /backup/db.sql                  # 文件不存在，gzip 报错
aws s3 cp /backup/db.sql.gz s3://bk/ # 上传了空文件
echo "备份完成"

echo $?     # 0 —— 因为最后一条 echo 成功了
# 结果：监控显示脚本成功，实际备份早就废了

陷阱二：未定义变量当空字符串

# 拼错变量名，删掉整个目录
TARGET_DIR=/data/app
rm -rf "$TARGT_DIR"/      # 拼错了：TARGT 而不是 TARGET
# 展开成 rm -rf "/" —— 未定义变量是空字符串

# 更隐蔽的版本：变量名后面跟了字符
FILE=report
echo "$FILE_backup"       # 空！bash 认为变量名是 FILE_backup
echo "${FILE}_backup"      # report_backup ✓

陷阱三：管道只返回最后一个命令的状态

# 这条命令的退出码是多少？
cat /nonexistent/file | grep foo | wc -l
echo $?     # 0！因为 wc 成功了

# 三个命令里两个失败了，但你完全不知道 —— 这就是 pipefail 存在的理由

# 常见受害者
curl -s https://api.example.com/data | jq '.items[]' | while read -r id; do
    process "$id"
done
# curl 失败 → jq 收到空输入 → 循环一次都不执行，脚本"成功"结束

陷阱四：其他几个静默失败点

写法会发生什么
cd /some/dir目录不存在时 cd 失败，但脚本继续在原目录执行后续的 rm -rf *
rm $FILESFILES 为空时变成 rm（无参数），报错但不删东西；有通配符没匹配时，字面量传给命令
[ $x = "yes" ]x 为空时变成 [ = "yes" ]，语法错误
local v=$(cmd)cmd 失败不会触发 set -e，因为 local 自己返回 0
核心认知：Shell 的错误处理是"opt-in"（主动开启），不是"opt-out"。几乎所有其他语言都是"异常不捕获就中断"，Shell 反过来 —— "你不显式检查，它就当没发生"。所以每个脚本的第一行都该是 set -euo pipefail。
模块 2

set -euo pipefail：三个开关与它们的例外

这三个开关是 Shell 脚本质量的分水岭。但 -e 有很多例外，不了解这些例外，你会写出"该退出时没退出"或"不该退出时退出了"的脚本。

-e（errexit）：命令失败就退出

# 基本行为
set -e
false
echo "这行不会执行"

# 但下面这些情况，失败【不会】导致退出：

# 1. 命令在 if / while / until 的条件位置
if grep -q foo file; then ...; fi        # grep 失败是"正常的假"
while read -r line; do ...; done < f     # read 到 EOF 返回 1

# 2. 命令是 && 或 || 的一部分（除了最后一个）
cmd1 && cmd2        # cmd1 失败不退出
cmd1 || true        # 显式忽略错误的标准写法

# 3. 命令前面有 !（取反）；4. 管道中非最后一个命令（未开 pipefail）
! grep -q foo file
false | true

# 5. 算术表达式的返回值是 0 时
i=0
((i++))              # 返回 1（i++ 的值是 0）→ 脚本直接退出！
i=$((i + 1))         # 安全写法
((i++)) 这个坑每年都要坑一批人。原因是算术命令的返回值由表达式的值决定：值为 0 返回 1，非 0 返回 0。而 i++ 是"后置自增"，表达式的值是自增前的值。所以 i=0; ((i++)) 返回 1，在 set -e 下脚本立刻退出，而且没有任何错误信息。

-u（nounset）：用未定义变量就报错

# 开启后
set -u
echo "$UNDEFINED"
# bash: UNDEFINED: unbound variable
# 退出码 1

# 但下面这些是安全的（不算未定义）
echo "${UNDEFINED:-default}"    # 有默认值，不报错
echo "${UNDEFINED-}"            # 显式允许为空
echo "$@"                       # 位置参数特殊：$@ 和 $* 在无参数时是空，不报错
echo "$1"                       # 这个会报错！$1 未定义
echo "${1:-}"                   # 安全

# 数组的坑
arr=()
echo "${arr[@]}"                # bash 4.4+ 安全；更早版本在 set -u 下会报错
echo "${#arr[@]}"               # 安全

-o pipefail：管道里任何一段失败都算失败

# 不开 pipefail
set -e
false | true | true
echo "还活着"        # 会打印

# 开了 pipefail
set -eo pipefail
false | true | true
echo "不会到这里"     # 退出码是 1（最右边那个非零的）

# pipefail 的返回值规则：取管道中【最后一个非零】退出码
# 如果全部成功，返回 0
# 例：exit 2 | exit 3 | exit 0  →  返回 3

# 常见的"合法失败"要显式处理
grep -q pattern file | cat    # 没匹配时整个管道返回 1
# 如果这就是预期行为，加 || true
grep -q pattern file | cat || true

完整开关清单

开关作用建议
set -e命令失败退出必开。但要记住那五个例外
set -u未定义变量报错必开。位置参数用 ${1:-} 兜底
set -o pipefail管道整体失败必开。注意 grep 这类"1 是正常值"的命令
set -x打印每条执行的命令调试时临时开，别提交到生产脚本
# 一行开启全部（推荐）；等价的长写法 set -o errexit -o nounset -o pipefail
set -euo pipefail

# 临时关闭某个开关（做一段允许失败的逻辑）
set +e
risky_command
rc=$?
set -e
[[ $rc -eq 0 ]] || log "risky_command failed with $rc"

# 查看当前所有开关
set -o
模块 3

变量与引号

Shell 里 90% 的诡异 bug 都跟引号有关。核心只有一句话：不加引号的变量会经历"分词"和"通配符展开"两次改造，你的数据会被打散、被当成文件名。

不加引号会发生什么

# 场景一：空格导致参数错位
file="my report 2026.pdf"
rm $file
# 实际执行：rm my report 2026.pdf
# 删了三个不存在的文件，报错；如果真有叫 my 和 report 的文件，就被误删了

rm "$file"
# 正确：rm "my report 2026.pdf"

# 场景二：通配符被意外展开
pattern="*.log"
echo $pattern        # 输出：a.log b.log c.log（被当成 glob 展开了）
echo "$pattern"       # 输出：*.log

# 场景三：空变量变成"消失的参数"
args=""
cmd $args            # 变成 cmd（无参数）
cmd "$args"           # 变成 cmd ""（一个空字符串参数）—— 两者语义完全不同

# 场景四：换行被压成空格
v=$(printf 'a\nb')
echo $v              # a b（一行）
echo "$v"             # a
                     # b（两行）

$@ 与 $* 的区别（最常考）

写法展开结果（参数为 a "b c" d）说明
$@a b c d（4 个词）错。"b c" 被拆开了
"$@""a" "b c" "d"（3 个词）正确。每个参数保持独立
$*a b c d（4 个词）错。同样被打散
"$*""a b c d"（1 个词）用 IFS 首字符连接成一个字符串
# 转发参数的标准写法
my_wrapper() {
    echo "参数个数: $#"
    for arg in "$@"; do
        echo "  [$arg]"
    done
}
my_wrapper a "b c" d
# 参数个数: 3
#   [a]
#   [b c]
#   [d]

# 什么时候用 "$*"：需要把参数拼成一个字符串时
msg="$*"                  # "a b c d"
IFS=,; msg="$*"          # "a,b,c,d"（用 IFS 首字符连接）

参数展开的完整工具箱

# ---- 默认值系列 ----
${var:-default}      # var 未定义或为空 → 用 default（不赋值）
${var-default}       # 只在【未定义】时用 default（空字符串算已定义）
${var:=default}      # 未定义或为空 → 用 default 并【赋值给 var】
${var:?message}      # 未定义或为空 → 打印 message 到 stderr 并退出
${var:+alt}          # var 已定义且非空 → 用 alt，否则用空

# 实战
: "${DB_HOST:?DB_HOST must be set}"     # 强制要求环境变量，否则退出
PORT="${PORT:-8080}"                       # 有默认值的配置项
NAME="${1:-world}"                          # 位置参数默认值

# ---- 字符串处理 ----
${#var}              # 长度
${var#prefix}        # 从【头】删最短匹配
${var##prefix}       # 从【头】删最长匹配
${var%suffix}        # 从【尾】删最短匹配
${var%%suffix}       # 从【尾】删最长匹配
${var/old/new}       # 替换第一个
${var//old/new}      # 替换全部
${var:2:5}           # 从下标 2 取 5 个字符
${var,,}             # 转小写（bash 4+）
${var^^}             # 转大写（bash 4+）

# 实战：去掉扩展名、去掉目录
path="/var/log/nginx/access.log"
echo "${path##*/}"        # access.log（basename）
echo "${path%/*}"         # /var/log/nginx（dirname）
echo "${path##*.}"        # log（扩展名）
echo "${path%.*}"         # /var/log/nginx/access

数组

# 定义（用空格分隔，不要用逗号！）
arr=(apple banana "cherry pie")

echo "${arr[0]}"          # apple
echo "${arr[@]}"          # 所有元素（每个独立）
echo "${#arr[@]}"         # 元素个数：3
echo "${arr[@]:1:2}"      # 从下标 1 取 2 个
arr+=(date)               # 追加

for x in "${arr[@]}"; do echo "[$x]"; done

# 关联数组（bash 4+，相当于 map）
declare -A conf
conf[host]=localhost; conf[port]=5432
echo "${conf[host]}"
for k in "${!conf[@]}"; do echo "$k=${conf[$k]}"; done
三个最常见的引号错误，每一个都真实造成过事故：
① rm -rf $DIR/ —— DIR 为空时变成 rm -rf /。必须写 rm -rf "${DIR:?}/"。
② [ $x = yes ] —— x 为空时语法错误。必须写 [ "$x" = yes ] 或 [[ $x == yes ]]。
③ for f in $LIST —— 文件名带空格时被拆开。用数组，不用空格分隔的字符串。
模块 4

条件判断

Shell 有三套判断语法，行为差异很大。混用是 bug 的温床。结论先行：bash 脚本里一律用 [[ ]]，只在写 POSIX sh 时用 [ ]。

三者的区别

语法本质关键差异
test expr外部命令（也有内建）所有参数都是普通字符串，需要自己加引号
[ expr ]等同于 test，是命令不是语法] 是参数不是括号，前后必须有空格。变量必须加引号
[[ expr ]]bash 关键字（不是命令）不做分词和 glob；支持 && || =~；变量可不加引号
# [ ] 的经典错误
x=""
[ $x = "yes" ]        # ✗ 展开成 [ = "yes" ] → "unary operator expected"
[ "$x" = "yes" ]       # ✓

[ $x -eq 1 ]          # ✗ x 为空时同样报错，且 x 非数字时也报错
[[ $x -eq 1 ]]        # ✓ 空字符串当 0 处理（不报错，但语义要想清楚）

# [ ] 不能用的写法
[ $a -gt 1 && $b -lt 5 ]      # ✗ && 被当成 [ 的参数
[ $a -gt 1 ] && [ $b -lt 5 ]  # ✓ 用两个 [ ] 加 shell 的 &&
[ $a -gt 1 -a $b -lt 5 ]      # ✓ 用 -a（已废弃，不推荐）

[[ $a -gt 1 && $b -lt 5 ]]    # ✓ [[ ]] 原生支持

数值比较 vs 字符串比较（最容易混）

数值比较字符串比较说明
-eq= 或 ==相等
-ne!=不等
-lt / -le< / <=小于 / 小于等于
-gt / -ge> / >=大于 / 大于等于
# 用错了会怎样
a=10; b=9
[ "$a" > "$b" ]      # ✗ 字符串比较："10" < "9"（按字典序，'1' < '9'）→ 假
[ "$a" -gt "$b" ]    # ✓ 数值比较 → 真

# 字符串比较在 [ ] 里要转义 < >（否则被当成重定向！）
[ "$a" \> "$b" ]     # ✓ 但很难看
[[ "$a" > "$b" ]]    # ✓ [[ ]] 里不用转义

# 推荐：算术比较用 (( ))
if (( a > b )); then echo "a is bigger"; fi
# 变量名前不用加 $，支持 C 风格的运算符
(( a > 5 && b < 20 ))

常用测试运算符

运算符含义
-e path存在（文件或目录）
-f path存在且是普通文件
-d path存在且是目录
-L path是符号链接
-s path存在且大小 > 0
-r / -w / -x可读 / 可写 / 可执行（对当前用户）
-z str字符串为空
-n str字符串非空
f1 -nt f2f1 比 f2 新（修改时间）
f1 -ot f2f1 比 f2 旧

[[ ]] 的独门能力

# 1. 正则匹配 =~（不需要引号，引号会让它变成字面量）
if [[ $email =~ ^[a-zA-Z0-9._%+-]+@[a-zA-Z0-9.-]+\.[a-z]{2,}$ ]]; then
    echo "valid"
fi

# 捕获组存在 BASH_REMATCH 里
if [[ "v1.2.3" =~ ^v([0-9]+)\.([0-9]+)\.([0-9]+)$ ]]; then
    echo "major=${BASH_REMATCH[1]} minor=${BASH_REMATCH[2]} patch=${BASH_REMATCH[3]}"
fi

# 2. 通配符匹配（右侧不加引号才是模式）
[[ $file == *.log ]]      # ✓ 模式匹配
[[ $file == "*.log" ]]    # ✗ 引号让 * 变成字面量

# 3. 逻辑组合
[[ -f $f && -r $f ]] || die "file not readable"
[[ $x == a || $x == b ]]

# 4. 不需要给变量加引号（[[ ]] 内部不做分词）
[[ $var == "hello world" ]]     # 即使 var 含空格也安全
=~ 的右侧不要加引号。[[ $x =~ "^abc" ]] 匹配的是字面量 ^abc 而不是"以 abc 开头"。但如果你把正则存在变量里，引用变量时也不能加引号：re='^abc'; [[ $x =~ $re ]] ✓，[[ $x =~ "$re" ]] ✗。
模块 5

函数与返回值

Shell 函数最大的限制：返回值只能是 0~255 的整数。想返回字符串，只能靠 stdout。这个设计决定了 Shell 函数的写法和其他语言完全不同。

return 的真实含义

# return 设置的是"退出状态"，不是"返回值"
check_file() {
    [[ -f $1 ]] || return 1
    return 0
}

if check_file /etc/passwd; then echo "ok"; fi

# 返回值被截断成 8 位
f() { return 300; }
f; echo $?        # 44（300 mod 256）

# 负数也不行
f() { return -1; }
f; echo $?        # 255

怎么"返回字符串"

# 方案一：echo 到 stdout + 命令替换（最常用）
get_version() { echo "1.2.3"; }
ver=$(get_version)

# ⚠️ 陷阱：函数里的 log 输出会污染 stdout
get_version() {
    echo "fetching..." >&2      # 必须重定向到 stderr
    echo "1.2.3"
}

# 方案二：用全局变量（简单但不可重入）
compute() { RESULT=$(( $1 * 2 )); }
compute 21; echo "$RESULT"

# 方案三：nameref（bash 4.3+，最优雅）
compute2() { local -n out=$1; out=$(( $2 * 2 )); }
compute2 myvar 21; echo "$myvar"

local 与作用域

# 不加 local 就是全局变量（会污染调用者）
bad() {
    tmp="oops"       # 全局！
}
tmp="original"
bad
echo "$tmp"        # oops —— 被覆盖了

# 加 local
good() {
    local tmp="safe"
}
good
echo "$tmp"        # original

# ⚠️ 致命陷阱：local 会掩盖命令的退出码
f() {
    local out=$(false)     # local 自己返回 0，false 的失败被吞掉
    echo "still here"
}
set -e; f; echo "and here"   # 两行都打印

# 正确写法：分开声明和赋值
f() {
    local out
    out=$(false)           # 这行的退出码是 false 的，set -e 会生效
}

# 函数参数
greet() {
    local name="${1:-world}"
    local greeting="${2:-Hello}"
    echo "$greeting, $name"
}
greet "Alice" "Hi"     # Hi, Alice
greet                  # Hello, world

# $# $@ $* 在函数里指的是函数的参数，不是脚本的
命名规范：函数内部的临时变量一律 local。函数名前缀可以加业务域（db_connect、log_info），避免和外部命令撞名。不要把函数命名为 test、echo、ls 这类内置命令 —— 会覆盖掉它们。
模块 6

错误处理与 trap

脚本总会中途失败。问题不是"怎么避免失败"，而是"失败时能不能把现场清理干净"。trap 就是干这个的。

trap 的基本用法

# 语法：trap '要执行的命令' 信号名...

# 最常见的两个
trap 'rm -rf "$TMP"' EXIT        # 无论怎么退出都执行
trap 'echo "interrupted"; exit 130' INT TERM

# 完整的清理模板
cleanup() {
    local rc=$?
    [[ -n ${TMP:-} && -d $TMP ]] && rm -rf "$TMP"
    [[ -n ${LOCKFILE:-} && -f $LOCKFILE ]] && rm -f "$LOCKFILE"
    log "cleanup done (exit=$rc)"
    return $rc
}
trap cleanup EXIT

# 查看看当前设置了哪些 trap
trap -p

# 取消某个 trap
trap - EXIT

# 忽略某个信号（比如忽略 HUP，让脚本在终端关闭后继续跑）
trap '' HUP

ERR trap：出错时打印现场

# 这个 trap 在【任何命令返回非零】时触发（受 set -e 的例外规则影响）
set -Eeuo pipefail        # -E 让 ERR trap 传进函数和子 shell

trap 'echo "[ERR] line $LINENO: $BASH_COMMAND (exit=$?)" >&2' ERR

# 输出示例：
# [ERR] line 42: curl -fsS https://api.example.com (exit=22)

# 加调用栈（bash 4.4+ 的 FUNCNAME 数组）
trap 'echo "[ERR] line $LINENO in ${FUNCNAME[0]:-main}: $BASH_COMMAND" >&2' ERR

# 注意：ERR trap 不会在以下情况触发
#   - 命令在 if/while 条件里
#   - 命令是 && / || 的一部分（除了最后一个）
#   - 命令前有 !
#   和 set -e 的例外完全一致 —— 因为它们是同一套规则

set -x：调试利器

# 全局开 / 局部开（推荐，只包住可疑的一段）
set -x
set +x

# 自定义提示符，带上行号和函数名（强烈推荐）
export PS4='+[${BASH_SOURCE##*/}:${LINENO}:${FUNCNAME[0]:-main}] '
set -x
# 输出：+[deploy.sh:42:deploy] cp file1 file2

# 用子 shell 包住，退出后自动恢复
( set -x; risky_operation )

# 调试输出写到单独文件，不污染 stderr
exec 5> /tmp/debug.log
BASH_XTRACEFD=5

模块 7

四个高频模式

这四段代码几乎每个正经脚本都会用到。抄过去改改就能用。

① getopts 参数解析

#!/usr/bin/env bash
set -euo pipefail

usage() { echo "usage: $0 [-v] [-o output] <input>"; exit 2; }

verbose=0; output="out.txt"
# 开头的冒号：让 getopts 自己处理错误；选项后的冒号：该选项需要参数
while getopts ":vo:h" opt; do
    case $opt in
        v) verbose=1 ;;
        o) output=$OPTARG ;;
        h) usage ;;
        :) echo "option -$OPTARG requires an argument" >&2; exit 2 ;;
        \?) echo "unknown option: -$OPTARG" >&2; exit 2 ;;
    esac
done
shift $((OPTIND - 1))       # 去掉已解析的选项

[[ $# -eq 1 ]] || usage
input=$1
getopts 的三个限制：① 只支持短选项（-v），不支持 --verbose；② 选项必须在位置参数之前（cmd file -v 里 -v 不会被解析）；③ 不支持可选参数值。
需要长选项就用 getopt（注意不是 getopts，是外部命令）或者干脆手写 while [[ $# -gt 0 ]]; do case $1 in ...。

② 带时间戳的日志函数

# 输出到 stderr，避免污染 stdout（stdout 可能被管道接走）
log() {
    local level=$1; shift
    printf '%s [%-5s] %s\n' "$(date '+%F %T')" "$level" "$*" >&2
}
info()  { log INFO  "$@"; }
warn()  { log WARN  "$@"; }
die()   { log ERROR "$@"; exit 1; }

info "starting backup"
die  "cannot connect to database"

# 带颜色的版本（只在终端上色）
if [[ -t 2 ]]; then
    C_RED=$'\033[31m'; C_YEL=$'\033[33m'; C_OFF=$'\033[0m'
else
    C_RED=''; C_YEL=''; C_OFF=''
fi

# 用 printf 而不是 echo：echo 在不同 shell 里对 -n、-e、反斜杠的处理不一致
printf '%s\n' "hello"

③ mktemp 建临时文件

# 不要用 $$ 或 date 拼临时文件名 —— 会撞、会有竞争、会被预测
tmp=/tmp/myapp.$$          # ✗ 可预测，有符号链接攻击风险
tmp=/tmp/myapp.$(date +%s)  # ✗ 同一秒启动两个就撞了

tmp=$(mktemp)                       # ✓ 文件
tmpdir=$(mktemp -d)                  # ✓ 目录
tmp=$(mktemp /tmp/myapp.XXXXXX)      # ✓ 指定前缀，6 个 X 是占位符
tmp=$(mktemp -p /var/tmp)             # ✓ 指定目录

# 一定要配 trap 清理
tmpdir=$(mktemp -d)
trap 'rm -rf "$tmpdir"' EXIT

# 调试时想保留现场
trap '[[ -n ${KEEP_TMP:-} ]] || rm -rf "$tmpdir"' EXIT

④ read -r 逐行读文件

# 最正确的写法
while IFS= read -r line; do
    printf '%s\n' "$line"
done < "$file"

# 三个细节都不能省：
#  IFS=      保留行首行尾的空格/制表符
#  read -r   不把反斜杠当转义符（否则 Windows 路径会被吃掉）
#  < file    用重定向，不用 cat | while（后者让循环在子 shell 里跑）

# 错误写法：管道导致变量丢失
cat "$file" | while read line; do count=$((count+1)); done
echo "$count"     # 空！循环在子 shell 里

# 按分隔符拆字段
while IFS=: read -r user pass uid gid gecos home shell; do
    echo "$user -> $home"
done < /etc/passwd

# 最后一行没有换行符时会漏读，加个兜底
while IFS= read -r line || [[ -n $line ]]; do echo "$line"; done < "$file"
模块 8

静态检查：shellcheck

Shell 没有编译器帮你兜底，但 shellcheck 能补上大半。它做的不是"风格建议"，而是找出真正会出错的代码。每个项目都该在 CI 里跑。

它能抓什么

编号问题典型例子
SC2086变量没加引号（分词/glob）rm $file
SC2046命令替换没加引号rm $(find . -name x)
SC2155local 声明和赋值写在一起，掩盖退出码local x=$(false)
SC2181用 $? 判断，应该直接写 ifcmd; if [ $? -eq 0 ]
SC2164cd 没检查是否成功cd /tmp
SC2006用反引号，应该用 $()x=`date`
SC1090source 了动态路径，无法静态分析source "$DIR/x.sh"
SC2068用 $@ 而不是 "$@"for x in $@
# 安装
apt install shellcheck        # Debian/Ubuntu
brew install shellcheck       # macOS

# 基本用法
shellcheck script.sh

# 输出格式：gcc 风格（编辑器能直接跳转）
shellcheck -f gcc script.sh

# 只看严重级别 >= warning 的
shellcheck -S warning script.sh
# 级别：error > warning > info > style

# 指定 shell 方言（默认按 shebang 猜）
shellcheck -s bash script.sh
shellcheck -s sh script.sh

# 检查目录下所有 .sh
find . -name '*.sh' -exec shellcheck {} +

# 自动修复（只支持一小部分规则，慎用）
shellcheck -f diff script.sh | git apply

抑制误报

shellcheck 抓不到的三类问题：
① 逻辑错误。条件写反了、循环边界错了，它不知道你的意图。
② 并发问题。两个脚本同时写同一个文件，它看不出来。
③ 运行时依赖。命令存不存在、文件有没有权限，只有跑起来才知道。
所以 shellcheck 是下限保障，不是正确性证明。真正的验证还是要有测试 —— 哪怕只是一个在容器里跑一遍的 smoke test。
常见坑

十个真实踩过的坑

1
脚本没有 set -e，中间失败了还报成功
最经典的生产事故：备份失败但脚本 exit 0，监控一切正常，直到需要恢复时才发现文件是空的。每个脚本第一行都该是 set -euo pipefail。
2
rm -rf $DIR/ 里 DIR 为空
展开成 rm -rf /。用 ${DIR:?} 强制要求非空，或者写 rm -rf "${DIR:?}/"。这一条已经毁过无数台机器。
3
cd 失败后继续执行 rm -rf *
cd /app/build 失败（目录不存在），脚本仍在原目录跑 rm -rf *，删掉了不该删的东西。用 cd "$dir" || exit 1，或 set -e。
4
local x=$(cmd) 吞掉了 cmd 的失败
local 自己返回 0，set -e 看不到 cmd 失败。必须分开写：local x; x=$(cmd)。shellcheck 的 SC2155 就是抓这个。
5
((i++)) 在 set -e 下让脚本静默退出
i=0 时 i++ 表达式的值是 0，算术命令返回 1，脚本直接退出且没有报错。用 ((++i)) 或 i=$((i+1))。
6
cat file | while read 导致变量丢失
管道右边在子 shell 里执行，循环里改的变量外面看不到。用 while ... done < file 的重定向写法。
7
[ $x = yes ] 在 x 为空时报语法错误
展开成 [ = yes ]。永远给变量加引号，或者改用 [[ ]]。注意 [[ ]] 里变量不加引号也安全，这是它比 [ ] 好用的核心原因之一。
8
grep 没匹配到导致脚本中断
grep 在"没找到"时返回 1，这在 set -e 下会被当成错误。如果"没找到"是正常情况，写成 grep ... || true 或放进 if 条件里。
9
临时文件用 $$ 命名
PID 可预测、可复用，有符号链接攻击风险，多实例还会撞名。用 mktemp，并配 trap 清理。
10
用 echo 输出带反斜杠或 -n 的内容
echo 的行为在不同 shell 和不同版本间不一致（是否解释 -e、是否处理 \n）。需要精确控制就用 printf '%s\n' "$var"。
自测

六道题

1. 开了 set -e 之后，下面哪种情况命令失败【不会】导致脚本退出？
正确答案：if 条件里的命令。set -e 有五个例外：if/while/until 条件、&&/|| 的非最后一段、前面有 ! 的命令、管道非最后一段、算术表达式值为 0。
2. 参数是 a "b c" d 时，"$@" 展开成几个词？
正确答案：3 个。"$@" 保留每个参数的独立性，是转发参数的唯一正确写法。"$*" 才是用 IFS 首字符拼成 1 个字符串。
3. a=10, b=9，执行 [ "$a" > "$b" ] 的结果是？
正确答案：假。> 在 [ ] 里是字符串比较，按字典序 '1' < '9'。数值比较要用 -gt，或者用 (( a > b ))。
4. local out=$(false) 在 set -e 下会怎样？
正确答案：被吞掉。local 自己的退出码是 0，set -e 看不到 false 的失败。正确写法是 local out; out=$(false)，即 shellcheck SC2155。
5. 下面哪种方式能正确地把文件逐行读进循环并修改外部变量？
正确答案：重定向写法。管道会让 while 在子 shell 里执行，循环内的变量修改传不出来。for 循环则按空白分词，会把含空格的行拆散。
6. 命令超时被杀，timeout 返回的退出码是？
正确答案：124。这是 timeout 命令约定的"超时"退出码。130 是进程被 SIGINT（Ctrl-C）终止时的 128+2。
