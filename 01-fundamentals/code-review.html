二十分钟学会代码审查

代码审查是团队里性价比最高的知识传递机制，也是最容易变成互相挑刺的地方。这篇讲的是：看什么、不看什么、话怎么说、大 PR 怎么拆。

建议打开你团队最近一个 PR，用文末清单过一遍
开始前

先定标准：什么算"可以合并"

审查之所以经常吵架，往往不是因为技术分歧，而是因为双方对"合格"的定义不一样。先把标准写下来，后面所有的讨论都有依据。

标准含义
确实变好了合入后代码库的整体健康状况不下降。不是"完美"，是"比之前好"
解决真问题改动对应一个真实需求或缺陷，不是为了改而改
可维护三个月后别人能读懂、能改、能测
可回滚出问题时能独立回退，不牵连其他改动
关键取舍：审查的目标是"持续改善"，不是"达到完美"。如果一条评论只是"我会用另一种写法"，而两种写法都对 —— 那就不是必须改的项。把"必须改"和"建议"分开，是审查能长期维持的前提。
模块 1

双重目标：找缺陷，也传递知识

只盯着缺陷的审查，会退化成"抓错游戏"。作者开始防御，评论开始变短，最后大家只敢提交最小的改动，谁都不愿碰核心代码。

两个目标各自的价值

目标具体产出缺失后的后果
找缺陷边界、并发、错误处理、安全隐患被提前发现bug 流到线上，修复成本是审查时的 10~100 倍
传递知识作者学到项目约定；审查者了解新代码；团队形成共识知识集中在少数人身上，核心模块变成"只有他能改"

缺陷的价值可以量化：一个在审查阶段发现的空指针，修复成本是几分钟；同样的问题到了线上，是排查 + 热修 + 复盘 + 用户补偿。而知识传递的价值是隐性的 —— 它决定了半年后还有没有人敢动这块代码。

知识传递发生在哪

约定
"这个项目里所有外部调用都要设超时" —— 一句话让作者以后都不会再犯
历史
"这里之所以要加锁，是因为去年出过一次并发扣款事故" —— 代码里读不到的背景
取舍
"我们试过方案 A，但它在数据量超过 100 万时会退化，所以用了 B"
盲区
审查者问"这里为什么这么写"，作者被迫解释，往往自己就发现了问题

让知识传递真实发生的三个条件

评论要解释"为什么"，而不只是"改成这样"。只给结论的评论，作者只会照抄，下次照样犯。
允许作者反问。审查是讨论，不是判决。作者问"为什么"的时候，可能真的是你记错了约定。
把重复出现的问题沉淀成文档或 lint 规则。同一个问题被指出三次，说明该交给工具了，而不是继续靠人记。
最常见的失衡：审查变成单向输出。资深工程师写 20 条评论，初级工程师全部照改，一句不问。看起来效率很高，实际上作者没有建立判断力 —— 三个月后同样的 20 条还会再出现一次。
模块 2

该看什么：按优先级排序

审查时间有限，必须按"出错代价"排序。下面七类，从上到下优先级递减。前四类不改就不能合，后三类可以商量。

#检查项典型问题代价
1正确性逻辑写反、条件漏判、算法用错、单位不一致功能直接不可用
2边界条件空集合、0、负数、超长字符串、时区、闰年低频但必然发生的线上故障
3错误处理吞异常、只打日志不处理、失败后状态不一致故障时静默失败，排查极难
4并发安全共享可变状态、非原子读改写、锁粒度、死锁偶发、难复现、影响面大
5安全风险注入、越权、密钥硬编码、日志泄露敏感信息可能是一次事故级事件
6可读性命名、函数过长、嵌套过深、魔法数字影响长期维护成本
7测试覆盖新分支没测、只测 happy path后续改动没有安全网

第一类：正确性

先不看细节，先回答一个问题：这段代码做的事，和 PR 描述说的是同一件事吗？很多严重问题不是写错了，是写偏了。

# 常见形态：条件写反、边界用错、单位混用
if user.balance > amount:          # ✗ 余额刚好等于金额时应该允许支付
if user.balance >= amount:         # ✓

timeout = 30                       # ✗ 注释说要 30 秒，但下游 SDK 单位是毫秒
timeout_ms = 30 * 1000             # ✓ 变量名带上单位

total = price * quantity           # ✗ 金额用 float，0.1+0.2 != 0.3
total = Decimal(price) * quantity  # ✓

第二类：边界条件

边界要问的问题
空 / null空列表、空字符串、null 对象，每个都会走哪条路径？
零与负数数量为 0 时会不会除以零？金额为负会不会退钱给用户？
极大值一次查 10 万条会不会 OOM？分页参数传 100000 呢？
时间跨天、跨月、闰年、夏令时、时区不一致
编码与长度emoji（4 字节）、超长字符串、前后空格
重复与顺序同一请求发两次会怎样？消息乱序到达会怎样？

第三类：错误处理

# ✗ 吞掉异常，故障时完全静默
try:
    charge(order)
except Exception:
    pass

# ✗ 只打日志，但上层以为成功了
try:
    charge(order)
except Exception as e:
    logger.error("charge failed", exc_info=e)
    return True

# ✓ 明确失败语义，让调用方必须处理
try:
    charge(order)
except PaymentError as e:
    logger.error("charge failed", extra={"order_id": order.id}, exc_info=e)
    raise OrderPaymentFailed(order.id) from e

要重点看的三件事：失败后状态是否一致（扣了库存但没生成订单？）、重试是否安全（幂等键有没有）、错误信息是否够定位（有没有带上关键 ID）。

第四类：并发安全

  • 读-改-写不是原子操作：if (stock > 0) stock-- 在并发下会超卖。要用数据库条件更新、原子操作或锁。
  • 共享可变状态：单例里的成员变量、静态缓存、全局 map。多线程下必须用并发容器或加锁。
  • 锁的范围：锁太小保护不住，锁太大吞掉吞吐。特别要看锁内有没有网络调用。
  • 锁顺序：两处代码以不同顺序获取两把锁，就是死锁。
  • 双重检查的可见性：懒加载单例忘了 volatile，可能拿到半初始化对象。

第五类：安全风险

风险在 diff 里长什么样
SQL 注入字符串拼接 SQL："SELECT * FROM t WHERE id=" + id
命令注入Runtime.exec("sh -c " + userInput)、os.system(...)
越权只校验了登录，没校验"这个资源是不是你的"
密钥硬编码AK/SK、数据库密码直接写在代码或配置文件里
敏感信息落日志打印完整请求体，里面含身份证、token、银行卡
不安全的反序列化对不可信输入做 pickle / Java 原生反序列化
路径穿越用户传入的文件名直接拼到路径上，没做规范化校验

第六、七类：可读性与测试

可读性只看三件事：命名是否说了它是什么、函数是否只做一件事、嵌套是否超过三层。测试只看两件事：新增的分支有没有测、断言是不是真的在验证行为。

时间不够时的取舍：先扫一遍 diff 的文件列表和函数签名（3 分钟），再重点看涉及金额、权限、状态流转、并发的那几十行。80% 的严重问题集中在 20% 的代码里，剩下的格式问题交给工具。
模块 3

不该纠结什么：交给工具

任何"能被机器判定"的问题，都不该占用人的注意力。人肉检查格式，既慢又不一致，还容易变成权力展示。

不该在评论里说应该由谁管
缩进、换行、引号、分号格式化工具（gofmt / Prettier / ruff format / google-java-format）
命名风格（camelCase / snake_case）linter 规则 + 项目约定文档
未使用的变量、importlinter
圈复杂度、函数长度linter 阈值 + CI 门禁
明显的类型错误类型检查器（mypy / tsc / pyright）
已知的漏洞写法静态扫描（Semgrep / CodeQL / gitleaks）
"我觉得这样更好看"不该出现。没有客观依据的偏好，不该阻塞别人

为什么这条边界这么重要

因为人的注意力是审查中最稀缺的资源。一条 PR 有 30 条评论，其中 25 条是格式问题，作者会形成"这些评论都不用认真看"的习惯 —— 剩下 5 条真正重要的，也会被一起忽略。

"个人偏好"是最难识别的。它常常伪装成技术意见："我习惯用 for 循环而不是 stream""我觉得这个类应该叫 XxxManager"。判断标准很简单：你能说出一条会导致实际问题的理由吗？说不出，就是偏好。

约定怎么落地

层级手段强制性
格式提交前自动格式化（pre-commit hook）+ CI 校验强制，不通过不能合
风格linter 配置文件入库，全团队共用一份强制
架构约定文档 + 示例代码 + 审查时指出建议，允许有理由的例外
领域知识只能靠审查和口头传递讨论
一条实用规则：同一个问题如果被人在审查里指出超过三次，就该写进 linter 规则或文档。反复用人脑检查机器能查的东西，是团队效率的净损失。
模块 4

评论的写法：让人愿意改

同样一个问题，写法不同，接受度差好几倍。核心不是"委婉"，而是信息完整 + 明确优先级。

提问式 vs 命令式

写法效果
"这里应该用 try-with-resources"命令式。如果作者有理由，会觉得被压制
"这个流在异常时会不会没关闭？"提问式。给出思考方向，作者自己得出结论
"必须改成 X"只适用于有硬性依据（安全、规范、已知 bug）

提问式的隐含前提是：你可能不知道全部背景。作者可能确实有理由（比如这个流由框架关闭）。命令式一旦判断错，就很难下台。

用标签分级

标签含义作者该怎么做
must必须改，否则不合改，或给出充分理由反驳
should强烈建议改，或有理由地说明不改
nit吹毛求疵，可忽略有空就改，不改也能合
question我不理解，请解释回答，可能顺带发现 bug
praise这里写得好不用做任何事
# 没有标签：作者不知道哪条必须改
这里要加超时
命名不太好
这个循环可以优化

# 有标签：优先级一目了然
must: 这个 HTTP 调用没设超时，下游卡住会把线程池占满（参考上次 P1 事故）
should: 建议把 orderList 改成 pendingOrders，这里装的是待处理订单
nit: 这行可以合并到上面，纯属个人偏好，不改也行
question: 这里为什么用 for 而不是批量接口？是有意避免大请求吗

给建议，而不是只指出问题

# ✗ 只说问题
这个查询在数据量大时会很慢。

# ✓ 指出问题 + 给出方向 + 说明代价
这个查询在 order 表超过 100 万行时会全表扫描（where 里 create_time 没索引）。
建议加 (user_id, create_time) 的联合索引，或者把时间范围收窄到 7 天内。
前者要改表结构，后者会改变产品语义，你判断哪个更合适。

# ✓✓ 更好的做法：直接给 patch
```suggestion
WHERE user_id = ? AND create_time >= ?
```
"给建议"不等于"替对方写代码"。对于小而明确的问题，直接提 suggestion 最快；对于设计层面的问题，给方向 + 让作者决定更合适。审查者的角色是提供信息和判断依据，不是替作者做决定。

三个让评论变糟的习惯

  • 反问带情绪："你有没有想过并发？" —— 这不是提问，是质疑能力。改成"这里两个线程同时进来会怎样"。
  • 一次贴 30 条：作者会直接放弃逐条讨论。分批提，先提 must，改完再看下一轮。
  • 只贴链接："参考 Clean Code 第 3 章" —— 对方不一定有这本书，也不一定有时间读。把结论写出来。
一个简单有效的模板：「现象 + 为什么是问题 + 建议怎么做 + 优先级标签」。四句话，作者不用猜你的意图，也不用追问。
模块 5

大 PR 怎么审：分层，而不是逐行

一个 2000 行的 PR，逐行读到最后必然注意力涣散。正确的做法是先看骨架，再看肌肉，最后看皮肤。

第一层：接口契约（5 分钟）

只看对外暴露的东西：函数签名、API 路径与参数、数据结构、数据库表结构、消息格式。这一层决定了这个改动会不会影响别人。

看什么要问的问题
函数签名参数是不是太多？返回值能不能表达失败？命名是否准确？
API 变更是不是破坏性变更？老客户端还能用吗？要不要版本化？
数据结构字段可空吗？默认值是什么？加了必填字段会不会让老数据挂掉？
数据库加索引会不会锁表？迁移脚本可回滚吗？大表加字段的默认值怎么处理？
接口层的错误最贵。内部实现写错了，改一个函数就行；接口发布出去再改，要兼容老客户端、要写迁移、要通知上下游。所以审查时间应该优先花在签名和数据结构上。

第二层：核心逻辑（15 分钟）

跳过样板代码（getter、DTO 转换、配置加载），直接找有分支、有状态、有循环、有外部调用的函数。这些是 bug 的栖息地。

  • 主流程能不能用三句话说清？说不清说明抽象有问题。
  • 每个 if 的 else 分支去哪了？是有意省略还是漏了？
  • 状态流转有没有非法路径（比如从"已取消"直接到"已发货"）？
  • 外部调用有没有超时、重试、降级？

第三层：细节（5 分钟）

命名、注释、日志、错误信息、测试。这一层可以快速扫，发现问题标 nit 或 should，不值得阻塞合并。

为什么超过 400 行就该拆

PR 大小审查质量典型后果
< 100 行能逐行细看缺陷发现率最高，评论具体
100 ~ 400 行能看完，但会跳过部分可接受，适合单个功能点
400 ~ 1000 行只能扫读评论变成"看起来没问题"，LGTM 变成形式
> 1000 行基本没人真读等于没有审查，事故后才发现

拆的原则不是"按文件拆"，而是按可独立理解和回滚的单元拆：

先拆重构与功能。重命名、移动文件、格式化单独一个 PR，功能改动另一个。混在一起，diff 全是移动，看不出真实改动。
按层拆。数据层（表结构 + DAO）、逻辑层、接口层，各自可独立合并和回滚。
用 feature flag 隔离。代码可以先合进去但默认关闭，这样每个 PR 都小而完整，上线时机另行控制。
机械改动单独提。批量改 import、升级依赖版本、自动格式化 —— 这些 diff 巨大但风险低，应该单独一个 PR 并快速通过。
拆 PR 的隐性收益：小 PR 合得快，作者不用等一天；合得快，就能更早发现设计问题；发现问题早，返工成本就低。这是一个正反馈，大 PR 则是负反馈。
模块 6

被审查时怎么做

这一节比上一节更重要，因为它决定了团队敢不敢提意见。一个防御性强的作者，会让整个团队的审查质量下降。

把"人和代码"分开

收到的话防御性解读（错）中性解读（对）
"这里可能有并发问题"他觉得我不懂并发他指出一个我没想到的场景
"这个命名不清楚"他在挑刺我的命名对别人确实不直观
"建议拆成两个函数"他否定我的设计这是一个可讨论的重构建议

一个实用的心理技巧：把评论当成"未来的你在读这段代码时的困惑"。审查者只是提前替未来的维护者问了一句。

不同意的正确姿势

# ✗ 无效回应
"我觉得这样没问题。"                  # 没有信息量
"一直这么写的。"                      # 诉诸传统
"你说得对，我改。"                    # 表面顺从，实际没理解，下次还犯

# ✓ 有效回应：给出依据，或者承认不确定
"这里加锁会阻塞 200ms，因为锁内有一次 DB 查询。
 我改成乐观锁（version 字段），冲突时重试 3 次，可以吗？"

"我不确定这里会不会有并发。这个入口目前只有定时任务调用，单实例部署。
 如果以后要多实例，确实需要加锁，要不要现在就先加上？"

有效回应有三个特征：给出事实依据、承认不确定的部分、提出替代方案。三者有其一，讨论就能推进。

回复的时效与礼貌

  • 当天回复。超过一天的 PR，作者已经在做别的任务，上下文切换成本很高。
  • 逐条回复，包括不改的。不回复会让审查者不知道你是没看到还是不同意。
  • 改了之后留个"已改"。让人知道这轮讨论结束了，不用再翻一遍 diff。
  • 感谢具体的那一条，而不是笼统的"谢谢 review"。具体感谢说明你真的读了。
最伤团队的一种行为：把审查意见当成"审批障碍"。绕过审查直接合、找人"快速 LGTM"、在群里抱怨"又被卡了" —— 这些做法的代价会在半年后以"没人敢改核心模块"的形式还回来。
模块 7

可复用的审查清单

清单的价值不是"每次都全过一遍"，而是在你看不出问题时，提供一个兜底。熟练之后大部分项会变成下意识动作。

通用项（任何语言都适用）

类别检查点
正确性逻辑与 PR 描述一致；条件边界正确；单位统一；金额用定点数
空值可能为 null 的返回值都处理了；空集合不会导致除零或越界
错误处理没有空的 catch；异常带上关键上下文；失败后状态一致
资源连接、文件、流、锁都在 finally / try-with-resources 里释放
外部调用有超时；有重试且幂等；有降级或熔断
并发共享可变状态有保护；锁内无网络调用；锁顺序一致
安全无字符串拼接 SQL / 命令；有资源归属校验；无硬编码密钥；日志脱敏
数据迁移可回滚；大表加索引评估过锁表；新字段有默认值
兼容接口变更向后兼容；老数据能读；灰度期间新旧版本能共存
可观测关键路径有日志和指标；错误日志能定位到具体请求
测试新增分支有对应用例；断言具体；没有 sleep 等待

语言特定项

语言重点检查
Javaequals/hashCode 成对重写；集合初始化容量；Optional 不滥用；Stream 里不要有副作用；线程池不要用 Executors 默认工厂（无界队列）
Goerror 必须检查；goroutine 有退出路径（context）；defer 在循环里；slice 共享底层数组导致的意外修改；map 并发读写
Python可变默认参数（def f(x=[])）；裸 except；循环里字符串拼接；忘记 close 的文件
JS / TS== 与 ===；浮点金额；未处理的 Promise rejection；闭包捕获循环变量；any 泛滥
SQLWHERE 条件是否命中索引；有没有 SELECT *；隐式类型转换导致索引失效；N+1 查询

按 PR 类型的侧重

新功能
重点看接口设计、边界、错误语义。先问"这个功能不做什么"，边界往往比功能本身更容易出问题
Bug 修复
重点看根因是否被修掉，而不是症状。有没有对应的回归测试？会不会引入新问题？
重构
重点看行为是否完全不变。有没有测试保护？diff 里有没有混入功能改动？
依赖升级
看 changelog 里的 breaking change；锁文件是否一致；有没有引入新的传递依赖
配置 / 脚本
看默认值是否安全；密钥是否外置；脚本有没有 set -e；路径是否带引号
数据库迁移
可回滚吗？大表操作会不会锁表？执行时长评估过吗？回滚脚本测过吗？
模块 8

自动化能替代什么

把机器能做的交给机器，人才有余力做机器做不到的：判断设计是否合理、边界是否遗漏、这段代码三个月后还能不能改。

工具类型能替代的审查项代表工具
格式化缩进、换行、引号、行宽 —— 100% 可替代gofmt、Prettier、ruff format、google-java-format
Lint未使用变量、可疑写法、复杂度阈值、常见 bug 模式golangci-lint、ESLint、Ruff、Checkstyle、clang-tidy
类型检查类型不匹配、可能为 null、参数个数错误mypy、pyright、tsc、Flow
安全扫描注入、硬编码密钥、已知漏洞依赖、危险 APISemgrep、CodeQL、gitleaks、Trivy、npm audit
测试门禁改动是否让测试失败、覆盖率是否下降CI + diff-cover + jacoco
依赖检查许可证、版本冲突、过期依赖Dependabot、Renovate

机器替代不了的

只有人能判断的为什么
需求是否正确代码可以完美实现一个错误的需求，所有工具都会说"通过"
边界是否遗漏工具只能检查你写了的分支，无法告诉你"少了一个场景"
抽象是否合理分层、职责、耦合，取决于未来的演化方向
可运维性这个改动上线后怎么排查？回滚要多久？
团队约定不成文的领域知识，只存在于人的脑子里

自动化的真正价值不是"省时间"，是"消除争论"。格式有分歧时，不用讨论谁对，跑一下格式化工具即可。把主观问题变成客观问题，团队就少了一半的摩擦。
别让 CI 变成噪音源。如果 lint 报了 500 个历史遗留问题，新 PR 一提交就满屏红色，所有人都会学会忽略它。正确做法：先修历史问题或加白名单，再开启门禁，保证红色永远意味着"这次改动有问题"。
常见坑

十个代码审查中的典型错误

1
把格式问题混进技术讨论
30 条评论里 25 条是缩进和命名，真正重要的 5 条被淹没。格式交给工具，别占人的注意力。
2
评论不带优先级
作者不知道哪条必须改、哪条可以不理，只能全部照改或全部忽略。用 must / should / nit 分级。
3
只说"这里有问题"，不给方向
作者要猜你的意图，来回好几轮。给出"现象 + 为什么 + 建议"，一轮就能收敛。
4
LGTM 式橡皮图章
1000 行的 PR 五分钟就 approve，等于没有审查。要么认真看，要么明确说"我只看了接口层"。
5
一次提几十条评论
作者会直接放弃逐条讨论，或者机械地全改一遍。分批提，先解决 must。
6
用审查展示权力
"这个我一眼就看出来了""你应该知道这个规范"。结果是团队不敢提 PR，也不敢在 PR 里写不成熟的方案。
7
作者防御性强，把意见当人身攻击
讨论会迅速降温，审查者下次就只挑无关痛痒的说。把人和代码分开，是作者的责任。
8
重构和功能混在一个 PR
diff 里全是文件移动，看不出真实改动，reviewer 只能跳过。重构单独提，功能单独提。
9
只审代码，不审数据迁移和回滚
代码没问题，但迁移脚本锁表 20 分钟、且不可回滚。这类改动要单独评估执行时长和回滚方案。
10
同一个问题指出五次还不写进规则
说明该交给 linter 或文档了。反复用人脑检查机器能查的东西，是团队的净损失。
自测

六道题

1. 审查一个 1500 行的 PR，最合理的做法是？
正确答案：分层看 + 建议拆分。1500 行逐行读必然注意力涣散，实际效果等于没读。接口层的错误代价最高，应该优先看。
2. 下面哪条评论不该出现在代码审查里？
正确答案：纯个人偏好。说不出会导致什么实际问题的意见，不该阻塞别人。命名问题应该由 linter 规则或团队约定来管。
3. 作者不同意某条审查意见，最好的回应方式是？
正确答案：给依据 + 提替代方案。审查是讨论，不是判决。有理由的不同意完全合理，但必须让对方能判断你的理由是否成立。
4. 一个 PR 里同时做了"重命名文件"和"修改业务逻辑"，问题是什么？
正确答案：改动被掩盖。Git 会把重命名显示成大量删除 + 新增，真实逻辑改动藏在里面。机械改动和功能改动应该分开提。
5. 哪一项是自动化工具无法替代人工审查的？
正确答案：遗漏的边界场景。工具只能检查你写了的分支，无法告诉你"少写了一个 if"。这需要理解业务和需求。
6. 团队里同一条规范被审查指出过五次，最该做的是？
正确答案：沉淀成规则。反复用人脑检查机器能查的东西是净损失。写进 linter 或文档后，新人和老人都不会再犯。
