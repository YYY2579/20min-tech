二十分钟配好你的开发环境

开发环境的目标不是"看起来专业"，而是换台机器半小时能干活、别人 clone 下来行为一致。这篇讲清编辑器怎么选、settings.json 该改哪几项、三种远程模式的区别，以及大项目卡顿到底卡在哪。

建议打开 VS Code 跟着改：Ctrl+Shift+P → Open User Settings (JSON)
开始前

先建一个能承载配置的项目

下面所有配置都落在两类文件里：用户级（跟着你走，换项目不变）和工作区级（跟着项目走，提交到仓库）。先建一个项目目录，把工作区配置放进去。

# 建项目与工作区配置目录
mkdir -p demo/.vscode && cd demo
git init
printf 'node_modules/\ndist/\n.env\n' > .gitignore

# 工作区级配置：只放"这个项目必需"的东西，提交到仓库
cat > .vscode/settings.json <<'EOF'
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "files.eol": "\n"
}
EOF

# 推荐的扩展列表，别人打开项目时 VS Code 会提示安装
cat > .vscode/extensions.json <<'EOF'
{
  "recommendations": [
    "dbaeumer.vscode-eslint",
    "esbenp.prettier-vscode",
    "editorconfig.editorconfig"
  ]
}
EOF

# 看当前装了哪些扩展（排查冲突时很有用）
code --list-extensions | sort
先分清两个概念，后面全靠它：用户配置（User Settings）是全局的，放主题、字体、快捷键这类个人偏好；工作区配置（Workspace Settings）在 .vscode/settings.json，只对当前项目生效，应该提交到仓库。把个人主题写进工作区配置，是全组被迫用你的配色方案的经典原因。
模块 1

编辑器怎么选：场景问题，不是信仰问题

选项强在哪弱在哪适合谁
VS Code生态最大、远程开发体验最好、启动快、免费大型单体项目索引慢；Java 等重语言的重构能力弱于 JetBrains绝大多数后端、前端、运维、脚本开发
JetBrains 系
IDEA / GoLand / PyCharm		代码理解最深：重构、跳转、数据库工具、框架感知（Spring、Django）吃内存（单项目 2~4GB 常见）、启动慢、收费重度 Java/Kotlin、大型 Python/Go 单体、需要深度重构
Neovim极轻、纯键盘操作、SSH 进任何机器都能用、可完全定制配置成本极高（LSP、补全、调试都要自己拼）；团队协作难统一长期在终端工作、愿意把配置当项目维护的人

三条实际建议：

  • 不要为"哪个更好"争论。真正的判据是：你一天里有多少时间在做"跨文件重构"。超过一半，JetBrains 值那个内存；否则 VS Code 足够。
  • 可以混用。日常写代码用 VS Code，遇到大规模重命名/提取接口时用 IDEA 打开同一个目录，很常见也很合理。
  • 团队应该统一"格式化与 lint"，而不是统一编辑器。用 .editorconfig + 项目内的 formatter 配置，谁用什么编辑器都能产出一样的代码。
一个被低估的判据：远程开发能力。如果你的代码最终跑在 Linux 服务器上，而你在 Windows 或 macOS 上开发，那么"能不能把编辑器连着远端跑"比"补全快 50ms"重要得多。VS Code 在这件事上目前最成熟，JetBrains 也有 Gateway，Neovim 天生就在终端里。
模块 2

VS Code 核心配置：只改这十几项

settings.json 有上千个配置项，但真正影响日常的不到二十个。下面这份是"用户级"的起点，可以直接抄。

// 用户级 settings.json（Ctrl+Shift+P → Open User Settings (JSON)）
{
  // ---------- 编辑体验 ----------
  "editor.formatOnSave": true,
  "editor.formatOnPaste": false,
  "editor.tabSize": 2,
  "editor.rulers": [100],
  "editor.minimap.enabled": false,
  "editor.stickyScroll.enabled": true,
  "editor.largeFileOptimizations": true,

  // ---------- 文件 ----------
  "files.eol": "\n",
  "files.insertFinalNewline": true,
  "files.trimTrailingWhitespace": true,
  "files.autoSave": "onFocusChange",

  // ---------- 保存时自动修 ----------
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit",
    "source.organizeImports": "explicit"
  },

  // ---------- 搜索与监听（大项目必配） ----------
  "search.exclude": {
    "**/node_modules": true,
    "**/dist": true,
    "**/.git": true,
    "**/coverage": true
  },
  "files.watcherExclude": {
    "**/node_modules/**": true,
    "**/dist/**": true,
    "**/.git/objects/**": true
  },

  // ---------- 终端与 Git ----------
  "terminal.integrated.defaultProfile.windows": "Git Bash",
  "git.autofetch": true,
  "git.confirmSync": false,

  // ---------- 关掉不需要的 ----------
  "telemetry.telemetryLevel": "off",
  "workbench.startupEditor": "none",
  "update.showReleaseNotes": false
}
配置项为什么值得改
files.eol: "\n"Windows 默认 CRLF，会让 Git diff 出现整文件变更。统一 LF 是跨平台协作的第一条
editor.codeActionsOnSave保存时自动修 lint 并整理 import。值要写 "explicit"，新版 VS Code 已不接受布尔值
files.watcherExclude不排除 node_modules 会让文件监听句柄暴涨，Linux 上直接撞 inotify 上限
search.exclude搜索时不扫构建产物，结果更准、速度更快
editor.largeFileOptimizations打开几 MB 的压缩文件时不卡死（会关闭部分语法功能）
editor.formatOnPaste建议关。粘贴一段别人的代码就被重排，diff 会变得不可读

工作区配置该放什么

// .vscode/settings.json —— 提交到仓库，只放项目相关
{
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.formatOnSave": true,
  "eslint.workingDirectories": [{ "mode": "auto" }],
  "python.defaultInterpreterPath": "./.venv/bin/python",
  "go.testFlags": ["-v", "-count=1"],
  "[markdown]": { "editor.formatOnSave": false }
}

// ✗ 不要提交这些（个人偏好，属于用户配置）
// "workbench.colorTheme"、"editor.fontSize"、"editor.fontFamily"
// "terminal.integrated.fontSize"、"window.zoomLevel"

快捷键自定义

// keybindings.json（Ctrl+Shift+P → Open Keyboard Shortcuts (JSON)）
[
  { "key": "ctrl+alt+l", "command": "editor.action.formatDocument" },
  { "key": "ctrl+alt+t", "command": "workbench.action.terminal.toggleTerminal" },
  {
    "key": "ctrl+shift+r",
    "command": "workbench.action.quickOpen",
    "when": "editorTextFocus"
  }
]
配置优先级要记清：工作区 > 用户，语言专属（"[python]"）> 通用。所以你在用户配置里开了 formatOnSave，但项目里关了，最终是关。排查"为什么我的配置不生效"时，第一步永远是看有没有更高优先级的覆盖。
模块 3

必备扩展：五类，别超过十五个

扩展不是越多越好。每个扩展都会占用启动时间、内存和快捷键，而且它们之间会抢同一个功能（比如三个格式化插件同时想接管保存事件）。按类装，每类一个。

类别推荐说明
语言支持Python / Pylance、Go、rust-analyzer、Java Extension Pack提供跳转、补全、诊断。官方或语言团队维护的优先
LintESLint、Ruff、golangci-lint只装一个，且与 CI 用同一份配置，否则"本地过了 CI 挂"
格式化Prettier、Ruff formatter、gofmt同一语言只能有一个默认格式化器，否则保存时互相覆盖
Git 增强GitLens、Git Graph看每行是谁改的、看分支图。GitLens 功能多但偏重，可按需关功能
远程开发Remote - SSH、Dev Containers、WSL三个可以同时装，按场景选一个用
通用辅助EditorConfig for VS Code、Error Lens、Docker、YAMLEditorConfig 必装，保证跨编辑器一致
# 命令行装扩展（适合写进初始化脚本）
code --install-extension dbaeumer.vscode-eslint
code --install-extension esbenp.prettier-vscode
code --install-extension editorconfig.editorconfig
code --install-extension ms-vscode-remote.remote-ssh

# Developer: Startup Performance

# 怀疑某个扩展有问题：命令面板执行
# Help: Start Extension Bisect（二分法自动定位元凶）

# 给当前工作区禁用某个扩展（不影响其他项目）
# 扩展面板 → 齿轮 → Disable (Workspace)
三个真实的冲突场景：① Prettier 和 ESLint 都开了 formatOnSave，保存一次格式化两遍，光标乱跳；② 两个 Python 语言服务器同时启用，补全候选出现重复项；③ 装了三个主题/图标包，启动时互相覆盖，界面闪烁。判断方法：禁用一半扩展，看问题是否消失，二分定位。
模块 4

远程开发：SSH、容器、WSL 的区别

三种模式的共同点是：编辑器界面在你本地，代码、语言服务、终端、调试器都在"另一边"。区别在"另一边"是什么。

模式代码在哪解决什么问题不适合
Remote SSH远端服务器（开发机、跳板机）本地机器性能不够；代码必须跑在内网；团队共用一台大机器网络不稳定时体验很差；断线会中断长任务
Dev Containers本机或远端的 Docker 容器环境一致性：新人 clone 后一键得到完全相同的工具链；多项目依赖隔离需要 Docker；GUI 程序、内核模块调试不方便
WSLWindows 上的 Linux 发行版Windows 上需要 Linux 工具链（bash、gcc、systemd 生态）项目放在 /mnt/c 时 IO 极慢

为什么容器化开发环境能解决"我这能跑"

"我这能跑"的本质是环境未声明：运行时版本、系统库、全局工具、环境变量，全靠口头传承和手工安装。容器把这些写成文件，于是环境变成了可版本化、可复制、可评审的制品。

# .devcontainer/devcontainer.json —— 一个能用的最小配置
{
  "name": "order-api-dev",
  "build": { "dockerfile": "Dockerfile" },
  "remoteUser": "vscode",
  "forwardPorts": [8080, 5432],
  "postCreateCommand": "make setup",
  "mounts": [
    "source=${localEnv:HOME}/.ssh,target=/home/vscode/.ssh,type=bind,readonly"
  ],
  "customizations": {
    "vscode": {
      "extensions": ["golang.go", "editorconfig.editorconfig"],
      "settings": { "go.testFlags": ["-v"] }
    }
  }
}
# .devcontainer/Dockerfile —— 环境声明，和代码一起进 Git
FROM mcr.microsoft.com/devcontainers/go:1.22

# 装系统依赖（版本写死，别用 latest）
RUN apt-get update && apt-get install -y --no-install-recommends \
      postgresql-client jq \
    && rm -rf /var/lib/apt/lists/*

# 装项目工具（版本写死）
RUN go install github.com/golangci/golangci-lint/cmd/golangci-lint@v1.59.1
容器化环境带来的四个具体收益：① 新人 onboarding 从一天变成十分钟，只需装 Docker 和 VS Code；② 依赖不再互相污染，项目 A 要 Go 1.20、项目 B 要 1.22，各用各的容器；③ CI 和本地用同一个镜像，"CI 上能过本地不过"的问题大幅减少；④ 环境变更可评审，改 Dockerfile 走 PR，而不是"我在机器上装了个东西"。
WSL 的一个硬坑：文件系统。代码放在 Windows 盘（/mnt/c/...）时，每次文件读写都要跨文件系统转换，大型项目 npm install 可能慢 5~10 倍，文件监听也容易失效。正确做法是把代码放在 WSL 自己的文件系统里（如 ~/projects），从 Windows 侧通过 \\wsl$\ 访问。
模块 5

调试配置：launch 与 attach 的区别

调试配置的核心只有两个字段：request 是 launch 还是 attach。launch 是"由调试器启动进程"，attach 是"连上一个已经在跑的进程"。搞错这两个，就会出现"点了调试没反应"或"断点不生效"。

模式谁启动进程典型场景
launch调试器本地跑一个脚本、启动 dev server、跑单个测试
attach别人（容器、systemd、IDE 外部）调试容器里的进程、调试已启动的服务、远程调试
// .vscode/launch.json —— 四种最常用的配置
{
  "version": "0.2.0",
  "configurations": [
    {
      // 1) Node：用 npm 脚本启动，输出到集成终端
      "name": "dev server",
      "type": "node",
      "request": "launch",
      "runtimeExecutable": "npm",
      "runtimeArgs": ["run", "dev"],
      "console": "integratedTerminal",
      "skipFiles": ["<node_internals>/**"],
      "envFile": "${workspaceFolder}/.env",
      "autoAttachChildProcesses": true
    },
    {
      // 2) Node：attach 到一个已启动的进程（容器内调试常用）
      "name": "attach to node",
      "type": "node",
      "request": "attach",
      "port": 9229,
      "address": "127.0.0.1",
      "localRoot": "${workspaceFolder}",
      "remoteRoot": "/app",
      "restart": true
    },
    {
      // 3) Python：调试 Flask，不进第三方库源码
      "name": "python: flask",
      "type": "debugpy",
      "request": "launch",
      "module": "flask",
      "env": { "FLASK_APP": "app.py", "FLASK_DEBUG": "1" },
      "args": ["run", "--no-debugger"],
      "justMyCode": true
    },
    {
      // 4) Go：attach 到 delve 起的调试服务（容器/远端）
      "name": "go: remote attach",
      "type": "go",
      "request": "attach",
      "mode": "remote",
      "host": "127.0.0.1",
      "port": 2345,
      "substitutePath": [
        { "from": "${workspaceFolder}", "to": "/app" }
      ]
    }
  ],
  "compounds": [
    {
      "name": "api + worker",
      "configurations": ["dev server", "attach to node"],
      "stopAll": true
    }
  ]
}
字段作用与常见错误
program / module入口文件或模块。路径要写 ${workspaceFolder} 开头的绝对路径，相对路径容易解析错
cwd工作目录。读配置文件、找模板相对路径时全靠它
env / envFile环境变量。不要把生产密钥写进 launch.json，用 envFile 指向被 gitignore 的文件
consoleintegratedTerminal 能接受输入，internalConsole 不能。需要交互的程序必须用前者
preLaunchTask启动前跑构建任务，对应 tasks.json 里的 label。label 写错会导致调试静默不启动
sourceMapsTypeScript 等编译型语言必须开，否则断点位置对不上
justMyCode只调试自己的代码。排查第三方库问题时要设 false
substitutePath本地与远端路径映射。容器调试断点不生效，90% 是这个没配
生产环境绝对不要开远程调试端口。Node 的 --inspect、Go 的 delve、Java 的 JDWP 都是无认证的远程代码执行入口——连上就能读内存、改变量、调任意函数。调试端口只能绑 127.0.0.1，通过 SSH 隧道访问，且只在排查期间临时开启。
模块 6

代码片段与模板：把重复劳动消掉

判断该不该做 snippet 的标准很简单：同一个结构你一天内手写过三次以上。snippet 的价值不是"少打几个字"，而是保证结构一致——错误处理、日志、参数校验每次都长一样。

// .vscode/go.code-snippets —— 一个带占位符和变量的片段
{
  "HTTP handler with error log": {
    "prefix": "hhandler",
    "body": [
      "func ${1:Name}(w http.ResponseWriter, r *http.Request) {",
      "\\tctx := r.Context()",
      "\\tdefer func() {",
      "\\t\\tif err := recover(); err != nil {",
      "\\t\\t\\tlog.Error(ctx, \"panic in ${1:Name}\", \"err\", err)",
      "\\t\\t\\thttp.Error(w, \"internal error\", 500)",
      "\\t\\t}",
      "\\t}()",
      "$0",
      "}"
    ],
    "description": "handler + panic 兜底 + 日志"
  }
}
语法含义
$1 $2按 Tab 依次跳转的占位符
${1:default}带默认值的占位符，直接回车就用默认值
$0片段插入后光标的最终位置
${TM_FILENAME_BASE}当前文件名（不含扩展名）
${CURRENT_YEAR}-${CURRENT_MONTH}日期，适合文件头注释
${TM_SELECTED_TEXT}把选中的文本包进片段里

snippet 只解决"单个文件里的结构"，跨文件的脚手架要用生成器。新建一个服务、新建一个模块，涉及目录、配置、CI 文件，靠 snippet 做不到。

手段适合代价
snippet函数、结构体、测试骨架只能补全文本，不能建文件
项目内模板目录新服务、新模块要自己写复制脚本，模板容易过期
脚手架工具标准化程度高的项目要维护模板仓库与版本
# 常见的脚手架（用之前先看它生成了什么，别盲跑）
npm create vite@latest my-app -- --template react-ts
cookiecutter gh:org/service-template
go run github.com/org/scaffold@latest new-service order-api

# 一个最土但最有效的模板方案：模板目录 + 变量替换
cp -r templates/service services/order-api
find services/order-api -type f -name "*.tmpl" | while read f; do
  sed -i "s/__SERVICE_NAME__/order-api/g" "$f"
  mv "$f" "${f%.tmpl}"
done
模板的维护原则：模板必须是"能跑的"。做法是把模板本身当成一个真实项目，CI 里定期用它生成一次并跑构建。否则半年后模板里的依赖全部过期，新人用一次踩一次坑，最后没人用。
模块 7

性能：大项目为什么变慢

VS Code 变慢通常不是"编辑器不行"，而是它被迫处理了太多它不该处理的东西。按影响从大到小排，一共四类原因。

原因表现解法
文件监听耗尽保存后热重载不生效、Git 状态不刷新、CPU 持续占用配 files.watcherExclude；Linux 上调 fs.inotify.max_user_watches
语言服务内存不足补全变慢、跳转要等几秒、右下角一直转圈调大 TS server 内存；缩小 tsconfig 的 include 范围
扩展太多或太重的扩展启动 10 秒以上、输入有延迟Startup Performance 看耗时；Extension Bisect 二分定位
搜索/索引全仓库全局搜索卡住、CPU 打满配 search.exclude；避免在仓库根目录放大文件
// 大项目的三组排除配置，缺一不可
{
  // 1) 不监听：直接影响文件句柄数量
  "files.watcherExclude": {
    "**/node_modules/**": true,
    "**/dist/**": true,
    "**/build/**": true,
    "**/.git/objects/**": true,
    "**/vendor/**": true
  },
  // 2) 不搜索：影响全局搜索速度和结果质量
  "search.exclude": {
    "**/node_modules": true,
    "**/dist": true,
    "**/*.min.js": true,
    "**/package-lock.json": true
  },
  // 3) 不显示：只是视觉简化，但对大目录很有用
  "files.exclude": { "**/.cache": true }
}

// TypeScript 项目的专项优化（用户或工作区配置）
"typescript.tsserver.maxTsServerMemory": 4096,
"typescript.disableAutomaticTypeAcquisition": true
# Linux 上调 inotify 上限（默认常见 8192，大项目远远不够）
cat /proc/sys/fs/inotify/max_user_watches
sudo sysctl -w fs.inotify.max_user_watches=524288
# 永久生效写进 /etc/sysctl.d/99-vscode.conf

# 从命令行看 VS Code 的整体状态（进程、内存、扩展）
code --status

# 生成启动耗时报告，定位是哪个扩展拖慢的
code --prof-startup

常见坑

十个配置坑

1
装了三十个扩展，启动十几秒
每个扩展都要加载、注册命令、可能启动语言服务。按"语言/lint/格式化/Git/远程"五类各留一个，其余按工作区禁用。
2
把主题、字体、字号提交进 .vscode/settings.json
全组被迫用你的配色，还会在你休假时被人改掉。工作区只放项目必需项，个人偏好留在用户配置。
3
formatOnSave 与 lint 规则打架
保存一次格式化两遍，或者格式化把 lint 想要的换行又改回去。只留一个默认格式化器，lint 用 codeActionsOnSave 修。
4
没配 watcherExclude，Linux 上文件监听耗尽
node_modules 动辄几万个文件，句柄用完后再也不监听变更，热重载直接失效。排除目录 + 调大 inotify 上限。
5
WSL 里把项目放在 /mnt/c
跨文件系统访问极慢，npm install 可能慢十倍，文件监听还容易失效。代码放 WSL 自己的文件系统里。
6
Remote SSH 里扩展装在本地
语言服务读不到远端文件，表现为补全失效、找不到模块。语言类扩展必须装在远端工作区。
7
调试已在运行的进程却用了 launch 模式
launch 会再启动一个进程，两个进程抢同一个端口。已在跑就用 attach，并配好 port 或 processId。
8
容器调试断点不生效
本地路径和容器内路径不一致，调试器找不到源文件。用 substitutePath / localRoot + remoteRoot 做映射。
9
snippet 里硬编码了本机路径或用户名
换台机器就生成出错误代码。用 ${workspaceFolder}、${TM_FILENAME_BASE} 这类变量。
10
所有配置只存在自己电脑上
换机器重配半天，团队里每个人的格式化结果都不一样。用户配置走 Settings Sync，项目配置进仓库。
自测

六道题

1. 用户配置和工作区配置冲突时，哪个生效？
正确答案：工作区配置。优先级是"工作区 > 用户"，语言专属配置又会覆盖通用配置。所以"我的设置不生效"通常是项目里覆盖了。
2. 要调试一个已经在容器里运行的进程，应该用哪种模式？
正确答案：attach。launch 是由调试器启动新进程，会对已在运行的进程造成端口冲突。attach 需要 port 或 processId，容器场景还要配 substitutePath。
3. 新人入职最需要哪种方案来保证"环境一致"？
正确答案：Dev Containers。文档会过期、会漏步骤，而容器配置是代码，可版本化、可评审、可一键复现。
4. WSL 里开发时，项目代码应该放在哪？
正确答案：WSL 自己的文件系统。访问 /mnt/c 要跨文件系统转换，大量小文件读写会慢数倍，文件监听也容易失效。
5. 大项目里补全变慢、跳转要等几秒，最可能的原因是？
正确答案：语言服务内存与索引范围。调大 TS server 内存、缩小 include 范围、排除 node_modules 和 dist，通常能立刻改善。
6. 为什么不能把远程调试端口暴露在公网？
正确答案：等于开放 RCE。Node inspect、delve、JDWP 都能读内存、改变量、调函数。只能绑 127.0.0.1，通过 SSH 隧道访问，用完就关。
