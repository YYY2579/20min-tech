开始前

先建立正确的心理模型

学正则最大的障碍不是记不住符号，而是以为只有一套正则。实际上至少有三大流派，语法互相不兼容。先记住这个分层，后面所有困惑都能归位。

流派全称 / 来源典型使用者
BREBasic Regular Expression，POSIX 标准grep（默认）、sed（默认）、ed、vi
EREExtended Regular Expression，POSIX 标准grep -E、sed -E、awk、egrep（已废弃）
PCREPerl Compatible Regular Expressiongrep -P、PHP、Python（大部分）、Java、JavaScript（近似）
# 同一条"匹配 a 或 b"，三种写法完全不同
echo "a" | grep    'a\|b'        # BRE：转义的 \| 才是"或"
echo "a" | grep -E 'a|b'         # ERE：裸的 | 就是"或"
echo "a" | grep -P 'a|b'         # PCRE：同 ERE

# 但 BRE 里裸的 | 是普通字符
echo "a|b" | grep 'a|b'          # 匹配字面量，能命中
echo "a"   | grep 'a|b'          # 不匹配
本文最重要的三条结论，先记住：
① 先确认方言，再写表达式。在 grep 里试出的正则直接塞进 Python，十有八九行为不同。
② Shell 的引号和正则的转义是两层。你看到的 \\d 在 shell 处理完之后可能变成 \d，也可能变成 d。
③ 能不用正则就不用。解析 JSON 用 JSON 库，解析 URL 用 URL 库。正则只适合"模式简单、输入可控"的场景。
模块 1

两种流派：BRE / ERE 与 PCRE

BRE 和 ERE 的差别只有一个字：哪些字符"天生特殊"。BRE 认为大部分符号都是普通字符，要加反斜杠才特殊；ERE 反过来。

特殊字符对照表

字符BRE 里ERE 里PCRE 里
.特殊（任意字符）特殊特殊
*特殊（0 或多次）特殊特殊
^ $特殊（锚点）特殊特殊
+普通字符，要写 \+特殊特殊
?普通字符，要写 \?特殊特殊
|普通字符，要写 \|特殊特殊
( )普通字符，要写 \( \)特殊特殊
{ }普通字符，要写 \{ \}特殊特殊
# BRE：匹配 "ab" 或 "ac"；一个或多个 a；2~4 个 a
grep 'a\(b\|c\)' file
grep 'a\+' file
grep 'a\{2,4\}' file

# ERE：同样的意思
grep -E 'a(b|c)' file
grep -E 'a+' file
grep -E 'a{2,4}' file
GNU 的"宽容"是陷阱。GNU grep / sed 在 BRE 模式下也接受 \+ \? \|（作为扩展），所以你在 Linux 上写的 grep 'a\+' 能跑。但换到 macOS 的 BSD grep、BusyBox、或者 POSIX 严格实现上就失效了。写可移植脚本时，要么统一用 grep -E，要么只用 BRE 的原始语法。

grep 的三个模式

命令方言支持 / 不支持
grep PATTERNBRE支持 \( \) \{ \}、POSIX 字符类、GNU 扩展 \+ \? \| \b \w \s
grep -E PATTERNERE支持 + ? | ( ) { }、POSIX 字符类。不支持 \d \w \b（GNU 部分支持 \b \w，但不是标准）
grep -P PATTERNPCRE全都支持：\d \w \s \b、环视、非捕获组、懒惰量词、命名组
# 这条在 grep -E 下不工作（\d 被当成字面量 d）
echo "123" | grep -E '\d+'       # 无输出！

# 三种正确的写法
echo "123" | grep    '[0-9]\+'    # BRE + 区间
echo "123" | grep -E '[0-9]+'     # ERE + 区间
echo "123" | grep -P '\d+'        # PCRE

# 确认有没有 PCRE 支持（macOS / Alpine 通常没有）
grep -P 'x' /dev/null && echo "PCRE ok" || echo "no PCRE"
-P 不是 POSIX 标准，是 GNU 的扩展。它依赖 libpcre，很多精简环境（Alpine 的 BusyBox、macOS 的 BSD grep、某些容器镜像）根本没有。写可移植脚本时不要用 -P，用 -E + POSIX 字符类替代。
模块 2

元字符与转义

转义是正则里最容易出错的部分，因为你要同时穿过两层：Shell 的引号处理和正则引擎的转义。很多人写不对不是不懂正则，是没算清这两层。

哪些字符需要转义

字符特殊含义想匹配字面量时
. ^ $ * + ?见模块 5、6加 \
( ) [ ] { }分组、字符类、量词加 \
|或加 \
\转义符本身\\
-只在 [a-z] 内部特殊放开头/结尾，或 \-
]只在字符类内部特殊放字符类开头，或 \]
/在 sed 的 s/// 里是分隔符换分隔符（s|||）或转义

两层转义：shell 一层，正则一层

# 目标：匹配字面量 "a.b"（点不是通配符）
# 正则层面需要 a\.b，再考虑 shell 这一层

grep 'a\.b' file          # 单引号：原样传递 ✓（推荐）
grep "a\.b" file          # 双引号：\ 后是 . ，保留反斜杠 ✓
grep a\.b file           # 无引号：shell 吃掉 \ → grep 收到 a.b ✗
记一条规则就够了：正则永远用单引号包。
单引号里除了单引号本身，其他字符全部原样传递。这样你只需要考虑正则引擎这一层，不用算 shell 的账。
唯一例外：表达式里需要嵌入 shell 变量时，用双引号，但要把正则里的反斜杠写成两个。
grep -E "$prefix\\.[0-9]+" file

编程语言里的转义

# Python：一定要用 raw string（r 前缀）
re.search('\d+',  'abc123')    # ✗ Python 先处理 \d
re.search(r'\d+', 'abc123')    # ✓ 原样传给正则引擎

print('\n')      # 换行符 —— 这就是为什么不能不用 r
print(r'\n')     # 输出 \n 两个字符

# JavaScript：字符串构造写法要双反斜杠
/\d+/.test('abc123')     // 正则字面量（推荐）
new RegExp('\\d+')        // 字符串构造：双反斜杠

# Java：字符串里反斜杠也要双写
Pattern.compile("\\d+")
反斜杠数量的心智模型：每穿过一层"字符串字面量"，反斜杠翻倍。
Shell 单引号 / Python r'' / JS 正则字面量：1 层，写 \d；
Shell 双引号 / Python 普通字符串 / JS 或 Java 字符串：2 层，写 \\d。
这就是为什么复杂正则建议写到文件里，而不是塞进命令行。
模块 3

字符类

字符类（character class）用方括号表示"这里可以是集合里的任意一个字符"。它是正则里最不容易出错、也最该优先使用的结构。

基本形式

写法含义匹配示例
[abc]a、b、c 中的任意一个"a" "b" "c"
[^abc]除 a、b、c 外的任意字符"d" "1" "中"
[a-z]小写字母"m"
[a-zA-Z0-9_]字母数字下划线"_" "7" "Q"
[0-9a-fA-F]十六进制字符"F" "3"
[^0-9]非数字"a" " "

\d \w \s 的方言差异

简写等价于支持情况
\d[0-9]（PCRE 在 Unicode 模式下也匹配全角数字）PCRE ✓ / Python ✓ / JS ✓ / Java ✓ / grep -E ✗ / grep -P ✓
\D[^0-9]同上
\w[a-zA-Z0-9_]同上（GNU grep -E 部分支持）
\W[^a-zA-Z0-9_]同上
\s[ \t\n\r\f\v]同上
\S非空白同上
# 可移植写法：用 POSIX 字符类，所有流派都支持
grep -E '[[:digit:]]+' file
grep -E '[[:alpha:]]+' file
grep -E '[[:space:]]'  file

# ⚠️ 注意是双层方括号：[[:digit:]] 不是 [:digit:]
# 外层 [] 是字符类，内层 [:digit:] 是字符类的名字
grep -E '[:digit:]' file    # ✗ 这匹配的是 : d i g t 这几个字符！

POSIX 字符类全表

写法等价说明
[[:alpha:]][a-zA-Z]字母（受 locale 影响）
[[:digit:]][0-9]数字
[[:alnum:]][a-zA-Z0-9]字母或数字
[[:upper:]][A-Z]大写
[[:lower:]][a-z]小写
[[:space:]][ \t\n\r\f\v]空白字符
[[:blank:]][ \t]空格和制表符（不含换行）
[[:punct:]]标点符号! " # $ % & ' ( ) * + , - . / : ; < = > ? @ [ \ ] ^ _ ` { | } ~
[[:xdigit:]][0-9a-fA-F]十六进制
POSIX 字符类受 locale 影响。[[:alpha:]] 在 LC_ALL=C 下只匹配 ASCII 字母，在 zh_CN.UTF-8 下会匹配中文。
这在处理日志时是隐藏的坑：同一份脚本在服务器上（C locale）跑得好，在开发机上（UTF-8）匹配到意外的内容。需要确定性时显式设 LC_ALL=C。

字符类里不需要转义的字符

# 在 [] 内部，大部分元字符失去特殊含义
[.^$*+?(){}|]      # 全部是字面量，不用转义

# 只有三个特殊
[^abc]             # ^ 在开头表示"取反"
[a-z]              # - 在中间表示"范围"
[]a]               # ] 在开头表示字面量 ]

# 反斜杠在 [] 里的行为各流派不同
[\d]               # PCRE：数字；POSIX：反斜杠或 d
[\.]               # 大部分流派：字面量点（但不必要，[.] 就够了）
模块 4

分组与捕获

分组解决两件事：把多个字符当成一个整体（配合量词），以及把匹配到的部分提取出来。前者所有流派都支持，后者是方言差异最大的地方。

捕获组

# 基本语法：(pattern)，组号从左到右从 1 开始（0 是整个匹配）
([0-9]{4})-([0-9]{2})-([0-9]{2})     # $1=年 $2=月 $3=日

# 反向引用：在【模式内部】引用前面的组
([0-9])\1          # 匹配 11 22 33，不匹配 12
\b(\w+)\s+\1\b     # 找重复单词："the the" "is is"

# 找 HTML 成对标签（简单场景够用）
<([a-z]+)>.*?</\1>    # \1 必须是同一个标签名

非捕获组

# (?:pattern) —— 只分组，不占组号
(?:https?|ftp)://([^/]+)     # $1 是域名，协议部分不占组号

# 为什么要用：组号会被打乱
(https?|ftp)://([^/]+)       # $1 = 协议, $2 = 域名
(?:https?|ftp)://([^/]+)     # $1 = 域名（更清晰）

# 性能上也有好处：捕获组要保存匹配内容，非捕获组不用

命名组

语言语法取值
Python(?P<year>[0-9]{4})m.group('year')
PCRE / PHP(?<year>[0-9]{4}) 或 (?P<year>...)$year
JavaScript（ES2018+）(?<year>[0-9]{4})m.groups.year
Java(?<year>[0-9]{4})m.group("year")
.NET(?<year>...) 或 (?'year'...)m.Groups["year"]
# Python
m = re.search(r'(?P<year>\d{4})-(?P<month>\d{2})', '2026-10')
print(m.group('year'))      # 2026
print(m.groupdict())        {'year': '2026', 'month': '10'}

# JavaScript（ES2018+）
const m = '2026-10'.match(/(?<year>\d{4})-(?<month>\d{2})/);
console.log(m.groups.year);   // 2026

# Java
Pattern p = Pattern.compile("(?<year>\\d{4})");
if (p.matcher(s).find()) System.out.println(m.group("year"));

替换时的引用

# sed / grep：用 \1 \2（替换串里的 / 要转义，或换分隔符）
echo "2026-10-17" | sed -E 's|([0-9]{4})-([0-9]{2})-([0-9]{2})|\3/\2/\1|'

# Python：用 \1 或 \g<name>，必须加 r''
re.sub(r'(\d{4})-(\d{2})-(\d{2})', r'\3/\2/\1', '2026-10-17')
re.sub(r'(?P<y>\d{4})-(?P<m>\d{2})', r'\g<m>/\g<y>', '2026-10')

# JavaScript：用 $1 $2，命名组用 $<name>
'2026-10-17'.replace(/(\d{4})-(\d{2})-(\d{2})/, '$3/$2/$1')
反向引用 \1 和替换引用 $1 是两回事。
模式内部（描述"要匹配什么"）用 \1（PCRE/POSIX 通用，Python 也用 \1）。
替换串里（描述"替换成什么"）各语言不同：sed 用 \1、Python 用 \1 或 \g<1>、JS 用 $1、Java 用 $1。
混用会得到字面量 $1 或语法错误，而且往往不报错，只是结果不对。
模块 5

量词与贪婪

量词决定"重复几次"。贪婪与懒惰决定"在能匹配的前提下，尽量多吃还是少吃"。这是正则里最容易写出性能问题的部分。

量词全表

量词含义示例
*0 次或多次ab*c → ac, abc, abbc
+1 次或多次ab+c → abc, abbc（不含 ac）
?0 次或 1 次ab?c → ac, abc
{n}恰好 n 次a{3} → aaa
{n,}至少 n 次a{2,} → aa, aaa, ...
{n,m}n 到 m 次a{2,4} → aa, aaa, aaaa

贪婪 vs 懒惰

# 默认是贪婪（greedy）：尽量多匹配
# 输入：<b>bold</b> and <i>italic</i>
<.+>        # 匹配整个 "<b>bold</b> and <i>italic</i>"
            # 因为 .+ 会一路吃到最后一个 >

# 懒惰（lazy）：尽量少匹配，加一个 ?
<.+?>       # 匹配 "<b>" 和 "</b>" 和 "<i>" 和 "</i>"
            # 每个标签单独匹配

# 更精确的写法：不用 .，用排除字符类（性能更好，见模块 7）
<[^>]+>     # 同样效果，但没有回溯风险

# 懒惰量词全表
*?  +?  ??  {n,m}?
什么时候用懒惰，什么时候用排除类：懒惰适合"终点不好用字符类描述"的场景，如 START.*?END。排除类（[^>]）永远更快，因为不产生回溯 —— 引擎一路往前扫，不用"先吃到尾再往回吐"。能用排除类就别用 .*?。

占有量词（PCRE / Java）

# 占有量词：吃掉之后【不吐出来】，绝不回溯
a*+   a++   a?+   a{n,m}+

<.+>      # 贪婪：先吃到尾，再回溯找 >
<.+?>     # 懒惰：从少到多试
<.++>     # 占有：吃到尾就不回头 —— 这条会匹配失败！

<[^>]++>  # 正确用法：吃到 > 就停，不回溯，性能最好
(?><b>)     # 原子组，等价效果
语法支持情况
*? +? ??PCRE / Python / JS / Java / .NET 全支持
*+ ++ ?+PCRE / Java / .NET 支持；Python 3.11+ 支持；JavaScript 不支持
(?>...)PCRE / Java / .NET / Python 3.11+；JS 不支持
模块 6

锚点与边界

锚点不消耗字符，只断言"位置"。它们是把"包含"变成"完全匹配"的关键，也是多行文本处理最容易搞错的地方。

常用锚点

写法含义备注
^字符串开头（或行首，见 m 标志）在 [] 内部表示"取反"
$字符串结尾（或行尾）有些引擎里 $ 也匹配结尾换行之前
\b单词边界（\w 与 \W 之间）不消耗字符，只断言位置
\B非单词边界—
\A字符串绝对开头不受 m 标志影响（PCRE/Python）
\z字符串绝对结尾PCRE/Java；Python 用 \Z
\Z字符串结尾（允许末尾有一个换行）各语言含义略有差异

\b 的行为

# \b 匹配"从非单词字符到单词字符"或反过来的位置
# 输入：cat category concat
\bcat\b      # 只匹配第一个 "cat"
cat          # 匹配三处（作为子串）

# \b 对中文的行为要注意
# 在大多数引擎里，中文字符算 \W（非单词字符）
# 所以 \b中文\b 往往匹配不到东西

# 等价的手写方式
\bcat\b  ==  (^|[^a-zA-Z0-9_])cat([^a-zA-Z0-9_]|$)
# 后者要消耗字符，所以在连续匹配时会漏掉相邻的结果

多行模式：为什么 ^ 会在字符串中间匹配

# 默认：^ 只匹配整个字符串的开头
# 输入 "line1\nline2\nline3"
^line2       # ✗ 不匹配；开了 m 才匹配

# 各语言的开关方式
re.search(r'^line2', text, re.MULTILINE)   # Python
/^line2/m.test(text)                        // JS
grep -P '(?m)^line2'                       # PCRE
Pattern.compile("^line2", Pattern.MULTILINE) // Java
^ 在字符串中间匹配，只有三种可能：
① 开了 m 标志（多行模式）—— 这是最常见的原因；
② 字符串里真的有换行，而引擎默认把 ^ 解释成"行首"（某些工具如 sed 逐行处理，天然是"每行开头"）；
③ 用了 \n^ 之类的组合，或者 ^ 在字符类里（那时它是字面量或取反）。
排查方法：先确认标志位，再确认输入里有没有 \n。

为什么需要 \A 和 \z

# 危险场景：用 ^...$ 校验用户输入
^[0-9]+$

# 如果引擎默认让 $ 匹配"结尾或结尾换行之前"，那么
# 输入 "123\n" 会通过校验
# 输入 "123\n456" 在多行模式下也会通过

# 严格写法：用绝对锚点
\A[0-9]+\z      # PCRE
\A[0-9]+\Z      # Python

# 或者干脆用"完全匹配"的 API（见模块 8）
# Python: re.fullmatch(r'[0-9]+', s)
# Java:   Pattern.matches("[0-9]+", s)
# JS:     /^[0-9]+$/.test(s) 配合 s 不含 \n，或用 ^...$ 加 m 之外的方式

环视：不消耗字符的断言

语法含义
(?=...)后面必须是（正向前瞻）
(?!...)后面必须不是（负向前瞻）
(?<=...)前面必须是（正向后顾）
(?<!...)前面必须不是（负向后顾）
# 密码至少 8 位，且同时包含字母和数字
^(?=.*[a-zA-Z])(?=.*[0-9]).{8,}$

# 提取金额里的数字，但不包括货币符号
(?<=\$)[0-9]+        # 结果不含 $

# 支持情况：前瞻 PCRE/Python/JS/Java 全支持；后顾 JS 2018+ 要求固定长度
# POSIX BRE/ERE 完全不支持 —— grep -E 里写 (?=) 会被当字面量
模块 7

回溯灾难

这是正则唯一能真正"搞挂"生产的问题：一条看起来无害的表达式，遇到特定输入后 CPU 打满、进程卡死。而且它不报错、不超时、不占内存，只是无限算下去。

原理：回溯是"试错"

正则引擎（除 RE2 这类自动机引擎外）本质是深度优先搜索。当一条路径走不通时，它退回到上一个选择点换一条路。如果选择点嵌套，路径数量会指数级增长。

# 看这条表达式
(a+)+$

# 输入 "aaaa" 时，引擎要决定：
# 外层 + 迭代几次？内层 a+ 每次吃几个？
# "aaaa" 的切分方式有 2^(n-1) 种
#   a|a|a|a    aa|a|a    a|aa|a    ...    aaaa
# 共 8 种

# 如果末尾不匹配（比如输入是 "aaaaX"），引擎要把所有切分都试一遍
# n=20 → 约 50 万次     n=30 → 约 5 亿次     n=40 → 已经算不完了
一个真实的卡死例子。下面这条用来校验"由单词和空格组成的字符串"，看起来很合理：
^(\w+\s?)*$
输入一段 40 个字符的正常文本，它瞬间返回。输入 40 个字符再加一个 !，它会算上几分钟。因为末尾的 $ 无法满足，引擎要把 \w+ 和 \s? 的所有组合都试一遍 —— 2^40 量级。
如果这个正则挂在 HTTP 接口的参数校验上，一个请求就能打满一个核。这就是 ReDoS（Regular Expression Denial of Service）。

怎么识别危险模式

危险形状为什么危险
(a+)+ (a*)* (a|a)*嵌套量词。内外层可以表达同一种切分，路径数指数增长
(a|b|ab)+分支之间有重叠，同一个字符串有多种匹配方式
(\w+\s?)*量词套量词，且内层可匹配空串
(.*a){10}贪婪 + 大重复次数 + 固定后缀
^(\d+)*$经典 ReDoS 模式
.*.*.*多个 .* 串联，回溯空间相乘

判断口诀：只要看到"量词套在包含量词的分组外面"，就要警惕。再看这个分组是否可能匹配空串、分支之间是否有重叠 —— 三者占两个，基本就有问题。

四种修复方式

# 原始危险版本
^(\w+\s?)*$

# 修复 1：消除嵌套量词（最优解）
^\w+(?:\s+\w+)*$      # 用 \s+ 强制分隔，切分方式唯一

# 修复 2：原子组 / 占有量词（PCRE、Java、Python 3.11+）
^(?>\w+\s?)*$    ^(?:\w+\s?)*+$

# 修复 3：排除类代替 .*
<.*?>  →  <[^>]*>      ".*?"  →  "[^"]*"

# 修复 4：加长度限制（缓解，不是根治）
^.{1,100}$

工程上的四道防线

限制输入长度
在跑正则之前先检查长度。回溯是指数级的，长度从 40 降到 20，耗时降 100 万倍。这是性价比最高的一道防线
加超时
Java 可以用 Matcher + 独立线程 + Future.get(timeout)；Python 用 regex 模块的 timeout 参数；JS 没有原生方案，只能靠 Worker + 终止
换线性引擎
Google 的 RE2（Go 内置、C++ 可用）保证线性时间，不支持反向引用和环视。Rust 的 regex crate 同理。牺牲表达力换确定性
静态检查
用 safe-regex（JS）、vuln-regex-detector、或 Semgrep 的规则扫描代码里的危险模式，在 CI 阶段拦住
# 实测回溯灾难（Python）
python3 - <<'EOF'
import re, time
pat = re.compile(r'^(a+)+$')
for n in (18, 20, 22, 24):
    s = 'a' * n + 'X'
    t = time.time(); pat.match(s)
    print(f'n={n}  {time.time()-t:.3f}s')
EOF
# n=18 0.031s → n=20 0.124s → n=22 0.496s → n=24 1.984s
# 每加 2 个字符，时间乘 4 —— 这就是指数增长

# 换成安全版本 ^a+$，n=100000 也是毫秒级
一句话总结：正则引擎默认"回溯匹配"，最坏是指数时间复杂度。任何"用户可控输入 + 复杂正则"都是攻击面 —— 简化表达式、限制长度，或换线性引擎。
模块 8

各环境差异

同一个需求，在 sed、Python、JS、Java 里的写法完全不同。这一节按环境列出最容易踩的差异点。

sed：默认 BRE

# 默认是 BRE，分组和或都要转义
sed 's/\(foo\|bar\)/baz/' file

# 加 -E 才是 ERE（GNU 也接受 -r，但 -E 更可移植）
sed -E 's/(foo|bar)/baz/' file

# 替换串里用 \1，不是 $1
sed -E 's/([a-z]+) ([a-z]+)/\2 \1/' file

# 特殊字符：& 表示"整个匹配"
sed 's/foo/[&]/' file        # foo → [foo]
# 想匹配字面量 & 要写 \&

# 分隔符可以换，避免转义路径里的 /
sed 's|/usr/local|/opt|g' file

# GNU 扩展：\b \+ \? \| 在 BRE 下也能用
# 但 BSD sed（macOS）不支持，写可移植脚本要用 -E

Python：re 模块

函数行为
re.match(p, s)只从开头匹配，不要求匹配到结尾
re.search(p, s)在任意位置找第一个匹配
re.fullmatch(p, s)整个字符串必须完全匹配（等价于 \A...\Z）
re.findall(p, s)返回所有匹配；有捕获组时返回组内容而不是整个匹配
re.sub(p, r, s, count=0)替换，count=0 表示全部
# 最经典的坑：findall 遇到捕获组
re.findall(r'\d+', 'a1 b22 c333')          # ['1', '22', '333']
re.findall(r'([a-z])(\d+)', 'a1 b22')      # [('a','1'), ('b','22')]

# match / search / fullmatch
re.match(r'\d+', 'abc123')        # None（不从开头开始）
re.search(r'\d+', 'abc123')       # 匹配到 '123'
re.fullmatch(r'\d+', '123abc')     # None（没有完全匹配）

# 编译一次重复使用
PAT = re.compile(r'(?P<key>\w+)=(?P<val>\w+)')
m = PAT.match(line); print(m.group('key'))

JavaScript：g 标志与 lastIndex 陷阱

// 这是 JS 正则最著名的坑
const re = /\d+/g;
re.test('a1');    // true
re.test('a1');    // false  ← 同一个正则，同一个输入，结果变了！
re.test('a1');    // true

// 原因：带 g 标志的正则有状态，lastIndex 记录上次匹配结束的位置
// 第二次调用从 lastIndex=2 开始找，找不到就返回 false 并把 lastIndex 归零
// 第三次又从 0 开始，所以又是 true

// 验证
const re2 = /\d+/g;
console.log(re2.lastIndex);   // 0
re2.test('a1');
console.log(re2.lastIndex);   // 2

// 解法一：不要用 g（test 只需要判断存在）
/\d+/.test('a1')

// 解法二：每次重置 lastIndex
re.lastIndex = 0;

// 解法三：每次都新建正则
/\d+/g.test('a1')
JS 方法行为
str.match(re)无 g：返回带捕获组的数组；有 g：只返回所有匹配的字符串，丢失捕获组
str.matchAll(re)返回迭代器，保留捕获组（必须带 g）
str.replace(re, rep)无 g 只替换第一个；有 g 替换全部
re.exec(str)有状态，配合 g 可以循环取所有匹配
// 用 exec 循环取所有匹配（传统写法）
const re = /(\w+)=(\w+)/g;
let m;
while ((m = re.exec('a=1 b=2')) !== null) {
    console.log(m[1], m[2]);
}
// 注意：循环体里 break，lastIndex 会停在中间，下次复用会从中间开始

// 现代写法
for (const m of 'a=1 b=2'.matchAll(/(\w+)=(\w+)/g)) {
    console.log(m[1], m[2]);
}

Java：matches 与 find

// matches() 要求【整个字符串】完全匹配
"abc123".matches("\\d+")        // false
"123".matches("\\d+")           // true

// find() 在任意位置找子串
Pattern p = Pattern.compile("\\d+");
Matcher m = p.matcher("abc123");
m.find();                          // true
m.group();                         // "123"

// 三个方法对照
// matches()    整个字符串          ≈ Python fullmatch()
// lookingAt()  从开头，不要求到结尾 ≈ Python match()
// find()       任意位置            ≈ Python search()

// 替换用 $1，不是 \1；循环里要预先 compile
"2026-10".replaceAll("(\\d{4})-(\\d{2})", "$2/$1");
四个环境的"完全匹配"对照表：
Python re.fullmatch(p, s) ≈ Java s.matches(p) ≈ JS 需要自己写 /^p$/ 且确保 s 不含换行 ≈ sed/grep 需要 ^p$ 配合 -x（grep 的整行匹配）。
不要假设 ^...$ 就等于"完全匹配" —— 多行模式、结尾换行、$ 的实现差异都会让你漏掉边界情况。
常见坑

十个反复踩的坑

1
在 grep -E 里用 \d
POSIX ERE 不支持 \d，它被当成字面量 d。用 [0-9] 或 [[:digit:]]，或者改用 grep -P。
2
没加引号，shell 吃掉了反斜杠
grep a\.b 里 shell 把 \. 变成 .，正则收到的是 a.b（点变通配符）。正则一律用单引号包。
3
Python 里不用 raw string
'\d' 在 Python 里可能被当成无效转义（3.12+ 会警告），'\n' 更是直接变换行。永远写 r'\d'。
4
以为 . 匹配换行
默认不匹配。需要跨行匹配要开 DOTALL（Python re.S、JS /s、PCRE (?s)），或者用 [\s\S]。
5
用 .* 匹配 HTML 标签
贪婪的 .* 会吃到最后一个 >。用 [^>]* 而不是 .*?，既正确又快（无回溯）。
6
捕获组打乱了编号
加了一个 ( ) 之后，原来的 $1 变成 $2。用非捕获组 (?:) 包住不关心的部分，或者改用命名组。
7
替换串里用了 $1 但环境是 sed
sed 用 \1，Python 用 \1，JS/Java 用 $1。混用不会报错，只会输出字面量。
8
JS 里带 g 的正则复用导致结果飘忽
lastIndex 是有状态的，test/exec 会推进它。要么去掉 g，要么每次重置 lastIndex，要么每次新建正则。
自测

六道题

1. 在 grep（默认 BRE）里匹配"a 或 b"，正确写法是？
正确答案：a\|b。BRE 里裸的 | 是普通字符，转义后才表示"或"。ERE（grep -E）里才写裸的 a|b。
2. 为什么 Python 里写正则要用 r'\d+' 而不是 '\d+'？
正确答案：避免 Python 的字符串转义。r 是 raw string，反斜杠原样保留。'\n' 是换行符，r'\n' 才是"反斜杠 + n"两个字符。
3. <.+> 和 <.+?> 匹配 "<b>bold</b>" 时，区别是？
正确答案：贪婪 vs 懒惰。.+ 贪婪，会吃到最后一个 >，所以匹配整个；.+? 懒惰，匹配到第一个 > 就停。实践中更好的是 [^>]+，没有回溯风险。
4. (a+)+$ 遇到 "aaaaX" 时为什么会卡住？
正确答案：指数级回溯。外层 + 迭代几次、内层 a+ 每次吃几个，组合数是 2^(n-1)。末尾的 X 让所有路径失败，于是全部试一遍。这就是 ReDoS。
5. JS 里 const re = /\d+/g; re.test('a1') 连续调用三次，结果是？
正确答案：true false true。带 g 的正则有 lastIndex 状态，第一次匹配后 lastIndex=2，第二次从 2 开始找不到就返回 false 并归零，第三次又从 0 开始。判断"是否存在"时不要用 g。
6. Java 的 String.matches() 和 Matcher.find() 的区别是？
正确答案：matches 是整体匹配。"abc123".matches("\\d+") 返回 false，因为不是纯数字；用 find() 才能找到里面的 "123"。对应的 Python 是 fullmatch 和 search。
