开始前

准备：手上要有的三件工具

工具用途
curl -v命令行看完整报文，最可靠。本文大量使用
浏览器 DevTools → Network看前端请求，勾选 Preserve log 和 Disable cache 才准确
Wireshark（第 1 期）看传输层，排查"连不上""TLS 握手失败"这类问题
# 最常用的一条：看完整请求响应头
curl -v https://example.com

# 只看响应头，不看 body
curl -I https://example.com

# 显示耗时分解，排查"到底慢在哪一段"
curl -o /dev/null -s -w "DNS:%{time_namelookup} 连接:%{time_connect} TLS:%{time_appconnect} 首字节:%{time_starttransfer} 总计:%{time_total}\n" https://example.com
那条耗时分解命令非常值得记住。它把一次请求拆成：DNS 解析、TCP 连接、TLS 握手、等待首字节、总耗时。慢在哪一段，一眼就看出来 —— 是域名解析慢，还是服务端处理慢，还是网络传输慢。这是排查"接口慢"最快的入口。
模块 1

HTTP 是什么：一句话与三个特征

一句话：HTTP 是"客户端主动发起请求、服务端返回响应"的文本协议。

特征含义与影响
请求-响应模型只能客户端先发起，服务端不能主动推。所以有了 WebSocket 和 SSE 来补这个短板
无状态服务端默认不记得你上一次是谁。每次请求都是独立的。所以需要 Cookie/Session/Token 来"记住登录状态"
可扩展靠头部字段扩展能力（缓存、鉴权、跨域、内容协商都在头部）
"无状态"是理解 HTTP 鉴权的钥匙。正因为服务端不记得你，所以每次请求都必须带上凭证 —— Cookie 是浏览器自动带，Token 是你手动放在 Authorization 头里。所有鉴权方案的差异，本质都是"凭证放在哪、存不存服务端"。
模块 2

报文结构：请求和响应长什么样

# ===== 请求报文 =====
GET /api/users/42?fields=name HTTP/1.1        ← 请求行：方法 + 路径 + 版本
Host: api.example.com                          ← 以下全是请求头
User-Agent: curl/8.0
Accept: application/json
Authorization: Bearer eyJhbGci...
Cookie: session=abc123

← 空行分隔
{ "name": "张三" }                              ← 请求体（GET 通常没有）


# ===== 响应报文 =====
HTTP/1.1 200 OK                                 ← 状态行：版本 + 状态码 + 原因
Content-Type: application/json; charset=utf-8  ← 以下全是响应头
Content-Length: 21
Cache-Control: max-age=60

← 空行分隔
{ "name": "张三" }                              ← 响应体

结构极其简单：起始行 + 头部 + 空行 + 正文。空行是关键分隔符，没有它就无法区分头部和正文。

常用请求头速记：Host 目标域名（HTTP/1.1 必需）、Accept 我能接受什么格式、Content-Type 我发的是什么格式、Authorization 凭证、Cookie 浏览器自动带、Referer 从哪个页面来的、If-None-Match 缓存校验。
模块 3

方法语义：幂等性为什么重要

方法安全幂等用途
GET是是读取资源。不产生副作用
HEAD是是只要响应头，不要正文
OPTIONS是是查询支持的方法，CORS 预检用它
POST否否创建资源。重复调用会创建多条
PUT否是全量替换。调 1 次和 10 次结果一样
PATCH否否部分更新
DELETE否是删除。删了再删还是"没了"
幂等性为什么是后端必懂的？因为它决定了"能不能安全重试"。
网络抖动、网关超时、用户狂点提交 —— 请求可能发了但你没收到响应。这时候你敢不敢重发？
GET / PUT / DELETE 幂等，可以放心重试。POST 不幂等，重试可能造成重复下单、重复扣款。
所以支付类接口几乎都不用裸 POST，而是要求客户端带一个唯一的幂等键（idempotency key），服务端靠它去重。

相关概念：安全方法（Safe）指不改变服务端状态的方法，GET / HEAD / OPTIONS 属于此类。爬虫和预加载可以放心调用它们，而 POST 不行。

模块 4

状态码：看到就知道往哪查

区间含义说明
1xx信息101 Switching Protocols（升级到 WebSocket）是唯一常见的
2xx成功200 OK、201 Created、204 No Content（成功但无正文）
3xx重定向需要客户端再发一次请求
4xx客户端错你的请求有问题。排查方向在请求侧
5xx服务端错请求没问题，是服务端挂了。排查方向在服务侧

高频状态码详解

状态码含义与排查方向
301 / 308永久重定向。浏览器和搜索引擎会缓存这个跳转。301 可能把 POST 变成 GET，308 保留方法
302 / 307临时重定向。302 可能改变方法，307 保留方法。登录跳转常用 302
304Not Modified，协商缓存命中。服务端说"你本地那份还是新的，直接用"。看到 304 说明缓存生效了
400请求格式错误。参数缺失、JSON 格式不对
401未认证。没登录、Token 过期或无效。注意：名字叫 Unauthorized，实际含义是"未认证"
403已认证但无权限。登录了，但你没有访问这个资源的权限
404资源不存在。路径写错，或者后端路由没匹配上
405方法不允许。接口只支持 POST，你用了 GET
429Too Many Requests，被限流了。看 Retry-After 头告诉你多久后重试
499Nginx 自定义：客户端主动断开连接。常见于客户端超时先走了
502Bad Gateway。网关（Nginx）把请求转给后端，但后端返回了无效响应。通常是后端进程挂了或崩溃了
503服务不可用。后端过载或正在重启。看有没有 Retry-After
504Gateway Timeout。网关等后端响应超时了。后端处理太慢或卡死
502 和 504 的区分是排查分水岭：
502 = 后端没给出有效响应（进程挂了、崩溃、端口没监听）→ 去看后端进程活着吗。
504 = 后端活着但太慢（超时了）→ 去看后端哪里慢（慢 SQL、外部依赖卡住）。
一个查"活没活"，一个查"为什么慢"，方向完全不同。
模块 5

缓存：性能优化的第一杠杆

HTTP 缓存分两种，理解它们的区别，你就理解了前端性能优化的一半。

类型判断依据行为
强缓存Cache-Control: max-age=3600
Expires（老，用绝对时间）		直接用本地缓存，根本不发请求。状态码显示 200 (from disk cache)
协商缓存ETag / If-None-Match
Last-Modified / If-Modified-Since		发请求问服务端"变了吗"。没变返回 304（无正文），变了返回 200 和新内容
# 协商缓存的完整交互
# 第一次请求，服务端返回：
ETag: "abc123"
Cache-Control: no-cache        ← 注意：no-cache 不是"不缓存"，是"每次都要校验"

# 第二次请求，浏览器带上：
If-None-Match: "abc123"

# 服务端发现内容没变：
HTTP/1.1 304 Not Modified
← 没有响应体，省了流量

Cache-Control 常用指令

指令含义
max-age=36003600 秒内直接用本地缓存（强缓存）
no-cache不是不缓存，是"每次都要向服务端校验"（走协商缓存）
no-store真的完全不缓存，连存都不存。用于敏感数据
private只有浏览器能缓存，CDN 等中间节点不能
public谁都能缓存（包括 CDN）
s-maxage=600专门给 CDN 等共享缓存用，优先级高于 max-age
must-revalidate过期后必须校验，不能用过期副本
immutable内容永不变化，浏览器连校验都跳过。适合带哈希指纹的静态资源
最常见的缓存事故：用户刷新了页面还是旧的。根源通常是 index.html 被强缓存了。
正确做法：HTML 入口文件用 no-cache（每次校验），带哈希指纹的 JS/CSS 用 max-age=31536000, immutable（缓存一年，因为文件名变了就是新文件）。这样既保证了更新及时，又保证了静态资源的最大缓存收益。
模块 6

连接管理：从 1.1 到 3

版本关键改进解决的问题
HTTP/1.0每个请求一个连接——
HTTP/1.1默认长连接（Keep-Alive）、管道化省掉重复建连的开销。但仍有队头阻塞：一个连接同时只能处理一个请求，前一个没回来后面的就得等
HTTP/2多路复用、二进制分帧、头部压缩（HPACK）、服务端推送一个连接上并行跑多个请求，解决了 HTTP 层的队头阻塞。浏览器从"每域名 6 个连接"变成 1 个连接
HTTP/3基于 QUIC（走 UDP 而非 TCP）解决了 TCP 层的队头阻塞 —— 一个包丢了，HTTP/2 的所有流都被卡住；QUIC 不会。还支持 0-RTT 建连
为什么 HTTP/1.1 时代要做"域名分片""雪碧图""资源合并"？因为每域名只有 6 个并发连接，资源多了就排队。HTTP/2 之后这些优化手段反而成了负优化 —— 合并成大文件会让多路复用失去意义，缓存粒度也变粗。所以"最佳实践"是有时代背景的，别盲目照搬老文章。
模块 7

鉴权：Cookie / Session / Token / JWT

因为 HTTP 无状态，服务端必须靠某种机制"记住你"。四种方案，本质区别在于凭证存在哪。

方案凭证存哪特点
Cookie浏览器，自动随请求发送只是个载体，本身不是鉴权方案。有 Domain / Path / Secure / HttpOnly / SameSite 属性
Session服务端内存/Redis，浏览器只存一个 sessionId有状态。能随时踢人下线，但多机部署要共享存储（通常用 Redis）
Token客户端自己保管服务端不存。无状态，但没法主动失效
JWT客户端，内容自包含Token 的一种标准格式。注意：只是签名，不是加密

JWT 的结构（一定要知道这点）

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiIxMjMifQ . dBjftJeZ4CVP...
     ↑ Header              ↑ Payload           ↑ Signature
   算法类型              存放的数据（claims）    签名

# Header 和 Payload 只是 Base64 编码，不是加密！
# 把中间那段拿去 base64 解码，就能看到里面的内容
echo "eyJzdWIiOiIxMjMifQ" | base64 -d
# 输出：{"sub":"123"}  ← 明文可见
关于 JWT 最危险的两个误解：
① "JWT 是加密的，别人看不到内容" —— 错。Payload 只是 Base64，任何人都能解码。绝不能往 JWT 里放密码、身份证号等敏感信息。
② "JWT 能随时踢人下线" —— 默认不能。因为服务端不存状态，签出去的 Token 在过期前一直有效。要支持主动失效，必须额外维护一个黑名单（放 Redis），那就又变成有状态了。

怎么选

单机 / 内部系统
Session + Cookie 最简单可靠。有状态反而是优点（能踢人、能查在线用户）
多端 / 微服务
Token 更合适。无状态、跨域友好、适合网关统一校验
成熟做法
短期 Access Token（15 分钟）+ 长期 Refresh Token。兼顾了无状态的性能和可控的失效
模块 8

CORS 与同源策略

跨域报错是前端最常见的困惑之一。理解它只需要三句话。

① 同源的定义：协议 + 域名 + 端口，三者完全相同才是同源。https://a.com 和 http://a.com 不同源（协议不同）；a.com 和 a.com:8080 不同源（端口不同）。
② 同源策略是浏览器强加的：它限制的是"JS 读取跨域响应的内容"。请求其实发出去了，服务端也处理了，只是浏览器不让 JS 拿到结果。
③ CORS 是服务端授权：服务端通过响应头告诉浏览器"我允许这个来源访问我"。 
# 服务端要返回的响应头
Access-Control-Allow-Origin: https://your-site.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true          # 允许带 Cookie
Access-Control-Max-Age: 86400                   # 预检结果缓存 24 小时

简单请求 vs 预检请求

类型触发条件行为
简单请求方法是 GET/POST/HEAD，且 Content-Type 是表单类或纯文本直接发，浏览器检查响应头决定是否放行
预检请求用了 PUT/DELETE、自定义头（如 Authorization）、或 Content-Type 是 application/json先发一个 OPTIONS 请求问服务端允不允许，通过了才发真正的请求
排查跨域问题的顺序：
① 看 Network 里有没有一个 OPTIONS 请求返回 4xx —— 那是预检失败，检查服务端有没有处理 OPTIONS。
② 看响应头里有没有 Access-Control-Allow-Origin —— 没有就是服务端没配。
③ 带 Cookie 时，Allow-Origin 不能是 *，必须是具体域名，且要配 Allow-Credentials: true。
注意：跨域是浏览器行为，用 curl 或 Postman 测永远不复现。别用它们来"验证跨域问题不存在"。
模块 9

HTTPS：TLS 到底做了什么

HTTPS = HTTP + TLS。TLS 解决了三个问题：机密性（别人看不到内容）、完整性（内容没被篡改）、身份认证（对面确实是这个网站）。

混合加密：为什么不只用一种

算法类型特点在 TLS 里的角色
对称加密快，但双方要共享同一把密钥用来加密实际数据（AES）
非对称加密慢，但公钥可以公开只用来安全地协商出对称密钥（RSA / ECDHE）

这就是 TLS 的精髓：用慢的非对称加密解决"怎么安全地交换密钥"，再用快的对称加密传输数据。

TLS 握手做了什么（简化版）

1. 客户端 → 服务端：ClientHello
   我支持的 TLS 版本、加密套件、一个随机数、SNI（想访问的域名）

2. 服务端 → 客户端：ServerHello + 证书
   选定的加密套件、另一个随机数、服务器证书（含公钥）

3. 客户端验证证书
   沿证书链验证：服务器证书 ← 中间证书 ← 根证书（内置在系统里）
   检查：域名匹配吗？过期了吗？被吊销了吗？签名有效吗？

4. 双方协商出会话密钥
   （ECDHE 场景下，用密钥交换算法各自算出同一个密钥，密钥本身不在网络上传输）

5. 之后所有数据用这个对称密钥加密传输
证书链的意义：你不可能把全世界所有网站的证书都预装在系统里。所以只有几十个根证书被内置，根证书签发中间证书，中间证书再签发服务器证书。验证时沿着链条往上走，直到某个内置的根证书 —— 这就是"信任的传递"。

性能上：TLS 1.2 需要 2 个 RTT（往返时间，即数据一来一回的耗时）才能开始传数据，TLS 1.3 优化到 1 个 RTT（会话恢复甚至能做到 0-RTT，把握手和数据一起发出去）。这也是为什么升级 TLS 1.3 能明显改善首屏速度。

SNI 让一个 IP 能托管多个 HTTPS 域名 —— 客户端在 ClientHello 里就告诉服务端"我要访问哪个域名"，服务端再返回对应证书。这也是为什么抓包能看到你访问了哪个域名（第 1 期讲过这点）。

模块 10

代理、网关与真实 IP

概念说明
正向代理代表客户端去访问。如翻墙工具、公司统一出口代理。服务端看到的是代理的 IP
反向代理代表服务端接收请求。如 Nginx。客户端以为自己直连了服务器
网关 Gateway反向代理 + 鉴权 + 限流 + 路由 + 日志。微服务的统一入口
CDN把静态资源缓存到离用户最近的边缘节点。基于 Cache-Control 和 s-maxage 判断是否缓存
接入代理后，后端拿到的 IP 是代理的 IP。所以有了这些转发头： 
X-Forwarded-For: 客户端IP, 代理1IP, 代理2IP   ← 逗号分隔，第一个是真实客户端
X-Real-IP: 客户端IP                          ← Nginx 常用
X-Forwarded-Proto: https                     ← 原始请求是 http 还是 https
安全警告：X-Forwarded-For 是客户端可以伪造的。如果你的服务直接暴露在公网、又信任这个头做 IP 白名单或限流，攻击者伪造一下就能绕过。必须在最外层网关把客户端传来的这个头覆盖掉，而不是追加。
模块 11

十个线上坑

1
把 no-cache 理解成"不缓存"
no-cache 是"每次都要向服务端校验"（走协商缓存）。真的不缓存是 no-store。这个误解会导致缓存策略完全配错。
2
用 POST 做查询接口
POST 不幂等，无法安全重试、无法被 CDN 缓存、语义也不对。查询就该用 GET。
3
把敏感信息放进 JWT
JWT 的 Payload 只是 Base64 编码，任何人解码就能看。只签名不加密。
4
JWT 设了很长的过期时间
无状态意味着签出去就撤不回来。Access Token 应该短（15 分钟），配 Refresh Token 续期。
5
用 curl 测跨域问题"没问题"
跨域是浏览器的行为，curl 完全不检查 CORS。必须用浏览器 DevTools 验证。
6
带 Cookie 的跨域请求配了 Allow-Origin: *
浏览器会直接拒绝。带凭证时必须是具体域名，且要 Allow-Credentials: true。
7
HTTPS 页面里加载 HTTP 资源
这叫"混合内容"，浏览器会直接拦截。全站必须 HTTPS，包括图片、脚本、接口。用相对协议或全站升级。
8
盲目信任 X-Forwarded-For
客户端可以伪造。做 IP 限流或白名单时，必须在最外层覆盖这个头。
9
302 重定向把 POST 变成了 GET
某些客户端在 302 后会改方法并丢掉请求体，导致参数丢失。需要保留方法时用 307 / 308。
10
接口超时了就直接重试 POST
可能造成重复下单、重复扣款。要么把接口设计成幂等（带幂等键），要么只在确认未生效时重试。
自测

六道题

1. 网关返回 502，最应该先检查什么？
正确答案：后端进程活着吗。502 表示网关拿到的是无效响应，通常是后端崩了。"太慢"对应的是 504，这是两个完全不同的排查方向。
2. 下面哪个方法是幂等的？
正确答案：PUT。PUT 是全量替换，调 1 次和调 10 次结果一样，所以幂等。POST 每次都创建新资源，不幂等 —— 这也是为什么支付接口必须带幂等键。
3. Cache-Control: no-cache 的含义是？
正确答案：每次都要校验。no-cache 走的是协商缓存，会发请求但服务端可能返回 304。"完全不存"是 no-store。
4. 关于 JWT，下面哪个说法是对的？
正确答案：Payload 只是 Base64 编码。它只做签名保证不被篡改，不做加密。而且服务端不存状态，签出去就撤不回来（除非额外维护黑名单）。
5. 用 curl 测试接口一切正常，但浏览器报跨域错误。最可能的原因是？
正确答案：服务端没配 CORS 头。同源策略是浏览器的行为，curl 和 Postman 都不会检查。所以它们永远无法用来验证跨域问题。
6. TLS 为什么同时用对称和非对称加密？
正确答案：混合加密。非对称加密慢但能安全交换密钥，对称加密快但不方便交换密钥。用前者解决密钥分发，用后者解决传输性能。

术语一句话解释
无状态 stateless服务端不记录上一次请求的上下文，每次都是独立的
幂等 idempotent执行一次和执行多次，对服务端状态的影响相同
安全方法 Safe不改变服务端状态的方法（GET / HEAD / OPTIONS）
强缓存直接用本地副本，不发请求。由 Cache-Control max-age 控制
协商缓存发请求问服务端内容变了吗，没变返回 304
ETag内容的唯一标识（通常是哈希），用于协商缓存
队头阻塞 HOL前面的请求没完成，后面的只能排队等
多路复用HTTP/2 特性，一个连接上并行跑多个请求
QUICHTTP/3 的底层协议，基于 UDP，避免 TCP 层队头阻塞
同源策略浏览器限制 JS 读取跨域响应的安全机制
CORS跨域资源共享，服务端通过响应头授权浏览器放行
预检请求非简单请求前先发的 OPTIONS，问服务端允不允许
Session服务端保存的会话状态，客户端只存 sessionId
JWT自包含的令牌格式，Header.Payload.Signature，只签名不加密
TLS传输层安全协议，提供加密、完整性、身份认证
混合加密非对称加密协商密钥 + 对称加密传输数据
证书链根证书 → 中间证书 → 服务器证书，逐级签发的信任传递
SNI客户端在握手时告知要访问的域名，让一个 IP 支持多 HTTPS 站点
RTT往返时间，衡量网络延迟的基本单位
反向代理代表服务端接收请求（如 Nginx）
X-Forwarded-For记录请求经过的代理链，客户端可伪造，需在最外层覆盖
