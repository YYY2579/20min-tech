二十分钟学透 SSH

SSH 天天用，但多数人只会 ssh user@host。真正拉开差距的是三件事：密钥怎么管、隧道怎么打、服务怎么加固。这篇按"一次连接的生命周期"讲，把每个环节的边界说清楚。

20:00
建议开两台机器（或一台 + 本地回环）跟着敲 —— 隧道和跳板不动手是学不会的
开始前

先确认版本与连通性

# 客户端和服务端版本（OpenSSH 8.x 之后默认禁用 ssh-rsa 签名）
ssh -V
sshd -V 2>&1 | head -1

# 生成一把现代密钥（ed25519，默认 256 位）
ssh-keygen -t ed25519 -a 100 -C "you@laptop"

# 把公钥装到目标机（比手工 cat 追加更安全，会帮你建目录设权限）
ssh-copy-id -i ~/.ssh/id_ed25519.pub deploy@10.0.0.5

# 验证：能登录，且不需要输密码
ssh -o BatchMode=yes deploy@10.0.0.5 'echo ok'
文件权限作用
~/.ssh/700目录本身不能对组和其他人开放
~/.ssh/id_ed25519600私钥。绝不能外传，也不能是 644
~/.ssh/id_ed25519.pub644公钥，可以随便给
~/.ssh/authorized_keys600服务端允许登录的公钥列表
~/.ssh/known_hosts600记录你连过的服务器的 host key，用于防中间人
~/.ssh/config600客户端配置，建议 600（里面有主机名和用户名）
先记住一条：SSH 的权限检查是"宁可错杀"的。
私钥是 644、~/.ssh 是 755、authorized_keys 的属主不是当前用户 —— 任何一条不满足，服务端都会直接拒绝公钥认证，而且默认只回一句 Permission denied (publickey)，不告诉你原因。排查时先看 ssh -vvv 的输出。
模块 1

一次连接到底发生了什么

SSH 不是"加密的 telnet"。它在一条 TCP 连接上做了三件独立的事：协商算法、验证服务器身份、验证用户身份。三件事分开理解，故障就能分层定位。

# 连接建立的五个阶段（简化）

1. TCP 三次握手            # 连到 22 端口
        │
2. 版本交换                # 双方各发一行 "SSH-2.0-OpenSSH_9.6"
        │
3. 算法协商 + 密钥交换      # 交换 KEXINIT，用 curve25519 算出共享密钥
        │                       # 这一步之后就全部加密了
4. 验证服务器              # 服务器用 host key 签名，客户端比对 known_hosts
        │
5. 验证用户                # 公钥 / 密码 / 键盘交互 / GSSAPI
        │
   加密信道建立，开始跑 shell 或命令

阶段 3：密钥交换在解决什么

要解决的问题做法
在不安全信道上协商出密钥Diffie-Hellman 类算法（curve25519-sha256、diffie-hellman-group-exchange-sha256）。双方各出一个临时私钥，公开部分交换后能算出同一个共享密钥，窃听者拿不到
前向保密每次连接都用临时密钥对（ephemeral）。即使以后服务器的长期私钥泄露，也解不开之前录下的流量
防重放交换过程带随机数和会话 ID，同一份握手包重放无效

阶段 4：host key 与 known_hosts

密钥交换只能保证"这条信道不被窃听"，但没法证明对面是谁 —— 中间人可以分别和两边握手。所以服务器要用自己的长期私钥（host key）对握手内容签名，客户端第一次连接时把公钥记进 known_hosts，以后每次比对。

# 第一次连接，会问你信不信这个指纹
The authenticity of host '10.0.0.5' can't be established.
ED25519 key fingerprint is SHA256:xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.
Are you sure you want to continue connecting (yes/no/[fingerprint])?

# 更安全的做法：从带外渠道拿到指纹，手工比对
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
# 输出：256 SHA256:xxxx root@host (ED25519)

# 指纹变了（重装系统 / 换机器 / 中间人）
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@

# 确认是正常的系统重装后，删掉旧记录
ssh-keygen -R 10.0.0.5
# 如果开了 HashKnownHosts，known_hosts 里的主机名是哈希过的，也要用 -R
看到 host key 变更告警，绝对不要习惯性 rm known_hosts。
这个告警的含义是"对面的身份和上次不一样了"，可能是重装系统，也可能是有人在中间人攻击。正确流程：① 通过带外渠道（控制台、云厂商面板、同事）确认服务器是否重装或换 IP；② 用 ssh-keygen -lf 比对指纹；③ 确认无误后再 ssh-keygen -R。
把 StrictHostKeyChecking 设成 no 来"图省事"，等于把这层防护整个关掉。折中的选择是 accept-new：首次自动接受，之后变更仍然报错。

阶段 5：公钥认证的具体流程

# 关键点：私钥永远不离开客户端

客户端                                      服务端
  │                                           │
  │  "我想用这把公钥登录"  ──────────────────> │
  │  （发送公钥，或只发指纹）                    │  查 authorized_keys
  │                                           │
  │  <──────────  挑战：一段随机数据（用公钥加密） │
  │                                           │
  │  用私钥解密 / 签名  ─────────────────────> │  用公钥验签
  │                                           │
  │  <──────────  认证通过                     │

# 所以：authorized_keys 里放的是公钥，泄露它不会导致别人能登录
# 但私钥泄露 = 别人可以冒充你，必须立刻从所有 authorized_keys 里删掉对应公钥
模块 2

密钥管理：选型、口令、agent

类型公钥长度评价
ed2551968 字节（256 位）默认首选。签名快、密钥短、没有可调参数（也就没有配错的空间）。OpenSSH 6.5+ 支持
rsa3072 / 4096 位兼容老系统（比如很旧的网络设备、老版本 Git 服务）。至少 3072 位，1024 位已不安全
ecdsa256 / 384 / 521 位能用，但实现依赖 NIST 曲线，部分团队出于信任原因不选
ed25519-sk—密钥存在 FIDO2 硬件钥匙里，物理接触才能签名。高安全场景
# 生成 ed25519（-a 是 KDF 轮数，越大越抗暴力破解，100 是常用值）
ssh-keygen -t ed25519 -a 100 -C "alice@laptop-2026"

# 兼容场景才用 RSA，且必须 3072 位以上
ssh-keygen -t rsa -b 4096 -o -a 100 -C "alice@legacy"

# 给已有私钥加 / 改口令
ssh-keygen -p -f ~/.ssh/id_ed25519

# 看公钥指纹和类型
ssh-keygen -lf ~/.ssh/id_ed25519.pub

passphrase 到底防什么

私钥文件落在磁盘上，如果没有口令，任何拿到这个文件的人（备份泄露、笔记本丢失、误提交到 Git）都能直接登录。加了口令后，私钥在磁盘上是加密的，攻击者需要暴力破解口令。

场景建议
个人笔记本一定要有口令，配合 ssh-agent 免去重复输入
CI / 自动化通常无口令，但必须限定权限（只读、只能部署到特定目录），并放在密钥管理服务里
服务器之间互信无口令 + authorized_keys 里加 from= 限制来源 IP

ssh-agent：把解密后的私钥留在内存里

# 启动 agent（多数桌面环境会自动起）
eval "$(ssh-agent -s)"

# 加入密钥，输入一次口令，之后本次登录内都不再问
ssh-add ~/.ssh/id_ed25519
ssh-add -l          # 列出已加载的密钥指纹
ssh-add -D          # 全部清除

# 带超时：3600 秒后自动失效（更安全）
ssh-add -t 3600 ~/.ssh/id_ed25519

# macOS 可以把口令存进 Keychain，重启后也不用重输
ssh-add --apple-use-keychain ~/.ssh/id_ed25519

# 确认当前 shell 能看到 agent
echo $SSH_AUTH_SOCK
agent 转发（ssh -A）是一把双刃剑。
它让你从 A 跳到 B 之后，还能用 A 上的密钥去连 C，私钥本身不用复制到 B。但代价是：B 上的 root 用户可以通过 SSH_AUTH_SOCK 借用你的 agent，以你的身份登录任何信任这把钥匙的机器。B 一旦被入侵，攻击者就能横向移动。
三条实践：① 只在必要时开 -A，不要写进全局配置；② 用 ssh-add -c，每次使用都弹确认；③ 更安全的替代是 ProxyJump —— 它只做 TCP 转发，不把你的 agent 暴露给跳板机。

多把密钥怎么区分

# 默认情况下，ssh 会按顺序尝试 ~/.ssh/id_* 里的所有密钥
# 服务器通常只允许尝试 6 次（MaxAuthTries），密钥多了会被拒

# 解法一：在 config 里为每个 Host 指定密钥 + IdentitiesOnly
Host github.com
  IdentityFile ~/.ssh/id_ed25519_github
  IdentitiesOnly yes        # 只用这一把，不遍历 agent 里的其他钥匙

Host gitlab.internal
  IdentityFile ~/.ssh/id_ed25519_work
  IdentitiesOnly yes

# 解法二：不同用途不同密钥，文件名自带语义
# id_ed25519_personal / id_ed25519_work / id_ed25519_ci

# 验证某台机器实际用了哪把钥匙
ssh -v git@github.com 2>&1 | grep -i "Offering public key"
模块 3

~/.ssh/config：把长命令变成别名

这是投入产出比最高的一个文件。写一次，之后所有 ssh、scp、rsync、git 都自动生效。

# ~/.ssh/config  权限 600

Host web
  HostName 10.0.0.5
  User deploy
  Port 2222
  IdentityFile ~/.ssh/id_ed25519_web
  IdentitiesOnly yes

Host db
  HostName db.internal.example.com
  User dba
  ProxyJump bastion

Host bastion
  HostName 203.0.113.10
  User jump
  IdentityFile ~/.ssh/id_ed25519_jump

# 通配符：内网机器统一走跳板 + 统一用户
Host 10.0.0.*
  User ops
  ProxyJump bastion
  ServerAliveInterval 30
  ServerAliveCountMax 3

# 所有主机通用的默认值（放在文件末尾，前面匹配到的优先）
Host *
  ServerAliveInterval 30
  ServerAliveCountMax 3
  AddKeysToAgent yes
  HashKnownHosts yes

# 拆分文件，团队可以共享一部分、个人保留一部分
Include ~/.ssh/config.d/*
Include ~/.ssh/config.work
字段说明
Host你敲的别名，可以写多个（空格分隔），支持 * 和 ? 通配
HostName真实域名或 IP。不写则等于 Host 的值
User登录用户名。不写则用本机当前用户名
Port端口，默认 22
IdentityFile私钥路径，可以写多行，按顺序尝试
IdentitiesOnly只用手动指定的密钥，不遍历 agent。多密钥场景必写
ProxyJump先连跳板机，再从跳板机连目标
LocalForward / RemoteForward把端口转发写进配置，登录即建立
RequestTTY / RemoteCommand登录后直接执行命令，不进入交互 shell
ControlMaster / ControlPath / ControlPersist连接复用：第一条连接建好后，后续连接直接走这条 TCP，省掉握手
# 连接复用：批量操作几十台机器时，能把总耗时砍掉一半以上
Host *
  ControlMaster auto
  ControlPath ~/.ssh/cm-%r@%h:%p
  ControlPersist 10m

# 效果：第一次 ssh 建立连接，10 分钟内再连同一台机器是毫秒级
# 关闭某条复用的连接
ssh -O exit web

# 注意：ControlPath 太长会超过 Unix socket 的 108 字节上限
# 用 %C 让 ssh 自己算一个短哈希
ControlPath ~/.ssh/cm-%C
配置的匹配规则：SSH 从文件顶部往下读，每个参数取第一个匹配到的值，而不是最后一个。所以"通配的默认值"要放在文件末尾，而具体的 Host 块要放在前面。
这条规则和大多数配置文件（后面的覆盖前面的）相反，是排查"我明明配了为什么不生效"的第一嫌疑人。用 ssh -G web 可以直接打印出最终生效的完整配置。
模块 4

端口转发：三种方向，三个真实场景

端口转发的本质是：SSH 客户端在本地监听一个端口，把收到的 TCP 连接塞进加密信道，由另一端帮你连到目标。方向不同，用途完全不同。

参数名字谁在监听典型场景
-L本地转发你的机器监听，流量发往远端网络访问只对服务器内网开放的数据库、管理后台
-R远程转发服务器监听，流量发回你的机器把本地开发服务暴露给远程；穿透 NAT
-D动态转发你的机器监听一个 SOCKS 代理端口浏览器 / 命令行走 SOCKS，按目标动态连

-L：把远端的内网服务搬到本地

# 场景：MySQL 只监听 127.0.0.1:3306，公网连不上
# 语法：-L [本地绑定地址:]本地端口:目标主机:目标端口
ssh -N -L 13306:127.0.0.1:3306 deploy@10.0.0.5

# 然后本地就能连了（注意：连的是 127.0.0.1，不是远端）
mysql -h 127.0.0.1 -P 13306 -u app -p

# 目标主机是"从服务器视角看"的地址，可以是内网另一台机器
ssh -N -L 15432:db.internal:5432 deploy@10.0.0.5

# 参数说明
-N   不执行远程命令，只做转发（不加会给你一个 shell，占着终端）
-f   转到后台（配合 -N 使用）
-T   不分配 TTY

# 只想让本机访问，绑 127.0.0.1（默认）
# 想让局域网同事也能用，绑 0.0.0.0 —— 但这等于把内网服务暴露给整个局域网
ssh -N -L 0.0.0.0:13306:127.0.0.1:3306 deploy@10.0.0.5

-R：把本地服务推到远端

# 场景一：本地起了个 3000 端的服务，想让远程机器（或远程的同事）访问
ssh -N -R 8080:127.0.0.1:3000 deploy@10.0.0.5
# 现在在 10.0.0.5 上访问 http://127.0.0.1:8080 就是你的本地 3000

# 场景二：穿透 NAT，让公网机器反连内网机器
# 内网机器主动连出去，公网机器监听 2222
ssh -N -R 2222:127.0.0.1:22 root@203.0.113.10
# 之后从公网机器：ssh -p 2222 localhost 就能进内网机器

# 默认 -R 只在远端的 127.0.0.1 上监听
# 要让外部能连，服务端 sshd_config 必须开：
GatewayPorts yes        # 或 clientspecified，由客户端指定绑定地址

# 端口被占用时让服务器自动分配
ssh -N -R 0:127.0.0.1:3000 deploy@10.0.0.5
# 加 -v 可以看到 "Allocated port 41234 for remote forward"

-D：一个 SOCKS5 代理，按目标动态转发

# 在本地 1080 起一个 SOCKS5 代理，所有流量从 10.0.0.5 出去
ssh -N -D 1080 deploy@10.0.0.5

# 命令行验证：看出口 IP 是不是服务器
curl --socks5-hostname 127.0.0.1:1080 https://ifconfig.me

# git 走代理
git -c http.proxy=socks5h://127.0.0.1:1080 clone https://github.com/org/repo

# 浏览器：设置 SOCKS5 代理为 127.0.0.1:1080，勾选"代理 DNS"
# 否则 DNS 仍在本地解析，会泄露你访问的域名
三个容易忽略的边界：
① -L 的目标地址是从 SSH 服务端解析的，不是从你本地解析。所以 -L 3306:db:3306 里的 db 要在服务器的网络里能解析。
② -R 默认只绑远端的回环地址，不开 GatewayPorts 的话外网连不上，这不是防火墙问题。
③ 转发是明文进隧道、明文出隧道：SSH 只保证中间那段加密，两端的应用协议本身没有加密。别以为套了 SSH 就万事大吉。
模块 5

跳板机与 ProxyJump

生产环境的目标机通常没有公网 IP，只能从堡垒机进。有两种做法：先登录堡垒机再手动 ssh（麻烦），或者让 SSH 客户端自动完成两跳（推荐）。

# 最直接：-J 指定跳板
ssh -J jump@203.0.113.10 deploy@10.0.0.5

# 多级跳转：按顺序经过 bastion1、bastion2
ssh -J alice@bastion1,alice@bastion2 deploy@10.0.0.5

# 每一跳都可以单独指定密钥和端口
ssh -J alice@bastion1:2222,bob@bastion2 deploy@10.0.0.5

# 写进 config 后，日常只需要 ssh db
Host db
  HostName 10.0.0.5
  User deploy
  ProxyJump alice@bastion1,alice@bastion2

# 等价的旧写法：ProxyCommand（OpenSSH 7.3 之前没有 -J）
ProxyCommand ssh -W %h:%p bastion
# %h = 目标主机，%p = 目标端口
# -W 表示把 stdio 转发到目标的 host:port

ProxyJump 和 agent 转发的区别

维度ProxyJumpssh -A（agent 转发）
跳板机上有没有你的私钥没有，只转发 TCP 字节流私钥不在，但 agent socket 在，可被借用
跳板机被入侵的风险低（只能看到加密流量）高（攻击者可以用你的身份连其他机器）
能否用不同密钥连每一跳可以通常共用 agent 里的钥匙
适用默认选择只在确实需要"从 B 再用我的身份连 C"时
# 验证跳转链路：-v 会打印每一跳的握手
ssh -v -J jump@203.0.113.10 deploy@10.0.0.5

# 常见失败：跳板机上没有目标机的 known_hosts，会卡在 yes/no
# 这时确认指纹后，在跳板机上先手动连一次，或者用 accept-new
ssh -o StrictHostKeyChecking=accept-new -J bastion deploy@10.0.0.5

# 也可以让 scp / rsync 走跳板
scp -J bastion ./app.tar.gz deploy@10.0.0.5:/opt/
rsync -avz -e "ssh -J bastion" ./dist/ deploy@10.0.0.5:/opt/dist/
为什么 -J 比"先 ssh 到堡垒机再 ssh"好：后者会在堡垒机上留下你的私钥使用痕迹（如果你拷了钥匙），或者要求你在堡垒机上再输一次密码；而且 scp、rsync、git 都没法直接复用。-J 只做 TCP 层转发，认证端到端发生在你和目标机之间，堡垒机看不到内容，也不需要信任你的密钥。
模块 6

加固：把门关到只留一条缝

一台暴露在公网的 22 端口，每天会收到几千到几万次撞库尝试。加固不是"可选优化"，是上线前的必做项。

# /etc/ssh/sshd_config.d/99-hardening.conf
# （Debian/Ubuntu 用 sshd_config.d/，RHEL 系确认 Include 指令是否存在）

PermitRootLogin no                  # 禁止 root 直接登录，先建普通用户再 sudo
PasswordAuthentication no          # 只允许公钥，彻底关掉密码撞库
KbdInteractiveAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no

AllowUsers deploy alice            # 白名单，比 AllowGroups 更细
MaxAuthTries 3                      # 一次连接最多试 3 把钥匙
LoginGraceTime 20                   # 20 秒内没完成认证就断开
MaxStartups 10:30:60                # 限制并发未认证连接，缓解暴力破解

X11Forwarding no
AllowAgentForwarding no
AllowTcpForwarding no               # 不需要隧道就关掉；需要时改成 local 或 yes
PermitTunnel no

ClientAliveInterval 60
ClientAliveCountMax 3

UsePAM yes
LogLevel VERBOSE
# 改完必须验证语法，否则重启后可能再也连不上
sshd -t
# 再重启（先确保当前会话不要断，另开一个窗口测试）
systemctl reload sshd      # Debian/Ubuntu 服务名可能是 ssh

# 关键：改配置前先给自己留后路
# 1. 保持一个已登录的会话不要关
# 2. 用第二个终端测试新连接
# 3. 云主机确认控制台 / VNC 可用

authorized_keys 的四个限制项

# 在公钥前面加逗号分隔的选项，只对这一把钥匙生效
from="10.0.0.0/8,*.corp.example.com",command="/usr/local/bin/backup.sh",restrict ssh-ed25519 AAAA... alice@laptop

# 逐项解释
from="..."         # 只接受来自这些 IP / 网段的连接（支持 CIDR 和通配符）
command="..."      # 强制登录后只执行这条命令，忽略客户端请求的 shell / 命令
restrict             # 关闭所有转发能力（端口、agent、X11、pty）
no-pty               # 不分配终端，只能跑非交互命令
permitopen="db:5432" # 只允许转发到这一个目标
expiry-time="20261231"  # 过期时间，到点自动失效
environment="A=1"    # 注入环境变量

# 验证某个 key 的选项是否生效
# 服务端日志里会显示：Accepted publickey for deploy ...
command= 不是沙箱。它只限制"登录后默认执行什么"，如果脚本本身有命令注入、或者允许传参，仍然可能被利用。真正的限制要靠独立的系统用户 + 文件系统权限 + SELinux/AppArmor。
同理，from= 依赖源 IP，在 NAT 或负载均衡后面可能全部变成同一个地址，白名单就失效了。

fail2ban：把撞库的 IP 关进小黑屋

# /etc/fail2ban/jail.d/sshd.local
[sshd]
enabled  = true
port     = ssh
filter   = sshd
logpath  = /var/log/auth.log      # RHEL 系是 /var/log/secure
maxretry = 5                      # 5 次失败
findtime = 10m                    # 10 分钟内
bantime  = 1h                     # 封 1 小时

# 生效与查看
systemctl restart fail2ban
fail2ban-client status sshd
fail2ban-client set sshd unbanip 203.0.113.77

# 注意：fail2ban 读的是日志。如果 sshd 没记失败日志（LogLevel 太低），它什么也看不到
加固的顺序错了会把自己锁在门外。正确顺序：
① 先确认公钥登录可用（ssh -o PreferredAuthentications=publickey）；
② 再关密码登录；③ 再关 root 登录；④ 最后才改端口 / 上防火墙。
每一步都用另一个终端验证，并且保留当前会话。永远不要在一次操作里同时改端口和关密码 —— 一旦出错，只能去机房或云控制台。

模块 8

保持连接：别让会话莫名其妙断掉

"SSH 过几分钟就断"几乎不是 SSH 的问题，而是中间的网络设备（NAT、防火墙、负载均衡）清理了空闲连接表项。两端都以为连接还在，实际上已经不通了。

机制在哪一端作用与边界
ServerAliveInterval客户端每隔 N 秒发一个加密的空包。能穿过 NAT，因为它是应用层数据
ServerAliveCountMax客户端连续 N 次没响应就断开（默认 3）。所以总超时 ≈ Interval × CountMax
ClientAliveInterval服务端服务端主动问客户端"还活着吗"。适合"客户端不配 keepalive"的场景
TCPKeepAlive内核只能检测对端主机是否宕机，不能防止 NAT 表项过期，因为保活包可能被中间设备丢弃或不转发
ControlPersist客户端复用连接，减少重复握手；不是保活机制
# 客户端：写进 ~/.ssh/config 的 Host * 块
ServerAliveInterval 30
ServerAliveCountMax 3
# 效果：90 秒内没响应才断开；期间每 30 秒有一个小包，NAT 不会清理表项

# 服务端：/etc/ssh/sshd_config
ClientAliveInterval 60
ClientAliveCountMax 3
# 效果：服务端每 60 秒探测一次，3 次无响应就释放会话

# 临时用（不改配置）
ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=3 deploy@10.0.0.5

mosh：为高延迟和移动网络设计的替代品

维度SSHmosh
传输层TCPUDP（默认 60000-61000）
断线恢复连接断了就没了，要重连换 IP、切 Wi-Fi、休眠唤醒后自动恢复
输入延迟每次按键要等服务端回显本地预测回显，高延迟下体验明显更好
端口转发支持不支持
认证完整的 SSH先用 SSH 登录，再由 mosh 接管会话
# 安装（两端都要）
apt install mosh        # 或 yum install mosh

# 使用：先走 SSH 认证，然后切到 UDP
mosh deploy@10.0.0.5

# 指定端口范围（防火墙要放行 UDP）
mosh --server="mosh-server new -p 60001:60100" deploy@10.0.0.5

# 注意：mosh 不保持 SSH 会话本身，它接管的是一个 shell
# 所以 mosh + tmux 才是完整方案：mosh 抗网络抖动，tmux 抗进程被杀
远程开发的标准组合：
ssh → tmux new -s work，所有长任务跑在 tmux 里。断线后重新 ssh，再 tmux attach -t work，现场原样恢复。
如果网络本身很差（跨国、4G、频繁切换网络），把 ssh 换成 mosh，但仍然在里面跑 tmux —— 两者解决的是不同层的问题，不能互相替代。
常见坑

九个真实踩过的坑

1
私钥权限是 644
客户端直接拒绝使用这把钥匙，报 UNPROTECTED PRIVATE KEY FILE。执行 chmod 600 ~/.ssh/id_*，目录 chmod 700 ~/.ssh。
2
看到 host key 变更就删 known_hosts
这等于关掉了中间人防护。先带外确认指纹，再 ssh-keygen -R。把 StrictHostKeyChecking 设成 no 是更糟的做法。
3
在 config 里把 Host * 写在最前面
SSH 是"第一个匹配到的值生效"，Host * 放前面会吃掉所有默认值，后面的具体配置反而不生效。通配块永远放末尾。
4
多把密钥时不写 IdentitiesOnly yes
客户端会把 agent 里的钥匙挨个试一遍，超过服务端 MaxAuthTries（默认 6）就被拒，报 Too many authentication failures。
5
用 ssh -A 做日常跳板
跳板机上的 root 可以借用你的 agent 登录其他机器。默认用 ProxyJump，只在确有必要时开转发，并配合 ssh-add -c。
6
以为 -R 配好就能被外网访问
服务端默认只在 127.0.0.1 监听。要外部可达，sshd_config 必须开 GatewayPorts yes，同时防火墙放行。
7
一次操作里同时改端口 + 关密码登录
配错了就彻底失去访问，只能去云控制台。加固要分步做，每一步用另一个终端验证，并保留当前会话。
8
把 TCPKeepAlive 当成防断线手段
它是内核级探测，保活包可能被 NAT 丢弃，防不住表项过期。要用应用层的 ServerAliveInterval。
9
私钥被提交进了 Git
即使后来删掉，历史里仍然有。立刻从所有 authorized_keys 移除对应公钥、换新密钥，并检查服务器日志有没有异常登录。预防靠 .gitignore + 提交前扫描。
自测

六道题

1. 公钥认证过程中，私钥会在什么时候传给服务器？
正确答案：永远不传。这是公钥认证的核心：私钥只在客户端本地参与运算。所以 authorized_keys 泄露不会导致别人能登录，但私钥泄露等于身份被盗。
2. known_hosts 的作用是？
正确答案：第三项。密钥交换只能保证信道不被窃听，不能证明对面是谁。host key 的比对补上了这一环，所以"变更告警"必须认真对待。
3. 要把远端只能内网访问的 MySQL（127.0.0.1:3306）映射到本地 13306，用？
正确答案：-L。本地转发：在你的机器上监听 13306，流量经 SSH 到服务器，再由服务器连它的 127.0.0.1:3306。-R 方向相反，-D 是 SOCKS 代理。
4. 关于 ProxyJump 和 ssh -A，哪个说法对？
正确答案：第二项。-A 虽然不复制私钥，但把 agent socket 暴露在跳板机上，root 可以借用它。ProxyJump 只做字节流转发，认证端到端完成。
5. 客户端报 Permissions 0644 ... are too open，应该？
正确答案：第三项。SSH 要求私钥只有属主可读写，目录只有属主可访问。放宽权限会被直接拒绝，这是保护机制不是 bug。
6. 想防止 SSH 会话被 NAT 超时断开，最有效的是？
正确答案：ServerAliveInterval。它在应用层定期发加密空包，能穿过 NAT 并刷新表项。TCPKeepAlive 是内核级探测，保活包可能被中间设备丢弃，防不住表项过期。
