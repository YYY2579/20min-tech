模块 1

语义化版本：三位数字各自承诺什么

语义化版本（Semantic Versioning，下称 SemVer）规定版本号形如 MAJOR.MINOR.PATCH，三段都是非负整数，且禁止前导零。三段之外的预发布标识和构建元数据，各有各的语法位置。

位置什么时候 +1对使用者的承诺
MAJOR
主版本号		做了不向下兼容的 API 变更升级必须改代码。你必须读变更日志、按迁移指南改，不能盲升
MINOR
次版本号		新增向下兼容的功能，或标记了废弃可以放心升。旧代码不用改就能跑，只是多了新能力
PATCH
修订号		做了向下兼容的问题修复应该无感升级，甚至建议自动升。行为不变，只是 bug 没了

三个数字是独立进位的：1.9.7 出一个不兼容变更，直接变 2.0.0，MINOR 和 PATCH 一起归零。新增功能则是 1.9.7 → 1.10.0，PATCH 归零。这个"归零"不是审美，是让排序规则保持单调：版本号可以按数值逐段比较大小。

什么算"API"

SemVer 说的 API 是你公开承诺给别人用的那部分，不只是函数签名。判断标准是"使用者是否合理地依赖了它"。

变更版本位为什么
删掉一个公开函数MAJOR调用方直接编译/运行失败
给函数加一个必填参数MAJOR等价于改了调用契约
给函数加一个可选参数（有默认值）MINOR旧调用方式仍然有效
修了一个 bug，但有人依赖了错误行为MAJOR 或 PATCH边界案例。若错误行为已被文档写明，改它算破坏契约；若只是实现意外，算 PATCH
改内部实现、重构私有方法PATCH 或不发版外部不可见，不构成 API 变更
提升最低运行时版本（如要求 Node 18+）MAJOR旧环境装不上，属于环境契约变更
改 CLI 的输出格式、配置文件字段名MAJORCLI 输出和配置就是 API，脚本会解析它

三条硬规则

已发布的版本内容不可修改。1.4.2 发布之后，哪怕只改一个错别字，也必须发 1.4.3。重新覆盖同版本制品，会让"同一版本号在不同机器上是不同代码"，锁文件和缓存全部失去意义。
1.0.0 是"公共 API 定型"的宣言。在这之前，任何东西都可以变。所以库作者不该羞于发 1.0.0，长期停在 0.x 反而是对使用者不负责。
构建元数据不参与比较。1.4.2+build.7 和 1.4.2+build.8 优先级完全相同，只是标注来源。别把 git sha 塞进这里指望它能排序。
为什么这套约定值得认真执行：它把"升级风险"从一句主观判断变成了可计算的量。Dependabot 看到 PATCH 就自动合并，看到 MAJOR 就开 PR 等人审；npm install 敢在 ^1.2.3 范围内随便取最新，是因为它相信你不会在 1.4.0 里删函数。整个生态的自动化，建立在这条信任上。一次撒谎，所有下游的自动化都变成负债。
模块 2

0.x 版本：一句"随时可能变"的免责声明

SemVer 规范第 4 条的意思很直白：主版本号为 0 时，表示处于初始开发阶段，任何东西都可能随时改变，公共 API 不应被视为稳定。换句话说，0.x 不是"早期版本"，是没有承诺。

# 同样是 ^，在 0.x 上语义完全不同（npm 的 caret 规则）
^1.2.3   →  >=1.2.3 <2.0.0     # 允许 MINOR 自由升
^0.2.3   →  >=0.2.3 <0.3.0     # 只允许 PATCH 升，MINOR 被当成"破坏位"
^0.0.3   →  >=0.0.3 <0.0.4     # 等于锁死，只能升到 0.0.4 之前

# 这就是为什么"我明明写了 ^，怎么升个小版本就炸了"
# 因为对方是 0.x，0.2 → 0.3 在它的语境里就是一次大版本
写法在 1.x 上的含义在 0.x 上的含义
^1.2.3允许到 2.0.0 之前^0.2.3 → 0.3.0 之前
~1.2.3允许到 1.3.0 之前~0.2.3 → 0.3.0 之前（与 caret 相同）
1.2.3精确锁定精确锁定
*任意版本任意版本，包括 0.0.1 到 0.9.9 的任意跳变

为什么很多项目永远停在 0.x

  • 发 1.0 意味着承诺。一旦 1.0，任何破坏性变更都要等下一个大版本，还要写迁移指南。停在 0.x 就永远有"我早说了不稳定"的退路。
  • 作者把 0.x 当"成熟度标签"用。这是误用：0.9.9 不代表"快好了"，只代表"还没承诺"。真正的成熟度应该由文档、测试覆盖率、issue 响应速度体现。
  • 生态惯性。一些语言社区（例如早期的 Rust crate、大量内部基础库）默认从 0.1.0 起步，然后靠 0.MINOR 递增来表达破坏性变更，形成了事实上的"0.x 里的 MAJOR"。
给使用者的操作建议（三条，按优先级）：
① 生产依赖优先选已发 1.0 以上的库；对只有 0.x 的关键依赖，在选型阶段就把"它会不会突然改 API"计入风险。
② 对 0.x 依赖用精确版本（"0.2.3" 而不是 "^0.2.3"），升级走人工 review。
③ 升级前必看 CHANGELOG 的 0.MINOR 段——那才是真正的破坏性变更清单，不要因为它"只是个小版本"就跳过。
模块 3

预发布版本：alpha、beta、rc 与排序规则

预发布标识写在 PATCH 之后，用连字符连接，例如 1.0.0-rc.1。它表示"这个版本指向 1.0.0，但还不是 1.0.0"。

阶段含义允许的变更
alpha内部验证，功能可能还没齐什么都能改，包括删功能。只给愿意踩坑的人用
beta功能冻结，开始找 bug只修 bug 和小调整，不再加新功能
rc
release candidate		候选发布版，理论上就是下一个正式版只修阻塞发布的问题。rc 期间还在改功能，说明 beta 阶段没做好

排序规则（这段必须记准）

预发布部分由点分隔的标识符组成，比较时逐段进行：纯数字段按数值比较；含字母的段按 ASCII 字典序比较；数字段的优先级低于字母段；所有前置段相同时，段数多的更大；带预发布标识的版本永远小于对应的正式版。

# 从小到大，完整的一条链
1.0.0-alpha
1.0.0-alpha.1
1.0.0-alpha.beta
1.0.0-beta
1.0.0-beta.2
1.0.0-beta.11        # 注意：比 beta.2 大，因为是数值比较，不是字符串比较
1.0.0-rc.1
1.0.0                # 正式版永远最大

# 反例：如果按字符串排序，beta.11 < beta.2，整个发布流水线会选错版本
两个高频踩坑点：
① 普通版本范围默认不匹配预发布。^1.0.0 不会解析到 1.1.0-rc.1，哪怕数值上它在范围内。要用预发布，必须显式写 ^1.1.0-rc.1 或精确版本。这是 npm 等工具的保护机制，避免"装个依赖装到了半成品"。
② 预发布版本之间不保证兼容。2.0.0-beta.1 到 2.0.0-beta.2 可以随意破坏 API，因为它们都还没承诺。 
# 用 npm 打预发布版本（会同时改 package.json 并创建 commit + tag）
npm version prerelease --preid=rc        # 1.0.0 → 1.0.1-rc.0
npm version prerelease --preid=rc        # 1.0.1-rc.0 → 1.0.1-rc.1
npm version 1.0.1-rc.1 --no-git-tag-version   # 只改文件，不碰 git

# 手工打 tag 的规范写法（annotated tag，带作者、时间、说明）
git tag -a v1.0.0-rc.1 -m "1.0.0-rc.1 候选版，仅修阻塞问题"
git push origin v1.0.0-rc.1
模块 4

版本范围与依赖：^、~ 和锁文件

版本范围描述的是"允许的集合"，不是一个确定的值。理解这一点，就理解了为什么必须有锁文件。

写法等价区间语义
^1.2.3>=1.2.3 <2.0.0允许 MINOR 和 PATCH 升级。最常用，适合遵守 SemVer 的库
~1.2.3>=1.2.3 <1.3.0只允许 PATCH 升级。保守，适合"MINOR 也不敢信"的库
1.2.3=1.2.3精确锁定。0.x 依赖、内部包常用
1.2.x>=1.2.0 <1.3.0等价于 ~1.2.0，写法更直观
*任意不要用。等于放弃所有兼容性保护
1.2.3 - 2.3.4>=1.2.3 <=2.3.4闭区间，跨大版本，慎用
^1.2.3 || ^2.0.0并集同时支持两条产品线（维护旧大版本时）

为什么锁文件不可省

范围只约束"直接依赖"，管不住"依赖的依赖"。你今天写 ^1.2.3，明天作者发了 1.2.4，里面又升了它自己的依赖——整棵树可能完全不同。锁文件记录的是某一次解析的完整结果：每个包的精确版本、下载地址、完整性哈希。

npm ls axios

依赖地狱是怎么形成的

  • 菱形依赖。A 依赖 C@1.x，B 依赖 C@2.x，你的项目同时用 A 和 B。npm 的做法是允许并存（嵌套 node_modules，两份 C 各跑各的）；Go 的做法是 MVS（最小版本选择），取满足所有要求的最低可行版本，冲突时被迫升到 2.x，可能让 A 编译不过。
  • peer dependency 冲突。插件要求宿主框架 ^17，你的项目是 18。npm 7 之后会尝试自动安装 peer，装不上就报 ERESOLVE。不要用 --legacy-peer-deps 一把梭，那只是把冲突藏起来。
  • 传递依赖爆炸。一个 200 行的工具库拖进 80 个包，其中 30 个你从没听过。体积、漏洞面、构建时间都被放大。
  • 多版本共存导致单例失效。React、日志库、状态管理这类"必须全局唯一"的包，一旦出现两份实例，就会出现"context 读不到""日志打两遍"的诡异问题。
工程上的四条硬规矩：① 锁文件必须提交到仓库，且 code review 时认真看它的 diff（新增了哪些包、来源是否可信）；② CI 用 npm ci 而不是 npm install，保证可重现；③ 依赖升级由机器人开 PR，但 MAJOR 升级必须人工读 changelog；④ 定期跑 npm audit / govulncheck，但别为了清零而盲目升大版本。

模块 6

发布流程：从冻结到灰度

发布不是"打个 tag 就完事"。一次可回滚的发布，是一条每一步都有产出、每一步都能停的流水线。

代码冻结。切出 release 分支，只允许修阻塞问题。主干继续开发下一个版本，两者不再混在一起。
确定版本号。按本次变更的最大级别定：有破坏 → MAJOR；有新增 → MINOR；只有修复 → PATCH。版本号在冻结时定，不在发布时临时拍。
写发布说明。CHANGELOG 面向"用这个库的人"，Release Notes 面向"运维和值班的人"——后者要额外写：配置有没有新增项、数据库有没有迁移、监控指标有没有变、已知问题是什么。
打 annotated tag。格式统一为 v1.4.0（带 v 前缀，便于 git describe 识别）。不要用轻量 tag，它没有作者和时间信息，审计时说不清是谁发的。
CI 构建制品。由 tag 触发，而不是由人工在本地构建。构建产物必须可复现：固定基础镜像 digest、锁定依赖、记录构建环境版本。
产出校验和与签名。发布 SHA256SUMS，有条件就签名（cosign / GPG）。使用者下载后能验证"这个包确实是你发的、没被篡改"。
灰度发布。按 1% → 5% → 25% → 100% 分批，每批至少观察一个完整的业务周期（含高峰）。每批之间自动比对关键指标，超阈值自动暂停。
观察与决策。看四类信号：错误率、P99 延迟、资源饱和度、业务指标（下单成功率、支付转化）。前三个正常但业务指标掉了，同样是事故。
全量或回滚。回滚不是"再发一次旧版本"这么简单——数据库迁移、消息格式、缓存结构都可能是单向的。所以回滚预案必须在发布之前写好并演练过。
# 完整的 tag 与推送（注意 --follow-tags 只推 annotated tag）
git tag -a v1.4.0 -m "1.4.0: 新增 batchGet，重试改指数退避"
git push origin v1.4.0
git push --follow-tags

# 从 tag 构建镜像：tag 不可变，镜像 tag 也不该可变
docker build -t registry.example.com/api:1.4.0 .
docker tag registry.example.com/api:1.4.0 registry.example.com/api:sha-$(git rev-parse --short HEAD)

# 记录 digest，部署时用 digest 而不是 tag，彻底避免"同名不同物"
docker inspect --format='{{index .RepoDigests 0}}' registry.example.com/api:1.4.0

# 签名与验签（sigstore）
cosign sign registry.example.com/api@sha256:...
cosign verify registry.example.com/api@sha256:... \
  --certificate-identity=ci@example.com \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com
回滚最大的障碍从来不是代码，是数据。如果这次发布加了一个 NOT NULL 字段、改了字段含义、删了一列，旧版本代码读新库就会直接崩。做法是 expand-contract（扩展—收缩）：第一次发布只加新字段并双写，代码兼容新旧两种读法；等新版本稳定后，再单独发一次清理旧字段。这样任何一次发布都可以安全回滚。
模块 7

破坏性变更：怎么删东西才不挨骂

破坏性变更不可避免，问题从来不是"能不能删"，而是有没有给使用者留出迁移的时间和工具。

手段适用做法与代价
编译期弃用标记库、SDKJava 的 @Deprecated、Rust 的 #[deprecated]、Go 的 // Deprecated: 注释。让调用方在构建时就看见警告，成本最低
运行期响应头HTTP API返回 Deprecation 与 Sunset 头，声明废弃时间和下线时间。客户端可以自动告警
双写 / 双读存储结构变更新旧字段同时写，读时优先新、回退旧。稳定后再停旧字段。代价是写放大和一段"两套真相"的时期
适配层 / 兼容 shim接口重构旧接口保留，内部转调新实现。可以让使用者零改动，但你要维护两份契约
自动化迁移工具语法级改动提供 codemod 脚本（jscodeshift、gofmt rewrite、ESLint --fix），把"改代码"从几小时压到几分钟

给使用者多少时间

没有统一答案，但可以按使用者的升级成本分档。原则是：影响面越大、升级越难，给的窗口越长。

对象建议窗口依据
内部服务、同一团队1~2 个迭代可以直接改代码，沟通成本低
公司内跨团队的基础库至少 1 个季度要排期、要回归测试
公开 SDK / 开源库至少 6 个月，且跨越至少一个 MINOR使用者可能半年才升一次依赖
公开 HTTP API12 个月以上客户端可能装在用户设备上，无法强制升级
# 迁移指南的最小结构（MIGRATION.md）
## 1.x → 2.0

### 必改项
| 旧写法 | 新写法 | 说明 |
|---|---|---|
| client.get(k) | client.fetch(k) | 返回值从 string 改为 Buffer |
| retry: 3 | retry: {times: 3} | 支持指数退避配置 |

### 可自动迁移
npx @org/codemod v1-to-v2 ./src

### 时间表
- 2.0.0-rc.1  2026-09-01  开始征集反馈
- 2.0.0       2026-10-01  正式发布，1.x 进入维护
- 1.9.x       2027-04-01  停止修复（仅安全补丁）
- 1.x EOL     2027-10-01  完全停止支持

### 回滚方式
2.0 未改动数据格式，可直接降级到 1.9.x
一条经验法则：弃用（Deprecated）和移除（Removed）必须分两次发布。在 MINOR 版本里标记废弃并保留实现，至少一个 MINOR 周期后在 MAJOR 里删除。跳过"标记"直接删，等于把迁移成本全部转嫁给使用者——这也是很多库被替换掉的真实原因。
模块 8

内部版本与对外版本：别让 latest 上生产

对外版本回答"这个 API 兼容不兼容"，内部版本回答"这份制品到底是哪次提交构建的"。两者要能双向追溯，但承担的功能不同。

标识例子作用
语义化版本1.4.2兼容性承诺，给人看，用于依赖解析
构建号build.1847CI 流水线自增编号，定位"第几次构建"
git shaa3f9c21精确指向源码提交，唯一可信的追溯锚点
构建时间20261017T1423Z排查"这个镜像是不是昨天的"
组合写法1.4.2+build.1847.sha.a3f9c21SemVer 的构建元数据位，不参与比较，只做标注

镜像 tag 规范

tag可变？用途
1.4.2不可变发布制品，生产环境只认这个
sha-a3f9c21不可变每次提交构建，用于测试环境和问题复现
1.4可变跟随 1.4.x 的最新补丁，方便"取最新修复"，不适合生产固定
1可变跟随 1.x 最新，仅用于尝鲜
latest可变默认 tag。禁止用于生产部署
# 一次构建打多个 tag，各司其职
SHA=$(git rev-parse --short HEAD)
docker build \
  -t registry.example.com/api:1.4.2 \
  -t registry.example.com/api:1.4 \
  -t registry.example.com/api:sha-$SHA \
  -t registry.example.com/api:latest .

# 部署时用 digest 锁定，连 tag 被覆盖都不怕
kubectl set image deploy/api api=registry.example.com/api@sha256:9f2c...

# 反查：这个正在跑的容器到底是哪个提交
docker inspect --format='{{index .Config.Labels "org.opencontainers.image.revision"}}' <container>
为什么 latest 不能上生产，四个具体理由：
① 它可变。同一个名字，今天指向 1.4.2，明天指向 1.5.0，你的部署清单没有任何变化，行为却变了。
② 缓存会骗你。节点上已有 latest 时，docker pull 可能不会真正拉新层，导致集群里跑着三个不同版本。
③ 回滚无参照。出事时你说"回滚到上一个 latest"，但上一个 latest 是什么？没人知道。
④ 审计断链。安全扫描报告说"latest 有高危漏洞"，你无法回答"我们线上跑的是不是这个"。
常见坑

十个发布事故

1
package.json 改了版本号，但忘了打 tag
代码里的版本和制品对不上，出问题时无法从版本号定位提交。用 CI 校验：tag 名必须等于包里的版本号，不一致就构建失败。
2
覆盖已发布版本的制品
修了个小问题，直接重新构建同名 1.4.2 推上去。结果两台机器上的 1.4.2 内容不同，锁文件的完整性哈希全部失效。任何改动都必须发新 PATCH 版本。
3
生产用 latest 或浮动 tag 部署
发布不可复现、回滚无参照、审计断链。生产只用不可变 tag 或 digest。
4
在 MINOR 里偷偷删了公开 API
下游按 SemVer 信任你，自动升级后编译失败。破坏性变更必须走 MAJOR，并提前在 MINOR 里标记废弃。
5
对 0.x 依赖用了 ^
以为 ^ 只升补丁，实际 0.2 → 0.3 就是一次破坏性变更。0.x 依赖应锁精确版本，升级走人工 review。
6
锁文件没提交，或 CI 用 npm install
每次构建解析出的依赖树都可能不同，"昨天能构建今天不能"就是这么来的。锁文件入库，CI 用 npm ci / --frozen-lockfile。
7
changelog 直接贴 commit 列表
"chore: bump deps""fix typo"对使用者毫无信息量。自动生成只能当草稿，必须人工改写为"影响 + 迁移方式"。
8
发布和数据库迁移绑在同一次上线
迁移不可逆，代码想回滚也回不去。用 expand-contract 拆成两次发布，保证任意时刻都能回退。
9
灰度只看错误率，不看业务指标
错误率 0%、延迟正常，但下单成功率掉了 3%——这是最典型的"技术指标正常、业务已经出事"。灰度必须带业务指标比对。
10
回滚预案只写在文档里，从没演练过
真出事时才发现旧镜像已被清理、旧版本读不了新表结构、配置项不兼容。回滚要像发布一样定期演练。
自测

六道题

1. 一个库删除了一个公开函数，按 SemVer 应该升哪个位？
正确答案：MAJOR。删除公开 API 属于不向下兼容的变更，调用方必须改代码。哪怕只删了一个函数，也必须发大版本。
2. 下面哪个版本号最大？
正确答案：1.0.0-rc.1。预发布段按 ASCII 字典序比较，rc 大于 beta。注意 beta.11 也大于 beta.2，因为数字段按数值比较，不是字符串比较。
3. ^0.2.3 在 npm 里等价于哪个区间？
正确答案：>=0.2.3 <0.3.0。0.x 阶段 MINOR 被当作破坏位，所以 caret 只允许 PATCH 升级。而 ^0.0.3 更严格，等价于锁死 0.0.3。
4. 为什么锁文件必须提交到仓库？
正确答案：固定整棵依赖树。范围允许"任意满足条件的版本"，每次解析结果可能不同；锁文件记录精确版本 + 完整性哈希，配合 npm ci 才能保证今天和半年后构建出同样的东西。
5. 关于预发布版本，哪个说法正确？
正确答案：永远小于正式版，且默认不匹配。这是保护机制，避免生产环境装到半成品。要用预发布必须显式写 ^1.1.0-rc.1。
6. 一次发布加了不可逆的数据库字段变更，最大的问题是？
正确答案：回滚失效。代码可以回退，数据不会。正确做法是 expand-contract：先加新字段双写、代码兼容双读，稳定后再单独发一次清理旧字段。

术语表

术语一句话解释
SemVer语义化版本，MAJOR.MINOR.PATCH 三段表达兼容性承诺
MAJOR主版本号，不兼容变更时 +1
MINOR次版本号，向下兼容的新功能时 +1
PATCH修订号，向下兼容的修复时 +1
预发布标识连字符后的部分，如 -rc.1，优先级低于正式版
构建元数据加号后的部分，如 +sha.abc，不参与版本比较
版本范围描述"允许哪些版本"的表达式，如 ^1.2.3
锁文件记录整棵依赖树精确版本与哈希的文件，保证可重现
传递依赖依赖的依赖，你不直接声明但会被安装
菱形依赖两个依赖要求同一个包的不同版本，形成冲突
peer dependency对等依赖，要求宿主环境提供，插件常用
MVS最小版本选择，Go 的依赖解析策略，取满足要求的最低版本
annotated tag带作者、时间、说明的 Git tag，发布必须用这种
Conventional Commits用 feat/fix/BREAKING CHANGE 等前缀规范提交信息
Keep a Changelog变更日志格式约定，固定六个分类
灰度发布按比例逐步放量，观察指标后再扩大范围
expand-contract先扩展（加新字段双写）再收缩（删旧字段），保证可回滚
制品 digest镜像内容的哈希，比 tag 更可靠的身份标识
EOLEnd of Life，停止支持，不再发补丁
下一步怎么练：拿一个你自己的小项目，完成这五件事 —— ① 按 SemVer 补一个 CHANGELOG，把最近三次发布按六个分类写清楚；② 给项目加 CI 校验：tag 名必须等于包内版本号；③ 写一份 MIGRATION.md，挑一个你最近改过的接口做迁移对照表；④ 把镜像 tag 从 latest 改成"版本号 + sha"，并在部署清单里改用 digest；⑤ 设计一次 expand-contract 的字段变更，写清两次发布的顺序和回滚步骤。
