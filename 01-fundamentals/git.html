准备与阅读姿势

模块 1

三个区：Git 的全部秘密

几乎所有"Git 到底怎么工作的"困惑，都源于不知道有三个区。记住这张图，后面全通。

  工作区                暂存区                本地仓库            远程仓库
 Working Dir    →     Staging Area    →     Repository    →     Remote
（你正在编辑的文件）  （准备提交的快照）   （.git 里的历史）  （GitHub 等）

         git add          git commit        git push
       ←───────         ←────────         ←────────
       git restore       git restore --staged    git fetch
区域通俗说法说明
工作区你眼前的文件夹实际编辑文件的地方。改了但没 add，改动只存在这里
暂存区购物车决定"这次提交要包含哪些改动"。可以只提交部分文件，甚至文件的部分行
本地仓库你的存档点每次 commit 在这里留下一个不可变的快照。断网也能提交
远程仓库团队共享的存档点GitHub / GitLab / Gitee。push 上去别人才能看到
为什么要有暂存区？因为它让你能把一次改动拆成多个干净的提交。你改了三个文件、修了两个 bug，可以分两次提交，历史清晰。没有暂存区，你只能一次性全提交。
模块 2

分支只是一个指针

这是最值得花五分钟的地方。Git 的分支不是文件夹的拷贝，只是一个 41 字节的文件，里面存着一个 commit 的哈希值。

提交历史（每个圆圈是一次 commit，箭头指向父提交）

        A ←─ B ←─ C ←─ D
                        ↑
                      main        ← main 就是一个指向 D 的指针

创建分支 new 后：

        A ←─ B ←─ C ←─ D
                        ↑    ↑
                      main   new   ← 两个指针指向同一个 commit，零拷贝

在 new 上提交一次：

        A ←─ B ←─ C ←─ D ←─ E
                        ↑    ↑
                      main   new

切回 main 再提交一次：

        A ←─ B ←─ C ←─ D ←─ E
                        ↓    ↑
                        F    new
                        ↑
                      main
由此推出的三个重要结论：
① 创建分支几乎零成本（就是一个文件），所以 Git 鼓励你随便建分支。SVN 建分支要拷贝整个目录，所以没人愿意建。
② 切换分支就是换一个指针，然后让工作区的内容变成那个指针指向的快照。
③ 删除分支只是删掉一个指针，commit 本身还在（除非没有别的指针指向它，才会被垃圾回收）。

HEAD：你现在站在哪

# HEAD 是一个特殊的指针，通常指向某个分支，表示"你当前在哪"
HEAD → main → D

# 切分支就是把 HEAD 指向另一个分支
git switch new        # HEAD → new → D

# 直接 checkout 某个 commit，HEAD 就"脱离"了分支，这叫 detached HEAD
git checkout a1b2c3d  # HEAD → a1b2c3d（不再指向任何分支）
Detached HEAD 是新手翻车高发区。在这个状态下提交的 commit 不属于任何分支，一旦你切走，它们就没有指针指向了 —— 表面上"消失了"（其实还能用 reflog 找回来）。
想在上面干活，先建个分支：git switch -c 新分支名

commit 到底是什么

很多人以为 commit 存的是"这次改了什么"（diff）。不是。每个 commit 存的是整个项目的一个完整快照，外加：

  • 指向父 commit 的指针（可以有 0 个、1 个、2 个或多个）
  • 作者、提交者、时间
  • 提交信息
  • 一个由以上内容算出来的哈希值

所以 commit 是不可变的——改了内容哈希就变了，等于换了一个新 commit。这也解释了为什么 rebase 会"改写历史"：它实际上是在创建一批全新的 commit。

# 看一个 commit 的完整信息
git show a1b2c3d
git cat-file -p a1b2c3d    # 看原始对象内容
模块 3

日常五件套

看状态。git status —— 任何时候不确定，先敲它。它会告诉你哪些文件改了、哪些已暂存、当前在哪个分支。
看差异。git diff（工作区 vs 暂存区）、git diff --staged（暂存区 vs 上次提交）。提交前一定先看 diff，这是防止误提交的最后一道关。
暂存。git add 文件名 或 git add -p（交互式，逐块选择要暂存的改动，强烈推荐）。
提交。git commit -m "信息"。信息要写清楚"做了什么、为什么"。
推送。git push。第一次推新分支要 git push -u origin 分支名，-u 建立追踪关系，之后就能直接 push。
提交信息的规范（团队协作必备）：推荐 Conventional Commits —— feat: 新功能、fix: 修 bug、docs: 文档、refactor: 重构、test: 测试、chore: 杂项。
例：fix: 修复订单金额计算时未处理优惠券的问题。好处是可以自动生成 changelog，也方便 review 时快速判断改动性质。
模块 4

分支操作与冲突解决

# 查看分支
git branch                 # 本地分支，带 * 的是当前分支
git branch -a              # 含远程分支
git branch -vv             # 显示每个分支追踪的远程分支和领先/落后数

# 创建与切换
git switch -c feature/login      # 创建并切换（推荐，语义清晰）
git switch main                  # 切换
git checkout -b feature/login    # 老写法，等价

# 合并：把 feature 合进当前分支
git switch main
git merge feature/login

# 删除分支
git branch -d feature/login      # 已合并才能删
git branch -D feature/login      # 强制删（未合并也删，谨慎）

冲突是什么，怎么解

冲突的本质：两个分支修改了同一个文件的同一处，Git 不知道你想保留哪个。注意——改同一个文件不同位置不会冲突，改同一行才会。

<<<<<<< HEAD          ← 当前分支的内容（ours）
当前分支的代码
=======
要合并进来的分支的代码
>>>>>>> feature/login  ← 对方分支的内容（theirs）
打开冲突文件，搜索 <<<<<<< 找到冲突位置。
手工改成你想要的最终内容，把三行标记（<<<<<<<、=======、>>>>>>>）全部删掉。
暂存并提交：git add 冲突文件 然后 git commit。
想放弃这次合并：git merge --abort，回到合并前的状态。
实用技巧：用 git mergetool 或 VS Code 的冲突解决界面，比手改文本直观得多。
想先看看会冲突吗：git merge --no-commit --no-ff 分支名 然后 git merge --abort，空跑一次。
模块 5

merge 还是 rebase

这是团队协作里最常争论的问题。结论先给：本地整理用 rebase，公共分支用 merge。永远不要 rebase 已经推送到远程、别人可能拉取过的分支。

对比mergerebase
做了什么新建一个合并提交，有两个父提交把你的提交一个个"搬到"目标分支的最新位置
历史形状分叉后合并，保留真实时间线一条直线，看起来像顺序开发的
commit 哈希不变全部改变（因为父提交变了）
安全性安全，不改写历史改写历史，会影响别人的仓库
适用公共分支、已推送的分支自己的本地分支，提交前整理
# 典型场景：本地分支落后于 main，想同步最新代码
git switch feature/login
git rebase main            # 把我的提交搬到 main 最新提交之上

# 如果 rebase 过程中有冲突
# 解决冲突 → git add 文件 → git rebase --continue
# 想放弃 → git rebase --abort

# 交互式 rebase：整理本地提交（合并、改信息、删掉、排序）
git rebase -i HEAD~3       # 处理最近 3 个提交
# 交互式 rebase 打开后，每行前面可以改成：
pick    # 保留
reword  # 保留但改提交信息
squash  # 合并到上一个提交，信息也合并
fixup   # 合并到上一个提交，丢弃自己的信息
drop    # 删掉这个提交
黄金法则：不要 rebase 已经推送、且别人可能基于它工作的分支。你改写了历史，别人拉下来会产生重复提交和一堆诡异冲突。
只 rebase 自己的本地分支，或者团队明确约定过的分支。
一个很实用的替代方案：同步主分支时用 git merge main（不 rebase），等你这个功能分支准备合并前，再 git rebase -i 把中间那些"改一下""修个 typo"的碎提交压成一个干净的提交。这样既有安全的历史，又有整洁的最终提交。
模块 6

暂存与清理

# stash：临时把手头的改动收起来，去处理别的事
git stash                    # 收起所有已追踪文件的改动
git stash -u                 # 连未追踪的新文件一起收
git stash list               # 看有哪些暂存
git stash pop                # 恢复最近一个，并从列表移除
git stash apply stash@{1}    # 恢复指定的，但保留在列表里
git stash drop               # 删掉最近一个
git stash -m "调试到一半"     # 带说明，多个 stash 时很有用

典型场景：你在 feature 分支写到一半，突然要去 main 上修个紧急 bug。git stash → 切分支 → 修完 → 切回来 → git stash pop。

# clean：删除未追踪的文件（危险，先 dry-run）
git clean -n                 # -n 是 dry run，只列出要删什么，不真删
git clean -f                 # 删未追踪文件
git clean -fd                # 连未追踪目录一起删
git clean -fd 删掉的东西找不回来（它们从未被 Git 追踪，reflog 也救不了）。永远先跑 -n 看一眼。
模块 7

撤销与救火：本篇最重要的一节

先记住一句话：只要 commit 过，几乎什么都能救回来。真正救不回来的只有"从未 commit 过就被删掉的文件"。

场景一：改了文件，还没 add，想放弃改动

git restore 文件名            # 把工作区文件恢复到上次提交的状态（改动会丢）
git restore .                # 所有文件
git checkout -- 文件名        # 老写法，等价

场景二：add 了，想取消暂存（保留改动）

git restore --staged 文件名
git reset HEAD 文件名         # 老写法，等价

场景三：commit 了，但提交信息写错 / 漏了文件

git commit --amend -m "新信息"     # 修改最近一次提交
git add 漏掉的文件
git commit --amend --no-edit       # 把漏的文件补进上次提交，不改信息
注意：amend 会生成新的哈希值。如果那个提交已经推送到远程，amend 后需要 force push，而 force push 会影响别人。所以 只 amend 还没推送的提交。

场景四：想撤销某个提交 —— reset 的三种模式

这是最容易搞混的地方，用一张表说清。git reset --模式 目标commit，意思是"把当前分支指针移到目标 commit"：

模式HEAD 指针暂存区 / 工作区
--soft移动都不动。撤销的改动全部留在暂存区，可以直接重新 commit
--mixed移动暂存区重置，工作区不动。改动保留但变成"未暂存"（默认模式）
--hard移动两个都重置。改动彻底消失（但通常还能用 reflog 找回）
git reset --soft HEAD~1      # 撤销最近一次提交，改动回到暂存区 ← 最常用
git reset HEAD~1             # 等价于 --mixed，改动回到工作区
git reset --hard HEAD~1      # 彻底丢弃最近一次提交的所有改动 ← 危险
git reset --hard origin/main # 把本地强行对齐远程（丢弃本地所有差异）

场景五：已推送的提交要撤销 —— 用 revert

git revert a1b2c3d           # 生成一个"反向提交"，抵消那次改动
git revert HEAD~1            # 撤销倒数第二个提交
reset 和 revert 怎么选？
reset：改写历史，删掉那些提交。适合还没推送的本地提交。
revert：不改历史，新增一个反向提交。适合已推送、别人可能已经拉取的提交。
团队协作中，撤销公共分支上的提交一律用 revert。

场景六：终极保命 —— reflog

reflog 记录了 HEAD 在你本地仓库走过的每一步。误 reset、误 rebase、误删分支、detached HEAD 丢了提交 —— 它几乎都能救回来。

git reflog                   # 看 HEAD 的移动历史，每行有哈希值
# 找到你想回到的那一步，然后：
git reset --hard a1b2c3d     # 回到那个状态
# 或者把丢失的提交捞成一个新分支：
git branch rescue a1b2c3d
reflog 的两个限制：① 只存在于本地，远程仓库没有，换台机器就没了；② 默认只保留约 90 天（不可达对象 30 天）。
所以：出事了别慌，先敲 git reflog。这是每个 Git 使用者都该刻进肌肉记忆的第一反应。
模块 8

远程协作

# 关联远程仓库
git remote add origin git@github.com:user/repo.git
git remote -v                # 查看已配置的远程

# 拉取：fetch 和 pull 的区别很关键
git fetch origin             # 只下载远程更新到本地，不改你的工作区（安全）
git pull origin main         # = fetch + merge，直接合并到当前分支
git pull --rebase            # = fetch + rebase，历史更干净

# 推送
git push -u origin feature/x # 首次推送并建立追踪
git push                     # 之后直接推
git push --force-with-lease  # 比 --force 安全：别人推过新东西就拒绝
养成习惯：先 fetch 看一眼，再决定 merge 还是 rebase。git pull 一上来就自动合并，冲突起来你会很被动。
推荐流程：git fetch → git log HEAD..origin/main --oneline（看远程多了什么）→ 再决定怎么合。
永远不要用 git push --force，改用 --force-with-lease。前者会无条件覆盖远程，别人的提交直接消失；后者会先检查远程有没有你不知道的新提交，有就拒绝推送。这一个参数的差别，可能就是一个同事一下午的工作。

PR / MR 流程

从最新 main 建分支。git switch main && git pull && git switch -c feature/xxx
小步提交。一个提交做一件事，信息写清楚。别攒一个几千行的巨型提交。
推送并开 PR（Pull Request，GitLab 里叫 MR / 合并请求 —— 就是"请求把我的分支合进主干"，也是代码评审的载体）。描述里写清楚：改了什么、为什么改、怎么验证、有没有影响面。
根据 review 意见继续提交（不用 amend 已推送的提交，直接加新提交，评审记录更清晰）。
合并前把 main 的最新改动同步进来（merge 或 rebase，看团队约定），确保能干净合并、CI 通过。
合并后删掉分支（本地和远程都删），保持仓库干净。
模块 9

团队分支策略

策略做法适合
Git Flow长期存在 main / develop 两条主干，外加 feature / release / hotfix 分支有明确版本发布节奏的产品（如客户端软件）
GitHub Flowmain 始终可部署，所有改动走短分支 + PR绝大多数互联网团队，推荐
Trunk-based所有人直接往主干提交，分支存活不超过一天，靠功能开关控制灰度CI/CD 极其成熟、测试覆盖高的团队
给大多数团队的建议：GitHub Flow。main 永远可发布，功能分支存活时间尽量短（一两天），靠 PR 做代码评审，合并后立即部署。Git Flow 对大多数互联网产品来说太重了。

.gitignore 与几个容易忽略的文件

# .gitignore —— 只对"未追踪"的文件生效
node_modules/
.venv/
__pycache__/
*.log
.env
.DS_Store
dist/
build/
最常见的困惑：把已追踪的文件加进 .gitignore，为什么还生效？因为 .gitignore 只管未追踪的文件。要让已追踪的文件停止被追踪：
git rm --cached 文件名（保留本地文件，只从 Git 移除），然后提交。

另外两个值得知道的文件：.gitattributes（控制换行符、二进制文件处理）、.gitkeep（Git 不追踪空目录，放个空文件占位）。

模块 10

进阶：五个能救命的命令

1. bisect —— 二分查找"哪个提交引入了 bug"

git bisect start
git bisect bad                # 当前版本有问题
git bisect good v1.0          # 这个版本是好的
# Git 会自动切到中间版本，你测试后标记 good 或 bad，直到定位到罪魁祸首
git bisect reset              # 结束后回到原状态
# 有自动化测试的话，可以直接 git bisect run ./test.sh 全自动完成

几百个提交里找 bug，手工会累死，bisect 只需 log₂(n) 次。

2. cherry-pick —— 把某个提交搬到别的分支

git cherry-pick a1b2c3d       # 把那个提交的改动应用到当前分支
git cherry-pick a1b2c3d..e5f6g7h   # 一段区间

典型场景：在 main 上修了个 bug，想让发布分支也带上这个修复，但不想合并 main 的其他改动。

3. blame —— 看每一行是谁、哪次提交改的

git blame 文件名
git log -L 10,20:文件名        # 看这 10 行到 20 行的修改历史（更好用）
git log --follow -p 文件名      # 追踪文件重命名前的历史

4. 找丢失的东西

git fsck --lost-found         # 找出所有悬空对象
git log --all --oneline --graph  # 看所有分支的完整历史，可能就看到了"丢了"的提交
git log -S "某段代码"           # 搜哪次提交引入或删除了这段代码（pickaxe）

5. 让 log 变好看

git log --oneline --graph --all --decorate
# 建议配个别名（一次性配置，永久生效）
git config --global alias.lg "log --oneline --graph --all --decorate"
# 之后 git lg 即可
模块 11

十个致命坑

1
git push --force 覆盖了同事的提交
别人的工作直接消失。永远用 --force-with-lease，它会检查远程有没有你不知道的新提交。
2
rebase 了已推送的公共分支
所有人的本地历史都和远程对不上，拉取时产生大量重复提交和诡异冲突。黄金法则：只 rebase 自己的本地分支。
3
git reset --hard 之后才发现丢东西了
别慌，先 git reflog。绝大多数情况都能救回来。真正救不回的是从未 commit 过的文件。
4
在 detached HEAD 上提交
提交不属于任何分支，切走就"消失"了。要么先 git switch -c 分支名，要么用 reflog 找回。
5
提交了密钥、密码、大文件
一旦推送，历史里就永久存在（就算删掉文件，旧提交里还在）。必须用 git filter-repo 重写历史并立刻轮换密钥。预防靠 .gitignore + 提交前检查 diff。
6
把 .gitignore 当成"删除已追踪文件"的工具
它只对未追踪文件生效。要停止追踪已提交的文件，用 git rm --cached。
7
攒一个几千行的巨型提交
没法 review、没法定位问题、冲突起来极痛苦。小步提交，一个提交做一件事。
8
直接 git pull 不看远程有什么
一上来就自动合并，冲突时很被动。先 git fetch 看一眼远程的改动，再决定 merge 还是 rebase。
9
提交时把不该提交的文件带上
比如 node_modules、.env、本地配置。提交前养成 git status + git diff --staged 的习惯，这是最后一道关。
10
误删了未提交的改动
这是唯一真正救不回来的情况。所以重要改动要频繁提交（哪怕是临时提交），或者先 git stash 保底。
自测

六道题

1. Git 的分支本质上是什么？
正确答案：一个指向 commit 的指针。所以创建分支几乎零成本（就一个 41 字节的文件），这也是 Git 鼓励随便建分支的原因。
2. 想把最近一次提交撤销，但改动要保留在暂存区，用哪个？
正确答案：--soft。它只移动分支指针，暂存区和工作区都不动，改动全留在暂存区。--mixed（默认）会把改动退回工作区，--hard 会彻底丢弃。
3. 一个已经推送到远程、别人可能已拉取的提交要撤销，应该用？
正确答案：revert。它生成一个反向提交来抵消改动，历史是往前走的，别人拉取不会出问题。reset 和 amend 都会改写历史，在公共分支上会害到别人。
4. 误操作把分支搞乱了，第一个该敲的命令是？
正确答案：git reflog。它记录了 HEAD 在你本地的每一步移动，误 reset、误 rebase、误删分支基本都能靠它找回。注意它只在本地、默认保留约 90 天。
5. 一个文件已经被提交过了，现在想让它停止被 Git 追踪但保留本地文件，怎么做？
正确答案：git rm --cached。.gitignore 只对未追踪的文件生效，对已追踪文件无效。--cached 表示只从 Git 索引移除，本地文件保留。
6. 想在自己的本地功能分支上整理提交历史，把几个碎提交压成一个，应该用？
正确答案：git rebase -i。交互式 rebase 正是为"整理本地提交"设计的。黄金法则是：只 rebase 自己本地、未共享的分支。
