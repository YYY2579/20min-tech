先明确一件事：Markdown 不是排版工具。它没有"页边距""字号""行距"这些概念，最终长什么样由渲染器决定——GitHub、VS Code 预览、VitePress、飞书导入，同一个文件能渲染出四种样子。想让 Markdown 精确控制样式，是在跟工具的定位对抗。要精确排版，用 Word、LaTeX 或 HTML + CSS。
模块 1

Markdown 的定位：可读的纯文本

Markdown 的设计目标只有一个：让源文件在没渲染的时候也能读。所有语法都是围绕这个目标做的妥协。

它是什么它不是什么
纯文本，任何编辑器都能打开，能进 Git不是 WYSIWYG（所见即所得）编辑器
用最少的符号表达结构（标题、列表、代码、链接）不是排版系统，没有精确的字体、间距、分页控制
可被程序解析，能转成 HTML、PDF、幻灯片不是标准化的单一格式，方言很多
适合写文档、笔记、说明、变更记录不适合写需要复杂表格、图文混排、封面页的正式出版物

这个定位带来一个直接推论：内容结构比样式重要。标题层级表达的是文档大纲，不是"这行字要大一点"；列表表达的是并列或步骤关系，不是"这行要缩进"。一旦把 Markdown 当样式工具用，换一个渲染器就全乱。

什么时候不该用 Markdown：需要精确分页的合同与标书、需要复杂表格合并单元格的报表、需要嵌入大量图表编号与交叉引用的论文、需要多人实时协作并留痕的会议纪要。这些场景用 Word、LaTeX 或在线文档更合适，硬套 Markdown 只会浪费时间。
模块 2

语法要点：五个必踩的坑

坑一：标题层级

# 一级标题（整篇只应有一个）
## 二级标题
### 三级标题

# ✗ 错误：跳级
# 一级
#### 四级        # 中间跳过了二、三级，大纲会断

# ✗ 错误：# 后面没有空格
##没有空格的标题   # 多数解析器不认，会当成普通文本

# ✗ 错误：用标题代替加粗
#### 注意          # 这只是"字大一点"，但破坏了文档大纲

标题的唯一职责是构建大纲。渲染器会用它生成侧边栏目录、锚点链接、PDF 书签。跳级会让目录结构错乱；用标题代替强调，会让目录里塞满"注意""说明""总结"这种无意义条目。

坑四：表格的对齐与限制

# 冒号决定对齐：左、居中、右
| 参数 | 类型 | 默认值 |
|:-----|:----:|------:|
| retry | int | 3 |
| timeout | int | 3000 |

# 表格里不能直接换行，用 <br> 强制断行
| 字段 | 说明 |
|------|------|
| status | 200 成功<br>4xx 客户端错误<br>5xx 服务端错误 |

# 单元格里出现竖线要转义，否则会被当成列分隔符
| 表达式 | 含义 |
|--------|------|
| a \|\| b | 逻辑或 |

表格是 Markdown 里最脆弱的部分。它不支持合并单元格、不支持多行段落、不支持嵌套列表。一旦发现需要这些，说明这段内容不该用表格——改用小标题加列表，或者干脆拆成两段说明。

# 引用式：适合同一 URL 多次出现，或 URL 很长
部署流程见 [部署手册][deploy]，回滚见 [回滚手册][deploy]。

[deploy]: https://example.com/docs/deploy "部署手册"

# ✗ 反例：alt 写成"图片"或留空

模块 3

渲染差异：CommonMark 与 GFM

Markdown 最初由 John Gruber 发明，语法描述相当宽松，各家实现互不兼容。后来出现了两份事实标准：CommonMark（严格规范，带完整测试用例）和 GFM（GitHub Flavored Markdown，在 CommonMark 基础上加扩展）。

特性CommonMarkGFM / 常见扩展
标题、列表、代码块、链接支持支持，行为基本一致
表格不支持支持（GitHub、GitLab、多数静态站点）
任务列表 - [ ]不支持支持，渲染成可勾选复选框
删除线 ~~text~~不支持支持
裸 URL 自动成链接不自动自动（GFM autolink）
脚注 [^1]不支持GitHub 支持，其他渲染器不一定
内嵌 HTML允许GitHub 会过滤危险标签，很多平台直接禁用
数学公式 $...$不支持GitHub、部分静态站点支持，需要 KaTeX 插件
警告块 > [!NOTE]不支持GitHub 支持，其他平台多不支持

换行规则：最容易被误解的一条

# 源文件里这样写（一个换行）
第一行
第二行

# 渲染结果：多数渲染器会合并成一段，中间只有一个空格
# 也就是说，"回车"不等于"换行"

# 想真正换行，两种写法：
# 1) 行尾加两个空格（hard break，肉眼看不见，极易被编辑器删掉）
第一行··
第二行

# 2) 行尾加反斜杠（更明显，推荐）
第一行\
第二行

# 3) 空一行，另起一段（最推荐，语义清晰）
第一行

第二行
为什么这条特别坑中文写作者：中文习惯"一段话里手动折行"，而在 Markdown 里这样做，渲染后会被拼回一行，看起来像"空格丢了"或者"排版乱了"。正确做法是一段写成一整行，不手动折行，让渲染器自己去折。这也让 diff 更干净——改一个字不会牵动整段。

方言差异带来的实际问题

  • 同一个文件在 GitHub 好看，导进公司 wiki 就散架。因为 wiki 可能不支持表格或 HTML。团队要约定"最小语法子集"：标题、列表、代码块、链接、粗体，这五样几乎所有渲染器都支持。
  • HTML 是逃生舱，但不可移植。用 <br>、<details> 能解决排版问题，但很多平台（尤其是文档站的安全策略）会直接过滤掉。
  • 预览和发布不一致。VS Code 的预览用 markdown-it，GitHub 用自己的实现，静态站点又是一套。所以要在目标平台上验证，不能只看编辑器预览。
模块 4

技术文档的四种类型

写文档最常见的错误不是"写得不好"，而是用错类型——在 README 里长篇论述架构决策，在 Runbook 里讲设计理念。四种文档回答四个完全不同的问题。

类型回答的问题读者更新频率
README这是什么？怎么在 5 分钟内跑起来？新使用者、新同事随功能变，高频
设计文档为什么这么设计？有哪些取舍？边界在哪？评审人、后续维护者设计期密集，定稿后冻结
ADR当时在什么约束下，做了什么决策，代价是什么？半年后的自己、新加入的人只增不改，一条一决策
Runbook出事了第一步做什么？怎么判断？怎么回滚？凌晨三点被叫起来的值班人随系统变，需定期演练

README：五行之内让人跑起来

# 项目名

一句话说明它解决什么问题（不要写"这是一个基于 XX 的 YY 系统"）。

## 快速开始

```bash
git clone https://example.com/repo.git
cd repo
cp .env.example .env
docker compose up -d
```

打开 http://localhost:8080，用 `admin` / `admin` 登录。

## 它解决什么问题

- 场景 A：……
- 场景 B：……

## 文档

- [架构说明](docs/architecture.md)
- [部署手册](docs/deploy.md)
- [常见问题](docs/faq.md)

## 开发

```bash
make test      # 跑单元测试
make lint      # 代码检查
```

## 许可证

MIT

README 的判据：一个没接触过项目的人，能不能在 5 分钟内把它跑起来。不能，就说明 README 不合格。常见毛病是开头先写三百字背景介绍，把"怎么装"埋到最后。

设计文档：把取舍写清楚，而不是把结论写清楚

# 订单超时关闭 —— 设计文档

## 背景
订单创建后 30 分钟未支付需自动关闭。当前靠定时任务每 5 分钟扫一次全表，
数据量到 2000 万后单次扫描超过 4 分钟，已经影响到主库。

## 目标与非目标
目标：关闭延迟控制在 1 分钟内；不增加主库读压力。
非目标：不改动支付回调逻辑；不引入新的存储组件。

## 方案对比
| 方案 | 延迟 | 成本 | 风险 |
|------|------|------|------|
| 扫表 | 5 分钟 | 低 | 主库压力大，已不可行 |
| 延迟消息队列 | 秒级 | 中 | 需要保证消息不丢 |
| Redis ZSet 轮询 | 秒级 | 低 | 需要处理 Redis 故障时的补偿 |

## 选型
选延迟消息队列。理由是可靠性由 MQ 保证，补偿逻辑简单；
Redis 方案在故障时需要额外的对账任务，长期维护成本更高。

## 边界与失败处理
- 消息重复投递：关闭操作做幂等，按 order_id 加唯一约束
- 消息丢失：每天凌晨跑一次对账，补关超过 1 小时未关闭的订单
- MQ 不可用：降级为每 10 分钟扫一次，只扫"应关闭未关闭"的索引

## 影响面
订单服务、MQ 集群、监控（新增关闭延迟指标）

ADR：一条决策一个文件，只增不改

# docs/adr/0007-use-postgresql-for-orders.md

# 7. 订单库选用 PostgreSQL

- 状态：已接受
- 日期：2026-09-20
- 决策者：订单组、DBA

## 背景
订单表需要强事务、行级锁、JSONB 存扩展字段，且团队已有 PG 运维经验。

## 决策
订单主库使用 PostgreSQL 16，不使用 MySQL。

## 后果
- 正面：支持 JSONB 索引，省掉一张扩展表；事务隔离级别满足需求
- 负面：团队现有的 MySQL 备份脚本需要重写；分库分表中间件选型受限
- 风险：PG 的连接数模型与 MySQL 不同，连接池配置需要重新压测

## 备选方案
- MySQL 8：生态更熟，但 JSON 查询能力弱，需要额外扩展表
- TiDB：水平扩展好，但当前数据量用不上，运维复杂度偏高

ADR 的价值在"记录当时的约束"。半年后有人问"为什么不用 MySQL"，答案不是"PG 更好"，而是"当时团队有 PG 经验、需要 JSONB 索引、数据量用不上分布式"。ADR 不改写历史——决策变了就新写一条，状态标为"取代 0007"。

Runbook：写给凌晨三点、神志不清的自己

# Runbook：订单接口 5xx 升高

## 症状
告警 `OrderApi5xxRateHigh`：5 分钟内 5xx 比率 > 2%。

## 影响
用户无法下单。影响面看大盘"下单成功率"，低于 95% 视为严重。

## 第一步：判断范围（2 分钟内完成）
```bash
kubectl get pods -n prod -l app=order-api
kubectl top pods -n prod -l app=order-api
```

- 只有 1 个 pod 异常 → 跳到"单实例故障"
- 全部 pod 异常 → 跳到"依赖故障"

## 单实例故障
```bash
kubectl describe pod <pod> -n prod | tail -30
kubectl logs <pod> -n prod --previous --tail=200
```
若是 OOMKilled：`kubectl delete pod <pod>` 让它重建，然后继续观察 5 分钟。

## 依赖故障
```bash
kubectl exec -it <pod> -n prod -- curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://inventory:8080/health
```
若 inventory 超时，联系基础架构组（值班电话见置顶），同时开启降级开关：
```bash
kubectl set env deploy/order-api FEATURE_INVENTORY_CHECK=off -n prod
```

## 回滚
```bash
kubectl rollout undo deploy/order-api -n prod
kubectl rollout status deploy/order-api -n prod
```

## 验证恢复
下单成功率回到 99% 以上，5xx 比率低于 0.1%，持续 10 分钟。

## 事后
在 incident 频道记录时间线，24 小时内补 RCA。
Runbook 的三条铁律：① 命令必须可以直接复制执行，不要写"进入容器后检查一下网络"；② 每一步都要有判断分支，不能只有一条顺路；③ 必须定期演练。一份从没被执行过的 Runbook，大概率在真出事时第一步就卡住——比如权限不够、命令参数已经过期。
模块 5

图表与公式：什么时候该画

文字擅长表达"是什么"和"为什么"，图擅长表达结构、时序、状态流转。判断标准很简单：如果这段话里有三个以上的"然后""同时""如果"，就该画图。

图类型适合表达不适合
流程图 flowchart判断分支、处理步骤精确的时序与并发
时序图 sequence多角色按时间顺序交互、请求链路复杂的状态机
状态图 state订单状态、连接状态等有限状态机线性流程
ER 图 erDiagram表结构与关系查询逻辑
架构图组件与依赖关系时序（画成箭头会误导）
# 流程图：支付回调的处理分支

# 时序图：一次下单经过哪些服务
```mermaid
sequenceDiagram
    participant C as 客户端
    participant O as order-api
    participant I as inventory
    participant P as pay
    C->>O: POST /api/orders
    O->>I: 预占库存
```

Mermaid 的最大好处是"图也是文本"：能进 Git、能 review diff、不会像截图那样过期。代价是布局由渲染器自动决定，复杂图会排得很丑。超过 15 个节点就该拆图，而不是继续加。

公式

# 行内公式：用单个美元符号
缓存命中率 $h = \frac{N_{hit}}{N_{total}}$ 直接决定回源压力。

# 块级公式：独立成段
$$
P99 = \text{sort}(latencies)[\lceil 0.99 \times n \rceil]
$$

# 注意：下划线在数学模式和强调语法之间会打架
# 变量名尽量用单个字母，或用 \text{} 包住多字母
$\text{hit\_rate} = \frac{hits}{total}$
公式和图表都依赖渲染器支持。GitHub 支持 Mermaid 和 $...$ 数学；VitePress、Docusaurus 需要装插件（如 markdown-it-mathjax3、remark-math + rehype-katex）；很多公司内网 wiki 两者都不支持。发布前一定要在目标平台确认，否则读者看到的是一堆源码。
模块 6

文档即代码：放进仓库，跟着一起评审

文档腐化的根本原因不是"没人写"，而是文档和代码分居两地。代码改了，文档在另一个系统里，没有任何机制提醒你同步。

做法效果
文档放在仓库的 docs/ 目录和代码同一个版本、同一个分支，checkout 下来就是配套的
文档变更走同一个 PR改接口的 PR 必须同时改文档，reviewer 能看到两边
PR 模板加一条检查项"是否影响文档？"强制作者想一次
CI 跑 markdownlint + 链接检查格式和死链在合并前就被拦住
发布时归档文档版本v1 的文档跟着 v1 的代码，用户查旧版不会看到新 API

怎么防止文档过期

  • 能自动生成的不要手写。API 文档从代码注释或 OpenAPI 描述生成；配置项从 schema 生成表格。手写的部分越少，腐化越慢。
  • 代码示例要能被测试。把文档里的命令抽成脚本，CI 里跑一遍。跑不通就说明文档过期了。
  • 少用截图。截图三个月后必然对不上 UI，而且无法被搜索、无法 diff、体积还大。能用文字或 Mermaid 就别截图。
  • 给文档加"最后验证时间"。不是装饰，是让读者知道这份内容可能有多旧。超过半年的 Runbook 应该重新演练一次。
一个反直觉的建议：删掉过期的文档，比补写新文档更重要。错误的信息比没有信息更危险——读者会照着做，然后踩坑。文档评审时应该明确问一句："这份文档里有哪些内容已经不再成立？"
模块 7

写作原则：先给结论，再给理由

技术文档的读者不是来欣赏文笔的，是来解决问题的。所以他们最关心的是"我该做什么"，其次才是"为什么"。

先给结论。第一段就说清"这份文档解决什么问题、你需要做什么"。不要用"随着业务的发展……"开头，那是把结论埋在第三屏。
短句子，一句话一个意思。超过 40 字的中文句子，读者要回读。把"由于该服务在初始化阶段需要加载大量配置且这些配置来自远端，因此在网络异常时会导致启动失败"拆成三句。
给可运行的例子。"配置一下超时时间"没用，"在 config.yaml 里设置 timeout: 3s"才有用。示例要能复制粘贴就跑。
删掉废话。"众所周知""显而易见""简单来说""需要注意的是"——这些词不提供信息，只增加阅读成本。尤其是"简单"，它会让卡住的人觉得自己很笨。
用具体数字代替形容词。"性能很好"→"P99 延迟 45ms"；"数据量很大"→"单表 2000 万行"；"尽快处理"→"5 分钟内"。
明确边界。写清"这个方案不解决什么""什么情况下不要用"。只讲优点的文档，读者无法判断该不该用。
别这么写改成
本服务具有较高的可用性单实例故障时自动切换，实测切换耗时 8 秒
请合理配置连接池连接池设为 max=20，超过数据库 max_connections 的 1/4 会引发排队
需要注意的是，删除操作不可恢复删除后数据保留 7 天，可在控制台"回收站"恢复
支持多种部署方式支持 Docker Compose 与 Kubernetes Helm 两种部署方式，见下文
如遇问题请联系管理员在 #oncall-order 频道 @order-oncall，15 分钟内响应
关于"中文排版"的两点：① 中英文之间加空格、数字与中文之间加空格，是排版习惯而非 Markdown 规范，但能显著提升可读性；② 标点用全角，代码和命令里的标点必须是半角——混用会导致复制出来的命令直接报错，这是技术文档里最实际的坑。

# 一个能直接用的 CI 检查（GitHub Actions）
name: docs
on: [pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npx markdownlint-cli2 "**/*.md" "#node_modules"
      - name: Check links
        uses: lycheeverse/lychee-action@v1
        with:
          args: --no-progress --max-concurrency 8 "./**/*.md"
规则管什么建议
MD001标题层级只能逐级递增必须开，直接关系大纲结构
MD013单行最大长度（默认 80）中文文档建议关掉，80 字符对中文太短
MD033禁止内联 HTML按平台定。需要 <br> 就关掉
MD040代码块必须指定语言必须开，影响高亮和可读性
MD041文件第一行必须是一级标题建议开，保证每篇文档有明确主题
MD024同级标题不能重名建议开，否则锚点链接会指向错误位置
工具链的正确心态：格式问题交给机器，人只负责"内容对不对、结构清不清楚"。如果 code review 里还在讨论"这里该不该空行"，说明 lint 没配好，浪费的是最贵的注意力。
常见坑

十个写作坑

1
以为回车就是换行
CommonMark 里单个换行是软换行，渲染后会被拼成一段。要换行用空行分段，或行尾加反斜杠。
2
用标题代替加粗来强调
标题会进目录、生成锚点。用四级标题写"注意"，目录里就全是"注意"。强调用 **粗体**。
3
代码块不写语言
没有高亮，读者要自己猜是 bash 还是输出，也没法按语言检索。至少写 text。
4
列表嵌套缩进不对
只缩进一格会被当成同一层，缩进过多会变成代码块。与父项内容对齐，通常是 2 或 4 个空格。
5
表格里塞长段落
表格不支持换行和段落，只能靠 <br> 硬断，而且很多渲染器会过滤 HTML。内容太长就改成小标题加列表。
6
图片不留 alt 文本
读屏软件读不出来，图片加载失败时读者也不知道丢了什么。alt 要写"这张图表达了什么"，不是"图片"。
7
用截图代替文字说明
截图不能搜索、不能 diff、UI 一改就过期，体积还大。能用文字或 Mermaid 就别截图。
8
文档和代码分居两个系统
代码改了没人提醒你改文档，半年后文档全是错的。文档放仓库，跟着 PR 一起评审。
9
README 先写三百字背景，安装步骤在最后
读者的目标是在 5 分钟内跑起来。第一屏就放"这是什么 + 怎么装 + 怎么验证"。
10
命令里混用全角标点
从文档复制出来的命令带全角引号或全角空格，粘到终端直接报错，而且极难看出原因。
自测

六道题

1. Markdown 源文件里写了两行文字，中间只有一个换行，多数渲染器会怎么显示？
正确答案：合并成一段。单个换行是软换行（soft break）。要真正换行，用空行分段，或行尾加两个空格 / 反斜杠。
2. 下面哪个特性是 GFM 有、CommonMark 没有的？
正确答案：表格与任务列表。CommonMark 只定义核心语法，表格、删除线、任务列表、裸 URL 自动链接都是 GFM 的扩展。
3. 想记录"为什么当时选了 PostgreSQL 而不是 MySQL"，应该写哪种文档？
正确答案：ADR。它记录的是决策上下文、备选方案和后果，而且只增不改。README 讲怎么用，Runbook 讲出事怎么办。
4. Runbook 最重要的写作要求是？
正确答案：可执行、有分支、演练过。Runbook 的读者是凌晨三点被叫起来的人，不能有"检查一下网络"这种无法执行的步骤。
5. 文档腐化最有效的根治手段是？
正确答案：文档即代码。同仓库、同 PR、同版本，加上 CI 检查和自动生成，才能让文档和代码同步演进。靠运动式检查一定会反弹。
6. 表格单元格里需要换行，正确做法是？
正确答案：用 <br>。Markdown 表格不支持多行，回车会直接破坏表格结构。但更稳妥的做法是：内容需要多行时，说明它不该用表格表达。

文档骨架速查

# README 的最小结构
项目名 → 一句话定位 → 快速开始（可复制的命令）→ 解决什么问题
→ 文档索引 → 开发命令 → 许可证

# 设计文档的最小结构
背景（为什么现在要做）→ 目标与非目标 → 方案对比（表格）
→ 选型理由 → 边界与失败处理 → 影响面

# ADR 的最小结构
编号 + 标题 → 状态（提议/已接受/已取代）→ 日期 → 背景
→ 决策 → 后果（正面/负面/风险）→ 备选方案

# Runbook 的最小结构
症状（对应哪条告警）→ 影响（怎么判断严重程度）→ 第一步（判断范围）
→ 分支处置（命令可直接复制）→ 回滚 → 验证恢复 → 事后动作
