开始前

建一个可以随便搞坏的仓库

这篇里的命令都会改写历史。在真实仓库里练容易出事，先建一个沙盒。

# 建沙盒
mkdir /tmp/git-lab && cd /tmp/git-lab
git init -b main
git config user.name "You"
git config user.email "you@example.com"

# 造几个提交
for i in 1 2 3 4 5; do
  echo "line $i" >> file.txt
  git add file.txt && git commit -m "chore: commit $i"
done

# 看清历史（单行 + 图形）
git log --oneline --graph --all

# 记下当前 HEAD，搞坏了随时回来
git tag backup HEAD

# 恢复：git reset --hard backup
最重要的一条安全习惯：动手改历史之前先打 tag。
git tag backup HEAD 只占几字节，但它让"搞坏了"从灾难变成一个 reset --hard。
另外：git reflog 会保留 90 天内的 HEAD 移动记录，几乎所有"提交丢了"的事故都能靠它找回。先学会 reflog，再学 rebase。
模块 1

三种工作流，选错了天天打架

模型分支结构适用条件代价
Git Flowmain + develop + feature/* + release/* + hotfix/*有明确版本发布节奏、需要同时维护多个线上版本（如客户端、私有化部署）分支太多、合并路径复杂；持续交付团队用它是灾难
GitHub Flowmain + 短生命周期 feature 分支 + PRWeb 服务、能随时发布、有基本 CI要求 main 始终可发布；回滚靠 revert 而不是切分支
Trunk-based几乎只有 main，分支存活 < 1 天团队成熟、CI 快（< 10 分钟）、有 feature flag 能力对工程能力要求最高；没有 flag 系统会直接崩

为什么大多数团队该用 GitHub Flow

  • 发布频率决定流程。一天发几次的团队，develop 分支只会变成一个"延迟合并的缓冲区"，代码在里面等着，冲突在里面堆积
  • release 分支的价值在"同时维护多个版本"。如果你的线上永远只有最新版，release 分支就是纯负担
  • hotfix 分支在 GitHub Flow 里是多余的。main 就是生产状态，修 bug 就是从 main 拉分支、提 PR、合并、发布，不需要单独的 hotfix 通道
  • Git Flow 的作者本人在 2020 年给原文加了注：如果是持续交付的 Web 应用，建议改用更简单的工作流
你的情况建议
Web 服务，一天多次发布GitHub Flow，或向 trunk-based 演进
客户端 / 私有化部署，要维护 3 个版本Git Flow 的 release + hotfix 分支确实有用
单体仓库，几十人协作trunk-based + feature flag，否则合并地狱
外包交付、按里程碑验收Git Flow 的仪式感反而是优点，便于对账
流程的复杂度必须匹配发布能力。没有自动化测试、没有灰度、没有快速回滚，却硬上 trunk-based，结果是主干长期处于半坏状态，所有人都被阻塞。
反过来，一天发十次却用 Git Flow，你会花大量时间在合并 develop 和 release。先看发布能力，再选流程。
模块 2

rebase：从 -i 到 --onto

先明确 rebase 到底做了什么

# 你的分支 feature 从 main 的 C2 分出来，之后 main 前进到 C4
#
#       C3---C4  main
#      /
#  C1-C2
#      \
#       F1---F2  feature

git switch feature
git rebase main

# 结果：F1 F2 被"复制"到 C4 之后，feature 指向新的提交
#
#  C1-C2-C3-C4
#            \
#             F1'---F2'  feature

# 关键点：F1' 和 F1 内容相同但 SHA 不同，是全新的提交
# 所以：rebase 之后必须 force push，而且别人基于旧 F1 的工作会失效
rebase 的黄金法则：不要 rebase 已经推送到共享分支的提交。
因为 rebase 会生成新 SHA，别人拉取后会出现"同一份改动有两个提交"，合并时冲突翻倍。
例外情况：你自己的 feature 分支（只有你在推），随便 rebase。判断标准是"有没有别人基于这个分支工作"，不是"有没有 push 过"。

交互式 rebase：整理提交的万能工具

# 整理最近 3 个提交
git rebase -i HEAD~3

# 编辑器里会打开这样的列表（顺序是从旧到新）
pick a1b2c3d feat: 加用户列表接口
pick e4f5g6h fix typo
pick i7j8k9l 改了点东西

# 可用的指令
# pick   = 保留
# reword = 保留但改提交信息
# edit   = 停下来让你修改这个提交的内容
# squash = 合并到前一个提交，保留两条信息
# fixup  = 合并到前一个提交，丢弃本条信息
# drop   = 删除这个提交
# exec   = 执行一条 shell 命令（可用来逐提交跑测试）
# break  = 在这里暂停
场景操作
三个提交其实是一个功能后两个改成 fixup 或 squash
提交信息写错了改成 reword
想拆开一个大提交改成 edit，停下来后 git reset HEAD~ 重新分批 add
某个提交不该有drop，或直接删掉那一行
调整提交顺序直接调换行的位置（可能冲突）
每个提交都要能编译在第一个提交后加 exec npm test

--autosquash 配合 fixup!：最实用的组合

# 场景：你提交了 3 个 commit，review 时发现第 1 个有 bug

# 1. 直接改代码，然后生成一个"待合并"的提交
git add .
git commit --fixup=a1b2c3d
# 提交信息自动变成 "fixup! feat: 加用户列表接口"

# 2. 继续改，继续 fixup
git commit --fixup=a1b2c3d

# 3. 推送前一次性整理（不需要手动编辑 todo 列表）
git rebase -i --autosquash main

# 打开编辑器时，fixup 提交已经被自动排到目标提交后面并标为 fixup
# 直接保存退出即可

# 4. 让 autosquash 成为默认行为
git config --global rebase.autosquash true
这个工作流的价值：review 期间不用小心翼翼地 amend（会打断别人的 review diff），可以放心地"打补丁"，最后一次性折叠成干净的历史。
--fixup=amend:<sha> 还能同时更新提交信息，--fixup=reword:<sha> 只改信息不改内容（Git 2.32+）。

--onto：把一段提交搬到别处

# 语法：git rebase --onto 新基底 旧基底 要移动的分支
# 含义：把 "旧基底..分支" 之间的提交，重新接到 "新基底" 上

# 典型场景一：分支从错误的地方拉出来了
# 你以为从 main 拉的，实际从 feature-a 拉的
git rebase --onto main feature-a my-feature

# 典型场景二：只把最后 3 个提交搬到 release 分支
git rebase --onto release main~3 my-feature

# 典型场景三：从一条长分支里摘出某个功能
# 结构：main - A - B - C - D (dev)
# 只想把 C 和 D 搬到 main 上
git rebase --onto main B dev

# 典型场景四：删掉中间某个提交
# main - C1 - C2 - C3 - C4，想删掉 C2
git rebase --onto C1 C2 main
参数含义
--onto <newbase>新的落点（这段提交要接在谁后面）
<upstream>旧基底的"排除点"，这个提交之后的才被移动
<branch>要移动的分支，省略则用当前 HEAD
记忆方法：--onto A B C 读作"把 B 之后、C 之前的提交，接到 A 上"。
画个图验证：git log --oneline --graph --all，确认 B..C 正是你想搬的那几个提交，再执行。先看清楚，再动手，比事后用 reflog 找回省事得多。

冲突处理与安全网

# 冲突时 rebase 会停下来，状态是 "interactive rebase in progress"
git status                    # 看哪些文件冲突
# 手工解决后
git add <file>
git rebase --continue

# 跳过这个提交（放弃它的改动）
git rebase --skip

# 完全放弃，回到 rebase 之前
git rebase --abort

# 让 git 记住你解决过的冲突，下次自动复用
git config --global rerere.enabled true

# 同时更新栈式分支（Git 2.38+），避免逐个 rebase
git rebase --update-refs main

# 强制推送的正确姿势：只在你确认远端没被别人改过时才成功
git push --force-with-lease
# 比 --force 安全：远端 HEAD 与你记录的不一致时直接拒绝

# 更严格：即使远端 ref 没变，也检查本地是否有未推送的改动
git push --force-with-lease --force-if-includes
--force-with-lease 不是万能的。它的判断依据是本地记录的远端 ref。
如果你刚执行过 git fetch，本地记录就是最新的——此时别人推了新提交，你仍然会覆盖掉它。正确顺序是：fetch → 看远端有没有新提交 → 再 force-with-lease，而不是无脑 fetch 后强推。
模块 3

分支管理：命名、生命周期、hotfix

命名规范

# 推荐格式：类型/工单号-简短描述
feat/USER-123-add-export
fix/ORDER-456-null-pointer
refactor/PAY-789-split-service
docs/readme-quickstart
chore/bump-node-20

# 反例（都在真实项目里见过）
test          # 完全看不出做什么
zhangsan      # 人名
fix           # 哪个 fix？
feature/new   # 太笼统
tmp-20240301  # 日期对别人没意义
前缀用途
feat/新功能
fix/bug 修复
hotfix/线上紧急修复（Git Flow 下从 main/tag 拉）
release/发布准备（只允许改版本号和修复阻塞问题）
refactor/不改变行为的重构
chore/构建、依赖、配置
docs/文档

分支的生命周期

创建：从最新的 main 拉。git switch -c feat/x origin/main，不要从本地过期的 main 拉。
开发：小步提交，随时 rebase main 保持同步。分支存活超过 3 天就该警惕，超过 1 周基本会有冲突。
提 PR：推送后开 PR，描述写清"改了什么、为什么、怎么验证"。CI 必须绿。
合并：按团队策略 squash 或 rebase merge，然后立刻删掉远端分支。
清理：git fetch --prune 清掉本地已删除的远端分支引用。
# 查看哪些分支已经合并进 main（可以安全删除）
git branch --merged main

# 删除本地分支（-d 会检查是否已合并，安全）
git branch -d feat/done

# 强制删除（没合并的，慎用）
git branch -D feat/abandoned

# 清理远端已删除分支的本地引用
git fetch --prune
# 或设为默认
git config --global fetch.prune true

hotfix 的正确流程

# Git Flow 下的 hotfix：从线上 tag 拉，修完同时合回 main 和 develop
git switch -c hotfix/ORDER-999 v1.4.2
# ... 修复 ...
git commit -am "fix: 订单金额精度丢失"

# 1. 合进 main 并打新 tag
git switch main
git merge --no-ff hotfix/ORDER-999
git tag -a v1.4.3 -m "hotfix: 金额精度"
git push origin main --tags

# 2. 合回 develop（这一步最容易忘！）
git switch develop
git merge --no-ff hotfix/ORDER-999

# 3. 删掉 hotfix 分支
git branch -d hotfix/ORDER-999
hotfix 最经典的事故：修了 main 忘了 develop。
下次从 develop 发版时，这个 bug 又回来了。而且因为已经"修过"，没人会再查一遍。
防御手段：① 用脚本或 CI 检查 hotfix 分支是否同时合并到了两条线；② 更彻底的做法是只保留一条长期分支（GitHub Flow），从根上消除这个问题。

merge 的三种方式

方式历史形态取舍
merge commit保留分支结构，多一个合并节点历史真实，但图会很乱
squash merge整个 PR 变成一个提交main 最干净，但丢失中间提交，bisect 粒度变粗
rebase merge每个提交线性接在 main 后，无合并节点历史线性且保留粒度，但要求分支先 rebase
# 团队常用配置：squash 为主，保留 PR 号
# GitHub 仓库设置里勾选 "Allow squash merging"
# 默认提交信息格式： "feat: 加导出功能 (#123)"

# 本地 squash 合并
git switch main
git merge --squash feat/export
git commit -m "feat: 加导出功能 (#123)"
模块 4

submodule 与 subtree

对比submodulesubtree
本质父仓库记录一个指向子仓库某次提交的指针（gitlink，mode 160000）子仓库的文件和历史被复制进父仓库的某个子目录
元数据.gitmodules + 索引里的 gitlink无额外元数据，就是一个普通目录
克隆需要 --recurse-submodules 或事后 init普通 clone 即可，无感
版本锁定精确锁定到某个 commit，不会漂移锁的是内容快照，语义上没那么清晰
上手成本高，一堆人卡在 detached HEAD低，但对父仓库贡献者透明
仓库体积小，只存指针大，子项目历史全进父仓库
适合第三方依赖、需要独立发布的组件想"内嵌"且不想让同事学新命令

submodule 的完整操作

# 添加
git submodule add https://github.com/org/lib.git vendor/lib
git commit -m "chore: 引入 lib 子模块"

# 克隆带子模块（推荐，一步到位）
git clone --recurse-submodules https://github.com/org/app.git

# 已经克隆了，补初始化
git submodule update --init --recursive

# 更新到 .gitmodules 里配置的分支的最新版
git submodule update --remote vendor/lib

# 在所有子模块里执行命令
git submodule foreach 'git status --short'

# 查看子模块状态
git submodule status

# 移除（三步，缺一不可）
git submodule deinit -f vendor/lib
git rm -f vendor/lib
rm -rf .git/modules/vendor/lib

三个必踩的坑

坑一：忘记初始化，目录是空的

# 现象：clone 下来 vendor/lib 是个空目录
ls vendor/lib            # 什么都没有
git submodule status     # 前面有个 - 号，表示未初始化

# 解法
git submodule update --init --recursive

# 一劳永逸：让 clone 默认带子模块
git config --global submodule.recurse true

坑二：detached HEAD，提交丢失

# submodule 默认 checkout 到某个 commit，而不是分支
cd vendor/lib
git status
# HEAD detached at a1b2c3d

# 你以为在改代码，提交了 —— 但没有任何分支指向这个提交
# 父仓库 push 之后，下次别人 update 会重新 checkout 到旧 commit
# 你的提交就"消失"了（其实还在 reflog 里，但没人找得到）

# 正确做法：先切到分支再改
cd vendor/lib
git switch main
git pull
# ... 修改、提交、推送 ...
cd ../..
git add vendor/lib       # 父仓库记录新的 commit 指针
git commit -m "chore: 升级 lib 到最新"

坑三：版本漂移，没人知道用的是哪个版本

# 父仓库只记录了一个 SHA，看不出对应哪个版本
git diff vendor/lib
# -Subproject commit a1b2c3d...
# +Subproject commit e4f5g6h...

# 想看清到底改了什么，得进子模块看
cd vendor/lib
git log --oneline a1b2c3d..e4f5g6h

# 防御：在 CI 里加检查，子模块指针变化时必须附带说明
# 或者用 git submodule status --recursive 输出到构建日志
submodule 的核心问题不是技术，是"心智负担"。
新人第一次遇到子模块，通常会在 detached HEAD 里提交代码，然后困惑"为什么我的改动不见了"。
如果团队里有人不熟悉 git，优先考虑 subtree 或直接用包管理器（npm / pip / go mod）。submodule 适合"必须锁定到精确 commit 且需要独立仓库"的场景，不是通用的代码复用手段。

subtree 的用法

# 添加：把子仓库拉到 vendor/lib，可选 --squash 压缩历史
git subtree add --prefix=vendor/lib https://github.com/org/lib.git main --squash

# 拉取上游更新
git subtree pull --prefix=vendor/lib https://github.com/org/lib.git main --squash

# 把本地修改推回上游（需要权限）
git subtree push --prefix=vendor/lib https://github.com/org/lib.git main

# 好处：clone 的人完全无感，就是普通目录
# 代价：--squash 后历史被压平；不 squash 会让父仓库体积暴涨
模块 5

hooks：把规则变成机器执行

hook 是 git 在特定动作前后调用的脚本。客户端 hook 在本地跑（可被跳过），服务端 hook 在仓库端跑（无法跳过）。

hook时机典型用途
pre-commit提交前lint、格式化、密钥扫描、禁止提交大文件
prepare-commit-msg打开编辑器前自动插入工单号、分支名
commit-msg信息写完后校验提交信息格式（Conventional Commits）
post-commit提交后通知、统计（不能阻断提交）
pre-push推送前跑单测、禁止推到 main
pre-rebaserebase 前禁止 rebase 已发布的分支
post-checkout / post-merge切分支 / 合并后自动装依赖、提示配置变更
pre-receive服务端收到推送强制校验，无法绕过
update服务端逐分支分支级权限、保护规则
post-receive服务端接收后触发部署、发通知

为什么 .git/hooks 里的脚本"传不出去"

# git 不会跟踪 .git/hooks 目录，所以写在里面的脚本
# 只对当前克隆有效，同事拉下来什么都没有

# 解法一：把 hooks 放进仓库，改 core.hooksPath 指过去
mkdir -p .githooks
cp .git/hooks/pre-commit.sample .githooks/pre-commit
chmod +x .githooks/pre-commit
git config core.hooksPath .githooks
# 注意：core.hooksPath 是本地配置，需要每个人自己执行一次
# 可以放进 bootstrap 脚本或 Makefile 的 setup 目标里

# 解法二：用框架管理（推荐）
# pre-commit（Python 生态，最通用）
pip install pre-commit
# .pre-commit-config.yaml 里声明规则，pre-commit install 写入 hook

# husky（Node 生态）
npx husky init

# lefthook（Go，快，语言无关）
lefthook install

两个最有价值的 hook

# .githooks/commit-msg —— 强制 Conventional Commits
#!/usr/bin/env bash
msg_file="$1"
pattern='^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\(.+\))?!?: .{1,72}$'

# 允许 merge / revert 提交跳过
if grep -qE '^(Merge|Revert)' "$msg_file"; then exit 0; fi

if ! head -1 "$msg_file" | grep -qE "$pattern"; then
  echo "✗ 提交信息不符合规范"
  echo "  格式: type(scope): subject"
  echo "  示例: feat(user): 加导出按钮"
  echo "  类型: feat fix docs style refactor perf test build ci chore revert"
  exit 1
fi
# .githooks/pre-push —— 禁止直接推 main
#!/usr/bin/env bash
branch="$(git rev-parse --abbrev-ref HEAD)"
if [ "$branch" = "main" ] || [ "$branch" = "master" ]; then
  echo "✗ 禁止直接推送到 $branch，请走 PR"
  exit 1
fi

# 也可以顺便跑快速测试
# npm test -- --bail || exit 1
客户端 hook 永远只是"防手滑"，不是"安全边界"。
git commit --no-verify 一行就能跳过所有客户端 hook。任何必须保证的规则（提交信息格式、不能删分支、必须过测试）都要在服务端或 CI 里再实现一遍。
分工：客户端 hook 追求快（秒级），给人即时反馈；CI 追求全（跑全量测试），做最终卡点。

CI 里的等价物

hook 想做的事CI 里的实现
pre-commit 的 lint单独的 lint job，失败则 PR 不可合并

模块 6

大仓库优化

当 git clone 要十几分钟、git status 要几秒，问题不在网络，在仓库结构。monorepo 尤其需要这套手段。

浅克隆：只要最近的提交

# 只要最近 1 个提交，体积可能从 2GB 降到 200MB
git clone --depth 1 https://github.com/org/big-repo.git

# 要最近 50 个提交
git clone --depth 50 ...

# 按时间浅克隆
git clone --shallow-since="2024-01-01" ...

# 事后加深
git fetch --deepen 100
git fetch --unshallow          # 补全所有历史（会很久）

# 局限：blame、log、bisect 只能看到浅层历史
# 适合：CI 构建、只读部署，不适合日常开发

partial clone：不要 blob，用时再取

# 只拉提交和树对象，文件内容按需下载
git clone --filter=blob:none https://github.com/org/big-repo.git

# 更激进：连树对象都不要（Git 2.36+）
git clone --filter=tree:0 ...

# 排除大文件类型
git clone --filter=blob:limit=1m ...

# 好处：clone 快、磁盘占用小，checkout 时才拉需要的文件
# 代价：首次切分支或看老文件时会有网络延迟
# 需要服务端支持（GitHub/GitLab 都支持）

sparse checkout：只要部分目录

# 1. 开启 cone 模式（推荐的目录级稀疏检出）
git sparse-checkout init --cone

# 2. 指定需要的目录
git sparse-checkout set services/payment libs/common

# 3. 查看当前范围
git sparse-checkout list

# 4. 加回全部
git sparse-checkout disable

# 组合使用：大 monorepo 的标准姿势
git clone --filter=blob:none --sparse https://github.com/org/mono.git
cd mono
git sparse-checkout set services/payment
手段解决什么代价
--depth历史太长看不到早期历史，blame 失效
--filter=blob:none文件太大太多需要网络，离线体验差
sparse-checkout目录太多，只关心一部分切分支时可能缺文件
commit-graphlog / merge-base 慢需要定期维护
fsmonitorstatus 慢（文件多）平台相关，行为偶有异常
# 后台维护：自动做 gc、commit-graph、prefetch
git maintenance start

# 手动生成 commit-graph，加速 log 和 merge-base
git commit-graph write --reachable

# 开启文件系统监视（macOS / Windows 支持较好）
git config core.fsmonitor true
git config core.untrackedCache true

# 看看是什么让仓库变大
git count-objects -vH
git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '/^blob/ {print $3, $4}' | sort -rn | head -20
不要用 --depth 1 做日常开发。浅克隆的仓库在 git log、git blame、git merge-base 上都会退化，rebase 时也可能因为缺少共同祖先而失败。
正确分工：CI 用 --depth 1，开发者用 --filter=blob:none（保留完整历史，只省文件内容）。
模块 7

历史重写：删掉不该提交的东西

有些东西一旦进了历史就永远在：密钥、几十 MB 的二进制、误提交的数据库转储。删掉当前文件不够，历史里还在。

什么时候该重写

情况要不要重写
密钥 / token 泄露要，但先轮换密钥。重写只是清理痕迹，不能撤回已泄露的事实
误提交大文件，仓库已经很大要，否则每次 clone 都要付这个代价
提交信息写错（最近的）要，用 rebase -i 或 commit --amend 就够
想删掉某人的提交记录不要，历史是审计依据，用 revert 表达"撤销"
仓库已经有很多 fork / 克隆慎重，重写会让所有 fork 失效

git filter-repo 的标准流程

# 安装（不要用已废弃的 git filter-branch）
pip install git-filter-repo

# 1. 先做一个全新克隆（不要在原仓库上操作）
git clone --no-local https://github.com/org/app.git app-clean
cd app-clean

# 2. 删掉某个文件的所有历史
git filter-repo --path config/secrets.env --invert-paths

# 3. 删掉整个目录
git filter-repo --path node_modules/ --invert-paths

# 4. 删掉超过 10MB 的文件
git filter-repo --strip-blobs-bigger-than 10M

# 5. 替换历史里的敏感字符串（保留文件，只改内容）
git filter-repo --replace-text expressions.txt
# expressions.txt 每行一条：
# ghp_xxxxxxxx==>***REMOVED***
# AKIAIOSFODNN7EXAMPLE==>***REMOVED***

# 6. 检查结果
git log --oneline | head
git count-objects -vH
filter-repo 会默认删掉 origin 远端，这是故意的安全设计——防止你手滑直接 push --force 覆盖掉所有人的仓库。
它的输出是不可逆的。操作前必须有完整备份，并且在全新克隆上做，不要在还有未推送提交的工作副本上做。

重写之后必须做的事

加回远端并强推所有分支和 tag：git remote add origin ...，然后 git push --force --all 和 git push --force --tags。
通知所有协作者重新克隆。这是最重要的一步——旧克隆里的历史和新历史没有共同祖先，直接 pull 会把旧提交全部合并回来，等于白做。
清理服务端缓存：GitHub 的旧提交在一定时间内仍可通过 SHA 直接访问，需要联系支持或等 GC。分支保护、PR 引用也要检查。
轮换所有被删掉的密钥。历史清理不等于密钥安全，爬虫早就在你推送的几秒内抓走了。
加防护：pre-commit 密钥扫描 + 服务端 push rule，避免下次再犯。
# 协作者的正确做法：不要 pull，重新克隆
mv app app-old          # 先留着备份
git clone https://github.com/org/app.git
# 把 app-old 里未推送的改动手工挑过来

# 如果非要复用旧克隆（不推荐）
git fetch origin
git reset --hard origin/main
# 这样会丢掉所有本地未推送提交

分支保护规则

规则作用
Require PR before merging禁止直接推 main
Require approvals ≥ 1至少一人 review；核心模块建议 2 人
Dismiss stale approvals有新提交时作废旧 approval，防止"批完又改"
Require status checksCI 必须绿；要指定具体 job，别只写"任意检查"
Require linear history禁止 merge commit，强制 squash 或 rebase
Require conversation resolution所有 review 评论必须解决
Include administrators管理员也不能绕过，否则规则形同虚设
Restrict force push / deletion防止误删 main 或强推覆盖历史
"Include administrators" 是最容易被跳过的一项。
不勾选的话，出问题时管理员会习惯性地"我直接推一下"，久而久之所有人都知道规则可以绕过。规则的价值在于没有例外——真需要紧急操作时，临时关闭保护、操作、再打开，这个动作本身会留下审计记录。

常见坑

十个踩过的坑

1
rebase 了别人也在用的分支
SHA 全变，别人 pull 后出现重复提交、冲突翻倍。只 rebase 自己的分支，共享分支用 merge。
2
用 --force 而不是 --force-with-lease
直接覆盖远端，可能把同事刚推的提交抹掉。用 --force-with-lease，并且 fetch 后先确认远端没新提交。
3
clone 后子模块目录是空的
忘了 --recurse-submodules。补执行 git submodule update --init --recursive，或设 submodule.recurse true。
4
在 submodule 的 detached HEAD 上提交
提交不属于任何分支，父仓库下次 update 会覆盖掉。改子模块前先 git switch main。
5
以为 .git/hooks 里的脚本会同步给同事
hooks 目录不进版本库。用 core.hooksPath 指向仓库内目录，或用 pre-commit / husky 框架。
6
把客户端 hook 当成安全边界
--no-verify 一行就跳过。必须保证的规则要在服务端或 CI 里实现。
7
日常开发用了 --depth 1
blame、log、merge-base 全部退化，rebase 可能找不到共同祖先。CI 才用浅克隆，开发用 --filter=blob:none。
8
在还有未推送提交的仓库上跑 filter-repo
未推送的提交会丢。必须在全新克隆上操作，操作前打 tag 或完整备份。
9
重写历史后让同事 pull
旧历史会作为合并基被重新拉回来，等于没清理。必须通知所有人重新克隆。
10
分支保护没勾 Include administrators
管理员随手直推 main，规则变成摆设。要么全约束，要么承认没有规则。
自测

六道题

1. rebase 之后为什么必须 force push？
正确答案：生成新 SHA。rebase 是把提交"复制"到新基底上，内容相同但父提交不同，SHA 必然不同。远端还是旧 SHA，普通 push 会被拒绝。
2. 想把 feature 分支上"B 之后"的提交搬到 main 上，命令是？
正确答案：--onto main B feature。读作"把 B 之后、feature 之前的提交，接到 main 上"。不加 --onto 时第一个参数是新基底，语义完全不同。
3. submodule 的父仓库记录的是什么？
正确答案：commit 指针（gitlink，mode 160000）。所以父仓库能精确锁定版本，但也因此 clone 时必须显式初始化，否则目录是空的。
4. 为什么 .git/hooks 里的脚本同事拉不到？
正确答案：.git 目录不进版本库。解法是把 hooks 放进仓库（如 .githooks），用 core.hooksPath 指过去，或用 pre-commit / husky 这类框架管理。
5. 大仓库里，开发者日常最合适的克隆方式是？
正确答案：--filter=blob:none。它保留完整提交历史（blame、log、merge-base 都正常），只按需下载文件内容。--depth 1 会让历史相关操作全部退化，适合 CI 不适合开发。
6. 用 filter-repo 删掉泄露的密钥后，第一步该做什么？
正确答案：轮换密钥。清理历史只是删掉痕迹，泄露已经发生——公开仓库几秒内就会被爬虫抓走。轮换之后再做历史重写和通知。
