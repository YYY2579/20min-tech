开始前

搭一个能跑的最小工程

后面的例子都基于这个三文件的小项目。先把它跑起来，再谈原理。

# 目录结构
demo/
├── Makefile
├── main.c
├── util.c
└── util.h

# 确认工具链（GNU Make 4.x 才支持 --trace 等特性）
make --version | head -1
cc --version | head -1

# 一条命令验证：改一个文件，看 make 只重编它
make
touch util.c
make
概念在这份工程里对应什么
输入main.c、util.c、util.h、编译器、编译参数
变换编译（.c → .o）、链接（.o → 可执行文件）
输出main.o、util.o、app
依赖图app 依赖两个 .o，两个 .o 依赖各自的 .c 和 util.h
Windows 上先别用系统自带的 make：如果 make --version 报的是 "GNU Make 3.81" 或者根本没有 make，说明你用的是很老的移植版或没装。建议在 WSL2 里做这章的练习 —— 后面讲的 tab 缩进、/bin/sh、路径分隔符，在原生 Windows 上行为都不一样，容易把工具的问题误判成自己的问题。
模块 1

构建的本质是一张依赖图

把构建工具的所有功能剥掉，剩下的模型只有三个元素：节点（文件）、边（依赖）、规则（怎么从依赖生成节点）。所有构建工具都在做同一件事：在这张图上求一个拓扑序，然后按序执行。

# 一张最小的依赖图

        util.h
        /    \
       v      v
   util.c    main.c
       \      /
        v    v
      util.o  main.o
          \   /
           v v
           app

# 拓扑序的一种合法结果：
util.h → util.c → util.o → main.c → main.o → app
# 注意：util.c 和 main.c 之间没有边，所以它们可以并行
要素在图里是什么工程含义
节点文件（源文件、目标文件、最终产物）也可能是"动作"，比如 clean 这种不对应文件的伪目标
边A 依赖 BB 变了，A 就可能需要重算
规则给定依赖，如何产出目标一条命令行，或一段插件代码
调度拓扑排序 + 并行度限制make -j8 就是"同时跑 8 个入度为 0 的节点"

为什么"图"这个视角重要

  • 增量构建：只有"输入变了"的节点及其下游需要重算。图告诉你下游是谁。
  • 并行：没有依赖关系的节点可以同时跑。图告诉你哪些能并行。
  • 缓存：一个节点的"输入指纹"相同，就能直接复用上次的输出，跳过执行。
  • 正确性：漏掉一条边，就会漏编译；多写一条边，就会过度编译。构建系统的 bug 绝大多数是图的边写错了。
三种构建系统的图，粒度不同：
Make 的节点是文件，边要你手写，粒度最细也最容易漏。
CMake 的节点是target（库、可执行文件），依赖通过 target_link_libraries 传递，比文件级抽象一层。
Bazel 的节点是rule 实例，依赖必须显式声明在 BUILD 文件里，构建过程在沙箱中执行，所以它能保证"没声明的依赖一定读不到"。粒度越粗，越不容易漏边，但灵活性越低。
模块 2

Makefile 的三个核心

Makefile 只有一种句式：目标 : 依赖，换行后跟一个 tab 再加命令。所有的复杂度都长在这个骨架上。

# 最小可用的 Makefile（注意：命令行开头必须是 TAB，不是空格）
CC      = cc
CFLAGS  = -O2 -Wall -Wextra
TARGET  = app
OBJS    = main.o util.o

$(TARGET): $(OBJS)
	$(CC) $(CFLAGS) -o $@ $^

%.o: %.c util.h
	$(CC) $(CFLAGS) -c -o $@ $<

.PHONY: clean
clean:
	rm -f $(OBJS) $(TARGET)

自动变量：不用手写文件名

变量含义例子
$@当前目标的文件名规则 app: ... 里是 app
$<第一个依赖模式规则里就是那个 .c 文件
$^所有依赖，去重，空格分隔链接时最常用
$+所有依赖，保留重复链接顺序敏感时用
$?所有比目标新的依赖只重新处理变化的部分
$*模式规则匹配到的"茎"%.o: %.c 里，main.o 的 $* 是 main
$(@D) / $(@F)目标的目录 / 文件名输出到 build/ 时有用

变量：四种赋值方式的区别很关键

写法求值时机什么时候用
=递归展开，用到时才求值值里引用了后面才定义的变量
:=立即展开，定义时就固定推荐默认用这个，行为可预测，也不会重复执行 $(shell ...)
?=未定义时才赋值允许外部用 make CC=clang 覆盖默认值
+=追加（保持原变量的展开方式）往 CFLAGS 里加选项
# 一个经典的坑：= 让 shell 命令被执行多次
NOW = $(shell date +%s)      # 每次引用都执行一次 date
NOW := $(shell date +%s)     # 只执行一次

# 常用函数
SRCS := $(wildcard src/*.c)                    # 通配符展开
OBJS := $(patsubst src/%.c,build/%.o,$(SRCS))  # 路径替换
DEPS := $(OBJS:.o=.d)                          # 后缀替换（更简洁）

# 条件判断
ifeq ($(DEBUG),1)
  CFLAGS += -g -O0
else
  CFLAGS += -O2
endif

为什么 .PHONY 必须写

假设目录里恰好有一个叫 clean 的文件（有人手滑 touch clean，或者某个脚本产出了同名文件）。此时 make clean 会认为"目标已存在且没有更新的依赖"，于是什么都不做，还返回成功。这是最阴险的一类 bug：CI 显示绿，但产物根本没清理。

# 声明伪目标后，make 会跳过"文件是否存在"的检查，永远执行
.PHONY: all clean test install

# 另一个作用：跳过隐式规则搜索，略微提速（大项目里能感觉到）

# 顺带一提：默认目标永远是第一个出现的规则
# 想显式指定就写：
.DEFAULT_GOAL := all
missing separator 这个报错 99% 是缩进问题。Make 要求命令行以真正的 tab 字符开头，四个空格不行。编辑器里把 tab 显示出来（Vim 的 :set list，VS Code 的 "Render Whitespace"），一眼就能看出来。
实在不想用 tab，GNU Make 3.82+ 支持 .RECIPEPREFIX = > 改成别的字符，但这会让你的 Makefile 不可移植（BSD make 不认），团队协作时别这么干。
模块 3

增量构建：为什么改了文件有时不重编

增量构建要回答一个问题：这个目标还算不算"新"？两种主流答案，代价完全不同。

策略判断依据代表工具
时间戳目标的 mtime 是否早于任一依赖Make、早期 CMake、多数脚本
内容哈希把所有输入（文件内容 + 命令行 + 环境）算一个指纹，比对指纹Bazel、Gradle、Cargo、Go、Bazel 系

时间戳的五个失效场景

场景后果
时钟回拨 / 多机时钟不同步源文件 mtime 比目标还新（或更旧），导致永远重编或永不重编
NFS / 虚拟机挂起挂载端和宿主端时间基准不一致，mtime 乱序
从压缩包解压、rsync 不带 -t文件 mtime 变成"现在"，所有目标都被判定为过期，全量重编
git checkout 切换分支git 会把 mtime 设为当前时间，即使内容没变，也会触发重编
只改了编译参数Make 完全不感知。改了 -O2 到 -O0，它认为目标比源文件新，不重编
# 复现第 5 条：改 CFLAGS 不会触发重编
make                          # 全量编译
# 编辑 Makefile，把 -O2 改成 -O0
make                          # 输出：make: 'app' is up to date.   ← 编译参数变了但没重编

# 正确做法：把参数写进一个 stamp 文件，让它成为依赖
FLAGS_STAMP := .build-flags
$(FLAGS_STAMP): Makefile
	@echo '$(CC) $(CFLAGS)' > $@.tmp
	@cmp -s $@.tmp $@ || mv $@.tmp $@
	@rm -f $@.tmp

# 然后让所有 .o 依赖这个 stamp
%.o: %.c $(FLAGS_STAMP)
	$(CC) $(CFLAGS) -c -o $@ $<

头文件依赖：Make 最经典的漏边

# 只写 %.o: %.c 是不够的。改了 util.h，main.o 不会重编
main.o: main.c              # 漏了 util.h

# 手工维护头文件依赖是灾难。让编译器自己生成：
CFLAGS += -MMD -MP
# -MMD：生成 .d 文件，列出该源文件包含的所有非系统头文件
# -MP：为每个头文件生成一个空的伪目标，避免头文件被删后报错

-include $(DEPS)          # 前面的减号：文件不存在也不报错

# 生成的 main.d 长这样：
# main.o: main.c util.h
# util.h:

调试：先看它打算做什么，再看它为什么这么想

make -n只打印将要执行的命令，不执行。改完 Makefile 先跑这个
make -d打印完整的决策过程（哪个目标被考虑、为什么重建）。输出极长，配合 grep
make -d 2>&1 | grep -A3 "must remake"直接定位"为什么重编"
make -p打印 Make 内部数据库：所有变量、规则、隐式规则
make -B无视时间戳，全部重做。用来验证"是不是增量判断出了问题"
make --traceGNU Make 4.0+：逐条打印"因为 X 比 Y 新，所以重建 Z"
半成品目标文件比不编译更危险。如果编译被 Ctrl-C 打断，或者磁盘写满，可能留下一个"比源文件新但不完整"的 .o。下次 make 认为它是最新的，直接链接，得到一个运行时才崩的二进制。
解法：在 Makefile 开头加 .DELETE_ON_ERROR:，命令失败时自动删掉目标文件。
模块 4

任务编排：并行、顺序、失败处理

图的拓扑序不唯一，这正是并行的空间。但并行会把"隐藏的依赖"变成"偶发的编译错误"，这是构建系统最典型的翻车方式。

# 并行：同时跑 N 个任务
make -j8              # 8 个并发
make -j$(nproc)        # 按 CPU 核数（Linux）
make -j$(sysctl -n hw.ncpu)   # macOS
make -j                # ⚠ 无限制并发，容易把机器打爆，别用

# 顺序依赖：只保证"先生成目录"，但目录变化不触发重建
build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c -o $@ $<

build:
	mkdir -p $@
# 竖线右边叫 order-only prerequisite（仅顺序依赖）
# 不加竖线的话，目录 mtime 一变，所有 .o 都会被判定过期

# 失败处理
make -k              # keep going：某个目标失败后继续做其他不相关的目标
make -i              # ignore errors：忽略所有命令的失败（危险，只用于清理）
make -j8 -k          # 组合：并行 + 尽量多收集错误

# 只跑某个目标
make clean all
make -C subdir        # 切到子目录执行
make -f other.mk      # 指定 Makefile

并行的收益与天花板

阶段能否并行说明
预处理 + 编译几乎线性每个 .c 独立，8 核接近 8 倍（受内存带宽限制，通常 6~7 倍）
链接通常串行最终链接只有一个任务，是阿姆达尔定律里的"串行部分"
代码生成取决于图protobuf、模板、IDL 生成的产物被大量目标依赖，容易成为瓶颈
测试可并行但要控制并发数，否则数据库连接、端口会打架
# 算一下理论上限（阿姆达尔定律）
# 总工作量 1000 秒，其中链接等串行部分 100 秒
# 8 核：100 + 900/8 = 212.5 秒 → 加速比 4.7x
# 32 核：100 + 900/32 = 128 秒 → 加速比 7.8x
# 结论：串行部分占 10%，再怎么加核也超不过 10x

# 内存是隐形天花板：每个 gcc 进程约 100~300MB
# 16 核全开可能吃掉 4GB，小内存 CI 机器会 OOM
make -j16 # 在 4GB 的 runner 上可能被 OOM Killer 干掉
递归 make 是并行的天敌。父 Makefile 里写 $(MAKE) -C sub，如果子目录之间其实有依赖（比如 B 要用 A 生成的库），-j 会让它们同时跑，出现"有时成功有时失败"的竞态。
三个应对：① 显式写出子目录之间的依赖；② 用 .NOTPARALLEL: 放弃并行（慢但正确）；③ 干脆换成非递归的构建系统（CMake 的 target、Bazel 的 package）。递归 make 的并行正确性，靠人肉维护，迟早出错。
模块 5

现代工具：各自解决什么问题

不要问"哪个最好"，要问"我的瓶颈是哪种"。下面这张表按适用场景和你为此付出的代价来排。

工具擅长代价
Make任意"文件 → 文件"的任务编排；C/C++ 小项目；运维脚本的入口（make deploy）依赖要手写，容易漏；不跨平台（tab、shell）；没有包管理
CMakeC/C++ 的事实标准。生成 Ninja / Makefile / Xcode 工程；跨平台；有 target 级的传递依赖DSL 复杂，PUBLIC/PRIVATE/INTERFACE 三个关键字劝退；配置阶段本身可能很慢
Bazel超大 monorepo、多语言；内容哈希 + 沙箱 + 远程缓存，正确性和速度都强学习曲线陡；BUILD 文件要手维护；生态偏 Java/C++/Go；小项目属于杀鸡用牛刀
GradleJVM 生态（Java/Kotlin/Android）；增量编译、构建缓存、配置缓存Groovy/Kotlin DSL 有学习成本；守护进程吃内存；构建脚本本身可能变成"代码项目"
npm scripts前端 / Node；几行 JSON 就能串联任务；生态无缝没有依赖图，只能顺序串；没有增量；跨平台 shell 行为不一致（Windows 的 rm 不存在）
Cargo / go build语言内置，零配置；锁文件 + 内容哈希，增量可靠只能构建本语言；定制化空间小

同一件事，五种写法

# 目标：编译 src/*.c，输出 build/app

# ---- Make ----
app: $(OBJS)
	$(CC) -o $@ $^

# ---- CMake ----
add_executable(app src/main.c src/util.c)
target_include_directories(app PRIVATE include)
target_link_libraries(app PRIVATE pthread)

# ---- Bazel ----
cc_binary(
    name = "app",
    srcs = ["src/main.c", "src/util.c"],
    deps = [":util"],
)

# ---- Gradle（JVM）----
plugins { id 'java' }
dependencies { implementation 'com.google.guava:guava:33.0.0-jre' }

# ---- npm scripts ----
"scripts": { "build": "tsc -p tsconfig.json" }
一个实用的判断顺序：
① 语言有官方工具（Go、Rust、Swift）→ 直接用官方的，别折腾。
② C/C++ → CMake + Ninja，几乎无争议。
③ JVM → Gradle（新项目）或 Maven（求稳）。
④ 前端 / Node → 包管理器 scripts + 一个任务编排器（Turborepo / Nx），别用裸 npm scripts 管几十个包。
⑤ 多语言 monorepo、构建时间以十分钟计 → 才考虑 Bazel。它的收益来自"大规模 + 远程缓存"，小项目只会收获复杂度。
模块 6

构建缓存：为什么 CI 上必须缓存依赖目录

缓存的本质是用空间换时间，用"输入指纹"换"输出复用"。指纹算错，就会拿到错误的产物 —— 这比慢更可怕。

层级典型实现命中率 / 收益
编译器缓存ccache、sccache重复编译同一文件时 80%~95% 命中，单文件从 2s 降到 0.1s
本地构建缓存Gradle build cache、Bazel 本地 disk cache切分支后复用未变模块的产物
远程构建缓存Bazel --remote_cache、Gradle remote cache、Turborepo remote cache整个团队 / CI 共享。新人第一次构建也能命中
依赖缓存npm / pip / Maven / Gradle 的本地仓库CI 上冷启动 3~5 分钟 → 热缓存 30~60 秒
# ---- ccache：最容易被忽略的一层 ----
export CC="ccache gcc"
ccache -s                  # 看命中率、缓存大小
ccache -C                  # 清空
# 默认缓存在 ~/.ccache，默认上限 5GB，建议调到 10~20GB
ccache -M 20G

# ccache 的指纹包括：预处理后的源码、编译器版本、编译参数、include 的文件
# 所以改注释不会失效（预处理后注释被去掉），改头文件会失效

# ---- GitHub Actions 缓存依赖目录 ----
- uses: actions/cache@v4
  with:
    path: |
      ~/.npm
      ~/.cache/pip
      ~/.gradle/caches
      ~/.gradle/wrapper
    key: deps-${{ runner.os }}-${{ hashFiles('**/package-lock.json', '**/requirements.txt') }}
    restore-keys: |
      deps-${{ runner.os }}-

# key 里必须包含锁文件的哈希。只写 deps-linux 会导致
# 依赖升级后仍然命中旧缓存，装出旧版本
缓存键（cache key）设计的三条铁律：
① 必须包含所有会影响输出的输入：锁文件哈希、编译器版本、关键环境变量、构建参数。少一项就可能"命中错误的缓存"。
② 不要缓存构建产物本身，除非你有内容哈希校验。缓存 node_modules 是常见的坏习惯：它和 lockfile 不同步时，你会得到一棵"看起来装好了"的依赖树。
③ 恢复键（restore-keys）只用于降级复用，命中后仍然要跑一次安装/校验命令，不能直接信任。

为什么远程缓存对 CI 的收益特别大

CI 的 runner 通常是一次性容器，每次从零开始。没有缓存时，每次构建都要重装依赖、重编所有代码。远程缓存把"上一次构建（可能是同事的机器、也可能是上一个 commit）的产物"直接搬过来，把"重算"变成"下载"。

场景无缓存有远程缓存
改一个前端组件重装依赖 3min + 全量构建 4min依赖命中 40s + 只重建受影响包 50s
改一行后端代码全量编译 8min只编译该模块 1min
只改 README仍然全量 8min几乎全部命中，30s
模块 7

可复现构建：同样的输入，同样的输出

可复现（reproducible build）的定义很严格：在相同输入下，任何人、任何时间、任何机器构建出的产物，逐字节相同。它不是为了洁癖，而是为了三件事：安全审计（能验证二进制确实来自这份源码）、缓存正确性（哈希相同才能复用）、故障复现。

四类不确定性来源

来源表现解法
时间__DATE__ / __TIME__ 宏、zip/jar 里的条目时间、日志里的构建时刻设 SOURCE_DATE_EPOCH，打包时固定 mtime
路径调试信息里嵌入绝对路径，不同人机器上不同-fdebug-prefix-map / -ffile-prefix-map
顺序文件遍历顺序、哈希表迭代顺序、并行输出拼接顺序显式排序（LC_ALL=C sort），不要依赖 readdir 顺序
环境编译器版本、glibc 版本、locale、时区、CPU 指令集固定工具链，在容器里构建
# ---- 1. 固定时间戳 ----
export SOURCE_DATE_EPOCH=1700000000

验证可复现性的方法很朴素：构建两次，比哈希。
make clean && make && sha256sum app，换个目录再来一次，两次哈希必须一致。不一致就用 diffoscope 逐层对比，它能告诉你差异具体在哪个字节、哪个段。
注意：只验证"同机两次"是不够的，真正要验证的是"不同路径 + 不同时间 + 不同机器"。所以最有效的做法是在 CI 里用一个干净的容器跑两次。

为什么"在容器里构建"几乎是必选项

  • 工具链固定：镜像里写死 gcc 13.2、glibc 2.35，不会因为同事升级了系统就变。
  • 路径固定：统一挂载到 /src，路径污染自然消失。
  • 环境变量干净：不会被本机的 CFLAGS、LANG、代理设置影响。
  • 可审计：镜像有 digest，能回答"这个二进制到底是用什么构建的"。
模块 8

构建慢，先测量再优化

"构建太慢"是一个症状，不是诊断。盲目加 -j、盲目上缓存，通常只能拿到 20% 的收益。真正的大头往往在别处。

先量出总时长和各阶段占比。在 CI 里给每一步打时间戳，或者本地用 time make -j8 加 --trace 的时间戳。典型分布：装依赖 40%、编译 45%、测试 10%、打包 5%。
找关键路径，不是找最慢的任务。总时长由最长的那条依赖链决定。一个 30 秒的代码生成任务如果被 200 个目标依赖，它就是关键路径；把它优化到 3 秒，收益远大于把 200 个 1 秒的编译任务优化到 0.9 秒。
先修正确性，再谈速度。如果增量构建本身就是错的（漏依赖、不感知参数变化），你优化出来的"快"是假的 —— 它只是"少做了该做的事"。
按收益排序动手：缓存依赖 > 并行 > 增量 > 拆分模块 > 换工具。换工具是最后一步，不是第一步。
手段典型收益代价 / 风险
缓存依赖目录3~5 分钟 → 30~60 秒缓存键设计错会装出旧依赖
-j$(nproc)编译阶段 4~7 倍内存不足会 OOM；隐藏依赖会暴露成竞态
ccache / sccache重复编译 5~20 倍首次无收益；缓存目录要持久化
拆模块只重编受影响部分需要清晰的依赖边界，前期设计成本高
换 Ninja比 Make 快 10%~30%（调度开销更小）要配合 CMake 生成，手写不现实
分布式 / 远程执行线性扩展基础设施复杂，只在超大项目上划算

# GNU Make 4.0+：每条命令的起止时间，能画出时间线

不要用"减少正确性"换速度。常见的坏主意：
① 去掉 -MMD 让依赖变少（结果：改头文件不重编，线上跑的是旧逻辑）；
② 用 make -i 让失败不中断（结果：产物缺了一块，但 CI 是绿的）；
③ 缓存整个 build/ 目录（结果：缓存键没算对，复用了别人的产物）；
④ 把测试从 CI 里删掉（结果：构建快了，故障率上去了）。
构建系统的第一优先级永远是"产物正确"，第二才是"快"。
常见坑

九个真实踩过的坑

1
Makefile 的命令行用了空格缩进
报 missing separator。Make 只认 tab。在编辑器里打开"显示空白字符"，或临时用 cat -A Makefile 看行首是 ^I 还是空格。
2
没写 .PHONY
目录里一旦出现同名文件，make clean 就静默不执行。CI 上表现为"清理了但还是用了旧产物"，极难排查。
3
只写 %.o: %.c，不生成头文件依赖
改了 util.h，只有直接包含它的 .c 重编，其他 .o 用的是旧声明，链接时结构体大小不一致，运行时崩。加 -MMD -MP 和 -include $(DEPS)。
4
改了编译参数，但 make 不重编
Make 只看文件 mtime，不看命令行。把参数写进 stamp 文件并让它成为依赖，或者干脆 make clean。这是"增量构建骗了你"的典型案例。
5
用了 make -j 不带数字
无限制 fork，机器瞬间卡死，甚至触发 OOM。永远写 -j$(nproc) 或一个明确的数字。
6
递归 make 加并行，子目录之间有隐藏依赖
表现是"十次里失败一次"，错误信息还互相矛盾。要么显式声明子目录依赖，要么用 .NOTPARALLEL:，要么换非递归构建。
7
CI 缓存键没包含锁文件哈希
依赖升级后仍然命中旧缓存，装出旧版本，本地能跑 CI 不能跑。key 里必须放 hashFiles('**/package-lock.json') 这类指纹。
8
把 build/ 整个目录缓存起来
缓存的是"上一次的产物"，而不是"可复用的编译结果"。源码变了但缓存键没变时，会直接用旧产物，产出与源码不符的二进制。缓存依赖目录，不要缓存产物目录。
9
在 CI 上构建，但产物里嵌了 runner 的绝对路径
调试信息、panic 栈、日志里的路径都指向 /home/runner/work/...。加 -trimpath（Go）或 -ffile-prefix-map（C/C++），并在容器里用固定挂载点。
自测

六道题

1. Makefile 里 $< 和 $^ 的区别是？
正确答案：$< 是第一个依赖，$^ 是所有依赖。目标文件名是 $@。模式规则 %.o: %.c 里，$< 就是那个 .c 文件，所以编译命令常写 -c -o $@ $<。
2. 为什么 .PHONY: clean 是必须的？
正确答案：第三项。如果目录里恰好有个叫 clean 的文件，Make 会认为目标已存在且无需更新，直接跳过并返回成功。声明伪目标后，永远执行。
3. 改了 CFLAGS 从 -O2 到 -O0，make 却说 up to date。原因是？
正确答案：Make 不跟踪命令行。这是时间戳型增量构建的固有缺陷。解法是把编译参数写进一个 stamp 文件，让它成为 .o 的依赖；或者改完参数后 make clean。
4. build/%.o: src/%.c | build 里竖线的作用是？
正确答案：order-only 依赖。目录的 mtime 会随着里面文件的增删而变化，如果不加竖线，每次新增文件都会让所有 .o 被判定过期，导致全量重编。
5. 关于内容哈希型增量（Bazel / Gradle），哪个说法对？
正确答案：第三项。代价是要对输入做哈希，首次构建会慢一些；收益是正确性更高，而且指纹天然适合做远程缓存的键。
6. CI 构建要缓存 node_modules，正确的做法是？
正确答案：第一项。更稳的做法其实是只缓存 ~/.npm 这类"下载缓存"，然后每次跑 npm ci 重建 node_modules —— 这样依赖树一定和 lock 文件一致，而下载仍然走缓存。

一份可直接用的 Makefile 骨架

CC       := cc
CFLAGS   := -O2 -Wall -Wextra -MMD -MP
TARGET   := app
SRCS     := $(wildcard src/*.c)
OBJS     := $(patsubst src/%.c,build/%.o,$(SRCS))
DEPS     := $(OBJS:.o=.d)

.PHONY: all clean
.DEFAULT_GOAL := all
.DELETE_ON_ERROR:

all: $(TARGET)

$(TARGET): $(OBJS)
	$(CC) $(CFLAGS) -o $@ $^

build/%.o: src/%.c | build
	$(CC) $(CFLAGS) -c -o $@ $<

build:
	mkdir -p $@

clean:
	rm -rf build $(TARGET)

-include $(DEPS)
