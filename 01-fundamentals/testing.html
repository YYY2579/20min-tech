开始前

先承认一件事：测试是资产，也是负债

测试能防止回归，但它本身也是需要维护的代码。一套设计糟糕的测试，改一行业务代码要改二十个测试文件 —— 这种测试不但没有保护你，还在收税。

维度好的测试坏的测试
改业务代码时只有真正改变行为的测试会失败重构一下内部结构，几十个测试全红
失败时看名字就知道哪条规则坏了只知道"assertion failed"，得打断点查
运行时间单元测试全量几秒到几十秒跑一次十分钟，没人愿意在本地跑
稳定性同样的代码永远同样结果重跑一次就过了（flaky）
# 一条判断标准：测试的名字能不能当需求读
✓ 满 300 元减 50，满 300 元时实付 250
✓ 优惠券过期后下单，返回 COUPON_EXPIRED
✗ test_calc_1
✗ test_order_works
这份文档的前提：测试的目的不是"证明代码是对的"（做不到），而是在代码被改动时，快速告诉你哪条既定行为被破坏了。所有设计取舍都围绕这一条。
模块 1

测试金字塔：比例错了，后面全错

金字塔不是"三种测试都要写"的意思，它说的是成本和反馈速度的分布。越往下越快越便宜，越往上越慢越贵。

层级测什么单次耗时建议比例失败时说明什么
单元测试单个函数 / 类的逻辑分支毫秒级约 70%某段逻辑写错了，定位到行
集成测试模块之间、与真实依赖的协作百毫秒 ~ 秒级约 20%接口契约、SQL、序列化、事务出问题
端到端 E2E从用户入口到最终结果秒级 ~ 分钟级约 10%整体链路断了，但很难定位到具体位置

数字不必精确，重要的是数量级关系。一个常见的中型服务：单元测试 800 个跑 15 秒，集成测试 120 个跑 3 分钟，E2E 20 个跑 12 分钟。这个结构是健康的 —— 开发者本地只跑单元测试就能获得大部分信心。

为什么倒金字塔是灾难

倒金字塔指大量 E2E、少量单元测试。它在项目早期看起来很"高效"（一个测试覆盖一整条链路），但会在三个地方崩掉：

问题具体表现
反馈太慢改一行代码要等 20 分钟才知道有没有破坏东西，开发者干脆不跑，等到 CI 挂了再回来看
定位太难一个 E2E 失败可能是 30 个环节里任何一个，排查成本远超修复成本
极度脆弱改个按钮文案、调个接口字段，几十个 E2E 全红。最后大家的共识变成"红了就重跑"
无法覆盖分支E2E 只走主流程，异常分支（超时、重试、权限不足）几乎测不到
一个常被忽略的成本：E2E 的失败要人工判断"是真 bug 还是环境问题"。假设 20 个 E2E 有 5% 的 flaky 率，每天跑 10 次，你每天要做 10 次人工判断。一个月后没人再看 E2E 结果了 —— 这时候它已经等于不存在。

测试该跟着什么走

判断一个逻辑该写在哪一层，问一个问题：它的失败原因可能来自几个地方？

逻辑合适的层级理由
折扣计算、税费公式单元测试纯函数，输入输出明确，分支多
SQL 是否正确（含 JOIN、分页）集成测试只有真实数据库能验证语法和语义
JSON 序列化的字段名集成测试 / 契约测试单元测试用 mock 会掩盖真实序列化行为
登录 → 下单 → 支付E2E，1~2 条价值在于验证"链路是通的"，不在覆盖分支
事务回滚集成测试需要真实事务管理器，mock 无法模拟
一条经验法则：把 80% 的断言写在纯逻辑上，把 20% 的断言写在"接线是否正确"上。前者便宜且稳定，后者才是真正容易出错的地方 —— 但它的数量必须少，否则维护成本爆炸。
模块 2

单元测试的边界：测行为，不测实现

这是单元测试唯一重要的原则。搞错这一条，其他技巧都是白费。

什么是"行为"，什么是"实现"

行为是调用者能观察到的契约：返回值、抛出的异常、对外发出的调用、持久化的副作用。实现是达成行为的方式：内部用了哪个辅助函数、循环怎么写、缓存放在哪一层。

# 被测代码
class PriceService:
    def total(self, items, coupon):
        subtotal = sum(i.price * i.qty for i in items)
        return self._apply_coupon(subtotal, coupon)

    def _apply_coupon(self, amount, coupon):
        if coupon and amount >= coupon.threshold:
            return amount - coupon.discount
        return amount

# ✗ 测实现：断言内部调用了 _apply_coupon
def test_total(mocker):
    spy = mocker.spy(svc, "_apply_coupon")
    svc.total(items, coupon)
    spy.assert_called_once()          # 重构改名就红，毫无价值

# ✓ 测行为：断言最终金额
def test_total_applies_coupon_when_threshold_met():
    assert svc.total([Item(price=100, qty=3)], Coupon(threshold=300, discount=50)) == 250
断言对象类型说明
返回值 / 抛出的异常行为最稳定的断言，优先用它
写入数据库 / 发出的消息行为对外可见的副作用，可以断言
调用了某个外部依赖行为仅限跨进程边界的依赖（支付、短信）
内部方法被调用几次实现重构就会红，不要断言
私有字段的值实现同上
日志打印了什么多半是实现除非日志本身是产品需求（审计日志）

什么是好断言

  • 具体：断言 == 250，而不是 != 0 或 is not None。模糊断言等于没断言。
  • 完整：验证整个返回对象的关键字段，而不是只挑一个。否则字段错位、默认值丢失都测不出来。
  • 有失败信息：断言库大多支持附加说明，写明"期望什么、为什么"。失败时不用回去读代码。
  • 断言原因而不是现象：assert result == [] 要配一句注释说明"为什么这里应该是空"。
# 浮点数不要用 ==
assert result == pytest.approx(0.3, abs=1e-9)      # Python
assertEquals(0.3, result, 1e-9);                   # JUnit
expect(result).toBeCloseTo(0.3, 9);                # Jest

# 集合类断言要明确是否关心顺序
assert result == [1, 2, 3]                          # 关心顺序
assert sorted(result) == [1, 2, 3]                  # 不关心
assert set(result) == {1, 2, 3}                     # 不关心且去重

一个测试只验证一件事

注意："一件事"指的是一个行为，不是一行断言。验证"下单成功"可以断言订单状态、库存扣减、消息发出 —— 这三条共同构成一个行为。而"下单成功 + 优惠券过期报错"是两件事，必须拆开。

# ✗ 一个测试塞了三个场景
def test_order():
    assert create_order(valid).status == "OK"
    assert create_order(expired_coupon).code == "COUPON_EXPIRED"
    assert create_order(no_stock).code == "OUT_OF_STOCK"
# 第一条失败后，后面两条根本不执行。你一次只能修一个问题。

# ✓ 拆成三个，名字即文档
def test_create_order_succeeds_with_valid_coupon(): ...
def test_create_order_rejects_expired_coupon(): ...
def test_create_order_rejects_when_stock_insufficient(): ...
为什么必须拆：① 失败时能立刻知道坏的是哪条规则；② 一个场景的前置条件不会污染另一个；③ 未来只想删掉某个场景时，不用动其他测试。代价只是多写几行，收益是长期的。

AAA 结构

Arrange（准备）、Act（执行）、Assert（断言）。中间用空行隔开，读的人一眼能看出被测动作是哪一行。

def test_refund_exceeding_paid_amount_is_rejected():
    # Arrange
    order = an_order(paid=100, status="PAID")
    service = RefundService(repo=FakeOrderRepo([order]))

    # Act
    result = service.refund(order.id, amount=150)

    # Assert
    assert result.ok is False
    assert result.code == "REFUND_EXCEEDS_PAID"
    assert repo.get(order.id).status == "PAID"   # 状态未被修改
模块 3

测试设计方法：从"随便想几个"到"系统覆盖"

凭直觉写用例，通常只覆盖了正常路径。下面四种方法能把用例从"想到哪写到哪"变成"可以论证覆盖完整"。

方法一：等价类划分

把输入空间切成若干类，每一类里任取一个值，效果相同。于是每类只需一个用例。

例子：优惠券满 300 减 50。输入是订单金额，规则分三段：

等价类范围代表值期望
无效（负数）amount < 0−1拒绝
有效但不够门槛0 ≤ amount < 300150原价
有效且达门槛amount ≥ 300500减 50

三个用例覆盖了整个输入域。如果只写"金额 500"一个用例，前两类的行为完全未知。

方法二：边界值分析

bug 几乎总是长在边界上（< 写成 <=、循环差一位）。所以对每个边界，取边界值本身、边界两侧各一个。

边界要测的值为什么
amount ≥ 300299 / 300 / 301299 和 300 是"减不减"的分界，301 确认没有上界错误
1 ≤ qty ≤ 990 / 1 / 99 / 100两端各测"刚好合法"和"刚好非法"
字符串长度 ≤ 2019 / 20 / 2120 与 21 之间是经典的 off-by-one
时间窗口 00:00–23:5923:59:59 / 00:00:00跨天、时区、夏令时都藏在这里
# pytest 参数化，一次写清边界
@pytest.mark.parametrize("amount,expected", [
    (299, 299),      # 门槛下一分
    (300, 250),      # 刚好达门槛
    (301, 251),      # 门槛上一分
    (0,   0),        # 下界
])
def test_coupon_threshold(amount, expected):
    assert apply_coupon(amount, COUPON_300_50) == expected

方法三：判定表

当多个条件组合决定结果时，逐个条件测会漏掉组合。判定表把所有组合列出来，再合并等价的行。

例子：是否包邮，取决于三个条件：会员、金额满 99、偏远地区。

会员满 99偏远结果
是—否包邮
是—是不包邮（偏远加价）
否是否包邮
否是是不包邮
否否否不包邮
否否是不包邮

8 种组合合并成 6 行（"是"会员时金额不影响结果，用 — 表示无关）。如果只写"会员包邮"和"满 99 包邮"两个用例，就会漏掉"会员 + 偏远"这个组合 —— 而这恰恰是最容易写错的分支顺序问题。

方法四：状态迁移

有状态的对象（订单、支付单、工单），bug 集中在非法迁移和重复迁移上。先画出状态机，再对每条边和每个非法迁移各写一个用例。

# 订单状态机
CREATED --pay--> PAID --ship--> SHIPPED --confirm--> DONE
   |                |
 cancel          refund
   |                |
CANCELED        REFUNDED

# 要测的三类
1. 合法迁移：CREATED --pay--> PAID
2. 非法迁移：CANCELED --pay--> ? 必须拒绝
3. 重复迁移：PAID --pay--> ? 必须幂等或拒绝
用例类型数量估算价值
每条边的正向迁移边数（上例 6 条）保证主流程可用
非法迁移（终态出发）终态数 × 事件数最容易漏，也最容易出事故
重复事件（幂等）关键事件数网络重试、用户重复点击的真实场景
四种方法怎么配合用：先用等价类把输入域切块，再用边界值补上每块的两端，条件有组合就用判定表，对象有状态就用状态迁移。四步下来，用例数量通常比"凭感觉写"多 2~3 倍，但每一条都能说清"为什么需要它"。
模块 4

Mock 的边界：什么时候必须，什么时候有毒

Mock 的本质是用一个可控的假对象替换真实依赖。它的价值在于隔离不确定性和慢速依赖；它的代价是你测的不再是真实系统。

先分清 mock 和 stub

类型作用断言什么
Stub（桩）提供预设的返回值，让被测代码能跑下去不针对它断言，只关心被测代码的输出
Mock（模拟对象）除了返回值，还记录"被怎么调用"断言它是否被调用、调用几次、参数是什么
Fake（伪实现）一个能真正工作的简化实现，如内存版 Repository不额外断言，但行为接近真实
Spy（间谍）包住真实对象，记录调用但真的执行既看真实结果，也看调用记录
# Stub：只为让流程跑通
sms = StubSmsSender()                  # send() 直接返回成功
service = RegisterService(sms)
service.register("13800000000")
assert repo.find_by_phone("13800000000") is not None

# Mock：要验证"确实发了短信，且发给谁"
sms = Mock()
service.register("13800000000")
sms.send.assert_called_once_with("13800000000", ANY)

必须 mock 的三种情况

情况理由
不可控的外部系统支付、短信、第三方 API。你无法让它们返回 500，也无法让它们慢 30 秒
有真实副作用发邮件、扣款、发 MQ。测试不能真的给用户发短信
非确定性当前时间、随机数、UUID。不控制它们，断言就无法固定

除此之外，自己项目内部的类尽量不要 mock。想 mock 一个内部类，通常说明这个类的边界设计有问题，或者这个测试本该是集成测试。

过度 mock 的四种症状

  • 测试全绿但线上炸：mock 的返回值和真实实现不一致。你测的是"我以为它会返回什么"。
  • 重构即全红：改一个方法签名，20 个测试文件要跟着改。这说明测试耦合了实现结构。
  • 测试里全是 when(...).thenReturn(...)：一个测试配了 8 个 stub，说明被测单元依赖太多，应该先拆设计。
  • 没人看得懂测试在验什么：mock 的编排本身占了 30 行，真正的断言只有 1 行。
# ✗ 过度 mock：连自己的 Value Object 都 mock
when(user.getId()).thenReturn(1L)
when(user.getName()).thenReturn("张三")
when(user.getLevel()).thenReturn(Level.GOLD)
when(coupon.isValid()).thenReturn(true)
when(coupon.getDiscount()).thenReturn(50)
# 这时候"用户"和"优惠券"已经不是对象了，是一堆设定好的返回值

# ✓ 用真实对象构造，只 mock 外部依赖
User user = new User(1L, "张三", Level.GOLD);
Coupon coupon = Coupon.fixed(50, LocalDate.now().plusDays(1));
when(paymentClient.charge(any())).thenReturn(ChargeResult.ok());
最危险的 mock 是 mock 掉"你想验证的东西"。比如要验证"库存不足时不下单"，却 mock 了库存服务的返回值 —— 那你验证的只是"if 分支能走通"，而不是"库存服务真的会返回不足"。被 mock 的边界，就是测试的盲区边界。
Mock 与真实实现的漂移是慢性毒药。接口加了必填参数、返回值多了个字段、异常类型改了 —— mock 完全不知道，测试依然全绿。对策：对关键外部依赖额外写契约测试（用真实的 schema / 录制回放验证），让 mock 的假设定期被真实世界校验一次。
模块 5

集成测试：让真实依赖上场

集成测试要回答的问题是：这些零件拼在一起，还工作吗？单元测试全绿、集成测试全红，是非常常见的情况 —— 因为单元测试里的每个 mock 都"太配合"了。

数据库怎么处理

方案优点缺点
内存数据库（H2 / SQLite）快，无需外部依赖SQL 方言不同，生产能跑的语句这里报错，反之亦然。索引、锁、事务隔离行为都不一样
真实数据库容器行为完全一致，包括方言、约束、隔离级别启动慢（几秒），需要 Docker
共享测试库简单，团队都在用测试互相污染，并行跑必炸，数据状态不可控
录制回放无需真实依赖，快只覆盖录过的路径，SQL 改了不知道
用 H2 替代 PostgreSQL 是经典陷阱。H2 的 GROUP BY 宽松、不支持部分索引、JSON 类型行为不同、ON CONFLICT 语法缺失。结果就是：本地全绿，预发环境一片红。要么用同款数据库容器，要么接受"这类测试不覆盖 SQL 正确性"。

testcontainers 的思路

核心思想：测试启动时用 Docker 拉一个真实的依赖实例，测试结束自动销毁。每个测试套件拿到独立的容器和独立的端口，天然隔离，也不需要团队共享一个"测试数据库"。

# Java + JUnit 5
@Container
static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16-alpine");

@DynamicPropertySource
static void props(DynamicPropertyRegistry r) {
    r.add("spring.datasource.url", pg::getJdbcUrl);
    r.add("spring.datasource.username", pg::getUsername);
    r.add("spring.datasource.password", pg::getPassword);
}

# Python
from testcontainers.postgres import PostgresContainer
with PostgresContainer("postgres:16-alpine") as pg:
    engine = create_engine(pg.get_connection_url())
    run_migrations(engine)
    # 跑测试

# Go
req := testcontainers.ContainerRequest{
    Image:        "postgres:16-alpine",
    ExposedPorts: []string{"5432/tcp"},
    WaitingFor:   wait.ForListeningPort("5432/tcp"),
}

关键成本数字：容器冷启动约 3~8 秒，镜像已在本地时约 1~2 秒。所以做法是整个测试进程共用一个容器，每个测试用例只清数据，不要每个用例起一个容器。

测试隔离的三层

层级做法代价
事务回滚每个测试包在事务里，结束回滚最快，但测不到真实提交行为（如唯一约束在提交时才校验的场景）
清表每个测试前 TRUNCATE 相关表快，可靠。注意外键顺序和自增序列
独立 schema / 库每个 worker 一个 schema支持并行，实现复杂一些
# 事务回滚的典型写法（pytest）
@pytest.fixture
def db_session(engine):
    conn = engine.connect()
    tx = conn.begin()
    session = Session(bind=conn)
    yield session
    session.close()
    tx.rollback()          # 一切改动消失，测试之间零污染
    conn.close()
并行跑集成测试的前提是"每个 worker 有独立的数据空间"。做法：用 worker id 拼 schema 名或库名（test_db_${PYTEST_XDIST_WORKER}）。共享一个库再靠"清表"来隔离，在并行下必然互相删数据。
模块 6

测试数据管理：别让 fixture 变成沼泽

测试数据是最容易被忽视的成本中心。一个 500 行的 conftest.py，加上一堆互相依赖的 fixture，维护成本会超过业务代码。

三种造数据的方式

方式特点什么时候用
固定 fixture一份写死的 JSON / SQL，所有测试共用只读的参考数据：国家列表、配置项
工厂函数代码构造对象，字段有合理默认值，按需覆盖绝大多数场景。可读、可控、类型安全
共享 fixture 链fixture 依赖 fixture，层层叠加慎用。超过两层就该拆
# 工厂函数：默认值合理，只写测试关心的字段
def an_order(**kw):
    defaults = dict(
        id=next_id(), user_id=1, amount=100,
        status="CREATED", created_at=datetime(2026, 1, 1),
    )
    return Order(**{**defaults, **kw})

# 测试里一眼能看出"这个用例特殊在哪"
order = an_order(amount=299)              # 只关心金额
order = an_order(status="PAID")            # 只关心状态
工厂函数最重要的设计是"默认值必须合法"。如果默认值造出来的是一个非法对象，每个测试都要先补三个字段才能用，那工厂就失去意义了。默认值 = 一个最普通的、能走通主流程的实例。

每个测试独立数据

共享数据是 flaky 的头号来源。两个测试都读写 user_id=1，谁先跑谁后跑结果就不同。

反模式后果
所有测试用同一个 user_id一个测试改了余额，另一个测试的断言就挂了
测试依赖"上一条测试插入的数据"单独跑这个测试就失败，只能全量跑
全局自增 ID 跨测试复用断言里写死 id=1，换个执行顺序就变 id=7
测试之间通过数据库传递状态并行执行直接爆炸
# 唯一性用随机后缀，而不是写死
email = f"user-{uuid4().hex[:8]}@test.local"

# 断言不要依赖具体 ID，用返回的对象或业务键
created = api.create_user(email=email)
assert api.get_user(created["id"])["email"] == email
# 而不是 assert created["id"] == 1

清理策略

首选：事务回滚。最快、最彻底，但只适用于不验证提交语义的测试。
次选：每个测试前清空。比"测试后清理"更可靠 —— 因为测试失败时清理代码可能不执行，而"前置清理"保证下一次是干净的。
兜底：整库重建。CI 上每个 job 起一个全新容器，跑完即销毁。这是最贵但最不会出错的方案。
别在测试里连生产库或共享的开发库。一次误跑的 DELETE 就能清掉同事三天的调试数据。测试连接串必须指向本地容器或专门的测试实例，并且建议在测试启动时校验库名包含 test，否则直接 abort。
模块 7

Flaky 测试治理：不稳定的测试等于没有测试

Flaky（间歇性失败）是测试体系最致命的病。它的真正危害不是"多跑一次就过"，而是团队从此不再相信红色 —— 真 bug 出现时，大家的第一反应是"重跑一下"。

成因典型表现定位方法
时间依赖 now()、跨天/跨月失败、时区差异把系统时间固定住再跑；在 23:59 附近跑一次
执行顺序单独跑通过，全量跑失败随机打乱顺序跑 20 次；看是否与某个测试共存时必挂
并发并行执行时偶发失败，串行正常固定单线程跑一遍；再提高并行度复现
外部依赖网络抖动、第三方限流、容器启动慢看失败时间点是否与依赖的延迟尖刺对齐

成因一：时间

# ✗ 直接用当前时间，跨天必挂
coupon = Coupon(expires_at=datetime.now() + timedelta(hours=1))
assert coupon.is_valid()

# ✓ 注入时钟，测试里给固定值
class Coupon:
    def __init__(self, expires_at, clock=datetime.now):
        self.expires_at, self.clock = expires_at, clock
    def is_valid(self):
        return self.clock() < self.expires_at

# 测试里
fixed = lambda: datetime(2026, 1, 1, 12, 0, 0)
assert Coupon(datetime(2026, 1, 1, 13, 0), clock=fixed).is_valid()

# 或者用 freezegun 冻结时间（Python）
@freeze_time("2026-01-01 12:00:00")
def test_coupon_valid(): ...

# Java：注入 Clock，测试用 Clock.fixed(...)
# JS：jest.useFakeTimers() + jest.setSystemTime(...)

成因二：执行顺序

根因永远是共享可变状态：全局变量、单例、静态字段、数据库里的残留数据、被 monkey-patch 的函数没还原。

# 定位：随机顺序跑 20 次，找出"总是成对出现"的测试
pytest -p no:randomly          # 先确认串行固定顺序是否稳定
pytest -p randomly --randomly-seed=12345
for i in $(seq 1 20); do pytest -q || echo "FAIL seed=$i"; done

# JUnit：@TestMethodOrder 或直接随机化
# Jest：--randomize（新版本支持）
常见污染源修法
模块级全局变量被修改每个测试前重置，或用 fixture 的 setup/teardown
monkey-patch 后没还原用上下文管理器 / fixture 自动还原，别手写赋值
数据库残留数据每个测试前清表（见模块 6）
单例的缓存暴露 reset 方法，测试 teardown 调用
环境变量被改用 monkeypatch.setenv（自动还原）而不是 os.environ[...] = ...

成因三：并发

并行执行时，测试之间争抢同一份资源：同一个数据库行、同一个端口、同一个临时目录、同一个外部账号的配额。

  • 端口冲突：不要写死 8080。用 port=0 让系统分配，再从 socket 读回实际端口。
  • 临时目录冲突：用框架提供的独立临时目录（tmp_path / @TempDir），不要用 /tmp/test.db。
  • 数据竞争：每个 worker 独立 schema / 独立账号。
  • 限流配额：共享一个测试账号调第三方 API，并发一高就被限流。用 mock 或按 worker 分配账号。

成因四：外部依赖

真实网络是不可靠的。集成测试里连真实第三方，等于把对方的可用性变成你的构建成功率。

处理原则：跨进程边界的依赖，在单元测试里一律 mock；集成测试里只对"自己拥有的"依赖用真实实例（自己的数据库、自己的缓存）；第三方的行为用契约测试 + 录制回放验证，而不是每次构建都真连。

治理流程：隔离 → 定位 → 修复 → 防复发

立刻隔离：打上 @flaky 标记移出主流水线，但必须建 issue 并设截止时间。直接删掉或无限重试都是掩盖。
量化：记录失败率。跑 100 次统计失败次数，低于 1% 的也值得修 —— 因为它会一直消耗信任。
复现：按四大成因逐项排除。固定时间、固定顺序、单线程、断网，四个变量分别控制一次。
防复发：把"随机顺序跑"和"重复跑 N 次"加进 CI 的定时任务（ nightly ），让新引入的 flaky 当天就暴露。
自动重试是最坏的处理方式。它把"偶发失败"变成"偶发通过"，问题被永久掩盖。更糟的是，重试会让真实的并发 bug 在线上以更低频率出现 —— 那时候你没有重试按钮。重试只能作为临时止血，必须配一条带 deadline 的修复项。
模块 8

覆盖率的陷阱

覆盖率是发现"哪里完全没测"的工具，不是"测试好不好"的指标。把它当 KPI，团队会写出大量"执行但不验证"的测试。

行覆盖 vs 分支覆盖

# 一段简单代码
def discount(level, amount):
    if level == "GOLD":
        return amount * 0.8
    return amount

# 只写一个测试
assert discount("GOLD", 100) == 80
# 行覆盖率：100%（每一行都执行过了）
# 分支覆盖率：50%（if 的 false 分支从未走过）
指标统计什么盲区
行覆盖哪些代码行被执行过只走一个分支就 100%，另一条路径完全没测
分支覆盖每个 if / case 的真假两侧是否都走过仍然不管"断言对不对"，也不管组合条件
条件覆盖复合条件里每个子表达式组合爆炸，实际很少严格统计
路径覆盖所有可能的执行路径循环存在时路径无限，理论上不可达

工程上够用的是分支覆盖。它比行覆盖只多一点成本，但能挡掉"只测了 happy path"这个最大的漏洞。

为什么 100% 覆盖不等于没 bug

覆盖率测不到的东西例子
断言是否正确执行了所有代码，但一行断言都没写，覆盖率照样 100%
需求是否正确代码完全按错误的需求实现，测试也按错误需求写，全绿
并发问题单线程测试 100% 覆盖，竞态一个都没触发
性能与资源功能全对，但内存泄漏、N+1 查询
集成问题单元测试全覆盖，但 SQL 在真实库上语法错误
边界与异常覆盖率不区分"走通"和"走通得对不对"
用覆盖率做 KPI 会导致一个可预测的后果：开发者写大量"调用一下、不断言"的测试，或者把断言写成 assert result is not None。覆盖率上去了，缺陷率不变，维护成本翻倍。指标一旦成为目标，就不再是好指标。

覆盖率的正确用法

看"未覆盖的部分"，而不是总百分比。报告里那些红色的行，往往就是没人想过的情况。
设下限而不是目标。比如"核心模块不低于 70%，不允许下降"，防止新代码把整体拉低。
按模块分级。支付、权限、金额计算要求高；配置加载、DTO 转换可以低。
结合变更覆盖（diff coverage）：只看本次改动的行有没有被测到。这比全量覆盖率有效得多。
# 只看本次改动行的覆盖（diff coverage）
coverage run -m pytest && coverage xml
diff-cover coverage.xml --compare-branch=origin/main --fail-under=80

# 分支覆盖（Python）
coverage run --branch -m pytest
coverage report -m --skip-covered

# Java（JaCoCo）关注 branch 而不是 line
mvn test jacoco:report
# 报告里看 "Branch Coverage" 列

# JS（Istanbul / c8）
npx c8 --branches 80 --reporter=text npm test
一个可用的判断标准：如果覆盖率从 65% 涨到 80%，缺陷率明显下降，说明之前的缺口是真的；如果从 80% 涨到 95% 但缺陷率不变，说明剩下的 15% 是 getter、异常兜底、日志分支 —— 继续投入的回报已经很低。覆盖率有边际收益递减，别追最后那几个点。
常见坑

十个测试设计中的典型错误

1
只测正常路径
边界、空值、超时、权限不足全都没测。线上事故几乎全部发生在这些分支上。
2
断言太弱：assert result is not None
只要不抛异常就通过，等于什么都没验证。断言要具体到值、状态、错误码。
3
一个测试验证五件事
第一条失败后后面全不执行，一次只能修一个问题；失败信息也无法定位是哪条规则坏了。
4
断言内部方法被调用
重构（改名、拆分、换实现）就全红。测行为不测实现，这是单元测试的第一原则。
5
用 H2 代替生产用的 PostgreSQL
方言、约束、事务隔离都不同，本地全绿、预发全红。要么用同款容器，要么不测 SQL。
6
测试之间共享数据
谁先跑谁后跑结果不同，单独跑还过不了。每个测试必须构造自己的数据。
7
测试里直接用 datetime.now()
跨天、跨月、闰秒、时区都会导致偶发失败。注入时钟，测试里给固定值。
8
flaky 测试加个自动重试就完事
把"偶发失败"变成"偶发通过"，真实 bug 被永久掩盖，团队从此不再相信红色。
9
把覆盖率当 KPI
会催生大量"调用但不断言"的测试。覆盖率涨了，缺陷率不变，维护成本翻倍。
10
测试里连共享开发库或生产库
一次误跑的 DELETE 就能清掉别人的数据。测试连接串必须指向本地容器，并在启动时校验库名。
自测

六道题

1. 一个团队有 300 个 E2E 测试、20 个单元测试，每次 CI 要跑 40 分钟，红了就重跑。主要问题是什么？
正确答案：倒金字塔。应该把大部分断言下沉到单元测试（毫秒级、定位准），E2E 只保留少量关键链路。"红了就重跑"是信任已经崩塌的信号。
2. 优惠券门槛是"满 300 减 50"，用边界值分析至少要测哪几个金额？
正确答案：299 / 300 / 301。边界值取"边界两侧各一个 + 边界本身"，专门抓 < 写成 <= 这类 off-by-one。0/150/300 是等价类划分的思路。
3. 下面哪种情况不应该 mock？
正确答案：领域对象。它们是纯数据 + 纯逻辑，用真实对象构造更简单也更可信。mock 它们只会让测试充满 when().thenReturn()，且重构即全红。
4. 单元测试用 H2 跑，本地全绿，预发环境报 SQL 语法错误。最可能的原因是？
正确答案：方言差异。H2 对 GROUP BY、JSON 类型、ON CONFLICT 等语法支持不同。这类断言应该放在用真实数据库容器的集成测试里。
5. 一个测试单独跑通过，全量跑就失败。最可能是哪类 flaky 成因？
正确答案：执行顺序。单独跑通过说明逻辑本身没问题，全量跑才失败说明被别的测试污染了：全局变量、单例缓存、数据库残留、没还原的 monkey-patch。
6. 关于覆盖率，哪个说法是对的？
正确答案：看未覆盖部分 + diff coverage。覆盖率不检查断言是否正确、需求是否正确、并发是否安全。设成 KPI 只会催生"执行但不断言"的假测试。
