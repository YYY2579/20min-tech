模块 1

自动配置原理

自动配置 = 条件装配 + 启动器传递依赖。理解它就理解了一半的 Spring Boot。

三个注解的关系

@SpringBootApplication
// 等价于三个注解复合：
@SpringBootConfiguration   // 本质就是 @Configuration，标记这是主配置类
@EnableAutoConfiguration   // 开启自动配置，核心
@ComponentScan            // 扫描主类所在包及子包，可指定 basePackages/excludeFilters

@EnableAutoConfiguration 的展开链条

@EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector.class) 导入一个选择器
选择器调用 SpringFactoriesLoader.loadFactoryNames()，读取所有 jar 里的 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 文件（2.7 之前是 META-INF/spring.factories 的 EnableAutoConfiguration 键）
得到一批自动配置类的全限定名列表，逐个作为普通 @Configuration 类注册进容器
每个自动配置类身上挂着一堆 @Conditional 系列注解，条件不满足就整体跳过
配置类里的 @Bean 方法再带一层 @ConditionalOnMissingBean，让用户定义的 bean 能覆盖默认实现
// META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.example.autoconfigure.AppCacheAutoConfiguration

// ===== 自动配置类的标准写法（写 starter 的人视角）=====
@AutoConfiguration
@ConditionalOnClass(RedisOperations.class)      // classpath 里有 redis 相关类才生效
@ConditionalOnProperty(prefix = "app.cache", name = "type", havingValue = "redis")
public class AppCacheAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                 // 用户自己配了 CacheManager 就不覆盖
    public CacheManager cacheManager(RedisConnectionFactory factory) {
        return RedisCacheManager.builder(factory).build();
    }
}

常用条件注解速查

注解生效条件
@ConditionalOnClass / OnMissingClassclasspath 里存在（或不存在）指定类
@ConditionalOnBean / OnMissingBean容器里已有（或没有）指定 bean。注意：加在 @Bean 上只按已注册的排序判断，有顺序陷阱
@ConditionalOnProperty配置属性匹配，如 havingValue="redis"
@ConditionalOnWebApplication / OnNotWebApplication是否 Web 环境（SERVLET / REACTIVE）
@ConditionalOnExpressionSpEL 表达式为 true
@ConditionalOnCloudPlatform运行在指定云平台（如 Kubernetes）

starter 机制

一个 starter 通常只有两样东西：一个几乎只有依赖的 pom + 一个 autoconfigure jar（放自动配置类 + 注册文件 + 额外配置类）。以 spring-boot-starter-web 为例，它本身没有代码，只把 spring-web、spring-webmvc、tomcat-embed-core 拉进来。

<!-- starter 的 pom 骨架 -->
<artifactId>app-cache-spring-boot-starter</artifactId>
<dependencies>
  <dependency>...app-cache-autoconfigure...</dependency>  <!-- 逻辑都在这 -->
  <dependency>...spring-data-redis...</dependency>
</dependencies>
调试三板斧：① 启动加 --debug，控制台输出条件评估报告（每个自动配置类"为什么生效/为什么跳过"）；② 访问 /actuator/conditions 端点看同样信息；③ IDE 装 Spring Boot 插件可以直接看 Bean 依赖图。"某个 starter 没生效"先看条件报告，90% 是 classpath 或属性前缀写错。
模块 2

IoC 与 Bean 作用域

作用域生命周期典型场景
singleton每个容器唯一实例（默认）无状态 Service、Repository。有状态字段的 singleton 是并发事故源
prototype每次 getBean() / 注入点创建新实例有状态的命令对象、每次请求要独立状态的工具类
request每个 HTTP 请求一个（仅 Web 环境）封装当前请求数据的 holder
session每个 HTTP 会话一个用户登录态相关的临时 bean
applicationServletContext 级别一个全局共享配置
prototype 的两个反直觉点：① 销毁回调不归容器管——原型 bean 创建后容器不再跟踪，@PreDestroy 不会被调用，资源要自己清理；② 注入 singleton 里的 prototype 是"一次性"的——注入发生在 singleton 创建时，之后永远是同一个原型实例。要每次拿新的，用 ObjectProvider<T> 或 @Scope(proxyMode = TARGET_CLASS)。

循环依赖与三级缓存

Spring 用提前暴露半成品的方式解决单例循环依赖。DefaultSingletonBeanRegistry 里三张表：

级别结构放什么
一级singletonObjects完全初始化好的单例（属性填充 + 初始化完成）
二级earlySingletonObjects提前暴露的实例：已实例化、属性还没填。没有 AOP 代理能力
三级singletonFactoriesObjectFactory 工厂，调用 getObject() 时才会生成代理对象。这才是能返回代理的地方
A 开始创建 → 实例化后（构造器已执行、属性未填充），把 ObjectFactory 放进三级缓存
A 填充属性需要 B → 容器开始创建 B
B 填充属性需要 A → 查一级缓存没有 → 查二级没有 → 触发三级缓存的 ObjectFactory，拿到 A 的早期引用（如果 A 需要代理，这里拿到的就是代理对象）→ 顺手提升到二级缓存
B 完成初始化进一级缓存；A 拿到 B，完成自己的初始化进一级缓存
三级缓存解决不了的情况：① 构造器注入的循环依赖——实例化阶段就要依赖，那时还没进缓存，直接抛 BeanCurrentlyInCreationException；② prototype 的循环依赖——原型不缓存，同样无解；③ @Async / @Transactional 的代理在极端顺序下可能注入不一致（拿到的是代理，但引用固定）。

Spring Boot 2.6+ 默认 spring.main.allow-circular-references=false，一有循环依赖直接启动失败——这是好事，逼你改设计。正确解法是用 setter/字段注入打破环或加 @Lazy 让一方延迟初始化，而不是把开关打开。 
// 三种注入方式对循环依赖的友好度
@Autowired public Foo(Bar bar) { }        // ✗ 构造器注入：循环必炸
@Autowired public void setBar(Bar bar) { }  // ✓ setter 注入：能解
@Autowired private Bar bar;               // ✓ 字段注入：能解
@Lazy @Autowired private Bar bar;         // ✓ 注入的是懒加载代理，最省事
模块 3

AOP 与事务实战

代理是怎么选出来的

机制选择条件特点
JDK 动态代理目标类实现了接口基于接口，反射调用。只能代理接口方法
CGLIB目标类没有接口生成子类字节码，可代理普通方法。不能代理 private / final / static 方法。Spring Boot 2.x 起 spring.aop.proxy-target-class=true 是默认值，即默认走 CGLIB

自调用：事务头号杀手

@Service
public class OrderService {

    @Transactional
    public void createOrder(Order o) {
        orderDao.save(o);
        updateStock(o.getSkuId());   // ✗ this 调用，绕过代理！
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void updateStock(Long skuId) {
        // 期望：新开一个事务，扣库存失败不影响主流程
        // 实际：被合并进 createOrder 的事务里，REQUIRES_NEW 形同虚设
    }
}
// 解法一：注入自己（Spring 4.3+ 支持自注入）
@Service
public class OrderService {
    @Lazy @Autowired private OrderService self;  // 注入的是代理对象

    @Transactional
    public void createOrder(Order o) {
        orderDao.save(o);
        self.updateStock(o.getSkuId());        // ✓ 走代理
    }
}

// 解法二：拆成两个 Bean（更干净，推荐）
@Service public class OrderService {
    @Autowired private StockService stockService;   // 注入的是代理
    @Transactional public void createOrder(...) { stockService.updateStock(...); }
}

七种传播行为

传播行为语义
REQUIRED（默认）有事务就加入，没有就新建。90% 场景用这个
REQUIRES_NEW挂起当前事务，强行新开一个。原事务回滚不影响它（经典用途：记录日志，业务失败也要留下日志）
NESTED嵌套事务，用 Savepoint 实现。依赖 JDBC 驱动支持 savepoint
SUPPORTS有就加入，没有就非事务运行
NOT_SUPPORTED挂起当前事务，非事务运行
MANDATORY必须在已有事务里运行，否则抛异常
NEVER必须没有事务，否则抛异常

事务的其他关键属性

@Transactional(
  rollbackFor = Exception.class,        // ✓ 受检异常也要回滚，强烈建议加上
  noRollbackFor = BusinessWarnException.class,
  readOnly = true,                         // 只读事务：部分数据库会优化（如 MySQL 不会加行锁）
  timeout = 5,                          // 秒。超时抛 TransactionTimedOutException
  isolation = Isolation.READ_COMMITTED, // 隔离级别，MySQL InnoDB 默认 RR
  propagation = Propagation.REQUIRED
)
@Transactional 默认只对 RuntimeException 和 Error 回滚。受检异常（如 IOException）默认提交——这是最大的坑，没有之一。工程规范里统一写 rollbackFor = Exception.class。
模块 4

Spring MVC 请求处理流程

客户端请求到达内嵌容器（Tomcat / Jetty / Undertow）
Filter 链（Servlet 规范）：如 CharacterEncodingFilter、HiddenHttpMethodFilter。先于 DispatcherServlet
DispatcherServlet（前端控制器，Spring MVC 的入口）
HandlerMapping：拿着请求 URL 和方法，找到 @RequestMapping 对应的 HandlerMethod，包装成 HandlerExecutionChain（附带 Interceptor 列表）
Interceptor.preHandle 依次执行（按注册顺序），返回 false 直接中断
HandlerAdapter 反射调用 Controller 方法。ArgumentResolver 负责参数绑定（@RequestParam / @PathVariable / @RequestBody / 自定义参数解析器）；返回值经 HttpMessageConverter（Jackson）序列化，或走视图渲染
Interceptor.postHandle 在 HandlerAdapter 返回 ModelAndView 之后、视图渲染之前执行（按注册顺序逆序）；响应写出后 afterCompletion 一定执行（渲染异常时 postHandle 不执行，afterCompletion 仍执行）
异常沿链抛出，由 HandlerExceptionResolver 处理：@ExceptionHandler / @ControllerAdvice / ResponseStatusExceptionResolver / DefaultHandlerExceptionResolver
扩展点作用范围典型用途
FilterServlet 层，先于 DispatcherServlet编码、鉴权、日志、限流（一次请求执行一次）
InterceptorSpring MVC 层，能拿到 HandlerMethod登录校验、打点、耗时统计。可拿到目标方法信息，Filter 拿不到
ArgumentResolver方法参数绑定自定义注解注入当前用户，如 @CurrentUser User u
@ControllerAdvice全局异常 / 全局数据绑定统一异常响应体、统一包装格式
// 一个"当前用户"参数解析器的骨架（工程里极其常用）
public class CurrentUserArgumentResolver implements HandlerMethodArgumentResolver {
    public boolean supportsParameter(MethodParameter p) {
        return p.hasParameterAnnotation(CurrentUser.class) && p.getParameterType() == User.class;
    }
    public Object resolveArgument(MethodParameter p, ...) {
        return UserContext.get();   // 从 ThreadLocal / RequestContextHolder 拿
    }
}

// 注册（WebMvcConfigurer 是 Spring Boot 的推荐扩展入口）
@Configuration public class WebConfig implements WebMvcConfigurer {
    public void addArgumentResolvers(List<HandlerMethodArgumentResolver> rs) {
        rs.add(new CurrentUserArgumentResolver());
    }
}
Interceptor 的坑：addInterceptors() 的注册顺序就是 preHandle 的执行顺序，而 postHandle / afterCompletion 是逆序执行。另外静态资源和错误页不会过自定义 Interceptor（走默认处理器），登录拦截的白名单要配 excludePathPatterns。
模块 5

Actuator 健康检查

引入 spring-boot-starter-actuator 即可。默认只暴露 /actuator/health 和 /actuator/info，其余要手动开。

端点用途
/actuator/health聚合所有 HealthIndicator。任一 DOWN 则整体 DOWN，HTTP 503
/actuator/info构建信息（git、version）
/actuator/metrics指标列表：jvm.memory.used、http.server.requests、system.cpu.usage
/actuator/env/{property}查看配置来源与优先级，排查"配置为什么不生效"神器
/actuator/loggersPOST 动态修改日志级别，线上排查不用重启
/actuator/threaddump线程栈快照，排查死锁/卡死
/actuator/heapdump堆转储（文件很大）。敏感，务必保护
/actuator/prometheus暴露 Prometheus 格式指标（需 micrometer-registry-prometheus）
# application.yml：最小可用配置
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,env,loggers   # 白名单，别用 "*"
  endpoint:
    health:
      show-details: always          # 显示各组件明细，调试用；生产可改 never
      probes:
        enabled: true               # 开启 k8s 探针分组
server:
  shutdown: graceful                # 优雅停机，部署必备
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
// 自定义健康检查：把"下游依赖活着吗"暴露出去
@Component
public class PaymentHealthIndicator implements HealthIndicator {
    @Override
    public Health health() {
        long t0 = System.currentTimeMillis();
        boolean ok = pingPaymentGateway();          // 你自己的探测逻辑
        long cost = System.currentTimeMillis() - t0;
        if (ok && cost < 200) {
            return Health.up().withDetail("latencyMs", cost).build();
        }
        return Health.down().withDetail("latencyMs", cost).build();
    }
}
生产三条军规：① 别配 include: "*"——env 端点会泄露脱敏前的配置、heapdump 能直接下载堆文件。② 用 Spring Security 给 /actuator 加角色控制，或把管理端口独立出来（management.server.port=9091，只监听内网）。③ k8s 探针用分组后的地址：就绪 /actuator/health/readiness、存活 /actuator/health/liveness。直接探 /health 会在 DB 抖动时把 Pod 杀掉（liveness 挂了会重启容器，这恰恰是最不该杀的场景）。

配置管理

profile：一套代码多环境

# src/main/resources/ 下：

application-dev.yml        # 开发环境
application-prod.yml       # 生产环境（注意：打包后也在 jar 里）

@Configuration @Profile("dev") public class DevConfig { ... }   // 只在 dev 生效
@Profile("!prod")                                        // 非 prod 才生效

@ConfigurationProperties(prefix = "app.mail")
public class MailProperties {

    private int port = 465;

    // getter / setter 不能省（除非用 record）

对比项@Value@ConfigurationProperties
绑定形式单个值，写 SpEL批量绑定到对象，支持嵌套、集合、Map
松散匹配不支持支持：smtp-auth = smtpAuth = SMTP_AUTH（环境变量）

校验不支持可加 @Validated + JSR-303 注解
RelaxedBinding无下划线/中划线/驼峰自动归一

配置优先级（从高到低，节选常用）

序号来源
1命令行参数 --app.mail.port=25（最高）
2环境变量 APP_MAIL_PORT=25（容器部署标准姿势）
3jar 外 ./config/application.yml、jar 外 ./application.yml
4jar 内 application-{profile}.yml（profile 专属优先于公共的）
5jar 内 application.yml
6@PropertySource、SpringApplication 默认属性（最低）
"改了配置不生效"排查顺序：① 是不是被更高优先级的来源覆盖了（命令行 > 环境变量 > jar 外 > jar 内）？用 /actuator/env/app.mail.port 看最终值来自哪个文件。② yaml 的缩进是不是用了 tab？③ 外部文件放对位置了吗——jar 同级或 ./config/ 子目录，不在 classpath 里。④ profile 专属文件有没有被打进 jar（resources 下就会）。⑤ key 名和 @ConfigurationProperties 前缀对不对得上。
模块 7

启动慢的排查

一个空 Spring Boot Web 应用启动约 1.5~2.5 秒，接了全栈 Starter 的工程常见 5~10 秒。超过这个量级就该查。

定位工具

# 1. 条件评估报告：看哪些自动配置在浪费时间
java -jar app.jar --debug 2>&1 | grep -A3 "Negative matches"

# 2. 启动耗时分解（Spring Boot 2.4+，需要 BufferingApplicationStartup）
public static void main(String[] args) {
    new SpringApplicationBuilder(App.class)
        .applicationStartup(new BufferingApplicationStartup(2048))
        .run(args);
}
# 然后 GET /actuator/startup（需要 management.endpoint.startup.enable=true）
# 输出每个 bean 的初始化耗时，一眼看出谁是元凶

# 3. JVM 层：类加载与编译耗时
java -Xlog:class+load=info -jar app.jar   # JDK9+ 统一日志
java -XX:+PrintCompilation -jar app.jar   # JIT 编译情况

# 4. 火焰图（Arthas，线上不重启也能看）
thread -n 3                # 最忙的 3 个线程栈
trace com.example.FooService bar          # 方法内部调用耗时

常见元凶与解法

元凶解法
组件扫描范围太大主类放在根包，扫描全盘。缩小 basePackages，或用 @ComponentScan.Filter 排除
用了一堆不需要的 starter用 --debug 看条件报告，exclude 掉没用的自动配置类
@PostConstruct / InitializingBean 里发网络请求初始化阶段查配置中心、建长连接。改懒加载或异步化
全量懒加载一刀切spring.main.lazy-initialization=true 能让启动快 30%~50%，但首请求 RT 暴涨。压测前务必预热
JVM 冷启动开 AppCDS（-XX:+AutoCreateSharedArchive 或 -XX:ArchiveClassesAtExit 归档类），对启动有明显改善；要再进一步上 GraalVM Native Image
日志/字节码增强全类扫描的 agent（如某些 APM、arthas trace）会让启动慢数倍，压测环境关掉再比
Tomcat 默认参数线程默认 200（server.tomcat.threads.max），每个线程默认栈 1MB。高并发小服务别盲目调大
一个务实的启动时间基线：轻量 API 服务 < 3s；带 ORM + Redis + MQ 的中等服务 3~6s；接了配置中心、注册中心的全家桶 6~12s。如果超过 15s，先查有没有在初始化阶段做阻塞 IO，而不是先怀疑框架。容器化部署时注意：JVM 在 cgroup 限制下可能拿不到"看似很多"的 CPU，启动时间会变长——这是容器感知（JDK 10+ 已支持 UseContainerSupport）与 requests/limits 配置的问题。
排雷

十个线上坑

1
同类内方法自调用，事务悄悄失效
this.b() 走的是原始对象不是代理。表现是 REQUIRES_NEW 变 REQUIRED、异常不回滚、readOnly 无效。解法：自注入 @Lazy 或拆类。
2
@Transactional 抛受检异常不回滚
默认只回滚 RuntimeException/Error。统一写 rollbackFor = Exception.class。
3
事务方法把异常 catch 掉不抛
代理靠异常触发回滚。catch 后要么抛出去，要么手动 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()。
4
private / final / static 方法上加 @Transactional
CGLIB 无法覆盖这些方法，注解完全无效且没有任何报错——最安静的坑。
5
@Transactional 方法内部用子线程
事务绑定在调用者的 ThreadLocal 上，新线程里的操作不在同一事务。子线程要么走消息队列异步化，要么别指望一起回滚。
6
循环依赖在 2.6+ 直接启动失败
默认禁止。别急着把 allow-circular-references 改回 true，那是把设计问题藏起来。正确解法：setter/字段注入、@Lazy、拆 bean。
7
Actuator 开 include "*" 且没有鉴权
/actuator/env 泄露配置、/actuator/heapdump 可直接下载堆文件（里面可能有明文密钥）。白名单端点 + 角色保护 + 独立管理端口，三件事都要做。
8
外部配置放错位置导致"不生效"
只认 jar 同级的 application.yml 或 ./config/ 子目录。放 classpath 里没用。排查用 /actuator/env/{key}。
9
singleton bean 里持有可变状态
默认单例，多个请求并发改同一个字段 = 数据错乱。无状态是铁律；要状态就 prototype 或用 ThreadLocal / 请求作用域。
10
生产开着 spring.jpa.show-sql=true 或 root 日志 DEBUG
每条 SQL 都打日志，CPU 和磁盘双杀，日志量大到淹没问题。开发环境用 application-dev.yml 开，生产 profile 关掉。
自测

六道题

1. @SpringBootApplication 展开后是哪三个注解的组合？
正确答案：@SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan。自动配置的入口是 @EnableAutoConfiguration，它通过 @Import(AutoConfigurationImportSelector.class) 去读所有 jar 里的 AutoConfiguration.imports 文件。
2. OrderService.createOrder()（带 @Transactional）内部用 this.updateStock() 调用同类里带 REQUIRES_NEW 的方法，结果是？
正确答案：事务失效、合并进同一个事务。this 指向原始对象而非 Spring 生成的代理，切面根本没机会执行。解法是注入自己（@Lazy）或拆成两个 Bean。
3. Spring 三级缓存里，能够"按需生成 AOP 代理对象"的是哪一级？
正确答案：三级缓存 singletonFactories。它存的是 ObjectFactory，调用 getObject() 时才生成代理；生成的结果会提升到二级缓存。一级缓存只放完全初始化好的单例。
4. @Transactional 方法抛出一个 IOException（受检异常），默认行为是？
正确答案：不回滚，直接提交。默认只对 RuntimeException 和 Error 回滚。要受检异常也回滚必须显式写 rollbackFor = Exception.class——这是被坑最多的场景。
5. 同一份 jar，在启动目录放了 application.yml，jar 内也有一份。最终生效的是？
正确答案：外部优先。外部配置（命令行 > 环境变量 > jar 外 > jar 内）就是为了"同一份制品跑在不同环境"。注意位置是 jar 同目录或 ./config/ 子目录，放 classpath 里无效。
6. Spring Boot 2.6 及以后，项目里存在循环依赖，默认会发生什么？
正确答案：默认启动失败（spring.main.allow-circular-references 默认 false）。这是官方逼你改设计。解法是 setter/字段注入、@Lazy 或拆 Bean，而不是把开关打开。
