模块 1

所有权：没有 GC，也没有手动 free

Rust 回答的是一个很具体的问题：一块堆内存，什么时候释放，由谁负责？答案是"由唯一的所有者负责，所有者离开作用域就释放"。

三条规则

每个值都有且只有一个所有者（owner）。
同一时刻只能有一个所有者。
所有者离开作用域时，值被 drop（调用析构并释放内存）。

move 发生的三个时机

// ① 赋值
let a = String::from("x");
let b = a;              // a 被 move 到 b，a 之后不可用

// ② 传参（按值传递）
fn take(s: String) {}
let c = String::from("y");
take(c);                 // c 被 move 进函数，函数结束时 drop

// ③ 返回（把所有权交出去）
fn make() -> String { String::from("z") }
let d = make();         // 返回值把所有权交给调用方
为什么需要 move 而不是拷贝？因为 String 在栈上只有一个"指针 + 长度 + 容量"，真正的字符数据在堆上。如果赋值时做浅拷贝，两个变量会指向同一块堆内存，离开作用域时就会 double free。Rust 的选择是：直接把源变量作废，从根上消除二次释放。

Copy 与 Clone 的分界

类型赋值时原因
i32 / f64 / bool / charCopy，两个变量都可用全部在栈上，固定大小，位复制就是完整复制
&T（共享引用）Copy引用本身就是个地址，复制地址不产生所有权问题
String / Vec / BoxMove持有堆内存，复制会产生两个所有者
&mut T不是 Copy可变引用必须独占，复制会破坏独占性
// 需要两份堆数据时，显式 clone（深拷贝，有成本）
let a = String::from("x");
let b = a.clone();      // 堆上复制一份，a 和 b 都可用

// 函数想"用一下但不拿走"，用引用
fn len(s: &String) -> usize { s.len() }
let c = String::from("hello");
let n = len(&c);          // 借出去，c 仍然可用

部分 move 与 Drop 顺序

struct P { name: String, age: u32 }
let p = P { name: "a".into(), age: 1 };
let n = p.name;         // 只移走 name 字段
// println!("{:?}", p);  // ✗ p 已被部分移走，整体不能再用
println!("{}", p.age);   // ✓ 未移走的字段还能用

// 局部变量按声明逆序 drop；结构体字段按声明顺序 drop
实现了 Drop 的类型不能部分 move。因为 drop 时需要访问完整对象，编译器会直接拒绝。这是"我只想拿走一个字段"时报错的真正原因，不是借用检查器在刁难你。
模块 2

借用与生命周期：为什么这条规则能消灭数据竞争

一条规则，两个方向

// 同一时刻，要么有任意多个 &T，要么有唯一一个 &mut T，二者不能共存

let mut v = vec![1, 2, 3];
let a = &v;          // 共享借用
let b = &v;          // 再来一个共享借用，没问题
// let c = &mut v;   // ✗ 已有共享借用，不能再可变借用
println!("{:?} {:?}", a, b);

// a、b 最后一次使用之后，借用就结束了（NLL），此时可以可变借用
let c = &mut v;
c.push(4);
为什么这条规则能消灭数据竞争？数据竞争需要三个条件同时成立：① 两个执行流；② 至少一个在写；③ 没有同步。"共享不可变、可变不共享"在编译期就排除了 ①+② 的组合 —— 只要存在可变借用，就不可能有第二个引用指向同一块数据。跨线程时再由 Send / Sync 把这条规则延伸到线程边界，于是数据竞争在安全代码里根本无法表达。

NLL：借用结束于最后一次使用

// Rust 2018 起（NLL），借用不再持续到作用域末尾，而是到最后一次使用
let mut s = String::from("hi");
let r = &s;
println!("{}", r);      // r 最后一次使用
s.push_str("!");        // ✓ 此刻 r 的借用已经结束

// 但如果是这样，就会报错：
let r = &s;
s.push_str("!");        // ✗ cannot borrow as mutable
println!("{}", r);      // r 后面还要用，借用仍然活着

生命周期标注：什么时候必须写

// 编译器无法推断"返回的引用来自哪个参数"时，必须标注
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

// 只有一个引用参数时，省略规则自动处理，不用写
fn first(s: &str) -> &str { &s[..1] }
// 等价于 fn first<'a>(s: &'a str) -> &'a str

// 方法里 &self 优先：返回值默认绑定到 self 的生命周期
impl Foo {
    fn name(&self) -> &str { &self.name }
}
场景要不要标注
函数只有一个引用参数，返回引用不用，省略规则自动绑定
函数有多个引用参数，返回引用必须，否则编译器不知道返回的引用依赖谁
方法返回 &self 的字段不用，默认绑定到 self
结构体持有引用必须给结构体加生命周期参数
返回 &'static str（字面量）写 'static，表示活到程序结束
生命周期标注不改变任何东西的存活时间。它只是向编译器描述多个引用之间的关系，让编译器能验证"返回的引用不会比它指向的数据活得更久"。如果标注之后仍然报错，说明你的设计里确实存在悬垂引用的可能，该改的是数据的所有权结构，不是继续加 'a。
最常见的报错长这样：cannot borrow `x` as mutable because it is also borrowed as immutable。翻译成人话是"你手上还攥着一个不可变引用，不能同时再要一个可变引用"。先找到那个引用最后一次被使用的位置，通常把那段代码挪到一个块里就能解决。
模块 3

Result 与 ?：把错误当成值

// Result 就是个枚举，没有异常、没有隐式栈展开
enum Result<T, E> { Ok(T), Err(E) }

fn parse(s: &str) -> Result<i32, std::num::ParseIntError> {
    s.parse::<i32>()
}

? 做了两件事

fn read_port(path: &str) -> Result<u16, Box<dyn std::error::Error>> {
    let text = std::fs::read_to_string(path)?;   // ① 出错就提前 return Err
    let port = text.trim().parse::<u16>()?;      // ② 顺带做 From 转换
    Ok(port)
}

// ? 展开后大致等价于：
// match expr {
//     Ok(v)  => v,
//     Err(e) => return Err(From::from(e)),
// }

// 关键点：From::from(e) 意味着函数返回的错误类型必须能"接住"这个错误
// io::Error 和 ParseIntError 都能转成 Box<dyn Error>，所以上面能编译
错误类型选择适合代价
Box<dyn Error>应用层、脚本、原型类型被擦除，不能按具体类型分支；有一次堆分配
自定义 enum库、需要调用方精确处理的场景要手写 Display、Error、From，样板代码多
thiserror库：用 derive 自动生成上面那堆样板多一个依赖，但几乎是社区标准
anyhow应用：带上下文的动态错误同样不能按类型分支，适合"只往上抛"的场景
// 自定义错误的标准结构
#[derive(Debug)]
enum AppError {
    Io(std::io::Error),
    BadPort(u16),
}

impl std::fmt::Display for AppError {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result {
        match self {
            AppError::Io(e) => write!(f, "io: {}", e),
            AppError::BadPort(p) => write!(f, "bad port: {}", p),
        }
    }
}

impl std::error::Error for AppError {}

// 实现 From，? 才能自动转换
impl From<std::io::Error> for AppError {
    fn from(e: std::io::Error) -> Self { AppError::Io(e) }
}

unwrap 的使用边界

场景可以用吗
测试代码、示例可以。失败就该让测试挂掉
原型、一次性脚本可以。先跑通再说
逻辑上不可能失败（如解析常量）用 expect 并写清理由，比 unwrap 好排查
处理外部输入、网络、文件不可以。这是正常失败路径，必须传播
库的公开 API不可以。让调用方决定怎么处理
// unwrap：失败时 panic，信息只有 Debug 输出
let n: i32 = "42".parse().unwrap();

// expect：失败时带上你的说明，排查快得多
let n: i32 = "42".parse().expect("配置项 port 必须是数字");

// Option 也能用 ?，None 时提前返回 None
fn first_char(s: &str) -> Option<char> {
    let c = s.chars().next()?;
    Some(c)
}
unwrap 在 release 下不会消失，它就是 panic!。很多从 Go/Java 过来的人误以为它像 assert 一样在发布版被裁掉。一个 unwrap 就是一条"这里出错就整个线程崩溃"的声明，在服务端代码里尤其危险（默认 panic 会 unwinding 整个线程，若在 panic = "abort" 下则直接终止进程）。
main 也可以返回 Result： 
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let n: i32 = "42".parse()?;
    println!("{}", n);
    Ok(())
}
这样 ? 在 main 里也能用，出错时打印 Debug 信息并以非零码退出。
模块 4

trait 与泛型：静态分发和动态分发差在哪

trait Shape {
    fn area(&self) -> f64;

    // 默认方法：可以不实现
    fn describe(&self) -> String {
        format!("area = {:.2}", self.area())
    }
}

struct Circle { r: f64 }
impl Shape for Circle {
    fn area(&self) -> f64 { 3.14159 * self.r * self.r }
}

两种写法的本质区别

// 静态分发：编译期为每个具体类型生成一份代码（单态化）
fn print_area<T: Shape>(s: &T) {
    println!("{}", s.area());
}

// 动态分发：运行时通过 vtable 找方法
fn print_dyn(s: &dyn Shape) {
    println!("{}", s.area());
}

// where 子句：约束多的时候比尖括号好读
fn run<T>(s: T) where T: Shape + Send + 'static { }
维度静态分发 T: Trait动态分发 dyn Trait
调用开销直接调用，可内联一次 vtable 间接跳转，通常阻止内联
内存表示零开销，就是具体类型胖指针：数据指针 + vtable 指针，16 字节
代码体积膨胀：每个类型一份只有一份
编译速度更慢（单态化要展开）更快
能否异构集合不能，Vec<T> 只能装一种能，Vec<Box<dyn Trait>>
"dyn 一定更慢"是个过度简化。真正的差距在能不能内联：静态分发下 area() 可能被完全内联成几条乘加指令；动态分发则必须真的跳一次。但在"每次调用都要做几十微秒 IO"的场景里，这一次跳转完全不可见。先按可读性选，热路径再用 benchmark 决定。

孤儿规则：为什么不能给别人的类型实现别人的 trait

// 允许：trait 是你定义的
impl MyTrait for Vec<u8> {}

// 允许：类型是你定义的
impl std::fmt::Display for MyType {}

// 不允许：trait 和类型都是别人的
// impl std::fmt::Display for Vec<u8> {}
// error[E0117]: only traits defined in the current crate can be implemented
//               for types defined outside of the crate

规则：impl Trait for Type 里，trait 和 type 至少要有一个是当前 crate 定义的。否则两个库各自给 Vec<u8> 实现 Display，下游同时依赖这两个库时，编译器无法确定用哪一份实现 —— 这就是所谓的"实现冲突"。孤儿规则用一条编译期限制，换掉了整个生态的链接期灾难。

绕过孤儿规则的唯一正当方式是 newtype：用一个本地定义的单字段元组结构体把外部类型包起来，再给这个新类型实现 trait。 
struct Wrapper(Vec<u8>);   // 本地类型
impl std::fmt::Display for Wrapper { /* ... */ }
代价是每次访问内部值都要 .0，但它是零开销的（编译后完全消失）。
选择标准：如果"每个实现类型只可能有一种对应关系"，用关联类型（如 Iterator::Item）；如果"同一类型可能有多组对应关系"，用泛型参数（如 From<T>）。用错了的直接后果是调用处必须写类型标注，或者编译器报 "type annotations needed"。
模块 5

智能指针：五种工具，各管一件事

类型解决什么线程安全运行时开销
Box<T>把值放到堆上；递归类型；trait object取决于 T一次分配，无额外元数据
Rc<T>单线程共享所有权（引用计数）否（!Send / !Sync）计数 +1/-1，非原子
Arc<T>多线程共享所有权（原子引用计数）是（T: Send + Sync 时）原子操作，比 Rc 略贵
RefCell<T>内部可变性，借用检查从编译期挪到运行期否运行时计数，违规 panic
Mutex<T>跨线程的内部可变性，锁 + 数据绑定是系统锁，可能阻塞

Rc / Arc：共享所有权

use std::rc::Rc;
use std::sync::Arc;

let a = Rc::new(String::from("shared"));
let b = Rc::clone(&a);        // 计数 1 → 2，只加计数不复制数据
println!("{}", Rc::strong_count(&a));   // 2
drop(b);                       // 计数回到 1

// 多线程用 Arc；Rc 跨线程会直接编译失败（不是运行时出错）
let shared = Arc::new(vec![1, 2, 3]);
let h = std::thread::spawn({
    let s = Arc::clone(&shared);
    move || println!("{:?}", s)
});
h.join().unwrap();

RefCell：把借用检查推迟到运行期

use std::cell::RefCell;

let cell = RefCell::new(5);
*cell.borrow_mut() += 1;        // 运行时登记一个可变借用
println!("{}", cell.borrow());  // 5 + 1 = 6

// 同时持有可变和不可变借用 → 运行时 panic，不是编译错误
let m = cell.borrow_mut();
// let r = cell.borrow();       // panic: already mutably borrowed
drop(m);                       // 释放后才可以再借
RefCell 把编译期错误变成了运行时 panic。它的价值在于某些结构（图、双向链表、观察者）在编译期确实无法表达"运行时才知道的借用关系"。但它不是"绕过借用检查器"的万能钥匙 —— 一旦你在热路径上用它，就要接受"可能 panic"和"每次 borrow 都有计数开销"这两个代价。

Rc<RefCell<T>> 到底是什么意思

// 从外到内读：Rc 提供"多处共享"，RefCell 提供"共享之后还能改"
use std::rc::Rc;
use std::cell::RefCell;

let shared = Rc::new(RefCell::new(vec![1, 2, 3]));
let a = Rc::clone(&shared);
let b = Rc::clone(&shared);

a.borrow_mut().push(4);        // 通过 a 修改
println!("{:?}", b.borrow());  // 通过 b 能看到 [1, 2, 3, 4]

// 多线程版本：Arc<Mutex<T>> 或 Arc<RwLock<T>>
// 注意 Mutex 会阻塞，RefCell 会 panic —— 语义不同
Rc 的循环引用会泄漏。A 持有 B 的 Rc，B 持有 A 的 Rc，两个计数永远不归零，析构永远不执行。解法是用 Weak<T> 打破其中一条边：Weak 不增加强引用计数，用 upgrade() 取回 Option<Rc<T>>，对象已释放时得到 None。父节点持子节点的 Rc、子节点持父节点的 Weak，是最常见的树/图结构写法。
模块 6

异步：Future 是惰性的，运行时是必需品

pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> { Ready(T), Pending }
Future 是惰性的：创建一个 Future 不会执行任何东西。 
let f = async { println!("run"); };   // 什么都没打印
// 必须 poll 或 .await 才会真正开始
这和 JavaScript 的 Promise 完全不同 —— Promise 一创建就开始跑。Rust 的 Future 只是一份"待执行的状态机描述"。

async/await 编译成了什么

// 源码
async fn fetch(id: u32) -> String {
    let a = step1(id).await;
    let b = step2(a).await;
    b
}

// 大致等价于一个手写的状态机（编译器生成）
enum Fetch {
    Start { id: u32 },
    WaitStep1 { fut: Step1 },
    WaitStep2 { fut: Step2 },
    Done,
}
// 每个 .await 就是一个状态；poll 时按当前状态推进，遇到 Pending 就保存现场返回

// 状态机的大小 = 所有状态里最大的那个，所以递归 async fn 必须装箱
// fn rec(n: u32) -> impl Future { async move { rec(n-1).await } }
// ✗ 编译错误：递归类型无限大 → 改成 Box::pin(rec(n-1))
角色谁提供做什么
Executortokio / async-std / smol不断 poll 任务，Ready 就结束，Pending 就挂起等唤醒
Reactor运行时把 epoll/kqueue 事件翻译成 Waker 唤醒
Timer运行时sleep、timeout 需要它，标准库没有
// 标准库只有 Future trait，没有运行时。所以必须引入 tokio 之类
#[tokio::main]
async fn main() {
    let body = reqwest::get("https://example.com").await.unwrap()
        .text().await.unwrap();
    println!("{}", body.len());
}

// #[tokio::main] 展开后大致是：
// fn main() { tokio::runtime::Runtime::new().unwrap().block_on(async { ... }) }

三个必须知道的边界

不要阻塞 executor
std::thread::sleep、同步文件 IO、CPU 密集计算都会占住 worker 线程，让同一线程上的其他任务饿死。用 tokio::task::spawn_blocking 或 spawn_blocking + rayon
不要跨 await 持锁
std::sync::MutexGuard 不是 Send，跨 await 持有会编译失败。就算换成 tokio::sync::Mutex，也要尽量缩短持锁区间，否则并发度归零
Future 可能不是 Send
多线程运行时要求 Future: Send。持有 Rc、RefCell 或裸指针跨 await，都会让整个 Future 变成 !Send
异步不等于更快。它解决的是"大量并发连接下，线程栈和上下文切换太贵"的问题。如果只是几个并发任务，同步阻塞代码更简单也更快；如果是 CPU 密集，异步毫无帮助，该用多线程或 SIMD。异步的收益只在 IO 密集 + 高并发这个交集里成立。
模块 7

三个高频报错，怎么读、怎么改

① 一边遍历一边修改

let mut v = vec![1, 2, 3];
for x in &v {
    v.push(*x);       // ✗ cannot borrow `v` as mutable
}                     //   because it is also borrowed as immutable

// 原因：for 循环持有 v 的不可变借用，整个循环期间都活着

// 改法一：先收集到新集合
let extra: Vec<i32> = v.iter().copied().collect();
v.extend(extra);

// 改法二：用索引，每次只借用一瞬间
for i in 0..v.len() {
    let x = v[i];
    v.push(x);
}
// 注意：这样会无限增长，实际要限制范围

读法：错误信息里 first borrow occurs here 指向借用开始的位置，second borrow occurs here 指向冲突的位置，borrow later used here 告诉你第一个借用为什么还活着。三个位置连起来看，问题基本就清楚了。

② 闭包捕获了什么

let s = String::from("hi");

let f = || println!("{}", s);   // 按引用捕获 &s
f();

let g = move || println!("{}", s);  // 按值捕获，s 被移进闭包
// println!("{}", s);            // ✗ s 已经被移走

// 三个 trait 对应三种能力，编译器自动选最小的那个
// FnOnce：只能调用一次（会消耗捕获的值）
// FnMut ：可以多次调用，可能修改捕获的值
// Fn    ：可以多次调用，不修改捕获的值

fn call<F: Fn()>(f: F) { f(); }        // 要求不消耗、不修改
fn call_once<F: FnOnce()>(f: F) { f(); }
Rust 2021 起闭包是"精确捕获"的：只捕获实际用到的字段，而不是整个结构体。这让很多以前会冲突的代码能编译了。但 move 仍然是整体 move，如果你只想移一个字段，先在闭包外用 let 拆出来。

③ Send / Sync 报错怎么读

// 典型报错
// error: future cannot be sent between threads safely
//    = help: the trait `Send` is not implemented for `Rc<String>`
//    = note: held across an await point

// 读法分三步：
// 1. 找到 "not implemented for XXX" —— XXX 就是罪魁祸首
// 2. 看 "held across an await point" —— 说明它活过了 .await
// 3. 把它挪到 await 之前 drop 掉，或换成 Send 的等价类型

// 常见替换：Rc → Arc，RefCell → Mutex，&T → Arc<T>

// 自己判断：Send = 可以安全地把所有权移到另一个线程
//          Sync = 可以被多个线程同时持有 &T
// 绝大多数类型自动实现；裸指针、Rc、RefCell 不满足
不要用 unsafe 硬绕。unsafe impl Send for MyType {} 是你在向编译器担保"这个类型跨线程绝对安全"。担保错了的后果是数据竞争，而且是那种压测跑一万次都不出现、上线后随机崩的竞争。先尝试改数据结构，实在不行再考虑 unsafe，并且要写清 Safety 注释。
模块 8

为什么编译慢：四个真实原因

原因机制缓解
单态化泛型为每个具体类型生成一份机器码，Vec<u8> 和 Vec<String> 各一份，serde_json 一类的库会被展开几十次用 dyn Trait 替代泛型；把泛型函数抽到独立 crate 减少重复展开
宏展开derive(Serialize, Deserialize) 会在编译期为每个结构体生成大量代码，过程宏还要单独编译一个 proc-macro crate减少不必要的 derive；把重宏的类型集中到一个 crate
LLVM 优化opt-level 越高越慢；codegen-units 越小优化越彻底但越慢；LTO 会把所有 crate 的 IR 合起来再优化开发用 opt-level = 0；发布才开 LTO
依赖数量每个依赖都要完整编译一遍，且默认并行度受核数限制cargo tree 看依赖树；cargo build --timings 找瓶颈
# 看每个 crate 的编译耗时，生成 HTML 报告
cargo build --timings

# 开发时关掉优化、保留增量编译（dev profile 默认就是）
# Cargo.toml
[profile.dev]
opt-level = 0
incremental = true

# 发布时用更激进的设置（编译更慢，运行更快）
[profile.release]
opt-level = 3
lto = "thin"          # fat 更慢但可能更快；thin 是折中
codegen-units = 1     # 单单元，优化最彻底，编译最慢
增量编译的边界：incremental 只对"小改动"有效，改了公共依赖或 profile 设置就会全量重编。而且 release 默认关闭增量编译（因为会影响优化效果）。所以"改一行等三分钟"通常发生在 release 构建或依赖大改之后，不是 Rust 本身慢。
不要为了编译速度把 codegen-units 调到很大。它确实能并行加速编译，但会限制跨单元优化，运行时性能可能下降 5%~15%。正确的做法是：dev 用默认，release 用 1，而不是全局改一个值。
常见坑

十个从"能编译"到"能上线"之间的坑

1
用 unwrap 处理用户输入和网络返回
unwrap 就是 panic，release 下也不会消失。一个畸形请求就能让处理线程崩溃，在 panic=abort 下甚至直接终止进程。
2
在 async 任务里调用阻塞函数
std::thread::sleep、同步文件 IO、CPU 密集计算都会占住 executor 的 worker 线程，同一线程上的其他任务全部饿死。用 spawn_blocking 隔离。
3
跨 await 持有 std::sync::MutexGuard
它不是 Send，多线程运行时下直接编译失败。就算改用 tokio::sync::Mutex，长时间持锁也会把并发度压成 1。
4
Rc 互相持有形成环
强引用计数永远不归零，析构永远不执行，内存静默泄漏。树/图结构里父持子用 Rc、子持父用 Weak。
5
借用检查不过就到处 clone
clone 能立刻让编译器闭嘴，但每次都是真实的堆分配和内存复制。热路径上几个 clone 就能把性能打回 GC 语言的水平。
6
用 RefCell 绕过借用检查
编译期错误变成运行时 panic，而且每次 borrow 都有计数开销。它适合图结构，不适合当"万能可变容器"。
7
对 String 做字节切片
&s[0..2] 切在多字节字符中间会直接 panic。中文、emoji 场景必踩。用 char_indices 或 chars 处理。
8
依赖 release 下的整数溢出行为
debug 下溢出 panic，release 下静默回绕（除非开 overflow-checks）。同一份代码两种行为，测试环境永远发现不了。
9
用 unsafe impl Send/Sync 硬绕编译错误
这是在向编译器担保"跨线程绝对安全"。担保错了就是数据竞争，压测一万次不出现，上线随机崩。
10
所有错误都塞进 Box<dyn Error>
类型被擦除，调用方无法用 downcast 之外的方式按类型分支，也没法针对不同错误做不同重试策略。库的公开 API 应该用具体错误类型。
自测

六道题

1. let b = a; 之后（a 是 String），a 还能用吗？
正确答案：不能。String 持有堆内存，浅拷贝会产生两个所有者并导致 double free，所以 Rust 让源变量失效。要两份就 clone，只借用就传引用。
2. 为什么同一时刻不能既有 &T 又有 &mut T？
正确答案：排除数据竞争。竞争需要"两个执行流 + 至少一个写 + 无同步"，而"存在可变借用"就意味着"不存在其他引用"，组合条件在类型层面不成立。
3. 生命周期标注 'a 的作用是？
正确答案：描述关系。标注不改变运行时行为，只是给借用检查器的约束。标注后仍报错，说明设计里确实有悬垂风险，该改的是所有权结构。
4. fn f<T: Trait>(x: &T) 与 fn f(x: &dyn Trait) 的关键差别是？
正确答案：单态化 vs 动态分发。静态分发零开销但膨胀、编译慢；动态分发只有一份代码、支持异构集合，代价是一次间接调用和胖指针。
5. Rc<RefCell<T>> 表达的是什么？
正确答案：共享 + 内部可变。Rc 负责"多处持有"，RefCell 负责"共享之后还能改"，代价是借用检查挪到运行期。多线程对应 Arc<Mutex<T>>。
6. 为什么 Rust 的 async 必须配一个运行时（如 tokio）？
正确答案：标准库只有 trait。Future 是惰性的状态机，需要有人 poll、需要 IO 就绪时唤醒、需要定时器。这些都不在 std 里。
