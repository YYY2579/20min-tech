开始前

先建立坐标系

运行时的核心决策只有三个：代码怎么变成机器码（解释 / JIT / AOT）、内存谁回收、何时暂停（GC / 引用计数 / 手动）、并发怎么调度（OS 线程 / 协程 / 单线程事件循环）。后面所有差异都是这三个选择的下游。

# 确认本机四个运行时的版本
java -version          # JDK 17 / 21 LTS 最常见
node -v                # V8 版本：node -p process.versions.v8
python3 -V             # 3.11+ 有特化解释器；3.13 有实验性 JIT 与无 GIL 版本
go version             # 1.22+ 修了循环变量捕获；1.21+ 有 PGO
两个提醒：① 下文所有数字是典型量级，会随版本、硬件、堆大小变化，用做对比和排障参考，不是精确基准；② 本文讲的是运行时机制，不涉及某个语言的具体语法。
模块 1

JVM：内存区域、类加载、JIT 与 GC

运行时数据区（JDK 8 及以后）

区域存什么关键点
堆 Heap对象实例和数组。GC 的主战场分代：Eden : Survivor(S0/S1) : Old 默认 8 : 1 : 1（-XX:NewRatio=2）。默认上限约为物理内存的 1/4，容器里务必用 -XX:MaxRAMPercentage 管住
Metaspace类元数据（替代 JDK7 的 PermGen）占用宿主机本地内存，默认无上限，必须配 -XX:MaxMetaspaceSize 防止吃光内存
虚拟机栈栈帧：局部变量表、操作数栈、返回地址默认 -Xss 512K~1M（平台相关）。递归过深抛 StackOverflowError
本地方法栈native 方法栈帧JNI 调用链在这里
PC 寄存器当前线程执行的字节码行号每个线程私有
CodeCacheJIT 编译后的机器码满时停止编译（flushed），-XX:ReservedCodeCacheSize
直接内存NIO ByteBuffer 的堆外内存不受堆大小限制，靠 -XX:MaxDirectMemorySize 控制；GC 只能间接回收

类加载：五步与双亲委派

加载：字节流 → Class 对象（不限于 class 文件，也可以从网络、加密文件生成）
验证：文件格式、元数据、字节码、符号引用校验，防止恶意字节码
准备：为静态变量分配内存并赋零值（不是代码里的初始值，final 常量除外）
解析：符号引用 → 直接引用
初始化：执行 <clinit>()，真正运行静态赋值和静态块。类的初始化是线程安全的，且只做一次

三类加载器构成双亲委派链：Bootstrap（C++ 实现，加载 rt 包核心类）→ Platform（JDK 9+ 合并了 Extension）→ Application（classpath）。一个类加载请求先委派父级，父级找不到才自己加载。同一份 class 被不同加载器加载 = 两个不同的类——Tomcat 的 webapp 隔离、热部署都靠打破委派实现（JDK 9+ 由 Thread.getContextClassLoader 配合）。

JIT：C1 与 C2

编译器定位说明
C1快速编译（tier 1-3）编译快、优化少，尽快让热点方法脱离解释执行
C2极致优化（tier 4）编译慢但优化激进，峰值吞吐的主要来源
分层编译两者混用（默认）方法先解释 → C1 → 够热再 C2；OSR（栈上替换）让循环热点也能被替换

C2 的招牌优化：方法内联（消除调用开销，是其他优化的基础）、逃逸分析（对象不逃逸就栈分配/标量替换，省掉堆分配和 GC 压力）、锁消除（逃逸分析发现无竞争则去掉同步）。代价是去优化（deopt）：假设"这个调用点只有一种类型"被后续代码打破，就退回解释或重新编译——写多态混乱的热点代码等于反复触发 deopt。

GC：分代假说与收集器谱系

分代建立在两个假说上：绝大多数对象朝生夕死（弱分代假说 → 新生代用复制算法）、熬过越多次 GC 的对象越难死（强分代假说 → 老年代用标记-清除/整理）。

收集器暂停特性说明
Serial / Serial OldSTW，年轻/老年代都用单线程，客户端模式；简单场景几十毫秒级
Parallel ScavengeSTW吞吐优先，JDK 8 服务端默认组合
CMS并发标记，停顿较短标记-清除，有内存碎片；JDK 14 已移除，别用了
G1目标可设，默认 -XX:MaxGCPauseMillis=200JDK 9+ 默认。堆切 region，混合回收；单 region 超过 50% 即 humongous 大对象，分配慢且难回收
ZGC目标 <10ms，实测通常亚毫秒着色指针 + 读屏障，支持 TB 级堆，JDK 15 起生产可用
Shenandoah与 ZGC 同级Brooks 转发指针，Red Hat 主导，OpenJDK 可用
# JDK 21 + 16G 容器内存的生产组合
java -XX:+UseZGC \
     -XX:MaxRAMPercentage=75 \
     -XX:InitialRAMPercentage=50 \
     -XX:MaxMetaspaceSize=512m \
     -Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=100m \
     -jar app.jar
容器里的 JVM 是最经典的坑：JDK 8 的 JVM 看不到 cgroup 限制，-Xmx 不设时按宿主机内存算，容器 limit 2G 它敢开到 8G，直接被 OOM Killer 杀掉。JDK 10+ 支持 UseContainerSupport，但正确姿势仍是显式配 -XX:MaxRAMPercentage，并给系统和直接内存留 25%。
模块 2

V8：隐藏类、内联缓存与分代 GC

隐藏类（Hidden Class / Map）

V8 在运行时给每个对象关联一个隐藏类，描述它的属性布局。属性访问走的是"固定偏移"，像 C++ struct 一样快——前提是对象结构稳定。

// 反模式：动态增删属性，每次加属性都引发隐藏类转换链跳变
const o = {};
o.a = 1;            // 隐藏类 C0 → C1
o.b = 2;            // C1 → C2
delete o.a;        // ✗ 直接退化成字典模式（慢一个量级）

// 正模式：构造函数里一次性初始化所有字段，保持结构一致
class Point {
  constructor(x, y) { this.x = x; this.y = y; }   // 所有实例同一条转换链
}
// 推论：热路径上的对象，字段顺序和数量要一致；别用对象当"可扩展字典"

内联缓存（IC）

状态含义性能
Monomorphic调用点只见过的 1 种隐藏类最快：一次类型检查 + 直接偏移访问
Polymorphic2~4 种隐藏类线性比几次，仍可接受
Megamorphic5 种以上或不可知最慢：走全局 megamorphic stub cache，哈希查找

数组同理：元素种类（element kind）从 PACKED_SMI → PACKED_DOUBLE → PACKED 一路退化，开洞（holey）后再想紧凑回去，V8 不会帮你做。const a = [1,2,3]; a[100]=4; 这类写法会让整条热路径退化。

四级执行管线

层角色
Ignition解释器，直接执行字节码。启动快靠它
Sparkplug基线编译器（V8 9.1+），字节码快速转机器码
Maglev中层优化编译器（Chrome 117+），介于基线和 TurboFan
TurboFan顶层优化编译器，图-based 优化。假设被打破时去优化（deopt）

GC

新生代用 Semi-space 复制（Scavenger）：对象先分配在 from 空间，活对象复制到 to，两个 semi-space 交换；熬过两次 GC 晋升老年代。老年代用标记-清除-整理，配合并发标记（增量标记 + 写屏障）减少停顿。大对象直接进老年代（大对象空间），超过限制（默认单对象 > 256KB 量级，依版本）直接分配失败。Node 进程默认堆上限约 2GB（64 位），超了先 OOM 而不是慢慢涨——调 --max-old-space-size 或从根本上少建对象。

# Node 排查三件套
node --max-old-space-size=4096 app.js   # 放宽老生代上限
node --trace-gc app.js                  # 打印每次 GC 的类型与耗时
node --trace-deopt app.js               # 打印去优化点，找热点代码的类型不稳定
# 或者直接生成堆快照离线分析：node --heapsnapshot-near-heap-limit=3 app.js
V8 的性能是"惯"出来的，不是"配"出来的：同样的算法，结构稳定的对象 + 类型单一的数组 + 少分配临时对象，可以差出 5~10 倍。遇到 JS 热点慢，先看 --trace-deopt 和隐藏类转换，再怀疑算法。
模块 3

CPython：GIL、引用计数与分代 GC

GIL：全局解释器锁

GIL 保证同一时刻只有一个线程在执行字节码。原因有二：CPython 的内存管理（引用计数）不是线程安全的，加一把大锁比细粒度锁简单得多；历史路径依赖延续至今。

场景多线程有效吗
IO 密集（网络、磁盘）有效：IO 操作会释放 GIL，线程可并行等待
CPU 密集（计算、编解码）无效：线程抢不到执行权，甚至更慢。用多进程（multiprocessing）

线程切换间隔由 sys.getswitchinterval() 控制，默认 5ms。间隔调大减少切换开销，调大响应延迟；反之亦然，一般不用动。3.13 引入了无 GIL 的自由线程构建（PEP 703，实验性），这是 CPython 三十年来最大的一次并发模型松动，但生态扩展需要重新编译适配，短期生产仍按"有 GIL"设计。

引用计数 + 分代 GC

# 引用计数：对象头里的 ob_refcnt，归零立即释放
import sys
a = [1, 2, 3]
sys.getrefcount(a)      # 当前引用数（含 getrefcount 自己那次）

# 致命盲区：循环引用，双方引用计数永远到不了 0
class Node:
    def __init__(self):
        self.parent = None
        self.child  = None

a = Node(); b = Node()
a.child = b; b.parent = a    # 互相引用，引用计数清不掉 → 必须靠分代 GC

# 分代 GC：默认三代，阈值 700 / 10 / 10
import gc
gc.get_threshold()      # (700, 10, 10)：gen0 分配 700 次触发一次，逐级晋升
gc.collect()            # 手动全量回收，返回不可达对象数
gc.freeze()             # fork 前冻结现有对象，避免 copy-on-write 失效

分代 GC 是 STW 的：回收期间所有线程挂起。平时 gen0 很快（微秒~毫秒级），但大堆 + 大量长生命周期对象时一次 gen2 全量回收可能到几十甚至上百毫秒。服务进程内存只涨不降，先怀疑循环引用或缓存无上限，用 gc.set_debug(gc.DEBUG_SAVEALL) 或 objgraph 定位。

另一个常见坑：引用计数让"大对象延迟释放"变得隐蔽——del 一个对象只是减计数，任何角落的引用（闭包、异常 traceback、缓存）都会让它继续占内存。tracemalloc + objgraph.show_backrefs() 是排查内存泄漏的标准组合。

解释器性能的拐点

3.11 引入特化自适应解释器（PEP 659）：热点字节码在运行时被替换为针对实际类型的特化指令，典型负载比 3.10 快 10%~60%，且不需要 JIT——把"预热"逻辑做进了解释器。3.12/3.13 继续改进并加入实验性 JIT（PEP 744）。但 CPython 的天花板仍在：纯计算密集型场景通常比 C 慢 10~50 倍，重计算下沉到 C 扩展 / NumPy / Cython 是标准姿势。

模块 4

Go：GMP 调度与三色标记 GC

GMP 调度模型

角色含义关键点
Ggoroutine（用户态协程）初始栈仅 2KB，按需扩容，64 位上限 1GB。创建成本几百纳秒，单进程跑几十万个很常见
MOS 线程（machine）由 runtime 管理，数量默认受 10000 上限约束
P逻辑处理器（processor）数量 = GOMAXPROCS，默认等于 CPU 逻辑核数。每个 P 带一个本地运行队列（默认 256）

调度逻辑：新建的 G 优先进当前 P 的本地队列，P 从本地队列取 G 交给 M 执行；本地空了去全局队列偷、去其他 P work-stealing；网络 IO 交给 netpoller 统一管理，goroutine 阻塞 IO 不占 OS 线程；M 因系统调用阻塞超过约 20μs，P 会被剥离交给其他 M（handoff）。1.14 起支持基于信号的异步抢占，死循环 goroutine 无法再饿死调度器。

三色标记 GC

标记开始：开启写屏障，STW 第一段（极短，微秒级）
并发标记：GC 协程与用户 goroutine 同时跑，把可达对象从白推到灰再推到黑；写屏障记录"黑对象引用了白对象"防止漏标
标记终止：STW 第二段（同样极短），重新扫描少量残余
并发清除：不遍历对象本身，按 span 元数据回收，与用户代码并行

Go 用混合写屏障（Dijkstra 插入屏障 + Yuasa 删除屏障，1.14 起）兼顾两者。暂停时间实测通常在 1ms 以下，堆到几百 GB 也能维持亚毫秒级——这是它适合延迟敏感服务的核心原因。代价是 GC 占用 CPU 目标 25%（GOGC=100 表示"堆涨到存活量的 2 倍就触发下一次"），内存换 CPU。

# Go 排查命令
GODEBUG=gctrace=1 ./app          # 每次 GC 的 STW、并发标记、辅助 GC 耗时全打印
GOMAXPROCS=4 ./app                # 限制逻辑处理器数（默认 = 逻辑核数）
GOGC=50 ./app                     # 更激进 GC，省内存；=off 完全关闭（危险）
go tool pprof http://localhost:6060/debug/pprof/heap   # 堆剖析（需 net/http/pprof）
Go 的 GC 快，不等于你可以随便分配：写屏障、辅助标记（assist）、GC 占用的 25% CPU 都是真实成本。高 QPS 服务里减少临时对象仍然是第一优化手段——GODEBUG=gctrace=1 看 GC 频率，sync.Pool 复用热点对象，别让 GC 周期变成固定背景负载。

对比的三种错误姿势：① 用冷启动数据比吞吐——JVM 是"起得慢、跑得久"的类型，服务跑几天后 C2 代码是全场最快的；② 用空进程比内存——JVM 的内存随负载和堆配置伸缩，要拿稳态 + 峰值比；③ 拿默认参数比 GC 暂停——G1 不调参、ZGC 不换，等于让选手穿拖鞋赛跑。任何基准测试先对齐参数和工作负载。
模块 6

跨语言调用：JNI、FFI 与 cgo

JNI：Java 调原生代码

// Java 侧声明 native 方法
public class NativeDemo {
    static { System.loadLibrary("demo"); }        // 加载 libdemo.so
    public native int add(int a, int b);
}

// C 侧实现，命名规则：Java_类全路径_方法名
#include <jni.h>
JNIEXPORT jint JNICALL
Java_NativeDemo_add(JNIEnv *env, jobject obj, jint a, jint b) {
    return a + b;
}

# 编译
gcc -shared -fPIC -I"$JAVA_HOME/include" -I"$JAVA_HOME/include/linux" demo.c -o libdemo.so

性能要点：每次跨越 JNI 边界都有成本（参数转换、引用表操作，通常在几十到上百纳秒级），且JIT 无法优化边界两边的代码。GetStringUTFChars / ReleaseStringUTFChars 这类成对操作必须配对，漏 Release 就是内存泄漏。对象引用分局部引用（自动管理但表有上限，大量循环里要 DeleteLocalRef）和全局引用（NewGlobalRef，需手动 DeleteGlobalRef）。现代替代：JDK 22+ 的 Foreign Function & Memory API（Panama 项目，JEP 454），纯 Java 调 C、无样板代码、且能和 JIT 更好地配合。

FFI：通用概念与 CPython 实践

FFI（Foreign Function Interface）指一门语言调用另一门语言编译出的 ABI。CPython 的三个选项：ctypes（标准库，零依赖，每次调用开销约微秒级，适合低频调用）、CFFI（API 模式预编译，CTA 级更快，适合热点）、Cython（把 Python 编译成 C 扩展，适合把热点函数整体下沉）。共同铁律：调用方不拥有 C 侧分配的内存，free 的责任要划清，否则泄漏或 double-free。

cgo：Go 调 C

// 紧挨 import "C" 的注释是 C 源码，编译期由 cgo 处理
package main

/*
#include <stdlib.h>
static int add(int a, int b) { return a + b; }
*/
import "C"
import "fmt"

func main() {
    r := C.add(C.int(1), C.int(2))   // 类型必须显式转换，没有隐式转换
    fmt.Println(r)
}

# 关闭 cgo：纯 Go 构建，静态链接、可交叉编译
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o app .
方案单次调用开销量级主要代价
JNI几十~上百 ns样板代码、引用管理、JIT 屏障
ctypes约 1μs无编译期检查，热点循环别用
CFFI(API)亚微秒需要构建步骤
cgo约 50~80ns依赖 gcc、拖慢编译、默认禁交叉编译、C 内存不进 GC
三条工程红线：① 别在 FFI 边界上做高频小调用——把数据批量化，一次传一批，而不是一次一个元素；② cgo 调用会阻塞 OS 线程（但 Go 运行时会做 handoff，不至于拖垮整个 P），C 函数里执行久的任务要考虑线程预算；③ 能不用 cgo 就不用（CGO_ENABLED=0 带来的纯静态二进制，对容器分发和安全面都是巨大优势），Go 侧替代品优先：net、os/exec 都不行时的最后手段才是 cgo，或用 21+ 的 purego / 系统调用。
模块 7

选 Runtime 的决策依据

延迟敏感的微服务 / Serverless
选 Go。冷启动 1~10ms、GC <1ms、内存占用低、静态二进制部署简单。函数计算场景冷启动排序：Go < V8 < CPython < JVM。
长跑的计算密集 / 企业后端
选 JVM。C2 峰值吞吐最高，生态（Kafka、Spark、ES、Hadoop）无可替代。接受启动慢、内存高，用 ZGC 治停顿。
脚本 / 数据科学 / AI 周边
选 CPython。库生态是决定性因素；CPU 密集部分下沉 C 扩展/NumPy；并发用多进程绕开 GIL。
Web 服务 / 前后端同构 / 边缘
选 Node（V8）。启动快、JSON 处理链最短、npm 生态最大；注意隐藏类稳定性与 --trace-deopt。

决策树（按约束倒推）

第一步：有没有硬性延迟/内存指标？有（P99 < 10ms、实例 < 128MB、Serverless 冷启动 < 100ms）→ 基本只剩 Go 和 V8，JVM 出局
第二步：负载是计算密集还是 IO 密集？计算密集（编解码、压缩、矩阵）且长跑 → JVM/Go；IO 密集（网关、代理、CRUD）→ 全家桶都行，看生态
第三步：团队和生态在哪？大数据/企业中间件 → JVM；数据/ML → CPython；前端团队全栈 → Node。切换运行时是组织决策，不只是技术决策
第四步：要不要复用某个语言的库？要 → 选那个 runtime + FFI/gRPC，别为了"性能"重写轮子
第五步：遗留系统怎么办？优先 进程间通信（HTTP/gRPC）而不是进程内 FFI——服务边界清晰、故障隔离、可独立伸缩，FFI 只用于确实压不下来的热点
一句话总结：JVM 用启动时间和内存换峰值吞吐；V8 用单线程的简单换开发效率和生态；CPython 用执行速度换生态和开发速度；Go 用一点峰值吞吐换部署简单和延迟确定性。没有更好的运行时，只有更匹配约束的运行时。
排雷

十个线上坑

1
容器里 JVM 不设 MaxRAMPercentage
JVM 按宿主机内存算堆，容器 limit 2G 它敢开 8G，被 OOM Killer 直接杀死。显式配 -XX:MaxRAMPercentage=75，JDK 8 老应用更要补 UseContainerSupport。
2
G1 堆里塞大对象
超过 region 一半即 humongous，分配慢、回收差、碎片多。大数组/大缓存改分片或堆外，别直接怼堆。
3
以为"分代 GC 一定快"
老年代 Full GC（Serial/CMS/Parallel Old）在大堆下是秒级 STW。延迟敏感就上 ZGC，别停留在"GC 就是卡一下"的认知。
4
V8 里动态增删对象属性
隐藏类转换链跳变，delete 直接退化字典模式，IC 变 megamorphic，热点接口慢一个量级。构造函数里一次初始化所有字段。
5
JS 数组混类型、开洞
[1,2,3] 里塞字符串，或 a[10000]=x 开大洞，元素种类退化不可逆。热路径数组保持同类型紧凑，别用稀疏数组当 Map。
6
CPython 用多线程做 CPU 密集计算
GIL 下多线程零加速甚至更慢。要么多进程（multiprocessing），要么把热点下沉 C 扩展/NumPy。IO 密集才用多线程。
7
Python 循环引用导致内存只涨不降
引用计数管不了互相引用。先 gc.collect() 验证，再用 objgraph/tracemalloc 定位持有者；缓存要有上限（functools.lru_cache 的 maxsize）。
8
goroutine 泄漏
channel 阻塞没有退出路径，goroutine 只增不减，最后 OOM。每个 goroutine 都要有退出条件（ctx.Done() / channel close），用 runtime.NumGoroutine() 做监控。
9
Go 1.22 前循环变量被闭包共享捕获
for 循环里 go func(){ use(i) }() 全是最后一个值。升级 1.22+（每次迭代新变量），或老版本手动 i := i。
10
为省事开 cgo
引入 gcc 依赖、编译慢十倍、不能交叉编译、C 内存泄漏难查。默认 CGO_ENABLED=0；纯 Go 替代不了再上，调用要批量化。
自测

六道题

1. JDK 9 及以后，服务端默认的垃圾收集器是？
正确答案：G1。它按 region 划分堆、混合回收，默认目标停顿 200ms（-XX:MaxGCPauseMillis）。ZGC 是 JDK 15 起生产可用的低延迟选项，目标停顿 <10ms（实测亚毫秒）。CMS 已在 JDK 14 移除。
2. ZGC 的设计目标停顿时间是？
正确答案：<10ms（实测通常亚毫秒）。靠着色指针 + 读屏障实现，支持 TB 级堆。注意"目标 <10ms"不等于"永远不卡"——大堆 + 极端负载下仍有波动，只是数量级远小于 G1。
3. JS 热点函数突然变慢，--trace-deopt 显示频繁去优化，最可能的原因是？
正确答案：对象结构不稳定。同一调用点出现多种隐藏类，TurboFan 的类型假设反复失效，反复 deopt 重编译。修复：构造函数统一初始化字段、热路径对象结构一致、数组保持同类型紧凑。
4. 关于 CPython 的 GIL，哪个说法正确？
正确答案：字节码级互斥，但 IO 释放。所以 IO 密集（网络/磁盘）多线程有效，CPU 密集无效——后者用多进程。3.13 起有实验性的无 GIL 构建（PEP 703），但生产短期仍按有 GIL 设计。
5. Go 中 GOMAXPROCS 的默认值和含义是？
正确答案：逻辑核数。GOMAXPROCS 决定 P 的数量，P 是 M（OS 线程）运行 G（goroutine）的"许可"。默认等于 NumCPU。注意它不等于线程数——M 可以更多，只是同时只有 GOMAXPROCS 个线程在执行 Go 代码。
6. Go 的一个 goroutine 初始栈大小是？
正确答案：2KB 起步、动态扩容、上限约 1GB。这就是 goroutine 能开几十万个的原因——对比 OS 线程默认 8MB 栈。栈扩容是复制到更大空间，深递归会持续触发扩容，成为隐藏成本。
