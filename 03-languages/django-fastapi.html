模块 1

Django 的 MVT 架构

Django 自己叫 MVT（Model-View-Template）。它和经典 MVC 的对应关系是：View 相当于 Controller（在 views.py 里写业务逻辑），Template 才是 View（负责渲染）。别被名字绕晕。

组件位置职责
Modelmodels.py数据结构 + ORM。一个类 = 一张表，字段 = 列
Viewviews.py请求处理逻辑：查数据、调业务、返回响应。相当于 MVC 的 Controller
Templatetemplates/*.htmlHTML 渲染，Django 模板语言（DTL）。相当于 MVC 的 View
URL 分发urls.py路由表，正则/路径匹配到 View 函数
ORMmodels.objectsManager/QuerySet 体系，数据库操作全部走它
# models.py
from django.db import models

class Author(models.Model):
    name = models.CharField(max_length=64)

    class Meta:
        db_table = "author"

class Book(models.Model):
    title  = models.CharField(max_length=128)
    price  = models.DecimalField(max_digits=8, decimal_places=2)
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name="books")
    created_at = models.DateTimeField(auto_now_add=True)

# views.py
from django.shortcuts import render, get_object_or_404

def book_list(request):
    books = Book.objects.all()          # 此刻没有 SQL，只是拿到 QuerySet
    return render(request, "books/list.html", {"books": books})

def book_detail(request, pk):
    book = get_object_or_404(Book, pk=pk)   # 查不到直接抛 404
    return render(request, "books/detail.html", {"book": book})

# urls.py
urlpatterns = [
    path("books/", book_list, name="book-list"),
    path("books/<int:pk>/", book_detail, name="book-detail"),
]

一次请求的完整链路

WSGI/ASGI handler：uWSGI/Gunicorn/uvicorn 把 HTTP 请求交给 Django
中间件请求侧（process_request）：按 MIDDLEWARE 列表从上到下，如 Session、Auth、CSRF
URL resolver：用 ROOT_URLCONF 逐层匹配，解析出 View 函数和参数
View 执行：你的业务代码在这里跑，ORM 按需发 SQL
响应返回：Template 渲染成 HttpResponse，或 DRF 序列化成 JSON
中间件响应侧（process_response）：按从下到上的逆序执行，可改响应头
Django 的"全家桶"哲学：ORM、迁移、Admin、认证、Session、表单校验、模板全部内置，开箱即用且互相咬合。好处是技术决策少、招人好招；代价是各部分耦合深，想换掉 ORM 或模板引擎会很痛。
模块 2

ORM 与 QuerySet 惰性求值

QuerySet 是惰性的：构建查询不碰数据库，第一次"求值"才发 SQL，结果还会缓存。这是 Django ORM 最核心的机制，也是最多误用的地方。

# ===== 求值触发点：只有这些动作会真的执行 SQL =====
qs = Book.objects.filter(price__gt=50)    # 1 次都没查，只是构造
qs = qs.order_by("-created_at")          # 还是构造，QuerySet 可链式

len(qs)          # 求值：SELECT ... 并缓存到 qs._result_cache
list(qs)        # 求值（已缓存则直接返回缓存）
bool(qs)        # 求值（内部就是 len > 0）
qs[0]            # 切片求值：带步长的切片会缓存全部，负数索引不支持
for b in qs:    # 迭代求值
    ...

# ===== 不求值的方法：返回新 QuerySet，零成本 =====
Book.objects.filter(...).exclude(...).annotate(...).order_by(...).values(...)

# ===== 直查聚合的方法：各自单独发 SQL =====
qs.exists()      # SELECT 1 ... LIMIT 1，比 len(qs) 快得多
qs.count()       # SELECT COUNT(*)，不复用 _result_cache
qs.iterator()    # 流式游标，不缓存，适合百万级导出（省内存）

常用查询 API 速查

写法作用
filter(price__gt=50)双下划线查找：gt/lt/gte/lte/contains/icontains/in/startswith/isnull
exclude(...)NOT 条件
Q(price__lt=10) | Q(author__name="A")复杂 OR/AND 组合，| 是 OR，, 是 AND，~ 是否定
annotate(n=F("price") * 2)F() 表达式：数据库侧计算，避免读-改-写的竞态
values("id", "title") / values_list(...)只取部分字段，返回 dict/元组，省内存和反序列化开销
only("title") / defer("content")单对象级字段裁剪，大文本字段用 defer 提速
select_for_update()行锁，必须在 transaction.atomic() 里用
bulk_create(objs, batch_size=500)批量插入，一条 SQL 多行，但不会调用 save() 信号
update(price=100)直接 UPDATE，不加载对象、不触发 save 信号
# 事务的标准写法（Django 4.x+ 推荐）
from django.db import transaction

with transaction.atomic():
    order = Order.objects.create(user=u)
    order.items.create(sku=sku, qty=1)     # 同一事务，任一步抛异常整体回滚
    # 嵌套用 transaction.atomic() 会创建 savepoint

# 原子自增：不要 read-modify-write，会竞态
Book.objects.filter(pk=1).update(views=F("views") + 1)   # ✓ 数据库侧 +1
b = Book.objects.get(pk=1); b.views += 1; b.save()       # ✗ 并发下丢更新
缓存的另一面：已求值的 QuerySet 会把所有行加载进内存（_result_cache）。10 万行的表 list(Book.objects.all()) 能把内存打爆。大结果集一律 .iterator() 或分页（Paginator / limit-offset）。另外在循环里反复引用同一个未求值 QuerySet 会每次都查库——先 list() 固化一次。
模块 3

N+1 查询与两种解法

N+1 是 Django 应用的头号性能杀手：1 次查主表，循环里每次查 1 次关联表，总共 N+1 次 SQL。

# 触发 N+1：1 次查书，循环里每次查作者 = 1 + N 次 SQL
books = Book.objects.all()                # 第 1 次
for b in books:
    print(b.author.name)                   # 每次都触发 SELECT author

# ===== 解法一：select_related（JOIN，一次查完）=====
# 用于 ForeignKey / OneToOne（多对一、一对一），SQL 层 JOIN
books = Book.objects.select_related("author").all()
for b in books:
    print(b.author.name)                   # 零额外查询

# ===== 解法二：prefetch_related（两次查询 + Python 拼接）=====
# 用于 ManyToMany / 反向 ForeignKey
authors = Author.objects.prefetch_related("books").all()
for a in authors:
    print(a.books.all())                   # 命中预取缓存，不再查库

# Prefetch 对象：自定义预取的 queryset 与缓存属性名
from django.db.models import Prefetch
Author.objects.prefetch_related(
    Prefetch("books", queryset=Book.objects.filter(price__gt=50), to_attr="cheap_books")
)
for a in authors:
    print(a.cheap_books)                   # 直接是 list，不再 QuerySet
对比项select_relatedprefetch_related
SQL 次数1 次（JOIN）2 次（主表 + 关联表）
适用关系ForeignKey / OneToOneManyToMany / 反向 FK
实现层数据库 JOINPython 侧按主键拼接
风险关联多时 JOIN 结果集膨胀大结果集两次查询都全量进内存
# ===== 检测 N+1 的三种手段 =====
# 1. django-debug-toolbar：开发环境看每个请求的 SQL 数和明细（首选）
# 2. 测试里断言查询数：
from django.test import TestCase
class BookTest(TestCase):
    def test_no_n1(self):
        with self.assertNumQueries(2):        # 超过 2 次直接测试失败
            list(Book.objects.select_related("author"))

# 3. 开发时打印所有 SQL：
from django.db import connection
print(len(connection.queries))      # 需 settings 里 DEBUG=True
DRF 序列化里的 N+1 更隐蔽：嵌套 serializer（如 author = AuthorSerializer()）会为每个对象触发一次查询。解法不在 serializer，而在 ViewSet 的 queryset——queryset = Book.objects.select_related("author") 一行搞定。SerializerMethodField 内部查库同样会炸，能挪到 queryset 层就挪。
模块 4

中间件与信号

中间件：请求的"洋葱"

# 自定义中间件（新版约定：__init__ + __call__）
import time

class TimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response      # 启动时执行一次，别放重活

    def __call__(self, request):
        t0 = time.perf_counter()              # 请求侧：View 之前
        response = self.get_response(request)
        cost = (time.perf_counter() - t0) * 1000
        response["X-Cost-Ms"] = f"{cost:.1f}"   # 响应侧：View 之后
        return response

# settings.py：顺序即请求侧执行顺序，响应侧逆序
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",   # request.user 从这里来
    "mysite.middleware.TimingMiddleware",
]

信号：事件钩子

from django.db.models.signals import post_save, pre_delete
from django.dispatch import receiver

@receiver(post_save, sender=Order)
def on_order_created(sender, instance, created, **kwargs):
    if created:                          # created=False 表示是更新
        send_sms(instance.user.phone)      # 同步执行！慢操作会把请求拖垮

# 常用内置信号
pre_init / post_init        # 模型实例化前后
pre_save / post_save        # 保存前后（update 不经过 save() 就不会触发！）
pre_delete / post_delete    # 删除前后
m2m_changed                 # 多对多关系变化
request_started / request_finished   # 请求生命周期
信号的三个坑：① 同步执行——在请求线程里跑，发短信、调第三方 API 会直接拖慢接口，重活丢 Celery；② 事务内的信号先于提交执行——收到 post_save 时事务可能还没提交，异步任务去读库可能读不到，要用 transaction.on_commit() 注册回调；③ update() 不触发 save 信号，批量操作静默跳过。中间件和信号别同时用同一套逻辑，二选一：横切 HTTP 层用中间件，模型事件用信号。
模块 5

DRF 序列化与视图集

Django REST Framework（DRF）是 Django 做 API 的标准答案：Serializer 管校验和序列化，ViewSet + Router 管路由和权限。

from rest_framework import serializers, viewsets, status
from rest_framework.permissions import IsAuthenticated

class BookSerializer(serializers.ModelSerializer):
    author_name = serializers.CharField(source="author.name", read_only=True)

    class Meta:
        model = Book
        fields = ["id", "title", "price", "author", "author_name"]

    def validate_price(self, value):          # 单字段校验
        if value <= 0:
            raise serializers.ValidationError("价格必须为正数")
        return value

    def validate(self, attrs):                # 跨字段校验
        if attrs["title"] == attrs.get("author"):
            raise serializers.ValidationError("标题不能与作者同名")
        return attrs

class BookViewSet(viewsets.ModelViewSet):
    # 注意 select_related：DRF 的 N+1 在 queryset 层解决
    queryset = Book.objects.select_related("author").order_by("-created_at")
    serializer_class = BookSerializer
    permission_classes = [IsAuthenticated]      # 认证 + 权限是每个 View 显式声明的

# urls.py：一个 register 就是全套 CRUD 路由
from rest_framework.routers import DefaultRouter
router = DefaultRouter()
router.register("books", BookViewSet)        # GET/POST /books/、GET/PUT/DELETE /books/{id}/
urlpatterns = [path("api/", include(router.urls))]
组件说明
ModelSerializer根据 Model 自动生成字段和验证器，写 CRUD 用这个
Serializer完全手写字段，非模型数据用这个
ViewSetlist/create/retrieve/update/destroy 一套方法对应一套动作
Router自动生成 URL 路由，还能生成可浏览 API 页面
权限/认证IsAuthenticated / IsAdminUser / 自定义 permission_classes；TokenAuthentication、SessionAuthentication、JWT（第三方）
SerializerMethodField自定义字段：get_<field>(self, obj)。内部查库就是 N+1 温床
DRF 安全两件事：① SessionAuthentication 会强制 CSRF 检查——用 cookie session 的 SPA 要么处理 CSRF token，要么换 JWT；② 权限默认是 AllowAny，忘记写 permission_classes 的接口等于裸奔，用 DEFAULT_PERMISSION_CLASSES 全局兜底。
模块 6

FastAPI：异步路由与依赖注入

async 与 def 的区别（第一个大坑）

路由写法执行位置规则
async def 路由事件循环内直接跑里面只能写非阻塞代码。同步阻塞调用会把整个事件循环卡死
def 路由丢进线程池（anyio 默认上限 40 线程）可以写阻塞代码（requests、同步 ORM）。这是故意的兼容设计
from fastapi import FastAPI
import httpx, time

app = FastAPI()

@app.get("/good")
async def good():
    async with httpx.AsyncClient() as c:
        r = await c.get("https://api.github.com")   # ✓ 异步 IO
        return {"status": r.status_code}

@app.get("/bad")
async def bad():
    time.sleep(3)                # ✗ 阻塞整个事件循环 3 秒，所有请求一起卡死
    return {"ok": True}

@app.get("/safe")
def safe():
    time.sleep(3)                # ✓ def 路由在线程池执行，不影响事件循环
    return {"ok": True}

依赖注入 Depends

from fastapi import Depends, HTTPException, Header
from typing import Annotated

# 带 yield 的依赖：请求后置逻辑（finally 语义）
async def get_db():
    db = AsyncSessionLocal()
    try:
        yield db
    finally:
        await db.close()        # 请求结束/异常都一定执行

Db = Annotated[AsyncSession, Depends(get_db)]

# 依赖可以带依赖；use_cache=True 时同一请求内复用实例
async def get_current_user(db: Db) -> User:
    u = await db.get_user()
    if not u:
        raise HTTPException(status_code=401, detail="未登录")
    return u

@app.get("/books")
async def list_books(db: Db, user: Annotated[User, Depends(get_current_user)]):
    return await db.list_books()

# 类作为依赖：把复用逻辑组织成对象
class Pagination:
    def __init__(self, page: int = 1, size: int = 20):
        self.skip = (page - 1) * size
        self.limit = size

@app.get("/books2")
async def list_books2(p: Annotated[Pagination, Depends()]):
    return await db.list(p.skip, p.limit)
能力用法
全局/路由级依赖FastAPI(dependencies=[...]) 或 @app.get(..., dependencies=[...])
依赖缓存同一请求内相同依赖只执行一次（默认），use_cache=False 关闭
后台任务BackgroundTasks：响应返回后执行，适合发邮件/日志
生命周期lifespan 上下文管理器替代废弃的 on_event，做连接池初始化
APIRouter按模块拆路由：app.include_router(books.router, prefix="/api")

Pydantic 校验与自动文档

from pydantic import BaseModel, Field, field_validator, model_validator, EmailStr
from typing import Annotated

class BookIn(BaseModel):
    title: Annotated[str, Field(min_length=1, max_length=128)]
    price: Annotated[float, Field(gt=0, description="售价（元）")]
    author_email: EmailStr                       # 需 pip install email-validator

    @field_validator("title")
    @classmethod
    def strip_title(cls, v: str) -> str:
        return v.strip()

    @model_validator(mode="after")
    def check_price(self):
        if self.price > 10000:
            raise ValueError("价格异常")
        return self

@app.post("/books", response_model=BookOut, status_code=201, tags=["books"])
async def create_book(book: BookIn):
    return await crud_create(book)     # 请求体自动校验、转换、文档化
特性说明
自动校验请求体/Query/Path 参数声明类型即校验，失败返回 422 + 错误明细（含字段路径）
自动 OpenAPI启动即生成 /openapi.json，/docs（Swagger UI）、/redoc（ReDoc）开箱可用
response_model声明响应结构，自动过滤未声明字段、做文档同步——防泄露利器
Pydantic v2核心用 Rust 重写（pydantic-core），校验速度比 v1 高数倍；API 从 @validator 改为 @field_validator
依赖请求数据Header / Query / Cookie / Body 类型注解即绑定
响应泄露：不加 response_model 时，直接 return ORM 对象会把密码哈希、内部 ID、软删除标记全序列化出去。永远显式声明 response_model，或至少用 schemas 控制字段白名单。另外生产环境记得 FastAPI(docs_url=None, redoc_url=None) 或给 /docs 加依赖保护。

排雷

十个线上坑

1
DEBUG=True 上了生产
500 页面泄露 traceback、settings、环境变量。上线前用 python manage.py check --deploy 过一遍，它会逐项警告。
2
QuerySet 在循环里被反复求值
以为 QuerySet 有缓存，实际每次访问都发 SQL。要么先 list() 固化，要么检查是不是每次重新构造了新 QuerySet。
3
for 循环访问外键对象，N+1 查询
1 次主查询 + N 次关联查询。外键/一对一用 select_related，多对多/反向 FK 用 prefetch_related。用 django-debug-toolbar 或 assertNumQueries 兜底。
4
list(大表) 把内存打爆
QuerySet 求值会把全部行加载进内存。大数据量用 .iterator() 或分页。
5
信号处理函数里同步发短信/调第三方
信号在请求线程里执行，慢操作直接拖垮接口。重活丢 Celery；且事务未提交时异步任务可能读不到数据，用 transaction.on_commit()。
6
async 路由里写阻塞代码
FastAPI 的 async def 里调用 time.sleep、同步 ORM、requests，整个事件循环被卡住，所有请求一起超时。要么换 async 客户端，要么改成 def 路由走线程池。
7
ORM 注入：.extra() / .raw() / text() 拼接字符串
用户输入直接拼进 SQL 参数。全部改用参数化：.raw(sql, [params])、text("... :name") + 绑定字典。
8
FastAPI 不写 response_model
直接 return ORM 对象，密码哈希、内部字段全泄露。显式声明 response_model 做字段白名单。
9
CORS 用通配符 + 允许带凭证
allow_origins=["*"] + allow_credentials=True 浏览器直接拒绝，且等于放弃同源保护。白名单具体域名。
10
Django 同步 ORM 写在 async 视图里
Django 的 ORM 是同步的，async def 视图里直接查库会阻塞事件循环。用 sync_to_async 包裹，或干脆别写 async 视图。
自测

六道题

1. Django 的 QuerySet 什么时候真正执行 SQL？
正确答案：求值时才执行。filter/order_by/exclude/annotate 都只是往查询里加条件，返回新 QuerySet。第一次求值（迭代、切片、len、bool）才发 SQL，结果缓存进 _result_cache，之后复用。
2. 要消除 "for book in books: book.author.name" 的 N+1 查询，应该用？
正确答案：select_related。它是 SQL JOIN，一次查完，用于 ForeignKey/OneToOne（多对一）。多对多和反向外键才用 prefetch_related。values() 返回字典没有 .author 对象可用。
3. FastAPI 中一个用 def（非 async）定义的路由，会在哪里执行？
正确答案：线程池。FastAPI 把 def 路由交给 anyio 的线程执行器（默认上限 40 线程），所以同步代码（requests、同步 ORM）放在 def 路由里是安全的；放在 async def 里会卡死整个事件循环。
4. 带 yield 的依赖函数，yield 之后的代码什么时候执行？
正确答案：请求结束后。yield 前的代码在依赖注入时执行，yield 后的代码在响应发送后、异常也保证执行——这是关数据库连接、释放锁的标准姿势。
5. Django 的 post_save 信号里直接同步调用发短信 API，主要风险是？
正确答案：拖慢请求 + 事务可见性问题。信号在请求线程同步执行；且 post_save 可能在事务提交前触发，异步任务去查库会扑空。解法：重活丢 Celery，并用 transaction.on_commit() 注册发送回调。
6. 下列关于 FastAPI 自动文档的说法，哪个是对的？
正确答案：自动生成、可关闭。FastAPI 从类型注解和 Pydantic 模型推导 OpenAPI 规范，/docs（Swagger UI）和 /redoc 开箱可用。但它暴露全部 API 结构，生产环境应 docs_url=None 或加依赖保护。
