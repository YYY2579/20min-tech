模块 1

渲染与协调：虚拟 DOM 不是性能银弹

一个常见误解是"虚拟 DOM 比直接操作 DOM 快"。事实相反：直接写最优的原生 DOM 操作，永远比 React 快。虚拟 DOM 买到的是"你不需要手写那些操作"，以及"状态和视图的对应关系可以被推理"。

一次更新发生了什么

触发（trigger）：setState、useReducer 的 dispatch、或根节点 root.render。React 把这次更新排进调度队列。
渲染（render）：调用组件函数，得到新的元素树（一堆普通 JS 对象，描述"我想要什么 UI"）。这一步是纯计算，不碰 DOM。
协调（reconcile）：把新树和上一次的树对比，算出最小变更集。这一步是 React 内部做的，你无法干预，只能通过 key 和组件结构影响它。
提交（commit）：把变更一次性写进真实 DOM，然后执行 layout effect、绘制、再执行 passive effect。
"渲染"不等于"更新 DOM"。组件函数被调用（render）是很便宜的——就是跑一段 JS、创建对象。真正贵的是 commit 阶段的 DOM 写入和布局。
所以"减少渲染次数"本身不是目标，"减少昂贵的渲染"才是。一个只返回几个 div 的组件渲染 100 次，可能还不如一次大列表的 diff 贵。

diff 的三条启发式规则

规则行为
类型不同，整棵子树重建<div> 变成 <span>，或 <A/> 变成 <B/>，旧子树直接卸载（state 全丢），新的从头挂载
类型相同，复用 DOM 节点只更新变化的属性；子节点递归对比
列表靠 key 匹配同层子元素用 key 建立"旧元素 → 新元素"的映射，决定谁复用、谁移动、谁销毁

注意第一条的推论：在 JSX 里写 {cond && <A/>} 和写三元表达式，对 state 的影响是一样的——条件为假时 A 被卸载，它的 state 消失。想让 state 保留，要用 CSS 隐藏，或者把状态提到父组件。

key 为什么必须稳定

// ✗ 用数组下标：删除第一项后，所有 key 都往前挪了一位
{items.map((item, i) => (
  <Row key={i} data={item} />
))}
// 结果：React 认为"第 0 个还是第 0 个"，于是复用旧的 DOM 和 state，
// 只是把 data 换成了新值。输入框里的内容、展开状态、动画全部错位。

// ✓ 用稳定唯一 id
{items.map(item => (
  <Row key={item.id} data={item} />
))}

// ✗ 每次渲染都生成新 key（随机数 / Math.random / Date.now）
// 等于告诉 React "所有元素都换了"，每次全量卸载重建，性能和行为双崩
key 的三条要求：① 在兄弟节点之间唯一（不需要全局唯一）；② 跨渲染稳定（同一份数据永远得到同一个 key）；③ 不要用下标，除非列表只追加不重排、不删除、不排序。
另外，key 不只是给列表用的——给组件加 key 可以强制重置它的 state，这是"切换用户时清空表单"的常用技巧：<Form key={userId} />。

协调的复杂度

通用的树 diff 算法复杂度是 O(n³)，对上千节点的 UI 完全不可接受。React 用三条启发式把它降到 O(n)，代价是"跨层级移动的节点会被重建而不是复用"。这就是为什么把组件从 A 位置挪到 B 位置（同一层之外）时，它的 state 会丢。

模块 2

函数组件与 Hooks：为什么不能写在条件里

Hooks 的实现方式决定了它的规则。理解实现，规则就不用背。

每个函数组件实例（Fiber）上挂着一个链表，按调用顺序存所有 Hook 的状态。第一次渲染时依次创建节点；后续渲染时，React 沿着这条链表按顺序取下一个 Hook 的状态给你。

// 你写的代码
function Counter() {
  const [a, setA] = useState(0);      // hook #1
  const [b, setB] = useState('');     // hook #2
  useEffect(() => {}, []);           // hook #3
}

// React 内部大致是这样取状态的（示意）
// let hookIndex = 0;
// const state = fiber.memoizedState[hookIndex++];

// 所以如果某次渲染跳过了 hook #1：
if (cond) { const [a, setA] = useState(0); }   // ✗ 条件调用
const [b, setB] = useState('');
// 那么 b 会读到原本属于 a 的状态 —— 类型错乱、行为诡异
Hooks 的三条规则，全部来自这个实现：
① 只能在函数组件或自定义 Hook 的顶层调用——不能在条件、循环、嵌套函数里；
② 顺序必须每次渲染完全一致——所以不能提前 return 之前调用一部分 Hook；
③ 只能在 React 函数组件或自定义 Hook 里调用——普通函数里调用会报 "Invalid hook call"。
装 eslint-plugin-react-hooks，这三条会被静态检查出来。不要手动绕过它。

每次渲染都是一次独立的快照

function Chat({ roomId }) {
  const [count, setCount] = useState(0);

  function handleClick() {
    setTimeout(() => {
      alert(count);   // 捕获的是"点击那一次渲染"的 count
    }, 3000);
  }

  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>+</button>
      <button onClick={handleClick}>3 秒后提示</button>
    </>
  );
}
// 点 + 三次，再点"3 秒后提示"：弹出来的是 3，不是 0
// 因为 handleClick 是"点提示按钮那次渲染"创建的，闭包里是那一刻的 count

这不是 bug，是函数式渲染的必然结果：每次渲染都会创建新的 props、state、函数，它们构成一个不可变的快照。所谓"闭包陷阱"，本质是你读到的是旧快照。

两个解法，按场景选：
① 需要"最新值"时用 ref：const countRef = useRef(count); countRef.current = count;，回调里读 countRef.current；
② 需要"基于最新值计算"时用函数式更新：setCount(c => c + 1)，它拿到的 c 一定是队列里的最新值。
不要把 count 加到 setTimeout 的依赖里就以为解决了——那只是让 effect 重跑，闭包仍然是旧的那一个。

自定义 Hook 只是"函数复用"，不是"状态共享"

function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  const toggle = useCallback(() => setOn(v => !v), []);
  return [on, toggle] as const;
}

// 两个组件各自调用 useToggle()，各自有独立的状态
// 自定义 Hook 复用逻辑，不复用状态 —— 状态永远属于调用它的组件实例
模块 3

状态管理：从 useState 到外部 store

React 自带的状态能力够用到"跨多层组件共享"为止。超过这个边界，才需要引入外部方案——而大多数项目引入得太早。

useState vs useReducer

维度useStateuseReducer
适合单个、独立的简单值多个字段互相关联的状态
更新逻辑散落在各个事件处理器里集中在一个 reducer 函数里
可测试性要渲染组件才能测reducer 是纯函数，可以直接单测
复杂转换容易写出多个 setState 的组合天然适合"状态机"式的转换
// 三个字段必须一起变 —— 用 useState 很容易漏掉一个
const [state, dispatch] = useReducer(reducer, { status: 'idle', data: null, error: null });

function reducer(state, action) {
  switch (action.type) {
    case 'start':   return { status: 'loading', data: null, error: null };
    case 'success': return { status: 'done', data: action.data, error: null };
    case 'fail':    return { status: 'error', data: null, error: action.error };
    default: return state;
  }
}
// 不可能出现 "status 是 loading 但 data 还有旧值" 这种非法组合

Context：适合"低频变化的全局值"

const ThemeContext = createContext('light');

function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext.Provider value={theme}>
      <Toolbar />
    </ThemeContext.Provider>
  );
}

function Button() {
  const theme = useContext(ThemeContext);   // 直接取，不用逐层传 props
  return <button className={theme}>ok</button>;
}
Context 的性能陷阱：Provider 的 value 一变，所有消费者都会重渲染，不管它有没有用到变化的那部分。
更糟的是：如果 value 是个对象字面量，value={{ user, setUser }}，那么 Provider 每次渲染都会创建新对象，即使内容没变，所有消费者也全部重渲染。
三个解法：① value 用 useMemo 包住；② 按更新频率拆成多个 Context（用户信息 / 主题 / 语言各一个）；③ 高频变化的值根本不该放 Context，改用外部 store 配合选择器订阅。

什么时候才真的需要外部状态库

信号说明
多个不相关的子树要读写同一份状态Context 会导致整棵树重渲染，需要"按选择器订阅"
状态更新非常频繁（输入、拖拽、实时数据）每次 setState 都触发 React 渲染，需要绕开
需要"组件外"读写状态事件总线、路由守卫、工具函数里要改状态
需要时间旅行 / 持久化 / 中间件Redux 生态的强项
服务端数据缓存这不该用状态库，用 TanStack Query / SWR
选型顺序建议：useState → useReducer → Context（低频）→ Zustand / Jotai（高频、跨子树）→ Redux Toolkit（需要严格规范和中间件）。
关键区分：服务端状态（从接口拉的数据）和客户端状态（UI 开关、表单草稿）是两类东西。前者用查询库管缓存和失效，后者才用状态库。把它们混在一个 store 里，是大型项目最常见的架构错误。
模块 4

useEffect：依赖数组的三种写法

effect 的本质是"把组件和外部系统同步"。不是"生命周期钩子"，不是"渲染后执行一次"。想清楚"我在同步什么"，依赖数组自然就写对了。

写法执行时机典型用途
useEffect(fn)每次渲染后几乎不用，容易死循环
useEffect(fn, [])仅挂载后一次初始化订阅、只跑一次的分析上报
useEffect(fn, [a, b])挂载后 + a 或 b 变化后绝大多数场景
useEffect(() => {
  const id = setInterval(() => setTick(t => t + 1), 1000);
  return () => clearInterval(id);   // 清理函数
}, []);   // 空依赖：只在挂载时建立，卸载时清理

清理函数什么时候执行

组件卸载时，React 调用清理函数。
依赖变化、下一次 effect 执行之前，先调用上一次的清理函数，再执行新的 effect。
StrictMode 开发模式下：挂载 → 立即清理 → 再挂载。这是故意模拟"组件被反复挂载"，用来暴露没写清理的副作用。

所以清理函数必须是幂等的：调用两次不会出错。常见错误是清理时把全局状态重置成"初始值"，第二次挂载后状态就错了。

闭包陷阱在 effect 里的表现

// ✗ 依赖数组漏了 roomId
useEffect(() => {
  const conn = createConnection(roomId);
  conn.connect();
  return () => conn.disconnect();
}, []);   // roomId 变了也不会重连，连的还是旧房间

// ✓ 依赖写全，eslint-plugin-react-hooks 会帮你检查
useEffect(() => {
  const conn = createConnection(roomId);
  conn.connect();
  return () => conn.disconnect();
}, [roomId]);
不要用"删依赖"来消除重复执行。那只会让闭包读到旧值，产生更难查的 bug。正确做法是：
① 把在 effect 里用到、但不需要触发重跑的值放进 ref；
② 把整个逻辑抽到自定义 Hook 里，让依赖关系显式化；
③ 用 useEffectEvent（实验性 API，稳定前可用 ref 模拟）读取最新值而不触发重跑。

useLayoutEffect 的区别

对比useEffectuseLayoutEffect
执行时机绘制之后（通常是异步的）DOM 更新后、浏览器绘制前（同步）
会阻塞绘制吗不会会
典型用途数据请求、订阅、日志测量布局、同步滚动位置、避免闪烁
SSR不执行（服务端没有 DOM）警告，因为服务端无法同步执行
// 需要"先测量再绘制"的场景：用 useLayoutEffect 避免闪一下
useLayoutEffect(() => {
  const h = ref.current.getBoundingClientRect().height;
  setHeight(h);   // 在绘制前完成，用户看不到跳动
}, [content]);
useLayoutEffect 里做重活会直接卡住渲染。它是同步的，执行期间浏览器不能绘制。测量 + 一次 setState 是合理的；循环读几十个元素的布局、或者在里面发请求，会让页面明显卡顿。默认用 useEffect，只在"必须赶在绘制前"时才换。
模块 5

性能优化：memo 什么时候真有用

memo / useMemo / useCallback 的作用只有一个：保持引用相等。它们不会让计算变快，反而增加了比较成本。只有当"引用相等"能阻止一次昂贵的渲染时，才是净收益。

API作用什么时候有用
React.memo(Comp)props 浅比较相等时跳过渲染组件本身渲染贵，且 props 大多不变
useMemo(fn, deps)缓存计算结果计算真的贵（排序、过滤大数组），或结果要作为依赖/ props
useCallback(fn, deps)缓存函数引用函数要传给 memo 子组件，或作为别的 Hook 的依赖
// 典型有效组合：三者必须配合，少一个就失效
const Child = memo(function Child({ item, onSelect }) {
  return <div onClick={() => onSelect(item.id)}>{item.name}</div>;
});

function Parent({ list }) {
  const [sel, setSel] = useState(null);
  // onSelect 必须稳定，否则 memo 白做
  const onSelect = useCallback(id => setSel(id), []);
  return list.map(i => <Child key={i.id} item={i} onSelect={onSelect} />);
}
三个常见的"负优化"：
① 给所有组件套 memo。每次渲染都要做一次 props 浅比较，props 多的时候比较本身就不便宜；而且如果 props 里有一个每次新建的对象/函数，memo 永远失效，纯亏。
② useMemo 包一个 a + b。创建依赖数组 + 比较依赖的成本，比加法本身高得多。
③ useCallback 包一个没传给任何 memo 组件的函数。引用稳定了，但没有任何人因此跳过渲染。
正确的优化顺序：① 用 Profiler 找到真正慢的组件；② 先看能不能减少渲染范围（把状态下移、把不相关部分拆出去）；③ 再看能不能减少工作量（虚拟列表、分页、把重计算移到 Web Worker）；④ 最后才上 memo。React 官方文档的说法是："memo 是性能优化的最后手段，不是默认写法。"

React 18 的自动批处理

// React 18 之前：只有 React 事件处理器里的更新会被合并
setTimeout(() => {
  setA(1);   // 旧版本：触发两次渲染
  setB(2);
}, 0);

// React 18 起：所有场景都自动批处理（包括 Promise、setTimeout、原生事件）
async function load() {
  const d = await fetchData();
  setA(d.a);   // 只触发一次渲染
  setB(d.b);
}

// 需要"立刻读到更新后的 DOM"时，用 flushSync 退出批处理（慎用）
flushSync(() => setA(1));
console.log(ref.current.textContent);   // 此时 DOM 已更新
批处理意味着"setState 之后 state 不会立刻变"。setCount(count + 1); console.log(count) 打印的还是旧值——因为这次渲染的 count 是常量。
连续两次 setCount(count + 1) 只会加 1（两次都基于同一个旧值）。要加 2 必须写 setCount(c => c + 1) 两次。
模块 6

七个每天都在踩的坑

1. setState 是异步的

function handle() {
  setCount(count + 1);
  console.log(count);        // 旧值！这次渲染的 count 是常量
  setCount(count + 1);       // 还是基于旧值，最终只加 1
}

// 需要连续更新就用函数式
setCount(c => c + 1);
setCount(c => c + 1);        // 加 2

2. 对象状态是替换，不是合并

const [user, setUser] = useState({ name: 'ann', age: 3 });

setUser({ age: 4 });
console.log(user);   // { age: 4 } —— name 没了！

// 必须手动展开
setUser(u => ({ ...u, age: 4 }));

// class 组件的 this.setState 才是合并的，函数组件不是 —— 这是迁移时的高频 bug

3. 用 index 做 key

// 列表有排序、删除、插入时，index key 会导致：
// - 输入框内容错位
// - 展开/折叠状态串到别的行
// - CSS 动画重放
// - 受控组件的值对不上

// 没有 id 时，至少用一个业务上稳定的字段组合
<Row key={item.type + '-' + item.code} />

4. 在渲染过程中做副作用

// ✗ 渲染函数必须是纯的：同样的 props/state 必须返回同样的结果
function Bad({ id }) {
  fetch('/api/' + id);            // 每次渲染都发请求
  localStorage.setItem('last', id);  // 渲染期间写外部状态
  return <div>{id}</div>;
}

// StrictMode 下会渲染两次 → 请求发两次、写入两次
// 并发渲染下更糟：渲染可能被中断、丢弃、重放

// ✓ 副作用放 effect 或事件处理器
useEffect(() => { localStorage.setItem('last', id); }, [id]);
React 18 的并发渲染让"渲染必须纯"从建议变成了硬要求。渲染可能被暂停、丢弃、重新执行；一个"渲染到一半"的结果可能永远不会提交到 DOM。在渲染里改 ref、改全局变量、发请求，都会产生你无法复现的 bug。

5. 在 JSX 里创建新对象/数组/函数

// 每次渲染都是新引用 → 子组件的 memo 永远失效
<Child style={{ color: 'red' }} />
<Child items={list.filter(x => x.ok)} />
<Child onSave={() => save(id)} />

// 修法：常量提到组件外、结果用 useMemo、函数用 useCallback
const STYLE = { color: 'red' };
const okItems = useMemo(() => list.filter(x => x.ok), [list]);
const onSave = useCallback(() => save(id), [id]);

6. 状态提升了但没提升对

// ✗ 把"输入框的值"提到页面顶层 → 每次按键整页重渲染
function Page() {

模块 7

数据获取：为什么不该在 useEffect 里裸发请求

"在 useEffect 里 fetch 然后 setState"能跑，但它把缓存、去重、重试、竞态、错误边界全部留给了你。这五件事每一件都有坑。

问题裸 fetch 的后果
重复请求两个组件请求同一份数据，发两次；切回来又发一次
没有缓存每次挂载都重新拉，用户体验和数据一致性都差
请求瀑布父组件拿到数据才渲染子组件，子组件才开始请求，串行叠加
竞态快速切换参数，旧响应覆盖新数据
卸载后 setStateReact 18 不再警告，但仍然是浪费和无意义的状态写入
错误处理每个组件都要写 loading / error / retry 三套状态
// 每个组件都要重复这一坨
const [data, setData] = useState(null);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);
useEffect(() => {
  setLoading(true);
  fetch(url)
    .then(r => { if (!r.ok) throw new Error(r.status); return r.json(); })
    .then(setData)
    .catch(setError)
    .finally(() => setLoading(false));
}, [url]);
推荐做法：用查询库。TanStack Query / SWR 把"服务端状态"当成一等公民：缓存、去重、后台刷新、失效重取、分页、乐观更新、重试都是内建的。
const { data, isLoading, error } = useQuery({ queryKey: ['user', id], queryFn: fetchUser }) 一行替代上面全部，还自带缓存和竞态处理。

Suspense 的思路：把"等待"交给框架

// 传统：组件自己管理 loading 状态
if (isLoading) return <Spinner />;
if (error) return <ErrorView />;
return <Profile data={data} />;

// Suspense：组件"声明"自己在等，由上层统一兜底
<Suspense fallback={<Spinner />}>
  <Profile />   // 内部读取尚未就绪的数据时，会"抛出一个 Promise"
</Suspense>

// 原理：组件在渲染期间 throw 一个 Promise，React 捕获它、
// 显示最近的 Suspense 边界，等 Promise resolve 后重新渲染

Suspense 的价值是把 loading 状态从每个组件里抽出来，让"加载中的 UI"变成布局层面的决策（整个区域一起转圈，而不是每个小组件各转各的）。配合 React.lazy 还能做代码分割。

Suspense 不是"自动帮你发请求"。它只提供"等待的机制"，数据怎么取、缓存在哪、什么时候失效，仍然要由查询库或框架（Next.js 的 Server Components）提供。没有配套的数据层，Suspense 只会让你多写一层包装。

加载与错误状态的三种层次

层次处理方式适用
组件内局部 isLoading / error只有一个小组件依赖这份数据
区域级Suspense + ErrorBoundary 包住一块一个区块整体加载 / 整体失败
页面级路由层的 loader / errorElement整页依赖同一份数据

组件拆分的粒度

信号该怎么做
一个组件超过 200 行大概率能按"区块"拆
JSX 里有明显的注释分段每段就是一个组件
某个 prop 只在深层用到把状态下移，或拆出子树
同一段 UI 出现第二次抽组件（出现第三次才抽 Hook）
组件同时管数据和展示拆成"容器"和"展示"两层
不要为了"复用"过早抽象。两个长得像但语义不同的 UI，强行合并成一个带 8 个 boolean prop 的"通用组件"，维护成本远高于复制两份。重复两次可以忍，重复三次再抽象——而且抽象时要看的是"变化的方向是否一致"，不是"当前长得像不像"。

样式方案的取舍

方案优点代价
CSS Modules零运行时、作用域隔离、写法标准动态样式要靠多套 class 切换
CSS-in-JS（运行时）样式和 props 强关联运行时开销、SSR 需要抽取、包体积大
Tailwind无运行时、约束设计系统、改样式不用起名字JSX 变长、需要团队约定
原生 CSS + 变量最简单、浏览器原生作用域要自己管

选型的核心问题不是"哪个好看"，而是"样式是否需要根据运行时状态大量变化"。需要就偏向 CSS-in-JS / Tailwind；不需要就 CSS Modules，成本最低。

常见坑

十个真实事故

1
列表用 index 做 key
删除、排序、插入后，state 和 DOM 会错位到别的行。输入框内容串行、折叠状态乱跳。必须用稳定唯一 id。
2
setState 之后立刻读 state
读到的是这次渲染的常量，不是新值。连续两次 setCount(count+1) 只加 1。要连续更新用函数式 setCount(c => c+1)。
3
以为 setState 会合并对象
函数组件的 setState 是整体替换，只传 { age: 4 } 会把 name 弄丢。必须 setUser(u => ({...u, age: 4}))。
4
在条件或循环里调用 Hook
Hooks 按调用顺序存状态，跳过或乱序会让状态错配到别的 Hook 上。必须在顶层、顺序固定。
5
useEffect 依赖写不全，靠删依赖消警告
闭包会读到旧值，出现"参数变了但请求没重发""监听器指向旧状态"这类难查的 bug。依赖必须写全。
6
在渲染函数里发请求或写 localStorage
渲染必须是纯的。StrictMode 下执行两次、并发渲染下可能被丢弃重放，副作用会重复或丢失。
7
Context 的 value 直接写对象字面量
Provider 每次渲染都产生新引用，所有消费者全部重渲染。用 useMemo 包住，或按更新频率拆分 Context。
8
给所有组件套 memo，还配上一堆 useCallback
浅比较本身有成本，props 里只要有一个新引用就完全失效。应该先用 Profiler 定位，memo 是最后手段。
9
useEffect 里请求不处理竞态
快速切换 id 时旧响应可能后到，把新数据覆盖掉。用 AbortController 或 cancelled 标记，或直接用查询库。
10
把服务端数据和 UI 状态混在一个 store
接口数据需要缓存、失效、重取、去重，UI 状态不需要。混在一起会导致"缓存逻辑手写一遍，还写不对"。用查询库管前者。
自测

六道题

1. 关于虚拟 DOM，哪个说法正确？
正确答案：后者。虚拟 DOM 的价值是"你不需要手写 diff 和更新逻辑"，而不是性能。每次更新都要跑一遍 render + diff，这些开销是真实存在的。
2. 为什么 Hook 不能写在 if 里？
正确答案：顺序错位。React 沿链表按顺序取每个 Hook 的状态，某次渲染少调一个，后面的 Hook 就会读到前面那个的状态。
3. 执行 setCount(count + 1); setCount(count + 1); 后 count 增加多少？
正确答案：1。两次都基于同一次渲染里的 count 常量。要加 2 必须用函数式更新：setCount(c => c + 1) 两次。
4. useEffect 的清理函数什么时候执行？
正确答案：卸载时 + 每次重跑前。所以清理函数必须幂等。StrictMode 开发模式下还会额外执行一次，用来暴露没写清理的问题。
5. React.memo 什么时候会失效？
正确答案：props 引用每次都变。memo 做的是浅比较，style={{color:'red'}} 每次都是新对象，比较必然不等，于是每次都重渲染，还多付了比较成本。
6. 为什么"在 useEffect 里裸发请求"不够好？
正确答案：要自己实现一整套数据层。查询库（TanStack Query / SWR）内建了这些能力，还顺带解决了请求瀑布和后台刷新。
