一个架构前提，后面全篇都在用：PHP-FPM 是"无共享（share-nothing）"架构。每个 worker 进程一次只处理一个请求，请求结束就把所有状态（静态属性、全局变量、单例里的数据）全部丢掉，下一个请求从零重新引导框架。理解这条，才能理解 OPcache、队列、缓存存在的意义。
模块 1

PHP 8 新特性：从"弱类型脚本"到现代语言

PHP 8.0 是分水岭：JIT、命名参数、match、属性提升；8.1 补上枚举和 readonly。语法层面的债基本还完了。

<?php  // 每个文件第一行，declare 必须紧跟其后且前面不能有输出
declare(strict_types=1);   // 文件级强制标量类型：传错类型直接 TypeError，而不是悄悄转型

class User
{
    // 构造函数属性提升 + readonly：一行完成声明、赋值、锁定
    public function __construct(
        public readonly int $id,
        private string $name = 'anon',
        private ?string $email = null,      // 可空类型要显式写 ?
    ) {}

    public function name(): string
    {
        return strtoupper($this->name);
    }
}

$u = new User(id: 1, name: 'tom');   // 命名参数：跳过中间的可选参数
$u?->name();                          // nullsafe：$u 为 null 时整条链短路返回 null

$label = match($u->id) {              // match 是表达式，用 === 严格比较
    1, 2, 3 => 'vip',           // 多值并列
    default => 'normal',       // 必须有 default，否则没匹配上抛 UnhandledMatchError
};

enum Status: string              // Backed Enum，8.1+；不写 : string 是 Pure Enum
{
    case Active = 'active';
    case Banned = 'banned';

    public function label(): string
    {
        return match($this) {
            self::Active => '正常',
            self::Banned => '封禁',
        };
    }
}
Status::from('active');      // 按值取实例，不存在抛 ValueError
Status::Active->label();       // 枚举可以带方法

特性版本解决什么问题
声明文件 strict_types7.0标量类型错误立即报错，不再静默转型（"1abc" 悄悄变 1 的时代结束）
构造函数属性提升8.0省掉一长串声明+赋值，DTO 写法从 20 行变 5 行
match 表达式8.0严格 === 比较、是表达式能赋值、不会漏 break
命名参数8.0调用时可跳过可选参数，可读性大幅提升

readonly 属性8.1不可变对象，写一次后修改抛 Error
never 返回类型8.1标记 exit/die/抛异常的函数，静态分析更准
JIT8.0把热点字节码编译为机器码，计算密集型提升明显
JIT 要说实话：开启方式是在 OPcache 里配 opcache.jit=tracing + opcache.jit_buffer_size=64M。但典型 Web 应用是 IO 密集型（时间都花在等数据库），JIT 通常只带来 5%~10% 的整体提升；它对图像处理、加解密、模板渲染这类 CPU 密集代码才有 2~3 倍收益。结论：开，但别指望它救命。
模块 2

请求生命周期：Nginx 到 PHP-FPM 再到 Laravel

① Nginx 收到请求。静态文件（JS/CSS/图片）自己直接返回，不过 PHP——这是 Nginx + PHP 分工的第一原则。
② 匹配到 location ~ \.php$。Nginx 通过 FastCGI 协议把请求转给 PHP-FPM 的 socket，同时设置 SCRIPT_FILENAME 告诉 FPM 执行哪个文件。
③ FPM master 分配 worker。master 是 root，负责监听端口和管理进程池；worker 才是真正执行 PHP 的进程。一个 worker 同时只处理一个请求，处理完就去池里等下一个。
④ worker 引导框架。入口永远是 public/index.php：加载 composer 自动加载 → 从 bootstrap/app.php 拿到 HTTP Kernel → 处理请求 → 返回响应。注意：每个请求都重新走一遍这个流程，这就是无共享的代价。
⑤ worker 归还。请求结束，worker 内所有内存、静态属性、单例数据全部销毁。如果 pm.max_requests 到了上限，worker 主动退出换新的，这是防内存泄漏的保险丝。
# /etc/php/8.3/fpm/pool.d/www.conf —— 进程池配置，直接决定容量上限
[www]
pm = dynamic                  # dynamic：按负载伸缩；static：固定数量；ondemand：按需拉起（省内存但首请求慢）
pm.max_children = 50          # 并发硬上限：超过就排队等待，不是报错
pm.start_servers = 5
pm.min_spare_servers = 2
pm.max_spare_servers = 10
pm.max_requests = 500         # 每个 worker 处理 500 个请求后自杀重生，防内存缓慢泄漏
request_terminate_timeout = 30s  # 单个请求最长 30 秒，防止一个死循环拖死 worker

# nginx.conf —— 动静分离 + FastCGI 转发
server {
    root /var/www/html/public;      # 站点根目录必须指到 public/，指到项目根 = 泄露 .env
    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }
    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.3-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        include fastcgi_params;
    }
    location ~ /\.(?!well-known).* { deny all; }   # 拦截 .env / .git 等隐藏文件
}
换算说明
单 worker 内存Laravel 应用约 20~40MB（含框架、ORM、扩展），复杂项目更高
max_children 上限可用内存 ÷ 单 worker 内存。8G 给 PHP：8000 ÷ 30 ≈ 250 个左右，要留 30% 余量
并发模型进程池 + 阻塞 IO。每个 worker 等数据库时是纯阻塞的，所以并发上不去时别先加机器，先看慢 SQL 和外部调用
无共享架构的四个推论，全是大坑：
① 不能用内存做跨请求状态——静态属性里缓存的数据，下一个请求就没了。用户登录状态、限流计数必须存 Redis/Session。
② 每个请求都要重新加载框架——composer 自动加载、配置解析、容器编译。没有 OPcache 的话每个请求都在"编译"几百个 PHP 文件，这是 PHP 慢的刻板印象的来源。
③ 本地文件写冲突——多 worker 同时写同一个文件（日志、缓存文件）会互相覆盖，生产必须用集中的日志和缓存。
④ 后台长任务不该跑在 FPM 里——发送邮件、生成报表这类几十秒的活会占着 worker 不放，拖垮整个进程池。必须扔队列。
模块 3

Composer 与自动加载

Composer 是 PHP 的事实标准包管理器，但它的自动加载机制值得单独讲——因为生产性能直接取决于你怎么用它。

// composer.json —— 最小可用配置
{
    "require": { "laravel/framework": "^11.0" },
    "require-dev": { "phpunit/phpunit": "^10.5" },
    "autoload": {
        "psr-4": { "App\\": "app/" }        // 命名空间前缀 → 目录映射（PSR-4）
    },
    "scripts": {
        "post-autoload-dump": ["@php artisan package:discover"]
    }
}
约束含义说明
^11.0>=11.0.0 <12.0.0最常用。不破坏兼容的前提下拿最新小版本
~11.0>=11.0 <12.0.0效果和 ^ 类似（主版本非 0 时）
~11.0.5>=11.0.5 <11.1.0只升补丁，锁定次版本
11.*>=11.0 <12.0通配写法
11.3.2精确锁定生产强烈建议用 lock 精确锁定

自动加载是怎么工作的

# 开发时：PSR-4 动态查找，类文件不存在就现场拼路径去 include，有文件系统开销
composer dump-autoload

# 生产：生成 classmap（类全名 → 文件绝对路径的映射表），之后 O(1) 直达，不再遍历目录
composer install --no-dev --optimize-autoloader

# 权威 classmap：连"文件不存在"的检查都省掉，最快；但新增文件必须重新 dump
composer dump-autoload --classmap-authoritative
两条生产纪律：
① composer.lock 必须提交进 Git。它锁定了所有间接依赖的精确版本。composer update 会按 semver 规则解析出新版本——同一份 composer.json，今天和明天的依赖可能不一样。生产只允许 composer install，update 是开发者的手动动作。
② require-dev 的包永远不进生产。PHPUnit、Laravel Debugbar、Telescope 这类工具进了生产 = 白送攻击面 + 拖慢自动加载。部署命令固定为 composer install --no-dev --optimize-autoloader。 
# 安全体检：定期看依赖漏洞（composer audit 读 GitHub Advisory 数据库）
composer audit
composer audit --format=plain | grep -i critical

中间件：洋葱模型

请求由外向内穿过中间件到达控制器，响应由内向外穿回来。Laravel 用 Pipeline 模式实现，顺序是：全局中间件 → 中间件组（web/api）→ 路由中间件 → 控制器。

中间件干什么
TrustProxies信任代理头，否则拿不到真实客户端 IP
EncryptCookies / StartSessionweb 组：Cookie 加解密 + Session 启停
VerifyCsrfTokenweb 组：校验 CSRF Token，API 组没有它，API 靠 Token 认证
auth / throttle登录校验 / 限流（按用户或 IP）

服务容器：Laravel 的心脏

容器解决的是"把实现交给接口，用时才解析"。控制器里写一个类型提示，Laravel 靠反射自动 new 出依赖链——你从来没写过 new，但一切都装好了。

// app/Providers/AppServiceProvider.php
public function register(): void
{
    // singleton：整个请求周期内同一个实例（注意：请求结束就销毁，不是全局单例）
    $this->app->singleton(PaymentGateway::class, function ($app) {
        return new StripeGateway(config('services.stripe.key'));
    });
    // 上下文绑定：给 AdminBillingService 的构造参数注入另一个实现
    $this->app->when(AdminBillingService::class)
              ->needs(PaymentGateway::class)
              ->give(MockGateway::class);
}

// 控制器：零样板代码拿到依赖，容器按类型提示递归解析
class OrderController extends Controller
{
    public function __construct(private PaymentGateway $pay) {}

    public function store(StoreOrderRequest $request)
    {
        // 表单请求类：授权逻辑 + 校验规则都在 StoreOrderRequest 里
        $data = $request->validated();
        return new OrderResource($this->pay->charge($data));
    }
}

// Facade 不是新语法，是容器服务的静态代理：
Cache::get('key');              // 等价于 app('cache')->get('key')
app(PaymentGateway::class)->charge($data);  // 直接手动解析，等价写法
Facade 的真相：Cache::get() 能工作，是因为 Cache 这个类实现了 __callStatic，把调用转发到容器里解析出的实例。它不引入任何全局状态，测试时 Cache::shouldReceive() 就能 Mock。
调试技巧：怀疑 Facade 指向错服务时，php artisan tinker 进去敲 app(PaymentGateway::class)，看解析出来的是哪个类。

Eloquent ORM 与 N+1 问题

<?php  // 模型 = 一行数据 + 行为； migrations 管表结构，两者要同步演进
class Order extends Model
{
    protected $fillable = ['user_id', 'total', 'status'];  // 白名单：只允许这些字段被 mass assignment

    public function user(): BelongsTo { return $this->belongsTo(User::class); }
    public function items(): HasMany   { return $this->hasMany(OrderItem::class); }
}

// 查询构造器：where 链式调用，永远走预处理绑定，天然免疫 SQL 注入
$orders = Order::query()
    ->where('status', Status::Paid)
    ->whereBetween('created_at', [$from, $to])
    ->with(['user', 'items'])
    ->latest()
    ->paginate(20);          // 分页，别用 all() 把全表捞进内存

N+1：Laravel 头号性能杀手

// ✗ 经典 N+1：1 条 SQL 查订单，循环里每条订单再查 1 次用户 = 101 条 SQL
$orders = Order::all();                    // 第 1 条
foreach ($orders as $o) {
    echo $o->user->name;                   // 每条触发 1 条：select * from users where id = ?
}

// ✓ 预加载：2 条 SQL。第二条用 where id in (...) 一次性捞回所有关联
$orders = Order::with('user', 'items.product')->get();
// select * from orders;
// select * from users where id in (1,2,3,...);

// 按条件预加载 + 统计，把"循环里 count"也干掉
$users = User::with(['posts' => fn ($q) => $q->where('published', true)->latest()->limit(5)])
             ->withCount('orders')     // 生成 orders_count 字段，替代 $user->orders->count()
             ->orderByDesc('orders_count')
             ->get();
把 N+1 变成不可能：在 AppServiceProvider::boot() 里加一行 Model::preventLazyLoading(! app()->isProduction())。开发/测试环境里一旦发生懒加载直接抛 LazyLoadingViolationException，页面当场报错——逼着你在写代码的时候就 with() 好。
线上发现 N+1 的工具：Laravel Debugbar（开发）、Telescope（开发/预发）、或者 DB::listen(fn ($q) => log($q->sql, $q->time)) 采一把慢查询。 
// 大数据集处理：chunk 分段，游标 cursor 用生成器，都不会把 50 万行塞进内存
Order::query()->chunk(1000, function ($orders) {
    foreach ($orders as $o) { $o->markExported(); }
});

// 事务：闭包自动回滚，别手动 begin + commit 然后忘了 try
DB::transaction(function () use ($order, $items) {
    $order->save();
    $order->items()->createMany($items);   // 任一步抛异常，整体回滚
}, attempts: 3);                            // 死锁时自动重试 3 次
模块 6

队列：把慢活扔出请求

发邮件、调第三方 Webhook、生成报表、同步 ES——任何超过 100ms 且用户不盯着结果的操作都该进队列。请求同步等它，等于 worker 被占着几十秒。

<?php
class SendWelcomeEmail implements ShouldQueue
{
    use Dispatchable, InteractsWithQueue, Queueable, SerializesModels;

    public int $tries = 3;                 // 最多重试 3 次
    public array $backoff = [10, 30, 60];  // 第 1/2/3 次重试前分别等 10/30/60 秒

    public function __construct(
        public User $user                  // 必须 public：任务会被序列化进 Redis/MQ
    ) {}

    public function handle(Mailer $mailer): void
    {
        $mailer->to($this->user->email)->send(new Welcome($this->user));
    }

    public function failed(\Throwable $e): void   // 重试耗尽后的兜底
    {
        Log::error('欢迎邮件最终失败', ['user' => $this->user->id, 'err' => $e->getMessage()]);
    }
}

// 投递
SendWelcomeEmail::dispatch($user)->onQueue('emails')->delay(now()->addMinutes(5));

// 链式任务：A 成功才跑 B，任一失败后续取消
Bus::chain([new ExportReport($user), new NotifyOwner($user)])->dispatch();

// 常驻 worker：一条命令守着队列跑，别用 queue:listen（每任务重启框架，慢）
php artisan queue:work redis --queue=high,default --tries=3 --timeout=60

php artisan queue:restart    // 部署后必须执行：通知所有 worker 当前任务跑完后平滑退出
驱动适用
redis生产首选。延迟毫秒级，配合 Horizon 有完整监控面板
database小项目免运维，但高频时有行锁竞争
sqs / beanstalkd云原生或特定基础设施场景
sync本地调试/测试：任务当场执行，不异步
队列三条铁律：① 任务必须幂等——网络抖动会导致同一条任务被投递两次（at-least-once），处理逻辑要能重复执行（用唯一键去重、用状态机判断）。② 队列不是实时通道——用户点了"发送验证码"，邮件可能 3 秒后才到，别拿同步链路的时间预期做 UX。③ 监控 Horizon 的失败数和队列深度——队列堆积几百条没人发现，是线上事故的标准前奏。
模块 7

安全常见坑：注入、反序列化、文件包含

<?php
// ===== 1. SQL 注入：拼字符串 = 把钥匙递给攻击者 =====
// ✗ 危险：字符串直接拼进 SQL
DB::select("SELECT * FROM users WHERE email = '{$email}'");
// 输入 ' OR 1=1 --  → 整表拖走；输入 '; DROP TABLE users; -- → 直接删库

// ✓ 预处理 + 绑定：SQL 结构和数据彻底分离，注入在协议层面就不可能
DB::select('SELECT * FROM users WHERE email = ?', [$email]);
DB::select('SELECT * FROM users WHERE email = :e', ['e' => $email]);
User::whereEmail($email)->first();               // ORM 等价安全写法

// 必须拼动态列名/排序时，用白名单，不要用用户输入原文
$sort = in_array($_GET['sort'], ['id', 'created_at'], true) ? $_GET['sort'] : 'id';

// ===== 2. 反序列化：PHP 最危险的函数 =====
// ✗ 反序列化用户可控数据 = PHP 对象注入
$obj = unserialize($_POST['data']);
// 攻击者可构造任意对象，触发魔术方法（__destruct/__wakeup/__toString）
// 组合框架/库里现成的"gadget"形成 POP 链，Laravel 生态就有公开利用链 → RCE

// ✓ 只接受 JSON：纯数组，不可能实例化类
$data = json_decode(file_get_contents('php://input'), true);

// ===== 3. 文件包含：LFI / 路径穿越 / 伪协议 =====
// ✗ include 拼接用户输入
include __DIR__ . '/pages/' . $_GET['page'] . '.php';
// page=../../../../etc/passwd        → 任意文件读取
// page=php://filter/read=convert.base64-encode/resource=index.php → 读源码
// page=php://input（配合 allow_url_include）→ 直接 RCE

// ✓ 白名单映射
$pages = ['about' => 'about.php', 'contact' => 'contact.php'];
$file = $pages[$_GET['page'] ?? ''] ?? abort(404);
include __DIR__ . '/pages/' . $file;

// ===== 4. 时序安全比较：别用 == 比 token =====
// ✗ == 慢且可能被"魔术哈希"绕过：两个 md5 都是 "0e123..." 开头时 == 判真
if ($token == $expected) { /* ... */ }

// ✓ hash_equals：恒定时间比较，且全等
if (!hash_equals($expected, $token)) { abort(403); }

// ===== 5. XSS：Blade 转义 vs 不转义 =====
{{ $userInput }}      // {{ }} = htmlspecialchars 自动转义，安全
{!! $userInput !!}    // {!! !!} = 原样输出，用户可控数据进去就是存储型 XSS
攻击根因防线
SQL 注入SQL 字符串拼接用户输入PDO 预处理绑定 / ORM；动态标识符用白名单
对象注入unserialize 用户可控数据只用 json_decode；必须 unserialize 时设 allowed_classes
LFI/RFIinclude 路径含用户输入白名单；关 allow_url_include；open_basedir
XSS未转义输出用户内容模板默认转义；富文本场景用 HTML Purifier 白名单过滤
CSRF表单无 Token 校验Laravel web 中间件组默认开启，别把表单路由挪到 api.php
批量赋值create($request->all())只用 $request->validated()；模型配 $fillable 白名单
.env 泄露是 PHP 项目最常见的"秒杀级"事故。里面躺着 APP_KEY、数据库密码、Redis 密码、各第三方 API Key。三条防线：① 站点根目录必须指到 public/，.env 在项目根目录层；② Nginx 加 location ~ /\.(?!well-known).* { deny all; } 兜底；③ APP_KEY 泄露 = 所有加密 Cookie/令牌可被伪造，泄露后必须 php artisan key:generate 轮换并让所有 Session 失效。
模块 8

性能优化：OPcache 是底线，队列是杠杆

# php.ini / conf.d/10-opcache.ini —— 生产必调
opcache.enable=1
opcache.memory_consumption=256        # 给编译后的字节码留的内存，MB。项目越大越要多
opcache.interned_strings_buffer=16
opcache.max_accelerated_files=20000   // 要大于项目的 PHP 文件数（含 vendor），否则缓存装不下
opcache.validate_timestamps=0          # 生产 = 0：不检查文件 mtime，零开销。
opcache.revalidate_freq=0              # 配合上面：改代码不会生效，必须重启 FPM 或 touch 系统 reload
opcache.jit=tracing                    # JIT：计算密集型收益大，IO 型一般
opcache.jit_buffer_size=64M

# 部署流程：代码上线后平滑重启，让 OPcache 重新编译
php-fpm -t  &&  kill -USR2 $(cat /run/php/php8.3-fpm.pid)   # USR2 = 平滑 reload，不丢连接

# Laravel 侧四连 cache，把引导开销压到接近零
php artisan config:cache      # 把所有 config/*.php 合并成一个缓存数组
php artisan route:cache        # 路由注册表编译成 PHP 数组，闭包路由会失效，注意
php artisan view:cache         # Blade 模板预编译
php artisan event:cache        # 事件-监听器映射缓存

# 注意：本地开发用 config:cache 后改 .env 不生效，先 artisan config:clear
手段量级代价/注意
OPcache没开 → 开了：快 2~5 倍零成本，唯一必做项。validate_timestamps=0 要求部署即重启
config/route/view cache省 10~30ms 引导route:cache 不支持闭包路由
消除 N+1查询数 101 → 2改代码层面，preventLazyLoading 兜底
Redis 缓存热点读接口从 50ms → 5ms引入一致性成本（先更新库再删缓存 + TTL 兜底）
异步队列接口 2s → 200ms任务幂等 + 失败监控
Laravel Octane数百 rps → 数千 rps常驻内存打破无共享假设：单例/静态属性跨请求累积，老代码可能有内存泄漏和状态污染，迁移前必须压测
优化顺序永远是：先测量，再动手。装一个 clockwork 或看 DB::listen 的耗时分布：PHP 项目 80% 的"慢"在数据库和外部 HTTP 调用，不在 PHP 本身。加机器解决不了没走缓存的循环查询。
避坑

十个线上坑

1
用 == 比较 token 或密码
== 先做类型转换，两个不同字符串都可能被"魔术哈希"判等（都以 0e 开头的数字型哈希串），还有时序攻击风险。一律 === 或 hash_equals()。
2
unserialize 用户可控的输入
PHP 对象注入的入口。攻击者构造恶意对象触发魔术方法，沿框架现成 gadget 组成 POP 链，最终可远程执行代码。跨服务传数据用 JSON。
3
include/require 路径里拼用户参数
../../ 路径穿越读任意文件，php:// 伪协议读源码甚至 RCE。文件包含只能走白名单映射表。
4
SQL 用字符串拼接"图省事"
报表导出、动态筛选这类需求最容易出现 "WHERE status = '$status'"。所有值走预处理绑定，动态列名/表名走白名单。
5
循环里访问关联属性，N+1 到麻木
100 个订单 = 101 条 SQL，还全都是小查询。开发环境开 Model::preventLazyLoading() 让它直接抛异常，用 with() 预加载。
6
以为静态属性可以"缓存"数据
PHP-FPM 无共享：静态属性在请求结束即销毁，下一个请求重新计算。跨请求缓存只能放 Redis/APCu，进程内缓存只对单次请求有效。
7
上线没开 OPcache，或开了但 files 数不够
每个请求都在现场编译几百个 PHP 文件。另外 opcache.max_accelerated_files 小于项目文件数时，缓存反复失效，症状是"时快时慢"。
8
composer.lock 不进 Git，线上跑 composer update
同一份 composer.json 每次解析出的依赖版本可能不同，昨天好的代码今天挂。生产只允许 composer install --no-dev --optimize-autoloader。
9
站点根目录指到项目根，.env 裸奔
浏览器直接访问 /.env 就能下载数据库密码和 APP_KEY。根目录必须指到 public/，并加 Nginx 隐藏文件拦截。APP_KEY 泄露后要轮换。
10
队列任务不幂等、不监控
at-least-once 语义下重投必然发生，不幂等就重复发邮件/重复加钱。加上失败任务表和 Horizon 告警，队列堆积是事故前奏。
自测

六道题

1. 订单列表页展示 100 个订单及其用户名，实际向 MySQL 发了多少条查询？
正确答案：101 条。这是教科书式的 N+1：主查询 1 条，循环内每个 $order->user 触发一次懒查询共 100 条。修法是 Order::with('user') 预加载，2 条 SQL 解决。
2. unserialize($_POST['data']) 直接反序列化用户输入，最严重的后果是？
正确答案：对象注入 → POP 链 → RCE。unserialize 会实例化任意类并触发 __destruct/__wakeup 等魔术方法，攻击者串联框架和库里现成的"gadget"就能执行代码。跨服务传数据一律用 JSON。
3. 在 PHP-FPM 的无共享架构下，哪种方式能跨请求保存数据？
正确答案：都不能，必须用外部存储。worker 处理完请求就把所有进程内状态销毁，下一个请求从零引导框架。登录态、限流计数这类跨请求状态必须放 Redis（或 Session 驱动指到 Redis）。
4. 校验密码重置 token，正确的比较方式是？
正确答案：hash_equals()。== 有类型转换和"魔术哈希"问题（"0e..." 开头会被判等），还有字节级时序攻击；hash_equals 是恒定时间比较，且要求严格相等。
5. composer update 和 composer install 的区别是？生产部署用哪个？
正确答案：生产用 composer install。update 会重新解析依赖版本（今天解析出的和明天可能不同），install 严格按 composer.lock 安装，保证环境可复现。lock 文件必须提交 Git。
6. 生产环境 OPcache 的推荐配置是？
正确答案：validate_timestamps=0。生产代码不会热更新，关掉 mtime 检查可去掉每次请求的 stat 开销；代价是发版后必须重启 FPM（kill -USR2 平滑 reload）。留 1 会让 OPcache 周期性 stat 全部脚本文件，是隐性性能损耗。
