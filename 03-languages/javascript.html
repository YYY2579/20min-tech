开始前

两个运行环境，两套细节

JavaScript 的"标准"叫 ECMAScript，它只规定语言本身。setTimeout、console、fetch 这些是宿主环境提供的，浏览器和 Node 的实现并不完全一样。本文以浏览器为主，Node 的差异会单独标注。

// 1. 打开控制台（F12），这几行先跑一遍，建立直觉
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// 输出顺序：1 4 3 2 —— 这就是本篇文章的第一课

// 2. 看一个值到底是什么类型
console.log(typeof null);            // "object"（历史 bug，永远修不了）
console.log(Object.prototype.toString.call([]));   // "[object Array]"

// 3. Node 里确认版本与事件循环阶段
node -v
node --trace-uncaught app.js
先记住一个区分：语言层（作用域、this、原型、类型转换）在所有引擎里行为一致；宿主层（定时器精度、微任务与渲染的顺序、模块解析）各环境有差异。
比如 process.nextTick 只在 Node 有，而且它优先于 Promise 微任务；浏览器里根本没有这个东西。
阅读姿势：这篇不教 for 怎么写。每个模块都在回答同一个问题——"引擎在这一刻到底做了什么决定"。理解了决定，语法只是表象。
模块 1

事件循环：单线程怎么做到"并发"

JS 的执行线程只有一个。所谓异步，不是"同时做多件事"，而是"把回调排进队列，等当前这段代码跑完再依次取出执行"。理解队列的优先级，就理解了 80% 的"为什么我的代码没按顺序执行"。

三个组成部分

组件是什么例子
调用栈 Call Stack当前正在执行的函数帧，后进先出任何同步函数调用
宏任务队列 Task Queue一轮事件循环取一个任务执行setTimeout / setInterval / I/O / 用户事件 / MessageChannel
微任务队列 Microtask Queue当前任务结束后立刻清空，清空过程中新产生的微任务也一并执行Promise.then / queueMicrotask / MutationObserver

一轮循环的精确顺序

取出一个宏任务，压入调用栈执行，直到栈空。
清空微任务队列。执行过程中新产生的微任务会被追加到队尾，同一轮内全部执行完，不会留到下一轮。
（浏览器）可能发生渲染：样式计算 → 布局 → 绘制。这一步不是每轮都发生，取决于刷新率和是否有视觉变更。
取下一个宏任务，回到第 1 步。
console.log('A');                          // 同步
setTimeout(() => console.log('B'), 0);   // 宏任务
Promise.resolve()
  .then(() => console.log('C'))            // 微任务
  .then(() => console.log('D'));           // 微任务（上一行产生）
queueMicrotask(() => console.log('E'));   // 微任务
console.log('F');                          // 同步

// 输出：A F C E D B
// A、F 是同步代码，先跑完
// 然后清空微任务：C、E 入队顺序 → C E，C 执行时把 D 追加到队尾 → D
// 微任务清空后才取宏任务 B
微任务可以饿死渲染。如果微任务里不断产生新的微任务（比如递归 Promise.resolve().then(loop)），这一轮永远结束不了，页面直接卡死——比死循环更糟，因为死循环至少还能被调试器中断。
推论：不要用微任务做"分片处理大数组"，那不会让出主线程。要让出，必须用宏任务（setTimeout / MessageChannel）或 requestIdleCallback。

为什么 setTimeout(fn, 0) 不立即执行

  • 0 不是 0。HTML 规范规定嵌套层级超过 5 层的定时器，最小延迟被钳制为 4ms；后台标签页里定时器还会被节流到 1 秒甚至更久。
  • 它是个宏任务。即使延迟真的是 0，也必须等当前同步代码跑完、微任务清空，才轮到它。
  • 计时从"注册"开始，但执行要看队列。如果主线程被一段 200ms 的同步代码占住，你的 0ms 定时器会在 200ms 后才跑。
// 实测：0ms 定时器的实际延迟
const t0 = performance.now();
setTimeout(() => {
  console.log('实际延迟', performance.now() - t0);   // 常见 1~5ms
}, 0);

// 用 MessageChannel 可以拿到更快的"宏任务"（不受 4ms 钳制）
const ch = new MessageChannel();
ch.port1.onmessage = () => console.log('next tick');
ch.port2.postMessage(null);
API队列类型典型用途
Promise.then / catch / finally微任务异步结果处理，优先级最高
queueMicrotask微任务确保在渲染前执行，且不产生额外 Promise
MutationObserver微任务监听 DOM 变更，回调在渲染前批量触发
setTimeout / setInterval宏任务延迟执行、轮询（注意 4ms 钳制）
requestAnimationFrame渲染前回调动画，每帧一次，与刷新率对齐
requestIdleCallback空闲回调低优先级后台计算
process.nextTick（Node）独立队列，优先于微任务Node 内部大量使用，业务代码慎用
Node 的事件循环不是"一个队列"，而是六个阶段：timers → pending callbacks → idle/prepare → poll → check（setImmediate）→ close callbacks。每个阶段之间都会清空 process.nextTick 队列和 Promise 微任务队列。
所以 setTimeout(fn,0) 和 setImmediate(fn) 谁先执行，在 Node 里取决于当前在哪个阶段——在主模块里顺序不确定，在 I/O 回调里 setImmediate 一定先。这个不确定性是真实存在的，不要依赖它。
模块 2

this：五种绑定，一条优先级

this 不指向"函数自己"，也不指向"函数的作用域"。它由调用方式在运行期决定——唯一例外是箭头函数，它在定义时就锁死了。

绑定规则调用形式this 指向
默认绑定fn()非严格模式 → globalThis；严格模式 → undefined
隐式绑定obj.fn()obj（只看调用时点号左边是谁）
显式绑定fn.call(o) / apply(o) / bind(o)o
new 绑定new Fn()新创建的实例对象
箭头函数() => {}没有自己的 this，取定义处外层作用域的 this

优先级：new > 显式 > 隐式 > 默认。箭头函数不参与这套规则，它直接跳过。

const obj = {
  name: 'obj',
  regular() { console.log(this.name); },
  arrow: () => console.log(this.name),   // 定义在模块顶层，this 是 undefined 或 module.exports
};

obj.regular();          // "obj"（隐式绑定）
obj.arrow();            // undefined（箭头函数的 this 跟 obj 无关）

const f = obj.regular;
f();                    // 丢失绑定：严格模式下 this === undefined，非严格是 globalThis
f.call(obj);            // "obj"（显式绑定救回来）
最常见的 this 事故：把方法当回调传出去。
setTimeout(obj.method, 100)、arr.map(obj.method)、el.addEventListener('click', obj.method)——这三种写法都会丢失 this，因为调用点变成了裸函数调用。
修法：obj.method.bind(obj)、() => obj.method()、或者干脆把方法写成箭头函数字段（类字段写法）。

class 里的 this 更严格

class Counter {
  count = 0;
  // 箭头函数字段：每个实例各有一份，this 永久绑定到实例
  inc = () => { this.count++; };

  // 原型方法：所有实例共享，this 由调用方式决定
  dec() { this.count--; }
}

const c = new Counter();
setTimeout(c.inc, 0);      // ✓ 箭头字段，this 没问题
setTimeout(c.dec, 0);      // ✗ TypeError: Cannot read properties of undefined

// 原因：class 内部默认是严格模式，裸调用时 this 是 undefined，不是 globalThis
// 代价：箭头字段是实例属性，不在原型上，1000 个实例就多 1000 个函数对象

bind 的两个细节

function f(a, b) { console.log(this.x, a, b); }

const g = f.bind({ x: 1 }, 10);
g(20);                     // 1 10 20（bind 可以预置参数，这叫偏函数）

const h = g.bind({ x: 2 });  // 二次 bind 无效：this 已经锁死
h(30);                     // 1 10 30（this 仍然是 {x:1}）

// bind 返回的是"绑定后的新函数"，原函数不变
// 被 bind 过的函数，new 调用时 this 仍然指向新实例（new 优先级高于 bind）
三条实用结论：① 需要把方法当值传出去时，用箭头函数或 bind；② 类里如果方法会被解构或当回调，用箭头字段，但注意内存成本；③ 判断 this 时不要看函数在哪定义，只看调用表达式长什么样。
模块 3

原型链：JS 唯一的继承机制

JS 没有类。class 是语法糖，底层仍然是"对象 → 原型对象 → 原型的原型 → null"这条链。理解两个容易混的东西：__proto__ 和 prototype。

名字是什么谁能有
obj.__proto__对象的实际原型（规范里叫 [[Prototype]]），属性查找就是沿着它走所有对象
Fn.prototype一个普通对象属性，当 Fn 被 new 调用时，会把它设为新实例的 [[Prototype]]只有函数（箭头函数没有）
Object.getPrototypeOf(o)读原型的标准方法，等价于读 __proto__ 但更安全—
function Person(name) { this.name = name; }
Person.prototype.greet = function() { return 'hi ' + this.name; };

const p = new Person('ann');
Object.getPrototypeOf(p) === Person.prototype;   // true
p.greet();                                        // 找到的是 Person.prototype.greet

// 查找路径：p 自身 → Person.prototype → Object.prototype → null
p.toString();        // 来自 Object.prototype
p.hasOwnProperty('name');   // true，自身属性
p.hasOwnProperty('greet');  // false，来自原型

class 只是糖，但有四个真实差异

class Animal {
  constructor(name) { this.name = name; }
  speak() { return '...'; }
}
class Dog extends Animal {
  speak() { return 'woof'; }
  static create(n) { return new Dog(n); }
}
const d = new Dog('rex');
Object.getPrototypeOf(Dog.prototype) === Animal.prototype;  // true
Object.getPrototypeOf(Dog) === Animal;                       // true（静态方法也继承）
差异class函数构造器
必须用 new 调用是，否则 TypeError否，裸调用会污染全局
内部严格模式是（方法体内 this 默认 undefined）否，取决于文件
方法可枚举否（不可枚举）是（会被 for...in 遍历到）
变量提升不提升（TDZ）函数声明会提升
原型链查找是有成本的。读一个不存在的属性，引擎要沿整条链走到 null。更麻烦的是内联缓存（inline cache）退化：同一个函数如果被传入结构差异很大的对象，属性访问会从"单态"退化为"多态"甚至"超态"，性能可能掉几倍到几十倍。
实践：热路径上的对象保持相同的"形状"（属性的增删顺序一致）；纯字典用途用 Object.create(null) 避免走到 Object.prototype；不要给 Object.prototype 加东西。 
// 用原型实现"类"的经典模式，理解它能看懂大量老代码
function Shape() {}
Shape.prototype.area = function() { return 0; };

function Circle(r) { this.r = r; }
Circle.prototype = Object.create(Shape.prototype);   // 建立原型链
Circle.prototype.constructor = Circle;                // 修回 constructor
Circle.prototype.area = function() { return Math.PI * this.r ** 2; };

// 现代写法（更干净）
const proto = { area() { return 0; } };
const circle = Object.create(proto, {
  r: { value: 2, writable: true, enumerable: true },
});
模块 4

闭包与作用域：变量到底活多久

闭包不是"函数里返回函数"这种语法现象，而是：函数在定义时就记住了它所在的词法环境，即使外层函数已经返回，那个环境依然活着。这是 JS 能做模块、能做私有状态、能做柯里化的根本原因。

function makeCounter() {
  let n = 0;                       // 被闭包捕获，不会随函数返回而销毁
  return {
    inc: () => ++n,
    get: () => n,
  };
}
const c = makeCounter();
c.inc(); c.inc();
console.log(c.get());   // 2
// n 无法从外部访问，这就是"私有变量"——在 class 的 # 私有字段出现之前，
// 这是 JS 唯一的封装手段

// 经典：循环里的 var 与 setTimeout
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));   // 3 3 3 —— 三个闭包共享同一个 i
}

for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i));   // 0 1 2 —— 每轮迭代创建新的绑定
}
// let 在 for 里的行为是规范特例：每次迭代都复制一份新的绑定

// var 的函数作用域会穿透块
if (true) { var leaked = 1; }
console.log(leaked);   // 1
if (true) { let hidden = 1; }
// console.log(hidden);  // ReferenceError

暂时性死区（TDZ）

console.log(a);   // undefined —— var 提升并初始化

console.log(b);   // ✗ ReferenceError: Cannot access 'b' before initialization
let b = 1;

// TDZ 的范围是从"进入作用域"到"声明语句执行"之间
function f() {
  // 这里就是 x 的 TDZ
  const x = 1;
}
const 只保证"绑定"不变，不保证值不变。
const arr = [1]; arr.push(2); 完全合法，arr 仍然指向同一个数组。
需要真正不可变，要用 Object.freeze()——但它只冻结一层，嵌套对象仍然可改，需要递归冻结或 structuredClone + 深冻结。

闭包的两个代价

  • 内存。被捕获的变量不会释放。如果一个闭包捕获了很大的对象，而这个闭包被长期持有（事件监听、定时器、缓存），这块内存就一直占着。这是前端内存泄漏的头号来源。
  • 旧值。闭包捕获的是绑定，不是值。所以循环里、异步回调里读到的往往是"最后一次赋值"的结果——这就是著名的"闭包陷阱"，在 React Hooks 里会被放大成"状态读不到最新值"。
// 泄漏示例：监听器持有大对象，且从不移除
function attach() {
  const bigData = new Array(1e6).fill('x');
  document.getElementById('btn').addEventListener('click', () => {
    console.log(bigData.length);   // 闭包捕获了 bigData
  });
}
// 只要元素还在 DOM 里，bigData 就释放不掉
// 修法：用完 removeEventListener，或用 WeakRef / 把数据放在外部按需取
模块 5

类型转换：== 到底做了什么

JS 是弱类型语言，但不是随机类型。转换有明确规则，只是规则分两步：先 ToPrimitive（对象转原始值），再按类型对转换。搞懂这两步，所有"诡异"的等式都能推出来。

== 的比较规则（按顺序匹配）

两边类型行为
相同类型直接按 === 比较（但 NaN !== NaN，+0 === -0）
null == undefinedtrue（规范特例，只有这两者互等）
null / undefined 与其他false（不会转成 0，这是最容易记错的）
number == stringstring 转 number
boolean == 任意boolean 先转 number（true→1，false→0）
object == 原始值object 先 ToPrimitive（先 valueOf 后 toString），再比较
[] == false
// 1. false 是 boolean → 转成 0        → [] == 0
// 2. [] 是 object → ToPrimitive：valueOf 返回数组本身（不是原始值），
//    改用 toString → ""                → "" == 0
// 3. string 与 number → "" 转成 0      → 0 == 0
// 结果：true

[] == ![]        // true（![] 是 false，回到上一题）
null == 0        // false（特例：null 只和 undefined 相等）
null >= 0        // true（>= 走的是数值比较，null 转 0）
undefined == 0   // false
NaN == NaN       // false
'1' == 1         // true
'1' === 1        // false
工程结论：永远用 ===。唯一值得用 == 的场景是 x == null——它能同时匹配 null 和 undefined，是判断"空值"的惯用法。
其它任何情况用 == 都是在给未来的自己埋雷，尤其是 0 == ''、'' == false 这类"看起来该相等"的组合。

+ 的两种语义

// 规则：先对两个操作数做 ToPrimitive，只要有一个是 string，就做字符串拼接
1 + 2          // 3
'1' + 2        // "12"
1 + '2'        // "12"
1 + 2 + '3'    // "33"（从左到右：先 3，再拼 "3"）
'1' + 2 + 3    // "123"

[] + []        // ""（两个空数组都变空字符串）
[] + {}        // "[object Object]"
({}) + []      // "[object Object]"
[1,2] + [3]    // "1,23"（数组 toString 是 join(',')）

// 其它算术运算符只做数值转换
'6' - 1        // 5
'6' * '2'      // 12
'6' / '2'      // 3

这就是为什么表单取到的值必须显式转换：input.value 永远是字符串，'10' + 5 得到 '105'，而 '10' - 5 得到 5。同一个表达式里两种语义并存，是 JS 里最日常的 bug 来源。

ToPrimitive 的细节

const obj = {
  valueOf() { return 42; },
  toString() { return 'obj'; },
};
obj + 1        // 43（+ 走 default hint，先 valueOf）
`${obj}`       // "obj"（模板字符串走 string hint，先 toString）
String(obj)    // "obj"
Number(obj)    // 42

// Symbol.toPrimitive 可以完全接管
const o2 = { [Symbol.toPrimitive](hint) { return hint === 'number' ? 1 : 'x'; } };
o2 * 2         // 2
`${o2}`       // "x"
显式转换的三条正路：Number(x)（严格，非法输入得 NaN）、parseInt(x, 10)（宽松，从开头解析到非法字符）、Boolean(x)（只有 0、-0、NaN、''、null、undefined、false 这七个是假值）。
注意 parseInt('08') 在老引擎里会被当成八进制，所以永远传第二个参数 10。
模块 6

异步演进：从回调到 await

三种写法解决的是同一个问题，但错误处理和组合能力完全不同。理解每一代为什么被淘汰，比记住 API 重要。

第一代：回调

getUser(id, (err, user) => {
  if (err) return handle(err);
  getOrders(user.id, (err2, orders) => {
    if (err2) return handle(err2);   // 每层都要重复判断
    getDetail(orders[0].id, (err3, detail) => {
      if (err3) return handle(err3); // 缩进越来越深，错误处理越容易漏
    });
  });
});

回调的问题不是"难看"，而是三个结构性的：无法用 try/catch 捕获异步错误（错误在另一个调用栈里抛出）、无法组合（想并发三个请求再合并，得自己维护计数器）、无法取消。

第二代：Promise

状态说明
pending初始状态，既未成功也未失败
fulfilled成功，值不可再变
rejected失败，原因不可再变
// then 永远返回一个新的 Promise，这是链式调用的基础
fetch('/api/user')
  .then(r => {
    if (!r.ok) throw new Error('HTTP ' + r.status);  // throw → 变成 rejected
    return r.json();                                  // 返回 Promise → 会被展开
  })
  .then(user => fetch('/api/orders/' + user.id))
  .then(r => r.json())
  .catch(err => console.error(err))     // 捕获链条上任意一环的错误
  .finally(() => hideLoading());        // 无论成功失败都执行
三个高频错误：
① 忘记 return。.then(() => { fetch(x) }) 没有 return，下一个 then 拿到的是 undefined，而且这个请求的错误会变成未处理拒绝；
② catch 放太早。.then(a).catch(b).then(c) 里 b 捕获后，c 仍会执行（catch 也返回 fulfilled 的 Promise）；
③ 没有 catch。浏览器会触发 unhandledrejection 事件，Node 从 15 起默认直接终止进程。

第三代：async / await

async function load(id) {
  try {
    const r = await fetch('/api/user/' + id);
    if (!r.ok) throw new Error('HTTP ' + r.status);
    const user = await r.json();
    return user;                        // async 函数总是返回 Promise
  } catch (e) {
    console.error(e);                   // 同步 try/catch 就能捕获异步错误
    throw e;                            // 想让调用方也感知，必须重新抛
  } finally {
    hideLoading();
  }
}

// await 后面不是 Promise 也没关系，会被 Promise.resolve 包一层
const x = await 42;    // 42，但会多一个微任务 tick
async/await 最大的性能陷阱：把可以并行的写成串行。
const a = await fa(); const b = await fb(); —— 总耗时是两者之和。
改成 const [a, b] = await Promise.all([fa(), fb()]); —— 总耗时是两者最大值。
这不是语法问题，是语义问题：await 的本质是"暂停当前函数，等结果"。暂停两次就是串行两次。

组合器：四个方法，四种失败语义

方法成功条件失败行为
Promise.all全部成功任一失败立即 reject（其他请求仍在跑，结果被丢弃）
Promise.allSettled永远成功返回每个的 {status, value|reason}，不会 reject
Promise.race第一个 settle 的第一个失败的会直接 reject
Promise.any第一个成功的全部失败才 reject，抛 AggregateError
// all：要么全拿到，要么全不要 —— 适合"缺一个就没法渲染"的场景
const [user, orders] = await Promise.all([getUser(), getOrders()]);

// allSettled：部分失败也要展示 —— 适合仪表盘、批量操作
const results = await Promise.allSettled(urls.map(u => fetch(u)));
const ok = results.filter(r => r.status === 'fulfilled');

// any：多源竞速，谁先成功用谁 —— 适合多 CDN 容灾
const data = await Promise.any(mirrors.map(m => fetch(m)));

七个数值与集合的陷阱

1. 0.1 + 0.2 !== 0.3

0.1 + 0.2                  // 0.30000000000000004
0.1 + 0.2 === 0.3          // false

// 原因：IEEE 754 双精度，64 位里 1 位符号、11 位指数、52 位尾数
// 0.1 在二进制里是无限循环小数，存进去就被截断了

// 判断相等要用误差范围
Math.abs(a - b) < Number.EPSILON      // 只适用于量级接近 1 的数

// 金额场景：用整数分，或字符串 + 定点库
const cents = 1999;                   // 19.99 元
(cents / 100).toFixed(2);              // "19.99"（注意 toFixed 返回字符串）

// 安全的整数范围
Number.MAX_SAFE_INTEGER                // 9007199254740991（2^53 - 1）
// 超过就用 BigInt：9007199254740993n

2. NaN 不等于自己

NaN === NaN            // false（规范规定）
Object.is(NaN, NaN)      // true（唯一可靠的判断之一）
Number.isNaN(NaN)       // true（不会做类型转换）
isNaN('abc')             // true —— 全局 isNaN 会先转数字，别用

// Object.is 与 === 只在两处不同
Object.is(0, -0)           // false（=== 是 true）
Object.is(NaN, NaN)      // true （=== 是 false）

3. sort 默认按字符串排序

[10, 9, 1, 100].sort()               // [1, 10, 100, 9]  ← 字典序！

// 要保留原数组：[...arr].sort((a,b) => a-b) 或 arr.toSorted()（ES2023）

// 比较器返回 NaN 会导致排序结果未定义（比如元素里有 undefined）

4. 浅拷贝与深拷贝

方式层级说明

模块 8

模块化：ESM 与 CommonJS

两套模块系统并存是 JS 的历史包袱。它们的差异不只是 import/require 的写法，而是加载时机、绑定语义、依赖图能否静态分析——最后一点直接决定了 tree shaking 能不能做。

维度ESM（import / export）CommonJS（require / module.exports）
加载方式静态，编译期确定依赖图运行时，require 是一个函数调用
执行时机依赖先全部求值，再执行本体require 到哪一行才执行到哪
导出绑定活绑定（值变了导入方能看到）值拷贝（导出那一刻的快照）
能否条件导入否（顶层静态），动态用 import()是，可以在 if 里 require
顶层 await支持不支持
严格模式默认严格默认非严格
this 顶层值undefinedmodule.exports
tree shaking可以（静态分析未使用的导出）基本不行
// ESM：导出的是"绑定"，不是值的快照
// counter.js
export let count = 0;
export function inc() { count++; }

// main.js
import { count, inc } from './counter.js';
inc();
console.log(count);   // 1 —— 看到的是最新值

// CommonJS：导出的是值的拷贝
// counter.cjs
let count = 0;
module.exports = { count, inc() { count++; } };

// main.cjs
const { count, inc } = require('./counter.cjs');
inc();
console.log(count);   // 0 —— 拿到的是导出时的快照
为什么 ESM 必须是静态的？因为打包工具要在不执行代码的前提下知道"哪些导出被用到了"。如果 import 可以写在 if 里、模块名可以是变量，静态分析就不可能，tree shaking 也就无从谈起。
代价是：ESM 的 import 会被提升到模块顶部，且不能用在条件语句里。需要按需加载就用动态 import()，它返回 Promise，也是代码分割的基础。

循环依赖：两套系统都会出问题，但表现不同

// ESM：a.js 与 b.js 互相 import
// a.js
import { b } from './b.js';
export const a = 'a';
console.log('a sees b =', b);

// b.js
import { a } from './a.js';
export const b = 'b';
console.log('b sees a =', a);

// 从 a.js 入口执行：
// b.js 先执行，此时 a 还在 TDZ → ReferenceError: Cannot access 'a' before initialization
// 这就是 ESM 循环依赖的典型表现：不是 undefined，而是直接抛错

CommonJS 的循环依赖不会抛错，但会拿到不完整的 exports：require 返回的是当前已经挂到 module.exports 上的那部分，未执行到的导出是 undefined。这比报错更难查，因为代码能跑，只是某个值是 undefined。

避免循环依赖的三条实践：① 把共享的类型/常量抽到第三个模块（不依赖任何一方）；② 用依赖注入代替模块级 import（把需要的函数当参数传进来）；③ 真需要互相引用时，用动态 import() 延迟到运行时。
检测手段：madge --circular src/ 可以扫出整个项目的循环依赖图。

互操作：三个必须知道的细节

// 1. 在 ESM 里导入 CJS：default 就是 module.exports
import lodash from 'lodash';          // 整个 module.exports
import { debounce } from 'lodash';      // Node 会尝试静态分析命名导出，不保证成功

// 2. 在 CJS 里导入 ESM：只能用动态 import()
const mod = await import('./esm.mjs');   // require() 不支持 ESM

// 3. ESM 里没有 __dirname / __filename / require
import { fileURLToPath } from 'node:url';
import path from 'node:path';
const __dirname = path.dirname(fileURLToPath(import.meta.url));

常见坑

十个真实事故

1
用 == 比较，被隐式转换骗了
0 == ''、[] == false、'1' == 1 全都成立。统一用 ===，只有 x == null 这个惯用法例外。
2
把方法当回调传出去，this 丢了
setTimeout(obj.fn)、arr.map(obj.fn) 都会变成裸调用。用 bind、箭头函数包装，或写成类字段箭头函数。
3
循环里用 var 配异步回调
三个 setTimeout 打印出三个相同的最终值，因为闭包共享同一个 var 绑定。改用 let，或立刻用 IIFE 捕获当前值。
4
以为 setTimeout(fn, 0) 会立刻执行
它是宏任务，要等同步代码和所有微任务跑完；嵌套超过 5 层还会被钳制到最小 4ms。想让出主线程要用宏任务，不是微任务。
5
Promise 链里忘记 return
下一个 then 拿到 undefined，请求的错误也变成未处理拒绝。箭头函数带花括号时一定要检查有没有 return。
6
把可以并行的 await 写成串行
连续两个 await 的耗时是两者之和。互不依赖的请求用 Promise.all 并发，耗时取最大值。
7
用 sort() 排数字，得到字典序
[10,9,1].sort() 得到 [1,10,9]。必须传比较器 (a,b) => a - b。另外 sort 原地修改，需要副本就先展开。
8
用 JSON 深拷贝，丢了 Date 和 undefined
Date 变成字符串、undefined 和函数直接消失、循环引用抛错。用 structuredClone，注意它也不保留 class 原型。
9
用浮点数算钱
0.1 + 0.2 !== 0.3，累加多次后误差会放大到分。金额一律用整数分存储和计算，展示时再除 100。
10
在 ESM 项目里直接 require，或用 __dirname
"type": "module" 之后 require、__dirname、__filename 都不存在。用 import.meta.url 推导路径，或用 createRequire 兼容老包。
自测

六道题

1. 下面代码的输出顺序是？
console.log(1); setTimeout(()=>console.log(2)); Promise.resolve().then(()=>console.log(3)); console.log(4);
正确答案：1 4 3 2。同步代码先跑完（1、4），然后清空微任务队列（3），最后才取宏任务（2）。微任务永远优先于下一个宏任务。
2. 严格模式下，const f = obj.method; f(); 里 this 是什么？
正确答案：undefined。this 由调用点决定，f() 是裸调用，走默认绑定；严格模式下默认绑定是 undefined，非严格才是 globalThis。这就是"丢失绑定"。
3. 关于 __proto__ 和 prototype，哪个说法对？
正确答案：后者。属性查找沿 [[Prototype]]（即 __proto__）走；Fn.prototype 只是一个普通属性，被 new Fn() 用作新实例的原型。
4. 为什么 [] == false 成立？
正确答案：前者。注意 [] 在布尔上下文里其实是真值（只有七个假值），这里的相等完全来自 == 的转换规则，不是"空数组等于假"。
5. Promise.all 与 Promise.allSettled 的关键区别是？
正确答案：失败语义不同。两者都是并行的。all 适合"缺一个就不能渲染"，allSettled 适合"部分失败也要展示"，比如仪表盘。
6. 为什么 CommonJS 难以做 tree shaking？
正确答案：运行时才能确定依赖。require 可以写在 if 里、参数可以是变量，打包工具无法静态知道哪些导出被用到。ESM 的 import 必须在顶层静态书写，才能被分析。
