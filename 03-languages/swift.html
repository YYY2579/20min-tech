Swift 是什么，在哪跑

事实说明
出身Apple 2014 年发布，替代 Objective-C 的一门编译型、类型安全语言。2015 年底开源，跑在 Apple 平台 + Linux + Windows

模块 1

可选型：Optional 是一种类型

Swift 的 null safety 不在语法糖层，而在类型系统里：Optional 是标准库定义的泛型枚举，String? 就是 Optional<String> 的语法糖。

// Optional 的本质（简化版定义）
enum Optional<Wrapped> {
    case none            // nil
    case some(Wrapped)   // 有值
}

var name: String? = "Tom"       // Optional<String>.some("Tom")
name = nil                        // Optional<String>.none —— 赋 nil 合法，因为类型是 String?

var mustHave: String = "Tom"   // 非可选：永远不可能为 nil
// mustHave = nil            ← 编译错误：nil 不能赋给非可选类型

四种解包方式

方式语义nil 时
if let x = opt绑定解包：非空时代入新常量 x走 else 分支
guard let x = opt守卫解包：非空时 x 在函数剩余部分可见；空则必须退出（return / throw / break）执行 else 后退出当前作用域
opt ?? defaultnil 合并：空则用默认值得到 default
opt!强制解包：断言非空运行时崩溃：Fatal error: Unexpectedly found nil while unwrapping an Optional value
// if let：局部解包，作用域仅在花括号内
if let name = name {
    print("名字长度 \(name.count)")
} else {
    print("没有名字")
}

// Swift 5.7 起同名简写：if let name { }

// guard let：提前退出模式，Happy Path 在右边
func greet(_ person: String?) -> String {
    guard let name = person else {
        return "匿名用户"
    }
    return "你好，\(name)"     // name 在这里可用，无需再解包
}

// ?? 链：一层层兜底
let display = user.nickname ?? user.name ?? "佚名"

// 可选链：任何一环为 nil，整条链短路，且结果本身仍是可选
let street = user.address?.street?.name   // String? —— 别忘再解包

// 可选绑定可以一次绑多个（逗号分隔），任一为空整体失败
if let name = user.name, let addr = user.address {
    print("\(name) 住在 \(addr.city)")
}

可选链 vs 强制解包 vs 隐式解包

隐式解包可选型（String!）是给"现在没有、但用之前一定有"的值用的，典型场景是 Interface Builder 的 outlet：@IBOutlet weak var label: UILabel!。它在赋值前就访问会崩溃，报错 Unexpectedly found nil while implicitly unwrapping an Optional value。
工程铁律：业务逻辑里不写 !（if let / guard let / ?? 三件套覆盖 95% 场景）；! 只出现在测试和对不变量有 100% 把握的地方。SwiftUI 时代 outlet 都被 @State 取代，String! 的存在感已越来越低。

可选的进阶操作

// map / flatMap 直接作用在 Optional 上
let len = name.map { $0.count }          // Int? —— 有值则变换，nil 则 nil
let nested = opt.map { $0.asInt() }.flatMap { $0 }   // 防止 Optional<Optional<T>>

// switch 可以直接匹配 nil
switch name {
    case .some(let v): print("有值 \(v)")
    case .none:     print("nil")
}

// == nil 判空也合法（编译器魔法）
if name == nil { ... }
模块 2

值类型 vs 引用类型

三种声明，两种语义

声明语义赋值时发生什么
struct值类型复制一份，两个变量此后互不影响
enum值类型同上（枚举可带关联值）
class引用类型复制的是引用，两个变量指向同一对象，改一个两个都变
struct Point { var x: Int; var y: Int }

var a = Point(x: 1, y: 2)
var b = a                    // 复制：b 是独立副本
b.x = 99
print(a.x)                  // 1 —— a 不受影响

class Counter { var count = 0 }
let c1 = Counter()
let c2 = c1                   // 同一对象
c2.count = 10
print(c1.count)             // 10 —— 同一个实例

// let + struct = 深度不可变，编译期就锁死
let fixed = Point(x: 0, y: 0)
// fixed.x = 1             ← 编译错误：let 的结构体属性也不能改

写时复制（COW）：值类型的性能魔法

String、Array、Dictionary、Set 都是 struct，但复制百万级元素不可能真拷贝——标准库用写时复制：复制时只复制引用和引用计数，任何一方尝试修改时才真正拷贝底层缓冲区。所以 var b = a（a 是 Array）是 O(1)。

自定义 struct 没有自动 COW。如果你写了一个持有大数组的 struct，每次赋值都真拷贝。需要时手动实现（isKnownUniquelyReferenced + 引用类型存储桶），或者——90% 的场景直接用标准库容器 + 组合，别自己造。

怎么选：Apple 官方指南的落地版

选 struct（值类型）选 class（引用类型）
建模数据：坐标、尺寸、金额、配置项、DTO需要共享可变状态：数据库连接、缓存、下载管理器
需要与外部状态无关的独立性需要继承（struct 不能继承）
多线程安全诉求：值类型天然无数据竞争需要 identity 语义（=== 判断同一对象）
默认选项——Apple 建议"优先 struct"与 OC 桥接的既有类型

枚举：不只是常量集合

// 带关联值的枚举：每个 case 可以携带不同类型的数据
enum NetworkResult {
    case success(Data, HTTPURLResponse)
    case failure(Error)
    case cancelled
}

func handle(_ r: NetworkResult) {
    switch r {
        case .success(let data, let resp):
            print("\(resp.statusCode): \(data.count) 字节")
        case .failure(let err):
            print("错误 \(err)")
        case .cancelled:
            break
    }
}

// 递归枚举要加 indirect（值类型默认不能递归包含自己）
indirect enum LinkedList {
    case end
    case node(Int, LinkedList)
}
模块 3

ARC 与循环引用

Swift 的内存管理是编译期插入的自动引用计数：每个对象被强引用一次计数 +1，归零时立即析构。没有 GC，没有手动 free——唯一要防的是循环引用。

三种引用强度

强度计数释放后访问限制
strong（默认）+1安全互持即泄漏
weak+0自动置 nil（运行时清零）必须是 var，必须是可选类型
unowned+0崩溃（访问已释放内存）可以是 let，非可选

循环引用长什么样

// 场景 1：两个对象互持（经典：父持子、子回持父）
class Parent {
    var child: Child?
}
class Child {
    var parent: Parent?     // ✗ strong 回指 → Parent/Child 永远无法归零
}

// ✓ 修复：回指的一方用 weak
class Child {
    weak var parent: Parent?  // weak 让引用计数不 +1，断开环
}

// 场景 2：闭包捕获 self（更隐蔽，更高频）
class ViewController: UIViewController {
    var onFinish: (() -> Void)?

    func setup() {
        onFinish = {
            // ✗ 闭包里直接用 self：闭包持 self，self 持闭包 → 泄漏
            self.dismiss(animated: true)
        }
        onFinish = { [weak self] in
            self?.dismiss(animated: true)   // ✓ 捕获列表降强度
        }
    }
}

weak 还是 unowned？

场景选择
delegate、dataSource（可能被提前释放，且回调时对方可能已走）weak var delegate: SomeDelegate?
闭包里 self 随时可能已被释放（异步回调、延时执行）[weak self]，self 变可选，配 self?.xxx
闭包与 self 同生共死、同步执行（如 lazy 初始化、动画 completion 里 self 一定活着）[unowned self]，写法干净但赌上安全性
判断口诀："回指用 weak，同步同寿用 unowned，拿不准就用 weak。"unowned 一旦对象已释放还去访问，直接 EXC_BAD_INSTRUCTION 崩溃且难以定位；weak 最坏情况只是变成 nil 走 else 分支。生产代码里 unowned 应当稀少——看到它先问一句"self 真的必然活着吗"。
排查工具：Xcode 的 Memory Graph Debugger（可视化循环引用）、Instruments 的 Leaks 模板、以及 deinit 里打日志确认对象真的被释放了。
模块 4

协议与扩展：Swift 的多态主力

Swift 的"接口"叫 protocol。struct / enum / class 都能实现协议——这让值类型也能参与多态，是"面向协议编程"（Protocol-Oriented Programming, POP）的地基。

// 协议声明：属性 + 方法要求
protocol Drawable {
    var area: Double { get }
    func draw() -> String
}

// struct 实现协议（注意：值类型也能"多态"）
struct Circle: Drawable {
    var radius: Double
    var area: Double { .pi * radius * radius }
    func draw() -> String { "圆(r=\(radius))" }
}

// 协议作为类型：统一处理不同实现
func renderAll(_ items: [Drawable]) {
    for item in items {
        print(item.draw())
    }
}

renderAll([Circle(radius: 1), Rectangle(), Triangle()])   // 异构集合

扩展：给协议默认实现 + 给类型加方法

// 协议扩展：给所有实现者提供默认实现
extension Drawable {
    func draw() -> String {
        "面积 \(area) 的图形"          // 默认实现
    }
}
// 具体类型自己实现了 draw() 就用具体的；没实现就用默认 —— 像 mixin

// 给现有类型加方法（不用继承、不用改源码）
extension String {
    func isEmail() -> Bool {
        contains("@") && contains(".")
    }
}

// 带约束的扩展：只对满足条件的类型生效
extension Array where Element: Numeric {
    func total() -> Element { reduce(0, +) }
}

// 协议关联类型 + 扩展：泛型算法的标准写法
protocol Container {
    associatedtype Item
    var count: Int { get }
    subscript(i: Int) -> Item? { get }
}

some 与 opaque type

some 是 Swift 5.1 引入的不透明结果类型：对外隐藏具体类型，只暴露"某个实现了协议的类型"，且编译器知道它到底是什么（保持静态分发）。

// 没有 some：每个返回不同类型的地方都要写泛型签名
func makeCollection() -> some Collection {
    [1, 2, 3]                  // 编译器知道是 Array<Int>，调用方只知道是 Collection
}

// SwiftUI 里 body 的类型：some View —— 整个框架的地基
struct ContentView: View {
    var body: some View {
        Text("Hello")
    }
}
协议扩展的方法是静态分发，不是动态分发。这点和 Kotlin 扩展函数一样：调用哪个实现取决于编译期声明的类型。具体类型自己写的方法（动态分发）优先于协议扩展的默认实现。混用"协议扩展"和"具体类型方法"时，用协议类型调用看到的是扩展实现，用具体类型调用看到的是自己的实现——行为差异是 POP 的经典面试题。
模块 5

闭包与尾随闭包

闭包 = 能捕获上下文的匿名函数。Swift 的闭包是引用类型（这点和 struct 函数不同），也是回调、排序、动画的核心工具。

// 完整形式
let add: (Int, Int) -> Int = { (a: Int, b: Int) -> Int in
    return a + b
}

// 类型推断：从上下文推断参数与返回类型，可省略
let nums = [3, 1, 2]
nums.sorted(by: >)                    // 运算符可直接当函数：升序排序
nums.sorted { $0 < $1 }                // 尾随闭包 + $0/$1 隐式参数

// 闭包捕获外部变量：捕获的是引用
var counter = 0
let incr = { counter += 1 }        // 闭包持有 counter
incr(); incr()
print(counter)                  // 2 —— 闭包改的是外面的 counter

尾随闭包：Swift 代码风格的标志

最后一个参数是闭包时，可以把闭包提到括号外，代码读起来像 DSL：

// 普通写法
UIView.animate(withDuration: 0.3, animations: {
    self.view.alpha = 0
}, completion: { finished in
    self.view.removeFromSuperview()
})

// 尾随闭包（Swift 5.3 起支持多个尾随闭包，第一个省略标签，其余保留）
UIView.animate(withDuration: 0.3) {
    self.view.alpha = 0
} completion: { finished in
    self.view.removeFromSuperview()
}

// SwiftUI 的 DSL 全靠尾随闭包嵌套
VStack {
    Text("标题")
    ForEach(items) { item in
        Text(item.name)
    }
}

逃逸与非逃逸

类型含义
非逃逸（默认）闭包在函数返回前执行完毕，函数一返回闭包就消亡。编译器可优化掉 retain/release，闭包内还可隐式使用 self
@escaping闭包可能"逃过"函数生命周期：存起来、传给别的线程异步执行。此时闭包里必须显式写 self（否则编译错误）——这是防循环引用的强制提醒
// @escaping 的典型形态：异步回调
func loadConfig(completion: @escaping (Result<Config, Error>) -> Void) {
    DispatchQueue.global().async {
        // ... IO ...
        completion(.success(config))
    }
}

// 调用方 + 循环引用处理
loadConfig { [weak self] result in
    guard let self = self else { return }
    self.apply(result)
}

// @autoclosure：把表达式自动包成闭包，调用处保持"普通表达式"观感
func logIf(_ condition: @autoclosure () -> Bool, _ msg: String) {
    if condition() { print(msg) }
}
logIf(1 > 0, "正数")       // 看起来就是普通参数
模块 6

错误处理：throws / try / do-catch

// 1. 定义错误：任意遵循 Error 协议的类型，惯例用 enum
enum ConfigError: Error {
    case fileNotFound(String)
    case invalidFormat(line: Int)
}

// 2. 抛出：函数标注 throws，用 throw 抛出错误
func loadConfig(path: String) throws -> Config {
    guard FileManager.default.fileExists(atPath: path) else {
        throw ConfigError.fileNotFound(path)
    }
    return parse(...)          // 正常 return
}

// 3. 捕获：do-catch 全都要 try
do {
    let cfg = try loadConfig(path: "/etc/app.conf")
    start(cfg)
} catch ConfigError.fileNotFound(let p) {
    print("找不到文件：\(p)")
} catch ConfigError.invalidFormat(let line) {
    print("第 \(line) 行格式错误")
} catch {
    print("其他错误：\(error)")     // 兜底分支，error 隐式可用
}

try 的四种形态

写法语义
try在 do-catch 里调用；错误向上传播给最近的 catch
try?把结果包成 Optional：抛错得 nil，成功得值。错误本身被丢弃
try!断言绝不抛错；抛了就崩溃。只用于 IOCTL 类 API 或测试
try await异步 throwing 函数的组合写法：let x = try await load()
// try? 的实战：失败就 nil，不关心为什么
let data = try? Data(contentsOf: url)      // Data?
let cfg = try? loadConfig(path: p)        // Config?

// try? 链上 ??：失败走默认值
let port = (try? readPort()) ?? 8080

// 注意：try? 会丢掉具体错误。需要诊断信息就老老实实 do-catch

// Result 类型：把成功/失败当值传递（错误回调场景）
func fetch(completion: (Result<User, NetworkError>) -> Void) {
    // ... 网络请求 ...
    completion(.success(user))       // 或 completion(.failure(.timeout))
}

fetch { result in
    switch result {
        case .success(let user): show(user)
        case .failure(let err): alert(err)
    }
}
throws vs Result 怎么选：同步调用链（函数直接调函数）用 throws——控制流清晰，编译器强制处理；异步回调（闭包里通知结果）用 Result 或 completion handler——因为 @escaping 闭包不能 throws。Swift 5.5 的 async/await 统一了两者：异步 throwing 函数 func f() async throws -> T，调用处 try await f()，do-catch 照常捕获。
模块 7

SwiftUI：声明式 UI 基本模式

SwiftUI（2019 发布，iOS 13+）的核心思想：UI 是状态的函数。你描述"数据长这样时界面该长什么样"，框架负责在数据变化时高效刷新。

import SwiftUI

struct CounterView: View {
    @State private var count = 0        // 视图私有状态

    var body: some View {                 // 描述界面（可多次求值）
        VStack(spacing: 16) {
            Text("点击了 \(count) 次")
                .font(.title)
            Button("点我 +1") {
                count += 1               // 改状态 → 框架自动重新求值 body
            }
        }
        .padding()
    }
}

五种数据流属性（背这张表就会用 SwiftUI）

属性包装器用途
@State视图自己私有的值类型状态（计数、开关、输入）。值变化触发重组
@Binding子视图读写父视图的状态（双向绑定），不持有数据本身
@StateObject视图创建并持有的引用型模型（ObservableObject），随视图生命周期
@ObservedObject视图使用但不持有的 ObservableObject（由外部传入）
@EnvironmentObject跨层级注入的共享模型（用户会话、主题），整棵子树可用
// ObservableObject + @Published：模型层的标准姿势
class UserViewModel: ObservableObject {
    @Published var name: String = ""     // 变化自动通知视图
    @Published var isLoading = false

    func load() {
        isLoading = true
        // 异步请求...
    }
}

struct ProfileView: View {
    @StateObject private var vm = UserViewModel()

    var body: some View {
        VStack {
            if vm.isLoading {
                ProgressView()
            } else {
                Text(vm.name)
            }
        }
        .onAppear { vm.load() }        // 生命周期钩子
    }
}

UIKit 命令式 vs SwiftUI 声明式

维度UIKitSwiftUI
心智模型创建控件 → 手动改状态 → 手动同步界面定义状态 → 界面 = f(状态)，框架 diff 后更新
视图类型UIView 是 class，引用类型，可变View 是 struct，值类型，body 可反复求值
异步边界GCD / 回调async/await + @MainActor
预览编译运行模拟器#Preview 实时渲染（Xcode 15+）/ PreviewProvider
布局Auto Layout 约束 / FrameVStack/HStack/ZStack + 修饰符链
SwiftUI 三定律：① body 是纯函数——不要在 body 里做 IO、发请求、改外部状态（副作用放 .onAppear / Button 动作里）；② View 是轻量值类型，创建一万个 Text 也不贵，框架只更新真正变化的部分；③ 数据驱动一切——界面不同步，99% 是数据没有用 @State/@Published 包起来，改了但框架不知道。
模块 8

与 Objective-C 互操作要点

存量 Apple 生态全是 OC 写的，Swift 的互操作是双向桥接。但两门语言的 nil 语义、类型系统差异极大，这里是事故高发区。

桥接机制

方向机制
Swift 调 OCBridging Header（{ProductModule}-Bridging-Header.h）：把要用的 OC 头文件 import 进去，全工程 Swift 可见

最大的语义断层：OC 的 nil 是"消息黑洞"，Swift 的 nil 是"必须显式处理的状态"。OC 里 [nil length] 返回 0 不崩；同样的代码迁移到 Swift，nil.count 直接崩溃。表现：从 OC 拿回来的 String! 没判空就用 → 崩溃；调 OC API 返回 nil 当"没数据"处理 → 在 Swift 里要先解包。迁移清单：所有 OC 头文件补 nullable/nonnull 标注；Swift 侧对返回值先 if let / guard let。
另外两个常见坑：① OC 的 instancetype 在 Swift 里仍是原类型，继承链正常；② Swift 的 enum、struct、泛型不能直接暴露给 OC（@objc 不支持泛型类型），共享模型层要么包一层 OC 类，要么下沉到 C 接口。
坑

十个线上坑

1
struct 里修改属性忘了加 mutating
值类型方法默认不能改自身属性，编译报 "cannot assign to property: self is immutable"。改属性的方法必须标 mutating func。
2
闭包里强引用 self，ViewController 永远不释放
闭包持 self、self 持闭包，引用计数到不了 0。所有 @escaping 闭包、存储型闭包属性都先写 [weak self]，再在闭包里 guard let self。
3
unowned 当 weak 用
unowned 在对象释放后不置 nil，访问即崩溃。异步/延时/生命周期不确定的场景一律 weak，别赌。
4
用 String! 图省事，运行期崩在解包上
隐式解包可选型每次使用都是一次未检查断言，崩溃信息只有一行 Fatal error。业务逻辑用 if let / guard let / ??，outlet 也建议逐步换成 @State。
5
数组下标越界
Swift 的 Array 越界访问是运行时崩溃（不像 Dictionary 返回 Optional）。遍历优先 for-in，取单个元素用 first / last / dropFirst，必须下标时先判断 indices.contains(i)。
6
可选链的结果忘了它还是 Optional
let street = user.address?.street 得到的是 String?，直接当 String 用会编译错误或（用了 !）崩溃。链式解包用 if let a = x, let b = a.y。
7
依赖协议扩展的"多态"
协议扩展的方法是静态分发，调用哪个实现取决于编译期类型；具体类型自己的方法才是动态分发。同一份代码换个声明类型行为就变。
8
@escaping 闭包里不写 self
Swift 6 起这是编译错误（显式 self 要求）。别用 self! 糊弄，正确姿势是 [weak self] + guard let self。
9
把 OC 的 nil 语义带进 Swift
OC 里给 nil 发消息安全返回 0，Swift 里访问 nil 可选直接崩。OC 迁移过来的 API 返回值先解包再计算。
10
enum 递归包含自身忘了 indirect
enum Node { case node(Int, Node) } 编译报 recursive enum 错误。加 indirect enum 即可（编译器自动装箱，引用语义）。
自测

六道题

1. var name: String? = nil 中，String? 的本质是？
正确答案：泛型枚举 Optional<String>。可空性是类型系统的一部分：nil 只是 Optional.none 的语法糖，解包就是 switch/if let 匹配 .some。这也是 Swift 和 Java null 的根本差异——Java 的 null 任何引用类型都能是，Swift 必须显式声明 Optional 才能是 nil。
2. delegate 属性应该用 weak 还是 unowned？
正确答案：weak。delegate 的持有方（如 VC）随时可能被释放，之后若还有回调进来，unowned 会访问已释放内存直接崩溃，weak 则自动置 nil 走安全路径。unowned 只用于"闭包与 self 同生共死且同步执行"的确定场景。
3. var b = a（a 是包含 10 万元素的 Array），随后 b.append(1)。会发生什么？
正确答案：写时复制（COW）。Array 是 struct，赋值时只复制引用和计数；直到某一方真正修改时才拷贝底层缓冲区。所以 Swift 的值类型既有"复制语义"的安全，又有接近引用类型的性能。自定义 struct 没有这个福利，需要手动实现。
4. func load() throws -> Data 被调用时，正确的错误捕获写法是？
正确答案：do-catch 包住 try。裸 try 只允许错误继续向上传播（本函数也得标 throws）。try? 会把错误吞成 Optional，try! 则断言不抛错、抛了直接崩——两者都只适用于特定场景。
5. VStack { Text("A"); Text("B") } 这种写法用到的语言特性是？
正确答案：尾随闭包。当函数最后一个参数是闭包时，Swift 允许把闭包移到括号外，函数签名不变。SwiftUI 的整个 DSL（VStack { ... }、List { ... }）都建立在此之上，读起来像声明式 markup。
6. struct ContentView: View { var body: some View { ... } } 中 some View 的含义是？
正确答案：不透明结果类型（opaque result type）。some 让编译器保留具体类型信息（静态分发、性能更好），同时向调用方隐藏。any View 则是存在类型（type erasure），有运行时开销，两者用途相反——框架 API 用 some，需要"异构集合"时才不得不用 any。
