模块 1

内存结构：每一块各自会怎么炸

背"堆栈方法区"没有意义。有意义的是：哪块线程私有、受哪个参数控制、溢出时抛哪个错误。

区域存什么私有参数溢出表现
程序计数器当前字节码行号是无唯一不会 OOM
虚拟机栈栈帧：局部变量表、操作数栈、动态链接、返回地址是-XssStackOverflowError / unable to create new native thread
堆对象实例、数组否-Xms -XmxOOM: Java heap space
元空间类元信息、字节码、运行时常量池否-XX:MaxMetaspaceSizeOOM: Metaspace
直接内存DirectByteBuffer 申请的堆外内存否-XX:MaxDirectMemorySizeOOM: Direct buffer memory
# 堆的分层（默认 NewRatio=2，SurvivorRatio=8）
┌──────────── 新生代 1/3 ────────────┬──── 老年代 2/3 ────┐
│   Eden 80%   │  S0 10% │  S1 10%  │   长期存活的对象    │
└──────────────┴─────────┴──────────┴────────────────────┘
     Minor GC 在这里发生                 Full / Mixed GC
  • Eden 占 80%：绝大多数对象活不过第一次 GC（弱代假设），空间压给 Eden 能减少 GC 次数。
  • 为什么容忍 10% 浪费：要复制的存活对象很少，复制比"标记-清除整片区域"快得多。
32GB 这个数字怎么来的：压缩指针（-XX:+UseCompressedOops）用 32 位表示地址，靠"右移 3 位"把范围放大到 32GB。堆一超过它就失效，每个引用从 4 字节变 8 字节，对象变大、缓存命中率下降。要么控制在 31GB 内，要么直接上 64GB 以上，中间地带最亏。

六种 OOM 与病因

错误信息几乎可以断定是
Java heap space对象太多或太大。先查泄漏，再看 -Xmx 是否过小
GC overhead limit exceeded98% 时间在 GC 却回收不到 2%，本质仍是堆不够或泄漏
Metaspace动态代理、CGLIB、脚本引擎、热部署导致的类加载器泄漏
unable to create new native thread线程数触到 ulimit -u 或 pid_max。加堆只会更糟
Direct buffer memoryNetty / NIO 的堆外内存没释放，或上限设得太小
Requested array size exceeds VM limit试图创建接近 Integer.MAX_VALUE 的数组
"unable to create new native thread" 最容易被误判。很多人第一反应是加堆，结果越加越糟 —— 堆越大，留给线程栈的空间越少。正确方向是数线程（jstack | grep '^"' | wc -l、ps -o nlwp），找谁在无限建线程。
模块 2

垃圾回收：分代假设、G1 的 Region、ZGC 的低延迟

GC 的所有设计都建立在一个统计事实上：绝大多数对象朝生夕死。由此推出"频繁回收一小块、偶尔回收全部"。

存活判定与晋升

不是引用计数（处理不了循环引用），而是从 GC Roots（栈上局部变量、静态属性、常量、JNI 引用、活跃线程）出发做可达性分析，走不到的就是垃圾。

晋升路径触发条件
年龄每熬过一次 Minor GC 年龄 +1，到 -XX:MaxTenuringThreshold（默认 15）进老年代
动态年龄判断Survivor 中同龄对象总和超过一半，这批直接晋升。这条最常被忽略，却是"对象提前变老"的主因
大对象超过 -XX:PretenureSizeThreshold 直接进老年代（仅 Serial / ParNew 有效）
担保失败Minor GC 前发现老年代放不下可能晋升的对象，退化为 Full GC

收集器谱系

收集器停顿要点
Serial / ParallelSTWParallel 是吞吐优先，适合离线批处理；小堆（几百 MB）用 Serial 反而最省
CMS低停顿标记-清除、并发收集。JDK 9 废弃、JDK 14 移除，不要再选
G1可预测JDK 9 起默认，面向"停顿可控"，不是绝对低延迟
ZGC极低JDK 15 转正，JDK 21 有分代版，停顿与堆大小基本无关

G1：把堆切成 Region

# 堆划分为约 2048 个等大 Region（1~32MB，2 的幂），角色动态分配：
# E=Eden  S=Survivor  O=Old  H=Humongous（大于半个 Region 的大对象）
# Young GC 回收全部 Eden；Mixed GC 回收全部 Young + 收益最高的一部分 Old
  • 为什么不物理分代：每次不必回收整个老年代，挑"垃圾最多"的几个 Region 先收，把一次大停顿拆成多次小停顿。
  • Humongous：单个对象超过 Region 一半就要占连续 Region。反复创建 3MB 的 byte[] 会不断触发这类分配，最终拖出 Full GC。
  • 跨 Region 引用：每个 Region 有一份 Remembered Set（底层是卡表），记录"我被谁引用"，回收单个 Region 时不必扫全堆。
  • 并发标记用 SATB：以标记开始那一刻为快照，之后的新引用由写屏障记录，保证不漏标。
-XX:MaxGCPauseMillis=200 是目标，不是承诺。G1 靠"这次只收 N 个 Region"逼近目标。设成 20ms，它每次只敢收一两个，回收速度跟不上分配速度，最后退化成 Full GC，反而更慢。200ms 是个合理起点，别往死里压。

ZGC：停顿为什么能和堆大小脱钩

G1 的停顿主要花在复制存活对象上，堆越大越久。ZGC 把标记、转移、重映射全做成并发，STW 阶段只剩根扫描这种与堆大小弱相关的事。

  • 着色指针：64 位指针里借几位存状态（Marked0 / Marked1 / Remapped），指针本身就知道"标记过没有、搬走没有"。
  • 读屏障 + 并发转移：加载引用时检查颜色并当场修正；搬家时旧地址留转发指针，应用线程不用停。
ZGC 不是免费的。① 必须用 64 位指针存颜色位，不能开压缩指针，同样对象更占内存；② 读屏障让每次引用加载多几条指令，纯计算负载会掉吞吐；③ 4GB 小堆上 G1 本来就只停几十毫秒，换 ZGC 收益不明显。它的甜蜜点是几十 GB 到 TB 级、对 P99 敏感的在线服务。

模块 3

集合框架：三个被反复讲错的结论

HashMap 的真实结构

# JDK 8：数组 + 链表 + 红黑树。链表长度 ≥ 8 且表长 ≥ 64 才树化
DEFAULT_INITIAL_CAPACITY = 16    # 桶数组长度，永远是 2 的幂
DEFAULT_LOAD_FACTOR      = 0.75f
TREEIFY_THRESHOLD = 8 / UNTREEIFY_THRESHOLD = 6 / MIN_TREEIFY_CAPACITY = 64
  • 扰动：h ^ (h >>> 16)。下标只用到低位，不把高 16 位混进来，高位信息就白算了。
  • 定位：(n - 1) & hash。n 是 2 的幂，等价于取模但快得多。
  • 扩容：容量翻倍，元素新下标只有两种可能 —— 原位或原位 + 旧容量，判据是 (e.hash & oldCap) == 0。所以不必重算 hash，一条桶拆成高低两条链直接挂过去。
  • 为什么是 0.75：桶内近似泊松分布，负载越高链表越长。0.75 下一个桶装到 8 个元素的概率约千万分之六 —— 这也是树化阈值定成 8 的原因。

陷阱一：并发扩容的死循环与静默丢数据

# JDK 7 的 transfer 用头插法搬迁链表
# 线程 A 刚记下 e 与 e.next 就被挂起；B 完成后链表已逆序
# A 醒来按旧关系继续插 → 形成环

# 结果：get() 落到这个桶上时 e = e.next 永远走不到 null，CPU 100%，线程永不返回

JDK 8 改成尾插，环没有了，问题没消失：两个线程同时 put 到同一个空桶，后写的覆盖先写的；size 用非原子的 ++ 会少算。JDK 8 不会死循环，但会静默丢数据 —— 后者更难查。

陷阱三：ArrayList 与 LinkedList 的性能反直觉

操作ArrayListLinkedList实际
get(i)O(1)，一次地址计算O(n)，从头或尾遍历ArrayList 完胜
头部插入O(n)，整体后移O(1)唯一由 LinkedList 赢的一项
中间插入O(n) 移动 + O(1) 定位O(n) 定位 + O(1) 改指针常常还是 ArrayList 快
遍历连续内存，预取友好指针跳转，cache miss差一个数量级
每元素开销4 字节引用（压缩指针）约 24 字节的 Node10 万元素差 2MB 以上

为什么中间插入链表也未必赢：ArrayList 的 System.arraycopy 底层是 memmove，走内存带宽，移动 10 万个引用只要几十微秒；LinkedList 要先走到第 i 个节点，每次 next 都是随机访问，节点散在堆上几乎必然 cache miss。除非明确在做头部增删，默认用 ArrayList；真要做队列用 ArrayDeque。

ArrayList 扩容是 1.5 倍不是 2 倍：oldCapacity + (oldCapacity >> 1)。1.5 倍更省内存，代价是扩容更频繁。已知规模时直接 new ArrayList<>(size)，省掉全部扩容复制。

ConcurrentHashMap：从分段锁到桶锁

版本并发方案并发度
JDK 7Segment 分段锁：默认 16 个 Segment，各自继承 ReentrantLock 管一段数组受 Segment 数限制，默认 16
JDK 8CAS + synchronized 锁单个桶头：桶空用 CAS 插入，非空只锁这一个桶理论上等于桶的数量
  • get 完全无锁：val 和 next 都是 volatile，不会读到半个对象。
  • size 用 CounterCell 分散计数：类似 LongAdder，避免所有线程抢一个 baseCount。代价是 size() 只是近似值。
  • 扩容支持协助：搬迁中的桶放一个 ForwardingNode 占位，其他线程遇到它会转去帮忙搬迁，而不是干等。
  • 弱一致性迭代器：不抛 ConcurrentModificationException，但不保证看到遍历开始后的修改。
为什么不允许 null？get(key) 返回 null 有两种含义："不存在"和"存在但值是 null"。单线程可用 containsKey 二次确认，但并发下两次调用之间 map 可能已变。与其给一个不可靠的语义，不如直接禁止。
模块 4

线程池：七个参数、四种拒绝、为什么禁用 Executors

参数含义踩坑点
corePoolSize核心线程数，空闲也保留设太大浪费，设太小任务排队
maximumPoolSize最大线程数队列无界时它永远用不上
keepAliveTime / unit非核心线程空闲存活时间只对超出 core 的线程生效
workQueue任务队列整个线程池的行为由它决定
threadFactory线程工厂不起名，jstack 里全是 pool-1-thread-3
handler拒绝策略默认 AbortPolicy 会抛异常，很多人没接

提交一个任务，到底走了哪几步

核心线程未满 → 直接新建核心线程执行，不管队列里有没有活。
核心线程满了 → 任务进队列排队，不是新建线程。
队列也满了 → 新建非核心线程，直到 maximumPoolSize。
最大线程也满了 → 触发拒绝策略。
第 2、3 步的顺序是反直觉的，也是所有事故的根源。很多人以为"任务多了就加线程"，实际是"先排队，排不下才加线程"。所以用了无界队列，maximumPoolSize 就是废参数，线程数永远停在 core，任务无限堆积直到堆被撑爆。

四种拒绝策略

策略行为适用
AbortPolicy默认。抛 RejectedExecutionException能接受失败、调用方会处理
CallerRunsPolicy让提交任务的线程自己执行天然背压，调用方被拖慢就不会继续猛提
DiscardPolicy静默丢弃几乎不该用 —— 出问题连日志都没有
DiscardOldestPolicy丢掉队首最老的，再重试只适合"新数据更重要"的实时场景

CallerRunsPolicy 的隐藏风险：它跑在调用方线程里。调用方若是 Tomcat 请求线程、任务又慢，请求线程会被占住。它适合"任务短、只想限速"，不适合"任务长、想丢弃"。

为什么《阿里巴巴 Java 开发手册》禁用 Executors

工厂方法内部实现后果
newFixedThreadPoolcore = max = n，LinkedBlockingQueue 无界队列无限增长 → 堆 OOM
newSingleThreadExecutor同上，n = 1同上，且单线程更容易积压
newCachedThreadPoolcore = 0，max = Integer.MAX_VALUE来多少建多少 → unable to create new native thread
# 正确姿势：每个参数都写清楚
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8, 16, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),        # 有界队列，容量要算过
    r -> new Thread(r, "order-sync-" + SEQ.incrementAndGet()),
    new ThreadPoolExecutor.CallerRunsPolicy());

# 线程数起点：CPU 密集 ≈ 核数 + 1；IO 密集 ≈ 核数 × (1 + 等待/计算)
# 例：请求 10ms，9ms 等 DB、1ms 计算 → 8 核 × 10 = 80。真实值靠压测
线程池必须隔离。一个池子同时跑"下单"和"发短信"，短信接口一超时就把线程占满，下单跟着死。共享线程池 = 共享故障。按业务拆池，各自独立的核心数、队列和拒绝策略。
Spring 的坑：@Async 不配 Executor 时，Spring Boot 2.x 默认用 SimpleAsyncTaskExecutor —— 不复用线程，每次调用新建一个。高并发下等于加强版 cachedPool，一定要自己声明 ThreadPoolTaskExecutor。
模块 5

泛型擦除：编译期存在，运行期消失

Java 的泛型是编译期语法糖 + 编译器插入的强制转换。理解这点，很多"为什么不能"就不用背了。

List<String> list = new ArrayList<>();
list.add("hello");
String s = list.get(0);
# 编译后：String s = (String) list.get(0);  ← 编译器自动插的 checkcast
# 类型参数被替换成上界，无上界就是 Object；<T extends Number> 擦成 Number
# 泛型签名仍留在 class 的 Signature 属性里（反射能读到），但方法体里的检查没了
做不到的写法原因
new T()擦除后不知道 T 是什么，无法调构造器。要传 Class<T> 或 Supplier<T>
new T[10]擦除后只能变 new Object[10]，但数组运行时记得自己的元素类型，语义对不上
x instanceof List<String>运行时没有 List<String> 这个类型
f(List<String>) 与 f(List<Integer>)擦除后签名相同，编译报 "same erasure"
class Box<T> { static T v; }静态成员属于类本身，T 是实例化时才确定的

为什么不能 new T[]，但能 new Object[]

# 数组是"具体化"的：运行时知道元素类型，每次写入都检查
Object[] objs = new String[1];
objs[0] = 42;        # 编译通过，运行时 ArrayStoreException —— 真实类型是 String[]

# 泛型是擦除的：如果允许 new T[10]，擦除后变成 Object[10]，
# 你能往里塞任何东西，取出来时的 checkcast 才炸 —— 错误被推迟到很远的地方

# 正确做法一：传 Class，让反射创建真正有类型的数组
static <T> T[] newArray(Class<T> c, int n) {
    return (T[]) java.lang.reflect.Array.newInstance(c, n);
}
# 正确做法二：传数组工厂（JDK 11 的 toArray 就是这思路）
String[] arr = list.toArray(String[]::new);
网上常见的 (T[]) new Object[n] 是错的。它绕过编译检查，但数组真实类型是 Object[]。一旦被当成 String[] 用，任何写入都会在调用方抛 ArrayStoreException，堆栈还指不到你这里。这就是"堆污染"。

通配符：PECS 一句话

# Producer Extends, Consumer Super —— 只读用 extends，只写用 super
void printAll(List<? extends Number> src) {
    for (Number n : src) System.out.println(n);  # ✓ 读出来一定是 Number
    # src.add(1);                                 # ✗ 不知道真实类型是 List<Integer> 还是 List<Double>
}
void fill(List<? super Integer> dst) {
    dst.add(1);                                   # ✓ 一定是 Integer 的父类型，塞 Integer 安全
    # Integer x = dst.get(0);                     # ✗ 只能读成 Object
}
泛型是不变的（invariant）：List<Integer> 不是 List<Number>，否则你就能往"实际是 List<Integer>"的引用里塞 Double。数组是协变的，所以允许，代价是运行时 ArrayStoreException；泛型在编译期就拒绝。这就是"数组协变 + 泛型擦除"不能混用的根本原因。
模块 6

类加载：双亲委派为什么存在，又为什么必须被打破

阶段做什么容易忽略的点
加载读字节码，生成 Class 对象数组类由 JVM 直接创建，不走类加载器
验证格式、元数据、字节码、符号引用验证最耗时，但保证不会执行非法指令
准备静态变量分配内存并赋零值static int x = 10 此时是 0；static final 编译期常量此时已是 10
解析符号引用 → 直接引用可以延迟到首次使用时才做
初始化执行 <clinit>：静态赋值与静态块这一步你写的代码才真正跑起来

触发初始化的六个时机（主动引用）：new、读写静态字段、调静态方法、反射、初始化子类前先初始化父类、作为启动类。注意：通过子类访问父类的静态字段，不会初始化子类。

双亲委派：先问爸爸，爸爸不行我再上

   Bootstrap（lib/modules） → Platform → Application（classpath） → 自定义
# loadClass 的逻辑：
# 1. 自己加载过没有（findLoadedClass）
# 2. 有父加载器就让父加载器 loadClass
# 3. 父加载器抛 ClassNotFoundException，才调自己的 findClass
它解决两个问题：① 避免重复加载 —— 同一个类被不同加载器加载会得到不同的 Class 对象，instanceof 和强转全部失效；② 防止核心类被篡改 —— 你自己写个 java.lang.String，委派到 Bootstrap 时发现已加载，根本不会用你的。

三个必须打破它的场景

场景为什么要破怎么破
SPI / JDBCDriverManager 在 rt.jar 里由 Bootstrap 加载，但它要实例化 classpath 下厂商的 Driver，而 Bootstrap 看不见 classpath线程上下文类加载器：Thread.currentThread().getContextClassLoader()，打通"父请求子"
Tomcat一个容器跑多个应用，各自要能用自己的 Spring 版本每个应用一个 WebappClassLoader，先自己加载（除 java.* 等），加载不到再往上委派
热部署不重启进程就要换实现丢弃旧 ClassLoader，用新的重新加载同名类
# JVM 判断"两个类是不是同一个类"：全限定名相同 且 同一个 ClassLoader 实例加载
Class<?> v1 = oldLoader.loadClass("com.x.UserService");
Class<?> v2 = freshLoader.loadClass("com.x.UserService");
v1 != v2        # true，两个完全不同的 Class 对象
# 旧对象仍指向 v1，不会被"替换"；只有新建的对象才用 v2
# 等旧对象全部不可达、oldLoader 也无人引用，整片元空间才能回收
JVM 自带的 HotSwap 只能改方法体。通过 JDI 的 redefineClasses 替换字节码，不能增删字段和方法、不能改继承关系。JRebel 这类工具要靠重写类结构才能做到"真正"热部署，Arthas 的 retransform 受同样限制。
元空间泄漏的头号原因是类加载器泄漏。典型链条：ThreadLocal 的 value 持有应用对象 → 线程池的线程（生命周期等于进程）持有 ThreadLocalMap → key 是弱引用被回收，但 value 是强引用 → 指向类 → ClassLoader → 整个应用的元空间。所以用完必须 remove()；reload 后 Metaspace 只涨不跌，先查线程池残留引用。
模块 7

四类性能问题：从现象倒推原因

第一类：频繁 Full GC

原因怎么确认怎么解
内存泄漏GC 后存活量单调上升，jstat -gcutil 的 O 列只涨不跌dump 堆，用 MAT 找 dominator
大对象日志里出现大量 Humongous 分配分批查、分页返回、别一次性 toByteArray
显式 System.gc()日志里 Full GC 的触发原因写着 System.gc()-XX:+DisableExplicitGC，并找出谁在调（常见于 NIO 直接内存清理、RMI）

第二类：内存泄漏的七个现场

场景为什么泄漏
静态集合做缓存static Map 只 put 不 remove，等于把对象钉在 GC Root 上。缓存必须有上限和淘汰
ThreadLocal 未 remove线程不死，value 就一直被 ThreadLocalMap 强引用（key 弱、value 强）
监听器未注销被注册方持有你的引用，你的对象就永远活着
自定义类加载器旧的被静态字段或线程持有 → 整个应用的类都卸不掉
连接 / 流未关闭socket 和缓冲区不会因 GC 而释放，还会耗尽文件描述符
非静态内部类隐式持有外部类引用，长生命周期的内部类实例会拖住整个外部对象
关于 String.substring：JDK 6 里它共享原字符串的 char[]，截一个字符却留住整个大字符串，是经典泄漏。JDK 7u6 之后改成复制，这个问题已经不存在了。网上还在传的结论是十年前的，别照搬。

第三类：线程池打满

jstack <pid> > s1.txt; sleep 5; jstack <pid> > s2.txt
grep -c "State: RUNNABLE" s1.txt   # 真在算
grep -c "State: BLOCKED"  s1.txt   # 抢锁
grep -c "State: WAITING"  s1.txt   # 等 IO / park
  • 全 RUNNABLE 且都在跑业务代码：真算不过来，加线程或加机器，但先确认下游扛得住。
  • 大量 BLOCKED：锁竞争。看 waiting to lock 指向哪个对象，顺着栈找那把锁。
  • 大量 WAITING 在 socketRead：下游慢。这时加线程只是把下游压得更死。
  • 队列持续增长但线程数不涨：几乎可以确定用了无界队列。

第四类：锁竞争

手段说明
缩小临界区只锁真正共享的几行，别把 IO、日志、序列化包在锁里
锁分段按 key 的 hash 分成 N 把锁，把竞争分散
无锁结构高并发计数用 LongAdder，它把热点分散到多个 Cell
常被忽略的成本：上下文切换。线程数远超核数时，CPU 大量时间花在保存/恢复寄存器和换栈上。vmstat 1 的 cs 列、pidstat -w 1 的 cswch/s 能看到。cs 每秒几十万而 CPU 利用率不高，说明线程开多了，不是开少了。

拿到 heap dump 之后

先看直方图，别急着开 MAT。排前几名的类往往一眼看出问题：某个 DTO 有几百万实例、char[] 占了 80% 内存。
再看 Dominator Tree。它回答"回收这个对象能释放多少"，这个数叫 Retained Heap，比 Shallow Heap（对象自身大小）有用得多。
对可疑对象查 Path to GC Roots，务必选 exclude weak/soft references；隔 10 分钟再 dump 一次做对比，只涨不跌的就是泄漏点。
dump 之前先确认磁盘。转储文件约等于堆的实际使用量，8GB 的堆就是 8GB 的文件。磁盘满会把"服务慢"升级成"彻底起不来"。建议加 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump，路径指向大盘。
常见坑

八个把服务打死的写法

1
用 Executors.newFixedThreadPool
内部是无界 LinkedBlockingQueue，积压时不拒绝、不扩容，直接把堆撑爆。必须手动 new ThreadPoolExecutor。
2
以为设了 maximumPoolSize 就会扩容
顺序是"核心满进队列，队列满才建线程"。队列无界时 maximumPoolSize 永远用不上，线程数卡在 core。
3
线程池里用 ThreadLocal 却不 remove
线程不销毁，value 就被强引用。既泄漏对象，又可能把上一个请求的用户信息带给下一个请求。
4
多线程往同一个 HashMap 里写
JDK 7 会形成环形链表，get 死循环、CPU 100%；JDK 8 不死循环了，但会静默覆盖、size 少算。
5
new HashMap<>(expectedSize) 直接传元素个数
构造器只把表长调到不小于该值的 2 的幂，阈值还要乘 0.75。想装 1000 个要传 1334，否则装到 768 就扩容。
6
用可变对象做 key
放进去之后改了字段，hashCode 变了，桶的位置也变了。这个 key 既查不到也删不掉，只能等整个 map 被回收。
7
@Async 不配执行器就上线
Spring Boot 2.x 默认用 SimpleAsyncTaskExecutor，它不复用线程，每次调用新建一个。高并发下线程数失控。
8
在业务高峰执行 jmap -histo:live 或 dump
:live 会先触发一次 Full GC，大堆上可能停几秒到几十秒，务必低峰执行。
自测

六道题

1. 为什么单机堆通常不建议设成 40GB？
正确答案：压缩指针失效。它靠右移 3 位把 32 位地址的表示范围放大到 32GB。超过之后每个引用占 8 字节，同样对象更大，实际能装的可能反而变少。
2. Region 是 16MB，现在分配一个 40MB 的数组，会发生什么？
正确答案：Humongous 分配。G1 规定超过 Region 一半的对象必须放在连续 Region，不能跨普通 Region 拆分。这类对象回收代价高，频繁创建会触发并发周期甚至 Full GC。
3. core=4、max=8、队列容量 100。前 4 个任务已在跑，提交第 5 个会怎样？
正确答案：进队列。顺序是"核心满 → 入队 → 队列满 → 扩到 max → 拒绝"。第 5 到第 104 个任务全部排队，队列满了才启用第 5 个线程。
4. 为什么 Java 不允许 new T[]？
正确答案：数组具体化、泛型擦除。数组运行时带元素类型，写入时做 ArrayStoreException 检查；擦除后只能创建 Object[]，语义对不上。(T[]) new Object[n] 只是把错误推迟到调用方。
5. DriverManager 由 Bootstrap 加载，为什么能加载 classpath 下厂商的 Driver？
正确答案：线程上下文类加载器。这是 SPI 的标准破法：父加载器拿不到子加载器可见的类，于是用 Thread.currentThread().getContextClassLoader() 反向委托。
6. GC 后存活量稳定在 1GB，堆上限 4GB，但 Young GC 每秒好几次。最该做什么？
正确答案：查分配速率。GC 后只存活 1GB 说明没有泄漏，加堆只会让每次 GC 更慢。频繁 Young GC 说明 Eden 被快速填满：要么分配太猛，要么新生代太小。
