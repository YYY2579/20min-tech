模块 1

指针的本质：地址加类型

指针变量里存的是一个地址。但只有地址不够 —— 类型决定了从这个地址读几个字节、怎么解释这几个字节、以及 +1 到底加多少。

int    n = 0x01020304;
int   *pi = &n;
char  *pc = (char *)&n;

printf("%zu\n", sizeof(pi));      // 8，64 位平台上指针固定 8 字节
printf("%p\n",  (void *)pi);      // 同一个地址
printf("%p\n",  (void *)pc);      // 同一个地址

printf("%d\n", *pi);              // 一次读 4 字节
printf("%d\n", *pc);              // 一次读 1 字节（有符号 char 可能是负数）

printf("%p %p\n", (void *)(pi + 1), (void *)(pc + 1));
// pi + 1 前进 4 字节；pc + 1 前进 1 字节
// 指针运算的单位是 sizeof(*p)，不是 1 字节
写法含义常见误解
p + 1前进 sizeof(*p) 字节以为前进 1 字节
*(p + i)等价于 p[i]以为 p[i] 是特殊语法
&p[i]等价于 p + i—
p->m等价于 (*p).m—
void *只存地址，不能解引用、不能做指针运算GCC 允许 void* 按 1 字节算，但那是扩展，不是标准 C
指针大小和类型无关。64 位平台上 char*、int*、struct Foo* 都是 8 字节。但指针运算和类型强相关，把 int* 强转成 char* 再 +1，行为完全不同。函数指针在极少数平台（如部分 DSP、老式 x86 分段模式）大小可能不同，不要假设它们一定相等。

多级指针与"指针的指针"

int n = 42;
int *p = &n;      // p 指向 n
int **pp = &p;    // pp 指向 p

**pp = 100;        // 两次解引用，改的是 n
printf("%d\n", n); // 100

// 典型用途：函数里要修改调用方的指针本身
void alloc(int **out, size_t n) {
    *out = malloc(n * sizeof(int));
}
int *arr = NULL;
alloc(&arr, 10);   // 必须传 &arr，否则函数改的是副本
NULL 不是 0 号地址的保证。C 标准只保证 NULL 是一个"不等于任何对象地址"的空指针常量，它的二进制表示不一定全 0（虽然几乎所有现代平台都是）。所以判空要写 if (p == NULL) 或 if (!p)，不要写 if ((intptr_t)p == 0)。

数组与指针退化：sizeof 为什么会骗你

int a[10];

printf("%zu\n", sizeof(a));        // 40（10 × 4）
printf("%zu\n", sizeof(a[0]));     // 4
printf("%zu\n", sizeof(a) / sizeof(a[0]));  // 10，求元素个数的标准写法

int *p = a;                      // 数组名退化为指向首元素的指针
printf("%zu\n", sizeof(p));        // 8，不是 40

退化的三个例外

场景结果
sizeof(a)整个数组的字节数，不退化
&a类型是 int (*)[10]，不退化；&a + 1 跳过整个数组
用字符串字面量初始化字符数组char s[] = "abc" 得到 4 字节数组，不退化
其他所有表达式退化为指向首元素的指针

函数参数里的数组其实是指针

// 下面三种写法在编译器眼里完全一样，都是 int *
void f(int a[10]);
void f(int a[]);
void f(int *a);

void f(int a[10]) {
    printf("%zu\n", sizeof(a));   // 8，不是 40！
}

// 所以长度必须单独传，这是 C 接口里最常见的参数组合
void process(const int *a, size_t n);
这个坑的经典后果：在函数里写 for (i = 0; i < sizeof(a)/sizeof(a[0]); i++)，在 main 里是对的，挪进函数就变成 8/4 = 2，只处理前两个元素。而且它不会报错，只是结果不对。

二维数组的类型

int m[3][4];

// m 退化为指向"含 4 个 int 的数组"的指针，类型是 int (*)[4]
// m[i] 是 int[4]，再退化为 int*
// m[i][j] 等价于 *(*(m + i) + j)

printf("%zu\n", sizeof(m));       // 48
printf("%zu\n", sizeof(m[0]));    // 16
printf("%zu\n", sizeof(m[0][0])); // 4

// 作为参数时，第二维不能省
void g(int m[][4], int rows);   // ✓
// void g(int **m, int rows);     // ✗ 类型不兼容，int** 不是二维数组
不要用 int ** 接收二维数组。二维数组是一整块连续内存，m[i] 是靠 m + i*4*sizeof(int) 算出来的；而 int** 是"指针的数组"，需要先读一个指针再跳转。两者内存布局完全不同，混用会读到完全错误的位置。

结构体对齐：为什么 sizeof 比字段加起来大

struct A {
    char  c;   // 偏移 0，占 1 字节
    int   i;   // 偏移 4（前面补 3 字节）
    char  d;   // 偏移 8
};              // sizeof = 12（末尾再补 3 字节，凑成 4 的倍数）

struct B {
    int   i;   // 偏移 0
    char  c;   // 偏移 4
    char  d;   // 偏移 5
};              // sizeof = 8（末尾补 2 字节）

// 字段一样，只是顺序不同：12 字节 vs 8 字节，差 50%

规则有两条：① 每个字段的起始偏移必须是它自身对齐要求的整数倍（int 通常是 4）；② 结构体总大小必须是最大对齐要求的整数倍，这样数组里每个元素都自然对齐。

为什么要对齐？CPU 访问内存是按字（word）或缓存行（64 字节）来的。一个 4 字节的 int 如果横跨两个缓存行，需要两次访问再拼接；某些架构（早期 ARM、SPARC）遇到未对齐访问会直接触发总线错误，不是慢，是崩。原子操作更是硬性要求对齐。

缓存行与伪共享

// 一个缓存行通常 64 字节。两个线程各改一个变量，
// 如果它们落在同一行，会互相把对方的缓存行置为无效

struct Counter {
    long a;    // 线程 1 改
    long b;    // 线程 2 改 —— 与 a 同行，产生伪共享
};

// 解决：用填充把两个变量推到不同缓存行
struct Padded {
    long a;
    char pad[64 - sizeof(long)];
    long b;
};
// 或使用 _Alignas(64)
模块 4

字符串：一个 \0 引发的所有问题

// C 没有"字符串类型"，只有"以 \0 结尾的 char 数组"这个约定
char s[] = "abc";        // 栈上 4 字节：'a' 'b' 'c' '\0'，可修改
char *p  = "abc";        // 指向 .rodata，修改是 UB（通常段错误）

printf("%zu\n", sizeof(s));   // 4，编译期就知道
printf("%zu\n", sizeof(p));   // 8，指针大小
printf("%zu\n", strlen(s));   // 3，运行时数到 \0 为止
printf("%zu\n", strlen(p));   // 3
函数行为问题
strlen从指针开始数到 \0O(n)；没有 \0 就会一直读下去
sizeof编译期求值，数组是总字节数对指针永远是指针大小
strcpy复制到 \0 为止完全不检查目标容量，缓冲区溢出的头号来源
strcat追加到目标末尾同样不检查剩余空间
sprintf格式化到缓冲区不知道缓冲区多大
strncpy最多复制 n 字节源串长度 ≥ n 时不补 \0，得到的不是合法字符串
snprintf最多写 n 字节，保证以 \0 结尾返回值是"原本想写的长度"，可能大于 n
char buf[8];
strcpy(buf, "this is way too long");   // 溢出，写坏栈上的相邻数据

// strncpy 的经典陷阱
char dst[8];
strncpy(dst, "0123456789", sizeof(dst));
printf("%s\n", dst);   // 没有 \0，越界读，行为不确定

// 正确做法一：手动补 \0
strncpy(dst, src, sizeof(dst) - 1);
dst[sizeof(dst) - 1] = '\0';

// 正确做法二：snprintf 一步到位
snprintf(dst, sizeof(dst), "%s", src);
strcpy 为什么危险？它没有任何"目标有多长"的信息 —— 函数签名里就没有这个参数。它只知道自己要复制到源串的 \0 为止，目标装不下就写穿。这是几十年来最多的一类安全漏洞（缓冲区溢出）的根源，也是很多远程代码执行的入口。

memcpy 与 memmove

char buf[16] = "0123456789";

// memmove 处理重叠区间，内部会判断方向
memmove(buf + 2, buf, 5);      // 结果 "0101234789"

// memcpy 不保证处理重叠，重叠时行为未定义
// memcpy(buf + 2, buf, 5);    // ✗ 可能得到错误结果

// 经验：不确定是否重叠就用 memmove，代价通常可以忽略
strtok 不可重入。它把"下一次从哪里开始"存在函数内部的静态变量里，多线程同时用会互相踩，甚至嵌套调用都会错乱。多线程或需要嵌套时用 strtok_r（POSIX），它把状态放在调用方传进来的 char **saveptr 里。
strlen 返回的是字节数，不是字符数。UTF-8 下一个汉字占 3 字节，一个 emoji 可能占 4 字节。用 strlen("中文") 得到 6，不是 2。C 标准库没有"按字符遍历 UTF-8"的函数，要么用第三方库，要么自己按首字节的高位判断码点长度。
模块 5

未定义行为：编译器可以假设它不存在

UB（Undefined Behavior）不是"结果不确定"，而是标准对程序的行为不作任何要求。优化器有权假设"这段代码永远不会执行到 UB"，并据此删改代码。

六类最常见的 UB

类型例子后果
有符号整数溢出INT_MAX + 1优化器可以假设 x + 1 > x 恒成立
数组越界a[10]（长度 10）读到相邻变量或栈保护页，可能段错误
空指针解引用*p 而 p == NULL段错误；优化器也可能直接删掉判空
未初始化读取int x; if (x)读到任意值，且可能让编译器做出错误推断
严格别名违规用 float* 读 int 的内存-O2 下重排导致读到旧值
求值顺序 / 序列点i = i++ + 1C11 起明确是 UB，结果不可预测

为什么"优化器删掉了我的判空"

// 一段看起来在防御空指针的代码
int deref(int *p) {
    int v = *p;        // 如果 p 是 NULL，这里已经是 UB
    if (p == NULL) {   // ← 优化器认为这行永远不成立，直接删掉
        return 0;
    }
    return v;
}
// 因为"解引用空指针是 UB"意味着"p 一定非空"，于是判空是死代码
// GCC/Clang 在 -O2 下确实会删掉这个分支

// 正确写法：先判空，再解引用
int deref(int *p) {
    if (p == NULL) return 0;
    return *p;
}
另一个经典例子：有符号溢出。 
int f(int x) {
    if (x + 1 < x) return 1;   // 本意是检测溢出
    return 0;
}
因为 x + 1 不允许溢出，优化器可以推出 x + 1 > x 恒成立，于是整个 if 被删掉，函数永远返回 0。用 -fwrapv 可以强制回绕语义，但更该做的是用无符号数或编译器内建函数判断。

严格别名：为什么 float* 读 int 会出错

// 违反严格别名规则（strict aliasing）
int   n = 0x3f800000;
float f = *(float *)&n;      // UB：通过 float* 访问 int 对象

// -O2 下编译器可能认为这两个指针不可能指向同一块内存，从而重排读写顺序

// 正确做法一：memcpy（编译器会优化成一条 mov，零开销）
float f;
memcpy(&f, &n, sizeof f);

// 正确做法二：union 类型双关（C99 起允许，C++ 不允许）
union { int i; float f; } u = { .i = 0x3f800000 };
printf("%f\n", u.f);
UB 最可怕的地方是"它现在能跑"。换编译器版本、换优化级别、在中间加一行 printf，行为都可能突变。这类 bug 叫 heisenbug —— 你一加日志它就好了，一删日志又坏了。所以"我测过没问题"对 UB 毫无意义。
能抓一部分 UB 的工具：-fsanitize=undefined（UBSan）会在运行时检查有符号溢出、移位越界、空指针、对齐错误、部分别名问题。开销很小（通常 10%~30%），建议在测试环境常开。
模块 6

内存管理：五个错误，一个对策

void *malloc(size_t n);              // 分配 n 字节，内容不确定
void *calloc(size_t cnt, size_t sz); // 分配 cnt*sz 字节并清零
void *realloc(void *p, size_t n);     // 调整大小，可能搬家
void  free(void *p);                 // 归还，p 必须来自 malloc/calloc/realloc

// 标准写法：先检查，再使用
int *a = malloc(100 * sizeof(int));
if (a == NULL) { /* 处理失败，不要继续 */ }

// realloc 的坑：失败时返回 NULL，但原指针仍然有效
int *tmp = realloc(a, 200 * sizeof(int));
if (tmp == NULL) { /* a 还在，不能丢 */ }
else { a = tmp; }

五个错误

错误表现典型原因
重复释放glibc 报 double free or corruption，或堆结构被破坏后随机崩两条路径都 free 了同一个指针；循环里 free 没置空
野指针读到垃圾值，或段错误free 之后没置 NULL，继续用
泄漏RSS 持续上涨，最终 OOM忘记 free；指针被覆盖，原地址再也拿不到
越界写坏相邻内存或堆元数据，崩溃点离案发现场很远循环多跑一次；malloc(n) 却写了 n+1
释放后使用读到已被重新分配的数据；偶尔"看起来正常"free 后还在用指针，尤其是被别的线程复用之后
// 越界如何破坏堆：malloc 返回的块前面有元数据
┌────────────┬──────────────────┬────────────┐
│ 块头(大小等) │  用户可用区域      │ 下一块头    │
└────────────┴──────────────────┴────────────┘
// 写超了就会改到下一块的块头，free 时才崩，栈已经指不到源头

// free 之后立即置空，是最便宜的习惯
free(p);
p = NULL;      // 再 free 一次是合法的 no-op
三个容易忽略的细节：① free(NULL) 是合法的，什么都不做；② malloc(0) 的返回值可以是 NULL，也可以是"可 free 的唯一指针"，两种都符合标准，所以别对 0 字节做假设；③ 只能 free malloc 家族返回的原始指针，free(p + 1) 或 free 栈地址都会破坏堆。

减少碎片与分配次数

// ① 批量分配，而不是循环里一次次 malloc
int *arr = malloc(n * sizeof(int));   // 一次

// ② 固定大小对象用内存池，避免频繁 split/merge
// ③ 长期运行的服务，考虑 jemalloc / tcmalloc 替换默认分配器
//    多线程下它们的锁竞争通常明显更小

// ④ 能用栈就用栈：生命周期明确的小数组没必要上堆
int buf[256];   // 栈上，函数返回自动回收，零分配开销
alloca 不是 malloc 的替代品。它在当前函数的栈帧上分配，函数返回自动释放，看起来很美。但：① 大小不受控时直接爆栈；② 不能在循环里用（每次循环都分配，直到函数返回才释放）；③ 不可移植。只适合"大小很小且编译期可估算"的场景，绝大多数情况下不该用。

宏的三个经典错误

// 错误一：没有括号，优先级被破坏
#define SQUARE(x) x * x
SQUARE(1 + 2)          // 展开成 1 + 2 * 1 + 2 = 5，不是 9

// 修正：每个参数和整体都加括号
#define SQUARE(x) ((x) * (x))

// 错误二：参数被求值多次
int i = 5;
SQUARE(i++)            // 展开成 ((i++) * (i++)) —— 同一表达式里改两次 i，UB

// 即使加了括号也救不了，因为宏是文本替换，不是函数调用

// 错误三：多语句宏在 if 后面被拆散
#define LOG(msg) printf(msg); fflush(stdout);
if (ok) LOG("hi");   // 展开后只有 printf 在 if 里，fflush 无条件执行

// 修正：用 do { } while (0) 包起来
#define LOG(msg) do { printf(msg); fflush(stdout); } while (0)
为什么是 do { } while (0) 而不是 { }？因为 if (x) { ... }; else ... 里的那个分号会让 else 悬空，编译失败。而 do { } while (0) 后面必须跟分号，正好和函数调用写法一致，在任何上下文里都安全。

用函数替代宏

// C99 起可以用 static inline，兼顾类型检查和零开销
static inline int square(int x) { return x * x; }

// 优点：参数只求值一次、有类型检查、能调试、能取地址
// static 保证每个 .c 文件有一份内部链接的副本，不会重复定义

// 只写 inline 不给 static 放在头文件里，可能链接失败
// （C99 的 inline 语义和 C++ 不同，容易踩坑）
写法类型检查求值次数能调试
#define无看写法，可能多次难（符号被替换掉）
static inline有一次可以
普通函数有一次可以，但有调用开销
assert 也是宏，也会带来副作用问题。定义 NDEBUG 后（release 构建常这么做），assert(expr) 整个消失，expr 里的函数调用也不会执行。 
assert(init_device() == 0);   // release 下 init_device() 根本不会被调用
所以断言里只放纯检查，不要放有副作用的表达式。

static 的三个含义

位置含义
函数内的局部变量生命周期变成整个程序，只初始化一次
文件作用域的变量/函数内部链接，其他 .c 文件看不见，避免命名冲突
头文件里的 static 函数：每个包含它的 .c 都会得到一份副本。这避免了重复定义，但会让代码体积变大，也让"函数指针比较"变得不可靠（不同 .c 里地址不同）。头文件里优先用 static inline，让编译器决定要不要真的内联。

能力说明
能查堆越界、释放后使用、重复释放、未初始化读取、内存泄漏
不能查栈上越界（部分能查）、全局变量越界、数据竞争（要用 helgrind）

Sanitizer：编译期插桩，运行期检查

# AddressSanitizer：堆/栈/全局越界、UAF、双重释放、泄漏
gcc -g -fsanitize=address -fno-omit-frame-pointer app.c -o app

# UndefinedBehaviorSanitizer：有符号溢出、移位越界、空指针、对齐
gcc -g -fsanitize=undefined app.c -o app

# 组合使用（最常用的组合）
gcc -g -fsanitize=address,undefined app.c -o app

# 泄漏检测默认开启，可用环境变量控制
ASAN_OPTIONS=detect_leaks=1 ./app
工具抓什么开销注意
ASan越界、UAF、双重释放、泄漏约 2 倍内存和少量 CPU编译和链接都要加参数
UBSan有符号溢出、移位、空指针、对齐10%~30%开销小，适合常开
TSan数据竞争5~15 倍只能发现实际发生的竞争
ASan 和 valgrind 不能同时用。两者都接管内存分配器，一起开通常会直接崩或给出混乱结果。选择建议：日常开发和 CI 用 ASan + UBSan（快、集成简单）；需要精确定位泄漏来源时再用 valgrind 的 --track-origins。
常见坑

十个"能编译、能跑、会炸"的写法

1
用 strcpy / sprintf 往固定大小的缓冲区里写
它们不知道目标有多大，源数据一长就写穿。这是缓冲区溢出的头号来源，用 snprintf 并检查返回值。
2
free 之后继续使用指针
这块内存可能已经被分配给别人，你读到的是别人的数据，写进去会破坏别人的状态。free 后立刻置 NULL。
3
返回指向局部变量的指针
函数返回后栈帧就失效了，那块内存随时会被下一次调用覆盖。编译器通常会给警告，但不会阻止你。
4
在函数里用 sizeof(arr)/sizeof(arr[0]) 求长度
数组参数已经退化成指针，结果是 8/4=2。长度必须作为单独的参数传进来。
5
给宏传带副作用的参数
SQUARE(i++) 会展开成两次 i++，同一个表达式里改两次变量是 UB。宏参数被求值的次数取决于宏体里出现了几次。
6
不检查 malloc 的返回值
分配失败返回 NULL，直接解引用就是段错误。在内存受限的嵌入式环境里这非常常见。
7
随手用 __attribute__((packed)) 省空间
所有字段变成未对齐，x86 上变慢，ARM 上可能直接崩。优先调整字段顺序，通常能白拿 20%~50% 空间。
8
用 x + 1 < x 检测有符号溢出
有符号溢出是 UB，优化器会假设它不发生，直接把整个判断删掉。改用无符号数或编译器内建函数。
9
用 int 存指针或地址
64 位平台上指针 8 字节、int 4 字节，高位被截断。要用 intptr_t / uintptr_t，且只在确实需要整数运算时用。
10
多线程读写同一个全局变量却以为"只是读"
C11 之前标准里根本没有线程概念；即使现在，无同步的并发读写也是数据竞争，属于 UB，优化器可能把读提到循环外。
自测

六道题

1. int *p 指向一个 int，p + 1 实际前进了多少字节？
正确答案：sizeof(int)。指针运算的单位是"所指类型的大小"，不是 1 字节，也不是指针自身的大小。
2. void f(int a[10]) 里 sizeof(a) 是多少？
正确答案：8。形参里的 int a[10] 和 int *a 完全等价，方括号里的数字没有约束力。长度必须单独传。
3. struct { char c; int i; char d; } 在常见平台上 sizeof 是多少？
正确答案：12。int 要求 4 字节对齐，c 后面补 3 字节；整体大小要是最大对齐的倍数，末尾再补 3 字节。把 int 放最前面就能压到 8。
4. strncpy(dst, "0123456789", sizeof(dst))（dst 是 8 字节）之后，dst 一定是个合法字符串吗？
正确答案：不一定。strncpy 只在源串短于 n 时用 \0 填充；源串更长时写满 n 字节且不加终止符。用 n-1 再手动补 \0，或直接用 snprintf。
5. if (x + 1 < x) return 1; 在 -O2 下最可能发生什么？
正确答案：被优化掉。有符号溢出是 UB，优化器假设它不会发生，推出 x+1 > x 恒成立，判空分支成为死代码。
6. 关于 ASan 与 valgrind，哪个说法对？
正确答案：第三个。ASan 编译期插桩、速度快，适合 CI；valgrind 运行时翻译指令，慢但不需重编。两者都接管分配器，不能同开。

术语表

术语一句话解释
数组退化数组名在大多数表达式里变成指向首元素的指针
悬垂指针指向已释放或已失效内存的指针
野指针未初始化或 free 后未置空的指针
UB未定义行为，标准不作任何要求，优化器可任意假设
序列点表达式求值顺序的约束点，跨过它之前所有副作用必须完成
严格别名不同类型的指针不能指向同一对象，否则 UB
对齐对象地址必须是某个值的整数倍，否则访问变慢或崩溃
padding为满足对齐而在字段之间或末尾插入的空洞字节
缓存行CPU 与内存之间搬运数据的最小单位，通常 64 字节
伪共享两个线程改同一缓存行里的不同变量，互相让对方的缓存失效
堆元数据分配器放在每块内存前后的管理信息，越界会破坏它
