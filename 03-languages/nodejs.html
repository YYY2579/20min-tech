先建立一个总认知：Node 的"单线程"指的是你的 JS 代码跑在单线程上。I/O、文件系统、DNS、加密这些活由 libuv 丢给操作系统（epoll/kqueue/IOCP）或它自己的线程池去做，完成后再以回调的形式排回主线程。所以：任何一段同步 JS 代码（含一个大 JSON.parse）执行期间，整个进程的所有请求一起停摆——这是后面所有坑的总根源。
模块 1

事件循环：六个阶段与执行顺序

事件循环不是"一个队列 FIFO"，而是分阶段的循环。每个阶段有自己的回调队列，一轮循环里按固定顺序进入。

阶段执行什么要点
timers到期的 setTimeout / setInterval 回调只执行"到点"的；poll 阶段会计算本轮该阻塞多久来等 timer
pending callbacks上一轮遗留的系统回调典型如 TCP 连接被拒（ECONNREFUSED）的错误回调
idle / prepare内部使用不用关心
poll执行 I/O 回调（网络、文件）没有可执行回调时会阻塞等待，时长参考 timers 里最近的到期时间
checksetImmediate 回调poll 之后立刻跑，专门设计给"当前 I/O 后尽快执行"
closeclose 事件回调socket.on('close') 等

两个"循环外"的优先队列：process.nextTick 队列和 微任务（Promise）队列。每执行完一个宏任务（一个阶段的一批回调、一次 IO 回调），都会先把 nextTick 队列掏空，再掏空微任务队列，然后才回到事件循环。nextTick 优先级高于 Promise。

// 例 1：nextTick vs Promise vs setTimeout（顺序完全确定）
setTimeout(() => console.log('A: setTimeout'), 0);
Promise.resolve().then(() => console.log('B: promise.then'));
process.nextTick(() => console.log('C: nextTick'));
console.log('D: 同步代码');

// 输出顺序：D → C → B → A
// 同步代码最先；当前操作结束后，nextTick 队列先于微任务队列；
// setTimeout 的回调要等事件循环真正跑到 timers 阶段才执行。
// 例 2：I/O 回调内部，setImmediate 一定先于 setTimeout(0)（Node 文档级结论）
const fs = require('node:fs');

setTimeout(() => console.log('E: setTimeout(0)'), 0);
setImmediate(() => console.log('F: setImmediate'));

fs.readFile(__filename, () => {
  console.log('G: readFile 回调');
  setTimeout(() => console.log('H: IO 里的 setTimeout'), 0);
  setImmediate(() => console.log('I: IO 里的 setImmediate'));
});

// 确定的顺序：G → I → H
// G 执行完后，nextTick/微任务队列先清空；然后事件循环从 poll 进入 check 阶段，
// I 立即执行；H 要等下一轮循环的 timers 阶段。
// 注意：顶层 E 和 F 的顺序是不确定的！取决于主模块执行到事件循环是否超过 1ms。
// 超过 1 秒级别的延迟请用 setTimeout(fn, ms)，不要用 setImmediate 冒充"立即"。
一句话记住优先级：当前同步代码 → nextTick 队列 → 微任务（Promise）队列 → 事件循环（timers → pending → poll → check → close，一轮一轮转）。
Node 11+ 的一个变化：timers 和 poll 阶段在每轮循环开始时会做一次"对齐"，所以 setTimeout(0) 的实际触发时间在 1ms 上下浮动，不要把 setTimeout(fn, 0) 当精确计时用。
模块 2

单线程与 libuv 线程池

主线程只有一条，但异步能力分两条路：网络 I/O 走操作系统的多路复用（Linux epoll、macOS kqueue、Windows IOCP），另一批操作 libuv 用线程池模拟异步。

操作实现方式说明
TCP/HTTP/UDP 网络请求epoll/kqueue/IOCP事件循环本体，真·单线程，无线程开销
fs 文件读写（异步版）libuv 线程池默认 4 个线程，用 UV_THREADPOOL_SIZE 调
dns.lookup / dns.resolve线程池 / getaddrinfodns.lookup 走线程池，dns.resolve 走网络
crypto 异步 API
（pbkdf2、scrypt、randomBytes）		libuv 线程池同理；同步版（pbkdf2Sync）则直接占死主线程
zlib 压缩/解压libuv 线程池大文件 gzip 别忘了它占线程池名额
你的 JS 同步代码主线程这里发生的一切，全网请求一起等
// 线程池大小默认 4 —— 并发跑 10 个大文件 gzip，实际只有 4 个在并行
UV_THREADPOOL_SIZE=8 node server.js     // 启动前设置，进程内读不到（要早于 require libuv）

// 验证：4 个线程池任务并发 vs 8 个的耗时差
const zlib = require('node:zlib'), fs = require('node:fs');
const big = Buffer.alloc(64 * 1024 * 1024, 'x');      // 64MB
console.time('gzip');
Promise.all(Array.from({length: 8}, () => zlib.gzip(big)))
  .then(() => console.timeEnd('gzip'));   // UV_THREADPOOL_SIZE=4 时约是 =8 的两倍耗时
"异步"不等于"不占线程"。fs.readFile 异步版把活丢给线程池，主线程确实解放了——但线程池只有默认 4 个位置。一窝蜂的 fs 异步操作会在线程池里排队，表现就是"回调迟迟不来"。CPU 密集任务更糟：它连线程池都去不了，只能占主线程，唯一解是 worker_threads 或独立进程。
模块 3

异步陷阱：回调、Promise、async/await

// ===== 1. 回调地狱：嵌套三层，错误处理要写三遍 =====
getUser(id, (err, u) => {
  if (err) return handle(err);
  getOrders(u, (err, os) => {
    if (err) return handle(err);
    getItems(os, (err, is) => { /* 越嵌越深，return 都容易漏 */ });
  });
});
// 现代写法：async/await + Promise，错误用一个 try/catch 收
try {
  const u = await getUser(id);
  const os = await getOrders(u);
  const is = await getItems(os);
} catch (err) { handle(err); }

// ===== 2. forEach(async ...) 是错的：不等、不串行、不接错 =====
urls.forEach(async (u) => {
  const r = await fetch(u);     // forEach 不等这个 await
  await save(r);                // 所有请求被同时发出，save 可能乱序
});                             // save 抛错 → unhandledRejection → Node 15+ 杀进程

// ✓ 串行（保序、限量）：
for (const u of urls) { await save(await fetch(u)); }

// ✓ 并发（一个失败整体 reject，慎用）：
const rs = await Promise.all(urls.map(fetch));

// ✓ 并发且容错（单个失败不影响其他，推荐批量场景）：
const rs = await Promise.allSettled(urls.map(fetch));
const ok = rs.filter(r => r.status === 'fulfilled').map(r => r.value);
const bad = rs.filter(r => r.status === 'rejected').map(r => r.reason);

// ===== 3. floating promise：没人接的 Promise =====
async function risky() { throw new Error('boom'); }
risky();                        // 没有 await、没有 .catch()

// Node 15 起，unhandledRejection 的默认行为 = 抛出异常、进程退出（code 1）
process.on('unhandledRejection', (reason) => {
  console.error('未接住的拒绝：', reason);
  process.exit(1);              // 上报后主动退，交给 PM2/systemd 拉起来
});
await 写在错误的位置 = 性能白给。把三个互不依赖的请求用 await 串起来，总耗时是三者之和；用 Promise.all 是取最大值。经验法则：循环里的 await 基本都该改成 Promise.all + 并发上限（p-limit 之类），除非顺序本身就是业务约束。 
// try/catch 的位置：包住 await，不要包住函数定义
async function load() {
  try {
    const cfg = await readConfig();
    return cfg;
  } catch (e) {
    // finally 里别再 await：会吞掉/延迟原始异常
    return defaultConfig();
  }
}

// .catch() 与 await 混用时，注意链式：then().catch() 捕获的是整条链
fetch(url).then(r => r.json()).catch(err => fallback());
模块 4

流与背压

流（Stream）解决两件事：不把整个文件/响应读进内存，以及用背压防止生产者把消费者冲爆。

类型例子
Readablefs.createReadStream、http req、process.stdin
Writablefs.createWriteStream、http res
DuplexTCP socket（可读可写）
Transformzlib.createGzip()、crypto Cipher：读写之间的加工厂
// 背压的机理：write() 返回 false = 内部缓冲超过 highWaterMark
const readable = fs.createReadStream('access.log');   // 默认每次读 64KB
const writable = fs.createWriteStream('out.log');    // 默认缓冲 16KB

readable.on('data', (chunk) => {
  const ok = writable.write(chunk);      // 缓冲没超 → true；超了 → false
  if (!ok) {                            // false 是背压信号：消费者忙不过来
    readable.pause();                    // ① 暂停读端，停止生产
    writable.once('drain', () => readable.resume());  // ② 缓冲排空后恢复
  }
});

// Transform：把日志转成大写再写出去
const { Transform } = require('node:stream');
const upper = new Transform({
  transform(chunk, encoding, cb) {
    this.push(chunk.toString().toUpperCase());   // 推进可读侧
    cb();                                        // 必须调用 cb()，否则整个流卡死
  },
});

// pipeline：自动背压 + 错误传播 + 句柄清理（pipe 做不到后两件）
const { pipeline } = require('node:stream');
pipeline(
  fs.createReadStream('access.log'),
  upper,
  fs.createWriteStream('out.log'),
  (err) => { if (err) console.error('管线失败', err); else console.log('完成'); }
);

// 异步迭代：for await 逐块消费，天然背压
for await (const chunk of fs.createReadStream('big.log')) {
  // 每块默认 64KB，内存恒定
}
highWaterMark 不是硬上限，是"开始背压"的水位线。对象模式（objectMode）默认是 16 个对象，字节模式 Readable 默认 64KB、Writable 默认 16KB。生产者比消费者快时，缓冲仍可能涨到远超它——所以 write() 返回 false 时的 pause/resume 不是可选优化，是必需逻辑。stream.pipe() 会自动处理背压，但它不传播错误：目标流出错时源流还在傻傻地读，文件句柄泄漏就是这么来的。用 pipeline() 或 pipeline()` 的 stream/promises 版本替代 pipe。 
// 常见性能组合：读大文件 → 按行切割 → 逐行处理 → 批量写库
const readline = require('node:readline');
const rl = readline.createInterface({ input: fs.createReadStream('big.log') });
let batch = [];
rl.on('line', (line) => {
  batch.push(parse(line));
  if (batch.length >= 1000) { flushToDb(batch); batch = []; }   // 批量写，别逐行 insert
});
模块 5

集群模式：cluster 与 PM2

单进程 Node 只用得满一个 CPU 核，且一个未捕获异常就整体退出。cluster 用多进程共享端口把这两个问题一起解决。

// cluster.js —— 每个 CPU 一个 worker，挂了自动补
const cluster = require('node:cluster');
const os = require('node:os');

if (cluster.isPrimary) {
  const n = os.cpus().length;
  console.log(`主进程 ${process.pid} 启动 ${n} 个 worker`);
  for (let i = 0; i < n; i++) cluster.fork();

  cluster.on('exit', (worker, code) => {
    // 平滑退出（reload）时 code 为 0 不补；异常崩溃才补
    if (code !== 0) {
      console.warn(`worker ${worker.process.pid} 崩溃(code ${code})，1s 后重启`);
      setTimeout(() => cluster.fork(), 1000);     // 加延时，防疯狂崩溃重启打满 CPU
    }
  });
} else {
  require('./server');   // 每个 worker 跑同一个 HTTP server，监听同一个端口
}
机制说明
端口共享只有主进程真正 listen，worker 通过 IPC 把连接"接"过来处理
分发策略非 Windows 默认轮询（RR）；Windows 上由操作系统分发（SCHED_NONE）
隔离性worker 间不共享内存，一个 worker 崩溃不影响其他；Session 等共享状态必须外置（Redis）
Sticky SessionWebSocket / Socket.io / 长轮询必须把同一客户端固定到同一 worker，否则握手后断连。用 Nginx ip_hash 或 cluster sticky 模块
# PM2：生产事实标准的进程管理器
pm2 start server.js -i max        # 集群模式，worker 数 = CPU 核数
pm2 start server.js -i 2 --name api   # 固定 2 个 worker，命名进程
pm2 reload api                    # 零停机重启：先起新的，再下旧的（restart 是直接杀）
pm2 logs api --lines 100          # 看日志
pm2 monit                         # 实时 CPU/内存面板

// ecosystem.config.js —— 声明式配置，替代一长串命令行参数
module.exports = {
  apps: [{
    name: 'api',
    script: './server.js',
    instances: 'max',
    exec_mode: 'cluster',
    max_memory_restart: '500M',     // 内存超限自动重启，兜住泄漏
    env: { NODE_ENV: 'production' },
  }],
};

// 部署更新三步：pm2 reload（零停机）→ 健康检查 → 出问题 pm2 stop 回滚
CPU 密集型任务怎么办？cluster 是多进程，启动开销大（每个 worker 独立 V8 实例，几十 MB 起）；如果只是偶尔算个哈希、压个图，用 worker_threads（线程级，共享内存可选，启动几毫秒）更合适。高频、重度的计算才上独立微服务（Go/Rust），Node 的舒适区是高并发 I/O。
模块 6

内存管理与 V8 GC

V8 把堆分成两代：新生代（小、死得快的对象）和 老生代（活得久的对象）。GC 策略因此不同。

区域算法特性
新生代Scavenge（半空间复制）频率高、单次快（亚毫秒级）。活过两轮 GC 晋升到老生代
老生代Mark-Sweep + Compact整堆标记 + 清理，堆越大停顿越久（几十到数百毫秒），期间主线程全停
堆外内存不计入 V8 堆Buffer / ArrayBuffer 走这里，受操作系统约束，heapUsed 看不到它们
// 看内存：rss 才是进程真实占用，heapUsed 只是 V8 堆已用
setInterval(() => {
  const m = process.memoryUsage();
  console.log({
    rssMB:        (m.rss / 1048576).toFixed(1),        // 进程常驻物理内存（含堆外）
    heapUsedMB:   (m.heapUsed / 1048576).toFixed(1),   // V8 堆已用
    externalMB:   (m.external / 1048576).toFixed(1),   // 堆外（Buffer 等）
    arrayBuffersMB: (m.arrayBuffers / 1048576).toFixed(1),
  });
}, 5000);

// 堆上限：64 位默认约 2GB 起（视机器内存可到 ~4GB），超了直接 OOM 崩溃
node --max-old-space-size=4096 server.js

// 内存泄漏排查标准流程：
// 1. node --heapsnapshot-signal=SIGUSR2 server.js，业务高峰期和低峰期各 kill -USR2 一次
// 2. Chrome DevTools → Memory → 载入两个快照 → Comparison 视图
// 3. 看 Retained Size 异常大的对象和它的"保留树"，顺藤摸到引用它的模块级变量

Node 里最常见的四种泄漏写法

  • 无上限的模块级缓存：const cache = new Map() 只进不出，内存单调涨。用 lru-cache 或加 TTL 清理
  • EventEmitter 监听器只加不减：每个请求都 emitter.on('x')，超过 events.maxListeners（默认 10）就告警，更糟的是监听器闭包抓住了请求级大对象
  • setInterval 不清：回调里引用了请求上下文，整个对象树被定时器钉死
  • 被 Buffer 骗过的监控：只盯 heapUsed，结果 Buffer 堆外分配把机器内存吃光——监控必须看 rss
GC 停顿是延迟毛刺的常见来源。老生代堆涨到 1GB+ 时，一次 Mark-Compact 可能停几百毫秒，对 P99 延迟敏感的服务就是故障。缓解手段：控制堆大小（小堆 = 短停顿）、复用对象池、减少长生命周期大对象、以及把大块内存操作拆到 worker_threads。Node 14+ 可用 --max-semi-space-size 调新生代，大新生代减少对象晋升、降低老生代压力。
模块 7

CommonJS vs ESM

维度CommonJS（CJS）ESM
文件标识.js + package.json 无 "type".mjs，或 package.json "type": "module"
导入导出require() / module.exportsimport / export
加载时机同步，运行时求值静态分析 + 异步加载，顶层就能 await
路径必须带扩展require('./a') 补全 .jsimport './a.js' 必须写全，不补全
__dirname / __filename内置没有，要用 import.meta.url 自己拼
导出绑定值的拷贝（exports.x = 1 后改不影响引用方）活的只读绑定，源模块改了引用方看得到
Tree Shaking基本不可能静态结构，打包器可摇树
互相调用CJS 可以 require() ESM（Node 22.12+/23+）ESM 可以 import CJS（默认导入 = module.exports）
// CJS
const { readFile } = require('node:fs');
module.exports = { readFile };
console.log(__dirname);            // 当前目录

// ESM 等价写法
import { readFile } from 'node:fs';
export { readFile };
import { fileURLToPath } from 'node:url';
import { dirname } from 'node:path';
const __dirname = dirname(fileURLToPath(import.meta.url));   // 唯一标准姿势

// ESM 顶层 await：模块加载时就能跑异步初始化
const cfg = await loadConfig();      // CJS 里不可能这么写

// ESM 引入 CJS：默认导入是 module.exports 本体
import express from 'express';          // 常见包仍是 CJS，这么写没问题

// CJS 引入 ESM：低版本 Node 直接抛 ERR_REQUIRE_ESM
// const { x } = require('./pure-esm.mjs');   // ✗ Node < 22.12 报错
const { x } = await import('./pure-esm.mjs');  // ✓ 动态 import 全版本通用
双包陷阱（dual package hazard）：一个包同时提供 CJS 和 ESM 入口（package.json 的 exports 字段按 require/import 条件分流）时，CJS 和 ESM 拿到的是两个不同模块实例——状态不共享，instanceof 都可能判 False。症状是"同一个类在两个文件里行为不一样"。排查：确认引用方和被引用方用的是同一套模块系统。
模块 8

常见性能坑：阻塞、大 JSON、假异步

操作量级参考解法
fs.readFileSync 读 1GB 文件秒级停摆createReadStream 流式读
JSON.parse 10MB 字符串约 100~300msworker_threads / 流式解析（stream-json）
JSON.parse 100MB 字符串约 1~3 秒，全站卡死同上；或从源头避免（别传大 JSON）
crypto.pbkdf2Sync 一次几十~几百 ms用异步 pbkdf2 / scrypt
深层递归 / 大 RegExp 回溯不定，可能爆栈改迭代；RegExp 加超时或换非回溯引擎
巨型 for 循环（千万次级）整段占死主线程分片 + setImmediate 让出；或 worker
// 大 JSON.parse：峰值内存 = 原字符串 + 解析后对象（常为 2~3 倍）
const raw = await readFile('data.json', 'utf8');   // 100MB 字符串
const obj = JSON.parse(raw);                    // 又一份 100MB+ 的对象树

// ✓ 方案一：丢进 worker_threads，主线程零感知
const { Worker } = require('node:worker_threads');
const w = new Worker('./parse-worker.js', { workerData: raw });
w.on('message', (obj) => use(obj));      // 解析在主线程外完成

// ✓ 方案二：流式逐条解析，内存恒定（JSON Lines / NDJSON）
const { parser } = require('stream-json');
fs.createReadStream('data.ndjson')
  .pipe(split2())                              // 一行一条 JSON
  .on('data', (line) => handle(JSON.parse(line)));

// 长循环让出事件循环：每 1000 条让一次，请求不再集体卡死
let i = 0;
function work() {
  const end = Math.min(i + 1000, total);
  for (; i < end; i++) heavyTask(i);
  if (i < total) setImmediate(work);      // 本轮结束再排下一片
}
work();
最隐蔽的"假异步"：用 async 包一个全是同步计算的函数，它确实返回 Promise，但计算过程照样占死主线程——async 关键字不产生任何并行。判断标准只有一个：看这段代码里有没有真正的 I/O 等待点。没有，就该拆去 worker_threads。
避坑

十个线上坑

1
主线程跑大 JSON.parse / 同步 fs
100MB JSON.parse 能让整个进程停 1~3 秒，期间所有请求一起超时。大对象解析进 worker_threads，文件读用流。
2
urls.forEach(async fn)
forEach 不等 await：请求全部并发发出、写库乱序、异常变成 unhandledRejection。要串行用 for...of，要并发用 Promise.all/allSettled。
3
floating promise 没人 catch
Node 15+ 起未处理的 Promise 拒绝默认直接杀进程。入口处装 process.on('unhandledRejection') 兜底并主动退出，交给 PM2 拉起。
4
nextTick / Promise 里递归
nextTick 队列和微任务队列永远排不空，事件循环根本没机会跑，timer 和 I/O 全部饿死。递归逻辑必须让出到下一轮（setImmediate）。
5
用 stream.pipe 串管线然后不管错误
pipe 不传播错误：下游挂了上游还在读，句柄泄漏、内存堆积。用 pipeline()，它在任何一段失败时销毁整条链。
6
无视 write() 返回的 false
消费端处理不过来时写缓冲无限膨胀，内存缓慢涨到 OOM。false 出现要 pause 读端、drain 后 resume。
7
cluster 多进程没做 sticky session
WebSocket/Socket.io 握手连到 worker A，后续帧被分到 worker B，连接秒断。Nginx ip_hash 或 sticky 模块固定同一客户端。
8
模块级 Map 当缓存，无上限无清理
典型内存泄漏：只进不出，heapUsed 单调上涨直到 OOM。加 LRU 上限或 TTL，必要时 max_memory_restart 兜底。
9
setInterval 里跑可能重叠的 async 任务
上一次还没跑完下一次又触发，任务排队叠加。改用递归 setTimeout，或加"运行中"标志跳过本轮。
10
CJS/ESM 混用踩坑
ESM 里写 require/__dirname 直接 ReferenceError；CJS require() ESM 在 Node 22.12 之前抛 ERR_REQUIRE_ESM。新项目统一 ESM，旧包用动态 import() 过渡。
自测

六道题

1. 下面代码的输出顺序是？
setTimeout(() => console.log('A'), 0); Promise.resolve().then(() => console.log('B')); process.nextTick(() => console.log('C')); console.log('D');
正确答案：D → C → B → A。同步代码最先；当前操作结束后先掏空 nextTick 队列（C），再掏空微任务队列（B）；setTimeout 的回款要等事件循环跑到 timers 阶段（A）。
2. async function boom() { throw new Error('x'); } 然后直接 boom() 不 await 不 catch。Node 18 的默认行为是？
正确答案：默认抛出异常、进程退出。Node 15 起 unhandledRejection 的默认行为从 warning 改为 throw。生产应显式注册 process.on('unhandledRejection') 做日志上报，然后主动退出让 PM2 拉起。
3. writable.write(chunk) 返回 false，意味着什么？
正确答案：背压信号。false 不代表失败（数据已进缓冲），代表"再写就要涨内存了"。正确做法是暂停可读端，监听一次 drain 后再 resume。pipeline/pipe 会自动处理这件事，手写 data 事件时必须自己做。
4. 下列哪组操作走的是 libuv 线程池（默认 4 线程）？
正确答案：fs / dns.lookup / crypto / zlib。网络 I/O 走 epoll/kqueue/IOCP（事件循环本体），而文件系统、DNS 查询、加密、压缩由 libuv 线程池模拟异步，容量受 UV_THREADPOOL_SIZE 限制。同步 JS（JSON.parse 等）只在主线程，谁都不分流。
5. cluster 模式部署 Socket.io 服务，客户端频繁断线重连，最可能的原因和修法？
正确答案：需要 sticky session。主进程按轮询把连接分给不同 worker，而 WebSocket 是有状态的长连接，握手后必须留在同一 worker。另外 worker 间不共享内存，Socket.io 的适配器也要指到 Redis。
6. 一个 CommonJS 文件里 require() 一个纯 ESM 包，会发生什么？
正确答案：ERR_REQUIRE_ESM（22.12+/23+ 之前）。CJS 是同步加载，ESM 支持顶层异步，所以历史上不能 require()。低版本用 const m = await import('./x.mjs') 动态导入；双向互通时还要注意双包陷阱（CJS 和 ESM 是两个模块实例，状态不共享）。
