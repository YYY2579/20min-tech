开始前

把编译器和观察手段准备好

C++ 的行为和工具链强绑定。同样的代码，加不加 -O2、开不开 sanitizer，跑出来的结果可能完全不同。先记住这四条。

# 正常构建：开全警告
g++ -std=c++20 -Wall -Wextra -Wpedantic -O2 main.cpp -o main

# 调试构建：关优化 + 抓内存错误和未定义行为
g++ -std=c++20 -g -O0 -fsanitize=address,undefined main.cpp -o main_dbg

# 看编译器到底生成了什么
g++ -std=c++20 -O2 -S main.cpp -o -   # 汇编输出到 stdout
objdump -d --demangle main.o          # 反汇编目标文件
三个必开的开关：① -fsanitize=address（ASan）抓越界、use-after-free、泄漏；② -fsanitize=undefined（UBSan）抓有符号溢出、空指针解引用、非法移位——这些在 -O2 下会被编译器"利用"，产生你完全看不懂的行为；③ -D_GLIBCXX_ASSERTIONS 给容器的下标和迭代器加检查。三者都只在调试构建开，会拖慢 2~20 倍。
阅读姿势：每个模块都按"机制 → 为什么这么设计 → 边界在哪"走。如果只记一件事，记 RAII：C++ 里所有资源管理的正确写法，最终都能还原成"把资源绑到一个对象的生命周期上"。
模块 1

RAII：C++ 真正的世界观

RAII 是 Resource Acquisition Is Initialization 的缩写，中文译作"资源获取即初始化"。这个名字起得很糟——它听起来像在讲构造函数，实际讲的是析构函数。

完整表述是：把资源的生命周期绑定到一个栈对象的生命周期上。构造时获取，析构时释放。因为栈对象离开作用域一定会被析构，所以资源一定会被释放。它靠两条语言规则保证，跟 GC 无关、跟异常无关：

  • 正常离开作用域：按构造的逆序析构。
  • 异常抛出（栈展开，stack unwinding）：从 throw 点逐层销毁已构造完成的局部对象，直到找到 catch。这是标准强制要求的。

第二条是关键。它意味着你不需要 try/finally，也不需要 defer——异常路径和正常路径走的是同一段析构代码。

// 手写资源管理：每个提前返回点都要记得释放
int bad_read(const char* path) {
    std::FILE* fp = std::fopen(path, "rb");
    if (!fp) return -1;
    char* buf = (char*)std::malloc(4096);
    if (!buf) { std::fclose(fp); return -1; }        // 清理点 1
    if (std::fread(buf, 1, 4096, fp) == 0) {
        std::free(buf); std::fclose(fp); return -1;     // 清理点 2
    }
    std::free(buf); std::fclose(fp);                     // 清理点 3
    return 0;
}

// RAII 版本：清理点只有一个
class File {
public:
    explicit File(const char* path) : fp_(std::fopen(path, "rb")) {
        if (!fp_) throw std::runtime_error("open failed");
    }
    ~File() { if (fp_) std::fclose(fp_); }
    File(const File&) = delete;              // 禁止拷贝，否则 double close
    File& operator=(const File&) = delete;
    File(File&& o) noexcept : fp_(o.fp_) { o.fp_ = nullptr; }
    std::FILE* get() const noexcept { return fp_; }
private:
    std::FILE* fp_;
};

数一下清理点：左边 3 个，右边 1 个。工程代码分支一多，左边这种写法几乎必然漏掉一个——这就是历史上无数内存泄漏和句柄耗尽的来源。

标准库已经把绝大多数资源包好了

资源RAII 包装说明
堆内存unique_ptr / shared_ptr不要裸 new/delete
互斥锁lock_guard / unique_lock构造加锁，析构解锁
文件fstream / ifstream / ofstream析构自动 close

std::mutex mtx;
void update() {
    std::lock_guard<std::mutex> lk(mtx);            // 构造时 lock()
    if (bad()) return;                              // 提前返回也解锁
    if (worse()) throw std::runtime_error("x");   // 抛异常也解锁
    do_work();
}
析构函数里绝对不能抛异常。C++11 起析构函数默认 noexcept，异常真从析构函数逃逸会直接 std::terminate——不给任何 catch 机会。
深层原因：如果栈展开过程中（已有一个异常在飞）析构函数又抛一个，C++ 无法同时处理两个，标准选择直接终止。所以析构里做可能失败的操作，必须自己 try/catch 吞掉并记日志。
Rule of Zero 是终点。理想状态下析构、拷贝构造、拷贝赋值、移动构造、移动赋值一个都不写，全靠成员对象自己的 RAII。只有直接管理裸资源时才需要写全五个——写一半最危险，因为编译器生成的默认版本是浅拷贝，直接 double free。
模块 2

移动语义：所有权能否转移

C++11 之前，函数返回一个大 vector 要付一次深拷贝。移动语义解决的问题是：当源对象马上就要死了，为什么还要复制内容？直接把指针偷过来不行吗？

值类别判断标准典型例子
左值 lvalue有名字、能取地址、生命周期不止这一行x、arr[0]、*p、++i
纯右值 prvalue临时对象、字面量，没有名字42、"abc"、Foo()、a + b
将亡值 xvalue本质是左值，但被标记为"可被搬空"std::move(x)、static_cast<Foo&&>(x)

工程上只需一个判断：能取地址、后面还要用的，是左值；马上要销毁的临时对象，是右值。右值引用 T&& 就是"只绑右值"的引用类型，它存在的意义是让编译器帮你选出"可以安全搬空"的那些对象。

std::move 什么都不做

// libstdc++ 的实现，本质就这一行
template <class T>
constexpr std::remove_reference_t<T>&& move(T&& t) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(t);
}

std::string a = "a very long string ...";
std::string b = std::move(a);   // 这里才发生移动：调用移动构造函数
// a 现在处于"有效但未指定"（valid but unspecified）状态：
// 标准只保证可以安全析构、可以重新赋值，不保证它是空的
std::move 是类型转换，不是操作。它只把表达式变成右值，让重载决议去选移动构造/移动赋值；真正"搬"的动作发生在被调用函数体里。由此推出两个常见错误：
① std::move(x) 之后继续读 x 的值——结果未指定，不同标准库实现可能不一样；
② const std::string s; auto t = std::move(s); —— 这里发生的是拷贝。因为 const T&& 绑不到 T&& 参数，移动构造签名不匹配，只能回退到拷贝。const 对象永远移不动。

移动构造什么时候真的被调用

写法结果
T b = std::move(a);调用移动构造
v.push_back(std::move(a));调用移动构造
return local_var;通常一次构造都不发生——NRVO 直接在调用方栈上构造
T b = a; / v.push_back(a);拷贝构造（a 是左值）
T b = makeT();C++17 起保证省略，直接构造到 b 上
auto v2 = std::move(v1);O(1) 指针交换；而 auto v2 = v1 是 O(n) 逐元素拷贝

noexcept 决定 vector 扩容时是搬还是抄

// 扩容要把旧元素搬到新内存。若移动构造可能抛异常，搬到一半失败就无法回滚
// （旧数组已被破坏）。所以标准规定用 std::move_if_noexcept 决策。

struct Good { Good(Good&&) noexcept = default; };  // 扩容时移动
struct Bad  { Bad(Bad&&) {} };                        // 扩容时拷贝！

// 灌 100 万个元素：Good 约 20 次移动；Bad 约 20 次全量拷贝，可能差几十毫秒
规则：移动构造/移动赋值只要不抛异常，就必须标 noexcept。这不是风格问题。标准库容器、std::swap、std::sort 都会读这个标记，漏写会在你完全没意识到的地方退化成拷贝。

完美转发：让参数原样传下去

需求：写一个工厂 make<T>(args...)，希望 args 传给 T 的构造函数时保持原来的值类别——左值进来就拷贝，右值进来就移动。

// 万能引用（forwarding reference）：T&& 在模板推导上下文里才成立
template <class T, class... Args>
std::unique_ptr<T> make(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}

// 引用折叠：T 推导为 Foo& 时，Foo& && 折叠成 Foo&（传左值）
//           T 推导为 Foo  时，Foo &&   保持 Foo&&（传右值）
template <class T> void relay(T&& x) {
    target(std::forward<T>(x));   // 保持原样
    // target(std::move(x));      // 错：左值进来也会被强转成右值
}
万能引用只在两种情况下成立：① template<class T> void f(T&& x)（T 需要被推导）；② auto&& x = ...。
写成 void f(Widget&& x) 或 void f(std::vector<int>&& x) 那是普通右值引用，只能绑右值，跟转发毫无关系。这个区分在 code review 里被问得极多。
模块 3

智能指针：三种所有权模型

智能指针不是"自动 delete 的指针"，而是三种明确的所有权语义。选错语义比不用智能指针更糟。

类型语义sizeof开销
unique_ptr独占，不可拷贝只可移动8 字节零开销，析构时一次 delete
shared_ptr共享，计数归零才释放16 字节控制块堆分配 + 原子增减计数
weak_ptr不增计数的弱引用16 字节用前必须 lock() 提升
// unique_ptr 是默认选择
auto p = std::make_unique<Widget>(1, 2);
auto q = std::move(p);        // 转移所有权，p 变 nullptr
// auto r = p;                // ✗ 编译错误，拷贝构造被 delete

// 自定义 deleter 会占空间（无状态函数对象可利用 EBO 消掉）
auto f = std::unique_ptr<std::FILE, decltype(&std::fclose)>(
    std::fopen("a.txt", "r"), &std::fclose);   // sizeof 变 16

// 参数怎么表达所有权
void take(std::unique_ptr<Widget> w);   // 接管，调用方必须 move
void use(const Widget& w);              // 只用一下，别传智能指针
void maybe(Widget* w);                 // 可为空且不接管
被违反最多的接口原则：不要用 const shared_ptr<T>& 表示"我只想用一下这个对象"。这逼调用方必须用 shared_ptr 管理对象，还多一层间接。
正确表达：T& / const T& = 不接管、不为空；T* = 不接管、可为空；unique_ptr<T> 按值 = 接管；shared_ptr<T> 按值 = 真的要共享所有权。

控制块：那 16 字节里有什么

// 控制块通常包含：强引用计数（原子）、弱引用计数（原子）、deleter、allocator
// 它是堆上单独分配的一块内存

std::shared_ptr<Widget> a(new Widget);   // 2 次 malloc：对象一次，控制块一次
auto b = std::make_shared<Widget>();     // 1 次 malloc：两者放在同一块内存

// make_shared 的副作用：只要还有 weak_ptr 活着，整块内存（含已析构的对象）都不释放

引用计数的增减是原子操作，单线程下也有成本（lock 前缀指令）；多线程频繁拷贝同一个 shared_ptr 会造成 cache line 争用——这在压测里是真实的性能问题。

shared_ptr 的线程安全是"半安全"的，被误解得最厉害：
① 引用计数安全：多线程各自拷贝/销毁不同的 shared_ptr 实例（指向同一对象）没问题；
② 指向的对象不安全：多线程通过它读写同一个 Widget，照样要加锁；
③ 同一个实例被并发读写不安全：一个线程 reset()、另一个线程拷贝它，就是数据竞争。
标准库的保证只到"不同实例共享同一控制块"这一层。

weak_ptr：打破循环引用

struct Node {
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;   // ✗ 循环引用
};
auto a = std::make_shared<Node>();
auto b = std::make_shared<Node>();
a->next = b;    // b 计数 = 2
b->prev = a;    // a 计数 = 2
// 离开作用域各减到 1，永远不归零 → 内存泄漏

struct Node2 {
    std::shared_ptr<Node2> next;
    std::weak_ptr<Node2> prev;    // ✓ 反向指针用 weak，不增计数
};

if (auto p = node->prev.lock()) p->doSomething();  // 期间保证存活
else { /* 对象已销毁 */ }
场景该用什么
工厂返回对象unique_ptr
容器持有元素vector<T> 或 vector<unique_ptr<T>>
父子节点（父持有子）父 → 子 shared_ptr，子 → 父 weak_ptr
缓存（可能被别处删除）weak_ptr，lock 失败就重建
观察者列表vector<weak_ptr<Observer>>
pimpl 惯用法unique_ptr<Impl>（析构必须定义在 .cpp 里）
pimpl + unique_ptr 的经典编译错误：类里写 std::unique_ptr<Impl> p_; 而 Impl 只是前向声明的不完整类型时，编译器生成的析构函数会在头文件里实例化 delete Impl，此时 Impl 不完整，直接编译失败。
解法：类里声明 ~Widget();，在 .cpp 里定义 Widget::~Widget() = default;。移动构造同理。
模块 4

模板：编译期的一门子语言

模板不是"泛型语法糖"，它是图灵完备的编译期计算系统。理解这一点，才能理解为什么模板错误信息那么长、编译那么慢、为什么 concepts 是 C++20 最重要的特性。

template <class T>
T maxOf(T a, T b) { return a < b ? b : a; }

maxOf(1, 2);          // 实例化出 maxOf<int>
maxOf(1.0, 2.0);      // 实例化出 maxOf<double>
maxOf(1, 2.0);        // ✗ 推导冲突：T 不能同时是 int 和 double
maxOf<double>(1, 2.0); // ✓ 显式指定，int 被转换

每个不同的实参类型都生成一份独立的机器码，这就是模板代码膨胀：vector<A> 和 vector<B> 是两套完全独立的代码。也正因为"模板定义必须在调用点可见"，模板实现通常全放头文件，显著拖慢编译——一个中等项目 include 了 <algorithm> 和 <map>，预处理后可能几万行。

特化：为特定类型换实现

// 主模板
template <class T>
struct Hasher { std::size_t operator()(const T& v) const {
    return std::hash<T>{}(v);
} };

// 全特化：所有参数都指定
template <>
struct Hasher<std::string> {
    std::size_t operator()(const std::string& s) const {
        return fnv1a(s.data(), s.size());
    }
};

// 偏特化：只指定一部分参数（只有类模板能偏特化，函数模板不行）
template <class T>
struct Hasher<std::vector<T>> {
    std::size_t operator()(const std::vector<T>& v) const {
        std::size_t h = 0;
        for (auto& e : v) h ^= Hasher<T>{}(e) + 0x9e3779b9 + (h << 6) + (h >> 2);
        return h;
    }
};

SFINAE：C++11 时代的"约束"

SFINAE 是 Substitution Failure Is Not An Error 的缩写：模板参数替换失败时不报错，只把这个候选从重载集里剔除。这条规则本是编译器实现细节，被意外发现可以用来做编译期条件判断。

// 只有当 T 有 size() 方法时，这个重载才成立
template <class T>
auto len(const T& t) -> decltype(t.size()) { return t.size(); }

// 用 enable_if 做条件启用（C++17 之前的日常写法，极其丑陋）
template <class T, class = std::enable_if_t<std::is_integral_v<T>>>
void onlyInt(T v) { /* ... */ }
SFINAE 的工程代价：错误信息会膨胀到几百行（编译器要把每个被剔除的候选都打印出来）；写起来反人类，一个"要求 T 可比较"要十几行 type traits。这就是 C++20 引入 concepts 的直接动机。

Concepts：把约束写进签名

#include <concepts>

template <class T>
concept Addable = requires(T a, T b) {
    { a + b } -> std::convertible_to<T>;
};

template <Addable T>                 // 简洁写法
T sum3(T a, T b, T c) { return a + b + c; }

template <class T>
    requires std::ranges::range<T> && Addable<std::ranges::range_value_t<T>>
auto total(const T& r) { /* ... */ }

收益很直接：报错从"模板内部第 847 行实例化失败"变成"T 不满足 Addable"，而且约束参与重载决议，让重载集更精确。C++20 之后的新代码应该默认这么写。

constexpr：把计算搬到编译期

constexpr int fib(int n) { return n < 2 ? n : fib(n-1) + fib(n-2); }
static_assert(fib(20) == 6765);                  // 编译期验证

// C++20: consteval 强制编译期求值，运行期调用直接编译失败
consteval int twice(int n) { return n * 2; }

// C++17: if constexpr —— 编译期分支，未选中的分支不会被实例化
template <class T>
std::string describe(const T& v) {
    if constexpr (std::is_pointer_v<T>)          return v ? "ptr" : "null";
    else if constexpr (std::is_arithmetic_v<T>) return std::to_string(v);
    else                                        return "other";
}
constexpr 的价值不是"跑得快"，而是"把错误从运行期挪到编译期"。查表、哈希、序列化格式解析都可以在编译期完成。代价是编译时间变长、调试信息变差，且 constexpr 函数里不能随便抛异常或调用非 constexpr 函数。

标准库：容器怎么选，视图为什么快

std::vector<int> v;
for (int i = 0; i < 1'000'000; ++i) v.push_back(i);
// 约扩容 20 次（libstdc++ 按 2 倍，MSVC 按 1.5 倍），总拷贝 ≈ 2n
// 摊还到每次 push_back 是 O(1)，但单次扩容仍然是一次 O(n) 的尖峰

v.reserve(1'000'000);   // 已知大小时先预留，消掉尖峰

std::vector<int> a; a.reserve(10);  // size()==0, capacity()==10
std::vector<int> b; b.resize(10);   // size()==10，元素都被构造为 0

string_view：一个指针 + 一个长度，换来零拷贝

void log1(const std::string& s);

void log2(std::string_view sv);   // sizeof == 16（64 位）
log2("hello");   // 零拷贝：只存 ptr + len
std::string s = "hello";
log2(s);      // 零拷贝

string_view 最大的坑是生命周期。它不拥有内存，源字符串一销毁或重新分配，视图立刻悬空，而且不会有任何警告。三个高危写法：

③ 把 string_view 存成成员变量，而源字符串是外部传入的。
经验法则：string_view 只用于函数参数，不用于返回值，不用于成员变量。

算法：组合比手写循环更清楚，也常常更快

// 经典 erase-remove：删掉所有偶数，O(n) 只遍历一遍
v.erase(std::remove_if(v.begin(), v.end(),
                       [](int x){ return x % 2 == 0; }),
        v.end());
// remove_if 不真删，只把保留的元素往前挪，返回新的逻辑结尾

std::erase_if(v, [](int x){ return x % 2 == 0; });   // C++20

// ranges：惰性视图，不产生中间容器，遍历时才计算
auto r = v | std::views::filter([](int x){ return x > 10; })
           | std::views::transform([](int x){ return x * x; })
           | std::views::take(5);
ranges 的反直觉之处：视图不拥有数据，只引用原容器。原容器一旦修改（尤其 vector 扩容），视图里的迭代器就失效。另外 views::filter 在 begin() 时可能需要线性扫描找到第一个满足条件的元素，打破了"range 的 begin 是 O(1)"的直觉。
模块 6

七个会咬人的语言细节

1. 对象切片（object slicing）

struct Base { int a; virtual void f() const { puts("Base"); } };
struct Derived : Base { int b; void f() const override { puts("Derived"); } };

void byValue(Base b) { b.f(); }
Derived d; byValue(d);          // 输出 "Base"：Derived 的部分被切掉，vtable 也换了

std::vector<Base> v; v.push_back(d);   // 同样切片，虚函数派发失效
void byRef(const Base& b) { b.f(); }  // 输出 "Derived"
std::vector<std::unique_ptr<Base>> vp;  // 多态容器

切片是静默发生的，编译器基本不警告。本质是：C++ 的对象布局是值语义的，把派生类对象赋给基类对象，只拷贝基类那部分字节，vtable 指针也被替换成基类的。

2. 隐式转换与 explicit

class Buffer {
public:
    Buffer(int size);              // ✗ 非 explicit：int 能隐式变成 Buffer
    operator bool() const;        // ✗ 隐式转换到 bool
};
void send(const Buffer& b);
send(1024);        // 编译通过！构造了一个 1024 字节的 Buffer

explicit Buffer(int size);         // ✓
explicit operator bool() const;   // ✓ if (buf) 仍可用（语境转换）

单参数构造函数一律加 explicit，除非你确实需要隐式转换（如 std::string 从 const char* 构造）。operator bool 也要加，否则会出现两个对象被转成 bool 再做整数加法的诡异情况。

3. 基类析构函数必须是 virtual

struct Base { ~Base() {} };                     // ✗ 非虚
struct Derived : Base { std::vector<int> data; };

Base* p = new Derived();
delete p;   // 只调用 ~Base()，vector 的析构没跑 → 内存泄漏（UB）

struct Base2 { virtual ~Base2() = default; };  // ✓

反过来的规则同样重要：不打算被继承的类就标 final。这能让编译器做去虚化优化，也防止别人继承出一个析构有问题的子类。

for (auto x : getVector().items()) { ... } // ✗ 只有 getVector() 被延长，

6. 未初始化与有符号溢出

int x;              // 局部内置类型不初始化，值不确定（不是 0）
int g;              // 全局/静态 → 零初始化

int f(int x) { return x + 1 > x; }
// 有符号溢出是 UB，编译器假设它不发生，可能把整个函数优化成 return true

for (std::size_t i = n - 1; i >= 0; --i) { ... }
// ✗ 无符号永远 >= 0，死循环。无符号溢出是定义良好的模运算，但同样危险

7. ODR 违反与 inline 变量

int counter = 0;             // ✗ 放头文件里：每个 .cpp 一份定义，链接报错

extern int counter;          // ✓ 头文件声明，某个 .cpp 定义
inline int counter = 0;      // ✓ C++17：inline 变量，全程序唯一

struct Config { inline static std::string name = "app"; };  // ✓ 无需 .cpp 再定义
ODR 最阴险的形态是"两个 .cpp 里同一个 inline 函数定义不同"（比如靠宏切换实现，头文件没同步）。链接器只会随便挑一个，行为取决于链接顺序——这类 bug 在开启 LTO 后可能突然出现或消失，极难定位。
模块 7

性能：零开销抽象承诺了什么

Stroustrup 的原话是："你不用的东西，不该付出代价；你用的东西，手写代码也不可能更好。"注意这是承诺不是保证——它成立的前提是你用对了抽象。

抽象运行时开销条件
模板 / 泛型0编译期展开，没有类型擦除
inline 函数0编译器真的内联了（inline 关键字只是允许跨 TU 定义，不保证内联）
RAII / unique_ptr0默认 deleter，与裸指针同大小同速度
虚函数1 次间接跳转vtable 查表，且通常无法内联
shared_ptr原子计数 + 控制块拷贝一次几十周期，跨核争用更贵
std::function可能堆分配 + 间接调用捕获超过 SBO 缓冲（通常 16 字节）时分配
异常不抛时接近 0表驱动实现，但抛出时极慢（微秒级）

缓存友好常常比算法复杂度更重要

std::vector<int> v(1'000'000, 1);
std::list<int>   l(1'000'000, 1);

// 遍历 100 万个 int 的实测量级（现代 x86，-O2）：
// vector：约 0.5 ~ 1 ms   （一个 cache line 装 16 个 int）
// list  ：约 8 ~ 15 ms    （每个节点一次 cache miss）
// 差 10 倍以上，而两者的算法复杂度都是 O(n)
访问模式典型延迟类比（1 周期 = 1 秒）
L1 cache 命中约 4 周期4 秒
L2 cache 命中约 12 周期12 秒
L3 cache 命中约 40 周期40 秒
主存约 200 周期3 分钟
SSD 随机读约 10 万周期1 天

这解释了一个反直觉的事实：数据量在几万到几百万时，vector 上的线性查找经常快过 set 的 O(log n) 查找。因为 vector 的每次比较都在同一两条 cache line 上，而红黑树每下降一层就是一次潜在 cache miss。

# 开 LTO：让链接器跨 .cpp 内联、做常量传播
g++ -std=c++20 -O2 -flto -o app *.cpp

# PGO：先用真实负载跑一遍收集分支 profile，再据此优化
g++ -std=c++20 -O2 -fprofile-generate -o app_pgo *.cpp
./app_pgo < typical_workload.txt
g++ -std=c++20 -O2 -fprofile-use -o app *.cpp
LTO 的代价：链接时间可能翻几倍，内存占用大幅上升（链接器要把所有 TU 的 IR 同时载入），而且会放大 ODR 违反的后果。大型项目通常只在 release 构建开 LTO，并且分模块做 thin LTO。
优化优先级：① 先测量（perf / VTune），别猜；② 先改数据布局（结构体数组 vs 数组结构体、减少指针跳转、把热字段放一起）；③ 再改算法；④ 最后才考虑指令级优化。绝大多数"C++ 很慢"的案例，根因是指针追逐和无谓的堆分配，不是虚函数或异常。

C++20：concepts + ranges 一段完整示例

// 对容器做过滤 + 变换 + 求和，全程不产生中间容器
template <std::ranges::input_range R>
    requires std::is_arithmetic_v<std::ranges::range_value_t<R>>
auto sumOfEvensSquared(R&& r) {
    auto view = std::forward<R>(r)
        | std::views::filter([](auto x){ return x % 2 == 0; })
        | std::views::transform([](auto x){ return x * x; });
    return std::accumulate(view.begin(), view.end(),
                           std::ranges::range_value_t<R>{});
}
std::vector<int> v = {1,2,3,4,5,6};
auto s = sumOfEvensSquared(v);   // 4 + 16 + 36 = 56

常见坑

十个真实事故

1
基类析构没写 virtual，用基类指针 delete 派生对象
只调用基类析构，派生类成员（vector、string、句柄）全部泄漏。这是 UB，ASan 不一定报。有虚函数的类，析构必须是虚的。
2
std::move 之后继续使用源对象
对象处于"有效但未指定"状态，标准不保证是空的。不同标准库、不同优化级别下表现可能不同。move 之后只允许析构或重新赋值。
3
移动构造函数忘了 noexcept
vector 扩容时退化成拷贝。百万元素的容器，从"搬 20 次指针"变成"拷 20 次全量数据"，性能差一个数量级。
4
按值传多态对象，发生对象切片
派生类部分被切掉，虚函数派发失效。多态对象一律用引用或智能指针传递，容器用 vector<unique_ptr<Base>>。
5
shared_ptr 循环引用，内存永不释放
双向关系必须有一个方向用 weak_ptr：父子节点、观察者列表、缓存回指。用之前必须 lock() 检查。
6
erase 之后继续用旧迭代器
vector 的 erase 会让插入点之后的迭代器全部失效。用 it = v.erase(it) 的写法，或 C++20 的 erase_if。
7
把 string_view 存成成员变量或作为返回值
它不拥有内存，源字符串一销毁就悬空，且没有任何警告。string_view 只该出现在函数参数位置。
8
单参数构造函数没加 explicit
int 会静默转换成你的类型，重载决议出现意外匹配。所有单参数构造函数默认加 explicit。
9
有符号整数溢出，还指望它回绕
有符号溢出是 UB，-O2 下编译器假设它不发生，可能把 if (x + 1 > x) 优化成恒真。需要回绕就用无符号，或用 __builtin_add_overflow 显式检查。
10
在头文件里定义非 inline 的全局变量
每个包含它的编译单元都生成一份定义，链接报 multiple definition；用 static 规避又变成每个 TU 各一份，状态不共享。C++17 起用 inline 变量。
自测

六道题

1. std::move(x) 实际做了什么？
正确答案：它只是一个 static_cast<T&&>。真正的移动发生在随后调用的移动构造/移动赋值函数体里。所以 std::move 一个 const 对象，得到的仍然是拷贝。
2. 自定义类型写了移动构造但没标 noexcept，把对象放进 vector 会怎样？
正确答案：退化成拷贝。vector 扩容要保证强异常安全，移动若可能抛异常就无法回滚，所以宁可拷贝。这是"漏写 noexcept 导致性能差一个数量级"的经典案例。
3. sizeof(std::unique_ptr<T>) 在默认 deleter 下通常是多少？
正确答案：8 字节（64 位平台）。unique_ptr 用空基类优化（EBO）把无状态 deleter 塞进不占空间的基类。shared_ptr 才是 16 字节：对象指针 + 控制块指针。
4. 下面哪种情况会导致对象切片？
正确答案：按值传参。形参是 Base 对象，只能用 Base 的拷贝构造初始化，Derived 的成员和 vtable 全部丢失。引用和指针不会切片。
5. 关于 shared_ptr 的线程安全，哪个说法正确？
正确答案：引用计数原子，对象不原子。多线程各持副本读同一对象是安全的；但通过指针修改对象、或并发 reset 同一个实例，都是数据竞争。
6. 为什么遍历 std::vector<int> 常比 std::list<int> 快十倍以上？
正确答案：缓存局部性。两者复杂度都是 O(n)，但一个 cache line 能装 16 个 int，list 每个节点都要追一次指针。一次主存访问约 200 周期，这个差距远大于算法复杂度带来的差异。
