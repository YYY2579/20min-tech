准备一个能观察运行时的小程序

# 一个能练手的程序：main.go
package main

import (
    "fmt"
    "runtime"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    for i := 0; i < 100000; i++ {
        wg.Add(1)
        go func() { defer wg.Done() }()
    }
    wg.Wait()
    fmt.Println("goroutines:", runtime.NumGoroutine())
}

GODEBUG=gctrace=1 go run main.go

先记住三个默认值：goroutine 初始栈 2KB；GOMAXPROCS 默认等于 CPU 核数；GOGC 默认 100，意思是堆比上次 GC 后的存活量翻倍就再触发一次。
模块 1

goroutine 与 GMP：为什么能开一百万个

"goroutine 很轻"这句话没解释任何东西。真正要回答的是：它轻在哪、调度发生在哪一层、代价什么时候会回来。

三个角色

角色是什么关键点
Ggoroutine：栈、指令指针、状态初始栈 2KB，可增长；由 runtime 创建和销毁，不绑内核线程
Mmachine：真正跑代码的 OS 线程受内核调度；阻塞的系统调用会占住一个 M
Pprocessor：调度上下文数量 = GOMAXPROCS（默认 CPU 核数），持有本地运行队列 runq（256 个）
# 一个 P 绑定一个 M 才能执行 G；P 是"许可证"，不是线程

        ┌─────────── 全局队列 sched.runq ───────────┐
        └───────────────────┬───────────────────────┘
                            │ 本地队列空时来取
     ┌──────────┐      ┌────▼─────┐      ┌──────────┐
     │    M0    │◄────►│    P0    │      │   runq   │ 256
     └──────────┘      └────┬─────┘      └──────────┘
                            │ 偷一半
     ┌──────────┐      ┌────▼─────┐
     │    M1    │◄────►│    P1    │  ← work stealing
     └──────────┘      └──────────┘

调度发生的四个时机

  • 主动让出：go 语句、channel 阻塞、runtime.Gosched()、time.Sleep。
  • 本地队列空：先从全局队列取（每 61 次调度检查一次全局队列，防止全局队列饿死），再随机挑一个 P 偷它一半的 G。
  • 阻塞系统调用：M 进入 syscall 时会把 P handoff 给其他 M，让别的 goroutine 继续跑。这是 Go 能"一个线程阻塞不影响全局"的关键。
  • 异步抢占：Go 1.14 之前只能在函数调用检查点抢占，一个死循环可以饿死整个 P；1.14 起 sysmon 发信号（SIGURG）强制抢占。

栈是怎么长的

# 每个函数入口都有一段栈检查（编译器插入）
if sp < g.stackguard0 { runtime.morestack() }

# morestack：分配一块 2 倍大的新栈，把旧栈内容整体复制过去，
# 再修正所有指向旧栈的指针 —— 所以 Go 必须精确知道栈上哪些字是指针
# 64 位平台单 goroutine 栈上限默认 1GB

# 对比 pthread 默认 8MB 栈：100 万线程光栈就要 8TB 虚拟地址
"能开百万个"不等于"该开百万个"。2KB × 100 万 = 2GB，加上每个 G 的结构体和调度开销，真实占用更高。更常见的错误是每个请求开一个 goroutine 却不管并发上限：下游一慢，goroutine 堆积，内存和调度开销一起爆炸。该用带缓冲的 channel 或 golang.org/x/sync/semaphore 做并发限流。
容器里的坑：较早的 Go 版本 GOMAXPROCS 只读 CPU 核数，不感知 cgroup 的 CPU quota。一个限制 2 核的容器跑在 64 核宿主机上，会开出 64 个 P，线程数暴涨、调度开销变大。要么显式设 GOMAXPROCS 环境变量，要么用 uber-go/automaxprocs 这类库自动对齐。
模块 2

channel：同步、队列与关闭的三个坑

底层就是一个带锁的环形缓冲

# runtime.hchan 的关键字段
type hchan struct {
    qcount, dataqsiz uint   # len(ch)、cap(ch)
    buf              unsafe.Pointer  # 环形数组
    sendq, recvq     waitq  # 阻塞在这条 channel 上的 sudog 链表
}
类型语义什么时候阻塞
无缓冲同步交接：发送方直接把数据拷到接收方的栈上，双方必须同时就绪没有接收方就绪时，发送方一直等
有缓冲队列：先写进环形数组，接收方从另一头取缓冲满时发送阻塞；缓冲空时接收阻塞
# 无缓冲：这两行的顺序决定了会不会死锁
ch := make(chan int)
go func() { ch <- 1 }()   # 必须有人同时在收
fmt.Println(<-ch)

# 同一 goroutine 里先发后收，无缓冲必然死锁：
# ch <- 1        ← 永远等不到接收方
# <-ch
# fatal error: all goroutines are asleep - deadlock!

# 有缓冲：只要不超过容量就不会阻塞
buf := make(chan int, 3)
buf <- 1; buf <- 2; buf <- 3
# buf <- 4        ← 第 4 个才会阻塞
fmt.Println(len(buf), cap(buf))   # 3 3

select：多路复用

# 多个 case 同时就绪时，runtime 会伪随机选一个（防止固定顺序饿死后面的）
select {
case v := <-ch1:  fmt.Println("ch1", v)
case ch2 <- x:     fmt.Println("sent")
case <-time.After(time.Second): fmt.Println("timeout")
default:            fmt.Println("no one ready")   # 非阻塞分支
}

# nil channel 上的收发永远阻塞 —— 在 select 里等于"永久禁用这个分支"
var never chan int
select {
case <-never:        # 永远不会被选中
case <-done: return
}
用 nil channel 做动态开关是很常用的技巧：想让某个分支暂时失效，就把对应的 channel 变量置 nil，而不是写一堆 if。

关闭 channel 的三个坑

操作结果
向已关闭的 channel 发送panic: send on closed channel
重复关闭panic: close of closed channel
关闭 nil channelpanic: close of nil channel
从已关闭的 channel 接收立即返回零值，第二个返回值 ok 为 false；缓冲里的数据会先被读完
# 正确的约定：只有发送方关闭；有多个发送方时，谁都不要关
for v := range ch { ... }   # channel 关闭且缓冲耗尽后自动退出

# 多个发送方时，用额外的信号 channel 或 sync.Once
var once sync.Once
closeCh := func() { once.Do(func() { close(done) }) }

# 接收方判断"是零值还是关闭"
v, ok := <-ch
if !ok { # channel 已关闭且没有剩余数据 }
最常见的 goroutine 泄漏：向一个永远没人接收的 channel 发送。这个 goroutine 会永久阻塞在 sendq 上，栈和它引用的所有对象都无法回收。pprof 的 goroutine profile 里会看到成百上千个停在 chan send 的栈。凡是可能长期阻塞的 goroutine，都要给它一条退出路径（done channel 或 context）。
模块 3

interface：nil 不等于 nil

这是 Go 里最容易写出"看起来对、跑起来错"的地方。根源是：接口变量是两个字，不是一个字。

# 空接口 eface：两个字
type eface struct {
    _type *_type          # 动态类型信息
    data  unsafe.Pointer  # 指向真实数据
}

# 非空接口 iface：也是两个字
type iface struct {
    tab  *itab            # 类型 + 方法表（做动态调用的跳转表）
    data unsafe.Pointer
}
经典陷阱：把 nil 指针赋给接口，接口就不再是 nil。 
type MyErr struct{ Msg string }
func (e *MyErr) Error() string { return e.Msg }

func bad() error {
    var p *MyErr = nil
    return p            # ← 返回的 error 不是 nil！
}

fmt.Println(bad() == nil)   # false
# 因为 iface 里 tab 指向 *MyErr 的类型信息（非 nil），只有 data 是 nil

# 调用 bad().Error() 会直接 panic：nil pointer dereference
# 这就是"错误明明返回了 nil，上层却一直进错误分支"的元凶

# 正确写法：显式返回 nil
func good() error {
    var p *MyErr
    if p == nil { return nil }
    return p
}
判断方式结果说明
e == nil只看 tab 和 data 是否都为空持有 nil 指针时返回 false
e.(*MyErr) == nil取出 data 再判空能识别，但类型写死了
reflect.ValueOf(e).IsNil()反射判断底层值可行但慢，只适合兜底

类型断言必须用 , ok

# 不带 ok 的断言，失败直接 panic
n := v.(int)          # panic: interface conversion: interface {} is string, not int

# 带 ok 的断言，失败时 n 是零值
n, ok := v.(int)
if !ok { # 类型不匹配，走兜底逻辑 }

# 多类型分支用 type switch
switch x := v.(type) {
case int:    fmt.Println("int", x)
case string: fmt.Println("string", x)
case nil:    fmt.Println("nil interface")
default:      fmt.Println("other")
}

方法集：值接收者和指针接收者不一样

type T struct{}
func (t T)  Value()  {}
func (t *T) Pointer() {}

var _ interface{ Value() }   = T{}    # ✓
var _ interface{ Pointer() } = T{}    # ✗ 编译错误：T 没有 Pointer 方法
var _ interface{ Pointer() } = &T{}   # ✓

# 规则：*T 的方法集包含 T 和 *T 的全部方法；T 只包含值接收者的方法
# 所以"结构体实现了接口吗"这个问题，必须问清楚是 T 还是 *T
接口不是越多越好。Go 的惯例是"小接口"：io.Reader 只有一个方法，io.Writer 只有一个，组合起来却几乎能描述所有 IO。接口应该由使用方定义，而不是实现方定义 —— 这样实现方不必为了满足某个大接口而写一堆空方法。
模块 4

内存与 GC：三色标记、混合写屏障、GOGC

三色标记在并发下会漏标

# 白：未访问（待回收）  灰：已访问但子对象未扫描  黑：已扫描完
# 不变式：黑色对象不能指向白色对象（强三色不变式）

# 并发标记时，用户代码随时在改指针，漏标只有一种组合：
#   ① 一个黑色对象新增了指向白色对象的引用
#   ② 同时，所有能到达该白色对象的灰色对象都删掉了这条路径
# 结果：白色对象被误判为垃圾
写屏障时机解决的问题
插入屏障（Dijkstra）写入新指针时，把新指向的对象置灰堵住条件 ①
删除屏障（Yuasa）删除指针时，把被删除的旧对象置灰堵住条件 ②
混合写屏障（Go 1.8+）两者结合：写入时把新对象置灰，删除时把旧对象置灰两者都堵，且栈不需要重新扫描
混合屏障为什么能把 STW 压到极低：它规定 GC 开始时所有栈上的对象都视为黑色，扫描过的栈也保持黑色，于是栈永远不需要在标记结束时重新扫描。STW 只剩两个瞬间：开启写屏障（mark setup）和关闭写屏障（mark termination），Go 1.8 之后通常在 100 微秒以内，且与堆大小基本无关。

GOGC 与 GOMEMLIMIT

# GOGC=100（默认）：下次 GC 的目标堆 = 本次 GC 后的存活堆 × 2
# 存活 500MB → 堆涨到 1GB 时触发下一次 GC
# GOGC=50 更激进（内存小、CPU 多花）；GOGC=200 更懒（内存大、GC 少）
# GOGC=off 关闭自动 GC，只靠 runtime.GC() 手动触发 —— 几乎不该用

# GOMEMLIMIT（Go 1.19+）：软限制，单位可用 MiB/GiB
GOMEMLIMIT=4GiB ./server

# 它是"软"的：当堆已经无法再压缩时，GC 会拼命跑但也可能突破上限
# 典型用法：GOGC 保留默认，另加 GOMEMLIMIT 兜底，防止突发流量把内存打爆
# 只设 GOMEMLIMIT 不设 GOGC，会让 GC 在接近上限时变得非常频繁（CPU 飙升）
GC 触发条件说明
堆增长达阈值最常见。阈值由 GOGC 和上次存活量算出
两分钟强制一次forcegcperiod，防止长期不分配的程序永远不回收
手动 runtime.GC()会完整跑一轮，通常只在测试或内存敏感的时刻用

对象分配走哪条路

# 小对象（≤32KB）走三级缓存，避免每次都锁全局堆
P.mcache  ──►  mcentral（按 size class 分类）  ──►  mheap（页管理）
   │                    │                            │
每个 P 私有         全局，需要加锁              向 OS 要内存（arena）

# 小于 16 字节且不含指针的对象走 tiny allocator，多个对象合并到一块内存
# 大对象（>32KB）直接走 mheap，按页分配
# GC 是非移动式的（不压缩），所以指针不会变，但堆可能碎片化
GC 回收了内存，不代表操作系统看到内存下降。Go 的 scavenger 会慢慢把空闲 span 归还给 OS，但策略保守。容器里看 RSS 一直很高，先确认是真的泄漏（看 heap profile 的 inuse），还是只是没归还。可以用 debug.FreeOSMemory() 强制归还，但不要放进热路径。
模块 5

错误处理：为什么 errors.Is 比字符串匹配好

# error 就是一个接口，没有异常、没有栈展开
type error interface { Error() string }

# 惯例：error 放最后一个返回值；if err != nil 立刻处理；错误串小写、不加标点
func Load(id string) (*User, error) {
    u, err := db.Get(id)
    if err != nil {
        return nil, fmt.Errorf("load user %s: %w", id, err)   # %w 建立包装链
    }
    return u, nil
}
写法能否穿透包装能否区分类型问题
err.Error() == "not found"否否改一个字就失效；包装后串变了
strings.Contains(err.Error(), "not found")碰巧可以否会把"not found in cache"这类无关错误也算进去
errors.Is(err, ErrNotFound)是，逐层 Unwrap按哨兵值—
errors.As(err, &target)是按具体类型target 必须是指针
# 哨兵错误：包级变量，供 errors.Is 比对
var ErrNotFound = errors.New("not found")

if errors.Is(err, ErrNotFound) { # 能穿透 %w 包装的多层错误 }

# 自定义类型：需要携带字段时用
type ValidationError struct { Field string }
func (e *ValidationError) Error() string { return "invalid: " + e.Field }

var ve *ValidationError
if errors.As(err, &ve) { fmt.Println(ve.Field) }   # 取出具体类型再读字段

# 自己实现包装：实现 Unwrap() error，errors.Is/As 就能继续往下找
func (e *MyError) Unwrap() error { return e.Inner }
%w 和 %v 的区别只有一点：%w 会把原错误存进新错误的 Unwrap() 链，%v 只是把字符串拼进去。需要上层用 errors.Is/As 判断时用 %w；只是记录日志、不打算程序化判断时用 %v（避免无意中暴露内部错误类型）。

panic 的使用边界

场景用 panic 吗
程序启动时配置缺失、端口被占可以。启动阶段就该崩，让编排系统重启
不可能发生的不变量被破坏可以。这是 bug 的信号，越早暴露越好
用户输入非法、下游返回 404不可以。这是正常业务分支，用 error
# recover 只在 defer 里生效，且必须是 defer 直接调用 f()
defer func() {
    if r := recover(); r != nil {
        log.Printf("panic: %v\n%s", r, debug.Stack())
    }
}()

# 注意：goroutine 里的 panic 无法被外层 recover 捕获
go func() {
    defer func() { recover() }()   # 只能在自己的 goroutine 里兜
    panic("boom")
}()
# 如果没兜住，整个进程退出 —— 不是只死这一个 goroutine
最容易出事的地方：HTTP handler 里起了 goroutine 却没 recover。一个后台 goroutine panic，整个服务进程直接退出，而日志里只有一行 panic 栈。凡是 go func(){...}() 里跑不受控代码，都应该包一层 recover。
模块 6

并发安全：Mutex、WaitGroup、context 与 race detector

四个同步原语的边界

原语关键规则常见误用
sync.Mutex零值可用；不可重入；不可复制结构体按值传参时把锁复制了一份，等于没锁。go vet 的 copylocks 能查
sync.RWMutex读多写少；写锁会阻塞后续读（防写饥饿）；读锁不能升级为写锁在持有读锁时再去拿写锁 → 永久死锁
sync.WaitGroupAdd 必须在 Wait 之前完成在 goroutine 里 Add，可能 Wait 已经返回；计数器减到负数会 panic
sync.OnceDo 保证只执行一次，即使 f panic 也算执行过把可恢复的失败放进 Once，之后再也重试不了
# 不可重入的后果：同一个 goroutine 重复 Lock 会自己把自己锁死
func (s *Svc) A() { s.mu.Lock(); defer s.mu.Unlock(); s.B() }
func (s *Svc) B() { s.mu.Lock(); defer s.mu.Unlock() }   # ← 死锁

# 正确做法：拆出不加锁的内部方法
func (s *Svc) A() { s.mu.Lock(); defer s.mu.Unlock(); s.bLocked() }

context：取消是协作式的

# 四个构造函数，覆盖绝大多数场景
ctx, cancel := context.WithCancel(parent)          defer cancel()
ctx, cancel := context.WithTimeout(parent, 3*time.Second)
ctx, cancel := context.WithDeadline(parent, t)
ctx := context.WithValue(parent, key, val)          # 只放请求域数据

# 取消不会杀死 goroutine，它只是关掉一个 channel。你必须主动检查
select {
case <-ctx.Done(): return ctx.Err()   # Canceled 或 DeadlineExceeded
case v := <-work:  handle(v)
}

race detector 怎么用

# 编译时插桩，运行时检测 happens-before 冲突
go test -race ./...
go run -race main.go
go build -race -o app ./cmd/app

# 典型输出
WARNING: DATA RACE
Write at 0x00c0000b4010 by goroutine 7:
  main.main.func1()
Previous read at 0x00c0000b4010 by main goroutine:
  main.main()
race detector 只能发现"实际执行到"的竞态。它靠向量时钟记录每个内存访问的 happens-before 关系，没被调度到的交错就检测不到。所以 -race 通过不等于没竞态，只是这次没撞上。开销大约是内存 5~10 倍、速度 2~20 倍，只在测试和预发开，不要上生产。
比加锁更好的方案往往是"不要共享"。每个 goroutine 处理自己的数据，用 channel 传所有权，而不是用 Mutex 保护一块共享内存。Go 的谚语是"通过通信来共享内存，而不是通过共享内存来通信" —— 但这句话有边界：高频、细粒度的小状态用 Mutex 更快，channel 的锁和调度开销不适合做计数器。
模块 7

六个语义陷阱：编译器不会提醒

① 循环变量捕获（Go 1.22 之前）

# Go 1.21 及之前：整个循环只有一个 i，所有闭包共享它
for i := 0; i < 3; i++ {
    go func() { fmt.Print(i) }()   # 大概率输出 333，而不是 012
}
# 循环结束时 i 已经是 3，goroutine 才开始跑

# 1.22 起每次迭代都创建新变量，上面的代码输出 012
# 老代码的两种修法：
for i := 0; i < 3; i++ {
    i := i                          # 影子变量
    go func() { fmt.Print(i) }()
}
for i := 0; i < 3; i++ {
    go func(n int) { fmt.Print(n) }(i)   # 传参
}
升级到 1.22 要小心：新语义会让"依赖共享变量"的老代码行为改变。如果项目里有 for 循环里起 goroutine 又在外部改这个变量的写法，升级后可能从"全都读到最后一个值"变成"各读各的"。go.mod 里的 go 版本决定了用哪套语义，不要只改版本号不跑测试。

② defer 的参数在注册时就求值

func f() {
    x := 1
    defer fmt.Println(x)   # 参数此刻就算好了，输出 1
    x = 2
}

# 想读最终值，必须用闭包（闭包捕获的是变量本身）
defer func() { fmt.Println(x) }()   # 输出 2

# 同样的坑：defer 一个方法值时，接收者也是立刻求值的
defer resp.Body.Close()   # resp 此刻的值被保存

③ defer 在循环里会堆积

# 错误：一万次循环注册一万个 defer，全部堆到函数返回才执行
for _, p := range paths {
    f, _ := os.Open(p)
    defer f.Close()        # ← 文件描述符可能先被耗尽
}

# 正确：包一层函数，让 defer 在每轮结束时执行
for _, p := range paths {
    func() {
        f, err := os.Open(p)
        if err != nil { return }
        defer f.Close()
        # 处理 f
    }()
}

④ 切片会共享底层数组

a := []int{1, 2, 3, 4, 5}
b := a[1:3]              # b = [2 3]，与 a 共享同一块数组
b[0] = 99
fmt.Println(a)           # [1 99 3 4 5] —— a 被改了

# append 更隐蔽：容量够就原地写，容量不够才新分配
c := a[:2]               # len=2 cap=5
c = append(c, 100)       # 容量够 → 直接写进 a[2]
fmt.Println(a)           # a[2] 变成了 100

# 要真正独立，必须复制
d := append([]int(nil), a[1:3]...)
e := slices.Clone(a[1:3])   # Go 1.21+
这个坑在生产上的典型形态：从一个大的 []byte 里切出一小段传给下游，整块大数组都不会被 GC 回收。10MB 的响应体里切出 100 字节缓存起来，等于把 10MB 钉死在内存里。长期持有切片片段时，一定要 Clone。

⑤ range 给的是副本

type Item struct{ N int }
items := []Item{{1}, {2}}

for _, it := range items {
    it.N = 100           # 改的是副本，items 不变
}
for i := range items {
    items[i].N = 100     # 用索引才能改原值
}

⑥ nil map 可读不可写

var m map[string]int
fmt.Println(m["x"])   # 0，读 nil map 合法
m["x"] = 1            # panic: assignment to entry in nil map

# 必须 make。声明时直接给字面量也可以
m = make(map[string]int)

# 另一个高频问题：map 的 value 不可寻址
type C struct{ N int }
cm := map[string]C{"a": {1}}
cm["a"].N = 2          # ✗ 编译错误：cannot assign to struct field
v := cm["a"]; v.N = 2; cm["a"] = v   # ✓ 取出、改、放回
map 并发读写是 fatal error，不是 panic，recover 抓不住。运行时会直接打印 fatal error: concurrent map read and map write 并退出进程。注意它只在恰好撞上时触发，测试环境可能永远复现不了。要么加锁，要么用 sync.Map（只适合读多写少、key 集合稳定的场景）。
模块 8

性能：逃逸分析、pprof、sync.Pool

先看逃逸分析，再谈优化

# -m 打印逃逸决策，-m -m 更啰嗦但更详细
go build -gcflags="-m" ./...
go build -gcflags="-m -m" ./...

# 典型输出
./main.go:12:6: moved to heap: buf        # 局部变量被搬到堆上
./main.go:15:10: x escapes to heap        # x 逃逸
./main.go:20:9: leaking param: p          # 参数被存到了外部

# 常见的四种逃逸原因
# 1. 返回局部变量的指针
# 2. 把值放进 interface{}（装箱）
# 3. 被闭包捕获且闭包逃逸
# 4. 大小在编译期不确定的分配（如 make([]T, n) 里 n 是变量）
逃逸不等于慢。Go 的分配器很快（mcache 是每 P 私有的，多数分配不需要锁），一次堆分配大约几十纳秒。真正贵的是分配带来的 GC 压力：分配越多，GC 越频繁。所以优化的目标是"减少热路径上的分配次数"，而不是"消灭所有逃逸"。

pprof：三件套加两个补充

类型回答什么问题入口
CPU profile时间花在哪些函数上/debug/pprof/profile?seconds=30
heap profile内存被谁占着（inuse）／谁分配得最多（alloc）/debug/pprof/heap
goroutine现在有多少 goroutine、都卡在哪/debug/pprof/goroutine?debug=1
block谁在阻塞（channel、锁）/debug/pprof/block
mutex锁竞争有多严重/debug/pprof/mutex
# 1. 引入即可注册 handler（只监听本地，别暴露到公网）
import _ "net/http/pprof"
go func() { http.ListenAndServe("127.0.0.1:6060", nil) }()

# 2. 采 30 秒 CPU
go tool pprof http://127.0.0.1:6060/debug/pprof/profile?seconds=30

# 3. 看堆：默认 inuse_space（当前占用），-alloc_space 看累计分配
go tool pprof -alloc_space http://127.0.0.1:6060/debug/pprof/heap

# 4. 浏览器里看火焰图，比命令行直观
go tool pprof -http=:8080 http://127.0.0.1:6060/debug/pprof/profile?seconds=30

# 5. block / mutex 默认是采样的，需要先开采样率
runtime.SetBlockProfileRate(1)          # 1 = 全采样，生产建议调大
runtime.SetMutexProfileFraction(1)

# 6. 基准测试直接产出 profile
go test -bench . -benchmem -cpuprofile cpu.out -memprofile mem.out
heap profile 默认每 512KB 采样一次（runtime.MemProfileRate），所以小对象的数字是估算值，不要拿它当精确的内存账单。要看精确值用 runtime.ReadMemStats 或 GODEBUG=gctrace=1 的堆大小。

sync.Pool：只适合"临时对象"

# 典型用法：复用 buffer，减少分配
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

b := bufPool.Get().(*bytes.Buffer)
b.Reset()                    # ← 必须重置，池里的对象是脏的
defer bufPool.Put(b)

# 注意：Pool 里的对象随时可能被 GC 清掉，不能假设 Put 进去就一定还在
# 也不能用它做连接池 —— 数量不可控、没有健康检查、不保证归还
优化的顺序永远是：先测量，再改，再测量。没有 profile 的优化都是猜。而且 Go 的编译器每年都在变，"某个写法一定更快"的结论经常过期 —— 用 go test -bench 在自己的版本上验证。
常见坑

八个把服务拖垮的写法

1
向一个没人接收的 channel 发送
goroutine 永久阻塞在 sendq 上，栈和它引用的对象都回收不了。pprof 的 goroutine 视图里会看到成百上千个停在 chan send 的栈。
2
同一个 goroutine 里对无缓冲 channel 先发后收
发送会一直等接收方，而接收方就是自己，永远等不到。运行时直接报 all goroutines are asleep - deadlock。
3
把 wg.Add(1) 写进 goroutine 里
Wait 可能在这行执行之前就返回了，主流程提前往下走。Add 必须在启动 goroutine 之前、在同一个 goroutine 里调用。
4
context 一路传下去，但从没检查 ctx.Done()
取消是协作式的，不检查就等于没传。请求已经超时返回了，后台还在傻算，连接和内存都占着。
5
后台 goroutine panic 没有 recover
goroutine 里的 panic 无法被外层 recover 捕获，会直接终止整个进程。
6
在循环里 defer f.Close()
所有 defer 都堆到函数返回才执行，循环一万次就同时开着一万个文件描述符，很容易触发 too many open files。
7
长期持有一个大切片的片段
切片共享底层数组，切出 100 字节缓存起来，等于把整块 10MB 数组钉在内存里。跨请求持有要 slices.Clone。
8
在 1.22 之前的循环里直接捕获循环变量
所有闭包共享同一个变量，goroutine 真正跑起来时循环早已结束，读到的全是最后一个值。
自测

六道题

1. GOMAXPROCS 控制的是什么？
正确答案：P 的数量。P 是调度上下文，一个 P 绑定一个 M 才能跑 G。goroutine 数量不受它限制，OS 线程数也可以超过它。
2. 在同一个 goroutine 里执行 ch := make(chan int); ch <- 1; <-ch，会怎样？
正确答案：死锁。无缓冲 channel 要求收发同时就绪，而唯一的 goroutine 卡在发送上，没人执行接收。运行时会检测到全部阻塞并直接报错。
3. var p *MyErr = nil; var e error = p，此时 e == nil 吗？
正确答案：不是 nil。接口是两个字：类型信息 + 数据指针。p 为 nil 只让 data 为空，tab 仍指向 *MyErr 的类型。
4. 混合写屏障主要解决了什么问题？
正确答案：不漏标且不用重扫栈。它结合插入与删除屏障，并规定栈上对象初始为黑色，STW 只剩开启/关闭写屏障两个瞬间，通常一百微秒以内。
5. 为什么推荐 errors.Is 而不是比较错误字符串？
正确答案：能穿透包装且不依赖文案。用 %w 包装后字符串会一层层叠加，字符串比较立刻失效；errors.Is 会逐层 Unwrap 找到原始哨兵值。
6. b := a[1:3] 之后修改 b[0]，a 会变吗？
正确答案：会变。切片只是"指针 + 长度 + 容量"的描述符，切片操作不复制元素。要独立就 slices.Clone。
