二十分钟学透 TypeScript

TS 的价值不在于"多了一套语法"，而在于把一类错误从运行期挪到编辑期。这篇讲类型系统怎么推理、什么时候它在骗你、以及为什么很多团队的 TS 最终退化成了"带注解的 any"。

建议开一个空目录，npm i -D typescript 后跟着 tsc 试
开始前

只装编译器就够开始了

TS 不需要框架、不需要构建工具。装一个 typescript 包，就有 tsc 可以用了。所有类型错误都是它报的，跟运行时无关。

# 初始化（生成 tsconfig.json）
npm i -D typescript
npx tsc --init

# 只做类型检查，不产出 JS —— CI 里最常用的一条
npx tsc --noEmit

# 直接运行 .ts（Node 22+ 可用 --experimental-strip-types，或装 tsx）
npx tsx app.ts

# 看编译器到底在干什么（性能排查用）
npx tsc --noEmit --extendedDiagnostics
npx tsc --noEmit --generateTrace trace
先建立最重要的认知：类型在运行时不存在。tsc 做的事是"擦除"——把类型注解删掉，产出的 JS 里没有任何类型信息。所以不能用类型做运行期判断：if (typeof x === 'MyInterface') 这种写法根本编译不过，因为接口没有运行时表示。
阅读姿势：本文不教 interface 怎么写。每个模块都在回答"编译器在这一步推了什么、它凭什么相信你"。理解了推导过程，报错就不再是天书。
模块 1

类型系统到底买到了什么

"少写 bug"是结果，不是机制。拆开看，类型系统提供三样具体的东西，每一样都可以单独衡量。

收益具体机制没有它会怎样
编译期发现错误属性名拼错、参数少传、null 未判断，在编辑器里就红上线后 Cannot read properties of undefined
类型即文档函数签名本身就是最准确的接口说明，且不会过期注释写着"返回数组"，实际返回 null
重构的安全网改一个字段名，所有引用点立刻报错全局搜索替换，漏掉字符串拼接里的那种
编辑器智能提示自动补全、跳转定义、内联文档靠记忆和翻源码
// 一个真实的收益量化：重命名字段
interface User { id: string; userName: string; }

function greet(u: User) { return 'hi ' + u.userName; }

// 把 userName 改成 username：
// 编辑器立刻在所有引用点标红，包括：
//   - greet 里的 u.userName
//   - 构造 User 对象的地方
//   - 解构赋值 const { userName } = u
// 而字符串 'userName' 不会被改 —— 这既是限制也是保护
但类型系统只能证明"类型正确"，不能证明"逻辑正确"。
function divide(a: number, b: number): number { return a / b; } 类型完美，b 为 0 时照样返回 Infinity。
function getUser(id: string): User 类型完美，用户不存在时返回 null 就崩了——除非你把返回类型写成 User | null。类型的表达力上限，取决于你写签名的诚实程度。

结构化类型：TS 是"鸭子类型"的静态版

interface Point { x: number; y: number; }

function len(p: Point) { return Math.hypot(p.x, p.y); }

const p3 = { x: 3, y: 4, z: 5 };
len(p3);   // ✓ 合法！只要"形状"满足就行，多的字段不影响

class Vec { constructor(public x: number, public y: number) {} }
len(new Vec(3, 4));   // ✓ 也合法，跟 Point 没有任何继承关系

这叫结构化类型（structural typing），跟 Java/C# 的"名义类型"相反。好处是极其灵活，坏处是两个语义完全不同的类型，只要字段一样就能互相赋值——这是 TS 里最容易被忽视的一类 bug，后面模块 8 会展开。

模块 2

类型推断：什么时候该写，什么时候别写

TS 的推断能力很强，绝大多数局部变量根本不需要标注。写多了是噪音，写少了会退化成 any。判断标准只有一条：这个类型信息对"读代码的人"和"检查代码的编译器"是否必要。

推断从哪里来

来源例子
初始值let n = 0 → number；let s = 'a' → string
函数返回值function f() { return 1 } → number
上下文（contextual typing）[1,2].map(x => x + 1) 里 x 自动是 number
控制流分析if (typeof x === 'string') 之后 x 被收窄
字面量收窄const c = 'on' → 类型是 'on'，不是 string
// 这些标注是纯噪音
const n: number = 0;
const s: string = 'hello';
const arr: number[] = [1, 2, 3];

// 这些标注有实际作用
const status: 'idle' | 'loading' | 'done' = 'idle';  // 限定取值范围
const cache: Map<string, User> = new Map();          // 空容器推不出元素类型
let v: string | number = 0;                         // 声明"以后会变宽"
const handlers: Record<string, () => void> = {};          // 空对象需要形状
三条实用规则：
① 局部变量不标——初始值已经说明了类型；
② 函数参数必须标——不标就是隐式 any（strict 下直接报错）；
③ 公共 API 的返回值建议标——这是"契约"而不是"实现细节"，改了实现也不会意外改变对外类型。

返回类型要不要写

// 不写：返回类型由实现推导，改实现会悄悄改契约
function getUser(id: string) {
  return db.find(id);          // 推出来是 User | undefined
}
// 后来有人加了一行 if (!user) return null; → 返回类型变成 User | null | undefined
// 所有调用方的类型都变了，但没有任何地方报错

// 写：契约先行，实现必须满足它
function getUser(id: string): User | undefined {
  return db.find(id);          // 如果返回 null，这里直接编译报错
}

// 导出的函数、库的公开 API、递归函数（否则可能推成 any）—— 都该写
递归函数不写返回类型会出事。TS 需要先知道返回类型才能检查函数体，而递归时它只能先推成 any，再回头发现推错了。显式标注是唯一的解法。
模块 3

泛型：类型的参数化

泛型的本质是"让类型之间的关系可以被表达"。不是为了少写几个 any，而是为了说明"输入是什么类型，输出就是什么类型"——这个约束是 any 永远表达不了的。

// 没有泛型：要么 any（丢失信息），要么重载一大堆
function firstAny(arr: any[]): any { return arr[0]; }
const a = firstAny([1, 2]);   // a 是 any，之后随便用都不报错

// 有泛型：T 把输入和输出绑在一起
function first<T>(arr: T[]): T | undefined { return arr[0]; }
const b = first([1, 2]);       // b 是 number | undefined
const c = first(['x']);        // c 是 string | undefined

约束：extends 限定能传什么

// 不加约束，函数体里不能访问任何属性
function longest<T>(a: T, b: T) {
  // return a.length > b.length ? a : b;  // ✗ T 上可能没有 length
}

// 加约束：T 必须"至少长这样"
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}
longest('abc', 'de');        // ✓ string 有 length
longest([1,2,3], [4]);          // ✓ 数组有 length
// longest(1, 2);               // ✗ number 没有 length

// keyof 约束：K 必须是 T 的键
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}
const u = { name: 'ann', age: 3 };
const n1 = get(u, 'name');   // string（精确到属性类型）
// get(u, 'email');          // ✗ 'email' 不在 keyof User 里

默认值与推断位置

interface ApiResponse<T = unknown, E = Error> {
  data: T;
  error: E | null;
}

type A = ApiResponse;                 // T = unknown, E = Error
type B = ApiResponse<User>;           // T = User
type C = ApiResponse<User, HttpError>; // 两个都指定

// 泛型可以写在函数、接口、类、类型别名上
// 调用时通常能自动推断，推断不出来才需要显式写 <T>
const empty = new Map<string, number>();   // 空容器必须显式指定

泛型在工具类型里的应用

// 手写一个 Pick，理解它为什么需要两个类型参数
type MyPick<T, K extends keyof T> = {
  [P in K]: T[P];
};

// 手写一个 ReturnType，用到条件类型 + infer
type MyReturnType<F> = F extends (...args: any) => infer R ? R : never;

function f() { return { a: 1, b: 'x' }; }
type R = MyReturnType<typeof f>;   // { a: number; b: string }

// 条件类型 + 分发：传入联合类型时逐个处理
type ToArray<T> = T extends unknown ? T[] : never;
type X = ToArray<string | number>;   // string[] | number[]
// 注意不是 (string | number)[]，因为裸类型参数会"分发"
// 想阻止分发：[T] extends [unknown] ? ...
泛型不是越多越好。一个函数如果有 5 个类型参数、3 层条件类型，调用方基本不可能推断正确，报错也读不懂。泛型应该只出现在"类型关系必须被保留"的地方；如果只是想接受任意类型，用 unknown 更诚实。
模块 4

联合类型与收窄：TS 最实用的部分

真实世界的值经常是"几种可能之一"。联合类型让你把这个事实写进类型，而收窄（narrowing）让编译器在你排除掉某些可能后，自动把类型变精确。

type Result = string | number | null;

function fmt(r: Result) {
  // 这里 r 是 string | number | null，不能直接调 toUpperCase
  if (r === null) return '-';          // 收窄掉 null
  if (typeof r === 'string') return r.toUpperCase();  // 收窄成 string
  return r.toFixed(2);                    // 剩下的只能是 number
}

四种收窄手段

手段写法适用
typeoftypeof x === 'string'原始类型（注意 typeof null === 'object'）
in'radius' in shape区分有不同字段的对象
instanceoferr instanceof HttpErrorclass 实例（运行时真的存在）
自定义谓词function isUser(x: unknown): x is User复杂结构、接口（没有运行时表示）
断言函数function assert(x: unknown): asserts x is User校验失败直接抛错的场景
// 自定义类型谓词：返回值写成 "x is User"，编译器就信你
function isUser(x: unknown): x is User {
  return typeof x === 'object' && x !== null
    && typeof (x as User).id === 'string';
}

// 断言函数：调用后如果没抛错，类型就确定了
function assertUser(x: unknown): asserts x is User {
  if (!isUser(x)) throw new Error('not a user');
}
function handle(x: unknown) {
  assertUser(x);
  console.log(x.id);   // x 已经是 User
}
类型谓词是一句"你向编译器做的承诺"，它不会验证你的实现。
function isUser(x: unknown): x is User { return true; } 完全能编译通过，然后所有调用点都在裸奔。
谓词函数必须自己写完整的运行时校验，或者用 Zod、Valibot 这类库自动生成。手写时最容易漏的是：数组要 Array.isArray、null 要单独排除（typeof null 是 'object'）、数字要排除 NaN。

可辨识联合：把状态机写进类型

// 用一个共同的字段（discriminant）区分各个分支
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: User[] }
  | { status: 'error'; message: string };

function render(s: State) {
  switch (s.status) {
    case 'idle':    return '等待';
    case 'loading': return '加载中';
    case 'success': return s.data.length + ' 条';  // s 已被收窄，能访问 data
    case 'error':   return s.message;
  }
}

这种写法的价值：不可能出现"loading 状态下访问 data"，因为那个分支里根本没有 data 字段。相比 { loading: boolean; data?: User[]; error?: string } 这种"三个可选字段"的写法，可辨识联合把非法状态在类型层面就排除掉了。

穷尽检查（exhaustiveness check）是这套模式的杀手锏。在 switch 最后加一个 default: assertNever(s)，将来给 State 加一个新分支时，所有没处理它的地方都会编译报错。这是"新增状态不会漏改"的唯一可靠保障。
模块 5

工具类型：七个够用的

标准库内置了一批"类型函数"，它们接收类型、返回类型。不用背全部，这七个覆盖了 90% 的场景。

工具类型作用实用场景
Partial<T>所有属性变可选PATCH 接口的请求体、表单草稿
Required<T>所有属性变必填配置合并后校验完整性
Pick<T, K>只保留指定键列表接口只返回摘要字段
Omit<T, K>去掉指定键创建请求体去掉 id / createdAt
Record<K, V>构造键值映射枚举到文案的映射表
ReturnType<F>取函数返回类型复用已有函数的返回结构
Parameters<F>取函数参数元组包装函数时转发参数
interface User {
  id: string;
  name: string;
  email: string;
  createdAt: Date;
}

// 1. Partial：更新接口，只传要改的字段
function updateUser(id: string, patch: Partial<User>) { /* ... */ }
updateUser('u1', { name: 'ann' });   // ✓ 只传一个字段

// 2. Omit + Partial 组合：创建时不要 id 和时间
type CreateUserInput = Omit<User, 'id' | 'createdAt'>;
// { name: string; email: string }

// 3. Pick：列表页只要摘要
type UserSummary = Pick<User, 'id' | 'name'>;
// { id: string; name: string }

// 4. Record：枚举到展示文案
type Status = 'idle' | 'loading' | 'error';
const LABEL: Record<Status, string> = {
  idle: '等待', loading: '加载中', error: '出错',
};
// 少写一个键会报错 —— 这是 Record 相比 { [k: string]: string } 的最大价值

// 5. ReturnType：不重复声明返回结构
function parseConfig() {
  return { port: 8080, host: 'localhost' };
}
type Config = ReturnType<typeof parseConfig>;
// { port: number; host: string }

// 6. Parameters：写装饰器 / 包装函数
function withLog<F extends (...a: any) => any>(fn: F) {
  return (...args: Parameters<F>): ReturnType<F> => {
    console.log('call with', args);
    return fn(...args);
  };
}

// 7. Required：配置合并后校验
type RawConfig = Partial<{ port: number; host: string }>;
type FinalConfig = Required<RawConfig>;
Partial 是浅的。Partial<User> 只让第一层属性可选，嵌套对象里的字段仍然是必填。需要深层可选得自己写递归类型（或者用 type-fest 的 PartialDeep）——但递归类型正是后面要讲的"编译慢"元凶之一。

satisfies：既校验又不丢类型

// 用类型注解：值被"拓宽"成注解的类型，丢失字面量信息
const a: Record<Status, string> = { idle: '等待', loading: '加载中', error: '出错' };
// a.idle 的类型是 string，不是 '等待'

// 用 as const：类型精确，但完全不校验
const b = { idle: '等待', loading: '加载中' } as const;
// 少写一个键也不会报错

// 用 satisfies（TS 4.9+）：既校验形状，又保留字面量类型
const c = {
  idle: '等待', loading: '加载中', error: '出错',
} satisfies Record<Status, string>;
// c.idle 的类型是 '等待'，同时少键 / 多键都会报错
模块 6

any / unknown / never：三个"空"的差别

类型含义能做什么
any关闭类型检查，双向兼容（可以赋给任何类型，也能接收任何类型）读写任意属性、调用、当任何类型用
unknown未知类型，只能接收，不能使用赋值、typeof 判断、类型断言之后才能用
never不可能存在的值（空集）可以赋给任何类型；没有任何值能赋给它
// any：一路畅通，错误留到运行时
const a: any = JSON.parse('{}');
a.foo.bar.baz();        // 编译通过，运行时报错

// unknown：必须先证明类型
const u: unknown = JSON.parse('{}');
// u.foo;               // ✗ 'u' is of type 'unknown'
if (typeof u === 'object' && u !== null && 'foo' in u) {
  console.log((u as { foo: string }).foo);   // 收窄或断言后才能用
}
为什么该用 unknown 而不是 any：any 会沿着调用链传染——一个 any 传进函数，函数的返回值也可能变成 any，最后整个模块失去检查。unknown 是"安全的 any"：它接受一切，但在你证明它是什么之前，什么都不能做。
典型用法：函数参数接收外部数据（JSON、catch (e)、第三方回调）、泛型默认值、需要"待定类型"的占位。

never：空集的三个用途

// 1. 穷尽检查（最实用）
function assertNever(x: never): never {
  throw new Error('unhandled case: ' + JSON.stringify(x));
}

type Shape = { kind: 'circle'; r: number } | { kind: 'rect'; w: number };

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2;
    case 'rect':   return s.w * s.w;
    default: return assertNever(s);   // 加新分支时这里会报错
  }
}

// 2. 表示函数永远不返回（抛错或死循环）
function fail(msg: string): never { throw new Error(msg); }

// 3. 条件类型里过滤掉所有类型
type NonString<T> = T extends string ? never : T;
type R = NonString<string | number>;   // number（never 在联合里会被吸收）
never 是"空集"，所以它和任何类型的交叉都是 never，和任何类型的联合都会被吸收。
never | string = string；never & string = never。
这解释了一个常见困惑：为什么收窄到 never 的变量还能被赋给别的类型——因为空集是任何集合的子集。

三者关系速查

any     ⊃ 所有类型（双向兼容，逃逸舱口）
unknown ⊃ 所有类型（单向：只能进不能出）
never   ⊂ 所有类型（单向：只能出不能进）

// 赋值方向
let n: never = (() => { throw 1; })();
let s: string = n;      // ✓ never 可以赋给任何类型
let a: any = 1;
let b: string = a;     // ✓ any 可以赋给任何类型
let u: unknown = 1;
// let c: string = u;  // ✗ unknown 不能赋给具体类型
模块 7

tsconfig：每个开关关掉了什么

TS 的严格程度不是"开或关"，而是十几个独立开关。很多团队只写了 "strict": true 就以为万事大吉，实际上还有几个关键项在 strict 之外。

{
  "compilerOptions": {
    // 目标与模块
    "target": "ES2022",          // 产出的 JS 语法版本
    "module": "ESNext",          // 产出的模块格式
    "moduleResolution": "bundler", // 怎么找 node_modules
    "lib": ["ES2022", "DOM"],     // 能用哪些内置 API 的类型

    // 严格系列
    "strict": true,               // 打开下面这一组（不含后两项）
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,

    // 工程约束
    "noEmit": true,               // 只检查不产出（打包工具负责产出）
    "skipLibCheck": true,          // 跳过 .d.ts 的类型检查
    "isolatedModules": true,       // 保证每个文件能独立转译
    "esModuleInterop": true,       // 允许 import cjs 默认导出
    "forceConsistentCasingInFileNames": true
  }
}

strict 到底包含什么

开关关掉之后会怎样
strictNullChecks最重要的一项。null 和 undefined 可以赋给任何类型，等于放弃一半的类型安全
noImplicitAny推断不出类型时默默用 any，错误全部漏到运行时
strictFunctionTypes函数参数变成双变（bivariant），把不安全的赋值放进来
strictBindCallApplycall/apply/bind 的参数不再检查
strictPropertyInitializationclass 字段不初始化也不报错，运行时是 undefined
noImplicitThisthis 隐式为 any
useUnknownInCatchVariablescatch 到的变量变成 any 而不是 unknown
alwaysStrict不生成 "use strict"
strict 之外，还有两个强烈建议打开：
① noUncheckedIndexedAccess：让 arr[0] 的类型变成 T | undefined。这会带来大量改动（所有下标访问都要判空），但它反映的是事实——越界访问在 JS 里就是返回 undefined。适合新项目；老项目可以先在关键模块开。
② exactOptionalPropertyTypes：区分 { a?: string } 和 { a?: string | undefined }。不开的话，显式传 undefined 会被当成"没传"，在 PATCH 接口里会导致字段被误删。

skipLibCheck 的取舍

// 开启：跳过所有 .d.ts 的检查
"skipLibCheck": true

// 收益：编译时间大幅下降（大型项目常见从 30s 降到 8s）
// 代价：依赖包里的类型冲突、重复声明不会被发现
//       你自己的 .d.ts 里写错了也不会报

// 实践：几乎所有人都开。但要注意 ——
// 它跳过的是"声明文件之间的检查"，不是"你的代码对声明的使用"
// 所以类型不匹配的调用照样会报错
推荐的新项目配置：strict: true + noUncheckedIndexedAccess: true + noImplicitOverride: true + noFallthroughCasesInSwitch: true + skipLibCheck: true。
老项目迁移：先开 noImplicitAny，再开 strictNullChecks（这两个收益最大、改动最集中），最后补剩下的。不要一次性全开，几千个错误会让人直接放弃。
模块 8

四个让类型系统失效的坑

1. 类型断言 as 滥用

// as 是"我保证"，不是"请检查"
const el = document.getElementById('app') as HTMLDivElement;
el.innerHTML = 'x';   // 如果 id 不存在，el 是 null，运行时崩

// 更安全的写法
const el2 = document.getElementById('app');
if (!(el2 instanceof HTMLDivElement)) throw new Error('#app missing');
el2.innerHTML = 'x';   // 这里 el2 已经是 HTMLDivElement

// 双重断言是最危险的：编译器完全不检查
const n = 'abc' as unknown as number;   // 编译通过，运行时是字符串

as 只应该在两种情况下用：① 你比编译器知道得更多，且能说清为什么（比如 DOM 查询后已经手动校验过）；② 迁移过程中临时压制错误，并留下 TODO。任何 as any 都该被 code review 拦下来。

2. 结构化类型带来的意外兼容

interface UserId { value: string }
interface OrderId { value: string }

function cancelOrder(id: OrderId) { /* ... */ }
const uid: UserId = { value: 'u1' };
cancelOrder(uid);   // ✓ 编译通过！两个类型形状完全一样

// 修复：加一个"品牌"字段，让它无法被意外构造
interface UserId { readonly __brand: 'UserId'; value: string }
interface OrderId { readonly __brand: 'OrderId'; value: string }
// 这叫 branded type / nominal typing 模拟
结构化类型的另一个陷阱：空对象类型。{} 在 TS 里表示"任何非 null/undefined 的值"，所以 function f(x: {}) 能接受字符串、数字、数组——几乎等于 any。
要表示"空对象"应该用 Record<string, never>；要表示"任意对象"用 object 或 Record<string, unknown>。

3. enum 的争议

// 数字枚举：会生成运行时代码，且反向映射
enum Status { Idle, Loading, Error }
// 编译后：
// var Status;
// (function (Status) {
//   Status[Status["Idle"] = 0] = "Idle";
//   ...
// })(Status || (Status = {}));
// 体积变大，且 Status[0] === 'Idle' 这种反向映射很少用得上

// 字符串枚举：没有反向映射，但仍然生成对象
enum Color { Red = 'RED', Blue = 'BLUE' }

// 更推荐的写法：联合字面量 + as const 对象
const Status2 = { Idle: 'idle', Loading: 'loading' } as const;
type Status2 = typeof Status2[keyof typeof Status2];   // 'idle' | 'loading'
方案运行时开销评价
enum生成对象能用，但体积大、和 isolatedModules 有冲突、跨包共享麻烦
const enum0（内联）有内联问题：不同编译设置下行为不一致，isolatedModules 下直接报错
联合字面量0推荐。纯类型，无运行时痕迹，可 tree shake
as const 对象一个普通对象需要"值"的时候用（遍历、映射文案）

4. 类型体操过度，编译变慢

// 这类递归类型在大型项目里是性能杀手
type DeepPartial<T> = T extends object
  ? { [K in keyof T]?: DeepPartial<T[K]> }
  : T;

// 对一个大接口调用一次，可能展开成几百个类型
// 如果它出现在循环、泛型约束、联合类型里，开销是指数级的

// 排查手段
npx tsc --noEmit --extendedDiagnostics
// 关注 "Check time" 和 "Types" 两个数字

npx tsc --noEmit --generateTrace trace
// 用 Chrome 打开 trace/trace.json，看哪个类型最耗时
几个已知的"编译慢"写法：① 深层递归条件类型（DeepReadonly、DeepPartial）；② 对联合类型做笛卡尔积式的映射；③ 巨型字符串字面量联合（几百个值的联合，每次比较都线性扫描）；④ 在 .d.ts 里写复杂的类型体操，而它被所有文件引用。
原则：类型应该服务于"防错"，不是"炫技"。一个需要三屏注释才能看懂的类型，维护成本远高于它防止的 bug。
常见坑

十个真实事故

1
用 as any 绕过报错
它会把 any 传染给调用链下游，一个文件失守，整个模块的类型检查形同虚设。要用 unknown + 类型守卫，或老实修类型。
2
没开 strictNullChecks
null 和 undefined 可以赋给任何类型，等于放弃一半类型安全。这是 strict 里收益最大的一项，迁移时优先级最高。
3
把类型谓词写成 return true
编译器完全相信你，但运行时什么都没校验。谓词函数必须写完整校验：Array.isArray、排除 null、排除 NaN。
4
以为接口能在运行时判断
类型在编译后被擦除。typeof x === 'User'、x instanceof User 对 interface 都无效，必须手写守卫或引入 Zod 之类的运行时校验。
5
结构化类型导致 UserId 和 OrderId 互通
形状一样的两个类型可以互相赋值。用 branded type（加 readonly __brand 字段）模拟名义类型。
6
Partial 以为是深层的
Partial<T> 只作用于第一层，嵌套对象里的字段仍然必填。需要深层可选得写递归类型，注意编译开销。
7
数组下标访问不判空
默认 arr[0] 的类型是 T，实际越界返回 undefined。开 noUncheckedIndexedAccess 让编译器提醒你。
8
导出函数不写返回类型
改实现会悄悄改契约，所有调用方跟着变而没有任何报错。公共 API 的返回类型是文档，应该显式写。
9
用 enum 又开 isolatedModules
const enum 在 isolatedModules 下直接报错，普通 enum 会生成运行时对象、增加体积。优先用联合字面量。
10
写三层递归类型体操，编译从 8 秒变 60 秒
用 --extendedDiagnostics 和 --generateTrace 定位。类型应服务于防错，不是炫技；复杂类型放进独立文件并限制使用范围。
自测

六道题

1. 关于 any 和 unknown，哪个说法对？
正确答案：后者。any 会关闭检查并沿调用链传染；unknown 是"安全的 any"——什么都能赋给它，但在证明类型之前什么都不能做。
2. interface UserId { value: string } 和 OrderId { value: string }，为什么能互相赋值？
正确答案：结构化类型。这正是它和 Java/C# 名义类型的根本差异。需要区分时用 branded type，加一个 readonly __brand: 'UserId' 字段。
3. strict 里最重要、收益最大的一项开关是？
正确答案：strictNullChecks。不开它，null 和 undefined 可以赋给任何类型，等于放弃一半的类型安全，也是线上崩溃最常见的原因。
4. never 在 switch 的 default 分支里起什么作用？
正确答案：穷尽检查。所有分支都处理完时，default 里的值被收窄成 never，可以赋给 never 参数；一旦漏了分支，它就有具体类型，传参报错。
5. satisfies 相比类型注解和 as const，优势是什么？
正确答案：两者兼得。类型注解会把值拓宽成注解类型；as const 完全不校验；satisfies 校验形状的同时保留 '等待' 这种字面量类型。
6. 为什么类型谓词 function isUser(x: unknown): x is User 有风险？
正确答案：它是单向承诺。return true 也能编译通过，然后所有调用点都失去保护。谓词函数必须自己写完整的运行时校验。
