开始前

先认清楚：你每天都在用 DSL

DSL（Domain Specific Language，领域特定语言）不是新潮玩意，它就在你眼皮底下：

SQL查询领域的 DSL，几乎所有后端都在写
正则表达式文本匹配领域的 DSL
CSS 选择器文档样式领域的 DSL
Dockerfile / docker-compose.yml部署领域的 DSL
Makefile / GitHub Actions YAML构建与 CI 领域的 DSL
protobuf / OpenAPI 定义接口描述领域的 DSL（IDL）
本篇的核心问题：什么时候该造一个新的 DSL，什么时候用普通函数库就够了？以及，如果决定要"让代码生成代码"，五种主流机制各有什么代价？
模块 1

外部 DSL vs 内部 DSL

分界线只有一条：是否需要独立的解析器。需要，就是外部 DSL；寄生在宿主语言的语法里，就是内部 DSL。

维度外部 DSL内部 DSL
典型代表SQL、正则、protobuf、Nginx 配置、Lua 配置表Java Stream 链式、jOOQ、Rust Builder、Kotlin 块结构、Ruby Rake
解析器需要：词法 → 语法 → 语义分析（ANTLR、Pest、手写递归下降）不需要，复用宿主语言的解析器
IDE 支持弱。要单独做语法高亮、补全、错误检查强。直接继承宿主语言的全部工具链
表达力上限高。可以设计完全贴合领域的语法受宿主语言语法约束，拗不过来的部分只能放弃
错误提示可以精确到领域概念（"字段 X 缺少类型"）报错是宿主语言的类型错误，领域信息丢失
跨语言可以，一份定义多语言消费（protobuf 的卖点）不行，和宿主语言绑死
成本高。解析器 + 工具链 + 版本演进全要自己养低。一个库的体量

内部 DSL 的三种形态

① 链式 Fluent API —— 读起来像句子

// Java Stream / jOOQ 风格：方法名连起来就是 DSL
List<String> names = users.stream()
    .filter(u -> u.getAge() >= 18)
    .map(User::getName)
    .sorted()
    .collect(Collectors.toList());

// jOOQ：SQL 变成 Java 代码，编译期就能查出字段错误
Result<Record1<String>> r = dsl.select(USERS.NAME)
    .from(USERS)
    .where(USERS.AGE.ge(18))
    .fetch();

② Builder —— 参数多、可选多时的标准解

// Rust 的 Builder 惯用法（consuming builder）
let server = ServerBuilder::new()
    .bind("0.0.0.0:8080")
    .workers(8)
    .timeout(Duration::from_secs(30))
    .build()?;   // 构造时做校验，缺必填项编译不过

// 对比：Go 没有默认参数，多字段结构体常用函数式选项
srv := NewServer(
    WithAddr(":8080"),
    WithWorkers(8),
    WithTimeout(30*time.Second),
)

③ 块结构 DSL —— 用闭包模拟关键字

// Kotlin：Gradle Kotlin DSL / Ktor 路由，靠尾随 lambda 造出"关键字"
http {
    route("/api") {
        get("/users") { call.respond(userService.list()) }
        post("/users") { call.respond(userService.create(call.receive())) }
    }
}

// Ruby：Rakefile，块 + 无括号方法调用读起来像配置语言
task :default => [:test]
task :test do
  sh "go test ./..."
end
判断口诀：用户是程序员吗？是 → 内部 DSL（白嫖 IDE）。用户是业务/策划/运维吗？是 → 外部 DSL（语法自己定，但要养解析器）。用户还没有出现？→ 别造，先用配置格式。
模块 2

五种宏 / 编译期生成机制对比

宏的本质是编译期执行的一段代码，输入是语法树，输出是语法树。五种机制的差别在于：操作的是文本还是语法树，以及工具链帮不帮你。

机制阶段操作对象表达力与主要坑
Lisp 系宏
(defmacro)		编译期S 表达式
（代码即数据）		表达力最强，可任意变换语法树。坑：卫生性（变量捕获）、可读性差
Rust 声明宏
(macro_rules!)		编译期token 流
（模式匹配式）		中等表达力，写重复结构很快。坑：递归深度限制、错误信息指向宏内部
Rust 过程宏
(derive/属性/类函数)		编译期TokenStream
（可解析为 AST）		强，能做任意代码变换（#[derive]、#[tokio::main]）。坑：编译变慢、依赖生态分裂
C/C++ 预处理器编译前纯文本
（无语义感知）		最弱。坑：无作用域、难调试。X-Macro 是用补丁补漏的经典技巧
C# Source Generator编译期Roslyn 语法树强，可读可遍历的 API。坑：增量编译缓存行为、生成代码的调试体验
Java 注解处理器
(APT / KSP)		编译期javax.lang.model 元素中等，生成 Java/Kotlin 代码。坑：元素级 API 啰嗦、KSP 需单独维护一套

Lisp 宏：代码即数据

;; Clojure：unless 在标准库里不存在，十行代码自己造
(defmacro unless [cond & body]
  `(if ~cond nil (do ~@body)))    ;; 反引号模板，~ 是插值，~@ 是展开列表

;; (unless false (println "hi")) 展开为：
;; (if false nil (do (println "hi")))
;; 输入和输出都是 S 表达式 —— 语法树直接就是数据结构

;; 卫生性问题示例：宏内部引入的 x 捕获了调用方的 x
(defmacro bad [x] `(let [x 1] (+ x ~x)))   ;; 两个 x 撞车，Racket 用 syntax-rules 解决

Rust 两种宏

// 声明宏：模式匹配 token，vec! 的真实实现（简化）
macro_rules! my_vec {
    ( $( $x:expr ),* $(,)? ) => {
        {
            let mut v = Vec::new();
            $( v.push($x); )*      // $(...)* 对每个匹配的 token 重复
            v
        }
    };
}
let nums = my_vec![1, 2, 3];      // 展开成三段 push

// 过程宏：读 AST 生成代码，库作者用得最多
use proc_macro::TokenStream;

// 三种过程宏：
// #[derive(MyTrait)]      —— 给结构体/枚举自动实现 trait
// #[my_attribute]         —— 替换/包裹被标注的 item
// my_proc_macro!(...)     —— 类函数宏，输入任意 token

pub fn my_derive(input: TokenStream) -> TokenStream {
    let ast: DeriveInput = syn::parse(input).unwrap();  // syn 解析语法树
    let name = &ast.ident;                        // 取出结构体名
    quote::quote! {                               // quote 生成代码
        impl MyTrait for #name {
            fn describe(&self) -> String { stringify!(#name).to_string() }
        }
    }.into()
}

C 预处理器与 X-Macro：没有循环就用文件重复

/* colors.def —— 纯数据，故意没有 include guard，可以被反复包含 */
X(RED,   "#FF0000")
X(GREEN, "#00FF00")
X(BLUE,  "#0000FF")

/* 用法一：生成枚举。## 是 token 粘贴运算符 */
#define X(name, hex) COLOR_##name,
enum Color {
#include "colors.def"
};
#undef X

/* 用法二：同一个文件换个 X 定义，再生成一张字符串表 */
#define X(name, hex) hex,
const char* color_hex[] = {
#include "colors.def"
};
#undef X
X-Macro 的思想至今活着："数据只写一份，按需生成不同形态"。现代等价物是代码生成器（protoc、sqlc）——把 .def 文件换成 .proto / .sql，把预处理器换成正式生成器。

模块 3

代码生成实战：protoc、OpenAPI、ORM

代码生成的正确用法是跨边界的契约翻译：一份定义，多语言消费，边界上不出错。

① protobuf：IDL 驱动，跨语言 RPC 的标配

// order.proto —— proto3 语法
syntax = "proto3";
package shop;
option go_package = "example.com/shop/pb;pb";

message Order {
    string id = 1;
    repeated LineItem items = 2;      // repeated = 可变长数组
    OrderStatus status = 3;
    int64 created_at = 4;             // 字段编号即线上契约，永不复用
}
message LineItem { string sku = 1; int32 qty = 2; }
enum OrderStatus { PENDING = 0; PAID = 1; SHIPPED = 2; }

service OrderService {
    rpc GetOrder(GetOrderRequest) returns (Order);
}
# 生成 Go 结构体 + gRPC 客户端/服务端桩代码
protoc --go_out=. --go-grpc_out=. order.proto

# 生成 Python
protoc --python_out=. order.proto

# 生成 TypeScript（protobuf-es 等插件）
protoc --es_out=. order.proto

② OpenAPI Generator：REST 契约 → 客户端与服务端骨架

# openapi.yaml 定义接口 → 生成类型安全的 client，前后端并行开发
openapi-generator-cli generate -i openapi.yaml -g typescript-axios -o src/client
openapi-generator-cli generate -i openapi.yaml -g spring        -o server

# 纪律：生成物放独立目录/包，CI 校验 git diff，防止有人手改生成文件

③ ORM 实体生成：从 SQL 出发反向生成

-- sqlc：schema.sql + queries.sql → 类型安全的 Go 代码，无反射 ORM
-- queries.sql
-- name: GetOrder :one
SELECT * FROM orders WHERE id = $1;

-- name: ListOrders :many
SELECT * FROM orders WHERE created_at > $1 ORDER BY created_at DESC LIMIT $2;
# 一条命令，读 schema + queries，生成 models.go 和 querier.go
sqlc generate

# 生成的代码长这样（类型全对齐，SQL 写错编译期就报）
func (q *Queries) GetOrder(ctx context.Context, id string) (Order, error) { ... }
type Order struct {
    ID        string
    Status    OrderStatus
    CreatedAt time.Time
}

生成方式对比

方式输入输出适用与代价
protobuf.proto 文件多语言 POJO/struct + RPC 桩跨语言 RPC、存储格式。代价：二进制不可读、schema 演进要守规矩
OpenAPI Generatoropenapi.yamlclient / server 骨架REST 契约先行。代价：生成的 server 往往只是骨架，业务逻辑仍手写
sqlc.sql 文件类型安全数据访问层拒绝反射 ORM 的团队。代价：复杂动态 SQL 支持弱
模板引擎
(Jinja/StringTemplate)		模板 + 数据任意代码定制化最强。代价：模板代码无类型检查，是最差的代码生成形态

模块 4

反射的代价与替代

反射让程序在运行时读写类型信息。它是很多框架的基石，也是一笔被低估的账单。

账单明细

代价说明
编译期检查归零方法名是字符串，拼错编译不报，运行时 NoSuchMethodException
性能损失Method.invoke 有参数检查和访问检查，JIT 难以内联；热路径上比直接调用慢数倍
模块化破坏JDK 9 模块化（JPMS）之后，对 JDK 内部类的反射可能抛 InaccessibleObjectException
重构失效IDE 的"查找引用"、"安全重命名"对反射调用无能为力，改字段名 = 埋雷
可读性下降"字符串驱动"的控制流无法静态追踪，新人读代码像考古
// 反射调用：字符串拼方法名，慢，且拼错运行期才炸
Method m = obj.getClass().getMethod("calcPrica", double.class);  // 拼写错误！
m.invoke(obj, 99.0);   // NoSuchMethodException: calcPrica —— 上线后某个深夜

// 直接调用：编译期检查，JIT 可内联
obj.calcPrice(99.0);

替代方案的阶梯

方案检查时机相对性能典型场景
直接调用编译期1x常规代码
MethodHandle编译期（部分场景）接近直接调用LambdaMetafactory、 invokedynamic 底层
编译期生成编译期1x序列化、DI、ORM 映射——生成专用适配代码
反射运行期数倍~十倍级框架的通用逻辑，不得不动态时
字符串 Eval运行期最差配置里塞代码，万不得已不要用
序列化框架的代际更替就是这条阶梯的实证：Java 的 Jackson 默认走反射，kotlinx.serialization 用编译器插件在编译期生成序列化代码；Go 用 struct tag + 编译期生成（如 easyjson）；Rust 用 serde derive 在编译期生成。共同趋势：反射方案在让位给编译期生成。
反射不是不能用，而是要有边界：框架底层用反射（一次编写，全员受益）没问题；业务代码里每个模块都"getMethod + cast"就是在给后人埋雷。判断标准：这段动态代码，一年后还有人敢改吗？
模块 5

Python 装饰器与元类

Python 把"运行期改写代码"做成了语言的一等公民：装饰器改函数，元类改类。

装饰器 = 语法糖

# @dec 完全等价于 func = dec(func)，导入时执行一次，不是每次调用
import functools, time

def timed(func):                       # 计时装饰器
    @functools.wraps(func)              # 保留 __name__/__doc__，否则日志和调试全乱
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            print(f"{func.__name__} took {time.perf_counter()-start:.3f}s")
    return wrapper

def retry(times=3):                    # 带参数装饰器：三层嵌套
    def deco(func):
        @functools.wraps(func)
        def wrapper(*a, **kw):
            for i in range(times):
                try: return func(*a, **kw)
                except Exception:
                    if i == times - 1: raise
        return wrapper
    return deco

@timed
@retry(times=2)
def fetch(url): ...
# 等价于 fetch = timed(retry(2)(fetch))
# 堆叠顺序：靠近函数的先应用；调用时最外层先执行

元类：控制"类的创建"

# 元类是 type 的子类。定义类时 __new__ 被调用，可以改写/注册这个类
REGISTRY = {}

class RegistryMeta(type):
    def __new__(mcs, name, bases, ns):
        cls = super().__new__(mcs, name, bases, ns)
        if bases:                # 跳过基类自身，只注册子类
            REGISTRY[name] = cls
        return cls

class Plugin(metaclass=RegistryMeta): pass

class AuthPlugin(Plugin): pass
# AuthPlugin 定义的瞬间，REGISTRY["AuthPlugin"] 已自动就位 —— 插件系统的经典实现

# 现代替代：__init_subclass__（Python 3.6+），普通类就能挂钩子，比元类轻得多
class Plugin:
    def __init_subclass__(cls, **kw):
        super().__init_subclass__(**kw)
        REGISTRY[cls.__name__] = cls
装饰器与元类的隐性成本：① 调用栈每加一层，出错时堆栈就深一层，日志像洋葱；② 导入期副作用让启动变慢、测试难隔离；③ IDE 跳转和静态分析对动态注册失效。优先级建议：普通函数 > 装饰器 > __init_subclass__ > 元类。元类是最后手段，Django ORM、ABCMeta 之外的场景，九成用不着。
模块 6

Lua 嵌入：配置与插件 DSL

Lua 是嵌入式脚本之王：解释器体积约 200KB、纯 ANSI C 无依赖、设计目标就是"嵌入宿主程序"。

三种典型用途

用途形态代表与关键风险
配置 DSL求值一个 Lua 表，得到配置游戏数值表。比 JSON/YAML 强：可计算、可复用常量。风险：配置错误变成运行时错误
插件 / mod 系统受限解释器执行第三方脚本魔兽世界插件、Roblox、各类游戏 mod。风险：沙箱逃逸、无限循环拖死主线程
网关 / 业务规则嵌入 NGINX（OpenResty）写路由与逻辑APISIX、Kong 的插件生态。风险：阻塞调用拖垮事件循环

游戏配置：比 JSON 多出来的表达力

-- weapon.lua：策划可以直接写公式，不用改引擎代码
local BASE_DAMAGE = 100

return {
    weapon = {
        sword = { damage = BASE_DAMAGE * 1.0, speed = 1.2 },
        bow   = { damage = BASE_DAMAGE * 0.8, speed = 0.9, range = 300 },
    },
    -- 函数也是合法配置：平衡性调整无需重新编译
    crit_chance = function(level) return math.min(0.05 * level, 0.5) end,
    -- 按环境切换，JSON 得写三份
    server = DEV and { exp_rate = 10 } or { exp_rate = 1 },
}

网关路由：OpenResty 风格的 Lua 逻辑

-- APISIX / OpenResty：每个请求都会执行这段 Lua，注意别写阻塞操作
local cjson = require "cjson"

local routes = {
    { pattern = "^/api/v1/users",  upstream = "user_service" },
    { pattern = "^/api/v1/orders", upstream = "order_service" },

ngx.req.read_body()
local uri = ngx.var.uri

for _, r in ipairs(routes) do
    if string.find(uri, r.pattern) then
        ngx.log(ngx.INFO, "route ", uri, " -> ", r.upstream)
        break
    end
end

ngx.header["Content-Type"] = "application/json"
ngx.say(cjson.encode({ ok = true, path = uri }))

C 侧集成：最小骨架

/* 标准 lua C API：建状态 → 加载 → 执行 → 取全局量 */
#include <lua.h>
#include <lauxlib.h>

lua_State *L = luaL_newstate();
luaL_openlibs(L);                       // 打开标准库 —— 注意：这会带上 os.execute 等危险函数

if (luaL_loadbuffer(L, script, len, "config") || lua_pcall(L, 0, 0, 0)) {
    fprintf(stderr, "lua error: %s\n", lua_tostring(L, -1));
    return 1;
}
lua_getglobal(L, "routes");           // 从配置表里取值
Lua 嵌入的安全三件套，缺一件就是事故：① 函数白名单——不调 luaL_openlibs 全开，手动只注册安全函数（去掉 os.execute、io.open、loadstring）；② 指令数 hook——lua_sethook 设 count hook，超预算直接 error，防死循环；③ 内存上限——自定义 alloc 函数统计用量，超限拒绝分配。默认全开标准库的 Lua 沙箱约等于没沙箱。
模块 7

DSL 设计的坑

造 DSL 的最大风险不是技术实现，是造完之后只有你一个人懂，而需求还在天天变。

症状根因处方
评审会上说不出 DSL 的目标用户是谁没有真实需求，为造而造砍掉。先用配置格式（YAML/TOML），需求稳定且高频后再抽
语法靠"约定"，没有正式解析器内部 DSL 硬拗超出宿主语言表达力的语法上 ANTLR/Pest 写真正的解析器，或砍需求
报错只有"语法错误：第 3 行"AST 没保留源码位置token 携带位置信息一路传到错误提示
每个新需求都要改解析器设计时没留扩展点预留表达式/函数调用机制，别把每种写法都焊死
用户偷偷绕过 DSL 直接改代码DSL 表达力不够或学习成本太高复盘：是补表达力，还是承认该用通用语言
生成代码没人敢动，也没人动得了无 diff 校验、无版本锁定CI 强制生成 + git diff 检查 + 生成器版本锁定
三条红线的自查：① 过度设计——先问"不用 DSL 行不行"，答案通常是"行"。 DSL 应该是被需求挤出来的，不是被灵感喷出来的。② 调试困难——写第一行解析器之前，先回答"语法错误时长什么样、怎么定位"；断点能进 DSL 吗？栈里能看懂吗？③ 学习成本——团队平均已经要学几种 DSL 了？再加一种，边际成本谁付？
务实的演化路径：配置格式（JSON/YAML）→ 带逻辑的配置（Lua 表 / 模板变量）→ 内部 DSL（宿主语言的链式/块结构 API）→ 外部 DSL（独立解析器）。每上升一级，都应该是被真实需求逼的，而不是被野心推的。停在越低的一级，维护越便宜。
模块 8

十个坑

1
为想象中的需求设计图灵完备 DSL
目标是"让业务自己写规则"，最后造出一门没人会维护的语言。先提供函数库和配置格式，需求被验证三次以上再抽 DSL。
2
内部 DSL 硬拗超出宿主语言的语法
在 Java 里用链式调用模拟 if/else，代码像天书。宿主语言的语法边界就是内部 DSL 的天花板，越界即灾难。
3
宏/生成代码调试断链
断点进不去、栈里全是展开后的噪声、报错行号指向宏定义处。写宏的同时就要写展开后的调试视图（cargo expand、rust-analyzer 的宏展开）。
4
生成代码被手改，下次生成静默覆盖
CI 里没有"重新生成 + git diff --exit-code"这一步，手改的补丁迟早丢失。生成物必须 boring，且 DO NOT EDIT 头要加。
5
反射万能论：字符串拼方法名
"这样最灵活"，直到某次重命名字段，线上半夜 NoSuchMethodException。反射是框架的底层工具，不是业务的日常手段。
6
宏错误信息指向宏内部而非调用点
用户看到的是 50 行展开代码里第 3 个 token 不匹配。Rust 的 macro_rules 尤其如此，过程宏里要主动构造可读错误。
7
Lisp 宏忽略卫生性导致变量捕获
宏内部引入的变量名与调用方撞车，行为随上下文漂移。Racket 的 syntax-rules / syntax-parameters 就是为解决这个而生。
8
Lua 沙箱白名单不严
直接 luaL_openlibs 全开标准库，第三方脚本一个 os.execute 就拿下宿主进程。白名单 + 指令 hook + 内存限额，三件套一件不能少。
9
装饰器叠了七八层
一次调用的执行路径横跨八个文件，堆栈像洋葱，测一个 bug 要剥半天。控制层数，能用组合就不用嵌套。
10
DSL 语法变更不提供迁移路径
外部 DSL 的存量文件全部报错，业务停摆。语法变更要版本化（proto 的 reserved、DSL 的 dialect 声明），并提供自动迁移工具。
自测

六道题

1. 判断外部 DSL 与内部 DSL 的分界线是？
正确答案：是否需要独立解析器。SQL、protobuf 需要自己的解析器，是外部 DSL；Java Stream、Builder 寄生在宿主语言语法里，是内部 DSL。图灵完备与否不是分界——很多配置型 DSL 并不图灵完备。
2. Rust 里的 #[derive(Debug)] 属于哪种机制？
正确答案：过程宏。Rust 的过程宏分三种：derive（自动实现 trait）、attribute（替换被标注项）、类函数宏（my_macro!(...)）。macro_rules! 是声明宏，靠 token 模式匹配，做不了"读结构体字段再生成代码"这类事。
3. C 语言的 X-Macro 技巧解决什么问题？
正确答案：多次包含 + token 粘贴。数据只写一份（colors.def），每次 #include 前用 #define X 改变展开形态，就得到枚举、字符串表等不同产物。它的现代等价物就是 protoc / sqlc 这类正式代码生成器。
4. 关于生成代码，正确的工程纪律是？
正确答案：版本锁定 + diff 校验 + 标准头。"记得"是不会记得的——没有 CI 校验，手改的补丁某次生成后静默消失，故障在几周后才爆发。生成物必须 boring，这是纪律不是洁癖。
5. 反射方案相对编译期生成的主要工程代价是？
正确答案：编译期检查归零 + 性能 + 重构失效。方法名拼错运行期才炸、JIT 难内联、IDE 重命名覆盖不到反射调用。这也是序列化框架从反射（Jackson）转向编译期生成（kotlinx.serialization、serde derive）的原因。
6. 把 Lua 嵌进网关做插件系统，防死循环的正确手段是？
正确答案：指令计数 hook + 白名单 + 内存上限三件套。lua_sethook 的 count hook 每执行 N 条指令回调一次，超限抛错，这是 Lua 官方的执行预算机制。只开白名单函数（去掉 os.execute 等）防逃逸，内存 alloc 统计防撑爆宿主。

术语表

术语一句话解释
外部 DSL有独立语法和解析器的领域语言，如 SQL、protobuf、正则
内部 DSL寄生在宿主语言语法里的领域 API，如链式调用、Builder、块结构
Fluent API链式方法调用，读起来像句子的接口风格
Builder 模式用链式 setter 逐步构造复杂对象，构建时统一校验
宏编译期执行的代码变换：输入语法树，输出语法树
卫生宏保证宏内部引入的标识符不会捕获调用方变量的宏机制
声明宏Rust macro_rules!，按 token 模式匹配展开
过程宏Rust 编译期读 AST 生成代码的宏，分 derive/attribute/类函数三种
Source GeneratorC# 基于 Roslyn 的编译期源码生成机制
注解处理器Java APT / Kotlin KSP：编译期扫注解生成代码
X-MacroC 预处理器技巧：同一数据文件多次包含，生成不同形态代码
Token 粘贴C 预处理器 ## 运算符，把两个 token 粘成一个（COLOR_##name）
反射运行期读写类型信息、调用方法的机制，代价是编译期检查归零
MethodHandleJava 的方法句柄，比反射快且更可内联的动态调用机制
装饰器Python 的 @语法糖，导入时把函数替换成包装后的版本
元类type 的子类，控制类的创建过程，Python 最重的元编程机制
__init_subclass__Python 3.6+ 的类继承钩子，比元类轻量的替代
沙箱限制脚本能力的执行环境：函数白名单 + 执行预算 + 资源上限
词法/语法分析把源码文本切成 token、再组织成语法树的过程，外部 DSL 的地基
AST抽象语法树，代码的结构化表示，宏与编译期生成的操作对象
下一步怎么练：① 用 macro_rules! 或 C# Source Generator 给一个重复的数据结构写派生实现，用 cargo expand / 反编译确认产物；② 给一个已有项目加 sqlc，把最脏的查询从 ORM 迁过去，对比代码量和类型安全；③ 用 lua_sethook 给一个嵌入 Lua 的配置系统加执行预算和函数白名单；④ 复盘你项目里最老的一个"自制 DSL"：它的目标用户真的存在吗？
