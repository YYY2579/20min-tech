模块 1

执行顺序：为什么 WHERE 里不能用 SELECT 的别名

SQL 声明的书写顺序和数据库的实际执行顺序不一样。理解这一点，"哪个子句能用什么列/别名"这类问题就再也不会错。

书写顺序 vs 逻辑执行顺序

步骤逻辑执行顺序在做什么
①FROM / JOIN / ON确定数据来源，做连接。ON 在 JOIN 求值阶段生效
②WHERE按行过滤。此时 SELECT 的别名和计算结果还不存在
③GROUP BY分组。分组键之后的阶段才是"组"的视角
④HAVING按组过滤。可以用聚合函数和（多数数据库允许）SELECT 别名
⑤SELECT计算查询列表、别名、窗口函数
⑥DISTINCT去重（在 SELECT 计算之后）
⑦ORDER BY排序。可以用 SELECT 别名（标准 & MySQL 都允许）
⑧LIMIT / OFFSET最后才截取。对应 SQL Server 的 TOP / FETCH NEXT
-- 一条把顺序演全的查询
SELECT city, COUNT(*) AS cnt            -- ⑤ SELECT：别名 cnt 在这里诞生
FROM users                              -- ① FROM
WHERE created_at >= '2026-01-01'         -- ② WHERE：此时 cnt 还不存在
GROUP BY city                           -- ③ GROUP BY
HAVING COUNT(*) >= 2                 -- ④ HAVING：聚合可用（MySQL 也允许写 HAVING cnt >= 2）
ORDER BY cnt DESC                     -- ⑦ ORDER BY：别名可用
LIMIT 10;                              -- ⑧ LIMIT

报错长什么样

-- ✗ 错误：WHERE 引用 SELECT 别名
SELECT city, COUNT(*) AS cnt
FROM users
WHERE cnt >= 2
GROUP BY city;
-- PostgreSQL: ERROR: column "cnt" does not exist
-- MySQL:      ERROR 1054 (42S22): Unknown column 'cnt' in 'where clause'

-- ✓ 正确：把同样的条件下沉到 HAVING，或者重复写表达式
HAVING COUNT(*) >= 2;   -- HAVING 在 GROUP BY 之后，聚合已可算
三条可背的推论：
① WHERE 不能用 SELECT 别名（WHERE 比 SELECT 先执行）；ORDER BY 可以（ORDER BY 比 SELECT 后执行）。
② 窗口函数在 SELECT 阶段计算，所以 WHERE、GROUP BY、HAVING 里都不能直接写窗口函数——想按窗口结果过滤必须套子查询（见模块 3）。
③ ON 和 WHERE 的作用点不同：ON 决定"怎么连接"，WHERE 决定"连接后保留哪些行"。对 OUTER JOIN，这个区别会改变结果集（见模块 2）。

方言差异备忘

模块 2

JOIN 语义、NULL 传播与 ON vs WHERE

五种 JOIN 在说什么

类型结果集
[INNER] JOIN只保留两表都匹配的行。orders 中 user_id = NULL 的那行（id=105）永远匹配不上任何 user
LEFT [OUTER] JOIN左表全部保留；右表无匹配时，右表列填 NULL
RIGHT [OUTER] JOIN镜像：右表全部保留，无匹配填 NULL。多数场景可以改写成 LEFT JOIN（把表换个序）
FULL [OUTER] JOIN左右都全保留。MySQL 8.0 之前不支持，要用 LEFT JOIN UNION RIGHT JOIN 模拟
CROSS JOIN笛卡尔积：左表 m 行 × 右表 n 行。5 users × 5 orders = 25 行。故意用时才用

ON vs WHERE：OUTER JOIN 的分水岭

-- 写法 A：过滤条件放 ON —— LEFT JOIN 语义完整保留
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o
  ON u.id = o.user_id AND o.status = 'paid';
-- 王五只有 pending 订单 → 右表填 NULL，王五仍然出现在结果里，amount = NULL

-- 写法 B：同样的条件放 WHERE —— LEFT JOIN 退化成 INNER JOIN
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE o.status = 'paid';
-- 因为 WHERE 在连接之后过滤：NULL = 'paid' 得 UNKNOWN → 王五、赵六、孙七全被筛掉
记住这条：WHERE 会把 NULL 行筛掉，IS NULL 是唯一能留住它们的方式。
想"保留左表所有行，右表只挑一部分"，条件必须写在 ON 里；写在 WHERE 里，数据库会老老实实执行完 LEFT JOIN 再把那些 NULL 行删掉——执行计划还是 LEFT JOIN，语义已经变 INNER JOIN。这类 bug 不会报错，只会让数据"悄悄变少"，是最难查的一类。

NULL 传播：三值逻辑

SQL 的布尔是三值：TRUE / FALSE / UNKNOWN。任何与 NULL 的比较都得 UNKNOWN，WHERE 只放行 TRUE。

表达式结果说明
NULL + 1NULL算术传播
NULL = NULLUNKNOWN判空必须用 IS NULL
NULL <> 'paid'UNKNOWN"不等于"也判不出 NULL 行
NOT (NULL = 'paid')UNKNOWN取否还是 UNKNOWN，不是 TRUE
NULL AND FALSEFALSE唯一能把 UNKNOWN 摁成确定值的情况
NULL OR TRUETRUE同上
WHERE UNKNOWN行被丢弃只有 TRUE 能过 WHERE 这一关
-- NULL 传播的实战：LEFT JOIN 后统计
-- users：5 人；orders：5 笔，其中一笔 user_id 是 NULL

-- ✗ 想数"每人几笔订单"，结果全是 0 / 1，没单的人被漏掉
SELECT u.name, COUNT(o.id)
FROM users u LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.name;

-- ✓ COUNT(可空列) 只数非 NULL，没单的人得 0；COUNT(*) 则每行都数，无单的人也数 1
SELECT u.name, COUNT(o.id) AS order_cnt
FROM users u LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.name
ORDER BY order_cnt DESC;
COUNT 的三个变体：COUNT(*) 数所有行；COUNT(col) 数 col 非 NULL 的行；COUNT(DISTINCT col) 数去重后的非 NULL 值。LEFT JOIN 后要"数关联上的行数"，必须 COUNT(右表主键)，用 COUNT(*) 会把没关联上的行也数成 1。
模块 3

窗口函数：不折叠行的 GROUP BY

GROUP BY 把多行压成一行；窗口函数保留每一行，同时在"窗口"上计算。语法骨架：函数() OVER (PARTITION BY ... ORDER BY ... 帧子句)。

常用窗口函数对照

函数行为
ROW_NUMBER() OVER (...)窗口内从 1 连续编号，永远唯一，即使 ORDER BY 值相同也不并列
RANK() OVER (...)并列后跳号：1, 2, 2, 4
DENSE_RANK() OVER (...)并列后不跳号：1, 2, 2, 3
LAG(col, n, def)取当前行往前第 n 行的值；越界给默认值
LEAD(col, n, def)取当前行往后第 n 行的值
SUM/AVG/COUNT/MIN/MAX OVER在窗口上聚合，每行都返回一个值
FIRST_VALUE / LAST_VALUE / NTH_VALUE窗口内第 1 / 最后 / 第 n 个值
NTILE(n)把窗口均分成 n 桶，返回桶号（1~n）

例子 1：每组 Top-N（ROW_NUMBER 的经典用法）

-- 每个城市消费金额前 2 的用户
WITH ranked AS (
  SELECT u.city, u.name,
         SUM(o.amount) AS total,
         ROW_NUMBER() OVER (
           PARTITION BY u.city
           ORDER BY SUM(o.amount) DESC
         ) AS rn
  FROM users u
  JOIN orders o ON o.user_id = u.id
  WHERE o.status = 'paid'
  GROUP BY u.city, u.name
)
SELECT city, name, total
FROM ranked
WHERE rn <= 2      -- 窗口函数结果在 CTE 里，外层 WHERE 随便过滤
ORDER BY city, rn;
为什么必须套一层？窗口函数在 SELECT 阶段（第 ⑤ 步）计算，WHERE 是第 ② 步——窗口函数不能直接写在 WHERE 里。标准解法是子查询 / CTE。有些方言（Teradata、Snowflake、BigQuery、Oracle 23ai）支持 QUALIFY rn <= 2，但 MySQL 8.0 不支持 QUALIFY，跨库兼容的写法就是 CTE。

例子 3：累计与环比（帧子句是关键）

-- 按时间累计消费额
SELECT created_at::date AS d, amount,
       SUM(amount) OVER (
         ORDER BY created_at
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM orders
ORDER BY created_at;

-- 与昨天的差额（LAG 默认偏移 1）
SELECT d, amount,
       LAG(amount, 1, 0) OVER (ORDER BY d) AS prev_amount,
       amount - LAG(amount, 1, 0) OVER (ORDER BY d) AS diff
FROM daily_sales
ORDER BY d;
帧子句的默认值会咬人：写了 ORDER BY 但没写帧子句时，默认是 RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW——RANGE 按"值"算边界，排序值相等的行会被算进同一帧。同一天的 3 笔订单，每行的累计值都包含当天全部 3 笔。想严格"逐行"累计，必须显式写 ROWS BETWEEN ...。
模块 4

CTE 与递归 CTE

WITH 是什么

CTE（Common Table Expression）就是给子查询起名字：只作用于本条语句，执行完即销毁，不落盘、不进元数据。深层嵌套子查询的替代品。

-- 可读性对比：同样的逻辑
-- 写法 A：三层嵌套子查询
SELECT * FROM (
  SELECT city, SUM(amount) t FROM (
    SELECT u.city, o.amount FROM users u JOIN orders o ON o.user_id = u.id
  ) x GROUP BY city
) y WHERE t > 100;

-- 写法 B：CTE，一层一个关注点
WITH joined AS (
  SELECT u.city, o.amount
  FROM users u JOIN orders o ON o.user_id = u.id
),
by_city AS (
  SELECT city, SUM(amount) AS total FROM joined GROUP BY city
)
SELECT * FROM by_city WHERE total > 100;

递归 CTE：遍历树的标准武器

递归 CTE 固定分两段：锚点（anchor）给起点，递归项每一步只基于上一轮的结果 Join 原表，直到没有新行。

-- 组织架构：employees(id, name, manager_id)，manager_id 为 NULL 即老板
WITH RECURSIVE org AS (
  -- ① 锚点：从顶层开始
  SELECT id, name, manager_id, 0 AS depth
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  -- ② 递归项：每一轮把"上一轮找到的人"的下级找出来
  SELECT e.id, e.name, e.manager_id, o.depth + 1
  FROM employees e
  JOIN org o ON e.manager_id = o.id
)
SELECT * FROM org ORDER BY depth, id;

-- 生成 1..10 的序列（最小递归例子）
WITH RECURSIVE seq(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 10
)
SELECT * FROM seq;
递归 CTE 的四条军规：
① 必须有 UNION 或 UNION ALL 连接两段；能确定无重复就用 UNION ALL，省掉去重开销。
② 递归项里只能引用一次 CTE 自身（PG 限制），写两次会报错。
③ 一定要有终止条件（上面 WHERE n < 10）。没有终止条件的递归是生产事故：MySQL 8 的默认递归上限是 cte_max_recursion_depth = 1000，超过直接报错；PostgreSQL 没有硬编码层数上限，会一直跑到内存爆掉。
④ MySQL 8.0+ 和 PostgreSQL、SQL Server、Oracle 都支持 WITH RECURSIVE；MySQL 5.7 没有 CTE，老库要手写存储过程或应用层递归。

性能控制

CTE 在 PostgreSQL 12+ 可以显式控制是否物化：WITH ... AS MATERIALIZED (...) 强制算出中间结果（被多次引用时省重复计算）；AS NOT MATERIALIZED 强制内联展开。默认行为：只被引用一次通常内联，被引用多次通常物化。MySQL 8.0 会自动物化 CTE，没有这个开关。

模块 5

事务隔离与锁行为

四个隔离级别在防什么

隔离级别脏读不可重复读幻读说明
READ UNCOMMITTED会会会几乎不用。Oracle 不支持；MySQL 可以设但 InnoDB 实际按 RC 处理
READ COMMITTED (RC)不会会会PostgreSQL / SQL Server / Oracle 的默认。每条语句看到新的快照
REPEATABLE READ (RR)不会不会基本不会MySQL InnoDB 的默认。事务开始时的快照贯穿整个事务
SERIALIZABLE不会不会不会最严格：读写都加锁 / 冲突即报错，吞吐最低
  • 脏读：读到别人还没提交的修改。对方回滚，你手里的数据就是幻觉。
  • 不可重复读：同一事务内两次 SELECT 同一行，值不一样（被别的事务提交改了）。
  • 幻读：同一事务内两次范围查询，行数不一样（别的事务插入 / 删除了行）。
MySQL 的 RR 为什么"基本不会"幻读？普通 SELECT 是快照读（靠 MVCC 读事务开始时的版本），天然看不到别人插入的新行。但把普通 SELECT 换成 SELECT ... FOR UPDATE（当前读，读最新版本并加锁）时，InnoDB 靠 next-key 锁（记录锁 + 间隙锁）把范围锁住来防幻读。所以"MySQL 没有幻读"是有前提的说法：只有快照读下成立；混合使用快照读和当前读，仍可能观察到不一致。

三种锁的粒度

锁锁什么触发条件（InnoDB）
记录锁 Record索引上的一行唯一索引等值查询命中
间隙锁 Gap索引记录之间的"空隙"（不含记录本身）范围查询；RR 级别默认开启（可设 innodb_gap_lock，但通常不建议关）
Next-Key记录锁 + 左侧间隙锁RR 下的范围扫描默认行为，防幻读的主力，也是死锁的主要来源
-- 显式加锁的写法
BEGIN;
SELECT amount FROM orders WHERE id = 101 FOR UPDATE;  -- 排他锁，别的事务读这行也要等
UPDATE orders SET amount = amount - 50 WHERE id = 101;
COMMIT;

-- 共享锁（MySQL InnoDB 专用语法）
SELECT ... LOCK IN SHARE MODE;   -- 别人能读不能改

-- 死锁长这样：两个事务反向更新两行
-- T1: UPDATE t SET v=1 WHERE id=1;  UPDATE t SET v=2 WHERE id=2;
-- T2: UPDATE t SET v=3 WHERE id=2;  UPDATE t SET v=4 WHERE id=1;
-- 一方报错：ERROR 1213 (40001): Deadlock found when trying to get lock

锁相关的关键参数与事实

参数 / 事实值 / 行为
innodb_lock_wait_timeout默认 50 秒。等锁超时后事务回滚（注意不是整条 SQL 报错后自动重试）
innodb_deadlock_detection默认 ON，死锁在毫秒级被检测并回滚代价小的一方。高并发争用同几行时检测本身耗 CPU，可按官方建议关闭并靠 lock_wait_timeout 兜底
加锁发生在什么时候两阶段锁 2PL：锁在需要时加，在事务提交 / 回滚时才统一释放。推论：事务里加锁越晚、持有越短，死锁越少
MVCC 读旧版本靠 undo log；长事务会让 undo log 无法清理，历史版本堆积 → 大查询拖慢全库
information_schema.innodb_trx排查长事务的第一现场，看 trx_started 和 trx_query
最常见的线上事故：一个忘记提交的事务。BEGIN 之后连接进了连接池没关，事务挂着，next-key 锁不释放，后续写同一范围的请求全部排队 50 秒后超时。三个防线：① 代码里严禁在事务里做 RPC / 发消息；② 设置合理的 statement timeout；③ 监控 information_schema.innodb_trx 中超过 10 秒的事务。
模块 6

优化写法：让索引活下来

EXISTS vs IN vs NOT IN vs NOT EXISTS

-- 查"下过单的用户"：EXISTS 和 IN 语义等价，小表驱动大表
SELECT * FROM users u
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);

SELECT * FROM users u
WHERE u.id IN (SELECT o.user_id FROM orders o);   -- MySQL 5.6+ 优化为 semi-join

-- ✗ 危险：NOT IN 的子查询只要含一个 NULL，结果集恒为空！
-- orders.user_id 有 NULL（id=105）→ 下面这条查不出任何行
SELECT * FROM users u
WHERE u.id NOT IN (SELECT o.user_id FROM orders o);
-- 原理：id NOT IN (1,2,NULL) 展开为 id<>1 AND id<>2 AND id<>NULL，最后一项恒 UNKNOWN

-- ✓ NULL 安全的正确写法
SELECT * FROM users u
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
背这一条：反连接（找"不存在"的数据）永远用 NOT EXISTS，不要用 NOT IN 带子查询。NOT IN 的子查询结果里只要有一个 NULL，整个查询返回空集——而且不报错，只是"数据没了"。修复版 NOT IN 也可以（加 WHERE o.user_id IS NOT NULL），但 NOT EXISTS 天生免疫 NULL，且多数执行计划下等价或更快。

索引失效的六个惯犯

写法后果
WHERE phone = 13800000000
（phone 是 VARCHAR）		隐式类型转换：列被转成数字再比较，索引失效，全表扫描。改成 WHERE phone = '13800000000'
WHERE name LIKE '%三'前置通配符，无法用 B+ 树索引。只有 LIKE '张%' 这种后缀通配能走索引
WHERE DATE(created_at) = '2026-03-01'函数包裹列，索引建立在 created_at 上，用不上。改成范围：created_at >= '2026-03-01' AND created_at < '2026-03-02'
WHERE amount + 100 > 500同上：表达式在列的一侧，索引失效。把代数整理成 amount > 400
WHERE a = 1 OR b = 2
（a、b 各有索引）		可能索引合并，也可能全表扫描。不确定时拆成 UNION 两条各走索引的查询
WHERE status <> 'paid'负向条件（!= / NOT IN / NOT LIKE）通常不走索引，除非建了对应索引且优化器认为选择率低

其他高频优化

问题解法
深分页：LIMIT 1000000, 10 要扫过 100 万行再丢 999990 行keyset 分页：WHERE id > 上一页最大 id ORDER BY id LIMIT 10；或延迟关联：先走覆盖索引拿到 10 个 id 再回表
UNION 慢UNION 会去重（排序或哈希），数据量大时很贵。确认不需要去重就用 UNION ALL
SELECT *① 阻断覆盖索引；② 多取无用列增加 IO 和网络；③ 表加列后行为悄悄变化。列出真正需要的列
COUNT(*) 慢MySQL InnoDB 的 COUNT(*) 是全表扫描中最小的索引；没有"顺手"的精确 count。要近似值用 EXPLAIN 的 rows 估算或维护计数表
大事务一条 INSERT 灌 100 万行 → undo log 暴涨、锁持有久、主从延迟。分批（如每批 1000 行）提交
EXPLAIN 不会看看四列：type（ALL = 全表扫描，要优化到 ref/range/const）、key（实际用的索引，NULL 即没用索引）、rows（预估扫描行数）、Extra（出现 Using filesort / Using temporary 就要警惕）
-- EXPLAIN 实战
EXPLAIN SELECT * FROM orders WHERE user_id = 1;
-- type=ref   key=idx_user_id   rows=2   Extra=NULL          ← 健康的索引查找
EXPLAIN SELECT * FROM orders WHERE user_id + 1 = 2;
-- type=ALL   key=NULL          rows=5   Extra=Using where  ← 全表扫描

综合练习：三道真题练手

都在 s0 的数据集上跑。每题先自己写，再对答案。答案给了 PostgreSQL 方言，换成 MySQL 把 ::date 改成 DATE() 即可。

练习 1：每个城市的 paid 订单总额与人均，只保留人均 >= 100 的城市，按总额降序。考点：JOIN + GROUP BY + HAVING + 别名在 ORDER BY 中的可用性。
练习 2：找出"没有任何 paid 订单"的用户姓名。考点：NOT EXISTS 与 NOT IN 的 NULL 差异（孙七没单、赵六 city 为 NULL、orders 里 user_id 为 NULL 的那行都不该影响结果）。
练习 3：按 created_at 排序，输出每笔订单与上一笔订单的金额差，第一行差值为该行金额本身。考点：LAG 带默认值。
-- 练习 1 答案
SELECT u.city,
       SUM(o.amount) AS total,
       SUM(o.amount) / COUNT(DISTINCT o.user_id) AS avg_per_user
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.status = 'paid'
GROUP BY u.city
HAVING SUM(o.amount) / COUNT(DISTINCT o.user_id) >= 100
ORDER BY total DESC;

-- 练习 2 答案
SELECT u.name
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.user_id = u.id AND o.status = 'paid'
);
-- 预期输出：王五（只有 pending）、赵六、孙七（无订单）
-- 如果改用 NOT IN (SELECT user_id FROM orders WHERE status='paid')，
-- 子查询结果 {1,2,NULL} 含 NULL → 结果为空集，这就是 NULL 传播的坑

-- 练习 3 答案
SELECT id, amount,
       amount - LAG(amount, 1, 0) OVER (ORDER BY created_at) AS diff
FROM orders
ORDER BY created_at;
坑

十个线上坑

1
WHERE 里引用 SELECT 别名
WHERE 比 SELECT 先执行，别名还不存在。报错 unknown column / column does not exist。要么下沉到 HAVING（聚合条件），要么重复写完整表达式。
2
LEFT JOIN 的右表过滤写在 WHERE 里
NULL 行被 WHERE 筛掉，LEFT JOIN 静默退化成 INNER JOIN，数据"悄悄变少"且不报错。右表条件放 ON，或显式写 IS NULL 分支。
3
NOT IN 的子查询含 NULL，结果恒为空
id NOT IN (1, 2, NULL) 恒为 UNKNOWN，一行都不返回。反连接一律用 NOT EXISTS。
4
窗口函数写在 WHERE / GROUP BY 里
窗口函数在 SELECT 阶段求值。按窗口结果过滤要套 CTE / 子查询。MySQL 8.0 不支持 QUALIFY，别写。
5
ORDER BY 后忘了帧子句，累计值算错
默认 RANGE 把排序值相等的行并入同一帧，同一天的 3 笔订单每行累计都含全天。逐行累计必须显式 ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW。
6
数字和字符串比，索引悄悄失效
WHERE varchar_phone = 13800000000 触发隐式类型转换，列被函数化，走不了索引，EXPLAIN 里 type=ALL。常量类型永远跟列类型一致。
7
函数包裹索引列
DATE(created_at) = '...'、amount + 100 > 500 这类写法让索引失效。一律改写成列在左、常量/函数在右侧的范围条件。
8
深分页 LIMIT offset 巨大
LIMIT 1000000, 10 要先扫描并丢弃 100 万行。改 keyset 分页（WHERE id > last_id）或延迟关联。
9
事务里做 RPC / 发消息 / 睡 sleep
事务持锁时间被外部延迟拉长，死锁和锁等待雪崩。事务里只放纯数据库操作，网络调用放到事务提交之后。
10
用 SELECT * 然后按列名取数
阻断覆盖索引、多传无用列、别人加一列就改变结果结构。显式列名，顺带白捡覆盖索引的性能。
自测

六道题

1. 下面哪个子句可以使用 SELECT 列表中定义的别名？
正确答案：ORDER BY。逻辑执行顺序里 ORDER BY（第 ⑦ 步）在 SELECT（第 ⑤ 步）之后，别名已存在；WHERE（第 ② 步）在 SELECT 之前，一定不行。GROUP BY 用别名是方言扩展：PostgreSQL、MySQL 允许，SQL Server 不允许，所以不能当成通用写法。
2. users LEFT JOIN orders ON u.id = o.user_id，然后 WHERE o.status = 'paid'。结果是？
正确答案：等价于 INNER JOIN。LEFT JOIN 先把不匹配的行补 NULL，WHERE 再按行过滤：NULL = 'paid' 得 UNKNOWN，这些行被丢弃。想保留左表全部行，条件必须写在 ON 里。
3. orders 的 user_id 列含有 NULL。SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders) 返回？
正确答案：空集。id NOT IN (1, 2, NULL) 展开为 id<>1 AND id<>2 AND id<>NULL，最后一项恒 UNKNOWN，整个 WHERE 恒不成立。这就是反连接必须用 NOT EXISTS 的原因。
4. 分数排名 100、95、95、88。想要"并列第 2，下一个是第 3 名"，用哪个？
正确答案：DENSE_RANK()。三者都按 ORDER BY 排序：ROW_NUMBER 强行唯一；RANK 并列后跳号（占用名次）；DENSE_RANK 并列不跳号。要求"绝对唯一编号"用 ROW_NUMBER，要"真实名次"用 RANK。
5. WHERE phone = 13800000000（phone 是 VARCHAR 且有索引）会发生什么？
正确答案：索引失效。字符串列与数字比较时，数据库把列转成数字（而不是把数字转成字符串，那样每条记录都要转换），列上套了转换函数，B+ 树索引用不了。MySQL 的 EXPLAIN 里 type=ALL、key=NULL。正确写法是给字符串常量加引号。
6. MySQL InnoDB 默认隔离级别下，关于幻读哪个说法准确？
正确答案：快照读靠 MVCC，当前读靠 next-key 锁。InnoDB 默认 REPEATABLE READ：普通 SELECT 读事务开始时的快照，天然看不到别的事务新插入的行；SELECT ... FOR UPDATE / UPDATE / DELETE 是当前读，RR 下会用记录锁 + 间隙锁把范围锁住来防幻读。说"MySQL 没有幻读"必须加上"快照读"这个前提。

术语表

术语一句话解释
逻辑执行顺序FROM→WHERE→GROUP BY→HAVING→SELECT→DISTINCT→ORDER BY→LIMIT，与书写顺序不同
三值逻辑SQL 布尔有 TRUE/FALSE/UNKNOWN，NULL 参与的运算结果为 UNKNOWN，WHERE 只放行 TRUE
NULL 传播NULL 参与任何算术或比较都得 NULL/UNKNOWN，判空只能用 IS NULL
Semi-join半连接：只返回左表能匹配上右表的行，EXISTS / IN 的典型执行方式
Anti-join反连接：只返回左表匹配不上右表的行，NOT EXISTS 的执行方式
窗口函数OVER (PARTITION BY ... ORDER BY ...) 上计算，保留明细行同时给出聚合值
帧子句 frame窗口函数的计算范围，ROWS 按行、RANGE 按值，默认 RANGE UNBOUNDED PRECEDING
CTEWITH 定义的语句级临时命名结果集，提升可读性，可被多次引用
递归 CTE锚点 UNION ALL 递归项的结构，遍历层级数据，必须有终止条件
MVCC多版本并发控制：读旧版本不加锁，写时生成新版本，靠 undo log 保留历史
快照读读事务开始时的历史版本，不加锁（普通 SELECT）
当前读读最新已提交版本并加锁（UPDATE / DELETE / FOR UPDATE）
记录锁 / 间隙锁 / Next-KeyInnoDB 三种锁：锁一行 / 锁空隙 / 两者兼有；RR 下范围扫描默认 next-key
两阶段锁 2PL锁只增不减、提交时才统一释放；推论是事务内加锁越晚持有越短
脏读 / 不可重复读 / 幻读读未提交 / 两次读同行的值变了 / 两次范围查询行数变了
SARGable查询条件能有效利用索引（列在左、无函数包裹、类型匹配）的写法
覆盖索引索引包含查询所需的全部列，无需回表，EXPLAIN 的 Extra 出现 Using index
回表通过二级索引拿到主键后再查聚簇索引取整行，多一次随机 IO
keyset 分页用上一页的排序键做 WHERE 条件翻页， offset 不随页数增长
延迟关联先用覆盖索引查出目标 id，再回表取完整行，减少随机 IO 次数
