二十分钟学透查询优化器

慢查询 90% 的解法不在加机器，在让优化器选对计划。这篇讲 CBO 怎么估行数、EXPLAIN 每列读什么、JOIN 三种算法怎么选、子查询怎么被改写，最后给一套慢查询改写手册。默认 MySQL 8.0，关键处对比 PostgreSQL。

先建立正确认知：优化器不是敌人，它只是在信息不全的情况下做估算。排查慢查询的顺序永远是：① 它实际花了多久、扫了多少行（EXPLAIN ANALYZE）→ ② 为什么选了这个计划（统计信息 + 代价）→ ③ 改写 SQL 或改索引，而不是一上来就 force index。跳过前两步直接加 hint，经常把 3 秒变成 30 秒。
模块 1

基于代价的优化器框架（CBO）

CBO 干两件事：逻辑优化（把 SQL 改写成等价但更好算的形式）和物理优化（在多个执行计划里挑代价最小的）。它的判断完全建立在统计信息上。

统计信息：优化器的眼睛

统计项MySQL 8.0 来源影响什么
表行数innodb_table_stats（采样估算）全表扫描代价、驱动表大小
索引 cardinalityinnodb_index_stats，按页采样等值条件的选择率
列 min/max索引统计的一部分范围条件估算
直方图ANALYZE TABLE ... UPDATE HISTOGRAM（8.0 新增，等深/等宽）范围选择率，解决 BETWEEN 估算偏差
空值比例采样IS NULL / IS NOT NULL 估算
-- 选择率估算：优化器的核心算式
等值条件：匹配行数 ≈ 表总行数 / cardinality(列)
范围条件：匹配行数 ≈ 表总行数 × (值在 min~max 中的相对位置)
无统计时：  MySQL 默认猜（如 range 猜一定比例，函数猜固定值）

-- 代价模型（简化）：总代价 = IO 代价 + CPU 代价
读一个页的 IO 代价    = 1.0     -- io_block_read_cost 默认 1.0
比较一行的 CPU 代价  = 0.2     -- cpu_tuple_cost 默认 0.2
一次索引查找的 CPU   = 0.1     -- cpu_key_match_cost？实际 0.1~0.4 之间取
建哈希表的 CPU       = 0.2~0.4 -- hash join 相关

-- 直方图实战：范围估算从"瞎猜"变"有据可查"
ANALYZE TABLE t_order UPDATE HISTOGRAM ON create_time WITH 256 BUCKETS;
SELECT * FROM information_schema.column_statistics;  -- 查看直方图

估算不准的三大根源

问题现象对策
列相关性被忽略city='北京' AND level='VIP'，优化器按独立事件相乘，实际高度相关，行数估少 10 倍建联合索引让 cardinality 覆盖组合；或上直方图
数据倾斜status 列 99% 是 1、1% 是 0，等值估算按平均值，查稀有值反而估多直方图（8.0）；或改写查询让优化器知道具体值
统计信息过期大批量导入后没 ANALYZE，cardinality 是上个月的值，计划整体跑偏导入后 ANALYZE TABLE；或开 innodb_stats_auto_recalc
逻辑优化都做了什么（看不到但影响巨大）：① 常量传播（WHERE 1=1 直接消掉）；② 外连接转内连接（WHERE 里的条件让外连接无意义时）；③ 子查询展开/半连接化；④ 分区裁剪；⑤ 等价改写（IN 列表去重排序）。你写的 SQL 和优化器执行的经常不是一回事，这就是为什么要看执行计划而不是"我觉得"。
模块 2

执行计划阅读

EXPLAIN 是"优化器的估算"，EXPLAIN ANALYZE 是"实际发生的真相"。两者对不上的地方就是问题所在。

列读什么
id执行顺序号：大 id 先执行；同 id 按上到下。 UNION 会出现多行
select_typeSIMPLE（简单查询）/ PRIMARY（含子查询的外层）/ DERIVED（物化派生表）/ UNION / SUBQUERY
table正在访问哪张表；出现 <derivedN> / <subqueryN> 说明是物化结果
type访问方式，性能第一指标：const > eq_ref > ref > range > index > ALL
possible_keys可能用的索引（预估阶段）
key实际用的索引。NULL = 全表扫描
key_len索引用了多长（字节）。判断联合索引用了几列：utf8mb4 4 字节/字符
ref索引列的匹配来源：const（常量）/ func / 某表某列
rows预估要扫描的行数。与 filtered 相乘 ≈ 预估结果集
filtered按 WHERE 条件过滤后剩余比例（百分比）
Extra关键信号：Using index（覆盖）/ Using index condition（ICP）/ Using filesort / Using temporary / Using join buffer
-- EXPLAIN ANALYZE（MySQL 8.0，树状输出，含真实执行数据）
mysql> EXPLAIN ANALYZE SELECT * FROM t_order WHERE user_id = 888 ORDER BY create_time LIMIT 10;
-> Limit: 10 row(s)  (actual time=0.052..0.058 rows=10 loops=1)
    -> Sort: t_order.create_time DESC, ...
        (actual time=0.051..0.053 rows=10 loops=1)
        -> Index lookup on t_order using idx_user (user_id=888)
           (actual time=0.031..0.048 rows=42 loops=1)
-- 读法：预估 rows=42，实际 rows=42（准）；排序只排了 42 行（快）
-- 如果 actual rows=50000 而预估 42，就是统计信息或写法出了问题

-- 三个必看对比：
-- 1. actual time：真实耗时（毫秒），Limit 节点是总时间
-- 2. rows vs estimated rows：偏差 > 10 倍就要警觉
-- 3. loops > 1：该节点被执行多次，成本 = 单次 × loops
最常见的误读：① 看到 type=ref 就觉得没问题——ref 后面跟 500 万 rows 一样慢；② 看到 key 有值就放心——可能选了个区分度极低的索引，每次扫 25% 的表；③ 只看 EXPLAIN 不看 EXPLAIN ANALYZE——预估行数可能和真实差 1000 倍，那说明统计信息骗了优化器，改 SQL 之前先修统计。
模块 3

JOIN 算法：Nested Loop / Hash / Sort Merge

两张表 JOIN，数据库只有三种物理算法。选错算法的代价是天差地别的：NLJ 是毫秒，无索引 BNL 可能是分钟。

算法原理适用条件MySQL / PG
Nested Loop Join外层结果集每行，去内层索引里查匹配内层连接键有索引；外层（驱动表）结果集小两者都有，PG 默认优先
Block Nested Loop外层整块存入 join buffer，内层逐行与 buffer 比对内层无索引；外层小（能放进 buffer）MySQL 特有，8.0.20 后被 hash join 取代
Hash Join小表建内存哈希表，大表逐行探测等值连接；至少一表无索引；大表 JOIN 大表MySQL 8.0.20+ / PG 主力
Sort Merge Join两表先按连接键各自排序，再顺序归并连接键已有序（索引）；范围连接；等值PG 有；MySQL 无显式实现
-- 驱动表原则：永远是"过滤后行数小"的表驱动"行数大"的表
-- 反例理解：用 100 万行的表驱动 10 行的表，NLJ 要做 100 万次索引查找
-- 正确：10 行驱动 100 万行，只做 10 次索引查找，每次带出 10 万行

-- MySQL 8.0 hash join 的执行计划长相
mysql> EXPLAIN SELECT * FROM t_order o JOIN t_user u ON o.user_id = u.user_id
    -> WHERE o.amount > 900;
+----+-------------+-------+------------+------+---------------+----------+---------+-------------+------+----------+----------------------------------------+
| id | select_type | table | partitions | type | possible_keys | key      | key_len | ref         | rows | filtered | Extra                                  |
+----+-------------+-------+------------+------+---------------+----------+---------+-------------+------+----------+----------------------------------------+
|  1 | SIMPLE      | o     | NULL       | ALL  | idx_time      | NULL     | NULL    | NULL        | 1M   |    33.33 | Using where                            |
|  1 | SIMPLE      | u     | NULL       | eq_ref| PRIMARY      | PRIMARY  | 8       | db.o.user_id |    1 |   100.00 | NULL                                   |
+----+-------------+-------+------------+------+---------------+----------+---------+-------------+------+----------+----------------------------------------+
-- 读法：o 全表 + amount 过滤（约 33 万行），每行用 PRIMARY 等值查 u（eq_ref，1 次树查找）
-- 这是 NLJ：o 驱动、u 被驱动。如果 u.user_id 没主键，就会退化成 hash join 或 BNL

算法选择速查

# 场景 → 算法 → 你该做什么
内层有索引 + 驱动表小        → NLJ     → 确保内表连接键有索引
内层无索引 + 驱动表小        → Hash/BNL → 加 join_buffer_size；或给内表加索引
大表等值 JOIN 大表（无索引） → Hash Join → MySQL 8.0 自动；<8.0.20 加索引或拆批
连接键已有序                 → Merge Join → 保持索引顺序，避免中间排序
范围连接（>、<、BETWEEN）    → NLJ / Merge → Hash 不支持范围连接
MySQL 版本行为差异（面试高频）：8.0.20 之前，无索引的等值 JOIN 走 Block Nested Loop（Extra: Using join buffer (hash join 出现前的 block nested loop)）；8.0.20 起 hash join 取代 BNL。所以老文档里"Using join buffer 就要加索引"的说法在今天要修正：先看 Extra 具体是哪种 join buffer，如果是 hash join 且驱动表不大，可能已经是最优。
模块 4

子查询优化：半连接、物化、IN→EXISTS

子查询是慢查询重灾区，因为优化器对它的处理策略有五六种，选错就是数量级差距。

策略行为适用
semijoin（firstMatch）IN (SELECT) 转成半连接：外表每行去内表找第一个匹配即停内表有索引、结果去重
semijoin（loosescan）对分组内表（一对多）跳跃扫描，每组只查一次内表连接键有索引且是分组型
materialization把子查询结果物化成临时派生表（可能自动加索引 auto-key）子查询结果小、被多次引用
IN → EXISTS语义等价改写，让外层成为驱动表外层小、内层大时手写 EXISTS 更快
物化 derivedFROM 里的子查询直接物化成临时表复杂派生表，避免重复执行
-- 经典场景：查"下过单的用户"
SELECT * FROM t_user WHERE user_id IN (SELECT user_id FROM t_order);
-- 优化器可能：① semijoin-firstMatch（默认，内表 idx_user 有索引时最优）
--            ② materialization（把子查询结果物化成临时表再 JOIN）

EXPLAIN SELECT * FROM t_user WHERE user_id IN (SELECT user_id FROM t_order);
+----+--------------+-------------+------------+--------+---------------+----------+---------+-------------+--------+----------+--------------------------+
| id | select_type  | table       | type       | key    | key_len | ref         | rows    | filtered | Extra                    |
+----+--------------+-------------+------------+--------+---------------+----------+---------+-------------+--------+----------+--------------------------+
|  1 | SIMPLE       | t_user      | index      | PRIMARY| 8       | NULL        | 1000000 |   100.00 | Using index              |
|  1 | SIMPLE       | <subquery2> | semijoin   | idx_user| 9       | db.t_user..|       1 |   100.00 | FirstMatch(t_order)      |
+----+--------------+-------------+------------+--------+---------------+----------+---------+-------------+--------+----------+--------------------------+
-- Extra: FirstMatch(t_order) 就是 semijoin 生效的标志

-- 手动切换策略（排查用）
SET optimizer_switch = 'semijoin=off';                # 关闭半连接，退回物化
SET optimizer_switch = 'materialization=off';       # 关闭派生表物化
SET optimizer_switch = 'subquery_to_derived=off';   # 8.0.22+：子查询转派生表

-- NOT IN 与 NOT EXISTS 的 NULL 陷阱（血泪坑）：
SELECT * FROM t_user WHERE user_id NOT IN (SELECT user_id FROM t_order);
-- 若子查询结果含 NULL，整个 NOT IN 永远返回空集！
SELECT * FROM t_user WHERE NOT EXISTS (SELECT 1 FROM t_order WHERE t_order.user_id = t_user.user_id);
-- NOT EXISTS 无 NULL 问题，语义等价但更安全、常更快
两个必须记住的事实：① NOT IN (含 NULL 子查询) = 空结果集，这是 SQL 语义不是 bug——NOT IN 展开成 AND 链，任何 NULL 比较都返回 UNKNOWN；② IN 与 EXISTS 在纯等值且无 NULL 时等价，但执行上"IN 适合大表驱动小表、EXISTS 适合小表驱动大表"，手写时要配合数据规模。MySQL 8.0 会自动做大部分转换，但 PostgreSQL 不会自动把 NOT IN 转 anti join，那边必须手写 NOT EXISTS。
模块 5

排序与分组的实现

ORDER BY / GROUP BY 是 CPU + 内存大户。理解"什么时候走索引有序、什么时候 filesort、什么时候临时表"，就理解了这类慢查询的全部。

场景实现方式EXPLAIN 信号
ORDER BY 走索引索引本身有序，顺序扫描即可无 Using filesort
ORDER BY 内存排序结果集进 sort_buffer 快排Using filesort
ORDER BY 落盘sort_buffer 放不下，写临时文件多路归并Using filesort（慢，看 status）
GROUP BY 走索引紧凑索引扫描，边读边聚合无 Using temporary
GROUP BY 临时表先物化分组再聚合Using temporary + Using filesort
-- 排序相关参数
sort_buffer_size        = 256KB   -- 会话级，放不下就落盘
max_length_for_sort_data = 4096   -- 超过则用"双路排序"（只读排序列+主键）
max_sort_length         = 1024    -- 排序键前 N 字节参与比较

-- 双路 vs 单路排序
单路（row 数据小）：一次性读全字段进 buffer 排序 → 内存省但可能两次回表
双路（row 数据大）：buffer 只存 排序列 + 主键 → 排序后按主键回表取行
-- 宽表 + 大 offset 时双路常更快，因为 buffer 能装更多待排项

-- GROUP BY 优化：让分组顺序匹配索引顺序
CREATE INDEX idx_ut ON t_order(user_id, create_time);

-- 走索引分组（无 Using temporary）：
SELECT user_id, COUNT(*) FROM t_order GROUP BY user_id;
-- 不匹配索引顺序时：
SELECT user_id, COUNT(*) FROM t_order GROUP BY user_id ORDER BY NULL;  -- 禁止隐式排序，消掉多余 filesort
三条实战规则：① ORDER BY 的列顺序和方向必须与索引完全一致（混合 ASC/DESC 时 8.0 支持降序索引，之前只能全升序匹配）；② SELECT 的排序列不要跨表分散——两表各排一列时 filesort 无法避免，尽量把排序字段冗余到单表；③ 分组 + 计数这类"周期性重复计算"，直接建汇总表预聚合，别指望优化器每次现场算百万行。

模块 7

慢查询改写手册

按出现频率排序的八种改写。每种都先看执行计划，再动手。

深翻页改游标：LIMIT 100000,10 → WHERE create_time < 上一页末条 LIMIT 10，把 offset 换成索引范围条件
select * 改按需取列：让查询走覆盖索引（Extra: Using index）；必须取整行时用延迟关联（子查询拿主键再 JOIN）
大 IN 拆批：IN 列表 5000 个值改临时表 JOIN，或 500 个一批循环——IN 过长时优化器可能直接放弃索引
OR 改 UNION ALL：WHERE a=1 OR b=2 且 b 无索引 → 拆成两个走各自索引的查询 UNION ALL（注意去重时用 UNION）
NOT IN 改 NOT EXISTS：避开 NULL 语义陷阱，同时让优化器走 anti join
拆分大 SQL：一条 30 表 JOIN 拆成多次单表查询 + 内存关联。数据库的 JOIN 算法没有"应用层 HashMap"灵活，应用层关联常快数倍
预聚合替代实时计算：count/sum over 百万行且周期性重复 → 汇总表 + 定时任务，查询变点查
修统计信息再谈索引：ANALYZE TABLE 刷新 cardinality，或 UPDATE HISTOGRAM 修范围估算。很多"索引失效"其实是统计过期造成的误判
-- 改写前后对比的标准流程（以深翻页为例）
-- 改写前：
EXPLAIN ANALYZE SELECT * FROM t_order ORDER BY create_time LIMIT 100000, 10;
-- actual time=850ms，Sort 节点 rows=100010

-- 改写后（延迟关联 + 游标）：
EXPLAIN ANALYZE
SELECT o.* FROM t_order o JOIN (
  SELECT order_id FROM t_order
  WHERE create_time < '2026-10-01 00:00:00'
  ORDER BY create_time DESC LIMIT 10
) t ON o.order_id = t.order_id;
-- actual time=0.3ms：子查询走 idx_time 覆盖扫描 10 行，回表 10 次

-- 提速 2800 倍，没加一台机器、没改一行代码逻辑
Hint 的正确用法：FORCE INDEX 是诊断工具不是生产工具——它绕过了优化器的估算，统计信息一变就可能从 3 秒变 30 秒。正确顺序：先修统计信息（ANALYZE / 直方图）→ 再改索引 → 还不行才考虑 hint，且必须配套监控。MySQL 8.0 的优化器 hint（/*+ INDEX(t, idx) */）比 FORCE INDEX 更细粒度（可指定 join order、semijoin 策略），优先用它。
模块 8

真实执行计划逐列解读

四个典型输出，覆盖 90% 的线上场景。每个都按"先看什么、结论是什么、怎么改"讲。

场景一：健康的计划（覆盖索引 + 范围）

mysql> EXPLAIN SELECT order_id, user_id, create_time FROM t_order
    -> WHERE user_id = 888 AND create_time > '2026-09-01';
+----+-------------+---------+------------+-------+---------------+----------+---------+-------------+------+----------+---------------------+
| id | select_type | table   | partitions | type  | possible_keys | key      | key_len | ref         | rows | filtered | Extra               |
+----+-------------+---------+------------+-------+---------------+----------+---------+-------------+------+----------+---------------------+
|  1 | SIMPLE      | t_order | NULL       | range | idx_user      | idx_user | 9       | const       |  120 |   100.00 | Using index         |
+----+-------------+---------+------------+-------+---------------+----------+---------+-------------+------+----------+---------------------+
-- 结论：type=range、key=idx_user、Extra=Using index（覆盖，零回表）
-- rows=120 小结果集。注意 key_len=9：user_id(8) + 1（可空标记），create_time 未进 key_len
-- 因为范围列只用于定位起点，若要 create_time 也消 filesort，索引需为 (user_id, create_time)

场景二：索引失效（隐式转换）

mysql> EXPLAIN SELECT * FROM t_order WHERE phone = 13800000000;
+----+-------------+---------+------------+------+---------------+------+---------+------+---------+----------+-------------+
| id | select_type | table   | partitions | type | possible_keys | key  | key_len | ref  | rows    | filtered | Extra       |
+----+-------------+---------+------------+------+---------------+------+---------+------+---------+----------+-------------+
|  1 | SIMPLE      | t_order | NULL       | ALL  | idx_phone     | NULL| NULL    | NULL | 1000000 |    10.00 | Using where |
+----+-------------+---------+------------+------+---------------+------+---------+------+---------+----------+-------------+
-- 结论：type=ALL、key=NULL、rows=100 万 = 全表扫描
-- 诊断：phone 是 VARCHAR 却传数字 → 隐式转换，索引列被函数包裹
-- 修复：WHERE phone = '13800000000'（加引号）。EXPLAIN 立刻变 ref/rows=2

场景三：无索引 JOIN（BNL/Hash）

mysql> EXPLAIN SELECT * FROM t_order o LEFT JOIN t_ext e ON o.order_id = e.order_id;
+----+-------------+-------+------------+------+---------------+------+---------+------+---------+----------+-------------------------------------+
| id | select_type | table | partitions | type | possible_keys | key  | key_len | ref  | rows    | filtered | Extra                               |
+----+-------------+-------+------------+------+---------------+------+---------+------+---------+----------+-------------------------------------+
|  1 | SIMPLE      | o     | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 1000000 |   100.00 | NULL                                |
|  1 | SIMPLE      | e     | NULL       | ALL  | NULL          | NULL | NULL    | NULL |  500000 |   100.00 | Using where; Using join buffer (hash join) |
+----+-------------+-------+------------+------+---------------+------+---------+------+---------+----------+-------------------------------------+
-- 结论：e 表 order_id 无索引 → 100 万行 × 50 万行 的匹配
-- MySQL 8.0 自动选了 hash join（小表建哈希表），比 BNL 快但仍是 O(N)
-- 修复：CREATE INDEX idx_order ON t_ext(order_id); 之后 e 变 eq_ref，总成本从 O(N) 降 O(N log N)

场景四：子查询被物化

mysql> EXPLAIN SELECT * FROM t_order WHERE user_id IN (SELECT user_id FROM t_vip_user);
+----+--------------+-------------+------------+--------+---------------+----------+---------+----------------+------+----------+--------------------------+
| id | select_type  | table       | type       | key    | key_len | ref            | rows    | filtered | Extra                    |
+----+--------------+-------------+------------+--------+---------------+----------+---------+----------------+------+----------+--------------------------+
|  1 | SIMPLE       | <derived2>  | ALL        | NULL   | NULL    | NULL           |   50000 |   100.00 | NULL                     |
|  1 | SIMPLE       | t_order     | ref       | idx_user| 9       | <derived2>.user_id |      20 |   100.00 | Using index condition    |
+----+--------------+-------------+------------+--------+---------------+----------+---------+----------------+------+----------+--------------------------+
-- 结论：子查询被物化成 derived2（临时表），外层用 ref 关联
-- Extra 的 Using index condition = ICP 生效，回表前先过滤
-- 诊断点：derived2 rows=50000 若远大于实际 VIP 数，说明统计过期或 VIP 表没 ANALYZE
-- 若 VIP 表只有 500 行但物化出 5 万行，先 ANALYZE TABLE t_vip_user 再评估
读计划的四步口诀：① 先找 type=ALL 且 rows 大 的节点——那是主要成本；② 看 key=NULL 的节点是不是本该走索引；③ 看 Extra 有没有 Using filesort / Using temporary / Using join buffer 三件套；④ 最后用 EXPLAIN ANALYZE 的 actual rows 对比 rows，偏差大就先修统计信息，别急着改 SQL。
深坑

十个线上坑

1
只看 type 不看 rows 和 filtered
type=ref 但 rows=500 万一样慢死。type 只说明访问方式，成本 = rows × 单行成本。永远把 rows × filtered 算出来看结果集大小。
2
驱动表选反：大表驱动小表
用 100 万行表驱动 10 行表，NLJ 做 100 万次索引查找。驱动表永远是过滤后行数小的那张。JOIN 顺序不对时用 STRAIGHT_JOIN 或优化器 hint 固定。
3
filesort 落盘
sort_buffer_size 默认 256KB，排 10 万行就写临时文件，多路归并慢一个量级。排序列别跨表、顺序匹配索引、必要时拆查询。
4
Using temporary：GROUP BY 建了临时表
分组顺序和索引不一致时优化器建临时表再聚合，百万行直接卡死。GROUP BY 顺序对齐索引列，或加 ORDER BY NULL 去掉多余排序。
5
NOT IN 子查询含 NULL，结果永远为空
SQL 语义：NOT IN 展开成 AND 链，遇 NULL 返回 UNKNOWN，整体空集。改 NOT EXISTS，既安全又能走 anti join。
6
隐式转换让索引失效
VARCHAR 列传数字、JOIN 列字符集不一致（utf8 vs utf8mb4），都会把索引列包进转换函数，EXPLAIN type=ALL。统一类型和字符集。
7
深翻页 LIMIT 100000,10
每翻一页多扫 10 行还多排一次序，第 100 页比第 1 页慢 100 倍。改游标（WHERE 排序列 < 上页末值 LIMIT 10）或延迟关联。
8
OR 连接导致全表扫描
WHERE a=1 OR b=2，b 无索引时整个查询 ALL。拆成 UNION ALL 各走索引；或给 b 补索引后评估 index_merge。
9
统计信息过期，优化器持续选错索引
大批量导入/删除后 cardinality 失真，好索引被弃用。ANALYZE TABLE 刷新；范围估算偏差大就 UPDATE HISTOGRAM。别用 FORCE INDEX 掩盖。
10
ORDER BY 与索引顺序差一点，filesort 就回来
索引 (user_id, create_time)，ORDER BY create_time（少了 user_id）或 ASC/DESC 混合，都无法用索引有序。排序列必须完整匹配索引列顺序和方向。
自测

六道题

1. EXPLAIN 的 type 值中，性能最差的是哪个？
正确答案：ALL。性能谱：system > const > eq_ref > ref > range > index > ALL。range 只读索引中满足条件的部分，index 扫全索引，ALL 扫全表——大表上 ALL 是最贵的访问方式。
2. Hash Join 最适合哪种场景？
正确答案：等值连接 + 大表 + 无索引。Hash Join 把小表建哈希表、大表逐行探测，一次 O(N+M)，完美绕过"没有索引就没有 NLJ"的死局。范围连接它不支持（哈希无法处理范围），那还是 NLJ 或 Merge Join。
3. Extra 出现 Using index condition 表示？
正确答案：ICP 生效。零回表是 Using index（覆盖索引）的能力。Using index condition 表示 WHERE 中索引相关条件下推到存储引擎，在页内先过滤，减少的是回表次数而非归零。
4. IN 改写为 EXISTS 的主要场景和收益是？
正确答案：小表驱动大表。等值无 NULL 时 IN 与 EXISTS 语义等价，但执行方向不同：IN 倾向内表物化、EXISTS 倾向外表逐行探测内表索引。外层小时 EXISTS 更快。注意 NOT IN 与 NOT EXISTS 在 NULL 语义下不等价，改写要小心。
5. EXPLAIN ANALYZE 相比 EXPLAIN 最大的价值是？
正确答案：真实执行数据。EXPLAIN 全是优化器的预估（基于统计信息），EXPLAIN ANALYZE 会真正执行并给出 actual time / actual rows / loops。预估 rows=42 实际 rows=50 万，说明统计信息或数据分布骗了优化器——这是排查的起点。
6. 优化深翻页 LIMIT 100000,10 的首选手段是？
正确答案：游标法。它把"跳过 10 万行"变成"从某个索引位置开始读 10 行"，offset 彻底消失，每页耗时恒定。调大 sort buffer 只是让排序不落盘，扫描量没变；force index 不改变 offset 的本质成本。
