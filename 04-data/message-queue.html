开始前

起一个能练的 Kafka 环境

Kafka 是理解 MQ 概念体系最好的载体（Topic / Partition / Consumer Group / Offset 这套词几乎成了行业通用语）。本地用 KRaft 模式（Kafka 2.8+ 起支持，用 Raft 协议替代 ZooKeeper 做元数据管理，不再依赖外部 ZooKeeper）单节点起步即可。

# docker-compose.yml —— 单节点 KRaft 模式
services:
  kafka:
    image: bitnami/kafka:3.7
    ports: ["9092:9092"]
    environment:
      KAFKA_CFG_NODE_ID: "1"
      KAFKA_CFG_PROCESS_ROLES: "broker,controller"
      KAFKA_CFG_CONTROLLER_QUORUM_VOTERS: "1@kafka:9093"
      KAFKA_CFG_LISTENERS: "PLAINTEXT://:9092,CONTROLLER://:9093"
      KAFKA_CFG_ADVERTISED_LISTENERS: "PLAINTEXT://localhost:9092"
      KAFKA_CFG_CONTROLLER_LISTENER_NAMES: "CONTROLLER"

# 启动
docker compose up -d

# 进容器敲命令（3.x 起用 kafka-*.sh 脚本）
docker exec -it <容器名> bash
kafka-topics.sh --bootstrap-server localhost:9092 --list
一个反直觉的点：Kafka 的"Topic 有多个 Partition"，Partition 才是真正的存储与并行单元，Topic 只是个逻辑名。顺序性、并行度、容量、扩展性都由 Partition 数决定 —— 这是全文反复出现的核心概念，先记住它。
阅读提示：本文用 Kafka 的概念体系讲通用原理（Partition / Offset / Consumer Group / Rebalance），遇到 RabbitMQ 等实现差异时会明确标注。术语首次出现一律就地加括注，不用回头翻术语表。
模块 1

为什么需要消息队列

MQ（Message Queue，消息队列）本质是一个带持久化的异步缓冲区。它的价值可以拆成四条，但每条都对应具体的业务痛点，不是概念口号。

价值业务例子解决什么痛点
解耦订单创建后要通知：库存、积分、风控、推荐、短信五个下游下单服务不用同步调用五个系统。加一个新下游（比如"会员等级计算"）只改消费端，下单服务零改动
削峰秒杀 10 万 QPS 涌入，数据库只能扛 2000 QPS请求先落 MQ，消费端按数据库能承受的速率（比如每秒 2000）匀速拉取。峰值被摊平成平均
异步用户上传视频后要转码，转码要 3 分钟上传接口把转码任务丢进 MQ 立刻返回，接口响应从 3 分钟降到 100ms，转码完成后回调通知
广播配置中心变更要通知 500 个服务实例刷新本地缓存发布一条消息，每个实例作为独立消费者组都收到一份（Kafka 里靠不同 group.id 实现）

但引入 MQ 也引入了四类新复杂度

这是很多教程不讲的另一半 —— MQ 不是免费的午餐，它把"同步调用的确定性"换成了"异步的不确定性"：

新引入的复杂度具体表现
一致性本地事务成功但消息没发出去，或消息发出去了本地事务回滚 —— 这就是分布式事务问题，需要本地消息表 / 事务消息 / 最大努力通知来兜底
重复消费网络抖动、消费者重启、Rebalance 都会导致同一条消息被消费多次。MQ 只能保证"至少一次"，去重必须消费端自己做
顺序错乱并发消费 + 重试会打乱消息顺序，而业务往往依赖顺序（如"下单→支付→发货"）
运维成本多了一套有状态的中间件：要监控、要扩容、要处理积压、要做容灾。MQ 本身挂了的概率远低于你的业务代码，但它挂了的后果更严重
最常见的误判："加了 MQ 系统就高可用、就解耦了"。MQ 只是把同步调用的耦合，变成了通过消息格式的隐式耦合 —— 你改了消息结构，所有消费端都可能崩。而且它把"一次请求的失败"变成了"一条消息的丢失或积压"，故障从显式变成了隐式，排查更难。引入前先问：这个场景真的需要异步吗？能接受最终一致吗？
模块 2

核心模型（用 Kafka 的概念体系）

Kafka 的模型是当前 MQ 领域的事实标准。理解下面这张表，再看任何 MQ 都能快速映射。

概念含义RabbitMQ 的对应概念
Producer 生产者发消息的一方，决定消息进哪个 PartitionProducer / Publisher
Topic 主题消息的逻辑分类，如 order-createdExchange + Queue 的组合（不直接对应）
Partition 分区真正的存储与并行单元。一个 Topic 分成多个 Partition，分布在不同 broker 上没有直接对应；Queue 更接近"单个 Partition"
Offset 偏移量消息在 Partition 内的单调递增序号，消费者用它记录"读到哪了"靠 delivery tag + ACK 机制，无全局序号概念
Consumer 消费者拉取（pull）消息的一方Consumer，但默认是推送（push）模型
Consumer Group 消费者组一组消费者共同消费一个 Topic，每个 Partition 只被组内一个消费者消费多个 Consumer 竞争消费同一 Queue
Rebalance 重平衡组内成员变化时，重新分配 Partition 归属的过程无完全对应（靠 Queue 重新绑定近似）
Broker 代理一个 Kafka 服务节点，存储 Partition 的副本Broker 节点

消费模型：Pull vs Push

Kafka 是 Pull 模型（消费者主动拉），RabbitMQ 默认是 Push 模型（Broker 主动推）。这个差异决定了积压时的行为：

# Pull 模型（Kafka）：消费者按自己的节奏拉，天然支持批量、天然背压
优点：消费者不会被压垮（自己控制速率）；支持长轮询（没数据就等一会儿）
缺点：没数据时会有空轮询开销（用 fetch.min.bytes + fetch.max.wait.ms 缓解）

# Push 模型（RabbitMQ）：Broker 主动推给消费者
优点：实时性最好，消息一到就推
缺点：消费者处理不过来时会积压在消费者内存里，需要 prefetch 限制未确认消息数
Partition 数量的三个硬约束（一定要背下来）：
① 并行度上限：一个消费者组内，同时工作的消费者数不会超过 Partition 数。10 个 Partition 最多 10 个消费者并行，第 11 个会空闲。
② 顺序性边界：Kafka 只保证 单个 Partition 内有序，跨 Partition 无序。
③ 不可减少：Partition 数只能增不能减（减少会破坏 key 的路由映射），所以初始值要估好。

主流选型对比

选型的核心是匹配场景，不是选"最强的"。四个维度定生死：吞吐量级、延迟要求、是否需要顺序/事务、团队运维能力。

延迟毫秒级（批量发送会增加延迟）微秒级，最低毫秒级毫秒级
顺序性Partition 内有序Queue 内有序支持严格顺序（顺序消息）Partition 内有序
事务消息支持（幂等 + 事务，配置较复杂）支持（AMQP 事务，性能差）原生支持事务消息，是最大卖点支持

生态最丰富（流处理 Kafka Streams / Flink 首选、CDC、Kafka Connect）成熟（AMQP 协议标准，语言客户端全）较好（国内生态好，金融场景多）中（社区相对小）

选型建议（直接给结论）

选 Kafka
日志采集、埋点、流式计算、CDC 数据同步。要吞吐和生态，能接受运维复杂度。大数据场景默认答案
选 RabbitMQ
业务量不大（万级以内）、要低延迟、要灵活的路由规则（多种 Exchange 类型）、团队运维人手少。传统业务解耦首选
选 RocketMQ
电商、金融交易，要事务消息和严格顺序，要延迟消息。国内业务系统、对 Java 生态友好的场景
选 Pulsar
多租户、要存算分离做弹性扩展、团队有较强的中间件运维能力。新项目可以考虑，但别为它增加运维负担
一句话原则：业务消息（解耦、削峰）优先 RabbitMQ 或 RocketMQ；数据管道（日志、流处理）优先 Kafka。不要用 Kafka 做"业务消息 + 延迟消息"（它原生没有延迟消息，硬做很别扭）；也不要用 RabbitMQ 扛日志（吞吐扛不住）。用错工具的代价远大于选"次优但合适"的工具。
模块 4

投递语义：至多一次 / 至少一次 / 恰好一次

这是 MQ 最核心也最容易被误解的概念。先看定义，再看为什么"恰好一次"在工程上基本是幻觉。

语义含义实现方式
至多一次
At Most Once		消息可能丢，绝不重复先提交 Offset 再处理消息。处理前崩了就丢了
至少一次
At Least Once		消息不丢，可能重复先处理消息再提交 Offset。处理成功但提交前崩了，下次会重来
恰好一次
Exactly Once		不丢也不重，各一次需要事务或幂等生产 + 消费端事务性提交。代价极高

为什么"恰好一次"在跨系统场景基本做不到

关键在于：消息的确认（提交 Offset）和你的业务处理（写数据库）是两个独立的系统，无法用一次原子操作完成。用一个经典的"两军问题"式分析：

# 顺序 A：先提交 Offset，再处理业务
提交 Offset 成功 → 此时进程崩溃 → 业务没执行 → 消息丢失（至多一次）

# 顺序 B：先处理业务，再提交 Offset
业务执行成功 → 此时进程崩溃，Offset 没提交 → 重启后重新消费 → 业务重复执行（至少一次）

# 无论哪种顺序，崩溃点都存在。根本原因是：
"业务写库" 和 "提交 Offset" 无法放在同一个事务里
（除非业务库和 MQ 共享事务，这通常不现实）
Kafka 的"Exactly Once"是有限定条件的：Kafka 的事务机制（transactional.id + isolation.level=read_committed）确实能实现"消费-处理-生产"链路内的恰好一次，但仅限 Kafka 内部流转（读 Kafka → 处理 → 写 Kafka）。一旦你的"处理"是写外部数据库或调外部 API，Kafka 的事务管不到那里，依然会重复。
工程上的正解：至少一次 + 消费端幂等。
不要再追求"MQ 层保证不重复"，那是徒劳的。正确做法是：用至少一次语义（不丢消息），然后让消费端具备幂等性（重复执行结果不变）。这样即使消息重复 100 次，业务结果也只生效一次。这是所有成熟系统的做法 —— 下文模块 5 专门讲幂等怎么设计。
模块 5

幂等与重复消费

幂等（Idempotent）指同一操作执行一次和执行多次，对系统状态的影响相同。因为 MQ 只能保证至少一次，幂等是消费端的必修课，不是可选项。

为什么会重复（重复的三个来源）

  • 消费端崩溃：处理完业务、还没提交 Offset 就挂了，重启后重新消费
  • Rebalance（重平衡）：消费者组扩缩容时，Partition 被重新分配，未提交 Offset 的消息会被新消费者重新消费
  • 生产者重试：生产者发送超时后重试，但第一次其实成功了，导致 Broker 里出现两条相同的消息

幂等键的设计（幂等的核心）

幂等键（Idempotency Key）是业务上能唯一标识"这一次操作"的字段。选得好不好直接决定幂等方案能不能落地。

幂等键来源说明与边界
业务唯一 ID最好。如订单号 order_id、支付流水号 trade_no。天然唯一，语义清晰
消息自带 ID生产者发消息时生成 UUID 放进消息头。注意：不能直接用 Kafka 的 offset（Rebalance 后可能变）
业务字段组合如 user_id + 活动_id + 日期。要保证组合确实唯一，否则会误判为重复

方案一：数据库去重表（强一致，推荐用于关键业务）

-- 建一张去重表，幂等键加唯一索引
CREATE TABLE idempotent_record (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  idem_key    VARCHAR(128) NOT NULL,
  biz_type    VARCHAR(32)  NOT NULL,
  created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_key (idem_key, biz_type)   -- 唯一约束是幂等的根本保证
);
// Java 消费端幂等模板：靠唯一索引冲突来去重
@KafkaListener(topics = "order-created")
public void onMessage(String payload) {
    OrderMsg msg = JSON.parseObject(payload, OrderMsg.class);
    String idemKey = msg.getOrderId();   // 用订单号做幂等键

    try {
        // ① 先插去重记录，唯一索引冲突会抛异常
        idempotentMapper.insert(new IdempotentRecord(idemKey, "order-created"));
    } catch (DuplicateKeyException e) {
        // ② 插入失败说明已经处理过，直接返回（幂等成功）
        log.info("重复消息，已忽略: {}", idemKey);
        return;
    }

    // ③ 首次处理，执行真正的业务逻辑
    businessService.handle(msg);
    // ④ 业务与去重记录在同一个事务里，保证原子性
}
去重表的两个边界条件：
① 去重记录必须和业务操作在同一个事务里，否则"插了去重记录但业务失败"会导致消息被永久跳过。
② 去重表会无限增长，要定期归档。或者只保留 N 天（幂等窗口期）—— 超过窗口期的重复消息极罕见，可接受。

方案二：Redis 去重（高性能，适合非关键路径）

// Redis SET NX 天然原子，适合高并发去重
String key = "idem:order-created:" + orderId;
// setIfAbsent = SET key value NX EX seconds
Boolean first = redis.opsForValue()
        .setIfAbsent(key, "1", Duration.ofHours(24));   // 24 小时幂等窗口

if (Boolean.FALSE.equals(first)) {
    log.info("重复消息，忽略");
    return;
}
businessService.handle(msg);   // 首次才执行
Redis 去重的致命弱点：Redis 不是强一致的。主从切换时，刚 SET 的 key 可能还没同步到从库就丢了，导致重复消息被再次执行。而且 Redis 的 key 过期后去重能力就消失了。
结论：资金、库存、订单状态这类关键业务必须用数据库去重表（唯一索引是硬约束）；埋点、通知、日志这类允许偶发重复的业务才用 Redis 去重。

方案三：天然幂等的写法（最优雅，但适用范围有限）

-- 不用去重表，把操作本身设计成幂等的
-- ✗ 非幂等：每次执行都 +1
UPDATE account SET balance = balance + 100 WHERE user_id = 1;

-- ✓ 幂等：设置成绝对值，执行多少次结果都一样
UPDATE account SET balance = 1000 WHERE user_id = 1;

-- ✓ 幂等：带版本号 / 状态机约束
UPDATE orders SET status = 'PAID'
WHERE order_id = 123 AND status = 'UNPAID';   -- 只有未支付才更新
-- 重复执行时 status 已是 PAID，影响行数为 0，天然幂等
三种方案的选型口诀：能用状态机约束就用状态机（零额外存储）；关键业务用数据库去重表（强一致）；高频非关键用 Redis 去重（性能好但可能漏）。真实系统里三者常常组合使用。
模块 6

顺序性保证

顺序性是个"看起来简单、做起来很贵"的需求。核心矛盾是：顺序和并行天然对立 —— 要严格全局有序，就只能串行处理，吞吐直接崩。

级别含义代价
全局有序整个 Topic 的消息严格按发送顺序被消费极高。只能单 Partition + 单消费者，等于放弃所有并行能力，吞吐降到单机下限
分区内有序同一个 Partition 内有序，跨 Partition 无序低。这是 Kafka 的默认保证，只要用对分区键就能满足绝大多数业务

用分区键（Partition Key）保证业务顺序

原理：相同分区键的消息一定进入同一个 Partition（Kafka 用 hash(key) % partition_num 决定），因此必然被同一个消费者按顺序处理。

# 关键：把"需要保证顺序的维度"作为分区键
# 场景：同一个订单的状态变更（创建→支付→发货）必须有序
producer.send(new ProducerRecord<>(
    "order-events",
    msg.getOrderId(),     // ← 分区键 = 订单号，同一订单必进同一分区
    msg
));

# 效果：
✓ 订单 A 的三条消息 → 都在 Partition 3 → 按序消费
✓ 订单 B 的三条消息 → 都在 Partition 7 → 按序消费
✓ 不同订单之间并行，吞吐不受影响

# 反例：不设分区键（或设错）
producer.send(new ProducerRecord<>("order-events", msg));
✗ 消息轮询（round-robin）进入各分区，同一订单的消息被打散 → 乱序
重试导致的乱序（最隐蔽的坑）：即使你设了分区键，如果消费者处理失败后"跳过这条、继续处理下一条"，或者把失败消息丢进重试队列稍后再处理，顺序就乱了。
正确做法：① 同一个 Partition 内串行处理，失败就阻塞（或暂停该分区），绝不跳过；② 如果必须重试，把失败消息连同它的顺序上下文一起放回原分区，而不是丢到别的队列；③ Kafka 生产者要开 max.in.flight.requests.per.connection=1（或配合 enable.idempotence=true），否则生产者重试本身就会导致乱序。
顺序性设计的三条铁律：
① 先问业务真的需要全局有序吗 —— 99% 的场景只需要"同一个实体内部有序"，用分区键就够了。
② 分区键的粒度决定并行度 —— 用订单号做键，不同订单可并行；用"地区"做键，同地区被迫串行，可能成为瓶颈。
③ 分区键变化会导致路由漂移 —— 分区数一旦增加，hash(key) % n 的结果会变，历史消息的归属分区会改变。所以扩容分区前要考虑顺序性影响。
模块 7

积压处理

消息积压（Lag，滞后量）是 MQ 运维的头号日常问题。它不可怕，可怕的是你不知道在积压，或者积压了瞎扩容。

积压的常见原因

原因表现与判断方法
消费能力不足生产速率长期 > 消费速率。看 Lag 是持续增长而非突发
消费逻辑变慢某次发版后 Lag 突增。多半是消费端加了同步 RPC 调用或慢 SQL
消费者挂了 / 卡住Lag 突然暴涨且消费端 CPU 很低。检查消费者是否假死（GC 停顿、死锁）
突发流量秒杀、大促导致生产瞬时激增。Lag 是尖峰，流量过去后能自动追上
Rebalance 频繁消费者反复上下线，每次 Rebalance 都暂停消费（Stop-The-World）。看日志里的 Rebalance 次数

监控什么指标

指标含义告警阈值建议
consumer_lag当前最新 Offset - 消费者已提交 Offset，即未消费消息数绝对值（如 > 10 万）和增长趋势都要告警
lag 增长速率单位时间 Lag 的增量，反映"追上还是落后"持续为正（如 5 分钟均值 > 0）即告警
消费耗时 P99单条消息处理耗时的 99 分位突增说明消费逻辑劣化
rebalance 次数消费者组重平衡频率频繁（如每小时 > 5 次）说明消费者不稳定
rebalance 耗时单次重平衡耗时超过几十秒说明分区太多或消费者太多
只监控"队列长度"是远远不够的。队列长度高不代表有问题（可能是正常批量），长度低也不代表没问题（可能消费端挂了但生产者也没发）。必须监控 Lag 的"变化趋势" —— 一个持续增长 10 分钟的 Lag，比一个高位稳定的 Lag 危险得多。

为什么"加消费者"不一定有效（关键认知）

# Kafka 的并行度上限 = Partition 数
Topic 有 4 个 Partition，现在有 4 个消费者，Lag 很高。

✗ 错误操作：直接把消费者扩到 10 个
结果：只有 4 个在工作，其余 6 个空转（一个 Partition 只能被组内一个消费者消费）
      Lag 一点没降，还浪费了 6 台机器

✓ 正确操作（按顺序判断）：
① 先看是不是 消费逻辑太慢 → 优化代码（批量处理、去掉同步 RPC、加索引）
② 再看 消费者数是否已达 Partition 数 → 如果到了，先扩 Partition 再扩消费者
③ 检查 是否在反复 Rebalance → 调大 session.timeout.ms / max.poll.interval.ms
④ 紧急情况用 临时消费者组跳过积压（见下）

应急手段：临时消费者组快速消化积压

起一个临时的消费者组（新的 group.id），把消费逻辑简化成"只搬运不处理"：从原 Topic 读出来，直接转发到一个新建的多分区 Topic。
把新 Topic 的分区数设为原来的 10 倍（如 4 → 40），这样就能起 40 个消费者并行搬运，快速清空积压。
再起正常业务消费者组消费新 Topic，做真正的业务处理。因为新 Topic 分区多，并行度大幅提升。
积压清完后停掉临时消费者组，恢复原有链路。注意：这个方案会打乱顺序，只适合不要求顺序的场景。

死信队列（DLQ，Dead Letter Queue）

死信队列是存放"多次重试仍失败"消息的兜底队列。它的意义是：不能让一条永远失败的消息阻塞整个分区（否则后面的消息全部堵住）。

# 消费端标准流程：重试 + 死信兜底
try {
    handle(msg);
    ack();                             // 成功，确认
} catch (RetryableException e) {     // 可重试异常（网络抖动、超时）
    if (retryCount < 3) {
        requeueWithDelay(msg, retryCount);   // 延迟重试，指数退避
    } else {
        sendToDLQ(msg);                // 超过重试上限，进死信队列
        ack();                         // 必须 ack，否则会一直重试阻塞分区
    }
} catch (FatalException e) {         // 不可重试异常（数据格式错、参数非法）
    sendToDLQ(msg);                    // 直接进死信，不浪费重试次数
    ack();
}
没有死信队列的后果（真实事故模式）：一条格式错误的消息在消费端抛异常，消费者不断重试、不断失败、永远不 ack。Kafka 里表现为"Offset 卡住不动，Lag 无限增长"，RabbitMQ 里表现为"消息无限 requeue，把消费者 CPU 打满"。整条链路因为一条坏消息彻底瘫痪。
所以：任何消费端都必须有"重试上限 + 死信兜底 + 死信告警"，缺一不可。死信队列还要有人看，否则等于没有。
模块 8

可靠性设计：消息不丢

消息可能在三个环节丢失：生产端、存储端（Broker）、消费端。要保证不丢，三个环节都得配齐，漏一个就等于白做。

环节一：生产端不丢

配置作用与边界
acks=all (-1)消息要等所有 ISR 副本都写入才算成功。可靠性最高，但延迟增加
retries发送失败自动重试次数。设大一点（如 Integer.MAX_VALUE）
enable.idempotence=true开启幂等生产者，解决重试导致的重复和乱序（Broker 用 producerId + sequenceNumber 去重）
max.in.flight.requests.per.connection开启幂等后可设 > 1 仍保证顺序；不开幂等时必须设 1，否则重试会乱序
delivery.timeout.ms发送总超时。超时后进回调，要在回调里记录失败，别静默丢弃
acks=1 的陷阱：只等 Leader 写入就返回成功。如果 Leader 刚写完就宕机、且数据还没同步到副本，消息就丢了。关键业务必须用 acks=all，配合 min.insync.replicas=2（至少 2 个副本确认才成功）。

环节二：存储端（Broker）不丢

核心靠 副本机制和 ISR（In-Sync Replicas，同步副本集合）。

机制说明
副本数 replication.factor每个 Partition 存几份。生产环境至少 3（能容忍 1 个节点故障）
ISR 同步副本集合和 Leader 保持同步的副本列表。落后太多的副本会被踢出 ISR
min.insync.replicas至少几个副本写入才算成功。配合 acks=all 使用，建议设为 2（3 副本场景）
刷盘策略 flushKafka 默认不主动刷盘，靠操作系统页缓存异步刷。靠副本而非刷盘保证可靠性。RabbitMQ 需手动设持久化队列 + 持久化消息
unclean.leader.election必须设为 false。允许非 ISR 副本当选 Leader 会丢数据，换取可用性
Kafka 的可靠性哲学与 RabbitMQ 不同：Kafka 默认不保证单机刷盘（数据在页缓存里，机器断电会丢），它的可靠性来自多副本冗余（数据在多个 broker 的内存/磁盘上）。所以 Kafka 千万不要用单副本。
RabbitMQ 则相反：默认消息在内存里，必须显式声明 durable=true（队列持久化）+ delivery_mode=2（消息持久化）+ 发布确认（publisher confirm），三者缺一不可。

环节三：消费端不丢

要点说明
先处理再提交 Offset保证"至少一次"。处理成功才提交，失败不提交（下次重来）
关掉自动提交enable.auto.commit=false。自动提交会在处理完成前就提交，处理失败也丢了
异常要有兜底处理失败要么重试要么进死信队列，不能"catch 住然后 ack"（等于丢消息）
ACK 时机RabbitMQ 用 basicAck；一定要在处理完成后手动 ack，别用 autoAck=true
端到端不丢消息的完整配置清单（Kafka 版）：
生产端：acks=all + retries=MAX + enable.idempotence=true
存储端：replication.factor=3 + min.insync.replicas=2 + unclean.leader.election.enable=false
消费端：enable.auto.commit=false + 手动提交 Offset + 死信队列
这三组配置是"消息不丢"的最低要求，缺一不可。
常见坑

十个线上坑

1
以为加了 MQ 就高可用、就解耦
MQ 把同步耦合换成了消息格式的隐式耦合，还引入了不一致、重复、顺序、积压四类新问题。引入前先确认：业务真的需要异步吗？能接受最终一致吗？
2
在消费者里做耗时操作
消费逻辑里调同步 RPC、跑慢 SQL、做大文件处理，会让单条消费耗时飙升，直接导致 Lag 爆炸。耗时操作应拆成"消费 → 落库 → 异步处理"两步。
3
没有死信队列（DLQ）
一条永远失败的消息会无限重试、永远不 ack，把整个分区的消费堵死。必须有"重试上限 + 死信兜底 + 死信告警"。
4
重试没有上限、没有退避
失败就立刻无限重试，会把下游打垮（重试风暴）。必须设重试上限，且用指数退避（如 1s、2s、4s、8s）。
5
把 MQ 当数据库用
拿 MQ 存需要长期查询、需要复杂条件检索的数据。MQ 是消息管道不是存储，消息消费完就该归档或删除。长期存储用数据库。
6
分区数设置不当
分区太少 → 并行度上不去，扩消费者无效；分区太多 → Rebalance 慢、文件句柄多、元数据开销大。一般按"预期峰值吞吐 / 单分区吞吐"估算，并留 2~3 倍余量。
7
消费端没有幂等
以为 MQ 保证不重复，结果 Rebalance 或重试导致业务重复执行（重复扣款、重复发券）。至少一次语义下，幂等是消费端的必修课。
8
只监控队列长度，不监控 Lag 趋势
长度高位稳定可能是正常的，持续增长才危险。必须监控 Lag 的"变化速率"，而不是只看绝对值。
9
生产者用 acks=1 或单副本
Leader 写完就返回成功，Leader 一挂数据就丢。关键业务必须 acks=all + replication.factor=3 + min.insync.replicas=2。
10
改了消息格式不兼容老消费端
给消息加字段、改字段类型、改语义，导致还没升级的消费端反序列化失败，整条链路崩。消息结构必须向后兼容，或用 Schema Registry 管理版本。
自测

六道题

1. 关于"恰好一次（Exactly Once）"，下列说法正确的是？
正确答案：至少一次 + 消费端幂等。根本原因是"业务写库"和"提交 Offset"无法放进同一个事务。Kafka 的事务只在"读 Kafka → 处理 → 写 Kafka"链路内有效，一旦写外部数据库就管不到了。
2. 一个 Topic 有 4 个 Partition，消费者组当前有 4 个消费者，Lag 持续增长。最不该做的操作是？
正确答案：直接扩到 12 个。一个 Partition 只能被组内一个消费者消费，消费者数超过 Partition 数时，多出来的会空转，Lag 不会下降。正确顺序是先扩 Partition，再扩消费者。
3. 要保证"同一个订单的状态变更消息按序消费"，最合理的做法是？
正确答案：用订单号作为分区键。相同 key 必进同一分区，因此按序被同一消费者处理，且不同订单之间仍可并行。全局有序（单分区单消费者）代价极高，吞吐会崩。
4. 关键业务（如资金扣减）的重复消费去重，应该用哪种方案？
正确答案：数据库去重表 + 唯一索引。Redis 主从切换时会丢 key，去重不可靠。唯一索引是数据库层的硬约束，能确保即使消息重复 100 次业务也只生效一次。
5. 关于死信队列（DLQ），下列说法正确的是？
正确答案：存放多次重试仍失败的消息，避免阻塞分区。没有死信队列，一条永远失败的消息会让 Offset 卡死、Lag 无限增长。但死信队列必须有告警，否则等于没有。
6. Kafka 要保证消息不丢，生产端的正确配置是？
正确答案：acks=all + retries 大 + 幂等生产者。acks=1 只等 Leader 写入，Leader 宕机会丢；acks=0 完全不确认。还要配合存储端 replication.factor=3 和消费端手动提交 Offset，三端齐备才真正不丢。

}
