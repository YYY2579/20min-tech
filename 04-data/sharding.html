二十分钟学透分库分表

分库分表本身不难，难在拆完之后不出事：扩容不抖动、ID 不冲突、跨分片查询不把内存打爆、迁移可回滚。这篇按"什么时候拆 → 怎么拆 → 拆完怎么办"的顺序讲。

模块 1

什么时候必须分：四个硬信号

拆分的触发条件不是"表变大了"，而是下面四个信号里至少命中两个。只看数据量很容易过度设计。

信号经验阈值为什么是它
单表行数> 1000 万行
（保守 500 万，激进 3000 万）		InnoDB 二级索引 B+ 树到 3~4 层，且 DDL（加字段/加索引）变更锁表时间从秒级涨到小时级，备份恢复时间同步变长
单库连接数活跃连接 > 500
（MySQL 默认 max_connections=151）		连接是内存 + 线程，云 RDS 的连接配额通常更小；连接打满后表现为"间歇性连不上"
写 QPS持续 > 5000
（单机写瓶颈经验值）		单机写受 redo/undo 刷盘、行锁竞争、purge 线程限制，加从库不解决写入
单实例数据量> 500 GBmysqldump 备份要 2~4 小时；xtrabackup 物理备份 30~60 分钟起；恢复时间（RTO）超出业务容忍

一组可对照的算术

# 1000 万行 × 行大小 1KB ≈ 10GB 数据
# 二级索引 idx_user：每条约 20B（8B user_id + 8B 主键 + 页开销）→ 约 200MB，树高 3 层
# 行大小涨到 4KB（宽表含 text）：1000 万行 ≈ 40GB，一页 16KB 只放 4 行，页分裂更频繁
拆之前的三条捷径（按优先级排序）：
① 读扩散：加从库做读写分离，读 QPS 问题先不拆；
② 归档：3 个月前的完成订单搬到历史库/冷存储，主表瘦身 70% 很常见，很多"该拆表"的团队其实只是没归档；
③ 垂直拆分优先于水平拆分：把大字段（text/blob）和低频字段拆到扩展表，成本低、收益立竿见影。
以上都不见效，再上分库分表。
模块 2

垂直拆分 vs 水平拆分

两个词只差一个字，但拆的对象、解决的问题、引入的麻烦完全不同。90% 的场景应该先垂直拆，水平拆是最后手段。

维度垂直拆分水平拆分（分库分表）
拆什么列 / 表：按业务域或字段访问频率拆行：按分片键把数据行分散到多库多表
解决什么库内表耦合、单库连接数耗尽、大字段拖慢整行扫描单表行数过大、单库容量/写入并发上限
不解决什么单表 2000 万行照样慢跨分片查询变复杂（这是代价不是收益）
引入复杂度跨库 JOIN、跨库事务（可用最终一致）分片键设计、跨分片查询/分页/聚合、全局 ID、分布式事务、扩容迁移
典型动作用户库 / 订单库 / 支付库分离；text 字段拆扩展表t_order 按 user_id % 16 拆成 16 张表 / 2 个库
回退成本低：合并回单库即可极高：基本不可逆
-- ===== 垂直拆分的两种形态 =====

-- 形态一：按业务域分库（微服务化同步进行）
db_user    -- t_user, t_user_addr         用户域
db_order   -- t_order, t_order_item       交易域
db_pay     -- t_pay_flow, t_refund        支付域

-- 形态二：按访问频率拆表（冷热分离，最实用）
-- 拆前：宽表含 4KB text 详情，遍历 1000 万行 ≈ 40GB，一页 16KB 只放 4 行
CREATE TABLE t_order (order_id BIGINT PRIMARY KEY, ..., detail TEXT);  -- 行大小 4KB
-- 拆后：主表瘦身到 200B/行，一页放 16 行
CREATE TABLE t_order (...);            -- 高频字段
CREATE TABLE t_order_ext (order_id BIGINT PRIMARY KEY, detail TEXT, invoice TEXT);  -- 低频字段，详情页才 JOIN
垂直拆分的头号坑：拆完之后原来一个本地事务变成两个库的分布式事务。订单创建要同时写 db_order 和 db_pay，本地事务失效。缓解手段：① 合并写入方（同一服务内串行调用 + 最终一致）；② 能用消息补偿就别上 XA；③ 对强一致场景，评估是否根本不拆这两个库。
模块 3

四种分片算法

分片算法回答一个问题：一条 order_id=12345 的数据，该去哪个库哪张表？选错算法，扩容时就要重写全量数据。

算法路由方式优点缺点
哈希取模db = key % 16数据最均匀，无热点扩容最痛苦：16→32 库时 100% 数据要重新哈希迁移
范围分片order_id ∈ [0,1000w) → 库0扩容友好（只迁边界后新增段）；范围查询天然命中单分片尾部热点：递增 ID 的写流量永远砸在最后一个分片
一致性哈希key 映射到哈希环，归最近的节点扩容只搬邻居约 1/N 的数据节点少时严重倾斜，必须配虚拟节点；实现复杂
查表法额外映射表：user_id → db_no路由规则随时可改，支持按用户等级/地域定制多一次查询（映射表自身要缓存 + 高可用）；映射表是单点

哈希取模 vs 范围分片：一张图看懂扩容代价

# 取模：2 库扩 4 库，几乎所有 key 的归属都变了
order_id=100:  100 % 2  = 0 → 旧库0    100 % 4 = 0 → 新库0   (没搬)
order_id=101:  101 % 2  = 1 → 旧库1    101 % 4 = 1 → 新库1   (没搬)
order_id=102:  102 % 2  = 0 → 旧库0    102 % 4 = 2 → 新库2   (要搬)
order_id=103:  103 % 2  = 1 → 旧库1    103 % 4 = 3 → 新库3   (要搬)
# 结论：偶数库翻倍时约 75% 数据需要迁移（1/4 留下，3/4 搬走）

# 范围：2 库扩 4 库，只把"后半段"切一刀，前两个库不动
旧: [0,5000w) → 库0, [5000w,1亿) → 库1
新: [0,2500w) → 库0, [2500w,5000w) → 库1, [5000w,7500w) → 库2, [7500w,1亿) → 库3
# 只迁移了原库1的数据，且迁移期间可灰度切换路由规则

ShardingSphere 真实分片算法（5.x 内置 SPI）

# 在 sharding-algorithms 里配置，以下均为官方内置类型
t_order_mod:            # MOD：整数取模
  type: MOD
  props:
    sharding-count: 16          -- 分 16 个逻辑单元

t_order_hash_mod:       # HASH_MOD：先哈希再取模，避免数字型 key 规律分布
  type: HASH_MOD
  props:
    sharding-count: 16

t_order_range:          # BOUNDARY_RANGE：范围分片
  type: BOUNDARY_RANGE
  props:
    sharding-ranges: 1000000,5000000,10000000   -- 4 个区间 4 个分片

t_order_inline:         # INLINE：Groovy 表达式，最灵活
  type: INLINE
  props:
    algorithm-expression: t_order_$->{order_id % 16}
    -- 库路由表达式：ds_$->{user_id % 2}

t_order_class_based:    # CLASS_BASED：自定义 SPI 实现类
  type: CLASS_BASED
  props:
    strategy: STANDARD
    algorithmClassName: com.example.MyShardingAlgorithm
算法选择的工程经验：
① 日订单量 < 100 万且未来 3 年可控 → 哈希取模，简单均匀，别为想象中的扩容提前付费；
② 按 user_id 分片是电商的默认答案（买家查订单是最高频路径，user_id 做分片键保证"我的订单"落单库）；
③ 范围分片只适合"按时间归档"的表（日志、流水），必须配好边界滚动策略，否则尾库必热；
④ 一致性哈希 + 虚拟节点主要用于缓存层和自研分库中间件，用 ShardingSphere 的话，它的定位算法（MOD 系列）已经够用。
模块 4

分布式 ID：雪花算法与号段模式

分库分表后 AUTO_INCREMENT 彻底报废：多个库各自从 1 开始，主键直接冲突。必须换发号器。雪花和号段占了生产环境的 95%，其余是 UUID 和 Redis incr。

雪花算法（Snowflake）的 64 bit 构成

┌─┬─────────────────────────────┬───────────────┬───────────────┐
│0│        41 bit 时间戳         │  10 bit 机器号 │  12 bit 序列号 │
│ │  毫秒级，可用 2^41 ms        │  2^10=1024 个  │ 2^12=4096 个   │
│ │  ≈ 69.7 年                   │   工作节点     │  每毫秒每节点   │
└─┴─────────────────────────────┴───────────────┴───────────────┘
      ↑ 永远置 0，保证 ID 为正数

# 容量算术（必须记住这组数）
单节点单毫秒最多：2^12 = 4096 个 ID
单节点每秒最多：  4096 × 1000 = 409.6 万 个 ID
全网最多：        409.6 万 × 1024 节点 ≈ 41.9 亿 个/秒
总可用时长：      2^41 ms ≈ 69.7 年（从自定义纪元起算，如 2020-01-01）
# 一个 Java 实现的时序部分（核心逻辑）
synchronized long nextId() {
  long now = currentMillis();
  if (now < lastTimestamp) {
    // 时钟回拨：NTP 同步导致时间倒退
    throw new RuntimeException("Clock moved backwards"); // 拒绝发号，阻塞等待
  }
  if (now == lastTimestamp) {
    seq = (seq + 1) & 4095;        // 同毫秒内序列号 +1，用位与实现取模循环
    if (seq == 0) { now = waitNextMillis(); }  // 4096 个用完，自旋到下一毫秒
  } else {
    seq = 0;
  }
  lastTimestamp = now;
  return (now << 22) | (workerId << 12) | seq;   // 左移 22 = 10(机器) + 12(序列)
}

号段模式（Leaf/美团 segment 方案）

-- 号段表：每个业务一行，一次取一段
CREATE TABLE leaf_alloc (
  biz_tag     VARCHAR(64)  PRIMARY KEY,
  max_id      BIGINT       NOT NULL,
  step        INT         NOT NULL,   -- 每次发放的号段长度，如 1000
  update_time TIMESTAMP    DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB;

-- 发号：一条 UPDATE 原子占用一个号段（利用行锁，天然互斥）
UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = 'order';
SELECT max_id, step FROM leaf_alloc WHERE biz_tag = 'order';
-- 拿到 [max_id, max_id+step)，在内存里逐个 +1 发放，发完再取下一段

-- 双 buffer 优化：内存常驻两个号段，后台线程提前异步加载下一段，
-- 当前段用到 10% 时触发加载，发号路径永不被 DB 延迟阻塞

四种方案横向对比

方案趋势DB 压力性能致命短板
雪花算法大致递增（同节点）零依赖百万级/秒时钟回拨导致 ID 重复或发号阻塞
号段模式递增但有跳跃极低（一次取 1000）百万级/秒依赖 DB 可用性；号段浪费（重启丢未用完的段）
UUID无序零依赖纳秒级36 字符，索引膨胀 ~9 倍，页分裂严重，不要做主键
Redis incr严格递增高（每次网络往返）十万级/秒Redis 故障丢号；持久化策略丢数据风险
选型建议：绝大多数业务用雪花（有成熟实现：百度 uid-generator、美团 Leaf、滴滴 TinyID、MyBatis-Plus 的 ASSIGN_ID）。对"ID 必须严格单调递增且连续"的场景（如财务单号展示）用号段模式。二者可以组合：号段保证趋势递增，雪花的高位塞入业务/租户标识。
模块 5

跨分片查询与聚合

拆分前一条 SQL 搞定的事，拆分后要拆成"下发 → 归并 → 二次加工"。ShardingSphere 的归并策略分三种，理解它们才能预测慢在哪。

归并类型适用 SQL原理与风险
流式归并ORDER BY ... LIMIT各分片按索引有序返回，中间件做堆归并逐条出数。内存 O(分片数)，不会爆
内存归并GROUP BY / DISTINCT各分片全量结果拉回内存，用 HashMap 聚合。分片数 × 结果集大时直接 OOM
装饰者归并LIMIT把 limit 改写下推（limit 100000,10 → 各分片 limit 100010,10 再归并），数据量随 offset 线性涨

问题一：按非分片键查订单（最经典）

-- 场景：t_order 按 order_id % 16 分片，现在要按 user_id 查
SELECT * FROM t_order WHERE user_id = 888;

-- 方案 A：全分片扫描 + 归并（16 次查询，慢，仅适合低频后台）
-- 方案 B：二级索引冗余（推荐）—— 维护一张按 user_id 分片的索引表
CREATE TABLE t_order_idx_user (
  user_id  BIGINT,
  order_id BIGINT,
  PRIMARY KEY (order_id),
  KEY idx_user (user_id)
) ;  -- 按 user_id % 16 分片，查到 order_id 后再回订单库精确查

-- 方案 C：基因法（把 user_id 的低位嵌入 order_id）
-- 构造：order_id = (seq << 4) | (user_id % 16)
-- 查询：用 user_id % 16 推出分片号，同时从 order_id 中也能推出 user_id 的分片基因
-- 好处：order_id 和 user_id 两个维度都能定位到同一分片，避免跨库

问题二：跨库 JOIN

-- 反例：订单和订单项分在不同库，中间件做笛卡尔积再过滤
SELECT o.*, i.product_id FROM t_order o JOIN t_order_item i ON o.order_id = i.order_id;

-- 正解一：绑定表（bindingTables）—— 两个表用相同分片键 + 相同算法，
-- 中间件知道 o 和 i 一定在同库同号表，JOIN 下推到单库完成，零跨库
-- 正解二：应用层拆两次单库查询，在内存里 Map 关联
SELECT * FROM t_order WHERE user_id = 888;      -- 第 1 次：命中 1 个分片
SELECT * FROM t_order_item WHERE order_id IN (...) -- 第 2 次：命中 1 个分片

-- 正解三：全局表（broadcastTables）—— 字典表 t_dict 冗余到每个库，
-- JOIN t_dict 时本地完成，不需要跨库

问题三：深分页

-- 反例：offset 越大越慢，且慢得和分片数成正比
SELECT * FROM t_order ORDER BY create_time DESC LIMIT 100000, 10;
-- 16 个分片各取 100010 行 = 160 万行拉回内存归并，P99 直接几百毫秒到秒级

-- 正解：游标法（书签/延迟关联），把 offset 转成索引范围条件
SELECT * FROM t_order
WHERE create_time < '2026-10-16 23:59:59'   -- 上一页最后一条的时间
ORDER BY create_time DESC LIMIT 10;                -- 每次只取 10 行，offset 消失
聚合查询三条军规：① count(*)、sum() 跨分片会把各分片结果集全拉回内存，亿级表一次就能让中间件 OOM，能预聚合到汇总表就预聚合；② 任何 LIMIT 大 offset 都改书签/游标；③ 全局唯一键（如 user_phone 唯一索引）在分片后失效——同一手机号落到两个库都能插入成功，需要映射表路由或全局索引服务兜底。
模块 6

分布式事务：XA / Saga / TCC / 最终一致

分库之后，"订单创建同时写订单库和支付库"这种本地事务就没了。四种方案的取舍本质是用一致性换性能，还是用性能换一致性。

方案原理一致性性能侵入性适用场景
XA/2PCprepare + commit 两阶段，协调者统一提交强一致差（同步阻塞）低遗留系统、并发低、 legacy 改造
Saga长事务拆成本地事务序列，失败时逐个执行补偿最终一致好中长流程（旅行预订、开户流程）
TCCTry 预留资源 / Confirm 确认 / Cancel 释放最终一致
（接近强一致）		好高（每个服务三个接口）短平快、高并发、资源明确（库存/余额）
消息+对账本地事务写消息表，投递后消费，定时对账补偿最终一致最好低互联网默认选择，可接受秒级延迟

MySQL XA 的真实命令序列

-- 一个跨两库的转账：扣款库 + 入账库
-- 阶段一：各分支 prepare
XA START 'xa_db1_1';
UPDATE account SET balance = balance - 100 WHERE user_id = 1;  -- 库1
XA END 'xa_db1_1';
XA PREPARE 'xa_db1_1';        -- 此时库1 已持久化但未提交，资源锁定

XA START 'xa_db2_1';
UPDATE account SET balance = balance + 100 WHERE user_id = 2;  -- 库2
XA END 'xa_db2_1';
XA PREPARE 'xa_db2_1';

-- 阶段二：全部 prepare 成功才提交，任一失败则全部 rollback
XA COMMIT 'xa_db1_1';  XA COMMIT 'xa_db2_1';
-- 或：XA ROLLBACK 'xa_db1_1'; XA ROLLBACK 'xa_db2_1';

-- 关键风险：prepare 之后协调者宕机，分支事务悬挂，资源一直锁着。
-- 必须配 XA RECOVER（MySQL 自动）或 seata 的 TC 侧定时回查
XA RECOVER;   -- 查看处于 PREPARED 状态的分支

TCC 的三个阶段（以扣库存为例）

-- Try：预留资源，不动最终状态
UPDATE stock SET frozen = frozen + 10 WHERE sku = 'A001';  -- 可用量不动

-- Confirm：确认扣减，把预留转正式（要求幂等，靠事务流水号去重）
UPDATE stock SET frozen = frozen - 10, sold = sold + 10 WHERE sku = 'A001';

-- Cancel：释放预留（同样幂等）
UPDATE stock SET frozen = frozen - 10 WHERE sku = 'A001';

-- 三个接口都要做幂等：INSERT INTO tcc_tran(xid, status) 先查再插
-- 空回滚（Try 没执行就 Cancel）、悬挂（Cancel 先于 Try 到）都要防护

最终一致性：本地消息表

-- 同一个本地事务里：写业务数据 + 写消息（这是原子性的关键）
START TRANSACTION;
INSERT INTO t_order (...) VALUES (...);
INSERT INTO t_local_msg (id, payload, status) VALUES (uuid, '{"orderId":100}', 0);
COMMIT;

-- 定时任务扫描未发送消息投递 MQ，成功后标记 status=1；消费方幂等；每日对账补偿异常
落地顺序建议：先上消息 + 对账（成本最低、性能最好、能扛住 99% 场景）；资金类强一致且低并发的老系统短期用 XA（如 Seata 的 XA 模式）过渡；库存、余额这种资源明确的场景，量大了再升级 TCC；跨多家外部系统（航司、酒店）的长流程才考虑 Saga。Saga 没有隔离性，中间态会被其他事务读到，设计时必须接受这个事实。
模块 7

扩容：双写迁移 / 预分片 / 一致性哈希

扩容是分库分表生命周期里最危险的动作，比拆分本身危险。三条路线，按"事前准备成本"从低到高排。

路线一：预分片（事中零成本，强烈推荐）

# 一开始就按最大规模分逻辑表，例如 2 库 × 512 表 = 1024 张逻辑表
# 实际只部署 2 个库，每库 512 张表，大部分表是空的（空表只有结构，无数据）
#
# 扩容 2→4 库时：
#   1. 新库执行 512 张空表的 DDL
#   2. 路由规则从 user_id % 1024 映射到 2 库，改为按 1024 个分片重新分配
#   3. 逐分片迁移：把分片 512~1023 的数据搬到新库，双写校验后切流
# 全程不需要改一条业务 SQL，也不需要重新哈希已有数据

# 为什么是 1024 而不是 1000：1024 = 2^10，翻倍扩容时分片数成整数倍（2/4/8/16 整除），
# 取模映射无歧义；1000 拆 4 份会出现 250 这种不均匀边界

路线二：双写迁移（事后扩容的标准动作）

全量同步：用 mysqldump/xtrabackup 把旧库数据导入新库；导入期间产生的增量用 binlog（Canal/Debezium）回放追平
双写：业务写请求同时写新旧两套库。注意双写不是事务的——先写新成功、写旧失败要靠补偿队列重试，反之亦然
校验：比对两边条数、checksum（如每表 CRC32 聚合）、抽样逐字段比对。校验不通过必须先修数据再往下走
切读：读流量灰度切到新库，观察错误率和延迟，旧库保留只读兜底
切写：写流量切新库，此时旧库停写；保留双写窗口若干天作为回滚余地
下线：确认无回滚需求后旧库归档，双写代码摘除
# binlog 增量回放的关键配置（旧库）：必须是 ROW 格式、row_image=full
SET GLOBAL binlog_format = 'ROW';
# 全量开始时记录 SHOW MASTER STATUS 的 File+Position，导入完成后从该点追增量

路线三：一致性哈希 + 虚拟节点

# 环上 2^32 个点，key 哈希后顺时针找第一个节点
# 4 个物理节点无虚拟节点时实测负载比可达 3:1；每节点拆 150~200 个虚拟节点后方差 < 10%
# 扩容只影响"新节点逆时针到下一个虚拟节点之间"的数据：4→5 节点搬约 1/5，取模要搬 3/4
# Redis Cluster 思路不同：固定 16384 个哈希槽按槽迁移，本质是查表法
扩容期最大风险不是技术是组织：双写期间两套库都可能短暂不一致，校验窗口要覆盖至少一个完整业务周期（如月末结账）。历史上多数扩容事故都死于"校验 3 天觉得没问题就切了，结果月底对账发现漏单"。另外，扩容后必须重新 ANALYZE TABLE，否则新库统计信息为空，优化器直接选错索引。
模块 8

ShardingSphere / MyCAT 生态与真实配置

产品形态语言支持定位与注意点
ShardingSphere-JDBC客户端 Jar 包仅 Java无代理层、性能最好；额外占用应用资源；升级要跟应用发版
Sharding-Proxy独立代理服务任意（MySQL 协议）对应用透明、多语言可用；多一跳网络延迟；自身要高可用部署
MyCAT独立代理服务任意（MySQL 协议）老牌分库中间件（Cobar 后继），1.6 之后社区活跃度下降，新项目不建议
Seata事务协调者 TCJava 为主配合上面任一分库方案补上分布式事务（AT/XA/TCC/Saga 四种模式）

databaseName: sharding_db

dataSources:
  ds_0:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource

    username: app
    password: app123
  ds_1:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    driverClassName: com.mysql.cj.jdbc.Driver
    jdbcUrl: jdbc:mysql://10.0.0.2:3306/ds_1?serverTimezone=UTC&useUnicode=true
    username: app
    password: app123

rules:
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_${0..1}.t_order_${0..15}
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: db_inline
        tableStrategy:
          standard:
            shardingColumn: order_id
            shardingAlgorithmName: tbl_inline
        keyGenerateStrategy:
          column: order_id
          keyGeneratorName: snowflake
      t_order_item:
        actualDataNodes: ds_${0..1}.t_order_item_${0..15}
        databaseStrategy:
          standard:

            shardingAlgorithmName: db_inline
        tableStrategy:
          standard:
            shardingColumn: order_id
            shardingAlgorithmName: tbl_inline

    # 绑定表：两个表分片键和算法一致，JOIN 时路由到同库同号表，避免笛卡尔积
    bindingTables:
      - t_order, t_order_item

SELECT * FROM t_order WHERE user_id = 888;
# 中间件改写为（可用 sql-show 验证）：
# SELECT * FROM ds_0.t_order_8 WHERE user_id = 888;
# 推导：user_id % 2 = 0 → ds_0；order_id 若=888 则 888 % 16 = 8 → t_order_8
什么时候别用中间件：分片数很少（2 库 4 表）、SQL 模式非常固定时，自己在 DAO 层"计算分片号 → 拼表名"只要几十行代码。中间件的价值在治理（监控、限流、加密、影子库），不在分片本身。
深坑

十个线上坑

1
用自增主键当分片键
ID 递增等于时间递增，写流量永远砸在最后一个分片（尾库热点）；且多库各自 AUTO_INCREMENT 会撞主键。必须换雪花/号段全局 ID，再考虑分片。
2
一致性哈希不加虚拟节点
4 个物理节点直接上环，实测负载比能到 3:1，一个节点打满其他在乘凉。每个物理节点至少配 150~200 个虚拟节点才能把方差压进 10%。
3
扩容只加机器，忘了搬数据
新节点空跑、旧节点继续打满，监控上"扩容了但没完全扩容"。一致性哈希方案要主动触发再平衡；预分片方案要按分片逐个迁移并切流。
4
跨库 JOIN 直接下发
中间件遇到跨库 JOIN 会做笛卡尔积再内存过滤：2 库 × 10 万行 = 10 亿次比对，直接把应用拖死。要么配 bindingTables，要么拆成两次单库查询在内存关联。
5
深分页 limit 100000,10
每个分片都要返回 100010 行再归并，16 分片 = 160 万行回内存。改成书签/游标：WHERE create_time < 上一页最后一条 LIMIT 10，offset 消失。
6
双写迁移只写新不写旧
切回旧链路时发现丢了几个月数据，而旧链路往往还挂着别的报表任务。双写期必须双向可回滚，且全量校验（条数 + checksum + 抽样）通过后才能切流。
7
雪花算法时钟回拨
NTP 同步让机器时间倒退 2 秒，序列号复用产出重复 ID，直接造成主键冲突或数据覆盖。对策：回拨 < 阈值等待重试、> 阈值拒绝发号并告警、或准备备用 workerId 段。
8
字典表没做广播表，大表误配成广播表
t_dict 这种小字典表没配 broadcastTables，每次 JOIN 都跨 16 个库；反过来把千万级大表误配成广播表，会在每个库都冗余一份，磁盘和同步直接爆。
9
以为唯一索引分片后还有全局约束力
user_phone 的唯一索引只在单库内生效，两个用户同手机号落到不同库都能插入成功，脏数据事后极难清理。要么路由到同库（查表法），要么维护全局唯一索引服务。
10
count(*) / sum() 跨分片全量归并
各分片结果集全部拉回中间件内存做聚合，亿级表一次查询 OOM。能预聚合到汇总表就预聚合；必须实时的用游标分批拉取，别一次全量归并。
自测

六道题

1. 单表 800 万行、读多写少、从库也扛不住了。按优先级，第一个该做的动作是？
正确答案：先归档 + 垂直拆分。水平拆分是不可逆的单向门，应该最后做。读扩散优先加从库和缓存，容量问题优先归档冷数据，大字段拖慢扫描就垂直拆。三条捷径都无效才上分库分表。
2. 一致性哈希中"虚拟节点"的核心作用是？
正确答案：缓解数据倾斜。物理节点少时环上位置随机性差，负载比可达 3:1；每节点拆出 150~200 个虚拟节点后方差可压到 10% 以内。减少迁移量是一致性哈希本身（相比取模）的特性，不是虚拟节点的功劳。
3. 雪花算法中，12 bit 序列号决定了单节点单毫秒最多产生多少个 ID？
正确答案：4096 个。2^12 = 4096，即单节点每秒上限约 409.6 万个 ID。1024 是 10 bit 机器号的上限（节点数），65536 是 2^16，都不对。
4. t_order 按 order_id % 16 分片，现在要支持"按 user_id 查订单列表"，最常用的方案是？
正确答案：二级索引冗余（或基因法）。全分片扫描在 16 库 × 大表时代价不可接受；重新生成历史 ID 不可能。基因法是索引冗余的变体：把 user_id 的低位嵌进 order_id，两个维度都能定位同分片。
5. TCC 分布式事务的三个阶段是？
正确答案：Try-Confirm-Cancel。Try 预留资源、Confirm 确认执行、Cancel 释放预留。Commit/Rollback 是 XA 的词汇；Begin-Prepare-Commit 是 2PC 的词汇。三个接口都必须幂等，还要防空回滚和悬挂。
6. 预分片方案（如一次分 1024 张逻辑表）的主要好处是？
正确答案：扩容零改造。事前把路由格子打满（1024=2^10，翻倍整除友好），扩容只是把某些分片搬到新库，SQL 和路由逻辑一行不改。代价是早期要维护大量空表结构，以及单表行数被 1024 除过之后更小。

术语表

术语一句话解释
垂直拆分按列/业务域拆库拆表，解决耦合和单库容量，行数不降
水平拆分按分片键把行分散到多库多表，解决行数和写并发
分片键决定数据路由到哪个分片的列，选错全盘皆输
哈希取模key % N 路由，最均匀但扩容要重哈希
范围分片按 key 区间路由，扩容友好但有尾库热点
一致性哈希环上顺时针找节点，扩容只搬约 1/N 数据
虚拟节点物理节点在环上的多个副本，用于均衡负载
查表法用额外映射表决定路由，灵活但多一次查询
基因法把分片基因嵌进 ID，使多个维度都能定位同分片
绑定表分片键与算法一致的表组，JOIN 可下推到单库
广播表字典表在每个库冗余一份，JOIN 本地完成
雪花算法1+41+10+12 bit 的发号器，单节点 409.6 万 ID/秒
号段模式一次从 DB 取一段号在内存发放，双 buffer 消除阻塞
时钟回拨机器时间倒退导致雪花 ID 重复或阻塞发号
XA / 2PCprepare + commit 两阶段，强一致但同步阻塞
Saga长事务序列 + 补偿回滚，无隔离性
TCCTry-Confirm-Cancel，业务层实现，性能好侵入强
本地消息表业务与消息同事务写入，异步投递 + 对账补偿
双写迁移新旧库同时写、校验后切流的扩容标准动作
预分片事前打满逻辑分片格子，扩容只搬数据不改路由
