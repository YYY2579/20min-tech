二十分钟学透 RabbitMQ

RabbitMQ 难的不是发消息，是不丢消息、不重复、不堆积。这篇的重点是 AMQP 0-9-1 模型、确认机制、死信与延迟消息、Quorum 队列，以及生产环境最常见的六个事故点。

模块 1

AMQP 0-9-1 模型：消息怎么流动

AMQP 0-9-1 的核心模型就一句话：生产者从不直接发消息给队列，而是发给 exchange，由 exchange 按 binding 规则路由到队列。

Producer 发消息：指定 exchange 名、routing key、消息体（headers + body，body 是不透明的字节数组）
Exchange 查 bindings：每个 binding 记录"什么 routing key 的规则对应哪个队列"，exchange 按类型匹配，把消息副本投递到每个匹配的队列
Queue 暂存：消息在队列里排队，等消费者来取。队列可以绑定多个 exchange，一个 exchange 也可以绑定多个队列
Consumer 消费并 ack：确认后 broker 才删除消息；不确认就重新投递
组件关键事实
ConnectionTCP 连接，建立成本高（TCP 握手 + AMQP 协商）。一个连接可开多个 channel
Channel复用连接的逻辑通道，不是线程安全的。每个线程一个 channel，不要跨线程共享。绝大多数报错发生在 channel 上
Exchange只做路由不存消息。默认有一个 direct 类型的匿名 exchange（名为 ""），routing key 等于队列名时直投该队列
Bindingexchange 与 queue 的绑定关系，可带额外参数（headers exchange 的 x-match 等）
Queue真正存消息的地方。durable 队列的元数据持久化，消息是否持久化看 delivery_mode
Routing key生产者给的字符串。direct 精确匹配、topic 通配匹配、fanout 忽略、headers 匹配消息头
# 用 CLI 验证模型（等价于管理界面里的 bindings 页）
rabbitmqctl list_exchanges name type messages_in
rabbitmqctl list_bindings source_name source_kind destination_name routing_key
rabbitmqctl list_queues name messages messages_ready messages_unacknowledged consumers
和 Kafka 的本质区别（选型先想清楚）：RabbitMQ 是智能 broker、哑消费者——broker 决定消息给哪个消费者，消费完就删除，擅长复杂路由和按序分发；Kafka 是哑 broker、智能消费者——消息按 offset 顺序保留，消费者自己管理进度，擅长高吞吐回放。要"多条业务线复杂路由、单消息确认、延迟/死信"选 RabbitMQ；要"百万 TPS、事件回放、流处理"选 Kafka。
模块 2

Exchange 四种类型与通配规则

类型匹配规则典型场景
directrouting key 完全相等才投递点对点任务分发：按 order.created 精确路由到订单队列
topic通配匹配：* 匹配一个词，# 匹配零或多个词（词以 . 分隔）发布订阅：order.*.paid、log.# 收全部日志
fanout忽略 routing key，广播给所有绑定队列广播配置变更、群发通知
headers不看 routing key，匹配消息头；x-match: all 全匹配 / any 任一匹配多条件复杂路由（较少用，topic 通常够）
# topic 通配实例：消息 routing key = "order.cn.paid"
绑定 "order.*"        # ✓ 命中（* 匹配 "cn"）
绑定 "order.cn.#"     # ✓ 命中（# 匹配 "paid"）
绑定 "order.#"        # ✓ 命中
绑定 "*.paid"         # ✗ 不命中（* 不能跨 . 匹配 "order.cn"）
绑定 "order.cn.paid"  # ✓ 精确相等也命中（topic 包含 direct 行为）

# headers 实例：x-match=all 时，绑定参数必须全部出现在消息头里
绑定参数：{"x-match":"all","format":"pdf","type":"report"}
消息头带 format=pdf 且 type=report 才投递

# 用 CLI 手工建 binding 验证路由
rabbitmqctl set_permissions -p / app ".*" ".*" ".*"
rabbitmqadmin declare exchange name=order.topic type=topic
rabbitmqadmin declare queue name=q.paid durable=true
rabbitmqadmin declare binding source=order.topic destination=q.paid routing_key="order.*.paid"
一个高频错误： unroutable 消息静默丢失。direct/topic exchange 找不到匹配的 binding 时，消息直接丢弃，生产者不报错（除非开了 publisher confirm 也看不到路由失败的特殊处理——3.x 之后 confirm 只保证"到达 exchange"）。解法：① 开 alternate-exchange（备份 exchange，收容无法路由的消息）；② 生产者开 mandatory 标志 + returns 回调；③ 上线前用 rabbitmqctl list_bindings 核对 binding 拼写。
模块 3

消息确认机制：三道防线

消息丢失只发生在三个环节：生产者→broker、broker 自身、broker→消费者。每个环节都有对应机制，但都要显式开。

防线一：Publisher Confirm（生产者确认）

# 原理：channel 进 confirm 模式后，broker 每收到（持久化）一条消息回一个 confirm
channel.confirmSelect()                        # 开启 confirm 模式

# 两种确认方式：
# 1. 同步等待：每条消息 waitForConfirms，简单但吞吐低（每条一个 RTT）
# 2. 异步回调（推荐）：批量 confirm，维护"已发送未确认"序号集合
channel.addConfirmListener(
  (sequenceNumber, multiple) -> { /* ack：从待确认集合移除 */ },
  (sequenceNumber, multiple) -> { /* nack：重发或记日志告警 */ }
);

# mandatory + returns：路由不到队列时触发的回调（publisher confirm 不覆盖这个）
channel.addReturnListener((replyCode, replyText, exchange, routingKey, properties, body) -> {
  log.error("消息无法路由: exchange={}, routingKey={}", exchange, routingKey);
});

防线二：Broker 侧持久化

# 三个条件同时满足，重启才不丢消息：
1. queue 声明为 durable = true          # 队列元数据持久化
2. 消息 properties.deliveryMode = 2      # PERSISTENT，消息体持久化
3. 消息落盘：默认异步刷盘；需要更强保证用 quorum 队列（Raft 多数派落盘才算提交）

# 声明持久化队列 + 发持久化消息（Java 客户端）
channel.queueDeclare("order.paid", true, false, false, null);
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
    .deliveryMode(MessageProperties.PERSISTENT_TEXT_PLAIN.getDeliveryMode())
    .contentType("application/json").build();
channel.basicPublish("order.topic", "order.cn.paid", props, body);

防线三：Consumer Ack（消费者确认）

模式行为风险
auto ack
（autoAck=true）		消息一出队就视为确认处理中崩溃 = 消息丢失。只适合可容忍丢失的场景（日志上报）
manual ack业务处理完调 basicAck生产必须用。忘记 ack 会导致消息一直 unacked，队列只进不出
nack / rejectbasicNack(requeue=false) 或配合死信requeue=true 处理失败会立即重投，可能死循环打满 CPU
# prefetch / QoS：限制通道上未确认消息的数量（关键参数）
channel.basicQos(10);        # 最多 10 条未 ack，处理完才会推新的
channel.basicQos(10, true);  # 第二个参数 global=true 对整个连接生效（3.x 已废弃，用 channel 级）

# prefetch 设多少合适？
# 设 1：慢速处理（每条几十 ms）且要严格顺序时
# 设 10~50：常规业务，平衡吞吐与重试粒度
# 设 0（无限）：prefetch 关闭，broker 会一次性推完全部消息，容易 OOM 和堆积
prefetch 太大会埋两个雷：① 所有消息被推到一个消费者变成 unacked，该消费者崩溃后全部消息重新排队，其他消费者闲着；② 内存里堆几百 MB 未确认消息，触发 vm_memory_high_watermark 流控。默认值 0（无限）是反模式，Spring Boot 里通过 spring.rabbitmq.listener.simple.prefetch 显式设置。
模块 4

死信队列（DLX）

死信 = 被 broker 判定"这个消费者处理不了"的消息。DLX 是给死信准备的另一条出路，是 RabbitMQ 做重试和兜底的基石。

消息变成死信的三种条件

  1. 消费者 basicNack / basicReject 且 requeue=false（显式拒绝）
  2. 消息 TTL 到期（队列级 x-message-ttl 或消息级 expiration）
  3. 队列满：超过 x-max-length / x-max-length-bytes，队头消息被挤出

声明方式（在队列参数里指定，不是 exchange 自己）

# 声明一个带 DLX 的业务队列
Map<String,Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "dlx.exchange");
args.put("x-dead-letter-routing-key", "order.retry");   # 不写则沿用原 routing key
channel.queueDeclare("order.paid", true, false, false, args);

# 死信队列本身 + 它的 exchange 要单独声明
channel.exchangeDeclare("dlx.exchange", "direct", true);
channel.queueDeclare("order.retry.q", true, false, false, null);
channel.queueBind("order.retry.q", "dlx.exchange", "order.retry");

# CLI 等价操作
rabbitmqctl set_policy -p /prod dlx ".*" \
  '{"dead-letter-exchange":"dlx.exchange","message-ttl":60000}' --apply-to queues
DLX 最实用的组合：TTL 阶梯重试。业务队列（30s TTL + DLX）→ 重试队列 A（1min TTL + DLX）→ 重试队列 B（5min TTL + DLX）→ 死信兜底队列（人工处理/告警）。消息每次消费失败就 nack(requeue=false)，在各级队列里躺够时间后回到业务队列。注意这是"近似延迟"：RabbitMQ 的 TTL 过期检查是周期性的，且只有消息到达队头才检查，同队消息不按个体 TTL 排序。
死信循环陷阱：死信队列又绑回原 exchange 时，消息可能无限循环变死信。务必在最后一层设 x-dead-letter-exchange 为空或指向一个"墓碑队列"（如 order.dead 只告警不再投递）。另外死信消息会在 headers 里带上 x-death 数组，记录了每次死亡的原因、队列、时间，排查时用 rabbitmqctl list_queues 看不到，要在管理界面或消息详情里看。
模块 5

延迟消息：两种实现路线

RabbitMQ 原生不支持任意延迟，工程上就两条路：插件、或 TTL+DLX 组合。

方案原理取舍
rabbitmq_delayed_message_exchange 插件
（推荐）		exchange 类型声明为 x-delayed-message，消息头带 x-delay（毫秒），broker 的 mnesia 存储到期时间，到期后按路由键投到目标 exchange延迟精确到消息级，无队头阻塞；插件与集群镜像模式不兼容，仅支持持久化消息，升级需验证插件兼容性
TTL + DLX 组合队列级 TTL 到期 → 进 DLX → 业务队列零依赖；队头阻塞：队列按队头 TTL 检查，头部没到期后面的都卡着，只适合同一延迟时间的批量
消息级 expiration + DLX每条消息单独设 TTL看似灵活，但过期消息不重排队：后到的短 TTL 消息必须等前面长 TTL 消息到期才检查，队头阻塞更严重
# 启用延迟插件（3.8+ 版本自带，社区插件需单独下载匹配版本）
rabbitmq-plugins enable rabbitmq_delayed_message_exchange
rabbitmqctl list_enabled_plugins | grep delayed     # 确认已启用

# 声明延迟 exchange（Java）
Map<String,Object> args = new HashMap<>();
args.put("x-delayed-type", "direct");              # 内部按 direct 规则路由，可选 fanout/topic/headers
channel.exchangeDeclare("order.delay", "x-delayed-message", true, false, args);

# 发一条延迟 30 秒的消息
AMQP.BasicProperties props = new AMQP.BasicProperties.Builder()
    .headers(Map.of("x-delay", 30000))
    .deliveryMode(2).build();
channel.basicPublish("order.delay", "order.paid", props, body);

# 用 rabbitmqadmin 声明（CLI）
rabbitmqadmin declare exchange name=order.delay type=x-delayed-message \
  arguments='{"x-delayed-type":"direct"}'
三个必须知道的延迟消息事实：① 延迟消息必须持久化（deliveryMode=2），否则插件不生效；② 延迟 exchange 的消息存在 mnesia 表里，节点重启后已入队的延迟消息仍然有效（3.8+ 做了持久化），但插件必须在新节点同样启用；③ 高精度延迟（秒级以下）或超长延迟（小时/天）都不适合用消息队列，前者用定时任务轮询，后者直接用数据库状态机 + 调度。
模块 6

镜像队列与 Quorum 队列

这是 RabbitMQ 3.8 之后最大的架构变化，也是升级时最容易踩的坑。

对比项经典镜像队列
（classic mirrored）		Quorum 队列
实现主队列 + 若干镜像从，主挂了一个从被提升为主基于 Raft 共识协议，日志复制，多数派写入即提交
声明方式queue type=classic + policy ha-modex-queue-type: quorum（策略或队列参数）
一致性异步复制，主从切换可能丢消息、可能脑裂强一致：多数派确认才算成功，故障切换不丢已确认消息
性能快（异步），但同步阻塞模式（ha-sync-mode=automatic）下慢比经典队列慢（共识开销），但比同步镜像队列快且稳
适用场景临时/非关键队列所有生产队列的默认选择
# 经典镜像队列配置（3.13 起已废弃，仅维护不支持新特性）
rabbitmqctl set_policy -p /prod ha-all "^order\." \
  '{"ha-mode":"all","ha-sync-mode":"automatic","ha-promote-on-failure":"when-synced"}'

# Quorum 队列（推荐）
rabbitmqctl set_policy -p /prod qq "^order\." \
  '{"queue-type":"quorum","delivery-limit":5}' --apply-to queues

# 也可以用 x-queue-type 声明单个 quorum 队列
Map<String,Object> args = Map.of("x-queue-type", "quorum");
channel.queueDeclare("order.paid", true, false, false, args);
版本事实（2024 年起）：RabbitMQ 3.13 正式废弃经典队列镜像（deprecated），官方建议全部迁移到 Quorum 队列；4.0/4.1 起经典镜像队列进入移除倒计时，新集群请直接用 Quorum 队列。从镜像迁移到 Quorum 的方法：建新 quorum 队列 → 双写/ shovel 同步 → 切换 → 删旧队列。Quorum 队列还有两个好用的机制：delivery-limit（消息重复投递上限，达到后自动进死信，专治毒消息）和 at-least-once 保证（消费端仍要幂等）。
3.13 起还推出了 Stream 队列（append-only 日志，类 Kafka 语义，支持回放），适合大吞吐事件流场景；以及 Khepri（替代 mnesia 的元数据存储，4.x 可选启用）。常规业务队列仍然用 Quorum。
模块 7

集群、高可用与流控水位

集群基本事实

  • RabbitMQ 集群不共享队列内容：队列在哪个节点创建就存在哪个节点，其他节点只有元数据。客户端连任何节点都能收发全集群的队列（节点间转发）
  • 所有节点必须用同一个 Erlang Cookie（/var/lib/rabbitmq/.erlang.cookie），不一致直接加入失败
  • 元数据（队列/exchange/binding 定义）全集群同步；队列里的消息不做分片——所以单队列吞吐上限由所在节点决定
  • Quorum 队列的成员分布在多个节点，用 Raft 保证多数派存活即可用
# 组集群（三节点示例）
rabbitmqctl stop_app
rabbitmqctl join_cluster rabbit@node1     # 加入已有集群
rabbitmqctl start_app
rabbitmqctl cluster_status                # 查看集群成员与角色

# 节点下线维护：先摘除流量再停
rabbitmqctl forget_cluster_node rabbit@node3   # 在别的节点上执行

内存与磁盘水位（生产事故第一大来源）

配置默认值行为
vm_memory_high_watermark0.4（物理内存 40%）超过后触发 alarm，阻塞所有生产者连接，消费者继续。生产常调 0.6
disk_free_limit50MB磁盘剩余低于此值触发 alarm，同样阻塞生产者。50MB 太小，必须调大（如 2GB 或相对值）
disk_free_limit_relative1.0（乘内存）相对内存的比例，比绝对值更稳
# 调水位（重启不丢，写进 rabbitmq.conf 更稳）
rabbitmqctl set_vm_memory_high_watermark 0.6
rabbitmqctl set_vm_memory_high_watermark absolute 4GB     # 或绝对值
rabbitmqctl set_disk_free_limit 2GB
rabbitmqctl set_disk_free_limit_relative 2.0              # 相对值：2 倍内存

# rabbitmq.conf 写法
vm_memory_high_watermark.relative = 0.6
disk_free_limit.absolute = 2GB

# 查当前告警
rabbitmq-diagnostics alarms
rabbitmqctl status | grep -A5 "Alarms"
alarm 触发时的现象极具迷惑性：不是报错，而是生产者连接被阻塞、发送超时，业务侧表现是"消息发不出去、一直在重试"。根因通常是：① 消费者挂了/消费不动，队列堆积吃光内存；② 磁盘满（未清理的队列数据 + 日志）。监控必须覆盖：rabbit_queue_messages_ready（就绪消息数）、rabbit_queue_messages_unacked、mem_used/disk_free、连接数 rabbit_connections。日常防堆积三板斧：给队列设 x-max-length + overflow: reject-publish、监控积压告警、消费者加看门狗（卡住自动重启）。

Spring Boot 集成要点

生产者：ConfirmCallback + ReturnsCallback 必须配对

@Bean
public RabbitTemplate rabbitTemplate(ConnectionFactory cf) {
  RabbitTemplate t = new RabbitTemplate(cf);
  t.setConfirmCallback((correlationData, ack, cause) -> {
    if (!ack) log.error("broker 未确认消息: {}", cause);   // nack：落库或告警
  });
  t.setReturnsCallback(ret -> log.error("消息无法路由: {}", ret.getRoutingKey()));
  return t;
}

// 发消息：convertAndSend，消息体自动用 MessageConverter 序列化
rabbitTemplate.convertAndSend("order.topic", "order.cn.paid", orderEvent,
    msg -> { msg.getMessageProperties().setDeliveryMode(MessageDeliveryMode.PERSISTENT); return msg; });

消费者：手动 ack 的标准写法

@RabbitListener(queues = "order.paid")
public void onOrderPaid(OrderEvent ev, Channel channel,
    @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
  try {
    orderService.process(ev);            // 幂等处理（按业务单号去重）
    channel.basicAck(tag, false);       // 确认
  } catch (RetryableException e) {
    channel.basicNack(tag, false, false);  // 进死信队列，稍后重试
  } catch (Exception e) {
    log.error("不可重试错误，转人工", e);
    channel.basicNack(tag, false, false);
  }
}
序列化的大坑：Spring 默认的 SimpleMessageConverter 对 String/byte[] 没问题，但用 Jackson2JsonMessageConverter 发 Java 对象时，会写入 __TypeId__ 头，消费端必须有同一个类的依赖，否则反序列化直接失败。跨语言（Java 发、Go 收）场景务必自定义 MessageConverter，只发纯 JSON + contentType。另一个坑：spring.rabbitmq.listener.simple.retry.enabled=true 的内存重试是在消费线程内 sleep 重试，会把 prefetch 的槽位占满，造成队头阻塞——长重试用 DLX 阶梯，别用内存重试。
Spring 侧"重试 + 死信"标准组合拳：业务队列（配 x-dead-letter-exchange 指向重试交换机，TTL 阶梯）→ 重试队列（配 DLX 指回业务交换机，TTL 逐级拉长 10s/60s/300s）→ 最终死信队列（order.dead，只告警不消费，人工介入）。消费者侧只做快速失败 + nack(requeue=false)，重试节奏全部交给队列 TTL，天然分布式、不怕进程重启。
模块 9

十个线上坑

1
消息没做持久化三件套
durable 队列 + deliveryMode=2 + 落盘（或 quorum 队列）缺一不可。生产默认 autoAck + 临时队列发"重要消息"，重启 broker 全丢。发消息前先问自己：这条消息值不值得持久化？
2
没开 publisher confirm，broker 丢消息无感知
没有 confirm 时生产者只管发，exchange 不存在、队列满、消息被丢弃都不知道。必须 correlated 模式 + ConfirmCallback + ReturnsCallback 三件套。
3
消费者用 autoAck，处理到一半崩了
消息一出队就删了，业务没执行成功也找不回来。生产一律 manual ack，处理完再 basicAck。
4
prefetch 用默认的 0（无限）
broker 一次性把所有消息推给一个消费者，全变成 unacked。该消费者一挂，全部消息重排队；同时内存暴涨触发流控。设 10~50。
5
消费失败用 requeue=true 立即重投
毒消息（如 JSON 格式错误）会在"取出→抛异常→重投"之间死循环，每秒几千次，CPU 打满还刷爆日志。用 nack(requeue=false) + DLX 阶梯重试。
6
重复消费不做幂等
at-least-once 语义下重投、网络抖动重连都会导致重复投递。按业务单号/唯一键做去重表或 Redis 幂等，别指望"正好一次"。
7
队列不设上限，无限堆积
消费者故障几小时后，几百万条消息堆积吃光内存和磁盘，触发 alarm 阻塞所有生产者，故障扩散到整个集群。设 x-max-length + overflow，配积压告警。
8
磁盘水位用默认 50MB
队列数据很快就能吃掉 50MB，然后 alarm 阻塞生产。调到 2GB 或 disk_free_limit_relative，并纳入监控。
9
3.13 之后还在新建经典镜像队列
镜像队列已废弃，异步复制有丢消息和脑裂风险，新特性不再支持。新建队列一律 quorum 类型，存量制定迁移计划。
10
大消息直接发
消息体超过几十 MB 会显著拖慢集群（单 channel 串行 + 复制开销），逼近 128MB 上限直接报错。大文件放对象存储（S3/OSS），消息里只传 URL。
自测

六道题

1. RabbitMQ 中生产者发送消息的正确路径是？
正确答案：生产者→exchange→queue。AMQP 0-9-1 里生产者从不直接操作队列，exchange 根据类型（direct/topic/fanout/headers）和 routing key 查 bindings 决定投递到哪些队列。无法路由时消息默认被丢弃。
2. 关于 publisher confirm，下列说法正确的是？
正确答案：confirm 只保证"broker 收到"（对持久化消息是落盘后确认）。消息到 exchange 后没有匹配的 binding 会被静默丢弃，这种丢失要开 mandatory 标志 + addReturnListener 才能感知。
3. 一条消息变成死信，不可能的原因是？
正确答案：basicAck 是正常确认，消息就此删除，不会进死信。死信只有三种来源：nack/reject 且 requeue=false、TTL 到期、队列溢出（max-length/max-length-bytes）。
4. 需要"每条消息不同的延迟时间"（如 5 秒、3 分钟、1 小时后各不同），应该用？
正确答案：x-delayed-message 插件。消息级 expiration + DLX 有严重队头阻塞：RabbitMQ 只在消息到达队头时检查 TTL，长 TTL 消息堵在后面短 TTL 消息也过期不了。插件按到期时间排序投递，没有队头问题。队列级 TTL 只适合同一批相同延迟的消息。
5. 关于 Quorum 队列与经典镜像队列，说法正确的是？
正确答案：Quorum 基于 Raft 共识，多数派写入成功才向生产者确认，故障切换不丢已确认消息。经典镜像队列是异步复制，主从切换可能丢消息，3.13 起已废弃。Quorum 还有 delivery-limit 机制自动处理反复失败的毒消息。
6. 生产者突然全部超时、连接被阻塞，消费者正常。最可能的原因是？
正确答案：alarm 触发流控。内存超过水位或磁盘剩余低于 disk_free_limit 时，broker 会阻塞所有生产者连接（不报错，就是卡住），消费者不受影响。常见根因是队列堆积吃光资源。默认 disk_free_limit 只有 50MB，一定要调大并监控。
