二十分钟学透 TiDB

TiDB 是"MySQL 协议 + 计算存储分离 + Raft 多副本 + 水平扩展"的分布式数据库。你会 MySQL，这篇重点讲它和单机 MySQL 到底哪里不一样：架构、Region、分布式执行、HTAP、扩容缩容，以及迁移前必须知道的兼容性差异。

模块 1

整体架构：TiDB / TiKV / PD 三组件

一句话概括分工：TiDB 负责"想"，TiKV 负责"存"，PD 负责"管"。三层各自独立扩缩容，这就是计算存储分离。

组件职责关键点
TiDB ServerSQL 层：协议接入、解析、优化、生成分布式执行计划、与 TiKV 交互无状态，多实例对等，前面挂负载均衡即可。默认端口 4000，状态端口 10080
TiKV Server分布式事务型 KV 存储，数据按 Region 分片、Raft 多副本底层引擎 RocksDB；数据以 MVCC key-value 形式存储。端口 20160
PD ServerPlacement Driver：集群元信息、TSO 时间戳、调度决策全局时钟源 + 调度器（副本迁移、leader 均衡、热点均衡）。端口 2379/2380
TiFlash（可选）列存副本，HTAP 的"AP"侧异步 learner 副本，MPP 计算。端口 9000

辅助组件生态

工具用途
TiCDC增量数据订阅，把 TiDB 的变更流转发到 Kafka / 下游（MySQL、TiDB 等）
DMData Migration：从 MySQL 全量 + 增量迁移到 TiDB
Dumpling + Lightning逻辑导出 + 物理导入，大数据量从 MySQL 迁入
BRBackup & Restore：集群级物理备份到 S3/HDFS/本地
Prometheus + Grafana监控（tiup playground --monitor 自带，Grafana 3000 端口）

数据是怎么落地的

-- 表数据最终是 KV 对（简化示意，实际编码更复杂）
-- 行数据：key = t{表ID}_r{行ID}，value = 各列编码后的字节
-- 索引：   key = t{表ID}_i{索引ID}_{索引值}_{行ID}，value 为空或行ID
-- 所以 TiDB 没有"表文件"概念，一张表被打散成大量 KV，按 key 范围分片
和单机 MySQL 的心智模型差异：MySQL 里"一张表 = 一个 ibd 文件 + 一棵 B+ 树"；TiDB 里"一张表 = 按 key 范围切成的许多个 Region，每个 Region 3 个副本分布在不同 TiKV 上"。查询一条数据，TiDB 要先从 PD 拿到 key 属于哪个 Region、leader 在哪台机器，再发请求。这就是为什么 TiDB 的点查延迟是毫秒级而不是微秒级 —— 网络绕了一圈。
模块 2

Region、Raft 与多副本

Region：TiDB 的分片单位

概念数值与说明
Region 大小默认上限约 96MB，超过就自动分裂（split）。可调（max-region-size）
Region 与 Raft 组一个 Region 就是一个 Raft Group，多个副本（peer）。生产常规 3 副本，跨机架/可用区部署可 5 副本
Leader / Follower / Learner读写都走 leader；follower 只同步、可投票；learner（TiFlash）只同步、不投票、不参与选主

写入链路：Raft 多数派 + 2PC

TiDB 发起事务：从 PD 的 TSO 拿全局时间戳（start_ts），事务内读写都带版本号
Prewrite：选一个 key 作为 primary，其余为 secondary；primary 先写锁记录，然后各 Region 的 leader 并行 prewrite，各副本 Raft 日志同步
Commit：多数派确认 prewrite 后，TiDB 发 commit（带 commit_ts），异步清理锁。模型类似 Google Percolator
故障恢复：leader 挂了，PD 指挥剩余副本按 Raft 选新 leader，秒级到分钟级；已提交的数据不丢（多数派已确认）
-- 看 Region 分布与副本状态
mysql> SELECT * FROM information_schema.tikv_region_status LIMIT 5;
mysql> SELECT count(*) FROM information_schema.tikv_region_status;   -- 集群 Region 总数

-- PD 侧（命令行/接口）看调度与健康
tiup ctl:v8.5.4 pd -u http://127.0.0.1:2379 store
tiup ctl:v8.5.4 pd -u http://127.0.0.1:2379 region
Raft 多副本 ≠ 你的数据有三份完整拷贝在同一个逻辑层。它是"每个 Region 三个副本"，leader 单点写、follower 只保一致性。读默认走 leader（保证最新）； follower read / stale read 是新版本能力，需显式开启，别默认假设读被分摊了。
计算存储分离的扩容语义：加 TiDB 节点 → 查询能力线性涨（无状态，立刻生效）；加 TiKV 节点 → PD 调度 Region 副本/leader 往新节点迁移，容量和吞吐逐步涨（迁移期间有流量开销，避开高峰）；加 PD → 元信息与调度能力增强，保持奇数个（3/5/7），2 个 PD 有脑裂风险。
模块 3

分布式执行计划

TiDB 优化器干两件 MySQL 优化器不干的事：把能下推的算子推到 TiKV/TiFlash，以及决定 join 在哪些节点并行做。

看计划

mysql> EXPLAIN SELECT c.name, COUNT(*) FROM orders o JOIN customers c ON o.cust_id = c.id
    -> WHERE o.status = 'PAID' GROUP BY c.name;

mysql> EXPLAIN ANALYZE SELECT ...;   -- 真实执行：输出 actRows / time / memory

-- 统计信息与计划绑定
mysql> ANALYZE TABLE orders;                       -- 手工收统计信息
mysql> CREATE GLOBAL BINDING FOR SELECT ... USING SELECT ...;  -- 固定执行计划
mysql> SHOW GLOBAL BINDINGS;

核心算子

算子含义
PointGet / BatchPointGet主键/唯一键精确点查，直接定位单行，最快路径
TableReader / IndexReader把 TableRangeScan / IndexRangeScan 的 coprocessor 请求发给 TiKV
IndexLookUp先扫索引拿到行 ID，再回表读行数据（类似 MySQL 回表，但是分布式版）
Selection / TopN / Limit过滤 / TopN / 限制，可下推到 TiKV 侧执行
HashJoin / MergeJoin连接。TiDB 层做，两表数据都拉到计算节点
HashAgg / StreamAgg哈希/流式聚合，支持部分下推（partial + final 两阶段）
MPP（Exchange + TableFullScan tiflash）TiFlash 多节点并行执行，大表 AP 查询的杀手锏

慢查询与 SQL 诊断

-- TiDB 把慢日志直接落成表，查起来比翻文件舒服
mysql> SELECT query_time, query FROM information_schema.slow_query
    -> WHERE time >= '2026-10-17 00:00:00' ORDER BY query_time DESC LIMIT 10;

-- 按 SQL 指纹聚合的统计（每 30 秒刷新）
mysql> SELECT digest_text, exec_count, avg_latency, sum_latency
    -> FROM information_schema.statements_summary
    -> ORDER BY sum_latency DESC LIMIT 10;

mysql> ADMIN SHOW SLOW LIMIT 10;   -- 当前 TiDB 节点内存里的慢日志
排查套路和 MySQL 一致但入口不同：MySQL 看 slow log + EXPLAIN，TiDB 看 statements_summary（谁最贵）+ EXPLAIN ANALYZE（慢在哪一步）+ slow_query 表（历史明细）。计划走偏时的三板斧：ANALYZE TABLE 收统计信息 → GLOBAL BINDING 绑死好计划 → 必要时加 Hint。
模块 4

HTAP 与 TiFlash 列存

TiDB 是行存引擎（TiKV），TiFlash 是异步列存副本。同一张表可以同时被 TP 和 AP 查询命中，这就是 HTAP。

概念说明
TiFlash 副本以 Raft learner 身份异步同步数据，不投票、不影响 TP 写入性能。按表开启
DeltaTree 存储TiFlash 的列存结构，写入先进内存层再合并落盘，适合批量读
智能选择优化器按代价自动选择行存/列存；也可强制：SET SESSION tidb_isolation_read_engines='tiflash'
MPPTiFlash 节点间通过 Exchange 并行算，大表 JOIN/聚合不再单点扛
-- 给表加 TiFlash 副本
mysql> ALTER TABLE orders SET TIFLASH REPLICA 1;

-- 看副本同步进度（available=1 才能被查询选中）
mysql> SELECT * FROM information_schema.tiflash_replica;

-- 强制走列存（验证 HTAP 效果）
mysql> SET SESSION tidb_isolation_read_engines = 'tiflash';
mysql> EXPLAIN SELECT status, SUM(amount) FROM orders GROUP BY status;

-- 报表查询显式指定引擎（HINT 方式）
mysql> SELECT /*+ read_from_storage(tiflash[orders]) */ * FROM orders;
TiFlash 的三个现实约束：① 副本同步有延迟（通常秒级），强一致读取不要指望它；② 列存副本吃内存和磁盘，小集群别乱开；③ 高并发点查走 TiFlash 反而更慢 —— 列存为吞吐优化，不为点查优化。正确姿势：TP 走 TiKV，大报表/宽表 JOIN 走 TiFlash。
模块 5

扩容与缩容（tiup 实操）

多机部署的标准姿势

# topology.yaml（最小生产形态：3 PD + 3 TiKV + 2 TiDB）
server_configs:
  tidb: {}
  tikv: {}
  pd: {}
tidb_servers:
  - host: 10.0.1.11
  - host: 10.0.1.12
pd_servers:
  - host: 10.0.1.13
  - host: 10.0.1.14
  - host: 10.0.1.15
tikv_servers:
  - host: 10.0.1.21
  - host: 10.0.1.22
  - host: 10.0.1.23
monitoring_servers:
  - host: 10.0.1.31
grafana_servers:
  - host: 10.0.1.31

# 部署 + 启动
tiup cluster deploy tidb-prod v8.5.4 ./topology.yaml --user root -i
tiup cluster start tidb-prod
tiup cluster display tidb-prod

扩缩容命令

# 扩容：先改 topology.yaml 加节点，再 scale-out（-N 按新拓扑补几个节点）
tiup cluster scale-out tidb-prod ./topology.yaml -N 1

# 缩容：指定节点（IP:端口），PD 先把副本迁走再下线
tiup cluster scale-in tidb-prod --node 10.0.1.23:20160

# 滚动重启（改配置后）、升级（按官方文档的组件顺序执行）
tiup cluster restart tidb-prod
tiup cluster upgrade tidb-prod v8.5.4

# 清理 playground 残留
tiup clean playground
缩容的三条铁律：① 下线 PD 前确认剩余 PD 仍是奇数且健康；② 下线 TiKV 前确认没有业务连接指向它，并等 PD 把 Region 副本迁完（看 store 状态和 leader 数清零）；③ 滚动升级严格按官方文档的组件顺序（PD 通常最先、TiDB 通常最后，且不支持跨大版本跳升），别自行发挥，升级前先备份 metadata 与配置。
扩容效果的正确预期：加 TiDB 是即时的（无状态）；加 TiKV 后 Region 迁移有过程，期间 coprocessor 流量和 IO 会涨，低峰期扩、避开大促；3 副本是底线，跨 AZ 部署用 5 副本 + Placement Rules 控制副本分布。
模块 6

MySQL 兼容性：能连、能跑，但不全等

TiDB 说"MySQL 兼容"主要是指协议和大部分 SQL 语法。迁移前必须过一遍差异清单，尤其是存储过程和自增列。

维度TiDB 现状（以所用版本官方文档为准）影响
协议MySQL wire protocol，JDBC/MyBatis/DBeaver 直连客户端生态基本零成本
自增列auto_increment 不保证连续、不保证递增趋势；推荐 AUTO_RANDOM（打散写入）别依赖自增值做业务逻辑；高并发写入要防自增热点
存储过程/触发器/自定义函数/事件不支持（视图、CTE、窗口函数支持）有这类对象的系统要改造成应用层实现
外键较新版本开始支持，以所用版本文档为准迁移前用实际版本验证
隔离级别默认快照隔离（Snapshot Isolation），与 MySQL 的 RR 行为有差异；也支持 RC依赖 RR 间隙锁语义的应用要重测并发行为
事务大小单事务默认上限约 100MB（txn-total-size-limit）大批量写要分批提交
分区表支持 Range/List/Hash 等，分区裁剪行为与 MySQL 有差异复杂分区 SQL 迁移后要验证计划
Hint 语法兼容部分 MySQL Hint + TiDB 自有 Hint（如 /*+ USE_INDEX(t, ix) */、HASH_JOIN）调优手段需要重新学一套
系统库information_schema 类似但有 TiDB 特有表（statements_summary 等）监控/巡检脚本要适配
-- 迁移一致性校验（DM 场景）
sync-diff-increment --config ./diff.toml    # 校验上下游数据是否一致

-- 从 MySQL 迁入：DM 任务 + Lightning 全量导入
tiup dmctl --master-addr 127.0.0.1:8261 operate create task1 ./task.yaml
tidb-lightning -config ./lightning.toml
"兼容 MySQL"最大的三个谎言级差异：① 存储过程/触发器直接不可用，不是慢，是没有；② 自增列的语义变化会让"先插入再拿 Last_insert_id 做关联"这类代码出现意外；③ 默认隔离级别是快照隔离而不是 RR，依赖间隙锁防并发的业务逻辑要重新设计。上线前用真实业务流量回放（或影子库）验证，别只看功能测试。
模块 7

典型场景与限制

适合的场景

分片替代
原本 MySQL 分库分表 + 中间件的架构，用一套 TiDB 收敛，去掉应用层分片逻辑
海量数据水平扩展
单机放不下/写不动时加节点，存储与计算独立扩
HTAP 混合负载
实时交易 + 实时报表共存，TiFlash 扛 AP，不动 TP
高可用
Raft 多副本自动选主，无主从切换人工操作，副本跨 AZ 部署
弹性伸缩
大促前扩容、大促后缩容，按需付费

不适合 / 要谨慎的场景

场景原因
强依赖存储过程/触发器的遗留系统功能缺失，改造成本可能超过换库收益
极致低延迟点查网络 + Region 定位，延迟毫秒级；本地 MySQL 微秒级
数据量小、并发低的业务杀鸡用牛刀，运维一套分布式集群的成本远超单机 MySQL
超大单事务 / 大批量一次性写事务大小、锁持有时间都受限，要拆分
频繁 DDL 变更超大表online DDL 要 backfill，千万级表加索引会持续消耗资源

运维监控入口

tiup cluster display tidb-prod集群拓扑与组件状态
Grafana（3000 端口）官方 Overview / TiDB / TiKV / PD 面板
information_schema.statements_summary按指纹聚合的 Top SQL
information_schema.tikv_region_status / tiflash_replicaRegion 与 TiFlash 副本状态
tiup ctl pd -u http://pd:2379 storeTiKV store 健康与 Region/leader 数
br backup full / br restore full集群物理备份与恢复
热点是分布式库的永恒话题：自增主键顺序写会集中打一个 Region；时间戳字段做范围查询会集中读新数据。三板斧：AUTO_RANDOM 替代自增、建表时 SHARD_ROW_ID_BITS 打散行 ID、PRE_SPLIT_REGIONS 预分裂。发现热点看 Grafana 的 TiKV 面板（leader/流量分布）和 pd-ctl 的 hot 命令族。
模块 8

十个线上坑

1
拿单机 MySQL 的延迟预期套 TiDB
点查要走 PD 定位 + 网络转发，毫秒级是正常。极致低延迟的业务留在 MySQL，别硬迁。
2
依赖存储过程/触发器
TiDB 不支持，不是性能问题是能力问题。迁移前先盘对象清单，评估改造量。
3
自增主键顺序写打成写入热点
高并发 INSERT 集中打一个 Region 的 leader。用 AUTO_RANDOM / SHARD_ROW_ID_BITS / PRE_SPLIT_REGIONS 三板斧。
4
单个事务里塞几十万行
事务大小默认上限约 100MB，超限直接报错；大事务还阻塞 GC 推进。按万行级分批提交。
5
没统计信息就怪优化器
大批量导入/DDL 后统计信息过期，计划走全表扫。ETL 流程里加 ANALYZE TABLE，或确认自动 analyze 已开。
6
GC 被长事务堵住
长事务/长查询不提交，MVCC 旧版本不能清理，存储膨胀、查询变慢。监控 tidb_gc_life_time 与活跃事务时长，杀掉失控长事务。
7
高峰期扩容缩容
Region 迁移吃 IO 和网络，恰好撞上业务高峰就是双倍压力。扩缩容排低峰，缩容前等副本迁完。
8
PD 集群用偶数节点
2 个 PD 网络分区时有脑裂风险。生产保持 3 或 5，缩容 PD 后重新数一遍。
9
报表全怼 TiFlash 不看副本状态
副本还在同步（available=0）就查，要么报错要么读到旧数据。查 tiflash_replica 确认可用，并接受秒级延迟。
10
升级跳版本 / 不备份就升级
跨大版本升级有兼容性风险和数据格式变更。严格按官方升级文档的组件顺序执行，升级前备份 PD/TiKV 元数据，先在测试集群演练。
自测

六道题

1. TiDB 集群里负责分配全局时间戳（TSO）的是哪个组件？
正确答案：PD。PD 是集群的大脑：元信息、TSO 授时、Region 调度（副本迁移、leader 均衡、热点处理）都归它管。TiDB Server 无状态只做 SQL 处理。
2. TiDB 中数据分片与多副本的基本单位是？
正确答案：Region。数据按 key 范围切成 Region（默认上限约 96MB），每个 Region 是一个 Raft 复制组（生产常规 3 副本）。Region 在 TiKV 节点间自动分裂、迁移、均衡。
3. 想给集群加一个 TiDB 节点，正确的命令是？
正确答案：scale-out。scale-in 是缩容（下线节点）。TiDB Server 虽然无状态，但也要通过 tiup 纳管（写入集群元数据、纳入监控和配置管理），裸起进程不在 PD 的管控视野里。
4. 高并发顺序写入把单个 Region 的 leader 打满，首选优化手段是？
正确答案：打散写入键。自增主键顺序写天然集中在一个 Region。AUTO_RANDOM（随机行 ID）和 SHARD_ROW_ID_BITS（位打散）把写入分散到多个 Region，从源头消除热点。
5. 想强制一条报表 SQL 走 TiFlash 列存引擎，正确的是？
正确答案：tidb_isolation_read_engines（会话级指定读引擎）或 /*+ read_from_storage(tiflash[orders]) */ HINT。前置条件是表已经 ALTER TABLE ... SET TIFLASH REPLICA 且副本同步完成（tiflash_replica.available = 1）。
6. 关于 TiDB 与 MySQL 的兼容性，哪个说法是对的？
正确答案：协议与多数 SQL 兼容，但存储过程/触发器/自定义函数不支持。客户端生态（JDBC、MyBatis）零成本直连；但自增列语义、默认隔离级别（快照隔离）、Hint 体系都和 MySQL 有差异，迁移前必须逐项验证。
