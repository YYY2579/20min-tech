模块 1

倒排索引：ES 为什么搜得快

MySQL 的"like '%词%'" 是全表扫描。ES 反过来存：不问"这行有什么词"，而问"这个词在哪些行里"。这个反向的映射就是倒排索引。

概念说明
分词 Analysis写入时按分词器（analyzer）把文本切成词条（term）。standard 分词器：小写化 + 按标点空格切词
词条字典所有 term 的有序集合。查询时先在字典里二分定位，不是全表扫
倒排表 Posting List每个 term 对应包含它的文档 ID 列表 + 位置信息（做短语查询）。一个 term 命中 1000 万篇文档，就是一个 1000 万的 ID 列表
相关性评分BM25 算法（5.0+ 取代 TF-IDF）：词频越高分越高，字段越短分越高，稀有词权重更高
Doc Values正排的列式存储，聚合和排序靠它。text 字段没有 doc values，不能直接聚合
_source文档原文，返回结果时用。可以 disable 省磁盘，但 update 和 reindex 会受影响
# 看一条文档是怎么被切词的（最有价值的学习命令）
GET /my-index/_analyze
{
  "field": "title",
  "text": "Elasticsearch 分布式搜索引擎"
}
# 返回 tokens：elasticsearch、分布式、搜索引擎

# 写入 3 篇文档后，title 字段的倒排结构大致是：
# 分布式   -> [doc1]
# elasticsearch -> [doc1, doc2, doc3]
# 搜索引擎 -> [doc1]

# 搜 "分布式"：字典定位 term -> 拿 posting list [doc1] -> BM25 打分 -> 返回
GET /my-index/_search
{
  "query": { "match": { "title": "分布式" } }
}
一句话理解 ES 与数据库的分工：ES 的搜索快在"词 → 文档"的反查；聚合排序快在 doc values 列式存储。两者都不需要读 _source 原文，这就是 ES 能在百亿级文档上做亚秒聚合的原因。
模块 2

分片与副本：开局决定终局

分片数在建索引时定下，后期几乎改不了（7.x+ 的 split API 有严格上限：目标分片数必须是源分片的倍数）。开小了无法扩容，开大了集群被元数据压垮。

参数说明
主分片 Primary数据的真实切分。写入按路由（默认 doc _id 哈希）落到某个主分片。7.x 默认 1 个，8.x 默认 1 个
副本 Replica主分片的完整拷贝。可随时增减。两个作用：高可用（主挂了副本顶上）+ 读吞吐（读可以分发到副本）
分片大小业界经验值：单个分片 10GB ~ 50GB。日志类常按 30~50GB 规划，搜索类偏小
分片公式主分片数 ≈ 总数据量 ÷ 目标分片大小。1TB 日志 ÷ 40GB ≈ 25 个主分片
节点数关系至少保证主分片数 ≥ 数据节点数，才能均匀铺开；副本数决定每节点平均持有 shard 数 =（主+副）×分片数/节点数

过度分片（over-sharding）是隐形杀手

  • 每个分片都有固定开销：分片级别的元数据、segment 文件句柄、线程池任务。一个分片再小也占几十 MB 级堆内存（term dictionary、fielddata 元数据等）
  • 1000 个分片的集群，每个搜索请求要扇出到 1000 个分片，每个分片返回自己的 top N 再归并 —— 查询延迟和堆压力随分片数线性上升
  • 经验红线：单节点分片数控制在 20 个/GB 堆内存以内（即 30GB 堆的节点，分片数不超过 600 个），否则 GC 和查询都会变形
# 建索引时就规划好（7.x/8.x 都可以）
PUT /logs-2026.10
{
  "settings": {
    "number_of_shards": 25,
    "number_of_replicas": 1
  },
  "mappings": { "properties": { "msg": { "type": "text" } } }
}

# 查看集群分片分布
GET /_cat/shards/logs-2026.10?v
GET /_cat/nodes?v&h=name,heap.percent,ram.percent,cpu,load_1m,disk.used_percent

# 诊断分片是否过大/过小的聚合查询
GET /_cat/indices?v&h=index,docs.count,store.size,pri.store.size&s=store.size:desc
"先开 100 个分片备用"是最常见的错误。数据没多少，分片开销先吃满堆内存，集群还没上量就天天 GC。正确姿势：按当前数据量 ÷ 40GB 算，留出 2~3 倍增长空间即可，真不够了用 split/rollover 滚动新索引（日志场景按天/周滚动本来就是标准做法）。
模块 3

写入路径：refresh、flush 与 segment merge

ES 的"近实时（NRT）"就诞生在这条路径上：写入 1 秒后可搜，不是因为数据落了盘，而是因为内存里新建了 segment。

文档进入内存缓冲：写入请求到达主分片，先追加到 translog（事务日志，保证掉电不丢），再写入内存 buffer
refresh（默认 1 秒）：buffer 中的文档生成一个新的 segment 并打开文件句柄供搜索。不 fsync，不写 translog 之外的新磁盘数据 —— 这就是"1 秒后可搜"的全部秘密
translog fsync：按 index.translog.durability 策略。request 模式每个请求都 fsync（最安全默认），async 模式每 5 秒批量 fsync（吞吐优先，最多丢 5 秒）
flush：触发条件为 translog 过大（默认 512MB）或 30 分钟。真正把 segment fsync 落盘、清空 translog、更新 commit point
segment merge：后台把多个小 segment 合并成大 segment。被删除/更新的文档在此刻才真正物理消失，merge 本身消耗 CPU 和磁盘 IO
# 写性能三板斧
# 1. 批量写：bulk 每批 5~15MB 或 1000~5000 文档，拒绝单条循环
POST /_bulk
{ "index": { "_index": "logs", "_id": "1" } }
{ "msg": "hello", "level": "INFO" }
{ "index": { "_index": "logs", "_id": "2" } }
{ "msg": "world", "level": "WARN" }

# 2. 调大 refresh 间隔：批量导入时关掉近实时
PUT /logs/_settings
{ "index": { "refresh_interval": "30s" } }
# 导完记得改回 1s，或用 _refresh 接口立即生效
POST /logs/_refresh

# 3. 导入完成后 force merge：把小段合成大段，提升查询速度
POST /logs/_forcemerge?max_num_segments=1
# 注意：只对不再写入的索引做，online 索引 force merge 会产生大段

# translog 模式切换（写吞吐优先时）
PUT /logs/_settings
{ "index": { "translog": { "durability": "async" } } }
操作发生了什么影响
refreshbuffer → 新 segment（内存 + 打开句柄）不 fsync，掉电丢这段。段数量暴涨会让查询变慢
flushsegment fsync + 清 translog真正的持久化点。触发时短暂写 IO 尖刺
merge多段合并、物理删除已删文档持续后台 IO；段太多查询慢，段太大删文档回收慢
"写入后立刻搜不到"类问题，90% 是 refresh_interval 被改大了没改回来。排查顺序：① GET /索引/_settings 看 refresh_interval；② _cat/segments 看段数量是否异常（几千个段 = merge 跟不上）；③ _cat/thread_pool/write?v 看写线程池是否打满有拒绝。
模块 4

映射与动态映射陷阱

mapping 定义字段怎么切词、怎么存。动态映射是新手最好的朋友，也是集群崩溃的头号原因。

两种字符串类型，选错全盘皆输

类型行为用途
text写入时分词，倒排索引按词条命中。没有 doc values，不能聚合/排序全文搜索：正文、标题、日志内容
keyword不分词，整值精确匹配。有 doc values，聚合/排序/精确过滤都靠它ID、状态码、标签、枚举、邮箱
# 标准姿势：一个字段同时要搜索和聚合，用 multi-field
PUT /logs
{
  "mappings": {
    "properties": {
      "msg":     { "type": "text", "analyzer": "standard" },
      "status":  { "type": "keyword" },
      "level":   { "type": "keyword" },
      "@timestamp": { "type": "date" },
      "content": {
        "type": "text",
        "fields": {
          "raw": { "type": "keyword" }     # content 搜索用 content，聚合用 content.raw
        }
      }
    }
  }
}

动态映射（dynamic mapping）

  • 默认 "dynamic": true：文档里出现新字段，ES 自动猜类型（字符串→text+keyword 多字段，数字→long/double，日期串→date）
  • 陷阱一：mapping 爆炸。日志里带 hostname、trace_id、随机 key 的 JSON，每个新 key 都变成一个映射字段。几十万上百万字段的映射，集群状态（cluster state）膨胀，所有节点同步变慢，堆内存被元数据吃光
  • 陷阱二：类型推断冲突。自动推断把字段定成 long，上游某天发了个字符串，写入直接报错
  • 陷阱三：text 字段被用来聚合。日志按 msg 聚合 → fielddata 疯狂加载 → 堆爆 OOM（7.x 后 fielddata 默认关，报错而不是炸，但查询照样失败）
# 生产级防御：显式 mapping + dynamic templates
PUT /logs
{
  "mappings": {
    "dynamic_templates": [
      {
        "strings_as_keyword": {          # 所有字符串默认 keyword
          "match_mapping_type": "string",
          "mapping": { "type": "keyword" }
        }
      }
    ]
  },
  "settings": {
    "index.mapping.total_fields.limit": 1000,     # 字段数硬上限，防爆炸（默认 1000）
    "index.mapping.depth.limit": 20               # 嵌套深度上限
  }
}

# 严格模式：新字段直接拒绝写入（推荐给日志管道）
PUT /logs/_mapping
{ "dynamic": "strict" }

# 查看字段数量和类型
GET /logs/_mapping
GET /_cat/fielddata?v                          # 看哪些字段在用 fielddata（内存大户）
映射几乎不可变：已存在的字段不能改类型（text 改 keyword 要 reindex）；只能加新字段、改分析器要重建索引。所以映射必须在第一批数据写入前定好，日志管道上线第一天就要配 dynamic templates。
模块 5

查询 DSL：bool 组合与相关性

ES 查询分两个上下文：query context 算相关性分数，filter context 只判是否匹配。搞混这两个概念，写不出高性能查询。

上下文行为
Query 上下文计算 BM25 得分，按分数排序。结果默认不缓存（分数依赖每个查询）
Filter 上下文只有"是/否"，不算分。结果可被节点缓存（bitset），且能利用 filter cache。能放 filter 的绝不放 query
# bool query 四大子句
# must    -> 必须匹配，算分（query context）
# filter  -> 必须匹配，不算分（filter context，可缓存）
# should  -> 应该匹配，配合 minimum_should_match
# must_not -> 必须不匹配，filter context

GET /logs/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "msg": "timeout error" } }          # 分词后 OR 匹配，算分
      ],
      "filter": [
        { "term":  { "level": "ERROR" } },               # 精确匹配，缓存
        { "range": { "@timestamp": { "gte": "now-1h" } } }
      ],
      "must_not": [
        { "term": { "service": "deprecated-api" } }
      ],
      "should": [
        { "match": { "msg": "database" } }               # 命中加分，不命中不扣
      ],
      "minimum_should_match": 0
    }
  }
}

高频查询类型对照

查询作用域要点
termkeyword / 数字 / 日期精确匹配不分词。对 text 字段用它等于查原始 term，通常查不到
termskeyword多值 IN，等价 SQL IN
matchtext先分析查询串再匹配，默认 OR，可用 operator: "and"
match_phrasetext短语匹配，词序和相邻性都要对
multi_match多字段跨字段搜同一串，best_fields / most_fields / cross_fields
range数字 / 日期gte/gt/lte/lt，时间范围查询必用
exists任意字段存在性，处理稀疏字段

相关性与分页

# 看一条文档为什么排第一 —— 排错最实用的命令
GET /logs/_search
{
  "explain": true,
  "query": { "match": { "msg": "timeout" } }
}

# 函数分：给新文档加权（recency）、给特定来源加权
GET /logs/_search
{
  "query": {
    "function_score": {
      "query": { "match": { "msg": "timeout" } },
      "functions": [
        { "exp": { "@timestamp": { "origin": "now", "scale": "1h", "decay": 0.5 } } }
      ]
    }
  }
}

# 深分页：from+size 超过 max_result_window（默认 10000）直接报错
# 正确做法 1：search_after 游标翻页（利用上一页最后一条的排序值）
GET /logs/_search
{
  "size": 100,
  "sort": [ { "@timestamp": "desc" }, { "_doc": "asc" } ],
  "search_after": ["2026-10-17T10:00:00", 12345]
}

# 正确做法 2：PIT（point in time，7.10+）固定视图再翻页，保证一致性
POST /logs/_pit?keep_alive=1m
# 返回 pit_id，后续查询带 "pit": {"id": "xxx", "keep_alive": "1m"}
查询性能口诀：过滤条件全放 filter（缓存 + 不算分），只有"按文本相关度排序"的才放 must/match；排序字段用 keyword/date/数字（有 doc values），永远别对 text 排序；翻页过 1 万条换 search_after。
模块 6

聚合性能

ES 的聚合（aggregation）跑在 doc values 上，比 SQL 的 GROUP BY 快一个量级，但用错方式的代价是直接 OOM。

聚合族谱

类型作用关键参数
Metric 聚合单值统计：avg/sum/min/max/cardinality/statscardinality 默认精度 100，误差约 3%~5%
Bucket 聚合分组：terms/date_histogram/range/histogramterms 的 size、shard_size
Pipeline 聚合对其他聚合的结果再加工：derivative/cumulative_sum/moving_avg只对 metric 聚合结果生效
# 经典三层聚合：按服务分桶 → 桶内按状态码分桶 → 桶内算 P95
GET /logs/_search
{
  "size": 0,                                  # 只要聚合不要文档
  "aggs": {
    "by_service": {
      "terms": { "field": "service", "size": 10, "shard_size": 50 },
      "aggs": {
        "by_status": {
          "terms": { "field": "status" },
          "aggs": {
            "latency_p95": { "percentiles": { "field": "latency_ms", "percents": [50, 95, 99] } }
          }
        }
      }
    }
  }
}

# cardinality 去重 UV：快但近似
GET /logs/_search
{
  "size": 0,
  "aggs": { "uv": { "cardinality": { "field": "user_id", "precision_threshold": 1000 } } }
}
# precision_threshold 100 → 误差 ~3%；1000 → 内存换精度；精确去重要全量扫或预计算

# 时间直方图：日志曲线图的标准聚合
GET /logs/_search
{
  "size": 0,
  "aggs": {
    "over_time": {
      "date_histogram": { "field": "@timestamp", "calendar_interval": "1h" },
      "aggs": { "error_rate": { "filter": { "term": { "level": "ERROR" } } } }
    }
  }
}

聚合的性能红线

  • terms 聚合必须有 doc values。text 字段聚合会报错（fielddata 默认关闭），这是设计保护不是 bug
  • terms size 别贪大。size=1000 的 terms 聚合 = 每个分片都排 1000 个桶再归并。深翻页用 composite 聚合（支持 after 游标）而不是加大 size
  • 全局序数（global ordinals）：keyword 字段首次聚合时构建"值→序号"的内存映射，高基数字段（百万级不同值）这块内存很大。可用 eager_global_ordinals 在刷新时预构建，避开查询时的卡顿
  • date_histogram 用 calendar_interval（1h/1d）而不是 fixed_interval 跨时区场景，语义更符合预期
聚合 OOM 的标准配方：对百万级高基数字段做 terms size=10000 聚合 + 并发几十个查询。分片各自在堆内排大 Map，直接触发 circuit breaker。预防：聚合字段基数控制在十万级以内，size 控制在三位数，超长尾用 composite 分页，或者把明细预聚合成独立统计索引。
模块 7

集群运维：重启、水位、堆内存与快照

滚动重启（升级/换配置必做）

关分片分配：PUT /_cluster/settings {"persistent":{"cluster.routing.allocation.enable":"none"}}，防止重启期间集群把副本疯狂重分配
可能先同步刷新：POST /_flush/synced，减少恢复时间（可选）
停一个节点，改配置/升级，重启，等它重新加入并恢复完（GET /_cat/recovery 看进度）
逐节点重复，直到全部完成，期间集群 health 是 yellow（副本缺失）属正常
恢复分配：把 enable 改回 all（或 primaries），等 health 变 green

磁盘水位：集群只读的触发链

水位默认阈值行为
low磁盘使用率 85%不再给该节点分配新分片
high磁盘使用率 90%开始把该节点的分片迁走去别的节点
flood-stage磁盘使用率 95%该节点上索引被置为只读块（index.blocks.read_only_allow_delete），写入全部报 403，直到手动解锁
# 看水位和块状态
GET /_cluster/allocation/explain
GET /_cat/allocation?v&h=node,disk.used,disk.avail,disk.total,shards

# flood-stage 后的解锁姿势（先扩容/清理，再手动解除只读）
PUT /logstash-*/_settings
{ "index.blocks.read_only_allow_delete": null }

# 提前规划：按容量配 watermark，按索引设 ILM rollover 自动滚新索引
PUT /_cluster/settings
{
  "transient": {
    "cluster.routing.allocation.disk.watermark.low": "85%",
    "cluster.routing.allocation.disk.watermark.high": "90%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "95%"
  }
}

JVM 堆与文件系统缓存的配合

  • 堆内存不超过物理内存的 50%（且 Xms = Xmx，禁动态调整），剩下的一半给文件系统缓存（page cache） —— segment 文件、doc values 的冷读全靠它
  • 绝对不要超过 31GB。超过这个线，JVM 关闭压缩普通对象指针（compressed oops），同样的堆能装的对象数骤降，等于白给一倍内存。常见做法：堆 26~30GB 封顶，或 16GB 分节点铺开
  • 堆里的大户：fielddata（已默认关闭）、term dictionary、segment 元数据、查询缓存、聚合堆。分片越多元数据越大 —— 堆问题最后常常回到分片规划
  • GC：默认 G1。关注 GET /_nodes/stats/jvm 里 old GC 频率和耗时，old GC 每次超过 1 秒就要警惕

# 4. 自动化：SLM 策略定期快照 + ILM 管理索引生命周期
PUT /_slm/policy/nightly
{
  "schedule": "0 30 2 * * ?",
  "name": "<nightly-{now/d}>",
  "repository": "my_backup",
  "retention": { "expire_after": "30d" }
}

# ILM：hot（可写可查）→ warm（只读+ shrink 合并）→ cold（可搜索快照）→ delete
PUT /_ilm/policy/logs_policy
{
  "phases": {
    "hot":    { "actions": { "rollover": { "max_size": "50gb", "max_age": "1d" } } },
    "warm":   { "min_age": "3d",  "actions": { "shrink": { "number_of_shards": 1 } } },
    "delete": { "min_age": "30d", "actions": { "delete": {} } }
  }
}
运维三定律：① 磁盘 95% 之前就要有告警，等集群只读写已经晚了；② 堆内存没超过 31GB 且 Xms=Xmx，否则 GC 抖动会以"查询偶发几秒"的形式出现；③ 快照恢复到新集群是灾难恢复的唯一手段，没测过恢复的快照等于没有快照。
模块 8

十个线上坑

1
日志索引不配 mapping，动态映射字段爆炸
带随机 key 的 JSON 被自动映射成几十万字段，cluster state 膨胀、堆内存被元数据吃光。上线第一天就要配 dynamic templates 和 total_fields.limit。
2
对 text 字段做聚合或排序
text 没有 doc values，聚合直接报 fielddata 禁用错误，排序失败。聚合排序必须用 keyword，用 multi-field 的 .raw 子字段。
3
term 查询打在 text 字段上
term 不做分析，查的是原始 term。text 字段存的是切词后的结果，term: "Timeout Error" 永远查不到 "timeout error" 的文档。搜文本用 match。
4
分片开得过大或过度分片
1TB 数据开 5 个分片 = 单分片 200GB 恢复慢；反过来为"将来"开 100 个小分片，元数据先压垮堆内存。按 10~50GB/分片规划，宁少勿多。
5
bulk 逐条循环写
每条一个 HTTP 请求，网络和序列化开销主导，吞吐差一个量级。bulk 每批 5~15MB / 1000~5000 文档，多线程并行发。
6
导入时没调大 refresh_interval
1 秒 refresh + 高频写入 = segment 数量暴涨，查询变慢、merge 压力山大。批量导入调 30s，导完改回，或 force merge。
7
from + size 深翻页
超过 max_result_window（默认 10000）直接报错，就算不报，深翻页每个分片都要排前 N 万条。用 search_after 或 PIT。
8
JVM 堆超过 31GB 或超过物理内存 50%
超过 31GB 丢压缩指针，堆效率骤降；超过 50% 物理内存，page cache 被挤占，冷查询全磁盘 IO。堆设 26GB 封顶或 16GB 多节点。
9
磁盘写满到 flood-stage 才发现
95% 水位触发索引只读块，业务写入全 403。85%/90% 就要配告警，日常用 ILM 滚索引 + 快照 + 清理。
10
滚动重启前没关分片分配
节点一停集群立刻开始副本重分配，恢复流量和重启流量叠加，集群可能雪崩。先 allocation.enable=none，逐节点重启完再恢复。
自测

六道题

1. ES 查询中，什么条件下应该用 filter 子句而不是 must？
正确答案：不需要算分就用 filter。filter context 不计算 BM25 分数，结果以 bitset 形式被节点缓存，后续相同过滤直接命中缓存。这是 ES 查询优化第一原则：状态码、时间范围这类条件全放 filter。
2. 一个 text 字段存了 "Timeout Error"，用 term 查询 "timeout error" 搜不到，原因是？
正确答案：term 不分析查询串。text 字段写入时被 standard 分词器切成 timeout、error 两个词条，倒排表里没有 "timeout error" 这个整体 term。搜文本内容要用 match（它会先分析查询串）。
3. 关于分片规划，哪个说法是对的？
正确答案：按 10~50GB 规划且后期几乎不可改。过度分片每个分片都吃堆内存和元数据，查询扇出开销线性上升。副本只是主分片的完整拷贝，加副本提升的是读吞吐和高可用，不增加数据容量。
4. 写入文档 1 秒后就能被搜到，主要靠哪个机制？
正确答案：refresh 生成可搜索的 segment。它不 fsync 数据，只是让新文档在内存文件系统里可被检索；flush 才是把 segment fsync 落盘并清 translog 的持久化动作。这也是"数据可能丢最近几秒"的原因。
5. JVM 堆内存的推荐配置是？
正确答案：≤50% 物理内存且 ≤31GB 左右，Xms=Xmx。31GB 是 JVM 压缩对象指针的边界，超过它堆效率骤降；超过物理内存一半会挤占 page cache，冷查询全走磁盘。剩下的内存留给文件缓存是 ES 的设计核心。
6. 磁盘使用率达到 95% 触发 flood-stage 水位后，会发生什么？
正确答案：索引进入只读状态（index.blocks.read_only_allow_delete），这是 ES 的自保机制：宁可拒绝写入也不能写满磁盘导致节点崩溃。85% 时停止分配新分片、90% 开始迁走分片，三级水位层层递进。
