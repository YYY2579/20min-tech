模块 1

核心概念：五件事必须刻在脑子里

概念是什么工程含义
Topic 主题消息的分类管道，如 orders、logs生产者往 topic 写，消费者从 topic 读
Partition 分区topic 的物理分片，有序不可变的日志并行单位和顺序单位。一个分区只被同组一个消费者消费
Offset 偏移分区内消息的序号，从 0 单调递增消费者靠 offset 定位进度，过期数据按 offset 之前的整体删除
Consumer Group一组消费者共同消费一个 topic组内分区水平分摊；不同组各自独立收到全量（广播）
Replica 副本分区的多个拷贝，分布在不同 broker一个 leader 对外服务，follower 异步拉取，故障时选举

两条铁律

  • 顺序只保分区内：同一个分区内 offset 递增即有序；跨分区、跨 topic 没有任何顺序保证。"消息乱序"类事故 90% 是因为业务把需要顺序的消息发到了不同 key
  • 消费者数 > 分区数就浪费：组内消费者比分区多时，多出的消费者空转（分不到分区）。分区数是消费并行度的天花板
# 看 topic 全貌：分区、副本分布、leader 是谁
docker exec -it kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic demo

# 输出字段解读
# PartitionCount:3        分区数（只能加不能减）
# ReplicationFactor:1     副本因子
# Leader:1               该分区 leader 所在 broker
# Isr:1                  同步副本列表（in-sync replicas）
# Configs                该 topic 级别的配置覆盖

# 看每个分区的首尾 offset（数据量 = 末尾 - 开头）
docker exec -it kafka /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic demo

模块 2

副本机制与 ISR

这是 Kafka"不丢数据"语义的核心。三个缩写必须分清：LEO、HW、ISR。

缩写全称含义
LEOLog End Offset日志末端偏移——下一条消息的写入位置。每个副本各自维护
HWHigh Watermark高水位 = ISR 中最小的 LEO。消费者只能读到 HW 以下的消息，之上的属于"未提交"数据
ISRIn-Sync Replicas与 leader 保持同步的副本集合。落后超过 replica.lag.time.max.ms（默认 30s）就被踢出

同步流程

生产者写入 leader：消息追加到 leader 日志，LEO 前进
follower 拉取：follower 向 leader 发 fetch 请求，补齐数据，自身 LEO 前进
HW 推进：leader 发现所有 ISR 副本都追上了，把 HW 推到新的 LEO
消费者可见：只有 offset < HW 的消息对消费者可见。没进 ISR 同步的消息，消费者看不到
故障恢复：leader 挂了，从 ISR 中选新 leader（要求 HW 一致，防止数据回退）；旧 leader 恢复后按 HW 截断掉多余部分

关键 broker 配置

# server.properties 里和数据安全直接相关的几项
default.replication.factor=3          # 自动建 topic 的默认副本数（默认 1，生产必须显式建 topic）
min.insync.replicas=2                 # 配合 acks=all：至少 2 个副本同步才允许写。默认 1
unclean.leader.election.enable=false  # 默认 false：不允许 ISR 外副本当 leader
replica.lag.time.max.ms=30000         # follower 落后 30s 被踢出 ISR
offsets.topic.replication.factor=3    # __consumer_offsets 的副本数，默认 3
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2       # 事务状态主题的最小 ISR，默认 2
auto.create.topics.enable=false       # 生产建议关掉：防手滑拼错 topic 名自动建成 1 分区 1 副本

acks 与 min.insync.replicas 的组合语义

组合语义
acks=0发出去就不管。不确认、可丢失。只适合 metrics 日志
acks=1leader 写入即回。leader 随即崩溃且未复制时会丢数据
acks=all等所有 ISR 副本确认。配合 min.insync.replicas=2 = 至少两处落盘
acks=all + min.isr=1名存实亡：只剩 leader 也允许写，等价于 acks=1 的丢失风险
ISR 不足时写请求报 NOT_ENOUGH_REPLICAS 错误——这是系统在保护你，不是故障，客户端应重试
unclean.leader.election.enable=true 是"拿数据换可用性"的开关。开启后，ISR 之外的落后副本也能当选 leader，服务不中断，但该副本上缺失的消息永久丢失（且消费者毫无感知）。默认 false 意味着：宁可暂时不可用（等 ISR 恢复），也不丢已确认的消息。除非你做的是可丢数据的日志管道，否则别开。
模块 3

Producer 语义：acks、幂等、事务

三档投递语义

语义配置风险
至多一次acks=0，或 acks=1 + 不重试发送失败不重试，直接丢
至少一次acks=all + retries 拉满（默认行为）重试可能重复，消费端要幂等
精确一次enable.idempotence=true（+ 事务）有性能代价，且事务版有额外开销
# Java 生产者：推荐的生产基线配置
Properties props = new Properties();
props.put("bootstrap.servers", "kafka-1:9092,kafka-2:9092,kafka-3:9092");
props.put("key.serializer", "org.apache.kafka.common.serialization.StringSerializer");
props.put("value.serializer", "org.apache.kafka.common.serialization.StringSerializer");

props.put("acks", "all");                      // 3.0 起默认就是 all
props.put("enable.idempotence", "true");     // 3.0 起默认 true，防重试重复
props.put("max.in.flight.requests.per.connection", "5");  // 幂等允许下最多 5，兼顾并行与顺序
props.put("retries", "2147483647");        // 幂等开启时默认值，配好重连退避即可
props.put("linger.ms", "20");               // 攒 20ms 凑批，吞吐换微小延迟
props.put("batch.size", "65536");          // 64KB 批次，默认 16KB
props.put("compression.type", "lz4");       // none/gzip/snappy/lz4/zstd，压缩比换 CPU
props.put("buffer.memory", "33554432");    // 32MB 发送缓冲，默认值
props.put("delivery.timeout.ms", "120000"); // 2 分钟总超时（含重试），默认值

幂等生产者：原理就两点

开启 enable.idempotence=true 后，broker 为每个生产者实例分配 PID，每条消息带分区内单调递增的序列号。broker 缓存每个 (PID, partition) 最近提交的序号：重复序号直接丢弃、乱序序号拒绝。这解决了"网络超时重试导致同一条消息写两次"和"重试乱序"。

幂等的边界：它只保证单会话内单分区不重不丢。生产者重启会拿新 PID，跨会话去重做不到——那需要业务层的业务 ID 去重或事务。幂等也不解决消费者重复，端到端 exactly-once 要靠事务 + read_committed。

事务：跨分区原子写

// 事务生产者：多条消息要么全部可见，要么全部不可见
props.put("transactional.id", "order-service-1");   // 固定且唯一，崩溃恢复靠它
KafkaProducer<String, String> producer = new KafkaProducer<>(props);
producer.initTransactions();                        // 初始化事务状态

producer.beginTransaction();
producer.send(new ProducerRecord<>("orders", orderId, payload));
producer.send(new ProducerRecord<>("order-events", orderId, event));
producer.commitTransaction();                       // 失败则 abortTransaction()

// 消费者必须显式隔离事务消息，否则仍会读到未提交的
props.put("isolation.level", "read_committed");   // 默认 read_uncommitted

事务消息在日志里是普通消息 + 特殊标记（COMMIT/ABORT 控制记录）。只有 read_committed 消费者会跳过 ABORT 事务的消息；默认的 read_uncommitted 照单全收。

事务不是免费的：事务消息要走事务状态 topic（__transaction_state）协调，吞吐大约打对折、尾延迟升高。判断标准：你的"多分区原子写"需求是真的（下游会把半成品当成事实），还是伪的（其实消费端能容忍）？伪需求别用事务，用业务 ID 去重更轻。
模块 4

Consumer rebalance 协议

消费者组的分区分配不是客户端私聊，而是由 group coordinator（broker 端组件）统一编排的。rebalance 期间整个组停止消费，这就是"消费卡顿"的头号来源。

两个线程、两个超时

机制参数/默认值作用
心跳线程heartbeat.interval.ms=3000后台线程周期性发心跳，证明"我还活着"
会话超时session.timeout.ms=4500045 秒（3.0 起，此前 10s）没收到心跳 → coordinator 判定死亡 → 踢出组 → rebalance
轮询线程max.poll.interval.ms=300000两次 poll() 之间处理逻辑超过 5 分钟 → 主动退出组 → rebalance
单次拉取量max.poll.records=500一次 poll 最多返回 500 条，控制单轮处理时长

eager vs cooperative sticky

协议工作方式影响
Eager（贪婪式）
RangeAssignor / RoundRobin		全局停摆：所有消费者先撤销全部分区，再按新成员列表重新分配每次成员变化全体停顿一次；分配完成后才能继续消费
Cooperative Sticky（2.4+，推荐）增量移交：两阶段——只撤销"需要移动的分区"，分配给新主人，其余分区不动未受影响的分区全程不停；停顿窗口小一个数量级
// 切 cooperative sticky：Java 消费者一行配置
props.put("partition.assignment.strategy",
          "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");

# 命令行看组的实时状态
docker exec -it kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group demo-g1

#   CURRENT-OFFSET  已消费到的 offset
#   LOG-END-OFFSET  分区末尾 offset（滞后量 = 末尾 - 当前）

消费循环的正确姿势

// 手动提交 offset：至少一次语义的标配
props.put("enable.auto.commit", "false");        // 关掉自动提交，自己掌握时机
props.put("isolation.level", "read_committed"); // 配合事务生产者

consumer.subscribe(topics);
while (running) {
  ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(200));
  for (ConsumerRecord<String, String> r : records) {
    process(r);                      // 业务处理，必须能在 max.poll.interval.ms 内完成
  }
  consumer.commitSync();             // 处理完再提交：崩了重来 = 重复消费（至少一次）
}

// 长耗时处理（如调用外部 API）拆两轮 poll，中间用 resume 暂停分区，
// 避免超过 max.poll.interval.ms 被踢出组
"先提交后处理"是丢消息陷阱，"先处理后提交"是重复陷阱。没有完美解，只有取舍：金融类选至少一次 + 业务幂等（先处理后提交）；日志类选至多一次省心（先提交后处理）。rebalance 风暴的根源通常是 max.poll.interval.ms 设太小，或消费逻辑偶发变慢——调大超时 + 用 cooperative sticky，比加消费者数量更管用。
模块 5

零拷贝与页缓存

Kafka 高吞吐不是靠玄学，是两个朴素事实：磁盘顺序读写够快 + 数据尽量不复制。

零拷贝（sendfile）

传统读文件发网络：磁盘 → 内核页缓存 → 用户缓冲区 → socket 缓冲区 → 网卡。4 次拷贝、4 次上下文切换
Kafka 的 sendfile 路径：数据从页缓存直接进 socket 缓冲区，CPU 只做 DMA 搬运描述符。2 次拷贝、2 次切换
生产者侧同理：消息先进内存 buffer，攒批后顺序 append 到 segment 文件，几乎全是顺序 IO

页缓存是主力，磁盘是兜底

事实推论
消费热点数据（最近写入）基本命中 OS page cache不要给 Kafka 配太小内存； broker 自身堆 6GB 常够，其余留给页缓存
Kafka 不逐条 fsync，靠多副本冗余保证持久单 broker 掉电丢尾部消息是设计内的，用 acks=all + RF=3 兜底
消费滞后到 retention 外的老数据会真实读盘追积压时吞吐会掉，提前扩容/加分区，别等 LAG 告警
压缩在 producer 侧做，端到端压缩透传开 compression.type=lz4/zstd，带宽和磁盘双省
磁盘选型经验：多块普通 HDD 做日志盘 + 页缓存，往往比单块高价 SSD 更划算——顺序写把 HDD 的顺序带宽用满即可。真正吃随机 IO 的是 page cache 未命中的旧数据追读，那是偶发场景。
模块 6

Kafka Streams 与 Connect

两个官方生态组件，定位完全不同：Streams 是"你的应用里的流计算库"，Connect 是"Kafka 与外部系统的搬运工"。都不需要额外集群。

Kafka Streams（流处理库）

抽象说明
KStream不可变记录流，每条都是 insert 语义
KTablechangelog 流，同 key 后者覆盖前者（物化视图）
窗口滚动（tumbling）、跳跃（hopping）、会话（session）窗口
状态存储本地 RocksDB + changelog topic 备份，故障自动恢复
exactly-onceprocessing.guarantee=exactly_once_v2（2.6+，默认 at_least_once）
// 30 秒滚动窗口统计每用户订单数
StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> orders = builder.stream("orders");

orders.groupByKey()
      .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofSeconds(30)))
      .count()
      .toStream()
      .to("order-counts-30s", Produced.with(stringSerde, longSerde));

Properties props = new Properties();
props.put("processing.guarantee", "exactly_once_v2");  // EOS v2，开销小于 v1
props.put("num.stream.threads", "4");                // 并行度 = 消费的分区数
new KafkaStreams(builder.build(), props).start();

Connect 的运维盲区：① 死信队列（DLQ）一定要配 errors.tolerance=all + DLQ topic，否则一条毒消息能让 connector 无限重启；② connector 内部有自己的消费者组（connect-{name}），offset 存在内部 topic，别和业务组混为一谈；③ 配置改了要重启 task 才生效，发布窗口要评估。
模块 7

KRaft：Kafka 没有 ZooKeeper 之后

KIP-500 用 Kafka 自己的 Raft 协议管理元数据，替代 ZooKeeper。4.0 起 ZooKeeper 模式已被移除——这是近两年 Kafka 最大的架构变化。

版本节奏（排坑必背）

版本状态
2.8KRaft 早期预览（early access），别上生产
3.3KRaft 生产就绪（新集群）
3.5 ~ 3.9提供 ZK → KRaft 在线迁移工具，双写过渡
4.0移除 ZooKeeper 模式，只保留 KRaft；新一代消费者重平衡协议（KIP-848）就绪

架构变化

维度ZooKeeper 模式KRaft
元数据存哪外部 ZK 集群（znode）broker 内的 __cluster_metadata 日志 topic
谁来当管家ZK 选出一个 controllercontroller quorum（3 或 5 个节点）Raft 共识
故障转移秒级到几十秒，依赖 ZK 会话超时秒级，Raft 选举更快
运维组件Kafka + ZK 两套只有 Kafka，部署简化
元数据规模ZK 全量 znode 在内存，万级分区吃力日志快照 + 流式拉取，可扩展性更好

node.id=1
controller.quorum.voters=1@localhost:9093   # 生产：3 个 voter，如 1@k1:9093,2@k2:9093,3@k3:9093
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
advertised.listeners=PLAINTEXT://localhost:9092

# 元数据日志相关
metadata.log.segment.bytes=1073741824
metadata.log.max.snapshot.interval.ms=3600000
metadata.max.idle.interval.ms=5000     # 提高 broker 间元数据传播频率（降低延迟，费点流量）

# 初始化存储（首次启动前必须做一次）
/opt/kafka/bin/kafka-storage.sh format -t <cluster-id> --config config/kraft/server.properties

# 首选 leader 选举（KRaft 下用这个命令，不再走 ZK）
/opt/kafka/bin/kafka-leader-election.sh --bootstrap-server localhost:9092 --election-type PREFERRED --topic demo
行动建议：新集群直接用 KRaft（4.x 没得选）。存量 ZK 集群：3.x 版本用官方迁移工具（KIP-866 双写阶段）滚动升级，先在预发跑通元数据校验再动生产。迁移期间两套系统并存，回滚预案要提前写好。
模块 8

三大顽疾：分区倾斜、消息乱序、rebalance 风暴

分区倾斜

某些分区数据量/流量远超其他分区。后果：消费组里负责该分区的消费者 LAG 永远降不下来，整体消费进度被最慢的一个分区卡死。

  • 根因：key 分布不均（少量超级用户贡献大部分流量）、key 为 null（轮询但负载实际不均）、自定义 partitioner 有偏
  • 解法：① 重新设计 key（加二级散列后缀）；② 热点 key 单独拆 topic；③ 加分区后注意 key 到分区的映射会变，有顺序要求的业务要评估
# 诊断：看每个分区的 LOG-END-OFFSET 差距
kafka-get-offsets.sh --bootstrap-server localhost:9092 --topic demo --time -1
# 最大分区 offset ÷ 平均 offset 明显大于 1，就是倾斜

消息乱序

  • 根因 1：重试。acks≠all 或未开幂等时，重试可能把旧消息写到新位置之后
  • 根因 2：多个生产者实例并发写同一分区（各自缓冲攒批节奏不同）
  • 根因 3：业务上需要顺序的消息用了不同 key，落到了不同分区
  • 解法：同 key 进同分区（默认行为）+ enable.idempotence=true + max.in.flight.requests.per.connection ≤ 5；跨分区顺序要求 = 单分区串行，牺牲并行度

rebalance 风暴

  • 现象：日志里 rebalance 一条接一条，消费几乎停滞，LAG 持续上涨
  • 根因：① max.poll.interval.ms 太小，业务偶尔超时；② 频繁发布重启（每次进出都是一次成员变更）；③ GC 停顿超过 session.timeout.ms
  • 解法：切 CooperativeStickyAssignor、调大 max.poll.interval.ms（如 600000）、poll 循环里暂停/恢复分区、用静态组成员（group.instance.id）让重启不触发 rebalance
// 静态组成员：进程重启后凭 group.instance.id 认领回原分区，不触发 rebalance
props.put("group.instance.id", "order-consumer-3");   // 每个实例唯一且固定
模块 9

十个线上坑

1
分区倾斜，消费 LAG 只降一个分区
热点 key 把流量灌进少数分区，负责它的消费者成瓶颈。重新设计 key 或单独拆 topic；加分区能缓解但要重算 key 映射，顺序业务先评估。
2
以为 Kafka 全局有序
顺序只在分区内成立。需要顺序的消息没用同一个 key，跨分区必然乱。要么同 key，要么业务自带序号在消费端排序。
3
没开幂等就狂重试
网络抖动触发重试，同一条消息写进去两遍，且可能乱序。enable.idempotence=true（3.0+ 默认开）+ max.in.flight ≤ 5。
4
acks=all 但 min.insync.replicas=1
配置看着安全实则裸奔：只剩 leader 一个副本也允许写，leader 挂了照样丢。acks=all 必须配 min.insync.replicas=2 以上。
5
开启 unclean leader election 换可用性
落后副本当选 leader，缺失的消息永久丢失且消费者无感知。默认 false 是对的，别为了"服务不中断"把它打开。
6
max.poll.interval.ms 设太小
业务偶发变慢（调外部接口、GC）就超过间隔被踢出组，触发 rebalance，越慢越踢、越踢越慢。调到 5~10 分钟，或长任务拆多轮 poll。
7
还在用 eager 分配器
RangeAssignor 每次成员变化都全体撤销全部分区再重分，停顿明显。2.4+ 换 CooperativeStickyAssignor，增量移交不停全组。
8
offset 提交时机搞反
先 commit 后处理：处理失败消息永久丢失；先处理后 commit：崩溃后重复消费（至少一次，需业务幂等）。按业务取舍，别无意中混用。
9
分区数拍脑袋，消息超 1MB 硬发
分区过多（几千）拖垮 broker 文件句柄和内存，消费者还空转；max.message.bytes 默认约 1MB，大消息报 RecordTooLargeException，应外置存储传引用。
10
不看消费者 LAG，事务当糖豆撒
LAG 涨了没人发现，业务延迟几小时才暴露；事务生产者让吞吐约减半，非原子写需求别用。监控 kafka-consumer-groups 的 LAG 并配告警。
自测

六道题

1. 关于 Kafka 的 HW（高水位）和 LEO，哪个说法正确？
正确答案：HW = ISR 中最小 LEO。它划出"已提交"与"未提交"的界线：消费者只能消费 HW 以下的消息。leader 故障时也按 HW 截断旧 leader 的多余数据，防止已提交数据回滚。LEO 只是各副本自己的日志末端。
2. acks=all 配合 min.insync.replicas=2、副本因子 3 的语义是？
正确答案：至少 2 个同步副本。min.insync.replicas 是下限而非全员：acks=all 要求等所有 ISR 副本确认，但 ISR 最少必须有 2 个，否则直接拒绝写入（保护数据不丢）。三个副本可以容忍 1 个故障仍正常写入。
3. eager 协议和 cooperative sticky 协议的核心区别是？
正确答案：全组停摆 vs 增量移交。两者都由 group coordinator 编排，都只在组内分配。eager（Range/RoundRobin）每次成员变化所有消费者先 revoke 全部分区再重新 assign，停顿窗口大；cooperative sticky（2.4+）分两轮只动该动的分区，生产推荐。
4. 消费者偶发处理一批消息超过 5 分钟，最可能发生什么？
正确答案：超过 max.poll.interval.ms 触发 rebalance。注意区分两个超时：session.timeout.ms（默认 45s）管"心跳线程有没有活着"，max.poll.interval.ms（默认 5 分钟）管"业务处理有没有卡住"。前者不触发主动退出，后者才是处理慢的杀手，也是 rebalance 风暴的常见根因。
5. 幂等生产者的去重原理是？
正确答案：PID + 分区内序列号。去重在 broker 侧完成，不需要消费者参与、也不依赖消息内容（内容相同的两条业务消息仍会都写入）。注意幂等只覆盖单会话单分区；生产者重启拿新 PID，跨会话去重需要业务 ID 或事务。
6. 发现某 topic 有一个分区 offset 远高于其他分区，消费组 LAG 只降这个分区，应该？
正确答案：解决 key 分布。这是典型分区倾斜：整体进度被最慢分区卡死。单开消费者组没用（同一条消息会被两组都消费，且组内仍是单消费者拿这个分区）；缩短 retention 只会丢数据。加分区能缓解但要重新计算 key→分区映射，有顺序要求的业务先评估。
