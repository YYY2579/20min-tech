0-2 分钟

数据库到底是个什么东西

先用最直白的话说：数据库就是一堆被严格管起来的表格。

你完全可以用 Excel 存数据，那为什么要用数据库？三个原因：

  • 数据量大。Excel 几万行就开始卡，数据库千万行照样秒查。
  • 多人同时用。Excel 两个人同时改就会冲突覆盖，数据库有事务和并发控制机制来保证不出错（第 15 分钟会讲）。
  • 关系复杂。用户和订单是有关联的，Excel 表达不了这种关系。

层级结构：库 → 表 → 行 → 列

层级叫什么类比
数据库 Database一个项目一个库一个 Excel 文件
表 Table存一类东西文件里的一个 Sheet
行 Row / 记录一条数据Sheet 里的一行
列 Column / 字段一个属性Sheet 的表头

主键：每一行的身份证

主键（Primary Key）是一列（或几列的组合），用来唯一标识一行，不允许重复、不允许为空。比如用户表的 id。

为什么要主键？因为"张三"可能有两个人，但 id 不会有。后面所有"修改这一行""删除这一行""把订单关联到用户"的操作，靠的都是主键。
2-5 分钟

连上数据库，建第一张表

先补一个名词：SQL（Structured Query Language，结构化查询语言）就是你和数据库对话用的语言。本文里所有大写的英文关键词（SELECT、CREATE、WHERE……）都是 SQL 语句的一部分，你照着敲就行。

连接

mysql -h 127.0.0.1 -u root -p
# -h 主机地址  -u 用户名  -p 之后会提示你输密码

建库建表

-- 建一个库，字符集一定用 utf8mb4（下面会解释为什么）
CREATE DATABASE shop DEFAULT CHARSET utf8mb4;
USE shop;

-- 建一张用户表
CREATE TABLE users (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  name       VARCHAR(50)  NOT NULL,
  email      VARCHAR(100) UNIQUE,
  age        INT,
  balance    DECIMAL(10,2) DEFAULT 0.00,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

逐行读一遍：

  • BIGINT PRIMARY KEY AUTO_INCREMENT —— 整数主键，自动递增，插入时不用自己填
  • VARCHAR(50) NOT NULL —— 最长 50 字符的字符串，不能为空
  • UNIQUE —— 唯一约束，邮箱不允许重复
  • DECIMAL(10,2) —— 共 10 位、其中 2 位小数的精确数字，存钱只能用这个
  • DEFAULT CURRENT_TIMESTAMP —— 不填就自动记录当前时间

选数据类型的三条铁律

钱绝不用 FLOAT
浮点数有精度误差，0.1 + 0.2 不等于 0.3。金额一律用 DECIMAL，或存成分数用整数。
够用就好，别乱开大
能 INT 就别 BIGINT，能 VARCHAR(50) 就别 VARCHAR(255)。字段越窄，索引越小，查询越快。
时间用 DATETIME
存创建时间、更新时间。TIMESTAMP 有 2038 年上限，新项目优先 DATETIME。

SQL 分四类，知道分类就不会乱

类别全称干什么
DDL数据定义语言建库建表改结构：CREATE / ALTER / DROP
DML数据操纵语言增删改数据：INSERT / UPDATE / DELETE
DQL数据查询语言只查不改：SELECT（用得最多，占日常 80%）
DCL数据控制语言管权限：GRANT / REVOKE
5-9 分钟

查询：SELECT 五件套

90% 的 SQL 都是这几个关键词的组合。先塞点数据进去，然后一条条试。

下面这条 INSERT INTO 是"往表里插数据"，属于增删改里的"增"，第 15 分钟会细讲。现在先照抄执行，把数据准备好就行。 
INSERT INTO users (name, email, age, balance) VALUES
('张三', 'zs@x.com', 28, 1000.00),
('李四', 'ls@x.com', 35, 2500.50),
('王五', 'ww@x.com', 19, 300.00),
('赵六', 'zl@x.com', 42, 8800.00);

五件套的完整形态

SELECT   name, age          -- 要哪些列
FROM     users              -- 从哪张表
WHERE    age >= 18          -- 过滤条件
ORDER BY age DESC           -- 排序，DESC 从大到小，ASC 从小到大
LIMIT    10;                -- 只取前 10 条

WHERE 能写什么

写法含义
age >= 18 AND age < 40区间，AND 是"且"，OR 是"或"
name = '张三'等值比较，字符串用单引号
name LIKE '张%'模糊匹配，% 代表任意多个字符
age IN (18, 28, 35)在某个集合里
age BETWEEN 20 AND 30闭区间，含两端
email IS NULL判断空值只能用 IS NULL，写 = NULL 永远查不到东西
NOT age > 18取反

聚合：把多行压成一行

SELECT age, COUNT(*) AS cnt   -- AS 给结果列起个别名，纯粹为了好读
FROM users
GROUP BY age          -- 按年龄分组，每组算一次
HAVING COUNT(*) > 1;   -- 对分组后的结果再过滤

五个聚合函数：COUNT 计数、SUM 求和、AVG 平均、MAX 最大、MIN 最小。

WHERE 和 HAVING 的区别（新手最容易混）：
WHERE 在分组之前过滤原始行，不能用聚合函数。
HAVING 在分组之后过滤结果，专门用来筛聚合值。
记法：先筛人（WHERE），再筛组（HAVING）。

书写顺序 ≠ 执行顺序（这条很值钱）

你写的顺序数据库实际执行的顺序
SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMITFROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

看出差别了吗？SELECT 是在 WHERE 之后才执行的。这就解释了一个经典困惑：为什么 WHERE 里不能用 SELECT 起的别名，但 ORDER BY 里可以。

9-12 分钟

JOIN：关系型数据库的价值所在

为什么要把数据拆成多张表？因为重复存储是灾难。

如果订单表里每次都存一遍"张三、zs@x.com、28岁"，那用户改了邮箱，你得改几千条订单记录 —— 迟早改漏。正确做法是：用户信息只存一份，订单里只存用户 id。查的时候再拼起来，这个"拼"就是 JOIN。

CREATE TABLE orders (
  id         BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id    BIGINT,          -- 这里存 users 表的 id
  amount     DECIMAL(10,2),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO orders (user_id, amount) VALUES (1, 199.00), (1, 88.00), (2, 500.00);

三种 JOIN

类型结果
INNER JOIN只保留两边都能匹配上的行（交集）。没下过单的用户不出现
LEFT JOIN保留左表全部行，右表匹配不上就填 NULL。常用！能查出"没下过单的用户"
RIGHT JOIN保留右表全部行。实际中很少用，把两张表换个位置写 LEFT JOIN 就行
SELECT u.name, o.amount
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
ORDER BY u.id;

结果：王五、赵六没有订单，他们的 amount 显示为 NULL —— 这就是 LEFT JOIN 的价值。

一个特别隐蔽的坑：你写了 LEFT JOIN，但又在 WHERE 里过滤了右表的字段（比如 WHERE o.amount > 100），那 NULL 行会被全部滤掉 —— LEFT JOIN 就悄悄退化成了 INNER JOIN。要过滤右表条件，请写进 ON 里，或者用 o.amount IS NULL OR o.amount > 100。
实用句式：找出所有没下过单的用户
SELECT u.name FROM users u LEFT JOIN orders o ON u.id = o.user_id WHERE o.id IS NULL;
12-15 分钟

索引：从几秒到几毫秒的秘密

先说结论：索引就是书的目录。没有它，数据库只能从第一行翻到最后一行，这叫"全表扫描"；有它，三四次就能定位到目标行。

为什么目录能这么快？因为索引底层是排好序的多层结构（B+ 树）：每一层都能砍掉大部分候选数据。哪怕表里有 1000 万行，也只需要三四次比较就找到。代价是索引要占额外磁盘，而且每次插入或修改数据都要同步维护它 —— 所以不是越多越好。

怎么建索引

-- 建表时声明
CREATE TABLE users ( ..., INDEX idx_age (age) );

-- 或者事后补加
CREATE INDEX idx_age ON users(age);

-- 看一张表上都有什么索引
SHOW INDEX FROM users;
类型说明
主键索引主键自动就有，唯一且非空
唯一索引UNIQUE 约束自动创建，值不能重复
普通索引最常用，只为加速查询
联合索引多列合成一个索引，如 (a, b, c)

联合索引与"最左前缀"

建了联合索引 (name, age)，相当于建了按姓名排序、姓名相同时再按年龄排序的目录。所以：

查询条件能用上索引吗
WHERE name = '张三'能。只用到了最左边一列
WHERE name = '张三' AND age = 28能。两列都用到，效率最高
WHERE age = 28不能。跳过了最左列，索引整条作废
最左前缀原则一句话：联合索引只能从最左边那列开始用，不能跳着用。所以建联合索引时，把最常用的筛选列放最左边。

索引失效的五种情况（重点）

列被函数包住
WHERE YEAR(created_at) = 2026 用不上索引。改成 created_at >= '2026-01-01'
列参与运算
WHERE id + 1 = 10 用不上。改成 WHERE id = 9
隐式类型转换
字段是字符串却传数字：WHERE phone = 13800000000，要加引号
前导模糊匹配
LIKE '%张' 用不上（前面有 %）。LIKE '张%' 才能用上
OR 连接非索引列
WHERE a = 1 OR b = 2，只要 b 没索引，整个条件就退化成全表扫描
索引不是越多越好
每个索引都占磁盘，且每次 INSERT/UPDATE 都要同步维护 —— 写入会变慢。只给真正高频的查询条件建。
15-18 分钟

增删改与事务

三个写操作

INSERT INTO users (name, email, age) VALUES ('钱七', 'qq@x.com', 30);

UPDATE users SET age = 29, balance = balance + 100 WHERE id = 1;

DELETE FROM users WHERE id = 4;
血泪忠告：UPDATE 和 DELETE 必须先 SELECT 验证。
写 UPDATE users SET balance = 0; —— 少了 WHERE，全表余额清零，且无法撤销。标准流程是：先用同样的 WHERE 跑一遍 SELECT 看结果，确认无误，再把 SELECT 换成 UPDATE/DELETE。

事务：要么全成功，要么全失败

转账是经典场景：A 扣 100，B 加 100。如果扣完钱系统崩了，钱就凭空消失了。事务就是解决这个的。

（下面假设有一张 accounts 表，只有两个字段：id 和 balance 余额。你可以自己建一张跟着练。）

START TRANSACTION;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- 两条都成功才提交
-- 中途出错就写 ROLLBACK; 全部撤销，回到开始前的状态

ACID：事务的四个保证

字母中文含义
A Atomicity原子性要么全做，要么全不做，没有中间态
C Consistency一致性事务前后数据都满足业务规则（如余额不能为负）
I Isolation隔离性多个事务同时跑，互不干扰
D Durability持久性提交了就永久生效，断电也不丢

隔离级别：够用就好，别深挖

级别解决什么问题代价
读未提交什么都不解决会读到别人没提交的脏数据
读已提交脏读同一事务里两次读结果可能不一样
可重复读（MySQL 默认）脏读 + 不可重复读可能出现幻读（MySQL 用间隙锁基本解决了）
串行化全部性能极差，几乎不用
新手结论：不用改，用 MySQL 默认的"可重复读"就够了。知道有这回事、知道脏读是什么，已经超过大部分人。
18-20 分钟

慢查询定位与六个必踩的坑

EXPLAIN：让数据库告诉你它打算怎么查

EXPLAIN SELECT * FROM users WHERE email = 'zs@x.com';

会输出一张表，新手只看四列：

列看什么
type最重要的列。从好到坏：const > eq_ref > ref > range > index > ALL。看到 ALL 就是全表扫描，必须优化
key实际用了哪个索引。显示 NULL 就是没用索引
rows预估要扫描多少行。数字越大越危险
Extra看到 Using filesort（额外排序）或 Using temporary（临时表）要警惕

深分页问题

-- 慢：要扫描前 100010 行，丢掉前 100000 行
SELECT * FROM users ORDER BY id LIMIT 100000, 10;

-- 快：用主键游标，从上次的位置继续
SELECT * FROM users WHERE id > 100000 ORDER BY id LIMIT 10;

六个必踩的坑

1
UPDATE / DELETE 忘了写 WHERE
全表被改。没有撤销键。永远先 SELECT 验证。
2
用 = NULL 判断空值
NULL 表示"未知"，任何和它的比较结果都是未知。必须用 IS NULL / IS NOT NULL。
3
字符集用了 utf8 而不是 utf8mb4
MySQL 里的 utf8 是残缺的三字节版本，存 emoji 会直接报错。新库一律 utf8mb4。
4
金额用了 FLOAT / DOUBLE
浮点有精度误差，对账时会出现 0.01 的诡异差额。用 DECIMAL。
5
给每个字段都建索引
写入性能暴跌，磁盘暴涨。索引只建在高频查询条件上。
6
SELECT * 一把梭
取回用不到的列，浪费带宽、可能破坏索引覆盖。明确写出需要的列。
自测

五道题，检验是不是真懂了

1. 想查"所有没下过单的用户"，应该用哪种 JOIN？
正确答案：LEFT JOIN + WHERE 右表主键 IS NULL。LEFT JOIN 保留左表全部用户，没订单的右表字段是 NULL，用 IS NULL 一筛就出来了。
2. 建了联合索引 (name, age)，下面哪个查询用不上索引？
正确答案：WHERE age = 28。这违反了最左前缀原则 —— 跳过了最左边的 name 列，索引整条作废。
3. WHERE 和 HAVING 的区别是？
正确答案：WHERE 先于分组，HAVING 后于分组。所以 COUNT(*)、SUM() 这类聚合函数只能写在 HAVING 里。
4. EXPLAIN 结果里 type 显示 ALL，说明什么？
正确答案：全表扫描。ALL 是 type 里最差的一档，意味着数据库把整张表翻了一遍，数据量一大就会很慢。
5. 下面哪条 SQL 用不上索引？
正确答案：WHERE YEAR(created_at) = 2026。索引列被函数包住就失效了 —— 因为数据库没法直接拿函数的计算结果去查目录。改写成范围比较即可。

术语表（看不懂的回来查）

术语一句话解释
主键 Primary Key唯一标识一行的字段，不重复、不为空
外键 Foreign Key指向另一张表主键的字段，用来建立关联（如 orders.user_id）
索引 Index加速查询的目录结构，底层是 B+ 树
全表扫描没有可用索引时，逐行检查整张表，很慢
最左前缀原则联合索引只能从最左列开始使用，不能跳列
事务 Transaction一组要么全成功、要么全失败的操作
ACID事务的四个保证：原子性、一致性、隔离性、持久性
脏读读到了别的事务还没提交的数据
幻读同一事务内两次相同查询，第二次多出了新行
执行计划EXPLAIN 的输出，数据库打算怎么执行这条查询
字符集 / 排序规则决定能存哪些字符、怎么比较。新库统一 utf8mb4
DDL / DML / DQL / DCLSQL 的四大分类：定义 / 增删改 / 查询 / 权限
下一步怎么练：给自己设计一个真实场景（比如记账、书单、健身记录），设计三张表，把增删改查全部写一遍，然后给高频查询条件加上索引，用 EXPLAIN 前后对比。跑通这一个练习，你就真的会 MySQL 了。

之后值得单独学：备份与恢复（mysqldump）、主从复制、分库分表、以及 MySQL 之外的 Redis（缓存）和 MongoDB（文档型）。
