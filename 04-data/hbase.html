二十分钟速通 HBase

HBase 的知识就一条主线：LSM 树决定写入，RowKey 决定分布，Region 决定扩展。这篇讲清 MemStore→HFile→Compaction 全链路、RowKey 防热点三板斧、读写路径，以及 Phoenix 二级索引怎么用。

20:00
建议起一个 HBase 跟着敲：docker run -d -p 2181:2181 -p 16010:16010 harisekhon/hbase
开始前

起一个能练的环境

# 单机 standalone（自带 ZooKeeper，学习够用）
docker run -d --name hbase -p 2181:2181 -p 16010:16010 -p 16000:16000 harisekhon/hbase

# 进 shell
docker exec -it hbase hbase shell

# 最小四连：建表 → 插数 → 查 → 扫
create 'student', 'info'
put 'student', 'row1', 'info:name', 'Tom'
put 'student', 'row1', 'info:age', '18'
get 'student', 'row1'
scan 'student', {LIMIT => 10}

# 常用运维命令
status 'simple'                      # 集群状态
status 'detailed'                    # 每台 RegionServer 的 region 数、请求数
list                                 # 所有表
describe 'student'                   # 表结构、列族、压缩编码全在里面
数据模型先记住三点：① 没有"列"的 schema —— 列是 列族:限定符 动态拼出来的；② 一个 Cell = RowKey + 列族 + 限定符 + 时间戳 + 值，写一次就是一个新版本；③ 行内按列族字典序排序存储，RowKey 全局字典序 —— 这个排序属性是 RowKey 设计的一切基础。
模块 1

LSM 树模型：写入的哲学

HBase 用 LSM 树（Log-Structured Merge Tree）换掉了 B+ 树的随机写。核心思想：写全部是顺序追加，合并和排序留给后台。

写 WAL：客户端的 put 先追加到 HLog（Write-Ahead Log），崩溃后靠它恢复。这是"不丢数据"的唯一保证
写 MemStore：数据进入每个列族独立的内存有序结构（MemStore，跳表实现），写满默认 128MB（hbase.hregion.memstore.flush.size）触发下一步
Flush 成 HFile：MemStore 排序后刷成磁盘上的 HFile（不可变、有序、带布隆过滤器和索引块）。HFile 一旦生成就不再改
Compaction：小 HFile 越写越多，读要逐个查。compaction 把多个 HFile 合并成大 HFile。删除标记和过期版本在这一刻才真正物理消失

两种 Compaction

类型行为触发与影响
Minor把若干个小 HFile 合并成一个中等 HFile，不做全量清理触发频繁、代价小。hbase.hstore.compactionThreshold 默认 3（文件数超过就合并）
Major一个 Store 内所有 HFile 合并成一个，彻底清理删除标记、过期版本、TTL 数据代价大（全 Store 重写），默认 7 天一次。IO 尖刺的主要来源，大表要放维护窗口
# 看 LSM 各层状态（排障第一现场）
hbase hbck -summary                     # 一致性检查

# 手动触发 compaction（低峰期执行）
major_compact 'student'                  # 整表 major
compact 'student', 'cf1', 'rowkey'       # 只压某个 region 的某个列族

# 关键参数（hbase-site.xml）
hbase.hregion.memstore.flush.size: 128m          # MemStore 刷盘阈值
hbase.hstore.compactionThreshold: 3              # minor compaction 文件数阈值
hbase.hstore.compaction.max: 10                  # minor 一次最多合多少文件
hbase.hregion.majorcompaction: 604800000         # major 间隔，默认 7 天（ms）
hbase.regionserver.hlog.sync: true               # WAL 同步，见模块 4
LSM 的代价是读放大和 compaction 放大：一次读可能同时查 MemStore + 多个 HFile；写 1 份数据，compaction 期间可能被反复重写 10 次以上。大表场景 compaction 是磁盘 IO 的最大消费者 —— 监控 compactionQueueSize，长期大于 0 说明 compaction 追不上写入，要么降写入要么加机器。
模块 2

RowKey 设计：唯一的索引

HBase 只有 RowKey 一个索引，RowKey 决定了数据落在哪个 Region、读写走哪台机器。RowKey 设计错 = 集群一半机器闲死一半机器忙死。

三个致命错误

设计后果
单调递增（时间戳、自增 ID）热点。所有写集中在最后一个 Region（尾部 Region），单节点扛全部写入，其余节点空闲
直接哈希（MD5(user_id)）均匀但失去顺序性：范围扫描退化为全集群扫，行相关数据被打散到不同 Region
过长（100+ 字节）RowKey 在每次读写、HFile 索引、block cache 里都存在，长度直接乘上数据量。建议 10~100 字节

防热点三板斧

# 1. 盐值（Salting）：前缀散列，把均匀性拉满，牺牲范围扫描
# 原 key: user12345  加盐后: (hash(user12345) % N) + "_" + user12345
# N = Region 数量预期。写均匀了，但查单个 user 要扫 N 个 region？
# 不 —— 查的时候用同样的盐值函数算出前缀，单点定位。牺牲的是"范围扫描"

# 2. 哈希前缀：同盐值，更常用的说法
# 原 key: order_20261017_0001
# 加盐后: 7_order_20261017_0001   （7 = md5(key).substring(0,1) 转 int % 16）

# 3. 时间戳倒排：把"最近的最热"反转成"最早的最热"
# 热点数据永远在尾部？反转：Long.MAX_VALUE - timestamp 作为 key 前缀
# 现在最新数据的 key 最小，写在头部 Region，负载被时间摊平
# 时序场景标配：scan startRow=(MAX-now) 天然拿到最近的数据

# 组合示例：消息表 rowkey = salt(4位) + 倒排时间戳 + 用户ID
# 0a_9223372036854775807_u1001  →  写均匀 + 按用户查 + 最新消息最小
RowKey 设计 checklist：① 长度 ≤ 100 字节，能短则短；② 写入均匀（盐值/哈希/倒排至少用一样）；③ 需要范围扫描的数据必须在同一 Region（盐值前缀会打散，要权衡）；④ 高频查询的过滤条件要么是 RowKey 前缀，要么接受全表扫描；⑤ 和 Cassandra 比，HBase 的 RowKey 设计就是"分片策略 + 聚簇索引 + 分区键"三合一。
模块 3

Region 与 RegionServer

Region 是 HBase 的分布式单元和扩展单元：一张表按 RowKey 范围切成多个 Region，散在集群各台 RegionServer 上。

组件职责
Region一段连续的 RowKey 区间 [startKey, endKey)。一个 Region 包含若干列族的 Store，是负载均衡和分裂的最小单位
RegionServer托管 Region 的进程，处理该区间所有读写。单机性能上限由它决定（内存、GC、compaction 都在这里）
HMaster管分配：Region 的 split、迁移、负载均衡、宕机恢复。不在数据读写路径上（挂了不影响读写，只影响管理）
hbase:meta系统表，记录"哪个 RowKey 在哪个 RegionServer"。客户端先查它再发读写， ZooKeeper 存 meta 的位置

分裂与预分区

  • Region 超过 hbase.hregion.max.filesize（默认 10GB）自动 split 成两半。生产建议 Region 保持在 10~20GB：太小元数据开销大，太大单点恢复慢
  • 新表只有 1 个 Region，所有写先打在一台机器上，直到它涨到 10GB 才分裂 —— 这就是"新表热点"的根源。解法是建表时预分区
  • 单台 RegionServer 托管 region 数经验值：几十到一两百。超过 200 要警惕（flush 和 compaction 排队）
# 预分区：建表时直接指定分裂点
create 'student', 'info', {SPLITS => ['5', 'a', 'f', 'm', 's']}
# 建表即有 6 个 region：(-∞,5) [5,a) [a,f) [f,m) [m,s) [s,+∞)

# 按盐值均匀预分区（0-f 十六进制前缀，16 个 region）
create 'events', 'cf', {SPLITS => ['1','2','3','4','5','6','7','8','9','a','b','c','d','e','f']}

# 查看 region 分布
hbase(main):001> list regions 'student'          # 2.x shell 语法
# 或看 Web UI: http://<master>:16010 → Table Regions

# 手动分裂/迁移
split 'tableName', 'splitKey'
move 'encodedRegionName', 'targetServerName'      # 把 region 挪到指定机器
balancer                                                        # 触发一次负载均衡
自动 split 的坑：split 瞬间产生"父子 region 并存 + 元数据变更 + 可能的 compaction 连锁"，对写入有秒级抖动。高写入表在建表时就把分区规划好，依赖自动 split 等于把抖动留给生产。另外 split 出的 region 不会自动再均衡，记得 balancer。
模块 4

读写路径

写路径：三步，第三步才是落内存

定位：客户端查 ZooKeeper 拿到 hbase:meta 位置，再查 meta 找到 RowKey 所属的 RegionServer，连接缓存复用
写 WAL：put 请求同时追加到 HLog。按 hbase.regionserver.hlog.sync（默认 true，每个写都同步）决定何时刷盘
写 MemStore + ack：数据进对应列族的 MemStore（内存有序），然后才向客户端返回成功
# WAL 同步策略（吞吐 vs 安全的开关）
# hbase.regionserver.hlog.sync = true（默认）：每次 put 都 sync WAL，最安全
# 关掉 sync：异步批量刷，吞吐可提升 2~3 倍，但 RegionServer 宕机会丢这段 WAL
# 折中：批量写业务自己攒批，sync 保持 true

读路径：三层缓存 + 布隆过滤器

BlockCache：HFile 的数据块缓存在 JVM 堆外/堆内。读的第一站，命中率是读性能生命线
MemStore：还没刷盘的最新数据，第二站
HFile：前两级都没命中才读磁盘。每个 HFile 的布隆过滤器先判断"这行不可能在这个文件里"，直接跳过整个文件
# 删除与版本
delete 'student', 'row1', 'info:age'              # 删除：写墓碑标记，不是物理删
deleteall 'student', 'row1'                       # 删整行

# VERSIONS：每个 Cell 保留几个版本，major compaction 才真正清理
create 'orders', 'cf', {VERSIONS => 3, TTL => 2592000}   # 保留 3 个版本，30 天过期
get 'orders', 'row1', {COLUMN => 'cf:amount', VERSIONS => 3}   # 取最近 3 个版本

# scan 优化：永远带 startRow/stopRow，别全表扫
scan 'student', {STARTROW => 'row1', STOPROW => 'row2', LIMIT => 100}
scan 'student', {COLUMNS => ['info:name'], CACHE => 500}    # 只取需要的列 + 大 RPC 批量
全表 scan 是 HBase 头号性能杀手：没有 WHERE 下推，没有二级索引，一条不带 STARTROW/STOPROW 的 scan 会把全集群数据过一遍，客户端 OOM、RS GC、网络打满三连。scan 必须带 RowKey 范围；要按非 RowKey 查，用 Phoenix 二级索引（模块 7）。
模块 5

强一致与单行事务

HBase 的一致性模型可以一句话概括：单行强一致 + 原子，跨行不保证。这来自它的架构本质：一行数据只属于一个 Region，只由一台 RegionServer 负责。

操作一致性保证
单行 put / get / delete原子 + 强一致。写完立即可读（MemStore 同步），没有主从延迟
increment / append原子，基于行锁实现。计数器场景的安全选择
checkAndPut / checkAndDelete检查-然后写的乐观并发，单行内原子。HBase 版的 CAS
多行 put不保证原子。要么全成要么全败要靠业务层补偿
跨 Region 操作不保证。多 Region 扫描会看到"半新半旧"的快照
# checkAndPut：HBase 版的乐观锁，库存扣减的安全写法
put 'inventory', 'sku1001', 'cf:stock', '100'
# 只有当前 stock 等于 100 时才扣成 99，避免并发覆盖
checkAndPut 'inventory', 'sku1001', 'cf:stock', '100', 'cf:stock', '99'

# 原子计数器
incr 'inventory', 'sku1001', 'cf:stock', 1          # 不减库存反而加，演示用
incr 'metrics', 'pv', 'cf:count', 1                 # 高并发计数场景

# Java API 里对应 BatchOnRow 的多种原子操作
# Table.incrementColumnValue / checkAndMutate 是同一语义的客户端实现
事务边界怎么划：把需要原子性的数据设计进同一行（列族 + 限定符灵活），HBase 就给你免费的事务。需要多行原子（转账两边）？要么引入分布式事务（代价极高），要么改用 NewSQL（TiDB/OceanBase），要么把一致性下沉到消息队列 + 幂等消费。HBase 从来不是事务数据库，别用它的短处。
模块 6

GC 优化：JVM 是 RegionServer 的命门

RegionServer 是 JVM 进程，写路径全程在堆内（MemStore）。GC 停顿超过 ZooKeeper 会话超时，节点会被踢出集群，引发 region 迁移风暴。

手段说明
MSLABMemStore Local Allocation Buffer：MemStore 内存按 2MB 块预分配、复用，消灭堆碎片。默认开启，除非有特殊理由别关
堆外 MemStorehbase.regionserver.offheap.global.memstore.size（默认 0.4 = 40% 堆外），把 MemStore 挪出 JVM 堆，GC 压力骤降
堆大小RegionServer 堆通常 8~16GB。再大收益递减而 GC 停顿变长，不如多开机器
G1 回收器默认 GC 已是 G1GC（HBase 2.x 起）。关注 -XX:MaxGCPauseMillis 和 old GC 频率
会话超时zookeeper.session.timeout 与 GC 停顿赛跑。大堆 + 长 compaction 时适当调大，但会拖慢故障检测
# hbase-env.sh 里的关键配置
export HBASE_HEAPSIZE=12g                      # RegionServer 堆，8~16g 区间
export HBASE_OFFHEAPSIZE=2g                    # 堆外缓存（BlockCache/索引）
export HBASE_OPTS="$HBASE_OPTS -XX:+UseG1GC -XX:MaxGCPauseMillis=200"
export SERVER_GC_OPTS="-XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:InitiatingHeapOccupancyPercent=45"
export HBASE_REGIONSERVER_OPTS="-Xms12g -Xmx12g"

# hbase-site.xml
hbase.regionserver.offheap.global.memstore.size: 0.4   # 40% 堆外给 MemStore
hbase.bucketcache.ioengine: offheap                    # BlockCache 用堆外 bucketcache
hbase.bucketcache.size: 2048                            # MB，二级缓存大小
hbase.regionserver.hlog.sync: true                      # 保持 WAL 同步

# GC 排查入口
# 1. RegionServer 日志里搜 "Pause" / "Full GC"
# 2. jstat -gcutil <pid> 1s 看各区占用和老年代增长
# 3. GC 日志：-Xlog:gc*:file=... -XX:+UseGCLogFileRotation
# 4. RS Web UI (16030) → JVM 环境 / 线程栈
GC 问题的根因通常不在 GC：① MemStore 太大（flush.size 调大 + 堆不变 = 停顿变长）；② compaction 太频繁（写太快或文件太小）；③ 一次 RPC 拿回太多数据（客户端 scan CACHE 太大）撑爆堆。调 GC 参数之前先看这三条。
模块 7

Phoenix 二级索引

原生 HBase 只有 RowKey 一个索引，按其他列查只能全表扫。Phoenix 在 HBase 上加了 SQL 层和二级索引，是用 HBase 又不被全表扫折磨的标准答案。

Phoenix 是什么

  • 一个 SQL 中间件：客户端发标准 SQL，Phoenix 编译成 HBase 的 scan/put，数据还是原生的 HBase 格式（Phoenix 表 = HBase 表，列映射到列族限定符）
  • 支持完整 SQL：JOIN、子查询、聚合、事务（单行级别）、序列，还有 JDBC 驱动，BI 工具能直接连
  • 没有二级索引时：SELECT * FROM user WHERE phone = '138xxx' 退化成全表 scan。这就是索引存在的理由

三种二级索引

类型机制适用与代价
Global Index索引是独立 HBase 表，更新异步。查询先查索引拿到 RowKey，再回查数据表读多写少、点查场景。两次 RPC；异步更新意味着索引短暂不一致
Local Index索引数据和原数据在同一个 Region，查询单次 RPC 搞定写频繁也吃得消（同步维护），但只能用于该表自身查询，不支持 JOIN 下推
Covered Index索引里直接包含查询要返回的列，不用回表查询列固定的看板类 SQL 最快。索引体积变大
# Phoenix 建二级索引
CREATE INDEX IF NOT EXISTS idx_user_phone ON user (phone);                    # global
CREATE LOCAL INDEX idx_user_city ON user (city);                              # local
CREATE INDEX idx_user_name_age ON user (name) INCLUDE (age, city);            # covered

# 函数索引（Phoenix 4.3+）：对表达式建索引，常见于大小写不敏感查询
CREATE INDEX idx_user_upper_name ON user (UPPER(name));

# 确认查询走了索引
EXPLAIN SELECT * FROM user WHERE phone = '13800000000';
# 计划里出现 RANGE SCAN over idx_user_phone 而不是 FULL SCAN 就对了

# 建索引后对存量数据生效：异步写入索引（global），期间查询可能走全表
# 大表建索引选低峰期；可用 ASYNC 关键字异步创建避免长时间阻塞
CREATE ASYNC INDEX idx_big_phone ON big_table (phone);
二级索引的代价：写放大。每写一行数据，global 索引要异步多写一份，local 索引同步多写一份。写吞吐可能腰斩，存储翻倍。规则：① 只给真正高频的过滤列建；② 一张表索引数控制在 3 个以内；③ 能靠 RowKey 设计解决的不建索引；④ 索引会让 compaction 更忙，GC 和 IO 都要重新评估。
模块 8

与 Cassandra 对比及典型场景

Cassandra 和 HBase 是宽表存储的两大代表，架构同源（LSM、列族）但哲学相反：一个 AP 一个 CP。选型时的区别全在一致性上。

维度HBaseCassandra
一致性强一致（单行），CAP 里选 CP可调一致性（ONE/QUORUM/ALL），默认 AP
架构中心化：HMaster 分配，RegionServer 分管 Region。依赖 ZooKeeper/Keeper去中心化：一致性哈希 + vnode， gossip 协议，无单点管理角色
数据分布Region = 连续 RowKey 范围，范围扫描快Token 环哈希分布，范围扫描要二级索引或额外设计
查询模型只有 RowKey；SQL 靠 Phoenix，二级索引有代价CQL 类 SQL，按查询建模（query-first），二级索引较弱
写路径WAL + MemStore，单 Region 单点写入口CommitLog + Memtable，多副本并行写
生态Hadoop/HDFS 全家桶、Spark、Flink、Hive 集成最深独立部署简单，多数据中心复制开箱即用
运维重：Master/RS/ZK 三层，compaction 要盯着较轻：加节点即可，但 vnode 和 compaction 策略要懂

选型一句话

  • 要强一致、范围扫描、Hadoop 生态 → HBase（订单、库存、账号类状态数据）
  • 要多活容灾、极高写入、最终一致可接受 → Cassandra（全球部署的 feed、消息、IoT 写入）

HBase 的典型应用场景

消息 / Feed
Facebook Messenger 的存储底座。RowKey = 会话 ID + 倒排时间戳，天然按时间线扫描
时序 / 监控
OpenTSDB 底层就是 HBase。指标按 metric+tag 编码成 RowKey，倒排时间戳保留最近数据
搜索 / 推荐
用户画像、行为日志的随机读写。列族动态加列，不需要预先定 schema
交易状态
订单、物流的宽表。单行原子操作 + 强一致，适合状态机类数据
历史归档
海量明细的冷存。压缩 + 分层存储，成本比关系型低一个量级
什么时候别用 HBase：数据量小（TB 以下 MySQL 够了）、需要复杂二级查询（上 ES）、需要多行事务（上 NewSQL）、运维团队撑不起三层架构（上云托管版）。
模块 9

十个线上坑

1
RowKey 用单调递增（时间戳、自增 ID）
所有写集中打在最后一个 Region，单节点热点、集群一半闲置。加盐值前缀、哈希前缀或时间戳倒排至少一样。
2
新表不预分区，单 Region 裸奔
新表只有 1 个 region，所有读写打一台机器，直到涨到 10GB 才自动 split。建表时用 SPLITS 参数预分区。
3
scan 不带 STARTROW/STOPROW
全表扫描 = 全集群数据过一遍，客户端 OOM、RS GC、网络三连击。scan 必带 RowKey 范围，LIMIT 和 CACHE 都要设。
4
列族开太多
每个列族独立 MemStore + flush + compaction，5 个以上列族会让 flush 和 compaction 排队恶化。生产建议 1~2 个列族。
5
major compaction 撞业务高峰
major 重写整个 Store，磁盘 IO 尖刺 + 读延迟抖动。避开高峰，或调整 compaction 策略（ ExploringCompactionPolicy/ RatioBasedCompactionPolicy）控制节奏。
6
为吞吐关掉 WAL sync
hlog.sync=false 时 RegionServer 宕机会丢未刷盘的 WAL，数据静默丢失。攒批 + 保持 sync 才是正路。
7
单行超大（MB 级 Cell）
读一行把整个 block 拉进内存，BlockCache 被撑爆。大对象走对象存储，HBase 只存指针；或 2.x 起用 MOB（Medium Object）特性。
8
按非 RowKey 字段直接查
原生 HBase 没有 WHERE，条件查只能全表 scan。要么 RowKey 设计覆盖查询模式，要么上 Phoenix 二级索引。
9
堆太小 / 不监控 GC，节点被 ZK 踢出
GC 停顿超过 session timeout，RegionServer 假死引发 region 迁移风暴。8~16g 堆 + MSLAB + 堆外 MemStore，GC 日志进监控。
10
不设 TTL/VERSIONS，数据无限增长
每个 Cell 默认多版本，旧版本不清理，HFile 只涨不减。建表就设 TTL 和 VERSIONS，靠 major compaction 回收。
自测

六道题

1. 用时间戳做 RowKey 前缀（如 20261017_xxx）会有什么问题？
正确答案：写入热点。单调递增的 RowKey 让所有写都落在尾部 Region，其他 RegionServer 闲置，直到该 Region 分裂。解法：盐值前缀（hash % N）、哈希前缀、或时间戳倒排（Long.MAX_VALUE - timestamp）。
2. HBase 一次 put 的正确路径顺序是？
正确答案：先 WAL 再 MemStore，然后才 ack。WAL 是崩溃恢复的保证，必须落在数据进内存之前；HFile 是 MemStore 刷盘（满 128MB）的产物，不是写路径的一环。异步删除大块时 UNLINK 式的优化不存在于 HBase，ack 时机由 WAL sync 策略决定。
3. 关于 HBase 的一致性，哪个说法是对的？
正确答案：单行原子强一致，跨行不保证。一行数据只属于一个 Region、一台 RegionServer，这是强一致的物理基础；increment、checkAndPut 提供单行 CAS。多行原子要靠业务设计（把数据放同一行）或换 NewSQL。
4. Region 什么时候会自动分裂？
正确答案：超过 max.filesize（默认 10GB），从中间 split 成两半。生产建议 Region 保持 10~20GB。新表只有 1 个 region 时要手动预分区，否则前期所有读写集中在一台机器。
5. Phoenix 中，哪种二级索引查询时不需要回查数据表？
正确答案：Covered Index。用 INCLUDE 把返回列塞进索引，查询在索引表一次拿全，省掉第二次 RPC。Global 是先查索引再回表（两次 RPC），Local 是同 Region 单次 RPC 但仍要扫数据。
6. HBase 和 Cassandra 最核心的区别是？
正确答案：一致性模型。两者底层都是 LSM 列族存储，但 HBase 选 CP（单行强一致、中心化 Master 架构），Cassandra 选 AP（去中心化、QUORUM 可调）。HBase 强在范围扫描和 Hadoop 生态，Cassandra 强在多活部署和高写入弹性。

# hbase-site.xml 里最该盯的
hbase.hregion.max.filesize: 10g                  # Region 分裂大小，10~20GB 区间
hbase.hregion.memstore.flush.size: 128m          # MemStore 刷盘阈值
hbase.hstore.compactionThreshold: 3              # minor compaction 触发文件数
hbase.hregion.majorcompaction: 604800000         # major 间隔，默认 7 天

hbase.bucketcache.size: 2048                     # MB，堆外 BlockCache
hbase.regionserver.region.split.policy: ConstantSizeRegionSplitPolicy  # 2.x 默认

术语表

术语一句话解释
LSM 树日志结构合并树：写全部顺序追加，排序合并后台做，用读放大换写性能
WAL / HLog预写日志，崩溃恢复的唯一保证，先落 WAL 再写 MemStore
MemStore每个列族的内存有序缓存（跳表），写满 128MB 刷成 HFile
HFile / StoreFile磁盘上的不可变有序文件，带布隆过滤器和多级索引块
Store一个列族在一个 Region 内的存储单元 = MemStore + 多个 HFile
Compaction把小 HFile 合并成大 HFile 的后台过程，删除标记在此物理生效
Minor Compaction合并部分小文件，代价小，触发频繁
Major Compaction合并整个 Store 全部文件，彻底清理删除/过期数据，IO 尖刺来源
Region一段连续 RowKey 区间，分布式和分裂的最小单元，归属单台 RegionServer
RegionServer托管 Region 的进程，读写、flush、compaction 都发生在这里
HMaster管理面：region 分配、split、迁移、负载均衡，不在数据路径
RowKey行的唯一键，全局字典序，唯一的索引，决定数据分布
列族 ColumnFamily列的物理分组，独立 MemStore 和 compaction，建议 1~2 个
Cell最小存储单元 = RowKey + 列族 + 限定符 + 时间戳 + 值
盐值 SaltingRowKey 加哈希前缀打散写入，防热点，牺牲范围扫描
时间戳倒排Long.MAX_VALUE - timestamp 做前缀，把热点从尾部摊平的技巧
BlockCacheHFile 数据块的读缓存，命中率是读性能生命线
布隆过滤器HFile 级的"这行不在这个文件"快速判断，ROW 级读优化必开
MSLABMemStore 的块化预分配缓冲，消灭 JVM 堆碎片
checkAndPut检查-然后写的单行原子操作，HBase 版乐观锁
PhoenixHBase 上的 SQL 层，提供二级索引、JOIN 和 JDBC
Global IndexPhoenix 的独立表索引，异步更新，查询两次 RPC
Local Index与数据同 Region 的索引，同步维护单次 RPC
Covered Index索引含返回列的覆盖索引，查询不回表
