开始前

起一个能练的主从环境

# MySQL 8.0 主库配置（my.cnf）
[mysqld]
server-id = 1
log-bin = mysql-bin
binlog_format = ROW                  # 生产必须 ROW，原因见模块 2
gtid_mode = ON
enforce-gtid-consistency = ON

# 从库配置（另一台/另一个容器）
[mysqld]
server-id = 2
relay-log = relay-bin
read_only = 1
super_read_only = 1                  # 连 root 都不能写，防误操作

# 创建复制账号（主库执行）
CREATE USER 'repl'@'%' IDENTIFIED BY 'ReplPass123';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

# 从库执行（8.0.23+ 语法）
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='master-ip',
  SOURCE_PORT=3306,
  SOURCE_USER='repl',
  SOURCE_PASSWORD='ReplPass123',
  SOURCE_AUTO_POSITION=1,            # 用 GTID 自动定位，不用记 binlog 文件名
  GET_SOURCE_PUBLIC_KEY=1;
START REPLICA;
SHOW REPLICA STATUS\G

模块 1

三种复制模式：RPO 由什么决定

复制模式的差别只在一点：主库返回"写入成功"给客户端时，从库到底收到没有。这一个差别决定了故障时丢多少数据（RPO）。

模式行为RPO 与取舍
异步复制主库写完 binlog 就向客户端确认，不等从库RPO > 0，主库宕机可能丢已确认的事务。写性能最好，从库故障完全不影响主库
半同步复制主库等至少一个从库确认收到 binlog 才向客户端确认RPO = 0（收到即不丢）。写延迟增加一个网络 RTT，从库无响应会拖慢主库
同步复制主库等所有从库都应用完才确认最强一致，但任何一个从库卡住整个写入就卡住，生产中几乎不用全同步

MySQL 半同步的关键：wait point 选哪个

MySQL 的半同步有两个等待点，由 rpl_semi_sync_source_wait_point 控制，这是决定"切换丢不丢数据"的参数：

wait point确认时机故障后果
AFTER_SYNC
（默认，推荐）		从库收到 binlog 事件并写入 relay log（未执行）就确认主库宕机时，已确认的事务都已在从库 relay log 里，从库升级后先应用 relay log 再开放写，不丢数据
AFTER_COMMIT主库先在存储引擎提交、再等从库确认主库在"已提交但没等到从库确认"时宕机，客户端以为成功其实丢了；且主库提交后无法回滚
# 安装插件（MySQL 8.0）
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';

# 主库开启半同步（8.0.23+ 参数名）
SET GLOBAL rpl_semi_sync_source_enabled = 1;
SET GLOBAL rpl_semi_sync_replica_enabled = 1;      # 从库也要开！
SET GLOBAL rpl_semi_sync_source_wait_point = AFTER_SYNC;
SET GLOBAL rpl_semi_sync_source_timeout = 2000;    # 2 秒等不到就降级为异步，防止从库卡死拖垮主库

# 确认半同步真的在工作（重点看前两个字段）
SHOW GLOBAL STATUS LIKE 'Rpl_semi_sync_source_status';   # ON 才是生效，OFF = 降级了
SHOW GLOBAL STATUS LIKE 'Rpl_semi_sync_source_clients';  # 有几个半同步从库
SHOW GLOBAL STATUS LIKE 'Rpl_semi_sync_source_no_tx';    # 降级后写了多少个事务（>0 说明丢过数据）
半同步最大的坑：超时后静默降级。rpl_semi_sync_source_timeout 到期等不到从库，主库自动切回异步继续服务——不报错、不阻塞，但从这一刻起 RPO 从 0 变成"可能无限"。监控必须盯 Rpl_semi_sync_source_status，变成 OFF 立刻告警。这就是"号称零丢失的架构，故障时丢了几十分钟数据"的标准剧情。

PostgreSQL 的对应物：同步流复制

synchronous_commit确认条件
remote_apply从库应用完 WAL 才确认。最强一致，读从库一定读到
on从库收到并刷盘（flush）WAL 即确认（未应用）。默认值
remote_write从库收到并写入操作系统缓存即确认（没刷盘）
local只等本地刷盘。等价于异步复制
# PostgreSQL 主库配置
wal_level = replica
max_wal_senders = 10
synchronous_commit = on
synchronous_standby_names = 'FIRST 2 (s1, s2)'    # 前 2 个在线的同步备库确认即可提交
# 也常用 'ANY 1 (s1, s2, s3)'：任一个确认即可，比 FIRST 更可用

# 查看同步状态
SELECT pid, application_name, sync_state, write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
# sync_state: async / sync / potential / quorum

# 单条事务单独控制（对账类任务想异步就异步）
SET synchronous_commit TO local;
INSERT INTO audit_log ... ;      # 这条不等同步备库
PG 的 remote_apply 是个宝：主库提交时同步备库已经应用完了，此时把读流量切到从库不会读到旧数据，是真正的"写完读得到"。MySQL 的半同步（AFTER_SYNC）只保证"收到"不保证"应用完"，主从切换瞬间从库可能还差几秒的 relay log，所以切换脚本必须包含等从库追平（Seconds_Behind_Master=0）这一步。
模块 2

MySQL 复制链路与 GTID

三个线程的分工

主库 dump thread：从库的 IO 线程连上时，主库起一个 dump 线程把 binlog 事件推给它
从库 IO thread：接收 binlog 事件，写入本地 relay log
从库 SQL thread：读 relay log 并重放（单线程）→ 这就是延迟的根源，多线程并行复制（模块 4）就是优化这个线程

binlog_format 为什么必须 ROW

格式问题
STATEMENT记录 SQL 原文。NOW()、RAND()、UUID() 在主从执行结果不同，数据静默不一致。触发器和存储过程也有隐患
MIXEDMySQL 自动判断，大部分情况安全但边界 case 不可控
ROW
（生产唯一选择）		记录行变更前后镜像，语义绝对一致。代价是 binlog 体积大（可用 binlog_row_image=minimal 只记变化的列）
# 切换 binlog 格式（运行中改，影响之后的事务）
SET GLOBAL binlog_format = ROW;
SET GLOBAL binlog_row_image = minimal;    # 只记录修改的列，显著减小 binlog 体积

# 线上检查 replication 健康的核心字段
SHOW REPLICA STATUS\G
# 关注：
# Replica_IO_Running: Yes          —— IO 线程活着
# Replica_SQL_Running: Yes         —— SQL 线程活着
# Seconds_Behind_Source: 0         —— 秒级延迟（不可靠，见模块 4）
# Last_SQL_Errno / Last_SQL_Error  —— 重放失败原因（1062 主键冲突最常见）
# Retrieved_Gtid_Set / Executed_Gtid_Set —— 收到 vs 执行到的 GTID

GTID：全局事务 ID

GTID 格式：server_uuid:事务号，每台服务器唯一。主从建链时用 SOURCE_AUTO_POSITION=1，从库自动计算自己缺哪些事务，不用再手工记 master_log_file + master_log_pos——这是 GTID 最大的工程价值：主库切换、从库重建、级联复制都不怕位点对不上。

# 主库执行
SHOW GLOBAL VARIABLES LIKE 'gtid_mode';          # ON / OFF
SELECT @@global.gtid_executed;                   # 已执行的 GTID 集合
SHOW MASTER STATUS;                             # 当前 binlog 文件和位置

# 从库
SELECT @@global.gtid_executed;                   # 从库执行到哪了

# 经典故障：主库 binlog 被 purge 但从库还没取
# 报错：Got fatal error ... 'Cannot replicate because the master purged ...'
# 恢复思路：看从库缺哪段 GTID，从备份 + binlog 补，或用 pt-slave-restart 跳过损坏事务
GTID 跳号问题：从库 sql_slave_skip_counter（GTID 模式下应改用 SET GTID_NEXT='server_uuid:N' + 空事务 + BEGIN;COMMIT;）跳过冲突事务时，如果跳错会把从库数据改脏。跳过事务前必须先用 pt-table-checksum 确认影响范围，或者干脆重建从库——跳过一条 UPDATE 可能就是一次生产事故。
模块 3

PostgreSQL 流复制要点

# 主库：postgresql.conf
wal_level = replica                    # logical 表示还要发逻辑变更（逻辑复制）
max_wal_senders = 10                   # 并发 WAL 发送进程数（从库数 + 余量）
max_replication_slots = 10             # 复制槽数量
wal_keep_size = 2048                   # 保留的 WAL 量（MB），防止从库掉线期间 WAL 被清
synchronous_standby_names = 'ANY 1 (s1, s2)'

# pg_hba.conf：放行复制连接（复制专用条目，不是普通用户条目）
host replication repl 10.0.0.0/24 scram-sha-256

# 从库：用 pg_basebackup 拉基础备份
pg_basebackup -h primary -D $PGDATA -U repl -P -R -X stream -S slot_s1
# -R 自动写 standby.signal 和 primary_conninfo；-S 用复制槽；-X stream 边传边收 WAL

# 从库关键文件与参数
standby.signal                        # 有这个文件就是备库模式（PG 12+）
hot_standby = on                       # 备库可读（默认 on）
max_standby_streaming_delay = 30s      # 备库查询冲突时最多等 30s 再取消查询
primary_slot_name = slot_s1            # 用哪个复制槽（防 WAL 被清理）

复制槽：WAL 的保险与地雷

复制槽让主库保留从库还没取走的 WAL，从库掉线几天再上线也能续传。但槽不回收，主库 WAL 会无限堆积——复制槽相关事故占 PG 运维事故的很大比例：从库下线忘删槽，几天后主库磁盘满，集群雪崩。

# 主库查复制槽状态（重点看 restart_lsn 和 retained_wal）
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots;

# 查 WAL 总体积和磁盘占用
SELECT pg_size_pretty(sum(size)) FROM pg_ls_waldir();

# 从库下线：先删槽（确认从库不再回来）再停
SELECT pg_drop_replication_slot('slot_s1');

# 查复制延迟（PG 12+，比字节差直观）
SELECT application_name,
       pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS lag_bytes
FROM pg_stat_replication;
备库查询冲突：备库重放 WAL 时要清理与查询冲突的行（VACUUM 删除的行正在被读），超过 max_standby_streaming_delay 就取消查询并报 canceling statement due to conflict with recovery。长查询被反复取消时，要么调大延迟，要么把重查询路由到主库。这是"从库读数莫名报错"的常见根因。

逻辑复制槽：异构与选择性复制

wal_level=logical 后可以建 publication/subscription，按表粒度复制，且从库可写（物理备库只读）。适合：报表库按需订阅几张表、PG 大版本升级（逻辑复制做零停机迁移）、异构数据库间同步。逻辑复制不复制 DDL 和序列值，切流前要手工对齐表结构和自增值。

# 主库：发布（PG 10+）
CREATE PUBLICATION pub_orders FOR TABLE orders, order_items;
# 订阅端
CREATE SUBSCRIPTION sub_orders CONNECTION 'host=primary dbname=prod user=repl'
  PUBLICATION pub_orders WITH (copy_data = true, create_slot = true);

# 查订阅状态和延迟
SELECT subname, latest_end_lsn, last_msg_send_time, last_msg_receipt_time FROM pg_stat_subscription;
模块 4

复制延迟：原因与处理

延迟的本质：从库重放速度跟不上主库产生速度。排查先分清是"偶发尖刺"还是"持续追赶不上"。

原因机制处理
大事务一个 UPDATE 扫 500 万行，从库重放要 60 秒，从库整体延迟 60 秒拆事务（每批 1 万行提交一次）；大表变更走在线工具（pt-osc、gh-ost）
SQL 线程单线程从库 SQL thread 一个线程重放所有库的 binlog开并行复制（见下）
无主键/低选择性索引ROW 格式下从库按主键定位行，全表扫补主键；大表加合适索引
从库硬件差磁盘 IOPS 跟不上，relay log 重放慢主从同规格；SSD；分离读流量
备库被长查询占用（PG）热点行冲突导致 WAL 重放被频繁取消/等待调 max_standby_streaming_delay；长查询路由主库
# MySQL 并行复制（5.7+ 逻辑时钟方案，按库分并发重放）
slave_parallel_type = LOGICAL_CLOCK
slave_parallel_workers = 8              # 通常 4~16，超过 CPU 核数无益
slave_pending_jobs_size_max = 134217728 # 等待队列缓冲上限（128MB），防大事务 OOM

# 确认并行复制生效
SHOW REPLICA STATUS\G
# 关注 Slave_parallel_workers > 1

# 大事务治理（源头）
SET GLOBAL binlog_group_commit_sync_delay = 100;   # 微妙级：等 100μs 攒一批提交，减少 fsync
# 治标不治本，真正的大事务要在应用层拆
Seconds_Behind_Master 是个会撒谎的字段：它的计算方式是"当前时间 - 最后一个重放事件的时间戳"。如果主库 10:00 产生了一个大事务，从库 10:05 开始重放到 10:06 完成，重放期间这个字段显示 0（因为事件时间戳是 10:00），重放完成后突然跳到 300。可靠做法：MySQL 用 Heartbeat（或 pt-heartbeat 表，每秒钟更新一次，从库读表和主库时间差）；PG 用 pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) 按字节算。监控告警必须用可靠指标，否则"切换时从库还差 5 分钟"这种事根本发现不了。
降延迟三板斧（按见效速度排序）：① 拆大事务（收益最大， bulk insert/update 每 5000~10000 行 COMMIT）；② 开并行复制（slave_parallel_workers=8）；③ 补主键。补一条反直觉的：给主库降写入压力（合并批量、去掉不必要的更新）往往比优化从库更有效——延迟是"产"和"消"的速度差，只优化消不解决产。
模块 5

主从切换与数据一致性校验

切换的标准流程（以 MySQL 为例）

等从库追平：pt-heartbeat 或 GTID 对比确认 Seconds_Behind_Source=0 且持续几秒稳定
堵写：主库 SET GLOBAL read_only=ON（等业务连接自然断开，或先摘流量）
确认从库无遗漏：对比主从 gtid_executed，从库 ⊇ 主库才算齐
提主：从库 STOP REPLICA; RESET REPLICA ALL; → SET GLOBAL read_only=OFF → 业务切连接
旧主转从：等旧主恢复后挂到新主下（GTID 模式下直接 CHANGE REPLICATION SOURCE TO + AUTO_POSITION）
# 对比 GTID 集合（从库执行，主库执行，肉眼比对）
SELECT @@global.gtid_executed;

# 自动化工具（可选）：MHA / Orchestrator / 自研脚本
# 云上直接用 RDS 的切换 API，内核已封装上述流程

pt-table-checksum：在线校验主从一致性

原理：在主库上按 chunk（默认 1000 行，用索引切分）计算每块的 CRC32 校验和，通过复制流把校验语句复制到从库执行，再对比两边结果。全程在线、低负载，是业界标准做法。

# 校验整个库
pt-table-checksum \
  --host=primary --user=root --password=xxx \
  --databases=order_db \
  --replicate=percona.checksums \        # 把结果写到主库的这张表，随复制流到从库
  --recursion-method=dsn \               # 自动发现所有从库（在从库上建 dsns 表或用 processlist）
  --chunk-time=1                          # 每 chunk 最多跑 1 秒，控制对主库的影响

# 查结果（主库执行，含所有从库的差异行数）
SELECT db, tbl, chunk, this_crc, master_crc, cnt, this_cnt
FROM percona.checksums
WHERE master_cnt <> cnt OR master_crc <> this_crc;

# 只校验最近变更（增量校验，适合定期巡检）
pt-table-checksum --replicate-check-only --databases=order_db

# 修复差异（先 --dry-run 看，再加 --execute 真修）
pt-table-sync --execute --print \
  h=primary,u=root,p=xxx,D=order_db,t=orders \
  h=replica1,u=root,p=xxx
pt-table-checksum 的三个使用前提：① 表必须有主键或唯一索引（否则按索引切分 chunk 会漏行/重复行）；② binlog_format 必须是 ROW（STATEMENT 下校验语句在从库重放结果不可预期）；③ 大表会跑很久，用 --chunk-size 控制单批行数。只校验不修复等于没做——计划里必须包含修复步骤和修复后的二次校验。
PG 的对应做法：逻辑校验用 pg_dump 对比或自写 checksum（按主键范围聚合 md5(string_agg(...))，主备各跑一次对比）；物理一致性由 WAL 的每页 full_page_writes + 校验和机制保证。跨版本升级用逻辑复制（publication/subscription）做双跑校验，比物理流复制更适合异构。
模块 6

CAP 与一致性模型谱系

CAP 定理：网络分区（P）发生时，一致性（C）和可用性（A）只能二选一。注意是"分区发生时"，不是常态下的三选二——这是最常被误引用的地方。

系统类型分区时的选择代表
CP 系统放弃可用：少数派分区停止服务，等网络恢复etcd、ZooKeeper、TiKV、PolarDB 共识层
AP 系统放弃一致：继续服务，接受短暂不一致，恢复后合并Cassandra、DynamoDB、Redis Cluster
CA 系统不存在（分区不可避免）。单机数据库是"不需要分区"的特例——

一致性模型的强弱谱系

模型保证例子
强一致（线性一致）所有读都读到最新写，像单副本一样etcd/ ZooKeeper 的读；Raft apply 后的读
顺序一致所有节点看到相同的操作顺序，但不一定是实时顺序共识日志的顺序保证
因果一致有因果关系的操作保序，无因果的可乱序评论回复必须晚于评论出现
读己之写自己写完后，自己一定能读到刚发的朋友圈刷新后必须可见
最终一致不再有新写时，所有副本最终收敛到相同值DNS 传播、缓存刷新、异步复制
# 工程含义对照（选架构时对着看）
转账余额          → 强一致（DB 事务 / 共识）
库存扣减          → 强一致（唯一约束 / 分布式锁）
订单状态查询      → 读己之写（写后路由主库读，或版本号比对）
点赞数、粉丝数    → 最终一致（计数器异步聚合）
配置、功能开关    → 最终一致（可容忍分钟级生效）
日志、埋点        → 尽力而为（可丢）

分布式共识：Paxos 与 Raft

共识问题：一组机器如何对某个值达成一致，并且在少数机器故障时仍能工作。两个前提假设：节点会故障（crash）、消息会丢失/延迟但不会篡改（异步网络 + 多数派诚实）。

算法核心机制工程地位
PaxosProposer/Acceptor/Learner 两阶段（Prepare + Accept），多数派持久化即达成理论基石，难懂难实现，直接用在生产的很少
RaftLeader 选举（term + 心跳）+ 日志复制 + 安全性约束（只复制 leader 日志）工程主流：etcd、TiKV、Consul、ClickHouse Keeper、OceanBase Paxos（化用）
# Raft 的关键数字与规则
多数派 = N/2 + 1                    # 3 节点容忍 1 故障，5 节点容忍 2 故障
leader 选举：term 递增 + 随机超时   # 随机化打破选票僵局
提交条件：多数派持久化即提交      # 这就是"写成功"的定义
日志连续性：只追加不修改            # 冲突日志整段丢弃，保证安全性
读操作：默认 leader 读（或 read index 保证线性一致）
为什么主流数据库都往共识协议上靠：MySQL 半同步是"1 主 1 从确认"的弱共识，故障判定靠超时和人工；PG 的 quorum commit 用 ANY 1 做多数派思想；而 TiKV/OceanBase/CockroachDB 直接用 Multi-Raft，把"不丢数据"从配置参数变成协议保证——这是现代分布式数据库和传统主从架构的分水岭。
模块 7

脑裂与仲裁机制

脑裂（split-brain）：网络分区后，两侧都认为自己还是主，都接受写。等网络恢复，两边数据冲突，无法自动合并。所有 HA 设计的核心就是让分区中只有一侧能当主。

多数派仲裁
3 节点集群，2 节点在线才能选举出主。少数派自动降级为只读。etcd/Raft 的标准做法，最可靠
仲裁节点/witness
引入不存数据的第三节点参与投票，2 节点机房 + 1 个 witness 即可自动仲裁。MySQL MHA、Redis Sentinel 都用类似思路
Fencing（隔离）
把旧主"杀掉"或"断供"：STONITH（重启对方）、关闭存储访问、撤销网络路由。光"降级"不够，必须让旧主物理上写不进去
租约/epoch
主带租约（lease），超时失效；每次切换 epoch 递增，旧主写入因 epoch 过期被拒绝
# MySQL 侧防脑裂的具体手段
# 1. 半同步 + 只读兜底：主库检测到半同步降级（status=OFF）时自动 set read_only
#    靠巡检脚本或 group_replication 的 group_replication_switch_to_multi_primary 控制
# 2. MHA：从库变主后给旧主发 kill 命令（STONITH 思想）
# 3. 网络层：VIP 只指向一个主，切换时先撤 VIP 再切

# PostgreSQL 侧
synchronous_standby_names = 'ANY 1 (s1, s2)'     # 至少 1 个同步备确认，多数派思想
# 配合 repmgr/patroni 的 leader lease + DCS（etcd/ZooKeeper）做自动仲裁

# 判断是否可以安全提主的命令（PG patroni 场景）
patronictl -c /etc/patroni.yml list        # 看集群状态和 Leader
patronictl -c /etc/patroni.yml switchover   # 受控切换（先等从库追平）
没有仲裁的 HA 等于定时炸弹。最经典的剧本：一主一从 + 异步复制，中间网络抖动，从库被提升为主，业务双写几分钟，网络恢复后两边都有"对方没有"的订单。规则：任何自动切换都必须先回答三个问题——① 少数派怎么阻止自己当主？（read_only/多数派）② 旧主怎么被强制闭嘴？（fencing）③ 出现双写怎么发现、怎么合并？（校验 + 人工决策，自动合并冲突数据基本不现实）。
实践建议（按规模递进）：单机房一主两从 → 用半同步 + 脚本化切换（人工确认）；跨机房/不能停机 → 上 MHA、Orchestrator 或 PG 的 Patroni+etcd，让专业工具处理选主和 fencing；对 RPO=0 有硬要求 → 直接选 Multi-Raft 内核的分布式数据库（TiDB/OceanBase/PolarDB-X），别在主从复制上打补丁。
模块 8

十个线上坑

1
半同步静默降级成异步，没人发现
从库超时后主库自动降级继续服务，RPO 从 0 变无限，故障时丢几十分钟数据。必须监控 Rpl_semi_sync_source_status，OFF 立即告警。
2
wait point 用了 AFTER_COMMIT
主库已提交但从库没收到时宕机，客户端收到成功但数据丢了，且无法回滚。用默认的 AFTER_SYNC，保证已确认事务都在从库 relay log 里。
3
binlog_format 用了 STATEMENT
NOW()/RAND()/UUID() 在主从执行结果不同，数据静默不一致，checksum 才能发现。生产一律 ROW。
4
拿 Seconds_Behind_Master 当切换依据
大事务期间这个值会显示 0（时间戳是旧的），切换过去数据差一大截。用 pt-heartbeat 或 GTID 对比确认追平。
5
从库没开 super_read_only
read_only 对 root 和 SUPER 权限无效，业务误连从库写了一条 UPDATE，切换时冲突或数据丢。必须 super_read_only=1。
6
没开并行复制，一个大事务卡死从库
SQL thread 单线程重放，60 秒的大事务让从库延迟 60 秒，期间所有读从库的业务看到旧数据。开 slave_parallel_workers + 拆大事务。
7
主库 binlog 过期，从库断线续不上
从库宕机几天，主库 log 被 purge，报 "master purged required logs"。根治是 GTID + 自动重建从库，别硬跳 GTID。
8
PG 复制槽不监控，主库磁盘被 WAL 打满
从库下线忘删槽，主库为它保留 WAL，几天后磁盘满集群雪崩。监控 restart_lsn 和 retained WAL 大小，设告警。
9
切换后从不做一致性校验
以为"追平了"就一致，其实冲突跳过的 GTID 早已埋雷。定期 pt-table-checksum 巡检，切换后立刻全量校验。
10
一主一从异步复制，无任何仲裁
网络分区后人工在两个"主"之间决策，双写几分钟才发现。至少一主两从 + 半同步 + 自动切换工具，别赌网络永远不抖。
自测

六道题

1. MySQL 半同步复制中，rpl_semi_sync_source_wait_point 应该选哪个？为什么？
正确答案：AFTER_SYNC。它在从库收到 binlog（未执行）时就确认，主库此时尚未提交；万一主库宕机，从库有全部已确认事务的 relay log，应用后即可安全提主。AFTER_COMMIT 是主库先提交再等从库，主库在"已提交未确认"窗口宕机会丢已告知用户成功的数据。
2. 关于半同步的超时降级，正确的认识是？
正确答案：静默降级。超时（默认 10 秒，建议调短到 1~2 秒）后主库以异步模式继续服务，从这一刻 RPO 从 0 变成可能无限，而业务毫无感知。必须监控 Rpl_semi_sync_source_status，OFF 立即告警。
3. 从库延迟 60 秒，最可能的根因和处理是？
正确答案：大事务 + SQL 线程单线程。ROW 格式下从库重放速度取决于事务大小，一个 500 万行的 UPDATE 要重放几十秒，期间从库整体延迟。处理：应用层拆批（每批 1 万行提交）+ slave_parallel_workers=8 + 大表变更用 gh-ost/pt-osc。
4. PostgreSQL 想让"写完立刻读从库也一定读到"，应该配？
正确答案：remote_apply。它要求同步备库应用完 WAL 才向主库返回提交成功，此时从库数据已最新，读从库不会读到旧值。on 只保证从库收到并 flush，未应用；local 等于异步。
5. 关于 CAP 与共识，说法正确的是？
正确答案：分区发生时二选一。CAP 常被误引成"平时三选二"，实际 P（分区）不可避免，讨论的是分区期间的选择。Raft 用 leader 选举 + 多数派日志复制实现 CP：少数派分区停止服务保一致，etcd/TiKV 是其工程代表。
6. 防止脑裂最有效的手段组合是？
正确答案：仲裁 + fencing。心跳再快也分不清"对方死了"还是"网络断了"，唯一可靠的区分办法是多数派投票；而光让旧主"知道"自己该退位不够，必须让它物理上写不进去（fencing），否则它可能在收到通知前继续接受写入造成双写。
