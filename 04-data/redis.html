开始前

起一个能练的环境

# 一条命令起一个 Redis（用你第 2 期学的 Docker）
docker run -d -p 6379:6379 --name redis redis:7-alpine

# 连上去
docker exec -it redis redis-cli

# 常用元命令
PING              # PONG 表示活着
INFO server       # 看版本、运行时长
DBSIZE            # 当前库有多少 key
SELECT 1          # 切换库（默认 0-15 共 16 个库，但生产建议只用 0）
FLUSHALL          # 清空所有数据（危险）
一个反直觉的点：Redis 的"16 个库"是单实例内的逻辑隔离，不是分布式分片。而且集群模式下只有 db 0。生产环境建议只用 db 0，靠 key 前缀区分业务。
模块 1

为什么 Redis 这么快

原因说明
纯内存操作最根本的原因。内存随机读写比磁盘快几个数量级
单线程模型命令串行执行，没有锁竞争、没有线程切换开销，还天然保证了单个命令的原子性
IO 多路复用一个线程用 epoll 管理成千上万个连接，不是"一个连接一个线程"
高效的数据结构为每种类型定制底层编码，小数据用紧凑结构（如 ziplist），大数据才切换
必须纠正的一个认知：Redis 的"单线程"指的是"命令执行"是单线程。
实际上 Redis 6.0 之后，网络 IO 是多线程的（读请求、写响应可以并行），只有命令的执行仍然是单线程。另外持久化、异步删除（UNLINK）等也是在后台线程做的。
关键推论：任何一条慢命令都会阻塞整个实例。所以 KEYS *、FLUSHALL、大 key 的 DEL 在线上都是事故制造机 —— 它们执行期间，所有其他请求都得排队。
模块 2

五种基本数据结构

类型结构典型场景
String字符串 / 数字 / 二进制缓存对象（JSON 序列化）、计数器、分布式锁、Session 共享
Hash字段 → 值 的映射存对象的部分字段、购物车。比 String 存整个 JSON 更省内存，且能单独改字段
List双向链表消息队列（简单版）、最新列表、时间线
Set无序不重复集合去重、标签、共同好友（交集）、抽奖（随机取）
ZSet有序集合（带分数）排行榜、延时队列、范围查询
# ===== String =====
SET user:1:name "张三"
GET user:1:name
SETEX code:13800000000 300 "8848"      # 带过期时间，验证码场景
SET lock:order:42 "uuid-xxx" NX EX 30   # 分布式锁的标准写法
INCR article:100:pv                   # 原子自增，天然适合计数器
INCRBY counter 10
MSET k1 v1 k2 v2                       # 批量，比循环 SET 快得多

# ===== Hash =====
HSET user:1 name "张三" age 28 city "北京"
HGET user:1 name
HGETALL user:1
HINCRBY user:1 age 1
HGETALL 在小 hash 上没问题，但大 hash（几万字段）要避免，会阻塞

# ===== List =====
LPUSH queue:tasks "task1"              # 左边进
RPOP queue:tasks                       # 右边出 → 简易 FIFO 队列
BRPOP queue:tasks 5                    # 阻塞版：没数据就等 5 秒（推荐，避免空轮询）
LRANGE news:latest 0 9                # 取最新 10 条
LTRIM news:latest 0 99                # 只保留 100 条，其余裁掉

# ===== Set =====
SADD article:100:tags "redis" "cache"
SISMEMBER article:100:tags "redis"     # O(1) 判断存在，比 List 遍历快
SINTER user:1:friends user:2:friends   # 共同好友
SRANDMEMBER lottery 3                  # 随机抽 3 个（不删除）

# ===== ZSet =====
ZADD rank 100 "张三" 200 "李四"
ZREVRANGE rank 0 9 WITHSCORES          # 排行榜前 10
ZRANK rank "张三"                      # 查排名
ZINCRBY rank 10 "张三"                 # 加分
ZRANGEBYSCORE rank 100 200            # 按分数范围查
ZSet 做延时队列很实用：把"要执行的时间戳"当分数，然后轮询 ZRANGEBYSCORE queue 0 当前时间戳 LIMIT 0 10，取出来的就是到期的任务。比用定时扫表优雅。

四种高级结构

类型用途关键命令
Bitmap签到打卡、活跃用户统计。一个用户一天只占 1 bitSETBIT / GETBIT / BITCOUNT
HyperLogLog基数统计（UV）。用 12KB 就能统计上亿个不重复元素，误差约 0.81%PFADD / PFCOUNT

SETBIT sign:1001:202603 5 1
BITCOUNT sign:1001:202603              # 本月签到天数
# 100 万用户的日活，用 Bitmap 只占 125KB

PFCOUNT uv:20260305                    # 约等于去重后的用户数
# 注意：只能估数，不能取出具体是谁。要精确值就得用 Set，但内存大得多

# GEO 附近的人

模块 4

过期与内存淘汰

这两件事经常被混为一谈，其实是两套机制。

机制触发条件说明
过期删除key 到达 TTLRedis 用"惰性删除 + 定期抽样删除"。所以过期了不一定立刻消失，可能还占着内存
内存淘汰内存达到 maxmemory按 maxmemory-policy 策略淘汰 key，腾出空间
EXPIRE key 60          # 60 秒后过期
TTL key                # 剩余秒数。-1 表示永不过期，-2 表示 key 不存在
PERSIST key            # 移除过期时间
SET k v EX 60          # 设值同时设过期，原子操作

八种淘汰策略

策略行为
noeviction默认值。不淘汰，内存满了直接报错。适合当数据库用、不能丢数据的场景
allkeys-lru在所有 key 中淘汰最近最少使用的。纯缓存场景的首选
allkeys-lfu淘汰访问频率最低的。比 LRU 更适合"热点数据稳定"的场景
allkeys-random随机淘汰。一般不用
volatile-lru / lfu / ttl / random只在设置了过期时间的 key 里淘汰。适合"缓存和持久数据混用同一实例"
最容易踩的坑：用了默认的 noeviction。内存写满后所有写操作直接报错 OOM command not allowed，服务瞬间不可用。
纯缓存场景一定配 maxmemory-policy allkeys-lru，并设置 maxmemory（通常是物理内存的 70%~75%，要留出持久化 fork 的空间）。
模块 5

持久化：RDB 与 AOF

方式原理优缺点
RDB定时把内存数据快照写入磁盘（二进制）文件小、恢复快。但两次快照之间的数据会丢
AOF把每条写命令追加到日志文件丢数据少（最多丢 1 秒）。文件大、恢复慢
混合持久化RDB 全量 + AOF 增量（Redis 4.0+）推荐。兼顾恢复速度和数据安全
# RDB 配置
save 900 1          # 900 秒内至少 1 个 key 变化就触发快照
save 300 10
save 60 10000

# AOF 配置
appendonly yes
appendfsync everysec    # 每秒刷盘（推荐）。always 最安全但最慢，no 由系统决定
aof-use-rdb-preamble yes  # 开启混合持久化
RDB 的 fork 陷阱：生成快照时 Redis 会 fork 一个子进程，fork 期间会短暂阻塞主线程（内存越大阻塞越久）。而且写时复制会让内存占用短暂翻倍。
所以：① 内存不要超过物理内存的 75%；② 大实例（比如 32G 以上）建议在从库上做持久化，别在主库做；③ 注意系统是否开了透明大页（THP），它会让 fork 变得很慢，Redis 官方建议关掉。
模块 6

缓存三大问题（必考必踩）

这三个词是后端面试的常客，也是线上事故的常客。它们的区别在于问题出在哪一层。

问题现象根因
缓存穿透大量请求查根本不存在的数据，每次都打到数据库恶意攻击，或查询了不存在的 ID
缓存击穿某一个热点 key 过期瞬间，大量并发请求同时打到数据库单个热点数据过期
缓存雪崩大量 key 同时过期，或 Redis 整体宕机，数据库被压垮过期时间设置得过于集中

缓存穿透的两种解法

# 方案一：缓存空值（简单有效）
查库发现不存在 → 往 Redis 写 key = "NULL"，TTL 设短一点（如 60 秒）
下次同样的请求直接命中这个空值，不再查库

# 方案二：布隆过滤器（适合数据量大的场景）
启动时把所有合法 ID 加载进布隆过滤器
请求先过过滤器：说不存在就一定不存在，直接拒绝

# 注意：布隆过滤器说"存在"可能是误判，说"不存在"一定准确
# 所以它只能拦掉"肯定不存在"的请求，不能完全替代缓存空值

缓存击穿的解法

# 方案一：互斥锁 —— 只让一个请求去查库，其他等待
SET lock:hotkey uuid NX EX 10
拿到锁的请求查库并回填缓存，没拿到的短暂等待后重试

# 方案二：逻辑过期 —— 热点 key 永不过期，值里存一个逻辑过期时间
发现逻辑过期后，异步开一个线程去更新，当前请求先返回旧数据
# 优点：请求永远不阻塞。缺点：会短暂返回旧数据

缓存雪崩的解法

  • 过期时间加随机值：EXPIRE key (3600 + random(0,600))，避免同时失效
  • 多级缓存：本地缓存（Caffeine）+ Redis，Redis 挂了还有本地兜底
  • 高可用架构：主从 + 哨兵 / Cluster，避免单点故障
  • 限流降级：数据库前面加限流，Redis 挂了时直接降级返回兜底数据，别把库打穿
一句话记住三者区别：穿透是查不存在的数据（缓存和库都没有），击穿是一个热点 key 过期，雪崩是一批 key 同时过期或 Redis 整体挂了。
模块 7

缓存与数据库一致性

这是分布式系统里没有完美解的问题。先接受一个事实：在并发场景下，缓存和数据库的强一致必须靠分布式锁或事务，代价极高。工程上追求的是"最终一致 + 极短的不一致窗口"。

方案对比

方案问题
先更新数据库，再更新缓存并发下会写脏：两个线程交错执行，缓存里可能留下旧值
先删缓存，再更新数据库删除后、更新前有请求进来，会把旧值读回缓存，之后一直脏
先更新数据库，再删缓存
（Cache Aside，推荐）		业界最常用。只有极小的概率出问题（读请求恰好在删除前读到了旧值并写入缓存）
延迟双删更新库前删一次，更新库后延迟几百毫秒再删一次。用来兜底那个极小概率
工程实践建议：
① 默认用 Cache Aside（先更新库，再删缓存），别用"更新缓存"，因为删除更简单也更不容易出错。
② 给缓存设过期时间——这是最终的兜底，就算出现短暂不一致，过期后自动恢复。
③ 对一致性要求极高的场景（如余额）不要用缓存，直接读库，或者用"读库 + 写库 + 缓存只做旁路加速"的模式。
④ 更彻底的方案是订阅数据库 binlog（Canal、Debezium 这类工具能像"从库"一样订阅数据库的变更日志，数据一改就收到通知），异步刷新缓存。这样业务代码不侵入，但引入了延迟。
模块 8

分布式锁

# 正确的加锁：SET key value NX EX seconds
SET lock:order:42 "uuid-abc-123" NX EX 30

# 为什么 value 要放一个唯一值？
# 为了解锁时能确认"这把锁是我加的"，避免误删别人的锁

# 错误的写法（两个常见错误）
SETNX lock:order:42 1      # ✗ 没有过期时间，进程崩了就死锁
EXPIRE lock:order:42 30    # ✗ 两条命令不原子，中间崩了照样死锁

# 解锁必须用 Lua 保证"判断 + 删除"的原子性
EVAL "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end" 1 lock:order:42 uuid-abc-123
两个必须知道的问题：
① 业务执行时间超过锁的过期时间怎么办？锁会自动释放，别的线程进来了，两个线程同时操作同一份数据。解法是看门狗（watchdog）：后台线程定期给锁续期。Redisson 已经内置了这个机制。
② 主从切换时锁会丢。主库加了锁还没同步到从库就宕机了，从库升主后锁就没了，另一个线程能拿到。这就是 Redlock 算法想解决的问题（向多数节点加锁），但 Redlock 本身在业界有争议（Martin Kleppmann 和 Redis 作者 antirez 有过著名论战）。
实践建议：用 Redisson（Java 生态最常用的 Redis 客户端，已经内置了看门狗、可重入锁、公平锁等完整实现），别自己手写。对正确性要求极高的场景（如资金），不要只靠 Redis 锁，要在数据库层加唯一约束或乐观锁做最终防线。
模块 9

其他高频实战场景

限流
固定窗口：INCR + EXPIRE，简单但临界点会突刺。
滑动窗口：用 ZSet 存时间戳。
令牌桶：用 Lua 脚本实现，最平滑
计数器
INCR 是原子的，天然适合点赞数、阅读量。高并发下可以先在本地聚合再批量写，减少 Redis 压力
Session 共享
多台应用服务器共享登录状态，把 Session 存 Redis。这是 Redis 最经典的用法之一
排行榜
ZSet 的 ZREVRANGE 天然就是排行榜。支持实时更新分数、查排名、查区间
消息队列
简单用 List 的 BRPOP；需要消费者组、ACK 就用 Stream。但高吞吐场景还是用 Kafka/RabbitMQ
去重
Set 的 SADD 返回值能告诉你是否已存在。海量去重用 Bitmap 或 HyperLogLog
模块 10

高可用：主从、哨兵、Cluster

方案解决什么局限
主从复制数据备份 + 读写分离（从库可分担读）主库挂了需要人工切换，不能自动故障转移
哨兵 Sentinel监控主库，挂了自动选举新主库并通知客户端本质还是单主写入，容量受单机限制
Cluster 集群数据分片，容量和吞吐可以水平扩展。16384 个槽位分给多个主节点运维复杂；多 key 操作要求 key 在同一个槽（用 hash tag 强制）
# Cluster 的多 key 限制与解法
MGET user:1 user:2         # ✗ 可能报 CROSSSLOT 错误（不在同一槽）
MGET {u1}:name {u1}:age    # ✓ 用 hash tag {} 强制路由到同一个槽
怎么选：数据量小、只要高可用 → 主从 + 哨兵。数据量大（单机内存放不下）或写吞吐高 → Cluster。云上通常直接用托管版，省掉运维。
模块 11

运维排查：大 key 与热 key

这两个是 Redis 线上事故的顶级元凶，必须会查。

大 key（单个 key 的 value 太大）

危害：操作它耗时长，会阻塞整个实例；网络传输慢；持久化和主从同步变慢。

# 1. 扫出大 key（用 SCAN 而不是 KEYS！）
redis-cli --bigkeys                    # 官方工具，会统计每种类型最大的 key
redis-cli --memkeys                    # 按内存占用排序

# 2. 看单个 key 的实际内存占用
MEMORY USAGE user:1:biglist

# 3. 看底层编码（能判断数据结构是否退化）
OBJECT ENCODING user:1:biglist
# listpack / ziplist = 紧凑编码（小数据）
# quicklist / skiplist / hashtable = 大数据结构（内存占用高）

# 4. 删除大 key 用 UNLINK 而不是 DEL
UNLINK bigkey       # 异步删除，不阻塞主线程

热 key（某个 key 的访问量极高）

危害：所有请求集中在一个节点上，该节点 CPU 打满，而集群其他节点很闲。

# 1. 开实时统计（注意：有性能开销，排查完记得关）
redis-cli --hotkeys                    # 需要 maxmemory-policy 是 lfu 系列
redis-cli --lfucounter

# 2. 用 monitor 抓实时命令流（只在排查时短时开启）
redis-cli monitor | head -10000

# 3. 客户端侧统计（更准，生产推荐）
# 在应用层埋点记录每个 key 的访问次数

其他必备排查命令

redis-cli --latency持续测延迟，看有没有周期性卡顿
SLOWLOG GET 10看最慢的 10 条命令
CONFIG SET slowlog-log-slower-than 10000设置慢日志阈值（微秒）
INFO memory看内存使用、碎片率
INFO stats看命中率（keyspace_hits / misses）
INFO replication看主从状态和同步偏移
CLIENT LIST看当前所有连接，排查连接泄漏
SCAN 0 MATCH user:* COUNT 100渐进式遍历 key，替代 KEYS
线上绝对不能用的四个命令：
KEYS * —— 遍历所有 key，key 多了直接卡死整个实例。用 SCAN 替代。
FLUSHALL / FLUSHDB —— 清库，误操作等于删库。用 CONFIG SET rename-command 把它禁用掉。
DEL 大key —— 同步删除会阻塞。用 UNLINK。
HGETALL 大hash —— 一次返回几万个字段，阻塞 + 撑爆网络。用 HSCAN 分批。
模块 12

十个线上坑

1
用了默认的 noeviction 淘汰策略
内存写满后所有写操作报 OOM 错误，服务瞬间不可用。纯缓存场景必须配 allkeys-lru。
2
线上执行 KEYS *
单线程执行，key 多了会阻塞整个实例几秒甚至几十秒。用 SCAN 替代。
3
用 DEL 删大 key
同步删除会阻塞主线程。用 UNLINK 异步删除。
4
分布式锁用 SETNX + EXPIRE 两条命令
不原子，中间宕机就死锁。正确写法是 SET key value NX EX 30 一条命令搞定。
5
解锁时不校验 value 直接 DEL
可能删掉别人加的锁。必须用 Lua 脚本做"判断 + 删除"的原子操作，或直接用 Redisson。
6
所有 key 设了相同的过期时间
到期时集中失效，数据库被瞬间打穿（雪崩）。过期时间要加随机偏移。
7
把 Redis 当数据库用，不设过期时间
内存只增不减，迟早 OOM。缓存数据一定要设 TTL。
8
主库上做持久化，内存又配得很大
fork 时阻塞时间长、写时复制导致内存翻倍，可能触发 OOM Killer。建议在从库上做持久化。
9
Cluster 模式下做跨槽的多 key 操作
报 CROSSSLOT 错误。用 hash tag（如 {user1}:name）把相关 key 强制路由到同一槽。
10
以为缓存能保证强一致
缓存与数据库的强一致在并发下代价极高。工程上追求最终一致 + 短不一致窗口，并始终给缓存设 TTL 兜底。
自测

六道题

1. 大量请求查询"根本不存在的用户 ID"，导致数据库压力暴增。这属于？
正确答案：缓存穿透。特点是查的数据在缓存和数据库里都不存在，所以每次请求都绕过缓存直达数据库。解法是缓存空值或布隆过滤器。
2. 某个爆款商品的缓存 key 过期瞬间，大量并发请求同时打到数据库。这属于？
正确答案：缓存击穿。关键在于"某一个热点 key"过期。解法是互斥锁或逻辑过期。而雪崩是"大批 key 同时过期或 Redis 整体挂掉"。
3. 正确的分布式锁加锁命令是？
正确答案：SET key value NX EX 30。它是一条原子命令，同时保证了"只在不存在时设置"和"带过期时间"。分两条命令写的话，中间崩溃就会造成死锁。
4. 关于 Redis 的"单线程"，哪个说法是对的？
正确答案：命令执行单线程。所以任何一条慢命令都会阻塞所有其他请求 —— 这就是为什么 KEYS * 和大 key 的 DEL 在线上是事故制造机。
5. 缓存与数据库一致性，业界最常用的方案是？
正确答案：先更新数据库，再删缓存。删比更新更不容易出错（避免并发写脏），而且配合 TTL 兜底，出问题的概率极小。追求强一致就不该用缓存。
6. 要删除一个 value 有几百万条记录的大 key，应该用？
正确答案：UNLINK。DEL 是同步删除，大 key 会阻塞主线程很久。UNLINK 把内存回收放到后台线程。另外 KEYS 本身在线上就是禁忌命令。

关键配置项

# redis.conf 里最该改的几个
maxmemory 4gb                      # 通常设物理内存的 70%~75%
maxmemory-policy allkeys-lru       # 纯缓存场景首选，别用默认的 noeviction
appendonly yes                     # 开启 AOF
appendfsync everysec               # 每秒刷盘，性能和安全平衡
aof-use-rdb-preamble yes           # 混合持久化
slowlog-log-slower-than 10000      # 慢日志阈值（微秒）
timeout 300                        # 空闲连接超时，防连接泄漏
