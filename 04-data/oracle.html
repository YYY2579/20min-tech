模块 1

实例、数据库与存储层次

Oracle 里"实例"和"数据库"是两个东西，这是理解后面所有机制的地基。

概念定义
数据库 Database磁盘上的一组文件：数据文件（.dbf）、控制文件、联机重做日志、参数文件（spfile/pfile）、归档日志、口令文件
实例 Instance内存结构（SGA/PGA）+ 后台进程。非 RAC 下一个实例只能挂载（mount/open）一个数据库
RAC多个实例同时挂载同一个数据库，靠共享存储和 Cache Fusion 协同

逻辑存储层次：表空间 → 段 → 区 → 块

层级说明要点
表空间逻辑容器，数据按表空间落盘。系统必备：SYSTEM、SYSAUX、UNDO、TEMP、USERS大表/热表独立表空间是基本运维习惯，便于单独扩容、迁移、备份
段 Segment一个逻辑对象占用的空间：表段、索引段、UNDO 段、临时段表空间里"段空间管理"分自动（ASSM，位图）和手工（MSSM，空闲列表），新建库默认 ASSM
区 Extent一组连续的 Oracle 块，段按需向表空间申请本地管理表空间（LMT）下由位图自动分配，基本不用操心
块 Block最小 IO 单位，默认 8KB（DB_BLOCK_SIZE），建库时定，之后不能改一个块 = 块头 + 行目录 + 行数据 + 空闲空间。PCTFREE 预留更新空间，防行迁移
-- 看库的整体布局
SELECT tablespace_name, status, contents FROM dba_tablespaces;
SELECT file_name, tablespace_name, bytes/1024/1024 AS mb, autoextensible
FROM dba_data_files;

-- 建一个独立表空间放大表（标准习惯）
CREATE TABLESPACE orders_ts DATAFILE '/u01/oradata/ORCL/orders01.dbf'
  SIZE 2G AUTOEXTEND ON NEXT 256M MAXSIZE 32G
  SEGMENT SPACE MANAGEMENT AUTO;

-- 高水位线与碎片
ANALYZE TABLE orders ESTIMATE STATISTICS;   -- 老方法，现在用 DBMS_STATS
SELECT table_name, num_rows, blocks, avg_row_len FROM dba_tables WHERE table_name = 'ORDERS';
和 MySQL/PG 的关键差异：MySQL 的 ibdata/独立表空间、PG 的 relation 文件都是"表 = 文件"的近似模型，而 Oracle 是严格分层：段可以跨多个数据文件，一个表空间可以装很多段，空间回收靠段扩展 + HWM 下移（SHRINK）。这决定了 Oracle 的空间治理思路完全不同：看段、看 HWM、看碎片，而不是看文件大小。
行链接/行迁移：一行装不进一个块（太长）或更新后放不下原位置，会拆到多个块（链接）或搬走留转发指针（迁移）。两者都让单行读取变成多次 IO。和 MySQL InnoDB 的行溢出（overflow page）是同一类问题的不同实现。
模块 2

SGA、PGA 与共享池

内存两大块

结构组成职责
SGA
（共享，全局）		共享池、Buffer Cache、Redo Log Buffer、Large Pool、Java Pool、Streams Pool所有会话共享。数据块缓存、SQL/PLSQL 解析结果、字典缓存都在这里
PGA
（私有，会话）		排序区、哈希区、会话内存、游标状态、位图合并区每个会话/进程私有。大排序、大哈希 JOIN 的工作区

SGA 组件逐个看

组件说明
共享池 Shared Pool库缓存（解析后的 SQL/PLSQL 及执行计划）+ 数据字典缓存（表/列/权限等）。共享池不足的经典报错是 ORA-04031
Buffer Cache数据块缓存，对应 MySQL 的 InnoDB Buffer Pool。块有多个替换池（DEFAULT/KEEP/RECYCLE），可给热表单独指定
Redo Log Buffer重做缓冲区，LGWR 刷到联机重做日志。提交的"落盘"指的就是它
Large Pool共享服务器（MTS）会话区、RMAN 备份、并行查询消息缓冲。不命中 Shared Pool 的 LRU 链

内存管理参数（11g 之后的自动管理思路）

参数作用
MEMORY_TARGET / MEMORY_MAX_TARGET自动内存管理（AMM）：SGA+PGA 一个总量，实例自动切分
SGA_TARGET / SGA_MAX_TARGET自动共享内存管理（ASMM）：只自动管 SGA，PGA 单独管
PGA_AGGREGATE_TARGETPGA 总量目标，排序/哈希工作区自动在其中分配
实践建议：生产用 ASMM 而不是 AMM。AMM 要求关掉 HugePages、且 /dev/shm 要够大，大内存机器上反而更难调。常见姿势：设 SGA_TARGET（+SGA_MAX_TARGET 留余量）、PGA_AGGREGATE_TARGET，用 v$memory_dynamic_components 看自动调整结果。

共享池与解析：硬解析 / 软解析

-- 解析次数与命中率（软解析占比低就是没绑变量）
SELECT * FROM v$sysstat WHERE name IN
  ('parse count (total)', 'parse count (hard)', 'execute to parse %');

-- 没绑变量的典型现场：text 相同、sql_id 不同的游标泛滥
SELECT sql_id, executions, sql_text FROM v$sql
WHERE parsing_schema_name = 'APP' AND sql_text LIKE '%WHERE order_id =%'
ORDER BY LAST_ACTIVE_TIME DESC;

-- 兜底参数（不推荐生产长期开）
ALTER SYSTEM SET cursor_sharing = FORCE SCOPE = both;   -- 强制字面量转绑定
ALTER SYSTEM SET session_cached_cursors = 200 SCOPE = spfile;  -- 会话游标缓存，减少软解析
硬解析是 Oracle 性能的第一杀手。每硬解析一次，就要扫共享池、拿 latch、算执行计划。应用 SQL 里字面量写死（WHERE id = 10086）时，游标数爆炸、shared pool latch 争用、CPU 飙升。正确姿势是绑定变量（JDBC 的 PreparedStatement 天然就是）；cursor_sharing=FORCE 是兜底不是解药，极端场景会让计划变差。
模块 3

Redo 与 Undo：提交与读一致性的根基

MySQL InnoDB 也是 redo/undo 双日志，Oracle 的版本更成熟、分工更极端：Redo 管"别丢"，Undo 管"别乱看"。

日志记什么用途
Redo Log数据块的变更向量（change vectors），物理级崩溃恢复前滚；提交时 LGWR 把它从 log buffer 写进联机重做日志，写完才算提交成功
Undo Log数据块的前镜像（旧值）事务回滚；多版本读一致性（MVCC）；闪回查询

一次提交的完整链路

改 Buffer Cache：server process 在 SGA 的 buffer cache 里改块（此时数据文件还没动）
记 Redo Buffer：同时把变更向量写进 redo log buffer
COMMIT：LGWR 把 redo buffer 写进联机重做日志文件（写盘 + 确认）——从这一刻起事务提交生效
异步写数据文件：DBWn 之后把脏块批量写回 .dbf；CKPT 负责推进检查点、通知 DBWn、更新控制文件
归档：日志组写满后 ARCH 进程归档到归档目录，填满后循环覆盖
-- 日志与检查点状态
SELECT group#, sequence#, status, members, archived FROM v$log;
SELECT * FROM v$log_history WHERE rownum <= 10;   -- 最近日志切换频率

-- 提交等待（commit 慢就看它）
SELECT event, total_waits, time_waited_micro/1000 AS ms
FROM v$system_event WHERE event = 'log file sync';

-- UNDO 配置与使用
SHOW PARAMETER undo;
SELECT tablespace_name, status FROM dba_tablespaces WHERE contents = 'UNDO';
SELECT * FROM v$undostat;   -- 每 10 分钟一个间隔的 undo 使用统计
读一致性（consistent read）的机制：一个查询开始时会记录 SCN，之后读到"比我新的未提交块"时，用 UNDO 里的前镜像构造旧版本。所以 Oracle 的读不加锁、也不被写阻塞（类似 PG 的 MVCC，而 MySQL 的 RR 隔离也靠 undo，但锁策略更保守）。代价是：UNDO 保留窗口内不能覆盖，长查询会撞上 ORA-01555。
ORA-01555 snapshot too old 的完整因果链：查询执行时间长 > UNDO_RETENTION 保留窗口 > 查询需要的前镜像被覆盖 → 报错。常见诱因：大表全表扫描跑几分钟、批量任务和长报表并发、UNDO 表空间太小且自动扩展关闭。解法：调大 UNDO_RETENTION、开 UNDO 表空间自动扩展（RETENTION GUARANTEE 需谨慎，会阻塞 DDL）、拆分大查询。
模块 4

执行计划与 Hint

拿到执行计划

-- 方式一：EXPLAIN PLAN + DBMS_XPLAN 展示
EXPLAIN PLAN FOR
SELECT * FROM emp e WHERE e.deptno = 10;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY());

-- 方式二：看真实执行过的计划（带实际行数）
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(sql_id => '&sql_id', format => 'ALLSTATS LAST'));

-- 方式三：sqlplus 里一条语句出计划 + 统计
SQL> SET AUTOTRACE ON EXPLAIN STATISTICS

-- 让这条 SQL 自己采集真实行数
SELECT /*+ GATHER_PLAN_STATISTICS */ * FROM emp WHERE deptno = 10;

计划里的关键算子

访问路径何时出现 / 好坏
TABLE ACCESS FULL全表扫。小表没问题；大表出现说明缺索引或条件不可索引
INDEX UNIQUE SCAN唯一索引精确查，最快
INDEX RANGE SCAN索引范围查，最常见的健康路径
INDEX FAST FULL SCAN多块读扫全索引，统计/报表场景比全表扫省 IO
INDEX SKIP SCAN复合索引前导列不在条件里时的跳跃扫，大数据量低基数列常见
NESTED LOOPS / HASH JOIN / SORT MERGE JOIN三种连接方式。小驱动表+内表索引 → NL；大表等值 JOIN → Hash；两边已有序 → SMJ
SORT ORDER BY排序，看有没有 spilled to disk（PGA 放不下会写临时表空间）

统计信息：计划的"眼睛"

-- 手工采集（大表/批量导入后必须做）
EXEC DBMS_STATS.GATHER_TABLE_STATS(ownname => 'APP', tabname => 'ORDERS', estimate_percent => DBMS_STATS.AUTO_SAMPLE);
EXEC DBMS_STATS.GATHER_SCHEMA_STATS(ownname => 'APP', cascade => TRUE);

-- 看表/索引统计与直方图
SELECT table_name, num_rows, blocks, last_analyzed, stale_stats FROM dba_tab_statistics WHERE owner = 'APP';
SELECT column_name, histogram, num_distinct, density FROM dba_tab_col_statistics WHERE owner = 'APP' AND table_name = 'ORDERS';

Hint：直接告诉优化器怎么干

-- 常用 Hint 一览（写在 SELECT 后第一个注释里，格式：/*+ ... */）
SELECT /*+ INDEX(e emp_dept_idx) */ * FROM emp e WHERE deptno = 10;
SELECT /*+ FULL(e) */ * FROM emp e;                          -- 强制全表扫
SELECT /*+ USE_NL(e d) LEADING(e) */ * FROM emp e JOIN dept d ...;  -- 指定连接方式与驱动表
SELECT /*+ PARALLEL(e 4) */ * FROM emp e;                    -- 并行度 4
SELECT /*+ FIRST_ROWS(10) */ * FROM emp;                  -- 优化返回前几行的响应速度
SELECT /*+ APPEND */ * FROM t;                            -- INSERT 走直接路径，绕过 buffer cache
Hint 静默失效的三大原因：① 写错位置（必须在 SELECT 关键字后的第一个注释里）；② 引用对象不存在（索引名/别名写错，Oracle 不报错直接忽略）；③ 被 SQL Profile / Baseline 覆盖。所以 Hint 不是"保险"，写错就是"我以为在管，其实没管"。要确认 Hint 生效，用 DISPLAY_CURSOR 看 Outline Data 或计划形态是否变化。
和 MySQL 对比：MySQL 8.0 也有 optimizer hints，但语法分散在每条语句之后、生态工具链弱；Oracle 的统计信息体系（DBMS_STATS 全套策略、直方图、动态采样）和 SPM（SQL Plan Baseline / Profile）成熟得多。Oracle DBA 调优的日常就是"先看统计信息，再看计划，最后才动 Hint"。
模块 5

RAC 与 Data Guard

RAC：多实例共享一个库

概念说明
Cache Fusion节点间通过私有高速互联（Heartbeat Network）传递块镜像，一个节点要读另一个节点正在改的块时，直接跨节点传，不走磁盘
GCS / GES全局缓存服务（管块的一致性状态）/ 全局队列服务（管锁的全局视角）
共享存储 + ASM所有节点访问同一组数据文件。ASM 是 Oracle 的卷管理器：磁盘组（Disk Group）、分配单元（AU，默认 1MB）、冗余级别（External/Normal/High）
SCANSingle Client Access Name，一个域名背后三台 SCAN Listener，客户端只连 SCAN，节点故障对它透明
脑裂防护节点失联超过阈值（misscount）会被踢出集群并重启（CSS 服务 + voting disk 仲裁）
-- RAC 实例状态
SELECT inst_id, instance_name, host_name, status FROM gv$instance;
-- 全局视角查询：GV$ 是所有实例的并集，V$ 是本实例
SELECT inst_id, sid, serial#, username, event FROM gv$session WHERE username IS NOT NULL;

-- 跨节点读等待（RAC 专属调优重点）
SELECT event, total_waits, time_waited_micro/1000 AS ms FROM v$system_event
WHERE event LIKE 'gc%' ORDER BY time_waited_micro DESC;

Data Guard：主备容灾

概念说明
物理备库块级同步，直接应用 redo。最常用，切换快
逻辑备库把 redo 转成 SQL 在备库执行。可开放读写，但有限制（部分数据类型/DDL 不支持）
快照备库临时打开可写用于测试，用完切回备库继续同步
保护模式最大保护（同步，主库无备库确认就 hang）/ 最大可用（同步，备库挂了主库降级继续）/ 最大性能（异步，不影响主库性能）
Switchover / Failover计划内角色互换（无丢失）/ 故障时紧急切换（可能丢数据，需追平 gap）
Active Data Guard付费选项：备库在应用 redo 的同时开放只读，可做报表分流、Far Sync 异地级联
-- Broker 命令行管理（dgmgrl）
$ dgmgrl sys/oracle@primary
DGMGRL> SHOW CONFIGURATION;
DGMGRL> SHOW DATABASE standby STATUS REPORT;
DGMGRL> VALIDATE DATABASE verbose standby;   -- 切换前演练检查
DGMGRL> SWITCHOVER TO standby;                -- 计划内切换

-- 主库看备库进度
SELECT dest_name, status, gap_status FROM v$archive_dest_status;
SELECT process, status, sequence#, block# FROM v$managed_standby;
RAC 和 MySQL 组复制（MGR）解决的不是同一个问题。MGR 是单写多读的复制组，扩展性靠读；RAC 是多写（不同实例写不同块），靠 Cache Fusion + 共享存储线性扩展写能力，代价是互联延迟敏感（跨机房部署 RAC 是著名大坑）。PG 生态对应物是 Citus/共享磁盘类方案，思路又不同。

模块 7

AWR 与 ASH 性能诊断

AWR/ASH 是 Oracle 自带的"黑匣子 + 显微镜"，也是它相对 MySQL performance_schema 体系的核心优势。

工具机制回答什么问题
AWR默认每小时采一次快照，保留 8 天，存 SYSAUX 表空间"过去这段时间系统在干什么、什么最贵"
ASH每秒采样活动会话，每 10 个样本取 1 个写入 AWR；内存里保留约 1 小时滚动窗口"这一秒谁在等什么"（实时热点）
ADDM对比两个 AWR 快照自动给建议"有什么明显问题、怎么改"
-- 手动抓一个快照（调优前后各抓一次做对比）
SQL> EXEC DBMS_WORKLOAD_REPOSITORY.CREATE_SNAPSHOT();

-- 生成报告（回答实例、起止快照、输出文件名）
$ sqlplus / as sysdba
SQL> @?/rdbms/admin/awrrpt.sql          # 单实例 AWR
SQL> @?/rdbms/admin/awrrpti.sql         # RAC 全局
SQL> @?/rdbms/admin/ashrpt.sql          # ASH 报告
SQL> @?/rdbms/admin/addmrpt.sql         # ADDM 建议

-- 不跑脚本，直接查 ASH 聚合（实时热点）
SELECT sql_id, event, COUNT(*) AS samples
FROM v$active_session_history
WHERE sample_time > SYSDATE - INTERVAL '10' MINUTE
GROUP BY sql_id, event ORDER BY COUNT(*) DESC FETCH FIRST 20 ROWS ONLY;

-- 时间模型：系统时间都花哪了
SELECT * FROM v$sys_time_model;

AWR 报告阅读顺序

先看 Top 5 Timed Foreground Events：占比最高的事件就是瓶颈方向。log file sync 高 = 提交慢；db file sequential read 高 = 单块读多（索引/回表）；db file scattered read 高 = 全表扫多；gc buffer busy 高 = RAC 跨节点争用
再看 SQL Statistics：按 Elapsed Time / CPU / Buffer Gets 排序的 Top SQL，拿到 sql_id 直接挖
Instance Efficiency：Buffer Cache Hit Ratio（长期低于 90% 要警惕）、Soft Parse %、Execute to Parse %
Segments by Physical Reads / Row Lock Waits：找到被反复全扫的热表、被锁竞争的热行
和 MySQL/PG 的工具对照：MySQL 的 performance_schema + sys schema 记录的是"计数器"，需要自己聚合；PG 的 pg_stat_statements 只记 SQL，缺等待维度。Oracle 的 AWR/ASH 是开箱可用的时间序列，10 分钟就能定位一次昨天下午的卡顿。调优套路：AWR 定性 → ASH 定量 → v$sql 抓元凶 → 改 SQL/索引/参数 → 对比前后 AWR。
模块 8

闪回技术（Flashback）

Oracle 的后悔药全家桶，底层都靠 UNDO 里的前镜像。误删数据、误更新、逻辑损坏，多数场景不用恢复备份。

技术用途命令
闪回查询看一张表几分钟前的样子（排查/取数）SELECT ... AS OF TIMESTAMP / SCN
闪回版本查询看一行在时间段内的所有历史版本（谁改的、改前改后）VERSIONS BETWEEN SCN/TIMESTAMP
闪回表把表数据回滚到某个时间点（行级恢复）FLASHBACK TABLE t TO TIMESTAMP
闪回删除恢复被 DROP 的表（回收站机制）FLASHBACK TABLE t TO BEFORE DROP
闪回事务反向撤销一个事务的变更（事务级回退）DBMS_FLASHBACK.TRANSACTION_BACKOUT
闪回数据库整个库回退到过去（大范围逻辑损坏）FLASHBACK DATABASE TO TIMESTAMP
-- 闪回查询：5 分钟前的订单长什么样
SELECT * FROM orders
AS OF TIMESTAMP (SYSTIMESTAMP - INTERVAL '5' MINUTE)
WHERE order_id = 10086;

-- 闪回版本查询：这行被谁改过
SELECT versions_startscn, versions_endscn, versions_operation, versions_xid, amount
FROM orders VERSIONS BETWEEN SCN 1000 AND 2000
WHERE order_id = 10086;

-- 闪回表：误 UPDATE 后整表回滚（需要开行移动）
ALTER TABLE orders ENABLE ROW MOVEMENT;
FLASHBACK TABLE orders TO TIMESTAMP TO_TIMESTAMP('2026-10-17 14:00:00', 'YYYY-MM-DD HH24:MI:SS');

-- 闪回删除：找回被 DROP 的表
FLASHBACK TABLE orders TO BEFORE DROP RENAME TO orders_recovered;
PURGE TABLE orders;   # 彻底删除，不进回收站

-- 闪回数据库：先建还原点（需要闪回恢复区）
CREATE RESTORE POINT before_migration GUARANTEE FLASHBACK DATABASE;
SHUTDOWN IMMEDIATE; STARTUP MOUNT;
FLASHBACK DATABASE TO RESTORE POINT before_migration;
ALTER DATABASE OPEN RESETLOGS;
闪回不是万能的，边界要记牢：① 闪回查询/表依赖 UNDO，超出 UNDO_RETENTION 窗口就报 ORA-01555；② TRUNCATE / DDL 之后的表不能闪回查询（DDL 会让 UNDO 里的前镜像失效），但 DROP 可以用闪回删除找回（回收站）；③ 闪回表会改变 rowid且需要短暂排他锁，大表慎用；④ 闪回数据库要求开了闪回恢复区（DB_RECOVERY_FILE_DEST_SIZE）且日志连续。
模块 9

十个线上坑

1
SQL 里字面量写死，不绑变量
游标泛滥、硬解析爆炸、shared pool latch 争用、CPU 打满。用 PreparedStatement/绑定变量；cursor_sharing=FORCE 只是兜底。
2
批量导入后忘记收统计信息
优化器按老统计信息估算行数，索引不用、全表扫描横行。DBMS_STATS.GATHER_TABLE_STATS 必须进 ETL 流程。
3
Hint 写错还以为是 Hint 生效了
索引名写错、位置不对，Oracle 静默忽略，计划照旧。验证 Hint 要看 DISPLAY_CURSOR 的实际计划形态，不是看 SQL 文本。
4
长查询撞 ORA-01555
报表跑几分钟，UNDO 前镜像被覆盖直接报错。调大 UNDO_RETENTION、拆查询、把大报表挪到备库（Active Data Guard）。
5
闪回当备份用
UNDO 保留窗口通常几十分钟，撑不起"三天前误删"。闪回是急救，RMAN + Data Guard 才是保险。
6
RAC 上忽略互联网络
Cache Fusion 全部流量走私有心跳网络，带宽不够或走公网交换机，gc 等待飙升。互联必须专用万兆、独立网卡、专用交换机。
7
把表随便放默认表空间
热表和 SYSTEM/SYSAUX 混在一起，备份恢复粒度粗、空间故障影响面大。大对象独立表空间是底线。
8
开发直连生产查数不带超时
一条没加 WHERE 的查询在 SQL Window 里全表扫，占 PGA、堵回滚段。用 Resource Manager profiles 限制空闲超时和单查询资源。
9
归档模式没开或归档满了不管
数据库 hang 在等归档，全部写入阻塞。监控 v$archive_dest_status 的 gap/valid，归档目录要独立盘 + 告警。
10
以为 Data Guard 同步就零丢失
最大性能模式是异步，主库崩了备库有 gap，强制切换要丢数据。要零 RPO 必须最大保护/最大可用 + 同步日志传输，且接受提交延迟代价。
自测

六道题

1. Oracle 事务提交时，哪个进程负责把 redo 从 log buffer 写到联机重做日志？
正确答案：LGWR。提交时 LGWR 把 redo log buffer 写进联机重做日志（并确认），写完事务才算提交成功。DBWn 是异步把脏块写回数据文件的，CKPT 负责推进检查点、通知 DBWn、更新控制文件。
2. Oracle 读一致性（一个事务内看到的数据不被打断）主要靠什么实现？
正确答案：UNDO 前镜像。查询记录开始 SCN，读到更新的未提交块时用 UNDO 里的旧值构造一致读版本，所以读不阻塞写、写不阻塞读。Redo 是崩溃恢复用的，不是读一致性用的。
3. AWR 快照的默认采集间隔和保留时间大约是？
正确答案：每小时一次、保留 8 天（可用 DBMS_WORKLOAD_REPOSITORY.MODIFY_SNAPSHOT_SETTINGS 调整）。ASH 是每秒采样、每 10 个取 1 个入 AWR，内存里保留约 1 小时滚动窗口。
4. 某张表被 DROP 之后想找回，正确的做法是？
正确答案：TO BEFORE DROP。DROP 后表进了回收站（名字变成 BIN$...），可以直接闪回找回；PURGE 或清理回收站后就只能靠备份恢复。闪回查询/闪回表对 DDL 之后的表无效。
5. RAC 中两个节点同时想读同一个数据块的不同版本，靠什么保证一致性？
正确答案：Cache Fusion。节点间通过私有高速互联直接传递块的当前镜像（而不是都走磁盘），GCS 管块状态、GES 管全局锁。Data Guard 是主备容灾，和 RAC 的实时缓存一致性是两回事。
6. 大报表跑了 4 分钟报 ORA-01555，最可能的原因和首选处理是？
正确答案：UNDO 保留窗口不够。查询要构造旧版本时，需要的前镜像已被覆盖。处理：调大 UNDO_RETENTION、UNDO 表空间自动扩展、拆分/并行化大查询，或把报表放到备库（Active Data Guard）跑。加日志组、扩 SGA 都不解决这个问题。
