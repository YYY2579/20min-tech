二十分钟学透备份与恢复实战

备份不是为了"有个文件"，是为了在故障时按 RTO 把数据找回来。这篇讲物理与逻辑备份的分界、xtrabackup 与 pg_basebackup 的真实命令、PITR 到秒级的恢复、3-2-1 策略，以及为什么"没验证过的备份等于没备份"。

开始前

起一个能练的环境

# MySQL 8.0（必须开 binlog，否则没法做增量恢复和 PITR）
docker run -d -p 3306:3306 --name mysql \
  -e MYSQL_ROOT_PASSWORD=root \
  -v /data/mysql:/var/lib/mysql \
  mysql:8.0 --log-bin=mysql-bin --binlog-format=ROW

# PostgreSQL 15（开启 WAL 归档）
docker run -d -p 5432:5432 --name pg \
  -e POSTGRES_PASSWORD=root \
  -v /data/pg:/var/lib/postgresql/data \
  postgres:15 -c wal_level=replica -c archive_mode=on \
  -c "archive_command=test ! -f /wal_archive/%f && cp %p /wal_archive/%f"

# 验证归档目录
docker exec pg ls /wal_archive | head      # 应该看到 000000010000000000000001 这类段文件
先建立一个认知：备份和恢复是两个不同的系统。备份决定你"有什么可恢复"，恢复流程、脚本、演练决定你"多久能恢复"。生产事故复盘里最常见的一句话是"备份一直有的，但没人会恢复/恢复要 6 小时"——备份做得再勤，恢复没演练过就是零。
模块 1

备份类型：两个维度四种组合

备份分类有两个正交维度：物理还是逻辑（拷贝什么）、全量、增量还是差异（拷多少）。

维度一：物理备份 vs 逻辑备份

类型内容工具与取舍
物理备份直接拷贝数据文件、redo/WAL、页结构xtrabackup、pg_basebackup、文件系统快照。快、一致性强、可增量；但跨版本/跨平台恢复受限
逻辑备份SQL 语句/表数据导出（可读文本）mysqldump、pg_dump。灵活、跨版本、可单表恢复；但大数据量慢几倍，恢复是一次次 INSERT

维度二：全量 / 增量 / 差异

类型内容恢复时需要
全量某一时刻的完整数据只需要这一份。恢复最简单，占空间最大
增量自上次备份（任意类型）以来的变更全量 + 按顺序的全部增量。省空间，链条断一份就废
差异自上次全量以来的变更全量 + 最后一份差异。恢复简单，越往后差异越大
数据库的"增量"通常是免费的：MySQL 的增量就是 binlog，PG 的增量就是 WAL——这俩是数据库自己为崩溃恢复写的日志，开启归档就是备份。所以生产组合几乎总是：每周物理全量 + 实时 binlog/WAL 归档。binlog/WAL 归档让 RPO 趋近于 0（取决于归档方式，见模块 2、3），且几乎零额外成本。
逻辑备份的经典陷阱：mysqldump 默认不是一致性的。不加 --single-transaction 时，mysqldump 会锁表或逐表 dump，混合 InnoDB/MyISAM 的库 dump 出来的数据是"时间拼图"——A 表是 10:00 的快照，B 表是 10:03 的快照，恢复后关联数据对不上。正确姿势：--single-transaction --quick --triggers --routines --events --hex-blob --master-data=2，且确认所有表都是 InnoDB。
模块 2

MySQL 备份体系：xtrabackup + binlog PITR

Percona XtraBackup 是 MySQL 物理备份的事实标准：在线、不锁表（InnoDB）、支持增量。注意老命令 innobackupex 在 2.3 版本后已被 xtrabackup 取代。

完整流程：全量 → 增量 → 恢复到任意时间点

# ===== 1. 全量备份（周日凌晨）=====
xtrabackup --backup \
  --user=backup --password=BakPass123 \
  --target-dir=/backup/full_20261011 \
  --parallel=4 --compress --compress-threads=2

# ===== 2. 增量备份（每天晚上，基于上次备份）=====
xtrabackup --backup \
  --user=backup --password=BakPass123 \
  --target-dir=/backup/inc_20261012 \
  --incremental-basedir=/backup/full_20261011

# 链式增量：周三的基于周二
xtrabackup --backup --target-dir=/backup/inc_20261013 \
  --incremental-basedir=/backup/inc_20261012 ...

# ===== 3. 准备（prepare）：合并增量 + 回滚未提交事务 =====
xtrabackup --decompress --target-dir=/backup/full_20261011    # 先解压
xtrabackup --prepare --apply-log-only \
  --target-dir=/backup/full_20261011                          # 全量只回滚不应用增量
xtrabackup --prepare --apply-log-only \
  --target-dir=/backup/full_20261011 \
  --incremental-dir=/backup/inc_20261012                      # 应用增量 1
# 有更多增量就逐个 --incremental-dir 继续；最后一个增量去掉 --apply-log-only 做最终 prepare

# ===== 4. 恢复到测试实例 =====
# 目标数据目录必须为空（或先停实例）
xtrabackup --copy-back --target-dir=/backup/full_20261011
chown -R mysql:mysql /var/lib/mysql

PITR：全量 + binlog 恢复到指定时间点

# 场景：周二 14:30 有人误删了订单表，现在要恢复到 14:25 的状态
# 1. 用最近的物理全量（如周日）+ 增量恢复到数据目录（如上）
# 2. 找到 14:30 时的 binlog 位置
mysqlbinlog /data/mysql/mysql-bin.000008 \
  --start-datetime="2026-10-13 14:20:00" \
  --stop-datetime="2026-10-13 14:30:00" > /tmp/events.sql
grep -n "DROP\|DELETE" /tmp/events.sql          # 确认误操作 SQL 的位置

# 3. 从 binlog 起点重放到误操作前（跳过危险语句）
mysqlbinlog /data/mysql/mysql-bin.000008 \
  --start-position=4 \
  --stop-position=12345 \                       # 误操作事件的 start position
  | mysql -u root -p

# 4. 之后的事件如果也要（跳过误操作本身），用 exclude 或手动裁剪
mysqlbinlog --start-position=12400 ... | mysql -u root -p

# 5. 校验：对比关键表行数、抽查最近订单
SELECT COUNT(*) FROM orders;
SELECT MAX(created_at) FROM orders;
binlog 过期 = PITR 能力消失。默认 binlog_expire_logs_seconds=2592000（30 天），但如果磁盘紧张有人手改小、或 purge 策略激进，上周的全量 + 已删的 binlog = 只能恢复到全量时刻。备份系统的第一监控项就是 binlog 归档的连续性和保留期，清理策略必须和备份保留策略对齐（保留 90 天备份，binlog 至少 90 天）。
备份账号与锁的影响：xtrabackup 需要 RELOAD、PROCESS、LOCK TABLES、REPLICATION CLIENT、BACKUP_ADMIN 权限（专用低权限账号，别用 root）。非 InnoDB 表备份时 xtrabackup 仍会短暂 FLUSH TABLES WITH READ LOCK——表多的大库，FTWRL 能卡住写入几十秒，安排备份窗口或用 --no-lock（前提是无非 InnoDB 表）。MySQL 8.0 的 LOCK INSTANCE FOR BACKUP 比 FTWRL 轻得多，允许备份期间继续写。

逻辑备份的正确姿势（单表/跨版本场景）

# 一致性逻辑备份
mysqldump -u root -p \
  --single-transaction \                        # InnoDB 一致性快照，不锁表
  --quick \                                    # 逐行读取，不全表进内存
  --triggers --routines --events \              # 别漏触发器和存储过程（迁移场景必踩）
  --hex-blob \                                 # 二进制安全
  --master-data=2 \                            # 在输出里注释记录 binlog 位点（恢复/PITR 要用）
  --all-databases > /backup/dump_all_20261011.sql

# 恢复逻辑备份（大文件注意 max_allowed_packet）
mysql -u root -p --max_allowed_packet=512M < /backup/dump_all_20261011.sql

# PG 逻辑备份
pg_dump -Fc -d prod -f /backup/prod_20261011.dump      # 自定义格式，支持并行恢复
pg_restore -d prod_test -j 4 /backup/prod_20261011.dump  # -j 并行，恢复快数倍
pg_dump -d prod --table=orders > orders_only.sql        # 单表导出
模块 3

PostgreSQL 备份：pg_basebackup + WAL 归档 PITR

# ===== 1. 基础备份（物理全量，在线不阻塞业务）=====
pg_basebackup -h primary -D /backup/base_20261011 \
  -U repl -P -R -X stream -S slot_base -Ft -z -g
# -R 写 standby.signal + primary_conninfo；-X stream 边传边收 WAL（推荐）
# -S slot_base 用复制槽保证备份期间 WAL 不被清理；-Ft tar 格式；-z gzip；-g 压缩；-P 进度

# ===== 2. WAL 归档配置（postgresql.conf）=====
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /wal_archive/%f && cp %p /wal_archive/%f'
# 生产建议用 pg_receivewal 做流式归档，比 archive_command 的 cp 更实时：
# pg_receivewal -h primary -D /wal_archive --slot=wal_archive -S
archive_timeout = 300                          # 秒：空闲时最多 5 分钟切一段 WAL，保证归档连续性

# ===== 3. PITR 恢复到指定时间点 =====
# 3a. 恢复基础备份到新数据目录
rm -rf /var/lib/postgresql/data/*
tar -xzf /backup/base_20261011/base.tar.gz -C /var/lib/postgresql/data/

# 3b. 配置恢复参数（PG 12+）
touch /var/lib/postgresql/data/recovery.signal
cat >> /var/lib/postgresql/data/postgresql.auto.conf <<EOF
restore_command = 'cp /wal_archive/%f %p'
recovery_target_time = '2026-10-13 14:25:00'
recovery_target_action = 'promote'             # 到达目标时间后提升为新主
EOF

# 3c. 启动，PG 自动重放 WAL 到目标时间点后 promote
pg_ctl -D /var/lib/postgresql/data start
# 日志里看到 "recovery stopping before commit ... " 和 "promoted" 即成功
recovery_target_time 用错时区是经典事故：recovery_target_time 用的是服务器时区解释的时间字符串，而 binlog/WAL 里记录的时间可能是 UTC。容器里 TZ 没设、跨时区恢复，明明写了 14:25 却恢复到 06:25。对策：恢复前 SHOW timezone; 确认，并在恢复后用关键表 SELECT MAX(created_at) 验证实际恢复到哪一刻。
PG 的三个恢复目标（按精度选）：recovery_target_time（时间点，最常用）、recovery_target_xid（事务 ID，精确但要先查出误操作事务的 xid）、recovery_target_lsn（WAL 日志序列号，最精确）。配合 recovery_target_inclusive 控制是否包含目标本身。日常恢复用 time 足够；金融对账类恢复用 xid/lsn 更稳。

一致性快照的其他选项

方式适用
pg_backup_start/stop手工控制的一致性快照（低层 API）
pgBackRest / Barman / wal-g生产推荐。全量+增量+WAL 归档一体化，支持远程存储、保留策略、并行、校验
云厂商 RDS 备份托管版自带，关注下载到本地的能力和跨区域复制
# pgBackRest 最小配置（/etc/pgbackrest/pgbackrest.conf）
[global]
repo1-path=/var/lib/pgbackrest
repo1-retention-full=2                       # 保留 2 份全量
repo1-retention-full-type=count

[prod]
pg1-path=/var/lib/postgresql/data

# 命令
pgbackrest --stanza=prod backup --type=full
pgbackrest --stanza=prod backup --type=incr      # 增量
pgbackrest --stanza=prod backup --type=diff      # 差异
pgbackrest --stanza=prod info                    # 备份列表与校验状态
pgbackrest --stanza=prod restore --target-time="2026-10-13 14:25:00" \
  --delta --recovery-option=promote
模块 4

备份策略：3-2-1 原则与 RPO/RTO

策略不是"多备几份"，是用 RPO/RTO 反推出的具体频率、保留期和存放位置。

3 份数据
1 份生产 + 2 份备份。只备一份的话，备份损坏/被误删/勒索病毒一锅端，直接归零
2 种介质
本地磁盘 + 对象存储/磁带。同介质批量故障（磁盘阵列损坏、机房事故）会同时带走两份
1 份异地
至少一份在另一个机房/城市。机房级火灾、断电、网络事故，本地备份全部不可用

RPO / RTO 的计算与策略推导

指标定义计算示例
RPO能丢多少数据（时间）每天 02:00 全备 + binlog 实时归档 → RPO ≈ 0（恢复到故障前最后一刻）
每天 02:00 全备、binlog 只留 7 天且归档中断 → RPO = 距上次备份的时间，最坏 24h
RTO多久能恢复业务500GB 库：物理恢复（copy-back）≈ 2~3h + binlog 重放 ≈ 1h → RTO ≈ 4h
同数据量逻辑恢复（pg_restore -j 4）≈ 6h+ → 逻辑备份做主力 RTO 不达标
# 一套典型生产策略（500GB MySQL，日增量 20GB）
全量备份：  每周日 02:00  xtrabackup 全量，保留 4 周
增量备份：  每天 02:00    基于最近备份，保留 2 周
binlog：    实时归档到对象存储，保留 90 天（对齐审计要求）
异地：      全量每周同步到异地对象存储（跨区域复制）
保留：      全量 4 周 + 月度归档保留 1 年（合规）
监控：      备份失败、binlog 归档中断、备份文件校验和 三项告警

# 保留策略自动化（pgBackRest 示例）
repo1-retention-full=4          # 4 份全量
repo1-retention-diff=7          # 7 份差异
repo1-retention-archive=2       # WAL 归档保留 2 份全量的时长
repo1-retention-archive-type=full
算 RTO 时必须用"演练值"不是"理论值"：理论上 500GB copy-back 按磁盘 200MB/s 算 40 分钟，实际要算上：备份解压（压缩过的备份翻倍时间）、增量合并（几小时也可能）、binlog 重放（取决于故障期间写入量）、启动校验、业务连接恢复。经验值：理论耗时 × 2~3 才是能写进 SLA 的数字。
按业务分级配策略（别一刀切）：核心交易库（RPO≈0，RTO<1h）→ 全量+实时 binlog + 热备（半同步从库）+ 月度恢复演练；一般业务库（RPO<1h，RTO<8h）→ 每日全量或增量 + binlog，季度演练；历史归档库（RPO<24h 可接受）→ 周全量 + 冷存储，年度演练。策略写进文档、纳入监控，否则等于没有。
模块 5

恢复演练：备份系统的期末考试

行业调研（Veeam、Databarracks 等机构的年度报告）反复给出同一个结论：约三分之一的组织在过去一年遇到过备份恢复失败，而失败的头号原因就是"没测过恢复"。备份文件的正确率和你的恢复成功率是两个概率，只有演练能把它们拉齐。

定期恢复测试：每月抽 1 个备份（随机抽，别总抽最新的）恢复到隔离环境，跑通校验脚本
记录真实 RTO：从"开始恢复"计时到"业务能读写"，每次记录，和 SLA 对比
校验数据不只是启动成功：核心表行数、最大时间戳、金额合计、关键记录抽查，四项全过才算恢复成功
混沌场景演练：每季度一次"全挂"演练——假设主库和从库全丢，只许用备份+binlog/WAL 恢复，走完整流程
回归生产流程：演练必须用生产同款工具和账号（备份账号权限对不对、脚本路径是否存在），不能是"我知道怎么弄"
# 自动化恢复验证的最小脚本逻辑（伪代码）
restore_to_isolated_env $LATEST_FULL_BACKUP       # 恢复到隔离网段的测试实例
assert_eq $(mysql -e "SELECT COUNT(*) FROM orders") $EXPECTED_COUNT
assert_eq $(mysql -e "SELECT MAX(id) FROM orders")    $EXPECTED_MAX_ID
assert_eq $(mysql -e "SELECT SUM(amount) FROM orders") $EXPECTED_SUM
record_rto $START_TIME                               # 记录耗时到看板
cleanup                                             # 销毁测试环境，别让它变成影子库

# 备份文件自身的校验（防静默损坏）
md5sum /backup/full_20261011/* > /backup/full_20261011.md5
md5sum -c /backup/full_20261011.md5                 # 恢复前先验证，别等 copy-back 一半报错
xtrabackup --prepare --target-dir=/backup/full_20261011 2>&1 | tail -20
# prepare 成功本身就是一次校验：能 apply-log 说明备份结构完整
"备份成功"≠"备份可用"，三个静默失败场景：① 备份脚本报错但退出码是 0（没写 set -e / 没检查退出码），看板上全是绿色其实文件是空的；② 备份的是从库而从库复制断了三周，备出来的是三周前的数据还以为是最新的；③ 对象存储开了版本控制但存储桶策略变更，旧备份被静默清理。对策：备份任务加"文件大小 > 阈值"校验 + 定期随机恢复 + 备份源数据新鲜度检查。
模块 6

云备份与跨区域

能力做法注意点
快照云盘快照（EBS/云磁盘）秒级创建、增量存储快照≠一致性备份：数据库在线打快照要用文件系统/应用一致性代理，否则像"拔电源"
对象存储归档xtrabackup 流式备份直传 OSS/S3：--stream=xbstream低频/归档型存储取回有延迟和费用，RTO 要算进去
跨区域复制对象存储跨区域复制（CRR）自动同步备份桶加密备份要确认 KMS 密钥也跨区域可用，否则异地恢复不了
托管数据库备份RDS 自动备份 + binlog，支持按时间点恢复自动备份在实例删除后的保留策略、能否下载到本地，先确认
# xtrabackup 流式备份直传对象存储（不停机、不落本地盘）
xtrabackup --backup --user=backup --password=xxx \
  --stream=xbstream --parallel=4 --compress \
  | ossutil cp - oss://backup-bucket/mysql/full_20261011.xbstream \
  --meta "Content-Type:application/octet-stream"

# 从对象存储流式恢复
ossutil cp oss://backup-bucket/mysql/full_20261011.xbstream - \
  | xbstream -x -C /backup/restore/ --decompress

# 跨区域同步（对象存储侧配置，命令行确认状态）
aws s3api get-bucket-replication --bucket backup-bucket

# 云盘快照一致性（MySQL 例）
mysql -e "FLUSH TABLES WITH READ LOCK; SYSTEM aws ec2 create-snapshot ...; UNLOCK TABLES;"
# 或用备份代理自动处理；生产更推荐 xtrabackup 而不是裸快照做逻辑备份
云备份的三个隐性成本：① 取流量费——灾时从对象存储拉 500GB 备份回本地机房，出流量费可能是备份存储费的十几倍；② API 限速——大规模恢复时对象存储下载带宽是瓶颈，提前测过实际吞吐；③ 密钥依赖——备份用 KMS 加密，灾时 KMS 服务不可用或密钥被禁用，备份就是一堆乱码。对策：灾前把关键备份副本留在目标恢复区域的存储里，密钥做多区域副本。
混合云/多云建议：生产在 A 云 → 备份同区域对象存储（快速恢复）+ 跨区域复制（机房级容灾）+ 每季度一份离线/异地物理介质或另一朵云的副本（防账号级事故：AK 泄露被删库、勒索软件有内鬼权限时，异地副本是最后防线）。备份必须防"删备份的人"，隔离（air-gapped/不可变存储 object lock）是 2020 年后备份架构的必选项。
模块 7

十个线上坑

1
备份从不验证，故障时才发现是坏的
备份任务退出码没检查、文件被截断、存储静默损坏，看板全绿。备份系统必须含：文件大小/校验和校验 + 定期随机恢复演练。
2
binlog/WAL 过期，PITR 窗口消失
磁盘紧张把 binlog 保留从 90 天改成 3 天，上周的全量备份+已删 binlog = 只能恢复到全量时刻。binlog 保留期必须与备份保留策略对齐并监控。
3
备份锁影响业务（FTWRL 卡住写入）
mysqldump 不加 --single-transaction，或 xtrabackup 遇到大量非 InnoDB 表触发 FTWRL，备份期间全库写入卡住几十秒，业务超时一片。用 --single-transaction、MySQL 8.0 的 LOCK INSTANCE FOR BACKUP、或物理备份替代。
4
备份的是断线几周的从库
备份脚本连从库省资源，从库复制线程悄悄挂了三周没人发现，备出来的是三周前的数据还标着"最新备份"。备份源要检查复制状态（Seconds_Behind/GTID 差距），或直接备主库。
5
恢复时忘关 binlog，二次故障
在从旧备份恢复出来的实例上做修复操作，binlog 开着，这些操作又被复制到别的从库，污染扩大。恢复演练环境必须 reset master/skip-log-bin。
6
逻辑备份漏了触发器和存储过程
mysqldump/pg_dump 默认行为有差异（MySQL 默认含 routines 是 5.1+ 默认开，PG 的触发器需要 --table 粒度注意），恢复后业务逻辑缺失，报错"找不到存储过程"。备份命令固定带全参数并纳入 checklist。
7
备份账号权限不足，任务半夜失败
为安全把备份账号权限砍了，RELOCK/PROCESS/BACKUP_ADMIN 缺一个，备份失败告警被当噪音忽略，一周后才发现"最新备份是一个月前"。权限变更要走备份系统回归测试。
8
恢复目标目录没清空，copy-back 失败
xtrabackup --copy-back 要求数据目录为空，直接往有文件的目录拷报错，惊慌中 rm -rf 错目录。恢复 SOP 第一步永远是"确认目标实例已停止、目录已备份性清空"。
9
恢复完不校验，带着脏数据上线
物理恢复成功启动 ≠ 数据完整。必须跑核心表行数/时间戳/金额合计校验，确认恢复到的时刻正确（尤其 PITR 目标时间时区问题）。
10
备份和密钥、工具绑死在一处
备份加密密钥只存在被灾的机器上、恢复用的 xtrabackup 版本和备份版本不匹配、恢复 SOP 只在某个老员工脑子里。灾备三件套：密钥异地、工具版本记录、SOP 文档化。
自测

六道题

1. 每周日全量 + 每天增量 + binlog 实时归档，RPO 和 RTO 的组合是？
正确答案：RPO≈0，RTO 取决于恢复链路实测。binlog/WAL 实时归档让数据可恢复到任意时刻；RTO 则是另一回事——要算全量 copy-back、增量 prepare 合并、binlog 重放的总耗时，500GB 库通常按小时计，必须用演练实测值 ×2~3 作为 SLA。
2. xtrabackup 恢复流程的正确顺序是？
正确答案：先 prepare 再 copy-back。prepare 阶段把增量合并进全量并回滚未提交事务，是恢复前必须的"预处理"；跳过 prepare 直接 copy-back 得到的是不一致的崩溃状态数据。最后一个增量 prepare 时不加 --apply-log-only。
3. MySQL 要做一致性逻辑备份，mysqldump 必须加的参数是？
正确答案：--single-transaction。它在单事务里对 InnoDB 做一致性快照，全程不锁表（FTWRL 只在极短的切换瞬间）。--lock-all-tables 会长时间阻塞写入，只适合全部表都是 MyISAM 的老库。同时建议带 --master-data=2 记录位点供 PITR。
4. PostgreSQL 恢复到"今天 14:25 误操作之前"，核心配置是？
正确答案：recovery.signal + restore_command + recovery_target_time。PG 的 PITR 三要素：标记进入恢复模式、告诉它去哪找归档 WAL、设定停止重放的目标（时间/xid/LSN），到达后 promote 成可写。务必先确认服务器时区与目标时间的解释一致，恢复后用 MAX(created_at) 验证。
5. 关于 3-2-1 备份原则，正确的是？
正确答案：3 份、2 介质、1 异地。只备一份，备份损坏或被误删就归零；只放本地，机房事故全没；同介质批量故障（阵列坏）会同时带走两份。现代演进是再加"一份不可变/隔离副本"防勒索软件和账号级删除。
6. 备份任务连续一周显示"成功"，最危险的可能是？
正确答案：静默失败。备份系统的失败常常不是"报错"而是"没验证"：退出码未检查、文件大小未校验、备份源数据不新鲜。对策：备份任务内置文件校验和 + 备份源状态检查 + 每月随机抽取恢复演练，把"备份成功率"变成实测数字。
