迁移第一定律：先摸清家底，再动手。动手前必须拿到四份清单：① 数据量清单（每张表的行数、容量、最大单行）；② 流量清单（QPS、峰值时段、慢 SQL TOP）；③ 依赖清单（外键、触发器、存储过程、定时任务、视图、上下游服务）；④ 约束清单（字符集、时区、精度要求、合规要求）。90% 的迁移事故源于家底不清——以为只是 MySQL 搬家，上线后才发现有个每日 3 点的存储过程没人知道。
模块 1

迁移方法论：六步流程

不管多大的迁移项目，骨架都是这六步。顺序不能乱，每一步都有明确的出口标准。

① 评估：数据量、流量、依赖、约束四清单（见上）。输出物：迁移可行性报告 + 风险等级。判断是"能在线迁"还是"必须停机"
② 方案：选同构/异构路径，定同步方式（双写 or CDC）、校验方案、切流方案、回滚方案。输出物：迁移方案文档 + 演练计划
③ 双写/同步：存量数据全量搬迁 + 增量实时同步（CDC）。新旧库并行运行，此时生产仍以旧库为准。出口标准：同步延迟稳定在秒级、全量校验通过
④ 校验：行数、checksum、抽样比对、金额合计。多轮、不同时间点反复跑。出口标准：连续 N 轮校验零差异
⑤ 切换：灰度切流（先内部/只读流量，再全量），双写期结束后摘除旧库写入。窗口控制在分钟级
⑥ 回退预案：切换后观察期（如 48h）内任何异常，按预案切回旧库。回退不是"重来一遍"，是预先设计好的反向通道
迁移类型典型停机窗口方案要点
同构迁移（MySQL→MySQL）分钟级（仅切换瞬间）xtrabackup 全量 + binlog CDC 追赶，双写或读写分离灰度
异构迁移（Oracle→MySQL/PG）分钟级~小时级语法转换 + CDC + 长校验周期（数据转换风险高）
停机可接受（小库/内部系统）小时级导出 → 停写 → 导入 → 校验 → 切域名。最简单最稳，别为了炫技上双写
双写期的黄金规则：旧库永远是真相（source of truth）。双写阶段所有写入以旧库为准，新库只做镜像；读流量可以按百分比灰度到新库，但一旦发现任何数据不一致，第一动作是回滚读流量，不是修数据。切换点（cutover）是唯一的所有权转移时刻，必须精确到秒并全员值守。
模块 2

同构迁移：MySQL → MySQL

同构迁移最稳的套路：物理全量 + binlog 实时追赶 + 校验 + 秒级切换。

步骤 1：全量搬迁

# 方案 A：xtrabackup 物理迁移（大数据量首选，TB 级）
xtrabackup --backup --user=backup --password=xxx \
  --target-dir=/backup/migrate --stream=xbstream --parallel=8 \
  | ssh dst-server "xbstream -x -C /var/lib/mysql --decompress"

# 方案 B：mydumper/myloader 逻辑迁移（中等数据量，多线程）
mydumper -u root -p xxx -h src-host -B order_db \
  -o /backup/dump -t 8 -c --trx-consistency-only \
  --rows 100000 --statement-size 100000000
# -t 8 线程；-c 压缩；--rows 每文件 10 万行（myloader 并行粒度）；--trx-consistency-only 一致性快照
myloader -u root -p xxx -h dst-host -B order_db \
  -d /backup/dump -t 8 -o > /backup/load.log

# 方案 C：mysqldump（小库 < 10GB，最简单）
mysqldump -h src-host -u root -p --single-transaction --master-data=2 \
  --set-gtid-purged=auto --databases order_db | mysql -h dst-host -u root -p

步骤 2：binlog 增量追赶（迁移后到切换前的增量）

# 记录全量开始时的 binlog 位点（方案 C 用 --master-data=2 自动记录）
SHOW MASTER STATUS;                       # File: mysql-bin.000088, Position: 157

# 把目标库挂成源库的从库，自动追赶增量
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='src-host', SOURCE_USER='repl', SOURCE_PASSWORD='xxx',
  SOURCE_LOG_FILE='mysql-bin.000088', SOURCE_LOG_POS=157;
START REPLICA;

# 监控追赶进度
SHOW REPLICA STATUS\G                      # Seconds_Behind_Source=0 表示已追平

步骤 3：切换（停机窗口分钟级）

# 1. 源库停写（应用层开关或只读）
SET GLOBAL read_only = ON;

# 2. 等目标库追平（Seconds_Behind=0 且持续 10 秒）
# 3. 校验（模块 5 的方法）
# 4. 目标库提权
STOP REPLICA; RESET REPLICA ALL;
SET GLOBAL read_only = OFF;

# 5. 应用连接切到目标库（改配置中心/域名解析）
# 6. 观察 24h，确认无问题后源库转只读归档或下线
GTID 场景更省心：源库开 GTID 时，目标库用 SOURCE_AUTO_POSITION=1 挂从，不用记位点；即使中途目标库重建，也能自动续传。这就是迁移前先在源库开 GTID 的原因——开启 gtid_mode=ON 在线生效，不影响业务。
模块 3

异构迁移：Oracle → MySQL/PG 语法差异

异构迁移的真正工作量不在数据，在 SQL 和数据库对象。先跑一遍应用 SQL 的兼容性扫描，把差异列成清单逐条改写。

差异点OracleMySQL / PG 等价写法
分页ROWNUM <= 20LIMIT 20（两者都支持）
空值处理NVL(a, 0)IFNULL(a, 0) / COALESCE(a, 0)
当前时间SYSDATE / SYSTIMESTAMPNOW() / CURRENT_TIMESTAMP
序列seq.NEXTVALMySQL：AUTO_INCREMENT；PG：nextval('seq')
层次查询CONNECT BY PRIORWITH RECURSIVE（两者都支持）
字符串拼接'a' || 'b'MySQL：CONCAT('a','b')（PG 兼容 ||）
布尔类型NUMBER(1) 表示TINYINT(1) / BOOLEAN
日期运算date + 7（天）DATE_ADD(d, INTERVAL 7 DAY) / d + INTERVAL '7 day'
空字符串'' 等于 NULL（Oracle 特性）'' 是空串，不等于 NULL——语义差异，数据迁移必查
大小写默认大写存储（不区分）Linux 下表名区分大小写（lower_case_table_names）
# 对象级差异（迁移项目的真正大头）
# 1. 存储过程：Oracle PL/SQL 完全不兼容，必须重写（MySQL 存储过程语法/PG PL/pgSQL）
# 2. 触发器：语法和触发时机语义都有差异，重写 + 逐条测试
# 3. 定时任务：DBMS_JOB → MySQL EVENT / PG pg_cron / 应用层调度
# 4. 分区表：Oracle 分区策略 → MySQL RANGE/LIST 分区或 PG 声明式分区
# 5. 物化视图：PG 有原生支持；MySQL 需用 Flexcube 或定时刷表模拟
# 6. 包（PACKAGE）：拆成多个存储过程或改为应用层封装

# 字符集检查（迁移前后各跑一次）
# MySQL
SELECT table_name, column_name, character_set_name, collation_name
FROM information_schema.columns
WHERE table_schema = 'order_db' AND character_set_name NOT IN ('utf8mb4','ascii');

# PG
SELECT table_name, column_name, character_set_name
FROM information_schema.columns
WHERE table_schema = 'public' AND character_set_name <> 'UTF8';
Oracle→MySQL 最隐蔽的三个语义坑：① 空字符串：Oracle 里 WHERE name = '' 查不到 name 为 NULL 的行，MySQL 能——同样的 SQL 两边结果集不同；② NUMBER 无精度声明（如 NUMBER）在 MySQL 侧要显式定 DECIMAL(38,10) 或 DOUBLE，定小了直接报错或截断；③ 隐式类型转换：Oracle 里 WHERE id = '123' 能走索引，MySQL 里字符串和数字比较可能让索引失效，慢查询爆发。
自动化辅助工具（别神化，也别忽视）：Oracle→MySQL 可用 ora2pg（开源，评估+ schema 转换 + 数据迁移一体，生成评估报告极有用）、AWS SCT/IBM IIDR 等商业工具；Oracle→PG 同样首选 ora2pg。工具能做 60%~80% 的语法转换，剩下的必须人工逐条过。建议流程：ora2pg 生成初稿 → 人工评审每个对象 → 测试环境全量回归。
模块 4

增量同步：三种 CDC 技术路线

存量数据搬完后，增量同步有三条路，按团队能力和延迟要求选。

方案原理取舍
Canal伪装成 MySQL 从库拉 binlog，解析后投到 MQ 或直接写下游阿里出品、部署简单、社区资料多；只支持 MySQL/MariaDB
DebeziumKafka Connect 连接器，读 binlog/redo log 转成变更事件流生态强（支持 MySQL/PG/Oracle/SQL Server/MongoDB）、与 Kafka/Flink 集成好；依赖 Kafka
Flink CDCFlink 数据源直读 binlog，YAML/SQL 声明整库同步整库同步声明式配置、exactly-once；需要 Flink 集群
# ===== Canal 最小配置 =====
# canal/conf/example/instance.properties
canal.instance.master.address=src-host:3306
canal.instance.dbUsername=canal
canal.instance.dbPassword=Canal123
canal.instance.filter.regex=order_db\\..*
canal.mq.topic=order_binlog
# 需要源库账号有 REPLICATION SLAVE 权限，且源库开 binlog（ROW 格式）
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'canal'@'%';

# 消费端处理逻辑要点（以订单表为例）
# INSERT → 目标库 INSERT ... ON DUPLICATE KEY UPDATE
# UPDATE → 同样 upsert（按主键）
# DELETE → 目标库 DELETE WHERE id = ?（或软删除标记）
# DDL   → 同步执行（小心：目标库 DDL 期间锁表影响同步延迟）
# ===== Flink CDC 整库同步（YAML 管道）=====
source:
  hostname: src-host
  port: 3306
  username: flink
  password: Flink123
  database: order_db
  table-list: order_db.orders,order_db.order_items
  scan.startup.mode: initial            # initial：先快照全量再增量
  server-id: 5400-5404                  # 伪装从库的 id 段，别和真从库冲突

sink:
  hostname: dst-host
  database: order_db
  table-list: order_db.orders,order_db.order_items
# 一条命令起全量+增量：bin/flink-cdc.sh pipeline.yaml
CDC 的三个通用陷阱：① 乱序：并发 consumer 时同一条记录的 INSERT 和 UPDATE 可能乱序到达，按主键 hash 分区保证顺序；② DDL 不同步：源库加字段的 DDL 事件，下游 schema 没跟上就会丢字段数据——同步链路要有 schema 变更流程；③ 延迟毛刺：源库大事务（一条 binlog 事件几百 MB）会让 CDC 延迟飙升几分钟，感知不到"同步正常"的假象。监控 CDC 延迟（事件时间 vs 当前时间）和源库 binlog 位点差距，比监控"进程活着"重要。
模块 5

数据校验：三层验证体系

校验是迁移的"高考"，只比行数等于只检查了"卷子交了"——内容对不对是另一回事。

层级方法能发现什么
① 行数级每张表 count(*)，新旧库对比丢表、整批漏同步。发现不了行内数据错误
② 聚合级count(distinct id)、sum(amount)、max(updated_at) 等聚合值对比内容不一致、重复行、精度丢失
③ 抽样级按主键随机抽 N 条（如每表 1000 条）逐字段比对字段级差异：字符乱码、默认值错误、时间戳时区偏移
# ① 行数对比（在两侧执行，结果写中间表比对）
SELECT table_name, table_rows FROM information_schema.tables
WHERE table_schema = 'order_db' ORDER BY table_name;
# 注意：information_schema 的 table_rows 是估算值，精确对比用 COUNT(*)
SELECT COUNT(*) FROM orders WHERE id <= 1000000;    # 按 ID 分段 count，避免长事务

# ② 聚合对比（金额表必做，防精度丢失）
SELECT COUNT(*), COUNT(DISTINCT id), SUM(amount), MAX(updated_at), MIN(created_at)
FROM orders;
# 两侧结果必须完全一致，SUM(amount) 差一分钱都是精度问题

# ③ 全表 checksum（PostgreSQL 示例，按主键分块）
SELECT id % 100 AS bucket, COUNT(*), md5(string_agg(id::text || '|' || amount::text, ',' ORDER BY id))
FROM orders GROUP BY id % 100;
# 两侧各跑一次，逐 bucket 比对 md5。千万级表几分钟出结果

# MySQL 侧可用 pt-table-checksum（迁移目标库当"从库"用）
pt-table-checksum --host=dst --databases=order_db --replicate=percona.checksums
SELECT tbl, this_crc, master_crc FROM percona.checksums
WHERE master_crc <> this_crc;
校验要"多轮多次"：迁移同步是持续追赶的过程，一次校验通过不代表稳定。标准动作是连续 3 天、每天 3 个时间点跑全量校验，全部零差异才敢谈切换。大表（>1 亿行）全表 checksum 太慢时，用"按主键分桶 + 最近 7 天数据全量校验 + 历史数据抽样"的组合。校验发现的差异必须定位到根因再修——直接 UPDATE 目标库把数字改一致，是在给自己埋雷。
比对时的隐形差异：两侧 time_zone 设置不同，datetime 列差 8 小时；字符集不同，中文变问号；浮点列在新库用了不同的 DECIMAL 精度，SUM 差 0.0000001。对策校验前统一两侧时区和字符集声明，浮点对比用 ROUND(amount, 2) 或转成整数（分）再比。
模块 6

停机窗口控制与灰度切流

目标：把停机从"小时级"压到"分钟级"。手段是灰度——先让一小部分流量走新库，验证没问题再放大。

阶段 0 影子流量：新库只接镜像流量（CDC 同步），不服务真实读。观察同步稳定性和新库性能
阶段 1 只读灰度 1%：把 1% 的读请求路由到新库，对比响应时间和数据正确性（重点：新库读到的和旧库一致）
阶段 2 读灰度 10% → 50% → 100%：每级观察至少一个业务高峰。写流量仍全部走旧库（或双写）
阶段 3 双写期：写流量同时写新旧两库（或旧库写 + CDC 同步），此阶段旧库仍是真相，新库任何异常可秒级回滚读流量
阶段 4 切换：停旧库写 → 等同步追平 → 校验 → 写流量切新库。窗口 = 追平时间 + 校验时间 + 切换时间，通常 5~15 分钟
阶段 5 观察期：48~72 小时双跑或旧库只读待命，确认无问题后下线旧库写入路径
# 切流开关（应用层配置中心，秒级生效）
migration:
  order-db:
    read-new-ratio: 0.10        # 10% 读流量走新库
    write-mode: old-only        # old-only → dual-write → new-only 三态
    dual-write-async: true      # 双写异步化：旧库写成功即返回，新库后台补

# 切换窗口预算（500GB 库的典型值）
停写旧库              0s（配置中心推送）
等待 CDC 追平         < 30s（同步延迟平时 < 5s）
快速校验（行数+聚合）  60~120s（几千张表，跑聚合对比）
写流量切换            10s（配置中心 + 连接池刷新）
回滚操作              30s（读流量切回旧库即可，双写数据已在）
# 合计：2~5 分钟。这就是"分钟级停机"的构成
双写不是免费的：① 双写竞态：同一行并发写，新旧库写入顺序不同，最终值可能不同——解法是写入带版本号/时间戳，后写覆盖前写，或以旧库为准回放；② 回环同步：CDC 把旧库的变更同步到新库，新库的变更又被同步回旧库（双向同步场景）——必须做循环检测（如同位点跳过）或干脆不做双向；③ 双写放大延迟：新库慢查询会拖累旧库写入路径，双写必须异步化 + 熔断（新库连续超时就只写旧库，告警人工介入）。
模块 7

回滚预案与十个坑

回滚预案的核心问题只有一个：切换后新库产生了新数据，怎么合回旧库？

# 回滚预案的三种设计（按停机容忍度选）
# A. 双写期可回滚（最稳）：切换后 48h 内保持双写，新库的写入实时回流旧库
#    回滚 = 读流量切回旧库，写入本来就双份，数据零丢失

# B. 反向 CDC 回滚：切换后新库的 binlog 反向同步回旧库
#    Canal/Debezium 反向部署一份，回滚前先追平，再切读流量

# C. 停机回滚（最后手段）：导出新库增量 → 停写 → 合入旧库 → 切回
#    耗时小时级，但任何场景都成立，必须准备兜底脚本

# 回滚决策 checklist（切换后 2 小时内任何异常启动）
# □ 核心接口错误率 > 1%？        → 回滚
# □ 数据校验发现不一致？        → 先修数据，修不了回滚
# □ 新库容量/连接数打满？        → 扩容 or 回滚
# □ 慢查询导致 P99 > 500ms？     → 优化 or 回滚
# □ 下游任务（报表/对账）失败？  → 修复 or 回滚

十个线上坑

1
字符集没统一，中文迁移后变乱码
源库 utf8、目标库 latin1，或连接字符集没设 utf8mb4，中文全变问号且不可逆。迁移前两侧 + 连接串三处都确认字符集。
2
精度丢失：金额列对不上账
Oracle NUMBER 转 MySQL DECIMAL(10,2) 截断了小数，或 float 累加误差，SUM 差几分钱。金额一律 DECIMAL(18,2) 或整数分，迁移后跑 SUM 比对。
3
自增 ID 冲突
迁移时显式插入了源库 ID，目标库自增计数器没跟着涨，切换后新插入撞主键报 Duplicate entry。迁移后执行 ALTER TABLE t AUTO_INCREMENT=MAX(id)+1。
4
触发器/存储过程漏迁移
对象清单没盘全，切换后审计触发器不生效、统计存储过程丢失，业务逻辑静默缺失。用 information_schema 导出对象清单逐项核对。
5
Oracle 空字符串语义差异
Oracle '' = NULL，MySQL '' ≠ NULL，WHERE 条件结果集不同，迁移后部分查询少返回数据。迁移时把 Oracle 空串显式转 NULL 或反之，逐条 SQL 回归。
6
双写竞态导致两边数据不一致
同一行并发写入，新旧库应用顺序不同，双写期就出现分歧，还以为"切换后再说"。写入带时间戳版本、以旧库为准，或干脆单写+CDC 不做双写。
7
切换窗口没演练，实际花了 3 小时
以为"停写→校验→切流"只要 10 分钟，实际校验脚本跑了 2 小时。切换窗口每个环节都要提前演练计时，预算 ×2。
8
CDC 大事务延迟毛刺被忽视
源库夜间批处理一个事务改 500 万行，CDC 延迟 10 分钟，正好撞上切换窗口，同步没追平就切了，丢数据。切换前监控 CDC 位点延迟，大事务时段避开切换。
9
校验只比行数，不比内容
行数一致但金额字段被截断、时间差 8 小时、中文乱码，上线后财务对账发现差异。行数+聚合+抽样三层校验，连续多轮零差异才切换。
10
没有回滚预案，或预案没演练
切换后新库慢查询爆发，只能现场决策，慌乱中又写了脏数据。回滚方案（双写回流/反向 CDC/停机回滚）三选一，并演练过至少一次。
自测

六道题

1. 迁移方法论六步的正确顺序是？
正确答案：评估→方案→双写/同步→校验→切换→回退。每步有出口标准：评估要四清单（数据/流量/依赖/约束），方案要含校验和回滚设计，同步要延迟稳定，校验要连续多轮零差异，切换窗口分钟级，回退是预先设计不是临时补救。
2. 同构迁移（MySQL→MySQL）TB 级数据，最合适的全量搬迁方式是？
正确答案：xtrabackup 物理迁移。TB 级数据逻辑导出（dump/insert）要十几个小时还可能丢一致性；xtrabackup 是在线物理备份，配合 xbstream 流式传输 + 并行，速度受磁盘/网络带宽限制，且天然一致性快照。之后用 binlog CDC 追赶增量。
3. 关于异构迁移中 Oracle→MySQL 的空字符串，正确的是？
正确答案：Oracle '' = NULL。所以 Oracle 里 WHERE name = '' 匹配的是 NULL 行，MySQL 匹配的是空串行，同一条 SQL 在两侧结果集不同——这是数据迁移后"莫名少数据/多数据"的经典根因，必须显式统一语义。
4. 数据校验三层体系中，能发现"金额字段被截断、精度丢失"的是？
正确答案：聚合级 + 抽样级。行数一致只证明"条数没丢"，证明不了内容对。SUM(amount) 差一分钱、字段值乱码、时间戳偏移 8 小时，都要靠聚合值对比和抽样逐字段比对才能发现。三层校验是递进关系，不能互相替代。
5. 关于 CDC 增量同步，说法正确的是？
正确答案：乱序 + 延迟毛刺都要处理。多分区并发消费破坏单行顺序（INSERT 先于 UPDATE 到达会丢更新），按主键 hash 分区；源库大事务产生超大 binlog 事件，CDC 延迟飙升几分钟，切换窗口要避开。DDL 也不是能忽略的——不加字段同步下游就丢数据。
6. 切换后想保留"可回滚"能力，最稳的设计是？
正确答案：双写期保留 + 新数据回流旧库。回滚最大的难题是"切换后新库产生了新数据"，双写保持期让这些数据实时在旧库也有副本，回滚 = 切读流量，秒级完成。完全不设计回滚的切换，出问题时连"怎么退回去"都要现场讨论。
