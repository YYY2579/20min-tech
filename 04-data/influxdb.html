开始前

模块 1

时序数据：它到底特殊在哪

指标、监控、IoT、日志时间戳 —— 这类数据的访问模式和交易数据完全不同，所有时序数据库的设计都是围着下面四个特征转的。

特征对存储引擎的要求
写多读少写入远高于读取（一台机器每秒几十万点很常见）。优化追加写，不优化更新（时序数据几乎不更新）
时间戳驱动数据按时间严格有序到达，时间就是天然主索引。查询几乎必带时间范围
时间范围读 + 降采样"最近一小时每秒均值"是标准查询模式。原始点密集存储，按窗口预聚合（downsample）成粗粒度长期保留
生命周期强原始数据 7~30 天，降采样数据留 1 年，汇总再留 3 年。TTL 不是可选项，是核心机制

时序 vs 关系型

维度MySQL / PostgreSQL时序数据库
主键业务 ID（随机分布）（序列标识 + 时间戳），时间单调
写入随机位置插入，维护 B+ 树顺序追加，LSM 结构天然契合
压缩通用压缩针对时间戳和指标值特化压缩（delta-of-delta、gorilla），典型 10:1 ~ 100:1
查询点查、事务范围扫、聚合、降采样
更新核心能力基本不支持（迟到数据靠写新时间点）
选型第一问：数据带不带时间戳？带 → 时序库（InfluxDB/TDengine/Prometheus）；不带 → 关系型。第二问：要不要多维度灵活聚合？要 → InfluxDB；只要采集+告警+生态 → Prometheus。第三问：数据量是否超单机？超 → 看分布式方案。
模块 2

InfluxDB 2.x 架构：bucket、org 与 token

2.x 把 1.x 的"database + retention policy + user"体系换成了"bucket + organization + token"，上手第一件事就是建立这套心智模型。

概念解释
Organization（org）组织/租户单位，所有资源挂在 org 下。多团队用多 org 隔离
Bucket数据容器 = 1.x 的 database + retention policy 合体。写入和查询都按 bucket 指定，每个 bucket 有自己的保留期
TokenAPI 密钥，1.x 的 user/password 在 API 层的替代。有四种权限：operator / all-access / read-write / read。读写分离就发两个 token
Measurement类似表名。一个 bucket 内多个 measurement 共存（cpu、mem、disk）
Seriesmeasurement + tag 集合 + field 的唯一组合。series 数量 = 高基数问题的核心指标（模块 6）

存储引擎 TSM

  • TSM（Time-Structured Merge Tree）：LSM 树的时序变体。数据先写 WAL（崩溃恢复），再进内存 Cache，满后压缩成不可变的 TSM File 落盘
  • TSM File 内按 series 聚合并压缩：时间戳用 delta-of-delta、浮点用 Gorilla XOR 压缩，压缩比通常 10:1 以上
  • 后台 compaction 把小 TSM 合并成大 TSM，同 LSM 思路
  • TSI（Time Series Index）：1.6+ 引入的倒排式序列索引，替代早期的 in-memory index。它让高基数不再必然炸内存，但也解释了 cardinality 依然关键 —— 索引本身也吃磁盘和内存
# bucket 的日常操作（CLI）
influx bucket create -n sensors -o myorg -r 30d       # 建 bucket，保留 30 天
influx bucket ls                                       # 列出所有 bucket
influx bucket update -i <id> -r 7d                       # 改保留期

# token 最小权限实践：采集端只给写 token，看板只给读 token
influx auth create -o myorg --write-bucket sensors -d "collector-write"
influx auth create -o myorg --read-bucket sensors -d "grafana-read"

# HTTP API 直接写（生产最常见的路径）
curl -i -XPOST "http://localhost:8086/api/v2/write?org=myorg&bucket=sensors&precision=ns" \
  --header "Authorization: Token my-token" \
  --data-binary "temperature,location=room1 value=22.5 1729161600000000000"
2.x 的认证设计有个大坑：HTTP API 必须带 token，且 ?org= 参数和 token 里的 org 要对应。新手最常见的 401 不是密码错，是漏了 org 参数或用了 operator token 之外的错误 scope。
模块 3

行协议 Line Protocol

InfluxDB 的写入格式只有一种：一行一条数据。格式错了服务端会静默丢数据或报 400，是新手第一大坑。

# 语法：measurement,tag_key=tag_value field_key=field_value timestamp
#        逗号分隔 tag    空格分隔 field   空格后是纳秒时间戳（可省略=服务端时间）

# 完整示例
weather,location=us-midwest,season=summer temperature=82,humidity=71i 1465839830100400200

# 拆解：
# weather        → measurement（表名）
# location,season → 两个 tag，逗号分隔，全部是 string
# temperature=82  → float 字段（不加后缀默认 float）
# humidity=71i    → 整数字段（i 后缀）
# 1465839830100400200 → 纳秒时间戳

# 字段类型后缀表
# 82        float   82i  integer   true  boolean
# "hello"   string（必须加双引号）   1465839830100400200 本身不带后缀

# 字符串值含空格/逗号/等号必须转义，不能加引号糊弄
weather,location=us\,midwest msg="hello\ world" 1465839830100400200

# 精度：precision 参数支持 ns / us / ms / s，默认 ns
curl -XPOST "http://localhost:8086/api/v2/write?org=myorg&bucket=b&precision=ms" --data-binary "..."

tag 和 field 的区别（1.x 时代叫 tag / field，至今没变）

维度TagField
类型只能是 stringfloat / integer / boolean / string
索引建索引，按 tag 过滤/分组极快不建索引，过滤要全扫
用途维度：host、region、service、sensor_id指标值：temperature、latency、count
数量低基数（几十到几千个不同值）随意
"把 user_id 当 tag" 是 InfluxDB 头号事故。tag 建索引，100 万个 user_id 就是 100 万个 series，TSI 索引和查询性能双爆（模块 6 详述）。判断标准：这个字段的 distinct 值会不会超一万？会 → 放 field；不会 → 放 tag。
模块 4

Flux 查询语言基础

Flux 是 2.x 的默认查询语言，用管道（|>）把操作串起来。它和 SQL 的思维差别很大：先选数据流，再逐级变换。

# Flux 的"Hello World"：最近一小时 room1 的温度
from(bucket: "sensors")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "weather")
  |> filter(fn: (r) => r.location == "room1")
  |> filter(fn: (r) => r._field == "temperature")
  |> yield(name: "mean")

# 五个核心函数
# from(bucket)      指定数据源
# range(start/stop) 时间窗口，Flux 里必须显式给！
# filter(fn)        按 record 过滤（r._measurement / r.tag / r._field）
# aggregateWindow   按时间窗口聚合（降采样的核心）
# yield()           输出，可多次 yield 出多张结果表

# 降采样：每 5 分钟一个均值点
from(bucket: "sensors")
  |> range(start: -7d)
  |> filter(fn: (r) => r._measurement == "weather" and r._field == "temperature")
  |> aggregateWindow(every: 5m, fn: mean, createEmpty: false)

# 按维度分组统计：每个 location 的小时均值
from(bucket: "sensors")
  |> range(start: -24h)
  |> filter(fn: (r) => r._measurement == "weather")
  |> aggregateWindow(every: 1h, fn: mean, column: "_value", timeSrc: "_stop")
  |> group(columns: ["location"])
  |> yield(name: "per_location")

Flux 常用算子速查

算子作用
aggregateWindow(every, fn)时间窗口聚合：mean/sum/max/min/count/last
group(columns)按列分组，把多 tag 拆成多张结果表
map(fn)对每行做变换，如单位换算、打标签
join()关联两个数据流（性能敏感，慎用）
pivot()行转列：把 _field 变成列名，Grafana 常用
sum() / count()全局聚合，返回单值
top() / bottom()取前 N / 后 N，如 CPU 最高的 5 台机器
Flux 第一大坑：不写 range()。没有时间边界的 Flux 查询会尝试扫描 bucket 全部历史数据，直接超时或拖垮实例。所有 from() 后面第一件事就是 range()，而且 start 尽量用相对时间（-1h）而不是绝对时间戳。
模块 5

保留策略与降采样

时序数据的成本不在写入，在无限期保留。InfluxDB 的答案是多级 bucket + task 自动降采样。

保留策略（Retention）

层级典型配置用途
原始 bucket保留 7~30 天明细排查、故障定位
降采样 bucket保留 1 年（1 分钟粒度）看板趋势、容量规划
汇总 bucket保留 5 年+（1 小时粒度）年度报表、同比分析
# 1.x 保留策略语法（存量系统会见到）
CREATE RETENTION POLICY "seven_days" ON mydb DURATION 7d REPLICATION 1
CREATE RETENTION POLICY "one_year" ON mydb DURATION 52w REPLICATION 1 DEFAULT

# 2.x 就是 bucket retention，无需单独概念
influx bucket create -n metrics_raw -o myorg -r 7d
influx bucket create -n metrics_1m -o myorg -r 365d
influx bucket create -n metrics_1h -o myorg -r 1825d

降采样 Task：Flux 的定时任务

# 把原始数据聚合成 1 分钟粒度，写进降采样 bucket
# 创建方式：influx task create -f task.flux
option task = {
  name: "downsample_1m",
  every: 1m,
  offset: 10s
}

raw = from(bucket: "metrics_raw")
  |> range(start: -2m)                    # 每 1m 跑一次，处理上两分钟的数据
  |> filter(fn: (r) => r._measurement == "cpu")

aggregated = raw
  |> aggregateWindow(every: 1m, fn: mean)
  |> map(fn: (r) => ({ r with _measurement: "cpu_1m" }))

aggregated
  |> to(bucket: "metrics_1m", org: "myorg")

# 管理 task
influx task ls
influx task run retry -i <task-id>          # 补跑历史数据
influx task log -i <task-id>                # 看执行日志，排查没数据的原因
降采样的黄金法则：原始数据保留 ≤30 天，趋势数据 1 年，汇总数据 5 年。一套三级 bucket 能把存储成本压到 1/10。判断某查询要不要建汇总层很简单：如果它每天被看 100 次以上，聚合逻辑就该固化下来，而不是每次查询现算。
模块 6

高基数：series cardinality 爆炸

InfluxDB 的一切性能问题，最后几乎都能追溯到 series 数量。这是时序数据库的第一性原理：series 数是内存和索引的硬成本。

什么是 series

  • series = measurement + tag 集合 + field 的唯一组合。cpu,host=h1 usage=1.0 和 cpu,host=h2 usage=1.0 是两条 series
  • 每个 series 在 TSI 索引里有一条记录，series 总数直接决定索引体积。100 万 series 和 100 个 series 的查询开销天差地别
  • 官方经验：单 bucket 控制在 百万级 series 以内是舒适区；超过就要开始拆分 bucket 或重新设计 tag

基数爆炸的标准配方

错误设计后果
cpu,user_id=100001 usage=55100 万用户 = 100 万 series，索引直接爆
api,request_id=abc-123 latency=12每条请求一个 series，请求量即 series 量
sensor,uuid=<随机> temp=22设备每次重连换 UUID，series 无限增长
log,container_id=<12位哈希> lines=42容器重建即新 series，K8s 场景一天几十万
# 排查 cardinality：1.x
SHOW SERIES CARDINALITY
SHOW CARDINALITY ON mydb                            # 按 measurement 统计

# 2.x：通过 _internal bucket 或 API 看索引统计
from(bucket: "_internal")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "boltdb_stats" or r._measurement == "tsm1_engine")

# CLI 方式（2.7 起有 cardinality 子命令族）
influx v1 cardinality                                # v1 兼容接口的 cardinality 查询

# 自救三板斧
# 1. 高基数 tag 降级为 field（放弃按它过滤，换查询模式）
# 2. 高基数 tag 哈希/取模收敛：trace_id → trace_id % 1000 作为 tag
# 3. 高基数维度不进 InfluxDB：明细进日志系统，指标只留聚合维度
一个真实的性能曲线：10 万 series 时查询 10ms；100 万 series 时同样查询变 500ms+；1000 万 series 时索引开始疯狂吃内存，实例随时可能 OOM。cardinality 不是"以后再说"的问题，是 schema 设计第一天就定死的问题 —— 改 schema 要迁历史数据。
模块 7

1.x 与 2.x 的差异

两代产品数据模型和 API 完全不兼容，但 1.8 提供兼容层。国内大量存量系统还在 1.x，迁移方案必须懂。

概念1.x2.x
数据容器database + retention policy（RP 是 database 内的子概念）bucket（RP 合并进 bucket 的 retention 设置）
查询语言InfluxQL（类 SQL）为主，1.8 起支持 FluxFlux 为主（UI 默认），InfluxQL 通过 dbrp 映射保留
认证user/password，写权限按 databaseorganization + token（API key），权限按 bucket scope
管理界面仅数据浏览，配置靠 HTTP API / influxd 命令完整 UI：bucket、token、task、dashboard、alert 全可视化
客户端influxdb-java / go 等语言 clientinfluxdb-client-*（新 SDK）+ v1 兼容 API
订阅Kapacitor 链路task + checks + notification endpoints（内置）

InfluxQL vs Flux 同一查询

# InfluxQL（1.x，类 SQL 思维）
SELECT mean("value") FROM "cpu" WHERE "host" = 'h1' AND time > now() - 1h GROUP BY time(5m)

# Flux（2.x，管道思维）
from(bucket: "mydb/autogen")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "cpu" and r.host == "h1")
  |> aggregateWindow(every: 5m, fn: mean)

迁移路径（1.8 → 2.x 不停机）

1.8 作为跳板：升级存量到 1.8（同时支持 InfluxQL 和 Flux，客户端无感）
双写：采集端同时写 1.8 和新 2.x，校验数据一致性（重点核对时间戳精度和字段类型）
建 dbrp 映射：2.x 上执行 influx v1 dbrp create，把 bucket 映射成 1.x 的 database+RP，老客户端直连 2.x
切流量：读流量先切 Grafana datasource，写流量灰度切采集端，1.8 缩容为备份
# dbrp：让 InfluxQL 老客户端无缝访问 2.x 的关键映射
influx v1 dbrp create \
  --db mydb --rp autogen \
  --bucket-id <bucket-uuid> \
  --org myorg --token my-token

# 老客户端配置不变，把 URL 从 1.8:8086 指向 2.x:8086 即可
# url = "http://influxdb2:8086"  database = "mydb"  retention-policy = "autogen"
新装默认 2.x，但 2.x OSS 有几个缩水要知道：① 不支持集群（多节点高可用只有 InfluxDB Enterprise / Cloud 有）；② 无内置 RBAC 细粒度（token 是粗粒度 scope）；③ 部分 2.x 早期 bug 在 2.7.x 才稳定。单机百万 series 以内，OSS 完全够用；要集群就评估 TDengine、VictoriaMetrics 或商业版。
模块 8

与 Prometheus 的选型对比

两个都是监控时序库，但设计哲学几乎相反：Prometheus 是 pull + 拉取生态，InfluxDB 是 push + 通用存储。

维度PrometheusInfluxDB
采集模型Pull 拉取：定期 scrape 目标 /metrics，服务发现驱动Push 推送：Telegraf / 客户端主动写，网关设备友好
查询语言PromQL（函数式，为告警规则设计）Flux / InfluxQL（通用分析导向）
数据模型metric + label（与 tag 同义），同样受高基数困扰measurement + tag + field
存储本地 TSDB（WAL + block），单机 2 周典型保留TSM 引擎，保留策略灵活（bucket 级）
水平扩展OSS 单机；扩展靠 Thanos / Cortex / VictoriaMetricsOSS 单机；扩展靠 Enterprise 集群
告警原生 PromQL 告警规则 + Alertmanager，生态最成熟checks + notification（2.x），或 Kapacitor
生态位K8s / 云原生监控事实标准IoT / DevOps / 业务指标通用指标库

选型决策树

跑在 K8s 上、要 Pod 自动发现、要现成告警 → Prometheus（+ Alertmanager + Grafana），这是云原生默认答案
设备在 NAT 后、防火墙内、只能主动上报 → InfluxDB push 模型天然合适，Prometheus pull 得改 Pushgateway（不推荐）
指标要长期保留 + 多级降采样 + 业务维度关联分析 → InfluxDB（Flux 的 join/pivot 比 PromQL 灵活）
高基数是大头（百万 label 组合） → 两个都危险，认真做 schema 收敛，或评估 VictoriaMetrics（对高基数更友好）
已有 Prometheus 想要长期存储 → remote_write 到 Thanos/VictoriaMetrics/InfluxDB，不要推倒重来
# 混合架构常见姿势：Prometheus 负责实时告警，InfluxDB 负责长期归档
# prometheus.yml
remote_write:
  - url: "http://influxdb:8086/api/v1/prom/write?org=myorg&bucket=metrics"
    bearer_token: my-token
# Prometheus 的数据按 /api/v1/prom/write 兼容协议直接进 InfluxDB bucket
# 注意：prometheus 的 __name__ 变成 measurement，label 变 tag —— cardinality 原样搬过来
一句话选型：云原生 K8s 监控选 Prometheus（拉取 + 告警 + 服务发现是降维打击）；IoT / 业务指标 / 长期分析选 InfluxDB（推送 + 灵活保留 + Flux 分析）；大规模高基数两个 OSS 都别硬扛，上 VictoriaMetrics 或商业方案。
模块 9

十个线上坑

1
把高基数 ID 当 tag（user_id、trace_id、UUID）
series 数量随用户量线性爆炸，TSI 索引膨胀、查询变慢、实例 OOM。判断标准：distinct 值会不会超一万。会 → 放 field 或收敛精度。
2
Flux 查询不写 range()
没有时间边界 = 扫描 bucket 全部历史，查询超时或拖垮实例。from() 后第一件事永远是 range(start: -1h) 这类相对窗口。
3
bucket 不设保留期，数据无限增长
磁盘早晚写满，且查询时间范围越大越慢。原始 7~30 天 + 降采样 1 年 + 汇总 5 年，三级 bucket 是标准解法。
4
时间戳精度混乱
客户端发毫秒、服务端按纳秒解释，数据落到 1970 年或查询永远 range 不到。统一 precision 参数，行协议时间戳自己算好。
5
field 类型后期变更
同一 measurement 的同一 field，昨天是 float 今天是 string，InfluxDB 直接报 field type conflict，写入失败。schema 一开始就定死。
6
所有服务共用一个 all-access token
采集端拿到全权 token，误操作能删 bucket。采集端发 write-scope token，看板发 read-scope token，按最小权限拆。
7
1.x 迁 2.x 直接停机切换
数据模型不兼容，客户端 SDK 不兼容，直接切必然大面积报错。走 1.8 双写 + dbrp 映射的灰度路径。
8
降采样 task 的 every 和 range 不匹配
task 每 1m 跑但 range 只取 -30s，边界数据被反复漏采；或窗口重叠导致重复点。every 和 range 留重叠余量，range 覆盖上一个周期。
9
把 InfluxDB 当日志/事件存储
每条请求写一行带十几个 field 的明细，写入吞吐直接崩。明细进日志系统（ES/Loki），InfluxDB 只放聚合后的指标。
10
小批量高频 HTTP 写入
每条数据一个 POST，HTTP 开销主导，吞吐上不去。攒批 5000 行 / 5~10MB 一次，或上 Telegraf 自动攒批 + gzip。
自测

六道题

1. 集群查询越来越慢、内存持续上涨，最可能的根因是？
正确答案：高基数 tag 导致 series 爆炸。series = measurement + tag 集合 + field 的唯一组合，每个 series 都在 TSI 索引里有记录。100 万 series 和 100 个 series 的查询开销差几个量级，且索引常驻内存。保留期太短只会省内存，不会让查询变慢。
2. 下面哪行是合法的 Line Protocol？
正确答案：cpu,host=h1 usage=55.0 1729161600。tag 在 measurement 后用逗号连接且必须是 string，field 用空格分隔，时间戳可省略（默认服务端纳秒时间）。usage=55.0 是 field 不是 tag，不能放在逗号段里。
3. Flux 查询的正确起手式是？
正确答案：from 后立即 range。range 给数据流加时间边界，Flux 引擎据此裁剪要读的 TSM block。顺序写反虽然语法合法，但过滤在全量数据上做，性能差一个量级；完全不给 range 会扫描全部历史直接超时。
4. InfluxDB 2.x 的 bucket 相当于 1.x 的什么？
正确答案：database + RP 合体。1.x 里一个 database 下挂多个 RP 分别设保留期；2.x 取消 RP 概念，保留期直接是 bucket 的属性。需要不同保留期的数据就建多个 bucket，而不是一个 bucket 多个 RP。
5. tag 和 field 的核心区别是？
正确答案：tag 建索引且只能是 string。按 tag 过滤/分组走 TSI 索引，百万 series 内毫秒级；field 过滤要扫数据。所以维度放 tag、指标值放 field，且 tag 必须低基数 —— 高基数放 tag 就是 series 爆炸。
6. 与 Prometheus 相比，InfluxDB 的典型优势场景是？
正确答案：推送模型 + 灵活保留。Prometheus 是 pull + 服务发现 + Alertmanager，K8s 场景是事实标准；InfluxDB 的 push 模型对 NAT 后设备友好，bucket retention + Flux task 降采样适合长期指标归档。高基数场景两个 OSS 都要收敛 schema。
