一个前置认知：MySQL 的索引是引擎层概念（InnoDB 的 B+ 树），不是 Server 层。所以"索引失效"的真相分两种：① 优化器认为走索引不划算（选择率太高），主动选全表扫描；② SQL 写法让索引列无法比较（函数、转换、前缀通配），物理上就用不上。排查时先分清是哪一种。
模块 1

B+ 树结构与容量计算

InnoDB 的所有索引都是一棵 B+ 树。把"千万级表只要 2~3 次 IO"这句话算出来，是理解索引一切行为的地基。

三个必背常量

参数值含义
数据页大小16 KB（16384 B）InnoDB 磁盘分配的最小单位，一个页 = 一个 B+ 树节点
页内目录项≈ 1170 条非叶子节点每条 = 8B 主键 + 6B 页指针，16384 / 14 ≈ 1170
叶子行数行大小决定1KB/行 → 16 行/页；500B/行 → 32 行/页

三层 B+ 树到底能撑多少行（完整计算）

# 前提：bigint 主键（8B）、行大小 1KB（一页 16 行）

# 第 1 层（叶子）：每页 16 行
2 层树容量 = 1170 个叶子页 × 16 行 = 18,720 行

# 第 2 层：根节点指向 1170 个页，每个页又是叶子
3 层树容量 = 1170 × 1170 × 16 = 约 2190 万行

# 第 3 层：
4 层树容量 = 1170 × 1170 × 1170 × 16 = 约 256 亿行（现实中不存在）

# 换成 500B 行大小（一页 32 行）：
3 层树容量 = 1170 × 1170 × 32 = 约 4380 万行

# 所以"3 层 B+ 树支撑千万行"的准确表述：
#   1KB 行 → 3 层 ≈ 2200 万行；500B 行 → 3 层 ≈ 4400 万行
#   1000 万行、1KB 行的表，索引高度正好 3 层

高度与 IO 次数的换算

# 一次主键点查的磁盘 IO = 树高 - 1（根节点常驻 buffer pool，不读盘）
树高 3 → 最多 3 次页定位，其中根页命中内存，实际随机 IO = 2 次

# 时间换算（NVMe SSD 随机读 20~100μs）：
2 次 IO × 50μs = 0.1ms；加 buffer pool 命中（命中率 99%）后平均 < 0.01ms

# 结论（面试标准答案）：
#   千万级表的主键点查，索引层面只需要 2 次随机 IO，是微秒~毫秒级；
#   慢的不是 B+ 树深度，是回表、是扫了多少行、是排序用了磁盘。
结构要点（决定后面所有行为）：① 只有叶子节点存数据，非叶子只存"目录"（键值 + 页号），所以非叶子能存上千条目，树才矮；② 叶子节点间用双向链表串联，所以范围扫描（BETWEEN）只需定位起点后顺序翻页，不用回溯父节点；③ 页内记录按主键有序，页内查找用"稀疏目录 + 二分"，不是逐行扫。
B+ 树是"往矮里长"的，不是"往高里长"。树高每 +1，容量 ×1170，但 IO +1。真正让查询从毫秒变秒的三件事：树高从 3 变 4（表大到千万级以上 + 行很宽）、随机 IO 变成顺序全表扫描（优化器弃索引）、排序缓冲区放不下（filesort 落盘）。建索引、写 SQL 都是在和这三件事作斗争。
模块 2

聚簇索引 vs 二级索引

InnoDB 的表又叫"索引组织表"：数据本身就是按主键组织的 B+ 树。这一点是 InnoDB 和 MyISAM 的分水岭。

对比项InnoDB（聚簇）MyISAM（非聚簇）
主键索引叶子节点存整行数据，找到索引即找到行叶子节点存行地址（偏移量），还要去数据文件取
二级索引叶子节点存主键值 → 拿主键回聚簇索引查（回表）叶子节点存行地址 → 直接定位数据，无回表
数据与索引同一个 .ibd 文件，物理按主键排列.MYD 数据 + .MYI 索引，两个文件
必须主键是。无显式主键则选第一个非空唯一索引，否则生成 6 字节隐藏 row_id否
COUNT(*)扫描某个索引统计（无 WHERE 时选最小索引）直接读计数器，O(1)
插入性能自增主键顺序追加快；随机主键（UUID）页分裂严重行插入位置不影响索引结构
-- 回表的完整路径（二级索引叶子存的是主键值）
SELECT * FROM t_order WHERE user_id = 888;

-- 执行过程：
-- 1. 在 idx_user(user_id) 这棵二级 B+ 树里定位 user_id=888
-- 2. 叶子节点拿到主键值，比如 order_id = 5001234
-- 3. 拿 order_id 去聚簇索引再查一次（这一次就是"回表"）
-- 4. 取出整行
-- 代价：匹配 N 行 = 2N 次 B+ 树查找（N 次二级 + N 次聚簇）

-- EXPLAIN 佐证：type=ref，Extra 没有 Using index
+----+---------+--------+-------+---------------+----------+---------+-------+------+----------+-------------+
| id | table   | type   | key   | key_len | ref         | rows | filtered | Extra       |
+----+---------+--------+-------+---------------+----------+---------+-------+------+----------+-------------+
|  1 | t_order | ref    | idx_user | 9     | const       |   42 |   100.00 | Using where |
+----+---------+--------+-------+---------------+----------+---------+-------+------+----------+-------------+
推论一：主键越小，二级索引越小。二级索引每片叶子都存一份主键值：int（4B）比 bigint（8B）省一半，UUID（36B 字符串）让索引膨胀近 9 倍，还带来随机插入的页分裂。能自增 int 就别用 UUID。
推论二：没有主键的 InnoDB 表，每行都背着 6 字节隐藏 row_id，且二级索引实际按它回表——这就是为什么"必须给表显式定义主键"是 InnoDB 铁律。
模块 3

回表、覆盖索引与延迟关联

回表是二级索引查询的默认动作，覆盖索引是把回表消掉的手段。判断标准只有一个：执行计划 Extra 里有没有 Using index。

-- 场景：idx_user(user_id)，查"用户 888 的所有订单金额"

-- 写法 A：select * → 必然回表
SELECT * FROM t_order WHERE user_id = 888;
-- Extra: Using where           ← 没有 Using index，说明回表了

-- 写法 B：只查索引里有的列 → 覆盖索引，零回表
SELECT order_id, user_id FROM t_order WHERE user_id = 888;
-- Extra: Using index           ← 只访问 idx_user 就拿到全部结果

-- 写法 C：需要 amount（不在 idx_user 里）→ 回表，除非建覆盖索引
CREATE INDEX idx_user_amount ON t_order(user_id, amount);
SELECT order_id, user_id, amount FROM t_order WHERE user_id = 888;
-- Extra: Using index           ← 三列全在新索引里，零回表

延迟关联：既要回表又要分页时的标准解法

-- 反例：深分页 + 回表，limit 100000,10 要回表 100010 次
SELECT * FROM t_order ORDER BY create_time LIMIT 100000, 10;

-- 正解：先用覆盖索引拿到 10 个主键（零回表），再回表取整行
SELECT o.*
FROM t_order o
JOIN (
  SELECT order_id FROM t_order
  ORDER BY create_time
  LIMIT 100000, 10          -- 覆盖索引扫描，只翻叶子页链表
) t ON o.order_id = t.order_id;   -- 只回表 10 次

-- 效果：100010 次回表 → 10 次回表，P99 从几百 ms 降到几 ms
-- 前提：create_time 上有索引（idx_time），子查询走 Using index
覆盖索引的三个实战要点：① EXPLAIN 出现 Using index 就是覆盖，没有就是回表；② 索引列顺序按"等值条件列在前、排序列/范围列在后"设计，让 (user_id, create_time) 这类组合同时服务过滤和排序；③ 覆盖索引是有成本的——每个索引都是一棵要维护的 B+ 树，写放大和页分裂都翻倍。只为高频查询建覆盖索引，别把每列都塞进去。
模块 4

联合索引与最左前缀

联合索引 (a, b, c) 不是"三个单列索引"，排序规则是先按 a、再按 b、再按 c。匹配必须从最左列开始，中间不能断。

-- 索引：KEY idx_name_phone (user_name, phone)
-- 逻辑排序效果（想象 Excel 按两列排序）：
-- (张三, 138..) < (张三, 139..) < (李四, 137..) < (王五, 136..)
-- 即：name 相同才轮到 phone 有序，name 不同时 phone 完全无序

匹配规则全表

查询条件用到的索引列原因
user_name = '张三'user_name最左前缀命中
user_name = '张三' AND phone = '138...'user_name, phone两列等值，全命中
user_name LIKE '张%' AND phone = '138...'user_name, phonename 是前缀范围，phone 仍可二分定位
phone = '138...'无缺最左列 name，整棵索引用不上
user_name = '张三' AND phone LIKE '%138'只用 user_namephone 前缀通配无法二分，只能过滤（ICP 可用）
user_name > '张' AND phone = '138...'只用 user_name范围列之后的列无法定位，只能过滤
user_name BETWEEN '张' AND '李' AND phone='138'只用 user_name同上：范围断开后续匹配
-- 三条设计原则：
-- 1. 把选择性最高的等值列放最左（区分度：user_id 百万级 > status 4 个值）
-- 2. 范围列放最后（BETWEEN / > / < / LIKE 前缀 之后的列只能过滤）
-- 3. 排序列若想消掉 filesort，顺序必须与 ORDER BY 完全一致：
--    KEY(user_id, create_time) 才能优化
SELECT * FROM t_order WHERE user_id = 888 ORDER BY create_time DESC LIMIT 10;
-- 走索引有序扫描，Extra 无 Using filesort；缺 create_time 或顺序错都会排序

-- MySQL 8.0.19+ 的 index skip scan：
-- 优化器会自动"跳"过前导列（仅当前导列区分度极低时），
-- 让 (user_name, phone) 支持纯 phone 查询。可用 optimizer_switch='skip_scan=off' 关闭
最左前缀最常犯的错：以为 (a,b) 索引能服务 "WHERE b = ?"。不能。虽然物理上 b 在页内也有序，但不同 a 值下的 b 段互不相邻，全库扫描 b 只能全表。解决办法：① 建 (b) 单列索引；② 如果查询总是 (b,c) 形态，直接建 (b,c)；③ 8.0 以上可以指望 skip scan，但别把它当设计依据。
模块 5

索引下推 ICP

ICP（Index Condition Pushdown）把 WHERE 中能用索引列判断的条件下推到存储引擎层，在回表之前就过滤掉不匹配的行。MySQL 5.6 引入，默认开启。

-- 索引：KEY(zipcode, address)，行很宽（含大字段）
SELECT * FROM user_addr
WHERE zipcode = '100000' AND address LIKE '%朝阳%';

-- 没有 ICP：
--   引擎层按 zipcode 范围取出所有行 → 全部回表 → Server 层再过滤 address
--   回表次数 = zipcode='100000' 的行数（可能几万行）

-- 有 ICP：
--   address 是索引的一部分，引擎层在页内直接判断 LIKE，不满足不取出
--   回表次数 = 同时满足两个条件的行数（可能几百行）
--   EXPLAIN Extra: Using index condition
Extra 值含义
Using index conditionICP 生效：索引列条件下推到引擎层过滤，减少回表
Using index覆盖索引：所有列都在索引里，零回表（比 ICP 更强）
Using whereServer 层还有过滤条件（非索引列），或回表后过滤
Using MRR多范围读取：二级索引结果按主键排序后批量回表，把随机 IO 变顺序
# ICP 相关开关（默认全开，排查时可逐个关）
SET optimizer_switch = 'index_condition_pushdown=off';
SET optimizer_switch = 'mrr=on,mrr_cost_based=off';   -- 强制走 MRR
SET GLOBAL innodb_adaptive_hash_index = ON;

# 适用范围：InnoDB 和 MyISAM 的 range / ref / eq_ref / index 访问都支持；
# 全表扫描（type=ALL）和聚簇索引扩展（secondary index 的 extended secondary）有关，
# 分区表、子查询等场景有限制。对"回表成本高"的宽表收益最大。
ICP 与覆盖索引的关系：覆盖索引是"连引擎层都不用出"，ICP 是"少出引擎层"。二者叠加时优先覆盖；不能覆盖时，ICP 把回表次数从"索引匹配数"降到"索引 + 条件下推后的匹配数"，对大结果集 + 宽表的场景经常有 10 倍以上差距。
模块 6

哈希索引与自适应哈希索引

哈希索引是 O(1) 等值查找，但 InnoDB 没有显式哈希索引，只有自动的 AHI。理解边界才能不踩坑。

类型是否可控说明
InnoDB 显式哈希不支持InnoDB 的 CREATE INDEX 只有 BTREE 一种形态（含全文、空间索引）
自适应哈希 AHI全局开关，不可按索引定制InnoDB 自动监测"热点页"，为频繁等值访问的页在内存建哈希索引
MEMORY 引擎哈希支持CREATE INDEX ... USING HASH —— 但数据只在内存，重启即失
自定义哈希列手动实现加一列 crc = CRC32(email)，索引建在 crc 上，模拟等值哈希（《高性能 MySQL》经典技巧）
-- 自适应哈希索引的真实配置（MySQL 8.0）
innodb_adaptive_hash_index = ON          -- 默认开；写多读少、或 latch 争用高时可关
innodb_adaptive_hash_index_parts = 8     -- 8.0.18+：分区减少锁竞争

-- 查看 AHI 状态
SHOW ENGINE INNODB STATUS\G
-- 看 SEMAPHORES 段：大量 OS waits / spin rounds 说明 AHI 争用严重
-- 看 INSERT BUFFER AND ADAPTIVE HASH INDEX 段的 hash searches/s 趋势

-- 关闭 AHI 的正确姿势（重启生效于全局）：
SET GLOBAL innodb_adaptive_hash_index = OFF;   -- 需重启实例才完全释放内存结构

哈希 vs B+ 树的能力边界

能力哈希索引B+ 树
等值查询O(1)，理想O(log n)，树高 3 也是常数级
范围查询不支持叶子链表顺序扫描，天然支持
排序不支持索引本身有序
最左前缀只能用全部列支持部分列匹配
内存占用额外哈希表即数据本身
AHI 的两个真相：① 它只对等值查询加速（WHERE pk = ? / 唯一索引等值），对范围、排序、JOIN 无效，别指望它救范围查询；② 它不是免费的——高并发点查时 AHI 的 latch 可能成为瓶颈（8.0 用分区缓解）。纯点查负载且 buffer pool 命中率已很高时，AHI 收益边际，写密集场景建议直接关掉。
模块 7

索引失效的八种场景

每种都给了"反例 → 现象 → 正解"。判断标准：EXPLAIN 的 type 变成 ALL、key 变 NULL、rows 暴涨。

-- 1. 对索引列用函数
-- ✗ WHERE DATE(create_time) = '2026-10-16'          → type=ALL，扫全表
-- ✓ WHERE create_time >= '2026-10-16' AND create_time < '2026-10-17'
--    范围命中 idx_time，Extra 无 filesort

-- 2. 隐式类型转换（字符串列传数字）
-- ✗ WHERE phone = 13800000000        → 列是 VARCHAR，数字让列被转换，type=ALL
-- ✓ WHERE phone = '13800000000'      → 引号保住字符串类型，type=ref
--    注意：MySQL 8.0.21+ 对这类转换会告警，但不会自动改对

-- 3. OR 连接非索引列
-- ✗ WHERE user_id = 888 OR amount = 100   → amount 无索引，整体 type=ALL
-- ✓ 拆 UNION all：
SELECT ... WHERE user_id = 888
UNION ALL
SELECT ... WHERE amount = 100;   -- 各走各的索引

-- 4. != / <> / NOT IN / NOT EXISTS
-- ✗ WHERE status != 0    → 大多数场景优化器选全表（排除多行时索引无意义）
-- ✓ 改成 IN 正集合：WHERE status IN (1,2,3)

-- 5. LIKE 前缀通配
-- ✗ WHERE user_name LIKE '%张三'    → 前缀不定，type=ALL
-- ✓ WHERE user_name LIKE '张三%'    → 前缀确定，type=range
-- 后缀通配的检索需求：上全文索引（模块 8），别硬凹 B+ 树

-- 6. 联合索引跳过最左列 / 中间断
-- ✗ 索引(user_name, phone)，WHERE phone = '138...'          → 无索引
-- ✗ WHERE user_name > '张' AND phone = '138...'  → 范围列后断开，phone 失效

-- 7. 字符集/排序规则不一致（JOIN 场景）
-- ✗ a.phone utf8mb4 与 b.phone utf8，JOIN 时整列隐式转换 → 索引失效
-- ✓ 建表时统一 utf8mb4_general_ci，JOIN 列字符集校对规则一致

-- 8. 大数据类型选择性假象（如对 TEXT 前缀建索引但查询没前缀长度）
-- ✗ 索引(content(100))，WHERE content = '很长...' 全串比较 → 不走前缀索引
-- ✓ 用前缀索引就查前缀：WHERE LEFT(content,100) = '...' 或覆盖其他列

EXPLAIN 佐证（隐式转换的典型输出）

-- phone 上有索引 idx_phone，但传入数字：
mysql> EXPLAIN SELECT * FROM t_order WHERE phone = 13800000000;
+----+-------------+---------+------------+------+---------------+------+---------+------+----------+-------------+
| id | select_type | table   | partitions | type | possible_keys | key  | key_len | ref  | rows     | filtered | Extra       |
+----+-------------+---------+------------+------+---------------+------+---------+------+----------+----------+-------------+
|  1 | SIMPLE      | t_order | NULL       | ALL  | idx_phone     | NULL | NULL    | NULL | 9982317  |    10.00 | Using where |
+----+-------------+---------+------------+------+---------------+------+---------+------+----------+----------+-------------+
-- type=ALL、key=NULL、rows=998 万：索引彻底没用上

-- 加上引号：
mysql> EXPLAIN SELECT * FROM t_order WHERE phone = '13800000000';
+----+-------------+---------+------------+------+---------------+----------+---------+-------+------+----------+-------+
| id | select_type | table   | partitions | type | possible_keys | key      | key_len | ref   | rows | filtered | Extra |

|  1 | SIMPLE      | t_order | NULL       | ref  | idx_phone     | idx_phone| 66      | const |    2 |   100.00 | NULL  |
+----+-------------+---------+------------+------+---------------+----------+---------+-------+------+----------+-------+
最容易骗过代码评审的一条："我知道隐式转换不好，但我们 ORM 生成的 SQL 参数是对象类型。"——ORM 拼出来的 SQL 一样会中招。凡是 WHERE 里出现数字字面量匹配字符串列，先去 EXPLAIN 看一眼 type。另一个隐蔽的：WHERE create_time = DATE(NOW())，等于对索引列套函数，直接 ALL。

索引选择、cardinality 与全文索引

cardinality：优化器选索引的依据

-- 看索引统计信息
mysql> SHOW INDEX FROM t_order;
+---------+------------+--------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+---------+
| Table   | Non_unique | Key_name     | Seq_in_index | Column_name | Collation | Cardinality| Sub_part| Packed| Null | Index_type| Comment |
+---------+------------+--------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+---------+
| t_order | 0          | PRIMARY      | 1            | order_id    | A         | 9973128   | NULL     | NULL  | NO   | BTREE     |         |
| t_order | 1          | idx_user     | 1            | user_id     | A         | 998416    | NULL     | NULL  | NO   | BTREE     |         |
| t_order | 1          | idx_time     | 1            | create_time | A         | 9985217   | NULL     | NULL  | NO   | BTREE     |         |
+---------+------------+--------------+--------------+-------------+-----------+-------------+----------+--------+------+------------+---------+
-- Cardinality = 该列不同值的估计数。order_id ≈ 997 万（几乎唯一，选择性 100%）
-- user_id ≈ 99.8 万（100 万用户，选择性 ~10%），create_time ≈ 997 万（秒级几乎唯一）
-- 优化器的决策逻辑（简化版）：
估算匹配行数 = 总行数 × (1 / cardinality)
-- user_id=888：1000 万 × (1/99.8 万) ≈ 10 行 → 走索引（回表 10 次便宜）
-- status=1（4 个值）：1000 万 × (1/4) = 250 万行 → 走索引要回表 250 万次，
--   随机 IO 比顺序全表扫描贵 → 优化器主动选全表（这是"正确的失效"）

-- 统计信息不准的修复：
ANALYZE TABLE t_order;                    -- 重新采样（默认 20 个页）
SET GLOBAL innodb_stats_persistent_sample_pages = 50;  -- 提高采样精度
SHOW STATUS LIKE 'handler_read%';           -- 验证实际读了多少行

-- 确认优化器选错时的兜底（谨慎）：
SELECT * FROM t_order FORCE INDEX(idx_user) WHERE user_id = 888;

倒排索引与全文索引基础

-- 正排索引：文档 → 词项列表
doc1 → [mysql, index, btree]
doc2 → [postgres, index]

-- 倒排索引：词项 → 文档列表（posting list）
mysql    → [doc1]
postgres → [doc2]
index    → [doc1, doc2]        -- 检索 "index" 直接命中两个文档，无需遍历
-- 本质：用预处理换查询速度，空间换时间。B+ 树做不到"词在任意位置"的匹配

-- InnoDB 全文索引（MySQL 5.6+ 内置）
CREATE FULLTEXT INDEX ft_content ON t_article(content);

SELECT * FROM t_article
WHERE MATCH(content) AGAINST('数据库 索引' IN NATURAL LANGUAGE MODE);

SELECT * FROM t_article
WHERE MATCH(content) AGAINST('+mysql -oracle' IN BOOLEAN MODE);  -- 布尔模式

-- 中文必须用 ngram 解析器（默认按空格分词，中文整篇是一个词）
CREATE TABLE t_article (
  id BIGINT PRIMARY KEY,
  content TEXT,
  FULLTEXT KEY ft_content (content) WITH PARSER ngram
) ENGINE=InnoDB;

-- ngram 参数（默认中文 2 字一词）
innodb_ft_min_token_size = 2     -- 配合 ngram_token_size 使用
ngram_token_size = 2             -- "数据库原理" → 数据/据库/库原/原理/.....（滑窗）
InnoDB 全文索引的边界：① 只对 InnoDB/MyISAM 的 CHAR/VARCHAR/TEXT 生效，且修改文本会触发 FTS 辅助表同步，写入有额外开销；② 相关性排序能力很基础（词频 × IDF 的简化版），要相关度打分、同义词、分词插件就上 Elasticsearch；③ 停止词和最小词长会过滤短词（"的"这类会被丢掉），检索不到别奇怪。B+ 树索引解决"精确/范围/排序"，全文索引解决"包含关系"，二者互补。
深坑

十个线上坑

1
WHERE 条件对索引列套函数
DATE(create_time)='2026-10-16'、LEFT(phone,3)='138' 都让索引失效，type=ALL。改成范围条件或表达式索引（MySQL 8.0 函数索引）。
2
字符串列查数字，隐式转换
phone = 13800000000（列是 VARCHAR）触发全列转换，EXPLAIN type=ALL、rows=998 万。加引号即可，但 ORM 生成的参数类型要一起检查。
3
select * 把覆盖索引打成回表
明明建了 (user_id, amount) 覆盖索引，一句 select * 全部回表。按需取列，或用延迟关联（子查询拿主键再 JOIN）。
4
联合索引列顺序拍脑袋
(status, create_time) 查 status + 时间范围还行，但查 (create_time) 单独条件时完全用不上。等值列在前、范围列在后、高区分度在前。
5
LIKE '%关键词' 当前缀用
前缀通配让 B+ 树无法二分，直接全表。'关键词%' 才能走 range。模糊检索需求应该建全文索引或上 ES。
6
深翻页 limit 100000,10 配 order by
要么 filesort 十万行、要么回表十万次。用书签法（WHERE create_time < 上一页末条 LIMIT 10）或延迟关联。
7
索引建太多，写入雪崩
一张表 12 个索引，每次 INSERT 要维护 12 棵 B+ 树，页分裂和 double write 全涨，写入 QPS 直接腰斩。单表索引建议 ≤ 5 个，先删从未用过的。
8
统计信息过期，优化器选错索引
大批量导入后没 ANALYZE TABLE，cardinality 还是旧值，优化器选了个区分度极低的索引，慢查询爆发。导入后必须刷新统计。
9
在低区分度列上建单列索引
status（4 个值）、gender（2 个值）、is_deleted 建索引几乎不用——除非数据极度倾斜且查稀有值。这类列只能做联合索引的辅助过滤。
10
用 UUID/随机字符串做主键
随机主键导致聚簇索引页分裂（写入放大）、二级索引膨胀近 9 倍、buffer pool 命中率下降。用自增或雪花（趋势递增）。
自测

六道题

1. 1000 万行、行大小 1KB 的 InnoDB 表，索引树高 3 层。一次主键点查最多涉及几次磁盘 IO？
正确答案：2 次。树高 3 意味着最多定位 3 个页，但根节点 99% 以上的查询都会命中 buffer pool（缓存），实际随机 IO 是 2 次。这也是"三层 B+ 树支撑千万行"的完整含义：容量 1170×1170×16 ≈ 2190 万行，代价 2 次 IO。
2. 哪个现象说明查询走了覆盖索引？
正确答案：Extra 里的 Using index。它表示所有需要的列都在索引里，无需回表。type=ref 只说明用了二级索引等值匹配，仍可能回表；rows 小也可能来自全表扫描的估算。
3. 索引为 KEY(user_name, phone)，哪条 SQL 能用上这个索引？
正确答案：第一个。注意 B 选项 WHERE 子句里条件的书写顺序不影响，实际还是只有 phone 等值——缺最左列 user_name，索引整体失效。最左前缀看的是哪些列被等值匹配，不是书写顺序。
4. 关于索引下推 ICP，正确的说法是？
正确答案：下推到引擎层、减少回表。ICP 让引擎在页内就用索引列判断条件，不满足的行不取出。它减少而非消除回表；彻底零回表是覆盖索引（Using index）的能力。
5. 下列哪种写法一定让索引失效（假设列上都有索引）？
正确答案：对索引列套函数。索引存的是 create_time 原值，套上 DATE() 后无法二分定位，只能全表扫描。IN 多个值会走 range，LIKE '张%' 前缀确定也走 range，都是有效用法。
6. SHOW INDEX 里的 Cardinality 表示什么？
正确答案：不同值的估计数。优化器用它估算匹配行数（总行数 / cardinality），选择率高时主动弃索引走全表——这是"合理的失效"，不是 bug。采样估算会过期，大批量导入后要 ANALYZE TABLE 刷新。

术语表

术语一句话解释
B+ 树多路平衡查找树，非叶子只存目录，叶子存数据且链表相连
数据页InnoDB 磁盘管理单位，16KB，一个页即一个 B+ 树节点
树高 / 阶根到叶子的层数；3 层 ≈ 2200 万行（1KB 行）
聚簇索引InnoDB 主键索引，叶子存整行，数据按主键物理排列
二级索引非聚簇索引，叶子存主键值，查询需回表
回表二级索引查到主键后，再去聚簇索引取整行的过程
覆盖索引查询列全在索引里，零回表，EXPLAIN 显 Using index
延迟关联先用覆盖索引拿主键再回表取整行，深分页标配
联合索引多列组成的 B+ 树，排序按列序依次进行
最左前缀联合索引必须从最左列开始连续匹配，范围列会截断后续
ICP索引下推：索引条件下推到引擎层过滤，减少回表
MRR多范围读取：二级索引结果按主键排序后批量回表
自适应哈希 AHIInnoDB 自动为热点页建的哈希索引，只加速等值查询
Cardinality索引列不同值的估计数，优化器选索引的核心依据
选择率匹配行数 / 总行数，过高时优化器主动弃索引
索引合并多个单列索引取并集/交集使用，EXPLAIN 显 index_merge
索引跳跃扫描MySQL 8.0.19+ 跳过低区分度前导列直接匹配后续列
页分裂随机插入导致页写满拆页，UUID 主键写入慢的根因
倒排索引词项 → 文档列表，全文检索的基础结构
ngram中文分词解析器，按 n 字滑窗切词（默认 2）
