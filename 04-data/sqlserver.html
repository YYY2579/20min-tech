模块 1

体系结构与内存架构

SQL Server 的内存管理思路和 MySQL/PG 差别很大：默认能拿多少拿多少，靠 max server memory 自己勒住。不理解这一点，运维就要吃大亏。

两大引擎

引擎组成职责
关系引擎命令解析器、查询优化器、查询执行器解析 SQL、生成执行计划、执行并下发存储引擎请求
存储引擎访问方法、缓冲区管理器、事务服务、锁管理器页的读写、事务日志、锁、行版本控制

存储基本单位：页与区

  • 页（page）= 8KB，是 IO 的最小单位。页头 96 字节 + 行偏移数组 + 行数据。单行数据最大 8060 字节，超出的列可存到溢出页。
  • 区（extent）= 8 个连续页 = 64KB，是分配的基本单位。统一区（8 页给同一对象）vs 混合区（8 页分给最多 8 个对象）。
  • 页类型：数据页、索引页、IAM/GAM/SGAM 分配位图页、PFS 页空闲空间页等。碎片化、填充率（fill factor）说的都是页内空间利用率。

内存：buffer pool 与 plan cache

消费者作用调优点
Buffer Pool缓存数据页和索引页，内存里最大的头。读请求命中 buffer pool 就不碰磁盘内存不足时疯狂换出 → PAGEIOLATCH_* 等待飙升
Plan Cache缓存编译后的执行计划，避免重复编译计划污染、参数嗅探、频繁重编译都发生在这里
查询内存授予排序、哈希连接的工作区（workspace memory）并发大查询多时 RESOURCE_SEMAPHORE 等待
列存/内存优化表列存索引缓存、Hekaton 内存表按需，大内存场景才显价值
-- 限制 SQL Server 最多用多少内存（必须配，不然它敢把系统吃干）
EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'max server memory (MB)', 10240;  -- 32G 机器留 8G 给系统和其他进程
RECONFIGURE;

-- 看内存都花哪了
SELECT type, SUM(single_pages_kb + multi_pages_kb) AS cache_kb
FROM sys.dm_os_memory_clerks
GROUP BY type ORDER BY cache_kb DESC;

-- 看计划缓存里的"一次性" SQL（未参数化导致缓存膨胀的元凶）
SELECT cp.objtype, cp.cacheobjtype, cp.usecounts, cp.size_in_bytes, st.text
FROM sys.dm_exec_cached_plans cp
CROSS APPLY sys.dm_exec_sql_text(cp.plan_handle) st
WHERE cp.objtype = 'Adhoc' AND cp.usecounts = 1
ORDER BY cp.size_in_bytes DESC;
不设 max server memory 是最常见的运维事故。SQL Server 默认按需拿内存，还可能触发系统内存压力去"借"，OS 被吃光后 RDP 都连不上。32G 机器建议 SQL Server 留到 24G 左右。
大内存实例（几百 GB）还要考虑 Lock Pages In Memory（LPIM），防止内核把 buffer pool 页换出去造成延迟毛刺。
Plan cache 的 LRU 是"零成本计划"逻辑：编译成本高的计划更不容易被清。optimize for ad hoc workloads 开启后，首次执行只存一个小的 stub 计划，第二次执行才缓存完整计划，能显著抑制 SQL 字符串硬编码带来的缓存膨胀。生产高峰期千万别 DBCC FREEPROCCACHE。
模块 2

索引与执行计划（和 MySQL 的核心差异）

概念对照：SQL Server vs MySQL InnoDB

概念SQL ServerMySQL InnoDB
聚集索引表可以是堆（heap）也可以有聚集索引。有聚集索引时，叶级就是数据行本身必须有聚集索引，默认用主键，没有显式主键则选第一个唯一非空索引或隐藏列
非聚集索引定位叶级存书签：有聚集索引时存聚集键，堆表存 RID（文件:页:行）叶级存主键值，回表拿整行
覆盖索引支持 INCLUDE (列)：把非键列挂在叶级，不参与 B 树排序无 INCLUDE 语法，只能把所有列塞进键里（影响排序和大小）
筛选索引支持带 WHERE 的部分索引，只索引满足条件的行不支持
索引视图支持物化视图（视图上建唯一聚集索引）不支持物化视图
列存索引列存索引（columnstore），压缩比常达 10 倍，分析型利器无列存索引（有列存格式的外部表生态）
统计信息直方图 200 步；表行数 ≤500 时每 500 次修改触发自动更新，>500 按约 20% 变化触发持久化统计信息，采样页数默认 20 页，10% 行变化触发重算

建一个覆盖索引（最高频的调优动作）

-- 查询：按客户查近 3 个月订单，按金额倒序取前 20
SELECT TOP 20 OrderId, OrderDate, TotalAmount, Status
FROM dbo.Orders
WHERE CustomerId = @cust AND OrderDate >= '2026-07-01'
ORDER BY TotalAmount DESC;

-- 覆盖索引：等值列在前、范围列在后，SELECT/ORDER BY 相关列进 INCLUDE
CREATE NONCLUSTERED INDEX IX_Orders_Customer_Date
  ON dbo.Orders (CustomerId, OrderDate)
  INCLUDE (TotalAmount, Status)
  WITH (FILLFACTOR = 90, ONLINE = ON);   -- ONLINE = ON 只有 Enterprise 支持

执行计划怎么读

  • SSMS 里 Ctrl + M 实际执行计划、Ctrl + L 预估计划；数据流向是从右往左、从下往上。箭头上挂着"预估行数"，和实际行数差一个数量级，说明统计信息过期或估算模型选错，后面必然跟着烂计划。
算子含义与关注点
Clustered Index Seek / Scan在聚集索引上定位/扫描。Seek 好、Scan 要看返回行数
Key Lookup / RID Lookup回表拿未覆盖列。高并发下每次回表都是一次随机 IO，出现它就该考虑覆盖索引
Nested Loops嵌套循环。外表小、内表有索引时最优
Hash Match哈希连接/聚合。大表 join 无索引时的主力，吃内存
Merge Join归并连接。两边都有序时高效
Sort / Stream Aggregate排序与流式聚合，看有没有溢出到磁盘（tempdb 压力）
Parallelism / Gather Streams并行与汇总。OLTP 高并发系统里频繁并行是灾难
Implicit Conversion（警告）隐式转换让索引失效，最常见的写法是把字符串传给数字列或混用 N'' 前缀
-- 看真实执行时的 IO 和时间（SQLCMD / SSMS 都能开）
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
SELECT * FROM dbo.Orders WHERE OrderId = 12345;
-- 关注 logical reads：同一个查询逻辑读从 5000 降到 50，就是索引在起作用
-- 隐式转换是索引第一杀手：NVARCHAR 参数查 VARCHAR 列，计划里出现
-- CONVERT_IMPLICIT，索引直接报废。统一参数类型，别混 N'' 前缀

统计信息：SQL Server 的"计划灵魂"

-- 手动全量更新某表的统计信息（大表定期做，别等 20% 阈值）
UPDATE STATISTICS dbo.Orders WITH FULLSCAN;

-- 看直方图（评估某值的选择性估算准不准）
DBCC SHOW_STATISTICS (dbo.Orders, IX_Orders_Customer_Date);

-- 开启异步自动更新：统计信息更新不阻塞查询（2016 之前没有）
ALTER DATABASE MyDB SET AUTO_UPDATE_STATISTICS_ASYNC ON;
参数嗅探（parameter sniffing）是 SQL Server 的著名坑：存储过程第一次执行时按传入参数生成计划并缓存，之后所有参数复用这个计划。参数 A 生成索引 Seek、参数 B 需要全表 Scan，缓存不改，计划就时快时慢。处理三件套：OPTION (RECOMPILE)（每次编译，小查询可用）、OPTION (OPTIMIZE FOR (@p UNKNOWN))、或用 Query Store 强制一个好计划。
模块 3

锁、阻塞与行版本控制

SQL Server 默认悲观并发：读也要加锁。扛不住并发时，开行版本控制（RCSI）是最有效的改造。

锁的层级与模式

层级粒度从粗到细：数据库 → 表 → 页 → 行。锁粒度越细并发越高，但锁管理开销越大
S / X / U共享 / 排他 / 更新（先 S 后 X，用于先读后写，减少死锁）
IS / IX / SIX意向锁。在表级声明"我下面的行加了 S/X"，让表锁和行锁能快速判断冲突
Sch-S / Sch-M架构锁。查询编译 / DDL 改表结构时持有，DDL 会阻塞所有访问

行版本控制：RCSI 与快照隔离

特性READ COMMITTED SNAPSHOT (RCI)SNAPSHOT ISOLATION
开启方式ALTER DATABASE db SET READ_COMMITTED_SNAPSHOT ONALTER DATABASE db SET ALLOW_SNAPSHOT_ISOLATION ON
一致性级别语句级：每条语句看到自己开始时的快照事务级：整个事务看到同一个快照
对写冲突写仍然用锁，写之间互斥不变乐观并发：提交时发现被别人改过直接报错（错误码 3960）
版本存储都存在 tempdb，每行版本约 14 字节额外开销；长事务/长查询会阻止版本清理，把 tempdb 撑爆
-- 开启 RCI（需要短暂独占数据库，有活动会话时会卡住，低峰期做）
ALTER DATABASE MyDB SET READ_COMMITTED_SNAPSHOT ON;

-- 查谁在阻塞谁（替代 sp_who2 的精确版）
SELECT r.session_id, r.blocking_session_id, r.wait_type, r.wait_time, r.wait_resource,
       s.login_name, s.host_name, s.program_name, st.text
FROM sys.dm_exec_requests r
JOIN sys.dm_exec_sessions s ON s.session_id = r.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
WHERE r.blocking_session_id <> 0;

-- 会话级设置锁超时和死锁优先级（应用层建议都配上）
SET LOCK_TIMEOUT 5000;        -- 5 秒等不到锁就报错，别无限等
SET DEADLOCK_PRIORITY LOW;   -- 被当牺牲品时优先牺牲我

-- 死锁的扩展事件捕获（system_health 默认会话已经在记，但自己建更可控）
CREATE EVENT SESSION [CaptureDeadlocks] ON SERVER
ADD EVENT sqlserver.xml_deadlock_report
ADD TARGET package0.event_file (SET filename = N'C:\XEvents\deadlocks.xel');
ALTER EVENT SESSION [CaptureDeadlocks] ON SERVER STATE = START;
死锁只会留下错误 1205，然后杀掉一个会话。数据库不会重试，重试必须应用层做：捕获 1205（和 -2 超时、-3 连接断开）后按指数退避重试 2~3 次。
老手段 Trace Flag 1222 / 1204 可以把死锁图写进错误日志；现代做法是直接用上面的 xml_deadlock_report 扩展事件，能拿到完整的进程/资源等待图。
锁升级：单条语句在同一对象上持有的锁超过约 5000 个时，会自动升级到表级锁。批量更新/删除几十万行时，升级成表锁会阻断所有并发读。解法：分批做（每次几千行）、降低批次内行数。
模块 4

常用系统视图（DMV）

DMV（Dynamic Management Views）是 SQL Server 排查问题的核心武器库。所有计数器自实例启动累计，跨重启对比没有意义。

类别常用 DMV看什么
SQL 执行sys.dm_exec_query_stats
sys.dm_exec_sql_text
sys.dm_exec_query_plan		每个计划的执行次数、总/平均耗时、逻辑读、计划 XML
当前请求sys.dm_exec_requests
sys.dm_exec_sessions		正在跑什么、谁在阻塞、等待什么
等待统计sys.dm_os_wait_stats
sys.dm_os_waiting_tasks		系统整体在等什么，定位瓶颈类型
索引健康sys.dm_db_index_physical_stats
sys.dm_db_index_usage_stats		碎片率、页数、索引被用了多少次（没人读的索引就该删）
缺失索引sys.dm_db_missing_index_details优化器建议但还不存在的索引（要人工甄别，别全建）
锁与事务sys.dm_tran_locks

-- 找最烧时间的 20 条 SQL（排障第一查询）
SELECT TOP 20
    qs.total_elapsed_time / qs.execution_count / 1000.0 AS avg_elapsed_ms,
    qs.execution_count,
    qs.total_logical_reads / qs.execution_count AS avg_logical_reads,
    SUBSTRING(st.text, (qs.statement_start_offset / 26) + 1,
        ((CASE qs.statement_end_offset
              WHEN -1 THEN DATALENGTH(st.text)
              ELSE qs.statement_end_offset END - qs.statement_start_offset) / 26) + 1) AS sql_text,
    qp.query_plan
FROM sys.dm_exec_query_stats qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) st
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) qp
ORDER BY qs.total_elapsed_time DESC;
-- 注：statement_start_offset 单位是字节，Unicode 字符占 2 字节，所以要 /26 换算偏移

-- 系统在等什么（排除后台噪声后的等待统计）
SELECT wait_type, wait_time_ms / 1000.0 AS wait_sec, waiting_tasks_count
FROM sys.dm_os_wait_stats
WHERE wait_time_ms > 0
  AND wait_type NOT LIKE '%SLEEP%'
  AND wait_type NOT LIKE '%QUEUE%'
  AND wait_type NOT LIKE '%BACKGROUND%'
ORDER BY wait_sec DESC;

-- 只写没人读的索引（每个索引都有维护成本，删之）
SELECT OBJECT_NAME(ius.object_id) AS table_name, si.name AS index_name,
       ius.user_seeks, ius.user_scans, ius.user_lookups, ius.user_updates
FROM sys.dm_db_index_usage_stats ius
JOIN sys.indexes si ON si.object_id = ius.object_id AND si.index_id = ius.index_id
WHERE ius.database_id = DB_ID(N'MyDB') AND ius.object_id > 100
  AND ius.user_seeks + ius.user_scans + ius.user_lookups = 0
  AND ius.user_updates > 0
ORDER BY ius.user_updates DESC;
缺失索引 DMV 的建议不能照单全收。它只按"预估收益"排序，不知道你的写入压力和已有索引，很容易建出一堆重复索引。正确姿势：拿建议当线索，合并去重后手工定稿，并在测试环境验证执行计划确实变好。
模块 5

Always On 可用性组（AG）

SQL Server 高可用的主力方案。AG 在数据库级工作：一个可用性组包含若干数据库，每个库在多个副本间同步。

概念说明
主副本 / 辅助副本主副本可读写，辅助副本默认只读（需显式开可读 + 读意向路由）。一个 AG 只有一个主副本
同步 / 异步同步：主库等副本确认才提交（延迟换安全）；异步：不等（性能换可能丢数据）
故障转移模式自动故障转移 = 同步 + 自动模式 + 健康检测；手动计划内 / 强制（有数据丢失风险）
侦听器（Listener）AG 的虚拟网络名，客户端连它，故障转移时 VIP/DNS 跟着走。多子网场景依赖 DNS 更新
WSFCAG 默认依赖 Windows 故障转移集群做仲裁和健康检测（多数节点/文件共享见证防脑裂）

高可用方案选型

方案粒度适用场景局限
Always On AG数据库级高可用 + 读写分离 + 异地灾备Enterprise 才支持多副本多库；Basic AG（2016+ Standard）限制多
故障转移集群 FCI实例级整实例高可用，包括系统库、登录名、Agent 作业共享存储，存储是单点；故障时全部库一起切
日志传送数据库级便宜的灾备，可延迟应用（防逻辑误删）无自动故障转移，切换要手工，延迟分钟级
复制对象级报表分发、跨库数据分发不是高可用方案，延迟和冲突管理复杂
-- AG 同步状态一眼看（排障必查）
SELECT ar.replica_server_name, ar.availability_mode_desc, ar.failover_mode_desc,
       drs.synchronization_state_desc, drs.is_primary_replica,
       drs.log_send_queue_size, drs.redo_queue_size, drs.last_commit_time
FROM sys.dm_hadr_database_replica_states drs
JOIN sys.availability_replicas ar ON ar.replica_id = drs.replica_id;

-- 把库加入辅助副本：先 NORECOVERY 还原备份，再执行
ALTER DATABASE MyDB SET HADR AVAILABILITY GROUP = [MyAG];

-- 计划内切换到辅助副本（无数据丢失，先确认同步状态是 SYNCHRONIZED）
ALTER AVAILABILITY GROUP MyAG FAILOVER;

-- 强制故障转移（主副本全挂时，可能丢数据）
ALTER AVAILABILITY GROUP MyAG FORCE_FAILOVER_ALLOW_DATA_LOSS;
读辅助副本前想清楚两件事：① 同步副本的"零丢失"只到提交确认那一刻，提交延迟会增加（通常几毫秒到几十毫秒，跨地域另说）；② 辅助副本可读依赖行版本控制，要在辅助库上开快照隔离，否则读操作会和重做（redo apply）互相阻塞。
同步挂起排查套路：先看 synchronization_state_desc 是不是 SYNCHRONIZED；再看 log_send_queue_size（主库发送侧堆积 → 网络或副本不可达）和 redo_queue_size（副本重做堆积 → 副本负载高或长查询阻塞重做）。对症处理。
模块 6

SQL Server Agent 作业

Agent 是 SQL Server 自带的调度器，概念和 Linux cron 一一对应：作业 = 计划任务，步骤 = 命令，计划 = 触发规则。

概念说明
作业 Job由一个或多个步骤组成，可按步骤设置成功/失败流向（on success / on failure 跳转）
步骤子系统T-SQL、CmdExec、PowerShell、SSIS、Analysis Services 命令、复制任务等
计划 Schedule一次性 / 每天 / 每周 / 每月，可带起止时间和启用状态
操作员 Operator通知对象（邮件/寻呼/net send），依赖 Database Mail 发信
代理帐户 Proxy给非 sysadmin 用户跑 CmdExec/SSIS 等子系统的安全上下文
USE msdb;

-- 每晚 02:30 的索引维护作业（碎片 > 30% 重建，5%~30% 重组）
EXEC dbo.sp_add_job @job_name = N'NightlyIndexMaintenance';

EXEC dbo.sp_add_jobstep
    @job_name = N'NightlyIndexMaintenance',

性能调优常用手段

套路永远是五步：量化（监控）→ 定位（DMV/等待统计）→ 假设 → 优化（最小改动）→ 验证（前后对比）。跳过前两步直接加索引，大概率是帮倒忙。

常见等待类型速查

等待类型含义典型原因与处理
PAGEIOLATCH_SH / _DT等 buffer pool 未命中的页从磁盘读入内存不足或查询扫了不该扫的表。加索引/加内存/改写 SQL
SOS_SCHEDULER_YIELDCPU 上主动让出，量大 = CPU 饱和编译/执行吃满 CPU，看 Top SQL 找最耗 CPU 的语句
CXPACKET并行线程之间互相等待并行度太高或倾斜。降 MAXDOP、调并行阈值，别一刀切禁并行
LCK_M_*等锁长事务、锁升级、缺失索引导致锁范围大。查阻塞链
WRITELOG / LOGBUFFER等日志落盘提交太密集或日志盘慢。合并事务、换 SSD、检查 VLF 碎片
RESOURCE_SEMAPHORE等查询内存授予并发大查询太多。限制并发、降大查询内存、加内存
ASYNC_NETWORK_IO等客户端慢慢取结果应用层一次拉太多行（SELECT * 没分页）

模块 8

十个线上坑

1
不设 max server memory
SQL Server 默认能吃多少吃多少，OS 内存被榨干后 RDP 都进不去。32G 机器实例留 24G 左右，并评估 LPIM。
2
参数嗅探导致计划时快时慢
同一存储过程不同参数走缓存计划，性能忽高忽低。对不稳定的参数用 OPTION (RECOMPILE) 或 OPTIMIZE FOR UNKNOWN，或用 Query Store 强制计划。
3
隐式转换让索引全废
NVARCHAR 参数查 VARCHAR 列（或反之）、数字列和字符串比较，执行计划里出现 CONVERT_IMPLICIT，索引直接变扫描。统一参数类型。
4
SELECT NOLOCK 用于对账和统计
脏读之外还会因页拆分读到重复行/丢行，数字永远对不上且难复现。要无阻塞读请开 READ_COMMITTED_SNAPSHOT。
5
Key Lookup 泛滥不当回事
非覆盖索引每行回一次表，高并发下随机 IO 打满磁盘。把 SELECT 列表常用列 INCLUDE 进索引叶级。
6
大表统计信息常年不更新
自动更新的 20% 阈值对千万级大表几乎不触发，基数估算越来越离谱，计划某天突然走全表扫描。大表定期 UPDATE STATISTICS WITH FULLSCAN，并开异步更新。
7
开了 RCI 但没人管 tempdb
版本存储被长事务/长查询堵住清理，tempdb 疯长甚至把磁盘写满。监控 sys.dm_tran_top_version_generators，控制事务时长，tempdb 按官方建议配置多文件。
8
死锁不重试、不抓现场
死锁报 1205 就 500 给用户。应用层要捕获 1205/-2/-3 指数退避重试；服务端开 xml_deadlock_report 扩展事件留证据。
9
批量更新触发表级锁升级
一条 UPDATE/DELETE 动几十万行，锁数超阈值升级成表锁，全库卡住。按批次（每批几千行）处理，避开高峰。
10
Full 恢复模式却从不备份日志
日志文件无限增长直到撑爆磁盘，且"最近一次全备"永远追不上。Full/Bulk-logged 模式必须配日志备份，否则改 Simple。
自测

六道题

1. SQL Server 中"聚集索引"的叶级存的是什么？
正确答案：数据行本身。聚集索引的叶级就是表数据，所以一张表只能有一个聚集索引。非聚集索引的叶级才存书签：有聚集索引时存聚集键，堆表存 RID。MySQL InnoDB 同理，但 SQL Server 的表还可以是堆（heap，完全无序存储）。
2. 想让查询完全不回表，应该用哪种索引特性？
正确答案：INCLUDE 包含列。把 SELECT 列表用到的非键列挂到非聚集索引叶级，查询只读索引就能拿到全部列，消除 Key Lookup。MySQL 没有 INCLUDE 语法，只能把列全部写进键里，会影响键长和排序效率。
3. 排查"最耗时的 SQL"，首选哪个 DMV？
正确答案：sys.dm_exec_query_stats。它缓存了每个已执行计划的执行次数、总耗时、逻辑读、物理读，配合 sys.dm_exec_sql_text 和 sys.dm_exec_query_plan 两个表值函数就能拿到 SQL 文本和执行计划。注意计数器自实例重启累计。
4. 开启 READ_COMMITTED_SNAPSHOT 后，行版本数据存放在哪里？
正确答案：tempdb。行版本（每行约 14 字节额外开销）统一放在 tempdb 的版本存储里，这也是为什么长事务/长查询会撑爆 tempdb —— 旧版本被堵着不能清理。RCI 让读不阻塞写，但写之间仍然互斥。
5. 死锁发生时，以下哪种做法是正确的？
正确答案：抓 1205 重试 + xml_deadlock_report 抓现场。数据库只会杀掉代价较低的牺牲品（可用 SET DEADLOCK_PRIORITY 调整），不会替你重试。加大超时对死锁无效，SERIALIZABLE 反而增加死锁概率。
6. 关于 Always On 可用性组的自动故障转移，必要条件是哪组？
正确答案：同步副本 + 自动模式 + WSFC 健康。异步副本默认只支持手动强制故障转移（可能丢数据）。此外自动故障转移面向的是"副本故障"，主库整体宕机时切换也需要集群仲裁正常、辅助副本已同步（SYNCHRONIZED）。
