模块 1

文档模型与 BSON

MongoDB 存的是 BSON（Binary JSON）——在 JSON 的类型基础上加了 Date、ObjectId、Decimal128、二进制等类型。理解 BSON 比理解 SQL 建表更重要，因为所有坑的根源都是"文档"这个粒度。

BSON 类型对应 JSON注意点
StringstringUTF-8
Int32 / Int64numbershell 里的数字默认是 double，大整数必须用 NumberLong()，否则丢精度
Doublenumber不能用来存金额，0.1+0.2 ≠ 0.3
Decimal128无128 位十进制浮点，金额的正确选择
ObjectId无12 字节：4 字节时间戳 + 5 字节机器/进程随机值 + 3 字节自增计数器。大致有序但同一秒内不保证全局单调
Date无UTC 毫秒时间戳。没有时区信息，展示层自己转
Arrayarray可嵌套文档，元素可以是不同类型
Embedded Docobject子文档。更新语义见下文

核心限制：单文档 16MB

这是 MongoDB 最著名的硬限制。设计文档时心里要一直绷着这根弦：任何内嵌数组都可能长到 16MB。超限时报错 BSONObjectTooLarge，只能重构数据模型。

# 16MB 换算成现实：约 1000 万个小整数，或几万个含 5 个字段的子文档
# 一旦评论数组设计成内嵌，热帖迟早撑爆
db.posts.insertOne({
  title: "热帖",
  comments: [ /* ... 无界增长，最终 16MB 爆炸 ... */ ]
})

文档更新语义

WiredTiger 存储引擎用 MVCC：更新文档不是原地改字节，而是写一个新版本。推论：文档越小、更新越局部（用 $set 改单个字段而不是 replaceOne 整篇替换），写放大越小。大文档频繁更新是性能头号杀手。

db.users.updateOne({ _id: 1 }, { $set: { "profile.city": "上海" } })   # 只改嵌套字段，好
db.users.replaceOne({ _id: 1 }, { name: "x", age: 30, ... })            # 整篇替换，重写整个文档，差

schema 校验（3.6+）

# "无模式"是误解——集合级可以强约束结构
db.createCollection("orders", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["userId", "amount", "status"],
      properties: {
        userId:    { bsonType: "objectId" },
        amount:    { bsonType: ["decimal"], minimum: 0 },
        status:    { enum: ["PENDING", "PAID", "SHIPPED"] },
        createdAt: { bsonType: "date" }
      }
    }
  },
  validationLevel: "moderate"   # strict=全部文档强制；moderate=只校验新增/修改的
})
最佳实践：给所有生产集合加 validationLevel: moderate 的 validator。它几乎零成本，却能挡住"手滑写错字段名"和"状态值乱写"这两类最常见的数据污染。
模块 2

复制集、选举与一致性语义

复制集（Replica Set）是 MongoDB 高可用的最小单位，也是分片集群里每个 shard 的底层形态。读写关注（writeConcern / readConcern）的组合语义是本文档最值得背下来的一张表。

架构与角色

角色职责要点
Primary唯一写入口，所有写操作在这里执行，产生 oplog一个时刻只有一个。挂掉后触发选举
Secondary异步拉取并重放 primary 的 oplog默认可读（readPreference 控制）。同步有延迟
Arbiter只投票不存数据凑奇数节点用。生产环境已不推荐（不如用隐藏的轻量 secondary）

oplog 是一个有上限的集合（capped collection），记录每个写操作。secondary 落后太多（超过 oplog 窗口）就再也追不上，只能全量重同步。

选举机制

MongoDB 用 类 Raft 的共识协议：成员间默认约 2 秒一次心跳，10 秒收不到就认为对方失联；失联节点发起选举，需要大多数（majority）成员投票才能成为 primary。3 节点集群容忍 1 挂，5 节点容忍 2 挂。选举通常 12 秒内完成（选举超时 10s + 心跳间隔）。

为什么是奇数节点：因为选举要"大多数投票"。4 节点的大多数是 3（容忍 1 挂），5 节点的大多数也是 3（容忍 1 挂，但能再容忍 1 个投票成员故障）。3 个数据节点是生产最低配，2 节点 + 1 arbiter 的写法过时了。

writeConcern：写到几个副本算成功

写法语义
w: 0发出去就不管，不确认、可能丢。只适合日志类
w: 1默认值。primary 收到即返回，未等 secondary 同步。primary 挂可能回滚
w: "majority"等大多数数据节点确认。生产标配
j: true额外要求副本写入 journal（预写日志）才确认。默认 journal 刷盘间隔约 100ms，j: true 保证进程崩溃不丢
wtimeout: 5000等副本确认的超时，超时返回错误。防止"卡死等一个失联副本"

readConcern：读哪个版本的数据

级别语义
local默认值。读本节点最新数据，不管别的副本是否跟上。可能读到即将回滚的数据
majority只读"已被大多数副本确认"的数据。与 w: majority 配合 = 不会读到会被回滚的旧值
linearizable线性一致读：读之前先等本节点追上 majority 的写入点。最慢，但保证读到"最新已确认写"
snapshot快照读（配合事务/因果会话使用）
available分片集群下类似 local 的宽松版

组合语义（背这张表）

组合结果
w:1 + readConcern: local默认组合。最快，但主从切换可能丢刚"确认"的写，也可能读到旧值
w:majority + rc:local写不丢，但可能读到未来会被回滚的数据（旧值）
w:majority + rc:majority推荐组合。写已同步到多数，读只读已同步的，无回滚风险、读写一致
w:majority + rc:linearizable最强读。用于"写完必须立刻读到"的场景（如支付后查余额）
w:majority + j:true再进一步：副本确认前先落 journal，防进程崩溃
# 在 mongosh 里怎么用
db.orders.insertOne(
  { userId: ObjectId("65f..."), amount: NumberDecimal("99.50") },
  { writeConcern: { w: "majority", j: true, wtimeout: 5000 } }
)

db.orders.find({ status: "PAID" }).readConcern("majority")

# 客户端会话级默认（推荐，一次设置全局生效）
# Java: MongoClientSettings.writeConcern(MAJORITY).readConcern(MAJORITY)

回滚（rollback）

primary 挂了但还有未同步到 secondary 的写入，新 primary 选举产生后，老 primary 恢复时会发现自己有一段"多余"的操作，MongoDB 把这些操作原样保存到 rollback 目录（.bson 文件）而不是自动重放——需要人工或用 mongorestore 决策。用 w: majority 可以从根上避免回滚。

绝大多数"数据丢了"的工单，根因都是默认的 w:1 + readConcern: local。关键业务（订单、支付、库存）的客户端连接串请显式设置 majority，别依赖默认值。
模块 3

分片集群架构与分片键

数据量大到单机放不下、或写吞吐超过单机时，就要分片。分片集群 90% 的灾难来自分片键选错，而分片键在 5.0 之前几乎不可改。

三个组件

组件职责要点
mongos无状态路由。客户端连它，它把请求转发到对应 shard 并聚合结果可以部署多个。本身不存数据，挂了不影响数据安全
Config Server存元数据：哪个 chunk 在哪个 shard、分片键范围、集群配置必须是复制集（3 节点）。挂了集群元数据就不可写
Shard每个 shard 本身是一个复制集，存一部分数据可以是单节点（开发）或复制集（生产）

分片键：选错即灾难

类型行为评价
范围分片按分片键值切连续区间（如日期 2026-01 ~ 2026-03）支持范围查询高效路由；单调递增键（时间戳、自增 ID）会让所有写打向最后一个 chunk
哈希分片对键值取哈希后打散写入均匀，但范围查询要广播到所有 shard
复合键如 { region: 1, _id: 1 }，前面是范围后面保证基数兼顾局部性与打散
Zone / Tag把某些键范围绑定到特定 shard用于"热点数据放好机器"、"就近读写"
# 开启分片并指定分片键
sh.enableSharding("shop")

# 哈希分片：写入均匀，日志/流水类集合首选
sh.shardCollection("shop.orders", { userId: "hashed" })

# 范围分片：适合有明显时间范围且查询带时间条件的场景
# 注意单调递增键的风险：写入全落在"当前 chunk"，形成单点热点
sh.shardCollection("shop.events", { tenantId: 1, createdAt: 1 })

# 查看分片状态与数据分布
sh.status()
db.orders.getShardDistribution()      # 每个 shard 有多少文档、多大

chunk 与均衡器

数据按分片键切成 chunk（默认 128MB，可调 1~1024MB）。chunk 在 shard 间分布不均超过阈值（约 chunkSize 的 3 倍）时，balancer 自动迁移 chunk。迁移是后台进行的，有带宽和 IO 限制。

# 手动切分与迁移（紧急打散热点时用）
sh.splitAt("shop.orders", { userId: NumberLong("500000000000000000000000") })
sh.moveChunk("shop.orders", { userId: 100 }, "shard0002")

# jumbo chunk：太大无法迁移的 chunk（超过 128MB 或含过多文档）
# 出现 jumbo 说明分片键基数太低（如只有 true/false 两个值的字段），必须换键
分片键不可变性（核心认知）：MongoDB 5.0 之前，分片键一旦选定就不能改——选错只能导出数据、建新集合、按新键分片、切换流量，俗称"洗数据"。5.0+ 提供了 reshardCollection 命令可以改键，但底层同样是重建索引+迁移数据，代价巨大且要求业务配合。选键前用真实数据分布做压测，别拍脑袋。

选键四条军规：① 基数要足够大（避免 jumbo chunk）；② 写入不能单调（避免热点）；③ 尽量覆盖高频查询条件（避免广播）；④ 提前想清楚——这是最难反悔的一个决定。
模块 4

索引：类型、规则与 explain

MongoDB 的索引是 B-Tree，用法和 MySQL 很像，但多几种特有类型。没有索引的查询 = 全表扫描，在千万级集合上就是事故。

类型创建方式适用与陷阱
单字段createIndex({price:1})最常用。1 升序 -1 降序
复合createIndex({category:1,price:-1})遵循 ESR 规则（见下）
Multikey对数组字段自动生效对数组每个元素建索引项。两个数组字段的复合索引会爆炸（笛卡尔积）
唯一{unique:true}并发下保证唯一的唯一手段，比应用层查重可靠
稀疏{sparse:true}只索引存在该字段的文档
TTL{expireAfterSeconds:3600}字段必须是 Date。过期删除是后台任务，不保证精确到秒
文本createIndex({content:"text"})每个集合只能有一个文本索引，支持多语言分词
地理空间createIndex({loc:"2dsphere"})GeoJSON 点/线/面查询，附近的人
哈希createIndex({_id:"hashed"})只能用于分片键，打散写入
部分partialFilterExpression只索引部分文档，省空间
# 常用索引创建
db.products.createIndex({ price: 1 })                                   # 单字段
db.products.createIndex({ category: 1, price: -1 })                     # 复合：先类别后价格
db.products.createIndex({ tags: 1 })                                    # 数组 → multikey
db.users.createIndex({ email: 1 }, { unique: true })                    # 唯一索引
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 3600 }) # TTL：1 小时后自动删
db.articles.createIndex({ title: "text", body: "text" }, { weights: { title: 3 } })  # 全文检索，标题权重 3 倍
db.places.createIndex({ location: "2dsphere" })                            # 地理位置
db.orders.createIndex({ status: 1 }, { partialFilterExpression: { status: "PENDING" } })  # 部分索引：只为待处理订单建索引

# 管理
db.products.getIndexes()
db.products.dropIndex({ price: 1 })
db.products.totalIndexSize()          # 索引总大小

# 全文检索查询（集合只能有一个 text 索引）
db.articles.find({ $text: { $search: "机械键盘 评测" } }, { score: { $meta: "textScore" } })
          .sort({ score: { $meta: "textScore" } })

# 地理查询：找 5 公里内的店
db.places.find({
  location: {
    $near: {
      $geometry: { type: "Point", coordinates: [116.40, 39.90] },
      $maxDistance: 5000
    }
  }
})

ESR 规则（复合索引设计第一定律）

复合索引字段顺序按 Equality（等值匹配）→ Sort（排序）→ Range（范围匹配） 排列。违反它，索引要么用不上，要么排序阶段要额外排。

# 查询：状态等值 + 按创建时间排序 + 金额范围
db.orders.find({ status: "PAID", amount: { $gt: 100 } }).sort({ createdAt: -1 })

# 正确索引：等值在前，排序在中，范围在最后
db.orders.createIndex({ status: 1, createdAt: -1, amount: 1 })
# ✗ 错误：{amount:1, status:1, createdAt:-1} —— 范围字段放最前，后面的排序和等值都低效

explain：判断索引有没有用上

db.orders.find({ status: "PAID" }).sort({ createdAt: -1 })
        .explain("executionStats")

# 关键字段：
#   stage: "IXSCAN"  = 用了索引扫描（好）
#   stage: "COLLSCAN" = 全表扫描（必须优化）
#   stage: "SORT" + sortPattern... 用了内存排序（索引没覆盖排序，注意 32MB 排序上限）
#   docsExamined / nReturned：相差几百倍说明索引选择性差
#   executionSuccess:false + errorMessage：比如排序超限报 "Sort exceeded memory limit"
覆盖查询（Covered Query）：查询的字段和投影全部在索引里，MongoDB 就完全不读文档，只扫索引。{name:1, price:1} 索引上查 find({name:"x"},{name:1,price:1,_id:0}) 就是覆盖查询。explain 里 totalDocsExamined: 0 即为覆盖。高频查询优先设计成覆盖查询。
模块 5

聚合管道：从查数据到算数据

聚合管道（Aggregation Pipeline）是 MongoDB 的"SQL 查询编译器"：文档依次流过一个个 stage，每个 stage 做变换。它比 find 强大得多，但也更容易把内存跑爆。

高频 stage

Stage作用
$match过滤文档。越早放越好（后面 stage 处理的文档更少）
$project投影/重塑字段，支持计算新字段
$group分组聚合，_id 是分组键，支持 $sum/$avg/$max/$push 等累加器
$sort / $limit / $skip排序与分页。skip 大偏移量性能差，用范围条件翻页
$lookup左外连接另一集合（等值连接）
$unwind把数组字段拆成多行文档
$facet同一份输入并行跑多个子管道，一次返回多种聚合结果
$bucket按数值区间分桶统计
$merge / $out结果写回集合（$out 覆盖目标集合）
# 典型：统计每个城市的订单总额 Top10
db.orders.aggregate([
  { $match: { status: "PAID", createdAt: { $gte: ISODate("2026-01-01") } } },  # ① 尽早过滤
  { $lookup: {                                                              # ② 连接用户表拿城市
      from: "users",
      localField: "userId",
      foreignField: "_id",
      as: "user"
  } },
  { $unwind: "$user" },                                                      # ③ 数组拆成单文档
  { $group: {                                                               # ④ 按城市分组
      _id: "$user.city",
      totalAmount: { $sum: "$amount" },
      orderCount:  { $sum: 1 },
      avgAmount:   { $avg: "$amount" }
  } },
  { $sort: { totalAmount: -1 } },                                           # ⑤ 按总额降序
  { $limit: 10 }
])

# $lookup 高级用法（3.6+）：带 let/pipeline 的条件连接
db.orders.aggregate([
  { $match: { status: "PAID" } },
  { $lookup: {
      from: "users",
      let: { uid: "$userId" },
      pipeline: [
        { $match: { $expr: { $eq: ["$_id", "$$uid"] } } },
        { $project: { name: 1, level: 1, _id: 0 } }
      ],
      as: "user"
  } }
])
# $facet：一次请求返回多个维度的统计（商品列表页的筛选条）
db.products.aggregate([
  { $match: { category: "外设" } },
  { $facet: {
      byBrand: [                                                  // 按品牌分组的数量
        { $group: { _id: "$brand", count: { $sum: 1 } } },
        { $sort: { count: -1 } }
      ],
      priceBuckets: [                                             // 价格区间分布
        { $bucket: {
            groupBy: "$price",
            boundaries: [0, 100, 500, 1000, 5000],
            default: "5000+",
            output: { count: { $sum: 1 } }
        } }
      ],
      topRated: [                                                 // 评分最高的 5 个
        { $sort: { rating: -1 } },
        { $limit: 5 },
        { $project: { name: 1, rating: 1, _id: 0 } }
      ]
  } }
], { allowDiskUse: true })     # facet 结果放不进内存时必须开这个
100MB 内存限制：聚合管道的每个 stage 默认最多用 100MB 内存（$group 遇到大基数、$sort 遇到大数据量时最容易触发），超了直接报错：
Executor error: Exceeded memory limit for $group ... 104857600 bytes
两个解法：① 给 $match 加索引、让 $group 前数据更少（治本）；② 加 { allowDiskUse: true }，把中间结果落临时磁盘文件（治标，注意临时目录 dbpath 的空间）。生产环境建议给聚合接口加 explain 预检，别等报错。
模块 6

模式设计：嵌入还是引用

这是 MongoDB 数据建模唯一的核心问题。判断标准不是"关系范式"，而是数据怎么被访问。

策略什么时候用代价
内嵌（Embed）子数据一定随父文档一起被读取、数量有界（如订单里的收货地址、商品规格）文档变大；数组无界增长会撞 16MB
引用（Reference）子数据单独被查询、数量无界（用户的所有订单）、多父文档共享（标签）查询要 $lookup 或多次 find
反范式化为省一次 join，把常用字段冗余到另一份文档（如订单里存 userNickname）更新要应用层同步维护多处，可能不一致
桶模式大量小文档按时序/维度装桶（如每小时一条的指标装进"天"文档）访问要定位桶；桶内也要防溢出
计算模式写入时预聚合（如每次更新顺手维护 totalViews 字段）写变复杂，读极快

大数组的正确形态：桶模式

# ✗ 反例：评论内嵌进帖子，热帖迟早 16MB 爆炸
{ _id: post1, title: "...", comments: [ /* 10 万条 */ ] }

# ✓ 方案 A：评论独立集合 + 引用（无界数据的标准解）
{ _id: comment1, postId: post1, author: "u1", text: "...", createdAt: ISODate(...) }
db.comments.createIndex({ postId: 1, createdAt: -1 })   # 查帖子的评论走这个索引

# ✓ 方案 B：桶模式（适合时序/流水，读最近 N 条极快）
{ _id: "sensor7:2026-10-17", sensorId: 7, date: "2026-10-17",
  count: 1440,                       // 桶内条数，用于判断是否溢出
  measurements: [ {ts: ..., v: ...}, ... ]   // 每 1 分钟一条，一天 1440 条，远小于 16MB
}

反范式化的边界

冗余字段能干掉 $lookup，但更新源字段时必须同步所有副本，这没有数据库帮你做，全靠应用代码。判断标准：这个冗余字段改不改？只读不写的维度信息（如商品下单时的名称快照）适合冗余；会变的状态（如用户昵称）谨慎冗余。

建模三问：① 这份数据主要怎么被读？（决定嵌不嵌）② 会长到多大？（决定要不要分桶/引用）③ 冗余字段谁负责同步？（决定反不反范式）——三个问题都有答案了再动手建集合。
模块 7

十个线上坑

1
以为"无模式"等于不用设计 schema
同一集合里字段名五花八门（name/Name/NAME）、类型混乱（金额有时是 string 有时是 number），查询和索引全废。上线前用 $jsonSchema validator 兜底，至少 validationLevel: moderate。
2
内嵌数组无界增长
评论、消息、流水内嵌进父文档，数据量上来后单文档冲向 16MB，更新越来越慢直到 BSONObjectTooLarge 报错。有界的嵌，无界的引用。
3
分片键选了单调递增字段
用 _id（ObjectId）或 createdAt 直接做范围分片键，所有新写入都打向"当前最大 chunk"，集群退化成单节点写入，且切分后产生大量空 chunk 迁移。单调键用哈希分片，或构造复合键打散。
4
分片键基数太低
用 status（只有几个值）、gender 这种字段做分片键，chunk 少得可怜且无法再切分，形成 jumbo chunk 永远迁不动。分片键基数至少要有几千个不同值。
5
分片键选错想改
5.0 之前分片键完全不可变，选错只能全量导出重建。5.0+ 有 reshardCollection 但代价巨大。选键前用生产真实数据分布验证，别拍脑袋。
6
聚合管道撞 100MB 内存限制
$group 大基数直接报 Exceeded memory limit。解法：$match 加索引前置过滤、$project 减少中间文档宽度、最后手段 allowDiskUse: true（注意临时目录磁盘空间）。
7
复合索引不按 ESR 规则排列
把范围字段放索引最前，导致等值查询和排序都用不满索引，explain 里出现 SORT 阶段甚至 COLLSCAN。记住：Equality → Sort → Range。
8
关键业务用默认读写关注
默认 w:1 + readConcern: local，主从切换时可能丢已"确认"的写、读到会被回滚的数据。订单支付类操作必须 w:majority + readConcern:majority，客户端连接串层统一设置。
9
用应用层查重代替唯一索引
先 find 再 insert，并发下两个请求同时查不到、同时插入，产生重复数据。唯一性必须靠 createIndex({unique:true}) 在数据库层保证，重复键错误码 11000 是可以预期的业务异常。
10
用 double 存金额、用本地时间存 Date
double 存钱 0.1+0.2≠0.3，对账差几分钱；本地时间存进去丢了时区，跨国业务全乱。金额用 Decimal128 或整数分，时间统一存 UTC 的 Date 类型。
自测

六道题

1. 一个帖子的评论设计成内嵌数组，热帖数据量涨到 2000 万条小文档时会怎样？
正确答案：超过 16MB 报错，需重构。16MB 是 BSON 单文档硬限制，超限直接写入失败。评论这类无界数据应该独立成集合 + 引用，或按时间分桶。数组字段加索引（multikey）也救不了体积问题。
2. 想要"写入已同步到大多数副本，且读到的数据一定不会被回滚"，应该用什么组合？
正确答案：w:majority + readConcern:majority。w:majority 保证写已同步到多数副本（不会在选举后回滚）；readConcern:majority 保证只读已同步的数据。默认组合 w:1 + local 在主从切换时既可能丢写也可能读到旧值。
3. 用 createdAt 时间戳字段做范围分片键，最可能出现什么问题？
正确答案：写入热点。单调递增的分片键让所有新数据落在键值最大的一端，集群写入能力被单个 chunk/单 shard 限制。解法是哈希分片或 {tenantId:1, createdAt:1} 这类前置高基数字段的复合键。"广播到所有 shard"是哈希分片键做范围查询的代价。
4. 聚合管道执行 $group 时报 "Exceeded memory limit for $group, 104857600 bytes"，最先该做什么？
正确答案：先减少进入 $group 的数据量。100MB 是单 stage 内存上限。$match 加索引前置过滤、$project 收窄文档宽度都是治本；allowDiskUse 是兜底，且临时文件吃 dbpath 磁盘空间，大并发下可能把磁盘写满。
5. 关于"内嵌 vs 引用"的决策，下列哪个说法正确？
正确答案：看数据量和访问模式。有界 + 一起读的数据（地址、规格）适合内嵌；无界 + 单独查的数据（用户的订单）必须引用。MongoDB 建模的第一性问题不是规范化，而是"这份数据怎么被读、会长到多大"。
6. 保证"用户邮箱全局唯一"最可靠的方式是？
正确答案：数据库层唯一索引。"先查后插"在并发下两个请求会同时查不到、同时插入，产生重复。唯一约束必须在存储层强制，重复键错误（code 11000 / DuplicateKey）是预期内的业务分支，应用正常捕获处理即可。
