模块 1

列式存储：为什么它快

行式数据库按"行"存，一行的所有列挨在一起；列式数据库按"列"存，一列的所有值挨在一起。OLAP 场景 99% 的查询只碰几列，列存就是为这个而生的。

机制说明
列式读取查 5 列就不读其他 95 列，IO 直接少一个数量级。宽表（100+ 列）优势最大
高压缩率同一列数据类型相同、值域接近，LZ4/ZSTD 压缩比通常在 5:1 ~ 20:1。官方常见说法：1TB 行存数据 → 100GB 左右列存
向量化执行不是一行一行算，而是一次处理一"块"（block，约 65,536 行），能吃满 SIMD 指令，单线程吞吐可达 每秒数亿行 级别的简单计算
多核并行每个 part 的分片可以分给不同线程，max_threads 默认取 CPU 核数，单查询天然并行
稀疏索引主键索引不是逐行的，而是每 index_granularity（默认 8192 行）记一个标记，索引可以完全放进内存

代价是什么

弱项说明
点查弱按主键查单行不如 MySQL 直接命中 B+ 树。ClickHouse 适合"扫一批"而不是"点一行"
事务弱没有跨表事务，单条 INSERT 的一个 block 内原子。UPDATE / DELETE 是 mutation，异步重写整个 part
并发弱默认 max_concurrent_queries 100、单查询内存默认上限约 10GB，几百个并发复杂查询就能把机器拖死
定位一句话：ClickHouse 是 OLAP / 日志分析 / 报表 引擎，不是 MySQL 的替代品。选型判断标准很简单：写基本不更新、查询扫大量行只取少量列 —— 用它；频繁单行增删改、强事务 —— 别用它。
模块 2

MergeTree 引擎家族

表引擎决定了数据怎么存、怎么合并。选错引擎是 ClickHouse 最常见的架构级错误，而且后期改引擎要搬数据，代价极大。

MergeTree 本体

CREATE TABLE events (
    event_date Date,
    event_time DateTime,
    user_id    UInt64,
    page       String,
    stay_ms    UInt32
) ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)          # 按月分区
ORDER BY (event_date, user_id)            # 排序键 = 主键 = 稀疏索引依据
SETTINGS index_granularity = 8192;
  • part：每次 INSERT 生成一个 part（物理目录），后台 merge 线程把小 part 合成大 part。所有"合并"都发生在这里
  • ORDER BY 就是排序键，也是主键。它不保证唯一性 —— 同样键的两行可以同时存在，直到某次 merge 才可能去掉重复（取决于引擎）
  • 查询时同键多行都返回，想要去重要么建表时选对引擎，要么查询时自己 GROUP BY

家族成员怎么选

引擎合并时行为适用场景
MergeTree只按排序键归并，不去重不聚合原始流水、日志。不关心重复的默认选择
ReplacingMergeTree排序键相同的行只保留最后写入的一行（可带 version 列定"最后"）需要去重的宽表、CDC 结果表。只在 merge 时去重，不保证实时
SummingMergeTree排序键相同的行，数值列求和后合并简单预聚合：点击量、金额汇总。非聚合列取任意一行的值
AggregatingMergeTree按 AggregateFunction 类型列存储聚合状态（uniq、sumIf 等）复杂预聚合：UV（uniq）、漏斗、多维汇总
CollapsingMergeTreesign=+1/-1 的两行互相抵消，等价于"更新"需要更新历史数据的场景。写两行（新值 +1，旧值 -1）
VersionedCollapsingMergeTree带 version 列，乱序也能正确折叠Collapsing 的乱序安全版本
# ReplacingMergeTree：去重表的标准写法
CREATE TABLE user_profile (
    user_id    UInt64,
    nick       String,
    updated_at DateTime
) ENGINE = ReplacingMergeTree(updated_at)  # version 列：取 updated_at 最大的行
ORDER BY (user_id);

# SummingMergeTree：预聚合表
CREATE TABLE pv_daily (
    stat_date Date,
    page      String,
    pv        UInt64
) ENGINE = SummingMergeTree
ORDER BY (stat_date, page);

# AggregatingMergeTree：UV 统计
CREATE TABLE uv_daily (
    stat_date Date,
    uv_state  AggregateFunction(uniq, UInt64)
) ENGINE = AggregatingMergeTree
ORDER BY (stat_date);
INSERT INTO uv_daily SELECT event_date, uniqState(user_id) FROM events GROUP BY event_date;
ReplacingMergeTree 的头号误区：以为插入了去重数据，查询就查不出来重复。
去重只发生在后台 merge。一条新数据插入后、merge 之前，同样的 key 查出来是两行。查询侧兜底手段：GROUP BY user_id HAVING ... 取一行，或者 FINAL（见模块 7 的代价）。
模块 3

分区与索引

ClickHouse 的索引体系分两层：分区做粗粒度裁剪，稀疏主索引 + 跳数索引做 part 内定位。理解这层的顺序，才能看懂 EXPLAIN。

分区（PARTITION BY）

  • 分区是物理目录：每个分区一个目录，查询时按分区表达式直接跳过无关目录（partition pruning）
  • 典型写法：toYYYYMM(date) 按月、toMonday(date) 按周、tuple() 单分区（小表）
  • 不要用高基数字段做分区键（如 user_id、事件 ID），也不要按天分得太细 —— 分区太多会让 merge 任务碎片化。日志场景按月足够

稀疏主索引

  • 主键索引按 index_granularity（默认 8192 行）为粒度记录"这个 granule 的最小值"，一个 1 亿行的表索引只有约 1.2 万条记录，全放内存
  • 因为稀疏，同一个 granule 内的行不能被索引区分 —— 查单行要读整个 8192 行的 granule。这就是它不适合点查的原因
  • 主键就是 ORDER BY 的前几个字段。把查询过滤最高频的字段放前面，后面的字段只参与排序不参与定位

跳数索引（Skip Index）

主索引之外的第二层。按 part 粒度存储，查询时能跳过整个 granule，对"非主键列的等值/范围过滤"有效：

类型作用示例
minmax记录 granule 内最大最小值，范围查询跳过对 status_code 建 minmax
set(N)记录 granule 内出现过的 N 个值，等值 IN 跳过对 city 建 set(100)
ngrambf_v1对字符串的 n-gram 建布隆过滤器，支持 LIKE 前缀ngrambf_v1(1,3,0,42)
tokenbf_v1对分词后的 token 建布隆过滤器tokenbf_v1(10240,2,0)
bloom_filter对任意列建布隆过滤器，等值跳过bloom_filter GRANULARITY 3
# 建跳数索引的语法
ALTER TABLE events ADD INDEX idx_page set(100) GRANULARITY 4;
ALTER TABLE events MATERIALIZE INDEX idx_page;   # 对已有数据建索引（重操作）

# 验证索引是否被用上
SETTINGS use_skip_indexes = 1;
EXPLAIN indexes = 1
SELECT count() FROM events WHERE page = '/home';

TTL：让数据自己过期

# 表级 TTL：3 个月前的数据自动删分区
) ENGINE = MergeTree
ORDER BY (event_date, user_id)
TTL event_date + INTERVAL 3 MONTH;

# 列级 TTL：过期后把列置默认值而不是删整行
TTL event_date + INTERVAL 7 DAY DELETE WHERE stay_ms = 0;   # 条件 TTL

# TTL 由后台线程按 ttl_interval 检查（默认 4 小时一次）
SHOW server_settings LIKE 'ttl%';
TTL 不是精确到期的：默认 4 小时扫一次，到期数据可能在磁盘上多待半天。不能把 TTL 当合规删除的精确手段，需要精确删还是要走分区 DROP PARTITION（秒级且不产生 IO）。
模块 4

数据导入：批量、乱序与 Exactly-once

ClickHouse 的性能一半靠引擎，一半靠"怎么喂数据"。喂错了，再好的配置也跑不动。

批量是第一生产力

# 正确：一次插入 1 万 ~ 10 万行
INSERT INTO events VALUES
('2026-10-01', '2026-10-01 10:00:00', 1001, '/home', 120),
...                          # 一批至少 1000 行，官方建议 1000 ~ 100000

# 错误示范（每个新手都干过）
INSERT INTO events VALUES (...);   # 循环逐行插 → part 爆炸，merge 永远追不上

# 22.x+ 小插入救星：服务端自动攒批
SET async_insert = 1;                 # 服务端把并发小 INSERT 合成块
SET wait_for_async_insert = 1;        # 等攒批完成再返回，保证读得到

# 从文件直接灌（CSV/TSV/Parquet）
INSERT INTO events SELECT * FROM file('events.tsv', TSV, 'event_date Date, ...');
part 爆炸是 ClickHouse 第一大病：每次 INSERT 生成一个 part，后台 merge 有速率上限。写入速度 > merge 速度时，part 数量滚雪球 —— 查询变慢、Too many parts 报错（parts_to_throw_insert 默认 3000）。规则：保证单分区 part 数维持在三位数以内。用 SELECT partition, count() FROM system.parts GROUP BY partition 日常巡检。

乱序插入问题

  • MergeTree 假设数据大致按主键有序到达。批量插入顺序颠倒的数据时，每个 part 的键范围错乱，merge 时无法"顺序拼接"，只能做更贵的交叉合并
  • 更糟的是跨分区乱序：今天的 INSERT 里混进上个月的数据，会产生大量极小 part，merge 直接崩
  • 工程对策：① 上游按时间分片后按序发送；② 大延迟数据单独一张"迟到表"，定期 INSERT SELECT 归位；③ 批量内先 ORDER BY 再插

Exactly-once：只有 Replicated 表能做到

能力MergeTree（单机）ReplicatedMergeTree
重复 INSERT 同一批数据插几次存几份insert_deduplicate=1 时块级去重
原理无状态，不记录已插入的块块指纹（block id）记录在 ClickHouse Keeper 中，重试/重发同指纹直接跳过
注意该设置对非 Replicated 表完全无效，不会报错，但照样重复22.x 起默认开启；块 id 可由客户端生成保证重试幂等
# 客户端保证幂等的标准姿势：显式指定 insert_deduplication_token（23.x+）
INSERT INTO events SETTINGS insert_deduplication_token = 'batch-uuid-123'
VALUES (...);

# Kafka → ClickHouse：Kafka 引擎表 + 物化视图落库（见模块 5）
# MySQL → ClickHouse：MaterializeMySQL 引擎（CDC 实时，19.x+）

模块 5

物化视图与投影

两个名字都带"预计算"，但机制完全不同。混用它们是经典事故来源。

物化视图（Materialized View）

  • ClickHouse 的 MV 是插入触发器：源表每插入一个 block，触发引擎把 block 按 SELECT 语句变换后写入目标表。不是查询时替换原表的"视图"
  • 目标表必须用聚合引擎（AggregatingMergeTree / SummingMergeTree 等），MV 本身只是管道
  • 只对新数据生效：建 MV 之前的历史数据不会自动回填，要手动 INSERT SELECT 灌一次
  • 查询永远查目标表，源表可以保留也可以 TTL 掉
# 实时 UV 统计：源表 → MV → 聚合表
CREATE TABLE uv_mv (
    stat_date Date,
    uv        AggregateFunction(uniq, UInt64)
) ENGINE = AggregatingMergeTree ORDER BY stat_date;

CREATE MATERIALIZED VIEW uv_view TO uv_mv
AS SELECT
    event_date,
    uniqState(user_id) AS uv
FROM events
GROUP BY event_date;

# 查询时用 uniqMerge 合并状态
SELECT stat_date, uniqMerge(uv) AS uv FROM uv_mv GROUP BY stat_date ORDER BY stat_date;

Kafka 实时管道（MV 的经典组合）

# 1. Kafka 引擎表（只是管道，不存数据）
CREATE TABLE kafka_events (event_date Date, user_id UInt64, page String)
ENGINE = Kafka SETTINGS kafka_broker_list = 'kafka:9092',
    kafka_topic_list = 'events', kafka_group_name = 'ch_consumer',
    kafka_format = 'JSONEachRow';

# 2. 目标表（真正的存储）
CREATE TABLE events (event_date Date, user_id UInt64, page String)
ENGINE = MergeTree ORDER BY (event_date, user_id);

# 3. MV 把 Kafka 数据搬进目标表
CREATE MATERIALIZED VIEW kafka_to_events TO events
AS SELECT * FROM kafka_events;

投影（PROJECTION）

维度物化视图投影
本质独立的管道 + 目标表，数据多存一份同一张表内的附加数据副本（另一份排序/聚合）
查询方式应用显式查目标表透明加速，优化器自动选（可用 SETTINGS optimize_use_projections=0 关闭）
数据一致性与源表最终一致，有延迟与主数据强一致（同一 part 内维护）
代价存储 + 写入翻倍存储 + 写入也翻倍（但无跨表一致性烦恼）
# 投影：给表加一份按 page 聚合的副本，查询按 page 汇总时自动走它
ALTER TABLE events ADD PROJECTION pv_by_page (
    SELECT page, count() AS pv, sum(stay_ms) AS total_ms
    GROUP BY page
);
ALTER TABLE events MATERIALIZE PROJECTION pv_by_page;   # 对已有数据生效
MV 的"只对新数据生效"坑过无数人：晚上 8 点建好 UV 物化视图，一看数字很小 —— 因为今天之前的数据没回填。建完 MV 必须补一次历史数据，否则图表断崖。
模块 6

从 MySQL/PostgreSQL 过来：语法差异

会 SQL 不等于会写 ClickHouse。下面这些差异没有报错提示，只有慢查询和错数据。

概念MySQL / PostgreSQLClickHouse
主键唯一约束 + 索引稀疏索引 + 排序键。不保证唯一，重复键可以共存
UPDATE/DELETE行级操作，毫秒级，事务内mutation：异步重写整个 part，大表上以小时计，期间产生额外 IO
事务ACID，跨表跨行单条 INSERT 的一个 block 内原子。没有跨表事务
JOIN嵌套循环 / hash / 索引，优化器选hash join 为主。大表在线 JOIN 是灾难，应宽表化或用字典
NULL普遍使用Nullable 类型有额外存储和计算开销，能用默认值就别用 NULL
自增 IDAUTO_INCREMENT没有。需要序列用 generateSnowflakeID() 或上游生成
ALTER轻量（多数场景）加列是元数据操作（秒级）；改类型、删列是 mutation（重写数据）
分页LIMIT OFFSET同样支持，但深分页要扫全部前序行，大表用 LIMIT BY + 分区裁剪
# ===== 日期函数：MySQL 的 DATE_FORMAT → ClickHouse 的 formatDateTime =====
SELECT formatDateTime(event_time, '%Y-%m-%d %H:00:00') AS hour_bucket, count()
FROM events GROUP BY hour_bucket;
# 更高效的做法：时间先归整再聚合，减少分组基数
SELECT toStartOfHour(event_time) AS h, count()
FROM events GROUP BY h;

# ===== PG 的 generate_series → ClickHouse 没有，用数组或系统表 =====
SELECT arrayJoin(range(toUInt32(1), 101)) AS n;

# ===== ClickHouse 特有的 LIMIT BY：每组取前 N =====
SELECT user_id, page, event_time
FROM events
ORDER BY user_id, event_time DESC
LIMIT 3 BY user_id;        # 每个 user_id 取最近 3 条

# ===== WITH TOTALS：PG/Oracle 有的 ROLLUP 平替 =====
SELECT page, count() FROM events GROUP BY page WITH TOTALS;
mutation 不是普通 UPDATE：ALTER TABLE t UPDATE col = v WHERE id = 1 提交后立刻返回，但它在后台重写包含这些行的每个 part。百万级行的表上一个 mutation 可能跑几十分钟，期间磁盘 IO 翻倍。ClickHouse 的正确姿势是"追加写"：更新 = 插一行新版本 + ReplacingMergeTree 去重，或者 CollapsingMergeTree 折叠。
模块 7

性能优化：宽表、PREWHERE 与 FINAL

宽表设计：把 JOIN 消灭在写入时

  • OLAP 的第一优化原则：查询时少 JOIN，写入时多冗余。维度表（用户、商品、地区）在 ETL 阶段打成宽表，一条记录查所有列
  • 实在要关联小维表：用外部字典（dictionary）或 LowCardinality(String) + ENUM，字典常驻内存，dictGet() 是内存查找不走 join
  • LowCardinality(String)：低基数（几百到几万个不同值）字符串列的利器，字典编码通常省 5~10 倍内存，聚合也能走全局序数
# 宽表 + 低基数类型
CREATE TABLE events_wide (
    event_date Date,
    city       LowCardinality(String),   # 几百个城市，字典编码
    device     LowCardinality(String),
    user_id    UInt64,
    stay_ms    UInt32
) ENGINE = MergeTree PARTITION BY toYYYYMM(event_date)
ORDER BY (event_date, city);

# 字典 JOIN 的替代：dictGet
SELECT user_id, dictGet('user_dict', 'nick', toUInt64(user_id)) AS nick
FROM events_wide LIMIT 10;

PREWHERE：先过滤再读列

  • ClickHouse 的列存读取是"按需读列"。PREWHERE 先算过滤条件、用结果去读其他列，能少读大列（长字符串、大 JSON）
  • 对 MergeTree，优化器会自动把 WHERE 提升为 PREWHERE（move_primary_key_columns 相关优化），所以多数情况写 WHERE 就够；显式 PREWHERE 用于强制语义或兼容旧版
  • 真正常见的性能杀手是 SELECT * —— 把 200 列全读出来只为查 2 列。永远点名要查的列
# PREWHERE 显式写法（等价语义，显式提示优化器）
SELECT user_id, stay_ms
FROM events_wide
PREWHERE event_date = '2026-10-01'      # 先按分区裁剪
WHERE stay_ms > 5000;

# 看查询瓶颈：rows_read vs rows_returned
SELECT query, read_rows, result_rows, query_duration_ms
FROM system.query_log WHERE type = 'QueryFinish' ORDER BY query_duration_ms DESC LIMIT 10;

FINAL：最贵的四个字母

写法行为
SELECT ... FROM t FINAL WHERE ...查询时实时执行"合并"：跨 part 按排序键去重/折叠。每个查询都要做一遍，CPU 和内存双倍消耗
GROUP BY + any/argMax查询时按业务键自去重，只碰查询真正需要的列，通常比 FINAL 便宜
写入时保证唯一上游去重后写入，或 Replicated + insert_deduplicate。根治方案
# 替代 FINAL 的惯用法：argMax 取每个 key 最新的版本
SELECT user_id,
       argMax(nick, updated_at)      AS nick,
       max(updated_at)               AS updated_at
FROM user_profile
GROUP BY user_id;
FINAL 的正确用法：只用于低并发管理查询、对账、巡检。放在高并发 API 查询里，QPS 一上来 CPU 直接打满 —— 而且 FINAL 无法利用主键索引跳过 granule，是全表归并。生产上要么 GROUP BY 去重，要么把去重下沉到写入侧。

更多必调项

max_threads默认 CPU 核数。高并发多租户场景要往下调，防止单查询吃满机器
max_execution_time单查询最大秒数，默认 0（不限）。必须设，兜底慢查询
max_memory_usage单查询内存上限，约 10GB。GROUP BY 大基数聚合前先估算
max_bytes_before_external_group_by超限自动溢写磁盘，防大分组 OOM
parts_to_throw_insert单分区 part 数超限直接拒绝插入（默认 3000），防 part 爆炸的最后防线
use_query_cache21.6+ 查询缓存，重复相同 SELECT 直接命中，适合看板
模块 8

十个线上坑

1
循环逐行 INSERT
每次插入生成一个 part，merge 永远追不上写入，part 数滚雪球直至 Too many parts 报错。至少攒 1000 行一批，或开 async_insert。
2
高频小批量乱序插入
跨分区、跨主键乱序的小 part 会让 merge 退化成交叉合并，磁盘 IO 和 CPU 双高。上游按时间分片按序发送，迟到数据走单独表。
3
以为 ReplacingMergeTree 查出来就没重复
去重只在后台 merge 时发生，未合并前同键多行都返回。兜底：查询时 GROUP BY 去重，或 FINAL（低并发场景）。
4
高并发查询用 FINAL
FINAL 每次查询都实时归并全 part，不能利用主键索引，CPU 和内存双倍消耗。看板和 API 场景禁用，用 argMax 替代。
5
把 UPDATE/DELETE 当日常操作
mutation 异步重写整个 part，大表上以小时计，期间磁盘 IO 翻倍、查询变慢。正确姿势是追加写 + 去重引擎。
6
分区键选了高基数字段
按 user_id 分区会产生几十万个分区目录，merge 调度碎片化，元数据爆炸。分区键用日期类低基数表达式。
7
把 ORDER BY 当唯一约束
MergeTree 主键不保证唯一。上游重试、双写、回灌都会产生重复行，上游必须自己做幂等。
8
线上查询 SELECT *
宽表 200 列全读，IO 和网络全浪费。永远点名要查的列，大字段（String/JSON）按需取。
9
两张大表在线 JOIN
ClickHouse 的 JOIN 是 hash join，两张十亿级表 join 直接吃光内存。要么宽表化，要么字典，要么先聚合再 join。
10
不设 TTL、不巡检磁盘
日志类数据只增不减，磁盘写满集群进入只读。建表即设 TTL，日常巡检 system.parts 和磁盘水位。
自测

六道题

1. MergeTree 的 ORDER BY 定义的主键，下面哪个说法是对的？
正确答案：稀疏索引，不保证唯一。索引每 8192 行（一个 granule）只记一个标记，同 granule 内的行无法区分；排序键相同的两行可以同时存在，直到后台 merge 才可能去掉。点查单行也不是它的强项。
2. 一张用户画像表需要"同一 user_id 只保留最新一条"，应该选哪种引擎？
正确答案：ReplacingMergeTree。带 version 列（这里是 updated_at）时，后台 merge 对相同排序键的行保留版本最大的那行。注意去重不是实时的，未 merge 前查询仍可能查到多行，需要 GROUP BY 或 FINAL 兜底。
3. 想用 insert_deduplicate 实现 Exactly-once 插入，前提是？
正确答案：只对 ReplicatedMergeTree 有效。块级去重依赖 ClickHouse Keeper 里记录的 block id，单机 MergeTree 没有这个协调机制，设置它不会报错但完全不生效。22.x 起默认值为 1。
4. 一条查询要按 event_date 过滤后取两列大字符串，应该怎么写？
正确答案：点名列 + PREWHERE。列存的优势就是"只读要用的列"，SELECT * 把 200 列全读出来是最大的浪费；PREWHERE 先算过滤条件再读其他列。对 MergeTree，优化器通常会自动做 WHERE→PREWHERE 提升，但显式写更保险。
5. 为什么 ClickHouse 不推荐用 ALTER TABLE ... UPDATE 更新数据？
正确答案：mutation 重写整个 part。提交后立刻返回但后台执行，重写期间磁盘 IO 翻倍、查询变慢，十亿级行的表上一个 mutation 可能跑几小时。正确做法是追加写新版本行 + ReplacingMergeTree 去重，或 CollapsingMergeTree 折叠。
6. SummingMergeTree 对"相同排序键"的多行记录会怎么合并？
正确答案：数值列求和，非聚合列取任意值。这是"保留最后一行"（ReplacingMergeTree）和"求和"（SummingMergeTree）的关键区别。也因为非聚合列取任意值，SummingMergeTree 不适合明细混合场景。

SELECT * FROM system.parts WHERE active巡检 part 数量和大小，防 part 爆炸
OPTIMIZE TABLE t FINAL强制触发合并（运维窗口用，线上慎用）
ALTER TABLE t DROP PARTITION '202601'秒级删分区，比 DELETE 高效几个数量级
EXPLAIN indexes = 1 SELECT ...看索引和分区裁剪是否生效
KILL QUERY WHERE query_duration_ms > 60杀掉超时慢查询
SELECT ... FROM system.query_log ORDER BY query_duration_ms DESC LIMIT 10找最慢的查询
SELECT table, sum(rows) FROM system.parts GROUP BY table估算每张表的行数
SHOW CREATE TABLE t看建表语句：引擎、分区、排序键、TTL 全在里面
SET async_insert = 1, wait_for_async_insert = 1小插入攒批，22.x+ 救星
INSERT INTO t SETTINGS insert_deduplication_token = 'uuid'显式幂等令牌，Exactly-once
SELECT argMax(col, ver) FROM t GROUP BY key替代 FINAL 的去重惯用法
dictGet('dict', 'col', key)字典查找，替代小表 JOIN

关键配置项

# server 级（config.xml）里最该盯的几个
max_threads                    # 默认 CPU 核数；高并发多租户往下调
max_execution_time = 120       # 单查询最大秒数，必须设
max_memory_usage = 10GB        # 单查询内存上限
parts_to_throw_insert = 3000   # 单分区 part 数上限，防爆炸最后防线
merge_tree.max_bytes_to_merge  # 单次合并最大字节，防单次合并 IO 尖刺
async_insert = 1               # 22.x+ 小插入自动攒批

# 日常巡检 SQL（建议放监控）
SELECT partition, count() AS parts, formatReadableSize(sum(bytes_on_disk)) AS size
FROM system.parts WHERE active GROUP BY partition ORDER BY parts DESC;

术语表

术语一句话解释
列式存储按列连续存储数据，查询只读需要的列，高压缩、适合 OLAP
MergeTreeClickHouse 的核心引擎家族：INSERT 生成 part，后台 merge 合并
Part每次插入生成的物理数据单元，合并的最小单位
排序键 / 主键ORDER BY 定义的键，数据在 part 内按它有序，也是稀疏索引依据，不保证唯一
Granule索引粒度，默认 8192 行，主键索引按它记录边界值
分区PARTITION BY 定义的物理目录，查询时整目录跳过
跳数索引part 内的二级索引（minmax/set/bloom_filter 等），跳过无关 granule
ReplacingMergeTreemerge 时对相同键保留最后一行，实现最终一致去重
SummingMergeTreemerge 时相同键的数值列求和，做简单预聚合
AggregatingMergeTree存储 AggregateFunction 聚合状态，做 UV 等复杂预聚合
物化视图插入触发器：源表数据按 SELECT 变换后增量写入目标表，只对新数据生效
投影表内附加数据副本，查询时透明加速，与主数据强一致
MutationALTER UPDATE/DELETE 的异步重写操作，大表上极重
insert_deduplicate块级去重开关，只对 ReplicatedMergeTree 有效，22.x 默认开启
PREWHERE先计算过滤条件再读其他列，减少大列 IO
FINAL查询时实时执行合并，去重准确但极贵，禁用于高并发
LowCardinality低基数字符串列的字典编码类型，省 5~10 倍内存
ClickHouse Keeper替代 ZooKeeper 的协调服务，管复制、块去重、DDL 协调
TTL数据/列的自动过期机制，按 ttl_interval（默认 4h）周期性执行
part 爆炸小批量高频插入导致 part 数远超 merge 速度，查询劣化直至拒绝写入
