二十分钟学透 RocksDB 与 LSM 树

RocksDB 不是一个数据库，是嵌进你程序里的存储引擎。LSM 树用"追加写 + 后台合并"换来高写入吞吐，代价是写放大、读放大、空间放大的三角权衡。这篇把这套机制和调参的坑一次讲清。

开始前

它是什么，不是什么

RocksDB 是 Facebook 基于 LevelDB 重写的嵌入式 KV 存储引擎（C++ 库），没有网络服务、没有账号体系、没有 SQL。你的进程链接它，它把数据落在你指定的目录——这就是"嵌入式"的含义。

认知事实
"像 MySQL 一样装一个服务"不对。没有独立进程，没有连接协议。它是你程序里的一个 .so/.a，API 就是函数调用
"数据在内存里所以快"不对。数据全在磁盘（SSTable 文件），MemTable 只是写缓冲。它靠顺序 IO + 缓存提速，不是内存数据库
"能替代 Redis"不对。RocksDB 是磁盘 KV，微秒级延迟；Redis 是内存数据结构服务，亚毫秒到毫秒级。定位不同，经常搭配使用
"MyRocks / TiKV 是新数据库"对了一半。它们是把 RocksDB 当存储引擎、外面包一层分布式/协议层的产品

谁在用 RocksDB

MyRocks
MySQL 的存储引擎，替代 InnoDB，Facebook 主力
TiKV
分布式 KV，Raft 层 + RocksDB 层，TiDB 的存储底座
Flink
有状态流计算的本地状态后端（大 state 场景标配）
Kafka Streams
本地状态存储 + changelog topic 恢复
CockroachDB / Yugabyte
分别 fork 出 Pebble / DocDB 做单机存储层
业务自研
本地缓存持久化、特征存储、消息投递状态、元数据存储
模块 1

LSM 树层次结构

LSM（Log-Structured Merge）树的核心思想：把随机写变成顺序写。数据从内存逐层往下刷，每下一层数据量约扩大 10 倍。理解层级结构，后面所有参数都有了意义。

L0 到 L6 各是什么

层数据来源键范围特性
L0MemTable flush 直接产生多个文件间键范围可重叠，新的在左边。一次读可能要查多个 L0 文件
L1 ~ L6Compaction 逐层下推每层内部全局有序、文件间键范围不重叠，查一层最多命中一个文件
容量每层约为上一层的 10 倍target_file_size_base=64MB，max_bytes_for_level_base=256MB（默认值）
层数num_levels=7（即 L0~L6）最后一层（L6）即 bottom level，删除标记在这里被真正物理清除

一次点查的完整路径

db->Get(ReadOptions(), "user:1001", &value)

// 1. 查活跃 MemTable（内存 skiplist）
// 2. 查 Immutable MemTable（如果有）
// 3. 查 L0 的每个 SSTable（按生成时间从新到旧，找到即停）
// 4. 查 L1 ~ L6，每层最多一个文件可能命中（键范围不重叠）
//    每层都先过布隆过滤器，说"不存在"就跳过整个文件
// 5. 全部没命中 → Not Found
为什么 L0 特殊：flush 是并发进行的，多个 Immutable MemTable 可能同时刷出多个 L0 文件，它们键范围互相重叠。而 L1 及以下由 compaction 保证"层内有序不重叠"，所以点查每层只查一个文件。L0 文件越多，读放大越严重，这是 level0_file_num_compaction_trigger（默认 4）存在的原因。
模块 2

写路径：从 WAL 到 SSTable

一次 Put 要经过四站。每一站的设计目标只有一个：不丢数据 + 顺序写磁盘。

① 写 WAL（Write-Ahead Log）：先把操作追加到日志文件（顺序 IO，快），再动内存。进程崩溃后靠重放 WAL 恢复。支持组提交（group commit）：多个并发写共享一次 fsync
② 写 MemTable：内存里的跳表（skiplist），同时是全量数据的活跃写缓冲。write_buffer_size 默认 64MB
③ MemTable 写满 → 变为 Immutable MemTable：切换为只读，同时新建活跃 MemTable 接收写入。max_write_buffer_number 默认 2，即最多 1 个活跃 + 1 个不可变；超过就阻塞写入等 flush
④ Flush → L0 SSTable：Immutable MemTable 刷成有序的 SSTable 文件（含数据块 + 索引块 + 布隆过滤器块），落 L0。删掉对应的 WAL 段
⑤ Compaction 逐层下推：L0 文件攒够触发 compaction，挑选与 L1 重叠的文件归并排序后下沉，逐级直到 L6。删除旧文件、合并多版本、物理清除已删数据

关键机制

机制说明
删除 = 写墓碑Delete 不是原地删，是写一个 tombstone 标记。直到 compaction 到 bottom level 才物理移除——所以删完立刻看磁盘占用不会降
多版本共存同一 key 的新旧值可同时存在不同层/文件，Get 时取最新版本。这是迭代器快照和 MVCC 语义的基础
组提交并发写共享一次 WAL fsync，吞吐远高于一写一刷。默认 WAL 同步策略 WriteOptions::sync=false（异步，崩了可能丢尾部）
写停顿保护L0 文件超过 level0_slowdown_writes_trigger（默认 20）降速，超过 level0_stop_writes_trigger（默认 36）停写等 compaction
// 写路径上的 API 选择
db->Put(WriteOptions(), key, value);              // 单条写，每次一个 WAL 追加
rocksdb::WriteBatch batch;                        // 批量写，合并成一次 WAL 追加 + 一次 MemTable 插入
batch.Put(cf, "k1", "v1");
batch.Put(cf, "k2", "v2");
batch.Delete(cf, "k3");
db->Write(WriteOptions(), &batch);                // 整个 batch 原子生效

rocksdb::WriteOptions wo;
wo.sync = true;                                   // 等 WAL fsync 才返回，最安全最慢
wo.disableWAL = true;                             // 完全不写 WAL，崩了丢未刷盘数据（缓存场景）
"数据写进去了"是个有歧义的说法。默认 sync=false 时，写进 MemTable 就算成功，但还在操作系统页缓存里，进程崩了有 WAL 兜底，机器掉电则丢失。要"掉电不丢"必须 wo.sync=true 或开 WAL 自动同步。批量导入时先用 disableWAL 提速、导完 CompactRange，是常见组合拳。
模块 3

Compaction 策略与三种放大

Compaction 是 LSM 的心脏，也是唯一可以调出巨大性能差异的旋钮。先记住三角权衡，再看策略。

三种放大

类型定义量级参考
写放大磁盘写入总量 ÷ 用户写入量。 compaction 反复重写同一份数据Leveled 典型 10~40x；Universal/Tiered 可降到 5~10x
读放大一次点查实际访问的 SSTable 数量（含布隆过滤器检查）Leveled 约 1~2 次/层，靠布隆过滤；Universal 层内多文件，显著更高
空间放大磁盘占用 ÷ 逻辑数据量。旧版本数据未及时清除Leveled 约 10%；Tiered/Universal 可达 2 倍以上

三角不可能同时最优：压写放大 → 空间/读放大升；压读放大 → 写放大升。调参就是按你的读写比例选站位。

策略对比

策略结构适用
Leveled
（RocksDB 默认）		每层一个有序 run，层间 10 倍容量。compaction 拿 L_n 一个文件和 L_n+1 重叠文件归并读多写少、数据量大、要求低读放大。写放大最高
Universal
（≈ Size-Tiered）		动态层：把大小相近的多个 SSTable 合成一个 tier，整 tier 归并写多读少、批量导入。写放大低，读放大和空间放大高
FIFO不管键，按时间淘汰最老的文件（类 TTL 队列）日志、时序数据，只留最近 N 天
术语对齐："Tiered（Size-Tiered）"是通用 LSM 术语，Cassandra 默认用它；RocksDB 原生只有 Leveled / Universal / FIFO 三种 style，其中 Universal 就是 Size-Tiered 思路的工程实现。看到"分层 compaction"和"平铺 compaction"的争论，指的是这一对。 
// Leveled（默认）关键参数
options.write_buffer_size = 64 << 20;        // 64MB MemTable
options.target_file_size_base = 64 << 20;    // L1 文件目标大小
options.max_bytes_for_level_base = 256 << 20;// L1 总容量，下层逐层 ×10
options.level0_file_num_compaction_trigger = 4;// L0 攒够 4 个文件触发 compaction

// 切 Universal：写密集场景
options.compaction_style = rocksdb::kCompactionStyleUniversal;
options.num_levels = 1;                        // 常配合少量层级

// 切 FIFO：纯时序/TTL 数据
options.compaction_style = rocksdb::kCompactionStyleFIFO;
options.max_open_files = -1;                   // FIFO 需要能打开所有文件

// compaction 限速：防后台 IO 打满前台请求
options.rate_limiter = std::shared_ptr<rocksdb::RateLimiter>(
    rocksdb::NewGenericRateLimiter(100 << 20));   // 限制 compaction 合计 100MB/s
Leveled 写放大的来源：每下一层，数据就要被重写一遍。7 层、每层 10 倍容量时，一份数据从 L1 到 L6 平均被重写约 5~6 次，这就是 10~40x 写放大的算术本质。SSD 有写入寿命——云盘按量计费的 IOPS 也会被 compaction 悄悄吃光。写密集业务用 Universal 或平铺策略，别用默认。
模块 4

布隆过滤器与块缓存

LSM 读多层的代价靠两样东西抵消：布隆过滤器挡掉不存在的文件，块缓存挡住热数据。不配这两样，LSM 的读性能会难看。

布隆过滤器

属性说明
粒度每个 SSTable 一个过滤器，存在文件尾部的 filter block
语义"这个 key 一定不在这个文件" / "可能在"。有误判（假阳性），无漏判
默认精度约 10 bits/key，误判率约 1%
代价约 1.2% 的额外空间；查询时多一次内存计算
// 创建 DB 时显式配置（RocksDB 默认不建布隆过滤器！）
rocksdb::BlockBasedTableOptions table_options;
table_options.filter_policy.reset(rocksdb::NewBloomFilterPolicy(10, false));  // 10 bits/key
options.table_factory.reset(rocksdb::NewBlockBasedTableFactory(table_options));

// 效果：点查不在库里的 key，只碰内存，零磁盘 IO
// 注意：RangeScan / 迭代器遍历用不上过滤器，只加速点查

块缓存（Block Cache）

属性说明
是什么内存 LRU 缓存，存解压后的数据块、索引块、过滤器块
默认大小仅 8MB——生产基本都要调大。经验值：可用内存的 20%~30%
块大小block_size 默认 4KB。范围扫描多可调到 16~64KB 减索引开销
索引块cache_index_and_filter_blocks 默认 false（每次查询重新加载）。数据量大时设 true
// 共享块缓存（多列族/多实例时复用）
auto cache = rocksdb::NewLRUCache(1 << 30);   // 1GB
rocksdb::BlockBasedTableOptions table_options;
table_options.block_cache = cache;
table_options.cache_index_and_filter_blocks = true;   // 索引/过滤器也进缓存
table_options.block_size = 16 << 10;                 // 16KB 块，适合范围扫描
读优化三件套：① 建布隆过滤器（点查必备）；② 块缓存给到 1GB 以上并缓存索引过滤器块；③ 热 key 少就还能再上 optimize_filters_for_hits。顺序全量遍历（迭代器）的场景反过来：过滤器没用，块要设大减少索引查找。
模块 5

列族与合并算子

列族（Column Family）让一个 DB 里跑多套独立配置的数据；合并算子（Merge Operator）让你在服务端做"读-改-写"而不必先读出来。

列族

问题答案
是什么同一 DB 内的独立键空间，各有自己的 MemTable、SSTable 和 compaction 参数
默认列族default 永远存在。不指定 CF 的读写都落在它上面
原子性一个 WriteBatch 跨多个 CF 的写入原子生效（同一个 WAL 序列）
最大坑打开 DB 时必须列出所有已存在的 CF，漏一个直接报错（见坑 7）
// 1. 创建列族
rocksdb::ColumnFamilyHandle* cf_orders = nullptr;
db->CreateColumnFamily(rocksdb::ColumnFamilyOptions(), "orders", &cf_orders);

// 2. 跨列族原子写（订单 + 用户统计一个批次）
rocksdb::WriteBatch batch;
batch.Put(cf_orders, "order:1001", "{status:PAID}");
batch.Put(default_cf,    "stats:orders", "1");
db->Write(rocksdb::WriteOptions(), &batch);

// 3. 重启时必须带全部列族打开，否则报错
std::vector<rocksdb::ColumnFamilyDescriptor> cf_descs;
cf_descs.emplace_back(rocksdb::kDefaultColumnFamilyName, rocksdb::ColumnFamilyOptions());
cf_descs.emplace_back("orders", rocksdb::ColumnFamilyOptions());
std::vector<rocksdb::ColumnFamilyHandle*> handles;
rocksdb::DB::Open(rocksdb::DBOptions(), path, cf_descs, &handles, &db);

合并算子（Merge Operator）

场景：计数器、累加器、只追加的列表。没有 Merge 时，你要 Get 出来、改、再 Put——并发下丢更新，还多一次读。Merge 把"合并逻辑"下沉到引擎：读路径遇到 merge 操作数会自动合并出结果。

// 自定义 Merge：把所有操作数累加到现有值上
class CounterMerge : public rocksdb::MergeOperator {
 public:
  bool FullMerge(const rocksdb::Slice& key, const rocksdb::Slice* existing_value,
                  const std::deque<std::string>& operand_list,
                  std::string* new_value, std::shared_ptr<rocksdb::Logger> logger) const override {
    int64_t total = existing_value ? std::stoll(existing_value->ToString()) : 0;
    for (const auto& op : operand_list) total += std::stoll(op);
    new_value->append(std::to_string(total));
    return true;
  }
  const char* Name() const override { return "CounterMerge"; }
};

options.merge_operator = std::make_shared<CounterMerge>();

// 使用：三条 Merge 累加，Get 直接拿到 3
batch.Merge("page:home:pv", "1");
batch.Merge("page:home:pv", "1");
batch.Merge("page:home:pv", "1");
db->Write(wo, &batch);
db->Get(ro, "page:home:pv", &value);   // value == "3"
Merge 算子的正确性条件：合并操作必须可结合、可交换（引擎可能把多个 merge 操作数分批部分合并，顺序不保证）。计数、位或、集合并集都满足；"append 到字符串末尾"要小心——部分合并会打乱拼接顺序，需要额外带序号自己排序。
模块 6

嵌入式 KV 的典型用法

用法就一句话：链接库、Open、CRUD、迭代。真正难的是选对使用场景和参数。

最小可用示例

// demo.cpp —— 编译：g++ -std=c++17 demo.cpp -o demo -lrocksdb
#include <cstdio>
#include <string>
#include "rocksdb/db.h"
#include "rocksdb/options.h"
#include "rocksdb/write_batch.h"

int main() {
  rocksdb::DB* db = nullptr;
  rocksdb::Options options;
  options.create_if_missing = true;               // 目录不存在则创建

  rocksdb::Status s = rocksdb::DB::Open(options, "/tmp/rocksdb_demo", &db);
  if (!s.ok()) { fprintf(stderr, "open failed: %s\n", s.ToString().c_str()); return 1; }

  db->Put(rocksdb::WriteOptions(), "user:1001", "Alice");
  db->Put(rocksdb::WriteOptions(), "user:1002", "Bob");

  std::string value;
  db->Get(rocksdb::ReadOptions(), "user:1001", &value);
  printf("user:1001 = %s\n", value.c_str());   // Alice

  // 全量迭代（生产大库别这么干，会慢）
  rocksdb::Iterator* it = db->NewIterator(rocksdb::ReadOptions());
  for (it->SeekToFirst(); it->Valid(); it->Next()) {
    printf("%s = %s\n", it->key().ToString().c_str(), it->value().ToString().c_str());
  }
  delete it;
  delete db;
  return 0;
}

快照迭代（遍历中不被写入干扰）

// 拿一个一致性快照，之后的所有读都基于这个版本
const rocksdb::Snapshot* snap = db->GetSnapshot();
rocksdb::ReadOptions ro;
ro.snapshot = snap;

rocksdb::Iterator* it = db->NewIterator(ro);
for (it->Seek("user:"); it->Valid(); it->Next()) {
  // ... 处理，期间别人的写入不影响这次遍历
}
delete it;
db->ReleaseSnapshot(snap);   // 用完必须释放，否则旧版本永不回收，空间泄漏

选场景的判据

  • 键值访问模式：点查、前缀扫描、范围遍历为主。需要二级索引/复杂查询 → 不选它
  • 数据量大于内存：内存放得下用 map 更快；放不下又必须本地持久 → RocksDB 主场
  • 写密集 + 读可预测：顺序灌、后台 compaction、布隆挡空——LSM 的甜蜜点
  • 同进程内共享：多进程同时 Open 同一目录会冲突（单写者模型），需要分布式就上 TiKV/Pebble 这类外层
常用维护操作：CompactRange() 手动触发全量 compaction（删数据后回收空间、批量导入后整理）；Checkpoint 做一致性备份（快照式硬链/拷贝，不停写）；ldb 工具（随源码构建）可命令行查看 SST 内容、触发 compaction。
模块 7

MyRocks 简介

MyRocks = MySQL + RocksDB 存储引擎。Facebook 为解决"InnoDB 在我们这种体量下太占空间"的问题，把 RocksDB 塞进了 MySQL。它是理解 LSM 工业落地的最好样本。

维度InnoDBMyRocks
存储结构B+Tree，原地更新页LSM，追加写 + compaction
空间效率页分裂留下碎片，压缩一般整块压缩（zstd/lz4），Facebook 报告省约 50% 空间
内存Buffer Pool 独占一份缓存直接吃 OS page cache，无双份缓存
写入随机写，SSD 上写放大明显顺序写为主，海量小写入吞吐更高
读B+Tree 三四层，随机 IO 少多层 SST + 布隆，随机读略逊（依赖缓存）
功能外键、全文、空间索引齐全不支持外键/空间索引；范围删除和热点行反复更新不如 InnoDB
复制binlog 逻辑复制同样用 binlog，但要注意 compaction 的磁盘抖动

什么时候认真考虑 MyRocks

  • 数据量 TB 级、存储成本敏感（云盘按 GB 计费时省一半空间很香）
  • 写入吞吐是瓶颈，SSD 寿命/IOPS 预算紧张
  • 读模式偏点查和前缀扫描，热点数据能被 page cache 兜住
代价清单（迁移前必读）：① 丢掉外键和空间索引，应用层自己保证完整性；② 热点行反复 UPDATE 会让 LSM 堆积多版本，compaction 压力山大；③ 大范围 DELETE 靠 range tombstone，比 InnoDB 慢；④ 团队要学会看 compaction 指标（stall、IO 队列、写放大）。OLTP 通用负载上 InnoDB 仍是更稳的默认选择。
模块 8

定位对比：Redis / B-Tree / LSM

三个都"存数据"，但属于三个不同的世界。放错位置是架构事故的开始。

维度RedisB-Tree（InnoDB）RocksDB（LSM）
定位内存数据结构服务通用 OLTP 关系数据库嵌入式 KV 引擎
数据位置内存（可选持久化）磁盘，Buffer Pool 缓存磁盘，MemTable + Block Cache 缓存
写模型内存改 + 异步持久化原地更新页，随机写追加 + 后台 compaction，顺序写
点查延迟亚毫秒（内存）低（缓存命中时）低~中（看缓存与 L0 文件数）
吞吐特征单线程，10 万 QPS 级写受随机 IO 限制写吞吐极高，读依赖缓存
数据结构String/Hash/ZSet 等表、索引、事务字节 KV，无 schema

热点读        →  Redis（扛 QPS，挡住磁盘）
持久化/事务   →  MySQL/PostgreSQL（B-Tree，业务正确性）

一句话选型：要"快"用 Redis，要"对"用 B-Tree，要"装得下还写得动"用 LSM。现实中三者常常同时出现在一个系统里，不是三选一。RocksDB 的定位更接近"零件"——单独用的场景，多半是本地状态存储。
模块 9

十个线上坑

1
write_buffer_size 调到几 GB 当"内存库"
MemTable 越大 flush 尖刺越狠（一次刷几个 GB 的 SST），恢复时重放 WAL 也更慢。64~256MB 是常见合理区间，别靠它撑吞吐。
2
块缓存用默认 8MB
数据量上 GB 后 8MB 缓存形同虚设，点查大量打磁盘。按可用内存的 20%~30% 给，并开 cache_index_and_filter_blocks。
3
不建布隆过滤器
RocksDB 默认不建过滤器，查不存在的 key 要把每层每个文件都翻一遍。点查多的场景必须显式配 NewBloomFilterPolicy。
4
迭代器不用快照
遍历期间并发写入会让迭代器看到"半新半旧"的数据，业务逻辑出错。长遍历先 GetSnapshot，用完 ReleaseSnapshot。
5
compaction 不限速
后台 compaction 把磁盘 IO 打满，前台读写延迟毛刺。用 NewGenericRateLimiter 限制 compaction 总带宽，和业务 IO 错峰。
6
L0 文件堆积导致停写
L0 超过 level0_stop_writes_trigger（默认 36）时 RocksDB 直接拒绝写入。根因常是 compaction 跟不上（磁盘慢/限速太狠/单线程 flush），看日志里的 stall 信息。
7
打开 DB 漏掉列族
Open 时只列了 default，报 "Column families not opened" 或数据"消失"。必须先用 ListColumnFamilies 拿到全部 CF 再 Open，CF 名是硬编码在代码里的契约。
8
批量删除后磁盘不释放就以为删干净了
Delete 只写墓碑，数据文件原样躺着。要么等 compaction 下沉到底层，要么手动 CompactRange 立即回收。监控的是逻辑量，磁盘可是物理量。
9
拿 RocksDB 当关系数据库
没有二级索引、没有 JOIN、没有范围事务。需要这些能力要么应用层自己建索引表，要么外层用 TiKV/CockroachDB，别硬拗。
10
备份只拷贝 SST 文件
缺了 WAL 和 MANIFEST，恢复时状态不一致，直接打不开。用 DB::Checkpoint 或 Flush 后配合归档，别手工 cp 文件了事。
自测

六道题

1. L0 和 L1 及以下层级的关键区别是？
正确答案：L0 文件键范围重叠。所以一次点查可能要翻多个 L0 文件（按新到旧），而 L1~L6 每层最多一个文件命中。L0 文件过多会推高读放大甚至停写，这正是 level0_file_num_compaction_trigger 存在的原因。所有层都在磁盘上。
2. 一次 Put 的正确写路径顺序是？
正确答案：先 WAL 再 MemTable。WAL 先行保证崩溃可恢复；MemTable 写满转 Immutable，flush 成 L0 SSTable，之后靠 compaction 逐层归并下沉。顺序反了（先内存后日志）崩溃窗口内就会丢数据。
3. 关于 Leveled 和 Universal（Size-Tiered）compaction，哪个说法正确？
正确答案：三角权衡。Leveled 每层单 run，查找高效、旧版本清理快，代价是数据被反复重写（写放大 10~40x）；Universal 整 tier 归并，重写少（写放大 5~10x），但层内多文件让读要翻更多 SST、旧数据停留更久（空间放大可达 2x）。写密集选 Universal，读密集/大数据量选 Leveled。
4. 布隆过滤器说某个 key "不存在"时？
正确答案：说不存在就一定不存在。布隆过滤器只可能假阳性（说"存在"其实不在，默认 10 bits/key 约 1% 误判率），判定"不存在"100% 可靠。它只加速点查，范围扫描用不上；而且"删除"只是写墓碑，未 compaction 前数据还在文件里。
5. 合并算子（Merge Operator）最适合解决什么问题？
正确答案：服务端 read-modify-write。计数器场景里 Get 出来加一再 Put 有并发丢更新和双倍读的代价；Merge 把合并逻辑下沉到引擎，读路径自动合并操作数。前提是合并操作可结合、可交换——引擎可能分批部分合并，顺序不保证。"合并文件"那是 compaction 的活。
6. MyRocks 相对 InnoDB 的核心优势是？
正确答案：写吞吐 + 空间。LSM 把随机写变顺序写，配合 zstd/lz4 整块压缩，Facebook 报告省约 50% 空间。代价是丢掉外键/空间索引、随机读略逊、热点行反复更新会让 compaction 承压——所以它不是 InnoDB 的无脑替代品。
