二十分钟学透图数据库 Neo4j

图数据库的核心优势只有一句话：遍历关系的成本只与走过的子图大小有关，与全图数据量无关。这篇讲清楚属性图模型、Cypher 语法、免索引邻接、因果集群，以及用图做权限和风控的真实姿势。

模块 1

属性图模型：节点、关系、标签、属性

Neo4j 遵循属性图模型（Labeled Property Graph）。四个概念，全部背下来只要一分钟，但每个都有工程含义。

概念是什么工程含义
节点 Node一个实体，如一个用户、一台服务器内部有固定大小的引用指向它的所有关系，这是性能的根源
关系 Relationship两个节点间的有类型、有方向的连接，如 (:User)-[:FOLLOWS]->(:User)关系必须有一个类型，方向在查询里可省略语义但存储时保留。关系上也能挂属性（如 since）
标签 Label节点的分类，如 :User、:Server。一个节点可以有多个标签类似"表名"，查询时指定标签能大幅缩小扫描范围
属性 Property键值对，存在节点或关系上值可以是 string、number、boolean、日期时间、字符串列表等。null 不允许

和关系模型的本质区别

维度关系数据库属性图
连接表达外键 + JOIN，运行时按条件匹配关系是一等公民，物理上直接存指针
遍历成本随 JOIN 层数指数级恶化（递归 CTE 尤其明显）每跳都是指针跟随，成本与走过的边数成正比
模式先建表结构，数据必须符合先有数据，标签/属性即兴扩展
适合的查询"查满足条件的行"，集合运算"找路径、找邻居、找模式"，遍历运算
# 关系的物理真相：每个节点记录里存着一个关系链表头
# 遍历 (a)-[:FOLLOWS]->(b) 不是"扫 follows 表再连接"
# 而是：从 a 的记录直接拿到它所有 FOLLOWS 关系的引用，逐个跳过去

# 关系可以带属性 —— 这是关系模型做不到的（需要额外关联表）
MATCH (a:User {name:'Alice'})-[r:FOLLOWS]->(b:User)
RETURN b.name AS friend, r.since AS sinceWhen
ORDER BY r.since DESC
建模小抄：实体看"会不会有多个同类的属性要查"→ 做成节点；关系看"是不是两个实体间的一次具体互动"→ 做成关系；分类用标签（可以多个）；属性只放"直接描述自己"的键值。拿不准时问：这个查询是"找邻居/找路径"还是"算汇总"？后者可能不该用图。
模块 2

Cypher 核心语法

Cypher 是声明式查询语言：你描述"图的形状"，引擎负责找到它。核心就三个关键字家族：MATCH（读）、CREATE/MERGE（写）、REMOVE/DETACH DELETE（删）。

MATCH：模式匹配

# 1. 最基本：带标签 + 属性条件的节点
MATCH (u:User {email: 'alice@example.com'})
RETURN u.name, u.city

# 2. 遍历一层关系（-- 无向，--> 有向，<-- 反向）
MATCH (a:User {name:'Alice'})-[:FOLLOWS]->(b:User)
RETURN b.name

# 3. 关系带属性过滤 + 变量
MATCH (a:User {name:'Alice'})-[r:FOLLOWS]->(b:User)
WHERE r.since >= date('2024-05-01')
RETURN b.name, r.since

# 4. 变长关系：1 到 3 跳（* 表示任意跳，*..3 表示最多 3 跳）
MATCH (a:User {name:'Alice'})-[:FOLLOWS*1..3]->(b:User)
RETURN DISTINCT b.name

# 5. 可选匹配（左连接）：没有也不丢行
MATCH (u:User)
OPTIONAL MATCH (u)-[:FOLLOWS]->(f)
RETURN u.name, count(f) AS followsCount   // 没关注人的用户 count=0，不会消失

# 6. 参数化查询（生产必须用参数，防注入 + 命中查询缓存）
MATCH (u:User {email: $email})
RETURN u

CREATE 与 MERGE：写的语义

# CREATE：无脑新建。重复执行会造出重复节点 —— 幂等写入别用它
CREATE (:User {name: 'Eve', email: 'eve@example.com'})

# MERGE：有就用，没有就建（类似 MySQL 的 upsert）
MERGE (u:User {email: 'eve@example.com'})
ON CREATE SET u.createdAt = datetime(), u.loginCount = 0
ON MATCH  SET u.lastLoginAt = datetime()
RETURN u

# MERGE 关系 + 属性（保证不会重复加同一条关注）
MATCH (a:User {email:'alice@example.com'}), (b:User {email:'eve@example.com'})
MERGE (a)-[:FOLLOWS {since: date('2026-10-17')}]->(b)

# ✗ 经典错误：一次 MERGE 整个长 pattern
#   MERGE (a:User {email:'x'})-[:FOLLOWS]->(b:User {email:'y'})
#   如果 a 存在但关系不存在，它会尝试 MERGE 关系部分，语义容易失控
# ✓ 正确姿势：先分别 MERGE 两个节点，再 MERGE 关系

最短路径与路径函数

# shortestPath：找两点间最短的一条路径（按跳数）
MATCH p = shortestPath((a:User {name:'Alice'})-[:FOLLOWS*..6]-(b:User {name:'Dave'}))
RETURN p, length(p) AS hops

# allShortestPaths：所有最短路径之一组
MATCH p = allShortestPaths((a:User {name:'Alice'})-[:FOLLOWS*..6]-(b:User {name:'Dave'}))
RETURN p

# 路径常用函数
// length(p)          路径跳数
// nodes(p)            路径上的节点列表
// relationships(p)    路径上的关系列表
// [n IN nodes(p) | n.name]  列表推导，取所有节点名

# 二度好友推荐（社交图谱最经典查询）
MATCH (me:User {name:'Alice'})-[:FOLLOWS]->()-[:FOLLOWS]->(fof)
WHERE NOT (me)-[:FOLLOWS]->(fof) AND fof <> me
RETURN fof.name, count(*) AS mutualFriends
ORDER BY mutualFriends DESC
LIMIT 10

删除

# 删节点前必须先删关系，否则报错（防止孤儿关系）
MATCH (u:User {name:'Eve'})
DETACH DELETE u          // DETACH = 先删所有关系再删节点

# 只删关系，保留节点
MATCH (a:User {name:'Alice'})-[r:FOLLOWS]->(b:User {name:'Bob'})
DELETE r

# 批量删（大图慎用，长事务阻塞别人）
MATCH (u:User {city: '深圳'})
DETACH DELETE u
MERGE 是 Cypher 里唯一容易埋雷的写操作。记住三条：① MERGE 的匹配部分必须有唯一约束兜底，否则并发下两个事务都判断"不存在"、都去创建，产生重复；② 复杂 pattern 拆成"节点 MERGE + 关系 MERGE"两步；③ MERGE 的 ON CREATE SET / ON MATCH SET 分别处理新建和命中两种路径，初始化逻辑放 ON CREATE。
模块 3

索引与约束

图数据库的索引用途和关系库一样：让"找到起始节点"这一步不要全图扫描。Neo4j 4.x 之前只有 schema 索引；5.x 默认创建 token lookup 索引，标签查找也是索引化的。

类型语法说明
范围索引CREATE INDEX ... FOR (u:User) ON (u.email)单属性 B-Tree，支持 =、<、>、范围、存在性
复合索引... ON (u.lastName, u.firstName)多属性联合，前缀规则和 MySQL 一样
文本索引CREATE TEXT INDEX ... ON EACH [a.title, a.body]全文分词检索，支持 CONTAINS 谓词
查找索引CREATE LOOKUP INDEX ... ON EACH labels(n)5.x 引入，按标签/关系类型快速定位起始节点
唯一约束CREATE CONSTRAINT ... REQUIRE u.email IS UNIQUE自动建索引 + 强制唯一，MERGE 的最佳搭档
存在约束... REQUIRE u.name IS NOT NULL强制属性必填
节点键... REQUIRE (u.a, u.b) IS NODE KEY多属性联合唯一 + 必填
# ===== 索引创建（5.x 语法）=====
CREATE CONSTRAINT user_email IF NOT EXISTS
FOR (u:User) REQUIRE u.email IS UNIQUE

CREATE INDEX person_lastname_firstname IF NOT EXISTS
FOR (p:Person) ON (p.lastName, p.firstName)

CREATE TEXT INDEX article_content IF NOT EXISTS
FOR (a:Article) ON EACH [a.title, a.body]

CREATE LOOKUP INDEX node_label_lookup IF NOT EXISTS
FOR (n) ON EACH labels(n)

CREATE LOOKUP INDEX rel_type_lookup IF NOT EXISTS
FOR ()-[r]-() ON EACH type(r)

# 索引是后台创建的，大图上要先等它 online 再跑依赖查询
CALL db.awaitIndex('user_email', 300)

# 查看索引状态（POPULATING = 还在建，ONLINE 才可用）
SHOW INDEXES YIELD name, type, state, populationPercent

约束：MERGE 的并发安全网

# 没有唯一约束的 MERGE 在并发下会创建重复节点：
#   两个事务同时 MATCH 不到 email=x 的节点 → 同时 CREATE → 库里有俩
# 唯一约束让数据库在提交时强制检查，第二个事务直接报
#   Neo.ClientError.Schema.ConstraintValidationFailed

# 建约束前先清洗存量重复数据，否则约束创建失败
MATCH (u:User)
WITH u.email AS email, collect(u) AS nodes
WHERE size(nodes) > 1
UNWIND tail(nodes) AS dup
DETACH DELETE dup
顺序很重要：① 先建唯一约束（它会自动建配套索引）；② 再让业务用 MERGE 做幂等写入。反过来的话，先上线 MERGE 后补约束，期间可能已经产生重复数据，补约束时会失败，还得先做数据清洗。
模块 4

遍历性能：免索引邻接

这是图数据库对抗关系数据库的唯一核心技术优势，叫 Index-Free Adjacency（免索引邻接）。不理解它，就无法解释"为什么图查询快"。

原理

每个节点在存储里物理保存着指向自己所有关系的直接引用（类似链表指针，且进出方向分开存）。从节点 A 跳到邻居 B，就是一次指针解引用，不需要查索引、不需要扫关系表、不需要按外键做哈希连接。

查询关系库（递归 CTE / 多 JOIN）Neo4j
1 跳邻居按外键索引查 friends 表指针跳一次
3 跳邻居3 层自连接，中间结果集膨胀指针跳三次
10 跳路径递归 CTE 层数爆炸，基本不可用指针跳十次，依然线性
数据翻倍时每次 JOIN 成本随之增长同一个查询成本不变（只与走过的子图有关）
# 查询计划里看得到区别：NodeByLabelScan 之后直接 Expand（扩展）
EXPLAIN
MATCH (a:User {name:'Alice'})-[:FOLLOWS]->(b)-[:FOLLOWS]->(c)
RETURN c.name

# PROFILE 会显示每个算子的实际行数和命中（db hits）
PROFILE
MATCH (a:User {name:'Alice'})-[:FOLLOWS]->(b)-[:FOLLOWS]->(c)
RETURN c.name

性能上限来自哪里

既然每跳这么便宜，瓶颈在哪？答案是起始节点的定位和结果集的规模：

  • 起始点没索引：不带标签和属性的 MATCH (a) 触发 AllNodesScan 全节点扫描，大图上直接卡死
  • 中间结果爆炸：高度节点（supernode）一跳出来几百万邻居，内存和耗时都爆
  • 无界变长遍历：[:FOLLOWS*] 不限跳数，组合爆炸
# ✗ 反例：全节点扫描 + 无界变长路径
MATCH (a)-[:FOLLOWS*]-(b) WHERE a.name = 'Alice' RETURN b

# ✓ 正例：标签+属性定位起点（走索引），限定跳数，限定类型
MATCH (a:User {name:'Alice'})-[:FOLLOWS*1..4]-(b:User)
RETURN b
Supernode（超高度节点）是图库的头号性能杀手。典型场景：(:User)-[:HAS_ROLE]->(:Admin) 里 Admin 节点挂了几百万条关系；或"大 V 有几千万粉丝"。遍历到它的一跳会瞬间拉取全部关系。解法：拆分关系类型（把关注按时间/地区拆成不同类型）、加中间节点分层、或者查询时用 LIMIT 与更精确的中间条件收敛。
模块 5

集群架构：因果集群

Neo4j 的集群叫因果集群（Causal Cluster），核心是 Raft 共识协议。架构简单到只有两种服务器角色，但"因果一致性"四个字很多人没搞懂。

角色职责要点
核心服务器 Core参与 Raft 共识，复制所有数据，可读可写写只能发生在 leader。大多数存活才能选举新 leader
只读副本 Read Replica异步复制 leader 的数据，只提供读不参与投票。可无限水平扩展读能力

部署形态

  • 最小高可用：3 个 core，容忍 1 个故障。生产中核心至少 3，推荐奇数个
  • 读压力大：加 read replica，查询走 neo4j:// 路由自动负载均衡
  • 客户端连接协议分两种：neo4j://（集群路由，自动选 leader/副本）和 bolt://（直连单节点）——生产必须用 neo4j://
  • 副本是异步复制，所以副本上的读可能滞后于 leader
# 查看集群拓扑
CALL dbms.cluster.overview()

# 典型输出（简化）：每台机器的角色、地址、状态
// name        addresses       role       state
// core-1      localhost:7687  LEADER     ENABLED
// core-2      localhost:7688  FOLLOWER   ENABLED
// core-3      localhost:7689  FOLLOWER   ENABLED
// replica-1   localhost:7690  READ_REPLICA  ENABLED

# 客户端连接串（Java 示例）
// GraphDatabase.driver("neo4j://core-1:7687", AuthTokens.basic("neo4j","password"))
// driver.executeQuery(...) 会自动路由：写去 leader，读去副本
为什么不能把只读副本当强一致读：副本是异步复制。在副本上执行"写完立刻读"，可能读到旧值——这不是 bug，是设计。需要读到最新已提交数据时，要么读 leader（路由 bolt:// 到 core leader），要么用因果链（bookmark），见下一模块。
模块 6

ACID 与因果一致性

Neo4j 在单节点上是完整 ACID 的——这点经常被忽视，很多人以为"图数据库 = 最终一致 = 不能做交易"。集群下的一致性是"ACID + 因果一致性"的组合。

ACID 保证（单节点）

特性Neo4j 的实现
A 原子性一个事务里的多个 CREATE/MERGE 要么全提交要么全回滚。事务用 BEGIN ... COMMIT 或客户端 API
C 一致性约束（唯一/存在/节点键）在提交时强制校验，事务级生效
I 隔离性写写冲突用悲观锁，先到先得，后到的等或失败
D 持久性事务日志（WAL）+ 定期 checkpointer 刷盘
# 显式多语句事务
BEGIN
CREATE (a:User {email:'a@x.com'})
CREATE (b:User {email:'b@x.com'})
CREATE (a)-[:FOLLOWS]->(b)
COMMIT

# 上面的三条是一个原子单元：b 创建失败，a 也不会留下

因果一致性：集群下的"读写你自己的写"

问题场景：写请求打到 leader，写完立刻发一个读请求——负载均衡把它路由到了还没同步的副本，读到了旧值。对用户来说就是"我刚关注的人，刷新一下关注列表居然没了"。

解法是 bookmark（书签）机制：

  • 每个写事务返回一个 bookmark（本质是事务在 Raft 日志里的位置）
  • 下一个请求携带上一个 bookmark，驱动保证该请求只在"至少应用了那个写入"的节点上执行
  • 官方驱动自动完成这条链（session.lastBookmark()），业务无感
# Java 驱动的标准写法（伪代码）
// try (var session = driver.session(SessionConfig.builder().withDefaultAccessMode(AccessMode.WRITE).build())) {
//   session.executeWrite(tx -> tx.run("CREATE (u:User {email:$e})", params).consume());
//   bookmark = session.lastBookmark();   // 拿到写事务的书签
// }
// // 后续读请求带着这个 bookmark，保证读到刚才的写
// driver.executableQuery("...").withBookmark(bookmark)...
三句话记住一致性全景：① 单节点 = 全 ACID，可以做资金类强一致写入；② 集群 = 写走 Raft 多数派确认，读副本异步；③ "写后读一致"靠 bookmark 因果链，不是靠随机路由碰运气。框架（Spring Data Neo4j 等）都内置了 bookmark 传递，自己拼驱动时千万别丢。
模块 7

对比：Cypher vs 递归 CTE

"图查询用 SQL 递归 CTE 不行吗？"——能写，又慢又难读。同一个"三度人脉"需求，两种写法的差距就是图数据库的存在意义。

SQL 递归 CTE 写法

-- 表结构：follows(follower_id, followee_id)
WITH RECURSIVE reach AS (
  -- 锚点：我关注的人（第 1 跳）
  SELECT followee_id AS uid, 1 AS depth
  FROM follows WHERE follower_id = 1
  UNION ALL
  -- 递归：沿关注边继续走，最多 3 跳
  SELECT f.followee_id, r.depth + 1
  FROM follows f JOIN reach r ON f.follower_id = r.uid
  WHERE r.depth < 3
)
SELECT u.name, MIN(depth) AS min_depth
FROM reach JOIN users u ON u.id = reach.uid
GROUP BY u.name;

Cypher 写法

MATCH (me:User {id: 1})-[:FOLLOWS*1..3]-(f:User)
RETURN f.name, min(length(p)) AS minDepth

（严谨的带最短深度版本：MATCH p=(me:User {id:1})-[:FOLLOWS*1..3]-(f:User) RETURN f.name, min(length(p)) AS minDepth）

差距在哪

维度递归 CTECypher
可读性锚点/递归/终止条件三段式，3 跳就要 20 行一行声明式模式匹配
关系属性边上加属性要建关联表再 JOIN关系直接带属性，随跳过滤
方向控制两张列谁是 follower 要记清楚-> <- - 直观
环处理递归可能死循环，要自己记访问集合引擎自动处理环
多类型边UNION 多个递归分支[:FOLLOWS|:FRIEND*] 一行搞定
执行性能每跳一次自连接 + 中间结果物化指针跳转，无中间物化
但别走另一个极端：图数据库不擅长聚合分析。"统计每个城市所有订单金额并按品类汇总"这种多维分析，列存数仓（ClickHouse）比图快一个数量级。图的正确姿势是"找关系和路径"，不是"算账"。选型前先数一下查询里有多少"跳"。
模块 8

典型场景：权限、风控、知识图谱

细粒度权限
最高频场景。"Alice 能看订单 O-100 吗？"建模为 (用户)-[:成员于]->(组)-[:有权限]->(资源) 的图，一次遍历得到答案，改权限就是改一条边。IAM、数据行级权限的标准解
风控反欺诈
找"欺诈环"：共享设备、共享 IP、共享联系人的账号团伙。环形模式匹配是图的杀手级查询，关系库要 JOIN 几十层
知识图谱
实体-关系-实体，问答推理。配合 NLP 抽取实体入图，回答"岳飞的岳父的儿子的父亲是谁"这类多跳问题
依赖与影响分析
微服务调用链、IT 资产依赖："机房 A 挂了会影响哪些业务？"沿依赖边向下遍历，秒级出爆炸半径
推荐系统
协同过滤的图式表达：共同购买、共同关注的人、最短兴趣路径。实时性好
主数据/血缘
数据表之间的字段级血缘，一条链路出问题能反向定位所有下游报表

权限场景完整示例

# 建模：用户-组-资源，组可嵌套（组也是"成员"）
CREATE (alice:User {name:'Alice'})
CREATE (admins:Group {name:'订单管理员'})
CREATE (super:Group {name:'超级管理员'})
CREATE (o100:Order {id:'O-100', region:'CN'})
CREATE (alice)-[:属于]->(admins)
CREATE (admins)-[:属于]->(super)
CREATE (super)-[:可读]->(:Resource {type:'订单'})

# 鉴权查询：Alice 对某订单的可见性（嵌套组 + 继承一次算完）
MATCH (u:User {name: $username})-[:属于*0..5]->(g:Group)-[:可读]->(r:Resource {type: '订单'})
WHERE r.region = $userRegion OR g.name = '超级管理员'
RETURN DISTINCT r.id
LIMIT 1   // 只要查到一条就放行，命中即返回

# 反向查询："这个订单现在谁能看？"（权限审计，图独有的便利）
MATCH (o:Order {id:'O-100'})<-[:可读*0..5]-(g:Group)<-[:属于*0..5]-(u:User)
RETURN u.name
选型自检：满足这三条再上 Neo4j —— ① 关系本身是核心业务数据（不是附属信息）；② 查询是"多跳遍历/路径/环检测"型；③ 深度会变（今天 2 跳，明年 5 跳）。只满足一两条的话，PostgreSQL + 递归 CTE 或物化路径字段可能就够了，别为了时髦引入新组件。
模块 9

十个线上坑

1
用 CREATE 做幂等写入
重复执行就造重复节点。幂等写必须用 MERGE，且 MERGE 的属性上要有唯一约束兜底，否则并发下照样重复。
2
一次 MERGE 整个长 pattern
节点和关系混在一个 MERGE 里，部分命中时语义失控，可能建出意想不到的边。拆成"先 MERGE 节点，再 MERGE 关系"两步。
3
删节点忘了 DETACH
直接 DELETE 带关系的节点会报错（防止孤儿关系）。要么 DETACH DELETE 节点，要么先删关系。批量删大关系量的节点要分批，防长事务。
4
查询不带标签和起始条件
MATCH (a)-[:R]->(b) 不带标签触发 AllNodesScan，亿级图上直接跑挂。所有查询以"标签 + 属性（走索引）"定位起始节点。
5
变长路径不设上限
[:FOLLOWS*] 不限跳数，遇到环或密集子图就是组合爆炸。永远写 [:TYPE*1..N]，N 按业务最深需求设定。
6
撞上 supernode 而不自知
一个节点挂几百万关系（大 V 粉丝、热门标签），遍历到它的一跳瞬间拉爆内存。按时间/地区拆分关系类型，或加中间节点分层。
7
导入数据一条一个 CREATE
百万级导入逐条执行，几个小时都跑不完。用 LOAD CSV + USING PERIODIC COMMIT 批量导入，或 apoc.periodic.iterate 分批；先建索引再导（否则唯一约束校验也慢）。
8
不用 bookmark，副本读到旧值
写完立刻读，请求被路由到未同步的副本，用户以为数据丢了。用官方驱动 + 因果链（自动带 bookmark）；裸写 Bolt 手动维护。
9
把 Neo4j 当关系库/数仓用
大量单表 CRUD、group by 汇总、报表分析，图库既不比 PostgreSQL 快也不比 ClickHouse 快，还多一套运维。图只干遍历的活。
10
查询字面量写死
MATCH (u:User {email:'a@b.com'}) 字面量不进查询缓存，还容易注入。生产全部参数化 {email: $email}，驱动层自动走计划缓存。
自测

六道题

1. "免索引邻接（index-free adjacency）"指的是什么？
正确答案：节点直接持有关系引用。这是图遍历成本与全图规模无关的原因——代价只在找起始节点时才付（那时才需要索引）。注意起始定位仍然需要索引，"免索引"仅指遍历阶段。
2. 需要"有就复用、没有就创建"的幂等写入，应该用？
正确答案：MERGE + 唯一约束。单独 MERGE 在并发下仍可能重复创建（两个事务同时判定不存在）；唯一约束让数据库在提交时兜底。Cypher 没有 ON CONFLICT 语法，那是 PostgreSQL 的。
3. 找 Alice 到 Dave 的最短关注路径，正确的 Cypher 是？
正确答案：shortestPath 配变长模式。shortestPath 只接受单条关系模式，所以必须写成 -[:FOLLOWS*..6]- 的形式，且必须给出跳数上限。第二项少了 * 会变成固定一跳，第三项不是合法语法。
4. 关于 Neo4j 因果集群，哪个说法正确？
正确答案：core 管共识、副本管读。读副本不投票，挂多少个都不影响集群写入（只影响读容量）；写必须经过 leader 走 Raft 多数派确认，不存在多主合并。这也是"最小 3 个 core"的原因。
5. 为什么删除带关系的节点必须用 DETACH DELETE？
正确答案：防止孤儿关系。DETACH 的作用是先删除该节点的所有关系再删节点本身，不是级联删别的节点。不加 DETACH 会报 Neo.ClientError.Schema.ConstraintValidationFailed 类型的删除错误。大批量删要注意分批，避免长事务。
6. 和关系库的递归 CTE 相比，Cypher 处理多跳遍历的优势是？
正确答案：声明式 + 免索引邻接。同一个 3 跳查询，递归 CTE 要锚点/递归/终止三段共 20 行且每跳一次自连接，Cypher 一行；深度从 3 跳到 10 跳，图库代价仍是走过的子图大小，递归 CTE 则加速恶化。注意 Cypher 不自动去重，要 DISTINCT。

按场景查语句

MATCH (u:User {email:$e}) RETURN u按标签+属性定位节点（走索引）
MATCH (a)-[:FOLLOWS]->(b) RETURN a,b遍历一层有向关系
MATCH (a)-[:FOLLOWS*1..3]-(b) RETURN b1~3 跳变长遍历（必须设上限）
MATCH p=shortestPath((a)-[*..6]-(b)) RETURN p最短路径
MERGE (u:User {email:$e}) ON CREATE SET ... ON MATCH SET ...幂等写入（配唯一约束）
MATCH (u) DETACH DELETE u删节点及其所有关系
CREATE CONSTRAINT ... REQUIRE u.email IS UNIQUE唯一约束（自动建索引）
EXPLAIN / PROFILE MATCH ...看查询计划与实际 db hits
CALL dbms.cluster.overview()集群拓扑与角色
LOAD CSV WITH HEADERS FROM 'url' AS row ...CSV 批量导入（配 PERIODIC COMMIT）
CALL db.awaitIndex('name', 300)等索引建完再跑查询
MATCH (n) DETACH DELETE n清空全库（练习前重置数据）
