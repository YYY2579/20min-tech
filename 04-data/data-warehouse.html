模块 1

数仓是什么：与 OLTP 的本质区别

Inmon 的定义：数据仓库是一个面向主题的、集成的、非易失的、时变的数据集合，用于支持管理决策。四个词逐个拆开都有工程含义。

特性工程含义反面教材
面向主题按分析对象组织（会员、交易、商品），不按业务功能（下单、支付）把 50 张业务表原样搬进 Hive 就叫数仓
集成多个来源（订单库、支付库、CRM、埋点）统一编码、统一口径后进入同一用户 ID 在订单库是 user_id、在 CRM 是 uid，直接 JOIN 对不上
非易失只追加和批量更新，不单行 UPDATE/DELETE，保留历史快照用 UPDATE 覆盖历史数据的表，回溯不了上月状态
时变每个数据都带时间维度（dt 分区），任意时刻的状态可重建只有最新值的快照表，无法回答"上周这个用户是什么等级"

OLTP vs OLAP

维度OLTP（业务库）OLAP（数仓）
典型操作按主键点查、单行增改全表/分区扫描 + 聚合（group by 千万行）
数据模型三范式 ER，减少冗余维度建模星型，故意冗余换取查询简单
存储行存（B+ 树）列存为主（Parquet/ORC），压缩比 5~10 倍
数据范围当前值全历史（3 年常见）
写入方式高并发小事务批量 T+1 / 小时级调度任务
关注点一致性、并发、延迟吞吐、口径、血缘、可回溯
# 一个直观的体量对比（同一份 1 亿行订单数据）
MySQL 行存原始大小          ≈ 60 GB
Hive Parquet 列存 + 压缩    ≈ 6 GB      -- 只扫 amount 一列时读 < 1 GB
# 列存的收益来自：按需读列 + 同列同类型压缩率高（如 status 只有 4 个值）
模块 2

维度建模：事实表与维度表

Kimball 的核心思想：把所有业务拆成"谁在什么时候对什么做了多少"——度量存事实表，各种"谁/什么/何时"存维度表。

事实表三分类（高频考点）

类型粒度与行含义典型例子
事务事实表一个事务/事件一行，最稀疏。事件发生那一刻的状态，之后不再更新订单流水、支付流水、埋点事件
周期快照事实表固定周期一行，记录周期末的状态（余额、库存余量）每日库存快照、每月账户余额、每日用户余额表
累积快照事实表一个完整业务过程一行，跨越多个时间点，每里程碑更新一次日期字段订单（下单→支付→发货→签收→售后，一行多个时间戳）
-- 事务事实表：dwd_trade_order_detail，一行 = 一个订单
CREATE TABLE dwd_trade_order_detail (
  order_id     BIGINT,      -- 退化维度（无维度表，直接放事实表）
  user_sk      BIGINT,      -- 代理键，指向 dim_user
  shop_sk      BIGINT,
  product_sk   BIGINT,
  date_sk      INT,         -- 日期代理键，如 20261015
  amount       DECIMAL(12,2),-- 可加性度量
  quantity     INT,          -- 可加性度量
  discount     DECIMAL(12,2),-- 半可加性（不可按用户跨期汇总）
  status       VARCHAR(16),   -- 当前状态，历史状态看流水
  create_time  TIMESTAMP
) PARTITIONED BY (dt STRING);   -- Hive 方言：MySQL 用分区表或按 dt 分表

-- 周期快照事实表：一天一行，覆盖式写（库存这种不能只记流水）
CREATE TABLE dwd_stock_daily_snapshot (
  product_sk   BIGINT,
  warehouse_sk BIGINT,
  date_sk      INT,
  stock_qty    INT,      -- 期末库存：不可跨天累加！
  locked_qty   INT,
  in_qty       INT,      -- 当日入库：可加性
  out_qty      INT       -- 当日出库：可加性
) PARTITIONED BY (dt STRING);

-- 累积快照事实表：一行贯穿订单全生命周期，里程碑日期逐次更新
CREATE TABLE dws_trade_order_accum (
  order_id     BIGINT PRIMARY KEY,
  user_sk      BIGINT,
  amount       DECIMAL(12,2),
  create_time  TIMESTAMP,   -- 里程碑 1：下单
  pay_time     TIMESTAMP,   -- 里程碑 2：支付（可能为 NULL）
  ship_time    TIMESTAMP,   -- 里程碑 3：发货
  finish_time  TIMESTAMP,   -- 里程碑 4：签收
  refund_time  TIMESTAMP,   -- 里程碑 5：退款（部分单无）
  dt           STRING         -- 最后更新日期
);
怎么判断用哪种事实表？三个问题：① 事件会多次发生吗（每次一行 → 事务）？② 要记录每个周期末的状态吗（→ 周期快照）？③ 一个业务对象有明确的开始-结束流程且中间态要暴露吗（→ 累积快照）？
订单表在建模时通常两个都要建：DWD 放事务流水（可加、可追溯），DWS 放累积快照（供"订单转化漏斗"分析）。

维度表与代理键

-- 维度表不用业务主键做主键，用无意义的代理键（surrogate key）
CREATE TABLE dim_user (
  user_sk      BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 代理键
  user_id      BIGINT NOT NULL,                  -- 业务主键（自然键）
  user_name    VARCHAR(64),
  city         VARCHAR(64),
  level        VARCHAR(16),
  start_date   DATE,                          -- SCD2 生效日期
  end_date     DATE                           -- SCD2 失效日期
);

-- 为什么用代理键：业务主键会被复用/回收（手机号注销再注册），
-- 且 SCD2 下一个 user_id 对应多行历史，必须靠代理键区分版本
模块 3

缓慢变化维 SCD 与拉链表

维度表也会变：用户改了城市、商品换了类目、员工调了部门。问题是历史事实按哪个版本关联。三种标准解法 + 一种极限方案。

方式实现保留历史代价
SCD 1直接 UPDATE 覆盖旧值不保留，报表按新值回溯会得到错误历史最简单，行数不膨胀
SCD 2INSERT 新行 + start_date/end_date 标记版本区间全量保留，事实表按生效日期关联对应版本行数随时间线性膨胀，需拉链表/分区控制
SCD 3加一列存"上一个值"（current_city, prev_city）只保留上一个版本只适合"只看上一版"的窄场景，列数受限
拉链表SCD 2 的分区优化版：按天分区，每天只产出变化的行全量保留每日合并任务逻辑复杂，是全公司最核心的几张大表

拉链表每日增量合并（真实 SQL）

-- 目标：dim_user_zipper，分区 dt，每行带 start_date/end_date
-- 输入：ods_user_snapshot（每日全量快照，dt 分区）

-- Step 1: 找出"变化的用户" = 今日快照与当前生效版本不一致
WITH cur AS (
  SELECT user_id, user_name, city, level
  FROM dim_user_zipper
  WHERE end_date = '9999-12-31'          -- 9999-12-31 表示"当前生效"
), snap AS (
  SELECT user_id, user_name, city, level
  FROM ods_user_snapshot
  WHERE dt = '2026-10-16'
)
SELECT s.user_id
FROM snap s LEFT JOIN cur c ON s.user_id = c.user_id
WHERE c.user_id IS NULL                          -- 新用户
   OR s.user_name <> c.user_name
   OR s.city      <> c.city
   OR s.level     <> c.level;                  -- 属性变化

-- Step 2: 变化用户旧版本封口（end_date 改为昨日）
INSERT OVERWRITE TABLE dim_user_zipper PARTITION (dt = '2026-10-16')
SELECT user_sk, user_id, user_name, city, level, start_date,
       CASE WHEN user_id IN (变更用户集合) THEN '2026-10-15' ELSE end_date END AS end_date
FROM dim_user_zipper WHERE dt = '2026-10-15';

-- Step 3: 变化用户写入新版本（start_date = 今日，end_date = 9999-12-31）
INSERT INTO dim_user_zipper PARTITION (dt = '2026-10-16')
SELECT NULL, user_id, user_name, city, level,
       '2026-10-16' AS start_date, '9999-12-31' AS end_date
FROM ods_user_snapshot WHERE dt = '2026-10-16'
  AND user_id IN (变更用户集合);

-- 查询：取用户在 2026-09-01 时的等级（SCD2 的正确姿势）
SELECT level FROM dim_user_zipper
WHERE user_id = 88
  AND start_date <= '2026-09-01' AND end_date > '2026-09-01';

-- 或关联事实表：按订单发生日期对齐维度版本
SELECT f.order_id, f.amount, d.city
FROM dwd_trade_order_detail f
JOIN dim_user_zipper d
  ON f.user_sk = d.user_sk
 AND f.date_sk BETWEEN d.start_date AND d.end_date;  -- 事实发生时点的维度版本
拉链表最大的坑：删除用户。快照表里用户没了，拉链表只会追加新版本，永远不会把 end_date 封口，导致该用户永远显示为"当前有效"。正确处理：合并任务里做一次"快照全量 user_id LEFT JOIN 拉链表当前版本"，把快照中不存在的用户封口为昨日。漏了这步，DAU 里会永远躺着注销用户。
模块 4

星型 / 雪花 / 星座模型

模型结构存储适用
星型一张事实表 + 若干张非规范化宽维度表（城市信息直接冗余在用户维度里）维度冗余大默认选择：JOIN 少、查询快、业务好理解
雪花维度再规范化拆子表（用户 → 城市 → 省 → 大区）省存储维度层级复杂且需严格一致（如行政区划）
星座多个事实表共享同一组维度表（订单、物流、退款都关联 dim_user）—成熟数仓的必然形态，保证跨主题口径一致
-- 星型：dim_shop 里冗余了 city、province、region，查区域销售一次 JOIN
SELECT d.province, SUM(f.amount)
FROM dwd_trade_order_detail f
JOIN dim_shop d ON f.shop_sk = d.shop_sk
GROUP BY d.province;                      -- 1 次 JOIN 搞定

-- 雪花：dim_shop 只存 city_sk，再 JOIN dim_city、dim_province
SELECT p.province, SUM(f.amount)
FROM dwd_trade_order_detail f
JOIN dim_shop s ON f.shop_sk = s.shop_sk
JOIN dim_city c ON s.city_sk = c.city_sk
JOIN dim_province p ON c.province_sk = p.province_sk
GROUP BY p.province;                      -- 3 次 JOIN，但行政区划全库只有一份
实践结论：维度建模默认用星型（宽维度表），因为数仓的瓶颈是"人写 SQL 写不对"，不是存储。只有行政区划、组织机构这类"一处改处处跟着改"的强一致层级才用雪花拆子表。星座是共享维度的自然结果，不需要刻意设计——只要所有主题的 dim_user 是同一张表，星座自动成立。
模块 5

四层架构：ODS / DWD / DWS / ADS

分层的目的是依赖单向、复用逐层沉淀、问题逐层隔离。数据只能从上往下流，任何一层不许跨层引用。

层职责粒度硬性规矩
ODS
贴源层		业务库数据原样落地，只做格式转换与源表一行一行对齐不做清洗、不改写、不删历史；按 dt 分区
DWD
明细层		清洗（去重、空值处理、单位统一）、维度退化、拉宽成宽表一行一个事件/明细不做聚合；字段命名全公司统一
DWS
汇总层		按主题轻度汇总，沉淀通用指标一行一个"主题 × 周期 × 维度组合"只做 GROUP BY 聚合；不写复杂 CASE 业务逻辑
ADS
应用层		面向具体报表/接口/画像的高聚合结果一行一个指标值允许反规范化；表随应用生命周期消亡
-- 一条数据从 ODS 流到 ADS 的完整链路（日活场景）

-- ODS：埋点日志原样落盘
CREATE TABLE ods_log_event (event_name STRING, user_id BIGINT, ts BIGINT, props MAP<STRING,STRING>)
PARTITIONED BY (dt STRING);

-- DWD：清洗 + 统一编码（事件名小写、user_id 转 0 兜底、时间转东八区日期）
INSERT INTO dwd_user_event_detail PARTITION (dt = '${date}')
SELECT
  LOWER(event_name)                          AS event_name,
  COALESCE(user_id, -1)                      AS user_id,   -- 未登录标 -1
  FROM_UNIXTIME(ts/1000, 'yyyy-MM-dd')        AS event_date,
  ROW_NUMBER() OVER (PARTITION BY event_name, user_id, ts) AS rn
FROM ods_log_event WHERE dt = '${date}';
-- rn = 1 过滤掉重复上报（Hive 用 QUALIFY 或子查询）

-- DWS：按用户 × 日轻度汇总
INSERT INTO dws_user_daily_summary PARTITION (dt = '${date}')
SELECT user_id, event_date,
       COUNT(DISTINCT CASE WHEN event_name = 'app_launch' THEN ts END) AS launch_cnt,
       MAX(ts) AS last_active_ts
FROM dwd_user_event_detail WHERE dt = '${date}'
GROUP BY user_id, event_date;

-- ADS：直接服务"日活看板"
INSERT INTO ads_dau_daily PARTITION (dt = '${date}')
SELECT event_date,
       COUNT(DISTINCT user_id) AS dau,
       COUNT(DISTINCT CASE WHEN last_active_ts > 0 THEN user_id END) AS active_users
FROM dws_user_daily_summary WHERE dt = '${date}'
GROUP BY event_date;
分层是纪律不是形式：ADS 直接 JOIN ODS 是经典事故——源表改一个字段，十几个报表同时挂。正确做法：ADS 只依赖 DWS，DWS 只依赖 DWD，DWD 只依赖 ODS，调度系统要配置成"不允许跨层依赖"，越层即报警。
模块 6

指标体系：一个口径走全公司

数仓最大的价值不是快，是口径一致。"GMV 到底含不含退款"这种问题，靠指标分层的定义一次性解决。

概念定义例子
原子指标不可再拆的业务度量，只有"名词"没有"限定"支付金额、订单数、退款金额
业务限定修饰原子指标的维度条件（渠道 = App）、（品类 = 数码）
时间周期统计的时间范围近 1 天、近 7 天、自然月、年初至今
派生指标原子指标 + 时间周期 + 若干业务限定近 7 天 App 渠道数码品类支付金额
复合指标派生指标之间的运算（比值、差、条件组合）支付转化率 = 支付人数 / 访客数
一致性指标全公司唯一一份定义的派生/复合指标，一处定义多处引用指标字典里的"官方 GMV"
-- 派生指标的落地：把"时间周期"做成分区/字段，而不是每次现算
-- DWS 表：一行 = 一个（用户 × 日期）的原子指标组合
CREATE TABLE dws_user_order_1d (
  user_id     BIGINT,
  dt          STRING,
  order_cnt   INT,          -- 原子指标：订单数
  order_amt   DECIMAL(12,2),-- 原子指标：下单金额
  pay_cnt     INT,          -- 原子指标：支付订单数
  pay_amt     DECIMAL(12,2),-- 原子指标：支付金额
  refund_amt  DECIMAL(12,2) -- 原子指标：退款金额
);

-- 派生指标"近 7 天支付金额"：对原子指标做 7 天窗口求和
SELECT user_id, SUM(pay_amt) AS pay_amt_7d
FROM dws_user_order_1d
WHERE dt BETWEEN '2026-10-10' AND '2026-10-16'
GROUP BY user_id;

-- 复合指标"支付转化率"：两个派生指标相除，必须在同一维度粒度上
SELECT
  SUM(pay_cnt) * 100.0 / NULLIF(SUM(order_cnt), 0) AS pay_cvr
FROM dws_user_order_1d
WHERE dt = '2026-10-16';
-- NULLIF 防除零；比率型指标禁止"先算比率再平均"（辛普森陷阱）
一致性指标的落地手段：① 建指标字典（每个指标一行：名称、SQL 表达式、负责人、依赖表）；② DWS 层的原子指标全公司共用，报表只准引用 DWS；③ 指标变更走"版本化"：改口径必须加后缀（pay_amt_v2），旧报表继续引用旧列，禁止原地改列语义。
模块 7

调度依赖与数据质量监控

数仓是个 DAG：上游没跑完，下游跑了就是错数。调度的核心是依赖表达，质量的核心是在错数流出前拦住。

依赖编排的三个层次

天级依赖：ADS 依赖 DWS 当日分区，DWS 依赖 DWD 当日分区，DWD 依赖 ODS 当日分区。最小单位是"一个分区一天"，表达为 ds = '${date}'
跨周期依赖：周期快照要"昨天分区存在"才能算环比；月报要等本月所有天分区就绪。漏配这类依赖是月初月报空跑的头号原因
外部依赖：等业务库 binlog 同步完成（如 Canal 延迟告警）、等上游团队交付。用"信号任务"表达，别用 sleep 猜时间
# Airflow / DolphinScheduler 里依赖的典型写法（伪代码）
ods_task >> dwd_task >> dws_task >> ads_task
dwd_task >> dws_task_7d_window        -- 跨周期：7 天窗口要等 dwd 连续 7 天分区
dws_task >> ads_monthly_report         -- 月报依赖本月全部天分区

# 关键参数：失败重试、超时告警、上游失败不跑下游（默认行为）
retries: 3
retry_delay: 5m
execution_timeout: 2h
# 上游失败时下游的正确行为是"不执行"而不是"用空分区执行"

数据质量六类规则

规则类型检查什么典型阈值
完整性行数、字段非空率、分区是否产出行数同比波动 > ±30% 告警
唯一性主键/代理键是否唯一COUNT(*) vs COUNT(DISTINCT key) 不等即失败
一致性跨表关联：事实表的维度键必须能在维度表找到孤儿记录 > 0.1% 告警
值域枚举值、数值范围、时间合法性status 出现枚举外取值即失败
及时性任务完成时间是否在 SLA 内日报 > 次日 09:00 未完成即告警
准确性与业务系统对账（金额、笔数）差异 > 1 笔即失败并阻断下游
-- 常用的四条质量检查 SQL（可直接进调度前置/后置节点）
-- 1. 主键唯一性
SELECT COUNT(*) - COUNT(DISTINCT order_id) AS dup_cnt
FROM dwd_trade_order_detail WHERE dt = '${date}';        -- 必须为 0

-- 2. 行数波动（与昨天同时点比）
SELECT t.cnt / y.cnt - 1 AS ratio
FROM (日分区行数) t, (前一天行数) y;                          -- ABS(ratio) < 0.3

-- 3. 孤儿维度键
SELECT COUNT(*) FROM dwd_trade_order_detail f
LEFT JOIN dim_user d ON f.user_sk = d.user_sk
WHERE d.user_sk IS NULL;                              -- 必须为 0

-- 4. 值域检查
SELECT COUNT(*) FROM dwd_trade_order_detail
WHERE status NOT IN ('CREATED','PAID','SHIPPED','FINISHED','REFUNDED');
质量检查的接入方式：① 每个核心表后面挂"质量任务"，失败即阻断下游（fail fast）；② 用开源框架（Great Expectations、Deequ）把规则配置化，别每个表手写一套；③ 质量规则本身要版本化——提高阈值前先看历史分布，防止告警风暴。

Kimball vs Inmon：路线之争

维度Kimball（自底向上）Inmon（自顶向下）
出发点维度建模，数据集市优先，总线架构（bus matrix）协调企业级 ER 建模，先建 3NF 的中心 EDW，再派生数据集市
建设顺序先部门集市（快），汇总成企业仓库先企业仓库（慢），再建集市
规范化星型，维度宽表冗余3NF 强规范化，无冗余
见效周期数周~数月出第一个报表数月~数年才见效
灵活性需求驱动，加主题加集市模型稳定，但前期需求收集极重
适合互联网、快速迭代、需求多变大型传统企业、强监管、数据源极多且杂
代表作《数据仓库工具箱》（Kimball & Ross）《数据仓库》（Inmon）
# 两者在今天的融合形态（业界主流做法）
ODS（贴源，3NF 风格）
  ↓ 清洗
DWD（明细，Kimball 维度建模）
  ↓ 汇总
DWS（轻度汇总，兼顾 Inmon 的一致性）

深坑

十个线上坑

1
把业务库三范式原样搬进数仓
50 张表 JOIN 出结果，业务看不懂、查询慢到超时、改一个字段全链路抖。数仓要星型建模：一行一个事件 + 宽维度表，用冗余换简单。
2
DWD 层就开始做聚合
明细层按天汇总之后，下游要按小时/按门店的维度就再也拆不出来了。DWD 必须保留最细粒度，聚合全部下沉到 DWS。
3
拉链表漏处理"删除用户"
快照里消失的用户，拉链表永远不会封口，永远显示当前有效，DAU 里永远躺着注销用户。合并任务必须做一次"快照全量 LEFT JOIN 当前版本"补齐封口。
4
维度表用 UPDATE 覆盖（SCD1 滥用）
用户改城市后直接 UPDATE，历史订单的 city 全变成新城市，"上月北京的单"变出上海的量。需要历史回溯的维度必须 SCD2。
5
同名指标多套口径
支付金额在交易组含退款、在财务组不含、在 BI 组含未支付。必须建指标字典 + 一致性指标，改口径要版本化（pay_amt_v2），禁止原地改列语义。
6
分区裁剪失效：WHERE 条件加了函数
写 WHERE from_unixtime(ts/1000,'yyyy-MM-dd')='2026-10-16'，Hive 无法静态推断分区，全表扫描 3 年分区。必须写 WHERE dt='2026-10-16'，让分区裁剪生效。
7
调度只配一级依赖，没有跨周期和外部依赖
月报月初空跑、7 天窗口任务用 3 天分区算出"近 7 天"。依赖必须显式声明：分区级、跨周期级、外部信号级，别用 sleep 猜。
8
只监控任务失败，不监控数据对不对
任务全绿但产出 10 万行垃圾（上游空投递）。核心表必须配行数波动、主键唯一、孤儿键、值域检查，失败即阻断下游。
9
小文件问题
每小时一个分区、每分区 50KB，一天 24 个小文件，一年后 HDFS NameNode 被几千万文件压垮，每个查询调度开销比计算还大。用合并任务（INSERT OVERWRITE 合并）或调大文件尺寸（hive.merge.size）。
10
ADS 层只增不减
每个需求新建一张 ADS 表，三年后 800 张表、一半没人查，但每天还在跑调度烧资源。ADS 表要标注需求方和下线日期，无人使用 90 天自动下线。
自测

六道题

1. "每日每个仓库的期末库存"应该建成哪种事实表？
正确答案：周期快照事实表。库存是"状态量"不是"事件"，每个周期末拍一行，行里有可加性度量（当日入/出库量）和不可加性度量（期末库存余额）。事务事实表适合支付流水这类离散事件。
2. 用户改了城市，要求"历史订单的收货城市按当时值统计"，用什么方案？
正确答案：SCD2。它保留每个历史版本，事实表按订单发生日期关联对应版本，历史统计才准确。SCD1 丢历史、SCD3 只保留上一个版本，都做不到任意时点回溯。
3. 星型模型和雪花模型的核心区别是？
正确答案：维度是否规范化。星型维度是宽表（城市、省份冗余在一起），JOIN 少查询快；雪花把维度拆成规范化的层级子表，省存储但 JOIN 多。数仓默认选星型。
4. DWD 明细层的核心职责是？
正确答案：清洗 + 最细粒度明细。DWD 严禁聚合（那是 DWS 的事），也严禁原样照搬（那是 ODS 的事）。它做的是"干净的一行一个事件"，是全公司的明细数据底座。
5. 拉链表（zipper table）主要解决什么问题？
正确答案：SCD2 的低成本实现。它每天只把变化的维度行写入分区，旧版本封口、新版本开口，比"每天全量快照"省 90%+ 存储。代价是合并逻辑复杂，且必须处理"快照中消失的用户"。
6. Kimball 与 Inmon 的核心差异是？
正确答案：建设顺序与出发点不同。Kimball 从数据集市出发、维度建模、快速见效；Inmon 先建规范化的企业级数据仓库再派生集市、周期长但模型稳。与行/列存储无关；适用企业规模也说反了。

按场景查写法

PARTITIONED BY (dt STRING)Hive 表分区标准写法，WHERE dt='...' 才能裁剪
INSERT OVERWRITE TABLE ... PARTITION(dt='${date}')按分区覆盖写，拉链表每日合并的核心句式
ROW_NUMBER() OVER (PARTITION BY key) rn去重：取 rn=1，DWD 清洗标配
end_date = '9999-12-31'拉链表"当前生效版本"的哨兵值约定
COUNT(*) - COUNT(DISTINCT key)唯一性质量检查，必须为 0
LEFT JOIN dim ... WHERE dim.sk IS NULL孤儿维度键检查，必须为 0

# 一条链路的建表口径速记
ODS  原样落地      源表字段一个不少，只转格式，按 dt 分区
DWD  清洗 + 宽表    一行一事件，维度退化（维度键冗余进事实），零聚合

术语表

术语一句话解释
维度建模Kimball 的核心方法：度量进事实表，描述进维度表
事实表存度量（可加数值）的表，行数巨大，只追加不更新
维度表存"谁/什么/何时"描述属性的表，行数小，会缓慢变化
事务事实表一个事件一行，最稀疏、最常用
周期快照事实表固定周期末拍一行状态，适合库存/余额
累积快照事实表一个业务全过程一行，多个里程碑日期逐步更新
代理键维度表无意义自增主键，隔离业务主键变化与历史版本
退化维度没有维度表的维度（如订单号），直接放事实表
可加性度量能否跨维度/时间相加：可加、半可加（库存）、不可加（比率）
SCD缓慢变化维：维度属性随时间变化的处理策略
SCD1/2/3覆盖 / 加行保版本 / 加列保上一版
拉链表SCD2 的分区实现：每日只产出变化行，历史全保留
星型 / 雪花 / 星座宽维度 / 规范化维度子表 / 多事实共享维度
ODS / DWD / DWS / ADS贴源 / 明细 / 汇总 / 应用四层
原子指标不可再拆的业务度量，如支付金额
派生指标原子指标 + 时间周期 + 业务限定，如近 7 天 App 支付金额
复合指标派生指标间的运算，如转化率 = 支付人数/访客数
一致性指标全公司唯一口径的指标，一处定义多处引用
分区裁剪WHERE dt 条件让引擎只读相关分区，数仓性能第一杠杆
Kimball / Inmon自底向上集市优先 / 自顶向下 EDW 优先两派
