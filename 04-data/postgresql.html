准备环境与阅读姿势

方式怎么做
最省事浏览器搜 "online postgres playground"，打开即可用，无需安装
推荐用 Docker 一条命令起一个：docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=123456 postgres
本地安装装 PostgreSQL 后自带一个命令行客户端 psql，也推荐装图形工具 pgAdmin 或 DBeaver

连接：

psql -h 127.0.0.1 -U postgres -d postgres
# psql 里以反斜杠开头的是元命令，不是 SQL：
# \l 列出所有库   \dt 列出表   \d 表名 看表结构   \du 看用户   \q 退出
三条会立刻绊倒你的 PostgreSQL 特性：
① 字符串用单引号，双引号是给"标识符"（表名、列名）用的 —— 和 MySQL 的反引号不同。
② 标识符默认转小写。你写 SELECT * FROM Users，PG 会去找名为 users 的表。想保留大写必须加双引号，但那会带来无穷麻烦，建议全程小写下划线命名。
③ 默认隔离级别是"读已提交"，不是 MySQL 的"可重复读"。这个差异会真实影响你的代码，第 7 模块详说。
模块 1

为什么选 PostgreSQL

两者都能扛住绝大多数业务。差别在于：PG 更像一个"什么都能干"的平台，MySQL 更像一个"专注读写的引擎"。

维度MySQLPostgreSQL
默认隔离级别可重复读读已提交
连接模型一个连接一个线程一个连接一个进程（更重，必须用连接池）
回收机制后台 purge 线程自动清理需要 VACUUM，配不好会表膨胀
索引类型基本只有 B+ 树B-tree / GIN / GiST / BRIN / Hash 五种
JSON 支持有 JSON 类型，索引能力有限JSONB 可完整索引、可任意路径查询
数组类型不支持原生支持，可索引
层级结构库 → 表库 → 模式 schema → 表
字符串类型char/varchar/text 有性能差异三者性能完全相同，推荐一律用 text
UPSERTON DUPLICATE KEY UPDATEON CONFLICT DO UPDATE
分页LIMIT 偏移, 条数LIMIT 条数 OFFSET 偏移
什么时候该选 PG：需要复杂查询（窗口函数、CTE）、需要 JSON + 关系混合建模、需要地理数据（PostGIS）、需要严格的数据一致性、或者做数据分析类场景。
什么时候 MySQL 也够：典型 Web 业务的增删改查，生态和运维人才更成熟。
模块 2

三层结构：库 → 模式 → 表

MySQL 是"库 → 表"两层，PG 多了一层 schema（模式）。这一层不是多余的，它让你能在同一个库里做逻辑分区。

-- 建库（PG 里库和 MySQL 一样是物理隔离的）
CREATE DATABASE shop;

-- 建模式：相当于库内的一个命名空间
CREATE SCHEMA sales;
CREATE SCHEMA hr;

-- 同一个库里的两张同名表，靠 schema 区分
CREATE TABLE sales.users (...);
CREATE TABLE hr.users    (...);

-- 搜索路径：不写 schema 时按这个顺序找
SHOW search_path;              -- 默认 "$user", public
SET search_path TO sales, public;
实用价值：多租户系统可以每个租户一个 schema（隔离性好），或者用 schema 把"业务表"和"运维表"分开。默认那个 public 模式就是你不写 schema 时用的。
模块 3

数据类型：PostgreSQL 的护城河

这是 PG 和 MySQL 拉开差距最明显的地方。别的数据库存不了的东西，PG 原生就能存。

数值

类型说明
smallint / int / bigint2 / 4 / 8 字节整数
numeric(10,2)精确小数，存钱只用它（等价于 MySQL 的 DECIMAL）
real / double precision浮点数，有精度误差，别用来存金额
GENERATED ALWAYS AS IDENTITY自增主键的标准写法（PG 10+）。老代码里的 serial 是历史遗留

文本

PG 的一个重要差异：char(n)、varchar(n)、text 三者的存储和性能完全相同。带长度限制的版本只是加了个约束检查。所以 PG 社区的主流做法是：一律用 text，长度约束交给 CHECK 或应用层。

另外 citext 扩展提供大小写不敏感的文本类型，处理邮箱地址很省事。

时间

类型说明
timestamptz带时区的时间戳，业务首选。内部统一存 UTC，显示时按会话时区转换
timestamp不带时区，存"墙上时间"。跨时区场景慎用
date / time只有日期 / 只有时间
interval时间间隔，可以直接参与运算
SELECT now() + interval '7 days';        -- 七天后的此刻
SELECT now() - created_at AS 已注册时长 FROM users;

JSONB：让 PG 同时当文档数据库用

类型存储方式特点
json原始文本保留键顺序和空格，每次访问都要重新解析，不能建索引
jsonb二进制解析后不保留键顺序、会去重键，可以建 GIN 索引，查询快得多

除非你需要原样保存 JSON 文本，否则一律用 jsonb。

CREATE TABLE events (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  data jsonb
);

INSERT INTO events (data) VALUES ('{"user": 1, "tags": ["a","b"], "score": 90}');

-- ->  取出仍是 jsonb     ->> 取出为文本
SELECT data->>'user' AS 用户, data->'tags' AS 标签 FROM events;

-- @> 是"包含"操作符，这是 jsonb 最强的地方
SELECT * FROM events WHERE data @> '{"user": 1}';

-- 给 jsonb 建 GIN 索引，上面这种查询就能走索引
CREATE INDEX idx_events_data ON events USING gin (data);
这条路线很实用：核心字段用普通列（可约束、可索引），灵活多变的扩展字段塞进一个 jsonb 列。既享受关系型的严谨，又保留文档型的灵活，不用为了几个字段就加一张表。

数组

CREATE TABLE posts (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tags text[]
);

INSERT INTO posts (tags) VALUES (ARRAY['python','sql']);

-- 操作符：@> 包含   <@ 被包含   && 有交集
SELECT * FROM posts WHERE tags @> ARRAY['python'];
SELECT * FROM posts WHERE tags && ARRAY['python','go'];

-- 展开数组为多行，再聚合回去
SELECT id, unnest(tags) AS tag FROM posts;

CREATE INDEX idx_posts_tags ON posts USING gin (tags);

其他"别的数据库没有"的类型

类型用途
uuid分布式场景的主键，用 gen_random_uuid() 生成（PG 13+ 内置）
boolean真布尔类型，不是 0/1 的伪装
枚举（enum）自定义取值集合，如状态字段
range范围类型，如 tstzrange。用来做"时间段不重叠"的约束非常优雅
inet / cidr / macaddrIP 地址和网段，可直接做包含判断
tsvector全文检索的专用类型
几何类型点、线、多边形，PostGIS 扩展更是地理信息领域的标准
-- 范围类型实战：会议室预订，保证同一会议室时间段不重叠
CREATE TABLE bookings (
  room   text,
  during tstzrange,
  EXCLUDE USING gist (room WITH =, during WITH &&)
);
-- EXCLUDE 让数据库自己拒绝了所有时间冲突的预订，应用层不用写任何判断
-- 注意 USING gist：EXCLUDE 约束依赖 GiST 索引才能工作（GiST 是模块 6 讲的五种索引之一）
模块 4

建表与六种约束

CREATE TABLE orders (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  order_no   text NOT NULL UNIQUE,
  amount     numeric(10,2) NOT NULL CHECK (amount > 0),
  status     text DEFAULT 'pending',
  created_at timestamptz DEFAULT now()
);

COMMENT ON TABLE orders IS '订单主表';
约束作用
PRIMARY KEY主键，唯一且非空
NOT NULL不允许为空
UNIQUE值不能重复（注意：多个 NULL 不算重复）
CHECK自定义条件，如 amount > 0、status IN (...)
FOREIGN KEY外键，保证引用完整性。ON DELETE CASCADE 表示主表删除时子表跟着删
EXCLUDEPG 独有。用操作符表达"任意两行不能同时满足某关系"，配合 GiST 索引使用
关于外键的取舍：外键能让数据库帮你守住数据一致性，但会给写入带来额外开销，且在高并发下可能引发锁竞争。互联网大厂的常见做法是不用数据库外键，靠应用层保证。小项目、内部系统建议用上 —— 免费的保险为什么不买。
模块 5

查询进阶：PG 真正拉开差距的地方

基础的 SELECT / WHERE / JOIN 语法和 MySQL 一致，这里不再重复。本模块只讲 PostgreSQL 独有的强力武器 —— 这些才是它真正拉开差距的地方。

窗口函数：分组内计算，但不合并行

聚合（GROUP BY）会把多行压成一行；窗口函数保留每一行，同时算出分组统计值。这是做排行榜、同环比、累计值的标准工具。

SELECT
  name,
  dept,
  salary,
  RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS 部门内排名,
  SUM(salary) OVER (PARTITION BY dept) AS 部门总薪资,
  ROUND(salary * 100.0 / SUM(salary) OVER (PARTITION BY dept), 1) AS 占比百分比,
  LAG(salary) OVER (PARTITION BY dept ORDER BY salary) AS 上一档薪资
FROM employees;
函数作用
ROW_NUMBER()连续序号，1 2 3 4，不并列
RANK() / DENSE_RANK()并列时跳号（1 2 2 4）/ 不跳号（1 2 2 3）
LAG() / LEAD()取上一行 / 下一行的值，做环比必备
SUM() OVER (ORDER BY ...)累计求和（不加 ORDER BY 则是全组求和）
FIRST_VALUE() / LAST_VALUE()取组内第一 / 最后一个值
经典用法：取每组里最新的一条（比如每个用户最近一笔订单）—— 用窗口函数编号再筛，比写子查询干净得多：
SELECT * FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) rn FROM orders) t WHERE rn = 1;

CTE（WITH 子句）：把查询拆成可读的步骤

WITH 活跃用户 AS (
  SELECT user_id, COUNT(*) AS 订单数
  FROM orders
  WHERE created_at > now() - interval '30 days'
  GROUP BY user_id
),
高价值 AS (
  SELECT * FROM 活跃用户 WHERE 订单数 >= 5
)
SELECT u.name, h.订单数
FROM 高价值 h JOIN users u ON u.id = h.user_id;

递归 CTE 能处理树形结构（组织架构、评论楼中楼、分类目录）：

WITH RECURSIVE 下属 AS (
  SELECT id, name, manager_id, 1 AS 层级 FROM employees WHERE id = 1
  UNION ALL
  SELECT e.id, e.name, e.manager_id, d.层级 + 1
  FROM employees e JOIN 下属 d ON e.manager_id = d.id
)
SELECT * FROM 下属 ORDER BY 层级;

DISTINCT ON：PG 独有，取每组第一条

-- 每个部门薪资最高的那个人（MySQL 里要写一堆子查询）
SELECT DISTINCT ON (dept) dept, name, salary
FROM employees
ORDER BY dept, salary DESC;
注意：ORDER BY 必须以 DISTINCT ON 里的列开头，否则结果不确定 —— 它取的是"排序后每组的第一条"。

UPSERT：有则更新，无则插入

INSERT INTO counters (name, cnt) VALUES ('pv', 1)
ON CONFLICT (name) DO UPDATE SET cnt = counters.cnt + 1;

-- 或者干脆什么都不做
INSERT INTO tags (name) VALUES ('python')
ON CONFLICT (name) DO NOTHING;

原子操作，不会有并发竞态。前提是 name 列上有唯一约束或主键。

RETURNING：写操作顺便把结果拿回来

INSERT INTO users (name) VALUES ('张三') RETURNING id, created_at;
UPDATE users SET status = 'active' WHERE id = 1 RETURNING *;
DELETE FROM users WHERE id = 1 RETURNING name;

省掉一次额外查询，也避免了"插入后怎么拿自增 id"的经典困扰。

分组集：一次查询出多个维度的汇总

SELECT dept, city, SUM(salary)
FROM employees
GROUP BY ROLLUP (dept, city);
-- 结果同时包含：每个部门每个城市、每个部门合计、以及总计

还有 CUBE（所有维度组合）和 GROUPING SETS（精确指定要哪些组合）。做报表时极其省事。

LATERAL：让子查询能引用左边的表

-- 每个用户最近 3 笔订单
SELECT u.name, o.amount
FROM users u
CROSS JOIN LATERAL (
  SELECT amount FROM orders WHERE user_id = u.id
  ORDER BY created_at DESC LIMIT 3
) o;

普通子查询看不到左边的表，LATERAL 可以。实现"每组取前 N 条"的另一种优雅解法。

模块 6

五种索引类型：选对类型比加索引更重要

MySQL 只有 B+ 树，PG 有五种。选错类型，加了索引也白搭。

类型擅长什么典型场景
B-tree等值、范围、排序（默认类型）99% 的普通查询。不指定 USING 就是它
GIN"包含多个元素"的查询jsonb、数组、全文检索 tsvector
GiST几何、范围、最近邻地理坐标、时间段重叠、EXCLUDE 约束
BRIN超大且天然有序的表按时间顺序写入的日志表，索引体积极小
Hash只有等值查询用得少，B-tree 通常更好
CREATE INDEX idx_a ON t (col);                          -- B-tree（默认）
CREATE INDEX idx_b ON t USING gin (jsonb_col);          -- GIN
CREATE INDEX idx_c ON logs USING brin (created_at);      -- BRIN

四种"高级索引"写法，非常实用

部分索引：只给关心的行建索引

-- 只索引未完成的订单（通常只占 1%）
CREATE INDEX idx_pending ON orders (created_at) WHERE status = 'pending';
-- 索引体积可能只有全量索引的 1%，查询同样走索引

表达式索引：给"计算后的值"建索引

-- 直接给 lower(email) 建索引，这样函数包裹也不会失效
CREATE INDEX idx_email_lower ON users (lower(email));
SELECT * FROM users WHERE lower(email) = 'a@b.com';   -- 走索引
这条解决了 MySQL 篇里"索引列被函数包住就失效"的问题。PG 里你可以直接给函数结果建索引，所以 lower(email)、date(created_at) 这类查询也能走索引。

覆盖索引（INCLUDE）：把需要的列塞进索引

CREATE INDEX idx_cover ON orders (user_id) INCLUDE (amount, status);
-- 查询只涉及这三列时，不用回表读原始数据，纯索引扫描

并发建索引：不锁表

CREATE INDEX CONCURRENTLY idx_big ON big_table (col);
生产环境必用。普通 CREATE INDEX 会阻塞该表的写入，大表上可能锁几分钟。CONCURRENTLY 不阻塞写入，代价是耗时更长，而且不能在事务块里执行。

怎么知道索引有没有被用上

SELECT indexrelname AS 索引名, idx_scan AS 被使用次数
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;
-- idx_scan = 0 的索引从来没被用过，是纯粹的负担，可以考虑删掉
模块 7

事务、MVCC 与 VACUUM

这三件事是一体的，理解了 MVCC，才能理解为什么 PG 需要 VACUUM。

事务基础

BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  SAVEPOINT sp1;                        -- 打个存档点
  UPDATE accounts SET balance = balance + 100 WHERE id = 2;
  ROLLBACK TO sp1;                      -- 只撤销后半部分，前半部分保留
COMMIT;

SAVEPOINT 是 MySQL 也有但少用的能力：事务内部可以部分回滚。

MVCC：为什么 PG 读写不互相阻塞

先说核心机制：UPDATE 不覆盖原行，而是写入一个全新的版本；旧版本继续留在表里，给还在运行的老事务看。

每一行都记录着两个隐藏字段：xmin（创建它的事务号）和 xmax（删除它的事务号）。数据库靠这两个数字判断"这一行对当前事务是否可见"。

举个具体例子：同一行被改了两次，表里就有三个版本。事务 A 在第二个版本产生时启动，它看到第二个版本；事务 B 在第三个版本产生时启动，它看到第三个版本。两个事务各看各的，读不阻塞写、写不阻塞读，谁也不用等谁。

隔离级别说明
读已提交（默认）每条语句开始时取一次快照。同一条 SQL 里看到的数据是一致的，但同一事务的两次查询可能看到不同结果
可重复读整个事务开始时取一次快照，全程看到同一份数据。可能出现"序列化失败"
可序列化最严格，并发冲突时会让事务重试。金融场景按需使用
这是 PG 和 MySQL 最容易踩出 bug 的差异。MySQL 默认"可重复读"，很多人在 MySQL 上验证过的代码逻辑，直接搬到 PG 就会出问题。

典型场景：事务里先 SELECT 判断余额够不够，再 UPDATE 扣款。在"读已提交"下，两次之间别人可能已经改过数据了。正确做法是用 UPDATE ... WHERE balance >= 100 把判断和更新合成一条原子语句，或者显式加锁 SELECT ... FOR UPDATE。

需要更强一致性时，显式提升隔离级别：

BEGIN ISOLATION LEVEL REPEATABLE READ;
-- 或者
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

VACUUM：MVCC 的代价

旧版本行（称为"死元组"）不会自动消失。它们仍然占着磁盘空间，只是对任何事务都不可见了。VACUUM 的工作就是把这些空间标记为可复用。

命令作用
VACUUM 表名回收死元组空间，不锁表，可以并发执行
VACUUM ANALYZE 表名回收空间 + 更新统计信息（优化器靠它选执行计划）
VACUUM FULL 表名真正把空间还给操作系统，但会锁表重写整张表。生产环境慎用
好消息：autovacuum 默认是开着的，会自动帮你清理。你不需要天天手动跑。
坏消息：长事务会拖住 autovacuum —— 因为老事务可能还需要看旧版本，死元组就不敢清。所以线上千万不要开一个几小时不提交的事务，它会拖垮整个库的清理节奏，导致表持续膨胀。

监控表膨胀：

SELECT relname, n_live_tup, n_dead_tup,
       ROUND(n_dead_tup * 100.0 / NULLIF(n_live_tup + n_dead_tup, 0), 1) AS 死元组占比
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC LIMIT 10;

锁与死锁

-- 查看当前阻塞关系
SELECT pid, state, wait_event_type, LEFT(query, 60)
FROM pg_stat_activity
WHERE state != 'idle';

-- 主动取消一个卡住的查询
SELECT pg_cancel_backend(12345);

PG 会自动检测死锁并杀掉其中一个事务，返回错误。所以死锁不会永久卡住，但会报错 —— 应用层需要有重试逻辑。

行级锁的常用写法：SELECT ... FOR UPDATE（排他锁）、FOR SHARE（共享锁）、FOR UPDATE NOWAIT（拿不到锁立刻报错，不等待）。

模块 8

性能诊断与运维

EXPLAIN 和 EXPLAIN ANALYZE 的区别

命令做什么
EXPLAIN只给预估计划，不实际执行
EXPLAIN ANALYZE真正执行并给出实际耗时、实际行数。排查慢查询用这个
EXPLAIN (ANALYZE, BUFFERS)再加上缓存命中情况，能看到磁盘读了多少
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE user_id = 42;

读执行计划时，重点看两件事：

  • 有没有出现 Seq Scan（顺序扫描 = 全表扫描）。小表上它是正常的，大表上就是问题
  • 预估行数和实际行数差多少。差得离谱说明统计信息过期，跑一下 ANALYZE 表名

常见节点，认识这几个就够了：

  • Index Scan —— 走索引取数据，通常是好事
  • Index Only Scan —— 只用索引就拿到全部结果，不用回表，最快
  • Bitmap Heap Scan —— 命中行数较多时的折中方案
  • Seq Scan —— 全表扫描。小表上正常，大表上要警惕
  • Nested Loop / Hash Join / Merge Join —— 三种表连接算法，由优化器自动选择，一般不用人工干预

找出最耗资源的 SQL

-- 需要先启用扩展：CREATE EXTENSION pg_stat_statements;
SELECT LEFT(query, 70) AS 语句, calls AS 调用次数,
       ROUND(total_exec_time::numeric, 0) AS 总耗时ms
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;

这是线上排障的第一个动作 —— 别猜，直接看谁最耗时。

连接池：PG 的硬性要求

PG 每个连接对应一个独立操作系统进程（MySQL 是线程）。进程的内存开销远大于线程，所以 PG 的 max_connections 默认只有 100，开太多会直接把机器吃垮。

结论：任何生产环境的应用都必须走连接池。应用侧用连接池（如 HikariCP），或者中间加一层 PgBouncer。绝不要让每个请求都新建一个连接。

备份与恢复

# 逻辑备份：导出单个库
pg_dump -Fc -d shop -f shop.dump
pg_restore -d shop_new shop.dump

# 全库备份
pg_dumpall -f all.sql

# 物理备份 + 持续归档 = 可以恢复到任意时间点（PITR）
# 原理：定期做基础备份，同时把 WAL 日志持续归档出去

WAL（预写日志）是 PG 保证持久性的核心：任何修改先写日志再写数据文件。它同时支撑了崩溃恢复、流复制（主从）和时间点恢复三件事。

分区表

CREATE TABLE logs (id bigint, created_at timestamptz)
PARTITION BY RANGE (created_at);

CREATE TABLE logs_2026_01 PARTITION OF logs
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

表太大（比如几亿行）时的标准解法：按月分区后，查询会自动只扫相关分区，过期数据直接 DROP 整个分区（秒级），不用做昂贵的批量 DELETE。

模块 9

八个生产坑

1
用 MySQL 的"可重复读"思维写 PG 代码
PG 默认"读已提交"。事务里"先查后改"的逻辑在并发下会出错。把判断条件写进 UPDATE 的 WHERE，或用 SELECT ... FOR UPDATE。
2
开了长事务不提交
长事务会阻止 VACUUM 清理死元组，导致表持续膨胀、查询越来越慢。务必设置事务超时，连接池里开启自动回滚空闲事务。
3
不配置连接池，直接裸连
每个连接一个进程，几十个并发就能把内存吃光，报 "too many clients"。
4
大表上用普通 CREATE INDEX
会阻塞写入。生产必须用 CREATE INDEX CONCURRENTLY（注意它不能在事务里跑）。
5
标识符大小写踩坑
不加双引号的标识符会被转成小写。用驼峰命名又忘了加引号，就会报"表不存在"。
6
把 json 当 jsonb 用
json 不能建索引、每次访问都要重新解析。除非要原样保留 JSON 文本，否则一律 jsonb。
7
VACUUM FULL 当日常清理用
它会排他锁表并重写整张表，大表上等于停机。日常靠 autovacuum，只有磁盘真的回收不了时才考虑。
8
忘了 ANALYZE，优化器选错计划
统计信息过期会导致优化器严重误判行数，该走索引却全表扫描。批量导入数据后手动跑一次 ANALYZE。
自测

六道题

1. PostgreSQL 的默认事务隔离级别是？
正确答案：读已提交。这是 PG 和 MySQL 最容易引发 bug 的差异 —— MySQL 默认是可重复读。在"读已提交"下，同一事务里两次查询可能看到不同数据。
2. 为什么 PG 需要 VACUUM，而 MySQL 不太需要？
正确答案：MVCC 会留下旧版本。UPDATE 不覆盖原行而是写新版本，旧版本变成"死元组"继续占空间，需要 VACUUM 回收。MySQL 的 InnoDB 有后台 purge 线程自动处理。
3. 要查询 jsonb 列里"包含某个键值"的数据，应该建哪种索引？
正确答案：GIN。GIN 专为"一个字段里包含多个元素"的查询设计，适合 jsonb、数组、全文检索。B-tree 处理不了这种包含关系，BRIN 是给超大有序表用的。
4. 下面哪个操作在生产环境的大表上最危险？
正确答案：VACUUM FULL。它会持有排他锁并重写整张表，大表上等同于停机。日常清理靠 autovacuum 就够了，建索引则应该用 CONCURRENTLY 版本。
5. 想让 WHERE lower(email) = 'a@b.com' 走索引，该怎么做？
正确答案：建表达式索引。这是 PG 比 MySQL 强的地方 —— 可以直接给函数计算结果建索引，让这类查询也能走索引。（citext 是另一个可行方案，但不是唯一解。）
6. 为什么 PostgreSQL 的应用必须使用连接池？
正确答案：每连接一个进程。这是 PG 和 MySQL（线程模型）的核心架构差异。max_connections 默认只有 100，几十个并发就可能把内存吃光。

术语一句话解释
schema 模式库内部的命名空间，PG 比 MySQL 多的那一层
MVCC多版本并发控制。更新时写新版本而非覆盖，实现读写不阻塞
死元组被更新或删除后遗留的旧版本行，仍占空间但不可见

WAL预写日志。先写日志再改数据，保证崩溃后能恢复

表达式索引对函数计算结果建索引，解决函数包裹列导致索引失效的问题
窗口函数保留每一行，同时计算分组统计值
CTEWITH 子句定义的临时结果集，可递归
UPSERT存在则更新、不存在则插入的原子操作

连接池复用数据库连接的中间层，PG 上属于硬性要求
PgBouncer最常用的 PG 连接池中间件
