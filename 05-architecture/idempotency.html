二十分钟学透幂等性设计

网络会重试、MQ 会重投、用户会连点、定时任务会重跑。幂等不是可选项，是接口的出厂配置。这篇讲唯一索引、token、状态机、乐观锁、分布式锁五种手段怎么落地，以及"先查后插"为什么是竞态之王。

开始前

幂等的定义与数学性质

幂等（Idempotence）：同一操作执行一次与执行 N 次，对系统状态的最终影响相同。数学表达：f(f(x)) = f(x)。

操作类型是否天然幂等示例
查询天然幂等SELECT ... WHERE id=1
设置绝对值天然幂等UPDATE ... SET balance=100（重复执行结果都是 100）
删除天然幂等DELETE ... WHERE id=1（第二次影响 0 行，状态不变）
增量修改不幂等UPDATE ... SET balance=balance-100（扣两次扣两百）
插入不幂等INSERT INTO orders ...（插两次两条记录）
自增不幂等counter = counter + 1
追加不幂等INSERT INTO log ... / append to list
核心认知：不幂等的操作占多数，而"重复执行"是分布式系统的常态。客户端超时重试、网关重试、MQ 至少一次投递、定时任务重叠、用户连点——每一层都可能把你的请求变成两次。所以幂等必须是服务端的承诺：客户端去重不可靠，网络重试不可控。
模块 1

业务场景：哪些接口必须幂等

场景重复来源重复的后果
支付用户连点"确认支付"；网络超时客户端重试；渠道重复回调资金损失：同一笔订单扣款两次，客诉 + 资损
下单提交按钮双击；超时重发；页面刷新重提重复订单、重复占库存、重复发优惠券
消息消费MQ 至少一次投递；消费者 ack 前宕机；rebalance 重分配重复扣库存、重复加积分、重复发消息
支付回调渠道重发成功通知（间隔几秒到几小时都可能）重复入账、重复改订单状态
定时任务任务执行到一半进程重启；多实例部署重复调度重复批处理、重复结算、重复发奖
批量导入同一文件重复上传；失败后重试重复数据入库，清理成本极高

判断标准：写操作 + 可重入 = 必须幂等

一条实用规则：任何修改状态的接口，只要可能被客户端、网关、MQ、定时任务中的任何一方重放，就必须做幂等。在微服务架构里，这实际上意味着所有写接口都要有幂等设计——区别只是幂等键选什么。

模块 2

手段一：唯一索引与去重表

最可靠、最常用的手段。利用数据库唯一约束的原子性，让并发下的重复插入只有一个成功——不需要锁，不需要先查。

业务表带唯一键

-- 订单表：biz_no 业务唯一号，从源头保证一单一条
CREATE TABLE orders (
  id          BIGINT PRIMARY KEY,
  biz_no      VARCHAR(64)  NOT NULL COMMENT '业务唯一号：20241000123',
  user_id     BIGINT       NOT NULL,
  amount      DECIMAL(10,2) NOT NULL,
  status      TINYINT      NOT NULL DEFAULT 0,
  created_at  TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_biz_no (biz_no)
) ENGINE=InnoDB;

-- 并发重复提交时：两条 INSERT 只有一条成功，另一条报 1062 唯一键冲突
INSERT INTO orders (id, biz_no, user_id, amount) VALUES (1, '20241000123', 1001, 99.50);

-- 处理冲突的两种方式
INSERT IGNORE INTO orders (...) VALUES (...);   -- 冲突时静默跳过（影响行数=0）
INSERT INTO orders (...) VALUES (...)
  ON DUPLICATE KEY UPDATE id = id;              -- 冲突时执行空更新，同样返回成功

-- 注意 REPLACE INTO：先 DELETE 再 INSERT，会重置自增、触发触发器，慎用

通用去重表（适合所有写操作）

-- 幂等日志表：所有写操作的统一去重入口
CREATE TABLE idem_log (
  idem_key    VARCHAR(128) PRIMARY KEY COMMENT '幂等键：pay:20241000123:capture',
  biz_type    VARCHAR(32)  NOT NULL,
  status      TINYINT      NOT NULL DEFAULT 0 COMMENT '0=处理中 1=成功 2=失败',
  result      JSON,
  created_at  TIMESTAMP   DEFAULT CURRENT_TIMESTAMP,
  finished_at TIMESTAMP   NULL,
  KEY idx_created (created_at)
) ENGINE=InnoDB;

-- 标准流程：
-- 1. INSERT idem_log(idem_key) → 冲突(1062)说明是重复请求
-- 2. 查旧记录：status=1 直接返回 result（幂等返回）；
--    status=0 返回"处理中，请稍后重试"；status=2 允许按策略重试或返回错误
-- 3. 执行业务（与 INSERT 在同一事务）
-- 4. UPDATE idem_log SET status=1, result=..., finished_at=NOW() WHERE idem_key=...
为什么不用"先查后插"：SELECT ... WHERE idem_key=? 查到没有 → INSERT。两个并发请求会同时查到"没有"，然后双双插入成功——这是最经典的竞态（见坑 1）。唯一索引的价值就在于把"判断 + 插入"合并成一个原子操作，并发下天然只有一个成功。

去重表的两条运维纪律

  • 保留窗口 = 最大重试/回溯窗口 + 1：消息回溯一般 3 天，回调重试一般 24 小时，保留 7 天是常见选择。超期数据归档到历史表，主表定期 DELETE。
  • Redis 加速但必须数据库兜底：高频场景可先 SETNX idem:key 1 EX 86400 挡一层（性能高），但 Redis 丢数据/主从切换可能丢 key，数据库唯一索引是最终防线，两层都要有。
模块 3

手段二：Token 机制

Token 适合"用户主动触发的一次性提交"（下单、支付）。核心是先领token、提交时原子消费。

进入表单页：客户端调 GET /api/token，服务端生成 UUID，SET token:<uuid> <user_id> EX 600 存入 Redis，返回给前端
提交：前端把 token 放到请求头或表单隐藏域，随业务请求一起提交
原子消费：服务端用 Lua 脚本做"验证 + 删除"，保证两步原子
执行：消费成功才执行业务；失败（返回 0）说明 token 不存在或已被消费，直接返回"重复提交"
# 原子消费 token 的 Lua（验证 + 删除必须原子，否则并发下 token 可复用）
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 token:abc-123 1001

# 返回 1 = 消费成功，继续业务；返回 0 = token 不存在/已被消费 → 拒绝

# 为什么不能分两步？
# GET 比对成功后、DEL 之前进程崩溃 → token 还在，下次提交还能用 → 幂等失效
# 两个并发请求同时 GET 成功 → 都认为自己是第一个 → 双双执行业务
Token 的三个盲区：① 只管"一次"，不管"结果"——token 消费后业务执行失败，客户端重试会拿到"重复提交"而不知所措，需要配合去重表返回上次结果；② Redis 丢 key = 幂等窗口失效（主从切换、AOF 丢数据），所以 token 是性能优化层，数据库唯一索引才是兜底；③ token 过期时间要大于用户填表单的最长时间（10 分钟常见），太短用户还没提交就失效，太长则占用内存。
模块 4

手段三：状态机、乐观锁与分布式锁

状态机：把执行动作变成条件迁移

-- 订单状态机：INIT(待支付) → PAID(已支付) → SHIPPED(已发货) → DONE
-- 幂等的关键：UPDATE 带旧状态条件，影响行数=0 就是重复请求
UPDATE orders
   SET status = 'PAID', paid_at = NOW()
 WHERE id = ? AND status = 'INIT';

-- 影响行数 = 1：首次支付，继续后续流程
-- 影响行数 = 0：已是 PAID（渠道重复回调）或订单已取消 → 直接返回上次结果，幂等
-- 状态机 + 条件 UPDATE 是业务幂等的通用范式，且顺带解决了并发（CAS 语义）

乐观锁版本号：并发控制，防旧数据覆盖

-- 典型余额扣减：先查出版本号，更新时校验版本未变
SELECT balance, version FROM account WHERE id = ?;      -- 得到 balance=500, version=7

UPDATE account
   SET balance = balance - 100, version = version + 1
 WHERE id = ? AND version = 7 AND balance >= 100;

-- 影响行数 = 0：版本变了（别人改过）或余额不足 → 重试或失败
-- 注意：乐观锁是并发控制，不是幂等控制；但它让"基于旧快照的重复扣减"失败，
--       与状态机/去重表组合使用，构成完整防线

分布式锁：互斥，但不管结果重放

# 加锁：SET key value NX EX seconds，value 放唯一值用于解锁校验
SET lock:order:42 "uuid-abc" NX EX 10

# 解锁：Lua 保证"判断是我的锁 + 删除"原子
EVAL "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end" 1 lock:order:42 uuid-abc

# 锁的三个事实：
# 1. 锁只保证"同一时刻只有一个执行"，不保证"重复请求返回相同结果"
# 2. 锁过期时间必须大于业务最坏执行时间，否则锁放掉后第二个请求穿透（坑 2）
# 3. 锁要配合去重表：拿到锁 → 查去重表 → 已处理直接返回 → 未处理才执行

五种手段对比

手段适用场景并发安全结果可重放主要风险
唯一索引插入类操作（订单、流水）是（DB 原子）否（冲突即报错）索引膨胀；需处理 1062
去重表所有写操作，通用方案是是（存 result）表膨胀，需清理策略
Token用户一次性提交（下单、支付页）是（Lua 原子）否Redis 丢 key；只管一次
状态机有明确状态流转的业务（订单、支付单）是（CAS）是（查旧状态返回）状态设计错误会放过非法迁移
乐观锁并发更新同一行（余额、库存）是（CAS）否高竞争下重试风暴；不挡重复请求
分布式锁复杂业务流程互斥是（近似）否锁过期、Redlock 争议、性能开销
生产组合拳（推荐）：Token（挡前端双击）→ 去重表/唯一索引（挡服务端重试，可返回旧结果）→ 状态机（保证业务只执行一次合法迁移）→ 乐观锁（兜底并发覆盖）。四层各挡一类重复，任一层失效不至于资损。
模块 5

接口幂等 vs 业务幂等与幂等键设计

层面管什么典型实现
接口幂等
（传输层）		同一请求 ID 不重复执行。客户端每次请求生成唯一 ID，全链路传递HTTP 头 Idempotency-Key（Stripe 的实践，金融 API 常用）；RPC 框架的 request_id 透传
业务幂等
（领域层）		同一业务单据不重复处理。幂等键 = 业务唯一标识唯一索引、去重表、状态机，键如 pay:20241000123:capture

幂等键：客户端生成 vs 服务端生成

方式优点缺点与适用
客户端生成双击、重试都能对上同一个键；实现简单要防伪造/恶意构造相同键。适合用户主动触发场景（表单提交）
服务端生成可靠，按业务单据派生，无法伪造只能挡"同一单据重复"，挡不住双击生成两个单。必须与客户端键组合
组合使用客户端带 request_id 防重 + 服务端按 biz_no 去重推荐：两层键各管一层重复

幂等键设计规范

# 命名公式：<biz_type>:<biz_id>:<action>
pay:20241000123:capture      # 支付单 20241000123 的"扣款"动作
order:20241000123:create     # 订单创建
stock:sku8888:deduct:order99 # 库存扣减要带订单号，否则同一订单重试被误判

# 三条设计原则：
# 1. 精确到"这次操作"：用 user_id 做键 → 用户第二单被当成重复（经典错误，坑 4）
# 2. 可读可运维：键能直接看出业务含义，排障时能 grep
# 3. 带 TTL：覆盖最大重试窗口即可（如 7 天），不要永久保留
全链路幂等：只挡入口是不够的。一次支付成功通常要写：支付单、流水、账务科目、发消息通知、加积分。每一跳都可能重放，每一跳都要幂等——入口幂等 + 下游消息消费幂等，缺一个都会出现"订单只有一个，积分加了两遍"。
模块 6

消息消费幂等与重试风暴

为什么 MQ 一定会有重复

  • 至少一次投递（at-least-once）是主流默认：Kafka 消费者默认自动提交位点，可能重复；RocketMQ 默认至少一次；RabbitMQ 手动 ack 模式消费后不 ack 就重投。
  • 重复的具体来源：生产者发送超时后重发；消费者处理完业务、ack 前宕机；rebalance 后消息被重新分配；运维手动消息回溯。
  • 结论："恰好一次"要靠消费端幂等实现，不能指望 MQ 保证。
# 消费幂等的标准模板
msg_id     = message.getId()          # MQ 全局消息 ID（同一消息重投不变）
biz_key    = "stock:deduct:" + msg.getOrderId()   # 业务唯一键，比 msg_id 更可靠

# 1. 尝试插入去重记录（唯一索引冲突 = 重复消费）
rows = INSERT IGNORE INTO idem_log (idem_key, biz_type) VALUES (biz_key, 'stock_deduct');
if (rows == 0) {
    ack(message);                     # 已处理过，直接确认，不执行业务
    return;
}

# 2. 执行业务 + 更新去重记录，在同一个本地事务里
try {
    deductStock(msg.getSkuId(), msg.getQty());
    UPDATE idem_log SET status=1 WHERE idem_key = biz_key;
    ack(message);
} catch (e) {
    # 不回滚去重记录（或标记 status=2 允许重试），消息进入重试队列
    nack(message);
}
顺序消息 + 幂等：RocketMQ 顺序消息保证分区内有序，但重试会破坏顺序（失败的消息被延迟重投，后面的消息先到）。解法：业务侧用版本号/状态机兜底——如"已发货"状态拒绝"已发货"之前的迁移，乱序到达时旧操作自然失败。

重试风暴：必须防的系统级故障

链路：下游故障 → 消息全部消费失败 → 按策略重试 → 重试流量压垮刚恢复的下游 → 再次全线失败 → 雪崩。

对策做法关键参数
指数退避重试间隔逐次翻倍：1s、2s、4s、8s、16s……上限次数 5~16 次（RocketMQ 默认 16 级延迟后进死信）
抖动 jitter间隔加随机量，防止大量消息同步重试形成尖峰±20%~50% 随机
死信队列 DLQ超过重试次数的消息进 DLQ，人工介入，不再自动重试DLQ 必须配监控告警
消费限流消费端线程池 + 令牌桶，控制对下游的压力按下游容量设定 QPS 上限
熔断下游错误率超阈值直接快速失败，给它恢复时间错误率 > 50% 持续 10s 打开，半开探测恢复
重试的正确姿势是"退避 + 上限 + 死信 + 熔断"组合，单靠任何一个都会出事：只退避不上限 → 无限重试；只上限不熔断 → 重试期间照样压垮下游；有死信但没告警 → 消息静静躺在 DLQ 里业务停摆没人知道。
模块 7

十个坑

1
先查后插的竞态
SELECT 查到没有 → INSERT。两个并发请求同时查到"没有"，双双插入成功，重复单产生。解法：唯一索引兜底，或 INSERT ... ON DUPLICATE KEY，把判断和插入合并成原子操作。任何"先查后写"在高并发下都是竞态之王。
2
分布式锁过期早于业务执行完
锁设 10 秒，业务最坏要 15 秒，锁在第 10 秒放掉，第二个请求进来，两个请求同时执行业务。锁时间要按最坏路径评估，或使用 Redisson 看门狗自动续期；更稳的是用数据库唯一索引做最终防线，别把锁当唯一保障。
3
重试风暴
下游一故障，所有客户端立即原样重试，把刚恢复的下游再次打死，雪崩循环。必须指数退避 + 抖动 + 次数上限 + 死信队列 + 熔断，组合使用。
4
幂等键维度选错
用 user_id 做幂等键，用户下第二单被当成"重复请求"拒绝；或用整个请求体做键，字段顺序变化就失效。幂等键要精确到"这次操作"：biz_no + action，且与业务单据号对齐。
5
只挡创建入口，不挡回调
下单接口做了幂等，支付渠道的重复回调（间隔几分钟甚至几小时）照样重复入账。每个写入口都要单独幂等：创建、回调、消息消费、定时任务，一个都不能漏。
6
幂等记录不过期，表无限膨胀
去重表 3 年 10 亿行，主键索引比数据还大，插入越来越慢。保留窗口 = 最大重试/回溯窗口 + 1（通常 7 天），定时归档 + 清理，这是运维任务不是可选项。
7
Token 验证与消费不原子
GET 比对成功后、DEL 之前进程崩溃，token 还在，还能再提交一次；并发两个请求同时 GET 成功，都继续执行业务。必须用 Lua 做"验证 + 删除"的原子操作，并且数据库去重兜底。
8
乐观锁没写在 WHERE 条件里
UPDATE 时忘了 AND version=old_version，锁形同虚设，旧数据照样覆盖新数据。版本号条件必须进 WHERE，且每次更新递增；漏写等于没写。
9
消息去重只 ACK 不推进状态
判出重复就 ack 跳过，但第一条消息其实处理失败进了 DLQ，重复消息被跳过，业务永远停在那一步。正确顺序：业务处理成功才写幂等记录；失败就 nack 重试，别让"去重"掩盖"没处理"。
10
超时重试与用户取消并发
支付请求超时，客户端自动重试；同时用户点了取消。两个请求并发改订单状态，可能"取消后又支付成功"。状态机是唯一防线：定义合法迁移集合（如 PAID 不允许转 CANCELLED 需走退款），非法迁移直接拒绝。
自测

六道题

1. 下列哪个操作天然幂等？
正确答案：SET balance=100。它设置绝对值，重复执行结果都是 100。而扣减（balance-100）、插入都会随执行次数改变状态，都不幂等。
2. "先查后插"（SELECT 没有就 INSERT）的问题是什么？
正确答案：并发竞态。检查和插入之间有时间窗，并发请求都会通过检查。解法是唯一索引 + INSERT ... ON DUPLICATE KEY，把"判断 + 插入"合并为一个原子操作，让数据库保证只有一个成功。
3. 用状态机实现幂等的核心 SQL 技巧是？
正确答案：UPDATE 带旧状态条件。条件更新是原子的 CAS：首次执行影响 1 行，重复执行（状态已变）影响 0 行，直接返回上次结果即可。不带条件的 UPDATE 和"先查后判"都有竞态。
4. Token 机制为什么必须用 Lua 脚本消费？
正确答案：保证验证+删除原子。分两步做：GET 成功后进程崩溃 → token 未删，还能再提交；两个请求同时 GET 成功 → 都执行业务。Lua 脚本在 Redis 中原子执行，杜绝这个窗口。
5. 防止重试风暴的最佳实践组合是？
正确答案：退避 + 抖动 + 上限 + DLQ + 熔断。退避降低压力、抖动防同步尖峰、上限防无限重试、DLQ 隔离毒消息、熔断给下游恢复时间。单靠任何一个都不够：立即重试会打死下游，纯长间隔会拖慢正常恢复。
6. 在 MQ 至少一次投递（at-least-once）语义下，保证业务不重复的正确做法是？
正确答案：消费端幂等。at-least-once 下重复是常态（生产者重发、ack 前宕机、rebalance、回溯），消费端必须用幂等键去重；且顺序是"业务成功才写幂等记录"，失败 nack 重试——否则会用"去重"掩盖"未处理"。

术语一句话解释
幂等同一操作执行一次与 N 次，最终状态相同（f(f(x))=f(x)）

悲观锁SELECT ... FOR X 先锁行再改，简单但并发度低、有死锁风险

消息回溯按时间或位点重新消费历史消息，是重复的重要来源
