开始前

DDD 到底是什么，不是什么

Eric Evans 2003 年《Domain-Driven Design》提出的核心主张只有一句：软件的核心复杂度在业务领域，技术框架是次要的；让代码结构反映业务结构，而不是数据库表结构。

DDD 是DDD 不是
一套划分业务边界的方法（战略设计）一套强制代码规范（不是“必须四层架构”）
让开发和业务用同一套语言对话（通用语言）银弹。简单 CRUD 系统套 DDD 是灾难
把易变业务规则收拢到领域层的技术手段微服务的同义词。DDD 不强制分布式
持续重构的指导，不是一次性建模Up-front 大设计。画三个月类图再动手必死
先泼冷水：如果你做的是管理后台、表单流转、数据报表这类行为少、状态简单的系统，老老实实 MVC + 三层 + 快速迭代，别上 DDD。DDD 的成本是概念数量暴涨（实体/值对象/聚合/领域服务/事件……），收益只有复杂业务规则才撑得起来。判断标准见模块 8。
模块 1

战略设计：限界上下文与通用语言

战略设计回答“系统该切成几块、每块的边界在哪”，这是 DDD 最大的价值，也是 80% 团队跳过的部分。

限界上下文（Bounded Context）

同一个词在不同上下文里含义不同。“商品”在三个上下文里是三个模型：

上下文“商品”关注什么典型字段
商品中心是什么：类目、属性、详情spuId, title, categoryId, attrs
库存上下文有多少、在哪：可售数量、仓位置skuId, availableQty, warehouseId
营销上下文怎么卖：活动价、优惠资格skuId, promoId, discountPrice

如果用一个“大商品表”把三类字段塞在一起，任何一方的需求都会污染另外两方 —— 改库存要动商品详情表，营销加个字段要全表 ALTER。限界上下文就是强制这些概念分家的边界，边界内模型保持自洽。

通用语言（Ubiquitous Language）

开发、产品、业务专家在指定上下文内使用同一套词汇，且这套词汇直接出现在代码里：类名、方法名、表名。

# 通用语言落地的检查方法：把需求文档里的名词抠出来
需求原文："用户下单后，已发货的订单才能申请售后，已完成的不能"

通用语言抽取：
  - 名词：用户、订单、售后单、发货
  - 状态：待支付 → 已支付 → 已发货 → 已完成（这是 Order 的状态机）
  - 规则："已发货才能售后" = 售后单创建的领域规则，不是 if 随便放哪的问题

代码体现（而不是 "status == 3" 这种魔法值）：
  OrderStatus.SHIPPED.canApplyAfterSale()   // 规则收在枚举/实体里
  AfterSaleOrder.create(order, reason)       // 创建时校验规则

上下文映射（Context Mapping）

边界画好了，上下文之间怎么协作？常见关系：

关系方向/语义落地形态
防腐层 ACL下游通过适配层消费上游，翻译成自己的模型Adapter/Translator 类，见模块 4
开放主机服务 OHS上游提供稳定公开的协议REST API、事件契约（Published Schema）
共享内核两上下文共用一小块模型，需同步演进公共 jar 包。谨慎使用，是耦合源
客户/供应商下游依赖上游，上游排期要考虑下游团队协作约定
遵奉者下游凑合用上游模型，不做翻译临时方案，腐化温床
上下文映射图是架构图的真正核心。画清楚“谁通过什么协议消费谁、变更怎么传播”，比画部署图有价值得多。团队吵架“这个字段归谁管”，答案就在上下文边界里。
模块 2

战术设计：实体、值对象与聚合

实体 vs 值对象

概念判等标准要点
实体 Entity按唯一标识（ID）判等有生命周期，状态会变。User、Order
值对象 Value Object按属性值判等，不可变无 ID，改了就是换一个。Address、Money
// 值对象：不可变 + 按值判等。Java 用 record（JDK 16+）
public record Money(BigDecimal amount, Currency currency) {
    public Money {
        if (amount.compareTo(BigDecimal.ZERO) < 0)
            throw new IllegalArgumentException("金额不能为负");
    }
    public Money add(Money other) { // 返回新对象，不修改自己
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("币种不同");
        return new Money(amount.add(other.amount), currency);
    }
}
// 值对象的意义：把"校验 + 行为"绑在数据上，消灭散落各处的 if (amount < 0)

// 实体：按 ID 判等，行为即状态机
public class Order {
    private final OrderId id;
    private OrderStatus status;
    private List<OrderItem> items;       // 聚合内的实体
    private final Instant createdAt;

    public void ship() {                     // 领域行为，不是 setter
        if (status != OrderStatus.PAID)
            throw new IllegalStateException("只有已支付订单能发货，当前: " + status);
        this.status = OrderStatus.SHIPPED;
    }
}
// 贫血 vs 充血的分界：Order 里有没有 ship()/pay() 这种带规则的业务行为。
// 全是 getter/setter，领域逻辑在 Service 里裸奔 = 贫血模型（多数项目的现状）

聚合与聚合根（Aggregate / Aggregate Root）

聚合是一组必须保持一致的对象集群，外界只能通过聚合根访问。订单和订单项就是经典聚合：

// 聚合根：Order。不变量（invariant）：订单总额 = 所有明细项金额之和
public class Order {                          // ← 聚合根
    private OrderId id;
    private List<OrderItem> items;         // ← 聚合内实体
    private Money total;                   // ← 由 items 推导，冗余存储
    private Address address;               // ← 值对象

    public void addItem(OrderItem item) {
        if (status != OrderStatus.DRAFT)
            throw new IllegalStateException("非草稿状态不能加商品");
        items.add(item);
        this.total = total.add(item.subtotal());   // 维护不变量
    }

    public void removeItem(OrderItemId itemId) { /* 同理工整 total */ }
}

// 外部代码只能这样访问（通过根）：
order.addItem(newItem);
// 不能这样（绕过根破坏不变量）：
order.getItems().add(newItem);   // ✗ 直接改集合，total 没更新

聚合设计三原则

小聚合。聚合只放真正需要一致的实体。Order 里塞 User 信息、商品详情是常见错误 —— 那些用 ID 引用即可。大聚合 = 大事务 = 锁竞争 = 性能灾难。
引用 ID，不引用对象。聚合之间只存对方 ID（userId 而不是 User user），需要数据时通过 ACL 或查询服务按 ID 批量捞。一个聚合一个 Repository。
一次事务只改一个聚合。跨聚合的变更用领域事件最终一致（模块 5）。硬要在同一事务里改两个聚合，边界就画错了。
模块 3

领域服务、领域事件与分层架构

领域服务（Domain Service）

逻辑放不进任何实体/值对象时才用领域服务，典型特征：涉及多个聚合，或需要访问外部资源。注意它和应用服务的区别：

类型职责例子
应用服务编排：事务、鉴权、调 Repository、发事件。不含业务规则OrderAppService.placeOrder(cmd)
领域服务纯业务规则，跨聚合协调。无状态、无事务注解PricingService（订单 + 优惠 + 用户等级算价）
基础设施服务技术能力：发邮件、调支付网关PaymentGateway（由领域层定义接口，基础设施实现）
// 领域服务：算价格需要 Order（商品金额）+ User（等级）+ Coupon（优惠券）三个聚合
public class PricingService {   // 领域层，纯 POJO，不注入 Repository
    public Money price(Order order, UserLevel level, List<Coupon> coupons) {
        Money base = order.total();
        double rate = level.discountRate();
        Money discounted = base.multiply(rate);
        for (Coupon c : coupons) {
            if (c.applicableTo(discounted)) discounted = c.apply(discounted);
        }
        return discounted;
    }
}

四层架构（严格版 DDD 分层）

层内容依赖方向
接口层Controller、DTO、参数校验、序列化→ 应用层
应用层事务边界、编排用例、发领域事件→ 领域层
领域层实体、值对象、聚合、领域服务、领域事件。不依赖任何框架→ 无（最内层）
基础设施层Repository 实现、MQ、外部网关、ORM 映射→ 被外层依赖（依赖倒置）
// 依赖倒置的关键：领域层定义接口，基础设施层实现
package com.shop.order.domain.repository;      // 领域层
public interface OrderRepository {
    Order findById(OrderId id);
    void save(Order order);                  // 按聚合整体保存
}

package com.shop.order.infrastructure.persistence;  // 基础设施层
@Repository
public class JpaOrderRepository implements OrderRepository {
    @PersistenceContext private EntityManager em;
    public Order findById(OrderId id) {
        return OrderMapper.toDomain(em.find(OrderPO.class, id.value()));
    }
    // PO ↔ Domain 转换关在这一个类里，ORM 污染不外溢
}
// 收益：领域层单测不需要 Spring 容器，不需要数据库，直接 new 出来测

领域事件（Domain Event）

// 领域事件 = 已经发生的事实，命名用过去式
public record OrderPaid(OrderId orderId, Money paidAmount, Instant occurredAt) {}

// 聚合内产生事件，应用层统一发布（事件收集器模式）
public void pay(Money amount) {
    if (status != OrderStatus.CREATED) throw new IllegalStateException();
    this.status = OrderStatus.PAID;
    registerEvent(new OrderPaid(id, amount, Instant.now()));  // 先攒着
}

// 应用层事务提交后发布，保证"状态已落库，事件才发出"
@Transactional
public void placeOrder(PlaceOrderCmd cmd) {
    Order order = Order.create(cmd);
    orderRepo.save(order);
    domainEvents.publishAll(order.drainEvents());  // afterCommit 发布
}
领域事件 ≠ 集成事件。领域事件是进程内的、表达业务事实的；集成事件是跨服务的契约，要版本化、加字段只能加不能删。跨上下文一定发后者（通常经 MQ），且契约要在上下文映射图里显式登记。
模块 4

防腐层 ACL：真实代码结构

ACL 是 DDD 里性价比最高的战术：你的系统要依赖一个模型混乱、说改就改的上游（第三方、遗留系统、别的团队），在边界上建一层翻译，脏东西全拦在这。

// 场景：对接遗留 ERP 的库存接口，上游字段是 is_k、kcb（库存比）、拼音缩写
// 上游返回（不可控，随时变）：
// { "spu_bh": "SP001", "kcb": "12.00", "is_k": 1, "ckdm": "WH01" }

// ① 领域层：我方的库存视图模型（通用语言驱动）
package com.shop.inventory.domain.model;
public record SkuAvailability(SkuId skuId, AvailableQty qty, WarehouseId warehouseId) {}

// ② 领域层定义端口（接口），防腐层实现它
public interface AvailabilityQueryPort {
    SkuAvailability query(SkuId skuId);
}

// ③ 防腐层实现：翻译 + 异常转换 + 兜底全关在这里
package com.shop.inventory.infrastructure.acl;
public class ErpAvailabilityAcl implements AvailabilityQueryPort {
    private final ErpStockClient erpClient;        // 上游 SDK
    private final MeterRegistry metrics;          // 防腐层要埋监控

    @Override
    public SkuAvailability query(SkuId skuId) {
        ErpStockResp resp;
        try {
            resp = erpClient.queryStock(skuId.value());   // 上游抛 ErpBizException
        } catch (ErpTimeoutException e) {
            metrics.counter("acl.erp.timeout").increment();
            throw new AvailabilityQueryFailedException("ERP 超时: " + skuId, e);
        }
        // 字段映射：上游的"黑话"→ 领域语言，默认值策略也在这
        return new SkuAvailability(
            SkuId.of(resp.getSpuBh()),
            AvailableQty.of(resp.getKcb()),          // 字符串转值对象，解析失败有明确异常
            WarehouseId.of(resp.getCkdm())
        );
    }
}
// 上游改字段？只改这个类。上游挂？异常在这里转成业务异常，调用方不认识 ErpTimeoutException
ACL 必做清单为什么
异常翻译成领域异常调用方代码不该出现上游的异常类型，换供应商不用改业务
字段映射集中一处上游加字段/改类型，改动半径锁定在一个类
埋监控指标超时率、失败率、字段解析失败率，上游劣化第一时间发现
兜底策略显式化返回“库存未知”还是“按有货放行”？这是业务决策，写在 ACL 里评审
最常见的失败：ACL 变成透传层。上游 DTO 直接出现在 Controller 返回值里，或者 ACL 里开始写业务判断（“ERP 说库存 0 但我们是预售商品要放行”）——前者等于没建，后者让业务规则泄漏到边界外。ACL 只翻译，不决策。
模块 5

CQRS 与事件溯源简述

CQRS：读写分离的两个模型

CQRS（Command Query Responsibility Segregation）把写模型（保证不变量、丰富领域逻辑）和读模型（为查询优化的扁平结构）分开：

侧模型存储
写侧 Command聚合根，校验不变量，产生领域事件规范化表（MySQL）
读侧 Query面向页面的宽表，join 全预先算好ES / Redis / 物化视图
// 传统架构：一个 Order 表同时服务下单和列表页
// 列表页要 订单+用户+商品+物流 四表 join，还带 12 个筛选条件 → 慢查询

// CQRS：写侧只管写好 Order 聚合
@Transactional
public void placeOrder(PlaceOrderCmd cmd) {
    Order order = Order.create(cmd);
    orderRepo.save(order);                        // 写模型：规范表
    events.publishAll(order.drainEvents());       // OrderCreated 事件
}

// 读侧消费事件，物化成一张查询友好的宽表
@EventListener
public class OrderListViewProjector {
    public void on(OrderCreated e) {
        esRepo.index(new OrderListViewDoc(
            e.orderId(), e.userId(), e.userName(),
            e.items(), e.status(), e.createdAt()   // 冗余全带上，查询零 join
        ));
    }
}
// 列表页直接查 ES，单索引 + 过滤，P99 从 800ms 降到 20ms

事件溯源（Event Sourcing）：存事件不存状态

不保存实体的当前状态，只保存发生过的所有事件，当前状态 = 重放事件。状态是事件的 fold（左折叠）：

// 事件流（append-only 存储）
OrderCreated{orderId: 42, items: [...], total: 299}
OrderPaid{orderId: 42, amount: 299}
OrderItemRemoved{orderId: 42, itemId: 7}
OrderRefundApplied{orderId: 42, amount: 50}

// 重放得到当前状态
Order state = Order.empty();
events.forEach(state::apply);   // 每个 apply 方法改一点状态

// 收益：天然审计日志（谁在何时改了什么全在里面）、可回放出新视图、
// 时间旅行调试（replay 到故障前的状态）
// 代价：查询困难（要物化视图/CQRS 配合）、事件 schema 演进噩梦、
// 事件量大（1 亿订单 × 平均 10 事件 = 10 亿行）、运维陌生
务实结论：CQRS 可以单独用（读写负载差异大、列表页慢，这是最常见的正当理由）；事件溯源几乎总要和 CQRS 捆绑，且只建议给“审计即生命”的领域（金融台账、合规系统）。普通电商订单系统上事件溯源，是给自己挖运维坑。事件驱动的最终一致细节见本期《事件驱动架构》。

DDD 与微服务边界的关系

问题答案
一个限界上下文 = 一个微服务？推荐的起点。但一个上下文初期可以只做一个模块，等团队/负载需要再拆出去。反过来（一个服务塞多个上下文）是绝大多数微服务烂账的根源
上下文内部还要分层吗？要。四层架构在单体模块里同样成立，它是未来拆服务的接缝
跨上下文调用怎么走？ACL + 领域事件。同步调用用 ACL 包住的 HTTP/RPC 客户端；状态传播用集成事件（见《事件驱动架构》）
聚合应该跨服务吗？绝对不行。聚合是一致性边界，跨服务就没有本地事务了。跨服务只存在最终一致的协作
单体里的 DDD 完全合理且推荐：模块 = 限界上下文，包之间依赖清晰（order → 不允许反向依赖 inventory 的 domain），未来某个上下文要拆成微服务时，边界早已画好，切口干净。DDD 是为拆分做准备的方法，不是要求现在就拆。
模块 7

DDD 落地争议：何时不值得

项目特征建议
CRUD 为主，业务规则 = 字段校验不要 DDD。MVC + 三层 + 活跃记录模式，追求开发速度
规则多且常变（定价、促销、风控）DDD 收益最大。规则收在领域层，改规则不动外围
强一致性金融核心（账务、支付）DDD + 事件溯源可考虑，但配强审计和压测团队
团队 < 5 人且 3 个月内要上线验证先活下去。用 DDD 的通用语言和上下文意识就行，全套战术以后补
遗留系统改造成本评估中从画上下文映射图开始，先划边界再谈重构
大数据/报表/AI 特征工程为主领域复杂度低，数据复杂度高。用 DDD 的意义有限

业界常见批评与回应

批评务实回应
“概念太多，学习曲线陡”先只做战略设计（上下文 + 通用语言 + 事件），战术设计按需引入
“Repository/Factory 样板代码爆炸”用框架能力减样板的（Spring Data JPA、MapStruct），但保留领域层不依赖 ORM 的底线
“性能差：纯领域对象不敢直接查库”CQRS 读侧直接查宽表；写侧聚合保持小，N+1 用按 ID 批量加载解决
“最后都写成贫血模型”症状是 setter 满天飞。检查标准：Order 有没有 ship()/pay()。没有就是退化
“建模三个月，业务早变了”模型本来就要演进。拒绝一次性完美建模，每个迭代改一点
DDD 失败的头号原因不是技术，是组织：领域专家不参与建模，开发自己拍脑袋“通用语言”，模型和业务实际对不上，最后变成四层架构包着贫血模型 —— 比不用 DDD 还多三层间接。没有领域专家可访谈的项目，不要启动 DDD。
模块 8

九个落地坑

1
用 DDD 的名义做过度设计
5 个表单的管理后台上了聚合根+领域服务+事件溯源，一个简单查询穿透 6 层。复杂度不够时，DDD 的每一层都是纯成本。
2
聚合画得巨大
把 User 及其订单、优惠券、地址、日志全塞进一个聚合，保存一次锁一片表，并发写直接打架。原则：只放必须一致的实体，其余用 ID 引用。
3
聚合之间直接持有对象引用
Order 里嵌 User 对象、User 里塞 List<Order>，ORM 级联加载 N+1、序列化死循环。聚合间只存 ID，数据按需查询。
4
一个 Repository 返回多个聚合
findOrderWithUserAndItems 把三个聚合一次捞回，模糊了聚合边界，事务范围失控。一个聚合一个 Repository，别的用 ID 单独查。
5
领域层偷偷依赖框架
实体里 import 了 org.springframework 或 javax.persistence，领域单测必须起容器。判据：domain 包的依赖图里不应该出现框架 jar。
6
通用语言停留在文档里
需求写“履约”，代码叫 orderService.sendGood()，测试叫 TC03。语言不统一，模型和实现对不上。类名方法名必须用业务词。
7
领域事件同步执行当 MQ 用
@EventListener 同步发短信、同步调库存，事务被拖长、异常互相影响。跨上下行的最终一致必须走 MQ + 本地 outbox。
8
防腐层被绕开
业务代码直接注入 ErpClient 用上游 DTO，ACL 形同虚设。治理方法：上游 SDK 的依赖只允许出现在 infrastructure.acl 包，用 ArchUnit 规则卡住。
9
没有领域专家参与建模
开发自嗨建出的“完美模型”和业务实际两回事，上线即返工。DDD 是协作方法，不是开发闭门造车的框架。
自测

六道题

1. 同一个“商品”概念，在商品中心、库存、营销三个系统里字段完全不同。DDD 用什么概念描述这种边界？
正确答案：限界上下文。同一个术语在不同上下文里有不同模型和含义，边界强制它们分家。共享内核是相反方向的模式——多个上下文共用同一小块模型，这里明显不适用。
2. 关于聚合设计，下列哪种做法是正确的？
正确答案：只存 ID。大聚合导致大事务和锁竞争；绕过聚合根直接改内部集合会破坏不变量（如改了订单项但总额没更新）。小聚合 + ID 引用 + 一次事务改一个聚合是三条核心原则。
3. 订单总额必须等于所有明细项之和，这个校验应该放在哪？
正确答案：聚合根内部。这是聚合的“不变量”（invariant），必须由聚合自己保证，任何修改入口都无法绕过。放 Controller 会被其他调用路径绕过；放数据库则业务规则泄漏到存储层，且无法在单测中快速验证。
4. 对接一个字段命名混乱、接口说改就改的遗留 ERP 系统，最合适的模式是？
正确答案：防腐层。把字段映射、异常转换、兜底策略全部关在边界适配器里，上游的脏模型和变更不会渗入核心领域。共享内核只会把混乱扩散；遵奉者等于任其污染。
5. 关于 CQRS 与事件溯源，哪个说法符合工程现实？
正确答案：CQRS 可单独用，事件溯源几乎总要配 CQRS。因为事件溯源只存事件流，查询当前状态必须靠物化视图（读模型）。普通系统用事件溯源是自找运维麻烦，它适合审计即生命的金融台账类场景。
6. 一个团队 4 个人，要做的是活动报名 CRUD 系统，2 个月后要上线验证。最合理的做法是？
正确答案：快速实现 + 边界意识。CRUD 系统的领域复杂度撑不起全套战术设计；而拆微服务会让 4 人团队死在运维上。合理的折中是用包划分上下文、保持通用语言，等业务规则真的复杂起来再深化。

下一步怎么练：① 拿你现在的项目，画出所有限界上下文和它们之间的调用/事件关系（上下文映射图）；② 找出最常出 Bug 的那个模块，检查它的核心实体有没有业务行为，把散落的 if 收进聚合根；③ 给对接最乱的那个外部系统补一层 ACL，并用 ArchUnit 写规则禁止业务代码直接依赖它的 SDK。

之后值得单独学：《实现领域驱动设计》（Vaughn Vernon，战术部分比 Evans 原著更可操作）、事件风暴（Event Storming）工作坊方法、以及用 ArchUnit 落地架构约束。
