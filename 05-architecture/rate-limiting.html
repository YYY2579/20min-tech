开始前

三个词的关系：限流、熔断、降级

它们经常一起出现，但解决的问题完全不同。混用的后果是：限流阈值挡住了正常用户，熔断该断的时候没断。

手段保护谁触发依据本质动作
限流自己（不被冲垮）请求速率超过配额拒绝或排队一部分请求，系统继续服务
熔断自己（不被慢依赖拖死）下游错误率/慢调用超阈值一段时间内不再调用下游，直接返回失败或兜底
降级用户体验资源紧张或核心链路故障关闭非核心功能，把资源让给核心流程
一句话区分：限流是"控制进来的量"，熔断是"控制出去的量"，降级是"控制提供服务的质量"。三者共同构成服务的自我保护层。没有自我保护的系统，一个慢依赖就能把所有线程占满，最后谁都用不了。

典型时序：一次大促故障中三者的协作

# 0ms    大促开始，QPS 从 2,000 涨到 15,000
# 50ms   网关限流发现超过单机 3,000 QPS 的配额 → 超出的请求返回 429 或排队
# 200ms  商品服务线程池使用率到 80% → 熔断器开始观察库存服务
# 600ms  库存服务错误率超 50% → 熔断器 Open，直接走兜底库存缓存
# 800ms  推荐服务（非核心）被降级开关关闭 → 线程和连接全部让给下单链路
# 30s    熔断器进入 Half-Open，放 20% 探测流量试库存服务
# 结果：下单成功率从 40% 恢复到 92%，但推荐位显示"暂时不可用"
模块 1

四种限流算法的真实缺陷

面试都会背，但线上选错算法的代价是：要么临界点放过双倍流量，要么误杀正常突发。

固定窗口计数器（Counter Window）

每秒一个计数器，归零重置。问题在临界点：限 100/s，如果第 1 秒的第 900ms 打满 100 个，第 2 秒的第 100ms 又打满 100 个，200ms 内实际放过了 200 个请求，瞬时速率是额度的 2 倍。

# 单机版固定窗口（Redis，Lua 保证原子性）
local c = redis.call('INCR', KEYS[1])
if c == 1 then
  redis.call('EXPIRE', KEYS[1], 1)   -- 窗口 1 秒
end
if c > tonumber(ARGV[1]) then return 0 end
return 1
# 调用：EVAL script 1 rate:api:search 100
# 缺陷：临界突刺；且"过期"依赖 EXPIRE，Redis 惰性删除会让计数多存活一小会儿

滑动窗口（Sliding Window）

把窗口切成小格（如 1 秒切 10 格，每格 100ms），统计最近 N 格的总数。Sentinel 的默认统计就是滑动窗口（LeapArray，默认 2 个桶）。消除了临界突刺，代价是内存和时间精度。

实现方式做法适用
分格滑动窗口1s 切 N 个小桶，统计最近 N 桶总和绝大多数业务限流，Sentinel / Guava RateLimiter 都走这个思路
ZSet 滑动窗口score 存毫秒时间戳，ZREMRANGEBYSCORE 滑出旧数据后 ZCARD 计数需要精确到每一次请求、分布式场景
TCP 式滑动窗口字节流级别的连续窗口传输层协议，业务限流用不到
# Redis ZSet 精确滑动窗口限流（Lua）
local now = redis.call('TIME')[1] * 1000   -- 毫秒时间戳
local key = KEYS[1]
local window = tonumber(ARGV[1])   -- 窗口毫秒，如 1000
local limit = tonumber(ARGV[2])    -- 配额，如 100
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)   -- 滑出过期请求
local cnt = redis.call('ZCARD', key)
if cnt >= limit then return 0 end
redis.call('ZADD', key, now, now .. ':' .. math.random())
redis.call('PEXPIRE', key, window)
return 1
# 代价：每个请求在 ZSet 里留一条记录。1万 QPS × 1000 配额 = 100万元素常驻，内存和 O(N) 清理要考虑

漏桶（Leaky Bucket）

请求进水，恒定速率出水，桶满则溢出（拒绝）。特点：输出绝对平滑，但不允许任何突发——哪怕下游此刻很空闲，流量也必须排队匀速通过。适合"保护脆弱下游"（如对接第三方 API、写数据库），不适合"保护自己"。

令牌桶（Token Bucket）

恒定速率往桶里放令牌，请求拿到令牌才能通过，桶满则令牌丢弃。特点：允许突发（攒下的令牌可以一次用掉），长期速率被严格限制。Sentinel 的 FlowRule 支持 controlBehavior = rate_limiter（匀速排队，漏桶思想）和默认的 default（快速失败，令牌桶思想）。

算法突发容忍输出平滑度典型问题
固定窗口差（临界 2 倍）不平滑临界突刺放过双倍流量
滑动窗口好较平滑统计开销、内存
漏桶无（强制排队）绝对平滑误杀正常突发；队列积压导致延迟
令牌桶好（吃存量令牌）长期平滑桶深度设置不当等于没限流
选型经验：面向 C 端用户、要防刷 → 滑动窗口（Sentinel 默认即可）；保护脆弱下游、写库 → 漏桶/匀速排队；对延迟敏感又允许秒杀突发 → 令牌桶。别在网关用固定窗口扛大促流量。
模块 2

分布式限流：GCRA 与 CRDT 两条路线

单机限流数内存即可，分布式限流必须依赖共享存储（Redis）或节点间协商。这里有两条学术和工程都验证过的路线。

GCRA（Generic Cell Rate Algorithm，通用信元率算法）

这是 Google Cloud Armor 限流功能使用的核心算法，也是 ATM 网络里做流量整形的老算法。它不用"数窗口内的请求数"，而是维护一个理论到达时间（Theoretical Arrival Time, TAT）：

# GCRA 核心逻辑（IETF RFC 7003 描述的连续状态模型）
# 每条限流规则定义：emission_interval（发射间隔，= 1/速率）+ tolerance（容忍突发量）
#
# 新请求到达，current_time 时刻：
#   if current_time < TAT - tolerance:  拒绝（来太早，桶里没配额了）
#   else: 放行，并更新 TAT = max(TAT, current_time) + emission_interval
#
# 特点：
# 1. 只需要维护一个浮点数 TAT，不存任何请求记录 → 内存 O(1) 而非 O(请求数)
# 2. 天然支持"平滑度 + 突发容忍"两个参数，等价于带突发限制的令牌桶
# 3. 精度不受时钟回拨影响（如果用单调时钟）
工程意义：ZSet 滑动窗口要为每个请求存一条记录，10 万 QPS 下 Redis 内存和清理成本很高；GCRA 每条规则只存一个 TAT 值。超大规模限流（网关层、云厂商产品）优先 GCRA 类算法。Google Cloud Armor 的 rate limit threshold + ban duration 就是基于它实现的。

CRDT 限流（无主协商的分布式限流）

思路：放弃"强一致的全局计数"，让每个节点本地计数，节点间通过 gossip 或 Redis 定期合并，用 CRDT（无冲突复制数据类型） 保证合并结果收敛。

CRDT 类型合并语义限流效果
PN-Counter（增减计数器）每节点维护 +N/-N 两个集合，合并取并集求和精确全局计数，但合并开销随节点数增长
G-Counter（只增计数器）每节点一个自增值，合并取 max限流常用。可能重复计数（节点 A 已同步的增量又被算一次）
LWW-Register最后写入者获胜（按时间戳）只保留最新快照，适合低频同步

代价与收益：CRDT 限流的精度是"最终收敛"，合并周期内各节点配额是过配的（over-admission）。例如全局限 10,000 QPS、20 个节点、5 秒合并一次：每个节点在合并周期内按 10,000/20=500 本地配额执行，极端情况下全局瞬时可达 10,000 + 19×500 = 19,500。所以 CRDT 限流必须把全局阈值调低（乘一个 0.7~0.9 的安全系数），用精度换可用性和零协调延迟。

什么时候用 CRDT 限流：① Redis 不可用也不允许限流失效的场景（多活架构）；② 限流规则允许 10%~30% 过配；③ 节点数中等（< 100）。绝大多数公司用"Redis 集中计数 + 本地兜底配额"就够了：Redis 正常走全局精确限流，Redis 挂了退化成本机限流（本地阈值 = 全局阈值 / 节点数），这是 Sentinel 集群限流的基础思路。
模块 3

限流层级：网关、应用、分布式怎么摆

限流放在哪一层，决定了它保护的范围和误伤的半径。原则：粗粒度放外层，细粒度放内层；外层保命，内层保公平。

层级典型实现粒度适用与注意
网关限流Nginx limit_req、Spring Cloud Gateway + RedisRateLimiter、Kong、EnvoyIP / 用户 / API 路径第一道防线，挡恶意流量。基于 IP 的要小心 NAT 出口误杀一整栋办公楼下单
应用限流Sentinel SphU.entry、Guava RateLimiter、Hystrix（舱壁）接口 / 方法 / 用户 / 热点参数贴近业务，能做差异化配额（VIP 双倍）。单机限流不解决单节点热点
分布式限流Redis + Lua、Sentinel 集群流控（Token Server）、GCRA 类实现全局资源（总库存、总短信量）保证全局总量不超。Redis 成了新单点，要评估 Redis 故障时的降级策略
客户端/接入侧SDK 内置退避、连接池上限单客户端防止自家客户端把自家服务打挂（重试风暴）

Nginx 网关限流配置（真实参数）

# 1. 定义限流区：按客户端 IP，10MB 状态区约存 16 万个 IP 状态
limit_req_zone $binary_remote_addr zone=api_limit:10m rate=50r/s;

# 2. 应用限流：burst=100 允许排队突发，nodelay 不延迟直接处理
location /api/ {
    limit_req zone=api_limit burst=100 nodelay;
    limit_req_status 429;
    # 超过 burst 的请求直接 429，不排队（nodelay）
    # 不加 nodelay 时，超出部分按 rate 速率延迟处理，客户端会明显感到变慢
}

# 3. 连接数限流（防慢连接攻击）
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;
limit_conn conn_limit 20;   # 单 IP 最多 20 个并发连接
分层配额要相乘不要相加：网关限 1,000 QPS、应用限 800 QPS，全局真实上限是 min(1000, 800 × 节点数)，不是 1000 + 800。配错方向（外层比内层松）会导致内层无限流可限、直接打满线程池。外层配额应该 ≥ 内层单机配额 × 健康节点数，且留 10%~20% 余量给节点扩缩容抖动。
模块 4

Sentinel 与 Hystrix 对比

Hystrix 在 2016 年后基本停止大版本演进（官方明确不再添加新特性），Sentinel 是它的替代者。但两者设计哲学不同，不是简单的"新版 vs 旧版"。

维度Hystrix（Netflix）Sentinel（阿里）
核心理念隔离：线程池隔离 + 信号量隔离，故障资源互相不占流量控制：一切皆可配额化（流控、熔断、热点、系统自适应）
隔离手段线程池隔离（默认，异步）、信号量隔离信号量隔离（并发线程数控制），没有线程池隔离
统计方式滑动窗口（10 个桶 × 1s），基于 RxJava 响应式滑动窗口（LeapArray，默认 2 桶 × 500ms）+ 多种统计结构
熔断判据错误百分比、异常数；Closed/Open/Half-Open慢调用比例、异常比例、异常数；同样三态
规则配置代码写死或 Archaius 动态配置（无官方控制台）动态数据源（Nacos / Apollo / ZK / Redis），控制台实时改规则秒级生效
生态Spring Cloud 官方集成（1.x 时代）Spring Cloud Alibaba、Dubbo、gRPC、WebServlet 全适配
系统保护无系统自适应保护：按 Load1 / CPU / RT / 线程数 / QPS 自动限流（BBR 思想）
性能开销较高（线程切换、响应式装箱）低（纯内存计数 + 无锁结构）
// Sentinel 代码示例：资源 + 流控规则 + 熔断规则
public static void initFlowRules() {
    List<FlowRule> rules = new ArrayList<>();
    FlowRule rule = new FlowRule("createOrder")   // 资源名
        .setCount(800)          // 单机阈值 800 QPS
        .setGrade(RuleConstant.FLOW_GRADE_QPS)
        .setStrategy(RuleConstant.STRATEGY_CHAIN)   // 关联流控：入口是 /order/create 才限
        .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER); // 匀速排队
    rules.add(rule);
    FlowRuleManager.loadRules(rules);
}

// 熔断规则：慢调用比例超 30% 且 RT 超 200ms，持续 10s → 熔断 10s
DegradeRule dr = new DegradeRule("queryStock")
    .setGrade(CircuitBreakerStrategy.SLOW_REQUEST_RATIO.getType())
    .setCount(0.3)               // 阈值 30%
    .setSlowRatioThreshold(200)  // RT 大于 200ms 算慢调用（ms）
    .setMinRequestAmount(20)     // 最少 20 个请求才评估，防止低流量误判
    .setStatIntervalMs(10000)    // 统计窗口 10s
    .setTimeWindow(10);          // 熔断持续 10s 后进入 Half-Open
DegradeRuleManager.loadRules(Collections.singletonList(dr));

// 使用：try-with-resources 包裹受保护调用
try (Entry entry = SphU.entry("createOrder")) {
    // 业务逻辑
} catch (BlockException e) {
    // 被限流/熔断/系统保护，走兜底
    return fallback();
}
选型结论：新项目直接 Sentinel。但注意 Sentinel 用信号量隔离而非线程池隔离：好处是无线程切换开销，坏处是被保护的依赖如果同步阻塞，当前线程仍然被占住。所以"超时设置"必须配（Sentinel 的熔断规则本身要求 RT 阈值，业务代码里也要有 RestTemplate/Feign 的 connect/read timeout），否则隔离形同虚设。
模块 5

熔断器状态机与工程实现

熔断器只有三个状态，但每个状态的进入条件、退出条件、探测策略决定了它是"救火队员"还是"事故放大器"。

状态行为进入条件
Closed 关闭正常放行所有请求，后台持续统计错误率/慢调用初始状态；或 Half-Open 探测成功后回到此态
Open 打开所有请求直接失败（或走 fallback），不调用下游，持续一个时间窗统计窗口内错误率/慢调用比例超过阈值（如 50% / 30%）
Half-Open 半开放行少量探测请求，成功若干次则 Closed，失败则回 OpenOpen 状态持续时间窗结束后自动进入
# 状态机文字版（对应 Resilience4j / Sentinel 行为）
Closed ──错误率>50% 持续10s──▶ Open ──10s 后──▶ Half-Open
  ▲                                  │                      │
  │                                  │                      ├─ 探测成功 → Closed
  └────────── 探测全部成功 ◀─────────┘                      └─ 探测失败 → Open

核心参数（Resilience4j CircuitBreaker 为例）

# application.yml 真实配置项
resilience4j.circuitbreaker.instances.stockService:
  slidingWindowType: COUNT_BASED      # COUNT_BASED 或 TIME_BASED
  slidingWindowSize: 50               # 按数量：最近 50 次调用；按时间：最近 50 秒
  minimumNumberOfCalls: 20            # 至少 20 次调用才评估，防低流量误判（关键！）
  failureRateThreshold: 50            # 失败率超 50% 触发熔断
  slowCallRateThreshold: 30           # 慢调用（RT>1s）比例超 30% 也触发
  slowCallDurationThreshold: 1s       # RT 超过 1s 算慢调用
  waitDurationInOpenState: 10s        # Open 状态持续 10s 后进 Half-Open
  permittedNumberOfCallsInHalfOpenState: 10  # Half-Open 放 10 个探测请求
  automaticTransitionFromOpenToHalfOpenEnabled: true
最容易犯的三个熔断错误：
① 没有 minimumNumberOfCalls：凌晨低峰期 5 个请求挂了 3 个就熔断，然后把全部流量打给 fallback，fallback 也挂 → 级联故障。
② fallback 又去调同一个故障下游：熔断是为了不调用它，fallback 里写"重试一次库存服务"，等于熔断白做。
③ Half-Open 探测流量太大：Open 10s 后一次性放进全部真实流量，下游还没恢复又被冲垮。探测请求要小（5~10 个），且最好优先用健康检查类轻量请求。
模块 6

降级策略：兜底数据与功能开关

降级不是"出错就返回 null"。好的降级是提前设计好的、分级的、可演练的服务能力收缩方案。

四级降级策略

级别做法适用场景
L1 兜底数据返回缓存/静态默认值（如默认商品图、"稍后重试"提示）推荐位、评论数、库存数量等非关键字段异常
L2 功能裁剪关闭非核心功能（推荐、足迹、积分计算）CPU/线程紧张，保核心下单/支付链路
L3 异步化同步改异步（下单后优惠券计算改消息队列），削峰写下游压力大，允许最终一致
L4 只读/维护页全站只读或静态化，引导去 App/小程序核心链路全面故障，止损

兜底数据的三种来源

# 1. 本地缓存兜底（最快，允许陈旧）
// 定时任务每 30s 刷新一次商品基础信息到 Caffeine，RPC 挂了用本地副本
Product p = localCache.get(id);
if (p == null) p = remoteService.get(id);   // 本地没有再走远程

# 2. 静态配置兜底（零依赖）
// 兜底文案、默认排序、降级开关的初始值都写在配置文件里，不依赖任何存储
// 关键：兜底数据本身必须"永远可用"，不能兜底数据也要查数据库

# 3. 降级开关（动态，秒级生效）
// 接入配置中心（Nacos/Apollo），事故中一键关闭功能，不用发版
boolean recommendOn = configCenter.getBoolean("feature.recommend.enabled", true);
if (!recommendOn) return emptyRecommendList();   // 直接返回空，不打下游
降级开关的三条纪律：① 默认值必须是"开"——配置中心挂了，功能默认可用，而不是默认全站降级；② 开关要能按用户维度灰度（先给 1% 用户关推荐，观察核心指标不掉再全量）；③ 每次大促前演练一遍——没演练过的降级开关，第一次用一定是反向操作（把正常功能关了）。
模块 7

热点参数限流

接口级限流解决"总量"，但秒杀场景的流量高度集中在一个参数值上：商品 A 占 90% 流量，接口级限 1000 QPS 对它毫无意义，商品 B 却被误伤。

Sentinel 的热点参数限流（Param Flow）对方法的某个参数值单独计数：

// 热点规则：第 0 个参数（商品ID）单机每秒最多 100 次
// 但给"爆款商品"单独开 1000 的例外配额（paramIdx=0, paramValue=SKU_12345）
ParamFlowRule rule = new ParamFlowRule("getSkuDetail")
    .setParamIdx(0)                    // 对第 0 个参数限流
    .setCount(100)                     // 每个参数值默认 100 QPS
    .setDurationInSecond(1);
ParamFlowRule exception = new ParamFlowRule("getSkuDetail")
    .setParamIdx(0).setCount(1000)
    .setParamValue("SKU_12345");   // 爆款商品单独配额
// 实际效果：普通商品 100 QPS，SKU_12345 走 1000 QPS 的独立令牌桶
场景做法
单参数热点Sentinel ParamFlow，对参数值独立计数 + 例外配额
热点 key 打缓存Redis 热 key 本地缓存（应用内缓存热 key，读多写少的数据）
热点 key 分片把 key 复制 N 份（key1~keyN），请求随机打其中一片，读时合并
全局热点Redis 侧对热点参数值单独计数（token:sku:12345 独立 key）
热点限流的代价：每个参数值一路独立计数，内存和统计开销随参数基数线性增长。10 万个 SKU 各一个桶，Sentinel 的 ParamMetric 会有可感知的 GC 压力。参数基数大（如 userId 级别）时，改用"统计 + 动态发现"：平时只统计，发现某个参数值占比突增（如超过总量 20%）再动态创建限流桶。
模块 8

与 WAF、业务风控的关系

三者都在"拒绝请求"，但拒绝的对象和依据完全不同。搞混的后果：用限流挡爬虫（挡不干净），用风控挡正常突发（误伤用户）。

体系拒绝依据判断对象典型实现
WAF请求内容特征（SQL 注入、XSS、恶意 UA、已知攻击载荷）单个请求本身ModSecurity、阿里云 WAF、AWS WAF（匹配规则 + 速率规则）
限流速率 / 并发量超配额请求的"量"，不管内容网关 limit_req、Sentinel、Redis 计数
业务风控行为模式异常（异地登录、批量注册、薅羊毛、撞库）用户/设备/会话的长期行为规则引擎 + 设备指纹 + 名单 + 模型评分

一条请求的完整检查链

请求 → CDN/WAF（内容特征、IP 信誉）
      → 网关限流（速率配额，全局总量保护）
      → 业务网关（登录态、权限）
      → 业务风控（行为识别：这个用户 1 分钟内领了 5 张券？设备集群？）
      → 应用层限流（接口级、热点参数级）
      → 熔断/降级（依赖异常时自我保护）
      → 业务逻辑
边界划分建议：WAF 挡"明显的恶意报文"，限流挡"量"，风控挡"伪装成正常用户的异常行为"。限流拒绝时返回 429 带 Retry-After 头；WAF/风控拒绝时返回 403 且不带细节（不告诉攻击者为什么被拦）。风控判定"黑名单用户"后，应该由风控系统通知限流系统对其降配额，而不是各判各的。
模块 9

十个线上坑

1
限流阈值拍脑袋定（"先限 1000 吧"）
正确姿势：阈值 = 单机压测容量 × 0.7，再按历史峰值系数验证。没压测过的数字，大促当天就是第一个倒下的。改一次阈值要能说清"依据是哪个压测报告的哪个数"。
2
网关按 IP 限流，误杀 NAT 后的一整个园区
学校、公司、移动网络共用出口 IP，单 IP QPS 轻松上千。按 IP 限流必须叠加：登录用户优先按 userId 限流，IP 限流阈值放宽且只挡明显异常。
3
熔断没有最小请求量阈值，低峰期误触
半夜 5 个请求挂 3 个，错误率 60%，熔断打开，fallback 又去打同一个下游，故障扩散。必须配 minimumNumberOfCalls（如 20）和 minimumRequestAmount。
4
熔断的 fallback 里重试同一个故障下游
熔断的意义就是"别调用它"。fallback 只能走：本地缓存、静态默认值、读副本、返回友好错误。任何对故障依赖的重试都是负优化。
5
级联限流：一层拒绝引发下一层流量放大
网关 429 后客户端立即重试，重试流量再次触发 429，循环放大；或者上游限流后大量请求涌入降级链路，把兜底缓存服务也压垮。限流必须配合客户端退避（指数退避 + jitter）和兜底链路自己的限流。
6
限流后直接返回 500 或空页面，用户体验崩了
正确姿势：返回 429 + Retry-After 秒数；页面显示"当前排队人数较多，预计 5 秒后可试"；能排队的场景（下单）进入等待页而不是拒绝。限流是保护系统，不是把用户拒之门外。
7
分布式限流把 Redis 打成了瓶颈
每个请求都去 Redis INCR，Redis 变成全链路最忙的组件，网络 RTT 和 Redis 单线程反而成为瓶颈。对策：本地批量预取（一次取 100 个配额本地消耗）、GCRA 类 O(1) 算法、只对核心接口走全局限流。
8
熔断打开期间，正常用户请求全部失败且没有任何提示
熔断是内部机制，对用户应该表现为"服务降级中"（少了推荐位、库存显示"查询中"），而不是全盘报错。要把熔断状态和降级策略联动，而不是各写各的。
9
Sentinel 集群流控的 Token Server 单点故障导致限流失效
集群模式依赖 Token Server 分配全局配额，Server 挂了若客户端没有降级策略，限流直接失效流量裸奔。要给 Token Server 配高可用，并配置"Server 不可用时退化成本机限流"。
10
限流/熔断规则从不复盘，一次配错全年受害
每次触发限流/熔断都要记录：触发时间、阈值、当时 QPS、拒绝量、影响用户数。每季度复盘一次阈值是否还合理。规则是活的，业务涨了 10 倍，阈值还是去年那个数，就是隐患。
自测

六道题

1. 固定窗口限流"限 100 QPS"，在第 1 秒最后 100ms 和第 2 秒前 100ms 各通过 100 个请求。这说明固定窗口的缺陷是？
正确答案：临界突刺。固定窗口在窗口边界处可能放过接近双倍流量，滑动窗口通过细分桶统计最近 N 个桶来消除这个问题。
2. 需要对接一个脆弱的第三方 API，对方要求"请求速率必须严格匀速，不允许任何突发"，应该选？
正确答案：漏桶。漏桶以恒定速率出水，不允许任何突发，适合保护脆弱下游。令牌桶允许吃掉存量令牌形成突发，反而不适合此场景。
3. Sentinel 相比 Hystrix 的核心设计差异是？
正确答案：Sentinel 流量控制为核心，Hystrix 隔离为核心。另外 Sentinel 支持系统自适应保护、动态数据源实时下发规则，Hystrix 2016 年后基本停止演进。
4. 关于熔断器 Half-Open 状态，哪种做法是对的？
正确答案：放少量探测请求。一次性放全部流量可能把刚恢复的下游再次冲垮，导致反复熔断。探测要小而轻。
5. GCRA 算法相比 ZSet 滑动窗口的核心优势是？
正确答案：只维护一个理论到达时间 TAT。ZSet 滑动窗口要为每个请求存一条记录，海量 QPS 下内存和清理成本高。GCRA 正是 Google Cloud Armor 使用的算法。
6. 网关限流配 1000 QPS、应用限流配 800 QPS × 3 节点，全局实际上限是？
正确答案：2400 QPS（min 约束）。分层限流是取 min 不是相加。外层配额应 ≥ 内层单机配额 × 健康节点数并留 10%~20% 余量，否则内层会先满、外层形同虚设。
