模块 1

安全架构四原则

原则不是口号，是遇到具体设计问题时给你答案的决策依据。每条原则都对应一类常见事故。

原则含义架构落地
纵深防御
Defense in Depth		多层控制，单层失效不致命网络层（WAF/DDoS）→ 网关层（认证/限流）→ 服务层（授权/校验）→ 数据层（加密/脱敏）→ 运维层（审计/堡垒机），每层都假设上一层可能被突破
最小权限
Least Privilege		每个主体只拿必需权限，且限期回收服务账号按库授权；DB 用户禁止跨库；AK/SK 按操作粒度拆分；离职/转岗自动回收
默认安全
Secure by Default		安全是默认值，不是配置项新服务默认开 TLS、默认无公网入口、默认拒绝；想开洞要显式申请，而不是默认全通
失败安全
Fail Safe / Fail Closed		出错时关闭通道，而不是敞开鉴权服务挂了拒绝登录（而不是放行）；配置拉取失败用本地默认安全配置；熔断时走降级而不是裸奔

另外三条工程原则

零信任输入
不信任任何输入，包括"内网服务传来的"。反序列化、SQL 拼接、命令执行的入口全部按不可信数据处理。
攻击面最小化
每多一个端口、端点、依赖、管理员入口，就多一分暴露。下线废弃接口，关掉不用的端口，删掉没人用的 AK。
职责分离
开发不碰生产数据、运维不碰代码、DBA 不审自己的变更。敏感操作双人控制，关键权限分人持有。
用原则裁决争论。当"这个内部接口要不要做鉴权"吵不出结果时，默认安全 + 零信任输入直接给答案：要，而且默认就要。原则的价值就是把"每次重新论证"变成"按既定方针办"。
模块 2

威胁建模入门：STRIDE

威胁建模（Threat Modeling）是在设计阶段系统化地找威胁，而不是上线后靠渗透测试撞运气。核心工具是 DFD（数据流图）+ STRIDE 清单，两小时能过一遍核心链路。

STRIDE 六类威胁

威胁违反的性质典型场景与缓解
S 假冒
Spoofing		认证伪造 token / 盗用 session。缓解：强认证、MFA、短期凭证
T 篡改
Tampering		完整性改请求金额、改数据库记录。缓解：签名、参数化查询、审计日志
R 抵赖
Repudiation		不可否认"我没操作过"。缓解：全操作审计日志、操作留痕带身份与时间
I 信息泄露
Information Disclosure		机密性接口返回多余字段、日志打印敏感信息。缓解：字段级脱敏、最小返回
D 拒绝服务
Denial of Service		可用性流量打满、慢请求占满连接。缓解：限流、熔断、容量冗余
E 提权
Elevation of Privilege		授权普通用户访问管理接口、水平越权看别人订单。缓解：RBAC + 对象级授权

四步实战流程

画 DFD：四个元素——外部实体（用户/第三方）、进程（服务）、数据存储（DB/缓存）、数据流（API 调用）。重点是标出信任边界（内网/外网、不同租户之间）。
对每个元素套 STRIDE：不是每个元素都中六枪，但每个元素都要过一遍清单，防止遗漏。
风险矩阵排序：影响 × 概率分成四象限，先处理"高影响 × 高概率"（通常是注入和越权）。
处置并记录：每个威胁三条出路——缓解（加控制）、转移（买保险/用云商能力）、接受（写明风险登记，责任人签字）。

示例：下单接口的 STRIDE 分析（节选）

DFD 元素威胁处置
POST /api/ordersT：篡改金额参数金额服务端重算，不信客户端传值
POST /api/ordersI：返回过多字段泄露他人信息响应 DTO 白名单，禁止直接返回实体
GET /api/orders/{id}E：改 id 看别人订单（IDOR）服务端校验订单归属当前用户
用户 → 网关S：伪造 JWT短期 token + 签名校验 + 黑名单撤销
订单 DBR：删库后不认账binlog + 操作审计日志异地留存
短信网关D：被打爆影响正常短信按手机号限流 + 图形验证码
威胁建模的产出物是一页威胁清单，不是几百页报告。清单随架构文档一起入库、一起评审。新功能上线前用同一套流程过一遍——这就是安全左移的最轻量形态。
模块 3

身份与访问管理 IAM

IAM 四件事：身份（你是谁）、认证（证明你是你）、授权（你能干什么）、审计（你干了什么）。四件缺一件，前面三件都白做。

RBAC vs ABAC

维度RBAC 基于角色ABAC 基于属性
模型用户 → 角色 → 权限，静态绑定策略匹配属性：用户属性 + 资源属性 + 环境属性
例子角色"财务"拥有"查看报表"权限部门=财务 且 资源密级=内部 且 时间=09:00-18:00 且 地域=北京
优点简单、直观、好管理细粒度、灵活、能表达复杂策略
缺点角色爆炸；无法表达动态条件策略复杂、调试难、性能开销
适用内部管理系统、权限不常变的场景多租户 SaaS、强合规、动态授权场景

工程实践：主体 RBAC 打底（角色管理不爆炸），热点资源用 ABAC 补细粒度。全 ABAC 的系统策略文件能长到没人敢改。

凭证管理

  • JWT 双 token：access token 15 分钟 + refresh token 7 天轮换。access 短到不需要复杂撤销机制；refresh 泄露可单独吊销。
  • OAuth2 / OIDC：把"管密码"这件事外包给专业身份提供商；自建登录只在不接外网的内部系统考虑。
  • API Key 治理：按调用方 + 用途一对一发，禁止共用；带速率限制；90 天强制轮换；泄露时可单发吊销。

零信任：不信任内网

控制做法
服务身份每个服务一个身份（mTLS 证书或 SPIFFE 工作负载身份），调用方身份可验证
东西向加密服务间全部 mTLS，内网流量也加密，防嗅探与中间人
短期凭证云上 STS 临时凭证 15 分钟级，不用长期 AK；凭证自动轮换
持续评估每次访问都认证授权，不因"已在内网"免检；异常行为实时降权
认证服务的故障处理必须是 fail closed。鉴权中间件异常时直接放行，等于把认证变成装饰品——攻击者只要想办法让你的鉴权服务超时（比如打满它的连接），就获得了全场通行证。正确做法：异常拒绝 + 告警，可用性靠副本和限流保证，不靠放行保证。
模块 4

数据安全：分级、加密、脱敏

数据安全的第一步不是加密，是知道自己有什么数据。没有分级分类的加密等于给所有门上同样的锁——贵的浪费，薄的失守。

数据分级示例

级别定义加密要求访问与审计
公开已公开信息（商品介绍）传输 TLS 即可不限访问；不要求审计
内部一般业务数据（订单记录）传输 TLS + 磁盘加密员工按需授权；登录审计
秘密用户 PII、手机号、地址传输 TLS + 存储加密 + 字段级加密按需授权 + 全操作审计 + 脱敏展示
机密支付凭证、鉴权密钥字段级加密（KMS 管钥）+ 硬件加密机可选双人控制 + 全操作告警 + 禁止导出

加密分层

  • 传输加密：TLS 1.2+（推荐 1.3），禁用 SSLv3 / TLS 1.0 / 1.1 和弱套件（RC4、DES）。证书用 ACME 协议自动续期，杜绝"证书过期导致全站故障"。
  • 存储加密：数据库 TDE + 磁盘加密防"硬盘被盗"；对象存储服务端加密防"备份泄露"。
  • 字段级加密：手机号、身份证用 AES-256-GCM 应用层加密——防的是 DBA 拖库、日志误打、备份外发。注意：字段加密后该字段无法直接索引和模糊查询，需要检索的字段用确定性加密或单独建哈希索引，两者都要在方案评审时想清楚。

KMS 与信封加密

# 信封加密：数据密钥加密数据，主密钥加密数据密钥
1. 从 KMS 生成 DEK（数据密钥）—— KMS 返回明文 DEK + 密文 DEK
2. 用明文 DEK 在本地加密业务数据
3. 销毁明文 DEK，密文 DEK 与密文数据一起存储
4. 解密时：把密文 DEK 交给 KMS 换回明文 DEK，本地解密

# 好处：
# - 大批量数据加密不用每次调 KMS（本地加密，无网络开销）
# - 轮换 KEK 只需重新加密 DEK，不用重加密全库
# - 权限收敛在 KMS：谁能调 Decrypt，谁能解密数据

脱敏

场景做法
展示脱敏138****1234；前端按角色决定是否给全量（客服看全号、运营看掩码）
日志脱敏日志框架配脱敏规则：手机号/身份证/token/密码字段正则替换后再落盘
测试数据脱敏生产数据出库必须脱敏；需要保留格式的用 FPE（保格式加密），保留关联关系的用映射表
接口返回响应 DTO 白名单；禁止把实体对象直接序列化返回（字段泄露的重灾区）
密钥管理三条红线：① 密钥不硬编码在代码、配置、镜像里——进 Git 就等于公开；② 密钥不进日志——日志的受众范围远大于密钥该有的范围；③ 用 KMS / Vault 统一管，带版本、带轮换、带审计。满足这三条，密钥泄露的爆炸半径才可控。
模块 5

应用安全控制点：OWASP 到架构层

OWASP Top 10 是漏洞清单，架构师的活是把每条映射成某个架构层上的控制点——否则清单永远停留在安全团队的 PPT 里。

OWASP Top 10（2021）架构层控制点具体措施
A01 失效的访问控制网关 + 服务双层统一鉴权网关；对象级授权（IDOR：查订单必须校验归属）；默认拒绝；管理接口独立分区
A02 加密失败传输 + 存储全链路 TLS 1.2+；KMS 信封加密；禁用 MD5/SHA1 于安全场景
A03 注入服务层参数化查询 / ORM；命令执行白名单；模板引擎自动转义；输入按白名单校验
A04 不安全设计设计阶段STRIDE 威胁建模进评审；用例安全评审；威胁清单入库
A05 安全配置错误部署层CIS 基线扫描；IaC 模板统一收口；默认口令强制修改；目录列表关闭
A06 脆弱组件供应链SCA 依赖扫描（已知 CVE）；SBOM 归档；补丁 SLA：严重 24h / 高危 7 天
A07 认证失败IAMMFA；登录限速 + 锁定；短期 token；禁止明文传输凭证
A08 数据完整性失败供应链 / 更新镜像签名验证（cosign）；更新通道加密 + 签名；CI/CD 权限最小化
A09 日志监控失败运维登录/越权/删改全记录；日志异地集中；异常行为告警（防"被拖库半年没人发现"）
A10 SSRF服务层出站白名单；屏蔽元数据地址（169.254.169.254）；禁止用户控制完整 URL

IDOR 越权：最小示例

// 反例：只判断了"登录"，没判断"归属"
@GetMapping("/api/orders/{id}")
public OrderVO get(@PathVariable Long id) {
  return orderService.findById(id);   // 改 id 就能看任何人的订单
}

// 正例：对象级授权，归属不符一律 404（不提示"存在但无权看"）
@GetMapping("/api/orders/{id}")
public OrderVO get(@PathVariable Long id, @LoginUser Long userId) {
  OrderVO order = orderService.findById(id);
  if (!order.getUserId().equals(userId)) {
    throw new NotFoundException();   // 404 而非 403，不泄露资源存在性
  }
  return order;
}
控制点放错层 = 没放。权限校验只写在前端按钮上，后端接口裸奔，一个 curl 就打穿。鉴权要么在网关统一做（横切关注点），要么在每个服务的方法级强制做，唯独不能只做在客户端。
模块 6

SDL 与合规落地

安全开发生命周期（SDL）把安全活动嵌进研发流程；合规要求（等保、个保法）最终都要翻译成具体的架构动作，否则过检就是补材料。

SDL 六阶段

阶段安全活动工具 / 产出
需求安全需求入库：数据分级、合规范围、隐私影响评估安全需求清单；PIA 报告
设计威胁建模（STRIDE + DFD）、安全架构评审威胁清单 + 处置记录
开发安全编码规范；密钥扫描；依赖漏洞扫描Semgrep / gitleaks / Trivy 进 CI，门禁阻断
测试SAST 静态扫描 + DAST 动态扫描 + 渗透测试SonarQube / OWASP ZAP / 人工渗透报告
发布配置基线核查；SBOM 归档；镜像签名配置核查单；签名镜像
运维漏洞响应 SLA；补丁管理；安全事件响应严重 24h / 高危 7 天 / 中危 30 天闭环

等保 2.0（三级）对架构的要求

合规要求架构落地动作
安全通信网络网络分区：DMZ / 应用区 / 数据区，区之间防火墙策略默认拒绝，只放行必要端口
传输加密全链路 TLS 1.2+，含内部东西向流量；证书集中管理自动续期
安全区域边界边界接入控制 + 入侵防范（WAF/IDS）；区域间访问需显式授权
安全审计操作日志集中采集、异地留存 ≥ 6 个月、防篡改（只写存储）
集中管控统一身份源（SSO）；运维操作走堡垒机；高危操作双人控制

个保法（PIPL）对架构的要求

合规要求架构落地动作
最小必要收集字段清单评审制：新增收集字段需说明必要性；能少收就不收
单独同意同意管理服务：记录每项处理的同意/撤回时间戳；撤回可执行（停用数据）
可删除权用户数据可定位、可删除——包括备份：逻辑删除 + 备份过期策略，不是只删主库
跨境传输出境安全评估 / 标准合同；架构上数据分区存放，境内数据不出境集群
泄露通知数据泄露 72 小时内通知监管与用户；架构支撑：影响面评估能力（知道哪些数据、涉及多少人）
合规的正确姿势是"一次设计，处处过检"。按等保三级设计的分区、加密、审计，同时覆盖个保法的删除权与同意管理——两套要求底层是同一套控制。反过来，为过检补材料、过检后拆除的做法，既贵又假，一出事全暴露。
模块 7

十个真实的坑

1
安全后补
上线前一周才找安全团队，补出一堆"紧急改造"，成本是设计期做的 5~10 倍。把威胁建模放进方案评审环节，两小时换两周返工。
2
过度依赖 WAF
以为买了 WAF 就安全。WAF 防不住业务逻辑漏洞（越权、IDOR、重复提交）和 0day，它的规则库永远滞后于新攻击手法。
3
密钥硬编码
代码里写死 API Key、数据库密码，一进 Git 历史永远删不干净。用 KMS/Vault + CI 密钥扫描（gitleaks/trufflehog），提交时自动拦截。
4
日志泄露敏感信息
日志打印完整手机号、token、密码、身份证。日志的受众（运维、监控平台、日志厂商）远大于密钥该有的范围。日志框架统一配脱敏规则，落盘前替换。
5
权限只在前端控制
按钮藏起来了，接口没鉴权，一个 curl 就越权。鉴权必须在网关或服务端强制，前端控制只是体验不是安全。
6
内部流量裸奔
东西向无认证无加密，一个服务被攻破（或被员工利用）全网失守。服务间 mTLS + 服务身份，把内网当敌对环境。
7
已知 CVE 不修
依赖组件爆高危漏洞，没人跟踪没人升级，直到被扫出来通报。SCA 扫描 + SBOM 清单 + 补丁 SLA（严重 24h / 高危 7 天）闭环。
8
测试数据用生产真数据
"图省事"直接拷生产库到测试环境，测试库被拖库等于生产泄露。生产数据出库必须脱敏；需要格式保留用 FPE。
9
鉴权服务故障时 fail open
鉴权中间件异常直接放行，攻击者打满鉴权服务就获得全场通行证。fail closed：异常拒绝 + 告警，可用性靠副本和限流保证。
10
没有密钥轮换与泄露预案
密钥泄露后不知道怎么换、不敢换，只能重启了事。KMS 带版本支持轮换；泄露应急预案提前演练（吊销 → 轮换 → 审计 → 复盘）。
自测

六道题

1. STRIDE 中的 T（Tampering）指的是哪类威胁？
正确答案：篡改。典型场景是修改请求参数（如订单金额）、篡改数据库记录。对应控制：服务端重算关键值、参数化查询、全操作审计日志。
2. 鉴权服务出现故障时，正确的架构行为是？
正确答案：fail closed。放行等于把认证变成装饰品——攻击者只要让鉴权服务超时就获得全场通行证。可用性问题用副本、限流、降级（只读也不该匿名）解决，不用安全换可用。
3. 用户改订单 ID 就能查看他人订单，这类漏洞的架构层防御是？
正确答案：对象级授权。这就是 IDOR（不安全直接对象引用），OWASP A01。ID 用 UUID 只是增加猜测难度，不是防御；验证码防机器人不防越权。唯一正解是服务端每次校验资源归属。
4. 关于数据库密码等密钥的管理，正确的做法是？
正确答案：KMS / Vault 统一管理。代码常量会进 Git 历史；配置中心明文 = 谁能读配置谁就能拿密码；镜像环境变量对任何能拉到镜像的人可见。只有 KMS 模式满足权限收敛 + 轮换 + 审计三要素。
5. RBAC 与 ABAC 的核心区别是？
正确答案：角色静态 vs 属性动态。RBAC：用户→角色→权限，简单但难表达"只有财务在工作时间能看报表"这类条件。ABAC 用属性策略表达细粒度动态授权，代价是策略复杂。实践是 RBAC 打底 + 热点资源 ABAC 补细粒度。
6. 日志里打印了用户完整手机号和登录 token，违反了哪条原则/要求？
正确答案：脱敏与最小暴露。日志的受众（运维平台、监控系统、日志厂商）远大于手机号和 token 该有的可见范围。日志框架应在落盘前统一做正则脱敏，敏感字段一律掩码或丢弃。
