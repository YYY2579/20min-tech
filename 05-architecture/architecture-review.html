二十分钟学会架构评审

这篇教的是怎么判断别人的技术方案对不对。写方案是执行能力，评审方案是判断能力 —— 后者才是往架构岗走的门槛。核心不是挑刺，是在方案上线前把风险找出来。

开始前

先建立一个正确的心态

架构评审（Architecture Review，指在方案落地前，由一组有经验的人对设计文档做风险审查的过程）最容易走偏成两件事：一是变成挑刺大会，谁说得狠谁显得厉害；二是变成走过场，大家点头通过，出了事再复盘。这两种都错。

评审的目标是降低不确定性，不是证明谁聪明。方案里有"事实错误"要指出来，但更多的是"取舍不同"——同样一个问题有多个合理答案，评审要做的是把取舍摆到台面上，确认作者是知情地做了选择，而不是没意识到。
评审的是方案，不是人。所有问题都对着"这个设计"说，不对着"你怎么连这都没想到"说。语言上多用"这里如果 X 会怎样"，少用"这明显不对"。
评审要有产出。一场没有留下"待办清单 + 负责人 + 截止时间"的评审等于没开。附录给了一份可直接用的清单模板。
评审的深度和方案的影响面成正比。改一个内部工具接口，口头对齐即可；动支付主链路或数据模型，必须走完整流程。别对所有方案用同一把尺子。
一句话预热：评审者最值钱的能力不是"我懂多少技术"，而是"我知道哪里会出事"。这篇文档把"哪里会出事"拆成了 8 个维度：目标、量级、容量、可用性、数据、可观测性、成本、反模式。每个维度都给了可直接问的问题。
模块 1

评审到底在评审什么

新手评审者拿到一份方案，会本能地去挑技术细节的错。老手会先做一件事：把方案里的论断分成三类，因为三类问题的处理方式完全不同。

类型特征评审者的正确动作
事实错误客观错了。例如"Redis 单线程所以不会有并发问题"、"MySQL 主从是强一致的"、"HTTP 默认有超时"必须当场指出并纠正。这类问题没有商量余地，它是知识缺口，讲清楚原理即可
取舍不同有多个合理答案。例如选 MySQL 还是 PostgreSQL、用同步还是异步、要不要分库分表不要说你错了。要问：你为什么这么选？约束条件是什么？另一个选项的代价你评估过吗？
信息缺失方案没说清，无法判断对错。例如没说 QPS 量级、没说一致性要求、没说失败路径这是最高频的问题。把缺失的信息一条条问出来，往往问着问着作者自己就发现问题了

风险的量化公式

评审的本质是在做风险排序。风险不是一个模糊的词，它可以粗略量化：

# 风险 ≈ 发生概率 × 影响面 × 不可逆程度

发生概率：这个故障在一年内会发生的可能性有多大？
          （比如"磁盘写满"在日志不清理的机器上几乎是必然）

影响面：发生时会波及多少用户 / 多少业务？
          （比如"某个内部报表挂了" vs "支付全链路挂了"）

不可逆程度：能不能快速回滚？会不会永久丢数据？
          （比如"多删了一列"和"删库"的不可逆程度天差地别）

# 评审的时间应该按这个乘积分配，而不是平均分配
最容易被忽视的一类：不可逆的破坏性操作。很多方案对"性能"、"可用性"讨论得很细，却对"这个操作一旦执行能不能撤销"只字不提。
评审时必须单独问：这个变更能不能灰度？能不能回滚？回滚需要多久？有没有可能丢数据？尤其是数据迁移、schema 变更、删表删列、批量刷数据这四类操作，必须逐个确认回滚方案。
模块 2

拿到方案先问的 5 个问题

不管方案多长，先问这五个问题。它们能在 5 分钟内帮你判断这份方案"有没有想清楚"，也决定了后面评审要花多少力气。

1 · 量级多大
QPS 多少？峰值多少？数据量多大？用户多少？没有量级就没有架构。十万 QPS 和一百 QPS 的方案完全不同。如果作者答不上来，说明方案还没到能评审的阶段
2 · 单点在哪
哪个组件挂了会导致整体不可用？有没有备份？切换要多久？单点（SPOF，Single Point of Failure，单点故障）是可用性的头号敌人
3 · 挂了怎么办
依赖的下游超时了怎么办？数据库主库挂了怎么办？缓存全失效了怎么办？方案里有没有"失败路径"的设计
4 · 一致性要求
数据能丢吗？能短暂不一致吗？能接受最终一致吗？一致性要求决定了技术选型的下限，必须先明确
5 · 成本多少
机器、带宽、存储、人力各花多少？人力成本最常被漏掉——多引入一个中间件，就要有人长期维护它

这五个问题的追问话术

问题继续追问
量级这个 QPS 是日均还是峰值？峰值系数取了多少？数据量是当前还是三年后？增长曲线是什么形状（线性还是指数）？
单点这个组件本身有高可用吗？它依赖的东西有高可用吗？故障切换是自动还是手动？切换期间的请求怎么办？
失败下游超时设了多少？超时后是重试、降级还是报错？重试会不会放大流量？有没有熔断？
一致性能接受丢多少数据（RPO）？能接受中断多久（RTO）？读到自己刚写的数据是硬需求吗？
成本这套东西谁来运维？新增了几个需要 7×24 值班的组件？有没有更简单的替代方案？
为什么这五个问题最有效：它们不涉及具体技术选型，所以不会引起作者防御心理；但它们直接对应了架构的四个根本约束 —— 规模、可用、一致、成本。一份答不上这五问的方案，细节写得再漂亮也是空中楼阁。
模块 3

容量与性能评审

这是评审里最容易"看起来有数据、其实全是错的"的部分。三个高频错误：用均值、用不真实的压测数据、把峰值当均值规划。

QPS 估算的标准方法

# 从业务量反推 QPS，而不是拍脑袋

第一步：日均请求数 = 日活用户数 × 人均请求次数
第二步：平均 QPS = 日均请求数 / 86400（一天的秒数）
第三步：峰值 QPS = 平均 QPS × 峰值系数

# 举例：100 万日活，人均 20 次请求
日均请求 = 1,000,000 × 20 = 20,000,000
平均 QPS = 20,000,000 / 86400 ≈ 231
峰值系数取 5 → 峰值 QPS ≈ 1,157

# 注意：峰值系数不是常数
# 普通业务 3~5；有早晚高峰的业务 5~10；
# 秒杀 / 抢购 / 春晚红包可以到几十甚至上百倍
评审点要问的问题 / 常见错误
峰值系数作者用的系数是多少？依据是什么？错误做法：直接拿平均 QPS 去做容量规划。结果就是高峰期必崩
读写比读多写少还是写多读少？这决定了要不要缓存、要不要读写分离
单请求成本一个请求打几次数据库？调几个下游？QPS 要乘以"每请求的下游调用数"才是下游的真实压力
热点分布流量是均匀的还是有热点？均匀假设往往不成立，一个爆款商品的流量可能占全站 30%

延迟指标：只看 P99，别看均值

为什么均值毫无意义：假设 100 个请求，99 个耗时 10ms，1 个耗时 3000ms。均值是 (99×10 + 3000) / 100 ≈ 40ms，看起来很美。但那个 3000ms 的请求就是一个真实用户卡了三秒。
用户体感由尾延迟决定，不是均值。所以性能指标必须看分位数：P50（中位数）、P95、P99、P999。P99 = 1000ms 意味着 1% 的请求超过 1 秒 —— 在日均百万请求下，这就是每天一万个卡顿的用户。
指标含义怎么用
P50一半请求比它快看"典型用户"的体感
P9999% 请求比它快性能验收的主指标。通常要求 P99 小于某个阈值
P99999.9% 请求比它快看极端情况，反映 GC、锁竞争、慢查询
均值算术平均几乎不要用于性能判断，会被长尾拉偏

压测数据要真实

  • 数据量要真实：在空表上压测，索引全在内存里，结果毫无参考价值。要用接近生产的数据量（比如 5000 万行）压。
  • 请求分布要真实：按生产实际的读写比、参数分布、热点比例来压，别只用同一个 ID 循环。
  • 网络要真实：压测机和被测服务在同一台机器上，省掉了网络往返，结果会偏乐观。跨机房、跨可用区要单独测。
  • 要压到极限：只压到 50% 负载没意义。要找到拐点 —— 从哪个 QPS 开始延迟陡增、错误率上升。
容量评审的黄金问题："这套系统在单节点故障、流量翻三倍的情况下，还能不能撑住？" 如果答案是不能，就要问清楚降级方案是什么，以及降级后哪些功能会受影响。容量规划不是算"能撑多少"，而是算"撑不住的时候会发生什么"。
模块 4

可用性评审

可用性评审的核心动作只有一个：逐层列出所有单点，然后问每一层的故障处理方案。单点不可能全部消除，但必须每一个都有明确的态度（消除 / 冗余 / 接受并降级）。

单点清单：从外到内逐层扫

层次常见单点典型问题
入口层DNS、CDN、负载均衡（LB）、WAFLB 是单台还是集群？DNS 挂了有没有备用解析？证书什么时候到期？
网关层API 网关、鉴权服务网关挂了所有流量都进不来，它自己有没有多实例？
应用层无状态应用实例实例挂一个会不会影响？有没有健康检查摘除？
缓存层Redis 主节点主挂了多久恢复？恢复期间打库会不会把库打穿？
数据层MySQL 主库、分片主库挂了切换要多久？切换时会不会丢数据？
中间件MQ、注册中心、配置中心注册中心挂了服务还能互相发现吗？配置中心挂了能启动吗？
外部依赖第三方支付、短信、地图第三方挂了怎么办？有没有兜底？超时设多少？
基础设施机房、可用区、电力、时钟单机房部署吗？有没有跨可用区？NTP（网络时间协议，用于同步机器时钟）靠谱吗？

故障域隔离

故障域（Failure Domain，指一个故障能同时影响的资源范围）隔离的意思是：让一次故障的影响范围尽可能小。评审时要问：

  • 物理隔离：多个可用区部署，还是全挤在一个机柜里？
  • 逻辑隔离：多租户共用一套资源吗？一个大客户把资源占满，会不会影响其他客户？
  • 依赖隔离：核心业务和边缘业务共用同一个数据库 / 缓存吗？边缘业务拖垮共享资源怎么办？
  • 线程隔离：调用不同下游用同一个线程池吗？一个下游变慢会不会把线程池占满，拖垮所有调用？

降级预案

降级（Degradation）指在资源不足或依赖故障时，主动关闭非核心功能，保住核心链路。评审时要问：这个系统的核心功能是哪一个？故障时哪些功能可以砍掉？砍掉的开关在哪，谁能一键触发？
典型降级：关掉个性化推荐返回默认列表、关掉实时库存展示、把同步调用改成异步、返回缓存里的旧数据、直接返回兜底文案。

优雅停机

发布、扩缩容时进程会被 kill。评审时要确认：收到停止信号（SIGTERM）后，进程会不会先把正在处理的请求做完、从注册中心摘除、再把连接关掉？如果直接 kill -9，正在处理的请求全部失败，用户看到 502。

依赖超时与熔断

# 超时（Timeout）：没有超时的外部调用是定时炸弹
✗ 错误：调用下游不设超时，下游卡住时自己的线程/连接全被占满
✓ 正确：每个外部调用都要设连接超时和读取超时，且超时值要有依据

# 熔断（Circuit Breaker）：下游持续失败时，快速失败而不是继续打
# 三态：
关闭（正常放行）→ 失败率超阈值 → 打开（直接拒绝，不打下游）
    → 等待一段时间 → 半开（放少量请求试探）
    → 成功则关闭，失败则继续打开

# 重试（Retry）：重试必须有上限、有退避、只重试幂等的操作
✗ 无限重试：下游越慢越重试，流量翻倍，把下游彻底打死
✓ 有限重试 + 指数退避 + 抖动：重试 2~3 次，间隔 100ms/200ms/400ms 加随机
重试放大陷阱（Retry Storm）：假设 A 调 B、B 调 C，每层都重试 3 次。C 抖了一下，B 的重试把流量放大 3 倍，A 的重试再放大 3 倍 —— C 承受的是 9 倍流量，本来只是抖动，结果被打死。评审时要问：重试链路是不是每层都在重试？应该只在最靠近用户的一层重试，或者用统一的超时预算。
模块 5

数据评审

数据是架构里最不能出错的资产 —— 机器挂了可以重启，数据丢了不可逆。数据评审围绕五件事：一致性、增长、备份、变更、删除。

1. 一致性要求是否明确

一致性级别含义典型场景
强一致任何时刻读到的都是最新写入的值账户余额、库存扣减、订单状态。代价最高，需要分布式事务或单点串行
最终一致写入后一段时间内收敛到一致，中间可能读到旧值缓存刷新、搜索结果、Feed 流、统计报表
弱一致不保证收敛，只保证"最终会"点赞数、浏览量这类可以丢一点的数据
评审必问：这份方案里，哪些数据是强一致需求？很多事故的根源是把强一致需求当成了最终一致（比如用缓存做库存，结果超卖），或者反过来，给非核心数据上了分布式事务，把系统复杂度抬到天上，收益却为零。一致性要求要按字段明确，不是按系统。

2. 数据量增长曲线

  • 当前多少行？日增多少？三年后多少？ 线性增长和指数增长的处理方式完全不同。
  • 单表多大就撑不住了？ 经验值：MySQL 单表超过 2000 万行，查询性能开始明显下降（前提是有合适索引）。
  • 增长最快的表是哪个？ 通常是日志、流水、消息这类只增不减的表，它们才是分库分表的第一目标。
  • 有没有归档策略？ 三年以上的历史数据是留着、归档到冷存储、还是直接删？

3. 备份与恢复演练

# 两个关键指标，必须能明确回答
RPO（Recovery Point Objective，恢复点目标）：
    最多能容忍丢多少数据？比如 RPO = 5 分钟，意味着可以丢最近 5 分钟的数据

RTO（Recovery Time Objective，恢复时间目标）：
    最多能容忍中断多久？比如 RTO = 30 分钟，意味着半小时内要恢复服务

# 评审必问：
1. 备份频率是多少？是全量还是增量？
2. 备份存在哪？和主库在同一个机房吗？（同机房等于没备份）
3. 最近一次"真实恢复演练"是什么时候？恢复耗时多久？
4. 备份文件加密了吗？能校验完整性吗？（备份损坏 = 没有备份）
最经典的数据事故：备份存在但恢复不了。很多团队每天备份，但从没演练过恢复，真出事时发现备份文件损坏、版本不兼容、或者恢复要花 8 小时（远超 RTO）。评审时"有没有备份"不是问题，"有没有演练过恢复"才是。没有演练过的备份等于没有备份。

4. Schema 变更方案

变更类型风险评审要问
加字段低（多数情况秒级）有没有默认值？大表加字段会不会锁表？
改字段类型高（可能锁表 + 数据转换）用在线 DDL 工具（如 gh-ost、pt-online-schema-change）吗？
删字段 / 删表极高（不可逆）确认过没有代码在用吗？有没有先改名观察一段时间？
加索引中（大表建索引会锁写）是在线建索引吗？会不会影响写入？
数据迁移极高双写还是停机？怎么校验迁移前后一致？能不能回滚？

5. 删除策略

  • 软删还是硬删？ 软删（用 is_deleted 标记）保留数据可追溯，但表会越来越大，且所有查询都要带过滤条件。
  • 硬删的代价是什么？ 数据不可恢复，且删除大表会占用大量 IO、产生大量 binlog。
  • 合规要求呢？ 用户注销后必须删除个人数据（GDPR、《个人信息保护法》等要求），但"删除"要覆盖主库、从库、备份、缓存、日志、数仓 —— 评审时要问清楚范围。
  • 级联删除吗？ 删一个用户，他的订单、消息、文件都要一起删吗？外键约束（Foreign Key）会不会导致删除失败或误删？
数据评审的一句话总结：把每一次"数据会变化"的操作，都问一遍"变了之后能不能变回来"。能变回来的，风险可控；变不回来的，必须有额外的谨慎（灰度、双写、先观察、再删除）。
模块 6

可观测性评审

可观测性（Observability，指通过系统的外部输出——指标、日志、链路——推断系统内部状态的能力）经常被当成"上线后再说"的事，但它是评审里性价比最高的一块：没有可观测性，出了故障你连"哪里坏了"都不知道，恢复时间会被无限拉长。

黄金四信号（Four Golden Signals）

Google SRE 提出的四个必看指标，评审时逐条确认方案是否覆盖：

信号英文看什么
延迟Latency请求耗时。要区分成功请求和失败请求的延迟（失败的快速返回会拉低平均延迟，掩盖问题）
流量TrafficQPS、并发数、请求量，反映系统负载
错误Errors错误率、错误码分布。要区分"显式错误"（5xx）和"隐式错误"（200 但内容是错的）
饱和度Saturation资源有多满：CPU、内存、连接池、队列长度、磁盘 IO。饱和度是故障的先行指标

告警要指向用户影响，不要指向机器状态

反面案例："CPU 超过 80% 就告警"。CPU 80% 时用户可能完全没感觉，这是噪音告警，久而久之所有人都麻木了（告警疲劳）。
正确做法：告警要基于 SLO（Service Level Objective，服务等级目标，比如"P99 延迟 < 200ms，可用性 > 99.9%"）。告警触发条件是"错误预算被快速消耗"—— 也就是"用户正在受影响"。
评审必问：这条告警响了，值班的人知道要做什么吗？如果不知道，它就不该是告警，应该是仪表盘上的一个指标。
评审点要问的问题
trace_id有没有全链路追踪 ID？一个请求从入口到各个下游能不能串起来？没有 trace_id，跨服务排查等于大海捞针
日志结构化日志是纯文本还是 JSON？纯文本日志无法高效检索和聚合。有没有统一的字段（时间、级别、trace_id、用户 ID、耗时）？
日志级别生产环境是 INFO 还是 DEBUG？DEBUG 日志在高 QPS 下会拖垮磁盘 IO。错误日志里有没有打全栈信息？
敏感信息日志里会不会打印手机号、身份证、密码、Token？这是安全合规红线
采样高 QPS 下全量打日志不现实，采样策略是什么？错误请求是不是 100% 保留？
仪表盘有没有一个能一眼看出"系统是否健康"的总览面板？值班的人第一时间看什么？
评审必问的"灵魂三问"：① 这个系统半夜挂了，值班的人怎么知道？② 知道了之后，怎么定位到是哪个环节？③ 定位之后，怎么确认修复生效了？如果三个问题都有清晰答案，可观测性基本合格。
模块 7

成本评审

成本是最容易被忽略的评审维度，因为技术评审容易只关注"能不能实现"。但一个技术上完美、成本上不可持续的方案，一样是失败的设计。成本分四块，第四块最常被漏。

成本类型包含什么评审要问
机器成本服务器、容器、数据库实例、缓存实例需要多少台？规格多大？能不能用更小的规格 + 更好的算法实现？弹性伸缩能省多少？
带宽成本公网流量、跨机房流量、CDN返回的数据能不能压缩？能不能减少往返次数？跨可用区流量是要单独计费的
存储成本数据库存储、对象存储、日志存储、备份存储冷热数据分层了吗？日志保留多久？日志和备份的存储成本经常超过业务数据本身
人力成本开发、运维、值班、排障多引入一个中间件，就要有人长期维护、升级、排障。这个组件的收益值不值得这份人力？
人力成本为什么最该被重视：机器成本是一次性的、可预测的；人力成本是持续的、隐性的、会累积的。每引入一个新技术（新消息队列、新数据库、新网关），团队就多了一份"认知负担 + 运维负担 + 半夜被叫醒的概率"。
评审必问：这个新组件，团队里有几个人真正懂它？出了问题谁能解决？如果没有第二个人懂，那它就是一个"人形单点"—— 那个人离职或休假，系统就成了黑盒。这比机器单点更危险。

成本评审的经典提问

  • 有没有更简单的方案？ 能用数据库解决的事，非要引入 Kafka 吗？能用单体解决的事，非要拆微服务吗？
  • 复杂度换来了什么？ 每个新组件都要能回答"它解决了什么、不引入它会怎样"。
  • 三年后的总成本是多少？ 不只看当下的机器费，还要看数据增长、流量增长带来的成本曲线。
  • 有没有被锁死？ 用了某云厂商的专有服务，将来能不能迁走？迁移成本多大？
模块 8

十条"看起来对但有问题"的反模式

反模式（Anti-pattern，指看起来合理、实际会导致问题的常见做法）是评审的高频命中区。这十条的共同特点是：方案里写着很自然，但边界条件下一碰就碎。

#反模式为什么错 / 正确做法
1用平均值评估性能均值会被长尾掩盖，用户体感由 P99 决定。改用分位数（P95/P99/P999）做性能指标
2liveness 探针检查外部依赖存活探针（liveness probe，判断容器是否要重启）如果去 ping 数据库，数据库抖动会导致所有实例被判定为"不健康"然后集体重启，雪崩。存活探针只该检查进程自身；依赖检查放 readiness（就绪探针）
3要求缓存与数据库强一致并发下强一致代价极高。缓存应追求"最终一致 + 极短不一致窗口 + TTL 兜底"。真正需要强一致的字段不要走缓存
4无限重试下游越慢越重试，流量被放大，把本来只是抖动的下游彻底打死（重试风暴）。必须有限次数 + 指数退避 + 抖动，且只重试幂等操作
5没有超时的外部调用下游卡住时，自己的线程/连接池会被占满，故障从下游传导到自己。每个外部调用都要设连接超时和读取超时
6全量加载到内存SELECT * 捞出几百万行塞进 List，内存瞬间打满 OOM。必须分页 / 流式处理 / 分批
7同步调用链过长A→B→C→D 同步串行，延迟累加、任一环故障全链路失败、线程占用时间 = 所有下游耗时之和。能异步就异步，能并行就并行，能缓存就缓存
8单点没有备份某个组件只有一份，挂了就全挂。评审要逐层扫单点，至少保证核心链路没有单点
9把 Secret 当加密把密码、密钥明文写进配置文件或代码里提交到仓库，以为"没人看得到"。必须用密钥管理服务（KMS / Vault）+ 环境变量注入 + 定期轮换
10容量按均值规划用平均 QPS 算容量，高峰必崩。容量必须按峰值规划，且留出故障冗余（N+1 或 N+2）
反模式的通用识别方法：问一句"如果这个假设不成立会怎样"。反模式本质上都是依赖了一个不成立的假设：假设流量是均匀的、假设下游不会慢、假设不会并发、假设数据不会增长、假设机器不会挂。评审时把方案里的隐含假设逐条拎出来，反模式自然现形。
常见坑

评审者自己容易犯的九个错

评审是双向的。被评审的方案会犯错，评审者自己也会。这九条是评审者最常犯的问题。

1
只看架构图，不看数据流
架构图画得漂亮不代表设计对。真正的问题往往藏在"一个请求到底经过了哪些组件、读写了几次库、调了几次下游"的数据流里。评审时要求作者把关键链路的时序讲一遍。
2
不问失败路径
大多数方案只描述"正常流程"，对"下游超时怎么办、数据库挂了怎么办、消息丢了怎么办"只字不提。评审的核心价值恰恰在失败路径上，必须主动追问。
3
被术语唬住
听到"我们用 CQRS + Event Sourcing + 领域驱动"就点头。术语不是正确性的证据。要问："这个模式解决了你的什么具体问题？不引入它行不行？"
4
只提问题，不给方案
指出"这里会超时"很容易，难的是给出"加 500ms 超时 + 熔断 + 降级返回兜底"的可执行建议。评审要产出可落地的改进，不只是列一堆问号。
5
用自己的场景去套别人的方案
"我们当年用 Kafka 就好了"——但对方的量级可能只有你的千分之一。评审要基于对方给出的约束，而不是自己的经验惯性。
6
追求完美，阻塞进度
把所有问题都标成"必须解决"，导致方案永远上不了线。评审要做风险分级：阻塞项、建议项、可忽略项。不是所有问题都值得现在解决。
7
没有记录和跟进
会上讨论得很热闹，散会后没有任何记录。问题和待办要落到文档，明确负责人和截止时间，下次评审先看上次的待办有没有闭环。
8
只审技术，不审运维
"上线后怎么部署、怎么扩容、怎么回滚、怎么值班、谁来修"这些问题同样重要。一个无法运维的方案，技术上再优雅也是失败的。
9
把评审当成审批
评审不是"批准/否决"的投票，而是共同降低风险的协作。目标是让方案变得更好，不是分出谁对谁错。姿态错了，作者会防御，真问题就藏起来了。
自测

六道题

1. 评审时，作者选择用 PostgreSQL 而不是团队熟悉的 MySQL，两者都能满足需求。你作为评审者应该？
正确答案：问清约束条件和理由。这属于"取舍不同"而非"事实错误"。评审者的职责是把取舍摆到台面上，确认作者评估过引入陌生技术带来的运维/人力成本，而不是替他做决定。
2. 一份方案说"系统平均响应时间 40ms，性能良好"。这个结论最大的问题是什么？
正确答案：均值掩盖长尾。99 个请求 10ms、1 个请求 3000ms，均值也才 40ms，但那 1% 的请求是真实卡顿的用户。性能验收必须看 P95/P99/P999。
3. 服务 A 调 B，B 调 C。C 抖了一下变慢，每层都配置了"失败重试 3 次"。最可能发生什么？
正确答案：重试放大到约 9 倍。B 的重试放大 3 倍，A 的重试再放大 3 倍。重试必须有限次数 + 指数退避 + 抖动，且最好只在最靠近用户的一层重试，配合统一超时预算。
4. 关于 Kubernetes 的存活探针（liveness probe），下面哪种配置是危险的？
正确答案：在存活探针里检查外部依赖。数据库抖动会让所有实例被判定为不健康并集体重启，造成雪崩。存活探针只该判断进程自身；依赖检查应放在就绪探针（readiness）。
5. 一个方案要新增一个自研的分布式任务调度中间件。成本评审时，最容易被忽略的是？
正确答案：人力成本。机器成本是一次性可预测的，人力成本是持续隐性累积的。如果只有一个人懂这个组件，他就是"人形单点"，比机器单点更危险。评审要问"有几个人真正懂它"。
6. 数据评审时，作者说"我们每天都有备份，数据是安全的"。最该追问的是？
正确答案：追问恢复演练。"有备份"和"能恢复"是两回事。没演练过的备份可能损坏、版本不兼容、或恢复耗时远超 RTO。评审要确认 RPO/RTO 是否被真实演练验证过。

术语表

术语一句话解释
架构评审在方案落地前，由有经验的人对设计做风险审查的过程
SPOF 单点Single Point of Failure，某个组件挂了会导致整体不可用
峰值系数峰值 QPS 与平均 QPS 的比值，用于容量规划，普通业务 3~5，大促可达数十倍
P99 / P99999% / 99.9% 的请求快于该值，用于衡量尾延迟
尾延迟最慢那一小部分请求的延迟，决定用户体感
故障域一次故障能同时影响的资源范围，隔离故障域可缩小影响面
降级资源不足时主动关闭非核心功能，保住核心链路
熔断下游持续失败时快速失败，避免继续打；三态为关闭/打开/半开
重试风暴多层重试导致流量成倍放大，把抖动的下游打死
优雅停机收到停止信号后先处理完在途请求再退出
RPORecovery Point Objective，最多容忍丢多少数据
RTORecovery Time Objective，最多容忍中断多久
在线 DDL不锁表地修改表结构（如 gh-ost、pt-online-schema-change）
最终一致写入后一段时间内收敛到一致，中间可能读到旧值
可观测性通过指标/日志/链路等外部输出推断系统内部状态的能力
黄金四信号延迟、流量、错误、饱和度，Google SRE 提出的必看指标
SLOService Level Objective，服务等级目标，如"P99 < 200ms"
错误预算允许的不可用额度（如 99.9% 即每月约 43 分钟），用尽则冻结发布
trace_id贯穿一次请求全链路的唯一标识，用于跨服务追踪
反模式看起来合理、实际会导致问题的常见做法
