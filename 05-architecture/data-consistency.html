模块 1

一致性模型谱系

一致性不是开关，是光谱。工程上的正确姿势：按业务容忍度选最弱的满足要求的模型——每强一级，都是真金白银的延迟和复杂度。

模型保证直观解释典型实现
线性一致最强所有操作看起来在某一瞬间原子完成；写完立刻所有人都能读到etcd、ZooKeeper（Raft/ZAB 共识）
顺序一致强保全局操作顺序，但不保证与实时时间对齐理论模型，实际系统少有纯实现
因果一致中有因果关系的操作保序，无因果的可乱序因果追踪系统（学术原型为主）
最终一致弱不再更新后，副本最终收敛到相同值Redis 主从、DNS、Cassandra 默认
读己之写场景型自己写完的，自己一定能读到写后读主库；按会话路由
会话一致场景型同一会话内读己之写，换会话不保证电商购物车、社交 Feed
单调读场景型不会读到比上次更旧的值（不倒退）读修复后的副本、粘性会话

一个时间线例子（最终一致的可见窗口）

# 主库在北京，从库在上海，异步复制
T1  10:00:00.100  用户在北京节点写入  X = 1
T2  10:00:00.150  同一用户在上海节点读 X  →  读到 0（旧值！）
T3  10:00:00.300  再读 X                    →  读到 1（复制已追平）

窗口 ≈ 150ms，但高峰期复制延迟可能到秒级。
业务上这叫"我刚发的朋友圈刷新一下没了"——投诉重灾区。
选型口诀：先问"最弱的模型是什么还能满足业务"。余额扣减要强一致（读主库/行锁）；帖子点赞最终一致就够；购物车会话一致即可；Feed 流单调读防倒退。一上来全按最强设计，延迟和成本双输。
模块 2

CAP 与 PACELC 的实践含义

CAP 讲的是网络分区发生时的取舍，PACELC 补上了"没有分区时"的那半边——后者才是你每天在做的选择。

CAP 的正确用法

阵营分区时的行为典型系统
CP保一致牺牲可用：少数派节点拒绝服务，直到分区恢复或重新选主etcd、ZooKeeper、HBase、Spanner
AP保可用牺牲一致：各节点继续服务，分区恢复后对账/合并冲突Cassandra、DynamoDB、Redis 主从
"CAP 三选二"是被误读的说法。没有分区时，C 和 A 都要考虑，只是延迟不同——同步强一致延迟高，异步最终一致延迟低。CAP 只描述分区那一瞬间的行为；把"我们选了 CA"挂嘴边，通常意味着没搞懂 CAP 在讲什么。

PACELC：没有分区时的另一半

表述：如果发生分区（P），在可用性（A）和一致性（C）之间取舍；否则（E），在延迟（L）和一致性（C）之间取舍。每个系统都在这两个维度上有确定站位：

系统分区时无分区时含义
DynamoDBAPEL默认最终一致读换低延迟；可开强一致读（代价是延迟翻倍）
CassandraAPEL一致性级别 ONE 低延迟，QUORUM 折中，ALL 强一致
MongoDBAPEC多数派读写保一致性，写确认等待多数副本
SpannerCPECTrueTime + 2PC 换全局强一致，延迟以数十毫秒计
etcd / ZooKeeperCPECRaft 多数派提交，配置类小数据强一致

实践含义

  • 每次存储选型都是一次 PACELC 表态：选 Cassandra 就是选"平时低延迟、分区时保可用"；选 etcd 就是选"任何时候强一致、牺牲写入延迟"。
  • "既要强一致又要低延迟"的方案评审结论 = 没想清楚。可以在同一系统里混用（下单强一致走 PG、用户资料最终一致走 Dynamo），但同一个数据不能既要又要。
  • 把一致性声明写进架构文档：每个数据域标注"强一致 / 最终一致 + 收敛时间目标"，下游团队按声明做设计，避免互相假设。
模块 3

分布式事务方案对比

五种方案没有排名，只有适用场景。选错方案的代价：2PC 拖垮数据库、TCC 写三倍代码、Saga 读到中间状态。下表是真实权衡。

方案一致性隔离性性能复杂度适用场景
2PC / XA强一致有（锁资源到提交）低中传统数据库、短事务、低并发；Seata XA 模式底层即此
TCC最终一致无（业务层防冲突）高高资金、库存等高价值短流程；Seata TCC 模式
Saga 编排最终一致无高中长流程跨多服务（下单→支付→物流），有中心协调者
Saga 协同最终一致无高中同上；事件链无单点，但链路追踪更难
本地消息表最终一致无高低发消息/发事件，与业务同库保证不丢；接收方无侵入
最大努力通知弱无最高低支付结果通知商户等可重试、允许延迟的场景

2PC 的问题（为什么不默认用它）

# 两阶段：prepare → commit
阶段一（prepare）：协调者问所有参与者"能提交吗"，参与者锁定资源、写 redo/undo 日志
阶段二（commit）：协调者通知"提交"，参与者释放锁、正式生效

问题 1：prepare 后参与者资源被锁，长事务下数据库连接/行锁被长时间占用
问题 2：协调者单点——commit 前宕机，参与者全部悬挂（锁着资源等指令）
问题 3：同步阻塞，吞吐受最慢参与者拖累

TCC 三接口（以库存服务为例）

// Try：预留资源（冻结库存 10 件，可多次调用需幂等）
boolean tryDeduct(String bizNo, String skuId, int count);

// Confirm：确认扣减（把冻结的 10 件真正扣掉）
boolean confirmDeduct(String bizNo);

// Cancel：回滚预留（释放冻结的 10 件）
boolean cancelDeduct(String bizNo);

// 三个接口全部按 bizNo 幂等：网络重试/重复投递不能重复扣

本地消息表（可靠性最高的轻方案）

-- 消息与业务数据同库，靠本地事务保证不丢
CREATE TABLE msg_outbox (
  id          BIGINT PRIMARY KEY,
  biz_id      VARCHAR(64)  NOT NULL,
  topic       VARCHAR(64)  NOT NULL,
  payload     JSON         NOT NULL,
  status      TINYINT      NOT NULL DEFAULT 0,  -- 0 待发送 1 已发送 2 失败
  retry_count INT          NOT NULL DEFAULT 0,
  created_at  DATETIME     NOT NULL,
  KEY idx_status (status, id)
);

-- 发送流程：
-- 1. 同一个本地事务里写业务表 + 插 msg_outbox（status=0）
-- 2. 定时任务（每 1s）扫 status=0 且 id 递增的批量发送到 MQ
-- 3. 发送成功 → status=1；失败 → retry_count++
-- 4. retry_count > 5 → status=2，进死信表 + 告警人工
选型决策顺序（按此顺序问自己）：① 能不能不用分布式事务（服务内单库事务覆盖）？② 不能的话允许最终一致吗？允许 → 本地消息表 / Saga / TCC 按流程长度选；③ 必须强一致 → 2PC/XA，且把事务压到最短（准备阶段不锁长资源）；④ 跨公司/外部系统 → 最大努力通知 + 对账，别幻想强一致。
模块 4

对账与补偿设计

对账是异步系统的兜底机制：任何"最终一致"的声明，背后都应该有一个对账任务在验证它真的收敛了。没有对账的异步链路等于闭眼开车。

三层对账

层级频率发现问题的时效
准实时对账5~15 分钟分钟级发现差异，立即告警，控制爆炸半径
日切对账T+1 全量发现跨日、补单、批量遗漏类问题
财务月结月度与财务账目逐笔勾兑，出审计报告

对账 SQL（找单边账）

-- 差异类型一：本地有、渠道无（短款嫌疑）
SELECT l.id, l.amount
FROM local_trade l
LEFT JOIN channel_trade c ON l.channel_no = c.channel_no
WHERE l.create_time >= DATE_SUB(NOW(), INTERVAL 1 DAY)
  AND l.status = 1
  AND c.channel_no IS NULL;

-- 差异类型二：状态不一致（金额或状态对不上）
SELECT l.id, l.amount AS local_amt, c.amount AS channel_amt, l.status, c.status
FROM local_trade l
JOIN channel_trade c ON l.channel_no = c.channel_no
WHERE l.amount != c.amount OR l.status != c.status;

补偿设计四原则

  1. 幂等：补偿单号唯一键约束，"同一补偿执行多次 = 执行一次"。重复退款事故的第一来源就是补偿不幂等。
  2. 可重入：先查当前状态再操作，补偿执行到一半失败时重试能接着走，而不是从头再退一次。
  3. 逆操作先行：设计正向流程时就设计好逆向接口（Cancel / 冲正），别等出事故了才发现原操作不可逆。
  4. 有界重试 + 升级：指数退避重试（1min/5min/30min），5 次失败进死信队列 + 电话告警，人工处理台兜底。永远允许人工介入，永远不留"自动走到黑"的补偿。
对账的常见死法是"跑着但没人看"。差异表每天几百条没人处理，三个月后没人知道基线是多少。对账必须闭环：差异条数进监控看板，超过阈值（如 >10 条或环比突增）自动告警，每条差异有处理状态跟踪（待处理/已补单/已退款/误报关闭）。
模块 5

Quorum 机制：NWR

Quorum（多数派）是副本存储里调节一致性的旋钮：N 个副本，写等 W 个确认、读等 R 个副本返回，W + R > N 就保证读到最近写入。

N=3 时的组合与代价

配置读延迟写延迟说明
W=3, R=1最低（任一副本）最高（等全部）强一致读；写最慢，一个副本慢就拖死写
W=1, R=3最高最低写最快；读最慢，适合写多读少
W=2, R=2中中最常用折中：读写至少重叠 1 个副本，P99 最低
W=2, R=1低中不满足 W+R>N：可能读到旧值，属最终一致
# 为什么 W+R>N 能读到最新写？
写 X=1 得到 2 个副本确认（W=2）；读从 2 个副本（R=2）收集
2 + 2 = 4 > 3 → 读的 2 个副本里必至少 1 个包含 X=1
取版本号最大的返回值 → 读到 X=1 ✓

落地形态

  • Cassandra：一致性级别 ONE / QUORUM / ALL / LOCAL_QUORUM（真实可选值），按读写操作单独指定。
  • etcd / Raft 系：写必须多数派（(N+1)/2）确认才返回，读默认走 leader（强一致），可用 serializable 读换低延迟。
  • DynamoDB：默认最终一致读（省一半延迟、费用减半），强一致读需显式指定。
W+R>N 有个隐藏前提：失败节点不能丢已确认的数据。节点宕机恢复后落后于其他副本，若恰好躲过了读的 R 个集合，就会丢已确认写。配套机制：读修复（read repair，读时发现旧副本后台修补）、 hinted handoff（临时托管）、反熵（anti-entropy，Merkle 树比对）。没有这些，Quorum 只是降低了概率，没有消灭窗口。
模块 6

时钟与顺序

分布式系统里，物理时间是参考信息，不是排序依据。依赖时间戳判先后的系统，会在时钟回拨、NTP 跳变的那一天集体出错。

物理时钟的三个坑

问题后果
NTP 误差同机房理论 <1ms，实际 1~10ms；跨区 10~100ms，相差百毫秒是常态
时钟回拨NTP 同步导致时间倒流，"后发生"的事件时间戳反而更小，排序和去重逻辑错乱
闰秒UTC 插入闰秒时未处理的系统出现时间重复/跳变

反例：时间戳排序丢更新

# 两个节点时间差 100ms，都写同一个 key
10:00:00.050  节点 B 写 X = 2   # 实际后发生
10:00:00.100  节点 A 写 X = 1   # 实际先发生

按"时间戳大的赢"合并 → X = 1（旧值覆盖新值，B 的写入丢失）
按"时间戳小的赢"合并 → X = 2（先发生的被丢弃，因果颠倒）

结论：跨节点排序永远不要用物理时间戳。用版本号、序号或共识协议。

三种替代方案

方案机制能力边界
Lamport 时钟本事件 +1；发消息携带计数值；接收方取 max 后 +1保 happened-before 偏序；无法判断并发（不可比 = 并发，也可能只是不知道）
向量时钟每节点维护向量 [A:5, B:3]，发送合并各方向量能精确判断因果与并发（可比的才是因果）；向量随节点数增长
HLC混合逻辑时钟：(物理时间, 逻辑计数器)，单调不减接近物理时间且单调；CockroachDB 等采用，适合做事务时间戳

Snowflake ID 的时钟回拨

# Snowflake：41bit 毫秒时间戳 + 10bit 机器 + 12bit 序列
# 回拨处理三选一（生产必须实现其中一种）：
1. 拒绝发号：回拨 < 阈值（如 5ms）时短暂等待时钟追回
2. 借号：从备用号段/其他机器借序列，回拨期间继续发
3. 报错 + 告警：超过容忍阈值直接失败，让人工介入修 NTP
✗ 不处理：回拨后毫秒数变小，可能发出与回拨前重复的 ID（主键冲突）
工程三字诀：排序用序号，去重用唯一键，时间只用来展示。版本号（乐观锁）、单调递增 ID、共识协议日志序号都是可靠顺序；数据库唯一约束、幂等键是可靠去重；物理时间戳放进"创建时间"字段给人看可以，参与业务裁决不行。
模块 7

数据库选型与一致性保证

先定一致性需求，再选数据库；不要反过来。同一份数据换一个存储，一致性语义可能完全变了——这个切换必须过 ADR。

数据库 / 形态一致性保证关键机制坑
PostgreSQL / MySQL 单机强一致ACID 事务 + 隔离级别RR 隔离下也有间隙锁死锁风险
MySQL 主从最终一致（默认异步）binlog 复制切主丢数据；半同步在退化为异步时仍有窗口
PostgreSQL 流复制同步/异步可选WAL 流复制 synchronous_commit = on 才强一致，写延迟 +1 个 RTT
Redis 主从最终一致异步复制可用 WAIT numreplicas timeout 提升同步度（仍非强一致）
etcd / ZooKeeper线性一致Raft / ZAB 共识写吞吐受多数派 RTT 限制，别当业务数据库用
Kafka分区内有序 + 可配持久性acks=all + min.insync.replicasacks=1（默认）丢数据；多分区间无全局顺序
MongoDB多数派近似线性一致writeConcern:majority + readConcern:majority默认 w:1 配置下故障会丢已确认写
Cassandra可调 NWR一致性级别 ONE~ALL默认 ONE；轻量事务（LWT）很慢，别当强一致用

读己之写的落地手法

  • 会话内固定读主库：写后 N 秒内该用户的请求路由到主库，或用"写后等一个复制延迟窗口"再读从。
  • 版本号回执：写操作返回数据版本号，读请求携带"至少版本 V"，从库版本 < V 时改读主库或等待。
  • 因果令牌：把上一次读到的版本作为本次读的前置条件，存储层保证不返回更旧的数据。
最危险的切换：把 MySQL 换成"最终一致"的存储而不改读路径。代码里到处是"写完立刻查"的逻辑，换库后全部读到旧值。迁移评审必问：原系统的读己之写保证还在吗？不在的话，读路径要怎么改？
模块 8

十个真实的坑

1
把最终一致当强一致用
支付成功后立刻查余额查到旧值，用户投诉"钱没了"。异步链路读路径要么读主库，要么带版本等待，别默认从库即最新。
2
缺少对账
消息"应该"会到，没人验证到没到。月底财务发现差账时已经积累了几千条。准实时对账 + 差异告警是异步系统的安全带。
3
时钟回拨
NTP 同步导致节点时间倒流，依赖时间戳排序/去重的逻辑集体错乱，ID 生成重复。用单调时钟、HLC 或版本号，物理时间只用于展示。
4
网络分区下的脑写
旧主感知不到新主已选出，继续接受写，恢复后数据被回滚或双写冲突。用多数派提交（Raft）+ fencing token（递增纪元号拒绝旧主写入）防护。
5
2PC 用于长事务
prepare 之后锁资源几十秒，数据库连接池被打满，连带拖垮无关业务。长流程用 Saga/TCC，2PC 只留给秒级短事务。
6
TCC 的 Try 没有幂等
Confirm 网络超时重试，冻结被重复执行，库存多扣。三个接口全部按业务单号幂等，这是 TCC 的及格线。
7
Saga 没有隔离性
下游服务读到"订单已创建未支付"的中间态，按此状态做了错误决策（如给未支付订单发货）。设计时让中间态对外不可见，或用语义锁。
8
本地消息表只投一次
发送失败没有重试机制，消息永久丢失，下游永远等不到。消息表必须有状态机（待发送/已发送/失败）+ 重试 + 死信 + 对账四件套。
9
用自增 ID 做分布式排序
分库后各库自增 ID 冲突或跳变，按 ID 排序结果错乱。全局唯一 ID 用 Snowflake/号段，排序另建单调序号字段。
10
补偿接口不能重入

自测

六道题

1. "用户发的帖子，自己刷新后一定能看到"描述的是哪种一致性？
正确答案：读己之写。它只约束"自己的写对自己可见"，比线性一致弱得多、成本也低得多。落地手法：写后短时间内该用户请求路由到主库，或读请求携带版本号等待从库追平。
2. 3 副本系统配置 W=2、R=2，能保证什么？
正确答案：读到最近写入。2+2=4>3，读的 2 个副本与写的 2 个副本必至少重叠 1 个，取版本号最大的返回值即可。注意前提：失败节点不能丢已确认数据，否则仍需读修复/反熵兜底。
3. 关于 2PC（XA）的主要问题，哪个说法不对？
正确答案："适合所有场景"是错的。2PC 是强一致方案，代价正是阻塞、锁资源、协调者单点。它只适合短事务低并发；长流程用 Saga/TCC，发消息用本地消息表。不存在"一个方案通吃"的分布式事务。
4. 两个节点时间相差 100ms，都写了同一个 key。按物理时间戳合并会怎样？
正确答案：可能丢更新/因果颠倒。跨节点排序永远不要用物理时间戳。可靠顺序来自版本号、单调序号或共识协议日志；物理时间戳只放进"创建时间"字段给人看。
5. PACELC 理论相比 CAP 补充了什么？
正确答案：无分区时的 L/C 权衡。DynamoDB 平时用低延迟的最终一致读（EL），分区时保可用（AP）；Spanner 任何时候都选一致性（PC/EC）但延迟高。每次存储选型都是一次 PACELC 表态。
6. 本地消息表方案中，消息发送失败后的正确处理是？
正确答案：有界重试 + 死信 + 告警 + 对账。消息表必须有状态机（待发送/已发送/失败）和重试计数；只标记不重试等于丢消息；无脑重插会造成重复投递，必须靠消费端幂等 + 对账双重保证。

关键数字与公式速记

# Quorum（N 副本）
强一致读最近写：  W + R > N
Raft/etcd 多数派： floor(N/2) + 1
常用折中（N=3）： W=2, R=2

# 时钟精度参考
同机房 NTP 理想误差   < 1ms
同机房实际常见       1 ~ 10ms
跨可用区             10 ~ 100ms
跨地域               50ms ~ 数百 ms
结论：物理时间戳不能做跨节点排序依据

# 补偿重试节奏（参考）
重试间隔：1min → 5min → 30min → 2h → 8h（共 5 次）
第 5 次失败 → 死信队列 + 电话告警 + 人工处理台
