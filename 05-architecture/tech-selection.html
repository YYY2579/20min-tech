开始前

选型的本质

技术选型不是"找出最好的技术"，而是在当时的约束下（团队、时间、规模、预算）找出期望代价最低的解。同一个结论，约束变了就得重新评估——所以选型一定要记录"触发重新评估的条件"。

常见误区现实
找"最好"的技术只有"最适合当前约束"的技术。五年后你的团队规模、数据量都会变，结论也会变
选型是一次性的选型是带退出条件的决策：数据量到什么量级、团队扩到多少人、开源项目是否停止维护，都要重新评估
技术问题是主要风险多数项目死于运维成本、团队学习曲线和生态缺失，而不是技术能力不足
模块 1

选型六步流程

需求定义：写下这个组件必须解决的 3 个问题和明确的非目标（不解决什么）。附上规模数字：峰值 QPS、数据总量、团队人数、可用 deadline。没有数字的需求无法评估。
候选清单：3~5 个候选。必须包含一个 null option（什么都不引入，扩展现有方案/自己写）。大量"选型"在加了 null option 后直接关闭——加个参数、扩两台机器就能解决的事，引入新组件纯属负担。
加权评估：用模块 2 的七维评估表，团队集体打分。功能匹配和许可协议是一票否决项，不过线直接出局，不打分。
POC：用接近生产规模的数据和故障场景验证，验收标准提前写死（见模块 3）。POC 的目的是证伪风险假设，不是证明"它很好"。
决策：写 ADR（架构决策记录，见模块 6），团队 review 通过。记录"选了 X"和"为什么不选 Y"——后者半年后更有价值。
复盘：上线 3~6 个月后回看：选型时的预测 vs 实际（性能、问题数、运维人月），更新评分权重。不复盘的团队会重复踩同一个坑。
时间分配建议：需求定义 20%、候选调研 20%、评估 15%、POC 30%、决策记录 5%、复盘 10%。多数团队的问题是把 80% 时间花在调研功能列表上，POC 只给三天——正好颠倒了。
模块 2

七个评估维度

维度建议权重具体看什么
功能匹配一票否决核心功能是否支持、边界条件（分页、事务、TTL、多租户、时区）、版本路线图是否覆盖你的需求
许可协议一票否决能否商用、是否传染、修改是否必须开源（模块 5）。AGPL/SSPL 对 SaaS 公司可能是红线
运维成本15%~25%部署难度、监控指标是否暴露、备份恢复方案、故障排查文档质量、是否需要专职人员（DBA/SRE）
社区活跃度10%近 3 个月 commit 频率、issue 平均关闭周期、release 节奏、贡献者分布（是否 1~2 人独大）、Stack Overflow 问题量
性能10%~15%贴近生产场景的压测，看 P99/P999 而不是平均值，关注容量上限和性能衰减曲线
团队熟悉度10%~15%学习曲线、招人难度（市场上简历量）、内部已有经验、文档中文质量
长期风险10%~15%版本节奏（是否有 LTS）、核心维护者健康度（是否公司支持）、云托管版是否形成新锁定、退出成本

场景：电商订单库，峰值 8 万 QPS 读 / 1.2 万 QPS 写，数据量 800GB，团队 6 个后端 + 1 个 DBA，要求事务强一致。

模块 3

POC 设计：验证风险，不是验证功能

demo 已经证明"它能跑"。POC 要回答的是三个问题：在我们的数据规模下性能如何、故障时表现如何、边界情况会不会炸。

验证项怎么做通过标准（示例）
真实规模压测生产数据脱敏副本或同量级同分布生成数据，跑核心读写链路。数据量至少峰值的 1/10P99 < 50ms @ 10k QPS；CPU < 60%；无 OOM
故障注入杀节点、断网、磁盘写满、时钟跳变、下游接口超时抖动单节点故障 30s 内自动恢复；已确认数据不丢；监控有告警
边界用例大对象（100MB 的行）、热点 key 单点、空值、并发写同一行、网络分区 5 分钟不崩溃、不死锁、延迟可接受、数据一致
运维演练按文档做一次备份 + 恢复；按文档做一次版本升级恢复耗时 < RTO；升级零数据丢失
# POC 验收标准必须在开测前写死，示例：
1. 压测：50 并发混合读写 30 分钟，P99 < 50ms，错误率 < 0.01%
2. 故障：kill -9 任一数据节点，30 秒内服务自动恢复，已确认写不丢
3. 恢复：备份 + 恢复全流程 < 2 小时（RTO 要求内）
4. 运维：备份、扩缩容、监控告警均有文档且团队实操通过

# 反模式：测了三天很开心，因为只测了 happy path
# 正确姿势：至少覆盖一个完整业务周期（含对账批次）+ 一次故障演练
POC 最大的自欺是"用 demo 配置跑生产问题"。压测环境务必核对：连接池大小、副本数、缓存命中率、JVM/系统参数、网络拓扑（同机部署延迟≈0）。任何一项和生产不一致，结论就不可信。
模块 4

供应商锁定评估

锁定不是原罪——完全无锁定意味着全面自研，成本更高。关键是退出成本可估算、可承受。

锁定类型表现退出难度
数据锁定专有存储格式、专有备份格式高。要写转换工具，大数据量迁移以周计
API 锁定专有 SDK / 连接协议 / 专有语义（如某家的顺序消息）中~高。需要重写数据访问层，业务侵入
运维锁定托管服务控制面、专有运维工具链中。自建等价物通常可行但费人力
知识锁定内部机制只有供应商懂，出问题只能提工单低但痛。团队要有人理解其内部机制
集成锁定深度定制代码、专有插件高。定制越多，迁移工程量越大

选型时问自己六个问题

  1. 数据能否完整导出为标准格式（SQL/CSV/Parquet）？导一份全量要多久？
  2. API 是否有开源等价物？（如用 Kafka 开源 API 而非云厂商专有 SDK）
  3. 团队是否理解其内部机制，还是完全黑盒？
  4. 最坏情况（涨价 10 倍、服务关停、战略放弃）的预案是什么？
  5. 迁移到第二方案需要多少人月？这个数字要写进 ADR。
  6. 是否存在第二供应商 / 开源实现，保证有议价能力？
实用策略：① 数据访问层包一层 Repository/DAO，业务代码不直接依赖专有 SDK；② 优先用开源 API 而非厂商增强 API；③ 托管服务省运维，但把"导出通道"作为验收项——定期演练导出，别等想走的时候才发现导不出来。
模块 5

开源协议的商业影响

协议能否商用核心义务传染性 / 代表项目
MIT可以保留版权声明即可，几乎无限制无传染。Rails、React（+专利条款）、Vue
Apache 2.0可以保留声明 + 声明修改 + 明确专利授权无传染。Kafka、Spark、Kubernetes、gRPC
BSD可以类似 MIT；3-clause 禁止用作者名宣传无传染。PostgreSQL、Nginx、Go 标准库部分
GPL v2/v3可以用分发衍生作品必须开源同协议强传染。Linux（GPLv2）、MySQL（GPLv2 双许可）
LGPL可以修改库本身要开源，动态链接闭源程序可用弱传染。glibc、Qt（双许可）
AGPL谨慎GPL + 通过网络提供服务也触发开源义务强传染（SaaS 也中）。MongoDB 曾用后改 SSPL
SSPL高风险提供云服务必须开源整个服务栈（含管理层）OSI 不承认为开源协议。Elasticsearch/Kibana 7.11+、MongoDB 4.0+
BUSL受限禁止竞争性云服务，4 年后自动转 GPL非 OSI 开源。MariaDB MaxScale、部分 HashiCorp 产品
SaaS 公司的红线是 AGPL/SSPL：GPL 的传染只在"分发软件"时触发，SaaS 不分发所以安全；但 AGPL 把"通过网络提供服务"也视为分发，SSPL 更要求开源整个服务栈。公司产品是 SaaS 形态的，引入依赖前必须扫协议（SBOM），有 AGPL/SSPL 组件的一律法务确认。
产品要分发给客户（软硬一体、私有化部署）的，注意 GPL/LGPL 传染：GPL 组件链入主产品，可能导致整个产品被迫开源。MySQL 的 GPL 就是经典案例——不想开源就买商业授权（双许可模式）。
模块 6

决策记录：ADR

ADR（Architecture Decision Record）= 一个轻量 markdown 文件，记录"当时为什么这么决定"。放在 docs/adr/ 里跟代码一起版本管理。

# docs/adr/0007-order-mq-choice.md

## 状态
已接受（2024-06-15）

## 背景
订单系统需要引入消息队列，用于订单状态广播与库存异步扣减。
约束：峰值 2 万 msg/s；团队 6 人无专职运维；需保证顺序消息；
预算内不接受按量计费的商业 MQ。

## 决策
选用 RocketMQ 5.x 自建三主三从集群，不用 Kafka，不用云托管版。

## 备选与理由
- Kafka：生态最好，但顺序消息需单分区写，热点订单号会打偏；
  且运维组件多（ZK/KRaft），6 人团队 hold 不住。
- 云托管 MQ：运维最省，但年费约 12 万超出预算，
  且专有 SDK 形成 API 锁定（见 ADR-0003 锁定评估）。

## 后果
正面：顺序消息开箱可用；Java 生态友好；团队有 2 年 RocketMQ 经验。
负面：自建集群需 0.5 人月/月运维投入；社区中文资料多于英文，
排障主要靠内部文档。
风险：若吞吐涨到 10 万 msg/s，需重评估分片方案（触发条件已记录）。
ADR 的价值不在写，而在"被引用"。半年后有人提"换成 Kafka 吧"，先贴 ADR-0007 链接讨论约束是否变化，而不是从零再吵一轮。防止反复翻烧饼，是 ADR 最大的收益。Code review 里出现 ADR 链接，说明决策文化形成了。
模块 7

选型落地：灰度、回退与复盘

决策通过只是开始。落地方式决定了选型的成败——同样的组件，灰度上线是收益，大爆炸切换是事故。

三步落地

阶段做法验证目标
影子流量生产流量复制一份打到新组件，结果丢弃不生效（只记录比对差异）功能正确性、性能水位、与旧方案的输出差异率
灰度切流按用户尾号/内部账号切 1% → 5% → 25% → 100%，每档观察至少一个业务周期真实用户下的错误率、P99、业务指标（转化率是否变化）
全量 + 摘旧旧方案保留一个观察期（如 2 周）再下线确认无回退需求后才释放旧资源

回退设计（上线前就要想好）

  • 特性开关：新旧路径用开关控制，切流与回退都是改开关，不发版。开关默认值 = 旧路径。
  • 数据兼容：新组件改 schema 的，上线期做双写 + 回填，保证回退时旧库数据完整。不能回退的迁移等于裸奔。
  • 回退触发条件写死：错误率 > 0.5% 持续 5 分钟、P99 劣化 > 50%、核心业务指标下跌，任一命中自动回退，不临场讨论。

复盘指标（上线 3~6 个月回看）

指标选型时的预测复盘时的实际
P99 延迟 / 吞吐POC 压测值生产监控值（通常更差，差距即认知偏差）
故障次数与恢复耗时POC 故障注入值真实故障记录 + 复盘耗时
运维投入预估人月/月实际人月/月（告警数、工单数、值班打扰次数）
团队上手速度预估学习周期第一个独立排障的人何时出现
触发重新评估的条件ADR 里写明的阈值是否已接近（数据量、QPS、团队规模）
最常见的落地失误是"回退方案只写在文档里，从没演练过"。回退涉及开关、数据兼容、监控观测，链条比上线更长。上线前必须做一次回退演练：灰度切过去，再切回来，验证数据一致性和耗时——切得回去的灰度才是真灰度。
模块 8

十个选型坑

1
Demo 驱动选型
供应商 demo 环境 3 台机器跑得飞起，上生产 30 台机器各种问题——demo 用的是小数据、默认配置、最优路径、预热缓存。凡是 demo 完美的，更要按生产规模复测。demo 只配证明"存在"，不配证明"可行"。
2
追新：选刚发布的"下一代 X"
star 30k、发布 6 个月，但没有生产验证、没有生态工具、Breaking change 每两个月一次，最后团队成了上游的小白鼠。生产选型看"谁在生产用它、用了多久"，避开 0.x/1.x 早期版本，除非你有陪它长大的余量。
3
只看 GitHub star 数
star 是营销指标，可能是一次 viral 事件刷出来的，且只涨不减。要看：近 3 个月 commit 频率、issue 平均关闭周期、release 频率、贡献者是否集中在 1~2 人（bus factor=1 的项目，作者一离职就烂尾）。
4
忽视运维成本
选型只比功能矩阵，上线后发现没有监控、没有备份方案、故障只能 grep 日志，团队多养一个专职工程师。运维成本要折算成人月/年进 TCO：一个"功能赢 1 分但每月多 3 人月运维"的选项，通常不是好交易。
5
性能数据造假识别不出来
常见包装手法：① 关掉持久化和副本测吞吐；② 单机小数据 vs 集群大数据混着比；③ 只报均值不报 P99（均值 10ms，P99 可能 2s）；④ 客户端与服务器同机部署（网络延迟≈0）；⑤ 缓存 100% 命中的稳态测试。识别方法：复现其测试配置，逐项核对测试报告的方法论章节，不方法论的一律存疑。
6
一票否决项没先设
协议是 AGPL、核心功能不支持、团队无人会运维——这些是红线，先过滤再打分。把否决项当普通维度打分，会出现"总分最高但一票否决"的尴尬结论，浪费所有人时间。
7
集体决策变成一言堂
架构师拍板，落地时团队没人理解内部机制，出问题没人会修、没人愿意接。评分必须团队参与 + POC 期让一线的人真用一遍——他们的反对意见往往就是未来的事故预告。
8
没有 null option
忘了评估"什么都不换，扩展现有方案"。有时加两个参数、加一台机器、写 200 行代码就解决的事，引入新组件带来的是新依赖、新故障域、新学习成本。先问"能不能不换"，再问"换什么"。
9
口头决策，没有 ADR
三个月后有人问"当时为啥选它"，没人记得，于是再调研一轮、再吵一轮、结论还可能翻转。没有 ADR 的选型决策会以更高频率重新发生——这是最大的隐性成本。
10
忽视退出成本
只评估"进来多容易"，不评估"出去多难"。选型当天就要算迁移人月，并把"数据可导出性"写进验收标准。锁定的代价不在迁移那天才出现，从第一天起你的议价能力就在流失。
自测

六道题

1. 评估维度中，哪两项应该设为一票否决项？
正确答案：功能匹配和许可协议。核心功能不支持，其他分数再高也没用；协议不合规（如 SaaS 公司引入 AGPL/SSPL），是法律风险不是技术问题。否决项先过滤再打分，不参与加权。
2. POC 最应该验证什么？
正确答案：验证风险假设。功能是否齐全在 demo 阶段就能确认，POC 的钱要花在"生产规模压测 + 故障注入 + 运维演练（备份恢复、升级）"上，且验收标准要在开测前写死。
3. 一家做 SaaS 的公司要引入开源组件，最需要警惕的协议是？
正确答案：AGPL/SSPL。GPL 的传染只在"分发软件"时触发，SaaS 不分发所以基本安全；但 AGPL 把"通过网络提供服务"也视为分发，SSPL 更要求开源整个服务栈。MIT/Apache/BSD 都无传染，可自由商用。
4. 判断一份性能测试报告是否造假，最该先看什么？
正确答案：测试方法论。常见包装：关持久化/副本测吞吐、单机小数据冒充集群、只报均值（P99 可能差 100 倍）、客户端与服务端同机部署（延迟≈0）、缓存全命中稳态。复现不了配置的数据，一律存疑。
5. ADR（架构决策记录）的核心价值是？
正确答案：防止反复翻烧饼。半年后有人重提已否决的方案时，先看 ADR 里记录的约束是否变化。ADR 只记"为什么"，不记"怎么做"——后者是技术文档的职责。
6. 关于供应商锁定，哪个认识是正确的？
正确答案：退出成本可估算可承受。全面无锁定 ≈ 全面自研，成本更高。务实做法：数据访问层加 Repository 隔离、优先用开源 API、托管服务省运维但把"数据可导出"写进验收并定期演练导出。

选型评审会议程（60 分钟版）

需求与约束（10 分钟）：主讲人复述"必须解决的 3 个问题、非目标、规模数字"。数字不全的会直接休会补齐——没有数字的评审是空谈
否决项过滤（5 分钟）：逐个候选过协议合规与核心功能清单，不过线当场出局，不进入打分环节
评分表过堂（20 分钟）：每维度的打分依据逐条念，与会者可挑战任一分数。挑战成功的分数当场改，改要记录理由
POC 结果汇报（15 分钟）：对照提前写死的验收标准逐项过，不达标就是不过，不接受"后续会优化"
拍板与行动项（10 分钟）：明确结论、ADR 负责人、POC 补测项、重新评估的触发条件与时间点。散会前每个人知道自己要干什么
评审会的三个危险信号：① 全程只有一人在讲，其他人沉默——结论不会被执行；② 讨论变成功能清单朗诵——评估维度没人真看；③ "先上再说，有问题再换"——说出这句话时说明回退成本和退出成本根本没算过。
下一步怎么练：拿你团队正在用或正在评估的一个组件，完整走一遍流程：① 写下必须解决的 3 个问题 + 非目标 + 规模数字；② 列 3 个候选 + 1 个 null option；③ 填加权评分表（每项附依据）；④ 写一份 ADR 草稿，包含"为什么不选 Y"和"触发重新评估的条件"。
