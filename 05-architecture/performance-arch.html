模块 1

性能需求：把"快"变成数字

"系统要快"不是需求，是愿望。性能需求有三类指标，必须同时给出：延迟、吞吐、并发，而且每个都要带条件（数据量、时段、负载）。

指标定义示例（电商下单 API）
延迟 Latency请求从发出到收到响应的耗时，看分位数不看平均P50 < 80ms，P99 < 500ms，P999 < 1s
吞吐 Throughput单位时间完成的请求数：QPS（查询）/ TPS（事务）日常 5000 QPS，大促峰值 60000 QPS
并发 Concurrency系统同时处理的在途请求数，决定线程池/连接池下限峰值在途 1200（由 Little's Law 推出，见下）

为什么平均值是谎言

两个服务平均延迟都是 100ms，用户体验可能天差地别：

服务P50P99P999用户感知
服务 A98ms130ms150ms稳定，所有人都觉得快
服务 B60ms420ms2400ms一半人觉得飞快，1% 的人以为网站挂了

投诉来自长尾，监控必须盯 P99 / P999。尾延迟（Tail Latency）往往由单个慢节点、一次 GC、一条慢 SQL 造成，在微服务里还会被 fan-out 放大：一个请求调用 20 个下游，每个下游 P99 都是 100ms，整条链路 P99 接近 2000ms。

Little's Law：并发 = 吞吐 × 延迟

# 并发数 L = 到达率 λ × 单请求耗时 W
目标：5000 QPS，单请求平均耗时 100ms（0.1s）
并发 L = 5000 × 0.1 = 500 个同时在途请求

推论：线程池 / 连接池 / 队列长度至少按这个数量级配，
否则请求在池外排队，延迟指标必然失真。
性能目标必须写成"带条件的数字"。"P99 < 200ms"是半成品；"P99 < 200ms（单表 5000 万行、缓存命中率 90%、峰值 1 万 QPS 条件下）"才是可验收的目标。少了条件，压测通过与否全凭一张嘴。
模块 2

性能预算：像分钱一样分毫秒

Performance Budget：把端到端总延迟切成预算，分配到每一段，超支要么优化要么重谈需求。预算的本质是团队间的契约——它让"前端怪后端慢、后端怪数据库慢"变成"谁的段超支谁负责"。

一个真实分配示例（详情页，总预算 300ms）

段预算占比约束
前端渲染（FCP/LCP）120ms40%JS bundle < 200KB gzip；首屏不超 3 个阻塞请求
建连 + 网络往返40ms13%同城部署；连接复用率 > 95%
网关路由 + 鉴权10ms3%本地校验 JWT，不远程查会话
聚合服务（含下游并行）80ms27%3 个下游并行调用，取 max 不计 sum
DB 查询30ms10%全部命中索引；单条 SQL < 20ms
Redis 查询15ms5%同机房；pipeline 合并多次访问
buffer（不可预见）5ms2%专款专用，不许提前花

分配三原则

  • DB 段给最小预算：数据库是最贵的共享资源，毫秒应该花在减少访问次数上，不是允许它慢。
  • 串行段相加、并行段取 max：三个 50ms 的下游调用串行是 150ms 预算，并行只要 50ms——先并行化再谈分配。
  • 永远留 5%~10% buffer：没有余量的预算等于没有预算，第一次 GC 抖动就全线超支。
执行方式：压测时按段打点。每个请求在网关、服务入口、下游调用前后各记一个时间戳，上报到追踪系统，出报告时直接对照预算表看谁超支。前端同理：LCP / TTFB 有明确预算，超出时 CI 告警（Lighthouse CI）。
模块 3

端到端延迟拆解

优化前先拆。下面是一次真实量级的拆解（POST /api/orders，同城 IDC 部署，连接池已预热）：

段P50P99说明
DNS + TCP + TLS 建连0 / 40ms80msTLS 1.3 是 1-RTT；连接池复用时此项为 0
客户端到网关网络8ms25ms同城 1~2ms；跨省 20~30ms；跨运营商更差
网关路由 + 鉴权2ms8msNginx + Lua 或 Envoy；远程鉴权会再加 5~15ms
业务服务处理25ms90ms含参数校验、业务规则、编排逻辑
下游 RPC（并行）15ms45ms3 个约 20ms 的调用并行，耗时取 max 不是 sum
DB 查询（主库）3ms15ms命中索引；全表扫描在千万级表上 500ms+
Redis 查询0.5ms2ms同机房；含序列化约 0.2ms
序列化 / 反序列化1ms4msJSON 解析 1KB 约 5μs；大对象 Protobuf 快 3~5 倍
日志 / 监控埋点1ms5ms同步写日志是隐形杀手，必须异步批量
响应回传网络5ms20ms2KB 响应体；开启压缩后 CPU 换带宽

预算分配演算（目标 P99 ≤ 300ms）

# 串行段直接相加，并行段取最大
建连/网络往返      60ms   # 建连 40 + 网关往返 20
网关处理           10ms
业务 + 下游并行   120ms   # 业务 60 + max(库存 40, 价格 30, 促销 45)
DB                 30ms
序列化 + 日志      15ms
响应回传           40ms
buffer             25ms
------------------------
合计              300ms   # 刚好用满，任何一段超支都违约

拆解工具

  • 分布式追踪（Jaeger / SkyWalking / OpenTelemetry）：看每个 span 的耗时与父子关系，一眼定位超支段。
  • async-profiler / Arthas：火焰图看 CPU 栈，trace 命令看方法级耗时。
  • tcpdump + Wireshark：确认到底是网络慢还是服务慢，排除"以为慢在这、其实慢在那"。
最常见的拆解错误：盯着平均值优化。P99 由长尾构成，平均 50ms 的服务 P99 可能 800ms。所有预算和报告都以分位数对齐，平均值只用来观察趋势，不用来做验收。
模块 4

异步化与并行化

并行化让关键路径取 max 而不是 sum；异步化把耗时操作移出请求链路。两者是延迟优化的前两大杠杆，代价是复杂度和一致性。

并行化：代码长这样

// Java：三个下游并行，总耗时从 135ms 降到约 45ms
CompletableFuture<StockVO> stockF =
    CompletableFuture.supplyAsync(() -> stockClient.query(ids), ioPool);
CompletableFuture<PriceVO> priceF =
    CompletableFuture.supplyAsync(() -> priceClient.query(ids), ioPool);
CompletableFuture<PromoVO> promoF =
    CompletableFuture.supplyAsync(() -> promoClient.query(ids), ioPool);
CompletableFuture.allOf(stockF, priceF, promoF).join();
// 注意：ioPool 独立线程池。共用一个池会相互拖死（Hystrix 舱壁模式）
// Go：errgroup 并发 + 错误传播
g, ctx := errgroup.WithContext(ctx)
var stock StockVO
g.Go(func() error { var err error; stock, err = queryStock(ctx, ids); return err })
g.Go(func() error { _, err := queryPrice(ctx, ids); return err })
if err := g.Wait(); err != nil { return err }

异步化：三种形态与代价

形态做法代价
消息队列削峰写请求入 Kafka，下游按能力消费延迟从 50ms 变成秒级；要处理重复消费、顺序、对账
受理即返回接口返回"已受理"，后台异步处理，结果轮询/推送客户端复杂度上升；需要任务状态查询接口
事件驱动状态变更发事件，关注方各自响应链路变长排错难；最终一致
两条红线：① 强一致场景不许异步——扣款、创建订单主记录这类操作异步化等于把一致性 bug 写进架构；② 异步必须可观测——队列堆积深度、消费延迟、死信数量三个指标必须进监控，否则"异步"就是"悄悄丢请求"的体面说法。
模块 5

预计算与 IO 优化

这一模块的主题是把成本挪出关键路径：能提前算的别实时算，能批量做的别逐条做，能少拷贝的别多拷贝。

预计算与空间换时间

手段做法量化收益
缓存Redis 存热点查询结果，命中率目标 90%+DB 3ms → Redis 0.5ms，且挡住绝大部分流量
预聚合报表用离线/Flink 窗口预计算，查询直接读结果表5 分钟聚合查询 → 20ms 点查
本地缓存Caffeine 存配置/热点商品，expireAfterWrite=5m0.5ms → 0.05ms；注意多节点不一致窗口
CDN静态资源 + 可缓存 GET 接口推到边缘跨省 30ms → 10ms；命中率 95%+
HyperLogLogUV 统计用 12.5KB 近似结构代替全表 count(distinct)3 秒全表扫描 → 1ms 查询，误差 0.81%

IO 优化四板斧

1. 批处理（收益最大）

// 反例：循环单查，100 个 SKU × 3ms = 300ms
for (String id : ids) { skuMap.put(id, skuClient.query(id)); }

// 正例：一次批量查询，15ms
List<SkuVO> list = skuClient.batchQuery(ids);   // 底层一条 IN 查询

# MySQL 批量插入：每批 500~1000 行，比逐条 INSERT 快 10~50 倍
INSERT INTO t (a, b) VALUES (1, 2), (3, 4), ... ;   # 一次事务一次 fsync

# Redis pipeline：1000 条命令一次网络往返
# 逐条：1000 × 0.5ms = 500ms；pipeline：约 5ms

2. 零拷贝

  • sendfile：Nginx 返回静态文件时数据不经过用户态，CPU 占用接近零。API 网关返回大 JSON 时同理可评估。
  • Kafka 的 zero-copy：producer 写 page cache，broker 用 sendfile 直接发给 consumer，全程不进用户态——这是 Kafka 高吞吐的核心设计之一。
  • mmap：读大文件比 read 少一次拷贝；但小文件 mmap 的建立/拆除开销不划算，且要注意页缓存压力。

3. 连接复用

# HikariCP 连接池 sizing：SSD 时代近似 公式 = CPU 核数 × 2 + 1
4 核机器 → maximum-pool-size = 9
# 池子太小：请求排队等连接，延迟飙升
# 池子太大：DB 端连接数打满 + 上下文切换，吞吐反而降

# HTTP keep-alive：复用 TCP 连接，省掉 1-RTT 握手（20~40ms）
# OkHttp / HttpClient 默认 keep-alive，注意 idle 超时别短于 LB 的

4. 协议与压缩

  • gRPC / Protobuf vs REST / JSON：同等数据体积小 3~5 倍、解析快 3~5 倍，内部服务间通信首选；对外兼容性场景保留 REST。
  • 压缩是 CPU 换带宽：响应体 > 1KB 开 gzip / zstd；小响应体开了反而更慢（压缩头开销）。
  • 顺序写优于随机写：LSM 结构（RocksDB / HBase）把随机写转换成顺序写，写吞吐高一个数量级，代价是读放大和 compaction 抖动。
模块 6

容量与扩展性设计

容量规划回答两个问题：目标负载需要多少机器，以及不够时怎么加。两个都答不上来，就是在等事故发生。

容量计算（完整演算）

# 已知：单接口基准测试，4 核机器单节点 2000 QPS（CPU 水位 70%）
目标峰值 QPS：20000
基础节点数 = 20000 / 2000 = 10
加冗余系数 30%（突发 + 个体性能差异）= 13
加 N+1 容错（坏一台不塌）= 14 台

# 另一个视角验证：并发数验证
Little's Law：L = 20000 QPS × 0.05s（P50 耗时）= 1000 并发
单节点线程池 200 → 需要 ≥ 5 个节点并行服务，与 14 台结论兼容 ✓

扩展方式对比

方式做法优点局限
垂直扩展升配（4C8G → 16C32G）零改造，当天生效有物理上限、通常要停机、单价越来越贵
水平扩展无状态服务多副本 + LB理论无上限前提：无状态化改造完成
读写分离主写从读读吞吐翻倍复制延迟带来最终一致；写仍是单点
分片 Sharding按 key（用户 ID）哈希分库分表突破单机写入上限跨片查询/事务复杂；扩容要迁移数据
弹性伸缩HPA 按指标自动扩缩成本优化扩容生效 2~5 分钟，扛不住秒级突发

无状态化三件事（水平扩展的前置条件）

  1. Session 外置：登录态入 Redis，任何请求落到任何节点都能处理。
  2. 本地缓存降级：Caffeine 只存"允许短暂不一致"的数据；一致性要求高的入分布式缓存并接受延迟。
  3. 定时任务改分布式调度：单机 Timer/Quartz 改 XXL-Job 或 Quartz 集群模式，避免 N 个节点同时执行 N 遍。

峰值与弹性

日常 5000 QPS、大促 60000 QPS，峰谷比 12 倍。按峰值买 12 倍机器全年空转是浪费；全押弹性则扩容来不及。务实组合：

  • 常备容量 = 峰值 × 60%（应对 P95 以下日子）
  • 弹性容量 = 峰值 × 40%，提前 1 天预热扩容（镜像拉取 + JVM 预热 + 缓存预热）
  • 排队与限流兜底：超过容量的请求进队列或返回"繁忙"，比打挂系统体面
HPA 别只看 CPU。CPU 是滞后指标——流量来了 CPU 才涨，等扩容到位流量高峰已过。领先指标选请求队列长度 / QPS / 消费延迟。另外务必预留扩容生效时间：告警延迟 30s + 调度 10s + 拉镜像 30s + 启动 30s + 预热 60s ≈ 2.5 分钟，这期间只能靠常备容量扛。
模块 7

性能测试体系

五类测试回答五个不同问题。只做其中一种，等于只验证了一个维度。

类型回答的问题方法通过标准
基准 Benchmark单接口的理论上限在哪单接口阶梯加压至极限知道拐点 QPS 与拐点时的主要瓶颈
负载 Load目标负载下满足 SLO 吗目标 QPS 持续 10~30 分钟P99 达标、错误率 < 0.1%、无降级触发
压力 Stress系统的极限和 degradation 曲线1.5x / 2x / 3x 逐级加压记录每级的延迟与错误率，画出曲线
稳定性 Soak长时间跑会不会泄漏/衰减70% 目标负载跑 12~24 小时24h 后 P99 劣化 < 10%、内存无持续增长
破坏性 Chaos故障下核心链路表现如何杀节点 / 断网 / 注入延迟 / 杀 DB 主核心链路有降级、无数据错误、恢复时间符合 RTO

测试数据真实性 Checklist

  • 数据量同级：索引在 100 万行和 1 亿行是两个世界。生产 5000 万行的表，压测库至少同量级。
  • 数据分布一致：热点账号、长尾、空结果比例贴近生产——全是均匀分布的压测数据会高估索引效果。
  • 缓存打两轮：冷缓存（命中率 0%）测 DB 真实水位；热缓存（命中率 90%）测服务上限。
  • 下游 mock 按 P99 模拟：mock 全部 0ms 响应的压测，结论只对"没有下游"的系统成立。

标准流程

基线：记录当前各接口 P50/P99/QPS/错误率，没有基线就没有"变慢了多少"。
单接口：逐个接口基准测试，找出理论瓶颈（CPU / DB / 下游）。
全链路：按真实流量比例混合场景，验证链路级 SLO 与资源竞争。
峰值演练：按历史峰值 1.2 倍加压，验证扩容预案与限流兜底真的能执行。
稳定性：长时间跑，抓内存泄漏、连接泄漏、缓存腐烂。
回归常态化：每次发版跑一轮负载测试，性能衰减是渐进的，只在发布前测一次等于没测。

模块 8

十个真实的坑

1
前期不设计，后期硬扛
架构阶段不定性能目标和预算，上线后靠加机器续命，加到第 20 台发现瓶颈是单条慢 SQL。延迟预算在方案评审时就要落到表上。
2
性能目标缺失或不可度量
"系统要快"无法验收也无法告警。合格目标形如：P99 < 200ms @ 1 万 QPS、单表 5000 万行、缓存命中率 90%。
3
测试数据量不真实
开发环境 1 万行数据测得飞快，生产 5000 万行全表扫描。数据量、分布、缓存命中率三项必须与生产同级，否则压测是自欺欺人。
4
只看平均延迟
均值 100ms 的服务 P99 可能 800ms，投诉全部来自长尾。监控和验收一律看 P99/P999，平均值只用于观察趋势。
5
压测环境缩水
生产 32 核压测 8 核、生产 SSD 压测机械盘、生产万兆压测千兆——规格差一倍，结论全作废。至少同代同核数同盘型。
6
凭猜优化，不用 Profiler
以为瓶颈在 DB，结果 30% 时间耗在 JSON 序列化和日志同步写盘。先用火焰图和追踪定位再动手，猜错的优化经常越优越慢。
7
异步化丢掉可靠性
消息队列没有 confirm/ack、没有重试、没有对账，高峰期悄悄丢请求。异步链路三件套：可靠投递 + 死信告警 + 准实时对账。
8
缓存解决一切
缓存命中率从 95% 掉到 80% 时 DB 流量翻 4 倍，性能雪崩；且一致性问题只是被推迟爆发。缓存要有容量上限、命中率监控和降级预案。
9
容量规划拍脑袋
按日均 QPS 买机器，大促峰值 12 倍流量瞬间打挂。按峰值 × 冗余系数规划，用弹性补差，用限流兜底，三者缺一不可。

自测

六道题

1. 评估一个接口的延迟指标，最该看哪个？
正确答案：P99 分位数。投诉来自长尾：P50 60ms、P99 420ms 的服务，1% 的用户在承受 400ms+ 的体验。平均值会把长尾完全稀释掉；最大延迟又太容易被单次异常带偏。
2. 某接口串行调用 3 个下游，每个 50ms，并行化之后总耗时约为？
正确答案：约 50ms。三个调用互不依赖时并行发起，耗时由最慢的那个决定。这也是延迟预算分配的核心规则：串行段相加、并行段取 max。注意给并行调用独立的线程池，避免相互拖死。
3. 单机基准 2000 QPS，目标峰值 20000 QPS，冗余系数 30% 再加 N+1 容错，大约需要几台？
正确答案：14 台。计算：20000 ÷ 2000 = 10 台基础；×1.3 冗余 = 13 台；+1 台容错 = 14 台。容量规划漏掉冗余系数和 N+1 是常见错误，前者应对突发和个体差异，后者保证坏一台不塌。
4. 目标 5000 QPS、单请求平均耗时 100ms，按 Little's Law 需要多少并发处理能力？
正确答案：500。Little's Law：L = λ × W = 5000 × 0.1 = 500 个在途请求。线程池、连接池、队列长度都按这个量级配置，配小了请求在池外排队，延迟指标必然失真。
5. 压测数据库用了 1 万行数据，生产同表有 5000 万行，压测结论可信吗？
正确答案：不可信。数据量决定执行计划（全表扫描 vs 索引扫描）、决定 buffer pool 命中率、决定 IO 量级。压测数据必须在数据量、分布、缓存命中率三个维度与生产同级，否则是在验证一个不存在的系统。
6. 关于性能预算（Performance Budget），正确的理解是？
正确答案：分段延迟预算。它把"前端怪后端、后端怪 DB"变成"谁的段超支谁负责"，是团队间的契约。压测按段打点，报告直接对照预算表，buffer 专款专用不许提前花。

# 容量公式

所需节点  = ceil(目标QPS × 冗余系数 / 单机QPS) + 1   # N+1
