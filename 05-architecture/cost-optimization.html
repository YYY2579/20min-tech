开始前

云成本花在哪：四大构成

不看清构成就优化，等于医生不诊断就开刀。先知道你家的钱主要烧在哪一项，才知道该动哪里。

成本项计费方式典型占比与特点
计算 Compute按实例规格 × 时长（包年包月/按量/Spot）通常占 50%~70%。最容易优化也最容易浪费：规格过大、无人使用、24h 开机但只白天用
存储 Storage按 GB × 时长 + 请求次数占 10%~20%。增长最稳定，问题多在"只存不删"：日志、备份、旧快照
网络 Network出流量（公网出/跨区/跨可用区）+ 固定 IP + LB占 5%~15%，但最容易被低估：CDN 没开、跨区调用、公网出流量都是隐形黑洞
数据库/中间件实例规格 + 存储 + 备份 + 只读实例占 10%~30%。RDS、Redis、Kafka 实例规格通常按峰值预留，日常水位低
优化第一定律：成本 = 用量 × 单价 × 时间，三个因子都能动，但优先级是 用量 > 规格/单价 > 计费模式。先把没人用的东西关掉（用量清零），再把过大的规格缩回去（单价下降），最后才是买 RI 改计费模式。跳过前两步直接买 RI，是把浪费锁死三年。

模块 1

浪费识别：三类浪费与排查手段

行业经验：云账单里 20%~40% 是可以安全砍掉的浪费。分三类，各有各的查法。

三类浪费

类型表现排查手段
闲置资源实例/磁盘/IP/负载均衡创建后没人用；测试环境常年开机；离职人员的资源云监控 CPU/内存利用率连续 7 天 < 5%；云管平台的"闲置报告"；资源标签缺拥有者
过度配置8C16G 的机器跑着 CPU 10% 的服务；RDS 按大促峰值规格常驻；只读实例无读流量用量 vs 规格对比分析；降配观察（先压测再降）；rightsizing 报告
超额预付费RI/Savings Plans 买超了实际用量；包年包月实例到期未续被按量计费（更贵）预付覆盖率 vs 实际用量曲线；到期提醒；RI 利用率报告

闲置资源排查（以阿里云/腾讯云监控为例）

# 1. 找出 CPU 利用率连续低于阈值的实例（云监控 API 或控制台）
#    阈值参考：7 天平均 CPU < 10% 且内存 < 20% → 高度疑似闲置

# 2. 找出未挂载的云盘（创建了没绑定实例，纯烧钱）
aliyun ecs DescribeDisks --Status Available --RegionId cn-hangzhou

# 3. 找出闲置的公网 IP（未绑定实例的 EIP 按时长计费）
aliyun vpc DescribeEipAddresses --Status Available

# 4. 找出没有后端服务器的 SLB（LB 实例费照付）
#    控制台看监听后端服务器组为空、或健康检查数为 0 的实例

# 5. 找出无人认领的资源（标签策略）
#    没有 owner / project 标签的资源 = 没人管的资源 = 优先清理对象
判断"闲置"要小心：CPU 低不代表没用。① 消息队列消费者平时 CPU 低，流量来了忙；② 定时任务机每天只跑 2 小时；③ 灾备实例平时 standby。所以闲置判定必须结合流量指标（QPS、消息堆积）、业务owner确认、多天窗口，不能只看一个 CPU 曲线。稳妥做法：先降配观察两周，再缩容，不要直接关机。
模块 2

优化手段一：计费模式与 Spot 实例

同样的机器，计费模式选对，单价能差 3~10 倍。

模式价格折扣约束适用
按量付费基准 100%随时开关弹性部分、不确定的用量、短期测试
包年包月约 50%~70%1 年承诺稳定的基线负载
Spot / 抢占实例1~2 折可能被随时回收（提前 2~5 分钟通知）无状态、可容忍中断：CI 构建、渲染、离线计算、部分无状态 Web
预留实例 RI约 40%~60%1~3 年承诺，绑定实例族/区域长期稳定的基线负载
Savings Plans约 40%~60%1~3 年承诺"每小时花 X 元"，不限实例族比 RI 更灵活，承诺的是消费额不是实例

真实计算：一个服务该用什么组合

# 场景：某 API 服务，日常需要 10 台 4C8G 常驻，大促额外需要 10 台两周
# 单价（以某云为例，年付单价，单位：元/台/月）
按量付费：     350 元/台/月
包年包月：     210 元/台/月（6 折）
Spot 实例：     70 元/台/月（2 折）

# 方案 A：全部按量
月成本 = 10 × 350 = 3,500 元（基线部分）

# 方案 B：基线 10 台包年 + 大促 10 台按量两周
基线月成本 = 10 × 210 = 2,100 元
大促增量 = 10 × 350 × 0.5 个月 = 1,750 元
大促当月 = 2,100 + 1,750 = 3,850 元，其余 11 个月 = 2,100 元

# 方案 C：基线 10 台 RI + 大促 10 台 Spot（服务无状态且能容忍个别重启）
基线月成本 = 10 × 150 = 1,500 元（RI 4~5 折）
大促增量 = 10 × 70 × 0.5 = 350 元
大促当月 = 1,850 元，其余 11 个月 = 1,500 元

# 年化对比：A = 42,000；B ≈ 2,100×12 + 1,750 = 26,950；C ≈ 1,500×12 + 350 = 18,350
# C 比 A 省 56%。但 C 的前提：服务无状态、可容忍 Spot 回收、有健康检查和自愈
Spot 实例的铁律：① 只给无状态、可快速恢复的负载用；② 必须处理回收通知（AWS 是 2 分钟，阿里云抢占实例通知更短），实现优雅停机（drain 连接 → 摘流量 → 退出）；③ 数据库、Redis、有状态中间件绝对不用 Spot；④ 混部时 Spot 占比建议不超过 50%，且跨多个可用区/实例族分散，避免一次回收一大片。
模块 3

优化手段二：自动伸缩与存储分层

自动伸缩：让用量匹配负载曲线

大多数业务负载有明显的昼夜周期：白天高、凌晨低，低谷常常只有峰值的 20%~30%。定时伸缩 + 指标伸缩结合：

# 定时伸缩示例（Kubernetes CronHPA / 云厂商定时任务）
08:00  从 4 副本扩到 12 副本    # 上班流量上来前就绪
23:00  从 12 副本缩到 4 副本    # 夜间低谷缩容
# 配合 stabilizationWindowSeconds 防抖动，配合 PDB 保证缩容不打死关键副本

# 效果：日平均副本从 12 降到 6.5 → 计算成本省约 45%（保留少量弹性缓冲）
# 注意：缩容省的是"副本数 × 时长"，但数据库等有状态组件不缩

存储分层与生命周期

存储类型单价参考取回速度适用数据
标准存储0.12~0.15 元/GB/月实时热数据：频繁访问的图片、日志
低频访问0.08 元/GB/月 + 取回费毫秒级月访问几次：历史图片、月报
归档 / 冷归档0.015~0.03 元/GB/月分钟~小时级（需解冻）合规留存、备份、审计日志
# 对象存储生命周期规则（以 AWS S3 为例，等价配置各云都有）
{
  "Rules": [
    {
      "ID": "logs-lifecycle",
      "Filter": { "Prefix": "app-logs/" },
      "Transitions": [
        { "Days": 30, "StorageClass": "STANDARD_IA" },
        { "Days": 90, "StorageClass": "GLACIER" }
      ],
      "Expiration": { "Days": 2555 }
    }
  ]
}
# 效果：日志量 10TB/月
# 全标准存储：10,240GB × 0.12 = 1,229 元/月
# 分层后（30 天标准 + 60 天低频 + 长期归档）：
#   最近 30 天标准：10,240 × 0.12 = 1,229
#   31~90 天低频：20,480 × 0.08 = 1,638
#   90 天以上归档（平均 5 个月存量）：51,200 × 0.02 = 1,024
# 月成本从 12,288（全标准）降到 3,891，省 68%
存储优化的关键动作：① 删除"永远不会被访问"的数据——超过保留期的日志、失败的转码临时文件、无主的上传垃圾；② 压缩——日志 gzip 后通常只有 1/5~1/10 体积，转存前先压；③ 本地缓存 + CDN替代重复回源，存储请求次数也是钱。
模块 4

优化手段三：CDN、预留实例与计算策略

CDN：用边缘流量替代源站流量

流量类型不经 CDN经 CDN（命中率 95%）
100GB 图片/视频分发公网出流量 8,000 元 + 源站带宽压力CDN 流量约 2,400 元
源站压力100GB 全打到源站仅 5GB 回源，源站带宽降 95%
# CDN 省钱三要点
# 1. 命中率是生命线：95% 以下说明缓存策略有问题（URL 带随机参数、Cache-Control 设错）
# 2. 静态资源上 CDN，动态 API 不要（CDN 缓存动态内容既费钱又容易脏）
# 3. 文件合并 + 压缩：100 个小文件合并成 1 个，请求数费用和连接开销都降

RI / Savings Plans 怎么买不亏

# 购买前的三个验证
# 1. 用量基线：过去 6 个月最低用量作为承诺基线，不要按平均或峰值
#    例：月均 20 台、最低 16 台 → 承诺覆盖 16 台，其余按量/弹性
# 2. 折扣率对比（同承诺期）
#    AWS EC2 Instance SP：1 年 no-upfront ≈ 28% off；3 年 ≈ 54% off
#    Compute SP：1 年 ≈ 20% off；3 年 ≈ 66% off（更灵活）
#    阿里云 Savings Plans / 预留实例券：1 年约 6 折，3 年约 4 折
# 3. 覆盖率目标：60%~80% 是甜点区
#    < 50%：买少了，基线在按量付费（贵）
#    > 90%：买超了，业务缩水时 RI 变成纯浪费（转售折价大）

# 承诺额计算公式（Savings Plans）
每小时承诺额 = 基线实例数 × 实例按量单价 × (1 - 目标折扣率) × 0.8（8 折安全线）
# 例：10 台 4C8G，按量 0.5 元/台/小时，目标 3 年 Compute SP 66% off
承诺额 = 10 × 0.5 × 0.34 × 0.8 ≈ 1.36 元/小时
# 实际用量 8 台时：8 × 0.5 = 4 元/小时按量价，SP 只覆盖 1.36 → 其余 2.64 按量，不浪费
# 实际用量 14 台时：SP 覆盖 1.36 + 4 台按量，正好覆盖增量
RI/SP 最大的坑是"买错"：① 绑定错了区域/实例族，用不了；② 按峰值买，业务下滑后承诺额变成沉没成本；③ 忽略"标准化 RI vs 可转换 RI"的差异——可转换 RI 贵 5%~10% 但能换实例族，业务在演进期选它。买之前用云厂商的 Cost Explorer 类工具模拟：按去年最低用量买，覆盖率控制在 80% 以内。
模块 5

FinOps：让成本可视、可分账、可问责

FinOps 是一套"财务 + 工程 + 业务"协作的成本管理实践。核心不是省技巧，而是让每个团队看见自己花多少钱、并对数字负责。

① 标签策略（一切的前提）：所有资源必须带标签：owner（团队/人）、project（项目）、env（prod/staging/dev）、app（应用名）。没有标签的资源在分账报表里是一笔糊涂账，占比通常 15% 以上。
② 分账报表：按标签聚合账单，生成"团队 × 环境 × 应用"的月度成本报表，发给每个团队负责人。看不见的成本没人管。
③ 成本可视化：搭建成本看板（Grafana + 账单 API 或云厂商 Cost Tools）：日趋势、环比、预算消耗进度、异常突增告警。
④ 责任到团队：给每个团队设月度预算，超预算 80% 告警，超 100% 需要说明。研发负责人对成本负责，就像对可用性负责。
⑤ 优化例会：每月一次成本 Review：本月浪费 TOP 5、优化项进展、新上线的成本影响评估。把成本纳入技术方案评审（大方案必须附成本估算）。
⑥ 异常检测：成本突增自动告警（如日费用环比涨 50%），常见原因是配错规则、忘记关的资源、被刷流量。

成本分摊到应用（示例结构）

# 月度分账报表（按标签聚合）
团队        env      应用           月成本     环比     负责人
交易       prod     order-api      12,400    +8%     张三

交易       staging  order-api       3,100   -15%     张三

# 无标签资源优先处理：能删的删，删不掉的补标签
FinOps 成熟度三个阶段：① 可见（知道花了多少）——大多数公司停在这；② 可问责（每个团队对自己的账单负责）；③ 可预测（新方案上线前能算出成本影响，容量和成本联动规划）。到第三阶段，成本优化才从"运动"变成"日常"。
模块 6

架构层优化：从源头降本

前面的手段是"买得更便宜"，架构优化是"用得更少"。用量降 50%，比单价降 50% 更彻底，而且没有 SLA 风险。

减少跨区流量
同机房/同可用区调用免费，跨区按流量计费且延迟高。把频繁互调的服务放同一可用区，数据库与计算就近部署。一次架构评审能省每月数万跨区费。
缓存降后端负载
缓存命中率从 80% 提到 95%，后端 QPS 降 75%，机器和数据库都能缩。Redis 内存扩容比数据库扩容便宜一个量级。
Serverless 按需
低频任务（报表、图片处理、Webhook）用函数计算，没有流量不计费。日调用 1000 次的任务常驻 2 台机器是纯浪费。
异步化削峰
同步改消息队列，消费端按平均速率处理，按峰值配机器改成按均值配，配合夜间缩容。
数据冷热分离
3 个月前的订单归档到廉价存储，主库只留热数据，RDS 规格可以降一档。
压缩与协议
启用 HTTP/2、gzip/br 压缩，API 响应体瘦身，出流量和序列化 CPU 同时降。
# 架构优化 ROI 计算示例：缓存改造
改造前：商品详情 API，QPS 5,000，全部打到 RDS，需要 6 台应用 + db.m6.2xlarge RDS
  RDS 月成本：8,600 元；应用 6 台 × 210 = 1,260 元；合计 9,860 元/月
改造后：加 Redis 缓存，命中率 95%，DB QPS 降到 250
  RDS 降配到 db.m6.xlarge：4,300 元；应用缩到 3 台：630 元；Redis 4G：480 元
  合计 5,410 元/月
# 月省 4,450 元（45%），且 P99 RT 从 80ms 降到 8ms —— 省钱的同时性能还更好
判断标准：好的架构优化同时降本和提质（缓存、异步化、就近部署）；单纯的降本动作（缩规格、删冗余、降副本）必须配合压测和监控，否则就是在省小钱埋大雷。

降本动作安全分级

风险级动作执行要求
低风险删闲置资源、测试环境定时开关、存储分层、开 CDN确认 owner 后直接执行，周报跟踪
中风险规格右调、定时伸缩、快照策略收紧压测验证 + 灰度观察一周 + 保留回滚窗口
高风险生产库缩配、退灾备、降副本数、Spot 替换核心实例架构评审 + SRE 双签 + 故障演练 + 大促窗口禁用
# 降本动作的通用安全流程
1. 数据说话：该资源 30 天用量曲线 + 成本占比
2. 归属确认：找到 owner，通知相关方（SRE + 业务方）
3. 灰度执行：先降 20% 观察 3 天，指标不动再降到位
4. 监控兜底：降本后 72 小时重点盯 RT、错误率、饱和度
5. 回滚预案：记录原配置，异常一键恢复
模块 7

十个线上坑

1
只看账单总额，不看 SLA 和业务指标
把生产库缩配、把灾备节点退了，月省 5,000，一次故障损失 50 万。成本优化必须按环境分级：生产核心链路降本要谨慎，测试/开发环境才是大头。
2
预留实例 RI/Savings Plans 买错
按去年峰值买 3 年全量承诺，今年业务下滑 40%，承诺额变成纯浪费，转售要折价 30%+。按最低用量买、覆盖率控制在 80% 以内、优先选可转换 RI。
3
忽视数据传输费这个黑洞
图片没走 CDN 全从源站出、跨可用区调用频繁、NAT 网关流量没规划，网络费能占到账单 20%+。每月看一次"网络费用"明细，CDN 命中率和跨区调用是重点。
4
Spot 实例用在有状态服务上
Spot 被回收 = 数据丢 + 服务中断。数据库、Redis、Kafka 绝对不用 Spot。无状态服务用 Spot 也要跨 AZ 分散、做优雅停机、控制占比 < 50%。
5
CPU 低就缩容，不看其他指标
CPU 10% 但内存 85%（缓存型服务）、或连接数打满（代理型服务），缩容后先挂的是内存和连接。降配前看四维指标 + 压测验证。
6
测试环境常年全量开机
dev/staging 环境 7×24 开着比生产还大，占了账单 30%+。定时开关（工作日开机、夜间和周末关机）能省 60%~70%，用 IaC 脚本化重建。
7
存储只增不减，快照无限累积
自动快照策略配了 365 天留存，3 年后磁盘快照费用超过实例本身。备份要分层：日备保留 7 天、周备 4 周、月备 12 个月，更早进归档。
8
没有标签体系，成本无法归因
账单是一笔总数，问"哪个服务这个月多花了 2 万"没人答得上。先建标签策略再谈优化，否则优化成果也无法归因到团队。
9
优化只做一次，之后成本反弹
清理了一批闲置实例，半年后新的闲置又堆成山，没有例行机制。FinOps 要常态化：周报闲置、月报预算、季度 Review。
10
降本动作没通知业务和 SRE，搞出故障
把"没人用"的实例关机，其实是某团队的灾备；把 RDS 只读实例退了，大促时读流量无处去。任何降本动作必须：确认 owner + 查监控流量 + 通知相关方 + 保留回滚窗口。
自测

六道题

1. 云成本优化的正确优先级是？
正确答案：先砍用量再谈单价。跳过前两步直接买 RI/SP，等于把现有浪费锁死 1~3 年。用量归零（删闲置）永远是最优先、最安全的优化。
2. 下列哪种负载最适合用 Spot/抢占实例？
正确答案：CI 构建/离线任务。Spot 可能被随时回收，只适合无状态、可容忍中断、可快速恢复的负载。数据库和缓存是有状态服务，绝对不能用。
3. 某服务过去 6 个月用量在 14~22 台之间波动（月均 18），买 Savings Plans 承诺多少合适？
正确答案：按最低用量 14 台承诺。按峰值买，业务低谷期承诺额变成纯浪费；全按量则基线部分多花 40%~60%。承诺基线 = 历史最低用量 × 0.8 安全线，覆盖率 60%~80% 是甜点区。
4. 关于 FinOps 标签策略，最重要的是？
正确答案：核心是 owner/project/env/app 四类标签。没有标签的资源在分账里是糊涂账（通常占 15%+），测试环境的钱也常常是大头。标签体系是成本可视、问责的前提。
5. "把测试环境从 7×24 开机改为工作日 8 小时开机"，大约能省多少计算成本？
正确答案：约 60%~70%。8h×5 天 = 40 小时 / 168 小时 ≈ 24% 运行时长，节省约 76%，考虑启停损耗留余量约 60%~70%。测试环境是成本优化收益最大的地方之一。
6. 发现某实例 CPU 连续 7 天低于 5%，第一反应应该是？
正确答案：先确认再动手。CPU 低不代表没用：消息消费者平时闲、定时任务机每天只跑 2 小时、灾备实例平时 standby。稳妥路径：确认 owner → 看流量指标 → 降配观察 → 缩容或回收。
