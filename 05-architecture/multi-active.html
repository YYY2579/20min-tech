二十分钟学透多活与容灾架构

多活不是"多部署几个机房"就完事。这篇讲清楚同城双活 / 异地多活 / 单元化的真实差别、数据同步怎么解决冲突、切流回切怎么做不翻车，以及自增 ID、时钟漂移、双向同步回环这几个经典坑。

开始前

先统一两个指标的语言

多活讨论里 90% 的争吵，源于 RTO 和 RPO 没对齐。先记住这两个定义，全文都建立在这上面。

指标含义业务翻译
RTO
Recovery Time Objective		从故障发生到业务恢复可用允许的最长时间"最多能忍多久不能下单"
RPO
Recovery Point Objective		故障后恢复到的数据时间点，即能容忍丢多少数据"最多能丢多少钱的订单"
RPO=0 的含义：数据零丢失。技术上要求同步复制（每笔事务必须等对端确认才提交），而光速决定了跨城同步每笔事务要多等 25ms 以上，写吞吐直接被打下来。RPO=0 只适合同城，异地多活的 RPO 通常是秒级。这是物理限制，不是工程能力问题。
模块 1

容灾等级：GB/T 20988-2007 六级

国家标准《信息安全技术 信息系统灾难恢复规范》（GB/T 20988-2007）把容灾能力分成 6 级。金融、支付类系统通常要求第 5 级以上，普通业务系统第 3~4 级足够。

等级RTO 要求RPO 要求典型方案
第 1 级2 天以上1 天 ~ 7 天备份介质异地存放，无热备场地。灾难后基本靠重新搭环境
第 2 级24 小时以上1 天 ~ 7 天备份介质异地 + 备用场地、硬件到位
第 3 级12 小时以上数小时 ~ 1 天电子链路传输备份数据，部分关键设备热备
第 4 级数小时 ~ 2 天数小时 ~ 1 天数据库定时复制，应用双机/集群，定时数据同步
第 5 级分钟级0 ~ 30 分钟实时数据复制，应用双活就绪，可自动/半自动切换
第 6 级分钟级0（零丢失）同步复制 + 双活自动切换，切换过程数据不丢

等级不是越高越好

  • 成本跳变点在第 5 级：进入第 5 级意味着应用要能双活运行（无状态化改造、数据实时同步、流量调度），投入比第 4 级高一个数量级。
  • 第 6 级（RPO=0）+ 异地 = 矛盾：同步复制跨 1000km，每笔事务多 25~40ms，核心交易链路吞吐可能下降 5~10 倍。银行核心系统用第 6 级，但都是同城双活 + 异地灾备。
  • 先定业务指标，再定技术等级。没有业务共识的容灾目标等于没有目标：问清楚"中断 1 小时损失多少、丢 1 小时数据损失多少"，再选等级。
常见组合：同城双活（RPO≈0、RTO 分钟级，覆盖机房级故障）+ 异地灾备（RPO 分钟级、RTO 小时级，覆盖城市级故障）= 业界主流的两地三中心。城市级全实时多活（三地五中心）只有头部电商、支付、运营商玩得动。
模块 2

四种部署形态对比

形态覆盖故障域跨活 RTTRPO特点与适用
同城双活机房级1~5ms≈0数据库同步复制，两边同时服务。城市级故障（光缆挖断、停电）会同时挂两边，不防城市级灾难
两地三中心机房 + 城市25~40ms（同城活间）秒级~分钟级同城双活 + 异地灾备（异步复制）。当前最主流，成本与能力的平衡点
异地多活
（三地五中心）		城市级25~40ms秒级多个城市同时服务，需单元化 + 流量调度 + 冲突避免设计。复杂度最高，架构改动侵入所有业务
异地冷备
暖备		城市级—分钟~小时级灾备中心平时不接流量，故障时拉起。便宜、简单，RTO 小时级。中小系统的务实选择

关键认知

  • 同城双活是"机房级"容灾，不是"多活"的全部。把两个机房部署在同一城市，光缆同时挖断就全完——所以同城双活之上必须有异地灾备兜底。
  • 异地多活的核心难点从来不是"多部署一份"，而是"两边都能写"。一旦只有一个活能写，就退化成了"主备"，多活的收益（城市级故障下业务不中断）也就不存在。
  • 距离是物理约束：北京-上海直线距离约 1000km，光在光纤中速度约 20 万 km/s，往返理论 10ms，实际路由和交换设备叠加后通常 25~40ms。广州-深圳同城约 1~3ms。跨太平洋 120ms+，跨洋多活等于让用户每次下单多等一个心跳，基本不可行。
模块 3

单元化架构（Set 化）

单元化是异地多活的落地形态：把用户按维度切成 N 份，每份（一个 Set）是一个自包含的"小系统"，一个用户的全部流量在同一个 Set 内闭环。

一个 Set 里有什么

# 每个 Set 是完整的技术栈，独立自治：
接入层   nginx / gateway      # 只服务本单元用户
应用层   biz-app              # 无状态，按单元部署
缓存层   Redis 集群           # 单元内缓存，不跨单元读
数据层   MySQL 分片            # 按 user_id 分库，本单元分片可写，其余为只读副本

# 全局流量走向（三地五中心示例）：
DNS / GSLB  ──按用户路由──▶  城市A-Set1 / Set2 / Set3
                            城市B-Set4 / Set5
                            城市C-中心Set（全局数据、跨单元查询）

路由规则

方式做法优缺点
取模路由set_id = user_id % N简单，但扩容 N 变化时大部分用户要迁移
路由表uid → set_id 映射存配置中心灵活，切流/迁移改表即可，生产常用。需保证路由表全局一致
分段路由按 UID 尾号灰度（尾号 0-9 → Set1）适合切流灰度：先切 10% 用户，观察无问题再放全量

单元化三条铁律

  1. 封闭性：一个用户的主要业务（读写）必须在同一个 Set 完成，跨单元调用只允许读且要走中心单元或只读副本。封闭率要做到 90% 以上，否则多活的延迟优势会被跨活调用吃掉。
  2. 写唯一：任意一份数据全局只有一个 Set 能写，其他 Set 持有只读副本。这是避免双向同步冲突的根本手段——没有写写冲突，同步就只剩单向复制。
  3. 中心单元：全局共享数据（商品目录、配置、用户基础资料）由中心 Set 统一写、各 Set 订阅变更。中心 Set 是逻辑概念，可跨城市部署保证自身高可用。
单元化的收益：① 跨活 RTT 从 25~40ms 降回同城的 1~5ms，用户无感知；② 故障域缩小到 1/N 用户，一个 Set 挂了只影响一小片；③ 数据分片天然并行，容量随单元数水平扩展。
代价：单元间数据访问受限（不能随便 join 别人的库）、用户迁移要搬数据、架构复杂度显著上升。日活和团队规模不够时不要上。
模块 4

数据同步：binlog、DTS 与冲突解决

多活的数据层同步，主流做法是基于数据库 binlog 的异步复制，而不是业务双写。

同步链路（MySQL 生态）

# 源库 MySQL ──binlog──▶ Canal/Debezium ──▶ MQ(Kafka/RocketMQ) ──▶ 消费端 ──▶ 目标库

# Canal：伪装成 MySQL slave，向主库发送 dump 协议拉取 binlog
#   → 解析成行级变更（RowData），投递给 MQ，由消费端回放到对端
# Debezium：Kafka Connect 生态，Red Hat 开源，同样读 binlog，直接对接 Kafka
# DTS：阿里云数据传输服务，托管版同步/迁移/订阅，支持双向

# 监控同步延迟（源库执行）
SHOW SLAVE STATUS\G     # 看 Seconds_Behind_Master（异步复制的滞后秒数）
# Canal 侧看位点差：源库 binlog position 与 Canal 已解析 position 的差值

为什么不用业务双写

  • 双写 = 两个库的写入顺序无法保证一致，对端失败还要考虑补偿，代码侵入每个写路径。
  • binlog 同步与业务解耦：业务代码零改动，对端挂了消息在 MQ 里堆积，恢复后自动追平。
  • binlog 天然保序（同表同行变更顺序一致），消费端单分区单线程即可保序。

双向同步与冲突解决

两个活都能写同一份数据时，必须回答"冲突了听谁的"。策略按优先级排列：

策略做法适用与风险
唯一写原则按分片/维度保证一份数据只有一个写来源（单元化的基础）首选。从设计上消灭冲突，而不是解决冲突
增量合并可加性字段（库存、余额、计数）同步增量而非绝对值：A 活 -1、B 活 -1 → 合并为 -2适合计数器类。要求同步的是操作不是结果，实现上要把 UPDATE 解析为 delta
最后写入优先
LWW		每条记录带版本时间戳，冲突时取时间戳大的简单但依赖全局时钟同步。NTP 抖动 100ms 就可能把新数据判成旧的
业务规则合并按业务语义合并（如状态机只允许 PAID→SHIPPED 合法迁移）最可靠但要为每类冲突写规则，成本高。金融常用
人工介入冲突记录进死信表，报警 + 人工处理兜底。冲突率必须低到人工可处理（< 10 条/天）
回环（loop）问题：A 的变更同步到 B 后，B 的同步链路可能把这条变更再推回 A，A 再推回 B……无限循环，两边 CPU 打满、MQ 堆积。解法：同步链路带上来源实例标识（source DB ID / 同步任务 ID），消费端丢弃"来源是自己"的消息；或保证 A→B 与 B→A 使用不同的 MQ 集群/链路，物理上不互通。
模块 5

流量调度：GSLB、DNS 与就近接入

手段粒度与生效速度适用与坑
DNS 智能解析粗。受 TTL 缓存影响，切换生效 5 分钟 ~ 数小时按来源 IP 归属地/运营商返回不同城市入口 IP。只能做第一跳调度，切流演练前必须先确认各地 TTL 设置（建议提前调低到 60s 以下）
GSLB
全局负载均衡		细。秒级生效，可按 UID、按比例灰度基于健康检查结果和调度策略分配流量，支持按尾号灰度切流。切流主力。本身要高可用（多节点集群，否则单点）
Anycast细，但不可控多个城市宣告同一 IP，BGP 路由就近到达。适合无状态接入层；路由波动会把用户"瞬移"到另一城市，长连接全断，有状态服务慎用

健康检查：摘除与恢复

# 主动探测：GSLB 定期请求各城市入口的 /health
#   /health 要查真实依赖（DB ping、缓存 ping、核心接口探活），不能只返回 200

# 被动探测：统计真实请求的错误率/超时率
#   错误率 > 50% 持续 30 秒 → 摘除；错误率 < 5% 持续 2 分钟 → 恢复

# 关键：摘除阈值与恢复阈值必须不同（滞回 hysteresis），防止网络抖动时反复摘除-恢复
健康检查误判是二次事故的常见源头：一次网络抖动摘除了健康节点，流量涌向对端，把对端也压垮（级联雪崩）。防护：① 探测要有多节点交叉验证，不能单探测点说了算；② 摘除前要求连续 N 次失败；③ 恢复时先放 5% 流量观察（半开探测）；④ 各城市保留最小应急容量（至少能扛平时 50% 流量）。

就近接入的真实边界

  • 就近接入只对接入层有意义。用户被调度到北京活后，他写的所有数据也必须留在北京 Set（否则跨活访问立刻产生延迟）。
  • 用户漫游：上海用户出差到北京，DNS 把他调度到北京活，但他的数据在 Set-A。解法是路由表按 user_id 而非 IP 定位——接入层根据登录态里的 UID 反查路由表，再代理到正确的 Set。
模块 6

多活数据一致性六原则

按用户维度路由
一个用户的主要流程（读写）在同一个 Set 内闭环。这是多活一致性的地基，其他原则都建立在它上面
避免跨活事务
跨城市 2PC 每笔事务等 25~40ms，吞吐暴跌。改成本地事务 + 异步消息（Saga/最终一致），对账兜底
全局数据走中心
配置、商品目录等全局数据由中心单元统一写，各单元订阅，允许秒级延迟。各单元不许直接写全局表
缓存与库同单元
Redis 与本地 MySQL 放同一 Set，禁止跨活读缓存（缓存同步的延迟比数据库同步更难控）
分布式 ID 分段
各单元用发号器/Snowflake 变种，分配不同 worker id 段，禁止各自 AUTO_INCREMENT（冲突经典来源）
接受读己之写受限
用户切城市后几秒内可能读到旧数据。产品层要接受"最终一致"，或提供"刷新强制读主"按钮

跨活调用先探测再调用

# 客户端 RPC 框架隐式传参：入口从登录态取 user_id，路由到本 Set 的服务
# 跨 Set 调用（如看他人公开信息）流程：
1. 本地 Set 只读副本查询      # 优先，延迟 1~5ms，数据可能有秒级延迟
2. 副本没有 → 中心单元查询    # 次选，延迟 10~30ms
3. 必须实时 → 直连对方 Set    # 最后手段，延迟 25~40ms，且对方故障会传导

# 铁律：同步调用链上不允许超过 1 次跨 Set 调用
# 链路 A→B→C 三次跨活 = 100ms+ 起步，故障概率按乘法叠加
模块 7

切流、回切与脑裂防护

切流流程（以 A 活故障、切到 B 活为例）

前置检查：B 活容量已扩容到平时的 1.5 倍以上；数据同步延迟为 0 或已知；依赖服务（支付、消息）健康。容量不够就切 = 把故障放大
入口切流：GSLB/DNS 把 A 的用户路由切到 B。按 UID 尾号灰度：1% → 10% → 50% → 100%，每档观察 5~10 分钟错误率和延迟
停写 A：A 的应用层打开"只读开关"（禁写），数据库切只读账号。注意：定时任务、消息消费者、补偿脚本也必须停——它们是最常被漏掉的写来源
等待 drain：存量请求处理完（长连接优雅退出，通常 30~60 秒），确认 A 无新写入后再动数据层
验证：B 的错误率、核心接口成功率、数据位点对账（抽样比对 A/B 关键表行数与关键字段）
修复 A 与回切：A 修复后同样灰度回切。回切前先双向比对数据，冲突按预设规则合并，否则回切瞬间双向同步会爆发大量冲突

脑裂：定义、检测与防护

层面检测手段防护手段
网络层心跳超时心跳本身检测不了脑裂（分区两边都认为对方死了），必须引入第三方仲裁
仲裁层ZooKeeper / etcd 的 quorum（多数派）3 或 5 节点集群，分区后少数派侧自动放弃主身份。2 节点做不到仲裁，至少 3
数据库层MySQL Group Replication 单主模式（Paxos 多数派选主）多数派不可达时自动只读，从协议上杜绝双主。双主同步架构天然有脑裂风险，慎用
应用层全局开关（配置中心）fencing（隔离）：检测到分区后，旧主自动降级为只读（关闭写入口）。切流铁律：先停写旧活，再放行新活，两活永远不允许同时可写
没有演练过的切流方案等于没有方案。混沌工程实践：定期随机杀单元、断网、制造数据延迟，验证：① 切流耗时在 RTO 内；② 回切不丢数据；③ 监控和告警真的能发现。只演练"切过去"不演练"切回来"是最常见失误——回切更脏（冲突合并、双写追平），失败就是二次事故。
模块 8

十个线上坑

1
两活各自 AUTO_INCREMENT，主键冲突
两个活的库都设了自增起始值，同步后大量主键冲突，同步链路中断、数据追不平。必须用发号器/Snowflake 变种，每单元分配不同 worker id 段，从根上取消自增。
2
时钟漂移导致 LWW 冲突解决误判
用时间戳比大小解决冲突，但两台机器 NTP 偏移 200ms，新的数据被判定为旧的，直接被覆盖丢失。跨活机器必须统一 NTP 源并监控偏移，或干脆不用 LWW。
3
双向同步回环
A→B 同步的变更被 B→A 链路原样推回，无限循环，MQ 堆积、CPU 打满。同步链路必须带来源实例标识，消费端过滤"来源是自己"的消息。
4
把跨活同步延迟当成 bug 查半天
用户在上海活下的单，在北京活查不到——其实是同步延迟 1~3 秒。要么把读路由回原单元（按 UID 路由），要么产品层接受最终一致并给"强制读主"入口。
5
切流只切了流量，没停写
GSLB 切走了入口流量，但旧活的应用还在跑、定时任务还在写、消息消费者还在消费，旧主库继续写入导致两边数据分叉。停写必须是全链路：应用开关 + 数据库只读账号 + 定时任务 + 消费者。
6
回切前不做数据比对，冲突集中爆发
旧活停写期间仍有遗漏的写来源（补偿任务、手工修数据），回切后双向同步瞬间涌入大量冲突记录，追平要几小时甚至引发数据错误。回切流程必须包含双向比对 + 冲突预合并。
7
健康检查误判引发级联雪崩
一次网络抖动摘除了健康节点，流量涌向对端把对端压垮，最后全站不可用。探测要多节点交叉验证、摘除要连续失败 N 次、恢复要半开探测、每城保留最小应急容量。
8
RPO=0 做成跨城
同步复制跨 1000km，每笔事务多等 25~40ms，核心交易吞吐下降一个数量级，最后被迫回退异步，RPO 目标形同虚设。RPO=0 只适合同城（RTT 1~5ms）。
9
同步延迟没有监控
同步落后 50 万条没人发现，切流时数据缺一大块，业务直接错账。位点差/Seconds_Behind_Master/消费滞后必须配告警（如超过 10 秒即告警、超过 60 秒打电话）。
10
只演练切过去，没演练切回来
切流演练很成功，回切时冲突合并失败、数据对不上，灾变成了二次事故。回切（冲突、双写追平、灰度放量）比切流更脏，必须纳入定期演练并记录耗时。
自测

六道题

1. 业务方说"我们的系统 RPO=0"，这在跨城异地多活架构下意味着？
正确答案：物理上几乎不可行。RPO=0 要求每笔事务等对端确认才提交（同步复制）。同城 RTT 1~5ms 可以承受，跨城 25~40ms 会让写吞吐下降一个数量级。跨城多活的 RPO 通常是秒级，用异步复制 + 监控延迟来保障。
2. 异地多活中两个活都可能写同一行数据，最可靠的冲突避免手段是？
正确答案：唯一写原则。从设计上消灭冲突远比解决冲突可靠。LWW 依赖全局时钟（NTP 抖动会误判），分布式锁跨城加锁延迟高且自身可用性差。单元化按 user_id 分片，让每片只有一个写来源，其余持有只读副本。
3. 用 Anycast 做接入层调度的最大风险是？
正确答案：路由波动导致连接瞬移。Anycast 靠 BGP 宣告相同 IP 实现就近到达，但网络抖动或策略变化会让流量瞬间换路径，用户的 TCP 长连接全部断连。它适合无状态的接入层（如 DNS、静态资源），有状态服务要谨慎。
4. 双向同步出现"数据无限循环、两边 CPU 打满、MQ 持续堆积"，最可能的原因是？
正确答案：回环。A→B 的变更被 B 的同步链路当成新变更再推回 A，形成死循环。解法：同步消息带来源实例标识，消费端丢弃"来源是自己"的消息；或让两个方向的同步走物理隔离的不同链路。
5. 切流时最关键、也最常被遗漏的动作是？
正确答案：全链路停写 + drain。只切入口流量而漏掉定时任务、补偿脚本、消息消费者，旧库会继续写入，两边数据分叉，且分叉点极难排查。另外切流前要确认对端容量已扩容（通常 1.5 倍）且同步延迟为 0。
6. 关于脑裂防护，下面哪个说法是对的？
正确答案：需要第三方仲裁 + 隔离。网络分区时两边都会认为对方死了，心跳本身无法区分"对方宕了"和"链路断了"。要用 ZooKeeper/etcd 的多数派（至少 3 节点）或 MySQL Group Replication 的 Paxos 选主，并配合 fencing：旧主自动降级只读。2 节点集群无法仲裁。
