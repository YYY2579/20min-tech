开始前

准备一个能试接口的环境

API 设计的知识必须"看得见响应"才记得住。起一个最简单的 HTTP 服务，用 curl 观察状态码、Header、错误响应体。

# 用 Python 起一个 3 行的 HTTP 服务（或换成任何你熟悉的栈）
cat > server.py <<'EOF'
from http.server import HTTPServer, BaseHTTPRequestHandler
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.end_headers()
        self.wfile.write(b'{"code":0,"data":{"id":1},"message":"ok"}')
HTTPServer(("", 8000), H).serve_forever()
EOF
python server.py

模块 1

什么时候该拆微服务（先讲什么时候不该）

绝大多数团队拆微服务的动机是"别人都在拆"，而不是"我的系统扛不住了"。微服务是用分布式复杂度换取独立演进能力 —— 如果团队还没有这个需求，就纯亏。

什么时候不该拆（四个红线）

不该拆的情形为什么，以及拆了会怎样
团队规模小（< 10 人）微服务的核心收益是"多个小团队各自独立发布"。人少的时候，沟通成本本来就很低，拆了反而每个人都要维护多个服务，运维负担翻几倍
领域没理清业务边界还模糊时拆出来的服务，边界一定是错的。而错误边界的代价极高：要么大量跨服务调用（分布式单体），要么反复重构
没有运维能力微服务要求你有：日志聚合、链路追踪、指标监控、CI/CD、容器编排。缺一个，线上出问题就抓瞎
没有性能/扩展压力如果单体能扛住，拆分不会带来任何性能提升，只会增加一次网络调用（延迟 + 故障点）

单体优先原则（Monolith First）

业界（Martin Fowler 等）的共识是：先做单体，等边界清晰了再拆。但这里有个关键前提 —— 单体必须是"模块化单体"（Modular Monolith），而不是一坨面条。

面条式单体
所有代码互相直接调用，没有模块边界。这种代码将来拆不动，因为拆任何一块都会牵连全局
模块化单体
代码内部有清晰的模块边界（包结构 / 模块），模块之间只通过明确的接口通信。这种单体将来能平滑拆成微服务
实践建议：即使是单体，也要在代码里画出"未来可能成为微服务的边界"（用包/模块隔离，模块间只允许通过接口调用，禁止跨模块直接访问对方的数据库表）。做到这一点，将来拆分只是"把模块的网络调用从本地调用改成 RPC"，成本极低。反之，边界混乱的单体是永远拆不动的。
判断标准（什么时候该拆了）：① 多个团队在同一个代码库上频繁冲突，发布互相阻塞；② 某个模块需要独立扩容（比如搜索模块吃 CPU，其他不吃）；③ 某个模块的技术栈确实需要不同（如 AI 推理用 Python，业务用 Java）；④ 某个模块的可用性要求显著高于其他（如支付）。四条中至少命中两条，才值得付出分布式代价。
模块 2

拆分维度：怎么拆才不拆错

拆分的核心问题只有一个：边界画在哪里，才能让"跨边界的调用"最少。因为每一次跨边界调用都是一次网络请求，都是延迟、故障点和一致性问题。

正确维度一：按业务能力拆（Business Capability）

把系统按"业务提供的能力"切分，每个能力对应一个服务。判断标准：这个服务的名字能不能用一个"业务名词"说清楚。

服务职责（业务能力）
用户服务注册、登录、资料、权限
订单服务下单、取消、查询订单状态
库存服务扣减、回滚、查询库存
支付服务发起支付、支付回调、退款

正确维度二：按 DDD 限界上下文拆（Bounded Context）

DDD（Domain-Driven Design，领域驱动设计）中的限界上下文指"一个模型在其中保持一致的边界"。通俗说：同一个业务名词，在不同上下文里含义不同，就应该拆开。

# 经典的例子："商品"这个词在不同上下文里是不同的东西

商品上下文（Product）
  属性：名称、描述、图片、类目、上架状态
  关心的是"怎么展示、怎么被搜到"

库存上下文（Inventory）
  属性：SKU、可用数量、锁定数量、仓库位置
  关心的是"能不能卖、卖了多少"

订单上下文（Order）
  属性：下单时的商品快照、成交价、数量
  关心的是"这一单买了什么、什么价"

# 结论：不要设计一个"万能商品服务"被所有上下文共用。
# 每个上下文持有自己需要的"商品"字段，通过 ID 关联，各自演进。

反例：按技术分层拆（最常见的错误）

✗ 错误拆法：按技术层次拆
  用户控制器服务 / 用户业务逻辑服务 / 用户数据访问服务
  → 一个业务需求要改三个服务，跨三次网络调用，
  → 这就是"分布式单体"（Distributed Monolith），最糟的形态

✓ 正确拆法：按业务能力 / 限界上下文拆
  用户服务（含它自己的控制器、业务逻辑、数据访问）
  → 一个业务需求只改一个服务，边界内聚
为什么"按技术分层拆"是灾难：它把变更频率不同的东西拆开了，把变更频率相同的东西也拆开了。结果就是：改一个功能要在 3 个服务里改代码、发 3 次版、协调 3 次发布；一次请求要跨 3 次网络调用，延迟和故障点都翻倍。这种拆分带来的复杂度是纯粹的负收益。

拆完怎么验证拆得对

检查跨服务调用次数：一个业务请求（如"下单"）跨服务调用 > 4 次，说明边界可能画错了（太细，或者把内聚的东西拆开了）。
检查数据库共享：如果两个服务访问同一张表，说明边界是假的 —— 共享数据库是分布式单体的第一特征。
检查发布依赖：改服务 A 是否必须同时改服务 B 才能上线？如果是，说明它们应该是一个服务（要么合并，要么用契约保证兼容）。
检查数据一致性：如果两个服务之间需要强一致（跨服务事务），说明边界切在了不该切的地方 —— 强一致的数据应该在同一服务内。
模块 3

通信方式选型

服务间通信有两条根本路线：同步（请求-响应）和异步（消息）。选错的代价很大，先看同步的三种协议对比。

同步通信：REST / gRPC / GraphQL

维度RESTgRPCGraphQL
协议HTTP/1.1 或 2 + JSONHTTP/2 + Protobuf（二进制）HTTP + JSON，单端点
性能中（JSON 文本、体积大）高（二进制、多路复用、头部压缩）中（可能因 N+1 查询变差）
契约弱（靠文档，易漂移）强（.proto 文件即契约，可生成代码）强（Schema 即契约）
浏览器友好最好（原生支持）差（需 gRPC-Web 代理）好（但需要客户端库）
调试难度最容易（curl 直接调）难（二进制，需专用工具 grpcurl）中（单端点，请求体复杂）
流式弱（SSE 勉强）强（双向流原生支持）中（Subscription）
适用对外 API、浏览器调用、简单内部调用内部服务间高频调用、低延迟、强契约前端聚合多个数据源、客户端字段按需

异步通信：消息队列

当调用方不需要立即拿到结果时，应该用 MQ 而不是同步调用。这能削峰、解耦、并在下游故障时让上游不受影响。

场景该用什么理由
下单后通知库存/积分/风控MQ 异步下单不需要等这些完成，异步更快更解耦
查询用户资料同步 REST / gRPC必须立刻拿到结果
扣库存（下单流程内）同步调用要立即知道成功与否才能决定订单状态
发送短信 / 邮件MQ 异步失败也不该阻塞主流程，可重试
选型口诀：要立刻拿结果 → 同步（内部高频用 gRPC，对外用 REST）；不需要立刻拿结果 → 异步（MQ）；前端要灵活聚合数据 → GraphQL。
最重要的一条：能用异步的地方就不要用同步。每一条同步调用链都是一条潜在的"级联失败"路径 —— 下游慢了、挂了，上游就被拖死（见模块 7）。
别同时用三种：一个团队内部同时上 REST + gRPC + GraphQL 会导致客户端碎片化、工具链重复、维护成本翻倍。建议：对外 REST（兼容性好），内部 gRPC（性能好），前端聚合才考虑 GraphQL。三者各司其职，不要重叠。
模块 4

REST API 设计规范

REST（Representational State Transfer，表述性状态转移）的核心思想是：用 URL 表示资源，用 HTTP 方法表示操作，用状态码表示结果。下面每一条都配正反例。

1. 资源命名

✓ 正确：名词复数，表示资源集合
GET    /users            查用户列表
GET    /users/123        查单个用户
POST   /users            创建用户
PUT    /users/123        全量更新用户
PATCH  /users/123        部分更新用户
DELETE /users/123        删除用户
GET    /users/123/orders 查某用户的订单（子资源）

✗ 错误：动词进 URL
GET  /getUser?id=123
POST /createUser
POST /deleteUser?id=123      ← 用 DELETE 方法
GET  /users/123/getOrders

✗ 错误：命名风格混乱
/users  /userList  /user_list  /User   ← 大小写、单复数、下划线混用
✓ 统一用小写 + 连字符：/user-groups  /order-items

2. HTTP 方法语义

方法语义幂等说明
GET查询是只读，不该有副作用（不要用 GET 做删除）
POST创建 / 非幂等操作否每次调用都可能产生新资源。需幂等时要额外设计（见模块 5）
PUT全量替换是执行多次结果相同。未提供的字段会被清空
PATCH部分更新否（通常）只更新提供的字段
DELETE删除是删多次结果都是"不存在"

3. 状态码使用（最常被用错）

状态码含义典型误用
200 OK成功，响应体带数据——
201 Created资源创建成功，Location 头带新资源 URL创建成功却返回 200
204 No Content成功但无响应体（如 DELETE 成功）——
400 Bad Request参数校验失败（客户端错）所有错误都返回 400
401 Unauthorized未认证（没登录 / token 无效）与 403 混用
403 Forbidden已认证但无权限与 401 混用
404 Not Found资源不存在——
409 Conflict状态冲突（如重复创建、并发修改）重复创建却返回 400
429 Too Many Requests被限流限流却返回 500
500 Internal Error服务端自己的 bug把参数错误也返回 500
503 Service Unavailable服务不可用（过载 / 维护）——
两个最常见的原则性错误：
① HTTP 状态码全返回 200，把业务错误塞进响应体的 code 字段。这破坏了 HTTP 语义，让网关、监控、客户端无法基于状态码做统一处理（比如限流、重试、告警都依赖状态码）。正确做法：HTTP 状态码表达"协议层结果"，响应体表达"业务层结果"。
② 把服务端 bug（500）和客户端参数错误（400）混为一谈。前者是你的责任，要告警；后者是调用方的责任，不该告警。混在一起会导致告警噪音淹没真问题。

4. 统一错误响应格式

// 建议的错误响应体结构（所有接口统一）
{
  "code": 40001,                        // 业务错误码，全局唯一
  "message": "订单状态不允许取消",        // 给人看的，可直接展示
  "trace_id": "a1b2c3d4-...",           // 链路追踪 ID，排查问题必备
  "details": [                          // 字段级错误明细（可选）
    { "field": "quantity", "issue": "必须大于 0" }
  ]
}

// 配合的 HTTP 状态码
HTTP/1.1 409 Conflict                   // 状态冲突 → 409，不是 200

5. 版本策略

方案示例评价
URL 路径版本/v1/users最常用、最直观，网关易路由。缺点是不符合"URL 表示资源"的纯粹主义
请求头版本Accept: application/vnd.api.v2+jsonURL 干净，但调试不便，容易被缓存忽略
查询参数版本/users?version=2不推荐，污染资源语义
无版本（只做兼容演进）加字段不改字段最理想：只做向后兼容的增量变更，永远不需要新版本
版本策略的正确姿势：优先做兼容演进（只加字段、不改字段含义、不删字段、新增枚举值要兼容）。只有发生破坏性变更（改字段类型、改语义、删字段）时才发新版本。不要每个小改动都发新版本，那会让客户端维护成本爆炸。
破坏性变更前要给旧版本定明确的废弃时间表（如提前 6 个月公告），并在响应头加 Deprecation 和 Sunset 提示。

6. 分页设计

方式参数适用与边界
偏移分页?page=1&size=20简单直观，适合后台管理。深分页性能差（OFFSET 100000 要扫前 10 万行），且数据变动时会漏/重
游标分页?cursor=xxx&size=20推荐用于大数据量 / 信息流。基于"上一页最后一条的排序值"定位，性能恒定，不受数据变动影响
// 分页响应体的标准结构（要包含分页元信息）
{
  "data": [ {...}, {...} ],
  "pagination": {
    "page": 1,
    "size": 20,
    "total": 1357,                  // 总数（游标分页可省略，或返回 has_more）
    "has_more": true,
    "next_cursor": "eyJpZCI6MTIzfQ=="  // 游标分页用
  }
}
分页的边界条件（容易被忽略）：① size 必须有上限（如最大 100），否则 ?size=1000000 一次把库拖垮；② total 字段在超大表上很贵（COUNT 全表），可以用估算或干脆不返回，用 has_more 替代；③ 游标分页的 cursor 要不透明（Base64 编码，别暴露内部字段），防止被构造。
模块 5

幂等设计

幂等（Idempotent）指同一请求执行一次和执行多次，对系统状态的影响相同。在微服务里这几乎是必需的 —— 因为网络超时后客户端会重试，而重试会真的发出第二次请求。

哪些接口必须幂等

必须幂等原因
支付 / 退款重复扣款、重复退款是资金事故，绝对不能发生
创建订单用户网络卡顿会重复点击，或客户端超时重试
扣库存 / 发券重复扣减 / 重复发放会导致数据错误
所有 POST 类写操作凡是非幂等的写操作，在分布式环境下都要考虑重试带来的重复

幂等键（Idempotency Key）的设计

# 客户端生成幂等键，放进请求头（业界标准做法，参考 Stripe）
POST /v1/payments
Idempotency-Key: 7d3f9a2e-4b1c-4f8d-9e2a-1b3c5d7e9f0a
Content-Type: application/json

{ "order_id": "O123", "amount": 10000 }

# 关键点：
✓ 幂等键由客户端生成（服务端生成无法防重，因为重试是新请求）
✓ 同一次业务操作的多次重试，必须用同一个幂等键
✓ 不同业务操作必须用不同的键
✗ 用 UUID 在服务端每次生成 → 每次都不一样 → 完全失效

存储方案对比

方案实现优缺点
幂等表（DB）幂等键加唯一索引，插入冲突即重复强一致、可靠。适合资金类。缺点是有 DB 开销，表会增长
RedisSET key NX EX 86400高性能。缺点：主从切换会丢 key，去重可能失效。适合非关键路径
状态机约束UPDATE ... WHERE status='待支付'零额外存储，最优雅。但只适用于有状态流转的场景
// 幂等表方案（Java 示例）
public PaymentResult pay(String idemKey, PayRequest req) {
    // ① 查是否已处理过，已处理直接返回上次结果
    IdemRecord exist = idemMapper.selectByKey(idemKey);
    if (exist != null) {
        return JSON.parseObject(exist.getResult(), PaymentResult.class);
    }
    // ② 未处理，插入记录（唯一索引防并发）
    try {
        idemMapper.insert(idemKey, null);   // result 先空
    } catch (DuplicateKeyException e) {
        // 并发下另一个线程抢先插入了，短暂等待后返回其结果
        return waitAndGetResult(idemKey);
    }
    // ③ 执行真正的业务
    PaymentResult result = doPay(req);
    // ④ 回填结果（同一事务）
    idemMapper.updateResult(idemKey, JSON.toJSONString(result));
    return result;
}

幂等窗口期（Idempotency Window）

幂等记录不能永久保留（表会无限膨胀）。工程上设一个幂等窗口期（如 24 小时 / 7 天），窗口内的重复请求被拦截，窗口外的不再保证。
窗口期怎么定：要大于"客户端最大重试时长 + 人工排查时间"。支付类建议 7 天以上，普通业务 24 小时足够。但要注意：窗口期外如果真的来了重复请求，业务必须靠"状态机约束"这类天然幂等的机制兜底，不能完全依赖幂等表。
幂等设计的三个层次（从强到弱）：
① 天然幂等：操作本身幂等（PUT、状态机 UPDATE），零成本，优先用；
② 幂等表：强一致，适合资金等关键路径；
③ Redis 去重：高性能但可能漏，适合非关键路径。
真实系统通常是"幂等键 + 状态机 + 兜底对账"三层组合。
模块 6

API 网关职责

API 网关（API Gateway）是所有外部流量的统一入口。它的价值在于"把横切关注点（cross-cutting concerns）从每个服务里抽出来，集中处理"。

网关该做什么

职责说明
路由把 /api/order/* 转发到订单服务。网关的核心职责
鉴权统一校验 token / 签名，把认证后的用户信息（如 user_id）透传给下游，避免每个服务重复实现
限流在入口处限流，保护后端服务（见模块 8 的限流算法）
熔断降级下游服务不可用时，网关直接返回兜底响应，避免请求堆积
日志与追踪统一记录访问日志、生成 trace_id 并透传（链路追踪的起点）
协议转换对外 REST，内部转 gRPC；或做 SSL 终止（HTTPS 在网关解密）
灰度 / 流量染色按 header / 用户 ID 把流量路由到不同版本的服务（见模块 8）

网关不该做什么（边界）

网关里绝对不能写业务逻辑。以下都属于反模式：
① 在网关里做数据聚合 / 编排（如"调 3 个服务拼装响应"）—— 这让网关变成了"业务逻辑层"，每次业务变更都要改网关，网关成为发布瓶颈和单点故障。聚合应该由 BFF（Backend For Frontend，为前端定制的后端聚合层）承担。
② 在网关里直接访问数据库 —— 彻底破坏了分层，网关应该是无状态的纯转发层。
③ 把网关当唯一的鉴权点 —— 内部服务之间绕过网关互相调用时，鉴权就失效了。服务本身也要有校验能力（纵深防御）。
④ 网关做重计算 / 大文件转换 —— 网关是流量入口，CPU 密集操作会拖垮整个入口。
网关选型速记：Nginx / OpenResty（性能最强，Lua 扩展灵活，但配置复杂）；Spring Cloud Gateway（Java 生态，与 Spring Cloud 集成好）；Kong / APISIX（插件生态丰富，开箱即用的限流、鉴权、可观测）；Envoy（服务网格数据面事实标准，适合 Kubernetes）。选型先看团队技术栈和是否需要服务网格，别只看性能。
模块 7

服务间调用的健壮性

这是微服务最容易出事的地方。同步调用链上的每一个环节，都可能成为整条链路的故障源。核心是防"级联失败"（Cascading Failure，一个服务慢/挂导致上游跟着挂）。

超时设置原则

# 核心原则：每一层都必须有超时，且超时时间要"逐层递减"

外层超时 > 内层超时，给内层留出"处理 + 返回"的余量：

  网关超时    3s
    └─ 服务 A 调用服务 B 的超时  1s
         └─ 服务 B 调用服务 C 的超时  500ms
              └─ 服务 C 查数据库的超时  200ms

✗ 致命错误：没有超时
  → 下游卡住时，线程池被耗尽，上游服务自己也挂了
  → 这就是级联失败的起点

✓ 超时值的设定依据
  基于 P99 延迟设置，通常是 P99 的 1.5~2 倍
  例：服务 B 的 P99 是 300ms → 超时设 500ms 左右
"没有超时"是微服务头号杀手。一个没有超时的 HTTP 客户端，在下游挂起时会无限等待，导致调用方线程池被占满，进而调用方也不可用 —— 故障沿调用链向上蔓延，最终整个系统雪崩。
同时要注意：连接超时（connect timeout）和读取超时（read timeout）要分开设置，连接超时通常设得很短（如 1s），读取超时按业务设。

重试策略与退避

# 重试必须满足三个条件，否则比不重试更糟
① 只重试"可重试"的错误：网络超时、5xx、限流(429) 可重试；
   400/401/403/404 这类客户端错误绝不能重试（重试还是错）
② 必须有重试上限：通常 2~3 次，不能无限重试
③ 必须用指数退避 + 抖动：

  第 1 次重试：等 100ms
  第 2 次重试：等 200ms
  第 3 次重试：等 400ms
  再叠加随机抖动（jitter）：等待时间 = 基础值 × (0.5 ~ 1.5 的随机数)

✗ 没有抖动的后果：重试风暴
  1000 个客户端同时失败 → 同时等待 200ms → 同时重试
  → 下游瞬间收到 1000 个并发请求（本来只有一个）
  → 下游再次被打垮 → 又一轮重试 → 雪崩
重试的放大效应（一定要理解）：如果调用链有 3 层，每层都重试 3 次，那么最底层的一个请求可能被放大成 3 × 3 × 3 = 27 次调用。越底层、越接近数据库的服务，越不应该重试（或者重试次数要越少）。
原则：重试应该在调用链的"最上游"统一做，越往下重试次数越少。同时下游服务要能识别"这是重试请求"（比如带一个 retry 标记的 header），避免重复处理。

舱壁隔离（Bulkhead）

舱壁来自船舶设计：把船体分成多个独立舱室，一个舱进水不会沉船。在微服务里指把不同下游的调用资源隔离，避免一个下游的故障拖垮所有调用。

隔离方式实现效果
线程池隔离给每个下游分配独立线程池下游 A 慢时只占满 A 的线程池，不影响调用 B 的线程
信号量隔离限制每个下游的并发数更轻量（无线程切换），但不支持超时中断
连接池隔离每个下游独立连接池防止一个下游占满共享连接池

级联失败与雪崩的完整链条

# 雪崩是怎么发生的（一条完整的因果链）

服务 C（数据库）变慢  →  服务 B 的请求开始超时
  →  B 的线程被卡住，线程池逐渐耗尽
  →  B 无法处理新请求（包括来自 A 的）
  →  A 调用 B 开始超时，A 的线程池也被耗尽
  →  A 无法处理新请求，网关开始大量超时
  →  整个系统不可用，但根因只是 C 变慢了一点

# 打断链条的手段（每一环都要有）
① 超时：让 B 不会无限等 C
② 熔断：C 连续失败时，B 直接快速失败，不再调用 C
③ 舱壁：C 的故障只影响 B 调 C 的那部分资源
④ 降级：C 不可用时，B 返回兜底数据（如缓存、默认值）
⑤ 限流：在入口就限制流量，避免过载
模块 8

服务治理：限流、熔断、降级、灰度

治理的核心目标：在部分组件故障时，保证系统整体仍然可用（而不是全挂）。这是微服务和单体的最大区别 —— 单体挂了就全挂，微服务有机会"局部降级"。

限流算法对比

算法原理优缺点
固定窗口计数每个时间窗口内计数，超过阈值拒绝最简单。缺点：临界点突刺——窗口交界处可能瞬间通过 2 倍流量
滑动窗口把窗口切细，按滑动区间统计平滑了临界问题。实现稍复杂，需存细粒度计数
令牌桶恒定速率往桶里放令牌，请求取令牌，桶满则丢弃允许突发流量（桶里攒的令牌可一次用掉）。最常用
漏桶请求先进桶，以恒定速率流出输出绝对平滑，但不容忍突发（多余请求排队或丢弃）
# 令牌桶 vs 漏桶，一句话区分
令牌桶：允许突发（平时攒着，忙时一起用）→ 适合"允许偶尔突发"的 API
漏桶：  强制匀速（不管来多少，都匀速放行）→ 适合"必须保护下游"的场景

local now = tonumber(ARGV[1])                       -- 当前时间
local rate = tonumber(ARGV[2])                      -- 每秒补充速率

熔断器状态机（Circuit Breaker）

熔断器像一个"自动开关"：下游连续失败到一定比例就"跳闸"，快速失败，避免资源被耗尽；过一段时间"半开"试探，恢复则"闭合"。

状态行为转换条件
CLOSED
闭合		正常放行请求，统计失败率失败率超过阈值（如 50%）→ 转 OPEN
OPEN
打开		直接快速失败，不调用下游等待一段时间（如 30s）→ 转 HALF_OPEN
HALF_OPEN
半开		放行少量试探请求试探成功 → 转 CLOSED；失败 → 回到 OPEN
熔断器参数建议（可直接用）：统计窗口 10 秒；最小请求数 20（低于这个数不熔断，避免样本太少误判）；失败率阈值 50%；OPEN 状态持续 30 秒；HALF_OPEN 放行 5 个试探请求。
关键：熔断必须配合降级 —— 熔断只是"不调用下游"，但上游总得返回点什么，否则用户看到的就是报错。降级就是"返回兜底数据"。

降级的层次

第一层：返回缓存数据。下游挂了，返回上次缓存的结果（可能有点旧，但用户能用）。代价最小，效果最好。
第二层：返回默认值 / 兜底数据。如推荐服务挂了，返回热门榜单；商品评价服务挂了，不展示评价区。
第三层：关闭非核心功能。大促时关掉"猜你喜欢""最近浏览"，把资源让给下单主流程（功能降级）。
第四层：整体降级 / 限流。实在扛不住时，入口直接限流，返回"系统繁忙，请稍后再试"，保住核心链路的可用性。

灰度发布与流量染色

# 流量染色（Traffic Coloring）：给流量打标记，按标记路由

方式一：Header 染色
  用户请求带 X-Gray: true → 网关路由到 v2 版本服务
  适合：内部测试、白名单用户

方式二：用户 ID 取模
  hash(user_id) % 100 < 5  → 5% 的用户走新版本
  适合：按比例灰度

方式三：全链路染色（推荐）
  入口打标 → 标记随调用链透传（放请求头 / 上下文）
  → 链路中所有服务都按同一个标记路由到对应的灰度版本
  # 关键：标记必须透传，否则 A 走新版本、B 走老版本，可能不兼容
灰度的三个坑：① 流量标记没有全链路透传 —— 入口路由到新版，但内部调用丢了标记，导致新旧版本混跑、数据不一致；② 灰度环境共用生产数据库 —— 新版本的 schema 变更会直接破坏老版本；③ 没有快速回滚能力 —— 灰度出问题时不能立刻把流量切回。灰度发布前必须确认这三点。
常见坑

十个反模式

1
分布式单体（Distributed Monolith）
拆成了多个服务，但服务之间强耦合：共享数据库、必须同步发布、一次请求跨七八次调用。这是最糟的形态 —— 承担了分布式的全部代价，却没得到任何好处。判断标准：改一个功能要不要改多个服务。
2
同步调用链过长
一次用户请求串行调用 5 个服务，延迟叠加、故障点叠加。可并行化的调用要并行（如用 CompletableFuture），可异步化的要改成 MQ。链路越长，可用性越差（0.99^5 ≈ 0.95）。
3
没有设置超时
下游卡住时调用方线程被无限占用，线程池耗尽，故障沿调用链向上蔓延形成雪崩。每一层都必须设超时，且超时时间逐层递减。
4
重试没有退避和抖动
失败后立刻重试，且所有客户端同时重试，会把下游瞬间打垮（重试风暴）。必须用指数退避 + 随机抖动，并设重试上限（2~3 次）。
5
多个服务共享同一个数据库
共享数据库意味着共享 schema，一个服务改表会影响其他服务，无法独立演进 —— 这是分布式单体的第一特征。每个服务应该有自己的数据存储。
6
接口没有版本管理
直接改接口字段，导致老客户端全部失败。要么做向后兼容的增量演进，要么用 URL 版本（/v1/）并给旧版本明确废弃时间表。
7
错误码不统一 / 状态码乱用
所有错误都返回 200 把错误塞进 code；或 401 和 403 混用；或参数错误返回 500。这会让网关、监控、客户端无法统一处理。HTTP 状态码表达协议层结果，响应体表达业务结果。
8
把网关当业务逻辑层
在网关里做数据聚合、编排、访问数据库。这会让网关变成发布瓶颈和单点故障。网关应该只做路由、鉴权、限流、日志等横切关注点。
9
写接口没有幂等设计
客户端超时重试导致重复下单、重复扣款。所有非幂等的写接口都必须设计幂等键，关键业务用幂等表（唯一索引）。
10
先拆服务，后补可观测性
没有日志聚合、链路追踪、指标监控就上微服务，出问题时无法定位是哪个服务的问题，排查时间从分钟变成小时。可观测性要和服务拆分同步建设，不能事后补。
自测

六道题

1. 关于"什么时候该拆微服务"，下列说法正确的是？
正确答案：模块化单体优先。微服务是用分布式复杂度换独立演进能力。团队小、边界模糊、缺运维能力时拆，只会纯亏。拆分前应先把单体做成"模块化单体"（模块间只通过接口通信）。
2. 下列哪种拆分维度是典型的错误做法？
正确答案：按技术分层拆。这会把内聚的业务逻辑拆散，导致一个需求要改三个服务、跨三次调用 —— 典型的分布式单体。正确做法是按业务能力或限界上下文拆，每个服务内聚自己的全栈逻辑。
3. 关于服务间调用的超时设置，正确的是？
正确答案：每层都设超时且逐层递减。没有超时是微服务头号杀手，会导致线程池耗尽、级联失败。超时值应基于 P99 延迟设定（约 P99 的 1.5~2 倍），设太短会导致正常请求被误杀。
4. 熔断器的三种状态转换顺序是？
正确答案：CLOSED → OPEN → HALF_OPEN。CLOSED 正常放行并统计失败率；失败率超阈值转 OPEN（快速失败）；等待一段时间转 HALF_OPEN 放行少量试探请求；成功则回 CLOSED，失败则回 OPEN。
5. 关于幂等键（Idempotency Key）的设计，正确的是？
正确答案：客户端生成，同一次操作的重试复用同一个键。服务端每次生成的话，重试就是新请求、无法防重；时间戳无法区分"重试"和"新请求"。幂等键通常放在请求头 Idempotency-Key 里。
6. 关于 API 网关的职责，下列哪一项是反模式？
正确答案：在网关做业务逻辑和访问数据库。这会让网关变成业务逻辑层和发布瓶颈，成为单点故障。网关只应处理横切关注点（路由、鉴权、限流、熔断、日志、协议转换），数据聚合应由 BFF 承担。
