开始前

遗留系统的真实困境

遗留系统（Legacy System）不是"老的技术栈"，而是"改不动又不敢弃"的系统。它的困境从来不只是技术问题。

困境典型表现真实后果
文档缺失注释是 5 年前某离职同事的名字；PRD 和代码对不上；数据库表含义靠口口相传任何改动都是考古。新人上手 3 个月才敢提第一个 MR
技术债累积单类 8,000 行、方法 500 行、没有测试；循环依赖成网；同一个逻辑复制了 20 份改一处炸三处，发布靠祈祷，回归测试成本指数上升
不敢动"它能跑就别动"；唯一懂的人不敢休年假；发布要三个人盯着需求响应越来越慢，业务方失去耐心，形成恶性循环
耦合深订单、库存、会员、优惠券全在一个库里 join；报表直接查业务库无法拆服务，无法扩容单点，大促时全链路绑在一起死
数据脏外键缺失、状态机不闭合、历史脏数据几千万行迁移时才发现"文档里的字段实际有一半是空的"
改造前必须回答的三个问题：① 为什么改？——"技术栈老"不是理由，"大促扛不住、需求交付周期从 2 周变 2 个月"才是。② 改到什么程度？——拆微服务？换数据库？还是先补测试和文档？③ 谁买单？——改造占用 30%~50% 研发资源，没有业务方支持，半年后就会因"没产出业务需求"被砍。

遗留系统的量化画像（改造前先做这个）

# 用数字说话，而不是"这系统很烂"
代码规模：      42 万行 Java，最大单文件 6,800 行，最大方法 780 行
测试覆盖：      行覆盖 8%，核心链路 0 单测
依赖关系：      循环依赖 17 处，与 9 个外部系统直连（其中 3 个已无文档）
数据库：        1 个 MySQL 800GB，380 张表，最大表 4.2 亿行
发布频率：      双周发布，每次回归 5 人日
故障记录：      近一年 P2 以上 6 次，其中 4 次与该系统相关
需求交付周期：  从评审到上线平均 34 天（同类新系统 8 天）
# 这组数字才是立项材料：交付周期 4 倍 + 故障占比 67% → 改造投入产出比清晰可见
模块 1

四种改造策略

策略选择取决于系统还在不在生长、业务能不能停、团队有多少资源。选错策略比不改造更糟。

绞杀者模式（Strangler Fig Pattern）

名字来自绞杀榕：新功能长在新系统里，老系统被逐渐"包裹"直至枯萎。核心：在老系统外面加一个 Facade 层（网关/代理），按领域把流量一块块切到新服务，切一块老系统少一块。适合老系统仍在持续迭代的场景。

# 绞杀者模式的流量切换演进
阶段 0：老系统单体承载 100% 流量
  [用户] → [老系统]

阶段 1：引入 Facade，按 URI 路由分流
  [用户] → [Facade 路由层]
              ├─ /order/**    → [新订单服务]    5% 流量（灰度）
              └─ 其他          → [老系统]       95%

阶段 2：订单域全量切换，开始绞杀会员域
  [Facade] ├─ /order/**  → [新订单服务]  100%
  [Facade] └─ /user/**   → [新会员服务]  10%（灰度中）
  [Facade] └─ 其他        → [老系统]

阶段 3：老系统只剩历史查询（只读），停止写入
阶段 4：老系统下线，Facade 退化为普通网关
绞杀者模式的三个工程要点：① Facade 必须是薄的——只做路由、协议转换、灰度，不放业务逻辑，否则它自己变成新的遗留系统；② 每次只切一个领域，切完观察一个完整业务周期（至少含一次结算/对账）再切下一个；③ 老系统要能继续改——没切走的部分还要支撑业务需求，不能冻结。

修缮者模式（Refactoring / Boy Scout Rule）

不推倒重来，在老系统内部持续小步重构："让代码比你来时更干净一点"。适合系统还要活很久、但整体健康、只是局部腐烂的场景。

  • 手法：先补测试（ characterization test 表征测试：先锁住当前行为，哪怕行为是错的）→ 小步提取方法/类 → 每次重构不超过 50 行 → 与业务需求同行（改哪补哪）
  • 节奏：每个迭代固定 20% 容量做重构，5 人日改一个 500 行方法，一年下来系统质变
  • 适用判断：系统 10 万行以内、团队能 hold 住、没有拆服务的硬需求

抽象分支（Branch by Abstraction）

在代码里引入一个抽象层（接口），让老实现和新实现并存，通过开关切换：

// 第一步：把对老 ORM 的直接依赖收敛到一个接口后面
public interface UserRepository {
    User findById(Long id);
    void save(User user);
}

// 第二步：两个实现并存，新实现对接新服务
public class LegacyUserRepository implements UserRepository { /* 直连老库 */ }
public class RemoteUserRepository implements UserRepository { /* 调新会员服务 */ }

// 第三步：开关切换，可灰度、可秒回滚
@Configuration
public class RepoConfig {
    @Bean public UserRepository userRepository(
            @Value("${user.repo.mode:legacy}") String mode,
            LegacyUserRepository legacy, RemoteUserRepository remote) {
        return "remote".equals(mode) ? remote : legacy;
    }
}

与绞杀者的区别：绞杀者在流量入口分流（进程外），抽象分支在代码内部切换（进程内）。抽象分支适合"模块级替换"（换 ORM、换存储、换算法），不适合拆服务。

事件拦截（Event Interception / Change Data Capture）

不改老系统的写入路径，通过拦截数据库变更事件（binlog / CDC）驱动新系统演进。适合"老系统改不动，但又必须让它参与新架构"的场景：

方式做法适用
binlog 订阅（CDC）Canal / Debezium / Flink CDC 订阅 MySQL binlog，异步同步到新库/新服务数据迁移、缓存刷新、异构同步
消息拦截在老系统的 MQ 消费端旁挂一个消费者，复制流量给新系统老系统已用 MQ 解耦的场景
API 拦截Facade 层复制读请求给新系统做"影子验证"新系统正确性验证期
策略改造粒度业务中断适用场景
绞杀者领域/服务级无（灰度切换）持续迭代的大系统拆服务
修缮者方法/类级无系统还能活，局部腐烂
抽象分支模块级无（开关回滚）换存储/换框架/换依赖
事件拦截数据级无老系统写入路径不可动
模块 2

数据迁移与双写对账

系统改造，数据是最后一关也是最大的一关。代码可以灰度回滚，数据错乱可能无法挽回。

迁移三阶段（每阶段都有退出条件）

① 双写期（1~4 周）：老库照常服务，新库并行写入。新库不对外提供读，只验证写入正确性。此时老库是唯一真相源。
② 校验期（1~2 周）：全量对账 + 增量对账，差异率达标（如 < 0.001%）后，开放少量灰度读（5% 流量读新库，读失败自动降级读老库）。
③ 切换期（灰度放量）：读流量 5% → 50% → 100% 切到新库，老库转为只读备份，保留至少一个完整业务周期（如含月结）后再下线。

双写的三种实现与陷阱

方式做法主要问题
应用双写业务代码里同时写老库和新库侵入业务；两个写不原子（老库成功新库失败怎么办）；回滚要清理双写代码
CDC 双写订阅老库 binlog，异步写入新库延迟（秒级）；binlog 不包含业务语义（需要回表补字段）；大事务/DDL 是难点
异构双写（推荐）老库 → binlog → MQ → 新库，消费者幂等写入架构复杂度；需要保证顺序和幂等
# 对账系统的三个层次（都要做）
# 1. 全量对账：迁移完成后跑一遍，逐表比对新老库
#    SELECT COUNT(*), SUM(amount), MAX(updated_at) FROM order  -- 两边结果必须一致
# 2. 增量对账：双写期间持续跑，比对最近 N 分钟变更的记录
#    按 updated_at 取增量，逐字段 diff，差异写差异表告警
# 3. 业务对账：用业务指标验证
#    老库订单总额 = 新库订单总额（财务口径）；昨天日切报表两边一致

# 对账差异的经典来源（排查清单）
# a. 时区/时间精度：老库 DATETIME 秒级 vs 新库 TIMESTAMP 毫秒
# b. 字符集：utf8 vs utf8mb4，emoji 和生僻字在新库截断
# c. 精度：老库 DECIMAL(10,2) vs 新库 DECIMAL(19,4)，金额字段类型不同
# d. 状态映射：老库状态码 0/1/2 的语义与新枚举不对应
# e. 并发乱序：CDC 异步到达顺序与提交顺序不一致，后写的旧值覆盖新值
#    → 解法：带版本号/时间戳的条件更新（UPDATE ... WHERE version < 新version）
双写期最大的坑：回滚不干净。双写跑了三周发现问题要回滚，老库是真相源没问题，但新库已经产生了对外的影响（新库的 ID 被下游记了、新库触发过消息）。对策：① 双写期新库绝对不发出游消息、不生成对外可见的 ID；② 新库表加"环境标记"字段，出问题能一键标记数据无效；③ 回滚预案在双写上线前就写好并演练。
模块 3

渐进式替换的节奏控制

改造失败的常见原因不是技术，是节奏：要么太急（三个月拆完然后爆炸），要么太慢（拆了两个服务后热情耗尽）。

阶段时间目标退出标准
试点期1~2 个月选一个"痛但小"的领域（如消息通知）验证全链路打法新服务稳定运行一个完整业务周期，团队跑通"灰度-监控-回滚"闭环
加速期3~6 个月按"痛点 × 耦合度"排序逐个绞杀，每 2~4 周切一个领域核心域全部切换，老系统写入量 < 20%
收尾期2~3 个月老系统只读化、数据归档、下线，Facade 退化老系统停机，运维成本账单下降

领域切分排序矩阵（先切谁）

领域类型优先级理由
边缘 + 低耦合
（通知、日志、报表）		P0 最高试错成本低，适合建立信心和基建（监控、灰度、对账工具）
边缘 + 高耦合
（优惠券计算）		P1业务价值有限但技术风险高，放第二批
核心 + 低耦合
（商品详情）		P1价值高风险可控，第二批次主力
核心 + 高耦合
（订单、支付）		P2 最后数据一致性要求最高，必须等基建和团队成熟，一次只动一个
# 每轮切换的标准动作 checklist（切任何域都走这个）
□ 1. 领域边界确认：与业务方对齐"这个域包含哪些功能、不包含哪些"
□ 2. 数据影响评估：涉及哪些表、是否双写、对账方案是什么
□ 3. 新服务开发 + 表征测试（老系统行为先锁住）
□ 4. 影子流量验证：线上流量复制到新服务比对响应（不对外）
□ 5. 灰度方案：5% → 25% → 50% → 100%，每档观察 ≥ 1 个业务日
□ 6. 监控就绪：QPS/RT/错误率/业务指标（如订单创建成功率）双轨对比
□ 7. 回滚预案：Facade 一键切回老系统，回滚演练过一次
□ 8. 老系统代码清理：下掉该域的废弃代码和定时任务
□ 9. 复盘文档：本轮发现的问题、耗时、对下轮的改进
节奏失控的三个信号：① 一个域切了两个月还没完（边界没划清，需求在膨胀——砍范围）；② 连续两个域回滚（基建不成熟——停下来补基建，别硬冲）；③ 老系统还在接大量新需求（没和业务方谈好"新需求只进新系统"——先谈规则再动手）。
模块 4

组织与沟通：如何获得业务方支持

技术改造最大的资源不是技术，是业务方的耐心和老板的信任。不会汇报的架构改造，技术再对也会被砍。

把技术语言翻译成业务语言

技术说法（别说）业务说法（这么说）
"我们要做微服务拆分，治理技术债""大促扩容从 3 天缩短到 3 小时；新需求交付从 34 天降到 2 周"
"数据库需要分库分表""支撑明年 10 倍订单量不重构；订单查询从 3 秒回到 200 毫秒"
"老系统要重构，需要 3 个月不接新需求""先试点通知域 6 周，期间业务正常；之后每批 2 周，只影响 20% 研发资源"

争取支持的四步

① 用故障和交付数据立项：展示遗留系统的量化画像（模块 0 那张表）：故障占比、交付周期、大促风险。数据比"技术很烂"有说服力 10 倍。
② 给业务方"不改造的代价"和"改造的路径"：明确说清楚不改会怎样（明年大促有 60% 概率扛不住）、改造分几批、每批影响什么。让业务方做选择题，不是问答题。
③ 早期胜利（Quick Win）：第一个试点必须选业务可感知的（如订单查询从 3 秒到 200ms，或一个长期难上的需求因为改造 suddenly 变容易）。一次可见的胜利换来后面三批的信任。
④ 制度化保障：约定"新需求只进新系统"（防止老系统继续长大）、每双周同步进度、每批结束请业务方参与验收。让业务方有参与感，而不是被通知。
内部沟通的三个关键角色：① Sponsor（发起人）：通常是技术 VP 或业务负责人，负责要资源和挡"为什么还不交付业务需求"的质疑；② 领域专家：老系统最懂的人（哪怕要离职也先把知识挖出来，访谈 + 录像 + 补文档）；③ 翻译者：架构师里最会汇报的那个，负责把进度翻译成业务方和老板关心的语言。
模块 5

反模式：大爆炸重写为何大多失败

Joel Spolsky 2000 年的《Things You Should Never Do》是这篇的圣经：Netscape 重写代码库是它衰败的开始。二十多年过去，这个规律几乎没变。

大爆炸重写的死法清单

阶段会发生什么
第 1~3 个月团队士气高涨，架构图画得漂亮，业务方期待"全新的系统"
第 4~6 个月发现老系统里有 30% 的"隐藏需求"没人记得为什么存在（某个 2019 年为大客户加的 hack），逐个考古
第 7~9 个月业务方等不及了：旺季来了、大客户要签约，新系统还不能上，老系统也得继续改——两条战线并行
第 10~12 个月新系统终于"完成"，切流量的当天发现数据对不上、性能差 10 倍、三个业务方 workflows 走不通
结局回滚老系统，或者带着伤上新系统，团队疲惫不堪。平均结局：两年后老系统还在，新系统成了第二个遗留系统。
# 大爆炸重写的数学：为什么总是超时
老系统 42 万行代码，沉淀 8 年
团队判断："重写只需要 6 个月，我们写新代码比读老代码快"
实际：
  - 老系统里 8 年积累的隐藏业务规则 ≈ 3 万行等价逻辑，没人能完整讲出来
  - 新系统从零搭建同样功能，纯开发 6 个月 + 补齐隐藏需求 4 个月 + 联调对账 2 个月 = 12 个月
  - 这期间老系统还在接需求（两条线并行，效率再降 30%）→ 实际 16~18 个月
  - 切换期风险不可估（数据、性能、回滚）
# 结论：大爆炸 = 用一个确定的大风险，替换一堆确定的小风险。绞杀者 = 持续交付价值 + 风险均摊。
唯一允许"重写"的条件（同时满足）：① 系统即将下线或业务即将关停并转（比如产品线要换方向）；② 有完整的、最新的文档和测试（说明系统是被维护的，只是技术栈要换）；③ 切换可以灰度且可回滚。三条缺一条，就走绞杀者。历史上成功的"重写"（如某些换语言场景）本质上都是分模块灰度切换的绞杀者。
模块 6

案例剖析：电商单体拆分与核心系统换库

案例 A：电商单体 → 领域服务（18 个月绞杀）

阶段动作结果关键决策
M1-M2 试点切"消息通知"域（短信/推送），搭 Facade + 灰度 + 监控基建通知故障率降 80%选最小最独立的域建立信心
M3-M8 加速依次切：商品详情 → 购物车 → 会员 → 营销老系统流量降到 45%每域 4~6 周，每批结束清理老代码
M9-M14 攻坚切订单 + 库存：双写 4 周 + 对账 2 周 + 灰度 6 周单量大促 3 倍无故障核心域单开专项，DBA + 业务方驻场
M15-M18 收尾老系统只读化 → 数据归档 → 停机研发成本降 35%老系统保留只读 3 个月才彻底下线

可复用的经验：① Facade 路由层第一天就建好，所有切换走同一条流水线；② 每批都做"影子验证"——灰度前把线上真实流量复制给新服务比对响应差异；③ 大促前 3 个月冻结核心域切换，避免"改造 + 大促"双风险叠加。

案例 B：核心账务系统换库（MySQL → 分布式数据库）

# 背景：单库 800GB 撑不住，要换成分布式数据库，但这是账务系统，错一分钱都是事故
# 策略：抽象分支 + CDC 双写 + 长周期对账，绝不用大爆炸

# 时间线：
W1-W4    抽象分支：所有数据访问收敛到 Repository 接口，老实现保留
W5-W8    新库建库 + 历史数据全量迁移（停机窗口 4 小时 + 迁移中增量追平）
W9-W14   双写期：新库写入但不对外；对账系统跑起来
         - 全量对账：逐表 diff，发现 3 类问题（时区、金额精度、状态映射）→ 修复
         - 增量对账：每 5 分钟比对，差异率从 0.3% 降到 0.0002%
W15-W16  影子读：线上读流量复制到新库，比对结果（不影响对外）
W17-W22  灰度读：1% → 10% → 50% 读流量切新库，读失败自动降级老库
W23-W24  写流量灰度：同样的阶梯，写切换前做三次全量对账
W25+     老库转只读备份，保留 2 个完整月结周期后下线

# 关键数字：
# 对账峰值发现差异：单日 4,300 条（时区问题），修复后稳定在 5 条/天以下
# 灰度期间发生 2 次读降级回切，均因新库慢查询，用户无感知
# 全程零资金差错、零长时间停机（最长 12 分钟只读窗口）
换库案例的三条铁律：① 读可以先切、写必须最后切——读错了能发现，写错了难挽回；② 对账先行——对账系统比迁移脚本更重要，没有对账的迁移是盲飞；③ 降级开关常驻——切换后至少保留 3 个月"一键切回老库"的能力，月结这类关键节点前做一次完整演练。
模块 7

十个线上坑

1
立项理由是"技术栈老了"，不是业务痛点
老板问"所以呢？能多赚钱还是少故障？"就答不上来。立项必须带量化数据：交付周期、故障占比、大促风险、扩容成本。
2
大爆炸重写，想三个月推倒重来
老系统 8 年的隐藏业务规则没人能完整讲出来，重写中持续考古，两条战线并行，平均 16~18 个月才勉强切换，还回滚过。绞杀者 + 灰度是唯一稳妥路。
3
没先补测试就重构，改哪炸哪
没有表征测试（characterization test）锁住当前行为，重构等于蒙眼拆炸弹。哪怕行为是错的，也先测试锁住，再小步改。
4
双写不做对账，切流量的当天才发现数据不一致
时区、金额精度、字符集、状态映射，每一类都能产生几千条差异。对账系统必须先于切换就绪，差异率达标才放量。
5
双写期新库就对外发消息/生成 ID，回滚时污染已发生
新库在双写期必须"哑巴"：不发出游消息、不生成对外可见标识。回滚预案上线前写好并演练一次。
6
Facade 层里塞业务逻辑，自己变成新遗留系统
路由层只做路由/协议转换/灰度。业务逻辑进 Facade = 两年后又要改造 Facade。发现 Facade 超过 2,000 行就是危险信号。
7
老系统被冻结，新需求全憋着等新系统
业务方等不起。正确规则：老系统继续接需求（但不扩大地盘），新需求一律进新系统。切走一个域就冻结一个域。
8
核心域和大促撞车，改造 + 大促双风险叠加
切换期遇大促 = 事故概率指数上升。大促前 2~3 个月冻结核心域切换，改造让位于保障，节后继续。
9
老系统知识只在几个老人脑子里，没提前挖
唯一懂订单优惠叠加规则的人休产假，改造停摆。访谈 + 录像 + 补文档必须第一个月就做，别等"有空"。
10
灰度不可回滚，"切过去就不能切回来"
Facade 没有一键回滚开关，出问题只能现场改代码。每一批切换前，回滚演练必须真实执行过一次，确认 5 分钟内能全量切回。
自测

六道题

1. 关于绞杀者模式，下列说法正确的是？
正确答案：Facade + 按域灰度切流。绞杀者模式名字来自绞杀榕：新系统逐渐包裹老系统，切一个域老系统少一块，全程业务无感、可回滚。"内部小步重构"是修缮者模式。
2. 老系统要换存储引擎（如换 ORM、换数据库），代码内模块级替换、要可灰度可回滚，最合适？
正确答案：抽象分支。进程内引入抽象层让新旧实现并存，通过配置开关灰度、秒级回滚，适合模块级替换。绞杀者是进程外流量分流，CDC 不改写入路径适合数据同步。
3. 数据迁移双写期，新库最应该遵守的纪律是？
正确答案：新库保持"哑巴"状态。双写期老库是唯一真相源，新库一旦产生对外影响（消息、ID），回滚就污染已发生。写失败必须进重试/告警，不能静默跳过。
4. 大爆炸重写失败的首要原因是什么？
正确答案：隐藏业务规则 + 双线并行。8 年的系统里有大量"没人记得为什么但不敢删"的逻辑；同时老系统还在接需求，重写平均 16~18 个月且切换风险不可控。绞杀者把大风险摊成小风险。
5. 遗留系统改造要获得业务方支持，最有效的做法是？
正确答案：量化痛点 + 快速可见的胜利。技术语言（"治理技术债"）打动不了业务方；交付周期从 34 天降到 2 周才行。第一个试点要选业务方能感知的效果，一次胜利换三批信任。
6. 核心账务系统换库，切换顺序应该怎么排？
正确答案：先读后写。读切错能通过对账发现、影响可控；写切错可能造成资金差错、难以挽回。写切换前要做多次全量对账，切换后保留一键回切能力至少一个完整月结周期。

□ 监控双轨对比就绪
□ 回滚演练真实执行过一次
□ 老系统该域代码清理

# 收尾期
□ 老系统只读化，只读保留 ≥ 1 个完整业务周期
□ 数据归档方案执行
□ 停机窗口 + 应急预案
□ 成本对比报告：改造前后研发/运维成本
