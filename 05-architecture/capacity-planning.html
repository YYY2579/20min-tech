二十分钟学透容量规划与性能基线

容量规划不是"买几台机器"，是一套可计算、可验证、可复盘的工程方法。这篇讲峰值系数怎么取、单机容量怎么压出来、扩容怎么决策，以及为什么"只看 CPU"一定会出事。

开始前

容量规划到底规划什么

容量规划（Capacity Planning）回答三个问题：业务到多少量时系统会挂？挂之前多久能加上资源？加资源要花多少钱？三个都答不上来，就是在裸奔。

单机容量
一台机器在 SLA（如 P99 < 200ms）约束下能扛的最大流量。这是所有规划的原子单位，必须压出来，不能估。
水位
当前用量 / 容量的比率。健康水位通常 40%~60%，超过 70% 就该预警，超过 80% 就该动手。
冗余度
为容灾预留的余量。N+1 是底线（挂一台还能扛），核心链路 N+2。大促期间按峰值容量规划，日常按均值。
峰值系数
峰值流量 / 平均流量。电商常见 3~5 倍，秒杀场景 50 倍以上。按平均值买机器，大促一定挂。
核心公式（后面反复用）：
所需机器数 = ceil( 预估峰值QPS × 峰值系数 ÷ (单机安全QPS × 可用率) )
其中 单机安全QPS = 压测极限QPS × 0.7，可用率 = 健康节点数 ÷ 总节点数（考虑发布、灰度、故障占位）。
模块 1

容量规划方法论：六步法

这套流程的价值在于每一步都有数字产出，评审时能拿数字说话，而不是"我觉得够了"。

① 明确业务指标：未来 3~6 个月的流量目标（QPS、DAU、订单量），由业务方给出，写进容量规划文档。没有业务承诺的容量规划是猜谜。
② 采集历史基线：从监控系统导出过去 90 天的 QPS、CPU、内存、RT、错误率，算出日均、峰值、峰值系数、同比/环比增长率。
③ 压测单机容量：在生产等配环境做单机压测，找到 P99 RT 突破 SLA 的拐点（饱和点），记录该点的 CPU、内存、IO、连接数。这一步是整个方法的地基。
④ 计算需求：用核心公式算出目标机器数，对比现有容量得出缺口，输出采购/扩缩容清单。
⑤ 制定扩容预案：明确"什么指标触发扩容、谁来执行、多久能生效"。弹性伸缩的从触发到就绪通常要 3~10 分钟，预案必须跑在故障前面。
⑥ 复盘校准：每次大促后对比预估 vs 实际，误差超过 30% 就要修正模型。容量模型是迭代出来的，不是一次算对的。

# 日常容量计算
所需节点 = ceil(12000 / (980 × 0.85)) = ceil(12000 / 833) = ceil(14.4) = 15 台
现有 8 台 → 缺口 7 台

# 大促容量计算（按大促峰值 + 冗余度 N+2）
大促节点 = ceil(20000 / (980 × 0.85)) = ceil(24.0) = 25 台
叠加 N+2 冗余 → 27 台

所需节点 = ceil(12000 / (1400 × 0.5 × 0.85)) = ceil(20.2) = 21 台

安全系数 0.7 不是魔法数字：它覆盖了压测环境与生产的差异（数据量、缓存命中率、网络拓扑）、机器性能抖动（5%~10%）、以及监控告警的响应时间。核心支付链路建议 0.6，读多写少的展示链路可以到 0.75。系数本身要写进文档并说明依据。
模块 2

性能基线：压测与历史外推

容量规划的地基是单机容量数字，这个数字只能从压测来。历史外推只能告诉你"涨多快"，不能告诉你"上限在哪"。

三种压测的定位

类型环境回答的问题局限
基准压测独立压测环境，生产等配单机极限 QPS、饱和拐点数据量、缓存命中率与生产有差距
全链路压测生产环境，流量打标隔离真实容量、瓶颈链路、容量规划验证成本高，需要压测平台和隔离方案
线上引流生产，复制真实请求回放验证真实流量模型下的表现有风险，只读接口可做，写接口需隔离

单机压测标准流程（以 JMeter 为例）

# 1. 准备：生产等配机器（同规格 ECS/容器、同 JVM 参数、同数据量级）
# 2. 梯度加压：每档持续 5 分钟，记录指标
线程数 50  → 100 → 200 → 400 → 800 → 1600
# 3. 每档记录：QPS、P50/P99/P999 RT、错误率、CPU、内存、GC 次数、DB 连接数

# 4. 判定饱和点：满足以下任一条即认为到达极限
#    a. P99 RT 超过 SLA（如 200ms）
#    b. 错误率超过 0.1%
#    c. CPU 持续 > 80% 且 QPS 不再增长
#    d. GC 时间占比 > 10% 或发生 Full GC

# JMeter 命令行（非 GUI，压测机单独部署）
jmeter -n -t plan.jmx -l result.jtl -e -o report/ -Jthreads=400 -Jduration=300

历史数据外推法

# 外推模型：容量需求 = 当前容量 × (1 + 月环比增长率)^月数
# 例：当前 8 台，月环比增长 15%，6 个月后
8 × (1.15)^6 = 8 × 2.313 = 18.5 → 19 台

# 注意三个修正：
# 1. 增长率要剔除外推窗口内已知的大促（大促是一次性的，不改变趋势线）
# 2. 摩尔定律式优化：单机性能提升（JVM 调优、索引优化）会让模型右移
# 3. 季节性：教育类 9 月涨、电商类 11 月涨，外推要按日历对齐，不能简单按月
压测环境与生产的差异是最大的坑：压测环境通常数据量小（生产几个亿的行，压测库几万行，索引全走内存，快得虚假）、缓存全命中（没有真实热点分布）、网络多一跳。对策：① 压测库脱敏后恢复生产等量数据；② 压测前先冷缓存再测；③ 核心结论必须用一次全链路压测在生产验证。

模块 3

扩容决策：水平 vs 垂直，提前 vs 弹性

方式做法优势代价与适用
水平扩容 Scale Out加机器/加实例，负载均衡分摊理论无上限，成本线性，故障域隔离需要应用无状态化、共享存储、服务发现。首选
垂直扩容 Scale Up升配：4C8G → 8C16G零改造，对有状态服务（DB、Redis）几乎是唯一选择有物理上限；升配要重启；单点风险变大；大规格单价更贵
提前扩容按规划提前买/开资源大促容量确定，不依赖弹性速度占用资金，容量利用率低
弹性伸缩ASG / HPA / KEDA 按指标自动加减成本优，应对不可预见流量扩容有时延（3~10 分钟），应对不了秒级突发

扩容触发决策树

Q: 流量增长是渐进的还是突发的？
├─ 渐进（日环比 < 10%）
│   └─ 弹性伸缩即可，配合月度规划批量调整
├─ 可预见突发（大促、活动，提前知道时间）
│   └─ 提前扩容 + 压测验证 + 活动后缩容（提前 2~4 周采购）
└─ 不可预见突发（被刷、爆款、热点）
    └─ 三层防御：
        ① 限流（立即生效，牺牲部分请求保系统）
        ② 弹性伸缩（3~10 分钟生效，追渐进部分）
        ③ 降级（关非核心功能，给核心让资源）

Kubernetes HPA 配置示例

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 6       # 下限 = N+2 冗余，任何时候不少于 6 个
  maxReplicas: 60      # 上限要匹配下游容量（DB 连接池！）
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60   # CPU 60% 就扩，不是 90% 才动
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 600  # 缩容观察 10 分钟，防抖动
HPA 按 CPU 扩容易滞后：CPU 从 60% 涨到 90% 只要几十秒，Pod 从调度到 ready 却要 30 秒以上，等新 Pod 就绪系统可能已经过载。并发连接数、QPS、队列长度是更领先的指标（KEDA 支持自定义指标）。另外 maxReplicas 一定要匹配数据库连接池上限，否则扩容越多，DB 先挂。

扩容前的检查清单

# 每次扩容/升配前过一遍（任何一条不过就停下来）
□ 1. 瓶颈确认：是 CPU、内存、IO 还是连接数？只扩不相关的维度等于浪费
□ 2. 下游容量：DB 连接数、Redis 带宽、下游服务容量是否也够？瓶颈可能在下游
□ 3. 扩容上限：节点数 × 单节点连接池 ≤ DB max_connections × 0.7
□ 4. 单机安全 QPS 是否有压测依据？没有就先补压测再谈数量
□ 5. 发布影响：新节点纳入发布批次需要多久？滚动发布期间容量是否够
□ 6. 回滚/缩容方案：扩容后如何评估效果、何时缩回去，责任到人
□ 7. 监控就绪：新节点的 QPS/RT/资源指标接入告警，避免"盲扩"
模块 4

四维容量模型：CPU/内存/IO/连接数

"只看 CPU"是容量规划第一大坑。系统先被哪个维度打满，哪个就是瓶颈，而它往往不是 CPU。

维度健康水位先满的典型场景满了怎么办
CPU持续 60% 以下，峰值不超 80%计算密集型：图片处理、加解密、序列化、复杂 SQL水平扩容；算法优化；异步化
内存使用率 70% 以下，无频繁 Full GC大对象缓存、JVM 堆不足、内存泄漏、Elasticsearch 堆扩容或升配；优化缓存策略；修泄漏
IOutil < 60%，await < 10ms（SSD）日志写盘、大文件、数据库随机写、NoSQL 落盘换 SSD/ESSD；批量写；异步落盘；加缓存
连接数峰值不超过池上限 80%DB 连接池打满、Redis 连接、句柄数（ulimit -n）调池 + 控制并发；加代理（ProxySQL）；升规格

模块 5

大促与活动保障

大促保障 = 容量 × 压测验证 × 预案 × 值班四件套。少任何一件，都是在拿生产环境赌运气。

大促容量规划时间线

时间点动作产出
T-6 周业务目标对齐：峰值 QPS、订单量、核心链路清单容量规划文档 v1
T-4 周资源采购/申请，缩容非大促资源腾预算资源清单

预案清单（每条都要可执行）

# 预案模板（每条必须包含：触发条件、执行动作、执行人、回滚方式）
# 例 1：下单接口 RT 突增
触发：P99 RT > 500ms 持续 3 分钟
动作：① 关闭"猜你喜欢"推荐（非核心）；② 购物车接口限流降级到只读缓存
执行：SRE oncall 一键开关
回滚：RT 恢复后 10 分钟逐步打开

# 例 2：数据库 CPU > 90%
触发：DB CPU 90% 持续 5 分钟
动作：① 开启全局限流（QPS 砍半）；② 只读流量切只读实例；③ 大 SQL 查杀
执行：DBA + 服务负责人双确认

# 例 3：缓存集群命中率暴跌
触发：命中率 < 90% 持续 2 分钟（可能热 key 或节点故障）
动作：① 本地缓存兜底开启；② 热 key 探测并本地化；③ 必要时限流保 DB
全链路压测的三个关键设计：① 流量打标（压测流量带特殊标记，影子库/影子表隔离，不污染真实数据）；② 数据构造（按真实分布造数据，别全是空库）；③ 压到位（按目标峰值的 1.2~1.5 倍压，留出模型误差）。只压不隔离、压完不留存报告，等于白压。
模块 6

成本与容量的平衡

容量不是越大越好，每一分冗余都是钱。平衡点在于：故障恢复时间 × 业务损失 vs 冗余资源成本。

策略做法适用
日常保水位按均值 + 30% 冗余常驻稳定业务，利用率 60% 左右
大促前扩容提前 2~4 周按峰值开资源可预见峰值，用时间换成本
错峰混部在线业务与离线任务错峰使用同一批机器大数据/计算平台与在线服务混部
分级保障核心链路高冗余，边缘服务低冗余所有系统。评论挂了无所谓，支付挂了要命
Serverless低频/突发流量用函数计算按量付费图像处理、报表、Webhook 等弹性场景
# 成本-风险量化示例
某服务峰值 10,000 QPS，单机安全 QPS 800
方案 A：常驻 13 台（980×0.85=833/台，13×833=10,829）
  年成本 = 13 × 4C8G × 单价 × 12
方案 B：常驻 6 台（覆盖日均 5,000 QPS）+ 弹性扩 7 台
  日常成本 = 6 台常驻；大促 20 天按需扩 7 台
  年成本 ≈ 6×12 + 7×(20/30) = 72 + 4.7 ≈ 77 台·月 vs A 方案 156 台·月
  # 节省约 50%，代价：大促期间弹性扩容有 5~10 分钟空窗，需要预案兜底
决策原则：不可预见的流量风险用弹性扛，可预见的峰值提前备，核心链路冗余给足，边缘链路能省则省。把每个服务标注 SLO 等级（S/A/B/C），容量策略按等级走，不要所有服务一个标准。
模块 7

十个线上坑

1
只看 CPU 做容量判断，被连接数/IO 偷袭
CPU 才 50% 但 DB 连接池打满，请求全在排队等连接，表现为"莫名变慢"。必须四维一起看，连接数和队列长度优先。
2
按日均值买机器，大促当天挂
均值 2,000 QPS、峰值 6,000 QPS，按均值配 3 台，峰值日直接过载。容量必须按峰值 × 安全系数算，日常低水位是正常代价。
3
忽视峰值毛刺（分钟级尖峰）
整点秒杀、定时任务集中触发、缓存同时过期，都能造成秒级 5~10 倍毛刺。对策：限流削峰、过期时间加随机值、任务打散。
4
容量规划一次定终身，从不复查
业务涨了 5 倍，容量还是去年的数字；或者业务萎缩了，机器白放两年。容量规划是季度例行工作，每次大促后必须校准模型。
5
压测环境与生产差异巨大，数字不可信
压测库几万行数据全内存，生产几亿行走磁盘，同样的 SQL 差 10 倍。压测库要等量数据、真实分布，核心结论要全链路压测验证。
6
弹性扩容来不及：从触发到就绪 10 分钟，故障 3 分钟就到
扩容速度永远追不上突发流量。弹性只补渐进增长，秒级突发必须靠限流、缓存、降级先扛住。
7
HPA maxReplicas 不匹配下游 DB 连接池
扩容到 100 Pod，每个 20 连接 = 2,000 连接，MySQL 直接 max_connections 打满全线崩溃。扩容上限要先除以下游容量。
8
压测不留数据、不复盘，下次从零开始
每次压测都重新摸瓶颈。必须沉淀：单机容量表、瓶颈清单、压测脚本进仓库，形成资产。
9
预留冗余算了节点数，忘了网络/中间件容量
应用层够了，但 SLB 连接数、Redis 带宽、Kafka 分区吞吐先打满。容量规划要覆盖全链路每个组件，不只是应用服务器。
10
大促缩容不及时，活动后资源白放一个月
大促开的 20 台忘了退，月账单一堆。预案里要写"活动结束 48 小时内缩容"，并指定责任人。
自测

六道题

1. 某服务预估峰值 12,000 QPS，单机压测极限 1,400 QPS，安全系数取 0.7，可用率 0.85。需要多少台？
正确答案：15 台。单机安全 QPS = 1400 × 0.7 = 980，再乘可用率 0.85 得 833，12000 ÷ 833 ≈ 14.4，向上取整 15 台。忘了可用率会少配 2 台，发布或故障时就过载。
2. 关于四个容量维度，哪个说法是对的？
正确答案：瓶颈取决于负载特征。计算密集型先满 CPU，缓存密集型先满内存，写密集型先满 IO，高并发服务常常先满连接数。只盯 CPU 会漏掉真实瓶颈。
3. 面对"双 11 零点秒杀"这种可预见的突发流量，最合适的组合是？
正确答案：提前扩容 + 压测 + 预案。弹性扩容从触发到就绪要 3~10 分钟，追不上秒级突发；可预见峰值必须提前备，弹性只兜渐进部分和未知部分。
4. 压测环境测出单机 1,400 QPS，直接用它规划生产容量，最大的风险是？
正确答案：压测环境通常偏乐观。小数据量全走内存、缓存全命中、缺少真实热点分布，会让 QPS 虚高。必须用等量数据 + 全链路压测校正，并保留 0.7 安全系数。
5. 订单服务要从 10 台扩到 50 台，DBA 说"先别扩"。最可能的原因是？
正确答案：连接数瓶颈。水平扩容会线性放大对 DB 的连接需求，DB 连接数是共享瓶颈。扩容前必须验证：节点数 × 单节点池 ≤ DB 最大连接 × 70%。
6. 历史数据外推容量时，下列哪种做法是对的？
正确答案：剔除一次性事件 + 季节性对齐。大促峰值不代表常态趋势，直接用会严重高估；同时教育、电商等行业有强季节性，简单按月外推会错。
