二十分钟学透架构文档与 ADR

架构文档的价值不在"写完"，而在不过期。这篇讲三件事：C4 四级视图怎么画、ADR 怎么把"为什么"留痕、以及怎么让文档跟着代码一起活。

20:00
边看边数：你团队里有几份文档，是上周之后就没人改过的？
模块 1

架构文档写给谁看

动笔前先回答一个问题：这份文档是给谁看的？读者错了，内容全是废话。架构文档不是论文，是工程资产——评判标准是"三个月后还有人靠它做决定吗"。

读者他关心什么文档必须回答的问题
新入职开发系统全貌、代码从哪读起系统由哪几个服务组成？一个请求的数据流是什么？入口仓库是哪个？
运维 / DevOps部署形态、外部依赖、故障点有几个部署单元？依赖哪些外部系统（各自 SLA）？哪些组件没有副本？
产品 / 业务方能力边界、改造成本哪些需求好做、哪些难做、为什么？哪些是历史包袱不能动？
评审 / 审计合规、安全控制点数据怎么分级？传输和存储怎么加密？审计日志在哪、留多久？
半年后的你自己当时为什么这么设计这个方案评估过哪些备选？为什么否掉了？哪些是妥协？

文档要服务的四个目的

新人 onboarding
把"口头传承"变成可检索资产。可度量目标：新人第一次独立提 PR 的时间从 2 周降到 3 天。
跨团队沟通
一份共同的图。会议上所有人指着同一个容器视图讨论，而不是各自心里一张不同的图。
决策留痕
ADR。防止同一个技术争论每两年爆发一次——因为没人记得两年前已经吵过并且有结论。
影响分析
改一个容器之前，先查谁依赖它。数据流图是依赖分析的底图，拍脑袋改法事故的源头。

质量属性必须可度量

"高性能、高可用、高安全"这类词在架构文档里等于没写。每个属性都要有数字、条件和测量方式：

属性不合格写法合格写法
可用性系统高可用全年 99.95%，允许计划外停机 4.38 小时；核心接口有降级开关
延迟响应速度要快详情页 P99 < 300ms（1 万 QPS、缓存命中率 90% 条件下实测）
持久性数据不丢RPO = 0（同步复制），RTO < 5 分钟；允许丢失最近 1 秒非核心日志
安全安全可靠通过等保三级；敏感字段 AES-256-GCM 加密；审计日志留存 180 天
扩展性支持水平扩展无状态服务，HPA 3 分钟内容量翻倍；分片键为用户 ID，支持 32 分片
每篇架构文档至少回答三个问题：系统是什么（上下文）、由什么组成（容器）、为什么是它（ADR）。回答不了这三条的文档，基本都是摆设——写它花了两周，读它没人超过五分钟。
模块 2

C4 模型：四级视图

C4 是 Simon Brown 提出的一套架构图抽象层级。核心思想像看地图：先看全国，再看城市，最后才看街道——不允许一上来就画到门牌号。

层级回答的问题图里的元素示例
L1 Context
系统上下文		我们建的系统是什么？谁在用？和哪些外部系统交互？1 个系统方块 + 用户角色 + 外部系统电商系统、买家、卖家、微信支付、ERP
L2 Container
容器		系统由哪些可独立运行/部署的单元组成？各用什么技术？Web 应用、API 服务、数据库、缓存、消息队列SPA + 订单 API + MySQL + Redis + Kafka
L3 Component
组件		每个容器内部有哪些模块？职责和交互是什么？控制器、领域服务、仓储、客户端适配器OrderController、PricingService、StockClient
L4 Code
代码		类、接口、数据结构长什么样？类图、ER 图交给 IDE / 代码生成，不手绘
最大的误解：Container 不是 Docker 容器。C4 里的 Container 指"独立运行的进程/应用"——一个 Spring Boot jar、一个数据库实例、一个 Node 服务都算。它常常恰好跑在一个 Docker 容器里，但两件事没有必然关系。

画图规则

  • 自上而下逐层细化：L1 里的每个外部系统，在 L2 里体现为一组接口，而不是重新画一遍业务细节。
  • 每层图必须自包含：只看当前这一张图就能看懂，不需要对照上层。
  • 不允许跳级：从 L1 直接蹦到类图，读者五分钟内必然流失。
  • 一图只讲一件事：要么讲数据流，要么讲部署拓扑，不要混在一张图里。
  • 每个元素带技术标注：L2 的方块上必须写"Spring Boot 3 + PostgreSQL 15"这种级别，只写"订单服务"四个字的信息量约等于零。

维护策略（不同层级不同待遇）

层级维护频率谁来维护
L1业务或系统边界变化时更新（通常半年到一年一次）架构师
L2每次发布核对一次，有变化即更新（与 CI 比对配合）架构师 + 各服务 owner
L3重大重构时更新，平时不动服务 owner
L4不手维护，用 IDE 生成或代码即文档没人

C4 是抽象层级工具箱，不是 UML 套件。它的胜负手是"从 L1 讲起"——先让所有人对系统边界达成共识，再谈内部结构。跳过 L1 直接讲组件的会议，通常以吵架收场，因为每个人心里的"系统"根本不是同一个东西。
模块 3

文档模板：六块就够

不要从空白页开始。arc42 模板有 12 节，完整版没人坚持得下来；工程上能长期存活的只有下面 6 块。用固定模板的好处：评审者知道去哪找内容，作者不会漏项。

板块内容对应 C4 层
1. 系统上下文一段话概述 + L1 图 + 外部依赖表（名称 / 用途 / SLA / 负责人 / 不可用时降级预案）L1
2. 容器视图L2 图 + 容器表（名称 / 技术栈 / 职责 / 部署单元 / 数据存储）L2
3. 关键决策ADR 索引：编号 / 标题 / 状态 / 日期，逐条链接到 docs/adr/ 下的文件—
4. 质量属性可度量目标表：属性 / 目标值 / 当前实测值 / 测量方式与频率—
5. 风险与技术债风险表：描述 / 影响 / 概率 / 缓解措施 / 责任人 / 复盘日期—
6. 运维信息部署拓扑、环境清单、SLO、值班表、runbook 链接、常用排查命令—

# 订单平台架构文档

> 负责人：@zhangsan   最后更新：2026-10-10   版本：v3

## 1. 系统上下文

一句话：订单平台承接买家下单、卖家发货、支付结果落地，
对外依赖微信支付与公司 ERP。

| 公司 ERP | 库存同步 | 99.9% | 供应链组 | 本地库存兜底 30 分钟 |

模块 4

ADR：把"为什么"写下来

代码记录了系统"是什么"，ADR 记录"为什么是它而不是别的"。没有 ADR 的团队，每隔一段时间就把同样的选型争论重新吵一遍，因为没人记得上次的结论和理由。

三要素

部分回答什么写作要求
背景 Context当时面对什么问题、有哪些约束写"逼你决策的力量"：截止日期、团队技能、合规要求、历史包袱
决策 Decision最终选了什么一句话能说完，主动语态："选择 PostgreSQL 15 作为订单库"
后果 Consequences选了之后发生了什么好的 / 坏的 / 中性的分开列；坏处必须写缓解措施

MADR 模板（社区最常用的 Markdown ADR 格式）

# ADR-0007：订单库选型 PostgreSQL

- 状态：已接受
- 日期：2026-03-12
- 决策者：@zhangsan @lisi
- 取代：ADR-0003（MySQL 选型，2024-08-15）
- 相关：ADR-0005、ADR-0009

## 背景

订单主链路需要 ACID 事务（扣库存与建单必须原子）；
运营后台有 20+ 维度组合筛选；商品快照 schema 频繁变化。
团队 6 名后端均有 PostgreSQL 运维经验，无人有 MongoDB 经验。

## 决策驱动因素

- 事务正确性优先于模型灵活性
- 复杂查询性能（运营后台不可接受 3 秒级响应）
- 运维成本：优先复用团队现有技能

## 备选方案

1. MongoDB 7 —— 文档模型适配商品快照，但多文档事务需额外设计，
   且团队无运维经验，招人成本高。
2. MySQL 8.0 —— 生态最熟，但 JSON 查询与窗口函数弱于 PG，
   运营后台 20 维筛选需要大量中间表。
3. PostgreSQL 15 —— 事务强、JSONB、窗口函数完善，团队有经验。

## 决策

选择 PostgreSQL 15 作为订单库，商品快照用 JSONB 列存储。

## 后果

- 好：下单主链路用单库事务覆盖，无需引入 Seata AT 模式。
- 好：运营筛选 SQL 从 3.2s 降到 180ms（窗口函数 + 部分索引）。
- 坏：水平分片方案弱于 MySQL 生态，单表过 5 亿行时需引入 Citus，
      预计 3 人周改造成本。
- 中性：DBA 工具链需从 MySQL 迁移，预计 2 人周。

第二条真实 ADR（反面教材修正版）

# ADR-0012：支付结果通知用本地消息表而非 TCC

- 状态：已接受   日期：2026-04-02   决策者：@wangwu

## 背景

支付回调后需通知积分服务加积分。业务允许秒级延迟，
但不能丢（丢一次积分 = 一次客诉 + 一次人工补单）。

## 备选方案

1. TCC：积分服务需改造出 Try/Confirm/Cancel 三个接口，强一致但侵入大。
2. 本地消息表：订单库同事务写 outbox，准实时投递 + 对账兜底，积分服务零改造。

## 决策

选择本地消息表 + 准实时对账。积分到账延迟 < 5s。

## 后果

- 好：积分服务无侵入；消息不丢（同库事务保证）。
- 坏：积分到账有秒级延迟；需实现对账任务（已排期 2026-05）。

编号与状态规则

  • 编号单调递增、永不复用：文件名 docs/adr/0007-order-database-postgresql.md，编号是引用锚点。
  • 状态流转：提议 → 已接受 →（被新 ADR 取代 | 已废弃）。只追加，不删改——历史决策也是资产。
  • 一个 ADR 只做一个决策：把三件事写进一份 ADR，等于都没写清楚。
  • 被否决的备选必须写进"备选方案"节：这是 ADR 最值钱的部分，直接消灭下一轮重复争论。
评审 ADR 时重点审两节："备选方案"和"坏的后果"。只写"我们决定用 X"的 ADR 是装饰品；写清楚"评估过 Y，因为 Z 否掉，选了 X 的代价是 W"的 ADR，才能让半年后的新人（和你自己）不重蹈覆辙。

入库与评审：四条纪律

  1. 文档放业务仓库的 docs/ 目录，不是 Confluence / 语雀 / wiki：和代码共享同一个 PR 生命周期。
  2. Definition of Done 加一条："行为变更必须同步文档"。PR 模板放一个勾选框，reviewer 有权因此打回。
  3. 图放 diagrams/*.mmd / *.puml，Markdown 引用，不贴截图。截图无法 review、无法搜索、无法 diff。
  4. CI 三件套：Markdown 风格检查、死链检查、图渲染检查（渲染失败说明语法写错，图已经坏了）。

CI 配置示例

# .github/workflows/docs.yml
name: docs
on: [pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Markdown 风格检查
        run: npx markdownlint-cli2 "docs/**/*.md"
      - name: 死链检查
        run: npx lychee docs/ README.md --exclude-mail
      - name: 图渲染检查（渲染失败则 CI 失败）
        run: npx @mermaid-js/mermaid-cli -i docs/diagrams/context.mmd -o /tmp/context.svg
文本图的真正红利在评审环节。PR 里图变了，diff 直接告诉你"订单 API 到 Kafka 的连线被删了"——这个变更因此被认真讨论。截图图的变更从来没人审过，因为看 diff 只看得到一堆二进制字节变了。
模块 6

保鲜机制：让文档不过期

文档腐烂（documentation rot）是默认结局，不是意外。保鲜靠机制，不靠觉悟。下面六条按性价比排序，第一条最值得做。

机制具体做法频率
同仓同 PRdocs/ 与代码同一仓库，行为变更在同一个 PR 里提交文档更新每次变更
DoD 卡点PR 模板勾选"文档已同步"，reviewer 可因此打回；和代码评审同一场每次 PR
CI 比对真实部署每日拉取集群 deployment 列表与文档容器表比对，不一致即告警到值班群每日
ADR 季度回顾把半年前的 ADR 标注为"仍有效 / 部分过时 / 已被演进替代"每季度
事故回路复盘发现"文档没写 X"，48 小时内补文档并指定具名 owner事故后
单一 owner每份文档一个具名负责人，禁止署名"架构组"这种集体名词长期

CI 比对脚本（容器视图 vs 集群实际）

#!/usr/bin/env bash
# 每日跑：文档声明的部署单元与集群实际 deployment 比对
kubectl get deploy -n order -o name | sed 's|deployment.apps/||' | sort > /tmp/actual.txt
grep -oP '(?<=\| k8s: )[a-z0-9-]+' docs/architecture.md | sort > /tmp/documented.txt
if ! diff -u /tmp/documented.txt /tmp/actual.txt; then
  echo "容器视图与集群不一致，请更新 docs/architecture.md"
  exit 1
fi

三个腐烂指标（每月看一次）

  • 时间差：文档最后修改时间与对应代码目录最后提交时间相差 > 90 天 → 进腐烂清单，owner 限期处理。
  • ADR 引用数：没人引用的 ADR 说明该决策已无人关心，要么合并进新 ADR，要么标记废弃。
  • 新人反馈：onboarding 时记录"文档没答上来的问题"，每月汇总补录——这是文档缺口最真实的来源。
最有效的单条机制是"文档与代码同 PR"。它不增加任何工作量，只是把"改代码顺手改文档"从美德变成流程。反过来，任何"每季度集中更新一次文档"的制度，最后都会退化成每季度集中编一次文档。
模块 7

十个真实的坑

1
文档写完即过期
立项时写一份精美 PPT，上线后再没人打开。正确做法：只维护 L1/L2 两张图 + ADR 索引，进仓库跟代码走评审，砍掉一切"为评审而写"的章节。
2
图与实现脱节
文档画的是 3 个服务，实际已经拆成 7 个。解法是 CI 每日比对文档容器表与集群 deployment 清单，不一致直接告警，不等季度盘点。
3
只有架构图，没有决策记录
后人只看到"用了 Kafka"，不知道"评估过 RabbitMQ 因为运维成本否掉"，于是重复争论。ADR 必须记录被否决的备选和理由。
4
用 UML 类图讲架构
一上来画 20 个类的继承关系，读者五分钟就跑了。用 C4 从上下文开始，一层一层讲；类图只在讲具体模块时用。
5
文档只写给评审看
满篇"高内聚低耦合"，没有一个具体数字。每个质量属性都要可度量：P99 多少毫秒、可用性几个 9、SLO 是什么。
6
没有版本和 owner
共享盘里躺着 arch_v1.ppt、arch_v2.ppt、arch_final_真的final.ppt。单一事实源：放仓库、带日期、带具名负责人。
7
文档评审走过场
文档评审和代码评审分开进行，代码合了文档没更新。把"文档已同步"写进 PR 模板和 DoD，reviewer 有权打回。
8
图用手绘工具画
每次改图要开 draw.io、导出 PNG、上传，改图成本高到没人改，最后图彻底躺平。用 Mermaid 文本图：diff 可见、PR 里直接渲染。
9
ADR 只记结论不记背景
"我们决定用 Kafka"——三个月后没人知道为什么，也不敢改。MADR 模板强制写背景、决策驱动、备选方案三节，缺一节打回。
10
把架构文档写成需求文档
写满功能列表和原型截图，真正的部署拓扑、数据流、SLO 一个字没有。固定六块模板，写完对照检查，缺块打回。
自测

六道题

1. 新同学入职，你想让他在 10 分钟内理解"系统与外部世界的边界"，应该给他看哪张图？
正确答案：C4 L1 系统上下文图。它只回答一个问题：系统是什么、谁在用、和谁交互。ER 图和部署图都预设了读者已经懂系统结构，不适合作为第一张图。
2. ADR 的核心三要素是？
正确答案：背景 / 决策 / 后果。背景写"当时面对什么约束"，决策写"选了什么"，后果写"好的坏的中性的分开列"。MADR 模板在这三节之外补充了决策驱动因素和备选方案。
3. 为什么团队应该用 Mermaid 文本画图，而不是 draw.io 导出 PNG 贴文档？
正确答案：能进 git diff。图变了，diff 直接显示"哪条连线被删了"，变更因此被认真评审。PNG 的变更在 diff 里只是一堆二进制字节，从来没人审过。draw.io 适合白板讨论，不适合长期维护。
4. 团队第三次争论"要不要上 Kafka"，前两次讨论没有任何记录。最该补的机制是？
正确答案：ADR 决策留痕。争论反复发生的根源是"决策和理由没有落盘"，每次都是新人重新推演。一份记录备选方案和否决理由的 ADR 能直接终结重复争论。
5. 关于 C4 L4 Code 图（类图 / ER 图），推荐的做法是？
正确答案：不手维护。L4 变化频率太高，手绘必腐化。用 IDE 的类图生成、ER 工具或文档注释（Javadoc / TypeDoc）即可，把维护成本降到零。
6. 以下哪项最能防止架构文档过期？
正确答案：同仓同 PR。它把"顺手改文档"从美德变成流程卡点，成本几乎为零。集中更新周最后都会退化成集中编文档；发链接和凑页数对保鲜没有任何作用。
