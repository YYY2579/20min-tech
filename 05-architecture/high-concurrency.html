开始前

指标体系：QPS/TPS/并发数/响应时间的关系

这四个量不是独立的，一个公式串起来：并发数 = QPS × 平均响应时间（Little's Law 的工程表述）。

指标定义注意
QPS每秒查询/请求数（Queries Per Second）泛指所有请求，读多写少系统常用
TPS每秒事务数（Transactions Per Second）一个事务可能含多个请求。写场景（下单/支付）用 TPS 更贴切
并发数系统同时处理的请求数= QPS × RT。QPS 1万、RT 100ms → 并发 1000
响应时间 RT从发请求到收完响应看 P99/P999，平均会骗人（长尾才是体验杀手）
吞吐量单位时间处理的数据量/业务量和 QPS 的区别：1 个请求搬 10MB 和搬 10B 完全不同
# 核心公式（Little's Law）：L = λ × W
# 并发数 L = 到达率 λ(QPS) × 停留时间 W(RT)

# 算例 1：接口 RT 50ms，目标支撑 10,000 QPS
并发线程需求 = 10000 × 0.05 = 500 个线程同时处理

# 算例 2：秒杀峰值 50,000 QPS，RT 200ms（含排队）
并发 = 50000 × 0.2 = 10,000 个在途请求
# 这意味着：无论你开多少线程，队列/连接/内存都得按 1 万在途设计

# 算例 3：反过来，系统只有 200 个工作线程，RT 最多多少？
max_qps = 200 / 0.05 = 4,000 QPS（RT 50ms 时）
# 超过就排队，RT 线性恶化，直到超时雪崩
这张表是后面所有决策的算力基础：扩容要扩到多少、连接池开多大、压测打到什么目标——全部从这三个数（目标 QPS、目标 RT、现有并发容量）推出来，不是拍脑袋。
模块 1

并发四板斧：缓存、异步、扩容、隔离

所有高并发手段，逃不出这四类。按成本从低到高、见效从快到慢排：

板斧手段见效代价
缓存本地缓存（Caffeine）、分布式缓存（Redis）、CDN、浏览器缓存分钟级，读提升 10~1000 倍一致性窗口、缓存成本、命中率治理
异步MQ 削峰、线程池并行、CompletableFuture、非阻塞 IO天级，写提升 5~50 倍最终一致性、补偿逻辑、调试复杂度
扩容水平扩容（加机器）+ 无状态化、分库分表、读写分离周级，线性扩展数据一致性、分布式复杂度、钱
隔离线程池隔离、信号量隔离、集群隔离、业务分级天级，防雪崩资源利用率下降

隔离的具体做法（以线程池隔离为例）

// 反模式：所有下游调用共用一个线程池
private static final ExecutorService POOL = Executors.newFixedThreadPool(200);

// 库存服务 RT 从 10ms 劣化到 2s → 200 线程全卡在库存调用上
// → 支付、优惠券全部拿不到线程 → 全站雪崩（一个慢依赖拖死所有）

// 正解：每个下游一个线程池，配额隔离
private static final ExecutorService INVENTORY_POOL  = // 库存调用专用
    new ThreadPoolExecutor(20, 20, 0, MINUTES, new ArrayBlockingQueue<>(200),
        new ThreadFactoryBuilder().setNameFormat("inv-%d").build(),
        new CallerRunsPolicy());   // 队列满 → 调用方线程执行 → 天然背压

public InventoryVO query(Long skuId) {
    try {
        return INVENTORY_POOL.submit(() -> inventoryClient.get(skuId)).get(300, MILLISECONDS);
    } catch (TimeoutException e) {
        throw new DownstreamTimeoutException("inventory");   // 快速失败，别死等
    }
}
// 库存再慢，最多占 20 线程 + 200 排队，其余业务不受影响
Sentinel/Hystrix 的舱壁模式就是线程池隔离的框架化。自研时三个要点：① 每个下游独立池 + 独立队列；② 队列必须有界（无界队列 = 内存耗尽）；③ 拒绝策略明确（快速失败 or 调用方执行，不要静默丢弃）。
模块 2

读写分离与分库分表回顾

读写分离：主写从读

问题解法
主从延迟写后读走主库（按业务判断：支付后查订单状态）；关键读强制走主；监控 Seconds_Behind_Master，超阈值熔断从库读
复制延迟放大大事务会堵复制：DELETE 百万行、一次 INSERT 十万条，从库秒级落后。批量操作必须分批
连接数翻倍主库 2000 连接、从库每个 2000，5 个从库 = 1.2 万连接。MySQL 默认 max_connections=151，一定要调且要算内存

分库分表：容量与写入的极限解法

维度分库分表
解决单库连接数/IO/CPU 上限单表数据量（B+ 树深度、索引维护成本）
路由按 sharding key（user_id % 库数）同一库内按 user_id % 表数
代价跨库事务（不可能）、跨库 join（不可能）分页深翻页、count 全表扫描
# 单库单表演进路线（经验值，非定律）
单表 < 500 万行        → 不用分，索引正常扛
单表 500 万 ~ 5000 万   → 先优化：归档历史数据、加合适索引、分区表
单表 > 5000 万 且持续涨 → 分表（同库分表最简单，无跨库问题）
单库写入 > 3000 TPS    → 分库（先加从库分摊读，再分库分摊写）

# 分片键选择是生死决策：
# ✓ user_id：数据均匀、查询多带 user_id、同一用户数据在同库（可本地事务）
# ✗ 时间/状态：热点全在最新分片；order_id 随机：查用户订单要广播所有分片

# 深分页问题：LIMIT 1000000, 10 要扫 100 万行再丢 999990
# 解法：游标分页 WHERE id > 上一页最大 id LIMIT 10（ O(log n) ）
SELECT * FROM orders WHERE user_id = ? AND id > ? ORDER BY id LIMIT 10;
分库分表不可逆，上之前必须问三个问题：① 单表真的到 5000 万了吗？（多数项目没有，是运维懒）；② 所有查询都带分片键吗？（按手机号查订单 = 全库路由，方案作废）；③ 有全局 ID、跨片查询、分布式事务的配套方案吗？没有想清楚就分，是给自己埋三年的坑。更推荐先试：归档 + 分区表 + 读写分离。
模块 3

连接池调优：数据库与 HTTP 客户端

连接池是“用有界资源服务无界并发”的经典矛盾。开小了排队，开大了把对端打死。

核心公式（HikariCP 官方建议）

# HikariCP 作者的铁律：connections = (core_count * 2) + effective_spindle_count
# SSD 时代 effective_spindle_count 视为 1（不再按机械盘头数算）

# 算例：4 核 CPU 的应用服务器，SSD 数据库
pool_size = 4 * 2 + 1 = 9   # 对！9 个连接往往比 100 个更快

# 为什么不是越大越好？
# 1. MySQL 每个连接一个线程，100 个连接 = 100 个线程抢 CPU，上下文切换爆炸
# 2. InnoDB 内部锁竞争随连接数上升，purge、buffer pool 刷新都被拖慢
# 3. 连接本身吃内存：每连接 sort_buffer + join_buffer 默认 256KB+128KB

# 多台应用服务器时的总量核算
10 台应用 × 10 连接 = 100 连接 → 检查 MySQL: max_connections ≥ 100 + 预留 50
SHOW VARIABLES LIKE 'max_connections';        # 默认 151！
SHOW STATUS LIKE 'Threads_connected';         # 当前连接数
SHOW STATUS LIKE 'Aborted_connects';          # 被拒连接，涨了就是不够

HikariCP 关键配置

参数建议值说明
maximumPoolSize按公式算，通常 10~20别再默认 10 或拍 100
minimumIdle= maximumPoolSize固定池大小，避免伸缩抖动
connectionTimeout30000（30s，默认）等连接超时。压测时别设太短，否则全抛异常看不出队尾
maxLifetime< MySQL wait_timeout默认 1800000（30 分钟）。MySQL 8.0 起 wait_timeout 默认 8h，但防火墙/中间件可能 5 分钟掐断
keepaliveTime0（禁用）或 > 30s保活探测，防中间设备掐长连接
leakDetectionThreshold60000连接借出超 60s 未还就打警告日志，抓连接泄漏神器

HTTP 客户端连接池（OkHttp / Apache HttpClient）

参数建议理由
maxConnections / maxTotal按下游容量算，通常 50~200超过下游承受能力 = 把对方打挂
maxConnectionsPerRoute= maxConnections（单下游）OkHttp 默认 5！单下游只有 5 条连接，高并发下严重排队
connectionTimeout1~3s建连超时宜短，下游 IP 挂了快速失败
readTimeout按下游 P99 定，3~10s读超时是主要耗时来源，必须设
idle connection eviction30~60s清理空闲连接，防对端掐断后拿到死连接
最常见的连接池事故：每次请求 new 一个客户端/连接。HTTP 短连接每次 TCP 握手 + TLS 握手（2 个 RTT 起步），RT 从 5ms 变 30ms，且 TIME_WAIT 堆积耗尽端口。第二个事故：池开得比下游容量大——数据库 max_connections=151，10 台应用各配 50，第 4 台就连不上了。
模块 4

无状态化、会话保持与热点治理

无状态化：水平扩容的前提

状态集中化方案注意
登录会话 SessionRedis 集中存储，客户端带 sessionIdRedis 成了关键路径，要主从 + 本地缓存兜底
本地文件/缓存对象存储（OSS/S3）+ CDN本地磁盘扩容无效，是反模式
本地定时任务分布式调度（XXL-Job/ElasticJob）多机部署时定时任务会重复执行 N 次
节点内存数据Redis + 本地缓存双层见本期《缓存架构设计》多级缓存一致性

热点 key：流量倾斜的治理

  • 检测：Redis --hotkeys（LFU 模式下）、客户端埋点统计、Proxy 层统计（twemproxy/Codis 有热点上报）
  • 本地缓存兜底：热 key 加 Caffeine 本地缓存（TTL 秒级），命中率 99% 的请求根本不到 Redis
  • key 复制：hotkey#1 ~ hotkey#N 多副本散列到不同节点，读随机选一个，写全写 + 短 TTL 容忍不一致
  • 读扩散：把单个热 key 的 value 拆成多个子 key（如大 list 分段），请求分散到不同 slot

库存扣减：高并发写的经典题

# 方案演进（按并发量选）

# ① 数据库行锁：UPDATE stock SET n = n - 1 WHERE sku = ? AND n > 0
# 单行更新 = 串行化，1000 QPS 就是极限，且行锁等待堆积

# ② Redis 预扣（Lua 原子）：扣减在 Redis，异步同步 DB
-- stock.lua：扣减 + 防超卖 + 防重（同一请求幂等）
local stock = redis.call('GET', KEYS[1])
if stock == false then return -1 end          -- 未初始化
local n = tonumber(stock)
if n <= 0 then return 0 end                 -- 售罄
local used = redis.call('SISMEMBER', KEYS[2], ARGV[1])
if used == 1 then return -2 end          -- 重复请求
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])          -- 记录已扣用户
return 1
# 调用：EVAL script 2 stock:sku88 used:sku88 req-abc

# ③ 扣减异步化：Redis 扣成功即返回"抢购成功"，落库走 MQ
# 用户体验最快；DB 最终一致；超卖的账用对账兜底（Redis 与 DB 库存日终核对）

# ④ 分段库存：10000 件拆 100 段，每段 100 件，请求哈希到段，段内行锁
# 锁竞争降 100 倍；缺点是某段卖完其他段有余（运营可接受）
库存扣减的铁律：Redis 可以快，但数据库必须是最终真相。Redis 丢数据（宕机、淘汰）就会超卖，所以：① Redis 扣减前先落扣减流水（异步批量也行）；② DB 保留兜底校验（WHERE n > 0）；③ 日终对账修复漂移。纯 Redis 扣减不上账，丢一次数据就是一批超卖订单。
模块 5

削峰填谷与线程模型

削峰：把脉冲流量摊平

手段机制适用
MQ 缓冲请求进队列，消费者按能力匀速处理下单、支付等写流量。用户等待 = 异步结果通知
漏斗限流令牌桶/漏桶，超过速率直接拒绝或排队保护型场景。拒绝要优雅（排队页/验证码分流）
答题/验证码把请求压力转移给客户端，拉长到达间隔秒杀防刷。把 1 秒的脉冲摊到 5 秒
预约开售提前收意向，开售时均匀放量大促运营手段，非技术
# 削峰算例：秒杀 60,000 QPS 涌入，系统只能扛 5,000 TPS 落库
# 不削峰：60,000 并发打进来，DB 连接池瞬间耗尽 → 全站超时
# MQ 削峰：请求全部进队列（MQ 抗 10 万+ 写入），
#           消费者 20 个实例 × 250 TPS = 5,000 TPS 匀速消费
#           队列深度 60,000/5,000 = 12 秒消费完 → 用户等 12 秒收到"抢购成功"
# 关键：MQ 要有积压监控（lag 突增 = 消费能力不足），且积压上限要能算
#       积压上限 = 可容忍最大等待时间 × 消费速率 = 60s × 5000 = 30 万条

线程模型：IO 密集 vs CPU 密集

类型特征线程数公式
CPU 密集计算为主（加解密、压缩、图像处理）线程数 = CPU 核数（+1）。多了纯增加切换开销
IO 密集等数据库/Redis/HTTP 为主线程数 = 核数 × (1 + 等待时间/计算时间)，经验 50~200
混合型大部分业务服务按 RT 拆解：计算段用 CPU 数，等待段按公式放大
# IO 密集线程数算例：业务 RT 100ms，其中 CPU 计算 10ms、等下游 90ms
# 4 核机器，期望 CPU 不空转：
# 每线程 100ms 内干活 10ms → 单线程 CPU 利用率 10%
# 打满 4 核需要 4 / 0.1 = 40 个业务线程 → 支撑 QPS = 40 / 0.1s = 400 QPS/实例
# 目标 4000 QPS → 10 实例；或用异步/协程把等待时间"折叠"（见下）

# 阻塞模型的根本问题：一个线程 = 一份栈内存（默认 1MB）
# 1000 并发 = 1GB 栈内存 + 1000 次上下文切换/请求
# 异步/协程方案（WebFlux/virtual thread/Go goroutine）：
# 等待时不占线程 → 同样 4 核可挂 1 万在途请求，内存是栈的 1/100
# 代价：调试栈断裂、异常难追、线程上下文变量（ThreadLocal）失效
务实结论：90% 的业务系统用阻塞模型 + 有界线程池就够了，Tomcat 默认 200 线程能扛 200/0.05 = 4000 QPS。需要 > 1 万并发在途再考虑异步/协程。别为了技术时髦把团队拖进响应式的深渊。
模块 6

容量估算与压测：用数字说话

单机 MySQL 写入上限估算

# 一次事务提交，InnoDB 的磁盘成本（SSD，RAID10）
# 1. redo log 顺序写：组提交后一次 fsync，批量越大摊得越薄
#    单条 redo 约 200~600B，组提交 100 条一次 fsync → 每条摊 ~1ms 的 1/100
# 2. binlog 顺序写：同组提交机制
# 3. 脏页刷盘：随机写，最贵。双1配置（sync_binlog=1, innodb_flush_log_at_trx_commit=1）
#    时一次提交 = 2 次 fsync，SSD 上单 fsync ~0.5~1ms

# 保守估算（双1，单行 INSERT，无慢 SQL）：
单机 TPS ≈ 1000ms / (2 × 1ms fsync) × 组提交加速系数 ≈ 1000~3000 TPS

# 现实修正：
# - 关闭双1（sync_binlog=1000 / flush_log=N）：丢数据换性能，可到 5,000~8,000
# - SSD 换成 NVMe：fsync 降到 ~0.1ms，可再翻倍
# - 大事务/复杂索引/触发器：直接打对折
# - 云 RDS（共享存储）：看规格，保守按自建 60% 估

# 行业常说"单机 MySQL 写入上限约 2000 TPS"就是这么来的，不是拍脑袋，
# 是 fsync 成本 ÷ 组提交效率的经验值。读（主从+缓存）可以轻松上万 QPS

容量规划模板

步骤算例（电商大促）
① 峰值 QPS 预估日常 2,000 QPS，大促 ×10 = 20,000 QPS（按 UV×转化×集中系数估）
② 按接口拆流量占比商品详情 70%（读）、下单 5%（写）、支付 2%（写）、其他 23%
③ 各环节容量核对详情读 14,000 QPS → Redis 集群（单节点 8 万 QPS，2 主够）+ 本地缓存扛 80%
④ 写下沉核算下单 1,000 TPS + 支付 400 TPS > 单机 2,000 → 分 4 库，或 MQ 削峰到 800 TPS
⑤ 单机能力 × 冗余系数单机 4,000 QPS × 目标利用率 60% = 2,400 有效 QPS/实例 → 20,000/2,400 ≈ 9 → 部署 12 台留余量
⑥ 压测验证按目标 1.5 倍（30,000 QPS）压，看瓶颈点和拐点，不达标回炉

压测模型：单机、全链路、生产镜像

模型做法能发现什么
单机基准一台实例梯度加压（100→1000→5000 QPS）单机拐点、RT 曲线、GC 影响
全链路压测流量染色 + 影子库表，生产环境或 1:1 仿真DB 容量、缓存容量、下游依赖、真实网络
生产引流线上小比例真实流量（1%→10%）数据倾斜、缓存命中率、长尾
# 压测必看的四个拐点（JMeter/wrk 梯度加压时记录）
# 1. RT 拐点：P99 从 100ms 跳到 500ms 的 QPS = 真实容量上限（不是错误率拐点）
# 2. 错误率拐点：超时/5xx 开始出现的压力点，通常紧挨 RT 拐点之后
# 3. 资源拐点：CPU > 70% 持续、内存 GC 频率翻倍、DB 连接池等待 > 0
# 4. 恢复能力：压力撤掉后 RT 能否 10 秒内回到基线（不能 = 队列积压设计有问题）

# 报告必含数字（样例）：
# 目标 20,000 QPS，实测拐点 24,000 QPS @ P99 380ms，CPU 峰值 68%
# 瓶颈：库存服务 DB 连接池（等待 120ms）→ 扩容从库 / 加本地缓存后复测
没有压测的容量规划是玄学。最常见的悲剧：按“理论值”估算 10 台够，上线当天真实流量带了 30% 大查询和爬虫，实际容量只有 6 台。压测的另一半价值是发现未知瓶颈——你以为瓶颈在 DB，压出来发现是日志同步写磁盘。
模块 7

十个线上坑

1
连接池按拍脑袋配置
默认 10 太小排队、设 100 把 DB 打挂。用公式算：核数×2+1，总量乘实例数核对 max_connections。
2
每次请求新建 HTTP 客户端
无连接复用，RT 涨 6 倍，TIME_WAIT 耗尽端口。客户端必须单例 + 连接池，OkHttp 注意 maxConnectionsPerRoute 默认只有 5。
3
线程池无界队列
Executors.newFixedThreadPool 默认 LinkedBlockingQueue 无限堆积，内存 OOM 前毫无征兆。必须 new ThreadPoolExecutor 显式有界队列 + 拒绝策略。
4
所有下游共用一个线程池
一个慢依赖（库存 P99 劣化）占满线程，全站一起超时。按下游分池隔离 + 快速失败。
5
主从延迟上读后写读走从库
用户刚下的单查不到（从库还没同步），投诉“订单丢了”。支付/下单后查询强制走主，或加延迟容忍逻辑。
6
分库分表前没想清楚分片键
选了随机 order_id 或时间，结果“按用户查订单”要全库扫描。分片键必须覆盖 80% 以上查询条件。
7
热点 key 不设本地兜底
爆款商品 key 单节点 10 万 QPS，Redis 该节点 CPU 100%，集群其他节点闲着。本地缓存 + key 复制双管齐下。
8
Redis 扣库存不落账
Redis 淘汰/宕机丢扣减记录，超卖一批订单。扣减流水必须异步落库 + DB 兜底校验 + 日终对账。
9
MQ 积压无监控无上限
消费者 bug 导致 lag 涨到千万条，发现时已经积压 3 小时。lag 必须告警，且积压上限 = 可容忍等待 × 消费速率，超限要熔断入口。
10
上线前没压测，按理论值扩容
真实流量带大查询和爬虫，实际容量只有估算一半，大促当晚雪崩。上线前按目标 1.5 倍压测，看 RT 拐点而不是平均。
自测

六道题

1. 系统当前 500 QPS，平均 RT 100ms。要支撑 5000 QPS 且 RT 不变，同时处理的并发请求会变成多少？
正确答案：500 个并发（5000 × 0.1s）。本题是陷阱：并发数 = QPS × RT，原来 500×0.1=50，QPS 翻 10 倍且 RT 不变，并发也翻 10 倍 = 500。线程池、队列、DB 连接都要按 500 在途设计。
2. 一台 4 核应用服务器连 SSD 数据库，HikariCP 连接池 size 最合理的初始值是？
正确答案：9 左右。这是 HikariCP 作者的公式（4 核 SSD：4×2+1）。连接数远超 CPU 处理能力时，MySQL 内部锁竞争和上下文切换会让总吞吐反而下降。50/200 是拍脑袋配置的典型，会把数据库打挂。
3. 秒杀 6 万 QPS 涌入，系统落库能力 5000 TPS，最合理的削峰手段是？
正确答案：MQ 削峰 + 异步。开 6 万线程内存先崩；纯拒绝损失 90% 用户体验（且集中拒绝也耗资源）。队列把脉冲摊成匀速，用户等约 12 秒收到结果，这是大促标准做法（需配积压监控）。
4. 关于“单机 MySQL 写入上限约 2000 TPS”这个经验值，它的主要依据是？
正确答案：fsync 成本。sync_binlog=1 + innodb_flush_log_at_trx_commit=1 时每次提交要刷 redo + binlog，SSD 单次 fsync 亚毫秒级，组提交能把批量开销摊薄，最终落在 1000~3000 TPS 区间。关双 1 或 NVMe 可以显著上探。
5. 高并发扣减库存，下列哪种说法是对的？
正确答案：Redis 快 + DB 兜底 + 对账。Redis 会丢数据（淘汰、宕机、误操作），纯 Redis 扣减一旦丢记录就是超卖。DB 侧 WHERE n>0 是最后防线，日终对账修复漂移。
6. 一个接口 RT 100ms，其中 10ms 是 CPU 计算、90ms 在等数据库和下游。提高单机吞吐最有效的方向是？
正确答案：压等待时间。90% 的时间在等，加线程只是让更多线程一起等（内存和切换成本暴涨）；加 CPU 核只加速那 10%。缓存命中、合并下游调用、MQ 异步化、或协程/异步 IO 折叠等待，才是对准瓶颈的优化。

spring:
  datasource:
    hikari:
      maximum-pool-size: 16            # 按公式算，不是越大越好
      minimum-idle: 16                 # 固定池，避免伸缩抖动
      connection-timeout: 30000        # 等连接超时（ms）
      max-lifetime: 600000             # 必须小于对端 wait_timeout
      leak-detection-threshold: 60000  # 连接泄漏检测（ms）

# 线程池（显式构造，禁用 Executors 工厂方法）
new ThreadPoolExecutor(
    8, 16, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),              # 有界！
    new ThreadFactoryBuilder().setNameFormat("biz-%d").build(),
    new CallerRunsPolicy()                     # 拒绝策略：背压给调用方
);

# MySQL 侧核对
SHOW VARIABLES LIKE 'max_connections';    # 默认 151，多实例部署必查
SHOW STATUS LIKE 'Threads_running';       # 正在执行的连接，持续接近上限 = 过载
SHOW STATUS LIKE 'Aborted_connects';      # 连接被拒次数，涨了要扩容

术语表

术语一句话解释
QPS / TPS每秒请求数 / 每秒事务数，后者一个事务可含多个请求
Little's Law并发数 = 到达率 × 停留时间，容量估算第一公式
P99 / P99999%/99.9% 请求的响应时间上限，比平均值更能体验瓶颈
吞吐量单位时间处理的业务量，区别于请求数（还要看单请求数据量）
四板斧缓存、异步、扩容、隔离，高并发手段的四大类
无状态化实例不存本地状态，是水平扩容的前提
读写分离主库写从库读，注意主从延迟对写后读的影响
分库分表按分片键拆分数据库和表，解决容量与写入上限，代价是不可逆
连接池复用数据库/HTTP 连接的有界资源池，大小按公式而非直觉
舱壁隔离每个下游独立线程池/资源配额，防单点劣化扩散
背压过载时把压力回传给调用方（拒绝/排队），而非自己崩溃
削峰填谷用队列把脉冲流量摊成匀速消费，保护后端
令牌桶/漏桶两种限流算法：允许突发 vs 严格匀速
热点 key访问量集中的缓存 key，用本地缓存/key 复制治理
双 1 配置sync_binlog=1 + innodb_flush_log_at_trx_commit=1，最安全最慢
组提交多个事务合并一次 fsync，摊薄磁盘成本的机制
全链路压测带流量染色的端到端压测，影子库表隔离数据
容量拐点RT 或错误率突变的压力值，即系统真实容量上限
IO 密集/CPU 密集等待为主/计算为主的负载，决定线程池规模公式
异步/协程折叠等待时间的执行模型，高并发在途的解法，代价是调试难
下一步怎么练：① 算出你系统的“当前 QPS × RT = 并发数”，画出容量仪表盘；② 检查项目的 HikariCP/OkHttp 配置，用公式重算一遍；③ 用 wrk/JMeter 做单机梯度压测，找到 RT 拐点，和你的理论估算对比；④ 给最核心的写接口设计 MQ 削峰 + 积压监控 + 对账方案。
