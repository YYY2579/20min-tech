二十分钟学透单体、模块化与微服务边界

微服务不是免费午餐，是分布式复杂度贷款。这篇讲清楚什么时候该拆、按什么边界拆、绞杀者模式怎么渐进落地，以及"分布式单体"这种拆了比不拆更糟的产物。

开始前

先记住一句话

拆分服务是手段不是目的。多数团队需要的是模块化单体，而不是微服务——把进程内边界理清楚，能解决 80% 的"代码乱"问题，且不用付分布式的税。

症状通常病因通常药方
改个需求动半个系统模块边界不清，耦合弥漫模块化单体（先做这个）
A 团队发布总被 B 团队阻塞变更频率不同却绑在同一发布节奏拆高变更频率模块
一个模块 OOM 拖垮全站资源不隔离进程隔离（拆服务）
团队 30 人，沟通成本爆炸组织规模超过了单体协作半径微服务 + 团队拆分
模块 1

演化路径的四个阶段

阶段特征问题
0. 巨石应用
Big Ball of Mud		无模块边界，数据库所有表共享，任何代码可以调任何代码改动全局扩散，新人上手按月计
1. 模块化单体进程内模块边界清晰，schema 按模块归属，公开 API 交互，架构测试守护几乎无分布式问题；部署和扩展仍是整体
2. 分布式单体服务拆了，但共享数据库、强同步调用链、必须一起部署最糟形态：微服务的成本 + 单体的坏处
3. 微服务独立部署、数据自治、异步优先、故障隔离分布式复杂度全部到账

康威定律：结构复刻沟通

Conway's Law：系统设计最终复刻组织的沟通结构。推论很直接：

  • 5 个人的团队拆 20 个服务 = 灾难。每人 own 0.25 个服务，排障靠缘分，服务边界天天变。
  • 反过来用（逆康威定律 / Inverse Conway Maneuver）：先改组织结构，再拆服务。想让系统按业务能力拆，先按业务能力组团队（Spotify 的 squad 模型即此思路）。
  • 经验数字：一个微服务团队 6~10 人（两个披萨能喂饱），超过 15 人沟通成本开始指数上升。
真实参照：GitHub 长期是 Rails 大单体，团队规模数千人；Shopify 的核心系统至今是模块化单体（Rails monolith + 严格的组件化边界），微服务只用于特定任务。大规模团队也能守住单体，关键在模块化。国内不少"微服务改造"项目，改完性能更差、发布更慢，原因是直接从阶段 0 跳到了阶段 2。
模块 2

模块化单体：先把这个做好

目录组织：package by feature vs package by layer

# 按层分包（不推荐）：技术层次优先，业务被切碎
src/main/java/com/shop/
├── controller/           # 所有 Controller：OrderController + PaymentController + ...
├── service/              # 所有 Service：OrderService + PaymentService + ...
├── repository/           # 所有 Repository，随便互相调
└── model/                # 所有实体，被所有人 import
# 后果：改"下单"要动 4 个目录 12 个文件；删"优惠券"功能要全文搜索

# 按特性分包（推荐）：业务优先，模块自包含
src/main/java/com/shop/
├── order/                # 订单模块：外部只看 api/ 包
│   ├── api/OrderController.java      # 公开入口
│   ├── api/OrderQueryService.java    # 对外暴露的接口
│   ├── domain/Order.java             # 聚合根，包内可见
│   ├── domain/OrderService.java      # 业务逻辑
│   ├── infra/OrderRepository.java    # 只操作 order_ 前缀的表
│   └── dto/
├── payment/              # 同样结构
├── catalog/
└── shared/               # 少量共享内核（工具、基础模型），保持最小

模块化五条规则

  1. 公开 API：模块间只通过 api/ 包的接口/facade 交互，实现类不跨模块 import。
  2. 数据归属：数据库表按模块前缀归属（order_、payment_），不允许跨模块直接 SQL join 别人的表——这是未来拆服务时数据能否自治的预演。
  3. 依赖方向：依赖单向，禁止循环。用架构测试守护：Java 用 ArchUnit，Python 用 import-linter，Node 用 dependency-cruiser，CI 里跑，违规即构建失败。
  4. 共享内核最小化：shared 包只放真正通用的东西（分页、异常、基础实体）。 shared 膨胀 = 模块化失败的前兆。
  5. 模块可独立测试：每个模块能脱离其他模块跑单测（用接口 mock），这是未来能独立部署的前置条件。
# ArchUnit 示例：守护"order 包不允许依赖 payment 包的实现"
classes().that().resideInAPackage("..order..")
  .should().onlyDependOnClassesThat().resideInAnyPackage("..order..", "..shared..", "java..")

# CI 里执行，违反规则构建失败 —— 边界靠机器守护，不靠 review 自觉
模块化单体能撑多大？单团队 10~20 人、日活百万级、单库能扛的 QPS，都可以不拆服务。先模块化，撑不住再拆进程——而且模块化做得好，拆服务只是把 api/ 接口换成 HTTP/RPC，成本低一个数量级。
模块 3

微服务的真实代价

收益代价代价的量级
独立部署扩展每服务一套流水线 + 监控 + 告警 + on-callN 个服务的运维负担超线性增长，Google SRE 经验：服务数翻倍，排障时间可能翻两番
团队自治接口版本兼容、跨团队协作成本跨服务需求要 N 个团队对齐排期，会议成本指数上升
故障隔离网络不可靠：超时、重试、幂等、熔断全套必备一个功能调 5 个服务 = 5 套超时重试配置；漏一个就是故障
技术异构分布式事务：跨服务一致性只能最终一致 + Saga + 对账资金类业务对账补偿逻辑复杂度远超本地事务
按需伸缩排障难度：链路追踪、日志聚合、指标关联是必需品没有 trace 体系，一个跨 10 服务的请求出问题=盲猜

接口数量的乘法

# N 个服务，两两之间可能有接口：最坏 N*(N-1)/2
5 个服务  → 最多 10 条链路    # 还能 hold
20 个服务 → 最多 190 条链路  # 版本兼容开始失控
50 个服务 → 最多 1225 条链路 # 没有平台团队兜着就是灾难

# 一个"小需求"的真实成本：改 5 个服务
5 个 repo 改代码 → 5 条 PR → 5 次 review → 5 条流水线 → 5 次发布
# 单体时代：1 个 repo、1 次发布。这就是"部署独立性"换来的东西
微服务让简单的事情变难，让难的事情（大规模团队并行）变可能。团队规模、变更频率、故障隔离需求没到那个量级时，你付的全是前半句的代价。
模块 4

拆分依据：三个真正可靠的信号

DDD 限界上下文
同一词汇在不同上下文含义不同："商品"在 catalog 是 SKU 属性，在 order 是下单快照，在 payment 是金额计算单元。限界上下文 = 天然模块/服务边界；聚合根 = 事务一致性边界
康威定律
边界跟着团队走。一个服务一个团队（6~10 人）。先组团队再拆服务；团队没拆就拆服务，边界会随人员变动反复重划
变更频率
把"总是一起改的代码"放一起，"从不一起改的"分开。git 提交共现分析能辅助发现真实耦合：两个目录的文件总在同一个 commit 里，就是同一个模块

非功能性拆分信号

  • 性能隔离：CPU 密集的报表/算法与在线交易分开，避免报表跑批把交易链路 CPU 吃光。
  • 安全边界：PCI-DSS 支付卡环境要求网络与数据隔离，合规范围内的代码天然该独立。
  • 技术栈差异：AI 推理要 Python + GPU，交易核心要 Java + 严格事务，运行时诉求不同，拆开对两边都好。

拆分顺序

先拆"变更最频繁且与其他模块耦合最低"的，别先拆最痛的。最痛的模块往往耦合最深（订单模块谁都调它），拿它开刀会同时得罪所有人还拆不干净。正确的第一个候选通常是：通知、报表、对账、文件处理这类边缘但高频变更的模块——风险小、见效快、能验证整套运维体系。

模块 5

拆分反模式

反模式症状解法
按层拆分OrderControllerService、PaymentControllerService……按技术层建服务。改一个需求穿透所有服务，发版要全服务协调按业务能力拆（订单服务、支付服务），不按 controller/service 拆
纳米服务一个服务一个方法/一个实体。一次用户请求 30 个 RPC，延迟线性叠加，故障点相乘；服务数上百，运维爆炸合并到合理粒度：一个聚合根一个服务，服务内允许批量化接口
分布式单体服务间共享数据库 + 强同步调用链 + 必须一起部署。本地跑不起来；一个服务故障全局传导；发布要全服务对齐数据先自治：每个服务只碰自己的表；调用改异步；发布解耦
按 CRUD 实体拆UserService/OrderService 就是对单表的 CRUD 包装，没有业务逻辑，纯透传按用例拆：谁用这个数据、用来干什么，围绕用例组织
一刀切同粒度所有服务一样大。核心交易 30 个功能，边缘工具 2 个功能，都拆成独立服务粒度按变更频率和团队配置，允许不同粒度共存
分布式单体的识别特征（中 3 条以上基本确诊）：① 多个服务直接 SELECT 同一张表；② 接口超时时间设得越来越长（掩盖同步链路过长）；③ 发布窗口要"所有服务一起发"；④ 本地开发必须把 10 个服务全跑起来；⑤ 数据库 ER 图比服务架构图还整齐。拆成了这样，成本已付、收益全无，是最亏的结果。
模块 6

绞杀者模式：渐进拆分

Strangler Fig（绞杀者无花果）：榕树种子在宿主树上发芽，气根包围宿主最终取而代之。新功能建新服务，旧功能逐步迁移，老系统自然"枯萎"。核心是在新旧之间加一层 facade（门面）。

加接入层：在客户端和老系统之间加 facade（API Gateway / 路由层 / BFF）。客户端只依赖 facade，从此后端怎么拆它无感——facade 是保险丝，没有它一切迁移都是大爆炸
新功能直接建新服务：不经过老系统，facade 直接路由过去。新服务不背历史包袱
旧功能逐个迁移：facade 加开关 → 新服务双跑/影子流量验证 → 切换路由 → 摘除老代码。一次一个功能，每步可回滚
数据迁移：新旧库双写 + 存量回填 + 对账校验 → 灰度切读 → 切写 → 旧库归档。数据迁移通常占整个迁移 60% 的工作量，且必须带对账工具
老系统下线：无人调用的功能先从 facade 摘路由，观察一个完整业务周期，再下线下架
迁移策略做法风险
大爆炸重写冻结旧系统，重写一套，选日切换最高。重写周期 6 个月起，期间旧系统继续烂，切换日双系统并行排障，业界成功率极低
并行运行新旧同时服务，流量比对成本翻倍，适合核心链路的影子验证阶段，不适合长期
绞杀者facade 路由 + 逐功能迁移 + 数据双写对账推荐。每步小、可回滚、风险分散；代价是周期长，要长期维护两套并行
绞杀者模式的前提条件是模块化：迁移单元是"一个功能/一个限界上下文"，前提是老系统里这些边界已经清晰。巨石应用上没有"功能"可拆，只有一团代码——所以顺序永远是：先模块化单体，再绞杀者拆服务。
模块 7

该不该拆：12 项检验清单

逐项回答是/否。超过 8 项为"是"才考虑拆；6~8 项先做模块化和组织调整；少于 6 项老老实实做单体。

#检验项为"是"的标准
1模块边界已在代码里清晰能画出模块依赖图且无循环，有架构测试守护
2团队规模超过 15~20 人沟通成本已经明显影响交付速度
3存在变更频率差异大的模块有的模块周级发版，有的季度不动
4部署冲突频繁经常"等另一个模块发完才能发"
5故障需要隔离一个模块 OOM/死循环会拖垮全站
6有技术异构刚需如 Python AI 推理必须独立部署
7拆完能不共享数据库数据可划分，跨模块查询可走 API
8运维体系就绪CI/CD、日志聚合、链路追踪、监控告警齐备
9容错手段就绪超时、重试、幂等、熔断、降级有统一封装
10事务可接受最终一致跨模块流程能改 Saga + 对账补偿
11接口可定义清楚能写出稳定的公开 API 契约并版本化
12拆错能合回去接口可逆，facade 常驻，合并成本已知
即使全过，也先只拆 1~2 个最独立的模块（通知、报表、对账类），跑完"开发→部署→排障→回滚"全流程，验证运维体系真能兜住，再拆下一个。一次拆 10 个服务的团队，都在同时学习十门新课。
模块 8

十个坑

1
按技术层拆服务
controller-service/repository 三层各建服务，一个需求穿透所有服务，改一行代码发五个版。必须按业务能力（订单、支付）拆，不按技术层拆。
2
纳米服务
一个服务一个方法，一次页面请求 30 个 RPC，延迟叠加、故障点相乘。粒度按聚合根定，服务内提供批量接口，别把"小"当"干净"。
3
拆成分布式单体
共享数据库 + 同步调用链 + 统一发布，等于用微服务的成本买单体的坏处。数据先自治（每服务只碰自己的表），这是拆服务的前置条件不是可选项。
4
团队没长大先拆服务
5 个人维护 20 个服务，没人能完整理解系统，排障靠缘分。康威定律反咬：结构要先匹配组织，拆分节奏跟着团队扩张走。
5
没有 facade 直接迁移
客户端直连老系统，每迁一个功能就要改所有调用方，迁移变成大爆炸。先在接入层加 facade 让调用方只依赖一层抽象，再逐个换后端。
6
把共享数据库当"集成数据库"
服务间通过对方的表集成（直接 join/查别人的表），schema 一改全网震。集成只能走 API；拆库前先停止跨模块 join，用接口替代。
7
拆完没有可观测性
链路跨 10 个服务，出问题时没有 trace、日志散在各处，排查以天计。先建 trace/log/metric 体系再拆——这是基础设施不是加分项。
8
跨服务事务硬上 2PC
分布式事务协调器跨服务锁资源，延迟爆炸、可用性下降、协调器成新单点。改 Saga（本地事务 + 补偿）+ 对账兜底，业务上接受最终一致。
9
数据迁移不做对账
双写丢了一条差异没发现，切写后新旧库不一致，用户投诉才发现。双写必须带对账工具（行数、校验和、关键字段抽样比对），差异告警，切写前差异必须为零。
10
拆完合不回去
服务间形成深度耦合（互相 import DTO、共享工具库），合并比重拆还难。拆分时保持接口可逆：facade 常驻、依赖方向单向、共享代码最小化，让"合回去"始终是选项。
自测

六道题

1. 大多数中小团队面对"代码乱、改不动"的问题，最该先做的是？
正确答案：先模块化单体。模块边界清晰后，既能解决 80% 的耦合问题，又不用付分布式税；而且将来真要拆服务，成本低一个数量级。跳过模块化直接拆服务，大概率拆成分布式单体。
2. 按 controller/service/repository 三层拆分服务的问题在于？
正确答案：按技术层拆，变更穿透所有服务。改"下单"要动 OrderControllerService + OrderService + OrderRepositoryService 三层，发布要全服务协调。应按业务能力（订单服务、支付服务）拆。
3. "分布式单体"的典型特征是？
正确答案：共享数据库 + 同步链 + 统一发布。等于付了微服务的成本（网络、运维、部署）却享受着单体的坏处（全局耦合、无故障隔离）。解法是数据先自治、调用改异步、发布解耦。
4. 绞杀者模式的第一步是什么？
正确答案：先加 facade。facade 是保险丝：有了它，后端换实现调用方无感，每个功能迁移都可灰度可回滚；没有它，每次迁移都是大爆炸。数据双写是后续迁移单个功能时才做的事。
5. 关于拆分边界，下面哪个依据最可靠？
正确答案：限界上下文 + 变更频率 + 团队结构。DDD 限界上下文给出业务语义边界，变更频率给出拆分优先级（总是一起改的放一起），康威定律要求边界匹配团队。按表拆和按行数拆都是拍脑袋。
6. 决定拆微服务之前，必须具备的运维能力是？
正确答案：可观测性 + CI/CD + 容错体系。服务数上去后，没有 trace 排障靠猜，没有统一容错一个网络抖动放大成全站故障。K8s 只是部署手段不是充分条件；分库更不是前置条件。

绞杀者迁移步骤

# 标准动作序列
1. facade 上线（Gateway/路由层），客户端全量切到 facade
2. 新功能直接建新服务，facade 直连
3. 旧功能逐个迁移：
   facade 开关 → 新服务影子流量 → 切路由 → 摘老代码
4. 数据迁移：双写 + 回填 + 对账（差异=0）→ 灰度切读 → 切写 → 归档
5. 老系统观察一个业务周期后下线

# 每步可回滚：facade 开关就是回滚开关
# 铁律：数据对账差异不为零，不切写

模块化改造四周计划（不动业务、只立边界）

第 1 周 · 盘点：用 git log 做提交共现分析，统计最近 3 个月哪些目录总在一个 commit 里出现；列出数据库表清单和每张表被哪些模块读写。产出：真实耦合图（通常和你想的不一样）
第 2 周 · 划边界：按耦合图 + 限界上下文定义模块（建议先 5~8 个，别一步到 20 个），确定每个模块的公开 API 和表前缀归属。产出：模块依赖图 + API 清单，全员 review 一轮
第 3 周 · 立规矩：加架构测试到 CI（依赖方向、禁止跨模块访问 repository/entity），当前违规只告警不拦截；shared 包做瘦身，把业务代码请出去。产出：CI 里的边界守卫
第 4 周 · 收口：架构测试从告警改为拦截，新代码必须合规；挑一个最大的违规点做一次"样板迁移"（搬家 + 改调用方 + 补测试），跑通全流程。产出：可复制的迁移套路
改造期的三个纪律：① 不借机重写业务逻辑——模块化只搬代码不改行为，混在一起就会无限期烂尾；② 每周违规数只减不增，连续两周增长说明边界划错了，停下来重划；③ 模块数量控制在个位数起步，长出来一个再加一个。
下一步怎么练：① 给你现在的项目画一张模块依赖图，标出循环依赖和 shared 包的胖层；② 用 git log 统计最近 3 个月哪些目录总在同一个 commit 出现（提交共现），对比你想象中的模块边界；③ 加一条架构测试规则到 CI（如"order 包只能依赖 order/shared"），看第一次运行挂几个文件；④ 选一个边缘高频模块（如通知），按绞杀者五步法写一份迁移方案。
