开始前

缓存分类与分层架构

缓存的本质是“用更快的读换一致性代价”。选哪层缓存，是在延迟、成本、一致性之间选位置。

层级延迟量级容量一致性/成本特征
浏览器/CDN~10ms（边缘）无限大一致性最弱，靠 TTL + 主动刷新；成本最低
Nginx 本地缓存~1ms磁盘受限proxy_cache，静态资源/接口缓存
应用本地缓存~0.1ms（堆内）堆内存（GB 级）无网络开销；多实例不一致；进程重启即丢
分布式缓存~1ms（同机房）集群（TB 级）集中一致控制点；要运维 Redis 集群
数据库缓存~10ms（内存命中）Buffer PoolInnoDB Buffer Pool 本身就是缓存，别忽略它

多级缓存的典型形态

# 典型电商读链路（命中率逐层递减，延迟逐层递增的反向）
用户请求
  → CDN（静态图片/详情页壳）            命中率 ~40%，省掉最多流量
  → Nginx 本地缓存（秒杀页/配置）       命中率 ~30%
  → 应用本地缓存 Caffeine（商品基础信息） 命中率 ~20%，微秒级返回
  → Redis 集群（库存/价格/详情）          命中率 ~9%
  → MySQL（最终真相）                   命中率 ~1%，并回填上面所有层

# 各层 TTL 设计（外层短、内层长，逐层兜底）
CDN:      60s + 主动 purge（发布商品时刷新）
Nginx:    30s
Caffeine: 5~10s（短！本地缓存 TTL 是最后一道一致性的补偿）
Redis:    30min~24h（基础数据可长，库存/价格要短或主动失效）
分层的核心思想：越靠前的层容量越小、一致性越弱、失效要越快。本地缓存 TTL 长 = 长达几分钟的脏数据，任何“更新后立刻生效”的需求都会被打脸。本地缓存只放“偶尔旧一会儿没关系”的数据。
模块 1

四种缓存模式对比

模式读流程写流程一致性
Cache Aside
（旁路缓存）		先读缓存，miss 则读 DB 并回填更新 DB，删除缓存最终一致，业界默认选择
Read Through缓存自己读 DB（对应用透明）同 Cache Aside 或配合 Write 模式同 Cache Aside
Write Through同 Read Through先写缓存，缓存同步写 DB强一致，写延迟高
Write Behind
（Write Back）		同 Read Through只写缓存，异步批量刷 DB弱一致，丢数据风险

Cache Aside 的标准实现

// 读：miss 才查库，回填要设 TTL
public ProductVO getProduct(Long id) {
    String key = "product:" + id;
    String json = redis.get(key);
    if (json != null) {
        if ("__NULL__".equals(json)) return null;   // 空值标记，防穿透
        return deserialize(json);
    }
    ProductVO vo = productDao.load(id);            // 查库
    if (vo != null) {
        redis.setex(key, ttlWithJitter(3600), serialize(vo));  // TTL 加随机抖动
    } else {
        redis.setex(key, 60, "__NULL__");                 // 短 TTL 空值
    }
    return vo;
}

// 写：更新 DB 后删缓存（不是更新缓存）
@Transactional
public void updateProduct(ProductVO vo) {
    productDao.update(vo);
    redis.del("product:" + vo.getId());    // 删除而非覆盖，见下方说明
}
为什么删缓存而不是更新缓存？① 更新是写操作，可能失败、可能被覆盖；删除是幂等的，失败重试就行。② 并发下“更新缓存”会写脏：线程 A 写库 v2、线程 B 写库 v3、B 先更新缓存 v3、A 再更新缓存 v2 → 缓存长期脏。删除方案最坏情况只是下次 miss 读一次库。懒加载（lazy load）比急加载（write-through）更适合读多写少。

Write Behind 的适用与风险

# Write Behind 适合：写极密集且允许丢的场景
# - 点赞数、阅读量、在线人数：先写 Redis 计数器，每 5s 批量刷 DB
# - 风险：Redis 宕机丢最近 5s 数据 → 计数回退，用户投诉"我点的赞没了"
# 缓解：刷盘间隔 ≤ 业务可容忍丢失窗口 + Redis AOF everysec（最多丢 1s）

# Write Through 适合：缓存即主存储（Redis 当 DB 用的系统）
# - 每次写穿透到 DB，读永远命中缓存，一致性最好，写 RT 翻倍
模块 2

穿透、击穿、雪崩：成因与对策

这三个是缓存架构的基础题，但工程上要按“发生频率 × 伤害”排序治理。

问题根因对策优先级
穿透查不存在的数据，缓存永远 miss空值缓存 / 布隆过滤器 / 接口层参数校验中（攻击面）
击穿单个热 key 过期，并发直插 DB互斥锁回填 / 逻辑过期 / 热点永不过期高（热点必发生）
雪崩大批 key 同时过期，或 Redis 整体故障随机 TTL / 多级缓存 / 高可用 / 限流降级最高（事故级）

布隆过滤器的正确用法

# 布隆过滤器：说"不存在"一定准确，说"存在"可能误判（假阳性率可调）
# 因此它只能拦"肯定不存在"的流量，拦不掉之后的所有 miss

# 容量规划：n = 预期元素数，p = 可接受误判率
# 位数组大小 m = -n·ln(p) / (ln2)² ；哈希函数个数 k = (m/n)·ln2
# 例：1 亿商品 ID，误判率 1% → m ≈ 9.6 亿 bit ≈ 120MB，k ≈ 7 个哈希

# 三种落地方式
# ① Redisson 的 RBloomFilter（Redis 4.0+ 已内置 Bloom 类型，支持 BF.ADD/BF.EXISTS）
BF.ADD product:filter "sku-10001"
BF.EXISTS product:filter "sku-10001"     # 0 = 一定不存在
# ② 本地布隆（Guava BloomFilter）：零网络成本，但重启要重建、多实例各一份
# ③ 启动时全量加载 + binlog 增量维护（见模块 3）

# 坑：删除元素不支持（计数布隆才行）；元素少时误判率比理论值高
# 坑：Redis 集群下 BF 是单 key，不能跨节点扩容 —— 大集合只能本地布隆

击穿：互斥锁回填的完整实现

// 互斥锁：只放一个请求去查库，其他等待后重试（保护 DB，牺牲少许延迟）
public ProductVO getWithMutex(Long id) {
    String key = "product:" + id;
    String json = redis.get(key);
    if (json != null) return deserialize(json);

    String lockKey = "lock:product:" + id;
    String token = UUID.randomUUID().toString();
    try {
        for (int i = 0; i < 3; i++) {               // 最多重试 3 次
            if (redis.set(lockKey, token, NX, EX, 10)) {   // 拿到锁
                json = redis.get(key);                  // 双重检查：可能别人已回填
                if (json != null) return deserialize(json);
                ProductVO vo = productDao.load(id);    // 查库（慢，但只有一个线程做）
                redis.setex(key, ttlJitter(3600), serialize(vo));
                return vo;
            }
            Thread.sleep(50);                           // 没拿到锁，短暂退避
        }
        return productDao.load(id);               // 兜底：直接查库，别让请求失败
    } finally {
        unlock(lockKey, token);                         // Lua 校验 value 后删除
    }
}
// 注意：锁 TTL 要大于查库耗时；查库超时会连带锁失效 → 需要看门狗续期

逻辑过期：热点永不过期的变体

// 逻辑过期：key 物理 TTL 不设，value 里包一个逻辑过期时间字段
{
  "data": { "id": 88, "name": "爆款T恤", "price": 99 },
  "expireAt": 1729166400000
}

// 读到时判断 expireAt：
// 未过期 → 直接返回
// 已过期 → 尝试拿互斥锁 → 拿到则异步重建数据，当前请求先返回旧值
//         → 拿不到锁说明别人正在重建，直接返回旧值

// 优点：热点 key 永不过期，绝对零击穿；请求永不阻塞
// 缺点：会返回旧数据（业务可接受才行）；需要异步重建线程池
雪崩治理的优先级：① Redis 高可用（主从 + 哨兵/Cluster，别单点）；② 多级缓存（Redis 挂了本地缓存兜底）；③ 随机 TTL（EXPIRE = base + random(0, 600)，杜绝同秒失效）；④ DB 前限流熔断（挂了时直接返回兜底页，别把库打穿）；⑤ 预热（大促前把热点数据提前灌入，避免开闸瞬间集体 miss）。
模块 3

一致性策略：延迟双删与 binlog 订阅

方案对比

方案机制残留脏数据窗口
先更新 DB，再删缓存Cache Aside 标准流极小概率：删缓存前一刻的读请求把旧值写回了缓存
先删缓存，再更新 DB删除后有请求读库写回旧值较大：更新 DB 前的所有读都会污染
延迟双删删缓存 → 更新 DB → 延迟 N 毫秒再删一次用延迟覆盖极小概率（N > 一次读库耗时）
binlog 订阅失效Canal/Debezium 订阅变更，异步删缓存毫秒级延迟，业务代码零侵入

延迟双删的实现要点

public void updateWithDoubleDelete(ProductVO vo) {
    redis.del("product:" + vo.getId());          // ① 先删
    productDao.update(vo);                        // ② 更新 DB
    // ③ 延迟再删：异步等一会儿，覆盖"删缓存与更新之间的旧读回填"
    delayExecutor.schedule(() -> redis.del("product:" + vo.getId()),
        500, TimeUnit.MILLISECONDS);              // 500ms > 读库+写缓存全流程
}
// 局限：延迟时间是猜的（太短漏删、太长浪费）；第二次删之前仍可能脏；
// 只缓解概率，不根治。一致性要求高就上 binlog 方案

binlog 订阅：最干净的方案

# 架构：MySQL → Canal/Debezium → MQ → 缓存失效服务 → 删 Redis
# 关键：失效的依据是"数据库真实变更"，不是业务代码自觉

# Canal 配置（canal.properties 核心项）
canal.instance.master.address = 10.0.1.10:3306
canal.instance.dbUsername = canal
canal.instance.dbPassword = ******
canal.mq.topic = db.binlog.product          # 变更发到 MQ

# 消费者：解析 binlog，删对应缓存 key
public void onBinlog(CanalEntry.Entry entry) {
    if (entry.getHeader().getTableName().equals("product")) {
        for (RowData row : entry.getRowChange().getRowDatasList()) {
            Long id = row.getAfterColumns(0).getValue();
            redis.del("product:" + id);            // 只删，不写缓存
            metrics.counter("cache.invalidate.binlog").increment();
        }
    }
}

# 代价：Canal/Debezium 集群运维；binlog 到删缓存有 100ms~1s 延迟；
# 好处：改代码忘删缓存也不会脏；分库分表时按 canal 的库表路由删对应 key
# 适用：一致性要求高 + 团队能养一套 CDC。普通系统 Cache Aside + TTL 已够
务实结论：① 默认 Cache Aside（先更库后删缓存）+ TTL，TTL 是最终兜底；② 删缓存失败要重试（本地队列 + 指数退避，或 binlog 补偿）；③ 一致性敏感数据（价格、库存）TTL 设短（分钟级）+ 发布时主动删；④ 余额类数据不要缓存，直接读库。追求强一致 + 缓存，逻辑上就是矛盾的。
模块 4

大 key / 热 key 治理

类型定义（经验阈值）危害
大 keyString > 10KB；Hash/ZSet/List > 5000 元素或 > 10MBDEL/过期时阻塞（异步删也占带宽）；主从同步单 key 阻塞；网络序列化慢
热 key单 key QPS > 5000，或占单节点流量 > 30%单节点 CPU 打满，集群倾斜；该节点故障时缓存雪崩加倍

大 key 的发现与拆分

# 发现（用 SCAN 不用 KEYS）
redis-cli --bigkeys                          # 抽样统计各类型最大 key
redis-cli --memkeys                          # 按内存排序
redis-cli --hotkeys                          # LFU 模式下找热 key

# 修复：拆分而非删除重建
# ✗ 反模式：一个 hash 存 100 万用户 -> product:all:users
# ✓ 拆成 product:users:{shard} 100 个，按 id % 100 路由
#   - 每个 key 1 万字段，读写都分散
#   - 批量操作用 pipeline 按 shard 分组执行

# 删除大 key：UNLINK 异步删；或 scan + 分批 DEL 控制节奏
UNLINK big:hash:100w                     # 不阻塞主线程

# 预防：写入侧拦截（客户端代理层或封装 RedisTemplate）
# - 单 value > 32KB 告警拒绝；集合 > 1 万元数告警
# - 上线前用规范 + 压测数据卡住，别等线上发现

热 key 的四种解法

本地缓存兜底（首选）。Caffeine 缓存热 key，TTL 1~5s。90% 请求在应用内消化，Redis 节点压力骤降。代价：秒级不一致。
key 复制散列。hotkey#1 ~ hotkey#100 多副本分布到不同节点，读随机选一个；写时全写 + 短 TTL。适合读远多于写的配置类数据。
value 拆分。热 key 的 value 拆成多个子 key（大 list 按段、hash 按字段组），请求打散到不同 slot。
迁移到本地/静态化。极热的配置、商品基础数据直接下发到客户端本地或推送到 CDN，根本不进 Redis。
# 热 key 检测三板斧
# 1. redis-cli --hotkeys（需 maxmemory-policy 为 allkeys-lfu，且是采样估计）
# 2. MONITOR 抓实时命令流（只用于短时排查，会拖慢实例）
# 3. 客户端埋点：代理层/RedisTemplate 封装统计 key 维度 QPS（生产推荐，最准）
# 4. 集群层：Proxy（Codis/twemproxy）或 Redis 7 的 CLIENT TRACKING + 慢查询分析
热 key 治理的顺序：先本地缓存（最简单有效），再复制散列，最后才考虑改架构。见过为治理一个热 key 把整个缓存层重构的——而那个 key 加个 3 秒本地缓存就解决了。先测量（key 级 QPS 监控），再治理，没有监控的热 key 治理都是玄学。
模块 5

缓存与数据库双写：组合策略

多级缓存下的失效传播

# 问题：更新了 DB 和 Redis，本地缓存（Caffeine）还是旧的！
# 更新流：
DB 更新 → 删 Redis → 通知所有应用实例删本地缓存 → 完成

# 通知两种方式：
# ① Redis Pub/Sub：发布 db-changed 消息，各实例订阅后清本地缓存
#   缺点：Pub/Sub 不持久化，实例不在线就漏消息（靠本地 TTL 兜底，要短）
# ② MQ 广播（推荐）：变更事件发 MQ，所有实例消费后清本地缓存
#   优点：持久化 + 重试，实例重启后补收；天然支持灰度

# Caffeine + MQ 组合的标准形态
@Bean
public Cache<Long, ProductVO> productCache() {
    return Caffeine.newBuilder()
        .maximumSize(100_000)               // 必须设上限！防 OOM
        .expireAfterWrite(Duration.ofSeconds(5))   // 短 TTL：本地一致性的最后防线
        .recordStats()                      // 命中率监控
        .build();
}

@RabbitListener(queues = "cache.invalidate.product")
public void onInvalidate(Long productId) {
    productCache.invalidate(productId);     // 收到广播，清本地
}
# 读路径：本地缓存 → Redis → DB，每层 miss 回填上层
# TTL 梯度：本地 5s < Redis 30min，本地短是设计核心（不一致窗口 = 本地 TTL）

Redis 集群下的缓存设计要点

要点做法
多 key 操作Cluster 只有同 slot 才能 MGET/MSET/Lua。用 hash tag {user1}:a {user1}:b 强制同槽，或拆成单 key pipeline
批量查询按节点分组 pipeline，避免 N 次往返；大集合用 SSCAN/HSCAN 游标
热点与集群热 key 复制后打散多节点；大 key 拆分本身就是天然的负载均衡
过期抖动批量写入设相同 TTL → 同批同秒过期 → 击穿叠加。TTL = base + random(0, 30%)
客户端缓存Redis 6+ client-side caching + tracking，服务端失效通知（需要客户端支持）
多级缓存的最大风险不是慢，是“不知道旧数据在哪一层”。线上排查“用户改了价格为什么还看到旧价”，要逐层确认：本地缓存清了吗？Redis 删了吗？CDN purge 了吗？治理手段：每一层都有监控指标（命中率、命中量）、每一次失效都有日志/事件、灰度环境能一键清全链路缓存。
模块 6

预热、降级与典型事故复盘

缓存预热

  • 大促前全量预热：离线任务把热点商品灌入 Redis（限量：只灌 TOP N 商品，全量灌会把 Redis 打爆且大部分不命中）
  • 本地缓存预热：启动时加载高频配置（黑名单、类目树），WarmUp 用限速加载防启动风暴
  • 实时预热：运营发布商品/改价时，主动触发对应 key 回填，而不是等自然 miss

缓存降级预案（Redis 故障时）

级别动作触发条件
L1 本地兜底读直接走本地缓存（容忍旧数据）Redis P99 > 50ms 或错误率 > 1%
L2 限流读库本地未命中直连 DB，入口限流到 DB 能扛的 QPSRedis 完全不可用
L3 服务降级非核心功能关闭（推荐、榜单），保核心链路DB 压力 > 70%
L4 兜底页静态兜底数据/默认值，保证不 500全链路过载

三个经典事故复盘

序列化不兼容
缓存里存 Java 序列化对象，类加了个字段，反序列化直接抛 InvalidClassException，所有读 miss 打穿 DB。处方：用 JSON/Protobuf，字段只加不减；类改动先发版缓存格式兼容版本。
大 value 撑爆带宽
某接口把 5000 商品的详情拼成一个 8MB JSON 塞 Redis，单 key 拉高节点内存和带宽，主从同步卡住。处方：value 拆多个 key + pipeline；设置 32KB 写入告警。
过期抖动
批量导入 10 万商品统一 TTL 1 小时，整点集体过期，DB 瞬时 10 万 QPS。处方：TTL 加 ±20% 随机；批量导入错峰；热点 key 提前续期。
序列化兼容性是缓存架构的隐形炸弹：缓存里躺着的旧格式数据，会在你升级反序列化库、改字段名、换 JDK 的那天集中爆炸。处方：① 只用自描述格式（JSON/Protobuf/MessagePack）；② 绝不用 Java 原生序列化/PDX 二进制做跨版本缓存；③ 升级时新旧格式共存一个版本周期。
模块 7

十个架构坑

1
用“更新缓存”代替“删缓存”
并发写会留脏值（A 写 v2、B 写 v3、缓存被 A 覆盖成 v2）。一律先更库后删缓存，删除是幂等的。
2
不设 TTL，把缓存当数据库
内存只增不减迟早 OOM；且数据永远旧。缓存数据必须 TTL，TTL 是一致性的最终兜底。
3
批量写入统一 TTL
同批 key 同秒过期，集体击穿 DB。TTL = base + random(0, 30% base)，错峰失效。
4
本地缓存 TTL 设太长
Caffeine 设 30 分钟，MQ 失效消息漏一条就旧半小时。本地缓存 TTL ≤ 10s，当 Redis 的减震层而不是数据源。
5
多级缓存只删了 Redis
本地缓存/CDN 还是旧数据，用户看到“改了没生效”。全链路失效要有事件广播 + 逐层 purge。
6
大 key 直接 DEL
同步删除阻塞主线程秒级，期间所有请求排队。UNLINK 异步删，或分批删。
7
热 key 无本地兜底
单 key 10 万 QPS 打一个节点，该节点 CPU 100% 拖慢全集群。热 key 加本地缓存 + 复制散列。
8
缓存 Java 序列化对象
类一升级反序列化崩，全线 miss 打穿 DB。用 JSON/Protobuf，升级时新旧格式共存过渡。
9
缓存不设上限（Caffeine/Guava）
maximumSize 不设，本地缓存无限增长直到 OOM。必须设 maximumSize + weight 策略。
10
没有缓存命中率监控
命中率从 95% 跌到 60% 没人发现，DB 压力悄悄翻倍。命中率、大 key 数、热 key 数、内存水位必须全部上监控。
自测

六道题

1. 更新商品价格时，缓存侧最稳妥的做法是？
正确答案：先更新数据库，再删缓存。删缓存是幂等的（失败可重试），而“更新缓存”在并发下会写脏（两个写线程交错覆盖）。异步同步 DB 会丢数据，不适合价格这类关键数据。
2. 一批 10 万商品在同一时刻被设置相同的 1 小时 TTL，最可能发生什么？
正确答案：集体过期打穿 DB。这就是“过期抖动”。解法：TTL 加随机值（1 小时 ± 10 分钟）、批量导入错峰、热点 key 提前续期。缓存雪崩的典型形态之一。
3. 关于布隆过滤器防缓存穿透，哪个说法准确？
正确答案：说"不存在"一定准，说"存在"可能误判（假阳性）。所以它拦掉的是"肯定不存在"的恶意流量，但误判放过的请求仍会 miss，通常还要配合缓存空值。它也无法删除元素、容量要预先规划。
4. 秒杀商品 key 在 10 万 QPS 下单节点 CPU 打满，最优先的治理手段是？
正确答案：本地缓存兜底。秒杀是典型读远多于写，本地缓存吸收 90%+ 读请求，成本最低见效最快。key 复制是补充手段。缩短 TTL 反而制造更多回源，是反向操作。
5. 多级缓存（本地 + Redis + CDN）架构下，数据更新后只删了 Redis，会导致？
正确答案：旧数据持续到各层 TTL 到期。各层缓存独立生效，删 Redis 不会传播到本地和 CDN。必须通过 MQ 广播 + CDN purge 做全链路失效，并把本地 TTL 压到秒级缩小不一致窗口。
6. 缓存里存储 Java 原生序列化的对象，最大的风险是？
正确答案：版本兼容噩梦。缓存在 TTL 内会长期驻留旧格式字节，类一升级全部 InvalidClassException。JSON/Protobuf 这类自描述格式加字段向后兼容，是缓存序列化的底线要求。
