开始前

三个案例，一套方法论

系统设计（System Design）不是"背架构图"，而是在给定约束下做取舍并说明理由。三个案例看起来毫不相干，但推演流程完全一样：

澄清需求。功能需求是什么？非功能需求（QPS、延迟、可用性、一致性）是什么？先问清楚再动手，这是所有案例的共同第一步。
容量估算。QPS、存储、缓存、带宽各是多少？把数字算出来，架构才有依据。这是新手最常跳过、也最加分的一步。
接口与数据模型。对外暴露什么接口？数据存成什么样？主键、索引、分片键怎么定？
核心方案对比。每个关键决策列出 2~3 个候选方案，讲清各自的代价，给出选择和理由。
瓶颈与演进。当前方案的瓶颈在哪？量级涨 10 倍，哪里先崩？这是区分"会做"和"想清楚了"的分水岭。
一个贯穿全篇的换算常数，背下来：一天 = 86400 秒 ≈ 105 秒。日均量 ÷ 105 ≈ 平均 QPS。例如"日均 1 亿请求"≈ 平均 1000 QPS。峰值再乘峰值系数（普通业务 3~5，大促可到几十倍）。这个心算能让你在任何场合秒答量级。
案例 1 · 短链

需求与容量估算

短链系统（URL Shortener）：把长 URL 压缩成一个短码，用户访问短链时跳转到原始地址，例如 https://s.cn/aB3xK9 → 原始长链接。

需求澄清

维度内容
功能需求① 输入长 URL 生成短码；② 访问短码 302 跳转；③ 可选：自定义短码、设置过期时间、访问统计
非功能需求① 读远多于写（读:写 ≈ 100:1）；② 跳转延迟要极低（< 50ms）；③ 短码不可枚举（不能被爬虫顺序扫）；④ 高可用（跳转挂了等于业务挂了）
规模假设每天新增 1000 万条短链，读写比 100:1

容量估算（把每一步都写出来）

# ---- 1. QPS ----
写：日均 10,000,000 条
     平均写 QPS = 10,000,000 / 86400 ≈ 116
     峰值写 QPS = 116 × 5（峰值系数）≈ 580

读：日均 10,000,000 × 100 = 1,000,000,000 次
     平均读 QPS = 1,000,000,000 / 86400 ≈ 11,574
     峰值读 QPS = 11,574 × 5 ≈ 57,870（约 5.8 万）

# 结论：这是一个典型的「读密集型」系统，优化的重心在读路径

# ---- 2. 存储 ----
每条记录大小估算：
  短码 7 字节 + 长 URL 平均 200 字节 + 创建时间/用户ID/过期时间等元数据 ≈ 500 字节

3 年数据量 = 10,000,000 × 365 × 3 = 10,950,000,000 条（约 109.5 亿）
总存储 = 109.5 亿 × 500 字节 ≈ 5.5 TB

# 结论：单机 MySQL 放不下，必须分库分表；或冷热分层，老数据归档

# ---- 3. 缓存内存 ----
按二八定律：20% 的数据承担 80% 的访问
若只缓存最近 7 天：10,000,000 × 7 = 7000 万条
缓存单条 ≈ 短码 7 + URL 200 + Redis 对象开销 ≈ 300 字节
缓存内存 = 70,000,000 × 300 字节 ≈ 21 GB

# 结论：21GB 需要 Redis 分片（单实例 21GB 风险高），或缓存更短的时间窗口

# ---- 4. 带宽 ----
峰值读 5.8 万 QPS，每次跳转响应体极小（302 状态行 + Location 头 ≈ 300 字节）
峰值出带宽 ≈ 57,870 × 300 字节 ≈ 17 MB/s ≈ 140 Mbps
# 结论：带宽不是瓶颈，短链的响应体极小
容量估算的三个产出：① 读 QPS 5.8 万 → 必须用缓存扛读；② 存储 5.5 TB → 必须分库分表；③ 缓存 21 GB → Redis 要分片。每一个数字都直接指向一个架构决策，这就是"先算再做"的意义。
案例 1 · 短链

短码生成、读写路径与缓存

短码生成方案对比（核心决策）

方案原理优点 / 代价
自增 ID 转 62 进制全局自增 ID（MySQL 自增 / Redis INCR / 号段模式），把数字转成 62 进制字符优点：无冲突、长度短且可控、生成快。代价：顺序递增可被枚举（爬虫能顺扫）；需要发号器
哈希（MD5/SHA 截断）对长 URL 做哈希，取前 N 位优点：无状态、相同 URL 得到相同短码（天然去重）。代价：有冲突，需加盐重试或用布隆过滤器；长度固定不可压缩
随机字符串生成随机字符，查库确认不冲突优点：不可枚举。代价：需查重（多一次读）、随机数依赖；短码越短冲突概率越高
号段模式（推荐组合）发号器一次取一段 ID（如 1~1000）缓存在内存，用完再取，减少发号器压力优点：性能高、不依赖每请求都打 DB。代价：进程重启会浪费一段号（无所谓）
# 62 进制的容量（a-z A-Z 0-9 共 62 个字符）
62^6 = 568 亿     # 6 位够用很久
62^7 = 3.5 万亿   # 7 位基本用不完

# 自增 ID 转 62 进制示例
ID = 123456789  →  62 进制 = "8m0Kx"

# 缓解「可枚举」：在 ID 上做可逆混淆（如异或一个常数、位重排）
# 混淆后仍是唯一、无冲突的，但顺序被打乱，无法顺扫
obfuscated = id XOR 0x5DEECE66D
short_code = base62(obfuscated)

# 推荐组合：号段模式发号 + 混淆 + 62 进制 → 短、无冲突、不可枚举

写路径

# 生成短链（写）
1. 校验长 URL 合法性（格式、长度上限、是否恶意/黑名单）
2. 可选查是否已存在（去重；用哈希方案时天然去重）
3. 向发号器取一个全局唯一 ID（号段模式：内存里取）
4. ID 混淆 → 转 62 进制 → 得到短码
5. 写入 DB：短码为主键（或唯一索引），存长 URL + 元数据
6. 写入缓存（可选，写时预热）
7. 返回短链 https://s.cn/{short_code}

# 关键：短码作为主键 / 唯一索引，天然防止重复写入

读路径（重点优化对象）

# 访问短链（读，QPS 是写的 100 倍）
1. 收到短码
2. 查缓存 → 命中 → 返回 302 + Location: 原始 URL  （绝大多数请求走到这里就结束了）
3. 未命中 → 查 DB → 回填缓存（Cache Aside）→ 返回 302
4. 查不到 → 返回 404 或默认页

# 302 还是 301？
302（临时重定向，推荐）：浏览器每次都来问，服务端能统计访问量、能随时改目标
301（永久重定向）：浏览器会缓存，减少服务端压力，但失去统计能力、且改动不生效

缓存策略

  • Cache Aside（旁路缓存）：读时先查缓存、未命中查库回填；写时先写库再删缓存。短链数据几乎不变，所以写冲突极少。
  • TTL 设置：短链数据不可变，可以设长 TTL（如 7 天）甚至"永不过期 + LRU 淘汰"，让热点自然留在内存里。
  • 穿透防护：不存在的短码会被反复查询打库，需缓存空值或布隆过滤器兜底。
  • 热点 key：极少数爆款短链（如分享到社交平台的）会形成热 key，可加本地缓存（Caffeine）做多级缓存。
最容易翻车的一个细节：短码可枚举。如果短码就是 1, 2, 3... 的 62 进制，爬虫可以从 "1" 顺序扫到 "zzzzzz"，把全站链接爬光。解法是混淆或随机化短码。另一个细节：发号器本身会成为写路径的单点，所以号段模式（一次取一批）比每请求打一次 Redis 更稳。
案例 1 · 短链

瓶颈与演进：量级涨 10 倍先崩哪

组件当前状态涨 10 倍后（读 58 万 QPS）
缓存 Redis21GB，需分片先崩。单实例扛不住 58 万 QPS + 21GB。解法：Redis Cluster 分片，或加本地缓存挡掉大部分读
数据库5.5TB，需分库分表读请求大部分被缓存挡住，DB 压力可控；但缓存未命中时的回源会放大。解法：读写分离 + 按短码哈希分片
发号器号段模式，内存取号写 QPS 5800，号段模式仍能扛。若换成每请求打 Redis 的方案，这里先崩
网络 / 带宽140 Mbps1.4 Gbps，仍不是瓶颈（响应体太小）
跳转延迟< 50ms跨机房回源会拖慢。解法：把热点短链推到 CDN / 边缘节点，就近跳转
短链案例的三个通用结论：① 读密集型系统，缓存是第一优先级；② 不可枚举是短码生成方案的硬约束，顺序 ID 必须混淆；③ 发号器是高并发写路径的隐藏单点，号段模式是标准解法。这三点可以直接迁移到任何"生成唯一短标识"的场景。
案例 2 · 秒杀

核心难点与分层削流

秒杀系统：在极短时间内（如 1 秒内）涌入海量用户抢购有限库存。核心难点就三个：超卖、瞬时高并发、防刷。

需求澄清

维度内容
功能需求① 展示商品和库存；② 抢购下单；③ 支付；④ 未支付超时释放库存
非功能需求① 绝不超卖（超卖 = 事故，必须赔付）；② 能扛瞬时百万级 QPS；③ 防脚本刷单；④ 下单接口要快（用户感知）
规模假设商品库存 1000 件；秒杀开始瞬间涌入 100 万请求

量级估算

# 100 万请求集中在 1 秒内 → 瞬时 QPS = 1,000,000
# 但真正需要落库的只有 1000 单（库存数量）

# 核心思路：把 100 万请求削成 1000 次真实下单
削减比 = 1,000,000 / 1000 = 1000 : 1
# 也就是 99.9% 的请求应该在到达数据库之前就被挡掉

# 如果 100 万请求全部打到数据库：
数据库瞬间被打死，整个系统雪崩
# 所以秒杀架构的本质 = 分层限流 + 异步削峰

分层削流：把请求一层层减下去

层次手段削掉多少
1 前端按钮置灰（防重复点击）、秒杀开始前禁止提交、随机延迟提交过滤掉重复点击
2 页面静态化商品详情页静态化推 CDN，秒杀开始前用户刷的是 CDN 静态页，不打后端把浏览流量全部挡在 CDN
3 验证码 / 答题下单前先做验证码或简单算术题，过滤掉脚本、拉长请求时间挡掉大部分机器流量
4 网关限流令牌桶 / 漏桶算法，只放固定速率的请求进来（如 1 万 QPS），超出直接拒绝把 100 万削到 1 万
5 应用层限流按用户维度（同一用户限 1 次）、按商品维度限流进一步削峰
6 库存前置库存放 Redis，不查数据库判断是否有货，无货直接返回"已售罄"把有货判断变成内存操作
7 消息队列Redis 预扣成功的请求发到 MQ，异步创建订单削峰填谷，保护数据库
分层削流的核心思想：让每一层只处理"该层能处理"的流量。CDN 处理浏览、验证码挡脚本、网关限流削峰、Redis 判断库存、MQ 异步落库。最终只有等于库存数量的请求会真正写数据库。这和"给数据库加机器"是完全不同的思路 —— 前者是架构，后者是堆资源。
案例 2 · 秒杀

库存扣减方案对比与超卖解法

三种库存扣减方案对比

方案做法优点 / 代价
数据库行锁直接 UPDATE ... WHERE stock > 0 靠 DB 行锁保证原子优点：简单、绝对不超卖。代价：行锁竞争严重，高并发下大量请求排队，DB 扛不住
Redis 预扣用 Lua 脚本在 Redis 里原子判断并扣减优点：内存操作、高并发、极快。代价：要处理 Redis 与 DB 的一致性；Redis 挂了要有兜底
MQ 异步下单Redis 扣减成功后发消息，消费者异步创建订单 + 扣 DB 库存优点：削峰、解耦、用户体验快（返回"排队中"）。代价：最终一致，需要处理消息丢失/重复
生产方案通常是三者组合：Redis 预扣（挡掉 99.9%）→ MQ 异步（削峰）→ DB 落库（最终一致）。Redis 是"快速过滤器"，DB 是"最终账本"。

超卖的根本原因

超卖 = "读-判断-写"三步不是原子操作。
库存 = 1，两个请求同时进来：
请求 A 读到 stock = 1 → 判断 > 0 → 准备扣减
请求 B 读到 stock = 1 → 判断 > 0 → 准备扣减
两个都判断通过 → 都执行扣减 → stock 变成 -1，卖出了 2 件。
根因：并发下"判断有货"和"扣减库存"之间存在时间窗口，两个请求都通过了判断。解法只有一个方向：让"判断 + 扣减"变成一步原子操作。

解法一：数据库原子更新（不超卖的最强保证）

-- 把「判断」写进 WHERE 条件，让数据库的行锁保证原子性
UPDATE seckill_stock
SET stock = stock - 1
WHERE item_id = 1001 AND stock > 0;

-- 关键：检查 affected rows（受影响行数）
-- = 1 → 扣减成功，可以下单
-- = 0 → 库存已为 0，售罄，拒绝
-- 这一条 SQL 本身就不会产生超卖，因为 WHERE stock > 0 和 SET 在同一个原子操作里

-- 乐观锁版本（另一种原子写法）
UPDATE stock
SET stock = stock - 1, version = version + 1
WHERE item_id = 1001 AND version = #{oldVersion} AND stock > 0;

解法二：Redis + Lua 原子扣减（高并发首选）

-- Redis 的 Lua 脚本整体原子执行，中间不会被打断
-- KEYS[1] = 库存 key，例如 seckill:stock:1001

local stock = redis.call('GET', KEYS[1])
if not stock then
  return -1          -- 库存 key 不存在
end
if tonumber(stock) <= 0 then
  return 0           -- 已售罄
end
redis.call('DECR', KEYS[1])
return 1             -- 扣减成功

-- 调用方式（Java 伪代码）：
-- Long result = redis.eval(luaScript, Collections.singletonList("seckill:stock:1001"));
-- if (result == 1) { 发消息到 MQ 异步下单 } else { 返回"已售罄" }

# 为什么必须用 Lua？
✗ 错误：先 GET 判断，再 DECR —— 两条命令之间有窗口，并发下超卖
✓ 正确：Lua 脚本整体原子执行，判断和扣减不可分割

Redis 与数据库的一致性

  • Redis 预扣成功但落库失败怎么办？ 靠 MQ 重试 + 幂等（用唯一订单号去重），保证最终一致。
  • Redis 挂了怎么办？ 降级到数据库原子更新（慢但正确），或直接返回"系统繁忙"。绝不能因为 Redis 挂了就放行所有请求。
  • 怎么防止少卖？ 未支付订单超时释放库存时，要同时回补 Redis 和 DB，且回补要幂等（防止重复回补导致超卖）。
案例 2 · 秒杀

订单状态机与演进：涨 10 倍先崩哪

订单状态机

状态含义转移条件
待支付下单成功，占用库存，等待付款用户支付 → 已支付；超时未付 → 已取消
已支付付款成功，库存真正消耗发货 → 已完成；退款 → 已退款
已取消超时未支付，库存需回补终态
已关闭风控/系统关闭的订单终态

超时取消的实现

# 方案一：Redis ZSet 延时队列（轻量）
ZADD order:delay <到期时间戳> <orderId>
# 后台任务轮询：
ZRANGEBYSCORE order:delay 0 <当前时间戳> LIMIT 0 100
# 取出到期的订单 → 取消 + 回补库存 → ZREM

# 方案二：MQ 延时消息（RabbitMQ TTL+DLX / RocketMQ 延时消息）
# 下单时发一条 15 分钟后投递的消息，消费者收到就取消订单

# 方案三：定时扫表（最简单，但大表下慢）
SELECT * FROM orders WHERE status = '待支付' AND created_at < NOW() - INTERVAL 15 MINUTE;
# 需要 status + created_at 联合索引，且要分页避免全表扫

# 回补库存必须幂等：用「已回补」标记或唯一约束防止重复回补
UPDATE stock SET stock = stock + 1 WHERE item_id = 1001 AND order_id = ? AND released = 0;
超时取消的两个坑：① 回补不幂等 —— 消息重复投递导致库存被回补两次，反而超卖；② 取消和支付并发 —— 用户在第 14 分 59 秒支付，同时定时任务在取消。必须用状态机 + CAS（Compare And Swap，比较并交换）保证只有一个操作成功：UPDATE orders SET status='已支付' WHERE id=? AND status='待支付'。

瓶颈与演进：量级涨 10 倍

组件涨 10 倍后的瓶颈解法
Redis 库存 key先崩。单个商品的库存 key 是超级热 key，1000 万 QPS 全打到一个分片库存分桶：把 1000 库存拆成 10 个桶各 100，请求随机打到一个桶，分散热点
MQ消息量暴增，消费跟不上导致积压增加消费者、分区扩容；用 Kafka 分区提高并行度
数据库写入订单表写入量大分库分表（按订单 ID 或用户 ID）；异步写 + 批量提交
网关限流限流阈值本身成为配置热点限流规则本地化 + 定期拉取，避免每次限流都查配置中心
秒杀案例的三个通用结论：① 绝不超卖靠的是原子操作（DB 的 WHERE stock > 0 或 Redis 的 Lua）；② 分层削流比堆机器有效，让每一层只处理它该处理的流量；③ 热 key 要用分桶打散，一个商品的库存不能只放一个 key。
案例 3 · 排行榜

需求、为什么用 ZSet 与数据结构

排行榜：实时展示用户按某种分数（积分、票数、销售额）的排名，支持查前 N 名、查某人排名、查某区间。

需求澄清

维度内容
功能需求① 实时更新分数；② 查 Top N；③ 查某用户的排名和分数；④ 查区间（第 100~200 名）；⑤ 多维度榜（日榜 / 周榜 / 总榜）
非功能需求① 排名要实时（不能是 T+1 离线）；② 更新要快（每次加分都要反映）；③ 查询要快（< 10ms）
规模假设1000 万用户参与排名

为什么用 Redis ZSet

操作ZSet 复杂度说明
插入 / 更新分数O(log N)底层是跳表（skiplist），插入时维护有序性
查排名 ZRANKO(log N)直接返回名次，不用扫全表
取 Top N ZREVRANGEO(log N + M)M 是返回条数，从跳表尾部倒序取
按分数区间查O(log N + M)ZRANGEBYSCORE，天然的区间查询
为什么不用 MySQL？排行榜每次更新分数，如果用 ORDER BY score DESC LIMIT 10 实时查，在千万行数据上即便有索引也要几十到几百毫秒，且每次查询都消耗数据库 CPU。排行榜是"写少读多 + 需要有序 + 需要实时排名"的典型场景，正是 ZSet 的主场。MySQL 只适合做离线的全量榜或最终持久化。

数据结构设计

# 核心：一个 ZSet 就是一张榜
# member = 用户 ID，score = 分数
ZADD rank:20261015 1000 "user:1001"
ZADD rank:20261015 2500 "user:1002"
ZADD rank:20261015 1800 "user:1003"

# 取前 10 名（带分数）
ZREVRANGE rank:20261015 0 9 WITHSCORES

# 查某人的排名（ZREVRANK 从高到低，返回 0-based）
ZREVRANK rank:20261015 "user:1001"     # 返回 2，表示第 3 名

# 加分（原子操作）
ZINCRBY rank:20261015 50 "user:1001"

# 取区间：第 100~200 名
ZREVRANGE rank:20261015 99 199 WITHSCORES

# 多维度榜：用不同的 key 区分
rank:daily:20261015    # 日榜
rank:weekly:2026W42    # 周榜
rank:all               # 总榜
同分怎么办？ ZSet 的 score 相同时，按 member 的字典序排。如果业务要求"同分先到者排前"，就要把 score 设计成组合值：
score = 真实分数 × 10^10 + (10^10 - 到达时间戳)
这样分数高的排前，同分时时间早的（时间戳小 → 补数大）排前。关键：分数部分要占足够高位，避免和时间部分串位。
案例 3 · 排行榜

分片聚合、深翻分页与演进

分片与聚合：大榜拆小榜

1000 万用户的单个 ZSet 会有内存和热点压力。拆分思路有两种：

方案做法代价
按用户 ID 哈希分片拆成 N 个小榜（如 16 个），每个榜放一部分用户查全局 Top N 时要从 N 个榜各取 Top N 归并（聚合）
只维护 Top NRedis 里只保留前 1000 名，全量榜放数据库/离线计算查榜外用户排名要另算；但内存和性能最优
两级榜Redis 存热榜（Top N），MySQL 存全量；定期从全量重算热榜榜单有延迟；重算有成本
# 聚合示例：从 16 个分片榜取全局 Top 10
# 1. 每个分片取自己的 Top 10（并行查询）
ZREVRANGE rank:shard:0 0 9 WITHSCORES
ZREVRANGE rank:shard:1 0 9 WITHSCORES
... （16 个分片）

# 2. 应用层归并 16 × 10 = 160 条，取分数最高的 10 条
# 3. 返回给用户

# 优化：如果只需要 Top 10，每个分片取 Top 10 就够（数学上保证）
# 但如果是「查某人全局排名」，就得遍历所有分片查 ZREVRANK 再累加
# → 这就是分片的代价：全局排名查询变贵

分页深翻问题

深翻（Deep Pagination）指翻到很后面的页，例如"第 10000 页"。用 ZREVRANGE key 99990 99999 虽然 Redis 内部是 O(log N + M)，但 start 很大时仍要定位跳表节点，且"翻到第 10000 页"这种需求本身往往是无意义的（没人真会看第 10000 页）。
更好的方案：用分数游标替代 offset。记住上一页最后一条的 score，下一页用 ZREVRANGEBYSCORE key (lastScore -inf LIMIT 0 10 继续取。这样每次都从游标处继续，不随页码变深而变慢。缺点：不能随机跳到任意页。 
# 游标分页（推荐）：不随页码加深而变慢
# 第一页
ZREVRANGEBYSCORE rank:all +inf -inf LIMIT 0 10
# 记下最后一条的 score = 1850

# 下一页：取分数小于 1850 的
ZREVRANGEBYSCORE rank:all (1850 -inf LIMIT 0 10

# 对比 offset 分页（不推荐深翻）
ZREVRANGE rank:all 99990 99999   # 页码越深越慢

持久化与重建

  • Redis 内存数据不可靠：重启、主从切换都可能丢数据，所以 ZSet 不能是唯一数据源。
  • 持久化策略：Redis 开 AOF/RDB 只是缓解；真正的权威数据应落在数据库（如用户积分表）。
  • 重建方式：日榜可以在每天零点用定时任务从流水/积分表全量重算一次；或增量地从变更日志（binlog/消息）重放。
  • 双写一致性：加分时同时写 DB 和 Redis（DB 为准）；Redis 丢了就从 DB 重建。

瓶颈与演进：量级涨 10 倍

组件涨 10 倍后（1 亿用户）解法
单个 ZSet先崩。1 亿成员的 ZSet 内存巨大且成为热点按用户哈希分片成几十个小榜；或只保留 Top N 热榜
全局排名查询要遍历所有分片，延迟累加预聚合、定期把全局排名刷进一张"排名快照"表
写放大每次加分都是 ZINCRBY，高频写本地聚合后批量写（如每 100ms 合并一次加分）
持久化大 ZSet 的 RDB 快照耗时长在从库做持久化；分片后每个实例数据量下降
排行榜案例的三个通用结论：① "有序 + 实时排名"用 ZSet 是标准答案；② 分片能扩展容量，但代价是全局排名变贵，要权衡；③ 深翻分页用分数游标替代 offset，这是所有有序集合分页的通用技巧。
常见坑

跨案例的十个通用陷阱

这三个案例共享同一批"看起来对、实际会翻车"的设计陷阱。它们几乎出现在所有系统设计里。

1
只算平均 QPS，不算峰值
用日均 QPS 做容量规划，高峰必崩。容量必须按峰值（均值 × 峰值系数）规划，且留冗余。这是短链、秒杀、排行榜共同的第一个坑。
2
短码用顺序自增，导致可枚举
爬虫从短码 1 顺序扫到最大，全站链接被爬光。必须对 ID 做混淆或使用随机短码。
3
把 301 当 302 用（或反之）
301 永久重定向会被浏览器缓存，失去统计能力且改动不生效；302 临时重定向才能统计和随时改目标。短链默认用 302。
4
秒杀库存只放 Redis，不做 DB 兜底
Redis 挂了或数据丢失，库存判断失效，要么全放行（超卖）要么全拒绝（业务损失）。DB 必须是最终账本，Redis 只是快速过滤器。
5
Redis 扣库存不用 Lua，先 GET 再 DECR
两条命令之间有窗口，并发下超卖。判断和扣减必须在同一个 Lua 脚本里原子执行。
6
超时订单回补库存不幂等
消息重复投递导致库存被回补多次，反而超卖。回补必须带幂等标记（唯一约束或 released 字段）。
7
排行榜用 MySQL 实时 ORDER BY 查
千万行上每次查询几十到几百毫秒，且消耗 DB CPU。实时有序排名是 ZSet 的活，MySQL 只做离线全量榜。
8
排行榜同分没有二级排序
同分时排名不稳定，用户会看到自己的名次跳动。要么把时间戳编进 score，要么明确业务接受按 member 字典序。
9
缓存与数据库双写不一致
先更新库再更新缓存（并发写脏），或先删缓存再更新库（读回旧值）。正确姿势是 Cache Aside：先更新库，再删缓存，配合 TTL 兜底。
10
热点 key 不做分桶
一个爆款商品的库存、一个爆款短链的缓存，会把单个分片的 CPU 打满。库存要分桶、热缓存要加本地缓存，把热点打散。
自测

六道题

1.（短链）日均 1 亿次跳转，读写比 100:1。平均读 QPS 大约是多少？
正确答案：约 1157。1 亿 / 86400 ≈ 1157。记住"一天 ≈ 105 秒"，日均量除以 105 就是平均 QPS。峰值还要再乘峰值系数（3~5）。
2.（短链）为什么短码生成不推荐直接用顺序自增 ID？
正确答案：可被枚举。顺序短码可被爬虫从 1 顺序扫描。解法是对 ID 做可逆混淆（异或 + 位重排）或使用随机短码，既保持唯一无冲突，又不可顺扫。
3.（秒杀）库存为 1，两个请求并发扣减，结果库存变成 -1。根本原因是？
正确答案：非原子操作。两个请求都读到 stock=1、都判断 >0、都扣减。解法是让判断和扣减原子化：DB 用 UPDATE ... WHERE stock > 0，Redis 用 Lua 脚本。
4.（秒杀）用 Redis 扣库存，为什么必须用 Lua 脚本而不是 GET 后再 DECR？
正确答案：Lua 原子执行。分开的 GET + DECR 两条命令之间存在时间窗口，并发下会超卖。Lua 脚本作为一个整体执行，中间不被打断，保证判断和扣减的原子性。
5.（排行榜）实现实时排行榜，为什么首选 Redis ZSet 而不是 MySQL？
正确答案：ZSet 的跳表结构。ZSet 支持 O(log N) 的插入、查排名、取区间，天然适合"实时有序排名"。MySQL 每次实时 ORDER BY 都要消耗大量 CPU 且延迟高，只适合做离线全量榜。
6.（排行榜）排行榜翻到很后面的页（如第 10000 页），更好的做法是？
正确答案：分数游标分页。offset 越深定位成本越高且这种需求本身无意义。用上一页最后一条的 score 作为游标，用 ZREVRANGEBYSCORE key (lastScore -inf LIMIT 0 10 继续取，成本恒定。缺点是不能随机跳页。
