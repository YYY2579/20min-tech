开始前

先建立正确预期

GoF（《Design Patterns》四位作者 Gang of Four）1994 年提出 23 个模式时，主流语言还没有泛型、没有闭包、没有函数式编程。很多当年要手写几十行的模式，今天语言特性一行就能表达。

常见误解工程现实
“学完 23 个模式就能写出好架构”模式是命名和沟通工具，不是架构能力本身。先有问题，再有模式，不要反向操作
“代码里每处都要套个模式”多数业务代码一个 if/else 或一个函数指针就够了。模式的成本是类数量暴涨
“不用模式 = 代码烂”Spring 的 RestTemplate 内部是模板方法，Controller 是门面。你早就在用模式，只是没写类图
“面试要手写单例”手写只是门槛，真正的题是“单例在 Spring 容器下为什么是反模式”（见模块 2）
本篇立场：按“实战价值排序”组织，不讲 UML 类图，只讲每个模式解决什么问题、在什么代码里出现、坑在哪。23 个模式在模块 1 给全景表，之后只讲高频的 10 个。

模块 2

单例：手写、枚举、与 Spring 下的反模式

单例是面试保留节目，但真正的分水岭是理解“容器单例 vs 手写单例”的区别。

双重检查锁（DCL）的标准写法

// Java：DCL 必须加 volatile，否则可能拿到半初始化对象
public class ConfigHolder {
    // volatile 两个作用：① 可见性 ② 禁止指令重排（new 分三步：分配内存/初始化/赋值引用）
    private static volatile ConfigHolder instance;

    private ConfigHolder() {}

    public static ConfigHolder getInstance() {
        if (instance == null) {            // 第一次检查：避免每次加锁
            synchronized (ConfigHolder.class) {
                if (instance == null) {    // 第二次检查：避免重复创建
                    instance = new ConfigHolder();
                }
            }
        }
        return instance;
    }
}

// 没有 volatile 的后果：线程 A 执行到"已分配内存、还没初始化"，
// 线程 B 第一次检查通过，直接拿到引用去用 → NPE 或读到默认值

为什么枚举是实现单例的最优解

// Effective Java 作者 Joshua Bloch 推荐写法
public enum Singleton {
    INSTANCE;

    public void doSomething() { /* ... */ }
}

// 优点：JVM 保证枚举实例唯一；自动防反射攻击（反射 newInstance 对枚举直接抛异常）；
// 自动支持序列化（不会因反序列化创建新实例）；写法三行搞定

Spring 容器下，手写单例是反模式

维度手写单例（DCL）Spring 单例 Bean（默认 scope）
可测试性差。静态状态无法在测试间隔离，无法 mock好。注入即可替换，测试用另一个 profile 直接覆盖
生命周期无初始化/销毁钩子有完整的 @PostConstruct / @PreDestroy
依赖管理只能硬编码 new 或再掏一个静态 ServiceLocator声明式注入，依赖图由容器管理
隐藏耦合类内部 Singleton.getInstance() 是隐式全局依赖，调用方看不出构造器注入让依赖显式化，读构造函数就知道依赖什么
结论：在 Spring/Guice 这类 DI 容器里，永远不要手写单例。把类声明成普通 Bean，容器默认就是单例（singleton 是默认 scope），且线程安全由容器保证。手写单例的每一个理由（唯一实例、延迟加载）容器都更好地解决了。

反例场景：只有当你写的是不被容器管理的库代码（给第三方 SDK、JDK 内部的工具类）才考虑手写，且首选枚举。
模块 3

工厂家族与“策略+工厂”消灭 if-else

三种工厂的分工

模式解决什么典型代码
简单工厂一个方法按参数创建不同产品。不是 GoF 模式，但最常用Shape create(String type)
工厂方法把创建延迟到子类，新增产品 = 新增工厂类，符合开闭原则LoggerFactory.newLogger()
抽象工厂创建产品族（如 Win/Mac 两套 Button+Checkbox），换整套实现UIFactory.createButton()

策略模式：消灭 if-else 的标准武器

// ===== 反模式：每年都在长的 if-else =====
public class PriceCalculator {
    public double calc(User user, double amount) {
        if (user.getLevel().equals("VIP")) {
            return amount * 0.8;
        } else if (user.getLevel().equals("SVIP")) {
            return amount * 0.7;
        } else if (user.getLevel().equals("NEW") && amount > 100) {
            return amount - 20;
        }
        return amount;
    }
}
// 问题：每加一个等级改一次这个类；分支条件互相耦合；单测要覆盖所有分支组合

// ===== 策略模式 =====
public interface DiscountStrategy {
    String level();
    BigDecimal calc(BigDecimal amount);
}

public class VipStrategy implements DiscountStrategy {
    public String level() { return "VIP"; }
    public BigDecimal calc(BigDecimal amount) { return amount.multiply(new BigDecimal("0.8")); }
}
// SVIPStrategy、NewUserStrategy 同理，各自一个类

// ===== 策略工厂：用 Map 注册表代替 if-else =====
public class DiscountFactory {
    private final Map<String, DiscountStrategy> registry = new HashMap<>();

    public DiscountFactory(List<DiscountStrategy> strategies) {  // Spring 注入所有实现
        for (DiscountStrategy s : strategies) registry.put(s.level(), s);
    }

    public DiscountStrategy get(String level) {
        DiscountStrategy s = registry.get(level);
        if (s == null) throw new IllegalArgumentException("未知等级: " + level);
        return s;
    }
}
// 新增等级 = 新增一个 @Component 类，老代码一行不改（开闭原则）

Go 的等价写法（没有继承，用函数+map）

// Go 惯用法：策略本质就是函数，不需要类层级
type DiscountFunc func(amount float64) float64

var strategies = map[string]DiscountFunc{
    "VIP":  func(a float64) float64 { return a * 0.8 },
    "SVIP": func(a float64) float64 { return a * 0.7 },
}

func Calc(level string, amount float64) (float64, error) {
    f, ok := strategies[level]
    if !ok {
        return 0, fmt.Errorf("未知等级: %s", level)
    }
    return f(amount), nil
}

TypeScript：策略 + 泛型，类型也安全

// TS：策略用类型收窄，编译期就能发现漏掉的等级
type Level = 'VIP' | 'SVIP' | 'NEW';
interface Strategy { calc(amount: number): number }
const registry: Record<Level, Strategy> = {
  VIP:  { calc: a => a * 0.8 },
  SVIP: { calc: a => a * 0.7 },
  NEW:  { calc: a => a > 100 ? a - 20 : a },
};
// Record 强制每个等级都必须实现，编译期杜绝漏分支
什么时候 if-else 才是对的：① 分支 ≤ 2 且稳定不变；② 分支逻辑本身是同一函数内的两三行；③ 只是参数解析。模式是给“会持续增长的分支”准备的——为一个不会变的 if-else 建 6 个类就是纯粹的过度设计。
模块 4

观察者与事件总线：解耦的双刃剑

观察者模式解决“一个动作触发多个下游反应”。框架化之后就是事件总线。

经典观察者

public interface OrderEventListener {
    void onOrderPaid(OrderPaidEvent event);
}

public class OrderService {
    private final List<OrderEventListener> listeners = new CopyOnWriteArrayList<>();

    public void register(OrderEventListener l) { listeners.add(l); }

    public void pay(Long orderId) {
        // ... 核心支付逻辑（事务内）
        for (OrderEventListener l : listeners) {  // 通知在事务提交后做，见坑 #6
            l.onOrderPaid(new OrderPaidEvent(orderId));
        }
    }
}
// 库存服务、积分服务、短信服务各自注册 listener —— 支付完成后自动触发
// 加一个"发优惠券"下游 = 新增一个 listener，OrderService 不用改

框架化：Spring 事件 / Guava EventBus

// Spring：发布端零依赖，注解即可
@Service
public class OrderService {
    @Autowired private ApplicationEventPublisher publisher;

    @Transactional
    public void pay(Long orderId) {
        // ... 支付逻辑 ...
        publisher.publishEvent(new OrderPaidEvent(orderId));  // 默认同步执行
    }
}

@Component
public class SmsSender {
    @EventListener
    @Async  // 关键：不加这个，listener 异常会回滚支付事务！
    public void handle(OrderPaidEvent e) { /* 发短信 */ }
}
形态同步/异步可靠性适用
进程内 EventBus（Guava）同步无（进程崩了全丢）同进程解耦，非关键下游
Spring @Async 事件异步（线程池）无（重启丢、队列满丢）通知类、可容忍丢失
MQ 事件（Kafka/RocketMQ）异步高（持久化+重试）跨服务、不能丢的事件
本地事务发件箱 outbox异步最高（与业务同库事务）金融级“业务成功=事件必发”
观察者的三个暗坑：① 同步 listener 抛异常会中断主流程——支付成功后发短信失败导致接口报错，用户以为支付失败；② 响应延迟叠加——5 个同步 listener 各花 50ms，接口就多 250ms；③ 调试断点打不进——发布方看不到谁订阅了，全项目搜索事件类名是常态。

规则：关键路径不同步通知，通知不关心结果，跨进程必须走 MQ。更详细的事件可靠性设计见本期《事件驱动架构》。
模块 5

适配器、防腐层与代理

适配器：不只是“接口转换”

// 场景：你的系统用 User 模型，第三方 SDK 用 CustomerDTO，字段名/类型全不一样
public interface UserClient {            // 你的领域语言
    User findById(Long id);
}

public class ThirdPartyUserClientAdapter implements UserClient {
    private final CustomerSdk sdk;      // 第三方的、会变的东西

    public User findById(Long id) {
        CustomerDTO dto = sdk.query(id);   // 字段映射、异常转换、默认值填充都关在这里
        return new User(dto.getCid(), dto.getCname(), "86-" + dto.getPhone());
    }
}
// 价值：第三方 SDK 换供应商/改字段，只改 Adapter 一个类，业务代码零感知

当适配的对象是另一个限界上下文/外部系统时，它就升级为架构级模式——防腐层（Anti-Corruption Layer, ACL）。详细见本期《领域驱动设计实战》。

代理：静态、动态与 AOP 的本质

类型机制例子
静态代理编译期写死，一个接口一个代理类手写的 LoggingUserService 包住 UserService
JDK 动态代理运行时生成代理类，只能代理接口Spring AOP 默认方式，Proxy.newProxyInstance
CGLIB/ByteBuddy运行时生成子类字节码，可代理普通类Spring 对无接口的 Bean 自动启用；final 类不可代理
// AOP 的本质：把"横切关注点"从核心逻辑里剥离，用代理统一注入
@Around("@annotation(Retryable)")
public Object retry(ProceedingJoinPoint pjp) throws Throwable {
    int max = 3;
    for (int i = 1; i <= max; i++) {
        try { return pjp.proceed(); }
        catch (Exception e) {
            if (i == max) throw e;
            // 指数退避重试
            Thread.sleep(Math.min(1000L * (1L << (i - 1)), 5000));
        }
    }
    throw new IllegalStateException("unreachable");
}
// 事务 @Transactional、缓存 @Cacheable、限流 @RateLimiter、重试 @Retryable —— 全是代理
Spring AOP 的经典坑：同类内自调用不生效。this.method() 走的是原始对象不是代理，注解全失效。解法：① 注入自身代理（AopContext.currentProxy()）；② 拆成两个 Bean；③ 用 AspectJ 编译期/加载期织入（不走代理）。

另一个大坑：@Transactional 方法内发 MQ 消息，事务回滚了消息已经发出去了。解法是事务同步器或 outbox 模式（见《事件驱动架构》模块 6）。
模块 6

模板方法与责任链：框架的骨架

模板方法：不变的部分自己管，变的部分交给子类

// 场景：订单导出，流程固定（鉴权→查数→转换→写文件），各家渠道转换逻辑不同
public abstract class OrderExporter {
    public final File export(Long merchantId, DateRange range) {  // final：流程不许改
        checkPermission(merchantId);                 // ① 固定步骤
        List<Order> orders = loadOrders(merchantId, range);  // ② 固定步骤
        String content = transform(orders);          // ③ 可变：钩子方法
        return writeFile(content);                    // ④ 固定步骤
    }

    protected abstract String transform(List<Order> orders);  // 子类实现

    protected void checkPermission(Long merchantId) { /* 默认实现，可覆盖 */ }
    protected List<Order> loadOrders(Long id, DateRange r) { /* ... */ }
    private File writeFile(String content) { /* ... */ }
}

public class CsvOrderExporter extends OrderExporter {
    protected String transform(List<Order> orders) { /* 拼 CSV */ }
}
// 新增导出格式 = 一个子类，流程代码零重复。Spring JdbcTemplate 同款思想

责任链：请求沿链走，直到有人接

// 场景：下单前校验 —— 风控、库存、优惠资格、黑名单，规则会不断增加
public interface OrderCheckHandler {
    void handle(OrderContext ctx, CheckChain chain);
}

// 每个 handler 做自己的事，然后决定放行还是拦截
public class RiskCheckHandler implements OrderCheckHandler {
    public void handle(OrderContext ctx, CheckChain chain) {
        if (riskClient.isBlack(ctx.getUserId())) {
            ctx.reject("命中风控黑名单");   // 拦截：不调用 chain.doHandle
            return;
        }
        chain.doHandle(ctx);              // 放行：交给下一个
    }
}

// 组装链条（Spring 注入所有 handler，按 order 排序）
public class CheckChain {
    private final List<OrderCheckHandler> handlers;
    private int index = 0;

    public void doHandle(OrderContext ctx) {
        if (index >= handlers.size()) return;
        handlers.get(index++).handle(ctx, this);
    }
}
// 新增规则 = 新增一个 @Component，不碰任何老代码
你已经在用的责任链链上的节点
Servlet Filter Chain编码 → 鉴权 → 日志 → XSS 过滤 → 业务 Servlet
Spring Security FilterChainCORS → CSRF → 认证 → 授权 → 业务
Spring MVC InterceptorpreHandle → Controller → postHandle → afterCompletion
Koa / Express 中间件logger → bodyParser → auth → route handler
责任链的两个坑：① 顺序敏感——鉴权放在日志后面就是安全事故，要用显式 order 注解而不是依赖注入顺序；② 责任漂移——把所有业务逻辑都塞进 handler，链条变成第二个主流程，调试时栈深十几层。责任链只放横切校验，不放核心业务。
模块 7

模式的本质与反模式警示

模式是命名，不是银弹

“策略模式”四个字，比“我写了一个接口和几个实现类，用的时候选一个”沟通效率高 10 倍。模式的首要价值是团队语言：说“这里用 ACL 隔离第三方”全组都懂边界在哪；说“加个适配器吧”比贴 50 行代码讨论快得多。第二价值才是复用结构。

真正的工程判断 = 识别重复出现的“变化点”，然后选一个名字最响的模式来安放它。顺序永远是：先写直白的代码 → 发现变化 → 抽象 → 命名。反过来（先画类图再写代码）就是过度设计。

反模式清单

反模式症状处方
模式崇拜为 2 个分支建 5 个类；接口只有一个实现也叫 XxxStrategy一个实现的接口没有抽象价值，直接写类
过度设计“预留扩展点”遍布代码，90% 永远不会来YAGNI。真出现第二次重复再重构
上帝类一个 Service 2000 行，用“中介者”名义把所有逻辑收拢到自己按限界上下文拆，而不是换模式
单例收集器全局静态 Map 当注册中心，测试之间互相污染交给 DI 容器；静态状态不可 mock
滥用观察者事件层层转发，一次下单触发 27 个 listener，栈深 40 层画事件拓扑图，深度 > 3 或 fan-out > 5 就该合并
抽象泄漏工厂方法套工厂方法套抽象工厂，找不到真正干活的类抽象层数 ≤ 2；实现类必须 3 次跳转内可达

模块 8

十个工程坑

1
Spring 容器里手写 DCL 单例
丢失 DI 能力、不可测试、隐藏全局依赖。容器管理的类声明成普通 Bean 即可，默认就是线程安全单例。
2
DCL 单例忘了 volatile
指令重排会让其他线程拿到“已分配内存未初始化”的对象，偶发 NPE/默认值，极难复现。加 volatile 或直接用枚举。
3
策略模式接口只有一个实现类
这是最典型的过度设计：接口、工厂、注册表全套齐上，只为一个不会变的分支。等第二个实现出现再抽象。
4
if-else 改策略后，分支逻辑互相调用
策略类之间本应独立，结果 SVIP 策略里 import VIP 策略算折扣，出现隐藏的顺序依赖。策略必须自包含。
5
同步观察者里做耗时操作
支付接口里同步发短信+推送+加积分，P99 从 80ms 涨到 600ms。通知类下游一律 @Async 或走 MQ。
6
观察者异常影响主流程
listener 抛异常，同步场景直接冒泡到接口层，用户看到“支付失败”但钱已扣。listener 必须 try-catch 记录，或异步隔离。
7
AOP 同类自调用，注解静默失效
this.internal() 不经过代理，@Transactional/@Retryable 全部不生效，且不报错。注入自身代理或拆类，关键路径加集成测试验证。
8
@Transactional 里发 MQ 消息
消息先于事务提交发出，事务随后回滚 → 下游收到“幽灵事件”。用 TransactionSynchronizationManager 注册 afterCommit 回调，或 outbox 模式。
9
责任链顺序靠注入顺序
Bean 注入顺序不稳定，鉴权 handler 某次排在日志后面，安全审计失效。用 @Order 或 HandlerOrder 显式声明，并加测试锁定顺序。
10
适配器里写业务逻辑
ACL 本该只做字段映射和异常转换，结果塞进定价规则。第三方一升级，业务跟着崩。适配器只翻译，不决策。
自测

六道题

1. 在 Spring Boot 项目里需要一个全局唯一的配置持有者，最恰当的做法是？
正确答案：@Component。DI 容器默认 singleton scope，天然线程安全，还能注入依赖、可测试、有生命周期钩子。手写单例在容器环境下全是反模式；枚举适合的是不被容器管理的库代码。
2. 电商折扣规则按会员等级不断扩展，每个等级算法不同，最合适的模式组合是？
正确答案：策略 + 工厂。策略把每个等级算法隔离成独立类，工厂/Map 注册表按等级路由，新增等级只需新增一个 Bean。责任链适合“逐个校验拦截”场景，不适合二选一的算法分派。
3. 关于 Spring 的 @Transactional，哪种情况会静默失效？
正确答案：同类内自调用。A 通过 this 调用 B，绕过了代理对象，事务拦截器根本没机会执行。解法：注入自身代理、拆成两个 Bean，或用 AspectJ 织入。跨 Bean 调用和抛异常都是事务正常工作的场景。
4. Servlet Filter、Koa 中间件、Spring Interceptor 共同体现的是哪个模式？
正确答案：责任链。请求沿着一串处理器依次传递，每个节点可以处理、拦截或放行，且节点的添加不影响其他节点。观察者是“广播通知”，没有“沿链传递直到有人处理”的语义。
5. 对接一个字段名和异常体系都不同的第三方支付 SDK，最该用的模式是？
正确答案：适配器/ACL。把第三方模型、字段映射、异常转换全部关在适配器里，业务代码只面对自己的领域语言。SDK 升级或换供应商时只改这一个类，污染不会渗进核心逻辑。
6. 关于“是否使用设计模式”，下列哪种判断最符合工程理性？
正确答案：等重复出现再抽象。模式的成本是类数量和间接层，应该由真实的变化驱动，而不是预测驱动。为不发生的分支拆类是过度设计；而彻底禁用 if-else 同样是迷信——简单直白本身也是美德。

下一步怎么练：拿自己项目里最长的那个 if-else 或 switch，改写成“策略 + 注册表工厂”，对比单元测试数量变化；再给一个同步通知链路加 @Async 和 MQ，用压测对比 P99；最后检查项目里有没有只有一个实现的接口——那是可以安全删掉的“假模式”。
