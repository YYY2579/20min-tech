二十分钟学透事件驱动架构

事件驱动的难点不在“发消息”，在最终一致性：怎么保证消息不丢不重、顺序不乱、系统不乱循环。这篇把 outbox、Saga、对账、幂等等硬机制讲透。

建议起一套 Kafka + 数据库（docker-compose 即可），边看边把 outbox 表建出来。
开始前

先分清三个词：事件、消息、命令

这三个词在中文里被混用，但它们的方向、语义、耦合度完全不同。分不清就会设计出错的契约。

类型语义时态耦合特征
命令 Command“请做某事”。可能被拒绝将来时点对点，发送方知道谁该做，期待结果/失败
事件 Event“某事已发生”。不可更改的事实过去时广播，发送方不关心谁消费，无返回
消息 Message传输载体统称。上面两种的报文都是消息—技术概念，含 headers/payload
// 命令：期望被执行，允许失败
PlaceOrderCommand { orderId, items, address }        // 发给订单服务
ChargePaymentCommand { orderId, amount }             // 发给支付服务，可被拒绝（余额不足）

// 事件：已经发生的事实，不可撤销，只能补偿
OrderCreated { orderId, items, total, occurredAt }   // 订单已创建（广播给库存/营销/搜索）
PaymentSucceeded { orderId, paidAmount }             // 支付已成功（广播）

// 反例：把命令当事件发 —— OrderCreationRequested，收方不知道要不要执行，
// 出了事互相甩锅（"我以为你拒绝了"）。命名规范：事件一律过去式
设计自检：① 你的消息名是过去式吗？不是 → 你在发命令，请确认接收方和失败处理。② 发送方需要知道消费者是谁吗？需要 → 这不是事件驱动，是 RPC，别披着事件的外衣。③ 消费者能否安全地重复处理同一条消息？不能 → 你还没做幂等（模块 5 见）。
模块 1

事件模式三形态

1. 事件通知（Event Notification）

事件只带 ID 和最少信息，消费者按需回查。耦合最低，但消费者要知道去哪拉数据：

// 订单服务只发通知，不带明细
OrderCreated { orderId: 42, occurredAt: "2026-10-17T10:00:00Z" }

// 库存服务收到后，自己回查订单详情
public void on(OrderCreated e) {
    OrderDetail detail = orderClient.getDetail(e.orderId());   // 回查
    inventoryService.reserve(detail.getSkuIds());
}
// 优点：订单服务改字段不影响消费者；消费者按需取数
// 缺点：消费者依赖订单服务的查询接口（时点耦合）；回查量大时打挂上游

2. 事件携带状态传输（Event-Carried State Transfer）

事件自带消费者需要的全量数据，消费者无需回查，还能建自己的本地副本：

// 事件带上消费者要的一切
OrderCreated {
    orderId: 42,
    userId: 1001,
    items: [ { skuId: 88, qty: 2, price: 99.00 } ],
    total: 198.00,
    address: { province: "广东", city: "深圳", detail: "..." },
    occurredAt: "2026-10-17T10:00:00Z"
}

// 库存服务直接把 items 落自己的库，零回查
// 甚至可以在本地维护一份"订单只读副本"，查询完全不碰订单服务
// 优点：自治性强、消费者可用性不受上游影响；缺点是事件会变大、字段变更要兼容

3. 事件溯源（Event Sourcing）

不存当前状态，只存事件流，状态由重放得到。详细机制见本期《领域驱动设计实战》模块 5。事件驱动语境下它的位置是：事件流即数据源，是前两种模式的极端形式。

形态事件大小耦合方向适用
事件通知小（几个字段）消费者→生产者查询接口上游模型稳定、查询便宜
携带状态传输大（全量字段）生产者→消费者数据契约消费者要自治、要本地副本
事件溯源流（按顺序全部）无（自己就是源）审计/金融台账，配 CQRS
选型经验：80% 的集成事件用携带状态传输——消费者自治、不回查、上游挂了消费者照常工作。事件通知只适合“变更很少但消费者很多”的通知场景（如缓存失效广播）。
模块 2

EventBus / EventBridge：事件路由层

事件驱动需要一层“事件从哪来、到哪去、规则是什么”的基础设施。进程内叫 EventBus，云上叫 EventBridge/EventRouter。

进程内 EventBus

// 轻量进程内总线：类型即 topic，同步分发 + 异常隔离
public class EventBus {
    private final Map<Class<?>, List<Consumer<Object>>> handlers = new ConcurrentHashMap<>();

    public <T> void subscribe(Class<T> type, Consumer<T> handler) {
        handlers.computeIfAbsent(type, k -> new CopyOnWriteArrayList<>()).add(h -> handler.accept(type.cast(h)));
    }

    public void publish(Object event) {
        List<Consumer<Object>> hs = handlers.get(event.getClass());
        if (hs == null) return;
        for (Consumer<Object> h : hs) {
            try { h.accept(event); }
            catch (Exception e) {
                log.error("事件处理失败: {}", event, e);   // 单个 handler 失败不影响其他
                metrics.counter("eventbus.error").increment();
            }
        }
    }
}
// 本质是观察者模式框架化。同步执行，只适合同进程、非关键下游

  arn  = aws_sqs_queue.inventory_queue.arn
  # 死信队列 + 重试策略
  dead_letter_config {
    arn = aws_sqs_queue.dlq.arn

    maximum_event_age_seconds = 300
  }
}
自建 vs 托管怎么选：自建 Kafka/RocketMQ 需要运维副本、rebalance、消息堆积治理；EventBridge/SNS/SQS（云）、RocketMQ（云厂商托管）省运维但绑定厂商、单 topic 吞吐和单价受限。规则：< 10 万 TPS、无强顺序要求 → 托管；高吞吐或强顺序 → 自建 Kafka 分区模型。
模块 3

最终一致性与补偿事务 Saga

跨服务的事务没有两阶段提交的优雅解法（2PC 性能差、锁太久），工程答案是 Saga：一串本地事务 + 失败时的补偿。

两种编排方式

方式机制优缺点
编排 Choreography无中心，服务监听彼此事件，链式反应简单松耦合；但流程看不见，加一环要改多方，容易循环
协同 Orchestration中央 orchestrator 按状态机发命令、监听结果流程集中可见、可观测；中心组件是单点（做成无状态+持久化状态机）
// Saga 状态机示例：下单流程，任一步失败走补偿
//
//  [创建订单] --OrderCreated--> [扣库存] --StockReserved--> [扣款] --Paid--> 完成
//      |                            |                          |
//      v 失败                       v 失败                     v 失败
//  (无需补偿)                   [释放库存]                 [释放库存 + 退款]

// 协同式：状态机 + 命令 + 补偿，全部持久化
public class PlaceOrderSaga {
    public void start(CreateOrderCmd cmd) {
        sagaState = new SagaState(START);        // 状态先落库
        send(new CreateOrderCommand(cmd));        // ① 发命令，不是直接调
    }

    public void on(OrderCreated e) {
        sagaState.advance(ORDER_CREATED);
        send(new ReserveStockCommand(e.orderId(), e.items()));  // ②
    }

    public void on(StockReserved e) {
        sagaState.advance(STOCK_RESERVED);
        send(new ChargePaymentCommand(e.orderId(), e.total())); // ③
    }

    public void on(PaymentFailed e) {           // ③ 失败 → 补偿链
        send(new ReleaseStockCommand(e.orderId()));    // 撤销 ②
        send(new CancelOrderCommand(e.orderId()));     // 撤销 ①
    }
}
// 关键：状态 + 已执行步骤持久化，进程崩溃重启后能接着补偿，不能"补偿到一半丢了"

Saga 的三个铁律

  • 补偿 ≠ 回滚。回滚是“当没发生”，补偿是“做相反的事”（退款、释放库存），补偿本身也可能失败，要能重试且幂等。
  • 隔离性缺失是固有代价。Saga 执行中，其他事务可能读到中间状态（库存已扣、订单未创建）。要么接受可读，要么用语义锁（如订单先置“处理中”）。
  • 每一步都要幂等 + 可重试 + 有超时。命令发出后没收到响应，分不清“对方没收到”还是“响应丢了”——靠幂等重试，靠超时查询兜底。
没有补偿机制的 Saga 不是 Saga，是分布式事故。经典案例：支付成功但订单创建失败，没有 CancelOrder 补偿，用户钱扣了订单不存在，客服手工修了三年。每个正向步骤设计时就要同时写出逆向步骤。
模块 4

Outbox：消息必达的正确姿势

“业务事务提交了，但消息没发出去”是事件驱动第一号事故。outbox（发件箱）模式用同一个本地事务解决：

// 错误示范：事务提交后才发消息 —— 两个失败窗口
@Transactional
public void placeOrder(CreateOrderCmd cmd) {
    orderRepo.save(Order.create(cmd));
}
kafka.send("order-created", event);   // ✗ ① 事务回滚了消息照样发
                                        // ✗ ② 这里抛异常，订单建了消息没发

正确姿势：outbox 表 + 中继（relay）

-- 1. 建 outbox 表（和业务表在同一个数据库）
CREATE TABLE outbox (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    aggregate_id  VARCHAR(64)  NOT NULL,     -- 聚合 ID，保证同聚合有序
    event_type    VARCHAR(128) NOT NULL,
    payload       JSON         NOT NULL,
    created_at    TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_pending (created_at, id)         -- 中继扫描用
) ENGINE=InnoDB;
// 2. 业务写入和事件入 outbox —— 同一个本地事务，原子性由数据库保证
@Transactional
public void placeOrder(CreateOrderCmd cmd) {
    Order order = Order.create(cmd);
    orderRepo.save(order);                          // 业务表
    outboxRepo.save(new OutboxRow(
        order.getId().value(),                      -- aggregate_id
        "OrderCreated", order.toCreatedEventJson()  -- outbox 表
    ));
}
// 要么都成功，要么都回滚。从此不存在"订单建了消息没发"
// 3. 中继进程：扫 outbox → 发 MQ → 标记已发（或删行）
@Scheduled(fixedDelay = 1000)
public void relay() {
    List<OutboxRow> pending = outboxRepo.findPending(500);   -- 批量 500 条
    for (OutboxRow row : pending) {
        try {
            // 发送时带 eventId = outbox.id，消费者做幂等键
            mqClient.send(row.getEventType(), row.getPayload(), row.getId());
            outboxRepo.markDone(row.getId());       -- 或 DELETE（表会膨胀）
        } catch (Exception e) {
            metrics.counter("outbox.relay.fail").increment();
            // 不删行，下一轮重试；连续失败超阈值告警
            break;                                  -- 保序：失败即停
        }
    }
}

工程细节清单

细节做法
中继与业务同库不同部署中继可多实例，用 SELECT ... FOR UPDATE SKIP LOCKED 或按 id 取模分片，避免重复发
outbox 表膨胀已发送行定时归档/删除（每天一次 DELETE 限批），或改用 Debezium 直接读 binlog
顺序保证按 aggregate_id 分区到同一 partition；中继单线程扫或同聚合串行发
发成功但 markDone 前崩溃重发 → 消费者靠 eventId 幂等去重。这就是为什么幂等是强制项
不想写中继？用 CDC。Debezium/Canal 订阅业务库 binlog，把 INSERT into outbox 自动转成 MQ 消息，业务零侵入。代价是多一套 Debezium 集群要运维。日均事件 < 100 万，自写中继更划算；> 1000 万或懒得维护，上 Debezium。
模块 5

最终一致性工程套件：对账、幂等、乱序

幂等：一切重试的地基

// 消费者侧幂等三件套：唯一键 + 状态机 + 业务判重
// ① 唯一键：事件 ID 建唯一索引，重复插入直接失败
CREATE TABLE processed_event (
    event_id    VARCHAR(64) PRIMARY KEY,     -- = outbox.id 或 MQ messageId
    event_type  VARCHAR(64) NOT NULL,
    processed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

@Transactional
public void handlePaymentSucceeded(PaymentSucceeded e) {
    // 先尝试登记事件 ID，重复事件在这里被拦下
    try {
        processedEventRepo.insert(e.eventId());      -- 唯一键冲突 = 已处理过
    } catch (DuplicateKeyException ex) {
        log.info("重复事件，忽略: {}", e.eventId());
        return;
    }
    orderService.markPaid(e.orderId());              -- 同一事务里做业务
}

// ② 状态机守卫：只允许合法迁移，天然幂等
if (order.getStatus() == OrderStatus.PAID) return;   -- 已支付，重复通知无害

// ③ 业务判重：唯一业务单号（如支付流水号）
-- payment_record 表：biz_no 唯一索引，重复回调插入失败即幂等

对账：最终一致的安全网

层级对账内容频率
实时对账关键链路双方状态比对（订单状态 vs 支付状态）每次消费时
小时级对账扫描 N 小时前未完结的 Saga/卡住的中间态每小时
日终对账全量流水双边核对（我方 vs 渠道方），出差异报表每天
-- 经典对账 SQL：找出"订单已创建但 10 分钟没动静"的卡单
SELECT o.id, o.status, o.created_at
FROM orders o
LEFT JOIN payment_record p ON p.order_id = o.id
WHERE o.status = 'CREATED'
  AND o.created_at < NOW() - INTERVAL 10 MINUTE
  AND p.id IS NULL;
-- 结果进告警或自动补偿队列：查支付渠道实际状态 → 推进或取消

乱序处理：不要假设消息按序到达

  • 版本号/时间戳丢弃旧值：if (event.version <= currentVersion) return; 状态机只认前进，不认回退
  • 局部顺序：Kafka 单 partition 有序。把同一实体的所有事件发同一 key（如 orderId），消费者按 key 单线程/同队列处理
  • 乱序容忍设计：消费“库存已扣”前先确保“订单已创建”，否则挂起等齐（或回查补偿）
  • 不要试图全局排序：跨 topic、跨服务的全局顺序不存在。把顺序要求收敛到单实体
顺序性只能局部保证。Kafka 的 partition 有序是“单分区单消费者”的有序，一旦并发消费或分区重分配，顺序即破。设计原则：假设任何消息可能乱序、重复、延迟数小时，系统仍能收敛到正确状态。做不到这一点，就不是最终一致，是最终不一致。
模块 6

领域事件与集成事件

维度领域事件集成事件
范围限界上下文内部，进程内跨上下文/跨服务，经 MQ
目的解耦聚合间的副作用（扣库存、发短信）对外发布契约，别的上下文依赖它
演进随意改，重构友好版本化契约。加字段可以，删字段/改语义 = 破坏性变更

示例OrderPaid（进程内）shop.order.paid.v1（契约）
// 事件契约演进的兼容规则
// ✅ 可以：新增可选字段（老消费者忽略，新消费者用默认值）
{
  "orderId": 42,
  "paidAmount": 198.00,
  "paidAt": "2026-10-17T10:00:00Z",
  "channel": "WECHAT"        // v2 新增，老消费者安全
}

// ❌ 不行：改字段类型/语义、删字段、改事件名
// "paidAmount": "198.00"  字符串→数字，老消费者解析崩
// "amount" 改名，老消费者直接 null

// 正确姿势：破坏性变更发新事件名 shop.order.paid.v2，两版并行跑一个迁移周期
// Schema Registry（Confluent/Apicurio）在 CI 里做兼容性检查，不兼容直接卡发布
事件契约是 API，且比 REST API 更难改。REST 至少你知道谁在调；事件广播出去你不知道有几个消费者，改坏一个就是线上事故。每个事件 topic 必须有 owner、有文档、有兼容性测试。没有 Schema Registry 至少也要在代码库里集中定义事件类并评审。
模块 7

消息顺序性与重试治理

顺序保证的层级

机制保证范围代价
Kafka 单 partition同 key 消息有序key 倾斜时单分区热点；分区数只增不减
RocketMQ MessageQueueSelector同业务 key 进同一队列队列级串行，吞吐受限
全局序列号（如 MySQL 自增 ID 发号）全局可比的顺序基准发号器单点/性能瓶颈
版本向量 + 丢弃旧值不保证到达有序，保证结果有序需要事件带单调版本号
// 版本号模式：乱序到达，结果不错乱
public void apply(OrderStatusChanged e) {
    synchronized (orderLock) {
        if (e.version() <= order.getStatusVersion()) {
            // 旧版本事件晚到：丢弃（幂等 + 保序合一）
            metrics.counter("event.stale.dropped").increment();
            return;
        }
        order.setStatus(e.newStatus());
        order.setStatusVersion(e.version());
    }
}
// 生产者：每次状态变更 version = ++current，事件带 version
// 消费者：版本小的直接丢。乱序的"已发货(3)"不会覆盖"已完成(4)"

重试与死信的三级防线

第一级：消费者本地重试。失败立即重试 3 次，间隔 100ms/500ms/2s 指数退避。只治瞬时故障（网络抖动、锁冲突）。
第二级：重试队列。本地重试耗尽，消息进 retry-topic（如 RocketMQ 的 %RETRY%），延迟 30s/1min/5min 逐级放大。绝不在原队列无限重试——会阻塞后面所有消息（队头阻塞）。
第三级：死信队列 DLQ。重试 N 次仍失败（通常是代码 bug 或毒消息），进 DLQ 并告警，人工/定时任务介入。DLQ 必须有监控：堆积 = 有人在丢消息。
# RocketMQ 消费重试语义（不同 MQ 行为不同，用前查文档）
# 普通消息：失败进 %RETRY%topic，默认重试 16 次，间隔逐级拉长（10s→30s→...→2h）
# 超过次数进 %DLQ%topic，不再自动消费，需人工处理
# 顺序消息：消费失败会挂起当前队列（suspendCurrentQueueTime），重试成功才继续
# 事务消息：半消息 + 回查，用于"本地事务与发消息原子"（outbox 的替代路线）
不同 MQ 的语义差异巨大：RocketMQ 失败自动进重试 topic；Kafka 消费者要自己实现重试 topic；RabbitMQ 的死信交换机（DLX）是另一套机制。照着 RocketMQ 经验写 Kafka 重试，大概率写出队头阻塞。
模块 8

十个典型坑

1
事务提交后才发消息
两个失败窗口：事务回滚消息已发（幽灵事件）、消息发失败订单已建（丢事件）。用 outbox 同事务写库，或 RocketMQ 事务消息。
2
消费者不幂等
at-least-once 投递 + 重试 = 必然重复。重复扣款、重复发货都这么来的。唯一键 + 状态机 + 业务单号三重判重是标配。
3
事件无限膨胀
图省事把整个聚合序列化进事件，1KB 变 500KB，还带上历史字段只增不减。事件只带消费者要的字段，定期清理下线字段。
4
无限重试不设上限
毒消息（解析失败、NPE）卡住重试队列，看起来在忙其实零进展。必须重试计数 + DLQ + 告警。
5
循环事件
A 发事件触发 B，B 处理又发事件触发 A，系统自激振荡，监控上一片“繁忙”。规则：事件链深度 > 3 必须报警，环路上加链路 ID 去重。
6
假设消息按序到达
重试、多分区、并发消费都会乱序。“先删后建”乱成“先建后删”= 数据丢失。用版本号丢弃旧事件，把顺序要求收敛到单实体。
7
调试断点打不进
发布方看不到消费者，问题靠翻日志。必须：全链路 trace ID 贯穿（生产者注入，消费者透传）、事件台账可查（谁在何时消费成功/失败）。
8
同步监听当 RPC 用
在 @EventListener 里调外部 HTTP，消费者超时拖垮发布方事务。监听器只做本地快操作，跨进程一律异步。
9
事件契约随意改
上游删字段/改类型，下游消费全线 NPE，且你根本不知道有几个下游。Schema Registry 兼容性检查 + 事件 owner 制。
10
outbox 表只增不删
跑三个月表几个亿，中继扫描越来越慢。已发送行定时归档删除，或直接上 Debezium 读 binlog 不建表。
自测

六道题

1. “OrderCreated”和“PlaceOrderCommand”的本质区别是？
正确答案：事实 vs 请求。事件是过去式、不可撤销、广播给不关心的接收方；命令是将来时、期待执行结果、点对点。混用会导致失败时责任不清——“我以为你拒绝了”这类甩锅。
2. 要保证“订单入库”和“订单事件发出”要么都成功要么都失败，最稳妥的方案是？
正确答案：outbox 同事务。业务表和 outbox 表在同一个数据库事务里，原子性由本地事务保证；之后中继扫 outbox 发 MQ，失败了靠重试和消费者幂等兜底。其他两种方案都存在“一半成功”的窗口。
3. 消费者收到重复的 PaymentSucceeded 事件，正确的处理是？
正确答案：唯一键判重。at-least-once 语义下重复是必然的（重试、重平衡、宕机重连都会造成）。“相信不重复”是赌博；抛异常只会制造无限重试。
4. 一条消息因代码 bug 每次消费都失败，最合理的链路行为是？
正确答案：分级重试 + DLQ + 告警。原地无限重试会造成队头阻塞，后面全堵死；直接丢弃是丢数据。DLQ 让毒消息被隔离且可见，修完 bug 还能重放。
5. 关于消息顺序，哪个说法是对的？
正确答案：局部有序。Kafka 单 partition 有序、RocketMQ 单队列有序，但跨分区、重平衡、重试后都会乱序。工程解法是：同一实体的事件发同一 key，并用版本号丢弃迟到的旧事件，不依赖到达顺序。
6. Saga 事务里“扣款成功但通知库存失败”，正确的补偿动作是？
正确答案：反向补偿 + 幂等。分布式事务没有回滚，只有补偿；且补偿也可能失败/重复，必须可重试幂等。分布式下也做不到“当没发生”——可能已经有其他服务读到了中间状态。
