先把你自己这台机器看清楚

后面所有结论都要落到具体数字上。先花一分钟，把下面几条命令的输出留在手边。

# 1. 一句话看清拓扑：几路、几核、几线程、缓存多大
lscpu

# 2. 缓存行大小（写并发数据结构时必须知道，通常是 64 字节）
getconf LEVEL1_DCACHE_LINESIZE

# 3. 每个核心的缓存大小（index0 一般是 L1d）
for i in /sys/devices/system/cpu/cpu0/cache/index*; do
  echo "$(cat $i/level) $(cat $i/type) $(cat $i/size)"
done

# 4. 看指令集扩展（x86 才有 Flags 这一行，ARM64 叫 Features）
grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E 'avx|sse|amx|aes' | sort -u

# 5. 看每个逻辑核的最大频率（判断大小核最直接的办法）

模块 1

x86 与 ARM 的本质差异

先给结论：CISC 和 RISC 的分界，在今天已经基本消失了。真正影响你的是指令编码方式、寄存器数量、内存模型和生态，而不是教科书上那句"复杂指令 vs 精简指令"。

维度x86-64ARM64（AArch64）
指令长度变长，1~15 字节。有大量历史遗留的前缀字节定长 4 字节。取指和解码的边界天然对齐
通用寄存器16 个（rax~r15），其中 rsp/rbp 有专用用途31 个（x0~x30）+ 零寄存器 xzr + 栈指针 sp
操作数形式经典是二操作数（dest 兼作 src），AVX 引入三操作数三操作数为主：add x0, x1, x2
访存算术指令可以直接带内存操作数，一条指令完成"读+算"严格 load/store 架构，必须先 ldr 到寄存器再算
条件执行依赖 RFLAGS 标志位，配合 jcc 跳转NZCV 标志 + 几乎每条指令都可条件执行（csel、b.eq）
内存模型TSO（Total Store Order），较强，硬件保证 store-store 顺序弱内存模型，需要显式屏障（dmb/ldar/stlr）
典型场景PC、服务器、几乎所有商业软件的第一优先平台手机、嵌入式、Apple Silicon、云服务器（Graviton / 倚天 / 鲲鹏）

变长 vs 定长，差在哪

x86 的变长编码带来两个后果：代码密度高（同样逻辑占的内存少，i-cache 命中率好），但解码极难——CPU 必须先判断这条指令有几个字节，才能知道下一条从哪开始。所以现代 x86 前端会一次抓 16~32 字节，用多路并行的预解码器去猜边界，猜错了就浪费解码带宽。

ARM64 定长 4 字节，解码器可以无条件并行切分，前端简单得多。代价是代码体积大 20%~30%，对 i-cache 压力更大。这是纯粹的工程权衡，不是谁更先进。

; x86-64：同一条 add，编码长度随操作数变化
55                    push   rbp
48 89 e5              mov    rbp, rsp
8b 45 fc              mov    eax, [rbp-0x4]     ; 3 字节
03 45 f8              add    eax, [rbp-0x8]     ; 3 字节，一条指令完成读+加

; AArch64：全部 4 字节，必须先 load 再 add
a9bf7bfd              stp    x29, x30, [sp, #-16]!
910003fd              mov    x29, sp
b9400fe0              ldr    w0, [sp, #12]
b9400be1              ldr    w1, [sp, #8]
0b010000              add    w0, w0, w1

数一下：x86 用 4 条指令 11 个字节完成的事，ARM64 用了 5 条指令 20 个字节。但 ARM64 的每一条都能在一个周期内被无歧义地解码，而 x86 那条 add eax,[rbp-8] 到了后端会被拆成 load + add 两个微操作（micro-op，简称 uop）。

寄存器多，到底有什么用

寄存器是 CPU 里最快、也最贵的存储。31 个通用寄存器意味着编译器可以把更多局部变量一直留在寄存器里，减少访存。x86-64 只有 16 个，编译器经常被迫 spill（把变量写回栈），函数调用一深，栈上的读写就上来了。

但这条优势被两个因素抵消了大半：① x86 有强大的 store-to-load forwarding（存储转发），刚写进栈的值再读出来延迟只有 4~5 个周期；② 现代乱序执行引擎用寄存器重命名（register renaming）把 16 个架构寄存器映射到几百个物理寄存器上，消除了假依赖。所以"寄存器少所以慢"是个过度简化的说法。

最容易踩的认知坑："ARM 是 RISC 所以更省电、更快"。
省电主要来自工艺、电压频率曲线和芯片设计目标，不是 ISA。Intel 的 Atom 系列也是 x86，一样能做到几瓦；Apple M 系列快，靠的是超宽的乱序窗口、巨大的缓存和统一内存架构，不是因为它是指令集更"精简"。
真正由 ISA 决定差异的，是内存模型——这一点在写无锁代码时会要你的命，后面模块 4 会再提。
模块 2

微架构的六个关键指标

指令集是"语言"，微架构是"说话的人"。同一句 x86 指令，在不同代 CPU 上执行需要的周期数可以差一倍。看微架构，主要看这六个数字。

指标典型范围它决定了什么
流水线深度12~20 级（NetBurst 曾到 31 级）决定分支预测失败的惩罚。深流水线频率容易拉高，但一预测错就要清空整条流水线，代价 = 深度 × 周期
发射宽度4~8 条/周期每周期最多能"发射"多少条微操作到执行单元。这是吞吐上限
乱序窗口 / ROB224~630 项能同时在"飞行中"的指令数量。窗口越大，越能靠乱序填满流水线气泡
分支预测器TAGE 类，数千~数万项历史决定控制流的可预测性。预测错误一次，代价 15~20 个周期
执行单元数量ALU 4~6，FP 2~4，Load 2~3决定某类指令（整数、浮点、访存）的并行度上限
缓存层级L1 32~48KB / L2 0.5~2MB / L3 8~96MB决定实际内存延迟，往往是真实业务里差距最大的那一项

用数字感受一下几代产品的演进

微架构（举例）发射宽度ROB 项数备注
Skylake（2015，服务端主力多年）422414~19 级流水线，一个时代的基线
Sunny Cove（2019）5352Ice Lake 服务端
Golden Cove（2021）6512Sapphire Rapids 的 P-core
Zen 3 / Zen 4（AMD）6256 / 320Zen 4 支持 AVX-512，但用双 256 位单元实现
Apple Firestorm（M1）8约 630超宽 + 巨大缓存，单核性能标杆

注意：这些数字各家口径不完全一致（有的算宏指令、有的算微操作），只用来建立量级感，别拿去做精确对比。

性能 = IPC × 频率，但两者互相拉扯

IPC（Instructions Per Cycle，每周期执行指令数）衡量"每个周期能干多少活"。同一个程序跑出 IPC 3.0，说明平均每周期退休 3 条指令；如果只有 0.8，说明流水线大部分时间在等。

# 实测 IPC（需要 perf，Linux）
perf stat -e cycles,instructions,branches,branch-misses,cache-misses ./your_program

# 输出里自己算：
#   IPC = instructions / cycles
#   分支预测失败率 = branch-misses / branches   （一般应 < 1%）
#   cache-misses 高 → 瓶颈在内存，不在 CPU

深流水线能上高频，但预测失败惩罚更重；宽发射能提 IPC，但功耗和面积上去了，频率就得降。所以没有"全面更强"的微架构，只有针对某类负载的取舍。

为什么"发射宽度 8"不等于"快 8 倍"

因为程序本身没那么多可并行的指令。看这段代码：

// A：依赖链 —— 每条都等上一条的结果
for (i = 0; i < n; i++) s = s + a[i] * b[i];

// B：四条独立累加 —— 打断依赖链
for (i = 0; i + 3 < n; i += 4) {
    s0 += a[i]   * b[i];
    s1 += a[i+1] * b[i+1];
    s2 += a[i+2] * b[i+2];
    s3 += a[i+3] * b[i+3];
}
s = (s0 + s1) + (s2 + s3);

A 的问题不是加法慢（延迟 1 个周期），而是浮点加法延迟通常 3~4 个周期，而循环里下一次加法必须等上一次的结果。这时候发射宽度是 8 还是 4 完全没用，CPU 每个周期只能推进 1/4 条加法。

B 把一条依赖链拆成四条，理论吞吐直接提升 4 倍。这就是指令级并行（ILP，Instruction Level Parallelism）：硬件能榨出多少并行，取决于你给了它多少。

一条实用判据：如果 perf stat 显示 IPC 很低（< 1）而 cache-miss 和 branch-miss 都不高，那多半是依赖链太长，而不是 CPU 不行。这时候改算法（拆累加器、用前缀和、改数据布局）比换机器有用得多。
模块 3

大小核异构：调度器怎么选核

手机早就这么干了，服务器和 PC 从 2021 年开始全面跟进。核心思想很朴素：用大核保峰值性能，用小核保能效和面积。

方案代表产品结构
ARM big.LITTLE早期的 Exynos、麒麟大簇 + 小簇，同一时刻只有一簇工作（集群迁移），切换有开销
ARM DynamIQ近年的移动 SoC大中小核可以在同一个簇内混排，共享 L3，支持每核独立 DVFS
Intel P-core / E-coreAlder Lake（2021）起P-core 支持超线程且宽而深；E-core（Gracemont）没有超线程，但面积效率极高
Apple P/I 核M 系列、A 系列P 核极宽，I 核极省电，靠系统统一调度

为什么 E-core 划算

Intel 官方口径是：4 个 E-core 占用的面积大致相当于 1 个 P-core（不含超线程），而在多线程吞吐上能提供更高的总性能。代价是单线程性能弱、没有 AVX-512、缓存更小。

所以异构芯片的设计意图非常明确：把"多任务并行"和"单任务冲刺"分开处理。你的构建任务、日志压缩、批处理，跑在 E-core 上很划算；你的数据库主线程、低延迟 RPC，必须待在 P-core 上。

调度器到底怎么选

ARM 侧：EAS（Energy Aware Scheduling，能耗感知调度）。内核里维护一张能耗模型表（EM，Energy Model），描述"某个 CPU 在某个频率下跑某个负载要多少毫瓦"。调度时它同时优化性能和能耗，把轻负载往小核推。
Intel 侧：Thread Director + 硬件反馈。CPU 通过 MSR 上报每个逻辑核的"class"（性能等级）和建议，内核的调度器据此把任务优先放到 P-core。Windows 11 上这套是系统级支持的；Linux 上支持是近几年才逐步补齐的，老内核会把所有核当同质的用。
兜底：schedutil / 频率调节器。如果内核不认识异构拓扑，就只能靠 CPU 频率和负载猜测，效果会明显打折。

运维视角：怎么确认自己踩没踩到小核

# 每个逻辑 CPU 的最大频率：大核明显更高
lscpu -e=CPU,CORE,SOCKET,NODE,MAXMHZ,MINMHZ

# 更细的：直接读每个核的 cpuinfo_max_freq（单位 kHz）
for c in /sys/devices/system/cpu/cpu[0-9]*; do
  echo "$c $(cat $c/cpufreq/cpuinfo_max_freq 2>/dev/null)"
done

# 判断两个逻辑核是不是同一个物理核的两个超线程
cat /sys/devices/system/cpu/cpu0/topology/thread_siblings_list

# 把进程绑到大核（假设 0-7 是 P-core）
taskset -cp 0-7 $PID
Kubernetes 里的坑：cpu-manager-policy=static 只保证把 Pod 绑到独占的 CPU 集合，不保证绑到 P-core。在异构节点上，延迟敏感的服务可能被绑到 E-core，P99 直接翻倍。
解法：① 用节点标签 + taint 把关键业务调度到纯 P-core 的节点池；② 或者用 cpuset 显式指定物理核编号；③ 上线前用 lscpu -e 在节点上核对一遍，别信云厂商的"通用型"描述。
模块 4

多核与超线程：共享了什么，争了什么

SMT（Simultaneous Multithreading，同时多线程），Intel 叫 Hyper-Threading。它的本质不是"多了一个核"，而是让两个线程共用一套执行资源，用线程 A 的停顿去填线程 B 的空洞。

资源是否共享后果
通用寄存器、PC、APIC私有每个线程有独立的架构状态，操作系统看到两个"逻辑 CPU"
执行单元（ALU/FP/Load-Store）共享两个线程抢同一批端口，单线程性能会下降
ROB、发射队列共享（通常静态或动态分区）一个线程占满窗口，另一个线程就被饿死
L1 / L2 缓存共享两个线程互相驱逐对方的缓存行，这是性能下降的主因
L3 缓存全核共享跨核、跨线程都在抢
分支预测器 / BTB部分共享两个线程的分支历史互相污染

什么时候超线程是赚的

负载类型SMT 收益原因
Web 服务、API 网关（大量等待 IO）+20%~30%线程经常阻塞，正好用另一个线程填空
编译、日志处理、批处理+15%~25%指令混合度高，执行单元利用率不满
纯浮点密集（LINPACK 类）0%~10%FP 单元本来就跑满了，第二个线程抢不到
大内存随机访问（数据库、Redis）可能为负L1/L2 被对半砍，cache miss 上升，延迟变差
已开启 Spectre/MDS 等缓解明显缩水部分缓解手段会刷新缓冲区、限制推测，抵消收益

为什么对延迟敏感的服务，超线程有害

假设一个 32 核 64 线程的机器跑 Redis。Redis 是单线程处理命令的，你给了它 64 个"CPU"，但它只用得上 1 个。如果这个线程和另一个忙线程恰好是同一个物理核的两个超线程，那么：

  • L1d（32KB）被两个线程分着用，有效容量可能只剩一半多
  • 分支预测器被污染，分支失败率上升
  • 执行端口被抢占，单线程 IPC 下降 10%~30%

结果就是平均延迟没变，P99 抖了。这类问题极难排查，因为 CPU 利用率看起来只有 3%。

# 确认是不是超线程：Thread(s) per core 为 2 就是
lscpu | grep -E 'Thread|Core|Socket'

# 找出成对的逻辑核（0 和 1 是一对，绑定 0 就够了）
for c in /sys/devices/system/cpu/cpu[0-9]*/topology/thread_siblings_list; do
  echo "$c: $(cat $c)"
done | sort -u

# 关闭 SMT（需要重启，且影响全机）
echo off > /sys/devices/system/cpu/smt/control
cat /sys/devices/system/cpu/smt/active
绑核最容易犯的错：把两个关键线程分别绑到 CPU 0 和 CPU 1，以为"一人一个核"，实际上它们是同一个物理核的两个超线程，抢得更凶。
正确做法是先读 thread_siblings_list，只绑每个物理核的第一个逻辑 CPU（比如 0,2,4,6…），或者干脆在 BIOS 里关掉 SMT。

另外，云厂商的 vCPU 绝大多数就是超线程。同样标"8 vCPU"的实例，可能是 4 物理核 ×2 线程，也可能是 8 个独占物理核（部分计算型/高性能型规格），实际性能能差 1.5 倍以上。采购前一定确认"每核线程数"。

模块 5

指令集扩展与 SIMD

SIMD（Single Instruction Multiple Data，单指令多数据）：一条指令同时处理 4 个、8 个甚至 16 个数据。这是 CPU 上唯一"免费"的数量级加速来源——前提是你的数据布局和算法允许。

扩展位宽平台要点
SSE / SSE2128 位x86x86-64 的基线，一定有。4 个 float 或 2 个 double
AVX256 位x86仅浮点。8 个 float
AVX2256 位x86补齐了 256 位整数运算，实际业务里最常用的一档
AVX-512512 位x86 服务器16 个 float + 掩码寄存器（可以按 lane 开关），部分型号支持 VNNI/BF16 等矩阵指令
NEON / ASIMD128 位ARM64ARM64 上强制存在，不需要检测。4 个 float
SVE / SVE2128~2048 位可变ARM64向量长度由硬件决定（"长度无关"编程），同一份二进制适配不同实现

理论加速比 vs 实际加速比

操作理论加速实测常见值
float32 数组加法（AVX2）8×5~7×（数据在 L1/L2 时）
float32 数组加法（AVX-512）16×8~12×，且可能触发降频
大数组 memcpy—1.1~1.3×，因为瓶颈是内存带宽不是计算
稀疏矩阵乘—接近 1×，访存不连续，向量化基本失效
base64 编解码—3~8×（有专门的查表 + 位运算向量化实现）
SHA-256 计算—5~10×（用 SHA-NI 指令，不是通用 SIMD）

规律很清楚：计算密集 + 数据连续 + 数据在缓存里 = 有得赚；访存密集 = 白干。因为 SIMD 只加速"算"，不加速"取"。

编译器自动向量化的条件

GCC/Clang 在 -O3（GCC 12 起 -O2 也默认开）会尝试向量化循环，但必须同时满足：

条件不满足会怎样
没有循环携带依赖（第 i 次迭代不依赖第 i-1 次的结果）直接放弃，这是最常见的原因
访存连续且步长为 1（或可识别的固定步长）退化成 gather/scatter，通常不向量化
指针不重叠（编译器能证明）不敢向量化，怕语义改变。用 restrict 告诉它
循环体内没有函数调用、没有不可向量的分支放弃，或者只能部分向量化
迭代次数可计算，或有运行时检查生成"向量化主循环 + 标量尾巴"
目标架构确实有该指令（-march 要对）默认 -march=x86-64 只有 SSE2
// 能被向量化：连续访存、无依赖
void add(float * restrict a, const float * restrict b, int n) {
    for (int i = 0; i < n; i++) a[i] += b[i];
}

// 不能被向量化：a[i] 依赖 a[i-1]
void prefix(float *a, int n) {
    for (int i = 1; i < n; i++) a[i] += a[i-1];
}
# 让编译器告诉你它干了什么（这是最有用的一条命令）
gcc -O3 -march=native -fopt-info-vec-optimized -fopt-info-vec-missed -c x.c

# Clang 的等价写法
clang -O3 -march=native -Rpass=loop-vectorize -Rpass-missed=loop-vectorize -c x.c

# 看生成的汇编里有没有 ymm/zmm 寄存器
objdump -d x.o | grep -E 'ymm|zmm|xmm' | head

# 确认本机到底支持哪一档
gcc -march=native -dM -E - </dev/null | grep -E '__AVX|__SSE|__ARM_NEON'
AVX-512 的两个现实问题：
① 降频。在部分 Intel 型号（尤其是 Skylake-SP 一代）上，持续执行 512 位重指令会让全核频率下降 10%~20%，短时间爆发型负载反而变慢。Ice Lake 之后改善很多。
② 不是所有核都有。Intel 消费级 12~14 代把 AVX-512 屏蔽了（E-core 不支持），服务器才完整支持；AMD Zen 4/5 支持但用双 256 位单元实现，吞吐不如原生 512。
结论：写库的时候用运行时派发（runtime dispatch，编译多份内核，启动时按 CPUID 选），别在编译期一把梭 -march=native——那样二进制换台机器就 SIGILL 崩了。
模块 6

为什么同样的代码，换个 CPU 差几倍

这不是玄学。把差距拆开，无非六个来源，每一个都有量级。

因素量级机制
主频1.2~1.6×3.0GHz vs 4.5GHz。注意是全核睿频，不是标称的单核最大频率
微架构 IPC1.3~2.0×窗口大小、发射宽度、执行单元数量
L3 容量与命中率1.5~3×8MB vs 32MB，工作集刚好卡在边界时差距最大
分支预测能力最高 5~6×不可预测的分支在弱预测器上代价极高
内存带宽 / 通道数2~4×双通道 DDR4-3200 ≈ 51GB/s；8 通道 ≈ 205GB/s
NUMA 局部性1.5~2×跨节点访存延迟约为本地的 1.5~2 倍

最戏剧性的例子：分支预测

// 同一段代码，只因为数据先排了序，快好几倍
long sum = 0;
for (int i = 0; i < N; i++)
    if (data[i] >= 128) sum += data[i];

数据随机分布时，这个分支有约 50% 的概率跳转，分支预测器基本只能瞎猜。每猜错一次，流水线要清空，代价 15~20 个周期。假设 N = 10 万，就是 5 万次失败 × 17 周期 ≈ 85 万个周期白烧。

把 data 排序后再跑，分支变成"前一半全不跳、后一半全跳"，预测准确率接近 100%，这些周期全部省下来。业界那个著名的 StackOverflow 问题里，实测差距在 5~6 倍量级——而这跟 CPU 型号一点关系都没有。

工程上的启示：数据布局和访问顺序，往往比换硬件更值钱。把热数据排在一起、把随机访问改成顺序扫描、把 90% 命中的分支放到前面，这些改动零成本，收益却是数量级的。

内存墙：真正的大头

层级典型延迟相对 L1容量
L1d4~5 周期（约 1.3ns）1×32~48KB
L212~14 周期约 3×0.5~2MB
L340~60 周期约 12×8~96MB
本地 DRAM80~100ns（约 250 周期）约 60×GB 级
跨 NUMA 节点 DRAM130~180ns约 100×—

一次 cache miss 的时间，够 CPU 执行几百条指令。所以现代 CPU 的性能问题，八成是"数据没在缓存里"，而不是"算得慢"。这也解释了为什么 L3 从 8MB 涨到 32MB 能让某些服务快一倍：工作集刚好从"装不下"变成"装得下"。

排查顺序（照这个来，别瞎猜）：
① perf stat 看 IPC。IPC 高（>2）→ 计算密集，优化算法；IPC 低（<1）→ 在等，继续往下。
② 看 cache-misses 和 LLC-load-misses。高 → 内存瓶颈，改数据布局、缩小工作集、考虑绑 NUMA。
③ 看 branch-misses。高 → 改分支结构（无分支写法、排序、查表）。
④ 以上都不高但就是慢 → 依赖链太长，或者被同核的兄弟线程抢资源。
模块 7

ARM 服务器能不能上生产

能，而且很多公司已经上了。但它不是"换个 CPU 而已"，是一次全链路的多架构适配。

平台特点适配成本
AWS Graviton 系列自研核，性价比通常比同代 x86 实例高 20%~40%低（生态最成熟）
Ampere Altra最高 80 核，单核单线程（无 SMT），频率稳定中
阿里倚天 710国内云上可得，配套工具链较完整中
华为鲲鹏 920核多，适合高并发无状态服务中

好消息：大部分代码根本不用改

  • Java / Go / Node / Python（纯 Python）/ Rust：源码级可移植，重新编译或换个运行时镜像就行
  • 容器化服务：只要基础镜像有多架构版本，改个 platform 参数即可
  • MySQL / PostgreSQL / Redis / Nginx / Kafka：官方或发行版都有 aarch64 包

坏消息：这几类一定会出问题

问题表现解法
JNI / native 依赖启动报 UnsatisfiedLinkError 或找不到 .so找 aarch64 版本，或自己编译（netty-tcnative、rocksdb、jemalloc 是高发区）
手写 SIMD / intrinsics编译直接失败，或运行结果错抽象出可移植层，ARM 用 NEON 重写；或用 #ifdef 分叉
闭源二进制根本没有 aarch64 版本换方案，或跑在 x86 节点上（别用 QEMU 模拟跑生产）
镜像架构不匹配exec format error用 buildx 构建多架构镜像
调优参数照搬性能不及预期ARM 的缓存行、页大小、NUMA 拓扑、THP 行为都可能不同
# 1. 确认当前架构
uname -m                       # x86_64 或 aarch64

# 2. 构建多架构镜像（一次构建，两个平台都能拉）
docker buildx create --use --name multi
docker buildx build --platform linux/amd64,linux/arm64 -t reg/app:1.0 --push .

# 3. 在 x86 机器上验证 arm64 镜像能不能跑（仅测试，别用于生产）
docker run --rm --platform linux/arm64 reg/app:1.0 /app --version

# 4. 检查二进制依赖的架构
file ./app                    # 看 ELF 的 Machine 字段
ldd ./app                     # 看依赖的 .so 是否齐全
迁移顺序建议：先挑一个无状态、依赖少、流量小的服务做试点 → 压测对比 P99 和单位成本 → 再推有状态服务 → 最后才碰数据面（数据库、消息队列）。
千万别一上来就把 MySQL 主库迁过去：ARM 上的页大小（常见 4KB，也有 64KB 内核）、NUMA 拓扑、内存带宽特性和 x86 都不同，参数要重调。

什么时候不该上 ARM：① 依赖 x86 专属闭源软件（某些商业数据库、加密卡驱动）；② 重度依赖 AVX-512 做数值计算；③ 超低延迟交易，每一纳秒都要抠，且已经在 x86 上调优到位；④ 团队没有多架构 CI 能力——那维护成本会吃掉全部收益。

字段怎么读，容易误读在哪
CPU(s)逻辑 CPU 总数，不是物理核数。= Socket × Core/socket × Thread/core
Thread(s) per core2 就是开了超线程。这个值决定了"逻辑核"和"物理核"要除以几
Core(s) per socket每颗物理 CPU 的物理核数
Socket(s)主板上插了几颗 CPU。大于 1 就一定有 NUMA
Model name型号字符串。虚拟机里可能是伪造的，别太当真
CPU max MHz单核最大睿频。全核睿频通常低 10%~25%，重载时看这个会高估

Address sizes物理地址位数决定最大内存（46 位 = 64TB），虚拟地址 48 位 = 256TB
L3注意括号里的 (1 instance)：说明是所有核共享一块，不是每核独享
NUMA node0 CPU(s)最关键的一行。它告诉你哪些逻辑核属于哪个内存节点，绑核绑内存都靠它

flags 里该看什么

flag含义 / 用途
lmLong Mode，支持 64 位。没有它说明是 32 位 CPU 或内核
avx / avx2256 位向量。AVX2 才有整数运算，实际业务的门槛线
avx512fAVX-512 的基础指令集。只有 f 不代表全都有，还要看 bw/vl/dq/vnni

aes / sha_ni加解密硬件加速。有 sha_ni 的机器算 SHA-256 能快 5~10 倍
bmi1 / bmi2位操作指令（如 tzcnt、pdep），哈希表、位图会用到
hypervisor出现这个说明你在虚拟机里，看到的拓扑可能是假的

判断是否支持 AVX-512：三种方法

# 方法一：查 flags（最简单，但可能被 hypervisor 屏蔽）
grep -o 'avx512[a-z0-9_]*' /proc/cpuinfo | sort -u

# 方法二：让编译器告诉你（最可靠，直接看宏）
gcc -march=native -dM -E - </dev/null | grep -i avx512

# 方法三：实际跑一条 512 位指令，看会不会 SIGILL
cat > t.c <<'EOF'
#include <immintrin.h>
int main(void){ __m512d a = _mm512_set1_pd(1.0); a = _mm512_add_pd(a,a);
                double o[8]; _mm512_storeu_pd(o,a); return (int)o[0]-2; }
EOF
gcc -O2 -mavx512f t.c -o t && ./t && echo "AVX-512 OK"
为什么方法一可能骗你：云厂商为了让你能在不同代际的宿主机之间热迁移，会在 hypervisor 层把 CPUID 里较新的特性屏蔽掉。所以你买了台新机器，avx512f 却看不到——不是你买错了，是云平台为了保证实例族内同构。
反过来，如果你在自己编译的软件里用了 -march=native，然后把这台机器上编的二进制挪到另一台，很可能直接 Illegal instruction 崩掉。
常见坑

十个认知与操作坑

1
把 lscpu 的 CPU(s) 当成物理核数
64 个逻辑 CPU 可能是 32 核 64 线程。按 64 核做容量规划，实际算力会差一半。看清 Thread(s) per core。
2
用 -march=native 编译生产二进制
换台机器、换批实例就 Illegal instruction。要么统一用 -march=x86-64-v2/v3，要么做运行时派发（多份内核 + CPUID 选择）。
3
把两个关键线程绑到相邻的逻辑核编号
CPU 0 和 CPU 1 往往是同一个物理核的两个超线程，抢 L1 和分支预测器。先读 thread_siblings_list 再绑。
4
在异构节点上不做核隔离就跑延迟敏感服务
K8s 的 static CPU 策略不区分 P-core 和 E-core。关键服务可能被绑到小核，P99 直接翻倍。
5
以为 AVX-512 一定比 AVX2 快
部分型号跑 512 位重指令会降频 10%~20%，短时爆发负载反而更慢。而且内存带宽打满时，加宽向量毫无意义。
6
看到 avx512f 就以为全套都有
f 只是基础集，bw/vl/dq/vnni 是独立的。写 intrinsics 前把需要的子集全部检查一遍。
7
只盯着主频选机器
3.8GHz 的老架构可能打不过 2.6GHz 的新架构。同频 IPC 差 1.5 倍是常态，缓存容量差 2 倍更致命。
8
认为开超线程一定提升吞吐
内存随机访问型负载（数据库、Redis）开 SMT 可能让 P99 变差。吞吐敏感开，延迟敏感关或做核隔离。
9
在 ARM 上照搬 x86 的调优参数
页大小、缓存行、NUMA 拓扑、THP 行为都不同。x86 上的 THP 建议（比如 Redis 关 THP）在 ARM 上要重新验证。
10
没有 perf 数据就开始优化
"感觉是 CPU 不行"十次有八次是内存或锁。先跑 perf stat 看 IPC 和 cache-miss，再决定改什么。
自测

六道题

1. 一台机器 lscpu 显示 CPU(s)=64、Thread(s) per core=2、Core(s) per socket=16、Socket(s)=2。它的物理核总数是？
正确答案：32 核。2 路 × 16 核/路 = 32 物理核，再乘以每核 2 线程 = 64 逻辑 CPU。容量规划和绑核都要按物理核算。
2. x86-64 与 ARM64 在内存模型上的关键差异是？
正确答案：x86 TSO，ARM64 弱内存模型。在 x86 上"碰巧能跑"的无锁代码，到 ARM 上可能因为指令重排而出现可见性错误。跨架构的无锁代码必须用 std::atomic 的 acquire/release 语义。
3. 程序 IPC 只有 0.6，cache-miss 和 branch-miss 都不高。最可能的原因是？
正确答案：依赖链太长。缓存和分支都没问题，说明指令取到了、也猜对了，但每条都要等上一条算完。解法是拆累加器、改算法增加并行度，而不是换硬件。
4. 关于超线程（SMT），哪个说法正确？
正确答案：共享执行单元和 L1/L2。收益来自"用 A 的停顿填 B 的空洞"，所以只在执行单元没跑满时有效。数据库、Redis 这类缓存敏感负载，开了 SMT 反而可能让 P99 变差。
5. 想让编译器把循环向量化，下面哪个做法没有帮助？
正确答案：在循环体里调用外部函数。除非函数被内联且可向量化，否则编译器会直接放弃。另外要注意：-march=native 编出的二进制不能跨机器分发。
6. 在云主机上 grep 不到 avx512f，最可能的原因是？
正确答案：被 hypervisor 屏蔽。为了保证同一实例族里不同批次宿主机行为一致、支持热迁移，云平台会裁剪 CPUID。想确认真实能力，只能在物理机上验证，或看厂商的规格文档。
