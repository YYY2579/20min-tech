模块 1

三个根本问题：原子性、可见性、有序性

所有并发 bug 都能归到这三类。分清是哪一类，才知道该用什么手段修 —— 加锁解决全部三个，原子变量只解决单个变量的三个，屏障只解决顺序。

原子性：操作被拆开了

// 看起来是一行，实际是三步：读 → 加 → 写
counter++

// 汇编层面（x86-64）大致是：
//   mov  eax, [counter]    ; 读
//   add  eax, 1            ; 加
//   mov  [counter], eax    ; 写

// 两个线程交错执行，就会丢更新：
// T1 读 0 → T2 读 0 → T1 写 1 → T2 写 1 → 结果是 1，不是 2

真实事故：库存扣减、账户余额、优惠券领取计数。表现是"高并发下少扣了""发放数量对不上"，压测时必现，但 QPS 低的时候完全正常。修法有三种：加锁、用原子变量（atomic.AddInt64 / fetch_add）、或者把操作下沉到数据库用一条 SQL 完成（UPDATE ... SET n = n - 1 WHERE n > 0）。

可见性：一个线程改了，另一个看不见

// 典型的"永不退出"循环
var stop bool

func worker() {
    for !stop {        // 编译器可能把 stop 读到寄存器里，只读一次
        doSomething()
    }
}

func main() {
    go worker()
    time.Sleep(time.Second)
    stop = true        // 另一个 goroutine 永远看不到这个修改
}

原因是现代 CPU 有多级缓存和 store buffer：写操作先进本核的缓冲区，什么时候对其他核可见没有保证。加上编译器优化，读循环可能被提升成"只读一次内存"。修法：用原子变量或加锁（Go 里 sync/atomic，Java 里 volatile，C++ 里 std::atomic）。

有序性：指令被重排了

// 初始化与发布之间的顺序，可能被编译器或 CPU 调换
var config *Config
var ready bool

func init() {
    config = loadConfig()   // ① 写数据
    ready = true            // ② 置标志
}

func use() {
    if ready {              // ③ 看到标志
        config.Get("k")     // ④ 但 config 可能还是 nil
    }
}

① 和 ② 之间没有依赖，编译器和 CPU 都可以调换顺序；③ 和 ④ 之间也一样。结果就是"标志已经置位，数据却还没准备好"，空指针崩溃。修法：用 release/acquire 语义把两步绑成一个原子发布（Go 的 atomic.Store + atomic.Load、Java 的 volatile 写读、C++ 的 memory_order_release/acquire）。

问题本质典型症状修法
原子性复合操作被中断计数少、余额错、重复发放锁 / 原子指令 / 数据库原子更新
可见性写的结果没传到其他核循环不退出、状态读到旧值原子变量 / 锁 / 内存屏障
有序性指令顺序被改变初始化未完成就被使用、空指针release/acquire 配对
一个必须建立的直觉：单核上正确的代码，多核上不一定正确。单核的线程切换发生在指令边界，天然保证原子性；多核是真并行，两个核同时读写同一块内存，缓存一致性协议只保证"最终一致"，不保证"看起来像顺序执行"。这就是为什么这类 bug 只在多核服务器上出现，在开发者的单核虚拟机里跑一万次都正常。
模块 2

锁的代价与选择

锁不是"慢"，竞争才是慢。无竞争时一次 mutex 加解锁在几十纳秒量级；一旦有竞争，线程要进内核挂起、等唤醒、再切换回来，成本跳到微秒级，差了两个数量级。

类型行为无竞争开销适用与边界
互斥锁拿不到就阻塞，让出 CPU，由内核挂起~10~30 ns（用户态快路径）临界区较长、可能阻塞。默认选择
自旋锁拿不到就循环重试，不让出 CPU~5~20 ns临界区极短（几十条指令）、且持锁线程不会被调度走。内核里常用，用户态慎用
读写锁读共享、写独占读锁比互斥锁略贵读远多于写、且读临界区不短。写少时可能写饥饿
乐观锁先改，提交时用 CAS 或版本号校验，失败重试一次 CAS冲突率低。冲突高时重试成本爆炸
无锁 / 无等待用原子指令保证进度一次原子指令 + 内存屏障特定数据结构（队列、栈）。实现难度高，见模块 3

自旋锁为什么不能滥用

自旋的前提是"锁马上就会释放"。如果持锁线程被操作系统抢占（时间片用完、发生缺页），自旋的核就白烧 CPU，而且可能一烧就是几毫秒。更糟的是多核机器上所有等待者一起烧，把真正持锁的线程挤得更慢。

所以自旋锁的适用条件很苛刻：临界区只有几条指令、持锁期间不调用任何可能阻塞的函数、不会被抢占。这也是为什么内核里的自旋锁要配合关抢占使用，而用户态程序基本不该手写自旋锁。

读写锁的陷阱

读写锁看起来很美，实际有两个问题：

  • 写饥饿。读者源源不断时，写者永远等不到"没有读者"的时刻。glibc 的 pthread_rwlock 默认偏向读者。要避免就得用"写者优先"的实现，但那又会饿死读者。
  • 读锁并不便宜。每次加读锁都要改共享的计数器，多个核同时改同一缓存行会导致缓存行来回弹跳（cache line bouncing），读多的时候这个开销可能超过临界区本身。读极短时，普通互斥锁反而更快。
选择的实用顺序：① 能不用共享状态就不用（消息传递、线程本地存储、分片）；② 必须共享就用最普通的互斥锁，把临界区缩到最小；③ 临界区里绝对不能做 IO、不能调用外部服务、不能 sleep；④ 只有在 profiling 证明锁竞争是瓶颈时，才考虑读写锁、分片锁或原子操作。先正确，再快。 
// 分片锁：把一把大锁拆成 N 把，按 key 哈希到不同的锁
// 适合 map 这类天然可分区的结构，能把竞争降低 N 倍
type ShardedMap struct {
    shards [64]struct {
        mu sync.Mutex
        m  map[string]int
    }
}

func (s *ShardedMap) Get(k string) int {
    idx := fnv32(k) % 64          // 同一个 key 永远落同一个分片
    sh := &s.shards[idx]
    sh.mu.Lock()
    defer sh.mu.Unlock()
    return sh.m[k]
}
模块 3

CAS 与无锁编程

CAS（Compare-And-Swap，比较并交换）是一条硬件指令，不是软件算法。x86 上是 lock cmpxchg，ARM 上是 LDXR/STXR 组成的 LL/SC 序列。它的语义是：如果内存当前值等于期望值，就写入新值并返回成功；否则不做任何修改并返回失败。整个过程原子。

// CAS 的伪代码语义
bool cas(void *addr, T expected, T desired) {
    // 以下三步由硬件保证不可分割
    if (*addr == expected) { *addr = desired; return true; }
    return false;
}

// 用 CAS 实现原子自增
for (;;) {
    T old = load(addr);
    if (cas(addr, old, old + 1)) break;   // 失败就重读重试
}

ABA 问题

CAS 只比较值，不比较"这个值有没有被改过"。经典场景是无锁栈：

线程 1 读栈顶 A，准备执行 CAS(top, A, A->next)，此时被挂起。
线程 2 弹出 A、弹出 B，然后把 A 重新压回栈。此时栈顶又是 A，但 A->next 已经指向了别处（原来是 B，现在可能是 C 或空）。
线程 1 恢复执行，CAS 成功（因为栈顶确实是 A），把 top 设成它之前读到的旧 next —— 而那个节点可能已经被释放了。
结果：栈结构损坏，或者访问已释放内存。
解法做法代价
带版本号的 CAS把 {指针, 计数器} 打包成一个 128 位值一起 CAS，每次修改计数加 1，ABA 就不可能成立x86 需要 cmpxchg16b，某些平台不支持；Java 用 AtomicStampedReference
延迟回收节点弹出后不立即释放，等确认没有线程持有旧引用再回收（hazard pointer、epoch、RCU）内存占用上升，实现复杂
不自己实现用语言或库提供的并发容器几乎没有，推荐

为什么无锁不等于更快

成本说明
缓存行争用所有线程 CAS 同一个变量，这个缓存行在核间来回迁移，每次失败重试都要重新读。竞争越激烈，有效吞吐越低
内存屏障lock 前缀指令会串行化 store buffer，本身就有几十个周期的固定开销
重试风暴N 个线程抢一个 CAS，理论上有 N-1 个要重试，高竞争下 CPU 全花在失败重试上
实现复杂度内存回收、ABA、伪共享，每一项都能写出线上事故

实测结论很反直觉：低竞争时无锁略快于 mutex，中等竞争时两者接近，高竞争时 mutex（会让出 CPU）通常反而更好，因为排队比空转更节省资源。这就是为什么成熟的运行时（Go 的 sync.Mutex、Java 的 ReentrantLock）都做成"先自旋几次，再阻塞"的混合策略。

无锁的真正优势不是性能，是进度保证：持锁线程被杀死或挂起时，锁会永远不释放；无锁算法里任何一个线程卡住，其他线程仍能继续（lock-free），甚至每个线程都能在有限步内完成（wait-free）。这个性质在实时系统、信号处理、内核中断上下文里是刚需，在普通业务代码里基本用不上。
模块 4

内存模型与 happens-before

内存模型是语言给程序员的契约：它规定了"一个线程的写，在什么条件下对另一个线程可见"。有了它，你不需要知道 CPU 到底怎么重排，只按规则推理即可。

happens-before 的五条来源

规则含义
程序顺序同一线程内，前面的语句 happens-before 后面的语句
监视器锁对同一把锁的 unlock happens-before 后续的 lock
volatile / 原子变量对同一变量的写 happens-before 后续的读
线程启动与终止Thread.start() 之前的操作对子线程可见；子线程的所有操作对 join() 之后可见
传递性A hb B，B hb C，则 A hb C。这条是把零散的同步点连成链的关键

只要建立了 happens-before，前一个线程的所有写（不只是被同步的那个变量）都对后一个线程可见。这是最容易忽略的一点：不是"volatile 变量本身可见"，而是"volatile 写之前的所有写，都对读到这个 volatile 值的线程可见"。

volatile 到底保证什么

保证说明
可见性写立即对其他线程可见，读总是读到最新值
有序性禁止 volatile 读写与其他内存操作之间的特定重排（写前不重排、读后不重排）
不保证原子性volatile int n; n++ 依然是读-改-写三步，依然会丢更新

C++ 里没有 volatile 的并发语义（它只用于 MMIO 和信号处理），要用 std::atomic。默认的 memory_order_seq_cst 最强也最贵；acquire/release 只约束必要的顺序，性能更好；relaxed 只保证原子性，不保证任何顺序。

双重检查锁为什么曾经是错的

// 曾经广泛流传、实际有 bug 的写法（Java 5 之前）
public class Singleton {
    private static Singleton instance;      // 少了 volatile
    public static Singleton get() {
        if (instance == null) {             // 第一次检查，无锁
            synchronized (Singleton.class) {
                if (instance == null) {     // 第二次检查，持锁
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

问题在 new Singleton() 不是原子操作，它分三步：① 分配内存；② 调用构造函数初始化；③ 把引用赋给 instance。②和③之间没有依赖，可能被重排成 ①③②。

此时线程 A 执行到 ③ 后被切走，instance 已经非空但对象还没初始化。线程 B 进入 get()，第一次检查发现非空，直接返回一个半成品对象，后续访问字段就是 0 或 null。

修法：给 instance 加 volatile。Java 5 之后的内存模型明确规定 volatile 写不能与之前的写重排，②③ 的顺序被固定，问题消失。C++ 里对应的是 std::atomic + release/acquire，或者更简单 —— 用函数内静态变量，C++11 保证它的初始化是线程安全的。

更好的做法是根本不要手写单例。依赖注入容器、函数内静态变量、或者启动时显式初始化，都比双重检查锁清晰。DCL 的价值主要在于它是一个绝佳的教学案例：它证明了"看起来加了锁"和"正确"之间还差一个内存模型。
模块 5

死锁：四个条件与破解

死锁不是"锁用多了"，而是四个条件同时成立。破坏任意一个，死锁就不可能发生。这也是所有预防手段的出发点。

必要条件含义怎么破坏
互斥资源一次只能被一个线程持有很难破坏（共享读场景可用读写锁、不可变数据、无锁结构）
占有并等待持有 A 的同时去申请 B一次性申请所有资源；或者申请 B 失败时释放 A 再重试
非抢占别人持有的锁不能强行夺走用带超时的 tryLock，超时后释放自己持有的锁并回退
循环等待存在 A 等 B、B 等 A 的环全局规定加锁顺序（按地址、按 ID 排序），最实用
// 死锁的标准形态：两个线程以相反顺序加锁
func transfer(from, to *Account, amount int) {
    from.mu.Lock()          // 线程 1：锁 A，等 B
    defer from.mu.Unlock()  // 线程 2：锁 B，等 A
    to.mu.Lock()
    defer to.mu.Unlock()
    from.balance -= amount
    to.balance += amount
}

// 修法一：按唯一 ID 排序，保证所有人用同一个顺序
func transfer(from, to *Account, amount int) {
    first, second := from, to
    if first.id > second.id {
        first, second = second, first
    }
    first.mu.Lock()
    defer first.mu.Unlock()
    second.mu.Lock()
    defer second.mu.Unlock()
    // 注意：这里要按原始的 from/to 做业务，不能用 first/second
}

// 修法二：带超时，失败就放弃并回退（适合无法排序的场景）
if !from.mu.TryLock() { return ErrBusy }
defer from.mu.Unlock()
if !to.mu.TryLockTimeout(50 * time.Millisecond) {
    return ErrBusy          // defer 会释放 from，不会持有并等待
}
死锁不一定发生在两把显式的锁上。这些都会构成"持有并等待"：
① 持锁时调用了一个会回调你的函数（回调里又去拿同一把锁 → 重入死锁，非可重入锁直接卡死）；
② 持锁时做网络请求，对端超时重试又打到你的另一个线程，那个线程在等同一把锁；
③ 线程池里任务 A 提交任务 B 并 wait 它的结果，而池子里所有线程都在做同样的事 —— 这叫线程饥饿死锁，把有界线程池和嵌套任务放在一起就会出现。

活锁与饥饿

现象特征例子
死锁所有线程都阻塞，CPU 占用为 0交叉加锁
活锁线程都在跑，但谁也推进不了，CPU 占用很高两个线程都用"冲突就重试 + 相同退避时间"，反复撞车
饥饿某些线程长期拿不到资源读写锁偏向读者，写线程永远排不上；低优先级线程被高优先级抢占

活锁的解法是随机化退避（加抖动），破坏"总是同时重试"的对称性。饥饿的解法是公平锁（按等待顺序排队），代价是吞吐下降。

怎么检测

jstack <PID> | grep -A 20 "deadlock"JVM 会直接算出死锁环并打印
gdb -p <PID> -ex "thread apply all bt" -ex detach看所有线程栈，找都在 futex/pthread_mutex_lock 的线程
cat /proc/<PID>/task/*/stack内核态栈，看是否卡在文件锁或内核锁上
go tool pprof http://localhost:6060/debug/pprof/goroutineGo 的 goroutine dump，能看到 semacquire 的等待链
perf top -p <PID>活锁时 CPU 高但无进展，看热点在哪个自旋函数
模块 6

协程模型

协程不是"更轻的线程"，它是用户态调度的执行流。核心区别在于：线程由内核调度，切换要进内核；协程由运行时调度，切换只在用户态保存/恢复寄存器。

维度有栈协程（stackful）无栈协程（stackless）
代表Go 的 goroutine、Lua 的 coroutine、Java 的虚拟线程C++20 coroutine、Rust async、Kotlin suspend、JS async/await
栈每个协程有自己的栈（Go 初始 2KB，按需增长）共用线程栈，状态存在编译器生成的状态机对象里
切换点任意位置，函数内部也能挂起只能在 await/yield 处挂起
内存每个协程几 KB 起一个状态机对象，通常几百字节
传染性无，普通函数直接调用有：调用链上每一层都要标 async（函数着色问题）
切换成本保存/恢复寄存器 + 栈指针，几十纳秒一次函数返回 + 状态机跳转，更接近普通调用

用户态调度省掉了什么

操作典型耗时说明
线程上下文切换1~5 µs陷入内核、保存完整寄存器与 FPU 状态、切换页表（可能刷 TLB）、调度决策
协程切换20~200 ns纯用户态，保存少量寄存器，不换页表，不刷 TLB
创建线程10~50 µs分配内核栈（默认 8MB 虚拟内存）、注册调度实体
创建 goroutine~1 µs 以内分配 2KB 栈，放进运行队列

差距在数量级上。所以一台机器开几千个线程就吃力（每个 8MB 虚拟栈 + 内核调度开销），但可以开几十万个 goroutine。

M:N 调度

Go 的运行时把 M 个 goroutine 复用到 N 个 OS 线程上，核心结构是 GMP：

角色含义
Ggoroutine，包含栈、指令指针、状态
Mmachine，真正的 OS 线程，执行 G 的载体
Pprocessor，逻辑处理器，持有本地运行队列。P 的数量默认等于 GOMAXPROCS（CPU 核数），M 必须绑定一个 P 才能执行 G

这套设计的关键在于：P 的数量限制了真正并行的数量，而 M 可以远多于 P（某个 M 因系统调用阻塞时，P 会被交给另一个 M）。所以 GOMAXPROCS 设得比核数大不会提升 CPU 密集型任务的吞吐，只会增加调度开销。

为什么协程不适合 CPU 密集任务

  • 并行度不会增加。协程是并发（concurrency）不是并行（parallelism）。真正的并行受限于核数，开十万个协程做计算，还是只有 N 个核在跑，反而多了调度开销。
  • 抢占不自由。Go 在 1.14 之前只在函数调用处检查抢占标志，一个没有函数调用的死循环会永久占住 P，让同 P 上的其他 goroutine 饿死。1.14 之后用信号实现异步抢占，但仍有开销。
  • 栈增长有成本。有栈协程栈不够时要扩容并搬移整个栈（Go 的栈是可移动的，指针会被调整），深递归场景开销明显。
  • 阻塞系统调用会拖住线程。协程里做同步 IO（尤其 cgo 调用），运行时会新开一个 OS 线程顶上，线程数暴涨，失去协程的意义。
一句话选择：IO 密集、大量并发连接 → 协程（Go / 虚拟线程 / async）；CPU 密集 → 固定大小的线程池，数量等于核数；两者混合 → 分离成两个池，别让计算任务堵住 IO 任务的调度器。
模块 7

Actor 与消息传递

共享内存和消息传递是两种哲学：前者用同步原语保护同一块数据，后者让数据只属于一个执行体，通过发消息来协作。前者快但容易错，后者不容易错但有传递成本。

维度共享内存消息传递
数据归属多个线程访问同一块内存每份数据有唯一所有者
同步手段锁、原子变量、条件变量发送/接收消息，天然串行化
典型 bug竞态、死锁、可见性消息丢失、邮箱堆积、顺序错乱
性能快（直接读写内存）有拷贝或入队开销
可扩展性跨进程/跨机几乎不可行天然支持分布式（位置透明）

Actor 模型的三条规则

每个 Actor 有唯一地址和邮箱。外部只能往邮箱发消息，不能直接读它的内部状态。
消息串行处理。一个 Actor 同一时刻只处理一条消息，所以内部状态不需要加锁 —— 这是它消灭数据竞争的根源。
处理消息时可以创建新 Actor、发消息给别的 Actor、改变自己的状态。但不能共享可变状态。
// Actor 风格的计数器（伪代码）
type Counter struct {
    count int          // 只被本 actor 的 mailbox 处理循环访问，无需加锁
    inbox chan Msg
}

func (c *Counter) run() {
    for msg := range c.inbox {      // 串行处理，天然互斥
        switch m := msg.(type) {
        case Inc:
            c.count += m.N
            m.Reply <- c.count
        case Get:
            m.Reply <- c.count
        }
    }
}

// 外部只能发消息，拿到的是一个 channel，不是 count 本身
func (c *Counter) Inc(n int) int {
    reply := make(chan int, 1)
    c.inbox <- Inc{N: n, Reply: reply}
    return <-reply
}

代价是什么

代价说明
邮箱无界 → 内存爆炸生产快、消费慢时消息堆积。必须有背压（backpressure）：有界队列 + 阻塞发送，或丢弃 + 降级
消息拷贝大对象传递要么深拷贝（CPU 与 GC 压力），要么用不可变数据共享（要求纪律）
没有全局一致性跨 Actor 的操作不是原子的。转账要么用 saga/补偿，要么把两个账户合并进一个 Actor（会限制并行度）
调试困难调用栈不再是"谁调了谁"，而是消息流。需要分布式追踪才能还原因果
死信与顺序消息可能丢、可能乱序、可能重复投递，业务要自己处理幂等
Go 的 channel 不是 Actor。channel 是一等公民的数据结构，可以在任意 goroutine 之间传递；Actor 是执行体的封装，消息必须发给某个 Actor 的邮箱。CSP（Communicating Sequential Processes，Go 采用的模型）强调"通过 channel 同步"，Actor 强调"通过邮箱解耦"。两者都能避免共享可变状态，但 Actor 天然带地址、可跨机，CSP 的 channel 是进程内的。
模块 8

并发 bug 的排查

竞态难复现的根本原因是时间窗口极窄：两条指令之间可能只隔几个 CPU 周期，要恰好在这个窗口内发生线程切换或另一核写入。所以它的出现概率可能是百万分之一，但生产环境每秒百万请求，一天就撞上好几次。

为什么难复现

因素说明
窗口极窄两条指令之间只有几纳秒，绝大多数时候不会撞上
依赖硬件需要多核、特定的缓存状态、特定的内存序，单核开发机永远不复现
依赖负载低并发时线程不交错，高并发才暴露。压测是必要手段
观察即改变加日志、挂调试器都会改变时序，bug 消失（典型的 Heisenbug）
编译器与优化级别-O0 下顺序恰好正确，-O2 重排后出错

race detector 的原理

主流实现是 ThreadSanitizer（Go 的 -race 就是它）。做法是给每个内存位置维护向量时钟（vector clock，记录每个线程最后访问它的逻辑时间），每次读写都检查：

  • 两次访问同一地址；
  • 至少有一次是写；
  • 两者之间没有 happens-before 关系（不通过锁、原子变量、channel 建立顺序）。

三条同时满足，就报数据竞争。

指标典型值
CPU 开销5~15 倍
内存开销5~10 倍（影子内存记录访问历史）
漏报有。没执行到的路径不检测
误报极少（它只报真正缺少 happens-before 的访问）
最常见的错误用法：在测试环境跑一次 -race，没报错就上线。正确的做法是：把它放进 CI，每次提交都跑；并且用高并发压测驱动，让代码路径尽量都被执行到。覆盖率不够的 race 检测，等于没检测。

组合排查法

先确认是不是并发问题。单线程压测正常、多线程异常；或者降低并发就消失；或者加日志后消失 —— 三条中任一条成立，基本可以锁定。
用 race detector 扫一遍。能直接给出两处冲突访问的调用栈，这是成本最低的一步。
放大窗口。在可疑位置插入随机 sleep、runtime.Gosched()、或者人为增加循环次数，让交错更容易发生。只用于复现，不要提交。
加压。把并发数调到远高于生产（比如 10 倍），跑长稳测试。竞态的概率随并发上升而急剧上升。
加带序号的结构化日志。每条日志带线程 ID、时间戳、单调递增序号，事后还原交错顺序。日志本身要无锁或低开销，否则会掩盖问题。
用确定性重放。rr 这类工具能录下整个执行过程并重放，让 bug 100% 复现。代价是只支持特定平台，且录制开销大。
# Go：把 race 检测放进 CI，并用高并发驱动
go test -race -count=10 ./...
GOMAXPROCS=8 go test -race -run TestConcurrent -count=100

# 看 goroutine 数量和阻塞点
curl -s http://localhost:6060/debug/pprof/goroutine?debug=1 | head -30

# C/C++：TSan + 压测
gcc -fsanitize=thread -g -O1 -pthread stress.c -o stress
TSAN_OPTIONS="halt_on_error=0 history_size=7" ./stress

# 看上下文切换是否异常（锁竞争激烈时每秒几万次）
pidstat -w -p <PID> 1
perf stat -e context-switches,cpu-migrations -p <PID> sleep 5
最后的防线是设计，不是排查。把共享可变状态降到最少：能用不可变数据就不用可变，能用消息传递就不用共享内存，能用一个 goroutine 独占一份数据就不要加锁。竞态的数量与共享状态的数量是平方关系 —— 少一处共享，少十处 bug。
常见坑

十个踩过才知道的坑

1
用 volatile 当计数器
volatile 只保证可见性和有序性，不保证原子性。n++ 仍是读-改-写，多线程下照样丢更新。计数要用 atomic 或加锁。
2
双重检查锁忘了 volatile
new 的三步可能被重排成"分配-赋值-初始化"，另一个线程会拿到半初始化对象。Java 里必须给 instance 加 volatile，C++ 用 atomic 或函数内静态变量。
3
在锁里做 IO 或调用外部服务
临界区从纳秒级变成毫秒级，所有线程排队。锁内只做内存操作，IO 移到锁外，或者用"先在锁内取快照，锁外再处理"。
4
不同代码路径用不同的加锁顺序
A 函数先锁 X 再锁 Y，B 函数先锁 Y 再锁 X，必然死锁。全局规定顺序（按 ID、按地址排序），并写进注释。
5
手动 Lock 之后忘了 Unlock
中间 return 或 panic 就永久泄漏锁。Go 用 defer，Java 用 try/finally，C++ 用 RAII（lock_guard）。不要相信"我每一条路径都写了"。
6
以为读写锁一定比互斥锁快
读锁也要改共享计数，多核下缓存行弹跳很贵；写少时还会写饥饿。读临界区极短时，普通 mutex 往往更快。
7
认为无锁队列一定比 mutex 快
高竞争下所有线程 CAS 同一个缓存行，失败重试把 CPU 烧光；mutex 会让出 CPU 排队，反而更省资源。低竞争才有优势。
8
在协程里做 CPU 密集计算或同步阻塞调用
协程不增加并行度，还会占住调度线程；阻塞系统调用（尤其 cgo）会让运行时不断新建 OS 线程。计算任务放独立线程池。
9
用 sleep 代替同步
"等 100ms 对方应该写完了"在负载高时必然失效。用 channel、WaitGroup、条件变量、future 做真正的同步。
10
只在本地跑一次 -race 就认为没问题
race detector 只报实际执行到的路径。要放进 CI、配合高并发压测、反复跑，覆盖率不够等于没测。
自测

六道题

1. 两个线程各执行 100 万次 counter++，最终结果小于 200 万。这属于哪类问题？
正确答案：原子性。counter++ 是读、加、写三步，两个线程交错时会互相覆盖。修法是加锁或用原子自增。
2. 双重检查锁在 Java 5 之前为什么是错的？
正确答案：指令重排。赋值可能先于构造完成，另一个线程看到非空引用就直接返回半成品。加 volatile 禁止这种重排即可修复。
3. 无锁栈的 ABA 问题，最直接的解法是？
正确答案：带版本号的 CAS。值相同但版本不同就判定失败，ABA 无法成立。也可以用延迟回收（hazard pointer、epoch）避免节点被复用。
4. 要破坏死锁的"循环等待"条件，最实用的做法是？
正确答案：统一加锁顺序。所有人按同一顺序申请，就不可能形成环。加超时破坏的是"非抢占"条件，也是一条可行路径。
5. 为什么协程不适合 CPU 密集任务？
正确答案：不增加并行度。开十万个协程做计算，还是只有 N 个核在跑。CPU 密集应该用固定大小的线程池，数量等于核数。
6. 关于 race detector，哪个说法是对的？
正确答案：只能发现实际发生的竞争。它靠影子内存记录访问历史，没执行到的代码路径不检测，且有 5~15 倍 CPU 开销。要放进 CI 并配合高并发压测。

// C++11 的六种 memory_order，从强到弱
memory_order_seq_cst   // 全局单一总序，最安全也最贵（默认）
memory_order_acq_rel   // 读用 acquire，写用 release，用于读改写操作
memory_order_release   // 之前的读写不能重排到这条之后（发布数据）
memory_order_acquire   // 之后的读写不能重排到这条之前（获取数据）
memory_order_consume   // 依赖序，实践中基本没人用，多数编译器按 acquire 处理
memory_order_relaxed   // 只保证原子性，不保证任何顺序

// 典型的生产者-消费者发布模式
data = 42;                                    // 普通写
flag.store(true, std::memory_order_release);  // 发布：保证 data 先可见

// 消费者
while (!flag.load(std::memory_order_acquire)) {} // 获取：保证能看到 data
assert(data == 42);                              // 一定成立
