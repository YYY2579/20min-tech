二十分钟学透虚拟化原理

虚拟化不是"软件模拟一台电脑"，而是用硬件和内核配合，让每个 Guest 以为自己独占一台机器。理解这句话，就能解释为什么 VM 启动要几十秒、为什么 IO 有 10 倍差距、为什么容器不是虚拟化。

开始前

先确认你在哪一层

很多性能问题，第一步是搞清楚"我现在跑在裸机、虚拟机还是容器里"。

# 1. 我在虚拟机里吗？
systemd-detect-virt
# kvm / vmware / microsoft / none（none 表示裸机）

# 2. 虚拟化平台和型号
sudo dmidecode -s system-product-name
# KVM / VMware Virtual Platform / VirtualBox

# 3. CPU 是否支持硬件虚拟化（想在宿主机上开 KVM 才需要）
grep -E -o 'vmx|svm' /proc/cpuinfo | sort -u
# vmx = Intel VT-x，svm = AMD-V。有输出说明支持
sudo kvm-ok          # 需要 cpu-checker 包

# 4. 是不是容器（容器里通常没有 virt 标识，但 cgroup 名字会暴露）
cat /proc/1/cgroup | head -3
# 0::/docker/3f2a... 或 /kubepods/... 说明在容器里

# 5. 看 NUMA 拓扑（选型时决定绑核策略）
lscpu | grep -E 'Socket|Core|Thread|NUMA'
numactl -H | head -12
一个常见的误判：systemd-detect-virt 返回 none 不代表一定在裸机——某些精简的虚拟化环境（尤其是嵌套虚拟化或某些 ARM 平台）没有暴露 DMI 信息。反过来，kvm 也不一定说明你在云上，可能只是本地开发机。要交叉验证 /sys/class/dmi/id/product_name、/proc/cpuinfo 的 hypervisor 标志、以及磁盘设备名（/dev/vda 通常是 virtio）。
模块 1

虚拟化的三条路线

核心矛盾只有一个：Guest 内核以为自己在 Ring 0，可以执行特权指令，但它其实不在 Ring 0。三种方案就是三种"骗术"。

方式怎么骗Guest 要不要改代表
全虚拟化
（二进制翻译）		Hypervisor 扫描 Guest 的代码，把特权指令动态替换成对 Hypervisor 的调用不用改，装原版系统即可早期 VMware、VirtualBox（部分场景）、QEMU TCG
半虚拟化
（paravirt）		不骗了，直接约定一套 hypercall 接口，Guest 主动调用要改内核（或装驱动）Xen PV、virtio 驱动、KVM 的 PV 特性
硬件辅助CPU 新增一套"根模式/非根模式"，Guest 直接跑在硬件上，只有敏感操作才陷入不用改Intel VT-x、AMD-V、ARM EL2

为什么早期 x86 不能虚拟化

1974 年 Popek 和 Goldberg 提出一个架构要能虚拟化，必须满足"敏感指令集是特权指令集的子集"。x86 违反了这条：有一批指令既敏感又不是特权——它们能读到或影响全局状态，但在 Ring 3 下执行不会触发异常，只是安静地返回一个错误的值。

指令问题
popf试图改中断标志位，Ring 3 下不报错，只是静默失败。Guest 以为自己关了中断，其实没关
sgdt / sidt能读到真实的 GDT/IDT 地址，暴露 Hypervisor 的存在
smsw读到真实的机器状态字
lar / lsl段限长检查，结果与虚拟环境不一致

这些指令在 Ring 3 不陷入，Hypervisor 就没机会介入。VMware 的解法是二进制翻译：运行时扫描代码块，遇到这些指令就替换掉。代价是每次执行都要翻译/查缓存，早期实测开销 5~20 倍，而且代码缓存管理极其复杂。

硬件辅助：VT-x 与 AMD-V

2005 年前后 Intel VT-x 和 AMD-V 出现，思路是在 Ring 0 之外再加一层：

两种模式：root 模式（Hypervisor 跑这里）和 non-root 模式（Guest 跑这里）。Guest 内核仍然跑在自己的 Ring 0，但它处在 non-root 里，是一个"假的 Ring 0"。
VMCS：每 vCPU 一块内存（Virtual Machine Control Structure），保存 Guest 的寄存器状态、以及哪些操作要触发 VM Exit 的配置位图。
VM Exit：Guest 执行了被配置为"拦截"的指令（如读写 CR3、执行 hlt、访问特定 IO 端口），CPU 自动保存 Guest 状态、切到 root 模式、跳到 Hypervisor 的处理入口。
VM Entry：Hypervisor 处理完，执行 VMLAUNCH / VMRESUME 回到 Guest，CPU 恢复 Guest 状态。

ARM64 上对应的是 EL2（Hypervisor 异常级别），概念完全一致：Guest 内核在 EL1，Hypervisor 在 EL2，敏感操作触发异常到 EL2。

嵌套虚拟化（nested）为什么慢：L1 Hypervisor 本身跑在 L0 的 non-root 里，当 L2 Guest 触发 VM Exit 时，要先退出到 L1，L1 再决定是否需要退出到 L0。一次操作可能变成两三次 Exit，延迟翻倍。这就是"在云主机里再开 VM"体验差的原因。
模块 2

CPU 虚拟化：VM Exit 的代价

硬件辅助不是免费的。每一次 VM Exit 都是一次"上下文切换 + 世界切换"，比系统调用贵得多。

操作典型耗时说明
函数调用1~2 ns基线
系统调用50~500 ns用户态 → 内核态
VM Exit + Entry1~3 μs保存/恢复全部 vCPU 状态、切换世界。较新的 CPU 可到 0.5~1μs
进程上下文切换2~5 μs同量级，但 VM Exit 更不可控
一次网络收发包（虚拟化路径）5~20 μs可能包含多次 Exit

关键在于次数。一个 Guest 每秒触发 10 万次 VM Exit，光切换就是 0.1~0.3 秒的 CPU 时间——这还没算 Hypervisor 里处理逻辑的开销。

哪些操作会触发 Exit

类别例子优化手段
特权指令读写 CR3（切页表）、lgdt、invlpgVPID/ASID 让 TLB 不冲刷；PCID
IO 端口访问in / out 指令改用 MMIO 或 virtio；减少设备模拟
MMIO 访问读写设备寄存器内核同页合并（KSM）、减少 MMIO 次数

halt / 停机Guest 空闲时执行 hlt这是好事，让出物理 CPU

三个关键优化

1. VPID / ASID：别每次都冲 TLB

没有 VPID 时，每次 VM Entry/Exit 都要冲刷整个 TLB，因为 CPU 分不清哪些页表项属于哪个 Guest。VPID（Virtual Processor ID）给每个 vCPU 一个标签，TLB 项带上标签，切换时不用冲。这一项能把 Exit 密集场景的性能提升 10%~30%。

2. 大页：减少页表层级和 TLB 压力

2MB 大页让一个 TLB 项覆盖 512 倍的内存，TLB 命中率显著提升。KVM 上给 Guest 配 hugepages 通常能带来 5%~15% 的性能提升，内存密集应用更多。

3. CPU 绑核与隔离

# 宿主机上把物理核留给某个 VM 独占，避免调度抖动
# 1. 内核启动参数隔离 CPU（需要重启）
# isolcpus=4-11 nohz_full=4-11 rcu_nocbs=4-11

# 2. 把 vCPU 线程绑到隔离的物理核
# 先找到 vCPU 线程
ps -eLo pid,tid,psr,comm | grep -E 'CPU [0-9]+/KVM'
#  9812  9813   3 CPU 0/KVM
#  9814  9815   5 CPU 1/KVM
taskset -cp 4 9813
taskset -cp 5 9815

# 3. 验证：看 vCPU 线程是否稳定在指定核
watch -n1 'ps -eLo psr,comm | grep KVM'
"vCPU 数量"不等于"物理核数量"。给 VM 配 8 个 vCPU，如果宿主机只有 4 个物理核（8 线程），那么这 8 个 vCPU 是在 8 个超线程上分时复用。一旦所有 vCPU 同时忙，就会出现 vCPU 等待物理 CPU，Guest 里表现为 %steal 升高。这是云主机"看起来配置很高但很卡"的头号原因。
模块 3

内存虚拟化：影子页表与 EPT

内存虚拟化比 CPU 更麻烦，因为 Guest 的页表里存的是"Guest 物理地址"，而硬件 MMU 只认"宿主物理地址"。

三层地址

地址类型缩写含义
虚拟地址VAGuest 里进程看到的地址
Guest 物理地址GPAGuest 以为的"物理地址"
宿主物理地址HPA真正的内存条地址

Guest 的页表做的是 VA → GPA 的映射。硬件 MMU 需要 VA → HPA。中间少了一环。

方案一：影子页表（shadow page table）

Hypervisor 为每个 Guest 进程维护一份"影子页表"，里面直接是 VA → HPA。Guest 改自己的页表时，Hypervisor 要拦截（把 Guest 页表设为只读，写入触发缺页），然后同步更新影子页表。

优点缺点
Guest 侧 TLB 命中就是一次地址翻译，性能好每次 Guest 改页表都要 Exit，进程切换、mmap、缺页都会触发同步
不需要硬件支持影子页表本身占内存；实现复杂，容易出 bug

实测影子页表的开销在内存密集型负载下可达 30%~50%，进程创建/切换频繁时更糟。

方案二：EPT / NPT（硬件二级页表）

Intel 叫 EPT（Extended Page Table），AMD 叫 NPT（Nested Page Table），ARM 叫 stage-2 translation。思路是让硬件做两次翻译：

Guest 的 CR3 指向 Guest 页表，硬件先按它把 VA 翻成 GPA（这一步和裸机一样，由 Guest 内核控制）。
硬件再查 EPT（由 Hypervisor 维护），把 GPA 翻成 HPA。
两次翻译的结果可以缓存进 TLB，后续访问一次命中，不需要 Exit。
如果 EPT 里没有这个映射，触发 EPT Violation，退出到 Hypervisor，由它决定是分配内存还是报错。

这就是为什么 EPT 让虚拟化性能接近裸机：正常的地址翻译完全在硬件里完成，Guest 改页表也不再需要 Exit。

代价：TLB 压力翻倍

两次翻译意味着一次 VA→HPA 的映射要占更多 TLB 项（或者需要更长的查找）。这带来两个直接后果：

  • TLB miss 变多。同样大小的 TLB，能覆盖的内存范围变小。内存密集型应用（数据库、JVM 堆）受影响最大。
  • 页表遍历变长。4 级 Guest 页表 + 4 级 EPT = 最坏 20 次内存访问才能完成一次翻译（实际有缓存，但 miss 时确实很贵）。
# 看 EPT 的命中情况和缺页次数（KVM 宿主）
sudo perf kvm stat live
# 关注 EPT_VIOLATION / EPT_MISCONFIG 事件

# 看 Guest 里的 TLB 相关性能计数器
perf stat -e dTLB-load-misses,dTLB-store-misses -a sleep 5

# 缓解手段：大页
# Guest 内启用 2MB 大页（透明大页或显式 hugetlbfs）
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never

# 宿主机侧给 VM 分配 hugepages
cat /proc/meminfo | grep -i huge
一句话对比：影子页表是用软件换硬件（省硬件支持，费 Exit）；EPT 是用硬件换软件（省 Exit，费 TLB）。现代 CPU 都有 EPT，影子页表基本只剩历史意义，但它的思路（拦截写页表）在嵌套虚拟化和某些安全场景里还在用。
模块 4

IO 虚拟化：差距最大的地方

CPU 和内存虚拟化的开销通常在 5% 以内，IO 可以差 10 倍以上。选型时最该关注的就是这一层。

四种方案，四代技术

方案原理性能（相对裸机）典型场景
全模拟
emulated		QEMU 用软件模拟一块真实网卡（如 e1000），Guest 的每次寄存器读写都要 Exit 到 QEMU 处理10%~30%兼容性优先、老系统、调试
virtio
半虚拟化		Guest 装 virtio 驱动，和宿主约定共享内存环（vring），批量提交描述符，减少 Exit50%~80%绝大多数云主机的默认选择
vhost / vhost-user把 virtio 的后端从 QEMU 用户态进程挪到内核（vhost-net）或独立进程（DPDK），减少一次上下文切换70%~90%高吞吐网络、NFV
SR-IOV / 直通网卡硬件虚拟出多个 VF（Virtual Function），每个 VF 直接分配给一个 VM，DMA 直达90%~98%高性能计算、数据库、低延迟交易

virtio 为什么快

核心是把"一次操作一次 Exit"改成"一批操作一次 Exit"。以发送为例：

Guest 驱动把"要发的缓冲区地址和长度"写进 vring（一块 Guest 和宿主共享的物理内存），这是一个描述符数组。
Guest 更新 avail ring 的索引，然后写一个 MMIO 寄存器（或触发一个通知）告诉宿主"有新请求"。
宿主侧的 vhost 从 vring 里批量取出描述符，直接组包发出，一次处理几十个请求。
发完后宿主更新 used ring，必要时发一个中断给 Guest。Guest 也可以选择轮询（virtio_poll）避免中断开销。

对比全模拟：e1000 每发一个包，Guest 要读写好几个 MMIO 寄存器，每个都是一次 VM Exit。virtio 把几十个包压缩成一两次通知。

SR-IOV：把硬件切开

SR-IOV 让一块物理网卡在硬件层虚拟出多个 VF（Virtual Function），每个 VF 有自己的 PCI 配置空间、自己的队列和中断。通过 IOMMU（Intel VT-d / AMD-Vi）做 DMA 重映射，保证 VF 只能访问分配给它的内存。

# 宿主机上看网卡是否支持 SR-IOV
lspci -vv -s 0000:3b:00.0 | grep -i 'Single Root'
# Capabilities: [160] Single Root I/O Virtualization (SR-IOV)

# 开启 VF（不同驱动路径不同，以 Intel ixgbe 为例）
echo 8 > /sys/class/net/eth0/device/sriov_numvfs
lspci | grep 'Virtual Function'

# 把 VF 直通给 VM（libvirt 配置片段）
<interface type='hostdev' managed='yes'>
  <source><address type='pci' domain='0' bus='0x3b' slot='0x10' function='0x1'/></source>
</interface>

# 验证：Guest 里应该看到独立的网卡，且 driver 是真实驱动（如 ixgbevf）
ethtool -i eth0
SR-IOV 的三个代价：① 不能热迁移——VF 绑定了物理位置，迁移就得先解绑再重新绑定，会有秒级中断；② 宿主看不到流量，安全组、抓包、QoS 都要在交换机或 VF 侧做；③ VF 数量有限，一块卡通常 32~128 个，且要和宿主机自己用的队列抢。
所以云厂商的"高性能网络"通常是可切换的：普通模式走 virtio（能迁移、能限流），高性能模式走 SR-IOV（快但不能迁移）。

模块 5

容器不是虚拟化

这是最容易被说错的一句话。容器和 VM 解决的是不同的问题，只是用起来像。

维度虚拟机容器
隔离的是什么一整套硬件（CPU、内存、磁盘、网卡）视图：命名空间 + cgroup 限制
有没有自己的内核有，每个 VM 跑一个完整内核没有，共享宿主机内核
系统调用路径Guest 内核 → VM Exit → 宿主内核直接进宿主内核，没有中间层
启动时间秒到分钟（要引导内核、初始化设备）毫秒到秒（就是 fork + exec）
内存开销每台至少几百 MB（内核 + 页表 + 设备模型）几 MB 到几十 MB
隔离强度强，硬件级边界弱，共享内核，一个内核漏洞可能穿透
能否跑不同内核能，Windows / 老版本 Linux 都行不能，必须和宿主内核兼容
密度单机几十台单机几百到几千个

容器"看起来像虚拟机"的原因

因为容器做了一件很巧的事：给它一个独立的根文件系统。你在容器里看到 /etc/os-release 写着 Ubuntu，那只是镜像里带的文件，和内核版本毫无关系。所以：

# 容器里看"系统版本"
cat /etc/os-release
# PRETTY_NAME="Ubuntu 24.04 LTS"   ← 这只是镜像里的一个文本文件

# 但内核是宿主机的
uname -r
# 6.8.0-45-generic   ← 宿主机内核，不是 Ubuntu 24.04 自带的

# 证明共享内核：容器里看到的模块列表就是宿主的
ls /lib/modules/
# 通常为空或只有宿主版本，因为容器不该加载模块
一个直接推论：容器里不能"重启内核"、不能加载内核模块、不能改全局 sysctl。很多人在容器里装 Docker、装 VPN、装需要 /dev/net/tun 的软件，然后发现各种权限错误——因为它们本质上是在要求"操作宿主机内核"。这不是配置问题，是模型不允许。

那 Kata / gVisor / Firecracker 算什么

方案做法本质
Kata Containers每个容器跑在一个轻量 VM 里，接口还是容器运行时是 VM，只是用起来像容器
gVisor用 Go 实现一个用户态内核（Sentry），拦截应用的系统调用自己处理用户态内核，不是 VM 也不是普通容器
Firecracker极简 VMM，只保留 virtio-net/block 和最小设备模型，启动 <125ms微虚拟机，AWS Lambda 的底座
普通 runcnamespace + cgroup + chroot真容器

这些方案的共同目标是在"容器级轻量"和"VM 级隔离"之间找平衡点。多租户 SaaS 跑不可信代码时，值得付出这部分开销。

为什么 VM 的启动慢

不是"虚拟化本身慢"，而是要模拟一次完整的开机：固件（SeaBIOS/UEFI）→ 引导加载器 → 内核解压 → 设备探测 → init 系统 → 启动服务。这套流程在裸机上多久，在 VM 里也差不多，还要加上设备模拟的开销。

所以"快速启动"的 VM 方案（Firecracker、Cloud Hypervisor）都在做减法：去掉 BIOS、精简设备模型、直接用内核引导协议，把启动压到 100ms 级。代价是牺牲了兼容性（不能装 Windows、不能随便加设备）。

为什么容器的 IO 几乎无损

因为容器的 IO 路径和宿主机进程完全一样：应用 → 系统调用 → 宿主内核 → 块层 → 驱动。唯一多出来的是 overlayfs 的路径解析（如果用的是 overlay 根文件系统），以及 cgroup 的 IO 限速（如果配了 io.max）。

# 容器里测 IO，和宿主机测出来的差异通常 <5%（无 IO 限速时）
fio --name=randwrite --ioengine=libaio --iodepth=32 --rw=randwrite \
    --bs=4k --size=1G --numjobs=4 --runtime=30 --group_reporting

# 如果容器配了 IO 限速，会看到明显下降
cat /sys/fs/cgroup/<cgroup>/io.max
# 8:0 rbps=10485760 wbps=10485760 riops=1000 wiops=1000
一个反直觉的结论：容器的"轻量"不是因为技术更先进，而是因为它什么都不做——不模拟硬件、不引导内核、不隔离页表。它的快是用隔离强度换来的。需要强隔离时，还是得回到 VM 或微虚拟机。
模块 7

云主机选型：三个必须懂的陷阱

云上的"8 核 16G"和物理机的"8 核 16G"不是一回事。区别写在计费模型里。

陷阱一：共享型 vs 独享型

类型CPU 分配方式适用
共享型vCPU 是超卖的，多个 VM 分时复用同一批物理核。通常超卖 2~8 倍低负载、开发测试、个人站点
独享型vCPU 绑定到固定的物理线程，不超卖生产数据库、高并发服务、延迟敏感
裸金属整台物理机给你，没有 Hypervisor 层极致性能、特殊硬件、合规

共享型最典型的表现是 %steal 高——你的 vCPU 想跑，但物理核被别的 VM 占着。这个值在 top 里显示为 st，在 mpstat 里是 %steal。

# 判断是否被"邻居"影响
mpstat -P ALL 1 10
# %steal 持续 > 5% 就说明物理 CPU 不够分；> 20% 基本没法跑延迟敏感业务

# 看 CPU 的真实型号和频率（共享型常被限制在较低频率）
lscpu | grep -E 'Model name|MHz|CPU\(s\)'
cat /proc/cpuinfo | grep 'cpu MHz' | head -4

# 看是否被限频（cgroup cpu.max 或 cpufreq）
cat /sys/fs/cgroup/cpu.max
# 200000 100000  → 每 100ms 只能用 200ms 的 CPU 时间（= 2 核）

陷阱二：突发性能实例的 CPU 积分

这类实例（各家的叫法不同，常见后缀 t5/t6 或"突发型"）的卖法是：基准性能很低，但可以短时间冲到 100%。冲的额度来自"CPU 积分"。

机制说明
基准性能通常只有 10%~15% 的单核性能。比如 2 核实例的基准可能只有 0.2 核
积分获取空闲时按基准性能的余量累积，通常每分钟 1~2 分
积分消耗跑满 100% 时按超出部分消耗，1 vCPU 跑满 1 分钟约消耗 60 分
积分耗尽强制降频到基准性能，不是关机，是变慢——通常慢 5~10 倍
无上限模式可以关掉限制，但超出部分按量计费，账单可能翻几倍
这是云上最隐蔽的性能陷阱。压测时一切正常（积分充足），上线后跑了几小时突然变慢，CPU 使用率看起来还是 100%，但 QPS 掉到 1/5。因为 CPU 时间没变，但有效算力被限制了。
判断方法：看实例的 CPU 积分余额（云监控里有这个指标），或者观察"CPU 使用率 100% 但吞吐周期性下降"的模式。突发型实例只适合长期低负载、偶发峰值的场景，比如个人博客、测试环境、定时任务。

陷阱三：云盘的 IOPS 和吞吐是两回事

云盘通常按容量分档，每档有三个独立上限：IOPS、吞吐（MB/s）、容量。三者任一打满都会成为瓶颈，而且小文件看 IOPS、大文件看吞吐。

负载类型瓶颈例子
数据库（8K 随机读写）IOPSMySQL OLTP、Redis AOF
日志顺序写（1M 大块）吞吐Kafka、日志采集
混合负载两者都可能需要分别压测
# 分别测 IOPS 和吞吐
# 4K 随机读，看 IOPS
fio --name=iops --ioengine=libaio --iodepth=64 --rw=randread --bs=4k \
    --size=4G --runtime=30 --group_reporting

# 1M 顺序读，看带宽
fio --name=bw --ioengine=libaio --iodepth=32 --rw=read --bs=1M \
    --size=4G --runtime=30 --group_reporting

# 注意：fio 的 --size 要大于云盘缓存，否则测的是缓存不是盘
# 建议 --size 至少是内存的 2 倍，或用 --direct=1 绕过页缓存
模块 8

什么时候必须用 VM

容器能解决 80% 的问题，剩下 20% 是容器在模型上做不到的。

需要不同内核
老应用依赖 3.10 内核的某个行为，宿主机是 6.x；或者要跑 FreeBSD。容器共享内核，做不到。
强隔离 / 多租户
跑不可信代码（用户上传的函数、CI 任务）。容器共享内核，一个内核漏洞就是全部沦陷。
Windows / 异构系统
Windows 容器需要 Windows 宿主，Linux 上跑 Windows 只能靠 VM。
内核级调试
要改内核、装模块、用 kprobe/ftrace 深度调试。容器里没有权限，也不该有。
整机迁移 / 快照
VM 可以整机快照、热迁移、克隆。容器只能快照文件系统，进程状态带不走。
合规与边界
等保、金融合规常要求"物理隔离"或"独立内核"，容器很难论证满足。

决策流程

第一步：能不能共享内核？如果应用只依赖标准系统调用、不需要改内核参数、不需要加载模块 → 容器可行。
第二步：隔离要求有多高？跑自己的代码 → 容器够用。跑别人的代码 → 至少 Kata/gVisor，最好 VM。
第三步：性能瓶颈在哪？CPU 密集 → 容器和 VM 差别不大。网络/磁盘 IO 密集 → 优先容器，或 VM + SR-IOV。
第四步：运维复杂度能不能接受？容器需要镜像、编排、网络方案；VM 需要镜像模板、补丁、监控。团队能力决定最终选择。
实践中的常见组合：用 VM 做隔离边界（每个租户一台或一组 VM），用容器做部署单元（VM 内部跑 K8s 或 Docker Compose）。这样既有硬件级隔离，又有容器的部署效率。绝大多数云厂商的托管 K8s 就是这么做的——节点是 VM，Pod 是容器。
常见坑

十个选型与运维坑

1
把容器当虚拟机用
在容器里装 systemd、改内核参数、加载模块、跑 dockerd。这些操作要么失败，要么影响宿主机。容器是"一个进程"，不是"一台机器"。
2
给 VM 配的 vCPU 超过物理核数
8 个 vCPU 挤在 4 个物理核上，全部忙时互相抢，%steal 飙升。vCPU 总数不应超过物理线程数，延迟敏感场景还应留 1~2 核给宿主。
3
买了突发型实例跑生产
积分耗尽后 CPU 降到基准的 10%~15%，表现为"CPU 100% 但 QPS 掉到 1/5"。突发型只适合长期低负载 + 偶发峰值。
4
只看云盘的容量，不看 IOPS 档位
500GB 的高档盘和 5TB 的低档盘，IOPS 可能差 10 倍。数据库选盘要先算"每秒多少次 8K 随机写"，再对照档位。
5
用 fio 测云盘但不加 direct=1
测的是页缓存和云盘缓存，数字好看但不真实。必须 --direct=1，且 --size 大于内存，否则测不出真实 IOPS。
6
开了 SR-IOV 才发现不能热迁移
VF 绑定物理位置，迁移要解绑重绑，有秒级中断。需要迁移能力的业务应该用 virtio，或者接受"高性能 = 不可迁移"。
7
在 VM 里再开 VM（嵌套虚拟化）
一次操作可能触发两三层 VM Exit，性能下降 30%~60%，而且很多云厂商默认不开放 nested。CI 里跑模拟器要提前确认。
8
以为容器能限制所有资源
cgroup 能限 CPU、内存、IO、PID 数，但限不了内核态共享资源（如 conntrack 表、ARP 表、文件句柄总数）。一个容器打满 conntrack，全机网络都受影响。
9
忽略 %steal 这个指标
Guest 里看到的 CPU 使用率不包含"想跑但没排上"的时间。%steal 高说明宿主超卖严重，此时优化应用毫无意义，应该换实例规格。
10
用容器做安全边界
容器共享内核，逃逸漏洞（如 dirty pipe、overlayfs 提权）影响所有容器。多租户跑不可信代码，至少要用 Kata/gVisor 或独立 VM。
自测

六道题

1. 早期 x86 难以虚拟化的根本原因是？
正确答案：敏感非特权指令。比如 popf、sgdt 在 Ring 3 下静默失败而不报错，Guest 以为自己改了状态，实际没有。VMware 只能用二进制翻译把这些指令替换掉，开销 5~20 倍。
2. 一次 VM Exit + Entry 的典型耗时是？
正确答案：1~3 微秒。比系统调用（50~500ns）贵一个数量级。所以虚拟化优化的核心是减少 Exit 次数，而不是让单次 Exit 更快。
3. EPT/NPT 相比影子页表，最大的优势是？
正确答案：免 Exit。影子页表要在 Guest 每次改页表时拦截同步；EPT 让硬件做两次翻译，Guest 改自己的页表随便改。代价是 TLB 压力变大，一次映射占更多项。
4. virtio 比全模拟网卡快，核心原因是？
正确答案：批量 + 共享内存。全模拟的 e1000 每个包要读写多个 MMIO 寄存器，每次都是 Exit；virtio 把几十个描述符放进 vring，一次通知处理完。
5. 容器和虚拟机的本质区别是？
正确答案：共享内核 vs 独立内核。容器是 namespace + cgroup 包装的普通进程，系统调用直接进宿主内核；VM 有完整的 Guest 内核，中间隔着 Hypervisor。这决定了隔离强度和兼容性。
6. 突发性能实例的 CPU 积分耗尽后会发生什么？
正确答案：降频到基准。CPU 使用率仍显示 100%，但有效算力只剩一小部分，QPS 掉到几分之一。判断要看云监控里的"积分余额"指标，或观察周期性的吞吐塌陷。
