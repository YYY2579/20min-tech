开始前

准备一个能拆开看的工程

全程只用三个小文件，但覆盖了静态库、动态库、多编译单元、全局变量这几种情况。

// main.c
#include <stdio.h>
#include "mathx.h"

int g_counter = 42;          // 已初始化全局变量 → .data
int g_zero;                  // 未初始化全局变量 → .bss
const char *banner = "hi";   // 指针在 .data，字符串在 .rodata

int main(void) {
    printf("%s %d\n", banner, add(g_counter, 1));
    return 0;
}

// mathx.h
#ifndef MATHX_H
#define MATHX_H
int add(int a, int b);
#endif

// mathx.c
#include "mathx.h"
int add(int a, int b) { return a + b; }
# 编译并保留每个阶段的中间产物
gcc -E main.c -o main.i        # 预处理
gcc -S main.i -o main.s        # 编译成汇编
gcc -c main.s -o main.o        # 汇编成目标文件
gcc -c mathx.c -o mathx.o
gcc main.o mathx.o -o app      # 链接

# 一条命令完成全部，-v 能看到它到底调了什么
gcc -v main.c mathx.c -o app 2>&1 | grep -E "^ /usr|collect2|cc1|as "

配套工具，全部来自 binutils（GNU 二进制工具集）：

工具用途
file看文件类型：是 relocatable（.o）、executable 还是 shared object
nm列符号表，看每个符号是定义（T/D/B）还是未定义（U）
readelf看 ELF 头、段表、符号表、重定位、动态段。最该熟练的一个
objdump -d反汇编，看编译器到底生成了什么指令
ldd看可执行文件依赖哪些动态库（对不可信二进制不安全，见模块 7）
strings从二进制里捞可打印字符串，排查版本号、路径
ar打包/解包静态库（.a 本质就是一堆 .o 的归档）
平台差异先声明：文中的汇编、段名、重定位类型以 x86-64 Linux + GCC/ELF 为准。ARM64 的指令序列不同，macOS 用 Mach-O（段叫 __TEXT、__DATA），Windows 用 PE/COFF（段叫 .text、.rdata）。概念一一对应，名字和细节不同，不要把 Linux 的结论硬套到别的平台。
模块 1

四个阶段：每一步的输入输出

阶段驱动命令实际程序输入 → 输出做什么
预处理gcc -Ecc1 -E.c → .i展开宏、展开 #include、处理条件编译、去注释。产物仍是纯文本 C 代码
编译gcc -Scc1.i → .s词法/语法/语义分析、优化、生成汇编。这是唯一做优化的阶段
汇编gcc -cas.s → .o把汇编翻译成机器码，生成可重定位目标文件。此时地址全是占位
链接gcccollect2 → ld.o + .a/.so → 可执行合并段、解析符号、做重定位、生成最终地址
# 看预处理到底做了什么：行数会从几十行涨到几千行
wc -l main.c main.i
head -5 main.i          # 一堆 typedef 和 extern 声明，来自 stdio.h

# 只看用户代码的预处理结果，屏蔽系统头文件的行号标记
gcc -E -P main.c | tail -20

# 看生成的汇编（-S 已含优化，加 -fverbose-asm 保留变量名注释）
gcc -S -O2 -fverbose-asm main.c -o -
cat main.s

# 看目标文件的段和符号
readelf -S main.o       # 段表：.text/.data/.bss/.rodata 各多大
readelf -s main.o       # 符号表：每个符号的定义状态
readelf -r main.o       # 重定位表：哪些位置等着链接器来填
关键认知：.o 文件里的地址不是最终地址。编译 main.c 时编译器不知道 add() 会被放在哪，也不知道 printf 在哪个库。它只能生成一条"调用一个占位地址"的指令，并在重定位表里记一笔：此处需要填入符号 add 的地址。填这个坑，就是链接器的工作。

这也解释了为什么编译错误和链接错误必须分开看：编译错误是单个 .c 文件内部的问题（语法、类型、找不到头文件）；链接错误是跨文件的问题（符号找不到、重复定义、库的顺序不对）。报错信息的形态完全不同，前者带行号和列号，后者只有符号名。

模块 2

预处理与宏：文本替换的代价

预处理器的本质是一个不理解 C 语法的文本替换器。它不知道类型、不知道作用域、不做任何检查。所有"宏引发的诡异 bug"都源于这一点。

宏的三个经典陷阱

// 陷阱 1：没有括号，优先级被破坏
#define SQUARE(x) x * x
SQUARE(1 + 2)        // 展开成 1 + 2 * 1 + 2 = 5，不是 9
// 正确：#define SQUARE(x) ((x) * (x))

// 陷阱 2：参数被求值多次
#define MAX(a, b) ((a) > (b) ? (a) : (b))
MAX(i++, j++)        // i 和 j 各被自增两次，结果未定义
// 正确：用 inline 函数，或 GCC 的 typeof 扩展（不可移植）

// 陷阱 3：宏没有作用域，也不受命名空间约束
#define max(a, b) ...
// 之后任何叫 max 的函数、变量、成员都会被替换掉，包括 <algorithm> 里的 std::max

#include 到底做了什么

它就是把目标文件的全部内容原地粘贴进来，没有任何模块或命名空间的概念。所以：

  • 头文件里只能放声明（extern 变量、函数原型、类型定义、宏），不能放定义。放了定义，被两个 .c 包含就会重复定义。
  • 头文件必须用 include guard（#ifndef 或 #pragma once）防重复包含。缺了它，A 包含 B 和 C、B 和 C 又都包含 D 时，D 会被展开两次，类型重定义直接编译失败。
  • #include <stdio.h> 用尖括号是只在系统头文件路径里找，#include "x.h" 用引号是先找当前文件所在目录，再找系统路径。这个区别在交叉编译时经常出问题。
  • 一个 .c 包含 10 个常用头文件，预处理后轻松几万行。编译慢的一大半时间花在重复解析这些头文件上，这就是预编译头（PCH）和 C++20 modules 想解决的问题。
# 看头文件搜索路径（顺序即优先级）
gcc -E -v -x c /dev/null 2>&1 | sed -n '/search starts here/,/End of search list/p'

# 只生成依赖关系，不编译（构建系统用它跟踪头文件变化）
gcc -M main.c
gcc -MM main.c          # 排除系统头文件，输出更干净

# 展开所有宏后看某个宏到底是什么（排查库里宏定义冲突）
gcc -E -dM -x c /dev/null | grep -i _GNU_SOURCE
什么时候该用宏，什么时候不该：需要编译期决定的东西只能用宏 —— 条件编译（#ifdef DEBUG）、头文件保护、字符串化（#x）、拼接标识符（a##b）、跨平台分支。凡是能用 const / constexpr / inline / 模板表达的，都不要用宏 —— 后者有类型检查、有作用域、能在调试器里看到。
模块 3

编译优化与未定义行为

级别大致做了什么适用
-O0几乎不优化。每个变量都在栈上有位置，每条语句对应一段独立指令调试。断点、单步、看变量都符合直觉
-O1删死代码、合并常量、简单的寄存器分配。编译快，体积和速度都有改善需要可调试又想快一点
-O2在此基础上加指令调度、循环优化、函数内联（保守）、基于别名的优化生产环境的默认选择
-O3更激进的内联、向量化（SIMD）、循环展开计算密集；体积膨胀，可能因 cache 压力反而变慢
-Os / -Oz以体积为目标的优化嵌入式、镜像大小敏感的场景
-Og为调试设计的优化级别，保留大部分可调试性开发期想要 -O1 的性能又不想丢断点

为什么 -O2 下断点会"失效"

不是 gdb 坏了，是代码已经不存在了。三种情况：

变量被优化进寄存器。栈上没有这个变量了，gdb 只能显示 <optimized out>。想看只能在关键位置加 volatile 或打印日志。
函数被内联。调用点直接展开成函数体，符号表里没有这个函数，断点打不上。用 __attribute__((noinline)) 可以临时禁掉。
语句被重排或合并。源码第 10 行和第 12 行可能对应同一段指令，单步时行号会来回跳。这是编译器重排，不是调试信息错了。
# 编译时带上调试信息（-g 与优化级别互不冲突）
gcc -O2 -g -o app main.c mathx.c

# 想看变量真实值：用 -Og 开发，或对关键变量加 volatile
# 想看汇编与源码的对应关系
objdump -dS --no-show-raw-insn app | less

# 看内联决策（GCC 会输出每个函数为什么被内联/拒绝内联）
gcc -O2 -fopt-info-inline -c main.c -o /dev/null

未定义行为在优化下的表现

这是 C/C++ 最反直觉的部分。UB（Undefined Behavior，未定义行为）不是"结果不确定"，而是编译器可以假设它永远不会发生，并据此删掉代码。

// 典型例子：有符号整数溢出是 UB
int check(int x) {
    if (x + 1 > x) return 1;   // 编译器推理：若 x+1 溢出则 UB，而 UB 不可能发生
    return 0;                   // 所以 x+1 必然大于 x，这个分支是死代码
}

// gcc -O2 的实际输出：整个函数变成 return 1
// 也就是说，当 x == INT_MAX 时，这段代码返回 1，而"朴素"的机器语义应该是 0

// 另一个经典：空指针解引用会被当作"此指针非空"的证据
void f(int *p) {
    int x = *p;        // 若 p 为空则 UB
    if (p == NULL) {   // 编译器据此推断 p 一定非空 → 整个 if 被删掉
        abort();
    }
}
工程结论：① 把 -Wall -Wextra 当成最低配置，再加 -Wstrict-overflow、-Wnull-dereference；② 需要"溢出回绕"语义时用无符号类型（无符号溢出是定义良好的模运算），或显式写 __builtin_add_overflow；③ 用 UBSan（-fsanitize=undefined）在测试环境跑一遍，它会在运行时抓住这些行为，成本远低于上线后排查；④ 不要用"我在 -O0 下测过没问题"来论证正确性，-O0 和 -O2 的语义差异足以让 UB 表现完全不同。
模块 4

目标文件与符号

ELF（Executable and Linkable Format，可执行与可链接格式）文件用段（section）组织内容。链接器看的是段，加载器看的是段表映射出来的 segment，两套概念经常被混用。

段内容为什么放这里
.text机器指令只读可执行，多进程可共享同一份物理页
.rodata只读数据：字符串字面量、const 全局、跳转表写入会触发段错误，能提前暴露越界写
.data已初始化且非 0 的全局/静态变量必须在文件里存初值
.bss未初始化或初值为 0 的全局/静态变量只记录大小，不占文件空间，加载时由内核清零
.symtab / .strtab符号表与字符串表链接时需要；strip 后消失，不影响运行
.rela.text代码段的重定位表记录"哪个偏移处需要填哪个符号的地址"
.plt / .got过程链接表 / 全局偏移表动态链接的跳转与地址存储（见模块 5）
.dynamic / .dynsym动态段与动态符号表运行时动态链接器靠它找依赖和符号
.bss 为什么能省空间：一个 100MB 的全局数组 char buf[100*1024*1024]; 如果放在 .data，可执行文件就会真的大 100MB。放在 .bss，文件里只多一条"需要 100MB 零初始化空间"的记录，加载时内核用零页映射，实际内存按需分配。这是嵌入式和大数组场景必须知道的细节。

符号表怎么看

# nm 的字母含义：大写=全局，小写=局部
# T/t 代码段   D/d 已初始化数据   B/b 未初始化数据   R/r 只读数据
# U 未定义（本文件引用、别处定义）   W 弱符号
nm main.o
#                  U add          ← 只声明，没定义，等链接器填
# 0000000000000000 T main         ← 本文件定义
# 0000000000000004 D g_counter    ← 已初始化全局
# 0000000000000004 B g_zero       ← 未初始化全局
#                  U printf

# C++ 符号被 mangle，-C 反解成人能看的形式
nm -C libfoo.so | grep add
# 0000000000001139 T add(int, int)   ← 原始符号是 _Z3addii

# 看某个符号在哪个库里定义
nm -A /usr/lib/x86_64-linux-gnu/*.a 2>/dev/null | grep " T add"

重定位表

编译 main.c 时，call add 这条指令后面跟的地址是 0，同时在 .rela.text 里留一条记录：偏移 0x12 处，填入符号 add 的地址，类型 R_X86_64_PLT32。链接器扫描所有 .o，把同名符号合并、分配最终地址，再逐条回填。

# 看重定位条目
readelf -r main.o
# Offset          Info           Type            Sym. Name + Addend
# 000000000012  000500000004 R_X86_64_PLT32   add - 4

# 链接后这些条目应该全部消失（静态链接的情况下）
readelf -r app | head
静态库的链接顺序是有讲究的。链接器从左到右扫描命令行，静态库只被扫描一次，且只取出"当前还有未定义符号"的那些成员。所以 gcc main.o -lfoo -lbar 里，如果 foo 依赖 bar，bar 必须放在 foo 后面；如果顺序反了，链接器扫 bar 时还不需要它，扫 foo 时产生的未定义符号就没人管了，报 undefined reference。解法：把被依赖的库放右边，或者用 -Wl,--start-group ... -Wl,--end-group 让链接器反复扫描。
模块 5

静态链接、动态链接与 PIC

维度静态链接动态链接
产物所有用到的代码都复制进可执行文件只记录依赖（NEEDED），运行时加载 .so
体积大（每个程序各带一份 libc）小（多个进程共享同一份 .so 的物理页）
启动快，没有符号解析和库加载慢，要做库定位、符号绑定、重定位
部署拷一个文件就能跑，适合容器和救援工具需要目标机上有兼容版本的库
升级换库必须重新链接整个程序替换 .so 即可（前提是 ABI 兼容）
内存每个进程独立一份代码段共享，只有数据段各一份

PIC：为什么共享库必须是位置无关的

共享库被映射到哪个虚拟地址，在编译时是不知道的，而且不同进程可能映射到不同地址（ASLR）。如果代码里写死了绝对地址，就没法共享。PIC（Position Independent Code，位置无关代码）解决这个问题：

  • 模块内部的访问用 RIP 相对寻址（"相对当前指令指针偏移多少"），天然与加载地址无关。
  • 访问外部全局变量走 GOT（Global Offset Table，全局偏移表）：代码里只放"GOT 表项的位置"，GOT 里存的才是变量的真实绝对地址。加载时动态链接器把 GOT 填好。
  • 调用外部函数走 PLT（Procedure Linkage Table，过程链接表）：每个外部函数对应一小段跳板代码，第一次调用时跳到动态链接器去解析真实地址并写回 GOT，之后直接跳。
# 对比：不加 -fPIC 的代码里有绝对地址，加了的全是相对寻址
gcc -O2 -fno-pic -c mathx.c -o m_nopic.o
gcc -O2 -fPIC   -c mathx.c -o m_pic.o
objdump -d m_nopic.o | head -20
objdump -d m_pic.o   | head -20

# 看 GOT / PLT 里有什么
objdump -d -j .plt app
readelf -r app | grep -E "GLOB_DAT|JUMP_SLOT"

# 看程序依赖哪些库、需要哪些符号
readelf -d app | grep NEEDED
objdump -T app | grep UND
延迟绑定（lazy binding）：默认情况下，printf 的地址在第一次调用时才解析，而不是启动时。好处是启动快（没调用到的函数不花解析时间），坏处是第一次调用的延迟抖动，且 GOT 必须可写（有被攻击篡改的风险）。
要关掉它：链接时加 -Wl,-z,now（立即绑定），配合 -Wl,-z,relro 让 GOT 在重定位后变成只读（Full RELRO）。安全敏感的服务建议默认开启，代价是启动稍慢。

为什么动态链接启动慢

开销来源说明
库定位与 mmap每个依赖都要在搜索路径里找到、打开、映射，依赖还有传递闭包（A 依赖 B，B 又依赖 C）
符号解析把所有未定义符号在依赖树里查一遍。C++ 程序符号多，这一步能到几十毫秒
重定位逐条改写 GOT/数据段里的地址。RELRO 关闭时还要改代码段
缺页中断.so 的代码页是懒加载的，第一次执行到才从磁盘读，冷启动时这部分很可观
# 量化启动时的动态链接开销
LD_DEBUG=statistics ./app 2>&1 | head -20
# 输出里有 total startup time in dynamic loader 一项，单位是 cycles

# 看符号绑定过程（量很大，建议只对小程序用）
LD_DEBUG=bindings ./app 2>&1 | head -40

# 用 strace 看打开和 mmap 了哪些库
strace -e trace=openat,mmap ./app 2>&1 | grep "\.so" | head
模块 6

三类链接错误怎么破

第一类：undefined reference

含义很明确：某个符号被引用（U），但链接器在所有输入里都没找到定义。按下面的顺序排查，基本一次命中。

确认是真的没定义。nm -C 目标文件 | grep 符号名。显示 U 说明只有引用；如果连 U 都没有，说明这个 .o 根本没参与链接。
确认库加上了。忘了 -lm（数学库）、-lpthread（老版本 glibc 的线程库）是最常见的两个。现代 glibc 已经把 pthread 合进 libc，但显式加仍然更稳。
检查静态库的顺序。被依赖的放右边，或者用 --start-group/--end-group 包起来。
C/C++ 混用检查 extern "C"。C++ 编译器会把 add(int,int) 变成 _Z3addii，而 C 库导出的是 add，名字对不上必然找不到。
检查 #ifdef 分支。库可能因为没开某个编译选项，把函数编成了空实现或干脆没编进去。

第二类：multiple definition

同一个符号在两个 .o 里都有强定义。九成的原因是在头文件里写了变量的定义，然后被多个源文件包含。

// 错误：头文件里定义了变量，每个包含它的 .c 都会生成一份
int g_counter = 0;              // 放在 .h 里 → 两个 .o 各有一份 → 重复定义

// 正确：头文件里只声明
extern int g_counter;           // 声明
// 在且仅在一个 .c 里定义
int g_counter = 0;
GCC 10 的一个破坏性变化：以前 int g_counter;（不带初值）是暂定定义（tentative definition），多个 .o 里出现会被链接器合并成一个（-fcommon）。GCC 10 起默认改成 -fno-common，同样写法直接报 multiple definition。老项目升级编译器时集体爆炸，通常就是这个原因。临时兼容可以加 -fcommon，正解还是改成 extern 声明 + 单点定义。

另外，头文件里定义的 inline 函数不会重复（inline 有特殊链接语义），但头文件里定义的普通函数会。模板和类内定义的成员函数也是隐式 inline，所以安全。

第三类：ABI 不兼容

ABI（Application Binary Interface，应用二进制接口）是"编译后的约定"：结构体布局、参数传递方式、名字修饰规则、异常处理机制、标准库对象的内部布局。源码兼容不代表 ABI 兼容。

破坏 ABI 的改动后果
给类中间插入成员变量所有成员的偏移量变化，老代码按老偏移读写，数据错乱（不是崩溃，更难查）
增加/删除虚函数虚表（vtable）布局变化，虚调用跳到错误的函数
改变函数签名或默认参数名字修饰结果变化，运行时找不到符号
换编译器大版本（如 GCC 4 → 5）std::string / std::list 换了实现，受 _GLIBCXX_USE_CXX11_ABI 控制，两种 ABI 不能混链
Debug 与 Release 混链_GLIBCXX_DEBUG 会改变容器的布局和大小
# 看一个 C++ 符号被 mangle 成什么（用 c++filt 反解）
echo "_Z3addii" | c++filt          # add(int, int)
nm -C app | grep add               # 直接看反解后的名字

# 检查一个库用的是哪套 string ABI
nm -D libfoo.so | grep -c "__cxx11"    # 非 0 表示用了新 ABI（GCC 5 及以后）
nm -D libfoo.so | grep -c "_ZNSs"      # 非 0 表示用了老 ABI（GCC 4.x）

# 对比两个版本的导出符号差异（升级库之前必做）
diff <(nm -D --defined-only libfoo.so.1.0 | awk '{print $3}' | sort) \
     <(nm -D --defined-only libfoo.so.1.1 | awk '{print $3}' | sort)
最难查的一类：链接期正常，运行期崩溃或结果错乱。编译时符号名对得上（因为签名没变），但结构体布局变了。表现是"某个字段莫名其妙变成别的值""析构时堆损坏"。对策是版本化发布：库的 ABI 变了就升 soname（见模块 7），让新旧版本可以共存，而不是偷偷替换。
模块 7

库的版本管理：soname 与查找路径

Linux 上的共享库有三个名字，各管一件事。搞不清这三个名字，就永远理不清"为什么编译过了运行却找不到"。

名字示例谁用
真实文件名libfoo.so.1.2.3实际存放的文件，含完整版本号
sonamelibfoo.so.1运行时。链接时用 -Wl,-soname,libfoo.so.1 写进库的 .dynamic 段，可执行文件记录的是它
链接名libfoo.so编译时。-lfoo 找的就是这个，通常是开发包提供的符号链接
# 构建一个规范的共享库
gcc -O2 -fPIC -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.3 foo.c
ln -sf libfoo.so.1.2.3 libfoo.so.1     # 运行时找这个
ln -sf libfoo.so.1     libfoo.so       # 编译时找这个（属于 -devel 包）
ldconfig                                # 刷新缓存

# 看一个可执行文件到底需要哪个 soname
readelf -d app | grep NEEDED
# 0x0000000000000001 (NEEDED)  Shared library: [libfoo.so.1]

动态链接器的查找顺序

这个顺序是固定的，按优先级从高到低：

DT_RPATH（可执行文件里写死的路径）。已废弃，如果同时存在 DT_RUNPATH 则被忽略。
LD_LIBRARY_PATH 环境变量。方便调试，不适合生产。
DT_RUNPATH（链接时用 -Wl,-rpath 写入）。注意它只对本直接依赖生效，不传递给间接依赖，这是和 RPATH 的关键区别。
/etc/ld.so.cache。由 ldconfig 扫描 /etc/ld.so.conf 和 /etc/ld.so.conf.d/*.conf 生成，是生产环境的标准做法。
默认路径 /lib、/usr/lib（以及 64 位系统上的 /lib64、/usr/lib64）。

"找不到 .so" 的排查顺序

# 1. 先确认到底缺哪个（报错信息里通常有 soname）
./app
# error while loading shared libraries: libfoo.so.1: cannot open shared object file

# 2. 看依赖清单与 rpath
readelf -d app | grep -E "NEEDED|RPATH|RUNPATH"

# 3. 看动态链接器实际去哪找了（最直接的一步）
LD_DEBUG=libs ./app 2>&1 | grep -A2 "libfoo"

# 4. 确认库在不在、soname 对不对
find / -name "libfoo.so*" 2>/dev/null
readelf -d /path/to/libfoo.so.1.2.3 | grep SONAME

# 5. 缓存里有没有
ldconfig -p | grep libfoo

# 6. 临时验证（不要写进生产脚本）
LD_LIBRARY_PATH=/opt/foo/lib ./app
ldd 有坑。它本质上是设置环境变量后运行动态链接器，对不可信的二进制可能执行其中的代码。分析来源不明的文件时，用 objdump -p app | grep NEEDED 或 readelf -d 代替。
另一个坑：LD_LIBRARY_PATH 会污染子进程。它会被继承，导致这个 shell 里启动的所有程序都用你的库，包括 ls、systemctl，很容易把系统搞出诡异问题。生产上应该用 rpath 或 ldconfig。
模块 8

现代构建系统在解决什么

从手写 gcc a.c b.c 到 CMake、Bazel，解决的其实只有三件事：依赖关系的描述、增量构建的正确性、构建结果的可复用性。

工具核心模型适用
Make目标 : 依赖 → 命令，靠文件时间戳判断是否重建小项目、脚本编排。跨平台差，头文件依赖要手动生成
CMake生成器：写 CMakeLists.txt，生成 Makefile 或 Ninja 文件C/C++ 事实标准。target 制（PUBLIC/PRIVATE/INTERFACE）能正确传递编译选项和依赖
Ninja只负责"按依赖图最快地执行"，不做配置作为 CMake 的后端，比 Make 快很多
Bazel内容哈希 + 沙箱 + 远程缓存，声明式、可重现超大单体仓库、多语言、需要分布式构建

增量构建的原理与它为什么会错

Make 的规则简单到粗暴：目标文件比任一依赖旧，就重新生成。这带来两个经典问题：

  • 头文件不在依赖里。只写了 main.o: main.c，改了 mathx.h 不会触发重编，链接出来的还是旧代码。解法是用编译器自动生成依赖：gcc -MMD -MP -c main.c 会额外产出 main.d，里面列全了所有头文件，在 Makefile 里 -include $(DEPS) 即可。
  • 时间戳不可靠。从 git 切分支、rsync 同步、NFS 时钟漂移，都可能让文件时间倒流或相同，导致"该编的没编"或"每次都全编"。基于内容哈希的构建系统（Bazel、ccache）没有这个问题。
# 自动生成头文件依赖的标准写法
CFLAGS += -MMD -MP
# 编译后会得到 main.d，内容形如：
# main.o: main.c mathx.h

# ccache：把编译结果按"预处理后的源码 + 编译参数 + 编译器版本"哈希缓存
ccache gcc -O2 -c main.c -o main.o
ccache -s                    # 看命中率
# 注意：CCACHE_BASEDIR 和 -fdebug-prefix-map 能让不同路径下的构建命中同一份缓存

分布式构建与远程缓存

Bazel 这类系统的做法是：把每个编译动作的输入（源文件、头文件、编译参数、工具链）全部哈希，得到 action key；输出存进内容寻址存储（CAS）。换一台机器、换一个开发者，只要输入哈希一致，直接下载输出，不重新编译。

这要求构建是可重现的：不能依赖当前时间、随机数、绝对路径、环境变量。所以 Bazel 会强制在沙箱里执行每个动作，只暴露声明过的输入。

能力MakeCMake+NinjaBazel
头文件依赖自动跟踪需手动配置自动（编译器 -MMD）自动（沙箱强制声明）
跨平台差好好
本地增量时间戳时间戳 + deps内容哈希
远程/分布式缓存无需配合 ccache/sccache原生支持
学习成本低中高
选型建议：库或中小项目用 CMake + Ninja，生态最全，IDE 和包管理器（vcpkg、Conan）都支持。单一语言、几十万行以内的服务，Make 也够用。只有在仓库大到"改一行要编半小时"、或者需要跨团队共享构建缓存时，Bazel 的复杂度才划得来。
常见坑

十个踩过才知道的坑

1
在头文件里定义全局变量
被两个 .c 包含就 multiple definition。头文件里只能 extern 声明，定义放在某一个 .c 里。
2
静态库链接顺序写反
链接器从左到右只扫一遍静态库。被依赖的库要放右边，或者用 -Wl,--start-group 包起来强制多轮扫描。
3
用 -O2 编译然后抱怨断点打不上、变量看不了
变量进了寄存器、函数被内联、语句被重排。开发用 -Og，或者对关键变量加 volatile，别指望 -O2 下还能逐行调试。
4
用 -O0 的测试结果证明代码正确
有符号溢出、空指针解引用这类 UB，在 -O2 下会被编译器当成"不可能发生"而删掉分支。用 UBSan 在测试环境跑一遍才靠谱。
5
C 和 C++ 混用，忘了 extern "C"
C++ 会把函数名 mangle 成 _Z3addii，C 库导出的是 add，链接期直接 undefined reference。给 C 头文件加 #ifdef __cplusplus extern "C" { 包起来。
6
替换 .so 却不升 soname
ABI 变了但文件名没变，老程序加载新库，符号名对得上但结构体布局变了，运行期数据错乱。ABI 变更必须升 soname，让新旧版本共存。
7
生产环境用 LD_LIBRARY_PATH 指定库
会被子进程继承，污染整个会话；顺序也容易被其他变量覆盖。用 rpath 或 ldconfig 才是可运维的做法。
8
静态链接 glibc 后 getaddrinfo 行为异常
glibc 的 NSS（名字服务切换）靠 dlopen 动态加载 libnss_* 模块，静态链接下无法工作。要静态链接又需要域名解析，得改用 musl 或显式处理 NSS 依赖。
9
Makefile 不跟踪头文件依赖
改了 .h 不重编，跑的还是旧逻辑，排查半天以为是编译器 bug。加 -MMD -MP 并 include 生成的 .d 文件。
10
用 ldd 分析来源不明的二进制
ldd 会以运行方式加载目标程序，恶意文件可借此执行代码。改用 objdump -p 或 readelf -d 只读解析。
自测

六道题

1. 一个 100MB 的未初始化全局数组，会让可执行文件变大 100MB 吗？
正确答案：不会。未初始化或初值为 0 的全局变量放在 .bss，不占文件空间。如果给它一个非 0 初值，就会落到 .data，文件真的会变大。
2. 用 -O2 编译后 gdb 显示变量 <optimized out>，最可能的原因是？
正确答案：变量被优化掉了。-g 只负责生成调试信息，不阻止优化。-O2 下变量可能只存在于寄存器，gdb 无法从内存读。开发期用 -Og，或对关键变量加 volatile。
3. gcc main.o -lfoo -lbar 报 undefined reference，但符号确实在 libbar.a 里。最可能的原因是？
正确答案：链接顺序。链接器从左到右扫描，静态库只扫一次。扫 bar 时还不需要它，扫 foo 时产生的未定义符号就没人解析了。被依赖的库要放在依赖者右边。
4. 共享库必须用 -fPIC 编译，根本原因是？
正确答案：加载地址未知。如果代码里写死绝对地址，多个进程就无法把它映射到不同地址，也无法共享。PIC 用 RIP 相对寻址 + GOT/PLT 解决这个问题。
5. soname（如 libfoo.so.1）的作用是？
正确答案：运行时的名字。编译时找 libfoo.so，运行时找 libfoo.so.1。soname 在主版本升级（ABI 破坏）时才变，这样新旧版本可以共存。
6. C++ 代码调用 C 库函数报 undefined reference，符号名是 _Z3addii。正确做法是？
正确答案：extern "C"。C++ 为了支持重载会把函数名修饰成 _Z3addii，而 C 库导出的是 add。extern "C" 让 C++ 按 C 的规则生成符号，链接才能对上。注意 gcc 没有 -fno-mangle 这个选项。
