二十分钟学透无锁数据结构

无锁不是"更快"的同义词，它是用 CPU 空转换掉线程阻塞的一笔交易。这笔交易在低竞争下很划算，在高竞争下会亏得很惨。这篇讲清楚三个层级、内存序、ABA、以及为什么你多半不该自己写。

开始前

先建立三个前提

无锁编程难，不是难在 API，而是难在你脑子里的执行模型和 CPU 实际做的事不一样。先接受三件事。

前提含义
编译器会重排只要不改变单线程语义，编译器可以把你的读写顺序打乱。-O2 就会做
CPU 会重排x86 只保证"读不越过读、写不越过写"，ARM 几乎什么都敢重排
缓存是一致的，但不是即时的MESI 协议保证最终一致，但一个核写了，另一个核可能要过几十纳秒才看见
// 环境准备：确认你的编译器真的支持无锁原子操作
static_assert(std::atomic<int>::is_always_lock_free, "int 必须是 lock-free");
static_assert(std::atomic<void*>::is_always_lock_free, "指针必须是 lock-free");

// 注意：不是所有类型都 lock-free。64 位原子在 32 位平台上可能退化成内部锁
std::atomic<long long> x;
if (!x.is_lock_free()) { /* 它内部其实用了锁，你的"无锁"是假的 */ }

// 编译
g++ -std=c++17 -O2 -pthread demo.cpp
// 调试竞争问题
g++ -std=c++17 -O1 -g -fsanitize=thread -pthread demo.cpp
一个必须先说清楚的现实：std::atomic<T>::is_lock_free() 返回 false 时，标准库会在内部用一把锁来实现原子性。你以为自己写的是无锁代码，实际上每一行都在加解锁。这种情况在 32 位平台上的 64 位类型、以及大于 16 字节的结构体上很常见。
模块 1

三个层级：阻塞、无锁、无等待

这三个词有严格定义，不是形容词。区别在于"最坏情况下，系统还能不能整体向前走"。

层级保证典型实现
阻塞 blocking某个线程被挂起时，其他线程可能全部停住mutex、信号量、条件变量
无锁 lock-free任意时刻，至少有一个线程能在有限步内完成操作。系统整体有进展，但个别线程可能饿死CAS 循环、Treiber 栈、Michael-Scott 队列
无等待 wait-free每个线程都能在有限步内完成，不管别人在干什么fetch_add、单写多读的原子变量、部分引用计数

用一句话区分

  • 阻塞：一个人卡住，全队等。
  • 无锁：不管谁卡住，队伍总有人在前进，但可能总是同一个人。
  • 无等待：每个人都有自己的路，谁也不等谁。

还有一个更弱的层级叫 obstruction-free（无障碍）：只有在一个线程独占执行时才能保证完成。它比无锁弱，一般不单独提。

为什么"无锁"不等于"高性能"

因为无锁的进度保证是用重试换来的。一个 CAS 循环失败就重来，失败越多次，浪费的 CPU 越多。而 mutex 在竞争时会把线程挂起（park），让出 CPU 给真正干活的人。

场景mutexCAS 循环
低竞争（< 2 线程争抢）约 20ns（fast path 不陷内核）约 5~20ns，更快
中等竞争（4~8 线程）进入 futex，微秒级重试次数上升，纳秒级但 CPU 空转
高竞争（32+ 线程抢一个变量）排队，吞吐稳定几乎全部失败，吞吐崩塌

最后一行是关键：N 个线程同时对同一个 cache line 做 CAS，每次只有一个成功，其余 N-1 个失败重试。而且每次失败的 CAS 都会让 cache line 在核间来回弹（cache line ping-pong），一次转移 40~100ns。这时候 CAS 循环的总开销可能比一把 mutex 高一个数量级。

Herlihy 的层级图（1991）里有一条铁律：用 CAS 可以实现无锁队列，但不能用 CAS 实现无等待队列（在只提供 read/write 的模型下连无锁队列都做不出来）。也就是说，通用数据结构的"无等待"版本，要么不存在，要么需要特殊硬件指令。
推论：市面上号称"wait-free queue"的库，通常是在特定约束下（固定容量、单生产者、有限线程数）才成立。看到这个词先去看它的前提条件。
模块 2

原子操作与内存序

原子性解决"不被撕裂"，内存序解决"什么时候能被别人看见"。前者容易理解，后者是 90% 的 bug 来源。

六个内存序

memory_order语义典型代价
relaxed只保证原子性，不建立任何跨线程的顺序。编译器/CPU 可以随意重排最低，通常就是一条普通指令
consume依赖链上的读不能重排。语义复杂、编译器支持差，实践中不要用—
acquire用于 load。之后的读写不能上移到这条之前x86 上是普通 mov，几乎免费
release用于 store。之前的读写不能下移到这条之后x86 上是普通 mov，几乎免费
acq_rel同时具备 acquire 和 release，用于 CAS / RMW中等
seq_cst所有线程看到同一个全局顺序，默认值，最强也最贵x86 上 store 要 mfence 或 xchg，约 20~30 周期

acquire-release 到底在保证什么

// 线程 A：生产者
data = 42;                                   // ① 普通写
ready.store(true, std::memory_order_release); // ② release 写

// 线程 B：消费者
if (ready.load(std::memory_order_acquire)) {  // ③ acquire 读
    assert(data == 42);                      // ④ 一定成立
}

release 保证 ① 不会跑到 ② 后面；acquire 保证 ④ 不会跑到 ③ 前面。两者配对，就建立了 happens-before 关系：B 只要看到了 ready == true，就一定能看到 ① 的结果。

如果 ② 写成 relaxed，编译器或 CPU 完全可能把 ① 挪到 ② 之后。这时候 B 看到 ready == true，读到的 data 可能是 0。这就是最经典的数据竞争 bug，而且在 x86 上可能测不出来，一到 ARM 就炸。

x86 与 ARM 的指令差异

操作x86-64ARM64
load relaxedmovldr
load acquiremov（TSO 天然保证）ldar
store relaxedmovstr
store releasemov（TSO 天然保证）stlr
store seq_cstmov + mfence，或 xchgstlr + dmb ish

看这张表就明白了：在 x86 上，acquire/release 几乎不要钱（因为 TSO 本来就不允许大部分重排），所以很多人写 x86 代码时随手用 seq_cst 也没感觉慢。换到 ARM，每一条 seq_cst 都是一次 dmb，代价立刻显出来。

CAS 的两种形式

// compare_exchange_weak：允许"伪失败"（spurious failure），需要写在循环里
int expected = 0;
while (!atom.compare_exchange_weak(expected, 1)) {
    // 失败时 expected 被更新为当前值
}

// compare_exchange_strong：不会伪失败，但内部可能重试
if (atom.compare_exchange_strong(expected, 1)) { /* 成功 */ }

// 选择原则：
// 循环里用 weak（本来就要重试，省一条指令）
// 只试一次用 strong（不想写循环）
为什么会有"伪失败"？因为在 ARM 这类 LL/SC（Load-Link / Store-Conditional）架构上，CAS 是用"独占读 + 条件写"实现的。只要这期间 cache line 被别人碰过（哪怕值没变），条件写就会失败。所以"值相同但操作失败"是合法的，必须重试。

fetch_add 是最便宜的多线程计数器

std::atomic<long> counter{0};

// 单条指令完成"读+加+写"，不会被中断
counter.fetch_add(1, std::memory_order_relaxed);

// 如果只是想统计总数，relaxed 就够了 —— 你不在乎它和别的操作的顺序
// 这也是最常用的场景：QPS 计数、连接数、序列号发号

在 x86 上 lock xadd 无竞争时约 20 个周期。但所有核抢同一个计数器时，cache line 会在核间弹，吞吐会掉到每秒几百万次——比单线程的加法慢两三个数量级。解法是分片计数（每个线程一个计数器，读的时候求和），这也是 LongAdder 这类类的设计思路。

模块 3

无锁栈：最简单的例子，也是最危险的例子

Treiber 栈（1986）是所有无锁教材的第一个例子。它只有二十行，但包含了无锁编程的全部三个陷阱。

push 很干净

struct Node {
    int value;
    Node* next;
};

std::atomic<Node*> head{nullptr};

void push(int v) {
    Node* n = new Node{v, nullptr};
    n->next = head.load(std::memory_order_relaxed);
    // 如果 head 还是 n->next，就把 head 换成 n
    while (!head.compare_exchange_weak(n->next, n,
              std::memory_order_release,
              std::memory_order_relaxed)) {
        // 失败时 n->next 被自动更新为当前 head，直接重试
    }
}

注意 compare_exchange_weak 的第一个参数是引用，失败时会被写成当前值。所以循环体可以是空的——更新 n->next 这件事由 CAS 自己完成了。这个技巧很常用。

pop 有三个坑

// 看起来对的版本
int pop() {
    Node* old = head.load(std::memory_order_acquire);
    while (old && !head.compare_exchange_weak(old, old->next,
             std::memory_order_acquire,
             std::memory_order_relaxed)) {
        // 重试
    }
    if (!old) return -1;
    int v = old->value;
    delete old;          // ★ 坑 1：这里就炸了
    return v;
}
坑说明
1. 释放内存你 delete old 的瞬间，另一个线程可能还持着指向它的指针（在它自己的 CAS 循环里）。它下次读 old->next 就是 use-after-free
2. ABAold 被删掉、内存被复用、又被 push 回来，地址一样但内容变了。CAS 会误判"没变化"而成功
3. 读 next 不是原子的old->next 是普通读。如果 old 已经被别人 pop 并释放，这个读就越界了

坑 1 和坑 3 其实是同一个问题的两面：无锁结构里，"什么时候可以安全释放一个节点"是无法从引用计数推出来的。因为别的线程可能在不持有任何引用的情况下，手里攥着一个裸指针准备做 CAS。这就是所谓"内存回收问题"，它是无锁编程里最难的部分，比 CAS 循环本身难十倍。

如果你只记住一句话：无锁数据结构的难点不在插入删除的逻辑，而在内存回收。写一个能跑的 push/pop 只要半小时，写一个在 32 核上跑一年不出 use-after-free 的版本，可能要半年。
模块 4

无锁队列：链表 vs 环形缓冲

工程上真正用得多的不是链表队列，而是固定容量的环形缓冲（ring buffer）。原因很实际：不用管理节点生命周期。

Michael-Scott 队列：教科书的答案

MS 队列（1996）是第一个实用的无锁 FIFO 队列，至今仍是 ConcurrentLinkedQueue 这类实现的基础。核心思路：

永远有一个哑节点（dummy node）。head 指向哑节点，tail 指向最后一个节点。队列为空时 head == tail，而不是 null。
入队分两步。先 CAS 把新节点挂到 tail->next，成功后再 CAS 把 tail 前移。第二步失败不要紧，别的线程会帮忙推进（这就是"协助"机制）。
出队分两步。先读 head->next，取值，再 CAS 把 head 前移到它。旧 head 变成新的哑节点。

这个"两步 + 允许中间状态"的模式是无锁设计的通用套路：把一次原子修改拆成两步，中间状态对其他线程可见且可修复。代价是任何时刻都可能有线程看到"tail 落后于实际末尾"，所以读操作必须能处理这种情况。

但 MS 队列同样需要内存回收机制。出队后的节点什么时候能 free？还是要靠 hazard pointer 或 EBR。这就是为什么很多团队宁愿用环形缓冲。

环形缓冲：SPSC 版本几乎免费

SPSC（Single Producer Single Consumer，单生产者单消费者）是唯一一个能写得又简单又正确的无锁结构。因为只有两个线程，各自只写自己的索引，不需要 CAS。

template<typename T, size_t N>
class SpscQueue {
    // 两个索引分居两条 cache line，避免伪共享
    alignas(64) std::atomic<size_t> head_{0};   // 消费者写
    alignas(64) std::atomic<size_t> tail_{0};   // 生产者写
    alignas(64) T buf_[N];

public:
    bool push(const T& v) {
        size_t t = tail_.load(std::memory_order_relaxed);   // 只有我在写 tail
        size_t next = (t + 1) % N;
        if (next == head_.load(std::memory_order_acquire)) return false; // 满
        buf_[t] = v;                                        // 先写数据
        tail_.store(next, std::memory_order_release);       // 再发布索引
        return true;
    }

    bool pop(T& out) {
        size_t h = head_.load(std::memory_order_relaxed);
        if (h == tail_.load(std::memory_order_acquire)) return false; // 空
        out = buf_[h];
        head_.store((h + 1) % N, std::memory_order_release);
        return true;
    }
};

注意三个细节：① buf_[t] = v 必须在 tail_.store 之前，靠 release 保证；② 消费者读 tail_ 用 acquire，保证看到索引时数据也可见；③ 两个索引 alignas(64) 分开，否则它们落在同一条 cache line 上，生产者和消费者的写会互相使对方的缓存失效——这就是伪共享（false sharing）。

伪共享的代价有多大？实测在 32 核机器上，两个线程各写同一个 cache line 里的不同变量，吞吐可能只有分开时的 1/5 到 1/10。因为每次写都要把整条 line 从对方核"抢"过来。

MPMC 环形缓冲：Disruptor 的思路

多生产者多消费者时，简单的 head/tail 不够用了。LMAX 的 Disruptor 给出的方案是：

设计解决什么
预分配槽位环里的对象在启动时全部创建好，运行期只改字段，不 new/delete，GC 和 malloc 都消失了
序列号（sequence）每个生产者和消费者各维护一个单调递增的序列号，用序列号判断"能不能写/能不能读"，不用 CAS 抢索引
批量发布生产者一次可以占多个槽，消费者一次可以处理一批，摊薄同步开销
缓存行填充所有热点变量都 padding 到 64 字节，彻底消除伪共享
无锁但非无等待生产者和消费者之间靠 sequence 的可见性协作，本质仍是 CAS/acquire-release

Disruptor 的实测吞吐能到单机每秒千万级消息，比 ArrayBlockingQueue 高一个数量级。但它的收益有很大一部分来自"预分配 + 批量 + 缓存行对齐"，而不是"无锁"本身。这个区分很重要——很多场景下，你用一把锁 + 预分配 + 批量，也能拿到大部分收益。

模块 5

ABA 问题：地址没变，内容变了

ABA 是无锁编程的"幽灵 bug"：逻辑完全正确，测试完全通过，压力测试跑一周都没事，然后在大促当天崩了。

怎么发生的

// 初始栈：A -> B -> C
// 线程 1 准备 pop，读到了 head = A，next = B，正在算 CAS(A, B)

// 此时线程 2 干了三件事：
//   1. pop A   → 栈变成 B -> C
//   2. pop B   → 栈变成 C
//   3. push A  → 栈变成 A -> C   （A 的内存被复用了）

// 线程 1 的 CAS 现在执行：head 是 A 吗？是。换成 B？成功。
// 结果：head 指向了 B —— 但 B 已经被释放了。
// 栈变成 B -> ??? ，B 是野指针

关键在于 CAS 只比较值（指针地址），不比较历史。地址 A 确实还是 A，但它背后的对象已经经历了一轮"删除-重建"。

三种解法

方案做法代价
带标签的指针
tagged pointer		把"版本号"和指针打包在一起，每次修改版本号 +1。CAS 比较的是"指针+版本"这个整体需要 128 位 CAS；版本号会回绕（通常 16 位，65536 次后归零）
危险指针
hazard pointer		每个线程声明"我正在用这个指针"，回收者扫描所有线程的声明，确认没人用才释放每次访问要额外写一次共享内存；回收要扫描全部线程
纪元回收 / RCU
EBR / RCU		把时间分成纪元，只有"所有线程都离开旧纪元"后才批量回收回收有延迟；读侧几乎零开销（RCU 的最大优势）

方案一：tagged pointer

// x86-64 的虚拟地址实际只用 48 位，高 16 位空闲
// 可以把 16 位计数器塞进去，用 64 位 CAS 一次比较
struct TaggedPtr {
    uintptr_t raw;      // 低 48 位指针，高 16 位计数

    Node* ptr()  const { return (reinterpret_cast<Node*>(raw & 0x0000FFFFFFFFFFFF)); }
    uint16_t tag() const { return raw >> 48; }

    TaggedPtr next(Node* p) const {
        return { (reinterpret_cast<uintptr_t>(p)) | ((uintptr_t)(tag() + 1) << 48) };
    }
};

std::atomic<TaggedPtr> head;   // 8 字节，单条 CAS 搞定

这个技巧利用了"用户态地址空间用不满 64 位"这个事实。风险：① 未来 CPU 可能支持 57 位虚拟地址（Intel 的 5-level paging），高位的余量会变小；② 计数 65536 次就回绕，理论上仍然可能 ABA，只是概率极低；③ 依赖地址对齐和地址空间布局，可移植性差。

更稳妥的版本是用 __int128 + cmpxchg16b，把完整的 64 位指针和 64 位计数器打包。但 128 位 CAS 在很多平台上不是基线的（x86 需要 -mcx16，ARM 需要 ARMv8.1 的 LSE 扩展），而且比 64 位 CAS 慢不少。

方案二：hazard pointer

// 每个线程有一个全局可见的"危险指针"槽位
std::atomic<Node*> hazard[MAX_THREADS];

// 读侧：
do {
    p = head.load(std::memory_order_acquire);
    hazard[tid].store(p, std::memory_order_seq_cst);  // 声明"我在用 p"
} while (head.load(std::memory_order_acquire) != p);  // 复查：p 还是 head 吗

// 现在 p 安全了，可以放心读 p->next
auto next = p->next;

// 回收侧（要删除 retired 列表里的节点时）：
for (auto* n : retired) {
    bool in_use = false;
    for (int i = 0; i < MAX_THREADS; i++)
        if (hazard[i].load(std::memory_order_seq_cst) == n) { in_use = true; break; }
    if (!in_use) delete n;   // 确认没人引用，可以释放
}

关键在"声明 + 复查"这两步。声明之后如果 head 变了，说明你拿到的可能是旧值，重来。这个循环保证：你最终持有的指针，一定在声明之后仍然是有效的。

代价是每次读都要写一次共享内存（seq_cst store），这在读多写少的场景下是明显开销。所以 hazard pointer 适合"读操作不密集但结构复杂"的场景。

方案三：RCU / EBR

Linux 内核的 RCU（Read-Copy-Update）是这套思路的极致：读侧零开销（不需要原子操作、不需要屏障），只在写侧付出代价。做法是：

  • 读者进入临界区时标记"我在读"（在 Linux 里就是禁止抢占或标记 per-CPU 计数）
  • 写者修改时先复制一份新版本，原子替换指针，旧版本延迟释放
  • 等到所有 CPU 都经历过一次上下文切换（宽限期结束），确认没有读者还在旧版本上，才真正释放

这套机制在"读极多、写极少"的场景（路由表、配置、白名单）近乎完美。但它的语义是"读到的可能是旧值"，不保证实时性。用在需要强一致的场景会出问题。

一个反直觉的事实：ARM 的 LL/SC 指令（ldxr/stxr）天然免疫 ABA。因为 stxr 会在"这期间有人写过这条 cache line"时失败，哪怕写回的是相同的值。所以 ARM 上用 LL/SC 实现的无锁结构不需要 tagged pointer。
但 x86 只有 CAS，没有 LL/SC，所以 ABA 在 x86 上是必须正面解决的问题。这也是同一份无锁代码在两种架构上表现不同的原因之一。
模块 6

无锁的真实代价

前面讲的都是"怎么做到"，这一节讲"值不值得"。无锁有三笔隐藏成本，很多人算漏了。

成本一：高竞争下比锁更慢

这不是理论推演，是可以测出来的。假设 32 个线程各自做 100 万次自增：

实现耗时量级说明
单线程（基线）约 1ms纯寄存器加法
32 线程 + mutex约 200~800ms排队，有 futex 挂起/唤醒开销
32 线程 + 同一个 atomic可能 2~10 秒每次 CAS 都让 cache line 在 32 个核之间弹
32 线程 + 分片计数约 5~15ms每个线程一个计数器，最后求和

最后一行才是正解：与其纠结用锁还是用原子，不如消除共享。这是无锁编程最重要的一条经验——最好的同步是不需要同步。

成本二：内存回收极难

前面已经说过，但值得再强调一次。对比一下两种方案的心智负担：

任务加锁版本无锁版本
实现一个队列半小时，逻辑清晰两天，还要处理中间状态
节点释放出锁之后 delete 就行需要 hazard pointer / EBR / RCU，几百行
证明正确锁保证了互斥，推理简单要考虑所有交错，几乎无法手工证明
出 bug 后定位加日志、复现、看栈可能是百万分之一概率的 use-after-free，core dump 都指不到源头

成本三：正确性几乎无法验证

这是最要命的一点。无锁代码的 bug 具有三个特征：概率低、依赖时序、在 x86 上可能永远不出现。

工具能做什么局限
-fsanitize=thread (TSan)检测数据竞争对 relaxed 原子和复杂内存序的建模不完整，可能漏报或误报
Relacy穷举线程交错，模型检查只能测很小的场景（几线程、几步操作）
CDSChecker专门检查 C11/C++11 内存序同上，规模受限
压力测试提高复现概率不能证明正确，只能证伪
跨架构测试在 ARM 上跑（弱内存模型暴露问题）成本高，很多团队没有 ARM 环境
一个真实世界的规律：自研无锁结构的事故，绝大多数不是"逻辑写错了"，而是"内存序写松了"。开发者在本机 x86 上测了三个月没问题，上线后迁到 ARM 集群，一周内出了三次数据错乱。
原因是 x86 的 TSO 太强，把很多错误掩盖了。你写的 relaxed 在 x86 上碰巧能用，在 ARM 上就是不行。
模块 7

什么时候真的需要无锁

判断标准不是"我的服务要求高并发"，而是"我能不能容忍一次 10 微秒的线程挂起"。

四个真正成立的场景

超低延迟交易
撮合引擎、行情分发。延迟以纳秒计，一次线程唤醒（几微秒）就是几个数量级的差距。这里无锁是刚需，不是优化。
操作系统内核
中断上下文不能睡眠，所以不能用会阻塞的锁。Linux 的 RCU、per-CPU 变量、seqlock 都是为这个约束设计的。
特定数据结构
Disruptor 式的事件流水线、DPDK 的收发包环、内存分配器的线程本地缓存。结构固定、容量固定、访问模式可预测。
信号处理 / 异步回调
信号处理函数里只能调用异步信号安全的函数，mutex 不在其中。只能用原子操作或 volatile sig_atomic_t。

不需要无锁的场景（占了 95%）

场景更该做的事
Web 服务的请求计数分片计数（每线程一个），或者干脆用 metrics 库
连接池、对象池每线程一个池（thread-local），完全不需要共享
日志队列每线程一个缓冲，定期 flush 到共享队列
缓存分片（sharding）：按 key 哈希到 16 个分片，每个分片一把锁
任务分发用成熟的消息队列，或者 work-stealing 调度器

"分片"是被严重低估的技术。把一个热点结构拆成 N 份，每份一把锁，竞争立刻降到 1/N。实现成本几乎为零，正确性有保障，效果往往比无锁更好。

一个决策流程

先测量。用 perf / pprof 确认锁竞争真的是瓶颈。看 futex 的等待时间占比，或者直接看火焰图里 pthread_mutex_lock 的比例。
能消除共享吗？线程本地存储、分片、消息传递——这三招能解决绝大部分问题，而且没有正确性风险。
能接受偶尔的延迟尖刺吗？如果能，读写锁、分段锁、无锁读 + 加锁写的组合，都比纯无锁好维护。
非要用无锁，能用现成库吗？folly、boost.lockfree、moodycamel 都是经过大规模验证的。自己写只在"结构非常特殊且性能收益可量化"时才考虑。

性能对比：先看清代价再动手

操作无竞争高竞争（32 线程）
mutex lock/unlock约 20ns微秒级（futex 挂起/唤醒）
atomic load/store (relaxed)约 1ns仍约 1ns（只读不抢）
atomic CAS约 5~20ns可能几百 ns，且大量失败重试
atomic fetch_add约 20ns100ns 以上，吞吐崩塌
cache line 跨核转移—40~100ns
SPSC 队列 push/pop约 10~20ns不适用（只有一个生产者）

这些数字会随 CPU 代际变化，但量级关系是稳定的：一次跨核 cache line 转移（40~100ns）比一次 CAS 指令本身（5~20ns）贵得多。所以无锁优化的核心不是"减少指令"，而是"减少 cache line 的跨核移动"。

一句话总结：无锁不是"更高级的锁"，它是在特定约束下（低竞争、固定容量、简单结构、可接受内存不回收）才成立的一种设计。绝大多数业务代码，用分片 + 线程本地 + 成熟库，能拿到 90% 的收益，只承担 10% 的风险。
常见坑

十个无锁实践坑

1
用 relaxed 写"标志位 + 数据"的发布模式
数据写完了，标志位先可见，消费者读到标志却读到旧数据。必须用 release store + acquire load 配对。
2
在 x86 上测通了就认为没问题
x86 的 TSO 会掩盖大部分重排错误。上线到 ARM 就炸。CI 里必须有 ARM 或者至少用模型检查工具。
3
pop 之后立刻 delete 节点
别的线程可能还攥着这个指针准备 CAS。必须用 hazard pointer / EBR / RCU，或者干脆不释放（固定容量池）。
4
忽略了 ABA
地址没变但对象换了。用 tagged pointer 加版本号，或者改用带索引的环形缓冲（索引单调递增，天然无 ABA）。
5
两个热点变量挨在一起
伪共享会让两个线程互相使对方缓存失效，吞吐掉 5~10 倍。用 alignas(64) 分开，或加 padding。
6
以为 CAS 循环在高竞争下更快
32 个线程抢一个变量时，CAS 的失败重试会让吞吐崩塌，比 mutex 差一个数量级。分片才是解。
7
用 atomic<shared_ptr>
它内部通常是一把自旋锁，根本不是无锁的。高频路径上用它，等于给自己埋了个隐藏的串行点。
8
在信号处理函数里用 mutex
mutex 不是异步信号安全的，可能死锁。只能用 atomic 或 volatile sig_atomic_t，配合 lock-free 的标志位。
9
自己发明内存回收算法
hazard pointer 和 EBR 都是经过十几年打磨的。自己写的版本通常在高负载下才暴露问题，而且极难调试。
10
没测量就上无锁
90% 的"锁竞争"其实是临界区太长、在里面做了 IO 或者分配内存。先把临界区缩短，比换无锁有效得多。
自测

六道题

1. "lock-free" 的准确定义是？
正确答案：至少有一个线程能推进。第三个选项是 wait-free（每个线程都能完成）。lock-free 允许多个线程饿死，只要整体在前进。
2. 生产者写数据后 store(release)，消费者 load(acquire) 看到标志。这保证了什么？
正确答案：建立 happens-before。release 阻止前面的操作后移，acquire 阻止后面的操作前移。只要消费者读到了新标志，就一定能读到之前写的数据。
3. ABA 问题的本质是？
正确答案：CAS 缺少历史信息。地址 A 被释放又重建，CAS 看到还是 A 就成功了，但 A 背后的结构已经变了。解法是加版本号（tagged pointer）、hazard pointer 或 EBR。
4. 为什么 SPSC 环形队列不需要 CAS？
正确答案：每个索引只有一个写者。单写者的场景下，普通 store 加 release 语义就够了，不需要 CAS 的"比较再交换"。这是 SPSC 又简单又快的根本原因。
5. 32 个线程同时 fetch_add 同一个计数器，性能会怎样？
正确答案：大幅下降。每次原子操作都要独占 cache line，32 个核抢同一条 line，一次转移就要 40~100ns。解法是分片计数（每线程一个，最后求和）。
6. 项目里有个热点 map 出现锁竞争，第一步应该做什么？
正确答案：测量 + 分片。分片能把竞争降到 1/N，实现简单、正确性有保障，收益往往比换无锁更大。自旋锁在高竞争下更糟（空转烧 CPU）。
