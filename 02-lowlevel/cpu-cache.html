二十分钟学透 CPU 与缓存层次

大多数"程序变慢了"的结论，最后都落在这三件事上：指令没发出去（分支预测失败）、数据没取回来（缓存缺失）、两个核在抢同一行缓存（伪共享）。这篇讲清楚 CPU 到底怎么跑代码，以及为什么改一个结构体字段顺序能让吞吐翻倍。

模块 1

一条指令怎么执行

先建立一个准确的心智模型。教科书上的"取指 → 译码 → 执行 → 写回"是一条指令的生命周期，不是 CPU 的工作方式。真实 CPU 是同时有几十上百条指令处在不同阶段。

四个阶段各自在干什么

阶段动作真正的瓶颈在哪
取指 Fetch按 PC（程序计数器）从 L1I 取指令字节，推进 PC指令缓存缺失、跨缓存行的长指令、分支目标算不出来
译码 Decodex86 把变长的 CISC 指令翻译成定长的微操作（μop，micro-op）x86 译码宽度是硬限制，现代大核 4~6 条/周期；复杂指令会拆成多条 μop
执行 Execute乱序调度到空闲的执行单元（ALU / FPU / LSU / 向量单元）执行单元数量、数据依赖、操作数没就绪
写回 Writeback结果写进寄存器堆，标记 ROB（重排序缓冲）条目完成通常不是瓶颈，但要等前面所有指令都完成才能提交

流水线与超标量

流水线（pipeline）是把上面四个阶段拆成更细的十几级，让不同指令占据不同级，像工厂流水线一样重叠。理想情况下每周期完成一条指令，这就是 CPI = 1。

但现代 CPU 不止一条流水线，而是超标量（superscalar）：一个周期同时译码 4~6 条、同时发射、有 4 个以上的 ALU。理论上每周期能完成 4~6 条指令。

衡量指标是 IPC（Instructions Per Cycle，每周期完成指令数）：

IPC = 完成的指令数 / 消耗的周期数
CPI = 1 / IPC

# 一颗 3.0 GHz、IPC = 2 的核
每秒指令数 = 3.0e9 × 2 = 60 亿条/秒

# 实测经验值（通用业务代码，非纯计算内核）
IPC ≈ 2.0 ~ 3.0   紧凑循环、数据在 L1
IPC ≈ 1.0 ~ 2.0   普通业务逻辑、有一定分支
IPC ≈ 0.2 ~ 0.8   指针追逐、大数组随机访问、频繁 cache miss
为什么 IPC 上不去：理论宽度 4~6 是"发射能力"，不是"完成能力"。真正卡住的是三件事 —— ① 数据依赖：下一条要用上一条的结果，只能等；② 缓存缺失：执行单元空转等数据；③ 分支预测失败：前端取错了指令，整条流水线要清空重来。这三者合起来，才是 IPC 的真实上限。

为什么单核频率停在 4~5 GHz

2005 年之前，频率每 18 个月翻一倍，靠的是 Dennard 缩放（特征尺寸缩小，电压同比降低，功耗密度保持不变）。这个规律在 130nm~90nm 附近失效了：电压不能再线性下降，漏电流开始指数上升。

约束具体机制
动态功耗 ∝ C·V²·f频率翻倍，功耗也翻倍。3.0 GHz 到 6.0 GHz 意味着同样的芯片要散发两倍热量，风冷压不住
电压墙继续降压会让晶体管无法可靠区分 0 和 1，3~5 GHz 附近需要 ~1V 以上，再往上功耗爆炸
漏电功耗工艺越先进，静态漏电占比越高。即使不跑东西，芯片也在发热
互连延迟信号在硅里的传播速度有限，一个时钟周期内信号只能走约 1~2 mm。芯片越大，全局同步越难

所以 2006 年之后，厂商转向多核 + 更宽的发射 + SIMD：不提高频率，而是每周期做更多事，或者干脆堆核。这就是为什么今天的单核性能相比 2010 年只提升了 2~3 倍，而不是 10 倍。

对写代码的直接推论：单线程性能的提升空间已经很窄。如果你的服务是单线程瓶颈，靠"换更好的 CPU"最多拿到 20%~30%，靠"优化算法 / 减少内存访问 / 并行化"才能拿到数量级。反过来，如果你的热点函数 IPC 只有 0.5，先别急着多线程 —— 先看它是不是在等内存。
模块 2

为什么必须有缓存

因为 CPU 和内存的速度差已经从"几倍"变成了"两个数量级"，而且这个差距还在扩大。这个现象有个专门的名字：内存墙（Memory Wall）。

六组延迟数据

下面按数量级排列。以 3 GHz 的核为基准，一个周期 ≈ 0.33 ns。

层级典型延迟折算周期说明
寄存器~0.3 ns1 周期没有延迟，直接参与运算
L1 数据缓存~1 ns4~5 周期每核私有，32~48 KB。命中率通常 90%+
L2 缓存~3~4 ns12~14 周期每核私有，256 KB~1 MB
L3 缓存~10~20 ns30~60 周期多核共享，8~32 MB。跨 die 访问更慢
DRAM 内存~80~100 ns250~300 周期容量大但慢，是"内存墙"的本体
NVMe SSD~100 μs30 万周期随机读一次，CPU 能执行几十万条指令
机械硬盘~10 ms3000 万周期一次寻道，相当于 CPU 干了一秒钟的活

把 L1 和 DRAM 放在一起看：一次内存访问的时间，够 CPU 执行 250 条左右的简单指令。如果这些指令因为等数据而无法执行，执行单元就完全空转。

内存墙有多严重

# 一个直观的换算：光在 1 纳秒里走 30 厘米
3 GHz 的一个周期 = 0.33 ns  →  光走 10 厘米
一次 DRAM 访问 100 ns        →  光走 30 米

# 也就是说，CPU 等一次内存的时间里，信号理论上可以绕机房一圈
# 这不是比喻，这是物理约束：电信号在硅里的速度约是真空中一半

# 历史趋势（量级，非精确值）
1990 年：CPU 周期 ≈ 内存延迟 × 10
2000 年：CPU 周期 ≈ 内存延迟 × 100
今天  ：CPU 周期 ≈ 内存延迟 × 250 ~ 300

缓存的全部意义，就是用"小但快"的存储，把这 250 个周期的等待在大多数情况下藏起来。藏得住靠的是局部性原理，藏不住的部分就是性能损耗的来源。

为什么不用 SRAM 做整个内存

存储类型单元面积速度用途
SRAM6 个晶体管/bit最快缓存。贵、密度低、静态功耗高
DRAM1 个晶体管 + 1 个电容慢 100 倍主存。便宜、密度高，但需要定期刷新

SRAM 的单元面积是 DRAM 的 6 倍以上，同样的容量成本高一个数量级。用 SRAM 做 64 GB 内存，成本会高到无法商用。所以层次结构不是设计选择，是物理和经济的必然结果。

模块 3

缓存层次与局部性

三级的组织方式

层级典型容量归属关键特征
L132~48 KB（数据）
+ 32 KB（指令）		每核私有哈佛结构，指令和数据分开。4~8 路组相联，访问延迟 4~5 周期
L2256 KB~1 MB每核私有统一缓存（指令+数据）。8~16 路组相联，延迟 12~14 周期
L38~32 MB全核共享
（分片）		物理上切成多个 slice，用环形/网格互连。跨核访问比本地慢
TLBL1: 64 项
L2: 1536~2048 项		每核地址翻译缓存，它 miss 的代价和 cache miss 一样大，很多人忘了它
三个常被忽略的细节：
① L3 不是"一个大池子"。它被切成每核一块的 slice，靠环形总线连接。核 A 访问核 B 旁边的 slice，延迟比访问自己旁边的 slice 高 50% 以上。这就是为什么 NUMA 机器上要绑核。
② L1/L2 是 inclusive 还是 exclusive：Intel 传统上 L3 是 inclusive（L3 包含 L1/L2 的内容），好处是 L3 可以直接做探听过滤；AMD Zen 的 L3 是 victim cache（victim cache，被 L2 淘汰的块放进 L3），更省容量。行为不同，优化策略也不同。
③ 超线程的两个逻辑核共享同一份 L1/L2。所以"2 vCPU"不等于"2 份 L1"，同物理核上的两个线程会互相踢缓存。

局部性：缓存能起作用的唯一原因

类型含义代码里的表现
时间局部性刚访问过的地址，很可能马上再访问循环变量、累加器、热点函数、小范围的查找表
空间局部性访问了地址 X，很可能马上访问 X+1数组顺序遍历、结构体连续字段、顺序执行的指令
顺序局部性空间局部性的特例：指令和数组天然顺序硬件预取器（prefetcher）专门吃这个，能提前 4~10 个缓存行把数据拉进来

缓存行是 64 字节。这意味着你读一个 4 字节的 int，硬件实际搬了 64 字节。如果接下来用的数据在这 64 字节里，这次搬运就赚了；如果跳到 1 MB 之外，这 60 字节就白搬了 —— 这就是"空间局部性差"的真实成本。

平均访问延迟怎么算

核心公式是 AMAT（Average Memory Access Time，平均内存访问时间）：

AMAT = 命中时间 + 缺失率 × 缺失代价

# 只有一级缓存时
AMAT = T_L1 + (1 - H_L1) × T_mem

# 两级（L1 缺失后再看 L2）
AMAT = T_L1 + (1 - H_L1) × [ T_L2 + (1 - H_L2) × T_mem ]

# 代入真实数字：T_L1 = 1ns, H_L1 = 95%, T_L2 = 4ns, H_L2 = 80%, T_mem = 100ns
AMAT = 1 + 0.05 × [ 4 + 0.20 × 100 ]
     = 1 + 0.05 × [ 4 + 20 ]
     = 1 + 0.05 × 24
     = 2.2 ns

# 对比：假设完全没有 L2，全部 L1 缺失都打到内存
AMAT = 1 + 0.05 × 100 = 6.0 ns
# 一个 L2 把平均延迟从 6.0ns 降到 2.2ns，接近 3 倍

命中率是高度非线性的

# 固定 T_L1 = 1ns, T_mem = 100ns，只改命中率
H = 99.9%  →  AMAT = 1 + 0.001 × 100 = 1.10 ns
H = 99.0%  →  AMAT = 1 + 0.010 × 100 = 2.00 ns
H = 95.0%  →  AMAT = 1 + 0.050 × 100 = 6.00 ns
H = 90.0%  →  AMAT = 1 + 0.100 × 100 = 11.0 ns

# 关键观察：命中率从 99% 掉到 90%，只掉了 9 个百分点
# 但平均延迟从 2.0ns 涨到 11.0ns —— 5.5 倍
# 因为缺失率从 1% 变成 10%，是 10 倍
工程含义：优化缓存要看缺失率，不是命中率。命中率 99% 听起来很好，但缺失率 1% 意味着每 100 次访问就有一次要等 100 ns。如果这段代码本来只要 10 ns 就能算完，那一次缺失就把整体拖慢了 10 倍。
所以：把"最热的那 1% 访问"从内存挪进缓存，收益远大于"把命中率从 95% 提到 96%"。前者是消除长尾，后者是优化平均值。

组相联与冲突缺失

缓存不是全相联的（那样比较器成本爆炸），而是组相联（set-associative）：地址被切成 tag / index / offset 三段，index 决定落到哪一组，组内用 tag 并行比较。

# 64 字节缓存行、8 路组相联、32 KB L1 的地址切分
offset = 低 6 位      # 64 = 2^6，行内偏移
index  = 中间 6 位    # 32KB / 64B / 8路 = 64 组 = 2^6
tag    = 剩余高位

# 冲突缺失：两个地址的 index 相同但 tag 不同
# 如果映射到同一组且该组只有 8 个位置，第 9 个就会踢掉一个
# 经典案例：按 2 的幂做步长遍历二维数组
# 4096 × 4 字节 = 16 KB 步长 → 每次都落到同一组

这就是为什么有时候"数组大小改成 4096 的倍数之后突然变慢"。解法是把数组维度加个偏移（比如 [N][N+1]），破坏 2 的幂对齐。

模块 4

缓存行与伪共享

这是多线程性能问题里最隐蔽、也最容易修的一类。它的可怕之处在于：代码里没有任何共享变量，两个线程改的是完全不同的字段，性能却掉了 5~10 倍。

64 字节缓存行与 MESI

缓存和内存之间以 缓存行（cache line）为单位传输，x86 上固定 64 字节。多核之间要保证一致性，靠的是 MESI 协议（Modified / Exclusive / Shared / Invalid，四种状态）。

状态含义写操作时发生什么
M 已修改本核独占，且与内存不一致（脏）直接写，无需通知
E 独占本核独占，与内存一致静默升级为 M，零通信
S 共享多个核都有副本，与内存一致必须先发 Invalidate 让其他核作废，等 ACK 才能升级为 M
I 无效本核的副本已作废要重新从 L3/内存取

关键在 S → M 这一步：要跨核通信，等对方把缓存行作废并回 ACK。这个往返在同一个 socket 内约 40~70 周期，跨 socket 要 100~200 周期。

伪共享是怎么发生的

两个线程分别修改两个逻辑上无关的变量，但这两个变量恰好落在同一个 64 字节缓存行里。于是：

核 0 要写变量 A，发现缓存行是 S 状态（核 1 也有一份），发 Invalidate。
核 1 的副本作废，回 ACK，核 0 升级为 M，写入成功。
核 1 要写变量 B（同一行），发现是 I 状态，必须重新取整行（从核 0 或 L3）。
核 1 取到后发 Invalidate 给核 0，核 0 作废，核 1 升级为 M。
两个核就这样来回抢同一行，每次写都要一次跨核往返。这就是"缓存行乒乓"（cache line ping-pong）。

代码对比

/* ===== 版本 A：伪共享 ===== */
struct counters {
    long hits;   // 偏移 0
    long miss;   // 偏移 8，和 hits 同属一个 64 字节缓存行
};
struct counters c;

// 线程 0
for (long i = 0; i < N; i++) c.hits++;
// 线程 1
for (long i = 0; i < N; i++) c.miss++;

// 结果：两个线程在抢同一行，每次自增都是一次跨核往返
// 实测常见：比单线程还慢，或者只有单线程的 30%~50%


/* ===== 版本 B：手工填充（padding）===== */
struct padded {
    long hits;
    char pad[56];   // 8 + 56 = 64，下一个字段强制落到新的一行
    long miss;
};
// 代价：结构体从 16 字节涨到 128 字节
// 收益：两个线程各写各的行，互不干扰，接近线性加速


/* ===== 版本 C：对齐到缓存行（更严谨）===== */
// C11 / C++17 标准写法，不用手算 pad 大小
struct aligned_counter {
    _Alignas(64) long value;
};
// C++17 用 alignas(64)，并配合 std::hardware_destructive_interference_size
// 注意：这个常量在不同编译器上可能给出不同值，跨平台时不要硬编码 64

Java 的 @Contended

// JDK 内部注解，位于 jdk.internal.vm.annotation 包
// 作用是让 JVM 在字段前后自动插入 padding
// 第三方代码要生效，必须加 JVM 参数 -XX:-RestrictContended
// （默认只对 JDK 内部类生效，防止滥用导致堆膨胀）

// 更通用的做法：直接用 long 数组 + 索引错开，靠数组元素间距拉开
// 或者用 AtomicLongArray，每个线程用不同的下标
// 最土但最有效的做法：每个线程一个独立的 ThreadLocal 计数器，最后汇总

怎么检测伪共享

# perf c2c 是专门为伪共享设计的工具（Linux 4.10+）
perf c2c record -a -- sleep 10
perf c2c report

# 报告里重点看两列
#   HITM（Hit Modified）：某核访问的行在别的核里是 M 状态 → 就是伪共享
#   LLC Load Hitm：按缓存行聚合，哪一行被抢得最凶一目了然

# 没有 perf c2c 时的替代判断
# 1. 多线程版本比单线程还慢，且 CPU 利用率很高（不是阻塞）
# 2. perf stat 显示 cache-misses 异常高，但数据量明明很小
# 3. 把线程数从 2 加到 4，吞吐不升反降
伪共享最坑的一点：它不会报错，也不会阻塞，只会让 CPU 空转。
从 top 上看，CPU 是 100% 忙的，你以为是"算得多"，实际是"抢缓存抢得多"。这时候加机器、加线程都没用，只会让争抢更激烈。
经验法则：任何被多个线程高频写入的计数器、状态标志、引用计数，都要检查它和邻居是不是在同一行。尤其是结构体里"读多"和"写多"的字段混排时，几乎必然出问题。
模块 5

分支预测与乱序执行

为什么需要分支预测

流水线有十几级。如果取指阶段不知道下一条指令在哪（因为要等前面的条件判断算出来），流水线就会停下来等十几个周期。为了不让流水线停，CPU 干脆猜：猜完继续往下取，猜错了再回滚。

预测器原理准确率
静态预测固定规则，比如"向后跳转猜 taken"（循环继续）~70%
两级自适应用历史位记录每个分支最近几次的结果~90%
TAGE多条不同长度的历史表投票，现代大核标配~95%~97%

看起来 95% 已经很高了。但算一下：每 20 条指令有 1 个分支，5% 猜错，就是每 400 条指令错一次。每次错的代价是 15~20 周期（要清空流水线，从正确的地址重新取指）。

# 预测失败的代价计算
假设：IPC 理想值 = 3，每 20 条指令一个分支，预测准确率 95%

无预测失败时：1000 条指令 / 3 = 333 周期
失败次数：1000 / 20 × 5% = 2.5 次
额外周期：2.5 × 18 = 45 周期
实际周期：333 + 45 = 378 周期
实际 IPC：1000 / 378 = 2.65   // 掉了 12%

# 如果预测准确率掉到 80%（数据随机分布的分支）
失败次数：1000 / 20 × 20% = 10 次
额外周期：10 × 18 = 180 周期
实际周期：333 + 180 = 513 周期
实际 IPC：1000 / 513 = 1.95   // 掉了 35%

经典例子：分支 vs 无分支

// 版本 A：有分支。如果数组是随机数据，预测准确率约 50%
long sum = 0;
for (int i = 0; i < n; i++)
    if (a[i] >= 128) sum += a[i];

// 版本 B：无分支，用掩码消除条件跳转
long sum = 0;
for (int i = 0; i < n; i++) {
    int mask = -(a[i] >= 128);   // 条件成立时 mask = 0xFFFFFFFF，否则 0
    sum += a[i] & mask;
}

// 数据已排序时：A 和 B 差不多（分支高度可预测）
// 数据随机时：B 明显更快（A 有 50% 预测失败率）
// 编译器 -O2 有时能自动做这个转换，但不是总能
别过度迷信"消除分支"。现代编译器和 CPU 已经很强，手写掩码有时反而阻碍向量化。正确做法是：先测，确认分支确实是瓶颈，再改。用 perf stat -e branch-misses,branches 看失败率，如果低于 1%，改它没意义。

乱序执行：为什么有序的代码会乱序跑

程序的语义是顺序的，但 CPU 可以在不改变单线程可见结果的前提下，打乱实际执行顺序。三个关键机制：

机制作用
寄存器重命名
register renaming		架构寄存器只有 16 个，但物理寄存器有 180+ 个。每条写寄存器的指令分配一个新的物理寄存器，消除了假依赖（WAW / WAR）。这样 a = b + c; a = d + e; 两条指令可以并行
乱序发射
out-of-order issue		指令进入保留站（reservation station）排队，谁的操作数先就绪谁先执行，不看程序顺序
ROB 顺序提交
in-order retire		执行可以乱序，但结果必须按程序顺序提交。ROB（重排序缓冲）保证：要么全部生效，要么（异常/预测失败时）全部丢弃

所以"有序代码乱序执行"的本质是：执行阶段完全乱序，提交阶段严格有序。对单线程来说，你永远观察不到乱序的结果。但对多线程，另一个核看到的是内存的中间状态，这就是模块 6 要讲的问题。

乱序窗口是有限的：现代大核的 ROB 大约 200~500 项。如果一条 cache miss 的指令卡在 ROB 头部，后面的指令填满 ROB 后就无法再进来，整个窗口停滞。这叫 ROB 阻塞，是内存延迟影响 IPC 的主要路径。

推测执行的安全代价

分支预测 + 乱序执行意味着 CPU 会执行"可能不该执行"的指令。这些指令的结果会被丢弃，但它们对缓存的影响不会完全消失。Spectre / Meltdown（2018 年披露的侧信道攻击）就是利用这一点：通过测量缓存命中时间，推断出本不该被访问的内存内容。

缓解措施（微码更新、KPTI 页表隔离、retpoline 等）都带来了性能损失，典型在 5%~30% 之间，视负载而定。这也解释了为什么同一台机器打补丁前后跑分会有差异。

模块 6

内存屏障与可见性

这是"为什么我的双重检查锁会出问题"的根因。要讲清楚，得先知道 store buffer 这个东西的存在。

store buffer：写为什么不是立刻可见

核要写一个变量，如果这个缓存行不在自己手里（I 状态），就得先发 Invalidate、等 ACK。这个往返几十个周期，写指令不能干等 —— 所以 CPU 加了一个写缓冲（store buffer）：写操作先扔进 buffer，指令立即返回，后台慢慢同步。

# 经典 litmus test（石蕊测试）：Store Buffering
初始：x = 0, y = 0

线程 1              线程 2
x = 1;              y = 1;
r1 = y;             r2 = x;

# 问题：r1 == 0 且 r2 == 0 可能吗？

# 在 x86（TSO）上：不可能。x86 禁止 StoreLoad 重排
# 在 ARM / POWER（弱内存序）上：
#   完全可能！因为 x=1 还在 store buffer 里没刷出去，
#   线程 1 就已经执行了 r1 = y（读到 0）

x86 TSO vs ARM 弱内存序

重排类型x86 (TSO)ARMv8含义
Load → Load禁止允许两次读，后面的不能跑到前面
Load → Store禁止允许读后面的写不能提前
Store → Store禁止允许两次写保持顺序
Store → Load允许允许唯一允许的重排，由 store buffer 造成

TSO（Total Store Order，全存储序）是 x86 的内存模型：除了 Store→Load，其他顺序都保证。这让 x86 上写无锁代码"看起来"很容易，但也埋了坑 —— 在 x86 上测通的代码，搬到 ARM 上（比如 Graviton、Apple Silicon、鲲鹏）就可能出错。

编译器重排：比 CPU 更早的那一层

// 你以为的顺序
data = 42;
ready = 1;

// 编译器看到的：两个不相关的全局变量，可以随便换
// -O2 下很可能生成：先写 ready，再写 data
// 因为编译器不知道另一个线程在等 ready

// 修复：编译屏障，告诉编译器"这里不许跨越重排"
data = 42;
asm volatile("" ::: "memory");
ready = 1;

// 但编译屏障只管编译器，不管 CPU
// 要同时管住 CPU，必须用硬件屏障或原子操作

正确的写法

// ===== C11 / C++11 原子操作（推荐，可移植）=====
// 线程 1
data = 42;
atomic_store_explicit(&ready, 1, memory_order_release);
// release 语义：保证这条 store 之前的所有内存操作，
// 对"读到这个值的线程"都可见

// 线程 2
while (!atomic_load_explicit(&ready, memory_order_acquire)) { }
assert(data == 42);   // 一定成立
// acquire 语义：保证这条 load 之后的所有内存操作，
// 不会跑到它前面

// release + acquire 配对，就构成了 happens-before 关系
// 这是比"加个 barrier"更准确的思维模型


// ===== 硬件屏障指令（了解即可，别手写）=====
x86:   mfence (全屏障) / lfence (读) / sfence (写)
       // 实际上 x86 的 lock 前缀指令自带全屏障效果
ARMv8: dmb ish   // 数据内存屏障，inner shareable 域
       dsb ish   // 更强的数据同步屏障，等所有操作完成
       isb       // 指令同步屏障，用于修改代码后刷新流水线
三个必须纠正的认知：
① volatile 不是同步原语。C/C++ 的 volatile 只保证"不被优化掉、每次都从内存读"，不保证原子性，也不保证顺序。Java 的 volatile 语义更强（有 acquire/release 效果），但依然不保证复合操作的原子性（i++ 仍然不是原子的）。
② "x86 不会重排，所以不用加屏障"是错的。x86 允许 Store→Load 重排，而且编译器重排是另一回事。
③ 双重检查锁（DCL）在 Java 里必须给实例字段加 volatile。否则可能拿到一个"引用已赋值但构造函数还没跑完"的半初始化对象。
工程上的正确姿势：不要手写屏障。用语言提供的同步原语 —— 互斥锁、条件变量、std::atomic、java.util.concurrent、Go 的 channel 和 sync 包。这些原语已经把内存序封装好了。只有在写无锁数据结构（lock-free queue、RCU）时才需要关心 memory_order，而这类代码的正确性验证成本极高，没有充分理由不要自己写。
模块 7

写缓存友好的代码

前面六节是"知道"，这一节是"能改"。三个最有效的动作：改布局、改顺序、改分块。

遍历顺序：行优先 vs 列优先

// C 的二维数组是行优先存储（row-major）：a[i][j] 的地址 = base + (i*N + j)*sizeof(T)
#define N 4096
static int a[N][N];   // 4096 × 4096 × 4B = 64 MB，远超 L3

// 版本 A：行优先遍历 —— 内存连续，每 16 个 int 用满一个缓存行
long sum = 0;
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += a[i][j];

// 版本 B：列优先遍历 —— 每次跨越 4096*4 = 16 KB
long sum = 0;
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += a[i][j];
版本每次访问的缓存行利用率量级
A 行优先16 个 int / 64B，100%基准，比如 30~50 ms
B 列优先1 个 int / 64B，6.25%慢 5~10 倍，而且 TLB 也会被打爆（每次跨页）

这不是理论。同样 1600 万次加法，B 版本要额外搬 64 MB × 16 = 1 GB 的数据（每个元素都单独拉一整行），而 A 版本只搬 64 MB。

为什么很多人感觉不到：小数组（比如 512×512 = 1 MB）整个塞得进 L2/L3，列优先也只是多几次 L3 命中，差距不明显。一旦数组超过 L3 容量，差距立刻出现。所以压测要用真实规模的数据。

分块（blocking / tiling）

如果算法必须同时访问两个维度（比如矩阵乘法 C = A×B），单纯改顺序救不了。解法是分块：把大矩阵切成能塞进 L1/L2 的小块，在小块内部做完全部计算，再移动到下一块。

// 朴素矩阵乘法：内层循环每次跳 B 的一整行，缓存全废
for (int i = 0; i < N; i++)
  for (int j = 0; j < N; j++)
    for (int k = 0; k < N; k++)
      C[i][j] += A[i][k] * B[k][j];

// 分块版：块大小取到 L1 装得下（例如 64×64 的 float 块 = 16 KB）
#define BS 64
for (int ii = 0; ii < N; ii += BS)
 for (int jj = 0; jj < N; jj += BS)
  for (int kk = 0; kk < N; kk += BS)
   for (int i = ii; i < ii+BS; i++)
    for (int j = jj; j < jj+BS; j++) {
      float s = C[i][j];
      for (int k = kk; k < kk+BS; k++)
        s += A[i][k] * B[k][j];
      C[i][j] = s;
    }

// 块大小怎么定：让 A 的一个块 + B 的一个块 + C 的一个块
// 尽量塞进 L2（256KB~1MB）。64×64×4B = 16KB，三块 48KB，很宽裕
// 再配合编译器 -O3 -march=native 的自动向量化，能有 5~20 倍提升

AoS vs SoA

// AoS（Array of Structs）：一个对象的所有字段连续
struct Particle { float x, y, z, mass; };   // 16 字节
struct Particle ps[1000000];                 // 16 MB

// 只更新 x 时：每读 16 字节只用 4 字节，利用率 25%
for (int i = 0; i < n; i++) ps[i].x += vx[i];


// SoA（Struct of Arrays）：按字段拆成多个数组
struct Particles {
    float *x, *y, *z, *mass;
};
// 只更新 x 时：连续读 4 字节数组，利用率 100%
for (int i = 0; i < n; i++) X[i] += vx[i];
// 而且编译器能把这段自动向量化成 8 路 AVX2 或 16 路 AVX-512
布局优势什么时候用
AoS单个对象的字段在一起，访问一个对象的多个字段时局部性好；代码直观面向对象建模、对象整体读写、字段数少
SoA批量处理单个字段时带宽利用率 100%；易向量化；便于 SIMD数值计算、批处理、只更新部分字段、需要 SIMD
一个判断方法：看你的循环是"遍历很多对象，每个对象只碰 1~2 个字段"还是"遍历很多对象，每个对象的所有字段都要用"。前者用 SoA，后者用 AoS。数据库的列存 vs 行存是同一个道理。

其他几个立刻能用的技巧

用连续容器
优先 vector / array，别用 list / 链表。链表每次 next 都是一次潜在的 cache miss（指针追逐），遍历 100 万个节点可能是数组的 10 倍慢
小对象用值语义
指针多一层间接就多一次访存。热点路径上的小结构体（< 64 字节）直接按值传递，别用 shared_ptr 包一层
预取
硬件预取器能识别固定步长。实在不行用 __builtin_prefetch(p, 0, 3) 手动提示，但要提前 100~200 周期，太早太晚都没用
避免热字段混排
结构体里"每个线程都会写"的字段，和"只读"的字段分开。参考内核的 ____cacheline_aligned_in_smp
模块 8

怎么观测

没有测量就没有优化。这一节给的是判断路径：先分清是"算得多"还是"等得多"，再决定往哪优化。

第一步：perf stat 拿基础指标

# 最常用的一组
perf stat -e cycles,instructions,cache-references,cache-misses,branch-misses ./app

# 输出示例（数字是编的，看结构）
    12,000,000,000  cycles
    30,000,000,000  instructions     # IPC = 2.5
     2,000,000,000  cache-references
       100,000,000  cache-misses     # 缺失率 5%
       400,000,000  branch-misses

# 更细的：-d 会展开到 L1/L2/L3/LLC 各级
perf stat -d ./app

# 看停顿在哪（最有用的一组）
perf stat -e stalled-cycles-frontend,stalled-cycles-backend ./app
# frontend stall：取指/译码跟不上（分支预测失败、指令缓存缺失、代码太大）
# backend stall ：执行单元等操作数（cache miss、除法、依赖链）

第二步：从指标判断瓶颈类型

现象IPCcache-misses结论与下一步
计算密集> 2.5低（< 1%）已经很快了。想更快只能上 SIMD、多线程，或者换算法
访存密集< 1.0高（> 5%）backend stall 高。改数据布局、加缓存、分块、减少指针追逐
分支密集1.0~2.0低frontend stall 高、branch-misses 占比高。消除不可预测分支、查表替代
锁竞争低可能不高CPU 利用率高但吞吐低。用 perf c2c 或 perf lock 看争抢
系统调用多低低用 perf trace 或 strace -c 看 syscall 次数
IPC 要跟自己的基线比，不要跟别人的数字比。同一个程序在不同 CPU 上的 IPC 本来就不一样（宽度、缓存、频率都不同）。有意义的比较是：改动前 vs 改动后，同一台机器，同样的输入。

第三步：定位到具体函数和代码行

# 采样，看热点函数
perf record -g ./app
perf report

# 直接看汇编级的热点（哪个指令在等）
perf record -e cycles:pp ./app
perf annotate

# 只看 cache miss 发生在哪
perf record -e cache-misses:pp ./app
perf report

# 伪共享专项
perf c2c record -a -- sleep 10
perf c2c report

# 锁竞争专项
perf lock record ./app
perf lock report

第四步：确认缓存行与拓扑

getconf LEVEL1_DCACHE_LINESIZE缓存行字节数，x86 恒为 64
lscpu | grep -i cacheL1d/L1i/L2/L3 的容量与关联度
cat /sys/devices/system/cpu/cpu0/cache/index*/size逐级缓存大小，脚本里更好解析
numactl --hardwareNUMA 节点、每节点内存、节点间距离
numastat -p <pid>进程的内存分布在各 NUMA 节点的比例
taskset -c 0-3 ./app绑核，减少跨核迁移导致的缓存失效
perf stat -e cache-misses,LLC-load-misses ./app区分 L1/L2 缺失和最后一级缺失
perf bench mem memcpy测本机内存带宽基线，判断是否已打满
一个高频误判：看到 cache-misses 绝对值大就认为有问题。
绝对值大不代表有问题 —— 一个跑 10 分钟的服务当然会有几亿次 miss。要看的是"缺失率"和"每次缺失的代价占比"。正确做法：cache-misses / cache-references 得到缺失率，再结合 IPC 判断它有没有真的拖慢程序。
另一个误判：用 wall clock 测微基准，却没做 warm-up。第一次跑必然全是 cold miss，测出来的数字没有意义。至少跑 3 次取后两次。
常见坑

十个踩过的坑

1
以为缓存行是 32 字节
x86 从 Pentium 4 起就是 64 字节，ARM 主流也是 64（部分 Apple 芯片的 L1 是 128 字节）。按 32 算 padding 会导致仍然伪共享，或者浪费一倍内存。用 getconf LEVEL1_DCACHE_LINESIZE 确认。
2
多线程计数器放在同一个结构体里
这是伪共享的教科书案例。每个线程高频写的计数器，必须各自对齐到独立缓存行，或者干脆用 ThreadLocal 本地累加、最后汇总。
3
把 volatile 当同步原语用
C/C++ 的 volatile 不保证原子性、不保证顺序，只保证不被优化掉。Java 的 volatile 有内存序语义，但 i++ 依然不是原子操作。要同步就用锁或 atomic。
4
认为"x86 不会重排，所以不用管内存序"
x86 允许 Store→Load 重排（store buffer 造成），而且编译器重排跟架构无关。在 x86 上测通的代码搬到 ARM 服务器上可能直接出错。
5
列优先遍历大矩阵
C/C++ 是行优先存储。按列遍历时每次跨一整行，缓存行利用率只有 1/16，还可能每次触发 TLB miss。实测慢 5~10 倍。
6
AoS 布局却只遍历一个字段
比如 struct {x,y,z,mass} 数组只更新 x，带宽利用率 25%。改成 SoA 或拆成独立数组，通常能快 2~4 倍，还能被自动向量化。
7
热点路径上用链表 / 树 / 哈希表做指针追逐
每次 node = node->next 都可能是一次 cache miss，而且无法预取（地址依赖）。100 万节点的链表遍历可能是数组的 10 倍慢。能用数组就用数组。
8
二维数组维度取 2 的幂
4096×4096 的数组，按列访问时步长 16 KB，所有访问都映射到同一组缓存，产生冲突缺失。把维度改成 [N][N+1] 破坏对齐，可能直接快一倍。
9
在容器 / 云主机上跑 perf 得出错误结论
vCPU 是超线程出来的逻辑核，两个 vCPU 共享 L1/L2；PMU 常常不透传，cache-misses 读数不可信；lscpu 看到的是宿主机全部 CPU。性能结论必须在目标规格的机器上验证。
10
盲目加 padding 导致内存暴涨
把 100 万个 16 字节的结构体全部 pad 到 64 字节，内存直接涨 4 倍，反而把原本能进 L3 的数据挤出去了。padding 只该用在"被多线程高频写"的少数热点字段上。
自测

六道题

1. 两个线程分别自增结构体里相邻的两个 long 字段，程序比单线程还慢。最可能的原因是？
正确答案：伪共享。两个 long 占 16 字节，必然在同一个 64 字节缓存行里。每次写都要让对方核的副本失效并等 ACK，形成缓存行乒乓。修法是 padding 到 64 字节对齐，或用 @Contended / ThreadLocal 累加。
2. L1 命中时间 1 ns，L1 缺失率 5%，内存延迟 100 ns，没有 L2。平均访问延迟约是？
正确答案：6 ns。AMAT = 1 + 0.05 × 100 = 6 ns。如果中间加一级 L2（4 ns 延迟、80% 命中），AMAT = 1 + 0.05 × (4 + 0.2 × 100) = 2.2 ns。注意缺失率从 5% 降到 1% 时，AMAT 从 6 ns 降到 2 ns —— 收益来自缺失率，不是命中率。
3. 关于 x86 的内存序（TSO），哪个说法正确？
正确答案：只允许 Store→Load 重排。原因是 store buffer：写操作进缓冲后指令立即返回，后续的 load 可以先执行。这也意味着在 x86 上写无锁代码"看起来"很容易，但搬到 ARM（弱内存序，四种重排都允许）上就会出问题。
4. perf stat 显示 IPC = 0.4，cache-misses 占 cache-references 的 12%。下一步最该做什么？
正确答案：优化数据布局。IPC 0.4 说明大部分周期在等，缺失率 12% 说明等的是内存。加线程只会让多个核一起等内存，带宽反而更紧张；换 CPU 提升不到 20%。这类问题的数量级收益只能来自"少访问内存"。
5. 4096×4096 的 int 二维数组，按列遍历比按行遍历慢很多，根本原因是？
正确答案：空间局部性被破坏。C 是行优先存储，a[i][j] 按列走时地址步长是 16 KB。每次只用一个 int 却拉了整行 64 字节（利用率 6.25%），而且 16 KB 的步长会让大量访问映射到同一缓存组。
6. 双重检查锁（DCL）单例，为什么实例字段必须加 volatile（Java）？
正确答案：防止半初始化对象逸出。instance = new Singleton() 实际是三步：分配内存、调用构造、赋值引用。没有 volatile 时，赋值引用可能被重排到构造之前，另一个线程在第一次判空时就会拿到一个字段全是默认值的对象。volatile 的 release 语义禁止这个重排。

公式

# 平均内存访问时间
AMAT = T_L1 + (1 - H_L1) × [ T_L2 + (1 - H_L2) × T_mem ]

# IPC 与加速比
IPC = instructions / cycles
加速比 = (IPC_new × f_new) / (IPC_old × f_old)

# 预测失败的影响
额外周期 = 分支数 × 失败率 × 惩罚周期   # 惩罚约 15~20 周期

# 有效带宽（考虑缓存行浪费）
有效带宽 = 实际带宽 × (有用字节 / 缓存行字节)

# 伪共享的通信成本
每次写 ≈ 一次跨核缓存行所有权转移 ≈ 40~200 周期
