网络知识如果按教科书顺序学，会变成一堆需要背的名词。但如果按"线上出了问题怎么定位"的顺序学，每个知识点都自然挂在一条排查链路上。这份文档按后者的组织方式。

先建立排查的"层次感"

任何网络问题，先问一句：问题出在哪一层？下面这张表就是整份文档的骨架，后面每个模块都在填充它。

模块 1

分层模型与数据封装

分层的本质是"每一层只解决一个问题，并给上层提供一个抽象"。排查时它的价值在于：你可以按层逐级确认"问题出在哪一层"，而不是一上来就乱猜。

OSI 七层 vs TCP/IP 四层

OSI 七层TCP/IP 四层这一层加什么头对应协议 / 设备
应用层应用层HTTP 头、DNS 报文HTTP、DNS、SSH、gRPC
表示层（加密、压缩、编码）TLS、字符编码
会话层（连接管理）——（实际很少独立实现）
传输层传输层TCP 头 / UDP 头（含端口号）TCP、UDP、QUIC
网络层网络层IP 头（含源/目的 IP）IP、ICMP、路由器
数据链路层网络接口层以太网帧头（含 MAC 地址）以太网、ARP、交换机
物理层（电信号 / 光信号）网线、光纤、网卡
实践上只看四层就够了。OSI 七层是理论模型，真实协议栈是 TCP/IP 四层。排查时记住一个口诀：MAC 管"同一网段内谁收"，IP 管"跨网段送到哪台机"，端口管"送到这台机的哪个进程"。

数据封装：抓包看到的是什么

发送数据时，每往下走一层就加一个头（封装）；接收时每往上一层就剥掉一个头（解封装）。所以你在 tcpdump 里看到的"一个包"，是层层套娃的结果：

# 一个 HTTP GET 请求发出去时的完整封装
[ 以太网帧头(14B) ][ IP 头(20B) ][ TCP 头(20B) ][ HTTP 数据 ][ 帧尾(4B) ]

以太网帧头：目的 MAC + 源 MAC + 类型
IP 头：     源 IP + 目的 IP + TTL + 协议号 + 总长度
TCP 头：    源端口 + 目的端口 + 序号 + 确认号 + 标志位( SYN/ACK/FIN... )
HTTP 数据： GET /index.html HTTP/1.1 ...

# tcpdump 看到的输出（-nn 表示不解析成域名和服务名）
IP 10.0.0.1.54321 > 10.0.0.2.80: Flags [S], seq 1000, win 64240
    ↑源IP.源端口      ↑目的IP.目的端口  ↑S 表示 SYN 包

# 这就是为什么排查要"分层看"：同一个包，你能从不同层提取不同信息

MTU 与分片

MTU（Maximum Transmission Unit，最大传输单元）是链路层一次能传输的最大数据量，以太网默认 1500 字节。IP 包如果超过 MTU，就要被"分片"。

概念说明
MTU链路层单帧能承载的最大数据（含 IP 头 + TCP 头 + 数据）。以太网 1500
MSSMaximum Segment Size，TCP 单段能承载的数据部分。MSS = MTU - IP头(20) - TCP头(20) = 1460
PMTUD路径 MTU 发现。发大包时设置 DF（Don't Fragment）位，若中间链路 MTU 小则回 ICMP "需分片"消息，发送方据此调小
分片IP 层把大包切成多个小包。任一分片丢失，整个包都要重传，效率低。所以现代协议尽量靠 PMTUD 避免分片
线上最隐蔽的 MTU 坑：某些链路（VPN、隧道、PPPoE）的 MTU 小于 1500。小包（如 ping、握手）能通，但大包（如带大 JSON 的 POST、TLS 握手后的数据）会被静默丢弃，表现为"能连上但传大数据就卡死"。更糟的是，如果中间设备把 ICMP "需分片"消息也丢了，PMTUD 就失效（叫 "PMTU 黑洞"）。
排查方法：ping -M do -s 1472 目标IP（1472 = 1500 - 28），逐步减小 -s 的值，找到能通的临界值，就能算出实际路径 MTU。
模块 2

TCP 三次握手与四次挥手

这两个流程是面试必问，也是排查必懂。重点不是背过程，而是理解为什么是这个次数，以及TIME_WAIT / CLOSE_WAIT 大量堆积分别说明什么。

三次握手

# 客户端 Client          服务端 Server
     ──── SYN seq=x ──────────→       ① 我想建连，我的初始序号是 x
     ←─── SYN seq=y, ACK x+1 ────     ② 收到，我的序号是 y，确认你的 x
     ──── ACK y+1 ───────────→       ③ 收到，确认你的 y
     [连接建立，双方进入 ESTABLISHED]

# 用 tcpdump 观察（三次握手的三个包）
IP c.54321 > s.80: Flags [S],  seq 1000
IP s.80 < c.54321: Flags [S.], seq 2000, ack 1001
IP c.54321 > s.80: Flags [.],  ack 2001      # [.] 表示只有 ACK 没有其他标志
为什么是三次，不是两次？两次握手无法确认"客户端的接收能力"。核心问题是：服务端无法区分"这是一个新连接请求"还是"一个延迟到达的旧连接请求"。
设想一个旧 SYN 在网络里延迟很久才到达服务端，服务端以为客户端要建连，回复 SYN-ACK 并分配资源；但客户端根本没想建连，会忽略这个回复。如果是两次握手，服务端已经认为连接建立了，资源被白白占用。三次握手让客户端有最后一次机会说"我不认这个连接"，服务端收到第三个 ACK 才认为连接真正建立，从而过滤掉历史连接。
另一个角度：三次是双方都确认"自己发得出、收得到"的最小次数。双向各需一次"我发了、你收到了"的确认，共需要三次交互。

握手中的关键参数

参数作用
初始序号 ISN每次连接随机生成，防止旧连接的包被误认为新连接的数据
MSS 协商双方在 SYN 包里各自声明自己支持的 MSS，取较小值，避免分片
窗口缩放因子TCP 头里窗口字段只有 16 位（最大 64KB），用缩放因子可放大到 GB 级（高带宽延迟积链路必需）
SACK 选项选择性确认，允许只重传丢失的段，而不是全重传

四次挥手

# 主动关闭方 A          被动关闭方 B
     ──── FIN seq=u ──────────→     ① A 没数据要发了，但还能收
     ←─── ACK u+1 ────────────     ② B 确认。此时 A→B 方向关闭（半关闭）
                                   B 可能还有数据要发，继续发
     ←─── FIN seq=w ───────────     ③ B 也没数据要发了
     ──── ACK w+1 ───────────→     ④ A 确认
     [A 进入 TIME_WAIT，等 2MSL 后彻底关闭]
为什么是四次，不能像握手那样合并成三次？因为 TCP 是全双工的，两个方向要独立关闭。B 收到 A 的 FIN 后，只是知道"A 不再发数据了"，但 B 自己可能还有数据没发完。所以 B 先回一个 ACK（"我知道你要关了"），等自己数据发完再发自己的 FIN。这个"ACK 和 FIN 之间可能有间隔"，就是四次挥手存在的原因 —— 如果 B 恰好也没有数据要发，ACK 和 FIN 可以合并（延迟确认机制），看起来就像三次。这就是"挥手可能是三次"说法的来源。

TIME_WAIT 的作用与 2MSL

主动关闭方发完最后一个 ACK 后，不会立刻关闭，而是进入 TIME_WAIT 状态，等待 2MSL（MSL = Maximum Segment Lifetime，报文最大存活时间，Linux 默认 60 秒，所以 2MSL = 120 秒；内核参数 net.ipv4.tcp_fin_timeout 和 TIME_WAIT 相关）。

TIME_WAIT 存在的两个理由（缺一不可）：
① 保证最后一个 ACK 能到达对方。如果这个 ACK 丢了，B 会重传 FIN。如果 A 已经彻底关闭，收到 B 重传的 FIN 会回一个 RST（复位），B 就会异常。留着 TIME_WAIT，A 还能重新发 ACK。
② 让本次连接的"迷路包"在网络里自然消亡。等 2MSL 后，本次连接的所有包都已过期，不会污染下一个恰好用了相同"四元组"（源IP+源端口+目的IP+目的端口）的新连接。
为什么是 2MSL？因为要覆盖"一个来回"：A 发 ACK 到 B（1 个 MSL），如果 B 没收到会重传 FIN 回来（再 1 个 MSL）。2MSL 足以覆盖最坏情况。

大量 TIME_WAIT 和 CLOSE_WAIT 说明什么

状态谁产生的大量出现说明什么怎么处理
TIME_WAIT主动关闭方本机频繁主动断开短连接（如作为 HTTP 客户端不断请求下游、或短连接高并发服务器）优先改架构：用连接池/长连接复用，减少短连接数。其次才是调 tcp_tw_reuse（复用 TIME_WAIT 连接，仅对客户端出方向有效）
CLOSE_WAIT被动关闭方本机应用收到对方的 FIN 后，没有调用 close() 关闭自己的 socket。这是代码 bug（连接泄漏），不是内核参数问题只能查代码：检查是否所有分支都释放了连接、连接池是否配置正确、异常路径是否遗漏 close
一个必须记死的判断：
TIME_WAIT 多 → 通常是正常现象或架构问题（短连接太多），调参数只是缓解，根本解法是连接复用。
CLOSE_WAIT 多 → 几乎一定是应用 bug。内核已经帮你处理了收到 FIN 这件事（状态转成 CLOSE_WAIT 等你调 close），但你的代码没关连接。调内核参数完全没用，只会掩盖问题，直到文件描述符耗尽。
这就是那条经典建议的由来："看到大量 CLOSE_WAIT 别急着调参数，先去看代码。" 
# 快速统计各状态连接数（排查第一步）
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn

# 看谁在产生大量 TIME_WAIT（按对端 IP 聚合）
ss -tan state time-wait | awk 'NR>1{print $4}' | cut -d: -f1 | sort | uniq -c | sort -rn | head

# 看 CLOSE_WAIT 属于哪个进程（-p 需要 root）
ss -tanp state close-wait | head

# 相关内核参数（先理解再调，别抄作业）
net.ipv4.tcp_tw_reuse = 1        # 允许复用 TIME_WAIT 用于出向新连接
net.ipv4.tcp_fin_timeout = 30    # FIN_WAIT2 超时，不是 TIME_WAIT 时长
net.ipv4.ip_local_port_range = 1024 65535   # 扩大本地端口范围
模块 3

TCP 可靠传输

TCP 的"可靠"是靠四件事拼出来的：序号 + 确认、超时重传、快速重传、滑动窗口。理解它们，你才能看懂 netstat -s 里的重传统计。

序号与确认

TCP 把数据看成字节流，每个字节都有一个序号。接收方用 ACK 告诉发送方"我已经收到第 N 字节之前的所有数据"。注意是累积确认：ACK 1001 表示"1000 及之前的都收到了，我期待 1001"。

超时重传与 RTO

发送方每发一段数据就启动一个定时器，超过 RTO（Retransmission Timeout，重传超时时间）还没收到 ACK，就重传。RTO 不是固定的，而是动态计算的：

# RTO 的计算（简化版，RFC 6298）
测量一次 RTT（往返时延）→ 得到 SRTT（平滑 RTT）和 RTTVAR（RTT 偏差）
RTO = SRTT + 4 × RTTVAR

# 关键规则：
1. 每次重传，RTO 指数退避（翻倍）：1s → 2s → 4s → 8s...
   这就是"网络抖一下，恢复要好几秒"的原因
2. RTO 有下限（Linux 默认 200ms）和上限（通常 120s）
3. 用 Karn 算法：重传过的段不用于计算 RTT（因为无法区分 ACK 对应哪次发送）

快速重传

等 RTO 超时太慢了（至少 200ms 起）。TCP 用快速重传加速：如果发送方连续收到 3 个重复 ACK（同一个确认号），就立刻重传，不等超时。

# 快速重传的触发过程（收到 3 个重复 ACK）
发送方发:  seg1  seg2  seg3  seg4  seg5
seg2 丢了，seg3/4/5 都到了

接收方:  收到 seg1 → ACK 2
         收到 seg3 → ACK 2  (重复 ACK，因为缺 seg2)
         收到 seg4 → ACK 2  (重复 ACK 2)
         收到 seg5 → ACK 2  (重复 ACK 3)  ← 第 3 个重复 ACK！
发送方:  收到 3 个重复 ACK → 立刻重传 seg2，不等 RTO

SACK（选择性确认）

没有 SACK 时，接收方只能说"我期待 2"，发送方不知道 3/4/5 已经收到了，可能把 2/3/4/5 全部重传。有了 SACK，接收方可以精确告诉发送方"我收到了 3-5，只缺 2"，发送方只重传真正丢失的段。

为什么现代 TCP 几乎都开 SACK？因为在高带宽、有丢包的链路上，缺了 SACK 会导致大量无谓重传，带宽被浪费。Linux 默认开启（net.ipv4.tcp_sack=1）。

滑动窗口与流量控制

如果每发一段就等一个 ACK，吞吐会低得可怜（等于 RTT 倒数的带宽）。滑动窗口允许连续发送多段而不等 ACK，最多能发多少由接收方通告的"接收窗口"决定。这叫流量控制（防止发太快把接收方缓冲区撑爆）。

机制目的调节依据
流量控制别把接收方缓冲区撑爆接收方通告的接收窗口 rwnd
拥塞控制别把网络（中间链路）撑爆拥塞窗口 cwnd（见模块 4）
实际发送窗口两者取小min(rwnd, cwnd)

糊涂窗口综合征（Silly Window Syndrome）

如果接收方缓冲区只空出几个字节就通告窗口，发送方就发几个字节的小包 —— 为了传 1 字节数据要带 40 字节头，效率极低。这叫糊涂窗口综合征。两种解法：

  • 接收方：窗口小于某阈值（如 MSS 的一半）时，不通告，等缓冲区多空一点再通告。
  • 发送方：用 Nagle 算法，攒够一个 MSS 或等到收到 ACK 才发。代价是增加延迟 —— 这就是为什么对延迟敏感的场景要设 TCP_NODELAY（禁用 Nagle）。
线上现象对应：如果你发现应用有"偶尔多出几十毫秒延迟"，而且包都很小，很可能就是 Nagle 算法 + 延迟确认（delayed ACK）互相等待导致的（发送方等 ACK 才发，接收方等数据才发 ACK）。解法：对延迟敏感的 socket 设 TCP_NODELAY。
模块 4

TCP 拥塞控制

流量控制管的是"接收方能不能收得下"，拥塞控制管的是"网络这条路堵不堵"。TCP 看不到网络的全局状态，只能靠"丢包"和"延迟"这两个信号来推断拥塞，然后调整发送速率。

四个阶段

慢启动（Slow Start）：连接刚建立时不知道网络能承受多少，所以从小开始 —— cwnd 初始 10 个 MSS 左右，每收到一个 ACK 就翻倍（指数增长）。所以"慢启动"其实一点都不慢，是"指数启动"。
拥塞避免（Congestion Avoidance）：cwnd 达到慢启动阈值（ssthresh）后，改为每 RTT 只加 1 个 MSS（线性增长），小心翼翼地逼近上限。
快重传 + 快恢复（Fast Retransmit / Fast Recovery）：收到 3 个重复 ACK 说明"只是个别包丢了，网络没全堵"，于是重传丢失段，并把 cwnd 减半（而不是清零），进入拥塞避免。这是为了不做"从零开始"的过度惩罚。
超时后的处理：如果连重复 ACK 都没有（RTO 超时），说明网络可能真的严重拥塞，cwnd 直接降到 1，重新慢启动。所以"超时"比"快速重传"严重得多。

CUBIC 与 BBR 的区别

算法调节依据特点
CUBIC丢包。把丢包当成拥塞信号，丢包就降速Linux 默认。高带宽长距离链路上，靠丢包判断往往滞后；且无线/公网上的随机丢包会被误判成拥塞，导致无谓降速
BBR带宽和 RTT。主动探测链路的最大带宽和最小 RTT，在此模型下发送Google 提出。不把随机丢包当拥塞，在有丢包的链路上能保持高吞吐、且延迟更低（因为它按最小 RTT 发送，不会把队列填满）
为什么 BBR 在高丢包链路上表现更好？因为 CUBIC 的假设是"丢包 = 拥塞"。但真实链路的丢包有两个来源：① 拥塞导致的队列溢出（该降速）；② 链路本身的随机错误（不该降速）。
CUBIC 无法区分这两种，只要丢包就降速。如果链路有 2% 的固有丢包率，CUBIC 的吞吐会被压得很低。
BBR 则不依赖丢包作为信号，它周期性地探测"发送速率是否还能提高、RTT 是否变大"，据此建立带宽-延迟模型。随机丢包不会让它降速，所以它能跑满带宽。代价是 BBR 对链路公平性有争议（可能抢占 CUBIC 流的带宽），且在新版本（BBRv2）中才引入丢包敏感度。 
# 看和改本机拥塞控制算法
sysctl net.ipv4.tcp_congestion_control          # 查看当前算法
sysctl net.ipv4.tcp_available_congestion_control # 查看可用的
sysctl -w net.ipv4.tcp_congestion_control=bbr    # 切换到 bbr（需内核支持）

# 看每个连接的拥塞窗口和 RTT（ss -i 显示 TCP 内部信息）
ss -ti state established
# 输出里的 cwnd、rtt、retrans 就是排查拥塞的直接依据
模块 5

TCP 与 UDP 的取舍

一句话区别：TCP 是"可靠的字节流"，UDP 是"不可靠的数据报"。但现代协议越来越倾向于"在 UDP 上自己实现需要的可靠性"，因为 TCP 的内置机制在特定场景下反而是负担。

维度TCPUDP
连接面向连接（三次握手）无连接，直接发
可靠性序号、确认、重传、去重、保序不保证送达、不保证顺序
头部开销20 字节（含选项更多）8 字节
传输方式字节流（无消息边界）数据报（保留消息边界）
拥塞控制有（内置）无（要自己在应用层做）
队头阻塞有（一个包丢了，后面的都得等）无（每个包独立）
适用场景Web、文件传输、数据库、需要可靠有序DNS、视频/音频流、游戏、QUIC

QUIC 为什么选 UDP

QUIC 是 Google 提出的传输层协议（现在是 HTTP/3 的底层）。它完全可以基于 TCP 实现，但选择了 UDP，原因是：

  • 绕开中间设备的僵化：互联网上大量中间设备（防火墙、NAT）会检查并"修正"TCP 包。改 TCP 协议几乎无法部署。而 UDP 对中间设备来说是"看不懂的载荷"，可以自由演进。
  • 绕开 TCP 的队头阻塞：TCP 是单条字节流，一个包丢了，后面所有数据都得等重传。QUIC 在 UDP 上实现了多个独立的流，一个流丢包不影响其他流。
  • 可以更快建连：QUIC 把 TLS 握手和传输握手合并，首次连接 1-RTT，重连可以 0-RTT（见模块 7）。
  • 连接迁移：QUIC 用 Connection ID 标识连接，而不是四元组。手机从 WiFi 切到 4G，IP 变了，连接也不用断。
在 UDP 上做可靠性，你需要自己实现什么？① 序号（检测丢包和乱序）；② 确认与重传（哪些要重传、什么时候重传）；③ 拥塞控制（不能无脑发，否则会挤垮网络，这也是为什么"UDP 比 TCP 快"通常是错的 —— 不加拥塞控制的 UDP 只是"更没礼貌"）；④ 有序重组（或者像 QUIC 那样按流独立保证）；⑤ 连接管理（QUIC 用 Connection ID）。这就是"UDP 上的可靠性"的完整清单。
模块 6

DNS 解析全流程

DNS（Domain Name System，把域名翻译成 IP 的系统）是"平时不显眼、出问题就全站不可用"的典型。DNS 慢会导致整体慢，因为它是所有请求的第一跳。

递归查询 vs 迭代查询

应用发起"递归查询"：你的程序问本地 DNS 服务器（通常由运营商或 /etc/resolv.conf 指定）"www.example.com 的 IP 是多少"，并期望得到一个最终答案。
本地 DNS 发起"迭代查询"：如果本地 DNS 没有缓存，它依次问：根域名服务器 → 顶级域（TLD，如 .com）服务器 → 权威域名服务器（管理 example.com 的服务器）。每一步都返回"下一个该问谁"，而不是最终答案。
拿到权威答案后逐级返回，本地 DNS 把结果缓存起来（按 TTL），再返回给应用。
# 完整解析路径（以查 www.example.com 为例）
应用 → 本地 DNS (114.114.114.114)
       ├─ 问根服务器(.)    : "谁管 .com？"
       │  根服务器回: "去问 .com 的 TLD 服务器"
       ├─ 问 .com TLD 服务器: "谁管 example.com？"
       │  TLD 回: "去问 ns1.example.com（权威服务器）"
       └─ 问权威服务器      : "www.example.com 的 IP？"
          权威服务器回: "93.184.216.34"
本地 DNS 缓存该记录（按 TTL）→ 返回给应用

# 用 dig +trace 亲自走一遍这个迭代过程
dig +trace www.example.com

缓存层级与 TTL

缓存位置说明
浏览器缓存Chrome 有自己的 DNS 缓存，Chrome 里可访问 chrome://net-internals/#dns 查看和清除
操作系统缓存如 systemd-resolved、nscd；/etc/hosts 优先级最高
本地 DNS 服务器运营商或自建（如 CoreDNS）。这是缓存的主体，按 TTL 决定缓存多久
TTL一条 DNS 记录能被缓存多久（秒）。TTL 太短 → 解析频繁、延迟高、易被打垮；TTL 太长 → 换 IP 后长时间不生效
TTL 的工程取舍：计划做容灾切换/迁移前，提前把 TTL 调小（如 60 秒），切换完再调回去。否则一个 24 小时的 TTL 意味着你的切换要等一天才全网生效。但别长期把 TTL 设成 0 或 1 —— 那样每次请求都要递归解析，本地 DNS 压力剧增，解析延迟也高。

DNS 劫持与污染

类型原理现象
DNS 劫持运营商或恶意软件篡改本地 DNS 返回结果，把域名指向自己的服务器访问某网站跳到广告页或错误页
DNS 污染在解析路径上伪造响应，抢先返回错误 IP（常见于跨境的 UDP 53 端口干扰）解析到错误 IP、超时
DNS 缓存投毒攻击本地 DNS 服务器，把错误的记录写进它的缓存大量用户被导向错误 IP

缓解手段：① 用 HTTPS 加密 DNS（DoH，DNS over HTTPS）或 DoT（DNS over TLS），让中间人无法篡改；② 用可信的公共 DNS（如 8.8.8.8、1.1.1.1）；③ 关键域名用 DNSSEC 做签名校验。

为什么 DNS 慢会导致整体慢？因为 DNS 解析是所有网络请求的第一跳，且通常在关键路径上同步执行。如果解析要 500ms，那么每一个新连接都要多花 500ms。更糟的是解析失败往往表现为"应用超时"，让人误以为是业务代码慢。
排查方法：用 dig www.example.com +stats 看 Query time；用 curl -w 的 time_namelookup 字段单独看 DNS 耗时（见模块 8）。如果 DNS 耗时占比大，就该考虑加本地 DNS 缓存或改用更快的解析器。
模块 7

从 HTTP/1.1 到 HTTP/3 的传输层演进

这一节的主线只有一个词：队头阻塞（Head-of-Line Blocking，HOL Blocking）。HTTP 的每次演进，都是在解决不同层面的队头阻塞。

队头阻塞在两个层面的区别

层面问题解法
应用层队头阻塞
（HTTP/1.1）		一个 TCP 连接上，请求必须串行：前一个响应没回来，后一个请求不能发（或发了也要等前面的）。浏览器只能开多个连接（通常 6 个）缓解HTTP/2 的多路复用
传输层队头阻塞
（TCP）		TCP 是单条字节流，一个包丢了，后面所有数据（即使属于不同请求）都得等它重传。HTTP/2 的多路复用让这个问题更严重：所有请求挤在一条 TCP 流上，一丢包全部卡住HTTP/3 用 QUIC（基于 UDP），每个流独立重传

三代协议对比

版本传输层关键特性主要问题
HTTP/1.1TCP持久连接（keep-alive）、管道化（几乎没人用）应用层队头阻塞，需开多个连接
HTTP/2TCP多路复用（一个连接上并行多个流）、头部压缩（HPACK）、服务端推送TCP 层队头阻塞；丢包时所有流一起卡
HTTP/3QUIC（UDP）流级独立重传、0-RTT 建连、连接迁移部署复杂（UDP 可能被防火墙拦）；CPU 开销较高

QUIC 的 0-RTT 建连

# 建连往返次数对比（RTT = 往返时延）
HTTP/1.1 + TLS 1.2:  TCP握手(1 RTT) + TLS握手(2 RTT) = 3 RTT 才发出第一个请求
HTTP/2 + TLS 1.3:    TCP握手(1 RTT) + TLS握手(1 RTT) = 2 RTT
QUIC 首次连接:       传输握手 + TLS 合并          = 1 RTT
QUIC 重连(0-RTT):    复用上次的会话票据           = 0 RTT，第一个包就带数据

# 0-RTT 的代价：可重放攻击风险
# 因为 0-RTT 数据在服务器验证身份前就发出了，攻击者可以截获并重放
# 所以 0-RTT 只应用于"幂等的、安全的"请求（如 GET）
# 绝不能用于非幂等操作（如 POST 下单）
一句话总结演进逻辑：HTTP/1.1 用多连接绕开应用层队头阻塞；HTTP/2 用多路复用把连接数降到 1，但把队头阻塞下沉到了 TCP 层；HTTP/3 换到 UDP 上的 QUIC，用多流彻底消除了传输层队头阻塞，顺便把建连缩到 1 RTT 甚至 0 RTT。
模块 8

网络排查实战

排查的核心方法只有一条：按层次逐级确认，直到定位到"哪一层开始不正常"。不要一上来就抓包，先确定问题在哪一层，能省掉 90% 的时间。

按层次排查的标准流程

物理/链路层：ip -br link 看网卡是否 UP；ethtool -S eth0 看有没有 CRC 错误、丢包计数。如果链路层就丢包，上面全白搭。
网络层：ping 目标 看通不通、延迟多少、丢包率；traceroute 看在哪一跳断；ip route get 目标IP 看走哪条路由。注意：ping 通不代表服务可用，ping 不通也不代表服务不可用（可能被防火墙禁 ICMP）。
传输层：telnet 目标 端口 或 nc -zv 目标 端口 测端口是否可连；ss -tan 看连接状态；netstat -s 看重传、丢包统计。
应用层：curl -w 分解耗时；dig 查 DNS；看应用日志和错误码。

curl -w 耗时分解（最实用的单条命令）

# 把一次请求的耗时拆成 6 个阶段，一眼看出慢在哪
curl -w "\n\
DNS解析:  %{time_namelookup}s\n\
TCP连接:  %{time_connect}s\n\
TLS握手:  %{time_appconnect}s\n\
首字节:   %{time_starttransfer}s\n\
总耗时:   %{time_total}s\n\
" -o /dev/null -s https://www.example.com

# 怎么读这几个值（都是相对请求开始的累计时间）：
# time_namelookup  大 → DNS 慢
# time_connect - time_namelookup 大 → TCP 握手慢（网络延迟高）
# time_appconnect - time_connect 大 → TLS 握手慢
# time_starttransfer - time_appconnect 大 → 服务端处理慢（业务慢，不是网络慢）
# time_total - time_starttransfer 大 → 响应体传输慢（带宽问题）
这条命令的价值：它把"接口慢"这个笼统的问题，拆成了"DNS 慢 / 网络慢 / TLS 慢 / 服务端慢 / 传输慢"五个可区分的结论。绝大多数"网络慢"的误判，都是因为没做这个分解，直接归因到网络。

四类典型问题的定位方法

现象可能的根因怎么定位
丢包链路故障、拥塞、网卡错误、防火墙限速ping -c 100 看丢包率；mtr 看哪一跳开始丢；netstat -s 看 TCP 重传

抓包定位（tcpdump 三板斧）

# 1. 抓指定端口的包，-nn 不解析域名端口，-i any 抓所有接口
sudo tcpdump -i any -nn port 8080 -c 100

# 2. 抓包存文件，用 Wireshark 打开分析（线上首选）
sudo tcpdump -i any -nn -s 0 -w /tmp/cap.pcap port 8080
# -s 0 表示抓完整包（不截断），分析时才看得到 payload

# 3. 只看 TCP 标志位，快速判断连接问题
sudo tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'

# 关键：看到 RST 说明连接被拒绝/重置（端口没监听、或被防火墙拦）
#       看到大量重传（同一 seq 重复出现）说明丢包严重
#       看到 SYN 发了但没有 SYN-ACK 回复，说明对端不可达或被拦
抓包时的性能注意：tcpdump 在高流量机器上会消耗 CPU，-s 0 抓全包写盘更是 IO 大户。线上抓包务必：① 加过滤条件（只抓关心的端口/IP）；② 用 -c 限制包数；③ 尽量在流量低谷抓。否则排查问题会变成制造新问题。

常见坑

十个排查误区

1
用 ping 判断服务是否可用
ping 通只说明 IP 层可达，不代表端口有服务在监听；ping 不通也可能只是 ICMP 被防火墙禁了。判断服务要用 nc -zv host port 或直接 curl。
2
看到大量 CLOSE_WAIT 只调内核参数
CLOSE_WAIT 是本机应用收到 FIN 后没调 close()，是代码 bug。调参数毫无用处，只会拖到文件描述符耗尽。必须查代码：连接池、异常路径、finally 是否关闭。
3
以为 TCP 保证实时性
TCP 只保证"可靠有序"，不保证"及时"。它可能因为重传、拥塞控制、Nagle 算法而引入几百毫秒延迟。实时性要求高的场景要么用 UDP，要么设 TCP_NODELAY。
4
忽略 MTU，导致大包丢失
小包通、大包卡是典型 MTU 问题。用 ping -M do -s 1472 找临界值。VPN/隧道场景 MTU 往往小于 1500。
5
DNS 缓存 TTL 设得过长
做容灾切换时，长 TTL 会让切换迟迟不生效。计划切换前先把 TTL 调小（如 60s），切完再调回。
6
TIME_WAIT 多就直接调内核参数
TIME_WAIT 多是"短连接太多"的架构问题，根本解法是连接复用/连接池。调 tcp_tw_reuse 只是缓解，且只对出方向有效。
7
把接口慢一律归因于网络
用 curl -w 分解耗时。如果 time_starttransfer - time_appconnect 很大，是服务端处理慢（业务问题），不是网络问题。
8
线上无过滤条件地抓包
tcpdump 不加过滤、抓全包，会在高流量机器上消耗大量 CPU 和磁盘 IO，把排查变成制造故障。必须加端口/IP 过滤 + -c 限包数。
9
认为 UDP 一定比 TCP 快
不加拥塞控制的 UDP 只是"更没礼貌"，会挤垮网络。QUIC 在 UDP 上实现了完整的拥塞控制。速度差异来自机制，不来自协议名。
10
把 0-RTT 用在非幂等请求上
0-RTT 数据在身份验证前就发出，可被重放。只能用于 GET 等幂等请求，绝不能用于下单、支付。
自测

六道题

1. 为什么 TCP 建连是三次握手而不是两次？
正确答案：两次握手时，服务端收到一个延迟的旧 SYN 会误以为要建连并分配资源，而客户端根本不想建连。第三次 ACK 让客户端有机会拒绝，服务端收到它才确认连接真正建立。同时三次也是"双方都确认自己能发能收"的最小次数。
2. 服务器上出现大量 CLOSE_WAIT 连接，最可能的原因和处理方式是？
正确答案：代码 bug。CLOSE_WAIT 是"本机已收到对端 FIN，但应用还没调用 close()"的状态。内核帮不了你，调参数完全无效，只能查连接是否在所有路径（含异常路径）都被释放。
3. 关于 TIME_WAIT 等待 2MSL 的原因，哪个说法正确？
正确答案：保证最后 ACK 可达 + 让旧包消亡。如果最后 ACK 丢了，对方会重传 FIN，留着 TIME_WAIT 才能重发 ACK；同时 2MSL 足以让本次连接的所有包过期，避免污染使用相同四元组的新连接。
4. 为什么 BBR 在高丢包链路上比 CUBIC 表现更好？
正确答案：CUBIC 的假设是"丢包 = 拥塞"，无法区分拥塞丢包和链路固有随机丢包，有固有丢包的链路上会被压得很低。BBR 主动探测带宽和最小 RTT 建模，随机丢包不会让它降速。
5. HTTP/2 的多路复用解决了队头阻塞，但为什么 HTTP/3 还要换到 QUIC？
正确答案：传输层队头阻塞。HTTP/2 把多个请求复用到一条 TCP 流上，TCP 是单条字节流，一个包丢了后面全部卡住，多路复用反而放大了这个问题。HTTP/3 用 QUIC 的多流做独立重传，彻底消除。
6. 用 curl -w 排查接口慢，发现 time_namelookup 占比很大，说明问题在？
正确答案：DNS 解析慢。time_namelookup 是到"域名解析完成"的累计时间。它大说明卡在 DNS。排查用 dig +stats 看解析耗时，考虑加本地 DNS 缓存或换解析器。

OSI 七层理论分层模型，实际用 TCP/IP 四层
封装数据每下一层加一个头，抓包看到的是层层套娃
MTU链路层单帧最大数据量，以太网 1500 字节
MSSTCP 单段能承载的数据量，= MTU - 40 = 1460
PMTUD路径 MTU 发现，靠 ICMP 反馈调整包大小
三次握手SYN → SYN-ACK → ACK，建立连接并过滤旧连接
四次挥手双向独立关闭，因全双工所以 ACK 和 FIN 常不能合并
TIME_WAIT主动关闭方等待 2MSL，保证 ACK 可达 + 旧包消亡
CLOSE_WAIT被动关闭方收到 FIN 但应用未 close()，通常是代码 bug
RTO重传超时时间，动态计算，重传时指数退避
快速重传收到 3 个重复 ACK 立刻重传，不等超时
SACK选择性确认，只重传真正丢失的段
滑动窗口允许连续发送多段不等 ACK，提升吞吐
流量控制按接收方缓冲区大小调速，防撑爆接收方
拥塞控制按网络拥堵情况调速，防撑爆网络
慢启动连接初期 cwnd 指数增长，探测网络容量
CUBICLinux 默认拥塞控制，以丢包为拥塞信号
BBR基于带宽和 RTT 建模的拥塞控制，抗随机丢包
队头阻塞前面阻塞导致后面全部等待；HTTP/1.1 在应用层，TCP 在传输层
QUIC基于 UDP 的传输协议，多流、1-RTT/0-RTT 建连
多路复用一个连接上并行多个请求流（HTTP/2）
递归/迭代查询递归要最终答案；迭代返回"下一个该问谁"
TTL（DNS）一条记录能被缓存多久，影响切换生效速度
DoH/DoT用 HTTPS/TLS 加密 DNS，防劫持和污染
