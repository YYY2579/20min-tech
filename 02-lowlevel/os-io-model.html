模块 1

进程与线程

一句话区分：进程是资源分配的基本单位，线程是 CPU 调度的基本单位。

维度进程 Process线程 Thread
资源拥有独立的地址空间、文件描述符表、信号处理共享所属进程的地址空间和资源，只有栈、寄存器、程序计数器是私有的
隔离性强，一个进程崩溃通常不影响其他进程弱，一个线程段错误会拖垮整个进程
创建/切换成本高（要建地址空间、页表）低（共享地址空间，但仍有内核态切换成本）
通信需要 IPC（管道、共享内存、socket）直接读写共享内存（但要加锁）

1.1 上下文切换的成本到底花在哪

上下文切换（Context Switch）是指 CPU 从一个执行流切换到另一个。它不是"免费地换个人干活"，成本分布在四块：

成本来源说明
保存/恢复寄存器要把当前线程的寄存器、程序计数器、栈指针存进内核栈，再恢复另一个的。这部分本身很小
用户态↔内核态切换切换必须陷入内核，特权级切换有固定开销
TLB 失效这是大头之一。TLB（Translation Lookaside Buffer，地址翻译缓存）缓存了虚拟地址到物理地址的映射；切换到不同进程时地址空间变了，TLB 大量失效，后续访存要重新走多级页表
CPU Cache 污染另一个大头。新线程的代码和数据不在 L1/L2 缓存里，切换后一段时间 CPU 都在等内存，缓存命中率骤降
# 观察上下文切换
vmstat 1
# cs 列 = 每秒上下文切换次数
# in 列 = 每秒中断次数（含时钟中断）
# 如果 cs 上万且 r（运行队列）很长，说明线程太多在互相抢 CPU

pidstat -w 1
# cswch/s = 主动切换（等 IO/锁，自愿让出）
# nvcswch/s = 被动切换（时间片用完被抢占）
实践含义：线程数不是越多越好。如果线程数远超 CPU 核数，且任务是 CPU 密集的，大量时间会花在切换而非计算上（cs 很高但吞吐不涨）。经验值：CPU 密集任务 ≈ 核数；IO 密集任务可适度放大，但更推荐用异步 IO 或协程来避免"一请求一线程"。

1.2 协程：为什么能开几十万个

协程（Coroutine）是用户态的轻量级执行单元，由程序自己的调度器（而非内核）来切换。它和线程的根本区别在于：切换发生在用户态，不需要陷入内核。

特性线程协程
调度方内核调度器，抢占式用户态调度器，协作式（在 await/yield 处主动让出）
切换成本高（内核态切换 + TLB + cache）极低（只切换少量寄存器和栈，不陷内核）
栈大小通常 1~8MB（固定预留）几 KB 起（可增长），所以能开几十万
数量级数千已吃力几十万到百万
关键推论：一个协程的内存占用是 KB 级，而线程是 MB 级 —— 这就是"协程能开几十万"的直接原因。但要注意：协程只解决"并发连接的调度成本"，不解决"CPU 计算"。如果你的任务是 CPU 密集的，开再多协程也没用（它们还是要在有限的核上排队），甚至需要把阻塞的 CPU 任务丢到线程池里执行，避免阻塞整个事件循环。
三者适用场景：① 多进程：需要强隔离（如浏览器多标签、PHP-FPM 的 worker），或想绕开 GIL/全局锁；② 多线程：IO 密集且要共享内存、代码简单（传统 Java/Tomcat 模型）；③ 协程：海量并发连接、IO 密集（Go 的 goroutine、Python asyncio、Node.js）。
模块 2

内存管理

"free 内存只剩 500MB 了，是不是要 OOM？" —— 这是最常见的误判。要理解它，得先理解虚拟内存和 Page Cache。

2.1 虚拟内存：隔离与超配

虚拟内存（Virtual Memory）给每个进程一个"看起来独占整块内存"的假象，由 MMU（Memory Management Unit，内存管理单元）在硬件层面把虚拟地址翻译成物理地址。它带来两个核心能力：

能力说明
隔离进程 A 无法直接访问进程 B 的物理内存，一个进程越界也不会破坏别人。这是安全与稳定的基础
超配 Overcommit进程申请的虚拟内存总和可以超过物理内存。因为程序"申请了"不代表"立刻用到"，真正用到时才分配物理页

2.2 页表、多级页表与缺页中断

# 地址翻译链路
虚拟地址 → 查页表（多级）→ 物理页框号 → 加上页内偏移 → 物理地址
# 页表本身很大，所以用"多级页表"分级存储：只给真正用到的区域建页表
# 但多级页表意味着一次访存要多次读内存 → 用 TLB 缓存最近用过的映射

# 缺页中断（Page Fault）
# 访问的页不在物理内存里 → 触发缺页中断 → 内核负责把页从磁盘/swap 调入
# 主缺页（major fault）：要从磁盘读，慢
# 次缺页（minor fault）：只需分配物理页，快
为什么 swap（交换分区）会让性能急剧下降？因为 swap 把"内存"降级成了"磁盘"。一旦发生 swap 换入换出，每次缺页都要走磁盘 IO，而磁盘比内存慢好几个数量级。更糟的是可能引发抖动（thrashing）：进程频繁缺页→频繁换页→CPU 全花在换页上→真正有用的计算几乎停滞。
实践建议：对延迟敏感的服务（数据库、Redis、消息队列），宁可 OOM 也不要 swap，通常把 vm.swappiness 调到很低（如 1）。观察指标：vmstat 的 si/so（swap 换入/换出）持续非零就是危险信号。

2.3 Page Cache：为什么 free 内存少是正常的

Page Cache（页缓存）是内核用空闲内存缓存磁盘文件内容的机制。你读文件时，内核顺便把它缓存下来，下次读就命中内存。写文件时，数据先写到 Page Cache 就返回，由内核择机刷盘。

# free -h 的输出要这么读
              total   used   free   shared  buff/cache   available
Mem:           15Gi   3.2Gi  0.8Gi   0.1Gi       11Gi        11Gi
# free 很小 = 内存没浪费，被拿来当缓存了（好事）
# buff/cache = 块设备缓存 + 文件页缓存
# 真正该看的是 available：估算"还能给新程序用多少"，它已经把可回收的 cache 算进去了
# 只要 available 充足，free 再小也不会 OOM

# 手动释放缓存（一般不要做，缓存本来就是用来加速的）
echo 3 > /proc/sys/vm/drop_caches   # 3 = 释放 pagecache + dentries + inodes
必须纠正的认知：① "free 内存少 = 内存不足"是错的。Linux 的设计哲学是"空闲内存就是浪费"，所以会积极把内存用作 Page Cache，需要时再回收。② 判断内存压力看 available 和 si/so，不要看 free。③ Page Cache 是"可回收"的，但不等于"无代价" —— 回收干净页（未修改）几乎无成本，回收脏页（已修改未落盘）需要先写盘，会造成 IO 抖动。
模块 3

五种 IO 模型

理解 IO 模型的关键，是把一次 IO 拆成两个阶段：① 等待数据就绪（数据从网络/磁盘到达内核缓冲区）；② 把数据从内核缓冲区拷贝到用户缓冲区。五种模型的区别，就在于这两个阶段分别"阻塞在哪里"。

模型阶段一：等待数据阶段二：拷贝数据
阻塞 IO
Blocking		阻塞，一直等到数据就绪阻塞
非阻塞 IO
Non-blocking		不阻塞，立即返回；没数据就轮询重试阻塞
IO 多路复用
Multiplexing		阻塞在 select/poll/epoll 上，同时等多个 fd阻塞
信号驱动 IO
Signal-driven		不阻塞，数据就绪时内核发信号通知阻塞
异步 IO
AIO		不阻塞不阻塞，内核全程处理完再通知

3.1 逐个讲清"阻塞在哪"

# ========== 1) 阻塞 IO ==========
read(fd, buf, n)   # 一直卡住，直到数据到达并拷进 buf 才返回
# 最简单，但"一个连接一个线程"，连接多了线程爆炸

# ========== 2) 非阻塞 IO ==========
while(read(fd, buf, n) == EAGAIN) { /* 没数据，立刻返回，继续轮询 */ }
# 不阻塞在 read 上，但要用户态不停轮询 → CPU 空转，浪费严重

# ========== 3) IO 多路复用 ==========
n = epoll_wait(epfd, events, maxevents, timeout)  # 阻塞在这里
# 一个线程同时等多个 fd；哪些就绪了返回哪些，再对有数据的 fd 调 read
# 这是现代高并发服务器的核心（Redis/Nginx/Netty 都基于它）

# ========== 4) 信号驱动 IO ==========
sigaction(SIGIO, handler)   # 注册信号处理函数
# 数据就绪时内核发 SIGIO，用户态再去 read（read 时仍阻塞在拷贝阶段）
# 实际很少用，信号处理复杂且易出错

# ========== 5) 异步 IO ==========
aio_read(aiocb)   # 立即返回，内核把"等数据 + 拷数据"全做完再回调通知
# 两个阶段都不阻塞，这才是真正的异步
为什么说前四种本质上都是同步 IO？因为它们在"拷贝数据"这个阶段都是阻塞的。真正的分界线是阶段二：只有异步 IO（POSIX AIO、Linux 的 io_uring）做到了"连拷贝都不需要用户参与"。
常被搞混的一点：IO 多路复用常被误叫"异步"，其实它是"同步非阻塞"的升级版 —— 它只是让你能同时等多个 fd，拿到就绪通知后，read 拷贝数据那一步照样阻塞。Go 的 goroutine / Node.js 的 event loop 之所以"看起来异步"，是因为运行时把"阻塞的 read"藏进了自己的调度器里，用 epoll + 非阻塞 fd 模拟出了异步的编程体验。
模块 4

select / poll / epoll 的区别

这三个都是 IO 多路复用的具体实现。演进的主线只有一个：如何在高并发下把"找就绪 fd"的复杂度从 O(n) 降到 O(1)。

机制数据结构最大连接数查找就绪 fd 的复杂度
select位图（bitmap）FD_SETSIZE，通常 1024O(n)，每次要遍历全部 fd；且每次调用都要把 fd 集合从用户态拷到内核态
poll链表（pollfd 数组）无硬上限（受内存限制）O(n)，仍要遍历；但去掉了 1024 限制
epoll红黑树 + 就绪链表无硬上限O(1)，内核只返回就绪的 fd，无需遍历全部

4.1 epoll 为什么是 O(1)

# epoll 的三个系统调用
epfd = epoll_create(1)                     # 创建 epoll 实例（内核里一棵红黑树 + 一个就绪链表）
epoll_ctl(epfd, EPOLL_CTL_ADD, fd, event)  # 把 fd 注册进红黑树，只做一次（不像 select 每次都重传）
epoll_wait(epfd, events, max, timeout)     # 直接返回就绪链表里的 fd，O(1)

# 关键机制：
# 1) 红黑树：存所有被监听的 fd，增删改是 O(log n)，注册一次即可
# 2) 就绪链表：当某个 fd 有事件，内核通过回调把它挂到就绪链表
#    epoll_wait 只需要看这个链表有没有内容，不用遍历所有 fd
# 3) 事件回调：fd 就绪时由内核主动回调，而不是用户轮询

4.2 水平触发 LT 与边缘触发 ET

模式触发条件编程复杂度
LT
水平触发		只要 fd 上还有数据可读，每次 epoll_wait 都会通知低。可以一次没读完，下次还会提醒你。默认模式，不易出错
ET
边缘触发		只在状态变化时通知一次（从无数据变为有数据），之后不再重复通知高。必须一次性把数据读完（循环 read 到返回 EAGAIN），否则会丢事件
# ET 模式下必须循环读到 EAGAIN，否则残留数据不再触发通知
while (1) {
    n = read(fd, buf, sizeof(buf));
    if (n == -1) {
        if (errno == EAGAIN || errno == EWOULDBLOCK) break;  // 读干净了，退出
        else { /* 真错误 */ break; }
    } else if (n == 0) { /* 对端关闭 */ break; }
    // 处理 buf 中的数据
}
# 且 fd 必须设为非阻塞，否则最后一次 read 会卡住整个线程
LT vs ET 怎么选：① LT 更安全、更好写，缺点是就绪事件可能被重复通知（有轻微开销）。② ET 性能略高（减少了不必要的通知），但要求严格按"循环读到 EAGAIN + 非阻塞 fd"来写，写错了会静默丢数据、表现为"连接卡住"。Nginx 默认用 ET，Redis 用 LT —— 这不是谁对谁错，而是各自权衡了实现复杂度和性能。
为什么 Redis 和 Nginx 都基于 epoll？因为它们都是单线程（或少线程）事件驱动模型：一个线程要同时管理成千上万个连接。select 的 1024 上限和 O(n) 遍历在这种量级下直接崩掉；而 epoll 的 O(1) 就绪返回 + 无上限连接数，正好匹配"高并发、低单次计算量"的场景。反过来，如果是少量连接 + 每次处理大量计算的场景，epoll 的优势就没那么明显了。
模块 5

零拷贝

零拷贝（Zero-Copy）要解决的是"数据在内存里被反复搬运"的问题。典型场景是"把文件内容发到网络"（如静态文件服务、消息队列投递）。

5.1 传统 read + write 的开销

# 传统方式：read(file_fd, buf, n) + write(sock_fd, buf, n)
# 数据路径：磁盘 → 内核缓冲区 → 用户缓冲区 → socket 缓冲区 → 网卡

# 一共 4 次数据拷贝：
#   1) DMA 拷贝：磁盘 → 内核页缓存（Page Cache）
#   2) CPU 拷贝：内核页缓存 → 用户缓冲区（read 的返回值）
#   3) CPU 拷贝：用户缓冲区 → socket 发送缓冲区（write）
#   4) DMA 拷贝：socket 缓冲区 → 网卡

# 外加 4 次用户态↔内核态的上下文切换（read 进+出、write 进+出）

5.2 三种减少拷贝的手段

方案做法减少的拷贝
sendfile数据不经过用户态，内核直接从页缓存送到 socket 缓冲区省掉 2 次 CPU 拷贝（内核→用户、用户→内核），只留 2 次 DMA；上下文切换减到 2 次
mmap + write把文件映射到用户地址空间，write 时内核直接从映射区取数据省掉"内核→用户"的拷贝，但仍有"用户→socket"的拷贝；且 mmap 有缺页开销
splice在两个 fd 之间用管道直接搬数据，完全不经过用户态可做到真正的零 CPU 拷贝（配合硬件支持），适合代理/转发场景
# sendfile：把文件内容直接发给 socket（不经过用户态）
sendfile(sock_fd, file_fd, NULL, count);

# 带 DMA gather 的 sendfile（Linux 2.4+）：连"拷贝到 socket 缓冲区"都能省掉
# 只把"数据位置 + 长度"的元信息交给网卡，由网卡直接 DMA 读取页缓存

# splice：在两个 fd 之间搬数据，必须有一个是管道
splice(file_fd, NULL, pipe_fd, NULL, len, SPLICE_F_MOVE);
splice(pipe_fd, NULL, sock_fd, NULL, len, SPLICE_F_MOVE);
谁在受益：① Nginx 的静态文件服务默认用 sendfile（配置项 sendfile on），大文件传输时 CPU 占用和内存带宽明显下降。② Kafka 用零拷贝把日志文件投递给消费者：消息在磁盘上是顺序存储的，消费时直接 sendfile 到 socket，避免了"读到用户态再写出去"的双重拷贝 —— 这是 Kafka 高吞吐的关键之一。③ 各类反向代理、CDN 边缘节点。注意：零拷贝的前提是"数据不需要在用户态被加工"，一旦你要修改内容（压缩、加密），就绕不开用户态，零拷贝就失效了。
模块 6

文件系统与持久化

"文件写成功了，为什么断电后数据没了？" —— 因为你把"写进了 Page Cache"当成了"写进了磁盘"。

6.1 inode 与数据块

# 文件系统的两块核心元数据
# inode：存文件的元信息（权限、大小、时间戳、指向数据块的指针），但不存文件名
# 目录项（dentry）：存"文件名 → inode 号"的映射
# 数据块（block）：真正存文件内容
# 所以：文件名和文件内容是分开存的；硬链接就是多个文件名指向同一个 inode

stat file.txt          # 看 inode 号、块数、时间戳
df -i                  # 看 inode 是否用尽（inode 用尽时，即使还有空间也建不了新文件）

6.2 日志式文件系统与一致性

日志式文件系统（Journaling FS，如 ext4、XFS）在真正修改数据前，先把"要做的操作"写进一个日志区（journal）。这样如果写数据过程中断电，重启后可以根据日志重放或回滚，保证文件系统元数据不处于"改了一半"的损坏状态。

重要区分：日志式文件系统保证的是文件系统结构的一致性（不会出现"目录指向一个不存在的 inode"这种损坏），不保证你的文件内容不丢。要保证内容落盘，必须显式调用 fsync()。这也是数据库为什么要自己管理刷盘策略的原因 —— 数据库需要精确控制"哪些写、什么时候真正落盘"，才能满足自己的持久化保证（如 WAL 预写日志）。

6.3 fsync 的成本，以及 write 成功 ≠ 落盘

# write() 只是把数据写进 Page Cache（内存），立即返回成功
write(fd, buf, n);     # 返回成功 ≠ 数据到了磁盘
# 内核会择机（脏页达到阈值、或定时）异步刷盘

# fsync() 才强制把该文件的数据+元数据刷到磁盘（会阻塞等待磁盘确认）
fsync(fd);
# fdatasync() 只刷数据，不刷非必要元数据，稍快

# 代价：fsync 要等磁盘真正落盘，单次可能几毫秒到几十毫秒
# 机械盘上频繁 fsync 是性能杀手；SSD 好很多但仍有成本

# 关键配置：脏页刷盘阈值
sysctl vm.dirty_ratio          # 脏页占总内存比例上限，超过则同步刷盘（会卡住写入）
sysctl vm.dirty_background_ratio  # 超过则后台异步刷盘
三个必须记住的结论：
① write() 返回成功只代表数据进了内存，断电就丢。要落盘必须 fsync()。
② 数据库的"每事务 fsync"和"批量 fsync"是吞吐与安全的权衡。PostgreSQL 的 synchronous_commit=off、MySQL 的 innodb_flush_log_at_trx_commit=2 都是"放弃极端安全换吞吐"的选项，代价是崩溃时可能丢最近若干秒的数据。
③ O_DIRECT 绕过 Page Cache：数据库常用它避免"双重缓存"（自己管缓存 + 内核又缓存一遍），让刷盘时机完全可控。

锁与并发

锁的本质是"用性能换正确性"。选错锁类型，轻则吞吐低，重则死锁。

锁类型机制适用场景
互斥锁
Mutex		拿不到锁就让出 CPU，进入睡眠等待被唤醒临界区较长、竞争不激烈。避免 CPU 空转
自旋锁
Spinlock		拿不到锁就忙等（循环重试），不让出 CPU临界区极短、竞争少。省去睡眠/唤醒的切换成本，但长时间自旋会浪费 CPU
读写锁
RWLock		读读共享、读写互斥、写写互斥读多写少。提升读并发，但写饥饿风险

7.1 乐观锁与悲观锁

策略假设实现
悲观锁假设冲突总会发生，先加锁再操作数据库的 SELECT ... FOR UPDATE、互斥锁。适合写多、冲突频繁
乐观锁假设冲突很少，先操作，提交时再检查有没有被别人改过版本号 / CAS：更新时校验 version 没变才成功。适合读多写少
# 乐观锁的标准实现（版本号）
# 读：SELECT version FROM t WHERE id=1;   -- 假设拿到 version=5
UPDATE t SET value=?, version=version+1
WHERE id=1 AND version=5;
# 如果影响行数为 0，说明期间被改过 → 重试或报错
# 注意：乐观锁在高冲突下会大量重试，反而更慢

7.2 死锁的四个必要条件与预防

死锁（Deadlock）必须同时满足以下四个条件，破坏任意一个即可预防：

互斥：资源同一时刻只能被一个线程占用。
破坏方式：尽量用无锁结构 / 共享只读数据
持有并等待：拿着一个锁，又去等另一个锁。
破坏方式：一次性申请所有需要的锁，拿不到就全部释放重来
不可剥夺：锁不能被强行抢走。
破坏方式：给锁加超时（tryLock(timeout)），超时释放已持有的锁
循环等待：形成 A 等 B、B 等 A 的环。
破坏方式：全局约定加锁顺序（如永远按 id 从小到大加锁）—— 这是最实用的一招
线上排查死锁：Java 用 jstack <pid> 能直接打印出"Found one Java-level deadlock"和持锁链路；数据库死锁看 InnoDB 的 SHOW ENGINE INNODB STATUS。最实用的预防手段是统一加锁顺序，它几乎零成本，能消除绝大多数循环等待。

模块 8

容器相关的内核机制

"容器是什么？"标准答案是：容器 = namespace（隔离）+ cgroup（限制）+ 镜像（文件系统）。它不是一个新技术，而是把 Linux 已有的内核能力组合起来。

8.1 namespace：实现"看起来独立"

namespace隔离了什么效果
PID进程 ID 空间容器内进程看到自己的 PID 从 1 开始，看不到宿主机其他进程
NET网络设备、IP、端口、路由表容器有独立网卡和 IP、独立的端口空间
MNT挂载点容器有自己的文件系统视图（根目录就是镜像）
UTS主机名和域名容器可以有自己的 hostname
IPC进程间通信（信号量、共享内存）容器间的 IPC 互相隔离
USER用户和用户组 ID容器内 root 可映射成宿主机的普通用户（rootless 容器基础）

8.2 cgroup：实现"用不了太多"

cgroup 子系统限制什么
cpuCPU 使用配额（如 cpu.cfs_quota_us），限制能用多少个核的时间片
memory内存上限（memory.limit_in_bytes），超限触发 OOM Kill
blkio块设备 IO 带宽/IOPS 限制
pids限制容器内最大进程数（防 fork 炸弹）
# 在容器里看限制（cgroup v2 路径）
cat /sys/fs/cgroup/memory.max        # 容器内存上限
cat /sys/fs/cgroup/memory.current    # 当前使用量
cat /sys/fs/cgroup/cpu.max           # CPU 配额

# 关键陷阱：容器里 free / nproc 看到的是"宿主机"的值！
free -h        # ✗ 显示宿主机总内存，不是容器上限
nproc          # ✗ 显示宿主机核数，不是容器 CPU 配额
# 必须读 cgroup 文件（或 /sys/fs/cgroup/...）才准
为什么容器"看起来像虚拟机但其实不是"？
① 共享内核。所有容器共用宿主机的那一个内核。所以"容器内升级内核"是无效的（改的是宿主机），内核漏洞会影响所有容器（逃逸风险）。
② 不是硬件虚拟化。虚拟机有 Hypervisor 模拟完整硬件、跑独立内核；容器只是"进程 + 一组 namespace/cgroup 标签"，本质上就是宿主机上的普通进程。
③ 因此"容器里看到的内存和宿主机不一致"：free 显示宿主机总量（因为读的是宿主机的 /proc/meminfo），但容器实际被 cgroup 限制在更小的值。这就是很多 JVM 应用在容器里被 OOM Kill 的根因 —— JVM 按宿主机内存（或错误的默认值）配置了堆大小，超过了 cgroup 限制，被内核杀掉。
正确做法：① 给容器设明确的 memory limit；② 让 JVM 感知 cgroup 限制（JDK 8u191+/10+ 的 -XX:+UseContainerSupport 已默认开启，会用 cgroup 值而非宿主机值），或显式设 -XX:MaxRAMPercentage=75；③ 容器内存上限要略大于"堆 + 元空间 + 线程栈 + 堆外内存"的总和，留出余量；④ 用 kubectl describe pod 看 OOMKilled 事件确认是否被 cgroup 干掉。
常见坑

十个认知误区

1
以为线程越多吞吐越高
线程数超过核数后，大量时间花在上下文切换（TLB 失效 + cache 污染）而非计算。CPU 密集任务线程数≈核数是更优解。
2
忽略了上下文切换开销
vmstat 的 cs 列持续上万、r 队列很长，说明系统在"忙着切换"而不是"忙着干活"。用 pidstat -w 看是主动切换（等 IO）还是被动切换（被抢占）。
3
把 IO 密集任务用多进程处理
多进程适合隔离和 CPU 并行，但每个进程独立地址空间，海量 IO 连接下进程/线程数会爆炸。IO 密集更适合事件驱动 + epoll 或协程。
4
以为 write 成功就落盘了
write 只写进 Page Cache，断电就丢。要落盘必须 fsync。数据库的刷盘策略就是在"吞吐"和"崩溃时丢多少数据"之间取舍。
5
在容器里按宿主机内存配 JVM 堆
容器里 free 显示的是宿主机内存，JVM 若按它配堆，会超过 cgroup 限制被 OOM Kill。用 UseContainerSupport + MaxRAMPercentage，并留出堆外余量。
6
忽略 cgroup 限制导致被 OOM Kill
容器内存上限 = 堆 + 元空间 + 线程栈 + 直接内存 + 各种缓存。只按堆算上限，运行时一定会被内核杀掉。看 OOMKilled 事件确认。
7
用 LT 模式却按 ET 的思路写代码
LT 模式下没读完下次还会通知；ET 模式下不循环读到 EAGAIN 就会静默丢事件。两种模式的读法完全不同，混用会出"连接卡住"的诡异问题。
8
把 epoll 当成"性能银弹"
epoll 的优势在"大量连接、每次处理量小"。如果每次事件要跑几毫秒的计算，瓶颈在 CPU 而非 IO，换 epoll 也没用，需要的是水平扩展或异步化计算。
9
看到 free 内存少就以为要 OOM
free 小是因为内存被 Page Cache 占满（好事）。判断内存压力要看 available 和 si/so，不是看 free。
10
在延迟敏感服务上开了 swap
swap 会把内存访问降级成磁盘 IO，可能引发抖动（thrashing）导致性能雪崩。数据库/缓存类服务应把 swappiness 调到很低，宁可 OOM 也不要 swap。
自测

六道题

1. 关于进程和线程，哪个说法正确？
正确答案：进程管资源、线程管调度。线程共享所属进程的地址空间和资源，所以一个线程段错误会拖垮整个进程。进程间才需要 IPC。
2. 为什么说 select / poll / epoll 这三种 IO 多路复用"本质上都是同步 IO"？
正确答案：拷贝阶段仍阻塞。一次 IO 分"等数据"和"拷数据"两阶段，多路复用只优化了"等数据"，真正的异步 IO（io_uring/POSIX AIO）才做到拷贝也不阻塞。
3. epoll 相比 select 的核心优势是什么？
正确答案：O(1) 就绪返回。select 有 FD_SETSIZE（通常 1024）限制且每次要遍历全部 fd；epoll 用红黑树存监听的 fd、用就绪链表存已就绪的 fd，epoll_wait 只取就绪链表，无需遍历。
4. 传统 read + write 发文件，数据要经历几次拷贝？
正确答案：4 次拷贝 + 4 次上下文切换。sendfile 能省掉其中 2 次 CPU 拷贝（数据不经过用户态），这也是 Nginx 传大文件、Kafka 投递消息高效的原因。
5. "write() 返回成功"意味着什么？
正确答案：只进了 Page Cache。write 返回只代表数据进了内核内存，断电就丢。必须 fsync 才强制落盘。数据库自己管刷盘策略就是为了控制这一点。
6. 容器里运行 JVM 被 OOM Kill，最可能的原因是？
正确答案：JVM 堆超过 cgroup 限制。容器里 free 显示的是宿主机内存，JVM 若不感知 cgroup，会按宿主机配堆，超过 memory.max 就被 OOM Kill。用 UseContainerSupport + MaxRAMPercentage，并给堆外留余量。
