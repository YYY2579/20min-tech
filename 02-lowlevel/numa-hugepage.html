二十分钟学透 NUMA 与大页内存

这两件事的共同点是：默认配置下都能跑，但都跑不到最好。NUMA 决定你的内存访问要跨多远，大页决定你的地址翻译要几步。搞懂它们，多路服务器上那些"加机器反而更慢"的怪事就有解释了。

开始前

先确认你的机器到底有没有 NUMA

单路家用机通常只有一个节点，这篇的一半内容用不上。先跑三条命令确认。

# 1. 有没有 NUMA、几个节点、节点间距离
numactl --hardware

# 2. 系统层面的大页情况
grep -i huge /proc/meminfo

# 3. 透明大页当前策略
cat /sys/kernel/mm/transparent_hugepage/enabled
# 典型双路服务器的输出
available: 2 nodes (0-1)
node 0 cpus: 0 1 2 3 ... 31 64 65 ... 95
node 0 size: 128000 MB
node 0 free: 118432 MB
node 1 cpus: 32 33 ... 63 96 97 ... 127
node 1 size: 128000 MB
node 1 free: 120911 MB
node distances:
node   0   1
  0:  10  21
  1:  21  10

node distances 这张表是整篇的核心：对角线上的 10 是本地访问，非对角线的 21 是跨节点访问。这个数字是相对值不是纳秒，但比例有意义——21/10 ≈ 2.1，意味着跨节点访存的延迟大约是本地的一倍。

注意 cpus 那两行的编号规律：0-31 和 64-95 属于 node 0，中间跳过了 32-63。这是因为开了超线程，前一半编号是每个物理核的第一个线程，后一半是第二个线程。绑核时如果按 0-31 连续绑，实际绑到的是 32 个物理核——看起来对，但如果绑 0-63，就绑到了 32 个物理核的两个线程，全在 node 0，另一半内存完全没用上。
模块 1

NUMA 是什么：内存不再"等距"

NUMA（Non-Uniform Memory Access，非统一内存访问）：每个 CPU 有自己直连的内存控制器和内存条，访问自己的内存快，访问别人的慢。

为什么会变成这样

早期的多路服务器是 SMP（Symmetric Multiprocessing，对称多处理）架构：所有 CPU 通过一条共享的前端总线（FSB）访问同一个内存控制器。问题是总线是共享资源，CPU 越多，抢得越厉害，加核几乎线性递减。

后来把内存控制器搬进 CPU 内部（Intel 从 Nehalem 开始，AMD 从 Opteron 开始），每个 CPU 管自己那几根内存条，CPU 之间用专用互联（Intel 的 UPI、AMD 的 Infinity Fabric）通信。总线争抢消失了，但代价是内存访问不再等距。

架构内存访问扩展性
UMA / SMP所有 CPU 等距，延迟一致差，4 路以上总线就饱和了
NUMA本地快、远端慢（1.5~2 倍）好，可以做到 2/4/8 路甚至更多
NUMA + 单节点内多 Die同一插槽内也可能有跨 Die 访问AMD EPYC 的 CCD/IOD 结构就是这种

延迟差多少

访问路径典型延迟相对本地
本地节点 DRAM80~100 ns1.0×
跨 1 跳（2 路，直连）130~160 ns1.4~1.8×
跨 2 跳（4 路，经过中转）180~250 ns2.0~2.8×
同插槽跨 Die（EPYC）110~140 ns1.2~1.5×

对比一下：L3 命中约 40~60 个周期（15~25ns），本地 DRAM 约 80~100ns。跨节点的一次访存，够你做完 3~5 次本地访存。在内存密集的负载里，这个差距会直接体现在吞吐上。

不止延迟，还有带宽

跨节点访问走的是 CPU 间互联链路（UPI/xGMI），这条链路的带宽远小于本地内存通道的总带宽。举例：

资源典型带宽说明
单路 8 通道 DDR4-3200约 205 GB/s本地内存带宽
单条 UPI 链路约 10~12 GT/s（双向）实际可用带宽远低于本地内存
双路整机（各 8 通道）约 410 GB/s 理论只有当两个节点各用各的内存时才能接近

所以"跨节点"的代价是延迟和带宽双杀。一个所有线程都去访问 node 0 内存的程序，在双路机器上的表现可能还不如单路——因为多出来的一半内存带宽根本用不上。

这就是"加了机器反而更慢"的经典解释：你把服务从单路 32 核迁到双路 64 核，以为性能翻倍。结果所有线程的堆内存都是在主线程初始化时分配的，全部落在 node 0；node 1 上的 32 个核每次访存都要跨节点。结果是 64 个核抢一个节点的内存带宽，比原来 32 个核还慢。

模块 3

跨 NUMA 访问的代价：为什么多线程会莫名变慢

绝大多数 NUMA 性能问题不是"配置错了"，而是内存分配的位置和访问它的线程不在同一个节点。而这一切的根源，是 Linux 的默认分配策略。

默认策略：first touch（首次触碰）

Linux 默认用 local allocation（本地分配）：哪个 CPU 第一次写某一页，这一页就从那个 CPU 的本地节点分配。注意是"第一次写"，不是 malloc 的时候——malloc 只是拿到虚拟地址，物理页要等到真正访问时才分配（缺页中断）。

这个设计在单线程下完美。多线程下就成了陷阱：

// 典型的有问题的初始化方式
char *buf = malloc(64ULL << 30);      // 64GB
memset(buf, 0, 64ULL << 30);          // ★ 主线程一个人碰了全部页

// 然后开 64 个线程，每个线程处理 buf 的一段
// 结果：64GB 全部落在主线程所在的 node 0
//       node 1 上的 32 个线程，100% 跨节点访存

这就是最经典的 NUMA 事故。表现是：CPU 利用率上不去，numastat 里 numa_hit 全在 node 0，node 1 的 other_node 很高，free 命令看到 node 0 内存快用完而 node 1 几乎没动。

三种修法，代价不同

做法原理代价
并行初始化每个线程只碰自己将来要处理的那段内存，让页在正确的节点上分配零成本，最优解。但要求程序结构支持
numactl --interleave页按节点轮流分配，均摊到所有节点牺牲局部性，但带宽最大化。适合共享大缓冲区
numactl --membind强制只从指定节点分配节点内存不足会直接失败，不 fallback
// 并行初始化的写法（OpenMP 示例）
#pragma omp parallel for
for (size_t i = 0; i < n; i++)
    buf[i] = 0;          // 每个线程碰自己那段 → 页落在本地节点

// 或者用 numa_alloc_onnode / numa_alloc_interleaved 直接指定
void *p = numa_alloc_onnode(size, 1);   // 明确要 node 1 的内存
numa_free(p, size);

来源说明
网卡中断与内存不在一侧网卡插在 CPU0 的 PCIe 槽，但收包缓冲区在 node 1。数据要跨两次
内核的自动 NUMA 均衡numa_balancing 会周期性扫描并迁移页，本身有开销，还可能引发抖动。对延迟敏感的服务建议关掉
页缓存（page cache）读文件时页缓存分配在读操作的 CPU 上。如果多个节点都在读同一批文件，缓存会分裂成多份

# 关掉它（临时）

# 永久关：内核参数加 numa_balancing=disable

模块 4

绑核与绑内存：numactl 的四个选项

绑定的本质是让"用内存的人"和"内存所在的位置"对上。只绑 CPU 不绑内存，或者反过来，效果都很有限。

选项行为适用场景
--cpunodebind=N只允许进程跑在节点 N 的 CPU 上配合 --membind 使用，构成完整的节点隔离
--physcpubind=0-7绑到具体 CPU 编号（可用 -C 简写）需要精确控制到物理核时
--membind=N只从节点 N 分配内存。N 内存不够就分配失败严格隔离，一个进程一个节点
--preferred=N优先从节点 N 分配，不够时回退到其他节点希望本地优先但不希望失败
--interleave=N,M在 N 和 M 之间轮流分配页大缓冲区、共享缓存、带宽优先
--localalloc默认策略，从当前 CPU 的本地节点分配多线程且内存访问局部性好时

三种典型组合

# 组合 1：完整隔离。进程只用 node 0 的 CPU 和 node 0 的内存
numactl --cpunodebind=0 --membind=0 ./app

# 组合 2：带宽优先。两个节点都用，内存交错分配
numactl --interleave=all ./app

# 组合 3：多实例部署。每个实例独占一个节点，互不干扰
numactl --cpunodebind=0 --membind=0 ./app --port 8001 &
numactl --cpunodebind=1 --membind=1 ./app --port 8002 &

# 查看进程当前的绑定情况
numactl --show
numastat -p $PID

组合 3 是数据库类服务最常见的部署方式：一台双路机器跑两个 MySQL 实例，各占一个节点，等于把一台机器切成两台，NUMA 问题彻底消失。代价是故障域没变小，一台机器挂了两个实例一起没。

--membind 和 --preferred 的差别很关键：
--membind=0 时，如果 node 0 内存耗尽，分配直接失败（返回 NULL / 进程被 OOM），不会偷偷用 node 1。这是"严格"的含义。
--preferred=0 时，node 0 满了会回退到 node 1，程序不会崩，但性能会悄悄退化。
所以用 --membind 一定要确认节点内存够，并且留出余量。

注意：绑定只影响"之后的分配"

无论是 numactl 还是 mbind() 系统调用，都只对尚未分配的页生效。已经落在错误节点的内存不会自动搬家。要迁移已存在的页，得用 move_pages() 或 migrate_pages()。

# 对已经在跑的进程改绑定（内核 4.x+ 支持）
numactl --cpunodebind=0 --membind=0 -p $PID

# 但已有内存不会迁移。要迁移：
# 用 migratepages 工具（numactl 包提供）
migratepages $PID 0 1        # 把所有页从 node 0 迁到 node 1
# 或者用 C 调 move_pages() 精确控制

模块 5

大页是什么：把 262144 个页表项变成 1 个

CPU 访问内存要先做虚拟地址到物理地址的翻译。翻译靠页表，而页表在内存里——每访问一次数据，理论上要先访问好几次内存。CPU 用 TLB 缓存翻译结果来救场，但 TLB 条目很少。大页的作用，就是让每个 TLB 条目覆盖更多内存。

先算一笔账

页大小映射 1GB 需要多少页页表项占用TLB 覆盖
4KB（常规页）262144 个262144 × 8B = 2MB 页表1536 条 × 4KB = 6MB
2MB（大页）512 个512 × 8B = 4KB（一张表）1536 条 × 2MB = 3GB
1GB（超大页）1 个1 个 PUD 项1536 条 × 1GB = 1.5TB

这组数字值得记下来。用 4KB 页时，TLB 最多只能覆盖 6MB 的热数据，一旦工作集超过这个量（几乎必然），每次访问都可能 TLB miss，触发页表遍历（page walk）——x86-64 上是 4 级，每一级都可能是一次内存访问。

换成 2MB 页，同样的 TLB 条目能覆盖 3GB；换成 1GB 页，覆盖 1.5TB，基本等于"永不 miss"。

地址翻译的四级结构

48 位虚拟地址 → 4 级页表 → 物理地址

  PML4 (9 bit) → PDPT (9 bit) → PD (9 bit) → PT (9 bit) → offset (12 bit)
       ↓             ↓             ↓            ↓
    512 项         512 项        512 项       512 项

4KB 页：四级都要走，最后一级 PT 指向 4KB 物理页
2MB 页：走到 PD 就停，PD 项直接指向 2MB 物理页（PS=1）
1GB 页：走到 PDPT 就停，直接指向 1GB 物理页

少走一级，就少一次潜在的内存访问。在 TLB miss 的情况下，2MB 页的页表遍历比 4KB 页少一次内存访问，1GB 页少两次。叠加到每次 cache miss 上，差距就出来了。

两种大页：hugetlbfs 与 THP

类型分配方式特点
静态大页
hugetlbfs		启动时或运行时预留，从 nr_hugepages 池子里拿保证成功、不会退化；但预留的内存别人用不了，浪费
透明大页
THP		内核自动把连续的 4KB 页合并成 2MB无需配置、按需分配；但合并本身有开销，可能引起延迟抖动

一句话区分：静态大页是"提前订好座位"，THP 是"现场看看能不能拼桌"。前者确定性强，后者灵活但不可控。

静态大页的操作

# 看当前预留了多少
grep -i huge /proc/meminfo
# HugePages_Total:      16        ← 预留总数
# HugePages_Free:       16        ← 还没被用的
# HugePages_Rsvd:        0        ← 已承诺但未实际分配
# HugePages_Surp:        0        ← 超额分配的数量
# Hugepagesize:       2048 kB     ← 默认大页尺寸

# 运行时调整（2MB 页）
echo 512 > /proc/sys/vm/nr_hugepages
echo 512 > /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages

# 1GB 页必须在内核参数里预留，运行时基本改不动
# 在 GRUB 的 GRUB_CMDLINE_LINUX 里加：
default_hugepagesz=1G hugepagesz=1G hugepages=8

# 挂载 hugetlbfs 供应用使用
mount -t hugetlbfs none /dev/hugepages

# 看每个尺寸的池子
ls /sys/kernel/mm/hugepages/
# hugepages-1048576kB  hugepages-2048kB
1GB 大页为什么必须启动时预留：1GB 页要求物理内存中有连续的 1GB 空间。系统跑久了内存碎片化，很难再找到这么大一块连续物理内存。2MB 相对容易，但也可能失败。
所以：大页预留要写进内核参数，在系统刚起来、内存还干净的时候完成。运行时 echo 只适合小规模调整。
模块 6

透明大页 THP 的坑：为什么 Redis 让你关掉它

THP 听起来全是好处——自动、无需配置、免费提速。但它有一个致命的副作用：合并内存页的时候，会卡住正在运行的进程。

THP 的三种策略

值行为建议
always只要可能就用 2MB 页，内核主动合并。很多发行版的默认值通用场景可以，延迟敏感服务不行
madvise只有应用显式调用 madvise(MADV_HUGEPAGE) 的区域才用推荐折中方案：想用的自己开，不想用的不受影响
never完全关闭Redis、MongoDB 等官方建议
# 查看当前策略（方括号里是生效值）
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never

# 临时改
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled

# 永久改：内核参数加 transparent_hugepage=madvise
# 然后 grub2-mkconfig / update-grub

坑在哪：khugepaged 和内存规整

THP 有两个后台机制，都会引发问题：

khugepaged（大页合并内核线程）。它周期性扫描内存，寻找可以合并成 2MB 的连续 4KB 页。默认每 10 秒扫一轮，每轮扫 4096 页。扫描和合并时要拿内存锁，会短暂阻塞分配内存的进程。
内存规整（compaction）。如果找不到连续的 2MB，内核会尝试搬移已有的页来腾出连续空间。搬移需要暂停相关进程的页表操作，代价比扫描更大。
缺页时的直接合并。分配 2MB 页时如果失败，会触发同步规整，这次分配会阻塞几十微秒到几毫秒。

对一个 P99 要求 1ms 的服务来说，这几毫秒就是灾难。你会看到延迟曲线平时很平，每隔十几秒冒一个尖刺——周期正好对上 khugepaged 的扫描间隔。

Redis 为什么特别怕 THP

Redis 有两个特性让它对 THP 格外敏感：

  • 单线程执行命令。任何一次阻塞都会直接变成所有客户端的延迟。没有其他线程能顶上。
  • fork 做持久化。RDB/AOF 重写时 fork 子进程，靠写时复制（COW，Copy-On-Write）共享内存。如果内存是 2MB 大页，改一个字节就要复制整个 2MB；4KB 页只需要复制 4KB。写时复制的开销被放大 512 倍。

所以 Redis 官方文档明确建议关闭 THP，原因不是"大页不好"，而是它的持久化模型和 COW 与大页的粒度不匹配。

# 检查 THP 是否已经造成问题
grep -E 'thp_' /proc/vmstat
# thp_fault_alloc          ← 成功分配的大页数
# thp_fault_fallback       ← 分配失败退化成 4KB 的次数（高说明在反复挣扎）
# thp_collapse_alloc       ← khugepaged 合并成功的页数
# thp_collapse_alloc_failed← 合并失败次数
# thp_split_page           ← 大页被拆开的次数（说明大页没起到作用）

# 看 khugepaged 的扫描节奏
cat /sys/kernel/mm/transparent_hugepage/khugepaged/scan_sleep_millisecs
cat /sys/kernel/mm/transparent_hugepage/khugepaged/pages_to_scan

# 临时关掉合并，只保留分配（不动应用）
echo 0 > /sys/kernel/mm/transparent_hugepage/khugepaged/defrag
最隐蔽的一种情况：THP 开着，Redis 平时跑得好好的，某次 BGSAVE 时延迟突然飙到几百毫秒。
排查思路：① 确认 /sys/kernel/mm/transparent_hugepage/enabled 是 always；② 看 /proc/vmstat 里 thp_fault_alloc 是否在涨；③ 关掉 THP 后重测。如果关掉就好了，别再往下查了。
模块 7

什么时候该用大页

判据只有一条：有一个大块、长期驻留、随机访问的内存区域，而且 TLB miss 是瓶颈。满足就用，不满足就别折腾。

四类典型受益者

数据库缓冲池
MySQL InnoDB Buffer Pool、Oracle SGA、PostgreSQL shared_buffers。几十 GB 到上百 GB 的随机访问，TLB miss 严重。Oracle 和 MySQL 都原生支持大页。
JVM 堆
大堆（> 16GB）+ 随机对象访问。-XX:+UseLargePages，配合 -XX:+AlwaysPreTouch 预触所有页。
虚拟化
KVM/QEMU 的 guest 内存。大页减少 EPT/影子页表的开销，虚拟化场景收益最明显。
高性能网络
DPDK 的 mbuf 池、用户态协议栈的收发缓冲区。要求零抖动，必须用静态大页锁定内存。

各家的具体配置

# ---- MySQL / InnoDB ----
# my.cnf 里：
large_pages = ON
innodb_buffer_pool_size = 64G
# 前提：系统预留了足够的 2MB 大页
# 64G / 2M = 32768 个，留 10% 余量 → 36000

# ---- JVM ----
java -XX:+UseLargePages \
     -XX:LargePageSizeInBytes=2m \
     -XX:+AlwaysPreTouch \
     -Xms32g -Xmx32g -jar app.jar
# 注意：-Xms 和 -Xmx 必须相等，否则扩容时会失败

# ---- KVM 虚拟机 ----
# 在 libvirt XML 里给 guest 内存加 backend：
<memoryBacking>
  <hugepages><page size="2048" unit="KiB"/></hugepages>
</memoryBacking>

# ---- DPDK ----
# 预留 1GB 大页，DPDK 启动时挂载 hugetlbfs
default_hugepagesz=1G hugepagesz=1G hugepages=8

不该用大页的场景

场景原因
小内存服务（< 1GB）工作集本来就装得进 TLB，收益接近零，还浪费预留内存
内存碎片敏感的多租户环境预留的大页别人用不了，机器利用率下降
频繁 fork 的进程写时复制的粒度变成 2MB，fork 后性能反而变差（Redis 就是例子）
内存使用波动大的服务静态大页预留了就不能给别人用，缩容时浪费
容器密度优先的场景大页不可压缩、不可 swap，超卖能力下降
一个务实的顺序：① 先确认 TLB 真的是瓶颈（perf stat -e dTLB-load-misses,dtlb_store_misses.walk_completed）；② 如果是，先用 THP 的 madvise 模式试，改动最小；③ 效果不够再上静态大页；④ 上静态大页前一定要算清楚"预留多少、留多少余量"。
别一上来就改内核参数——大页预留是全局的，改错了影响整台机器上所有服务。
模块 8

观测：numastat 与 /proc 里的关键指标

NUMA 和大页的问题都有明确的量化信号，不需要猜。

numastat 的六个字段

字段含义
numa_hit按预期分配在本节点的页数。这个值应该占绝大多数
numa_miss本节点分配失败、被迫分到别的节点的页数
numa_foreign本节点的内存被别的节点拿走的页数
interleave_hit按 interleave 策略命中的页数
local_node在本节点 CPU 上分配的、且落在本节点的页数
other_node在本节点 CPU 上运行、但内存分到了别的节点的页数。这个高就是问题

注意 numa_miss 和 numa_foreign 是配对的：node 0 的 miss 数，等于 node 1 的 foreign 数。看到这两个数一起涨，说明有进程在"借"别人的内存。

# 全系统
numastat

# 按进程看（最有用）
numastat -p $PID

# 按 cgroup 看
numastat -c

# 只看内存总量分布
numastat -m

# 更细：每个虚拟内存区域的 NUMA 分布
cat /proc/$PID/numa_maps | head
# 7f2c00000000 default anon=262144 dirty=262144 N0=262144
#                          ↑ 页数              ↑ 全在 node 0

/proc/meminfo 里的大页字段

字段含义
HugePages_Total预留的大页总数。为 0 说明没配静态大页
HugePages_Free还没被使用的。等于 Total 说明预留了但没人用，纯浪费
HugePages_Rsvd已被承诺（reserve）但还没实际写入的
HugePages_Surp超出 nr_hugepages 的"超额"页，需要 nr_overcommit_hugepages 才可能出现
Hugepagesize默认大页尺寸，通常是 2048 kB
Hugetlb大页占用的总内存

/proc/vmstat 里的 THP 字段

字段怎么读
thp_fault_alloc缺页时成功分配大页的次数。持续增长说明 THP 在工作
thp_fault_fallback分配大页失败、退回 4KB 的次数。占比高说明内存碎片严重
thp_collapse_allockhugepaged 合并成功的页数
thp_collapse_alloc_failed合并失败次数。高说明后台一直在白忙
thp_split_page大页被拆回 4KB 的次数（madvise(MADV_NOHUGEPAGE) 或内存紧张时）
thp_zero_page_alloc用零页填充的大页数
thp_file_alloc文件页的大页分配（需要 shmem_enabled 或较新内核）
# 一次性看全（间隔 1 秒采样，看增量比看绝对值有用）
for i in 1 2 3; do
  grep -E 'thp_|numa_' /proc/vmstat
  echo '---'
  sleep 1
done

# 确认 TLB 是不是真的瓶颈（最直接的证据）
perf stat -e dTLB-loads,dTLB-load-misses,dtlb_store_misses.walk_completed ./app

# 如果 dTLB-load-misses / dTLB-loads > 5%，就值得考虑大页了
一个诊断顺序，照做就行：
① numactl --hardware 确认拓扑（几个节点、距离多少）。
② numastat -p $PID 看进程的内存分布。如果 90% 以上集中在一个节点而 CPU 用了两个节点 → NUMA 问题。
③ perf stat -e dTLB-load-misses 看 TLB 命中率。miss 率 > 5% → 大页可能有帮助。
④ 看 /proc/vmstat 里 thp_fault_fallback 的增量。增长快说明大页分配在失败，THP 没起到作用。
常见坑

十个 NUMA 与大页的坑

1
主线程 malloc + memset 初始化了整个大缓冲区
first touch 策略下，所有页都落在主线程所在的节点，其他节点的线程全部跨节点访存。改成并行初始化，或直接 interleave。
2
只绑 CPU 不绑内存
--cpunodebind=0 只是限制了跑在哪些核上，内存还是可能从 node 1 分配。要配 --membind 或 --localalloc。
3
以为 numactl 会迁移已有内存
绑定只影响之后的新分配。已经落在错误节点的页要显式迁移（move_pages / migratepages），或者重启进程。
4
用 --membind 却没算够内存
节点内存耗尽时分配直接失败，进程可能崩掉。--membind 不 fallback，这是它和 --preferred 的关键区别。
5
在双路上跑单个大实例，还抱怨扩容没效果
所有内存挤在一个节点，另一个节点的带宽白白浪费。要么 interleave，要么拆成两个实例各绑一个节点。
6
THP 用 always 跑延迟敏感服务
khugepaged 扫描和内存规整会带来周期性延迟尖刺。改用 madvise，或直接 never。
7
Redis 开着 THP 做持久化
fork 后 COW 的粒度是 2MB，改一个字节复制 2MB，BGSAVE 期间延迟暴涨。Redis 官方明确建议关 THP。
8
预留了大页但应用没用
HugePages_Total 很大、Free 也很大，说明预留了没人用，这部分内存彻底浪费。要么让应用用上，要么调小。
9
运行时给 1GB 大页 echo nr_hugepages
系统跑久了物理内存碎片化，找不到连续的 1GB，基本一定失败。1GB 页必须在启动参数里预留。
10
在容器里用 numactl 却看不到真实拓扑
容器默认只能看到 cpuset 分配的 CPU，NUMA 节点信息可能被裁剪。要用 --privileged 或挂载 /sys，更好的做法是用 cpuset.mems + K8s Topology Manager。
自测

六道题

1. numactl --hardware 显示距离矩阵对角是 10、非对角是 21。这说明什么？
正确答案：跨节点约为本地的 2.1 倍。距离是相对值，本地固定为 10。实际纳秒数要看硬件，但比例关系是可靠的。
2. 一个多线程程序，主线程 malloc 了 64GB 并 memset 初始化，然后开 64 个线程处理。最可能的结果是？
正确答案：全落在主线程的节点。Linux 默认 first touch 策略，物理页在第一次写入时分配，位置取决于当时的 CPU。修法是并行初始化或 interleave。
3. --membind 和 --preferred 的关键区别是？
正确答案：membind 严格、preferred 可回退。严格意味着确定性，也意味着节点内存必须留足余量，否则进程会因为分配失败而崩。
4. 用 4KB 页映射 1GB 内存，需要多少个页表项？换成 2MB 页呢？
正确答案：262144 个；512 个。1GB / 4KB = 262144，1GB / 2MB = 512。页表项每个 8 字节，所以 4KB 页的页表本身就要 2MB。
5. Redis 官方建议关闭 THP，最核心的原因是？
正确答案：COW 粒度放大。改一个字节就要复制整个 2MB 页，BGSAVE 期间延迟会明显上升。叠加 Redis 单线程执行命令，影响被进一步放大。
6. numastat 里哪个字段高，说明"在本节点跑，但内存分到了别的节点"？
正确答案：other_node。它的定义就是"在本节点 CPU 上分配、但页落在其他节点"。这个值持续增长，说明本地内存不够或者分配策略有问题。
