开始前

一段能跑出真实差距的代码

理论复杂度说"数组和链表遍历都是 O(n)"，但实测能差一个数量级。这个差距必须自己测一次，否则永远记不住。

// bench.c —— 对比数组遍历和链表遍历
// 编译: gcc -O2 -fno-omit-frame-pointer -g bench.c -o bench
#include <stdio.h>
#include <stdlib.h>
#include <time.h>

#define N 1000000

typedef struct Node { int v; struct Node *next; } Node;

int main(void) {
    int *arr = malloc(N * sizeof(int));
    for (int i = 0; i < N; i++) arr[i] = i;

    Node *head = NULL;
    for (int i = 0; i < N; i++) {
        Node *n = malloc(sizeof(Node));
        n->v = i; n->next = head; head = n;
    }

    struct timespec t0, t1;
    volatile long sum = 0;

    clock_gettime(CLOCK_MONOTONIC, &t0);
    for (int i = 0; i < N; i++) sum += arr[i];
    clock_gettime(CLOCK_MONOTONIC, &t1);
    printf("array: %.2f ms\n",
        (t1.tv_sec - t0.tv_sec) * 1e3 + (t1.tv_nsec - t0.tv_nsec) / 1e6);

    clock_gettime(CLOCK_MONOTONIC, &t0);
    for (Node *p = head; p; p = p->next) sum += p->v;
    clock_gettime(CLOCK_MONOTONIC, &t1);
    printf("list:  %.2f ms\n",
        (t1.tv_sec - t0.tv_sec) * 1e3 + (t1.tv_nsec - t0.tv_nsec) / 1e6);

    printf("sum=%ld\n", sum);   // 防止编译器把循环优化掉
    return 0;
}

在一台普通 x86 机器上，输出大概是这样：

array: 0.71 ms
list:  4.83 ms
sum=999999000000
这个差距其实被低估了。上面这段代码里，链表节点是按顺序 malloc 出来的，所以在堆上基本连续，CPU 预取器还能帮上忙。真实业务里的链表节点是"插入时随手分配"的，散落在堆的各处，每次 p = p->next 都可能是一次完整的内存访问 —— 差距会从 7 倍变成几十倍。
这就是模块 2 要展开的核心结论：理论复杂度相同，实际性能可以差两个数量级，差别全在内存访问模式上。
顺手做一次观测：编译时带上 -g，然后跑 perf stat -e cycles,instructions,cache-misses ./bench，对比两种遍历的 IPC 和 cache-misses。数组遍历的 IPC 通常能到 2 以上，链表遍历常常不到 0.5 —— 这就是"指针追逐"（pointer chasing）的真实代价。
模块 1

为什么工程里也要懂

99% 的场景应该用语言自带的容器，不要自己写。但那 1% 决定系统能不能扛住，而且"选错容器"这个错误通常在上线三个月后才暴露。

选错结构的代价是数量级的

# 场景：从 10 万条记录里，找出与另一批 ID 重复的部分

# 写法 A：List.contains() —— 每次线性扫描
for id in incoming:            # 10 万次
    if id in id_list:          # 每次最多扫 10 万个元素
        dup.append(id)
# 最坏 10^10 次比较 → 几分钟

# 写法 B：换成 set
id_set = set(id_list)          # O(n) 建表，一次性成本
for id in incoming:
    if id in id_set:           # O(1)
        dup.append(id)
# 10 万次哈希查找 → 几十毫秒

两段代码逻辑完全一样，读起来甚至 A 更直观，但性能差 4 个数量级。而且这个差距在测试环境里可能完全看不出来 —— 因为测试数据只有 100 条。

什么时候用现成的，什么时候自己设计

场景选择理由
普通业务逻辑用语言自带的（list / dict / map / set）实现经过充分测试，边界情况都处理过了。自己写只会引入 bug
需要"按插入顺序"或"按访问顺序"淘汰用 LinkedHashMap（Java）/ OrderedDict（Python）自带 LRU 语义，不用自己维护双向链表
热路径上的高频操作考虑自己设计标准容器为了通用性做了大量妥协（额外指针、装箱、锁），专用结构能快 5~50 倍
内存受限（嵌入式、千万级条目）必须自己设计通用容器的每元素开销可能是数据的 3~5 倍
需要特定语义（无锁、可持久化、范围查询）找成熟库，别自己写并发正确性极难验证，除非你是这个领域的专家
最常见的性能事故：在循环里做线性查找。形态有很多种 —— list.index()、if x in list、SELECT ... WHERE id = ? 没有索引、以及"在循环里调 RPC 查一条数据"。
它们的共同特征是：单次调用看起来很快（几十微秒），但被 N 次循环放大成分钟级。代码评审时很难发现，因为每一行单独看都没问题。

一个判断口诀

写代码时问自己三个问题：这个集合会有多大？（决定复杂度是否有意义）、我会查多少次？（决定要不要建索引/哈希）、数据在内存里怎么排布？（决定实际快慢）。

三个问题的答案组合起来，基本就决定了该用什么结构。答不出来，说明你还不了解这个场景的数据规模 —— 那才是真正该先搞清楚的事。

模块 2

数组与链表

教科书说"数组查询 O(1)、插入 O(n)；链表查询 O(n)、插入 O(1)"。这个表没错，但它漏掉了最重要的变量：常数因子。

操作数组链表实际差异
随机访问O(1)O(n)数组是一次地址计算 + 一次内存读；链表要追 n 次指针
头部插入O(n)O(1)数组要搬移全部元素（memmove 很快，1MB 约 50μs）；链表只需改两个指针
中间插入O(n)O(1)（前提是已持有前驱节点）链表"找到位置"本身是 O(n)，所以完整操作还是 O(n)
遍历O(n)O(n)这里是差距最大的地方，见下面的分析
内存开销每元素 4/8 字节每元素额外 8 字节指针 + 分配器头部（通常 8~16 字节）链表的内存占用是数组的 2~3 倍

为什么数组遍历快得多

关键在于 CPU 的缓存行（cache line，x86-64 上是 64 字节）和硬件预取器（prefetcher，硬件自动提前把后面的数据搬进缓存的机制）。

一次内存访问搬 64 字节，不是 4 字节。读 arr[0] 时，arr[0..15] 这 16 个 int 一起被装进缓存。接下来 15 次访问全部命中 L1，每次约 1ns。
预取器能识别顺序访问。当它发现你在按 +4 的步长连续读，会提前把后面几 KB 的数据搬进 L2。于是大部分访问的延迟被完全隐藏。
链表破坏了这两个机制。每个节点在堆上的位置是随机的，预取器无法预测下一个地址。更糟的是下一次访问的地址要等这一次访问的结果才知道 —— 这叫指针追逐（pointer chasing），硬件流水线在这里彻底停摆。
代价的具体数字：L1 命中约 1ns，L2 约 4ns，L3 约 15~40ns，主存约 80~100ns。链表每跳一次就是一次主存访问，数组每 16 个元素才一次。
一个具体的估算：100 万个节点，链表每次跳转 80ns（假设全部未命中），遍历耗时约 80ms；同样 100 万个 int 的数组占 4MB，顺序读的带宽约 10GB/s，耗时约 0.4ms。差 200 倍。
这就是为什么"链表插入是 O(1)"这个优势在实际中经常被吃掉 —— 你为了省下插入时的搬移，付出了遍历时 200 倍的代价。

那链表什么时候真的更优

场景为什么链表赢
元素本身很大（几百字节以上）数组插入时要搬移整个元素；链表只改指针。当元素大小 > 缓存行的几十倍时，搬移成本压倒指针追逐成本
需要稳定的引用 / 迭代器数组扩容后所有指针和迭代器全部失效（Java 的 ArrayList、C++ 的 vector 都是这样）；链表节点的地址永远不变
O(1) 拼接（splice）把整个链表接到另一个链表尾部，只改两个指针。数组做不到，必须整体复制
LRU 缓存需要"把节点从中间摘下来、挂到头部"，这个操作必须是 O(1)。所以 LRU 的标准实现是哈希表 + 双向链表
无锁队列用 CAS 交换头尾指针，天然适合链表。数组实现无锁队列要处理 ABA 和边界，复杂得多
侵入式链表把 next 指针嵌进业务结构体内部（Linux 内核的 list_head），省掉一次独立分配，一个对象可以同时挂在多条链上
工程上的默认选择：用"动态数组"（vector / ArrayList / slice），不要用链表。
几乎所有现代语言的标准库都在往这个方向走：Go 没有内置链表（container/list 存在但官方不建议用）、Rust 的 LinkedList 文档里直接写着"几乎总是比 Vec 慢"、Java 的 LinkedList 在实际 benchmark 中几乎全面输给 ArrayList。
只有在上面表格列出的那几种场景里，才考虑链表。
模块 3

哈希表

哈希表是工程上最重要的数据结构，没有之一。它的平均 O(1) 是把"比较"换成了"算地址"，代价是最坏情况会退化成 O(n)，而且可以被恶意触发。

三个组成部分

哈希函数
把任意 key 映射成一个整数。要求：计算快、分布均匀、抗构造碰撞。三者常常冲突，需要权衡
桶数组
一块连续内存，用 hash % capacity 定位。容量通常是 2 的幂，这样取模可以换成更快的位与
冲突处理
不同 key 落到同一个桶时的应对策略。分两大类：链地址法和开放寻址法

冲突处理：两种流派

方式做法优点缺点
链地址法
separate chaining		每个桶挂一条链表（或红黑树），冲突的元素接在后面实现简单；负载因子可以超过 1；删除简单每个元素多一个指针；节点分散在堆上，缓存不友好；极端情况下链表很长
开放寻址法
open addressing		冲突了就按某种探测序列找下一个空槽（线性探测 / 二次探测 / 双重哈希）全在数组里，缓存极友好；没有额外指针，内存紧凑负载因子必须 < 1（通常 0.7 就该扩容）；删除需要墓碑标记；聚集效应会让探测变长

线性探测的问题是一次聚集（primary clustering）：连续被占用的区域会越来越长，后续插入和查找都要走更远的探测序列。缓解手段有三种 —— 二次探测（步长取 i²，但可能探测不到所有槽）、双重哈希（用第二个哈希函数决定步长，效果最好）、以及 Robin Hood 探测（比较"离家距离"，把离家更远的元素往后挤，让探测距离分布更均匀）。

扩容与 rehash 的代价

当元素数量超过 容量 × 负载因子（load factor，负载因子）时，必须扩容。扩容不是简单的复制，每个元素都要重新计算位置，因为 hash % 新容量 的结果和原来不同。

实现默认负载因子扩容策略
Java HashMap0.75容量翻倍。因为容量是 2 的幂，元素要么留在原位，要么移到"原位 + 旧容量"，不需要重新算哈希
Redis dict1.0翻倍，但用渐进式 rehash：每次操作顺带迁移一个桶，把 O(n) 的停顿摊到多次操作里
Go map6.5 / 8（每桶 8 个槽）翻倍，渐进式扩容，每次写操作迁移一到两个桶
Abseil SwissTable约 0.875翻倍，用控制字节 + SIMD 一次比较 16 个槽
rehash 是一次 O(n) 的停顿，这是很多"周期性卡顿"的来源。一个装了 1000 万条目的 HashMap，扩容时要重新分配并迁移全部元素，可能停顿几百毫秒到几秒。
解法：预估容量，一次性分配够。Java 里写 new HashMap<>((int)(expected / 0.75f) + 1)，Go 里写 make(map[K]V, expected)。这一行代码能省掉上线后所有的扩容停顿。

Java HashMap 的树化：一个工程妥协

Java 8 之后，当单个桶的链表长度达到 8 且总容量 ≥ 64 时，链表会转成红黑树，把最坏查找从 O(n) 降到 O(log n)。当节点数降到 6 时再转回链表。

为什么要两个阈值（8 和 6）而不是一个？为了避免在临界点反复转换（hysteresis，迟滞）。如果都是 8，那么元素数在 8 附近抖动时会不停地树化/反树化，开销比两种结构本身都大。

哈希攻击：一个能打垮服务的输入

# 攻击原理：如果哈希函数是公开且确定的，攻击者可以离线构造大量碰撞的 key
# 假设服务端用 hash(key) = key.hashCode() % 10000
# 攻击者构造 10 万个 hashCode 全相同但内容不同的字符串

POST /api/lookup
{"keys": ["AaAaAa...", "BBBBBB...", ...]}   # 10 万个碰撞 key

# 结果：所有 key 落进同一个桶 → 链表长度 10 万
# 每次查找从 O(1) 变成 O(10万) → CPU 打满，服务不可用
# 这就是 HashDoS（哈希拒绝服务攻击）
防御手段说明
随机化哈希种子进程启动时生成随机 key，hash = SipHash(key, data)。攻击者无法离线构造碰撞。Python 3.4+、Rust 的 HashMap 默认都这么做
用抗碰撞的哈希SipHash（带密钥的伪随机函数）、MurmurHash3 的带种子版本
限制单次请求的元素数入口层限制 JSON 数组长度、表单字段数，让攻击者无法一次塞进 10 万个 key
树化 / 跳表兜底即使碰撞，最坏也是 O(log n)。Java 8 的树化就是这个思路
2011 年的一批安全事故就是这个原因。PHP、Java、ASP.NET、Ruby 等主流运行时都在那一年被证明可以构造碰撞输入，攻击者用一个几十 KB 的请求就能让一台服务器 CPU 打满。此后几乎所有语言都把默认哈希改成了带随机种子的版本。
如果你自己实现哈希表（比如在 C 里写一个），一定要加随机种子。用固定种子的哈希函数暴露在公网，等于给攻击者留了一个开关。
模块 4

树结构

树解决的问题是"既要能快速查找，又要保持顺序"。哈希表能 O(1) 查找，但它不支持范围查询和有序遍历 —— 这就是树存在的理由。

二叉搜索树的退化

# 依次插入 1, 2, 3, 4, 5（有序数据）
1
 \
  2
   \
    3
     \
      4
       \
        5

# 完全退化成链表，查找变成 O(n)
# 这在真实系统里非常常见：自增主键、时间戳、有序 ID 都是天然有序的输入

所以工程上不会直接用裸的 BST。要么用平衡树，要么用跳表，要么用哈希表。

结构平衡条件查找/插入/删除特点
AVL 树任意节点左右子树高度差 ≤ 1O(log n)更严格平衡，查找更快，但插入删除的旋转次数多。适合读多写少
红黑树最长路径 ≤ 2 × 最短路径O(log n)近似平衡，插入删除最多 3 次旋转。适合读写均衡。Java TreeMap、C++ std::map、Linux 的 CFS 调度器都用它
跳表 skiplist概率平衡（多层索引）期望 O(log n)实现比红黑树简单得多，范围查询天然高效。Redis 的 ZSet、LevelDB 的 memtable 用它
B 树 / B+ 树所有叶子在同一层O(log n)，但常数极小为磁盘设计，一个节点装一整页。见下文

B+ 树为什么适合磁盘

核心矛盾：磁盘的一次随机读要 100μs（SSD）到 10ms（机械盘），而 CPU 的一次比较只要 1ns。所以磁盘结构的设计目标不是"减少比较次数"，而是减少 IO 次数。

# InnoDB 的页大小是 16KB，B+ 树的每个节点就是一页

# 非叶子节点存的是 (主键, 子页指针)：
bigint 主键        8 字节
页指针             6 字节
合计每项          14 字节

# 一页能放多少个索引项：
16 × 1024 / 14 ≈ 1170 个

# 三层 B+ 树能存多少行？
第 1 层（根）      1 页          → 1170 个指针
第 2 层            1170 页       → 1170 × 1170 个指针
第 3 层（叶子）    136 万页      → 每页假设存 16 行（每行 1KB）
总计 ≈ 136 万 × 16 ≈ 2100 万行

# 关键结论：2000 万行的表，按主键查一行只需要 3 次 IO
# 而且根节点和第二层几乎常驻在 buffer pool 里，实际常常只要 1 次 IO
这就是"一个节点装一页"的全部意义。如果换成二叉搜索树，2000 万行需要约 25 层，也就是 25 次随机 IO —— 在机械盘上就是 250ms，完全不可用。B+ 树把 25 次压到 3 次，靠的是每个节点存上千个 key，把树的"扇出"（fanout）从 2 提到 1000 以上。
推论：树的高度 ≈ log(扇出, 行数)。扇出越大，树越矮，IO 越少。所以主键越短越好 —— 用 bigint 而不是 UUID 字符串，扇出能大好几倍。

B 树与 B+ 树的区别

特性B 树B+ 树
数据存放位置每个节点都存数据只有叶子节点存数据，内部节点只存索引
扇出较小（节点要分空间给数据）更大（内部节点全是索引，能放更多 key）
范围查询需要中序遍历，跨层跳转叶子节点之间有链表，顺序扫一遍即可
查询稳定性不同 key 的 IO 次数不同所有查询都走到叶子，IO 次数固定

LSM 树：另一个方向的取舍

B+ 树优化的是读。但写密集场景下，每次写入都要找到对应的页、修改、刷盘，随机写的代价很高。LSM（Log-Structured Merge Tree，日志结构合并树）反过来：所有写入都是顺序追加。

# LSM 的写路径
写入 → WAL（顺序写日志，保证持久化）
     → MemTable（内存里的有序结构，通常是跳表）
     → 内存满了，冻结成 Immutable MemTable
     → 后台刷成 SSTable（有序的、不可变的小文件，顺序写盘）
     → 后台定期合并（compaction），把多个 SSTable 归并成更大的

# 读路径（这就是代价）
查 MemTable → 查 Immutable → 从新到旧查各层 SSTable

模块 5

堆与优先队列

堆解决的问题是"我只需要知道最大/最小的那个，不需要全部有序"。这个"只需要"能省掉大量工作 —— 全排序是 O(n log n)，维护一个堆只要 O(log n)。

堆的性质

堆是一棵完全二叉树（complete binary tree，除最后一层外每层都填满，最后一层靠左连续），并且每个节点都不大于（小顶堆）或不小于（大顶堆）它的子节点。

因为是完全二叉树，它可以直接存在数组里，不需要指针：

# 0-indexed 的数组表示
节点 i 的父节点:   (i - 1) / 2
节点 i 的左孩子:   2 * i + 1
节点 i 的右孩子:   2 * i + 2

# 例：小顶堆 [1, 3, 2, 7, 5, 4]
        1          # index 0
      /   \
     3     2       # index 1, 2
    / \   /
   7   5 4         # index 3, 4, 5

# 关键：这个数组本身不是有序的，只有"父子关系"有序
# 所以不能二分查找，只能取堆顶
操作复杂度说明
取堆顶O(1)直接读 a[0]
插入O(log n)放到末尾，然后"上浮"（sift up）
弹出堆顶O(log n)把末尾元素移到堆顶，然后"下沉"（sift down）
建堆O(n)从最后一个非叶节点往前，依次下沉。不是 O(n log n)
查找任意元素O(n)堆不支持快速查找，这是它和搜索树的关键区别
为什么建堆是 O(n) 而不是 O(n log n)？因为大部分节点在底层，下沉的距离很短。精确计算是 n × Σ(h/2^h) ≈ 2n —— 高度为 h 的节点有 n/2^h 个，每个最多下沉 h 步，求和收敛到 2n。这个结论在面试和实际调优里都有用：如果你要建一个 n 元素的堆，直接 heapify 比 n 次 push 快一倍以上。

Top-K 为什么用大小为 K 的小顶堆

# 问题：从 1 亿个数里找最大的 100 个

# 方案 A：全排序 —— O(n log n)，还要 1 亿个元素的内存
sorted(nums)[-100:]

# 方案 B：大小为 K 的小顶堆 —— O(n log K)，内存只要 K
import heapq

def top_k(nums, k):
    heap = nums[:k]
    heapq.heapify(heap)              # O(k)，建的是小顶堆
    for x in nums[k:]:
        if x > heap[0]:              # 比堆顶（当前第 K 大）还大
            heapq.heapreplace(heap, x)   # 弹出最小，插入 x，O(log k)
    return heap

# 为什么是小顶堆而不是大顶堆？
# 因为堆顶必须是"当前这 K 个里最小的那个"
# 只有这样才能 O(1) 判断"新元素该不该进来"
# 如果堆顶是最大的，你永远不知道最小的那个要不要被淘汰
方案时间额外内存适用
全排序O(n log n)O(n)数据量小，或者本来就需要全序
大小为 K 的堆O(n log K)O(K)K 远小于 n，流式数据
快速选择 quickselect平均 O(n)O(1)数据在内存里、可以打乱、只要第 K 大

定时器与延时队列为什么用堆

定时器的核心需求是：快速找到"最早到期的那个任务"。这和堆的语义完全吻合 —— 按到期时间建小顶堆，堆顶就是下一个要执行的任务。

# 一个最小可用的定时器（伪代码）
heap = []                          # 按 (expire_at, task) 排序的小顶堆

def add_task(delay_ms, task):
    heapq.heappush(heap, (now() + delay_ms, task))

def run():
    while True:
        if not heap:
            sleep_until_next_event()
            continue
        expire_at, task = heap[0]
        if expire_at > now():
            sleep_until(expire_at)     # 睡到最早的那个到期时间
        else:
            heapq.heappop(heap)
            task()
实现特点
堆插入和取最小都是 O(log n)，实现简单。绝大多数场景够用
时间轮 timing wheel插入和删除都是 O(1)，适合海量定时任务。Netty 的 HashedWheelTimer、Kafka 的延时操作都用它
有序集合（ZSet / Redis）分布式场景下用 Redis 的 ZSet 按时间戳打分，多个实例共享同一个定时队列
堆做定时器有一个隐藏成本：取消任务。堆只支持"弹出堆顶"，不支持"删除中间某个元素"。要实现取消，只能打一个 cancelled 标记，等它浮到堆顶时再丢弃 —— 这叫惰性删除。
后果：如果大量任务被取消，堆会持续膨胀，内存不释放。这就是为什么海量短生命周期定时任务要用时间轮而不是堆 —— 时间轮支持 O(1) 的真正删除。
模块 6

图与遍历

图在工程里出现得比想象中多：依赖关系、调用链、社交关系、路由表、状态机 —— 只要涉及"多对多关系"，就是图。

两种表示法

表示空间判断 (u,v) 有边适合
邻接矩阵O(V²)O(1)，直接查 m[u][v]稠密图（边数接近 V²）、需要频繁判断两点是否相连、V 很小（几百）
邻接表O(V + E)O(degree(u))，要遍历 u 的邻居稀疏图（绝大多数真实场景）、需要遍历邻居

100 万个节点的社交网络，如果边有 5000 万条：邻接矩阵要 10^12 个格子（根本存不下），邻接表只要 1 亿个条目。所以真实系统几乎都用邻接表。

BFS 与 DFS 的适用场景

算法数据结构复杂度什么时候用
BFS队列O(V + E)无权图的最短路径、层序遍历、找"最少几步能到"。按层扩散，第一次到达就是最短
DFS栈 / 递归O(V + E)连通性判断、环检测、拓扑排序、找所有路径。一条路走到黑，天然适合"探索所有可能"
# BFS：无权图最短路径
from collections import deque

def bfs_shortest(graph, start, target):
    q = deque([(start, 0)])
    seen = {start}
    while q:
        node, dist = q.popleft()
        if node == target:
            return dist
        for nxt in graph[node]:
            if nxt not in seen:
                seen.add(nxt)          # 入队时就标记，不要出队时标记
                q.append((nxt, dist + 1))
    return -1

# 注意：seen.add 必须在入队时做
# 如果放在出队时，同一个节点会被重复入队多次，复杂度退化

最短路径：Dijkstra

# Dijkstra：单源最短路径，要求边权非负
import heapq

def dijkstra(graph, start):
    # graph[u] = [(v, weight), ...]
    dist = {start: 0}
    pq = [(0, start)]                 # (当前距离, 节点)，小顶堆

    while pq:
        d, u = heapq.heappop(pq)
        if d > dist.get(u, float("inf")):
            continue                  # 过期条目，跳过（惰性删除）
        for v, w in graph[u]:
            nd = d + w
            if nd < dist.get(v, float("inf")):
                dist[v] = nd
                heapq.heappush(pq, (nd, v))
    return dist

# 复杂度：O((V + E) log V)（二叉堆）
# 关键限制：边权必须非负。有负权要用 Bellman-Ford（O(VE)）或 SPFA
为什么 Dijkstra 不能处理负权边？因为它基于一个假设：一旦某个节点被弹出堆，它的最短距离就已经确定。这个假设依赖"路径只会越走越长"。有了负权边，后面可能出现一条更短的路绕回来，但节点已经被标记为"已完成"不再更新了。
实际影响：如果你的图里有"优惠""返利"这类负权语义，别用 Dijkstra。

拓扑排序：依赖解析的标准解法

# Kahn 算法：不断取出"入度为 0"的节点
from collections import deque

def topo_sort(graph, n):
    indeg = [0] * n
    for u in range(n):
        for v in graph[u]:
            indeg[v] += 1

    q = deque(u for u in range(n) if indeg[u] == 0)
    order = []
    while q:
        u = q.popleft()
        order.append(u)
        for v in graph[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)

    return order if len(order) == n else None   # None 表示有环

# 用途：构建系统的依赖编译、任务调度、包管理器的安装顺序
# 副产品：如果 order 的长度小于 n，说明存在循环依赖 → 可以直接报错
模块 7

五个高频算法套路

LeetCode 有两千多道题，但真正需要"新思路"的不到一百道。剩下的都能归到这五个套路里。套路的价值是：看到题先分类，而不是从零想。

套路一：双指针

用两个指针从两端或同向移动，把 O(n²) 的枚举降成 O(n)。适用信号：数组有序、或者需要"两端逼近"。

# 典型题：盛最多水的容器
# 给定高度数组，选两条线，使它们与 x 轴围成的面积最大
def max_area(h):
    i, j = 0, len(h) - 1
    best = 0
    while i < j:
        best = max(best, min(h[i], h[j]) * (j - i))
        # 关键：移动较矮的那一边
        # 因为移动高的一边，宽度变小、高度不会变大，面积只会更小
        if h[i] < h[j]:
            i += 1
        else:
            j -= 1
    return best

# 另一类：有序数组的两数之和（左右夹逼）
def two_sum_sorted(a, target):
    i, j = 0, len(a) - 1
    while i < j:
        s = a[i] + a[j]
        if s == target: return [i, j]
        if s < target: i += 1        # 和太小，左指针右移
        else:          j -= 1        # 和太大，右指针左移
    return []

核心是"单调性论证"：为什么可以放心地丢掉一整行/一整列？因为能证明被丢掉的那些组合不可能更优。说不出这个论证，双指针就是猜的。

套路二：滑动窗口

维护一个"窗口"[left, right]，右边界扩张、左边界收缩。适用信号：求"最长/最短的满足某条件的连续子串/子数组"。

# 典型题：无重复字符的最长子串
def length_of_longest_substring(s):
    last = {}                    # 字符 → 最后一次出现的下标
    left = 0
    best = 0
    for right, ch in enumerate(s):
        if ch in last and last[ch] >= left:
            left = last[ch] + 1  # 窗口左边界跳到重复字符的下一位
        last[ch] = right
        best = max(best, right - left + 1)
    return best
两个容易写错的地方：① 收缩用 while 不用 if —— 一次扩张可能需要在左边界连续收缩多次才重新满足条件；② 答案的更新位置 —— 求最长时在收缩之后更新（此时窗口合法），求最短时在收缩循环内部更新（每次合法都要试）。

套路三：二分查找（含找边界）

二分的难点从来不是"会不会"，而是边界写不对。用一个统一的模板可以消灭 90% 的 off-by-one。

# 统一模板：左闭右开区间 [lo, hi)
# 循环条件永远是 lo < hi，区间为空时退出
# 返回 lo == hi，是"第一个满足条件的位置"

def lower_bound(a, target):
    """第一个 >= target 的下标。若全部小于 target，返回 len(a)"""
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2      # 防溢出写法
        if a[mid] < target:
            lo = mid + 1               # mid 不满足，排除
        else:
            hi = mid                   # mid 可能满足，保留
    return lo

def upper_bound(a, target):
    """第一个 > target 的下标"""
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] <= target:
            lo = mid + 1
        else:
            hi = mid
    return lo

# 三个常用查询都能用这两个函数组合出来
# 存在性：lower_bound(a, t) < len(a) and a[lo] == t
# 等于 t 的个数：upper_bound(a, t) - lower_bound(a, t)
# 第一个 > t 的位置：upper_bound(a, t)
记住三句话，二分就不会错：① 区间定义为左闭右开 [lo, hi)；② 循环条件永远写 lo < hi；③ 只有确定 mid 不可能是答案时，才写 lo = mid + 1，否则一律 hi = mid。
这个模板的返回值天然是"第一个满足条件的位置"，所以找左边界、找插入位置、找第一个大于等于的值，全部是同一个函数。

套路四：回溯

回溯就是"带撤销的 DFS"。适用信号：求所有方案（排列、组合、子集、棋盘放置）。时间复杂度通常是指数级，所以只能处理 n ≤ 20 左右的规模。

# 回溯的固定骨架：选择 → 递归 → 撤销
def permute(nums):
    res = []
    path = []
    used = [False] * len(nums)

    def dfs():
        if len(path) == len(nums):       # 终止条件
            res.append(path[:])          # 注意：必须复制，path 后面会被改
            return
        for i, x in enumerate(nums):
            if used[i]:
                continue                 # 剪枝
            used[i] = True
            path.append(x)               # 做选择
            dfs()                        # 递归
            path.pop()                   # 撤销选择
            used[i] = False

    dfs()
    return res

# 三个必须写对的地方：
# 1. 终止条件要放在最前面，且要复制结果
# 2. 撤销操作必须和选择操作严格对称
# 3. 剪枝要放在"做选择"之前，否则白跑

套路五：动态规划

DP 的全部难度在状态定义。状态定义对了，转移方程几乎是自然写出来的；定义错了，怎么写都别扭。

# 典型题：零钱兑换 —— 用最少的硬币凑出 amount
def coin_change(coins, amount):
    # 状态定义：dp[i] = 凑出金额 i 所需的最少硬币数
    dp = [float("inf")] * (amount + 1)
    dp[0] = 0                                # 边界：凑 0 元需要 0 枚

    for i in range(1, amount + 1):           # 遍历金额
        for c in coins:                      # 遍历硬币
            if c <= i:
                dp[i] = min(dp[i], dp[i - c] + 1)
    return dp[amount] if dp[amount] != float("inf") else -1

# 状态定义的三要素：
#   1. dp[i] 的含义 —— 一句话能说清，且"最优子结构"成立
#   2. 转移方程 —— dp[i] 由哪些更小的状态推出
#   3. 边界与遍历顺序 —— 保证用到的子状态已经算好
遍历顺序决定它是 01 背包还是完全背包。上面这段代码，金额在外层、硬币在内层，且内层正序，所以同一枚硬币可以被重复使用 —— 这是完全背包。
如果是 01 背包（每件物品只能用一次），必须物品在外层、容量在内层倒序。这个顺序不是风格问题，是正确性问题：倒序保证了 dp[i-c] 用的是"上一轮"的值，而不是"本轮已经被更新过"的值。
模块 8

复杂度直觉

大 O 记号只描述增长趋势，不告诉你绝对时间。工程上真正要建立的是数量级直觉：n = 100 万时，O(n²) 是几分钟还是几小时。

复杂度n = 1000n = 10 万n = 100 万典型代表
O(1)1 ns1 ns1 ns哈希查找、数组下标
O(log n)10 ns17 ns20 ns二分查找、平衡树
O(n)1 μs0.1 ms1 ms一次遍历、哈希建表
O(n log n)10 μs1.7 ms20 ms排序、堆操作 n 次
O(n²)1 ms10 s11.5 天双重循环、冒泡排序

假设每次基本操作约 1ns（约 10 亿次/秒）。真实情况还要乘以常数因子，内存访问多的话会更慢。

为什么 O(n²) 的代码在小数据上测不出问题？因为 n 从 100 涨到 10 万，是 1000 倍的数据量，但耗时涨了 100 万倍。
测试环境用 100 条数据跑，O(n²) 只要 10μs，比网络延迟还小，你根本感觉不到。上线后数据涨到 10 万条，同样的代码要 10 秒 —— 用户会以为服务挂了。
这就是"压测要用生产量级数据"的根本原因。用 1000 条数据压测，测出来的瓶颈永远是网络和框架开销，业务代码的复杂度问题被完全掩盖。

怎么快速估算

数循环嵌套层数。单层 O(n)，双层 O(n²)，三层 O(n³)。但如果内层循环的次数和外层无关（比如固定 10 次），那还是 O(n)。
看有没有"每次减半"。循环变量每次除以 2 → O(log n)。归并排序的递归树每层 O(n)、共 log n 层 → O(n log n)。
警惕隐式的循环。list.index() 是 O(n)、x in list 是 O(n)、字符串拼接 s += t 在不可变字符串语言里是 O(n)。这些在代码里看起来像 O(1)，放在循环里就是 O(n²)。
把 n 代进去算。n = 10 万时，O(n²) 是 10^10 次操作。如果每次 1ns，就是 10 秒 —— 超过 1 秒就该改。
工程上的经验阈值：单次请求的 CPU 时间超过 100ms 就该审视算法；超过 1s 基本可以确定有 O(n²) 或者 N+1 查询；如果耗时随数据量平方增长（10 倍数据 → 100 倍耗时），那一定是嵌套循环。
反过来，n 小于 100 的时候，O(n²) 和 O(n log n) 的绝对差距不到 1 微秒 —— 这时候可读性比复杂度重要，不要为了消除一个 100 次的循环去写红黑树。
常见坑

十个真实踩过的坑

1
在循环里做线性查找
list.index()、if x in list、无索引的数据库查询。单次几十微秒，被 N 次循环放大成分钟级。改成 set / dict / 加索引。
2
以为链表插入 O(1) 就一定比数组快
"找到插入位置"本身是 O(n)，而且遍历时的指针追逐可能比数组慢几十倍。默认用动态数组。
3
HashMap 不预估容量
反复扩容触发 rehash，每次都是 O(n) 停顿。已知规模时用带初始容量的构造函数。
4
用可变对象做哈希 key
对象放进 map 后又修改了参与哈希的字段，导致再也查不到（哈希值和桶位置对不上）。key 必须是不可变的。
5
自己实现哈希函数且不加随机种子
暴露在公网会被构造碰撞输入打垮（HashDoS）。用带密钥的 SipHash 或直接用标准库。
6
用有序数据插普通二叉搜索树
自增 ID、时间戳这类天然有序的输入会让 BST 退化成链表，查找从 O(log n) 变 O(n)。要用平衡树或跳表。
7
Top-K 用大顶堆
找最大的 K 个要用小顶堆，堆顶是"当前 K 个里最小的"，才能 O(1) 判断新元素该不该进来。搞反了逻辑写不通。
8
BFS 在出队时才标记 visited
同一个节点会被重复入队多次，队列膨胀、复杂度退化。必须在入队时就标记。
9
二分查找的边界写错
lo/hi 的初始值、循环条件是 < 还是 <=、mid 要不要 +1，三个地方任一写错就死循环或漏解。统一用左闭右开模板。
10
用 1000 条数据压测 O(n²) 的接口
1000 条时 1ms，10 万条时 10 秒。压测数据量必须接近生产，否则复杂度问题会被完全掩盖。
自测

六道题

1. 遍历 100 万个元素，数组和链表的理论复杂度都是 O(n)，但实测差很多。根本原因是？
正确答案：内存访问模式。数组一次读 64 字节缓存行，覆盖 16 个 int；链表每次跳转都是独立的随机地址，且地址要等上一次读取结果才知道（指针追逐），硬件预取完全失效。
2. 从 1 亿个数里找最大的 100 个，最优方案是？
正确答案：大小为 K 的小顶堆，时间 O(n log K)，内存 O(K)。堆顶必须是"当前 K 个里最小的"，才能 O(1) 判断新元素该不该进来替换。
3. InnoDB 的 B+ 树三层能存约 2000 万行，主要靠什么？
正确答案：高扇出带来矮树。非叶子节点只存 (主键, 页指针)，16KB 一页能放约 1170 项。三层就是 1170 × 1170 × 每页行数。二叉搜索树要 25 层，就是 25 次随机 IO。
4. 关于 Dijkstra，哪个说法是对的？
正确答案：要求非负边权。负权边会让"已确定"的节点还能被更短的路径更新，破坏算法的核心假设。有负权要用 Bellman-Ford。
5. 二分查找中，什么情况下才写 lo = mid + 1？
正确答案：能排除 mid 时才 +1。如果 mid 仍可能是答案（比如找左边界时 a[mid] == target 也可能是第一个），就必须写 hi = mid 保留它。这个判断是二分不出错的唯一关键。
6. 一个接口在 1000 条数据时耗时 1ms，10 万条时耗时 10 秒。最可能的原因是？
正确答案：O(n²)。数据量涨 100 倍、耗时涨 10000 倍，正好是平方关系。O(n) 的代码应该只涨 100 倍（100ms 左右）。这类问题在测试环境用 1000 条数据完全测不出来。

术语表

术语一句话解释
时间复杂度操作次数随输入规模增长的趋势，忽略常数因子
均摊复杂度把偶发的昂贵操作平摊到多次操作上，如动态数组扩容
缓存行CPU 与内存之间传输的最小单位，x86-64 上是 64 字节
指针追逐下一次访问的地址依赖上一次读取的结果，导致流水线停顿
负载因子哈希表元素数 / 桶数量，超过阈值就要扩容
rehash扩容后重新计算所有元素的位置，是一次 O(n) 停顿
开放寻址冲突时在数组内探测下一个空槽，不额外挂链表
聚集 clustering开放寻址中连续占用的区域越来越长，导致探测变慢
HashDoS构造大量哈希碰撞的输入，让哈希表退化成链表，拖垮服务
扇出 fanout树的一个节点有多少个子节点，决定树的高度
B+ 树只有叶子存数据、叶子之间有链表的 B 树变体，适合磁盘和范围查询
LSM 树写入全部顺序追加、后台合并的结构，写快读慢
写放大一次逻辑写入实际产生的物理写入量
读放大一次逻辑读取实际要访问的存储层数或文件数
完全二叉树除最后一层外都填满、最后一层靠左连续的二叉树，可直接用数组存
堆化 heapify把无序数组整理成堆，复杂度 O(n)
拓扑排序把有向无环图排成线性序列，使所有边都从前指向后
惰性删除不立即删除，只打标记，等它自然浮到处理位置时再丢弃
