整篇文章只讲一条主线：数据从设备到进程，要经过哪些搬运工。先记住下面这四类角色，后面所有细节都挂在它们身上。

模块 1

CPU 怎么和设备通信

设备上有一些"寄存器"，CPU 要读写它们来配置设备、查询状态。问题是：这些寄存器不在内存里，CPU 怎么访问？有两种历史方案。

方案一：端口 IO（Port-Mapped IO，PMIO）

x86 有一条独立的总线空间叫 IO 空间，只有 64KB（16 位地址），用专门的指令 in / out 访问。这是 8086 时代留下的设计。

# 内核里的写法（arch/x86/include/asm/io.h）
u8  val = inb(0x60);        # 从端口 0x60 读一个字节（经典键盘控制器）
outb(0x41, 0x60);           # 往端口 0x41 写
u32 v = inl(0xCF8);         # 32 位读，PCI 配置空间就是走这条路

# 用户态看端口占用（需要 root）
cat /proc/ioports | head -20
#   0000-001f : dma1
#   0060-0060 : keyboard
#   03f8-03ff : serial
#   cf8-cff   : PCI conf1

端口 IO 有三个硬伤：地址空间只有 64KB、只能一次传 1/2/4 字节（不能批量）、只有 x86 系架构有（ARM、RISC-V 根本没有这个概念）。所以现代设备几乎不用它。

方案二：内存映射 IO（Memory-Mapped IO，MMIO）

把设备的寄存器映射到物理地址空间里。CPU 用普通的 mov 指令读写这段地址，硬件（北桥 / 内存控制器）发现地址落在设备区间，就把请求转发到设备而不是内存。

# 1. 从 PCI 配置空间读 BAR，拿到设备寄存器的物理地址
lspci -vv -s 02:00.0 | grep -A2 Region
#   Region 0: Memory at f7c00000 (32-bit, non-prefetchable) [size=16K]

# 2. 驱动里映射到内核虚拟地址
void __iomem *base = ioremap(0xf7c00000, 16 * 1024);

# 3. 用专用访问函数读写（不能直接解引用指针！）
u32 status = readl(base + 0x04);
writel(0x1, base + 0x00);
u16 v = readw(base + 0x10);

# 4. 用完解除映射
iounmap(base);
为什么不能直接 *(u32*)base？三个原因：
① 编译器会优化掉。它不知道这段地址会被硬件改变，可能把多次读合并成一次，或者干脆缓存到寄存器里。readl/writel 内部有 barrier() 阻止这种优化。
② 字节序问题。设备可能是大端，readl 会做转换（readl_be 是显式大端版本）。
③ 写合并/乱序。CPU 可能重排 MMIO 写操作的顺序，而设备对寄存器写入顺序有严格要求（先写地址再写数据）。writel 保证顺序。

为什么 MMIO 成了主流

维度端口 IOMMIO
地址空间64KB，非常紧张几乎无限（用物理地址空间的一大段）
传输粒度1/2/4 字节，逐字节搬可以映射大块内存，甚至把整个显存/设备内存映射进来
指令支持专用 in/out 指令，编译器难优化普通 load/store，编译器可以做寄存器分配、批量搬运（配合 SIMD）
架构支持基本只有 x86所有架构（ARM 的 Device 内存类型、RISC-V 的 MMIO 都是这个思路）
能否被 DMA 共享不能能。这是关键：设备和 CPU 可以访问同一块缓冲区
典型用途老式串口、PS/2、PCI 配置空间（ECAM 之外的老路径）现代一切：网卡、NVMe、GPU、USB 控制器

模块 2

三种 IO 方式：轮询、中断、DMA

设备完成一次传输后，CPU 怎么知道？这就是三种方式的全部区别。它们的本质是在"CPU 时间"和"延迟"之间做不同的取舍。

轮询（Polling）

CPU 不停地读设备的状态寄存器，看"完成位"有没有置起。

writel(START, base + REG_CMD);
while (!(readl(base + REG_STATUS) & STATUS_DONE))
    cpu_relax();          # 空转，不让出 CPU
data = readl(base + REG_DATA);

优点：延迟最低（亚微秒）、实现简单、无中断开销。缺点：等待期间这个核什么都干不了，多设备并发时无法兼顾。

什么时候仍然用轮询：① 极低延迟场景（高频交易网卡、DPDK 用户态驱动）；② 设备本来就很快（NVMe 的 IO 队列轮询模式，io_poll）；③ 中断风暴时内核会临时切换到轮询（NAPI 就是"中断 + 轮询"的混合体）。

中断（Interrupt）

设备完成时拉一根中断线（或发一个 MSI-X 消息），CPU 停下当前工作，跳到中断处理程序。

# 驱动注册中断处理
request_irq(irq, my_handler, IRQF_SHARED, "mydev", dev);
# 或者 MSI-X（现代设备首选，每个队列一个中断向量）
pci_alloc_irq_vectors(pdev, 1, 64, PCI_IRQ_MSIX);

# 中断处理分两半（这是 Linux 的核心设计）
# 上半部 hardirq：关中断上下文，只能做最紧急的事（应答设备、取数据）
# 下半部 softirq/tasklet/workqueue：开中断，做耗时的后续处理

# 看中断分布（哪个 CPU 在处理哪个设备的中断）
cat /proc/interrupts
#            CPU0       CPU1       CPU2       CPU3
#  32:     123456          0          0          0   IR-PCI-MSI  nvme0q0
#  33:          0      98234          0          0   IR-PCI-MSI  nvme0q1
#  45:      54321      54322      54323      54324   IR-PCI-MSI  eth0-TxRx-0

优点：等待期间 CPU 可以跑别的进程，天然支持多设备并发。缺点：每次中断有 2~10 微秒固定开销，高频小包场景会形成中断风暴。

中断开销的量化：一次中断从设备发出到处理程序返回，典型开销 2~5 微秒（含保存寄存器、切换栈、cache 污染）。如果网卡每秒收 100 万个小包，光中断就要吃掉 2~5 秒的 CPU 时间/秒 —— 也就是 2~5 个核满载。
这就是 NAPI 存在的原因：第一个包来了用中断唤醒，之后关掉中断改用轮询，一次处理一批（默认 budget 64 个包），处理完再开中断。用"批量"摊薄了每次中断的固定开销。

DMA（Direct Memory Access）

让一个专门的硬件（DMA 引擎，通常集成在设备控制器里）直接读写内存，CPU 只负责"下命令"和"收通知"。

# 1. CPU 准备：把地址、长度、方向写进设备的 DMA 寄存器
writel(dma_addr,  base + REG_DMA_SRC);
writel(len,       base + REG_DMA_LEN);
writel(DMA_START, base + REG_DMA_CMD);

# 2. DMA 引擎搬数据，CPU 去干别的
# 3. 完成后设备发中断（或 CPU 轮询完成位，追求更低延迟）

优点：CPU 几乎不参与，吞吐可跑满总线，支持分散/聚集。缺点：占用内存带宽，cache 一致性复杂，地址翻译需要 IOMMU。

三者对比

方式CPU 占用延迟吞吐适用场景
轮询100%（等待期间）最低，亚微秒取决于 CPU 读寄存器的速度DPDK、SPDK、极低延迟交易、NVMe io_poll
中断与事件数成正比2~10 微秒低（事件频繁时被中断开销压死）低频设备：键盘、串口、管理型事件
DMA接近 0（只有配置和完成通知）取决于传输量最高，可跑满总线网卡、磁盘、GPU、声卡 —— 所有高吞吐设备
DMA + 轮询1 个核满载极低最高DPDK 的标准组合
DMA + 中断很低中等高通用服务器的事实标准
一句话记忆：轮询是"我一直盯着"，中断是"好了叫我"，DMA 是"你帮我搬，搬完叫我"。现代设备一定是 DMA + 中断，只有在追求极致延迟或中断风暴时才退化成轮询。
模块 3

DMA 工作原理

DMA 听起来简单——"设备直接读写内存"。但这里有一个致命问题：设备只认识物理地址，而 CPU 用的是虚拟地址。而且 CPU 有 cache，设备写内存时不会更新 cache。这两个问题构成了 DMA 编程的全部复杂度。

问题一：地址翻译

进程的缓冲区在虚拟地址 0x7f0000001000，对应的物理页可能是 0x1a3f000，而且可能根本不连续（分散在多个物理页）。设备不知道这些，它需要一个"总线地址"。

# 流式 DMA 的典型流程
# 1. 拿到虚拟地址对应的 DMA（总线）地址
dma_addr_t h = dma_map_single(dev, buf, len, DMA_TO_DEVICE);
if (dma_mapping_error(dev, h)) { /* 处理失败 */ }

# 2. 把 dma_handle 写进设备寄存器
writel(h, base + REG_DMA_ADDR);

# 3. 传输完成后解除映射
dma_unmap_single(dev, h, len, DMA_TO_DEVICE);

# 多段不连续内存用 scatter-gather 版本，一次映射多段
int nents = dma_map_sg(dev, sg_list, orig_nents, DMA_FROM_DEVICE);

如果有多段不连续的内存（比如 sk_buff 的线性区 + 多个分片），用 scatter-gather 版本一次映射多段：

# 分散/聚集 DMA：一次告诉设备"N 段内存，各自的地址和长度"
int nents = dma_map_sg(dev, sg_list, orig_nents, DMA_FROM_DEVICE);
# 设备按 sg_list 里的描述符逐段搬运，不需要 CPU 先把它们拼成连续内存
# 这是零拷贝能成立的关键硬件能力

问题二：cache 一致性

CPU 写数据到缓冲区时，数据可能还在 CPU 的 cache 里没落到内存。如果这时启动 DMA，设备读到的是旧数据。反过来，设备 DMA 写完内存，CPU 读到的可能是 cache 里的旧值。

Linux 把 DMA 分成两类来解决这个问题：

类型分配接口一致性怎么保证
一致性 DMA
（coherent）		dma_alloc_coherent()
dma_free_coherent()		分配的内存默认不做 cache（或 write-combine），CPU 和设备看到的内容永远一致，不需要手动同步
流式 DMA
（streaming）		dma_map_single()
dma_map_sg()
dma_sync_*()		用普通可 cache 内存，靠 map/unmap 时的 cache 刷新来保证。需要严格的所有权切换
# 一致性 DMA：适合长期存在的描述符环、控制结构
ring = dma_alloc_coherent(dev, RING_SIZE * sizeof(*ring), &ring_dma, GFP_KERNEL);
# ring 是 CPU 看到的地址，ring_dma 是设备看到的地址，指向同一块物理内存

# 流式 DMA：适合一次性数据缓冲区（性能更好，因为能用 cache）
# 发送方向：CPU 写 → 刷 cache → 交给设备
memcpy(buf, data, len);
dma_map_single(dev, buf, len, DMA_TO_DEVICE);   # 内部会 clean cache
# ... 启动 DMA，等待完成 ...
dma_unmap_single(dev, addr, len, DMA_TO_DEVICE);

# 接收方向：设备写 → 无效化 cache → CPU 读
dma_map_single(dev, buf, len, DMA_FROM_DEVICE);
# ... 启动 DMA，等待完成 ...
dma_unmap_single(dev, addr, len, DMA_FROM_DEVICE);  # 内部会 invalidate cache
# 此时 CPU 才能安全读到设备写入的数据
流式 DMA 最容易出的 bug：忘记同步。
典型症状：设备明明写了数据，CPU 读到的却是全 0 或旧内容；或者 CPU 改了描述符，设备视而不见。
规则：缓冲区在"CPU 拥有"和"设备拥有"之间切换时，必须调用 dma_sync_single_for_device() 或 dma_sync_single_for_cpu()。
另一个陷阱：在 DMA 进行期间，CPU 绝对不能碰这块缓冲区。这不是"最好不要"，而是会读到半新半旧的数据（tearing）。

IOMMU：DMA 的地址翻译与保护

没有 IOMMU 时，设备拿到的是物理地址。这带来三个问题：① 32 位设备无法访问 4GB 以上的内存；② 驱动要给设备分配物理连续的大块内存（很难）；③ 设备可以 DMA 到任意物理地址，一个恶意或有 bug 的设备能读写整个内存。

IOMMU（Input/Output Memory Management Unit）就是给设备用的 MMU：

能力说明
地址翻译设备用 IOVA（IO 虚拟地址），IOMMU 翻译成物理地址。驱动可以给设备"看起来连续"的地址，实际映射到任意分散的物理页
访问隔离每个设备只能访问自己页表里映射的地址。越界访问被 IOMMU 拦截，产生 DMA fault 而不是静默损坏内存
支持 32 位设备把高地址内存映射到设备可见的低 32 位 IOVA，老设备也能用大内存
虚拟化直通把物理设备直接分配给虚拟机（VFIO），IOMMU 保证虚拟机只能访问自己的内存
# 检查 IOMMU 是否启用
dmesg | grep -i -E 'DMAR|IOMMU'
#  DMAR: IOMMU enabled
#  DMAR: Intel(R) Virtualization Technology for Directed I/O

# 看 IOMMU 分组（同组设备共享一个地址空间）
for g in /sys/kernel/iommu_groups/*; do
  echo "Group $(basename $g):"; ls $g/devices/
done

# 内核启动参数（要显式开启）
# Intel: intel_iommu=on    AMD: amd_iommu=on
# 关闭：intel_iommu=off    （性能敏感场景下有人关掉，但失去了隔离保护）
IOMMU 有性能代价。每次 DMA 都要走一遍页表翻译（有 IOTLB 缓存缓解）。所以：① 现代网卡支持 ATS/ATC，把翻译结果缓存在设备侧；② 内核支持 IOVA 大页和懒刷 TLB（iommu.strict=0）；③ 一些高频交易系统直接关掉 IOMMU 换性能，代价是失去 DMA 攻击防护。
模块 4

零拷贝与 DMA 的关系

"零拷贝"这个词被用得很滥。严格说它不是零次拷贝，而是零次 CPU 拷贝。DMA 拷贝仍然存在，只是不占 CPU。搞清楚这一点，才能判断什么场景该用它。

传统 read + write：4 次拷贝，4 次上下文切换

# 应用代码
n = read(fd, buf, len);        # 系统调用 1
write(sockfd, buf, len);       # 系统调用 2

# 4 次拷贝：DMA(磁盘→page cache) → CPU(page cache→用户缓冲)
#           → CPU(用户缓冲→socket 缓冲) → DMA(socket→网卡)
# 4 次用户态/内核态切换（read 进、read 出、write 进、write 出）
步骤动作谁在搬
1DMA：磁盘 → 内核 page cacheDMA
2CPU：page cache → 用户缓冲区CPU（read 返回）
3CPU：用户缓冲区 → socket 发送缓冲区CPU（write 调用）
4DMA：socket 缓冲区 → 网卡DMA

共 4 次拷贝（2 次 DMA + 2 次 CPU），4 次用户态/内核态切换（read 进、read 出、write 进、write 出）。数据在内存里被搬了 4 遍，其中 2 遍纯属浪费。

sendfile：2 次拷贝，2 次切换

# 应用代码
sendfile(sockfd, filefd, NULL, len);   # 一次系统调用搞定

# 内核内部：数据根本不进用户态
# 1. DMA：磁盘 → page cache
# 2. DMA：page cache → 网卡（通过 SG-DMA，网卡直接从 page cache 读）
步骤动作谁在搬
1DMA：磁盘 → page cacheDMA
2DMA（SG）：page cache → 网卡DMA

省掉了两次 CPU 拷贝（步骤 2 和 3），也省掉了两次上下文切换。但前提是网卡支持 SG-DMA（scatter-gather DMA） —— 它需要能直接按"物理页列表"去内存里取数据，而不是要求一段连续内存。

为什么 SG-DMA 是关键：page cache 的数据在物理内存里是分散的。网卡若只能读连续内存，内核就得先 CPU 拷贝拼成连续块，零拷贝就不成立。SG-DMA 让网卡按描述符表逐段取，把"拼接"下放给硬件。检查：ethtool -k eth0 | grep scatter-gather

其他零拷贝方案对比

方案CPU 拷贝次数限制
read + write2无（但最慢）
sendfile0不能修改数据内容；只能文件 → socket
MSG_ZEROCOPY0发送方向；需要网卡支持；有完成通知的复杂度

# 用 perf 看 CPU 时间花在哪（零拷贝方案里 memcpy 应该显著减少）
perf top -e cycles -g
# 搜 __memcpy_avx_unaligned / copy_user_enhanced_fast_string

# Nginx 的配置（sendfile 默认开）
# sendfile on;
# tcp_nopush on;    # 配合 sendfile，凑满一个 MSS 再发
零拷贝不是万能的。三个边界：
① 需要修改数据就不能用。sendfile 要求数据原样转发。要加 HTTP 头、要压缩、要加密，就得回到用户态。
② 小文件收益小。省下的 CPU 拷贝时间可能还不如系统调用本身的开销。
③ 依赖硬件。没有 SG-DMA 的网卡，内核会退化成"CPU 拷贝到连续缓冲区"，你以为开了零拷贝，实际没开。
模块 5

网卡收包全路径

这条路径把 DMA、中断、软中断、NAPI 全串起来了。理解了它，rx_dropped 增长、单核软中断 100%、PPS 上不去这些问题的原因就很清楚。

网卡收帧。PHY 解出信号，MAC 校验 FCS，确认是发给自己的，放入网卡内部 FIFO。
DMA 写入环形缓冲区。按 RX 描述符环里的空闲缓冲区地址，用 DMA 把帧写进内存，完全不经过 CPU。环大小由 ethtool -g 控制，典型 256~4096 个描述符。
发中断。更新描述符状态位后发 MSI-X 中断；开了中断合并则攒几个包再发一次。
硬中断只做最少的事。关闭该队列中断、标记"有活要干"、调度 NAPI，然后立刻返回。
软中断 NAPI 轮询。net_rx_action 调驱动的 poll()，一次最多取 budget（默认 64） 个描述符，为每个包分配 sk_buff，取完再开中断。
GRO 与协议栈。同流小包先合并，再走 netif_receive_skb → ip_rcv → tcp_v4_rcv，数据进入 socket 接收队列并唤醒进程 —— 此时已多了一次拷贝。

关键参数与观测点

参数 / 指标含义与调优方向
ethtool -g eth0RX/TX 环形缓冲区大小。丢包时调大（但吃内存：4096 × 2KB ≈ 8MB/队列）
ethtool -c eth0中断合并。延迟敏感调小，吞吐敏感调大
net.core.netdev_budget一次软中断最多处理多少个包（默认 300）
rx_dropped驱动层丢弃（环形缓冲区满）→ 调大 ring
rx_missed_errors网卡 FIFO 溢出，DMA 来不及写内存 → PCIe / 内存带宽瓶颈
softnet_stat 第 2 列软中断处理不过来（budget 用完丢弃）
# 1. 环形缓冲区与丢包计数
ethtool -g eth0
ethtool -S eth0 | grep -E 'drop|miss|error|fifo'

# 2. 软中断有没有堆积（第 2 列是 drop 计数，16 进制）
cat /proc/net/softnet_stat

# 3. 软中断 CPU 占用（si 列高就是它）
top -d 1

# 4. 中断在各核的分布（是否集中在一个核）
cat /proc/interrupts | grep eth0
ethtool -l eth0        # 有几个队列

# 5. 把队列 0 绑到 CPU 2
echo 4 > /proc/irq/$(cat /proc/interrupts | grep 'eth0-TxRx-0' | cut -d: -f1)/smp_affinity
最常见的网卡性能问题：所有软中断挤在一个核上。
原因：① 网卡只有一个 RX 队列（没开 RSS）；② 多队列但 irqbalance 把中断都分到 CPU0；③ 容器里看不到真实分布。
解法：ethtool -L eth0 combined N → 分散中断亲和性 → 配合 RPS（.../queues/rx-0/rps_cpus）。RPS 只分散软中断，硬中断仍在一个核上。
模块 6

磁盘 IO 全路径

磁盘路径比网卡多了一层"调度"和"合并"，因为块设备天然随机访问。blk-mq（多队列块层）是 4.20 之后的标准实现。

VFS + 文件系统。vfs_write 找到 inode，ext4/xfs 把"文件偏移"翻译成"块号"。写操作先写 page cache（此时 write 就返回了），读操作先查 cache。
回写。脏页由内核线程定期（默认 30 秒）或在脏页比例超阈值时批量落盘。
构造 bio 进入 blk-mq。bio 描述"哪些块 ↔ 哪些内存页"，被转换成 request，先进软件队列（每 CPU 一个，无锁），再分发到硬件队列。
IO 调度。在软件队列和硬件队列之间做合并与排序。NVMe 通常用 none，机械盘用 mq-deadline 或 bfq。
驱动下发。写进设备提交队列（NVMe 的 SQ），按门铃通知设备。设备内部还有 FTL、垃圾回收、磨损均衡 —— 这是"盘慢"但系统指标看不出来的地方。
完成中断。设备 DMA 写数据、更新完成队列、发 MSI-X；驱动在 BLOCK_SOFTIRQ 里调用 bi_end_io 解锁页面并唤醒进程。

四层队列，四个瓶颈点

队列位置满了会怎样
page cache 脏页内存达到 dirty_ratio 后写操作同步阻塞等回写（"write 突然变慢"的常见原因）
硬件队列 / tag每设备队列最常见的瓶颈。队列满后新请求排队，表现为 await 与 aqu-sz 上升
设备内部队列SSD 控制器设备自己排队，系统层面看不出来，只能从延迟推断
# 调度器（方括号是当前选中）与队列深度
cat /sys/block/nvme0n1/queue/scheduler
# [none] mq-deadline kyber bfq
cat /sys/block/nvme0n1/queue/nr_requests

# 关键观测指标
iostat -xz 1
#  await：平均完成时间（含排队）—— 涨了说明积压
#  %util：设备忙的占比 —— 对 SSD 意义不大，对机械盘是硬指标
#  aqu-sz：平均队列长度 —— 持续大于深度一半说明饱和

# 区分"排队"和"设备慢"
bpftrace -e '
tracepoint:block:block_rq_issue { @s[args->dev, args->sector] = nsecs; }
tracepoint:block:block_rq_complete /@s[args->dev, args->sector]/
{
  @us[comm] = hist((nsecs - @s[args->dev, args->sector]) / 1000);
  delete(@s[args->dev, args->sector]);
}'
SSD 的 %util 会骗人。一块 NVMe 可以并行处理几十万个 IO，%util 100% 时可能还有余力。判断饱和要看 await 是否随负载线性上升。
另外 SSD 用久了会因写放大和垃圾回收变慢，但 iostat 看不出原因 —— 用 smartctl 看 Percentage_Used。
模块 7

设备驱动模型：/dev、/sys、udev、设备号

三者的职责完全不同：/dev 是"怎么用这个设备"，/sys 是"这个设备是什么"，udev 是"设备插进来时该做什么"。

/dev 与 /sys 的分工

位置本质用途
/dev设备节点文件（字符设备 / 块设备）读写设备。open("/dev/nvme0n1") 就能操作磁盘。只有带设备号的文件，没有属性
/syssysfs，内核对象树的映射查询和配置设备。看设备型号、驱动、电源状态、队列参数；也能写（如调 scheduler）
/procprocfs，进程和内核状态进程信息 + 部分全局统计（/proc/interrupts、/proc/iomem）
# /dev 里是"文件"，ls -l 能看到类型和设备号
ls -l /dev/nvme0n1
# brw-rw---- 1 root disk 259, 0 ... /dev/nvme0n1
#                          ^^^  ^  major / minor
# brw- = 块设备，crw- = 字符设备

# /sys 是目录树，每个目录是一个内核对象
cat /sys/class/net/eth0/address     # MAC
cat /sys/class/net/eth0/speed       # 10000 (Mbps)
cat /sys/class/net/eth0/statistics/rx_dropped

设备号：major 与 minor

内核用一对数字标识设备：major 决定用哪个驱动，minor 决定是该驱动管理的第几个实例。

# 看当前系统的设备号分配
cat /proc/devices
# Character devices:
#   1 mem
#   4 tty
#   5 /dev/tty
#  Block devices:
#   8 sd
# 259 blkext          <-- NVMe 走这个"动态分配"的段

# 常见固定分配（记几个有用的）
#   8:0   = /dev/sda     8:1 = /dev/sda1
#   8:16  = /dev/sdb     8:17 = /dev/sdb1
#   1:3   = /dev/null    1:5 = /dev/zero    1:8 = /dev/random
#   4:0   = /dev/tty0    4:64 = /dev/ttyS0

# 手动创建设备节点（调试时有用，正常由 udev 做）
mknod /tmp/mydev c 240 0    # c = 字符设备，240 是 major，0 是 minor

udev：设备热插拔的响应者

内核发现新设备时，会通过 netlink 发一个 uevent。udev（现在是 systemd-udevd）收到后，按规则文件决定"要创建什么节点、设什么权限、跑什么脚本"。

# 规则目录（按文件名排序，先匹配先生效）
/etc/udev/rules.d/       # 本机自定义，优先级最高
/usr/lib/udev/rules.d/   # 发行版/软件包提供

# 典型规则：固定名字、权限、符号链接
SUBSYSTEM=="usb", ATTRS{idVendor}=="1234", ATTRS{idProduct}=="5678", \
  SYMLINK+="myusb", MODE="0666"
SUBSYSTEM=="block", KERNEL=="nvme0n1", SYMLINK+="ssd0"

# 调试：写规则前先看设备属性；改完重新加载
udevadm info -a -n /dev/nvme0n1 | head -40
udevadm test /sys/class/block/nvme0n1
udevadm control --reload-rules && udevadm trigger
为什么需要 udev：设备名（sda、sdb）是按发现顺序分配的，重启后可能变。如果你在 fstab 里写了 /dev/sdb1，某天加了块盘，系统就起不来了。
现代做法：用 /dev/disk/by-uuid/、/dev/disk/by-label/、/dev/disk/by-path/ 这些符号链接 —— 它们由 udev 根据设备属性生成，跨重启稳定。

常见坑

十个认知陷阱

1
以为 DMA 是"零开销"
DMA 省 CPU 时间，占内存带宽。带宽打满时 CPU 也会因为等内存而变慢。
2
直接解引用 ioremap 返回的指针
必须用 readl/writel。直接读写会被编译器优化掉，或者因为乱序导致设备收到错误的寄存器写入顺序。
3
DMA 传输期间 CPU 还去读写缓冲区
会读到半新半旧的数据（tearing）。所有权必须严格交接：map 之后 CPU 不碰，unmap 之后设备不碰。
4
流式 DMA 忘了 dma_sync
设备写了数据，CPU 读到旧值；或者 CPU 改了描述符，设备看不到。凡是缓冲区在两边来回交接，都要显式同步。
5
以为 sendfile 一定是零拷贝
需要网卡支持 SG-DMA，否则内核退化成 CPU 拷贝到连续缓冲区。用 ethtool -k 确认 scatter-gather 是 on。
6
看到 %util 100% 就认为磁盘到极限了
SSD 可以并行处理大量 IO，%util 100% 时可能还有余力。要看 await 是否随负载线性上升，以及 aqu-sz 是否持续高位。
7
网卡丢包就只调大 ring buffer
rx_dropped 涨是 ring 满，调大有效；但 rx_missed_errors 涨是 PCIe/内存带宽不足，调 ring 没用，要查链路速率和 NUMA 归属。
8
把 cache 不一致当成驱动 bug
设备写了数据 CPU 读到旧值，八成是流式 DMA 少调了 dma_sync，不是驱动写错了。先检查所有权交接。
自测

六道题

1. MMIO 相比端口 IO 的核心优势不包括？
正确答案："比普通内存更快"是错的。MMIO 访问通常比访问 DRAM 更慢（要走总线、不能 cache、有写屏障）。它的优势是空间大、可批量、跨架构、能和 DMA 共享缓冲区。
2. 一致性 DMA（dma_alloc_coherent）和流式 DMA 的关键区别是？
正确答案：cache 策略不同。一致性 DMA 牺牲 cache 换取"不用手动同步"，适合描述符环这类长期共享的结构；流式 DMA 用可 cache 内存（性能更好），但必须在所有权切换时显式 dma_sync。
3. 传统 read + write 发送文件，一共几次 CPU 拷贝？
正确答案：2 次 CPU 拷贝。全程 4 次拷贝：2 次 DMA + 2 次 CPU。sendfile 把 CPU 拷贝降到 0。
4. NAPI 的核心思想是？
正确答案：中断 + 批量轮询的混合。用中断避免空闲时的开销，用轮询摊薄高频场景下每次中断的固定成本。budget 默认 64，控制一次处理多少包。
5. IOMMU 不提供下面哪个能力？
正确答案：不提高带宽。IOMMU 做翻译和访问控制，反而引入翻译开销（靠 IOTLB 缓解）。它带来的是安全性、地址灵活性和虚拟化能力。
6. ethtool -S 显示 rx_missed_errors 持续增长，最可能的原因是？
正确答案：FIFO 溢出。rx_dropped 是 ring 满（调大 ethtool -g）；rx_missed_errors 是网卡内部 FIFO 溢出，说明 DMA 写内存跟不上收包 —— 查 PCIe 链路（LnkSta）、NUMA、内存带宽。

术语表

术语一句话解释
MMIO把设备寄存器映射到物理地址空间，用普通 load/store 访问
DMA直接内存访问，让设备绕过 CPU 直接读写内存
一致性 DMA不做 cache 的 DMA 内存，CPU 与设备视图永远一致
流式 DMA用可 cache 内存，靠 map/unmap 时刷 cache 保证一致性
scatter-gather一次 DMA 传输多段不连续内存，是零拷贝的硬件基础
IOMMU给设备用的 MMU，做 DMA 地址翻译和访问隔离
NAPILinux 网卡的中断+轮询混合机制，用批量处理摊薄中断开销
环形缓冲区 ring网卡 RX/TX 描述符数组，大小决定能缓冲多少个未处理包
中断合并攒够 N 个包或等 M 微秒再发一次中断，用延迟换 CPU
blk-mqLinux 多队列块层，每 CPU 一个软件队列，每设备队列一个硬件队列
设备号 major/minormajor 决定用哪个驱动，minor 决定是该驱动的第几个实例
udev监听内核 uevent，按规则创建设备节点、设权限、建符号链接
PIOProgrammed IO，CPU 亲自逐字节搬数据，不用 DMA 的老方式
零拷贝严格说是"零次 CPU 拷贝"，DMA 拷贝仍在，只是不占 CPU
中断亲和性指定某个中断由哪个 CPU 处理，用来把软中断分散到多核
下一步怎么练：在一台 Linux 上做五件事 —— ① 用 lspci -vv 找出所有设备的链路速率，看看有没有跑在 x1 上的；② 用 ethtool -S 和 /proc/net/softnet_stat 判断你的网卡有没有丢包；③ 用 bpftrace 追一次块层 IO 的完整耗时，画出直方图；④ 写一个 udev 规则，给某块盘建一个固定名字的符号链接；⑤ 用 strace -c 对比 read+write 和 sendfile 的系统调用次数与耗时。
