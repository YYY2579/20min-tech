开始前

三个随手可用的工具

编码问题全部发生在字节层面。只要你能看到字节，问题就已经解决一半。所以第一个要练的不是概念，是"怎么看字节"。

# 1. hexdump：看文件的原始字节（-C 表示同时显示 ASCII 侧栏）
printf '中文' | hexdump -C
# 00000000  e4 b8 ad e6 96 87      |......|
#           ↑"中" 3 字节  ↑"文" 3 字节

# 2. file：让系统猜一下编码（-i 输出 MIME + charset）
file -i somefile.txt
# somefile.txt: text/plain; charset=utf-8

# 3. iconv：转码。这是唯一正确的"修乱码"工具
iconv -f GBK -t UTF-8 in.txt -o out.txt
# -f 是"输入字节的真实编码"，-t 是"你想要的目标编码"

# 4. Python：验证字节序列是否合法
python3 -c "open('somefile.txt','rb').read()[:16]"
python3 -c "print('中文'.encode('utf-8'))"
iconv -f 填的是"字节实际是什么编码"，不是"我希望它是什么编码"。这一步填错，输出只会是另一种乱码。很多人反复转码越转越乱，就是因为把 -f 和 -t 搞反了，或者把已经是 UTF-8 的文件当成 GBK 又转了一次。
模块 1

字符集与编码不是一回事

这是整篇最重要的一句话：字符集解决"有哪些字符、编号是多少"，编码解决"编号怎么变成字节"。这两个问题被混为一谈，后面所有概念都会糊。

概念定义例子
字符集
charset		一组字符，加上每个字符的唯一编号（码点，code point）Unicode 给"中"分配的编号是 U+4E2D（十进制 20013）
编码
encoding		把码点映射成字节序列的规则UTF-8 把 U+4E2D 变成 3 个字节 E4 B8 AD

同一个字符集可以有多种编码。Unicode 是一个字符集，UTF-8 / UTF-16 / UTF-32 是它的三种编码方式。所以"把文件转成 Unicode"这句话是不成立的 —— 你只能说"转成 UTF-8"。

# 字符 "中" 在不同编码下的字节
码点:      U+4E2D          # 十进制 20013，这是"编号"，和编码无关
UTF-8:     E4 B8 AD        # 3 字节
UTF-16BE:  4E 2D           # 2 字节
UTF-16LE:  2D 4E           # 2 字节（字节序相反）
GBK:       D6 D0           # 2 字节

# 关键结论：同一个字，不同编码下的字节完全不同。
# 拿到一串字节，不告诉你编码，你无法确定它是什么字。
为什么"字节 + 编码"才能确定文本？因为字节本身没有自描述能力。D6 D0 在 GBK 里是"中"，在 Latin-1 里是两个带重音的拉丁字符，在某些二进制协议里可能是两个整数。
这就是所有乱码的根源：写的时候用一种规则，读的时候用了另一种规则。没有任何魔法能从字节里"猜出"编码 —— 工具只能基于统计做概率猜测，猜错的概率不低（尤其是短文本）。

码点的边界要知道

区间大小内容
U+0000 – U+007F128ASCII 全部内容（英文、数字、基本标点、控制字符）
U+0080 – U+07FF1920拉丁扩展、希腊字母、西里尔字母、阿拉伯字母
U+0800 – U+FFFF63488中日韩汉字、全角标点、大部分常用符号都在这里（基本多文种平面 BMP）
U+10000 – U+10FFFF1048576emoji、部分生僻汉字（如 𠮷 U+20BB7）、音乐符号（增补平面）

记住第三行和第四行的分界（U+FFFF）非常重要：UTF-16 在 BMP 内是 2 字节，超出 BMP 就要用 4 字节（代理对）；而 MySQL 的 utf8 最大只支持 3 字节，所以它存不了第四行的任何字符。这是模块 7 要展开的坑。

一个反直觉的事实：UTF-8 存中文比 GBK 多用 50% 的空间（3 字节 vs 2 字节）。那为什么还用 UTF-8？因为它兼容 ASCII —— 纯英文内容只占 1 字节，而 GBK 里的英文也是 1 字节，但 GBK 只覆盖中文圈。对于以英文为主的互联网内容，UTF-8 整体更省，而且它是唯一一个"全世界都能用同一套规则读写"的编码。

UTF-8 的长度规则（必须记住）

UTF-8 的长度由码点所在的区间决定，规则非常规整：

# 首字节的高位比特直接告诉你这个字符有几个字节
1 字节:  0xxxxxxx                              # U+0000 – U+007F
2 字节:  110xxxxx 10xxxxxx                     # U+0080 – U+07FF
3 字节:  1110xxxx 10xxxxxx 10xxxxxx            # U+0800 – U+FFFF
4 字节:  11110xxx 10xxxxxx 10xxxxxx 10xxxxxx   # U+10000 – U+10FFFF

# 验证 "中" = U+4E2D = 二进制 0100 1110 0010 1101
# 落在第三档，取 16 位填进模板：
11100100  10111000  10101101
= E4        B8        AD          # 和 hexdump 看到的完全一致
这个规则有个极其实用的推论：所有多字节字符的后续字节都以 10 开头（即落在 0x80–0xBF 区间）。所以只要一个字节的最高两位不是 10，它就是某个字符的首字节。
这意味着：UTF-8 可以自同步。即使你在流的中间开始读，也能在最多 3 个字节内找到字符边界。这是 UTF-8 能被广泛用于网络传输和日志切割的根本原因 —— 而 GBK 做不到（两个字节都可能是首字节，无法自同步）。
模块 3

乱码的三大成因

所有乱码都能归到这三类。看到乱码先分类，比盲目转码有效一百倍。

成因一：编码不匹配

用 A 编码写入，用 B 编码读取。这是最常见的一类，特征是整段文字全乱，但长度看起来差不多。

# 用 Python 复现：UTF-8 的字节，用 GBK 去解
>>> b = "中文".encode("utf-8")
>>> b
b'\xe4\xb8\xad\xe6\x96\x87'

>>> b.decode("gbk")           # 6 个字节被当成 3 个 GBK 汉字
'涓枃'                        # 结果"看起来还是汉字"，但完全没意义

# 反过来：GBK 的字节，用 UTF-8 去解
>>> b2 = "中文".encode("gbk")
>>> b2
b'\xd6\xd0\xce\xc4'

>>> b2.decode("utf-8")        # 直接失败，因为 D6 不是合法的 UTF-8 首字节
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd6 in position 0:
    invalid continuation byte
注意这两种情况的表现完全不同：
UTF-8 字节用 GBK 解 → 得到一串"像汉字但读不通"的字符（因为 GBK 的编码空间几乎覆盖所有字节组合）。这类乱码最难发现，因为它不报错。
GBK 字节用 UTF-8 解 → 通常直接抛异常（因为 UTF-8 有严格的格式校验）。报错反而是好事，说明问题暴露了。
推论：不报错的乱码比报错的乱码危险得多。

修复：用正确的编码重新解一次。前提是原始字节还在。

# 命令行修复：GBK 文件转 UTF-8
iconv -f GBK -t UTF-8 broken.txt -o fixed.txt

# Python 修复：已经是 str 就没救了，必须拿回原始 bytes
raw = open("broken.txt", "rb").read()
fixed = raw.decode("gbk")          # 用正确编码解
open("fixed.txt", "w", encoding="utf-8").write(fixed)

成因二：截断

按字节截断一个多字节字符，会留下半个字符。特征是末尾出现一个"�"（替换字符）或者直接报错，前面的内容完全正常。

# "中文" 的 UTF-8 是 6 个字节，按 4 字节截断会切在"文"的中间
>>> b = "中文".encode("utf-8")
>>> b[:4]
b'\xe4\xb8\xad\xe6'          # E6 是"文"的首字节，但后面两个字节被切掉了

>>> b[:4].decode("utf-8")
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe6 in position 3:
    unexpected end of data

# 如果程序用 errors="replace" 容错，就会变成 "中�"
>>> b[:4].decode("utf-8", errors="replace")
'中�'

截断在工程里出现的位置非常固定：

  • 日志切割：按固定字节数切分日志文件，切点落在字符中间
  • 数据库字段长度：VARCHAR(10) 在某些配置下按字节算，中文只够存 3 个
  • 消息队列的消息体上限：超过 1MB 按字节截断
  • 前端展示：substr(str, 0, 20) 在 PHP / JS 里是按字节或按 UTF-16 码元，都可能切坏
正确做法：永远按"字符"截断，不按"字节"。
Python：s[:10]（对 str 切片就是按字符）
Java：s.codePointCount() + offsetByCodePoints()，不要用 substring（它按 UTF-16 码元，emoji 会被切一半）
MySQL：LEFT(col, 10) 和 SUBSTRING(col, 1, 10) 都是按字符算的，安全
如果必须在字节层面截断（比如协议限制），从截断点往回退，退到第一个非续字节（最高两位不是 10）为止。

成因三：双重编码

把已经是 UTF-8 的字节，当成 Latin-1 解码成"字符"，再把这些"字符"重新编码成 UTF-8。结果每个字节都被单独处理了一遍，长度翻倍。

# 复现：这就是经典的 "ä¸­æ–‡" 型乱码
>>> s = "中文"
>>> s.encode("utf-8").decode("latin-1")
'ä¸\xadæ–‡'                    # 6 个字节变成 6 个 Latin-1 字符

>>> _.encode("utf-8")
b'\xc3\xa4\xc2\xb8\xc2\xad\xc3\xa6\xe2\x80\x93\xc2\xa1'
# 6 字节膨胀成 12 字节 —— 这就是"长度翻倍"的特征
乱码形态典型成因识别特征
ä¸­æ–‡双重编码（UTF-8 → Latin-1 → UTF-8）字节长度是正常值的 2 倍，字母带一堆重音符号
涓枃UTF-8 字节被 GBK 解码看起来是汉字，但语义完全不通，长度约为正常值的 2/3
中�截断只有末尾出问题，前面完全正常
?????目标编码无法表示该字符（如 GBK 存 emoji）整段变成问号，原始信息已丢失，不可逆
&#20013;&#25991;HTML 实体被转义了两次能看到 &# 开头的数字
双重编码是可以反向修复的，这是它和其他乱码最大的区别。因为信息没丢，只是多套了一层。修复方法就是把那一步反过来：
fixed = broken.encode("latin-1").decode("utf-8")
但要注意：如果 broken 里含有 Latin-1 无法表示的字符（U+0080–U+009F 之外的一些），encode("latin-1") 会失败。这时候用 errors="replace" 会丢数据，更好的选择是试 cp1252（Windows-1252，Latin-1 的超集）。
最危险的一种情况：?????。这表示在写入的时候，目标编码无法表示原字符，信息被永久丢弃了。比如把 emoji 写进一个 GBK 编码的字段，或者在转码时用了 iconv -c（丢弃无法转换的字符）。
这种情况不可逆 —— 只能重新取数据。所以排查乱码时，"能不能修复"的第一个判断就是：看是不是问号。是问号就别浪费时间了。
模块 4

BOM 是什么，什么时候是坑

BOM（Byte Order Mark，字节序标记）是文件开头用来声明"我是 UTF-16，而且是大端/小端"的几个字节。它在 UTF-8 里完全没有存在的必要，但 Windows 的工具链习惯性地加它。

编码BOM 字节说明
UTF-8EF BB BF对应 U+FEFF。UTF-8 无字节序问题，这个 BOM 纯粹是历史包袱
UTF-16 LEFF FE小端。x86 和 Windows 默认
UTF-16 BEFE FF大端。网络字节序
UTF-32 LE / BEFF FE 00 00 / 00 00 FE FF少见，但存在

U+FEFF 这个码点原本叫 ZERO WIDTH NO-BREAK SPACE（零宽不换行空格），后来被重新定义为 BOM。所以文件中间的 U+FEFF 是零宽空格，文件开头的 U+FEFF 才是 BOM —— 这个区别在某些解析器里会造成很诡异的行为。

为什么 Windows 记事本会加

历史原因：早期 Windows 的默认编码是本地代码页（中文系统上是 GBK/CP936），记事本需要一个明确的标记来区分"这是 UTF-8"和"这是 ANSI"。BOM 就是这个标记。在 UTF-8 还没有成为事实标准的年代，这是合理的工程妥协。

现在的问题是这个习惯保留了下来，而其他所有平台都默认"UTF-8 文件不带 BOM"。

四个真实的坑

JSON 文件带 BOM 会解析失败。RFC 8259 明确规定「Implementations MUST NOT add a byte order mark to the beginning of a JSON text」。严格实现的解析器（包括 Python 的 json.load 读二进制流时）会把 EF BB BF 当成非法字符。解法：用 encoding="utf-8-sig" 读，它会自动跳过 BOM。
Shell 脚本开头有 BOM 会跑不起来。内核检查文件头时，看到的不是 #! 而是 EF BB BF，execve 直接返回 ENOEXEC。报错信息通常不指向真正原因（"bad interpreter" 或 "cannot execute binary file" 之类），能让人排查半天。
PHP 文件带 BOM 会让 header() 失效。BOM 在 <?php 之前被当成输出发给浏览器，导致 "headers already sent" 错误。同样的问题也出现在任何"输出前不能有内容"的场景。
CSV 带 BOM 会让第一列列名变成 \ufeffid。Excel 能正常显示（它靠 BOM 识别 UTF-8），但程序读进来后第一列的键名多了个不可见字符，row["id"] 取不到值。
# 检查有没有 BOM：看文件前 3 个字节
head -c 3 file.txt | hexdump -C
# 有 BOM：00000000  ef bb bf
# 没 BOM：00000000  7b 0a 20  （{ 换行 空格，正常内容）

# 去掉 BOM（GNU sed）
sed -i '1s/^\xEF\xBB\xBF//' file.txt

# 或者用 tail 直接跳过前 3 字节（更安全，不依赖 sed 实现）
tail -c +4 file.txt > file.clean.txt

# Python 读取时自动跳过
open("data.json", encoding="utf-8-sig").read()

# Python 写入时明确不加 BOM（utf-8 就是不加，utf-8-sig 才会加）
open("out.json", "w", encoding="utf-8").write(data)
结论：不要主动写 BOM。
① 新建文件一律用无 BOM 的 UTF-8；
② 读别人给的文件时要能容忍 BOM（用 utf-8-sig 或在入口处剥掉）；
③ 唯一的例外是给 Excel 看的 CSV —— 加 BOM 反而是必要的，否则 Excel 会用本地代码页打开，中文全乱。
模块 5

中文排序与比较

"为什么 ORDER BY name 排出来的中文顺序是乱的" —— 因为它排的不是拼音，是编码值。

默认排序排的是什么

-- 三个名字，按 Unicode 码点比较
张  U+5F20
李  U+674E
王  U+738B

-- 码点顺序：张(5F20) < 李(674E) < 王(738B)
-- 拼音顺序：李(li) < 王(wang) < 张(zhang)

-- 所以 ORDER BY name 得到的是「张 李 王」，不是拼音序

在 MySQL 里，ORDER BY 使用的比较规则叫 collation（排序规则）。它决定了"两个字符串谁大"，包含三个维度：

维度取值含义
字符集utf8mb4 / gbk / latin1collation 必须属于某个字符集，不能跨字符集比较
语言/地区general / 0900_ai_ci / zh_0900按哪种语言的习惯排序。中文、日文、德文的规则都不同
敏感性ci / cs / ai / asci=不区分大小写，cs=区分；ai=不区分重音，as=区分
-- 看当前库/表/列用的什么 collation
SHOW VARIABLES LIKE 'collation%';
SHOW TABLE STATUS LIKE 'users'\G
SHOW FULL COLUMNS FROM users;

-- MySQL 8.0：用中文拼音 collation 排序
SELECT name FROM users ORDER BY name COLLATE utf8mb4_zh_0900_as_cs;

-- 通用技巧：转成 GBK 再排
-- GBK 的一级汉字（3755 个常用字）本身就是按拼音顺序编排的
SELECT name FROM users ORDER BY CONVERT(name USING gbk);

-- 建表时直接指定，避免每次查询都写 COLLATE
ALTER TABLE users MODIFY name VARCHAR(64)
  CHARACTER SET utf8mb4 COLLATE utf8mb4_zh_0900_as_cs;
ORDER BY CONVERT(name USING gbk) 有两个边界：
① 只对一级汉字（3755 个最常用字）有效。二级汉字（生僻字）在 GBK 里是按部首笔画排的，会插到奇怪的位置。
② CONVERT 会让索引失效，因为它在列上做了函数运算。大表上这么排会全表扫描。
所以生产上的正确做法是：加一个 name_pinyin 字段，写入时用 pypinyin / pinyin4j 生成，在它上面建索引。这样排序和搜索都能走索引。

应用层排序

# Python：用 locale 或 pypinyin
import locale
locale.setlocale(locale.LC_COLLATE, "zh_CN.UTF-8")
sorted(names, key=locale.strxfrm)

# 更可控的做法：显式生成拼音键
from pypinyin import lazy_pinyin
sorted(names, key=lambda s: lazy_pinyin(s))

# Java：Collator
Collator c = Collator.getInstance(Locale.CHINA);
Collections.sort(list, c);
为什么数据库排序和应用层排序结果可能不一样？因为两者用的 collation 实现不同：MySQL 用的是自己实现的 UCA（Unicode Collation Algorithm）变体，Java 用的是 JDK 里的规则表，Python 的 locale.strxfrm 依赖操作系统的 locale 数据。同一个名字列表，在三个地方排出来的顺序可能都不同。
要保证一致，只有一个办法：把排序键物化成字段，写入时算一次，之后所有地方都按这个字段排。
模块 6

长度计算：三个不同的"长度"

"这个字符串多长"这个问题，在不同语境下有三个完全不同的答案：字节数、字符数、显示宽度。混用它们是大量 bug 的来源。

Golen(s)64字节数（Go 的 string 就是字节切片）
Goutf8.RuneCountInString(s)21码点数
JavaScript 和 Java 的 length 是"UTF-16 码元数"，不是"字符数"。BMP 内的字符（中文、日文、大部分符号）占 1 个码元，超出 BMP 的字符（emoji、生僻字）占 2 个码元（代理对）。
后果："😀".length === 2，前端按 length 限制输入长度时，用户输入 10 个 emoji 会被算成 20 个字符。这是表单校验 bug 的头号来源。

显示宽度：第三个维度

等宽字体里，一个字符占几列和它的字节数、码点数都无关，取决于它的东亚宽度属性（East Asian Width）。

类别显示宽度例子
窄（Na / H / N）1 列英文、数字、半角标点
宽（W / F）2 列汉字、日文假名、韩文、全角标点、大部分 emoji
模糊（A）1 或 2 列希腊字母、部分符号，取决于终端设置
组合字符0 列重音符号、变体选择符，叠加在前一个字符上
# Python：用 unicodedata 判断东亚宽度
import unicodedata
def display_width(s):
    w = 0
    for ch in s:
        if unicodedata.combining(ch):
            continue                      # 组合字符不占位
        w += 2 if unicodedata.east_asian_width(ch) in ("W", "F") else 1
    return w

>>> display_width("中文abc")
7                                     # 2+2+1+1+1
>>> len("中文abc")
5                                     # 字符数是 5，但显示要 7 列

# 命令行里对齐表格，用 wcwidth 库更准（它处理了 emoji 和零宽连接符）
pip install wcwidth
这个"显示宽度"在什么地方会咬人？终端表格对齐（用 len() 算出来的 padding 会让中文列错位）、固定宽度的报表导出、短信长度计费（运营商按 70 个字符算一条，中文和英文都算 1 个，但 emoji 可能算 2 个）、以及 UI 里的"最多 20 个字"校验。

截断为什么会切出半个汉字

# 错误写法：按字节截断
>>> s = "中文测试"
>>> s.encode("utf-8")[:7].decode("utf-8")
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe6 in position 6
# 7 个字节 = 中(3) + 文(3) + 测的第 1 个字节

# 正确写法一：先按字符截，再编码
>>> s[:2].encode("utf-8")
b'\xe4\xb8\xad\xe6\x96\x87'          # 完整的两字符

# 正确写法二：必须在字节层截断时，回退到字符边界
def truncate_bytes(b, limit):
    if len(b) <= limit:
        return b
    end = limit
    while end > 0 and (b[end] & 0xC0) == 0x80:
        end -= 1                       # 0x80-0xBF 是续字节，往回退
    return b[:end]
为什么这个回退逻辑是对的？因为 UTF-8 的续字节最高两位固定是 10，也就是 b & 0xC0 == 0x80。只要截断点落在续字节上，就说明切在了字符中间，往前退到第一个非续字节即可。最多退 3 次（4 字节字符的情况）。
这段逻辑是 UTF-8 自同步特性的直接应用 —— GBK 做不到同样的事，因为 GBK 的两个字节都可能是首字节。

数据库与文件里的编码

这一节是工程上踩坑最密集的地方。核心只有一句：字符集要在每一层都对齐，任何一层不一致都会出问题。

MySQL 的 utf8 是个残缺实现

字符集名最大字节能存什么
utf83只是 utf8mb3 的别名。只能存 BMP 内的字符，存不了 emoji 和 U+10000 以上的生僻字
utf8mb33同上，这是它的正式名字
utf8mb44完整的 UTF-8。emoji、𠮷、音乐符号都能存
latin11只能存西欧字符，中文存进去会变成 ?
-- 症状：插入 emoji 报错
INSERT INTO posts (content) VALUES ('今天心情不错 😀');
-- ERROR 1366 (HY000): Incorrect string value: '\xF0\x9F\x98\x80' for column 'content'
--                                   ↑ F0 开头的 4 字节序列，utf8mb3 拒绝接收

-- 修复：把库、表、列全改成 utf8mb4（三处都要改）
ALTER DATABASE mydb CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
ALTER TABLE posts CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;

连接字符集：最隐蔽的一层

MySQL 的字符集有五个层次：server → database → table → column → connection。前四个是"数据怎么存"，最后一个是"数据怎么传"。

-- 看全部字符集相关变量
SHOW VARIABLES LIKE 'character_set%';

-- 典型输出（有问题的情况）
character_set_client      utf8mb4     # 客户端发来的字节按什么解
character_set_connection  utf8mb4     # 连接层内部用什么
character_set_results     utf8mb4     # 返回给客户端时用什么编
character_set_database    utf8mb4
character_set_server      utf8mb4

-- 只要这三行里有一个是 latin1，就会出现"表里看着对，程序读出来是乱码"

-- 会话级修复（临时）
SET NAMES utf8mb4;

-- JDBC 连接串（永久）
jdbc:mysql://host:3306/db?useUnicode=true&characterEncoding=utf8&connectionCollation=utf8mb4_0900_ai_ci
最坑的一种组合：表是 utf8mb4，连接是 latin1。写入时 MySQL 会把 UTF-8 字节当 Latin-1 解释，再转成 utf8mb4 存进去 —— 存进去的已经是错的。读出来时再反着转一次，看起来又是对的。所以程序里一切正常，但直接查库或者用别的客户端看就是乱码。
这类问题的特征是：同一个库，不同客户端看到的内容不一样。一旦发现这个现象，第一件事就是查 character_set_client。

文件读写：一定要显式指定 encoding

# Python：不写 encoding 会用"系统默认编码"

# Go：string 就是字节切片，读进来不需要转，但要小心 len()

模块 8

排查乱码的固定流程

不要凭感觉猜编码。按这四步走，每一步都有明确的判断依据。

第一步：看字节。用 hexdump -C 或 xxd 把原始字节打出来。这一步不做，后面全是猜。重点看开头几个字节有没有 BOM，以及有没有 3F（问号，说明信息已丢失）。
第二步：确认"声明"是什么。文件有没有 BOM？HTTP 响应头 Content-Type 里的 charset 是什么？HTML 里 <meta charset> 写的是什么？数据库的 character_set_client 是什么？声明和实际经常不一致，这正是问题所在。
第三步：验证"实际"是什么。把字节按候选编码逐个试解，看哪个能解出有意义的文本。优先试 UTF-8（因为有严格校验，能解通基本就是对的），失败再试 GBK、GB18030。
第四步：决定修复方式。字节完好 → 转码；双重编码 → 反向解一次；问号/替换字符 → 信息已丢失，只能重新取数据。
# ===== 完整排查脚本 =====
FILE=broken.txt

# 1. 看字节（前 64 字节足够判断）
hexdump -C "$FILE" | head -4

# 2. 看系统猜的结果
file -i "$FILE"

# 3. 判断是不是合法 UTF-8（能过就是 UTF-8）
if iconv -f UTF-8 -t UTF-8 "$FILE" > /dev/null 2>&1; then
    echo "合法 UTF-8 —— 问题在声明，不在内容"
else
    echo "不是 UTF-8 —— 试 GBK"
fi

# 4. 试 GBK 解码，看结果是否可读
iconv -f GBK -t UTF-8 "$FILE" | head -5

# 5. 确认后转码
iconv -f GBK -t UTF-8 "$FILE" -o fixed.txt

Python 版的自动化判断

# 按"能解通且像正常文本"的顺序试探
def sniff(raw: bytes):
    candidates = ["utf-8", "gb18030", "big5", "shift_jis", "latin-1"]
    for enc in candidates:
        try:
            s = raw.decode(enc)
        except UnicodeDecodeError:
            continue
        # latin-1 永远能解通，所以放到最后，并且要求可打印字符占比够高
        printable = sum(1 for c in s if c.isprintable() or c in "\r\n\t")
        if printable / max(len(s), 1) > 0.95:
            return enc, s
    return None, None

# 注意：这是启发式，短文本上误判率很高
# 生产系统不要靠猜，要在入口处强制声明编码
最重要的一条边界：一旦字节被错误解码成"字符"并存进了数据库，原始字节就丢了。
比如 GBK 的 D6 D0 被当成 Latin-1 解成两个字符，再存进一个 utf8mb4 字段，库里存的是那两个 Latin-1 字符的 UTF-8 编码 —— 原来的 D6 D0 已经找不回来了。
唯一的例外是双重编码（UTF-8 → Latin-1 → UTF-8），因为那一步是可逆的。判断方法：看字节长度是不是正常值的 2 倍。

线上系统的三层防御

入口层
HTTP 响应强制带 Content-Type: ...; charset=utf-8；请求体按声明的 charset 解码，解码失败直接返回 400，不要用 replace 兜底
存储层
库、表、列、连接四处统一 utf8mb4；连接串里显式写 characterEncoding；上线前跑一次全库字符集检查
输出层
日志、CSV、导出文件一律 UTF-8 无 BOM；给 Excel 的 CSV 单独加 BOM；文件头显式声明，不靠猜
常见坑

十个真实踩过的坑

1
把 Unicode 和 UTF-8 当同义词
"把文件转成 Unicode"这句话没有意义。Unicode 是字符集，UTF-8 是编码。转码只能转到具体编码。
2
MySQL 用 utf8 存 emoji
MySQL 的 utf8 是 utf8mb3 的别名，最大 3 字节。emoji 是 4 字节，直接报 ERROR 1366。必须用 utf8mb4。
3
只改了表的字符集，没改连接字符集
表是 utf8mb4、连接是 latin1，写入时就已经错了。表现是"程序里正常，直接查库乱码"，极难排查。要查 character_set_client。
4
按字节截断字符串
按字节切 UTF-8 会切出半个字符，末尾出现 � 或直接抛异常。要按字符切，或者在字节层回退到字符边界。
5
JSON 文件带 BOM 导致解析失败
RFC 8259 明确禁止 BOM。Windows 记事本保存的 JSON 常带。用 encoding="utf-8-sig" 读可以自动跳过。
6
Shell 脚本开头有 BOM
内核看到的不是 #! 而是 EF BB BF，execve 失败。报错信息通常不指向真正原因，能查很久。
7
对双重编码的文本直接 iconv 转码
双重编码要先"反向解一次"（encode latin-1 再 decode utf-8），直接转码只会得到第三种乱码。
8
以为 ORDER BY 能按拼音排中文
默认按 collation 的权重排，通常是码点顺序，不是拼音。要用 utf8mb4_zh_0900_as_cs，或者物化一个拼音字段。
9
Python 里 open() 不写 encoding
不写就用系统 locale，Windows 上是 GBK、Linux 上是 UTF-8。同一份代码在两个平台行为不同，是"本地能跑线上挂"的经典原因。
10
看到问号还以为能修复
????? 表示写入时目标编码无法表示该字符，信息已被永久丢弃。这种情况只能重新取数据，转码是徒劳的。
自测

六道题

1. Unicode 和 UTF-8 的关系是？
正确答案：字符集与编码的关系。Unicode 定义"有哪些字符、编号是多少"，UTF-8 / UTF-16 / UTF-32 是它的三种具体编码。同一个码点在不同编码下的字节完全不同。
2. 一个文本文件开头是 EF BB BF，这说明什么？
正确答案：UTF-8 BOM。UTF-8 本身没有字节序问题，这个 BOM 是 Windows 工具链的历史习惯。它会让 JSON 解析失败、让 shell 脚本无法执行。
3. 一段文字显示成「ä¸­æ–‡」，字节长度约为正常值的 2 倍。成因是？
正确答案：双重编码。特征是长度翻倍、字母带大量重音符号。这类乱码是可逆的：broken.encode("latin-1").decode("utf-8") 就能还原。
4. MySQL 里 LENGTH('中文') 和 CHAR_LENGTH('中文') 分别返回？
正确答案：6 和 2。LENGTH 返回字节数（UTF-8 下每个汉字 3 字节），CHAR_LENGTH 返回字符数。设计字段长度限制时要想清楚用的是哪一个。
5. MySQL 的 utf8 字符集为什么存不了 emoji？
正确答案：utf8 是 utf8mb3 的别名。BMP 之外的字符（U+10000 以上）在 UTF-8 里需要 4 字节，utf8mb3 直接拒绝。要用 utf8mb4。
6. 看到文本显示成「?????」，正确的判断是？
正确答案：不可逆。问号表示目标编码无法表示原字符，字节层面已经丢失。只有"编码不匹配"和"双重编码"这两种乱码是可修复的。
