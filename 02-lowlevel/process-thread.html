模块 1

进程与线程的本质区别

先说一个容易被忽略的事实：Linux 内核里没有"线程"这个独立概念。线程和进程都是 task_struct，区别只在于创建时 clone() 传了哪些标志位 —— 共享得多就是线程，共享得少就是进程。

共享什么、独享什么

资源线程之间说明
地址空间（mm_struct）共享同一份页表，一个线程改了全局变量，其他线程立刻能看到
文件描述符表（files_struct）共享一个线程 close(fd)，其他线程这个 fd 就废了 —— 这是很多诡异 bug 的来源
信号处理函数（sighand_struct）共享一个线程 signal() 改了 handler，全进程生效
工作目录 / 根目录（fs_struct）共享一个线程 chdir()，所有线程的 cwd 都变了
寄存器组独享包括通用寄存器、PC、SP、标志位
栈独享默认 8 MB 虚拟空间，主线程用进程启动时分配的栈
TLS（线程局部存储）独享__thread / thread_local 变量，靠 FS/GS 段寄存器定位
errno独享实际上是个宏，展开成 TLS 变量
信号屏蔽字独享每个线程可以屏蔽不同的信号
调度实体独享每个线程独立参与调度，有自己的 nice 值和 CPU 亲和性

clone 的六个关键标志

// 创建进程：什么都不共享（除了内核对象）
clone(fn, stack, SIGCHLD, arg);

// 创建线程：几乎全共享（glibc 的 pthread_create 底层就是这个）
clone(fn, stack,
      CLONE_VM       // 共享地址空间 ← 最关键的一条
    | CLONE_FS       // 共享 cwd / root
    | CLONE_FILES    // 共享 fd 表
    | CLONE_SIGHAND  // 共享信号处理函数
    | CLONE_THREAD   // 放进同一个线程组（同一个 PID 视角）
    | CLONE_SYSVSEM  // 共享 System V 信号量的 undo 列表
    | CLONE_SETTLS   // 设置 TLS 指针
    , arg);

// CLONE_VM 是分水岭：有没有它，决定了"切换时要不要换页表"
// 也就决定了上下文切换的成本量级

为什么线程切换比进程切换便宜

开销项线程切换进程切换说明
保存/恢复寄存器有有两者一样，约 20~30 个寄存器
切换页表（写 CR3）无有进程切换必须换页表基址
TLB 失效无有（PCID 可缓解）换了页表，原来的地址翻译全部作废，重新走页表遍历
缓存污染轻重同一进程的线程共享代码和数据，缓存还是热的
内核栈切换有有每个 task 有自己的内核栈（通常 16 KB）

PCID（Process Context Identifier，进程上下文标识）是 Intel 的优化：给每个进程的页表一个 12 位 ID，切换时带上 ID，TLB 条目按 ID 打标签，就不用整体刷掉。这让进程切换的 TLB 代价从"全刷"降到"部分失效"。Linux 从 4.14 起默认启用。

但真正的成本不在寄存器。保存 30 个寄存器大约几十纳秒，而缓存和 TLB 变冷之后的间接损失是几微秒到几十微秒。所以"线程切换比进程切换便宜"这句话，准确的说法是：线程切换的间接损失小得多，因为地址空间没变、热点数据还在缓存里。
模块 2

上下文切换的成本

一次切换到底保存了什么

# 直接成本（必须做的）
1. 通用寄存器    rax rbx rcx rdx rsi rdi rbp r8-r15   约 16 个
2. 指令指针      rip
3. 栈指针        rsp（用户栈）+ 内核栈指针
4. 标志寄存器    rflags
5. FPU/SIMD 状态 xmm0-15 / ymm0-15（AVX 有 16 个 256 位寄存器）
                 # 用 AVX-512 时是 32 个 512 位寄存器，保存成本更高
6. TLS 基址       fs_base / gs_base
7. 浮点控制字    fcw / mxcsr

# 进程切换额外要做的
8. 页表基址      CR3 ← 这一条引发 TLB 后果
9. 内核栈指针切换（每个 task 独立内核栈）

# 间接成本（更大，但常被忽略）
10. L1/L2 缓存被新任务的数据挤掉
11. TLB 条目失效，后续访问要走多级页表
12. 分支预测器历史被污染
13. 流水线需要重新填充

到底多贵

场景典型耗时说明
同进程线程切换1~3 μs直接成本约 0.5~1 μs，其余是缓存变冷的间接损失
跨进程切换3~10 μs加上页表切换和 TLB 失效
跨 NUMA 节点切换10~20 μs内存访问延迟本身翻倍
系统调用（非切换）0.1~0.5 μs只进出内核，不换 task，便宜得多

换算一下：如果每秒切换 10 万次，按 2 μs 算就是 0.2 秒/秒 —— 20% 的 CPU 时间花在切换上，业务一行代码没跑。

怎么观测

# vmstat 的 cs 列 = 每秒上下文切换总数（含中断引起的）
vmstat 1
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  8  0      0 812345  12345 456789    0    0     0    12  800 45000 60 30 10  0  0
#                                                          ↑    ↑
#                                                       中断  上下文切换

# pidstat -w 按进程看切换（-w 是关键）
pidstat -w 1
#   UID   PID   cswch/s nvcswch/s  Command
#  1000  1234   1200.00     50.00  java
#   cswch/s   = 自愿切换（voluntary），主动让出 CPU，比如等锁、等 IO
#   nvcswch/s = 非自愿切换（non-voluntary），被时间片强制剥夺

# 单个进程的累计切换次数
grep ctxt /proc/1234/status
# voluntary_ctxt_switches:     1234567
# nonvoluntary_ctxt_switches:    89012
怎么看这两个数的比例：
自愿切换远多于非自愿 → 线程大部分时间在等（锁、IO、sleep）。说明瓶颈不在 CPU，加线程可能有帮助，但要先确认下游扛不扛得住。
非自愿切换很高 → 可运行的线程比核多，在抢 CPU。加线程只会更糟，应该减线程或者加机器。
两个都很高，且 us + sy 接近 100% → 典型的"线程开太多在自相残杀"，sy（系统态）占比高说明时间都花在调度和锁上了。
一个反直觉的结论：上下文切换次数高，本身不是问题；切换带来的缓存失效才是。
一个 1000 线程的服务每秒切 50 万次，如果每个线程都在做短小的任务，可能完全没问题（比如 Go 的 goroutine 调度）。但如果每次切换都让 32 KB 的 L1 和 1 MB 的 L2 变冷，那每次都要重新预热几十微秒。判断标准应该是吞吐和延迟，不是切换次数本身。
模块 3

调度算法

Linux 的默认调度器是 CFS（Completely Fair Scheduler，完全公平调度器），从 2.6.23 起取代了 O(1) 调度器。6.6 内核起默认换成了 EEVDF（Earliest Eligible Virtual Deadline First），但核心思想仍是"虚拟时间"。

CFS 的核心：虚拟运行时间

CFS 不用固定时间片，而是给每个任务维护一个 vruntime（虚拟运行时间）。每次调度都选 vruntime 最小的任务跑。任务运行时 vruntime 增长，但增长速度与权重成反比：

vruntime += 实际运行时间 × (NICE_0_WEIGHT / 任务权重)

# NICE_0_WEIGHT = 1024
# 权重 = 1024 / 1.25^nice

nice 值 → 权重 → 相对 CPU 份额
  -20   →  88761  →  86.7 倍
  -10   →   9548  →  9.3 倍
    0   →   1024  →  1 倍（基准）
   10   →    110  →  0.108 倍
   19   →     15  →  0.0146 倍

# 也就是说：nice -20 的任务和 nice 19 的任务同时跑，
# CPU 时间分配大约是 88761 : 15 ≈ 5900 : 1

这就是"每个 nice 级别差 1.25 倍"的来源。注意这是权重比，不是绝对的 CPU 百分比 —— 实际分到多少还取决于同时有多少个任务在跑。

时间片怎么定

# CFS 的目标：让所有可运行任务在一个"调度周期"内都至少跑一次
sched_latency_ns       = 6 ms      # 默认调度周期
sched_min_granularity_ns = 0.75 ms # 单个任务的最小时间片

# 时间片 = 调度周期 × (本任务权重 / 所有任务权重之和)
# 但不少于 min_granularity

# 例：4 个同优先级任务
时间片 = 6ms × (1024 / 4096) = 1.5 ms

# 例：100 个同优先级任务
理想时间片 = 6ms / 100 = 0.06ms < 0.75ms
实际取 0.75 ms
此时调度周期被拉长到 100 × 0.75 = 75 ms

# 含义：任务越多，单个任务的响应延迟越长
# 这就是为什么"线程开太多"会让延迟变差，即使 CPU 没打满

实时调度：SCHED_FIFO 与 SCHED_RR

策略行为风险
SCHED_NORMAL普通 CFS/EEVDF 调度无
SCHED_BATCH批处理，减少唤醒抢占，适合纯计算延迟变高
SCHED_IDLE只在 CPU 空闲时跑，权重极低可能长期得不到 CPU
SCHED_FIFO实时，先进先出。一旦运行就一直跑，直到自己让出或被更高优先级抢占写错就是死机
SCHED_RR实时，带时间片轮转（默认 100 ms）同优先级之间能轮转，稍安全
SCHED_DEADLINE按 deadline 调度，需要指定 runtime/deadline/period参数算错会严重超时
# 实时任务的防死锁机制：RT throttling
cat /proc/sys/kernel/sched_rt_runtime_us     # 950000
cat /proc/sys/kernel/sched_rt_period_us      # 1000000
# 含义：每 1 秒的周期里，实时任务最多用 950 ms（95%）
# 剩下的 50 ms 留给普通任务，防止一个死循环的 RT 线程锁死整台机器

# 把一个线程设成实时优先级（需要 CAP_SYS_NICE 或 root）
chrt -f 50 ./realtime_app        # SCHED_FIFO, 优先级 50（1-99，越大越高）
chrt -r 50 ./realtime_app        # SCHED_RR
chrt -p 1234                     # 查某个进程的调度策略
不要把业务线程设成 SCHED_FIFO。一个跑飞的实时线程会让整台机器失去响应 —— 连 SSH 都登不进去，只能重启。实时调度只用于硬实时场景（音视频、工业控制、高频交易的关键路径），而且要配合 CPU 隔离（isolcpus）和充分的测试。

关于"CPU 密集任务饿死 IO 任务"

这个说法流传很广，但在 CFS 下并不成立，需要说清楚边界：

场景会不会饿死真实机制
CFS 下的 CPU 密集 vs IO 密集不会IO 任务睡眠时 vruntime 不增长，醒来后 vruntime 远小于 CPU 任务，会被优先调度。CFS 反而偏向 IO 型任务
RT 任务 vs 普通任务会RT 优先级绝对高于 CFS，只要 RT 任务可运行，CFS 任务就得不到 CPU。靠 RT throttling 兜底
固定大小线程池里的 CPU 任务 vs IO 任务会这才是真正的高频事故：所有工作线程都被 CPU 密集任务占满，IO 任务在队列里排队，看起来像"饿死"，其实是线程池饱和
cgroup 的 cpu.max 配额会CPU 密集任务耗尽了配额，整个 cgroup 被 throttle，里面的 IO 任务也一起被限流
正确的心智模型：内核调度器本身是公平的，饿死几乎总是发生在应用层的资源池上 —— 线程池、连接池、队列。所以遇到"IO 请求超时但 CPU 不高"，先看线程池是不是被慢任务占满了，而不是去调内核参数。
模块 4

线程池该开多大

这是本文最值钱的一节。答案不是一个数字，而是一个公式加三个约束。

CPU 密集：核数 + 1

# 为什么是 +1
N_cpu = 物理核数 + 1

# +1 的作用：当某个线程偶尔因为缺页、GC、日志刷盘而短暂阻塞时，
# 多出来的那个线程能顶上，不让 CPU 空转

# 注意三个前提
1. 这里的"核数"是物理核，不是超线程后的逻辑核
   # 超线程的两个逻辑核共享执行单元，对纯计算任务提升只有 10%~30%
   # 所以 8 物理核 16 逻辑核的机器，CPU 密集任务开 9 个，不是 17 个
2. 线程之间没有锁竞争。如果有，加线程只会加剧争抢
3. 任务粒度不要太细。如果一个任务只要几微秒，调度开销会盖过收益

IO 密集：用利特尔法则推

利特尔法则（Little's Law）是排队论的基石，形式极简：

L = λ × W

L = 系统中同时存在的请求数（并发度）
λ = 请求到达速率（吞吐，req/s）
W = 单个请求的平均处理时间（s）

# 变形：要达到吞吐 λ，且每个请求耗时 W，就必须有 L 个并发
需要的并发数 = 目标吞吐 × 单请求耗时

把它和"等待时间 / 计算时间"结合起来，就得到线程池的经验公式：

N_threads = N_cores × (1 + W / C)

N_cores = 物理核数
W       = 每个任务的等待时间（IO、锁、RPC，不占 CPU）
C       = 每个任务的计算时间（占 CPU）

# 推导：要让 N_cores 个核一直忙，就得有足够的线程在"计算"状态
# 一个线程的占空比 = C / (C + W)
# 要让 N_cores 个核满载，需要 N_cores / 占空比 = N_cores × (C+W)/C 个线程

完整算例

# 场景：8 物理核的机器，处理一个 HTTP 请求
#   其中 10 ms 是本地计算（JSON 解析、业务逻辑）
#   90 ms 是等数据库返回（纯等待，不占 CPU）

C = 10 ms
W = 90 ms
N_cores = 8

N = 8 × (1 + 90/10) = 8 × 10 = 80 个线程

# 用利特尔法则交叉验证：
# 假设目标吞吐 800 req/s，单请求总耗时 100 ms
L = 800 × 0.1 = 80
# 两个方法得到同一个数字，说明推导是对的

# 理论 CPU 利用率
每线程占空比 = 10 / 100 = 10%
80 个线程 × 10% = 8 个核  // 正好打满

三个必须检查的约束

约束检查什么不满足的后果
下游容量数据库连接池多大？下游服务能扛多少 QPS？80 个线程同时查库，连接池只有 20，剩下 60 个在等连接 —— 公式失效，实际并发被压到 20
内存每线程栈 8 MB（虚拟）+ 线程私有缓冲区80 × 8 MB = 640 MB 虚拟地址空间（通常没事），但如果每个线程有 1 MB 缓冲，就是 80 MB 实际内存
上下文切换线程数远超核数时，切换开销会上升80 线程 / 8 核 = 10 倍超配，切换频繁。如果 W 很小（比如 1 ms），这个公式给出的线程数会很小，不用担心
公式的三个失效场景：
① W 不是纯等待。如果"等待"其实是在自旋（spinlock），它占着 CPU，应该算进 C 而不是 W。
② W 波动极大。平均 90 ms 但 P99 是 2 s，那按平均值算出来的线程数会导致长尾请求堆积。要用高分位而不是平均值来估算。
③ 任务是混合型的。一个线程池里既有 5 ms 的缓存命中请求，也有 500 ms 的慢查询，用一个公式算没意义。正确做法是按任务类型拆成多个池，各自独立配置，避免慢任务占满快任务的线程。
实操建议：先用公式算出理论值，然后从理论值的 60%~70% 开始压测，逐步加，观察三个指标 —— 吞吐是否还在涨、P99 延迟是否开始劣化、nvcswch/s 是否飙升。找到吞吐拐点就停。不要一步到位开到理论值，因为公式里的 W 和 C 本来就是估的。
模块 5

协程是什么

协程不是"更轻量的线程"，它是一个完全不同的东西：在用户态自己实现调度，内核完全不知道它的存在。

三种并发模型

模型调度者切换成本
1:1 线程内核1~3 μs，要进内核态
N:1 协程用户态库几十纳秒，纯用户态函数调用
M:N 协程用户态运行时 + 内核M 个协程跑在 N 个线程上，兼顾两者

M:N 的关键在于：只有真正会阻塞的系统调用才占用一个内核线程，其余协程的切换全在用户态完成。

有栈 vs 无栈

类型实现代表
有栈
stackful		每个协程有自己的栈，切换时换 SP。可以在任意函数层级挂起Go goroutine、Lua coroutine、Java 的虚拟线程（Loom）
无栈
stackless		编译器把函数改写成状态机，只能在 await 点挂起，不保存调用栈Rust async、JavaScript async/await、Python asyncio、Kotlin 协程
// 有栈协程：可以在深层函数里挂起，调用栈自动保留
func handler() {
    data := fetchFromDB()      // 这里阻塞，整个栈被保存
    process(data)
}
// 优点：写起来和同步代码一样，没有"函数着色"问题
// 缺点：每个协程一个栈，内存开销大

// 无栈协程：只能在 await 处挂起，状态要显式保存
async fn handler() {
    let data = fetch_from_db().await?;   // 只能在这里挂起
    process(data)
}
// 优点：没有栈开销，编译后就是一个状态机，内存极小
// 缺点：async 会"传染"—— 调用它的函数也必须是 async
//       这就是常说的"函数着色（function coloring）"问题

为什么 Go 能开百万 goroutine

# 关键数字
goroutine 初始栈大小   = 2 KB（Go 1.4 起，之前是 8 KB）
栈增长方式            = 连续栈，按需翻倍复制（2KB → 4KB → 8KB ...）
栈上限                = 1 GB（64 位平台，可用 runtime/debug.SetMaxStack 调整）
GOMAXPROCS 默认值     = CPU 核数

# 对比 pthread
pthread 默认栈        = 8 MB（虚拟，ulimit -s 决定）
100 万个 pthread      = 8 TB 虚拟地址空间 → 直接失败
100 万个 goroutine    = 2 GB 起 → 可行，但要注意内存

# 所以"百万 goroutine"是真的，但不是免费的
# 100 万 × 2KB = 2 GB，这还没算每个 goroutine 的业务数据
# 实际经验：单机 10 万级 goroutine 很轻松，百万级需要精打细算

GMP 模型

字母含义说明
GGoroutine协程本身，包含栈、指令指针、状态
MMachine内核线程，真正被 OS 调度的实体
PProcessor逻辑处理器，持有本地可运行队列。数量 = GOMAXPROCS

M 必须绑定一个 P 才能执行 G。当某个 G 发起阻塞系统调用时，M 会和 P 解绑，P 被交给另一个 M 继续跑其他 G —— 这样阻塞一个系统调用不会浪费一个 P。这就是 M:N 的核心。

# 关键机制：work stealing（工作窃取）
每个 P 有自己的本地运行队列（最多 256 个 G）
P 的队列空了 → 随机去别的 P 的队列偷一半过来
这样天然实现了负载均衡，不需要中央调度器

# 调度点（什么时候会切换）
1. 函数调用时的栈检查（Go 1.14 起的异步抢占）
2. channel 操作阻塞
3. 系统调用返回
4. go 语句创建新 G
5. GC 的 safepoint
三个 Go 并发的实际坑：
① goroutine 泄漏：启动后永远阻塞在 channel 上，没人关。进程内存缓慢上涨，runtime.NumGoroutine() 持续增长。用 pprof 的 goroutine profile 能看到全部栈。
② GOMAXPROCS 在容器里不感知 cgroup 配额（Go 1.25 之前）。容器限 2 核但宿主机 64 核，Go 会开 64 个 P，导致频繁切换。用 automaxprocs 库修正。
③ CPU 密集的 goroutine 不会主动让出。Go 1.14 之前只有函数调用时才有抢占点，一个没有函数调用的死循环会让整个 P 卡住。现在有基于信号的异步抢占，但仍然建议在长循环里偶尔 runtime.Gosched()。

方式数据拷贝次数适用场景主要限制

为什么共享内存最快

# 管道 / socket 的数据路径（2 次拷贝）
进程 A 的用户空间
   ↓ write() 系统调用，拷贝 1
内核缓冲区
   ↓ read() 系统调用，拷贝 2
进程 B 的用户空间

# 共享内存的路径（0 次拷贝）
进程 A 的用户空间 ──┐
                    ├─→ 同一块物理内存页
进程 B 的用户空间 ──┘
# 建立映射后，读写就是普通的内存访问
# 但要自己保证：什么时候 A 写完了、B 可以读了

# 实践：POSIX 共享内存 + 信号量
shm_open("/mybuf", O_CREAT | O_RDWR, 0600);
ftruncate(fd, SIZE);
p = mmap(NULL, SIZE, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
# 之后 p 就是两个进程共享的内存
共享内存的三个陷阱：
① 没有同步就没有意义。共享内存只解决了"数据能互相看到"，没解决"什么时候能看"。必须配信号量或原子标志。
② 指针不能跨进程用。两个进程的映射地址可能不同，共享结构体里只能放偏移量，不能放绝对指针。
③ 进程崩溃会留下脏数据。共享内存不会自动清理，需要设计"所有者"机制或者用 shm_unlink 明确生命周期。

怎么选

先问是不是本机。跨机器只能用 socket；本机优先 Unix 域 socket（比 TCP 少走协议栈，快 2~3 倍）。
再问数据量大不大。单次超过几百 KB 或者每秒几十万次，考虑共享内存；否则 socket 足够，开发成本低得多。
再问要不要跨语言。共享内存的结构体布局依赖编译器和 ABI，跨语言容易出错。socket + 明确协议更安全。
最后问能不能改架构。如果两个进程通信非常频繁，通常说明它们本该是一个进程。先考虑合并，再考虑优化 IPC。
模块 7

同步原语

原语语义典型误用
互斥锁
mutex		同一时刻只有一个线程能进入临界区。所有权明确：谁加锁谁解锁忘记解锁、锁粒度太大、在持锁时做 IO
条件变量
condvar		让线程等待某个条件成立，由别人唤醒。必须配互斥锁使用用 if 而不是 while 判断条件（虚假唤醒）
读写锁
rwlock		读共享、写独占。适合读远多于写的场景读多写少时反而比 mutex 慢（引用计数开销）
信号量
semaphore		计数器，控制同时访问的个数。没有所有权：A 申请 B 释放是合法的当成互斥锁用（count=1），失去"可跨线程释放"的特性
自旋锁
spinlock		拿不到就忙等，不睡眠。只在临界区极短（几十纳秒）时划算在用户态用，临界区长，白烧 CPU
屏障
barrier		让 N 个线程都到达某点后才一起继续线程数变化时死锁

条件变量的正确写法

// ===== 错误：用 if 判断 =====
pthread_mutex_lock(&m);
if (!ready)                      // ✗ 虚假唤醒时会直接往下走
    pthread_cond_wait(&c, &m);
pthread_mutex_unlock(&m);
consume();

// ===== 正确：用 while 循环 =====
pthread_mutex_lock(&m);
while (!ready)                    // ✓ 醒来后重新检查
    pthread_cond_wait(&c, &m);
pthread_mutex_unlock(&m);
consume();

// 为什么必须用 while：
// 1. 虚假唤醒（spurious wakeup）：POSIX 明确允许 cond_wait 无故返回
// 2. 多个等待者被唤醒后，只有一个能拿到锁，其他的要重新等
// 3. 条件可能在唤醒和拿锁之间被别人改回去了

// ===== 发信号端 =====
pthread_mutex_lock(&m);
ready = 1;
pthread_cond_signal(&c);          // 唤醒一个；broadcast 唤醒全部
pthread_mutex_unlock(&m);
// 注意：signal 可以在解锁前也可以在解锁后，各有性能权衡
// 解锁前 signal：被唤醒者立刻阻塞在锁上（可能"hurry up and wait"）
// 解锁后 signal：可能错过（如果没人等），但通常更高效

读写锁为什么常常更慢

# pthread_rwlock 内部要维护读者计数
读加锁：原子递增计数 + 检查有没有写者在等
读解锁：原子递减计数 + 可能唤醒写者
# 两次原子操作，在竞争激烈时缓存行来回弹（伪共享）

# pthread_mutex 在无竞争时就是一次 CAS
# 所以：临界区极短 + 竞争少时，mutex 反而更快

# 经验法则
读:写 > 10:1 且 临界区较长（> 几百 ns） → rwlock 有优势
其他情况 → 直接用 mutex
四个必须知道的死锁模式：
① ABBA 死锁：线程 1 锁 A 再锁 B，线程 2 锁 B 再锁 A。解法：全局定义锁顺序，所有代码按同一顺序加锁。
② 自己锁自己：非递归锁重复加锁。解法：用递归锁，或者重构代码避免嵌套。
③ 持锁做 IO：拿着锁去查数据库，锁被持有几百毫秒，所有线程排队。解法：把 IO 挪到锁外，只对内存数据的修改加锁。
④ 条件变量丢失唤醒：先 signal 后 wait，信号丢了线程永远等下去。解法：条件判断和 wait 必须在同一个锁保护下。

"哪个线程在跑满 CPU"这个问题，答案在 /proc/PID/task 里。下面是完整的排查路径。

第一步：确认是哪个线程

# top -H：按线程显示（H = Threads）
top -H -p 1234
# 输出的 PID 列实际是 TID（线程 ID），能看到每个线程的 CPU%
# 按 P 按 CPU 排序，最上面那个就是元凶

# ps -L：列出进程的所有线程
ps -L -p 1234 -o pid,tid,psr,pcpu,stat,comm
#  psr = 跑在哪个核上；stat = R/S/D/Z

# pidstat -t：按线程统计（比 top 更适合脚本）
pidstat -t -p 1234 1
#   UID  TGID   TID    %usr %system  %CPU   CPU  Command
#  1000  1234  1234    0.00    0.00   0.0     3  java
#  1000  1234  1240   99.00    1.00 100.0     5  java|GC Thread#0
#                              ↑ 这个线程在跑满一个核

# 线程名（Java 里通过 Thread.setName 设置，会体现在 comm 里）
cat /proc/1234/task/1240/comm

第二步：看线程在干什么

# 1. 用户态还是内核态？
cat /proc/1234/task/1240/stat
# 第 3 个字段是状态：R=运行 S=睡眠 D=不可中断睡眠 Z=僵尸
# 第 39 个字段是 utime，40 是 stime（单位 jiffies）

# 2. 内核栈（需要 root）
cat /proc/1234/task/1240/stack
# 如果在 D 状态且栈里有 io_schedule，说明卡在磁盘 IO

# 3. 用户态栈（C/C++）
gdb -p 1240 -batch -ex "thread apply all bt" 2>/dev/null

# 4. Java 线程栈（TID 要转成十六进制）
printf "%x\n" 1240          # 输出 4d8
jstack 1234 | grep -A 20 "nid=0x4d8"

# 5. 看谁在等锁
cat /proc/1234/task/1240/wchan

第三步：整体判断

三种典型症状对照

现象判断下一步
单核 100%，其他核空闲，mpstat 明显不均衡单线程瓶颈用 perf top -t 看热点；考虑拆分任务或改多线程
所有核都 60~70%，cs 很高，sy 占比高线程过多在自相残杀减少线程数，或者查锁竞争（perf lock）
CPU 不高但延迟很高，r 列很大等 IO 或等锁看 D 状态线程数、iostat、连接池水位
load average 的准确含义：Linux 的 load 统计的是"运行中 + 不可中断睡眠（D 状态）"的任务数，不只是 CPU 队列。
所以一个纯 IO 阻塞的服务，CPU 只有 10%，load 却可能到 20。这时候 load 高不代表 CPU 不够，而是很多任务卡在 D 状态（通常是磁盘 IO 或 NFS）。判断依据是 vmstat 的 b 列（阻塞进程数）。
经验阈值：load / 核数 < 0.7 健康，> 1.0 需要关注，> 2.0 基本是故障。
常见坑

十个踩过的坑

1
用 nproc 的结果当物理核数
开了超线程的机器，nproc 是逻辑核数，通常是物理核的 2 倍。CPU 密集任务的线程池按逻辑核数开，会导致两个线程抢一个物理核的执行单元，吞吐反而下降。
2
线程池按公式算完直接用
公式给出的是"理论并发度"，但下游数据库连接池可能只有 20。80 个线程抢 20 个连接，实际并发被压到 20，多出来的线程只是在等连接。要先确认下游容量。
3
把 CPU 密集和 IO 密集任务放同一个线程池
慢的 CPU 任务会把所有工作线程占满，IO 任务在队列里排队，表现为"CPU 100% 但请求全超时"。按任务类型拆池，各自独立配置。
4
条件变量用 if 判断条件
POSIX 允许虚假唤醒，而且多个等待者被唤醒后只有一个能拿到锁。必须用 while 循环重新检查条件，否则会在条件不成立时继续执行。
5
持锁做 IO 或 RPC
锁被持有几百毫秒，所有线程排队。这把锁实际上变成了串行化的瓶颈。原则：只在锁内做内存操作，IO 一律挪到锁外。
6
把业务线程设成 SCHED_FIFO
实时线程一旦跑飞，会占满 CPU 让整机失去响应，SSH 都登不进去。实时调度只用于硬实时场景，且要配合 CPU 隔离和 RT throttling。
7
goroutine / 协程泄漏
启动后永远阻塞在 channel 或锁上，没人关闭。表现为内存缓慢上涨、NumGoroutine() 持续增长。用 pprof 的 goroutine profile 抓全量栈，找阻塞点。
8
线程栈设太大导致线程创建失败
默认 8 MB 栈 × 1000 线程 = 8 GB 虚拟地址空间。32 位进程直接失败，64 位也可能撞上 max_map_count 限制。线程多时把 pthread_attr_setstacksize 调到 256 KB~1 MB。
9
用 load average 判断 CPU 是否饱和
Linux 的 load 包含 D 状态（不可中断睡眠）任务。纯 IO 阻塞的服务 CPU 只有 10%，load 也可能到 20。要看 vmstat 的 r（运行队列）和 b（阻塞数）分开判断。
10
在容器里相信 nproc 和 free 的输出
容器看到的是宿主机资源。CPU 配额看 /sys/fs/cgroup/cpu.max，内存限制看 memory.max。JVM、Go runtime 在旧版本里都不感知 cgroup 限制，会按宿主机规格开线程和堆。
自测

六道题

1. 同一进程内的两个线程，哪个资源是不共享的？
正确答案：栈和寄存器组。线程共享地址空间（CLONE_VM）、fd 表（CLONE_FILES）、信号处理函数（CLONE_SIGHAND）、工作目录（CLONE_FS），但每个线程有自己的栈、寄存器、TLS、errno 和信号屏蔽字。
2. 8 物理核的机器，任务平均 10 ms 计算 + 90 ms 等数据库。按公式线程池该开多大？
正确答案：80 个。N = 8 × (1 + 90/10) = 80。交叉验证：若目标吞吐 800 req/s、单请求 100 ms，利特尔法则给出 L = 800 × 0.1 = 80，两者一致。但前提是数据库连接池能支撑 80 并发，否则实际并发会被连接池压到更低。
3. 线程切换比进程切换便宜，最主要的原因是？
正确答案：不换页表。两者都要进内核、都要保存寄存器。关键差别是线程共享地址空间，不需要写 CR3，TLB 不会失效，热点数据还在缓存里。直接成本只有几百纳秒，间接的缓存/TLB 损失才是大头。
4. pidstat -w 显示某进程 nvcswch/s（非自愿切换）很高，说明？
正确答案：在抢 CPU。非自愿切换是被时间片强制剥夺，说明就绪队列里有更多线程等着跑。这时候加线程会加剧争抢，正确做法是减线程或加机器。反过来，自愿切换（cswch/s）高才说明在等 IO/锁。
5. Go 能开百万 goroutine 的核心原因是？
正确答案：小栈 + M:N 调度。goroutine 初始栈 2 KB（pthread 默认 8 MB），按需翻倍增长。GMP 模型把 M 个 goroutine 复用到 N 个内核线程上，阻塞系统调用时 M 与 P 解绑，不浪费 P。100 万个 goroutine 约需 2 GB 栈内存，不是零成本。
6. 共享内存比管道快，根本原因是？
正确答案：零拷贝。管道要走两次系统调用、两次数据拷贝（用户→内核→用户）。共享内存建立 mmap 之后，两个进程访问同一块物理页，没有拷贝。但代价是必须自己实现同步，而且共享结构体里不能放绝对指针。

线程池容量公式

# CPU 密集
N = 物理核数 + 1

# IO 密集
N = 物理核数 × (1 + W / C)
    W = 等待时间（IO、RPC、锁等待，不占 CPU）
    C = 计算时间（占 CPU）

# 利特尔法则（交叉验证）
L = λ × W
    L = 并发度，λ = 目标吞吐(req/s)，W = 单请求耗时(s)

# 实例：8 核，10ms 计算 + 90ms 等待
N = 8 × (1 + 90/10) = 80
# 验证：目标 800 req/s × 0.1s = 80 并发 ✓

# 实际取值：理论值的 60%~70% 起压，观察拐点
