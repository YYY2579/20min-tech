模块 1

用户态与内核态的边界

CPU 在设计上就只信任一小部分代码。这个"信任"是硬件级别的，不是软件约定。

特权级：Ring 0 到 Ring 3

x86 定义了四个特权级，Linux 只用了两个：内核跑 Ring 0，应用跑 Ring 3。ARM64 上对应 EL0（用户态）和 EL1（内核态），概念一样。Ring 3 下 CPU 会硬件层面拒绝执行一批指令——不是内核检查后返回错误，而是直接抛 #GP（General Protection Fault）。

被禁的指令例子为什么禁
I/O 端口访问in / out能直接读写设备寄存器，绕过所有文件权限
改控制寄存器mov cr3, ...cr3 指向页表根，改了就能映射任意物理内存
关中断 / 停机cli / sti / hlt关掉中断就能独占 CPU，一条 hlt 让整机停住
加载 IDT/GDTlidt / lgdt能改写中断入口，等于接管整个系统

为什么应用不能直接操作硬件

不是"不安全"这么笼统，而是四个具体问题，每一个都足以让系统崩掉：

隔离
一块网卡只有一组寄存器。A 进程能直接写，B 进程的包就发不出去。硬件必须由内核仲裁。
抽象
硬盘有 SATA/NVMe/SCSI 十几种协议。内核统一成"文件"，应用只认 read。
复用
一千个进程读同一块盘，内核用页缓存和 IO 调度合并。没内核就是一千份随机读。
记账
谁用了多少 CPU、内存、带宽，得有地方统计和限额。这是 cgroup 和调度器的活。

跨界的三条通道

通道触发方式典型场景
系统调用主动执行 syscall 指令（老平台是 int 0x80）主动请求服务：读文件、发包、建进程
异常执行出错，CPU 同步抛出，如缺页 #PF、除零 #DE访问未映射内存、栈溢出。处理完可能重试原指令
中断外部设备异步发出，如网卡收包、时钟滴答与当前指令无关，处理完回到被中断处

三者都叫"陷入内核"，但语义完全不同：系统调用是自愿的、异常是被迫的、中断是外来的。

系统调用长什么样

一次调用需要三样东西：编号（要哪个服务）、参数（最多 6 个，放寄存器）、返回码。x86-64 的约定是：

寄存器用途
rax入参：调用号；出参：返回值（负数表示错误，如 -EPERM）
rdi, rsi, rdx, r10, r8, r9第 1~6 个参数（注意第 4 个是 r10，不是 rcx）
rcx, r11被 syscall 指令自动占用：存返回地址和 rflags
# 手写一次系统调用，不经过 libc 包装（x86-64）
.global _start
_start:
    mov $39, %rax        # 39 = __NR_getpid
    syscall              # 陷入内核
    mov %rax, %rdi       # 返回值当 exit 的退出码
    mov $60, %rax        # 60 = __NR_exit
    syscall

调用号是架构相关的：x86-64 的 getpid 是 39，ARM64 上是 172，i386 上是 20。所以别硬编码，用 syscall(SYS_getpid) 或直接调 getpid()。

# 查本机的调用号表
cat /usr/include/x86_64-linux-gnu/asm/unistd_64.h | head -8
# #define __NR_read 0 / __NR_write 1 / __NR_open 2 / __NR_close 3

# 数一数这个内核有多少个系统调用
grep -c '__NR_' /usr/include/x86_64-linux-gnu/asm/unistd_64.h
# 约 360~460（随内核版本增长，6.x 已超过 450）
三个概念别混：系统调用是内核提供的唯一合法入口（约 450 个）；库函数是 libc 的普通函数（几千个），有的内部调系统调用（fopen → openat），有的纯用户态（strlen）；命令是用户态程序（ls），一个命令内部可能发起几十上百次系统调用。
模块 2

一次系统调用到底花了什么

"系统调用很贵"人人会说，但贵在哪里必须能一条条列出来，否则优化时只能瞎猜。

陷入内核时发生了什么

阶段动作谁做的
1. 保存返回位置下一条指令地址存进 rcx，rflags 存进 r11CPU
2. 切换栈从 TSS 读出内核栈指针，栈从用户栈换到内核栈CPU
3. 切特权级CS 段选择子改为 Ring 0，跳到内核入口CPU
4. 保存现场压栈通用寄存器、浮点/SIMD 状态（按需）内核
5. 换页表开了 KPTI 时切 CR3，最贵的一步，会冲刷 TLB内核
6. 查表分发按 rax 查 sys_call_table，做参数合法性检查内核
7. 拷参数用户指针指向的数据必须 copy_from_user 拷进来，不能直接解引用内核
8. 干活 / 返回真正的逻辑；然后恢复现场、切回用户栈和页表、sysret内核 + CPU

为什么参数必须拷贝

用户传进来的是虚拟地址，只在当前进程页表里有效。内核不能信任它：野指针会让内核崩溃；指针可能指向内核空间，成为提权漏洞；拷贝中可能触发缺页；另一个线程随时可能改写这块内存（TOCTOU 竞态）。所以必须先 copy_from_user 复制一份再校验。

这就是 copy_from_user / copy_to_user 存在的原因。一次 write(fd, buf, 65536) 至少拷 64KB，是实打实的内存拷贝，驱动层通常还要再拷一次（除非零拷贝）。

量级：多少纳秒

下面是普通 x86-64 服务器（3.0GHz 左右）的典型数量级。绝对值随 CPU 代次、KPTI、Spectre 缓解而变化，看比例比看绝对值有用。

操作典型耗时说明
函数调用（同进程内）1~2 ns基线，只是压栈跳转
clock_gettime（vDSO）20~30 ns不陷入内核，只读共享内存
getpid（真实系统调用）50~100 ns几乎不干活，纯切换开销
read 命中页缓存（4KB）0.5~1.5 μs切换 + 拷贝 4KB
write 到 socket（小包）1~3 μs切换 + 协议栈 + 可能触发软中断
线程上下文切换（同进程）1~2 μs不用换页表，便宜些
进程上下文切换2~5 μs比系统调用贵一个数量级，要换地址空间、冲 TLB
KPTI（内核页表隔离）的代价必须知道。它是 Meltdown 漏洞的缓解措施，把内核页表从用户态页表里摘出去，代价是每次进出内核都要切 CR3 并冲刷 TLB。实测系统调用开销增加 30%~200%，IO 密集负载整体性能下降 5%~30%。用 cat /sys/devices/system/cpu/vulnerabilities/meltdown 看当前状态。云上买到"未打补丁"的老镜像确实更快，但那不安全，不要这么做。

怎么自己测

用 clock_gettime(CLOCK_MONOTONIC) 夹住一个百万次循环，算平均耗时；注意别让编译器把循环优化掉。也可以直接用 sudo perf bench syscall all，内核自带基准。

一句话结论：系统调用不是"很慢"，而是"比函数调用贵 30~100 倍"。一次 100ns 无所谓；但循环里做 100 万次就是 100ms——这就是"频繁小调用"问题的全部根源。
模块 3

常用系统调用速览

450 多个系统调用里，日常真正会碰到的不到 40 个。按用途分组记，比按字母背有效。

文件与 IO

调用作用要点
openat打开文件，返回 fd取代了 open。多一个 dirfd，支持相对目录打开，避免 TOCTOU 漏洞
read / write顺序读写返回值可能小于请求长度，必须循环；返回 0 表示 EOF
pread / pwrite带偏移的读写不改变文件偏移量，多线程读写同一 fd 时必须用
readv / writev一次读写多块不连续内存减少系统调用次数，见模块 4
stat / statx取文件元信息statx 能取创建时间（btime）和挂载 ID
fsync / fdatasync把脏页刷到持久介质最贵的调用之一，一次几毫秒到几十毫秒
mmap / munmap把文件或匿名内存映射进地址空间省掉 read 的拷贝，但引入缺页开销
ioctl设备专用控制通道"万能后门"，参数语义完全由驱动定义，没有统一规范
fcntl改 fd 属性设 O_NONBLOCK、文件锁、FD_CLOEXEC 都靠它
dup2复制 fd 到指定编号shell 的 2>&1 就是它

进程与线程

clone 是 fork 和 pthread_create 的共同底层，靠 flags 决定共享什么：CLONE_VM 共享地址空间（→ 线程）、CLONE_NEWPID 新建 PID 命名空间（→ 容器）。execve 用新程序替换当前映像，不创建新进程，PID 不变。exit_group 退整个线程组，普通 exit 只退当前线程。wait4 回收子进程，不调它会留僵尸。prctl 设进程属性，如进程名、PR_SET_PDEATHSIG、seccomp 模式。

内存与同步

调用作用
brk调整堆顶。glibc malloc 在小块分配时用它
mmap大块分配（默认 ≥128KB 走 mmap）、文件映射、共享内存
mprotect改页权限。JIT 用它把代码页从"可写"改成"可执行"
madvise给内核提建议：MADV_DONTNEED 立刻回收、MADV_HUGEPAGE 用大页
futex所有 pthread 锁、信号量、条件变量的基石，见下

futex（Fast Userspace muTEX）的设计思想值得单独说，因为它解释了通用模式：无竞争时完全不进内核。

// pthread_mutex_lock 的实质（简化）
if (atomic_cas(&lock->state, 0, 1) == 0)
    return;                  // 抢到锁，20ns 搞定，一次系统调用都没有

// 抢不到，才调 futex 让内核把自己挂到等待队列上睡眠
syscall(SYS_futex, &lock->state, FUTEX_WAIT, 1, NULL, NULL, 0);

// 别人解锁时 futex(FUTEX_WAKE) 唤醒一个等待者

所以"加锁很慢"不准确：无竞争时只是一条 CAS 指令（约 20ns），有竞争才退化到内核睡眠唤醒（约 2~5μs）。差两个数量级，这也是高并发下"锁竞争"比"锁本身"可怕得多的原因。

网络

socket 创建 fd；bind + listen 进入监听，backlog 是已完成连接队列上限；accept4 取出连接，比 accept 多 flags，能原子设置 SOCK_NONBLOCK | SOCK_CLOEXEC；connect 非阻塞时返回 EINPROGRESS，要等可写事件；epoll_create1 / epoll_ctl / epoll_wait 中只有 wait 会阻塞，另两个是 O(1)。

时间与身份

clock_gettime / gettimeofday 都走 vDSO 不进内核（见模块 5）；nanosleep 实际会睡至少指定时长，通常多 50~100μs；getpid 被 glibc 缓存，常常也不进内核；权限判断看 geteuid 而不是 getuid。

为什么新代码都用 openat？它多了 dirfd 参数，可以"相对于某个已打开的目录"打开文件。① 服务长期运行时当前工作目录可能被换掉，绝对路径会打开错文件；② 先用 open(dir, O_PATH) 拿目录 fd，之后所有操作相对它，即使目录被 rename 也不会跑偏。glibc 里 open() 现在本身就是 openat(AT_FDCWD, ...) 的包装。
模块 4

为什么频繁小调用慢，怎么批量

这是系统调用知识里最能直接换成性能的一节。

先算一笔账

假设要发 1MB 数据，四种写法：

写法系统调用次数纯切换开销问题
每次 write 1 字节1,048,576约 105 ms还没算协议栈。每字节配 40 字节 TCP/IP 头，带宽放大 40 倍
每次 write 1KB1,024约 0.1 ms可接受，但仍有一千次切换
每次 write 64KB16约 2 μs接近最优
writev 一次发完1约 1 μs需要数据分散在多个 buffer 才划算

注意第一行：纯切换开销 105ms，而 1MB 在千兆网上真实传输只要 8ms。切换开销比真实工作大了十几倍。这就是"频繁小调用"的破坏力。

第一层：用户态缓冲

标准库早替你想过。stdio 的 FILE* 自带缓冲区，默认 BUFSIZ（glibc 上是 8192 字节）。

// 慢：每次 printf 都可能触发一次 write
for (int i = 0; i < 100000; i++) printf("%d\n", i);

// 快：攒满 8KB 才 write 一次，调用次数降到 1/1000
// 注意：连终端时是行缓冲（遇 \n 就刷），连文件/管道时是全缓冲
setvbuf(stdout, NULL, _IOFBF, 1 << 16);   // 强制全缓冲 64KB

// 更彻底：自己拼大 buffer，最后一次 write
char buf[65536]; int n = 0;
for (int i = 0; i < 100000; i++) {
    n += snprintf(buf + n, sizeof(buf) - n, "%d\n", i);
    if (n > sizeof(buf) - 64) { write(fd, buf, n); n = 0; }
}
if (n) write(fd, buf, n);
行缓冲是个隐蔽的坑。程序在终端里跑得好好的，一重定向到文件就变慢或日志迟迟不落盘——因为缓冲模式变了。排查这类问题第一件事是确认 setvbuf 设置和 isatty(fileno(stdout)) 的返回值。

第二层：writev 合并多次写

数据天然分散在几个 buffer 里时（比如 HTTP 响应 = 状态行 + 头部 + body），naive 写法是三次 write，writev 一次搞定：

#include <sys/uio.h>
struct iovec iov[3];
iov[0].iov_base = "HTTP/1.1 200 OK\r\n";  iov[0].iov_len = 17;
iov[1].iov_base = headers;                iov[1].iov_len = hlen;
iov[2].iov_base = body;                   iov[2].iov_len = blen;

ssize_t n = writev(fd, iov, 3);   // 1 次系统调用，内核按顺序拼起来发
ssize_t m = readv(fd, iov, 3);    // 读侧对应，省一次拼接拷贝

边界：IOV_MAX 默认 1024，超过返回 EINVAL。而且 writev 不保证一次写完，返回值可能小于总长度，仍要循环。

第三层：零拷贝

普通 read + write 发文件要拷四次（磁盘→页缓存→用户 buffer→socket buffer→网卡），中间两次纯浪费。sendfile(out_fd, in_fd, &off, len) 让数据不经过用户态，拷贝降到 2 次、切换降到 1 次，是 Nginx 发静态文件的默认方式；splice 用管道中转可以做到 0 次拷贝。边界：sendfile 要求数据不需要修改，要加工内容还是得走用户态。

第四层：io_uring 的思路

前三层都在"减少次数"，io_uring 走另一条路：把系统调用本身变成共享内存里的队列操作。

共享两个环。内核和应用共享提交队列（SQ）和完成队列（CQ）。应用把"要做什么"写进 SQ，内核把"做完了"写进 CQ。
批量提交。攒 128 个请求调一次 io_uring_enter 全部提交，系统调用次数从 128 降到 1。
可选内核轮询。注册 IORING_SETUP_SQPOLL 后内核起线程轮询 SQ 环，应用连那一次 enter 都不用调，实现零系统调用。
异步完成。不像 epoll 只说"可读了"，io_uring 是"我已经把数据读进你的 buffer 了"，省掉再调一次 read 的往返。
方案每请求系统调用本质
阻塞 IO1（read 本身阻塞）一个线程一个连接
epoll + 非阻塞2（epoll_wait + read）事件通知，仍要自己读
io_uring（默认）<1（可批量摊薄）共享内存提交队列
io_uring + SQPOLL0内核线程轮询，烧一个核
但别急着上 io_uring。收益在高 IOPS + 小请求场景才明显（NVMe 上的数据库、代理）。普通业务一次请求读几十 KB，切换开销占比不到 1%，改造成本远大于收益。而且它有内核版本要求（5.1 引入，5.6 后才逐渐可用），部分容器运行时受 seccomp 限制会直接挡掉 io_uring_setup。
模块 5

vDSO：不进内核也能拿时间

如果每次取时间都要陷入内核，一个每秒打一万条日志的服务光取时间就要烧掉 1% 的 CPU。vDSO 就是为这类"高频但只读"的调用准备的旁路。

它是什么

vDSO（virtual Dynamic Shared Object）是内核在每个进程启动时自动映射进用户地址空间的一小段代码页。它是真正的机器码，由内核提供，但跑在用户态。

# 每个 Linux 进程地址空间里都有它，名字就叫 [vdso]
cat /proc/self/maps | grep vdso
# 7ffd3b7fe000-7ffd3b800000 r-xp 00000000 00:00 0  [vdso]
# 权限 r-xp：可读可执行，不可写

# 导出成文件看它导出了哪些函数
readelf -s /proc/self/map_files/* 2>/dev/null | grep FUNC | head

为什么快

内核把当前时间维护在一个用户态可读的共享内存页里，用 seqlock（乐观锁：读前后各取一次版本号，不一致就重读）保证读到自洽的值。取时间于是变成：读版本号 → 读秒/纳秒/TSC → 再读版本号校验，不一致就重试。

整个过程没有特权级切换、没有栈切换、没有页表切换，就是几十条普通指令加一次内存读。

调用耗时走 vDSO？
clock_gettime(CLOCK_MONOTONIC)20~30 ns是
gettimeofday20~30 ns是
time15~25 ns是
clock_gettime(REALTIME_COARSE)5~10 ns是，精度只到 tick（1~10ms）
getpid50~100 ns否（glibc 自己缓存）

怎么验证它真的没进内核

# 用 strace 统计，你会发现 clock_gettime 一次都没出现
strace -c -f ./your_program
# % time     seconds  usecs/call     calls    errors syscall
#  45.12    0.001234          12    100000           write
#   3.20    0.000087           8     10000           read
# 没有 clock_gettime 这一行，因为它压根没陷入内核

# 想强制走真实系统调用（做对比实验）
syscall(SYS_clock_gettime, CLOCK_MONOTONIC, &ts);   // 绕过 vDSO 包装

边界：vDSO 不能做什么

  • 只能读，不能改。无法替代任何需要写内核状态的操作，所以永远不会有 write 或 open 的 vDSO 版本。
  • 代码由内核决定。老内核可能没有新函数的实现，glibc 会退化成真实系统调用，你无法控制。
  • 时钟源不稳定时会退化。TSC 不可靠（跨核不同步、频率漂移）时内核会关掉 vDSO 快路径，虚拟机里尤其常见。看 cat /sys/devices/system/clocksource/clocksource0/current_clocksource。
  • vsyscall 是它的前身，已废弃。老的固定地址映射有安全风险，新内核默认 vsyscall=none。
通用启示：凡是"高频、只读、数据结构简单"的内核服务，都可以用"共享内存 + 用户态代码"旁路掉。vDSO 是时间，io_uring 的 SQ/CQ 环本质上是同一个思路用在 IO 上。
模块 6

追踪手段：strace / ltrace / perf

三个工具解决三个不同层次的问题，选错了会白忙一天。

工具原理开销什么时候用
straceptrace 挂住目标，每次进出内核停一次10~100 倍程序卡住、报错、行为诡异
ltrace同样用 ptrace，断在库函数入口（PLT）10~50 倍想知道调了哪些 libc 函数，如 malloc/free 配对
perf trace基于内核 tracepoint，不用 ptrace1.1~2 倍生产上想知道调用分布，又不方便停机
bpftraceeBPF 挂内核函数，聚合在核内完成< 1.1 倍按进程/参数聚合，长期观察

strace 的核心用法

# 1. 统计模式：最常用，先看全局（-f 必加，否则看不到子线程）
strace -c -f ./app

# 2. 只看某几类调用，大幅降噪
strace -e trace=file ./app          # 所有带文件路径的调用
strace -e trace=network ./app       # 所有网络相关

# 3. 加时间戳看每一步耗时（-tt 绝对时间，-T 单次耗时）
strace -tt -T -f ./app

# 4. 附加到运行中的进程（会暂停目标，生产慎用）
strace -p 12345 -c

# 5. 输出到文件再分析，避免拖慢终端
strace -o /tmp/trace.log -f -tt ./app
grep -E 'E[A-Z]+ ' /tmp/trace.log | head -20    # 找所有失败的调用

怎么读 -c 的统计表

% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 62.31    0.482913          48     10000           futex
 18.44    0.142883          14     10000           write
  9.87    0.076512           7     10000           read
  5.12    0.039681           3     12000      4000 openat
  2.01    0.015582         155       100           fsync
------ ----------- ----------- --------- --------- ----------------
100.00    0.775571                 42100      4000 total
  1. 先看 errors 列。4000 次 openat 失败，说明在反复尝试打开不存在的文件（常见于配置查找、动态库搜索路径）。这通常是逻辑问题，不是性能问题，但开销是实打实的。
  2. 再看 % time 最高的。futex 占 62%，说明大量时间花在锁等待上——这是并发设计问题，换更快的系统调用没用。
  3. 然后看 usecs/call 异常的。fsync 单次 155μs，只有 100 次但值得注意；如果变成 10000 次就是 1.5 秒。
  4. 最后看 calls 特别大的。10000 次 write 对应 10000 次切换，合并成 100 次就省掉 99%。
strace -c 的三个陷阱：① 时间统计包含阻塞等待——一次 read 等网络数据挂 100ms，这 100ms 会记到 read 头上，让你误以为 read 实现得差。看到异常大的 usecs/call 先怀疑"它在等什么"。② 必须加 -f，否则子线程的调用完全看不到，你会得出"程序什么都没干"的错误结论。③ 绝对值不可信，ptrace 的开销摊到每次调用上，所有值都被放大，看比例和次数。

perf trace 与 bpftrace：低开销替代品

# 汇总模式，开销远低于 strace；对运行中进程采样 10 秒
sudo perf trace -p 12345 -s sleep 10

# 统计系统调用总次数（不记录细节，开销最低）
sudo perf stat -e 'syscalls:sys_enter_*' -a sleep 5

# bpftrace：按进程统计调用次数，一条命令出结果
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'
选择建议：开发/测试环境定位 → strace -c -f（信息最全，慢也无所谓）。生产不能停机 → perf trace -s 或 bpftrace。只想看"哪个进程在疯狂调什么" → bpftrace 的 raw_syscalls 计数。
模块 7

四个典型性能问题

这四个几乎覆盖了"系统调用用得不对"的绝大多数线上事故。

问题一：大量小 write

症状：%sys 高（超过 30%）、%user 不高；strace -c 里 write 次数惊人；网络包数远大于业务请求数。根因：日志没缓冲、逐条发消息。每次 write 都要切内核、走一遍 TCP 栈、可能触发软中断、组一个几十字节的包。

strace -c -f -p <pid>      # 看 write 的 calls 数
sar -n DEV 1 5             # 看 pps 是否异常高
pidstat -w -p <pid> 1      # 看自愿上下文切换是否极高

修：应用层加缓冲（bufio / 批量接口）、日志改异步批量刷、TCP_CORK 攒包（和 TCP_NODELAY 二选一，别同时开）。

问题二：fsync 太多

症状：写延迟 P99 从 1ms 涨到 20ms；iostat -x 里 f/sync 高、aqu-sz 排队。根因：每条记录都 write + fsync。fsync 必须等数据真正落到介质，一次就是毫秒级；机械盘随机写 IOPS 只有 100~200，吞吐上限就是每秒一两百条。

做法每次 fsync 延迟吞吐
每条记录一次 fsync5~20 ms50~200 条/秒
每 100 条一次 fsync5~20 ms（摊薄）5000~20000 条/秒
group commit（多线程合并）同上接近设备上限

数据库的 group commit 就是这个思路：多个事务的 redo 先写进同一个 buffer，第一个到达的线程负责 fsync，其他线程在条件变量上等它完成再一起返回。100 个并发事务只产生 1 次 fsync。金融交易要求"返回成功即已持久化"，就只能接受延迟或换 NVMe。

问题三：epoll_wait 空转

症状：单核 100% 的 %sys，但 QPS 很低；epoll_wait 几百万次、几乎每次都返回 0。根因：timeout 传了 0。

int n = epoll_wait(epfd, events, 1024, 0);   // ✗ 立刻返回，没事件也返回
int n = epoll_wait(epfd, events, 1024, -1);  // ✓ 有事件才醒
int n = epoll_wait(epfd, events, 1024, 100); // ✓ 需要定时任务时给 100ms 超时

变种：等一个永远不会就绪的 fd（对端已关闭但没注销），或水平触发下没把数据读干净，每次都立刻返回同一事件。

怎么区分空转和真忙：看 epoll_wait 的 calls 数 ÷ 运行秒数。超过 10 万次/秒而 QPS 只有几百，肯定是空转。另外 grep voluntary_ctxt_switches /proc/<pid>/status，空转时这个数会疯涨。

问题四：漏了 O_NONBLOCK

症状：一个客户端卡住，整个服务无响应，但 CPU 是 0。/proc/<pid>/stack 显示线程停在 read 或 write 上。根因：事件循环单线程，某个 fd 是阻塞模式，对端不发数据就把整个循环卡死。

cat /proc/<pid>/task/<tid>/stack     # 看卡在哪个系统调用
cat /proc/<pid>/fdinfo/<fd>         # flags 04002 有 O_NONBLOCK；02 没有

int fd = accept4(lfd, NULL, NULL, SOCK_NONBLOCK | SOCK_CLOEXEC);   // ✓ 创建时就带上
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);    // ✓ 修改而不是覆盖
O_NONBLOCK 只影响"会不会阻塞"，不影响"数据是否完整"。read 返回 EAGAIN 表示"现在没数据"，返回小于请求长度表示"只读到这么多"，两种情况都必须正确处理。很多"偶发丢包"就是把 EAGAIN 当成了 EOF。

另外三个高频小问题：错误分支忘记 close 导致 fd 泄漏（最终报 EMFILE，用 ls /proc/<pid>/fd | wc -l 监控）；慢系统调用被信号打断返回 EINTR，语义是"请重试"；getaddrinfo 是阻塞的，DNS 抖动会卡住整个线程。

模块 8

容器里的系统调用

同一份二进制，在物理机上跑得好好的，进了容器就报 Operation not permitted。90% 是 seccomp 干的。

seccomp 是什么

seccomp（secure computing mode）是内核提供的一层系统调用过滤器。它用 BPF 程序描述"哪些调用允许、哪些拒绝"，在进入内核的第一步就判断，比任何权限检查都早。

Docker 默认加载一个白名单 profile，屏蔽约 44 个系统调用。被屏蔽的调用返回 EPERM 而不是 ENOSYS——因为返回 ENOSYS 会让程序以为内核太老，从而走奇怪的兼容路径。

被默认屏蔽的调用为什么屏蔽典型报错
mount / umount2能挂载宿主机设备，直接逃逸EPERM
ptrace能读写其他进程内存，注入代码EPERM（strace 失败的原因）
bpf能加载 eBPF 程序，历史上出过多次提权漏洞EPERM
init_module / finit_module加载内核模块EPERM
kexec_load / reboot加载新内核 / 重启宿主机EPERM
perf_event_open性能计数器，可做侧信道泄密EPERM（perf 用不了）
keyctl / add_key内核密钥环EPERM
clone3（老 runc）参数结构体新，老 profile 不认，直接拒EPERM 或 ENOSYS

怎么判断是 seccomp 还是权限问题

先看 errno。EPERM 通常是 seccomp 或 capability 不足；EACCES 是文件权限；ENOSYS 可能是内核不支持，也可能是运行时故意伪装的 seccomp 拒绝。
查进程的 seccomp 状态。grep Seccomp /proc/<pid>/status：0 未启用，1 strict 模式（几乎不用），2 filter 模式（Docker 默认）。
看容器安全配置。docker inspect <name> --format '{{.HostConfig.SecurityOpt}}'，出现 seccomp=unconfined 说明没过滤。
做对照实验。用 --security-opt seccomp=unconfined 重跑，问题消失就确认是 seccomp。
# 1. 看 seccomp 模式与能力位图
grep -E 'Seccomp|CapEff' /proc/self/status
# Seccomp: 2            ← 2 = filter 模式，Docker 默认
# CapEff: 00000000a80425fb
capsh --decode=00000000a80425fb   # 解码，确认没有 cap_sys_admin

# 2. 复现最小案例
strace -f -e trace=mount mount -t tmpfs none /mnt
# mount(...) = -1 EPERM (Operation not permitted)

# 3. 去掉 seccomp 再试，问题消失即确认
docker run --rm -it --security-opt seccomp=unconfined ubuntu:24.04 \
  bash -c 'mount -t tmpfs none /mnt && echo OK'

# 4. 若仍失败，是 capability 不够
docker run --rm -it --cap-add=SYS_ADMIN ubuntu:24.04 \
  bash -c 'mount -t tmpfs none /mnt && echo OK'

clone3 那个著名的坑

2023 年出现过影响面很大的问题：新版 glibc（2.34+）的 pthread_create 优先尝试 clone3，失败再回退 clone。老版本 Docker/runc 的 profile 里没有 clone3 规则，默认动作是 SCMP_ACT_ERRNO(ENOSYS)，按理能正常回退。但某些组合下（runc 1.1.5 之前）返回的是 EPERM 而非 ENOSYS，glibc 认为"这是权限问题"就不回退，于是所有建线程操作失败，程序起不来。判断：runc --version 低于 1.1.5 有风险；根治是升级运行时。

该不该放开 seccomp

--security-opt seccomp=unconfined 只应作为排查手段，不要写进生产编排。它把 44 个高危调用全部放开，配合默认 root 用户，容器逃逸门槛会大幅降低。正确做法是写自定义 profile：从默认 profile 出发，只把确实需要的那一两个调用（如 clone3、perf_event_open）改成 ALLOW。Kubernetes 里通过 securityContext.seccompProfile 指定。
需求需要放开什么风险
容器内跑 strace / gdbCAP_SYS_PTRACE + seccomp 放行 ptrace能读写同命名空间内其他进程内存
容器内跑 perfCAP_PERFMON + 放行 perf_event_open可做侧信道攻击
容器内挂载卷CAP_SYS_ADMIN + 放行 mount接近完全逃逸，慎用
容器内改内核参数/proc/sys 可写 + 该参数非 namespace 化影响宿主机所有容器
常见坑

十个真实踩过的坑

1
以为 write 一定会把数据写完
socket、管道、被信号打断后，返回值都可能小于请求长度。不检查就丢数据，且只在高压下偶发。
2
把 EINTR 当成真错误
被信号打断时什么都没发生，语义是"请重试"。很多框架在这里抛异常，表现为"偶发连接失败"。
3
在压测时挂 strace
开销 10~100 倍，测出的 QPS 和延迟毫无意义，还会因超时掩盖真正的瓶颈。
4
strace 不加 -f
多线程程序的工作线程全看不到，你只看到主线程在 futex 上等，得出"什么都没干"的错误结论。
5
日志逐条 write 且不缓冲
每秒一万条日志 = 一万次系统调用 + 一万个网络包。用异步 appender + 批量刷盘。
6
每条记录都 fsync
机械盘上直接把吞吐锁死在每秒一两百条。批量提交、接受延迟、换 NVMe，三选一。
7
epoll_wait 传 timeout=0
变成忙轮询，单核 100% 的 %sys 但 QPS 极低。传 -1 阻塞，或传有意义的超时。
8
accept 出来的 fd 忘了设 O_NONBLOCK
监听 fd 非阻塞不代表新连接也是。一个慢客户端就能让整个事件循环停住。用 accept4 一次带上。
9
fd 没设 CLOEXEC，被子进程继承
父进程 close 了连接也释放不掉（引用计数还在），表现为"端口不释放"和 fd 缓慢泄漏。
10
容器报 EPERM 就去加 --privileged
这是最危险的"修复"。正确顺序：看 errno → 看 Seccomp → 看 CapEff → 只放开需要的那一项。
自测

六道题

1. 用户态程序执行 cli（关中断）指令，会发生什么？
正确答案：CPU 抛异常。特权指令的拦截在硬件层，不是内核软件检查，所以进程收到 SIGSEGV 而不是 errno。
2. 一次 getpid 系统调用大约耗时多少？
正确答案：50~100 纳秒。它几乎不干实事，耗时全是模式切换。梯度：函数调用 1~2ns，系统调用 50~100ns，进程切换 2~5μs。
3. 为什么 clock_gettime 比 getpid 快好几倍？
正确答案：vDSO。内核在每个进程里映射了一段 [vdso] 代码页，用 seqlock 读共享数据，所以 strace -c 里看不到它。但它不是纯 libc 函数，特殊时钟源下会退化成真实系统调用。
4. 要发 1MB 数据，下面哪种写法最快？
正确答案：每次 64KB。1 字节写法光切换就要约 100ms，还要为每字节配 40 字节协议头。64KB 接近 socket 缓冲上限，切换降到 16 次。
5. strace -c 显示 futex 占 62% 时间，怎么优化？
正确答案：改并发设计。futex 时间高说明线程在等锁，方向是缩小临界区、按 key 分片、换无锁结构。而且 strace 的时间包含阻塞等待，62% 不代表 futex 本身慢。
6. 容器里 strace 报 ptrace: Operation not permitted，最可能的原因是？
正确答案：seccomp + capability 双重限制。用 grep Seccomp /proc/self/status 看是否返回 2，用 capsh --decode=$(grep CapEff /proc/self/status | awk '{print $2}') 看有没有 SYS_PTRACE。
