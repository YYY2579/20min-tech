二十分钟学透容器内核机制

容器不是"轻量虚拟机"，是一个被七层视图隔离、被 cgroup 限额、被 chroot 换了根目录的普通进程。这句话能解释容器 90% 的"怪现象"。

起一个容器：docker run -it --rm ubuntu:24.04 bash
开始前

起一个容器，先看它的"内脏"

这一节的所有结论，都能在下面这几条命令里亲眼看到。

# 1. 起一个容器，记下它的 PID（宿主机视角）
docker run -d --name demo nginx:alpine
PID=$(docker inspect -f '{{.State.Pid}}' demo)
echo $PID
# 12345

# 2. 在宿主机上，它就是一个普通进程
ps -p $PID -o pid,ppid,user,comm,args
# 12345  1  root  nginx  nginx: master process nginx -g daemon off;

# 3. 看它有哪些 namespace（每个 ns 是一个 inode）
ls -l /proc/$PID/ns/
# cgroup -> 'cgroup:[4026531835]'
# ipc    -> 'ipc:[4026532508]'
# mnt    -> 'mnt:[4026532506]'
# net    -> 'net:[4026532509]'
# pid    -> 'pid:[4026532507]'
# user   -> 'user:[4026531837]'
# uts    -> 'uts:[4026532505]'

# 4. 看它的根目录（不是宿主机的 /）
sudo ls -l /proc/$PID/root/
# 这就是 overlayfs 的 merged 目录
记住这个 PID。后面所有排查手段——nsenter、看真实 /proc、抓包、strace——都建立在"容器进程在宿主机有真实 PID"这个事实上。容器里的 PID 1，在宿主机上可能是 12345。
模块 1

七种 namespace，各自隔离什么

namespace 的作用是让进程看到不同的"系统视图"，不限制用量（那是 cgroup 的事）。

namespaceclone 标志隔离什么典型表现
PIDCLONE_NEWPID进程 ID 空间。容器里的 1 号进程是宿主机上某个普通进程，且看不到宿主机其他进程容器里 ps aux 只有自己几个进程；kill -9 1 会把容器干掉
NETCLONE_NEWNET网卡、IP、路由表、iptables 规则、端口空间、/proc/net容器有自己的 eth0 和 172.17.0.x；lo 默认是 down 的
MNTCLONE_NEWNS挂载点视图。每个 ns 有独立的 mount table容器看不到宿主机的挂载；/proc 要重新挂一次才是自己的
UTSCLONE_NEWUTS主机名（hostname）和域名（domainname）容器里 hostname 返回容器 ID，不影响宿主机
IPCCLONE_NEWIPCSystem V 共享内存、消息队列、信号量、POSIX 消息队列容器间的共享内存互不可见
USERCLONE_NEWUSERUID/GID 映射。容器里的 root 可以映射成宿主机的普通用户容器内 id 是 0，宿主机上对应 100000
CGROUPCLONE_NEWCGROUP/proc/self/cgroup 的显示路径容器里看到 /，宿主机看到 /docker/<id>

Linux 5.6 之后还有第八种 time namespace（CLONE_NEWTIME），隔离 CLOCK_MONOTONIC 和 CLOCK_BOOTTIME 的起点，主要用于 CRIU 迁移后保持时间连续。日常运维基本碰不到。

PID namespace：1 号进程的特殊性

容器里的 PID 1 和普通 init 一样，承担两个额外职责：回收孤儿进程和转发信号。这带来两个经典问题：

  • 应用不是为 PID 1 写的。很多程序（如 nginx、java）不会处理 SIGTERM 转发，也不会 wait() 孤儿进程，导致 docker stop 等 10 秒超时后 SIGKILL，以及僵尸进程堆积。解法是用 tini 或 --init。
  • PID 1 对默认信号免疫。内核不会给 PID 1 投递没有注册 handler 的信号。所以 kill -9 1 在容器里有效（SIGKILL 不可捕获），但 kill 1（SIGTERM）可能毫无反应。
# 看容器里的进程树（只有自己的）
docker exec demo ps -ef
# PID   USER     TIME  COMMAND
#     1 root      0:00 nginx: master process
#    29 nginx     0:00 nginx: worker process

# 宿主机上看到的是完整 PID，且能看到父进程是 containerd-shim
ps -ef | grep nginx
# root 12345 12300  0 10:00 ?  00:00:00 nginx: master process
# root 12400 12345  0 10:00 ?  00:00:00 nginx: worker process

# 用 --init 给容器加一个 tini 作为 PID 1
docker run -d --init --name demo2 nginx:alpine

NET namespace：为什么容器里 ping 不通 127.0.0.1

新建的 net namespace 里只有一块 lo，而且状态是 DOWN。Docker 会把容器接到网桥上并启用 eth0，但不会自动启用 lo——除非镜像的启动脚本自己做了。

# 容器里看网卡
ip addr
# 1: lo: <LOOPBACK> mtu 65536 qdisc noop state DOWN
# 2: eth0@if15: <BROADCAST,MULTICAST,UP> mtu 1500 state UP
#    inet 172.17.0.2/16 brd 172.17.255.255 scope global eth0

# 手动启用 lo（容器内需要 CAP_NET_ADMIN）
ip link set lo up

# 注意 eth0@if15 的 if15：这是宿主机上 veth 对的另一端索引
# 在宿主机上 ip link 能看到 vethXXXX，两边是一对

USER namespace：容器里的 root 不一定是真 root

默认情况下（非 rootless），Docker 容器里的 root 就是宿主机的 root，只是被 capability 和 seccomp 削掉了大部分权力。开启 userns-remap 后才会映射：

# 看 UID 映射表（三个数字：容器内起始、宿主起始、长度）
cat /proc/$PID/uid_map
#          0       1000          1
# 表示容器里的 uid 0 对应宿主机的 uid 1000

# 默认 Docker 没开 userns-remap 时是这样
cat /proc/$PID/uid_map
#          0          0 4294967295   ← 一一对应，容器 root = 宿主 root

# 开启 userns-remap（/etc/docker/daemon.json）
{ "userns-remap": "default" }
这是容器安全的核心认知："容器里是 root"默认等于"宿主机上是 root"，只是被 capability 限制了。一旦容器拿到 CAP_SYS_ADMIN 或发生内核逃逸，攻击者直接就是宿主 root。真正要靠 userns-remap 或 rootless 容器才能改变这个等式。
模块 2

cgroup v1 与 v2

namespace 管"看到什么"，cgroup 管"能用多少"。两套机制合起来才是一个容器。

维度cgroup v1cgroup v2
层级结构多棵树，每个控制器一棵（cpu 一棵、memory 一棵、blkio 一棵）一棵树，所有控制器挂在同一棵树上
进程归属一个进程可以同时属于不同树的不同的组一个进程只能属于一个组，路径唯一
挂载点/sys/fs/cgroup/cpu/...
/sys/fs/cgroup/memory/...		/sys/fs/cgroup/<group>/
CPU 限额cpu.cfs_quota_us + cpu.cfs_period_uscpu.max（"配额 周期"两个数一行）
内存限额memory.limit_in_bytesmemory.max / memory.high
IO 限额blkio.throttle.read_bps_deviceio.max（按设备号一行配 rbps/wbps/riops/wiops）
压力指标无统一接口PSI（pressure stall information），能看 CPU/IO/内存的真实阻塞时间
子组权限混乱，各控制器规则不同统一，支持委派给非 root 用户

v1 的四个具体问题

  • 无法原子地限制一组资源。要给容器同时设 CPU 和内存，得往两棵树的目录里分别写，中间有窗口期。
  • 统计口径不一致。memory 和 blkio 对同一个页的记账方式不同，OOM 时经常算不清是谁的责任。
  • 层级冲突。同一个进程在 cpu 树里在 A 组，在 memory 树里在 B 组，出问题时无法用一条路径定位。
  • 控制器数量爆炸。每个控制器一棵树，容器运行时要做十几次挂载，启动慢、易出错。

v2 的关键改进

# v2 的目录结构：一个容器一个目录，所有控制器都在里面
ls /sys/fs/cgroup/system.slice/docker-<id>.scope/
# cgroup.controllers  cgroup.subtree_control  cpu.max  cpu.stat
# io.max  io.stat  memory.max  memory.current  memory.events  pids.max

# 限制 2 核（200ms / 100ms）
echo "200000 100000" > /sys/fs/cgroup/.../cpu.max

# 限制内存 1G，软限 800M（超过软限会先触发回收而不是直接 OOM）
echo 1073741824 > /sys/fs/cgroup/.../memory.max
echo 838860800  > /sys/fs/cgroup/.../memory.high

# 限制 8:0 这块盘：读 10MB/s 写 10MB/s，读写各 1000 IOPS
echo "8:0 rbps=10485760 wbps=10485760 riops=1000 wiops=1000" \
  > /sys/fs/cgroup/.../io.max

# 看当前用量和 OOM 次数
cat /sys/fs/cgroup/.../memory.current
cat /sys/fs/cgroup/.../memory.events
# low 0 / high 12 / max 3 / oom 1 / oom_kill 1

为什么要迁移

PSI 是刚需
v2 的 cpu.pressure / io.pressure / memory.pressure 能直接告诉你"有多少时间被卡住了"，比看使用率有用得多。
rootless 容器
v2 支持把子树的控制权委派给普通用户，这是 rootless Docker / Podman 的前提。v1 做不到干净地委派。
systemd 统一管理
新版本 systemd 默认用 v2 记账，v1 下很多资源统计对不上，systemd-cgtop 数字会漂。
内核在移除 v1
新内核（6.x）里部分控制器的 v1 实现已经不再积极维护，新特性只加在 v2 上。
# 看当前用的是 v1 还是 v2
stat -fc %T /sys/fs/cgroup/
# cgroup2fs  → v2
# tmpfs      → v1（混合模式也是 tmpfs）

# 看挂载情况
mount | grep cgroup

# 内核启动参数强制 v2（GRUB 里加）
# systemd.unified_cgroup_hierarchy=1
迁移时最容易踩的坑：v1 的 cpu.cfs_quota_us = -1 表示"不限制"，v2 里没有这个概念——不写 cpu.max 就是 max。很多脚本把 -1 直接写进 v2 会报错。另外 v1 的 memory.memsw（内存+swap 合计限制）在 v2 里被拆成了 memory.max + memory.swap.max，换算关系不是 1:1。
模块 3

容器的文件系统：overlayfs

容器能"秒级启动"，一半功劳在镜像分层。overlayfs 是让多个只读层叠成一个可写视图的技术。

四个目录

角色作用
lowerdir只读层，可以有多个（镜像的每一层一个）。多个容器共享同一份
upperdir可写层，容器自己的修改都落在这里。每个容器一份
workdiroverlayfs 内部用的临时目录，必须在同一文件系统
merged合并后的视图，这就是容器看到的 /
# 宿主机上看某个容器的 overlay 挂载
mount | grep overlay
# overlay on /var/lib/docker/overlay2/abc.../merged type overlay (rw,relatime,
#   lowerdir=/var/lib/docker/overlay2/l/A1:/var/lib/docker/overlay2/l/B2:...,
#   upperdir=/var/lib/docker/overlay2/abc.../diff,
#   workdir=/var/lib/docker/overlay2/abc.../work)

# 镜像有几层，lowerdir 就有几个，用冒号分隔，靠前的优先级高
docker image inspect nginx:alpine --format '{{len .RootFS.Layers}}'
# 6

写时复制（copy-up）

容器要修改一个在只读层里的文件时，overlayfs 不会改原文件，而是：

把整个文件从 lowerdir 复制到 upperdir（copy-up）。注意是整个文件，不是只复制要改的那几个字节。
在 upperdir 的副本上做修改。lowerdir 里的原文件纹丝不动，其他容器看到的还是旧内容。
之后的读也走 upperdir（因为上层优先）。原文件被"遮蔽"了，但仍然占着磁盘。

copy-up 的代价和文件大小成正比。改一个 1GB 镜像层里的 1 字节配置文件，要先把 1GB 复制一遍。这就是为什么"容器里改大文件"很慢，也是为什么镜像层要尽量小。

# 看某个容器的可写层占了多少空间
docker ps -s
# CONTAINER ID   ...   SIZE
# abc123         ...   12.3MB (virtual 142MB)
#                       ↑可写层  ↑含镜像层的总大小

# 直接看 upperdir 目录
sudo du -sh /var/lib/docker/overlay2/<id>/diff

为什么容器层不能持久化

因为 upperdir 的生命周期绑在容器上：

操作upperdir 会怎样
docker restart保留，容器没被删除，可写层还在
docker stop + start保留
docker rm删除，数据全丢
docker run 新容器全新的空 upperdir，看不到旧容器的修改
K8s Pod 重建删除，Pod 是最小生命周期单位

所以要持久化，必须把数据写到挂载卷（volume/bind mount）上，让路径绕过 overlayfs，直接落到宿主机目录或网络存储。

# 三种挂载方式
docker run -v /data:/app/data nginx        # bind mount，直接映射宿主目录
docker run -v myvol:/app/data nginx        # named volume，Docker 管理的目录
docker run --tmpfs /tmp nginx              # 内存盘，容器删除即消失

# 注意：挂载点会"盖住"镜像里同路径的内容
# 如果镜像里 /app/data 有初始文件，挂一个空 volume 上去就看不见了
# 这叫 "volume shadowing"，是"挂载后配置丢失"的常见原因
不要用 docker commit 当备份。它把可写层打包成新镜像，看起来能"保存状态"，但：① 镜像会越来越大（每一层都是全量 diff）；② 里面混进了日志、临时文件、密钥；③ 无法回滚到某个时间点。正确做法是数据进 volume，配置进镜像构建流程。
模块 4

容器到底是什么

把所有机制拆掉之后，剩下的就是一个 clone() 出来的进程。

一次容器启动，内核里发生了什么

clone() 带一堆 CLONE_NEW* 标志。创建新进程的同时创建新的 namespace。这一步之后，子进程已经"看不到"宿主机的 PID、网络、挂载。
准备 rootfs。把镜像的若干层用 overlayfs 挂成一个 merged 目录，然后 pivot_root() 或 chroot() 切过去。
挂 /proc、/sys、/dev。注意 /proc 必须在新 PID namespace 里重新挂载，否则看到的是宿主机的进程列表。
设置 cgroup 限额。把 PID 写进 cgroup 的 cgroup.procs，设 cpu.max / memory.max / pids.max。
降权。设置 capability 集合（丢掉大部分）、seccomp 过滤器、AppArmor/SELinux 策略、只读挂载。
execve() 启动应用。容器里看到的 PID 1，就是这次 exec 的程序。

宿主机上它长什么样

# 1. 就是一个进程，父进程是 containerd-shim
ps -ef | grep -E 'containerd-shim|nginx'
# root 12300     1  0 10:00 ?  00:00:00 containerd-shim-runc-v2 -namespace moby
# root 12345 12300  0 10:00 ?  00:00:00 nginx: master process

# 2. 它的 cgroup 路径暴露了归属
cat /proc/12345/cgroup
# 0::/system.slice/docker-abc123...scope

# 3. 它的根目录是 overlay 的 merged
sudo ls -l /proc/12345/root
# /proc/12345/root -> /var/lib/docker/overlay2/abc.../merged

# 4. 它挂载的文件系统和宿主机不同
sudo cat /proc/12345/mountinfo | head -5
# 会看到 overlay / 以及容器自己的 proc、tmpfs、/dev/shm

# 5. 它的能力集被削过
grep Cap /proc/12345/status
# CapInh: 0000000000000000
# CapPrm: 00000000a80425fb
# CapEff: 00000000a80425fb   ← 只有默认那十几项
# CapBnd: 00000000a80425fb

所以"容器"没有对应的内核对象。你在 /proc 里找不到叫 container 的东西，只有进程、namespace、cgroup、挂载点。容器是一个约定，不是内核实体。

一个直接推论：宿主机上 ps aux 能看到所有容器里的进程（因为 PID namespace 只影响"容器内怎么看"，不影响"宿主机怎么看"）。同样，top 里也能看到它们的 CPU 占用。这让排查变简单，也让"容器隔离"这件事的边界变得很清楚。

为什么"容器里看不到宿主机进程"

不是内核隐藏了，而是 /proc 是在新 PID namespace 里挂载的。/proc 是虚拟文件系统，列出的内容由"挂载时所在的 PID namespace"决定。同一个内核挂两次，就是两份不同的视图。

ls /proc | grep -E '^[0-9]+$' | sort -n | tail -1          # 宿主机：89432
docker exec demo sh -c 'ls /proc | grep -E "^[0-9]+$" | wc -l'
# 容器里只有几十个，因为只列出本 namespace 的进程
模块 5

为什么容器里的 CPU/内存和宿主机不一致

这是容器运维最常见的困惑：-m 512m 起的容器，free -h 显示 64G。

根因：/proc 里的很多文件不是 namespace 化的

文件是否隔离容器里看到什么
/proc/cpuinfo否宿主机的所有 CPU 和型号，看不到 cgroup 的 CPU 限额
/proc/meminfo否宿主机总内存，不是 cgroup 的 memory.max
/proc/stat否宿主机的全局 CPU 时间，包含其他容器
/proc/loadavg否宿主机的负载，不是容器的
/proc/uptime否宿主机开机时长（time namespace 可以改）
/proc/self/cgroup是（cgroup ns）容器自己的 cgroup 路径
/proc/net/*是（net ns）容器自己的网络统计
/proc/sys/net/*是（net ns）容器自己的网络参数

后果：运行时和监控全部误判

  • JVM 按 /proc/meminfo 算默认堆，在 512MB 的容器里可能把 -Xmx 设成物理内存的 1/4（比如 16G），一启动就被 OOM Kill。Java 10+ 支持 UseContainerSupport 才会读 cgroup。
  • Node.js / Python 的并发度按 CPU 核数算，容器限了 1 核但看到 64 核，起 64 个 worker，全部挤在 1 核上互相抢。
  • 监控 agent 采集 /proc/stat，报的是宿主机的 CPU 使用率，容器明明在打满却显示 5%。
  • free -h 显示内存充足，实际 cgroup 已经接近 memory.max，随时 OOM。

lxcfs 的作用

lxcfs 是一个 FUSE 文件系统，它把 /proc 里的若干文件"替换"成按 cgroup 计算出来的值，再 bind mount 进容器。这样容器里 free、top、nproc 看起来就"正常"了。

# 宿主机上装并启动 lxcfs
apt-get install -y lxcfs
systemctl start lxcfs
ls /var/lib/lxcfs/
# proc/  cgroup/

# Docker 里挂进去（只挂需要的几个文件）
docker run -it --rm \
  -v /var/lib/lxcfs/proc/cpuinfo:/proc/cpuinfo:ro \
  -v /var/lib/lxcfs/proc/meminfo:/proc/meminfo:ro \
  -v /var/lib/lxcfs/proc/stat:/proc/stat:ro \
  -v /var/lib/lxcfs/proc/uptime:/proc/uptime:ro \
  --cpus=2 --memory=1g ubuntu:24.04 bash

# 容器里现在看到的是限额后的值
nproc        # 2
free -h      # 1.0Gi 而不是 64Gi
lxcfs 不是万能的。① 它只覆盖有限的几个文件（cpuinfo、meminfo、stat、uptime、diskstats、swaps、loadavg）；② 它是 FUSE，有额外开销，某些高并发读 /proc/stat 的场景会变慢；③ Kubernetes 默认不装，需要 DaemonSet 部署；④ 它只是"让显示正确"，不改变实际的资源限制。真正的限额还是靠 cgroup。

更现代的做法：直接读 cgroup

# 容器内读 cgroup v2 的限额和用量
cat /sys/fs/cgroup/memory.max        # 1073741824（1G）或 max
cat /sys/fs/cgroup/memory.current    # 当前用了多少
cat /sys/fs/cgroup/cpu.max           # 200000 100000 = 2 核
cat /sys/fs/cgroup/cpu.stat          # nr_throttled / throttled_usec
cat /sys/fs/cgroup/pids.max          # 进程数上限

# 应用应该优先读这些，而不是 /proc/meminfo
# Java: -XX:+UseContainerSupport（默认开启）
# Go: 用 automaxprocs 读 cpu.max
# Python: os.cpu_count() 仍然返回宿主机核数，需要自己读 cgroup
模块 6

容器逃逸的常见路径

逃逸的本质只有一句话：找到一条能影响宿主机内核或其他 namespace 的路径。下面按"配置错误"和"内核漏洞"分两类。

配置错误类（占绝大多数）

路径为什么危险检测
特权容器
--privileged		给全部 capability、放开所有设备、关掉 seccomp 和 AppArmor。等于宿主机 rootdocker inspect -f '{{.HostConfig.Privileged}}'
挂载 docker.sock容器内能调 Docker API，直接起一个挂载宿主 / 的新容器检查 mounts 里有没有 docker.sock
CAP_SYS_ADMIN能 mount、能改 namespace、能用 /proc/sysrq-trigger，几乎等于 rootcapsh --decode=$(grep CapEff /proc/self/status | awk '{print $2}')
挂载宿主目录
-v /:/host		直接读写宿主机文件系统，改 /etc/cron.d 或 authorized_keys 即可提权检查 mounts 的 source 路径
cgroup v1 release_agentv1 的 release_agent 能在 cgroup 空时以宿主 root 执行任意命令检查是否 v1 + 有写权限
core_pattern 管道把 core dump 管道指向一个脚本，崩溃时以宿主 root 执行检查 /proc/sys/kernel/core_pattern 是否可写
hostPath 挂载 /procK8s 里挂宿主 /proc，能读写宿主内核参数检查 Pod spec 的 hostPath

# 容器内如果能访问 /var/run/docker.sock：
docker -H unix:///var/run/docker.sock run -it --privileged \
  -v /:/host alpine chroot /host sh
# 此时已经是宿主机 root

内核漏洞类

这类不依赖配置错误，只要共享内核就可能被利用。历史上影响大的几个：

漏洞年份原理
Dirty COW (CVE-2016-5195)2016写时复制的竞态，可改写只读文件（如 /etc/passwd）
runc 逃逸 (CVE-2019-5736)2019覆盖宿主机上的 runc 二进制，下次 exec 时执行恶意代码
Dirty Pipe (CVE-2022-0847)2022管道缓冲区标志未初始化，可写只读文件页缓存
overlayfs 提权 (CVE-2023-0386)2023copy-up 时权限检查不当，可把 setuid 文件带进容器

共同点：都是内核态的内存/权限管理缺陷，与运行时无关，只能靠升级内核或 VM 级隔离。

一条实用的判断：如果你的容器满足以下任意一条，就不该把它当安全边界——① --privileged；② 挂载了 docker.sock；③ 有 CAP_SYS_ADMIN；④ 以 root 运行且没开 userns-remap；⑤ 挂载了宿主机敏感目录。
这五条中任何一条成立，攻击者拿到容器基本等于拿到宿主机。
模块 7

容器里排查问题

容器里缺工具、/proc 被隔离、没有权限——三个障碍各有解法。

障碍一：镜像里没有 ps / top / ss

精简镜像（alpine、distroless、scratch）里没有这些工具。三条路：临时装（apk add procps）、起一个 sidecar 共享 --pid=container:x --net=container:x、或者直接回宿主机用 /proc/<pid> 和 nsenter 看——最后一条最可靠。

障碍二：nsenter 进入容器的命名空间

# 语法：nsenter -t <宿主PID> -m -u -i -n -p -- <命令>
# -m 挂载  -u UTS  -i IPC  -n 网络  -p PID  -U user  -C cgroup

# 进入容器的完整命名空间，跑一个 shell
PID=$(docker inspect -f '{{.State.Pid}}' demo)
sudo nsenter -t $PID -m -u -i -n -p -- /bin/sh

# 只进网络命名空间（在容器网络里抓包）
sudo nsenter -t $PID -n -- tcpdump -i eth0 -nn

# 只进挂载命名空间（看容器的文件系统）
sudo nsenter -t $PID -m -- ls /app

# 注意：-p 进 PID ns 后，ps 看到的是容器内的 PID
# 但当前 shell 本身还是宿主机上的进程，只是"视图"变了

障碍三：docker exec 的原理

docker exec 做的事很简单：

Docker 向 containerd 发请求，containerd 找到容器对应的 init 进程 PID 和它的 namespace 文件（/proc/<pid>/ns/*）。
调用 setns() 把新进程加入这些 namespace——和 nsenter 是同一个系统调用。
设置 cgroup（新进程也受同样的限额）、capability、seccomp。
execve() 执行你指定的命令。

所以 docker exec 启动的进程：在容器内看是新进程，在宿主机上看是 docker/containerd 的子进程，而且它不受容器 PID 1 管理——PID 1 退出时它不会自动被杀（除非 cgroup 被销毁）。

# 验证：exec 进去的进程，父进程在宿主机上是谁
docker exec -d demo sleep 1000
ps -ef | grep 'sleep 1000'
# root 23456 23400 ... sleep 1000
# 23400 是 containerd-shim，不是容器里的 PID 1

# 在容器里看，它是 PID 30 左右，父进程是 0（因为父进程不在这个 ns 里）
docker exec demo ps -ef | grep sleep

模块 8

容器里不能随便改 sysctl

sysctl 分三类：namespace 化的（改了只影响自己）、全局的（改了影响整机）、只读的（根本不让改）。

参数隔离级别说明
net.*（ipv4.ip_forward、tcp_tw_reuse、somaxconn…）net ns每个容器独立，可以改（需要 CAP_NET_ADMIN）
kernel.hostname / domainnameUTS ns改的是容器自己的主机名
kernel.msgmax / msgmnb / shmmax / semIPC ns容器内独立
fs.mqueue.*IPC nsPOSIX 消息队列参数
vm.swappiness / dirty_ratio / overcommit_memory全局改了影响宿主机所有容器，通常不允许
kernel.pid_max / threads-max全局同上
fs.file-max / nr_open全局同上。容器内的 fd 限制靠 ulimit 和 cgroup，不靠这个
kernel.core_pattern全局改它可以让 core dump 执行任意程序，是逃逸手法之一
net.ipv4.ping_group_rangenet ns允许非 root 用户 ping 的组范围
# 容器里改 net.* 通常可以（有 CAP_NET_ADMIN）
sysctl -w net.ipv4.tcp_tw_reuse=1
# net.ipv4.tcp_tw_reuse = 1

# 改全局参数会被拒绝
sysctl -w vm.swappiness=10
# sysctl: setting key "vm.swappiness": Read-only file system
# 或者 Permission denied，取决于挂载方式

# Docker 允许在启动时通过 --sysctl 设置一部分参数
docker run --sysctl net.core.somaxconn=1024 --sysctl net.ipv4.tcp_syncookies=1 nginx
# 只能设 namespace 化的；设全局的会报 "sysctl is not in a separate namespace"

# K8s 里通过 securityContext.sysctls 设置（同样有限制）
# 从 1.22 起，net.* 之外的安全 sysctl 需要显式开启

原因很简单：全局参数是整机共享的一份状态。容器 A 改了 vm.overcommit_memory，容器 B 的内存分配行为也会变，多租户环境不可接受。

几个高频踩坑：
① Redis 要求 vm.overcommit_memory=1，容器里改不了。正确做法是在宿主机上设，或者接受 fork 失败的风险。
② Elasticsearch 要求 vm.max_map_count=262144，同样必须在宿主机设（sysctl -w vm.max_map_count=262144），这是 K8s 部署 ES 的必做步骤。
③ 改 net.core.somaxconn 看起来是 net ns 的，但 宿主机上的 nginx/HAProxy 监听队列用的是宿主的，容器内改了只影响容器内的监听。
④ ulimit -n 不是 sysctl，容器里改的是当前进程的限制，持久化要在 docker run 时加 --ulimit nofile=65536:65536。
常见坑

十个真实踩过的坑

1
在容器里用 free / nproc 判断资源
/proc/meminfo 和 /proc/cpuinfo 没被隔离，看到的是宿主机。要看 /sys/fs/cgroup/memory.max 和 cpu.max，或装 lxcfs。
2
把数据写在容器可写层
docker rm 或 Pod 重建后全丢。数据必须进 volume 或 bind mount，且要注意挂载会盖住镜像里的初始文件。
3
容器里 PID 1 不转发信号
docker stop 等 10 秒超时后 SIGKILL，业务无法优雅退出。加 --init 或用 tini，或在应用里显式处理 SIGTERM。
4
镜像里改大文件导致构建/启动慢
overlayfs 的 copy-up 是整文件复制，改 1 字节也要复制 1GB。把易变的内容放到靠上的层，或挂载出去。
5
用 --privileged 解决权限问题
这等于交出宿主机。正确做法是逐个加 capability（--cap-add）、逐个放开设备（--device），并保持 seccomp 开启。
6
挂载 docker.sock 做 CI
CI 容器能通过 socket 起特权容器，等于宿主 root。改用 rootless 构建（kaniko/buildah）或独立的构建节点。
7
容器里 ping 不通 127.0.0.1
新 net ns 的 lo 默认 DOWN。启动脚本加 ip link set lo up，或用 --network host。
8
JVM 堆按宿主机内存算
老版本 JDK 不读 cgroup，512MB 容器里设了 16G 堆，一启动就 OOMKilled。JDK 10+ 默认开启 UseContainerSupport，老版本要手动加参数。
9
在容器里改全局 sysctl
vm.max_map_count、vm.overcommit_memory 这类参数必须宿主机设。容器里改会报只读，用 --privileged 硬改则影响整机。
10
以为容器是安全边界
共享内核，一个内核漏洞影响所有容器。多租户跑不可信代码，要用 VM、Kata 或 gVisor。
自测

六道题

1. 容器里的 PID 1，在宿主机上是什么？
正确答案：普通进程。PID namespace 只改变"容器内怎么编号"，不改变宿主机视角，ps 能看到所有容器进程。
2. 容器限了 512MB 内存，但 free -h 显示 64G，原因是？
正确答案：/proc 未隔离。cgroup 限额是生效的（超了会 OOM），只是 meminfo 显示整机内存。看 memory.max，或装 lxcfs。
3. overlayfs 修改一个只读层里的 1GB 文件中的 1 个字节，会发生什么？
正确答案：整文件 copy-up。这是写时复制语义，也是"容器里改大文件很慢"的原因。
4. 下面哪个 sysctl 在容器里修改不会影响宿主机？
正确答案：net.* 是 net namespace 化的，每个容器独立。vm.* 和大部分 kernel.* 是全局的，容器里通常只读。kernel.hostname 属于 UTS ns，也可以改。
5. docker exec 的底层原理是？
正确答案：setns + execve。和 nsenter 同一个系统调用。所以 exec 的进程不受容器 PID 1 管理。
6. 下面哪种配置最接近"把宿主机 root 交出去"？
正确答案：--privileged。给全部 capability、放开设备、关掉 seccomp/AppArmor，基本等于宿主 root。

术语一句话解释
namespace隔离"能看到什么"的内核机制，共七种（加 time 是八种）
cgroup限制"能用多少"的内核机制，管 CPU、内存、IO、进程数
PID namespace隔离进程编号，容器内的 1 号在宿主机上是普通进程
NET namespace隔离网卡、IP、路由、iptables，新 ns 的 lo 默认 DOWN
MNT namespace隔离挂载表，每个 ns 看到不同的文件系统树

USER namespace隔离 UID/GID，容器 root 可映射成宿主普通用户
veth pair一对虚拟网卡，一端在容器、一端在宿主网桥
overlayfs联合文件系统，把多个只读层 + 一个可写层叠成一个视图
