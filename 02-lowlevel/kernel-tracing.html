二十分钟学透内核追踪

用户态工具只能看到系统调用的边界，看不到边界里面发生了什么。这篇讲清楚 ftrace、tracepoint、kprobe、perf、eBPF 各自的定位与开销，以及在生产上怎么用它们回答"到底慢在哪一行"。

建议开一台 Linux 虚机（内核 5.4 以上），用 root 跟着敲 —— 这篇几乎所有命令都需要 root
开始前

先把环境准备好

内核追踪的坑有一半出在环境上：tracefs 没挂、权限不够、内核编译时关掉了某个选项。先花两分钟把这几件事确认掉。

# 1. 内核版本（eBPF 的很多特性有版本门槛）
uname -r

# 2. 关键内核编译选项是否打开
grep -E 'CONFIG_(FTRACE|FUNCTION_TRACER|KPROBES|KPROBE_EVENTS|BPF|BPF_SYSCALL|DEBUG_FS)=' /boot/config-$(uname -r)

# 3. tracefs 挂载点（现代内核已经独立挂载，不再依赖 debugfs）
mount | grep -E 'tracefs|debugfs'
# 典型输出：tracefs on /sys/kernel/tracing type tracefs (rw,nosuid,nodev,noexec,relatime)
# 老内核只有：debugfs on /sys/kernel/debug type debugfs，此时路径是 /sys/kernel/debug/tracing

# 4. perf 是否可用
perf --version
cat /proc/sys/kernel/perf_event_paranoid   # 2 = 默认，普通用户不能测内核事件

# 5. bpftrace 装了吗
bpftrace --version

# 6. 确认你确实是 root
id -u    # 输出 0 才是
两个路径要分清：新内核（4.1+ 独立挂载 tracefs）用 /sys/kernel/tracing；老内核用 /sys/kernel/debug/tracing。两者内容完全一样，是同一个文件系统的两个挂载点。
如果 /sys/kernel/tracing 是空的，手动挂：mount -t tracefs nodev /sys/kernel/tracing。容器里通常没有权限，需要 --privileged 或 --pid=host 加挂载。
模块 1

内核追踪解决什么问题

用户态工具看到的世界是被裁剪过的。进程调用 read()，在你的程序里是一行代码；在内核里是一串函数调用、若干次锁竞争、可能还有一次磁盘等待。工具只看得到"进去"和"出来"两个时间点。

三类工具的分层

层次代表工具能看到什么 / 看不到什么
系统调用边界strace / ltrace看得到：调了哪个 syscall、参数、返回值、耗时。看不到：这 200ms 花在内核的哪个函数里
采样与计数perf / top / vmstat看得到：CPU 在哪个函数上、cache miss 多少、上下文切换多少次。看不到：单次请求的完整因果链
内核内部追踪ftrace / kprobe / eBPF看得到：任意内核函数的入参、返回值、调用栈、耗时。代价：有开销，配错了能把机器拖死
快照式状态/proc / /sys看得到：某一瞬间的计数器、队列长度。看不到：这个数字是怎么变成这样的

一个具体例子：read 为什么慢

# 应用层看到的现象
$ strace -T -p 12345
read(7, "....", 4096) = 4096 <0.203451>
# 这一行告诉你：read 花了 203 毫秒。然后呢？没有然后了。

# 这 203ms 可能的成因，strace 一个都答不了：
#   a) 数据不在 page cache，真的等了一次磁盘 IO
#   b) 文件在 NFS 上，等的是网络
#   c) 拿 inode 锁的时候被别的线程挡住了
#   d) 触发了内存回收（direct reclaim），在等 kswapd
#   e) cgroup 的 io.max 限流，请求在块层排队
#   f) 进程被调度出去了，CPU 让给了别人

# 用 ftrace 的 function_graph 看内部调用链（只追 vfs_read 一层）
cd /sys/kernel/tracing
echo function_graph > current_tracer
echo vfs_read > set_graph_function
echo 1 > tracing_on
cat /proc/12345/comm          # 先确认进程还在
# ... 让应用再发一次请求 ...
echo 0 > tracing_on
cat trace | head -60

典型的 function_graph 输出长这样，注意每行前面的耗时（微秒）和缩进层级，缩进就是调用深度：

# 字段：CPU | 任务-PID | 耗时 | 调用链
 1) app-12345  |  1002.113 us   |  } /* vfs_read */
 1) app-12345  |               |    down_read() {
 1) app-12345  |  1.203 us      |    }
 1) app-12345  |               |    filemap_read() {
 1) app-12345  |  998.002 us     |      pagecache_get_page();
 1) app-12345  |  999.441 us     |    }
读法：外层 vfs_read 共 1002 微秒，其中 filemap_read 占 999，而它里面 pagecache_get_page 又占了 998 —— 时间几乎全在等 page cache 回盘。反过来，如果时间分散在几十个短函数上，那是 CPU 密集型而非 IO 等待。
模块 2

ftrace：内核自带的追踪器

ftrace 是内核里编译进去的追踪框架，不需要装任何东西，通过 tracefs 里的几个文件控制。它的定位是"低门槛、够用、开销可预期"。

tracefs 里的核心文件

文件作用
available_tracers当前内核支持哪些 tracer。典型值：nop function function_graph
current_tracer写入 tracer 名字即启用。写 nop 关闭
tracing_on总开关。1 开 0 关。关掉后 trace 文件内容还在，可以慢慢读
trace读它得到当前缓冲区快照。读操作本身会阻塞到读完
trace_pipe流式读取，读到就被消费掉。适合边跑边看，用 Ctrl-C 停
set_ftrace_filter只追踪哪些函数。支持通配符和 :mod: 模块语法
set_ftrace_pid只追踪指定 PID。最有效的降噪手段
set_graph_functionfunction_graph 专用：从哪个函数开始画图
max_graph_depthfunction_graph 最大追踪深度，默认 0（不限）
buffer_size_kb每个 CPU 的环形缓冲区大小。默认很小（约 1.4MB/CPU）

function tracer：只看"谁被调了"

# 追踪所有 openat 相关的函数（通配符）
cd /sys/kernel/tracing
echo 0 > tracing_on
echo function > current_tracer
echo '*openat*' > set_ftrace_filter

# 只关心某个进程
echo 12345 > set_ftrace_pid

echo 1 > tracing_on
sleep 2
echo 0 > tracing_on
cat trace

# 输出格式（不含耗时，只有调用顺序）：
#  bash-1234  [002] d...  1024.113: SyS_openat -> 0xffffffff81234567
#  bash-1234  [002] d...  1024.115: do_sys_open -> 0xffffffff81234678

function_graph：看"谁调谁、各花多久"

# 完整配置流程（这是最常用的一套）
cd /sys/kernel/tracing
echo 0 > tracing_on

# 1. 清空历史配置（上次的 filter 会残留，导致你以为没生效）
echo > set_ftrace_filter; echo > set_graph_function; echo > set_ftrace_pid

# 2. 选 tracer
echo function_graph > current_tracer

# 3. 限定入口函数（不限定就会追踪全内核，直接卡死）
echo vfs_read > set_graph_function

# 4. 限制深度，避免输出爆炸
echo 4 > max_graph_depth

# 5. 打开耗时显示（默认就开）
echo funcgraph-duration > trace_options

# 6. 只跟这个进程
echo $(pgrep -f myapp) > set_ftrace_pid

# 7. 开始，跑几秒，停止
echo 1 > tracing_on
sleep 3
echo 0 > tracing_on

cat trace > /tmp/graph.txt
wc -l /tmp/graph.txt
function_graph 是 ftrace 里最贵的一个。它给每个被追踪函数的入口和出口都挂了一个回调，每次进出都要记录时间戳、写环形缓冲区。追全内核时开销可以到 数倍到数十倍，并且会严重扰动被测系统（本来 1ms 的操作变成 5ms，你测到的是追踪器的开销）。
生产上三条铁律：① 必须设 set_graph_function 或 set_ftrace_filter，绝不追全部；② 必须设 set_ftrace_pid；③ 只开几秒，抓完立刻 echo 0 > tracing_on。
模块 3

tracepoint 与 kprobe：静态探针 vs 动态探针

这是内核追踪里最重要的一个取舍。选错了，要么拿不到数据，要么把机器搞崩。

本质区别

维度tracepoint（静态）kprobe（动态）
怎么来的内核开发者在代码里手动埋的点，编译时就存在运行时往任意指令地址插一个断点（x86 上是 int3，改一个字节）
稳定性稳定 ABI。字段名写在 format 文件里，跨版本基本不变不稳定。函数可能被 inline、被改名、参数寄存器分配变了，脚本就废了
覆盖范围只有开发者埋过的地方。约 1500~2000 个点任意函数，包括你自己写的模块
开销低。静态跳转（static key）+ 一个函数调用较高。每次命中触发一次异常陷入（trap），百纳秒到微秒级
参数访问按名字，args->filename按寄存器，%di、$arg1，要懂 ABI

tracepoint：先看有什么，再看字段

# 列出所有 tracepoint 分类
ls /sys/kernel/tracing/events/
# block  cgroup  ext4  irq  kmem  net  sched  signal  sock  syscalls  tcp  ...

# 看某一类下有哪些点
ls /sys/kernel/tracing/events/syscalls/ | head -20
# sys_enter_openat  sys_exit_openat  sys_enter_read  sys_exit_read ...

# 看某个点的字段定义（这个文件是理解 tracepoint 的钥匙）
cat /sys/kernel/tracing/events/sched/sched_switch/format

format 文件明确告诉你每个字段叫什么、偏移多少、能不能打印成字符串：

name: sched_switch
ID: 314
	field:char prev_comm[16];	offset:8;	size:16;	signed:1;
	field:pid_t prev_pid;	offset:24;	size:4;	signed:1;
	field:long prev_state;	offset:32;	size:8;	signed:1;
	field:char next_comm[16];	offset:40;	size:16;	signed:1;
# 启用某个 tracepoint（写 1 到 enable）
cd /sys/kernel/tracing
echo 0 > tracing_on
echo 1 > events/sched/sched_switch/enable
echo 1 > tracing_on
sleep 1
echo 0 > tracing_on
cat trace | head -20

# 输出：
#  bash-1234 [002] d... 1024.113: sched_switch: prev_comm=bash prev_pid=1234 \
#    prev_prio=120 prev_state=S ==> next_comm=sshd next_pid=5678 next_prio=120

# 关闭所有 tracepoint 的快捷方式
echo 0 > events/enable

kprobe：往任意函数上插探针

# 语法：p[:[组/]事件名] 函数 [参数...]
# 参数取值：%寄存器名 或 $arg1 $arg2 ...（按 ABI 顺序）

# 例 1：追 do_sys_open 的入参（x86_64：di=filename, si=flags, dx=mode）
echo 'p:my_open do_sys_open filename=+0(%di):string flags=%si mode=%dx' \
  > /sys/kernel/tracing/kprobe_events

# 例 2：追返回值（kretprobe，用 r: 前缀）
echo 'r:my_open_ret do_sys_open ret=$retval' >> /sys/kernel/tracing/kprobe_events

# 启用
echo 1 > /sys/kernel/tracing/events/kprobes/my_open/enable
cat /sys/kernel/tracing/trace_pipe

# 删除（写完记得删，否则一直挂着）
echo '-:my_open' > /sys/kernel/tracing/kprobe_events
# 或者全清
echo > /sys/kernel/tracing/kprobe_events
kprobe 的三个真实风险：
① 可能让系统卡死。probe 到 schedule、kmalloc 这类极热路径，每次命中都是一次 int3 陷入，高 QPS 机器直接 CPU 100%。
② 有些函数不能 probe。黑名单在 /sys/kernel/tracing/kprobe_blacklist（含 do_exit 等），硬来返回 EINVAL；被 inline 的函数没有独立符号，报 No such file or directory。
③ 参数是猜的。5.4 和 6.1 上参数可能换寄存器，上生产前先在测试机验证 %di 拿到的确实是你以为的值。

uprobe：追用户态函数

# 语法：p:事件名 可执行文件:偏移量（或 :函数名）
echo 'p:my_malloc /usr/lib/x86_64-linux-gnu/libc.so.6:malloc size=%di' \
  > /sys/kernel/tracing/uprobe_events
echo 1 > /sys/kernel/tracing/events/uprobes/my_malloc/enable
怎么选，一句话：能用 tracepoint 就别用 kprobe。tracepoint 是内核维护的稳定接口，开销低、字段有名字、跨版本不坏。只有在 tracepoint 覆盖不到的地方（某个具体函数的内部状态）才动用 kprobe。
模块 4

perf 与内核事件

perf 的定位是采样 + 计数，而不是"记录每一次调用"。它的开销和采样频率成正比，所以天然适合生产（-F 99 意味着每秒每 CPU 只采 99 次）。

perf list：先知道有什么事件

# 全部事件几千条，一定要过滤
perf list | head -40
perf list hardware      # cycles instructions cache-misses branch-misses
perf list software      # cpu-clock task-clock page-faults context-switches
perf list tracepoint | grep sched   # perf 能直接用所有 tracepoint

perf stat：只要数字，不要样本

# 最基础：跑一个命令，看它花了多少周期、多少指令
perf stat ls

# 输出关键行：
#   1,234,567      cycles
#   2,345,678      instructions              #    1.90  insn per cycle
#     123,456      cache-misses              #   12.34% of all cache refs
#      12,345      branch-misses             #    0.50% of all branches

# 同时看多个事件（-e 用逗号分隔）
perf stat -e cycles,instructions,cache-misses,context-switches -p 12345 sleep 5

# 只看内核态 / 用户态；-A 按 CPU 分开统计
perf stat -e cycles:k -p 12345 sleep 5
perf stat -A -e cycles sleep 1
三个数字最有诊断价值：IPC 小于 1 说明 CPU 在等内存或分支预测失败；cache-misses 超过 10% 说明访存模式不友好；branch-misses 超过 5% 说明分支预测器被打爆。

perf record：采样，然后看火焰图

# 最常用的一条：以 99Hz 采样所有 CPU，采 10 秒，记录调用栈
perf record -F 99 -a -g -- sleep 10

# 只采某个进程
perf record -F 99 -g -p 12345 -- sleep 10

# 只采某个 tracepoint，并记录调用栈
perf record -e sched:sched_switch -g -a -- sleep 3

# 用 dwarf 方式展开栈（更准，但文件大、慢）
perf record -F 99 -g --call-graph dwarf -p 12345 -- sleep 10

# 看报告 / 非交互看前 20 个热点
perf report
perf report --stdio --sort comm,dso,symbol | head -40

# 生成火焰图
perf script > out.perf
./stackcollapse-perf.pl out.perf > out.folded
./flamegraph.pl out.folded > flame.svg

perf_event_paranoid：为什么你被拒绝

取值允许什么
0 / -1可以测内核事件（需 CAP_PERFMON 或 CAP_SYS_ADMIN）
1默认，可以测用户态，不能测内核
2 / 3只能测自己的进程 / 基本全禁
# 临时放开（重启失效）
echo 1 > /proc/sys/kernel/perf_event_paranoid

# 永久
echo 'kernel.perf_event_paranoid = 1' >> /etc/sysctl.d/99-perf.conf
sysctl -p /etc/sysctl.d/99-perf.conf
容器里跑 perf 的常见错误：perf_event_open: Permission denied。原因通常不是 paranoid，而是容器没给 --cap-add SYS_ADMIN（或 PERFMON），或者 seccomp 拦了 perf_event_open 系统调用。另外容器里的 perf 版本最好和宿主内核匹配，否则符号解析会出问题。
模块 5

eBPF 的加载与验证

eBPF 之所以能在生产上用，核心原因是内核在加载前会把你的程序静态检查一遍。这解决了 ftrace/kprobe 时代最大的痛点：一段写错的脚本可能让内核崩溃（panic），而 eBPF 保证"最坏情况是拒绝加载"。

加载流程

准备字节码。写 C 或 bpftrace 脚本，clang 编译成 BPF 指令集（不是 x86 指令）。
调用 bpf()。命令 BPF_PROG_LOAD，传入指令、程序类型（kprobe/tracepoint/xdp 等）和 license。
验证器逐条走查。模拟执行所有路径，检查寄存器类型、内存边界、循环是否有界。可能耗时几十毫秒到几秒。
JIT 编译后挂载。翻译成本机指令（bpf_jit_enable），再通过 perf_event_open 或 bpf_link 绑到探针上。

验证器到底保证了什么

保证具体含义
终止性程序一定会结束。不允许无界循环。5.3 之前干脆禁止循环，之后允许但必须能被证明有界（如 for (i=0; i<100; i++)）
内存安全每一次内存访问都要证明在合法范围内。访问 ctx 的字段前要检查指针非空；访问 map 的值要先 bpf_map_lookup_elem 并判空
不能任意读内核内存直接解引用内核指针会被拒绝（"R1 invalid mem access"）。要用 bpf_probe_read_kernel() 这类 helper，它会做安全检查
栈空间有限BPF 程序栈只有 512 字节。大结构体必须放 map（per-CPU array）或用 bpf_probe_read 分字段读
指令数上限5.2 之前是 4096 条，之后是 100 万条（复杂度的上限，不是写多少都行）
# 看验证器到底怎么拒绝你的（调试 eBPF 程序的第一手段）
bpftool prog load my_prog.o /sys/fs/bpf/my_prog

# 典型报错：
#  invalid mem access 'inv'        —— 访问了未验证的指针
#  R0 invalid mem access 'map_value_or_null'  —— lookup 后没判空
#  back-edge from insn 42 to 18    —— 有环，5.3 之前不允许
#  BPF program is too large        —— 超过指令数上限
#  unknown func bpf_probe_read#4   —— helper 版本不匹配

# 看已加载的程序和 map
bpftool prog list
bpftool map list
bpftool prog show id 42
验证器不是万能的，这是最容易被误解的一点。它保证的是"不会因为这段 BPF 代码让内核内存损坏或死循环"，不保证：
① 你的逻辑是对的（读错了字段它管不了）；
② 你的程序开销可接受（一个每毫秒触发百万次的 kprobe，验证器照样放行）；
③ 不会干扰业务（你在 tcp_sendmsg 里做复杂字符串处理，照样会拖慢网络）。
所以"eBPF 很安全"只对内核稳定性成立，对性能不成立。
模块 6

bpftrace 实战：五个能直接跑的单行脚本

bpftrace 是 eBPF 的高层封装，语法接近 awk：探针 / 过滤条件 / { 动作 }。它把"写 C + 编译 + 加载"压缩成了一行命令，是排查时最顺手的工具。

语法骨架

# 结构
探针类型:探针名 /过滤条件/ { 动作 }

# 常用内置变量
comm      # 当前进程名（16 字节，可能被截断）
pid tid   # 进程号 / 线程号
nsecs     # 单调递增纳秒时间戳（算耗时全靠它）
args      # tracepoint 的结构化参数，如 args->filename
arg0..argN# kprobe 的位置参数
retval    # kretprobe 的返回值
curtask   # 当前 task_struct 指针
kstack    # 内核调用栈
ustack    # 用户态调用栈

# 常用聚合函数
count()  sum(x)  avg(x)  min(x)  max(x)  hist(x)  lhist(x,min,max,step)

# 自定义 map 用 @ 开头，@ 后面为空表示匿名（打印时自动输出）
@start[tid] = nsecs
@[comm] = count()

① 统计各进程的系统调用次数（找谁在疯狂 syscall）

bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

# 输出（每 1 秒刷新，Ctrl-C 结束打印最终结果）：
# @[node]: 128934
# @[nginx]: 4211
# @[bash]: 88

# 只看某个进程，并按 syscall 号分组
bpftrace -e 'tracepoint:raw_syscalls:sys_enter /comm == "nginx"/ { @[args->id] = count(); }'

② 统计每个进程的系统调用总耗时（找慢在哪）

bpftrace -e '
tracepoint:raw_syscalls:sys_enter { @start[tid] = nsecs; }
tracepoint:raw_syscalls:sys_exit  /@start[tid]/
{
  $d = nsecs - @start[tid];
  @us[comm] = sum($d / 1000);
  delete(@start[tid]);
}'

# @start[tid] 必须在 exit 里 delete，否则 map 无限增长
# 用 tid 不用 pid：同进程多线程会并发进入 syscall

③ 抓慢 IO：超过 10ms 的块设备请求

bpftrace -e '
tracepoint:block:block_rq_issue
{
  @start[args->dev, args->sector] = nsecs;
}
tracepoint:block:block_rq_complete /@start[args->dev, args->sector]/
{
  $d = (nsecs - @start[args->dev, args->sector]) / 1000000;
  if ($d > 10) {
    printf("%-16s %-6d %-8s %6dms sector=%d\n",
           comm, pid, str(args->rwbs), $d, args->sector);
  }
  delete(@start[args->dev, args->sector]);
}'

# 注意用 (dev, sector) 做 key，不是只用一个 —— 并发请求会互相覆盖
# 这条脚本能直接告诉你"哪个进程的哪次 IO 慢了多少毫秒"

④ 谁在 fork（找出进程爆炸的元凶）

bpftrace -e '
tracepoint:sched:sched_process_fork
{
  printf("%-16s %-6d => %-16s %-6d\n",
         comm, pid, str(args->child_comm), args->child_pid);
}'

# 加个计数版，看谁 fork 最频繁
bpftrace -e 'tracepoint:sched:sched_process_fork { @[comm] = count(); }'

# 如果看到大量 nginx => nginx 的 fork，通常是配置了错误的 worker 模型
# 如果是 cron => sh，那是定时任务在跑

⑤ 追踪某个内核函数的入参和耗时

# 追 vfs_read：谁在读、读多少、花多久
bpftrace -e '
kprobe:vfs_read
{
  @s[tid] = nsecs;
  @file[tid] = arg0;
}
kretprobe:vfs_read /@s[tid]/
{
  $d = (nsecs - @s[tid]) / 1000;
  if ($d > 1000) {
    printf("%-16s %6dus ret=%d\n", comm, $d, retval);
  }
  delete(@s[tid]);
  delete(@file[tid]);
}'

# 看调用栈，回答"谁在调用这个函数"
bpftrace -e 'kprobe:vfs_read { @[kstack] = count(); }'
调试 bpftrace 脚本的套路：
① 先用 bpftrace -l 'tracepoint:block:*' 确认探针名存在；
② 用 bpftrace -lv 'tracepoint:block:block_rq_issue' 列出这个探针有哪些字段（等价于读 format 文件）；
③ 先用 bpftrace -e 'probe { printf("hit\n"); }' 确认能命中，再加逻辑；
④ 报 Unknown struct/union 说明字段名写错了，回到第 ② 步。
模块 7

生产环境的开销控制

这一节比前面所有技术细节都重要。追踪工具本身可以成为故障源——很多"排查过程中服务雪崩"的事故，都是因为开了不该开的东西。

各机制的开销量级

机制单次开销什么时候会失控
tracepoint约 0.1~1 微秒高频点（如 net:netif_receive_skb）在 10Gbps 流量下每秒百万次
kprobe约 1~5 微秒（含 trap）挂在 kmalloc、schedule 这类每秒千万次调用的函数上
function tracer约 0.5~2 微秒/函数不设 filter，全内核追踪
function_graph约 2~10 微秒/函数最容易失控。追全内核时开销 5~50 倍
perf record -F 99CPU 占用约 1~3%频率提到 -F 9999，或开了 dwarf 展开栈

五条控制手段

采样而非全量
perf 用 -F 99 而不是记录每一次。99 是经验值：能反映热点，又不至于失真（避免和 100Hz 的定时器共振）
过滤条件前置
在探针里过滤，不要在用户态过滤。/comm == "nginx"/ 写在花括号前面，内核里就丢掉了不匹配的事件
限定 PID
ftrace 用 set_ftrace_pid，bpftrace 用 /pid == 1234/。这一条通常能把开销降一个数量级
>
限制输出
printf 是最贵的操作之一（要格式化、要写 ringbuf）。用聚合（hist/count）代替逐条打印
控制缓冲区
ftrace 的 buffer_size_kb 太大吃内存，太小会丢事件（看到 LOST EVENTS 就调大）

一个可以直接抄的生产排查模板

# 场景：P99 从 20ms 涨到 800ms，怀疑是 IO

# 1. 先看整体，开销接近 0
iostat -xz 1 5        # %util / await / aqu-sz

# 2. 确认是不是这个进程（perf，1~3% 开销）
perf record -F 99 -g -p $(pgrep -f myapp) -- sleep 10
perf report --stdio --sort symbol | head -30

# 3. 确认是 IO 后，定位到具体请求（限时 15 秒）
timeout 15 bpftrace -e '
tracepoint:block:block_rq_issue { @s[args->dev, args->sector] = nsecs; }
tracepoint:block:block_rq_complete /@s[args->dev, args->sector]/
{
  @ms[comm] = hist((nsecs - @s[args->dev, args->sector]) / 1000000);
  delete(@s[args->dev, args->sector]);
}'

# 4. 确认是谁发起（追栈，只采 100 个样本）
timeout 10 bpftrace -e '
kprobe:submit_bio /pid == $1/ { @[kstack] = count(); if (@n++ > 100) { exit(); } }'

# 5. 收工，清理所有状态
echo 0 > /sys/kernel/tracing/tracing_on
echo nop > /sys/kernel/tracing/current_tracer
echo > /sys/kernel/tracing/kprobe_events
四条硬规则，请写进值班手册：
① 永远不要在生产上开无过滤的 function_graph。它会追踪内核里每一个函数调用，几秒钟就能产生几个 G 的缓冲区数据，并把 CPU 打满。
② 不要在超过 32 核的机器上做 perf record -a 而不限时。每核一个采样流，写盘速度会很可观。
③ bpftrace 的 map 必须有界。@[kstack] = count() 在栈种类多的时候会吃光内存。加 if (@x++ > 1000) { exit(); } 兜底。
④ 排查完要清理。kprobe 事件、tracepoint enable、tracing_on 都是"设置后一直生效"的状态，下次别人上来会看到一堆残留。
模块 8

四个典型排查场景

前面讲的是工具，这一节讲"遇到问题该按什么顺序用"。四个问题的答案形状完全不同。

场景一：这个函数谁在调用

你从 perf 火焰图上看到一个可疑函数占了 30% CPU，想知道是哪条业务路径调过来的。

# 方案 A：perf 直接看调用链（最省事）
perf record -F 99 -g -p 12345 -- sleep 5
perf report --stdio --sort symbol --call-graph

# 方案 B：bpftrace 抓内核栈，聚合成计数（出现最多的栈就是主路径）
bpftrace -e 'kprobe:my_suspect_func { @[kstack] = count(); }'
bpftrace -e 'kprobe:my_suspect_func { @[kstack(1)] = count(); }'  # 只要一层调用者

# 方案 C：ftrace 的 stacktrace 选项（不需要 bpftrace）
cd /sys/kernel/tracing
echo 1 > options/stacktrace
echo function > current_tracer
echo my_suspect_func > set_ftrace_filter
echo 1 > tracing_on; sleep 2; echo 0 > tracing_on
cat trace

场景二：IO 为什么慢

IO 慢有五个层次的原因，必须逐层排除。顺序错了会浪费大量时间。

层次怎么判断典型结论
文件系统追 ext4_file_write_iter 的耗时journal 提交、目录锁竞争
块层追 block_rq_issue 到 block_rq_complete排队时间 vs 实际传输时间
设备iostat 的 %util、smartctl盘本身到极限了，或者盘要坏了
# 区分"排队"和"传输"：这是块层追踪最有价值的信息
bpftrace -e '
tracepoint:block:block_rq_issue
{ @q[args->dev] = nsecs; }
tracepoint:block:block_rq_complete /@q[args->dev]/
{
  @total_us[args->dev] = hist((nsecs - @q[args->dev]) / 1000);
  delete(@q[args->dev]);
}'

# 如果直方图集中在 0~2ms，说明设备响应正常，慢在排队（队列太深或限流）
# 如果集中在 50ms 以上，说明设备本身慢（机械盘寻道 / SSD 写放大 / 云盘限速）

# 队列深度一直很满 = 已饱和
iostat -x 1 3

场景三：进程为什么阻塞

ps 的 STAT 列能先做粗分类：D 在等 IO（不可中断，kill -9 无效）、S 在等事件或锁、R 在跑或排队、Z 僵尸。

# 零成本第一招：看内核栈（D 状态特别有效）
cat /proc/12345/stack
# [<0>] io_schedule+0x3d/0x60
# [<0>] blk_mq_get_tag+0x11e/0x280   <-- 在等块层 tag，队列满了

# 第二招：看等在哪个函数
ps -o pid,stat,wchan:30,comm -p 12345

# 第三招：统计 off-CPU 时间分布
bpftrace -e '
tracepoint:sched:sched_switch /args->prev_state & 2/
{ @off[args->prev_comm] = hist((nsecs - @on[args->prev_pid]) / 1000000); }
tracepoint:sched:sched_wakeup { @on[args->pid] = nsecs; }'

场景四：内存是谁分配的

# 按调用栈统计 kmalloc 分配量（只采 500 个样本）
bpftrace -e '
tracepoint:kmem:kmalloc
{ @bytes[kstack] = sum(args->bytes_alloc); if (@n++ > 500) { exit(); } }'

# 先判断是内核内存还是用户内存
cat /proc/meminfo | grep -E 'Slab|SReclaimable|SUnreclaim'
slabtop -o | head -20
# Slab 大且 SUnreclaim 高 → 内核泄漏，追 kmalloc
# Slab 正常但 RSS 高 → 用户态泄漏，用 heaptrack / valgrind
四个场景的共性：都是"先用零成本工具定位层次，再上有成本的工具精确打击"。跳过第一步直接开 ftrace，是最常见的浪费时间方式。
常见坑

十个会浪费你半天的问题

1
开着 function_graph 忘了关
tracing_on 是持久状态，SSH 断开也不会自动关，机器会一直高开销直到有人发现。先写好 sleep && echo 0 再开。
2
filter 没清空，以为没生效
set_ftrace_filter 会保留上次的内容，两次实验叠加后你看到的是交集。每次实验前先 echo > set_ftrace_filter 清空。
3
在容器里找不到 /sys/kernel/tracing
容器默认不挂 tracefs。用 --privileged，或 nsenter 进宿主机 mount namespace 操作。
4
kprobe 报 "No such file or directory"
两种可能：函数被 inline 了（没有独立符号，用 /proc/kallsyms 确认），或者函数名写错了（注意内核符号没有参数类型后缀）。
5
用 %di 取参数，拿到一堆乱码
结构体传参或编译优化会改变寄存器分配。用 $arg1 更稳，先用 bpftrace 打印验证。
6
bpftrace 的 map 无限增长把内存吃光
@start[tid] 这种 per-thread 的 map，如果 exit 探针没命中（比如进程被 kill -9），条目永远不删。加 exit() 兜底或定期清理。
7
perf record 报 Permission denied
三层原因：perf_event_paranoid 太严、缺 CAP_PERFMON/CAP_SYS_ADMIN、容器 seccomp 拦了 perf_event_open。逐个排除，别一上来就改 sysctl。
8
看到 LOST EVENTS 却以为是程序 bug
环形缓冲区满了在丢事件，说明你的追踪点触发频率远超缓冲区写入速度。调大 buffer_size_kb，或者加过滤条件减少事件量。
9
eBPF 程序验证通过就以为没问题
验证器只保证内核不会因为这段代码崩溃，不保证开销可接受。一个挂在热路径上的 kprobe 照样能把 QPS 打下去一半。
10
追了半天发现时间花在"被调度出去"上
函数内部耗时看着很长，但那是因为进程在中途被抢占了。对比 nsecs 差值和实际 CPU 时间（task->se.sum_exec_runtime），差很多就说明是调度问题而非函数慢。
自测

六道题

1. tracepoint 和 kprobe 最本质的区别是？
正确答案：静态预埋 vs 动态插桩。tracepoint 字段名写在 format 文件里，是稳定 ABI；kprobe 运行时改指令插 int3，覆盖广但参数靠猜、跨版本易坏，开销也更高。
2. function_graph 在生产上最大的风险是？
正确答案：开销失控。它给每个函数的入口和出口都挂回调，不设 filter 等于追踪所有函数调用。必须限定入口函数、PID 和时长。
3. eBPF 验证器保证了下面哪一条？
正确答案：终止性 + 内存安全。验证器通过模拟所有路径，证明没有无界循环、没有非法内存访问。但它不管逻辑对不对，也不管开销大小 —— 一个每秒触发百万次的 kprobe 照样能通过验证。
4. bpftrace 里统计 syscall 耗时，为什么要用 @start[tid] 而不是 @start[pid]？
正确答案：线程并发会覆盖。tid 是线程号，每个线程独立。如果用 pid，多线程程序里线程 A 进入时记录的时间会被线程 B 覆盖，算出来的耗时完全错乱。
5. 进程处于 D 状态（不可中断睡眠），最可能的原因是？
正确答案：等 IO。D 状态意味着内核在 io_schedule 里，通常杀不掉（kill -9 也无效）。用 cat /proc/PID/stack 看具体卡在哪个函数，常见的是 blk_mq_get_tag（块层队列满）或某个文件系统锁。
6. 想在生产上排查"哪个进程的哪次磁盘 IO 慢"，最合适的第一步是？
正确答案：块层 tracepoint + 过滤。它直接给出"哪个请求慢了多少毫秒"，开销低且信息精确。function_graph 开销太大不适合生产；strace 只能看到 syscall 边界，无法区分排队和传输。
