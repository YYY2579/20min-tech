开始前

先看清你这台机器是怎么起来的

不要凭记忆。先跑这五条命令，把结果记下来，后面每个模块都会对应到其中一行。

# 1. 是 UEFI 还是 BIOS？目录存在且非空 → UEFI
ls /sys/firmware/efi 2>/dev/null && echo "UEFI" || echo "Legacy BIOS"

# 2. 本次启动用了哪些内核参数
cat /proc/cmdline

# 3. 各阶段耗时（最重要的一条）
systemd-analyze

# 4. 本次启动的完整日志
journalctl -b -p err              # 只看错误
journalctl -b -o short-monotonic  # 带微秒时间戳，看谁在等谁

# 5. 默认启动目标是什么
systemctl get-default
先建立一个心智模型：启动是一条责任链。固件负责找到引导器，引导器负责找到内核，内核负责找到根文件系统，init 负责把系统拉起来。任何一环断了，后面的环节根本没有机会执行——所以排障的第一原则是判断"卡在哪一环"，而不是一上来就翻日志。
模块 1

从上电到内核：固件做了什么

按下电源键后，CPU 从固定的物理地址取第一条指令，执行的是主板固件。这一阶段的操作系统完全不存在。

POST：先确认硬件是活的

POST（Power-On Self-Test，上电自检）由固件执行：初始化内存控制器、枚举 PCIe 设备、检测 CPU 与内存容量、初始化显卡（这就是为什么开机最早出现的是厂商 Logo）。这一步失败通常表现为蜂鸣码、Debug LED 常亮、或者干脆黑屏无输出——此时任何操作系统日志都不存在，只能看硬件。

BIOS 与 UEFI 的本质区别

维度Legacy BIOSUEFI
运行模式16 位实模式，只能寻址 1MB32/64 位保护模式，可直接寻址全部内存
分区表MBR，单盘最大 2TB，最多 4 个主分区GPT，支持 9.4ZB，最多 128 个分区
引导记录磁盘前 512 字节（MBR），其中引导代码只有 446 字节ESP 分区（FAT32）里的 .efi 可执行文件
引导项存储只能靠磁盘顺序 + 激活分区标志存在主板 NVRAM 里，可用 efibootmgr 管理
安全启动不支持支持 Secure Boot，验证引导链签名
驱动靠固件内置的 INT 13h 中断读盘有完整的驱动模型（UEFI Driver Model），支持网络启动

UEFI 的引导路径长什么样

# UEFI 固件按 NVRAM 里的 BootOrder 依次尝试
efibootmgr -v
# BootCurrent: 0001
# BootOrder: 0001,0000,0002
# Boot0001* ubuntu  HD(1,GPT,...)/File(\EFI\ubuntu\shimx64.efi)

# ESP 分区里通常长这样
/boot/efi/EFI/
├── BOOT/BOOTX64.EFI        # 兜底路径，找不到 NVRAM 项时用它
├── ubuntu/
│   ├── shimx64.efi         # 被微软签名的第一级引导器（Secure Boot 用）
│   ├── grubx64.efi         # 真正的 GRUB
│   └── mmx64.efi           # MOK 管理界面
└── Microsoft/Boot/bootmgfw.efi

注意 shim 这一层：微软不可能给每个 Linux 发行版签 GRUB，所以签了一个极小的 shim，由 shim 再去验证 GRUB 的签名，或者通过 MOK（Machine Owner Key，机器所有者密钥）让你自己注册密钥。这就是为什么装完 NVIDIA 驱动或自编译内核后，开机会出现一个蓝色的 "MOK management" 界面。

Secure Boot 到底在验什么

变量作用
PKPlatform Key，平台根密钥，一般由主板厂商持有
KEKKey Exchange Key，用于更新 db/dbx
db允许的签名证书白名单
dbx吊销列表，已知有漏洞的引导器会被加进来
# 查看当前 Secure Boot 状态（1 = 开启）
mokutil --sb-state
# 或
cat /sys/firmware/efi/efivars/SecureBoot-8be4df61-93ca-11d2-aa0d-00e098032b8c | od -An -t u1

# 查看/注册自己的密钥（自签名内核模块时必须）
mokutil --import mykey.der
mokutil --list-enrolled
一个反复出现的坑：自己编译了内核或装了第三方驱动（如 VirtualBox、ZFS、NVIDIA），重启后模块加载失败，dmesg 里写着 Key was rejected by service。
这不是驱动写错了，是 Secure Boot 拒绝了未签名的内核模块。三条路：① 用 MOK 注册自己的密钥；② 在固件里关掉 Secure Boot；③ 用发行版提供的 DKMS 签名流程。
模块 2

bootloader：GRUB2 的配置结构

GRUB2 最反直觉的地方是：你改的那个文件，不是它真正读的那个文件。

三层结构，必须分清

文件谁来改作用
/etc/default/grub人来改主配置：默认启动项、超时、内核参数。这是你唯一该手改的文件
/etc/grub.d/*偶尔改生成脚本（00_header、10_linux、30_os-prober…），决定菜单里出现哪些条目
/boot/grub2/grub.cfg
/boot/grub/grub.cfg		永远不要手改最终产物，由上面两者生成。下次内核更新就被覆盖

路径差异：RHEL/CentOS/Rocky 用 /boot/grub2/，Debian/Ubuntu 用 /boot/grub/。

/etc/default/grub 里真正重要的四行

# 默认启动哪个条目（从 0 开始计数，或写 "1>2" 表示子菜单第 2 项）
GRUB_DEFAULT=0
# 也可以用 saved，配合 grub-set-default 记住上次选择
GRUB_DEFAULT=saved
GRUB_SAVEDEFAULT=true

# 菜单停留时间（秒）。设为 0 会完全看不到菜单
GRUB_TIMEOUT=5

# ★ 最重要的一行：普通启动时传给内核的参数
GRUB_CMDLINE_LINUX="crashkernel=auto rd.lvm.lv=rootvg/root rhgb quiet"

# Debian/Ubuntu 专有：只在默认（非恢复）条目上追加的参数
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"

RHEL 系把 GRUB_CMDLINE_LINUX 应用到所有条目（包括救援条目），Debian 系则区分 LINUX（全部）和 LINUX_DEFAULT（仅默认条目）。搞混了会出现"正常启动生效、进恢复模式却没生效"的怪现象。

改完必须重新生成

# Debian / Ubuntu
sudo update-grub
# 等价于
sudo grub-mkconfig -o /boot/grub/grub.cfg

# RHEL / CentOS / Rocky / Fedora（BIOS 启动）
sudo grub2-mkconfig -o /boot/grub2/grub.cfg

# RHEL 系 UEFI 启动，路径不同，别抄错
sudo grub2-mkconfig -o /boot/efi/EFI/redhat/grub.cfg

# 验证：新参数有没有真的写进去
grep -n 'vmlinuz' /boot/grub2/grub.cfg | head
最容易出事的一步：在 UEFI 机器上把 grub.cfg 生成到了 BIOS 的路径，然后重启——参数没生效，或者更糟，GRUB 找不到配置直接掉进 grub> 提示符。
动手前先确认路径：ls /boot/efi/EFI/ 看有没有你的发行版目录。有就是 UEFI，生成到 /boot/efi/EFI/<distro>/grub.cfg。

RHEL 系的捷径：grubby

在 RHEL 系上，改内核参数不必碰 /etc/default/grub，grubby 会同时更新 BLS 条目（/boot/loader/entries/*.conf）和 GRUB 配置，更不容易出错。

# 给所有内核追加参数
grubby --update-kernel=ALL --args="transparent_hugepage=never"

# 删除某个参数
grubby --update-kernel=ALL --remove-args="rhgb quiet"

# 查看当前默认内核的参数
grubby --info=DEFAULT

临时改一次：不进系统也能改

重启，在 GRUB 菜单出现的几秒内按上下方向键停住倒计时（很多系统默认隐藏菜单，需要连按 Esc 或 Shift）。
光标停在要启动的条目上，按 e 进入编辑模式。这时看到的是这个条目的临时副本。
找到以 linux（UEFI）或 linux16（BIOS）开头的那一行，在行尾追加参数，例如 systemd.unit=rescue.target。
按 Ctrl+X 或 F10 用这份临时配置启动。改动不落盘，下次重启自动失效——这正是它的价值。
这是救火时最有用的技能。系统起不来、又不想进救援盘，就靠这一招临时加 rd.break、init=/bin/bash、systemd.unit=emergency.target。它不会破坏任何文件，失败了重启就回到原状。
模块 3

内核初始化：从 bzImage 到根文件系统

引导器把内核镜像读进内存并跳转过去，从这一刻起，控制权交给内核。但此时内核还是个"瞎子"——它没有驱动，甚至不知道根分区在哪。

第一步：解压自己

/boot/vmlinuz-* 是一个自解压镜像（x86 上叫 bzImage）。文件头部是一小段未压缩的引导桩（stub），它先完成最基本的初始化（建立临时页表、从 32 位切到 64 位长模式），然后把压缩过的内核（gzip/xz/zstd）解压到内存的高地址，再跳进去执行。

所以 vmlinuz 的大小（常见 8~15MB）远小于解压后的内核映像（几十 MB）。这也是"内核参数里能不能加 nokaslr"之类调试选项的分界线——stub 阶段的问题，内核日志根本来不及输出。

第二步：initramfs 救场

initramfs（initial RAM filesystem，初始内存文件系统）是一个 cpio 归档（通常再压缩成 .xz 或 .zst），被引导器一起加载进内存，由内核解包成一个临时的 rootfs。

为什么需要它说明
根分区在特殊设备上LVM、LUKS 加密盘、软 RAID、iSCSI、NFS root——内核没有这些驱动就找不到根
存储控制器驱动不在内核里发行版为了控制体积，把大量驱动编译成模块放在 initramfs 里
需要先做解密/激活LUKS 要密码、LVM 要 vgchange -ay，这些逻辑必须有人执行
需要打印启动画面/提示plymouth 也在 initramfs 里
# 看 initramfs 里到底装了什么（不用解压，直接列目录）
lsinitramfs /boot/initrd.img-$(uname -r) | head -30

# 解开来看（小心，会生成一堆文件）
mkdir /tmp/ir && cd /tmp/ir
zstd -dc /boot/initrd.img-$(uname -r) | cpio -idmv

# 重新生成（三个发行版三套命令）
update-initramfs -u -k all          # Debian / Ubuntu
dracut -f --regenerate-all          # RHEL / Fedora
mkinitcpio -P                       # Arch

第三步：切换根，交棒给 init

内核解包 initramfs，执行里面的 /init（一个 shell 脚本或二进制程序）。
/init 加载必要模块（modprobe），用 udev 创建设备节点，等待根设备出现。
挂载真正的根文件系统到 /sysroot（只读挂载，先验证）。
执行 switch_root（或 pivot_root）：把 /sysroot 变成新的 /，卸载并释放 initramfs 占用的内存。
执行 exec /sbin/init。至此内核初始化结束，PID 1 诞生。

注意最后一步是 exec：initramfs 的 /init 进程直接变成 PID 1，不是 fork 出新进程。所以如果 /sbin/init 不存在或是坏的，你会看到 Kernel panic - not syncing: No working init found。

一个高频故障：内核更新了，initramfs 没更新。
表现是新内核启动到一半卡住，报 Unable to find root device 或者直接 dracut:/# 提示符。原因是新内核的模块路径（/lib/modules/$(uname -r)）和旧 initramfs 里记录的设备名对不上。
应急：在 GRUB 里选旧内核启动，进系统后重新生成 initramfs。预防：别手动删 /lib/modules 下的旧版本目录，至少留一个能用的。
模块 4

init 系统：systemd 的 target 与并行启动

PID 1 的职责只有两件：把系统带到可用状态，以及回收孤儿进程。systemd 之所以快，不是因为代码优化得好，而是因为它把"串行等待"改成了"依赖图 + 并行"。

target 就是"一组要达成的状态"

target大致对应旧 runlevel含义
poweroff.target0关机
rescue.target1 / s单用户，挂载本地文件系统，起基本服务，需要 root 密码
multi-user.target3服务器标准状态：多用户、有网络、无图形界面
graphical.target5多用户 + 图形界面（依赖 multi-user）
emergency.target—最小化：只挂载根分区（只读），几乎不起任何服务
reboot.target6重启

default.target 是一个符号链接，指向真正的默认目标。改默认启动状态就是改这个链接：

systemctl get-default                 # 看当前默认
systemctl set-default multi-user.target   # 改成服务器模式
systemctl isolate rescue.target       # 立刻切到单用户（会停掉其他服务，慎用）

依赖关系：Wants 与 Requires 的区别

指令语义
Requires=强依赖。被依赖的单元启动失败，本单元也不启动
Wants=弱依赖。尽力启动，失败了也不影响本单元。绝大多数场景应该用这个
After=只控制顺序，不建立依赖。B 在 A 之后启动，但 A 挂了 B 照样起
Before=反向的顺序控制
Conflicts=互斥。启动本单元会先停掉对方
最常见的误解：After= 不等于"依赖"。
写了 After=network.target 只保证顺序，不保证网络真的可用。而且 network.target 只表示"网络管理服务已经启动"，不代表网卡拿到了 IP。要等地址就绪，得用 After=network-online.target + Wants=network-online.target。

并行启动的原理

旧式 SysV init 按 S01、S02 的编号严格串行执行脚本，前一个不返回，后一个就不能开始。systemd 的做法是：

建图。扫描所有单元的依赖声明，构造一张有向无环图（DAG）。
拓扑排序。找出所有"前驱都已完成"的节点，这些可以同时启动。
并发执行。每个服务 fork 出去自己初始化，谁先就绪谁先标记完成，不互相阻塞。
默认加隐式依赖。通过 DefaultDependencies=yes，systemd 自动给服务加上"在 sysinit 之后、在 shutdown 之前"这类约束，避免作者漏写。

所以 systemd 机器开机常常只要 3~8 秒，而同样硬件的 SysV 机器要 40 秒以上——差距主要来自消除了无谓的串行等待，而不是服务本身变快了。

socket 激活：更进一步的懒启动

服务不必开机就起。systemd 可以先监听端口（.socket 单元），等第一个连接到达时再启动对应的 .service，并把已排队的连接交给它。这样开机时间和内存占用都省了。SSH 之外的很多服务都可以这么配，但要注意：第一次连接会有额外延迟，对延迟敏感的接口别用。

模块 5

开机慢怎么查：systemd-analyze 三板斧

不要看 dmesg 猜。systemd 已经把每个单元的耗时都记下来了。

第一斧：总览

$ systemd-analyze
Startup finished in 3.412s (firmware) + 2.108s (loader) + 2.664s (kernel) + 12.887s (userspace) = 21.072s
graphical.target reached after 12.301s in userspace

这四段分别对应：firmware（固件 POST，改不了，只能调 BIOS 里的快速启动）、loader（GRUB 等待时间，改 GRUB_TIMEOUT）、kernel（内核 + initramfs）、userspace（PID 1 到目标达成）。

先看哪一段最大。如果 firmware 占了 20 秒，你去优化 systemd 是白费力气。

第二斧：谁最慢

$ systemd-analyze blame | head -10
         8.214s NetworkManager-wait-online.service
         4.902s cloud-init.service
         1.331s dev-sda2.device
          812ms systemd-udev-settle.service
          402ms snapd.service
blame 会骗人。它列出的是"这个单元自己花了多久"，但很多单元是并行跑的，加起来远超总时间。真正拖慢启动的，往往是一个"等别人"的单元——比如 NetworkManager-wait-online.service 常见 5~30 秒，它只是在等 DHCP。
所以 blame 只用来找嫌疑，定罪要靠 critical-chain。

第三斧：关键路径

$ systemd-analyze critical-chain
graphical.target @12.301s
└─multi-user.target @12.300s
  └─docker.service @9.114s +3.180s
    └─network-online.target @9.102s
      └─NetworkManager-wait-online.service @1.204s +7.890s
        └─NetworkManager.service @1.102s +96ms
          └─dbus.service @1.098s
            └─basic.target @1.090s

从下往上读：每一行是"我上面那个依赖，等了我多久"。这条链上的耗时是串行累加的，优化链上任何一环都能直接缩短总时间；优化链外的单元几乎没用。

还有两个进阶工具

# 生成 SVG 时序图，一眼看出谁和谁并行
systemd-analyze plot > /tmp/boot.svg

# 检查单元文件语法（改完 service 必跑）
systemd-analyze verify /etc/systemd/system/myapp.service

# 看某个服务自己报告的耗时明细
systemctl show -p ExecMainStartTimestampMonotonic -p ExecMainExitTimestampMonotonic myapp.service

# 看本次启动所有单元的启动时刻（按时间排序）
systemd-analyze dump | grep -E 'ActivateTimestamp|Unit:' | head -40

四个最常见的慢因与处理

现象原因处理
NetworkManager-wait-online 超长等 DHCP 或链路协商服务器用静态 IP；或 systemctl disable NetworkManager-wait-online（确认没有服务真的依赖它）
systemd-udev-settle 很慢在等所有设备探测完找出谁 Wants=systemd-udev-settle，改用具体设备单元
cloud-init 卡 30 秒以上元数据服务不可达（换网络/跨云）配 datasource_list，或直接 disable
random 熵不足无盘/无鼠标的机器，random-seed 加载慢装 haveged，或确认 systemd-random-seed 正常
模块 6

常用内核参数：cmdline 里该写什么

内核参数是"内核启动时的命令行开关"。它分两类：内核自己解析的（如 root=、console=），和被 init 系统接管的（systemd.*、rd.*）。写错了不会报错，只会静默失效——这是最坑的地方。

启动与根文件系统

参数作用
root=UUID=xxxx根文件系统。用 UUID 或 LABEL，别用 /dev/sda2（设备名会变）
ro / rw根分区初始挂载为只读/读写。发行版默认 ro，由 systemd 重新挂载为 rw
rootfstype=ext4显式指定根文件系统类型，一般不用写
rootflags=传给根文件系统的挂载选项
init=/bin/bash跳过 init 直接起 shell，救火常用。此时没有服务、没有网络、没有 job 控制
rd.break在 initramfs 阶段中断，进 switch_root 之前，root 挂在 /sysroot（只读）
rd.shellinitramfs 失败时给个 shell，而不是直接 panic

cgroup 与资源隔离

参数作用
systemd.unified_cgroup_hierarchy=1强制使用 cgroup v2。容器平台（K8s 1.25+）基本都要求 v2
systemd.unified_cgroup_hierarchy=0退回 v1 混合模式，老版本 Docker/K8s 的兼容做法
systemd.legacy_systemd_cgroup_controller=1混合层级下让 systemd 自己管控制器
cgroup_enable=memoryv1 下启用内存控制器（否则 memory.limit_in_bytes 不存在）
swapaccount=1v1 下统计 swap 用量，容器内存限制需要它
cgroup_disable=memory关掉内存控制器（极少用，性能敏感场景）

大页与内存

参数作用
hugepages=N预留 N 个 2MB 大页（默认页大小）
hugepagesz=1G hugepages=16预留 16 个 1GB 大页。顺序不能反，先声明 size 再给数量
default_hugepagesz=1G设定默认大页尺寸
transparent_hugepage=never关闭透明大页（THP）。Redis、部分数据库的官方建议
transparent_hugepage=madvise只对显式 madvise(MADV_HUGEPAGE) 的内存生效，推荐折中方案
numa=off关闭 NUMA，把所有内存当成一个节点（会损失局部性，仅排障用）
numa_balancing=disable关闭内核自动 NUMA 均衡（它会在后台迁移页，可能引起抖动）

参数作用
console=tty0 console=ttyS0,115200n8同时输出到本地屏和串口。最后一个 console 决定 /dev/console 指向谁
quiet抑制大部分内核日志。排障时第一件事就是去掉它
loglevel=7打印 debug 级日志（0~7，7 最啰嗦）
ignore_loglevel无视 loglevel，全打
nomodeset不用内核 KMS 驱动，装 NVIDIA 驱动黑屏时的救命参数

三个静默失效的坑：
① hugepages=16 hugepagesz=1G 写反了顺序——1G 的大页不会被预留，但也不报错，只是 HugePages_Total 为 0。
② 在 RHEL 系上改 /etc/default/grub 却没跑 grub2-mkconfig——文件改了，启动时用的还是旧配置。
③ 参数名拼错（比如 transparent_huge_pages）——内核不认识就直接忽略，日志里只有一行 Unknown kernel command line parameters，很容易漏看。
模块 7

启动失败怎么救：从救援模式到 chroot

先判断卡在哪一环，再选工具。选错了会浪费大量时间。

现象卡在对策
黑屏、无任何输出、蜂鸣固件/硬件查内存条、看 Debug LED、清 CMOS
停在 grub> 提示符GRUB手动 set root= / linux / boot，或进救援盘重装 GRUB
停在 dracut:/#initramfs找不到根设备。查 /dev/disk/by-uuid，改 root=
Kernel panic - not syncing内核选旧内核启动；加 nokaslr、maxcpus=1 缩小范围
进 emergency mode / 要 root 密码userspace多半是 /etc/fstab 写错，见下文
卡在 A start job is running for...某个 unit加 systemd.unit=emergency.target 进去 disable 它

方案一：rd.break（RHEL 系最常用，改密码/改 fstab）

# 1. GRUB 菜单按 e，在 linux 行尾加：
rd.break

# 2. 启动后进入 initramfs 的 shell，此时根在 /sysroot，且是只读
mount | grep sysroot
# /dev/mapper/rhel-root on /sysroot type xfs (ro,relatime)

# 3. 重新挂载为读写
mount -o remount,rw /sysroot

# 4. 切进真实系统
chroot /sysroot

# 5. 干活：改密码
passwd root

# 6. ★ SELinux 开启时必须做，否则改过的文件上下文不对，还是进不去
touch /.autorelabel

# 7. 退出并重启
exit
exit
touch /.autorelabel 这一步 90% 的人会忘。在 rd.break 环境下改文件，新文件的 SELinux 上下文是 unlabeled_t，系统起来后会被拒绝访问，表现为"密码改了但还是登不进去"或者干脆起不来。加上这个标记，下次启动会自动重打标签——代价是重启会慢几分钟（要遍历整个文件系统）。

方案二：init=/bin/bash（更快，但功能更少）

# GRUB 里在 linux 行尾加：
init=/bin/bash

# 进来后根是只读的，先重挂
mount -o remount,rw /

# 注意：此时没有 /proc /sys /dev，需要手工挂
mount -t proc proc /proc
mount -t sysfs sys /sys
mount -t devtmpfs dev /dev

# 改完记得（SELinux 开启时）
touch /.autorelabel
exec /sbin/init        # 或者直接 reboot -f

方案三：fstab 写错导致 emergency mode

这是生产环境最高频的启动故障。加了一块盘、写错一个 UUID、或者 NFS 服务器没起来，systemd 就会在挂载时失败，掉进 emergency shell。

# 1. 在 emergency shell 里，先看是谁失败了
systemctl --failed
journalctl -xb | grep -i 'mount\|failed'

# 2. 重挂根为读写
mount -o remount,rw /

# 3. 编辑 fstab，把出问题的行注释掉
vi /etc/fstab
# 或者更稳的做法：加 nofail 选项，让挂载失败不阻塞启动
# UUID=xxxx /data xfs defaults,nofail 0 0

# 4. 让 systemd 重新加载 fstab 并重试挂载
systemctl daemon-reload
mount -a

# 5. 继续启动
systemctl default        # 或 systemctl isolate multi-user.target
一条能省掉很多事故的经验：非关键数据盘在 /etc/fstab 里一律加 nofail。加 nofail 后即使盘没插、NFS 不通，系统照样能起来，只是那个挂载点空着。关键盘（根、/var）当然不能加。

方案四：GRUB 本身坏了，怎么重装

# 用 Live USB / 救援盘启动，先挂好原系统
lsblk                                  # 找到根分区，假设 /dev/sda2
mount /dev/sda2 /mnt
mount --bind /dev  /mnt/dev
mount --bind /proc /mnt/proc
mount --bind /sys  /mnt/sys
# UEFI 机器还要挂 ESP
mount /dev/sda1 /mnt/boot/efi

chroot /mnt

# --- BIOS 机器 ---
grub2-install /dev/sda
grub2-mkconfig -o /boot/grub2/grub.cfg

# --- UEFI 机器（RHEL 系）---
dnf reinstall grub2-efi grub2-efi-x64 shim-x64
grub2-mkconfig -o /boot/efi/EFI/redhat/grub.cfg

# --- UEFI 机器（Debian 系）---
grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=ubuntu
update-grub

# 退出并重启
exit
umount -R /mnt
reboot

UEFI 上还多一步：如果 NVRAM 里的启动项丢了，即使文件都在也进不去。用 efibootmgr 重建：

efibootmgr -c -d /dev/sda -p 1 -L "Linux" -l '\EFI\redhat\grubx64.efi'
efibootmgr -v          # 确认新条目在 BootOrder 里且排第一
模块 8

容器的"启动"和 OS 启动有什么不同

一句话：容器没有开机流程。没有固件、没有引导器、没有内核、通常也没有 init。它只是"一个被内核隔离起来的进程"，直接从 execve 开始。

阶段物理机 / 虚拟机容器
固件 POST有，几秒到几十秒无
bootloaderGRUB / systemd-boot无（镜像就是根文件系统）
内核初始化解压、探测硬件、挂根无（共享宿主机内核）
init / PID 1systemd，拉起几十个服务就是你的应用进程
启动耗时秒级毫秒级（进程启动时间）
状态有状态，可登录、可修复不可变，坏了就重建

PID 1 的三条特殊规则

在 Linux 里，PID 1 不是一个普通进程，内核对它有三条特殊对待：

规则后果
没有默认的信号处理器如果 PID 1 没有显式安装 SIGTERM 处理器，内核直接丢弃这个信号。这就是 docker stop 要等 10 秒然后 SIGKILL 的原因
不被 SIGKILL 杀死内核不允许杀死 PID 1（除非来自 init 自己的命名空间外）。所以 PID 1 卡死时只能重启容器
负责回收孤儿进程任何父进程先退出的进程都会被挂到 PID 1 名下，PID 1 必须 wait() 它们，否则变成僵尸

最经典的坑：shell form 吞掉信号

# ✗ shell form：实际执行的是 /bin/sh -c "java -jar app.jar"
CMD java -jar app.jar
# 进程树：PID 1 = /bin/sh，java 是它的子进程（PID 7）
# docker stop → SIGTERM 发给 sh → sh 不转发 → 10 秒后 SIGKILL
# 结果：应用没机会优雅关闭，退出码 137

# ✓ exec form：java 直接就是 PID 1
CMD ["java", "-jar", "app.jar"]
# docker stop → SIGTERM 直接到 JVM → 优雅关闭 → 退出码 143

退出码要会读：137 = 128 + 9（被 SIGKILL），143 = 128 + 15（被 SIGTERM），0 是正常退出。看到 137 且日志停在"shutting down"之前，基本可以断定是信号没传到。

什么时候需要真正的 init

如果你的进程会 fork 子进程（shell 脚本、cron、某些 Java/Python 的多进程模式），就需要一个"小而专"的 init 来收割僵尸、转发信号：

# 方案一：Docker 内置的 --init（实际是 tini）
docker run --init -d myapp:1.0

# 方案二：镜像里直接用它当入口
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["java", "-jar", "app.jar"]

# 方案三：Kubernetes 里没法加 --init，得在镜像里做
# 或者在 shell 脚本里用 exec 把 PID 1 让出去
#!/bin/sh
# 前置准备工作...
exec java -jar /app.jar
关于 exec 这个小技巧：shell 脚本里最后一行写 exec java ...，会用 java 进程替换掉当前 shell，PID 不变。这样 java 就成了 PID 1，直接收到信号。不写 exec 的话，shell 会 fork 一个子进程然后 wait，信号又卡在 shell 这一层了。

能不能在容器里跑 systemd

技术上可以（需要特权模式、挂载 cgroup、/sbin/init 存在），但这是反模式：

  • 违背"一个容器一个进程"的模型，日志、健康检查、生命周期全乱
  • 需要 --privileged 或大量 capability，安全性大幅下降
  • 镜像体积从几十 MB 涨到几百 MB
  • K8s 的探针、重启策略、资源限制都和 systemd 的假设冲突

例外场景：把容器当轻量虚拟机用（如 systemd-nspawn、LXC）、或者在 CI 里跑需要完整 init 的测试。生产容器不要这么干。

常见坑

十个启动相关坑

1
手改 /boot/grub/grub.cfg
下次内核更新或跑一次 grub2-mkconfig 就被覆盖。正确做法是改 /etc/default/grub，再重新生成。
2
UEFI 机器上把 grub.cfg 生成到 BIOS 路径
参数不生效，或者 GRUB 直接掉进 grub> 提示符。先 ls /boot/efi/EFI 确认是 UEFI，再决定输出路径。
3
rd.break 里改完文件忘了 touch /.autorelabel
SELinux 上下文是 unlabeled_t，系统起不来或登录被拒。改过 /etc/shadow、/etc/fstab 之后一定要打这个标记。
4
/etc/fstab 里的非关键盘没加 nofail
一块盘没插、一个 NFS 不通，整机就进 emergency mode。数据盘一律加 nofail。
5
用 /dev/sda2 而不是 UUID 写 root=
插拔硬盘、加装 NVMe 后设备名会变，直接找不到根。用 UUID 或 LABEL。
6
删了旧内核和 /lib/modules 下的旧目录
新内核起不来时没有退路。至少保留一个可用的旧内核和对应模块目录。
7
把 After=network.target 当成"网络已就绪"
network.target 只表示网络管理服务启动了，不代表网卡拿到 IP。要等地址得用 network-online.target。
8
看 systemd-analyze blame 就直接优化第一名
并行启动下 blame 的时间会重叠。要用 critical-chain 找真正串行在关键路径上的那个。
9
Dockerfile 用 shell form 启动应用
PID 1 是 /bin/sh，SIGTERM 不转发，docker stop 必然等满 10 秒再 SIGKILL，退出码 137。用 exec form 或加 --init。
10
内核参数拼错，以为生效了
内核不认识就静默忽略。改完用 cat /proc/cmdline 确认参数真的在，再看 dmesg 里有没有 Unknown kernel command line parameters。
自测

六道题

1. 在 UEFI 系统上，引导器文件实际存放在哪里？
正确答案：ESP 分区 + NVRAM。固件按 NVRAM 里的 BootOrder 找到 ESP 上的 .efi 文件。这也是为什么"文件都在但 NVRAM 项丢了"照样起不来，需要用 efibootmgr 重建。
2. 修改内核启动参数，正确的持久化流程是？
正确答案：改 /etc/default/grub 再重新生成。grub.cfg 是产物，手改会被覆盖。/etc/grub.d 是生成脚本，改它风险更高。RHEL 系还可以直接用 grubby。
3. initramfs 存在的根本原因是？
正确答案：先有驱动才能挂根。根分区在 LVM、软 RAID、LUKS 或远程存储上时，内核自己搞不定，必须靠 initramfs 里的模块和脚本来完成这一步，然后 switch_root。
4. 关于 systemd 的 After= 和 Requires=，哪个说法对？
正确答案：After 只管顺序。它不保证对方成功，甚至不保证对方存在。Requires 是强依赖（对方失败则本单元不启动），Wants 是弱依赖（尽力而为），日常应该优先用 Wants + After。
5. 系统进了 emergency mode，最可能的原因是？
正确答案：fstab 挂载失败。这是最高频的原因。进 emergency shell 后用 systemctl --failed 和 journalctl -xb 确认，注释掉问题行或加 nofail，再 systemctl default 继续。
6. 容器里 docker stop 总是等满 10 秒然后退出码 137，原因是？
正确答案：shell form 导致信号卡在 sh。PID 1 对未安装处理器的信号会直接丢弃。改用 exec form（CMD ["java","-jar",...]），或在脚本末尾用 exec，或加 --init。
