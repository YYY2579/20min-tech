开始前

造一块可以随便折腾的"磁盘"

不需要真的加一块盘。用一个普通文件当块设备（loop 设备，内核把文件映射成块设备的机制），格式化、挂载、删库、跑满 inode，全在里面做。

# 1. 造一个 512MB 的镜像文件
dd if=/dev/zero of=/tmp/test.img bs=1M count=512

# 2. 格式化成 ext4，并显式指定 inode 密度（方便后面观察 inode 耗尽）
mkfs.ext4 -i 16384 /tmp/test.img

# 3. 挂到 /mnt/t（-o loop 表示把这个文件当块设备用）
mkdir -p /mnt/t
mount -o loop /tmp/test.img /mnt/t

# 4. 看这个文件系统的全貌
df -Th /mnt/t
df -i /mnt/t
tune2fs -l /tmp/test.img | head -30

# 5. 收工
umount /mnt/t

需要装的工具：strace（看系统调用）、sysstat（提供 iostat）、iotop、lsof、attr、xfsprogs、btrfs-progs。Debian 系是 apt install strace sysstat iotop lsof attr，RHEL 系用 dnf install 同名包。

关于 root：挂载、改 /proc/sys/vm/dirty_*、跑 debugfs 都需要 root。在容器里通常没有 CAP_SYS_ADMIN，mount 会直接失败，所以要么用虚拟机，要么用 WSL2（WSL2 的内核支持 loop 挂载）。
本机内核版本会影响细节。文中涉及的默认值以 5.10 以上内核 + ext4 为准。用 uname -r 确认版本，用 mount | grep 挂载点 看实际生效的挂载选项，比记默认值可靠。
模块 1

文件系统抽象：VFS 与文件描述符

Linux 支持几十种文件系统，但上层只有一套 open/read/write/close。中间那层抽象叫 VFS（Virtual File System，虚拟文件系统）。它的价值不是"好看"，而是让 cp 这种程序不需要知道自己读的是 ext4 还是 NFS。

VFS 的四个核心对象

对象内核结构职责与生命周期
超级块struct super_block一个已挂载文件系统的全局信息：块大小、魔数、容量、操作方法表。挂载时从磁盘读出，卸载时释放
inodestruct inode一个文件的全部元数据（权限、大小、时间戳、数据块位置），但不含文件名。内存中的 inode 有引用计数，为 0 时回收
dentrystruct dentry路径中的一段名字到 inode 的映射，比如 /var/log 里的 log。全部缓存在内存里，叫 dcache
filestruct file一次 open 的产物：打开模式、当前偏移量、引用计数。同一个文件 open 两次，有两个 file 对象

"一切皆文件"到底统一了什么

统一的只是接口，不是实现。下面这些东西都能 open、都能塞进 epoll，但背后的读写函数完全不同：

对象read/write 的实际含义
普通文件读写 page cache，缺页时回磁盘
目录不能 write，只能通过 mkdir/unlink/rename 改；read 在早期实现里能读到目录项，现在基本不可用
块设备 /dev/sda绕过文件系统直接读写扇区，所以能用来做 dd 备份
字符设备 /dev/nullwrite 直接丢弃，read 立即返回 EOF
管道 / FIFOwrite 写入内核环形缓冲区，read 从中取；满了就阻塞
socketread/write 等价于 recv/send
/proc、/sys读写的是内核数据结构的视图，内容在读取时现场生成

文件描述符：三层表

fd（file descriptor，文件描述符）只是一个进程内数组的下标。真正的信息在两层全局结构里：

进程 A 的 fd 表            系统打开文件表               inode 表
 0 → stdin   ─┐
 1 → stdout  ─┼─→  struct file  ──→  struct inode  ──→  磁盘上的数据块
 2 → stderr  ─┤    (偏移量、flags、
 3 → /var/log/app.log ─┘     引用计数)
 4 → socket  ──→  另一个 struct file ──→  socket inode

这个结构解释了三件常被搞混的事：

  • fork 之后父子进程共享偏移量。因为子进程复制的是 fd 表，指向的是同一个 struct file。两个进程往同一个 fd 写，偏移量互相影响。
  • 各自 open 同一个文件，偏移量互不影响。因为有两个 struct file。这也是为什么多进程写同一个日志文件必须用 O_APPEND —— 追加模式下"定位到末尾 + 写"在内核里是一次原子操作，否则会互相覆盖。
  • dup 出来的 fd 共享偏移量。重定向 2>&1 就是用 dup2 让 fd 2 指向 fd 1 的同一个 file 对象。

为什么 open 有上限

限制查看方式含义
进程级软限制ulimit -n单个进程最多开多少个 fd，超了返回 EMFILE（Too many open files）
进程级硬限制ulimit -Hn软限制的上界，非 root 只能往下调不能往上调
系统级总量cat /proc/sys/fs/file-max整机所有进程合计的 fd 上限，超了返回 ENFILE
当前用量cat /proc/sys/fs/file-nr三个数：已分配 / 已分配但空闲（2.6 之后恒为 0）/ 上限
区分 EMFILE 和 ENFILE 很重要。EMFILE 是本进程开太多（连接泄漏、忘了 close），改 ulimit -n 或者修代码；ENFILE 是整机不够（通常是某个进程泄漏把全局额度吃光了），改 file-max 只是拖延，得找出那个进程。
排查手段：ls -l /proc/PID/fd | wc -l 数进程的 fd，lsof -p PID 看具体是什么文件，cat /proc/PID/limits 看该进程实际生效的限制。

还有一个容易被忽略的点：fd 是会被子进程继承的。服务端程序 fork 出子进程（或者 exec 一个外部命令）时，监听 socket 也会被带过去，导致父进程重启后端口仍然被占用。所以 open 和 socket 时应该加 O_CLOEXEC，让 exec 时自动关闭。

模块 2

inode、目录项与链接

一句话概括：文件名不在文件里，在目录里。文件本身只有编号（inode 号）和内容，名字是目录这个特殊文件里的一条记录。

inode 里存什么

字段说明
i_mode文件类型（普通/目录/设备/管道/socket/软链接）+ 12 位权限（含 setuid/setgid/sticky）
i_uid / i_gid属主与属组
i_size文件字节数。目录的 size 是它占用的目录项空间总和，不是目录里文件的个数
i_atime / mtime / ctime访问时间 / 内容修改时间 / 元数据变更时间。注意 ctime 不是创建时间，改权限也会更新它
i_links_count硬链接数。减到 0 且没有进程打开，数据块才真正释放
i_blocks占用的 512 字节块数量（含间接块），和 i_size 不成正比的就是稀疏文件
i_inoinode 号，在单个文件系统内唯一
数据块地址ext2/3 是 12 个直接指针 + 一级/二级/三级间接指针；ext4 默认改用 extent 树（一段连续块用"起始 + 长度"表示，大文件省指针）

没有文件名字段。这是理解硬链接、理解 rm 为什么不释放空间的钥匙。

目录项（dentry）

目录文件的内容就是一串 {inode 号, 名字长度, 文件类型, 名字} 的记录。所以"打开 /etc/nginx/nginx.conf"这个动作在内核里是：从根 inode 开始，逐个读目录文件，用名字查出下一级的 inode 号，直到拿到目标 inode。每一段查过的结果都缓存在 dcache 里，所以第二次访问同一个路径不再读盘。

# 看 inode 号：第一列就是
ls -li /etc/hostname
# 262146 -rw-r--r-- 1 root root 12 ... /etc/hostname

# 看一个文件的所有硬链接（按 inode 找）
find / -inum 262146 2>/dev/null
find / -samefile /etc/hostname 2>/dev/null

# 看 inode 的详细内容（ext4，只读模式，不需要挂载）
debugfs -R "stat <262146>" /dev/sda1

# 看文件系统层面分配了多少 inode、用了多少
df -i /

硬链接与软链接的本质区别

维度硬链接 ln a b软链接 ln -s a b
本质给同一个 inode 增加一个目录项新建一个独立文件，类型是 symlink，内容是目标路径字符串
inode 号与源文件相同与源文件不同，自己占一个 inode
文件大小与源文件相同（就是同一个文件）等于目标路径的字节数，/usr/bin/python3 就是 15 字节
链接数源文件的 i_links_count 加 1源文件的链接数不变
跨文件系统不行可以，甚至可以指向不存在的路径
指向目录普通用户不行；即使 root 也被内核禁止（防止目录树成环，只有 . 和 .. 是特例）可以
目标被删数据仍在，通过另一个名字照常访问变成悬空链接，ls 显示红色，readlink 仍能读出路径
权限位就是源文件的权限恒为 lrwxrwxrwx，实际权限由目标决定
为什么硬链接不能跨文件系统：目录项里存的是裸的 inode 号，没有"哪个文件系统"的信息。inode 号只在一个文件系统内部唯一 —— / 下的 inode 262146 和 /data 下的 inode 262146 是两个完全无关的文件。跨文件系统解析会直接指错，所以内核在 link() 里直接返回 EXDEV。
删除的真相：rm 实际调用的是 unlink()，只做两件事 —— 删掉目录项、把 inode 的链接数减 1。只有当链接数为 0 且没有任何进程持有打开的 fd 时，内核才回收 inode 和数据块。这就是"文件删了但磁盘没空"的全部原因，模块 7 会用到。
模块 3

日志式文件系统：崩溃时靠什么活下来

创建一个空文件，在磁盘上至少要改三处：inode 位图（标记这个 inode 已用）、inode 表（写入权限和时间戳）、目录项（把名字和 inode 号关联）。三次写如果只完成了一部分就断电，文件系统就会进入自相矛盾的状态：目录项指向一个没被分配的 inode，或者 inode 被占用却没有任何名字能找到它。

传统 fsck（file system check，文件系统检查）的做法是全盘扫描修复，几个 TB 的盘要跑几十分钟到几小时。日志（journal）的思路是：先把"打算怎么改"顺序写到一个固定区域，写成功了再改真正的元数据。崩溃后只需要重放日志尾部的一小段，几秒钟就能恢复一致。

一次事务的四个阶段

写入日志。把这次要改的所有元数据块（注意是块的副本，不是"操作语句"）写到 journal 区域。ext4 的 journal 是文件系统内的一个特殊 inode（inode 8），默认 128MB，可以用 mke2fs -J size= 调整。
提交。写一个 commit block 标记事务结束。这一刻事务才算"已提交"，在此之前崩溃，整个事务会被丢弃，文件系统回到事务前的状态。
检查点（checkpoint）。把 journal 里的块写回它们在文件系统里的真实位置。这一步可以慢慢做，做一半崩了也没关系 —— 日志还在，重启后重放一遍即可。
回收。确认所有块都已落位，释放 journal 空间给后续事务。

三种数据模式

日志保护的是元数据。用户数据要不要也走日志，由挂载选项决定。ext4 默认是 data=ordered。

模式行为崩溃后的结果性能
data=writeback元数据走日志，数据块随便什么时候写文件系统结构一致，但文件内容可能是旧数据或未初始化的块内容（安全风险：可能读到别人的数据）最快
data=ordered
（默认）		数据块先写，写完才提交元数据事务不会出现"文件变大了但里面是垃圾"，但可能丢掉最后一段写入中等
data=journal数据块也写进日志，落两次盘最强，数据和元数据都能重放最慢，且 ext4 下会禁用延迟分配

写屏障（barrier）

日志的正确性依赖一个假设：先写的块一定先落盘。但磁盘自带易失写缓存（write cache），它会重排写入顺序来提升性能，断电时缓存里没落盘的数据直接消失。结果就是"元数据提交了，数据还在缓存里丢了"，ordered 模式的保证被打破。

解决办法是写屏障：在提交事务前发一条 flush 命令，强制设备把缓存刷到介质上，再发后续写。ext4 默认 barrier=1，可以在 /proc/mounts 里确认。

# 看实际生效的挂载选项
mount | grep ' / '
cat /proc/mounts | grep ext4

# 查 ext4 的日志参数
tune2fs -l /dev/sda1 | grep -i -E "journal|mount options"

# 运行时改（写进 /etc/fstab 才能持久）
mount -o remount,data=ordered /
什么时候可以关 barrier：底层是带掉电保护电池（BBU 或超级电容）的 RAID 卡，且缓存策略是 write-back 时，缓存内容在断电后仍能保住，barrier 带来的 flush 就是纯开销，可以设 barrier=0。反过来，云盘、单盘 SATA、消费级 NVMe 上关 barrier 等于主动放弃崩溃一致性 —— 省下的那点 IOPS 换来的是断电后 fsck 和可能的数据损坏，不划算。
模块 4

写入路径与 fsync

这是全文最该记住的一节：write() 返回成功，只代表数据进了内核的 page cache，不代表落盘。掉电时，没落盘的部分就没了。

应用程序
   │  write(fd, buf, n)
   ▼
page cache（内核页缓存，标记为 dirty 脏页）  ←── write 在这里返回
   │  由内核回写线程（kworker/flush）或内存压力触发
   ▼
文件系统层：分配数据块、更新 inode、提交 journal 事务
   │
   ▼
块层：合并相邻请求、排序、按调度器策略下发
   │
   ▼
设备写缓存（易失，通常 64MB~4GB）
   │  flush 命令 / 缓存写满 / 掉电（数据丢失）
   ▼
持久介质（磁盘盘片 / NAND 闪存）

脏页回写的四个参数

参数默认作用
vm.dirty_background_ratio10脏页超过内存的 10% 时，后台开始回写，应用不受影响
vm.dirty_ratio20超过 20% 时，写进程被强制同步回写，表现为 write 突然卡住几百毫秒
vm.dirty_expire_centisecs3000脏页存活超过 30 秒就必须回写
vm.dirty_writeback_centisecs500回写线程每 5 秒醒一次检查

大数据量顺序写时，如果 dirty_ratio 太低，会频繁触发同步回写，出现周期性的写入毛刺。反过来调太高，一次掉电能丢的数据就更多。还有一种做法是设 dirty_bytes（非 0 时覆盖 ratio），按绝对字节数控制，对大内存机器更可控。

同步调用家族

调用保证什么
fsync(fd)文件数据 + 全部元数据（含 mtime、大小）+ 设备缓存 flush。最强也最贵
fdatasync(fd)数据 + 检索所必需的元数据（块映射、文件大小），不含 mtime。省掉一次元数据日志提交
sync()所有文件系统全刷。没有返回值、不等待完成、不保证设备缓存落盘，不能用于正确性保证
syncfs(fd)只刷该 fd 所在的文件系统，比 sync() 精确
O_SYNC每次 write 等价于 write + fsync，最慢
O_DSYNC每次 write 等价于 write + fdatasync

fsync 到底贵在哪

一次 fsync 至少包含三段串行等待：把脏页写进设备队列、等设备把数据写进介质、发 flush 命令等设备缓存落盘并返回。第三段是最容易被忽略的，因为它是一次完整的往返。

介质单次 fsync 量级说明
7200 转机械盘5~10 ms受限于一次寻道 + 旋转，本质是物理延迟，无法优化
SATA SSD0.1~1 ms受主控队列深度和 SLC 缓存影响，写满缓存后会明显变慢
NVMe SSD0.05~0.3 ms企业级带掉电保护，消费级在缓存写满后可能掉到几毫秒
网络云盘0.5~2 ms多一次网络往返，且受同盘其他租户影响，尾延迟长

按 1ms 算，单线程串行 fsync 的理论上限是 1000 次/秒。这就是为什么所有数据库都要做 group commit（组提交）：把同时到达的 N 个事务的日志合并成一次写 + 一次 fsync，吞吐直接乘以 N，代价是每个事务多等一点点。

为什么数据库要自己管刷盘

机制解决什么问题
WAL / redo log数据页是随机写、16KB 一个，直接刷很慢。改成顺序追加日志，只要日志 fsync 成功，事务就算持久化，数据页可以慢慢刷
doublewrite文件系统不保证 16KB 页的原子写。掉电可能只写了前 4KB，页被撕裂（partial page write），redo 也修不回来。做法是先把页写到一块连续区域并 fsync，再写正式位置
O_DIRECT绕过 page cache，避免"数据库缓冲池 + 内核页缓存"两份缓存，也避免内核回写时机不可控。代价是读写必须按块大小对齐
组提交把多次 fsync 合并成一次，摊薄固定开销
三个高频错误认知：
① "write 成功就是写好了"。不是，只进了 page cache。进程崩溃数据还在（内核还活着），机器掉电就没了。
② "rename 是原子的，所以文件安全"。rename 的原子性只保证"要么旧名字要么新名字"，不保证内容已落盘。正确姿势是：写临时文件 → fsync(临时文件) → rename → fsync(父目录)。少了最后一步，掉电后可能连新文件名都不存在。
③ "用了 O_DIRECT 就不需要 fsync"。O_DIRECT 只绕过缓存，数据仍可能停在设备缓存里，持久化语义还是要靠 fsync 或 O_DSYNC。 
# 观察 write 和 fsync 的真实耗时（-T 显示时间戳，-e 只看指定调用）
strace -T -e trace=write,fsync,fdatasync,openat -p <PID>

# 输出形如：write(3, "...", 4096) = 4096 <0.000021>
#           fsync(3)                = 0    <0.004312>
# 4ms 全花在 fsync 上，write 只花了 21 微秒 —— 这就是 page cache 的效果

# 看系统的脏页情况
grep -E "Dirty|Writeback" /proc/meminfo
模块 5

写放大与 SSD 的脾气

SSD 不是"更快的机械盘"，它的写入规则完全不同。读写的单位是页，擦除的单位是块，而且块只能整块擦。这一条物理限制派生出后面所有现象。

层级典型大小操作
页 page4KB / 8KB / 16KB读、写（写只能写"已擦除"的页，不能原地覆盖）
块 block256KB ~ 数 MB擦除（一次擦一整块，块内所有页一起失效）
Die / 通道—多个 die 可以并行读写，这是 SSD 高 IOPS 的来源

写放大是怎么来的

假设要改一个 4KB 的页，它所在的 1MB 块里其他页都是有效数据。FTL（Flash Translation Layer，闪存转换层，SSD 主控里负责逻辑地址到物理页映射的固件）不能原地改，只能：

把新数据写到一个新的空闲页，更新映射表，旧页标记为无效。
空闲页越来越少，触发垃圾回收（GC）：挑一个无效页比例高的块。
把这块里仍然有效的页读出来，搬到别的块。
整块擦除，变成新的空闲块。

写放大倍数 WAF（Write Amplification Factor）= 实际写进 NAND 的字节数 ÷ 主机请求写入的字节数。上例中为了写 4KB，可能要搬 1MB 再擦再写，WAF 轻松超过 10。稳态下消费级盘的 WAF 通常在 2~4，随机小写密集时能到 10 以上。

写入模式典型 WAF原因
大块顺序写（≥ 块大小）接近 1整块写满再换块，GC 几乎不需要搬数据
4K 随机写3~10+每次改一页都要牵动整块的 GC
写满 80% 以上容量显著升高空闲块少，GC 没有腾挪空间，被迫频繁搬运
所以"SSD 怕随机写"的准确含义是：随机写本身不慢（没有寻道），但它导致的写放大会消耗有限的擦写寿命（TLC 约 1000~3000 次 P/E cycle）、推高延迟、并在盘快满时让性能断崖式下跌。工程上的对策是：给 SSD 留出足够的空闲空间（建议使用率不超过 80%），尽量把随机写变成顺序写（日志、LSM 树都是这个思路）。

TRIM 的作用

删文件时，文件系统只是把块标记为空闲，SSD 并不知道这些块里的数据已经没用了。GC 时它会老老实实把这些"垃圾"当成有效数据搬走，白白消耗寿命和带宽。

TRIM 是一条命令，告诉 SSD"这些逻辑块的数据作废了"。FTL 收到后可以把对应页直接标记为无效，GC 时跳过不搬。

做法特点
mount -o discard每次 unlink 都同步发一条 TRIM。删大量小文件时性能会明显下降，不推荐在繁忙系统上用
fstrim -av批量扫描空闲块，一次性下发。由 fstrim.timer 每周自动跑（主流发行版默认开启）
blkdiscard /dev/sdX整盘丢弃，危险，只用于回收整块设备或重建 RAID 前
# 确认盘是否支持并已开启 discard（DISC-GRAN 非 0 表示支持）
lsblk -D

# 手动跑一次 trim（-v 显示每个挂载点回收了多少字节）
fstrim -av

# 看定时器状态
systemctl status fstrim.timer

# 看 SSD 的磨损与写入量（需要 root，字段随厂商差异较大）
smartctl -a /dev/nvme0 | grep -E "Percentage|Data Units"
模块 6

文件系统怎么选

文件系统特点硬限制适用
ext4最成熟、工具最全、几乎所有救援盘都支持。extent + 延迟分配 + 日志单文件 16TiB（4K 块）；inode 总数在 mkfs 时定死；支持缩小系统盘、通用场景、需要缩容的盘
XFSB+ 树索引目录、多个分配组（AG）并行分配、延迟分配、在线扩容单文件理论 8EiB；不能缩小；修复需卸载大文件、百万级文件的目录、高并发写、大数据盘
Btrfs写时复制、子卷、快照、数据校验和、透明压缩RAID 5/6 有已知的写入空洞问题，不建议用于生产需要快照回滚的场景、桌面、单盘校验
ZFS端到端校验、快照、去重、ARC 缓存、发送/接收复制CDDL 许可，不在 Linux 主线内核里；ARC 吃内存存储服务器、需要数据完整性保障的归档

为什么大数据盘常用 XFS

  • 目录查找是 O(log n)。ext4 的目录是线性的哈希树（htree），文件数上百万后创建和查找都会明显退化；XFS 的目录从一开始就是 B+ 树。
  • 分配组并行。XFS 把设备切成多个 AG（allocation group），每个 AG 有自己的空闲空间索引和锁。多线程并发写不同文件时不会抢同一把锁，这是它在多核机器上吞吐更好的核心原因。
  • 延迟分配 + 大 extent。先把写请求攒在内存里，等到回写时一次性分配一大段连续块，碎片少、元数据少。
  • 在线扩容简单。xfs_growfs /mountpoint 就能扩，不用卸载。RHEL/CentOS 从 7 开始默认就是 XFS。
选型时最该先问的一个问题：这块盘以后需不需要缩容？XFS 不能缩小，一旦选错，唯一的办法是备份 → 重建 → 恢复。云上扩缩容频繁的场景，ext4 更保险。反过来，如果盘只会变大、文件又大又多，XFS 更合适。

tune2fs -m 1 /dev/sdb1               # 事后改保留块比例

# XFS：扩容（只能扩）

df -i /data
模块 7

磁盘满了怎么查

"磁盘满"至少有四种完全不同的原因，用错排查方向会浪费大量时间。先做一件事：同时看 df -h 和 df -i，先分清是空间没了还是 inode 没了。

df 和 du 为什么对不上

原因表现与验证
已删除但被进程占用最常见。df 算的是文件系统层面已分配的块，du 遍历目录看不到这个文件（目录项已删）
挂载点覆盖先在目录里写了数据，之后把另一个文件系统挂到这个目录上，原数据被"盖住"，du 看不到但空间仍被占。卸载挂载后才能看到
保留块ext4 默认给 root 保留 5%，普通用户看到 df 100% 时，root 其实还能写
权限不足du 无法进入某些目录，统计结果偏小。用 root 跑一遍对比
稀疏文件与硬链接du 按实际占用块算，ls -l 显示的是逻辑大小；同一 inode 的多个硬链接，分目录统计会重复计数
快照 / 日志btrfs、zfs、LVM 快照占的空间不在任何目录里；ext4 的 journal 也占 128MB 左右

第一步：找已删除但被占用的文件

# 列出所有 link count 为 0 但仍被打开的文件
lsof +L1
lsof | grep -i deleted

# 输出里关注 SIZE/OFF 列，按大小排序
lsof +L1 2>/dev/null | awk '{print $7, $9}' | sort -rn | head

# 也可以在 /proc 里直接找
ls -l /proc/*/fd 2>/dev/null | grep deleted

怎么处理：找到持有该文件的进程 PID 和 fd 号（比如 /proc/12345/fd/7）。

  • 能重启服务：重启最干净，进程退出后引用释放，空间立刻回收。
  • 不能重启：用 : > /proc/12345/fd/7 把这个文件截断为 0。注意是截断不是删除，进程仍持有同一个 fd，继续写会从偏移 0 开始，日志内容会有空洞（前面是 \0）。
  • 绝对不能做的：再 rm 一次。目录项已经没了，rm 只会报 No such file，空间一点都不会释放。
为什么会发生：典型场景是 rm /var/log/app.log 之后没有 kill -HUP 让进程重开日志文件。进程的 fd 还指向原来的 inode，继续往里写，空间一直被占。正确做法是用 logrotate 的 create 模式配合 postrotate 发信号，或者用 copytruncate（有丢日志的窗口，但在不能重开文件时是唯一选择）。

第二步：inode 耗尽

# 关键：-i 看 inode，不是看空间
df -i
# Filesystem      Inodes  IUsed   IFree IUse% Mounted on
# /dev/sda1      6553600 6553600      0  100% /

# 找出哪个目录小文件最多（按目录聚合，别直接对全盘排序）
find / -xdev -type f 2>/dev/null | sed 's|/[^/]*$||' | sort | uniq -c | sort -rn | head -20

# 或者用 inode 数排序
for d in /var/*; do echo "$(find $d -xdev 2>/dev/null | wc -l) $d"; done | sort -rn | head

inode 耗尽的典型元凶：session 文件（每个用户一个）、邮件队列、缓存目录（每篇文章一个 HTML）、未清理的临时文件、百万级小文件的数据集。

注意：df -h 此时可能只显示 40% 使用率，但任何创建文件的操作都会报 No space left on device。这个报错和空间不足完全一样，所以排查时必须看 df -i。

根治办法只有两个：删掉小文件，或者换文件系统（XFS 动态分配 inode，不存在这个问题）。ext4 无法在线增加 inode 总数 —— resize2fs 扩容时会按比例增加，但缩容不会减少。

第三步：常规空间排查

df -hT各挂载点空间与文件系统类型
du -xhd1 / | sort -rh | head -20按一级目录看占用，-x 不跨文件系统
du -xhd1 /var | sort -rh | head逐层下钻，定位到具体目录
find /var -xdev -type f -size +1G -exec ls -lh {} \;找大于 1G 的单个文件
find /tmp -xdev -type f -mtime +7 -delete清理 7 天前的临时文件（先不加 -delete 看一遍）
tune2fs -m 1 /dev/sda1ext4 保留块从 5% 降到 1%，立即释放空间
journalctl --vacuum-size=500M限制 systemd journal 占用
findmnt -T /path确认这个路径到底在哪个文件系统上（排查挂载覆盖）
模块 8

观测：iostat 与 /proc/diskstats

磁盘慢的时候，第一个要回答的问题不是"哪个进程"，而是"是 IOPS 打满、带宽打满，还是延迟变高"。这三者的优化方向完全不同。

# -x 扩展字段，1 每秒采样，5 采 5 次
iostat -xz 1 5

# 输出关键列（Device 之后的顺序随版本略有差异，看表头对齐）
# r/s  w/s      每秒读/写完成次数
# rkB/s wkB/s   每秒读/写 KB
# r_await w_await  读/写平均耗时（ms，含排队）
# aqu-sz        平均请求队列长度
# %util         设备忙的时间占比
字段怎么读
await排队时间 + 服务时间。await 远大于设备本身的服务能力，说明在排队，瓶颈可能在队列深度或上游
r_await / w_await分开看读写。写延迟高但读正常，通常是回写压力或设备缓存写满
aqu-sz平均队列长度。持续大于 1 说明请求在堆积；配合 await 可以判断是"设备慢"还是"请求太多"
%util设备有请求在处理的时间占比。对单队列 SATA 盘，接近 100% 基本等于饱和
%util 的边界：它统计的是"有没有请求在处理"，不反映并行度。NVMe 盘有几十个队列、几千的队列深度，%util 显示 100% 时可能还有大量余量；RAID 卡后的虚拟盘同理。判断 NVMe 是否饱和要看 IOPS 是否接近标称值、await 是否明显上升，而不是看 %util。
还有一个交叉验证公式（Little's law）：aqu-sz ≈ IOPS × await ÷ 1000（await 单位 ms）。三个数对不上，说明采样窗口或聚合方式有问题。

/proc/diskstats 的字段

iostat 的数据就来自这里。每行前三个字段是主设备号、次设备号、设备名，之后是 14 个（新内核 20 个）计数器：

序号字段含义
4~7reads completed
reads merged
sectors read
ms reading		读完成次数、被合并的读次数、读扇区数（固定按 512 字节计）、读花费的毫秒
8~11writes completed
writes merged
sectors written
ms writing		写完成次数、合并的写次数、写扇区数、写花费的毫秒
12ios in progress当前正在处理的请求数，即瞬时队列深度
13ms doing io设备有 IO 的总毫秒数，%util 就是它的差分除以采样间隔
14weighted ms加权耗时，把队列深度也计入，用于算 aqu-sz
15~18discards ...discard 完成数、合并数、扇区数、耗时（内核 4.18 之后才有）
# 原始数据（字段顺序：major minor name 然后 4~18）
cat /proc/diskstats | grep -E " (sda|nvme0n1) "

# 自己算两次采样的差分，验证 iostat 的数字
awk '/ nvme0n1 /{print $4, $8, $6, $10}' /proc/diskstats; sleep 1; \
awk '/ nvme0n1 /{print $4, $8, $6, $10}' /proc/diskstats

定位到进程

iotop -oPa只显示真正有 IO 的进程，累计模式，-P 按进程而非线程
pidstat -d 1按进程看读写 KB/s，比 iotop 更适合脚本化
cat /proc/PID/io进程累计的 read_bytes / write_bytes（真实落盘量，不含缓存命中）
cat /proc/PID/stack内核态调用栈，看进程卡在哪个文件系统函数（需要 root 和内核符号）
bpftrace -e 'tracepoint:block:block_rq_issue { @[comm] = count(); }'按进程统计块层请求数（需要 bcc/bpftrace）
blktrace -d /dev/sda -o - | blkparse -i -块层全链路追踪，能看到每个请求的排队、下发、完成时间
一个实用的判断顺序：① iostat -xz 1 看是 await 高还是 %util 高；② await 高但 %util 不高 → 队列里请求少但每个都很慢，怀疑设备或远端存储；③ 两者都高 → 负载确实超了设备能力；④ 用 iotop -oPa 找到进程；⑤ 用 strace -T -e trace=write,fsync 或 /proc/PID/io 确认是哪个调用在等。
常见坑

十个踩过才知道的坑

1
以为 write 返回成功数据就安全了
write 只把数据放进 page cache。进程崩溃不影响（内核还在），但机器掉电、内核 panic 就丢了。需要持久化必须显式 fsync。
2
原子写文件时只 fsync 了文件，没 fsync 父目录
rename 的原子性不覆盖持久性。新建的目录项可能还在缓存里，掉电后文件名消失。顺序必须是：写临时文件 → fsync(文件) → rename → fsync(父目录 fd)。
3
rm 了大日志，空间一点没释放
进程还持有 fd，inode 链接数为 0 但引用计数不为 0，数据块不回收。用 lsof +L1 找出来，重启进程或截断 /proc/PID/fd/N。
4
磁盘报 No space left，但 df -h 只用了 40%
inode 耗尽。df -i 一看便知。ext4 的 inode 总数在 mkfs 时就定死了，只能删文件或换 XFS。
5
在 SSD 上开 mount -o discard
每次 unlink 同步发 TRIM，删大量小文件时延迟飙升。改用 fstrim.timer 周期性批量下发。
6
把数据库数据目录放在开了 COW 的 btrfs/zfs 上
写时复制会让数据库的随机写产生严重碎片和写放大。必须关掉 COW（btrfs 用 chattr +C，zfs 建独立 dataset 并设 recordsize）或换 ext4/xfs。
7
用 dd 测了个顺序写速度就认为磁盘没问题
dd 的顺序写几乎全落在缓存里，测不出真实能力。要用 fio 分别测 4K 随机读、4K 随机写、顺序读写，并带 fsync。
8
拿 %util 判断 NVMe 是否饱和
NVMe 多队列并行，%util 100% 时可能还有大量余量。要看 IOPS 是否接近设备标称、await 是否明显抬升。
9
容器里 df 看到的是宿主机的数字
没做 project quota 或 xfs quota 时，容器共享宿主机文件系统的容量视图。要按容器限制配额，得在挂载时启用 prjquota，并用 xfs_quota 设置。
10
在云盘上关掉 barrier 换性能
云盘没有你能控制的电池保护缓存，关 barrier 等于放弃崩溃一致性。省下的 IOPS 很有限，断电后可能直接 fsck 失败。
自测

六道题

1. 关于 inode，下面哪个说法是对的？
正确答案：文件名在目录项里。inode 存权限、大小、时间戳、数据块位置，唯独没有名字。目录本身也是一个文件，也有自己的 inode，其内容是 {名字, inode 号} 的记录表。
2. 硬链接不能跨文件系统的根本原因是？
正确答案：inode 号只在单个文件系统内唯一。目录项没有"哪个文件系统"的信息，跨 fs 解析会指到无关的文件，所以 link() 直接返回 EXDEV。软链接存的是路径字符串，所以可以跨。
3. 调用 write() 返回 4096 之后立刻断电，这 4096 字节一定丢了吗？
正确答案：不一定。write 只保证数据进了 page cache。如果内核的回写线程已经把它写出去、且设备缓存也刷了，就不会丢；否则会丢。要确定，必须 fsync 成功返回。
4. ext4 默认的 data=ordered 保证的是什么？
正确答案：数据先落盘，再提交元数据。这样崩溃后不会出现"文件大小已经更新，但内容还是垃圾块"。代价是每次提交前要等数据写完，性能介于 writeback 和 journal 之间。
5. 一个进程删除了 20GB 日志文件，但 df 显示空间没变。最可能的原因和处理方式是？
正确答案：fd 仍被持有。unlink 只减链接数，引用计数不为 0 时数据块不回收。用 lsof +L1 找到进程，重启它，或 : > /proc/PID/fd/N 截断。
6. SSD 上频繁 4K 随机写最主要的代价是？
正确答案：写放大。闪存不能原地覆盖，改一页会牵动整块的垃圾回收与搬运，实际写入 NAND 的数据可能是主机请求的数倍。对策是留足空闲空间、把随机写尽量变成顺序写。

脏页 dirty page已修改但尚未写回磁盘的缓存页
fsync把文件数据和元数据强制刷到持久介质，并 flush 设备缓存
journal日志区，先顺序记录元数据变更，崩溃后重放以保证一致
write barrier写屏障，强制设备缓存刷盘，保证日志提交顺序
写时复制 COW修改数据时不覆盖原位置，写到新位置再改指针
extent用"起始块 + 长度"描述一段连续块，替代逐块指针
稀疏文件逻辑大小远大于实际占用块数的文件，空洞不占空间
硬链接同一 inode 的另一个目录项，不能跨文件系统
软链接独立文件，内容是目标路径字符串，可跨文件系统
WAF写放大倍数，实际写入闪存的量 ÷ 主机请求写入的量
FTL闪存转换层，SSD 固件里做逻辑地址到物理页映射的部分
GC 垃圾回收SSD 搬移有效页、擦除整块以回收空间的过程
TRIM / discard告诉 SSD 哪些逻辑块的数据已作废，GC 时可直接丢弃
分配组 AGXFS 把设备切成的独立管理单元，可并行分配减少锁竞争
partial page write页只写了一部分就掉电，导致页撕裂，靠 doublewrite 兜底
下一步怎么练：① 用 loop 设备造一个 512MB 的 ext4，把 inode 密度调到极小，然后 touch 到 inode 耗尽，观察 df -h 和 df -i 的差异；② 写一个小程序，循环 write 后 fsync，用 strace -T 量出两者的耗时差；③ 造一个 2GB 文件，tail -f 挂着，然后 rm 它，用 lsof +L1 找出来并截断；④ 用 fio 在 SSD 上分别测 4K 随机写和 1M 顺序写，对比 IOPS 与延迟；⑤ 用 iostat -x 和 /proc/diskstats 手动算一次 aqu-sz，验证 Little's law。

之后值得单独学：fio 的完整压测方法、ext4/XFS 的元数据布局细节、NFS 与对象存储的一致性模型、容器存储驱动（overlayfs）的写时复制机制、以及 eBPF 在 IO 链路上的追踪。
