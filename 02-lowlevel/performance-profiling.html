性能分析不是玄学，是有固定顺序的排查流程。这篇讲清三件事：怎么测量才可信、火焰图到底在说什么、以及为什么优化顺序错了等于白干。

开始前

把观测工具装上

性能分析工具分两代：第一代是 perf、ftrace、strace 这类内核自带的；第二代是 eBPF（extended Berkeley Packet Filter，内核里的可编程虚拟机）系工具，代表是 bpftrace 和 bcc。两代都要会，因为前者简单直接，后者能回答前者回答不了的问题。

# 1. 确认内核版本。eBPF 需要 4.9+，bpftrace 建议 5.4+，BTF 支持建议 5.4+
uname -r

# 2. 装 perf（Debian/Ubuntu 系）
sudo apt install linux-perf
# RHEL / Fedora 系
sudo dnf install perf

# 3. 装 bpftrace
sudo apt install bpftrace

# 4. 看当前权限档位
cat /proc/sys/kernel/perf_event_paranoid

# 5. 临时放开（生产环境改之前先想清楚，见下面的警告）
sudo sysctl -w kernel.perf_event_paranoid=-1

# 6. 拉火焰图脚本（Brendan Gregg 的 FlameGraph，两个 Perl 脚本就够用）
git clone https://github.com/brendangregg/FlameGraph.git
export PATH=$PATH:$(pwd)/FlameGraph
paranoid 值含义能做什么
2（多数发行版默认）只允许用户态测量能 profile 自己的进程，看不到内核函数
1允许内核态测量能看到 syscall、内核栈，够用了
0额外允许 CPU 特定数据一般不需要
-1不限制全部功能，包括 raw tracepoint
容器里跑不了 perf，这不是配置问题。perf 需要 CAP_PERFMON（5.8 之前是 CAP_SYS_ADMIN）来读 PMU（Performance Monitoring Unit，CPU 里的硬件计数器），还需要宿主机的内核符号表 /proc/kallsyms。容器默认两者都没有。
要么在宿主机上跑，要么 docker run --privileged --pid=host -v /sys:/sys —— 但这等于把宿主机交给容器，生产环境别这么干。正确做法是在宿主机装 agent，把结果推出去。
一条命令验证环境是否可用：sudo perf stat -e cycles true。如果打印出 cycles 计数，说明 PMU 可用；如果报 Permission denied 或 not supported，先解决权限或虚拟化嵌套问题（很多云主机的 PMU 是关闭的，perf stat 的硬件事件会全部不可用，但 perf record -e cpu-clock 这类软件事件仍可用）。
模块 1

性能分析的基本方法

方法比工具重要。工具决定你能看到什么，方法决定你会不会看错。

先测量，再优化

人的直觉在性能问题上准确率极低。原因很简单：现代系统的瓶颈分布在 CPU、内存层级、锁、系统调用、网络、磁盘之间，而人对"哪一层慢"的直觉来自十年前的硬件模型。一个典型例子是"这段代码里有个 printf，肯定慢"—— 实际上 printf 写到行缓冲可能只要 200ns，而它旁边那次没加索引的数据库查询要 40ms。

更常见的错误是优化了不在关键路径上的代码。Amdahl 定律（Amdahl's law，描述并行化收益上限的经验法则）给出的结论很冷酷：如果一段代码只占总耗时的 5%，你把它优化到无限快，整体也只能快 5.3%。

手段开销能回答的问题不能回答
计数 counting极低（<1%）发生了多少次、总量多少是谁触发的、在哪条路径上
采样 sampling低（1%~5%）时间花在哪些函数上（统计意义上）短于采样周期的偶发事件
追踪 tracing高（10%~1000%）每一次调用的完整因果、参数、耗时不适合长时间开在生产上
选型口诀：先计数确认"有没有问题"，再采样找"问题在哪"，最后追踪确认"为什么"。反过来做（一上来就 strace）会得到一个几十万行的日志，然后什么都看不出来。

建立基线，一次只改一个变量

没有基线就没有"优化"。基线的意思是：在固定负载、固定数据量、固定机器配置下，记录一组可重复的指标。至少包括：吞吐（QPS）、延迟分位数（p50/p95/p99/p999）、CPU 使用率、内存 RSS、GC 次数（如果有）。

然后一次只改一个变量。同时改三处再测，你无法归因，只能得到一个"好像快了点"的结论 —— 而这种结论在下次出问题时毫无价值。

"快"和"快得可预测"是两件事

平均值是性能数据里最骗人的指标。100 个请求里 99 个 1ms、1 个 1000ms，平均值是 11ms，看起来还行，但那个 1000ms 的用户已经在投诉了。

# 一个真实的延迟分布长什么样（单位：毫秒）
p50   =    2.1      # 一半请求在这个值以内
p95   =    8.4
p99   =   47.0      # 长尾开始出现
p999  =  380.0      # 千分之一，通常是 GC / 锁等待 / 缺页
max   = 1240.0

# 如果只看平均值 = 3.9ms，你会得出"服务很健康"的错误结论

长尾的成因高度集中，就那么几类：锁竞争（等锁的线程被调度走）、GC 停顿、页缺失与内存回收、连接池耗尽、磁盘或网络抖动。所以 p99 一高，排查方向立刻收窄到这几个。

测量本身会骗你：协调遗漏（coordinated omission）。很多压测工具是"发一个请求，等它回来，再发下一个"。当服务变慢时，工具也跟着变慢，于是本来该在慢的时候发出的请求根本没被发出去，长尾被系统性地低估。
判断方法：如果压测工具报告的平均延迟是 5ms，但服务端记录的请求间隔是 50ms，说明发生了协调遗漏。修法是使用固定速率发压（如 wrk2、vegeta -rate）而不是闭环发压。

USE 方法：一分钟扫一遍系统

USE（Utilization / Saturation / Errors，利用率、饱和度、错误）是 Brendan Gregg 提出的一套检查清单，对每个资源都问三个问题。它的价值在于覆盖面—— 你不需要先怀疑某个东西，只要按清单走一遍。

模块 2

火焰图怎么读

火焰图（flame graph）是采样数据的可视化。它的坐标系和绝大多数图表都不一样，这是 90% 的人读错的地方。

三个坐标轴，各管一件事

维度表示什么常见误读
横轴采样占比。一个函数占的宽度 = 它出现在采样栈里的次数占总采样数的比例。横轴按函数名合并后排序，不是时间以为从左到右是时间流逝，去找"第 3 秒发生了什么"
纵轴调用栈深度。从下往上是被调用关系，最底下是入口（main / 线程启动函数）以为往上代表时间更晚
宽度该函数（含其子调用）消耗的 CPU 时间比例。宽度只由采样数决定，和栈深度无关以为"塔越高越慢"
最容易犯的错：把火焰图当时间轴看。火焰图里没有时间。它是一堆采样栈的聚合——把 30 秒内采到的几万个栈，按相同前缀合并、按字母排序后画出来。所以"左边先执行、右边后执行"完全不成立。
如果你需要时间维度，用火焰图的时间版本（FlameScope、或者 perf script 加时间戳自己切分），或者干脆用 trace。

怎么从图上找到真正的瓶颈

找宽而平的塔，不找高的塔。判断标准是"self 宽度"（自身宽度，不含子调用）：

先看顶层最宽的那几块。顶层函数的宽度就是它自己的 self time，因为下面没有子调用了。这些是"叶子节点"，是真正在烧 CPU 的代码。
再往下找到"平台"。如果某个函数很宽，但它的子函数加起来也很宽，说明它只是在转发，真正的工作在更下层。要找的是"自己很宽、子函数很窄"的那一层。
注意"平顶"。某个函数占满整行宽度（100%），且下面所有子调用都很窄，说明这个函数自己干了所有活 —— 通常是 memcpy、序列化、加解密、正则匹配这类。
忽略 __libc_start_main、start_thread 这类框架栈。它们宽是因为所有线程都从这进，不代表它们慢。
看颜色。火焰图默认颜色是随机分配的，只为区分相邻块，没有任何语义。有些变体会用颜色编码模块（蓝=用户态、红=内核态），但那要看生成脚本的参数，不能默认。
# 生成 on-CPU 火焰图的完整流程
# 1. 采样：-F 99 表示每秒 99 次，-g 表示记录调用栈
sudo perf record -F 99 -g -p 12345 -- sleep 30

# 2. 导出文本栈
sudo perf script > out.perf

# 3. 折叠：把相同栈合并成 "栈;栈;栈 计数" 的形式
stackcollapse-perf.pl out.perf > out.folded

# 4. 渲染成 SVG
flamegraph.pl out.folded > flame.svg
为什么是 99Hz 而不是 100Hz？采样频率如果和系统的某个周期性事件（定时器 tick、GC 周期）成整数倍关系，会形成锁步采样（lockstep sampling）——每次都恰好采到同一个位置，结果系统性偏斜。99 是质数附近的值，能打散这种共振。同理，-F 997 比 -F 1000 好。
栈是断的怎么办？如果你看到大量 [unknown]，或者栈只有两三层就断了，通常是两个原因：
① 二进制编译时开了 -fomit-frame-pointer（GCC 在 -O2 下默认开），perf 默认用帧指针展开栈，没有帧指针就断。解法：编译加 -fno-omit-frame-pointer，或者采样时用 --call-graph dwarf（开销大 2~5 倍，但不需要帧指针）。
② 缺少调试符号。装 -dbgsym / -debuginfo 包，或者至少保留未 strip 的二进制。

on-CPU 与 off-CPU：两个完全不同的问题

默认的 perf record 是 on-CPU 采样：每隔一段时间看"当前哪个线程在 CPU 上跑，栈是什么"。它只能看到正在消耗 CPU 的代码。

但很多性能问题不是 CPU 不够，而是在等：等锁、等磁盘、等网络、等页换入。这些线程不在 CPU 上，on-CPU 火焰图里完全看不到它们 —— 图会显示"CPU 很闲"，而服务很慢。

类型采样时机能回答典型工具
on-CPU线程被调度上 CPU 时定时中断CPU 时间花在哪些函数perf record -g
off-CPU线程离开 CPU（阻塞）时记录，回来时结束线程为什么不在跑、等了多久bpftrace / offcputime-bpfcc
wakeup线程被唤醒时谁唤醒了它、唤醒延迟多少wakeuptime-bpfcc
# 用 bcc 工具直接生成 off-CPU 火焰图（需要装 bcc-tools）
sudo offcputime-bpfcc -df -p 12345 30 > offcpu.folded
flamegraph.pl --color=io --title="Off-CPU Time" offcpu.folded > offcpu.svg

# 手工版：用 bpftrace 抓阻塞时长（按栈聚合）
sudo bpftrace -e '
tracepoint:sched:sched_switch /args->prev_state != 0/ {
    @start[args->prev_pid] = nsecs;
}
tracepoint:sched:sched_switch /@start[args->next_pid]/ {
    @us[args->next_pid] = hist((nsecs - @start[args->next_pid]) / 1000);
    delete(@start[args->next_pid]);
}'
判断该看哪张图，一句话：CPU 使用率高、吞吐上不去 → 看 on-CPU。CPU 使用率低、延迟高 → 看 off-CPU。两个都正常但就是慢 → 大概率在等下游（RPC、数据库），去看分布式追踪，不是单机工具能解决的。
模块 3

perf 常用命令

perf 是 Linux 内核自带的性能工具集，直接对接 PMU 和内核 tracepoint。它不需要装第三方依赖，是所有 Linux 机器的保底手段。

perf stat：看总量和比率

perf stat 不采样，只计数。它回答的是"这段程序跑一趟，消耗了多少 CPU 周期、执行了多少指令、缓存表现如何"。

# 基础用法：统计默认事件组
perf stat ./myapp

# 指定事件
perf stat -e cycles,instructions,cache-references,cache-misses,branch-instructions,branch-misses ./myapp

# 附着到已有进程，跑 10 秒
perf stat -p 12345 -- sleep 10

# 每个线程分开统计
perf stat -t 12345,12346 -- sleep 5
# 典型输出
 Performance counter stats for './myapp':

    12,345,678,901      cycles
     8,765,432,109      instructions              #    0.71  insn per cycle
       234,567,890      cache-references
        23,456,789      cache-misses              #   10.00% of all cache refs
     1,234,567,890      branch-instructions
        12,345,678      branch-misses             #    1.00% of all branches

       4.123456789 seconds time elapsed

怎么读这三个衍生指标

指标健康区间（经验值）说明
IPC
每周期指令数		计算密集 2~4
一般业务 1~2
<1 需警惕		IPC 低说明 CPU 大部分时间在等数据（缓存未命中、内存带宽、分支预测失败），而不是在算。IPC 低于 0.5 基本可以断定是访存瓶颈
缓存未命中率
cache-misses / cache-references		<5% 良好
>10% 偏高		注意 cache-references 统计的是 LLC（Last Level Cache，最后一级缓存，通常就是 L3）的访问。这个比率高说明工作集超出了 L3
分支预测失败率
branch-misses / branch-instructions		<2% 良好
>5% 有问题		每次失败要清空流水线，代价约 15~20 个周期。大量随机分支（如解析器里的 switch、无分支优化的排序）会推高它
IPC 是最省事的判据。同样是"CPU 100%"，IPC=3.0 说明真在算，优化方向是减少计算量（换算法、用 SIMD）；IPC=0.4 说明在等内存，优化方向是改数据布局（数组代替链表、提高局部性、预取）。两个方向的优化手段完全不重叠，判错了就是白干。

perf top：实时热点

相当于 CPU 版的 top。它按函数聚合采样，实时刷新，适合"现在就慢，我想立刻知道在哪"。

# 全局（所有进程）
sudo perf top

# 只看某个进程
sudo perf top -p 12345

# 只看某个线程
sudo perf top -t 12346

# 指定事件（比如看缓存未命中热点，而不是 CPU 时间热点）
sudo perf top -e cache-misses

# 显示调用链（按 e 键切换）
sudo perf top -g

输出里 Overhead 列是该符号占全部采样的比例，Shared Object 列是它来自哪个二进制（[kernel.kallsyms] 表示内核）。先看 Overhead 最高的前 5 行，超过 5% 的都值得看一眼。

perf record + report：采样分析

这是最常用的组合。record 把采样写进 perf.data，report 交互式浏览。相比 perf top，它可以事后慢慢分析，也能导出做火焰图。

# 采 30 秒
sudo perf record -F 99 -g -p 12345 -- sleep 30

# 采整个系统（所有 CPU）
sudo perf record -F 99 -g -a -- sleep 30

# 只采内核态
sudo perf record -F 99 -g --kernel-callchain -a -- sleep 10

# 文本模式看报告（适合贴到工单里）
sudo perf report --stdio

# 只看某个符号的调用链
sudo perf report --stdio --symbol=do_sys_open

# 看某个函数的调用者占比（反向）
sudo perf report --stdio -g caller
perf.data 会很大。默认采样率加上调用栈，30 秒可能几百 MB。三个控制手段：-F 99 降频率、--call-graph fp 用帧指针（比 dwarf 省很多）、-m 512 限制缓冲区大小（单位 KB，超出后丢弃最旧的）。在生产上采样，一定要先设 -m。

perf trace：系统调用视角

perf trace 是 strace 的轻量替代品。它基于内核 tracepoint 而不是 ptrace，开销低一到两个数量级。

# 跟踪某个进程的所有 syscall
sudo perf trace -p 12345

# 只看指定 syscall
sudo perf trace -e openat,read,write,fsync -p 12345

# 汇总模式：按 syscall 统计次数和耗时（最有用）
sudo perf trace -s ./myapp

# 看某个 syscall 的耗时分布
sudo perf trace -e nanosleep --duration 5 -a
工具实现机制相对开销适用
straceptrace 系统调用10x ~ 100x本地调试、单次复现
perf trace内核 tracepoint1.2x ~ 3x测试环境、短时生产排查
bpftraceeBPF + JIT<1.1x（视脚本）生产环境首选
绝对不要在线上对高 QPS 进程跑 strace -f。ptrace 会让目标进程每进一次 syscall 就停下来两次（进入、返回），由一个 tracer 线程接管。一个每秒 10 万次 syscall 的服务，加上 strace 后 QPS 会掉到几百，并且延迟从毫秒级涨到秒级 —— 这不是"变慢"，是"打挂"。
模块 4

eBPF 与 bpftrace

eBPF 是把用户写的程序注入内核执行的技术。它改变了性能分析的游戏规则：以前"要么开销大到不能上生产，要么信息少到没用"，现在可以两者兼得。

为什么 eBPF 比传统工具强

维度传统工具（strace / systemtap）eBPF
执行位置用户态进程，通过 ptrace 或内核模块通信内核态，事件触发时直接在内核里跑
上下文切换每次事件两次以上零次（数据攒在 ring buffer 里批量读）
编译方式解释执行或加载内核模块加载时JIT 编译成原生机器码
安全性内核模块崩溃 = 整机崩溃加载前有验证器做静态检查，禁止越界访问和死循环
开销10x ~ 100x<1% ~ 5%（取决于挂载点和脚本复杂度）
可观测范围只能看 syscall 边界内核函数、用户态函数、tracepoint、网络包、调度事件，任意位置

能观测什么

系统调用
谁在调、调了多少次、每次耗时多少、参数是什么。粒度到单个进程甚至单条线程
函数耗时
用 kprobe（内核函数入口）/ uprobe（用户态函数入口）在任意函数上打点，测进出时间差
网络
TCP 重传、连接建立耗时、每个连接的字节数、丢包位置。Cilium 就是基于 eBPF 做的网络方案
文件 IO
读写延迟分布、哪个文件被访问最多、页缓存命中率、直接 IO 还是缓冲 IO

四个可直接用的 bpftrace 单行脚本

# 1. 统计所有 syscall 的调用次数，按 syscall 名聚合
#    输出形如: @[sys_enter_read]: 128374
#    用途：快速看出这个进程是 IO 型还是计算型
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_* { @[probe] = count(); }'
# 2. 谁在打开文件（含文件名）
#    comm 是进程名，str() 把内核里的指针读成字符串
#    用途：排查"配置文件读不到""临时文件爆炸"
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat {
    printf("%-16s %s\n", comm, str(args->filename));
}'
# 3. 按进程统计 on-CPU 时间占比（99Hz 采样）
#    等价于"哪些进程在吃 CPU"，但比 top 更细，能挂过滤器
#    用途：容器里看不到宿主机 top 时，用这个定位是哪个容器在抢 CPU
sudo bpftrace -e 'profile:hz:99 { @[comm] = count(); }'
# 4. 读操作的延迟直方图（单位：纳秒）
#    kprobe 在函数入口记录时间戳，kretprobe 在返回时算差值
#    用途：判断读是走了页缓存（微秒级）还是真落到磁盘（毫秒级）
sudo bpftrace -e '
kprobe:vfs_read { @start[tid] = nsecs; }
kretprobe:vfs_read /@start[tid]/ {
    @ns = hist(nsecs - @start[tid]);
    delete(@start[tid]);
}'
读直方图的技巧：如果大部分样本落在 1μs ~ 10μs，说明命中页缓存；如果有明显的一坨落在 100μs ~ 10ms，说明有真实磁盘 IO；如果出现 10ms 以上的孤立长条，那是机械盘寻道或者存储层抖动。直方图的价值就在于它能同时显示"快路径"和"慢路径"两个峰，平均值会把它们糊成一个没意义的数。
bpftrace 的三个边界：
① 内核函数名不保证稳定。kprobe:vfs_read 在 5.x 能用，但内核版本升级后可能改名或内联掉。生产脚本要跟着内核版本回归测试。
② 内联函数探不到。编译器把函数内联后，符号在 /proc/kallsyms 里就没了，kprobe 会报 "symbol not found"。
③ 字符串拷贝有上限。str() 默认最多读 64 字节，长路径会被截断。要读更长用 str(ptr, 256)，但会增加开销。
模块 5

CPU 密集问题怎么查

现象：CPU 使用率打满、负载（load average）高、但吞吐上不去。这类问题相对好查，因为"在烧 CPU 的代码"是可见的。

确认真的是 CPU 瓶颈。看 vmstat 1 的 us + sy 是否接近 100%，wa（IO 等待）是否很低。如果 wa 很高，那就不是 CPU 问题，跳到模块 6。
找热点函数。sudo perf top -p <pid> 看前 10 行。如果热点在 [kernel.kallsyms] 里的 copy_user_enhanced_fast_string、__memmove_avx_unaligned 这类，说明瓶颈是内存拷贝，不是业务逻辑。
看 IPC 判断瓶颈类型。perf stat 拿到 IPC。高（>2）→ 计算受限，减少运算量；低（<0.6）→ 访存受限，改数据布局。
看缓存和分支。perf stat -e cache-misses,branch-misses。缓存未命中率 >10% 就要考虑工作集大小和访问模式；分支失败率 >5% 要看有没有可以用查表或无分支写法替代的条件跳转。
看是不是锁竞争伪装成 CPU 问题。自旋锁（spinlock）等待也会消耗 CPU。查 perf record -e cycles -g 里有没有大量栈顶是 native_queued_spin_lock_slowpath。有的话，问题在锁不在计算。

四个常见根因

根因perf 里的特征解法
算法复杂度高某个业务函数占 40%+，栈很浅换算法（O(n²)→O(n log n)），或加索引 / 哈希表
内存拷贝过多memcpy / memmove / copy_user 占大头减少序列化层数、用零拷贝（sendfile / splice）、用引用代替复制
缓存不友好IPC < 0.6，cache-misses >15%数组代替链表、结构体按访问频率重排字段、批量处理提高局部性
锁竞争futex / spin_lock / pthread_mutex_lock 在栈顶减小临界区、分段锁、无锁结构、每线程本地缓冲
伪共享（false sharing）值得单独记一笔。两个线程分别修改同一缓存行（64 字节）里的不同变量，硬件会把这一行在核心之间来回弹，性能可能下降 5~10 倍，而代码看上去毫无问题。
特征：多线程扩展性差（加核不提速），perf c2c 能看到 HITM（Hit Modified）计数异常。解法是把热点变量按缓存行对齐：C/C++ 用 alignas(64)，Java 用 @Contended（需要开启 -XX:-RestrictContended）。 
# 一次性拿全 CPU 侧的关键指标
perf stat -e cycles,instructions,cache-references,cache-misses,\
branch-instructions,branch-misses,context-switches,cpu-migrations \
-p 12345 -- sleep 10

# 检查伪共享（需要较新内核 + 支持 c2c 的 perf）
sudo perf c2c record -a -- sleep 10
sudo perf c2c report --stdio

# 看每个 CPU 核的负载是否均衡
mpstat -P ALL 1 5
模块 6

IO 密集问题怎么查

现象：CPU 不忙（可能只有 20%），但延迟很高、QPS 上不去。这类问题必须用 off-CPU 视角，因为线程大部分时间根本不在 CPU 上。

第一步：确认是不是真的 IO 问题

# iostat 的关键列（-x 显示扩展指标，1 表示每秒刷新）
iostat -x 1

# 输出里只需要盯四列：
#   %util     设备利用率。接近 100% 说明磁盘队列一直非空
#   await     平均等待时间（毫秒）= 排队时间 + 服务时间
#   r_await / w_await   分开看读和写
#   aqu-sz    平均队列长度。>2 说明请求在排队

# 按进程看谁在做 IO
pidstat -d 1

# 输出：kB_rd/s  kB_wr/s  kB_ccwr/s  iodelay（iodelay 是阻塞在 IO 上的时钟 tick 数）

# 看系统级换页（如果 si/so 不为 0，说明内存不足在换页，这是最糟的 IO）
vmstat 1
观测值含义下一步
%util ≈ 100%，await 高磁盘饱和看是读还是写；读写分离到不同盘；上 SSD
%util 低，await 高不是带宽问题，是单次 IO 慢可能是机械盘寻道、网络存储（NFS/EBS）抖动、RAID 卡电池问题
aqu-sz > 2 且持续请求在排队，队列深度不够或设备处理不过来调 nr_requests / IO 调度器；或减少并发
vmstat 的 si/so > 0内存不足，发生换页先解决内存，这不是 IO 优化能救的

第二步：用 off-CPU 找"谁在等什么"

关键是把"阻塞时长"和"阻塞原因"关联起来。下面这段脚本按内核栈聚合阻塞时间，能直接看出是等锁、等磁盘还是等网络。

# 按内核栈聚合 off-CPU 时间（微秒），跑 10 秒后自动打印
sudo bpftrace -e '
tracepoint:sched:sched_switch /args->prev_state != 0/ {
    @start[args->prev_pid] = nsecs;
}
tracepoint:sched:sched_switch /@start[args->next_pid]/ {
    @us[kstack] = sum((nsecs - @start[args->next_pid]) / 1000);
    delete(@start[args->next_pid]);
}
interval:s:10 { exit(); }'

输出会是这样的形状（栈从下往上读，最上面是阻塞点）：

# 等磁盘 IO
@us[
    blk_mq_dispatch_rq_list+...      # 提交块设备请求
    submit_bio+...
    ext4_writepages+...
    do_writepages+...
    __filemap_fdatawrite_range+...
    file_write_and_wait_range+...    # 这里是 fsync 的等待点
]: 4821330                            # 累计 4.8 秒

# 等网络
@us[
    sk_wait_data+...
    tcp_recvmsg+...
    inet_recvmsg+...
    sock_recvmsg+...
]: 1204550

# 等锁
@us[
    __schedule+...
    futex_wait_queue_me+...
    futex_wait+...
    do_futex+...
]: 890220
读法：哪个栈的累计时间最大，问题就在那里。上面三个栈分别指向三件完全不同的事：fsync 太频繁（把多次写合并成一次批量 fsync 就能解决）、下游响应慢（去看对端）、锁竞争（减小临界区）。
如果没有这些栈，只有 schedule，说明线程是被主动挂起的（比如在等条件变量），需要看用户态栈才能定位。

第三步：区分缓冲 IO 和直接 IO

# 看进程实际读了多少字节（rchar 是经过页缓存的逻辑读，read_bytes 是真正落到设备的）
cat /proc/12345/io

# 输出示例
rchar: 1284930221        # 逻辑读：程序要了 1.2GB
wchar: 38402931
syscr: 402133            # read 调用次数
syscw: 12043
read_bytes: 8472931      # 物理读：只有 8MB 真的走了磁盘 → 99% 命中页缓存
write_bytes: 38402931

rchar 和 read_bytes 的比值是最有价值的一个数：比值接近 1 说明基本没命中缓存（每次都要走盘），比值很大说明缓存效果很好。如果延迟高但这个比值也很大，那瓶颈不在磁盘，在网络或下游。

模块 7

内存问题怎么查

内存问题分三类，排查手段完全不同：泄漏（该释放的没释放）、分配热点（分配太频繁导致 CPU 和 GC 压力）、GC 压力（回收器本身成为瓶颈）。

内存泄漏：RSS 持续增长

判断标准不是"内存高"，而是"内存高且不回落"。正常程序的内存在高负载时上涨、空闲时下降；泄漏则是单调上升，且斜率与请求量正相关。

# 连续观察 RSS（单位 KB），看趋势不看绝对值
while true; do
  grep VmRSS /proc/12345/status
  sleep 5
done

# 更细的内存分布
cat /proc/12345/smaps_rollup
# 关注这几行：
#   Rss       实际占用的物理内存
#   Pss       按共享比例分摊后的占用（多进程场景更准）
#   Anonymous 匿名页（堆、栈）—— 增长通常就是泄漏
#   Private_Dirty 私有脏页 —— 也是泄漏的强信号

# 堆内存的实际分布（需要 jemalloc / tcmalloc 或者 glibc 的 malloc_info）
pmap -x 12345 | sort -k3 -n -r | head -20
glibc 的 malloc 不会把内存还给操作系统。即使程序 free 了，glibc 通常只把它放回自己的空闲链表，RSS 不下降。这就是"内存看起来泄漏但 valgrind 查不出泄漏"的常见原因。
判断方法：看 smaps 里的 Anonymous 是否持续增长。如果 free 之后 RSS 不降但 Anonymous 也不再涨，那不是泄漏，是分配器缓存。解法：调 MALLOC_ARENA_MAX，或者换 jemalloc / tcmalloc，它们有更积极的归还策略。

分配热点：谁在疯狂 malloc

高频小对象分配会带来三重代价：分配器本身的锁竞争、内存碎片、以及（在有 GC 的语言里）GC 频率上升。

# 用 uprobe 挂到 malloc 上，按调用栈统计分配次数
# 注意：只对动态链接 libc 的二进制有效，静态链接或自带分配器的要换符号
sudo bpftrace -e '
uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc {
    @[ustack] = count();
}
interval:s:10 { exit(); }'

# 按分配大小做直方图，看是不是大量小对象
sudo bpftrace -e '
uprobe:/lib/x86_64-linux-gnu/libc.so.6:malloc {
    @bytes = hist(arg0);
}
interval:s:10 { exit(); }'

如果直方图集中在 16~128 字节，且调用次数达到每秒几十万次，那就是典型的"小对象风暴"。解法是对象池或arena 分配：一次申请一大块，自己切片管理，把 N 次 malloc 变成 1 次。

GC 压力：看日志，不要猜

运行时开启方式关键指标
JVM-Xlog:gc*:file=gc.log:time,uptime:filecount=5,filesize=50m停顿时间、回收前后堆占用、Full GC 次数
GoGODEBUG=gctrace=1每轮 GC 的耗时、堆大小、STW 时间
Pythongc.set_debug(gc.DEBUG_STATS)各代回收次数、回收对象数
Node.js--trace-gcScavenge / Mark-Compact 的耗时
# Go 的 gctrace 输出，一行一轮
gc 14 @12.345s 0%: 0.021+2.1+0.003 ms clock, 0.17+1.2/3.4/0.9+0.02 ms cpu, 128->130->64 MB, 130 MB goal, 8 P
#     ↑轮次  ↑运行时长  ↑GC占用CPU比  ↑各阶段耗时(STW扫描+并发标记+STW终止)
#                                          ↑堆大小变化: 标记前->标记后->存活

# JVM 的 GC 日志，关键看这两行
[2.345s][info][gc] GC(12) Pause Young (Normal) (G1 Evacuation Pause) 512M->128M(2048M) 12.345ms
[8.901s][info][gc] GC(31) Pause Full (G1 Compaction Pause) 1900M->420M(2048M) 1832.441ms
#                                                              ↑Full GC 停了 1.8 秒，这就是 p99 的来源
GC 问题的判断标准不是"GC 次数多"，而是"单次停顿是否超过你的延迟预算"。如果 SLA 是 p99 < 100ms，那么一次 1.8 秒的 Full GC 会直接击穿它 —— 而这一秒半里，所有请求都在等。
优化顺序：① 减少对象分配（从源头降低频率）→ ② 调堆大小和分代比例 → ③ 换回收器（G1 → ZGC / Shenandoah，把停顿压到毫秒级）。换回收器是最后手段，因为它不解决"分配太多"这个根因。
模块 8

优化的顺序

这是全篇最重要的一节。同样的时间投入，做对了能快 100 倍，做反了只能快 1.2 倍 —— 而且代码变得更难维护。

层级典型手段收益量级代价
1. 算法与数据结构O(n²) → O(n log n)；嵌套循环换成哈希查找；去掉重复计算；加索引10x ~ 1000x改业务代码，逻辑风险中等，但收益最大
2. 架构与缓存加本地缓存 / 分布式缓存；批量化（N 次 RPC 合成 1 次）；异步化；连接池复用；减少跨服务调用5x ~ 50x改架构，一致性风险高，运维复杂度上升
3. 系统调用与 IO合并小写入（buffered writer）；批量读写；mmap / sendfile 零拷贝；io_uring；减少 fsync 次数2x ~ 10x需要理解语义，容易引入数据丢失风险
4. 指令级SIMD 向量化；消除分支；手动内联；预取；缓存行对齐1.1x ~ 2x可读性急剧下降，平台相关，几乎不可移植
顺序反过来就是浪费。真实场景：一个服务 QPS 上不去，工程师花两周把核心循环用 AVX2 重写，压测提升 1.3 倍。上线后仍然不够 —— 因为真正的瓶颈是每次请求要做 40 次 Redis 调用。后来把 40 次合并成 2 次批量调用，QPS 直接翻了 8 倍。
两周的 SIMD 工作，收益被一次架构调整完全淹没。而且那段 SIMD 代码现在没人敢改。

怎么判断"该往下一层走"

先算理论下界。如果一次请求必须做 40 次网络往返，每次 0.5ms，那延迟下界就是 20ms —— 这时候优化单次往返的 CPU 开销（比如 10μs）毫无意义，因为占比 0.05%。
再看 profile 的分布。如果火焰图里最宽的塔只占 15%，说明没有单点热点，是整体结构的问题 —— 该往上走一层（改架构），而不是往下钻（改指令）。
算投入产出比。每一层的收益上限是明确的：算法层能差几个数量级，指令层最多 2 倍。如果你的目标是把耗时砍一半，指令级优化理论上就做不到（除非你同时改了别的）。
确认瓶颈没被"藏起来"。有时候 profile 显示业务函数占 60%，但那是因为其他线程在等锁没被采样到。这时候优化业务函数只能拿到 1.6 倍，而解决锁竞争可能是 10 倍。所以先看 off-CPU，再看 on-CPU。
# 一个典型的"先算下界"练习
# 场景：接口 p99 = 120ms，profile 显示业务逻辑只占 8ms
# 结论：92% 的时间不在 CPU 上，不要动业务代码

# 查下去发现：一次请求串行调用了 12 个下游接口，每个平均 9ms
# 12 × 9ms = 108ms  ← 这就是下界

# 优化方案按收益排序：
#   1. 并行调用无依赖的下游（12 个变 3 批）      → 108ms → 27ms
#   2. 给可缓存的下游加缓存                      → 27ms → 8ms
#   3. 合并同源调用（3 个接口合并成 1 个批量）    → 8ms → 5ms
#   4. 优化本地序列化（从 2ms 降到 1ms）          → 5ms → 4ms  ← 最后才做
一句话总结顺序：先问"能不能不做"（算法层），再问"能不能少做"（架构层），再问"能不能一次做多件"（IO 层），最后才问"能不能做得更快"（指令层）。前三层是数量级的游戏，第四层是百分比的游戏。
常见坑

十个把排查带偏的坑

1
先改代码再测量
凭直觉改了三处，跑完发现快了 5%，但不知道是哪一处起的作用，也不知道有没有引入回归。正确做法是先建基线，一次只改一个变量。
2
把火焰图的横轴当时间轴
横轴是采样占比，不是时间。图上"左边"不代表"先发生"。要看时序必须用带时间戳的 trace，不是火焰图。
3
只看平均值，不看分位数
p50=2ms、p999=800ms 的服务，平均值可能只有 5ms，看起来健康。但千分之一的用户每次都在等 0.8 秒。
4
在生产环境对高 QPS 进程跑 strace -f
ptrace 的上下文切换开销是 10~100 倍。对一个每秒 10 万 syscall 的进程跑 strace，等于直接把服务打死。
5
只看 on-CPU 火焰图，找不到问题就以为"没有瓶颈"
CPU 使用率 20% 但延迟很高，说明线程在等。这时候要看 off-CPU 火焰图，on-CPU 图上什么都不会有。
6
采样频率用 100Hz 或 1000Hz
和系统定时器成整数倍会产生锁步采样，结果系统性偏斜。用 99 或 997 这类质数附近的值。
7
火焰图里全是 [unknown] 就直接放弃
八成是二进制编译时省略了帧指针。加 -fno-omit-frame-pointer 重编，或者采样时用 --call-graph dwarf。
8
把 glibc 不归还内存当成内存泄漏
free 之后 RSS 不降是 glibc 的正常行为。要看 smaps 里 Anonymous 是否持续增长，而不是看 RSS 的绝对值。
9
在容器里折腾 perf 权限
容器默认没有 CAP_PERFMON，也读不到宿主机内核符号。这不是配置问题，架构上就不该在容器里做全系统 profiling。要在宿主机装 agent。
10
跳过算法层直接做指令级优化
把 O(n²) 的循环用 SIMD 重写，最多快 4 倍；换成 O(n log n) 的算法，在 n=10 万时快 5000 倍。而且 SIMD 版本没人能维护。
自测

六道题

1. 火焰图的横轴表示什么？
正确答案：采样占比。宽度 = 该函数（含子调用）占用的采样数比例。纵轴才是栈深度。火焰图是聚合视图，没有时间维度。
2. perf stat 显示 IPC = 0.35，最可能的瓶颈是？
正确答案：访存受限。IPC 远小于 1 说明每个周期连一条指令都执行不完，典型原因是缓存未命中导致流水线停顿。优化方向是改数据布局和提高局部性，不是减少计算量。
3. 为什么生产环境不建议用 strace 排查性能问题？
正确答案：ptrace 开销太大。高 QPS 进程加上 strace 会直接被打挂。生产上应该用基于 tracepoint 的 perf trace 或基于 eBPF 的 bpftrace，开销低一到两个数量级。
4. 优化一个慢接口，正确的第一步是？
正确答案：先算下界、先定位层次。如果 92% 的时间在等下游 RPC，优化本地 CPU 代码的收益上限只有 8%。优化顺序是：算法 → 架构 → IO → 指令，反过来做基本是白干。
5. 服务 CPU 使用率只有 20%，但 p99 延迟 500ms。应该先看什么？
正确答案：off-CPU。CPU 闲而延迟高，说明线程大部分时间不在 CPU 上，是在等锁、等 IO、等下游。on-CPU 火焰图在这种情况下几乎全是空白，看不出任何东西。
6. 关于 eBPF 的低开销，根本原因是？
正确答案：内核态执行 + 零上下文切换。eBPF 程序加载时被验证器检查并 JIT 成原生机器码，事件发生时直接在内核里跑，结果攒在 ring buffer 里批量读。这是它比 ptrace 系工具快一到两个数量级的原因。

术语一句话解释
PMUPerformance Monitoring Unit，CPU 里的硬件计数器，能精确统计周期、指令、缓存事件

off-CPU线程被阻塞、不在 CPU 上的时间段，是延迟问题的主战场

USE 方法对每个资源检查利用率、饱和度、错误三项的排查清单
