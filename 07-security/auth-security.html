开始前

认证 vs 授权，先分清这两个词

这两个概念被混用是很多设计缺陷的源头。分清之后，你会发现它们的安全模型完全不同。

维度认证 Authentication授权 Authorization
回答的问题你是谁？（验证身份声明）你能干什么？（基于身份做决策）
典型凭证密码、TOTP、Passkey、签名证书角色、权限点、资源归属关系、属性策略
典型漏洞凭证填充、会话固定、JWT 伪造、MFA 绕过水平越权、垂直越权、IDOR、权限判定遗漏
失效模式冒充他人身份本人身份但做了超出权限的操作
凭证层
密码怎么存（哈希算法）、怎么传（TLS）、怎么找回（重置流程）
会话层
登录后怎么维持状态：Session Cookie 还是 JWT，怎么过期、怎么撤销
决策层
每个接口怎么判权：谁审核、审什么、漏一个接口会怎样
全篇主线：认证授权的事故，很少坏在密码学上，大多坏在流程上——重置链接不过期、登录不轮换会话 ID、判权只做在 Controller 一层。读的时候请对照自己系统的链路：登录 → 发会话 → 每次请求怎么验 → 每个接口怎么判权 → 登出怎么撤。
模块 1

会话管理：Session Fixation 与生命周期

会话安全的三个核心问题：会话 ID 怎么产生、登录时怎么处理、失效时怎么撤干净。Session Fixation 就是第二个问题的经典答案缺失。

Session Fixation 攻击原理（教学）

// 第 1 步：攻击者访问站点，拿到一个服务端分配的会话 ID（此时是未认证的匿名会话）
Set-Cookie: JSESSIONID=attacker-known-session-id

// 第 2 步：攻击者把这个 ID "种" 给受害者
// 手法一：XSS 里 document.cookie = "JSESSIONID=attacker-known-session-id"
// 手法二：URL 带会话 ID 的站点（?JSESSIONID=...）诱导点击

// 第 3 步：受害者用这个已被固定的会话 ID 登录
// 服务端验证密码通过，把该会话标记为"已认证"—— 但会话 ID 没变

// 第 4 步：攻击者用同一个 ID 访问，直接就是受害者的已登录态
// 全程不需要知道密码 —— 漏洞在于"登录成功后没有重新生成会话 ID"

// 修复：登录成功立刻 rotate 会话 ID（作废旧的，发新的）
session.invalidate();              // Java Servlet：作废旧会话
request.getSession(true);           // 创建全新会话（新 ID）
生命周期事件必须做的事常见错误
登录成功重新生成会话 ID（rotate），清空旧会话属性沿用匿名会话 ID，给 Fixation 留门
权限变更角色/权限变化时同步刷新会话内的权限快照会话里缓存了旧角色，提权后不生效、降权后仍有效
登出服务端作废会话（删 Redis 记录 / session store），再让客户端删 Cookie只删客户端 Cookie，服务端会话仍在，泄露的 Cookie 照样能用
过期双策略：绝对过期（如 12 小时强制重登）+ 空闲过期（如 30 分钟无操作）只设空闲不设绝对；过期时间过长（30 天）赌用户不会丢设备
敏感操作改密码、转账、绑定设备前二次认证（重新输入密码或 MFA）登录态一给到底，会话泄露后直接打穿所有敏感操作
Cookie 安全属性再强调一遍（与 XSS/CSRF 篇呼应）：HttpOnly（JS 读不到）、Secure（只走 HTTPS）、SameSite=Lax/Strict（跨站不携带）。注意 session ID 的长度与随机性——自增数字、时间戳当会话 ID，等于把枚举攻击的大门敞开。用密码学安全的随机源生成，至少 128 bit 熵。
模块 2

JWT 安全：五大攻击面

JWT（JSON Web Token，RFC 7519）把用户信息塞进 base64url 编码的 payload，服务端验签后信任。方便，但每个"方便"背后都有一个历史 CVE。

# JWT 三段结构：header.payload.signature（base64url，点分）
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..payload.....signature...
# header: {"alg":"HS256","typ":"JWT"}
# payload: {"sub":"1234","name":"zhangsan","exp":1735689600,"role":"user"}
# base64 是编码不是加密：payload 谁都能解码，别放敏感信息

攻击面一：alg=none 伪造

// 攻击原理：某些服务端库"信任 header 里声明的算法"，攻击者把 alg 改成 none 并删掉签名
{"alg":"none","typ":"JWT"}.{"sub":"1234","role":"admin"}.// 空签名段
// 库用"不验签"模式验证，攻击者自封 admin 成功
// 历史案例：CVE-2015-9235，jsonwebtoken < 4.2.2 未指定 algorithms 时中招

// 修复：验证时显式指定算法白名单，永不读 header 里的 alg 做决定
jwt.verify(token, secret, { algorithms: ["HS256"] });   // Node jsonwebtoken
Jwts.parser().verifyWith(key).build().parse(token)       // Java jjwt 0.12+ 强制密钥

攻击面二：弱密钥爆破

// HS256 是"密钥做 HMAC"的对称签名。密钥弱 → 离线爆破（工具：hashcat -m 16500）
// 一个 6 位数字密钥，现代 GPU 几分钟内就能算出，然后任意伪造令牌
// 修复：密钥至少 256 bit 随机（HS256 的安全强度与密钥长度成正比），从 KMS/环境变量注入
openssl rand -base64 48   # 生成高强度随机密钥

攻击面三：无过期与 refresh 不轮换

// 无 exp 的令牌 = 永久身份。泄露一次，永久有效，登出也撤不掉（无状态是双刃剑）
// refresh token 不轮换：长期令牌一旦泄露，攻击者无限续签
// 修复：access token 短寿命（5~15 分钟）+ refresh token 轮换：
// 每次用 refresh 换新 access 时，同时签发新的 refresh，旧的立即作废；
// 若检测到"已作废的 refresh 被再次使用"，视为泄露，作废该用户整个令牌家族

攻击面四：其他经典误用

误用后果与修复
payload 放敏感信息（手机号、身份证、内部角色细节）base64 可解码，令牌出现在日志/前端就裸奔。payload 只放非敏感标识，权限信息服务端现查
不校验 aud / iss给别的服务签发的令牌被本服务接受（令牌混用）。显式校验 audience 与 issuer（参考 jwt-go CVE-2020-26160 的教训）
令牌放 localStorageXSS 可直接读取偷走。会话 Cookie + HttpOnly 更稳；SPA 场景权衡后至少配强 CSP
把 JWT 当"加密"用JWS 只签名不加密；需要机密性用 JWE。payload 永远假设"可被任何人读取"
库 CVE 的通用教训：jsonwebtoken、pyjwt、jjwt、jwt-go 都出过"验证不严格"类 CVE（alg 混淆、aud 漏校、签名可选）。三条实践：① 升级依赖，安全版本修复已知问题；② verify 调用显式传全参数（algorithms、audience、issuer）；③ 用框架的标准集成（Spring Security OAuth、Django REST framework JWT）而不是裸调库。
模块 3

OAuth 2.0 与 OIDC 常见攻击

OAuth 2.0 是"委托授权"协议（让第三方应用有限度访问你的资源），OIDC 在它之上加"身份认证"层。它的攻击面集中在授权码流程和重定向 URI。

授权码流程（标准形态）

# 1. 客户端把用户重定向到授权服务器，带上 client_id、redirect_uri、scope、state
GET /authorize?response_type=code&client_id=app&redirect_uri=https://app.com/cb&scope=read&state=随机值

# 2. 用户登录并同意，授权服务器把授权码发到 redirect_uri
302 Location: https://app.com/cb?code=授权码&state=同一个随机值

# 3. 客户端用授权码 + client_secret 换 access token（服务端间请求）
POST /token  grant_type=authorization_code&code=...&client_id=...&client_secret=...

# 4. 用 access token 访问资源服务器 API
GET /api/me   Authorization: Bearer <access-token>

四大攻击与防御

攻击原理防御
授权码劫持授权码在浏览器/网络路径上被截获，攻击者抢先用它换 tokenPKCE（RFC 7636）：客户端先产生随机 code_verifier，用其派生 code_challenge 随授权请求发出，换 token 时出示 verifier —— 截到码也用不了
重定向 URI 篡改redirect_uri 校验宽松（前缀匹配/通配），授权码被发到攻击者域名精确全字符串匹配，禁止通配与前缀；https only；不用开放重定向拼 URI
登录 CSRF攻击者用自己的授权码回调你的 redirect_uri，把你的会话绑成他的账号state 参数：请求前存随机 state，回调时严格比对，并绑定会话
隐式模式token 直接放 URL fragment，进浏览器历史、Referer、日志；且无法 PKCE已废弃（OAuth 2.1）。改用授权码 + PKCE，公开客户端（SPA/移动端）同样适用
OIDC 的两个令牌别混：id_token 是身份断言（JWT，给客户端"证明用户已登录"用），access_token 是访问资源服务器的凭证。拿 id_token 去调 API 是常见误用——资源服务器可能接受它，但它没有被设计为资源访问凭据（audience 不同、通常是短命的）。
移动端/SPA 落地注意：公开客户端藏不住 client_secret，所以现代方案是授权码 + PKCE + 系统浏览器（不用 WebView：WebView 里宿主 App 能读用户密码，且无法查看地址栏防钓鱼）。refresh token 存系统安全 enclave（iOS Keychain / Android Keystore），不放 localStorage。
模块 4

密码存储：bcrypt 与 argon2

密码存储的目标不是"不可解密"，而是让拖库后的批量破解成本高到不可承受。选错算法的后果：同样一份泄露的数据库，MD5 几小时全破，bcrypt 要几年。

算法特性结论
MD5 / SHA-1 / SHA-256为"快"设计的通用哈希，GPU 每秒可算百亿次；无盐时彩虹表直接查禁止用于密码。"SHA-256 加盐哈希"仍是错的
bcrypt1999 年至今的业界默认，内置随机盐，cost 因子可调（2^cost 轮迭代），慢得恰到好处可用。cost 建议 10~12，每 18~24 个月复测调参
PBKDF2NIST SP 800-132 认可的 KDF，可调迭代次数，FIPS 友好可用。合规场景（金融、政府）首选，迭代 60 万次起
Argon2id2015 密码哈希竞赛冠军，memory-hard（吃内存），抗 GPU/ASIC 并行破解新项目首选。OWASP 推荐参数：m=19MiB, t=2, p=1
scrypt同样 memory-hard，比 Argon2 老，参数配置门槛高可用，Argon2id 更优
# ===== 三端正确姿势 =====
// Java（Spring Security 默认就是 bcrypt）
PasswordEncoder encoder = new BCryptPasswordEncoder(12);  // cost=12
String hash = encoder.encode(rawPassword);
encoder.matches(raw, hash);        // 验证：自动解析 salt 与 cost

// Python
import bcrypt
bcrypt.hashpw(pw.encode(), bcrypt.gensalt(rounds=12))     # bcrypt，cost=12
from argon2 import PasswordHasher
PasswordHasher().hash(pw)            # argon2id，默认参数即 OWASP 推荐值

// Node
const bcrypt = require("bcrypt");
await bcrypt.hash(pw, 12);          // cost=12，内部自动生成随机盐
"自己拼算法"是重灾区：MD5(SHA256(password + salt))、多轮 MD5、自研"加密"都挡不住专业破解 —— 攻击模型是"用你的算法跑 GPU 集群"，通用算法经过二十年对抗检验，自研没有。直接用库，用默认或文档推荐参数。
加盐的本质：每个密码用独立随机盐，让"同密码用户哈希不同"（彩虹表失效）、"批量破解必须逐用户进行"（无法一次计算打全库）。盐不用保密，跟哈希一起存即可。pepper（全局秘密，存 KMS 不进库）是可选加分项，但别指望它替代算法强度。
模块 5

权限模型：RBAC、ABAC 与越权

认证通过之后，每个请求都要回答"这个人能对这个资源做这个操作吗"。答漏了，就是越权（Broken Access Control）—— OWASP Top 10 的头名常客。

模型决策依据适用
RBAC角色 → 权限集合（admin 拥有 user:delete），用户绑定角色绝大多数后台系统，简单直观；细粒度不足（管不了"只能改自己的文章"）
ABAC属性策略：用户属性 + 资源属性 + 环境（时间/IP）+ 操作复杂多租户、数据行级权限；表达力强，实现与调试成本高
两者结合RBAC 管"功能入口"，ABAC 管"数据范围"生产主流。例：角色决定能进订单后台，归属属性决定能看哪些订单

两类越权与修复

// 水平越权：A 用户访问 B 用户的资源（同角色，跨账号）
GET /api/orders/1001   // 服务端只查"订单 1001 是谁的"了吗？没查就是 IDOR
// 危险代码：findById(1001) 直接返回
// 安全代码：查询强制带归属条件
SELECT * FROM orders WHERE id = ? AND user_id = 当前登录用户

// 垂直越权：低权限用户执行高权限操作
POST /api/admin/users/delete   // 普通用户登录态直接打管理接口
// 危险：只有前端隐藏了入口，服务端没判权
// 安全：服务端强制注解 + 集中式判权
@PreAuthorize("hasRole('ADMIN')")        // Spring Security
@require_role("admin")                     // 通用原则：每个敏感接口显式声明
防越权的工程纪律（比模型选择更重要）：
① 数据访问默认带租户/归属条件——Repository 层封装"当前用户"上下文，忘传参数就编译不过（或查询直接失败），比"记得传"可靠；
② 判权集中在网关/拦截器/注解，不散落在 if-else 里，漏一个接口能被测试发现；
③ 授权测试进 CI：同一接口用低权 token 打一遍，期望 403（自动化越权扫描）；
④ 默认拒绝：判权逻辑的默认分支是"拒绝"，不是"放过"。
模块 6

多因素认证（MFA）

MFA 把"单因子（密码）被破即全线崩溃"变成"还要第二道关"。因素分三类，强度差异巨大。

因素类型代表实现强度与坑
知道什么密码、PIN、安全问题最弱：可被钓鱼、爆破、重用。安全问题（母亲姓名）基本等于公开信息
拥有什么TOTP 动态码（RFC 6238，30 秒一变）、短信验证码、硬件密钥TOTP 防爆破但可被钓鱼（实时中继）；短信有 SIM 交换与 SS7 风险，仍比没有强
固有特性指纹、人脸、WebAuthn / Passkey最强：Passkey 绑定站点 origin，钓鱼网站拿不到凭证，是现在的主推方向
# TOTP 验证的最小实现逻辑（Python，pyotp）
import pyotp
secret = pyotp.random_base32()              # 开户时生成，存服务端，扫码给用户
totp = pyotp.TOTP(secret)
totp.verify(user_input_code)                # 校验当前窗口的 6 位码
# 服务端要点：每个码只许用一次（防重放）、限失败次数（防爆破）、
# 允许 ±1 个时间窗口（容忍时钟漂移，但别放宽到 ±10）
MFA 的三个典型误配：
① 只在前端"第二步"拦截：攻击者直接 POST 登录后接口或跳过第二步的接口，服务端必须对每个敏感接口强制判"已完成 MFA"的会话标记；
② 恢复码形同虚设：恢复码也应该是随机的、一次性使用的，且用后即焚 —— 固定不变的"备用密码"是后门；
③ 没有设备绑定与告警：新设备登录、MFA 更换、异地登录都该发通知，这是发现凭证泄露的主要信号源。
模块 7

高危流程审计：找回密码、枚举与限流

登录和会话之外，最常被攻破的是辅助流程：密码找回、用户枚举、暴力破解。它们的共同点是"平时没人审，出事就是批量账号沦陷"。

密码找回流程的 checklist

重置 token 必须随机且高熵：密码学随机数（CSPRNG），至少 128 bit；可预测（时间戳、用户 ID、MD5(手机号)）等于没锁门。
token 一次性 + 短过期：用后即焚，15~30 分钟过期；重置成功后作废该用户所有已发令牌，并强制下线其他会话。
token 绑定用户与用途：校验时确认"这个 token 是发给这个账号的、用于这个场景的"，不接受别处捡的 token。
重置链接的域名与 Host 头：邮件里的链接域名硬编码，不信请求的 Host 头（Host 头注入曾是大量密码重置投毒的根因）。
找回后全量通知：给用户发"您的密码已被修改"邮件/短信 —— 这是受害者发现自己账号被攻破的主要途径。

用户枚举与限流

// 用户枚举：错误信息、响应时间、注册接口暴露"账号是否存在"
"用户不存在" vs "密码错误"   // 两种响应 = 免费的账号探测接口
// 修复：统一模糊提示"用户名或密码错误"，注册/找回接口加验证码与频率限制

// 暴力破解与凭证填充（credential stuffing）：用泄露库的账号密码批量试
// 防线：登录限流（同账号 + 同 IP + 全局三维）、失败锁定（指数退避）、
// 设备指纹异常告警、以及 MFA（凭证填充的最大克星）
限流的三个维度都要有：只按账号限 —— 攻击者打一个账号列表慢慢磨；只按 IP 限 —— 攻击者换 IP 池（botnet）；只按全局限 —— 正常用户被连坐。账号 × IP × 全局三层，各自设阈值。验证码放最后一道（影响体验），别放第一道。
模块 8

真实配置与代码汇总

Spring Security 安全基线（Java）

// 密码编码器：bcrypt，cost=12
@Bean
PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(12); }

// 会话管理：固定防护 + 并发控制 + Cookie 加固
http.sessionManagement(s -> s
    .sessionFixation().migrateSession()          // 登录时轮换会话 ID（防 Fixation）

上线前八项自查

会话：登录 rotate 会话 ID；登出服务端作废；绝对 + 空闲双过期；Cookie 四件套齐全。
JWT：verify 显式传 algorithms / aud / iss；access ≤ 15 分钟；refresh 轮换 + 重放检测；payload 无敏感信息。
OAuth：redirect_uri 精确匹配；state 全流程校验；PKCE 开启；不用隐式模式。
密码：bcrypt(cost≥10) / argon2id；升级所有遗留 MD5/SHA 哈希（登录时透明重哈希）。
授权：敏感接口逐个有显式判权；数据查询带归属条件；默认拒绝。
找回：重置 token 高熵 + 一次性 + 短过期；Host 头不信任；修改后全量通知。
限流：登录/找回/MFA 验证三维限流；失败退避；异常告警。
依赖：认证相关库（jwt/session/oauth）保持最新，订阅 CVE 通告。
避坑

十个真实坑

1
登录成功后沿用旧的会话 ID
Session Fixation 的标准入口：攻击者先种一个匿名会话 ID，受害者登录后该 ID 直接变成已认证会话。登录成功必须 invalidate + 重建会话（migrateSession / session.regenerate）。
2
登出只删客户端 Cookie
服务端会话还在，泄露的 Cookie / 被记住的 token 照样能用。登出必须服务端作废会话记录（Redis/session store 删除），JWT 场景用黑名单或短过期兜底。
3
JWT 验证不指定 algorithms
库"信任 header 声明的 alg"时，攻击者发 alg=none 的空签名令牌即可伪造身份（CVE-2015-9235 同款）。verify 必须显式传 ["HS256"] 之类的白名单。
4
JWT payload 里放敏感信息
base64url 是编码不是加密，任何拿到令牌的人（日志、前端、中间人）都能解出手机号、身份证、内部角色。payload 只放非敏感标识，权限数据服务端现查。
5
access token 长期有效 + refresh 不轮换
令牌一签就是 30 天，泄露后登出都撤不掉；refresh token 永久有效等于给攻击者续期钥匙。access 短寿命（5~15 分钟）+ refresh 轮换 + 重放检测，缺一不可。
6
OAuth redirect_uri 用前缀匹配或通配
配置了 "https://app.com/" 当前缀，攻击者注册 "https://app.com.evil.com" 即可接收授权码。必须全字符串精确匹配，https only。
7
用 MD5 / SHA-256 存密码
"我加盐了"也不行 —— SHA-256 为速度设计，GPU 每秒百亿次，加盐只是逼对手逐用户算。用 bcrypt（cost 10~12）或 argon2id，慢是特性不是缺陷。
8
接口只查 ID 不查归属（IDOR）
GET /api/orders/1001 只按主键查，不改 ID 就能看所有人的订单、改所有人的资料。每个数据访问强制带 user_id = 当前用户条件，权限测试进 CI。
9
密码重置 token 可预测或不过期
token 用时间戳/用户 ID 生成、或 24 小时不过期、或可重复使用，都等于把账号送给攻击者。token 必须 CSPRNG 高熵、一次性、15~30 分钟过期，且邮件域名硬编码不信任 Host 头。
10
登录接口无限流，错误信息还区分"用户不存在/密码错误"
等于同时开放了账号枚举接口和暴力破解入口。统一模糊错误提示 + 账号×IP×全局三维限流 + 失败退避 + 异常告警，四件一套配齐。
自测

六道题

1. Session Fixation 攻击成立的根本原因是？
正确答案：登录后不轮换会话 ID。攻击者先获得一个匿名会话 ID 并"种"给受害者，受害者登录后该 ID 升级为已认证态，攻击者直接用同一 ID 就是登录态。修复：登录成功立即 invalidate 旧会话、创建新会话（migrateSession / regenerate）。
2. 关于 alg=none 攻击，正确的防御是？
正确答案：验证时固定算法白名单。alg=none 攻击的根因是库"信任令牌自己声明的算法"，攻击者改 alg 为 none 并去掉签名即可伪造。显式传 algorithms 参数后，none 不在白名单直接拒签。
3. 为什么密码存储不能用 SHA-256（即使加了盐）？
正确答案：太快。密码哈希要的是"故意慢"（可调成本的 KDF），bcrypt 的 cost 因子、argon2id 的 memory-hard 参数就是为拖慢破解设计的。加盐只解决彩虹表和同密码同哈希，不解决计算速度。碰撞漏洞对密码存储场景也不是主要威胁。
4. GET /api/orders/1001 能查看任意用户的订单。这是哪类漏洞？怎么修？
正确答案：水平越权 / IDOR。判据是"同角色用户访问了他人的数据行"。修复不是加角色校验（用户本来就是合法登录的），而是每个数据访问带资源归属条件，且判权默认拒绝、测试进 CI。
5. 关于 OAuth 2.0 的 PKCE，正确的是？
正确答案：用挑战码绑定授权码与发起方。授权码在回传路径上可能被截获，但攻击者没有 code_verifier 就换不到 token。公开客户端（SPA/移动端藏不住 secret）恰恰最需要 PKCE，配合授权码模式（而非已废弃的隐式模式）使用。
6. 下面哪项不属于密码找回流程的必要防护？
正确答案：信任 Host 头是错误做法。攻击者构造带恶意 Host 头的请求，重置邮件里的链接域名就被改成攻击者的，用户点链接即泄密。邮件域名必须硬编码，token 要高熵随机、一次性、短过期，并做全量通知。
