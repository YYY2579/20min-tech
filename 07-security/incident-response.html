二十分钟学透安全应急响应

应急响应的胜负，在入侵发生之前就已经决定了一半。这篇不讲概念名词，讲的是半夜被叫起来之后先做什么、再做什么、绝对不能做什么：取证、遏制、溯源、根除、恢复验证，以及真实环境里能直接抄的排查命令。

开始前

应急响应的三条铁律

在看任何流程之前，先把这三条刻进肌肉记忆。它们决定了你是在"处置事故"还是在"制造二次事故"。

铁律一：止血优先，但取证先于清除。遏制（断网、封 IP、下线）可以做在取证前面，但重装、还原、格式化必须做在取证后面。没有镜像和日志，你连"有没有被偷数据"都回答不了。
铁律二：不碰原始证据。不在被入侵主机上直接跑分析工具，不重启（内存证据全丢），不登进去"看看"。所有操作先镜像、先快照、先拷贝。
铁律三：按预案而不是按情绪。慌乱之下最常见的三个动作——直接重装、只改密码、只处理这一台机器——每一个都会把一次小事件拖成一次大泄露。
一个残酷的行业口径：应急响应领域普遍用 MTTD（平均检测时间）和 MTTR（平均遏制时间）衡量团队水平。业内的常见量级是 MTTD 按"天"甚至"月"计，而一次勒索软件从入侵到加密文件平均只需要数小时。检测速度就是损失上限——这也是复盘永远要把"怎么更早发现"排在第一改进项的原因。
模块 1

应急响应生命周期：六阶段

主流框架有两套：NIST SP 800-61（四阶段：准备、检测与分析、遏制/根除/恢复、事后活动）和 SANS PICERL（六阶段）。工程上把两者合并成六个可执行阶段最好用。

阶段目标关键动作与产出物
准备出事前把弹药备好应急预案与联系人清单、日志集中留存（≥6 个月）、备份可恢复演练、EDR/HIDS 覆盖、取证工具与镜像存放空间、每年至少 1 次演练
检测尽早发现异常，确认是不是真事件告警分诊（区分误报与真实）、确认现象与影响范围、定级。产出：事件单 + 初步时间线
遏制止血，防止损失扩大隔离主机、封禁 IP/账号、下线受影响功能、WAF 临时规则。遏制优先于彻底根除
根除找出并移除所有入侵要素删 Webshell/后门、清计划任务、修漏洞、换凭据、清横向移动痕迹。同源资产同步排查
恢复安全地把服务拉起来从干净备份还原、漏洞复测通过、后门复查、凭据全量轮换、灰度恢复 + 加强监控 7~14 天
复盘让下一次来得更晚、应对得更快完整时间线、根因分析、MTTD/MTTR 数据、改进项（检测规则、加固项、流程缺口）并落实到责任人和期限
阶段不是严格的瀑布。真实事件里"遏制"和"检测"经常交替循环：刚隔离一台，监控又爆出第二台。所以应急小组要滚动更新事件单，每次动作（谁、什么时间、对哪台机器、做了什么）都记录在案——这份记录既是后续溯源的素材，也是复盘和法律场景下的证据链。
遏制阶段最容易犯的错：过度遏制。直接拔网线、关机、删库，业务损失比入侵本身还大。正确做法是分级决策：核心数据库正被加密传播 → 立刻隔离；边缘站点 Webshell 一枚 → 先删后门、加 WAF 规则、观察。遏制强度与危害程度匹配，才是专业的应急响应。
模块 2

事件分级与上报流程

定级决定了响应速度、谁来指挥、要不要上报监管。定级错误是应急响应里最贵的错误之一——该报的重大事件没报，本身就是违法。

事件分级（参照《国家网络安全事件应急预案》口径）

级别典型情形响应要求
特别重大
（Ⅰ级）		重要系统大面积瘫痪、核心数据大规模泄露、关键业务中断超过规定时长、造成特别重大社会影响立即启动最高级响应，单位一把手牵头，按规定立即上报主管部门与属地网信、公安
重大
（Ⅱ级）		重要数据泄露、多个系统受控、勒索加密、较大范围业务中断启动应急预案，安全负责人现场指挥，按属地要求时限上报
较大
（Ⅲ级）		单系统被入侵、发现 Webshell/后门、小范围数据泄露、扫描与利用尝试频繁安全团队处置，事后书面报告，按需上报
一般
（Ⅳ级）		误报、无实质影响的扫描、单点异常已自愈记录归档，转为检测规则

上报流程要点

  • 内部上报：一线发现 → 安全团队（事件单）→ 安全负责人 → 管理层/法务/公关。涉及数据泄露的，法务和公关要在 1 小时内知情，因为对外口径和监管答复需要时间准备。
  • 监管上报：依据《网络安全法》《关键信息基础设施安全保护条例》，发生事件应按规定向属地网信部门、公安机关报告；关基运营者还应向保护工作部门报告。常见属地细则要求较大及以上事件数小时内初报、24 小时内补书面详情、处置完毕后提交总结。具体时限以属地网信部门和行业主管部门口径为准，提前问清楚并写在预案里。
  • 告知受影响个人（触发《个人信息保护法》泄露通知义务时）：通知监管部门和通知受影响个人，内容包括泄露信息种类、原因、可能危害、已采取的补救措施。这需要法务定稿，技术侧提供准确的事实边界。
  • 上报材料：初报三要素——发生了什么、影响范围、已做什么。不要等查清了再报，也不要为了好看隐瞒。
关基运营者的特殊点：《关键信息基础设施安全保护条例》要求运营者优先保障关键信息基础设施安全，建立健全网络安全监测预警制度，发生事件立即启动应急预案并报告。翻译成工程语言：你的等保/关基系统必须有7×24 的监测能力和可执行的值班表，而不是一份挂在墙上的预案文档。
模块 3

取证基础：镜像、内存、时间线

取证的目标只有一个：把攻击者留下的所有痕迹固定成不可篡改的证据，并还原出完整时间线。顺序永远是：先固定，后分析。

1. 磁盘镜像（优先级最高，顺序第一）

# ===== 磁盘镜像：挂载为只读，先固定再分析 =====
mount -o ro /dev/sdb1 /mnt/evidence-ro       # 只读挂载，防止手滑写盘
dc3dd if=/dev/sdb of=/evidence/disk.img hash=sha256 log=/evidence/dc3dd.log
dd if=/dev/sdb of=/evidence/disk.img bs=64K conv=noerror,sync status=progress

# 镜像完成后立刻算哈希，写进证据链记录；之后所有分析都在副本上做
sha256sum /evidence/disk.img > /evidence/disk.img.sha256
cp /evidence/disk.img /analysis/disk-work.img

2. 内存镜像（关机前最后的机会）

# ===== Linux 内存：LiME 内核模块 =====
insmod lime.ko "path=/evidence/mem.lime format=lime"
dd if=/proc/kcore of=/evidence/kcore.img bs=1M status=progress  # 应急备选

# Windows：winpmem 导出 .raw，Volatility 3 分析
vol3 -f mem.lime windows.pslist     # 列进程
vol3 -f mem.lime windows.netscan    # 网络连接（找 C2）
vol3 -f mem.lime windows.cmdline    # 进程命令行
vol3 -f mem.lime windows.malfind    # 找注入/隐藏代码
内存里有什么值得你为它拼命？① 不落地的后门——内存马、无文件攻击，磁盘上什么都扫不到；② 正在进行的连接——C2 通信的远端地址和端口；③ 密钥与凭据——SSH 私钥、Kerberos ticket、数据库口令；④ 已删除但仍在运行的进程代码——攻击者删了二进制文件，进程还在跑。
推论：任何情况下都不要先关机再取证。一断电，上面这些全部蒸发。

3. 日志保全（在轮转覆盖之前抢下来）

# ===== 日志保全：抢在轮转覆盖之前 =====
tar czf /evidence/logs-$(date +%F).tar.gz /var/log /var/log/nginx /var/log/apache2 2>/dev/null
rsync -avz --numeric-ids /var/log/ /evidence/var-log-snapshot/   # 保留属主/时间戳

# journald 持久化检查：默认 /run/log/journal 是临时的，重启就没了
ls /var/log/journal/          # 有这个目录才是持久化日志
journalctl --since "2026-10-10" --until "2026-10-16" > /evidence/journal-export.txt

# 集中日志场景：从 SIEM/ES 按时间窗导出，核对采集端与源端日志条数是否一致
sha256sum /evidence/logs-*.tar.gz >> /evidence/hashes.txt
日志保全的两个时间陷阱：① 轮转覆盖——logrotate 默认只留 4~13 份，Nginx 日志按天切割后 7 天前的就没了。发现得越晚，能抢到的日志越少，所以日志留存周期（等保要求 ≥6 个月）既是合规项也是取证生命线。② 时间不同步——业务机、数据库、K8s 节点、负载均衡各有各的时钟，拼时间线前先确认所有机器都接了 NTP/chrony，并记录每台的时钟偏差，否则"谁先谁后"全错。

4. 时间线重建

# ===== plaso/log2timeline 统一时间线 =====
log2timeline.py /evidence/case.plaso /analysis/disk-work.img
psort.py -o l2tcsv /evidence/case.plaso -w /evidence/timeline.csv
# 三个时间列都要看：mtime（内容修改）/ atime（访问）/ ctime（inode 变更）
# ctime 骗不了人 —— 攻击者可以 touch 改 mtime，但改不了 ctime

# 手工拼接最小可用时间线（半夜设备忘带时）
grep "POST /upload" /evidence/var-log-snapshot/nginx/access.log | head -50
grep "Accepted" /evidence/var-log-snapshot/secure | tail -50
last -50 -f /evidence/var-log-snapshot/wtmp
时间线的正确读法：不要只找"攻击者做了什么"，要找第一个异常点。入侵时间线几乎总是这个形状：最早一次异常登录/请求（入口）→ 数小时到数天的静默（踩点试探）→ 工具投放 → 提权 → 横向移动 → 数据外传或加密。把静默期找出来，你就知道了 MTTD 有多少天、监控该补在哪。
模块 4

常见入侵痕迹排查（可抄的命令）

这一模块是全文最该背下来的部分。以下命令在 CentOS/Ubuntu 类系统上直接可用，注意：在已做镜像的前提下，优先在只读挂载的副本或通过 EDR 远程执行。

1. Webshell（最高频的驻留方式）

# ===== Webshell：按时间 + 按特征 + 按发布包比对 =====
find /var/www /usr/share/nginx /data/webroot -name "*.php" -newermt "2026-09-01" -ls
grep -rln --include="*.php" -E "eval\(|assert\(|system\(|passthru\(|shell_exec\(|preg_replace\(.*/e" /var/www
find /data/webroot -name "*.jsp" -mtime -60 | xargs grep -l "Runtime.getRuntime"

# 和发布包对比是最可靠的：拿 CI 产物算 md5 逐文件 diff
md5sum -c release-20261010.md5 2>/dev/null | grep -v OK

# 看 Web 访问日志里的调用痕迹（文件路径 + 请求参数）
grep -E "\.(php|jsp|jspx|asp|aspx)\?" access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -30

# 注意图片马：合法图片尾部追加 PHP 代码，且 .htaccess 把 .jpg 当 php 解析
find /var/www -name "*.jpg" -size +100k | xargs tail -c 100 | grep -l "<?php"
Webshell 排查的三个经验：① 不要只搜 eval——变形马用字符串拼接、base64、回调函数绕开特征码，发布包对比才是金标准；② 关注 Web 目录之外——/tmp、/dev/shm、/var/tmp、上传目录、图片目录都是常见藏身处；③ 删文件只是止血，必须回查入口——漏洞还在，你删一次他传一次。

2. 计划任务与持久化

# ===== crontab 全家桶：系统级、目录级、用户级 =====
cat /etc/crontab; ls -l /etc/cron.d/ /etc/cron.daily/ /etc/cron.hourly/ /etc/cron.weekly/ /etc/cron.monthly/
for u in $(cut -f1 -d: /etc/passwd); do crontab -l -u $u 2>/dev/null | grep -v "^#" | grep . && echo "^^ user: $u"; done
ls -l /var/spool/cron/

# systemd timer（比 cron 更隐蔽，常被忽略）；一次性任务 at
systemctl list-timers --all
at -l 2>/dev/null || atq

# 用户自启动、RC 级持久化、动态链接器劫持（极隐蔽）
ls ~/.config/autostart/; grep -v "^#" /etc/rc.local | grep .
cat /etc/ld.so.preload 2>/dev/null; cat /etc/ld.so.conf.d/*.conf
持久化排查的正确姿势是"全覆盖 + 对比基线"。攻击者留后门的位置远不止 cron：systemd service/timer、rc.local、ld.so.preload、SSH authorized_keys、bashrc 里的一行 alias、内核模块、容器 init 脚本。没有基线库存（golden image）就逐项人工核，核不完就用配置管理工具（Ansible/Puppet）重建。判断某个任务可不可疑的简单标准：它下载东西、它连外网、它 base64 解码一段字符串、它写文件到 /tmp 或 /dev/shm——命中任意一条即高危。

3. SSH 公钥与异常账号

# ===== SSH 公钥、异常账号、登录记录 =====
for d in /root /home/*; do cat $d/.ssh/authorized_keys $d/.ssh/authorized_keys2 2>/dev/null; done
awk -F: '($3==0){print}' /etc/passwd      # UID 0 的 root 分身
awk -F: '($2==""){print}' /etc/shadow     # 空口令账号

last -50; lastb -50; lastlog     # 成功登录 / 失败爆破 / 全账号最近登录
ls -l /etc/passwd /etc/shadow /etc/group /etc/sudoers
grep -v "^#" /etc/sudoers | grep ALL      # 找 NOPASSWD: ALL 后门
w; who; ss -tnp | grep :22          # 当前在线会话与来源 IP
异常账号的三个高信号：① UID 0 的非 root 账号——典型提权痕迹；② 从未登录过的账号突然有登录记录（lastlog 交叉验证）——账号接管或新建账号；③ sudoers 里出现 NOPASSWD: ALL——攻击者给自己留的门。另外，authorized_keys 是最经典的持久化手段，且通过配置管理下发时几乎不留文件时间戳异常，必须靠多机对比和基线审计发现。

4. 挖矿与恶意进程

# ===== 挖矿进程与外联连接 =====
ps aux --sort=-%cpu | head -20
ls -l /proc/<PID>/exe /proc/<PID>/cwd    # 真实可执行文件（删除的显示 deleted）
ls -l /proc/*/exe 2>/dev/null | grep deleted   # 已删除仍在运行的二进制

# 外联连接聚合（矿池端口 3333/4444/5555/14444，或 443 伪装）
ss -tnp | awk '{print $4,$5,$6}' | sort | uniq -c | sort -rn | head -30
ls -la /dev/shm /tmp /var/tmp /run    # /dev/shm 是重灾区：tmpfs、重启清空
grep -rE "(curl|wget|python.*http)" /etc/cron* /var/spool/cron/ 2>/dev/null

# 内核模块：两数差得多 → 有隐藏模块（rootkit LKM）
ls /sys/module | wc -l; lsmod | wc -l
挖矿进程的三个反排查套路：① 父子互守——A 监控 B、B 拉起 A，杀一个另一个立刻重启，必须同时冻结（SIGSTOP）再连根拔；② 二进制删除——进程起来后自删，只留下 /proc 里的 deleted 记录，所以内存镜像和 /proc 采集要在杀进程之前；③ 改名伪装——进程名改成 kworker、systemd-journal 之类，只信 /proc/PID/exe 指向的真实路径，别信 ps 里的名字。

5. 其他必查项

cat ~/.bash_history /root/.bash_history攻击者手工操作记录（注意 unset HISTFILE 会关掉记录，且 history 可被伪造）
journalctl -u sshd --since "3 days ago" | grep -E "Accepted|Failed"SSH 登录成功/失败，定位爆破与首次登录
find / -xdev -newermt "2026-10-10" -type f -not -path "/proc/*" -not -path "/sys/*" | head -100按时间窗找新增文件（全盘慢，先缩小范围）
rpm -Va ; debsums -c校验系统二进制是否被篡改（RPM/Deb 系）
模块 5

遏制与根除：止血优先

遏制的目标是把损失曲线压平，不是"一次性解决所有问题"。根除才是一劳永逸，但根除需要时间和信息。顺序错了就是事故扩大化。

遏制手段分级（按强度从轻到重）

层级手段适用场景与代价
账号层禁用可疑账号、强制重置密码、吊销 token/会话、吊销 SSH key代价最小，优先做。注意：改密码前先确认没有把攻击者锁在门外导致其警觉删证据
网络层安全组/iptables 封禁 C2 IP 与网段、关闭高危端口、DNS sinkhole 恶意域名见效快、可逆。注意别封到自己的监控和备份通道
应用层WAF 虚拟补丁（先顶住漏洞）、下线受影响功能/接口、切只读模式业务影响可控，适合"有漏洞但没完全失控"的阶段
主机层EDR 远程隔离主机（保留出网受限的管理通道）、剔除出负载均衡池标准操作。隔离≠关机，关机丢内存证据
极端层拔网线、断交换机端口、整段网络隔离仅用于勒索加密正在扩散、数据正在外传的"进行时"灾难
遏制时最容易被忽视的一条：你的遏制动作本身就在告诉攻击者"你被发现了"。有经验的操作者会在察觉到封锁的瞬间启动"清障跑路"：删日志、清 webshell、加密扩散。所以专业团队的顺序是：能静默完成的前置动作（封 IP 留后端、关端口）先做；需要"宣布式"动作（全量改密码、公告）放在取证完成之后。当然，如果数据正在外传，别犹豫，先断。

根除清单

  • 入口修复：定位到具体漏洞（哪个组件、哪个接口、哪条链）并打补丁/改配置，复测通过才算修完——不是"发了补丁"就算。
  • 驻留清理：Webshell、计划任务、SSH key、系统服务、ld.so.preload、启动项——按模块 4 的清单逐项过。
  • 凭据轮换：所有可能暴露的密码、API key、数据库口令、JWT 签名密钥、对象存储 AK/SK。攻击者拿了数据库口令，你删了 Webshell 他照样能进来。
  • 横向移动清理：按模块 6 的方法检查攻击者是否从这台机器跳到了其他机器；同网段、同密钥、同信任关系的资产全部排查。
  • 信任关系重置：被入侵主机如果持有其他机器的免密登录信任（SSH 信任、K8s ServiceAccount token、内网 API token），全部撤销重发。
"止血优先"的正确理解：止血不是"把病治好"，是"别再流血"。业务凌晨三点还在跑，你能用 WAF 虚拟补丁顶住漏洞、隔离受控机器、保持其他服务正常，这就是成功。根治（升级组件、重构代码）可以放到白天低峰期做。唯一例外：确认数据正在被批量外传或加密时，一切让位于阻断。
模块 6

溯源思路：IP、样本、漏洞点

溯源回答三个问题：从哪进来的？干了什么？还会来吗？不一定能抓到人（涉及跨境、代理、云主机），但一定能还原攻击链——而还原攻击链本身就是加固的依据。

1. 入口定位（从日志倒推第一个异常点）

awk '$6 ~ /POST|PUT/ {print $1, $4, $7, $9, $10}' access.log | sort | uniq -c | sort -rn | head -30
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -20
grep "1.2.3.4" access.log > /evidence/attacker-session.log
grep -E "(union.*select|/etc/passwd|\.\./\.\./|%00|base64_decode)" /evidence/attacker-session.log

# 与组件版本比对：命中已知漏洞路径直接锁定（Log4j、Struts2、Shiro、Fastjson 各有特征）
grep -E "(\$\{jndi:|\$\{lower:j|%24%7Bjndi)" access.log

2. 漏洞点确认

  • 版本比对法：把受影响系统的组件版本（框架、中间件、依赖 jar/npm 包）与漏洞通告比对，mvn dependency:tree、npm ls、pip list 是日常就该会的东西。
  • 复现法：在隔离环境用公开 PoC 复现，确认可利用路径与日志中的请求一一对应。只在隔离环境做，别在生产试。
  • 排除法：把所有入口（对外端口、上传点、登录口、消息队列）列成表，逐一核对日志中是否有异常，没有异常的打问号继续观察——入口不一定在 Web 层，也可能是 VPN 弱口令、Git 仓库泄露、第三方供应链。

模块 7

恢复验证与复盘改进

恢复不是"服务起来了"，是证明威胁已经不存在，并且下次能更早发现。跳过验证的恢复，等于把同样的事故预约到下周。

恢复前的验证清单

验证项方法通过标准
入口漏洞用定位到的漏洞路径与 PoC 在隔离环境复测原利用路径返回预期错误/拦截，WAF 有对应规则
文件完整性与干净镜像/发布包逐文件比对（md5）；rpm -Va / debsums -c 校验系统文件无差异文件，或所有差异都有合理解释（业务配置）
持久化复查重跑模块 4 全清单：cron/systemd/authorized_keys/ld.so.preload/自启动全部清空或与基线一致
凭据轮换密码、密钥、token、AK/SK、JWT 签名密钥逐一确认已换清单签字，无遗漏项
网络行为恢复后 7~14 天加强监控，关注外联、异常登录、异常流量无新增可疑 IOC 命中
备份纯净性若从备份还原，确认备份制作时间早于入侵时间，且备份未被污染还原后全清单复查一遍
恢复顺序也有讲究：先恢复非核心、外部攻击面小的系统，观察 24 小时；再恢复核心系统。全程保持 WAF 规则和监控处于加强态，别一上线就撤。绝对不要用"直接重装省事"来跳过验证——重装可以，但前提是取证已完成、入侵路径已完全清楚（否则你只是把不知道有没有后门的系统，换成了不知道有没有后门的系统）。

复盘报告结构（可直接当模板）

  1. 事件概述：一句话说清发生了什么、影响哪些业务、持续多久。
  2. 完整时间线：从第一个异常点到处置完成，每个动作标注 UTC+8 时间和责任人。
  3. 影响评估：受影响系统、数据范围（类型/条数）、业务中断时长、是否需要通知个人。
  4. 根因分析：技术根因（漏洞/配置/流程）+ 管理根因（为什么没及时发现、为什么没早修复）。用 5 Whys 追到可落地的层级。
  5. 处置回顾：哪些动作做对了，哪些是运气，哪些本可以更快（MTTD/MTTR 数据说话）。
  6. 改进项：每条改进项必须有责任人 + 期限 + 验收标准，写进 backlog 而不是写完就归档。
改进项的四个常见方向（按性价比排序）：① 检测规则——把这次的 IOC 和攻击模式固化成 SIEM/EDR 规则（一次投入，长期生效）；② 暴露面收敛——不必要的端口关掉、不必要的接口下线、管理后台加白名单；③ 补丁与资产管理——资产不清是所有应急响应困难的源头，先有台账才能谈漏洞管理；④ 演练——每半年做一次桌面推演 + 一次实战演练（比如故意植入一枚"无害 Webshell"让团队找），比读十遍预案有用。
模块 8

十个常见坑

1
入侵后第一反应是直接重装系统
镜像没做、日志没拷就重装，内存证据和磁盘证据一起蒸发，从此无法回答"数据有没有被偷、从哪进来的、影响了多久"，监管报告只能靠猜。重装是根除阶段的选项，不是检测阶段的选项。
2
只处理当前这台机器，不排查同源资产
同一漏洞、同一镜像、同一密钥的机器有几十台，攻击者早就扫过一圈。至少要把同镜像、同网段、同密钥、同应用的资产全部过一遍模块 4 的清单。
3
只堵入口，不查横向移动
删了 Webshell 就以为完事，殊不知攻击者已经用拿到的凭据跳到了数据库和内网其他机器。一周后第二个业务又被加密，才发现"原来不止一台"。
4
在被入侵主机上直接跑分析工具
现场装 clamav、解压样本、跑扫描——写盘操作覆盖了证据、污染了时间线，还可能触发攻击者的反分析。正确做法：先镜像，分析在副本或只读挂载上做。
5
日志被轮转覆盖之后才想起来取证
Nginx 日志默认保留 7 天、journald 默认存在 /run 下重启就没。等业务方"上周就觉得不对"反馈上来，入口日志已经没了。日志留存 6 个月不是合规负担，是取证生命线。
6
恢复上线前不验证后门是否清除干净
删了一个显眼的 webshell 就恢复服务，结果 ld.so.preload 里还挂着一个、cron 里还藏着一个。恢复前必须完整重跑一遍持久化清单 + 文件完整性校验。
7
根除后不轮换所有凭据
攻击者早就 export 了数据库口令、对象存储 AK、JWT 密钥。你修了漏洞，他拿着旧钥匙照样天天来。所有可能暴露过的凭据，一个不留全部换掉。
8
各机器时间不同步，时间线拼不出来
业务机 UTC、数据库 CST、K8s 节点差 8 小时，时间线前后矛盾，连"哪个是第一个异常点"都定不了。全员 NTP/chrony 同步是应急准备的基建项，不是可选项。
9
遏制动作打草惊蛇，攻击者直接清障跑路
一上来全量改密码、全网公告，攻击者察觉后瞬间删日志、毁痕迹、加密扩散。静默动作先做（封 IP、关端口、隔离），宣布式动作放在取证完成后。
10
没有复盘，同类事件原样再来一次
改进项写在 PPT 里没有责任人，半年后同一个漏洞、同一台机器、同一种手法再次得手。复盘的价值不在报告，在改进项进 backlog 并被验收。
自测

六道题

1. 半夜监控告警：一台 Web 服务器疑似被植入 Webshell。此时第一动作应该是什么？
正确答案：先保全、再遏制。重启会丢失内存证据（内存马、连接、密钥），重装会丢失全部磁盘证据，两者都会让"数据是否泄露、从哪进来"变成永久悬案。遏制（封 IP、隔离、删后门）要做，但必须做在取证完成之后——除非数据正在外传。
2. 内存取证的核心价值是什么？
正确答案：不落地的威胁只在内存里。内存马、无文件攻击把代码全部藏在进程内存中，磁盘扫描一无所获；正在进行的 C2 连接、SSH 私钥、Kerberos 票据也一样。这些证据一关机就永久消失，所以"先镜像内存，再考虑其他"是铁律。
3. 排查 Web 服务器上的 Webshell，最可靠的方法是？
正确答案：与发布包比对。变形马用字符串拼接、base64、回调函数可以绕开任何关键字黑名单，但绕不过"这个文件不在我的发布产物里"。关键字 grep 只能作为辅助初筛，且必须结合文件修改时间交叉验证。
4. 发现挖矿进程后，直接 kill 掉就可以了，这个说法？
正确答案：先取证、连根拔。挖矿程序普遍有守护进程互守（杀一个另一个秒拉），所以正确顺序是：先 SIGSTOP 冻结并采集 /proc 证据与内存，再清除 cron/systemd 等所有持久化入口，最后才杀进程。只杀进程不清持久化，等于给它浇水。
5. 关于"止血优先"，下面哪种理解是对的？
正确答案：分级匹配。过度遏制（盲目断网、关机、全站下线）造成的业务损失可能比入侵本身更大。止血的标准动作是：封禁 C2、隔离受控机、WAF 顶住漏洞、下线受影响功能；根治（升级、重构）放到低峰期。唯一例外是勒索加密/数据外传正在进行——那时一切让位于阻断。
6. 根除阶段完成后，恢复服务前必须做的是？
正确答案：完整验证后才恢复。验证包括：原漏洞路径复测通过、文件与基线/发布包一致、cron/systemd/authorized_keys/ld.so.preload 全部复查、所有凭据已轮换、备份本身未被污染。恢复后还要保持 7~14 天加强监控。跳过验证的恢复，等于把同一次事故预约到下周。
