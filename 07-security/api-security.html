API 是现在最大的攻击面：每个接口都是一次"信任的传递"。这篇以 OWASP API Security Top 10 (2023) 为骨架，讲透 BOLA 越权、批量赋值、GraphQL 四件套、gRPC 安全面，以及网关/JWT/限流的落地配置。

开始前

一次 API 请求，安全边界在哪

# 一个最普通的请求，背后有四层信任传递
GET /api/v1/orders/1001 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

# 请求经过的每一环都可能被绕过：
# 客户端 → CDN/WAF → 网关(认证/限流) → 业务服务(授权/校验) → DB
# 任何一环"以为别人会查"，最终就是没人查
层该管的事典型失守
网关认证 token 合法性、API key、限流、WAF、请求体大小只验签不验权，越权请求畅通无阻
业务服务对象级授权、字段级授权、输入校验、业务流管控把鉴权全推给网关，BOLA 遍地
数据层查询天然带租户/属主条件SQL 不带 owner 条件，改 ID 就脱裤
客户端不保存任何秘密（菜单隐藏不是权限控制）把"按钮置灰"当安全边界
API 安全的铁律：授权判断必须发生在最靠近数据的那一层。网关能回答"你是谁、调得多不多"，回答不了"这个订单是不是你的"。凡是"网关验过 token 就放行"的设计，BOLA 一定存在。
模块 1

API 安全全景：OWASP API Top 10 (2023)

OWASP API Security Top 10 是 API 安全审计的事实标准。2023 版把"大量赋值"和"过度数据暴露"合并成了 BOPLA（对象属性级授权失效），并新增了"不受限的业务流访问"。

编号风险防御要点
API1BOLA 对象级授权失效每个对象查询强制带属主/租户条件；用 UUID 替代自增 ID 只是缓解不是修复
API2认证失效不暴露弱 token；登录/刷新限流；token 短过期 + 撤销机制
API3BOPLA 属性级授权失效（旧"批量赋值+过度暴露"）输入用 DTO 白名单绑定；输出只暴露必要字段
API4资源消耗不受限分页上限、深度/复杂度限制、频率限制、响应体上限
API5BFLA 功能级授权失效管理接口独立路由 + 角色校验；默认拒绝，显式授权
API6业务流不受限对"买票/抢券/转账"类流程做行为级风控，不只是频率限制
API7SSRF见 SSRF 篇：白名单、解析后校验、禁 gopher
API8安全配置错误CORS 收敛、错误页不泄露堆栈、调试接口生产关闭
API9库存管理不当API 资产台账：旧版本、影子 API、测试端点定期下线
API10不安全地消费第三方 API对接方响应按不可信输入处理：校验 schema、限响应大小、设超时

五条横切防线

认证 AuthN
你是谁。JWT/OAuth2/API Key/mTLS。重点在 token 生命周期管理，不只是"能不能登进去"
授权 AuthZ
你能动哪些对象和字段。对象级（这条订单是你的吗）+ 功能级（你能调管理接口吗）+ 属性级（你能改 role 吗）
输入校验
白名单 schema 校验，拒绝即报错。重点防批量赋值、类型混淆、超长/超深结构
限流
按用户/IP/接口多维配额，防爆破、防爬、防资源耗尽。429 + Retry-After 是标准姿势
审计
谁、何时、对哪个对象、做了什么、结果如何。事后溯源和风控的地基，出事时唯一的线索
模块 2

REST 常见问题：BOLA 与它的三个亲戚

BOLA（API1）：改个 ID 就看别人的数据

# 漏洞请求：登录用户 A 拿到自己的订单
curl -H "Authorization: Bearer <tokenA>" https://api.example.com/api/v1/orders/1001

# 攻击请求：把 1001 改成 1002，服务端没有任何属主校验
curl -H "Authorization: Bearer <tokenA>" https://api.example.com/api/v1/orders/1002
# → 返回了用户 B 的订单。遍历 1001~99999 就是一次全量脱裤
// ✗ 漏洞代码：只按 ID 查，不问归属
@GetMapping("/api/v1/orders/{id}")
public Order get(@PathVariable Long id) {
    return orderRepo.findById(id).orElseThrow();   // 谁都能查任何单
}

// ✓ 修复：查询强制带属主条件（当前用户从 token 取，不从参数取）
@GetMapping("/api/v1/orders/{id}")
public Order get(@PathVariable Long id) {
    Long uid = CurrentUser.id();                    // 服务端从 token 解析
    return orderRepo.findByIdAndUserId(id, uid)
            .orElseThrow(NotFoundException::new);  // 查不到就 404，不提示"存在但不属于你"
}
UUID 不是 BOLA 的解药：把 /orders/1002 换成 /orders/3f8a...uuid，只是让枚举变难，授权缺失本身没变 —— 邮件里的订单链接、爬虫、日志截图照样泄露 UUID。唯一正确的修复是对象级授权：每个数据访问都验证"当前主体对该对象有权限"。

批量赋值（API3）：POST 里夹带私货

# 攻击请求：注册接口里夹带 role 和 balance
curl -X POST https://api.example.com/api/v1/users \
  -H "Content-Type: application/json" \
  -d '{"name":"a","email":"a@x.com","role":"admin","balance":999999,"isVerified":true}'

# ✗ 直接绑 ORM 实体，Spring 的 BeanUtils/Jackson 会把每个字段都塞进去
// @PostMapping public User create(@RequestBody User user)
// User 实体上有 role/balance 字段 → 一并落库

# ✓ 用专用 DTO，只暴露可填字段
public record CreateUserRequest(
        @NotBlank String name,
        @Email String email,
        @Size(min = 8) String password) { }   // 没有 role，就没有批量赋值的入口

过度数据暴露（API3 的另一半）：响应夹带私货

# 响应里出现不该出现的字段
{"id":1,"name":"张三","password_hash":"$2a$10$...","phone":"138****","idCard":"3301..."}

# ✓ 输出也用 DTO，显式列出字段（@JsonIgnore 只对实体生效，DTO 更稳）
public record UserVO(Long id, String name, String avatar) { }

BFLA（API5）：功能级越权

请求问题
GET /api/v1/admin/users普通 token 调管理员端点 —— 管理接口要独立前缀 + 角色注解双重保护
PUT /api/v1/users/5/role水平越权改他人角色 —— 属主校验 + 角色变更走独立审批流
POST /api/v1/orders/1001/refund状态机漏洞：跳过前置状态直接退款 —— 服务端必须校验状态流转合法性

缺乏限流（API4）：认证之外的裸奔

  • 登录接口不限速 → 撞库（每秒几千次尝试，密码字典跑一遍）
  • 短信/邮箱接口不限速 → 轰炸机 + 短信账单爆炸
  • 列表接口无分页上限 → ?pageSize=1000000 一次拖全表
  • GraphQL/gRPC 的查询成本不限 → 一个请求打满 CPU（见模块 3、4）
模块 3

GraphQL 特有风险：四件套

1. 内省（introspection）泄露

# 生产环境如果开着内省，一个请求拿到全部 schema
curl -X POST https://api.example.com/graphql \
  -H "Content-Type: application/json" \
  -d '{"query":"{ __schema { types { name fields { name } } } }"}'
# 返回所有类型、字段、参数 —— 等于把接口文档和隐藏字段拱手送人
# 修复：生产环境禁用内省（Apollo Server: introspection: false）

2. 深度嵌套查询 DoS

# 恶意查询：friends 套 friends 套 friends，深度每 +1，数据量指数膨胀
query {
  user(id: 1) {
    friends {
      friends {
        friends {
          friends { id name email }
        }
      }
    }
  }
}
# 深度 10 就能把数据库连接池打干。修复：depth-limit（建议 ≤ 10）

3. 批量查询（aliases）攻击

# 一个请求体里塞 1000 个别名查询，绕开"每个请求限一次"的粗粒度限制
query {
  a: user(id: 1) { email }
  b: user(id: 2) { email }
  c: user(id: 3) { email }
  ...  # 直到 z 之后接着 aa, ab...
}
# 修复：complexity/cost analysis —— 给每个字段定价，整查询预算封顶
# graphql-cost-analysis: maximumCost 1000, defaultCost 1, multipliers

4. 字段级授权

GraphQL 的授权粒度是字段，REST 那套"端点级"中间件不够用。必须在解析器（resolver）里逐字段校验：

// ✗ 只要登录就能查任何用户的手机号
Query: { user: (_, {id}) => db.user.find(id) }

// ✓ 解析器级授权
Query: {
  user: (_, {id}, ctx) => {
    if (id !== ctx.userId && !ctx.hasScope("user:read:any")) {
      throw new ForbiddenError("not your object");   // 对象级
    }
    return db.user.find(id);
  }
}
User: {
  phone: (parent, _, ctx) => {
    if (!ctx.hasScope("user:read:phone")) return null;   // 属性级：没权限返回 null 或不返回
    return parent.phone;
  }
}

GraphQL 加固清单

措施配置示例
禁内省introspection: false（仅生产）
深度限制graphql-depth-limit(10)
复杂度/成本分析graphql-cost-analysis { maximumCost: 1000 }
持久化查询persisted queries 白名单，只允许注册过的查询
分页上限first/last 参数硬上限 100，服务端强制
N+1 防护DataLoader 批量化，防被利用放大查询量
错误脱敏生产只返回 "Internal server error"，不带堆栈和 SQL
模块 4

gRPC 安全面

gRPC 的安全问题一半来自"HTTP/2 + 二进制协议"带来的新攻击面，一半来自"内部服务没人管"的惯性。

1. 传输层：TLS 是底线，mTLS 是内网标准

# 服务端强制 TLS
server = grpc.server(
    ssl_server_credentials=[(
        open("server.crt","rb").read(),
        open("server.key","rb").read(),
        open("ca.crt","rb").read(),      // 第三份是客户端 CA，给了就是 mTLS
    )],
)

# 客户端带证书（内网服务间调用默认 mTLS）
creds = grpc.ssl_channel_credentials(
    root_certificates=open("ca.crt","rb").read(),
    private_key=open("client.key","rb").read(),
    certificate_chain=open("client.crt","rb").read(),
)
channel = grpc.secure_channel("grpc.example.com:443", creds)

2. 拦截器：认证/日志/限流的统一挂点

# Python 示例：把认证做成拦截器，每个方法自动过
class AuthInterceptor(grpc.ServerInterceptor):
    def intercept_service(self, continuation, handler_call_details):
        md = dict(handler_call_details.invocation_metadata)
        token = md.get("authorization", "").removeprefix("Bearer ").strip()
        ctx = verify_jwt(token)                     # 验签 + 过期 + scope
        if ctx is None:
            return grpc.unary_unary_rpc_method_handler(
                lambda req, ctx: ctx.abort(grpc.StatusCode.UNAUTHENTICATED, "bad token"))
        return continuation(handler_call_details)

server = grpc.server(
    thread_pool=futures.ThreadPoolExecutor(32),
    interceptors=(AuthInterceptor(), LoggingInterceptor(),))

3. 元数据（metadata）的坑

  • gRPC 的 metadata 就是 HTTP/2 header，token、trace-id 都走这里，必须走 TLS，明文 gRPC（h2c）等于把凭证写在网上传
  • metadata 不是白名单：客户端可以塞任意自定义头，不要信任客户端传入的 user-id/x-user-role 这类头，身份只从服务端验过的 token 取
  • 单个 header 有默认上限（通常 8KB），超限会被 RST_STREAM，可被用来做 DoS，网关要设请求头大小上限

4. Server Reflection：生产必须关

# 反射服务让 grpcurl 之类工具能列出全部服务和方法 —— 调试神器，生产情报泄露
# ✗ 生产开启
reflection.enable(server)

# ✓ 只在内部调试端口开启（走管理端口 + ACL）
mgmt = grpc.server(...)
reflection.enable(mgmt)          # 只对 debug server 开，不对业务端口开

5. 三种 API 形态的安全差异

维度RESTGraphQLgRPC
攻击入口每个 URL+方法通常单一端点 /graphql每个方法，二进制载荷
限流粒度按 URL 限流难：一个查询含 N 个子请求，要做复杂度定价按方法限流；HTTP/2 多路复用下按连接限不准
WAF 可见性JSON/明文，WAF 友好单端点 + 嵌套 JSON，传统 WAF 容易漏二进制，WAF 基本失效，靠 TLS+mTLS+服务端校验
授权粒度端点级 + 对象级字段级（resolver 里做）方法级 + 消息级
信息泄露错误页、版本头内省、详尽错误Server Reflection、protob 文件
Protobuf 二进制 ≠ 安全。很多人觉得"二进制看不懂所以安全"——grpcurl、protoc --decode 拿到 .proto 就能构造任意请求。二进制只是增加了爬虫门槛，该有的认证授权一个都不能少。
模块 5

API 网关安全控制

网关（Kong / APISIX / Spring Cloud Gateway / AWS API Gateway / Envoy）是横切防线的最佳挂点。但先记住它能做什么、不能做什么。

能力典型实现说明
JWT 验签Kong jwt plugin验签 + 过期 + iss/aud；网关拿到 claims 后下传给业务
API Keykey-auth plugin机器对机器场景；key 只做识别，授权仍靠业务
限流/配额rate-limiting / rate-limiting-advanced按 consumer/IP/路由多维；429 + Retry-After
请求体限制request-size-limiting挡超大 body，默认 128KB 级
IP 黑白名单ip-restriction管理接口只放办公网/VPN 出口
CORScors plugin显式源白名单，见下方坑
WAFModSecurity / OpenResty + 规则集对 SQLi/XSS 模式有效，对 BOLA 完全无效
审计日志http-log / kafka-log记录 who/where/what/status，送日志平台
网关的三个"不能"：① 不能替你判断 BOLA（它不知道订单归属）；② 不能替你校验业务字段（它不懂你的领域模型）；③ 不能防逻辑漏洞（重复领取、负余额、状态机跳跃）。这些必须在业务层实现。把网关当"安全已就绪"的团队，通常三项全裸。

CORS 的经典错配

# ✗ 致命组合：反射 Origin + 允许携带凭证
Access-Control-Allow-Origin: https://evil.com      # 反射了请求头里的 Origin
Access-Control-Allow-Credentials: true

# 浏览器视角：evil.com 的页面可以带着 cookie 读你的 API 响应
# 注意：Allow-Origin: * 与 Allow-Credentials: true 组合浏览器直接拒
# 真正危险的是"动态反射 Origin"这个写法，要显式白名单

# ✓ 显式白名单 + 必要才开 credentials
ALLOWED_ORIGINS = {"https://app.example.com", "https://admin.example.com"}
origin = request.headers.get("Origin")
if origin in ALLOWED_ORIGINS:
    resp.headers["Access-Control-Allow-Origin"] = origin
    resp.headers["Access-Control-Allow-Credentials"] = "true"
    resp.headers["Vary"] = "Origin"
模块 6

JWT 与 OAuth 的使用要点

JWT 的结构与验什么

# 三段：header.payload.signature（点号拼接）
header:    {"alg":"HS256","typ":"JWT","kid":"key-2024"}
payload:   {"sub":"1001","role":"user","iss":"https://idp.example.com",
            "aud":"api.example.com","exp":1719000000,"iat":1718999000,"jti":"abc123"}

# 服务端必须校验的七项（少一项就是漏洞）
[ ] 签名有效（用对算法和密钥）
[ ] alg 不是 none，且与期望一致（防 alg 混淆）
[ ] exp 未过期（留 60s 时钟偏移）
[ ] iss 与 aud 与你的服务匹配
[ ] nbf/iat 合理
[ ] sub 对应真实用户且状态正常（未被封禁）
[ ] jti 在需要时可用于撤销

JWT 的经典攻击面

攻击原理防御
alg: none把 header 改成 {"alg":"none"}，签名留空，服务端不校验直接信服务端只接受期望算法的白名单（HS256/RS256 显式指定）
算法混淆RS256 的服务端被喂 HS256 的 token，用公钥当 HMAC 密钥签名通过算法在服务端固定，不接受 header 里的 alg 决定
弱密钥爆破HS256 密钥是 "secret" 这类弱串，离线秒破密钥 ≥ 256bit 随机，定期轮换（靠 kid 支持多密钥）
kid 注入header 里 kid 被拼进 SQL/文件路径取密钥kid 只做查表键，不进 SQL/文件系统
jku/x5u 伪造诱导服务端去攻击者的 JWKS 地址取"公钥"禁用 jku/x5u，JWKS 地址服务端配置
不验 aud/exp拿别的系统的 token 调你的 API，或拿过期 token 一直用见上面七项校验，用成熟库（java-jwt/pyjose/nimbus）

存储与撤销

  • access token 短寿命（5~15 分钟）+ refresh token 轮换（一次一换，旧作废），别让 JWT 活几天
  • 存储位置：浏览器端优先 httpOnly + Secure + SameSite=Lax 的 cookie；localStorage 会被 XSS 一锅端，用了就必须配严格的 CSP
  • 撤销：JWT 天生难撤销。补救是 access token 短过期 + refresh 服务端可撤 + 必要时 jti 黑名单（Redis，TTL=token 剩余寿命）

OAuth 2.0 在 API 场景的要点

机制要点
授权码 + PKCE公开客户端（SPA/移动端）必须用 PKCE（code_verifier/code_challenge），防授权码拦截
state 参数每次授权生成随机 state 并校验，防 CSRF 绑定攻击者账号
redirect_uri精确全串匹配，不接受前缀/通配，防授权码被重定向到攻击者地址
scope 最小化按功能申请最小 scope；scope 里带资源标识（如 orders:read）
token 绑定mTLS-bound token（RFC 8705）或 DPoP，防 token 被盗用
设备流IoT/TV 场景用 device authorization grant，同样带 user_code 防钓鱼
一句话选型：内部微服务之间用 mTLS + 服务账号；面向浏览器/移动端用 OAuth 2.1 授权码 + PKCE + 短寿命 JWT；机器对机器用 client_credentials + scope 最小化。别自创 token 格式，别把 session id 当 bearer token 到处传。
模块 7

速率限制与防爬

三种限流算法

算法原理优缺点
固定窗口每分钟计数，整点清零简单，但窗口边界可突刺 2 倍（临界点前后各打满）
滑动窗口记录每个请求时间戳，统计最近 N 秒无突刺，内存随时间戳数增长（可用 Redis ZSet）
令牌桶恒定速率补令牌，请求取令牌，桶有容量最平滑，允许合理突发，业界标准（Guava RateLimiter、nginx limit_req 同思路）
漏桶请求进桶，恒定速率流出绝对平滑但不允许突发，适合对下游保护严格的场景
# Redis + Lua 令牌桶（原子、单次往返）
-- KEYS[1]=桶 key, ARGV[1]=容量, ARGV[2]=每秒补充速率, ARGV[3]=当前时间戳
local tokens = redis.call('GET', KEYS[1])
if tokens then
  tokens = tonumber(tokens)
else
  tokens = tonumber(ARGV[1])          -- 首次初始化满桶
end
local now = tonumber(ARGV[3])
local last = tonumber(redis.call('HGET', KEYS[1]..':ts', 't') or now)
tokens = math.min(tonumber(ARGV[1]), tokens + (now - last) * tonumber(ARGV[2]))
if tokens >= 1 then
  redis.call('SET', KEYS[1], tokens - 1)
  redis.call('HSET', KEYS[1]..':ts', 't', now)
  return 1                            -- 放行
end
return 0                              -- 拒绝，业务侧回 429

限流的四个维度

  • 按用户（登录态）：登录用户 100 次/分钟，最贴合业务
  • 按 IP：匿名流量 20 次/分钟，注意 NAT 后共享 IP 会误伤，要留余量
  • 按 API Key：对开放平台的合作方，超配额返回 429 + X-RateLimit-Remaining
  • 按接口：敏感接口（登录、短信、支付）单独低配额，与普通查询分开

防爬：从"限流"到"识别"

手段说明
响应头规范X-RateLimit-Limit / Remaining / Reset + 429 + Retry-After
行为分析请求间隔过于规律（机器人特征）、只走列表不详情、 UA 与 TLS 指纹不匹配
数据蜜标在响应里埋不可见标记（隐藏字段/1px 元素），出现在别人站点即证明被爬
签名参数关键查询要求带时间戳 + 签名（HMAC），签名算法放客户端 SDK，增加重放成本
验证码阶梯超阈值先出验证码再放行，别一上来全拦（误伤真实用户）
防爬的边界：客户端能看到的都能被模拟。任何"前端混淆/加密参数/签名"都只是提高成本，不是安全边界。真正的防线在服务端的业务风控：异常模式识别（新号高频、只拉不买）、数据分级（核心数据走授权接口）、以及法务兜底。
模块 8

十个真实坑

1
前端做权限控制，API 裸奔
按钮置灰、菜单隐藏只是 UX。攻击者直接调 API。每个接口都要服务端鉴权，管理接口独立前缀 + 角色校验双保险。
2
用自增 ID 且不查属主
BOLA：/orders/1002 遍历即脱裤。查询必须带 owner 条件；UUID 只是增加枚举难度，不是修复。
3
请求体直接绑 ORM 实体
批量赋值：POST /users 里夹带 {"role":"admin"}。用输入 DTO 白名单，实体永远不直接当入参。
4
响应返回整个实体
password_hash、内部备注、别人手机号全出去。输出也用 VO/DTO，显式列字段；序列化层加 @JsonIgnore 兜底。
5
JWT 不验 alg / 不验 aud / 不验 exp
alg:none、算法混淆、拿别的系统 token 来打。七项校验（签/alg/exp/iss/aud/nbf/用户状态）一项不能少，用成熟库。
6
JWT 活 30 天且无法撤销
token 泄露后攻击者用一个月。access 5~15 分钟 + refresh 轮换 + 服务端可撤 + 必要时 jti 黑名单。
7
登录/短信接口无限流
撞库、短信轰炸、账单爆炸。敏感接口单独低配额 + 验证码阶梯 + 按 IP/用户/设备多维限制。
8
GraphQL 生产开内省、无深度限制
一个 __schema 查询拿走全部 schema；嵌套查询打满数据库。禁内省 + depth-limit + 复杂度定价 + 持久化查询。
9
gRPC 生产开 Server Reflection、内网无 mTLS
grpcurl 直接列出全部服务方法；明文 h2c 把 token 送上路。反射只开在管理端口，服务间默认 mTLS。
10
CORS 反射 Origin + Allow-Credentials
evil.com 的页面能带着 cookie 读你的响应。Origin 显式白名单 + 按需才开 credentials + Vary: Origin。
自测

六道题

1. BOLA（对象级授权失效）的典型表现是？
正确答案：改 ID 访问他人对象。BOLA 连续多年排在 OWASP API Top 10 第一位，因为它无需任何"技术漏洞"，只要授权判断缺失。修复：查询强制带属主条件， UUID 只是缓解。
2. GraphQL 内省（introspection）在生产环境的正确做法是？
正确答案：关闭。一个 {__schema{types{name}}} 查询就能拿到完整 schema，隐藏字段、内部类型全泄露。调试环境单独开，生产关闭。
3. 防御批量赋值（mass assignment）最有效的手段是？
正确答案：输入 DTO 白名单。批量赋值的根源是"用户 JSON 字段 → ORM 实体字段"的自动映射没有边界。HTTPS 防传输窃听，XSS 过滤防脚本，都与这个问题无关。
4. 攻击者把 JWT header 改成 {"alg":"none"} 并清空签名，能得逞的原因是？
正确答案：服务端用 header 的 alg 决定验签方式。正确做法：算法在服务端固定（白名单），库不接受 alg:none。同类问题还有 RS256 服务端被喂 HS256 的算法混淆攻击。
5. 三种限流算法中，最平滑且允许合理突发的是？
正确答案：令牌桶。固定窗口在边界时刻可突刺 2 倍；漏桶绝对平滑但不允许突发；令牌桶恒定补充 + 桶容量缓冲，是 API 限流的事实标准。
6. gRPC 生产环境应该关闭的是？
正确答案：Server Reflection。反射是调试神器，但生产开启等于公开全部 API 清单。只在管理端口开；TLS/mTLS 和拦截器恰恰是必须开的。

JWT 验签 checklist

# 每一条都在线上见过缺失导致的事故
[ ] 算法服务端固定白名单，拒绝 alg:none，拒绝 RS256→HS256 混淆
[ ] 密钥 ≥ 256bit 随机，支持 kid 多密钥轮换
[ ] exp 必验（60s 时钟偏移）；nbf/iat 必验
[ ] iss / aud 与本服务匹配
[ ] sub 对应用户存在且未被封禁（高危操作实时查库）
[ ] access token ≤ 15 分钟，refresh 轮换 + 服务端可撤
[ ] 传输只走 TLS；浏览器存储优先 httpOnly cookie
[ ] 不用 jwt.io 默认示例密钥；JWKS 地址服务端配置，禁 jku/x5u
