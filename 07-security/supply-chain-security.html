二十分钟学透 供应链安全

模块 1

供应链攻击的四种形态

供应链攻击不攻击你的服务器，攻击你"装到服务器上的东西"。四种形态，攻击成本从低到高。

形态做法代表事件
依赖投毒向公开仓库提交恶意包，或劫持已有流行包的维护权，在版本更新里夹带恶意代码event-stream（2018，npm）
typosquatting注册与流行包拼写相近的名字（crossenv 仿 cross-env、colourama 仿 colorama），等手滑安装npm/PyPI 上的大量仿冒包
构建链攻击入侵构建系统/源码托管/发布流程，在制品产出环节植入后门，源码和签名可能都是"干净"的SolarWinds SUNBURST（2020）、xz-utils（2024）
镜像与制品篡改篡改容器镜像层、覆盖已发布的版本文件、劫持更新通道各类 registry 投毒案例
为什么供应链攻击性价比高：攻击一个目标要突破它的边界；投毒一个被 10 万个项目依赖的包，等于一次突破 10 万个目标。防御方的对应思路也要换：不能只守自己的服务器，要守"入口"——装什么、从哪装、装了之后信不信。
三类攻击者的动机差异：typosquatting 是撒网（盗 token、挖矿、偷 CI 密钥）；依赖投毒是精准（event-stream 只针对特定钱包应用释放载荷，静默 2 个月）；构建链攻击是国家级APT手法（SolarWinds 潜伏数月，签名合法、更新通道正规）。你的对手不一定是谁，但手法就这三类。
模块 2

依赖管理风险：传递依赖与 Lockfile

传递依赖：你看得见的依赖只是冰山一角

# 一个 npm 项目直接依赖 3 个包，实际装了 1372 个
$ npm ls | wc -l
1372

# 谁引进了这个有 CVE 的传递依赖？
$ npm ls minimatch
my-app@1.0.0 /path/to/my-app
└─┬ glob@7.2.3
  └─┬ minimatch@3.0.4      # 有已知 ReDoS CVE

风险要点：① 直接依赖你审得过来，传递依赖审不过来；② 一个包的恶意版本会被版本范围语义自动吸入（^1.2.3 会装到 1.x 最新）；③ 补丁升级可能拉进新的传递依赖（供应链的"连带升级"风险）。

Lockfile：可复现构建的第一道闸

生态锁定文件内容与作用
Node.jspackage-lock.json / yarn.lock / pnpm-lock.yaml记录全量依赖树 + 每个包的完整性哈希（integrity），装的时候逐个校验
Pythonpoetry.lock / requirements.txt + --require-hashes锁版本 + 逐包哈希，哈希不匹配即拒绝安装
Gogo.sum记录模块校验和，构建时对照 go.mod 验证
JavaMaven: dependencyManagement / Gradle: lockfiles锁定版本号；哈希校验需额外插件
# package-lock.json 里的 integrity 就是每包的防篡改指纹
"lodash": {
  "version": "4.17.21",
  "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
  "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4gLGJ6Z1O3vE1krgXZNrsQ+LFTGHVxVjcXPs17LhbZVGedAJv8XZ1tvj5FvSA=="
}

# CI 里必须用 npm ci（严格按 lockfile），不要 npm install（会改 lockfile）
$ npm ci          # 发现 lockfile 与 package.json 不一致直接失败
$ npm install     # 会重新解析版本范围、更新 lockfile —— CI 里用它是错的
lockfile 防住的是什么：它把"安装时按版本范围现算"变成"按锁定的精确版本 + 哈希安装"。攻击者就算攻陷了 npm 账号发布了新恶意版本，你的 CI 因为 lockfile 锁着旧版本而不会吸入；就算对方篡改了 tarball 内容，integrity 哈希不符会被 npm 拒绝。前提是：lockfile 必须进 Git、CI 必须 npm ci / pip-compile 严格模式。
hash 锁定（Python 侧的标准动作）：requirements.txt 直接写包名版本仍是"信任解析结果"，加 --require-hashes 才是"信任内容"： flask==3.0.3 --hash=sha256:... --hash=sha256:...。用 pip-compile --generate-hashes 生成，CI 用 pip install --require-hashes -r requirements.txt 安装，任何字节级的篡改都会失败。
模块 3

包仓库的信任模型：npm / PyPI / Maven

每个公共仓库都是一套"信任 + 缓解机制"的组合，理解它的信任边界，才知道哪些风险必须自己补。

仓库信任基础已有缓解 / 你要补的
npm账号 + 2FA（不强制所有账号）registry 提供 integrity 哈希、审计日志；补：开 2FA、用 npm provenance（构建来源证明）、看包流行度与维护活跃度
PyPI账号 + 2FA（API token 必须，普通账号已强制）trusted publishing（OIDC，无需长期 token）、PEP 740 attestations；补：--require-hashes、pip-audit
Maven Centralnamespace 验证（com.example 域名证明）+ PGP 签名发布需 GPG 签名、groupId 域名所有权校验；补：校验证书链、用受管仓库代理
Docker Hub账号 + 2FA；官方镜像有 Docker Official Images 流程镜像层摘要（digest）可锁定；补：只用 digest 引用、私有镜像扫描

Maven 的 namespace 模型为什么更强

Maven Central 要求 groupId 的域名部分（如 com.google.guava 里的 google.com）通过 DNS TXT 记录或 GitHub 仓库验证所有权。这意味着攻击者不能随意发布 com.apache.xxx 这种仿冒坐标，域名所有权成了准入闸。npm/PyPI 的命名空间是"先到先得"，抢注成本几乎为零——这正是 typosquatting 泛滥的土壤。

安装一个新包前的 30 秒尽调：① 周下载量与依赖者数量（一个被广泛依赖的包被投毒，很快会有人发现；反过来，没人用的包被投毒，可能永远没人发现）；② 维护者是谁、最近提交时间；③ 是否有可疑的 install 脚本（npm 的 preinstall/postinstall、pip 的 setup.py 执行逻辑）——大量恶意包就是靠安装脚本落地载荷；④ 仓库地址是否存在、Issues 是否正常。把这份尽调写进"新增依赖"的评审流程。
模块 4

SBOM：软件物料清单

SBOM（Software Bill of Materials）是你这个制品用了哪些组件的清单——相当于食品配料表。格式标准两个：CycloneDX（OWASP）和 SPDX（Linux 基金会，偏许可证合规）。

生成与查询

# syft（anchore）：从镜像/目录/包直接生成 SBOM
syft nginx:latest -o cyclonedx-json > sbom.cdx.json
syft dir:./my-app -o spdx-json > sbom.spdx.json

# 出了新 CVE，用 SBOM 秒级回答"我受影响吗"
grype sbom:./sbom.cdx.json --only-fixed      # 直接扫清单，不用重新分析镜像

# CycloneDX 的一个组件条目长这样
{
  "type": "library",
  "name": "lodash",
  "version": "4.17.21",
  "purl": "pkg:npm/lodash@4.17.21",
  "licenses": [{ "license": { "id": "MIT" } }],
  "hashes": [{ "alg": "SHA-256", "content": "..." }]
}
SBOM 解决的三个真实问题：① 新 CVE 爆发时的应急响应——Log4Shell 那种"全公司哪些服务受影响"的问题，没有 SBOM 要逐个翻部署清单，有 SBOM 一条命令；② 许可证合规——法务问"我们产品里有没有 GPL 组件"，SPDX 直接答；③ 攻击溯源——中勒索病毒后分析师要的"受感染镜像成分表"。SBOM 的价值平时看不见，出事那一天值全部预算。
SBOM 的工程落地：在 CI 构建末尾自动 syft 生成，和制品一起存（同 tag 归档到制品库），并做增量比对：这次构建的 SBOM 与上次 diff，新增组件要能对应到代码变更。没有 diff 的 SBOM 是一张过期地图。
模块 5

制品签名与验证：cosign / Sigstore / SLSA

为什么"下载时校验"和"构建时签名"要成对

hash 校验（lockfile 的 integrity）解决"内容没被篡改"，但前提是哈希来源可信；签名解决"这个制品确实是那个构建流程产出的"。cosign（Sigstore 项目）是当前事实标准。

# 1. 生成密钥对并签名镜像
cosign generate-key-pair                     # 产出 cosign.key / cosign.pub
cosign sign --key cosign.key registry.example.com/app:v1.2.3

# 2. 部署前验证（CI/K8s admission controller 里做）
cosign verify --key cosign.pub registry.example.com/app:v1.2.3

# 3. 无密钥签名（keyless，推荐）：身份来自 OIDC，签名上链存证
cosign sign registry.example.com/app:v1.2.3        # 自动拿 Fulcio 临时证书
cosign verify registry.example.com/app:v1.2.3 \
  --certificate-identity-regexp=https://github.com/my-org/my-repo \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com

# 4. 给制品附加 SBOM 与来源证明（attestation）
cosign attest --key cosign.key --predicate sbom.cdx.json \
  --type cyclonedx registry.example.com/app:v1.2.3
keyless 签名的革命性：传统 GPG 要管私钥分发，私钥泄露 = 信任崩塌。Sigstore 的 keyless 模式用 OIDC 身份换临时证书（Fulcio 签发、Rekor 透明日志存证），签名即"GitHub 上这个仓库的这个工作流产出的"。没有长期私钥可泄露，所有签名可公开审计。

SLSA 框架：给构建流程本身分级

等级要求实践含义
L1构建过程有文档SBOM 存在，能说清怎么构建的
L2使用托管构建服务，来源可认证GitHub Actions / 云厂商构建，非本地构建
L3构建平台防篡改，来源不可伪造隔离的构建环境 + 来源证明（provenance）签名
L4双人复核的构建，源码与构建双向可审计最高等级，多数团队不需要

SLSA 的核心洞见：只验证制品的哈希不够——构建流程本身也可能是被入侵的。 provenance（来源证明）记录"这个制品由哪个源码提交、在哪个构建平台、用什么命令产出"，并对这个记录签名。验证方用 slsa-verifier 或 GitHub 的 artifact attestations 校验。

# GitHub Actions：构建末尾产出 attestation（provenance）
- uses: actions/attest-build-provenance@v2
  with:
    subject-path: 'dist/app-v*.tar.gz'

# 下游验证：确认制品确实来自这个仓库的 release 工作流
gh attestation verify dist/app-v1.2.3.tar.gz --owner my-org
模块 6

CI/CD 供应链：GitHub Actions 的加固

Actions 的三条攻击面

Action 引用被劫持——uses: actions/checkout@v4 里的 v4 是可移动标签，攻击者拿下仓库就能把恶意 commit 推到 v4 标签上。修法：pin 到完整 commit SHA。
凭据长期化——AWS access key 直接写进 repo secrets，泄露即长期有效。修法：OIDC 联邦，用临时凭据。
PR 触发的投毒——外部 PR 跑 CI 时拿到 secrets。修法：pull_request_target 慎用、secrets 按需最小化、危险工作流只在受保护分支触发。
# 1. Pin 到 commit SHA，注释说明版本
- uses: actions/checkout@v4                      # 可移动标签，可被劫持
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683  # v4.2.2

# 2. OIDC 代替长期云密钥（以 AWS 为例）
permissions:
  id-token: write        # 换取 OIDC token
  contents: read         # 其余权限最小化
steps:
- uses: aws-actions/configure-aws-credentials@v4
  with:
    role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsDeploy
    aws-region: ap-southeast-1
# 临时凭据自动过期，仓库里不存在可泄露的 AK/SK
OIDC 部署的信任条件要写死：AWS 侧的 IAM role 信任策略必须限制 sub（具体仓库 + 分支/环境），否则任何仓库都能扮演这个角色： "token.actions.githubusercontent.com:sub": "repo:my-org/my-repo:environment:production"。少了 sub 限制的 OIDC 信任，等于把角色借给了整个 GitHub。
CI 里的其他加固项：① Dependabot / Renovate 自动升依赖，PR 带 CVE 说明和 changelog；② 分支保护：直推 main 禁止、review 必需、status check 必须过；③ 环境级 secrets：production 环境的 secret 只有部署工作流能读，且可加人工审批；④ runner 隔离：self-hosted runner 不要在公网 fork 的 PR 上跑。
模块 7

内部私服与准入控制

公共仓库是基础设施，内部私服是闸门：所有依赖必须经过它，它做缓存、审计、黑白名单。

# 架构：开发机 → 私服（Nexus/Artifactory/华为云/阿里云效）→ 公共仓库
开发机 --> Nexus Proxy(npm/pypi/maven) --> registry.npmjs.org / pypi.org / repo1.maven.org

# npm：.npmrc 强制走私服，禁掉公共源
registry=https://nexus.internal.example.com/repository/npm-group/
always-auth=true
# 私服侧：只放行审批过的外部包；内部包独立 hosted 仓库，读写分离

# pip：index-url 指向私服
pip config set global.index-url https://nexus.internal.example.com/repository/pypi-group/simple
pip config set global.extra-index-url ""     # 清掉备用源，防绕过

私服要做的四件事

能力说明
准入（allowlist）新包第一次被拉取时触发审批/扫描，恶意包进不来。这是私服最大的价值
隔离与缓存公共仓库挂了我有本地缓存，构建不中断；内部包不出内网
漏洞门禁已知高危 CVE 的版本拒绝提供，或拉取时告警
审计谁拉了什么包、什么版本、什么时间，全量日志——出事后定位"哪个团队中了毒包"靠它
内部包同样要防：内部包的常见事故是有人把带密钥的构建产物发了私服、内部包名与公共包撞名被误装（在 npm 里给内部包加 scope：@myorg/xxx，Maven 用独立 groupId）。私服上的内部包同样建议签名 + attestation，攻击者进了内网也不意味着能随便改你的制品。
模块 8

事件复盘：event-stream 与 xz-utils

event-stream（2018）：一个"友好的接手者"

npm 包 event-stream（周下载百万级）原作者疲惫不再维护，一个自称 right9ctrl 的用户主动接手维护，先发了几个正常版本建立信任，然后在 5.3.0 之后引入依赖 flatmap-stream——载荷藏在那个包里，只对 Copay 比特币钱包应用生效：窃取钱包里的数字货币。载荷在目标环境外完全静默，这就是精准投毒的教科书。

工程教训：① 维护权移交是信任悬崖——流行包的 owner 换了人，比新包还危险，因为版本号连续性骗过了所有人；② 引入新传递依赖要触发评审——flatmap-stream 是个 0 下载的新包，任何"依赖 diff"审查都能发现它；③ 精准载荷证明"我没被攻击"只是"还没轮到我"。

xz-utils / CVE-2024-3094（2024）：三年耐心的供应链渗透

攻击者 Jia Tan（JiaT75）用近三年时间在 xz 项目里建立维护者信誉：正常提 PR、参与邮件列表、逐步获得发布权限。2024 年 2 月发布的 5.6.0 / 5.6.1 源码 tarball 中被植入后门：构建系统（通过测试文件里的混淆脚本）在编译时把恶意代码注入 liblzma，篡改 IFUNC 解析，使 sshd 在认证环节放行特定持有者。后门只存在于发布 tarball，git 仓库里的源码是干净的——从 git tag 构建或审计 git 源码都发现不了。最终被微软工程师 Andres Freund 在排查 sshd 异常 CPU 延迟时发现。

工程教训（每条都价值百万）：① "从 git 构建"不等于安全——发布制品和源码可以不一致，要验 provenance；② 单一维护者依赖是系统性风险——关键基础设施项目人力单薄，xz 只有 1~2 个活跃维护者；③ 异常性能是最后的信号——sshd 多出来的几毫秒延迟暴露了后门，性能监控也是安全监控；④ 补丁要尽快——受影响的是当时主流发行版（Debian sid、Fedora Rawhide 等）的构建链，回退版本 + 扫描 SSHD 是标准应急动作。

SolarWinds（2020）：构建环境本身失守

攻击者入侵 SolarWinds 的构建服务器，在 Orion 平台的构建流程里植入 SUNBURST 后门。产出物带有 SolarWinds 的合法数字签名，通过官方更新通道分发给约 18000 家客户，静默 12~13 天后激活，回连 DGA 域名。影响美国政府多个部门和大量财富 500 强。

工程教训：① 签名证明的是"流程"，不是"内容"——构建环境被入侵后，合法签名照样为恶意制品背书，这就是 SLSA L3+ 要隔离构建环境、签 provenance 的原因；② 更新通道是最高价值目标——每家企业都自动装你的更新；③ 供应链审计要覆盖"构建机"这一层，而不只是源码和仓库。
模块 9

十个真实坑

1
CI 里用 npm install 而不是 npm ci
npm install 会重新解析版本范围并改写 lockfile，恶意新版本可被自动吸入。CI 一律 npm ci，严格按 lockfile 安装。
2
lockfile 没进 Git，或 .gitignore 忽略它
没有 lockfile 就没有可复现构建，每次 CI 装的版本都可能不同。package-lock.json / poetry.lock / go.sum 必须提交。
3
新增依赖不评审，直接 npm install 顺手就装
拼错一个字母就装上 typosquatting 包。新增直接依赖必须走 PR 评审 + 30 秒尽调（下载量、维护者、install 脚本）。
4
requirements.txt 不锁哈希
pip install 只锁版本号不锁内容。用 pip-compile --generate-hashes + pip install --require-hashes。
5
GitHub Actions 用 @v4 标签引用第三方 Action
标签可移动，对方账号失窃即被劫持。pin 到完整 commit SHA 并注释版本，用 Dependabot 管理更新。
6
云 AK/SK 写死在 repo secrets 里不轮转
长期密钥泄露就是长期失守。OIDC 换临时凭据，role-to-assume 的信任策略必须限定 sub。
7
部署只验镜像 tag 不验签名
tag 可被覆盖推送同名不同内容。用 digest 引用 + cosign verify，K8s 侧配准入控制器强制验签。
8
没有 SBOM，新 CVE 爆发靠人肉翻服务清单
Log4Shell 式应急没有 SBOM 要几天才能答"哪些服务受影响"。CI 构建自动 syft 生成 SBOM 随制品归档。
9
以为私有包/内网服务不会被投毒

自测

六道题

1. package-lock.json 里的 integrity 字段防住的是？
正确答案：防内容篡改。integrity 是每个包的哈希，安装时逐个校验。而"防止自动吸入新版恶意包"是 lockfile 锁版本号的功劳（配合 CI 用 npm ci）。两者配合：版本锁定 + 内容校验。
2. xz-utils 后门（CVE-2024-3094）最关键的教训是？
正确答案：验证构建来源。后门只存在于发布 tarball，git 仓库源码是干净的——审计 git、从 git tag 构建都发现不了。这正是 SLSA L3 与 cosign attestation 要解决的问题。
3. GitHub Actions 引用第三方 Action 最安全的写法是？
正确答案：pin 到完整 commit SHA。v4 是可移动标签，对方仓库被劫持后可以把恶意 commit 推到标签上；main 同理且更糟。SHA 不可变，用注释标版本，靠 Dependabot 管理升级。
4. 想彻底防住 typosquatting（拼写劫持）包，最有效的机制是？
正确答案：私服准入 + 依赖评审。typosquatting 利用的是命名空间"先到先得"，仓库侧无法根除（npm 已做回收，但新变体层出不穷）。私服白名单让新包第一次进入企业时有人工闸门，这是工程上最可靠的控制点。
5. cosign 的 keyless（无密钥）签名，身份信任来自？
正确答案：OIDC 身份 + Fulcio 临时证书 + Rekor 存证。keyless 模式没有长期私钥可泄露，签名即"这个仓库的这个工作流产出的"，且所有签名公开可审计。验证方校验证书里的 identity 和 issuer。
6. SLSA 框架主要解决什么信任问题？
正确答案：构建流程可信。只校验制品哈希不够——构建环境被入侵（SolarWinds）时合法签名照样背书恶意制品。SLSA 通过分级（托管构建、隔离环境、provenance 签名）让"怎么构建的"变得可验证。
