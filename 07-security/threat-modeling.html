模块 1

威胁建模解决什么问题

一句话：在写代码之前，用结构化方法找出"我们这个系统可能被怎么打"，并决定每个风险是修、是缓、还是接受。

阶段发现漏洞的成本典型手段
设计阶段1x（改一张图）威胁建模、架构评审
编码阶段约 6.5xSAST、代码评审
测试阶段约 15xDAST、渗透测试
上线后约 30~100x应急响应、漏洞修复、通报、赔偿

上表是 IBM System Sciences Institute 的经典结论，具体倍数随行业不同有出入，但量级关系稳定：越往后越贵。一次线上数据泄露的平均成本（IBM《数据泄露成本报告》口径）在数百万美元级，而威胁建模本身是"白板 + 半天"的投入。

没有威胁建模
架构定稿 → 开发 → 上线前渗透测试 → 发现"设计缺陷级"问题（如"所有接口都没鉴权"）→ 返工架构 → 延期
有威胁建模
架构评审时画出 DFD 和信任边界 → 发现"支付回调没有验签" → 设计上加 HMAC 验签 → 编码时直接实现
关键认知：威胁建模不产生"漏洞"，它产生"决策"。每个被识别出的威胁，最终要么变成一条安全需求，要么变成一条明确记录在案的"接受风险"决策。只识别不决策的威胁建模是浪费时间。
模块 2

四种方法论

方法论核心思路适用场景
STRIDE 逐元素对 DFD 里每个元素（外部实体/进程/数据存储/数据流）逐一过 6 类威胁最主流。微软提出，Threat Dragon / TMT 都内置。适合大多数业务系统
攻击树以"攻击者的目标"为根节点，自顶向下分解达成路径（AND/OR 树）高价值目标（支付、核心密钥），分析"要偷到数据有哪几条路，每条路怎么堵"
PASTA七阶段风险中心流程：定义目标→定义技术范围→应用分解→威胁分析→漏洞分析→攻击建模→风险与影响分析大型组织、需要把威胁建模和风险管理流程（ISO 31000 等）对齐时
风险矩阵按"可能性 × 影响"给威胁定级（低/中/高/严重）不是独立方法论，是优先级排序工具，通常叠加在前三者之上用

攻击树长什么样

# 攻击树示例：目标是"获取用户订单数据"
获取订单数据 (OR)
├── 直接查询数据库 (OR)
│   ├── 窃取数据库账号密码           # 缓解：密钥管理、网络隔离
│   └── 利用 SQL 注入                 # 缓解：参数化查询、WAF
├── 调用订单接口 (AND)
│   ├── 获得一个有效会话             # 缓解：强认证、异常检测
│   └── 绕过越权检查                 # 缓解：对象级授权校验（BOLA 防护）
└── 从备份/日志中恢复 (OR)
    ├── 窃取备份文件                 # 缓解：备份加密、访问审计
    └── 日志中打印了敏感字段          # 缓解：日志脱敏

# 读法：OR 节点满足任一子节点即达成目标，AND 节点需要全部子节点。
# 用法：每一个叶子（攻击路径）都要有缓解措施，缓解后的残余风险进风险矩阵。
PASTA 七阶段速记：① 定义业务目标 ② 定义技术范围 ③ 应用分解（画 DFD）④ 威胁分析 ⑤ 漏洞分析 ⑥ 攻击建模 ⑦ 风险与影响分析。它本质上是把 STRIDE 嵌进了一个更大的企业风险管理流程，对中小团队偏重，了解即可。
模块 3

STRIDE 六类威胁与缓解映射

STRIDE 是微软提出的威胁分类法，六类分别对应安全性的一个基本属性。记住"伪造、篡改、抵赖、泄露、拒绝、提权"六个词，再记对应的属性。

类别违反的属性典型威胁标准缓解
S 伪装认证伪造身份登录、盗用 token、仿冒客户端多因素认证、签名 token（JWT 验签）、mTLS、人机校验
T 篡改完整性改价格、改库存、改支付回调、改日志参数签名/HMAC、完整性校验、防重放（nonce+时间戳）、只读账户
R 抵赖不可否认性"我没下单""我没授权"审计日志（谁、何时、做了什么）、操作留痕、日志防篡改
I 信息泄露保密性拖库、越权查他人订单、日志打印敏感字段加密（传输 TLS、存储加密）、最小权限、脱敏、对象级鉴权
D 拒绝服务可用性短信轰炸、刷接口、CC 攻击、资源耗尽限流、配额、验证码、自动扩容、熔断降级
E 权限提升授权普通用户访问管理接口、水平越权改他人数据最小权限、RBAC/ABAC、水平/垂直越权校验、管理面隔离

STRIDE 与 DFD 元素的对应关系

不是每个元素都适用全部六类。按元素类型套，能显著提高效率、减少漏项：

DFD 元素适用的 STRIDE 类别
外部实体
（用户、第三方系统）		S（冒充外部实体）、R（抵赖）、I（泄露给不该看的实体）
进程
（API、服务、任务）		全部六类 —— 进程是分析重点
数据存储
（DB、缓存、对象存储）		T、I、D、R（通常不直接讨论 S/E，除非存储被直接访问）
数据流
（请求/响应链路）		T、I、D（重点：明文传输、无完整性校验的流）
信任边界
（内外网交界等）		跨边界的数据流默认不可信，重点审 S/T/I/E
最容易被漏掉的三类：R（抵赖）——出纠纷时拿不出证据，金融、电商场景是刚需；跨信任边界的数据流——"内网服务互相调用不需要鉴权"是最常见的错误假设；第三方集成的 T——回调接口不验签等于给攻击者开后门。
模块 4

DFD 绘制五要素

数据流图（Data Flow Diagram）是威胁建模的"地图"。五个要素，四个图形 + 一条线。

要素图形说明与示例
外部实体
External Entity		矩形（或小人）系统外的交互方：买家、运营人员、支付渠道、短信网关。永远不受我们控制，默认不可信
进程
Process		圆形 / 圆角矩形处理数据的组件：API 网关、订单服务、风控服务。编号（如 P1、P2）便于威胁清单引用
数据存储
Data Store		两条平行横线落盘的组件：MySQL、Redis、Kafka、对象存储、日志
数据流
Data Flow		带箭头的线数据的流向与内容：HTTPS 请求、SQL 查询、MQ 消息。标注协议和是否跨信任边界
信任边界
Trust Boundary		虚线框 / 虚线两侧信任级别不同的分界：公网↔DMZ、DMZ↔内网、内网↔数据库区。威胁建模的价值一半在信任边界上

一个最小 DFD 的 ASCII 示意

# ===== 最小电商下单 DFD（自包含示意） =====

   ┌─────────┐        HTTPS        ┌──────────────┐
   │  买家    │────────────────────▶│  API 网关     │ P1
   │(外部实体)│◀────────────────────│  (进程)       │
   └─────────┘       JSON/Token     └──────┬───────┘
                                          │ 内部 RPC
   ┌─────────┐       回调通知       ┌──────▼───────┐   ┌──────────┐
   │ 支付渠道  │◀───────────────────▶│  支付服务     │──▶│ 订单库    │
   │(外部实体)│   跨信任边界!        │  (进程) P2    │   │(数据存储)│
   └─────────┘                      └──────────────┘   └──────────┘

   ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄ 信任边界：公网 │ 内网 ┄┄┄┄┄┄
   买家、支付渠道回调在边界外；网关、支付服务、订单库在边界内

# 画图规则：
# 1. 每个进程编号（P1/P2...），威胁清单按编号引用
# 2. 每条数据流标注协议和载荷（HTTPS/JSON/Token）
# 3. 数据流穿过信任边界的地方，画重点标记（最危险）
DFD 不是部署图。部署图回答"有几台机器、什么配置"；DFD 回答"数据流经谁、存在哪、穿过哪些信任边界"。把进程画成机器、把数据流画成网络链路，是最常见的画错方式。正确粒度：一个进程 = 一个处理数据的逻辑组件，哪怕它部署在 10 个 Pod 上。
模块 5

建模四步流程

① 分解（Decompose）。搞清楚"我们在保护什么、系统长什么样"。产出：资产清单（用户数据、订单、密钥）、DFD、信任边界清单、入口清单（所有对外开放的接口/端口/队列）。常用提问："新人要黑这个系统，他会从哪进来？"
② 识别（Identify）。按方法论逐个元素过威胁。STRIDE 逐元素过；攻击树则从高价值资产倒推。产出：威胁清单，每条含 ID、所在元素、STRIDE 类别、描述、假设条件。
③ 缓解（Mitigate）。每条威胁选一种处理：修复（加验签、加鉴权）、缓解（WAF、限流降低成功率）、转移（保险、第三方合规）、接受（记录决策和理由）。每条必须落到负责人和期限，否则等于没处理。
④ 验证（Validate）。缓解措施做完了没？有效没？产出：安全测试用例（给 QA/渗透测试）、回归检查项。威胁建模的闭环在验证——没有验证环节，前面的努力有 50% 会烂尾。

威胁清单的推荐格式

# 每条威胁一行，进表格或 issue 系统都可以
ID: TM-014
元素: P2 支付服务 / 数据流"支付渠道回调"（跨信任边界）
类别: T 篡改
描述: 攻击者伪造支付渠道的"支付成功"回调通知，导致 0 元购
假设: 回调仅校验了渠道分配的 merchant_id，未验签
风险: 高（影响大 × 可利用性高）
缓解: 接入渠道官方 SDK 做 RSA 验签；增加回调 IP 白名单；增加金额二次核对
负责人: 张三 / 期限: 2026-11-01
状态: 已修复 / 待验证 / 已接受

# 关键字段：假设（assumption）——威胁建模暴露的往往是"我们以为安全"的错误假设
时长建议：第一次给核心系统做完整建模 2~4 小时；之后每个大版本/新架构决策后花 30~60 分钟增量更新。不要追求一次建模覆盖所有系统，按数据敏感度和攻击面排优先级。
模块 6

工具实操与建模时机

Microsoft TMT 与 Threat Dragon 的工作方式

工具建模方式产出与集成
Microsoft TMT选模板（如"Web 应用"）→ 拖元素 → 工具按元素类型自动生成 STRIDE 威胁清单 → 人工确认/补充报告（HTML/Excel）。注意：该工具已进入低维护状态，但对企业内部流程仍然可用
OWASP Threat Dragon画 DFD → 按元素逐个选择适用的 STRIDE 威胁 → 填缓解措施模型存为 JSON，可提交进 Git 做版本管理；Web 版可自托管
pytm用 Python 类定义元素、边界、数据流，运行后生成 DFD 和报告与代码同库评审；模板带 HTML/PlantUML 输出
threagile写 YAML 描述资产、数据流、技术栈 → 生成风险报告CI 里跑，架构变更时自动出风险差异报告
# pytm 示例：代码即威胁模型（示意，API 以官方仓库为准）
from pytm import TM, Server, Datastore, DataFlow, Boundary, Actor

tm = TM("电商下单")
internet = Boundary("公网")
internal = Boundary("内网")

buyer = Actor("买家"); buyer.inBoundary = internet
gateway = Server("API 网关"); gateway.inBoundary = internal
order_db = Datastore("订单库"); order_db.inBoundary = internal

# 数据流穿过信任边界，pytm 会为它生成对应的 STRIDE 威胁
DataFlow(buyer, gateway, "下单请求 HTTPS")
DataFlow(gateway, order_db, "写订单 SQL")
tm.process()

什么时候做威胁建模

新系统立项 / 架构设计期最佳时机。改图的成本几乎为零
大版本迭代新增对外接口、新数据流、新第三方集成时增量更新
引入新组件接入新的支付/短信/物流渠道、引入消息队列或缓存时
事故复盘后"这个威胁当时为什么没识别到"——补进威胁库
合规要求时等保、PCI-DSS、ISO 27001 均要求设计阶段风险评估
最差的时机是上线后。上线后再做威胁建模，你会发现 80% 的威胁已经"固化在架构里"，修复成本指数级上升。但如果一个老系统从来没做过，现在做也比不做好——优先做一次基线建模，之后随迭代增量更新。
模块 7

完整案例：电商下单链路

用一个简化但真实的电商下单系统，走一遍"分解 → 识别 → 缓解 → 验证"。

第一步：分解（资产 + DFD）

资产：用户个人信息（PII）、订单数据、库存数据、支付凭证、优惠券资产。入口：下单 API、支付回调、查询订单 API、管理后台。

第二步：识别（节选关键威胁）

ID元素类别威胁描述
TM-01数据流 1（买家→网关）S攻击者用窃取的 token 冒充他人下单，收货地址篡改为攻击者地址（账号盗用）
TM-02数据流 1T抓包篡改商品单价/优惠券 ID/购买数量，0 元购或超低价购
TM-03P3 支付服务 / 数据流 6T伪造支付成功回调：构造渠道通知报文，不验签则订单被置为"已支付"，0 元购
TM-04P3 支付服务R用户称"未支付"被扣款，平台无签名日志证明扣款请求由用户发起，纠纷无法仲裁
TM-05数据流 1 / P1D短信验证码接口被刷，产生高额短信费用并骚扰用户；下单接口 CC 攻击拖垮网关
TM-06DS1 订单库I越权查询：改订单号即可看他人订单（对象级授权缺失，BOLA）
TM-07DS1 订单库 / DS3I订单表明文存手机号/地址，或日志打印完整报文，泄露 PII
TM-08P4 管理服务 / 数据流 9E普通员工账号越权调用管理接口改价格、改库存、导全量数据
TM-09DS2 Redis（库存）TRedis 直连（无认证/弱口令），被改库存 key 或刷超卖脚本
TM-10P2 订单服务D重复提交订单（无幂等），订单表和库存缓存被刷爆

第三步：缓解（部分节选，含责任字段）

ID缓解措施处理方式
TM-01登录态 token 绑定设备指纹 + 异地登录二次验证；下单时短信二次确认（高价值订单）修复
TM-02价格以服务端 SKU 表为准，客户端只传 SKU ID + 数量；金额相关字段加参数签名；优惠券服务端二次校验有效期与适用商品修复
TM-03支付回调用渠道官方 SDK RSA/SM2 验签；回调来源 IP 白名单；金额与本地支付单核对（不一致进人工审核）；只认"已验签"的终态修复
TM-04支付请求/回调全量审计日志（含签名值、报文摘要、时间戳），日志只追加、定期归档取证修复
TM-05验证码 60s/号/天上限 + 图形验证码前置；网关按 IP/账号/设备限流；支付类接口单独配额缓解
TM-06查询接口强制校验"订单归属用户 == 当前登录用户"；订单号不使用连续可猜 ID，改用 UUID/混淆 ID修复
TM-07手机号/地址加密存储（应用层加密 + 密钥托管）；查询接口返回脱敏字段；日志脱敏规则（正则替换手机号/卡号）修复
TM-08管理后台独立域名 + 办公网 VPN；RBAC 细到按钮；敏感操作（改价/导数据）双人复核 + 审计修复
TM-09Redis 开启 ACL + 强密码 + 仅内网可达 + rename-command 禁用 FLUSHALL/KEYS；库存扣减用 Lua 保证原子修复
TM-10下单接口幂等键（userId + 客户端请求 ID），Redis 去重窗口 10s；重复请求返回首个订单结果修复

第四步：验证（给测试团队的安全测试用例）

  • 验 TM-03：构造无签名/错签名的回调报文，断言订单状态不变；重放同一签名报文，断言幂等拒绝
  • 验 TM-02：抓包改 price 字段为 0.01，断言服务端按 SKU 原价结算
  • 验 TM-06：登录用户 A，用 A 的会话查用户 B 的订单号，断言 403
  • 验 TM-05：脚本并发 100 次请求验证码接口，断言第 2 次起被限流
  • 验 TM-10：同一客户端请求 ID 连发 10 次下单，断言只生成 1 笔订单
这个案例的"正确打开方式"：十条威胁里，TM-02（改价格）和 TM-03（伪造回调）是"设计缺陷级"问题——它们不是代码 bug，是"信任了不该信任的输入"。这类问题只有威胁建模能在编码前以接近零成本发现。其余多为"实现层问题"，SAST/渗透测试也能发现，但晚一个阶段。
模块 8

十个常见坑

1
只列威胁，不做缓解决策
产出一张 50 行的威胁清单就宣布"建模完成"，没有 owner、没有期限、没有"修复/接受"决策。三个月后没人记得，风险原样存在。每条威胁必须有处理方式和负责人。
2
过度建模
给一个内部报表工具画 20 页 DFD、列 80 条威胁。建模成本超过系统本身价值。按数据敏感度和攻击面分级：核心交易系统详细建模，内部低敏系统 30 分钟过一遍即可。
3
安全团队闭门造车
安全工程师自己画图、自己识别威胁，开发不参与。结果：威胁清单脱离实际（提出的缓解方案技术上不可行），开发不买账，最后被扔进抽屉。建模会必须是"开发主讲架构 + 安全主讲威胁"的结对形式。
4
建模只做一次，不随架构演进
半年前给 v1.0 做了建模，之后加了开放 API、接了新渠道、上了消息队列，威胁模型没更新。威胁模型是活文档，架构变更必须触发增量评审。
5
把 DFD 画成部署图
进程画成"K8s 集群"，数据流画成"走 Service Mesh"，信任边界画不出来。部署图回答"在哪跑"，DFD 回答"数据怎么流"。没有数据流视角，就识别不了篡改和泄露类威胁。
6
忽略信任边界
"都是内网服务，互相调用不用鉴权"。一旦任一服务被攻破，攻击者在内网横向移动毫无阻碍。跨边界的数据流必须逐一验证认证、完整性和授权。
7
混淆资产、漏洞与威胁
把"用户数据库"（资产）、"MySQL 弱密码"（漏洞）、"攻击者拖库"（威胁）混为一谈列在一起，导致清单无法处理。正确结构：资产 → 威胁（谁怎么打）→ 漏洞（凭什么打成）→ 缓解。
8
用方法论名词唬人，不落地
满嘴 PASTA 七阶段、FAIR 量化模型，落到自己系统上一个数据流都画不出来。方法论是工具不是目的，能把 STRIDE 用熟就超过大多数团队了。
9
不验证缓解措施
安全需求写进 PRD 就完事，没人验证开发是否实现、实现是否有效。"已修复"和"已验证"是两回事，没有第四步（验证）的建模只完成了一半。
10
追求 100% 覆盖和零风险
试图列出所有威胁、消除所有风险，导致会议无限拉长。威胁建模是风险决策工具，不是完美主义工具。核心资产的高危威胁覆盖到了，剩下中低风险记录在案按迭代处理。
自测

六道题

1. STRIDE 中的 "T" 指什么，违反哪项安全属性？
正确答案：篡改（Tampering），违反完整性。六个词的对应关系是：S 伪装→认证，T 篡改→完整性，R 抵赖→不可否认性，I 信息泄露→保密性，D 拒绝服务→可用性，E 权限提升→授权。
2. DFD 五要素中，哪一个是"两侧信任级别不同的分界线"，也是威胁建模价值最集中的地方？
正确答案：信任边界。跨边界的数据流默认不可信，是 S/T/I/E 类威胁的高发区。很多入侵案例的根因就是"内网服务互调不鉴权"这类错误假设。
3. 攻击树中的 AND 节点表示什么？
正确答案：AND = 全部子节点都要满足，OR = 任一子节点满足即可。用 AND 分解攻击路径，能找出"最便宜的阻断点"——掐断 AND 下的任意一个子条件，整条路径就废了。
4. 关于威胁建模的时机，哪种说法是对的？
正确答案：设计阶段做基线 + 增量更新。上线后修复设计缺陷成本是设计阶段的数十倍；只做一次的威胁模型会随架构演进迅速过期。它是活文档，不是一次性项目交付物。
5. 威胁建模四步流程"分解→识别→缓解→验证"中，最容易被跳过的是哪一步？
正确答案：验证。"已修复"和"已验证"是两回事。没有验证环节，缓解措施可能根本没实现、或实现了但无效（如验签代码写错）。验证的产出是安全测试用例，交给 QA 和渗透测试执行。
6. 某团队画 DFD 时把"K8s 集群"画成一个进程，把"走 Service Mesh 的网络链路"画成数据流。问题出在哪？
正确答案：画成了部署图。DFD 里一个进程 = 一个处理数据的逻辑组件（哪怕部署在 10 个 Pod 上），数据流 = 数据的语义内容（如"下单请求：userId + skuId + 数量"），不是网络链路。没有数据流视角就识别不了篡改和泄露。

STRIDE 速查（含一句话缓解）

S 伪装 Spoofing认证：token 验签、mTLS、MFA
T 篡改 Tampering完整性：参数签名、HMAC、防重放
R 抵赖 Repudiation不可否认：审计日志、操作留痕
I 泄露 Info Disclosure保密性：TLS、加密存储、脱敏
D 拒绝服务 DoS可用性：限流、配额、熔断
E 提权 Elevation授权：最小权限、RBAC、越权校验
