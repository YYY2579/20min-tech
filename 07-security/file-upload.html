二十分钟学透 文件上传安全

上传漏洞的公式是：用户控制文件名/内容/大小 + 服务端信任 + 存储位置能执行或能访问。这篇把四层校验、存储隔离、图片库 CVE 和 zip slip 一次讲完，全部配可复现的代码。

开始前

先看清一次上传发生了什么

# 一个典型的 multipart/form-data 请求（抓包视角）
POST /upload HTTP/1.1
Host: www.example.com
Content-Type: multipart/form-data; boundary=----Boundary7MA4YWxkTrZu0gW

------Boundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="file"; filename="avatar.jpg"
Content-Type: image/jpeg

<二进制文件内容>
------Boundary7MA4YWxkTrZu0gW--
字段谁控制能否信任
filename客户端（攻击者可任意构造）不可信 —— 路径穿越、双扩展名都从这来
Content-Type客户端（抓包可改）不可信 —— 写 image/jpeg 内容也可以是 PHP
文件内容客户端不可信 —— 必须靠服务端检测
Content-Length客户端不可信 —— 与真实流长可能不一致
核心认知：multipart 里的每一个字段都是客户端写的，服务端拿到的只是一段字节。所谓"上传安全"，就是服务端决定这段字节以什么名字、存在哪、能不能被执行、有多大——四个决定权必须全部收归服务端。
模块 1

上传风险全景：五类后果

风险触发条件后果
Webshell上传 .php/.jsp/.aspx 等可执行脚本，且存储目录可被解析执行服务器被完全控制（RCE），最高危
存储型 XSS上传 .html/.svg/.swf，且与主站同域可被浏览器直接打开窃取 cookie、冒登录态、挂马钓鱼页
解析漏洞脚本文件被伪装成图片（shell.jpg），靠 Web 服务器配置缺陷触发执行间接 RCE（nginx/PHP-FPM/Apache 配置组合拳）
路径穿越filename 含 ../ 或绝对路径，被直接拼进落盘路径覆盖系统文件、配置文件，间接 RCE
资源耗尽无大小/频率限制、zip bomb、海量小文件磁盘/inode 打满，服务不可用

还有两类容易被忘的

  • SVG 上传 = XXE + XSS 二合一：SVG 是 XML，可带 <!ENTITY xxe SYSTEM "file:///etc/passwd">，服务端解析 XML 时泄露文件；直接在浏览器打开又执行其中的 JS。最稳妥的做法是干脆不接收 SVG，要接收就按不可信 XML 消毒
  • 图片元数据泄露：EXIF 含 GPS 位置、设备号；PNG textual chunk 可被利用来探测/泄露文件（ImageMagick CVE-2022-44268 就是拿 chunk 内容反射本地文件）
# 自测：一段"看起来是图片"的 polyglot（GIF 头 + PHP 代码）
printf 'GIF89a' > shell.gif
echo '<?php phpinfo(); ?>' >> shell.gif
# 文件头检测、getimagesize 都会认为它是合法 GIF
# 只有"真正解码一遍再重新编码"才能暴露它 —— 这是四层校验的最后一层
记住这条链：上传 shell.jpg（内容是 PHP）→ 访问 /uploads/shell.jpg/x.php → nginx 按 .php$ 转发给 PHP-FPM → PHP-FPM 因 cgi.fix_pathinfo=1 把不存在的 x.php 剥掉，拿前面真实存在的 shell.jpg 当脚本执行。上传的是图片，死的是服务器。这个链条上任何一环被正确配置都能断掉。
模块 2

四层校验：一层都不能少

第一层：扩展名白名单

用白名单，永远不要用黑名单。黑名单的经典翻车：封了 .php，漏了 .php3 .php4 .php5 .phtml .phar .inc、大小写 .PHP、双写 .php.jpg、老 IIS 的 .php;.jpg、NTFS ADS .php::$DATA。

# 白名单的正确用法：从内容推断类型，而不是信任用户给的扩展名
ALLOWED = {"jpg", "jpeg", "png", "gif", "webp", "pdf"}

def pick_ext(filename):
    ext = filename.rsplit(".", 1)[-1].lower() if "." in filename else ""
    # 用户扩展名只当"期望"，最终类型由第二、三层说了算
    return ext

第二层：Content-Type（只作辅助信号）

multipart part 的 Content-Type: image/jpeg 是客户端一行字，抓包就能改。它可以用于拒绝明显不匹配的请求（比如期望图片但 part 写 text/html），但不能作为判断依据。

第三层：Magic Number（文件头签名）

格式文件头（十六进制）说明
PNG89 50 4E 47 0D 0A 1A 0A固定 8 字节签名
JPEGFF D8 FF后跟 E0/E1（JFIF/EXIF）等
GIFGIF87a / GIF89a6 字节 ASCII
WebPRIFF .... WEBP偏移 8 字节处是 WEBP
PDF%PDF-通常还在文件末尾 512 字节内带 %%EOF
ZIPPK 03 04docx/xlsx/apk/jar 都是 zip
PHP<?php没有 magic，所以只能靠白名单+解码
# 读前 32 字节做判定（比只读 4 字节更稳）
def sniff(head: bytes):
    if head.startswith(b"\x89PNG\r\n\x1a\n"): return "png"
    if head.startswith(b"\xff\xd8\xff"):         return "jpeg"
    if head[:6] in (b"GIF87a", b"GIF89a"):       return "gif"
    if head[:4] == b"RIFF" and head[8:12] == b"WEBP": return "webp"
    if head.startswith(b"%PDF-"):                return "pdf"
    return None

第四层：内容深度检测（真正解码）

前两层都能被 polyglot 绕过（GIF 头后面挂 PHP）。唯一可靠的图片验证是用图片库完整解码一遍：

  • Python：PIL.Image.open(...) 后 .load() 真正解码像素，失败就拒；然后用 img.convert("RGB").save() 重新编码落盘 —— 重编码会天然剥掉附加的恶意数据和 EXIF
  • Java：ImageIO.read() 返回 null 即非图片；不要用 ImageIO.getImageReaders 只判断格式不解码
  • Node：sharp 的 .toBuffer() 走完整解码流水线
  • 通用库：python-magic（libmagic）、Apache Tika 做类型检测，但仍建议叠加图片重编码
四层校验的一句话总结：扩展名白名单决定"我接受什么"，Content-Type 只是提示，Magic Number 决定"它自称是什么格式"，只有真正解码并重编码才决定"它到底是什么"。任何只做前三层的上传功能，都等于没做。
模块 3

存储安全：让上传文件"无害化"

原则一：独立域名，与主站彻底隔离

  • 用户内容域名 files.example.com，应用域名 www.example.com —— 别用同一个域的不同路径
  • 注意 cookie：Set-Cookie: domain=.example.com 的子域共享会让隔离打折，核心业务的会话 cookie 要设 Host-Only（不写 domain 属性）
  • 更严格的做法：用户内容放完全独立的注册域（很多 UGC 平台这么干），彻底断掉同源读取

原则二：存储位置没有任何执行环境

# nginx：用户内容专用 server，没有任何动态语言配置
server {
  listen 443 ssl;
  server_name files.example.com;
  root /data/uploads;

  location / {
    add_header X-Content-Type-Options "nosniff" always;
    add_header Content-Security-Policy "default-src 'none'; style-src 'self'" always;
    add_header Content-Disposition "attachment";
    default_type application/octet-stream;
    try_files $uri =404;      # 不存在直接 404，不落到 PHP-FPM
  }

  # 关键：这里没有 location ~ \.php$，误传脚本也只会被当静态文件下载
}

# 更优解：对象存储（OSS/S3/CDN）
# - 没有执行环境，天然免疫 webshell
# - 源站 IP 隐藏，上传走后端直传 + 回调
# - CDN 边缘缓存，回源带宽可控
# - 注意 ACL：bucket 私有，读走签名 URL 或 CDN 鉴权模式

原则三：服务端生成文件名

  • 文件名 = uuid4().hex + "." + 检测出的真实扩展名，永远不出现用户原始文件名的任何部分
  • 需要展示原名时，原名只存数据库，下载时通过 Content-Disposition: attachment; filename*=UTF-8''xxx 下发并做 CRLF 过滤
  • 好处同时包括：防路径穿越（用户输入不进路径）、防覆盖（随机不冲突）、防猜测遍历（枚举不到别人文件）

原则四：下载响应头兜底

响应头作用
Content-Disposition: attachment强制下载而不是浏览器内联渲染，断掉 HTML/SVG 的 XSS 路径
X-Content-Type-Options: nosniff禁止 MIME sniffing，防止 text/plain 被 sniff 成 text/html
Content-Type: application/octet-stream默认按二进制处理
Content-Security-Policy即使渲染也不允许执行脚本/加载外站资源
什么时候可以内联？只有确认内容是你重新编码过的图片时，才允许 Content-Type: image/png + 内联显示。PDF、SVG、Office 文档一律 attachment。图片 CDN 做缩放参数（?x-oss-process=image/resize,w_200）时，也要校验处理参数，防止参数注入。
模块 4

图片处理库漏洞史： delegate 的教训

ImageMagick / GraphicsMagick 这类工具把"格式处理"外包给外部程序（delegate），历史上因此出了一整类 RCE。做上传处理的服务端，几乎都被这条链扫过。

CVE名称/问题原理与影响
CVE-2016-3714ImageTragickdelegate 调用外部命令时对内容转义不充分，构造的 SVG/MSL/MVG 里可嵌入 shell 命令，ImageMagick 处理时直接执行。影响 6.9.2-10 之前全部版本，2016 年 POC 公开后全网批量中招
CVE-2016-3718HTTP/FTP delegate文件名里带 https:// 等伪协议会触发 ImageMagick 自己去 fetch —— 相当于内置 SSRF + 信息外带
CVE-2022-44268PNG 信息泄露转换恶意 PNG 时，把 textual chunk 的内容当"文本"画进输出图，攻击者下载后再提取，可泄露服务器本地文件内容
CVE-2023-4863libwebp 堆溢出libwebp 的 VP8 解码堆缓冲区溢出，Chrome 和依赖 libwebp 的图像处理链（含 ImageMagick）都在影响面内，2023 年被在野利用
CVE-2023-36664Ghostscript 管道执行PostScript/PDF 处理链经 Ghostscript delegate 执行命令，ImageMagick + ghostscript 组合默认中招

2016 年的攻击载荷长这样（理解机制，别照着打生产）

<!-- 恶意 SVG：ImageMagick 把它交给 delegate 时，注释里的内容被拼进命令行 -->
<image url='https://example.com/x.jpg"|"touch /tmp/pwned; echo "vuln">'

# 或 MSL（Magick Scripting Language）里直接写：
<?... system("id > /tmp/owned") ?...>

四条铁律（血泪换来的）

不把 ImageMagick 直接暴露给不可信输入。用轻量专用库替代（sharp/libvips/PIL），需要 IM 时放进一次性容器，跑完即焚
policy.xml 收紧。禁用 EPHEMERAL、URL、HTTPS、HTTP、FTP、MVG、MSL、SVG、PS、EPS、PDF 相关 coder 的 delegate 权限
永远先解码重编码再处理。让用户文件先过一道"解码成像素"的关，后续处理面对的是你自己生成的干净位图
版本要追。libwebp/Ghostscript/libjpeg 这些底层 C 库的漏洞会顺着依赖链爬进你的服务，镜像构建要带安全更新基线

  <policy domain="coder" rights="none" pattern="MSL" />
  <policy domain="coder" rights="none" pattern="EPHEMERAL" />
  <policy domain="coder" rights="none" pattern="URL" />

模块 5

压缩包解压：zip slip 与 zip bomb

Zip Slip：条目名就是路径

zip 的每个条目自带文件名。解压代码如果直接 os.path.join(dest, entry_name)，而条目名是 ../../../../var/www/shell.jsp，文件就被写到了目标目录之外。2018 年 Snyk 披露时，.NET/Java/Node/Go 生态的主流解压库大面积存在这个问题，因为它不是某个库的 bug，是"手工拼路径"这个模式本身的 bug。

# 恶意 zip 的构造（仅演示原理）
python3 -c "
import zipfile
z = zipfile.ZipFile('evil.zip','w')
z.writestr('../../../../tmp/pwned.txt', 'owned')
z.close()
"
unzip -l evil.zip
# 条目名里的 ../ 会被天真的 join(dest, name) 原样继承

防御代码：规范化后必须仍在目标目录内

# Python：手动校验每条目的最终落点
import os, zipfile

def safe_extract(zf: zipfile.ZipFile, dest: str):
    dest_abs = os.path.abspath(dest)
    for info in zf.infolist():
        # 1. 拒绝绝对路径和越界条目
        target = os.path.abspath(os.path.join(dest_abs, info.filename))
        if target != dest_abs and not target.startswith(dest_abs + os.sep):
            raise ValueError("zip slip blocked: " + info.filename)
        # 2. 拒绝符号链接条目（tar 的经典攻击：先建 symlink，再写文件穿过它）
        if (info.external_attr >> 16) & 0o170000 == 0o120000:
            raise ValueError("symlink entry blocked: " + info.filename)
        if info.is_dir():
            os.makedirs(target, exist_ok=True)
            continue
        os.makedirs(os.path.dirname(target), exist_ok=True)
        with zf.open(info) as src, open(target, "wb") as out:
            out.write(src.read())

# 注意：zipfile.extractall() 高层 API 会过滤 ".."，但流式 open()+手写路径不会
# 不同生态标准库行为不一致 —— 不要依赖"框架应该帮我处理了"

Zip Bomb：压缩比武器化

样本压缩后解压后
42.zip约 42 KB约 4.5 PiB（嵌套 zip 层层展开）
常规炸弹几百 KB几十 GB，压缩比可达 10^3 ~ 10^5 量级
# 解压时必须设的上限（缺一个就是事故）
MAX_UNCOMPRESSED = 1 * 1024**3      # 单文件总计 1GB
MAX_ENTRIES       = 10000           # 条目数上限，防小文件轰炸
MAX_RATIO         = 100             # 压缩比上限：compressed_size * 100 见底就拒

def guarded_extract(zf, dest):
    total = 0
    infos = zf.infolist()
    if len(infos) > MAX_ENTRIES:
        raise ValueError("too many entries")
    for info in infos:
        total += info.file_size
        if total > MAX_UNCOMPRESSED:
            raise ValueError("decompression bomb: total too large")
        if info.compress_size and info.file_size / info.compress_size > MAX_RATIO:
            raise ValueError("suspicious compression ratio")
    safe_extract(zf, dest)
tar 比 zip 更危险：tar 条目除了路径穿越，还支持 symlink/hardlink 条目——先放一个指向 /etc/cron.d 的 symlink，再放一个"文件"条目，解压器就顺着链接把内容写进了系统目录。Python 3.12+ 的 tarfile 加了 filter='data' 参数强制过滤，老代码要显式升级。
模块 6

大小与频率限制

三道闸门，层层收紧

层级配置/做法挡住什么
边缘层nginx client_max_body_size 10m超大请求在到达应用前就被 413 拒掉，省应用资源
应用层读流时按 MAX+1 字节读，超了直接断Content-Length 造假、分块传输绕过边缘限制
存储层对象存储生命周期 + 磁盘配额 + inode 监控长期堆积把盘撑满
# nginx：全局与接口级都要设（默认只有 1m，容易忘）
http {
  client_max_body_size 10m;          # 全局兜底
  client_body_buffer_size  128k;     # 小请求走内存，大请求落临时文件
  client_body_temp_path /tmp/nginx_body 1 2;   # 临时目录要监控，磁盘打满常死在这
}
server {
  location /upload {
    client_max_body_size 5m;         # 上传接口单独收紧
    proxy_pass http://app;
  }
}

# Java Spring Boot：文件大小阈值
spring.servlet.multipart.max-file-size=5MB
spring.servlet.multipart.max-request-size=10MB
spring.servlet.multipart.file-size-threshold=128KB   # 超过先落临时文件

频率与配额：按"人"限，不按"连接"限

  • 按用户：登录用户每 24h 最多 N 个文件、总容量 M GB（超了拒绝并要求删除）
  • 按 IP：匿名上传按 IP 限速（如 10 次/分钟），防撞库式刷量
  • 按接口：全局限速，比如总上传带宽 limit_req 或网关侧 QPS 上限
  • 冷启动防刷：新注册用户/新 IP 更严的额度，防批量小号灌垃圾文件
# nginx 限速：按 IP 桶
limit_req_zone $binary_remote_addr zone=upload:10m rate=10r/m;

location /upload {
  limit_req zone=upload burst=5 nodelay;
  limit_req_status 429;
  client_max_body_size 5m;
  proxy_pass http://app;
}
# 注意：limit_req 按"请求数"不限字节；字节级限速用 limit_rate
# limit_rate 1m;  # 单连接限速 1MB/s
配额要可视化：给用户一个"我的文件"页面，能看到自己占了多少空间、有多少文件。没有配额展示的用户会无限囤积，存储账单和备份时间一起失控 —— 这是运维事故，不是安全事故，但一样要命。
模块 7

从漏洞版到安全版：完整代码

漏洞版（Flask，五个错误全犯）

# ✗ 反面对教材：每一行都有问题
@app.route("/upload", methods=["POST"])
def upload_bad():
    f = request.files["file"]
    name = f.filename                          # 1. 用户输入直接当文件名（路径穿越）
    if not name.endswith((".jpg", ".png")):    # 2. 黑名单式后缀检查，且可绕过
        return "no", 400
    f.save(os.path.join("/var/www/uploads", name))  # 3. 存进 Web 根目录，可被解析执行
    return "ok"                                # 4. 无大小限制、无频率限制、无内容检测

安全版（四层校验 + 服务端命名 + 重编码）

import io, os, uuid, logging
from flask import Flask, request, abort
from PIL import Image

app = Flask(__name__)
UPLOAD_DIR = "/data/uploads"          # nginx files 域名的 root，无执行环境
ALLOWED = {"png": "PNG", "jpeg": "JPEG", "gif": "GIF", "webp": "WEBP"}
MAX_SIZE = 5 * 1024 * 1024            # 5MB

def sniff(head: bytes):
    if head.startswith(b"\x89PNG\r\n\x1a\n"): return "png"
    if head.startswith(b"\xff\xd8\xff"):        return "jpeg"
    if head[:6] in (b"GIF87a", b"GIF89a"):      return "gif"
    if head[:4] == b"RIFF" and head[8:12] == b"WEBP": return "webp"
    return None

@app.post("/upload")
def upload():
    f = request.files.get("file")
    if f is None:
        abort(400, "no file")

    # ---- 大小：读 MAX+1 字节，超了即拒（不信 Content-Length）----
    data = f.read(MAX_SIZE + 1)
    if len(data) > MAX_SIZE:
        abort(413, "too large")

    # ---- 类型：Magic Number + 完整解码 ----
    kind = sniff(data[:32])
    if kind is None:
        abort(415, "unknown type")
    try:
        img = Image.open(io.BytesIO(data))
        img.load()                          # 真正解码，polyglot 活不过这一关
    except Exception:
        abort(415, "decode failed")

    # ---- 重编码：剥掉 EXIF/附加数据，输出干净位图 ----
    if img.mode not in ("RGB", "RGBA", "P"):
        img = img.convert("RGB")
    out = io.BytesIO()
    img.save(out, format=ALLOWED[kind])     # 用推断出的格式，不是用户给的扩展名

    # ---- 服务端命名：用户输入零参与 ----
    name = f"{uuid.uuid4().hex}.{kind}"
    path = os.path.join(UPLOAD_DIR, name)
    with open(path, "wb") as fp:
        fp.write(out.getvalue())
    os.chmod(path, 0o644)

    # 返回的是 files 域的下载地址，响应头由 nginx 加 attachment/nosniff
    return {"url": f"https://files.example.com/{name}"}, 201

模块 8

十个真实坑

1
只在前端做扩展名校验
JS 拦 .exe 只是体验优化。抓包改 filename、直接 POST 到接口，一秒绕过。前端校验永远只是 UX，不是安全边界。
2
用黑名单过滤扩展名
封了 .php 漏 .php3/.phtml/.phar/.inc，漏 .PHP 大小写、漏 .php.jpg 双写、漏 IIS 的 .php;.jpg。白名单只放行业务需要的格式。
3
用用户输入做文件名或路径
filename="../../../app/config.yml" 直接覆盖配置。服务端必须用 uuid4 生成名，用户原始文件名只存数据库、只用于展示。
4
信任 multipart 的 Content-Type 和扩展名
part 头全是客户端写的。写 image/jpeg、叫 avatar.jpg，内容照样是 PHP。判断类型只能靠 Magic Number + 解码。
5
只查文件头，不真正解码
GIF89a 头后面挂 PHP 的 polyglot 能过 getimagesize。必须完整解码并重编码落盘，让附加数据活不下来。
6
上传目录在 Web 根目录且带动态解析配置
nginx location ~ \.php$ + cgi.fix_pathinfo=1 时，/uploads/shell.jpg/x.php 会把 shell.jpg 当 PHP 执行。上传目录独立 server、无 location ~ \.php$、fix_pathinfo=0、try_files $uri =404。
7
把用户文件直接喂给 ImageMagick
CVE-2016-3714（ImageTragick）delegate 命令注入就是批量这么中的。换 sharp/libvips/PIL，或沙箱 + policy.xml 收紧 delegate。
8
解压 zip 直接 join 条目名
zip slip：../../ 写穿目标目录。每条目规范化后校验仍在目标目录内，并拒绝 symlink 条目；tar 用 filter='data'。
9
无大小、无频率、无配额限制
一个 10GB 文件或 42.zip 就能打满磁盘（nginx client_max_body_size 默认只有 1m，很多人根本没设）。大小、频率、用户配额三层都要有。
10
用户文件与主站同域同路径
上传的 .html/.svg 在主站域下直接渲染 = 存储型 XSS 偷 cookie。用独立域名 + attachment + nosniff + CSP，把用户内容当"另一个站"对待。
自测

六道题

1. 用户上传一个 .html 或 .svg 文件，最大的风险是什么？
正确答案：存储型 XSS。SVG 还是 XML，附带 XXE 风险。对策：独立域名 + Content-Disposition: attachment + nosniff，业务上尽量不收这类格式。
2. 上传了内容是 PHP 的 shell.jpg，访问 /uploads/shell.jpg/x.php 却执行了。原因是？
正确答案：nginx location + PHP-FPM fix_pathinfo 的组合缺陷。修法三连：上传目录独立 server 且无 PHP location、cgi.fix_pathinfo=0、try_files $uri =404。
3. 判断上传文件真实类型，最可靠的做法是？
正确答案：Magic Number + 真正解码。前两者都是客户端可控的字符串；GIF 头挂 PHP 的 polyglot 能过文件头检查，但过不了"解码成像素"这一关。
4. 防御 zip slip 的正确姿势是？
正确答案：逐条目校验落点。禁 zip 有时不现实（业务要收压缩包）；限大小防的是 zip bomb 不是 zip slip。核心是消灭"join(dest, 用户可控名)"这个模式。
5. CVE-2016-3714（ImageTragick）的根因是？
正确答案：delegate 命令注入。教训通用：不要把不可信文件喂给会转交外部程序的工具链；必须用就沙箱化 + policy.xml 禁用高危 coder + 先解码重编码。
6. 上传存储的正确姿势是？
正确答案：独立域 + 禁执行 + 随机名 + 对象存储。原始文件名只存数据库用于展示；用用户输入命名等于把路径穿越和覆盖漏洞留在生产里。
