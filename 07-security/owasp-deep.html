Top 10 版本变迁与使用方式

OWASP Top 10 大约每 3~4 年一版。2021 版相比 2017 版最大的结构性变化是新增了三类"工程化"风险，这直接反映了业界的复盘结论。

2021 编号名称与 2017 版的关系
A01失效的访问控制 Broken Access Control2017 年排第 5，2021 年升至第 1——34 个 CWE 与之相关，是出现频率最高的类别
A02加密失败 Cryptographic Failures由"敏感数据泄露"改名而来，更强调失败原因在加密本身
A03注入 Injection2017 年第 1，2021 降到第 3（SQL 注入在框架普及后下降，但 XSS 归并了进来）
A04不安全设计 Insecure Design全新类别：设计阶段的缺陷，代码写得再好也修不掉
A05安全配置错误 Security Misconfiguration延续，云原生时代权重上升
A06易受攻击的过时组件沿用，改名后强调"已知漏洞"而非"只是旧"
A07身份认证失败沿用并扩展，把凭证填充等问题纳入
A08软件和数据完整性失败全新类别：不验证完整性的更新与反序列化
A09日志监控失败全新类别，回应"入侵平均 200+ 天才被发现"的现实
A10SSRF 服务端请求伪造由社区投票新增，云时代元数据攻击的产物
正确用法：把 Top 10 当威胁建模的检查清单——设计评审时逐条问"这个系统会不会有这个问题"，而不是当"漏洞清单"事后打勾。每条都映射到具体 CWE，测试用例、修复指南都能在 OWASP Cheat Sheet 系列找到对应专题。下面所有内容是自包含的，不依赖外部链接。
模块 1

A01 失效的访问控制

风险：已认证用户能访问其权限之外的资源或功能。2021 版排名第一，CWE-200/201/352/639 等 34 个 CWE 归入此类。

真实场景

  • IDOR（不安全的直接对象引用）：订单接口 /api/orders/1001，登录用户把 1001 改成 1002 就看到了别人的订单——服务端只检查了"登录没"，没检查"是不是你的"。
  • 水平越权与垂直越权：同角色用户 A 看到用户 B 的数据（水平）；普通用户访问 /admin/users（垂直）。
  • 元数据与源码暴露：Spring Boot Actuator 的 /env、/heapdump 直接可下；.git 目录被打包下载。
  • 路径穿越：下载接口 /download?file=../../etc/passwd。
  • CORS 配置错误：Access-Control-Allow-Origin 反射任意 Origin 且允许带凭证，等于把接口开放给任意站点。

检测与修复

检测方法修复措施
抓包改资源 ID 逐个接口试（授权测试是黑盒测试的必备项）服务端强制对象级授权：每个请求校验"当前用户对目标资源"的权限，不依赖前端隐藏
自动化越权扫描（Burp 的 Autorize 类插件用低权限会话跑全站）默认拒绝：访问控制模型用白名单（谁能访问什么），不用黑名单（谁不能访问）
目录/文件扫描发现 actuator、.git、备份文件管理端点独立管理区 + 网络白名单；禁用 heapdump/env 等敏感端点
代码审计：所有 Controller 入口是否有授权注解/中间件权限注解/中间件统一拦截 + 服务层二次校验（纵深防御，别只在网关做）
// 反例：只从 token 取了 userId，没校验订单归属 —— 典型 IDOR
@GetMapping("/api/orders/{id}")
public Order get(@PathVariable Long id) {
    return orderDao.selectById(id);        // ✗ 谁的订单都能查
}

// 正例：查询条件里强制绑定当前用户
@GetMapping("/api/orders/{id}")
public Order get(@PathVariable Long id) {
    return orderDao.selectByIdAndUserId(id, currentUserId());  // ✓ 归属校验
}
最高频翻车点：把访问控制做在网关/前端（隐藏按钮、网关鉴权），内网服务之间零信任直接调用——一旦任何服务被 SSRF 或注入打穿，内网所有接口裸奔。正确姿势：每个服务自己做授权，网关只做粗粒度准入。
模块 2

A02 加密失败

风险：敏感数据（凭据、个人信息、支付信息）在传输或存储中未受恰当加密保护，或密钥管理失控。

真实场景

  • 传输层：登录接口还是 HTTP 明文；内网"以为安全"的管理后台全明文；TLS 只到网关，内网明文转发。
  • 密码存储：MD5/SHA1/单盐 SHA256 存密码——彩虹表 + GPU 爆破下形同虚设。
  • 对称加密误用：AES-ECB 模式（相同明文出相同密文，模式泄露）；硬编码密钥在客户端/前端 JS 里；IV 全零或固定。
  • 密钥管理：密钥写在配置文件和代码仓库里；从不轮换。

检测与修复

检测方法修复措施
抓包看是否明文传敏感字段；sslyze/testssl 扫协议与套件全链路 TLS 1.2+，关闭 SSLv3/TLS1.0/1.1 与弱套件（RC4、DES、NULL）
查数据库敏感字段是否明文；搜代码里的 key/secret 硬编码密码用 bcrypt/argon2/scrypt（自适应慢哈希 + 盐），禁止通用哈希
审查加密实现：模式、IV、密钥来源用 AEAD（AES-GCM/ChaCha20-Poly1305）保证机密性+完整性；IV 随机
审计密钥存放位置与轮换记录密钥进 KMS/Vault，应用只持有句柄；定期轮换 + 多版本共存过渡
页面/接口返回是否带多余敏感字段展示脱敏（手机号/身份证掩码）、返回字段最小化、日志脱敏
// 密码存储：bcrypt（自动加盐 + 可调成本因子）
String hash = BCrypt.hashpw(plainPassword, BCrypt.gensalt(12));  // cost=12
boolean ok = BCrypt.checkpw(input, hash);   // 校验

// AES-GCM：随机 12 字节 IV，密文带认证标签，禁止 ECB/CBC 无 MAC
byte[] iv = new byte[12]; secureRandom.nextBytes(iv);
var spec = new GCMParameterSpec(128, iv);   // 128-bit tag
var cipher = Cipher.getInstance("AES/GCM/NoPadding");
cipher.init(Cipher.ENCRYPT_MODE, key, spec);
两个反直觉点：① HTTPS 不等于数据安全——证书不校验（客户端 trustAllCerts 调试代码上线）、忽略证书过期告警，等于把 TLS 打成明文；② 前端"加密"不是加密——JS 里的 AES 密钥任何人都能拿到，前端加密只防顺手截包，不防攻击者。真正的数据安全边界在服务端。
模块 3

A03 注入

风险：不可信数据被送到解释器执行——SQL、NoSQL、OS 命令、LDAP、XPath、模板引擎。SQL 注入仍是数据泄露的头号入口。

真实场景

  • SQL 注入：后台订单查询接口拼接 "WHERE status='"+status+"'"，输入 ' OR 1=1-- 拖全表。
  • ORM 原生 SQL：JPA 的 createNativeQuery("... WHERE name='"+name+"'")、MyBatis 的 ${} 占位符（${} 是字符串拼接，#{} 才是参数绑定——这是 MyBatis 最高频的注入点）。
  • 日志/搜索接口：内部运营后台"没有外网暴露所以没关系"——被 XSS/CSRF 打穿后就是内网注入跳板。
  • 模板注入 SSTI：Thymeleaf/Freemarker/velocity 把用户输入当模板渲染，{{7*7}} 返回 49 即中招。
  • OS 命令：运维工具把用户输入拼进 shell（Runtime.exec("ping " + ip)）。

检测与修复

检测方法修复措施
授权范围内用 SQLmap/手工 Payload 逐参数测试参数化查询（PreparedStatement / ORM 绑定参数），数据与代码分离
代码审计：搜字符串拼接 SQL、${}、+ 拼 whereORM 排序/表名等无法参数化的位置用白名单枚举映射，不接受原始输入
WAF/日志里的注入特征告警输入校验（白名单、长度、类型）作为第二层，不能替代参数化
错误响应是否泄露 SQL/堆栈数据库账号最小权限（禁 DROP/文件读写）；错误信息统一化
// MyBatis：${} 是字符串拼接（可注入），#{} 才是参数绑定
-- 危险：ORDER BY ${sortField}   ← 用户可控即注入
-- 正确：ORDER BY ${allowedSort} ← 白名单枚举值
<if test="sortField=='name'">ORDER BY name</if>
<if test="sortField=='time'">ORDER BY created_at</if>

# Java 命令执行：不要拼字符串，用参数数组
Runtime.getRuntime().exec(new String[]{"ping", "-c", "2", ip});  // ✓
Runtime.getRuntime().exec("ping -c 2 " + ip);                      // ✗ shell 注入
过滤黑名单是自欺欺人：大小写混合（SeLeCt）、注释变形（sel/**/ect）、编码绕过（URL/Unicode）、宽字节（GBK 的 %bf%27）——黑名单永远有漏网。唯一可靠的防线是参数化 + 白名单。WAF 只是争取时间的补丁。
模块 4

A04 不安全设计 + A05 安全配置错误

这两条都是"上线前就该做对"的事：A04 是设计层面的缺陷，A05 是部署层面的疏忽。它们无法靠后期堆设备修复。

A04 不安全设计：业务逻辑的坑

核心问题是威胁建模缺失——设计时只想了"正常用户怎么用"，没想"攻击者怎么滥用"。

场景设计缺陷正确设计
找回密码验证码 6 位数字不限速、不失效限速 + 尝试次数上限 + 过期 + 与设备绑定
优惠券/红包无幂等无并发控制，可脚本并发重复领取幂等键 + 唯一约束 + 分布式锁 + 风控规则
转账/支付无金额上限、无幂等，可重放幂等 token、限额、对账、状态机校验
注册/登录无验证码无速率限制限速 + 验证码 + 设备指纹 + 异常拦截

A05 安全配置错误：默认值的坑

  • 管理端点暴露：Spring Boot Actuator 全部端点对公网开放（/env 泄露配置含密钥、/heapdump 下载后可提取密钥）、Druid 监控页无认证、K8s Dashboard/etcd 2379 端口暴露。
  • 云资源公开：S3/OSS 桶公共读、快照公开、RDS 公网可达。
  • 错误处理：DEBUG 模式上线、异常堆栈直接返回给客户端。
  • 默认凭据：数据库/中间件/管理台出厂口令没改。
  • CORS 通配：Access-Control-Allow-Origin: * 配合 credentials。
# Spring Boot Actuator 加固：只暴露健康检查，其余禁用
management:
  server:
    port: 9091            # 独立管理端口
  endpoints:
    web:
      exposure:
        include: "health,info"   # 只开这两个
  endpoint:
    health:
      show-details: never      # 不显示细节

# Nginx：关目录列表、统一错误页、隐藏版本号
server { 
  autoindex off;              # 关目录浏览
  server_tokens off;          # 隐藏版本号
  error_page 500 502 503 504 /50x.html;
  location /50x.html { internal; }
}
A04/A05 的落地抓手：① 设计评审必过威胁建模（STRIDE：仿冒、篡改、抵赖、信息泄露、拒绝服务、提权）；② 上线 checklist 固化配置基线（CIS Benchmark + 云配置基线），CI 里自动扫描；③ 把"最小暴露面"当默认价值观——默认关闭、按需开启，而不是默认全开、事后加固。
模块 5

A06 过时组件 + A08 完整性失败

这两条是"供应链"双生子：A06 是你用了有已知漏洞的旧东西，A08 是你无法保证用的东西没被篡改。Log4j（CVE-2021-44228）之后，这两条从"重要"升级为"战略级"。

A06 易受攻击的过时组件

  • 典型样本：Log4j2 JNDI 注入、Fastjson autoType、Struts2 系列、Shiro 反序列化、旧版 Spring/Jackson；以及镜像里的 OS 层 CVE（OpenSSH、OpenSSL、glibc）。
  • 传递依赖陷阱：你升级了直接依赖，但传递依赖里的旧版本没人管——mvn dependency:tree 一查全是惊喜。

A08 软件和数据完整性失败

  • 更新通道无签名：客户端/固件/Agent 下载更新不验签，中间人可投毒。
  • CI/CD 投毒：依赖混淆攻击（dependency confusion，把内部包名抢注到公网仓库，构建时拉到恶意版本）、构建脚本被改、镜像仓库拉取未验签镜像。
  • 不可信反序列化：接收端对序列化数据不验签直接反序列化——详见同系列反序列化专题。

检测与修复

检测方法修复措施
SCA 工具链：OWASP Dependency-Check、Trivy、Snyk、npm audit、mvn versions:display-dependency-updates建立升级节奏（安全补丁 SLA：高危 7 天内）；虚拟补丁过渡
SBOM（软件物料清单）比对 CVE 库，出事时快速回答"我在不在影响范围"CI 流水线 SCA 门禁：高危 CVE 阻断构建
镜像/制品是否签名可验证（cosign verify、GPG）制品签名 + 部署侧验签；镜像只从内部签名仓库拉取
依赖来源是否可能被抢注（内部包名是否已占用公网命名空间）内部包使用保留命名空间/私有仓库优先；lock 文件锁定版本与哈希
# CI 里做依赖漏洞门禁（示例）
npm audit --audit-level=high        # Node：高危即失败
mvn org.owasp:dependency-check-maven:check -DfailBuildOnCVSS=7
trivy image --exit-code 1 --severity HIGH,CRITICAL myapp:latest
cosign verify --key cosign.pub registry.example.com/myapp:latest  # 部署前验签
Log4j 教给行业的两件事：① 你需要知道自己在哪用了什么——没有 SBOM 和资产台账，出漏洞时连"影不影响我"都要查三天；② 漏洞藏在传递依赖里——直接依赖干干净净，Log4j 是某个日志门面带进来的。定期跑一次全量依赖树 + CVE 比对，是性价比最高的安全投入之一。
模块 6

A07 身份认证失败

风险：认证、会话、令牌管理存在缺陷，导致密码破解、会话劫持、身份冒充。

真实场景

  • 弱口令与凭证填充：123456、P@ssw0rd；拖库数据自动化撞库（credential stuffing）——你系统再安全，用户用的是别的站泄露的密码。
  • 无锁定无限速：登录/短信验证码接口可无限尝试，6 位验证码几分钟被爆破。
  • 会话管理缺陷：Session ID 登录前后不变（会话固定）；Cookie 无 HttpOnly（XSS 可偷）、无 Secure、无 SameSite（CSRF）；JWT 永不过期。
  • JWT 误用：只 base64 不解密（JWT 是签名不是加密，payload 谁都能看）；alg: none 被接受；不校验 exp/aud；签名密钥弱（如 "secret"）。
  • 密码找回缺陷：重置链接可预测、不过期、可复用；短信验证码返回在响应体里（"方便调试"）。

检测与修复

检测方法修复措施
测试连续错误登录是否锁定/限速；验证码是否可重放登录失败锁定（5 次/10 分钟）+ IP/账号维度限速 + 验证码
解码 JWT 看 payload；篡改 alg/exp 重放测试用成熟库校验（算法白名单 + exp/nbf/aud/iss 全验），禁止 none
检查 Cookie 属性；登录前后 session id 是否变化HttpOnly + Secure + SameSite；登录成功后重置会话 ID；合理过期时间
密码库比对泄露库（Have I Been Pwned 的 k-anonymity 模型）密码策略 + 泄露密码检测 + 多因素认证（TOTP/WebAuthn）
审查找回流程每一步的可枚举性找回令牌：足够熵、一次性、短时效、绑定请求上下文
# JWT 的三条军规
1. JWT 是签名不是加密 —— payload 别放敏感信息，谁都能 base64 解码看
2. 必须校验：签名算法（禁 none/HS/RS 混淆）+ exp + aud + iss
3. 注销/改密后原 JWT 仍然有效直到过期 —— 需要黑名单或短过期 + 刷新令牌
凭证填充为什么难防：因为攻击用的都是合法账号 + 正确密码（在别的站泄露的），WAF 看不到攻击特征，速率限制也可能被分布式 IP 绕开。唯一有效的防线是多因素认证 + 异常行为检测（异地登录、新设备、非常用时段触发二次验证）。这也是大厂推 MFA 的根本原因。
模块 7

A09 日志监控失败 + A10 SSRF

A09 日志监控失败：不是"没日志"，是"没告警"

OWASP 2021 把这一条单列，背景是业界统计：入侵被发现的平均时间以百天计。日志躺在那没人看，等于没记。

必须记录并告警的事件为什么
登录成功/失败、锁定、找回密码爆破、撞库、账号接管的第一现场
越权访问被拒绝、批量数据导出IDOR 扫描、拖库进行时
输入验证失败激增、WAF 拦截注入/扫描正在进行
管理员操作、权限变更、配置变更内部威胁 + 后门植入
服务端错误率突增、异常出网连接漏洞被利用、C2 通信
  • 日志字段四要素：who（主体）/ when（时间，统一时区 NTP）/ what（动作与对象）/ result（成功失败）。缺一个，事后就无法回答"发生了什么"。
  • 留存 ≥6 个月（国内法定要求，详见等配合规模块）；敏感数据脱敏后记录，日志本身也要防篡改（独立采集、只读账号）。
  • 告警要有人值班闭环——告警发到没人看的群等于没有告警。

A10 SSRF：让服务器替你访问

风险：服务端按用户提供的 URL 发起请求——攻击者借此扫描内网、访问云元数据、攻击内网服务。

  • 触发点：图片/头像 URL 导入、webhook 回调、OAuth 回调地址、RSS 订阅、PDF 生成服务抓取远程资源、消息卡片预览。
  • 云上最高价值目标：http://169.254.169.254/latest/meta-data/iam/security-credentials/——拿到实例角色的临时凭据，等于拿到云账号部分权限（AWS 2019 Capital One 事件正是这个路径）。
检测方法修复措施
找所有"填 URL"的功能，抓包看服务端是否真的去请求URL 白名单（scheme/host/端口），解析后的 IP 校验（禁私网/回环/链路本地段）
测试访问 169.254.169.254、内网 IP、file://、gopher://禁止重定向或每跳重新校验；DNS 重绑定防护（解析一次、用 IP 连接）
测试响应是否带回内网服务内容（信息回显）网络层：业务服务器出网策略默认拒绝内网敏感段；元数据用 IMDSv2（PUT 令牌）
// SSRF 防护的最小实现（概念级）
URL u = new URL(userInput);
if (!"https".equals(u.getProtocol()) && !"http".equals(u.getProtocol())) throw ...;
InetAddress addr = InetAddress.getByName(u.getHost());
if (addr.isLoopbackAddress() || addr.isSiteLocalAddress()
    || addr.isLinkLocalAddress() || addr.isAnyLocalAddress()) throw ...;  // 禁私网/回环/169.254
// 且：只用解析出的 IP 发起连接，不再走一次域名解析（防 DNS rebinding）
SSRF 的三个绕过套路，防护时都要覆盖：① 302 重定向——第一跳是公网合法地址，跳转到内网；② DNS 重绑定——域名第一次解析为公网 IP 过校验，第二次解析为 127.0.0.1；③ 协议走私——file:// 读本地文件、gopher:// 构造任意 TCP 报文打内网 Redis/MySQL。校验 scheme + 解析 IP + 用 IP 直连 + 禁/控重定向，四件套配齐。
模块 8

综合案例：一次拖库事件的完整攻击链

下面这条链条把 A01~A10 全部串起来。每个环节单独看都"不算大事"，连起来就是一次千万级数据泄露。看懂这条链，你就懂了为什么安全是体系不是功能。

【A06 过时组件】站点用了三年前某版本图片处理库，该版本存在已知 RCE（CVE-9.x）。攻击者先扫到这个组件版本，再用公开 PoC 拿下 Web 服务器。如果 SCA 在 CI 里拦下这个高危依赖，链在这里就断了。
【A05 配置错误】同一台服务器上跑着一个内部服务，Actuator 全端点开放且 DEBUG 模式没关。攻击者读 /env 拿到了数据库密码和云 AK，/heapdump 里直接提取出密钥。
【A10 SSRF】应用有个"订阅物流通知"的 webhook 功能，URL 用户可控。攻击者用它扫内网，访问 169.254.169.254 拿到实例角色临时凭据，进而操作对象存储。
【A03 注入】运营后台的订单搜索接口，SQL 用字符串拼接。攻击者从已控服务器横向进入内网后，用这个接口 UNION SELECT 把订单表、用户表整体拖出。
【A01 访问控制】拖库过程中发现 /api/orders/{id} 不校验归属，顺手把全平台近 90 天的订单信息按 ID 遍历导了一遍——业务方三天后才从客诉得知。
【A02 加密失败】数据库里的用户手机号是明文，密码是 MD5。泄露直接导致撞库风险外溢到其他站点；备份文件也没有加密，一起被拷走。
【A09 日志监控失败】全程 23 天没有任何告警：WAF 日志只存 30 天且无人看；没有登录异常告警；没有数据导出审计。攻击者静默完成了数据打包外传。这是整条链里唯一"零成本可断"的环节——只要导出量告警存在。
【A04 不安全设计】风暴期间攻击者还刷了新人优惠券（并发重复领取），业务方一度以为只是营销被薅，转移了对真正数据泄露的注意力。设计缺陷不仅造成损失，还会干扰应急响应的判断。
【A08 完整性失败】收尾调查发现：构建机上某个 npm 依赖两周前被换成了恶意版本（依赖混淆），每次构建都会把一份内网探测代码打进镜像。这意味着即使你重装被入侵的机器，新镜像依然是脏的。

按案例复盘：防护优先级怎么排

断链位置措施成本
最早可断：SCA 门禁CI 阻断高危 CVE 组件低，一天接入
暴露面收敛Actuator 端点最小化、DEBUG 关闭、管理端口白名单低，改配置
检测兜底批量导出告警、异常登录告警、日志留存 6 个月中，但一次投入长期生效
深度防御参数化 SQL、对象级授权、TOTP、webhook 白名单、出网策略高，进架构和流程
这个案例的真正教训：十条风险里，任何一条单独存在都不至于酿成大事——攻击者也不需要"高深技巧"，用的全是公开工具和默认配置。安全水位取决于你最弱的那一环，而最弱的环节往往是"没人觉得有问题"的环节。所以防护的正确顺序是：先断最低成本的链（SCA、配置基线、告警），再补架构级的（授权、加密、MFA）。
模块 9

十个常见坑

1
访问控制做在前端和网关
按钮隐藏、网关鉴权，内网服务之间裸调。任何一个服务被 SSRF/注入打穿，全部接口失守。每个服务自己做对象级授权。
2
JWT 当加密用 + 不验声明
把用户角色塞进 payload 以为别人看不到（base64 谁都能解）；不校验 exp/aud；接受 alg:none。JWT 是签名不是加密，声明要全验。
3
SQL 注入靠关键词黑名单过滤
大小写、注释、编码、宽字节变形轻松绕过。唯一可靠防线是参数化查询 + 白名单枚举。WAF 只是争取时间。
4
密码用 MD5 或单盐 SHA256
彩虹表 + GPU 每秒数十亿次哈希，等于明文。必须用 bcrypt/argon2 这类自适应慢哈希。
5
CORS 配了通配符还允许带凭证
Access-Control-Allow-Origin 反射 Origin + Allow-Credentials: true，等于把登录态接口开放给任意网站。Origin 必须白名单。
6
管理端点暴露公网
Actuator/env、Druid、K8s Dashboard、etcd 2379、Redis 6379 无认证对外。这类问题不需要任何攻击技巧，扫到就穿。
7
升级组件只看直接依赖
直接依赖升到最新，传递依赖里的旧版本（Log4j 就是这么进来的）没人看。定期全量依赖树 + CVE 比对。
8
日志记了一堆，但没有告警
日志入 ES 存着，没有任何规则；WAF 拦截记录没人看。日志的价值在告警闭环，不在归档。批量导出、登录异常、越权拒绝必须告警。
9
SSRF 只防了第一跳
校验了初始 URL，但服务端跟随 302 跳到内网、域名重绑定、gopher 协议走私全部没防。四件套：scheme 白名单 + IP 校验 + 用 IP 直连 + 重定向管控。
10
把 Top 10 当一次性 checklist
测评/上线前打一遍勾，之后新人不知道这回事，新模块不威胁建模。Top 10 要进设计评审模板、进新人培训、进 CI 门禁。
自测

六道题

1. 登录用户 A 把订单接口 URL 里的 1001 改成 1002，看到了 B 的订单。这属于哪类问题？
正确答案：A01 失效的访问控制。典型 IDOR：服务端校验了"登录没"（A07 范畴），但没校验"资源归属"。修复是在查询条件里强制绑定当前用户 ID，并让每个服务自己做授权、不依赖前端和网关。
2. 关于 JWT，下面哪个说法是对的？
正确答案：payload 谁都能看。JWT 是签名（防篡改）不是加密（防偷看）。另外签发后到过期前确实难以吊销，所以工程上用短过期 + 刷新令牌 + 黑名单（登出/改密场景）组合，而不是"永久有效"。
3. 防御 SQL 注入最可靠的方式是？
正确答案：参数化 + 白名单。黑名单可被大小写/注释/编码/宽字节变形绕过；WAF 是争取时间的补丁，规则永远滞后于新变形。数据与代码分离才是根治。
4. 某应用的"图片 URL 导入"功能，用户填任意 URL 服务端就去抓取。最大的风险是？
正确答案：SSRF。服务端代发请求让攻击者能扫内网、读元数据拿云临时凭据（AWS Capital One 事件路径）、用 gopher 打内网服务。防护四件套：scheme 白名单、解析后 IP 校验、用 IP 直连、管控重定向。
5. 密码在数据库里应该怎么存？
正确答案：bcrypt/argon2。慢哈希让离线爆破成本指数级上升，盐抗彩虹表，成本因子可随硬件提升。AES 可逆，密钥一泄全完；MD5 太快，GPU 下形同明文。
6. 2021 版 OWASP Top 10 排名第一的风险是？
正确答案：A01 失效的访问控制。它从 2017 版的第 5 升至第 1，34 个 CWE 归入此类，是真实世界出现频率最高的类别。注入降到第 3；"敏感数据泄露"在 2021 版更名为"加密失败"并降为第 2。
