二十分钟学透安全测试

SAST、DAST、IAST、SCA、Fuzzing 不是五个名词，是五道位置不同的防线。这篇讲清每道防线查什么、查不到什么，以及怎么在 CI 里组成门禁而不被误报淹没。

开始前

先把工具跑起来

本篇所有命令以工具当前官方文档为准。先用 Docker 把扫描器准备好，不用装一堆环境。

# ===== SAST：Semgrep（规则即代码，速度快，CI 友好） =====
pip install semgrep
semgrep --config=auto .                    # 用官方规则集扫当前目录
semgrep --config=p/security-audit .        # 安全审计规则集
semgrep --config=/path/to/your-rules.yml . # 自定义规则

# ===== SCA：Trivy 扫依赖漏洞（也扫镜像、IaC） =====
trivy fs --scanners vuln,secret,misconfig .
trivy image --severity HIGH,CRITICAL myapp:latest

# ===== DAST：OWASP ZAP（官方稳定镜像） =====
docker run -t zaproxy/zap-stable zap-baseline.py -t https://your-test-site.com
docker run -t zaproxy/zap-stable zap-api-scan.py -f openapi -t https://api.site/openapi.json

# ===== Fuzzing：libFuzzer（编译时插桩） =====
clang++ -fsanitize=fuzzer,address -g fuzz_target.cc -o fuzz_target
./fuzz_target -max_total_time=60            # 跑 60 秒模糊测试
纪律：DAST 和渗透测试只能扫你有书面授权的目标。扫自己的测试环境没问题；扫生产、扫第三方站点、扫不属于你的系统，先拿到授权（scope 文档），否则就是未授权测试，法律风险自负。
模块 1

左移理念与测试金字塔

安全左移（Shift Left）的核心思想：把安全测试尽量前移到开发阶段，让问题在最近的环节被发现。原因和模块 1 在威胁建模里讲过的一样——修复成本随阶段指数上升。

阶段手段成本反馈速度
编码时IDE 插件（Semgrep/CodeQL 本地规则）、pre-commit最低秒级
提交时SAST、SCA、密钥扫描、pre-commit hook低分钟级
合并后CI 全量 SAST/SCA + 安全门禁中十分钟级
测试环境DAST 基线扫描、IAST、Fuzzing较高小时级
上线前/后渗透测试、众测、红队最高周级
金字塔结构：底端是"快而窄"的 SAST/SCA（每次提交都跑），中间是 DAST/IAST（每次部署到测试环境跑），顶端是"慢而深"的渗透测试（每季度/大版本一次）。不要试图用 DAST 替代 SAST，也不要指望渗透测试兜住所有问题——它们的位置不同，覆盖的漏洞类型不同。
SAST 查什么
代码模式漏洞：注入、硬编码密钥、不安全反序列化、弱加密。不需要运行程序
DAST 查什么
运行时漏洞：暴露的接口、错误配置、认证缺陷、注入。站在黑盒视角打运行中的应用
SCA 查什么
你用的库有没有已知 CVE、license 风险、是否有恶意投毒包
IAST 查什么
运行中插桩监控数据流：能同时看到代码行和请求上下文，误报率最低
模块 2

SAST：静态应用安全测试

不运行程序，直接分析源代码/字节码，按规则或数据流模式找漏洞。

工具特点适用
Semgrep规则即 YAML，模式匹配 + 轻量数据流；速度快（万行秒级）；规则社区丰富CI 门禁首选，支持 30+ 语言
CodeQL把代码转成可查询数据库，用类 SQL 语法写深度数据流分析；能追踪跨函数污点复杂污点分析、0day 挖掘；GitHub 仓库免费
SonarQube质量 + 安全一体（代码异味、重复、漏洞）；商业版规则更多已有 Sonar 平台的团队直接加安全规则

Semgrep 自定义规则示例

# rules/no-hardcoded-secret.yml —— 禁止硬编码密钥
rules:
  - id: hardcoded-aws-key
    patterns:
      - pattern-regex: 'AKIA[0-9A-Z]{16}'      # 匹配 AWS Access Key ID 格式
    message: 疑似硬编码 AWS Access Key，应改用环境变量或密钥管理服务
    languages: [generic]
    severity: ERROR
    metadata:
      category: security
      owasp: "A07:2021"                          # 映射 OWASP 分类
      cwe: "CWE-798"

  - id: sql-string-concat
    patterns:
      - pattern-either:
          - pattern: cursor.execute(f"..." + $X)
          - pattern: cursor.execute("SELECT * FROM t WHERE id = " + $X)
    message: SQL 语句字符串拼接，存在注入风险，使用参数化查询
    languages: [python]
    severity: ERROR
    fix: cursor.execute("SELECT * FROM t WHERE id = ?", ($X,))   # 自动修复建议

# 运行
semgrep --config rules/ --error            # 有 ERROR 级发现就退出码非 0，CI 可据此失败

CodeQL 查询示例（Python 命令注入）

// ql/python/command-injection.ql —— 简化示意
import python
import semmle.python.dataflow.TaintTracking

from DataFlow::Node source, DataFlow::Node sink
where
  source instanceof RemoteFlowSource and        // 污点源：HTTP 请求参数
  sink = any(SystemCommandExecution cmd).getAnArgument()  // 污点汇：系统命令执行
select sink, "用户输入未经处理进入系统命令执行"

误报治理：SAST 的生死线

  • 分层规则：ERROR（门禁阻断：SQL 注入、硬编码密钥）/ WARN（不阻断但建单：弱随机数、可疑正则）/ INFO（不报）
  • 基线（baseline）：存量问题先全量记录为基线，门禁只查新增问题（Semgrep 的 --baseline-commit、Sonar 的 New Code 周期），否则第一次上门禁就几百个历史问题，团队直接关掉扫描
  • 误报闭环：每条 suppression（# nosemgrep）必须写理由 + 关联 issue；定期（如每季度）复审 suppression 列表
  • 指标：跟踪"新增问题数 / 千行代码、误报率、平均修复时长（MTTR）"，而不是"扫描器报了多少个"
SAST 的能力边界：它看不懂业务逻辑——"这个接口有没有鉴权""价格能不能改"它永远查不出来；它也不理解框架的"魔法"（动态代理、依赖注入配置错时可能漏报或误报）。SAST 是必要非充分条件。
模块 3

DAST：动态应用安全测试

黑盒视角：把应用跑起来，像攻击者一样发请求，从响应和状态变化判断漏洞。

工具特点与定位
OWASP ZAP开源，自动化脚本丰富（zap-baseline / zap-api-scan / zap-full-scan）。CI 集成首选
Burp Suite交互式测试的事实标准（Professional 版带主动扫描器）。适合人工渗透、业务逻辑测试
# ===== ZAP 三种扫描模式 =====
# 1. 基线扫描：只爬被动观察，不发攻击 payload。几分钟，CI 里每次部署都跑
docker run -t zaproxy/zap-stable zap-baseline.py \
  -t https://staging.site.com -r report.html

# 2. API 扫描：基于 OpenAPI/Swagger 文档逐接口测
docker run -t zaproxy/zap-stable zap-api-scan.py \
  -t https://staging.site.com/openapi.json \
  -f openapi -r api-report.html

# 3. 全量扫描：基线 + 主动攻击（会真的发包打点）。耗时几十分钟，定期跑
docker run -t zaproxy/zap-stable zap-full-scan.py \
  -t https://staging.site.com -r full-report.html

# 认证态扫描：带着登录 session 扫需要登录的接口（最容易踩坑的点）
docker run -t zaproxy/zap-stable zap-baseline.py \
  -t https://staging.site.com \
  --zapit-config='{"authentication":{"loginUrl":"https://staging.site.com/login",'\
'"loggedInRegex":"\\u002b\\u002b","username":"test@corp.com","password":"..."}}'

认证态扫描的四个难点

① 登录态怎么拿。表单登录（用户名密码 POST）、OAuth 设备码、SSO 重定向——每种流程 ZAP 的自动化脚本写法都不同。最稳妥的是预先在外部脚本里登录，把 cookie/JWT 注入 ZAP 的 context，别让扫描器自己猜登录流程。
② 登录态会过期。扫描跑 30 分钟，session 15 分钟失效，后半程全是"未授权 302 跳转"的噪音。要么调大 session TTL，要么让扫描器带重新登录脚本（ZAP 的 authentication script + session management）。
③ 副作用不可控。主动扫描会真的发 payload：可能创建一堆脏订单、触发真实短信/邮件、把测试数据写乱。扫专用测试环境 + 用测试账号 + 提前清理数据；涉及资金/消息的接口加扫描豁免清单。
④ 爬不深的动态界面。SPA/重度前端渲染的页面，爬虫抓不到接口。解法：提供 OpenAPI 文档走 zap-api-scan，或用 Burp 录一段操作导出 HAR/站点地图喂给 ZAP。
DAST 的定位：它擅长发现"暴露面"问题（未授权接口、错误配置、缺失的安全响应头、反射型注入），不擅长存储型注入的完整利用、业务逻辑漏洞（越权、价格篡改）、多步骤攻击链。DAST 通过 ≠ 安全，只说明"已知模式没命中"。
模块 4

IAST 与 RASP：运行时互补

技术原理特点
IAST
交互式应用安全测试		以 Agent 形式插桩到运行中的应用内部（JVM/CLR/Node），监控真实请求流经的代码路径和数据流测试阶段触发。准确率最高：直接看到"这个 HTTP 参数流进了 SQL 执行"，误报远低于 SAST/DAST
RASP
运行时应用自我保护		同样插桩在应用内，但部署在生产环境，发现攻击行为时在运行时直接阻断（抛异常/返回 403）生产防护。相当于一个贴着业务的 WAF，能理解业务上下文（知道哪个参数是订单 ID）
三者的互补关系：SAST 在编码期"读代码找模式"，DAST 在外部"发请求看响应"，IAST 在测试期"看真实数据流"，RASP 在生产"实时阻断"。覆盖矩阵上没有重叠浪费：IAST 发现的注入带完整代码行栈，直接甩给开发修；RASP 挡住的攻击产生告警，反哺 IAST/DAST 的规则。

选型建议

  • Java 技术栈：IAST/RASP 生态最成熟（商业产品多，开源有 OpenRASP 系方案）
  • 容器化/K8s 环境：注意 Agent 注入方式（sidecar / initContainer 修改启动参数）对启动耗时和镜像大小的影响
  • Serverless / 多语言小团队：RASP 收益/成本比下降，优先把 SAST/SCA 门禁做好
模块 5

SCA 依赖扫描与供应链

现代应用 60%~80% 的代码来自开源依赖。你的代码没问题，依赖有 CVE 一样出事——这就是 SCA（软件成分分析）和供应链安全要解决的问题（与 supply-chain 专题互为呼应）。

# ===== 各生态的 SCA 命令 =====
# Node：npm 官方审计
npm audit --audit-level=high
npm audit fix                      # 自动升级兼容版本（慎用 major 升级）

# Python
pip-audit                          # 基于 PyPI 安全公告数据库

# Go
govulncheck ./...                  # 官方工具，直接分析你的代码实际调用了哪些有漏洞的函数

# 通用：Trivy（扫依赖 + 镜像 + IaC + 密钥）
trivy fs --severity HIGH,CRITICAL --exit-code 1 .   # 有高危漏洞则退出码 1，CI 可阻断
trivy image --ignore-unfixed redis:7-alpine         # 忽略暂无修复版本的漏洞

# SBOM：软件物料清单，出事时能回答"我们到底用了什么"
syft packages myapp:latest -o cyclonedx-json > sbom.json

SCA 结果分四类处理

类型判断依据处理
可直接修有修复版本，且 semver 兼容升级提 PR 升级，跑回归测试
升级破坏兼容修复版本是 major 升级，API 变了排期迁移；期间评估可达性：漏洞函数你真调用了吗
无修复版本CVE 已公开但 upstream 没发补丁找 workaround（配置规避、升级大版本、虚拟补丁 WAF 规则）
不可达/不适用代码路径根本没调用漏洞函数（govulncheck 能精确判断）记录豁免理由，纳入复审
别只看 CVE 严重分。CVSS 9.8 的漏洞如果你的代码永远不碰那条路径，实际风险约等于零；反过来 CVSS 5.0 的漏洞在你核心链路上被公开利用（KEV 目录收录），就是红色警报。把 CISA KEV（已知被利用漏洞目录）接入你的 SCA 门禁优先级排序。
模块 6

Fuzzing 模糊测试

给程序喂大量"畸形但结构合法"的输入，观察崩溃/挂起/内存错误。特别适合解析器、协议实现、编解码库这类"输入空间巨大"的代码。

工具定位
AFL++经典覆盖率引导 fuzzer，C/C++ 生态为主，需编译插桩或 QEMU 模式
libFuzzerLLVM 内置，写一个 LLVMFuzzerTestOneInput 入口函数即可，与 Sanitizer（ASan/UBSan）配合是标配
OSS-FuzzGoogle 的持续 fuzzing 基础设施，开源项目可申请接入，7×24 自动跑
go-fuzz / cargo-fuzzGo / Rust 生态对应方案
// fuzz_parser.cc —— libFuzzer + AddressSanitizer 的 harness 骨架
#include <stdint.h>
#include <stddef.h>
#include <string>

extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
  if (size == 0) return 0;
  std::string input(reinterpret_cast<const char*>(data), size);
  // 调用被测函数：比如你的 JSON / protobuf / 自定义协议解析器
  MyParser::Parse(input);          // 不关心返回值，只关心它会不会崩
  return 0;
}

# 编译（ASan + UBSan 双 Sanitizer，发现即报错）
clang++ -fsanitize=fuzzer,address,undefined -g fuzz_parser.cc my_parser.cc -o fuzz_parser

# 跑 5 分钟，语料库放 corpus/ 目录，崩溃样本自动存 crash-* 文件
mkdir -p corpus && ./fuzz_parser corpus/ -max_total_time=300 -rss_limit_mb=2048

把 Fuzzing 接进 CI

  • nightly 构建：每次跑 30~60 分钟（fuzzing 是概率游戏，短跑收益有限）
  • 语料库持久化：把 corpus/ 存为 CI artifact，覆盖率只增不减
  • 崩溃即失败：crash 样本自动转 issue，附最小复现输入（libFuzzer 自带 minimize）
  • 公开接口慎跑：只 fuzz 自己的库/服务，别拿生产接口当靶子
模块 7

渗透测试与 CI 安全门禁

自动化测试覆盖"已知模式"，渗透测试回答"有没有人真的能打穿"。两者是互补关系，不是替代关系。

渗透测试与自动化怎么结合

环节自动化人工渗透
资产发现子域名枚举、端口扫描、指纹识别识别影子 IT、被遗忘的老系统
漏洞发现SAST/DAST/SCA 批量扫业务逻辑漏洞、多步攻击链、授权绕过
漏洞验证PoC 模板化复现评估真实影响（能拖多少库、影响多少用户）
修复验证回归扫描确认告警消失复测攻击路径是否真的堵死（还是只是被 WAF 挡了）

CI 安全门禁设计（GitHub Actions 示例）

# .github/workflows/security.yml —— 示意，具体 action 版本以官方为准
name: Security Gate
on: [push, pull_request]

jobs:
  sast:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: {fetch-depth: 0}          # 拉全历史，baseline 对比用
      - name: Semgrep
        run: |
          pip install semgrep
          semgrep ci --baseline=${{ github.event_name == 'pull_request' && 'origin/main' || 'HEAD~1' }}
          # PR 对比主干只报新增问题；push 报全量

  sca:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Trivy dependency scan
        run: trivy fs --severity HIGH,CRITICAL --ignore-unfixed --exit-code 1 .

  dast:
    needs: [sast, sca]
    if: github.ref == 'refs/heads/main'
    steps:
      - name: Deploy to staging & ZAP baseline
        run: |
          ./deploy-staging.sh
          docker run -t zaproxy/zap-stable zap-baseline.py \
            -t https://staging.site.com -I   # -I：不报告 WARN 级以下，只 FAIL HIGH

门禁阈值设计原则

  • 只对"新增"生效：历史存量记基线，新代码引入高危直接 FAIL——避免"修不完的旧账"逼团队关掉 CI
  • 分级阻断：CRITICAL/ERROR 阻断合并；HIGH/WARN 建单不阻断；INFO 只统计
  • 豁免有期限：豁免必须带到期日（如 30 天），到期自动重开 issue，防止"临时豁免"变"永久后门"
  • 门禁也要 SLA：扫描时间控制在 10 分钟内，超过 15 分钟开发者就会开始反感、找绕过手段
  • 误报申诉通道：开发者能一键申诉"这是误报"，安全团队 48 小时内裁决——没有申诉通道的门禁迟早被敌视
一条务实的演进路线：第 1 个月只上 SCA 密钥扫描（发现真实密钥泄露，见效最快）→ 第 2 个月 SAST 上 ERROR 级新增阻断 → 第 3 个月 DAST 基线扫描进 nightly → 稳定后再谈 IAST/RASP。不要第一天就上五层门禁，那是逼团队绕过你。
模块 8

十个常见坑

1
把扫描器当银弹
以为 CI 里挂了 SAST+DAST+SCA 就安全了。扫描器只认已知模式：业务逻辑漏洞、设计缺陷、0day 一个都发现不了。扫描通过 ≠ 没有漏洞。
2
误报疲劳，最后全员关扫描
第一周门禁报了 500 个"问题"，其中 480 个是测试目录里的示例代码。开发者从此学会给 CI 加 [skip ci]。解法：baseline 基线 + 分级阻断 + 申诉通道。
3
只扫不修
扫描报告很漂亮：本周发现 87 个漏洞，历史累计 1200 个。但没有 owner、没有排期、没有 SLA。漏洞是队列不是统计数字——跟踪 MTTR（平均修复时长）和"高危超过 30 天未修的数量"。
4
DAST 扫生产环境
主动扫描 payload 打到生产：脏数据、真实短信、甚至把服务扫挂。永远扫测试环境；实在要扫生产，走只读模式 + 维护窗口 + 书面授权。
5
DAST 不带认证态，扫了一堆 302
扫描器以匿名用户爬完站点，所有需要登录的接口根本没测到，报告一片绿却毫无意义。认证态注入 + 重登录脚本是 DAST 生效的前提。
6
SCA 只看 CVSS 分，不看可达性
CVSS 9.8 的漏洞在根本没调用的代码路径里，兴师动众升级 major 版本搞出兼容性事故。先用可达性分析（govulncheck、CodeQL）筛一遍再排优先级。
7
Fuzzing 跑 30 秒就下结论
"跑了没崩溃，我们的解析器很稳"。覆盖率引导 fuzzing 是长跑游戏， meaningful 的收益以小时/天计。要么跑够时长，要么接入 OSS-Fuzz 类持续基础设施。
8
门禁太严，开发者集体绕过
规则全设 ERROR，注释掉代码比写 suppress 理由还容易，结果 nosemgrep 满天飞，每条理由都是"误报"。门禁的通过率应该是个渐进优化的曲线，不是断头台。
9
渗透测试报告收进抽屉
一年一次的渗透测试，报告 PDF 存共享盘，没人认领修复。每份报告的高危项必须转成工单、有 owner 和 deadline，修完要复测签字。
10
安全测试只有安全团队在跑
开发觉得"安全是安全团队的事"，PR 里明知有拼接 SQL 也不改，因为"扫描器会报，报了有人管"。安全是质量属性：门禁 + 培训 + 把安全检查项放进 Definition of Done，让开发自己对 PR 的安全负责。
自测

六道题

1. 关于 SAST 和 DAST 的区别，哪个说法是对的？
正确答案：SAST 静态分析代码，DAST 黑盒打运行中的应用。两者覆盖的漏洞类型不同（SAST 查注入模式、硬编码密钥；DAST 查配置、认证、暴露面），是互补关系。SAST 读不懂业务逻辑，替代不了人工测试。
2. 为什么 IAST 的误报率通常远低于 SAST 和 DAST？
正确答案：IAST 在应用内部观察真实数据流。它能确定"这个 HTTP 参数确实流进了 SQL 执行器"，而 SAST 只能猜"这个字符串可能进了 SQL"，DAST 只能看"响应有点异常"。有上下文判断，误报自然少。
3. 团队第一次在 CI 上 SAST 门禁，一次报了 300 个存量问题，正确的处理方式是？
正确答案：建基线，只阻断新增。存量问题按风险排期分批修。一次全阻断只会逼团队给 CI 加 [skip ci] 或滥用 suppression——门禁的可信度一旦破产，重建成本极高。
4. DAST 扫描一个需要登录的站点，结果 80% 的响应是 302 跳转到登录页，最可能的原因和解法是？
正确答案：没有认证态。扫描器以匿名身份爬站，所有受保护接口根本没测到。解法：外部脚本预登录拿 cookie/JWT 注入 ZAP context，并配置自动重登录机制防止扫描中途 session 过期。
5. SCA 扫出一个 CVSS 9.8 的高危 CVE，但你用可达性分析发现项目根本没调用那个漏洞函数。正确的处理是？
正确答案：记录不可达豁免 + 复审。CVSS 是通用评分，不等于你的实际风险。可达性分析（govulncheck 等）能精确判断代码是否触达漏洞路径。但豁免要写理由并定期复审——代码演进后可能变得可达。
6. 关于 Fuzzing，哪种做法是正确的？
正确答案：配合 Sanitizer + 长跑 + 语料库持久化 + 崩溃闭环。Fuzzing 是概率游戏，短跑收益有限；打生产接口既是法律风险也是稳定性风险。崩溃样本要最小化复现并转成工单，否则等于白跑。
