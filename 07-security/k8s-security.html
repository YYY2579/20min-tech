开始前

先想清楚容器改变了什么

容器把"一台服务器跑一个应用"变成了"一台服务器跑几十个共享内核的应用"。隔离边界从硬件级降到了内核命名空间 + cgroup级 —— 这就是所有容器安全问题的根源。

维度虚拟机容器
隔离边界硬件虚拟化（Intel VT-x）共享宿主机内核，靠 namespace/cgroup/seccomp 隔离
逃逸代价需要 hypervisor 漏洞内核漏洞 / 配置错误即可，成本低得多
攻击面Guest OS 全套单个应用 + 运行时（runc/containerd）+ 内核
爆炸半径通常限于一台 VM同节点所有 Pod + 宿主机 + 集群凭证
本文靶场纪律：下面所有"逃逸演示"只用来说明机制，请在你自己机器上的 kind/minikube 里做。任何对共享集群的未授权测试都可能违反公司政策与法律。
模块 1

容器安全四层模型

层核心风险关键控制
镜像基础镜像带高危 CVE、镜像以 root 跑、镜像里烘焙密钥、镜像来源不可信最小化（distroless/alpine）、非 root、扫描（Trivy/Grype）、签名（cosign）、无密钥烘焙
运行时特权容器、capabilities 过多、可写根文件系统、逃逸漏洞（runc/containerd CVE）securityContext 硬化、seccomp/AppArmor、只读根文件系统、及时打补丁
集群etcd 明文、API server 暴露、RBAC 过宽、扁平网络、Secret 无加密RBAC 最小权限、etcd EncryptionConfiguration、私有 API server、NetworkPolicy、mTLS
供应链被篡改的镜像、带毒的基础镜像、不受控的镜像来源、构建流水线投毒镜像签名 + 验签准入、来源白名单（受信 registry）、CI/CD 加固、SBOM
四层是串联的：任何一层失守都会把风险传导给下一层 —— 镜像里的漏洞给了初始立足点，运行时的宽松配置给了逃逸机会，集群的宽 RBAC 把单 Pod 失守放大成集群失守，供应链没签名则连"失守的是哪个镜像"都查不清。纵深防御的每一层都在缩小爆炸半径。
模块 2

镜像安全：最小化是主线

1. 基础镜像选型

方案体积取舍
ubuntu:22.04约 78MBglibc 兼容性好，但 CVE 数量多，需要持续打补丁
alpine:3.20约 7.8MB极小、CVE 少；但 musl libc 与 glibc 有兼容差异（DNS、部分二进制），Java/Node 生态要实测
distroless约 2~20MB没有 shell、没有包管理器，攻击者拿到 shell 也干不了大事；Go/静态二进制首选
scratch0完全空镜像，只放静态二进制；连 ca-certificates 都要自己 COPY

2. 非 root 运行

# ✗ 默认以 root 跑 —— 容器内 root 加上逃逸就是宿主机 root
FROM ubuntu:22.04
COPY app /app
ENTRYPOINT ["/app"]

# ✓ 多阶段构建 + 静态编译 + distroless + 非 root 用户
FROM golang:1.22 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o /out/app ./cmd/server

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/app /app
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/app"]
非 root 的两个前置条件：① 应用不监听 1024 以下端口（要监听 80 就用 8080 + 容器端口映射，或用 capabilities: add: ["NET_BIND_SERVICE"] 精细授权）；② 数据目录提前 chown 或挂 emptyDir + fsGroup。满足不了这两条，"非 root"会在半夜被运维改回 root。

3. 构建卫生

  • .dockerignore：把 .git、*.pem、.env、node_modules 挡在构建上下文外 —— 防止密钥被打进镜像层
  • 多阶段构建：编译器、源码、依赖缓存留在 build stage，最终镜像只有产物
  • 禁止镜像内存密钥：任何进过镜像层的东西都能被 docker history / docker save 翻出来，密钥只能运行时注入（K8s Secret / Vault / KMS）
  • 镜像标签用 digest：image: registry/app:v1.2.3@sha256:abc...，不用 latest —— 保证运行的就是审计过的那个镜像

4. 扫描（CI 里跑，不是上线后补）

# Trivy：扫 OS 包 + 语言依赖 + 密钥泄漏，高危直接失败
trivy image --exit-code 1 --severity HIGH,CRITICAL \
  --ignore-unfixed registry.example.com/app:v1.2.3

# 扫 IaC 和集群配置
trivy config ./k8s-manifests/
trivy k8s --report summary cluster

# 生成 SBOM（软件物料清单），出事时能回答"我用了哪些组件"
trivy image --format spdx-json --output sbom.json registry.example.com/app:v1.2.3

# 密钥泄漏检测
trivy image --scanners secret --exit-code 1 registry.example.com/app:v1.2.3
模块 3

Pod 安全：securityContext 全字段

Pod 级 securityContext

字段作用
runAsNonRoot: true强制容器不能以 root 启动（镜像指定了 USER 0 会直接启动失败）
runAsUser: 10001指定 UID。建议 ≥ 10000，避开常见系统 UID 段
runAsGroup: 10001指定 GID
fsGroup: 10001挂载卷的文件属组，解决非 root 写 PVC 的问题
seccompProfile.type: RuntimeDefault启用运行时默认系统调用过滤（PSS restricted 的硬性要求）

容器级 securityContext

字段作用
allowPrivilegeEscalation: false禁止 setuid/setcap 提权（如 sudo、ping 提权链），性价比最高的一行
readOnlyRootFilesystem: true根文件系统只读。落盘路径用 emptyDir/tmpfs 显式挂载
capabilities.drop: ["ALL"]丢掉全部 Linux capabilities；需要哪个加哪个（如 NET_BIND_SERVICE）
privileged: true灾难开关：等价于宿主机 root，永远不要在生产用
procMount: Default防止容器把 /proc 重新挂成可写

seccomp 与 AppArmor

  • seccomp：按系统调用号过滤。RuntimeDefault profile 由容器运行时提供，挡住大多数逃逸所需的危险调用。自定义 profile 放节点 /var/lib/kubelet/seccomp/profiles/，用 seccompProfile.type: Localhost 引用
  • AppArmor：基于路径的强制访问控制，限制文件访问。K8s 里用注解加载：
metadata:
  annotations:
    container.apparmor.security.beta.kubernetes.io/app: runtime/default

Pod Security Standards（PSS）：内置的三档基线

档位定位核心要求
privileged不限制（基础设施组件用）无限制
baseline阻断已知提权手段禁 privileged、禁 hostPID/hostIPC/hostNetwork、禁大部分 hostPath、禁危险 capabilities、禁 procMount
restricted生产默认目标baseline 全部 + runAsNonRoot + seccomp RuntimeDefault + drop ALL capabilities + allowPrivilegeEscalation: false
# 在 namespace 上打标签启用（三种模式可叠加）
kubectl label ns production \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/enforce-version=latest \
  pod-security.kubernetes.io/audit=restricted \
  pod-security.kubernetes.io/warn=restricted

# enforce = 违规 Pod 拒绝创建
# audit   = 放行但记录审计事件
# warn    = 放行但给 kubectl 警告
# 升级路径：先 audit/warn 跑一周看存量违规，再切 enforce
落地顺序：① 全集群所有 namespace 先打 audit=restricted, warn=restricted，跑一周收集违规清单；② 按清单逐批修（改 securityContext、加 emptyDir 挂载、去掉特权）；③ 存量清零后切 enforce=restricted，只给真正需要的系统 namespace（kube-system 等）留 baseline/privileged。
模块 4

K8s 集群安全

1. RBAC：最小权限，默认拒绝

# ✗ 常见事故写法：给默认 SA 或整个团队绑了 edit/cluster-admin
kubectl create clusterrolebinding team-admin --clusterrole=edit --group=dev-team

# ✓ 按 namespace 的最小 Role（get/list/watch，不绑 create/delete）
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: production
  name: pod-viewer
rules:
  - apiGroups: [""]
    resources: ["pods", "pods/log"]
    verbs: ["get", "list", "watch"]        # 只读，没有 exec —— exec 等于进容器
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: production
  name: pod-viewer-binding
subjects:
  - kind: User
    name: alice@example.com
roleRef:
  kind: Role
  name: pod-viewer
  apiGroup: rbac.authorization.k8s.io
  • 高危 verbs 要审批：pods/exec（进容器）、pods/attach、secrets 读、create pods（可挂 hostPath 造特权 Pod）—— 这四类权限等于集群控制权
  • ServiceAccount 收紧：默认 SA 不绑任何 Role；应用 SA 加 automountServiceAccountToken: false，Pod 内就不该有 token 可偷
  • 定期审计：kubectl auth can-i --list --as=system:serviceaccount:ns:sa 逐个查权限，清理历史遗留的宽绑定

2. etcd：加密 + 访问控制

# etcd 是集群的唯一事实来源 —— Secret、证书、全在里面
# 访问控制：只允许 API server 节点访问 etcd（防火墙/安全组 2379/2380）
# 静态加密：API server 加 --encryption-provider-config
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets                # 加密 Secret，也可加 configmaps
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <BASE64_ENCODED_32_BYTE_KEY>
      - identity: {}           # identity 必须留最后，保证能读未加密旧数据
没有 EncryptionConfiguration 时，etcd 里的 Secret 是明文的。能读到 etcd 备份/磁盘的人等于拿到集群全部密钥。更稳妥的是 KMS 方案（Vault / 云 KMS provider），密钥不进节点磁盘，还支持轮换。

3. Secret：base64 不是加密

# 这是编码，不是加密 —— 任何能进 Pod 的人都能解开
kubectl get secret db-creds -o jsonpath='{.data.password}' | base64 -d

# 加固组合：
# 1) etcd 静态加密（上面）
# 2) RBAC 限制 secrets 的 get/list
# 3) 外部密钥管理：External Secrets Operator / Vault Agent 注入
#    —— Secret 不落 K8s，Pod 启动时从 Vault 拉，支持动态凭据和自动轮换
# 4) 应用侧：不要把 Secret 打进日志、错误页、环境变量（env 会出现在 describe 输出里）

4. API server 与网络

控制做法
API server 不暴露公网内网地址 + 办公网/VPN 白名单；--anonymous-auth=false 禁匿名
NetworkPolicy默认拒绝 + 按需放行（见下方 YAML）。没开 NP 的集群是扁平网络：一个 Pod 被攻破，所有服务可直连
控制平面加固kube-bench（CIS Benchmark）跑分；etcd/API server 通信走 TLS； admission webhook 开启
节点加固SSH 禁用密码登录、最小化节点软件、自动安全更新、CIS 基线
# NetworkPolicy：默认拒绝一切，再逐条放行
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}          # 选中 namespace 全部 Pod
  policyTypes: ["Ingress", "Egress"]   # 进出都默认拒
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-api
  namespace: production
spec:
  podSelector:
    matchLabels: {app: api}          # 目标：api Pod
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels: {app: frontend}   # 只允许同 namespace 的 frontend 进
        - namespaceSelector:
            matchLabels: {kubernetes.io/metadata.name: monitoring}  # 允许监控 namespace
      ports:
        - protocol: TCP
          port: 8080
NetworkPolicy 的前提：CNI 插件支持。flannel 不支持，Calico/Cilium/Weave 支持。很多集群"配了 NP 不生效"，八成是 CNI 的锅。验证方式：kubectl run test --rm -it --image=busybox -- wget -qO- --timeout=2 http://api-svc:8080，默认拒绝下应该超时。
模块 5

逃逸风险与防范

三条最常见的"人造逃逸通道"

配置后果正确做法
privileged: true容器进程≈宿主机 root：可挂载宿主块设备、改内核参数、访问所有设备删掉。确有特权需求用白名单 capabilities 逐项授
挂载 /var/run/docker.sock通过 Docker API 创建挂载宿主机 / 的容器 = 宿主机沦陷；等价于给 root永远不挂。要用容器能力改用 rootless 构建（Kaniko/BuildKit）或无守护进程方案
hostPID / hostNetwork / hostIPC看到宿主机全部进程/网络/共享内存；hostPID 下可操作宿主机进程、读宿主 /proc 里的密钥默认 false；监控/网络组件确有需求时单独 Pod 开，单独 namespace + NP 隔离

内核态逃逸：真实 CVE 时间线

CVE组件机制
CVE-2019-5736runc恶意镜像让容器内进程在 exec 时覆盖宿主 runc 二进制，下次容器启动执行恶意代码。影响 runc 1.0-rc6 之前版本
CVE-2020-15257containerd宿主机抽象 unix socket 未隔离，容器内可访问 hostNetwork 上的 containerd socket 而绕过权限
CVE-2022-0492Linux cgroup v1容器内可写 cgroup release_agent，让内核在 cgroup 释放时执行宿主机上的任意程序
CVE-2024-21626runc（Leaky Vessels）process.cwd 文件描述符泄漏到容器内，配合可写工作目录实现逃逸
这些 CVE 的共同前提：攻击者已经能在容器内执行代码。所以防逃逸的本质是分层假设失守：第一层（镜像最小化 + 非 root + 只读根fs）让他进不来；第二层（seccomp + capabilities 限制 + 不挂宿主 socket）让他动不了宿主；第三层（及时升级 runc/containerd/内核）把已知门焊死。任何一层单独都不够。

纵深防御配置（容器级）

# 防逃逸的四件套（任缺一件，爆炸半径就从 Pod 扩大到宿主机）
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  allowPrivilegeEscalation: false      # 断了 setuid 提权
  readOnlyRootFilesystem: true         # 断了落盘写 payload
  capabilities:
    drop: ["ALL"]                      # 断了 CAP_SYS_ADMIN 等危险权能
  seccompProfile:
    type: RuntimeDefault               # 断了危险系统调用（如 keyctl、unshare）
volumes:                                # 无 hostPath / 无 docker.sock
  - name: tmp
    emptyDir: {}                       # 要写只能写这里，容器销毁即消失

逃逸后能干什么（为什么不能只防"进容器"）

  • Pod 里的 ServiceAccount token（默认挂载在 /var/run/secrets/kubernetes.io/serviceaccount/）→ 调 API server → 按 SA 权限偷 Secret、建 Pod
  • 节点上的 kubelet 凭证、云实例元数据 → 拿临时云凭证 → 横向移动到控制平面
  • 同节点其他 Pod 的本地共享目录（emptyDir 不跨 Pod，但 hostPath 会）
自检命令：进自己的 Pod 跑一遍 cat /var/run/secrets/kubernetes.io/serviceaccount/token | head -c 20。有输出就说明 automountServiceAccountToken 没关 —— 这个 token 在容器里躺平，等着被偷。
模块 6

供应链：签名与准入

镜像签名（cosign + Sigstore）

# 1. 生成密钥对（私钥进 CI 保密系统，公钥进集群）
cosign generate-key-pair

# 2. CI 构建后签名（私钥由 CI 的 KMS/保密变量提供）
cosign sign --key cosign.key registry.example.com/app:v1.2.3

# 3. 发布方提供 attestation（构建来源证明）
cosign attest --key cosign.key --type slsaprovenance registry.example.com/app:v1.2.3

# 4. 集群侧验签（准入控制器自动完成，下面 Kyverno 示例）
cosign verify --key cosign.pub registry.example.com/app:v1.2.3

准入控制器：把"只能跑受信镜像"变成强制

两类主流方案：Kyverno（纯 YAML 策略，上手快）和 OPA Gatekeeper（用 Rego 语言，表达力强）。下面用 Kyverno 演示最常见的三条策略。

# 策略一：只允许受信 registry 的镜像，且必须带 digest
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-image-registries
spec:
  validationFailureAction: Enforce        # Enforce=拒绝，Audit=只记录
  background: true
  rules:
    - name: validate-registries
      match:
        any:
          - resources:
              kinds: ["Pod"]
      validate:
        message: "镜像必须来自 registry.example.com 且带 sha256 digest"
        pattern:
          spec:
            containers:
              - image: "registry.example.com/*@sha256:*"

# 策略二：强制镜像签名（cosign）
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-image-signature
spec:
  validationFailureAction: Enforce
  webhookTimeoutSeconds: 30
  rules:
    - name: check-signature
      match:
        any:
          - resources:
              kinds: ["Pod"]
      verifyImages:
        - imageReferences:
            - "registry.example.com/*"
          attestors:
            - entries:
                - keys:
                    publicKeys: |-
                      -----BEGIN PUBLIC KEY-----
                      <你的 cosign.pub 内容>
                      -----END PUBLIC KEY-----
# 策略三：Pod 必须符合 restricted 基线（等价于 PSS enforce 的策略化版本）
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-security-context
spec:
  validationFailureAction: Enforce
  rules:
    - name: check-hardening
      match:
        any:
          - resources:
              kinds: ["Pod"]
      validate:
        message: "必须 runAsNonRoot、drop ALL caps、只读根文件系统"
        pattern:
          spec:
            securityContext:
              runAsNonRoot: true
            containers:
              - securityContext:
                  allowPrivilegeEscalation: false
                  readOnlyRootFilesystem: true
                  capabilities:
                    drop: ["ALL"]

供应链全景

环节控制
构建CI 环境最小权限、构建缓存隔离、SBOM 生成（syft/spdx）
仓库Harbor / 受管 registry；拉取前扫漏洞；不可信镜像禁入；镜像不可变 tag
分发TLS 拉取；签名 + attestation；镜像来源白名单
准入Kyverno/Gatekeeper 验签 + 基线校验 + registry 白名单，三件事一次拦
运行时Falco 行为监控（异常 exec、敏感文件读）；镜像与运行态比对
SolarWinds 事件的教训：供应链攻击（如投毒公共镜像、劫持 CI）防的是"你信任的镜像被换掉"。没有签名和 attestation，出事时你无法回答"这个镜像是哪次构建产物、代码是什么版本"—— 响应时间以周计。签名 + SBOM 把这个时间压到小时。
模块 7

真实 YAML：一个 hardened Pod 与自查

可直接抄的生产 Pod 模板

apiVersion: v1
kind: Pod
metadata:
  name: secure-demo
  namespace: production
  labels: {app: secure-demo}
spec:
  serviceAccountName: app-sa
  automountServiceAccountToken: false      # 容器内无 token 可偷
  securityContext:                          # Pod 级
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: app
      image: registry.example.com/app:v1.2.3@sha256:64ec2a3f...   # digest 锁定
      ports:
        - containerPort: 8080               # 非特权端口
      securityContext:                      # 容器级
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      resources:                            # 上限防单 Pod 吃光节点
        requests: {cpu: 100m, memory: 128Mi}
        limits: {cpu: 500m, memory: 256Mi}
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}                          # 唯一可写路径

模块 8

十个真实坑

1
镜像默认以 root 跑，没设 runAsNonRoot
Dockerfile 不写 USER 就是 root；容器 root + 逃逸漏洞 = 宿主机 root。加 USER nonroot + securityContext.runAsNonRoot 双保险。
2
privileged: true 一把梭
为了"装个调试工具""改个 sysctl"就给特权 Pod。特权容器 = 宿主机 root。需要的能力用 capabilities 逐项授，调试用一次性 Pod。
3
挂载 /var/run/docker.sock
"让容器里能跑 docker"是最经典的沦陷配置：通过 Docker API 创建挂载宿主机 / 的容器直接拿下节点。改用 Kaniko/BuildKit rootless 或无守护进程构建。
4
hostPID / hostNetwork / hostIPC 图省事
hostPID 下能读宿主 /proc 里的所有进程环境和命令行参数（包括密钥）、操作宿主进程。只有网络/监控类组件单独开，并放独立 namespace + NP。
5
以为 Secret 的 base64 是加密
kubectl get secret -o jsonpath 一把 base64 -d 就还原。etcd 必须开 EncryptionConfiguration，敏感场景用 Vault/External Secrets，密钥别进环境变量和日志。
6
etcd 没加密、端口全网可达
etcd 明文存全部 Secret + 证书；2379/2380 若对集群外开放，拿到 etcd 等于拿到集群。访问控制 + 静态加密 + etcd 证书轮换，三件事都要做。
7
RBAC 图省事绑 cluster-admin / edit
给团队绑了集群级 edit，等于人人能读所有 namespace 的 Secret。按 namespace 最小 Role；高危 verbs（exec/secrets/create pods）单独审批。
8
没配 NetworkPolicy，网络全扁平
一个 Pod 被攻破就能直连集群内所有服务（数据库、Redis、API）。默认拒绝 + 按需放行；先确认 CNI 支持 NP（flannel 不支持）。
9
镜像用 latest、不扫描、不签名
latest 让"部署的到底是什么"不可知；不扫描让已知 CVE 躺到被利用；不签名让供应链投毒无法检测。CI 里扫描 + 签名，准入时验签 + digest 锁定。
10
不关 automountServiceAccountToken
每个 Pod 默认挂 SA token，容器内一步 curl K8s API 就能按 SA 权限行事。应用不需要调 API server 的就显式 false；默认 SA 不绑任何 Role。
自测

六道题

1. 给容器设 privileged: true 的直接后果是？
正确答案：等价于宿主机 root。特权容器几乎关闭了所有隔离（设备访问、capabilities、部分 seccomp）。生产一律禁用；确有特权需求用白名单 capabilities 逐项授权。
2. 关于 K8s Secret，哪个说法正确？
正确答案：默认未加密 + base64 不是加密。能读 etcd 或有 get secrets 权限的人都能还原。三件套：etcd 静态加密、RBAC 最小权限（get/list 分开授）、Vault/External Secrets 管理敏感凭据。
3. Pod Security Standards 中 restricted 档要求不包括？
正确答案：privileged 恰恰是 restricted 明确禁止的。restricted = baseline 全部禁令 + runAsNonRoot + seccomp RuntimeDefault + drop ALL capabilities + allowPrivilegeEscalation: false，是生产默认目标。
4. 某 Pod 挂了宿主机的 /var/run/docker.sock，风险是？
正确答案：宿主机沦陷。docker.sock 是 Docker 守护进程的控制接口，谁拿到谁就是宿主机 root。构建场景改用 Kaniko/BuildKit rootless，运行时不挂。
5. 集群里没配 NetworkPolicy 时的网络形态是？
正确答案：默认全通。K8s 网络默认无策略，且很多 CNI（如 flannel）不支持 NetworkPolicy。必须先确认 CNI 支持，再做 default-deny + 按需放行。
6. 防止供应链投毒（镜像被篡改）的核心机制是？
正确答案：签名 + 验签准入。CI 构建后用私钥签名，集群侧 Kyverno/Gatekeeper 验签后才允许运行，配合 SBOM/attestation 实现可追溯。"密码"和"压缩"与供应链信任无关。
