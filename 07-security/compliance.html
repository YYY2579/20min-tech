二十分钟学透等保与合规（工程落地）

开始前

中国合规版图：四套体系各管什么

工程团队最容易混淆的是"等保、关基、数安法、个保法"的关系。用一句话各自定位，后面才不会串台。

体系法律/标准依据管什么
等级保护《网络安全法》第 21 条 + GB/T 22239-2019所有网络运营者的安全保护基本制度：定级、备案、建设整改、测评、检查。是地基，其他都建立在它上面
关基保护《关键信息基础设施安全保护条例》2021.9 施行对重要行业关键系统的强化保护：认定机制、运营者主体责任、每年检测评估、事件报告
数据安全《数据安全法》2021.9 施行数据本身的分级分类、重要数据目录、风险评估、跨境安全评估
个人信息《个人信息保护法》2021.11 施行个人信息的处理规则：告知同意、最小必要、敏感信息、自动化决策、泄露通知
工程视角的四层落地：等保是骨架（你要建哪些控制项），关基是加强筋（被认定后要求更高），数安法和个保法是内容物（你系统里流动的数据归谁管、怎么管）。做技术方案时，正确的顺序是：先定级备案 → 按等保要求建控制 → 识别系统中的重要数据和个人信息 → 对这两类数据加专用管控（加密、脱敏、审计、出境评估）。
模块 1

等保 2.0：五级分类与定级

等保 2.0 的核心文件是 GB/T 22239-2019《网络安全等级保护基本要求》，2019 年 12 月 1 日实施，把云计算、移动互联、物联网、工业控制、大数据全部纳入了扩展要求。定级是整个体系的地基，定错了后面全歪。

五个级别

级别保护强度适用情形（摘要）
第一级自主保护受到破坏后损害公民/法人自身权益，不涉及国家安全和社会秩序。小型内部系统、个人网站
第二级指导保护破坏后严重损害公民/法人权益、或损害社会秩序。一般企业内部系统、普通门店系统
第三级监督保护破坏后严重损害社会秩序/公共利益、或损害国家安全。大多数面向公众的互联网业务系统定这一级
第四级强制保护破坏后特别严重损害社会秩序/公共利益、或严重损害国家安全。重要行业核心系统
第五级专控保护破坏后特别严重损害国家安全。极端重要系统，实践中极少

定级的两个维度

定级不是拍脑袋看系统大小，而是两个矩阵的交叉：受侵害客体（公民法人合法权益 / 社会秩序公共利益 / 国家安全）× 侵害程度（一般损害 / 严重损害 / 特别严重损害）。侵害程度取各客体中的最高值——一个系统哪怕用户量不大，只要泄露会影响社会秩序（比如健康码、支付、出行），就够三级。

定级最常见的两种错误：① 该定三级定了二级——以为"我们不是金融/政务，就是个 App"就定二级，等监管检查或出事件时被要求重新定级，前期备案和测评全部返工；② 盲目往高定——内部 OA 定四级，每年测评和整改成本翻几倍。正确姿势是组织业务、法务、安全一起按矩阵推演，形成书面定级报告并做专家评审，定级结论要经得起网安部门问"为什么"。
一个工程上很有用的经验：定级时把系统按"数据敏感度 + 服务范围 + 故障影响"三列打分，分数段对应级别，做成模板。以后新系统上线前直接套模板，避免每个新业务都要重新吵一轮。三级的典型信号：面向不特定公众提供服务、涉及钱、涉及大规模个人信息、中断会影响社会秩序。
模块 2

技术侧要求映射（一个中心三重防护）

GB/T 22239-2019 把技术要求拆成五大类，工程上叫"一个中心、三重防护"：安全管理中心 + 安全通信网络 + 安全区域边界 + 安全计算环境，外加安全物理环境。下面按类给出"要做什么 → 工程实现"的直接映射。

1. 安全物理环境（机房/云平台侧）

要求点工程实现
物理访问控制机房门禁 + 电子门禁记录；云场景映射为物理机区/专有云的管控和云厂商等责证明（公有云由云厂商承担，你要留存其合规资质）
防盗防破坏、防雷防火防水防静电机房选址与装修；公有云场景向云厂商索取合规认证（等保、ISO 27001、可信云）并归档
温湿度、电力供应动环监控 + UPS + 双路电；云场景关注多可用区部署
电磁防护涉密系统专用屏蔽机房；普通互联网系统一般按需

2. 安全通信网络

要求点工程实现
网络架构核心链路/设备冗余；业务区、管理区、DMZ 分区；云上对应 VPC 子网划分 + 多可用区
通信传输完整性/保密性全站 TLS 1.2+（关闭 SSLv3/TLS1.0/1.1）；校验技术（签名/MAC）；敏感数据传输加密（国密 SM2/SM4 场景按行业要求）
可信网络验证接入设备身份校验（802.1X/证书），高要求场景部署

3. 安全区域边界

要求点工程实现
边界防护互联网边界防火墙/安全组默认拒绝，按白名单开放；生产网与办公网隔离
访问控制按会话的 ACL，到端口级；非必要端口一律关闭（135/137/138/139/445/3389 是重灾区）
入侵防范WAF + IPS/IDS；云上对应 WAF + 云防火墙；边界攻击行为分析
恶意代码防范边界防病毒网关；邮件/上传文件扫描
安全审计边界设备的访问日志全量采集到日志中心，留存 ≥6 个月

4. 安全计算环境（工作量最大的一块）

要求点工程实现
身份鉴别口令复杂度（长度 ≥8、三类字符组合、90 天更换）、登录失败锁定（连续 5 次失败锁定 10 分钟是常见基线）、远程管理双因素、空口令/默认口令清零
访问控制删除或重命名默认账户（admin、guest、test）；账户按角色最小授权；敏感功能二次授权
安全审计覆盖登录、管理员操作、异常行为的审计记录；审计进程保护，防止被清理
入侵防范HIDS 主机入侵检测；最小化安装，关闭不必要的服务
恶意代码防范统一防病毒客户端 + 病毒库更新策略
资源控制CPU/内存/磁盘/带宽监控与告警；单用户/单进程资源上限；登录超时自动注销
数据完整性/保密性传输和存储加密；校验技术防篡改；敏感字段加密存储（数据库透明加密或应用层加密）
数据备份恢复本地每日全量/增量 + 异地定期备份；定期做恢复演练（这是测评高频不符合项）
剩余信息保护存储空间释放前清零（内存/缓存/临时文件清理）
个人信息保护个人信息采集告知同意、脱敏展示、访问审批留痕

5. 安全管理中心（"一个中心"）

通过系统管理、审计管理、安全管理三个模块对分散的控制点做集中管控。工程落地形态通常是：堡垒机 + 日志审计平台 + 统一监控告警 + 4A 平台的组合。核心要求是：管理流量与业务流量分离（独立管理区/带外管理），管理员操作全部经堡垒机并录屏留痕。

技术要求里最容易被测评打回的六项：① 空口令/默认口令；② 登录失败处理缺失（无锁定策略）；③ 审计功能未覆盖"管理员操作"和"异常行为"；④ 日志留存不足 6 个月；⑤ 关闭高危端口的策略缺失；⑥ 备份未验证可恢复。这六项不需要采购任何硬件，改配置就能过——过不了纯粹是因为没人管。
模块 3

管理侧要求：比技术更易翻车

管理要求分五大部分。无数团队技术分很高、管理分不及格，因为技术可以买，管理只能建。五部分对应到工程组织的落点如下。

管理域要求摘要工程组织里的落点
安全管理制度制度成文、发布、评审修订安全管理办法、开发规范、运维规范、应急响应预案——重点是有版本号和评审记录，不是写没写
安全管理机构岗位设置、人员配备、授权审批、沟通合作网络安全领导小组 + 安全专职岗位（三级系统要求设置）；跨部门的授权审批流
安全管理人员录用、离岗、考核、安全意识教育、外部人员管理入职/离职安全 checklist；年度安全意识培训记录（留照片、签到、试卷）；外包人员保密协议与权限管控
安全建设管理定级备案、方案设计、采购、软件开发、外包开发、工程实施、测试验收、交付、测评、供应商选择新系统上线流程里嵌入安全评审节点；第三方组件/SDK 的供应链审查；上线前安全测试报告
安全运维管理环境/资产/介质/设备维护/漏洞/网络系统/恶意代码/配置/密码/变更/备份/事件处置/应急预案/外包运维资产台账、变更管理流程、漏洞管理 SLA、密钥轮换、演练记录——这一块就是 DevOps 日常
三员分立是硬要求：三级以上系统要求系统管理员、安全管理员、审计管理员三岗分离，审计管理员独立于前两者。工程上的典型翻车是：DBA 兼任系统管理员又兼审计员，堡垒机和日志平台的 admin 是同一个账号。落地姿势：账号体系按角色拆分，日志平台用独立账号只读采集 + 告警，审计员对管理员的操作有查阅权而无配置权。
管理要求的"证据链"思维：管理项不像技术项有命令可查，它要的是可展示的证据——制度文件 + 发布记录 + 培训签到 + 审批单 + 演练报告。测评时拿不出证据等于没做。所以工程上要把这些产物统一归档（Wiki/文档平台 + 定期导出），而不是散落在邮件和聊天记录里。建议每个季度做一次"证据自查"，比等测评前补要轻松一个数量级。
模块 4

合规测评流程：四步闭环

定级备案：确定定级对象与级别（第二级以上），编制定级报告，组织专家评审，到公安机关办理备案，领取备案证明。变更（合并、拆分、重大改版）要重新定级或变更备案。
建设整改：按 GB/T 22239 对应级别的要求做技术和管理建设。差距分析 → 整改方案 → 采购/开发 → 实施。这一步决定测评分数，也是唯一能"提前做"的一步。
等级测评：委托有资质的测评机构（名单在属地网安部门/中国网络安全审查技术与认证中心体系内），现场测评：访谈（管理）、文档审查、配置检查（技术）、漏洞扫描/渗透测试。出具测评报告与整改建议。
监督检查：公安机关对备案单位开展监督检查，核对定级准确性、整改落实情况、测评结论。监督检查看的是持续性，不是一次性的测评分数。

测评周期（通行要求）

级别测评频率说明
三级每年至少一次源自《信息安全等级保护管理办法》；跨年度的重大变更要重新测评
四级每半年一次要求更严，整改窗口更短
二级自行确定（常见两年一次）运营者自行安排，但监督检查时可能被要求出示测评记录，具体以属地网安要求为准
关于"基本项/选择项/风险"的测评结论逻辑：测评按符合率打分，三级系统通常要求符合率达到一个较高门槛（常见口径 75% 以上，以测评机构判定为准），且高危风险项一票否决。所以正确策略是：把所有高危项（空口令、无锁定策略、日志不足 6 个月、无备份恢复验证）全部清零，中低风险项按性价比排期。不要平均用力，先清一票否决项。
测评机构不是你的对手，是帮你发现问题的人。但要注意：渗透测试和漏洞扫描一定在授权范围、授权时间窗内进行，提前协调好封禁策略，别让"测评流量"触发你自己的 WAF/IPS 把测评机构封了，或者触发监管对外的告警。测试前开好白名单，测试后及时关闭。
模块 5

关基条例、数据安全法、个保法要点

《关键信息基础设施安全保护条例》（2021.9.1 施行）

  • 认定机制：由保护工作部门制定认定规则，组织认定，通知运营者。不是自己说"我是关基"就是，也不是说不是就不是。
  • 运营者责任：建立健全网络安全保护体系和责任制，设置专门安全管理机构（负责人和关键岗位人员的背景审查）、安全保障经费、每年至少一次网络安全检测评估、对从业人员安全教育。
  • 事件义务：发生事件立即启动应急预案，向保护工作部门和公安机关报告。
  • 采购安全：采购网络产品和服务影响国家安全的，需通过国家安全审查。

《数据安全法》（2021.9.1 施行）工程相关要点

  • 数据分类分级：国家建立数据分类分级保护制度；各地区、部门制定重要数据目录。企业侧要落地为：数据资产盘点 + 分级打标 + 分级管控策略。
  • 风险管理：重要数据处理者应当定期开展风险评估，并向主管部门报送风险评估报告。
  • 事件处置：发生数据安全事件立即处置，按规定告知用户并向主管部门报告。
  • 数据出境：向境外提供数据须依法进行安全评估等程序（与个保法跨境条款衔接）。

《个人信息保护法》（2021.11.1 施行）工程相关要点

  • 告知同意 + 最小必要：收集限于实现目的的最小范围；隐私政策要"显著、清晰"；不同意非必要个人信息不能拒绝提供服务。
  • 敏感个人信息（生物识别、金融账户、行踪轨迹、14 岁以下儿童信息等）：单独同意 + 特定目的 + 充分必要性。
  • 自动化决策：画像、个性化推荐要提供拒绝选项；大数据杀熟被明确禁止。
  • 泄露通知：发生或可能发生个人信息泄露、篡改、丢失的，立即补救并通知监管部门和个人。
  • 工程映射：字段级打标（哪些是 PII）、脱敏/加密策略、访问审计、同意记录留痕、导出与删除接口（"删除权"的工程实现）。
三部法律 + 等保的工程串联：等保告诉你"系统要建哪些控制"；关基条例把被认定系统的控制标准抬高并要求年度检测评估；数安法管你库里的数据分级、评估、出境；个保法管你处理的自然人信息。落到技术方案上就是同一件事：数据资产分级 → 按级别定控制强度 → 全链路审计留痕 → 出境/共享走审批评估。
模块 6

DevOps 团队的合规落地

合规做进流水线，才不用每年突击。四个抓手：基线核查脚本化、变更全程留痕、日志集中留存 6 个月、漏洞管理有 SLA。

1. 基线核查（把等保要求变成可执行检查）

# 用开源基线内容把"检查项"自动化：CIS Benchmark + 等保定制项
# InSpec 写检查（可直接对接 CI 与合规报告）
control 'ssh-01' do
  impact 1.0
  title '禁止 root 直接 SSH 登录'
  desc  '等保-身份鉴别：远程管理应使用个人账户而非 root'
  describe file('/etc/ssh/sshd_config') do
    its('content') { should match /^PermitRootLogin\s+no/ }
  end
end

control 'pwd-01' do
  title '口令复杂度与更换周期'
  describe file('/etc/login.defs') do
    its('PASS_MAX_DAYS') { should cmp <= 90 }
    its('PASS_MIN_DAYS') { should cmp >= 1 }
  end
end

2. 变更留痕（合规的命根子）

  • 一切变更走 Git：基础设施（Terraform）、K8s 清单、配置（Ansible）、应用代码全部版本化，变更即 commit，天然有"谁、何时、改了什么"。
  • 发布关联审批：CI/CD 流水线记录每次发布的 commit、审批人、审批单号；高危操作（删库、改 ACL、开高危端口）强制二次审批 + 工单号。
  • 堡垒机兜底：所有人工登录经堡垒机，命令级/录屏级审计；堡垒机日志与 CI/CD 日志互备，任何一条链路断了都能还原操作时间线。
  • 数据库变更：DDL/DML 走工单 + SQL 审核平台；慢日志与审计日志留存 ≥6 个月。

3. 日志集中留存（6 个月是法律线）

# 《网络安全法》第 21 条：留存相关的网络日志不少于六个月
# 日志分类与留存策略（示例）
访问日志（nginx/网关）   —— 热 30 天 + 温 90 天 + 冷 180 天，共 6 个月
操作审计（堡垒机/4A）    —— 热 90 天 + 冷 180 天，命令级全量
安全设备日志（WAF/IPS）  —— 热 90 天 + 冷 180 天
数据库审计              —— 热 90 天 + 冷 180 天
系统日志（auth/syslog）  —— 热 30 天 + 冷 180 天

# 冷存储用对象存储 + 生命周期策略，成本远低于 ES 全量
# 关键：每条日志链路要算"采集完整性"——源端条数与采集端条数比对，
# 防止日志被本地清理或网络中断导致合规缺口而不自知

模块 8

十个常见坑

1
把合规等同于买设备
防火墙、WAF、堡垒机、日志审计买齐，管理侧制度、机构、人员、运维四块全空。测评时技术分高、管理分不及格，总评照样不过。管理要求没法采购，只能建设。
2
测评前一周突击整改
平时没人管，测评前买设备、补文档、改配置。突击买的设备没调试、补的制度没评审、改的配置没过测试，现场一测全露。测评只是验收，功夫在平时。
3
忽视管理要求，只堆技术
访谈环节答不上"多久做一次培训""谁负责漏洞管理""变更走什么流程"，直接大面积不符合。技术要求可以自动化，管理要求必须靠人和流程，反而更花时间养。
4
定级拍脑袋，该定三级定了二级
"我们不是金融"就定了二级，等监管检查或被通报时要求重新定级，备案、测评、整改全部返工，还留下整改不及时的记录。
5
日志只存 3 个月
ES 集群按容量只留 90 天，冷备也没做。《网络安全法》第 21 条明确要求网络日志留存不少于六个月，这是硬伤，一查一个准。
6
三员分立形同虚设
DBA 一个人既是系统管理员又是审计管理员，日志平台 admin 和堡垒机 admin 是同一套账号。制度写了三员分立，技术实现没拆。
7
堡垒机买了没人走
采购完发现太麻烦，运维还是直接 SSH 连，堡垒机上三个月没有一条会话记录。审计数据为空比没有堡垒机更难看。
8
高危漏洞年复一年不修
扫描报告每年都是同一批 Log4j、Shiro、fastjson 高危，测评建议书提了三年没人管。高危项在测评结论里一票否决，还直接对应监管处罚风险。
9
备份从不做恢复演练
备份任务天天绿，真到要用时发现备份文件损坏、密钥丢了、恢复步骤没人会。备份的有效性只能靠恢复演练证明，这也是测评高频不符合项。
10
把"过测评"当成"已合规"
测评报告一交就把 WAF 调成观察模式、日志策略改回 90 天、账户权限重新放开。监督检查看的是持续性，合规是状态不是项目。
自测

六道题

1. 大多数面向公众的互联网业务系统（涉及钱和大量用户信息），按等保 2.0 通常定几级？
正确答案：第三级。定级逻辑是"受侵害客体 × 侵害程度"取最高：面向不特定公众、涉及资金、涉及大规模个人信息、中断影响社会秩序的系统，破坏后严重损害社会秩序/公共利益，够三级。实践中绝大多数互联网业务系统都是三级。
2. 等保技术要求的"一个中心、三重防护"指的是？
正确答案：安全管理中心 + 通信网络/区域边界/计算环境。再加上安全物理环境共五大类技术要求。一个中心做集中管控，三重防护按网络层次纵深设防——这是 GB/T 22239-2019 技术部分的主框架。
3. 等级测评的正确流程顺序是？
正确答案：定级备案 → 建设整改 → 等级测评 → 监督检查。先定级才能确定要按哪级标准建，建设整改在测评之前（测评就是验收整改成果），最后是公安机关的持续性监督检查。
4. 《网络安全法》对网络日志留存的最低要求是？
正确答案：不少于六个月（第 21 条）。工程落地：热存储 30~90 天全量检索 + 对象存储冷备到 180 天以上。ES 按容量只留 90 天是最常见的踩法。
5. 关于"三员分立"，正确的做法是？
正确答案：三套角色分离，审计独立。审计管理员要有对管理员操作的查阅权但无配置权。制度写了分立、技术账号不拆，是测评访谈 + 配置检查双料不符合项。
6. 关于合规落地，下面哪种说法是对的？
正确答案：做进流水线。基线检查进 CI（不合规不合并）、镜像扫描进流水线（高危 CVE 不发布）、审批进发布流程、审计埋点进框架——合规的终态是工程师感受不到它，但每一步都自动满足。合规是状态不是项目，测评后调回原样正是监督检查要抓的。
