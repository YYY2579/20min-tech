开始前

为什么城堡模型失效了

传统模型把网络分成"可信内网"和"不可信外网"，边界上砌一堵防火墙。这个模型假设：墙内的人都是好人。现实中这个假设被三件事击穿：

边界消失
云、SaaS、移动办公、合作方接入之后，"内网"不再是一个网络位置，而是一堆互连的碎片
攻击者已在内
钓鱼一封邮件、一个供应链投毒的镜像、一个失陷的笔记本，攻击者落地时就已经"在墙内"
东西向流量占大头
数据中心流量里东西向占比被普遍认为超过 80%（Gartner 等机构的经典估算），而东西向传统上完全无管控

模块 1

网络分层防御：从边界到分区

纵深防御（Defense in Depth）的核心思想：不依赖任何单一控制，每层都假设上一层可能已被突破。

层部署内容策略要点
互联网边界边界防火墙、Anti-DDoS 清洗、CDN/WAF、云安全组只放行业务必需端口；隐藏源站；管理端口一律不暴露
DMZ面向公网的反向代理、WAF、邮件网关、DNSDMZ 到内网单方向发起（DMZ 可调内网，内网不主动连 DMZ）；最小化暴露面
内网边界内部防火墙 / 核心交换机 ACL按业务域分区；数据库层只允许应用层访问，禁止横向直达
内网分区VLAN/子网 + 微隔离 + NetworkPolicy按环境（prod/stage/dev）和业务域切开；管理面独立分区
主机层主机防火墙（iptables/nftables/Windows 防火墙）、HIDS每台机器自己也有防火墙；默认拒绝入站

分区的设计原则

  • 按信任级别分区，不按部门分区：同一"信任桶"的资产放一起，跨桶流量显式授权
  • 数据区是最后一道墙：数据库/缓存只接受来自应用区的指定端口；禁止应用服务器之间互相直连数据库
  • 管理面独立：SSH/RDP/kubectl/交换机管理只能从堡垒机发起，业务网段到管理面默认拒绝
  • 环境隔离：prod 与 dev/stage 不通网 —— dev 环境被攻破（开发机安全意识弱是常态）不应能摸到生产数据库
  • 云上等价物：VPC 划 subnet + 安全组（有状态、资源级）+ NACL（无状态、子网级）+ Transit Gateway 管控跨 VPC
一句话检验分区是否合格：随便挑一台办公区笔记本，它到生产数据库的 3306 端口应该是超时，而不是"能连上但没密码"。太多网络的答案是后者。
模块 2

防火墙与 ACL 设计原则

五条军规

默认拒绝（default deny）。规则表最后一条是 DROP ALL / deny any。先加白名单，而不是先封黑名单
规则自上而下 first-match。命中即停，顺序即优先级。把最精确的规则放最前面，最宽的兜底规则放最后，否则一条宽规则会让后面的精确规则永远不生效
状态检测。只放行"内部发起的连接"的回程流量（ESTABLISHED,RELATED），不要把回程方向单独写规则 —— 无状态 ACL 容易把回程打成筛子
每条规则带注释和工单号。谁、什么时候、为什么开的。没有注释的规则三个月后没人敢删，也没人敢留
定期审计 + 自动清理。每季度跑一遍：命中数为 0 的规则、过于宽松（any/any）的规则、临时规则到期 —— 规则表膨胀到几千条时，延迟和误判都会失控

云上：安全组 vs NACL

维度安全组 Security GroupNACL
作用范围弹性网卡 / 实例级整个子网级
状态有状态（回程自动放行）无状态（回程要单独写规则）
规则类型只有 allowallow + deny，按编号顺序匹配
典型用途每层服务的最小访问控制（默认实践）子网级粗粒度兜底，比如显式 deny 已知恶意网段
常见错误0.0.0.0/0 开放 22/3389/3306/6379忘了配回程规则导致"出站通、回包丢"的灵异故障
# iptables：一个"默认拒绝 + 按需放行"的主机防火墙骨架
iptables -P INPUT DROP          # 默认拒绝入站
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT       # 出站默认放行（生产建议收紧，见零信任）

iptables -A INPUT -i lo -j ACCEPT
iptables -A INPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A INPUT -p tcp --dport 22 -s 10.0.0.0/24 -j ACCEPT    # SSH 只放管理区
iptables -A INPUT -p tcp --dport 8080 -j ACCEPT                  # 业务端口全网
iptables -A INPUT -p icmp --icmp-type echo-request -m limit --limit 5/s -j ACCEPT

# nftables 等价写法（新内核首选，语法统一且更快）
table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;
    iif lo accept
    ct state established,related accept
    ip saddr 10.0.0.0/24 tcp dport 22 accept
    tcp dport 8080 accept
  }
}
血的教训：0.0.0.0/0 + 管理端口。公网可达的 SSH/RDP/数据库/Redis 端口，平均被扫描器"看见"的时间以分钟计。规则只有一条：管理端口只对堡垒机/VPN 出口开放，且必须配密钥/MFA，禁密码认证。云上检查方式：控制台看安全组入站规则，grep 到 0.0.0.0/0 就整改。
模块 3

IDS / IPS / WAF 的定位

设备看什么动作局限
NIDS网络流量（镜像/分光）告警看不到加密流量（除非有密钥）；镜像口带宽受限
NIPS网络流量（串接 inline）告警 + 阻断误杀风险；成为延迟瓶颈和单点
HIDS主机：文件完整性、日志、进程、系统调用告警Agent 资源占用；需逐台部署维护
WAFHTTP/HTTPS 应用层告警 + 阻断规则误报；对业务逻辑漏洞（越权、逻辑绕过）无效
NDR流量行为 + 机器学习基线告警误报调优周期长；需要基线期

开源/主流工具

Suricata / SnortNIDS/NIPS 双模式，规则语法相近，Suricata 多线程性能更好
Zeek（原 Bro）网络流量分析框架，生成高语义日志（DNS/HTTP/SSL/TLS 证书）
ModSecurity + CRSWAF 引擎 + OWASP 核心规则集，常以 Nginx/OpenResty 模块部署
FalcoCNCF 运行时安全，基于系统调用检测容器/主机异常行为
WazuhHIDS + 日志 + 合规扫描一体，SIEM 轻量替代

WAF 部署模式与真实边界

# 模式一：反向代理（最常用）
互联网 → [WAF] → 源站        # 需解密 HTTPS，源站 IP 对 WAF 之后隐藏

# 模式二：透明桥接
互联网 → [WAF 透传] → 源站   # 不改网络拓扑，单点故障即断网

# 模式三：Agent/Host 侧
源站进程内嵌 WAF 模块         # 看得见解密后的上下文，误报低，但占用应用资源

# 误报与绕过：
# 1. CRS 规则按模式匹配，%27（URL编码单引号）等变形可绕过 → 必须开规范化
# 2. WAF 与后端的解码差异（如 unicode 归一化）是经典绕过通道
# 3. BOLA/越权/逻辑漏洞 WAF 完全无感 —— 这是应用层测试的活
# 4. 只开 monitor 不 block = 日志系统，不是防御
WAF 的正确预期：它是一层提高攻击成本的过滤器，不是"装上就安全"。过滤已知攻击模式（SQLi/XSS/RCE 特征）、挡扫描器和脚本小子很有效；对针对性攻击和业务逻辑漏洞基本无效。别把 WAF 当修漏洞的替代品，它是争取补丁时间的缓冲带。
模块 4

零信任架构（NIST SP 800-207）

NIST SP 800-207《Zero Trust Architecture》（2020 年 8 月发布）是零信任的标准化定义。核心一句：永不信任，持续验证（never trust, always verify）—— 访问决策基于动态上下文，而非网络位置。

七项原则（tenets）

#原则
1所有数据源和计算服务都是资源 —— 无论个人设备还是云端工作负载
2所有通信默认不安全，无论位于什么网络位置 —— "在内网"不构成信任理由
3授权按单个连接/会话粒度授予 —— 不是"进了门就畅行无阻"
4访问策略是动态的 —— 综合身份、设备健康状态、行为、环境（位置/时间）持续评估
5持续监测和度量全部资产的完整性与安全态势
6认证与授权在放行前强制执行，且是动态的、持续刷新的
7尽可能采集资产、网络、通信的当前状态并反馈改进策略

Google BeyondCorp 的思路

Google 2014 年起公开的实践：把访问控制从"网络边界"搬到"用户 + 设备"身份上。员工从任何网络访问内部应用都不需要 VPN —— 访问代理根据员工身份、设备证书、设备健康状态（补丁级别、磁盘加密）授予特定应用的访问权。关键设计：

  • 消除特权网络：不存在"连上内网就比外网高级"这回事，所有访问都过同一个访问代理
  • 应用级授权：你能访问哪个应用是显式的 ACL，不是"同网段即可达"
  • 设备清单 + 设备证书：每台受管设备有证书和持续健康信号，非受管设备拿不到完整权限
  • 集中式访问代理 + 详细审计：所有访问可追因到"哪个人、哪台设备、什么上下文"

SDP（Software Defined Perimeter）模型

组件职责
SDP 客户端运行在终端，发起连接前先认证
SDP 控制器认证 + 策略决策（PDP），只在验证通过后才告知网关放行
SDP 网关策略执行点（PEP），真正转发应用流量

单包授权（SPA, Single Packet Authorization）是 SDP 的标志性机制：控制器完成认证前，网关对所有未授权流量静默丢弃（连端口都不响应）。效果：DDoS 扫描器看不到任何开放端口，攻击面从"全网可见"缩成"认证后可见"。

边界模型 vs 零信任

维度边界模型零信任
信任依据网络位置（在不在内网）身份 + 设备 + 上下文，每次请求都评估
授权粒度网段级（VPN 连上 = 全网段）应用/资源级（只给这一个应用）
横向移动失守一台 = 横扫网段每段都需重新授权，爆炸半径 = 单个资源
可见性边界有日志，内网无全链路日志 + 持续评估
适配场景物理集中、人员集中云、移动办公、混合办公
零信任不是产品，是架构演进：落地顺序通常是 ① 身份基座（IdP + MFA，先把"你是谁"做实）；② 设备管理（证书 + 健康检查）；③ 敏感应用切到访问代理（从最高危的开始）；④ 微隔离收敛东西向；⑤ 策略引擎 + 持续评估自动化。跳过身份直接买 ZTNA 盒子，是最常见的失败路径。
模块 5

微隔离：管住东西向

微隔离（Micro-segmentation）把防火墙的粒度从"网段"缩到"工作负载"：每台 VM/每个 Pod 有自己的访问策略，默认拒绝，显式放行。它是零信任在内网数据平面的落地形态。

实现机制适用
主机 Agent每台宿主机装 agent，把策略转成 iptables/nftables 规则物理机/虚拟机混合环境（代表：Illumio、Guardicore、NSX DFW）
Hypervisor 层在虚拟交换机上做策略，不碰 Guest OS全虚拟化环境，性能好但看不见 VM 内流量
云原生K8s NetworkPolicy / Service Mesh（Istio AuthorizationPolicy）容器环境（见容器与 K8s 篇）
云安全组按资源打标签做引用式规则（sg-web → sg-db:3306）云环境粗粒度微隔离

策略怎么定：从流量发现开始

先看流量再定策略。上线微隔离前跑 2~4 周流量学习（netflow/agent 观测），画出"谁在跟谁说话、用什么端口"。没有流量台账就开默认拒绝，等于闭眼封网
按角色建模。把工作负载抽象成 web / api / db / cache 几种角色，策略表达为"角色 → 角色 + 端口"，别写成 IP 对 IP（IP 会漂移，策略会烂掉）
从 monitor 到 enforce。策略先观察模式跑一周，核对没有合法流量被误拦，再切阻断。上来就 enforce 的团队都在半夜救过火
策略即代码。微隔离规则进 Git，变更走评审 —— 网络策略和应用代码一样需要 review 和回滚
# 一个角色化微隔离策略示例（逻辑表达）
web  → api   : tcp/443     # 前端到后端
api  → db    : tcp/3306    # 后端到数据库
api  → cache : tcp/6379    # 后端到缓存
mon  → *     : tcp/9100    # 监控抓 metrics（Prometheus node_exporter）
*    → 互联网 : tcp/443    # 出站 HTTPS（按需收紧到白名单域名）
其余全部默认拒绝 —— 含"db → db"、"api → api"这些横向路径
微隔离最大的坑是"策略腐化"：为了排障临时加了一条 any → any，救完火忘了删，三个月后策略千疮百孔。对策：① 临时策略强制 TTL，到期自动失效；② 每周报表列出过于宽松的规则；③ 变更全部走工单留痕。
模块 6

VPN 与 ZTNA

VPN 的三个结构性问题

  • 全网段授权：IPsec/SSL VPN 连上后通常能到整个内网段。攻击者拿下任意一台员工笔记本（钓鱼是最常态化的入口），横向移动成本几乎为零
  • 信任叠加而非信任验证：VPN 认证的是"用户有账号"，不管设备是否中毒、补丁是否落后
  • 性能与架构 hairpin：流量绕道 VPN 集中器再回来，跨国/跨云场景延迟爆炸；所有流量过集中器 = 单点 + 带宽瓶颈

四种远程访问形态对比

形态授权粒度特点与问题
IPsec VPN网络级（L3）成熟稳定；客户端重；全网段可见；移动端体验差
SSL VPN网络级或门户级浏览器友好；"网络扩展"模式同样是全网段；门户模式（反向代理单应用）更安全
ZTNA应用级用户/设备认证后只看到被授权的应用；基础设施对未认证用户不可见（SPA 静默丢弃）；按连接持续评估
SDP应用级与 ZTNA 高度重叠（SDP 是 CSA 的技术框架，ZTNA 更偏产品形态）；控制器-网关架构

ZTNA 的工作流（以访问代理型为例）

# 1. 用户登录：IdP 认证（含 MFA），设备证书校验
# 2. 策略引擎评估：身份 + 设备健康（补丁/EDR/加密状态）+ 上下文（时间/地理/行为异常）
# 3. 通过后由接入代理建立到具体应用的通道 —— 注意：只到这一个应用
# 4. 会话持续评估：设备掉线/EDR 报警/异地登录 → 实时吊销会话
# 5. 全程日志：who（人+设备）/when/what（应用+动作）/result

# 与传统 VPN 的关键差异：
# VPN：认证 → 全网段 IP 可达性 → 内网服务自己几乎不设防
# ZTNA：认证 → 单应用通道 → 服务仍要自己鉴权（纵深！）
ZTNA 不是"更安全的 VPN"：它改变的是信任模型。如果只把 ZTNA 当 VPN 用（连上后就当一个网段随便扫），你只是把边界从公司搬到了云上。正确的用法是：每个应用单独授权，策略显式登记，会话持续评估。这也正是微隔离和 SDP 存在的意义。

NTP monlist约 556×已大量修复，但仍有漏网服务器
DNS数十倍 ~ 百倍开放解析器 + 大响应（DNSSEC）即可放大
CLDAP / SSDP数十倍内网设备（打印机/IoT）被利用的常见选择
# 关键认知：放大攻击的请求很小，响应极大，且源 IP 可伪造
# 攻击者 → 1Mbps 伪造请求 → 反射器 → 50Gbps 打向受害者
# 所以单靠"买带宽"防不住，必须在流量路径上清洗 + 收紧自家反射面

# 自检：你的网络里有没有开放反射端口
nmap -sU -p 123,161,11211,1900 --open 你的网段        # NTP/SNMP/Memcached/SSDP
# 对外只开 443/80，其余 UDP 一律防火墙拒绝 —— 这条同样适用于云安全组

防护架构：清洗 + 任播 + 隐藏源站

  • Anycast 任播：同一个 IP 从全球多个点宣告，流量天然分散到最近节点， volumetric 攻击被"摊薄"到每个点
  • 清洗中心：流量牵引到清洗中心，扔掉恶意流量再回注源站（近源清洗 / 近目的清洗两档，时延与精度取舍）
  • 源站隐藏：业务只暴露 CDN/WAF 的 IP；源站 IP 进白名单；DNS 历史记录、证书透明度日志都可能泄露源站 IP，要定期检查
  • 云原生选项：AWS Shield Standard（自动、免费）+ Advanced（DDoS 响应团队、费用保护）；阿里云 DDoS 高防 + CDN；Cloudflare 的 Anycast + 清洗
  • CC 攻击的尽头是业务风控：带宽清洗解决不了"每个请求都像正常用户"。限流（按 IP/user/设备）、JS 挑战、验证码阶梯、业务规则（同一账号高频下单拦截）组合使用
DDoS 预案要在没被打时写好：① 源站 IP 列表和切换脚本；② 清洗服务商的联系方式和 API key；③ 哪些服务可以降级（关闭搜索、关闭图片）保住核心交易；④ 和云厂商约定"什么量级触发什么动作"。出事时现查文档的团队，通常死在头 30 分钟。

内网横移防范与常见坑

攻击者在内网怎么动（防御视角）

技术手法对应防御
凭据窃取内存抓密码哈希/NTLM、窃取浏览器保存的凭据、读配置文件里的密码LAPS 定期改本地管理员密码；凭据保护（Credential Guard）；禁密码复用
Pass-the-Hash拿到哈希直接用于 NTLM 认证，不需要破解明文禁用 NTLM 迁移到 Kerberos；本地管理员密码唯一化
Kerberoasting普通域用户即可申请服务票据，离线爆破服务账号密码服务账号用 120+ 位随机密码；定期轮换；监控异常 TGS 请求
远程执行横移RDP(3389)/SMB(445)/WinRM(5985,5986)/WMI/SSH(22) 批量尝试网络分区限制这些端口只到堡垒机；MFA；登录失败锁定
内网服务利用扫到未认证 Redis/Elasticsearch/Docker API 直接利用微隔离 + 一切内网服务强认证（见容器与 K8s 篇）

纵深防御：让横移每一步都付出代价

  • 网络层：东西向默认拒绝（微隔离/NetworkPolicy），RDP/SMB/WinRM 只能从堡垒机走
  • 身份层：SSO + MFA；特权访问走 PAM（定期改密、会话录屏）；本地管理员密码唯一且轮换
  • 主机层：EDR 覆盖全部服务器；PowerShell 日志 / 命令审计开启；关闭不必要的远程管理协议
  • 检测层：基线化流量（谁跟谁说话），偏离基线即告警；DNS 查询监控（C2 通信最常见的外带通道）；认证日志集中分析
  • 管理层：跳板机/bastion 是唯一入口，带 MFA 和会话录制；临时提权走审批而非长期授权
自检三问（对任何系统都适用）：① 办公网的一台笔记本到生产数据库，通不通？② 生产的一个 Web Pod 到另一个 Web Pod，要不要过鉴权？③ 出站的 DNS 查询，有没有日志和基线？三个答案都"是/不通/有"，才算有基本的东西向管控。
常见坑

十个高频开发坑

1
只有边界防御，内网全通
边界防火墙做得再厚，挡不住已经进来的钓鱼邮件和失陷笔记本。内网必须有第二层：分区 + 微隔离 + 东西向默认拒绝。
2
信任内网，跑明文协议
HTTP/Telnet/FTP/SMB 明文在内网跑，任何能嗅探的人都能拿到凭据。内网不是可信网，内网通信同样要 TLS/mTLS 和认证。
3
VPN 一把梭
连上 VPN 即全网段可达，横向移动零成本。改应用级授权（ZTNA）+ 微隔离，让失陷终端只能看到它该看的那一个应用。
4
0.0.0.0/0 开放管理端口
公网可达的 22/3389/3306/6379，分钟级被扫描器发现并常年暴力破解。管理端口只对堡垒机/VPN 出口开放，配密钥/MFA，禁密码认证。
5
防火墙规则只加不减
三年后规则表几千条，没人知道哪条还有用，也没人敢删。规则必须带注释和工单号，每季度清理命中数为零的规则和 any/any 宽松规则。
6
WAF 只开检测模式
monitor 模式下攻击全部放行，只留下日志。试运行调完误报后必须切 block；同时记住 WAF 对越权和逻辑漏洞无效。
7
出站流量不限制、无日志
数据外带、C2 回连、挖矿全走这条自由通道。egress 白名单 + DNS 查询日志 + 基线告警，是发现内网失陷最主要的抓手。
8
DMZ 与内网同一信任域
DMZ 的公网服务是暴露面最大的地方，却能和内网数据库直连。DMZ 到内网要单方向、按端口放行，内网不主动连 DMZ。
9
无流量基线，横移无从发现
出事后才想起查日志，发现根本没有东西可查。平时就要有 netflow/NDR 基线：谁跟谁说话、什么时候多了一个新对话。
10
忽略东西向与微服务间调用
服务间无 mTLS、无鉴权，一个失陷 Pod/VM 就能调用全部服务。东西向要显式授权（Istio AuthorizationPolicy / NetworkPolicy / 微隔离）。
自测

六道题

1. 零信任架构的核心主张是？
正确答案：永不信任，持续验证。NIST SP 800-207 的定义：所有通信默认不安全、授权按单个会话授予、策略动态评估。"在内网"不构成信任理由。
2. NIST SP 800-207 是什么？
正确答案：零信任架构标准。它给出了七项原则、两种部署模型（设备代理/网关、资源门户、 enclave 等）和与 IAM、微隔离、SIEM 的组合方式，是目前最常被引用的权威定义。
3. 微隔离（micro-segmentation）主要解决什么问题？
正确答案：东西向管控。数据中心流量 80% 以上是东西向，传统边界防火墙完全看不见。微隔离把策略粒度从网段缩到工作负载，默认拒绝 + 显式放行。
4. ZTNA 与传统 VPN 的关键区别是？
正确答案：应用级授权 vs 网段级可达。VPN 认证后给你整个内网段的 IP 可达性；ZTNA 认证后只建立到具体应用的通道，且会话持续评估、可实时吊销。
5. 关于反射放大 DDoS，哪个说法正确？
正确答案：Memcached 约 51,000×。放大攻击请求小、响应大、源 IP 可伪造，所以必须在流量路径上清洗 + Anycast 分散 + 收紧自家反射面（对外只开 80/443），单买带宽防不住。
6. 防火墙规则设计的首要原则是？
正确答案：默认拒绝。先定义允许什么，其余全拒；配合 first-match 顺序（精确规则在前、兜底在后）、状态检测（只放行 ESTABLISHED,RELATED 回程）和定期审计。
