模块 1

责任共担模型：云管什么，你管什么

所有云厂商都遵循同一套责任共担模型，但分界线随服务类型漂移——这是最容易出认知事故的地方。

服务类型云厂商负责你负责
IaaS
（ECS/EVM/CVM、S3/OSS/COS）		物理机、网络、存储硬件、虚拟化层操作系统补丁、防火墙规则、账号权限、数据加密、Bucket 公开性
PaaS
（RDS、Serverless）		+ 运行时、数据库引擎补丁账号权限、网络访问控制、参数组安全配置、数据分级
SaaS
（钉钉、企业邮箱）		几乎全部账号、MFA、权限分配、数据内容本身
最典型的责任事故："数据库被拖库，找云厂商索赔"。RDS 的引擎补丁是厂商的，但白名单 IP、数据库账号权限、是否公网可达全是你的。云厂商的安全是"地板"，不是"天花板"——地板之上每一层配置都是你的责任。
厂商术语对照表： AWS IAM ≈ 阿里云 RAM ≈ 腾讯云 CAM；AWS Security Group ≈ 阿里云/腾讯云安全组；AWS VPC ≈ 阿里云/腾讯云 VPC；AWS S3 ≈ 阿里云 OSS ≈ 腾讯云 COS；AWS KMS ≈ 阿里云 KMS ≈ 腾讯云 KMS；AWS CloudTrail ≈ 阿里云操作审计 ActionTrail ≈ 腾讯云操作审计。概念一一对应，学会一套迁移成本很低。
模块 2

身份与权限：IAM 最小权限实践

先看一个真实的过度授权策略

// AWS IAM 策略：这条"图方便"的策略 = 把保险柜钥匙贴在大门上
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "*",              // 所有操作
    "Resource": "*"            // 所有资源
  }]
}

// 收紧后的版本：只给某个 bucket 的读权限
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::my-app-assets",
      "arn:aws:s3:::my-app-assets/*"
    ],
    "Condition": {
      "Bool": { "aws:SecureTransport": "true" }   // 只允许 HTTPS
    }
  }]
}

最小权限的四条落地规则

按服务拆策略，不按人拆——一个"部署角色"只拥有它要部署的资源权限，而不是把 AdministratorAccess 发给每个开发。
用访问分析器（Access Analyzer）体检——AWS Access Analyzer / 阿里云 RAM 权限检查 / 腾讯云 CAM 访问分析会自动标出"未使用的权限"和"外部可访问的资源"。
通配符是腐败的起点——Action: "s3:*" 意味着包括 s3:DeleteBucket。每条策略写清楚具体 action，宁可多写几行。
条件键带上——aws:SecureTransport（禁 HTTP）、aws:SourceIp（限办公网出口 IP）、aws:RequestedRegion（禁在非常用区操作）。

角色扮演 vs 长期密钥

方式机制风险与适用
长期 AK/SK静态密钥写代码/配置文件最大风险源：进 Git = 泄露，无过期 = 长期有效。只用于本地开发的临时凭证
角色扮演
（AssumeRole / RAM 角色）		STS 换临时凭证，默认 1 小时过期首选。没有可泄露的静态秘密；配合 MFA 条件更稳
实例角色
（Instance Profile）		ECS/CVM 挂角色，SDK 自动取临时凭证服务器上的标准做法——代码里根本不该出现 AK/SK
OIDC 联邦企业 IdP / GitHub Actions 直接扮演角色CI/CD 与员工登录的最佳实践，见供应链篇
# 错误：代码里硬编码 AK/SK
const s3 = new AWS.S3({accessKeyId: "AKIA...", secretAccessKey: "..."});

# 正确：ECS 实例角色，SDK 自动取临时凭证，代码零密钥
const s3 = new AWS.S3();   // 默认凭据链会从实例元数据服务拿临时凭证
跨账号角色的"混淆代理"（confused deputy）防护：当你的角色允许第三方扮演时，信任策略必须带 ExternalId 条件，否则攻击者可以让自己的账号扮演你的角色来访问你的资源： "Condition": {"StringEquals": {"sts:ExternalId": "唯一随机字符串"}}。没有 ExternalId 的跨账号信任，是云上最隐蔽的越权模式。
模块 3

网络安全：暴露面收敛

安全组：0.0.0.0/0 是事故入口

# 高危配置（三家的安全组都这样）：对互联网开放管理端口
入方向 0.0.0.0/0  -> 22/tcp   (SSH)      # 爆破入口
入方向 0.0.0.0/0  -> 3389/tcp (RDP)      # 同上
入方向 0.0.0.0/0  -> 3306/tcp (MySQL)    # 数据库直接裸奔
入方向 0.0.0.0/0  -> 6379/tcp (Redis)    # 未授权访问经典款

# 收敛后的标准姿势
入方向 10.0.0.0/8   -> 22/tcp            # 管理流量只走内网
入方向 办公网公网出口IP -> 22/tcp          # 运维入口限死 IP
入方向 安全组ID(应用层) -> 3306/tcp        # 数据库只许应用安全组访问
公网 80/443 只挂在 WAF/CLB 后面           # 不直接挂到 ECS 上
安全组的三条工程纪律：① 引用安全组而不是 IP 段做东西向流量控制（应用安全组 → 数据库安全组），实例扩缩容不用改规则；② 管理平面与数据平面分离——SSH/RDP 走堡垒机或 SSM Session Manager（AWS）/ 云助手，不直接开公网；③ 定期用配置核查（AWS Config / 阿里云配置审计）扫"0.0.0.0/0 + 高危端口"组合，发现即告警。

网络分层与私网互联

机制作用安全要点
VPC 子网划分公网子网（NAT/CLB）+ 应用子网 + 数据子网数据层子网不配公网路由，出网走 NAT 网关
NAT 网关私网实例统一出网出口 IP 固定可控，方便给对方加白名单
私网连接
（PrivateLink/云连接/私网 CLB）		跨 VPC/跨账号服务互访不走公网敏感服务（数据库、中间件）只暴露内网 Endpoint
VPC Flow Logs记录网卡级流量五元组横向移动排查的核心证据，默认要开
模块 4

数据安全：KMS、Bucket 与加密备份

存储桶公开访问：一键公开，全球可读

# 错误示范：Bucket Policy 允许任何人读
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::my-bucket/*"
}

# 防护：账号级打开"阻止公共访问"（四段开关全开）+ 只允许 HTTPS + 只允许本账号
{
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": ["arn:aws:s3:::my-bucket", "arn:aws:s3:::my-bucket/*"],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}
Bucket 公开是数据泄露的第一大形态，且往往是"临时开一下方便调试，忘了关"。纪律：① 组织级（AWS Organizations SCP / 阿里云 RAM 策略 / 腾讯云 CAM 策略）强制拒绝"Public"的 ACL 与 Bucket Policy；② 静态网站托管走 CloudFront/CDN + OAC（源站访问身份），不要把 bucket 设 public；③ 配置审计持续扫描公开性。

KMS 与信封加密

概念说明
CMK（客户主密钥）你自己创建、自己管策略的 KMS 密钥。策略决定谁能用、能做什么（加密/解密/轮换）
信封加密KMS 只加密"数据密钥"，数据密钥加密实际数据。大文件不必每次都调 KMS，本地完成加解密
自动轮换开启后 KMS 每年自动换底层密钥材料，旧密文仍可解密——轮换不影响可用性
密钥策略 vs IAMCMK 的策略是"谁能用这把钥匙"，IAM 是"谁能调 KMS API"。两道门都要设
加密的常见误区：① "服务端默认加密就够了"——默认加密用云厂商托管密钥，合规场景（等保/金融）常要求 CMK 自管密钥；② 忘了备份也要加密（快照、OSS 跨区复制、日志归档，加密配置不会自动继承）；③ 密钥和数据放同一个账号同一个角色下——密钥的权限要和数据权限分离，拿到数据角色不该拿到解密能力。
模块 5

日志与审计：CloudTrail / 操作审计

云审计日志是事后溯源的唯一事实来源。原则：先全量收，再谈分析。

厂商管理事件审计数据事件（对象读写）
AWSCloudTrail（管理事件默认免费保留 90 天，但必须配 Trail 投递到 S3）S3 数据事件、Lambda Invoke 等需单独开启
阿里云操作审计 ActionTrail（投递到 SLS/OSS）OSS 访问日志、RDS SQL 洞察
腾讯云操作审计（投递到 CLS/COS）COS 访问日志、数据库审计

六条最小告警规则

# 1. 根账号（root）有任何活动 —— root 只该用于开户和应急
事件: ConsoleLogin / 任何 API，userIdentity.type = "Root"

# 2. 关闭了审计日志本身（攻击者消灭证据）
事件: StopLogging / DeleteTrail / UpdateTrail（CloudTrail）
事件: StopActionTrail / DeleteTrail（阿里云）

# 3. IAM 策略大改（提权前兆）
事件: CreatePolicyVersion / AttachUserPolicy / CreateAccessKey

# 4. 公开性变更（数据泄露前兆）
事件: PutBucketPolicy / PutBucketAcl（策略含 Public / * 立即高危）

# 5. 高危操作行为
事件: RunInstances（莫名开机挖矿）/ DeleteDBInstance / ModifyDBSubnetGroup

# 6. 异地/非常用时段登录
条件: sourceIPAddress 不在常用地域 + 非工作时间 ConsoleLogin
告警落地三件套：① EventBridge/云监控 → 钉钉/飞书/企业微信，5 分钟内到人；② Config / 配置审计规则做持续性合规检查（bucket 公开、安全组 0.0.0.0/0、未加密磁盘），漂移即告警；③ GuardDuty / 安全中心 / 云安全中心开启智能威胁检测（异常 API 调用、恶意 IP 通信），三个厂商都有，默认不开是最大浪费。
模块 6

容器与 Serverless 安全面

容器（ACK/EKS/TKE）

层面安全要点
镜像基础镜像最小化（distroless/alpine）、CI 里跑镜像扫描（Trivy/Grype）、只信签名镜像（cosign + 准入验签，见供应链篇）
运行时容器以非 root 跑、只读根文件系统、drop ALL capabilities、禁特权容器
集群API Server 不暴露公网、RBAC 最小权限（不给开发 cluster-admin）、NetworkPolicy 默认拒绝东西向
密钥Secret 加密存储（KMS 集成），或外部密钥服务挂载；镜像里不烤密钥

Serverless（函数计算 FC / Lambda / SCF）

  • 执行角色最小化：函数角色是云上最容易被过度授权的——一个函数给了 s3:*，代码里一个 SSRF 就是全桶读。按函数逐个收紧。
  • 触发器鉴权：API 网关/函数 URL 的认证方式别用 NONE；EventBridge/Kafka 触发要校验来源。
  • 环境变量里的密钥：明文 env 存密钥是常见做法但不达标，用 KMS 加密 env 或密钥管理服务。
  • 并发与依赖：函数层/依赖包的供应链同样要管（参考供应链篇的 lockfile + 扫描）。
容器与 Serverless 的共同误区："容器跑在集群里所以内网很安全"——东西向流量默认全通，一个被拿下的 Pod 能横着摸遍集群。默认拒绝的 NetworkPolicy + 服务间 mTLS（Istio/ASM 类）才是内网安全的正解。
模块 7

密钥泄露应急响应

AK/SK 泄露是云上最高频的安全事件（Git 泄露、日志打印、离职员工、钓鱼）。应急响应的目标：最短时间让密钥失效，同时算清影响面。

0~15 分钟：止损——控制台/CLI 立即 Disable 或 Delete 泄露的 AccessKey（阿里云 RAM / 腾讯云 CAM 同样操作）。先禁用再复盘，别先开会。
15~60 分钟：影响面排查——用 CloudTrail/操作审计查该密钥历史上所有调用记录：创建过什么资源（RunInstances 挖矿、CreateUser 留后门）、改过什么策略、读过什么 Bucket、从哪些 IP 发起（是否异常地域）。
1~4 小时：清理后门——重点查：攻击者创建的 IAM 用户/角色/AK（给自己留的持久化）、新增的安全组规则、公网开的 Bucket、新增的弹性网卡/镜像、计划任务（crontab、定时函数）。
当天：根因与通报——泄露路径定位（哪次提交、哪个日志、哪台机器），按合规要求评估是否需要上报；通知可能受影响的业务方。
一周内：制度化——全仓库密钥扫描（gitleaks 进 CI）、代码评审禁硬编码、服务器密钥改走实例角色/OIDC、历史密钥全量轮换。
# 用 CLI 查泄露密钥的历史调用（AWS）
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIAXXXXXXXX \
  --max-time 30d ago --max-items 50

# 阿里云：操作审计里按 AccessKeyId 过滤事件
# 关键看四类：Create*/Run*（建资源）、Put*Policy（改权限）、
#          GetObject（读数据）、ConsoleLogin（登录行为）
血的教训三条：① "改个名继续用"是错——泄露过的密钥必须作废重建，攻击者可能早已备份；② 别忘了查"攻击者创建的备用凭证"——删了泄露的那把，他三天后用自建的 AK 又回来了；③ 日志保留期是关键——Trail 只开 90 天默认的话，半年前的刺探你根本查不到，所以 Trail 必须投递到自己的存储并长期保留。
模块 8

云配置错误 TOP10

按真实泄露事件的出现频率排序。每条都可以用配置审计规则自动扫描，不需要人工。

#错误配置后果与检测
1存储桶公开可读/可写数据全球可达。检测：配置审计扫 bucket ACL/Policy 含 Public 或 Principal:*
2安全组 0.0.0.0/0 放通高危端口22/3389/3306/6379/9200 直接暴露。检测：规则 source 为 0.0.0.0/0 且端口在白名单外
3root/主账号日常使用root 权限无边界、无法审计到人。检测：root 有任何 API 调用即告警
4未启用 MFA密码泄露即门户大开。检测：主账号+所有 Console 用户无 MFA 设备即违规
5IAM 过度授权Action:* + Resource:*、给人发 AdministratorAccess。检测：Access Analyzer 标未使用权限
6审计日志未开/未留存出事无法溯源。检测：Trail/ActionTrail 是否存在且投递正常
7长期 AK/SK 硬编码进 Git 即泄露。检测：gitleaks 扫仓库 + 控制台"密钥年龄>90 天"报告
8数据库公网可达RDS 开公网地址 + 弱口令。检测：RDS 实例 publicIP 非空即告警
9磁盘/快照未加密快照被共享即裸奔。检测：EBS/云盘 encryption 为 false、快照共享范围
10日志服务本身可被关攻击者 StopLogging 毁证。检测：对 StopLogging/DeleteTrail 类事件配 SCP 拒绝 + 实时告警
一键自查的思路：三条免费/低成本动作覆盖大半风险——① 打开账号级的"阻止公共访问"组织策略（SCP/资源目录）；② 用 Access Analyzer / 配置审计跑一遍全账号扫描，把标红的排进 SLA；③ 给所有 Console 用户强制 MFA，主账号 MFA + 删除 root AK。这三件事一个下午能做完，挡住最常见的三类事故。
模块 9

十个真实坑

1
"临时"把 bucket 设成 public 忘了关
数据泄露第一大形态。组织级策略强制拒绝 Public ACL/Policy，静态站走 CDN + OAC，别图省事直接 public。
2
安全组图省事全放 0.0.0.0/0
"内网服务没关系"——VPC 内一个服务被拿下就能横摸数据库。东西向用安全组引用，管理面走堡垒机。
3
用 root 账号日常操作
权限无边界、审计不到人、密码泄露即全线失守。root 只开户和应急，日常用 IAM 用户 + MFA。
4
AK/SK 写死在代码/配置里进了 Git
就算删了提交历史里还在。CI 加 gitleaks，服务器用实例角色，泄露按模块 7 的应急流程作废+排查。
5
给人发 AdministratorAccess"反正都是自己人"
离职员工、被钓鱼的开发都能一键删库。按服务拆策略 + Access Analyzer 定期收权。
6
CloudTrail 只开默认 90 天，没投递 S3
半年前的刺探查不到，攻击者毁证也追不回。Trail 必须投递自有存储 + 长期保留 + WORM。
7
跨账号角色信任没设 ExternalId
混淆代理越权：第三方能用你的角色访问你的资源。sts:ExternalId 条件必须带。
8
快照/备份没加密、共享范围过大
共享出去的快照等于把数据送人。快照加密 + 共享对象白名单，定期审。
9
函数执行角色给了 s3:* 全桶权限
Serverless 最常见的过度授权，代码一个 SSRF 全库被读。按函数逐个收紧到具体 action+resource。
10
泄露应急只删了钥匙，没查后门
攻击者早建了备用 IAM 用户和 AK，三天后换钥匙又进来。应急必须查 Create*/Put*Policy 全量记录。
自测

六道题

1. 你用了云厂商的 RDS，数据库引擎补丁和底层硬件归谁管？
正确答案：责任共担，PaaS 层厂商管到运行时。RDS 的引擎补丁是厂商责任，但安全组白名单、数据库账号权限、是否开公网地址、参数组合规性全是你的。拖库事故里"找厂商索赔"从来不成立。
2. 服务器上运行的应用要访问 S3/OSS，最安全的凭据方式是？
正确答案：实例角色 + 临时凭证。代码和配置里不该出现静态 AK/SK——进 Git 即泄露、不过期即长期有效。实例角色让 SDK 自动获取 1 小时过期的临时凭据，权限还能按实例逐个收紧。
3. 发现公司 GitHub 仓库泄露了一枚云 AK，第一步应该？
正确答案：先禁用密钥。泄露的每一秒攻击者都可能在建挖矿实例、留后门账号。Git 历史删除是次要的（历史记录仍可恢复，且密钥本身必须作废）。之后按"影响面排查 → 清后门 → 根因通报 → 制度化"走完整流程。
4. 下列哪条 IAM 策略符合最小权限原则？
正确答案：具体 action + 具体资源 + 传输加密条件。s3:* 包含 DeleteBucket 等高危操作；*:* 等于把保险柜钥匙贴大门上。条件键（SecureTransport/SourceIp/RequestedRegion）是免费的额外收紧。
5. 云上数据泄露的最高频配置错误是？
正确答案：Bucket 公开。且常因"临时开一下忘了关"造成。防护：组织级 SCP/资源目录强制拒绝 Public、静态站走 CDN + OAC、配置审计持续扫描公开性。
6. 关于跨账号 IAM 角色信任，ExternalId 的作用是？
正确答案：防混淆代理。没有 ExternalId 时，知道角色 ARN 的任何账号都可能尝试扮演；带上约定的唯一随机串后，只有持有该串的调用方能通过 sts:ExternalId 条件校验。跨账号信任的标配。
