模块 1

对称加密：AES 与工作模式

AES 是块加密算法：把 128 bit（16 字节）的明文块加密成 128 bit 密文块，密钥 128/192/256 bit。但 AES 本身只加密一个块，"怎么加密任意长数据"由工作模式决定 —— 选错模式比选错算法更常见。

模式原理工程结论
ECB每个块独立用同一密钥加密，相同明文块 → 相同密文块禁用。著名的"ECB 企鹅图"就是明文结构直接暴露在密文里
CBC每块先与上一块密文异或再加密；需要 IV 和 padding；只加密不认证遗留系统常见。有填充 oracle 攻击史（BEAST/Lucky13），新系统别用
CTR把块加密当流加密用：加密"计数器"得到密钥流，与明文异或可并行、无需 padding，但同样不认证
GCMAEAD：CTR 加密 + GMAC 认证标签，一次同时提供机密性与完整性默认选择。TLS 1.3 唯一允许的模式；支持 AAD（附加认证数据）

IV / nonce 的唯一性：GCM 的生命线

# CBC 的 IV：只需"不可预测"，每次随机即可（通常与密文一起存储）
# GCM 的 nonce：必须"全局唯一"。为什么？
# 同一个 nonce + 同一个密钥加密两段不同明文 → 两段密钥流相同 →
# 两段密文异或 = 两段明文异或，信息直接泄露；更糟的是，
# 攻击者可借此恢复出认证密钥 H，之后能伪造任意认证标签。
# 所以 GCM nonce 重用不是"削弱安全性"，是"灾难"。

# 工程解法：
# ① 96 bit 随机 nonce（生日碰撞约 2^32 次后风险上升，适合短会话）
# ② 计数器/序列号 nonce：单调递增，配合同一密钥绝不重复（长连接推荐）
# ③ 别自己拼 nonce —— 用库的默认实现（cryptography 的 AESGCM 每次生成随机 nonce）

Python 正确姿势（cryptography 库）

from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

key = AESGCM.generate_key(bit_length=256)     # 256 bit 密钥，来自 CSPRNG
aesgcm = AESGCM(key)
nonce = os.urandom(12)                        # 96 bit 随机 nonce，只用于这一次加密
ct = aesgcm.encrypt(nonce, b"secret data", associated_data=b"user_id=42")
# 存储：nonce + ct（通常再 base64）。解密：
plain = aesgcm.decrypt(nonce, ct, associated_data=b"user_id=42")   # AAD 不一致会直接抛异常

Node 与 openssl

// Node：crypto 内置 AEAD
const cipher = crypto.createCipheriv("aes-256-gcm", key, nonce);
cipher.setAAD(Buffer.from("user_id=42"));
const ct = Buffer.concat([cipher.update(plaintext), cipher.final(), cipher.getAuthTag()]);
// getAuthTag() 拿到的 16 字节认证标签必须一起存储，解密时 setAuthTag 校验

# openssl 命令行（交互演示用，生产用库）
openssl enc -aes-256-gcm -pbkdf2 -iter 100000 -salt -in plain.txt -out enc.bin -pass pass:"强口令"
# 注意：enc 是"口令派生密钥"的演示形态，生产系统应使用 KMS 管理的原始密钥
两个高频错误：① 全站共用同一个 IV/nonce（写在配置里"方便复用"）—— GCM 下这是灾难级错误；② 只加密不认证——CBC/CTR 密文可被篡改（bit-flipping 攻击改明文），必须叠 HMAC 或直接用 GCM。"加密了"不等于"防篡改"，机密性和完整性是两个目标。
模块 2

非对称加密：RSA 与 ECC

非对称加密用一对密钥：公钥公开，私钥保密。它解决对称加密的"密钥怎么送"问题，但速度慢几个数量级 —— 所以真实系统几乎都是混合加密：非对称交换密钥，对称加密数据。

算法用途与要点工程结论
RSA加密用 OAEP 填充（不要 PKCS#1 v1.5，后者有 Bleichenbacher 攻击史）；签名用 PSS；密钥 ≥ 2048 bit（3072 更稳）兼容性好、速度慢、密钥长。新系统可以少用
ECC / ECDH同样的安全性用短得多的密钥：P-256 ≈ RSA-3072。ECDH 做密钥交换，ECDSA 做签名现代首选，TLS 1.3 / SSH 默认曲线
X25519专门为密钥交换设计的 Curve25519 变体，常数时间实现、参数无歧义密钥交换的最省心选择（Signal 协议、TLS 1.3 都在用）
Ed25519配套的数字签名算法签名的最省心选择

混合加密：一次完整的数据加密传输

# 场景：A 要把数据安全发给 B（B 的事先公布 RSA/ECC 公钥）
# 1. A 生成一个临时对称密钥 K（CSPRNG，只用一次 = 会话密钥）
# 2. A 用 K + AES-GCM 加密数据 → 密文 C（快）
# 3. A 用 B 的公钥加密 K → 加密后的密钥 W（RSA-OAEP / ECIES）
# 4. A 把 (W, C) 发给 B
# 5. B 用私钥解出 K，再解出明文
# 这就是 TLS 传输阶段的骨架，也是 age / PGP 大文件的思路
# ⚠️ 别用 RSA 直接加密大数据：RSA 密文长度受模长限制，且慢几个数量级

openssl 实战：生成、派生、加解密

# ===== RSA =====
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out rsa.key   # 生成私钥
openssl pkey -in rsa.key -pubout -out rsa.pub                              # 导出公钥
openssl pkeyutl -encrypt -pubin -inkey rsa.pub -in msg.txt -out msg.enc  # OAEP 加密
openssl pkeyutl -decrypt -inkey rsa.key -in msg.enc -out msg.dec          # 解密

# ===== ECC：X25519 密钥交换 + Ed25519 签名 =====
openssl genpkey -algorithm X25519 -out x25519.key           # 密钥交换私钥
openssl genpkey -algorithm ED25519 -out ed25519.key        # 签名私钥
openssl pkey -in ed25519.key -pubout -out ed25519.pub       # 签名公钥
openssl pkeyutl -sign -inkey ed25519.key -in file.txt -out file.sig   # 签名
openssl pkeyutl -verify -pubin -inkey ed25519.pub -sigfile file.sig -in file.txt  # 验签
非对称加密的经典误用：① 自己生成 DH 参数或复用可疑的群参数 —— 用标准曲线（X25519/P-256）或 openssl 生成并通过 openssl dhparam 3072 校验；② RSA 用 PKCS#1 v1.5 填充做加密 —— 兼容场景外一律 OAEP；③ 把私钥当普通文件提交进 Git —— 私钥是资产，进 KMS 或至少加密存储 + 权限最小化。
模块 3

哈希、长度扩展攻击与 HMAC

哈希函数把任意长输入压成定长摘要。它有三个你可能正在误用的前提：单向、抗碰撞、定长输出。而 MD5/SHA-1/SHA-2 家族的 Merkle-Damgård 结构，藏着一个叫"长度扩展"的坑。

算法状态用途
MD5已死。碰撞可构造（几秒级）仅存于兼容老文件校验位，安全场景零用途
SHA-1已死。2017 年 SHAttered 实证碰撞Git 对象名还在用，但别用做安全校验
SHA-256 / SHA-384 / SHA-512当前主力，无实用碰撞完整性校验、证书指纹、HMAC 底座
SHA-3（Keccak）新一代，海绵结构，无长度扩展问题可选；与 SHA-256 并存使用没问题

长度扩展攻击：为什么 SHA256(secret || msg) 不是安全的 MAC

# 一个看似合理的"签名"设计：服务端用 secret 拼上消息再哈希
mac = SHA256(secret + "amount=100")

# 攻击原理（Merkle-Damgård 结构的特性）：
# ① 这类哈希是"分块压缩"结构：处理完 secret+msg 的内部状态，
#    就等于继续处理后续数据时的初始状态
# ② 攻击者知道 mac（= 最终状态）和 secret+msg 的长度，
#    就能算出 SHA256(secret + msg + padding + 攻击者追加内容) 的值，
#    —— 全程不需要知道 secret！
# ③ 于是攻击者伪造出 mac' 对应 "amount=100&admin=1" 这类扩展消息

# 修复一（推荐）：用 HMAC，它就是为堵这个洞设计的
mac = HMAC-SHA256(key, "amount=100")
# HMAC 的 ipad/opad 双层结构打断了"内部状态 = 可继续扩展"的性质

# 修复二：把 secret 放尾部 —— SHA256(msg + secret) 不受长度扩展影响，
# 但仍有其他隐患（长度泄漏、拼接歧义）。直接 HMAC，别自己造。
# 三端 HMAC 正确姿势
// Python
import hmac, hashlib
hmac.new(key, msg, hashlib.sha256).hexdigest()

// Node
crypto.createHmac("sha256", key).update(msg).digest("hex")

// openssl 命令行验证
echo -n "amount=100" | openssl dgst -sha256 -hmac "key"
两个必须分清的领域：① 通用哈希 ≠ 密码哈希。存密码要用 bcrypt/argon2（慢速自适应，见认证篇），用 SHA-256 存密码是经典错误；② 完整性 ≠ 认证。公开文件的 SHA-256 值只防"下载损坏/篡改而未同时改公示值"的场景；要防"攻击者同时改文件和哈希"，必须 HMAC（对称密钥）或数字签名（非对称）。
比对哈希/签名/令牌时用常数时间比较（Python hmac.compare_digest、Node crypto.timingSafeEqual）—— 普通 == 的提前返回会泄露信息，这就是时序侧信道。
模块 4

密码学随机数：CSPRNG 与 Math.random

密钥、IV、盐、令牌、验证码 —— 凡是"猜不到"有价值的地方，都必须用 CSPRNG。用错随机源，等于用密码学保护了一把 predictability 的锁。

随机源性质结论
Math.random() / rand() / mt_rand()普通 PRNG，内部状态有限（如 V8 xorshift128+），观察少量输出可反推状态、预测后续安全场景禁用。只能用于抽奖、抖动、测试数据
os.urandom / secrets（Python）操作系统 CSPRNG（getrandom(2)，熵池 + DRBG）安全场景正确选择
SecureRandom（Java）同上，默认 NativePRNG安全场景正确选择
crypto.randomBytes（Node）同上，基于 OpenSSL DRBG安全场景正确选择
/dev/urandom（Linux）内核 CSPRNG，不会"阻塞"（初始化后）安全场景正确选择（别用 /dev/random，那是过时观念）
# 生成一个安全的会话令牌（三端）
// Python：secrets 模块就是为安全设计的标准库
import secrets
token = secrets.token_urlsafe(32)        # 256 bit 熵，URL 安全

// Java
SecureRandom sr = SecureRandom.getInstanceStrong();
byte[] b = new byte[32]; sr.nextBytes(b);   // Base64 编码后使用

// Node
crypto.randomBytes(32).toString("base64url")

# 反面教材：用时间戳 / 自增 ID / Math.random 当"随机 token"
Math.random().toString(36).slice(2)   // 预测成功只是时间问题
md5(Date.now())                          // 枚举空间小到可笑
"熵够不够"的粗判标准：安全令牌至少 128 bit 随机（16 字节 CSPRNG 输出，base64 后约 22 字符）。低于这个量级，即使源是 CSPRNG，也可能被在线暴力枚举。UUIDv4 是 122 bit 随机，勉强及格；要更长寿命的令牌直接用 32 字节。
审计自己代码的命令：全局搜索 Math.random、rand()、mt_rand、shuf()，逐个判断上下文是否涉及安全。
模块 5

数字签名与证书链（PKI / X.509）

非对称密码有三个用途：加密（公钥锁、私钥开）、签名（私钥签、公钥验，证明"这个消息确实出自持钥人且未被改过"）、密钥交换。PKI 就是把"签名"用在身份管理上的体系。

X.509 证书与证书链

# 一张证书里有什么：持有者身份、公钥、有效期、颁发者 CA、CA 的数字签名
openssl x509 -in server.crt -noout -text | head-30   # 看证书全文
openssl x509 -in server.crt -noout -subject -issuer -dates    # 主体、颁发者、有效期

# 证书链验证：服务器证书 → 中间 CA → 根 CA（根证书预装在操作系统/浏览器里）
openssl verify -CAfile root.crt -untrusted intermediate.crt server.crt
# 验证逻辑：每张证书的签名由上一级公钥验证，一路验到信任锚（根 CA）
# 校验项还包括：有效期、域名匹配（SAN 扩展）、用途（EKU）、吊销状态（CRL/OCSP）

# 吊销机制：证书泄露/误签发后作废
# CRL：定期下载的吊销名单（体积大、有延迟）
# OCSP：在线查询单张证书状态（实时，但有隐私与可用性问题，故有 OCSP Stapling）

自签名 vs CA 签发：边界在哪

# 自签名证书：自己签自己。能加密，但客户端无法验证"这是不是真的你的服务器"
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes \
  -subj "/CN=localhost"   # 本地开发/内网自用没问题
# 公网服务必须用受信任 CA 签发的证书，否则浏览器报警 = 用户被训练成"点掉警告"

# 域名匹配看的是 SAN（Subject Alternative Name），CN 已淘汰：
openssl x509 -in server.crt -noout -ext subjectAltName
代码侧要点：① 客户端验证 TLS 时不要关闭证书校验（verify=False、rejectUnauthorized: false 是线上事故的常见前兆）；② 校验"域名与 SAN 匹配"，不只是"链能验过"；③ 私钥只属于持有者，公钥可以随便发 —— 搞反这两个的"自研协议"，等于没加密。④ 签名验签和哈希一样，用常数时间比较。
模块 6

TLS 握手回顾与 TLS 1.3 简化

TLS 是密码学的集大成应用：证书认证 + 密钥交换 + 对称加密 + 完整性，一次握手全安排。TLS 1.3（RFC 8446）的核心变化是"删"——删掉了所有不安全的旧机制，并把握手压到 1-RTT。

握手在干什么（三步本质）

认证：服务器出示 X.509 证书链，客户端验证到信任锚，确认"对面是我要找的服务器"（防中间人）。
密钥交换：用 (EC)DHE 协商出预主密钥，双方各自派生会话密钥。每次握手的临时密钥用完即弃——这就是前向保密（PFS）：即使服务器私钥日后泄露，过去的会话也解不开。
加密传输：后续记录用 AEAD（AES-GCM / ChaCha20-Poly1305）加密，一次同时保证机密与完整。

TLS 1.2 → 1.3：被删掉的东西

1.3 删除 / 变更原因
RSA 密钥交换无前向保密：私钥泄露 = 历史流量全可解。1.3 只保留 (EC)DHE
静态 RSA / 静态 DH 套件同上，统一临时密钥交换
CBC 模式、压缩、重协商分别是 BEAST/Lucky13、CRIME、重协商攻击的根源
MD5/SHA-1 签名、RC4、3DES、DES全部淘汰
握手 2-RTT → 1-RTTClientHello 里直接带上密钥共享参数，ServerHello 后即可发应用数据
0-RTT 恢复重连时复用上次会话直接发数据。快但有重放风险，只应用于幂等请求
# 实战一：看线上握手详情（1.3 应该看到 TLSv1.3 + x25519 + AES-GCM）
openssl s_client -connect example.com:443 -tls1_3 < /dev/null 2>/dev/null | grep -E "Protocol|Cipher|Server Temp Key"

# 实战二：看证书链（服务端发的每一级证书）
openssl s_client -connect example:443 -showcerts < /dev/null 2>/dev/null | grep "BEGIN CERTIFICATE"

# 实战三：检查本地是否支持 1.3 与相关套件
openssl ciphers -v 'TLSv1.3' | head-5
运维侧 TLS 清单：协议只留 TLS 1.2/1.3（1.0/1.1 已废弃）；套件优选 ECDHE + AEAD；HSTS 头强制 HTTPS；证书到期监控（Let's Encrypt 90 天，自动化续期）；关闭客户端的证书校验来"排查问题"是借高利贷——查完必须还。
模块 7

密钥管理：KMS、信封加密与轮转

算法都是对的，事故都出在"密钥怎么管"。密钥管理覆盖生命周期六件事：生成、存储、分发、使用、轮转、销毁。任何一环裸奔，前面所有密码学都白搭。

信封加密：为什么云上都在用

# 问题：要加密数据库里 1TB 数据，密钥放哪？
# 方案 A：密钥和应用同机 —— 应用被攻破，密钥和数据一起没
# 方案 B：信封加密（envelope encryption）—— 两层密钥体系

# 1. KMS 里存 KEK（Key Encryption Key，密钥加密密钥，永不离开 KMS）
# 2. 加密数据时，先请 KMS 生成一个 DEK（Data Encryption Key，数据密钥）：
#    KMS 返回 (明文 DEK, 用 KEK 加密后的 DEK)
# 3. 用明文 DEK + AES-GCM 加密数据（本地完成，快）
# 4. 存储：密文数据 + 加密后的 DEK。明文 DEK 用后立即从内存擦除
# 5. 解密时：把加密的 DEK 发给 KMS 解出明文 DEK，再本地解密
# 收益：攻击者偷走数据库 + 备份也拿不到 KEK；KEK 可轮转、有审计日志

# AWS KMS / GCP Cloud KMS / 阿里云 KMS / HashiCorp Vault 都是这个模型，

轮转与版本化

# 密钥轮转（rotation）：定期换新密钥，旧数据仍能用旧密钥解
# 关键设计：密文必须标记"用哪个密钥版本加密的"
#   加密输出格式：{ "kid": "kms-key-v3", "nonce": "...", "ct": "..." }
# 解密时按 kid 取对应版本密钥 —— 这样轮转不需要重加密存量数据
# 轮转周期建议：KEK 1 年 / DEK 按数据分级（越敏感越短）
# 触发式轮转：疑似泄露时立刻轮转 + 作废旧版本（KMS 的 disable/schedule-deletion）
密钥管理的五大死罪：① 硬编码在源码/配置/容器镜像里（Git 历史就是泄露史）；② 全环境共用一个密钥（开发、测试、生产同钥，泄露面 ×N）；③ 不轮转（一个密钥用五年，泄露窗口也是五年）；④ 没有审计（谁在什么时候用了哪个密钥解了什么，答不上来）；⑤ 把密钥打进日志（排查一次线上问题，密钥进 ELK，全网可搜）。
正解：KMS 托管 + 环境变量/短期凭证注入 + 版本化密文 + 定期轮转 + 全链路审计。secret 扫描（gitleaks / trufflehog）进 CI。

上线前七项自查

搜自研加密：代码里搜 xor、base64 "加密"、自定义 cipher，全部替换为标准 AEAD。
搜硬编码密钥：gitleaks / trufflehog 扫全历史；确认密钥从 KMS/环境注入。
搜 ECB 与固定 IV：加密调用确认是 GCM/ChaCha20-Poly1305，nonce 每次不同。
搜 Math.random：安全相关随机全部换 CSPRNG。
搜 MAC 构造：secret+msg 哈希全改 HMAC；签名验签用标准库。
查 TLS 配置：协议版本、套件、证书到期监控、客户端校验未关闭。
查密钥管理：有没有轮转计划、审计日志、按环境隔离的密钥。
避坑

十个真实坑

1
用 AES-ECB 加密"看不出问题"的数据
相同明文块产生相同密文块，图片、JSON、重复字段的结构直接暴露（ECB 企鹅图）。一律用 GCM，没有例外场景。
2
IV/nonce 写死在配置里"复用"
CBC 下 IV 可预测、GCM 下 nonce 重用是灾难（密钥流复用 + 认证密钥可恢复，可伪造任意密文）。每次加密生成新 nonce，或维护全局计数器。
3
密钥硬编码在源码 / 配置 / 镜像里
Git 一次推送 = 永久泄露，改代码也改不了历史。KMS 托管 + 环境注入 + secret 扫描进 CI，泄露后立刻轮转。
4
自己实现加密算法或协议
侧信道、常数时间比较、填充校验、错误处理，每个细节都能单独毁掉整体。用 OpenSSL / libsodium / 语言标准库，别当发明家。
5
用 SHA256(secret || msg) 自制 MAC
Merkle-Damgård 结构的长度扩展攻击：知道 mac 和消息长度即可伪造扩展消息的合法 mac，全程不需要 secret。用 HMAC。
6
用 MD5 或 SHA-1 做安全校验
碰撞攻击已工程化（选碰几秒到几小时），"校验值匹配"不再证明内容未被调包。SHA-256 起步，密码场景用 bcrypt/argon2。
7
Math.random() 生成令牌、盐、IV、密钥
普通 PRNG 内部状态有限，观察少量输出可预测后续。安全随机一律 CSPRNG：secrets / SecureRandom / crypto.randomBytes / os.urandom。
8
只加密不认证（裸 CBC/CTR）
密文每一位都可被翻转来改明文（bit-flipping 攻击），接收方毫无察觉。用 AEAD（GCM）同时获得机密性与完整性。
9
客户端关掉证书校验"为了连通"
verify=False / rejectUnauthorized:false / trustAllCerts 一开，中间人攻击畅通无阻，TLS 退化成透明代理。排完问题必须还回来，CI 里加检查。
10
密钥永不轮转、全环境共用一把
泄露窗口无限长，且开发环境的泄露直接打穿生产。KEK 一年一换、DEK 按敏感度分级，KMS 轮转 + 版本化密文 + 审计日志三件套。
自测

六道题

1. 为什么新系统加密数据应该选 AES-256-GCM 而不是 AES-256-CBC？
正确答案：GCM = 加密 + 认证一体（AEAD）。CBC 密文可以被攻击者逐块翻转来篡改明文（bit-flipping），接收方无法察觉；GCM 自带认证标签，任何篡改都会导致解密失败。两者密钥长度一样，CBC 也没有"被破解"——它只是不提供完整性，且有过填充 oracle 攻击史。
2. 关于 AES-GCM 的 nonce，正确的做法是？
正确答案：每次唯一，且不需保密。同一密钥下 nonce 重用 = 两段数据用同一密钥流加密，明文异或即可泄露；更严重的是可恢复认证密钥 H，之后能伪造任意认证标签。nonce 本身不是秘密，随密文一起存储即可。
3. 服务端用 SHA256(secret + msg) 验证消息，为什么危险？
正确答案：长度扩展攻击。MD5/SHA-1/SHA-2 都是分块压缩结构，处理完 secret+msg 的内部状态就是最终 mac，攻击者可以此状态继续"处理"追加内容，算出合法的新 mac。HMAC 的 ipad/opad 双层结构正是为堵住这个洞设计的。
4. 生成密码重置令牌，下面哪种随机源是安全的？
正确答案：CSPRNG。Math.random 是普通 PRNG，内部状态可被预测；时间戳+用户名的枚举空间极小。安全令牌至少 128 bit 熵，用操作系统 CSPRNG 生成。
5. 信封加密（envelope encryption）的核心思想是？
正确答案：两层密钥体系。KEK 永不离开 KMS（泄露数据库也拿不到它），DEK 每次临时生成、用完即弃。非对称加密直接加密大数据又慢又受长度限制，信封加密用对称密钥加密数据、用 KMS 保护对称密钥，是云上数据加密的标准架构。
6. TLS 1.3 相比 1.2 最重要的安全变化是？
正确答案：只留前向保密的密钥交换 + 删除有攻击史的机制。1.3 删掉静态 RSA 密钥交换（私钥泄露即历史流量全解），统一 (EC)DHE 临时密钥；同时删掉 CBC（BEAST/Lucky13）、压缩（CRIME）、重协商。握手也降到 1-RTT。
