模块 1

输入验证：信任边界是第一道墙

所有漏洞的共同起点是把不可信数据当成了可信数据。先画清信任边界，再谈验证。

三条原则

白名单优先于黑名单——"只允许长度 4~20 的数字字母"永远优于"禁止 < > script 等关键字"。黑名单永远滞后于攻击变形，白名单从原理上封闭未知攻击。
服务端验证，客户端只是体验——前端的 required、maxlength、正则校验都可以被绕过（改包、直连 API、Postman）。所有校验必须在服务端重新执行一遍，客户端校验不重复做就是裸奔。
按类型校验，而非按字符串——能解析成 int 的就用 int 接，能解析成日期的就用日期库解析。类型即校验，比任何正则都可靠。
// Java：白名单验证 + 按类型解析
// 错误：黑名单思维，拦不住的变形一大堆
if (name.contains("<") || name.contains("script")) throw new BadRequest();

// 正确：白名单 + 长度 + 类型
private static final Pattern USERNAME = Pattern.compile("^[a-zA-Z0-9_]{4,20}$");
if (!USERNAME.matcher(input).matches()) throw new BadRequestException("illegal username");
long id = Long.parseLong(rawId);   // 解析失败直接抛， NumberFormatException 比注入安全一万倍
信任边界 Checklist：HTTP 请求的一切部分（URL、Query、Header、Cookie、Body）、上传的文件、外部系统的返回值、数据库里早期版本写入的脏数据、MQ 消息——全部在边界之外。"这是内网系统传来的所以可信"是事故报告里的高频开场白。
模块 2

注入与输出编码：三类注入的根因与修法

SQL 注入：唯一正解是参数化

// Java：MyBatis 用 #{}，JPA 用 :param，都不要用 ${}
// 错误：字符串拼接，注入经典款
String sql = "SELECT * FROM orders WHERE user_id = '" + userId + "'";
// 正确：预编译占位符
String sql = "SELECT * FROM orders WHERE user_id = #{userId}";

// Go：database/sql 的占位符
// 错误：fmt.Sprintf 拼 SQL
q := fmt.Sprintf("SELECT * FROM t WHERE id = %s", id)
// 正确：Query 传参
rows, err := db.Query("SELECT * FROM t WHERE id = $1", id)

// Python：DB-API 的 %s 占位（注意不是字符串格式化！）
// 错误：f-string 直接拼
cur.execute(f"SELECT * FROM t WHERE id = '{id}'")
// 正确：参数化查询
cur.execute("SELECT * FROM t WHERE id = %s", (id,))
为什么参数化是唯一正解：预编译让 SQL 语句结构先于数据发送给数据库，数据永远只是数据，改变不了解释器的语法树。而任何"转义单引号""过滤关键字"的输入侧方案，都有已知绕过手法（宽字节注入、二次注入、不同 DBMS 转义规则差异）。ORM 也不是免死金牌——MyBatis 的 ${}、JPA 的 createNativeQuery 拼串、Django 的 raw() 都保留了拼接后门。

OS 命令注入：能不用 shell 就不用

// Java：不要拼字符串再 Runtime.exec
Runtime.getRuntime().exec("ping -c 1 " + userInput);   // 输入 "8.8.8.8; cat /etc/passwd" 即中招
new ProcessBuilder("ping", "-c", "1", userInput).start();  // 参数数组不经 shell 解析

// Python：subprocess 默认不走 shell，别手动开 shell=True
subprocess.run(f"ping -c 1 {host}", shell=True)     // 头号大坑
subprocess.run(["ping", "-c", "1", host])            // 列表形式天然免疫

// Node.js：exec 走 shell，execFile 不走
exec(`ping -c 1 ${host}`)            // 命令注入
execFile("ping", ["-c", "1", host])   // 安全形式

XSS：输出侧按上下文编码

输出上下文危险字符正确编码方式
HTML 正文< > & " 'HTML 实体编码（&lt; 等）
HTML 属性" ' 反引号属性值必须加引号 + 实体编码
JavaScript 字符串' " \ 换行JSON 序列化 / \x 编码，不能只做 HTML 编码
URL 参数? & # /URL 编码（encodeURIComponent）
// React 默认转义，dangerouslySetInnerHTML 是逃生门
<div dangerouslySetInnerHTML={{__html: userComment}} />   // 直接 XSS，除非先过 DOMPurify
<div>{userComment}</div>                              // JSX 自动转义，默认安全
<div dangerouslySetInnerHTML={{__html: DOMPurify.sanitize(userComment)}} />  // 必须富文本时

// Vue：v-html 同理，{{ }} 是安全的
<div v-html="userComment"></div>   // 危险
<div>{{ userComment }}</div>        // 安全
框架默认安全，危险来自"逃生门"：React/Vue/Angular 的默认插值都做转义，XSS 几乎全部发生在 dangerouslySetInnerHTML、v-html、[innerHTML]、拼接 SQL/HTML 字符串这几个逃生口。Code Review 看到这几个 API 就该条件反射。
模块 3

敏感数据处理：日志脱敏与异常信息

日志脱敏：先分类，再处理

数据类别示例日志里的处理
身份凭证密码、token、AK/SK、Session ID绝不打印。框架默认可能打印请求体，要显式脱敏
个人隐私手机号、身份证、银行卡、住址掩码：138****0000；保留后四位用于排查
业务敏感订单金额、余额、健康数据按合规要求（等保/GDPR）决定是否可入日志
// Java：Logback 的脱敏配置 + 代码层掩码
// logback-spring.xml：用 %replace 转换器打手机号掩码
<pattern>%d{HH:mm:ss} %replace(%msg){'1[3-9]\d{9}', '****'}%n</pattern>

// 代码层：对象toString不要暴露敏感字段
log.info("login req: {}", req);   // req.toString 里带着 password 字段 = 泄露
log.info("login req: phone={}, codeLen={}", mask(req.getPhone()), req.getCode().length());

// Python：logging 的 filters 或脱敏工具
logging.info("user login: %s", user.__dict__)   // __dict__ 把 password_hash 也带出来了
logging.info("user login: phone=%s", mask_phone(user.phone))
最高频的日志泄露场景：① 异常栈里带出了请求参数（框架自动把出错的入参打进堆栈）；② 第三方 SDK 的 debug 日志默认打印全量报文；③ 为排查问题临时开的 log.debug(request) 忘了删。修法：入站日志统一走脱敏过滤器，禁止直接打印整个请求对象。

异常信息：对外只说"出错了"，细节留在日志里

// 反模式：把堆栈和 SQL 直接返回给调用方
catch (SQLException e) {
  return ResponseEntity.status(500).body(e.getMessage());  // 暴露表名、SQL、驱动版本
}

// 正确：对外一个 traceId，细节进内部日志
String traceId = UUID.randomUUID().toString();
log.error("query failed, traceId={}, sql={}", traceId, sql, e);
return ResponseEntity.status(500)
  .body(Map.of("error", "internal_error", "trace_id", traceId));
错误信息是攻击者的免费情报："Table 'orders' doesn't exist" 告诉对方数据库类型和表名；"expected int, got string" 帮对方校准注入 payload。统一错误响应格式 + 内部 traceId 排错，既安全又不影响可维护性。同理适用于 404 vs 403 的选择——越权访问返回 404 而不是 403，不告诉对方"这个资源存在但你不配"。
模块 4

文件操作安全：路径穿越与上传校验

路径穿越：先规范化，再校验前缀

// Java：canonical 路径 + 前缀白名单
File f = new File("/data/files/" + userPath);   // userPath = "../../etc/passwd" 即穿越

File base = new File("/data/files").getCanonicalFile();
File target = new File(base, userPath).getCanonicalFile();
if (!target.getPath().startsWith(base.getPath() + File.separator)) {
  throw new SecurityException("path traversal");
}

// Python：os.path.realpath 同样思路
path = os.path.join("/data/files", user_path)   // join 不做净化
base = os.path.realpath("/data/files")
full = os.path.realpath(os.path.join(base, user_path))
if not full.startswith(base + os.sep): raise SecurityError("traversal")

// Go：filepath.Clean + 前缀校验
full := filepath.Join(baseDir, filepath.Clean("/"+userPath))  // Clean 掉 ../ 后再拼
if !strings.HasPrefix(full, baseDir) { return errors.New("traversal") }
三个语言的共同模式：规范化（canonicalize）→ 校验前缀。只做字符串替换 replace("../","") 是错得最典型的做法——....// 替换后还原成 ../，嵌套编码也能绕过。另外注意 Windows 短文件名、符号链接、NUL 字节截断（C 系历史问题）这些边界。

文件上传：校验链要完整

大小限制——在网关/反代层（Nginx client_max_body_size）和应用层双重限制，别只靠前端。
类型校验——查魔数（magic bytes）而不是扩展名和 Content-Type（两者都随请求伪造）。白名单只放行需要的类型。
内容检查——图片要过图片解码器（畸形图片会让 ImageMagick 类库崩）；文档类考虑过杀毒引擎。
存储隔离——上传目录不可执行脚本（Nginx 对该 location 关 PHP/ CGI 解析），文件名重命名为随机 UUID，剥离原始文件名。
访问隔离——下载走签名 URL 或经应用层鉴权，不要直接把静态目录映射出去。
// Java：按魔数判断真实类型，不信 Content-Type
String mime = URLConnection.guessContentTypeFromName(name);  // 仅参考
byte[] head = Files.readAllBytes(path, /*前 12 字节*/);
boolean isPng = head[0]==(byte)0x89 && head[1]=='P' && head[2]=='N' && head[3]=='G';
// 再用 ImageIO.read(path) 真正解码一遍，能读出来才算合法图片

// Nginx：上传目录禁执行
location /uploads/ {
    location ~ \.(php|jsp|py|sh)$ { deny all; }   // 上传目录里的脚本一律拒
}
模块 5

并发与资源控制：竞态条件与 TOCTOU

竞态条件（Race Condition）

经典场景：优惠券领取、库存扣减、余额扣款。"先查后写"两步操作之间被并发插入，导致超卖、重复发券。

// 错误：check 和 act 分离，两个线程同时通过 check
if (couponRepo.countByUser(userId) < 1) {      // 查
  couponRepo.save(new Coupon(userId));         // 写 —— 中间被插一剑
}

// 正确一：数据库唯一约束兜底（最终防线）
CREATE UNIQUE INDEX uk_user_coupon ON coupon(user_id, campaign_id);
try { couponRepo.save(c); } catch (DuplicateKeyException e) { return "已领取"; }

// 正确二：原子 UPDATE（条件更新）
UPDATE stock SET n = n - 1 WHERE sku = ? AND n > 0;   // 影响行数 = 0 即售罄
并发安全的三层防线：① 数据库层——唯一索引、乐观锁（version 字段）、条件 UPDATE，这是唯一不会骗你的防线；② 应用层——分布式锁（Redis SET NX）控制并发入口；③ 幂等——同一请求重复提交结果一致（幂等键 + 去重表）。只做中间层不做数据库层，锁失效的那一刻就是事故。

TOCTOU（检查-使用时间差）

// 错误：检查和使用之间文件可能被换成符号链接
if (Files.exists(path)) {            // 检查（check）
  Files.readAllBytes(path);         // 使用（use）—— 此刻 path 可能已换人
}

// 正确：以"打开的文件句柄"为准，不再信路径
try (var in = Files.newInputStream(path)) {   // 打开即绑定，后续只认 fd
  // 对 in 操作；需要元数据时用 in.getChannel() 或 fstat，而不是再查一次路径
}
TOCTOU 的通用心法：把"检查"变成"使用"的一部分。不要在业务代码里先 exists() 再操作；要么打开后基于句柄操作，要么用原子系统调用（如 open(O_CREAT|O_EXCL) 防符号链接攻击）。安全领域里所有"先检查后使用"的模式都值得警惕。

资源控制：给每个入口加上限

资源失控后果控制手段
线程/连接池慢请求占满池，级联雪崩池化 + 超时 + 隔离（舱壁模式）
内存（解压/反序列化）zip 炸弹、超大 JSON 打满堆解压大小上限、流式解析、max depth
外部调用第三方挂了拖死自己超时 + 熔断 + 降级兜底
正则回溯恶意输入让 ReDoS 打满 CPU避免嵌套量词；用 RE2 类无回溯引擎
模块 6

依赖与反序列化安全

反序列化：不反序列化不可信数据

// Java：原生序列化 = 远程代码执行的头号通道
ObjectInputStream in = new ObjectInputStream(request.getInputStream());
Object obj = in.readObject();     // 恶意字节流构造 gadget chain，直接 RCE

// 正确一：换格式，用 JSON（无代码执行语义）
MyDto dto = objectMapper.readValue(body, MyDto.class);

// 正确二：必须用原生序列化时，上白名单过滤器（JEP 290，JDK 9+ 内置）
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
  "com.myapp.dto.*;java.base.*;!*");   // 只允许自己的 DTO 和基础类
in.setObjectInputFilter(filter);

// Python：pickle 同样能执行代码
pickle.loads(untrusted_bytes)     // __reduce__ 可执行任意命令
json.loads(untrusted_bytes)        // 或者 json/orjson，纯数据无副作用
反序列化的铁律：Java 原生序列化、Python pickle、PHP unserialize、Ruby Marshal、Node 的 node-serialize——这些格式的设计目标就包含"重建对象/执行代码"，对不可信输入使用时等于直接执行对方代码。跨服务通信一律用 JSON / Protobuf 这类纯数据格式；必须用原生序列化的内网通道，上白名单过滤 + 网络层隔离双保险。

依赖安全：三道闸

锁定版本——用 lockfile（package-lock.json / go.sum / poetry.lock）锁死传递依赖，保证构建可复现（供应链篇会展开）。
漏洞扫描——CI 里跑 mvn dependency-check / npm audit / pip-audit / govulncheck，已知 CVE 的版本直接 fail。
最小化引入——"为一个函数引一个包"是债务不是资产。每加一个传递依赖都是新的攻击面，评审时要问：这个包值得吗？

高危模式风险与修法

text/template 渲染用户输入模板注入。渲染内容用 html/template（自动上下文转义），text/template 只用于非 HTML

JavaScript / Node.js

高危模式风险与修法
eval() / new Function()任意代码执行。合法场景几乎为零，JSON 用 JSON.parse

// JS：原型链污染的最小复现与修复
// 攻击 payload: JSON.parse('{"__proto__": {"isAdmin": true}}')
// 若被 Object.assign/深合并进配置对象，之后所有对象的 isAdmin 都为 true
// 修复：合并时过滤危险键 + 用 Map 替代普通对象存配置
const DANGEROUS = new Set(["__proto__", "constructor", "prototype"]);
function safeMerge(target, src) {
  for (const k of Object.keys(src)) {
    if (DANGEROUS.has(k)) continue;
    target[k] = src[k];
  }
  return target;
}

// Node.js：JWT 必须验签
const payload = jwt.decode(token);            // 只解码不验签，伪造身份直通
const payload = jwt.verify(token, PUBLIC_KEY, // 验签 + 验声明
  { algorithms: ["RS256"], audience: "my-api", issuer: "auth-server" });
模块 8

错误处理与故障安全

安全代码在出错时的行为和正常时一样重要。故障安全（fail-safe）的意思是：出错时拒绝，而不是出错时放行。

// 反模式：鉴权中间件抛异常 → 兜底逻辑放行了请求
try {
  checkPermission(user, resource);
} catch (Exception e) {
  log.warn("auth error, pass through");   // 致命：鉴权系统故障 = 全员放行
}

// 正确：鉴权失败 = 拒绝，宁可误杀不可放过
try {
  checkPermission(user, resource);
} catch (AuthServiceDownException e) {
  throw new ServiceUnavailableException("auth temporarily unavailable", e);
}   // 503，让请求失败，绝不放行
"出错时放行"的常见变体：① 空 catch 块后继续走正常流程；② catch { return true; } 的校验函数；③ 解析失败时 catch → return null，调用方把 null 当"无限制"处理。Review 看到 catch 块里有 return true / pass / continue，立刻警觉。

其他故障安全要点

  • 默认拒绝：权限系统的默认值必须是"拒绝"（白名单式设计），而不是"允许除非显式禁止"
  • 安全默认值：新功能的开关默认关；新部署的存储桶默认私有；新注册的域名默认开 HSTS
  • 清理要彻底：finally 里关闭资源、清除线程局部变量里的敏感数据、临时文件用后即删
  • 超时即失败：鉴权服务超时应该 fail-closed（拒绝），而不是无限等待后 fail-open
模块 9

#检查项看什么

模块 10

十个真实坑

1
只做前端校验，服务端裸奔
required/maxlength 用 Postman 或 curl 一秒绕过。所有校验必须在服务端重做一遍，客户端校验只是体验优化。
2
以为 ORM 就免疫 SQL 注入
MyBatis ${}、Django raw()、Hibernate createNativeQuery 拼接都保留后门。参数化是唯一标准，与用不用 ORM 无关。
3
过滤关键词代替参数化
replace("'","''")、黑名单关键字都有已知绕过（宽字节、编码变形、二次注入）。修法是预编译，不是更努力地过滤。
4
日志里打印整个请求对象排查问题
toString 里的 password、token 全量落盘，日志系统成了泄露库。入站日志统一走脱敏过滤器。
5
异常堆栈直接返回给前端
表名、SQL、驱动版本、内网路径全暴露。对外统一错误响应 + traceId，细节只进内部日志。
6
文件上传目录配了脚本执行权限
传个 webshell 上去直接 RCE。上传目录必须禁执行，文件名重命名为 UUID，下载走应用层鉴权。
7
优惠券/库存"先查后写"没有 DB 兜底
并发下超卖、重复发券。唯一索引/条件 UPDATE 是最终防线，Redis 锁只是优化。
8
用 pickle / 原生序列化传不可信数据
等于直接执行对方代码。跨服务通信换 JSON/Protobuf；必须用就上白名单过滤器。
9
用 math/rand 生成 token
Go 的 math/rand、Python 的 random 都是可预测的。安全用途一律 crypto/rand、secrets 模块。
10
鉴权服务故障时"先放行再说"
catch 里 return true 让故障期间全员无鉴权访问。fail-safe 原则：出错时拒绝，503 好过裸奔。
自测

六道题

1. 关于防 SQL 注入，正确的工程结论是？
正确答案：参数化是唯一正解。转义有宽字节、二次注入等绕过手法；ORM 也保留了 raw()、${} 等拼接后门。预编译让数据结构先于数据到达数据库，数据永远无法改变语法树。
2. 用户上传头像，服务端校验文件类型最可靠的方式是？
正确答案：魔数 + 真实解码。扩展名和 Content-Type 都随请求伪造，攻击者把 PHP 脚本改成 .png、声明 image/png 就能过。真正能解码成合法图片，才说明内容结构是图片。
3. 优惠券领取接口"先查已领数量，再插入领取记录"，高并发下会？
正确答案：会超领，需要 DB 层兜底。两个线程可以同时通过"已领数量 < 1"的检查。唯一索引（user_id + campaign_id）或条件 UPDATE 是最终防线；Redis 分布式锁只是入口优化，锁失效即失效。
4. Python 代码里哪个写法对不可信输入是安全的？
正确答案：json.loads。pickle 的 __reduce__ 可执行任意命令，"内网"不是信任理由；eval 前的正则过滤是黑名单思维，永远有绕过。纯数据格式（JSON/Protobuf）没有代码执行语义。
5. Node.js 里 Object.assign(target, JSON.parse(userJson)) 遇到 {"__proto__": {...}} 会导致？
正确答案：原型链污染。__proto__ 键会顺着原型链写到 Object.prototype 上，之后所有对象读取该属性都拿到被污染的值（如 isAdmin: true）。修法：过滤 __proto__/constructor/prototype 键，或用 Object.create(null)、Map。
6. 鉴权中间件调用鉴权服务超时了，最安全的处理是？
正确答案：fail-closed，503 拒绝。故障安全原则：出错时拒绝而非放行。鉴权服务故障期间全员无鉴权访问，是比服务抖动严重得多的安全事故。用户体验和安全性冲突时，安全优先。
