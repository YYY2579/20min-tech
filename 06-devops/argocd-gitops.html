二十分钟学透 ArgoCD 与 GitOps

GitOps 把"部署"变成"Git 提交 + 自动协调"。ArgoCD 是 K8s 生态最主流的 GitOps 引擎。这篇讲机制：四条原则、控制器架构、同步策略、sync waves、多集群、密钥管理，以及自动同步误删、CRD 顺序、大仓库性能这些真实坑。

开始前

GitOps 四条原则（OpenGitOps 标准定义）

GitOps 不是"用 Git 管理配置"这么简单。CNCF OpenGitOps v1.0 给出四条原则，ArgoCD 的每个设计都能对应上：

#原则ArgoCD 的对应实现
1声明式整个系统的期望状态用 K8s 清单（可 Helm/Kustomize 生成）完整描述
2版本化 + 不可变期望状态存 Git，有完整历史，工件不可变（tag/commit SHA）
3自动拉取软件 agent（application-controller）主动从 Git 拉取并比对集群，而不是 CI 推送到集群
4持续协调agent 持续对比"Git 声明"与"集群实况"，有差异就修复（self-heal），并上报漂移

Push vs Pull：为什么"自动拉取"是划时代的设计

模式传统 CI 推送GitOps 拉取
谁发起CI 流水线 kubectl apply集群内 controller 轮询/webhook 触发
凭证位置CI 系统要存集群 admin 凭证集群外出不了网也能被管理；CI 只碰 Git，不碰集群
漂移处理没人管，kubectl edit 后状态腐烂持续协调，手工修改被自动纠正（self-heal）
回滚重新跑旧流水线，环境未必一致git revert，历史即回滚记录
审计流水线日志七零八落Git 提交历史就是审计日志（谁、何时、改了什么）
落地 ArgoCD 的前提：所有集群变更必须走 Git。只要还有人 kubectl edit 线上 Deployment，self-heal 就会和他"打架"。纪律比工具重要。
模块 1

ArgoCD 架构：四个组件 + 两个 CRD

组件（都跑在 argocd 命名空间）

组件职责排障关注点
api-serverWeb UI / CLI / API 入口，无持久化状态无状态，可多副本
repo-server克隆 Git 仓库、执行 manifest 生成（helm template / kustomize build），带本地缓存性能瓶颈常在这里，支持 sharding 扩容
application-controller核心循环：拉 Git → 对比集群 → 计算 diff → 执行同步。每个 app 一个 workerOOM/延迟 = 应用数过多或仓库太大
applicationset-controller管理 ApplicationSet，按生成器批量创建/删除 ApplicationApplicationSet 的控制器
notifications同步状态变化推送到 Slack/钉钉/Webhook配 trigger 模板
dexSSO/OIDC 认证（可选）对接企业 IdP

两个核心 CRD

# Application：一个"可部署单元"，连接一个 Git 路径和一个目标集群/命名空间
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: webapp
  namespace: argocd              # Application 必须建在 argocd 命名空间
  finalizers:
    - resources-finalizer.argocd.argoproj.io   # 级联删除保护
spec:
  project: default               # 所属 AppProject（权限边界）
  source:
    repoURL: https://github.com/example/gitops.git
    targetRevision: main         # 分支 / tag / commit SHA
    path: apps/webapp/overlays/prod
    # 如果用 Helm chart：
    # chart: webapp
    # helm:
    #   valueFiles: [values-prod.yaml]
    #   parameters: [{name: replicaCount, value: "3"}]
  destination:
    server: https://kubernetes.default.svc   # 目标集群
    namespace: prod
  syncPolicy:
    automated:                   # 不写 = 手动同步
      prune: true                # Git 里删掉的资源，集群里也删
      selfHeal: true             # 集群被手工改动的，自动改回 Git 声明
    syncOptions:
      - CreateNamespace=true     # 命名空间不存在时自动创建
    retry:
      limit: 5
# AppProject：Application 的权限边界（多团队必用）
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-a
  namespace: argocd
spec:
  description: Team A applications
  sourceRepos:
    - "https://github.com/example/gitops.git"   # 只允许这些 Git 仓库
  destinations:
    - server: https://kubernetes.default.svc
      namespace: "team-a-*"                     # 只允许部署到这些命名空间
  clusterResourceWhitelist:                      # 允许操作的集群级资源
    - group: ""
      kind: Namespace
  roles:
    - name: developer
      policies:
        - p, proj:team-a:developer, applications, sync, team-a/*, allow
      groups:
        - team-a-devs                              # OIDC 用户组
AppProject 是安全边界不是分类标签。没建项目时所有 Application 都挂 default，default 项目默认允许所有仓库和命名空间 —— 多团队环境必须给每个团队建 AppProject，否则 A 团队能把应用部署到 B 团队的命名空间。
模块 2

同步策略：手动、自动、Prune、Self-Heal

配置行为适用
手动同步Git 更新后 UI 显示 OutOfSync，人点 Sync生产核心应用的保守姿势
automated.prune: trueGit 中删除的资源，集群中同步删除高收益高风险，配合 finalizers
automated.selfHeal: true集群状态被手工改动偏离 Git 时，自动改回防"手工 kubectl edit"漂移
automated.allowEmpty允许同步到"空应用"（无资源）清空型操作，慎用

syncOptions：同步细节开关

CreateNamespace=true目标命名空间不存在时自动创建
PruneLast=true最后一步才执行删除，先建后删避免服务中断
ApplyOutOfSyncOnly=true只 apply 有差异的资源，大应用提速明显
Replace=true用 replace 替代 apply，解决不可变字段冲突（如 Job selector）
ServerSideApply=true使用 K8s 服务端 apply（SSA），大清单性能更好
RespectIgnoreDifferences=true让 ignoreDifferences 配置在同步时也生效

ignoreDifferences：告诉 ArgoCD "这些字段别看"

# 经典场景：HPA 自动改 replicas，导致 Application 永远 OutOfSync
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas        # replicas 交给 HPA，Git 里写几都行
    - group: ""
      kind: Service
      jsonPointers:
        - /spec/clusterIP       / 集群分配的 clusterIP 不该参与对比
        - /metadata/annotations/kubectl.kubernetes.io~1last-applied-configuration
健康状态（Health）机制：ArgoCD 不只是"apply 成功"，还会持续评估资源健康度（Deployment 看 availableReplicas、Pod 看 Ready 条件）。UI 上的 Synced + Healthy 才是真的部署完成。没接健康检查的自定义资源默认显示 Progressing，不是 bug。
模块 3

Sync Waves 与 Hooks：控制部署顺序

K8s apply 不保证资源创建顺序，但现实是：CRD 要先于 CR，数据库迁移要先于新版本 Deployment，缓存预热要在 Deployment 之后。ArgoCD 用 wave 和 hook 两个注解解决。

Sync Wave：同阶段内的顺序

# 注解 argocd.argoproj.io/sync-wave: "N"
# wave 小的先 apply；不写默认 0；负数更早；后一个 wave 会等前一个健康

# 1. CRD 最先（wave -1）
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: crons.example.com
  annotations:
    argocd.argoproj.io/sync-wave: "-1"

# 2. 配置和 RBAC（wave 0，默认）
kind: ConfigMap
...

# 3. 工作负载（wave 1）
kind: Deployment
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "1"

# 4. 冒烟验证 hook（wave 2）
kind: Job
metadata:
  annotations:
    argocd.argoproj.io/sync-wave: "2"
    argocd.argoproj.io/hook: PostSync

Hook：生命周期动作

Hook 类型时机典型用途
PreSync同步开始前，所有 wave 之前数据库备份、schema 检查
Sync作为 wave 的一部分参与排序迁移 Job（跟着 Deployment 走）
PostSync同步且所有资源健康后冒烟测试、缓存预热、发通知
SyncFail同步失败时告警、自动收集现场
# hooks 的删除策略注解（Helm 的 hook-delete-policy 类似）
metadata:
  annotations:
    argocd.argoproj.io/hook: PostSync
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
# 可选值：HookSucceeded / HookFailed / BeforeHookCreation
CRD 顺序事故的标准解法：把 CRD 放 wave -1、CR 放 wave 0+。更彻底的做法是把 CRD 拆成独立 Application 并用 sync-wave + AppProject 依赖，或者直接 argocd.argoproj.io/sync-wave 全部声明。永远不要依赖 apply 的自然顺序 —— 它不保证。
模块 4

多集群管理与密钥

多集群注册

# 方式一：CLI 添加外部集群（把该集群的 ServiceAccount token 存为 Secret）
argocd cluster add prod-cluster-context --kube-context prod

# 方式二：声明式（GitOps 管 ArgoCD 自己，生产推荐）
apiVersion: v1
kind: Secret
metadata:
  name: prod-cluster
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster      # 这个 label 让它被识别为集群凭证
type: Opaque
stringData:
  name: prod-cluster
  server: https://prod-k8s.example.com:6443
  config: |
    {
      "bearerToken": "<service-account-token>",
      "tlsClientConfig": {"insecure": false, "caData": "<base64-ca>"}
    }
模式架构适用
Hub-Spoke一套 ArgoCD 管 N 个集群主流：同信任域的多集群
每集群一套 ArgoCDArgoCD 自己也由上层 GitOps 管强隔离、多团队自治

密钥管理：Git 里绝不能存明文 Secret

GitOps 的最大矛盾：K8s Secret 要进 Git 才能被 ArgoCD 管理，但 Secret 不能明文进 Git。两种主流解法：

# 方案 A：Sealed Secrets —— 加密后的 Secret 可以安全提交 Git
# 1. 安装 controller + 导出公钥，本地用 kubeseal 加密
kubeseal --format=yaml < mysecret.yaml > sealedsecret.yaml

# sealedsecret.yaml —— 可以安全提交 Git（只有集群私钥能解）
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: db-credentials
  namespace: prod
spec:
  encryptedData:
    password: AgBy3i4OJSWK+PiTySYZZA9rO43cG...   # 密文

# 2. 集群里的 controller 自动解密成真正的 Secret

# 方案 B：External Secrets Operator（ESO）—— 密钥存外部 Vault/云 KMS
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
  namespace: prod
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: vault-backend       # 指向 Vault / AWS SM / 阿里云 KMS
    kind: SecretStore
  target:
    name: db-credentials      # 生成的 K8s Secret 名
  data:
    - secretKey: password
      remoteRef:
        key: prod/db/password  # Vault 里的路径
方案密钥存哪取舍
Sealed SecretsGit（加密态）零依赖、简单；但集群私钥丢了要全量重加密
External SecretsVault / 云 KMS密钥集中管理、可轮转；多一个依赖和网络链路
argocd-vault-pluginVaultrepo-server 装插件渲染时注入，不动集群
私有仓库凭证：仓库级用 argocd repo add（Secret label: argocd.argoproj.io/secret-type=repository），凭据模板用 repo-creds（同 URL 前缀匹配，避免每仓库存一份）。SSH 私钥和 token 都是 Secret，记得 RBAC 限制 argocd 命名空间的访问。
模块 5

与 Helm / Kustomize 配合

ArgoCD 不生产 manifest，只做"生成 → 对比 → 同步"。它原生支持三种配置管理工具：纯 K8s YAML、Helm、Kustomize，且可以组合。

三种工具形态

工具ArgoCD 里的配置最佳场景
Helmsource.chart + helm.valueFiles / parameters打包分发第三方 chart；values 覆盖
Kustomizesource.path + kustomize 的 overlays 目录环境差异（base + overlay），官方推荐
纯 YAMLsource.path 直接指向目录简单应用、CRD 集合
Directory 递归source.directory.recurse: true一个 Application 装一个目录树

多 Source（2.6+）：一个应用多个来源

# 典型组合：Helm chart 做主 + 一个 Git 目录放环境 values
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: webapp
spec:
  sources:
    - repoURL: https://charts.example.com
      chart: webapp
      targetRevision: 1.4.2
      helm:
        valueFiles:
          - $values/envs/prod/webapp-values.yaml     # $values 引用下面的 source
    - repoURL: https://github.com/example/gitops.git
      targetRevision: main
      ref: values
      path: .                                        # 只被引用，不直接部署

Helm 参数的两种注入方式

# 方式 A：valueFiles（推荐，文件在 Git 里可 review）
helm:
  valueFiles:
    - values-common.yaml
    - values-prod.yaml

# 方式 B：parameters（适合 CI 动态注入少量值）
helm:
  releaseName: webapp
  parameters:
    - name: replicaCount
      value: "3"
    - name: image.tag
      value: "v2.17.0"

# Helm chart 依赖了子 chart 时，ArgoCD 需要拉依赖：
helm:
  skipCrds: false          # true = 不装 chart 自带 CRD（用 wave 管）
选型建议：多环境差异用 Kustomize（overlay 语法比 Helm values 更适合"同结构不同值"）；需要参数化封装和分发给外部用 Helm。实际项目最常见组合：基础 chart 用 Helm，环境差异在 Git 目录用 Kustomize patch，ArgoCD 用多 source 组装。
模块 6

ApplicationSet 与大盘

100 个微服务 = 100 个 Application，手写 YAML 不现实。ApplicationSet 用生成器（generator）+ 模板批量生成 Application。

# appset.yaml —— 最常见的两种生成器
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: microservices
  namespace: argocd
spec:
  generators:
    # ① Git 目录生成器：gitops/apps/ 下每个子目录 = 一个应用
    - git:
        repoURL: https://github.com/example/gitops.git
        revision: main
        directories:
          - path: apps/*
    # ② List 生成器：显式列表（适合少量、差异大的应用）
    - list:
        elements:
          - name: webapp
            url: https://github.com/example/webapp.git
          - name: payment
            url: https://github.com/example/payment.git
  template:
    metadata:
      name: "{{name}}"                # 或 {{path.basename}}
      finalizers:
        - resources-finalizer.argocd.argoproj.io
    spec:
      project: default
      source:
        repoURL: "{{url}}"
        targetRevision: main
        path: "{{path}}"               # git generator 提供 {{path}}
      destination:
        server: https://kubernetes.default.svc
        namespace: "{{name}}"
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions: [CreateNamespace=true]

常用生成器对比

生成器产出 Application 的依据场景
ListYAML 里显式列的元素少量应用，精细控制
Git（目录）仓库里的目录结构最常用：目录即应用
Git（文件）应用元数据单独维护
Cluster已注册集群列表同一套应用铺到所有集群
Matrix两个生成器的笛卡尔积N 应用 × M 集群
Pull RequestGit 平台上的 PR预览环境（PR 关则环境销）

大盘与视图

argocd app list所有应用及健康/同步状态
argocd app get webapp单个应用详情：源、目标、同步结果
argocd app diff webapp看 Git 声明与集群实况的逐行差异
argocd app sync webapp手动触发同步（--dry-run 预演）
argocd app history webapp同步历史（对应 Git 提交）
argocd app tree webapp应用资源树，看父子归属
UI 大盘看三个数就够：① 全局健康红点应用数；② OutOfSync 应用数（> 3 个就该查为什么有人不走 Git）；③ 最近 24h 同步失败数。通知接 Slack/钉钉：只推 Degraded 和 SyncFail，别推全部状态变化。
模块 7

十个线上坑

1
开了 automated.prune，Git 删错目录 → 生产资源被级联删光
prune 会删掉"Git 里没有但 ArgoCD 创建过"的资源。防御：① 删 Git 文件前先在 UI 看 diff；② 敏感应用先手动同步；③ finalizer 保证级联删除有序；④ Application 的 PruneLast=true。
2
CRD 还没建好，CR 就开始 apply，同步失败刷屏
apply 无顺序保证。CRD 打 sync-wave: "-1"，CR 放 wave 0+，让 ArgoCD 按 wave 顺序等前序健康。
3
HPA 改 replicas，Application 永远 OutOfSync
HPA/Operator 会改 Git 里声明的字段。用 ignoreDifferences 排除 /spec/replicas 这类运行时字段，并加 RespectIgnoreDifferences=true。
4
大仓库（几千文件）同步慢、repo-server OOM
application-controller 每次 diff 都要全量生成 manifest。解法：拆小仓库/路径、repo-server 开 sharding（replicas 扩容 + 环境变量 ARGOCD_APPLICATION_NAMESPACES 分片）、加缓存 TTL。
5
ApplicationSet 删了但生成的 Application 还在（孤儿）
ApplicationSet 删除时默认不级联删除生成的 Application。模板里加 finalizers: resources-finalizer.argocd.argoproj.io，或在 AppSet 上加 argocd.argoproj.io/application-set-delete-policy。
6
卸载 Application 卡住不动
finalizer 级联删除时遇到无法删除的资源（如 Terminating 的 Pod、PV 回收）。解法：argocd app delete --cascade=false 只删应用记录，或手动清理卡住资源的 finalizer。
7
有人 kubectl edit 线上，selfHeal 和他反复拉锯
手工修改与自动协调的冲突。这不是 bug 是机制：要么把变更提 Git，要么在资源上加 argocd.argoproj.io/compare-options 豁免字段。纪律问题用培训解决。
8
Helm chart 升级后同步报 "immutable field" 错误
Job/StatefulSet 等资源的 selector 不可变。syncOptions 加 Replace=true 用 replace 重建，或接受 Job 用唯一名（generateName/哈希后缀）。
9
多集群 token 过期，应用集体 Unknown
ServiceAccount token 有有效期。用 argocd cluster add 时选长效方案，或声明式 Secret 定期轮转；监控 argocd_cluster_info 的 connected 状态。
10
Application 建在了业务命名空间，UI 里根本不显示
Application 必须建在 argocd 命名空间（或配置的 application namespaces）。建错地方的表现是" kubectl get app 有、ArgoCD UI 无"。
自测

六道题

1. GitOps 的"自动拉取"原则，指的是？
正确答案：集群内 agent 主动拉取。这是 GitOps 与传统 CI 推送的本质区别：CI 只负责把变更推 Git，集群控制器自己拉。好处是 CI 不需要存集群凭证，且漂移能被持续纠正。
2. 想实现"Git 里删掉某个 Deployment，集群里的也自动删除"，需要配置？
正确答案：automated.prune: true。prune 管"Git 删 → 集群删"，selfHeal 管"集群被手工改 → 改回 Git 声明"。两者经常一起开，但 prune 风险更高，删 Git 文件前必须先看 diff。
3. 一个应用包含 CRD 和对应的 CR，apply 时报 "no matches for kind"，最稳的解法是？
正确答案：sync-wave 控制顺序。ArgoCD 按 wave 从小到大同步，且后一个 wave 会等前一个资源健康后再开始。apply 两遍是碰运气，删 CRD 则丢掉了声明式管理。
4. HPA 自动修改 Deployment 的 replicas，导致应用长期显示 OutOfSync，怎么办？
正确答案：ignoreDifferences 豁免该字段。这类"运行时字段"（replicas、clusterIP、status）本就该由控制器管理，不该参与 Git vs 集群的 diff。 RespectIgnoreDifferences 保证同步阶段也跳过它。
5. 100 个微服务要批量接入 ArgoCD，最合适的做法是？
正确答案：ApplicationSet + Git 目录生成器。目录结构即应用清单，模板用 {{path.basename}} 等变量批量生成 Application，增删应用只需增删目录。手写 100 份 YAML 无法维护，Helm chart 装应用则丢掉了 GitOps 的可审计性。
6. 关于 K8s Secret 与 GitOps，正确做法是？
正确答案：加密或外置。私有仓库不等于安全（克隆权限、 fork、CI 日志都会泄露）。明文 Secret 进 Git 是公认反模式；手动 kubectl create 则丢掉了声明式管理，ArgoCD 还会把它当漂移清掉。

GitOps以 Git 为唯一事实源的持续交付模式，四条原则：声明式、版本化、自动拉取、持续协调
OpenGitOpsCNCF 的 GitOps 标准定义（v1.0，2021）
ArgoCDK8s 原生 GitOps 控制器，Application 为核心 CRD
ApplicationArgoCD 核心 CRD：连接 Git 路径与目标集群/命名空间的可部署单元
AppProjectApplication 的权限边界：限定仓库、目标命名空间、资源类型和角色
repo-server克隆仓库并生成 manifest 的组件，性能瓶颈常在此
application-controller执行"拉取-对比-同步"主循环的控制器
OutOfSyncGit 声明与集群实况存在差异的状态
Synced + Healthy部署完成的双条件：配置一致且资源健康
prune同步时删除 Git 中已不存在的资源
selfHeal自动纠正集群中偏离 Git 声明的手工修改

ApplicationSet按生成器批量创建 Application 的 CRD
Sealed Secrets加密 Secret 后可安全提交 Git 的方案
External Secrets从 Vault/云 KMS 同步密钥生成 K8s Secret 的方案
finalizer级联删除保护：resources-finalizer.argocd.argoproj.io
Drift（漂移）集群状态偏离 Git 声明的现象，GitOps 持续协调的目标就是消除它
