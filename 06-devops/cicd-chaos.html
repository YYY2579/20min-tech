开始前

起一个能练的环境

CI/CD 和混沌工程都必须在真实环境里练。看文档学不会，因为你永远不知道"没预料到的那一步"会在哪里失败。

# 本地起一个单节点 K8s 集群（kind 最快）
kind create cluster --name lab

# 装 Chaos Mesh（混沌工程实验平台，用 Helm 最省事）
helm repo add chaos-mesh https://charts.chaos-mesh.org
helm install chaos-mesh chaos-mesh/chaos-mesh -n chaos-mesh --create-namespace

# 装一个 demo 应用（用来做发布和故障演练）
kubectl create deployment demo --image=nginx:alpine --replicas=3
kubectl expose deployment demo --port=80 --type=NodePort

# 验证
kubectl get pods -n chaos-mesh         # 看 Chaos Mesh 组件是否 Running
kubectl get pods                        # 看 demo 的 3 个副本
kubectl get svc                         # 看 NodePort 端口
阅读提示：CI/CD 的核心不是"用哪个工具"，而是"把哪些步骤自动化、在什么条件下放行、失败了怎么办"。混沌工程的核心不是"能杀进程"，而是"用受控的实验去验证你对系统韧性的假设"。抓住这两条主线，工具只是实现细节。
模块 1

CI/CD 到底解决什么

先破除一个误解：CI/CD 不是"让部署自动化"这么简单。它真正解决的是软件交付的不确定性和人为错误。手工发布的问题不是慢，而是不可重复——同一个人做两次结果都可能不一样，更别说不同的人。

概念全称与含义解决什么
CI
持续集成		Continuous Integration：代码一提交就自动构建、跑测试让"集成"这件事从几周一次变成每次提交都做，问题在几分钟内被发现
CD
持续交付		Continuous Delivery：代码通过测试后随时可发布，但发布要人点一下保证任何时刻都有一个经过验证、可以上线的版本
CD
持续部署		Continuous Deployment：通过测试后自动发布到生产连"点一下"都省了，但要求极高的测试覆盖和回滚能力

DORA 四指标：用数据衡量你的交付能力

DORA（DevOps Research and Assessment，Google 收购的研究团队）用四个指标衡量一个团队的软件交付效能。前两个看速度，后两个看稳定性。关键洞察是：速度和稳定性不是对立的——高效能团队两者都好。

指标定义高效能团队参考值
部署频率多久部署一次到生产按需，一天多次（而非一周一次）
变更前置时间从代码提交到上线运行的时间小于一天
变更失败率发布导致故障需要回滚/修复的比例0%~15%
恢复时长 MTTR从故障发生到恢复服务的时间小于一小时
为什么"部署频率高"反而是好事？因为每次发布的变更量小。变更越小，出问题的概率越低，出了问题也越容易定位和回滚。反直觉的结论：发得越勤，单次风险越低，整体越稳定。那些"一个月攒一个大版本"的团队，每次发布都是豪赌。
模块 2

流水线设计

一条好的流水线只有一个目标：用最短的时间，给出"这个变更能不能上"的可信答案。所有设计取舍都围绕这个目标。

典型阶段划分

Lint & 静态检查：语法、格式、静态分析。几秒到几十秒，最便宜，最先跑，能在这一步拦住的问题绝不往后传。
编译 & 单元测试：构建产物 + 跑单测。分钟级。单测必须快，否则没人愿意等。
构建制品：打 Docker 镜像 / 编译二进制。只做一次，产出唯一制品，后续所有环境都用它。
集成测试 & 契约测试：需要依赖服务，验证模块间协作。较慢，但能发现单测发现不了的问题。
部署到测试环境 & 端到端测试：真实环境验证核心流程（冒烟测试）。
部署到生产：灰度、金丝雀、或直接全量（视策略而定）。

加速流水线的三个手段

手段说明
并行互不依赖的任务同时跑：单测、lint、构建镜像可以并行。总时长从"相加"变成"取最大"
缓存缓存依赖包（node_modules、Maven 仓库）、Docker layer。这一步通常能省掉一半以上时间
失败快速反馈把最可能失败、最便宜的检查放最前面。lint 挂了就别浪费时间构建镜像
# GitHub Actions 流水线示例：并行 + 缓存
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make lint            # 最快，放最前面

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/cache@v4     # 缓存依赖，省时间
        with:
          path: ~/.m2
          key: m2-${{ hashFiles('**/pom.xml') }}
      - run: make test

  build:
    needs: [lint, test]           # 前两步都过了才构建
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t myapp:${{ github.sha }} .
      - run: docker push registry/myapp:${{ github.sha }}   # 只构建这一次
两条铁律：
① 制品只构建一次。用同一份镜像部署到测试、预发、生产。如果你在预发构建一次、生产又构建一次，那你上线的东西从来没被测试过——两次构建的结果可能有微妙差异（依赖版本、构建时间、随机种子）。
② 环境一致性。用同一份镜像 + 同一份配置模板，只通过环境变量区分环境。凡是"预发能跑、生产报错"的问题，90% 出在环境不一致（基础镜像版本、依赖版本、配置项）。
模块 3

制品与版本管理

制品（artifact，指构建产出的可部署文件，如 Docker 镜像、jar 包、二进制）是交付的核心资产。管好它，回滚才有依据。

镜像 tag 规范：绝对不要用 latest

tag 方式评价
myapp:latest禁用。latest 是个移动目标，同一个 tag 每次构建内容都不同。你无法知道生产跑的是哪一版，回滚时也无从下手
myapp:v1.2.3语义化版本，适合正式发布。但同一个版本号可能被覆盖重建，要配仓库的不可变策略
myapp:git-a1b2c3d推荐。用 git commit SHA 做 tag，天然唯一、可追溯到具体代码，回滚时直接指向代码
myapp:v1.2.3-a1b2c3d最佳实践：语义版本 + commit SHA 双 tag，既有可读性又可追溯

不可变制品（Immutable Artifact）

不可变意味着：一个 tag 一旦推送，内容就永远不能改。要修改就发新版本。latest 之所以危险，就是因为它违反了不可变性。制品仓库（Harbor、Nexus、Artifactory）应该开启"tag 不可覆盖"策略，从机制上杜绝"偷偷改了同一个 tag"。

语义化版本（SemVer）

# MAJOR.MINOR.PATCH  →  1.4.2
MAJOR  # 不兼容的 API 变更（破坏性变更），如 1.x → 2.0
MINOR  # 向后兼容的新功能，如 1.4 → 1.5
PATCH  # 向后兼容的 bug 修复，如 1.4.2 → 1.4.3

# 预发布版本用连字符：1.5.0-rc.1、1.5.0-beta.2
# 构建元数据用加号：1.5.0+20261016
制品仓库要做的事：① 唯一可信源，所有环境只从这里拉镜像；② 开启不可变 tag，禁止覆盖；③ 配保留策略（如保留最近 100 个版本，其余归档），否则仓库会被历史镜像撑爆；④ 扫描镜像漏洞（Trivy、Clair），高危漏洞的镜像禁止部署。
模块 4

测试策略金字塔

测试金字塔的核心思想：越靠底层的测试越便宜、越快、越稳定，应该越多；越靠上层越贵、越慢、越容易不稳定，应该越少。倒过来的"冰淇淋甜筒"（大量 E2E、少量单测）是反模式。

层级测什么成本 / 速度占比建议
单元测试单个函数/类的逻辑最低 / 毫秒级最多，约 70%
集成测试模块间协作、真实依赖（DB、MQ）中 / 秒级约 20%
契约测试服务间的接口约定是否匹配中 / 秒级按服务数，关键接口必须有
端到端 E2E完整用户流程，跨所有服务最高 / 分钟级、易 flaky最少，只测核心路径，约 10%

契约测试：微服务时代的关键补充

契约测试（contract testing）解决的是"我改了接口，怎么知道下游会不会挂"。消费者（调用方）定义它期望的接口契约，提供者（被调用方）验证自己是否满足这个契约。这样不需要把所有服务都启动起来做 E2E，就能在 CI 阶段发现接口不兼容。Pact 是最常用的契约测试工具。

冒烟测试在部署流程里的位置

# 冒烟测试（smoke test）= 部署后立刻跑的最小核心路径验证
# 目的：确认"新版本至少能跑起来"，如果不行立刻回滚

# 部署流程里的位置：
1. 部署新版本到生产（灰度 1 个实例）
2. 对这个实例跑冒烟测试（健康检查 + 核心接口）
3. 通过 → 继续扩大灰度；失败 → 立即回滚
4. 全量后继续观察核心指标

# 冒烟测试要快（几十秒内），只测"服务活着 + 核心功能可用"
# 它不是 E2E 的替代品，而是部署流程里的一个安全闸门
curl -f http://new-pod/healthz || exit 1
curl -f -X POST http://new-pod/api/order -d '{"test":true}' || exit 1

测试数据管理

  • 测试数据要可复现：用固定种子生成，别依赖"数据库里恰好有那条数据"。
  • 每个测试自建自清理：测试自己准备数据、测试完清理掉，避免测试间互相污染（测试 A 改了数据导致测试 B 失败）。
  • 生产数据脱敏后使用：真实数据的分布最接近生产，但必须脱敏（去掉手机号、身份证、密码），且要合规。
  • 别共用测试环境的状态：多个流水线同时跑却共享一个测试库，是最经典的 flaky 来源。
关于 flaky test（时好时坏、结果不稳定的测试）：flaky 测试是流水线公信力的最大杀手。一旦出现，开发者就开始习惯性地"重跑一次看看"，最终对红灯麻木，真正的失败被忽略。处理原则：发现 flaky 立即隔离（quarantine）并修复，绝不能让它长期留在流水线里。宁可暂时跳过，也不要让整条流水线的可信度崩塌。
模块 5

部署策略对比

部署策略的本质是在"风险暴露面"和"资源成本 / 复杂度"之间做权衡。没有最好的策略，只有最合适的。

策略怎么工作适用场景代价
滚动
Rolling		逐个替换旧实例，新老版本短暂共存K8s 默认策略，绝大多数场景期间新旧版本同时在线，要求接口向后兼容；回滚要重新滚动
蓝绿
Blue-Green		部署一套全新的（绿），验证后一键切换流量需要秒级回滚的关键服务资源翻倍（两套环境同时跑）；数据库 schema 必须兼容两版
金丝雀
Canary		先放一小部分流量（如 1%）到新版本，观察指标，逐步扩大高流量、需要真实验证的核心服务需要精细的流量控制 + 自动指标对比，运维复杂度高
功能开关
Feature Flag		代码已部署，但新功能由开关控制是否对用户可见需要把发布和上线解耦、A/B 测试、快速关停代码里有大量分支，开关本身要管理，容易积累技术债

K8s 配置片段

# 1. 滚动更新（Deployment 默认）
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1              # 最多多出 1 个 Pod
      maxUnavailable: 0        # 保证始终有足够可用副本，零中断
  minReadySeconds: 10          # 新 Pod ready 后等 10s 再继续，避免假就绪

# 2. 金丝雀：两个 Deployment 共享一个 Service，靠副本数控制流量比例
# 稳定版 9 副本 + 金丝雀 1 副本 ≈ 10% 流量
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-canary
spec:
  replicas: 1                  # 用副本数近似流量比例（粗粒度）
  template:
    metadata:
      labels:
        app: demo
        track: canary          # 打上 canary 标签
    spec:
      containers:
      - name: app
        image: registry/myapp:v2.0.0-a1b2c3d

# 3. 蓝绿：切 Service 的 selector，一键把流量从 blue 切到 green
apiVersion: v1
kind: Service
metadata:
  name: demo
spec:
  selector:
    app: demo
    track: blue                # 改成 green 即完成切换
  ports:
  - port: 80
怎么选：不确定就用滚动更新（K8s 默认，够用）。需要秒级回滚或做重大变更 → 蓝绿。流量大、想用真实流量验证 → 金丝雀。想随时开关某个功能、不重新部署 → 功能开关。
实际上这四者常常组合使用：金丝雀发布 + 功能开关，是很多大厂的标准组合——金丝雀控制"代码版本"的灰度，功能开关控制"功能"的灰度，两者解耦。
模块 6

数据库变更与发布

这是发布里最难、最容易出事的部分。因为代码可以秒级回滚，但数据库一旦改了结构或数据，回滚就非常痛苦。核心原则：让数据库变更和代码变更解耦，永远保持"新旧两个版本的代码都能在同一个数据库上正常工作"。

先加后删的三步法（Expand-Contract）

第一步：Expand（扩展）——只做新增，不做删除或破坏性修改。比如加一个新列 full_name，同时保留旧列。此时旧代码完全不受影响。
第二步：双写 + 迁移数据——新代码同时写新旧两列，后台任务把历史数据从旧列迁到新列。此时新旧代码都能正常工作（旧代码读旧列，新代码读新列）。
第三步：Contract（收缩）——等所有实例都升级完、观察一段时间后，再删除旧列。这一步是破坏性的，但此时已经没有代码依赖它了。
# 三步法的具体时序（关键：每一步都可回滚）
T1 加新列 full_name（旧代码不知道它，无影响）        # 可安全回滚
T2 部署新代码：同时写 old_name 和 full_name         # 回滚 = 回退代码，数据还在
T3 后台任务回填历史数据的 full_name
T4 新代码改成只读 full_name，不再读 old_name
T5 观察稳定后，删除 old_name 列                    # 到这一步才不可逆

# ✗ 反例：一条 ALTER 同时改名 + 改类型 + 加约束
# 一旦失败或需要回滚，你可能已经丢了数据

大表加索引：必须用 CONCURRENTLY

# PostgreSQL：普通 CREATE INDEX 会锁表，大表上会阻塞所有写
CREATE INDEX idx_order_user ON orders(user_id);        # ✗ 大表上会锁住写入

# 正确做法：CONCURRENTLY 不锁表，在线建索引
CREATE INDEX CONCURRENTLY idx_order_user ON orders(user_id);

# 注意 CONCURRENTLY 的限制：
# ① 不能在事务块里执行（很多迁移工具默认包事务，要单独配）
# ② 失败会留下 INVALID 状态的索引，需要手动 DROP 后重建
# ③ 建索引期间会有额外 CPU 和 IO 开销，别在业务高峰期做

# MySQL 8.0+ 的在线 DDL（大多数加索引操作默认就是 ONLINE）
ALTER TABLE orders ADD INDEX idx_user (user_id), ALGORITHM=INPLACE, LOCK=NONE;
为什么"数据回滚"比"代码回滚"难得多？代码回滚只是把镜像换成旧版本，几秒钟的事。但如果新版本已经写入或修改了数据（比如把某列的值批量改了、删了一些记录），回滚代码后，旧代码面对的是被新代码改过的数据——结构对不上、值语义变了，回滚后反而更糟。
所以铁律是：数据库变更必须"向后兼容"，让新旧代码都能跑。任何"只有新代码才能处理"的数据变更，都必须先确认旧代码已经不可能再运行，才能做。这就是 Expand-Contract 存在的意义。
模块 7

回滚与降级

回滚能力是发布安全的底线。一个没有回滚方案的发布，等于一次不可逆的赌博。而回滚最关键的不是"怎么做"，是"什么时候做"——这个判断必须在发布之前就定好，不能等到出事时临时拍脑袋。

回滚决策阈值：提前定义，用数据触发

信号阈值示例（达到即回滚）
错误率5xx 占比 > 1%，且持续 2 分钟
延迟P99 > 基线值 × 2，且持续 5 分钟
核心业务指标下单成功率下降 > 5%，或支付成功率异常
健康检查冒烟测试失败，或就绪探针连续失败

把这些阈值写成自动化的：金丝雀发布时，流水线自动对比新旧版本的指标，超阈值自动回滚，不需要人盯着。

回滚的几种方式

# 1. K8s 回滚到上一个版本（滚动/蓝绿都适用）
kubectl rollout undo deployment/demo
kubectl rollout undo deployment/demo --to-revision=3   # 回滚到指定版本
kubectl rollout history deployment/demo                 # 查看历史版本

# 2. 蓝绿：切换 Service selector，秒级回滚
kubectl patch service demo -p '{"spec":{"selector":{"track":"blue"}}}'

# 3. 功能开关：最快的"回滚"，不重新部署
# 直接把开关关掉，新功能立即对用户不可见（代码还在，但走不到）
# 注意：功能开关只能回滚"功能"，回滚不了"有 bug 的公共代码"

# 4. 数据库：只能靠"向前修复"（forward fix）
# 因为回滚数据太难，通常的做法是发一个新版本修好它，而不是回退数据
重新定义"回滚"：回滚不是失败，是能力。一个团队如果从不回滚，通常意味着两种情况：要么发布太频繁但每次都幸运，要么出了问题宁可硬扛也不回滚（因为回滚流程不熟练、怕丢数据）。后者是灾难。
健康的文化是：回滚是一个被充分演练、可以在几分钟内完成的常规操作。团队应该定期演练回滚，确保它真的能用——"纸上有回滚方案"和"回滚方案真的能跑通"是两回事。

降级预案：回滚之外的第二条路

有时候回滚也来不及（比如依赖的下游服务挂了，回滚自己的代码没用）。这时需要降级——牺牲非核心功能，保住核心链路。

功能降级
关掉非核心功能（推荐位、个性化），保住主流程。如大促时关掉"猜你喜欢"
返回兜底数据
下游超时就直接返回缓存值或默认值，不让请求失败。如推荐服务挂了返回热门榜
限流
主动丢弃部分请求，保住系统整体可用，避免雪崩
只读模式
关闭写操作，保证读可用。适合数据库压力过大时
模块 8

混沌工程

混沌工程（Chaos Engineering）不是"随机搞破坏"，而是用受控的实验，主动验证系统在故障下的表现。它的核心信念是：系统一定会出故障，与其等着它在最坏的时刻以最意外的方式出问题，不如主动把它找出来。

四条核心原则

原则含义
从假设出发先写下"我们相信，即使某个节点挂掉，服务仍然可用"这样的假设，再用实验去验证它。不是漫无目的地杀进程
用真实环境测试环境的故障行为和生产往往不同（流量、数据量、配置都不同）。条件允许时，在生产做小规模实验
控制爆炸半径最重要的原则。实验必须限定影响范围：只影响 1 个实例、只影响 1% 流量、只影响测试账号。绝不"一次搞挂整个系统"
持续进行系统在变，一次实验不能保证永远安全。把混沌实验纳入 CI/CD，持续自动运行

实验设计方法

定义稳态假设：先明确"正常"是什么样。比如"下单接口成功率 > 99.9%，P99 < 500ms"。
设计实验：选定故障类型（杀 Pod、注入延迟、断网、填满磁盘）和影响范围（哪个服务、多少实例）。
控制爆炸半径：限定只影响最小范围，并准备好"一键停止"的机制。
执行并观察：运行实验，同时紧盯监控。如果稳态假设被打破，说明系统有韧性缺陷。
修复与验证：修复发现的问题（如加超时、加重试、加熔断），然后重跑同一个实验验证修复有效。

Chaos Mesh 能做什么

Chaos Mesh 是 CNCF 的 K8s 原生混沌工程平台，通过 CRD 定义实验。它的优势是"声明式"：你用 YAML 描述"要对哪些 Pod 施加什么故障"，Chaos Mesh 负责执行和恢复。

# 实验 1：Pod 故障（随机杀掉部分 Pod，验证副本自愈能力）
apiVersion: chaos-mesh.org/v1alpha1
kind: PodChaos
metadata:
  name: pod-kill-demo
spec:
  action: pod-kill              # 杀 Pod
  mode: one                     # 只影响 1 个 Pod（控制爆炸半径）
  selector:
    labelSelectors:
      app: demo
  scheduler:
    cron: "@every 5m"           # 每 5 分钟杀一次，持续验证

# 实验 2：网络延迟（模拟下游变慢，验证超时和降级）
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: net-delay-demo
spec:
  action: delay
  mode: all
  selector:
    labelSelectors:
      app: demo
  delay:
    latency: "500ms"            # 注入 500ms 延迟
    jitter: "100ms"
  direction: to
  target:
    selector:
      labelSelectors:
        app: inventory          # 只影响 demo 到 inventory 的调用

# 实验 3：网络分区（模拟服务间断网）
# action: partition，验证服务降级和熔断是否生效

# 实验 4：资源压力（打满 CPU / 内存 / 磁盘）
# kind: StressChaos，验证限流和 HPA 扩容是否及时

# 实验 5：DNS 故障（模拟域名解析失败）
# kind: DNSChaos，验证服务发现和重试机制
混沌工程 vs 故障演练的区别：
故障演练通常是手动、有剧本的：组织一次演练，按预定步骤关掉某个服务，看大家怎么响应。它更像一次消防演习，重点是检验人的响应流程。
混沌工程是自动化、持续、以验证系统假设为目标的：用工具持续注入随机故障，重点是发现系统本身的韧性缺陷。它不依赖人的参与，可以在半夜无人值守时运行。
两者不冲突，但混沌工程是更高阶的形态。没有完善的监控和可观测性，不要贸然做混沌工程——你连"系统是否还正常"都判断不了，实验就变成了纯粹的破坏。
混沌工程的三条红线：
① 必须先有可观测性。没有监控和告警，你不知道实验有没有造成伤害。
② 必须有紧急停止机制。实验失控时能一键终止（Chaos Mesh 支持 kubectl delete 掉实验 CRD 立即恢复）。
③ 必须从最小爆炸半径开始。第一次实验只影响 1 个非核心服务的 1 个实例，验证流程跑通后，再逐步扩大。绝不允许"第一次就在生产全量做"。
常见坑

十个线上坑

1
预发和生产分别构建镜像
生产跑的制品从未被测试过。两次构建可能有微妙差异。必须"制品只构建一次"，同一份镜像部署到所有环境。
2
没有回滚方案就发布
出事时手忙脚乱，只能硬扛或现场想办法。发布前必须有明确、经过演练的回滚方案，以及提前定好的回滚阈值。
3
数据库变更和代码同时上线
一旦要回滚代码，数据库已经变了，旧代码面对新结构直接崩。必须用 Expand-Contract 三步法解耦，保持向后兼容。
4
流水线太慢，没人愿意等
一条跑 1 小时的流水线，开发者会绕过它直接发布，CI 形同虚设。用并行和缓存把核心流水线压到 10 分钟以内。
5
只在预发测过就上生产
预发没有真实流量、数据量小，很多问题（性能、并发、数据边界）根本暴露不出来。关键变更要用金丝雀在真实流量下验证。
6
回滚时忘了数据已经变更
新版本写了新数据，回滚代码后旧代码读不懂这些数据，问题反而更严重。数据变更必须设计成"新旧代码都能处理"。
7
镜像用 latest tag
latest 是移动目标，无法确定生产跑的是哪一版，回滚无从下手。用 git commit SHA 或语义版本号做 tag，并开启不可变策略。
8
flaky 测试长期留在流水线里
开发者开始习惯性"重跑一次看看"，最终对红灯麻木，真正的失败被忽略。发现 flaky 立即隔离修复。
9
混沌实验爆炸半径过大
第一次就在生产全量杀 Pod，直接把服务搞挂。必须从最小范围（1 个非核心实例）开始，配好紧急停止机制。
10
没有可观测性就做混沌工程
连系统是否正常都判断不了，实验就变成了纯粹的破坏。混沌工程的前提是完善的监控、告警和链路追踪。
自测

六道题

1. 为什么"部署频率高"反而是件好事？
正确答案：变更量小所以风险低。DORA 研究发现速度和稳定性不矛盾。频繁小步发布，每次改动小、出问题概率低、定位容易、回滚快。反而是"一个月攒一个大版本"的做法每次都是豪赌。
2. 关于制品的构建，正确的做法是？
正确答案：只构建一次，所有环境复用同一份镜像。如果预发和生产分别构建，那你上线的东西从来没被测试过——两次构建可能有依赖版本、构建时间等微妙差异。制品必须唯一且不可变。
3. 需要修改数据库表结构，正确的做法是？
正确答案：Expand-Contract 三步法。核心是让数据库变更和代码变更解耦，任何时刻新旧代码都能在同一数据库上正常工作。一条 ALTER 改结构再和代码同时上线，一旦回滚代码，旧代码面对新结构会直接崩。
4. 关于回滚，哪个说法是对的？
正确答案：回滚是能力，阈值要提前定。回滚决策必须在发布前就定好（错误率、延迟超阈值即回滚），不能临时拍脑袋。代码回滚只是换镜像，数据回滚则可能不可逆，所以数据库变更必须向后兼容。
5. 混沌工程最重要的原则是？
正确答案：控制爆炸半径。混沌工程是受控实验而非随意破坏，必须限定影响范围（1 个实例、1% 流量），并有一键停止机制。原则是"从最小范围开始、逐步扩大"，绝不是"一次搞挂整个系统"。
6. 做混沌工程的前提条件是什么？
正确答案：完善的可观测性。如果连"系统是否还正常"都判断不了，实验就变成了纯粹的破坏。没有监控和告警，你无法知道注入的故障有没有造成伤害。可观测性是混沌工程的先决条件。

流水线配置模板

# 一条完整流水线的骨架（GitHub Actions 风格）
name: ci-cd
on:
  push:
    branches: [main]
  pull_request:

jobs:
  # 阶段 1：快速反馈（并行，最便宜的先跑）
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make lint

  unit-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/cache@v4
        with:
          path: ~/.m2
          key: m2-${{ hashFiles('**/pom.xml') }}
      - run: make test

  # 阶段 2：构建唯一制品（只此一次）
  build:
    needs: [lint, unit-test]
    runs-on: ubuntu-latest
    outputs:
      image: ${{ steps.build.outputs.image }}
    steps:
      - uses: actions/checkout@v4
      - id: build
        run: |
          IMAGE=registry/myapp:${{ github.sha }}
          docker build -t $IMAGE .
          docker push $IMAGE
          echo "image=$IMAGE" >> $GITHUB_OUTPUT

  # 阶段 3：集成测试（用同一个制品）
  integration-test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: make integration-test IMAGE=${{ needs.build.outputs.image }}

  # 阶段 4：部署 + 冒烟 + 金丝雀
  deploy:
    needs: integration-test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - run: kubectl set image deploy/demo app=${{ needs.build.outputs.image }}
      - run: ./scripts/smoke-test.sh          # 冒烟测试
      - run: ./scripts/canary-watch.sh         # 观察指标，超阈值自动回滚

发布前检查清单

制品是否唯一且可追溯用 git SHA 打 tag，同一镜像部署到所有环境，不用 latest
是否有明确的回滚方案回滚命令写好了吗？演练过吗？数据变更可逆吗？
回滚阈值是否已定义错误率、延迟、业务指标的阈值和持续时间，且最好自动化
数据库变更是否向后兼容新旧代码能否在同一 schema 上工作？是否用了 Expand-Contract？
大表操作是否在线执行加索引用 CONCURRENTLY，DDL 用 INPLACE + LOCK=NONE
是否配了冒烟测试部署后立即验证核心路径，失败自动回滚
可观测性是否就绪新版本的关键指标在大盘上能看到吗？告警配了吗？
发布窗口是否合适避开业务高峰；周五下午发布需要更谨慎（但不应绝对禁止）
是否通知了相关方重大变更通知依赖方、客服、值班人员
降级预案是否就绪下游挂了怎么办？能不能关掉非核心功能保住主链路？
