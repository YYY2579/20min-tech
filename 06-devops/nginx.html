二十分钟学透 Nginx 与负载均衡

Nginx 是所有后端和运维的"必经关口"：它站在流量入口，几乎所有线上事故都会经过它。这篇的重点不是背配置，而是location 匹配优先级、proxy_pass 的路径拼接、四层与七层的选择、以及 499/502/504 到底是谁的锅。

建议起一个 Nginx 跟着改配置：docker run -d -p 8080:80 --name ngx nginx
开始前

起一个能改配置的 Nginx

# 一条命令起一个 Nginx（映射配置和日志出来，方便改）
mkdir -p /tmp/ngx/conf.d /tmp/ngx/logs
docker run -d --name ngx -p 8080:80 \
  -v /tmp/ngx/conf.d:/etc/nginx/conf.d \
  -v /tmp/ngx/logs:/var/log/nginx \
  nginx:alpine

# 改完配置后校验语法（生产改配置前必做！）
docker exec ngx nginx -t

# 平滑重载（不断连接，比 restart 安全）
docker exec ngx nginx -s reload

# 看配置生效情况 / 版本信息
docker exec ngx nginx -T          # 打印最终生效的完整配置（含 include）
docker exec ngx nginx -v
一个必须养成的习惯：改配置永远先 nginx -t 校验，再 nginx -s reload。
为什么用 reload 不用 restart：reload 是"热重载" —— master 进程用新配置启动新的 worker，老 worker 处理完手头请求再退出，不丢连接。restart 会断掉所有连接。但如果配置里有语法错误，reload 会失败（这也是要先 -t 的原因）。
模块 1

Nginx 是什么、为什么快

Nginx 的核心竞争力就一个字：快。理解它为什么快，才能理解它的配置为什么长这样。

特性说明
事件驱动 + 异步非阻塞一个 worker 进程用 epoll（Linux 的 IO 多路复用机制）同时管理成千上万个连接，不需要为每个连接开一个线程
多进程 master-worker一个 master 管配置和 worker，多个 worker 各自独立处理请求，充分利用多核，一个 worker 崩了不影响其他
C 语言 + 内存池底层用 C 写，自己管理内存池，减少系统调用和内存分配开销
零拷贝 sendfile静态文件直接从磁盘送到网卡，不经过用户态，省掉两次内存拷贝

和 Apache prefork 模型的对比（关键差异）

模型机制问题
Apache prefork一个连接一个进程（或线程）。1000 个连接就要 1000 个进程进程重、内存占用大、上下文切换开销高。几千并发就撑不住了
Nginx 事件驱动一个 worker 管几万个连接，用事件循环处理"哪个连接有数据了"内存占用极低，单机几万并发不费劲
一句话记住：Apache 是"人多好办事"（每连接一个进程），Nginx 是"一个高手管全场"（事件循环）。并发连接的瓶颈不在 CPU，而在内存和文件描述符 —— 这也是为什么 Nginx 调优要调 worker_connections 和 ulimit（模块 7 讲）。

master-worker 架构

# 进程结构（ps 能看到）
root      1234  nginx: master process        # 读配置、管理 worker、处理信号
www-data  1235  nginx: worker process        # 实际处理请求
www-data  1236  nginx: worker process
www-data  1237  nginx: worker process        # 通常 = CPU 核数

# 为什么这么设计
✓ 多 worker 独立，利用多核，单个崩溃不影响整体
✓ reload 时 master 启新 worker、停旧 worker，实现零停机
✓ master 以 root 运行（绑 80/443 特权端口），worker 降权到 www-data（安全）
一个常见的认知误区："Nginx 是单线程的，所以慢"。错。Nginx 是多进程单线程 —— 每个 worker 是单线程的事件循环，但有多个 worker（默认等于 CPU 核数）。所以它是"多核并行 + 每核内事件驱动"，既利用了多核，又避免了线程切换开销。
模块 2

配置结构与 location 匹配优先级

Nginx 配置是树形结构。搞懂层级关系，就知道一条配置该写在哪；搞懂 location 优先级，就避开了 80% 的"配置不生效"问题。

配置层级关系

# 从外到内，作用域逐层收窄
全局块            # worker_processes、user 等，影响整个 Nginx
├── events 块       # worker_connections 等，连接处理相关
└── http 块         # HTTP 相关全局配置：log_format、gzip、upstream...
    ├── server 块     # 一个虚拟主机（一个域名/端口）
    │   ├── location 块  # 按 URL 路径匹配，做具体处理
    │   └── location 块
    └── server 块     # 另一个虚拟主机

# 继承规则：内层没配就继承外层，内层配了就覆盖外层
# 例：http 块配了 gzip on，所有 server/location 默认都开 gzip

用 include 组织配置

# 主配置里 include 进来，避免一个文件几千行
http {
    include /etc/nginx/conf.d/*.conf;      # 每个站点一个文件
    include /etc/nginx/mime.types;          # MIME 类型映射
    include /etc/nginx/sites-enabled/*;
}

# 推荐的组织方式：一个域名一个文件
conf.d/
├── api.example.com.conf
├── www.example.com.conf
├── upstreams.conf       # 所有 upstream 定义集中放
└── snippets/
    ├── ssl.conf          # SSL 公共配置
    ├── proxy.conf        # 反代公共头
    └── security.conf     # 安全响应头

location 匹配优先级（最容易搞错的地方）

Nginx 按下面的顺序决定用哪个 location，匹配到高优先级就不再往下看：

优先级修饰符含义
1（最高）location = /path精确匹配。URL 完全等于 /path 才命中。命中即停止
2location ^~ /path/前缀匹配且不做正则。以 /path/ 开头就命中，且命中后不再检查正则 location
3location ~ regex正则匹配（区分大小写）。按配置中出现的先后顺序匹配，第一个命中即用
3location ~* regex正则匹配（忽略大小写）。同 ~ ，也按顺序
4（最低）location /path/普通前缀匹配。记住最长前缀，但会先让位给正则 —— 如果正则命中了，就用正则
最反直觉的一点：普通前缀匹配"最长匹配优先"，但会被正则"截胡"。
Nginx 的实际流程是：① 先找所有前缀匹配，记下最长的那个；② 如果最长的前缀是 ^~，直接用，结束；③ 否则继续按顺序试所有正则 location，第一个命中就用正则；④ 正则都没命中，才用第 ① 步记下的最长前缀。
所以 location /api/ 配了反代，但如果有个 location ~ \.php$ 正则，那 /api/x.php 会走正则而不是 /api/。 
# 匹配优先级实战：请求 /static/logo.png 会命中哪个？
location = /static/logo.png { }        # 精确 → 优先，直接命中（如果有）
location ^~ /static/ { }               # 前缀且不做正则 → 命中即停
location ~ \.(png|jpg)$ { }            # 正则 → 会截胡普通前缀，但输给 ^~
location / { }                          # 兜底前缀 → 优先级最低

# 结果：/static/logo.png → 命中 ^~ /static/（因为 ^~ 优先于正则）
# 若是 /images/logo.png → 命中正则 ~ \.(png|jpg)$

# 最常用的兜底写法
location / {
    try_files $uri $uri/ /index.html;   # 单页应用：找不到文件就返回 index.html
}
实战建议：① 静态资源用 ^~（避免被正则误伤）；② 后端接口用普通前缀 + proxy_pass；③ 正则只用于必要的场景（如文件后缀）；④ 始终配一个 location / 兜底，否则没匹配的请求会返回 404 且很难排查。
模块 3

反向代理与负载均衡

这是 Nginx 最核心的用途。其中 proxy_pass 的路径拼接规则，是坑最多的地方。

proxy_pass 的两种写法与路径拼接规则

# 写法一：不带 URI（末尾没有 /）—— 保留原始路径
location /api/ {
    proxy_pass http://backend;         # 注意：http://backend 后面什么都没有
}
# 请求 /api/users → 转发到 http://backend/api/users   （原样带过去）

# 写法二：带 URI（末尾有 /）—— 替换掉 location 匹配的部分
location /api/ {
    proxy_pass http://backend/;        # 注意：末尾有个 /
}
# 请求 /api/users → 转发到 http://backend/users   （/api/ 被替换成 /）
这是 Nginx 最经典的坑：proxy_pass 末尾那个斜杠决定了一切。
规则：如果 proxy_pass 的 URL 包含 URI（哪怕只是一个 /），Nginx 会用这个 URI 替换掉 location 匹配的那部分；如果不包含 URI（只有 http://backend），就把完整原始路径原样传给上游。
记忆口诀：末尾有斜杠 = 替换（去掉前缀）；末尾没斜杠 = 保留（带上前缀）。
写错的表现：后端收到的路径多了或少了 /api 前缀，导致 404。 
# 更复杂的例子，帮你彻底搞懂

location /api/v1/ {
    proxy_pass http://backend/svc/;
}
# 请求 /api/v1/users → http://backend/svc/users
# 规则：/api/v1/ 被替换成 /svc/

location /api/v1/ {
    proxy_pass http://backend;
}
# 请求 /api/v1/users → http://backend/api/v1/users
# 规则：没有 URI，原样保留

# 正则 location 里 proxy_pass 带 URI 时，不能有未捕获的变量
location ~ ^/user/(\d+)/ {
    proxy_pass http://backend/u$1/;    # ✓ 用捕获组 $1
}

负载均衡算法

# upstream 定义后端服务器组
upstream backend {
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
    server 10.0.0.3:8080;
}
算法机制适用场景
轮询 round-robin
（默认）		按顺序依次分发后端机器性能一致、请求耗时接近
weight=N按权重分发，权重高的接更多请求机器配置不同（新老机器混用）
ip_hash按客户端 IP 哈希，同一 IP 固定到同一台后端需要会话粘性（Session 不共享的场景）
least_conn发给当前连接数最少的后端请求耗时差异大的场景（长连接、长请求）
hash $key consistent一致性哈希，按某个 key（如 URL、Cookie）分发缓存命中优化（同 key 到同后端，提高缓存命中率）
# 完整 upstream 配置示例
upstream backend {
    least_conn;                          # 用最少连接算法
    server 10.0.0.1:8080 weight=3;       # 权重 3
    server 10.0.0.2:8080 weight=1;
    server 10.0.0.3:8080 backup;         # 备份机，主节点全挂才启用
    server 10.0.0.4:8080 down;           # 手动下线（维护时用）

    keepalive 32;                        # 到上游保持 32 个空闲长连接（重要！）
    keepalive_timeout 60s;
    keepalive_requests 1000;             # 单个长连接最多处理多少请求后重建
}
最容易漏的配置：upstream 的 keepalive。
默认情况下，Nginx 到后端的连接每个请求都要重新建立（TCP 三次握手 + 可能 TLS 握手），在高 QPS 下这是巨大的开销。
但光加 keepalive 32 还不够 —— 还必须在 location 里配两个头，否则长连接不生效： 
location /api/ {
    proxy_pass http://backend;
    # 这两行必须配，否则 upstream keepalive 不生效！
    proxy_http_version 1.1;              # HTTP/1.0 不支持长连接，必须用 1.1
    proxy_set_header Connection "";      # 清空 Connection 头，避免发 close
}

健康检查

# 开源版 Nginx：被动的失败标记（请求失败到阈值就暂时踢掉）
upstream backend {
    server 10.0.0.1:8080 max_fails=3 fail_timeout=30s;
    # 30 秒内失败 3 次 → 标记为不可用 30 秒，期间不再分发
}
# 局限：只有真实请求失败才会标记，不能主动探测

# 主动健康检查需要 Nginx Plus（商业版）或用 OpenResty / 第三方模块
# Nginx Plus 写法：
# health_check interval=5s fails=3 passes=2 uri=/health;

# 更通用的做法：让上游服务自己保证健康，靠 K8s 的就绪探针摘流量
注意：开源版 Nginx 没有主动健康检查。它只做被动标记（请求失败了才踢）。如果一台后端已经死了但还没被标记，流量会继续打过去，用户就会看到 502。生产上通常靠外层（如 K8s Service + 就绪探针、云 LB）做主动健康检查。
模块 4

四层与七层

"四层"和"七层"指 OSI 模型的工作层次。Nginx 两种都支持，但用途完全不同。

层次Nginx 模块能看到什么典型用途
四层 L4stream 模块只看到 IP + 端口 + TCP/UDP 包TCP 转发、数据库代理、MySQL/Redis 负载均衡、非 HTTP 协议
七层 L7http 模块能看到 HTTP 请求：URL、Header、Cookie、方法HTTP 反代、按路径/域名路由、改 Header、缓存、限流
# 四层（stream）配置：注意是在 http 块"外面"
stream {
    upstream mysql_cluster {
        server 10.0.0.1:3306;
        server 10.0.0.2:3306;
    }
    server {
        listen 3307;
        proxy_pass mysql_cluster;        # 纯 TCP 转发，不看协议内容
        proxy_timeout 10s;
        proxy_connect_timeout 3s;
    }
}
对比维度四层七层
性能更好（不解析应用层协议，纯转发）略低（要解析 HTTP）
能看到应用信息看不到（不知道 URL、Header）能看到并改写
路由能力只能按 IP/端口能按 URL、域名、Header、Cookie 路由
SSL 卸载可以（SSL 透传或终止）可以（通常在这里终止）
会话保持按 IP 哈希按 Cookie / Header
什么时候用四层：① 非 HTTP 协议（数据库、Redis、MQ、gRPC 的 TCP 模式）；② 只需要转发、不需要看内容，追求极致性能；③ 做 TLS 透传（证书在后端，Nginx 不解密）；④ 对 HTTPS 只做 TCP 转发，把证书放在后端统一管理。
什么时候用七层：绝大多数 HTTP/HTTPS 场景 —— 需要按路径路由、改 Header、透传真实 IP、限流、缓存时，必须用七层。
模块 5

常用配置实战

这一节全是可直接复制的配置片段，覆盖线上 90% 的需求。

静态文件服务与缓存头

location ^~ /static/ {
    root /var/www/html;                  # 文件路径 = root + URI
    expires 30d;                         # 加 Cache-Control 和 Expires 头，缓存 30 天
    add_header Cache-Control "public, immutable";  # immutable 表示内容永不变，强缓存
    access_log off;                      # 静态资源不打访问日志，省 IO

    # 大文件传输优化
    sendfile on;                         # 零拷贝，磁盘直接到网卡
    tcp_nopush on;                       # 攒满一个包再发，减少网络开销
    open_file_cache max=1000 inactive=20s;  # 缓存文件句柄，减少 stat 调用
}

# 带哈希的静态资源（如 app.a1b2c3.js）可以设超长缓存
location ~* \.[0-9a-f]{8}\.(js|css)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
}

反向代理与真实 IP 透传（必配）

location /api/ {
    proxy_pass http://backend;

    # ===== 真实 IP 透传（关键！不配的话后端日志全是 Nginx 的 IP）=====
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;                              # 客户端真实 IP
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;          # IP 链
    proxy_set_header X-Forwarded-Proto $scheme;                           # 原始协议 http/https
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Port $server_port;

    # ===== 超时（AI/长请求要调大）=====
    proxy_connect_timeout 5s;            # 连后端超时
    proxy_send_timeout 60s;              # 发请求给后端超时
    proxy_read_timeout 60s;              # 读后端响应超时（流式响应要调大）

    # ===== 长连接（配合 upstream keepalive）=====
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}

# 说明：X-Forwarded-For 是"IP 链"，格式如 客户端IP, 代理1IP, 代理2IP
# 后端要取第一个（最左边）才是真实客户端 IP
# $proxy_add_x_forwarded_for = 原有 XFF + 当前 $remote_addr，自动追加
X-Forwarded-For 可以伪造！客户端可以自己带一个 X-Forwarded-For: 1.2.3.4 头，Nginx 默认会追加，于是后端看到的第一个 IP 是伪造的。
正确做法：在最外层入口（可信代理）用 proxy_set_header X-Real-IP $remote_addr（直接取 TCP 层的真实源 IP，不可伪造），或者用 real_ip 模块配合可信代理列表： 
# 用 real_ip 模块把 $remote_addr 改写成真实客户端 IP（推荐）
set_real_ip_from 10.0.0.0/8;          # 信任的代理网段
set_real_ip_from 172.16.0.0/12;
real_ip_header X-Forwarded-For;       # 从哪个头取真实 IP
real_ip_recursive on;                  # 递归剥离可信代理，找到最左的非可信 IP

# 配完之后 $remote_addr 就是真实客户端 IP 了
# 日志格式里用 $remote_addr 即可，不需要额外处理

WebSocket 升级配置

location /ws/ {
    proxy_pass http://backend;
    proxy_http_version 1.1;                          # WebSocket 需要 1.1
    proxy_set_header Upgrade $http_upgrade;          # 透传 Upgrade 头
    proxy_set_header Connection "upgrade";           # 声明要升级协议
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;

    proxy_read_timeout 3600s;                        # WebSocket 长连接，超时要设很大
    proxy_send_timeout 3600s;
}
# 少了 Upgrade/Connection 两行，WebSocket 握手会失败（返回 400 或直接降级为普通 HTTP）

gzip 压缩

gzip on;
gzip_min_length 1k;                      # 小于 1KB 不压缩（压缩反而更大）
gzip_comp_level 5;                       # 压缩级别 1-9，5 是性能/效果平衡点
gzip_types text/plain text/css application/json
           application/javascript text/xml application/xml;   # 默认只压 text/html
gzip_vary on;                            # 加 Vary: Accept-Encoding 头，让 CDN 正确缓存
gzip_disable "msie6";                    # 老 IE 不压（兼容）
gzip_proxied any;                        # 代理的请求也压缩
# 注意：不要压缩图片/视频（已压缩过，再压是浪费 CPU）

限流：limit_req 与 limit_conn

# limit_req_zone 必须写在 http 块里（定义共享内存区）
limit_req_zone $binary_remote_addr zone=perip:10m rate=10r/s;
# $binary_remote_addr：按客户端 IP 限流（比 $remote_addr 省内存）
# zone=perip:10m：名为 perip 的共享内存，10MB（约能存 16 万个 IP 状态）
# rate=10r/s：每秒 10 个请求

limit_conn_zone $binary_remote_addr zone=conn_perip:10m;   # 按连接数限流

server {
    location /api/ {
        # 请求速率限流
        limit_req zone=perip burst=20 nodelay;
        # burst=20：允许突发 20 个请求排队（超过就 503）
        # nodelay：突发请求立即处理，不排队延迟
        #   不加 nodelay → 突发请求被排队，逐个放行（平滑但有延迟）
        limit_req_status 429;            # 超限返回 429（默认 503）

        # 并发连接数限流
        limit_conn conn_perip 10;        # 单个 IP 最多 10 个并发连接
        limit_conn_status 429;

        proxy_pass http://backend;
    }
}
限流的经典坑：不配 burst，正常用户会被误杀。
rate=10r/s 意味着平均每 100ms 一个请求。如果用户浏览器同时加载 15 个资源（HTML + JS + CSS + 图片），瞬间超过 10 个，多出来的直接 503，用户看到页面错乱。
正确做法：一定要配 burst（允许一定的突发），并视情况加 nodelay（突发立即处理）。没有 burst 的限流是"误杀制造机"。

跨域（CORS）配置

location /api/ {
    # 简单请求：直接加响应头
    add_header Access-Control-Allow-Origin $http_origin always;
    add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE, OPTIONS" always;
    add_header Access-Control-Allow-Headers "Content-Type, Authorization" always;
    add_header Access-Control-Allow-Credentials "true" always;
    # 注意：Allow-Credentials 为 true 时，Allow-Origin 不能用 *，必须回显具体源

    # 预检请求（OPTIONS）：直接返回 204，不转发给后端
    if ($request_method = OPTIONS) {
        add_header Access-Control-Max-Age 86400;   # 预检结果缓存 1 天
        return 204;
    }

    proxy_pass http://backend;
}
# add_header 的 always 参数：即使返回 4xx/5xx 也带上这个头，否则错误响应会丢 CORS 头
模块 6

HTTPS 配置

HTTPS 配置不难，但有三个细节没做对会导致"部分客户端报错"或"安全评级低"。

完整 HTTPS 配置

server {
    listen 443 ssl;
    http2 on;                            # 开启 HTTP/2（1.25.1+ 的写法；旧版用 listen 443 ssl http2）
    server_name www.example.com;

    # ===== 证书配置（注意证书链要完整）=====
    ssl_certificate     /etc/nginx/ssl/fullchain.pem;   # 服务器证书 + 中间证书
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;     # 私钥
    ssl_trusted_certificate /etc/nginx/ssl/chain.pem;   # 用于 OCSP Stapling 验证

    # ===== 协议版本与加密套件 =====
    ssl_protocols TLSv1.2 TLSv1.3;       # 只留 1.2/1.3，禁用不安全的 1.0/1.1
    ssl_prefer_server_ciphers off;       # TLS1.3 下建议 off，让客户端选更优套件
    ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384;
    ssl_session_cache shared:SSL:10m;    # 会话缓存，减少重复握手
    ssl_session_timeout 1d;
    ssl_session_tickets off;             # 关闭 ticket（有安全隐患）

    # ===== HSTS（强制浏览器只用 HTTPS）=====
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    # ===== OCSP Stapling（加速证书状态校验）=====
    ssl_stapling on;
    ssl_stapling_verify on;
    resolver 8.8.8.8 1.1.1.1 valid=300s;
    resolver_timeout 5s;

    # ===== 其他安全头 =====
    add_header X-Frame-Options SAMEORIGIN always;
    add_header X-Content-Type-Options nosniff always;

    location / { proxy_pass http://backend; }
}

# ===== HTTP 自动跳转 HTTPS =====
server {
    listen 80;
    server_name www.example.com;
    return 301 https://$host$request_uri;   # 301 永久重定向
}

三个关键细节

细节问题与解法
证书链要完整最常见的坑。只配了服务器证书、没配中间证书，浏览器（有缓存）能正常访问，但部分客户端（如某些 Java/Android/curl）会报"证书不受信任"。必须用 fullchain.pem（服务器证书 + 中间证书拼接）
TLS 版本只留 TLSv1.2 和 TLSv1.3。TLS 1.0/1.1 已被各大浏览器废弃，且存在安全漏洞。留着会拉低安全评级
HSTS 要谨慎开启Strict-Transport-Security 会让浏览器"记住"该域名只能用 HTTPS，一旦开启就无法回退到 HTTP（max-age 期内）。首次上线建议先用短 max-age 测试，确认无误再调长
OCSP Stapling 是什么、为什么有用：客户端验证证书时，理论上要访问 CA 的 OCSP 服务器确认证书没被吊销 —— 这个请求很慢（跨网络），且泄露隐私。
Stapling 让 Nginx 自己去取 OCSP 响应并"钉"（staple）在 TLS 握手里一起发给客户端，客户端不用再访问 CA，握手更快。 
# 证书自动续期思路（Let's Encrypt）
# 方案一：certbot 自动续期
certbot renew --quiet --post-hook "nginx -s reload"
# 加进 crontab，每天跑两次（Let's Encrypt 官方建议）
0 0,12 * * * certbot renew --quiet --post-hook "nginx -s reload"

# 方案二：acme.sh（更轻量）
acme.sh --install-cert -d example.com \
  --key-file /etc/nginx/ssl/privkey.pem \
  --fullchain-file /etc/nginx/ssl/fullchain.pem \
  --reloadcmd "nginx -s reload"
# acme.sh 自带定时任务，无需额外配 crontab

# 关键：续期后必须 reload，否则 Nginx 还在用旧证书
# 建议设一个证书到期告警（到期前 30 天），作为兜底
模块 7

性能调优与排错

调优的核心就三件事：进程数、连接数、文件描述符。排错的核心是看懂错误码和日志。

核心调优参数

# ===== 全局块 =====
worker_processes auto;                   # 通常 = CPU 核数（auto 自动检测）
worker_rlimit_nofile 65535;              # 单个 worker 能打开的文件描述符上限

events {
    worker_connections 10240;            # 每个 worker 的最大连接数（默认 512 太小！）
    use epoll;                           # Linux 下用 epoll（最高效）
    multi_accept on;                     # 一次接受多个新连接
}

http {
    sendfile on;                         # 零拷贝，静态文件必开
    tcp_nopush on;                       # 配合 sendfile，攒包再发
    tcp_nodelay on;                      # 长连接下不攒包，降低延迟
    keepalive_timeout 65;                # 客户端连接保持时间
    keepalive_requests 1000;             # 单个长连接最多处理多少请求
    client_max_body_size 20m;            # 请求体大小上限（默认 1m，上传大文件要调大）
    client_body_buffer_size 128k;
    client_header_timeout 10s;
    client_body_timeout 10s;
    types_hash_max_size 2048;
    server_tokens off;                   # 隐藏版本号（安全）
}
默认 worker_connections 512 是线上最常见的容量陷阱。
最大并发连接数 = worker_processes × worker_connections。默认 4 核 × 512 = 2048 —— 看起来还行？
但注意：Nginx 作为反向代理时，一个客户端连接要占用两个连接（客户端→Nginx 一个，Nginx→后端一个）。所以实际能服务的客户端数只有一半。而且还要留出内部连接（如 upstream keepalive）。
还有一层坑：即使 Nginx 配得再大，如果操作系统 ulimit -n（进程能打开的文件描述符上限）还是 1024，那 Nginx 依然卡在 1024。必须同时调 worker_rlimit_nofile 和系统 ulimit。 
# 查看并调整系统级限制
ulimit -n                        # 看当前限制（默认常是 1024）

# 临时调整
ulimit -n 65535

# /etc/systemd/system/nginx.service.d/override.conf

# 或改 /etc/security/limits.conf

nginx hard nofile 65535

# 错误日志级别：debug info notice warn error crit alert emerg
# 级别越高记录越少。生产用 warn 或 error，排查时临时降到 info

                   'urt=$upstream_response_time '         # 后端耗时（关键！）

# 排错技巧：$request_time vs $upstream_response_time

# 如果 upstream_response_time 大 → 问题在后端应用

常见错误码：谁的问题？

错误码谁的问题含义与排查
499客户端客户端主动断开连接（Nginx 特有码）。常见原因：用户刷新/关闭页面、后端太慢用户等不及、超时时间配得太短。大量 499 说明后端响应太慢
502后端Bad Gateway。Nginx 连上了后端，但后端返回了非法响应或直接断开。常见原因：后端进程崩溃、后端返回格式错误、upstream 配置的后端地址不通
504后端Gateway Timeout。Nginx 连上了后端，但后端在 proxy_read_timeout 内没返回响应。后端处理太慢，要优化后端或调大超时
500后端后端应用自己抛的服务器错误（应用 bug），不是 Nginx 的问题
503NginxService Unavailable。常见于：限流触发（limit_req 超限默认返回 503）、上游全部不可用、Nginx 达到连接上限
413NginxRequest Entity Too Large。请求体超过 client_max_body_size，上传大文件时常见
404Nginx 或后端路径不存在。看日志的 $upstream_status：如果是 404 说明后端返回的；如果 upstream 没记录说明 Nginx 自己就没匹配到文件/location
301/302Nginx重定向。检查是 return 还是 rewrite 触发的，以及 Location 头指向哪里
499 和 504 的区分：两者都是"慢"，但方向相反。
499 = 客户端先不等了，主动断开（Nginx 记录到客户端断开）。
504 = Nginx 等到自己的超时时间，还没等到后端响应，主动断开后端并返回 504。
如果同时出现大量 499 和 504，说明后端确实很慢，用户在超时前就跑了，Nginx 的超时又比用户耐心长。

用 stub_status 看连接状态

# curl 访问的输出
Active connections: 291
server accepts handled requests
 10431 10431 88432
Reading: 0 Writing: 12 Waiting: 279
字段含义
Active connections当前活跃连接数
accepts总共接受的连接数
handled成功处理的连接数。handled < accepts 说明有连接被丢弃（连接数超限！）
requests总请求数。requests / handled = 平均每连接处理了多少请求（keepalive 效果）
Reading正在读请求头的连接数
Writing正在写响应的连接数
Waiting空闲的 keepalive 连接数（过大说明 keepalive_timeout 太长）
关键诊断点：如果 handled 明显小于 accepts，说明 Nginx 因为连接数达到上限丢弃了连接，需要调大 worker_connections 和 ulimit。如果 Waiting 很大（几百上千），说明空闲长连接太多，可以适当调小 keepalive_timeout。
常见坑

十个线上坑

1
location 匹配顺序搞错，规则不生效
以为前缀匹配就是最长优先，结果被正则 location 截胡。记住优先级：精确 = > ^~ 前缀 > 正则 ~ > 普通前缀。静态资源用 ^~ 避免被正则误伤。
2
proxy_pass 末尾斜杠导致路径拼接错误
末尾有斜杠 = 替换 location 匹配的部分；没斜杠 = 原样保留。写错的表现是后端收到多/少一个前缀，直接 404。
3
没配真实 IP 透传，日志全是网关 IP
不配 X-Real-IP / X-Forwarded-For，后端日志里所有请求的来源 IP 都是 Nginx 的 IP，无法定位用户、无法按 IP 限流。必须透传，并用 real_ip 模块处理可信代理。
4
限流没配 burst，正常用户被误杀
rate=10r/s 但没配 burst，页面并发加载十几个资源时，超出的直接被拒（503/429）。必须配 burst（并视情况加 nodelay）。
5
默认只开了 512 个连接数
worker_connections 默认 512，4 核才 2048，作为反向代理时每客户端占 2 个连接，实际只能服务 1000 个客户端。必须调大，同时调 worker_rlimit_nofile 和系统 ulimit。
6
没配 upstream keepalive，上游连接反复重建
默认每个请求都要和上游重新握手。高 QPS 下开销巨大。配 keepalive 时别忘了在 location 里加 proxy_http_version 1.1 和 proxy_set_header Connection ""，否则不生效。
7
证书链不全，部分客户端报错
只配了服务器证书没配中间证书，有缓存的浏览器正常，但 curl/Java/部分 Android 报"证书不受信任"。必须用 fullchain.pem（服务器证书 + 中间证书）。
8
rewrite 和 return 优先级混淆
return 直接返回（不转发），rewrite 改 URI 后继续处理。server 块里如果同时有 return 和 location，return 会优先执行。要跳转用 return 301，要改路径用 rewrite。
9
WebSocket 没配 Upgrade 头，握手失败
少配 proxy_set_header Upgrade / Connection "upgrade"，WebSocket 握手失败。而且 proxy_read_timeout 默认 60s 会掐断长连接，要调大。
10
改配置直接 restart 而不是 reload
restart 会断掉所有连接（用户请求中断）。应该 nginx -t 校验后 nginx -s reload 平滑重载。而且 reload 失败会保留旧配置继续运行，比 restart 安全得多。
自测

六道题

1. 请求 /static/logo.png，下面哪个 location 会被命中？（假设都存在）
正确答案：^~ /static/。优先级顺序是：精确 = > ^~ 前缀 > 正则 > 普通前缀。^~ 前缀命中后不再检查正则，所以它赢过正则 location ~ \.(png|jpg)$。如果是普通前缀 location /static/，则会被正则截胡。
2. 配置 location /api/ { proxy_pass http://backend/; }，请求 /api/users 会被转发到？
正确答案：http://backend/users。proxy_pass 末尾有斜杠（带了 URI），会用这个 URI 替换掉 location 匹配的部分（/api/），所以 /api/users 变成 /users。如果写成 proxy_pass http://backend;（没斜杠），则原样保留为 /api/users。
3. 后端应用处理很慢，Nginx 在超时时间内没等到响应，会返回哪个错误码？
正确答案：504。Nginx 连上了后端，但后端在 proxy_read_timeout 内没返回响应，Nginx 主动断开并返回 504。502 是连上了但后端返回非法响应/崩溃；499 是客户端主动断开（Nginx 特有码）。
4. 关于 upstream keepalive，哪个说法是对的？
正确答案：还需要配那两个头。upstream keepalive 是 Nginx 到后端的长连接复用，默认 HTTP/1.0 不支持长连接，必须用 proxy_http_version 1.1，并清空 Connection 头（否则会发 close）。少任何一个，keepalive 都不生效。
5. 客户端大量收到 503，且 stub_status 里 handled 明显小于 accepts，最可能的原因是？
正确答案：连接数达到上限。handled < accepts 说明 Nginx 接受了连接但没能处理，通常是因为 worker_connections 太小或系统 ulimit 限制。需要调大 worker_connections、worker_rlimit_nofile 和系统 ulimit。
6. 为什么反向代理场景下，一个客户端连接要占用两个 Nginx 连接？
正确答案：客户端↔Nginx 和 Nginx↔后端各一个。Nginx 作为代理，要同时持有到客户端的连接和到上游后端的连接。所以最大并发客户端数 ≈ (worker_processes × worker_connections) / 2，规划容量时必须考虑这个。

术语表

术语一句话解释
反向代理Nginx 代表后端接收客户端请求并转发，客户端不知道真实后端
正向代理代表客户端去访问外部服务（如公司上网代理），和反向代理方向相反

epollLinux 的 IO 多路复用机制，一个线程管理大量连接
worker实际处理请求的工作进程，数量通常等于 CPU 核数
四层 L4工作在 TCP/UDP 层，只转发不解析应用协议
七层 L7工作在 HTTP 层，能看 URL/Header 做智能路由
location按 URL 路径匹配的配置块，有精确/前缀/正则三种匹配方式

会话粘性同一用户固定路由到同一后端（如 ip_hash），用于 Session 不共享场景
least_conn把请求发给连接数最少的后端，适合请求耗时差异大的场景

HSTS让浏览器强制只用 HTTPS 访问，一旦开启无法在 max-age 内回退
OCSP StaplingNginx 代取证书吊销状态并附在握手里，加速验证
证书链服务器证书 + 中间证书的拼接，不全会导致部分客户端不信任
stub_statusNginx 状态页，显示活跃连接、读写等待连接数
sendfile零拷贝技术，静态文件从磁盘直接送网卡，不经过用户态
worker_connections单个 worker 的最大连接数，默认 512，线上必须调大
下一步怎么练：① 起一个 Nginx，写三个 location（精确、^~ 前缀、正则），用 curl 验证匹配顺序；② 配两个 upstream 后端（可用两个 nginx 容器），对比 proxy_pass 带斜杠和不带斜杠的路径差异；③ 配一个带 proxy_buffering off 的 SSE 转发，观察流式效果；④ 用 openssl s_client 检查你的证书链是否完整；⑤ 配 limit_req 并用 ab 压测，观察 burst 的作用。
