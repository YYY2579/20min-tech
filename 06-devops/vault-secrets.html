二十分钟学透 Vault 与密钥管理

密钥管理的目标不是"有个地方存密码"，而是任何人、任何流程都不再接触明文。这篇讲 Vault 的 Seal/Unseal 机制、动态凭据、K8s 集成和轮转，以及 dev 模式上生产、Token 泄漏这些高频事故。

开始前

起两个 Vault：一个练手，一个像生产

# ===== 练手：dev 模式（数据在内存、自动 unseal，仅供本地）=====
docker run -d --name vault-dev --cap-add=IPC_LOCK -p 8200:8200 vault server -dev
export VAULT_ADDR='http://127.0.0.1:8200'
docker logs vault-dev 2>&1 | grep "Root Token"     # 取 root token 后登录
vault login hvs.xxxxx
vault status

# ===== 像生产：3 节点 raft + 文件级 unseal（练初始化流程）=====
# 每台机器一份配置 vault.hcl：
#   storage "raft" { path = "/vault/data"  node_id = "node1"  retry_join { leader_api_addr = "https://vault-1:8200" } ... }
#   listener "tcp" { address = "0.0.0.0:8200"  tls_cert_file = "/tls/vault.crt"  tls_key_file = "/tls/vault.key" }
# 初始化（只在集群第一台做一次，输出 5 个 unseal key 分片 + root token）
vault operator init -key-shares=5 -key-threshold=3
# 之后每台节点启动后都要 unseal，集齐任意 3 个分片各执行一次：
vault operator unseal <key-share-1>
vault operator unseal <key-share-2>
vault operator unseal <key-share-3>
dev 模式的三条"自动"：自动 unseal、自动挂载 secret/ 引擎、root token 直接打印在日志里，数据全在内存。它唯一的合法用途是本地开发调试。任何 CI、测试共享环境、生产用它，都是把密钥放在一个重启即失、无加密边界的地方。
模块 1

密钥管理原则与 Vault 架构

先立原则，再看 Vault 怎么实现它们。

原则落地做法
不落盘明文不出现在代码、镜像、CI 变量、K8s manifest、日志里。Vault 的定位就是"运行时按需取"
不硬编码禁止配置文件里写死密码；配置里只写 Vault 路径，启动时/运行时注入
最小权限每个应用一份 policy，只授它能读的那几个路径；默认拒绝
短生命 + 轮转静态密码改动态凭据：Vault 按需创建数据库账号，租约到期自动吊销
可审计开 audit 设备，每次读取都留痕（token 做 HMAC 脱敏）
可撤销泄漏了不是改密码这么简单 —— 要能 revoke token/吊销租约，让泄出去的凭据立刻失效

Seal / Unseal：Vault 的核心安全模型

Vault 存的所有数据在落盘前都被加密，加密用的 key 叫 barrier key；而 barrier key 本身又被 master key 加密后存在存储后端。master key 不在任何磁盘上 —— 它由 unseal key 分片在内存中重建。

Shamir 门限分割：初始化时把 master key 拆成 N 份（默认 5），设定门限 M（默认 3）。任意 M 份可重建 master key，少于 M 份在信息论上不可能恢复。
Unseal 过程：Vault 启动后处于 sealed 状态，服务不可用。不同持有者各执行一次 vault operator unseal 提交分片，凑齐 M 份重建 master key，解密 barrier key，之后才能读存储、对外服务。
Auto-Unseal：把"保管分片"委托给云 KMS（AWS KMS / Azure Key Vault / GCP Cloud KMS）或 HSM（PKCS#11）。节点重启后自动调 KMS 解密，免人工拼钥匙，门限变成"谁能调用 KMS"。

存储后端与高可用形态

后端形态说明
Integrated Storage (Raft)内置于 Vault，3/5 节点推荐。数据在节点间复制，自动选主；免维护外部存储
Consul外置 KV已有 Consul 集群时复用；多一个要维护的组件
File本地文件系统仅单节点，不能 HA；本地实验用

HA 模式下同一时刻只有一个 active 节点处理写请求，其余 standby 待命（Raft 选主，约秒级切换）。vault status 里的 HA Enabled / HA Mode 就是看这个。

# vault status 关键字段解读
Sealed:              true/false    # sealed = 服务不可用，需要 unseal
Initialized:         true/false    # 是否已执行过 operator init
Key Shares:          5             # 分片总数
Key Threshold:       3             # 门限：凑齐 3 份才能 unseal
Unseal Progress:     1/3           # 已提交几份，还差几份
HA Mode:             active/standby # 只有 active 处理写
请求链路：客户端 → TLS(8200) → auth 认证换 token → policy 鉴权 → secret engine 生成/读取 → barrier 加密 → 存储后端。排错按这条链路走：连不上看 listener/TLS；401 看 token 是否过期；403 看 policy 路径和能力；慢看存储后端。
模块 2

KV 引擎与 Policy 策略

KV 是使用率最高的引擎，放配置类秘密（数据库连接串、API Key）。v2 是默认且唯一该用的版本，带版本管理和软删除。

# 启用 kv-v2（dev 模式默认挂在 secret/）
vault secrets enable -path=secret kv-v2

# 写入 / 读取 / 列表
vault kv put secret/prod/app db_user=appuser db_pass='S3cr3t!' db_host=10.0.1.5
vault kv get secret/prod/app
vault kv get -field=db_pass secret/prod/app      # 只取单个字段，脚本里最常用
vault kv list secret/prod

# 版本管理：put 覆盖生成新版本，历史版本可回看
vault kv metadata get secret/prod/app            # 看版本号列表
vault kv get -version=3 secret/prod/app          # 读第 3 版
vault kv rollback -version=3 secret/prod/app     # 回滚（生成一个新版本指向旧数据）

# 软删除 vs 彻底销毁
vault kv delete secret/prod/app                  # 软删：最新版标记删除，历史版仍在
vault kv undelete -versions=4 secret/prod/app    # 恢复被软删的版本
vault kv destroy -versions=4 secret/prod/app     # 彻底销毁指定版本，不可恢复
vault kv metadata delete secret/prod/app         # 删除整个 secret 及全部历史
KV v1/v2 路径差异是经典 404 来源：v2 的 API 路径是 secret/data/xxx（数据面）和 secret/metadata/xxx（元数据/版本面），而 v1 直接是 secret/xxx。写 policy 时写错路径的表现就是"明明有权限却 403/404"。不确定时 vault path-help secret/data/app 查看路径帮助。

Policy：HCL 写的授权规则

# app-policy.hcl —— 最小权限示例
path "secret/data/prod/app/*" {
  capabilities = ["read", "list"]        # 只读 + 列举，不给写
}
path "secret/metadata/prod/app/*" {
  capabilities = ["list", "read"]        # 元数据面（版本列表、删除操作用这条路径）
}
path "database/creds/app" {
  capabilities = ["read"]                # 允许读取动态数据库凭据
}
path "pki/issue/app" {
  capabilities = ["create", "update"]    # 允许签发证书
}

# 应用策略 + 签发一枚受限 token
vault policy write app-policy app-policy.hcl
vault token create -policy=app-policy -ttl=1h -explicit-max-ttl=8h
# 默认拒绝一切；能力包括 create/read/update/delete/list/sudo/deny，deny 优先
模块 3

Database 引擎：动态凭据

这是 Vault 相对"密码本"的本质升级：应用不存密码，Vault 按需在数据库里创建真实账号，租约到期自动删除。

# 1. 启用数据库引擎
vault secrets enable database

# 2. 配置数据库连接（用一个有建账号权限的管理员，仅 Vault 持有）
vault write database/config/mysql \
  plugin_name=mysql-database-plugin \
  connection_url="{{username}}:{{password}}@tcp(10.0.1.5:3306)/" \
  allowed_roles="app" \
  username="vault_admin" \
  password="Vault@dmin123"

# 3. 定义角色：创建什么样的账号、什么权限、活多久
vault write database/roles/app \
  db_name=mysql \
  creation_statements="CREATE USER '{{name}}'@'%' IDENTIFIED BY '{{password}}'; GRANT SELECT, INSERT, UPDATE ON appdb.* TO '{{name}}'@'%';" \
  revocation_statements="DROP USER '{{name}}'@'%';" \
  default_ttl="1h" \
  max_ttl="24h"

# 4. 应用读取凭据（每次都是新账号）
vault read database/creds/app
# 返回：username=vault-root-app-a1b2c3d4  password=...  lease_duration=1h  lease_id=database/creds/app/xxxx

# 5. 续租（长任务超出租期时）与提前归还
vault lease renew database/creds/app/xxxx
vault lease revoke database/creds/app/xxxx      # 立即吊销，数据库用户当场被删

静态 vs 动态凭据

维度静态密码（KV 里存）动态凭据（Database 引擎）
泄漏影响面长期有效，所有人共用，泄漏即全线失守只对该应用有效，租约最长 24h，过期自动失效
轮转靠人定期改，改完要同步所有使用方（痛苦根源）天生短命，无需人工轮转
审计数据库里只有一个共用账号，查不出谁干的每个实例一个账号，操作可追溯到具体实例
代价零账号创建/删除有开销；连接池要处理"凭据会变"
接入动态凭据后应用必须改两个习惯：① 不能缓存连接池里的旧密码不放 —— 凭据过期重连时要重新向 Vault 取（用 Vault Agent 自动续租可绕开）；② root/管理员凭据也要管起来：vault write -f database/rotate-root/mysql 定期轮换 Vault 配置里那个管理员密码，否则"管了所有人的密码，唯独门户大开"。
模块 4

PKI 与 Transit：证书与加解密服务

PKI 引擎：应用自己签证书

# 1. 启用并放宽租约上限（证书周期通常 90 天，默认 32 天的 max_ttl 会不够）
vault secrets enable pki
vault secrets tune -max-lease-ttl=87600h pki        # 10 年

# 2. 生成根 CA（private_key_type=internal 表示私钥留在 Vault 内）
vault write -field=certificate pki/root/generate/internal \
  common_name="example.internal" ttl=87600h > root_ca.crt

# 3. 定义角色：允许签哪些域名、多长有效期
vault write pki/roles/app \
  allowed_domains="example.internal" \
  allow_subdomains=true \
  max_ttl="72h" \
  require_cn=true

# 4. 应用按需签发（或走 /pki/issue/app 也可在角色里配 no_store）
vault write pki/issue/app common_name="app01.example.internal" ttl="24h"

# 5. 配置 CRL/CA 分发地址（客户端校验证书时要用）
vault write pki/config/urls \
  issuing_certificates="https://vault.example.com:8200/v1/pki/ca" \
  crl_distribution_points="https://vault.example.com:8200/v1/pki/crl"
vault read pki/crl/pem        # 取吊销列表
vault write pki/tidy           # 清理过期证书记录

Transit 引擎：加密即服务

# 场景：应用要存加密的手机号/身份证，但不想自己管密钥
vault secrets enable transit
vault write -f transit/keys/pii            # 创建密钥（AES256-GCM）

# 加密（输入必须 base64）/ 解密
vault write transit/encrypt/pii plaintext=$(base64 <<< "13800138000")
# 返回 ciphertext=vault:v1:AbCdEf... 存这个密文到数据库
vault write transit/decrypt/pii ciphertext="vault:v1:AbCdEf..."

# 密钥轮换：轮换后新数据用新版本加密，旧密文仍能解（ciphertext 里的 v1/v2 就是版本号）
vault write -f transit/keys/pii/rotate
vault read transit/keys/pii                # 看 latest_version 与 min_decryption_version

# 签名与验签（HMAC/非对称，按密钥类型）
vault write transit/sign/pii input=$(base64 <<< "payload")
vault write transit/verify/pii input=$(base64 <<< "payload") signature="vault:v1:..."
vault write transit/hmac/pii input=$(base64 <<< "payload")   # 算 HMAC，常用于 Webhook 签名
两个认知边界：① Transit 不是加密存储 —— 它只提供"用一下密钥"的服务，密文和明文都由调用方持有，别把 Vault 当对象存储用；② PKI 的根 CA 私钥在 Vault 里，Vault 的备份就是 CA 的命 —— 没备份 unseal 分片和快照，等于随时可能失去给全公司签证书的能力。根 CA 轮换成本极高，签发生命周期（24~72h）要短，根要长（10 年）。
模块 5

认证方法：Token、AppRole、Kubernetes

认证方法回答"你是谁"，通过后换一枚 Vault token，token 携带 policy 决定"你能干什么"。

方法凭据形态适用
TokenVault 自签发的令牌人首次登录、系统间引导；不适合长期给机器用
AppRoleRoleID + SecretID 两个部件CI/CD、传统虚拟机、无 K8s 的机器
KubernetesPod 的 ServiceAccount JWTK8s 内工作负载的首选，零静态凭据
Userpass/LDAP用户名密码人，接企业目录服务
JWT/OIDC外部 IdP 签发的 JWTCI SaaS（GitLab/GitHub Actions）、SSO 联邦
# ===== AppRole：给 CI 用的双因子（RoleID 可公开，SecretID 要保密）=====
vault auth enable approle
vault write auth/approle/role/ci \
  policies="ci-policy" \
  token_ttl=20m \
  token_max_ttl=1h \
  secret_id_ttl=10m          # SecretID 本身 10 分钟后作废，逼每次现取

vault read auth/approle/role/ci/role-id          # 固定不变，可放进 CI 配置
vault write -f auth/approle/role/ci/secret-id    # 每次不同，存进 CI 的受保护变量

# 换取 token
vault write auth/approle/login role_id=xxxx secret_id=yyyy
# 返回 auth.client_token，后续用它读 secret

# ===== Kubernetes Auth：Pod 用 SA token 换 Vault token =====
vault auth enable kubernetes
# Vault 所在集群：K8s API 地址 + 用于校验 JWT 的 token reviewer 权限
vault write auth/kubernetes/config \
  kubernetes_host="https://192.168.49.2:8443" \
  disable_local_ca_jwt=false

# 绑定：只有 default 命名空间里叫 app-sa 的 SA 能换 ci-policy
vault write auth/kubernetes/role/app \
  bound_service_account_names=app-sa \
  bound_service_account_namespaces=default \
  policies=app-policy \
  ttl=1h
选型口诀：K8s 里的负载用 Kubernetes Auth（无静态凭据，随 Pod 生命周期）；CI/VM 用 AppRole（SecretID 短 TTL，泄漏窗口小）；人用 OIDC/LDAP（接统一身份）。任何场景都不要把一枚长期 token 硬编码进代码 —— 那是把 Vault 的防线降级成配置文件。
模块 6

与 K8s 集成：Agent Injector

Vault Agent Injector 是一个准入 webhook：检测到 Pod 带特定注解时，自动注入 sidecar 容器，由它完成认证、读 secret、渲染成文件挂进业务容器。

# 部署（官方 Helm chart 一条命令；装完默认对所有命名空间生效）
helm repo add hashicorp https://helm.releases.hashicorp.com
helm install vault hashicorp/vault \
  --set "server.enabled=false" \            # 已有外部/独立部署的 Vault 集群时
  --set "injector.enabled=true" \
  --set "injector.externalVaultAddr=http://vault.default.svc:8200"

业务侧只加注解

apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  template:
    metadata:
      annotations:
        vault.hashicorp.com/agent-inject: "true"           # 开注入
        vault.hashicorp.com/role: "app"                    # 用哪个 k8s auth 角色
        vault.hashicorp.com/agent-inject-secret-dbpass: "secret/data/prod/app"
        vault.hashicorp.com/agent-inject-template-dbpass: |
          {{- with secret "secret/data/prod/app" -}}
          {{ .Data.data.db_pass }}
          {{- end -}}
    spec:
      serviceAccountName: app-sa
      containers:
        - name: app
          image: app:1.4.2
          command: ["/bin/sh","-c","source /vault/secrets/dbpass && ./app"]
  • 产物形态：sidecar 把渲染结果写到共享卷 /vault/secrets/dbpass，业务容器按普通文件读取。secret 不在环境变量里，不会随 docker inspect / /proc/<pid>/environ 泄露。
  • 更新机制：sidecar 持续 watch，Vault 侧数据变更后重新渲染并原子替换文件（inotify 生效），但应用要主动重读文件，多数框架需要自己实现 reload 钩子。
  • CSI Provider 是另一条路：用 SecretProviderClass 把 secret 挂成 volume/csi 驱动，适合不想注入 sidecar 的场景；功能比 injector 少（模板渲染能力弱）。
  • 排错入口：Pod 起不来先看 kubectl logs app -c vault-agent —— 90% 的问题是 policy 路径不对、role 绑定的 SA 不匹配、或 Vault 地址不可达。
注解里的路径必须和 policy 精确匹配：policy 授了 secret/data/prod/app/*，注解里写 secret/data/prod/application 就是 403。另一个高频错误是忘了给 Deployment 设 serviceAccountName，sidecar 用的是 default SA，k8s auth 直接拒绝。
模块 7

高可用、灾备与审计

生产形态

# 高可用：3 或 5 节点 raft（奇数个，容忍 (n-1)/2 故障）
vault operator raft list-peers              # 看集群成员
vault operator step-down                    # 主动让主下台（演练/维护窗口用）

# 备份：raft 快照 = 全部加密数据的完整副本
vault operator raft snapshot save /backup/vault-$(date +%F).snap
vault operator raft snapshot restore /backup/vault-2026-10-15.snap

# Auto-unseal 配置片段（seal 段，替换人工 unseal）
seal "awskms" {
  region     = "cn-north-1"
  kms_key_id = "arn:aws:kms:cn-north-1:123456789:key/xxxx"
}

# 灾备复制（DR Replication）：备集群复制存储与密钥，主挂后提升备为主
vault operator generate-dr-operation-token        # 在备集群生成 DR 操作令牌
vault operator promote -dr-recovery-secondary <dr-operation-token>

审计：合规的地基

# 开启文件审计设备（可同时开多个：file + syslog）
vault audit enable file file_path=/var/log/vault/audit.log
# 日志记录每次请求：路径、操作、token（HMAC 脱敏后）、时间、结果
# 注意：audit 设备一旦启用无法禁用，只能换路径 —— 这是防"擦日志"的设计
能力做法
监控telemetry { prometheus_retention_time = "24h" } + /sys/metrics，盯 seal 状态、请求延迟、lease 数量
根令牌治理初始化后 root token 立即改密或吊销，用 vault operator generate-root 流程生成新 root（需门限分片协作）
备份清单快照（加密数据）+ unseal 分片（解密钥匙）+ 配置文件。三样缺一，恢复就是不可能的
升级策略raft 滚动升级，先备后主；升级前必做快照；跨大版本先读升级说明
DR 复制和普通备份是两个维度：快照是"数据副本"（小时级 RPO，恢复要重放）；DR replication 是"热备集群"（秒级 RTO，主挂了 promote 备集群）。对 Vault 可用性敏感的业务（它挂了全公司读不到 secret）两个都要：日常快照保数据，DR 保连续服务。
模块 8

十个线上坑

1
生产环境用 dev 模式
内存存储、自动 unseal、无持久化，容器一重启所有 secret 消失且 root token 明文在日志里。dev 模式唯一用途是本地开发。
2
5 个 unseal 分片锁在同一台机器/同一个人手里
Shamir 门限的防"单点被拖走"意义归零。分片应分人、分设备、分地点保管；能上云 KMS auto-unseal 的场合优先自动 unseal。
3
Token 泄漏进代码、镜像或 CI 日志
表现为 git 历史里的 hvs. 开头字符串、打进镜像的 token 文件、CI 日志里 echo 出来的 token。对策：机器用 AppRole/K8s Auth 而非静态 token；泄漏后 vault token revoke 立即止血，别只改密码。
4
拿 root token 当日常钥匙
root 能绕过所有 policy，且审计里分不清"谁用 root 干了什么"。按需签发带 policy 的 token，root 只在初始化/灾难恢复时用，用完立即处理。
5
把 Vault 当日志中心/配置中心往 KV 里塞日志
KV 带版本管理，每条日志都是新版本，存储和快照体积爆炸、读延迟上升。日志进日志系统，配置进配置中心，Vault 只放秘密。
6
不开 audit 设备
出事后无法回答"谁在什么时候读了哪个 secret"，等保/合规直接不过。vault audit enable file 开起来，并接日志告警（如大量 403）。
7
动态凭据 lease 过期没人续
应用启动时取一次密码缓存到连接池，1 小时后 lease 到期数据库账号被删，连接池集体报错。解法：Vault Agent 自动续租，或应用实现"重连时重新取凭据"。
8
只部署单节点 Vault
单点 = 全公司 secret 读取的单点，重启/故障期间所有服务启动不了。至少 3 节点 raft，且跨可用区部署。
9
没有快照 + unseal 分片的备份
存储损坏或误删后，加密数据没有钥匙 = 永久丢失，且 PKI 根 CA 无法重建。定期 raft snapshot + 分片分人备份 + 恢复演练。
10
policy 图省事直接给 root 或 sudo
一个被注入的 Pod 拿到 root policy 就能读走全部 secret，爆炸半径无限大。按路径授最小能力，deny 规则优先，定期审计 policy 清单。
自测

六道题

1. Vault 启动后处于 sealed 状态，恢复服务的正确做法是？
正确答案：提交 unseal 分片凑齐门限。master key 只存在于分片的重建结果里，不落任何磁盘；sealed 是设计上的安全状态而不是故障。配了 auto-unseal（云 KMS/HSM）则由节点自动完成，不需要人工。
2. "5 个分片、门限 3"的准确含义是？
正确答案：任意 3 份可重建，少于 3 份无解。这是 Shamir 秘密共享的门限方案：N 份中任意 M 份可恢复，M-1 份不泄露任何信息。所以分片的分发数量要超过门限（丢 2 份还能开门），但单点持有量要低于门限（被拖走 2 份也开不了门）。
3. 应用读取了数据库动态凭据，租约到期后会发生什么？
正确答案：自动吊销，数据库账号被删。这就是动态凭据的安全价值：泄漏的凭据有明确寿命，不需要"改密码"这个协同动作。前提是应用/Agent 在租约到期前续租，否则会拿到失效凭据连不上库。
4. K8s 中让应用获得 Vault secret，推荐的方式是？
正确答案：Agent Injector sidecar + 文件卷。env 会随 /proc 和 kubectl describe 泄露，写死镜像则把秘密分发给每个能拉到镜像的人。sidecar 模式认证零静态凭据、secret 以文件形式消费，是 K8s 集成的标准答案。
5. dev 模式不能上生产的核心原因是？
正确答案：无持久化 + 自动 unseal + root token 明文。三条叠加的结果是：重启即全量丢 secret、任何人都能直接读全部数据、密钥在日志里裸奔。它和"生产模式"是同一套引擎的不同启动方式，不是功能裁剪版。
6. 关于 Vault 的审计（audit）设备，正确的是？
正确答案：记录脱敏请求日志且启用后不可禁用。不可禁用是防"擦日志"的设计；token 以 HMAC 形式记录，既保留关联性又不暴露原值。合规场景（等保、金融审计）audit 是硬性要求，不开等于没有溯源能力。
