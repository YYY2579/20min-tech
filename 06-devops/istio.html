二十分钟学透 Istio 与服务治理

Istio 是 Service Mesh 的主流实现，把流量管理、mTLS、可观测性从应用代码里搬到 Sidecar 代理。这篇讲机制：控制面/数据面怎么协作、VirtualService/DestinationRule 怎么写、规则优先级怎么排、Sidecar 开销怎么压。

开始前

Service Mesh 解决什么问题

微服务一多，每个服务都要自己实现：熔断、重试、超时、灰度、mTLS、链路追踪。用 SDK 的问题是多语言要写五遍、版本升级绑业务发布。Service Mesh 的思路：把这些能力下沉到每个 Pod 里的 Sidecar 代理，业务无感知。

能力SDK 方案的问题Service Mesh 方案
熔断/重试/超时每语言一套库，配置分散在代码里DestinationRule 统一配置，运维可改
灰度发布应用自己解析流量权重VirtualService 按权重路由，控制面秒级生效
mTLS证书管理埋进业务代码Sidecar 自动双向认证，证书自动轮转
可观测性各服务埋点口径不一Envoy 统一产出指标/日志/trace
故障演练改代码发版才能注入故障VirtualService 声明式注入延迟/中止
Mesh 不是银弹：它引入 Sidecar 资源开销（每 Pod 多一个容器）、新增一层故障点、排障链路变长（要会看 Envoy 配置）。10 个服务以内、流量简单的团队，Ingress + SDK 往往更划算。上 Mesh 的典型触发点：服务数 50+、多语言、合规要求全链路 mTLS。
模块 1

Istio 架构：控制面 + 数据面

两个平面

平面组成职责
数据面每个 Pod 里的 Envoy Sidecar（istio-proxy 容器）实际转发所有进出 Pod 的流量，执行路由、mTLS、遥测
控制面istiod 一个 Deployment（1.5+ 合并了 Pilot/Citadel/Galley）服务发现、下发配置（xDS）、签发证书、校验 CRD

xDS：控制面与数据面的协议

istiod 通过 xDS 系列 API 把配置推给每个 Envoy。Envoy 不需要重启，收到新配置热加载：

协议下发内容对应 Istio CRD
CDSCluster：有哪些上游服务、怎么连ServiceEntry、DestinationRule
RDSRoute：请求怎么路由、按什么权重VirtualService
EDSEndpoint：上游的具体 Pod IP 列表自动来自服务发现
LDSListener：监听哪些端口、走哪条链Gateway、Sidecar
SDSSecret：mTLS 证书与私钥自动签发轮转

注入与安装

# 安装（istioctl 方式，生产推荐）
istioctl install --set profile=demo -y        # demo = 全功能含 Kiali/Jaeger
istioctl install --set profile=default -y     # default = 生产最小集

# 命名空间级自动注入（打标签，之后新建 Pod 自动带 sidecar）
kubectl label namespace default istio-injection=enabled

# 验证注入：Pod 里应该有 2 个容器（app + istio-proxy）
kubectl get pod webapp-xxx -o jsonpath='{.spec.containers[*].name}'
# webapp istio-proxy

# 已有 Pod 要重启才会注入；排查用
istioctl analyze -n default                 # 静态检查常见配置错误，装完先跑它
流量走向（重点）：Pod 内所有进出流量被 iptables 规则劫持到 Envoy 的 15001 端口。应用容器以为自己在直连对方服务，实际是 app → 本地 Envoy → 对端 Envoy → 对端 app。所以 Kubelet 健康检查、应用探针也会被劫持 —— 这是模块 8 坑 3 的根源。
模块 2

流量管理：VirtualService 与 DestinationRule

这两个 CRD 是所有流量治理的地基：VirtualService 决定"请求去哪"，DestinationRule 决定"到了之后怎么处理这个子集的连接"。

VirtualService 核心能力

# vs.yaml —— 金丝雀 + 按 header 灰度 + 超时重试，一个例子全覆盖
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: webapp
spec:
  hosts:
    - webapp                # K8s Service 短名（同命名空间解析）
  gateways:
    - mesh                  # mesh = 仅集群内；配合 gateway 名 = 入口流量
  http:
    - match:                # ① 带内部灰度头的请求 → 全部去 canary
        - headers:
            x-canary:
              exact: "true"
      route:
        - destination:
            host: webapp
            subset: canary
    - route:                # ② 其余流量 90/10 金丝雀
        - destination:
            host: webapp
            subset: stable
          weight: 90
        - destination:
            host: webapp
            subset: canary
          weight: 10
      timeout: 5s            # ③ 超时
      retries:
        attempts: 3          # ④ 重试次数
        perTryTimeout: 2s
        retryOn: 5xx,reset,connect-failure

DestinationRule：定义 subset 与连接策略

# dr.yaml —— 用 label 划分版本，并配置熔断（outlierDetection）
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: webapp
spec:
  host: webapp
  trafficPolicy:
    connectionPool:
      tcp:
        maxConnections: 100      # 熔断：单 Pod 最大连接数
      http:
        h2UpgradePolicy: DEFAULT
        maxRequestsPerConnection: 10
    outlierDetection:
      consecutive5xxErrors: 5     # 连续 5 次 5xx → 摘除实例
      interval: 10s              # 扫描间隔
      baseEjectionTime: 30s      # 摘除时长，之后按比例恢复
      maxEjectionPercent: 50     # 最多摘 50%，防全摘导致雪崩
  subsets:
    - name: stable              # subset 名 = VS 里 destination.subset
      labels:
        version: v1
    - name: canary
      labels:
        version: v2

故障注入（ chaos 演练不用改代码）

# fault.yaml —— 给 10% 的请求注入 500ms 延迟 + 5% 请求直接中止
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: webapp-fault
spec:
  hosts: [webapp]
  http:
    - fault:
        delay:
          percentage:
            value: 10
          fixedDelay: 500ms
        abort:
          percentage:
            value: 5
          httpStatus: 503
      route:
        - destination:
            host: webapp
            subset: stable
路由匹配优先级（Istio 官方规则）：header/uri 匹配 > 精确（exact）> 前缀（prefix）> 正则（regex）> 端口。多个规则按"最精确者优先"，同精度按创建顺序。所以"灰度头规则放最前面"只是习惯，真正保证顺序的是匹配精度。排查路由不生效：istioctl x describe pod webapp-xxx 看合并后的实际路由。
模块 3

安全：自动 mTLS 与授权策略

PeerAuthentication：mTLS 三种模式

# pa.yaml —— 命名空间级强制 mTLS
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: default
spec:
  mtls:
    mode: STRICT          # STRICT = 只接受 TLS；PERMISSIVE = 明文/TLS 都收
模式行为适用场景
STRICT只接受 mTLS 连接，明文直接拒绝生产环境终态
PERMISSIVE明文和 mTLS 都接受迁移期默认值，兼容未注入 Pod 的调用方
DISABLE完全关闭 mTLS调试，生产禁用
证书自动管理：istiod 内置 CA，给每个 Sidecar 自动签发 SPIFFE 证书（默认 24 小时有效期，自动轮转），证书身份形如 spiffe://cluster.local/ns/default/sa/webapp —— 服务账号（ServiceAccount）就是身份，授权策略可以直接按 SA 写。

AuthorizationPolicy：四层模型

# ap.yaml —— 只允许 billing 服务调用 payment 的 POST /charge
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: payment-allow-billing
  namespace: default
spec:
  selector:
    matchLabels:
      app: payment          # 作用在哪些 Pod 上（不写 = 整个命名空间）
  action: ALLOW             # ALLOW / DENY / AUDIT / CUSTOM
  rules:
    - from:
        - source:
            namespaces: ["billing-ns"]      # 来源命名空间
      to:
        - operation:
            methods: ["POST"]               # HTTP 方法
            paths: ["/charge"]              # 精确路径
      when:
        - key: request.headers[x-version]   # 自定义条件
          values: ["v2"]
字段匹配维度
from.sourceprincipal（SA 身份）、namespaces、ipBlocks、remoteIp
to.operationmethods、paths、ports、hosts
whenheader、JWT claim、SNI 等任意键值
AuthorizationPolicy 的"拒绝一切"陷阱：一旦给某 Pod 配了任何一条 ALLOW 策略，该 Pod 立即变为默认拒绝（白名单模式），没被显式允许的流量全部 403。迁移期标准姿势：先 AUDIT（只记日志不拦截）观察 24 小时，确认没误伤再切 ALLOW。
模块 4

可观测性：Kiali、访问日志、追踪

Istio 的最大卖点之一：不改一行代码，自动获得三个平面的可观测性。全部由 Envoy 旁路产出。

Telemetry API：统一开关（Istio 1.10+ 替代 MeshConfig 里的散落配置）

# telemetry.yaml —— 全网格默认开访问日志，tracing 采样 10%
apiVersion: telemetry.istio.io/v1alpha1
kind: Telemetry
metadata:
  name: mesh-default
  namespace: istio-system
spec:
  accessLogging:
    - providers:
        - name: envoy        # 输出到 stdout，由采集器（OTel/Fluent Bit）收
  tracing:
    - providers:
        - name: jaeger       # 需先部署 tracing provider（Jaeger/Zipkin/OTel）
      randomSamplingPercentage: 10.0
      customTags:
        environment:
          literal:
            value: "prod"

模块 5

Gateway：入口流量治理

集群外流量进 mesh 的唯一正规入口是 Gateway（跑在 istio-ingressgateway Pod 里的 Envoy）。常见错误是直接用 Ingress Controller，绕过了 mesh 的 mTLS 和可观测性。

# gateway.yaml —— 对外暴露 443，配 TLS 证书
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: webapp-gw
spec:
  selector:
    istio: ingressgateway     # 选定 ingressgateway Pod（按标签）
  servers:
    - port:
        number: 443
        name: https
        protocol: HTTPS
        tls:
          mode: SIMPLE
          credentialName: webapp-tls   # 引用 K8s Secret 里的证书
      hosts:
        - "webapp.example.com"    # 精确域名，别用 *
# vs-ingress.yaml —— 把 Gateway 收到的流量路由进集群
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: webapp-public
spec:
  hosts:
    - "webapp.example.com"       # 必须和 Gateway 里的 host 一致
  gateways:
    - webapp-gw                  # 绑定上面的 Gateway（少了这行 = 只走 mesh 内）
    - mesh
  http:
    - route:
        - destination:
            host: webapp.default.svc.cluster.local
            port:
              number: 80
            subset: stable

东西向 vs 南北向

方向路径配置
南北向外部 → Gateway(ingressgateway) → 服务Gateway + VirtualService 绑定
东西向服务 A → 服务 B（全 mTLS）VirtualService 只写 hosts，gateways 用 mesh
新手最常犯：VirtualService 里写了 hosts 但 gateways 只写了 mesh，结果外网访问不通 —— Gateway 那条路根本没绑定。反过来，给 Gateway 配了证书但没建对应 Secret，ingressgateway 直接报错不 ready。排障第一招：kubectl logs -n istio-system deploy/istio-ingressgateway。
模块 6

Sidecar 开销与优化

Sidecar 不是免费的：每个 Pod 多一个容器，吃 CPU/内存，增加约 1~3ms 延迟，启动还比业务容器慢。优化核心是两件事：砍它接收的配置、砍它转发流量。

默认开销（istio-proxy 容器默认 limit）

指标默认值高流量服务建议
内存 request200Mi512Mi~1Gi（路由规则多时）
CPU request100m500m~1 核（QPS 上 3000 后）
延迟增量P99 +2ms 左右可测不可忽视，对延迟敏感服务提前评估
启动耗时1~3 秒（先于业务 ready）配合 holdApplicationUntilProxyStarts
连接开销每 Pod 多 2 条 mTLS 连接（入/出）高扇出服务关注 envoy_server_live 指标

优化三板斧

# 第一斧：Sidecar CRD —— 告诉 Envoy "你只需要关心这些上游"
# 默认 Envoy 会接收全网格所有服务的 endpoints，500 服务时内存爆炸
apiVersion: networking.istio.io/v1beta1
kind: Sidecar
metadata:
  name: webapp-sidecar
  namespace: default
spec:
  workloadSelector:
    labels:
      app: webapp
  egress:
    - hosts:
        - "default/*"          # 只接收本命名空间服务发现
        - "istio-system/*"     # 控制面必须留
  outboundTrafficPolicy:
    mode: REGISTRY_ONLY       # 只放行集群内已知服务，外部流量默认拒绝
# 第二斧：全局安装参数收窄监听范围
istioctl install --set profile=default \
  --set global.proxy.excludeOutboundPorts="443,3306" \   # 这些端口流量不劫持
  --set global.proxy.excludeInboundPorts="9090"            # 入向不劫持（管理端口）

# 单 Pod 级别覆盖（annotation 形式）
metadata:
  annotations:
    proxy.istio.io/config: |
      excludeOutboundPorts: "443"
# 第三斧：资源与启动顺序
# istioctl install 时调大 proxy 资源
istioctl install --set profile=default \
  --set global.proxy.resources.requests.cpu=200m \
  --set global.proxy.resources.requests.memory=256Mi

# Pod 级：业务容器等 proxy ready 后再起（避免启动期请求 503）
metadata:
  annotations:
    proxy.istio.io/config: |
      holdApplicationUntilProxyStarts: true
效果预期：一个 200 服务的集群，默认配置下每个 Envoy 缓存全部 endpoints，单 proxy 内存 300Mi+；加了 Sidecar CRD 收敛后通常能降到 80~120Mi，整体 Pod 内存降 30%~50%。大规模 mesh 的第一优化项永远是 Sidecar CRD，不是加机器。
模块 7

升级与版本兼容

兼容性铁律

  • 控制面（istiod）版本 ≥ 数据面（proxy）版本：新 istiod 兼容旧 proxy（N-1 个 minor 版本），反过来不行
  • Istio 官方支持最近 3 个 K8s minor 版本，升级 K8s 前先查 Istio 支持矩阵
  • CRD API 版本：v1alpha3 已废弃，新配置一律用 networking.istio.io/v1beta1 和 security.istio.io/v1beta1

金丝雀升级（生产标准姿势）

# 不停服升级：新旧两套 istiod 并存，逐命名空间重启 workload 切流量

# 1. 装新版本为 canary（revision 标签隔离）
istioctl install --set profile=default --revision=1-24 -y

# 2. 给测试命名空间打新版本标签，观察一个业务周期
kubectl label namespace canary-ns istio.io/rev=1-24 --overwrite

# 3. 确认无误，滚动切换生产命名空间（重启 workload 让 Pod 注入新 proxy）
kubectl label namespace default istio.io/rev=1-24 --overwrite
kubectl rollout restart deployment -n default

# 4. 全部切完后卸载旧版本
istioctl uninstall --revision=1-23 -y

# 升级前后必跑：
istioctl analyze --all-namespaces          # 升级前
istioctl proxy-status                       # 升级后，看每个 proxy 同步是否 STALE
升级事故 top1：istiod 和 proxy 跨大版本。典型症状是 Pod 日志刷 xds.lds: response rejected、服务间歇 503。原则：proxy 永远跟在 istiod 后面升，或者用 revision 金丝雀，绝不一次性全集群替换。
模块 8

十个线上坑

1
VirtualService 规则"没生效"或顺序错乱
规则按匹配精度优先（exact > prefix > regex），不是 YAML 书写顺序。想强制顺序就提升匹配精度，并用 istioctl x describe pod 看合并后的实际路由。
2
hosts 写错导致 503 NR
VS 的 host 必须是 K8s Service 名（同 ns 可短名）或完整 FQDN（webapp.default.svc.cluster.local），写成 Pod 名、IP、错命名空间都解析不到 upstream。
3
Kubelet 探针被 Sidecar 劫持，Pod 反复重启
探针流量也被 iptables 送进 Envoy，代理未就绪时探针失败。解法：探针端口重写为 http（由 sidecar 代转），或加 holdApplicationUntilProxyStarts 注解。
4
Gateway 配了但 VirtualService 没绑定 gateways 字段
外部流量根本进不来。VS 必须显式列出 gateway 名；hosts 还要和 Gateway 里的 host 完全一致。
5
配了一条 ALLOW 授权策略，服务突然全 403
AuthorizationPolicy 是白名单模型：一旦有 ALLOW，其余全部拒绝。迁移期先用 action: AUDIT 观察日志，确认放行清单完整后再切 ALLOW。
6
mTLS 直接上 STRICT，老服务全断
未注入 Pod 的明文调用方被拒。正确节奏：PERMISSIVE 迁移 → 全注入 → 确认 istio_requests_total 里无明文 → 切 STRICT。
7
Envoy 内存涨到 500Mi+，Pod 被 OOMKill
Envoy 默认接收全网格 endpoints。加 Sidecar CRD 收敛 egress hosts，大规模 mesh 能降 30%~50% 内存。
8
升级后 Pod 日志刷 xds.lds response rejected
istiod 与 proxy 跨大版本不兼容。用 revision 金丝雀升级，保证控制面版本领先数据面，最多跨一个 minor。
9
开了全网格访问日志，一个月存储费翻三倍
QPS 1000 的服务一天 8000 万行日志。默认关闭，按服务按需开，或用 Telemetry 的 filter 只记错误请求。
10
DestinationRule 的 subset 名和 VirtualService 引用不一致
症状：流量 100% 落到默认版本，金丝雀不生效。subset 名对不上时 Envoy 找不到 cluster 直接报错。istioctl analyze 能提前发现这类问题。
自测

六道题

1. Istio 数据面与控制面之间用什么协议同步配置？
正确答案：xDS。istiod 把 VirtualService/DestinationRule 等 CRD 转换成 Envoy 的 listener/route/cluster/endpoint/secret 配置主动推送，Envoy 热加载不重启。CRD watch 只是 istiod 获取用户意图的第一步。
2. 同一个 host 上有两条 VirtualService 规则：一条匹配 URI 前缀 /api，一条匹配路径精确 /api/charge。请求 GET /api/charge 走哪条？
正确答案：精确匹配优先。Istio 规则优先级：header/uri 精确 > 前缀 > 正则 > 端口，同精度才按创建顺序。所以"调整 YAML 书写顺序"经常不生效，要改的是匹配精度。
3. 想给某服务加白名单访问控制，直接创建一条 ALLOW 的 AuthorizationPolicy 会发生什么？
正确答案：立即默认拒绝（白名单模型）。只要存在任何 ALLOW 策略，未匹配的流量全部 403。安全做法：先 action: AUDIT 观察日志，补全放行清单后再切 ALLOW。
4. 200 个服务的集群，Envoy Sidecar 内存占用过大，最有效的优化是？
正确答案：Sidecar CRD 收敛。默认 Envoy 接收全网格所有服务的 endpoints，配置量与服务数成正比。用 workloadSelector + egress hosts 收窄后内存通常降 30%~50%。加 limit 只是延后 OOM。
5. 外部域名要接入 Istio 并复用 mesh 的 mTLS 与遥测，正确做法是？
正确答案：Gateway + VirtualService 绑定。南北向流量必须走 istio-ingressgateway，VS 的 gateways 字段要显式写上 Gateway 名，hosts 与 Gateway 一致。Ingress Controller 方案绕过了 mesh，没有 mTLS 和统一遥测。
6. 关于 Istio 升级，说法正确的是？
正确答案：istiod 领先 proxy（最多跨一个 minor）。revision 金丝雀让新旧 istiod 并存，逐命名空间切换，出问题秒级切回。Istio 只支持最近 3 个 K8s minor 版本，但不是一一绑定。
