二十分钟学透 Kubernetes 排障实战

开始前

造一个“故障训练场”

排障是熟练工种，先得有故障可排。下面这些 Pod 覆盖最常见的四类异常，全文案例都基于它们。

# 故障 1：镜像不存在 → ImagePullBackOff
kubectl create deploy broken-image --image=nginx:not-exist-tag

# 故障 2：容器启动即退出 → CrashLoopBackOff
kubectl create deploy crashy --image=busybox:1.36 -- /bin/sh -c "echo boot; exit 1"

# 故障 3：资源请求过大 → Pending
kubectl create deploy greedy --image=nginx
kubectl patch deploy greedy -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","resources":{"requests":{"cpu":"64","memory":"512Gi"}}}]}}}}'

# 故障 4：探针失败 → Pod 起来但不 Ready
kubectl create deploy badprobe --image=nginx
kubectl patch deploy badprobe -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","readinessProbe":{"httpGet":{"path":"/nope","port":80},"periodSeconds":5}}]}}}}'

# 观察四兄弟的状态
kubectl get pods -w
本篇假设：你能用 kubectl 完成基本操作（apply / get / describe / logs / exec）。排障篇不讲怎么建集群，讲的是出事后按什么顺序看什么。配套前置建议先看同目录 kubernetes.html 与 k8s-advanced.html。
模块 1

系统化排障方法论

高手和菜鸟的差距不在命令量，在顺序。乱翻一通半小时，按层排查五分钟。核心原则：先恢复业务，再找根因；先看系统自己说的，再看自己的猜测。

四层排查框架

层级查什么典型症状与工具
集群层控制面是否健康：API Server、etcd、scheduler、controller-manager、CoreDNS、CNIkubectl 卡住/超时、对象改动不生效。kubectl get --raw='/readyz?verbose'、看 kube-system Pod
节点层kubelet 存活、Ready 状态、磁盘/PID/内存压力、容器运行时节点 NotReady、Pod 被驱逐。kubectl describe node、journalctl -u kubelet
网络层DNS、Service/Endpoints、kube-proxy、NetworkPolicy、CNI能创建 Pod 但访问不通、间歇超时。get endpoints、netshoot 容器
应用层Pod 状态、探针、日志、退出码、资源用量、配置与密钥CrashLoop、5xx、慢查询。kubectl logs、describe pod
顺序心法：自上而下缩小范围，自下而上定位细节。先用集群/节点层排除“大面”问题（控制面挂了查应用层毫无意义），再扎进应用层细节。90% 的“应用故障”最后发现是节点或网络问题。

黄金四问（每次排障先过一遍）

最近改了什么？统计下来，大部分故障由变更引起：发版、配置更新、证书轮换、节点扩缩容、CNI/CSI 升级。先看变更记录，再动手。
影响面有多大？单个 Pod、单个服务、整个 namespace、整个集群？影响面决定响应级别和排查方向（单 Pod → 应用层；整个集群 → 控制面/节点）。
系统自己说了什么？K8s 的 Event、Pod 的 status、容器的退出码，已经把 80% 的答案写在脸上了。先读完再说。
能先止损吗？回滚版本、扩容副本、切流、重启。止损和定位可以并行，不要为了“搞清楚再修”让故障延长。

必备起手命令序列

# 30 秒看清全局（按这个顺序敲）
kubectl get nodes                          # 1. 节点都 Ready 吗
kubectl get pods -A -o wide | grep -v Running   # 2. 谁不在 Running
kubectl get events -A --sort-by=.lastTimestamp | tail -30   # 3. 最近发生了什么
kubectl top nodes                           # 4. 节点资源水位（需 metrics-server）
kubectl get apiservices | grep -v True      # 5. 有没有 API 扩展挂了
模块 2

Pod 状态机解读

Pod 的 status.phase 只有五个值，但每个异常 phase 背后都有一棵成因树。学会从现象反推，比背命令重要。

Pending：调度不出去

事件里的关键词含义与解法
FailedScheduling ... 0/5 nodes available: 3 Insufficient cpu资源不够。所有节点 requests 之和超了。降 requests、扩节点、或开 cluster-autoscaler
... had untolerated taint {key: value}候选节点有污点，Pod 没带 toleration。加 toleration 或换节点组
... didn't match Pod's node affinity/selector节点标签不匹配。检查 required nodeAffinity 与节点实际标签
... node(s) didn't match pod topology spread constraints打散约束卡住。域数量不够，改 ScheduleAnyway 或扩域
... unbound immediate PersistentVolumeClaimsPVC 没绑上，Pod 无法调度（VolumeBinding 在 Filter 阶段）。先解决 PVC（见模块 5）
... exceed quotanamespace ResourceQuota 打满。kubectl describe quota 看 used/hard
... skipped due to intersect with LimitRangeLimitRange 限制下，默认 requests/limits 换算后超限。调整 LimitRange 或显式指定

CrashLoopBackOff：容器反复退出

退出原因在 lastState.terminated 里，日志要看上一轮的。退避间隔 10s → 20s → 40s … 封顶 300s。

线索成因与解法
exitCode 137SIGKILL。① OOMKilled（超 memory limit）：kubectl describe pod 看 reason=OOMKilled，放大 limit 或修内存泄漏；② liveness 探针失败被 kubelet 杀
exitCode 143SIGTERM。优雅终止超时后被杀，或收到关闭信号后自己退出。检查 terminationGracePeriodSeconds 与应用退出逻辑
exitCode 0 也重启程序正常退出了 —— Command 写错（比如前台进程被 shell 包装后退出）、sidecar 模式的主进程结束。检查 command/args
exitCode 1 / 2应用自身报错。看 kubectl logs --previous。常见：配置缺失、连不上依赖（DB/Redis）、启动检查不过
Init:CrashLoopBackOffinit 容器挂了，主容器还没轮到。单独看 init 容器日志
启动慢被杀liveness 探针太激进。上 startupProbe 给启动预算（见进阶篇模块 6）

ImagePullBackOff / ErrImagePull

事件里的关键词含义与解法
manifest unknown / not foundtag 或仓库名写错。最常见。核对 image:tag，确认镜像真被推送了
authentication required / unauthorized私有仓库没配凭证。创建 imagePullSecret 并在 Pod 上引用（或打到 ServiceAccount 上）
toomanyrequests / rate limit触发仓库限流（Docker Hub 匿名拉取 100 次/6 小时）。用镜像仓库代理或配凭证
no route to host / i/o timeout节点到仓库网络不通。防火墙、代理、或 registry 证书问题（用 http 连 https 端口）
# 三兄弟的标准排查动作
kubectl describe pod <pod>          # 看 Events 段和 lastState —— 一半答案在这里
kubectl logs <pod> --previous       # 看上一轮（已崩溃）容器的日志
kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated}' | jq
# 输出里 reason/exitCode/message 三件套：OOMKilled / 137 / 各自的信息

其他常见 phase 与状态

状态含义
Running 但 0/1 Ready进程活着但 readiness 探针失败 —— Service 不会给它流量。“服务好了但没流量”的第一嫌疑人
Terminating 卡住优雅终止没完成：preStop 钩子阻塞、长连接不关、或 finalizer 没人移除
Completed正常退出（Job/CronJob）。Deployment 里出现说明 command 写错了
Unknownkubelet 长时间没上报状态，节点可能失联。配合 node NotReady 看
模块 3

事件与 describe 技巧

Event 是 K8s 的“黑匣子”，默认只保留 1 小时（--event-ttl，etcd 里默认 1h）。排障要趁早，且要会按时间排序。

kubectl get events -A --sort-by=.lastTimestamp全集群事件按时间正序，看最后的异常
kubectl get events --field-selector involvedObject.name=<pod>只看某个对象的事件，最干净
kubectl get events -A --field-selector type=Warning只看告警事件，过滤噪音
kubectl describe pod <pod> -n <ns>容器状态、探针配置、挂载、QoS 一页看全
kubectl get pod -o yaml > pod.yaml存证！改天复盘/对照历史时靠它

describe pod 的阅读顺序

# 从上到下，只看这五段
1. Status / Conditions    # Ready、Initialized、ContainersReady 哪个是 False
2. Events                 # 最近 20 条，Warning 优先 —— 排障的主入口
3. Containers.State       # waiting(reason) / running / terminated(exitCode)
4. Containers.Restart Count # 重启几次了、Last State 是什么
5. Volumes / QoS / Node    # 挂载对不对、QoS 类别、落在哪个节点

日志相关命令

kubectl logs <pod> --previous --tail=200看崩溃前一轮的日志（CrashLoop 必用）
kubectl logs <pod> -c <container> --since=30m多容器 Pod 指定容器；按时间窗过滤
kubectl logs -l app=web --tail=-1 --prefix按标签聚合多个 Pod 的日志，带 Pod 名前缀
stern web --since 10m第三方神器：多 Pod 彩色实时 tail，支持正则
两个盲区：① 被驱逐 Pod 的日志会随容器一起消失，重要现场先用 kubectl logs --previous 抢下来；② Event 有 1 小时 TTL，凌晨的故障早上九点再查，事件可能已过期。
模块 4

网络排障

K8s 网络问题有个特点：能建 Pod 不代表能通信。四类高频：DNS、Service 不通、NetworkPolicy 误伤、kube-proxy 模式问题。

DNS：先查 CoreDNS，再怀疑世界

# 标准验证动作（在任意 Pod 里执行）
kubectl run netbox --rm -it --image=nicolaka/netshoot -- bash
nslookup kubernetes.default.svc.cluster.local    # Service 全名必须能解析
nslookup myservice                                # 短名（靠 search 域）也要能解析
nslookup baidu.com                                # 外部域名（走节点上游 DNS）

# CoreDNS 自身状态
kubectl -n kube-system get deploy coredns
kubectl -n kube-system logs deploy/coredns --tail=100
kubectl -n kube-system get endpoints coredns       # 有没有后端
症状根因与解法
短名解析失败、全名正常Pod 的 dnsPolicy 不是 ClusterFirst（改了 Default/None），或 resolv.conf 的 search 域被覆盖
解析外部域名超时CoreDNS 的上游（节点 /etc/resolv.conf）配错；或集群 CIDR 与外部冲突
解析慢（几百 ms~秒级）ndots:5 经典问题：默认对每个域名先依次拼 4 个 search 域再查全名，外部域名一次查询变 5 次。对外部域名用带点的全名，或调 dnsConfig 的 ndots 与 searches
间歇性超时、日志有 conntrackUDP 并发打满 conntrack 表：sysctl net.netfilter.nf_conntrack_count/max，调大 max 或启用 conntrack 回收
# 调低 ndots、精简 search 域的 Pod 级配置
dnsConfig:
  options:
    - name: ndots
      value: "2"            # 默认 5，含点超过 2 段就直接查全名
  searches:
    - default.svc.cluster.local
    - svc.cluster.local
    - cluster.local    # 砍掉多余的 search 域

Service 不通：二分法定位

先看 Endpoints 有没有内容：kubectl get endpoints <svc>。为空 → selector 不匹配或后端 Pod 全不 Ready（回到模块 2）；有 IP → 继续往下
直接 Pod IP 通不通：从同节点/跨节点容器 curl <podIP>:port。不通 → CNI/跨节点路由/NetworkPolicy；通 → 问题在 Service 链路
ClusterIP 通不通：集群内 curl <clusterIP>:port。不通 → kube-proxy 规则或 conntrack；通 → 问题在 DNS 或外部入口
看 kube-proxy 规则：iptables 模式查 iptables -t nat -L KUBE-SVC-XXX 有没有对应链；IPVS 模式 ipvsadm -Ln 看 virtual server 和 real server
# Service 链路一键检查
kubectl get svc <svc> -o wide                 # ClusterIP 是什么
kubectl get endpoints <svc> -o yaml           # 后端 Pod IP 列表
kubectl get pods -o wide --show-labels        # Pod IP 和标签（核对 selector）
kubectl describe svc <svc> | grep -A3 Selector # Service 的 selector
经典事故：改了 Deployment 的 Pod 模板标签（如 app=web → app=web-v2），Service selector 还是老的，Endpoints 直接清空，流量全 502。发版改标签时，务必同步检查 Service selector。看 endpoints 比看 Pod 快十倍。

NetworkPolicy：默认放行，策略是“白名单叠加”

  • 前提：CNI 必须实现 NetworkPolicy。Flannel 默认不实现——你 apply 了策略但完全不生效，这是最隐蔽的坑。Calico/Cilium 可以
  • 多个策略是并集（允许的叠加），Pod 一旦被任何策略选中，就变成“只允许策略里声明的流量”
  • ingress 和 egress 是两个独立维度：只写了 ingress 策略，egress 仍全通；反过来同理
  • DNS 是隐藏依赖：默认拒绝 egress 时，必须放行 kube-system 里 CoreDNS 的 53/UDP+TCP，否则域名解析全挂
# 最小必要策略：只放行 ingress 8080，egress 全拒（先确认 DNS 已放行）
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-allow
spec:
  podSelector:
    matchLabels: { app: api }
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: gateway }
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: monitoring }
      ports: [{ protocol: TCP, port: 8080 }]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
      ports: [{ protocol: UDP, port: 53 }, { protocol: TCP, port: 53 }]
    - to: [{ podSelector: { matchLabels: { app: db } } }]
      ports: [{ protocol: TCP, port: 5432 }]

kube-proxy 三种模式

模式原理与排查
iptables默认。Service 翻译成 nat 表链，规则 O(n) 线性扫描。大规模集群（Service 上万）延迟明显。排查：iptables -t nat -L KUBE-SERVICES | head
ipvs基于哈希表，性能好，支持更多 LB 算法。排查：ipvsadm -Ln 看 VS/RS 是否齐全
nftables较新版本引入，替代 iptables 后端，规则管理更高效
模块 5

存储排障

PVC 相关的故障有个特征：Pod 卡在 ContainerCreating，事件里全是 FailedMount/FailedAttach。按绑定 → 挂载两段拆。

第一段：PVC 为什么 Pending

# 看 PVC 卡在哪一步
kubectl get pvc                          # STATUS=Pending 就是没绑上
kubectl describe pvc <pvc>               # Events 会说明原因
kubectl get storageclass                 # 有没有默认 SC（default 标记）
事件关键词成因与解法
waiting for first consumer to be created before binding正常行为，不是故障。SC 配了 volumeBindingMode: WaitForFirstConsumer，要等使用它的 Pod 被调度后才绑定。Pod 调度不出去 → PVC 一直 Pending，根因在调度
no persistent volumes available for this claim没有 PV 可绑：动态供给没工作（provisioner 挂了/参数错），或静态 PV 的 capacity/accessModes 不匹配
storageclass.storage.k8s.io "xxx" not foundPVC 引用的 SC 不存在，或名字拼错。删掉 storageClassName 用默认，或修正名字
failed to provision volume ... exceeds quota云厂商配额或 namespace ResourceQuota 打满。提配额或清理
node(s) had volume node affinity conflictPV 有 zone 限制（云盘跟节点同 AZ），Pod 被调度到了别的 AZ。给 Pod 加 nodeAffinity 或换拓扑感知 SC

第二段：挂载为什么超时

事件关键词成因与解法
Multi-Attach error for volume "pvc-xxx": Volume is already exclusively attached to one nodeRWO 卷被两个节点同时挂。老 Pod 没退干净（Terminating 卡住）、或 kubelet 缓存了旧的 attachment。强制删除卡住的 Pod，或上 CSI 的 attach detach 排查
Unable to attach or mount volumes: unmounted volumes=[data]attach 成功但 mount 失败。看 kubelet 日志与 CSI 节点插件日志
timed out waiting for the conditionCSI 驱动无响应（驱动 Pod 挂了/云 API 超时）。kubectl -n kube-system get pods | grep csi
# 节点侧定位（登录到 Pod 所在节点）
lsblk                                  # 块设备挂载情况
mount | grep pvc                       # 已挂载的 PVC
crictl ps -a | grep <pod>              # containerd 里的容器状态
journalctl -u kubelet --since "10 min ago" | grep -i volume   # kubelet 的挂载日志

# CSI 侧
kubectl -n kube-system get pods | grep -E 'csi|ebs|disk'   # CSI 驱动是否健康
kubectl get volumeattachment           # attach 到哪个节点、成功没有
存储排障口诀：PVC 先看绑定（事件说清楚），挂载先看节点（kubelet 日志说清楚），中间看 VolumeAttachment。另外记住：改 accessModes 不会生效（创建时定死），RWO 不能同时给两个节点 —— 多 AZ 扩容前先确认 SC 支持。
模块 6

节点问题

节点问题的传播路径是连锁的：一个节点 NotReady → Pod 被重新调度 → 其他节点过载 → 更多驱逐。所以要快杀。

NotReady 的排查链路

确认是节点问题还是控制面问题：kubectl get node 看 STATUS 和最后心跳时间。所有节点同时 NotReady → 大概率控制面/API Server 问题，别去查节点
看节点 condition：kubectl describe node <node>。Ready=False、MemoryPressure/DiskPressure/PIDPressure 哪个亮灯，直接决定方向
登录节点看 kubelet：systemctl status kubelet、journalctl -u kubelet --since "20 min ago"。kubelet 起不来最常见：证书过期、配置错、容器运行时（containerd/docker）挂了
看资源压力：df -h（磁盘）、df -i（inode）、free -m、ps aux | wc -l（进程数）。日志写满 /tmp、镜像堆积是常事
确认运行时与网络：systemctl status containerd、CNI 插件 Pod 是否在该节点正常
# 节点侧高频命令
kubectl describe node <node> | grep -A8 "Conditions:"   # 四个 pressure + Ready
kubectl get node <node> -o jsonpath='{.status.allocatable}' | jq   # 可分配资源
journalctl -u kubelet -n 200 --no-pager                  # kubelet 日志
du -sh /var/lib/containerd 2>/dev/null                  # 镜像/容器层占用
ls /var/log | head                                      # 日志文件是否爆了
sysctl vm.drop_caches=1                                 # 仅应急：释放 page cache
压力类型第一时间动作
MemoryPressurekubelet 开始按 QoS 驱逐 Pod。找内存大户（top pods --containers），必要时先扩容再查泄漏
DiskPressure清理：crictl rmi --prune 删未用镜像、清容器日志、设 logrotate。然后配 kubelet 的 imageGC 阈值
PIDPressure进程/线程泄漏。看是哪个 Pod（按 namespace 统计 /proc），重启该 Pod 止血
Ready=Falsekubelet 心跳断了。先救 kubelet（证书/运行时），不行就 kubectl drain 摘流换机器
切勿：节点一 NotReady 就无脑重启节点。不存证就重启，等于销毁现场；而且如果是磁盘写满，重启后照样 NotReady。先 describe、再登录、最后才动大手术。确认要重启时，先 kubectl drain <node> --ignore-daemonsets --delete-emptydir-data，避免 Pod 被硬杀。
模块 7

调试工具：kubectl debug 与 netshoot

容器里没有 curl、没有 dig、没有 tcpdump —— 这是排障第一堵墙。不要为了调试改生产镜像，用临时容器和旁路容器。

kubectl debug 的三种用法

# 1. 临时容器（Ephemeral Container）：进一个正在跑的 Pod，共享进程网络
kubectl debug <pod> -it --image=busybox:1.36 --target=<container>
# --target 指定共享哪个容器；不指定也能进，但看不到对方进程（除非 shareProcessNamespace）
# 适用：容器挂了进不去、镜像里没 shell

# 2. 复制 Pod：克隆一个带调试工具的副本，不动原 Pod
kubectl debug <pod> --copy-to=<pod>-debug --image=nicolaka/netshoot
# 适用：原 Pod 有严格安全策略，或怕污染现场

# 3. 节点调试：在目标节点上起一个特权 Pod

模块 8

三个完整故障案例

案例 1：间歇性 DNS 超时，服务随机报 connection timeout

现象：上午高峰期，约 5% 请求 DNS 解析耗时超过 1 秒，重试后恢复。应用日志只有超时，没有拒绝。

验证是 DNS 而非网络：netshoot 里 dig baidu.com 反复 20 次，记录耗时分布 —— 确认部分查询慢、部分正常
看查询放大了多少：临时 Pod 里 cat /etc/resolv.conf，发现 ndots:5 + 4 个 search 域 → 每个外部域名先查 4 个"域名.search域"再查全名，查询量放大 5 倍
看 CoreDNS 侧证据：kubectl -n kube-system logs deploy/coredns 出现大量 NXDOMAIN 和 conntrack insertion failed，CoreDNS 单副本 CPU 打满
三层修复：① CoreDNS 扩容到 3 副本 + nodeAffinity 打散；② 对高频访问外部域名的 Deployment 配 dnsConfig 降 ndots 到 2、砍 search 域；③ 节点调大 net.netfilter.nf_conntrack_max
验证：同时间段 dig 20 次全部 <20ms；给应用加 DNS 耗时监控面板，防复发
本案知识点：ndots 放大效应、CoreDNS 副本数、conntrack 表、dnsConfig 调优。DNS 问题一定要看放大倍数，只看“能不能解析”会漏掉 90% 的慢查询。

案例 2：发布后全站 502，Pod 明明 Running

现象：上线 web v2.3 后网关持续 502。kubectl get pods 全部 Running，日志没有任何错误。

分层定位：Pod Running → 先跳过应用层查网络层。kubectl get endpoints web —— 空的，答案已经出现
查为什么空：kubectl describe svc web，selector 是 app=web；kubectl get pods --show-labels，v2.3 的 Pod 标签变成了 app=web-v2 —— 标签改了就脱管
确认没有第二个原因：临时把标签改回 app=web 的 Pod 起来后 endpoints 有内容、502 消失 —— 单点根因确认
修复与止血：① 立即 kubectl rollout undo 回滚到 v2.2；② 修正 Deployment 标签回 app=web 后重新发布；③ readiness 探针确认正常（本案里探针是好的，否则 endpoints 也会空）
防复发：CI 加校验“Service selector 必须匹配 Deployment 标签”；监控加 endpoints 数量为 0 持续 1 分钟 告警 —— 比 502 告警早得多
本案知识点：endpoints 是 Service 的真实后端；502 + Pod Running = 先查 endpoints；selector 与标签脱管是最常见的“无声故障”。

案例 3：一个节点 NotReady，引发半个集群 Pod 重建

现象：凌晨告警 node-3 NotReady，随后多个服务 Pod 被重建，延迟飙升。

判断影响面：kubectl get nodes 只有 node-3 NotReady → 单节点问题，不去翻控制面
看 condition：kubectl describe node node-3：DiskPressure=True、Ready=False。事件有 eviction threshold met
登录节点找谁吃满了盘：df -h 显示 /var/log 100%；du -sh /var/log/containers/* | sort -h | tail 定位到某 Pod 的日志把磁盘写爆（应用 debug 级别狂打日志）
连锁反应确认：kubelet 开始驱逐该节点 Pod（先 BestEffort），被驱逐 Pod 涌向其他节点 → 其他节点 requests 超售、 pending 增多
止损与修复：① 清理并轮转日志（配 logrotate/容器日志 maxSize）；② kubectl cordon node-3 先别再调度进来；③ 修应用日志级别；④ uncordon 前确认磁盘水位恢复
防复发：磁盘使用率 >80% 告警（别等 100%）；kubelet 配 containerLogMaxSize/maxFiles；核心服务设 Guaranteed QoS 降低驱逐概率
本案知识点：节点压力的连锁传播、按 QoS 驱逐、磁盘类故障要在节点上找真凶。注意：清磁盘只是止血，不修日志量几天后复发。
模块 9

十个线上坑

1
只看 Pod 状态，不看 Events
Pending/CrashLoop 的原因 kube-scheduler 和 kubelet 都写在事件里了。describe pod 先看 Events 段，能省一半时间。
2
CrashLoop 看当前日志，一片空白
容器重启后旧日志没了，必须 kubectl logs --previous。当前日志为空恰恰说明它起来就挂了。
3
DNS 慢，只测“能不能解析”
ndots:5 让外部域名查询放大 5 倍，能解析但很慢。要看耗时分布和放大倍数，别用能不能通下结论。
4
Service 不通先怪 CNI
先 kubectl get endpoints。空 = selector 脱管或后端全不 Ready，跟网络八成没关系。
5
apply 了 NetworkPolicy 却没生效
CNI 不支持（如纯 Flannel）。策略对象创建成功但没人执行，是最隐蔽的“假安全”。
6
PVC Pending 就怀疑存储挂了
很可能是 WaitForFirstConsumer 在等 Pod 调度，而 Pod 调度不出去的根源在资源/污点/亲和性。
7
为调试给生产镜像装工具
改镜像 = 改发布物，风险不可控。用 kubectl debug 临时容器或 netshoot 旁路。
8
节点 NotReady 直接重启机器
不存证就重启等于销毁现场；磁盘写满重启也没用。先 describe、登录、再决定。
9
排障不存证，事后无法复盘
get -o yaml 存 Pod、存事件、存日志。Event 只有 1 小时 TTL，凌晨的故障早上就没了。
10
用 --force --grace-period=0 删 Pod
跳过优雅终止，长请求被硬切、PV 的 attachment 可能残留，还可能留下孤儿 finalizer。只在确认卡死时用。
自测

六道题

1. Pod 状态 ImagePullBackOff，describe 事件里写 manifest unknown。第一件事做什么？
正确答案：核对镜像 tag。manifest unknown 就是仓库里没这个 tag（拼错/没推/删了），与凭证无关（authentication required 才是凭证问题）。
2. 容器进入 CrashLoopBackOff，kubectl logs 当前输出为空。正确的排查命令是？
正确答案：logs --previous。容器重启后当前日志被清空，上一轮的日志还留着。exitCode + lastState + --previous 日志三件套定位绝大多数启动即崩。
3. Service 突然全 502，Pod 全部 Running 且日志正常。第一步查什么？
正确答案：get endpoints。502 + Pod Running 的典型组合是 endpoints 空（selector 与标签脱管，或后端全不 Ready）。先确认有没有后端，再查链路。
4. 应用访问外部域名时快时慢，全名解析正常但耗时几百毫秒。最可能的根因是？
正确答案：ndots 放大。默认 ndots:5 + search 域，让外部域名一次解析变 5 次查询，CoreDNS 压力上来后延迟抖动。解法：dnsConfig 调 ndots/searches，CoreDNS 扩容。
5. PVC 一直 Pending，事件写 waiting for first consumer。正确的理解是？
正确答案：等首个消费者。这是延迟绑定特性（保证 PV 与 Pod 同区），不是故障。Pod 调度不出去（资源/污点/亲和性），PVC 就会一直等。
6. 容器退出码 137、lastState.reason=OOMKilled，意味着什么？
正确答案：超 memory limit 被内核杀。137 = 128+9（SIGKILL）。reason=OOMKilled 是权威判定；探针失败不会有这个 reason。解法：放大 limit、修泄漏，JVM 注意 MaxRAMPercentage。
