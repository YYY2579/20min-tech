开始前

部署一个能练的 Harbor

Harbor 官方提供在线/离线安装包（自带 docker compose 编排），一条流程即可拉起全部组件。版本号按你实际要用的稳定版替换。

# 1. 下载安装包（示例用 v2.11.0）
wget https://github.com/goharbor/harbor/releases/download/v2.11.0/harbor-online-installer-v2.11.0.tgz
tar -xzf harbor-online-installer-v2.11.0.tgz
cd harbor

# 2. 生成自签证书（测试用；生产必须用受信任 CA 签发的证书）
mkdir -p /etc/harbor/ssl
openssl req -x509 -newkey rsa:4096 -sha256 -days 3650 -nodes \
  -keyout /etc/harbor/ssl/harbor.key \
  -out /etc/harbor/ssl/harbor.crt \
  -subj "/CN=harbor.internal.example.com" \
  -addext "subjectAltName=DNS:harbor.internal.example.com"

# 3. 生成配置并按需修改（保留策略、Trivy、jobservice 并发都在这里）
cp harbor.yml.tmpl harbor.yml
vi harbor.yml

# 4. 预处理 + 安装（--with-notary 可选，用于内容信任）
./prepare --with-trivy
./install.sh

# 5. 验证组件是否全部起来
docker compose ps        # 旧安装包用 docker-compose ps

harbor.yml 里最该改的几项

hostname: harbor.internal.example.com   # 必须与证书 CN/SAN 一致，客户端按此地址访问

https:
  port: 443
  certificate: /etc/harbor/ssl/harbor.crt
  private_key: /etc/harbor/ssl/harbor.key

harbor_admin_password: Harbor@2026       # 首次安装生效；登录后立即改密并换个人账号

database:
  password: harbor_db_pass
  max_idle_conns: 100                     # 默认 50；高并发 API 调用场景调大，缓解 too many clients
  max_open_conns: 900

data_volume: /data/harbor                 # 镜像 blob、PG 数据、Trivy 缓存全在这里，必须是独立大容量盘

trivy:
  ignore_unfixed: false                   # true = 不报告无补丁 CVE，降噪但会漏报
  timeout: 5m0s

jobservice:
  max_job_workers: 10                     # 复制/GC/扫描任务的并发 worker 数，按 CPU 调
三个部署期就要定的事：① data_volume 必须是独立盘/块存储 —— 镜像 blob 动辄 TB 级，和系统盘混用迟早把系统写满；② 证书 CN 与 hostname 不一致，客户端 push 会报证书错误；③ 默认管理员是 admin，密码在配置文件里明文可见，生产必须接入 LDAP/OIDC 并禁用直接用 admin 干活。
模块 1

镜像仓库的角色与 Harbor 架构

先把"为什么需要镜像仓库"讲清楚，再看 Harbor 内部怎么分工。镜像仓库承担四个角色：

角色干什么
构建产物库CI 流水线的终点。每个可发布版本在这里有唯一、不可变的落点（tag + digest）
存储与分发按 layer 增量存储，多节点 pull 时共享 layer 缓存，是集群发布速度的地基
统一入口所有环境（测试/预发/生产）从同一处拉镜像，杜绝"我这能跑你那不能跑"
安全门禁漏洞扫描、签名校验、准入控制都挂在这里，是软件供应链安全的第一道闸

Harbor 的组件分工

组件职责关键点
nginx
(proxy)		入口反向代理，TLS 终结与路由所有客户端请求的第一跳；请求体大小默认不限制（大镜像 push 不会被 413 打断）
core核心 API：项目、成员、配额、复制规则、扫描编排业务逻辑都在这，多副本无状态，可水平扩展
registry镜像存取本体（CNCF Distribution 实现），存 manifest 与 blob它只认"引用关系"：删 tag 只是删 manifest 引用，blob 文件还在
jobservice异步任务队列：复制、GC、扫描、保留策略执行重活都在后台跑，API 不阻塞；任务失败在这里查日志
portalWeb UI 前端纯静态前端，所有操作最终都落到 core 的 REST API
database
(PostgreSQL)		元数据：项目、成员、复制规则、任务记录、审计不存镜像 blob；DB 损坏不等于镜像丢失，但元数据全丢
redisjobservice 任务队列与运行时状态丢了你正在排的任务，但不影响已存镜像
exporterPrometheus 指标暴露采集 Harbor 自身指标：API 延迟、任务队列长度等
trivy-adapter漏洞扫描适配器（2.x 起内置 Trivy）负责下载/更新 CVE 库并执行扫描；1.x 时代用的是 Clair
notary内容信任/签名服务（Notary v1，DCT）可选组件，装的时候带 --with-notary；监听 4443 端口
# 一次 docker push 在 Harbor 内部的流转：
docker push → nginx(443) → core（鉴权、配额检查、写元数据）→ registry（写 manifest + blob）
                                                          ↘ jobservice（触发扫描/复制任务）
记住这条链路，排错时按跳查：push 报 401/403 → core 的认证与权限；报 quota exceeded → 项目配额；报 5xx 或连接断 → nginx/registry；任务卡住不动 → jobservice 日志（docker compose logs -f jobservice）。
模块 2

项目、成员与 RBAC

Harbor 的权限模型是"系统角色 + 项目角色"两层。镜像的最小管理单元是项目（project），类似 GitLab 的 Group/Project 关系。

项目角色权限矩阵

角色拉取推送成员管理项目配置
访客 Guest✓✗✗✗
开发者 Developer✓✓✗✗
维护者 Maintainer✓✓✓部分（扫描、保留策略）
项目管理员 Project Admin✓✓✓全部（含删除项目）

系统级只有一个系统管理员：管所有项目、复制规则、系统级配置（扫描、CVE allowlist、GC）。项目公开性是独立开关：public 项目任何登录用户（甚至匿名）可拉取，private 项目仅成员可见。

# 创建项目（带 500GB 配额，单位字节）
curl -u "admin:Harbor@2026" -X POST "https://harbor.internal.example.com/api/v2.0/projects" \
  -H "Content-Type: application/json" \
  -d '{"project_name":"prod","metadata":{"public":"false"},"storage_limit":536870912000}'

# 给 CI 创建机器人账号（机器人账号名格式：robot$<项目>+<名称>）
curl -u "admin:Harbor@2026" -X POST "https://harbor.internal.example.com/api/v2.0/robots" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "robot$prod+ci",
    "level": "project",
    "permissions": [{"kind":"project","namespace":"prod","access":[
      {"resource":"repository","action":"push"},
      {"resource":"repository","action":"pull"}]}],
    "duration": 90
  }'
# 返回体里的 secret 只显示一次，立即存进密钥管理系统；duration 单位是天

# 用机器人账号调 API / 登录（注意 $ 在 shell 里要转义或整体加引号）
docker login harbor.internal.example.com -u 'robot$prod+ci' -p '<返回的secret>'
curl -u 'robot$prod+ci:<secret>' "https://harbor.internal.example.com/api/v2.0/projects/prod/repositories"
RBAC 实践三条：① CI/CD 一律用机器人账号，按项目授权、可过期、可单独吊销，别共用 admin；② 人的账号走 LDAP/OIDC 接入，离职即在目录服务侧失效；③ library 项目默认 public，别把敏感镜像推进去 —— 这是最常见的"以为私有其实公开"事故。
模块 3

推送、拉取与 tag 治理

# 标准四步
docker login harbor.internal.example.com
docker tag app:1.4.2 harbor.internal.example.com/prod/app:1.4.2
docker push harbor.internal.example.com/prod/app:1.4.2

# 按 digest 拉取 —— 拿到的是字节级确定的内容，不随 tag 变动
docker pull harbor.internal.example.com/prod/app@sha256:3f7b21c9e5a1...

# HTTP 部署（只有测试环境这么干）：把地址加进 Docker 的白名单
# /etc/docker/daemon.json
{"insecure-registries": ["harbor.internal.example.com"]}
systemctl restart docker

tag 治理：发布确定性的根基

实践做法与理由
语义化版本 tag推 v1.4.2 而不是 latest。latest 是"会动的指针"，回滚时你不知道它指向哪
digest 固定部署K8s/Helm 里用 image: app@sha256:...，杜绝"同 tag 不同内容"导致的不可复现发布
immutable tag 规则项目 → Policy → Tag Immutability：匹配 v* 的 tag 禁止覆盖推送。防止手滑把生产 tag 顶掉
build 号溯源tag 里带构建号（如 v1.4.2-b20261017.3），配合 label 记录 commit、流水线 ID
禁止跨环境复用 tag同一份代码构建一次，逐环境晋升同一个 digest；不要每个环境重新构建各自打 tag
tag 覆盖是最隐蔽的发布事故：tag v1.4.2 被第二次推送后，老 digest 没有 tag 指向它，但文件还在。此时：① 用 tag 部署的节点拉到的是新内容，行为不一致；② 回滚到"v1.4.2"其实回不去旧版本。解法就是上表两条：immutable tag + digest 部署。
模块 4

镜像复制：跨机房与跨云分发

复制（Replication）是 Harbor 的内置能力，把镜像从一个 registry 同步到另一个，解决"跨机房拉取慢"和"多 registry 并存"两个问题。

模式触发方式适用场景
push-based
推送模式		本地 push 成功后自动/定时推到远端主动分发：总部仓库 → 各分支/边缘节点；镜像一出炉就送出去
pull-based
拉取模式		按 cron 计划从远端拉取上游同步：Docker Hub/公司总部 → 本地仓库；离线环境的更新窗口

一条跨机房复制规则的真实配置

# POST /api/v2.0/replication/policies
{
  "name": "bj-to-sh",
  "src_registry": {"id": 1},          # 源 registry：本 Harbor 的 registry 端点
  "dest_registry": {"id": 2},         # 目标：上海机房 Harbor（或 ACR/ECR，需先配好访问凭据）
  "filters": [
    {"type": "repository", "value": "prod/**"},   # 只复制 prod 项目下的仓库
    {"type": "tag", "value": "v*,release-*"},     # 只放行版本 tag，拦住 latest 和临时 tag
    {"type": "label", "value": "ga"}              # 可选：只同步打了 ga 标签的镜像
  ],
  "trigger": {
    "type": "scheduled",
    "schedule_param": {"type": "Daily", "hour": 2, "minute": 0}   # 每天 02:00，避开发布高峰
  },
  "enabled": true
}

# 手动触发一次（不等计划）
curl -u "admin:Harbor@2026" -X POST "https://harbor/api/v2.0/replication/executions" \
  -H "Content-Type: application/json" -d '{"policy_id":1}'

# 查看执行历史与失败原因
curl -u "admin:Harbor@2026" "https://harbor/api/v2.0/replication/executions?policy_id=1"
  • 增量传输：复制按 layer 去重，已存在的 layer 不重传。首次全量 + 日常增量，带宽压力主要在首传和基础镜像大版本更新。
  • 删除传播：规则里可开"本地删除时同步删除远端资源"。不开则远端只增不减，存储会慢慢失控；开了就要接受误删会同步扩散的风险，建议关闭并按保留策略治理。
  • 跨云目标：目标为 ACR/ECR/Docker Hub 时，先在 Harbor 里注册对应 registry 端点并配好凭据；云厂商的 token 通常 12~24 小时过期，要有轮换机制，否则复制任务会在某天集体失败。
  • 一致性：复制是异步的，"源删了 tag 但任务还没跑完"的窗口里两边不一致。对发布顺序敏感的场景，以源仓库的 digest 列表为准做校验。
跨机房分发的带宽账要提前算：一个 1.2GB 的应用镜像，200 个节点首次拉取就是 240GB 流量。三条路：① 机房内预热（复制 + 节点定时拉一次）；② 基础镜像尽量小（alpine/distroless，多阶段构建）；③ 大规模集群用 P2P 分发（Dragonfly/Kraken）在节点间共享 layer，registry 带宽只是兜底。
模块 5

漏洞扫描：Trivy 与 CVE 库

Harbor 2.x 内置 Trivy（1.x 时代是 Clair）。扫描对象是镜像里的 OS 包（dpkg/apk/rpm）和语言依赖（npm/pip/maven/go mod），对照 CVE 库输出漏洞清单。

触发方式说明
push 自动扫描项目配置里打开"Scan on push"，每次推送自动扫，结果实时更新
手动扫描UI 点扫描，或 POST /projects/{p}/repositories/{r}/artifacts/{ref}/scan
定时全量扫描系统级计划任务周期重扫全部镜像 —— 因为新 CVE 每天在爆，旧镜像不动也有新漏洞
# 本地用 Trivy CLI 复现 Harbor 的扫描（CI 门禁同款）
trivy image --severity HIGH,CRITICAL harbor.internal.example.com/prod/app@sha256:3f7b...

# 作为 CI 门禁：发现 CRITICAL 直接失败（exit code 1）
trivy image --exit-code 1 --severity CRITICAL \
  harbor.internal.example.com/prod/app@sha256:3f7b...

# 只看"有补丁可修"的漏洞，过滤掉修不了的噪音
trivy image --ignore-unfixed --severity HIGH,CRITICAL ...

CVE 库的更新策略（离线环境重灾区）

  • Trivy 的漏洞库（trivy-db）默认从 GitHub 拉取，每次扫描前检查更新。内网/离线环境拉不到，扫描结果要么失败，要么停在某个旧版本 —— 表现为"新爆的 CVE 扫不出来"。
  • 离线方案：一台有外网的机器定期 trivy image --download-db-only，把库同步到内网 HTTP 服务，再通过 TRIVY_DB_REPOSITORY 环境变量指向内网地址；扫描加 --skip-db-update 用本地库。
  • Harbor 侧看 trivy-adapter 容器日志判断 DB 更新是否正常；系统配置里可配 CVE allowlist（2.5+）：对确认误报/暂不修复的 CVE 加过期时间的豁免，而不是简单忽略。
  • 扫描会占 CPU（尤其首次解压大镜像），max_job_workers 别设太大，否则扫描和复制互相排队。
门禁分级建议：CRITICAL 直接拦（有 RCE/提权的必须修）；HIGH 设豁免期（如 7 天内修不掉需负责人审批）；MEDIUM/LOW 只报告不拦截。全部一刀切拦截的结果就是大家学会改门禁 —— 门禁的信用比严格更重要。
模块 6

镜像签名与内容信任

扫描回答"镜像有没有漏洞"，签名回答"这个镜像是不是可信方产的"。Harbor 原生集成 Notary（Docker Content Trust），同时生态里 cosign 签名产物也能作为 OCI artifact 存进 Harbor。

# ===== Notary / DCT（Harbor 原生）=====
# 部署时带 --with-notary，notary 服务监听 4443
export DOCKER_CONTENT_TRUST=1
export DOCKER_CONTENT_TRUST_SERVER=https://harbor.internal.example.com:4443

docker trust sign harbor.internal.example.com/prod/app:1.4.2     # 首次会生成签名密钥
docker trust inspect --pretty harbor.internal.example.com/prod/app:1.4.2
docker trust revoke harbor.internal.example.com/prod/app:1.4.2   # 撤销签名

# ===== cosign（云原生事实标准，签名作为 OCI artifact 附加）=====
cosign generate-key-pair          # 生成 cosign.key / cosign.pub（私钥进 KMS）
cosign sign --key cosign.key \
  harbor.internal.example.com/prod/app@sha256:3f7b21c9e5a1...
cosign verify --key cosign.pub \
  harbor.internal.example.com/prod/app@sha256:3f7b21c9e5a1...

# keyless 模式（CI 里推荐）：OIDC 身份换 Fulcio 短期证书，签名写入 Rekor 透明日志
cosign sign harbor.internal.example.com/prod/app@sha256:3f7b21c9e5a1...
cosign verify harbor.internal.example.com/prod/app@sha256:3f7b21c9e5a1... \
  --certificate-identity-regexp='.*@example\.com' --certificate-oidc-issuer=https://accounts.google.com
方案密钥形态适用
Notary (DCT)本地密钥对，托管在 Harbor Notary 服务Docker 客户端生态，简单场景
cosign + KMS私钥存云 KMS/HSM，不落开发机发布平台集中签名，团队规模化管理
cosign keyless无长期私钥，OIDC + 短期证书 + Rekor 日志GitHub Actions/GitLab CI 等 SaaS 流水线
签名的价值在"验证端"：光签不用等于没签。在 Kubernetes 侧配准入控制（Kyverno 的 verifyImages 或 Ratify），只允许带有效签名的镜像落地，签名门禁才算闭环。私钥管理是签名体系的阿喀琉斯之踵 —— 私钥进 KMS/HSM，多人授权使用，单人不具备完整签名能力。
模块 7

GC、保留策略、配额与横向对比

存储治理三件套：保留策略决定删哪些 tag，GC负责回收 blob，配额限制单个项目的天花板。

GC 的真实工作流程

删 tag：registry 删除 manifest 与 tag 的引用关系，blob 文件原样留在磁盘上。这是"删了 tag 空间不降"的第一层原因。
执行 GC：jobservice 清理已无引用的 manifest 记录，再调用 registry 的 garbage-collect 子命令，删除引用计数为 0的 blob 文件。
确认释放：共享 layer（基础镜像层被几十个镜像共用）只有全部 manifest 都不引用后才真正删除 —— 这是"跑了 GC 空间也不动"的常见原因。
# 配置 GC 计划（每天 04:00，1 个 worker）
curl -u "admin:Harbor@2026" -X PUT "https://harbor/api/v2.0/system/gc/schedule" \
  -H "Content-Type: application/json" \
  -d '{"schedule":{"type":"Daily","hour":4},"parameters":{"delete_untagged":false,"workers":1}}'

# 立即执行一次 + 查看历史
curl -u "admin:Harbor@2026" -X POST "https://harbor/api/v2.0/system/gc"
curl -u "admin:Harbor@2026" "https://harbor/api/v2.0/system/gc"

# 空间没降时的排查：看 layer 还被谁引用
curl -u "admin:Harbor@2026" "https://harbor/api/v2.0/projects/prod/repositories/app/artifacts?with_tag=true&page_size=100"

保留策略：让 tag 数量有上限

# 项目级保留策略：保留最近推送的 10 个 + 最近 30 天的 + 永远保留的
curl -u "admin:Harbor@2026" -X POST "https://harbor/api/v2.0/projects/prod/retentions" \
  -H "Content-Type: application/json" \
  -d '{
    "algorithm": "or",
    "rules": [
      {"disabled":false,"action":"retain","template":"latestPushedN","params":{"latestPushedN":10}},
      {"disabled":false,"action":"retain","template":"nDaysSinceLastPush","params":{"nDaysSinceLastPush":30}},
      {"disabled":false,"action":"retain","template":"always","params":{}}
    ],
    "trigger": {"kind":"Schedule","settings":{"cron":"0 0 3 * * *"}}
  }'

三方仓库对比

维度Harbor（自建）Docker Hub云厂商 ACR 等
匿名拉取限流无（自己说了算）100 次/6 小时，登录免费用户 200 次/6 小时按流量计费，一般不限次数

模块 8

十个线上坑

1
删了 tag 就以为磁盘空间会释放
删除只解除 manifest 引用，blob 文件原样还在；且被其他 tag 共享的 layer 不计入"可回收"。必须执行 GC，并确认没有 immutable tag / 保留策略仍在引用。
2
GC 跑完 df 数值就是不降
三种常见原因：layer 仍被其他 manifest 引用（引用计数没归零）；删除的文件仍被进程持有句柄（lsof 查 registry/trivy 容器）；底层是 overlayfs/快照型存储，删除的是上层而数据在下层。data_volume 用独立块存储可绕开第三类。
3
单个 layer 1GB+ 的巨型镜像
拉取慢、CI 节点缓存命中率低、每改一行代码也要重传一大层。解法：多阶段构建、按变动频率排序 Dockerfile 指令（不变的放前面）、基础镜像换 distroless/alpine、.dockerignore 排除无用文件。
4
用 latest 且允许覆盖 tag
部署拉到的内容不可复现，回滚时"回不去旧版本"。用语义化版本 tag + digest 固定部署，并开启 immutable tag 规则禁止 v* 被覆盖。
5
不配保留策略，tag 无限堆积
CI 每次构建都推 tag，一年攒几千个 tag，存储只增不减。项目级配 retention（最近 N 个 + 最近 N 天），并加定时任务执行。
6
以为配额管住了磁盘
项目配额只约束单项目维度，全局磁盘水位没人盯照样写满。配额之外必须对 data_volume 做容量监控 + 告警（80% 预警），并规划扩容/清理流程。
7
离线环境 Trivy CVE 库不更新
内网拉不到漏洞库，扫描结果停在旧版或全 unknown，形成"扫过=安全"的错觉。配内网 DB mirror + 定期下载，监控 trivy-adapter 的 DB 更新时间，别用 --skip-db-update 一直跑旧库。
8
CI 用 admin 账号登录 Harbor
权限过大、无有效期、无法按项目审计和单独吊销。给每条流水线建项目级机器人账号，设有效期，泄漏了单独 revoke 不影响其他流水线。
9
HTTP 部署忘配 insecure-registries
docker push 报 "http: server gave HTTP response to HTTPS client"。要么配 daemon.json 白名单（仅限内网测试），要么正经上 HTTPS 证书。生产出现这个错误说明有人在绕过安全基线。
10
复制规则不过滤 tag，全量同步
把 latest、临时 tag、失败构建的镜像也复制到异地，带宽爆炸且污染目标环境。filters 限定 repository + tag 模式，源端 tag 治理先做好，复制才有意义。
自测

六道题

1. Harbor 中 registry 组件的核心职责是？
正确答案：直接存取 manifest 与 blob。项目管理是 core 的职责，异步任务是 jobservice 的职责，权限入口是 nginx + core。理解分工才能按跳排错：push 报错先看 nginx/core，任务不动看 jobservice。
2. 删除镜像 tag 后磁盘空间没有变化，正确处理是？
正确答案：执行 GC 并确认引用关系。删 tag 只是解除 manifest 引用；blob 要等 GC 清理且引用计数归零后才真正删除。手动删文件会让 registry 元数据与存储不一致，是更严重的事故。
3. Docker Hub 匿名用户的拉取限制大约是？
正确答案：100 次/6 小时，按 IP 计。登录的免费用户是 200 次/6 小时。多集群共享 NAT 出口 IP 时很容易打满，所以基础镜像和业务镜像必须内网化，用 Harbor pull-based 复制 Docker Hub 官方镜像。
4. 防止生产镜像 tag 被同名推送覆盖，最有效的组合是？
正确答案：immutable tag 规则 + digest 部署。规则在服务端拒绝覆盖匹配模式的 tag，digest 让部署引用字节级确定的内容。两者结合才能既防手滑又防"同 tag 不同内容"。
5. 把总部的镜像分发到多个异地机房，最合适的机制是？
正确答案：Harbor 复制规则。复制按 layer 去重增量传输，带过滤器和计划触发，可审计可重试。手工 save/load 无法规模化；机房直连总部则每次发布都走跨区链路，发布速度被带宽绑架。
6. 内网隔离环境做镜像漏洞扫描，CVE 库的正确策略是？
正确答案：内网 mirror + 定期同步 + 监控。新 CVE 每天都在爆，旧库扫新漏洞等于没扫。--skip-db-update 配合一个永远不更新的库是最危险的组合：报告一片绿色，实际全是漏报。"内网无风险"也是错误假设，供应链和内部威胁都在射程内。

术语表

术语一句话解释
Registry镜像存取服务本体，只管 manifest 与 blob 的存储和引用关系
Project 项目Harbor 的镜像管理与 RBAC 单元，public/private 决定匿名可见性
Robot Account给 CI 用的项目级账号，格式 robot$项目+名称，可设有效期
Manifest镜像的"清单文件"：记录 layer 列表、digest、平台信息
Blob镜像的 layer 数据本体，多个镜像共享同一 blob 只存一份
Digest内容的 SHA256 摘要，镜像的字节级唯一 ID
Tag指向 digest 的可变指针，覆盖推送后指向就变了
Immutable Tag项目级规则：匹配模式的 tag 禁止覆盖推送
Replication 复制跨 registry 同步镜像，push-based 主动推、pull-based 计划拉
Retention 保留策略按"最近 N 个/最近 N 天/永远保留"规则自动清理 tag
GC垃圾回收：删除引用计数为 0 的 blob 文件，真正释放磁盘
Quota 配额项目级存储上限（字节），超限拒绝推送
TrivyHarbor 2.x 内置的漏洞扫描引擎，对照 CVE 库扫 OS 包与语言依赖
CVE公开漏洞编号库，Trivy 的漏洞库需定期更新
Notary / DCTDocker Content Trust 的签名体系，Harbor 原生集成
cosign云原生镜像签名工具，签名作为 OCI artifact 存储，支持 keyless
SBOM软件物料清单，记录镜像里所有组件及版本，漏洞响应时定位受影响面
镜像晋升同一 digest 从测试环境逐级晋升到生产，不在各环境重复构建
限流Docker Hub 按 IP 的拉取配额，匿名 100 次/6 小时
P2P 分发节点间共享 layer 的分发方式（Dragonfly 等），降低 registry 带宽压力
下一步怎么练：起一个 Harbor，完成这五件事 —— ① 建 prod 项目 + 机器人账号，用 CI 脚本推一个带语义化 tag 的镜像；② 配 immutable tag 规则，然后试着覆盖推送，看它被拒；③ 配一条 pull-based 复制规则同步 Docker Hub 官方 nginx，带 tag 过滤器；④ 删掉镜像 tag，跑 GC，用 du -sh /data/harbor 前后对比，并构造一个共享 layer 场景验证"引用不归零不释放"；⑤ 开 push 自动扫描，用 trivy CLI 复现结果并对一次 CRITICAL 漏洞做豁免。
