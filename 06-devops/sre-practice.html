二十分钟学透 SRE 工程实践

SRE 不是"高级运维"，是用软件工程方法解决稳定性问题。这篇的重点：SLI/SLO/SLA 怎么落地、错误预算怎么算、多窗口多燃率告警规则怎么写、Toil 怎么消灭、postmortem 怎么开。

开始前

先建立一个坐标系

SRE 一词出自 Google（《SRE：Google运维解密》），一句话定义："当你要求一个软件工程师去设计一个运维团队时，你会得到 SRE。"核心主张：运维问题的 70% 是工程问题，应该用写代码的方式解决，而不是堆人。

维度传统运维SRE
核心动作人肉值守、手工操作、救火写自动化代码、定 SLO、做容量与发布工程
对故障的态度故障是失败，要追责、要杜绝故障是常态，用错误预算管理"可以失败多少"
度量方式看 CPU、内存、在线时长（活动指标）看 SLI/SLO、错误预算、MTTD/MTTR（结果指标）
变更方式变更窗口、人工审批、能不动就不动小步快跑、自动化发布、用渐进式交付控制爆炸半径
时间分配80% 手工劳动 + 20% 改进最多 50% Toil，至少 50% 工程时间
规模逻辑人随服务数量线性增长用自动化让团队规模随服务数量亚线性增长
DevOps 和 SRE 的关系：DevOps 是一场文化运动（打破开发与运维的墙，没有标准答案）；SRE 是 Google 对 DevOps 理念的一种具体工程实现——SRE Workbook 原话：DevOps 是"class"，SRE 是"class 的一个具体实例"，它有可落地的规范（SLO、错误预算、Toil 上限）。
模块 1

SLI / SLO / SLA：可靠性三角

整个 SRE 体系的地基。三者的区别一句话：SLI 是"怎么量"，SLO 是"目标定多少"，SLA 是"违约了怎么办"。

概念定义例子
SLI
指标		服务可靠性的精细量化度量，通常是一个比值：好的事件数 / 总事件数HTTP 请求成功率、P99 延迟 < 300ms 的请求占比、数据新鲜度
SLO
目标		SLI 在某个时间窗口内的目标值，是内部承诺过去 30 天，API 成功率 ≥ 99.9%
SLA
协议		对外的合同承诺，达不到就赔钱。通常比 SLO 更宽松月度可用性 99.5%，未达标赔偿 10% 费用

怎么定义一条好 SLI

  • 用比率，不用绝对值。"99.9% 的请求成功"比"每分钟错误少于 100 个"更抗流量波动
  • 贴近用户感知。用户请求级指标（成功率、延迟分位数）优先于系统指标（CPU、磁盘）
  • 能算出来。SLI 必须能从监控数据直接算出，依赖现成的埋点，不能靠人工统计
  • 宁少勿多。一个服务 3~5 条核心 SLI 足够（可用性、延迟、吞吐、新鲜度），多了等于没有重点

真实 SLO 表（一个典型的 API 服务）

SLI口径SLO
请求成功率非 5xx 且非超时的请求 / 总请求30 天滚动 ≥ 99.9%
延迟达标率P99 延迟 < 300ms 的请求占比30 天滚动 ≥ 99%
数据新鲜度写入到可读的延迟 < 5s 的比例30 天滚动 ≥ 99.95%
SLO 不是越高越好。SRE 的核心理念是 "just reliable enough"（可靠得刚刚好）：定 99.999% 意味着 30 天只允许 25.9 秒故障，任何小抖动都会烧光预算，团队会被禁掉一切发布 —— 最后系统不是更可靠，而是更僵化、更不敢动。SLO 是产品决策，不是技术人员的虚荣心。
模块 2

错误预算：把可靠性变成可以花的钱

错误预算 = (1 − SLO) × 时间窗口。它的革命性在于：把"稳定性 vs 迭代速度"的扯皮，变成一个可以量化、可以分配、可以烧完再说的数字。

预算速算表（30 天窗口）

SLO允许不可用比例30 天错误预算
99.9%（三个九）0.1%43.2 分钟（720h × 0.001）
99.95%0.05%21.6 分钟
99.99%（四个九）0.01%4.32 分钟
99.999%0.001%25.9 秒

预算花超了怎么办（错误预算政策）

# 一条可以写进团队 Wiki 的错误预算政策
预算剩余 > 0        → 正常发布新功能
预算消耗 > 50%      → 所有发布必须过可靠性评审（灰度 + 回滚预案）
预算耗尽（SLO 已破） → 冻结功能发布，全员转入稳定性工作，
                       直到滚动窗口内 SLO 重新达标
错误预算的真正威力：它给了你一个停止发布、理直气壮拒绝需求的依据。以前"稳定性 vs 业务"靠嗓门大小，现在靠数字说话：预算烧完了，就是不许发。Google 的经验：这个机制让 SRE 和产品团队从对立变成协作，因为双方看同一个仪表盘。
一个常见误读：错误预算 ≠ "可以随便挂 43 分钟"。它是已消耗故障时间的滚动统计，窗口一直在滚动，旧故障的影响会随时间淡出。所以一次大事故的代价，取决于它发生后你还惹不惹事。
模块 3

多窗口多燃率告警（SRE Workbook 标准方案）

"CPU 超过 80% 告警"是活动指标告警，最大的问题是要么漏报要么狼来了。SRE Workbook 的答案是：基于 SLO 的多窗口、多燃率（Multiwindow Multi-Burn-Rate）告警。

燃率（Burn Rate）

燃率 = 实际错误率 ÷ SLO 允许的错误率

例：SLO = 99.9%（允许错误率 0.1%）
    当前 1 小时错误率 = 1.4%
    燃率 = 1.4% / 0.1% = 14.4  → 1 小时烧掉 30 天预算的 2%
    按这个速度，30 天预算 2 天就烧光

标准三级告警表（30 天 SLO）

级别长窗口短窗口燃率含义与动作
Page1 小时5 分钟14.4×1 小时烧掉 2% 预算，约 2 天耗尽 → 立即叫人
Page6 小时30 分钟6×6 小时烧掉 5% 预算，约 5 天耗尽 → 立即叫人
Ticket3 天6 小时1×3 天烧掉 10% 预算 → 开工单，工作时间处理

为什么必须两个窗口

  • 只有短窗口（5 分钟）：一次流量尖刺误报，短信疲劳，很快没人看告警
  • 只有长窗口（1 小时）：真实故障被平均掉，等触发时已经烧掉大量预算
  • 两个窗口都触发才告警：短窗口保证"现在正在坏"，长窗口保证"不是偶发尖刺"，误报和漏报同时下降

可直接用的 Prometheus 规则（SLO = 99.9%）

# prometheus-rules.yaml —— 以 http_requests_total 为例
groups:
- name: slo-availability-burn
  rules:
  # 14.4x：1h 窗口 + 5min 窗口，烧 2% 预算 → page
  - alert: ErrorBudgetBurn_14.4x
    expr: |
      (
        sum by (service) (
          rate(http_requests_total{code=~"5.."}[1h])
        ) / sum by (service) (
          rate(http_requests_total[1h])
        )
        > 14.4 * 0.001
      )
      and
      (
        sum by (service) (
          rate(http_requests_total{code=~"5.."}[5m])
        ) / sum by (service) (
          rate(http_requests_total[5m])
        )
        > 14.4 * 0.001
      )
    labels: {severity: page}
    annotations:
      summary: "{{ $labels.service }} 错误预算以 14.4 倍速燃烧"

  # 6x：6h 窗口 + 30min 窗口，烧 5% 预算 → page
  - alert: ErrorBudgetBurn_6x
    expr: |
      (
        sum by (service) (
          rate(http_requests_total{code=~"5.."}[6h])
        ) / sum by (service) (
          rate(http_requests_total[6h])
        )
        > 6 * 0.001
      )
      and
      (
        sum by (service) (
          rate(http_requests_total{code=~"5.."}[30m])
        ) / sum by (service) (
          rate(http_requests_total[30m])
        )
        > 6 * 0.001
      )
    labels: {severity: page}
    annotations:
      summary: "{{ $labels.service }} 错误预算以 6 倍速燃烧"

  # 1x：3d 窗口 + 6h 窗口，烧 10% 预算 → ticket
  - alert: ErrorBudgetBurn_1x
    expr: |
      (
        sum by (service) (
          rate(http_requests_total{code=~"5.."}[3d])
        ) / sum by (service) (
          rate(http_requests_total[3d])
        )
        > 0.001
      )
      and
      (
        sum by (service) (
          rate(http_requests_total{code=~"5.."}[6h])
        ) / sum by (service) (
          rate(http_requests_total[6h])
        )
        > 0.001
      )
    labels: {severity: ticket}
    annotations:
      summary: "{{ $labels.service }} 错误预算以 1 倍速燃烧"
数字怎么来的：30 天 = 720 小时预算。14.4 倍燃率意味着每小时消耗 14.4/720 = 2% 的预算；6 倍燃率下 6 小时消耗 36/720 = 5%；1 倍燃率下 72 小时（3 天）消耗 72/720 = 10%。换 SLO 只需改阈值里的 0.001（99.9% 的允许错误率）。
模块 4

Toil：识别它，然后消灭它

SRE 书对 Toil 的定义：与服务直接相关的、手工的、重复的、可自动化的、战术性的、没有持久价值的、并且随服务规模线性增长的工作。

Toil 特征反例（这不是 toil）
手工：人敲命令、人点页面设计一套自动化发布系统（这是工程项目）
重复：同样的事每周都在做一次性的架构迁移方案设计
可自动化：脚本能替人干创造性排障、新型事故的根因分析
没持久价值：干完系统没变好沉淀 runbook、改进监控覆盖
O(n) 增长：服务多一倍，活多一倍写一次代码，全集群生效的控制器

典型 Toil 清单

手工扩容
每次大促前手动改副本数 → 应做成 HPA + 定时策略
手工发版
登录机器 git pull + 重启 → CI/CD 一条命令
人肉巡检
每天截图 10 个监控面板 → 告警规则 + SLO 面板
反复配证书
手抄 Nginx 配置 → ACME 自动续期
50% 上限原则：SRE 团队花在 Toil 上的时间不得超过 50%。超过的后果：人永远在救火，永远没时间做自动化，Toil 越滚越大，团队倦怠离职。落地做法：连续两周记录时间账（每 30 分钟记一次干了什么），然后按"ROI 排序"消灭：优先自动化每周耗时 > 2 小时且规则明确的活。

消灭 Toil 的三板斧

  1. 自动化：能写成脚本的绝不做第二遍（注意：先写 runbook，跑顺了再自动化，别跳过第二步）
  2. 自助服务：把能力做成平台/API，让研发自己点按钮，而不是提工单给你
  3. 向上管理（push back）：对"每周让我干一次同样的事"的需求说不，或把它排进产品化路线
模块 5

On-Call 轮值与应急响应

On-call 是 SRE 的最后一道防线，设计目标是：该醒的时候醒，不该醒的时候别醒。

Google 的 on-call 设计准则

准则数字与理由
每班最多 2 起事故每起事故平均耗时按 25% 班次估算，2 起就是 50% 时间在救火，超过就没法学习和改进
On-call 占总时间 ≤ 25%剩下 75% 要留给工程项目，否则团队退化成运维组
主备双人制主值班（primary）负责响应，副值班（secondary）兜底升级，避免单点失联
新人有"跟随期"先当 3~6 个月 secondary，跟过至少一次完整事故才转 primary
每条告警必须可行动看到告警不需要做任何事的告警 = 噪声，直接删。标准："这需要人类智能介入吗？"

事故响应（Incident Response）流程

发现（Detect）：告警触发 → 值班人 5 分钟内响应（ack）。MTTD（平均检测时间）是核心指标
止损（Mitigate）：先恢复，后定位。回滚、切流量、降级、扩容，先把火扑灭，不要在现场读代码
指挥（Command）：大事故指定 Incident Commander（IC），只负责协调和决策，不亲自敲命令 沟通（Communicate）：每 30 分钟向干系人同步一次状态，哪怕结论是"还在查" 恢复（Recover）：确认 SLI 恢复达标，宣布事故结束，记录时间线 复盘（Learn）：48 小时内出 postmortem 草稿，行动项进 backlog
止损阶段最常见的错误：值班人在现场 debug 找根因，忘了止损。正确顺序永远是：止损 > 定位 > 根治。回滚慢 5 分钟，可能就是预算多烧 5 分钟。
模块 6

事后复盘：Blameless Postmortem

Google 的核心原则：对事不对人（blameless）。追责的团队会隐瞒事故、粉饰时间线，最后复盘变成形式主义。前 Google SRE 总监的说法："如果因为一次失误就开除人，那没人会再告诉你真相。"

Postmortem 模板（可直接抄）

# ===== 元数据 =====
事故编号:    INC-2026-0312-01
日期:        2026-03-12
作者:        值班工程师 A、B
状态:        草稿 / 评审中 / 已完成
影响时长:    47 分钟（14:02 - 14:49 UTC）

# ===== 影响 =====
影响范围:    支付成功率从 99.95% 跌至 91.2%
受影响用户:  约 3.1 万用户看到支付失败
收入影响:    约 ¥18.6 万交易失败
SLO 消耗:    3 天预算的 68%（1x 燃率下 6.8 倍）

# ===== 时间线（全部用 UTC）=====
14:02  告警 ErrorBudgetBurn_6x 触发，值班 ack
14:09  定位到 payment-api 5xx 突增，误以为是 DB 慢查询
14:21  发现是新版本 v2.17.0 引入的连接池配置错误
14:23  执行回滚到 v2.16.2
14:31  5xx 开始下降
14:49  SLI 恢复达标，事故结束

# ===== 根因分析（5 Whys）=====
1. 为什么支付失败？payment-api 连接池耗尽
2. 为什么连接池耗尽？新版本把 pool-size 从 50 改成了 5
3. 为什么没被发现？配置变更没走灰度，直接全量
4. 为什么没走灰度？该服务的发布流程被标记为"低风险"免检
5. 为什么免检？风险分级规则只看改动行数，不看配置项

# ===== 检测与响应评估 =====
MTTD: 2 分钟（告警及时）    MTTR: 47 分钟（定位绕了远路）
做得好的:  双人值班、回滚 2 分钟内完成
做得差的:  初期误判方向浪费 12 分钟、无 DB 连接池面板
运气成分:  事故发生在白天，夜间可能 MTTR 翻倍

# ===== 行动项（没有 owner 和 deadline 的行动项等于没有）=====
[P0] 发布流程风险分级加入"配置文件变更"类别 —— 负责人 A —— 03-20
[P0] payment-api 补充连接池使用率面板 —— 负责人 B —— 03-18
[P1] runbook 补充连接池耗尽排查手册 —— 负责人 C —— 03-25
[P2] 回滚后自动触发 5xx 对比看板 —— 负责人 B —— 04-10
复盘的质量标准：行动项全部是可执行的工程改进（加监控、改流程、补自动化），而不是"加强意识""提高重视"这类空话。Google 的经验值是：一次重大事故应该产出 3~5 个行动项，其中至少 1 个 P0。
模块 7

容量管理：别让系统饿死

容量管理的目标：保证容量始终跟得上需求，且成本不失控。核心公式只有一个：

所需容量 = 预测峰值需求 × (1 + 缓冲系数)

缓冲系数参考：
  常规服务        +30%
  核心支付/登录   +50%（峰值不可预测）
  已做过全链路压测 +20%

容量规划四步法

步骤做法工具/指标
1. 需求预测用历史数据做趋势 + 季节性预测（大促、早晚高峰）Prometheus + predict_linear()、业务侧排期
2. 压力测试找到单机极限 QPS / 并发上限，得出单机容量压测平台，记录拐点而非打挂为止
3. 配冗余N+1 起步（一台故障不雪崩），核心服务 N+2多可用区部署，反亲和打散
4. 持续验证容量水位超 60% 预警，超 80% 触发扩容评审容量看板 + 定期巡检自动化

容量水位看板（PromQL 示例）

# CPU 水位：过去 7 天 P95 值，避免被尖刺骗到
quantile_over_time(0.95,
  rate(container_cpu_usage_seconds_total[7d])
)[7d:5m]

# 单机极限：压测记录的 max_qps = 5000，当前峰值 1800
# 水位 = 1800 / 5000 = 36% → 健康；若 > 60% 预警，> 80% 必须扩容
最常见的容量错误：按平均值规划。按日均 QPS 买机器，大促当天直接雪崩。永远按预测峰值规划，并且留 N+1：任何一台机器挂掉，剩余机器要能扛住峰值流量。
模块 8

发布工程：让发布变得无聊

SRE Workbook 的发布理念：发布应该是无聊的（boring）——高频、小步、自动、可回滚。发布越频繁，每次变更越小，事故率越低。

渐进式发布（Progressive Delivery）阶段表

阶段流量比例观察时长通过条件
内部测试0%（内部账号）1 天功能正确、无新告警
金丝雀1%2~4 小时错误率、延迟与基线无显著差异
小流量10%1 天SLO 燃率无异常，业务指标正常
半量50%1 天同上
全量100%-保留回滚通道 24 小时

发布自动化三件套

# 1. 金丝雀分析（示例：Argo Rollouts / Flagger 的判定逻辑）
分析模板:
  指标:        error_rate, p99_latency
  基线:        稳定版过去 1 小时 P50
  通过条件:    error_rate < 基线 × 1.2 且 p99 < 基线 × 1.5
  失败动作:    自动回滚 + 通知值班

# 2. 特性开关（Feature Flag）：发布与解耦
代码合并 = 功能上线（默认关闭）
灰度 1% → 10% → 100% = 逐步开 flag
出问题 = 秒级关 flag，无需回滚代码

# 3. 自动回滚条件（示例）
IF 新版 5xx 率 > 1% 持续 5 分钟
OR SLO 燃率 > 6x 持续 30 分钟
THEN 自动回滚到上一版本
发布检查单（每次发布前过一遍）：① 有回滚方案且演练过；② 有监控覆盖新功能；③ 变更半径可控（配置、代码、数据库分开发布）；④ 数据库变更必须兼容旧版本（先加列后删列）；⑤ 发布时间避开业务高峰。
反模式：月度发布窗口。一个月发一次，每次几百个变更捆在一起，出问题无法定位是哪个变更，只能整体回滚。正确的做法是持续发布：小而频繁的变更，每次爆炸半径只有一个功能。

Google SRE Workbook 方法论落地清单

SRE Workbook 不是理论书，是一套"该怎么做"的清单。按投入产出排序的落地顺序：

优先级行动落地标准
P0定义核心 SLI每个服务 3~5 条，能从现有监控直接算出
P0设定 SLO 并公开全员可见的仪表盘，业务方签字认可
P0错误预算政策预算耗尽 = 冻结发布，写进团队规范
P1燃率告警替换阈值告警page 类告警 100% 走多窗口多燃率
P1Toil 记账团队 Toil 占比 < 50%，有月度数字
P1事故响应机制IC 角色、升级路径、沟通节奏演练过一次
P2Blameless postmortem每次事故 48h 内出稿，行动项有 owner
P2容量水位看板所有服务 > 80% 水位自动告警
P2渐进式发布发布 = 自动金丝雀 + 自动回滚，无需人工盯
一句话总结整篇：SRE 的全部技术，就是把"系统稳不稳"这个感性问题，变成 SLI/SLO/错误预算三个数字，然后用工程手段（自动化、渐进式发布、容量规划）去管理这三个数字。
模块 9

十个工程坑

1
SLO 拍脑袋定成 99.99% 或 100%
30 天只允许 4.32 分钟故障，一次小抖动就烧光预算，团队被永久禁发，最后系统僵化。SLO 是产品决策，要按"用户能容忍多少"倒推。
2
告警只看 CPU/内存/磁盘阈值
活动指标和用户体验脱节：CPU 90% 用户可能无感，错误率 5% 天塌了。核心告警必须绑 SLI/错误预算。
3
用单窗口短时间做燃率告警
5 分钟窗口遇到流量尖刺就误报，短信疲劳两周后没人看告警。必须长窗口 + 短窗口双条件。
4
错误预算烧穿了还继续发新功能
预算是零和的：不冻结发布，稳定性永远让位于迭代。预算政策要有牙齿，烧穿就停。
5
on-call 告警一天几十条，90% 不需要动作
每条 page 都该问一句"这需要人类智能介入吗？"。不需要的降级为 ticket 或直接删。
6
postmortem 追责到人，点名批评
下次没人敢写真相，时间线全是粉饰。Blameless 是复盘的命根子：假设每个人都基于当时的信息做了合理决策。
7
行动项写成"加强监控意识"且没有 owner
没有负责人和 deadline 的行动项 = 不存在。每条行动项必须有 P0/P1/P2、负责人、截止日期。
8
容量按日均流量规划，不留峰值缓冲
大促/早高峰直接雪崩。按预测峰值 × (1+30%~50%) 规划，且任何一台挂掉不能雪崩（N+1）。
9
Toil 不记账，以为"没多少"
实际一记账发现 80% 时间在手工劳动。连续两周记时间账，把 Toil 占比压到 50% 以下。
10
回滚靠人工操作，没有演练过
真故障时找不到人、不会操作、不敢操作。回滚必须是自动化的，且每月演练一次。
自测

六道题

1. 某服务 SLO 定为 99.9%（30 天滚动窗口），它的月度错误预算是多少？
正确答案：43.2 分钟。30 天 = 720 小时，720 × 0.1% = 0.72 小时 = 43.2 分钟。99.99% 才是 4.32 分钟，99.999% 只有 25.9 秒。
2. "14.4 倍燃率"告警的含义是？
正确答案：1 小时烧掉 2% 预算。30 天 = 720 小时，14.4/720 = 2%/小时。这是 SRE Workbook 里 page 级告警的核心档位，通常配 1h 长窗口 + 5min 短窗口。
3. 多窗口多燃率告警为什么要同时要求长窗口和短窗口都触发？
正确答案：兼顾当下与持续性。只有短窗口：流量尖刺就误报，告警疲劳。只有长窗口：故障被平均掉，触发时预算已烧光。双窗口是工程上的折中最优解。
4. 下列哪项不属于 Toil？
正确答案：设计自动扩容控制器。Toil 的判定标准：手工、重复、可自动化、无持久价值、O(n) 增长。设计控制器是工程项目，做完后 Toil 归零，这正是 SRE 该花 50% 以上时间做的事。
5. Google 对 on-call 班次负载的推荐上限是？
正确答案：每班最多 2 起事故、占比 ≤ 25%。按每起事故耗掉 25% 班次估算，2 起就是 50% 时间救火，人就废了。超限的解法是加人轮换或先做稳定性项目。
6. Blameless postmortem 的核心原则是？
正确答案：对事不对人。追责会让大家隐瞒事故、粉饰时间线，复盘失去意义。但注意 blameless ≠ 不追责：蓄意违规、能力缺失仍要单独处理。复盘产出的是可执行行动项（有 owner 有 deadline），不是检讨书。
