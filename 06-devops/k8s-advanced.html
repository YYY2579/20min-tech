模块 1

调度器深入：从“能调度”到“调度得对”

kube-scheduler 只做一件事：给每个待调度 Pod 挑一个节点。整个过程是流水线 + 插件，理解扩展点就理解了所有亲和性、污点、拓扑规则的落点。

调度框架的 10 个扩展点

扩展点时机代表插件与作用
QueueSort进入队列时排序PrioritySort按优先级从高到低出队
PreFilter过滤前预处理NodeResourcesFit / NodeAffinity / PodTopologySpread预计算，把 Pod 需求解析成可快速匹配的形式
Filter逐节点淘汰NodeResourcesFit / TaintToleration / NodePorts / VolumeBinding资源够不够、污点忍没忍、端口冲不冲突、PV 能不能绑。返回 false 就淘汰该节点
PostFilter全被淘汰后DefaultPreemption没有可行节点时触发抢占（见模块 2）
PreScore / Score给存活节点打分NodeResourcesFit / ImageLocality / PodTopologySpread每个插件打 0-100，加权求和选最高。分低不淘汰，只是不优选
Reserve选定后、绑定前VolumeBinding预留资源（如先创建 PV 绑定）。失败走 Unreserve 回滚
Permit绑定前审批Gang scheduling 类插件预占并等待同组其他 Pod 一起绑定
PreBind / Bind最终绑定DefaultBinder写 pod.spec.nodeName，Pod 脱离 Pending
记住这条主线就够了：PreFilter 算需求 → Filter 做减法（硬性） → Score 做排序（软性） → Bind 落笔。所有“调度不上去”的报错，都来自 Filter 阶段某个插件在事件里留的一句话。

三类调度约束的真实 YAML

# ===== NodeAffinity：把 Pod 钉到一类节点上 =====
nodeSelector:          # 最简单形式，等价于 requiredDuringScheduling
  disktype: ssd
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:  # 硬约束：不满足就 Pending
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/arch
              operator: In
              values: ["amd64", "arm64"]
    preferredDuringSchedulingIgnoredDuringExecution:   # 软约束：尽量，不满足也能调度
      - weight: 80
        preference:
          matchExpressions:
            - key: zone
              operator: In
              values: ["cn-north-1a"]

# 操作符：In / NotIn / Exists / DoesNotExist / Gt / Lt
# key 以 kubernetes.io/ 开头的是“众所周知”的标签，有格式校验，别乱造
# ===== Pod 间亲和 / 反亲和：让相关 Pod 聚或散 =====
affinity:
  podAffinity:              # 亲和：和 cache Pod 放一起，走本地回源
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app: cache
        topologyKey: kubernetes.io/hostname   # 在“同一台主机”范围内满足
  podAntiAffinity:         # 反亲和：同应用的副本不要挤在一台机器
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app: web
          topologyKey: kubernetes.io/hostname
# topologyKey 决定“范围”：hostname=同一节点，zone=同一可用区
# required 级 podAntiAffinity 会让副本数 > 节点数时直接 Pending，慎用
# ===== Taint / Toleration：节点“闲人免进”，Pod 凭证入场 =====
# 给专用节点组打污点（控制面、GPU 节点通常已自带）
kubectl taint nodes gpu-node-1 accelerator=nvidia:NoSchedule

# Pod 带容忍凭证才能调度上去
tolerations:
  - key: "accelerator"
    operator: Equal
    value: "nvidia"
    effect: NoSchedule
  - key: "node.kubernetes.io/not-ready"   # 节点故障时还能撑 300s
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 300
NoSchedulePreferNoScheduleNoExecute
新 Pod 不调度上来（已运行的不动）尽量不调度，没别的节点时也会来已运行的 Pod 也被驱逐（除非带 tolerationSeconds 宽限）

PodTopologySpread：均匀打散的现代解法

比 required podAntiAffinity 更细粒度：它约束的是“数量差”而不是“不能同节点”。

topologySpreadConstraints:
  - maxSkew: 1                          # 任意两个拓扑域内 Pod 数之差 ≤ 1
    topologyKey: topology.kubernetes.io/zone   # 按可用区打散；用 hostname 则按节点打散
    whenUnsatisfiable: DoNotSchedule      # 硬约束；ScheduleAnyway 是软约束
    labelSelector:
      matchLabels:
        app: web
    minDomains: 3                       # 较新版本支持
打散的隐藏前提：topologySpreadConstraints 只统计与当前 Pod selector 匹配且同 namespace 的 Pod。Deployment 扩到 3 副本、集群只有 2 个可用区时，第 3 个副本会一直 Pending，事件里写 doesn't satisfy spread constraint。节点扩起来之前，先改成 ScheduleAnyway 更稳妥。
排布决策速查：单 AZ 小集群 → 什么都不用配；多 AZ 有状态服务 → PodTopologySpread（topologyKey=zone, maxSkew=1）；Pod 必须同节点（sidecar） → podAffinity + hostname；专用硬件（GPU/ARM） → taint + toleration；负载不均想再平衡 → descheduler。
模块 2

优先级与抢占：谁挤掉谁

抢占解决的是一个具体问题：高优先级 Pod 要调度，但所有节点都不够资源。kube-scheduler 的做法是挑若干个低优先级 Pod 驱逐，腾地方。

# ===== PriorityClass：给 Pod 定“身价” =====
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority
value: 1000000          # 用户自定义范围：-2147483648 ~ 1000000000
globalDefault: false      # true = 没指定 priorityClassName 的 Pod 用它
description: "核心交易链路，可抢占普通离线任务"
preemptionPolicy: PreemptLowerPriority   # Never = 只排队，永不抢别人
# 内置两个“特权”优先级（用户不可达）：
#   system-cluster-critical = 1000000000
#   system-node-critical     = 2000000000（kubelet 自身就带这个）

抢占的执行链路

PostFilter 触发：高优先级 Pod 所有节点都 Filter 失败，DefaultPreemption 插件介入
模拟驱逐：找出“杀掉后能让本 Pod 调度成功”的节点，在每个候选节点上模拟删除低优先级 Pod，看是否腾出空间
选受害者：按“驱逐代价最小”排序 —— 优先选优先级差最多、数量最少、刚启动不久的 Pod；nominatedNodeName 先占坑，防止别人抢
优雅删除受害者：尊重 terminationGracePeriodSeconds，资源逐步释放，高优 Pod 可能等一会儿才真正 bind
抢占的三个反直觉点：
① 抢占不保证立刻调度。受害者走完优雅终止（最长 30 秒）才释放资源，这期间高优 Pod 仍是 Pending。
② 抢占可以连锁，被驱逐者也可能触发别人的抢占，形成驱逐风暴。
③ 优先级是静态身价，与资源用量无关。priority=100 的空转 Pod 照样抢走 priority=99 的 busy Pod。
实践：交易链路配 1000000 级 PriorityClass，离线计算配低值。别把整个集群都设成高优先级，那等于都没优先级。
模块 3

控制器模式：声明式背后的循环

你 kubectl apply 一个 Deployment 就完事走人，但集群里发生的是一场永不停歇的“观测 → 对比 → 行动”循环。所有内置组件和 Operator 都是同一个套路。

List-Watch：不是“收到通知”，而是“定期对账”

# ===== Informer 的三层结构 =====
Reflector ──List──> API Server   # 启动时全量拉一次，拿到 resourceVersion
         └─Watch─> API Server   # 之后只传增量（ADDED/MODIFIED/DELETED），断线自动重连续传
           │
           ▼
      DeltaFIFO 队列            # 增量事件先进队列，去重合并
           │
           ▼
  Indexer（本地缓存）           # etcd 的本地只读镜像，查询不走 API Server
           │
           ▼
  SharedInformer 分发           # 同一资源类型全集群只建一条 Watch，所有控制器共享
问题答案
为什么要本地缓存否则每个控制器、每个 ReplicaSet 都去 LIST 全量 Pod，API Server 直接被打爆
Watch 断了怎么办Reflector 自动重新 LIST + Watch（用最后的 resourceVersion）。控制器不需要保证不丢事件
resync 是什么周期性（常见 10 小时）全量重放缓存触发一次 reconcile。是安全网，不是性能优化

WorkQueue：控制器的事件队列

# 典型消费循环（伪代码，controller-runtime 封装了细节）
for item := range queue.Get() {
    key := item.(string)          // 形如 "namespace/name"，不是对象本身
    result, err := reconcile(key) // 真正干活的函数
    if err != nil {
        queue.AddRateLimited(key)  // 指数退避：5ms 起步翻倍，上限 1000s
    } else if result.RequeueAfter > 0 {
        queue.AddAfter(key, result.RequeueAfter)
    } else {
        queue.Forget(key)          // 成功，清除退避计数
    }
    queue.Done(item)
}
  • 去重：key 已在队列或正在处理时，重复 Add 会被合并 —— “事件丢失”不等于“状态丢失”，reconcile 读的是当前真实状态。
  • 限速：失败重试带指数退避（5ms 起步翻倍，上限 1000s），防止打爆 API Server。
  • 多 worker：可起 N 个 goroutine 并发消费，但同一个 key 不会被并发处理，天然避免竞态。

Level-triggered vs Edge-triggered

模式触发方式对事件丢失的态度
Level-triggered
（水位触发）		观察“当前状态 vs 期望状态”的差异，有差异就行动无所谓丢事件。漏一次通知没关系，下一轮对账照样能发现差异并修平 —— K8s 全部采用
Edge-triggered
（边沿触发）		每次“变化”触发一次动作丢一个事件就永久失同步，必须靠额外机制补。消息系统、部分中间件用这种
这是 K8s “自愈”的真正来源：Deployment 控制器不是记住了“我要创建 3 个 Pod”，而是持续核对“现在有几个、是不是我要的镜像/标签”。你手动删 Pod、改标签，下一轮对账就会被改回来。reconcile 因此必须幂等。
模块 4

Operator 与 CRD：把运维知识写进代码

CRD 扩展 API，Operator 是“带运维逻辑的控制器”。两者组合等于“用 YAML 声明一个高级资源，让代码替你维护它的一生”。你声明“要一个 3 节点的 MySQL 主从集群”，控制器负责建实例、配主从、跑备份、故障切换。

CRD YAML 骨架

# 一个最简但字段合法的 CRD
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: mysqlclusters.db.example.com       # 必须是 <plural>.<group>
spec:
  group: db.example.com
  scope: Namespaced                        # 或 Cluster
  names:
    plural: mysqlclusters
    singular: mysqlcluster
    kind: MySQLCluster
    shortNames: [mysql]                   # kubectl get mysql
  versions:
    - name: v1
      served: true
      storage: true                          # 每个 CRD 只能有一个 storage=true 的版本
      subresources:
        status: {}                          # /status 子资源独立更新
      additionalPrinterColumns:             # kubectl get 显示的额外列
        - name: Replicas
          type: integer
          jsonPath: .spec.replicas
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: ["replicas", "image"]
              properties:
                replicas: { type: integer, minimum: 1, maximum: 9 }
                image:    { type: string }
                version:  { type: string }
            status:
              type: object
              x-kubernetes-preserve-unknown-fields: true   # 结构不确定的字段透传
CRD 的硬性约束：① 结构schema 强制，嵌套字段也要写全 type/properties；② 单个 CR 大小有上限（约 1.5MB，etcd 请求限制）；③ 删除 CRD 会级联删掉所有 CR，先确认。

Reconcile 循环：Operator 的心脏

// controller-runtime 的骨架，看懂这个就看懂所有 Operator
func (r *MySQLClusterReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    // 1. 拿到触发源对象（从缓存读，不打 API Server）
    var cluster dbv1.MySQLCluster
    if err := r.Get(ctx, req.NamespacedName, &cluster); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)   // 已删除 = 无事可做
    }

    // 2. 处理 deletionTimestamp：被删了但 finalizer 还在 = 收尾时机
    if !cluster.DeletionTimestamp.IsZero() {
        r.cleanupBackups(ctx, &cluster)
        controllerutil.RemoveFinalizer(&cluster, myFinalizer)
        return ctrl.Result{}, r.Update(ctx, &cluster)
    }

    // 3. 期望 vs 现状：确保 StatefulSet 存在且副本数对
    if err := r.ensureStatefulSet(ctx, &cluster); err != nil {
        return ctrl.Result{RequeueAfter: 10 * time.Second}, err
    }

    // 4. 更新 status（status subresource）
    cluster.Status.Ready = int32(readyReplicas)
    if err := r.Status().Update(ctx, &cluster); err != nil {
        return ctrl.Result{}, err
    }
    return ctrl.Result{}, nil
}
返回值语义
Result{}, nil收敛完成，等新事件触发
Result{Requeue: true}立即重新入队，用于“刚改了状态，想马上再看一眼”
Result{RequeueAfter: d}延迟入队，用于轮询类逻辑（如检查备份是否完成）
Result{}, err失败，指数退避自动重试；持续错误打 Error 事件

级联删除：ownerReferences

# 控制器创建的子对象必须打上属主标记
ownerReferences:
  - apiVersion: db.example.com/v1
    kind: MySQLCluster
    name: prod-mysql
    uid: a1b2c3d4-...              # 必须是属主真实 UID
    controller: true                  # 标记“由我控制”
    blockOwnerDeletion: true         # 属主没删干净前，子对象不准消失（前台级联）

# 删除策略（metadata 上）：
#   默认（后台级联）：属主先消失，GC 后台清理子对象
#   foregroundDeletion：先删子对象，确认干净后才删属主
#   orphanDeletion：删属主，子对象保留为“孤儿”
kubectl delete mysqlcluster prod-mysql --cascade=orphan   # 保留子对象
写 Operator 的工程建议：① 别在 spec 里维护状态机，status 才是事实来源；② reconcile 要幂等；③ 能用 controllerutil.CreateOrUpdate 就别手写三段式；④ 上线前测一遍“删掉 Operator 自己 Pod”，看重新选主后是否收敛。
模块 5

HPA 与 VPA：自动伸缩的两条路

一个按指标横向加减副本，一个按用量纵向调整规格。解决的问题不同，混用会打架。

HPA（HorizontalPodAutoscaler）

# autoscaling/v2 的标准写法（v1 已废弃，只用 CPU 单指标）
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web
  minReplicas: 2
  maxReplicas: 20
  metrics:
    - type: Resource                      # 资源类指标，来自 metrics-server
      resource:
        name: cpu
        target:
          type: Utilization               # 按 requests 百分比；AverageValue 是绝对值
          averageUtilization: 70
    - type: Pods                           # Pod 自定义指标（如每 Pod QPS），需 prometheus-adapter
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "100"
  behavior:                               # 伸缩行为调优，v2 才有；还有 External 类型接外部指标
    scaleDown:
      stabilizationWindowSeconds: 300     # 默认 300s：连续 5 分钟都建议缩才动手，防抖动
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60               # 每分钟最多缩 10%
    scaleUp:
      stabilizationWindowSeconds: 0        # 扩容立即执行
      policies:
        - type: Pods
          value: 4
          periodSeconds: 15               # 每 15 秒最多加 4 个副本
要点说明
副本数公式ceil(currentReplicas × currentMetric / targetMetric)，多指标取最大值；容忍度默认 10%
CPU 利用率的分母是 requests，不是 limit，也不是节点容量。不设 requests 的 Pod 无法被 HPA 按 CPU 伸缩
同步周期默认 15~30 秒一次。指标毛刺 → 副本抖动 → 用 behavior 稳定窗口压住。0 副本起步需 KEDA
常见“不动”原因metrics-server 没装、targetRef 名字写错、指标类型没配 adapter、已达 max/min

VPA（VerticalPodAutoscaler）

上游 VPA 是树外项目（不属于 Kubernetes 核心，GKE 有托管版）。组件：Recommender（算建议值）、Updater（执行）、Admission Controller（新建 Pod 时改写 spec）。四种模式：

updateMode行为
Off只出建议不执行，用 kubectl describe vpa 看推荐值 —— 最常用
Initial只在 Pod 创建时按建议值设置，运行中不动
Recreate运行中变更需要重建 Pod（会中断服务）
Auto较新版本：支持原地调整（InPlacePodVerticalScaling），无需重建
updateMode: "Off"              # 先跑一周看建议值
resourcePolicy:
  containerPolicies:
    - containerName: app
      minAllowed: { cpu: 100m, memory: 256Mi }   # 设下限，防建议值砍到危险区
      maxAllowed: { memory: 8Gi }
      controlledResources: ["cpu", "memory"]
HPA + VPA 同时管同一字段 = 事故。HPA 改 replicas、VPA 改 requests/limits 本身不冲突，但如果 VPA 是 Recreate/Auto 模式，它会重建 Pod，指标剧烈波动，两个控制器互相“打架”。主流做法：HPA 为主 + VPA 只开 Off 当顾问。
模块 6

requests/limits 的真实行为

这是 K8s 里最被低估的模块。requests 和 limits 不是“配额数字”，它们直接翻译成 cgroup 参数，决定了你的进程会不会被节流、会不会被内核杀死。

CPU：requests 是权重，limits 是配额

字段落到 cgroup（v2）真实行为
requests.cpucpu.weight（由 cpu.shares 换算）只影响 CPU 竞争时的分配比例，不设上限。节点空闲时，requests 1m 的进程也能跑满一个核
limits.cpucpu.max = quota/period硬上限。默认 period=100000µs（100ms），quota = limit × 100ms。500m = 每 100ms 最多用 50ms
# limit 的真相：即使节点 CPU 全空闲，到了配额也得睡
# 容器内看节流计数（cgroup v2）：
cat /sys/fs/cgroup/cpu.stat
#   nr_throttled  被节流的周期数  ← 持续增长就是被限惨了
#   throttled_usec 被节流的累计时间
# cgroup v1 路径：/sys/fs/cgroup/cpu,cpuacct/cpu.stat
CPU throttle 的隐蔽性：节点监控显示 CPU 使用率很低，服务 P99 延迟却周期性毛刺（每 100ms 一次小高峰）。这是 CFS 配额耗尽的典型症状 —— 每 100ms 周期用满配额就被强制休眠到下一周期，哪怕其他 CPU 全空闲。
典型肇事者：JVM GC 线程、Go GC、多线程初始化、音视频转码这类突发多核负载。
解法：① 适当放大 limits；② 保守的团队直接不配 CPU limit（配 requests 保调度公平）；③ CPU Manager static 策略（需 Guaranteed QoS）绑核，绕开配额。

内存：没有“节流”，只有“击杀”

字段行为
requests.memory调度依据：节点上所有 Pod 的 requests 之和不能超过节点可分配容量（减去 kube-reserved / system-reserved / 驱逐阈值）
limits.memorycgroup memory.max。超过 = 内核 OOM Killer 直接杀容器，没有商量、没有限流过渡
# OOMKilled 的判定链条：
kubectl get pod web-xxx -o jsonpath='{.status.containerStatuses[0].lastState}' | jq
#   "terminated": { "reason": "OOMKilled", "exitCode": 137 }
# exitCode 137 = 128 + 9（SIGKILL）；143 = 128 + 15（SIGTERM，正常优雅终止）
# 内存“工作集”不是 RSS：kubelet 用 usage - inactive_file 算 working set
# JVM 用户必看：容器内 JVM 默认按节点物理内存算堆，很容易超 limit
java -XX:MaxRAMPercentage=75.0 -jar app.jar   # JDK8u191+ 默认已容器感知，按 limit 的 75% 算最大堆
“内存超 limit 被杀”和“节点内存不足被驱逐”是两条独立的死法：前者是自己超了 cgroup 上限（lastState.reason=OOMKilled），后者是节点整体吃紧 kubelet 主动驱逐（事件写 The node was low on resource: memory）。排查时先分清是哪一种。

一份生产级 Deployment 的资源配置

resources:
  requests:
    cpu: 500m          # 压测稳态值，用于调度和 HPA 分母
    memory: 512Mi       # 同样来自压测，偏保守
  limits:
    cpu: 2              # 留 4 倍余量防 throttle；或直接不设 limit
    memory: 1Gi        # limit 必须大于 requests，否则 QoS 降级
readinessProbe:          # 不就绪就摘流量，可以严格一点
  httpGet: { path: /healthz, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 5
livenessProbe:            # 失败就重启，必须宽松（留足启动时间）
  httpGet: { path: /livez, port: 8080 }
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 6       # 连续 6 次失败才重启，60 秒容忍窗口
startupProbe:             # 启动慢的服务用它，成功前 liveness 不生效
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 5
  failureThreshold: 60      # 最长给 300 秒启动
模块 7

QoS 类别与节点驱逐

每个 Pod 在创建时就自动分成了三六九等。这个分类平时看不见，节点资源紧张时直接决定谁先死。

QoS判定条件驱逐优先级
Guaranteed所有容器都设了 requests 和 limits，且 cpu 和 memory 都 requests == limits最后被驱逐（除非用量超 requests）
Burstable至少一个容器设了 requests/limits，但不满足 Guaranteed（最常见）中等：用量超 requests 的先被驱逐
BestEffort所有容器都没设 requests 和 limits最先被驱逐，永远排第一
# 查看 Pod 的 QoS（kubectl 默认不显示，要取字段）
kubectl get pod web-xxx -o jsonpath='{.status.qosClass}' ; echo
# 扫出集群里所有 BestEffort Pod（潜在第一批炮灰）
kubectl get pods -A -o json | jq -r '.items[] | select(.status.qosClass=="BestEffort") | "\(.metadata.namespace)/\(.metadata.name)"'

kubelet 驱逐：节点压力时的“末日审判”

# 硬驱逐阈值（kubelet 默认值，任一触发就开始杀 Pod）
eviction-hard:
  memory.available < 100Mi          # 节点可用内存
  nodefs.available < 10%           # 根文件系统（容器层、日志）
  nodefs.inodesFree < 5%          # inode 耗尽也算磁盘压力
  imagefs.available < 15%        # 镜像存储
  imagefs.inodesFree < 5%
eviction-pressure-transition-period: 5m  # 压力持续 5 分钟才动真格
# 节点 condition：Ready / MemoryPressure / DiskPressure / PIDPressure / NetworkUnavailable
压力类型第一反应
MemoryPressure杀 Pod 顺序：BestEffort → Burstable 超 requests 者 → Guaranteed。同时节点打 Taint node.kubernetes.io/memory-pressure 阻止新调度
DiskPressure先删已停止容器和未使用镜像（镜像 GC 阈值 85%/80%），还不够才杀 Pod
PIDPressure进程/线程泄漏的典型信号，杀 Pod 只是止血，要查应用 fork 行为
QoS 选型口诀：核心无状态服务（API 网关、交易链路）→ Guaranteed（requests==limits）；普通在线服务 → Burstable（requests 略低于 limits）；离线批处理、可牺牲任务 → 低 requests + BestEffort 或低优先级。
一个真实教训：核心服务忘了设 memory limit（requests 512Mi、limit 不设 → 还是 Burstable），节点抖动时它因“用量超过 requests”被优先驱逐，造成雪崩。设成 requests==limits 就能进 Guaranteed 保护区。
模块 8

十个线上坑

1
CPU limit 配得太小，服务“看起来闲但慢”
节点 CPU 使用率不高，P99 却每 100ms 周期性毛刺。CFS 配额耗尽就强制休眠，与节点空闲无关。查 cpu.stat 的 nr_throttled 可证实。
2
不配 readiness 探针，上线瞬间 502
Pod 进程起来了但连接池还没预热，Service 就把流量分过去，请求全错。readiness 失败时 Pod 会被移出 Endpoints，是唯一能“暖机”的机制。
3
liveness 探针配得太严，慢启动服务被反复重启
Java/Spring 启动要 60 秒，liveness 30 秒就开始杀，进入 CrashLoopBackOff（退避 10s 起翻倍、上限 300s）。正解是用 startupProbe 给足启动预算，liveness 只负责运行期死活。
4
删 Pod 卡 30 秒，以为滚动更新挂了
默认 terminationGracePeriodSeconds=30，SIGTERM 后应用不退出就要等满 30 秒再 SIGKILL。发版变慢、缩容慢都是这个。要么实现优雅退出，要么显式调小。
5
finalizer 卡住删除，namespace 永远 Terminating
控制器已下线但 finalizer 没人移除，对象删不掉。解法：patch 掉 finalizers，别直接动 etcd。
6
关键服务跑在 BestEffort 上，节点一抖动先死
没设 requests/limits = BestEffort QoS，节点内存压力时第一批被驱逐。核心服务至少设 requests==limits 进 Guaranteed。
7
JVM 不认容器 limit，OOMKilled 后一脸懵
JVM 按节点物理内存算默认堆，远超容器 limit。exitCode 137 + reason OOMKilled。用 -XX:MaxRAMPercentage=75 让 JVM 按容器 limit 计算。
8
required podAntiAffinity + hostname，副本扩不出去
3 副本要求分散在 3 台不同机器，集群只有 2 个 worker → 第 3 个 Pod 永远 Pending，事件写 didn't match anti-affinity。
9
新增节点组忘了 toleration，Pod 全部 Pending
新节点组（GPU、Spot、专用业务）通常带 NoSchedule 污点，旧工作负载没有对应 toleration，扩容扩不出来。节点组变更要同步审计 toleration。
10
HPA 和 VPA 同时自动改规格，两个控制器打架
VPA 的 Recreate/Auto 模式会重建 Pod，指标剧烈波动，HPA 跟着反复扩缩容，副本数震荡。规范做法：HPA 管 replicas，VPA 只开 Off 当顾问。
自测

六道题

1. 某 Pod 的 CPU limit 是 500m，节点整体很空闲，但监控显示它每 100ms 就被强制停顿一次。原因是？
正确答案：CFS 配额。limits.cpu 翻译成 cgroup 的 cpu.max（quota/period），500m = 每 100ms 最多 50ms。配额用完就休眠到下一周期，即使其他 CPU 全空闲。
2. 节点触发 MemoryPressure 开始驱逐时，Pod 的死亡顺序是？
正确答案：BestEffort → Burstable（超 requests 者）→ Guaranteed。核心服务要 requests==limits 进 Guaranteed 保护区。
3. 一个 Pod 里所有容器都配了 requests 和 limits，且 cpu、memory 全部 requests==limits。它的 QoS 是？
正确答案：Guaranteed。注意是“所有容器 + 所有资源类型”都满足相等，漏一个容器就是 Burstable。
4. K8s 控制器采用 level-triggered（水位触发）模式，最大的工程收益是？
正确答案：漏事件无害。Watch 断了重连、事件合并去重都不会失同步，因为 reconcile 比较的是“当前实际状态 vs 期望状态”。代价是必须幂等。
5. 一个 namespace 删不掉，一直卡在 Terminating，最可能的原因和处理方式是？
正确答案：finalizer 阻塞。常见于控制器已下线但 finalizer 仍在。处理：kubectl patch 移除 finalizers，或恢复对应控制器。绝不可直接操作 etcd。
6. topologySpreadConstraints 里 maxSkew=1、topologyKey=zone、whenUnsatisfiable=DoNotSchedule 的含义是？
正确答案：最大倾斜为 1。maxSkew 是“数量差的上限”，DoNotSchedule 让它成为硬约束 —— 可用区不够时新 Pod 会 Pending。软约束改用 ScheduleAnyway。
