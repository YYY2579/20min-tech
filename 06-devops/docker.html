十分钟理解并学会 Docker

上一期是"看"网络，这一期是"造"环境。目标：十分钟后你能自己写 Dockerfile、构建镜像、跑起容器，并且知道为什么这么做。

10:00
这一期光看没用 —— 每节都开个终端敲一遍，比读完十遍管用。
0-1 分钟

它到底在解决什么问题

你一定说过这句话，或者听别人说过：

"在我电脑上能跑啊。"
问题出在：代码之外还依赖一堆东西 —— 运行时版本、系统库、环境变量、目录结构、系统配置。这些东西没法跟代码一起提交，于是换个机器就崩。

Docker 的做法极其直接：把应用和它的一整套运行环境打包成一个标准件。这个标准件到哪都长得一样，跑起来的行为也一样。这就是"容器化"。

它和虚拟机到底差在哪

维度虚拟机Docker 容器
隔离层每个应用带一个完整 Guest OS共享宿主内核，只隔离进程
启动速度几十秒到几分钟毫秒到几秒
体积GB 级MB 级
一台机器能跑几个几个到十几个几十个很轻松
隔离强度强（硬件级）较弱（进程级），但足够日常用
一句话记住差异：虚拟机是"造一台新电脑"，Docker 是"给进程套个独立的小房间"。前者重但隔离彻底，后者轻但共享内核 —— 这也是为什么 Docker 只能跑 Linux 容器（Windows 容器除外，且需要对应内核支持）。
1-3 分钟

三个概念，一次说清

Docker 的名词不多，但新手最容易把它们搅在一起。用面向对象来类比，一秒就通。

概念类比说明
镜像 Image类 / 模板 / 光盘只读的。里面装好了代码 + 运行时 + 依赖 + 配置
容器 Container对象 / 实例 / 跑起来的程序镜像跑起来的实例。同一个镜像可以跑出 10 个互不干扰的容器
仓库 Registry应用商店 / npm存镜像的地方。Docker Hub 是官方的公共仓库
Dockerfile配方 / 源码一份文本文件，描述怎么把镜像一层层造出来
把它们串起来：写 Dockerfile → docker build 造出镜像 → docker push 推到仓库 → 别人 docker pull 拉下来 → docker run 跑成容器。整条链路就这五步。
为什么镜像能"到处跑"？因为它自带运行时。你的镜像里可能装了 Node 20，那么宿主机有没有 Node、装的是几版，完全无所谓 —— 容器里用的是镜像里那套。
3-5 分钟

装好，跑起来

第 0 步：装 Docker

Windows / Mac 直接装 Docker Desktop（自带 Docker Engine + 命令行 + 图形界面）。Windows 需要开启 WSL2 后端。Linux 用包管理器装 docker-ce。

装完在终端验证：

docker --version
docker run hello-world   # 拉取并运行一个测试镜像

看到 "Hello from Docker!" 就说明装好了。

第 1 步：跑一个真实服务（30 秒）

docker run -d -p 8080:80 --name web nginx

然后浏览器打开 http://localhost:8080 —— 你会看到 nginx 的欢迎页。你刚刚在 3 秒内跑起了一个 Web 服务器，没装任何东西。

这条命令每个参数都得懂，它是 Docker 的日常：
-d 后台运行（detached），不加的话终端会被占住
-p 8080:80 端口映射，格式是 宿主机端口 : 容器端口，顺序千万别反
--name web 给容器起个名字，不然只能用随机 ID 操作它
nginx 要用的镜像名，本地没有就自动从 Docker Hub 拉

第 2 步：观察它

docker ps                    # 看正在运行的容器
docker logs -f web           # 实时看它的日志，Ctrl+C 退出
docker exec -it web bash     # 进到容器里面看看，exit 退出
docker stats                 # 看 CPU / 内存占用
小提示：如果 bash 报错说找不到，换成 sh。alpine 这类精简镜像里通常只有 sh，没有 bash。

第 3 步：清理

docker stop web && docker rm web
docker rmi nginx             # 删镜像
5-7 分钟

命令速查：20 条覆盖 95% 场景

不用背。收藏这一页，用的时候复制。点右侧按钮直接复制。

容器（日常用得最多）

docker ps看运行中的容器
docker ps -a看所有容器，包括已停止的（排查"容器哪去了"必用）
docker logs -f 容器名实时看日志，容器起不来先看这个
docker exec -it 容器名 sh进容器内部，最常用的调试手段
docker stop 容器名 && docker rm 容器名停止并删除容器
docker inspect 容器名看容器的完整配置（IP、挂载、环境变量）
docker cp 容器名:/app/log.txt ./从容器里把文件拷出来

镜像

docker images列出本地镜像
docker pull node:20-alpine拉取镜像，alpine 版体积小很多
docker build -t myapp:v1 .用当前目录的 Dockerfile 构建镜像，注意最后那个点
docker build --no-cache -t myapp:v1 .不用缓存强制重建，怀疑缓存问题时用
docker history 镜像名看镜像每一层多大，排查镜像臃肿
docker rmi 镜像名删镜像

数据卷与网络

docker run -v /宿主机/路径:/容器/路径 镜像名目录挂载，数据落在宿主机上不会丢
docker volume ls看所有数据卷
docker network create mynet建一个自定义网络，容器间可直接用名字互访
docker run --network mynet --name db mysql把容器接入指定网络

清理（磁盘爆了就用）

docker system df看 Docker 占了多少磁盘
docker system prune -a清掉所有未使用的镜像、容器、网络 —— 谨慎，会删东西
7-9 分钟

Dockerfile 与分层缓存

这是拉开水平的一节。会写 Dockerfile 只是入门，懂分层才是内行。

一份标准 Dockerfile

# 1. 基础镜像
FROM node:20-alpine

# 2. 设置工作目录（后续指令都在这里执行）
WORKDIR /app

# 3. 先只拷依赖清单 —— 关键！
COPY package*.json ./

# 4. 装依赖（这一步最慢，所以要让它尽量命中缓存）
RUN npm install --production

# 5. 再拷业务代码
COPY . .

EXPOSE 3000
CMD ["node", "index.js"]

为什么 COPY 要分两次？

因为镜像每条指令生成一层，每层都有缓存。缓存的规则是：从第一条变化的指令开始，之后所有层全部作废重建。

Dockerfile 写法改一行业务代码后，构建时要做什么
COPY . . 放在 npm install 之前代码变了 → 这一层失效 → npm install 重新跑一遍（几分钟）
COPY . . 放在 npm install 之后代码变了 → 只重建最后两层 → 依赖缓存命中（几秒）
铁律：变化越频繁的放越下面。基础镜像 → 依赖清单 → 装依赖 → 业务代码。这个顺序能让你的构建从几分钟降到几秒。

构建与运行

docker build -t myapp:v1 .
docker run -d -p 3000:3000 --name app myapp:v1

别忘了 .dockerignore

和 .gitignore 一个道理。把 node_modules、.git、dist 排掉，否则它们会被 COPY 进镜像 —— 镜像瞬间胖几百 MB，而且缓存频繁失效。

# .dockerignore
node_modules
.git
*.log
.env
dist

进阶一眼：多阶段构建

编译型项目（Go、Java、前端）可以让最终镜像只保留产物，体积能小十倍：

FROM node:20 AS builder
WORKDIR /app
COPY . .
RUN npm install && npm run build

FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html

第二个 FROM 会丢掉第一个阶段的所有中间产物，最终镜像里只有编译好的静态文件。

9-10 分钟

数据、网络，和六个必踩的坑

数据持久化

容器删了，里面的数据就没了 —— 因为写入发生在可写层，它随容器一起销毁。要留住数据只有一条路：挂出来。

# 绑定挂载：宿主机目录映射进容器，适合开发
docker run -v $(pwd)/data:/var/lib/mysql mysql

# 命名卷：由 Docker 管理，适合生产
docker run -v mydata:/var/lib/mysql mysql

网络

容器之间默认不通。接到同一个自定义网络里，就能直接用容器名当主机名互访 —— 这是微服务部署的基础。

docker network create mynet
docker run -d --network mynet --name db  mysql
docker run -d --network mynet --name api myapi
# 现在 api 容器里可以直接连 db:3306，不用写 IP

至于多容器编排（一次起一堆、管理依赖关系），那是 Docker Compose 的活 —— 一个 docker compose up -d 搞定，值得单独学一节。

六个必踩的坑

1
容器刚启动就退出了
容器的生命周期 = 主进程的生命周期。主进程结束，容器就停。先看 docker logs，八成是配置错或端口被占。
2
-p 端口写反了
-p 8080:80 是 宿主机 : 容器。写反了浏览器就是打不开，而且不会有任何报错。
3
删了容器，数据全没了
没挂卷。数据库这类有状态服务，必须挂卷或用命名卷。
4
exec 进去装的东西，重启就消失
容器的可写层是临时的。任何要长期存在的改动，都必须写进 Dockerfile 重新构建。
5
改了代码，构建出来却没变
缓存。要么 --no-cache 强制重建，要么检查 .dockerignore 是不是把该拷的文件排除了。
6
镜像莫名其妙几个 G
基础镜像用了完整版（如 node:20 而不是 node:20-alpine），或者把 node_modules、.git 拷了进去。
自测

四道题，检验是不是真懂了

1. docker run -d -p 8080:80 nginx 里的 8080 是什么？
正确答案：宿主机端口。格式永远是 宿主机 : 容器。所以是访问 localhost:8080 转发到容器的 80 端口。
2. 镜像和容器的关系，最贴切的类比是？
正确答案：类与对象。镜像是只读模板，容器是它跑起来的实例，一个镜像可以同时跑出十个互不干扰的容器。
3. Docker 比虚拟机轻那么多的根本原因是？
正确答案：共享宿主机内核。虚拟机每个实例都要跑一整套操作系统，容器只是被隔离的进程，共用同一个内核。
4. 你只改了一行业务代码，重新 build 时会发生什么？
正确答案：从 COPY . . 开始失效。这正是把 COPY . . 放在最后的原因 —— 改代码不用重装依赖，构建从几分钟降到几秒。

Dockerfile 常用指令

指令作用
FROM指定基础镜像，必须是第一条指令
WORKDIR设置工作目录，之后的指令都在此目录执行（会生成一层，但几乎不占空间）
COPY从构建上下文拷文件进镜像，最常用
ADD类似 COPY，还能解压 tar、支持 URL —— 除非需要解压，否则用 COPY
RUN构建时执行命令，每条 RUN 生成一层，合并写能减小体积
ENV / ARGENV 是运行时的环境变量；ARG 只在构建阶段有效
EXPOSE声明容器监听哪个端口（只是文档作用，真正映射靠 -p）
VOLUME声明匿名数据卷
CMD容器启动时的默认命令，会被 docker run 后面的参数覆盖
ENTRYPOINT容器启动时的固定命令，不会被覆盖，常和 CMD 搭配

三个"看状态"的命令，记住就够用

命令回答什么问题
docker ps -a我的容器都去哪了？为什么它不见了？
docker logs 容器名它为什么起不来 / 为什么报错？
docker exec -it 容器名 sh它里面到底长什么样？
下一步怎么练：拿你手头任意一个项目，写一份 Dockerfile 把它跑起来。遇到问题依次用 docker logs → docker exec → 改 Dockerfile 重构建。跑通一个，你就真的会了。然后再学 Docker Compose（多容器编排）和 多阶段构建（减小镜像）。
