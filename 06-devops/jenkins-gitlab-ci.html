二十分钟学透 Jenkins 与 GitLab CI

两个工具代表了 CI/CD 的两条路线：Jenkins 是万能插件平台，GitLab CI 是仓库内生的流水线。这篇直接讲架构、Pipeline as Code、共享库、Runner、cache/artifacts 区别，以及流水线设计模式。

模块 1

Jenkins 架构：Controller / Agent / Executor

Jenkins 是主从（controller–agent）架构：controller 管调度和状态，agent 干实际工作。

角色职责
Controller
（原 master）		调度构建、存配置与历史、提供 Web UI。controller 上不跑重型构建，executor 数设为 0
Agent
（原 slave/node）		真正执行构建的机器，可以是物理机、VM、Docker 容器或 K8s Pod
Executoragent 上的并行构建槽位。一个节点 executor=2，就是同时跑 2 个构建
Workspace每次构建在 agent 上的工作目录，构建完默认保留，是磁盘杀手

Agent 连接方式

SSHcontroller 用 SSH 连 agent，稳定，适合固定机器
JNLPagent 主动外连 controller 的 50000 端口（Java Web Start），agent 在 NAT 后也能用
Docker / K8s按需拉起容器/Pod 跑构建，用完即毁，弹性与隔离的最佳实践
# Jenkinsfile 里把不同阶段调度到不同 agent
pipeline {
  agent none                      # 顶层不占 agent，每个 stage 自己指定
  stages {
    stage('Build') {
      agent { label 'linux && docker' }   # 表达式选节点
      steps { sh 'make build' }
    }
    stage('Test') {
      agent { kubernetes { yaml '''...Pod 模板...''' } }   # K8s 动态 Pod
      steps { sh 'make test' }
    }
  }
}
规模化的分水岭：单机 Jenkins（controller 兼 executor）跑十几个 job 没问题；上百个 job 后，controller 变瓶颈。标准演进路径：固定 agent 池 → Docker agent → K8s agent 弹性伸缩，同时把 controller 的 executor 清零、磁盘外挂、配置进 JCasC。
模块 2

Pipeline as Code：声明式 vs 脚本式

维度声明式 Declarative脚本式 Scripted
入口pipeline { } 代码块node { } 代码块
结构固定骨架：agent/stages/steps/post，有语法校验自由 Groovy，怎么写都对，写砸了运行时才炸
可视化Blue Ocean / Stage View 原生支持展示能力弱
适用团队标准流水线，默认选它需要复杂逻辑的边角场景，或老项目
// ===== 声明式：一个完整的真实 Jenkinsfile =====
pipeline {
  agent { label 'linux' }
  options {
    timeout(time: 30, unit: 'MINUTES')        // 防僵尸构建占死 executor
    buildDiscarder(logRotator(numToKeepStr: '20', artifactNumToKeepStr: '5'))
    disableConcurrentBuilds()               // 同一 job 不并发（部署类 job 必加）
    timestamps()                            // 日志带时间戳，排障神器
  }
  parameters {
    choice(name: 'ENV', choices: ['staging', 'prod'], description: '部署环境')
    booleanParam(name: 'SKIP_TESTS', defaultValue: false)
  }
  environment {
    REGISTRY = 'harbor.internal/library'
    IMAGE_TAG = "${env.BUILD_NUMBER}-${env.GIT_COMMIT.take(7)}"
  }
  tools { jdk 'openjdk-17' }
  stages {
    stage('Checkout') { steps { checkout scm } }
    stage('Test') {
      when { not { expression { params.SKIP_TESTS } } }
      parallel {
        stage('Unit')  { steps { sh 'mvn -q test' } }
        stage('Lint')  { steps { sh 'mvn -q checkstyle:check' } }
      }
    }
    stage('Build')  { steps { sh 'mvn -B package -DskipTests' } }
    stage('Publish'){ steps { sh "docker build -t ${REGISTRY}/app:${IMAGE_TAG} ." } }
    stage('Deploy') {
      // 人工审批门禁：点一下才继续
      input message: '确认部署到 ' + params.ENV + '？', submitter: 'ops,sre'
      steps { sh "./deploy.sh ${params.ENV} ${IMAGE_TAG}" }
    }
  }
  post {
    always  { junit 'target/surefire-reports/*.xml'; cleanWs() }
    success { sh 'curl -X POST $WEBHOOK_URL -d "build ok"' }
    failure { emailext subject: 'FAILED: ${JOB_NAME}', to: 'team@corp.com' }
  }
}
声明式的红线：① when 里用 expression 调 Groovy，复杂逻辑请挪到共享库函数；② input 会挂起流水线占着 agent/executor，审批门禁放在没有 agent 的 stage 或改用 GitLab 的 manual job；③ post.always 里 cleanWs() 清工作区，是磁盘治理的第一道防线。
模块 3

共享库：把流水线代码变成产品

20 个仓库各写一份 Jenkinsfile，是 CI 灾难的开始。共享库（Shared Library）把公共步骤抽成库，Jenkinsfile 里一行引用。

# 共享库仓库的标准目录结构
shared-library/
├── vars/                      # 全局步骤，每个 .groovy 文件 = 一个可调用步骤
│   ├── buildDocker.groovy     # → Jenkinsfile 里 buildDocker(...) 直接调
│   ├── notify.groovy
│   └── deployApp.groovy
├── src/                       # 普通 Groovy 类，按包路径引用
│   └── com/corp/ci/Version.groovy
└── resources/                 # 非代码资源（配置模板、脚本）
    └── com/corp/ci/deploy.template.sh

# vars/buildDocker.groovy —— 一个自定义步骤的写法
def call(Map config) {
  def tag = config.tag ?: "${env.BUILD_NUMBER}"
  sh "docker build -t ${config.image}:${tag} ${config.context}"
  sh "docker push ${config.image}:${tag}"
  return tag
}

# 业务仓库的 Jenkinsfile：三行消费共享库
@Library('corp-shared@v3.2.1') _          # 注意：固定 tag，别用 @master
pipeline {
  agent any
  stages {
    stage('Build') {
      steps {
        script {
          def tag = buildDocker(image: 'harbor/app', context: '.')
          deployApp(env: 'staging', tag: tag)
        }
      }
    }
  }
  post { always { notify(currentBuild.result) } }
}

共享库版本管理

引用方式评价
@Library('lib@master')禁用。库一升级，所有仓库明天集体变脸，出事无法定位是哪次改动
@Library('lib@v3.2.1')标准做法。git tag 语义化版本，升级 = 逐仓库改引用 + 各自验证
@Library('lib@main')折中：分支相对稳定，但仍建议 tag
共享库的隐藏成本：库的 bug 会同时污染所有仓库，且 Jenkinsfile 里看不出来。对策：① 库自带测试框架（Jenkins Pipeline Unit，JUnit 测 Groovy 步骤）；② 改动先在 1~2 个试点仓库灰度；③ 语义化版本 + CHANGELOG；④ 库代码也要过 CI——它首先是代码，其次才是流水线零件。
模块 4

凭据管理：密码不进 Jenkinsfile

Jenkins 的 credentials store 把密码加密存在 controller 磁盘（credentials.xml），流水线只按 ID 引用。Jenkinsfile 进 git，凭据绝不进。

常见凭据类型

类型用途
Username with password制品库、数据库、第三方 SaaS 的账号密码
Secret textAPI Token、Webhook 密钥
SSH Username with private keyGit 拉取、SCP 部署
Secret filekubeconfig、证书、JSON 密钥文件
Certificate代码签名、双向 TLS
// ===== 用法一：withCredentials 块，块内可用环境变量，出块即消失 =====
withCredentials([usernamePassword(credentialsId: 'harbor-creds', usernameVariable: 'HUB_USER', passwordVariable: 'HUB_PASS')]) {
  sh 'docker login -u $HUB_USER -p $HUB_PASS harbor.internal'
}

// 用法二：绑定成环境变量（credentials 插件）
environment {
  KUBECONFIG = credentials('prod-kubeconfig')   // 自动生成临时文件路径
}

// 用法三：密文文件
withCredentials([file(credentialsId: 'gcp-key', variable: 'GC_KEY')]) {
  sh 'gcloud auth activate-service-account --key-file=$GC_KEY'
}

// 日志里 Jenkins 会自动把凭据值打码成 ****，但注意：
// ① 命令 echo $HUB_PASS 仍是 ****（好事）
// ② 但把密码写进文件名/URL query 参数，会绕过打码泄露
// ③ secret text 打印到 stdout 一样被打码，别把明文二次编码（base64 后就不打码了）
凭据治理清单：① 按环境/项目分 Folder 放凭据，Folder 级权限隔离；② 定期轮换，轮换脚本走 Jenkins API 更新凭据；③ 能挂临时凭据就不挂长期凭据（如 K8s 用 ServiceAccount token，不用静态 kubeconfig）；④ 离职/换岗第一时间在 credentials 页面吊销。
模块 5

GitLab CI/CD：.gitlab-ci.yml 全解

GitLab CI 的哲学：流水线配置和代码住在同一个仓库，push/MR 自动触发，Runner 按需执行。没有中心化调度器，Runner 自己来领活。

# ===== 一份真实的生产级 .gitlab-ci.yml =====
stages: [lint, test, build, deploy]

variables:
  IMAGE: $CI_REGISTRY_IMAGE/app
  DOCKER_DRIVER: overlay2

default:
  image: node:20-alpine
  interruptible: true                  # 新 push 来了就取消旧流水线

# 模板：抽公共配置，用 extends 或 !reference 复用
.node_template:
  cache:
    key:
      files: [package-lock.json]
    paths: [node_modules/]
  artifacts:
    expire_in: 1 week
    paths: [dist/]

lint:
  stage: lint
  script:
    - npm ci --prefer-offline
    - npm run lint
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"

unit-test:
  stage: test
  extends: .node_template
  parallel:
    matrix:
      - NODE_VERSION: ["18", "20", "22"]     # 一条配置 = 3 个并行 job
  image: node:$NODE_VERSION-alpine
  script: [npm ci, npm test]

build-image:
  stage: build
  image: docker:24
  services:
    - docker:24-dind                        # sidecar 模式的 Docker daemon
  script:
    - docker build -t $IMAGE:$CI_COMMIT_SHA .
    - echo $CI_REGISTRY_PASSWORD | docker login -u $CI_REGISTRY_USER --password-stdin
    - docker push $IMAGE:$CI_COMMIT_SHA
  rules:
    - if: $CI_COMMIT_BRANCH == "main"          # 只在 main 构建镜像
      changes: [src/**/*, Dockerfile]      # 且这些路径有改动

deploy-staging:
  stage: deploy
  environment: { name: staging, url: https://staging.example.com }
  script: kubectl set image deploy/app app=$IMAGE:$CI_COMMIT_SHA -n staging
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy-prod:
  stage: deploy
  environment:
    name: production                       # protected environment → 只允许指定人触发
  when: manual                             # 人工点按钮才部署
  allow_failure: false
  script: kubectl set image deploy/app app=$IMAGE:$CI_COMMIT_SHA -n prod
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

pages:                                    # GitLab Pages：产物放 public/ 即发布静态站
  stage: deploy
  image: node:20-alpine
  script: [npm ci, npm run build, cp -r dist/* public/]
  artifacts: { paths: [public] }
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

Runner 类型与执行器

范围特点
Shared runner实例级共享，所有项目可用，适合小团队
Group runner组内项目共享，资源隔离粒度适中
Project runner绑定单个项目，安全与资源保障最强
shell直接在 runner 机器上跑，最快但污染环境、无隔离
docker每个 job 一个干净容器，最常用
docker+machine云上自动伸缩 Runner 虚拟机
kubernetes每个 job 一个 K8s Pod，弹性与隔离天花板
ssh / instance连到指定机器执行 / 云上按需开实例

cache vs artifacts（最常搞混的一组）

维度cacheartifacts
用途同项目 job 之间加速（依赖、编译缓存）把产物传给后续 stage/job或给人下载
存哪Runner 本地（分布式场景不保证命中）GitLab 服务器对象存储，全局可见
生命周期key 变了就换一份expire_in 到期删除（默认 30 天）
下载控制自动按 key 下载默认全部下载，可用 needs: {artifacts: false} 跳过
DAG 提速：默认按 stage 串行（lint 全跑完才 test）。加 needs 声明依赖后，GitLab 按 DAG 立即启动可并行的 job，大流水线能省 30%~60% 时间。needs: [{job: build, artifacts: true}] 表示"等 build 完并拿它的产物"。
模块 6

流水线设计模式

标准阶段划分

# 一条健康的流水线长这样（任一环节失败即中止）：
lint ──→ test ──→ build ──→ scan ──→ push ──→ deploy-staging ──→ smoke ──→ [人工] deploy-prod

# 每层的职责与门禁：
lint      # 秒级反馈：格式、静态检查。不过 = 代码风格债，不配叫 CI
test      # 单测 + 覆盖率门禁（如 coverage > 80% 才继续）
build     # 产出不可变制品（jar / docker image / 二进制），tag = commit SHA
scan      # 安全门禁：镜像漏洞（trivy）、依赖 CVE、密钥泄露（gitleaks）
push      # 推到制品库，从此"构建一次，到处运行"
deploy    # 同一制品依次晋级 staging → prod，环境间只改配置不改镜像
smoke     # 部署后 30 秒健康检查，失败自动回滚到上一版本

五个高频模式

不可变制品
只构建一次镜像，带上 commit SHA tag，staging 验证过的同一个 SHA 进 prod。杜绝"重新打包导致环境差异"
并行矩阵
测试按 Node 版本/OS/架构分片并行。GitLab 用 parallel:matrix，Jenkins 用 matrix 轴 + failFast
审批门禁
生产部署前的人工卡点。GitLab 用 protected environment + manual job；Jenkins 用 input 步骤，注意占 executor
制品晋级
镜像在 registry 里按环境打 tag 晋级（staging → prod），而不是重新构建。晋级 = 改 tag，秒级且可追溯
失败即停
failFast / interruptible：新 push 到达自动取消旧流水线，省算力也避免旧结果覆盖新结果

幂等与回滚

  • 部署脚本幂等：kubectl set image 跑两次结果一样；别用 kubectl create（第二次就报错）
  • 保留上一版本镜像：部署脚本默认记录 current/previous tag，回滚 = 重新部署 previous
  • 数据库迁移向后兼容：先加字段不删字段，代码滚动发布期间老代码能跑——这是 CI 之外但被 CI 牵连的架构纪律
模块 7

Jenkins vs GitLab CI 对比

维度JenkinsGitLab CI
配置位置Jenkinsfile 在仓库，但 job 结构大量在 Web 界面（自由式项目）全部在仓库的 .gitlab-ci.yml，GitOps 纯粹
执行单元controller 调度 + agent 执行，executor 槽位Runner 主动领活，无中心调度器
插件生态2000+ 插件，万能（也是债务来源）内置为主（容器扫描、DAST、Pages），扩展靠 CI 组件/模板
K8s 集成Kubernetes 插件：动态 Pod agent，成熟Kubernetes executor：每个 job 一个 Pod，更轻
凭据credentials store + withCredentials 注入CI/CD Variables（可 masked/protected）+ File 类型
触发方式Webhook（GitLab/GitHub 插件）、定时、上游下游push/MR/tag/调度/pipeline 订阅，天然绑定仓库事件
多仓库编排强项：一个 Jenkinsfile 触发多个仓库、聚合制品单仓库为主，跨仓库用 trigger + CI_JOB_TOKEN
运维成本高：controller HA、插件兼容、磁盘治理低：装 Runner 即用，SaaS 版零运维
适用复杂流水线、遗留系统、多仓库集中管控已在 GitLab 的团队，新项目默认选它
混合架构很常见：代码在 GitLab（用 GitLab CI 做 MR 级快速反馈），但跨仓库的集成部署、定时批处理、发布编排放在 Jenkins，通过 GitLab 的 trigger job 调用 Jenkins API。选型标准只有一条：谁能用更少的自定义代码覆盖 80% 场景。
模块 8

常见坑与防御

Jenkins 侧高频问题

# 1. 磁盘爆满：三大元凶 = workspace + artifacts + 构建历史
options {
  buildDiscarder(logRotator(numToKeepStr: '20', artifactNumToKeepStr: '5'))
}
post { always { cleanWs() } }              # Workspace Cleanup 插件
# 定期：du -sh /var/jenkins_home/* | sort -rh | head
# 大目录外挂到独立卷，JENKINS_HOME 只放配置

# 2. 并发构建互相踩：部署 job 必须 disableConcurrentBuilds()
#    跨 job 抢同一资源（如测试环境）用 lockable-resources：
lock(resource: 'staging-env', inversePrecedence: true) {
  sh './deploy.sh staging'
}

# 3. 共享库浮动引用：@Library('lib@master') → 固定 tag
#    库改动先在 canary 仓库验证，再全量升版本号

# 4. agent 版本不匹配：升级 controller 后老 agent 连不上
#    Jenkins 要求 agent 与 controller 大版本兼容，滚动升级：先 agent 后 controller

# 5. 安全基线：不要暴露公网；匿名用户禁 "Execute Groovy"
#    脚本沙箱（Script Security）默认开启，别全局关掉

GitLab CI 侧高频问题

# 1. cache 不命中：key 设计错误。缓存 key 跟着分支走，每个 MR 都是新 key
cache:
  key:
    prefix: npm
    files: [package-lock.json]        # 依赖文件没变 → key 不变 → 命中
  paths: [node_modules/]

# 2. artifacts 不设过期：存储月月涨。永远显式写 expire_in
artifacts:
  expire_in: 1 week

# 3. only/except 与 rules 混用：同一 job 两个都写，rules 胜出，only 被忽略
#    新项目统一用 rules；迁移期逐 job 替换，不要并行两套

# 4. flaky test：网络/时序导致的偶发失败
#    先重试兜底（retry: max: 2, when: [runner_system_failure, stuck_or_timeout_failure]）
#    再把 flaky 测试隔离到 nightly 流水线，建 flaky 看板逐周清零
#    重试是绷带不是解药——掩盖真实 bug 的团队走不远

# 5. docker build 慢/权限乱：dind 需要 privileged runner；
#    更快更安全：挂宿主 docker.sock（信任前提）或用 kaniko/buildah 免 daemon 构建

# 6. secret 出现在 MR 流水线日志：fork MR 可能访问变量
#    protected variable + protected branch，fork 的 MR 默认拿不到敏感变量
CI 系统本身就是生产系统：它能改你的代码、碰你的密钥、推你的镜像。被攻陷的 CI = 全线失守。安全基线：① runner 与源码仓库网络隔离；② 凭据最小权限 + 短周期；③ CI_JOB_TOKEN 范围最小化；④ 审计日志（谁改了什么流水线）接 SIEM；⑤ 第三方 action/组件固定版本，警惕供应链投毒。
排坑

十个线上坑

1
Jenkins 磁盘三个月爆满
workspace、artifacts、构建历史不清理。buildDiscarder + cleanWs() + expire_in 三件套必须写进模板，不是运维事后打扫。
2
两个部署 job 并发，环境被改乱
同一个 deploy job 忘记 disableConcurrentBuilds()，或跨 job 共享测试环境。部署类 job 一律禁并发，共享环境用 lockable-resources。
3
共享库引用 @master
库升级后所有仓库同时变化，半夜全线构建失败，回滚都不知道回哪。固定 git tag 版本，升级走灰度。
4
密码硬编码在 Jenkinsfile 或 .gitlab-ci.yml
文件进 git = 密码进 git 历史，删提交也删不掉。凭据进 credentials store / CI Variables，流水线只引用 ID。
5
flaky test 靠重试掩盖
retry: 2 让流水线变绿，但 bug 进了生产。重试只兜系统级抖动，测试代码的 flaky 要隔离 + 修复 + 看板清零。
6
GitLab cache 设计成按分支做 key
每个 MR 一套缓存，命中率 0，反而更慢。key 绑定依赖清单文件（package-lock.json），内容没变就复用。
7
artifacts 不设 expire_in
产物无限期占用 GitLab 存储，费用和备份体积一起涨。显式 expire_in: 1 week，需要留存的进制品库而不是 artifacts。
8
Jenkins 直接暴露公网
匿名用户可创建 job、可执行 Groovy 脚本 = 远程代码执行。内网 + 反向代理 + 认证是底线，脚本沙箱别关。
9
controller 升级不升 agent
remoting 版本不兼容，agent 集体掉线，构建全排队。滚动升级顺序：先 agent，后 controller，留一个兼容窗口。
10
部署重新构建镜像而不是晋级制品
"staging 验证过的镜像"和"prod 的镜像"不是同一个，玄学 bug 诞生。构建一次，按环境改 tag 晋级，commit SHA 是全链路唯一身份。
自测

六道题

1. GitLab CI 中 cache 和 artifacts 的核心区别是？
正确答案：用途与存储位置不同。cache 是"依赖加速"，存 Runner 本地、分布式下不保证命中；artifacts 是"产物传递"，存 GitLab、有 expire_in、下游 job 可下载。把构建产物放 cache 是最常见误用。
2. Jenkins 共享库应该怎么引用？
正确答案：固定 tag。浮动引用会让所有仓库随库升级同时变化，故障面瞬间放大且无法定位。升级 = 逐仓库改引用号 + 各自验证 + 有问题单独回滚。
3. 声明式流水线（pipeline { }）相比脚本式的主要优势是？
正确答案：结构与可维护性。声明式有固定骨架和语法校验，出错信息友好，Blue Ocean 可视化直接支持。脚本式更自由但容易写出没人敢动的"祖传 Jenkinsfile"。
4. GitLab CI 里想让 build 一完成 deploy-prep 就立刻开始（而不是等 build 阶段所有 job 都结束），应该用？
正确答案：needs 声明依赖。默认按 stage 串行：build 阶段全部结束才进下一阶段。needs 让 GitLab 按 DAG 只等待真正依赖的 job，build 一完成 deploy-prep 立即启动，大流水线通常能省 30%~60% 时间。
5. 防止同一 Jenkins job 的两个构建同时操作部署环境，最直接的做法？
正确答案：disableConcurrentBuilds()。加 executor 反而更乱；sleep 是竞态赌博。跨 job 争抢同一环境时，用 lock(resource: 'env') 把临界区锁起来。
6. 关于 CI 中的 flaky test，正确的处理姿势是？
正确答案：兜底 + 隔离 + 清零。无脑重试是把 bug 放大到生产；删测试是销毁安全网。系统性做法：retry 只兜 runner 级抖动，测试级 flaky 隔离后限期修复。

关键配置项

# Jenkinsfile 选项模板（直接抄）
options {
  timeout(time: 30, unit: 'MINUTES')
  buildDiscarder(logRotator(numToKeepStr: '20', artifactNumToKeepStr: '5'))
  disableConcurrentBuilds()
  timestamps()
}
post { always { cleanWs() } }

# .gitlab-ci.yml 健康默认值
default:
  interruptible: true
  retry:
    max: 2
    when: [runner_system_failure, stuck_or_timeout_failure]   # 只重试系统级失败
cache:
  key:
    prefix: deps
    files: [package-lock.json]
  paths: [node_modules/]
artifacts:
  expire_in: 1 week
  when: on_success

术语一句话解释
ControllerJenkins 主节点，负责调度、配置与 UI（旧称 master）
AgentJenkins 执行节点，实际干构建的机器（旧称 slave）
ExecutorAgent 上的并行构建槽位，决定同时跑几个 job
Jenkinsfile流水线即代码的定义文件，声明式或脚本式
声明式流水线固定骨架的 pipeline 语法，有校验和可视化
脚本式流水线自由 Groovy 的 node 语法，灵活但难维护
共享库跨仓库复用的 Jenkins 步骤库，按 tag 版本引用
凭据 storeJenkins 加密保存密码/密钥的地方，按 ID 引用
buildDiscarder构建历史与产物的保留策略，磁盘治理核心
RunnerGitLab CI 的执行器，主动领活，可选 shell/docker/k8s 等
Executor（GitLab）Runner 的运行方式（docker、shell、kubernetes 等）
cache同项目 job 间的依赖/编译加速数据，存 Runner 本地
artifacts传递给下游 stage 或供人下载的产物，存 GitLab 服务端
needs声明 job 间依赖，把流水线从阶段串行改成 DAG 调度
rulesGitLab CI 的条件规则，决定 job 是否进流水线（替代 only/except）
protected environment受保护的部署环境，只允许指定角色触发，生产标配
GitLab Pages用 artifacts 里的 public/ 目录直接发布静态站点
制品晋级同一 commit 构建的镜像按环境打 tag 推进，不重新构建
flaky test偶发失败的非确定性测试，靠重试掩盖等于埋雷
dindDocker-in-Docker，CI 里跑 docker build 的 sidecar 方案
