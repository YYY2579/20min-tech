二十分钟理解 Kubernetes

K8s 概念多、名词吓人，但骨架只有一句话：你声明期望状态，它负责让现实向期望靠拢。这份文档就围绕这一句展开。

20:00
别试图一次记住所有名词 —— 先抓住那一条主线，剩下的都是它的展开。
开始前

前置条件与练习环境

你需要先会 Docker。K8s 是"管理容器的系统"，不懂镜像和容器的话，这份文档会处处卡壳。如果还没学，先看本系列第 2 期《十分钟理解并学会 Docker》。

怎么搞到一个能练的集群

你不需要真的买服务器。三种方式，按省事程度排序：

方式说明
在线沙盒（最省事）浏览器搜 "killercoda kubernetes" 或 "play with kubernetes"，打开就是一个现成的集群，命令行直接能用，不用装任何东西
Docker Desktop设置里勾选 Enable Kubernetes，等它跑起来，你的电脑上就有一个单节点集群了
minikube / kind命令行工具，minikube start 或 kind create cluster，适合长期练习

先认识一个工具：kubectl（读作 cube-control）是装在你自己电脑上的命令行工具，用来和集群对话。注意它不在集群里 —— 你不需要登录任何服务器，敲命令，它通过网络把指令发给集群。本文所有以 kubectl 开头的命令，都是在你自己电脑的终端里敲的。

装好后验证：

kubectl version --client
kubectl get nodes      # 能看到一个 Ready 的节点就成功了
本文出现的所有术语，文末都有一张术语表。K8s 的名词密度很高，看不懂随时翻到最后。
0-2 分钟

它到底在解决什么问题

上一期你学会了用 Docker 跑一个容器。现在把规模放大一百倍。

假设你有 100 台服务器、要跑 1000 个容器。那么下面这些问题，Docker 一个都答不上来：

  • 某个容器半夜挂了，谁来自动重启它？
  • 流量涨了要扩到 20 个副本（副本 = 同一份应用的多个相同实例），谁来启动这 20 个、并把流量分发过去？
  • 要发布新版本，怎么做到不中断服务地逐步替换？出问题怎么一键回滚？
  • 100 台机器，哪个容器该放哪台？怎么知道哪台还有余量？
  • 容器重启后 IP 变了，其他服务怎么还能找到它？
K8s 就是回答这些问题的。一句话定位：它是数据中心的操作系统 —— Docker 管一个容器，K8s 管一整个集群的容器。

它自己不跑容器，它只是指挥：告诉各台机器上的代理该跑什么、该停什么、流量该往哪走。
2-5 分钟

灵魂：声明式与控制循环

这是整份文档最重要的一节。理解了它，K8s 剩下的部分都是自然推论。

命令式 vs 声明式

方式打车类比在 K8s 里的样子
命令式告诉司机"前面路口左转，再直行 200 米……"docker run：我命令你启动一个容器
声明式告诉司机"我要去天安门"，怎么走他自己决定kubectl apply：我要 3 个副本，怎么实现你自己决定

K8s 选了后者。你写一份 YAML 描述"我期望的样子"，提交给集群，然后就不管了。

它凭什么能"不管"

因为集群里有一群叫控制器（Controller）的程序，它们在做一件很笨但很有效的事：

读取期望状态。从存储集群状态的数据库（etcd）里，读出你声明的"我要 3 个副本"。
读取实际状态。去看一眼现在集群里真的跑着几个。
对比。期望 3 个、实际 2 个，差 1 个。
修正。那就再启动一个。然后回到第一步，永远循环。
这个循环就是"自愈"的全部秘密。容器挂了、节点宕机了、你手动删了一个 Pod —— 都只是让"实际状态"偏离了"期望状态"，控制器下一轮就会把它拉回来。

所以：你永远不需要写"如果挂了就重启"这种逻辑。你只需要声明你想要什么。
由此推出一个新手必踩的坑：直接修改一个正在运行的 Pod，改了会发现过一会儿又变回去了 —— 因为它是被 Deployment 管理的，控制器发现实际状态和期望不一致，就把它重建了。要改，就改 Deployment。
5-9 分钟

四个核心对象

K8s 有几十种对象，但日常 90% 的工作只涉及这四个。

Pod —— 最小的调度单位

K8s 不直接管理容器，而是管理 Pod。一个 Pod 里可以有一个或多个容器，它们共享网络和存储，像住在一个房间里。

新手疑问：为什么不能直接管容器？因为有时候两个进程必须待在一起（比如主应用 + 日志收集侧车），必须共享同一个网络命名空间。Pod 就是为这种"必须在一起"的场景准备的最小单元。日常你只需要记住：一个 Pod 通常放一个容器。
Pod 是易耗品。它随时可能被删掉重建，重建后 IP 会变、名字会变。所以绝对不要直接依赖 Pod 的 IP。那怎么办？往下看 Service。

Deployment —— 管副本数和发布

你不直接创建 Pod，而是创建 Deployment，由它去创建和管理 Pod。它负责三件事：

  • 副本数：始终保持你要求的 Pod 数量
  • 滚动更新：换镜像时逐个替换，服务不中断
  • 回滚：新版出问题，一条命令退回上一版

中间其实还有一层叫 ReplicaSet（负责保证"有 N 个 Pod 在跑"），Deployment 管 ReplicaSet，ReplicaSet 管 Pod。日常你不用管 ReplicaSet，但 kubectl get all 时会看到它。

Service —— 给 Pod 一个稳定入口

这是新手最困惑的对象，但它的存在理由极其简单：

Pod 的 IP 会变。今天 3 个副本的 IP 是 A、B、C，明天重启后变成 D、E、F。如果别的服务写死了 IP，立刻就挂了。

Service 就是解决这个的：它给一组 Pod 一个永远不会变的虚拟 IP 和域名，内部自动把请求转发到当前活着的 Pod 上。

类型用途
ClusterIP（默认）只在集群内部可访问。集群内的其他服务用它互访
NodePort在每个节点上开一个端口，供集群外部访问。练习时最常用
LoadBalancer向云厂商申请一个真实负载均衡器。生产环境用，要花钱

Service 怎么知道该转发给哪些 Pod？靠 label（标签）。你给 Pod 打上 app: web 标签，Service 的 selector 写 app: web，两者就匹配上了。这就是 K8s 里所有对象互相"找到对方"的通用机制。

Namespace —— 逻辑隔离

把集群从逻辑上切成若干块，比如 dev / test / prod。不同 Namespace 里的同名资源互不冲突。kubectl get pods -n dev 就是指定看哪个命名空间。

四个对象的关系

Deployment  # 你写的，声明副本数和镜像
   └── ReplicaSet  # 自动生成，保证数量
          ├── Pod 1
          ├── Pod 2
          └── Pod 3
                 ↑
             Service  # 按 label 选中这组 Pod，提供稳定入口
9-12 分钟

集群里都住着谁

这节是"了解"级别，知道每个组件负责什么就行，不用记细节。

控制面（Control Plane）—— 大脑

组件职责
kube-apiserver唯一入口。你敲的每条 kubectl 命令、集群里所有组件之间的通信，全都经过它。所有操作都要先问它
etcd存整个集群的状态，包括你声明的期望状态。它挂了集群就失忆，所以生产环境必须备份
kube-scheduler决定新 Pod 放到哪个节点上。它看每个节点还剩多少资源，以及你设的约束规则（比如"这个 Pod 只能放在有 SSD 的节点上"，这类规则叫亲和性）
kube-controller-manager跑着一大堆控制器，前面说的"控制循环"就在这里。Deployment 控制器就在这

工作节点（Node）—— 干活的

组件职责
kubelet节点上的"工头"。收到"在这台机器上跑一个 Pod"的指令，就去调用容器运行时把它跑起来，并持续汇报状态
kube-proxy实现 Service 的网络转发规则，让虚拟 IP 真正能把流量导到 Pod
容器运行时真正执行"跑容器"这个动作的（如 containerd）。这一层就是上一期学的 Docker 的底层
一句话串起来：你写 YAML → 提交给 apiserver → 存进 etcd → controller-manager 发现少了 Pod，创建它 → scheduler 决定放哪个节点 → 该节点的 kubelet 收到指令，让容器运行时跑起来 → kube-proxy 配好网络转发。全程你只写了一份 YAML。
12-15 分钟

写第一个 YAML

K8s 里所有东西都用 YAML 描述。YAML 就是一种用缩进表示层级的纯文本格式（表达能力和 JSON 类似，但更适合手写），没有花括号，全靠空格缩进体现从属关系。

别怕，格式高度规律，四个字段几乎固定：

字段含义
apiVersion用哪个版本的 API 来描述这个对象（照抄即可）
kind你要创建的是什么类型的东西 —— Deployment？Service？
metadata元信息：名字、标签、属于哪个命名空间
spec最重要的部分：你期望它长什么样。所有具体配置都写在这

Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3                # 我要 3 个副本
  selector:
    matchLabels:
      app: web               # 它管的是带 app=web 标签的 Pod
  template:                   # 以下就是 Pod 的模板
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:alpine
        ports:
        - containerPort: 80     # 容器里 nginx 监听的端口
        resources:
          limits:
            memory: "128Mi"
            cpu: "500m"

两个新手看不懂的写法：128Mi 表示内存 128 兆字节（Mi 和 MB 几乎一样）；500m 表示 CPU 半个核（m 是 millicore，1000m = 1 核）。resources.limits 是给这个容器设的资源上限，超出会被限制或杀掉 —— 第 17 分钟会再提到它的重要性。

YAML 两条铁律：① 缩进必须用空格，绝不能用 Tab，用 Tab 一定报错。② 层级靠缩进表示，缩进错了语义就全变了，而且报错信息往往很含糊。建议用支持 YAML 高亮的编辑器。

Service

apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: NodePort
  selector:
    app: web               # 关键！必须和 Pod 的 label 完全一致
  ports:
  - port: 80                  # Service 自己的端口，集群内访问 web-svc:80
    targetPort: 80            # 转发到 Pod 的哪个端口
    nodePort: 30080           # 节点上对外开放的端口，集群外访问用

四个端口，一次讲清（新手最大卡点）

外部用户访问 节点IP:30080
        ↓  nodePort —— 每个节点上开的端口，范围 30000-32767
   Service (web-svc)
        ↓  port —— Service 自己的端口，集群内其他服务访问 web-svc:80
        ↓  targetPort —— 转发到 Pod 的哪个端口
      Pod
        ↓  containerPort —— 容器里应用真正监听的端口
    容器内的 nginx
记忆法：数据从外往里流 —— nodePort（最外层，节点）→ port（Service 层）→ targetPort（Pod 层）→ containerPort（容器层）。targetPort 和 containerPort 通常一样，所以新手主要记 nodePort 和 port 的区别就够了。

提交并观察

kubectl apply -f app.yaml
kubectl get pods
kubectl get svc
# 不想暴露端口的话，临时映射到本地最方便：
kubectl port-forward svc/web-svc 8080:80
15-17 分钟

排障三板斧

K8s 排障比 Docker 简单，因为顺序是固定的。任何问题都按这三步走，不要跳。

第一步：看状态。kubectl get pods —— 状态栏写着什么？这是最重要的线索。
第二步：看事件。kubectl describe pod 名字 —— 拉到底部的 Events 区域。调度失败、镜像拉取失败、健康检查（探针）失败，原因都写在这里。
第三步：看日志。kubectl logs 名字 —— 前面两步都正常，说明是应用自己报错，看日志。

状态码速查（看到就知道往哪查）

状态含义与常见原因
Pending还没被调度到节点。通常是节点资源不够（内存或 CPU 被占满），或你设的调度约束没有节点能满足
ContainerCreating正在准备：拉镜像、挂载卷。停太久多半是镜像太大或存储有问题
ImagePullBackOff镜像拉不下来。镜像名拼错、tag 不存在、私有仓库没配密钥、网络不通
CrashLoopBackOff容器反复启动又退出。说明镜像能拉下来、能启动，但应用自己崩了 —— 去 kubectl logs 看
Running正常运行。注意：Running 不代表健康，还要看 READY 列的 1/1
Terminating正在删除。卡很久通常是卡在存储卷卸载上，或者还有控制器没处理完清理逻辑
OOMKilled内存超过 limits 被系统杀掉。调大 resources.limits.memory 或排查内存泄漏
CrashLoopBackOff 和 ImagePullBackOff 的区别，记住这个就不会白折腾：
ImagePull = 连镜像都没拿到 → 问题在配置（名字、权限、网络）。
CrashLoop = 镜像拿到了、跑起来了，但应用自己退出了 → 问题在应用（配置、依赖、启动命令）。

其他常用排障命令

kubectl get pods -o wide多显示 Pod 的 IP 和所在节点
kubectl get events --sort-by=.lastTimestamp按时间看集群最近发生了什么
kubectl exec -it Pod名 -- sh进容器里排查，注意 Pod 名后面要有两个横杠
kubectl logs -f Pod名 --previous看上一次崩溃前的日志（容器重启后就看不到了，加 --previous）
17-20 分钟

配置、存储，和六个坑

配置与密钥

别把配置写死在镜像里 —— 那样同一个镜像就没法在测试环境和生产环境通用。

对象用途
ConfigMap存普通配置：配置文件、环境变量。以明文存储
Secret存敏感信息：密码、Token、证书。内容是 base64 编码的（注意：编码不等于加密，生产环境要开静态加密）
kubectl create configmap app-config --from-literal=ENV=prod
kubectl create secret generic db-secret --from-literal=password=123456

然后在 Pod 里引用它们：

env:
- name: APP_ENV
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: ENV

存储：Pod 重建了数据怎么办

和 Docker 一样，Pod 里的数据随 Pod 一起销毁。持久化要用 Volume，而在集群里通常还要经过一层 PVC（持久卷声明） —— 你可以把它理解成"我要 10G 存储"的申请单，系统自动去找一块符合条件的存储给你。

记忆：ConfigMap / Secret 解决"配置从哪来"，Volume / PVC 解决"数据存哪去"。这两个问题在 Docker 里也遇到过 —— 概念是通的。

六个必踩的坑

1
直接改 Pod，改完又变回去了
Pod 由 Deployment 管理，控制器会把它拉回期望状态。改 Deployment，或者改 YAML 后重新 apply。
2
Service 选不到 Pod，访问直接超时
九成是 label 对不上。Service 的 selector 必须和 Pod 的 labels 完全一致（包括大小写）。用 kubectl describe svc 看 Endpoints 是不是空的。
3
端口搞混，怎么都访问不到
nodePort / port / targetPort / containerPort 四个端口含义不同，回头再看那一节。
4
不写 resources.limits
一个失控的 Pod 可能吃光整个节点的内存，把同节点上其他服务一起拖死。任何上生产的 Pod 都必须设 limit。
5
镜像用 :latest 或不写 tag
滚动更新时无法判断该不该拉新镜像，回滚也说不清回滚到哪一版。永远用明确的版本号。
6
把数据库直接跑在 Deployment 里
有状态服务（数据库、消息队列）需要稳定的存储和身份，应该用 StatefulSet，并且存储必须走 PVC。用 Deployment 跑数据库，重启一次数据就悬了。
自测

五道题，检验是不是真懂了

1. 你手动删掉了一个被 Deployment 管理的 Pod，会发生什么？
正确答案：自动补回来。这就是控制循环的作用 —— 期望 3 个、实际 2 个，差 1 个就补 1 个。整个过程你什么都不用做。
2. 为什么不能直接依赖 Pod 的 IP 地址？
正确答案：Pod 重建后 IP 会变。所以要用 Service 给一组 Pod 一个固定的虚拟 IP 和域名，由它来做转发。
3. Pod 状态是 CrashLoopBackOff，说明什么？
正确答案：应用自己反复崩溃。镜像拉取失败是 ImagePullBackOff；资源不足是 Pending。CrashLoop 说明问题在应用层，去 kubectl logs 看日志。
4. Service 靠什么找到它该转发给哪些 Pod？
正确答案：靠 label 标签。这是 K8s 里所有对象互相发现对方的通用机制。label 写错是最常见的"Service 访问不通"原因。
5. 在 K8s 里，"声明式"指的是什么？
正确答案：描述期望状态，由控制器负责达成。用 YAML 只是形式，核心在于"你不管过程，只管结果"。这也正是自愈能力的来源。
