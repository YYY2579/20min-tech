开始前

Helm 是什么，解决什么问题

一个微服务上 K8s 需要十几个 YAML：Deployment、Service、Ingress、HPA、ConfigMap、Secret……直接 kubectl apply 的问题：没有版本概念、没有回滚、多环境靠复制粘贴、变量靠 sed。Helm 把这一堆 YAML 打包成 Chart（包），安装成一个 Release（发布实例），支持升级、回滚、值覆盖。

概念类比说明
Chartapt 的 .deb 包一个目录/压缩包，含模板 + 默认值 + 元数据
Release已安装的软件实例同一个 chart 装两次 = 两个 release，互不影响
Repositoryapt 源存放 chart 的索引，也可以是 OCI Registry
Values安装参数覆盖模板里的默认值，实现一套模板多环境
# 版本说明：本文基于 Helm 3.x（2019 年后主流，无 Tiller）
helm version

# 快速体验：创建一个官方脚手架 chart
helm create myapp
cd myapp && tree -L 2
# myapp/
# ├── Chart.yaml          元数据：名称、版本、appVersion
# ├── values.yaml         默认值
# ├── charts/             依赖的子 chart
# ├── templates/          模板目录（*.yaml + _helpers.tpl）
# └── .helmignore

# 本地渲染看看输出，不真正安装
helm template myapp ./myapp

# 安装 / 查看 / 卸载
helm install myapp ./myapp -n default
helm list -n default
helm uninstall myapp -n default
模块 1

Chart 结构与核心文件

Chart.yaml（包元数据，必填）

# Chart.yaml
apiVersion: v2            # Helm 3 用 v2；v1 是 Helm 2 遗留格式
name: webapp              # chart 名，必须与目录名一致
description: Web application Helm chart
type: application         # application（默认）或 library（只提供模板，不安装）
version: 1.4.2            # chart 自身版本，每次改模板必须 +1
appVersion: "2.17.0"      # 被部署应用的版本，升级镜像改这里
kubeVersion: ">=1.24.0"   # 要求的 K8s 版本范围
dependencies:             # 声明依赖（见模块 4）
  - name: redis
    version: "17.3.1"
    repository: "https://charts.bitnami.com/bitnami"
    condition: redis.enabled

values.yaml（默认值，用户改动的入口）

# values.yaml —— 默认值要保守：副本 1、资源请求小、开关默认关
replicaCount: 1

image:
  repository: registry.example.com/webapp
  tag: ""                    # 空 = 默认用 .Chart.AppVersion
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80

ingress:
  enabled: false             # 默认关闭，按环境开启
  host: webapp.example.com

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 256Mi            # 只限内存不限 CPU 是常见实践

autoscaling:
  enabled: false
  minReplicas: 1
  maxReplicas: 10
  targetCPUUtilization: 70

templates/ 目录命名约定

文件作用
deployment.yaml工作负载模板，文件名即资源名（小写复数）
service.yaml / ingress.yaml / hpa.yaml与 K8s 资源一一对应
_helpers.tpl以下划线开头 = 不渲染成 K8s 资源，只定义可复用模板片段
NOTES.txt安装完成后打印给用户的提示信息（不是 K8s 资源）
tests/test-connection.yamlhelm test 用的测试 Pod
模块 2

模板语法：Go Template

Helm 用 Go 的 text/template。核心心智模型：模板 + Values = 最终的 YAML。所有魔法都是 {{ }} 里的表达式。

内置对象（模板里最常用的变量）

对象含义
.Valuesvalues.yaml + 用户覆盖后的值，如 .Values.replicaCount
.ChartChart.yaml 内容，如 .Chart.Name、.Chart.AppVersion
.Release本次发布信息：.Release.Name（安装名）、.Release.Namespace、.Release.IsInstall、.Release.IsUpgrade、.Release.Revision
.Capabilities集群能力：.Capabilities.KubeVersion（可写 if 判断兼容旧集群）、.Capabilities.APIVersions
.Template当前模板信息：.Template.Name、.Template.BasePath

控制结构与空白控制

# if / else if / else
{{- if .Values.ingress.enabled }}
apiVersion: networking.k8s.io/v1
kind: Ingress
...
{{- end }}

# with：把上下文切进去，里面直接用 .field
{{- with .Values.resources }}
resources:
  {{- toYaml . | nindent 12 }}
{{- end }}

# range：遍历列表/字典
{{- range .Values.extraEnv }}
- name: {{ .name }}
  value: {{ .value | quote }}
{{- end }}

# 变量赋值，避免在 with/range 里丢失外层上下文
{{- $name := include "webapp.fullname" . }}
...
{{- with .Values.resources }}{{ $name }}...{{ end }}
{{- 和 -}} 是空白修剪符：去掉标签前后产生的空行。不加 - 的话，每个 if 块都会在 YAML 里留下空行甚至缩进错位 —— 这是新手模板报错的第一大来源。规律：块级控制语句一律用 {{- ... }}。

常用内置函数与管道

函数作用
quote / squote加双引号 / 单引号，防止 YAML 把 123、true 解析成数字/布尔
default.Values.x | default "fallback"，值为空时用默认值
trunc 63 / trimSuffix "-"截断到 63 字符 / 去后缀，配合资源名长度限制（见模块 8）
upper / lower / title大小写转换
replace / contains / hasPrefix字符串替换、包含判断、前缀判断
b64enc / b64decBase64 编解码（Secret 场景）
toYaml / toJson把对象转成 YAML/JSON 文本，配 nindent 缩进
nindent N / indent N先换行再缩进 N 空格 / 只缩进 N 空格
required "msg"值为空时直接报错退出，用于强制必填项
lookup查询集群现有资源（helm template 时返回空，慎用）
tpl把字符串当模板再渲染一次，用于 values 里传模板
semverCompare语义化版本比较，如判断 .Capabilities.KubeVersion
# 管道的本质：左边的输出，作为右边函数的最后一个参数
{{ .Values.image.tag | default .Chart.AppVersion | quote }}
# 等价于：quote(default(.Values.image.tag, .Chart.AppVersion))

include / tpl 与 _helpers.tpl（官方脚手架写法）

# templates/_helpers.tpl
{{- define "webapp.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" -}}
{{- end -}}

{{- define "webapp.fullname" -}}
{{- if .Values.fullnameOverride -}}
{{- .Values.fullnameOverride | trunc 63 | trimSuffix "-" -}}
{{- else -}}
{{- $name := include "webapp.name" . -}}
{{- if contains $name .Release.Name -}}
{{- .Release.Name | trunc 63 | trimSuffix "-" -}}
{{- else -}}
{{- printf "%s-%s" .Release.Name $name | trunc 63 | trimSuffix "-" -}}
{{- end -}}
{{- end -}}
{{- end -}}

{{- define "webapp.labels" -}}
app.kubernetes.io/name: {{ include "webapp.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
helm.sh/chart: {{ printf "%s-%s" .Chart.Name .Chart.Version }}
{{- end -}}
define 与 include 的区别：define 定义命名模板（不在文件系统里输出）；template 可以引入但不能传管道；include 既能引入又能作为管道使用，所以 define + include 是唯一推荐组合。tpl 则是把"字符串"当模板二次渲染，比如 values 里允许用户传 hostname: "{{ .Release.Name }}.example.com"。

一个完整的 Deployment 模板（官方风格）

# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "webapp.fullname" . }}
  labels:
    {{- include "webapp.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app.kubernetes.io/name: {{ include "webapp.name" . }}
      app.kubernetes.io/instance: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app.kubernetes.io/name: {{ include "webapp.name" . }}
        app.kubernetes.io/instance: {{ .Release.Name }}
    spec:
      containers:
        - name: webapp
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag | default .Chart.AppVersion }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - name: http
              containerPort: {{ .Values.service.port }}
              protocol: TCP
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
          env:
            {{- range .Values.extraEnv }}
            - name: {{ .name }}
              value: {{ .value | quote }}
            {{- end }}
          {{- with .Values.resources }}
          resources:
            {{- toYaml . | nindent 12 }}
          {{- end }}
模块 3

值管理：多环境与覆盖优先级

一套 chart 服务 dev/test/prod 的关键：把所有环境差异都收进 values，模板里零 if 环境判断。

值来源优先级（从低到高，后者覆盖前者）

层级来源说明
1chart 内 values.yaml打包时的默认值
2父 chart 的 values.yamlumbrella chart 给子 chart 传值（见下）
3-f values-prod.yaml用户自定义文件，多个 -f 按顺序后者覆盖前者
4--set key=val命令行最高优先级，适合 CI 注入少量值
# 目录组织：一套模板 + N 个环境文件
myapp/
├── values.yaml            # 默认值（贴近开发/最小化）
├── values-dev.yaml        # 副本 1，ingress 关，log level debug
├── values-staging.yaml    # 副本 2，ingress 开，接测试域名
└── values-prod.yaml       # 副本 3，HPA 开，资源 limits 调大

# 安装时指定环境文件（可多个 -f，后者覆盖前者）
helm install webapp ./myapp -f values-prod.yaml -n prod

# --set 的三种写法
helm install webapp ./myapp \
  --set replicaCount=3 \
  --set image.tag=v2.17.0 \
  --set ingress.enabled=true \
  --set resources.requests.cpu=250m

# --set 特殊语法：
--set 'env[0].name=DEBUG,env[0].value=1'     # 数组
--set 'tags={web,api}'                       # 花括号会被 shell 吃掉，必须整体加引号
--set-file config=/path/to/file.conf        # 从文件读内容（大文本/证书）
--set-json 'labels={"team":"pay"}'          # JSON 形式设置
生产环境建议：环境差异用 -f 文件管理并入库，--set 只留给 CI 的少量动态值（如镜像 digest）。全用 --set 的命令会变成没人看得懂的 500 字符咒语，且没有版本记录。

子 chart 的值传递

# 场景：父 chart webapp 依赖子 chart redis
# 父 chart values.yaml 里，用"子 chart 同名 key"覆盖子 chart 的值
redis:
  enabled: true              # condition 开关（见模块 4）
  architecture: standalone
  auth:
    enabled: false
  master:
    persistence:
      size: 1Gi

# global 是特例：会下传给所有子 chart，无需逐层指定
global:
  imagePullSecrets:
    - name: registry-cred
  storageClass: fast-ssd
最经典的 Helm 困惑：改了子 chart 目录里 values.yaml 没用。覆盖规则是"父 chart 的 values 优先"，子 chart 自带的 values.yaml 只是它的默认值。正确做法是在父 chart values.yaml 里写 redis.xxx 覆盖，或者临时调试用 helm template --set redis.auth.enabled=false。
模块 4

依赖管理与 Umbrella Chart

依赖声明在 Chart.yaml 的 dependencies 字段，安装时 Helm 自动把子 chart 拉进 charts/ 目录并一起渲染。

# Chart.yaml 声明依赖
dependencies:
  - name: redis                       # 子 chart 名
    version: "17.3.1"                 # 语义化版本范围，^17.3.0 = 17.x.x
    repository: "https://charts.bitnami.com/bitnami"
    condition: redis.enabled          # 可选：用 values 里的键控制是否安装
    tags:                            # 可选：用 tag 批量控制
      - database
  - name: common                      # library 类型 chart 也可作依赖
    version: "2.x.x"
    repository: "https://charts.bitnami.com/bitnami"
helm dependency update ./myapp拉取依赖到 charts/，并生成 Chart.lock
helm dependency build ./myapp按 Chart.lock 精确版本安装（CI 用这个，保证可复现）
helm dependency list ./myapp查看依赖状态（OK / missing）

Umbrella（父）chart 模式

把一个完整系统拆成多个子 chart（前端、后端、数据库、缓存），再用一个父 chart 组装，父 chart 负责：统一命名、共享 global 值、统一开关。适合 10+ 服务的团队，但别过度设计：3 个服务以内单 chart 更省心。

文件作用
Chart.lock锁定依赖精确版本，必须提交 Git，保证团队/CI 装同一版本
charts/*.tgz拉下来的子 chart 包。不要提交 Git（可在 .gitignore 忽略），CI 里 build
condition依赖开关字段，如 redis.enabled=false 则不安装 redis
import-values进阶：把子 chart 的值导入父 chart（少用，调试困难）
Chart.lock 与可复现性：version 写 ^17.3.0 时，update 可能拉到 17.9.0；lock 记录的就是这次实际拉的版本。团队协作和 CI 一律用 helm dependency build（按 lock 装），只有升级依赖时才 update 并提交新 lock。
模块 5

Hooks：在生命周期节点做动作

数据库迁移、缓存预热、通知 Webhook 这些"安装/升级前后要做的事"，用 Hook 注解实现。Hook 资源带 helm.sh/hook 注解，Helm 在对应时机创建它，并单独跟踪其状态。

Hook 类型触发时机
pre-install模板渲染后、资源创建前
post-install所有资源创建成功后
pre-delete卸载任何资源之前
post-delete卸载完成后
pre-upgrade升级前（可用来做备份、schema 检查）
post-upgrade升级成功后（可用来发通知）
pre-rollback / post-rollback回滚前 / 后
testhelm test 时触发（用 helm.sh/hook: test）

Job 型 Hook 完整示例（数据库迁移）

# templates/job-migrate.yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "webapp.fullname" . }}-migrate
  labels:
    {{- include "webapp.labels" . | nindent 4 }}
  annotations:
    "helm.sh/hook": pre-upgrade,pre-install
    "helm.sh/hook-weight": "5"          # 同阶段多 hook 按权重从小到大执行
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: "{{ .Values.image.repository }}:{{ .Chart.AppVersion }}"
          command: ["./migrate.sh"]
# hook-weight 常见分配：
# -5 备份 / 0 默认 / 5 迁移 / 10 预热 / 15 通知
hook-delete-policy行为
before-hook-creation下次执行同类 hook 前，先删掉上一次残留的资源（防重名冲突，几乎必配）
hook-succeededhook 成功后删除资源（不留垃圾 Job）
hook-failedhook 失败后删除（保留现场排查用，则不配）
Hook 的两个大坑：① 不配 delete-policy，第二次 helm upgrade 时 Job 重名直接报 already exists；② hook 失败默认会阻塞整个 install/upgrade，没有超时机制（Helm 3 有 --timeout 兜底但语义不直观）。幂等的 hook + before-hook-creation 是标准答案。
模块 6

Chart 测试与 Lint

Chart 质量靠三道关：lint（静态检查）、template + kubeconform（渲染 + schema 校验）、helm test（运行时验证）。

三道关卡

# 第一关：lint（静态检查命名、版本号格式、必需字段）
helm lint ./myapp --strict     --strict 把 WARNING 也当 ERROR，CI 必加

# 第二关：渲染 + K8s schema 校验（不连集群）
helm template webapp ./myapp -f values-prod.yaml > out.yaml
kubeconform -strict -summary out.yaml

# 干跑（连集群，执行渲染 + 校验，但不真正创建资源）
helm install webapp ./myapp --dry-run --debug

# 第三关：运行时验证（需要 chart 里有 test hook）
helm test webapp -n default
# 会创建带 helm.sh/hook: test 注解的 Pod，exit 0 = 通过
# templates/tests/test-connection.yaml —— 官方测试写法
apiVersion: v1
kind: Pod
metadata:
  name: "{{ include "webapp.fullname" . }}-test-connection"
  annotations:
    "helm.sh/hook": test
spec:
  containers:
    - name: wget
      image: busybox
      command: ['wget']
      args: ['{{ include "webapp.fullname" . }}:{{ .Values.service.port }}']
  restartPolicy: Never

Chart Testing（ct）：开源社区标准 CI 工具

# ct lint：按每个改动过的 chart 分别 lint + 安装到 kind 集群验证
ct lint --chart-dirs . --validate-maintainers=false

# GitHub Actions 里的典型配置
- uses: helm/chart-testing-action@v2
- run: ct lint --target-branch main
- run: ct install --target-branch main   # 真装到 kind 集群，跑 helm test

# ct 依赖一个 lint 配置文件 ct.yaml：
# chart-repos: 声明外部仓库，供依赖解析
最低配 CI 三件套（没有理由不上）：① helm lint --strict；② helm template + kubeconform 校验渲染结果；③ chart 版本号变更检测（version 不变 = 拒绝合并）。这三步能拦住 80% 的 chart 事故。
模块 7

发布到仓库：Repo 与 OCI

Chart 打包（tgz）后分发有两条路：传统 HTTP 仓库（index.yaml） 和 OCI Registry（Helm 3.8+ 原生支持）。新项目推荐 OCI：复用已有的镜像仓库、自带认证、无需维护 index.yaml。

路线一：传统仓库

# 1. 打包（产物在 ./ 下）
helm package ./myapp
# myapp-1.4.2.tgz —— 版本号取自 Chart.yaml 的 version

# 2. 生成/更新索引并推到仓库（GitHub Pages / 对象存储 / chartmuseum）
helm repo index . --url https://charts.example.com/
git add . && git commit && git push

# 3. 使用方
helm repo add myrepo https://charts.example.com
helm repo update
helm search repo myrepo/webapp --version 1.4.2
helm install webapp myrepo/webapp -f values-prod.yaml

路线二：OCI Registry（推荐）

# 1. 登录 registry（复用镜像仓库凭证）
helm registry login registry.example.com -u admin

# 2. 打包并推送（不需要 index.yaml！）
helm package ./myapp
helm push myapp-1.4.2.tgz oci://registry.example.com/charts

# 3. 使用方直接拉 OCI chart（无需 helm repo add）
helm pull oci://registry.example.com/charts/myapp --version 1.4.2
helm install webapp oci://registry.example.com/charts/myapp --version 1.4.2

# 4. 列出仓库里可用版本（Helm 3.10+）
helm show chart oci://registry.example.com/charts/myapp --version 1.4.2
helm list --all   # 注意：OCI 安装的 release 也会记录 chart 来源
维度传统 RepoOCI Registry
索引维护 index.yamlRegistry 自动管理 tag
认证仓库自己实现复用镜像仓库认证体系
版本覆盖同版本可覆盖（不推荐）tag 不可变推送，更安全
依赖解析支持（dependencies 里可写 repo）Helm 3.8+ 支持（写 oci:// 地址）
存量兼容老 chartmuseum 用户多Harbor 2.x/ECR/GHCR 都支持
版本号铁律：每次改模板必须升 Chart.yaml 的 version。同一 version 推两次，传统仓库会覆盖但客户端有缓存，OCI 直接拒绝。CI 里用 chart-testing 的版本变更检测来自动化这一步。
模块 8

升级、回滚与工程红线

升级与回滚机制

# 升级 = 同 release 名装新 chart 版本，Helm 会做 3-way merge
helm upgrade webapp ./myapp -f values-prod.yaml -n prod

# 升级即回滚的准备
helm history webapp -n prod      # 看所有 revision
helm status webapp -n prod       # 当前状态

# 回滚到上一个版本（或指定 revision）
helm rollback webapp 1 -n prod
helm rollback webapp --wait -n prod

# 失败自动回滚 + 清理（CI/CD 推荐带上）
helm upgrade webapp ./myapp --atomic --timeout 5m -n prod
# --atomic：任何一步失败自动回滚并删除 release
# --wait：等所有 Pod ready 才算成功，配合 --timeout 超时判定
# --cleanup-on-fail：升级失败时删除本次创建的新资源

63 字符与 53 字符红线

# K8s 限制：
# - label 值最长 63 字符（app.kubernetes.io/instance 等）
# - 资源名（Deployment/Service 名）最长 253，但作为 DNS 子域的前缀部分实际受 63 限制
# - Helm release 名超过 53 字符时，生成的 pod-template-hash 会撞上限

# 标准防御：helper 里统一 trunc 63
{{- define "webapp.fullname" -}}
{{- .Release.Name | trunc 63 | trimSuffix "-" -}}   # 永远不要让名字超长
{{- end -}}

# 排查：安装时报 "must be no more than 63 characters" 就是这里
# 解法：缩短 release 名，或给 values 加 fullnameOverride 覆盖
helm install w ./myapp --set fullnameOverride=web -n prod

问题解法
模板渲染慢（几分钟）减少循环层级；把静态大段内容移出模板；用 library chart 复用；拆小 chart

upgrade 后 Pod 没重建检查 template 哈希是否变化（镜像 tag 用变量，别硬编码）；加 checksum/config 注解触发滚动
重复安装锁（pending 状态）：install 中途失败或被杀，release 可能卡在 pending-install/pending-upgrade，再次 install 报 cannot re-use a name that is still in use。Helm 3 的 release 记录存在 Secret 里，解法：先 helm rollback 或 helm uninstall --keep-history 清状态，必要时手动删对应 Secret（label owner=helm,name=webapp）。
本文 10 条红线的速记版：① 模板里零环境 if；② 控制语句全带 {{-；③ 字符串值 quote；④ 默认值保守；⑤ Chart.lock 提交 Git、charts/ 不提交；⑥ hook 幂等 + before-hook-creation；⑦ 名字一律 trunc 63；⑧ 升级必带 --atomic --wait --timeout；⑨ chart 版本号必须升；⑩ CI 三道关：lint --strict + template/kubeconform + test。
模块 9

十个线上坑

1
模板改了但 Chart.yaml version 没升，helm upgrade 没反应
Helm 按 chart 版本决定是否更新，同版本升级等于没升。每次改模板必须 +1 version，CI 加版本变更检测。
2
资源名超 63 字符，直接安装失败
报 "must be no more than 63 characters"。helper 里统一 trunc 63 | trimSuffix "-"，或给长环境名用 fullnameOverride。
3
release 卡在 pending-install，提示 cannot re-use a name
上次 install 失败留下 pending 状态。先 helm rollback 或删对应 Secret 再重装，别直接换 release 名（会留下孤儿资源）。
4
升级失败后 Pod 处于半新半旧状态，服务抖半死
没加 --atomic。升级必带 --atomic --wait --timeout 5m，失败自动回滚到上一个完整 revision。
5
hook Job 第二次升级报 already exists
没配 helm.sh/hook-delete-policy。加 before-hook-creation（执行前清旧的）+ hook-succeeded（成功即删）。
6
改了子 chart 的 values.yaml 发现不生效
父 chart values 优先级更高。在父 chart values.yaml 里用子 chart 同名 key 覆盖，公共配置放 global。
7
--set 命令写了一百多行，没人敢改也进不了 git
环境差异全部进 values-{env}.yaml 文件并入库，--set 只留给 CI 注入镜像 digest 等少量动态值。
8
charts/ 目录提交了 Git，依赖冲突天天有
charts/*.tgz 加 .gitignore，只提交 Chart.lock。CI 里 helm dependency build 保证版本可复现。
9
数字/布尔值没加 quote，YAML 解析类型错乱
value: {{ .Values.port }} 渲染成 08080 或被解析成布尔。字符串统一 | quote，数字确认 YAML 语义。
10
镜像 tag 写死，改了代码 upgrade 后 Pod 不重建
template 哈希没变 K8s 不滚动。tag 用 {{ .Chart.AppVersion }} 变量，并加 checksum/config 注解让配置变更也触发滚动。
自测

六道题

1. 关于 values 覆盖优先级，正确的是？
正确答案：--set > -f 文件 > 父 chart values > 子 chart 自带 values.yaml。这也是"改了子 chart 的 values.yaml 不生效"的原因 —— 父 chart 的值优先。
2. Helm 3 中，release 的版本记录存放在哪里？
正确答案：Secret。Helm 3 去掉了 Tiller，release 信息以带 owner=helm label 的 Secret 存在命名空间里。所以 pending 卡死时可以手动删 Secret 解锁，helm rollback/history 也都基于这些记录。
3. 一个 pre-upgrade 的数据库迁移 Job，最稳妥的注解组合是？
正确答案：pre-upgrade + weight + delete-policy。迁移必须在升级前跑；weight 控制多个 hook 的顺序；before-hook-creation 防止第二次升级 Job 重名冲突，hook-succeeded 及时清理。不加 delete-policy 是升级报 already exists 的头号原因。
4. 为什么模板里 {{ include "webapp.fullname" . | trunc 63 | trimSuffix "-" }} 要截到 63？
正确答案：K8s label 值上限 63 字符。release 名很长时（如 prod-payment-service-webapp）拼接出来的名字会超限。统一在 helper 里 trunc 63 防御，这也是官方脚手架的写法。
5. CI 中安装 chart 时，应该用哪条命令保证依赖版本可复现？
正确答案：helm dependency build。update 会按语义化版本范围重新解析，可能拉到次新版；build 严格按 Chart.lock。所以 Chart.lock 必须提交 Git，charts/*.tgz 反而应该 ignore。
6. 升级时希望"任何一步失败就自动回到上一个版本"，应该加什么参数？
正确答案：--atomic。失败时自动 rollback 并删除 release。--wait 等 Pod ready 才算成功，--timeout 兜底超时判定，三者是升级三件套。--force 是强制替换资源（用于不可变字段冲突），和回滚无关。
