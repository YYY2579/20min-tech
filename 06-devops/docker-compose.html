二十分钟学透 Docker Compose

compose 文件谁都会写，但启动顺序、变量插值、卷的语义、profiles、本地与生产的行为差异才是本地开发环境天天出问题的根源。这篇按 Compose 规范讲清楚这些，以及 K8s 之前你到底需不需要 compose。

建议边看边敲：docker compose up -d 起一套 web+db 再对着拆
开始前

确认你在用 v2

# v1（docker-compose，Python 实现）已停止维护，命令带连字符的是 v1
docker compose version        # v2：插件形式，输出 Compose version v2.x.x
docker-compose --version      # v1：2016 年的产物，别再用了

# 一条命令起一套 web + db + redis，然后对着拆
docker compose up -d
docker compose ps             # 看状态、端口映射
docker compose logs -f web    # 跟日志
docker compose exec web sh    # 进容器
docker compose down           # 拆环境（注意数据卷语义，见模块 5）
先对齐两个概念：① compose 文件是声明式描述（YAML）；② compose 项目（project）是一次 up 产生的运行实体，默认项目名 = 目录名，所有资源带前缀 <项目名>_（容器 proj-web-1、网络 proj_default）。改名用 -p 或 COMPOSE_PROJECT_NAME。
模块 1

compose 文件全景：三大顶层块

一个生产可用的 compose 文件只有三个必学顶层块：services（定义每个容器）、networks（自定义网络）、volumes（命名卷声明）。看懂下面这个文件，80% 的 compose 文件你都能读。

services:
  api:
    build: .                          # 从当前目录构建（等价 build.context: .）
    ports: ["8080:8080"]             # 宿主:容器
    environment:
      # 支持 ${VAR} 插值，见模块 3
      DB_HOST: db
      DB_PASSWORD: ${DB_PASSWORD:?请在 .env 里设置 DB_PASSWORD}
    env_file: .env.api                # 或从文件读一批变量
    depends_on:
      db: {condition: service_healthy}   # 等 db 健康检查通过再启动，见模块 2
    volumes:
      - ./src:/app/src                # bind mount：源码热挂载
      - api-cache:/app/cache          # 命名卷：持久数据
    networks: [backend]
    restart: unless-stopped           # 退出后总是重启（除手动 stop）

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data   # 数据落命名卷，容器重建不丢
    healthcheck:                          # 定义"就绪"
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [backend]

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--save", "60", "1"]
    networks: [backend]

networks:
  backend: {}                      # 自定义网络，服务间可用服务名互解析

volumes:
  pgdata: {}                       # 命名卷声明，数据由 Docker 管理
  api-cache: {}
废弃的 version 字段：老 compose 文件顶部都有 version: "3.8"。Compose 规范已把它标记为废弃，v2 遇到会告警并忽略 —— 新文件不要写。规范在 github.com/compose-spec/compose-spec 持续演进，不追版本号，字段以规范为准。

两个减少重复的 YAML 原生技巧：锚点（&common 定义、*common 引用）消除复制粘贴；x- 扩展字段（如 x-logging: &default-logging）存放复用片段，compose 规范明确允许且不会报未知字段。

模块 2

启动顺序：depends_on 到底等什么

本地环境最常见的 bug：app 起来了但连不上 5432，connection refused。根因是 depends_on 短语法只保证容器创建/启动，不保证服务就绪 —— postgres 容器进程起来了，但要几百毫秒到几秒才接受连接。

写法语义
depends_on: [db]只等 db 容器 started（短语法，不推荐）
depends_on: db: condition: service_healthy等 db healthcheck 连续成功（推荐）
condition: service_completed_successfully等依赖正常退出（exit 0），适合迁移/初始化任务

三个配套机制要一起用：

  • healthcheck：test 三种形式 —— NONE（禁用）、["CMD", ...]（exec 直跑）、["CMD-SHELL", "..."]（走 shell，可用管道）。start_period 给启动宽限期（期间失败不计重试），start_interval 可让探测在启动期更密集。
  • up --wait：docker compose up -d --wait 会阻塞到所有服务 healthy（或 running），配合 --wait-timeout。CI 里等依赖就绪的标准姿势，比 sleep 30 靠谱一万倍。
  • restart 策略：no（默认）/ always / on-failure[:n] / unless-stopped。本地开发用 unless-stopped，注意 always 在手动 stop 后宿主机重启还是会拉起。
wait-for-it 是反模式：镜像里塞 wait-for-it.sh db:5432 -- python app.py 只是把"等端口通"搬进容器，端口通了服务也可能没就绪，且拖慢崩溃时的重启。正确答案是 healthcheck + depends_on + up --wait，把"就绪"定义在 compose 层，各服务无感。 
# 一次性初始化任务：跑完 migration 就退出，api 等它成功
services:
  migrate:
    build: .
    command: ["python", "manage.py", "migrate"]
    depends_on:
      db: {condition: service_healthy}
    restart: "no"          # 任务型容器绝不自动重启
  api:
    build: .
    depends_on:
      migrate: {condition: service_completed_successfully}
      db: {condition: service_healthy}
模块 3

环境变量与 .env：插值的精确规则

compose 在读取 YAML 时先在宿主机做变量插值，再把结果写进容器。语法表：

写法含义
${VAR}替换为环境变量值；未设置时替换成空串并告警
${VAR:-default}未设置或为空时用默认值
${VAR-default}仅未设置时用默认值
${VAR:?错误信息}未设置/为空时直接报错退出，密码类变量必用
$$转义成字面量 $，防插值

.env 放哪、什么时候读

  • 默认从项目目录（第一个 -f 文件所在目录）加载 .env，--env-file other.env 可换。
  • 优先级：shell 环境变量 > .env 文件。CI 里 export 一个变量就能临时覆盖，不用改文件。
  • .env 只服务于宿主机插值；容器内变量来源是 environment 和 env_file，三者别搞混。
方式是否参与宿主机插值其他要点
environment是（值里可写 ${}）覆盖 env_file 同名变量；KEY 无值 = 从 shell 透传
env_file否（文件内容原样进容器）按文件顺序读取，后者覆盖前者；不参与 build
.env本身就是插值源只影响 compose 文件解析，不会自动进容器
# .env（项目目录，务必进 .gitignore）
DB_PASSWORD=s3cr3t
COMPOSE_PROJECT_NAME=myshop

# compose 文件里
services:
  api:
    environment:
      # 容器里拿到 DB_PASSWORD=s3cr3t
      DB_PASSWORD: ${DB_PASSWORD:?missing}
      # 密码里带 $ 的写法：$$ 转义，否则 $abc 会被当变量吞掉
      APP_SECRET: pa$$w0rd
      # 数组简写等价于 - KEY=VALUE
      TZ: Asia/Shanghai
血的教训：把 .env 提交进 git 是泄露事故第一名。正确姿势：.env 进 .gitignore，仓库里只放 .env.example（所有 key + 假值），新同事 cp .env.example .env 再填真值。配合 ${VAR:?}，漏配直接启动失败，而不是服务跑起来后才报连不上。
模块 4

profiles 与多环境：一套文件管三种场景

profiles：给服务分组，按需启动

标了 profiles 的服务默认不启动，只有显式启用才起。典型用途：调试工具、压测负载、可选依赖。

services:
  api:
    image: myshop/api
    ports: ["8080:8080"]
  db:
    image: postgres:16-alpine
  adminer:                      # 数据库 Web 管理界面
    image: adminer
    ports: ["8081:8080"]
    profiles: ["debug"]          # 不启用就不起
  k6:                          # 压测
    image: grafana/k6
    profiles: ["debug", "loadtest"]   # 可属多个 profile

# 启用：命令行指定 / 环境变量指定
docker compose --profile debug up -d
COMPOSE_PROFILES=debug,loadtest docker compose up -d

一个容易忽视的规则：被启用服务依赖的服务会自动启动，哪怕它自己带着 profile。比如给 api 挂上 debug 工具做 sidecar，api 无 profile、工具有 profile，启用工具时 api 作为依赖照样起来。

多文件覆盖：dev / prod 一套基座

两种组织方式，选一：

  • 自动 override：docker-compose.yml + docker-compose.override.yml 成对存在时，后者自动合并，不用写 -f。适合"默认开发配置，个别字段覆盖"。
  • 显式 -f 顺序合并：docker compose -f base.yml -f prod.yml up -d。后者覆盖前者：标量字段后者赢；列表类字段（ports、volumes 等）按项合并。不确定合并结果时 docker compose config 直接看最终产物 —— CI 里加一步 docker compose config -q 还能做语法校验。
# docker-compose.override.yml：开发专属，全部默认加载
services:
  api:
    build: .                     # 开发时用本地构建，不用镜像
    volumes: ["./src:/app/src"]     # 挂源码热重载
    environment:
      LOG_LEVEL: debug

# prod.yml：显式传入，覆盖 override 的默认值
services:
  api:
    image: registry.myshop.io/api:1.4.2   # 生产用固定 tag，禁 latest
    environment:
      LOG_LEVEL: info
判断标准：只在本地跑、要挂源码、要带调试工具 → compose + profiles + override；要上多副本、滚动更新、服务网格、统一声明式管理 → 直接上 K8s，别硬撑（模块 6 有边界表）。
模块 5

网络与存储：compose 的两条暗线

网络：服务名就是 DNS 名

同一项目里，每个服务加入名为 <项目>_default 的默认 bridge 网络，服务名/别名可直接解析（api 里连 db:5432 即可，不用记 IP）。自定义网络可以按用途切分，一个服务可同时加入多个。

  • aliases：给服务起额外 DNS 名，做蓝绿/版本切换时流量切别名很方便。
  • external: true：接入已存在的网络（比如先 docker network create shared），配 name: 指定真实名。跨项目通信的唯一正道 —— 服务名不出项目网络。
  • network_mode：host（共享宿主网络栈，无网络隔离）、service:[name]（共享另一个服务的网络栈，sidecar 模式，如 istio 早期的 pilot-agent 形态）、none。
  • ports vs expose：ports 发布到宿主（宿主:容器）；expose 仅文档作用，不发布端口，项目内互访根本不需要 expose。

卷：三种类型，别用错

类型写法适用与风险
命名卷- pgdata:/var/lib/postgresql/data数据库/有状态服务首选。数据由 Docker 管理，容器重建不丢
bind mount- ./src:/app/src源码、配置文件。宿主任意路径直接可见，容器内改动会写回宿主
tmpfstmpfs: /tmp内存盘，敏感临时数据，重启即失

常用修饰：:ro 只读（配置卷防篡改）；:z/:Z SELinux 重新打标；macOS/Windows 上 :cached/:delegated 换一致性换性能。长语法（type: bind,source: ...,target: ...）表达力更强，复杂场景推荐。

# 跨项目共享数据库：两边用同一个 external 网络 + 同一命名卷
# 项目 A（myshop）：db 加入 shared 网络，卷声明 external
networks:
  shared: {external: true, name: shared}
volumes:
  pgdata: {external: true, name: myshop_pgdata}   # 引用其他项目已创建的卷
postgres 的 initdb 规则：官方镜像只在 PGDATA 目录为空时初始化。命名卷第一次起会初始化；以后容器重建复用该卷，不会重新初始化，你的建表脚本不会重跑 —— 所以 schema 变更要走 migration 工具，不能靠 entrypoint 脚本。
模块 6

本地开发工作流：watch、构建与边界

文件监听：docker compose watch

v2.22+ 起 develop.watch 成为标准能力：监听宿主路径，按动作分 sync（同步文件）、rebuild（重建镜像）、sync+restart。比裸 bind mount 更可控（能排除 node_modules、能指定 rebuild 触发条件）。

services:
  api:
    build: .
    develop:
      watch:
        - path: ./src          # 源码改动：同步进容器
          action: sync
          target: /app/src
        - path: ./package.json # 依赖变了：重建镜像
          action: rebuild
        - path: ./static       # 静态资源：同步并重启进程
          action: sync+restart
          target: /app/static

# 起服务并进入 watch 模式
docker compose watch
# 或 up 时带 watch
docker compose up -d --watch

构建与日常命令

docker compose build [--no-cache] [service]构建/重建镜像，Dockerfile 层缓存默认生效
docker compose up -d --build配置变了要加 --build，否则只用旧镜像起容器
docker compose config打印合并后的最终配置，排查插值/合并问题的第一现场
docker compose run --rm api pytest跑一次性命令，退出即删容器；默认会拉起依赖服务
docker compose up -d --scale api=3起多个同服务副本（端口需随机映射或走内部负载）

工程化上再包一层 Makefile / task 脚本，把 up、test、migrate、down -v 固化成 make dev，新人一天内能跑起来。

与 K8s 的边界：什么时候该换了

维度Docker ComposeKubernetes
运行位置单机（Docker 引擎）集群（多节点调度）

模块 7

compose up 与 docker stack deploy：同名不同命

compose 文件可以喂给 docker stack deploy -c xxx.yml（Swarm 模式），但两边的引擎不同，字段支持差异巨大。最大的坑：你以为配了资源限制和副本数，本地跑时它压根没生效。

字段docker compose updocker stack deploy
deploy.replicas忽略，用 --scale生效（Swarm 服务副本数）
deploy.resources.limits生效（映射为容器资源限制）生效
deploy.resources.reservations忽略生效
deploy.placement / update / rollback_config忽略生效
depends_on生效忽略并告警（Swarm 无启动顺序概念）
healthcheck生效生效（Swarm 也支持）
ports宿主端口映射ingress/published ports，需 overlay 网络
结论：别写"一份 compose 文件同时服务 compose up 和 stack deploy"。要么本地 compose + 远端 K8s（各自文件，CI 分别校验），要么全面 Swarm/K8s。docker compose config 只验证 compose 语义，不验证 Swarm 兼容性。
模块 8

十个真实坑

1
depends_on 只等 started，应用连接被拒
容器起来了 postgres 还没 listen。改成 condition: service_healthy + up -d --wait。判断标准：报错是 connection refused 而不是鉴权失败。
2
.env 提交进 git / 放错目录不生效
密码进仓库是事故；放错目录（--project-directory 之外）则插值全是空串服务起不来。.env 进 .gitignore，仓库只留 .env.example；用 ${VAR:?} 让漏配直接报错。
3
密码里的 $ 被插值吞掉
DB_PASSWORD=abc$xyz 在 environment 里写 ${DB_PASSWORD} 时，$xyz 被当成变量名解析成空。字面量美元写 $$ 转义，或者密码本身别用 $。
4
容器重建后数据没了
三种丢数据路径：用了匿名卷（down 时随容器清理）、数据写在容器可写层（重建即失）、postgres 卷已存在导致 initdb 不跑而 schema 没迁移。数据库必须命名卷 + migration 工具，别赌。
5
container_name 写死，--scale 直接冲突
container_name: api 时第二个副本起不来（名字已占用），也无法在多个项目里复用同一文件。删掉它，让 compose 用 <项目>_<服务>_<序号> 自动命名。
6
healthcheck 写法错，永远 unhealthy
test: pg_isready 这种字符串写法已废弃；管道判断（如 ps aux | grep x）必须包在 CMD-SHELL 里。先 docker exec 手动跑一遍 test 命令，确认退出码为 0 再配上去。
7
服务名跨项目/宿主机解析失败
服务名只在所属项目的网络内有效。另一个 compose 项目或宿主机进程连 api:8080 会直接 name resolution error。跨项目用 external 网络 + 固定网络名，宿主访问走 localhost:published-port。
8
bind mount 的两宗罪：root 污染 + CRLF
① 容器内进程以 root 写文件，宿主目录出现 root 属主文件（node_modules 被覆盖、git status 一片红）；② Windows 编辑的脚本带 CRLF，容器里执行报 exec format error。统一容器内 UID/GID，脚本走 LF，或只用命名卷。
9
json-file 日志不设上限，磁盘悄悄打满
默认 json-file 驱动无限增长，本地开发跑几天几个 GB 很常见。全局或按服务配 logging.options 的 max-size / max-file：单文件 10m、保留 3 个。这是从 Docker 到 compose 都适用的底线配置。
10
deploy 段配了却没用，CI 拉起整堆调试服务
deploy.replicas 在 compose up 下被忽略（见模块 7）；忘了给 adminer/k6 等工具设 profiles，CI 的 up 把它们全拉起来，端口冲突、资源抢占。profile 是环境分组的第一道闸。
自测

六道题

1. compose up 后 api 报 connection refused，db 容器状态是 running。根因和正确修复是？
正确答案：service_healthy。depends_on 短语法等的是 started；就绪的定义要放进 healthcheck，CI 场景再配 up --wait。
2. 想让同一份基础配置在开发/生产用不同端口和镜像，最规范的组织方式是？
正确答案：基座 + 覆盖。override 自动合并适合开发默认值；生产用显式 -f 顺序，后者覆盖前者，docker compose config 验证最终结果。
3. 数据库密码是 pa$$word，compose 文件里 environment 应怎么写才能让容器拿到字面量 pa$$word？
正确答案：写 $$。compose 插值会把单个 $ 当变量起始，$$ 才表示字面美元符。
4. 同一宿主上另一个 compose 项目里的服务，想直接访问 myshop 项目的 api 容器。可行方案是？
正确答案：external 网络 + 别名。服务名 DNS 只在所属项目网络内有效，这是 compose 的隔离边界，不是 bug。
5. 关于 profiles，下列说法正确的是？
正确答案：默认不启动。这正是 profiles 做环境分组的价值：CI 里默认不带 debug 工具，依赖链上的服务仍会被自动拉起。
6. docker compose up 后你发现 deploy.replicas=3 没起 3 个副本、reservations 也没生效。解释和做法是？
正确答案：compose up 与 stack deploy 语义不同。compose up 下 replicas 忽略（用 --scale=3）、resources.limits 生效、reservations/placement 等 Swarm 专属字段无效。

术语表

术语一句话解释
Compose 规范compose 文件的开放标准，version 字段已废弃
project（项目）一次 up 的运行实体，默认取目录名，可用 -p / COMPOSE_PROJECT_NAME 指定
servicecompose 文件里的一个容器定义，项目内以服务名做 DNS
插值 interpolation读取 YAML 时在宿主机做 ${VAR} 替换，$$ 表示字面 $
.env项目目录下的插值变量文件，只影响 compose 解析，不自动进容器
env_file声明要注入容器的变量文件，不参与宿主机插值
healthcheck容器内就绪/存活探测，test 支持 CMD / CMD-SHELL / NONE
depends_on启动顺序控制，condition 可取 started / healthy / completed_successfully
profiles服务分组开关，未启用的 profile 服务默认不启动
override 文件compose.override.yml 自动合并，或 -f 多文件按顺序后者覆盖
命名卷volumes 顶层声明、Docker 管理的持久化存储，容器重建不丢
bind mount宿主路径直接映射进容器，适合源码/配置，改动双向可见
external 网络/卷引用 compose 之外已存在的资源，跨项目共享的唯一正道
network alias服务的额外 DNS 名，用于流量切换与兼容旧主机名
develop.watchv2.22+ 的文件监听，动作分 sync / rebuild / sync+restart
docker stack deploySwarm 模式的部署入口，deploy 段在此生效，忽略 depends_on
x- 扩展字段以 x- 开头的自定义顶层字段，用于存放可复用的 YAML 片段
下一步怎么练：把手上一个本地环境改造成"基座 + override + profiles"三段式：基座只留服务与网络，override 挂源码和 debug 日志，把 adminer/k6 收进 debug profile。再给 db 加上 healthcheck，把 depends_on 全部改成长语法，最后 docker compose config 检查一遍合并结果。
