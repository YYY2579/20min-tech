二十分钟学透 日志栈（EFK / Loki）

日志系统的一半成本在存，另一半在查。ELK 能全文检索但贵，Loki 便宜但不建全文索引。这篇讲采集对比、ES 索引生命周期、KQL、LogQL、结构化日志规范，以及索引爆炸、GC 压力这些真实事故。

开始前

两条技术路线，一个最小环境

# 路线 A：ELK（Elasticsearch + Kibana，重量级，全文检索）
docker run -d -p 9200:9200 -e "discovery.type=single-node" \
  -e "xpack.security.enabled=false" elasticsearch:8.14.0
docker run -d -p 5601:5601 -e ELASTICSEARCH_HOSTS=http://host:9200 kibana:8.14.0

# 路线 B：Loki（轻量，标签索引，配 Grafana）
docker run -d -p 3100:3100 grafana/loki:3.1.0 -config.file=/etc/loki/local-config.yaml
# Grafana 里加 Loki 数据源：http://loki:3100
# promtail 把容器日志推上来，或用 docker logging driver 直接推 Loki

# 验证
curl localhost:9200/_cluster/health     # ELK：看集群健康
curl localhost:3100/ready                # Loki：看是否就绪
curl -G localhost:3100/loki/api/v1/query_range \
  --data-urlencode 'query={job="app"}' --data-urlencode 'limit=5'
选型先验：日志量 < 50GB/天、查询以标签+时间为主 → Loki；需要全文检索、复杂聚合（用户行为分析、审计）→ ELK。两者可以共存：结构化日志进 Loki 便宜查询，关键审计日志进 ES 全文检索。
模块 1

日志采集架构：Filebeat / Fluentd / Logstash

采集器负责"读日志文件 → 解析 → 加工 → 发到存储"。三个主流选择，定位完全不同。

采集器实现语言资源占用特点
FilebeatGo低（~50MB）Elastic 出品，轻量、backpressure 机制成熟；解析能力弱，靠 Processor 和 Ingest Pipeline 补
Fluentd / Fluent BitRuby / C中 / 低插件生态 1000+，路由灵活，K8s 事实标准之一；Fluent Bit 是 C 重写，嵌入式友好
LogstashJVM高（>500MB）filter 能力最强（grok/mutate/geoip），吞吐高但重；通常不部署在每台机器上

经典链路

# 链路一（ELK 直连，中小规模）：Filebeat → Elasticsearch → Kibana
# 链路二（ELK + 缓冲，生产主流）：Filebeat → Kafka → Logstash → ES → Kibana
# 链路三（Loki）：promtail/agent → Loki ← Grafana 查询

# 为什么中间要加 Kafka？
# ① ES 重启/扩容时，日志峰值不会丢（Filebeat 背压会拖慢采集）
# ② 突发流量削峰，ES 按自己的节奏消费
# ③ 一份日志喂多个消费者（ES + 安全审计 + 计费）

Filebeat 配置示例

# /etc/filebeat/filebeat.yml
filebeat.inputs:
  - type: filestream
    id: app-logs
    paths:
      - /var/log/app/*.log
    parsers:
      - multiline:                    # 多行合并：Java 堆栈是一行一条的噩梦
          pattern: '^\d{4}-\d{2}-\d{2}'   # 新行特征：以日期开头
          negate: true
          match: after
    fields:
      service: api
      env: prod

processors:
  - drop_fields:                      # 丢噪音字段，降存储
      fields: ["agent.ephemeral_id", "agent.hostname"]
      ignore_missing: true

output.kafka:                         # 生产：发 Kafka 缓冲
  hosts: ["kafka1:9092", "kafka2:9092"]
  topic: "app-logs"
  partition.round_robin:
    reachable_only: true
  required_acks: 1

# 小规模也可以直连 ES：output.elasticsearch: hosts: ["es:9200"]
# 关键参数：queue.mem.events: 4096（内存队列，背压起点）
#          max_procs: 2（Filebeat 单机吃满 CPU 时限制线程数）

Logstash 管道示例

# /etc/logstash/conf.d/app.conf —— filter 是 Logstash 的主场
input {
  kafka {
    bootstrap_servers => "kafka1:9092"
    topics => ["app-logs"]
    codec => json
  }
}
filter {
  if [level] == "ERROR" {
    mutate { add_tag => ["error"] }        # 打标签，Kibana 里好筛
  }
  grok {
    match => { "message" => "%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} %{GREEDYDATA:msg}" }
    tag_on_failure => ["_grokparsefailure"]  # 解析失败打标，别静默丢
  }
  date {
    match => ["ts", "ISO8601"]               # 用日志里的时间，不用采集时间！
    target => "@timestamp"
  }
  mutate {
    remove_field => ["ts", "host", "message"]   # 清冗余字段
  }
}
output {
  elasticsearch {
    hosts => ["http://es1:9200"]
    index => "app-logs-%{+YYYY.MM.dd}"       # 按天建索引（ILM 会接管 rollover）
  }
}
多行合并是日志采集的第一大坑。Java 异常堆栈几十行、Python traceback、SQL 语句换行 —— 不合并的话，一条错误被拆成 50 条独立日志，堆栈上下文全丢。在采集端合并（Filebeat multiline / Fluentd multiline parser），不要让存储端猜。
模块 2

Elasticsearch 日志存储与 ILM

日志数据的特点是写多读少、时间相关、只关心近期。ES 的索引生命周期管理（ILM）就是为这个设计的。

索引设计三要素

概念说明
Index逻辑命名空间，日志按天分：app-logs-2026.10.17。删除旧日志 = 删整个索引，秒级
Shard索引分片。单 shard 控制在 30~50GB：太小则分片过多拖慢集群，太大则恢复慢
Mapping字段类型定义。text 全文检索（分词），keyword 精确匹配/聚合。日志的 msg 用 text，level/service 用 keyword
# 索引模板：新索引自动按此创建（关键！不配则 dynamic mapping 灾难）
PUT _index_template/app-logs
{
  "index_patterns": ["app-logs-*"],
  "template": {
    "settings": {
      "number_of_shards": 2,              # 按天 50GB/2 分片
      "number_of_replicas": 1,
      "refresh_interval": "30s",          # 日志不需要实时！30s 足够，默认 1s 浪费
      "codec": "best_compression"         # LZ4→DEFLATE，CPU 换空间
    },
    "mappings": {
      "dynamic": false,                   # 关掉动态映射，防字段爆炸
      "properties": {
        "@timestamp":  { "type": "date" },
        "level":       { "type": "keyword" },       # 精确匹配 + 聚合
        "service":     { "type": "keyword" },
        "trace_id":    { "type": "keyword" },
        "msg":         { "type": "text", "analyzer": "standard" },  # 全文检索
        "duration_ms": { "type": "long" }
      }
    }
  }
}

ILM：Hot → Warm → Cold → Delete

# ILM 策略：按天 rollover，热数据快存储，冷数据便宜存储，到期删除
PUT _ilm/policy/app-logs
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": {
            "max_age": "1d",               # 一天滚一个新索引
            "max_size": "50gb"
          },
          "set_priority": { "unbounce": 100 }   # 热索引优先留在内存
        }
      },
      "warm": {
        "min_age": "3d",                   # 3 天后转温
        "actions": {
          "shrink": { "number_of_shards": 1 },  # 缩分片，降开销
          "forcemerge": { "max_num_segments": 1 },  # 合并段，查询提速
          "readonly": { }
        }
      },
      "cold": {
        "min_age": "7d",                   # 7 天后转冷（可挂廉价磁盘/快照）
        "actions": {
          "searchable_snapshot": { "snapshot_repository": "s3-repo" }
        }
      },
      "delete": {
        "min_age": "30d",                  # 30 天删除
        "actions": { "delete": { } }
      }
    }
  }
}

# 索引模板里挂上 ILM：
"settings": { "index.lifecycle.name": "app-logs", "index.lifecycle.rollover_alias": "app-logs" }
# 写入用别名 app-logs，ES 自动 rollover 到 app-logs-000001
索引命名灾难：不配模板 + "dynamic": true（默认），日志里出现一个新字段就自动建 mapping。一万条日志带一万个不同字段名 → mapping 爆炸 → 集群元数据膨胀、查询全表变慢、GC 压力陡增。必须 dynamic: strict/false + 显式列字段，不匹配的字段直接拒收或忽略。
模块 3

Kibana KQL 检索

KQL（Kibana Query Language）是 Kibana Discover 的默认查询语法：结构化、无通配符性能陷阱、够用的表达力。Lucene 语法也仍支持。

# KQL 基础语法
level: ERROR                          # 字段等值（keyword 字段精确匹配）
level: ERROR and service: payment     # and / or / not，可加括号
not level: DEBUG                     # 取反
msg: timeout*                        # 通配符 *（任意多）?（单个）—— text 字段分词后匹配
trace_id: "abc123"                   # 带特殊字符的值加引号
level: (ERROR or WARN)               # 分组

# 存在性查询
trace_id: *                          # 字段存在的日志（有 trace_id 的）

# 范围查询（KQL 原生支持）
duration_ms >= 1000 and duration_ms < 5000
@timestamp >= "2026-10-17 00:00:00"   # 时间字段范围，注意时区

# 实战组合：支付服务的错误，且耗时超过 1 秒
service: payment and level: ERROR and duration_ms >= 1000

# 实战：查询 trace_id 贯穿的整条链路日志
trace_id: "4bf92f3577b34da6a3ce929d0e0e4736"
# → 按 @timestamp 排序，就能看到请求在网关、订单、库存服务间的完整流转

# Lucene 语法（仍可用，写regex 时方便）
msg: /timeout.*retry/                # 正则
level:ERROR AND service:payment      # 大写 AND/OR/NOT 也行
技巧说明
保存检索Discover 里 Save query，团队共享常用过滤（如"只看 ERROR"）
列选择只展示 level/service/trace_id/msg 四列，默认全列是噪音
时间过滤器右上角时间范围 + KQL 组合，KQL 里也可以写 @timestamp 范围
字段过滤器 +点字段值旁的放大镜，自动追加到查询栏，比手打快
相邻文档跳转点单条日志的展开按钮，看同一文件前后的上下文
KQL vs Lucene 的三个坑：① KQL 的 field: value 对 text 字段是分词后匹配，对 keyword 是精确匹配 —— msg: ERROR 可能匹配不到 "ERROR_CODE"；② 通配符开头的查询（*timeout）性能差，ES 要扫大量词项；③ KQL 的 and 优先级高于 or，复杂条件一律加括号。
模块 4

Loki 架构与 LogQL

Loki 的核心设计取舍：不建全文索引，只索引标签；日志内容按块压缩存对象存储。查询时先按标签定位流，再在压缩块里线性扫描内容。

架构组件

组件职责
Promtail / Grafana Agent采集端：读日志文件、打标签、推给 Loki
Distributor入口：校验、按标签哈希分发给 ingester
Ingester接收写入，内存中组 chunk，刷盘后传对象存储
Querier / Query-frontend查询执行与队列调度，大查询切片并行
Compactor压缩合并 chunk，加速查询
对象存储（S3/GCS）chunk 的最终归宿，便宜且可无限扩展
# Loki 配置核心（loki.yml，单机模式简化版）
auth_enabled: false                   # 单租户关闭；多租户模式强制开启

server:
  http_listen_port: 3100

ingester:
  lifecycler:
    ring:
      kvstore: { store: inmemory }     # 单机用内存，集群用 consul/etcd
  chunk_idle_period: 5m                # 块闲置 5 分钟就刷盘
  max_chunk_age: 1h                    # 块最多活 1 小时

schema_config:
  configs:
    - from: 2026-01-01
      store: tsdb                     # TSDB 模式，比 boltdb 查询快
      object_store: s3                # 块存 S3
      schema: v13
      index:
        prefix: loki_
        period: 24h

limits_config:
  retention_period: 720h              # 30 天保留
  ingestion_rate_mb: 10               # 每租户每秒 10MB 上限，防打爆
  max_query_length: 721h              # 单次查询最大跨度

LogQL：查询分两层

# 第一层：Log selector（标签匹配，决定扫哪些流）—— 必须写
{job="api", env="prod"}               # = 精确，!= 不等，=~ 正则，!~ 反向正则
{job=~"api|worker", env="prod"}       # 正则匹配多个 job

# 第二层：Log pipeline（过滤 + 解析 + 格式化）—— 链式 |
{job="api"} |= "error"                # 行过滤：包含 error（不区分大小写）
{job="api"} != "debug"                # 行过滤：不含 debug
{job="api"} |~ "timeout.*retry"       # 行过滤：正则

# JSON 日志解析（强烈推荐结构化日志）
{job="api"} |= "error" | json | level="ERROR" | duration_ms >= 1000
# 解析后可直接用字段过滤，比字符串 grep 快且准

# logfmt 解析（key=value 格式）
{job="api"} | logfmt | level="error" | line_format "{{.msg}}"

# 指标查询：从日志算指标！LogQL 的杀手锏
sum by (level) (rate({job="api"} | json [5m]))        # 每秒各级别日志条数
sum(rate({job="api"} |= "error"[5m])) / sum(rate({job="api"}[5m]))  # 错误率
topk(5, sum by (path) (count_over_time({job="api"} | json [1h])))   # Top 接口日志量

# 与 Prometheus 的衔接：Loki 指标可直接在 Grafana 里画
# → 同一张仪表盘上：指标面板用 Prometheus，日志量面板用 Loki LogQL
Loki 的性能边界：没有全文索引，内容过滤是全块扫描。查询 {job="api"} 再 grep 一个罕见关键词，可能要解压扫描几十 GB。优化手段：① 标签选择器尽量精确（加 env/instance）；② 时间范围别拉一个月；③ 高频查询用 metric queries 预聚合；④ chunk_target_size 调大减少块数量。Loki 不是"便宜的 ES"，它是"能算指标的日志系统"。
模块 5

Loki vs ELK：成本与能力对比

维度ELK (Elasticsearch)Loki
索引方式全文倒排索引，任何字段可搜只索引标签，内容靠块扫描
存储成本高：索引 + 原文 + 副本，约原始量 1.5~2 倍低：压缩块 + 标签索引，约原始量 10~20%
计算成本高：JVM 集群，大聚合吃内存低：Go 实现，单机能跑
全文检索强项，任意词毫秒级弱项，线性扫描
聚合分析强项，ES aggregation 丰富弱：只能 count_over_time/rate 类指标
日志算指标弱（要另写 pipeline）强项，LogQL 直接出指标
K8s 友好度中高，与 Prometheus 标签体系天然一致
运维复杂度高：分片、副本、GC 调优中：组件少，无状态 + 对象存储
查询语言KQL / Lucene / DSLLogQL（类 PromQL）
典型规模TB 级、多团队全文检索百 GB 级、运维监控为主
混合架构（越来越多团队的选择）：① 应用日志 → Loki（便宜、能算指标、和 Grafana 指标面板联动）；② 审计/安全日志 → Elasticsearch（全文检索 + 复杂分析）；③ 采集端 Filebeat/promtail 同时发两份。别追求"一个系统解决所有日志问题"，两类日志的查询模式和成本结构根本不同。
模块 6

结构化日志规范与脱敏

日志系统的上限，在应用写日志的那一刻就决定了。纯文本日志是上一代的事，JSON 结构化日志是现代日志栈的前提。

JSON 日志规范

# 差的日志：纯文本，没法过滤没法聚合
2026-10-17 10:23:45 ERROR order create failed user=12345

# 好的日志：一行一个 JSON 对象
{"ts":"2026-10-17T10:23:45.123Z","level":"ERROR","service":"order-api",
 "msg":"order create failed","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736",
 "span_id":"00f067aa0ba902b7","user_id":12345,"order_id":98765,
 "duration_ms":1523,"error_code":"STOCK_LOCKED"}

# 字段规范（全公司统一，跨服务才能查）
# ts        ISO8601 UTC，带毫秒 —— 别用本地时间！
# level     DEBUG/INFO/WARN/ERROR 四级，大写
# service   服务名，与 K8s label 一致
# msg       人类可读的简述，别把异常堆栈放这里
# trace_id / span_id  W3C Trace Context，贯穿全链路
# 业务字段   user_id/order_id 等用下划线命名，值为字符串或数字
# exception 异常类名 + stack 单独放，别塞进 msg

trace_id 贯穿：日志与链路的粘合剂

# 一次请求的完整视图（排障的黄金路径）：
# ① Grafana 指标面板发现 payment 错误率升高
# ② 点曲线 → Data link 跳到 Loki，查询 {service="payment"} | json | level="ERROR"
# ③ 从错误日志里拿到 trace_id
# ④ 用 trace_id 查 Loki 全链路日志（KQL: trace_id: "xxx"）
# ⑤ 或直接跳 Tempo 看调用链：哪个下游超时一目了然

# 代码里怎么传（各语言的标准做法）：
# Java:    MDC.put("traceId", context.traceId()) —— logback pattern %X{traceId}
# Python:  contextvars + logging Filter 注入
# Go:     context.WithValue + slog.Handler 包装
# 关键：HTTP 入口生成 trace_id，通过 header (traceparent) 传给下游

日志脱敏

# 原则：敏感数据不出应用。在日志输出前脱敏，别指望下游

# 应用层（首选）：日志框架里脱敏
# Java logback + MaskingConverter / Python logging.Filter 正则替换

# 采集层兜底：Filebeat script processor / Logstash ruby filter
filter {
  ruby {
    code => "
      event.set('msg', event.get('msg').to_s
        .gsub(/(1[3-9]\d{9})/, '138****8888')          # 手机号
        .gsub(/(\d{6})\d{8}(\d{4})/, '\1********\2'))  # 身份证
    "
  }
}

# 必须脱敏的字段：手机号、身份证、银行卡、密码、token、密钥
# 例外：trace_id / user_id 这类不可逆 ID 不算敏感，放心记

# 日志级别使用规范：
# ERROR —— 需要人处理的故障，配告警
# WARN  —— 异常但自愈/降级，不配告警
# INFO  —— 关键业务节点（下单、支付回调），可采样
# DEBUG —— 排查细节，生产默认关闭，动态开关
坑库

十个线上坑

1
动态映射导致字段爆炸，集群被拖垮
日志字段不固定（每次请求都带新的动态字段），ES 自动建 mapping，索引元数据膨胀、查询变慢、GC 压力陡增。索引模板必须设 dynamic: strict/false + 显式字段列表。
2
shard 太小或太大，集群整体性能崩
按天一个索引却设 20 个 shard，每天 1GB 数据 → 200 个 shard 全是小文件，合并和查询开销爆炸。单 shard 目标 30~50GB，日增量小就用月索引 + ILM rollover。
3
用了采集时间而不是日志时间，排障对不上
网络抖动让日志延迟 10 分钟入库，@timestamp 变成"入库时间"，错误日志排到了错误的时间段。Logstash date filter 必须用日志里的时间戳，解析失败打 tag 监控。
4
时间戳时区混乱：UTC 与本地时间混用
应用写本地时间（UTC+8），ES 存 UTC，Kibana 显示再转一遍，最后差 8 小时，查"刚才的日志"什么都看不到。规范：应用一律输出 ISO8601 UTC 带时区标识（Z），Kibana 显示层再转用户时区。
5
ES 大聚合和深分页触发 GC，集群假死
Kibana 对时间范围 30 天的索引做 terms 聚合、或 from+size 翻到第 10000 页 —— JVM 老年代暴涨，长 GC，节点失联。聚合加时间分片、深分页用 search_after、聚合字段用 keyword。
6
Loki 标签基数失控
把 pod_name、path、user_id 当 Loki 标签，每个组合一条流，ingester 内存爆炸。Loki 标签只放低基数维度（job/env/instance/service），高基数信息留给 LogQL 解析器。
7
ILM rollover 卡住，索引无限增长
rollover 条件写 max_size: 50gb 但写入别名配错，或 shrink 失败阻塞生命周期，索引一直涨到几百 GB。监控 ilm_explain 和索引大小，rollover 别名必须在索引模板里配对。
8
多行日志不合并，一条异常拆成 50 条
Java 堆栈每行一条独立日志，上下文全丢，按 ERROR 统计数量虚高 50 倍。采集端配 multiline 规则（以时间戳开头的行是新日志起点）。
9
日志量突增（大促/攻击）打爆采集和存储
DEBUG 级别被意外打开、重试风暴刷屏，ES 磁盘一天写满。三道防线：采集端限流（ingestion_rate_mb）、存储端限流、应用端日志采样 + 动态级别开关。
10
KQL 与 Lucene 语法混用，查询结果和预期不符
KQL 的 and 优先级高于 or、text 字段分词匹配、keyword 字段精确匹配 —— 同一个 msg: ERROR 在不同字段类型下结果不同。先确认字段类型，复杂条件加括号，团队统一用 KQL。
自测

六道题

1. 一个 200 节点的 Java 集群，每台部署轻量采集器，解析后发到 Kafka，再进 ES。最合适的采集器组合是？
正确答案：Filebeat + 集中式 Logstash。Filebeat 是 Go 实现、单机 ~50MB，200 台部署无压力；JVM 的 Logstash 每台 500MB+，部署 200 台纯浪费。重解析放集群外的 Logstash 消费 Kafka，资源集中、规则统一。
2. 关于 Loki 的索引设计，正确的是？
正确答案：只索引标签 + 块存储内容。这是 Loki 低成本的核心：索引体积小、存储压缩率高。代价是内容过滤慢，所以标签选择器要精确、时间范围别太大。
3. ES 日志索引最该防的"映射爆炸"问题是？
正确答案：dynamic mapping 字段爆炸。解法是索引模板里 dynamic: false/strict + 显式字段列表。shard 多是性能问题（可调），按天索引本就是日志场景的正确设计。
4. 应用日志里的时间戳应该怎么处理？
正确答案：日志内时间 + UTC + 显示层转换。入库时间会因为网络延迟、队列堆积而失真，排障时对不上事故时刻。跨时区团队必须统一 UTC 存储。
5. 想统计"过去一小时 error 级别日志的速率"，用 LogQL 应该写？
正确答案：rate 指标查询。LogQL 的 metric queries（rate/rate_over_time 族）才能产出可聚合的速率序列。count_over_time 是纯计数查询，返回的是原始日志匹配数，不能直接当速率用。
6. 关于 trace_id 贯穿日志体系，错误的做法是？
正确答案：只记 span_id 是错的。span_id 只标识单个操作，跨服务排障必须靠 trace_id 把网关、订单、库存、支付的日志串成一条线。W3C Trace Context 的 traceparent header 是标准透传方式。
