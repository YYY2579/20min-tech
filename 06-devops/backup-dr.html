开始前

起一个能练的复制环境

灾备的所有机制都长在"复制"上，先用 docker 把 MySQL 和 PG 的主从跑起来，后面每个模块都能立刻验证。

# ===== MySQL 8.0 一主一从 =====
docker run -d --name mysql-primary -p 3306:3306 -e MYSQL_ROOT_PASSWORD=Root123 \
  mysql:8.0 --server-id=1 --log-bin=mysql-bin --binlog-format=ROW \
  --gtid-mode=ON --enforce-gtid-consistency=ON

docker run -d --name mysql-replica -p 3307:3306 -e MYSQL_ROOT_PASSWORD=Root123 \
  mysql:8.0 --server-id=2 --relay-log=relay-log \
  --gtid-mode=ON --enforce-gtid-consistency=ON

# 主库建复制账号
docker exec -i mysql-primary mysql -uroot -pRoot123 -e \
  "CREATE USER 'repl'@'%' IDENTIFIED WITH mysql_native_password BY 'Repl123';
   GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';"

# 从库指向主库（8.0.23+ 新语法；旧版为 CHANGE MASTER TO / START SLAVE，仍兼容）
docker exec -i mysql-replica mysql -uroot -pRoot123 -e \
  "CHANGE REPLICATION SOURCE TO SOURCE_HOST='mysql-primary', SOURCE_USER='repl',
   SOURCE_PASSWORD='Repl123', SOURCE_AUTO_POSITION=1; START REPLICA;"

# 验证：看复制线程状态与滞后（字段名各小版本有 Source_*/Master_* 差异，以实际输出为准）
docker exec -i mysql-replica mysql -uroot -pRoot123 -e "SHOW REPLICA STATUS\G"

# ===== PostgreSQL 16 主备 =====
docker run -d --name pg-primary -p 5432:5432 -e POSTGRES_PASSWORD=pg123 \
  postgres:16 -c wal_level=replica -c max_wal_senders=10 -c synchronous_commit=on
docker exec -i pg-primary psql -U postgres -c \
  "CREATE ROLE repl REPLICATION LOGIN PASSWORD 'repl123';
   SELECT pg_create_physical_replication_slot('standby1');"

pg_basebackup -h localhost -p 5432 -U repl -D /tmp/pgstandby -R -S standby1 -P
# -R 自动写入 primary_conninfo，-S 使用复制槽防 WAL 被回收
三个必查项：① binlog-format=ROW 是跨机房复制的前提（STATEMENT 格式在主从 schema 不一致时会错）；② gtid-mode=ON 让位点对齐从"文件+偏移"变成"事务号"，切主换从不用再对日志坐标；③ PG 必须用复制槽（replication slot），否则备库网络抖动期间主库 WAL 被回收，备库直接断档重来。
模块 1

灾备等级与架构模式

国标 GB/T 20988-2007《信息安全技术 信息系统灾难恢复规范》把灾备能力分成六级，级别越高 RPO/RTO 越小、成本越高。

等级能力典型形态
第 1 级基本支持：数据定时备份每日备份到磁带/异地，恢复靠人，RTO 天级
第 2 级备用场地支持有备用机房和设备，无实时数据
第 3 级电子传输 + 部分设备支持备份数据电子化传送到备用场地
第 4 级电子传输 + 完整设备支持备用站点设备齐全，定时恢复，RTO 小时级
第 5 级实时数据传输 + 完整设备异步/同步复制到灾备中心，RTO 分钟级
第 6 级数据零丢失 + 远程集群同步复制 + 应用级双活，RPO=0、RTO 分钟级

四种部署架构模式

模式RPO / RTO关键约束
主备（冷备）RPO 小时级 / RTO 小时~天级备机房平时不接流量；最便宜，恢复最慢
同城双活RPO=0 / RTO 分钟级同步复制，写入延迟 = 2×同城 RTT（约 1~3ms）；机房距离通常 <50km
两地三中心RPO≈0~秒级 / RTO 分钟~小时级同城双活 + 异地冷备；跨地域用异步复制 + binlog/WAL 补偿
异地多活RPO 秒级 / RTO 分钟级多地域同时服务，靠单元化分片 + 异步同步；架构与运维最重
延迟是架构选型的第一约束：同城 RTT 约 1~3ms，同大区约 5~10ms，跨地域约 30~50ms。同步复制下一次提交至少多等 2×RTT，跨地域 30ms 就意味着每次写至少慢 60ms —— 对支付这类 QPS 数千的场景完全不可接受。所以同步只做同城，跨地域一定异步 + 补偿。
模块 2

RPO/RTO 与业务分级

RPO/RTO 不是技术指标，是业务用钱投票出来的结果：能容忍丢多少数据、停多久，取决于每分钟损失多少。

指标定义
RPO
恢复点目标		故障发生时最多能丢多少数据 = 故障点 − 最近可恢复点。由复制/备份策略决定
RTO
恢复时间目标		故障发生后多久业务必须恢复。由架构（自动切换 vs 人工恢复）决定
MTTR实际平均修复时间。RTO 是承诺，MTTR 是现实，两者要对齐

业务分级示例（按损失倒推）

级别业务类型RPO / RTO架构配置
L0支付、账务、库存扣减RPO=0，RTO≤5min同城双活同步复制 + 异地灾备；切换全自动
L1下单、交易核心链路RPO≤60s，RTO≤30min同城双活；异地半同步/异步 + 补偿
L2内容、Feed、一般在线业务RPO≤5min，RTO≤2h异步复制异地 + 定时切换
L3内部系统、离线报表RPO≤24h，RTO≤24h每日备份，冷备恢复

定级方法：和业务方一起算停机每分钟的损失和丢一分钟数据的代价（订单丢失 = 客诉 + 资损；Feed 丢失 5 分钟 ≈ 无感）。注意 RTO 每下降一个数量级，成本近似指数上升 —— 从"2 小时恢复"到"5 分钟恢复"，靠的不是更好的备份软件，是整套双活架构。

分级必须落到配置和演练，不能停在 PPT：L0 业务配了同步复制，但要验证"从库挂了主库会不会无限期阻塞"（半同步超时降级策略）；L1 业务说 RTO 30 分钟，要演练过切换脚本真实耗时。没演练过的 RTO 是许愿，不是指标。
模块 3

数据层灾备：MySQL

MySQL 跨机房的主流是三档：异步复制（异地）、半同步复制（同城）、MGR 组复制（同城强一致），按 RPO 要求和距离选。

# ===== 半同步：主库提交前至少等一个从库确认收到 binlog =====
# 8.0.26+ 新插件名；旧版为 rpl_semi_sync_master / rpl_semi_sync_slave
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';   # 主库
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so'; # 从库

SET GLOBAL rpl_semi_sync_source_enabled = ON;
SET GLOBAL rpl_semi_sync_source_timeout = 5000;   # 等从库 ACK 的超时（ms）

# 关键行为：超时后主库自动降级为异步继续服务 —— 不阻塞业务，但此窗口内 RPO>0
SHOW STATUS LIKE 'Rpl_semi_sync_source%';   # 看 tx_wait_cnt / avg_tx_wait_time 判断降级是否在发生

# ===== binlog 归档：异地恢复的原料 =====
SHOW BINARY LOGS;                                # 当前所有 binlog 文件
PURGE BINARY LOGS TO 'mysql-bin.000123';         # 谨慎清理，先确认下游都已消费
# 配置：binlog_expire_logs_seconds=604800（保留 7 天）+ 异地实时拉取归档
模式RPO特性与适用
异步复制秒级~分钟级性能无损失，主库宕机可能丢最后若干事务。跨地域默认选择
半同步复制≈0（超时窗口除外）主库至少等一个从库 ACK；从库 ACK 慢会拖慢写入。同城双活标配
MGR 组复制0（多数派提交）Paxos 多数派确认，强一致；跨地域写入延迟不可接受，适合同城
半同步的两个坑：① 超时设太短（如 1s）：跨机房稍有抖动就降级异步，你以为有同步实际在裸奔；设太长（如 30s）：从库一挂，主库写入集体卡顿 30 秒。建议 5~10s 起步 + 对 Rpl_semi_sync_source_status 做告警。② 半同步只保证"从库收到 binlog"，不保证从库应用完（relay log 已写但 SQL 线程未执行） —— 严格场景要求 rpl_semi_sync_source_wait_for_replica 之类参数确认回放，或切换前校验从库滞后为 0。

备份与 PITR

# 物理备份（XtraBackup）：全量 + 增量，恢复快，适合大库
xtrabackup --backup --target-dir=/backup/full --user=root --password=xxx
xtrabackup --backup --target-dir=/backup/inc1 --incremental-basedir=/backup/full \
  --user=root --password=xxx
xtrabackup --prepare --target-dir=/backup/full                     # 恢复前先 prepare
xtrabackup --prepare --target-dir=/backup/full --incremental-dir=/backup/inc1

# 逻辑备份（mysqldump）：小库/单表抽取，--master-data 记录 binlog 位点
mysqldump --single-transaction --master-data=2 --routines --triggers appdb > appdb.sql
# --single-transaction 用一致性快照不锁表；--master-data=2 把位点写进注释

# PITR：全量恢复 + 重放 binlog 到指定时间点
mysqlbinlog --stop-datetime="2026-10-15 14:23:00" /backup/binlog/mysql-bin.000456 | mysql -uroot -p
# GTID 模式下可改为 --stop-position 或按 GTID 集合回放，跨机房位点对齐更容易
模块 4

PostgreSQL 与 Redis 跨机房

PostgreSQL：流复制 + WAL 归档

# 主库配置
wal_level = replica
max_wal_senders = 10
synchronous_commit = on                          # on=等待 WAL 落盘；remote_apply 等备库回放完
synchronous_standby_names = 'ANY 2 (s1, s2)'     # quorum 提交：至少 2 个备库确认

# WAL 归档（PITR 的原料）
archive_mode = on
archive_command = 'test ! -f /wal_archive/%f && cp %p /wal_archive/%f'
# 恢复：restore_command = 'cp /wal_archive/%f %p' + recovery_target_time（PG 12+ 需 touch recovery.signal）

# 监控复制滞后
SELECT application_name, state, sync_state, replay_lag FROM pg_stat_replication;
# 跨地域省带宽：级联复制 —— 本地 standby 再串一个异地 standby，跨区只传一份

# 逻辑复制：只同步部分表/跨大版本，异步最终一致
CREATE PUBLICATION pub_orders FOR TABLE orders;              # 主库
CREATE SUBSCRIPTION sub_orders CONNECTION 'host=... dbname=...' PUBLICATION pub_orders;  # 备库
PG 跨机房的两个特有坑：① 复制槽断线 = 磁盘爆炸：槽位保留未确认的 WAL，备库长时间掉线会让主库 pg_wal 写满磁盘。监控 pg_replication_slots 的 restart_lsn 落后量，设上限。② 同步备库拖慢全集群：synchronous_standby_names 里一个备库变慢，主库所有提交都等它；quorum 模式（ANY n）比 FIRST 模式更抗单点抖动。

Redis：主从跨机房 + 防脑裂参数

# 跨机房主从（异步，切换可能丢数据）
replicaof 10.0.1.10 6379

# 防脑裂：当"健康从库不足"时拒绝写入，宁可停服务也不丢数据
min-replicas-to-write 1          # 至少 1 个从库
min-replicas-max-lag 10          # 且其滞后不超过 10 秒，否则主库拒绝写

# Sentinel 跨机房部署原则：哨兵多数派要与主库同侧
sentinel monitor mymaster 10.0.1.10 6379 3     # quorum=3
# 例：5 个哨兵，3 个在主机房、2 个在灾备机房，quorum=3
# 避免"备机房分区时备侧哨兵把主判死引发误切换"

# 备份：RDB 快照 + AOF 异地归档；跨集群同步用 RedisShake 等工具
redis-cli -h 10.0.1.10 BGSAVE                     # 触发快照
redis-shake -type=sync -source=10.0.1.10:6379 -target=10.1.1.10:6379

Redis 灾备的本质困境：主从复制是异步的，故障切换必然丢一段数据。对策是按业务分级 —— 缓存类丢了就回源重建；对丢失敏感的（如库存计数）要么接受短窗口不一致 + 对账补偿，要么不用 Redis 做主存储。

模块 5

备份体系：策略、工具与验证

备份是灾备的最后底线：复制解决"机房级故障"，备份解决"数据级灾难"（误删、勒索、逻辑错误）。

3-2-1 原则与备份类型

类型做法对 RPO 的影响
全量备份定期完整拷贝（XtraBackup/pg_basebackup）恢复基准点，间隔决定最差回退位置
增量备份基于上次全量/增量的差异（XtraBackup 增量链）缩短备份间隔，恢复时要按链重放
日志备份binlog / WAL 持续归档秒级 RPO 的关键，配合全量做 PITR
3-2-1 原则3 份副本、2 种不同介质、1 份异地防单点存储故障和机房级灾难
GFS 保留策略日备留 7 天、周备留 4~6 周、月备留 12 月、年备留 3~7 年平衡存储成本与可回看深度
# etcd（K8s 控制面）备份 —— 忘了它，集群状态全丢
etcdctl snapshot save /backup/etcd-$(date +%F).db
etcdctl snapshot status /backup/etcd-2026-10-15.db --write-table=sha256   # 校验快照完整性
etcdctl snapshot restore /backup/etcd-2026-10-15.db                       # 恢复到新数据目录

# 备份加密与防勒索：密文落盘 + 异地/WORM 存储（S3 Object Lock、磁带离线）
# 勒索软件会先找本地备份删，异地不可变副本是最后的恢复希望

# 文件级备份工具：restic / borg / rsync + 版本保留
restic -r s3:s3.amazonaws.com/backup-bucket init
restic -r s3:s3.amazonaws.com/backup-bucket backup /data/mysql --tag daily
restic -r s3:s3.amazonaws.com/backup-bucket forget --keep-daily 7 --keep-weekly 4 --keep-monthly 12 --prune
备份不验证 = 没备份：备份文件损坏、密码丢了、恢复步骤没人走过、依赖的某个组件版本对不上 —— 这些只在真实恢复时才暴露。必须自动化恢复验证：定期把备份恢复到隔离环境，跑 checksum + 抽样查询 + 起服务，通过才算备份成功。校验结果计入监控。
模块 6

应用层多活与流量切换

数据层复制好了，接下来是"流量怎么切"。这是灾备里最容易被低估的部分 —— 数据库切了，流量切不过去，业务照样全停。

流量切换手段对比

手段切换速度问题
DNS 切换分钟级（受缓存拖累）TTL 常被运营商/客户端缓存无视；长连接（gRPC/WebSocket）不随 DNS 重连
GSLB秒~分钟级按健康检查调度，成本高；健康检查判死有延迟
四层/七层 LB秒级需跨机房专线 + LB 集群自身高可用；连接引流（connection draining）要配
服务网格秒级region-aware 路由精细，但引入网格自身复杂度
# DNS 切流的准备动作（提前 24h 就要做）
# 1. 把故障域的 TTL 从 3600 降到 60，等旧 TTL 自然过期
# 2. 客户端侧排查：JVM 默认可能长时间缓存解析（networkaddress.cache.ttl）
#    长连接服务要做"连不上时重建连接"而不是复用旧 TCP
# 3. 切流后观察旧 IP 的连接数是否归零，判断流量是否真的搬完

# 灰度切流比例（七层 LB / GSLB 权重）
# 1% 观察 5min → 10% → 50% → 100%，每级看错误率/延迟/业务指标
# 错误率 > 0.5% 或 P99 延迟劣化 50% → 自动回切

数据一致性：多活的核心难题

模式做法与代价
单元化分片用户按 ID 哈希路由到"单元"（完整应用栈+数据分片），单元内数据闭环，跨单元走 RPC。大规模多活的主流，但改造量大
异步 binlog 同步主写一侧，变更经 binlog/WAL 异步同步到对侧（秒级最终一致）。简单，但对侧是只读副本；双向同步要处理冲突
双写应用同时写两侧。反模式：主键冲突、库存超卖、幂等和回滚复杂度爆炸
跨区事务2PC/TCC 在 30ms+ RTT 下每次提交多等 60ms+，只适合低频强一致操作
脑裂是多活的第一大敌：网络分区时两侧都能写，数据分叉且无法自动合并。防御三板斧：① fencing —— 少数派侧自动摘除自己（Redis min-replicas-to-write、PG quorum、MGR 多数派、VIP+仲裁）；② 写路径集中 —— 同一数据分片同一时刻只有一个可写单元；③ 对账兜底 —— 检测到分叉后按时间戳/版本号仲裁，补偿差异。宁可短暂停服务，不可长期双写分叉。
模块 7

灾备演练、切流决策与回切

灾备能力的唯一证据是演练。没演练过的架构等于不存在 —— 切换脚本里的一个错误参数、一个过期的证书，都只在真实执行时才暴露。

演练分级与频率

演练类型频率验证什么
备份恢复演练每月备份可用、恢复耗时、恢复后数据正确（对 RTO/RPO 取证）
桌面推演每季度runbook 完整性、决策链、人员分工与联系方式
单机房故障演练每季度断网/断电/杀进程下系统自动切换是否成立
全链路切换演练每半年 / 大版本后端到端切流 + 业务指标 + 回切全流程
混沌工程常态化持续（小爆炸半径）Chaos Mesh / ChaosBlade 随机注入故障，逼系统自愈

# 演练前（T-3 天）
# □ runbook 评审：每一步命令、回退点、预期输出写清楚

# □ 人员排班：主操作、复核、业务确认、观察员各就各位

# □ 与业务方约定演练窗口和允许的中断时长

切流决策矩阵

故障情形决策
单实例/单 AZ 故障不切机房。AZ 内自动/人工切换，秒级恢复
机房网络抖动，<RTO 预算观察 + 本地止损；频繁抖动反而说明链路问题，切过去也白搭
机房级故障，持续 > RTO 预算启动切流：按 runbook 提升备库、切流量、逐服务验证
数据层故障但应用正常先尝试数据库层面切换（提升从库），再评估是否整体切流
不确定根因先止损（限流/降级）再定位；严禁在没搞清状况时双写两侧

回切：比切换更危险的环节

老机房恢复：修复故障，以"从库"身份重新加入，反向同步数据（新机房 → 老机房），直到滞后归零。
数据校验：两侧 checksum / 行数对账，差异补偿。对不上就继续追，不追平不切回。
停写新机房：短暂停写（或进只读），完成最后一轮同步，确保无新写入丢失。
切回老机房：灰度回切流量，观察业务指标；回切同样要挑低峰窗口。
回切三不原则：① 不追平不切（先同步校验再动流量）；② 不在高峰切（回切也是变更）；③ 不省演练（回切脚本执行频率更低，生疏程度更高，出事概率更大）。很多团队切流很顺，回切时把故障期间的新数据全冲掉了 —— 因为反向同步忘了开。
模块 8

十个线上坑

1
只备份、从不演练
备份文件损坏、密码丢失、恢复步骤没人走过、依赖组件版本不匹配 —— 全部只在真实灾难时暴露。自动化恢复验证（起容器 + checksum + 抽样查询）是唯一解。
2
脑裂：两侧同时可写
网络分区后两个机房都接写，数据分叉无法自动合并。必须有 fencing：少数派自断（Redis min-replicas-to-write、PG quorum、MGR 多数派），宁可短暂停服不可长期分叉。
3
DNS 切换切不动
TTL 被运营商 LocalDNS 和客户端缓存无视，JVM 默认长时间缓存解析，gRPC 长连接更是不随 DNS 重建。提前降 TTL、应用层重连策略、必要时走 LB 而不是 DNS。
4
双写一致性灾难
两机房同时写订单：主键冲突、库存超卖、重复消息、回滚只回一半。用单元化分片让数据有唯一写入口，或主备 + 异步同步，别双写。
5
跨区延迟拖垮事务
同步复制跨地域每次提交多等 2×RTT（30ms 延迟 = 60ms+ 写入劣化），大事务尤其致命。同步只做同城，跨地域异步 + binlog 补偿，或改造为单元内闭环。
6
半同步超时降级无人知晓
从库一抖，半同步自动降级异步，RPO 从 0 变分钟级，但没人看 Rpl_semi_sync_source_status。对该状态做告警，降级即意味着灾备承诺失效。
7
回切顺序错误
先切流量再追数据，故障期间新机房的数据被反向同步冲掉。正确顺序：老机房恢复 → 反向同步 → 校验追平 → 停写 → 切回。
8
只切了数据库，漏了中间件
DB 切到备机房了，Kafka 消费者 offset、Redis、注册中心、定时任务、第三方回调地址还在老机房，服务看似恢复实际半瘫。切流清单要覆盖全部有状态组件。
9
RPO/RTO 拍脑袋定级
没和业务算过停机损失，定级形同虚设：L0 业务配了异步复制，L3 业务烧钱上双活。按每分钟损失倒推，并定期用演练数据修正。
10
演练环境与生产配置漂移
演练时脚本跑得顺，真实故障时因为生产多了几个服务、证书过期、参数不同而失败。演练必须用生产配置副本，变更加入演练清单，每次大版本后补演。
自测

六道题

1. 要做到 RPO=0（数据零丢失），最低配置是？
正确答案：同城同步复制 + 切换前确认回放。备份和异步复制都有"最后一个事务丢失"的窗口，只有同步复制能保证提交的事务已在对侧。注意半同步的超时降级窗口和"收到 binlog 但未应用"的细节，严格场景要额外校验从库滞后为 0。
2. 国标 GB/T 20988-2007 中最高的灾备等级是？
正确答案：第 6 级。特征是数据零丢失 + 异地双活/多活架构，RPO=0、RTO 分钟级。第 5 级是实时数据传输 + 完整设备（异步复制 + 快速恢复）。等级每升一级，都是成本量级的跨越。
3. MySQL 半同步复制等待从库 ACK 超时后，会发生什么？
正确答案：降级为异步。这是可用性优先的设计：不阻塞业务，但此窗口内主库宕机会丢数据。所以必须监控半同步状态（Rpl_semi_sync_source_status），降级即触发告警 —— 否则你的"同城双活"实际上在静默地裸奔。
4. 防止 Redis 主从脑裂丢数据的有效参数是？
正确答案：min-replicas-to-write + max-lag。当健康从库不足时主库拒绝写入，宁可短暂拒绝服务也不在"可能分叉"的状态下收写。AOF 和 backlog 解决的是别的层面（持久化和复制缓冲），不防脑裂。
5. 从灾备机房切回主机房的正确顺序是？
正确答案：先追平校验，再切流量。先切流量会把故障期间新机房产生的新数据覆盖丢失；双写合并是数据分叉的地狱。回切比切换更危险，因为执行频率低、人员生疏，必须写进 runbook 并演练。
6. "3-2-1 备份原则"指的是？
正确答案：3 份副本、2 种介质、1 份异地。它防三类风险：单副本损坏（多份）、单类介质批量故障（异介质）、机房级灾难（异地）。现代实践再加一条：异地副本要不可变（WORM/对象锁），防勒索软件顺着备份通道删过来。

核心参数速查

# MySQL 主库
log-bin=mysql-bin
binlog-format=ROW                # 跨机房复制必须 ROW
gtid-mode=ON                     # 位点对齐从文件+偏移变事务号
binlog_expire_logs_seconds=604800 # binlog 保留 7 天，先确认下游消费再清

# MySQL 半同步
rpl_semi_sync_source_enabled=ON
rpl_semi_sync_source_timeout=5000  # ms；超时降级异步，需配告警

# PostgreSQL
wal_level=replica
max_wal_senders=10
synchronous_commit=on
synchronous_standby_names='ANY 2 (s1, s2)'   # quorum 比 FIRST 抗单点抖动
archive_mode=on                             # WAL 归档 = PITR 的原料

# Redis
min-replicas-to-write 1
min-replicas-max-lag 10        # 从库不足时主库拒绝写，防脑裂
appendonly yes                 # AOF 降低单实例故障的丢失窗口

术语表

术语一句话解释
RPO恢复点目标：故障时最多能丢多少数据，由复制/备份间隔决定
RTO恢复时间目标：故障后多久业务必须恢复，由架构决定
MTTR实际平均修复时间；RTO 是承诺，MTTR 是现实
同城双活两机房同步复制同时服务，RPO=0、RTO 分钟级
两地三中心同城双活 + 异地冷备，兼顾 RPO 与地域级灾难
异地多活多地域同时服务，靠单元化分片 + 异步同步
单元化按用户维度分片，每个单元闭环处理自己的流量和数据
半同步复制主库提交前等至少一个从库确认收到 binlog，超时降级异步
MGR 组复制MySQL 基于 Paxos 多数派的强一致复制，适合同城
流复制PG 的物理复制：WAL 记录流式传到备库回放
复制槽PG 中保证 WAL 不被提前回收的机制，备库掉线会积累
WAL / binlogPG/MySQL 的变更日志，PITR 和复制的原料
PITR时间点恢复：全量备份 + 日志重放到指定时刻
脑裂网络分区导致多个节点同时认为自己是主，数据分叉
Fencing强制隔离故障/少数派节点的机制，防脑裂的核心手段
GSLB全局负载均衡，按健康检查在多地之间调度流量
3-2-1 原则3 份副本、2 种介质、1 份异地的备份策略
GFS 保留策略日备/周备/月备/年备的分层保留轮换
混沌工程受控注入故障验证系统韧性（Chaos Mesh/ChaosBlade）
切流 / 回切把流量搬到灾备机房 / 故障恢复后搬回，后者风险更高
下一步怎么练：用开始前的环境完成这五件事 —— ① 把 MySQL 配成半同步，然后停掉从库，观察主库降级与恢复；② 做一次 XtraBackup 全量 + binlog，把库删个表再按时间点恢复；③ PG 建复制槽，拔掉备库网线 10 分钟，观察主库 pg_wal 增长，再恢复；④ 给 Redis 配 min-replicas-to-write，停掉从库试写入，看拒绝行为；⑤ 写一份单机房切换 runbook，按 checklist 走一遍并记录每个时间点，算出你的真实 RTO。
