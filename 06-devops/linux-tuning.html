二十分钟学透 Linux 系统调优

调优不是抄 sysctl 大全，是先建立观测框架，再逐个证伪。这篇以 USE 方法论为主线，覆盖 CPU/内存/磁盘/网络四大资源的真实参数与稳妥值，以及"一次只改一个"的工程纪律。

覆盖 8 大模块 3 维 USE 模型 25+ 个真实内核参数 10 个线上坑 6 道自测
20:00
建议起一台 Linux 虚拟机跟着敲：vmstat 1、iostat -xz 1 先跑起来
开始前

工具先行：没观测就没调优

# 安装观测套件（sysstat 提供 sar/iostat/pidstat/mpstat）
apt install sysstat procps iproute2 linux-tools-common numactl fio ethtool

# 60 秒健康快检（Brendan Gregg 的经典十条，按顺序敲）
uptime                    # 负载均值：1/5/15 分钟，对比 CPU 核数判断过载趋势
dmesg -T | tail -25       # OOM、ECC 错误、磁盘 I/O error 都在这里
vmstat 1                  # r 列（等 CPU 的进程）持续大于核数 = CPU 饱和
mpstat -P ALL 1           # 每颗核心的 %usr/%sys/%iowait/%soft，定位单核瓶颈
pidstat 1                 # 哪个进程在烧 CPU
iostat -xz 1              # %util、await、avgqu-sz：磁盘饱和度与延迟
free -m                   # available 才是真实可用，别只看 free
sar -n DEV 1              # 网卡吞吐与错包
ss -s                     # socket 汇总：TIME_WAIT 堆积、recv-q 积压
top                       # 总览，重点看 wa 与 st（被偷走的时间，虚拟机）

# 当前生效的内核参数（读比写重要，调优前先存档现状）
sysctl -a > /root/sysctl-before.txt
sysctl -a --pattern 'net.ipv4.tcp' | sort
铁律：改任何参数之前，先把当前值全部导出存档。出了问题才知道改回了什么；团队复盘时，"我改了哪 3 个参数"必须能一句话说清。参数文件放 /etc/sysctl.d/99-tuning.conf，不要直接编辑 /etc/sysctl.conf，否则升级时被覆盖。
模块 1

性能观测方法论：USE 方法

USE（Utilization / Saturation / Errors，Brendan Gregg 提出）是排查性能问题的检查清单：对每个资源问三个问题，答不上来就说明观测有盲区。

维度含义典型症状
U 利用率资源被使用的时间比例（CPU %、磁盘 %util）CPU 90% util，但延迟正常 = 饱和的前兆
S 饱和度工作排不上队的程度（run queue、await、backlog）饱和才是用户可感知卡顿的直接原因
E 错误错误事件计数（drop、retrans、CRC、OOM）错误常被忽略，但它们是根因（网卡丢包、磁盘坏道）

把 USE 套到四大资源上

资源U（利用率）S（饱和度）E（错误）
CPU%usr/%sys/%iowaitrun queue（vmstat r）、调度延迟context switch 异常、迁移风暴
内存used/available 比例swap in/out（si/so）、major page faultOOM kill 计数
磁盘%utilavgqu-sz、await 排队I/O error、重试、smart 错误
网络带宽使用率recv-q/send-q 积压、syn backlog 满drop、retransmit、CRC error
USE 的正确用法：从错误（E）开始查——错误最便宜也最能一锤定音；再看饱和度（S）——它直接对应用户体验；利用率（U）放最后，因为高 util 不一定是问题（满载但无排队 = 健康的流水线）。顺序反过来的人，最容易把"CPU 高"当成本质问题。
模块 2

CPU 调优：调度、亲和性与中断

调度器与进程优先级

# CFS（完全公平调度器）是现代 Linux 默认，两个相关参数
kernel.sched_latency_ns       # 默认 24000000（24ms）：一个调度周期内所有任务各跑一次的目标
kernel.sched_min_granularity_ns  # 默认 3000000（3ms）：单次运行的最短时间，防过度切换
# 交互多的桌面/开发机可微调，生产服务器保持默认即可——收益小、风险大

# 优先级工具链（-20 最高优先，19 最低）
nice -n 10 ./batch-job          # 启动时降优先级，别和在线服务抢 CPU
renice 5 -p 12345               # 运行中改
chrt -f 50 ./realtime-task      # SCHED_FIFO 实时策略（慎用，能饿死普通任务）

# 把进程绑到指定核心（缓存亲和性、NUMA 局部性）
taskset -c 2,3 ./app            # 启动绑定
taskset -pc 2,3 12345           # 运行中绑定
# 系统服务固定绑核（nginx worker、redis、DPDK 应用常用）
systemctl set-property app.service CPUAffinity=2-5

中断亲和性：别让中断挤爆 CPU0

# 看当前中断分布（网卡队列中断、定时器）
cat /proc/interrupts
watch -n1 'cat /proc/interrupts | head -20'

# 网卡多队列中断手动分发到不同核心（irqbalance 是自动方案）
echo 2 > /proc/irq/32/smp_affinity      # 32 号中断只走 CPU1（位掩码：1=CPU0，2=CPU1，3=CPU0+1）
echo 4 > /proc/irq/33/smp_affinity      # 33 号中断走 CPU2

# 软中断（网络收包 softirq）观察
cat /proc/softirqs | grep NET_RX

# 自动化：装 irqbalance 守护进程，默认按负载自动均衡
apt install irqbalance && systemctl enable --now irqbalance
# 做了手动绑核/隔离核心的场景要停用它：systemctl stop irqbalance

核心隔离：给关键进程留"自留地"

# 内核启动参数（/etc/default/grub 的 GRUB_CMDLINE_LINUX，改完 update-grub）
isolcpus=2,3 nohz_full=2,3 rcu_nocbs=2,3
# isolcpus=2,3        从调度器隔离 CPU2/3，普通任务不会上去
# nohz_full=2,3        这两个核停止周期性 tick 中断（自适应 tick）
# rcu_nocbs=2,3        RCU 回调不在隔离核上执行
# 然后 taskset -c 2,3 把延迟敏感进程（DPDK、行情、交易）钉上去
# 代价：这两个核不能被普通进程用到，核心数要预留，普通业务机别碰

# CPU 频率调节（ Governors：performance / powersave / schedutil / ondemand ）
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
echo performance > /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor   # 延迟敏感场景锁最高频
isolcpus 不是"高性能开关"：它隔离了核，也就放弃了这些核上的自动负载均衡。调度错了（关键进程没绑上去，普通进程也上不去）会造成"一半核闲着、服务在剩下一半核上排队"。只有明确知道自己要隔离什么进程时才用，且必须配合绑核验证。
模块 3

内存调优：swappiness、overcommit 与 OOM

vm.swappiness 的真实语义

它控制"换出匿名页（进程堆内存）的倾向"，不是"用 swap 的程度"。值越大越倾向把冷的匿名页换出、保留文件缓存（page cache）。

取值行为
0除非接近 OOM 否则不换出。不等于"禁用 swap"，紧急时仍会换
10数据库/Redis 类延迟敏感服务的推荐值，尽量用内存、少换出
60（默认）平衡策略，桌面/混合负载合理
100激进换出，最大化 page cache。几乎不适合服务端
# 设置（重启永久生效）
sysctl -w vm.swappiness=10
echo "vm.swappiness = 10" >> /etc/sysctl.d/99-tuning.conf

# 观测 swap 行为（si/so 不为 0 就是在换页）
vmstat 1 | awk 'NR>2 {print "si="$7" so="$8}'
sar -W 1                        # pswpin/pswpout 每秒换页统计

overcommit 与 OOM Killer

# 内存超配策略：进程申请的内存总和可以超过物理内存吗？
vm.overcommit_memory = 0        # 默认：启发式判断，明显过分的申请才拒
vm.overcommit_memory = 1        # 永远允许（有 swap 兜底的虚机常见，但 OOM 风险大）
vm.overcommit_memory = 2        # 严格模式：不允许超过 RAM+swap×ratio，fork 多的服务会被拒
vm.overcommit_ratio = 50        # 配合 mode 2 使用：允许的超配比例
# 建议：绝大多数场景保持默认 0。JVM/数据库这类吃内存大户别动这个参数

# OOM 保护：给关键进程调低"被杀分数"（-1000 = 几乎免死）
grep -E 'oom_score|Killed' /var/log/kern.log
echo -1000 > /proc/$(pgrep -f 'redis-server')/oom_score_adj
# systemd 服务写法（重启也生效）：
# OOMScoreAdjust=-500

# 保留空闲内存下限，防止突发分配直接把内存抽干
vm.min_free_kbytes = 131072     # 16GB 机器量级参考，太小则突发分配失败，太大则浪费内存

# 透明大页 THP：数据库/Redis 官方建议关闭或 madvise
cat /sys/kernel/mm/transparent_hugepage/enabled
echo madvise > /sys/kernel/mm/transparent_hugepage/enabled   # 只对显式申请的程序生效
# Redis 场景直接 never；JVM 用 -XX:+UseTransparentHugePages 自己管理更稳
"swappiness=0 最好"是流传最广的误读。0 只是把换出推迟到 OOM 边缘，该换的时候照样换，且换的时候更凶（一次性大量换出造成延迟尖峰）。延迟敏感服务用 10，配合足够内存 + 监控 si/so，比盲目归零理性得多。
模块 4

磁盘 IO 调优：调度器、RAID 与挂载

I/O 调度器选择

调度器适用场景
noneSSD/NVMe 首选。闪存没有寻道时间，合并排序反而添延迟
mq-deadlineSATA HDD 稳妥默认，保证读请求不被写饿死
kyber面向延迟目标的调度器，可按读写设延迟上限
bfq桌面/多进程公平场景，吞吐不是最优但响应好
# 查看与切换（nvme 设备通常只有 none）
cat /sys/block/sda/queue/scheduler
echo none > /sys/block/sda/queue/scheduler        # SSD 用 none
echo mq-deadline > /sys/block/sdb/queue/scheduler # HDD 用 mq-deadline

# 预读：顺序读加大（如 8MB），随机读保持默认 128KB
blockdev --getra /dev/sda
blockdev --setra 4096 /dev/sda        # 单位是 512B 扇区：4096×512 = 2MB

# 队列深度（NCQ）：HDD 设 31，SSD 可提高
echo 31 > /sys/block/sda/queue/nr_requests

# 脏页回写：写密集型服务调大背景阈值，减少同步刷盘卡顿
vm.dirty_background_ratio = 5         # 默认 10，后台开始回写的脏页比例
vm.dirty_ratio = 20                   # 默认 20，同步阻塞写入的硬上限，谨慎调大
# 或按绝对值设（大内存机器更直观）：
# vm.dirty_background_bytes = 268435456（256MB）
# vm.dirty_bytes = 1073741824（1GB）

RAID 级别怎么选

级别磁盘利用率容错适用
RAID 0100%无纯性能、可重建数据（缓存、临时盘）
RAID 150%1 块盘坏系统盘、小容量高可靠
RAID 5(n-1)/n1 块盘坏读多写少。大盘重建风险高，慎用
RAID 6(n-2)/n2 块盘坏大容量数据盘主流选择
RAID 1050%每镜像组 1 块数据库/随机写密集首选，无校验计算开销

挂载参数

# /etc/fstab —— noatime 是性价比最高的一条
UUID=xxx /data ext4 defaults,noatime,nodiratime 0 2
UUID=yyy /logs xfs  defaults,noatime             0 2

# noatime：读文件不再更新 inode 访问时间
#   效果：日志/图片类随机读场景，写 IO 可降 30%~50%（原来每次 read 变 read+元数据写）
#   代价：atime 信息不准。99% 的服务端场景不需要 atime

# 其他常用组合：
#   data=writeback     崩溃可能丢数据但快（有 BBU/掉电保护时可用）
#   barrier=0          同上有保护时考虑，默认别关
#   discard/noatime + SSD 的 TRIM：现在 ext4/xfs 默认在线 discard，无需 mount 参数

# 验证基准：fio 压测（顺序/随机、读/写分开测）
fio -name=randread -rw=randread -bs=4k -iodepth=32 -size=4G -runtime=60 -ioengine=libaio -direct=1
fio -name=randwrite -rw=randwrite -bs=4k -iodepth=32 -size=4G -runtime=60 -ioengine=libaio -direct=1
磁盘调优的优先级：① 应用层少写（合并写、批量落库）→ ② 挂载 noatime → ③ 调度器与队列深度 → ④ RAID 级别重估 → ⑤ 才是硬件（NVMe、缓存卡）。跳过低层级直接买硬件的团队，往往在为应用层的写放大买单。
模块 5

网络调优：内核参数与 bypass

连接堆积三件套：backlog 全链路

一条 TCP 连接的 backlog 由三段组成：网卡队列 → 内核半连接/全连接队列 → 应用 accept 队列，任何一段满都会丢包或延迟。

# 1. 应用 accept 队列上限（受内核 somaxconn 封顶）
net.core.somaxconn = 4096            # 默认 128（老内核）/4096（新内核），高并发网关调到 4096+
# 注意：nginx 的 listen 80 backlog=511 也要一起改，否则内核调大了应用端还是 511

# 2. 半连接队列（SYN 洪水、握手积压）
net.ipv4.tcp_max_syn_backlog = 4096   # 默认 1024/2048，突发连接场景调大
net.ipv4.tcp_syncookies = 1           # 默认 1，半连接满时用 cookie 防 SYN flood，保持开启

# 3. 网卡收包队列（数据包在内核里排队等协议栈处理）
net.core.netdev_max_backlog = 5000    # 默认 1000，万兆网卡/小包高 PPS 必调
ethtool -g eth0                      # 同时确认网卡硬件 ring buffer（rx/tx 队列深度）拉满
ethtool -G eth0 rx 4096 tx 4096

# 观测 backlog 溢出（丢包就在这里体现）
nstat -az | grep -E 'TcpExtListenOverflows|TcpExtListenDrops|TcpExtTCPBacklogDrop'
ss -lnt | awk '{print $1}' | sort | uniq -c   # Recv-Q 列堆积 = 应用 accept 不过来

TIME_WAIT 与端口

# TIME_WAIT 堆积：高并发短连接的标配问题
net.ipv4.tcp_tw_reuse = 1             # 允许复用 TIME_WAIT socket 作为【出向】连接，安全且有效
# tcp_tw_recycle 在 4.12 已被移除，网上老教程还在教它——见到就绕道
net.ipv4.tcp_fin_timeout = 30         # FIN_WAIT_2 超时，默认 60，可降到 30
net.ipv4.ip_local_port_range = 10240 65535   # 出向连接可用端口范围，默认 32768 60999
# 治本还是上长连接池（HTTP keep-alive / 连接池），内核参数只是扩天花板

# 查看 TIME_WAIT 总量与分布
ss -s
ss -tan state time-wait | wc -l

缓冲区与 keepalive

# TCP 缓冲区自动调节（默认开），min/default/max 三档（字节）
net.ipv4.tcp_rmem = 4096 262144 16777216     # 收缓冲：4KB / 256KB / 16MB
net.ipv4.tcp_wmem = 4096 262144 16777216     # 发缓冲同款
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
# 大带宽长肥管道（跨国/10G+带宽×高延迟）必须调大，否则带宽上不去
# 内网低延迟小包场景保持默认，调大反而浪费内存

# keepalive：及时发现半死连接
net.ipv4.tcp_keepalive_time = 600     # 默认 7200 秒，空闲 10 分钟后开始探测
net.ipv4.tcp_keepalive_intvl = 30     # 探测间隔
net.ipv4.tcp_keepalive_probes = 3     # 3 次无响应判死

# 观测重传率（健康网络 retrans 比例应低于 0.1%）
sar -n ETCP 1 | grep -v retrans
nstat -az | grep TcpRetransSegs

conntrack：NAT/防火墙机器的隐形炸弹

# 容器/K8s 节点、网关机器必看
net.netfilter.nf_conntrack_max = 262144      # 跟踪表上限，默认常为 65536（偏小）
net.netfilter.nf_conntrack_buckets = 65536   # 哈希桶数，建议 = max/4
# 满了的现象：dmesg 报 "nf_conntrack: table full, dropping packet" → 随机丢连接
dmesg | grep conntrack
# 短期应急：调大 max；长期：减少 NAT 跳数、用 IPVS/直接路由模式、按需调小超时
net.netfilter.nf_conntrack_tcp_timeout_established = 86400

内核 bypass（简述）

DPDK
用户态收发包，绕过内核协议栈，绑定大页 + 独占核。PPS 千万级，SDN/网关常用，开发成本高
XDP / AF_XDP
内核内/内核旁路的可编程包处理，eBPF 加持。防火墙、负载均衡、DDoS 防御的新一代选择
busy poll
net.core.busy_read=50 让 socket 读自旋等数据，延迟换 CPU，只适合极端低延迟场景
网络调优的层次：内核参数解决"排队太长"；架构解决"连接太多"（长连接、连接池、LB 横向扩展）；bypass 解决"内核协议栈本身是瓶颈"。90% 的团队到不了第三层，把前两层做扎实就够。
模块 6

ulimit 与 systemd 资源限制

ulimit 与 limits.conf

# 查看当前 shell 的限制
ulimit -a
ulimit -n                  # open files：默认常为 1024，高并发服务远远不够
ulimit -u                  # max user processes：默认常为 4096 或 unlimited

# 永久生效：/etc/security/limits.conf（注意：只对 PAM 登录的会话生效）
*  soft  nofile  65535
*  hard  nofile  65535
*  soft  nproc   65535
*  hard  nproc   65535
# 按用户/组收紧比全局放开更安全：
# redis soft nofile 128000

# 系统级总量
fs.file-max = 2097152
fs.nr_open = 1048576       # 单进程打开文件数硬上限，调大 nofile 的前置条件

# 检查某进程当前实际限制
cat /proc/$(pgrep -f nginx)/limits | grep -E 'open files|processes'

systemd 才是服务的实际控制者

# 经典陷阱：limits.conf 改了，systemd 服务不生效！
# 因为 systemd 服务不经过 PAM 登录会话，limits.conf 对它无效
# 正确做法：用 drop-in 覆盖单元文件
systemctl edit nginx.service
# 在弹出的编辑器里写：
[Service]
LimitNOFILE=131070
LimitNPROC=8192
TasksMax=4096
MemoryMax=4G
CPUQuota=200%
IOWeight=500
OOMScoreAdjust=-500
Restart=on-failure
RestartSec=5
# 验证：systemctl daemon-reload && systemctl restart nginx
systemctl show nginx -p LimitNOFILE -p TasksMax

systemd 资源限制速查

指令控制对象
LimitNOFILE=打开文件数（socket 也算文件，高并发服务必调）
LimitNPROC=进程/线程总数（线程也占坑，多线程服务常撞这个）
TasksMax=cgroup 级任务数上限，默认 15% 内核 threads.max
MemoryMax=cgroup 内存硬顶，超了触发 cgroup OOM
MemoryHigh=软顶：超了回收并限流，不到杀的程度
CPUQuota=CPU 时间配额，200% = 2 个核
IOWeight=cgroup v2 IO 相对权重（10~1000）
OOMScoreAdjust=被系统 OOM Killer 选中的倾向，负值更安全
"too many open files" 排查口诀：先 lsof -p PID | wc -l 看是不是连接泄漏（最常见），再 cat /proc/PID/limits 确认限制值，最后才是调大。不查泄漏就调 limit，只是把爆炸时间推迟。
模块 7

调优流程：测量 → 假设 → 验证 → 固化

测量（建立基线）：记录调优前的 P99 延迟、吞吐、错误率、资源利用率。没有基线就没有"变好了"
定位瓶颈：用 USE 检查清单找到饱和/错误点，反对"感觉是网络问题"式猜测
提出假设："TCP backlog 满导致重传"→ 假设可证伪，有观测指标支撑
一次只改一个参数：同时改 5 个，好了不知道为什么好，坏了不知道回滚哪个
压测验证：用 wrk/fio/sysbench 复现负载，对比基线数据，记录前后数值
固化：写进 /etc/sysctl.d/、grub、fstab、systemd drop-in，全部纳入配置管理（Ansible/Puppet）
长期监控：调优不是一次性的，把指标接监控，回归立即发现
四条纪律：① 不抄陌生参数——每个参数都能说出"解决什么饱和/错误"再改；② 默认值往往是权衡的最优解，改它要有数据；③ 内核版本差异——4.x/5.x/6.x 默认值不同，云厂商镜像还有自己的定制，先 sysctl -a 看现状；④ 改完留文档：参数、原值、新值、原因、验证结果、日期、负责人。三个月后你会感谢自己。
模块 8

场景案例：真实组合拳

案例 1：Nginx 高并发网关（10 万长连接 + 突发短连接）

# /etc/sysctl.d/99-tuning.conf
net.core.somaxconn = 65535
net.ipv4.tcp_max_syn_backlog = 65535
net.core.netdev_max_backlog = 10000
net.ipv4.tcp_tw_reuse = 1
net.ipv4.ip_local_port_range = 10240 65535
net.ipv4.tcp_keepalive_time = 600
fs.file-max = 1048576

# nginx.conf 配套（不改应用端，内核白调）
worker_rlimit_nofile 65535;
events { worker_connections 65535; use epoll; multi_accept on; }
# listen 443 ssl backlog=65535;   ← backlog 要和 somaxconn 匹配
# systemd drop-in: LimitNOFILE=65535
# 结果参考：TIME_WAIT 从 6 万降到 1 万以内，accept 队列溢出归零

案例 2：Redis/数据库主机（延迟敏感）

# 核心原则：让数据待内存，别被换出去；别让后台任务抢延迟
vm.swappiness = 10
vm.overcommit_memory = 1        # 有 BGSAVE fork 需求的场景常见（配合足够内存）
vm.min_free_kbytes = 1048576    # 64GB 机器量级，按物理内存 1%~1.5% 取
net.core.somaxconn = 4096
# THP 关掉（Redis 官方建议）：
echo never > /sys/kernel/mm/transparent_hugepage/enabled
# 关 NUMA 自动迁移，减少延迟抖动（配合绑核使用时）
kernel.numa_balancing = 0
# 磁盘：SSD 用 none 调度器 + noatime 挂载，AOF 落盘延迟从 8ms 降到 2ms 级

案例 3：K8s 节点 / NAT 网关（连接数爆炸）

# 症状：dmesg 报 conntrack table full，随机连接超时
net.netfilter.nf_conntrack_max = 1048576
net.netfilter.nf_conntrack_tcp_timeout_established = 600
net.netfilter.nf_conntrack_buckets = 262144
net.ipv4.tcp_tw_reuse = 1
# 根治手段：Service 走 IPVS/直接路由减少 NAT 层数，
# 或升级到 eBPF 替代 kube-proxy iptables 模式（Cilium 等方案）
# 参数只是把爆炸阈值抬高 16 倍，架构才能治本

案例 4：日志/备份写入型主机（吞吐优先）

vm.dirty_background_ratio = 10
vm.dirty_ratio = 40              # 大内存机器放宽同步回写，减少 write 卡顿
vm.dirty_expire_centisecs = 3000
# 挂载 noatime + data=writeback（有 BBU/掉电保护前提下）
# 调度器 mq-deadline；预读调大适配顺序写：blockdev --setra 8192 /dev/sdb
# fio 验收：顺序写 IOPS 提升 15%+，await 波动收敛
案例的共同结构：先有症状数据（溢出计数、si/so、await）→ 改一个方向 → 验收指标 → 固化 + 监控。抄参数表谁都会，带着假设改参数才是调优。
排坑

十个线上坑

1
照抄网上 sysctl 大全一把梭
30 个参数一次性上线，性能没变，云厂商镜像升级后行为诡异。每个参数必须能对应一个观测到的问题，否则不动。
2
以为 vm.swappiness=0 是"禁用 swap"
0 只是推迟换出，OOM 边缘一次性大量换出反而造成延迟尖峰。延迟敏感服务用 10，并监控 si/so。
3
忘加 noatime，读操作也在写盘
随机读场景每次 read 附带 inode 元数据写，IO 凭空多三成。fstab 加 noatime 一行解决，代价几乎为零。
4
还在教/用 tcp_tw_recycle
该参数在 4.12 内核已被移除，且历史上在 NAT 环境下会随机掐断连接。用 tcp_tw_reuse=1 + 连接池。
5
conntrack 表打满，丢包丢得莫名其妙
容器/NAT 机器默认 65536 条很快打满，dmesg 报 table full。调大 max/buckets，同时按需缩短 established 超时。
6
改了 limits.conf，服务 limits 没变
systemd 服务不走 PAM 会话，limits.conf 对它无效。必须用 systemctl edit 加 LimitNOFILE，改完 systemctl show 验证。
7
THP 默认 always，数据库延迟周期性抖动
内核 compaction 造成毫秒级卡顿，Redis/MongoDB 官方都建议关。设 madvise 或 never，重启验证。
8
网卡中断全挤在 CPU0
单核 softirq 打满，其他核闲着，PPS 上不去。装 irqbalance，或按队列手动绑核分散中断。
9
overcommit_memory=2 一设，fork 全失败
严格模式下 JVM/Redis 这类预留大内存的进程直接无法启动。默认 0 是权衡解，改它先压测。
10
调完不记录、不监控，出问题无法回退
"好像三个月前改过点什么"。参数文件 + 注释 + 变更记录 + 监控告警，四件套缺一不可。
自测

六道题

1. USE 方法中的 S（Saturation）指的是？
正确答案：饱和度 = 排队程度。利用率高但无排队是健康的；一旦出现排队（CPU run queue、磁盘 avgqu-sz、网络 backlog），用户可感知的卡顿就开始了。
2. 关于 vm.swappiness，正确的说法是？
正确答案：倾向控制，0≠禁用。swappiness 权衡的是"换出冷匿名页"与"保留 page cache"。0 在接近 OOM 时仍会换出且换得更凶；数据库/Redis 推荐 10，并配合 si/so 监控。
3. 挂载参数 noatime 的作用与代价是？
正确答案：去掉 atime 更新。原来每次 read 会附带一次元数据写，日志/图片类随机读场景 IO 可降 30%+。服务端几乎不需要 atime，这是性价比最高的一条挂载参数。
4. net.ipv4.tcp_tw_reuse = 1 的安全含义是？
正确答案：仅出向 + 依赖时间戳。它复用本机作为客户端的 TIME_WAIT socket（timestamp 机制保证序列号不回绕），对入向服务端口无效。彻底解决 TIME_WAIT 堆积仍要靠连接池/长连接。
5. dmesg 出现 "nf_conntrack: table full, dropping packet"，后果是？
正确答案：随机丢连接。conntrack 表满后新连接无法建立跟踪项，报文被丢弃。应急调大 nf_conntrack_max 与 buckets，根治要减少 NAT 层数或用 IPVS/eBPF 替代 iptables。
6. 给 systemd 服务调大文件描述符限制，正确做法是？
正确答案：systemd drop-in。systemd 服务不经过 PAM 登录会话，limits.conf 与 profile 对它无效。改完用 systemctl show 服务 -p LimitNOFILE 验证生效。

术语表

术语一句话解释
USE 方法Utilization/Saturation/Errors，对每个资源逐项过问的排查清单
饱和度工作排队程度（run queue、await、backlog），直接决定用户体验
CFSLinux 默认的完全公平调度器，按虚拟运行时间分配 CPU
nice进程优先级偏移（-20 最高~19 最低），renice 可运行中调整
CPU 亲和性把进程/中断绑定到指定核心，提高缓存命中与可预测性
IRQ affinity硬件中断的 CPU 绑定位掩码，分散中断避免单核打满
isolcpus内核启动参数，隔离核心给指定进程专用，需配合绑核
swappiness换出匿名页倾向的参数，0≠禁用 swap，延迟敏感推荐 10
overcommit是否允许进程申请内存总量超过物理内存的超配策略
OOM Killer内存耗尽时内核按分数杀进程的机制，oom_score_adj 可调分
THP透明大页，默认开启可能造成数据库/Redis 延迟抖动
min_free_kbytes内核保留的空闲内存下限，防突发分配把内存抽干
I/O 调度器合并排序块层请求的算法（none/mq-deadline/kyber/bfq）
noatime挂载选项，读文件不更新访问时间，大幅降低随机读的写放大
RAID 10条带化镜像，随机写密集与数据库的首选，无校验开销
backlog连接排队三段：网卡队列→内核队列→应用 accept 队列
TIME_WAIT连接主动关闭后的等待态，高并发短连接会大量堆积
conntrack内核连接跟踪表，NAT/容器节点满了会随机丢连接
ulimit / LimitNOFILE进程级文件描述符限制；systemd 服务必须用 LimitNOFILE
DPDK / XDP用户态/内核态可编程包处理，绕过传统协议栈的高性能网络方案
