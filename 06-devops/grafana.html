模块 1

数据源接入

Grafana 本身不存数据，只做查询和渲染。数据源（Data Source）是核心抽象，一个面板可以引用多个数据源的查询。

数据源查询语言典型用途
Prometheus / VictoriaMetrics / ThanosPromQL指标监控的主力组合，兼容同一查询语言
LokiLogQL日志，与指标面板联动排障
Tempo / JaegerTraceQL / 查询 UI链路追踪，从指标下钻到 trace
Elasticsearch / OpenSearchLucene / DSQL已有 ELK 栈时的日志检索
MySQL / PostgreSQL / MSSQLSQL业务报表、运营数据
InfluxDB 2.xFluxIoT/老 InfluxDB 用户
JSON API / CSV / Infinity自定义接内部接口、第三方 SaaS

Prometheus 数据源配置要点

# UI 路径：Configuration → Data sources → Add → Prometheus
URL: http://prometheus:9090              # Grafana 容器内可解析的地址，不是 localhost
Scrape interval: 15s                     # 与 Prometheus 抓取间隔一致
Query timeout: 60s                       # 大查询放宽，别用默认 30s 截断
HTTP Method: POST                        # 长 PromQL 用 POST，避免 URL 超长
Custom query parameters: max_source_resolution=auto   # 让 Prometheus 自动降采样

# 关键：时间序列数据库（TSDB）与仪表盘时间范围的关系
# 面板查 [5m] 的 rate，时间范围选 30 天 → Prometheus 只返回 30 天前的原始点
# → 曲线不平滑，因为 rate 窗口内样本太少。长时间范围要用 recording rule
容器化部署的头号坑：URL 写 localhost。Grafana 跑在容器里时，localhost:9090 指向的是 Grafana 自己。用 docker-compose 的服务名（如 http://prometheus:9090）或主机网关地址。判断方法：数据源页面点 "Save & test"，提示 "Error reading Prometheus: ... connection refused" 基本就是它。
模块 2

Dashboard 结构：变量、行与面板

Dashboard 是 JSON。一个仪表盘由 模板变量（templating）+ 行（Row）+ 面板（Panel）+ 注释（Annotation）+ 链接（Link） 组成。

模板变量：仪表盘的"参数"

变量类型取值来源
query从数据源查询，如 label_values(up, job)
custom手写枚举值，如 env = prod,staging,dev
datasource让用户切换数据源，$datasource 引用
interval自动填充 $__interval，图表下采样粒度
constant / textbox常量 / 输入框，用于传 token 等
adhoc面板顶部动态加标签过滤器（K8s 场景神器）
# 变量配置示例（Dashboard settings → Variables → New）
Name:        job
Type:        query
Data source: Prometheus
Query:       label_values(up, job)          # 所有 job 的取值
Multi-value: true                            # 允许多选，等价 {job=~"$job"}
Include All: true                           # 加一个 All 选项

# 变量在查询里的用法（正则匹配用 =~，等值用 =）
sum by (instance) (rate(http_requests_total{job=~"$job", env="$env"}[$__rate_interval]))

# 变量进阶：串联依赖（第二个变量依赖第一个的取值）
Name:   instance
Query:  label_values(up{job="$job"}, instance)   # 只列 $job 选中的实例
# ↑ 关键设置：Refresh = On time range change / On dashboard load

# 魔术变量（Grafana 自动提供，查询里直接用）
$__interval         # 自动计算的下采样间隔，如 15s
$__rate_interval    # = max($__interval, 4×scrape_interval)，专为 rate 设计
$__range            # 当前时间范围秒数
$__from / $__to     # 时间范围毫秒时间戳
$__dashboard / $__user   # 仪表盘名 / 当前用户名，拼链接常用

Row 与 Panel 组织

# Dashboard JSON 的关键字段（Dashboard settings → JSON model 可看可改）
{
  "title": "API 服务监控",
  "templating": { "list": [ ... ] },       # 模板变量定义
  "time": { "from": "now-6h", "to": "now" },
  "refresh": "30s",                        # 自动刷新间隔
  "rows": [                                # 新版本已折叠成 panels + gridPos
    {
      "title": "核心指标",
      "panels": [
        {
          "type": "timeseries",             # 面板类型
          "title": "QPS",
          "gridPos": { "h": 8, "w": 12, "x": 0, "y": 0 },   # 24 列网格布局
          "targets": [ ... ],               # 查询
          "fieldConfig": { ... }            # 单位、阈值、覆盖
        }
      ]
    }
  ]
}
Row 的两种用法：① 分组折叠——把"详细指标"收进 Row，默认折叠，仪表盘首屏只留核心；② Repeat——Row 按变量重复（如每台机器一行），gridPos 自动重排。面板也可以单独 repeat（按变量渲染 N 个面板），但 repeat 超过 20 个面板会明显拖慢页面。
模块 3

Panel 类型选型

选错面板类型是新手仪表盘显得"不专业"的头号原因。先问：我要看趋势、看单值、看分布，还是看明细？

面板适合看什么不适合
Time series随时间变化的趋势：QPS、延迟、错误率多指标不同量纲时（用双轴或拆面板）
Stat单个数字 + 迷你趋势线：当前 QPS、错误总数需要精确对比多个时间点
Gauge百分比/容量类：磁盘使用率、CPU精确值（人眼读刻度不准）
Bar gaugeTop N 对比：各接口 QPS 排名时间趋势
Table明细与多维度：实例 × 指标矩阵趋势（表格看不出变化）
Heatmap分布随时间的变化：延迟分布、GC 停顿单点值
Logs日志流：错误堆栈、上下文聚合统计（用 metrics）
Piechart / Node graph构成占比 / 服务拓扑严肃的生产监控（可读性差）
# 面板配置关键项（Edit panel → 右侧）
# 1. Query：查询与图例（Legend 决定曲线怎么命名）
Legend: {{instance}} - {{job}}              # 自定义图例，默认是一长串 label
Min step: 15s                               # 与采集间隔一致，防过采样

# 2. Standard options：单位与阈值
Unit: percent (0-100)                       # 别用 raw number，带上单位
Thresholds: 70 (yellow) / 90 (red)          # Stat/Gauge 的变色阈值

# 3. Time series 专属
Stack series: normal                        # 堆叠面积图，看构成
Fill opacity: 10                            # 透明度，多曲线时不打架
# Display: Bars 适合 alert state，Points 适合稀疏数据

Heatmap 的正确打开方式

# Heatmap 需要 histogram 数据，格式 = [bucket上限] × [时间] × [计数]
# Prometheus 查询（Format: Heatmap）：
sum by (le) (increase(http_request_duration_seconds_bucket[$__rate_interval]))

# 或直接查原生直方图序列，Grafana 自动分桶
# 注意：没有 histogram 数据源时，Heatmap 会显示空白 ——
# 这是新手最常见的一个"面板坏了"假象

Logs 面板：从指标跳到日志

# Logs 面板查询 Loki（Data source: Loki）
{job="api", env="$env"} |= "error" | json | line_format "{{.msg}}"

# 与指标面板联动：给 Time series 面板配 Data link
# Edit panel → Data links → 新增：
Title: 查看该实例日志
URL:   /d/logs-dashboard?var-instance=${__field.fields.instance}&from=${__from}&to=${__to}
# 效果：点曲线上一个点，直接跳到该实例该时刻的日志
禁止把 20 条曲线放一个 Time series 面板还不加图例过滤。超过 10 条曲线，颜色就开始重复、图例变成一锅粥。解法：① 用 topk 限制曲线数；② 用变量把多实例拆成 repeat 面板；③ 把次要曲线移到折叠 Row 里。
模块 4

Transform：查询后的数据处理

Transform 在查询结果返回后、渲染前做加工。核心价值：把多个查询 JOIN 成一个表、把时序聚合成单值、重命名隐藏字段。

Transform作用
Join by field按共同字段把多个查询结果横向拼接（如 A 查询的 QPS + B 查询的错误率）
Merge纵向合并多个查询的结果序列
Reduce把每条时序聚合成一个值：mean / max / last / sum / count
Organize fields重命名、隐藏、排序字段 —— Table 面板美化主力
Labels to fields把 label 提升为表格列
Filter by value / name按值或名字过滤序列
Add field from calculation两列做四则运算（如错误率 = 错误 / 总数）
Rows to fields / Group by透视：把行转成列，按维度分组
# 实战：一个 Table 面板同时展示 QPS、P99、错误率（三个查询 JOIN）
# Query A: sum by (instance) (rate(http_requests_total[5m]))     → Value #A
# Query B: histogram_quantile(0.99, sum by (le,instance) (rate(..._bucket[5m])))
# Query C: sum by (instance) (rate(http_requests_total{status=~"5.."}[5m])) / sum by (instance) (rate(...[5m]))

# Transform 1: Join by field → Field: instance
# Transform 2: Organize fields → 重命名 "Value #A" 为 "QPS"，隐藏 Time
# 结果：一行一个实例，三列指标，还能加阈值着色

# 实战：Stat 面板显示"当前错误数"（Reduce: Last）
# Transform: Reduce → Mode: Last → Fields: 保留 Value，去掉 Time
# 面板类型选 Stat，配 thresholds 变色
Transform 在浏览器里跑，大数据量会卡。Join 两个各返回 5000 序列的查询，浏览器要算几万次字段匹配。能在 PromQL 里算的（sum/rate/topk）优先在服务端算，Transform 只做 JOIN、重命名、少量过滤这类轻量活。
模块 5

告警：Unified Alerting

Grafana 8+ 的新告警系统，告警规则存在 Grafana 自己这里（或配置为 Grafana Alertmanager），与 Prometheus 的告警规则是互补关系，不是替代关系。

Unified Alerting 核心概念

概念说明
Alert rule查询 + 条件（A/B 阈值）。可基于任何数据源（PromQL、SQL、Loki）
Condition对查询结果求值：WHEN max() OF A IS ABOVE 90，支持多个条件链
Notification policy路由树：匹配 label → 联系点（Contact point），支持分组等待/间隔
Contact point通知渠道：Email、Slack、钉钉、飞书、Webhook、PagerDuty
Silence / Mute timing静默规则 / 重复静默时间窗（如每晚维护窗口）
# UI 路径：Alerting → Alert rules → New alert rule
# 1. 选查询（可多查询 A/B/C）
#    A: max(1 - avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
# 2. 设条件：WHEN max() OF A IS ABOVE 90
# 3. 设 pending period：5m（等价 Prometheus 的 for）
# 4. 加 label：severity=critical, team=infra
# 5. 配 notification policy 路由到对应 contact point

# 告警状态机：Normal → Pending（条件满足但未过 pending）→ Firing → Normal
# No data 行为可选：Keep last state / Alerting / Normal（防数据断流误判）

Grafana 告警 vs Prometheus 告警：怎么分工

维度Prometheus rulesGrafana Unified Alerting
规则位置Git 里的 YAML，版本清晰Grafana 数据库/Provisioning 文件
recording rules支持，预计算降查询压力不支持预计算
多数据源只有 Prometheus 系Prometheus/Loki/SQL/Elastic 统一告警
规则测试promtool test rules 单测UI 预览，CI 测试较弱
路由能力Alertmanager 成熟（inhibit/silence 全）策略树 + mute timing，够用但略简单
推荐用法基础设施与 SLO 告警的主战场业务面板旁挂的轻量告警、SQL 数据源告警
实践建议：生产告警以 Prometheus rules + Alertmanager 为主（可测试、可 Git 管理、可抑制），Grafana Unified Alerting 用于两类补充：① 数据源不是 Prometheus 的（MySQL 慢查询、ES 集群健康）；② 仪表盘作者自助配置的轻量告警。同一个告警不要两边都配，否则恢复通知能收到四份。
模块 6

仪表盘设计原则

仪表盘是给人看的。目标读者不同，布局完全不同：值班要秒级定位，开发要下钻细节，老板要一个数字。

两套经典方法论

RED 方法（服务视角）
Rate 请求速率 · Errors 错误率 · Duration 延迟分布。
每个微服务一个 RED 仪表盘，是 Google SRE 推荐的微服务监控最小集。
USE 方法（资源视角）
Utilization 利用率 · Saturation 饱和度（队列） · Errors 错误。
每个资源（CPU/内存/磁盘/网卡）一个 USE 仪表盘，基础设施组标配。

可观测性布局：三层下钻

第一层 · 总览：全集群健康度（核心服务 RED + 资源 USE），只放 6~8 个面板，值班 30 秒内看出"哪个服务有问题"
第二层 · 服务下钻：单服务的完整视图（实例列表、依赖拓扑、慢请求 Top、错误日志），开发排障主场
第三层 · 明细：Table/Logs 面板 + 数据链接跳到日志和 trace，"最后一公里"
# 布局纪律（24 列网格）
# 1. 首屏从左到右、从上到下，重要程度递减
# 2. Stat 面板放最上面一行（一眼看到核心数字）
# 3. 相关面板相邻：QPS、错误率、P99 放同一行（同一时间轴方便对比）
# 4. 单位统一：所有延迟用 ms、所有比率用 percent，别一个面板秒一个面板毫秒
# 5. 阈值线：给关键图表加 Threshold（如 SLO 的 99.9% 线），一眼看出是否达标
# 6. 图例精简：Legend {{instance}} 而不是默认的一长串 label
# 7. 时间范围默认 6h，别默认 30 天（rate 窗口在 30 天尺度上没意义）
# 8. 加 Dashboard link：总览 → 服务 → 实例，形成下钻闭环
反模式清单：① 一个仪表盘 50+ 个面板（拆成多个，用 link 串联）；② 每个指标一个面板（同量纲的合并）；③ 3D 饼图、彩虹渐变（数据可视化不是选美）；④ 标题写 "监控"（写清楚监控对象）；⑤ 没有 dashboard description（新成员看不懂每个面板的含义）。
模块 7

Provisioning 与 GitOps

在 UI 里点的仪表盘是"雪花"——独一无二、无法重建、丢失即事故。Provisioning 把数据源、仪表盘、告警全部变成配置文件，进 Git，随 CI 部署。

目录结构与配置

# /etc/grafana/provisioning/ 下的三个目录
provisioning/
├── datasources/
│   └── prometheus.yml        # 数据源
├── dashboards/
│   └── dashboards.yml        # 仪表盘 provider（从哪加载 JSON）
└── alerting/
    ├── contact_points.yml    # 联系点
    └── policies.yml          # 通知策略树

# datasources/prometheus.yml
apiVersion: 1
datasources:
  - name: Prometheus
    type: prometheus
    access: proxy                # 经 Grafana 后端代理（推荐）
    url: http://prometheus:9090
    isDefault: true
    jsonData:
      httpMethod: POST
      timeInterval: 15s

# dashboards/dashboards.yml
apiVersion: 1
providers:
  - name: 'infra-dashboards'     # 逻辑名
    orgId: 1
    folder: 'Infrastructure'     # 仪表盘归属文件夹
    type: file
    disableDeletion: false       # true 则 UI 删不掉，防误删
    updateIntervalSeconds: 30    # 每 30s 重读磁盘
    allowUiUpdates: false        # false = UI 改了不生效，强制 Git 单一事实源
    options:
      path: /var/lib/grafana/dashboards   # 放仪表盘 JSON 的目录
      foldersFromFilesStructure: true     # 按子目录自动建文件夹

仪表盘 JSON 从哪来

# 方式一：Share → Export → Save to file，把 UI 做的仪表盘存进 Git
# 注意：导出前把 Dashboard settings → General → id 清空（uid 保留作链接）

# 方式二：用代码生成（推荐，JSON 手没法维护）
# - Jsonnet / grafonnet：以代码定义面板，输出标准 JSON
# - Terraform provider grafana：data "grafana_dashboard" 生成
# - 社区资源：grafana.com/dashboards 直接下载编号仪表盘 JSON

# 方式三：kube-prometheus-stack 自带 Grafana dashboards（K8s 场景直接抄）
# https://github.com/prometheus-community/kube-prometheus-stack
GitOps 工作流：开发在 UI 调好仪表盘 → Export JSON → PR 进 Git → CI 校验（jq empty *.json 查语法 + grafana-toolkit 或脚本查 schema）→ 合并 → 部署工具同步 JSON 到 Grafana 的 provisioning 目录 → Grafana 热加载。关键纪律：allowUiUpdates: false，否则 UI 会成为第二个事实源，漂移不可避免。
坑库

九个线上坑

1
变量下拉框是空的或依赖变量不刷新
子变量（instance 依赖 job）没设 Refresh = On dashboard load，初次打开时 $job 还是默认值，查询不到数据。变量 Refresh 三档要理解：On dashboard load / On time range change / On variable change，依赖链上的变量都要能触发刷新。
2
时间窗口与 rate 窗口不匹配，曲线不平滑
时间范围选 30 天，查询写 rate(x[5m]) —— Prometheus 只回原始点，rate 窗口内样本不足，曲线出现锯齿假象。rate 窗口 ≥ 4 倍采集间隔；大时间范围用 $__rate_interval 或查 recording rule。
3
高基数序列拖垮浏览器，面板转圈几分钟
查询返回几千条曲线，浏览器渲染 + JS 计算直接卡死。服务端限制：topk(20, ...)、sum by 聚合、label filters；面板端限制：Max data points 调小、曲线超过 20 条就拆面板。
4
直接用 $__interval 写 rate，窗口太短出空值
$__interval 在大时间范围下可能大于采集间隔好几倍，也可能等于采集间隔本身。rate 窗口一律用 $__rate_interval（Grafana 自动取 max($__interval, 4×scrape)），这是官方推荐做法。
5
容器里 URL 写 localhost，数据源连不上
Grafana 容器内 localhost 指向自己。用 compose 服务名或主机 IP。Save & test 显示 connection refused 时先查这个。
6
仪表盘全靠 UI 手点，服务器重装后全丢
没有 Provisioning、没有 Git 备份，仪表盘是单点资产。至少把 dashboard JSON 导出进 Git，配合 allowUiUpdates: false 防止漂移。
7
面板 repeat 一个变量出来 100 个面板
变量有 100 个实例，repeat by instance 直接渲染 100 个面板，页面卡死。repeat 控制在 20 个以内，超出用 Table 面板展示，或引入变量筛选。
8
时区混乱：服务器 UTC、团队在东八区
Grafana 默认浏览器时区，团队跨地域时同一张图对不齐。Dashboard settings → Timezone 显式设为团队所在时区；Prometheus 存储的是 UTC 时间戳，Grafana 只负责显示转换。
9
刷新间隔太短 + 重查询，Prometheus 被打满

自测

六道题

1. 想在一个 Table 面板里同时展示每个实例的 QPS 和错误率（两个不同查询），应该用？
正确答案：Join by field。两个查询各自返回带 instance 标签的结果，Transform 的 Join by field 按 instance 横向拼成一张表。or 连接的是序列不是字段；两个面板则失去了同行对比能力。
2. 写 rate() 时，Grafana 官方推荐的时间窗口变量是？
正确答案：$__rate_interval。它是 max($__interval, 4×scrape_interval)，专门为 rate 设计，避免窗口太短导致样本不足。$__interval 服务于图表下采样，$__range 是总时间范围。
3. 关于 Grafana Unified Alerting 与 Prometheus 告警的关系，正确的是？
正确答案：互补。Prometheus rules 有 Git 版本管理、promtool 单测、recording rule 预计算；Grafana 告警的优势是任何数据源（SQL/Loki）都能配、离仪表盘近。同一个告警两边都配会收到重复通知。
4. 一个面板要按 instance 变量重复渲染，但该变量有 200 个取值，最佳做法是？
正确答案：Table 或变量筛选。repeat 200 个面板会让浏览器卡死，Grafana 也不会自动分页。经验红线是 repeat 不超过 20 个；需要看全量对比时，Table 面板一行一个实例才是正解。
5. Heatmap 面板显示空白，最可能的原因是？
正确答案：数据格式不对。Heatmap 需要直方图数据（_bucket 序列或原生直方图），喂普通 Gauge 序列会得到空白面板。这是新手最常误判为"面板坏了"的假象。
6. 防止 Grafana 仪表盘被 UI 随意改掉、保证 Git 是唯一事实源，应该配？
正确答案：allowUiUpdates: false（UI 修改不持久化）+ disableDeletion: true（UI 删不掉）。全员 viewer 会挡住正常编辑需求；只读文件系统连 provisioning 都加载不了。

Data SourceGrafana 查询的后端：Prometheus、Loki、SQL 数据库等

Panel单个可视化单元，由查询 + 类型 + 配置构成

Transform查询返回后的浏览器端数据处理（JOIN/聚合/重命名）
Join by field按共同字段横向拼接多个查询结果
Heatmap热力图面板，需要 histogram bucket 数据
Unified AlertingGrafana 8+ 的统一告警系统，9.0 起默认

Contact point通知渠道：Email/Slack/钉钉/Webhook 等
Notification policy按 label 路由告警到联系点的策略树
Mute timing周期性静默时间窗，如每晚维护窗口不告警
Provisioning用 YAML/JSON 文件预配置 Grafana，替代手点 UI
Providerdashboards.yml 里声明仪表盘 JSON 的加载来源
