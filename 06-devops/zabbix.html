开始前

起一个能练的环境

# 最快的实验方式：Docker 全家桶（server + web + agent）
# 1. 先起数据库
docker run -d --name zabbix-db \
  -e MYSQL_ROOT_PASSWORD=rootpw \
  -e MYSQL_DATABASE=zabbix \
  -e MYSQL_USER=zabbix \
  -e MYSQL_PASSWORD=zabbixpw \
  mysql:8.0 --default-authentication-plugin=mysql_native_password

# 2. 起 server（容器间用容器名互联）
docker run -d --name zabbix-server --link zabbix-db:mysql \
  -e DB_SERVER_HOST=mysql \
  -e MYSQL_USER=zabbix -e MYSQL_PASSWORD=zabbixpw \
  -e MYSQL_DATABASE=zabbix \
  -p 10051:10051 \
  zabbix/zabbix-server-mysql:alpine-6.4-latest

# 3. 起 web（默认账号 Admin / zabbix）
docker run -d --name zabbix-web --link zabbix-db:mysql --link zabbix-server:zabbix-server \
  -e DB_SERVER_HOST=mysql -e MYSQL_USER=zabbix -e MYSQL_PASSWORD=zabbixpw \
  -e MYSQL_DATABASE=zabbix -e ZBX_SERVER_HOST=zabbix-server \
  -p 8080:8080 \
  zabbix/zabbix-web-nginx-mysql:alpine-6.4-latest

# 4. 在被监控机上装 agent 并指向 server
apt install zabbix-agent2
sed -i 's/^Server=.*/Server=192.168.1.10/' /etc/zabbix/zabbix_agent2.conf
systemctl restart zabbix-agent2

模块 1

架构：Server / Proxy / Agent 怎么分工

Zabbix 是 C 写的 server + PHP 写的 web 前端 + Go 重写的 agent 2。核心思想：server 决定"采什么"，agent 负责"给数据"。

组件职责关键事实
Zabbix Server调度采集、评估触发器、执行动作、写数据库C 编写，依赖 MySQL/PostgreSQL，是唯一"大脑"
Zabbix Proxy代替 server 采集一片区域，本地缓冲有独立数据库。跨公网/跨机房/大规模分层必用
Zabbix Agent被监控机上的采集器，按 key 返回数据被动模式监听 10050
Zabbix Agent 2同上，但用 Go 实现，内置插件支持 MySQL/Redis/Docker/Nginx 等插件，代码更少
Java Gateway专门采集 JMX监听 10052，server 通过它问 JMX
Web 前端配置、看图、告警管理PHP + Nginx/Apache，本身不采集数据

端口速记

端口方向用途
10051agent/proxy → server主动模式数据入口（trapper）。proxy 也从 10051 接收 server 配置
10050server → agent被动模式采集端口，server 主动来问
10052server → gatewayJMX 采集（Zabbix Java Gateway）
161 / 162双向SNMP 查询 / SNMP trap 接收
443 / 80用户 → webWeb 界面
数据流一句话：被动模式是"server 打电话问 agent"（server 要能连到 agent）；主动模式是"agent 每隔 N 秒打电话给 server 汇报"（agent 要能连到 server，NAT 后面也能用）。跨公网、大规模场景用 Proxy 缓冲，server 挂了 proxy 还能继续存数据，恢复后补传。
模块 2

概念体系：监控项 / 触发器 / 动作 / 模板

Zabbix 的对象层级是：模板 → 主机 → 监控项 → 触发器 → 动作。模板是复用的最小单位，改模板等于改所有挂它的主机。

对象作用与要点
主机组 Host group主机的逻辑分组，权限和动作条件的基本单位（如"生产环境-Linux 机房 A"）
监控项 Item一条待采集的数据，由 key（如 vm.memory.size[pavailable]）+ 类型 + 更新间隔组成
触发器 Trigger对监控项求值得到 OK / PROBLEM 的表达式，带严重性等级
动作 Action事件（如触发器报警）发生后做什么：发消息、执行远程命令、升级
模板 Template监控项/触发器/图/LLD 的打包。支持嵌套模板（一个模板挂另一个模板）
值映射 Value map把数字翻译成文字：0→"正常"、1→"宕机"。不配值映射，图上是裸数字
维护窗口 Maintenance一段时间内停止该主机的告警和动作，但数据照常采集
宏 Macro变量。{$CPU.UTIL.CRIT} 是用户宏（模板级可覆盖），{#FSNAME} 是 LLD 宏

监控项类型（type）怎么选

类型适用场景
Zabbix agent被动模式，server 主动来拉，最常用
Zabbix agent (active)agent 主动上报，防火墙/NAT 友好，推荐大规模默认
Simple check不需要 agent 的探活：icmppingsec、net.tcp.service[http]
HTTP agent直接 GET/POST 一个 URL，可解析 JSON/XML，监控 API 利器
SNMP agent网络设备、打印机等无 agent 设备
Dependent item依赖另一个主监控项的值，不单独采集（如从 JSON 里抠字段）
Calculated item用已有监控项做算术：last(/host1/key1)+last(/host2/key2)
Zabbix trapper接收 zabbix_sender 推来的数据，自定义脚本推送用

触发器严重性（severity）

# 从低到高 6 档，数字直接用在表达式里
0 Not classified  未分类      # 默认值，慎用，会让筛选失效
1 Information     信息
2 Warning         警告        # 如磁盘 80%
3 Average         一般        # 如 CPU 90%
4 High            严重        # 如服务宕了
5 Disaster        灾难        # 如核心数据库不可用
新手最常犯：所有触发器都挂"未分类"。后果是告警升级、动作条件、报表全都没法按严重性分流。模板里的触发器一律显式指定严重性，这是团队协作的基础。
模块 3

触发器表达式：误报的根源在这里

语法骨架：{主机:监控项.函数(参数)} 运算符 阈值。支持 and / or / 括号，支持 K/M/G 和 s/m/h/d 单位。

常用函数

函数含义
last()最近一个值。瞬时值，最容易被毛刺打脸
avg(5m) / avg(#5)5 分钟均值 / 最近 5 个值均值。防误报首选
max(1h) / min(5m)时间窗口内最大 / 最小值
sum(10m)窗口内求和（流量累计场景）
nodata(5m)5 分钟没有收到任何数据，agent 挂了比业务指标先知道
change()最近两个值不同就为真，适合状态位跳变
diff()最近值与上一个值不同（change 的严格版）
delta(1h)1 小时内的变化量（计数器差值）
strlen()>10字符串长度，判断返回值是否为空/超长
band(mask)按位与，适合多状态位一个整型返回的设备
# ===== 真实表达式示例 =====

# 1. CPU 空闲时间 5 分钟均值低于阈值（模板宏，可在主机级覆盖）
{Template_OS_Linux:system.cpu.util[,idle].avg(5m)}<{$CPU.IDLE.MIN}

# 2. 内存可用率低于阈值 10%，持续 5 分钟
{Template_OS_Linux:vm.memory.size[pavailable].avg(5m)}<10

# 3. 磁盘使用率超 90%（LLD 自动发现的文件系统，{#FSNAME} 是发现宏）
{Template_OS_Linux:vfs.fs.size[{#FSNAME},pused].last()}>90

# 4. 网卡入流量超过 100MB/s
{Template_OS_Linux:net.if.in[eth0].avg(5m)}>100M

# 5. agent 5 分钟无数据（配合正常触发器用，能发现"采不到"而非"值异常"）
{Template_OS_Linux:agent.ping.nodata(5m)}=1

# 6. 多条件组合：CPU 高且内存可用低，才算高危
({Template_OS_Linux:system.cpu.util.avg(5m)}>90 and \
 {Template_OS_Linux:vm.memory.size[pavailable].avg(5m)}<15)

# 7. 计数器类：最近一小时重启次数变化
{Linux:system.boottime.delta(1h)}>0

恢复表达式（recovery expression）

# 问题表达式：avg(5m) > 90
# 恢复表达式：avg(5m) < 80   ← 故意留 10% 的回差（hysteresis）

# 没有回差会发生什么？CPU 在 90 附近抖动时，
# 触发器会不停 OK→PROBLEM→OK→PROBLEM，每次翻转都是一条告警
# 这叫"告警抖动（flapping）"，是告警疲劳的第一大来源
三条铁律：
① 能 avg(5m) 就别用 last()。瞬时尖刺是真实存在的（GC、日志刷盘），但凌晨把你叫醒的成本更高。
② 高低阈值分开写，用恢复表达式留回差。
③ nodata 必须单独配。业务指标正常不代表采集链路正常，agent 挂了指标全部"静止"，不配 nodata 你永远不知道。
模块 4

自动发现与 LLD 低级别发现

"发现"要解决的是：主机数量、磁盘分区、网卡、数据库表都是动态的，不可能为每块盘手写监控项。Zabbix 有三层发现机制。

三层发现机制

机制发现什么产物
Network discovery按 IP 段扫描存活主机/服务扫描到的主机可以自动加入 Zabbix 并绑定动作指定的模板
Agent auto-registration主动模式的 agent 首次连上 server 时自报家门自动注册主机，通常配合"条件 → 绑定模板 + 加入主机组"的动作
LLD（低级别发现）主机内部的动态实体：磁盘、网卡、systemd 服务、数据库表发现规则定时执行，按返回的 JSON 自动批量生成监控项/触发器/图原型

LLD 的 JSON 协议

发现规则的原理：执行一个返回 JSON 的 key，JSON 里列出所有实体和它们的宏，Zabbix 为每个实体克隆原型。

# 自定义发现规则，执行：vfs.fs.discovery 的返回长这样
{
  "data": [
    { "{#FSNAME}": "/",        "{#FSTYPE}": "ext4" },
    { "{#FSNAME}": "/data",    "{#FSTYPE}": "xfs" },
    { "{#FSNAME}": "/boot",    "{#FSTYPE}": "ext4" }
  ]
}

# 于是你写一次原型监控项，{#FSNAME} 会被替换成 / /data /boot
# 一块新盘挂上来 → 下一次发现自动多出 3 个监控项 + 2 个触发器
# 盘被卸载 → 自动清理掉对应实体（默认保留 30 天可配置）

内置 LLD key（开箱即用，优先用）

vfs.fs.discovery发现文件系统，宏 {#FSNAME} {#FSTYPE}
net.if.discovery发现网卡，宏 {#IFNAME}，注意排除 lo 和 bond 的 slave
systemd.unit.discovery发现 systemd 服务，宏 {#UNIT.NAME}
sensor.discovery发现温度/风扇传感器，宏 {#SENSOR}
diskarray.discovery / ceph.*.discovery存储阵列、Ceph 集群的官方 LLD 模板
# 自定义 LLD：用 UserParameter 返回 JSON，发现所有 Nginx 的 server 块
UserParameter=nginx.server.discovery,awk '/server_name/{print $2}' /etc/nginx/conf.d/*.conf | sort -u | \
  awk 'BEGIN{printf "{\"data\":["} {printf "%s{\"{#SERVER}\":\"%s\"}",(NR>1?",":""),$1} END{print "]}"}'

# 用 Python 写更稳（JSON 转义不会出错）
UserParameter=app.queue.discovery,python3 /etc/zabbix/scripts/queue_discovery.py
LLD 的两个大坑：① 发现间隔别设太短（默认 1 小时足够），发现规则本身也消耗采集资源；② 发现宏里带特殊字符（如盘符 /mnt/a b）会让 JSON 出错，自定义 LLD 一定要用 json.dumps() 而不是字符串拼接。
模块 5

Zabbix agent 2 与主动 / 被动模式

维度被动模式 passive主动模式 active
连接方向server → agent:10050agent → server:10051
谁定时server 的 poller 按 item 间隔来问agent 每隔 RefreshActiveChecks 来拉一次列表
防火墙要求server 要能访问所有 agent（跨 NAT 很痛苦）agent 出站即可，NAT/公网场景唯一选择
server 压力每台 agent 占一个 poller 连接，量大时 poller 是瓶颈agent 自己批量汇报，server 压力小得多
适用小规模、内网、需要即时配置下发的场景中大规模默认推荐，Zabbix 官方模板默认也走主动

agent 2 配置文件要点

# /etc/zabbix/zabbix_agent2.conf
Server=192.168.1.10            # 允许谁做被动检查（逗号分隔，别图省事写 0.0.0.0/0）
ServerActive=192.168.1.10      # 主动模式上报给谁
Hostname=web-node-01           # 必须和 Web 界面里配置的主机名完全一致！
RefreshActiveChecks=120        # 每隔多少秒来拉一次要采集的 item 列表
BufferSend=5                   # 数据缓冲几秒再打包发，削峰
LogFile=/var/log/zabbix/zabbix_agent2.log

# agent 2 的杀手锏：内置插件，不用 UserParameter 也能采
Plugins.Mysql.Sessions.MySQL=zabbix:zabbixpw@tcp(127.0.0.1:3306)/zabbix
Plugins.Redis.Uri=tcp://127.0.0.1:6379
Plugins.Docker.Endpoint=unix:///var/run/docker.sock
# 然后直接用 mysql.datadir.size / redis.ping / docker.container.info 等 key
主动模式第一大坑：Hostname 不一致。agent 上报时用 Hostname 找自己在 server 上的配置，界面上叫 web01、agent 里写 web-node-01，结果就是"配置已同步但没有任何数据"。日志里能看到 host [web-node-01] not found。养成用 DNS 名或 Ansible 统一注入 Hostname 的习惯。
模块 6

自定义监控项：UserParameter

官方 key 覆盖不了的，用 UserParameter 把任意 shell 命令包装成监控项。返回值只支持数字或字符串，超时默认 3 秒。

# /etc/zabbix/zabbix_agent2.conf 里追加

# 1. 无参数：返回值必须单行
UserParameter=mysql.ping,mysqladmin ping | grep -c alive
UserParameter=service.nginx,systemctl is-active nginx

# 2. 带参数 [*]：请求 key 里的参数按位置映射 $1 $2 ...
UserParameter=port.listen[*],ss -ltn | grep -c ":$1 "
# 调用：zabbix_get -k port.listen[8080]

# 3. 多参数
UserParameter=file.line.count[*],wc -l < $1
# 调用：file.line.count[/var/log/nginx/access.log]

# 4. 磁盘 inode 使用率（百分比，整数）
UserParameter=vfs.fs.inode.pused[*],df -P $1 | awk 'NR==2{gsub("%","",$5);print $5}'

# 5. 外部脚本（推荐把复杂逻辑放脚本，配置里只留一行）
UserParameter=app.orders.pending,python3 /etc/zabbix/scripts/pending_orders.py
UserParameter=app.queue.depth,redis-cli -h 127.0.0.1 llen orders:queue

自测与推送

# server 上测某个 key（agent 机器上也能跑 zabbix_agentd -t key 自测）
zabbix_get -s 192.168.1.20 -p 10050 -k "port.listen[8080]"

# 主动推数据给 server（trapper 类型 item，适合低频自定义指标）
zabbix_sender -z 192.168.1.10 -s web-node-01 -k app.orders.pending -o 128

# 批量推（文件格式：主机 key 值）
zabbix_sender -z 192.168.1.10 -i /tmp/data.txt
三条军规：① 输出必须单行——awk 忘了 print 结束条件多打一行空行，agent 会报 Unsupported item key / value format error；② 命令必须幂等且快，超时（默认 3s，Timeout= 可调）的 key 会被 agent 杀掉；③ key 名遵守官方命名空间（业务.对象.属性），否则模板导出后和别人冲突。
模块 7

告警媒介、升级机制，以及和 Prometheus 的分工

动作与升级

动作 = 条件 + 操作。条件按触发器严重性、主机组、事件标签（event tag）组合；操作可以是发消息、远程命令、再发一条消息。

机制说明
媒介 Media typeEmail（SMTP）、短信（网关脚本）、钉钉/企微/飞书 Webhook、电话语音。脚本型媒介就是把告警内容作为 stdin 传给脚本
升级 Escalation没人处理就逐级加码：0min 通知值班 → 30min 通知主管 → 2h 通知总监。每步可指定不同用户组
恢复操作触发器恢复时自动发"已恢复"消息。不配的话值班永远不知道问题好了没
更新操作问题持续期间按周期重复通知（acknowledged 后停止）
抑制 Suppression基于时间的定时静默（如"每天凌晨 2 点批量任务期间不告警"）
确认 Ack值班在界面点"已知晓"，升级停止、消息里带确认人。事故复盘的核心数据
# 典型动作条件设计（生产环境）
条件1：触发器严重性 >= 高（High）
条件2：主机组 属于 "生产环境"
条件3：事件标签 不包含 "maintenance"   # 给不想告警的触发器打标签过滤

操作：
  步骤 1（立即）→ 发送消息给 "oncall" 用户，媒介：企业微信
  步骤 2（30 分钟后仍未恢复）→ 发送消息给 "sre-leader"，媒介：短信 + 电话
  步骤 3（2 小时后仍未恢复）→ 发送消息给 "cto"

恢复操作 → 发送消息给 "oncall"：问题已恢复，持续了 X 分钟

与 Prometheus 的定位差异

维度ZabbixPrometheus
采集模型agent 推送 / server 拉取，agent 协议HTTP 拉取 /metrics， exporter 生态
配置方式Web 界面 + 模板（可 YAML 导出版本管理）纯 YAML + 服务发现，GitOps 友好
数据模型主机 → item，带业务语义指标名 + label，多维模型，PromQL 很强
告警内置动作/升级/媒介，开箱即用的完整告警体系Alertmanager（额外组件），灵活但要自己搭
存储关系型数据库（MySQL/PG）自研 TSDB，本地 + 远程存储
强项网络设备、物理机、传统中间件、一体化运维K8s/云原生、动态扩缩容、微服务黄金指标
怎么分工（业界主流实践）：Zabbix 管基础设施层（物理机、网络设备、数据库、中间件、带外管理口），Prometheus 管云原生与业务应用层（K8s、容器、微服务 QPS/延迟/错误率）。两者不互斥：Zabbix 6.0+ 的 HTTP agent 支持 Prometheus 预处理，可以直接抓 exporter 的 /metrics 端点，把 Prometheus 指标汇入 Zabbix 告警体系——这是很多公司"只用一套告警"的落地方式。
模块 8

性能调优：NVPS、housekeeper 与数据库

Zabbix 的性能天花板由两个数决定：NVPS（每秒新增值数）和数据库写入能力。优化方向永远是"少采、晚采、合并采"。

zabbix_server.conf 关键参数

参数默认说明
StartPollers5被动采集的轮询器数量。被动 item 多就加
StartPollersUnreachable1处理不可达主机的 poller
StartTrappers5处理主动模式/agent 上报的接收器
StartDiscoverers1LLD 发现执行器，发现规则多就加
HousekeepingFrequency1每隔几小时跑一次清理。设 1，别设 0
CacheSize32M配置缓存，主机/item 极多时调大
HistoryCacheSize16M历史数据写缓冲，调大可缓解 DB 尖刺
ValueCacheSize8M触发器依赖的值缓存，内存够就调大

容量速算

# NVPS = 监控项总数 × 平均频率（次/秒）
# 例：5000 个 item，平均 30 秒一次 → 5000/30 ≈ 167 NVPS
# 参考值：单 server（8C16G + SSD + MySQL）稳妥线约 3000~5000 NVPS
# 超了就上 Proxy 分层，或者：
#   ① 降低频率：秒级采集 → 30s/1m，NVPS 直接降一个数量级
#   ② 用 Dependent item：一条 master item 采集，多个子项复用（JSON 预处理）
#   ③ 计算监控项代替重复采集

# housekeeper 慢 = DB 无限膨胀。按量设保留策略：
# 管理 → 一般 → housekeeper
#   History 保留        30 天    # 明细数据，量最大
#   Trends 保留         365 天   # 小时聚合，量小
#   Problems/Events     365 天
#   Audits 保留         365 天

# DB 侧配合（MySQL）：zabbix 库按时间分区表，删除旧分区是毫秒级；
# PostgreSQL 可用 timescaledb 扩展（官方推荐）
最常见的性能灾难：默认 90 天 history × 几千个秒级 item。history 表能涨到几百 GB，housekeeper 每天删不完，DB 磁盘 100%，server 卡死。上线第一天就把保留时间、频率、proxy 分层规划好，这是补不回来的债。
排坑

十个线上坑

1
触发器用 last() 导致毛刺误报
凌晨被 CPU 100% 叫醒，上去一看是个位数的瞬时值。持续性指标一律用 avg(5m)，并配恢复表达式留回差。
2
忘了配值映射，图上全是 0/1/2
icmpping、systemctl is-active 这类返回值不配 value map，值班看到图也不知道是活着还是死了。
3
发版期间没设维护窗口
一次发布刷出 200 条告警，值班直接麻木。维护窗口只静默告警不停止采集，发版前 10 分钟设上，是团队纪律。
4
housekeeper 默认配置，DB 一年涨到 800G
History 默认 90 天，但没人根据量调整。history 表太大时 DELETE 单行删会拖垮 DB，应按天/月分区后整分区 DROP。
5
主动模式 Hostname 与界面主机名不一致
agent 日志里 host not found，数据一条不来。主机名大小写、空格、域名后缀都要严格一致，用 CM 工具统一下发。
6
LLD 发现间隔设成 30 秒，key 数量爆炸
发现规则本身也占采集资源，网卡/分区多的机器会被发现动作反复创建删除 item。默认 1h 足够，只有真正动态的场景缩短。
7
在界面上直接改官方模板
下次升级模板被覆盖，改动全丢；多人改同一模板互相冲突。正确做法：克隆模板 → 改名 → 修改，且用 YAML 导出进 git。
8
Server 与 agent 时间不同步
图表错位、nodata 误报、触发器时间对不上。全链路 NTP/chrony 同步是监控系统的前提，监控自己先被监控。
9
nodata(1m) 设太短，机器重启就误报
开机慢的业务机 2 分钟起不来，nodata(1m) 先报警。nodata 阈值取"采集间隔 × 3 再加 1 分钟"量级，给重启留窗口。
10
权限体系没规划，所有人都是超级管理员
谁都能改触发器、谁能删主机组，出事无法追溯。用用户组 + 主机组权限做读写分离，审计日志（Administration → Audit）每季度看一次。
自测

六道题

1. 主动模式下，agent 把数据发到 server 的哪个端口？
正确答案：10051。10050 是 agent 被动模式的监听端口（server 来问），10051 是 server 的 trapper 端口（主动上报进来），10052 是 JMX Java Gateway。
2. 想检测"agent 挂了、5 分钟没有任何数据上报"，应该用哪个表达式？
正确答案：nodata(5m)。agent 挂了以后 last() 根本不会有新值，触发器停留在最后一次的求值结果上，永远不会触发。nodata 专门判断"多久没收到数据"。
3. LLD 发现规则执行后，agent/脚本应该返回什么格式的数据？
正确答案：JSON。LLD 协议规定返回 {"data":[{宏:值},...]}，Zabbix 用其中的 {#XXX} 宏去替换原型监控项里的同名占位符，从而批量生成实例。
4. 关于被动模式，说法正确的是？
正确答案：server 主动来拉。所以被动模式要求 server 能访问到 agent（跨 NAT 很麻烦）；主动模式反过来，agent 出站即可，更适合大规模和公网场景。
5. CPU 使用率在 90% 附近抖动，告警不停触发又恢复。最合适的解决方式是？
正确答案：均值 + 回差。avg(5m) 过滤毛刺；高低阈值分开写（90 触发 / 80 恢复）留出 10% 回差，避免边界抖动造成 flapping。调严重性治标不治本，缩短间隔只会放大问题。
6. 关于 Zabbix 与 Prometheus 的分工，主流实践是？
正确答案：分层共存。Zabbix 强在一体化（网络设备、物理机、带外、告警升级），Prometheus 强在动态服务发现与 PromQL。Zabbix 6.0+ 还能通过 HTTP agent 直接抓取 Prometheus 端点，把两套指标汇入统一告警。

术语表

术语一句话解释
NVPSNew Values Per Second，每秒新增的数据点数，衡量 Zabbix 规模的核心指标
Pollerserver 里执行被动采集的工作单元，数量由 StartPollers 决定
Trapperserver 10051 端口，接收主动模式上报与 zabbix_sender 推送
Proxy带独立数据库的采集代理，用于跨公网/大规模分层与本地缓冲
LLD低级别发现，按 JSON 协议自动批量创建监控项/触发器/图原型实例
发现宏 {#XXX}LLD 返回的实体占位符，原型里的同名宏会被替换
用户宏 {$XXX}模板级变量，可在主机级覆盖，如 {$CPU.UTIL.CRIT}
值映射 Value map把数字返回值翻译成人类可读文本的映射表
维护窗口定时静默告警与动作的机制，采集不中断
Dependent item依赖主监控项取值、不单独采集的监控项，省采集开销
Calculated item用已有监控项做算术运算的虚拟监控项
nodata()触发器函数，判断一段时间内是否完全没有收到数据
回差 hysteresis问题阈值与恢复阈值之间的缓冲带，防告警抖动
Housekeeperserver 里按保留策略清理 history/trends/events 的后台进程
升级 Escalation告警无人确认时按时间步逐级通知更多人的机制
确认 Ack值班在界面标记已知晓，停止升级并留痕
Auto-registration主动模式 agent 首次连接时自动注册主机的机制
Network discovery按 IP 段扫描并自动添加主机/执行动作的发现规则
Trend每小时聚合的历史数据，量小，适合看长期趋势
UserParameteragent 配置里把 shell 命令包装成监控 key 的指令
