Terraform 的语法一天就能学会，难的是 state 管理、模块边界和重构不炸生产。这篇直接讲声明式模型的本质、远程后端、count/for_each 的资源重建陷阱，以及和 Ansible 怎么分工。

开始前

一个最小可用骨架

# 安装（任选其一）
brew install terraform                  # macOS
choco install terraform                 # Windows
apt install terraform                    # Debian/Ubuntu 官方源

# 验证
terraform version

# 目录骨架（真实生产项目的常见布局）
infra/
├── versions.tf          # required_version + required_providers 版本约束
├── providers.tf         # provider 配置（region、默认标签）
├── backend.tf           # 远程后端（S3 + 锁）
├── main.tf              # 资源定义
├── variables.tf         # 输入变量
├── outputs.tf           # 输出（供人看或供下游用）
├── terraform.tfvars     # 变量取值（含环境差异，prod.tfvars / dev.tfvars）
└── modules/             # 本地模块目录
    ├── vpc/
    └── eks/

# 一条命令看当前这套代码到底要干嘛（不落任何改动）
terraform init && terraform validate && terraform plan
第一次跑一定会卡在 terraform init：它会下载 provider 插件（AWS provider 一个就 500MB+）。国内网络建议配镜像（.terraformrc 或 TF_CLI_CONFIG_FILE 指向镜像站），CI 里用 terraform init -backend=false 先做静态检查。
模块 1

IaC 理念与声明式配置

IaC（Infrastructure as Code）的核心主张：基础设施的状态应该由代码完整描述，代码是唯一事实来源（single source of truth）。Terraform 是其中"声明式"的代表。

范式做法特点
命令式（Imperative）写"步骤"：先建 VPC，再建子网，再建安全组……Ansible、shell 脚本、CloudFormation 的 Custom Resource。灵活，但重复执行结果不确定
声明式（Declarative）写"终态"：我要 3 台 t3.medium 的 EC2Terraform 自己算 diff。幂等：跑 100 次结果一样

声明式带来的三个工程红利

  • 可评审：基础设施变更走 Pull Request，和业务代码一样 review，改了什么一目了然
  • 可复现：用同一套代码 + 不同变量文件，建出开发 / 测试 / 生产三套环境，杜绝"环境差异"
  • 可回滚：git revert 一次提交，再 apply，环境回到上一个已知良好状态
关键认知：Terraform 不管你"怎么建"，只在乎"现在长什么样"和"应该长什么样"的差。所以你不需要在代码里写创建顺序——Terraform 用依赖图（resource → reference 隐式依赖 + depends_on 显式依赖）自动排拓扑序，能并行的并行，不能并行的排队。
模块 2

核心对象模型：Provider / Resource / Data / State

对象角色
Provider与某个云/服务对话的插件（aws、alicloud、kubernetes、helm、random……）。配置的是"怎么连"
Resource要管理的实体，如 aws_instance.web。配置的是"要什么"，Terraform 负责 create/read/update/delete
Data Source只读查询已有实体，如 data.aws_ami.ubuntu。不归 Terraform 管生命周期，每次 plan 都重新读
Variable输入参数，可带 type 校验、默认值、sensitive 标记
Output对外暴露的值（如 RDS 连接地址），供人查看或下游模块/CI 消费
StateTerraform 的记忆：记录"哪些真实资源对应哪段代码、哪些属性上次是什么"
# ===== 一个真实的最小例子：AWS 上一台 Web 机 =====
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"       # 锁大版本，小版本自动升
    }
  }
}

provider "aws" {
  region = var.aws_region
  default_tags {
    tags = {
      Environment = var.env
      ManagedBy   = "terraform"   # 标记归属，防手改误伤
    }
  }
}

# data source：查一个现成的镜像 ID（只读，不创建）
data "aws_ami" "ubuntu" {
  most_recent = true
  owners      = ["099720109477"]     # Canonical 官方账号
  filter {
    name   = "name"
    values = ["ubuntu/images/hvm-ssd/ubuntu-22.04-amd64-server-*"]
  }
}

# resource：创建一台 EC2，Terraform 会记录它的全部属性到 state
resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id          # 引用 data → 隐式依赖
  instance_type = var.instance_type             # 引用 variable → 隐式依赖
  subnet_id     = aws_subnet.public.id
  vpc_security_group_ids = [aws_security_group.web.id]

  user_data = templatefile("${path.module}/userdata.sh", {
    pkg = "nginx"
  })

  tags = { Name = "web-${var.env}" }
}

output "web_public_ip" {
  description = "Web 服务器公网 IP"
  value       = aws_instance.web.public_ip
}
读代码时盯住引用关系：data.aws_ami.ubuntu.id、var.instance_type、aws_subnet.public.id 这三个引用，就是 Terraform 画依赖图的边。改引用目标 = 改依赖 = 可能触发重建，这是后面所有坑的根源。
模块 3

State 文件管理与远程后端

State 是 Terraform 的唯一真相来源：代码描述"终态"，state 记录"现状与映射"。没有 state，Terraform 就不知道哪个真实资源对应哪段代码。

本地 state 的四个风险

  • 没有锁：两个人同时 apply，后写的覆盖先写的，资源双份或配置丢失
  • 不进 git：state 含敏感信息（数据库密码明文），但为了协作又必须共享——死结
  • 丢失即失忆：笔记本硬盘坏了，state 没了，只能 import 重建映射
  • CI/CD 拿不到：流水线跑完 state 留在 runner 容器里，下次跑又是"全新环境"

远程后端（backend）：S3 + 锁

# backend.tf —— 把 state 放对象存储，并加分布式锁
terraform {
  backend "s3" {
    bucket       = "mycorp-tfstate-prod"
    key          = "network/vpc/terraform.tfstate"   # 每个环境/组件一个 key
    region       = "cn-north-1"
    encrypt      = true                       # 服务端加密
    dynamodb_table = "tfstate-locks"          # 经典方案：用 DynamoDB 做锁表
  }
}

# AWS provider 5.x / Terraform 1.10+ 也可以不用 DynamoDB：
# backend "s3" { ... use_lockfile = true }   ← S3 原生条件写锁

# 非 AWS 场景对应物：
#   阿里云 OSS + OSS 锁 / Terraform Cloud / Consul / etcd / HTTP 后端

# 换后端 = 迁移 state，用 init 的 -migrate-state
terraform init -migrate-state -backend-config=prod.backend.hcl

# 看当前后端和全部资源映射
terraform state list
terraform state show aws_instance.web

后端设计的工程原则

原则做法
一环境一 statekey 按 环境/组件 隔离：prod/network/vpc.tfstate。blast radius 最小化
锁必须开远程后端的核心价值不是备份，是并发互斥
加密 + 最小权限开启服务端加密；IAM 策略只允许特定角色读写，禁止公网访问桶
版本化 + 备份开桶的版本控制，误删 state 能回滚；state 永远不进 git
State 里的敏感信息是明文。RDS 密码、AK/SK 全在 state 里躺着，加密只是存储层加密，有读权限的人打开文件就能看到。对策：① 用 KMS 客户管理密钥；② IAM 最小化；③ 敏感值尽量用 data 从 Secrets Manager 读，不在 tfvars 里硬编码；④ 输出也标 sensitive = true。
模块 4

模块化与复用：module、workspace 与目录分离

Module：Terraform 的复用单元

# 调用方：root module
module "vpc" {
  source  = "git::https://git.internal/infra/vpc-module.git?ref=v2.3.1"
  # source 也支持：./modules/vpc（本地）、registry（官方/社区）、OSS/HTTP

  name       = "prod"
  cidr_block = "10.0.0.0/16"
  azs        = ["cn-north-1a", "cn-north-1b"]

  # 模块之间传值用 output
}

resource "aws_instance" "app" {
  subnet_id = module.vpc.public_subnet_ids[0]    # 消费模块输出
}

# 被调用方：modules/vpc/{main,variables,outputs}.tf
# variables.tf 声明入参（可带 validation 校验块）
# outputs.tf   声明出参（output "public_subnet_ids" { value = aws_subnet.public[*].id }）

workspace vs 目录分离：环境隔离怎么选

方案机制问题
Workspace同一套代码，terraform workspace new prod 切 state，代码里用 terraform.workspace 区分所有环境共享一份代码和 provider 配置；prod/dev 差异只能靠 count 技巧绕；prod 和 dev 的变量漂移容易误伤
目录分离
（推荐）		envs/dev/ envs/prod/ 各自一份 root module，各自一个 state key，共同引用 modules/代码有重复，但环境差异显式化，改 prod 不影响 dev，权限也能按目录拆
# 目录分离的真实布局
infra/
├── modules/            # 纯复用逻辑，无环境概念
│   ├── vpc/
│   └── rds/
├── envs/
│   ├── dev/main.tf     # module "vpc" { source = "../../modules/vpc" ... }
│   └── prod/main.tf    # 同 module，不同入参 + 不同 backend key
└── global/             # 跨环境共享资源（如 DNS zone）单独一份

# 模块版本锁定：git ref / registry version，别用浮动分支
source = "git::https://git.internal/infra/vpc-module.git?ref=v2.3.1"
选型结论：多环境用目录分离（生产级项目的默认答案）；workspace 只适合"同一环境的临时实验分支"或开发者本地 sandbox。模块要带语义化版本 tag，升级模块 = 改 ref + 单独 PR review，而不是"一升级全环境跟着动"。
模块 5

工作流：plan / apply / destroy 与漂移检测

init：下载 provider、初始化后端。新克隆的仓库第一步永远是 init
validate：静态检查语法与引用，不连云。CI 里最先跑
plan：对比"代码终态 vs 现状"，输出将做的增/改/删。+ 创建 ~ 修改 - 销毁 -/+ 先建后删
apply：执行变更。生产必须走 plan 文件：terraform plan -out=tfplan → terraform apply tfplan，保证"批准的就是执行的"
destroy：按依赖图逆序删除全部资源。生产库资源必须加 lifecycle prevent_destroy 挡住
# 标准 CI 安全流
terraform init
terraform validate
terraform plan  -out=tfplan -var-file=prod.tfvars
# ↓ 人工审批 / PR review plan 输出
terraform apply tfplan

# 只刷状态不改资源（探测漂移，不落变更）
terraform plan -refresh-only

# 强制替换某个资源（重建），比老命令 taint 更明确
terraform apply -replace=aws_instance.web

# 只操作指定资源（只建议故障恢复用，日常禁用）
terraform apply -target=module.vpc

# 保存的 plan 是二进制，人能看的用 -no-color 落文件
terraform plan -no-color > plan.txt

漂移（drift）检测

漂移 = 有人在控制台/CLI 手改了 Terraform 管的资源。表现：下次 plan 出现一堆你没写过的"修改"。

场景处理
手改了标签等无害字段lifecycle { ignore_changes = [tags] } 让 Terraform 闭嘴
手改了实例类型等关键配置下一轮 apply 会改回去。要在代码里改，让 plan 说话
控制台建的资源想纳入管理terraform import 或 import 块（见模块 6）
想周期性发现漂移CI 定时跑 plan -refresh-only -detailed-exitcode，退出码 2 = 有漂移，发告警
-target 是糖衣毒药：它只算目标资源的依赖，很容易漏掉间接依赖，产出一个"看起来成功实则状态不一致"的结果。官方文档明说仅供故障恢复。日常排障请全量 plan。
模块 6

import 与 refactor：不重建的前提下改代码

把存量资源收编（import）

# 老式两步：先写 resource 代码，再 import 映射
resource "aws_instance" "web" {
  # 先按真实属性把代码写全，否则 import 后第一次 plan 一堆 diff
  ami           = "ami-0abc123"
  instance_type = "t3.medium"
}
terraform import aws_instance.web i-0abc123def456

# 新式（1.5+）：import 块直接写在代码里，生成配置也自动化
import {
  to = aws_instance.web
  id = "i-0abc123def456"
}
# terraform plan -generate-config-out=generated.tf 可让 Terraform 帮你写出初始配置

重构（refactor）：移动资源而不重建

重命名资源、把资源挪进 module、把 count 改 for_each——这些在旧版本里意味着"先 state rm 再 import"的极限操作。Terraform 1.1+ 的 moved 块让重构变成声明式：

# 场景 1：资源重命名 aws_instance.web → aws_instance.app
moved {
  from = aws_instance.web
  to   = aws_instance.app
}

# 场景 2：把散资源收进模块（地址前缀要带 module.）
moved {
  from = aws_s3_bucket.logs
  to   = module.logging.aws_s3_bucket.main
}

# 场景 3：count 改 for_each（键值保持不变时零重建）
# from 用索引、to 用键，Terraform 只改映射不动真资源
moved {
  from = aws_instance.web[0]
  to   = aws_instance.web["a"]
}

# 反向：代码里删掉了 resource，但不想删真资源
# ① terraform state rm aws_instance.web（从 state 除名，资源保留）
# ② 或 1.7+ 的 removed 块：声明"这个资源已不在代码里，也别销毁它"
removed {
  from = aws_instance.legacy
  lifecycle { destroy = false }
}
重构三原则：① 先 moved 后改代码，一次重构一个动作，plan 确认 0 变更再下一步；② 永远不在两个 PR 里同时重构同一块；③ 大规模重构前 terraform state pull > backup.tfstate 手动备份。
模块 7

与 Ansible 的分工

两者不是竞争关系：Terraform 管"基础设施生命周期"，Ansible 管"机器内部配置"。分界线是"资源创建/销毁"与"软件安装/配置文件"。

维度TerraformAnsible
管什么VPC、子网、EC2、RDS、LB、DNS、IAM、K8s 集群软件包、系统参数、配置文件、用户、服务状态
模型声明式 + state，幂等靠 diff 计算声明式任务，幂等靠模块自身设计
连不进去怎么办不关心机器内部，只调云 API需要机器已存在且可 SSH
典型时序先跑：把机器、网络、数据库建出来后跑：用 Terraform 产出的 IP/连接信息进场配置

经典组合：Terraform 产出 → Ansible 消费

# Terraform 侧：把新机器信息渲染成 Ansible inventory
resource "local_file" "inventory" {
  filename = "${path.module}/inventory.ini"
  content  = templatefile("inventory.tftpl", {
    hosts = aws_instance.web[*].public_ip
  })
}

output "web_ips" {
  value = aws_instance.web[*].public_ip
}

# ===== provisioner 能用，但请当作最后手段 =====
resource "aws_instance" "web" {
  # ...

  provisioner "local-exec" {
    # 机器建好后，本地触发一次 ansible-playbook
    command = "ansible-playbook -i inventory.ini site.yml --limit ${self.private_ip}"
  }
}

# 更云原生的做法：不用 provisioner，把配置烧进 user_data / cloud-init，
# 或让 CI 在 terraform apply 成功后单独跑 ansible。这样 Terraform 侧零 SSH 依赖。
为什么 provisioner 是反模式：① 它执行失败会把资源标记为 tainted，下次重建——一次 SSH 超时毁掉一台生产机；② provisioner 只在创建时跑，更新镜像后老机器不会重新配置；③ 它要求 Terraform 到机器的网络可达，把"云 API 工具"拖进"配置管理"的泥潭。正确分层：cloud-init 管首次引导，Ansible 管持续配置。
模块 8

常见坑与防御性写法

多云 Provider 与版本管理

# 同一套代码跨云：provider 是插件化的，换云≈换 provider 资源前缀
terraform {
  required_version = ">= 1.5.0"
  required_providers {
    aws        = { source = "hashicorp/aws",        version = "~> 5.0" }
    alicloud   = { source = "aliyun/alicloud",      version = "~> 1.200" }
    kubernetes = { source = "hashicorp/kubernetes", version = "~> 2.20" }
    helm       = { source = "hashicorp/helm",       version = "~> 2.10" }
    random     = { source = "hashicorp/random",     version = "~> 3.5" }
  }
}

# .terraform.lock.hcl 必须提交进 git —— 它锁的是 provider 二进制校验和，
# 保证每个人、每条流水线下载到的 provider 一模一样
terraform providers lock -platform=linux_amd64 -platform=darwin_arm64

循环依赖与 count / for_each 的坑

# 循环依赖：A 引用 B 的属性，B 又引用 A 的属性 → "Cycle error"
# 解法：把公共输入（如 VPC ID）提成 variable 或用 data source 查，打断环

# count 的索引陷阱：列表删掉中间一项，后面全部"位移"→ 连锁重建
resource "aws_instance" "web" {
  count = length(var.subnets)
  # var.subnets 从 ["a","b","c"] 变成 ["a","c"]
  # → web[1] 从子网 b 挪到 c，web[2] 被销毁 → 看起来"删一个毁两个"
}

# for_each 按 key 寻址，删一项只动那一项
resource "aws_instance" "web" {
  for_each = var.instances        # map 或 set，不能用 list
  subnet_id = each.value.subnet
  tags      = { Name = "web-${each.key}" }
}

# 删除即重建：改不可变属性（如 aws_instance 的 ami）→ 先删后建
# 想零停机先建后删：
lifecycle {
  create_before_destroy = true
  prevent_destroy       = true       # 生产数据库必加
  ignore_changes        = [tags["LastScan"]]
}

敏感变量与调试

# 标记敏感：plan/apply 输出里显示 (sensitive value)
variable "db_password" {
  type      = string
  sensitive = true
  # nullable + validation 双重保险
  validation {
    condition     = length(var.db_password) >= 16
    error_message = "密码至少 16 位。"
  }
}

# 环境变量注入，绝不出现在命令行历史里
export TF_VAR_db_password=$(vault kv get -field=password secret/prod/db)
terraform apply

# 出问题时的日志（调试完记得降级，DEBUG 日志巨大）
TF_LOG=DEBUG terraform apply 2>&1 | tee tf-debug.log
TF_LOG_PATH=/tmp/tf.log terraform plan          # 落盘，不刷屏
版本约束用 ~> 不用 >=：~> 5.0 允许 5.x 任意小版本、锁死大版本；>= 5.0 会让半年后的 6.0 悄悄进来，把你的配置炸掉。升级大版本 = 单独 PR + 单独 state 备份 + 灰度环境先跑。
排坑

十个线上坑

1
用本地 state 多人协作
两个人同时 apply，state 互相覆盖，资源双份或配置丢失。第一天就上远程后端 + 锁，这是 Terraform 工程化的分水岭。
2
state 文件提交进了 git
state 里 RDS 密码、AK 全明文，进 git 等于进所有开发者的电脑和 CI 日志。.gitignore 必须屏蔽 *.tfstate 和 .terraform/。
3
锁冲突就 force-unlock
force-unlock 是给"持锁进程确定已死"的场景用的。流水线还在跑你强开锁，两个 apply 并发写 state，事故瞬间翻倍。
4
用 count 管理一批机器，删列表中间项
count 按索引寻址，删中间项导致后面全部位移重建。实例类资源一律 for_each + map/set，键稳定，删一个只动一个。
5
在控制台改 Terraform 管的资源
产生漂移，下次 plan 出现一堆意外 diff，有人手一滑 apply 回去，把控制台的紧急修复也覆盖没了。改可以，改完同步回代码。
6
生产 RDS 没加 prevent_destroy
一次 terraform destroy -target 误操作或模块重构，数据库直接蒸发。production 级别的有状态资源必须 lifecycle prevent_destroy = true。
7
重度依赖 provisioner 做配置
SSH 超时一次资源就被标记 tainted 重建，update 时 provisioner 又不重跑，配置悄悄过期。用 cloud-init + Ansible 替代。
8
循环依赖，A 引用 B、B 引用 A
plan 直接报 Cycle error。根因是共享输入被互相引用。把公共值提成 variable 或用 data source 查询，依赖图立刻变 DAG。
9
敏感变量没标 sensitive
密码出现在 plan 输出、CI 日志、同事的终端录屏里。variable 和 output 都要标，注入走 TF_VAR_ 环境变量或 Secrets Manager。
10
provider 版本写 >= 且不提交 lock 文件
半年后一次 apply，新大版本 provider 改了 schema，全量 plan 报错甚至误改资源。用 ~> 锁大版本，.terraform.lock.hcl 必须进 git。
自测

六道题

1. 两个人同时 terraform apply 报 "Error acquiring the state lock"，正确的处理是？
正确答案：先确认再强解。锁存在说明有并发。force-unlock 只用于持锁方确定已死的场景；改本地 state 更是倒洗澡水把孩子倒掉——丢掉了锁保护。
2. var.subnets 从 ["a","b","c"] 改成 ["a","c"]，用 count 创建的 3 台实例会发生什么？
正确答案：索引位移导致连锁重建。count 按位置寻址，删中间项后 web[1]、web[2] 的内容全错位。for_each 按 key 寻址就没有这个问题——这就是生产代码优先 for_each 的原因。
3. 远程后端（S3 + 锁）解决的核心问题是？
正确答案：共享 + 锁。远程后端的本质是把 state 变成团队共享且并发安全的单一事实来源，本地 state 做不到这两点，与性能成本无关。
4. 关于 provisioner，业界共识的定位是？
正确答案：最后手段。provisioner 失败会污染资源（tainted 重建）、只在创建时执行、还要求 Terraform 到机器的网络可达。正确分层是 cloud-init 引导 + Ansible 持续配置。
5. 想把 aws_instance.web 重命名为 aws_instance.app 且不重建机器，最佳做法是？
正确答案：moved 块（1.1+）。直接改名会被判定为"删旧建新"；state rm + import 是老式手工体操，容易出错。moved 声明只改映射不动真资源。
6. 多环境（dev/staging/prod）隔离，社区主流推荐哪种？
正确答案：目录分离。环境差异显式、state 隔离、权限可拆。workspace 共享代码与 provider 配置，prod/dev 变量容易误伤，只适合临时实验。
